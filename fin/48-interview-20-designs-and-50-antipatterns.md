## 48.1 从事故到十分钟答题框架

### 合成教学事故：同一笔钱穿过四个错误边界

**以下事故完全虚构，不对应任何已证实机构或历史损失。**
设系统接受一笔 1,000.00 CNY 支付，内部金额为 100,000 分，渠道 A 与 B 都支持扣款。

| 时间 | 合成事件 | 被破坏的边界 |
|---|---|---|
| 10:00:00 | A 已扣款，返回包丢失 | 把传输结果当作经济事实 |
| 10:00:02 | 调度器把超时改为失败，向 B 新建扣款 | 意图身份被重试拆成两笔 |
| 10:00:03 | B 成功，A 回调也到达；两条分录都入账 | 缺少经济事实唯一键 |
| 10:01:00 | 旧主恢复，继续处理退款任务 | 租约过期后没有写入端 fencing |
| 次日 | 对账只比较汇总净额，重复收款与退款互相抵消 | 总额平衡掩盖逐笔差错 |

若 A、B 各扣 1,000.00 CNY，客户额外被扣 1,000.00 CNY；这是额外扣款，不自动等于平台最终净损失。
若随后两台退款 worker 各退款 1,000.00 CNY，则客户净支出为零，商户原应收的 1,000.00 CNY 出现缺口。
上述缺口尚未计手续费、追偿和拒付，不能把不同阶段的暴露直接相加作为最终损失。
止血顺序是暂停新增副作用、隔离旧主、保留在途义务、原键查单，再以新操作退款并逐笔复核。
不能直接删除重复流水、把全部 UNKNOWN 批改失败，或让模型“判断哪笔是假单”。

### 十分钟不是背组件，而是交出可证伪的设计

| 时间段 | 必答内容 | 白板交付物 |
|---|---|---|
| 0–1 分钟 | 角色、资产、地区、账户与外部最终性 | 系统边界和明确不做的事 |
| 1–2 分钟 | 成功定义、余额口径、确认边界 | 三条带量词的不变量 |
| 2–4 分钟 | 状态、身份、金额、事务与授权 | 一张状态机和一条资金路径 |
| 4–6 分钟 | 写入次序、幂等、恢复与跨服务一致性 | 正常时序与崩溃切点 |
| 6–8 分钟 | 热点、磁盘、网络、积压、故障域 | 一组可复算容量预算 |
| 8–9 分钟 | 重放、分区、乱序、对账与人工介入 | 故障注入和验收断言 |
| 9–10 分钟 | 取舍、降级、未证实假设 | 限制、监控与追问入口 |

评分建议：边界 15、守恒与权限 25、协议与事务 20、恢复 20、预算与验证 20，共 100 分。
若把超时当确定失败、允许裸改已入账事实，或把模型当最终执行权限，应先纠正红线再讨论分数。
“严格有序”必须说明是账户内、品种内还是全局；“零丢失”必须说明已确认边界与可容忍故障集合。
答题时把**已证明、设计目标、待验证、业务选择**写成四列，避免用产品名冒充证明。

## 48.2 双栈贯通：身份、证据、事务和副作用

### 先共享协议，再决定服务用什么语言

```text
Command = {tenant, operation_id, kind, amount_atoms:"100000", currency:"CNY",
           recipient_id, payload_hash, policy_version, approval_digest}
Evidence = {provider, merchant, provider_ref, event_id, operation_id,
            payload_hash, outcome:SUCCESS|DECLINED|PENDING, final, raw_hash}
Path: proposal -> trusted compiler -> risk/approval -> operation + outbox
      -> adapter -> evidence inbox -> adjudication + ledger + receipt outbox
Replay: same (tenant,operation_id) + same hash => prior receipt or current state
Conflict: same key + different hash => reject and audit; never overwrite payload
```

金额按资产最小单位传十进制字符串；解析器拒绝符号前缀、前导零变体、指数与超界值，再做规范化编码。
哈希绑定租户、意图、动作、金额、币种、收款人、策略与审批域；指定字段顺序、编码版本和字符规范。
`event_id` 是证据去重键，不自动是渠道因果序号；没有渠道版本协议就不能用大小比较裁决事实。
`final` 不是调用方可自填的信任标志：适配器须验证签名、商户、引用、金额及该渠道的最终性定义。

### PostgreSQL 15+ 教学 DDL：本地原子性而非全局魔法

```sql
CREATE TABLE fin_operation (
  tenant text NOT NULL,
  operation_id text NOT NULL,
  payload_hash bytea NOT NULL CHECK (octet_length(payload_hash) = 32),
  amount_atoms numeric(38,0) NOT NULL CHECK (amount_atoms > 0),
  currency text NOT NULL,
  state text NOT NULL CHECK (state IN ('NEW','UNKNOWN','SUCCESS','DECLINED')),
  revision bigint NOT NULL DEFAULT 0 CHECK (revision >= 0),
  PRIMARY KEY (tenant, operation_id)
);
CREATE TABLE fin_evidence (
  tenant text NOT NULL,
  provider text NOT NULL,
  merchant text NOT NULL,
  event_id text NOT NULL,
  operation_id text NOT NULL,
  raw_hash bytea NOT NULL CHECK (octet_length(raw_hash) = 32),
  received_at timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (tenant, provider, merchant, event_id),
  FOREIGN KEY (tenant, operation_id)
    REFERENCES fin_operation (tenant, operation_id)
);
CREATE TABLE fin_outbox (
  event_id text PRIMARY KEY,
  tenant text NOT NULL,
  operation_id text NOT NULL,
  revision bigint NOT NULL,
  event_kind text NOT NULL,
  payload jsonb NOT NULL,
  published_at timestamptz,
  UNIQUE (tenant, operation_id, revision, event_kind),
  FOREIGN KEY (tenant, operation_id)
    REFERENCES fin_operation (tenant, operation_id)
);
```

此 DDL 不是完整业务库：证据验签、原文存储、审批、分录、租约和渠道引用仍需独立表与权限。
证据持久化成功但裁决失败时，worker 必须能再次领取未裁决证据，不能简单“去重后直接返回”。
事务顺序：锁 operation → 校验同键同参 → 读取待裁决证据 → 裁决 → 写唯一凭证/分录 → 更新版本 → 写 outbox。
凭证唯一键至少覆盖租户、操作与经济事件类型；同事务提交，禁止先把状态改成功再异步补账。
借贷按币种平衡需专用入账过程或延迟约束触发器；普通行级 CHECK 不能检查整张凭证的聚合和。
数据库角色限制已入账分录的 UPDATE/DELETE；冲正是新凭证，附原凭证引用而非覆盖历史。

### Go：纯裁决核心，标准库即可编译

```go
package adjudication

import "fmt"

type Evidence struct {
    Binding [32]byte
    Outcome string
    Final   bool
}

// trusted 仅由已完成渠道验签和语义校验的可信适配器设置。
func Decide(current string, binding [32]byte, e Evidence, trusted bool) (string, error) {
    if !trusted || binding != e.Binding {
        return "", fmt.Errorf("untrusted or mismatched evidence")
    }
    switch current {
    case "NEW", "UNKNOWN", "SUCCESS", "DECLINED":
    default:
        return "", fmt.Errorf("invalid current state")
    }
    switch e.Outcome {
    case "PENDING", "SUCCESS", "DECLINED":
    default:
        return "", fmt.Errorf("invalid outcome")
    }
    terminal := current == "SUCCESS" || current == "DECLINED"
    if !e.Final || e.Outcome == "PENDING" {
        if terminal { return current, nil }
        return "UNKNOWN", nil
    }
    if terminal && current != e.Outcome {
        return "", fmt.Errorf("conflicting final evidence: quarantine")
    }
    return e.Outcome, nil
}
```

### Java：相同输入得到相同结果

```java
import java.security.MessageDigest;

final class Adjudication {
    enum State { NEW, UNKNOWN, SUCCESS, DECLINED }
    enum Outcome { PENDING, SUCCESS, DECLINED }

    static State decide(State current, byte[] binding, byte[] evidenceBinding,
                        Outcome outcome, boolean isFinal, boolean trusted) {
        if (current == null || outcome == null || binding == null
                || evidenceBinding == null || binding.length != 32
                || evidenceBinding.length != 32 || !trusted
                || !MessageDigest.isEqual(binding, evidenceBinding)) {
            throw new IllegalArgumentException("invalid or untrusted evidence");
        }
        boolean terminal = current == State.SUCCESS || current == State.DECLINED;
        if (!isFinal || outcome == Outcome.PENDING) {
            return terminal ? current : State.UNKNOWN;
        }
        State next = outcome == Outcome.SUCCESS ? State.SUCCESS : State.DECLINED;
        if (terminal && current != next) {
            throw new IllegalStateException("conflicting final evidence: quarantine");
        }
        return next;
    }
}
```

两段仅是同一正向支付动作的裁决器，不负责 I/O、签名、锁、事务、退款或拒付。
Java 数组在调用边界须做防御性复制或禁止并发修改；Go 的定长数组参数按值传递。
适配器把超时转换为无最终结论的观察，不能伪造一条 `DECLINED + final=true`；缺失证据继续 UNKNOWN。
终态冲突进入隔离队列并保留原状态；查明后以明确的新经济事件处理，不以最后到达者覆盖。
退款、拒付和成交撤销不是“成功变失败”，而是有独立身份和会计效果的逆向业务。
生产集成可选 Go `pgx/v5` 或 Java JDBC/jOOQ；重试范围必须是完整本地事务，不能包住外部扣款。
参考 [幂等](24-end-to-end-financial-idempotency.md) 与 [状态机和 Outbox](25-state-machines-tcc-saga-and-outbox.md)，消息重复投递由消费端唯一约束承接。

## 48.3 手算容量：先算约束，再谈“高性能”

### 假设场景与基础算术

假设高峰接受 20,000 个操作/秒，平均每个本地事务写操作、凭证、分录与 outbox 的逻辑数据共 1.5 KiB。
逻辑写入为 `20,000 × 1,536 = 30,720,000 B/s ≈ 29.30 MiB/s`，不是实际 WAL 吞吐。
若教学估计索引、WAL 和写放大合计为逻辑量的 3 倍，则单副本约 87.89 MiB/s；此倍数必须实测替换。
三个完整副本的总写入预算约 263.67 MiB/s，但复制网络和落盘等待应分别测量，不能相互抵消。
若该高峰持续整天，逻辑数据约 `30,720,000 × 86,400 = 2.654208 TB/日`，TB 按十进制计。
保留 30 天为 79.62624 TB 逻辑数据；冷热分层、压缩、索引和备份副本应单列，不能默认免费。

### 热点账与背压的上限

假设同一热点行的串行临界区平均占用 0.4 ms，则理想上限约 `1 / 0.0004 = 2,500 次/秒`。
这只是无排队、无额外开销时的算术界，不是 PostgreSQL、Go 或 Java 的已证实性能。
若希望单行利用率不超过教学设定的 60%，每个独立桶预算 1,500 次/秒；20,000/1,500 向上取整需 14 桶。
14 桶只是均匀分布的下界；有倾斜和跨桶转账时须重算，且不能把同一可透支额度复制到每桶。
可拆的是已分配的收款缓冲与额度，不是要求全局线性化的同一余额；总账户与子桶必须可核对。
若队列按 20,000 条/秒积压 30 秒，将有 600,000 条；每条含索引和对象开销假设为 512 B，则约 293 MiB。
实际还需预留 GC、批次、序列化和重试空间；队列满时拒绝或限流，不能静默丢弃已确认命令。

### 亿级对账与恢复预算

两侧各 1 亿行、每行规范化后 200 B，输入总量为 40 GB；256 桶平均每桶两侧合计约 156.25 MB。
两小时完成一次只读遍历的最低聚合吞吐为 `40 GB / 7,200 s ≈ 5.56 MB/s`，不包含排序和二次读写。
若文件读取、分桶落盘、排序归并形成合计 3 遍等量 I/O，预算约 16.67 MB/s；倾斜、解压和对象请求另算。
不能因平均桶小就把所有桶载入堆；用流式外排，限制每 worker 内存并记录最大桶而非只看均值。
恢复若要重放 600 万条日志，目标为 60 秒完成，则需至少 100,000 条/秒有效重放吞吐，另加选主与快照装载。
这是一项验收目标而非承诺；稳态压测和恢复压测必须分别执行，并报告 p99、最大积压、错误率及资源水位。

## 48.4 二十道编号设计题：同一套六项交付

每题均按“边界、不变量、方案、故障、验证、追问”作答；以下是展开答案的骨架，不是唯一实现。

### 设计题 01：万级请求下的热点账如何记账？

- **边界**：单币种平台收款汇总户；区分可并行收款与必须原子检查的付款额度。
- **不变量**：每笔凭证按币种借贷平衡；子桶合计等于总账；同一经济事件仅记一次。
- **方案**：稳定哈希分收款缓冲桶，事务内写凭证、分录和 outbox；定时有凭证归集，付款额度单独分配。
- **故障**：桶倾斜、归集重复、锁死锁；保留原键重试本地事务，归集挂账不得直接改总额。
- **验证**：混合并发收付、重复归集与崩溃重放；比较分录重算、桶余额、总账及未归集在途。
- **追问**：同一用户需全额实时可花时还能任意分桶吗？不能，先定义额度所有权和转移协议。

### 设计题 02：撮合热备如何定义“不丢单”？

- **边界**：单品种确定性状态机，三投票副本且最多一个故障；不承诺所有副本同时毁损后恢复。
- **不变量**：对外最终确认的命令属于已提交前缀；同一输入序列产生同一成交序列。
- **方案**：命令定序并复制提交后生效，外发成交带提交索引；快照包含 applied index、规则版本与校验和。
- **故障**：主机在写盘、复制、确认之间宕机；新主只恢复提交前缀，旧主经任期和出口 fencing 禁止继续发单。
- **验证**：逐切点断电、网络分区、快照损坏；校验提交命令、订单簿哈希、成交 ID 和确认回执一致。
- **追问**：本地 fsync 后立刻回“最终成功”够吗？不够，必须说明复制和选主保留这条记录的依据。

### 设计题 03：支付 UNKNOWN 如何收敛且不重付？

- **边界**：渠道支持稳定商户键、查单和回调；对不支持幂等的渠道不自动重发资金请求。
- **不变量**：超时不证明失败；UNKNOWN 期间保留在途义务；换路由不能创造第二个扣款意图。
- **方案**：记录尝试和外部键，按原键查单，验签回调和文件进入证据裁决；设退避、截止点及人工队列。
- **故障**：响应丢失、回调先到、查询暂时查无单；保持未知，不把短期查无单视为永不扣款。
- **验证**：扣款后丢响应、重复回调、迟到成功；断言只接受一次正向事实，外部多付独立登记并退回。
- **追问**：何时可切 B？须有协议级无副作用或撤销完成证据，不能仅靠本地等待时间。

### 设计题 04：部分成交与撤改同时发生怎么办？

- **边界**：OMS 对接外部交易场所；改单是否丧失优先级、是否原子由场所规则决定。
- **不变量**：累计成交不因回报乱序回退；冻结覆盖未完成义务；撤单申请不等于撤单成功。
- **方案**：委托链保留原单与替换单关系，成交按场所 execution ID 去重，依确认后的剩余义务释放冻结。
- **故障**：撤单在途时继续成交、改单被拒、FIX 重发；聚合订单数量状态与逐笔成交，矛盾回报隔离补查。
- **验证**：排列成交、撤单确认与拒绝顺序，检查成交数量、可撤数量、费用及冻结量守恒。
- **追问**：成交撤销如何处理？按场所标识新增撤销或更正事件，不删除原 execution。

### 设计题 05：强平瀑布如何避免自激反馈？

- **边界**：明确线性或反向合约、全仓或逐仓；不把标记价与实际可成交价混为一谈。
- **不变量**：任何减仓命令受仓位版本约束；同一风险义务不能被多个 worker 重复关闭。
- **方案**：可信价格新鲜度门禁、维持保证金计算、分级减仓、带令牌执行；保险基金与 ADL 按公开规则记账。
- **故障**：喂价中断、盘口枯竭、强平回报未知；暂停增险并保留在途减仓，升级人工处置而非无限市价扫单。
- **验证**：跳空、负价格适用品种、相关性突变和重复触发；核算权益、已实现损益、费用及基金分录。
- **追问**：为何不是触发后立即释放保证金？在途平仓未确认，仍有价格、执行和费用风险。

### 设计题 06：7×24 系统怎样不停机日切？

- **边界**：业务日、交易日与价值日分别建模；固定时区、日历版本和截止规则。
- **不变量**：已接受事件的会计归属不可随 worker 处理时间漂移；跨日迟到不得丢账。
- **方案**：受控切换业务 epoch，受理时绑定归属日；封存批次有水位，迟到走调整期或新版本报表。
- **故障**：切换中宕机、时钟回拨、在途外部成功次日到达；按原归属与显式调整规则处理。
- **验证**：切点前后并发和夏令时重复小时，按币种试算平衡，核对旧批次完整性及新批次增量。
- **追问**：UTC 零点就是全球结算日吗？不是，取决于市场、银行截止与会计政策。

### 设计题 07：拆合股与派息怎样批量执行？

- **边界**：公司行动含事件版本、登记日、除权日、支付日与托管方分配政策，不能只看当前持仓。
- **不变量**：资格快照可复现；总分权益可核对；碎股与税费尾差有明确归属。
- **方案**：固定权利快照，按比率生成独立权益分录；税费和现金替代分开，挂单处理遵循场所规则。
- **故障**：托管方更正、冻结仓位、合股不足一股；通过新版本差额调整，不重复跑全量到账。
- **验证**：手算 3:2 拆股及 1:10 合股样本，核对整数股、碎股、成本与现金总分账。
- **追问**：除权参考价能直接写成交易成交价吗？不能，参考调整不是已经发生的成交事实。

### 设计题 08：充值遇到 Reorg 怎样防重复可提现？

- **边界**：链特定确认和最终性策略；不声称等待固定区块数可消除所有重组风险。
- **不变量**：canonical 链上的有效事件才参与可用余额；被孤立事实保留且有反向证据。
- **方案**：存区块哈希与父哈希，定位共同祖先；事件使用链、区块哈希、交易哈希、日志索引标识，分待确认与可用桶。
- **故障**：已入账区块被撤、交易重入新块、深度超窗口；冻结受影响额度，冲正旧事实再接纳新 canonical 事实。
- **验证**：同交易不同块重放、日志索引变动、节点分歧；核对 canonical 余额、冲正引用与未决债务。
- **追问**：客户已经提现怎么办？形成风险暴露与追偿流程，数据库回滚不能追回外部资产。

### 设计题 09：两侧亿级流水如何在窗口内对账？

- **边界**：先固定完整批次、文件清单、时间水位与币种口径；缺文件不是差异已经归零。
- **不变量**：每条源记录可追踪且不被去重误吞；金额相等不能代替身份相等。
- **方案**：校验 manifest 和摘要，规范键后哈希分桶、外排归并；逐笔比较，差异按跨日、手续费、短长款分类。
- **故障**：重复文件、桶倾斜、部分重跑、字段缺失；版本化 staging，完成验证后原子发布结果集。
- **验证**：植入一正一负抵消差异、重复单和迟到单；复算笔数、借贷总额、最大桶及每条差异证据。
- **追问**：哈希相等是否足以认定记录相等？不够，哈希定位后仍比较业务键与关键字段。

### 设计题 10：AI 如何安全下单而不拥有裸执行权？

- **边界**：模型只提交结构化意图；策略、审批、资金与签名服务独立于提示词上下文。
- **不变量**：执行内容必须与审批摘要一致；限额由可信代码和原子预算约束；注入文本不能提升权限。
- **方案**：严格 schema、可信编译器、报价新鲜度与价格带、HITL、稳定操作键；执行后只用已验证回执更新事实。
- **故障**：新闻注入、工具超时、审批后价格漂移、模型换键重试；拒绝未知字段并重新风控，原意图先查单。
- **验证**：污染文档、伪造审批、截断 JSON、并发拆单绕限；检查没有未经授权的副作用和预算泄漏。
- **追问**：温度调为零是否可替代硬风控？不能，输出稳定性不是授权与守恒证明。

### 设计题 11：部分退款和拒付如何避免超退？

- **边界**：区分支付、退款、退回与拒付；约定退款和拒付冲突下的渠道及会计规则。
- **不变量**：累计已退与在途预占不能超过可退额度；每笔逆向操作有独立身份。
- **方案**：锁定退款额度，建立子操作和关联分录；UNKNOWN 退款继续占用额度，回执确认后结转。
- **故障**：退款成功但响应丢失、多个客服同时操作、拒付后退款也成功；登记实际双重出款与追偿，不抹去事实。
- **验证**：对 100.00 元并发申请 60.00 与 50.00 元，检查原子拒绝超额部分及在途额度恢复条件。
- **追问**：退款查无单能立刻释放吗？须按渠道最终性协议，不能只据一次查询。

### 设计题 12：跨币种换汇怎样保守恒？

- **边界**：报价币对、方向、精度、点差、有效期和交收日明确，报价不等于已成交。
- **不变量**：不同币种不直接相加求平；每币种借贷平衡，汇兑差额与头寸可解释。
- **方案**：固定报价快照，经外汇过渡科目分别记两币种；按契约舍入并把尾差写专用科目。
- **故障**：报价过期、单腿交收失败、重复成交回报；保留头寸和未决义务，按协议补偿而非假装原子回滚。
- **验证**：手算 100.00 USD 按 7.1234 兑换得 712.34 CNY，再独立核对费用、头寸及在途。
- **追问**：两腿金额都相等就没有汇率风险吗？不同单位不能比较，交收时差仍可能产生风险。

### 设计题 13：TCC、Saga 与 Outbox 怎么选？

- **边界**：TCC 适合能预留的资源；Saga 补偿是业务动作；Outbox 解决本地状态与消息的原子记录。
- **不变量**：Try、Confirm、Cancel 各自幂等；Cancel 后迟到 Try 不复活；已外部成交不能靠数据库事务撤销。
- **方案**：预留表和分支状态防空回滚、防悬挂；本地提交 outbox，消费者用 inbox 和业务唯一约束承接。
- **故障**：协调器重启、补偿失败、消息乱序；持久化分支事实并巡检重驱，超过边界交人工。
- **验证**：枚举三个动作的重复和乱序，崩溃后恢复；检查预留、可用和已消费总和。
- **追问**：有 Outbox 是否就是跨服务 exactly-once？不是，仍需消费幂等和外部能力约束。

### 设计题 14：百万订阅的行情如何处理断档？

- **边界**：交易事实不可丢，行情允许断连后重建；快照与增量的序号域必须同源。
- **不变量**：客户端只在连续序列上构建有效盘口；缺口时不能继续展示为已同步。
- **方案**：按品种预编码扇出，快照水位后衔接增量，慢消费者有界队列并触发重同步。
- **故障**：重连风暴、增量丢包、快照过旧、客户端回压；限速快照，分层缓存，丢弃失效本地视图。
- **验证**：删除与重复指定序号，注入慢连接；恢复盘口与源簿校验一致，量测队列上限和出口带宽。
- **追问**：为什么不让所有连接无限缓存？内存无界且数据失时，不能保证最终追得上。

### 设计题 15：Omnibus 总分账如何清结算？

- **边界**：平台内部客户明细与托管综合账户分离；明确交易成交、清算义务和交收完成的区别。
- **不变量**：客户总权益与外部资产、应收应付及调整项可桥接；在途券款不能被两次可用。
- **方案**：按账户、市场、币种、交收日轧差，保留逐笔穿透；DVP 或其他机制按外部场所能力建模。
- **故障**：交收失败、节假日差异、券不足或现金不足；建立失败交收池，计提费用并追踪补交收。
- **验证**：成交到交收跨周末样本，总分账、托管报表与未决清单三方核对。
- **追问**：净额为零是否可删原成交？不能，法律义务、费用和审计仍需逐笔证据。

### 设计题 16：提币 nonce 和冷热钱包怎么协同？

- **边界**：地址派生、审批、签名、广播与链上确认分权；应用日志不含私钥或完整敏感材料。
- **不变量**：同一地址的 nonce 分配唯一；提币意图与签名载荷绑定；替换交易不能改变收款经济意图。
- **方案**：持久化 nonce 调度与签名摘要，HSM/MPC 审核目的地和额度；热钱包水位调拨也走独立审批。
- **故障**：广播 UNKNOWN、低费卡住、nonce gap、链重组；按交易族追踪原交易与替换，保留预占。
- **验证**：并发申请、签名后进程崩溃、同 nonce 多哈希与替换被拒；核对链上余额和所有在途族。
- **追问**：RPC 查不到哈希是否未广播？不是，节点视图、传播和交易池保留策略都可能不同。

### 设计题 17：多地域容灾如何防双主？

- **边界**：先选共识仲裁与故障域；异步复制的确认边界不能冒称跨地域零数据损失。
- **不变量**：任一时刻只有持有效 epoch 的写者可产生被接受的副作用；旧主恢复不能复活授权。
- **方案**：多数派选主，数据库和出站执行端校验 fencing token；外部不支持 fencing 时用单一受控出口并限制可用性。
- **故障**：跨区分区、租约暂停、备份落后和误切换；隔离旧出口，证明新主日志水位再恢复写入。
- **验证**：双向断网及旧主长暂停后恢复，检查两端实际副作用；RPO 明确已确认数据与可恢复水位的损失窗口，RTO 明确故障/服务中断的计时起点及业务恢复验收终点，不能从某笔用户确认时刻计时。
- **追问**：拿到 Redis 锁就防双主了吗？不够，过期持有者必须在真正写入或执行点被拒绝。

### 设计题 18：PIT RAG 如何防未来信息泄漏？

- **边界**：研究、风控解释与自动交易分权；区分事件发生时间、公开时间、系统可见时间和修订时间。
- **不变量**：决策时只能使用当时已公开且按数据契约可获得的版本；数值与单位可追溯。
- **方案**：双时间版本存储，检索先按 as-of 权限过滤再排序；计算交给确定性算子并输出引用定位。
- **故障**：财报重述覆盖旧值、数据晚到、模型预训练记忆泄漏；保留旧版本，盲测与隔离评测限制污染。
- **验证**：加入未来修订和同名单位陷阱，对同一历史时点重跑；核对召回版本、算术和引用支持关系。
- **追问**：时间过滤后回测就可信了吗？不能，还要考虑幸存者偏差、交易成本和模型记忆污染。

### 设计题 19：AML 调查怎样可解释且不泄密？

- **边界**：模型辅助取证和起草，确定性规则及授权人员决定限制与申报；法律口径按地区审核。
- **不变量**：风险结论能回溯到证据与规则版本；账户隐私按最小权限隔离；调查不能凭空补事实。
- **方案**：结构化规则、受控图查询和证据包，字段脱敏，检索与导出均审计，报告事实与推断分栏。
- **故障**：同名误报、图关系污染、提示注入或越权查询；隔离不可信内容，人工复核并保留申诉路径。
- **验证**：已标注样本、同名实体、跨租户查询和敏感字段外泄测试；分别度量漏报、误报及证据覆盖。
- **追问**：模型置信度高是否可代替证据？不能，概率分数不是身份匹配或法律事实。

### 设计题 20：Paper Trading 如何成为上线门禁？

- **边界**：仿真是实验，不是成交承诺；规定撮合、延迟、费用、借券和数据可见性假设。
- **不变量**：历史不可见数据不能参与决策；同一配置和事件流可复跑；每次放量有审批及回退条件。
- **方案**：记录数据版本、策略摘要与随机种子，模拟排队和部分成交；离线、影子、受限试运行逐级评审。
- **故障**：忽略冲击、过拟合、WORM 配置失效、回执与模型记忆不一致；限制规模并以真实回执修复状态。
- **验证**：样本外、压力与故障回放，抽查审计包重建决策；检查止损开关、撤权与在途清理。
- **追问**：回测收益好是否可以跳过审批？不能，统计表现不能证明权限、实现或合规安全。

| 39 | 补录文件覆盖旧文件 | 使用不可变文件版本和摘要，差额调整并标记替代关系。 |
| 40 | 公司行动直接乘当前持仓 | 固定资格时点与事件版本，单独分配碎股、税和现金替代。 |
| 41 | N 个确认就是绝对安全 | 按链最终性和业务暴露分层入账，设置重组冻结与深重组升级路径。 |
| 42 | 充值只认 Transfer 事件名 | 核验链、合约地址、事件编码、收款地址及 token 实际语义。 |
| 43 | 广播失败便复用 nonce 发别的款 | 追踪原意图交易族，先核查链和交易池，替换保持同一经济意图。 |
| 44 | session 过期会撤销 allowance | 分别撤销会话、模块与授权，追踪撤权交易最终性和在途调用。 |
| 45 | 仿真通过就允许任意调用 | 固定状态和字节，检查资产及权限差；仍用目标、方法和额度硬限制。 |
| 46 | RAG 把最新财报用于历史时点 | 按公开时间、可见时间和版本作 as-of 过滤，保留修订前内容。 |
| 47 | 提示词写“不可越权”就够了 | 模型无执行凭据，工具代理做强类型白名单、权限交集和原子额度检查。 |
| 48 | HITL 点过同意即可随意改单 | 审批绑定载荷摘要、报价及期限，参数或风险变化触发重新审批。 |

## 48.6 测试与验收：让每句设计都有反例入口

### 最小双栈契约测试向量

| 当前状态 | 证据及条件 | Go / Java 一致预期 |
|---|---|---|
| NEW | 可信、同摘要、PENDING、非最终 | UNKNOWN；不产生成功分录 |
| UNKNOWN | 可信、同摘要、SUCCESS、最终 | SUCCESS；事务层只记一次 |
| SUCCESS | 重复最终 SUCCESS | SUCCESS；回放原凭证和回执 |
| SUCCESS | PENDING 或非最终 DECLINED | 保持 SUCCESS；不降级 |
| SUCCESS | 最终 DECLINED | 冲突错误；隔离证据，不改原终态 |
| 任意合法状态 | 错摘要或不可信来源 | 拒绝；无业务副作用 |

Go 测试应覆盖全部状态×结果×final×trusted，并增加非法状态和非法 outcome；Java enum 排除未知枚举但须测试 null。
上述是验收要求；涉及凭证和事务的断言仍待集成验证，不能把纯函数编译通过写成数据库或渠道集成已通过。
本次在 Go 1.19.8 / javac 17.0.21 编译片段，枚举 96 组合法状态、结果、最终性、信任与摘要匹配组合，双栈结果与预期一致。
该检查未覆盖全部非法输入，也未执行 PostgreSQL DDL、渠道集成或目标 Go 1.24+ / Java 21+ 环境验收。
共同性质：相同输入结果相同；重复终态证据不增记；未可信输入不可改变事实；终态冲突不静默覆盖。
输入摘要包含金额并不替代算术测试：另测 int64 边界、numeric(38,0) 边界、标度和舍入残差分配。

### 事务和恢复矩阵

| 注入点 | 必须观察的行为 | 判失败条件 |
|---|---|---|
| 分录写入后、本地提交前 kill | 全回滚或完整提交，可原键重试 | 成功状态存在但无平衡凭证 |
| 提交后、outbox 发送前 kill | 恢复后发送同一事件 | 消息永久缺失或产生第二凭证 |
| 渠道扣款后丢响应 | UNKNOWN、保留义务、原键查单 | 自动切渠道或直接解冻 |
| 旧主停顿超过租约再恢复 | 写入与出站均拒绝旧 epoch | 仍有被接受的外部副作用 |
| 对账中断后重跑同批次 | 同版本可恢复，发布一次 | 重复差异、漏记录或旧结果被覆盖 |
| 已审批意图修改收款人 | 摘要不符，重新审批 | 沿用旧批准继续执行 |

压测先报告数据分布、读写比、账户倾斜、消息大小、硬件、软件版本和副本布局，再给吞吐与分位数。
分别测试稳态、突发、长尾、节点故障及恢复；只报平均延迟会隐藏超时与队列发散。
资金验收至少核对凭证平衡、余额重建、预占义务、渠道事实和未决差异五个集合，不只是 HTTP 成功率。
停机、暂停 AI 与撤销授权不等于清空在途；演练要追踪到所有操作已收敛或明确移交人工责任人。

## 48.7 术语正名与自检答案

| 术语 | 本章使用的准确含义 |
|---|---|
| 不变量 | 在定义边界和合法状态迁移中始终成立的性质，不是“通常没出事”。 |
| 幂等 | 同一逻辑操作重复处理不增加经济效果，须指明作用域和保留期。 |
| UNKNOWN | 缺乏确定业务结论；不是失败、成功或可以无条件重试的别名。 |
| 线性化点 | 并发操作可视为瞬时生效的位置；不是任意一条日志打印时间。 |
| 提交与应用 | 共识提交表示日志被安全接受；应用表示状态机已执行，两者应分别追踪。 |
| fencing | 资源或出口拒绝旧世代持有者；仅在客户端检查租约不够。 |
| RPO / RTO | 可接受的数据损失窗口 / 恢复服务目标；需说明故障模型及测量起止点。 |
| 对账 / 平账 | 前者发现并解释差异；后者是授权后的调整，不能靠改数字掩盖原因。 |
| Finality / Reorg | 前者依链协议和风险策略定义；后者改变 canonical 历史，不能用应用 ACK 消除。 |
| PIT / HITL | 前者限制当时可见数据；后者是对确定载荷的授权流程，不是聊天里的泛化同意。 |

### 自检 A：重付与退款怎么记风险？

问题：一笔应付 1,000.00 CNY，A、B 均扣款，只有 B 已确认入内部账；客户究竟多付多少，账本要不要忽略 A？
**答案**：客户额外支付 1,000.00 CNY；A 的外部成功必须入差异和待退义务，不能因内部没有记录就否认事实。
退款应以独立操作绑定需退的外部款项，核对退款在途、手续费及最终回执；最终净损失需另算。

### 自检 B：14 个桶能保证 20,000 TPS 吗？

问题：按 0.4 ms 临界区、60% 利用率算出 14 桶，是否已经证明系统容量？
**答案**：没有；它只是均匀负载下的算术下界，还缺倾斜、跨桶事务、WAL、网络、索引、锁等待与恢复测试。
若业务余额不可拆，增加桶可能只是复制了额度；必须先证明分配额度之和不超过总额度。

### 自检 C：最终成功之后收到最终失败怎么办？

问题：回调 SUCCESS 已入账，查单又返回 DECLINED，是否让较新的结果覆盖？
**答案**：不能按抵达时间覆盖。保留原事实并隔离冲突，检查渠道版本、引用、金额、最终性与拒付语义。
若实为拒付或更正，创建对应新事件；若前次错误入账，经授权冲正，不删除原凭证。

### 自检 D：快照、WAL 和模型解释能证明什么？

问题：有快照、日志哈希链和模型生成的事故说明，是否足够证明完整可恢复且可合规上线？
**答案**：不能；快照须能衔接提交日志，哈希链须有受信锚点与保留控制，模型说明须逐项引用可信证据。
还需恢复演练、权限审计、法规适用性审核与外部事实核对；三种材料都不是实盘保证。
