## 46.1 引子：三起「锁还在、旧主人还在写」的事故

分布式锁有一个和缓存穿透、消息重复完全不同的气质：**它坏掉的时候，系统里没有任何一个组件会报错。** 锁服务认为自己删对了，新主人认为自己抢到了，旧主人认为自己还持有——三方都对，数据错了。下面三起事故分别长在三条线上：**过期判定**（事故一）、**时钟与进程停顿**（事故二）、**选主后的撤权**（事故三）。

### 事故一：锁在 6.9 秒前就过期了，旧主人还在把内存快照刷回库存表（2026-01-18）

某电商的库存服务用一把手写 Redis 锁防超卖：`SET lock:sku:8812 <uuid> NX PX 3000`（TTL 3 s），拿到锁的实例执行「读库存 → 校验 → 写回」；写回语句是**绝对值覆盖**（`UPDATE stock = ? WHERE sku = ?`，值来自进程内存里的一份快照）。大促期间这个热点 SKU 峰值扣减 **320 次/s**，单实例 JVM 堆 16 GB、G1。

| 时刻 | 事件 | 关键数字 |
| --- | --- | --- |
| 11:02:07.100 | 实例 inv-3 抢到锁，开始批量同步：把内存里 200 个 SKU 的库存快照逐条写回 | 临界区均值 210 ms |
| 11:02:08.400 | 晋升失败触发 Full GC（大量订单对象涌入老年代） | 停顿 **8.6 s** |
| 11:02:10.100 | Redis 侧 TTL 到期，key 被惰性/定期删除 | 比 GC 结束早 6.9 s |
| 11:02:10.150 | inv-6 在同一毫秒内抢到锁（`SET NX PX` 只花了 0.3 ms），开始自己的读-改-写 | 锁的所有权已换人 |
| 11:02:17.000 | inv-3 GC 结束。**它没有任何办法知道锁已经易主**，于是继续执行剩下的 140 条写回 | 140 条覆盖写 |
| 11:02:17.0–11:02:19.8 | 两边同时写同一批 SKU：inv-6 扣减、inv-3 用 GC 前的旧快照整值覆盖 | 双写窗口 **2.8 s** |
| 11:02:19.8 | inv-3 最后一条写回提交（`unlock` 那一步才失败并打了条 warn，没人看） | 静默 |
| 11:05 | 运营发现某 SKU 卖出量比实物多；导出 binlog 比对，约 **7.2 秒**窗口内完成的 2,300 余次扣减被旧快照抹掉 | 超卖 2,300 余件 |
| 复盘 | 大促差价 + 客诉赔付 + 人工拣货核销 | ≈ 84 万元 |

**这起事故的关键不是「GC 太长」，而是那个 2.8 秒**：从 GC 结束到旧主人写完手头批次，它一直在写一张它**已经没有资格写**的表。加长 TTL 只会把 8.6 秒的事故推迟到 12 秒的那次 GC；换 ZK 只会把「TTL 到期」换成「session 过期」，形状一模一样（[37 ZooKeeper vs etcd](37-zookeeper-vs-etcd.md) §37.5 已经把这个判据拆过一遍）。唯一能从根上解决的是：**让写回这条 SQL 自己知道「我是第几任主人」，并且拒绝过期的主人。**

### 事故二：Redlock 在 5 节点上「成功」了两次，中间隔着一次 7.8 秒停顿（2026-02-11）

某支付公司的对账任务用 Redlock（5 个**互相独立**的 Redis 实例，无复制、无协调）保证「同一账期只跑一次」。TTL 10 s，有效期按 `ttl − 加锁耗时 − 漂移补偿` 计算（参考实现的漂移系数是 `ttl × 0.01 + 2 ms`）。

| 时刻 | 事件 | 关键数字 |
| --- | --- | --- |
| 02:00:00.000 | 节点 A 在 5 个实例中的 4 个上 `SET NX PX 10000` 成功，自认有效期约 9.85 s | quorum 4 ≥ ⌈5/2⌉ |
| 02:00:00.200 | A 所在 VM 被宿主内存超分触发 ballooning + swap；随后 NTP 做了一次 `−1.8 s` 的**阶跃**（配置里关掉了 slew） | 停顿 **7.8 s**，墙钟还退了 1.8 s |
| 02:00:10.100 | 5 个实例各自按自己的时钟让锁到期 | 它们的钟前进了 10 s，A 的只前进了 6.2 s |
| 02:00:10.300 | 节点 B 用同样算法在 3 个实例上成功，开始跑对账 | **第二次加锁也「正确」** |
| 02:00:08.100（A 的钟） | A 恢复执行，它的 `validUntil` 还没到，于是继续跑同一账期 | A 视角：锁有效 |
| 02:00:10.3–02:03:40 | 两个进程同时生成差异表并同时写 `recon_diff`，索引里没有幂等键 | 双跑 3 分 32 秒 |
| 03:12 | 财务发现差异表行数是同期的 2.03 倍，重复行 12.4 万条 | 潜伏 71 分钟 |
| 复盘 | 冲正 + 人工核销 + 工时 | ≈ 46 万元 |

**多数派算术一次都没算错。** 出问题的是三件事的合取：① Redis 的 TTL 用**各实例自己的墙钟**；② 客户端的「有效期」是它**自己墙钟**上的区间；③ 进程在停顿期间，墙钟照走、而它什么都做不了。Redlock 的漂移补偿用的是 `ttl × 1%`，而真实环境里一次 NTP 阶跃、一次 VM 快照恢复、一次容器热迁移，跳的是**秒级**。§46.5 会把这条论证逐条展开。

### 事故三：网络分区 4 分 12 秒，两个 master 同时给同一批分片派活（2026-03-02）

某调度平台用 etcd（3 节点跨两机房 2+1）做 leader 选举：`/scheduler/leader` + lease TTL 15 s。leader 的唯一职责是给 600 个分片分配「这一轮给谁跑」。

| 时刻 | 事件 | 关键数字 |
| --- | --- | --- |
| 01:20:11 | 两机房链路抖动 + BGP 收敛，机房 B 的 etcd-3 被隔离，A 侧仍有 2/3 | 多数派还在 A 侧 |
| 01:20:26 | A 侧旧 lease 到期、选主完成，scheduler-2 成为新 leader | 换主 15–20 s |
| 01:20:26 | scheduler-1（原 leader，在 B 侧）**连不上 etcd，但也没收到任何「你已不是主」的否定信号**；代码在 watch 报错时只打日志重试，然后按本地缓存的 15 秒旧分片表继续派活 | 旧主未撤权 |
| 01:20:26–01:24:38 | 两个 leader 各自把同一批分片派给各自的执行器；执行器侧无 term 校验、无幂等键、写入用覆盖式 `UPSERT` | 600 分片 × 2 |
| 01:24:38 | 分区恢复，scheduler-1 收到 lease 丢失事件并退出主状态 | 脑裂窗口 **252 s** |
| 01:24:40 | 两批结果互相覆盖 `result` 表，3,800 个任务出现重复终态 | 3,800 个任务 |
| 复盘 | 重复扣款 1,900 笔、对账重跑 2 天 | ≈ 62 万元 |

**共识协议完全正确——它保证了「不会有第二个被多数派承认的主」。** 但它保证不了「旧主不再举手」：旧主在自己的网络里活着、自己的内存里有分片表、自己的定时器还在跑。**从协议视角看，这叫「已卸任」；从数据视角看，它还在写。** 而挡住它的工具不是更强的共识，是**任期（term）**：如果每次写都带 `term`，存储侧只接受不小于已见 `term` 的写，scheduler-1 的 252 秒就是 252 秒的**被拒绝日志**，而不是 1,900 笔重复扣款。

> 🩸 **三起事故的共同形状**：事故一是**过期判定是单方面的**（服务端按自己的钟宣布你死了，而你还在写）；事故二是**时间本身不可信**（多节点锁的「有效期」建立在有界时钟漂移这个前提上，而生产环境不提供这个前提）；事故三是**失去资格的人没有被告知，也没有被数据面挡住**。三件事的根是同一句话：**锁服务能给的只有「此刻我认为你可以进」，它给不了「你进入之后仍然可以写」。** 后半句只能由**被写的那个存储**来给。

## 46.2 一句话定位与唯一真问题

**定位**：分布式锁不是「协调组件的一个 API」，它是**一个用租约换崩溃恢复的分布式判定问题，其安全边界落在被保护的数据上，而不在锁服务上**。四类实现（Redis key + TTL、ZK 临时顺序节点、etcd lease + txn、进程内 watchdog）解决的都是同一个子问题：「如何让一个进程在一段时间内独占某资源」，而它们**都不解决**另一个子问题：「独占期结束后，那个可能还活着的旧主人如何被挡住」。

### 唯一真问题

> **锁安全不取决于锁服务多可靠，取决于旧主人能不能被挡住，所以 fencing token 才是答案。**

这句话拆成五条推论，全篇都在给它们找证据：

1. **「持锁」= 一个服务端单方面的判定，判据只有「心跳/续租有没有按时到」。** GC 停顿、swap、CPU 限流、VM 迁移、网络黑洞、进程真死，在这个判据上**完全同形**（→ comp/16、[37 ZooKeeper vs etcd](37-zookeeper-vs-etcd.md) §37.5）。所以误判不是 bug，是这套机制的定义域之外。
2. **只要系统是异步的（不能给消息延迟上界），就不存在「本地时钟 + 超时」能证明的互斥。** Redlock 的论证需要「有界时钟漂移 + 无任意长的进程停顿」；这两个前提在生产里恰好最不可靠（§46.5）。
3. **锁的两个用途必须分开定价：`efficiency`（减少重复劳动）与 `correctness`（防止互相破坏）。** 前者允许偶发双执行，后者一次双执行就是数据损坏。**同一个实现不可能同时是最便宜的和最安全的**，所以问题不是「选哪个锁实现」，而是「你先说清你要哪一档」。
4. **能挡住旧主人的位置只有一个：写入路径上的单调比较。** 谁拿着更大的 token，谁的话才算；旧主人手里的 token 一定更小，于是它的写被**存储**拒绝。这个机制不需要旧主人配合、不需要时钟准确、不需要网络对称——所以它是唯一在「旧主人自己都不知道自己已过期」的场景下仍然生效的机制。
5. **因此锁的正确形态是一个三层结构**（§46.3）：L1 原子获取互斥、L2 租约换崩溃恢复、L3 fencing 换误判安全。**只用 L1+L2 的系统，其可用性提升全部被记在「双写风险」这一栏的负债里。**

**它明确不承诺什么**：不承诺「拿到锁就一定互斥」（只承诺服务端视角下的独占）；不承诺「锁的 TTL 内你的进程一定在跑」（停顿是常态）；不承诺「锁服务 failover 后你的锁还在」（Redis 异步复制会丢，ZK/etcd 靠共识不丢但会被判过期）；不承诺「选举出来的主只有一个在服务」（只保证只有一个被协议承认）；不承诺「fencing token 会自己产生」（多数锁 API 根本不给你 token，得自己造，§46.6）。

### 三个「锁服务」卖给你的东西，与它们真实交付的东西

| 广告词 | 真实交付的 | 缺口由谁补 |
| --- | --- | --- |
| 「同一时刻只有一个客户端持有锁」 | 服务端视角下的独占，且在「心跳按时到」的假设内 | L3 fencing（客户端视角的独占永远无法证明） |
| 「持有者崩溃后锁自动释放」 | 崩溃（心跳停）后 TTL/lease 到期自动释放 | 反向风险：**没崩溃但被停顿**的持有者也会被释放 |
| 「锁服务高可用（多副本/多节点）」 | 锁服务的可用性（不因节点故障而不可用） | **与互斥安全无关**：5 个节点的 Redlock 和 1 个节点的 Redis 一样挡不住旧主人 |
| 「自动续租，业务跑多久都安全」 | 把「TTL 太短」换成「业务 hang 住则锁永不释放」 | 临界区超时 + 强制撤锁通道 + TTL 剩余监控 |
| 「Redis 单线程，命令原子」 | 单命令原子 → 一次 `SET NX` 不会两个都成功 | 原子 ≠ 单调：failover 后 `INCR` 可能回退，token 失效 |
| 「ZK/etcd 有共识，绝对安全」 | 共识保护的是**锁服务内部状态**的全序 | 共识保护不了「锁的使用者是否还活着」（事故三） |

### 解剖卡八问落点（本篇答案）

| 问 | 落在哪节 | 一句话答案 |
| --- | --- | --- |
| ① 承诺什么 | §46.2、§46.10 | 承诺「服务端视角的独占 + 崩溃自动释放」，不承诺「旧主人停手」 |
| ② 数据长什么样 | §46.3 | Redis：key + expires dict 里的 TTL；ZK：父节点下的临时顺序子节点；etcd：lease 对象 + 挂在其上的 key |
| ③ 一次读写走哪条路 | §46.3 | 加锁 = 1 次写（Redis 无复制确认 / ZK 一次 ZAB / etcd 一次 Raft，两次 fsync）+ 1 次 RTT 量级 |
| ④ 并发与一致 | §46.5、§46.7 | 多数派只能保证「服务端不会同时发两把锁」；互斥的**客户端侧**证明需要 fencing token |
| ⑤ 扩展维度 | §46.8、§46.10 | **不可横向扩**：同一把锁天生串行；只能「分桶」（按 key 拆锁）或「换形态」（行锁/唯一键/幂等） |
| ⑥ 系统级失效 | §46.11、→ comp/52 | 双写（假活）、脑裂（两个 master）、热点键饥饿（锁永不释放）、协调组件被续租流量打死 |
| ⑦ 看哪几个指标 | §46.12 | 锁等待 P99、续租失败数、TTL 剩余、fencing 拒绝数、`leader_is_primary` 实例数 |
| ⑧ 换掉它的信号 | §46.10 | 单键超过 `1,000 ÷ 持锁毫秒` QPS、锁数量超过租约续租预算、或「双写就赔钱」→ 换行锁/唯一键/幂等 + fencing |

## 46.3 锁的三个层次：互斥、租约、fencing

把「锁」当成一个整体来讨论，是所有争论的起点错误。它至少是三层叠起来的，**每层解决一个不同的失效，且每层都有自己的失效窗口**：

图 1 · 锁的三层结构与各自的失效窗口

```text
┌──────────────────────────────────────────────────────────────────────────┐
│ L3  fencing（单调 token + 存储侧校验）                                    │
│   解决：旧主人还活着、还以为自己持有、还在写                              │
│   手段：每次获取给出严格递增的 token，每次写带上它，存储拒绝 ≤ 已见的写    │
│   失效窗口：≈ 0（只要「token 单调」与「校验是原子的」两条成立）            │
├──────────────────────────────────────────────────────────────────────────┤
│ L2  租约（TTL / session / lease + 续租）                                  │
│   解决：持有者崩溃后锁能自动释放（不然一次崩溃 = 永久死锁）                │
│   手段：SET NX PX / ephemeral / lease TTL；客户端按 TTL/3 续租             │
│   失效窗口：停顿 P > TTL − 续租间隔 时，活人被判定死亡 → 双写              │
├──────────────────────────────────────────────────────────────────────────┤
│ L1  互斥（原子获取）                                                      │
│   解决：同一时刻服务端只把锁发给一个客户端                                │
│   手段：SET NX（单命令原子）/ create 顺序节点（共识定序）/ txn(CAS)       │
│   失效窗口：服务端 failover 丢锁（Redis 异步复制）→ 两把锁同时合法         │
└──────────────────────────────────────────────────────────────────────────┘
        ▲ 只用 L1+L2 的锁 = "efficiency 级" 锁；加上 L3 才是 "correctness 级"
```

### 三层的分工与失效窗口

| 层 | 回答的问题 | 典型实现 | 它的失效窗口 | 失效的后果 | 谁来兜底 |
| --- | --- | --- | --- | --- | --- |
| **L1 互斥** | 「同一时刻会不会有两个持有者？」 | Redis `SET NX PX`、ZK `create` 顺序节点、etcd `txn(create_revision == 0)` | failover：Redis 主从异步复制 → 锁没过去，两边都认为自己独占 | 双写 | 只有 L3 |
| **L2 租约** | 「持有者崩溃了怎么办？」 | key TTL / session timeout / lease TTL + 续租 | 停顿 `P > TTL − h`（h = 续租间隔）→ 活人被开除 | 双写（窗口 = `P − (TTL−h)` + 重连 + 手头批次） | 更长的 TTL 只能降频，L3 才能归零 |
| **L3 fencing** | 「旧主人醒来后还能写吗？」 | 单调 token + 存储侧 `WHERE fence < ?` / `If-Match` / leader epoch | token 不单调（Redis `INCR` failover 回退）或校验非原子 | 被拒绝的写（可观测、可告警）→ 不再是数据损坏 | 无（这就是终点） |

### 一句话判据：你要的是哪一档

| 用途 | 双执行的后果 | 可以用的最便宜形态 | 必须补的 |
| --- | --- | --- | --- |
| **efficiency**：同一报表只让一个实例跑、缓存重建只让一个人做 | 浪费 CPU/带宽，结果一样 | Redis `SET NX PX`（单实例即可） | 无（幂等即可） |
| **correctness**：扣款、发货、库存、账务、分片任务派发 | 数据损坏、赔钱 | 共识存储的锁/lease + **fencing token** | L3 强制 + 对账 |

> **这张表是评审上的第一句话**：先问「双执行的后果是什么」。答「浪费点资源」→ 别再纠结 Redlock 安不安全，用什么都行；答「赔钱」→ 讨论锁实现的性能毫无意义，先确认写入路径上有没有 token 比较。**绝大多数关于 Redlock 的争论，都是把 efficiency 的需求按 correctness 的措辞提出来，然后按 correctness 的价格去还价。**

### 三个层次为什么不能互相替代

- **L1 不能替代 L2**：没有租约，一次持有者崩溃就是永久死锁，你必须人工删锁（Redis 上最常见的土办法就是运维 `DEL`）。所以任何生产锁都带有 TTL——而 TTL 一出现，L2 的误判就必然出现。
- **L2 不能替代 L3**：TTL 越长误判越少，但发现真死越慢，且停顿分布的尾巴没有上界（事故一是 8.6 s，大促当天的另一次是 13.1 s）。**你在和一条没有上界的尾巴赛跑**，这在上篇 §37.9 账一已经算过一次：把阈值从 10 s 提到 30 s，误失效率降一个量级，但永远不会归零。
- **L3 不能替代 L2**：光有 token 而不释放锁，持有者崩溃后资源永久占用。fencing 解决的是**正确性**，不是**可用性**。
- **L3 甚至不能替代 L1**：极端情况下你完全可以不要锁服务——直接让每次写带一个自增版本号做 CAS（乐观锁），冲突就重试。**「没有锁」+「CAS + 单调版本」往往比「锁 + fencing」更便宜**（§46.10 会给出这张减法表）。

## 46.4 物理形态：四种实现，四条物理路径

四种主流实现在「一次加锁」这件事上的物理动作完全不同，**这决定了它们的延迟下限、续租成本在两个量级上分叉**（账三会算它），也决定了它们能不能顺手给出一个单调 token。

| 维度 | Redis `SET NX PX` | ZK 临时顺序节点 | etcd lease + txn | 应用内 watchdog |
| --- | --- | --- | --- | --- |
| 一次加锁的物理动作 | 1 次单机内存写 + `expires` dict 里插一条 TTL | 1 次 ZAB 提交（leader fsync + 显式 COMMIT 广播） | 1 次 Raft 提交（leader WAL fsync + bolt commit） | 无（本地状态机） |
| 加锁延迟量级（同 AZ） | 0.2–0.5 ms（1 RTT） | 1–3 ms（含多数派） | 2–5 ms（含两次 fsync） | < 1 µs |
| 持有判据 | key 存在且 value == 我的随机串 | 我的序号是父节点下最小 | txn 成功且 key 的 lease 未过期 | 本地 volatile 变量 |
| 单方面死亡判定 | TTL 到期（**各实例自己的时钟**） | session 超时（心跳没到） | lease TTL 到期（keepalive 没到） | 无 |
| **租约粒度** | **每把锁一个 TTL** | **每 session 一个超时**（一条连接一次心跳） | **每个 lease 一个 TTL**（可挂多个 key） | 每把锁 |
| 续租的物理动作 | 每把锁一次 `PEXPIRE`（Lua 比较 + 续期） | 心跳**不落盘、不产生事务**，只更新内存 `lastSeen` | 每个 lease 一次 `LeaseKeepAlive`，**每次都是一次 raft 写** | 每把锁一次 |
| 能否给出单调 token | ❌ `INCR` 在 failover 后可能回退 | ✅ `czxid`（epoch 高 32 位 + counter 低 32 位） | ✅ `revision` / 锁 key 的 `CreateRevision` | ❌ |
| failover 时锁的结局 | 可能**丢失**（异步复制，见 → comp/14） | 共识保证不丢，但可能已被判过期 | 共识保证不丢，但可能已被判过期 | 不适用 |
| 最怕什么 | 主从切换 + 停顿 | 大堆 + 长 GC；`cversion` 父节点膨胀 | lease 数量爆炸（账三）、DB 触 quota | 业务 hang 住 → 锁永不释放 |

### Redis：`SET NX PX` 加一把「有 TTL 的旗子」

物理形态极简：`redisDb` 里一个 string key，加上 `expires` dict 里一条 `(key → 到期毫秒)`。两个细节决定了它的全部坑：

1. **TTL 的判定用 Redis 自己的时钟**，删除靠「每 10 Hz 一轮的主动过期采样 + 访问时惰性删除」（Redis 7.x 默认 `hz=10`、每轮采样 20 个带 TTL 的 key，**以目标版本文档为准**）。所以「过期」在物理上不是一条事件，而是一段**最长可达数十毫秒到百毫秒级的区间**；对协调语义而言，这意味着「过期」既不是原子的也不是有序的（→ comp/12、→ comp/14）。
2. **释放必须比较 value**。`GET` 再 `DEL` 是两次命令，中间可能插入「锁过期 → 别人抢到 → 你删掉别人的锁」。所以释放必须是 Lua（单线程内原子）：

```lua
-- KEYS[1] = 锁的 key；ARGV[1] = 加锁时写入的随机串；ARGV[2] = 本次续期毫秒
-- Redis 7.x：EVAL / EVALSHA 均可，脚本内全程单线程原子
if redis.call("GET", KEYS[1]) == ARGV[1] then
  return redis.call("PEXPIRE", KEYS[1], ARGV[2])   -- 续期
else
  return 0                                          -- 已不是我持有，什么都不做
end
```

> 释放只需把 `PEXPIRE` 换成 `DEL`。**这个 `if` 就是「锁的全部身份校验」**——注意它校验的是「值相等」，不是「我是第几任」，所以它救不了「我过期了但还在写数据表」这件事（§46.5）。

### ZooKeeper：临时顺序节点 + 只看前驱

ZK 的锁不是「一个 key」，而是一棵**队列**：所有竞争者在同一父节点下 `create` 一个 `EPHEMERAL_SEQUENTIAL` 子节点，序号来自父节点的 `cversion`（10 位左补零）。持有判据是「我的序号是当前最小的」；否则**只 watch 排在前面那一个**——这是避免羊群效应的关键，如果 watch 父节点，一次释放会唤醒全部竞争者（→ comp/37 §37.9 账二的 1.4 GB/s 就是这么来的）。

```java
// Curator 5.x（Java 17）。核心是"顺序 + 只看前驱"，Curator 已经实现好
public final class SkuLock {
    private final CuratorFramework client;     // 已配置 sessionTimeout，如 10_000 ms
    private final InterProcessMutex mutex;     // 路径 /locks/sku-8812

    public SkuLock(CuratorFramework client, String sku) {
        this.client = client;
        this.mutex = new InterProcessMutex(client, "/locks/" + sku);
    }

    public void runOnce(Duration maxWait, Runnable criticalSection) throws Exception {
        if (!mutex.acquire(maxWait.toMillis(), TimeUnit.MILLISECONDS)) {
            throw new IllegalStateException("acquire timeout: " + maxWait);
        }
        try {
            criticalSection.run();             // 临界区必须自己也有超时
        } finally {
            mutex.release();                   // 只 release 自己的节点，Curator 保证
        }
    }
}
// 想要 fencing token：取该顺序节点的 czxid（Stat.getCzxid()，集群内单调），
// 或另建 /fence/sku-8812 顺序节点取 zxid（§46.6 的来源表；序号本身不可用）
```

**ZK 的租约是 session 级的**：一条 TCP 连接上的一次心跳就够续所有锁，**你持 1 把锁和持 100 把锁的续租成本一样**。这是它在「锁数量多」场景下比 etcd 省钱的根本原因（账三）。

### etcd：lease + txn，把租约做成一等公民

etcd 把「租约」显式建模成一个对象（lease），key 挂在 lease 上；lease 到期 → 一批 key 被删，并产生带 `revision` 的 DELETE 事件。加锁是两步但可以合成一次 txn（`CreateRevision == 0` 表示「这个 key 还从没被创建过」）：

```go
// clientv3（Go 1.21+）。lease 是租约，txn 是"仅当 key 未被创建时写入"
func Acquire(ctx context.Context, cli *clientv3.Client, key, holder string, ttlSec int64) (clientv3.LeaseID, int64, error) {
	lease, err := cli.Grant(ctx, ttlSec)        // 1 次 raft 写
	if err != nil {
		return 0, 0, err
	}
	txn, err := cli.Txn(ctx).
		If(clientv3.Compare(clientv3.CreateRevision(key), "=", 0)).
		Then(clientv3.OpPut(key, holder, clientv3.WithLease(lease.ID))).
		Commit()                                 // 再 1 次 raft 写
	if err != nil || !txn.Succeeded {
		_, _ = cli.Revoke(ctx, lease.ID)         // 抢失败要立刻还租约，别占着
		return 0, 0, fmt.Errorf("lock held or txn failed: %w", err)
	}
	// fencing token 就藏在这里：revision 单调递增，且跨重启/换主不回退
	return lease.ID, txn.Header.Revision, nil
}

// 续租：一条 keepalive 流保一个 lease（注意：每次 keepalive 都是一次 raft 写）
func KeepAlive(ctx context.Context, cli *clientv3.Client, id clientv3.LeaseID, stop <-chan struct{}) {
	ch, err := cli.KeepAlive(ctx, id)
	if err != nil {
		return
	}
	for {
		select {
		case _, ok := <-ch:
			if !ok { // 租约已被判过期：立刻主动停止临界区（撤权第一步）
				return
			}
		case <-stop:
			_, _ = cli.Revoke(context.Background(), id)
			return
		}
	}
}
```

**etcd 的租约是 lease 级的**：一个进程可以只开一个 lease、把 N 把锁都挂在上面，续租成本从 N 次降到 1 次——但代价是**误失效半径被放大**：这个 lease 一次被判死，N 把锁同时消失（§46.11 踩坑第 9 条）。

### watchdog：把「TTL 太短」换成「业务 hang 住则锁永不释放」

Redisson 的看门狗是最常见的「自动续租」实现：加锁成功且未 `unlock` 期间，后台按 `lockWatchdogTimeout / 3` 的节奏续期（Redisson 3.x 默认 `lockWatchdogTimeout = 30_000 ms`，即每 10 s 续一次；**以目标版本文档为准**）。

```java
// 伪代码骨架：看门狗的"续租"与"撤权"是两件必须分开的事
final class Watchdog implements Runnable {
    private final ScheduledExecutorService ses;  // 必须独立于业务线程池
    private final LockHandle lock;               // 含 key、随机 value、TTL
    private volatile boolean stopped;

    public void run() {
        if (stopped) return;
        if (!lock.renewIfMine()) {               // Lua: GET==value 才 PEXPIRE
            stopped = true;                       // 续租失败 = 已不是我：立刻撤权
            lock.onLost();                        // 停任务、上报、拒绝新请求
            return;
        }
        lock.recordTtlRemaining();               // 打点：用于 §46.12 的"TTL 剩余"
    }
}
// 三件事必须同时做，缺一不可：
// ① 续租线程独立于业务线程池（业务排队不能拖住续租）
// ② 续租失败 → 主动撤权（不是重试到成功为止）
// ③ 临界区自带超时 + 运营可强制撤锁（否则业务 hang 住 = 热点键永久饥饿）
```

**看门狗不是「更安全」，它只是把失效形状换了**：TTL 太短 → 双写；TTL 无限续 → 锁永不释放（热点键饥饿，排队长度线性涨，P99 会以「锁等待」的形式爆炸）。这两件事在观测上是**两个不同的指标**（§46.12 的「续租失败数」与「TTL 剩余」）。

## 46.5 Redlock 争议：5 节点、多数派、时钟与停顿

Redlock 是 2016 年前后 Redis 作者提出的多节点锁算法，也是分布式锁讨论里最著名的一桩公案。它的**算法本身是对的**，问题在于它被当成「correctness 级锁」使用时的前提。

### 算法：一次加锁在物理上做完了什么

| 步 | 动作 | 说明 |
| --- | --- | --- |
| 1 | 取当前时间 `T1`（**客户端墙钟**） | 后面所有判断都基于它 |
| 2 | 依次向 N=5 个**互相独立**的 Redis 实例发 `SET key <random> NX PX ttl` | 每实例带**很小的超时**（如 5–50 ms），避免一个慢节点拖死全局 |
| 3 | 统计成功数 `s` | 需要 `s ≥ ⌈N/2⌉+1`（5 节点要 3） |
| 4 | 取当前时间 `T2`，算耗时 `e = T2 − T1` | 用客户端墙钟 |
| 5 | 若 `s < 3` 或 `e ≥ ttl`，向**所有**实例发释放（Lua 比较删除），失败 | 释放要发全部 5 个，不只成功的那些 |
| 6 | 有效窗口 `validity = ttl − e − drift`，`drift ≈ ttl × 0.01 + 2 ms`（参考实现） | 折算「从加锁到用锁」这段的时钟不确定性 |
| 7 | 在 `validity` 内认为持有；到期**必须停手** | 停手靠客户端自觉，没有服务端强制 |

N 个独立实例、不需要复制、不需要协调——这是 Redlock 的设计卖点：**它把「Redis 单点 + 异步复制丢锁」的问题，换成了「多数派交集」的问题。**

```text
图 2 · Redlock 的多数派交集，与它挡不住的那个洞

  客户端 A                                   5 个独立 Redis（无复制、无协调）
  ┌──────────┐        T1=0 ms        ┌────┬────┬────┬────┬────┐
  │ A 的墙钟  │──SET NX PX 10000────▶│ R1 │ R2 │ R3 │ R4 │ R5 │
  │ valid    │        OK,OK,OK,OK   │ ✅ │ ✅ │ ✅ │ ✅ │ ✖  │  s=4 ≥ 3
  │  until   │◀────────────────────└────┴────┴────┴────┴────┘
  │ = 9.85 s │   validity = 10000 − e(130 ms) − drift(102 ms) ≈ 9.77 s
  └──────────┘
        │
        │   A 被 GC / swap / VM 迁移 停顿 7.8 s，期间墙钟照走
        ▼
  ┌──────────────────────────────────────────────────────────────┐
  │ t=10.0 s  5 个实例各自到期（它们的墙钟走满了 10 s）            │
  │ t=10.1 s  B 在 R2、R3、R4 上成功 ⇒ s=3 ≥ 3  ⇒ B 合法持锁        │
  │ t= 8.1 s（A 的钟）A 醒来，它的 validUntil 还没到 ⇒ 继续写数据   │

  └──────────────────────────────────────────────────────────────┘
  多数派交集只保证：同一时刻不会有两个客户端**各自拿到 qourum**；
  它保证不了：A 的"有效期"结束后 A 就真的停手。
```

### 为什么「多数派加锁」仍不能保证互斥

把这条论证拆成可检验的四步（这也是 Kleppmann 那篇 critique 的骨架，此处只取判据，不引原文）：

1. **Redlock 的互斥性证明依赖一个「有界时钟漂移 + 有界进程停顿」的系统假设。** 因为 TTL 由 5 个实例各自按自己的钟判定，而客户端按自己的钟判定「我还有效」，两边要能对得上，就必须假定漂移有上界（`drift` 只是把它折算成一个常数）。
2. **生产环境不提供这个假设。** NTP 会做阶跃（`step` 而不是 `slew`，运维为「快速收敛」关掉 slew 是常态）；VM 从快照恢复会跳时钟；容器被 CPU 限流后墙钟不跳但进程不跑；`CLOCK_MONOTONIC` 在某些虚拟化下 suspend 期间不前进。**一次秒级阶跃就足以让 `drift` 的 1% 假设失效。**
3. **即使时钟完全准确，进程停顿也无法被客户端自证。** 「从加锁成功到实际写数据」之间，进程可能停 8 秒（事故一就是 8.6 秒）。任何「客户端自己算有效期、自己停手」的方案，都要求**被停顿的那个客户端在恢复后立刻知道自己超时了**——而它恢复后的第一件事通常是把缓冲区里的写发出去。
4. **所以正确的判据不是「锁服务够不够可靠」，而是「存储会不会拒绝旧主人」。** Kleppmann 的判据可以压缩成一句话：**如果锁的失效会导致数据损坏，就必须有 fencing token；否则你用的不是一把 correctness 级的锁，只是把「通常互斥」包装成了「互斥」。**

### 五条隐含前提，与它们各自的破法

| Redlock 的隐含前提 | 物理上为什么会被打破 | 打破后的现象 |
| --- | --- | --- |
| 5 个实例的时钟漂移有界，且 `ttl × 1%` 覆盖得住 | NTP 阶跃、VM 快照/热迁移、容器热迁移 | 有效期算长了 → 旧主人还在写（事故二） |
| 客户端进程不会长时间停顿 | Full GC、swap、vCPU steal、宿主超分 | 同上，且它自己不知道 |
| 锁在 `validity` 内不会消失 | 实例**无持久化**重启 → key 丢失，A 仍以为自己持有，B 又能拿到 3 票 | 两个客户端**同时**持有多数派 |
| 节点重启后不会立刻对外服务 | 运维没有「重启后等待至少 ttl」的约定，或用了 `systemd` 秒起 | 同上 |
| 客户端会诚实执行「到期停手」 | 代码路径里没有检查有效期，或检查了但写批量已经提交 | 静默双写 |

> 另外两条常被忽略的工程事实：**Redis Cluster 不能直接跑 Redlock**（多把 key 落在不同节点，且槽迁移会引入额外失败），必须用 5 个独立实例；**Redlock 的加锁延迟是 5 次串行 RTT 或并发 RTT，本身就在 1–10 ms 量级**，它比单实例锁慢一个量级，却没有买到 correctness 级的保证——这正是它争议的核心：**用更高的成本，换来了一个并不能防住目标故障的机制。**

### 争议双方其实在同意的三件事

| 争点 | 主张「Redlock 可用」的一方 | 主张「必须 fencing」的一方 | 实际共识 |
| --- | --- | --- | --- |
| efficiency 场景 | Redlock 够用，单实例甚至就够 | 同意 | **efficiency 场景根本不需要 Redlock**（单实例 + 幂等即可） |
| 停顿问题 | 停顿会让任何锁失效，所以要靠上层补偿 | 停顿正是必须 fencing 的理由 | **停顿必然存在，差别只在有没有 L3** |
| 结论落点 | 在假设成立的系统里，算法是安全的 | 生产环境不提供这些假设 | **算法安全 ≠ 部署安全；部署环境由你负责举证** |

> **一句话总结这一节**：Redlock 不是「错的算法」，是「被放错位置的工具」。**它是一把 efficiency 级的锁；把它当 correctness 级锁用，就等于用 5 个节点的高可用，去替代一个只需要 1 个字段的 token 比较。**

## 46.6 fencing token：让旧主人的写被存储拒绝

fencing token 的机制只有两条，但两条都必须成立：

1. **单调**：锁服务每次「发出一个持有资格」时，同时发出一个严格递增的数（本次 > 所有历史）。它不需要唯一（重复没关系），只需要**取大者胜**。
2. **原子校验在存储侧**：写入必须与「比较 token」在同一条语句/同一次事务里完成；`if (token > last) { write }` 这种应用层两段式不成立——中间有窗口。

```text
图 3 · 一次 fencing 的完整时序：旧主人醒来，被存储挡住

 时间 ──────────────────────────────────────────────────────────────────▶
 锁服务（etcd / ZK / DB 序列）        旧主人 A（token=33）      新主人 B（token=34）      存储（max_fence=34）
 ─────────────────────────────────────────────────────────────────────────────────────────
 t0  ├─ 发锁给 A，token=33 ─────────▶ 开始干活（读快照）
 t1  │                              ✖ 停顿 8.6 s（GC）
     ├─ A 未续租，lease 到期
 t2  ├─ 发锁给 B，token=34 ────────────────────────────▶ 写 stock=997
                                                                        ├─ UPDATE ... WHERE fence<34 ✅ 提交
                                                                        │   max_fence 置为 34
 t3  │                              ▶ 醒来，仍以为持有
     │                                写 stock=1000（旧快照）
     │                                UPDATE ... WHERE fence<33
                                                                        ├─ 0 rows affected ❌
                                                                        │   fence_reject_total += 1
 t4  │                              读到 0 行 → 判定"我已失去资格"
     │                              主动停手、上报、丢弃缓冲
```

**这张图的三个要点**：

- **被拒绝的是一次写，不是一整批任务**。所以 token 必须跟着**每一次写**走，而不是「拿锁的时候校验一次」。
- **旧主人能自己发现**。`affected rows = 0` 是一个它无法忽略的信号——这比「等 `unlock` 抛异常」早得多，也比「等 session 过期事件」早得多。
- **拒绝是可观测的**：`fence_reject_total > 0` 就是「有一个僵尸主人在活动」的**唯一直接证据**（§46.12 的第五个指标）。

### token 从哪来：五种来源，只有三种在生产里单调

| 来源 | 单调性 | 成本 | 关键前提 |
| --- | --- | --- | --- |
| **etcd `revision` / 锁 key 的 `CreateRevision`** | ✅ 跨重启、跨换主单调（Raft 保证） | 0（加锁响应的 header 里就有） | 所有持有者必须从**同一个 etcd 集群**取号 |
| **ZK `czxid`**（锁节点或 `/fence/<res>` 顺序节点的 zxid） | ✅ 单调（epoch 高 32 位 + counter，epoch 变则 counter 归零，整体仍递增） | 0（`Stat.getCzxid()`） | 顺序节点的序号会随父节点重建归零，**不要用序号当 token** |
| **数据库自增序列 / `AUTO_INCREMENT`** | ✅ 单调（单主写） | 1 次写 | 序列的库本身不能多主写；分库要带库号前缀 |
| **Redis `INCR`** | ⚠️ **failover 后可能回退**（从库的 counter 落后于已应答的值） | 1 次写 | 只在单实例、无自动切换时可信 |
| **时间戳（`System.currentTimeMillis()`）** | ❌ 时钟回拨就倒退 | 0 | 不能用（[45 分布式 ID](45-distributed-id.md) §45.4 的回拨问题在这里是安全漏洞，不是 ID 冲突） |

### 存储侧：一条 `UPDATE ... WHERE fence < ?` 就够

```sql
-- MySQL 8.4 / PostgreSQL 15+ 通用的写法：比较与写入在同一条语句里
-- 表上多一列 fence，表示"最后一次被哪一任主人写过"
UPDATE inventory
   SET stock = :new_stock,
       fence = :token,
       updated_at = NOW(6)
 WHERE sku = :sku
   AND (fence IS NULL OR fence < :token);   -- ← 原子 CAS：旧主人的 token 一定更小

-- 判定：affected_rows = 0 有两种含义，必须区分（这是落地时最容易漏的一步）
--   ① 该行不存在            → 业务错误，按缺行处理
--   ② fence >= :token       → "我已失去资格"，立刻停手 + 上报 + 丢弃缓冲
SELECT fence FROM inventory WHERE sku = :sku;   -- 仅用于区分原因，不参与判定

-- 高并发写法（避免读-改-写的绝对值覆盖，进一步缩小事故面）
UPDATE inventory
   SET stock = stock - :delta, fence = :token
 WHERE sku = :sku AND stock >= :delta
   AND (fence IS NULL OR fence < :token);
```

```java
// 中间件/DAO 层的统一入口：把 "带 token 的写" 做成唯一通道，禁止裸 SQL
public final class FencedWriter {
    private final JdbcTemplate jdbc;
    private final Counter fenceRejected;   // Micrometer: fence_reject_total

    public boolean writeStock(long sku, int delta, long token) {
        int n = jdbc.update("""
            UPDATE inventory SET stock = stock - ?, fence = ?
             WHERE sku = ? AND stock >= ?
               AND (fence IS NULL OR fence < ?)
            """, delta, token, sku, delta, token);
        if (n == 0) {
            fenceRejected.increment();
            throw new FencedOffException("token=" + token + " 已被更高任期覆盖");
        }
        return true;
    }
}
// 纪律：① 所有写路径必须经 FencedWriter（用 ArchUnit/静态检查拦住裸 SQL）
//       ② FencedOffException 的处理只有一种：停手 + 上报，绝不重试
//       ③ token 存在 ThreadLocal 里是错的 —— 它会跨任务泄漏，必须显式传参
```

### 其它系统怎么做的：三张现成的答卷

| 系统 | 它是怎么"挡住旧主人"的 | 对你的启发 |
| --- | --- | --- |
| **Chubby**（Google 的锁服务） | 每次授予锁时发一个 **sequencer**（64 位，随锁一起单调递增），存储侧比较 sequencer 拒绝旧写；同时提供「锁延迟」（lock-delay）降低误判概率 | 锁服务**主动给 token** 才是完整设计；只给「你拿到了」是不完整的 API |
| **HDFS HA（QJM）** | JournalNode 只接受 **epoch 不小于当前**的 editlog 写；旧的 NameNode 一旦 epoch 落后，它的写会被拒（并且 `dfs.ha.fencing.methods` 还会尝试把旧 NN 进程杀掉） | 数据面校验（epoch）+ 物理隔离（fencing method）双保险；**杀掉旧主人是最贵的兜底，不是第一选择** |
| **Kafka** | 每个分区有 **leader epoch**，broker 拒绝 epoch 更小的 producer/leader 的写（客户端看到 `FENCED_LEADER_EPOCH`） | 「任期」是 fencing 的一种特化：**选主天然应该带 term，因为共识日志里本来就有它** |

> **一个反直觉的推论**：**共识系统天生自带 fencing（term/epoch 就写在日志条目里），而「锁 API」天生不带**。所以你用 etcd 做选主时，几乎不需要额外设计 token（用 revision / term 即可）；但你用 Redis 做锁时，token 得从别处来（数据库序列、或干脆放弃 correctness 级要求）。这就是为什么「选主」比「锁」容易做对——不是因为选主简单，而是因为它站在共识上。

## 46.7 选主：lease + term、quorum 与脑裂

选主是「锁 + 任期 + 撤权协议」的合体。它和锁的区别只有一条但很致命：**锁保护的是一个临界区，选主保护的是一个持续服务的角色**——角色没有「临界区结束」这个点，所以它必须靠**任期**而不是靠「解锁」来划边界。

### 选主的三件套

| 组件 | 作用 | 物理落点 | 缺了它会怎样 |
| --- | --- | --- | --- |
| **quorum**（多数派） | 保证同一时刻最多一个被承认的主 | Raft/ZAB 的多数派提交 | 分区两侧各选一个 → 双主 |
| **lease / TTL** | 主挂掉后能被替换（不然永久无主） | etcd lease TTL、ZK session timeout | 主进程崩了但 key 还在 → 永久无主，只能人工删 |
| **term / epoch** | 划出「第几任」，让旧任的写被拒 | Raft term、Kafka leader epoch、ZK 的 `czxid` 序 | 旧主仍能写 → 脑裂（事故三） |
| （第四件）**撤权协议** | 主在失去 lease 时**主动**停手（先拒新请求、等在途完成、再退出） | 应用代码 | 旧主"晚一步"停手，窗口内照旧写 |

### 脑裂的真实形状：协议没错，数据面在双写

```text
图 4 · 分区 4 分钟：协议侧只有一个主，数据面有两个

        机房 A（etcd-1, etcd-2）                 机房 B（etcd-3, scheduler-1 旧主）
        ┌───────────────────────────┐          ┌───────────────────────────┐
        │ quorum = 2/3 ✅            │  ✂ 分区  │ quorum = 1/3 ❌            │
        │ lease 到期 → 选主           │          │ 无法续租，但**也没收到**    │
        │ scheduler-2 = 新主 term=8  │          │ 任何否定信号（只能靠超时）  │
        └───────────┬───────────────┘          └───────────┬───────────────┘
                    │ 派活：分片 1..600                      │ 派活：分片 1..600（旧表）
                    ▼                                       ▼
        ┌───────────────────────────┐          ┌───────────────────────────┐
        │ 执行器池（A 侧）            │          │ 执行器池（B 侧）            │
        │ 无 term 校验、无幂等键      │          │ 无 term 校验、无幂等键      │
        └───────────┬───────────────┘          └───────────┬───────────────┘
                    └──────────────┬─────────────────────────┘
                                   ▼
                    结果表 result（UPSERT，谁后写谁赢）
                    → 1,900 笔重复扣款（事故三）
```

**这张图要记住的是**：Raft 把「第二个主」挡在了**协议内部**；但**数据面的写**不经过协议（它们直接写 MySQL/对象存储/Kafka）。所以「协议侧只有一个主」和「数据面只有一个主」是两件事，中间那层必须由 **term 校验 + 幂等**来兜。

### ZK 与 etcd 的 session/lease 语义差异（选主时最要命的一处）

| 维度 | ZooKeeper session | etcd lease |
| --- | --- | --- |
| 绑定的对象 | **一个 TCP 连接**（session id 可由客户端用 id+password 重连接管，但这是危险操作） | **一个 lease ID**（本质是个令牌，任何客户端拿着它都能 keepalive） |
| 谁判定死亡 | 服务端按 `sessionTimeout` 判定（客户端可请求，但被服务端 min/max 钳制） | 服务端按 lease TTL 判定（客户端 `Grant` 时指定） |
| 续租动作 | 连接上的心跳（**不落盘、不产生事务**） | `LeaseKeepAlive`（**每次都是一次 raft 写**） |
| 过期后效应 | 该 session 的**所有临时节点**被一次性删除，watch 触发 | 该 lease 上的**所有 key** 被一次性删除，产生带 revision 的 DELETE 事件 |
| 误失效半径 | session 内所有锁/选主 key（通常=一个进程的全部） | lease 上挂的所有 key（**可以很大，取决于你怎么复用**） |
| 双主风险点 | 用同一个 session id 在两个进程里重连 → 「session moved」并两边都可能以为自己活着 | 两个进程共用同一个 lease ID → **都会认为租约有效**，这是 etcd 最隐蔽的坑 |
| 天然 token | `czxid`（单调） | `revision` / `CreateRevision`（单调） |

> **一句话**：ZK 的租约绑**连接**、etcd 的租约绑**令牌**。绑连接的形态更难被误用（你没法两条 TCP 共享一个 session 而不被服务端发现），绑令牌的形态更灵活但**把安全性交给了使用者**——这也是为什么「共用 lease ID」的代码事故在 etcd 上比 ZK 多见。

### 选主的最小正确骨架（Go）

```go
// 选主 + 撤权的三阶段。关键在第二阶段：失去租约后必须先停新活、再等在途
type Leader struct {
	cli      *clientv3.Client
	key      string        // /scheduler/leader
	leaseTTL int64         // 15 s
}

func (l *Leader) Run(ctx context.Context, serve func(term int64) error, stopNew func()) error {
	sess, err := concurrency.NewSession(l.cli, concurrency.WithTTL(int(l.leaseTTL)))
	if err != nil {
		return err
	}
	defer sess.Close()
	e := concurrency.NewElection(sess, l.key)
	if err := e.Campaign(ctx, "scheduler-2"); err != nil { // 阻塞直到当选
		return err
	}
	// term（任期）：生产实现取 e.Observe() 返回的 kv 的 Revision —— 单调、跨重启有效；
	// 这里用 lease ID 占位只是为了让示例不依赖 Observe 的额外类型
	term := int64(sess.Lease())

	go func() {
		<-sess.Done() // 租约丢失（分区/停顿/被抢占）
		stopNew()     // ① 立刻拒绝新分片派发（不再认领）
		// ② 等在途任务收敛（有上限，如 2×最长任务时长）
		// ③ 退出进程，让编排层重启 —— 不要"自动抢回"，否则抖动放大
	}()
	return serve(term)
}
```

**这段代码的三条纪律**（比代码本身重要）：

1. **`sess.Done()` 之后不许再发新活**。不是「重试到连上为止」，是「立刻停」。事故三的 252 秒就是「重试到连上为止」的代价。
2. **在途任务必须有上限**。撤权窗口 = 你允许跑完的在途时间；这个数写进 SLO，并由执行器侧的幂等兜底。
3. **不要自动抢回**。旧主恢复后重新参与竞选是正常的，但「恢复即认为自己是主」是灾难。

### 选主与锁的关系：一张对照表

| 维度 | 分布式锁 | 选主 |
| --- | --- | --- |
| 保护对象 | 一个临界区（短、有明确结束点） | 一个持续服务的角色（没有结束点） |
| 边界靠什么划 | 解锁 / TTL 到期 | **term**（任期只在换主时变） |
| 谁检查资格 | 通常只有加锁那一刻 | **每一次写都要检查**（term 随写走） |
| 失权的典型后果 | 双写同一批数据 | 双 master 同时服务（脑裂） |
| 正确实现的最小集 | 锁服务 + token + 存储 CAS | quorum + lease + term + 撤权协议 + 幂等 |
| 长尾风险 | 停顿 > TTL → 双写 | 分区/停顿 → 脑裂窗口 = 分区时长 |
| 能否只靠锁服务 | 不能（必须存储侧配合） | 不能（必须数据面校验 term） |

## 46.8 三本账：TTL 与停顿、锁的 QPS 上限、续租流量

三个算例都按「乘法链 + 假设清单 + 量级结论」写，复算脚本与敏感性表在 §46.9。**先说清每本账的用途**：账一算「不加 fencing 你会赔多少」，账二算「锁根本不适合什么量级」，账三算「锁的数量会把协调组件打成什么样」。

### 账一 · 双写损失 = 误失效次数 × 窗口 × 写入速率 × 覆盖比例

| 步 | 项 | 推导 | 结果 |
| --- | --- | --- | --- |
| 1 | 锁 TTL `T` | `SET NX PX 10000` 或 Redisson `lockWatchdogTimeout` 默认值 | 10,000 ms |
| 2 | 续租间隔 `h` | 惯例 `T/3` | 3,333 ms |
| 3 | 误失效的最坏阈值 | `T − h`（停顿紧跟一次成功续租时所需的最小停顿） | **6,667 ms** |
| 4 | 加判定粒度 `g` | Redis 主动过期 10 Hz 采样 + 惰性删除 | 有效阈值 ≈ **6.7–7.2 s** |
| 5 | 一次真实停顿 `P` | 大堆 Full GC / VM 迁移（事故二是 7.8 s，事故一是 8.6 s） | 12.4 s |
| 6 | 单次双写窗口 `W` | `P − (T−h)` + 重连与事件投递 0.4 s + 手头批次 0.8 s | ≈ **6.9 s** |
| 7 | 单实例日误失效次数 | `k × Pr(P > 6.7 s)`，`k=6` 次/天、`Pr≈0.3%` | **0.018 次/天** |
| 8 | 300 实例集群 | `300 × 0.018` | ≈ **5.4 次/天 ≈ 1,971 次/年** |
| 9 | 命中「热点受锁资源」的比例 | 大部分锁保护的是低频任务，按 1/50 计 | ≈ **39 次/年** |
| 10 | 每次损失的覆盖写数 | `W 6.9 s × 20 次/s × 覆盖式比例 25%` | ≈ 34 次覆盖写 |
| 11 | 年期望坏单量 | `39 × 34 × 平均每次覆盖 1.5 件` | ≈ **2,000 件/年** |
| 12 | 折算金额 | 按 60 元/件（差价 + 客诉 + 人工核销） | ≈ **12 万元/年** |
| 13 | 加 fencing 之后 | 损失归零，只留「拒绝数」这一个可观测信号 | **0 元 + 1 列 + 1 条 `WHERE`** |
| 14 | 改成 `T=30 s` 之后 | 阈值 20 s ⇒ `Pr(P>20 s) ≈ 0.01%` ⇒ 约 65 次/年（降 30 倍） | 代价：真死发现从 10 s 变 30 s，且停顿尾巴**仍无上界** |

> **量级结论（非承诺值）**。假设：① `T=10 s`、续租 `T/3`；② 停顿分布 P99 = 2 s、P99.9 = 9 s，两者间按对数线性插值；③ 300 个持锁实例、每实例每天 6 次大停顿；④ 双写窗口内该资源写速率 20 次/s、其中 25% 是绝对值覆盖写；⑤ 每次覆盖平均废掉 1.5 件真实扣减；⑥ 每件综合成本 60 元。**换假设请按行重算**：堆从 16 GB 降到 4 GB，P99.9 通常落到 1–3 s，误失效约降一个量级（账一降到 ~1,000 元/年量级）；而**无论 T 调到多大、无论用 Redis 还是 ZK 还是 etcd，第 6 步的窗口都不会归零**——只有第 13 步能归零。第 14 步顺带回答一个常见问题：**调大 TTL 只是把概率从 0.3% 压到 0.01%，fencing 是把它变成「不可能发生的事故类型」。**

### 账二 · 单键锁的吞吐上限 = 1 ÷ 持锁时长（热点从这里开始）

| 步 | 项 | 推导 | 结果 |
| --- | --- | --- | --- |
| 1 | 临界区计算 | 库存校验、业务规则、组装写 | 25 ms |
| 2 | 临界区内 I/O | 读库存 + 写库 + 事务提交（→ comp/08） | 15 ms |
| 3 | 临界区总时长 `t_crit` | 1 + 2 | **40 ms** |
| 4 | 加解锁网络成本 | Redis 同 AZ RTT 0.4 ms ⇒ `2 × 0.4` | 0.8 ms |
| 4′ | 同上，etcd | RTT 含一次 Raft 提交约 2.4 ms ⇒ `2 × 2.4` | 4.8 ms |
| 5 | 单次占用 `T_lock` | `t_crit + 网络` | Redis **40.8 ms** / etcd **44.8 ms** |
| 6 | 单键上限 | `1,000 ÷ T_lock` | Redis **24.5/s** / etcd **22.3/s** |
| 7 | 业务需求（大促单 SKU） | 峰值扣减 | **600 次/s** |
| 8 | 需要多少个并行单位 | `600 ÷ 24.5` | **24.5 → 至少 25 个** |
| 9 | 分桶后单桶负载 | 按 32 桶（2 的幂，便于取模） | `600 ÷ 32 = 18.75/s`，余量 24% |
| 10 | 对照：不用锁，用单条原子 SQL | `UPDATE ... SET stock = stock - ? WHERE stock >= ?` 的行锁持有 ~0.6 ms | **1,600/s 量级** |
| 11 | 结论 | 锁把「行锁级 1 ms 的临界区」放大成「跨网络 40 ms 的临界区」 | 单键吞吐掉 **40–65 倍** |

> **量级结论（非承诺值）**。假设：① 临界区 40 ms（其中 I/O 15 ms）；② Redis 单实例同 AZ RTT 0.4 ms、etcd 一次写入 2.4 ms（含多数派与两次 fsync，硬件相关）；③ 无排队抖动、无重试；④ 行锁方案的单行持有 0.6 ms 为同库同机实测的中位数量级。**这张账是「锁的 QPS 永远等于 `1 ÷ 持锁时长`」这句口号的推导**：它和「Redis 能扛 10 万 QPS」完全不矛盾——10 万 QPS 是**不同 key** 的锁的总和；**同一把锁**的上限只有几十次每秒。第 10 步顺带给出结论：**能用一个原子 UPDATE 表达的业务，永远不要用分布式锁**（§46.10 的减法表第一行）。

### 账三 · 续租流量 = 持有者数 ÷ 续租间隔 × 租约粒度因子

| 步 | 项 | 推导 | 结果 |
| --- | --- | --- | --- |
| 1 | 持有中的锁数量 `N` | 5,000 个 Pod × 平均持有 1.8 把锁 | **9,000 把** |
| 2 | 每把锁的续租频率 | `1 ÷ (T/3)`，`T=15 s` | 0.2 次/s |
| 3 | 每 key 一个租约（Redis / 朴素 etcd 用法） | `9,000 × 0.2` | **1,800 次/s** |
| 4 | Redis 侧占用量级 | 单实例 10 万 QPS 量级，且 `PEXPIRE` 是 O(1) | 占 **~2%**，无事 |
| 5 | etcd 侧占用量级 | 每次 `LeaseKeepAlive` 都是一次 raft 写（两次 fsync）⇒ `1,800 × 2 = 3,600 fsync/s` | 占 leader 写能力的 **20–60%** |
| 6 | 改成一个进程一个 lease | `5,000 × 0.2` | **1,000 次/s**（降 44%），代价：误失效半径 = 该进程所有锁 |
| 7 | 再把 TTL 提到 60 s（续租 20 s） | `9,000 ÷ 20` | **450 次/s**（降 4×），代价：真死发现 60 s |
| 8 | ZK 侧的对照 | 心跳是 **session 级、不落盘、不产生事务**：`5,000 sessions ÷ 5 s` | **1,000 ping/s，但零 raft 写** |
| 9 | 结论 | 续租成本 = `N ÷ 续租间隔 × 租约粒度因子`（Redis=每 key、etcd=每 lease、ZK=每 session） | 锁数量是协调组件的**第一容量变量** |

> **量级结论（非承诺值）**。假设：① 5,000 个进程、平均持 1.8 把锁；② TTL 15 s、续租 `T/3 = 5 s`；③ etcd leader 写上限「数千到一万 txn/s 量级」，取决于 fsync 延迟与批量（**以目标版本与硬件文档为准**）；④ 心跳不与业务请求共用线程池。**这张账最反直觉的结论是第 8 步**：ZK 用「连接级心跳」把续租成本与锁数量**解耦**了，etcd 用「lease 级 keepalive」把它**耦合**了——所以「锁数量很大」的形态在 ZK 上更便宜，而「锁数量很少、语义要精确」的形态在 etcd 上更省心。这与 [37 ZooKeeper vs etcd](37-zookeeper-vs-etcd.md) §37.10 的选型判定一致：**ZK 赢在「多订阅者/多租约」，etcd 赢在「语义与运维」**。

## 46.9 三本账的复算脚本与假设敏感性

```python
# 三本账复算：改任一假设直接重跑（Python 3.9+，无第三方依赖）
def account_fencing_loss(T_ms=10_000, h_ratio=1/3, gran_ms=200, pause_s=12.4,
                         inst=300, big_pauses_per_day=6, p_gt=0.003,
                         hot_ratio=1/50, write_per_s=20, overwrite_ratio=0.25,
                         items_per_overwrite=1.5, yuan_per_item=60):
    """账一：年期望坏单量与折算金额"""
    thresh = T_ms * (1 - h_ratio) + gran_ms            # 有效误失效阈值
    window = pause_s - thresh / 1000 + 0.4 + 0.8        # 双写窗口（s）
    per_day = inst * big_pauses_per_day * p_gt          # 全集群误失效次数/天
    hit_per_year = per_day * 365 * hot_ratio            # 命中热点资源的次数/年
    covered = window * write_per_s * overwrite_ratio    # 每次的覆盖写数
    items = hit_per_year * covered * items_per_overwrite
    return thresh, window, per_day, hit_per_year, items, items * yuan_per_item

def account_lock_qps(t_calc_ms=25, t_io_ms=15, rtt_ms=0.4, demand_per_s=600, buckets=32):
    """账二：单键上限、所需桶数、分桶后负载"""
    t_lock = t_calc_ms + t_io_ms + 2 * rtt_ms
    cap = 1000 / t_lock
    return t_lock, cap, demand_per_s / cap, demand_per_s / buckets

def account_renew_cost(locks=9_000, ttl_s=15, renew_div=3,
                       fsync_per_write=2, etcd_write_cap=5_000):
    """账三：续租 QPS 与占 etcd 写能力的比例"""
    renew_qps = locks / (ttl_s / renew_div)
    return renew_qps, renew_qps * fsync_per_write, renew_qps / etcd_write_cap

th, w, pd, hy, items, money = account_fencing_loss()
print(f"账一：阈值 {th:.0f} ms，窗口 {w:.1f} s，{pd:.1f} 次/天，命中 {hy:.0f} 次/年")
print(f"      年坏单 {items:,.0f} 件 / {money:,.0f} 元；加 fencing 后为 0，只剩拒绝计数")
t_lock, cap, need, per_bucket = account_lock_qps()
print(f"账二：T_lock {t_lock:.1f} ms，单键 {cap:.1f}/s，需 {need:.1f} 桶，32 桶后 {per_bucket:.2f}/s")
qps, fsyncs, ratio = account_renew_cost()
print(f"账三：续租 {qps:,.0f} 次/s，fsync {fsyncs:,.0f}/s，占 etcd 写能力 {ratio:.0%}")
```

**敏感性（哪几个假设最值得改）**：

| 假设 | 变动 | 账一（年坏单） | 账二（单键上限） | 账三（续租 QPS） |
| --- | --- | --- | --- | --- |
| 大停顿概率 `Pr(P>阈值)` | 0.3% → 0.03%（堆从 16 GB 降到 4 GB） | 降约 10× | 不变 | 不变 |
| TTL `T` | 10 s → 30 s | 降约 30× | 不变 | 降 3× |
| 临界区时长 | 40 ms → 10 ms（把 I/O 换成异步） | 不变 | 24.5/s → **98/s**（4×） | 不变 |
| 锁数量 | 9,000 → 1,000 | 不变 | 不变 | 1,800 → **200 次/s**（9×） |
| 换 ZK（session 级租约） | — | 不变 | 略降（RTT 1–3 ms） | **续租与锁数量解耦** |
| 换 etcd（lease 级） | — | 不变 | 略降 | 与 Redis 同量级但每次都是 raft 写 |

> **量级结论（非承诺值）**。这个脚本的价值在于**它能让你当场回答「如果我改这个假设，账会变成什么样」**。评审上最常被问的三个数就是上表前三行：把 TTL 调大会怎样（账一降 30 倍，但发现变慢）、把临界区改小会怎样（账二涨 4 倍，但锁的「粒度」没变）、锁数量涨 10 倍会怎样（账三直接把协调组件打死）。**三个数必须一起报，只报一个都是误导。**

## 46.10 边界：什么时候不需要锁，Redlock 能不能用，fencing 贵在哪

### 第一张表先做减法：九种情况根本不需要分布式锁

| 你以为需要分布式锁的场景 | 物理上为什么不需要 | 正确做法 | 吞吐对照（账二口径） |
| --- | --- | --- | --- |
| 同库单行「读-改-写」 | 数据库的行锁本身就是锁，且是**同一次网络往返内**的锁 | `SELECT ... FOR UPDATE` 或单条 `UPDATE ... WHERE stock >= ?` | 数百到 1,600/s（vs 锁 24/s） |
| 「只允许创建一次」的实体 | 唯一键约束就是最强的互斥，且是**原子的** | `INSERT ... ON DUPLICATE KEY` / `UNIQUE` 冲突当正常分支 | 与普通写同量级 |
| 重复执行无副作用的动作 | 既然幂等，互斥只是省 CPU | 幂等键 + 重试（→ comp/43 §43.5 的「一件证据行」） | 不需要锁 |
| 同一 key 的写必须落到同一 worker | 分区/一致性哈希已经保证「单写者」 | Kafka 分区键、分片路由（→ comp/16） | 线性扩 |
| 单库范围内的「只跑一个」 | 数据库咨询锁足够，且不引入新组件 | PG `pg_try_advisory_lock` / MySQL `GET_LOCK`（**连接级，注意连接池复用**） | 与 DB 同量级 |
| 定时任务防重复（多实例部署） | 只需要「这一轮只让一个跑」，且允许偶发双跑 | 锁表 + `lock_until` CAS（ShedLock 一类），**用数据库时间函数，不用应用时钟** | 每轮一次写 |
| 短临界区 + 极高 QPS | 跨网络锁把 1 ms 放大成 40 ms（账二） | 乐观锁版本号 + CAS 重试，或单条原子 SQL | 高 |
| 「减少重复劳动」（报表、缓存重建） | 双跑无害，只需要降低概率 | Redis 单实例 `SET NX PX` 就够 | 10 万 QPS 量级 |
| 跨机房强互斥 | 跨机房 RTT 让租约判定必然抖动 | 改架构：把资源收敛到单机房，或改成「各自处理 + 对账」 | — |

> **判据一句话**：**能在一个进程内、一次网络往返内、或一条 SQL 里表达的互斥，任何分布式锁都是净成本。** 这句话在评审上最有用，因为绝大多数「我们需要分布式锁」的真实情况，是「我们把同一份数据的写者放到了多个进程里」（→ comp/43 的同一句式）。

### 第二张表：Redlock 到底能不能用

| 场景 | 能用吗 | 理由 |
| --- | --- | --- |
| 报表/对账任务防重复、缓存重建、清理任务 | ✅ 能 | efficiency 级需求；双跑浪费资源不损坏数据 |
| 限流/去重的「近似唯一」 | ✅ 能 | 丢失一次的后果是多重试一次，且通常有下游幂等 |
| 扣款、发货、库存、账务 | ❌ 不能单独用 | correctness 级需求；事故一二就是两个方向的反例 |
| 作为「选主」用（决定谁服务） | ❌ 不能 | 选主要 term/epoch，Redlock 不给单调任期；且没有撤权协议 |
| 有严格 SLO 的「恰好一个消费者」 | ⚠️ 只能作为优化 | 必须叠加幂等 + 对账，否则一次停顿就是重复处理 |
| 团队里没人能维护 ZK/etcd，且能接受双跑 | ✅ 能（单实例即可） | 单实例 Redis 锁的失效模式与 Redlock 只差「是否多数派」，都是 efficiency 级 |

### 第三张表：fencing 的落地成本，以及改不动存储时怎么办

| 改造点 | 工作量量级 | 风险 | 降级方案（改不动存储时） |
| --- | --- | --- | --- |
| 存储加一列 `fence`（或复用版本号列） | 1 次 DDL（在线 DDL，→ comp/05） | 老代码不写这一列 → 默认值破坏比较 | 用已有的 `version`/`updated_at` 列兼任，但要证明单调 |
| 所有写路径带上 token | 每个写接口 0.5 人日量级；40 个接口 ≈ 20 人日 | 漏改一处 = 一个后门 | 在 DAO/ORM 层统一拦截裸 SQL（ArchUnit/静态检查） |
| 锁服务给出单调 token | 0（etcd revision / DB 序列）或 1 个计数器节点（ZK） | Redis `INCR` 在 failover 后回退 | 用数据库序列；或退化成「单实例 + 不自动切换」 |
| 拒绝路径的处理（停手 + 上报 + 丢弃缓冲） | 每处 critical section 的异常分支 | 有人把 `FencedOff` 当可重试错误 → 重复率飙升 | 明确约定「不可重试异常」并在告警里单列 |
| 旧主人物理隔离（STONITH / `sshfence`） | 运维流程 + 权限 | 误杀正常节点 | 只在「阻塞型资源」（如共享文件系统）上作为最后手段 |
| **第三方/黑盒存储**（NFS、老系统、SaaS API） | 无法加 token | 只能靠「上游代理做 token 校验」 | 在中间加一层自己的代理/网关，由它持有 token 并串行化写入；或**缩短 TTL + 强幂等 + 对账**三件套兜底 |

> **成本结论（量级）**：一个中等规模服务（40 个写接口、一个存储）落地 fencing 大约 **20–30 人日**，一次性；之后每新增一个写接口多 0.5 人日。**对比账一的 12 万元/年期望损失与事故的 84 万元**，这笔投入的回收期在一个季度内——这就是「fencing token 才是答案」这句话在工程上的可支付性。

### 决策表：按顺序排除，五步走完

| 步 | 问 | 是 → | 否 → |
| --- | --- | --- | --- |
| 1 | 双执行的后果是「浪费资源」还是「数据损坏/赔钱」？ | 浪费 → **efficiency 级**：Redis 单实例锁即可，结束 | 损坏 → 下一步 |
| 2 | 能不能用一次网络往返内的机制（行锁 / 唯一键 / 原子 SQL / 咨询锁 / 分区单写）？ | 用那个，结束（**这一步能解决 80% 的「锁」需求**） | 下一步 |
| 3 | 临界区 QPS 是否会超过 `1,000 ÷ 持锁毫秒`（账二）？ | 必须**分桶**（按 key 拆 N 把锁）或改形态 | 下一步 |
| 4 | 能不能在每个写路径上做单调校验（加一列 + 一条 `WHERE`）？ | **锁服务 + token + 存储 CAS**，三层齐全 | 下一步 |
| 5 | 存储是黑盒、改不动？ | 加代理层做校验；做不到就只能「短 TTL + 幂等 + 对账」并**在风险清单里写明「本资源不具备 correctness 级锁能力」** | 回到 2 |

**这张表的用法**：从 1 往下走，**遇到的第一个「是」就是答案**。绝大多数团队的真实答案落在第 2 步；落在第 4 步的，才是真正需要分布式锁 + fencing 的场景（库存、账务、分片调度）。**最坏的一步是第 5 步**：不是因为你做错了，而是因为你在用一种**明确写在纸上的已知风险**去换工期——这至少是诚实的。

## 46.11 踩坑清单（现象 → 根因 → 定位 → 修复 → 防复发）

| 现象 | 根因（指到物理形态） | 定位 | 修复 | 防复发 |
| --- | --- | --- | --- | --- |
| 锁「莫名其妙」保护不住，偶发覆盖 | 释放时没比较 value：`GET` 后 `DEL` 之间锁已过期并被别人持有 | 加锁 value 是否有随机串；释放是否 Lua | 释放/续期一律 Lua 比较后再操作 | 代码评审硬性要求：无 Lua 不放行 |
| 业务偶发双跑，日志里只有一条 `unlock` warn | TTL 小于 P99.9 停顿（事故一） | 对比 GC 日志时间与双跑时间窗 | 缩短临界区 + 加 watchdog + 上 fencing | `jvm_gc_pause_seconds` 与 TTL 联动告警 |
| 某个热点键的锁排队无限增长，其他人全卡住 | watchdog 一直续租，持锁业务 hang 死 → 锁永不释放 | 看「TTL 剩余」始终接近满值 + 锁等待 P99 线性涨 | 临界区强制超时 + 运营强制撤锁通道 | 监控「TTL 剩余」不下降即告警 |
| Redis 主从切换后，同一把锁被两个客户端同时持有 | 主从异步复制：`SET NX` 没到从库，主库挂了从库晋升 | 切换时间与双写时间窗重叠 | `WAIT 1`/`min-replicas-to-write` 只能缩小窗口 | 承认它是 efficiency 级；correctness 靠 fencing |
| 用 5 个 Redis Cluster 节点跑 Redlock，行为诡异 | Cluster 有槽迁移与 MOVED，多 key 落在不同节点 | 客户端日志里的 MOVED/ASK | 改用 5 个**独立实例** | 架构图上标注「非 Cluster」 |
| Redlock 在夜里「偶尔」失效两次 | NTP 阶跃 / VM 迁移 → drift 假设失效（事故二） | 对比 `chronyc tracking`、宿主事件与事故时间 | 不要用墙钟做正确性判断；上 token | 关键系统禁用 Redlock 做互斥 |
| ZK 抢锁时全部实例被唤醒，集群被自己的锁打满 | watch 父节点而不是前驱节点（羊群效应） | `zk_watch_count` 与加锁 QPS 同向暴涨 | 用 Curator `InterProcessMutex`（只看前驱） | 禁止手写 ZK 锁 |
| etcd 上「同一个 lease 挂了 200 把锁」，一次抖动全丢 | lease 级租约：一次 keepalive 失败 → 该 lease 全部 key 被删 | lease 上的 key 数量 | 拆 lease 或接受半径（并配 fencing） | 规定「一个 lease 最多挂 N 把锁」 |
| 两个进程共用同一个 lease ID，都以为自己有锁 | lease ID 是令牌，任何客户端都能 keepalive | `LeaseTimeToLive` 的剩余时间总是被刷新 | 一个进程一个 lease；lease ID 永不持久化复用 | 代码里禁止序列化 lease ID |
| 选主切换后旧主还在派活（脑裂） | 撤权只靠「watch 报错重试」，没有主动停手（事故三） | `leader_is_primary` 出现 2 个实例 | 三阶段撤权：停新活 → 等在途 → 退出 | 数据面校验 term/epoch + 幂等 |
| 任务被重复执行，但锁明明「只有一个人拿到」 | 锁只保护了「开始」，没保护「每一次写」 | 比对结果表的写入来源实例 | 每次写带 token；执行器侧幂等键 | 锁粒度与写粒度对齐 |
| fencing token 用了 Redis `INCR`，越用越乱 | `INCR` 在 failover 后回退 → 旧 token 反而更大 | token 序列出现非单调 | 换 etcd revision / DB 序列 | token 来源必须写进设计文档并评审 |
| token 校验写成「先查后写」，仍然双写 | 应用层两段式，中间有窗口 | 出现 `fence` 倒退的行 | 改成单条 `UPDATE ... WHERE fence < ?` | 代码层禁用「先查后写」的 fencing |
| 定时任务用应用时钟算 `lock_until`，锁提前释放 | 各节点时钟漂移（[45 分布式 ID](45-distributed-id.md) §45.4） | 比对节点间 `NOW()` 差异 | 用数据库时间函数 | 所有时间比较都在同一时钟域 |
| 一把全局锁保护所有租户，整体退化成串行 | 锁粒度 = 全局（账二的反面） | 锁等待里 90% 来自同一把锁 | 按租户/键分桶 | 设计评审必须给出「锁的数量级」 |

## 46.12 观测：五个数覆盖 90% 的锁与选主故障

| 指标 | 看什么 | 拐点阈值 | 版本 / 开关前提 |
| --- | --- | --- | --- |
| **锁等待 P99**（`lock_acquire_wait_seconds`） | 排队是否在涨；涨 = 有人在临界区里超时 | 单键 P99 > 持锁时长的 1/2，或 > 100 ms | 需在客户端 SDK 埋点；Redisson 3.x 需自行埋点或接 Micrometer（以目标版本文档为准） |
| **续租失败数**（`lock_renew_fail_total`） | 是否已经「失去资格」（这是最接近事故的一个数） | `> 0` 且 5 分钟内持续 ⇒ 告警 | Redis 侧 Lua 返回 0 记一次；etcd 侧 keepalive channel 关闭记一次 |
| **TTL 剩余**（`lock_ttl_remaining_seconds`） | 持有中却不再下降 ⇒ watchdog 死了或业务 hang 住 | 持有中且剩余 < `TTL/3` 持续 2 个周期 | `PTTL`/`LeaseTimeToLive` 采样，注意采样本身也是流量 |
| **fencing 拒绝数**（`fence_reject_total`） | **唯一能直接证明「僵尸主人还在活动」的数** | `> 0` 即告警（不是错误率指标） | 在存储 CAS 返回 0 行处打点；必须与「行不存在」区分 |
| **双主信号**（`leader_is_primary` / `term` 冲突） | 同一角色被声明两次 | `sum by (role) (leader_is_primary) > 1`，任一时刻 > 0 持续 10 s | 各实例上报 `(role, term)`，服务端做「区间重叠检测」 |
| **协调组件负载**（`zk_outstanding_requests` / etcd `lease` 数量与写 P99） | 账三是否已经吃掉写能力 | etcd WAL fsync P99 > 25 ms；ZK `outstanding` 持续 > 100 | etcd 看 `etcd_disk_wal_fsync_duration_seconds`、`etcd_mvcc_db_total_size_in_bytes`；ZK 用 `mntr`（需在 `4lw.commands.whitelist` 里打开） |

```yaml
# 告警骨架（Prometheus 3.x，指标名需与你的 SDK 埋点对齐）
groups:
  - name: lock-and-leader
    rules:
      - alert: LockWaitHigh
        expr: histogram_quantile(0.99, sum by (le, lock) (rate(lock_acquire_wait_seconds_bucket[5m]))) > 0.1
        for: 10m
        annotations: {summary: "锁等待 P99 > 100ms，临界区在超时或锁粒度太粗"}
      - alert: LockRenewFailing
        expr: increase(lock_renew_fail_total[5m]) > 0
        for: 1m
        annotations: {summary: "续租失败=已失去资格，必须确认临界区已停手（fencing 是否生效）"}
      - alert: WatchdogStalled
        expr: (lock_ttl_remaining_seconds < lock_ttl_seconds / 3) and on (lock) (lock_held == 1)
        for: 30s
        annotations: {summary: "持有中但 TTL 剩余不再增长：watchdog 线程死了或业务 hang 住"}
      - alert: ZombieLeaderWriting
        expr: increase(fence_reject_total[10m]) > 0
        annotations: {summary: "有旧主人在写并被拒绝：查 term/任期与撤权流程，不要当成故障自愈"}
      - alert: SplitBrain
        expr: sum by (role) (leader_is_primary) > 1
        for: 10s
        annotations: {summary: "同一角色有多个主：立即阻断数据面写并核对 term"}
```

> **三条判读纪律**：① **`fence_reject_total` 不是坏指标**，它归零有两种可能——没有僵尸主人（好），或者 fencing 没生效（坏），必须与「续租失败数」联看。② **锁等待高 ≠ 锁服务慢**，先看临界区时长分布，再看锁粒度（账二）。③ **双主告警必须由「数据面」而不是「控制面」产生**：控制面的 `leader_is_primary` 只是自述，事故三里的两个 leader 都自述正常（各自连着自己的 etcd），真正发现问题是结果表里的重复行。

## 46.13 一页速记

| 记什么 | 具体结论 |
| --- | --- |
| **一句话本质** | 锁 = 一个用租约换崩溃恢复的**单方面判定**；它的安全边界不在锁服务，在被保护的数据上 |
| **唯一真问题** | 锁安全不取决于锁服务多可靠，取决于旧主人能不能被挡住 → **fencing token 才是答案** |
| **三层结构** | L1 原子获取互斥、L2 租约换崩溃恢复、L3 fencing 换误判安全；只有 L1+L2 = efficiency 级锁 |
| **误失效阈值** | 停顿 `P > TTL − 续租间隔` 就被判死（TTL 10 s、续租 T/3 ⇒ 约 6.7 s） |
| **Redlock 真相** | 5 独立实例 + 多数派 + `validity = ttl − e − drift`；证明依赖「有界时钟漂移 + 无长停顿」，生产不提供 |
| **为什么多数派不够** | 多数派只保证「不会同时发出两把锁」，保证不了「旧主人已经停手」 |
| **fencing 的两条** | ① token 严格单调（etcd revision ✅ / Redis `INCR` ⚠️ / 时间戳 ❌）；② 比较与写入原子（一条 `UPDATE ... WHERE fence < ?`） |
| **现成答卷** | Chubby 的 sequencer、HDFS 的 epoch + fencing method、Kafka 的 leader epoch（`FENCED_LEADER_EPOCH`） |
| **选主三件套** | quorum + lease + term；再加第四件「撤权协议」：停新活 → 等在途 → 退出，不要自动抢回 |
| **ZK vs etcd 租约** | ZK 绑**连接**（心跳不落盘、与锁数量无关）；etcd 绑**令牌**（每次 keepalive 都是 raft 写、可挂多 key） |
| **锁的 QPS** | 单键上限 = `1,000 ÷ (临界区 ms + 2×RTT ms)`；40 ms 临界区 ⇒ 约 24/s，分桶才能扩 |
| **续租流量** | `持有锁数 ÷ 续租间隔 × 租约粒度因子`；9,000 把锁 / 5 s = 1,800 次/s，etcd 上是 raft 写 |
| **什么时候不用锁** | 行锁、唯一键、原子 SQL、咨询锁、分区单写、幂等键——这六件能解决 80% 的「锁需求」 |
| **最该监控的两个数** | `fence_reject_total`（有僵尸主人）与 `lock_renew_fail_total`（已失去资格） |
| **换零件的信号** | 单键 QPS 超上限、锁数量把组件打死、或「双写就赔钱」而存储改不动 |

**如果只记五句：**

1. **锁服务只能承诺「此刻我认为你可以进」，承诺不了「你进入之后仍然可以写」。** 后半句只有被写的数据能给，方式是单调 token 的比较。
2. **所有基于超时的锁，都会在「进程停顿」这一类故障上误判，而停顿没有上界。** 调大 TTL 只能把概率压一个量级，永远压不到零。
3. **Redlock 是一把 efficiency 级的锁，放在 correctness 的位置上就必然出事。** 5 个节点的多数派买不到「旧主人停手」。
4. **选主比锁难在「撤权」**：协议保证只有一个主，但旧主在自己网络里还活着、还在派活——所以 term 要跟着每一次写走，旧主失联时必须主动停手。
5. **最便宜的锁是不用锁**：行锁、唯一键、原子 SQL、分区单写，比任何分布式锁快 40 倍以上（账二），且没有租约问题。

## 46.14 自检题（5 题）

**Q1.** 一个库存服务用 `SET NX PX 3000` 防超卖，TTL 3 s、大促期间单实例堆 16 GB。某天一次 8.6 秒 Full GC 之后，同一个 SKU 超卖 2,300 件，但监控上「锁从未失败过」。请回答：① 双写窗口从哪一刻开始、到哪一刻结束；② 为什么监控看不出问题；③ 把 TTL 改成 30 s 是否能避免；④ 唯一能归零的修法。

<details><summary>答案</summary>

**① 窗口**：从「服务端 TTL 到期」那一刻开始（此时另一个实例合法抢到锁），到「旧主人把手头批次写完」结束。按 §46.1 事故一：TTL 在 11:02:10.1 到期，旧主人 11:02:17.0 才恢复（GC 8.6 s），写完 11:02:19.8 ⇒ 旧主人**仍然认为自己持有锁的 2.8 秒**是重叠写窗口；被它覆盖掉的是「GC 期间与这 2.8 s 内别人做掉的约 7.2 s × 320/s ≈ 2,300 次扣减」。

**② 监控看不出**：锁服务的指标全是「成功/失败/延迟」——三次 `SET NX` 都成功了（一次是 inv-3、一次是 inv-6，中间一次是别人的无关 key），`unlock` 只打了一条 warn（因为 `DEL` 删的是别人的锁，如果代码比较了 value 就会返回 0）。**没有任何一个指标的对象是「数据是否被旧快照覆盖」**，所以必须靠 `fence_reject_total` 或对账。

**③ 改 TTL 30 s 不够**：误失效阈值变成 `TTL − TTL/3 ≈ 20 s`，8.6 s 的停顿确实挡得住；但大促当天另一次停顿是 13.1 s，明年堆再长大一次就是 25 s。**你只是在和一条无上界的尾巴赛跑**（账一第 14 步：0.3% → 0.01%，降 30 倍但不归零）。

**④ 唯一归零的修法**：写入路径带单调 token，存储侧 `UPDATE ... WHERE fence < :token`。旧主人醒来时它的 token 更小 ⇒ `affected_rows = 0` ⇒ 它自己知道失去资格并停手，同时 `fence_reject_total` 上报。此外还有两条必须同时做的：临界区改小 + 覆盖式写改增量写（`stock = stock - ?`）。

量级结论，非承诺值；假设见 §46.8 账一。
</details>

**Q2.** 有人说：「我们用 Redlock，5 个节点、容忍 2 个挂掉，比单实例 Redis 安全多了，为什么还要 fencing？」请用本篇的判据回答，并给出一个 Redlock 在两个节点上「同时合法」的具体时间线。

<details><summary>答案</summary>

**判据**：Redlock 提升的是「锁服务不出错」的概率（不会因为一个节点挂掉就丢锁），而 fencing 解决的是「锁服务即使完全正确，旧主人仍可能还在写」。**这是两个不同的失效面**：① 服务端视角的重复发锁（Redlock 改善了这一面，靠多数派交集）；② 客户端视角的「我还以为自己有效」（Redlock 完全没有改善，因为它依赖客户端自己的墙钟算 `validity`，并且**没有任何机制去拒绝一个已经过期的客户端**）。

**时间线（与事故二同形）**：`T1=0`，A 在 R1–R4 上 `SET NX PX 10000` 成功，`validity ≈ 9.77 s`；`t=0.2 s` A 所在 VM 被宿主超分 + NTP 阶跃，A 停顿 7.8 s；`t=10.0 s` 五个实例各自按自己的钟令锁到期；`t=10.1 s` B 在 R2、R3、R4 上成功（`s=3 ≥ 3`），**这是一次合法的加锁**；`t=8.1 s`（A 的钟）A 恢复，它的 `validUntil` 还没到，继续写。**两个客户端在同一物理时刻都认为自己拥有锁，而 Redlock 的每一次判断都是对的。**

补充：还有一条与时钟无关的破法——某个实例**无持久化重启**会让锁"消失"，此时 A 仍持有 2 票、B 又能拿到 3 票，两边的多数派都成立。所以 antirez 的实现要求「节点重启后延迟至少一个 TTL 再对外服务」，这是一条**运维约定**，不是算法保证。

量级结论，非承诺值。
</details>

**Q3.** 一个平台有 5,000 个 Pod，每个 Pod 平均持有 1.8 把 etcd lease 锁，TTL 15 s、每 5 s 续租一次。上线两周后 etcd 的写 P99 从 4 ms 涨到 40 ms，随后选主开始抖动。请给出：① 用量级算一遍续租压了多少写能力；② 三种降载手段及各自的代价；③ 为什么换 ZK 能缓解。

<details><summary>答案</summary>

**① 量级**：`9,000 把锁 ÷ 5 s = 1,800 次续租/s`，每次 keepalive 都是一次 raft 写、两次 fsync ⇒ **3,600 fsync/s**。若 leader 在该硬件上的写上限是「数千 txn/s 量级」，续租就吃掉了 20–60%——而且它与业务无关、**全天候不停**，于是 P99 被稳定抬高，选主的 lease 续期也排在同一条队列里 ⇒ 抖动（§46.8 账三第 3–5 步）。

**② 三种降载**：
1. **一个进程一个 lease**（把 1.8 把锁挂同一 lease）：`5,000 × 0.2 = 1,000 次/s`，降 44%。代价：误失效半径从「一把锁」放大到「该进程所有锁」，必须配 fencing。
2. **拉长 TTL**（15 s → 60 s）：续租降到 450 次/s，降 4×。代价：真死发现从 15 s 变 60 s，选主切换变慢。
3. **减少锁数量**（把「每个任务一把锁」改成「一个分片一把」「一个租户一把」，或干脆用分区单写消除锁）：最根本，代价是重构。

**③ 为什么 ZK 能缓解**：ZK 的租约是 **session 级**——心跳走的是连接上的 `PING`，**不落盘、不产生事务**，所以你持 1 把还是 100 把锁，心跳成本都一样（`5,000 sessions ÷ 5 s = 1,000 ping/s`，零 raft 写）。etcd 的 lease 是**令牌级**，每个 lease 的 keepalive 都要过一次 raft。**这是两种形态在「锁数量」这个维度上的分叉**，也是 → comp/37 §37.10 判定表里「多订阅者/多租约选 ZK」的那一行。

量级结论，非承诺值。
</details>

**Q4.** 你们决定上 fencing。有人提议：「在写之前先 `SELECT fence`，如果大于我的 token 就退出，否则再 `UPDATE`。」这个方案哪里不对？请给出正确的两条纪律，并说明为什么「token 用 Redis `INCR`」也不对。

<details><summary>答案</summary>

**错在「先查后写」是两段式**：`SELECT` 与 `UPDATE` 之间有一个窗口，两个旧/新主人可以在这段时间里交错——A 读到 `fence=7`（以为可以写），B 写入并置 `fence=8`，A 再写成功 ⇒ 又变成覆盖。**fencing 的全部有效性来自「比较与写入在同一条语句/同一次事务里原子完成」**，即 `UPDATE ... SET fence = :token WHERE fence < :token`，用 `affected_rows` 判定。

**两条纪律**：① 所有写路径必须经过同一个 `FencedWriter` 通道（禁止裸 SQL，用静态检查/ArchUnit 拦住）；② `FencedOff` 必须被当作**不可重试**异常——处理方式只有「停手 + 上报 + 丢弃缓冲」。

**为什么 `INCR` 不对**：Redis 的 `INCR` 是单实例状态，主从异步复制下 failover 会让 counter **回退**到从库的旧值（→ comp/14）。于是「后来的主人」可能拿到一个比前任更小的 token，它的写会被存储拒绝（拒绝还是轻的），更糟的是**旧主人的大 token 反而被接受** —— fencing 的单调前提被打破，机制失效。正确来源：etcd `revision`/`CreateRevision`、ZK `czxid`、数据库自增序列（单主写）。

量级结论，非承诺值。
</details>

**Q5.** 老板问：「我们已经在 etcd 上做了选主，为什么还会脑裂？Raft 不是保证只有一个 leader 吗？」请用协议面 / 数据面两张视角回答，并给出四道防线。

<details><summary>答案</summary>

**协议面**：Raft 保证「同一 term 内最多一个 leader 被多数派承认」，这是真的。但脑裂的真实形状不是「两个 leader 都被承认」，而是「**协议侧已经换人，旧主在自己那一侧还活着、还在干活**」——它连不上 etcd，收不到任何否定信号，于是按本地缓存的分片表继续派活（事故三，252 秒）。

**数据面**：写请求**不经过 Raft**（它们直接写 MySQL/对象存储/Kafka），所以协议的正确性与数据的正确性之间有一个空隙。这个空隙只能由 term 校验 + 幂等来填。

**四道防线**：
1. **每一次写都带 term/epoch**，存储侧拒绝更小的 term（Kafka 的 `FENCED_LEADER_EPOCH` 就是这个）。
2. **撤权协议**：主在 `sess.Done()` 之后立刻停止认领新工作（不重试到成功为止），等在途任务在**有上限**的时间内收敛，然后退出进程，**不要自动抢回**。
3. **幂等键**：执行器侧对「分片 + 轮次」做去重，最坏情况下也只是一次重复投递而非重复扣款。
4. **对账**：事后比对两批结果的差集，并在控制面自述（`leader_is_primary`）之外监控**数据面的重复终态**。

一句话：**Raft 保护的是「谁是主」这个判断，不保护「旧主还在写」这个事实。**

量级结论，非承诺值。
</details>
