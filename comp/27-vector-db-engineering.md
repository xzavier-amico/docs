## 27.1 引子：三起「向量库上线了，但结果不能用」的故障

向量库的故障有个统一特征：**P99 正常、错误率零、召回率没人测**。它不返回 5xx，它返回「3 条看起来也对的垃圾」或者「空列表」。所以它永远不会触发告警，只会触发客诉——而客诉到工程侧之间隔着客服、运营、产品三层翻译。

### 事故一：搜「连衣裙」返回 3 条，监控全绿（2026-01-13）

商品语义搜索：4,600 万 SKU、768 维、独立向量服务 12 分片 × 2 副本。设计时有一个看起来非常合理的决定：**商品的上下架状态变更太频繁（日均 40 万次），不往向量库里同步**，只在检索返回后去 Redis 查一次状态、把已下架的丢掉。上线前三个季度一切正常，因为下架率只有 4%，`top-100 × 96% = 96` 条，用户根本感觉不到。

大促结束后，运营做了一轮**季节清仓**：连衣裙类目 21 万 SKU 里有 19.4 万被批量下架，而它们正是「连衣裙」这个查询在 embedding 空间里的**中心簇**——同一个类目、相似标题、相似图片，向量几乎挤在一起。

| 时间 | 事件 | 数据 |
| --- | --- | --- |
| 01-13 09:10 | 搜索「连衣裙」，第一页 3 条，第二页 0 条 | top-100 候选 |
| 01-13 09:40 | 排查：接口返回 3 条，无错误、无超时、P99 = 41 ms（低于基线 46 ms） | 请求成功率 100% |
| 01-13 10:20 | 手工把 top-100 的 id 捞出来查状态：**97 条已下架** | 候选内下架率 97% |
| 01-13 11:00 | 确认机制：查询向量落进「清仓连衣裙」簇，图遍历先访问的 100 个邻居里 97 个是死货 | top-100 → 3 条 |
| 01-13 14:00 | 临时把 `limit` 从 100 提到 3,000（约 30 倍），第一页回到 10 条 | P99 41 → 620 ms |
| 01-13 ~ 01-17 | 修：状态字段同步进向量库 + 按 `category_id` 建分区索引，`expr` 下推；状态同步走 CDC | P99 = 12 ms，空结果率 0.4% |
| 01-17 复盘 | 4 天里「连衣裙」类目零结果会话 38.2 万次，GMV 估算损失 210 万元 | 客诉 1,912 张 |

注意第一行的数字：**故障期间 P99 是下降的**（41 ms < 基线 46 ms）。因为结果变少了，返回更快。**任何以「延迟 + 错误率」为轴的面板，都看不见这一类故障。**

### 事故二：升级重启用了 18 分钟，索引重建用了 9 小时（2025-12-06）

知识库检索：2.4 亿条 chunk、1024 维、单机 8 × 32C256G 的向量服务集群，`HNSW`（M=16，`efConstruction=200`）。变更单上写的是「升级到下一个 2.x 小版本，滚动重启，预计 30 分钟，22:00–23:00 窗口」。

| 时间 | 事件 | 数据 |
| --- | --- | --- |
| 12-06 22:00 | 停写，开始滚动升级 | 8 节点 |
| 12-06 22:18 | 新版本启动完成，但 `load` 集合失败：**索引文件版本不被识别** | 8/8 节点 |
| 12-06 22:55 | 查 release notes 确认：该小版本更换了索引文件格式，**旧索引不能读，只能重建** | — |
| 12-06 23:30 | 开始重建；第一次尝试 3 小时后被 OOM 打断（构建期常驻 + 查询段两份内存） | 内存需求翻倍 |
| 12-07 02:40 | 第二次尝试：先卸掉所有段腾内存（**等于放弃了回滚点**），重建开始 | — |
| 12-07 07:20 | 重建完成 + 抽样校验（recall@10 = 0.94） | 建图 8.3 h |
| 12-07 07:40 | 恢复写入，搜索侧灰度切流完成 | 停机 9 小时 40 分 |
| 12-07 复盘 | SLA 违约赔付 30 万元；且这一个窗口里**没有旧索引可以回滚** | — |

计划里最大的错误不是「没看 release notes」，而是**把索引当成了可以「升级」的对象**。索引是一份派生数据，它的格式由构建它的那版二进制决定；二进制一变，最便宜的正确动作是重建，而不是转换。而这个动作的成本是**机时**，不是**重启时间**——两者差一个数量级（18 分钟 vs 9 小时 40 分）。

### 事故三：把向量库当主库，切主丢了 40 分钟的新增商品（2026-02-21）

推荐素材库：collection 里存了 `id / embedding / title / price / status / stock / owner_id`——因为「过滤条件要用这些字段」。上游商品主库只存 `id + embedding_source_text`，两者靠双写同步，跑了一年没人对账。

## 27.2 一句话定位与唯一真问题

**定位**：向量库 = 「把一个不可读、不可解释、必须重算的派生数据（向量 + 索引），包装成一个带过滤条件的 top-k 服务」的那层工程。它有三个「不是」：

| 你以为的 | 真相 | 后果 |
| --- | --- | --- |
| 「向量库是个数据库」 | 它是**派生索引**：原文与业务字段必须在别处，向量可从原文重算 | 丢了就是丢了，重建以机时计（事故三） |
| 「向量库自己会扩容、会备份」 | 独立服务形态确实管分片与副本，但**副本常常是异步的**，快照粒度是天级 | 切主丢最近一段（事故三） |
| 「有 HNSW 就叫能检索」 | 线上 90% 的查询带过滤条件，而过滤与图遍历是**天然对立**的两件事 | 结果为空且不报错（事故一，→ comp/26、→ architect/18） |

### 唯一真问题

> **向量检索真正的难点不是「把向量存进去并算余弦」，而是「带标量过滤的 ANN」——过滤越严，pre-filter 的子集越小、post-filter 的结果越空、图内过滤的邻居越容易被剪断；三种策略没有全局最优，只有「按过滤选择性选路」，而这件事必须在设计期定，上线后改不动。**

「上线后改不动」不是夸张，是物理约束：换策略要改的是**索引结构**（要不要按过滤维度分区、要不要为标量字段建 payload 索引、要不要把状态字段同步进向量库），而这三件事都需要**重建索引**。而重建索引的窗口是机时（27.9 账四）。所以这条路是单向门：**选择性 → 策略 → 索引布局**，顺序不能倒。

## 27.3 两条路线：嵌入式库 vs 独立服务

向量检索从「一段代码」变成「一个系统」，中间隔着的不是算法，而是**六件脏活**：持久化、崩溃恢复、分片、副本、索引构建调度、备份。谁来干这六件事，决定了你选的是哪条路线。

| 谁干这六件脏活 | 代表 | 它的「集群」是什么 |
| --- | --- | --- |
| **嵌入式库**（in-process） | faiss、hnswlib、Annoy | 没有集群。索引是一个**文件 / 一段内存**，你的进程就是它的宿主 |
| **宿主内建索引**（扩展形态） | pgvector、ES 的 `dense_vector`、Oracle Vector | 集群属于**宿主系统**（PG 的主备、ES 的分片），索引只是宿主里多出来的一个访问路径 |
| **独立服务**（server 形态） | Milvus、Qdrant、Weaviate、Vespa | **自己**有分片、副本、段、集合、索引构建任务，甚至自己的 WAL / 对象存储布局 |

### 图 1 · 两条路线的职责划分（谁兜住哪一层）

```text
┌─────────────────── 路线 A：嵌入式库 / 宿主内建索引 ───────────────────┐
│  你的业务进程 / 你的 PG 实例                                          │
│  ┌──────────┐    ┌────────────────┐    ┌─────────────────────────┐   │
│  │ 业务事务  │──► │ 堆表 + vector 列 │──► │ HNSW/IVFFlat 索引（同库）│   │
│  └──────────┘    └────────────────┘    └─────────────────────────┘   │
│  持久化 = 宿主的 WAL + checkpoint（免费获得，且与业务数据同一事务）    │
│  扩容   = 宿主的（分库分表 / 只读副本 / 单机垂直扩）                   │
│  备份   = 宿主的（pg_dump / PITR / 快照）；代价随表大小线性涨           │
└──────────────────────────────────────────────────────────────────────┘
┌─────────────────── 路线 B：独立服务 ──────────────────────────────────┐
│  客户端 ──gRPC/HTTP──► 协调层（元数据 + 调度）──► 分片/段 ──► 副本     │
│  持久化 = 自己的（对象存储 + 消息日志 / 自己的 WAL，随目标版本而定）    │
│  扩容   = 自己的（加分片、迁段、换副本因子）；键选错则无法重切          │
│  备份   = 自己的（collection/段 快照 + 元数据导出）；粒度常为天级       │
│  另外多出：索引构建任务队列、段加载、一致性等级、版本升级的重建成本      │
└──────────────────────────────────────────────────────────────────────┘
```

**图 1 最重要的一格是左下角**：路线 A 的持久化与事务是**免费**的（宿主已经写了十年），路线 B 的持久化是**自己新造的一份**，而它天生比宿主弱——因为向量的权威源在别处，这份持久化只需要「够恢复派生数据」，产品自然不会给你 PITR（点到任意秒）这种待遇。这跟 `→ comp/19 §19.3` 里「RocksDB 给单机 LSM，跨节点复制要自己加一层共识」是同一个形状：**库只保证到「这台机器的盘」，服务才把脏活接管，而接管了就一定收钱。**

### 库 vs 服务：五列一张表

| 维度 | faiss（库） | pgvector（宿主内建） | Milvus / Qdrant（服务） |
| --- | --- | --- | --- |
| **谁负责持久化** | 你自己：`write_index()` 到文件，什么时候写、写没写完、机器挂了丢多少，全归你 | **PG**：向量跟着行一起进 WAL / 页面 / 主备复制，**与业务字段同一事务、同一 RPO** | 服务自己：写入先进 WAL/日志，再由 DataNode 落成段与对象存储；**RPO 由一致性等级与副本机制决定** |
| **谁负责扩容** | 你自己（内存不够就砍数据或换机器），没有分片概念 | 宿主：分库分表 / 只读副本；**单表向量索引不能跨机器**，超单机就是换零件 | 自己：加分片（shard）/ 加副本；**分片键一旦定错，重切要重灌数据** |
| **备份怎么做** | 复制索引文件（几百 GB 起），且必须与元数据对齐 | `pg_dump` / `pg_basebackup` / PITR / 云盘快照——**工具链现成**，但体积随表涨 | collection 快照（或段文件 + 元数据）；**常常不支持 PITR**，粒度多为「上次快照」 |
| **一致性语义** | 无（就是内存结构） | 强一致（同一事务内可见），`READ COMMITTED` 起就够用 | 客户端声明的等级：强 / 有界 / 会话 / 最终（27.6） |
| **什么时候选** | 离线批量算、评测、一次性召回；或作为自研服务的内核 | **行数 ≤ 千万量级、要求向量与业务数据同事务、且过滤条件能被 B-tree 高效缩小** | 亿级、多租户、需要独立扩缩容与多副本可用性；团队愿意多养一套服务 |

一句话把这张表压成判断：**「向量和业务数据必须一起对」→ 路线 A；「向量数据量自己就是一个系统」→ 路线 B。** 两条都想要的人，最后都写了一个「双写 + 对账」的组件——而那就是路线 B 欠下的债（事故三）。

## 27.4 pgvector：把向量放进事务里

### 物理形态：它只是「一个 varlena 列 + 一个索引方法」

pgvector 没有发明任何新东西，它做了两件极其朴素的事：把 `vector(d)` 实现成一个变长列类型（二进制：维度头 + d 个 float32），把 `ivfflat` / `hnsw` 实现成 PG 可插拔的**索引访问方法**。于是它的全部行为都能从 PG 的物理形态推出来（→ [11 PostgreSQL 对照](11-postgresql-heap-and-vacuum.md)）：

| 事实 | 数值 / 量级 | 推出的行为 |
| --- | --- | --- |
| `vector(768)` = 768 × 4 B + 头 | ≈ 3,072 B/行 | 一行 3 KB 已经不是「小行」；超过 TOAST 阈值（默认 2 KB 量级，以该版本文档为准）时**向量被外置到 TOAST 表**，行内只留 18 B 指针 |
| 向量在**堆表**里，邻居表在**索引**里 | 空间 = 向量 × 2（堆 + 索引）+ 邻居表（≈ 2M × 4 B/点） | 建索引之后，同一份数据占两倍盘 |
| 索引条目带 **TID**（堆指针） | 6 B | 行被 UPDATE 后 TID 变了 ⇒ 旧索引条目变成死条目，等 VACUUM 收尸 |
| 图/簇是**增量维护**的 | 每次 INSERT 都要在索引里插点、并把邻居列表回写 | 一条 INSERT 写的不只是一行，而是**十几个页** |

```sql
-- pgvector 0.7/0.8 语法；函数名、参数默认值以该扩展 README 为准
CREATE EXTENSION IF NOT EXISTS vector;

CREATE TABLE product_vec (
  id          bigserial   PRIMARY KEY,
  category_id int         NOT NULL,
  status      text        NOT NULL,
  updated_at  timestamptz NOT NULL DEFAULT now(),
  embedding   vector(768) NOT NULL
);

-- ① 向量索引：一次灌入、长期读 → HNSW；构建慢、吃 maintenance_work_mem
CREATE INDEX product_vec_emb_hnsw ON product_vec
  USING hnsw (embedding vector_cosine_ops) WITH (m = 16, ef_construction = 64);

-- ② 标量索引：让「先过滤」这条路有可能被优化器选中（27.5 的关键）
CREATE INDEX product_vec_cat_status ON product_vec (category_id, status);

-- ③ 查询期旋钮：不在索引里，按会话设
SET hnsw.ef_search = 100;
-- 0.8.0 起另有 hnsw.iterative_scan 与 hnsw.max_scan_tuples，
-- 取值与默认值以该版本 README 为准（它是「图内过滤」的官方形态）

-- ④ 混合查询：注意它可能被计划成 post-filter，必须看计划
EXPLAIN (ANALYZE, BUFFERS)
SELECT id, 1 - (embedding <=> $1) AS score
FROM   product_vec
WHERE  category_id = 42 AND status = 'online'
ORDER  BY embedding <=> $1
LIMIT  100;
```

### 从形态推出的三条推论

| 推论 | 你买到了什么 | 你付了什么 | 什么时候必须换路 |
| --- | --- | --- | --- |
| **① 向量与业务数据在同一事务里**（本篇要强调的第一优势） | 不需要「两份存储一致性」：不需要 CDC、不需要对账、不需要 outbox；`DELETE FROM` 之后向量与业务字段**同时消失**（合规删除一次就够）；崩溃恢复由 PG 的 WAL 统一兜住 | 向量写与业务写抢同一个 WAL、同一组 buffer、同一把锁；大批量灌向量会把业务表的 checkpoint 拖爆；长事务让索引膨胀（见③） | 表写速率或向量行数超过单机承载（千万行量级之上）→ 路线 B |
| **② 索引与堆表分离 → 向量索引也要付写放大** | 查询只碰索引页；点查、过滤、排序能复用同一套执行器 | 每行向量存两遍（堆 + 索引）；每次 INSERT 还要回写被选为邻居的已有点的邻接表；量化：一条 INSERT 的逻辑写 3 KB，物理写 ≈ 堆页 + TOAST 块 + 索引条目 + 邻接表回写 + WAL ≈ **2–3 倍**（不含后续 VACUUM 与索引整理） | 单表向量索引体积 > 机器内存的一半 → 走量化，或换独立服务 |
| **③ MVCC / VACUUM 语义直接套到向量索引上** | 快照读、并发一致性、`READ COMMITTED` 隔离——全部免费继承 | 每次 UPDATE 产生新 TID，索引里留下死条目；**但 HNSW 的图不能靠 VACUUM 重连**，只能让死条目占着内存、吃掉 `ef_search` 的候选预算（→ comp/26 的「墓碑吃掉有效宽度」）；空间膨胀只能靠 `REINDEX` 收回，而 `REINDEX` 就是一次全量重建 | 某列月变更率 > 20%，或向量需要频繁重算（模型升级）→ 不要在这种列上建 HNSW |

**第③条是本篇与 [11 PostgreSQL 对照](11-postgresql-heap-and-vacuum.md) 唯一的接口**：PG 的 VACUUM 能回收堆与 B-tree 的死条目，因为 B-tree 是「按键有序的结构」，删掉一条不影响其他条的可达性；而 HNSW 是「互相引用的图」，删一个点会让别的点失去通路（→ comp/26 的连通性论证）。所以**向量索引没有 HOT 更新，也没有就地整理**——它的唯一维护手段是重建。这一点直接决定了 27.8 的运维形态。

### pgvector 的边界（不是「行不行」，是「装不装得下」）

| 规模 | 向量本体 | HNSW 索引 | 判断 |
| --- | --- | --- | --- |
| 100 万 × 768 | 3.1 GB | ≈ 3.3 GB | 舒服。单机直接上，事务一致性白拿 |
| 1,000 万 × 768 | 31 GB | ≈ 33 GB | 可行，但构建要预热的 `maintenance_work_mem`、要 `max_parallel_maintenance_workers`，且**不能再和业务大表抢同一台机** |
| 1 亿 × 768 | 307 GB | ≈ 330 GB | 单表索引远超单机内存 ⇒ 查询变成随机 IO；只有「一查一重」的离线场景能忍 |
| 100 亿 × 768 | 30.7 TB | — | 不是调参问题，是形态问题（27.9 账三） |

> 版本纪律：pgvector 的 `hnsw` 支持 `CREATE INDEX CONCURRENTLY`，但并发构建更慢、日志更多；`ivfflat` 需要「先有数据再建索引」（`lists` 与数据量相关，建索引时数据太少会导致簇心失真）——**具体行为与参数建议以该扩展版本文档为准**，不要照抄别处的经验值。

## 27.5 混合检索：pre-filter、post-filter 与图内过滤

这是本篇的支点。线上 90% 的语义查询长这样：`WHERE tenant=42 AND status='online' AND category IN (...) ORDER BY distance LIMIT 10`。而 ANN 索引只会一件事：**在全体向量里按距离走图**。它完全不明白 `status` 是什么。

于是只有三条执行路径，每一条都有一个**随过滤选择性单调恶化的崩点**。

### 图 2 · 三条路径与它们各自的死法

```text
① post-filter（先 ANN 取 k 条，再丢掉不合格的）
   query ──► 图遍历（全库，ef=128）──► top-k ──► WHERE status='online' ──► 结果
                                          │
                                          └─ 崩点：k 条里合格的比例 ≈ s（选择性）
                                             s=1% → top-100 剩 1 条 → 空结果，且不报错

② pre-filter（先算出合格 id 集，再在这个子集上算距离）
   query ──► 标量索引/位图 ──► id 集(n_s = N×s) ──► 子集上算距离（暴力）
                    │
                    ├─ n_s ≤ 10⁵：可行，延迟 = n_s × d × 4B / 带宽
                    └─ n_s ≥ 10⁶：等于全扫 → 有索引等于没索引

③ 图内过滤（HNSW 遍历时检查每个候选点是否合格）
   query ──► 访问点 A（不合格，当跳板）──► 邻居 B（不合格）──► ...
                    │
                    ├─ 允许「穿越」不合格点：连通性保住，但要访问 ~1/s 个点才捞到一个合格的
                    │                        ⇒ 退化成 post-filter 的成本
                    └─ 不允许穿越（剪枝）：M0≈32 个邻居里合格 ≈ 32×s 个，
                                            s=1% → 0.32 个 ⇒ 有效度数 <1，图断裂
                                            ⇒ 召回塌到接近 s 的水平
```

### 先算账：post-filter 的可用边界

```
要拿到 k 条合格结果，过滤选择性 s ⇒ 必须先取 k' = k / s 条候选
   s = 50%   → k' = 200      P99 ≈ 6 ms      可接受
   s = 10%   → k' = 1,000    P99 ≈ 30 ms     勉强
   s = 1%    → k' = 10,000   P99 ≈ 300 ms    吞吐 ÷78，且 top-10,000 的召回本身在掉
   s = 0.1%  → k' = 100,000  比「直接暴力扫子集」更慢更不准
⇒ 量级结论：post-filter 的可用边界是 s ≥ 10%；s < 1% 时它只是在骗自己。
```

推导里的三个假设必须写出来（否则这行数字不能引用）：① 单查成本近似与候选预算 `ef` 成正比（图遍历每扩一次候选队列要多算 O(log) 个距离，`→ comp/26` 给了同一条量级的成本模型）；② 基线 `ef=128` 时 P99 = 4 ms、单节点 1,750 QPS；③ 过滤在应用层做，所以过滤本身不花服务端 CPU。换机器、换索引参数会把这几个数整体缩放，**但「∝k/s」这个形状不变**。

### 图内过滤为什么不是万能解：两种实现的两种死法

这一点工程上最容易被讲错。同样叫「filterable HNSW」，内部有两种实现（Qdrant 按过滤基数在两种策略间切换，具体阈值以目标版本文档为准；pgvector 的 `iterative_scan` 属于「允许穿越 + 分批扩大扫描」那一类）：

| 实现 | 遍历规则 | s 大时 | s 小时 | 它其实等价于 |
| --- | --- | --- | --- | --- |
| **剪枝式** | 不合格点既不进结果、也不进候选队列（等于图上被删掉） | 好：几乎没有损失 | **图断裂**：有效度数 <1，召回接近随机 | pre-filter 的最坏情况 |
| **穿越式** | 不合格点不进结果，但可以作为跳板继续走 | 好 | 成本 ≈ 1/s × 基线：等于用「多访问点」换「不漏」，实质是候选预算放大 | post-filter（成本那一半） |

**结论（锚 `→ comp/26`）**：图内过滤不消灭矛盾，它只是把矛盾挪到「有效度数」与「候选预算」两个旋钮上。想让 s < 1% 的查询又准又快，唯一的办法是**让过滤变成索引结构的一部分**——按过滤维度分区（分区键 = 查询必带的字段），让每个查询只在一个「图完整、候选充足」的小索引里跑。这条结论在 `→ architect/18 §18.7` 已经用完整的换挡表写过一遍，本篇只补一句工程侧的话：**分区键必须在建 collection/建表时定，定错了只能重灌数据。**

### 判定表：按选择性选路

| 过滤选择性 s | 合格子集规模 | 该用哪种策略 | 风险（真正的那个） |
| --- | --- | --- | --- |
| > 50% | 任意 | **post-filter 可以接受**（k' = 2k） | 全局 s 会骗你：候选池内的 s 可能远低于全局 s（事故一里全局下架率 4%、候选池内 97%） |
| 10%–50% | 任意 | **图内过滤**（穿越式）+ 标量索引下推 | 延迟 +10~30% 是常态；必须实测 recall，不能只看延迟 |
| 1%–10% | > 10⁶ | **分区索引**（分区键 = 过滤里最热、且查询必带的字段） | 分区数上千后每个小分区的图质量变差（点少、边稀） |
| 1%–10% | ≤ 10⁵ | **pre-filter 暴力**（子集上算距离） | 子集一变大延迟线性涨，必须设「子集上限 → 降级」开关 |
| < 1% | 任意 | **必须分区**（分区内再 hybrid）；否则这个功能不该用向量索引 | post-filter 返回空；剪枝式图内过滤召回崩；pre-filter 退化成全扫 |
| 任意，但 s 波动剧烈 | — | 候选不足时按 `k×10` 放大重试（最多 2–3 轮）**并封顶** | 无上限重试 = 高峰期自己打出雪崩（P99 可达均值的 4 倍） |

### 代码：把命中率算出来，别猜

```python
import math

def post_filter_budget(k=100, s=0.01, ef_base=128, lat_base_ms=4.0, qps_base=1750):
    """s: 过滤选择性（合格比例）。返回这一档选择性下 post-filter 的真实代价。
    假设：单查成本 ~ 候选预算 ef；ef=ef_base 时 P99=4ms、单节点 1750 QPS（量级结论）"""
    k_req  = math.ceil(k / s)              # 要拿到 k 条合格结果，必须先取这么多候选
    ef_req = max(k_req, ef_base)           # 候选预算必须 >= k_req，否则前排直接被截断
    mult   = ef_req / ef_base
    return dict(hits=k * s, k_req=k_req, ef_req=ef_req,
                p99_ms=lat_base_ms * mult, qps=qps_base / mult, mult=mult)

for s in (0.5, 0.1, 0.03, 0.01, 0.001):
    r = post_filter_budget(100, s)
    flag = "可接受" if r["mult"] <= 3 else ("不可接受" if r["mult"] > 20 else "边缘")
    print(f"s={s:6.1%} 期望命中={r['hits']:7.2f} 条  k'={r['k_req']:>6d}  "
          f"P99≈{r['p99_ms']:7.0f}ms  QPS≈{r['qps']:7.1f}  ×{r['mult']:5.0f}  {flag}")
# s= 1.0% 期望命中=   1.00 条  k'= 10000  P99≈    300ms  QPS≈   22.4  ×   78  不可接受
# 这一行就是事故一：用户搜「连衣裙」看到 3 条，而 P99 比基线还低
```

### pgvector 特有的坑：你写了 `WHERE`，不代表它先过滤

在 PG 里，「先过滤」和「先 ANN」不是由 SQL 写法决定的，而是**由优化器成本估算决定的**。同一条 SQL，可能被计划成：

- `Index Scan using product_vec_emb_hnsw` + `Filter: category_id = 42` —— **运行时丢弃**，等价 post-filter；
- `Bitmap Index Scan on product_vec_cat_status` + `Sort` —— 只在子集上算距离，等价 pre-filter 暴力。

两条路的成本模型随数据分布变化，**上线前是 A、上了量之后翻成 B**（或者反过来）。所以纪律只有一条：**混合检索的 SQL 必须带 `EXPLAIN (ANALYZE, BUFFERS)` 进上线检查单，并且把 `Rows Removed by Filter` 做成一个被监控的数字**。这个数字就是 post-filter 的直接证据——它涨，就是你的召回在掉。

## 27.6 Milvus 形态：段、异步建索引与一致性等级

Milvus 是「把 Lucene 的段思想搬到向量上」的分布式实现：**写入不修改任何已有结构，而是不断生产新的不可变单元**，再把不可变单元批量建索引。理解这一条，它的三条纪律（异步建索引、一致性等级、段加载）就全部是推论。

### 三层容器：collection → partition → segment

| 层 | 是什么 | 谁决定 | 工程后果 |
| --- | --- | --- | --- |
| **collection** | 逻辑表：schema + 索引定义 + 一致性等级 + 副本数 | 建表时定 | 换 schema（加字段、换维度、换度量）要新建 collection 重灌 |
| **partition** | collection 内的物理分组，查询可限定在其中一部分 | 写入时指定，或用 **partition key**（按某标量字段哈希，客户端无感） | **这就是 27.5 说的「让过滤变成索引结构的一部分」的落地手段**；分区键选错，查询只能 fan-out 全部分区 |
| **segment** | 真正存数据与索引的单元：一段向量 + 对应的倒排/标量索引 + 图 | DataNode 按写入量/时间自动切 | 查询的执行单位；段越多（碎段、增长段多）→ 每次查询要碰的段越多，延迟上抖 |

### 图 3 · 增长段 → 封存段 → 建索引（写入与查询的时序）

```text
写入（流式）                                            查询
gRPC ─► Proxy ─► WAL / 日志流                              Proxy ─► QueryNode ─► 已加载的段
                   │                                                  │
                   │ DataNode 按「行数/字节/时间」攒批                 ├─ 增长段 growing：
                   ▼                                                  │  可写、在内存、可能还没索引
            ┌──────────────────┐   封存(seal)   ┌──────────────────┐  │  ⇒ 只能暴力扫（慢）
            │ 增长段 growing    │ ────────────► │ 封存段 sealed     │  │
            │ 可写 / 只进内存   │               │ 只读 / 可建索引    │◄─┴─ 封存段 sealed：
            └──────────────────┘               └────────┬─────────┘     有索引 ⇒ 走图（快）
                                                        │
                                    create_index = 异步作业（不是同步 DDL）
                                                        ▼
                              IndexNode 后台建索引 ──► 索引文件落对象存储 ──► QueryNode 加载
                              期间：查询继续用「暴力 / 旧索引」跑，不阻塞写入
```

**图 3 的三条推论，就是本节其余全部内容**：

1. **`create_index` 是后台作业**，不是阻塞 DDL。它返回成功只意味着「任务已提交」。任务进度、失败重试、失败后集合是否还能查，全部要单独观测（27.12）。而任务**失败**时最常见的结果是「查询一直在暴力扫」——**性能塌了但功能正常**，所以没人报警。
2. **「插入成功」≠「可查」**：数据先进 WAL，被 DataNode 消费成段，封存后建索引，最后被 QueryNode `load`。这条链上任何一步没完成，数据就在库里但查不到。「插入后立刻查查不到」是这条链的正常行为，只有一致性等级能改变它。
3. **段是执行单位，也是开销单位**：一次查询要打到所有相关段再归并，段数越多 → 延迟越高、`ef` 预算被摊薄。这跟 ES 的「段数/分片数决定查询开销」是同一个形状（→ comp/22）。

### 角色分工（谁负责哪一段流水线）

| 角色 | 干什么 | 挂掉会怎样 | 观测入口 |
| --- | --- | --- | --- |
| **Proxy** | 客户端入口：鉴权、路由、结果归并 | 客户端连不上；已有连接可能还活着 | 各版本有 Proxy 侧指标（以目标版本 metrics 输出为准） |
| **Coordinator**（root / query / data / index，按版本可能是多进程或合并） | 元数据、拓扑、任务调度 | **新请求全部失败**（这是真正的单点形态风险）；已有段仍可被查 | 协调层日志 + 元数据服务（etcd 类）健康 |
| **DataNode** | 消费 WAL，把数据打包成段、flush 到对象存储 | 数据积压在 WAL 里：**能写不能查**（段不产出） | WAL 消费延迟 / 未 flush 的消息数 |
| **IndexNode** | 构建向量索引 | 段永远停在「无索引」状态，查询持续暴力扫 | 构建任务队列长度、单任务耗时 |
| **QueryNode** | 加载段、执行查询 | 该节点上的段不可查；副本不足则部分查询失败 | 段加载状态、内存占用、查询延迟 |

### 一致性等级：它唯一回答的问题是「我能不能读到自己刚写的」

| 等级 | 机制 | 能否读己之写 | 延迟代价 |
| --- | --- | --- | --- |
| **Strong** | 查询携带时间戳，等到相关段都消费到该时间点才返回 | ✅ 保证 | 最高：要等一次跨组件同步（同机房 ms 级，跨 AZ / 段未封存时更久） |
| **Bounded** | 允许落后一个时间窗（默认秒级，**以目标版本官方文档为准**） | ⚠️ 通常能，不保证 | 低 |
| **Session** | 保证同一客户端会话内读到自己刚写 | ✅ 对**本会话**保证，其他客户端可能看不到 | 低 |
| **Eventually** | 不等待，立即返回 | ❌ 不保证 | 最低 |

> 版本纪律：等级名称与默认值在 2.x 各版本间稳定，但「Bounded 的具体时间窗」「默认等级是什么」「`flush()` 之后是否就一定可见」「`load()` 与 `release()` 的副作用」这几件事**都随版本变过**——一律以目标版本官方文档与 release notes 为准。别把别处的默认值当契约写进代码注释。

### 代码：三个参数必须一起给（等级 + 过滤 + ef）

```python
from pymilvus import connections, Collection, CollectionSchema, FieldSchema, DataType

connections.connect(alias="default", host="milvus", port="19530")

fields = [
    FieldSchema("id",          DataType.INT64,        is_primary=True),
    FieldSchema("category_id", DataType.INT64),
    FieldSchema("status",      DataType.VARCHAR,      max_length=16),
    FieldSchema("embedding",   DataType.FLOAT_VECTOR, dim=768),
]
col = Collection("product_vec", CollectionSchema(fields), consistency_level="Bounded")

# ① 建索引是异步作业：立刻返回，IndexNode 后台构建；期间查询走暴力
col.create_index("embedding", {"index_type": "HNSW", "metric_type": "COSINE",
                               "params": {"M": 16, "efConstruction": 200}})
col.load()                       # ② 段加载进 QueryNode 之后才可能被查到

col.insert(rows)                 # 先进 WAL → 增长段；此时未必可查
col.flush()                      # 只保证「攒成封存段」，不等于「立即可见」

res = col.search(
    data=[q], anns_field="embedding", limit=100,
    param={"metric_type": "COSINE", "params": {"ef": 128}},   # ③ 查询期旋钮：写死就是写死
    expr='status == "online" and category_id == 42',          # 过滤下推，不是返回后再丢
    output_fields=["status"],
    consistency_level="Strong",                              # ④ 读己之写的唯一开关
)
```

## 27.7 Qdrant 与其它形态的差异点

只写与 Milvus 不同的地方，各两条。

| 差异点 | Qdrant 怎么做的 | 与 Milvus 的差别 → 工程后果 |
| --- | --- | --- |
| **进程形态** | 一个 Rust 单二进制，单机跑不依赖 etcd / 对象存储 / 消息队列；分布式模式才需要额外组件 | Milvus 天生是多组件栈，装起来就要一套协调层 + 对象存储 + 日志流。**后果**：千万级以下，Qdrant 的运维面小一个量级；但正是那套多组件让 Milvus 能干净地水平扩到亿级 |
| **payload 索引与向量索引并存** | 段内同时维护向量 HNSW 与 payload 的倒排 / 数值 / 地理索引，**filter 在遍历中生效**，并按过滤基数自动在两种遍历策略间切换 | Milvus 走 partition / partition key + `expr` 下推标量索引。**后果**：27.5 的「图内过滤」在 Qdrant 是默认路径，而在 Milvus 上更依赖分区设计——所以「按选择性选路」在两边的工作量完全不同 |
| **`on_disk` 与内存** | 向量、量化码、HNSW 索引、payload 索引都可**分别**配置在内存或 `on_disk`（mmap），内存只留热点结构 | Milvus 的段原则上要 `load` 进 QueryNode 内存才可查（有 mmap 相关选项，随版本）。**后果**：同样一台盘大的机器，Qdrant 能装十倍向量，代价是 P99 抖动变大、依赖 page cache 命中 |
| **一致性表达方式** | 用 `write_consistency_factor`（写入要几个副本确认）+ 请求级 `consistency`（weak / majority / all） | Milvus 是四档命名等级（Strong / Bounded / Session / Eventually）。**后果**：迁移时参数不能照抄；Qdrant 更接近「按请求声明读写副本数」，Milvus 更接近「按时间戳声明新鲜度」。具体取值与语义**以目标版本官方文档为准** |
| **分片语义** | 默认按点哈希分 shard（`shard_number` / `replication_factor`），也支持按 payload 字段做 custom sharding | Milvus 用 partition + partition key，语义是「查询可限定范围」而非「按哈希摊平」。**后果**：Qdrant 的哈希分片不能当成「按租户隔离」用——那需要 custom sharding 或每个租户一个 collection |
| **备份粒度** | 有 collection / 整个存储的 snapshot API，可以只对某个 collection 打快照 | Milvus 通常用独立的备份工具（快照 + 元数据导出）。**后果**：两者都**不提供 PITR**（不能恢复到任意秒），备份粒度就是你的 RPO |

```python
from qdrant_client import QdrantClient, models

client = QdrantClient(url="http://qdrant:6333")

# ① payload 索引不是可选项：没有它，filter 只能"先取再丢"（退化 post-filter）
client.create_payload_index("product_vec", field_name="status",
                            field_schema=models.PayloadSchemaType.KEYWORD)
client.create_payload_index("product_vec", field_name="category_id",
                            field_schema=models.PayloadSchemaType.INTEGER)

f = models.Filter(must=[
    models.FieldCondition(key="status",      match=models.MatchValue(value="online")),
    models.FieldCondition(key="category_id", match=models.MatchValue(value=42)),
])

hits = client.search(
    collection_name="product_vec",
    query_vector=("embedding", q),
    query_filter=f,                                   # 过滤进索引，不是返回后过滤
    search_params=models.SearchParams(hnsw_ef=128, exact=False),  # exact=True 用于造真值集
    limit=100,
    with_payload=["status"],
)
# 客户端 1.9+/1.10+ 起 search 逐步迁到 query_points，函数名以目标版本客户端文档为准
```

## 27.8 运维形态：备份、重建与升级

这一节是本篇的支点二，也是最容易在架构评审里被一句「备份有快照」带过去的地方。

### 为什么「导出成 JSON」不是一个方案

| 表达形式 | 1 条 768 维向量占多少 | 1 亿条合计 | 能不能直接用 |
| --- | --- | --- | --- |
| 二进制 float32（mmap 可加载） | 3,072 B | **307 GB** | ✅ 加载即用，图结构若一起存则免重建 |
| JSON 文本（每浮点 8–11 字符） | ≈ 8–9 KB | **800–900 GB** | ❌ 膨胀 2.6–2.9×，且**图结构存不下来** |
| CSV | ≈ 8 KB | ≈ 800 GB | ❌ 同上，还要处理精度与解析 |

**关键不是体积，是「图的不可导出性」**：HNSW 的索引是「谁指向谁」的邻接关系，它只对构建它的那版二进制有意义。你导出的只是**输入**（向量），不是**结果**（索引）。所以「从备份恢复」在向量库这里有两档完全不同的代价：

- **段/索引文件快照**（含索引）：恢复 = 拷贝 + 加载（分钟级到小时级，取决于盘带宽）。
- **向量数据导出**（不含索引）：恢复 = 拷贝 + **重算所有距离重建图**（机时，27.9 账四）。

第二档就是事故二那个 9 小时。第一档才是你真正想要的，但它的副作用是「格式与版本绑死」——**能直接加载的快照，只有同一版本能加载**。

### 故障 / 升级 × 恢复路径 × 时长 × 要不要重建

| 故障 / 变更 | 恢复路径 | 时长量级 | 要不要重建索引 |
| --- | --- | --- | --- |
| QueryNode / 查询节点 OOM 或挂 | 副本接管 + 重新 `load` 段 | 分钟级（∝ 段大小 ÷ 盘带宽） | 不要 |
| 协调层 / 元数据服务不可用 | 恢复元数据（etcd 类快照）+ 重新拉起协调层 | 分钟到小时 | 不要（元数据没丢时） |
| 少量段文件损坏 | 从对象存储 / 其他副本重拉该段 | 分钟级 | 不要（只重拉坏段） |
| 索引构建任务大面积失败 | 修掉失败原因（内存、磁盘、超时）后重跑任务 | 小时级 | **只重建索引**，不重算向量 |
| 升级：索引格式兼容 | 滚动重启 + 加载段 | 10–60 min | 不要 |
| **升级：索引格式不兼容** | 停写 → 全量重建 → 抽样校验 → 切流 | **1 亿条 2–3 h；2.4 亿 × 1024 维 8–10 h**（事故二） | **必须**，且期间没有回滚点 |
| 换 embedding 模型（维度或语义变） | 双写 + 双索引并行 + 灰度切读 | 天级（含重算 embedding） | **必须**，且**向量要重算** |
| 误删 collection / 表 | 从最近快照恢复 | 快照时间 + 导入时长 | 取决于快照是否含索引 |
| 磁盘写满 | 扩盘 / 下掉墓碑段 / 提高量化压缩 | 分钟到小时 | 墓碑占比 > 30% 时要重建才回收 |
| 副本落后 / 切主后数据缺一段 | 从上游权威源补 + 重算 + 对账 | 小时级 | 不必重建，但**必须能补**（事故三证明很多人不能） |
| 跨大版本升级（架构变化） | 读官方升级路径，常需「新集群 + 灌数据 + 切流」 | 天级 | 必须（新集群天然重建） |

### 多副本的真相：向量库的副本常常是异步的

必须讲清的一个事实：**独立向量服务的多副本，绝大多数场景下只保证「最终一致」**。副本追主靠的是日志/段的异步复制，而向量数据的体量让「同步复制」的代价高得离谱（一份 300 GB 的索引，同步写 = 每次写入都等对面把段刷下来）。所以：

1. **切主必然丢最后一段**——丢多少由复制延迟决定，不由你的期望决定（事故三丢了 40 分钟）。
2. **丢的那一段，只能从上游权威源补**——所以「上游能不能重算 embedding」是一个必须在设计期回答的问题，不是运维细节。
3. **副本数不是可用性开关，是成本开关**：每多一份副本 = 多一份内存（若全内存）+ 多一份盘 + 多一次索引构建（构建也翻倍）。

### 命令骨架：备份与重建的三个必须

```bash

pg_dump -Fc -d app > app.dump                        # 逻辑备份：慢、体积 ≈ 表大小
pg_basebackup -D /backup/base -Ft -z -P              # 物理备份：配合 WAL 归档才能 PITR

                pg_size_pretty(pg_total_relation_size('product_vec'))    AS tbl;"
```

## 27.9 三本账：存储、过滤陷阱与重建机时

四个算例，全部给乘法链。每个末尾标「量级结论」还是「承诺值」，量级结论都附假设清单，方便换假设复算。

### 账一 · 1 亿条 × 768 维的盘与内存

```
向量本体        = 1e8 × 768 × 4 B                = 307.2 GB     (1.00×)
HNSW 图         = 1e8 × (2M × 4 B)，M=16 → 128 B  =  12.8 GB     (+4%)
ID / 偏移 / 删除标记 = 1e8 × 64 B                 =   6.4 GB     (+2%)
标量字段 + 标量索引 = 1e8 × 200 B（估）            =  20.0 GB     (+7%)
单副本逻辑合计                                    = 346.4 GB
墓碑 / 碎段 / 版本冗余 ×1.15                      = 398 GB
× 2 副本（第二份同样占盘）                         = 797 GB ≈ 0.8 TB
构建期第二份索引（整库重建，非滚动）                = +398 GB ⇒ 峰值 ≈ 1.2 TB

内存侧（要求全内存常驻才谈得上 4 ms）：
  单副本热数据 = 向量 + 图 = 307 + 13 = 320 GB
  2 副本 = 640 GB RAM      ← 这才是真正的预算项
  叠 int8 量化：向量 76.8 GB ⇒ 单副本 ≈ 106 GB，2 副本 ≈ 212 GB（省 3.3×，recall 掉 1–2 点）
```

**量级结论**（±20%）。假设：① 768 维 float32、无稀疏字段；② M=16，邻居表按 2M 条边估；③ 标量字段含 `status/category_id/时间` 与一个倒排；④ 副本 2；⑤ 冗余系数 1.15（含墓碑与碎段）。换 M=32 会把图从 12.8 GB 抬到 ~26 GB（+4%），**不改变结论**；换 int8 会整体砍 3 倍，**这一项才是能动的旋钮**。

### 账二 · post-filter 陷阱：1% 选择性下的真实代价

```
要拿到 k = 100 条合格结果，选择性 s = 1%：
  先取候选 k' = k / s = 100 / 0.01 = 10,000 条
  top-100 里期望合格数 = 100 × 1% = 1 条          ← 事故一的那 3 条

延迟放大：候选预算 ef 必须 ≥ k'，即 128 → 10,000（78×）
  单查 P99：4 ms × 78 ≈ 300 ms
  单节点吞吐：1,750 QPS ÷ 78 ≈ 22 QPS
  要维持原 QPS：节点数 × 78
成本换算：假设单节点 ¥12.8 万/年、原 12 节点 ¥154 万/年
  ⇒ 154 万 × 78 ≈ 1.2 亿元/年   ← 结论不是"贵"，是"这个功能不该这样实现"
```

**量级结论**。假设：① 单查成本近似 ∝ `ef`（`→ comp/26` 的图遍历成本模型）；② `ef=128` 时 P99 = 4 ms、单节点 1,750 QPS（同机房、768 维、单副本、无过滤）；③ 过滤在应用层做，服务端不感知。**注意 78× 这个数字会随基线 `ef` 变化，但「∝ 1/s」的形状不会**：s 再降 10 倍，放大倍数也再涨 10 倍。

### 账三 · pgvector：100 亿行表 + 一个 HNSW 索引

场景：100 亿行的明细表（分区表），其中 5 亿行需要向量（`embedding` 可空，其余 95 亿行只存业务字段）。

```
向量本体   = 5e8 × 3,072 B                     = 1.54 TB（TOAST 外置，堆表只多 18 B/行指针）
HNSW 索引  = 5e8 × (3,072 + 128 + 64) B        ≈ 1.63 TB
构建距离计算量 = 5e8 × 200 次/点               = 1.0e11 次
   （每点约 2 × ef_construction=64 次层内距离计算 + 各层贪心，取 200 的量级）
单次代价 = 768×2 flops + 3 KB 随机访存 + TOAST 回表取向量 ≈ 2–5 µs
  ⇒ 2e5 ~ 5e5 单核秒 = 55 ~ 139 单核小时
并行 max_parallel_maintenance_workers = 8、并行效率 40%
  ⇒ 17 ~ 43 h（还要加 WAL 与 checkpoint 的干扰，实际常再 ×1.5~2）
内存峰值：构建工作集与 maintenance_work_mem 同阶；
  1.63 TB 的索引不可能全在内存 ⇒ 构建期大量随机 IO（退化行为以该扩展版本文档为准）
```

**两条结论**：
① **量级结论**：5 亿行要几十小时、一块 2 TB 的盘，以及一台装不下索引的机器——**单机 pgvector 的实用上限在千万行量级**（§27.4 的边界表）。
② 若 100 亿行全带向量：距离计算量 ×20 ⇒ **1,100–2,800 单核小时 ≈ 30–100 天**（8 并行）。这不是「慢」，是**形态不成立**——该做的是分片+独立服务（`→ architect/18` 的 L4/L5），或者干脆放弃「全量向量」而只对热数据做向量。

### 账四 · 重建机时：升级窗口到底够不够

```
建图机时 = N × 每点距离计算次数 × 单次代价 ÷ (并行度 × 并行效率)

A) 1 亿条 × 768 维（efConstruction=200，每点 ≈ 400 次距离计算）
   1e8 × 400 × 3 µs = 1.2e5 单核秒
   ÷ (64 线程 × 0.4) = 25.6  ⇒ ≈ 4,700 s ≈ 1.3 h
   加：拉数据 / 元数据重建 / 抽样校验 / 切流 ≈ 1 h
   ⇒ 单次全量重建 ≈ 2–3 h（低峰窗口 4 h：紧张但放得下）

B) 2.4 亿条 × 1024 维（事故二，单次代价按 4 µs）
   2.4e8 × 400 × 4 µs = 3.84e5 单核秒 ÷ (32 × 0.4 = 12.8) ≈ 3.0e4 s ≈ 8.3 h
   加校验与两次失败重试 ⇒ 9 h 40 min   ← 和事故二的停机时长对得上

C) 结论：窗口够不够，只看一个除式
   窗口(h) ≟ N × 每点次数 × 单次代价 ÷ 3600 ÷ (并行度 × 0.4) + 1 h
   放不下 ⇒ 唯一出路是分片滚动重建（单元 = 分片，不是集群）
   1 亿条、16 分片：单片 1.3 h ÷ 16 ≈ 5 min 建图，含校验与灰度 ≈ 20–30 min/片
```

**量级结论**。假设：① 每点距离计算次数 ≈ 2 × `efConstruction`（`→ comp/26` 的同一条成本模型）；② 单次 768 维 float32 距离计算 3 µs、1024 维 4 µs（含随机访存）；③ 并行效率 0.4（内存带宽与随机 IO 是共享资源）；④ 不含重新计算 embedding 的时间——**换模型时要把这一步单独加进去，它常常比建图更久**。

> 提醒一句：本文所有「小时」都是**机时**，不是**人时**。事故二的变更单写「预计 30 分钟」时，脑子里算的是重启时间（18 分钟）；真正决定窗口的是建图机时（8.3 小时）。**这两种时间差一个数量级，是向量库变更管理最常见的误判。**

## 27.10 架构边界：什么时候不该用向量库

### 能做什么 / 不能做什么 / 靠什么绕过

| 能做什么 | 不能做什么 | 靠什么绕过（以及绕过的代价） |
| --- | --- | --- |
| 在给定过滤条件下返回近似 top-k，recall 0.90–0.97 可调 | 保证精确 top-k（那是暴力扫，延迟由 `N×d×4/带宽` 决定） | 小规模直接 Flat；大规模用「召回 + rerank」两段式（多 3–5 ms） |
| 水平扩到亿级（分片 + 副本） | **换分片键**（分片键定了就只能重灌） | 上线前用「查询必带的过滤维度」当分片键；事后只能新建集合双写迁移 |
| 用一致性等级换新鲜度 | 提供跨系统的强一致（与业务库同一事务） | 用路线 A（pgvector）；或接受「双写 + 对账 + 补偿」这一整套债 |
| 用快照恢复到某个时间点 | **PITR 到任意秒**（多数产品只给「上次快照」） | 上游权威源必须可重算；把「重算 embedding 的时长」写进 RTO |
| 异步建索引，不阻塞写入 | 让索引构建的**时间**变短（它是 `N × 距离计算量`） | 分片滚动重建；或降低 `efConstruction`（用 recall 换机时） |
| 删除（软删 + 墓碑） | 立即释放空间与恢复图质量 | 墓碑 > 30% 就重建；定期重建写进日历 |
| 支撑多租户 | 用「返回后过滤」保住隔离与正确性 | 过滤必须下推到索引/位图；多租户场景 post-filter = 越权（`→ architect/18 §18.7`） |

### 系统级失效（只写这三件，使用级错误归 27.11）

| 失效 | 长什么样 | 为什么它是「系统级」 | 唯一有效的兜底 |
| --- | --- | --- | --- |
| **不可用：协调层 / 元数据打挂** | 新连接全失败、collection 列表都拉不出来；已有段可能还能查 | 拓扑与路由全在元数据里，它挂了就没有「哪个段在哪台机」这件事 | 元数据服务自身的高可用（etcd 类三节点）+ **降级开关**：把检索请求切到「倒排/关键词」或「热门兜底」，别让上游等超时 |
| **不一致：异步副本 + 双写漂移** | 切主丢最后一段（事故三）；或向量库与业务库长期漂移（0.1%~1% 的幽灵/缺失文档） | 向量库不产生权威数据，却可能**持有唯一副本**（业务字段也存进去时） | 权威源必须是业务库/对象存储；**定期抽样对账**（抽 1 万条比 `status/price`）；副本延迟进面板 |
| **成本失控：副本数 × 内存单价** | 账一那条链：320 GB/副本 × 2 × 单价 × 12 个月；加一个「为了稳」的第三副本再 ×1.5 | 向量库的成本是**容量的线性函数**，没有任何「冷热分层」自动生效的魔法 | 量化（int8 砍 3.3×）+ 冷热分层（热 5% 内存 / 冷 95% 盘）+ 把「每百万向量每月成本」做成一个被周周看的数 |

### ⑤ 扩展维度：四选一，选错就换零件

| 维度 | 在这个领域怎么落地 | 边界 / 单向门 |
| --- | --- | --- |
| **分片** | 按集合/租户/类目切；或按点哈希切 | 分片键 = **查询必带的过滤维度**；哈希分片会让每次查询 fan-out 全部片（若过滤与哈希无关） |
| **副本** | 提高查询吞吐与可用性 | 常常是**异步**的：买到可用性，买不到「不丢最后一段」 |
| **垂直切** | 不是拆列，是**减少每向量的字节数**：float32 → int8 → PQ → 磁盘型 | 每降一档 = recall 掉 1–5 点；PQ 后必须接 rerank 层 |
| **批处理摊薄** | 批量 insert、批量 query（一次请求 N 个向量）、批量重建 | 摊薄的是**固定开销**（RPC、锁、段查找），摊不掉距离计算量 |
| （四者都不成立的场景） | 单机、千万级、只读——那就不该上向量库，直接 faiss 文件 + Flat | 别为了「架构统一」引入一个服务 |

### 掉头信号（越过它，这个零件不再是正确选择）

| 信号 | 阈值 | 该换什么 |
| --- | --- | --- |
| 重建窗口超过低峰可用窗口 | 全量重建 > 4 h 且无法分片滚动 | 分片滚动重建；或改量化缩短机时 |
| 内存成本超过业务毛利可承受 | 每百万向量每月成本 > 收入贡献 | int8/PQ 或盘型索引（DiskANN 类） |
| 过滤选择性长期 < 1% 而无分区键 | 候选取空率 > 5% 持续一周 | 重建集合，按过滤维度分区（一次性大工程） |
| 向量表与业务表必须同事务对账 | 差异率 > 0.1% 且补不齐 | 回到路线 A（pgvector），或建 outbox + 对账链路 |
| 单机 pgvector 的索引 > 机器内存一半 | 索引 33 GB / 机器 64 GB | 换独立服务；或缩到热数据 |
| 需要 PITR / 需要多写事务 | 合规或财务要求 | 向量库只能是派生视图，权威源另建（这不是选型问题，是形态问题） |

## 27.11 踩坑清单（现象 → 根因 → 定位 → 修复 → 防复发）

| 现象 | 根因（指到物理形态） | 怎么定位 | 怎么修 | 怎么防复发 |
| --- | --- | --- | --- | --- |
| 结果里全是已下架 / 无权限的商品 | 只做了向量召回，**标量条件在应用层过滤**；候选池内的合规比例可能远低于全库比例（簇效应，事故一） | 取 top-k 的 id，按过滤条件回查真实合规率 | 把过滤下推（`expr` / `filter` / `WHERE` 进索引），并为该字段建标量/payload 索引 | 上线检查单加一条：**任何业务过滤不许出现在检索返回之后** |
| 过滤一严就返回空，且 P99 反而变好 | post-filter：`k' = k/s`，s=1% 时候选 1 万条才剩 100 | 算 `k × s` 是否 ≪ k；看「候选内命中率」 | 提高 `limit`/`ef`（临时）；根治靠分区或产品侧接受少结果 | 把「候选取空率」做成指标（27.12），阈值 5% 告警 |
| 写入成功但立刻查不到 | 段还在增长段/未封存，或索引仍是异步构建中；一致性等级是 Eventually/Bounded | 换 `consistency_level=Strong` 重试一次是否立刻可见 | 关键读用 Strong；或读自己的写回源权威源（点查 1 次） | 把「可见性延迟」写进接口契约，别让业务假设「写完即查得到」 |
| 升级后所有集合加载失败，被迫停机重建 9 小时 | 索引/段文件格式与二进制版本绑定，**旧索引不可读**（事故二） | 升级前查 release notes 的「索引格式变更」；在预发环境用真实段文件试加载 | 停写 → 重建 → 校验 → 切流；期间**保留旧索引**做回滚点 | 升级变更单必须写：①是否格式兼容 ②重建机时 ③盘能否放下两份 ④回滚方案 |
| 切主后丢了最后 40 分钟的新增数据，且补不回来 | 副本异步复制 + **业务字段只存在向量库里**（事故三） | 比对副本的段水位/日志位点；确认上游能否重算 | 从上游重放 + 重算 embedding；把业务字段迁回业务库 | 铁律：向量库只存「id + 向量 + 可重建的冗余字段」；上游必须能独立重建全量 |
| 没人知道重建要多久，真出事时只能干等 | 从来没演练过；「重建时长」只是印象 | 在预发用 1/10 数据量测一次，按 N 线性外推 | 立刻补一次演练，把结果写进预案 | 每季度一次「分片级重建演练」，把机时写进 runbook（不是估算，是实测） |
| pgvector 表越用越慢、索引体积只涨不跌 | UPDATE 产生新 TID，HNSW 留死条目；图不能就地整理（§27.4 推论③） | `pg_relation_size(索引)`、`pgstattuple`（需建扩展，HNSW 的输出细节以扩展文档为准）；`ef_search` 下的召回抽查 | `REINDEX CONCURRENTLY`（= 重建，要机时和内存） | 别把 HNSW 建在高频更新列上；月变更 > 20% 就换设计（拆冷热表） |
| 混合查询在测试环境很快、生产很慢（或反之） | PG 优化器在「HNSW + 过滤」与「位图 + 排序」之间按成本选路，数据分布一变就翻转 | `EXPLAIN (ANALYZE, BUFFERS)` 看 `Rows Removed by Filter` | 固定访问路径（必要时用 CTE/`MATERIALIZED` 强制先过滤），或调 `ef`/`enable_*` | 混合检索 SQL 上线必须附执行计划；计划变更进代码评审 |
| 同样参数下不同版本召回不一样 | 构建/查询默认值、量化默认开关、距离计算实现都随版本变过 | 固定 golden set 跑 recall@k 对比；记录版本号 | 把索引重建一遍到目标版本，再重测 | 「版本 + 参数 + recall」三件套一起进变更记录（纪律 7） |

## 27.12 观测：指标、拐点与告警

**纪律 7 先立**：三条产品（Milvus / Qdrant / pgvector）的指标**名字完全不同**，且还在跨版本改名。下表给的是「该看什么」，**取数入口与指标名以目标版本的 metrics 输出为准**——先 `curl /metrics | grep` 确认名字存在，再写进面板。**不确定的指标名不许凭记忆写**，写错的代价是整个面板被当成装饰。

| 该看什么 | Milvus 入口（版本敏感） | Qdrant 入口（版本敏感） | pgvector 入口 | 拐点（越线就动手） |
| --- | --- | --- | --- | --- |
| 段状态：增长段 / 封存段 / 已索引段 的比例 | 段信息查询接口与 QueryNode 侧指标（名字随版本变，以目标版本 metrics 为准） | collection 信息 + 段侧指标 | — | 增长段长期不封存（写入 > 封存速率）；碎段数持续上涨 |
| 索引构建任务进度与失败数 | SDK 的索引进度查询 + IndexNode 指标（函数名与指标名以目标版本文档为准） | collection 状态 + 优化器/索引构建指标 | `pg_stat_progress_create_index` | 有段长期「未建索引」；失败任务 > 0 且不自动重试 |
| 生效的检索宽度 `ef` / `nprobe` / `probes` | 查询参数里的 `ef`；服务端是否有覆盖以目标版本文档为准 | `hnsw_ef` / `hnsw_ef` 相关搜索参数 | 会话内 `SHOW hnsw.ef_search;`、`SHOW ivfflat.probes;`（**必须同会话读**，它是会话级 GUC） | 线上实际生效值与代码里的常量不一致（最常见的「调了没用」） |

| **候选取空率**（post-filter 陷阱的直接信号） | 应用侧埋点：请求放大后仍不足 k 的比例 | 同上 | `Rows Removed by Filter` 的比例 | > 5% 持续 10 min；或「返回 0 条」比例 > 1% |
| 过滤命中率（候选池内合规比例） | 应用侧埋点（拿返回 id 回查过滤条件） | 同上 | 同上 | 与全库比例偏离 > 5×（= 簇效应，事故一的前兆） |
| pgvector 索引膨胀 | — | — | `pg_relation_size('索引')`、`pgstattuple`（需 `CREATE EXTENSION pgstattuple`；HNSW 的具体输出以扩展版本文档为准） | 索引体积 / 行数 的比值环比涨 > 30% |
| 副本延迟 / 段水位差 | QueryNode 与 DataNode 的时间戳差（指标名以目标版本为准） | 副本侧指标 + 写入确认因子 | PG 侧原生 `pg_stat_replication`（若走主备） | 落后 > 1 min 且写入在涨 → 切主会丢这么多 |
| 内存 / 水位 | QueryNode 内存、段加载占用 | 容器内存 vs `on_disk` 比例 | `maintenance_work_mem` 与构建期峰值 | 内存 > 80% 水位；构建期峰值 > 可用内存 60% |

### 告警表达式骨架（示意，指标名先 grep 再落地）

```text
# ① 候选取空：post-filter 陷阱的"体温计"（应用侧埋点，与产品无关）
sum(rate(vector_search_candidate_short_total[5m]))
  / sum(rate(vector_search_total[5m])) > 0.05

# ② 过滤命中率与全库比例偏离过大 → 簇效应，top-k 已被"死货簇"占满
vector_filter_hit_ratio_in_candidates / vector_filter_hit_ratio_global > 5

# ③ 有段长期无索引 → 查询一直在暴力扫（功能正常，性能塌了）
max by (collection) (vector_segments_without_index) > 0

# ④ 索引构建任务失败/积压（指标名以目标版本 metrics 为准）
increase(vector_index_build_failed_total[15m]) > 0
   or max by (collection) (vector_index_build_queue_depth) > 10

# ⑤ pgvector 索引膨胀：体积/行数 比值持续上涨（需 pgstattuple 或 pg_relation_size）
pg_relation_size{index="product_vec_emb_hnsw"}
  / pg_stat_user_tables_n_live_tup{table="product_vec"} > <基线 × 1.3>

# ⑥ 副本延迟 → 决定"切主会丢多少"
max by (collection) (vector_replica_lag_seconds) > 60
```

**为什么第一条最值钱**：它是唯一一条能在「P99 下降、错误率为零、面板全绿」的情况下报警的指标。事故一里，`candidate_short` 从 4% 涨到 96%，而延迟指标一路变好——**如果没有这一条，你要等 4 天和 1,912 张客诉**。

## 27.13 一页速记

| 记什么 | 具体数字 / 结论 |
| --- | --- |
| 两条路线一句话 | **库/宿主内建索引**（faiss、pgvector）把持久化、事务、备份全交给宿主；**独立服务**（Milvus、Qdrant）自己管分片、副本、段、构建任务——接管了就收钱，且**副本常常是异步的** |
| 唯一真问题 | 带标量过滤的 ANN：过滤选择性 → 决定策略（post / pre / 图内 / 分区），而策略决定索引布局，**上线后改不动** |
| pgvector 的最大优势 | 向量与业务数据**同一事务、同一 WAL**：不需要两份存储一致性、不需要 CDC 对账、`DELETE` 一次就干净 |
| pgvector 的最大代价 | 向量存两份（堆 TOAST + 索引）+ 图不能靠 VACUUM 整理 ⇒ 高频更新列 = 膨胀 + `REINDEX`（= 重建） |
| pgvector 实用上限 | 千万行量级；1 亿行 = 307 GB 向量 + 330 GB 索引，已越过单机内存红毯；100 亿行不是调参问题 |
| post-filter 边界 | `k' = k/s`；s ≥ 10% 可用，s = 1% → k' 放大 100× → 延迟 ×78、吞吐 ÷78 |
| pre-filter 边界 | 合格子集 ≤ 10⁵ 可暴力（`n×d×4/带宽`）；≥ 10⁶ 等于没索引 |
| 图内过滤的两副面孔 | 剪枝式 → s 小时**图断裂**；穿越式 → 成本 ≈ 1/s × 基线（等于放大候选预算）。正解是**分区**（→ comp/26） |
| Milvus 三层 | collection（表/schema/一致性）→ partition（可限定查询范围）→ segment（执行单位：增长段可写 / 封存段可建索引） |
| `create_index` 的真相 | **异步作业**：返回 ≠ 建好；期间查询走暴力扫（慢但不报错）；失败也常常不报错 |
| 一致性等级的真相 | Strong 才能读己之写；`flush()` ≠ 可见；可见性延迟 = 写 → WAL → 段 → 封存 → 建索引 → load 这条链 |
| 存储乘法链（1 亿 × 768） | 307 GB 向量 + 13 GB 图 + 20 GB 标量 ≈ 346 GB → 冗余 398 GB → **2 副本 797 GB 盘 / 640 GB 内存** |
| 重建 = 重算所有距离 | `N × 每点次数(≈2×efC) × 单次代价 ÷ (并行度 × 效率)`；1 亿 × 768 ≈ **1.3 h 建图 / 2–3 h 全流程**；2.4 亿 × 1024 ≈ 8.3 h（事故二） |
| 备份的两档 | 含索引的段快照 → 加载即用（分钟–小时）；只导出向量 → **必须重建图**（机时）。JSON 导出是后者，且膨胀 2.6–2.9× |
| 升级真正的时间 | 不是重启时间（18 min），是**建图机时**（8–10 h）；两者差一个数量级 |
| 观测第一指标 | **候选取空率**（`candidate_short_ratio`）：唯一能在「变快 + 无错」时报警的数字；阈值 5% |
| 系统级失效只有三件 | 协调层/元数据挂 → 不可查；异步副本 + 双写漂移 → 不一致且补不回来；副本数 × 内存单价 → 成本失控 |

**如果只记五句：**

1. **向量库不是数据库，是派生索引。** 权威源、业务字段、可重算的原文都必须在你手里；把业务字段只存进向量库的人，会在某次切主后发现「补不回来」（事故三）。
2. **难点是带过滤的 ANN，不是余弦相似度。** 过滤选择性决定一切：s ≥ 10% 用 post-filter，1%–10% 靠图内过滤/payload 索引，< 1% 必须分区——这条链必须在设计期定，因为改它等于重建索引。
3. **post-filter 不报错，它只是让用户搜不到。** 候选池内的合规率可能比全库低一个数量级（簇效应），所以唯一可靠的报警指标是「候选取空率」，不是延迟。
4. **索引是派生数据，二进制一变就要重建。** 升级窗口要按 `N × 距离计算量` 的机时算，不是按重启时间算；能不能同时放下两份索引，决定了你**有没有回滚点**。
5. **pgvector 用一致性换规模，独立服务用规模换一致性。** 前者把向量放进事务里（千万级最香），后者把向量放进自己的集群里（亿级必须），中间没有免费方案。

## 27.14 自检题（5 题，答案折叠）

**1. 过滤选择性 1%，`limit=10`，你用 post-filter。请算出用户实际看到几条；如果产品经理不接受空结果，三条修法各要付什么代价？**

<details><summary>答案</summary>

先算：`k' = k/s = 10 / 0.01 = 1,000`；但你的 `limit=10`，所以期望合格结果 = `10 × 1% = 0.1` 条——**10 次查询里有 9 次返回空**。

三条修法的账单：

| 修法 | 具体动作 | 代价 |
| --- | --- | --- |
| 放大候选 | `limit` / `ef` 提到 ≥ 1,000 | 延迟 ×8 量级（128 → 1,024），且 `top-1000` 的召回本身低于 `top-10`（图的有效宽度被稀释）；QPS ÷8 |
| pre-filter 暴力 | 先用标量索引取合格 id 集 | 子集 100 万时 = `100万 × 768 × 4 B = 3 GB` 读，150 ms 量级；子集再大就退化成全扫 |
| 图内过滤 | 遍历时判过滤 | 剪枝式：每点 32 个邻居里合格 0.32 个 → 有效度数 <1 → **图断裂、召回塌**；穿越式：要访问 ~100 个点才捞到 1 个合格的，成本 ≈ post-filter 那一半 |
| **正解：分区** | 分区键 = 这个过滤字段（如 `tenant_id` / `category_id`） | 一次性重建成本（27.9 账四）+ 分区数上千后小分区图质量差 |

关键结论：**三条「不改索引结构」的修法都是在同一个坑里换姿势**；真正的修法是把过滤变成索引结构的一部分，而它只能在设计期做。产品侧如果坚持「永不返回不合规结果」，就同时接受「少返回」——并且必须把 `candidate_short` 打点，否则没人知道少了多少。

</details>

**2. 1 亿条 × 768 维、float32、2 副本、要求全内存常驻。给出盘与内存的乘法链；叠 int8 量化能省多少，代价是什么？**

<details><summary>答案</summary>

```
向量本体 = 1e8 × 768 × 4 = 307.2 GB
HNSW 图  = 1e8 × (2×16×4) = 12.8 GB
ID/标记  = 1e8 × 64 B     =  6.4 GB
标量+索引 = 1e8 × 200 B    = 20.0 GB
单副本 = 346.4 GB → 冗余 ×1.15 = 398 GB → ×2 副本 = 797 GB 盘
内存 = (307.2 + 12.8) × 2 = 640 GB        ← 真正的预算项
```

叠 int8：向量 76.8 GB（÷4）⇒ 单副本 ≈ 116 GB → ×2 副本 ≈ 266 GB 盘；内存 ≈ (76.8 + 12.8) × 2 ≈ 179 GB。**省 3.3×**，recall 通常掉 1–2 个百分点（必须在自己的 golden set 上实测，不许引用别处的数字）。

代价还有三条：① 量化是**索引属性**，开启即重建一次（机时按账四算）；② 距离用整数近似算，边界候选需要 rerank（多一层，+3–5 ms）；③ int8 对**分布偏移**敏感——换 embedding 模型后要重新标定量化参数。**量级结论，±20%**。

</details>

**3. 为什么 pgvector 的 HNSW 在高频更新的列上会持续膨胀，而且 VACUUM 修不好？它和 B-tree 的差别在哪？**

<details><summary>答案</summary>

差别在**「键是值」还是「边是引用」**：

- B-tree 的每个条目是「键值 → TID」，条目之间**互不引用**。删掉一条，其他条目的可达性完全不受影响。所以 VACUUM 可以安全地摘掉死条目、把页回收、让后续插入复用空间（→ [11 PostgreSQL 对照](11-postgresql-heap-and-vacuum.md) §11.6）。
- HNSW 的每个点是「一组指向邻居的边」。**物理删掉一个点，会让它的邻居失去通路**，图不连通 ⇒ 召回变成不可复现的随机下降（→ comp/26）。所以只能把点标成墓碑、检索时跳过——**但空间不释放、候选预算被死点吃掉**，表现就是「内存不降、recall 缓降」。

而 PG 的 `UPDATE` = 写新行版本 + 新 TID：索引里旧 TID 的条目成了死条目，VACUUM 能把这些**条目**摘掉，但它**不会重连图**（重连需要把所有点重新插入一遍）。于是：

- 高频更新列上，每次更新都在图上多一个墓碑、在索引里多一个死条目；
- `hnsw.ef_search` 的有效宽度随时间被侵蚀，召回缓慢下滑，指标上看起来像「模型变差了」；
- **唯一整理手段是 `REINDEX`（= 全量重建，付机时 + 内存峰值）**。

防复发：**不要把 HNSW 建在频繁变更的列上**。做法是把「稳定的向量」和「频繁变更的标量属性」分开——向量列只在 embedding 重算时变，状态/价格这类字段放在同一个堆表的其他列（走 B-tree 与 HOT），别让它们触发索引重建。

</details>

**4. 升级计划：2 亿条 × 1024 维，8 节点 × 32 核，低峰窗口 4 小时。算建图机时，判断窗口够不够，给两个方案。**

<details><summary>答案</summary>

```
2e8 × 400 次/点 × 4 µs = 3.2e5 单核秒
实际并行度不是核数，是"能腾出多少内存装构建工作集"：
  重建期必须同时保留在线查询段 + 新构建工作集，
  整集群一次只能腾出约 1 台机器的配额 ⇒ 32 线程、效率 0.4 ⇒ 12.8
3.2e5 ÷ 12.8 ≈ 2.5e4 s ≈ 7 h   ⇒  4 h 窗口不够（再加校验与灰度 ≈ 8 h）
```

**方案 A：分片滚动重建。** 单元是分片不是集群：16 分片 → 每片 7 h ÷ 16 ≈ 26 min（含校验与灰度 30–40 min）。任何时刻只有一片在重建，其余继续服务；出问题只回滚一片。**前提：必须能同时放下「该分片的旧索引 + 新索引」**（这正是 `→ architect/18 §18.8` 强调的「可回滚性来自容量」）。

**方案 B：临时加节点 + 双索引并行。** 加 2 台临时高内存节点，把 `efConstruction` 从 200 降到 100（机时大致减半，recall 掉 1–2 点），窗口压到 2–3 h。代价是钱与一次 recall 回归测试。

**两个方案都要求同一件事**：变更单上先写清「① 格式是否兼容 ② 建图机时 ③ 盘/内存放不放得下两份 ④ 回滚点在哪」。事故二的 9 小时 40 分，全部损失都来自第 ③④ 项没答。

</details>

**5. 「插入成功了但查不到」。请给出 10 分钟内定位到具体哪一层的顺序。**

<details><summary>答案</summary>

先把问题劈成三类：**数据没到 / 索引没有 / 一致性不保证**。按顺序各打一枪，每枪都是秒级：

1. **按主键精确查一次**（`expr id == x` / `WHERE id = x`，不带向量排序）。
   - 精确查也查不到 ⇒ **数据没到**：写失败、还在 WAL 未被 DataNode 消费、或进了增长段但客户端连的是另一个分片/集合。查 WAL 消费延迟与 DataNode 状态。
   - 精确查得到 ⇒ 进第 2 步。
2. **用 `Strong` 一致性等级重跑同一条向量查询。**
   - 变成能查到 ⇒ **等级问题**：你原来用的是 `Bounded`/`Eventually`，或跨客户端用了 `Session`（Session 只保证同一客户端读己之写）。这属于契约问题，不是 bug，改接口参数或改契约。
   - 仍然查不到 ⇒ 进第 3 步。
3. **看三个指标：增长段数 / 无索引段数 / 索引构建任务进度。**
   - 无索引段 > 0 或任务在跑 ⇒ **索引没有**：查询走的是暴力路径或旧索引，而该段还没进图。等任务完成，别在高峰期做批量灌入。
   - 段已封存、索引已完成、仍然查不到 ⇒ 检查**段是否被 `load` 到 QueryNode**（`release` 之后不可查）、以及该 id 是否落在未加载的分区。

把这条顺序写进 runbook 的价值：**它把「玄学查不到」变成一个 3 步排除法**，而且第 1 步就能区分「写丢了」和「索引慢」——这两件事的修复动作完全相反（一个要补数据，一个要等任务）。

</details>
