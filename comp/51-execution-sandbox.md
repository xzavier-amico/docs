## 51.1 引子：三起「沙箱起来了、跑完了、返回 200」的事故

执行面的事故有个共同形状：**任务成功率是绿的（99%+），沙箱启动日志干净，没有任何异常栈**，但三件坏事同时成立——① 隔离比团队以为的**弱**；② 启动比 SLO 以为的**慢**；③ 复用把上一个任务的**状态**带给了下一个租户。这三件事全都不在「任务成功率」的视野里：成功率只统计「有没有抛异常」，不统计「边界是不是真挡得住」「有没有在 SLO 内跑完」「跑之前那块地干不干净」。

### 事故一：容器不是安全边界，`docker.sock` 把「读文件」升级成「拿云凭据」（2025-10-14）

某 Agent 产品的「代码解释器」工具。部署形态是 K8s + 默认 `runc` 容器，`securityContext` 全默认：**以 root 跑、rootfs 可写、`automountServiceAccountToken` 未关**。为了让「用户 `pip install` 的包能落盘、能起子进程」，发布时加了两个开关：挂载 `/var/run/docker.sock`（「让他能起子容器做隔离」）与 `--privileged`（「否则某些包编译不过」）。

触发路径完全不需要 0day：一个用户让 Agent「看一下我的运行环境」，Agent 执行 `ls /` 把输出贴回对话；用户看到 `/host`、`/var/run/docker.sock` 这些名字，接着说「帮我看下 `/proc/1/environ`」，再接着说「`docker run -v /:/host --privileged` 起个容器把 `/host` 打个包」。

| 时刻 | 事件 | 证据 | 影响 |
| --- | --- | --- | --- |
| 10-14 09:12 | 用户第一次让 Agent 执行 `ls /`、`cat /proc/1/environ` | 会话记录里有完整命令回显 | 宿主路径、镜像 tag、节点名全部可见 |
| 10-14 09:20 | 通过 `docker.sock` 起特权容器，挂载宿主 `/` | 节点上多出一个不受管容器 | 读到另外 **3 个租户**的挂载卷 |
| 10-14 09:24–09:31 | 卷里有 `~/.aws/credentials` 与 `.env`；又从 `169.254.169.254` 拿到节点角色（egress 无限制） | CloudTrail + 卷内容 | 越权面从「文件」扩到「云 API」 |
| 10-14 15:54 | 风控发现异常 S3 `ListBucket` 调用，切流 | CloudTrail | **暴露 6 小时 42 分** |
| 10-14 18:00 | 应急轮转 41 个凭据、重跑 2 天审计、对外通报 1 次 | — | 直接成本约 $23k（人力 + 审计 + 赔付） |

根因链两段，只修一段都无效：**① 边界选错**——共享宿主内核 + root + 全量能力 + 可写 rootfs，它**根本不是安全边界，只是「进程分组 + 资源记账」**；**② 纵深缺失**——egress 白名单、metadata 封禁、卷挂载最小化三道「第二条命」一道都没有，于是「读一个文件」升级成「拿云凭据」。

### 事故二：隔离升级成 microVM 之后，P99 从 320 ms 变成 3.1 s（2025-12-02）

为了修事故一，架构组把执行面换成 Firecracker microVM（K8s `runtimeClass: kata-fc`）。隔离强度确实上去了：独立 guest 内核、极简设备模型、无 `docker.sock`。但**没有做预热池**——每个任务都走「建 microVM → 引导 guest 内核 → 起 guest agent → 挂工作区 → 冷启 Python → `import numpy`」。

| 段 | 容器（改前） | microVM 冷启（改后） | 说明 |
| --- | --- | --- | --- |
| 调度与放置 + rootfs 就绪 | 90–350 ms | 140–550 ms | 多一层 `runtimeClass` 决策与块设备挂载 |
| 引导（内核 + init） | 0（共享宿主内核） | **125–400 ms** | Firecracker 官方量级 ~125 ms 起，加 guest 用户态 |
| guest agent + vsock 挂载 | 0 | 120–350 ms | 工作区、只读 rootfs、时钟同步 |
| Python + 依赖 import | 150–500 ms（热页） | **380–1,200 ms**（冷页） | 冷页缓存是主要放大器 |
| 应用 SDK 初始化 | 40–120 ms | 70–200 ms | — |
| **合计** | **0.2–0.5 s**（P50 180 ms / P99 320 ms） | **0.8–2.6 s**（P50 1.4 s / P99 3.1 s，含排队） | 任务本身平均只跑 190 ms |

注意最后一行：**任务本身 190 ms，冷启动 1.4 s**——沙箱比它要干的活贵 7 倍。发布后两周：任务超时率 0.4% → 11%，客户端重试把执行请求量放大 3 倍（沙箱更贵、重试更多、更贵），SLO 违约赔付 $6,800。

修复不是「换回容器」，而是把启动从关键路径上摘掉：**预热池 + 快照恢复（snapshot restore 30–150 ms）+ 依赖预热**（`python -c "import numpy, pandas"` 打进镜像的 preload 钩子，把 `import` 从 900 ms 压到 120 ms）。修复后 P99 = 520 ms，且隔离强度一点没降。

### 事故三：浏览器池「24 个实例，实际只有 2 个能用」，任务全失败（2026-01-20）

网页操作类 Agent。24 个 headless Chromium 共享**同一个** `user-data-dir` 池，健康检查只看 CDP 端口 9222 通不通。跑了 3 天：

| 时刻 | 池可用 | 单实例 RSS | 任务成功率 | 队列 |
| --- | --- | --- | --- | --- |
| 01-17 12:00 | 24 | 420 MiB | 98.7% | 0 |
| 01-19 08:00 | 24 | 900 MiB | 97.9% | 0 |
| 01-20 03:10 | 24 | 1.5 GiB | 96% | 12 |
| 01-20 04:02 | 24 → 6 | 1.9 GiB（节点 32 GiB OOMKilled） | 71% | 380 |
| 01-20 04:05 | 6 → 2 | 重建脚本全失败：`SingletonLock` / `SingletonSocket` 残留 + profile 目录被占 | **12%** | 4,100 |
| 01-20 06:45 | 2 → 24（手动清目录 + 改每任务新 context） | 400 MiB | 98% | 0 |

RSS 从 420 MiB 涨到 1.9 GiB 不是「内存泄漏 bug」，而是**浏览器本来就这样**：renderer 进程、未解绑的 CDP 域监听、service worker、图片解码缓存、JS 堆里没回收的 detached DOM。**复用同一个 browser，就是复用一份只会涨的状态。**

后果：**2 小时 40 分不可用**，8,900 个任务失败，重跑 3 次（重复的下单动作被去重表拦住 1 次，没拦住 1 次），客诉 210 单。

> 🩸 三起事故对应本篇三个维度：**隔离强度（§51.3）、启动延迟（§51.4）、复用成本（§51.5）**，而浏览器池是三者同时最坏的那一格（§51.6）。

## 51.2 一句话定位与唯一真问题

**执行面 = 一个「把不可信代码塞进一个有边界的盒子里、跑完再把盒子扔掉」的工厂。** 它**不是**容器编排（K8s 负责放哪台机器，不负责盒子的形状），**不是**沙箱 SDK（SDK 只是盒子的一层壳），也**不是**一个可以「一次选型、永久定型」的组件——它的形状由「你能容忍多大的逃逸半径」和「你能接受多慢的冷启动」这两个数**联合**决定，而这两个数随业务（代码执行 / 网页操作 / 数据处理）变化。

三个「不是」一句话说完：它**不是容器编排**（编排决定放哪台机器，不决定共享不共享内核）；**不是 SDK**（SDK 只保证「我按某种方式起了个进程」，隔离强度由内核决定）；**不是无状态服务**（有冷启动、会崩、要池化，更像「短生命周期的数据库连接」而不是 HTTP 服务）。

### 唯一真问题

> **Agent 的执行天然不可信：隔离强度、启动延迟、复用成本构成一个不可能三角；而浏览器是最难池化的执行面——它有状态、吃内存、会崩。**

这个论断的三个角，每一个都能用一行算术钉死：

1. **隔离强度是「共享多少内核」的函数**。`runc` 容器共享宿主内核 → 逃逸只需一个内核漏洞或一处配置错误；microVM 用硬件虚拟化把内核也隔开 → 逃逸需要打穿 VMM 或 CPU 虚拟化；WASM 干脆没有内核接口 → 逃逸需要打穿运行时 JIT。**强度每上一档，兼容性掉一截**（§51.3）。
2. **启动延迟是「你要初始化多少层」的加法**。容器 = 命名空间 + 运行时；microVM = 上面再加一个 guest 内核；浏览器 = 上面再加一个多进程浏览器 + 一个 profile。**每一层都在冷启动账单上收一次费**，而任务的执行时间往往只有几百毫秒（§51.4）。
3. **复用省的是启动，付的是隔离**。一个沙箱服务 k 个任务，启动成本除以 k，但「上一个任务留下的文件、环境变量、内存里的凭据、被改过的依赖」也除以 1——**它全留给下一个任务**（§51.5）。浏览器把这条推到极端：它的状态既在磁盘（profile）也在内存（renderer 堆），而且**只会涨不会还**（§51.6）。

从这一个矛盾推出的全部设计：

| 从矛盾推出的约束 | 推出的设计 / 纪律 |
| --- | --- |
| 隔离强度只能按「最坏输入」选，且每档都有兼容性代价 | 分级：可信代码跑容器、用户代码跑 microVM、用户**二进制**只能跑 microVM + 无网络；兼容性必须**实测**（跑一遍真实依赖 + 一次真实任务）再定档 |
| 冷启动不能进关键路径 | **预热池**（pre-boot/pre-import）+ **快照恢复**；池大小由「新建速率 × 启动延迟」定，不由「并发数」定（§51.8 账二） |
| 冷启动比例决定 P99，不决定 P50 | 监控必须同时看「热启动分位」与「冷启动比例」；**1% 是硬分界**（§51.8 账三） |
| 复用必然引入状态 | 复用要有「代」（generation）+ 上限（次数/时长/内存）+ 每任务重置（工作区、env、凭据轮转） |
| 浏览器的内存只会涨 | 每任务一个 `BrowserContext`（不是新 Browser）、每 N 任务回收、`memory.max` 兜底、崩溃即重建 |
| 资源必须有硬上限，且要区分「杀」与「慢」 | `memory.max` 触发 OOM kill（任务失败）、`cpu.max` 触发节流（任务变慢）、`pids.max` 触发 fork 失败（诡异报错）（§51.7） |
| 网络是逃逸的第二条路；池化的前提是「可丢弃」 | egress 默认拒绝 + 白名单 + 封 metadata + 受控 DNS；沙箱除显式工具调用外必须无外部副作用，否则复用 = 重放事故 |

### 四个候选执行面（本篇的组织骨架）

| 候选 | 隔离机制 | 逃逸半径 | 冷启动量级 | 兼容性 | 典型用途 |
| --- | --- | --- | --- | --- | --- |
| **容器**（namespace + cgroup） | 共享内核，靠 7 类 namespace + cgroup v2 + seccomp + capability 收敛 | 内核漏洞 / 配置错误 / 挂载泄露 → **整台节点** | 0.3–2 s（受运行时与语言影响） | ~99% | 自家代码、可信工具、CI 类任务 |
| **gVisor**（`runsc`） | 用户态内核（Sentry）重实现系统调用，宿主只暴露极小接口 | Sentry 漏洞 / 平台层（ptrace、KVM）漏洞 | 0.4–2 s，且**每次 syscall 有税** | 90–97% | 多租户代码执行，要容器生态但不想共享内核 |
| **microVM**（Firecracker / Kata） | KVM 硬件虚拟化 + 极简设备模型（virtio-net/block/vsock） | VMM 或虚拟化漏洞 → 需两跳 | 冷 0.8–3 s；**快照恢复 30–150 ms** | 95–99% | 用户代码、不可信二进制、强合规多租户 |
| **WASM**（WASI 运行时） | 线性内存 + 能力导入（没有系统调用，只有宿主显式给的函数） | 运行时 JIT / 宿主函数漏洞 | **0.1–5 ms**（实例化） | 30–70% | 纯函数式计算、插件、规则引擎、确定性重放 |

### 浏览器的特殊性：它不是「第五个候选」，是「四个候选之上的一个有状态应用」

| 维度 | 普通代码沙箱 | 无头浏览器 | 后果 |
| --- | --- | --- | --- |
| 状态 | 工作区可丢弃 | profile / cookie / localStorage / IndexedDB / service worker / HTTP 缓存 | 复用 = 串租户；不复用 = 冷启动更贵 |
| 内存 | 单进程，几十到几百 MiB | 多进程（browser + renderer×N + GPU + network + storage），**每渲染进程 80–800 MiB** | 单节点只能放几十个（§51.6） |
| 崩溃 | 进程退出 = 任务失败 | renderer 崩 / browser 崩 / 僵尸进程 / 锁残留 | 池会「看起来有、实际不能用」 |
| 接口 | stdin/stdout 或 HTTP | CDP over WebSocket（长连接、有状态、断线要重连+重建上下文） | 健康检查不能只看端口 |
| 依赖 | 语言运行时 | 字体、emoji、编解码器、`/dev/shm`、`--no-sandbox` 与 seccomp 的冲突 | 容器里跑 Chromium 有一堆「不这么配就崩」的开关 |
| 可预测性 | 延迟 ≈ 代码复杂度 | 延迟 ≈ 页面复杂度 × 网络 × 反爬 | 单任务 P99 可到几十秒 |

### 解剖卡八问对照（本篇哪里答哪一问）

| 八问 | 落在哪节 | 一句话答案 |
| --- | --- | --- |
| ① 承诺什么 | §51.2、§51.9 | 承诺「在给定边界内执行不可信代码并回收」；**不承诺**「绝对不可逃逸」「零冷启动」「复用无污染」 |
| ② 数据长什么样 | §51.3、§51.6 | 沙箱 = 命名空间集合 + cgroup 树 + 只读 rootfs + 可写 tmpfs 工作区；浏览器 = 多进程树 + profile 目录 |
| ③ 一次执行走哪条路 | §51.4 | 排队 → 取池（命中则跳过初始化）→ 建/恢复沙箱 → 挂工作区 → 起运行时 → 执行 → 采集 → 销毁/回收 |
| ④ 并发与一致 | §51.5、§51.7 | 并发由「池容量 + 每沙箱并发度」决定；一致性靠「每任务重置」而不是靠锁；cgroup 是唯一硬边界 |
| ⑤ 扩展维度 | §51.8 | 垂直（每沙箱内存）→ 分片（节点数）→ 池化（复用）→ 批处理摊薄；**不可无限横向扩，因为每沙箱都吃固定内存** |
| ⑥ 会在哪崩 | §51.1、§51.10 | 满（节点 OOM、池空、pids 打满）、慢（冷启动进关键路径、CPU 节流）、假活（端口通但上下文已死） |
| ⑦ 看哪几个指标 | §51.11 | 启动延迟分位 + 冷启动比例、池命中率、OOM kill 数、CPU 节流比、浏览器崩溃率、egress 拒绝数 |
| ⑧ 换掉它的信号 | §51.9 | 出现一次「容器内的代码读到了不该读的东西」→ 立刻换 microVM；出现「任务只要 200 ms 而冷启动 2 s」→ 换池化形态 |

## 51.3 隔离强度谱系：namespace、gVisor、microVM、WASM 各挡得住什么

```text
图 1 · 隔离强度谱系：从「共享宿主内核」到「没有内核接口」

   攻击面：整个宿主内核 ◄────────────────────────────────────────► 只剩「宿主主动导入的函数」
  ┌──────────────┬──────────────┬───────────────┬──────────────┬────────────────┐

  │              │ ns+cg+seccomp│ 用户态内核      │ KVM+极简设备  │ 线性内存+能力    │
  ├──────────────┼──────────────┼───────────────┼──────────────┼────────────────┤
  │ 逃逸 = 一行   │ 逃逸 = 内核   │ 逃逸 = Sentry  │ 逃逸 = VMM /  │ 逃逸 = 运行时    │
  │ 代码          │ 漏洞或配错    │ 或宿主接口漏洞  │ 虚拟化漏洞    │ JIT 实现漏洞     │
  ├──────────────┼──────────────┼───────────────┼──────────────┼────────────────┤
  │ 冷启动 ~0     │ 0.3–2 s      │ 0.4–2 s       │ 冷 0.8–3 s    │ 0.1–5 ms        │

  ├──────────────┼──────────────┼───────────────┼──────────────┼────────────────┤
  │ 兼容性 100%   │ ~99%         │ 90–97%        │ 95–99%       │ 30–70%          │
  │              │              │ （长尾 syscall）│（需 virtio）  │（无 fork/线程）  │
  ├──────────────┼──────────────┼───────────────┼──────────────┼────────────────┤
  │ 多租户可用？  │ ❌ 不能      │ ✅ 可以        │ ✅ 推荐       │ ✅ 但只能跑编译  │
  │              │ 当安全边界    │               │              │ 到 wasm 的代码   │
  └──────────────┴──────────────┴───────────────┴──────────────┴────────────────┘
        越靠左：便宜、兼容、但挡不住          越靠右：挡得住、但兼容性与生态是代价
```

> 图里最容易误读的一格是「容器 0.3–2 s」。容器之所以比 microVM 快，**省掉的只是「引导 guest 内核」那一段（100–400 ms）**；一旦你的任务需要 JVM 或 CPython + 科学栈，两者都要在用户态付 1–2 s（§51.4）。**「容器快」是个相对量，不是绝对量。**

### 3.1 容器的真实边界：namespace 管「看见什么」，cgroup 管「用多少」，两者都不管「能不能打穿」

四类机制的职责必须分清，混淆它们就是事故一的开始：

| 机制 | 它实际做的事 | 它**不**做的事 | 常见误用 |
| --- | --- | --- | --- |
| **namespace**（mnt / pid / net / ipc / uts / user / cgroup / time） | 换一套「全局名字」：自己的 PID 树、网卡、挂载点 | 不限制资源、不拦系统调用；**内核仍是同一个** | 「进了容器就隔离了」——看不见宿主 PID ≠ 打不穿 |
| **cgroup v2** | 记账 + 限流：CPU 配额、内存上限、PID 数上限、IO 带宽 | **不是安全边界**；v1 时代已有由 `release_agent` 造成的逃逸（CVE-2022-0492 一类） | 「设了 `memory.max` 就安全了」——它只保证「被杀」，不保证「打不穿」 |
| **seccomp-bpf** | 按编号过滤系统调用（默认 profile 拒绝数十个高危调用，放行其余绝大多数） | 不识参数语义（只看寄存器与指针值） | 「开了 seccomp 就够」——默认 profile 仍允许 `clone`、`mount`（授予 `CAP_SYS_ADMIN` 时） |
| **capability + `no-new-privs`** | 把 root 拆成 ~40 个位；`CAP_SYS_ADMIN` 实质等于「新 root」 | 不拦文件系统路径、不拦网络目的地 | 「drop 了 `CAP_NET_RAW`」→ 但 `CAP_SYS_ADMIN` 还在，等于没 drop |

容器逃逸的**已知通道清单**（每一条都曾在真实事故里出现过，不是理论）：

1. **内核提权 / 容器逃逸 CVE**：共享内核意味着「宿主内核的一个 bug = 所有租户的 bug」，而你无法给每个租户打不同补丁。
2. **`docker.sock` / 容器运行时 socket**：挂进去等于把「起容器的权力」交给不可信代码（事故一）。
3. **宿主文件与设备的任何一条缝**：`hostPath` 挂 `/`、`/var/lib/kubelet`、`/proc`；`/proc/sys/kernel/core_pattern`、`/proc/sysrq-trigger` 配上特权就是直通车；`/dev/mem`、`/dev/kmsg`、未过滤的 `--device`。
4. **云 metadata 端点**：`169.254.169.254`（及各家变体）能换来**云凭据**，比本地文件值钱得多。
5. **`CAP_SYS_ADMIN` 与 user namespace**：前者在允许 `unshare` 的环境里能自己造挂载与 `procfs`；后者本身就是「低权限用户拿到大量内核接口」的入口，多家平台直接禁用，代价是 rootless 方案要另选。

**一句话结论**：`runc` 容器适合「我信任这段代码，只想给它干净的工作区和资源上限」；**不适合**「我完全不信任这段代码」。把不可信代码放进 `runc` 容器并声称「已隔离」，是执行面最常见的一类系统性错误。

### 3.2 gVisor：把内核搬到用户态，用「兼容性」换「共享内核的攻击面」

`runsc` 的核心思路：**不让不可信进程直接对宿主内核发系统调用**。它跑一个用内存安全语言写的用户态内核（Sentry），由 Sentry 解释应用发来的系统调用，真正需要落到宿主的部分（文件读写）通过一个受限的代理进程（Gofer）完成；网络栈也在用户态（netstack）。

| gVisor 挡住什么 | gVisor 挡不住 / 有代价 |
| --- | --- |
| 绝大多数「内核漏洞提权」类攻击：应用打的是 Sentry，不是宿主内核 | Sentry 自己的漏洞；平台层（`ptrace` / KVM / `systrap`）的漏洞 |
| 宿主 `/proc`、`/sys` 的绝大部分视图（Sentry 自己合成一套） | 合成出来的 `/proc` 与真实的不完全一致，依赖 `/proc` 细节的程序会挂 |
| 直接访问宿主设备、`ioctl` 长尾、部分 `mount` 语义 | 未实现的系统调用（版本相关，长尾里常年有 `io_uring`、部分 `clone` 标志、部分 fd 语义）；**以目标版本 `runsc` 的兼容性文档为准** |
| 网络层面的「想连哪就连哪」（可由 netstack 强制） | 系统调用密集负载的**性能税**：`systrap`/`ptrace` 平台下 syscall 开销明显升高，文件 I/O 密集任务常见慢 2–5×（量级结论，随平台与版本变化）；纯计算任务影响小 |
| 容器生态（OCI 镜像、`runtimeClass` 切换成本低） | GPU 支持有限（NVProxy 一类方案偏实验性），需要 GPU 的任务基本别选它 |

**选它的判据**：既要「Docker 镜像 + K8s 生态」，又**不能接受共享内核**，负载以读写文件、起子进程为主。**不选**：需要 GPU、需要 `io_uring` 一类长尾语义、或对 syscall 延迟极敏感（高频小文件 I/O）。

### 3.3 microVM：用硬件虚拟化把「内核」也变成租户私有的东西

microVM 的取舍是**用「多一层虚拟化」换「多一层硬件边界」**。它的关键不在于「跑在 KVM 上」（普通虚机也是），而在于**设备模型被砍到极小**：只保留 virtio-net、virtio-block、virtio-vsock、串口，没有 BIOS/UEFI、没有 PCI 枚举树、没有 USB/GPU 直通。这一刀同时买到三件东西：**攻击面小**（设备模拟代码少）、**启动快**（引导路径短）、**内存开销小**（每个 microVM 的 VMM 常驻可做到个位数 MiB 量级）。

| 变体 | 特点 | 什么时候用 |
| --- | --- | --- |
| Firecracker | AWS 开源，极简设备模型，官方给出 ~125 ms 引导与数 MiB 级 VMM 开销的量级；支持快照/恢复 | 密度优先的代码执行池 |
| Cloud Hypervisor | Rust 实现，设备支持比 Firecracker 多一些（热插拔、部分 virtio 设备） | 需要更丰富设备但又想快 |
| Kata Containers | 一个**OCI 兼容的壳**，VMM 可选 QEMU / Cloud Hypervisor / Firecracker | 已有 K8s，想用 `runtimeClass` 一行切换 |
| 云厂商托管方案 | 你只看到「沙箱 API」，看不到 VMM | 不想自己运维宿主机池 |

microVM 挡不住的：VMM 与 CPU 虚拟化的漏洞（历史上虚机逃逸案例集中在设备模拟与 CPU 特性上，所以「设备越少越安全」不是口号）、以及**你自己的配置**（把宿主目录共享进 guest、把云凭据放进 guest 环境变量）。

代价在别处：启动路径多一层内核、镜像要转成块设备或 rootfs、`vsock` 取代普通内网导致工具链要改、监控多采一层 guest 指标。

### 3.4 WASM：没有系统调用，就没有「系统调用攻击面」

WASM 的能力模型与前三个都不同：**它不是一个「受限的进程」，而是一个「只有内存和宿主导入函数」的计算单元**。它没有 `open`、没有 `socket`、没有 `fork`——想要任何能力，必须由宿主显式导入（WASI 里的 preopen 目录、时钟、随机数，或者你自己写的宿主函数）。

| WASM 挡住什么 | WASM 挡不住 / 有代价 |
| --- | --- |
| 一切「系统调用 → 内核漏洞」类逃逸：它根本没有系统调用 | 运行时 JIT 的实现漏洞、宿主导入函数实现里的越权（最常见：你把「能读任意路径」的函数导进去了） |
| 内存越界（线性内存有边界检查，且天然不可执行） | 编译兼容性：需要源码能编译到 wasm target；用户给的 `.py`/`.js`/二进制包**没法直接跑** |
| 副作用（默认没有文件、没有网络、没有环境变量） | 无 `fork`/`exec`、线程支持有限（`wasi-threads` 类方案仍在演进）、无 GPU |
| 秒级以下的隔离与回收（实例化 0.1–5 ms 量级） | 解释型语言在 wasm 里慢：把 CPython 编译到 wasm 后跑用户脚本，常见比原生慢一个量级（区间宽，**以目标运行时实测为准**） |

**选它的判据**：输入是**代码**而不是**语言运行时产物**，逻辑是「数据进 → 计算 → 数据出」（规则引擎、表达式求值、确定性重放、插件）。**不选**：用户要跑 `pip install`、要起子进程、要访问网络、要跑编译好的二进制。

### 3.5 「能挡住什么 / 挡不住什么」总表（评审时直接抄进风险登记册）

| 威胁 | 容器（默认） | 容器（加固） | gVisor | microVM | WASM |
| --- | --- | --- | --- | --- | --- |
| 读宿主其他租户的文件 | ❌ 能 | ⚠️ 取决于挂载与 userns | ✅ 挡 | ✅ 挡 | ✅ 挡 |
| 拿到云 metadata 凭据 | ❌ 能（要额外封网络） | ⚠️ 同左 | ✅ + 网络策略 | ✅ + 网络策略 | ✅ 无网络能力 |
| 借宿主内核漏洞提权 | ❌ 能 | ❌ 能（共享内核） | ✅ 基本挡 | ✅ 挡 | ✅ 不适用 |
| 持久化后门（写 rootfs / 起后台进程） | ❌ 能 | ⚠️ 只读 rootfs + tmpfs 才挡 | ✅ | ✅ 重建即可 | ✅ |
| 读宿主设备 | ❌ 能（特权） | ⚠️ 取决于设备挂载 | ✅ | ✅ | ✅ |
| 跑任意二进制 | ✅ | ✅ | ⚠️ 兼容性 | ✅ | ❌ 不行 |
| 用 GPU | ✅ | ✅ | ⚠️ 受限 | ⚠️ 需直通方案 | ❌ |

> 🩸 没有任何一档能同时满足「跑任意二进制」「用 GPU」「跑得飞快」。所以真实系统几乎总是**分档**：可信代码走容器、用户代码走 microVM、纯计算插件走 WASM、网页操作走浏览器池。**分档不是不彻底，而是唯一正确的形态**（§51.9）。

## 51.4 启动延迟：冷启动的五段、预热池与快照恢复

```text
图 2 · 一次「每任务一个新沙箱」的冷启动瀑布（microVM + CPython 科学栈）

t=0
│ ① 排队与放置（队列等待 + 调度 + 拉镜像层）              ████████           60–250 ms
│ ② 镜像/rootfs 就绪（块设备挂载 + overlay）              ██████             80–300 ms
│ ③ 沙箱引导（guest 内核 + init + agent + vsock 挂载）    ████████████       125–400 ms
│ ④ 运行时初始化（CPython + import numpy/pandas）         ████████████████████ 380–1200 ms
│ ⑤ 应用初始化（SDK、配置、工具 schema 编译）              ████████           70–200 ms
│ ⑥ 执行（真正的任务）                                     ██                 190 ms（本例）
└───────────────────────────────────────────────────────────────────────────────►
 合计 0.8–2.6 s，其中「执行」只占 8–20%          ← 这就是「沙箱比活贵」的算术来源
```

| 段 | 谁在付费 | 省它的正确手段 | 省错的代价 |
| --- | --- | --- | --- |
| ① 排队与放置 | 调度器、镜像分发 | 节点本地镜像预热（DaemonSet 预拉）、调度亲和（同类沙箱同节点） | 改成「随便调度」→ 每次冷拉一层 200 MB 镜像 |
| ② rootfs 就绪 | 存储 / 镜像层 | 只读共享的基线层 + 每任务只挂一个小 tmpfs；microVM 用块设备快照 | 用网络存储当 rootfs → 启动被 IOPS 限死 |
| ③ 沙箱引导 | 内核 + 容器/microVM 运行时 | **不进关键路径**：预热池、快照恢复 | 想「把 guest 内核裁小」→ 收益上限就是那 100–400 ms |
| ④ 运行时初始化 | 语言运行时 | 依赖预热（preload import）、镜像内置 `.pyc`/CDS、选更轻的运行时 | 让用户 `pip install` 后再 import → 每次 1–3 s |
| ⑤ 应用初始化 | 你的 SDK | 懒加载、连接池外置、配置预注入 | 每次重新编译工具 schema → 每次几十 ms |
| ⑥ 执行 | — | 这才是该被优化的地方 | 把 90% 精力花在 ⑥，然后 ①–⑤ 把 P99 拖成 3 s |

### 4.1 语言运行时是冷启动的隐藏大头（与隔离方案无关）

| 运行时 | 空进程启动量级 | 加典型依赖后 | 可用的压缩手段 |
| --- | --- | --- | --- |
| Go（静态二进制） | 5–20 ms | 20–80 ms | 基本无需优化；适合做「沙箱里的执行器」 |
| Node.js | 100–300 ms | 300 ms–1.2 s | 依赖裁剪、`--snapshot` 类机制（版本相关） |
| CPython | 30–80 ms | **0.4–1.5 s**（numpy/pandas/scipy） | 预编译 `.pyc`、懒 import、`-X importtime` 找前 10 个耗时模块 |
| JVM | 300–800 ms | 1–3 s（Spring 类应用） | AppCDS 类数据共享、`-XX:TieredStopAtLevel=1`、AOT（版本相关，**以目标版本为准**） |

**这一列数字与隔离方案正交**：无论你选容器还是 microVM，只要任务需要 CPython 科学栈，你就得为 ④ 付 0.4–1.5 s。**所以「换隔离方案」永远解决不了「冷启动慢」，能解决的只有「池化」与「快照」。**

### 4.2 预热池：把启动从关键路径上摘掉的唯一通用手段

预热池的做法很朴素：**提前把 N 个沙箱启动到「只差最后一口气」的状态**（已引导、已挂工作区、已 import 依赖），任务来了直接「领一个、注入代码、执行」。池里的沙箱分三级预热，每级的成本与命中价值完全不同：

| 预热级别 | 预热到哪一步 | 剩余启动成本 | 每沙箱常驻内存 | 适用 |
| --- | --- | --- | --- | --- |
| L0 · 冷 | 什么都没有 | 0.8–3 s | 0 | 低频、可容忍慢的批处理 |
| L1 · 起壳 | 沙箱已引导、rootfs 已挂 | 0.4–1.5 s | 几十 MiB（VMM / 命名空间开销） | 中等并发 |
| L2 · 起运行时 | 运行时已启动、依赖已 import、等代码 | 10–50 ms | 0.3–1.5 GiB（运行时 + 依赖常驻） | 高并发、短任务 |
| L3 · 恢复到现场 | 快照恢复（内存 + 设备 + 已 import 的堆） | 30–150 ms | 快照本身在盘/内存里的成本 | microVM 专属，密度与速度兼顾 |

两个必须自己算的数：**池多大**（§51.8 账二）与**命中率多少才够**（§51.8 账三）。纪律：**池按「新建速率 × 启动延迟」定，不按「并发数」定**——复用做得越好，新建速率越低，池反而越小，这与直觉相反。

### 4.3 快照恢复：让 microVM 也能毫秒级，但只对「可冻结的状态」有效

快照恢复（snapshot / restore）把「内核 + 用户态 + 已加载的模块 + 打开的文件描述符」一起冻结成镜像，恢复时直接映射回来。它把 §51.4 的 ③④ 两段基本抹掉，只剩「恢复 + 注入」：

| 方案 | 典型恢复量级 | 硬限制 | 什么时候不能选它 |
| --- | --- | --- | --- |
| microVM 快照（Firecracker 类） | **30–150 ms**（含重建 vsock 与工作区挂载） | 快照与宿主内核/CPU 特性/固件版本强绑定；热迁移语义有限 | 需要频繁换宿主机版本、或需要 GPU 直通 |
| 容器 checkpoint（CRIU 类） | 数百 ms–数秒 | 多线程、`epoll` 状态、外部连接、`pid` 语义的兼容性长尾 | 任务里有复杂线程池或长连接 |
| 语言层预热（预 import / 预编译） | 省 ④ 段的 30–70% | 只省运行时，不省内核与挂载 | 救不了 ③ 段 |

**这就是「为什么 microVM 能毫秒级、容器不一定」的答案**：microVM 的**冷**启动比容器慢（多引导一个内核），但它的状态可以被完整冻结，「快照恢复」把它拉到 30–150 ms；而容器的「快」依赖宿主内核已就绪，一旦要冻结用户态（CRIU），兼容性长尾又把它拖回数百毫秒到数秒。**隔离三角是被「快照」撕开一个角的——但只有 microVM 这一格撕得干净。**

## 51.5 复用成本：复用省的是启动，付的是隔离

复用的本质只有一句话：**把「沙箱生命周期」除以「它服务的任务数 k」**——启动成本、内存常驻、镜像分发全部除以 k，但**上一个任务留下的状态不除以 k，它原样留给下一个任务**。剩下的是把这句展开成可检查的四层清单。

### 5.1 四种复用模型：从「零隔离」到「零复用」

| 模型 | 做法 | 启动成本/任务 | 状态污染面 | 内存/任务 | 适用 |
| --- | --- | --- | --- | --- | --- |
| **进程复用** | 一个常驻解释器，每个任务 `exec` 一段代码进去 | ~0 | **全部**（globals、module 单例、`sys.modules`、连接池、`/tmp`） | 极小 | 只适合「自家代码 + 自家 prompt」的内部工具 |
| **沙箱复用（有重置）** | 同一沙箱服务 k 个任务，每任务清工作区、轮转凭据、杀残留进程 | 启动 ÷ k | 内存层污染**清不掉**（被改过的 module、未释放的堆） | 中 | 主流做法；k 取 20–100 |
| **快照回滚复用** | microVM 快照 + 每任务回滚到同一基线 | 快照恢复 30–150 ms | 接近零（内存与磁盘一起回滚） | 中（快照常驻） | microVM 专属，最干净的复用 |
| **零复用（每任务一沙箱）** | 任务结束即销毁 | 全价（0.8–3 s） | 零 | 高（同时在跑 N 个） | 强合规、任务 > 10 s、或任务不可重放 |

### 5.2 状态污染的四个层次（每一层都有对应的重置动作）

| 层 | 具体载体 | 典型事故 | 重置动作 |
| --- | --- | --- | --- |
| **文件系统** | `/work`、`/tmp`、`~/.cache`、`__pycache__`、pip 装过的包 | 上一个租户把凭据写进 `/work/out.json`，下一个租户 `cat` 到 | 每任务新建 tmpfs 工作区；`/tmp` 用 `emptyDir{medium:Memory}` |
| **进程内存** | 模块级单例、全局缓存、`sys.modules`、JIT 编译产物、连接池里的旧连接 | 任务 A 打了 `SET GLOBAL` 或改了单例配置，任务 B 读到被改的状态 | 只能靠「重启进程」或「快照回滚」；**清理函数清不干净** |
| **凭据与环境** | 环境变量里的 token、`~/.aws/credentials`、继承的 fd、metadata 的临时凭据 | 事故一里「读 `/proc/1/environ`」就是这一层 | 一次一租 + 任务结束即吊销（[47 密钥与凭据](47-secrets-and-credentials.md)）；`automountServiceAccountToken: false` |
| **内核与网络** | 后台进程、监听端口、改过的 `iptables`、残留 `unix socket` | 任务 A 起了监听端口的进程，任务 B 连上它读数据 | `pids.max` + 销毁重建；`kill -9` 整个 `cgroup.procs`；每任务新 netns |

### 5.3 复用次数 k 的算术：「至少污染一次」的概率随 k 线性逼近 1

设单任务引入「不可清理污染」的概率为 p（内存层难以完全清零，实测常见 0.1%–2% 这个量级，取决于任务类型），复用 k 次后「这一代沙箱已被污染」的概率：

```text
P(污染) = 1 − (1 − p)^k

p = 0.5%：k=20 → 9.5%    k=50 → 22.2%   k=100 → 39.4%
p = 1.0%：k=20 → 18.2%   k=50 → 39.5%   k=100 → 63.4%
p = 0.1%：k=20 → 2.0%    k=50 → 4.9%    k=100 → 9.5%
```

> **量级结论（非承诺值）**。假设：① 每次任务的污染事件独立；② 污染一旦发生就不会自愈（这是关键假设，也是「快照回滚」比「清理脚本」可靠的原因）；③ p 与 k 无关。**结论：k 不是一个「越大越省钱」的参数，它是一个「用隔离换启动」的旋钮——k 从 20 调到 100 只省 80% 的启动成本，却把污染概率从 ~10% 抬到 ~40%。所以 k 的取值必须由「一次串租户事故的代价」反推，而不是由「启动成本」正推。**

### 5.4 池的代码骨架：复用上限、代、每任务重置（Go）

两个对象、两个字段组先把语义钉住，代码只写「领」与「还」两个动作：

| 对象 | 字段 | 为什么必须有它 |
| --- | --- | --- |
| `Sandbox` | `Gen` | 代：镜像/快照版本。**换代即重建**，禁止跨代复用（否则「回滚过的镜像」与「没回滚的」混在一池） |
| `Sandbox` | `Uses` / `CreatedAt` | 两个上限：**次数**（§51.5 的 k）与**时长**（泄漏是时间的函数，不只是次数的函数） |
| `Sandbox` | `Work` / `Token` | 工作区（每任务新建 tmpfs）与凭据（一次一租，`Release` 即吊销） |
| `Pool` | `maxUses` / `maxAge` / `maxRSS` | 三条淘汰线；任一条触发 → **销毁**，不是「清一下继续用」 |

```go
// 池骨架：结构体字段见上表；这里只有「领」与「还」两个动作
func (p *Pool) Acquire(ctx context.Context, taskID string) (*Sandbox, error) {
	p.mu.Lock()
	for len(p.free) > 0 {
		s := p.free[len(p.free)-1]
		p.free = p.free[:len(p.free)-1]
		p.mu.Unlock()
		ok := s.Uses < p.maxUses && time.Since(s.CreatedAt) < p.maxAge && s.RSS() < p.maxRSS
		if ok && s.ResetForTask(ctx, taskID) == nil { // 新 tmpfs + 轮转凭据 + 杀残留进程
			return s, nil
		}
		s.Destroy(ctx) // 任一条超限：销毁重建，不做"尽力清理"
		p.mu.Lock()
	}
	p.mu.Unlock()
	return p.create(ctx, taskID) // 池空 → 冷启动：P99 的全部来源（§51.8 账三）
}

// Release：先吊销凭据，再判定淘汰 —— 三条返回路径（成功/失败/取消）都必须走到吊销
func (p *Pool) Release(ctx context.Context, s *Sandbox) {
	s.Uses++
	s.RevokeCredential(ctx)
	if s.Uses < p.maxUses && time.Since(s.CreatedAt) < p.maxAge {
		p.mu.Lock()
		p.free = append(p.free, s)
		p.mu.Unlock()
		return
	}
	s.Destroy(ctx)
}
```

> 🩸 两个细节值得点名：**① `Release` 里的吊销必须覆盖所有返回路径**——与 50 篇「预扣不归还」是同一个结构错误；**② `Destroy` 是「销毁」不是「清理」**——任何「清理脚本 + 继续复用」的方案，都会在 p = 0.5%、k = 100 的场合留下 ~40% 的污染概率。

## 51.6 浏览器池：唯一一个「有状态 + 吃内存 + 会崩」的执行面

```text
图 3 · 一个 headless Chromium 实例的进程树与内存账

  节点（32 GiB，预留 6 GiB 给系统/容器运行时/监控）
  ├─ browser 进程（主）      ~120–200 MiB   持有 profile、CDP 端点(:9222→ws)、会话
  ├─ zygote / crashpad       ~ 20– 40 MiB   进程孵化；崩溃转储（默认会写盘）
  ├─ network service         ~ 60–150 MiB   HTTP 缓存、连接池、DNS
  ├─ storage service         ~ 40–100 MiB   localStorage / IndexedDB / service worker
  ├─ gpu（无 GPU 时 swiftshader）~80–300 MiB  软件渲染：吃 CPU，且不会自己缩
  └─ renderer × N（site isolation：每个站点实例一个进程）
       ├─ site A            ~120–400 MiB   V8 堆 + DOM + 图片解码
       ├─ site B            ~120–800 MiB   长跑页面的 detached DOM 全在这里
       └─ ...
  ─────────────────────────────────────────────────────────────────────────────
  单实例（1–3 标签）起步 400–600 MiB；连续跑 500 个任务后实测 1.5–2.0 GiB
  ⇒ 26 GiB ÷ 1.5 GiB ≈ 17 个实例（按「长跑后」算，不是按「刚起时」算）
  ⇒ 若按 400 MiB 规划成 65 个 → 跑三小时进 OOM，且报警指向"内存不足"而非"池超配"
```

### 6.1 为什么浏览器的状态比容器多一个维度

| 状态 | 存在哪 | 复用会怎样 | 独立化的代价 |
| --- | --- | --- | --- |
| Cookie / localStorage / IndexedDB | profile 目录（磁盘） | 串号、串登录态、串 A/B 分组 | 新建 profile = 冷启动 + 首次访问慢 |
| HTTP 缓存 | profile 的 cache 目录 | 命中过期缓存 → 拿到别人看到过的页面 | 缓存命中没了，页面加载慢 2–5× |
| service worker | profile + storage service 进程 | **上一个租户注册的 SW 会拦截下一个租户的请求** | 只能靠新 `BrowserContext` 或新实例 |
| JS 堆 / detached DOM | renderer 进程内存 | **只涨不还**；OOM 的风险随时间累积 | 每任务回收上下文（不用杀进程） |
| GPU / 渲染缓存 | gpu 进程 | 上下文丢失、字体不一致 | swiftshader 兜底 = 更慢更占 CPU |
| CDP 会话 | WebSocket 连接 | 未解绑的 `Page`/`Runtime` 监听 = 泄漏 + 串消息 | 每任务独立 session + 显式 `detach` |

### 6.2 三种池化粒度：每任务 Browser / 每任务 BrowserContext / 复用 Tab

| 粒度 | 启动成本/任务 | 状态隔离 | 内存增长 | 判据 |
| --- | --- | --- | --- | --- |
| **每任务新 Browser 进程** | 300–900 ms（含首导航） | 最强 | 无（进程即回收） | 强隔离、低频；吞吐要求低 |
| **每任务新 BrowserContext**（`Target.createBrowserContext`） | 10–80 ms | 强（cookie/缓存/storage 隔离） | 中（browser 进程与 gpu 进程仍共享，页缓存与进程级缓存不回收） | **默认推荐**：事故三的修复就是这一档 + 定时回收 |
| **复用同一 Tab / 同一 Context** | ~0 | 无 | 高（就是事故三） | 只在「同一租户、同一会话、连续多步」时成立，且必须限步数与时长 |

三种粒度对应三种事故：第一档把 P99 拖到秒级（事故二），第三档把租户串起来并必然 OOM（事故三）。**第二档是唯一「成本可控 + 隔离够用」的默认值，但不免费**：browser、gpu、network service 这些**跨 context 共享**的部分照旧泄漏，所以必须叠加「每 N 任务 / 每 T 分钟回收整实例」。

### 6.3 崩溃恢复与健康检查：端口通 ≠ 实例可用

| 故障 | 表现 | 为什么端口检查抓不到 | 正确的探活 |
| --- | --- | --- | --- |
| renderer 崩溃（OOM / GPU） | 任务报「页面已崩溃」，但 browser 进程还活着 | 9222 仍然可连 | 每任务 `Page.navigate` 后再 `Runtime.evaluate("1+1")` |
| browser 主进程僵死 | CDP 连接能建，命令超时 | WebSocket 握手成功 | 探活带**命令级超时**（2–3 s）+ `Target.getTargets` 计数 |
| profile 锁残留 | 新实例起不来（`SingletonLock`/`SingletonSocket`） | 端口从来没起来过，「实例数」看着少却没人查原因 | `ready` 与 `desired` 分开监控；起不来要报警而不是无限重试 |
| 僵尸进程堆积 | 内存与 PID 都在涨，池「可用数」不变 | 端口是通的（老实例的） | `pids.max` + 采集 renderer 进程数，超阈值即回收 |
| 磁盘写满（crash dump / 缓存） | 全部实例同时挂 | 挂着之前端口是通的 | `ephemeral-storage` 上限 + 关掉崩溃转储 |

### 6.4 为什么浏览器池最容易 OOM：四个乘法项叠加

把内存账写成乘法链就明白它不是「某个 bug」：`单实例内存 ≈ 基线(0.35–0.6 GiB) + 页面数 × 每页(0.12–0.8 GiB) + 泄漏项(0.05–0.2 GiB/百任务)`；`可放实例数 = (节点内存 − 系统预留) ÷ 单实例内存（按长跑后取值）`。**四个项全往同一个方向推**：① 基线大（多进程模型）；② 每页大（V8 + 图片 + DOM）；③ 泄漏项随时间线性增长且不可回收；④ 每实例的并发标签数受限于「一个标签卡住会拖住其他」（CPU 峰值被 browser 与 gpu 进程共享）。结局不是「慢」，是 **OOMKilled + 池塌缩 + 任务全失败**（事故三）。正确做法只有三条：**按长跑后内存规划、按任务数/时长回收、池满时降并发而不是排队**。

## 51.7 资源与配额：cgroup v2 的三个上限，以及「杀」与「慢」的区别

### 7.1 关键文件：每一个都对应一条物理路径

| 文件（cgroup v2） | 语义 | 超限时的行为 | 症状该往哪查 |
| --- | --- | --- | --- |
| `memory.max` | **不可回收内存**的硬上限（超出触发内核 OOM killer） | **进程被杀**（`oom_kill` 计数 +1） | 任务「无缘无故失败」、Pod `OOMKilled` |
| `memory.high` | 软上限：超过施加回收压力 | **变慢**（回收 → 缺页 → 抖动），不杀 | P99 变差但无错误日志 |
| `memory.swap.max` | 交换配额（v2 里通常设 0） | 有 swap 就「慢死」，没 swap 就「快死」 | 延迟曲线拖尾 + IO 高 |
| `cpu.max` | `quota period`（如 `200000 100000` = 2 核） | **节流**（`nr_throttled` 增长），不杀 | 任务慢 2–10×、`cpu.stat` 里 `throttled_usec` 飙升 |
| `pids.max` | 进程/线程数上限 | `fork`/`clone` 返回 `EAGAIN` | 「诡异的空指针 / 起不来子进程」，而不是「被打死」 |
| `memory.events` / `memory.peak` | 事件计数与峰值 | — | **取证第一站**：`oom_kill > 0` 即被杀的铁证 |

```bash
# cgroup v2（内核 5.x+，systemd 发行版统一挂在 /sys/fs/cgroup）+ 手工沙箱
CG=/sys/fs/cgroup/agent-task-42
mkdir -p "$CG"

# ① 内存：max 触发 OOM kill（任务失败）；high 触发回收压力（任务变慢）
echo $((1024*1024*1024)) > "$CG/memory.max"    # 1 GiB：不可回收部分超了就被杀
echo $((768*1024*1024))  > "$CG/memory.high"   # 768 MiB：过了就只回收/节流，不杀
echo 0 > "$CG/memory.swap.max"                 # 不给 swap：宁可"快死"，不要"慢死"

# ② CPU：quota/period = 2 核；超了是节流（throttled），不是失败
echo "200000 100000" > "$CG/cpu.max"

# ③ PID：不设这个，fork 炸弹会把整台节点打死，且报警会指向错误的方向
echo 512 > "$CG/pids.max"

# ④ 把任务塞进去（真实系统里用 clone(CLONE_NEWNS|NEWPID|NEWNET|NEWUSER) 后再挂 cgroup）
echo $$ > "$CG/cgroup.procs" && exec python3 /work/main.py

# ⑤ 事后取证：先看「是不是被杀的」，再看「是不是被限流的」
cat "$CG/memory.events"   # oom / oom_kill：>0 说明被内核杀过
cat "$CG/memory.peak"     # 峰值（5.19+）；比反复采样 memory.current 可靠
cat "$CG/cpu.stat"        # nr_throttled / throttled_usec：>0 说明被节流过
```

### 7.2 「杀」与「慢」是两种完全不同的故障，必须用不同指标区分

| | OOM kill | CPU throttling | pids 打满 |
| --- | --- | --- | --- |
| 现象 | 任务**失败**，进程消失，退出码 137 一类 | 任务**成功但很慢**，延迟长尾 | 子进程起不来，报 `EAGAIN` / 莫名的 null |
| 面板 | `oom_kill` 计数、Pod 重启 | `nr_throttled`、`throttled_usec`、P99 拖尾 | fork 失败率、进程数接近 `pids.max` |
| 常见误判 | 「内存泄漏」（实际是 `memory.max` 太小或页缓存误算） | 「代码慢 / DB 慢」（实际是 1 核跑 2 核的活） | 「镜像有问题」 |
| 正确处置 | 先看 `memory.events`，再看 `memory.peak / memory.max` 比值 | 看 `cpu.max` 与任务实际需要几个核 | `pids.max` 按「正常线程数 × 3」留余量 |

### 7.4 网络 egress：逃逸的第二条路（也是唯一能换到「钱」的那条）

| --- | --- | --- |
| 默认拒绝出站 | netns 内 `default drop`，只放白名单（镜像仓库、包索引、业务 API） | 任务可扫内网、打 metadata、连 C2 |

## 51.8 三本账：内存、池大小、冷启动 P99

三本账分别回答三个不同的问题，不要混着算：**账一算「一台机器能放几个沙箱」，账二算「池子要多大」，账三算「P99 会不会破 SLO」**。三个答案的输入完全不同——这也是执行面容量规划最常见的错误来源（用账一的数去定账二，或用账二的平均值去答账三的分位数）。

### 账一 · 每沙箱内存 = 运行时 + 应用 + 页缓存（+ 峰值余量）

**假设清单**：Python 3.12 代码执行沙箱；业务是「读 CSV → pandas 处理 → 输出 JSON」；依赖为 numpy + pandas + matplotlib；任务数据平均 100k 行 × 20 列；节点 64 GiB；容器运行时 + kubelet + 监控预留 8 GiB；`memory.max` 按「单沙箱封顶」设。

| 组成 | 量级 | 是否可回收 | 备注 |
| --- | --- | --- | --- |
| 解释器基线（CPython + 标准库） | 38 MiB | ❌ anon | `import sys` 级别的空进程 |
| 科学栈 import（numpy/pandas/matplotlib） | 210 MiB | ❌ anon（大部分） | 首次 import 的峰值，之后常驻 |
| 应用/SDK 初始化 | 55 MiB | ❌ anon | 工具 schema、HTTP 客户端池 |
| 任务数据（DataFrame 峰值） | 60–200 MiB | ❌ anon | `100k × 20 × 8 B ≈ 16 MB`，但 pandas 的中间副本常放大 3–10× |
| 页缓存（读 CSV、`.pyc`、`pip` 缓存、字体） | 80–250 MiB | ✅ file（可回收） | 在 cgroup v2 里**计入** `memory.current` |
| 峰值余量（GC 抖动 + 序列化瞬时） | 上项的 25–30% | — | 不给余量 = 用 OOM 当 GC |

| 步 | 算式 | 结果 |
| --- | --- | --- |
| 单沙箱 anon（不可回收） | `38 + 210 + 55 + 150（数据中位）` | **453 MiB** |
| 单沙箱 file（页缓存） | 典型值，可被回收 | 150 MiB |
| `memory.current` 观测值 | `453 + 150` | 603 MiB |
| 定 `memory.max` | `453 × 1.30（峰值余量）≈ 590` → 取 768 MiB | 768 MiB |
| 节点可放沙箱（上限） | `(64 − 8) GiB ÷ 0.768 GiB = 56 ÷ 0.768` | **72 个** |
| 按 75% 水位（突发 + 碎片留活路） | `72 × 0.75` | **54 个** |

> **量级结论（非承诺值）**。假设：① 依赖集固定（版本一变，`import` 后内存可差 100 MiB）；② 任务数据中位 100k 行；③ 页缓存大部分可回收。**两个必须记住的方向：① 用 `RSS` 估容量会低估 25–35%（页缓存与 tmpfs 都算在 cgroup 里）；② 用 `memory.current` 估又会高估（file 型缓存可回收）。真正决定「会不会被杀」的是 anon + tmpfs + 内核不可回收部分，所以口径是「`memory.max` 按 anon × 1.3 定，容量按 `memory.max` 算」。**

### 账二 · 池大小 = 并发任务 × 单任务时长 ÷ 复用次数（先把单位说清）

这条式子抓对的是「**复用次数 k 必须出现在分母**」，但直接照抄会算出单位是「任务·秒」的东西，不是沙箱数。落成可用的三步：

| 步 | 式子 | 为什么是它 |
| --- | --- | --- |
| ① 同时在跑的沙箱数 | `= 并发任务数 C` | 每个在跑的任务占一个沙箱，与 k 无关 |
| ② 新建沙箱的速率 | `= C ÷ (单任务时长 T × 复用次数 k)` | k 把新建速率除下去，单位「个/秒」 |
| ③ 预热池大小 | `= 新建速率 × 启动延迟 L × 安全倍数` | Little 定律：池 = 到达速率 × 停留时间 |

**算例**：C = 120 并发任务、T = 45 s、启动延迟 L = 1.6 s（microVM 冷启）、安全倍数取 3（应对到达抖动）。

| 复用次数 k | 新建速率 = C ÷ (T × k) | 预热池 = 速率 × L × 3 | 同时驻留沙箱 | 常驻内存（按账一 0.75 GiB） |
| --- | --- | --- | --- | --- |
| 1（每任务一沙箱） | 120 ÷ 45 = **2.67 个/s** | 2.67 × 1.6 × 3 = 12.8 → **13** | 120 | 90 GiB（**一台 64 GiB 节点装不下**） |
| 20 | 120 ÷ (45×20) = **0.133 个/s** | 0.133 × 1.6 × 3 = 0.64 → **1–2** | 120 | 90 GiB（同上，与 k 无关） |
| 20（若 T=45 s、C=12） | 12 ÷ 900 = 0.013 个/s | 0.013 × 1.6 × 3 = 0.06 → **1**（取最小 1） | 12 | 9 GiB |

> **量级结论（非承诺值）**。假设：① 到达近似泊松、抖动由安全倍数吸收；② 沙箱内任务串行；③ 启动延迟取 §51.4 中位。**结论两层：① 复用把预热池从 13 压到 1–2，这是「省启动」的全部来源；② 它一点也没省「同时在跑的沙箱数」（120 照旧）——「复用省内存」只在「复用让任务串行化、从而降低并发」时成立。这就是「池要多大」与「要几台机器」是两个问题的原因。**

### 账三 · 冷启动 P99 = 各段之和 × 冷启动比例（分界点在 1%）

P99 是**混合分布**的分位数，不是「平均启动时间 × 某个系数」。设热启动 180 ms、冷启动分布落在 0.9–2.6 s（中位 1.5 s）、冷启动占比 p：

总延迟是混合分布：`总延迟 = p × 冷启动分布 + (1 − p) × 热启动分布`。**P99 落在哪一段，只取决于 p 与 1% 的大小关系**：`p > 1%` 时 99% 分位掉进冷启动那一段（因为热启动只占 `1 − p < 99%`）；`p = 1%` 时正好是分界点，P99 ≈ 热启动的高分位（~0.21 s）；`p < 1%` 时 P99 由热启动决定，冷启动只影响 P99.9。

| 冷启动比例 p | P99 落在 | P99 量级 | 与 800 ms SLO |
| --- | --- | --- | --- |
| 0.5% | 热启动 99.5 分位 | ~0.20 s | ✅ 达标 |
| **1%** | 分界点 | **~0.21 s** | ✅ 达标（但仍危险：任何抖动都会越线） |
| 2% | 冷启动中位 | **~1.50 s** | ❌ 超 1.9× |
| 4% | 冷启动 75 分位 | **~1.90 s** | ❌ 超 2.4× |
| 10% | 冷启动 91 分位 | **~2.20 s** | ❌ 超 2.75× |

**反推池的验收线**：每小时 8,000 个任务、SLO 要求 P99 ≤ 800 ms → 允许的冷启动次数 < `1% × 8,000 = 80 次/h` → **预热池命中率必须 > 99%**。事故二里 p ≈ 100%（没有池），所以 P99 直接就是冷启动分布本身。

> **承诺值 / 量级结论的边界**：`1%` 这个分界点是**数学恒等**（P99 的定义就是第 99 百分位），可以当承诺值用；「P99 ≈ 1.9 s」是**量级结论**，依赖冷启动分布的形状假设（这里取 0.9–2.6 s 的均匀/对数正态近似），换假设请在 1.3–2.2 s 区间内理解。

```python
# 三本账复算：改任一假设直接重跑（口径见 §51.8）
def mem_per_sandbox(interp=38, sci=210, app=55, data=150, headroom=1.30):
    anon = interp + sci + app + data          # MiB，不可回收
    return anon, anon * headroom              # (anon, 建议 memory.max)

def pool_size(concurrent, task_s, launch_s, k, safety=3):
    rate = concurrent / (task_s * k)          # 新建速率：个/秒
    return rate, max(1, round(rate * launch_s * safety)), concurrent

def p99_mix(p, warm=0.18, cold=(0.9, 2.6)):
    if p <= 0.01:                             # 99% 质量都在热启动里
        return warm * 1.18                    # 热启动分布的 ~99 分位
    q = (0.99 - (1 - p)) / p                  # 落在冷启动分布内的分位
    lo, hi = cold
    return lo + (hi - lo) * q

print("账一:", mem_per_sandbox())                          # (453, 589) MiB
print("账二 k=1:", pool_size(120, 45, 1.6, 1))           # (2.67, 13, 120)
print("账二 k=20:", pool_size(120, 45, 1.6, 20))         # (0.133, 2, 120)
for p in (0.005, 0.01, 0.02, 0.04, 0.10):
    print(f"账三 p={p:.1%}: P99≈{p99_mix(p):.2f}s")      # 1% 是硬拐点
```

## 51.9 架构边界：什么时候容器够、什么时候必须 microVM / WASM

### 9.1 一张判定表（评审时按「输入是谁」选，不按「性能」选）

| 你的输入长什么样 | 容器够吗 | 推荐档位 | 判据 |
| --- | --- | --- | --- |
| 自家 prompt 模板生成的固定代码（不接用户输入拼接） | ✅ 够 | 容器（加固） | 威胁模型是「误操作」而不是「恶意」 |
| 用户在对话里写的 SQL / 表达式（只读、有超时） | ⚠️ 勉强 | 容器 + 只读挂载 + 严格 egress | 不能写文件、不能出网则风险可控 |
| 用户上传的 Python/JS 代码（要 `pip install`、要读文件） | ❌ 不够 | **microVM**（或 gVisor） | 共享内核 + 可写 rootfs + 出网 = 事故一的全部条件 |
| 用户上传的二进制 / 需要 GPU / 强合规多租户 | ❌ 不够 | **microVM**（独立节点池） | 只有硬件虚拟化能给「内核级」承诺 |
| 用户提供的「规则/表达式/插件」，逻辑是数据进数据出 | ✅ 更好 | **WASM** | 毫秒级、无系统调用、可确定性重放 |
| 网页操作（登录、点击、抓取） | ❌ 不够 | 浏览器池（**建在 microVM 或加固容器之上**） | 浏览器执行的是不可信页面的 JS，自身也要被隔离 |
| 长时批处理（分钟级、要读写大文件） | ✅ 够 | 容器 + 独立节点池 + 无出网 | 启动成本占比低，隔离强度用「网络 + 挂载」补 |

三条边界值得单拎出来：

1. **容器不是「弱一点的 microVM」，而是「另一种东西」**：容器给的是**一致性**与**资源上限**，microVM 给的是**边界**。把不可信代码放进容器，是把「边界问题」当成了「配置问题」——配置再严，共享内核这条不变。
2. **WASM 不是「更快的容器」**：它快是因为**没有系统调用**；一旦你要「跑用户装的包」「起子进程」，你需要的正是它没有的东西。用它跑 CPython 科学栈，是拿「启动快」换「执行慢一个量级」。
3. **浏览器池必须建在某个沙箱之上**：renderer 是浏览器自己的沙箱（进程 + 站点隔离），但**这层内部仍会遇到浏览器 0day**。企业级形态是「microVM 里跑 Chromium」，不是「Chromium 自己当沙箱」。

### 9.2 浏览器池为什么不能当无状态服务

| 无状态服务的假设 | 浏览器池的现实 | 你要补什么 |
| --- | --- | --- |
| 扩副本 = 线性加吞吐 | 每实例有内存地板（0.4–0.6 GiB）+ 只涨不还的泄漏项 | 按「长跑后」规划 + 每 N 任务/每 T 分钟回收 |
| 请求结束 = 资源归还 | browser/renderer/gpu 进程、缓存、SW 都还在 | 每任务新 `BrowserContext` + 定期整实例回收 |
| 健康检查 = 端口/HTTP 200 | 端口通但 CDP 会话已死、renderer 已崩 | 命令级探活（navigate + evaluate + 超时） |
| 优雅重启 | 重启丢掉 profile 锁目录、僵尸进程、监听端口 | `SingletonLock` 清理 + `pkill` + 就绪探针 |
| 冷启动几十毫秒 | 300–900 ms（新 Browser）+ 首导航 1–3 s | 预热到「已起 Browser、已建 context」 |

### 9.3 多租户隔离的最小要求（缺一条就不该上线）

| # | 要求 | 缺了会怎样 |
| --- | --- | --- |
| 1 | 每个租户有**独立的内核边界**（microVM）或至少独立 user ns + 独立 seccomp 白名单 | 一个租户的漏洞 = 全平台（事故一） |
| 2 | 无宿主凭据：不挂 `docker.sock`、不 `automount` SA token、元数据端点封禁 | 「读文件」升级成「拿云凭据」 |
| 3 | egress 默认拒绝 + 白名单 + 受控 DNS | 内网扫描、C2、DNS 隧道 |
| 4 | 只读 rootfs + tmpfs 工作区 + `ephemeral-storage` 上限 | 持久化后门、磁盘写满拖垮节点 |
| 5 | 三个硬上限（`memory.max` / `cpu.max` / `pids.max`）必须都有 | 「杀」「慢」「fork 失败」三种故障混在一起，无法定位 |
| 6 | 时间上限 + 输出上限（字节/行数） | 一个死循环或 `yes` 就能占满整个池 |
| 7 | 凭据一次一租、任务结束即吊销（[47 密钥与凭据](47-secrets-and-credentials.md)） | 复用池变成凭据分发器 |
| 8 | 审计（命令、网络目的地、文件访问）可回溯；池的「代」与镜像版本可追踪 | 出事时只看到「任务成功」；修了镜像而老沙箱还在跑旧版 |
| 9 | 一个租户的用量上限（并发 + 单位时间总数） | 一个大客户吃掉整个池（与 50 篇「单租户吃满配额」同构） |

## 51.10 踩坑清单（现象 → 根因 → 定位 → 修复 → 防复发）

### ① 沙箱「跑得好好的」，但宿主被看光了

| 项 | 内容 |
| --- | --- |
| **现象** | 任务成功率高、无异常；某次安全扫描发现沙箱里能 `ls /host`、能连 `169.254.169.254`、`/proc/1/environ` 里能看到编排系统的注入变量 |
| **根因（指到物理形态）** | 共享宿主内核 + 全默认 `securityContext`（root、可写 rootfs、未关 SA token）+ `hostPath`/`docker.sock` 挂载 + egress 无策略。**容器只是命名空间视图，不是内核边界** |
| **定位** | 在沙箱里跑一次资产盘点：`ls /`、`cat /proc/1/environ`、`cat /proc/self/status`（看 caps）、`curl -m2 169.254.169.254`、`ls /var/run/*.sock`、`mount \| grep -v tmpfs`；任何一项有输出就是缺口 |
| **修复** | 换 microVM/`runtimeClass`；`drop: ALL` + `allowPrivilegeEscalation: false` + `readOnlyRootFilesystem`；移除 `hostPath` 与 `docker.sock`；egress 白名单 + 封 metadata |
| **防复发** | 把资产盘点做成每次发布的门禁用例（与单元测试同级）；新增挂载走评审（`hostPath` 一律拒绝） |

### ② 隔离升级后 P99 翻了十倍，团队以为是「microVM 太慢」

| 项 | 内容 |
| --- | --- |
| **现象** | 换 `runtimeClass` 后任务成功率不变，但 P50 从 180 ms 到 1.4 s、P99 从 320 ms 到 3.1 s；任务本身只跑 190 ms（事故二） |
| **根因** | 冷启动路径全部落在关键路径上：没有预热池、没有快照恢复、依赖每次现场 `import`。**这不是 microVM 的固有成本，是「没有池」的成本** |
| **定位** | 打三段计时：`sandbox_create`、`runtime_ready`（能执行第一条语句）、`task_done`。若 `runtime_ready − sandbox_create` 占 60% 以上 → 是运行时 import，不是虚拟化 |
| **修复** | 预热池（L2：运行时已起）+ 快照恢复（L3，30–150 ms）+ 依赖预 import；池大小按 §51.8 账二算 |
| **防复发** | 「启动延迟分位」与「冷启动比例」双指标看板；每次「新节点加入」都意味着池是空的——把扩容事件与 P99 告警关联 |

### ③ 复用一个池，把 A 租户的凭据交给了 B 租户

| 项 | 内容 |
| --- | --- |
| **现象** | 某租户报告「我的 Agent 输出了不属于我的订单号」；审计发现两个任务在同一沙箱里串行，前一个任务把结果写进了 `/work/out.json` |
| **根因** | 沙箱复用了工作区与环境变量，且 `ResetForTask` 只杀了主进程，没清 `/tmp` 与残留文件；凭据也没轮转（§51.5 的四层污染） |
| **定位** | 按 `sandbox_id` 聚合日志，找「同一 sandbox 服务多个 tenant」的分布；再查 `ResetForTask` 是否覆盖 `/work`、`/tmp`、env、fd、后台进程 |
| **修复** | 每任务新建 tmpfs 工作区；凭据一次一租 + `Release` 吊销；跨租户**直接禁止复用**（同租户可复用到 k 次） |
| **防复发** | 在池层加断言：`sandbox.tenant == task.tenant`，违反即报警并拒绝；把「污染概率 1−(1−p)^k」写进容量评审 |

### ④ `pids.max` 没设，一个 fork 炸弹把整台节点打死

| 项 | 内容 |
| --- | --- |
| **现象** | 节点整体不可用（kubelet 无法响应）、监控断流、宿主机负载 400+；任务日志里只有「卡住」 |
| **根因** | 只设了 `memory.max` 与 `cpu.max`，没设 `pids.max`；一个 `while True: fork()` 或线程池失控把 PID 表耗尽，导致**所有**容器（包括系统组件）都无法创建进程 |
| **定位** | `pids.current` 逼近 `pids.max`；`ps -eLf \| wc -l` 在节点上爆炸；容器内 `fork` 返回 `EAGAIN` |
| **修复** | 所有沙箱设 `pids.max`（如 512），并在池层监控「进程数/PID 上限」比值 |
| **防复发** | 「三个上限必须同时存在」写成准入检查（缺一即拒绝创建）；「PID 饱和度」做成节点级指标（对整机影响远大于单容器内存） |

### ⑤ 浏览器池「显示 24 个、实际 2 个能用」

| 项 | 内容 |
| --- | --- |
| **现象** | 池的 `size` 正常，但成功率掉到 12%、队列暴涨；重启 Pod 后恢复一会儿（事故三） |
| **根因** | ① 健康检查只看端口；② 复用同一 browser，RSS 只涨不还；③ 重建被 `SingletonLock`/`SingletonSocket` 与残留进程挡住；④ 池满时无限排队而非降并发 |
| **定位** | 对比 `pool_ready` 与 `pool_desired`；采集每实例 RSS 与 renderer 进程数；用命令级探活替代端口探活；看「重建失败率」 |
| **修复** | 每任务 `Target.createBrowserContext`；每 50 任务或 30 分钟回收整实例；`--disable-dev-shm-usage`；`memory.max` 兜底；重建前清锁目录；池满时对上游返回「排队/降级」而非静默排队 |
| **防复发** | 「就绪数/期望数」与「重建失败率」双告警；每季度演练一次「杀掉一半实例」，验证自愈 |

## 51.11 观测：六个指标覆盖 90% 的执行面故障

| 指标 | 含义 | 健康值 | 拐点 / 告警 | 它提前告诉你的坏事 |
| --- | --- | --- | --- | --- |
| `sandbox_start_seconds`（分位） | 从「决定创建」到「能执行第一条语句」 | P95 < 400 ms | P95 > 1 s | 冷启动进关键路径（§51.4） |
| **冷启动比例** | 取池未命中 ÷ 总任务 | < 1% | > 1% | **P99 立刻被冷启动接管**（§51.8 账三） |
| `sandbox_oom_kill_total` | cgroup OOM kill 次数（counter） | ≈ 0 | 任何非零 | `memory.max` 太小或账一算错 |
| `cpu_throttled_ratio` | `nr_throttled / 总周期` | < 5% | > 20% | 任务慢不是代码慢，是配额不够 |
| `sandbox_egress_denied_total` | egress 白名单拒绝次数 | 低且平稳 | 突增 10× | 有人在扫内网 / 有后门 / 依赖换域名 |
| 浏览器崩溃率 + 池就绪数 | 真实可用容量 | 崩溃 < 1%/千任务；ready ≈ desired | ready < 0.8 × desired | 池正在塌缩（事故三） |

```promql
sum by (reason) (rate(sandbox_egress_denied_total[5m]))
sum(browser_pool_ready) / clamp_min(sum(browser_pool_desired), 1)
sum(rate(browser_renderer_crash_total[10m])) / clamp_min(sum(rate(browser_task_total[10m])), 1)

# ⑥ 复用深度：超过 k 说明淘汰逻辑没生效
sum(sandbox_uses) / clamp_min(count(sandbox_uses), 1)
```

> 🩸 三条指标纪律：① **启动延迟必须按「热/冷」分开看**，混在一起的 P95 会在池命中率下降时「看起来还行」（事故二的盲区）；② **标签只允许 `pool`、`runtime`、`tenant`**，禁止 `task_id`/`sandbox_id`（与 50 篇同一红线，见 `→ comp/48` 的基数陷阱）；③ 指标名与开关前提随版本变（`container_cpu_cfs_*` 依赖 cgroup 统计导出、`memory.peak` 需内核 5.19+），上线第一件事是用真实任务抓一遍再抄名字。

## 51.12 一页速记

| 问题 | 一句话答案 |
| --- | --- |
| 容器能当安全边界吗 | **不能**。它共享宿主内核，只提供命名空间视图与资源上限 |
| gVisor 换到了什么 | 用「syscall 兼容性长尾 + 性能税」换「不共享宿主内核」 |
| 冷启动能压到多少 | 容器 0.3–2 s、microVM 冷 0.8–3 s、microVM 快照 30–150 ms、WASM 毫秒级 |
| 冷启动慢主要慢在哪 | 语言运行时 import（CPython 0.4–1.5 s / JVM 1–3 s），**与隔离方案无关**；池要多大见下 |
| 池要多大 | `新建速率 = C ÷ (T × k)`；`池 = 速率 × 启动延迟 × 安全倍数`。**不按并发数定** |
| P99 什么时候失控 | 冷启动比例 > **1%** 时，P99 就从「热启动」切换到「冷启动」 |
| 复用的三条淘汰线 | 次数（k）、时长、内存（`maxRSS`）；任一超限 → **销毁**，不是清理 |
| `memory.max` 与 `memory.high` | 前者**杀**（任务失败），后者**慢**（回收抖动） |
| `cpu.max` 超了会怎样 | **节流**（变慢），不失败；看 `nr_throttled` |
| `pids.max` 忘了设会怎样 | fork 炸弹打死**整台节点**，且报警指向错误方向 |
| 浏览器池最大的坑 | 复用同一 browser → 内存只涨不还 → 必然 OOM；修法是「每任务新 context + 定期回收」 |
| 多租户上线的最小要求 | 独立内核边界 + 无宿主凭据 + egress 白名单 + 三个硬上限 + 一次一租凭据 |

**一句边界**：执行面能把「跑什么、跑多久、跑多重」都管住，但**它管不住「跑完之后世界有没有被改过」**——副作用、外部写操作、真实世界的按钮，只能靠幂等与审计在应用层兜（`→ comp/52` 的语义漂移一类）。

## 51.13 自检题（5 题，答案要点）

**1. 团队说「我们的沙箱是 Docker 容器，已经隔离了」。请用三句话说明这句话为什么是错的，并给出一条能在 5 分钟内验证的做法。**

`runc` 容器与宿主**共享内核**：namespace 只改「看见什么」、cgroup 只限「用多少」，都不拦系统调用；默认 `securityContext` 常是 root + 可写 rootfs + 挂载 `docker.sock`/`hostPath`，三者凑齐等于没有边界。5 分钟验证：在沙箱里跑资产盘点（`ls /`、`cat /proc/1/environ`、`ls /var/run/*.sock`、`curl -m2 169.254.169.254`、`mount | grep -v tmpfs`），任何一项有输出即为缺口。

**2. 把执行面从容器换成 microVM 后 P99 从 320 ms 变成 3.1 s，而任务本身只要 190 ms。请给出诊断顺序，并说明为什么「把 guest 内核裁小」不是答案。**

先分三段计时：`sandbox_create`（引导）、`runtime_ready`（能跑第一条语句）、`task_done`。若 `runtime_ready − sandbox_create` 占大头 → 是 CPython/依赖 import（0.4–1.5 s），与虚拟化无关；若 `sandbox_create` > 500 ms → 是引导与挂载。裁 guest 内核的收益上限就是那 100–400 ms，**而 P99 的大头是运行时初始化与「没有池」**。顺序：① 预热池（L2）；② 快照恢复（30–150 ms，抹掉 ③④ 段）；③ 依赖预 import + `.pyc` 入镜像；④ 按 §51.8 账二定池、按账三验收「冷启动比例 < 1%」。

**3. 一个池的复用次数 k 从 20 提到 100，启动成本降了 80%，为什么不能直接提？给出你把决策写进评审时用的三个数。**

因为污染概率是 `1 − (1−p)^k`：p = 0.5% 时 k=20 → 9.5%，k=100 → 39.4%；而「内存层污染」清理不掉（改过的 module 单例、未释放的堆），只有销毁或快照回滚能解决。评审要给三个数：① 单任务污染概率 p；② 一次串租户事故的期望损失；③ 启动成本节省绝对值（每次多少 ms × 每月新建次数）。判据：`p × k × 事故损失 < 节省的启动成本`，否则 k 停在上限内。

**4. 浏览器池「显示 24 个实例、成功率 12%」。请说出至少四条根因，以及为什么「加实例」和「加内存」都救不了。**

根因：① 健康检查只看端口 9222，抓不到 renderer 崩溃与 CDP 会话僵死；② 复用同一 browser，RSS 长到 1.9 GiB（只涨不还）；③ 重建被 `SingletonLock`/`SingletonSocket` 与残留进程挡住，24 个变 2 个；④ 池满时无限排队，上游超时重试再放大压力。加实例救不了（新实例同样泄漏，32 GiB 节点上 1.5 GiB/实例只放 ~17 个）；加内存也救不了（泄漏是时间函数，OOM 只是「何时发生」）。修法：每任务 `Target.createBrowserContext` + 每 50 任务/30 分钟回收整实例 + 命令级探活 + `memory.max` 兜底 + 池满时降并发。

**5. 你要给一个「用户上传 Python 脚本并执行」的功能做容量规划：120 并发、任务 45 s、P99 要求 800 ms。请列出你会先算的四个数，以及分别用本篇哪一节的方法。**

① **单沙箱内存**（账一）：anon ≈ 450 MiB，`memory.max` 取 ×1.3 ≈ 0.6–0.8 GiB；② **同时驻留沙箱数**（= 120，与 k 无关）× 单沙箱内存 → 内存总量（120 × 0.75 = 90 GiB ⇒ 至少 2 台 64 GiB 且留水位）；③ **新建速率与预热池**（账二）：`R = C ÷ (T × k)`，k=20 时 0.133 个/s，池 1–2；④ **冷启动预算**（账三）：每小时任务数 × p < 1%，即池命中率 > 99%，否则 P99 直接变 1.5–1.9 s。④ 不达标时 ①②③ 算得再准也没用——**P99 由「池命中率」决定，不由「单实例性能」决定**。
