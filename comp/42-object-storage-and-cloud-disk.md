# 42. 对象存储与云盘：S3 语义、multipart、限流与 IOPS 模型

> **状态**：`已完成（初稿）` ｜ **所属**：第九部分 · 横切基础件 ｜ **编号**：42 / 53
> **本篇定位**：全仓唯一一处把「对象存储（S3 语义）」与「云盘（块设备）」这两件**看起来都是"存数据的东西"、实际契约完全相反**的基础件摆在同一张桌子上对照的篇目——一个是 HTTP 动词上的不可变对象，一个是「配额 × 块大小」的算术；一个卖无限容量但每次访问都是请求，一个卖固定容量但延迟是微秒级。它不重写「湖表怎么在对象存储上变成表」（归 [35 Iceberg / 表格式](35-iceberg-table-format.md) §35.3、§35.7）、不重写「只追加日志为什么快」（归 [28 Kafka 的日志](28-kafka-log-segments.md) §28.4）、不重写「大请求体怎么在入口被截断/缓冲」（归 [39 入口网关](39-gateway-and-load-balancing.md) §39.4）、也不重写「什么数据模型该选哪类存储」（那是 [eng/35 存储选型](../eng/35-storage-model-selection.md)）——它只回答一个问题：**当你把一个组件的数据放到对象存储或云盘上，它的语义、请求速率与 IOPS 配额会怎样反过来改写这个组件的行为。**
> **读法**：线上正在 503 / 上传雪崩，直接读 §42.4 与 §42.11；账单莫名涨（请求费、出网费、孤儿分片），读 §42.8 与 §42.5；数据库变慢但 CPU 不高，读 §42.6 与 §42.9 账三；被「重命名目录」「ls 很慢」「FUSE 上跑数据库」坑过，读 §42.3 与 §42.7。想先建立"这些墙长在哪"的直觉，读 §42.1 的三起事故；只想要结论的翻 §42.13。
> **一句话**：对象存储卖的不是硬盘，是 **HTTP 语义 + 无限容量**；云盘卖的也不是硬盘，是 **配额 × 块大小的算术**。

## 42.1 引子：三起「看起来无限、实际处处是墙」的事故

对象存储与云盘类事故的共同形状是：**没有任何组件"挂了"**。控制台是绿的、容量还有 90% 富余、SLA 页面写着 99.99%、也没有一条 ERROR 日志——但你看到的是「上传失败率 12%」「一个 rename 跑了 13 小时」「数据库 P99 从 4 ms 变成 41 ms」。原因不是磁盘坏了，而是**你以为你在用一块无限大的硬盘，实际你在用一个有请求速率上限、没有 rename、按请求计费的 HTTP 服务；或者你以为你在用一块"性能足够的盘"，实际你在用一份「每秒允许多少次 IO」的配额**。

三起事故分别打在三个不同的墙上：**请求速率（§42.4）**、**没有 rename（§42.3）**、**IOPS 配额（§42.6）**。

### 事故一：一个热点前缀 + 无抖动的立即重试，把 1,100 次上传/秒放大成 3,900 次/秒，`503 SlowDown` 持续 42 分钟（2026-02-26）

某 SaaS 的附件上传走「客户端拿 presigned URL 直传对象存储」，服务端只签发凭证与登记元数据。对象 key 由服务端生成，格式是 `uploads/{yyyy-mm-dd}/{appId}/{seq}.bin`——也就是**当天所有租户的上传都落在同一个日期前缀下**。选择这个格式的理由很正当：方便按天做生命周期清理。

晚高峰Upload QPS 1,100（平均 780 KB，聚合入向约 858 MB/s）。八点零四分开始，上传 P99 从 320 ms 抬到 480 ms，随后进程内出现第一批 503。团队的处理是"经典"的：SDK 本身有重试，业务代码外面又包了一层「失败立即重试，最多 3 次，不等待」，运维顺手把上传 worker 池从 200 扩到 500。

| 时间 | 事件 | 关键数字 |
| --- | --- | --- |
| 02-26 20:04 | 晚高峰上传 1,100 次/秒，P99 320 ms → 480 ms，首批 503 出现 | 1,100 PUT/s |
| 20:07 | 客户端 SDK 重试（带抖动）+ **业务层"立即重试 3 次"**（无退避）叠加，对象存储侧观测 PUT 3,900/s | **放大 3.5×** |
| 20:12 | 503 比例 12%；当天前缀的写入速率已越过该前缀 ~3,500 次/秒 的量级 | 越墙 |
| 20:15 | 上传 worker 池 200 → 500，**请求速率随之涨到 5,200/s**，503 比例升到 31% | 扩容加剧 |
| 20:18 | 网关内部队列积压 12,000 个任务，P99 8.4 s；前端弹「上传失败，请重试」，用户手动重试又乘一次 | 正反馈 |
| 20:52 | 定位：不是"对象存储挂了"，是**同一个前缀上的写入速率 + 无预算重试** | 42 分钟 |
| 21:20 | 改 key：前缀加 3 位哈希打散（`uploads/{hh}/{hash3}/{yyyy-mm-dd}/…`）；业务层重试改成「指数退避 + 全抖动 + 总共 2 次」；key 换成内容哈希（幂等） | 三处一起改 |
| 21:40 | 503 比例回落到 0.01%，P99 回到 330 ms | 恢复 |
| 复盘 | 上传不可用 42 分钟，失败 17,000 次；因 key 由服务端 `seq` 生成而重试产生 **2,300 个重复对象**，下游去重作业跑了 3 天 | 17,000 次失败 |

**教训不是"对象存储不稳"，而是"无限容量不等于无限请求速率"**：容量是「你存了多少」，请求速率是「你要那一小片 key 空间多快被读写」——前者几乎无上限，后者有明确的量级墙，而墙是按**前缀**（内部是分区）算的（§42.4）。第二层教训更贵：**重试必须带抖动和预算**，否则它就是一个免费的流量放大器；而"立即重试"这个写法把 SDK 里已经做好的退避整个绕过去了。

### 事故二：把「归档 90 天前的目录」写成 `mv`，4,200 万次 copy+delete 跑了 13 小时、账单 2.5 万元、报表少算 31%（2026-03-01 ~ 03-04）

某数据湖的原始日志区按 `dt=YYYY-MM-DD/hour=HH/` 组织，36 TB、**4,200 万个对象**（平均 0.86 MB）。运维要"把 90 天前的数据挪到归档前缀"，用的命令是挂载点上的 `mv`（s3fs 类 FUSE 挂载）——在任何人看来这都是"移动一个目录"。

对象存储没有目录，也没有 rename。`dt=2026-01-01/` 只是 1,200 个 key 的**公共前缀**；「移动目录」在物理上是**逐个对象 COPY（读+写一次）+ 逐个对象 DELETE**，而且这 8,400 万次操作**没有任何事务边界**。

| 时间 | 事件 | 关键数字 |
| --- | --- | --- |
| 03-01 22:00 | 开始 `mv archive/dt=…/  archive/2026Q1/…`，128 并发 | 4,200 万对象 |
| 03-01 22:00–次日 11:00 | 每对象 COPY 一次（经 FUSE 客户端中转：下载再上传）+ DELETE 一次 | **8,400 万次请求** |
| 期间 | 单前缀写入速率同样撞墙，实际吞吐 1,800 对象/秒（理论 128÷45 ms = 2,844/s） | 用时 **13 小时** |
| 03-02 03:00 | 下游 3 个按 `dt=` 路径扫的作业跑完：**一半对象还在旧前缀、一半已在新前缀**，两个作业读到的分区都不完整 | 非原子窗口 |
| 03-02 09:00 | T+1 报表 GMV 比昨日少 **31%**，无人报错，是运营先发现的 | 静默错数 |
| 03-02 11:00 | 移动完成；核对时发现 11 万个对象因客户端超时重试产生**两处各一份** | 双份 |
| 03-04 | 对账 + 重跑 + 人工补数，3 天才恢复口径 | 3 天 |
| 账单 | COPY 42M×0.035 元/千 ≈ 1,470 元；**经客户端中转的出网 36,000 GB×0.63 元/GB ≈ 22,700 元**；IA 提前删除（存了 20 天，最小 30 天）≈ 1,050 元 | **≈ 2.5 万元** |

**这起事故真正贵的不是 2.5 万元，而是 13 小时的非原子窗口**：移动期间每个消费者看到的都是"半个分区"，而**没有任何一个报错**——这正是对象存储最典型的失效形态：*你以为是原子的操作，其实是一个可以被任意时间切断的循环*。正确的做法在 [35 Iceberg / 表格式](35-iceberg-table-format.md) §35.3、§35.7 里已经写透：**「移动」在对象存储上应该被实现成"改一次指针"（新 `metadata.json` / 新分区索引），而不是"搬 N 个对象"**；真要搬，就用服务端批处理能力（S3 Batch Operations 一类）或生命周期规则，而不是 `mv`。

### 事故三：1 TB gp2 卷的 3,072 IOPS 配额被一个新接口打满，MySQL P99 4 ms → 41 ms，加 CPU 只会更糟（2026-05-16）

某订单库：MySQL 8.4 主库、8 vCPU / 32 GB、1 TiB gp2 卷。gp2 的 IOPS 模型是 `3 IOPS × 卷容量 GB`，1 TiB 就是 **3,072 IOPS 的稳态上限**（超过部分要靠 burst credit，而 1 TiB 的卷已经没有多少 credit 可烧）。

增长来自一个"很正常"的需求：订单列表页加了分页，每页 20 行，走二级索引回表，**每个请求要 5–7 次 16 KiB 随机读**。这个接口的 QPS 从 400 涨到 1,600。

| 时间 | 事件 | 关键数字 |
| --- | --- | --- |
| 05-16 10:00 | 新列表接口全量，读 QPS 400 → 1,600 | 1,600 QPS |
| 10:20 | 随机读需求 = 1,600 × 6 = **9,600 IOPS**；供给 3,072 → 利用率 ρ = 3.1 | ρ > 1 |
| 10:25 | `VolumeQueueLength` 由 2 涨到 38；`iostat` 的 r/s **钉死在 3,000**（正好配额），`await` 31 ms，`aqu-sz` 38 | 队列堆积 |
| 10:40 | SELECT P99 4 ms → **41 ms**；写入 TPS 从 800 掉到 240（写 IO 排在读后面） | 10.3× |
| 11:10 | 第一反应「CPU 才 45%，加机器」：8 → 16 vCPU，**P99 毫无改善**，反而因更多并发把队列推得更深 | 方向错 |
| 11:40 | 读 `iostat` / 卷队列长度：瓶颈在卷的 IOPS 配额，不在 CPU | 定位 |
| 12:10 | 在线改卷配方：gp3 1 TiB + provisioned **12,000 IOPS** + 500 MB/s | 见 §42.9 账三 |
| 12:25 | 饱和延迟量级 ≈ 队列深度 ÷ IOPS = 64 ÷ 12,000 ≈ 5.3 ms；实测 P99 回到 **5 ms** | 恢复 |
| 账单 | gp2 1 TiB 约 $102/月 → gp3 + 12,000 IOPS + 500 MB/s 约 $142/月（**+$40/月**） | +284 元/月 |

**"盘不够快"这件事在云上是算术题，不是玄学**：`需求 IOPS = QPS × 每请求 IO 次数`，`供给 IOPS = 卷的配额`，两者一比就知道有没有墙；而**吞吐 = IOPS × 块大小**（§42.6），所以你换了卷还得看块大小对不对。加 CPU、加连接池、加从库都改不了主库这块盘的配额——这就是"瓶颈识别错误"最经典的一种：**所有系统级指标都正常，除了一个业务从来没看过的数字（卷队列深度）**。

> 🩸 **三起事故的共同点**：没有一次是"存储坏了"。事故一是**把无限容量误当成无限请求速率**，并用无抖动重试给它装了放大器；事故二是**把"目录"和"rename"这两个 POSIX 概念带进了对象存储**，于是"移动"退化成一个可被切断的 8,400 万次循环；事故三是**把"一块盘"误当成"性能足够的盘"**，直到读到了那个真正的供给量：IOPS 配额。三者都通向同一句：**对象存储与云盘的 SLA 从来不承诺"你要多少给多少"，只承诺"在你的配额之内，我尽力"。**

## 42.2 一句话定位与唯一真问题；对象 / 块 / 文件三种语义分界

**定位**：对象存储 = **key → 一整块不可变字节 + 元数据**，所有操作都是 HTTP 动词（PUT/GET/DELETE/HEAD/LIST），每次操作一次请求、每次请求一次计费；云盘 = **一块挂在单机上的块设备**，随机写 4 KiB 页、延迟微秒级、但吞吐与 IOPS 由「卷型 + 容量 + 预配」三者决定。两者都不是"硬盘"，两者的 SLA 都是**分层的**：对象存储承诺持久性（99.999999999% 量级）但不承诺延迟与请求速率；云盘承诺持久性（io2 99.999% 量级）与**配额内的**性能，但不承诺"跨机可见"。

### 唯一真问题

> **它卖的不是硬盘，是「HTTP 语义 + 无限容量」：没有 rename、没有目录、会 503、5 GB 必须分片；云盘是「配额 × 块大小」的算术。**

这句话拆成五条推论，全篇都在给它们找证据：

1. **对象是整块替换，不是就地修改。** 改 1 个字节 = 重新 PUT 整个对象。于是"随机小写"这种数据库最基本的动作，在对象存储上等于"重传整个文件"（§42.7）。
2. **没有目录，也没有 rename。** `/` 只是一个用来做前缀过滤的字符；LIST 才是"目录"的真相，而 LIST 是分页的、有延迟的、按请求计费的。rename = copy + delete × 对象数，且不原子（§42.3、事故二）。
3. **容量几乎无上限，请求速率有明确量级。** 墙按前缀（内部是分区）算，撞墙的表现是 `503 SlowDown`——它**不是故障，是一个限流信号**（§42.4）。
4. **大对象必须分片，分片改变了一切计数。** 5 GiB 以上必须 multipart；一个 100 GB 对象的"一次上传"实际是 1,600 次请求，ETag 也不再是 MD5（§42.5）。
5. **云盘的所有性能问题都可以写成一行乘法。** `吞吐 = IOPS × 块大小`；`供给 = min(配额, 实例带宽)`；`饱和延迟 ≈ 队列深度 ÷ IOPS`。算不出来只是因为你没查那三个数（§42.6、§42.9 账三）。

**它明确不承诺什么**（后面逐条兑现）：不承诺"文件系统"（没有 rename/fsync/文件锁/目录语义，FUSE 只是把 HTTP 翻译成 POSIX，语义缺口还在，§42.7）；不承诺"低延迟随机写"（首字节 20–80 ms 量级，是本地盘 100 μs 量级的几百倍）；不承诺"请求速率随容量一起涨"（§42.4）；不承诺"移动/复制免费"（copy 是 GET+PUT，跨区还要出网费，§42.8）；云盘不承诺"多机共享"（块设备就是单机独占，多挂载写等于损坏，除非专门的集群文件系统 + 专门卷型）。

### 三种语义的分界：谁的"单位"是什么

```text
┌──────────────────────── 三种存储语义：单位、操作、墙 ────────────────────────┐
│                                                                             │
│  【文件存储 POSIX】        单位 = 文件(目录项)     例：ext4/xfs/NFS/EFS         │
│     open/read/write/pread/pwrite/rename/fsync/link/lock                     │
│     ✅ 就地随机写、✅ 原子 rename、✅ 目录树、✅ 字节范围锁                     │
│     ❌ 跨机共享要集群文件系统 + 锁服务；容量与 inode 数要预先规划               │
│                                                                             │
│  【块存储】                单位 = 扇区(512 B / 4 KiB)  例：EBS/云盘/本地 NVMe   │
│     read(offset,len) / write(offset,len) / flush                            │
│     ✅ 微秒~百微秒级随机读写、✅ 就地覆盖、✅ 你自己在上面建文件系统            │
│     ❌ 一台机器独占（多写 = 脑裂 + 损坏）；性能 = 配额，不是"物理盘全部"        │
│                                                                             │
│  【对象存储】              单位 = object key        例：S3/OSS/GCS/MinIO      │
│     PUT(整对象) / GET(可 Range) / DELETE / HEAD / LIST(分页)                  │
│     ✅ 容量近无限、✅ 11 个 9 持久性、✅ 一个 URL 给全世界                    │
│     ❌ 无 rename、无目录、无追加、无锁；每次访问 = 一次计费请求 + 数十 ms       │
└─────────────────────────────────────────────────────────────────────────────┘
        文件系统建立在块之上；对象存储不建立在你可见的任何东西之上
        （它的副本/纠删码是内部实现，不暴露给你，你也没法"修"它）
```

**一句话记住分界**：**块存储给你「地址」，文件存储给你「名字与目录」，对象存储给你「一个 URL 和一次 HTTP 事务」**。选错了不是性能问题，是语义问题——你在对象存储上追不了 `rename`，在云盘上做不了跨机共享，在文件系统上买不到"无限容量 + 按次计费"。

### 解剖卡八问：本篇答哪几问

| 问 | 本篇的答案 |
| --- | --- |
| ① 它承诺什么 | 对象存储：**持久性 + 容量 + 强一致的覆盖写（以厂商文档为准）**，不承诺延迟/请求速率/目录语义；云盘：**配额内的 IOPS 与吞吐 + 单机独占**，不承诺跨机共享 |
| ② 数据长什么样 | 对象 = `(bucket, key) → 不可变字节 + 用户元数据 + 系统元数据(ETag/存储类/版本)`；云盘 = 定长扇区序列 + 一层"卷→实例"的挂载关系（§42.3、§42.6） |
| ③ 一次读写走哪条路 | 对象：DNS/TLS → 鉴权 → 前缀分区 → 存储节点 → 返回 ETag；写是整对象（或分片）落地。延迟分解见 §42.4 表；云盘：应用 → 文件系统 → 块层 → 虚拟化层 → 卷配额 → 后端（§42.6） |
| ④ 并发与一致 | 对象存储：每个对象内**没有并发写语义**（后写覆盖，last-writer-wins），跨对象**没有事务**；云盘：块级没有并发语义，靠文件系统 + 数据库自己保证；**两者都不能替代锁服务**（`→ comp/46`） |
| ⑤ 扩展维度 | 对象存储：**分片 ✅（按前缀打散）+ 批处理摊薄 ✅（大对象、少请求）**，副本是厂商内部事；云盘：**只有垂直切**（换卷型/加预配/拆库分片），一架云盘不可横向扩 |
| ⑥ 系统级失效 | ① **请求速率撞墙 → 全局 503 雪崩**（§42.4）；② **语义缺失导致的静默错数**（rename 非原子、最终一致 LIST、ETag 误当校验，§42.3）；③ **成本失控**（请求费 + 出网费 + 孤儿分片，§42.8）；④ 云盘 **IOPS 配额打满 → 队列堆积 → P99 十倍**（§42.6） |
| ⑦ 看哪几个指标 | 5xx/`SlowDown` 比例、首字节 P99、未完成 multipart 数与字节、卷 `QueueLength`/`await`、请求费与出网费日环比（§42.12） |
| ⑧ 换掉它的信号 | 需要 rename/追加/随机小写/文件锁 → 换文件系统或数据库；单对象 < 1 MB 且被反复读 → 换 KV/缓存；云盘单卷 > 16,000 IOPS 量级仍不够 → 拆库或上本地 NVMe（§42.10） |

## 42.3 S3 语义：key 就是全部，其余都是约定

### 一个对象由什么组成

| 组成 | 是什么 | 约束与量级 |
| --- | --- | --- |
| **bucket** | 命名空间 + 区域 + 策略的容器 | 桶级策略、版本控制、生命周期都挂在它身上 |
| **key** | **1–1,024 字节**的 UTF-8 字符串，对象的唯一身份；可以包含 `/`，但 `/` 没有任何特殊含义 | 长度上限 1,024 字节；`/` 只是给人看的约定（下面「目录幻觉」） |
| **value** | 不可变字节流 | 单次 PUT ≤ 5 GiB 量级，单对象 ≤ 5 TiB（§42.5） |
| **user metadata** | 你自己写的 key-value（HTTP 头） | 2 KB 量级，以厂商文档为准；**改它也要重写整个对象** |
| **system metadata** | 大小 / 最后修改时间 / ETag / 存储类 / 版本 id / 校验和 | ETag ≠ 内容 MD5（见「ETag 不是 MD5」表） |

**这就是全部。** 没有 inode、没有目录项、没有"文件句柄"、没有"打开"这个概念。你以为的"目录"是两个约定叠出来的幻觉：① key 里用了 `/` 做分隔符；② LIST 时传 `delimiter=/`，服务端把公共前缀折叠成 `CommonPrefixes` 返回。**没有那一步 LIST，目录不存在。**

### 常用操作 → 物理动作 → 你付什么

这张表是本篇用得最多的一张，几乎所有"对象存储上的奇怪现象"都能在里面找到一行：

| 你写的操作 | 物理上发生了什么 | 请求数（N = 涉及对象数） | 你付什么 | 坑 |
| --- | --- | --- | --- | --- |
| `PUT`（新建/覆盖） | 整对象上传；同名 key **直接覆盖**，旧版本立刻不可见（开了版本控制则变成新版本） | 1（< 5 GiB）；大对象见 §42.5 | PUT 类请求费 + 存储费 | 覆盖不是"更新"，是"换一个对象"；并发写 = 后写全胜，无冲突检测 |
| `GET` | 整对象（或 `Range` 指定的一段）流出 | 1 / 每段 1 | GET 类请求费 + **出网费** | 出网费常常是账单主项（§42.8） |
| `GET` + `Range: bytes=a-b` | 只读一段，服务端不支持"随机写"，但支持**随机读** | 1 / 每段 1 | 同上 | 并行下载 = 并行请求，**请求数乘份数**；`416` 表示范围越界 |
| `DELETE` | 删一个对象；**没有"删目录"** | 1 / 每对象 1 | 通常免费（以报价为准） | 删"目录" = LIST 全量 + 逐对象 DELETE，且中途失败就是半个目录 |
| `HEAD` | 只取元数据 | 1 | GET 类 | `ls -l` 的真相：每个文件一次 HEAD，或一次 LIST 批量拿 |
| `LIST`（`ListObjectsV2`） | 按 key 字典序返回**最多 1,000 个**，用 `ContinuationToken` 翻页 | `ceil(N/1000)` | **按 PUT 类计费（约为 GET 的 12.5 倍量级）× 页数** | LIST 是对象存储里最容易被低估的成本与限流源；百万对象 = 1,000 页 |
| `COPY`（同桶复制） | 服务端读源 + 写目标；**单次 COPY 上限 5 GiB** | 1（≤5 GiB），更大要 multipart copy | PUT 类 | 这就是"rename"的一半（另一半是 DELETE） |
| `rename` / `mv` | **不存在**。语义上是 copy + delete | 2N（+ LIST 分页） | 2N 次请求 | 非原子、可被切断、不可回滚（事故二） |
| 追加/`>>` | **不存在**。只能读旧的 + 拼新的 + PUT 新的 | 1 GET + 1 PUT（整对象） | 双份流量 | 日志绝对不能"追加"到对象上方（§42.7） |
| 加锁 / `fsync` / `link` | **不存在** | — | — | 需要锁服务（`→ comp/46`）；持久性靠 PUT 返回 200 即成立 |

> **一条纪律**：只要你的伪代码里出现「遍历目录、对每个文件做某事」，就要在评审里把它当成 **N 次请求 × 2（读+写）+ 不可中断性** 来算账，而不是当成"一条 `mv` 命令"。

### ETag 不是 MD5（这一条错得最贵）

| 场景 | ETag 是什么 | 能不能当内容校验 |
| --- | --- | --- |
| 单次 PUT、无加密或 SSE-S3 | 通常是内容的 MD5（**强 ETag**） | 可以，但这只是厂商惯例，**不是协议承诺** |
| 单次 PUT + SSE-KMS / SSE-C | **不是**内容 MD5（加密后摘要） | ❌ |
| multipart 上传 | `MD5(拼接所有分片的 MD5) + "-" + 分片数`，形如 `d41d8…-1600` | ❌（它校验的是"分片集合"，不是"完整文件字节"） |
| 分片被并发重传、`CompleteMultipartUpload` 时顺序变化 | ETag 随之变化 | ❌ |

**正确姿势**：内容和完整性用**校验和**（`x-amz-checksum-crc32c` / `sha256` 一类，以目标版本文档为准）或你自己在元数据里存 `sha256`；ETag 只用来做"对象是否被换过"的**弱信号**（比如 `If-None-Match` 做条件请求、CDN/缓存校验）。**用 ETag 判等去做幂等键、去重、断点续传校验，会在加密或多分片那天静默失效。**

### 强一致：边界要对齐厂商文档，不要对齐"经验"

- **AWS S3 自 2020 年 12 月起**对新建/覆盖/删除对象以及 LIST 提供**强一致**读（"写成功返回后，任何后续读都能看到新值"）。这意味着"写完立刻 LIST 得到它"在 S3 上是成立的。
- **其它兼容实现不一定**：部分自建/兼容网关对 LIST 与覆盖写是**最终一致**的（秒级窗口）。**"以目标厂商文档为准"是唯一安全写法**——因为你的事故会发生在你换存储后端的那一天。
- **跨对象永远没有一致性**：写完 A 再写 B，没有"两个都可见或都不可见"的语义。要原子，只能靠**指针切换**（一块元数据对象的 PUT 是原子的，这正是 [35 Iceberg / 表格式](35-iceberg-table-format.md) §35.3 的全部秘密）。
- **并发写同一 key**：没有 CAS、没有锁（`If-Match`/条件写只在部分实现里有，且以文档为准），就是 last-writer-wins。所以"多实例同时写同一个 key"必然丢更新。

### presigned URL：把凭证换成"带过期时间的门票"

| 要素 | 事实 | 工程含义 |
| --- | --- | --- |
| 它是什么 | 用签名把「bucket/key/操作/过期时间」编码进 URL，持有者可无凭证访问 | 客户端直传的正确姿势；不必让文件流过你的服务（省带宽、省内存） |
| 过期上限 | SigV4 在长期凭证下最长 **7 天**；用 STS 临时凭证时**不能超过凭证本身的寿命**（以厂商文档为准） | 生成时**永远取小于业务超时窗口**的值；上传大文件要按"分片粒度"签发 |
| 它能约束什么 | 通常可约束 key 前缀、大小范围、内容类型（取决于实现） | 用**前缀 + 长度上限**限制滥用；不要在 URL 里放"任意 key"的签名 |
| 它的风险 | 一旦泄露，在有效期内等同于该操作权限；无法吊销（只能删凭证/改策略） | URL 不能进日志、不能进前端 localStorage；短有效期 + 服务端二次校验元数据 |

### 存储类：便宜的存储类都有"最低消费"和"取回费"

| 存储类 | 取回延迟（量级） | 最低存储时长 | 提前删除 | 典型用法 |
| --- | --- | --- | --- | --- |
| Standard | ms | 无 | 无 | 热数据、被频繁读的湖表 |
| Intelligent-Tiering | ms–小时（自动分层） | 无 | 无（但有监控费） | 访问模式不可预测 |
| Standard-IA / One Zone-IA | ms | **30 天** | 按剩余天数补费 | 每月读几次的备份 |
| Glacier Instant Retrieval | ms | **90 天** | 按剩余天数补费 | 季度读一次但要即时可用 |
| Glacier Flexible Retrieval | 分钟–小时 | **90 天** | 按剩余天数补费 | 合规归档 |
| Glacier Deep Archive | 小时级 | **180 天** | 按剩余天数补费 | 七年留存、几乎不读 |

> **最低存储时长的实际含义**：存进去 20 天就删/搬走，你仍然按 30 天（或 90/180 天）付费。所以"归档层"的成本模型不是"单价比"，而是 **单价 × max(实际天数, 最低天数) + 取回费**——这也是事故二账单里那笔 1,050 元提前删除费的来源。**具体天数与取回费以目标厂商定价页为准。**

## 42.4 请求模型与限流：无限容量 ≠ 无限请求速率

### 墙在哪：按前缀的分区速率

对象存储把 key 空间切成**分区**（partition），每个分区能承受的请求速率是**量级固定**的。AWS 文档给出的量级是：**每个"已分区前缀"约 3,500 次写入类请求/秒（PUT/COPY/POST/DELETE）与 5,500 次读取类请求/秒（GET/HEAD）**，并且服务端会随流量自动拆分分区——但**拆分需要时间，且不以你的意愿为转移**（`以目标厂商文档为准`，不同厂商、不同桶类型差距很大，S3 Express 一类的目录桶模型不一样）。

于是有三条推论：

1. **总速率够 ≠ 你的速率够**：全局 20,000 次/秒很安全，但如果这 20,000 次里有 12,000 次落在**同一个日期前缀**（事故一），那个前缀就撞墙了。
2. **key 的熵就是速率的上限**：`uploads/2026-02-26/{seq}` 这一天只有一个前缀；`uploads/2f6/2026-02-26/{seq}` 就有 4,096 个（3 位十六进制）。**打散前缀不是为了"均匀"，是为了让分区能并行**。
3. **DELETE 与 COPY 都在写入类额度里**：所以"归档/搬迁"这种批量 COPY 会与在线上传抢同一份额度（事故二一边搬一边写，就是互相拖慢）。

### 错误语义：哪些该重试、哪些重试就是自杀

| 响应 | 含义 | 该不该重试 | 怎么重试 |
| --- | --- | --- | --- |
| `503 SlowDown` | **限流**：你的请求速率超过该分区的可用额度 | ✅ 该重试，而且**必须退避 + 抖动** | 指数退避（base 100–500 ms，cap 数秒，全抖动），预算 3–5 次 |
| `500 InternalError` | 服务端内部错误，请求可能未生效 | ✅ 有限重试 | 同上；幂等 key 才安全 |
| `429`（部分兼容实现） | 限流（语义同 503） | ✅ | 同上，注意看清是哪一层（网关/存储）在限 |
| `RequestTimeout` / 连接重置 | 客户端或中间层超时 | ✅ | 大对象必须用 multipart 让单片可重传（§42.5），否则整对象重来 |
| `403 SignatureDoesNotMatch` / `AccessDenied` | 签名/策略问题 | ❌ **重试毫无意义** | 修凭证、修时钟偏移（SigV4 对时间敏感） |
| `404 NoSuchKey` | 对象不存在（或最终一致窗口内还看不到） | ⚠️ 只在已知最终一致的后端上短暂重试 | 别把它当成"限流"来重试 |
| `412 PreconditionFailed` | 条件写失败（`If-Match`/`If-None-Match`） | ❌ | 这是你想要的结果：说明有并发写，走业务冲突处理 |

> **一条判据**：**只有 5xx 与超时才值得重试，4xx 重试只是把错误变成更多的错误。** 而 5xx 的重试必须是"**指数退避 + 全抖动 + 有预算 + 幂等**"四件套——缺一件就是事故一。

### 重试放大的乘法链（这一幕在 `→ comp/50` 与 `→ eng/15` 里都会重演）

**带抖动的有限重试**，放大倍数是等比级数 `Σ p^k（k = 0..maxAttempts−1，p = 失败率）`：`p = 0.05`、重试 3 次 → **×1.053**（温和）；`p = 0.30`、重试 3 次 → **×1.43**（开始明显）。但真正的事故不是等比级数，而是**乘法套乘法**：

> `实际速率 ≈ 业务速率 × (1 + Σ p^k) × 无退避的并发尖峰 × 用户手动重试`
> `≈ 1,100 × 1.4 × 2.5 × 1.0 ≈ 3,900/秒` ← 事故一的实测值

**事故一的 3.5× 就是这么来的**：`1,100 ×（重试叠加 1.4）×（无退避造成的并发尖峰 2.5）≈ 3,900/秒`。而"把 worker 池从 200 扩到 500"直接把这个数字又推高 30%——**在限流场景下，扩容是最危险的处置动作之一**（与 [39 入口网关](39-gateway-and-load-balancing.md) §39.6 的"重试风暴"、`→ eng/18` 的熔断同源）。

### 一份能扛住限流的上传骨架

下面只为讲清四件事（幂等 key、退避 + 全抖动、预算、前缀打散），省略了错误分类与指标埋点——**生产里 503 与 4xx 必须分开打点**，否则你永远分不清"被限流"和"权限错了"。

```go
// 上传器核心：① 幂等 key ② 指数退避 + 全抖动 ③ 预算 ④ 单前缀打散
type Uploader struct {
	MaxAttempts int           // 总尝试次数预算（含首次）。3~5 是常见区间
	BaseDelay   time.Duration // 初始退避，100~500ms 量级
	MaxDelay    time.Duration // 退避上限，几秒量级
}

// key 设计：内容哈希天然幂等（同内容重传不会产生第二份），并让前缀熵足够大
func ObjectKey(tenantID string, body []byte) string {
	sum := sha256.Sum256(body)
	h := hex.EncodeToString(sum[:])           // 64 字符
	return fmt.Sprintf("up/%s/%s/%s/%s",       // up/2f6/a91/ => 4096 个一级前缀
		h[0:3], h[3:6], tenantID, h)           // 前缀打散 + 租户可读 + 内容定 key
}

func (u *Uploader) Put(ctx context.Context, key string, body []byte) (string, error) {
	var lastErr error
	for attempt := 0; attempt < u.MaxAttempts; attempt++ {
		if attempt > 0 {
			// 全抖动：sleep ∈ [0, backoff]，避免所有实例在同一毫秒醒来
			backoff := u.BaseDelay << uint(attempt-1)
			if backoff > u.MaxDelay { backoff = u.MaxDelay }
			jitter := time.Duration(rand.Int63n(int64(backoff) + 1))
			select {
			case <-time.After(jitter):
			case <-ctx.Done():
				return "", ctx.Err()
			}
		}
		etag, err := u.doPut(ctx, key, body)   // 内部用 SDK：SDK 自带重试要关掉或对齐，别叠两层
		if err == nil {
			return etag, nil                // ✅ 只信 "PUT 返回 200" 这一件事
		}
		if !isRetryable(err) {              // 4xx 一律不重试（403/404/412）
			return "", err
		}
		lastErr = err
	}
	return "", fmt.Errorf("give up after %d attempts: %w", u.MaxAttempts, lastErr)
}
```

**三个必须一起做的配套**：① **关掉或对齐 SDK 内建重试**（两套重试叠加等于 3×3 = 9 次）；② **客户端并发上限**按目标前缀的额度算（`并发 ≈ 目标 QPS × 单请求耗时`），不是"越大越快"；③ **把 503 打进指标**并按前缀聚合——否则你永远不知道是哪片 key 空间在撞墙。

### 吞吐上限：单连接是一条管子

单条 TCP 连接上的顺序 GET 有效吞吐通常是 **90–110 MB/s 量级**（受 RTT、窗口、服务端限速影响），要拿到 GiB/s 必须**并行多连接 + Range 分段**。这也解释了为什么"我把机器升级到 25 Gbps 网卡，下载还是 100 MB/s"——你没有并行。

| 手段 | 解决什么 | 代价 |
| --- | --- | --- |
| 多连接并发（客户端连接池） | 单连接吞吐上限 | 请求数不变，但并发请求也占额度；要限流 |
| Range 分段并行下载 | 单对象下载速度 | **每段一次 GET，请求费乘段数**；小对象反而更慢 |
| multipart 并行上传 | 单对象上传速度 | 请求数 = 分片数 + 2（§42.5） |
| Transfer Acceleration 一类加速 | 跨地域/跨洲长途链路 | 额外按 GB 计费；只对**远距离**有意义，同区反而更慢 |
| 同区部署（把计算放到存储旁边） | 从根本上消灭出网费与 RTT | 架构约束（不该为了省流量费把整个系统锁在一个区） |

## 42.5 multipart：大对象的代价是"请求数变成了分片数"

### 常量表（属于协议级常量，可以放心背）

| 常量 | 值 | 说明 |
| --- | --- | --- |
| 单次 PUT 最大对象 | **5 GiB** | 超过必须 multipart |
| 单片最小大小 | **5 MiB** | **最后一片除外**（可以小于 5 MiB，但只能是最后一片） |
| 单片最大大小 | **5 GiB** | 分片不是越大越好，也受请求超时约束 |
| 分片数上限 | **10,000** | 这条是"分片大小怎么定"的真正约束 |
| 单对象最大大小 | **5 TiB** | 由 `10,000 × 5 GiB` 封顶 |
| 服务端 COPY 上限 | **5 GiB**（单次） | 超过要 `UploadPartCopy` 分片复制 |
| 请求数 | `CreateMultipartUpload 1 + UploadPart ceil(size/part) + CompleteMultipartUpload 1` | **必须 +2**，还要算上失败重传 |

### 布局与 ETag 的真相

```text
一个 100 GB 的对象，用 64 MiB 分片上传：
  CreateMultipartUpload  → 1 次 PUT 类请求       （拿到 UploadId）
  UploadPart #1..#1600   → 1600 次 PUT 类请求    （可并发；每片可单独重传 ✅）
  CompleteMultipartUpload→ 1 次 POST             （提交分片清单，对象此刻才可见）
  ---------------------------------------------------------------
  合计 1,602 次请求  vs  "小对象一个 PUT"  = 请求数放大 1,602 倍

  对象可见性：Complete 之前，**这个对象根本不存在**（GET 返回 404）
             但已上传的分片**一直占存储并且计费** —— 它们不可见、不出现在 LIST 里
             它们只出现在 ListMultipartUploads / ListParts 里 ← 孤儿分片的唯一出口

  ETag：不是整个 100 GB 的 MD5，而是
        md5( concat( md5(part1), md5(part2), …, md5(part1600) ) ) + "-1600"
        ⇒ 你无法用它校验"文件内容是否等于本地文件"
```

### complete / abort：三条不可省的纪律

1. **`CompleteMultipartUpload` 才是"提交"，之前都是可丢弃的写入。** 所以"上传了 99% 然后进程被杀"的结果是**零影响**（对象不存在），而不是"半个文件"——这是 multipart 唯一一个比单次 PUT 更好的性质：**原子可见**。
2. **必须显式 `Abort`，或配生命周期规则自动清。** 分片一旦上传就**计费**（按存储费算），而且**不出现在 LIST 里**——所以"我们桶里明明只有 36 TB，账单却按 58 TB 收"这种故事，十次有八次是孤儿分片（§42.12 的巡检就是为它准备的）。
3. **单片失败只重传该片。** 这就是大对象必须 multipart 的第二个理由（第一个是 5 GiB 上限）：**单次 PUT 一个 100 GB 对象，任何一次网络抖动都让 100 GB 全部重来。**

### 分片大小怎么定：一条公式三档取

**一条公式三档取**：`part = max(5 MiB, ceil(size ÷ 10,000), 推荐档)`。三项各管一件事：`5 MiB` 是协议下限；`ceil(size ÷ 10,000)` 是"别撞 1 万片上限"的硬约束；推荐档按对象量级选——**64 MiB**（大对象、链路稳定）、**8–16 MiB**（小对象多、要高并发）、**128–256 MiB**（超大对象、追求少请求，但要确认单请求超时留够）。

| 对象大小 | 推荐分片 | 分片数 | 请求数 | 为什么 |
| --- | --- | --- | --- | --- |
| < 5 GiB | **不要 multipart** | — | 1 | 分片只会增加请求数，没有任何收益（除非要断点续传/并发） |
| 5–100 GiB | 8–16 MiB | 320–12,800 → 受 1 万上限约束 | 上界 1 万 | 单片重传成本低，并发度高 |
| 100 GiB–1 TiB | 64 MiB | 1,600–16,000 | ≤ 10,002 | 请求数与重传成本的平衡点 |
| 1 TiB 以上 | 128–512 MiB | ≤ 8,192 | ≤ 8,194 | 分片太细会撞 1 万上限；同时受单片上传超时约束 |

```python
# 分片规划器：给定对象大小与偏好，算出分片数、请求数与"分片太细"的风险
MiB, GiB, TiB = 1 << 20, 1 << 30, 1 << 40
MAX_PARTS, MIN_PART, MAX_PART, MAX_OBJECT = 10_000, 5 * MiB, 5 * GiB, 5 * TiB

def plan(size, prefer=64 * MiB):
    assert size <= MAX_OBJECT, f"超过单对象上限 {MAX_OBJECT/TiB:.0f} TiB（以厂商文档为准）"
    if size <= 5 * GiB:
        return dict(parts=1, part=size, reqs=1, note="单次 PUT 即可，别用 multipart")
    part = max(MIN_PART, -(-size // MAX_PARTS), prefer)   # 向上取整除法，保证不超 1 万片
    part = min(part, MAX_PART)
    n = -(-size // part)
    # 请求数 = 1(Create) + n(UploadPart) + 1(Complete)；失败重传另计
    return dict(parts=n, part=part, reqs=n + 2,
                note="ok" if n <= MAX_PARTS else "分片数越界，必须调大 part")

for size in (3 * GiB, 100 * GiB, 1 * TiB, 5 * TiB):
    p = plan(size)
    print(f"{size/GiB:>7.0f} GiB  分片 {p['part']/MiB:>5.0f} MiB × {p['parts']:>5d} 片  "
          f"→ 请求 {p['reqs']:>5d} 次  {p['note']}")
# 输出量级：3 GiB → 1 次请求；100 GiB → 1,602 次；5 TiB → 8,194 次（分片 512 MiB 档）
```

> **量级结论（非承诺值）**。假设：分片常量按 S3 协议量级（5 MiB / 5 GiB / 1 万片 / 5 TiB），不计重传。**结论**：multipart 把"一次上传"变成"一个分片数的循环"，**请求数与分片数成正比，而分片数由"对象大小 ÷ 分片大小"与"1 万片上限"两头夹住**——所以"分片大小"这个旋钮同时在改三件事：请求费（§42.8）、单片重传成本、以及并发度。

## 42.6 云盘：`吞吐 = IOPS × 块大小`，其余都是这句话的注脚

### 四种卷型模型的差别（不站队，只讲形态）

| 卷型族 | IOPS 怎么来 | 吞吐怎么来 | 突发（burst） | 形态上的性格 |
| --- | --- | --- | --- | --- |
| **容量比例型**（gp2 一类） | `3 IOPS × 容量 GB`，有上限（16,000 量级） | 与 IOPS 绑定（约 250 MB/s 上限量级） | 小卷有 credit，可短时突发到 3,000 IOPS 量级 | **便宜、无脑、但 IOPS 与容量绑死**：想加 IOPS 就得买容量 |
| **预配型**（gp3 一类） | 基线 3,000，**可独立预配到 16,000 量级** | 基线 125 MB/s，**可独立预配到 1,000 MB/s 量级** | 小卷有 burst 额度 | **IOPS 与吞吐解耦**：多数场景的最优起点（以厂商文档为准） |
| **预配型高端**（io1 一类） | `50 IOPS × 容量 GB`，可到 64,000 量级 | 与 IOPS 绑定 | 无 | 稳定高 IOPS，**按 IOPS 单独计费**，单价最贵的一档之一 |
| **高耐久预配**（io2 一类） | 更高比例、可到 10 万级甚至 25 万级（以文档为准） | 更高 | 无 | 面向"IOPS 与耐久性都要"的数据库主库 |
| **吞吐型 HDD**（st1/sc1） | 很低（几百量级） | 按容量给吞吐（MB/s 量级） | 有 credit | **只适合顺序大块**（日志、备份、冷数据）；随机读会惨不忍睹 |

**两个反直觉的点**：

1. **gp2 的"第一天很快、第三周变慢"不是玄学，是 burst credit 烧完了**：卷越小，可突发的倍数越大；一旦累计 IOPS 超过可兑换额度，性能回落到基线。**判断方法**：看 `BurstBalance` 一类指标（各厂商名字不同，以文档为准）是否单调下降到 0。
2. **gp3 的 IOPS 与吞吐是两个独立旋钮，谁先撞上限谁定义性能**：你预配 12,000 IOPS 但只给 125 MB/s，那么 16 KiB 随机读只能跑到 `125 MB ÷ 16 KiB ≈ 8,000 IOPS`——**你买的那 4,000 IOPS 存在但用不上**。

### 那条乘法：`吞吐 = IOPS × 块大小`

| 场景 | IOPS | 块大小 | 吞吐 | 谁先撞墙 |
| --- | --- | --- | --- | --- |
| OLTP 随机读（InnoDB 页） | 3,072（gp2 1 TiB 基线） | 16 KiB | **48 MB/s** | IOPS |
| 同上，但卷配到 12,000 IOPS / 500 MB/s | 12,000 | 16 KiB | 187 MB/s | **IOPS**（12,000 × 16 KiB = 187 MB/s，离 500 MB/s 的吞吐上限还远，那 4,000 IOPS 有富余但吞吐没用满） |
| 同上，块大小掉到 4 KiB（小行、无索引覆盖） | 12,000 | 4 KiB | **47 MB/s** | IOPS（同样字节数要 4 倍 IO） |
| 顺序扫大表（预读 1 MiB） | 500 | 1 MiB | **500 MB/s** | 吞吐 |
| Kafka broker 顺序写 | 2,000 | 64 KiB | 125 MB/s | 吞吐（此时 IOPS 额度根本用不完） |

> **关键推论**：**同一个"慢"，可能是 IOPS 不够，也可能是吞吐不够，改法完全不同**。诊断第一步永远是看 `r/s`（IOPS）与 `MB/s`（吞吐）**哪个先到顶**——如果 `r/s` 稳定在配额上而 `MB/s` 远低于配额，就是 IOPS 型瓶颈（小随机 IO）；反之是吞吐型（大顺序 IO）。

### 队列深度与饱和延迟：为什么 P99 会跳十倍

```text
  Little's law：延迟 × IOPS = 在途 IO 数（L = λ × W）
    ⇒ 饱和时：延迟 ≈ 在途 IO 数 ÷ 有效 IOPS
    例：并发 IO 深度 64、有效 IOPS 3,072 ⇒ 饱和延迟 ≈ 64 ÷ 3,072 ≈ 20.8 ms
        欠载时（ρ≈0.5）延迟 ≈ 设备服务时间 ≈ 0.3–2 ms
        ⇒ 同一个卷，P99 从 2 ms 跳到 21 ms，只需要"利用率越过 1"

   延迟
    │                                          ╭──── ρ>1：队列不收敛，延迟随时间线性上涨
    │                                    ╭─────╯
    │                            ╭───────╯        ← 拐点在 ρ≈0.7
    │                    ╭───────╯
    │        ╭───────────╯
    │────────╯
    └─────────────────────────────────────────────── 到达率 / 供给 IOPS（ρ）
         0.2      0.5      0.7      0.9   1.0

   ρ < 0.7：延迟 ≈ 服务时间（很稳）      ← 容量规划的目标区间
   ρ 0.7~1：延迟按 1/(1-ρ) 抬升（3~10 倍）
   ρ > 1  ：队列永不排空 → 延迟线性上涨 + 长尾爆炸 + 写饥饿 ← 事故三
```

**这就是"配额打满导致 P99 翻十倍"的全部数学**：你没有变慢，你只是**在一个已经饱和的队列里排队**。而修法只有两条：**降低到达率**（索引、缓存、批量、减少每请求 IO 次数）或**提高供给**（换卷型/加预配/拆库）。

### 三条云盘的硬边界

1. **不能跨机共享写。** 块设备是单机独占；挂到两台机器上写等于两个操作系统各写一半 → 文件系统元数据损坏。需要共享必须换**共享文件系统/集群卷型**（且它自带锁与配额模型，不要假设"和本地盘一样快"）。
2. **性能还受实例侧上限约束。** 卷配了 64,000 IOPS，但实例类型的 EBS 带宽/IOPS 上限（机型相关，**以实例类型文档为准**）可能只有其一半；这时候加预配是白花钱。**供给 = min(卷配额, 实例上限)。**
3. **首次读快照卷是"懒加载"的**：从快照创建的新卷，第一遍读块要从未就绪的后端拉取（`initialize` 一类的预热动作，以厂商文档为准），所以"新建卷跑压测第一分钟很慢"不是盘有问题，是块还没搬上来。

## 42.7 访问模式：为什么数据库不能跑在对象存储上，而日志与湖表可以

### 四种基本访问模式，各有各的墙

| 访问模式 | 对象存储 | 云盘 | 该用什么 |
| --- | --- | --- | --- |
| **顺序写、一次写多次读**（备份、湖表文件、图片） | ✅ 天生合适 | ✅ 也合适（吞吐型） | 对象存储（便宜 + 无限容量） |
| **顺序读、大块**（全表扫、恢复、下架） | ✅ 合适（并行 Range） | ✅ 合适 | 对象存储（计算侧就近读，注意出网费） |
| **随机读、小 IO**（点查、索引查） | ⚠️ 每次 20–80 ms，且按请求计费 | ✅ 合适（16 KiB 页） | 缓存 / KV / 数据库 |
| **随机覆盖写、原地更新**（数据页、目录项、B+ 树） | ❌ **根本做不到**（整对象替换） | ✅ 合适 | 数据库 + 云盘/本地盘 |
| **追加**（日志尾写、WAL） | ❌ 没有 append（只能读改写整对象） | ✅ 合适 | 本地盘/云盘（[28 Kafka 的日志](28-kafka-log-segments.md) §28.4） |
| **mmap 共享**（多进程映射同一文件） | ❌ 无 mmap；FUSE 上语义不可靠 | ✅ 单机可用，跨机不行 | 云盘 + 单机；跨机要文件服务 |

### POSIX 的每个动词，在对象存储上都变成一个请求

| POSIX 动作 | FUSE/对象存储上真实发生什么 | 请求数 | 谁在哭 |
| --- | --- | --- | --- |
| `open` / `close` | 基本免费（本地状态） | 0 | — |
| `read(fd, 4 KiB)` | 若未缓存：一次 Range GET（或整对象 GET） | 1 | **请求费与 RTT**：每次 20–80 ms |
| `write(fd, 4 KiB)` | 落本地缓存，`flush`/`close` 时**整对象重传** | 1（整对象） | **写放大 = 对象大小 ÷ 4 KiB** |
| `append` | 读出全对象 + 拼接 + PUT 新对象 | 1 GET + 1 PUT | 日志类负载直接死亡 |
| `rename` | copy + delete（目录则是 N 份） | 2N | 事故二；且不原子 |
| `fsync` | 一次 PUT（或等待已发起的 PUT 返回） | 1 | 每次提交一次 RTT |
| `ls` / `readdir` | `LIST` 1,000 条一页 | `ceil(N/1000)` | **目录越大越慢，且按 PUT 类计费** |
| `stat` / `getattr` | 每个文件一次 HEAD（缓存失效时） | N | `ls -l` 的 N 次往返 |
| `link` / `flock` / `O_EXCL` | 没有对等语义 | — | 需要外部锁服务（`→ comp/46`） |

> **一句话**：**FUSE 把对象存储"翻译"成 POSIX，但翻译不了语义**——`mv` 变成了循环、`>>` 变成了重传、`ls` 变成了分页、锁变成了"没有"。所以在挂载点上跑任何"依赖 rename 原子性 / 依赖 append / 依赖 fsync 顺序"的东西（SQLite、MySQL、Git 仓库、日志采集的正在写的文件），都是在**拿正确性换方便**。

### 为什么数据库绝对不能直接跑对象存储（一笔算术）

InnoDB 的页是 16 KiB，一个 1 GiB 的表空间是 **65,536 个页**。数据库的日常动作是"随机挑一页、改几个字节、刷回去"：

```
随机写放大 = 对象大小 ÷ 页大小 = 1 GiB ÷ 16 KiB = 65,536×
假设写入 200 页/秒（一个小库很普通的热度）：
  在云盘/本地盘上：200 × 16 KiB = 3.2 MB/s 的物理写
  在对象存储上  ：200 × 1 GiB = 200 GiB/s  ← 不存在这种可能
再加上每次 IO 的延迟：本地 100 μs 量级 vs 对象存储首字节 20–80 ms 量级（约 300–800×）
```

**四条不可绕过的语义缺口**（每一条都足以否决）：

1. **无原地改**：页级改写 = 整对象重传（上面那笔 65,536×）。
2. **无"两次独立落盘的顺序"**：WAL → 数据页这套崩溃恢复依赖 `fsync` 把**两份不同的东西**按顺序落到不同位置（[03 WAL、缓冲池与崩溃恢复](03-wal-bufferpool-crash-recovery.md)）；对象存储的"持久"是"这个对象 PUT 成功"，它无法表达"日志先持久、页后持久"这个顺序约束。
3. **无原子 rename**：数据库大量使用"写临时文件 → rename 生效"（WAL 段轮转、`atomic write` 配置文件、表空间 rename）。对象存储上 rename 是非原子的 copy+delete，**崩溃窗口里你会同时看到新旧两份或一份都没有**。
4. **无独占与锁**：一个文件被两个进程打开的语义（`flock`/`O_EXCL`）在对象存储上不存在，多实例 = 静默互相覆盖。

**能跑的例外只有一个**：把数据库的"存算分离"做成了**只读/不可变层**——例如把冷数据导出成 Parquet + 元数据指针（就是 [35 Iceberg / 表格式](35-iceberg-table-format.md) 干的事），或者把备份/归档放上去。**读多写零、对象大、请求数与业务事件解耦**，这三个条件同时满足才成立。

### 为什么日志与湖表可以（而 Kafka 必须用盘）

| 负载 | 能不能放对象存储 | 判据 |
| --- | --- | --- |
| **Kafka 的分区日志** | ❌ 不能（本地盘/云盘） | 它要**尾追加 + 立即可读 + page cache + sendfile**（[28 Kafka 的日志](28-kafka-log-segments.md) §28.4）。对象存储没有 append，每次追加都要重写整个段 |
| **Iceberg/Hudi 的数据文件** | ✅ 能 | 每个 Parquet 文件**一次写、永不改**；"改"由新文件表达；原子性由元数据指针提供（[35 Iceberg / 表格式](35-iceberg-table-format.md) §35.3） |
| 埋点/审计的原始事件（JSON/Avro 落湖） | ✅ 能 | 只追加 → 落到"每次一个新对象"，代价是**小文件 = 请求费**（§42.8） |
| 备份 / 快照 / 归档 | ✅ 能 | 一次写、极少读、可以用 IA/Glacier 降单价（注意最低存储时长） |
| 模型权重 / 镜像 / 静态附件 | ✅ 能 | 大对象 + CDN 前置，出网费由 CDN 吸收 |
| 正在写的本地日志文件（`app.log`） | ❌ 不能 | 追加语义 + fsync 语义（`→ comp/48` 的采集侧会处理"文件被轮转"） |
| SQLite / MySQL / Redis RDB 落盘 | ⚠️ 只能"最终产物" | 运行中的库文件绝对不行；导出的 dump 可以 |

**判据可以压成一句**：**"对象是否一次写成、之后只读"是唯一的分界线**。是 → 对象存储（便宜、无限、可并行）；否（要追加、要原地改、要 rename 生效） → 云盘或本地盘。

## 42.8 成本模型：四笔钱，其中两笔跟容量无关

### 四类费用（第 2、3 类才是失控的地方）

| 费用 | 按什么收 | 量级（**以目标环境报价为准**） | 什么时候炸 |
| --- | --- | --- | --- |
| **① 容量费** | GB·月，按存储类分档 | Standard ≈ $0.023/GB·月；IA ≈ $0.0125；Glacier IR ≈ $0.004；Deep Archive ≈ $0.001 | 版本控制 + 未过期快照 + **孤儿分片** |
| **② 请求费** | 每千次请求，分 PUT 类 / GET 类 | PUT/COPY/POST/**LIST** ≈ $0.005/千；GET/HEAD ≈ $0.0004/千（**LIST 与 PUT 同价，是 GET 的 12.5 倍**）；DELETE 通常免费 | **小文件**：请求数与对象数成正比，与字节数无关 |
| **③ 出网费** | 流出到公网的 GB | 前 100 GB/月免费，其后 ≈ $0.09/GB 起（阶梯下降）；跨区复制另行计费 | 把计算放到别的区/云；CDN 未前置；**经客户端中转的 copy（事故二）** |
| **④ 提前删除费** | 未达最低存储时长的剩余天数 | 按该存储类的容量单价折算 | 归档层做"短期搬家/清理"（IA 30 天、Glacier 90 天、Deep Archive 180 天） |
| 附加：检索费 / 加速费 / 监控费 | 按 GB 或按请求 | 归档层取回按 GB 收；加速按 GB 收；智能分层按对象数收监控费 | 归档层被"偶尔全量扫一遍"，检索费可能超过存储费 |

> 换算假设：下文人民币数字按 **1 USD ≈ 7.1 元** 折算。**汇率与单价都只是量级工具，报价请查目标厂商定价页。**

### 小文件 = 请求费主导（一张乘法链就够）

**一笔乘法链**：1 亿个 1 KB 对象（共 100 GB），每天全量读一遍——容量费 `100 GB × 0.16 元/GB·月 = 16 元/月`；写入 `1 亿 ÷ 1,000 × 0.035 元/千次 = 3,500 元`（一次性）；每次全量读 `1 亿 ÷ 1,000 × 0.003 元/千次 = 300 元`，每月 `300 × 30 = 9,000 元`；一次全量 LIST `10 万页 × 0.035 元/千次 = 3.5 元`（便宜，但会撞前缀限流）。于是 **请求费 ÷ 容量费 = 9,000 ÷ 16 ≈ 560 倍**。

> **量级结论（非承诺值）**。假设：① 对象均 1 KB、1 亿个；② 每天一次全量扫描；③ GET 0.003 元/千次、PUT 0.035 元/千次、容量 0.16 元/GB·月；④ 不计出网费（同区读）。**结论**：**当平均对象小于 1 MB 时，账单的主项是请求费而不是容量费**，而且它随"访问次数"线性增长，**与"你存了多少"无关**——这就是"小文件病"在对象存储上的账本形态（[35 Iceberg / 表格式](35-iceberg-table-format.md) §35.8 账二是同一件事的读侧版本）。

**反过来的判据**：把平均对象做大到 64 MB，同样 100 GB 只有 1,600 个对象，一次全量读只要 **0.005 元**——**430 倍的差**，全部来自"请求数 ÷ 对象数"。所以"合并小文件"这件事在对象存储上是**同时省请求费与省延迟**的，不只是"好看"。

### multipart 的请求数放大（§42.5 的账本面）

| 对象 | 单次 PUT 可行性 | multipart 请求数 | 请求费（PUT 类 0.035 元/千次） |
| --- | --- | --- | --- |
| 4 GiB | ✅ 1 次 | — | 0.000035 元 |
| 100 GiB | ❌ 必须分片（64 MiB × 1,600） | 1,602 | 0.056 元 |
| 1 TiB | ❌（256 MiB × 4,096） | 4,098 | 0.14 元 |
| 5 TiB | ❌（512 MiB × 10,000） | 10,002 | 0.35 元 |

**结论**：大对象的请求费**小到可忽略**（分钱级），所以**不要为了省请求费去调大分片**；调分片的理由永远是"重传成本 / 并发度 / 1 万片上限"。**真正被请求数杀掉的是"海量小文件"，不是"大对象分片"。**

### 出网费的三个陷阱

1. **同区免费、跨区收费、出公网最贵**：计算与存储不在同一区域时，每一次 GET 都在付 $0.02–0.09/GB 量级。**"把 Spark 集群放到另一个区去读这个桶"是最常见的账单事故**，而且延迟也一起变差。
2. **copy 经过客户端就是一次"下+上"**：服务端 copy（同桶内）只收请求费；而"下载到本地再上传"要付出网费（事故二那 22,700 元）。**能服务端 copy 就不要走客户端。**
3. **CDN 不是万能**：CDN 回源的流量仍然计费；但 CDN 命中率高时，回源量小、单价低。判据：**同一对象被不同用户读 > 数次，就该前置 CDN**。

### 云盘的账（与对象存储完全不同的一种贵）

| 项 | 计费维度 | 量级（以报价为准） | 备注 |
| --- | --- | --- | --- |
| 容量 | GB·月 | gp3 ≈ $0.08/GB·月；gp2 ≈ $0.10；io1/io2 更高 | **io 系列还要单独买 IOPS** |
| 预配 IOPS | 每 IOPS·月（超出基线的部分） | ≈ $0.005–0.065/IOPS·月（型号差 10 倍以上） | 12,000 IOPS 的差额就是几十美元/月 |
| 预配吞吐 | 每 MB/s·月（超出基线的部分） | ≈ $0.04/MB/s·月 量级 | 只对 gp3 一类可独立预配 |
| 快照 | GB·月（增量） | ≈ $0.05/GB·月 | 快照链越长，恢复越慢 |
| 隐性成本 | 停机扩卷、迁移、跨 AZ 复制 | — | **改卷型基本都要 detach/重建或在线迁移，是有窗口的操作** |

## 42.9 三本账：容量成本、请求成本、云盘 IOPS 反推盘型

三个算例，各带乘法链、假设清单与"量级结论"标签。账一用事故二的 36 TB / 4,200 万对象现场；账二用"1 亿个 1 KB 小对象"；账三用事故三的订单库反推盘型。

### 账一 · 容量成本 = 对象数 × 平均大小 × (1 + 版本/孤儿放大) × 单价 × 存储月数

| 步 | 项 | 推导 | 结果 |
| --- | --- | --- | --- |
| 1 | 逻辑容量 | 4,200 万 × 0.86 MB | 36.1 TB |
| 2 | 版本控制放大 | 开版本控制 + 30 天非当前版本保留，日均覆盖 3% | × 1.9 → **68.6 TB** |
| 3 | 孤儿分片放大 | 上传 3% 失败且未 Abort，分片字节按失败对象平均 60% 计 | +1.1 TB |
| 4 | 未过期旧快照 | 湖表 5 个快照 × 日均 400 GB 变更 | +2.0 TB |
| 5 | 计费容量合计 | 68.6 + 1.1 + 2.0 | **≈ 71.7 TB** |
| 6 | 账单（IA 存量） | 71,700 GB × $0.0125/GB·月 | **$896/月 ≈ 6,360 元/月** |
| 7 | 若误放 Standard | 71,700 × $0.023 | **$1,649/月 ≈ 11,700 元/月**（1.84×） |
| 8 | 若搬去 Glacier IR 但 90 天内又搬回 | 71,700 ×（90−30)/30 月 × $0.004 | **$574 提前删除费 ≈ 4,080 元** |
| 9 | 一次"归档搬家"的请求费 | （事故二）8,400 万次 × 0.035 元/千 | 2,940 元 + 出网 22,700 元 |

> **量级结论（非承诺值）**。假设清单：① 平均对象 0.86 MB、4,200 万个；② 版本控制放大取 1.9×（随覆盖频率与保留天数浮动，区间 1.2–3×）；③ 孤儿分片按失败率的字节占比估算；④ 单价按 IA $0.0125 / Standard $0.023 / Glacier IR $0.004，1 USD ≈ 7.1 元。**结论有两句**：① **容量账的真凶通常不是"数据多"，而是"同一个字节被存了几份"**（版本 + 孤儿 + 未过期快照，本例把 36 TB 变成 72 TB，**2 倍**）；② **搬家比存储贵**：一次搬家的请求费与出网费（25,640 元）≈ **4 个月**的 IA 存储费——所以"归档"应该用**生命周期规则**（服务端、按规则、可审计），不是用脚本搬。

### 账二 · 请求成本 = 对象数 × 每对象操作数 × 单价（与字节无关）

| 步 | 项 | 推导 | 结果 |
| --- | --- | --- | --- |
| 1 | 对象数 / 平均大小 | 1 亿个 / 1 KB | 100 GB |
| 2 | 首次写入请求 | 1 亿次 PUT | 3,500 元 |
| 3 | 每天全量读一次 | 1 亿次 GET | 300 元/天 |
| 4 | 每月读成本 | 300 × 30 | **9,000 元/月** |
| 5 | 每月容量成本 | 100 GB × 0.16 元 | **16 元/月** |
| 6 | 请求费 ÷ 容量费 | 9,000 ÷ 16 | **≈ 560×** |
| 7 | 若合并成 64 MB 大文件 | 1亿 → 1,600 个对象 | 一次全量读 0.005 元（**6 万倍**差） |
| 8 | 追加一次逐对象 HEAD 校验 | 1 亿次 HEAD ≈ GET 价 | +300 元/次全量校验 |
| 9 | 一次全量 LIST | 10 万页 × PUT 类价 | 3.5 元，但会撞前缀限流（§42.4） |
| 10 | 若对象更小（1 亿个 128 B） | 容量 12.8 GB（2 元/月），请求费不变 | 请求费 ÷ 容量费 ≈ **4,500×** |

> **量级结论（非承诺值）**。假设：① 每对象每轮一次 GET；② 单价 GET 0.003 元/千、PUT 0.035 元/千、容量 0.16 元/GB·月；③ 同区读，不计出网。**结论**：**请求成本是"对象数 × 访问次数"的函数，容量成本是"字节数 × 存储月数"的函数；两者的比值 ≈ (`每对象读写次数 × 请求单价`) ÷ (`对象大小 × 容量单价`)，所以对象越小、读得越勤，请求费越是主项**。这条式子也告诉你唯一的两个抓手：**把对象变大**（合并）或**减少访问次数**（缓存/批量/CDN）。

### 账三 · 云盘 IOPS 需求反推盘型：`需求 IOPS = QPS × 每请求 IO 次数`

| 步 | 项 | 推导 | 结果 |
| --- | --- | --- | --- |
| 1 | 业务量 | 订单列表 1,600 QPS，每请求 6 次 16 KiB 随机读（二级索引回表 + 聚簇索引） | 9,600 IO/秒 |
| 2 | 需求吞吐 | 9,600 × 16 KiB | **150 MB/s** |
| 3 | 现状供给（gp2 1 TiB） | 1,024 GB × 3 IOPS/GB | **3,072 IOPS / 约 250 MB/s 上限** |
| 4 | 利用率 ρ | 9,600 ÷ 3,072 | **3.1（> 1，必然排队）** |
| 5 | 饱和延迟量级 | 队列深度 64 ÷ 3,072 | **≈ 21 ms**（实测 P99 41 ms，含写饥饿） |
| 6 | 反推盘型（留 2–3 倍余量） | 需要 ≥ 20,000 IOPS 才舒服 → 单卷 gp3 上限 16,000 量级 | gp3 + 16,000 IOPS 或 io2 |
| 7 | 折中方案（事故三选它） | 12,000 IOPS + 500 MB/s，ρ = 0.8 | 延迟 ≈ 64 ÷ 12,000 ≈ **5.3 ms** |
| 8 | 月成本 | gp2 1 TiB ≈ $102 → gp3（$81.9 + IOPS 9,000×$0.005=$45 + 吞吐 375×$0.04=$15） | **≈ $142（+$40/月）** |
| 9 | 另一条路的成本 | 拆库 + 2 个只读实例分摊到 6,000 IOPS/库 | 多一份实例成本（数百美元/月）且**不解决"每请求 6 次 IO"** |
| 10 | 最便宜的一条 | 把每请求 IO 从 6 次降到 2 次（覆盖索引/去掉回表/加缓存） | 需求 3,200 IOPS，**现有卷就够，0 元** |

> **量级结论（非承诺值）**。假设：① 随机读块 16 KiB（InnoDB 页）；② 卷的有效 IOPS 等于预配值（不含实例侧上限，实际可能更低）；③ 饱和延迟用 `在途 IO 深度 ÷ IOPS` 近似（Little's law 的稳态近似，实际受队列调度影响）；④ 单价按 gp2 $0.10/GB·月、gp3 $0.08 + $0.005/IOPS + $0.04/(MB/s)。**结论三句**：① **云盘选型是纯算术**，`需求 IOPS`、`需求吞吐`、`供给`三个数一摆就出来了，算不出来只是没查配额；② **先改"每请求 IO 次数"，再改盘型**——第 10 步是 0 元方案，第 7 步是 284 元/月方案，第 9 步是最贵的；③ **供给 = min(卷配额, 实例带宽上限)**，只调一个可能白付钱。

### 三本账压成一张表

| 账 | 乘法链 | 谁在付 | 一次能还清吗 | 拐点信号 |
| --- | --- | --- | --- | --- |
| **容量账** | 对象数 × 平均大小 × (1+版本+孤儿+快照放大) × 单价 | 存储账单（月度复利） | ✅（expire/清理）但会再生 | 计费 GB ÷ 逻辑 GB > 1.5；孤儿分片 > 总量 5% |
| **请求账** | 对象数 × 每对象操作数 × 单价 + LIST 页数 × PUT 类价 | **每一个读它的作业** | ✅（合并小文件） | 平均对象 < 1 MB 且被反复读；请求费 > 容量费 |
| **IOPS 账** | 需求 = QPS × 每请求 IO 次数；供给 = min(卷配额, 实例上限) | 云盘账单 + 每一个请求的延迟 | ⚠️ 只能调（改成更少的 IO 或更多配额） | 卷 `QueueLength` 持续 > 4；`r/s` 钉在配额上；ρ = 需求/供给 > 0.7 |

```python
# 三本账压成可复算脚本（Python 3，无第三方依赖）。改任一假设直接重跑。
GB, TB, MiB = 1e9, 1e12, 1 << 20
USD = 7.1  # 折算用的汇率假设，仅作量级工具

def account_capacity(objects, avg_mb, ver_amp=1.9, orphan_tb=1.1, snap_tb=2.0,
                     price_gb_month=0.0125):
    """账一：容量 = 对象数 × 平均大小 × 放大 + 孤儿 + 快照"""
    logical_tb = objects * avg_mb * 1e6 / TB
    billed_tb = logical_tb * ver_amp + orphan_tb + snap_tb
    return logical_tb, billed_tb, billed_tb * 1e3 * price_gb_month

def account_requests(objects, reads_per_month, put=0.005, get=0.0004):
    """账二：请求费 = 对象数 × 操作数 × 单价（与字节无关）"""
    write_usd = objects / 1e3 * put
    read_usd = objects / 1e3 * get * reads_per_month
    return write_usd, read_usd

def account_iops(qps, io_per_req, block_kib=16, capacity_gb=1024, iops_per_gb=3.0,
                 queue_depth=64):
    """账三：需求 IOPS / 吞吐 vs 供给，饱和延迟 ≈ 队列深度 ÷ IOPS"""
    need_iops = qps * io_per_req
    need_mbps = need_iops * block_kib / 1024
    supply = capacity_gb * iops_per_gb
    rho = need_iops / supply
    lat_ms = queue_depth / supply * 1000
    return need_iops, need_mbps, supply, rho, lat_ms

l, b, usd = account_capacity(42_000_000, 0.86)
print(f"账一 逻辑 {l:.1f} TB → 计费 {b:.1f} TB（放大 {b/l:.2f}×）≈ ${usd:.0f}/月 ≈ {usd*USD:.0f} 元/月")
w, r = account_requests(100_000_000, reads_per_month=30)
print(f"账二 写 ${w:.0f} 一次性；读 ${r:.0f}/月  ⇒ 请求费是容量费(1.6 美元)的 {r/1.6:.0f} 倍")
n_iops, n_mbps, sup, rho, lat = account_iops(1600, 6)
print(f"账三 需求 {n_iops:.0f} IOPS / {n_mbps:.0f} MB/s；供给 {sup:.0f}；ρ={rho:.1f}；饱和延迟≈{lat:.1f} ms")
```

## 42.10 架构边界：不能当数据库、不能原子 rename、不能低延迟随机写

### 能做什么 / 不能做什么 / 靠什么绕过

| 你想做的事 | 对象存储能做吗 | 为什么（指到物理形态） | 靠什么绕过 |
| --- | --- | --- | --- |
| 存海量不可变文件（图片、备份、Parquet） | ✅ **强项** | 一个 key 一次 PUT，容量近无限 | 无 |
| 毫秒级点查一行数据 | ❌ | 每次 GET 一次 TLS + 首字节 20–80 ms，且无索引 | 缓存（`→ comp/12`）/ KV / 数据库 |
| 原子 rename / 原子"移动目录" | ❌ **根本不存在** | rename = copy + delete × N，无事务 | **改指针**（表格式 metadata、分区索引）、生命周期规则、服务端批处理 |
| 追加到文件尾部 | ❌ | 对象不可变，只能读改写整对象 | 换云盘/本地盘；或"一个事件一个对象"再合并 |
| 多实例并发写同一 key | ❌（静默丢更新） | last-writer-wins，无条件写/锁 | 每实例写自己的 key（key 里带分片/实例 id），再指针汇总 |
| 事务性"写 A 和 B 要么都成" | ❌ | 跨对象无事务 | 两阶段 + 幂等 + 指针提交（`→ comp/43`、`→ comp/45`） |
| 低延迟随机小写（数据库页） | ❌ | 整对象替换，写放大 = 对象大小 ÷ 页大小 | 数据库 + 云盘/本地盘 |
| 大规模并行读（分析） | ✅ **强项** | Range GET + 多连接 + 多对象并行 | 注意请求费与出网费 |
| 跨区域容灾 | ⚠️ 视配置 | 跨区复制是"按 GB 计费的异步复制" | 版本控制 + 复制规则（并接受它是最终一致） |
| **云盘**：单机高性能随机 IO | ✅ 强项 | 块级随机读写，微秒–百微秒级 | 受卷配额与实例上限约束 |
| **云盘**：跨机共享同一块卷 | ❌ | 块设备单机独占，多写 = 元数据损坏 | 共享文件系统/集群卷型/对象存储 |
| **云盘**：单卷横向扩 IOPS | ❌（有硬顶） | 卷型上限（16,000–25 万量级，以文档为准） | 拆库分片 + 多卷条带（条带要自己做，别指望自动） |

### 选型表：什么负载放哪儿

| 你的处境 | 选什么 | 判据（可量化） |
| --- | --- | --- |
| 平均对象 > 8 MB、一次写多次读、被多个引擎共享 | **对象存储** | 请求费 ÷ 容量费 < 0.2（§42.9 账二） |
| 平均对象 < 1 MB 且每天被扫一遍 | 对象存储 + **先合并**；或换 KV/数据库 | 请求费 ÷ 容量费 > 1 |
| 需要 < 10 ms 的点查/随机写 | 数据库 + 云盘（或本地 NVMe） | P99 要求 < 10 ms |
| 需要 rename/append/文件锁/mmap | 文件系统 + 云盘 | 出现 `rename`/`>>`/`flock` 任意一项 |
| 单卷 IOPS 需求 > 16,000 量级 | 拆库；或 io2 高端卷；或本地 NVMe + 副本 | 需求 IOPS ÷ 单卷上限 > 0.8 |
| 顺序吞吐型（日志、备份、导出） | 吞吐型卷（st1/sc1 一类）或对象存储 | 块大小 ≥ 64 KiB、IOPS 需求低 |
| 冷数据留存（合规 7 年） | 对象存储归档层 | 年读取次数 < 1，且能接受 30/90/180 天最低存储时长 |
| 客户端直传大文件（图片/视频/附件） | **presigned URL + multipart** | 文件 > 100 MB，且不想让流量过你的服务 |
| 跨区/跨云共享数据 | 对象存储 + 复制规则；**计算放到同区** | 出网费 > 容量费即需重新设计 |

### 解剖卡八问里最容易写错的两格

| 八问 | 本篇的答案 |
| --- | --- |
| **⑤ 扩展维度** | 对象存储：**分片 ✅ + 批处理摊薄 ✅**——"分片"是**把 key 空间打散到更多前缀**（提高可并发请求速率），"摊薄"是**把对象做大**（让请求数不随业务事件数线性增长）。**副本 ✗**（厂商内部多副本/纠删码，你看不见也管不了）、**垂直切 ✗**（没有"更大的对象存储"）。云盘：**只有垂直切**（换卷型、加预配、拆库分片），**单卷不可横向扩**；要横向只能靠"上层分片"（分库/分区/冷热分层）。 |
| **⑥ 系统级失效** | **只有四类**：① **请求速率撞墙 → 全局 503 雪崩**（含重试放大，事故一）；② **语义缺失 → 静默错数**（rename 非原子导致的半个目录、最终一致 LIST、用 ETag 当内容校验）；③ **成本失控**（小文件请求费、出网费、孤儿分片、提前删除费，§42.8）；④ **云盘配额打满 → 队列堆积 → P99 十倍**（事故三）。使用级错误（key 设计不好、没设生命周期、没开校验和）归 §42.11，两节不互相稀释。 |

## 42.11 踩坑清单（现象 → 根因 → 定位 → 修复 → 防复发）

| 现象 | 根因（指到物理形态） | 怎么定位 | 怎么修 | 怎么防复发 |
| --- | --- | --- | --- | --- |
| 上传 503 比例飙升，扩容后更糟 | 同一前缀写入速率越过分区额度；无抖动立即重试在放大流量 | 按 key 前缀聚合 5xx 与请求速率；看 SDK 重试次数与业务自建重试是否叠加 | 前缀打散 + 指数退避 + 全抖动 + 重试预算；**先降并发再谈扩容** | key 模板里强制带哈希分量；重试封装只留一处（关掉 SDK 内建那层） |

| `mv`/"归档搬家"跑了十几个小时，期间报表缺数 | 对象存储无 rename，move = N 次 copy + N 次 delete，**不原子** | 看搬迁脚本日志的完成百分比与下游读到的时间窗；查是否有"两处各一份" | 改指针/改分区索引；必要搬迁用服务端批处理 + 双写过渡 | 禁止在挂载点做 `mv`；"归档"定义为"新写入换前缀 + 旧前缀降存储类" |

| 下载只有 100 MB/s，网卡却是 25 Gbps | 单连接 TCP 吞吐上限 | `iperf`-类对比；看并发连接数 | 并行连接 + Range 分段 + multipart | 客户端封装默认打开并发；把"单流吞吐"写进文档 |
| 数据库 P99 突然十倍，CPU 不高 | 云盘 IOPS/吞吐配额打满 → 队列堆积（ρ > 1） | `iostat` 的 `r/s` 是否钉在配额；卷 `QueueLength`；`await` | 改卷型/加预配；或先把每请求 IO 次数降下来 | 把"需求 IOPS ÷ 供给"纳入容量评审；`QueueLength` 做告警 |
| 新买的卷"第三天变慢很稳定" | 容量比例型卷的 burst credit 烧完，回落到基线 | 看 burst 余额指标是否归零；对比基线与实测 IOPS | 换预配型卷或加大容量 | 容量比例型卷按"峰值需求"而不是"平均需求"选容量 |
| 换个专区部署 Spark，账单翻倍 | 计算与桶跨区 → 每次 GET 都按出网/跨区计费 | 账单按"数据传输"分项看；对比计算集群与桶的区域 | 计算就近部署；热数据前置 CDN/本地缓存 | 架构评审加一条：**桶与计算必须同区** |
| 用 ETag 做断点续传/去重，偶发校验失败 | multipart 的 ETag 是 `md5(md5s)-N`，加密场景也不是内容 MD5 | 看失败对象的 ETag 是否带 `-N` 后缀 | 改用 CRC32C/SHA256 校验和或自存哈希 | 代码评审禁止 `etag == md5` 这类断言 |

## 42.12 观测：六个数字定位 90% 的对象存储与云盘故障

| 指标 | 怎么读 | 版本 / 开关前提 | 拐点（越线就动手） | 它度量的是哪件物理事实 |
| --- | --- | --- | --- | --- |
| **5xx / `SlowDown` 比例（按前缀）** | 客户端埋点 + 服务端访问日志；按 key 前缀的前 2–3 段聚合 | 各 SDK 的错误码字段不同；**以目标版本 SDK 文档为准** | > 0.1% 持续 1 分钟，或 503 集中在单一前缀 | 是否撞了分区请求速率（§42.4） |
| **首字节时间 P99（TTFB）** | 客户端计时（DNS+TLS+首字节分开打） | 需在同一区测量，跨区值无意义 | > 200 ms（同区）或在无流量变化时突增 2× | 传输链路/服务端排队，而非"应用慢" |
| **重试率与放大倍数** | `重试请求数 ÷ 原始请求数` | 必须只有一层重试在生效（SDK 与业务层只能留一个） | > 1.3 即视为放大器在工作 | 事故一的核心指标 |
| **未完成 multipart 的分片数与字节** | `ListMultipartUploads` 巡检（定时任务落成指标） | 需要桶列举权限；分页 1,000 条/页 | 分片字节 > 总量 5%，或 24 小时未完成的分片 > 100 个 | 隐形计费（§42.5） |
| **卷 `QueueLength` / `await` / 有效 IOPS** | `iostat -x` 的 `aqu-sz`、`await`、`r/s`；云监控的卷队列深度 | 不同厂商指标名不同（如 `VolumeQueueLength`），**以文档为准** | 队列 > 4 或 `r/s` 钉在配额上、`await` > 10 ms | IOPS 配额是否被打满（§42.6） |
| **账单日环比（按请求数 / 出网 GB / 存储类）** | 云账单分项 + 按桶/前缀归集 | 标签（tag）要提前打，事后补不回来 | 任一维度日环比 > 30% 且业务量未涨 | 请求费、出网费、孤儿分片、提前删除费（§42.8） |

## 42.13 一页速记

| 记什么 | 具体结论 |
| --- | --- |
| 形态一句话 | 对象存储 = **key → 不可变整块字节**，一切操作是一次 HTTP 事务 + 一次计费；云盘 = **配额内的块设备**，性能是算术 |
| 三种语义分界 | 块给**地址**、文件给**名字/目录**、对象给**URL + 一次事务**；对象存储没有 rename/append/目录/锁 |
| rename 的真相 | = copy + delete × 对象数，**非原子**、可被切断；"移动"应该被实现成"改一次指针" |
| 目录的真相 | key 里的 `/` 无含义；LIST 传 `delimiter` 才折叠出目录；LIST 每页 1,000 条，**按 PUT 类计费** |
| ETag | 单次 PUT 通常 = MD5；**multipart = `md5(md5s)-N`**；加密后不是内容 MD5 → 校验用 CRC32C/SHA256 |
| 请求速率的墙 | 每个前缀约 3,500 写入 / 5,500 读取 次/秒量级（以厂商文档为准）；撞墙 = `503 SlowDown`，**不是故障是限流** |
| 重试纪律 | 指数退避 + **全抖动** + 预算 3–5 次 + 幂等 key；4xx 绝不重试；SDK 与业务层只留一层重试 |
| multipart 常量 | 单片 ≥ **5 MiB**（末片除外）、≤ 5 GiB；片数 ≤ **10,000**；单次 PUT ≤ 5 GiB；单对象 ≤ 5 TiB；请求数 = 片数 + 2 |
| 孤儿分片 | 不可见、不出现在 LIST、**照常计费**；必须 Abort 或配生命周期规则 |
| 云盘一行乘法 | **吞吐 = IOPS × 块大小**；`需求 IOPS = QPS × 每请求 IO 次数`；供给 = min(卷配额, 实例上限) |
| 云盘延迟模型 | 饱和延迟 ≈ 队列深度 ÷ IOPS；ρ > 1 时延迟随时间线性上涨（事故三的 10× 来源） |
| 成本四笔 | 容量 + 请求 + **出网** + 提前删除；小文件时请求费可 > 容量费 500 倍 |
| 判据 | 平均对象 < 1 MB 且被反复读 → 先合并再谈优化；跨区部署 → 先把计算搬到同区 |
| 首要指标 | 按前缀的 5xx、重试放大倍数、TTFB P99、未完成分片字节、卷队列深度、账单分项日环比 |
| 换零件信号 | 需要 rename/append/文件锁/mmap → 云盘或数据库；单卷 IOPS 需求 > 单卷上限 80% → 拆库或上本地 NVMe |

**如果只记五句：**

1. **对象存储卖的是 HTTP 语义，不是硬盘。** 每个 POSIX 动词在这里都变成一次计费请求，而"移动、追加、解锁、原子"这四个词没有对应实现——所以它在语义上比你以为的窄得多。
2. **容量无限，但请求速率有量级墙，而且墙按前缀算。** 3,500/5,500 量级不是"总配额"，是"每片 key 空间"；撞墙的表现是 `503 SlowDown`，处置是**降并发 + 打散前缀 + 退避重试**，不是扩容。
3. **5 GiB 以上必须分片，而分片把"一次上传"变成"一个 1,600 次的循环"。** 分片买到的是"单片可重传 + 提交前不可见"，代价是请求数与 ETag 语义；分片大小由 5 MiB 下限与 1 万片上限夹定。
4. **云盘的一切都是 `IOPS × 块大小` 与 `队列深度 ÷ IOPS`。** 想要低延迟，先问"需求 IOPS 是多少、供给是多少、ρ 是多少"，别去加 CPU、加连接数、加从库。
5. **对象存储的账单主项通常不是容量。** 请求费（小文件）、出网费（跨区/中转 copy）、孤儿分片与提前删除费，这四项加起来的失控速度远快于"数据涨了一倍"——而它们**全都可以在架构评审时用乘法链提前算出来**。

## 42.14 自检题（5 题）

**Q1.** 上传服务在晚高峰出现 12% 的 `503 SlowDown`，持久化层没报错，机器 CPU 30%。有人主张「先把上传 worker 从 200 扩到 500」。请说明为什么这是错的，并给出正确的处置顺序与验证指标。

<details><summary>答案</summary>

**错在三层**：

① **503 SlowDown 是限流，不是容量不足**。它表示"某片 key 空间上的请求速率超过了分区额度"（§42.4，写入类约 3,500 次/秒量级，**按前缀算**，不是按总账号算）。扩 worker 只会把同一个前缀上的请求速率推得更高——事故一里从 1,100/s 扩到 5,200/s，503 比例从 12% 升到 31%。

② **扩容同时放大了重试**。如果重试没有抖动，扩大并发 = 让更多实例在同一毫秒重试，正反馈更强。

③ **CPU 30% 已经说明不是本机瓶颈**：瓶颈在服务端的限流器（或客户端到存储的请求管道），本机只是"发得太多"。

**正确顺序**：
1. **先降并发**（worker 池或客户端令牌桶回到能维持 5xx < 0.1% 的水平）——急救；
2. **按 key 前缀切分指标**，确认 5xx 是否集中在单一前缀（`uploads/2026-02-26/` 这种日期前缀是元凶）；
3. **打散 key**：前缀里加哈希分量（3 位十六进制 → 4,096 个一级前缀）；
4. **重试改成指数退避 + 全抖动 + 预算**（并检查 SDK 内建重试是否与业务重试叠加，叠加就是 3×3=9 次）；
5. **幂等**：key 用内容哈希或客户端幂等键，否则重试产生重复对象（事故里 2,300 个重复）。

**验证指标**：按前缀的 5xx 比例、`重试请求数 ÷ 原始请求数`（应回落到 1.05 量级）、TTFB P99、每秒实际 PUT 数是否 ≤ 目标前缀额度。量级结论，非承诺值。

</details>

**Q2.** 有人说「我们的湖表数据都在对象存储上，`mv` 一下目录只是元数据操作，应该和本地盘一样快」。请用请求数和原子性两个维度反驳，并给出一个 36 TB / 4,200 万对象的具体量级。

<details><summary>答案</summary>

**请求数**：对象存储没有 rename。`mv dirA dirB` 对 4,200 万个对象 = **4,200 万次 COPY + 4,200 万次 DELETE = 8,400 万次请求**（§42.3 表）。按 128 并发、单请求 45 ms 算，理论 2,844 req/s → 8.4e7 ÷ 2,844 ≈ 8.2 小时；实际会撞前缀写入额度（§42.4），事故里跑成 **13 小时**。

**账单**：COPY 按 PUT 类计费 42M × 0.035 元/千 ≈ 1,470 元；**如果经客户端中转（FUSE 挂载的 `mv` 往往就是"下载再上传"），还要付 36,000 GB × 0.63 元/GB ≈ 22,700 元出网费**；IA 提前删除（存 20 天 vs 最低 30 天）≈ 1,050 元。合计 ≈ 2.5 万元，**其中 90% 是出网费**。

**原子性**：这 8,400 万次操作没有任何事务边界。13 小时里的每一个时刻，都有对象一半在新前缀、一半在旧前缀；下游按路径扫的作业读到的是**不完整的分区**，而且**不报错**（事故二里报表 GMV 少 31%，是运营发现的）。

**正确做法**：把"移动"实现成"改一次指针"——Iceberg 提交新 `metadata.json` 就同时完成了"换位置 + 原子生效"（[35 Iceberg / 表格式](35-iceberg-table-format.md) §35.3、§35.7）；真需要物理搬迁就用服务端批处理任务 + 双写过渡窗口。量级结论，非承诺值。

</details>

**Q3.** 一个 1 TiB gp2 卷承载 MySQL 主库，业务 QPS 从 400 涨到 1,600，每个查询 6 次 16 KiB 随机读。请算出需求 IOPS、供给 IOPS、利用率与饱和延迟，并给出三条改法（按性价比排序）与各自的月成本量级。

<details><summary>答案</summary>

**需求**：1,600 × 6 = **9,600 IOPS**，吞吐 = 9,600 × 16 KiB ≈ **150 MB/s**。
**供给**：gp2 1 TiB = 1,024 GB × 3 IOPS/GB = **3,072 IOPS**（吞吐上限约 250 MB/s 量级，本例不撞）。
**利用率**：ρ = 9,600 ÷ 3,072 = **3.1 > 1** → 队列永不排空。
**饱和延迟**：队列深度 64 ÷ 3,072 ≈ **21 ms**；欠载时约 1–2 ms → **P99 十倍**，与事故实测的 41 ms（含写饥饿）同量级。

**三条改法（性价比排序）**：

| 改法 | 效果 | 月成本 |
| --- | --- | --- |
| ① 把每请求 IO 从 6 降到 2（覆盖索引/去回表/加缓存） | 需求 3,200 IOPS，现有卷就够 | **0 元** |
| ② 换 gp3 + 12,000 IOPS + 500 MB/s | ρ = 0.8，延迟 ≈ 64 ÷ 12,000 ≈ 5.3 ms | ≈ +$40/月（约 284 元） |
| ③ 拆库 + 只读实例分摊 | 每库 6,000 IOPS | 多一份实例（数百美元/月），且**不解决"每请求 6 次 IO"** |

**必须强调的两点**：改卷型是有操作窗口的（在线改配受限于厂商能力，可能要迁移/重建）；而**加 CPU、加连接池、加从库都改不了这块盘的配额**——事故里把 8 vCPU 加到 16，P99 一点没变。量级结论，非承诺值。

</details>

**Q4.** 桶里明明只有 36 TB，账单按 58 TB 收；LIST 也能对得上。请给出至少三个根因与各自的定位方法，并说明为什么其中一个"永远不会出现在 LIST 里"。

<details><summary>答案</summary>

① **未完成/未 Abort 的 multipart 分片**（**这就是"永远不会出现在 LIST 里"的那个**）：分片一上传就计费，但只有 `CompleteMultipartUpload` 之后才成为对象；未完成的分片只出现在 `ListMultipartUploads`/`ListParts`。定位：定时巡检未完成上传（§42.12 脚本①），并按 `Initiated` 时间过滤。修：批量 Abort + 生命周期规则 `AbortIncompleteMultipartUpload`。

② **版本控制的历史版本**：`ListObjectsV2` 只列当前版本，历史版本要点 `ListObjectVersions`（或按非当前版本指标）。定位：对比当前版本总字节 vs 计费字节；查 `NoncurrentVersionExpiration` 是否配了。

③ **未过期的旧快照/旧文件（湖表）**：Iceberg 的旧快照引用的旧文件仍在盘上，LIST 能看见但"逻辑数据量"里没有它们。定位：`SELECT sum(file_size_in_bytes) FROM t.files` 与 `expire_snapshots` 配置（[35 Iceberg / 表格式](35-iceberg-table-format.md) §35.6）。

④ **提前删除费与最低存储时长**：不是"多存了字节"，而是"按最低时长补收"。定位：账单的"提前删除"分项；对比对象创建时间与存储类最低时长。

⑤ **副本/跨区复制的第二份**：跨区复制的目标桶是另一个桶，若按"源桶"看 LIST 自然对不上。定位：按桶+区域归集账单。

**通用判据**：**计费字节 > LIST 汇总字节 ≠ 存储系统算错了，而是"有两类字节你看不见"——未提交的分片与历史版本**。量级结论，非承诺值。

</details>

**Q5.** 团队要把「用户上传的附件（平均 800 KB，每天新增 200 万个，被 CDN 回源读 30 次/天）」从对象存储换成"自建 NAS + 云盘"，理由是"请求费太贵"。请给出你的判断口径，以及如果真的换，会在哪里付出更高的代价。

<details><summary>答案</summary>

**先算现有账**（按 §42.8 单价量级）：每天 200 万 × 0.8 MB = 1.6 TB/天新增（一年 584 TB 量级，需保留策略）。请求侧：写入 200 万次 PUT/天 = 2,000 千次 × 0.035 = 70 元/天；读取 200 万 × 30 次 = 6,000 万次 GET/天 = 60,000 千次 × 0.003 = 180 元/天；合计约 **250 元/天 ≈ 7,500 元/月**。容量费另算（按 Standard 0.16 元/GB·月，若保留 90 天约 144 TB ≈ 23,000 元/月）——**容量费远大于请求费**，所以"请求费太贵"这个理由本身站不住。

**换 NAS 的代价（按重要性）**：

① **失去 CDN 友好的前置能力 → 出网费转移但不消失**：自建带宽的 95 峰值口径往往比按量出网更贵，而且要为"30 次/天 × 200 万"的读流量准备带宽（约 6,000 万 × 0.8 MB = 48 TB/天回源，**这是不可能自建的**）。

② **容量规划变成你的责任**：584 TB/年增长 + 三副本 = 1.7 PB 物理盘，还要自己做故障替换、扩容、巡检。对象存储的 11 个 9 持久性是用钱买来的，自建要自己买单。

③ **可用性与语义退化**：NAS 是**单点/双机**，跨地域访问要回源；对象存储的多 AZ、跨区复制、版本控制、presigned URL 直传都失去，客户端直传要改成"过你的服务"（带宽 + 内存 + 入口 413/超时，见 [39 入口网关](39-gateway-and-load-balancing.md) §39.4）。

④ **运维成本显性化**：`ls` 慢、目录千万项、NFS 锁、跨机一致性——这些在对象存储上"不存在"（因为压根没有目录），到了 NAS 上全变成你要处理的问题。

**正确口径**：① 先确认请求费到底占账单多少（本例约 25%），**先做该做的三件事**：把 30 次/天的读**前置 CDN**（回源降到 1–2 次）、把小于 1 MB 的对象合并/去掉无谓 HEAD、开启生命周期降存储类；② 保留期从 90 天降到 30 天能砍掉 2/3 容量费；③ **只有当"数据完全可控/必须自建"是硬约束（合规、内网隔离）时**才考虑自建，并把"3 副本 + 跨 AZ + 带宽峰值"的账一起算进去。量级结论，非承诺值；具体选型归 [eng/35 存储选型](../eng/35-storage-model-selection.md)。

</details>
