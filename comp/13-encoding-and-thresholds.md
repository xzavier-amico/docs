## 13.1 引子：三起「内存没涨、延迟涨了」的故障

编码问题的共同特征是**没有一行代码变化、没有一个参数变化**，只是数据长到了某个尺寸，行为就换了形状。下面三起事故分别对应本篇三条主线：阈值跨线（§13.5–13.6）、真结构的遍历代价（§13.7）、配置漂移（§13.10）。

### 事故一：多加 10 个 field，内存多了 2.9 GB（2026-03-11）

`cache-profile` 存用户画像，一个用户一个 hash `up:{uid}`，约 40 万活跃用户，每 key 120 个 field（field 名平均 12 B，value 平均 40 B）。产品上线「兴趣标签 v2」，每个用户多 10 个 field，于是每个 key 从 120 个字段涨到 130 个。

`hash-max-listpack-entries` 是默认值 **128**。120 → 130 这一步，正好跨过阈值。

| 时间 | 事件 | 关键数字 |
| --- | --- | --- |
| 03-11 02:00 | 批量回填任务开始写 `up:{uid}` 的新增 10 个 field | 40 万 key 排队回填 |
| 02:04 | 前 3 万个 key 完成；`OBJECT ENCODING up:10086` 仍是 `listpack` | 内存 1.8 GB |
| 02:07 | 第 129 个 field 落地的那个瞬间，编码静默变成 `hashtable` | 单 key 内存 4.5 KB → 14.6 KB |
| 02:31 | 回填完成 28 万 key，其中 26.9 万个已跨线 | 内存 1.8 GB → 4.7 GB |
| 02:44 | `used_memory` 触及 `maxmemory` 60%，`evicted_keys` 开始以 4,000/s 增长 | 命中率 96% → 71% |
| 03:02 | 命中率 66%，回源把 MySQL 从 4,200 QPS 打到 19,000 | 接口 P99 40 ms → 1.1 s |
| 03:40 | 临时扩内存到 8 GB，并回滚标签 v2 | 命中率回到 95% |
| 复盘 | 42 分钟，接口超时 63 万次；根因是**一个 field 数越线**，不是流量涨 | — |

算一下那 2.9 GB 从哪来。listpack 模式下一个 field 对（12 B 名 + 40 B 值）占 `1 B prevlen + 1 B 编码 + 12 B + 1 B 编码 + 40 B ≈ 55 B`；hashtable 模式下每个 field 是 `dictEntry 24 B + key SDS 16 B（3 B 头 + 12 B + 1 B，装进 16 B 档）+ value robj 16 B + value SDS 48 B + 桶指针 8 B ≈ 112 B`。差 **57 B/field**，乘 `40 万 key × 130 field ≈ 5,200 万 field`，得 **2.96 GB**——和监控上看到的 2.9 GB 对得上。（journal 里那 130 个 field 全算，因为跨线是把**整张 hash** 重写一遍，不是只转新增的 10 个。）

> **性质：量级结论。** 假设 value 是普通字符串、jemalloc 按 8/16/32/48/64/80/96/112/128 档对齐、无 TTL（带 TTL 每 key 再加一个 `dictEntry 24 B + 桶 8 B`）、字段名长度分布均匀。把 value 换成整数（走共享整数对象）差距会变大到 4 倍以上；把 value 放大到 200 B，倍数会缩小到 1.4 倍。

### 事故二：导报表一条 `ZRANGE 0 -1`，主线程停 1.3 秒（2026-06-02）

排行榜 zset `rank:live:9901`，90 万成员。运营要「导出完整榜单做线下分析」，开发写了 `ZRANGE rank:live:9901 0 -1 WITHSCORES`，在管理后台点一下执行。

| 时间 | 事件 | 主线程停 | 其他业务 P99 |
| --- | --- | --- | --- |
| 14:20:00 | 点击导出，命令进入队列 | — | 6 ms |
| 14:20:00.011 | 命令开始执行：遍历 90 万节点，生成 90 万条 RESP 回复 | **1.3 s** | 累计 21 万请求超时 |
| 14:20:01.3 | 回复写完（约 39 MB 进 output buffer），开始排空网卡 | 0（异步 flush） | 恢复 6 ms |
| 14:20:03 | 客户端是同步读，网卡 1 Gbps 排 39 MB 要 0.31 s，期间该连接占用 | — | — |
| 复盘 | 1.3 s 的停顿等价于把实例 QPS 归零 1.3 s；同实例上 3 个业务全部超时 | — | — |

同一个命令在 100 个成员上只要 **30 μs**（listpack 里连续扫描 + 一次小分配）。差 4 个数量级不是「数据多了 9,000 倍」这个朴素解释——真正的分界点是：**90 万成员的 zset 一定是 `skiplist`，而 skiplist 的每一个节点都是独立 malloc 的一块内存**，遍历 90 万节点 = 90 万次指针追逐，每次大概率一次 cache miss（约 100 ns）；100 个成员的 listpack 是一次连续内存扫描，且整块可能就在 L1/L2 里。

> `ZRANGE` 的复杂度在文档里写的是 `O(log(N)+M)`，`M` 就是返回成员数——**这个 `M` 由调用方决定，不由数据库决定**。这是「服务端分页」永远比「全量导出」安全的原因，也是 §13.11 里那条「按命令分位延迟」比平均延迟更有用的原因。

### 事故三：全量同步之后，从库比主库多占 40% 内存（2026-09-18）

一位运维为了「省内存」，把主库 `hash-max-listpack-entries` 从 128 调到 512——直觉是「更多 key 保持紧凑编码，更省内存」。灰度只改了主库，从库沿用默认 128。

| 时间 | 事件 | 主库内存 | 从库内存 |
| --- | --- | --- | --- |
| 09-18 10:00 | 主库调参并重启，重启后按 512 重新编码存量 key | 3.6 GB | 3.6 GB |
| 10:20 | 从库因维护窗口重启，**全量同步**（RDB 载入） | 3.6 GB | 5.1 GB |
| 10:34 | 从库所在 8 GB 机器剩余内存 300 MB，触发 swap | 3.6 GB | 5.1 GB + swap |
| 10:41 | 从库延迟从 0 涨到 40 s（swap 把回放拖死），哨兵判定主观下线 | 3.6 GB | — |
| 10:52 | 哨兵提升从库为主库，业务开始读到 40 s 前的数据 | — | — |
| 复盘 | 一次「省内存」的调参，最终以**主从配置漂移 + 主库切换**收场 | — | — |

原因很直接：**RDB 里存的是逻辑数据（field/value），不是编码**。从库载入时按**自己的**阈值重新决定编码，所以同一份数据在两个节点上可以长得完全不一样。这件事的工程含义有三条：① 编码阈值属于**数据形态的一部分**，必须和主从配置一起版本化；② 切主之后内存可能突变，容量评估要按「最宽松的那套阈值」做；③ 想验证阈值改动的影响，`DEBUG RELOAD` 一次比看文档快（前提是 `enable-debug-command` 已开，7.0 起默认禁止）。

## 13.2 一句话定位与唯一真问题

> **Redis 的内存账不是「数据有多大」，而是「数据被切成多少个对象、每个对象套了几层指针」；而编码切换是一道单向门——跨线那一刻付一次 O(N) 的时间，跨线之后付永久的内存。**

这句话要拆成三截：

1. **「切成多少个对象」**：listpack 把 100 个 field 装进一块连续内存；hashtable 把它们拆成 100 个 `dictEntry` + 100 个 SDS + 100 个 `robj`。**同样 5.2 KB 的 payload，前者 5.5 KB，后者 11.2 KB**，差在指针和分配器对齐上，不在数据上。
2. **「单向门」**：`hash` 从 listpack 变 hashtable 之后，即使你把 130 个 field 删到只剩 3 个，编码**也不会退回** listpack。Redis 从不做反向转换——所以「临时批量导入」的痕迹会永久留在内存里，直到这个 key 被删掉重建。
3. **「O(N) 那一刻」**：跨线是把整张 hash 重写一遍，不是只转新增的那个 field。128 个 field 的哈希，一次跨线约 20–40 μs；40 万个 key 在同一分钟集中跨线，就是 8–16 s 的主线程时间。

### 八问卡（编码层版，密度对齐 `01-component-anatomy-method.md` §01.3）

| 问 | 一句话答案 | 数字 / 边界 |
| --- | --- | --- |
| ① 承诺什么 | 「小数据用紧凑编码省内存、大数据用真结构保复杂度」；**不承诺**「内存随删除而下降」，也**不承诺**「参数一改立刻生效」 | 存储型契约，不是延迟契约 |
| ② 数据长什么样 | 一个 key = `robj` + 类型对象；容器对象在阈值两侧是两种完全不同的内存布局 | 见 §13.3、§13.4 |
| ③ 一次读写走哪条路 | 主线程里：查 `dict` → 拿到 `robj` → 按 `encoding` 分派 → listpack 顺序扫 / hashtable 哈希 / skiplist 逐层下降 | 见 §13.7，listpack 0.3 μs vs skiplist 逐节点 |
| ④ 并发与一致 | 无并发（单线程），因此编码切换是**原子的、不可被打断的 O(N)**；不像 `dict` 扩容那样能增量 rehash | 这是与 Java `HashMap` 最大的差别 |
| ⑤ 扩展维度 | 不可扩，只能**换零件**：垂直（加内存）/ 拆 key（分桶）/ 换类型（hash → 多个 string）/ 换存储 | 见 §13.9 |
| ⑥ 系统级失效 | 慢（跨线 + 大结构遍历）、满（内存放大触发逐出）、语义漂移（主从阈值不一致导致内存与淘汰行为不同） | 见 §13.10 |
| ⑦ 指标 | `OBJECT ENCODING` 分布、`MEMORY USAGE` 分位、`mem_fragmentation_ratio`、`evicted_keys` 增速、分命令 `usec_per_call` | 见 §13.11，全部标版本与开关 |
| ⑧ 换掉它的信号 | 单实例数据集 > 内存 60% 且 `evicted_keys` 非零；或单 key > 10 万成员且存在全量遍历 | 见 §13.9 换挡表 |

## 13.3 物理形态：一个 key 到底占几块内存

Redis 的值不是「一段字节」，而是**四层嵌套的指针**：键空间字典 → `robj` 头 → 类型对象（可能是 SST 字符串，也可能是哈希表/跳表） → 元素本身。看懂这四层，所有内存问题都变成加法。

**图 1 · 一个 string key 的四层嵌套**

```text
┌─ 键空间 dict（server.db[i].dict）───────────────────────────────────┐
│  hash 桶数组（每槽 8 B 指针）                                        │
│      │                                                              │
│      ▼                                                              │
│  ┌─ dictEntry  24 B ──────────────────────────────┐                 │
│  │ key ──► SDS "user:10086"  3 B 头 + 12 B + \0   │  → jemalloc 16 B│
│  │ v   ──►（union）                                │                 │
│  └────────────────────┬───────────────────────────┘                 │
│                       ▼                                             │
│  ┌─ robj  16 B ───────────────────────────────────┐                 │
│  │ type:4 | encoding:4 | lru:24 | refcount:4 | ptr│                 │
│  └────────────────────┬───────────────────────────┘                 │
│                       ▼                                             │
│  ┌─ SDS "hello world..."  3 B 头 + 40 B + \0 ─────┐  → jemalloc 48 B│
│  └────────────────────────────────────────────────┘                 │
│                                                                     │
│  若该 key 有 TTL：另有一个 expires dict，再来一份 dictEntry + 桶指针 │
└─────────────────────────────────────────────────────────────────────┘
   合计：24 + 16 + 16 + 48 + 8 = 112 B，装的是 40 B 的 value
```

三条从这张图直接读出的结论：

1. **固定开销比 payload 大**。一个 40 B 的 value，加上键名、`robj`、`dictEntry`、桶指针，实占 **112 B**（无 TTL）。这就是「小 key 特别贵」的物理原因：1 亿个 40 B 的小 key ≈ **12.8 GB**，而数据本身只有 4 GB。
2. **`robj` 只为「通用」付费**。`robj` 里带 `lru`（用于淘汰）、`refcount`（用于共享整数对象），一个 16 B；容器类型还各自再套一层 `robj`。这就是为什么 7.0 以后 `dictEntry` 做了压紧——但**键空间这一层的四件套改不掉**。
3. **`jemalloc` 对齐是隐形的放大**。44 B 的 SDS 实际占 48 B 档，65 B 的 SDS 直接跳 80 B 档。**value 长度分布在档位边界附近时，内存会突然多 20%**——这是「同样的业务，A 集群比 B 集群多 15% 内存」最常见的解释，而不是内核或版本差异。

| 对象 | 一个实例占 | 说明 |
| --- | --- | --- |
| 键空间 `dict` 哈希桶 | 8 B / 槽 | 负载因子 1 左右，均摊到每个 key 约 8 B |
| `dictEntry` | 24 B | key 指针 + value union + next 指针（7.0 压缩后） |
| 键名 SDS | `3 B 头 + len + 1` 起 | ≤ 44 的短串走 `sdshdr8` 或 `embstr` 内联 |
| value `robj` | 16 B | 容器类型的元素级 `robj` 可被共享/内联 |
| TTL `dictEntry` + 桶 | 32 B | 有 TTL 才有；**「全量加 TTL」= 白送 30% 内存** |

## 13.4 五种编码的物理结构

### ziplist：连续字节 + 反向指针（历史包袱）

ziplist 是 7.0 之前 list/hash/zset 的紧凑编码：一整块连续字节，头部 `zlbytes(4) + zltail(4) + zllen(2)`，尾部 `zlend(1) = 0xFF`，中间是变长 entry。每个 entry 是 `prevlen + encoding + content`。

`prevlen` 的存在是为了**从后往前遍历**（`zltail` 给出最后一项偏移，靠 `prevlen` 一路往前跳）。它有两档长度：**前一项长度 < 254 时占 1 B，否则占 5 B**。这一档之差就是著名的**级联更新（cascade update）**：

**图 2 · ziplist 的级联更新：一次插入可能重写整张表**

```text
初始：三个 entry，长度分别是 200 / 200 / 200 字节
  ┌──────────────┬─────────┬──────────────┬─────────┬──────────────┐
  │ prevlen=0    │ 200 B   │ prevlen=201  │ 200 B   │ prevlen=201  │
  │  1 B         │         │  1 B         │         │  1 B         │
  └──────────────┴─────────┴──────────────┴─────────┴──────────────┘

某次更新把第 1 个 entry 从 200 B 撑到 254 B：
  ┌──────────────┬─────────┬──────────────┬─────────┬──────────────┐
  │ prevlen=0    │ 254 B   │ prevlen=255  │ 200 B   │ prevlen=201  │
  │  1 B         │         │ 5 B  ◄── 变长 │         │              │
  └──────────────┴─────────┴──────────────┴─────────┴──────────────┘
                                   │ 第 2 项总长 201 → 205，仍是 1 B 的 prevlen？
                                   ▼ 若它也被推到 254 以上 →
  ┌───────────────────────┬───────────────────────┬──────────────────┐
  │ 继续向后传播：第 3 项 prevlen 也变 5 B，第 4 项……直到末尾        │
  └───────────────────────┴───────────────────────┴──────────────────┘
  最坏情况：N 个 entry 各触发一次，总搬运量 O(N²)
```

**这就是 listpack 诞生的唯一原因。** 链表式的 `prevlen` 让「局部修改」有可能退化成「全表重写」，而 Redis 是单线程——重写期间整实例停摆。

### listpack：删掉 prevlen 的那一刀

listpack 保留「一整块连续字节」，但**每个 entry 只记录自己的长度**，不再记录前一项的长度；为了支持反向遍历，在 entry 尾部加一个 `backlen`（自身长度的可变编码，1–5 B，**不含**自身长度字段）。于是「上一项变长」永远不会导致「本项变长」，级联更新从结构上被消灭。

**图 3 · listpack 的布局**

```text
┌────────────┬────────────┬──────────────────────────────────────┬──────┐
│ total-bytes│ num-elems  │ entries                              │ 0xFF │
│    4 B     │ 2 B（>65535 │                                      │ 1 B  │
│            │  则不可信） │                                      │      │
└────────────┴────────────┴──────────────────────────────────────┴──────┘
                            │
   ┌────────────────────────┴───────────────────────────────────────────┐
   │ entry = encoding + data + backlen                                   │
   │                                                                     │
   │  ┌───────────┬────────────────┬───────────┐  ┌───────────┬───────┐  │
   │  │ enc(变长) │ data          │ backlen   │  │ enc      │ data  │… │
   │  │ 标识长度  │   12 B        │ 1–5 B     │  │          │       │  │
   │  └───────────┴────────────────┴───────────┘  └───────────┴───────┘  │
   │        ▲                                            │               │
   │        └── 正向往后：读 enc 就知道本项多长            │               │
   │                                                     ▼               │
   │  反向往回：读尾部 backlen 就知道本项多长（不需要前一项的信息）      │
   └─────────────────────────────────────────────────────────────────────┘
```

7.0 起 list/hash/zset 的紧凑编码全部换成 listpack（配置名也从 `*-max-ziplist-*` 改成 `*-max-listpack-*`）；7.2 起 set 也支持 listpack。**7.0 之后你在 `OBJECT ENCODING` 里已经看不到 `ziplist` 了**——不是它被删了，是不再有任何用户可见对象用它。

### intset：有序定长数组

set 的成员全是整数且数量 ≤ `set-max-intset-entries`（默认 512）时，用 intset：`encoding(4) + length(4) + 有序数组`，元素宽度由最大元素决定（`INTSET_ENC_INT16/32/64`）。两个要点：

- **有序 → 二分查找**，`SISMEMBER` 是 O(log N) 且缓存友好，比哈希表更快。
- **升级是单向的**：插入一个 2^31 的数，整块数组从 2 B/元素重编码成 4 B/元素（O(N)）；插入一个非整数成员，整个对象变成 hashtable；**且两者都永不降级**。

### quicklist：listpack 的链表

list 是唯一「天生就大」的类型——它可能有一千万个元素。quicklist 的做法是：**一串 listpack 节点组成双向链表**，每个节点按 `list-max-listpack-size`（默认 128）装若干个元素。

- 正数 = 每个节点最多装多少个元素；负数 `-1..-5` = 按节点字节数上限（约 4 KB / 8 KB / 16 KB / 32 KB / 64 KB）。
- 好处：`LPUSH/RPUSH` 只碰头尾两个节点（O(1)），中间节点整块紧凑存储。
- 代价：`LINDEX key 500000` 要沿链表走 3,900 个节点；`LRANGE` 大区间会把跨节点的元素拼成回复。**随机访问是 quicklist 最弱的操作**，这是「用 list 存 100 万条消息然后按索引取」翻车的原因。

### skiplist + dict：两套索引一份数据

zset 超过阈值后是「跳表 + 字典」组合，**同一份成员数据被两套结构同时索引**：

**图 4 · zset 的双索引：跳表管顺序，字典管点名**

```text
                    ┌───────────────────────────────────────┐
   zset ───────────►│ dict: member ──► score                │  O(1) 查分
                    │   "alice"  ──► 88.5                   │  （ZSCORE）
                    │   "bob"    ──► 91.0                   │
                    └───────────────────────────────────────┘
                    ┌───────────────────────────────────────┐
                    │ skiplist（按 score 有序，同分按 member）│  O(log N) 定区间
   L4  head ──────────────────────────────────► NULL        │  （ZRANGE）
   L3  head ──────────► bob ──────────────────► NULL        │
   L2  head ──────────► bob ──────► dave ─────► NULL        │
   L1  head ─► alice ─► bob ──────► dave ─────► NULL        │
                    │ 每个节点 = sds member + double score  │
                    │          + 不定长 level 数组           │
                    └───────────────────────────────────────┘
   ↑ 成员字符串只存一份（跳表与字典共享同一个 SDS），score 存两份
```

跳表层数的期望值由 `ZSKIPLIST_P = 0.25` 决定：一个节点有 `p` 的概率升到下一层，所以**每个节点的平均层数 = 1/(1-p) = 1.33**，最大 `ZSKIPLIST_MAXLEVEL = 32`（够 2^64 个元素）。这个 0.25 直接决定内存：层数越高，`forward` 和 `span` 指针越多。

| 层数 k | 概率 | 100 万成员的期望节点数 | 该层内存（16 B/节点） |
| --- | --- | --- | --- |
| 1（必有） | 1 | 1,000,000 | 16 MB |
| 2 | 0.25 | 250,000 | 4 MB |
| 3 | 0.0625 | 62,500 | 1 MB |
| 4 | 0.0156 | 15,625 | 0.25 MB |
| ≥5 | 0.0039 | 3,906 | 约 0.1 MB |
| **合计** | 1.333 / 节点 | — | **约 21.3 MB** |

## 13.5 阈值表与单向门

**这是本篇唯一需要背下来的表。** 注意阈值有两条腿：**元素个数** 和 **单个元素的字节数**——`hash-max-listpack-value`（默认 64）意味着**哪怕只有 2 个 field，只要某个 value 超过 64 B 就立刻变 hashtable**。很多人只记得「128 个」，于是在一个 `field → 2 KB 的 JSON` 的 hash 上永远看不到 listpack。

| 类型 | 紧凑编码 | 真结构编码 | 阈值参数（7.x 名） | 6.2 及更早的名字 | 默认值 |
| --- | --- | --- | --- | --- | --- |
| string | `int`（整数）/ `embstr`（≤44 B） | `raw` | `OBJ_ENCODING_EMBSTR_SIZE_LIMIT`（源码常量） | 同 | 44 B |
| list | listpack（quicklist 节点内） | — | `list-max-listpack-size` | `list-max-ziplist-size` | 128 |
| hash | listpack | hashtable | `hash-max-listpack-entries` / `hash-max-listpack-value` | `hash-max-ziplist-entries` / `-value` | 128 / 64 |
| set | intset | hashtable | `set-max-intset-entries` | 同 | 512 |
| set | listpack（7.2+） | hashtable | `set-max-listpack-entries` / `set-max-listpack-value` | — | 128 / 64 |
| zset | listpack | skiplist + dict | `zset-max-listpack-entries` / `zset-max-listpack-value` | `zset-max-ziplist-entries` / `-value` | 128 / 64 |

**单向门：哪些能退回，哪些永远退不回。**

| 转换 | 触发条件 | 会退回吗 | 工程含义 |
| --- | --- | --- | --- |
| `int` → `embstr` → `raw`（string） | 每次 `SET`/`APPEND`/`SETRANGE` 重新判定 | **会**：长度变短就回 `embstr` | string 的编码是「每次重算」，所以不必担心 |
| listpack → hashtable（hash） | field 数 > 128 **或** 任一 field/value > 64 B | **不会** | 删到剩 3 个 field 也是 hashtable，内存 3 倍 |
| listpack → skiplist（zset） | 成员数 > 128 或元素 > 64 B | **不会** | 排行榜扩容后内存永久上台阶 |
| intset → hashtable（set） | 加入非整数成员 | **不会** | 一个 `"unknown"` 哨兵值就能毁掉整组 set |
| intset（int16→int32→int64） | 插入更大的整数 | **不会** | 一个 10 位数让 512 个元素全部翻倍 |
| quicklist 节点内 listpack | 节点满则开新节点 | 双向，无需回退 | 默认 128/节点，调参直接影响节点数 |

**为什么不做反向转换？** 两个理由都很实在：① 判断「现在能不能退」需要重新扫一遍整张 hash，而这次扫描发生在**写命令的路径上**——为省内存而给写路径加一次 O(N)，是拿延迟换内存的坏交易；② 反向转换会在主从/持久化之间制造额外的状态差异（任何一方的判断阈值不同，数据形态就不同）。代价就是本篇反复说的那件事：**内存只会单调上台阶**。

## 13.6 跨线那一刻：O(N) 与「删除不缩容」

跨线不是「加一个 field」这么便宜的事，它是**整张 hash 重写一遍**：

```text
HSET up:10086 tag_new "..."   ← 第 129 个 field
   │
   ├─ 1. 发现 entries+1 > 128 → 决定 convert
   ├─ 2. 分配一个新 dict（桶数按 129 算，扩容到 256 桶）
   ├─ 3. 遍历 listpack 的 128 个 entry：
   │      为每个 field 创建 SDS（malloc）+ robj（malloc）+ dictEntry（malloc）
   │      插入新 dict
   ├─ 4. 释放原 listpack 的那一块连续内存
   └─ 5. 把 robj 的 encoding 改成 hashtable，指针指向新 dict
   整个 1–5 在单线程里原子完成：128 个 field ≈ 20–40 μs
```

对比一下 **hashtable 自身的扩容**：`dict` 扩容走的是**增量 rehash**——保留两张表，每次命令顺带迁移几个桶，所以永远不会有一次「卡 5 ms」的扩容。**编码转换没有这个优待**，它是原子的。这是理解「为什么阈值节点的抖动总出现在某个写命令上」的关键。

再把「一次性」和「批量」叠起来看，才有工程意义：

| 场景 | 单次代价 | 批量代价 | 观感 |
| --- | --- | --- | --- |
| 1 个 hash 跨线（128 field） | 20–40 μs | — | 看不见 |
| 40 万个 hash 在 1 小时内跨线（事故一） | 20–40 μs | 累计 8–16 s，摊薄后约 0.4% 主线程 | 可见但不算致命；**致命的是 2.9 GB 内存** |
| 40 万个 hash 在 1 分钟内跨线（批量回填） | 20–40 μs | 累计 8–16 s / 60 s = **13–27% 主线程** | P99 抬 2–5 倍，与事故一重叠 |
| 阈值被调到 4,096 后单个 hash 跨线 | 0.6–1.3 ms | 若同时有 200 个这样的 key | 出现秒级毛刺，`SLOWLOG` 抓不到（单条 < 10 ms 默认阈值时） |

> **性质：量级结论。** 单次转换耗时按「128 个 field × 约 200–300 ns（3 次 malloc + 1 次插入）」估，实际随 jemalloc 命中率、field 长度、CPU 在 2 倍内浮动。批量数字按「不与其他命令交错」的理想摊薄算，真实场景会和 `HGETALL` 等大命令叠加。

**「删除不缩容」还有第二层。** 即使不跨线，`HDEL` 掉的 field 留在 listpack 里也不会立刻归还内存——listpack 是整块重分配的结构，删元素通常只是缩短使用长度，**分配器不会把这块内存还给 OS**（jemalloc 的 dirty page 保留策略）。所以你会看到一条经典曲线：内存涨上去 → 业务量下来 → `used_memory` 降了 → `used_memory_rss` 不降 → `mem_fragmentation_ratio` 升到 1.6。**解法不是调参，是重建 key 或重启**，这也是「Redis 内存只能靠重启洗干净」这句话的物理来源。

## 13.7 一次读写链路：`HGET` 的两条路

同一条命令在两种编码下的物理路径完全不同——**这不是微优化，是 2 个数量级的差**。

| 步骤 | listpack（≤128 field） | hashtable（>128 field） | 量级 |
| --- | --- | --- | --- |
| 1. 键空间查找 | `dict` 哈希 + 比较 | 同 | 各 0.2–0.4 μs |
| 2. 拿到容器 `robj` | 直接读 `ptr` | 同 | — |
| 3. 定位 field | **从块头顺序扫描**，逐个比较 field 名 | `dict` 哈希 + 冲突链比较 | 顺序扫 O(N)，哈希 O(1) |
| 4. 取 value | 指针指向块内位置，**零分配** | 取 `robj` → SDS，共享引用 | — |
| 5. 组装回复 | 复制 value 字节 | 同 | — |
| **合计（100 field）** | **约 0.3–1 μs**（整块在 L2） | 约 0.4–0.6 μs | 打平 |
| **合计（10 万 field）** | 不可达（一定跨线） | 约 0.5 μs + 偶发 cache miss | 哈希胜 |

这张表最反直觉的一行是**「100 field 时两者差不多」**。紧凑编码的价值不在单次查找速度，而在两处：**内存**（省 50%）与**遍历**（`HGETALL` 扫 listpack 是连续读，扫 hashtable 是 10 万次指针追逐）。

所以取值的正确结论是：**listpack 是为「小对象 + 常遍历」设计的，hashtable 是为「大对象 + 常点查」设计的**。如果你的 hash 只有 20 个 field 却每次都要 `HGETALL`，listpack 帮你省的不只是内存，还有遍历时的 cache miss。

`HGETALL` 在 10 万 field 的 hashtable 上要多久？10 万次 `dictEntry` 遍历 + 10 万个 SDS 长度读取 + 拼 RESP。经验值 **8–15 ms**（不含网络），并且会一次性在 output buffer 里堆出约 12 MB 回复——这就是 12 篇事故二里「`HGETALL` 700 ms」的放大机制：50 万 field × 2.5 KB = 1.35 GB，除以 memcpy 带宽 2 GB/s 也要 0.6 s，几乎全部是**单线程上的内存拷贝**。

**图 5 · 一次 `HGET` 的分派决定后面所有代价**

```text
命令 HSET key f v  →  t_hash.c  →  先说 encoding？
                                        │
        ┌───────────────────────────────┴──────────────────────────────┐
        ▼                                                              ▼
  listpack（≤128 且每个元素 ≤64 B）                          hashtable（其余全部情况）
  ┌──────────────────────────────────┐                      ┌──────────────────────────────────┐
  │ 在连续块内顺序找 field，找到就地  │                      │ dictLookup：哈希 → 桶 → 冲突链比较 │
  │ 覆盖或尾部追加；块满则 realloc     │                      │ 每个 field 独立 malloc 的 dictEntry│
  │ 优点：省 50% 内存、遍历极快        │                      │ 优点：O(1)、可承载千万级 field     │
  │ 缺点：单次写 O(N) memmove，N≤128   │                      │ 缺点：内存 2–3 倍、遍历全是 cache miss│
  └──────────────────────────────────┘                      └──────────────────────────────────┘
                 │                                                              │
                 └──────────────► 一旦跨线，永不回头（§13.5 单向门）◄──────────┘
```

## 13.8 三本账：内存放大、键空间开销、遍历代价

### 账一：内存放大——紧凑编码 vs 真结构

场景：hash，field 名 12 B，value 40 B，分别用两种编码存放。

| 项 | listpack 每 field | hashtable 每 field |
| --- | --- | --- |
| 元素头 / 指针 | `prevlen 1 + encoding 1(+1)` ≈ 2–3 B | `dictEntry 24 + 桶 8` = 32 B |
| field 名存储 | 内联在块里，字段名 12 B | SDS `3+12+1=16` → jemalloc **16 B** |
| value 存储 | 内联在块里，value 40 B | `robj 16 + SDS 3+40+1=44→**48 B**` = 64 B |
| 单 field 合计 | **约 55 B** | **约 112 B** |
| 100 field 的 hash | 5.5 KB（+7 B 头） | 11.2 KB |
| 放大倍数 | 1.0× | **2.0×** |
| 1,000 万 field 总量 | 550 MB（**办不到**，128 就跨线） | 1.12 GB |

zset 更贵，因为它一份数据两套索引：

| 项 | 单成员（member 24 B） | 说明 |
| --- | --- | --- |
| 跳表节点基础 | 24 B | `ele` 指针 8 + `score` 8 + `backward` 8 |
| 跳表 level 数组 | 约 21.3 B | 期望 1.333 层 × 16 B（`forward` + `span`） |
| 成员 SDS | 32 B | `3+24+1=28` → jemalloc 32 档 |
| 字典项 + 桶 | 32 B | `dictEntry 24 + 桶 8`（成员 SDS 与跳表共用） |
| **合计** | **约 109 B → 取整 112–120 B** | payload 只有 24 B → **放大约 4.7×** |
| 100 万成员的 zset | 约 120 MB | 若在 listpack 里只有约 60 MB（但阈值 128 不允许） |

> **性质：量级结论。** 假设 jemalloc 尺寸档为 8/16/32/48/64/80/96/112/128 B、无 TTL、field 名与 value 长度固定、`dict` 负载因子约 1。换成带 TTL 的场景每 key 再加 32 B；value 含大量短整数时会走共享整数对象，hashtable 侧会省下 `robj` 与 SDS，倍数降到 1.5 倍左右。

### 账二：键空间开销——1 亿小 key 的成本

| 项 | 每 key | 1 亿 key |
| --- | --- | --- |
| `dictEntry` | 24 B | 2.4 GB |
| 键名 SDS（16 B 名） | 24 → 32 B | 3.2 GB |
| 哈希桶（均摊） | 8 B | 0.8 GB |
| value `robj` | 16 B | 1.6 GB |
| value SDS（40 B） | 48 B | 4.8 GB |
| **合计** | **128 B** | **12.8 GB** |
| 其中真实数据 | 56 B | 5.6 GB |
| **放大** | **2.3×** | — |

结论很硬：**1 亿个 40 B 的小 key 在 Redis 里就是一台 16 GB 实例**。所以「把用户会话拆成每属性一个 key」这种设计一定会撞墙，正确做法是一个 hash 装一个实体的所有属性（既省键空间，又常驻 listpack）。

### 账三：遍历与跨线的 O(N)

| 操作 | 数据结构 | 90 万成员的耗时 | 100 成员的耗时 | 倍差 |
| --- | --- | --- | --- | --- |
| `ZRANGE 0 -1` | skiplist / listpack | 0.9–1.4 s | 30 μs | 约 4 万倍 |
| `HGETALL` | hashtable / listpack | 10 万 field 约 8–15 ms | 100 field 约 8 μs | 约 1,500 倍 |
| `SMEMBERS` | hashtable / intset | 100 万成员约 120 ms | 512 成员约 3 μs | 约 4 万倍 |
| 跨线转换 | listpack → hashtable | — | 20–40 μs / 次 | 与 N 成正比 |

> **性质：量级结论。** 遍历耗时为「遍历 + 组装回复」的合计，按单节点 100 ns 的 cache miss 与 2 GB/s 的 memcpy 估算；实际随回复大小、客户端读速、是否走 output buffer 上限而变化。**这组数字的真正用法是判断「这条命令该不该出现在在线路径上」，不是精确预测。**

## 13.9 架构边界：编码能救什么、救不了什么

**能救的（改配置或改设计即可）：**

- 小对象的**内存**：让 hash/zset/set 常驻 listpack，省 40–50%。
- 小对象的**遍历**：连续内存扫描比指针追逐快一个数量级。
- 点查的**复杂度**：跨线之后 `HGET`/`ZSCORE` 稳定 O(1)/O(log N)，不受 field 数影响。

**救不了的（必须换形态）：**

- **单 key 的写吞吐**。一个热点 key 的所有写都在同一个主线程上串行（12 篇 §12.6），编码再紧凑也不解决问题；只能拆 key 或本地缓存。
- **大 key 的全量遍历**。任何「一次取回全部”的语义都是 O(N) 回复，编码只改变常数，不改变阶。
- **内存碎片**。跨线 + 删除造成的高水位只能靠重建 key 或重启，参数调不动。
- **跨实例的数据规模**。编码是单机策略，横向仍要靠 Cluster（`→ comp/15`）。

**⑤ 扩展维度四选一**：编码本身**不可扩展**，只能换零件。

| 手段 | 做什么 | 代价 |
| --- | --- | --- |
| 垂直（加内存） | 提高 `maxmemory`、上更大机型 | 单价最高；fork 停顿随内存涨（`→ comp/14`） |
| 拆 key（分桶） | `up:{uid}` → `up:{uid}:0..15`，每桶一个 hash | 多 key 命令失效，读要合并 N 份 |
| 换类型 | 大 hash → 多个 string / 用 `HSCAN` 契约化访问 | 失去原子性，语义要重写 |
| 换存储 | 大对象挪到 S3/MySQL，Redis 只存索引（`→ comp/38`） | 多一跳网络，延迟从 μs 到 ms |

**换挡表（什么时候它不再是正确选择）：**

| 信号 | 阈值 | 换向哪里 |
| --- | --- | --- |
| 单 key 成员数 | > 10 万且需要遍历 | 拆 key，或把明细放进列存/搜索（`→ comp/20`、`→ comp/21`） |
| `mem_fragmentation_ratio` | 长期 > 1.5 | 滚动重启 / 重建 key，不是调参 |
| `evicted_keys` 增速 | 非零且持续 10 分钟 | 扩内存 / 分片，而不是调 `maxmemory-policy` |
| 单实例数据集 | > 内存 60% | 上 Cluster（`→ comp/15`） |
| 跨线 key 占比 | `OBJECT ENCODING` 采样里 hashtable > 80% | 说明设计错位：该用 string 或多个 key，而非 hash |

## 13.10 踩坑清单（现象 → 根因 → 定位 → 修复 → 防复发）

| 现象 | 根因 | 定位 | 修复 | 防复发 |
| --- | --- | --- | --- | --- |
| 内存突然涨 2–3 倍，无流量变化 | hash/zset 跨过 entries 阈值，编码变真结构且**不可回退** | `redis-cli --bigkeys` + 抽样 `OBJECT ENCODING` | 扩内存撑住，随后重建 key（`DUMP`/`RESTORE` 或改结构） | 把「单 key 成员数上限」写进容量评审；回填任务前先算 `key 数 × 每 key 成员数` 是否跨线 |
| 2 个 field 的 hash 却是 `hashtable` | 只记得 128，忘了 `hash-max-listpack-value` = 64 B；某个 value 是 2 KB JSON | `OBJECT ENCODING` + `MEMORY USAGE key` | 把大 value 拆成独立 string，或用 `hash-max-listpack-value` 评估放大后内存 | 阈值表两条腿（entries + value 字节）进开发规范 |
| 调大阈值后单次写变慢、P99 抖动 | listpack 单次写是 O(N) memmove，阈值 4,096 时单次移动上百 KB | `INFO commandstats` 里 `cmdstat_hset.usec_per_call` 抬升 | 调回默认；热 path 用 `HINCRBY` 等非搬移命令 | 阈值调整必须带压测，禁止只按「省内存」单指标改 |
| 主从内存不一致 / 切主后内存突变 | RDB 只存逻辑数据，从库按**自己的**阈值重新编码 | 对比两侧 `CONFIG GET *-max-listpack-*` 与 `used_memory` | 统一配置并重启从库重同步 | 编码阈值纳入配置基线；主从配置差异进巡检 |
| 删除大量数据后 RSS 不降 | jemalloc 保留 dirty page；listpack 缩短不等于归还 | `used_memory` 降而 `used_memory_rss` 不降，`mem_fragmentation_ratio` 升 | 滚动重启，或 `MEMORY PURGE`（4.0+，只对部分场景有效） | 容量按 RSS 而非 used 定水位；`activedefrag` 评估（默认关） |
| 一个 `"unknown"` 让整组 set 变成 hashtable | intset → hashtable 单向 | `OBJECT ENCODING` 对比同类 set | 哨兵值改用独立 key | 约定型 set 不做「用字符串标记异常」的设计 |
| `LINDEX` 慢得离谱 | 100 万元素的 list 是 7,800 个 quicklist 节点，按下标访问要沿线走 | `LATENCY HISTORY lindex`（需 `latency-monitor-threshold` 开启） | 改用 zset 存「带序号的队列」，或直接换 stream | 禁止用 list 做「随机访问 + 大容量」 |
| `DEBUG` 相关命令在 7.x 报不可用 | 7.0 起 `enable-debug-command` 默认 `no` | 命令报错原文 | `CONFIG SET enable-debug-command local`（需 `yes`/`local`） | 排障手册写明各版本开关 |
| 大 key 判不出来 | `MEMORY USAGE` 对嵌套类型默认**采样**，`--bigkeys` 只看元素数 | 用 `MEMORY USAGE key SAMPLES 0` 取精确值 | 建立「长度 + 内存」双维度的 bigkey 报表 | 巡检按 `MEMORY USAGE` 排序，而非只按 `LLEN`/`HLEN` |

## 13.11 观测：指标、拐点与告警

| 指标 | 来源 | 版本 / 开关前提 | 拐点 | 说明 |
| --- | --- | --- | --- | --- |
| `OBJECT ENCODING key` | `OBJECT ENCODING` | 全版本 | 采样里 `hashtable`/`skiplist` 占比 > 80% | 最直接的「形态漂移」证据，**这是本篇第一指标** |
| `MEMORY USAGE key [SAMPLES n]` | `MEMORY USAGE` | 4.0+；**默认采样 5 个元素**，`SAMPLES 0` 才精确（O(N)，别对在线大 key 跑） | 单 key > 10 MB | 大 key 的唯一可信口径 |
| `MEMORY STATS` 的 `dataset.bytes` | `MEMORY STATS` | 全版本 | 与 `used_memory` 差 > 30% | 差值含碎片与开销，能区分「数据涨」与「开销涨」 |
| `mem_fragmentation_ratio` | `INFO memory` | 全版本 | > 1.5 碎片；**< 1 说明在 swap**（比 > 1.5 更危险） | 与 12 篇同一口径，避免两篇指标打架 |
| `evicted_keys` 增速 | `INFO stats` | 全版本 | 非零且持续 | 增速比总数有用：总数不清零，是历史累计 |
| `usec_per_call`（分命令） | `INFO commandstats` | 全版本；`CONFIG RESETSTAT` 清零 | 比基线涨 10× | 跨线或成员变大的第一信号 |
| `latency_percentiles_usec_<cmd>` | `INFO latencystats` | **7.0+**；`latency-tracking yes` 默认开 | `hgetall`/`zrange` 的 p99 > 10 ms | 平均延迟永远抓不到长尾 |
| `latency-monitor-threshold` 事件 | `LATENCY HISTORY <event>` | 全版本；**默认 0 = 关闭，必须显式开** | 出现 `command`/`fork` 事件 | 不开就永远看不到 |
| `redis-cli --bigkeys` | CLI | 全版本；用 `SCAN` 遍历，**对线上有 O(keys) 开销** | top10 元素数 | 只按元素数排序，内存要用 `--memkeys` |

一条重要提醒：**`--bigkeys` 报的「大 key」按元素数排，`MEMORY USAGE` 报的按字节排，两者经常不是同一批 key**。一个 200 个 field 的 hash 如果有 2 KB 的 value，元素数排不进 top10，但它是 400 KB 的内存炸弹。

## 13.12 一页速记

| 问题 | 一句话答案 |
| --- | --- |
| Redis 的内存为什么是数据的 2–5 倍 | 四层嵌套：键空间 `dictEntry` + 键名 SDS + value `robj` + value SDS；容器类型再乘一份指针开销 |
| 什么时候会换编码 | 跨过 `*-max-listpack-entries`（默认 128）**或** `*-max-listpack-value`（默认 64 B） |
| 换了能换回来吗 | 不能。除 string 每次重算外，所有容器编码都是单向门 |
| 跨线那一刻贵在哪 | 整张容器重写一遍，原子 O(N)，20–40 μs/次；批量跨线会叠加成主线程占用 |
| 为什么删了数据内存不降 | 一是编码不回退，二是 jemalloc 不还脏页；只能重建 key 或重启 |
| 为什么主从内存不一样 | RDB 存逻辑数据，从库按自己的阈值重新编码 |
| listpack 比 hashtable 快在哪 | 不是点查（差不多），是**遍历**：连续内存 vs 90 万次指针追逐 |
| zset 为什么最贵 | 一份数据两套索引（跳表 + 字典），单成员约 110–120 B |
| 两个必须记住的常量 | `hash-max-listpack-entries = 128`、`hash-max-listpack-value = 64`（7.0 起叫 listpack，之前叫 ziplist） |
| 一句话 | **编码是「把内存换成指针」的交易；阈值是单向门，跨过去就再也回不来。** |

## 13.13 自检题

**1. 一个 hash 有 200 个 field，你把其中 190 个 `HDEL` 掉，剩 10 个。内存会降到原来的 5% 吗？为什么？**
<details><summary>答案</summary>
不会。200 field 时编码已是 `hashtable`，`HDEL` 只删条目、**不触发反向转换**，编码永远是 hashtable。10 个 field 仍按每 field 约 112 B 计，加上 `dict` 的桶数组（不会自动缩小很多），实际内存约为 listpack 的 2 倍以上。要回收只能 `DEL` 后重建（`DUMP`/`RESTORE` 或重新写入），或滚动重启。
</details>

**2. 为什么 90 万成员的 `ZRANGE 0 -1` 要 1 秒多，而 100 个成员只要 30 微秒？只回答「数据多 9,000 倍」为什么不够？**
<details><summary>答案</summary>
因为换了结构。100 个成员在 listpack 里：一次连续内存扫描 + 一次小分配，整块可能就在 L2 缓存。90 万成员一定是 `skiplist`：每个节点是独立 malloc 的一小块，遍历要逐节点指针追逐，每次约 100 ns 的 cache miss；再加上生成约 39 MB 的 RESP 回复、写进 output buffer、由网卡排空。倍数来自三个叠加项：cache miss（约 10×）、回复构造与拷贝（按字节线性）、输出阻塞（按带宽）。所以正确的判断不是「少返回点数据」，而是「这条命令不该出现在在线路径上」。
</details>

**3. 主从两台机器数据完全相同，`used_memory` 差 40%，最可能的原因是什么？怎么验证？**
<details><summary>答案</summary>
编码阈值配置不一致（例如主库 `hash-max-listpack-entries=512`、从库默认 128）。RDB 只存逻辑数据，从库全量同步时按**自己的**阈值重新编码，于是同一份数据在两侧形态不同。验证：`CONFIG GET *max-listpack*`（6.2 及更早为 `*max-ziplist*`）对比两侧；再抽样 `OBJECT ENCODING` 对比同一个 key。修复：统一配置并重启从库重新全量同步；工程上把阈值纳入配置基线。
</details>

**4. 阈值 `hash-max-listpack-entries` 从 128 调到 4,096，内存能省多少、代价是什么？**
<details><summary>答案</summary>
内存：对「≤4,096 field 且每个 value ≤64 B」的 hash，能省约 50%（每 field 112 B → 55 B）。代价有三条：① listpack 单次写是 O(N) memmove，4,096 个 field 时单次写平均移动上百 KB，主线程直接吃掉吞吐；② 跨线那一刻从 20–40 μs 变成 0.6–1.3 ms，形成秒级毛刺；③ 主从/多集群配置漂移会让内存与切主行为不可预测。结论：**这个参数不是纯内存旋钮，是「内存 ↔ 单次写延迟」的交换比**，必须带压测改。
</details>

**5. 给你一个陌生实例，只能跑 5 条命令，怎么判断它有没有编码层面的隐患？**
<details><summary>答案</summary>
① `INFO memory` 看 `used_memory` / `used_memory_rss` / `mem_fragmentation_ratio`（>1.5 碎片，<1 在 swap）；② `INFO commandstats` 找 `usec_per_call` 最高的容器类命令（`hgetall`、`zrange`、`smembers`、`lrange`）；③ `MEMORY STATS` 看 `dataset.bytes` 与 `used_memory` 的差（开销占比）；④ `SCAN` 采样 1,000 个 key 逐个 `OBJECT ENCODING`，统计紧凑编码占比（<20% 说明大 key 遍地）；⑤ `INFO stats` 看 `evicted_keys` 与 `expired_keys` 的累计值判断是否已在淘汰。五条合起来能画出「数据形态 + 内存结构 + 是否有大 key」三件事，不需要看业务代码。
</details>
