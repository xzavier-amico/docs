## 26.1 引子：三起「延迟达标、结果不对」的故障

ANN 的故障和倒排那一路不同：倒排故障是「搜不到」，ANN 故障是**「搜得到，但搜错了，而且错得很有规律」**——返回的永远是库里的东西，永远长得像，只是不是最近的那几条。所以三起事故里，延迟面板从始至终是绿的。

### 事故一：`ef_search` 三年没动过，召回从 0.95 掉到 0.62（2025-09-22 起）

某内容平台的「语义搜索」：上线时 800 万向量、`d=768`、`M=16`、`ef_construction=100`、`ef_search=64`，离线 `recall@10 = 0.951`，线上 P99 = 8 ms。之后没人再碰过这几个参数——**因为它们「本来就好好的」**。

| 时间 | 事件 | 数据量 | 面板上看到什么 |
| --- | --- | --- | --- |
| 09-22 | 上线，验收通过 | 800 万 | `recall@10 = 0.951`，P99 8 ms，全绿 |
| 10-20 | UGC 日增 3.2 万条 + 历史内容回灌 | 2,400 万 | P99 9 ms，召回未复测 |
| 11-08 | 索引扩到两个分片，路由按 `hash(id)` | 4,800 万 | P99 11 ms，无异常 |
| 12-01 | 运营开始零星反馈「搜出来的东西不对劲」 | 6,200 万 | P99 12 ms，**比上线时还快** |
| 12-03 | 用 1,000 条查询跑离线 ground truth 复测 | 6,200 万 | **`recall@10 = 0.62`**（延迟一路达标） |
| 12-04 | `ef_search` 64 → 192，当日复测 0.92 | — | P99 26 ms，业务接受 |
| 12-10 | 再调 `M=16→32` + 重建（`ef_construction=200`），`ef_search` 回落到 96 | — | 0.95，P99 14 ms |
| 复盘 | 约 42 天空窗，受影响搜索 PV 约 2,100 万次；**全程零错误日志、零告警** | — | — |

根因不是「配置错了」，是**参数与数据量的关系被误解了**：`ef_search` 是**层 0 候选队列的宽度**，它买的是「跳出局部最小」的宽度；而图的直径、每层点数随 `N` 增长（≈ `log_M N`），同样的宽度在 6,200 万点上能走通的「跳数」相对变少，**召回单调下滑，而距离计算次数几乎不变**——所以延迟不动、内存不动、CPU 不动，只有正确率在掉。这是一个**结构上不可能被延迟指标发现的失效**。

### 事故二：离线建索引与在线查询抢核，P99 从 20 ms 到 900 ms（2025-06-11）

某 SaaS 的 RAG 检索，1.4 亿向量、16 分片。为修事故一的同类问题，团队排了「凌晨滚动重建 HNSW」的窗口。

| 时间 | 动作 / 事件 | 在线 P99 | 备注 |
| --- | --- | --- | --- |
| 06-11 01:00 | 开始滚动重建（每分片独立建图） | 20 ms | 流量低谷，判断「影响可控」 |
| 01:40 | 构建线程数被设成物理核数（`-1` 留白都没留） | 90 ms | 距离计算打满，L3 被建图打穿 |
| 02:10 | 构建期内存峰值 = 常驻索引的 1.6 倍（候选表 + 待插入缓冲 + 训练样本） | 260 ms | 两台节点 OOMKilled |
| 02:30 | 被踢的分片在剩余节点上重放，与新构建叠加 | **900 ms** | 网关超时率 7%，前端 1,200 次空结果 |
| 03:05 | 停掉构建，回滚分片分配 | 恢复正常 | **HNSW 无断点续建：进度归零** |
| 06-11~06-15 | 先停写入（先灌后建）再限流重建，构建线程 ≤ 物理核 − 8 | 20 ms（受控） | 总窗口从计划的 6 小时变成 4 天 |
| 复盘 | 当晚语义检索降级为「只走倒排」4 小时；重建长期挤占预算 | — | — |

**这一起和 §26.8 的「构建账」是同一件事**：建图不是「IO 后台任务」，它是**持续几个小时的满核 + 随机访存 + 1.6 倍内存**的负载。把它和在线查询放在同一批核上，等于让查询排队等它算完。

### 事故三：PQ 压了 8 倍内存，没做 rerank，点击率掉 11%（2025-11-14）

同一集群水位到 78%，团队决定上 PQ：`m=96`（768 维切 96 段、每段 8 维、每段 1 字节）→ 向量本体从 3,072 B/条压到 96 B/条，整库从 340 GB 降到 42 GB（图没压，见 §26.8），**约 8 倍**。

| 时间 | 事件 | 数据 |
| --- | --- | --- |
| 11-14 02:00 | PQ 索引上线，内存水位 78% → 19% | `recall@10` 从 0.94 掉到 0.68（离线复测） |
| 11-14 10:00 | 值班判断「0.68 也能用」，因为「top-3 基本还在」 | 未做 rerank |
| 11-16 | AB 实验：搜索位点击率 −11%，长尾 query（>8 字）−19% | 召回差的正是长尾 |
| 11-18 | 改成「PQ96 粗筛 top-200 + int8 精排 top-10」 | `recall@10` 回到 0.92，P99 +0.6 ms |
| 11-18 | 内存 42 GB → 87 GB（PQ 码 9.6 + int8 原文 76.8） | 相对原始 340 GB 仍省 3.8 倍 |
| 复盘 | 两天带病上线，搜索侧 GMV 影响约 260 万元 | — |

根因一句话：**PQ 返回的距离是「查表加和」的近似值，误差专门打乱 top-k 边界上的顺序**——最像的那 200 条大概率都在候选里，但**顺序和名次是错的**；不做 rerank 就等于把「粗筛」直接当答案。

三起事故分别对应本篇三大节：**合约与召回测量（§26.3）**、**构建与资源争抢（§26.7）**、**量化与精排（§26.6）**。

## 26.2 一句话定位与唯一真问题

**定位**：向量索引是「**把一个 `O(N·d)` 的全库比较，换成几千次比较 + 一份固定的内存开销**」的结构。精确检索（倒排）把「哪些 doc 命中」做成键值查找；ANN 把「哪几条最近」做成**概率性**答案——两者的分工写在 `→ comp/21` 与本节开头，不重复。

### 唯一真问题

> **ANN 不是「更快的精确检索」，是一份用正确率换延迟的合约——每种索引结构都有自己的崩盘点（召回悬崖、内存上限、构建超时），而召回率会随数据增长与分布漂移悄悄衰减，所以「延迟达标」从来不等于「检索正确」。**

这一句要能推出全部设计：

| 从合约推出的约束 | 推出什么 |
| --- | --- |
| 召回率是**产品参数**，不是实现细节 | 上线前必须写清「本接口的 recall@k 目标是多少、用哪 1,000 条查询量的」；写不出来就不许上（§26.3） |
| 召回率**不是常数** | 它随 `N`、分布漂移、墓碑比例、`ef_search` 四个量变化 → 必须做**周期性离线评测**，而不是上线时测一次（§26.11） |
| 每种结构的崩点不同 | 图怕 `ef_search` 太小与墓碑；IVF 怕簇心失配；量化怕距离近似 → 选结构 = 选你愿意接受哪种崩法（§26.4–26.6） |
| 「延迟达标」可以靠降 `ef_search` 买到 | 所以延迟 SLO 必须与召回 SLO **同一个看板、同一次评审**，否则一定有人用召回换延迟而无人知晓（§26.10 坑一） |
| 建索引要付 CPU/内存/时间 | 构建不是免费的运维动作，是一次**可以打垮在线集群**的资源事件（§26.7） |

### 解剖卡八问：本篇答哪几问

| 八问 | 落在哪节 | 一句话答案 |
| --- | --- | --- |
| ① 承诺什么 | §26.3 | 承诺「以概率 p 返回真实 top-k 的一部分」；**不承诺**「返回的一定是最近邻」，也不承诺 p 是常数 |
| ② 数据长什么样 | §26.4–26.6 | 三种物理形态：分层图的**邻接表** / 簇心 + **倒排桶** / 码本 + **定长码** |
| ③ 一次读走哪条路 | §26.4、§26.8 | 图是「逐层贪心下降 + 层 0 best-first」；成本项是**随机访存**，不是 FLOPs |
| ④ 并发与一致 | §26.7 | 并发插入要拿图节点锁；构建与查询争 CPU 与内存带宽；删除靠墓碑而非物理删除 |
| ⑤ 扩展维度 | §26.9 | 四选一：**分片**（按簇/租户切图，跨片要 fan-out）／**副本**（只买 QPS，不买容量）／**垂直切**（量化 = 拿精度换内存）／**批处理摊薄**（粗筛 + 精排）。**图本身不可横向扩**：边是全局的，切开的图只能各自近似 |
| ⑥ 会在哪崩 | §26.1、§26.9 | 只算系统级：召回静默衰减（语义漂移）／构建期把在线集群拖垮（慢）／内存装不下 → OOMKill + 分片重放（满） |
| ⑦ 看哪几个指标 | §26.11 | 离线召回、visited/簇数、tombstone 比例、构建进度、常驻内存（每条带版本 + 开关） |
| ⑧ 换掉它的信号 | §26.9 | `N` < 10~100 万回暴力检索更快；要 100% 召回 / 精确 top-1 / 唯一性 → 换倒排或主库；过滤选择性 < 1% → 走 pre-filter（`→ comp/27`） |

> 架构与选型（几套索引怎么分层融合、多少条该上什么档位、单节点容量与成本）在 `→ architect/18`；本篇不重复那几张换挡表，只讲「换挡之后，机器内部会发生什么」。

## 26.3 ANN 的合约：召回率是产品参数，不是实现细节

### 合约的精确改写

暴力检索的合约是**确定性的**：扫完全部 `N` 条、比较完 `N·d` 次乘加，返回的 k 条在全库范围内就是最近的 k 条。ANN 把这一条**替换成**：

> **存在一个概率 p，使得返回的 k 条里，有 ⌈p·k⌉ 条落在真实 top-k 里。**
> `p` 不是实现细节，而是你必须写进接口契约、并且**必须定期复测**的量。记住它的量纲：`p` 不能脱离「测它的那批 query、那个数据量、那天」单独引用。

| 维度 | 精确检索（Flat / 暴力） | 近似检索（HNSW / IVF / PQ） |
| --- | --- | --- |
| 返回值保证 | 一定是最近邻 | **以概率 p** 命中真实 top-k 的一部分 |
| 单查复杂度 | `O(N·d)`，`N` 每涨 10 倍延迟涨 10 倍 | `O(ef_search · d)` 量级，与 `N` 只有对数关系 |
| 延迟随数据的形状 | 线性，可预测 | 近似平坦，但**召回随 `N` / 分布 / 墓碑缓慢下滑** |
| 失败的样子 | 慢到超时（显式） | **结果不对（静默）** |
| 该测的指标 | P99 / QPS | P99 / QPS **+ recall@k** |
| 内存 | 只装向量 | 向量 **+ 索引结构**（图边 / 码本 / 簇心） |

一条锋利的表述：**精确检索的成本显式地写在延迟里，ANN 的成本被挪进了「正确率」这个通常没人看的栏位。** 所以下面的三件事，凡是没落到工程上，就等于没买这份合约。

### ① 召回率怎么测：用暴力检索做 ground truth，采样 1,000 条查询

先算清「测一次」的价钱：`1,000 条查询 × 1e8 向量 × 768 维` = `1,000 × 1.54e11 FLOP = 1.54e14 FLOP`，按 100 GFLOPs 有效算 ≈ **1,540 s ≈ 26 分钟**；若被内存带宽卡住（`1,000 × 307 GB / 26 GB/s`）则要 **3.3 小时**。**这个价钱决定了召回评测必须离线跑批、周期跑，而不是每请求跑。**

再算清「1,000 条够不够」：`recall = 0.9` 时，`SE = sqrt(0.9 × 0.1 / 1,000) ≈ 0.0095`，95% 置信区间约 **±1.9 个百分点**。也就是说**1,000 条查询只能分辨「3 个百分点以上」的变化**；想稳定看到 1 个点的波动，需要 `n = 1.96² × 0.9 × 0.1 / 0.01² ≈ 3,500` 条。别用 100 条查询去证明「召回 0.95」——那个区间宽到 ±6 个百分点，什么都证明不了。

```python
# recall_eval.py —— 离线召回评测：用暴力检索造 ground truth，采样 1,000 条真实查询
import numpy as np

K, NQ = 10, 1000

def load_matrix(snapshot):                        # 从离线快照读，绝不拉在线库（会污染在线 P99）
    return snapshot["vectors"], snapshot["ids"]    # (N, d) float32，已 L2 归一化

def brute_force(q, mat, ids, k=K):                # O(N·d)：这就是 ground truth，唯一可信的答案
    sims = mat @ q                                # 归一化后内积 = cosine
    part = np.argpartition(-sims, k)[:k]
    return set(ids[i] for i in part[np.argsort(-sims[part])])

def run(client, queries, snapshot, k=K):
    mat, ids = load_matrix(snapshot)
    hits, visited = [], []
    for q in queries:
        truth = brute_force(q, mat, ids, k)
        r = client.search(q, k=k, with_meta=True)   # 返回 ids + 本次实际访问的节点/簇数
        hits.append(len(set(r.ids) & truth) / k)    # recall@k：逐条算再平均，不要合并成一个大集合
        visited.append(r.visited)
    p = float(np.mean(hits))
    se = (p * (1 - p) / len(hits)) ** 0.5           # 1,000 条 → 95% CI 约 ±2 个百分点
    return {"recall@k": round(p, 4), "ci95_pp": round(196 * se, 1),
            "visited_p50": int(np.percentile(visited, 50)),
            "visited_p99": int(np.percentile(visited, 99))}

# 三条纪律：
#  1) 评测集必须从【线上真实查询分布】采样，且与建索引用的数据无交集（否则就是数据泄漏，§26.10）
#  2) 每次改 ef_search / nprobe / 数据量 +20%、或换 embedding 模型，都必须重跑
#  3) 结果写进时序库（带时间戳 + 数据量 + 参数），召回曲线才是可观测对象（§26.11）
```

### ② 悬崖：召回-延迟曲线没有「够用点」，只有拐点

`ef_search`（或 `nprobe`）往下调时，延迟近似线性下降，**召回却是先缓后陡再崩**——曲线在前半段「掉得比延迟还快」，跨过某个点之后是断崖。这个形状是候选队列宽度与图连通性之间的乘积关系决定的，不是噪声。

```text
recall@10
 1.00 ┤                                      ●─────●─────●    ← 平台：继续加 w 只买延迟
      │                             ●
 0.95 ┤                     ●
      │              ●
 0.90 ┤        ●                                   ← 悬崖段：w 每减半，召回掉 8~15 个百分点
      │     ●                                        （区间随数据/维度变化，必须自己测）
 0.80 ┤   ●
      │ ●
 0.70 ┼──────────────────────────────────────────────────────► 单查 P99 (ms)
        1    2    4    8    16   32   64  128
                     ▲              ▲
              业务说"能接受"     工程说"才开始稳"
判据：曲线上没有"够用点"，只有业务能签字的 (召回, 延迟) 组合；
     而这只对【本次测试的数据集与分布】成立——数据一变，整条曲线会平移。
```

### ③ 召回率不是常数：两类漂移会让它悄悄掉

| 漂移类型 | 机制（落到物理形态上） | 现象 | 谁受影响最重 |
| --- | --- | --- | --- |
| **数据量增长** | 图直径 ≈ `log_M N` 变长、每层点数变密但入口点覆盖变差；同样的 `ef_search` 能探索的相对范围变小 | 延迟不变、召回单调下滑（事故一） | HNSW（`ef_search` 与 `N` 脱钩）、IVF（簇内点数涨、`nprobe` 覆盖比例下跌） |
| **数据分布漂移** | 新类目/新语种/新租户/新 embedding 模型 → 簇心失效、图的邻域结构不再代表真实近邻关系 | 老 query 尚可、新 query 崩；长尾最差 | IVF（`k-means` 中心过期，必须重训）、PQ（码本偏差，量化误差整体变大） |
| **墓碑堆积** | 删除只标记不物理移除 → 遍历要跳过死点，有效候选变少 | 召回缓降 + 内存不释放（§26.4） | HNSW / Qdrant 类实现 |

**所以「召回率」必须写成三件套**：`recall@k` + 数据量 + 评测日期。库里任何一条「我们召回是 0.95」的结论，缺了后两项就等于没测。

## 26.4 HNSW：分层图、`M` 与 `ef_search`

### 物理形态：每层一张邻接表，节点按指数分布抽样到上层

```text
Layer 2  (≈ 1/M² 的点)                ●───────────────●
                                       │               │
Layer 1  (≈ 1/M 的点)      ●───────────●───────●───────●
                            │           │       │       │
Layer 0  (全部 N 个点)  ●───●───●───●───●───●───●───●───●───●
                         每节点 ≤ M0 = 2M 条出边（层 0）；上层 ≤ M 条
                         入口点固定在最高层（构建时抽到的最高层节点）

一次查询：
  ① 从入口点出发，在当前层反复「走到比当前更近的邻居」，直到没有更近的
  ② 下降一层，重复①（上层是高速公路：跳得远、不精确）
  ③ 到层 0 后换成宽度 = ef_search 的 best-first 候选队列：
     出队一个 → 把它没访问过的邻居入队 → 直到队列空或已出队 ef_search 个
  ④ 从访问过的点里取最近的 k 个返回

单个向量在内存里占的字节（这就是「图要多少钱」的全部答案）：
  ┌──────── 向量本体 4d B（d=768 → 3,072 B），必需 ────────┐
  ┌─ 层 0 邻接表 M0 × 4 B（M=16 → 128 B）─┐
  ┌─ 上层邻接表 ≈ M × 4 B × 层数摊销 ≈ 64 B ─┐
  ┌─ 槽位/墓碑位/ID→偏移映射：+10%~40%（按实现）─┐
  ⇒ 一台机器装得下的向量数 ≈ 可用内存 / (4d + 150~400 B)
```

### 三个旋钮：它们改的不是「性能」，是三条不同的路径

| 旋钮 | 它改的是哪条路径 | 常见区间 | 代价落在谁身上 | 能否在线改 |
| --- | --- | --- | --- | --- |
| `M` | 层 0 出边上限 `M0 = 2M`，即图的**连通性预算** | 16~32 | **常驻内存**：`+8 B/向量`（`M0` 翻倍）；构建时每候选要多比 `M` 个邻居 → 构建时间近似线性 | 不能（要重建 + 改预算） |
| `ef_construction` | 插入时 best-first 的候选队列宽度 → 决定长尾点会不会成孤岛 | 100~200 | **构建时间**（近似线性）与构建期临时内存；不影响常驻 | 不能（要重建） |
| `ef_search` | 查询时层 0 的候选队列宽度 | 40~128（各实现默认值差异大，**以目标版本的参数表为准**） | **延迟**（近似线性）；内存零成本 | 能（按请求 / 按会话） |

> 三个旋钮性质完全不同：`M` 是架构旋钮，`ef_construction` 是发布旋钮，`ef_search` 是运行旋钮。三者混着调，最后一定会出现「为了提召回把 `ef_search` 调到 2,000，延迟涨 6 倍，而真正的瓶颈其实是过滤」（`→ comp/27`）。

### 三个崩点

**崩点一：`ef_search` 太小 → 召回悬崖。** 层 0 的 best-first 需要足够宽的队列才能跨过「局部最小」（最近邻的邻居恰好都远）。宽度 `w` 决定能连续探索多少候选，而图的直径随 `N` 增长——所以**同一个 `w` 在小库上够用、在大库上不够**（事故一）。信号是 `visited` 与 `ef_search` 的实际生效值，不是延迟。

**崩点二：删除靠墓碑 → 图退化。** 物理上不删向量、不删边，只把节点标为 deleted，遍历时跳过：

设墓碑比例 `t = 已删未重建节点 / 总节点`，四条后果全部可用 `t` 算出来：

- **有效候选只剩 `(1-t)`**：要拿到 k 条结果，得探索 `k/(1-t)` 个活节点（`t=30%` → 1.43 倍候选）。
- **空间放大 `1/(1-t)`**：内存不释放（`t=30%` → 实际存 1.43 份）。
- **图连通性受损**：原来靠该节点搭桥的近邻对，现在要多跳几跳才能相遇 → `visited` 上升、召回下降，而延迟只是略升。
- **更新 = 删 + 插**：同一条数据在图中留下多个墓碑，于是「写得越多、读得越慢」。

判据（工业界共识区间，具体阈值以目标实现的重建策略为准）：`t > 10%` 召回开始可测地下滑、安排重建；`t > 30%` 必须重建。

**崩点三：内存必须同时装下「向量 + 图」。** 这一条没有调优空间，只有三个出口：

| 出口 | 具体动作 | 换掉了什么 | 代价 |
| --- | --- | --- | --- |
| 分片 | 按租户/簇切图，每片独立 | 单机内存上限 | 查询 fan-out（跨片各取 top-k 再归并），且**切开的图不再是全局图** → 召回再掉一点 |
| 量化 | 向量本体验 PQ/SQ（§26.6） | 向量那 307 GB | 距离近似误差 → 必须 rerank |
| 上磁盘 | 图与向量放本地 NVMe / mmap | 内存 | **每次邻居跳变成一次随机 IO**，延迟从 µs 到几十~几百 µs，等于换了个物种 |

## 26.5 IVF：簇、`nprobe` 与重训

### 物理形态：先聚类，把全库切成 `nlist` 个桶

```text
建（离线，一次性）：
  ① 采样训练样本 → k-means → nlist 个簇心（每个簇心 = 一个 d 维向量）
  ② 把 N 个向量逐个分配到最近的簇心 → 每个簇一个倒排桶（桶内通常放 PQ 码，便于顺序扫）
     桶 c = [ (id0, code0), (id1, code1), ... ]   簇内点数 ≈ N / nlist

查：
  ① 算查询向量到 nlist 个簇心的距离：nlist × d 次乘加   ← nlist 大时这一步不可忽略
  ② 取最近的 nprobe 个簇 → 只扫这几桶
  ③ 桶内逐条算近似距离（PQ 查表）→ 取 top-k
  扫描量 = N × nprobe / nlist 条；延迟 ≈ ① 的固定成本 + ③ 的线性成本
```

### 崩点三件

| 崩点 | 机制 | 怎么观测 | 怎么修 |
| --- | --- | --- | --- |
| `nlist` 与 `N` 不匹配（太大） | 单簇点数过少 → k-means 方差大、簇心不准；同时 ① 的 `nlist × d` 成本变主项；训练成本随 `nlist` 线性涨 | 簇内点数分布的标准差、① 的耗时占比 | 降 `nlist` 或换 HNSW；`nlist` 不是「越大越细」 |
| `nlist` 与 `N` 不匹配（太小） | 单簇过大 → 在相同召回目标下 `nprobe` 要更大，扫描量 ∝ `N·nprobe/nlist` 反而更多 | 扫描量 / 簇内点数 p99 | 升 `nlist`，`N` 涨 10 倍时 `nlist` 至少要跟着涨 3 倍（√ 关系） |
| `nprobe` 太小 | 真实近邻落在没扫的簇里（簇边界附近的点最容易漏） | 召回曲线（§26.3 ②）；`nprobe/nlist` 的覆盖比例 | 调大 `nprobe` 或改用 HNSW 做粗筛 |
| **数据分布漂移** | 簇心是训练那一刻的数据分布快照；新数据只会被塞进老簇，簇心永不更新 → 簇边界越来越差 | 最大簇 / 平均簇 比值 > 3~5；新增数据与训练样本的分布差异 | **重训**（= 重建索引，要排期） |

**`nlist ≈ 4√N ~ 16√N` 的来源与限定**：这个区间来自 faiss 官方「如何选索引」指南的经验规则（用它的 demo 数据集测出来的，SIFT/GIST 一类、均匀分布、低维），**不是定律**。按它算 `N=1e8` → `nlist ≈ 4e4 ~ 1.6e5`，每簇 625~2,500 条。换数据集（高维、强聚簇、长尾）、换距离度量、换量化方式，最优 `nlist` 都会移动，**以实测为准**——因为目标函数是「给定召回目标下的最小扫描量」，这条曲线只能测。

顺手算清一个常被忽略的账：**k-means 训练本身的成本**。

顺手算清一个常被忽略的账：**k-means 训练本身的成本**。`训练 MAC ≈ 迭代数 × 训练样本数 × nlist × d`；代入 `nlist=1e5`、训练样本取 `256 × nlist = 2.56e7`、迭代 10、`d=768`，得 `10 × 2.56e7 × 1e5 × 768 ≈ 2.0e16 MAC ≈ 4e16 FLOP`，按 100 GFLOPs 有效算 ≈ `4e5 s ≈ 4.6 天`（单机 CPU 口径；GPU 或分层 k-means 能压到小时级）。

**这就是为什么「重训 IVF」是一件要排期的事，而不是一次热更新**——也解释了为什么漂移发生后团队往往选择「先扛着」：不是不知道，是排不起这个窗口。**量级结论**，假设清单：全量 k-means、无剪枝、无 GPU、无分层采样优化；换实现会在 1~2 个数量级内浮动。

## 26.6 量化：SQ、PQ 与「粗筛 + 精排」

内存是被**维度**吃掉的（`4d` 占向量内存的 90% 以上，图边只占 5%~10%），所以省内存的第一刀永远砍在向量本体上。

### PQ 的物理形态：把 d 维切成 m 段，每段查一个小码本

```text
d = 768 维原始向量（3,072 B）──► 切成 m = 96 段，每段 8 维
  [x0..x7] [x8..x15] ... [x760..x767]
     │         │              │
     ▼         ▼              ▼
  码本₁      码本₂          码本₉₆      ← 每个码本 256 个 8 维中心
     │         │              │            体积 = 256 × 8 × 4 B = 8 KB/码本
   byte₀     byte₁          byte₉₅          → 一条向量的码 = 96 B（原 3,072 B）

查询时用 ADC（非对称距离计算）：
  ① 先算查询向量的 96 段分别到各自码本 256 个中心的距离 → 一张 96 × 256 的表
     （2.5 万次运算，微秒级，每查建一次，可缓存复用）
  ② 每条候选的距离 = 96 次查表 + 累加 ≈ 30~100 ns，全程不碰原始向量
  ③ 代价：这个距离是"查表加和"的近似值 —— 误差恰好打乱 top-k 边界上的顺序
```

### 四档压缩：压缩比是算出来的，召回损失必须实测

压缩比全部来自「原 3,072 B/条」这一个分母（`d=768, float32`）。**召回损失只给区间，任何精确数字都必须由你自己的数据集测出来**——同一档 PQ 在不同数据上能差 10 个百分点。

| 档位 | 物理存法 | 每向量字节 | 压缩比 | 召回损失（区间，必须实测） | 要不要 rerank |
| --- | --- | --- | --- | --- | --- |
| 不量化 | float32 原文 | 3,072 B | 1× | 0（这是基准） | 不需要 |
| **SQ8**（int8 标量量化） | 每维 1 字节（按每维 min/max 线性映射） | 768 B | **4×** | 很小，通常 0.5~2 个百分点（维度高、量化区间被离群值撑坏时会更大） | 可选（多数场景不必） |
| **PQ96**（乘积量化，`m=96`） | 96 段 × 1 B 码 | 96 B | **32×**（`4d/m = 3072/96`） | 大：通常在 5~25 个百分点（`m` 越小损失越大） | **必须**（粗筛 top-100~1,000 再精排） |
| **二值**（1 bit/维） | 768 bit = 96 B + 海明距离 | 96 B | **32×** | 最大：只适合当**粗筛**，单独用基本不可用 | **必须**（海明筛 top-1,000 后精排） |

> 两个容易混的写法：有人把 PQ 的压缩比写成「压到 `1/m`」，那个分母其实是**「先用 int8 存成 `d` 字节」**的口径；相对 float32 的准确式子是 `4d/m` 字节。`m=96` 时是 32×，`m=d/4=192` 时是 16×，`m=d/8=96` 时是 32×——数字对不上通常是分母不同，评审时先问分母。

### 「粗筛 + 精排」的账：rerank 几乎免费，但它要占内存

算一遍就够：PQ 粗筛 top-200（每条 96 B）= `200 × 96 B = 19 KB` 内存流量，微秒级；精排 top-10 = `200 × 768 × 2 = 3.07e5 FLOP ≈ 3 µs`（int8 或 float32 都够用）。

**所以 rerank 的计算代价可以忽略，真正的代价是「原始向量必须还在」**：

| 存法 | 每向量 | 1 亿条 | 相对 340 GB 全量 |
| --- | --- | --- | --- |
| 只存 PQ96 码 | 96 B + 8 B(id) | 9.6 + 0.8 = 10.4 GB | 32× |
| **PQ96 + int8 原文（可精排）** | 96 + 768 + 8 = 872 B | 87 GB | **3.8×** |
| PQ96 + float32 原文 | 3,072 + 96 + 8 | 317 GB | 1.07×（等于没省） |

这就是事故三的完整教训：**PQ 省下的是「距离计算的精度」，不是「数据还在不在」**。真要用 PQ 上线，架构上必须同时回答两个问题：精排用什么存（int8 是最常见的折中）、以及精排这一步的延迟预算从哪出。

## 26.7 构建的代价：为什么大批量要「先灌后建」

### 建图不是插入，是「每个点都要和几十上百个已有的点比一遍」

HNSW 的插入 = 一次查询（找邻居）+ 补边。所以构建复杂度是 `O(N log N)` 次距离计算，而且每一次都可能是一次**随机内存访问**——图在内存里散布，指针乱跳。

| 影响构建时长的量 | 机制 | 量级 |
| --- | --- | --- |
| `N` | 每次插入都要走一遍图 | `O(N log N)` |
| `ef_construction` | 每个候选要多展开一层 | 近似线性（100 → 200 约 ×2） |
| `M` | 每个候选多比较 `M` 个邻居 | 近似线性；内存也涨 |
| `d` | 单次距离计算变长 | 线性（但**逐渐被随机访存淹没**） |
| **线程数** | 并发插入要拿节点锁、抢内存带宽 | **加速比 8~20×，绝不是线性** |

**「单线程 / 多线程差异巨大」这句话的物理原因**：建图是「一边改邻接表、一边读别人的邻接表」，粗粒度锁会串行化，细粒度锁会有写冲突与缓存行伪共享；再加上 307 GB 的向量池随便跳，内存带宽很快就成为共同瓶颈。**所以「32 线程 ≈ 32 倍」这个假设是错的，按 8~20 倍估才不被打脸。**

### 1 亿 × 768 维的构建时长量级推导

```text
距离计算总量 ≈ N × 每插入次数
  每插入 ≈ 3e3 次（ef_construction=200 的层 0 best-first 展开 + 上层下降；M=16）
  总量   = 1e8 × 3e3 = 3e11 次
单次成本 ≈ 0.3~0.6 µs
  = 768 维 SIMD 距离 30~100 ns（在 cache 里）
  + 图邻居随机跳 100~300 ns（3.07e11 B 的池子里乱跳，必然 cache miss）
  取 0.4 µs ⇒ 单核 3e11 × 0.4 µs = 1.2e5 s ≈ 33 小时
并行度：32 线程实测加速 8~20× ⇒ 33 h / (8~20) ≈ 1.7~4 小时（纯建图）
再加上：快照落地（307 GB / 2 GB/s ≈ 2.5 分钟）+ 校验 + 预热（§26.8）
⇒ 单分片 2~6 小时；8 分片串行 = 1~2 天；16 分片并行（每台 1 片）= 一个通宵到一天
口径校准：公开的大规模实测（1e8 级、32~64 核）落在「数小时 ~ 2 天」，与本推导同量级。
```

**量级结论**，假设清单：`M=16`、`ef_construction=200`、每插入 3e3 次距离计算、单次 0.4 µs、并行度 8~20×、无 IO 等待。改任一假设（尤其 `ef_construction` 与并行度）会在这条链上原样放大或缩小——**不要把它当承诺值引用**。

### 为什么必须「先灌数据，再建索引」

| 理由 | 机制 | 不这么做的后果 |
| --- | --- | --- |
| **资源争抢** | 构建期满核 + 随机访存 + 1.6 倍内存峰值 | 在线 P99 从 20 ms 到 900 ms，甚至 OOMKill（事故二） |
| **码本必须代表最终分布** | IVF/PQ 的训练是**一次性快照**：样本选错，簇心与码本永久偏差 | 边灌边建的索引，后半段数据的量化误差整体偏大；重训=整体重建 |
| **无断点续建** | HNSW 构建是内存中一次性完成的；中途失败**进度归零** | 一个 4 小时的构建做到 90% 崩了，等于 0 |
| **增量插入比批量建慢** | 批量建可以按「由粗到细」排插入顺序、可并行分片建、可先算好邻域 | 逐条插入的图质量更差（后插入的点容易成孤岛）、总时长更长 |
| **失败可整体重来** | 影子索引 + 别名切换 | 没有影子索引就只能原地改，改坏即停机（`→ architect/18`） |


## 26.8 三本账：内存、延迟与构建时长

目标量级：**`N = 1e8`、`d = 768`、`M = 16`（`M0 = 2M = 32`）、float32**。全部给乘法链，评审时要求对方能复述。

```text
① 空间账：向量是钱，图是零头，量化是第一刀
   向量本体 = 1e8 × 768 × 4 B = 3.072e11 B = 307 GB（GiB 口径 286）
   HNSW 图  = 1e8 × (M0 + 上层摊销 M) × 4 B = 1e8 × (32+16) × 4 = 19.2 GB
              若按「M0 × 2 × 4 B = 256 B/节点」的实现口径（定向边成对计）→ 25.6 GB
              区间 150~400 B/节点（M 16→32、定长数组 vs 压缩邻接表、墓碑位）⇒ 15~40 GB
   对齐/槽位/ID 映射 ×1.10 ⇒ 合计 ≈ 330~380 GB
   ⇒ 单机 512 GB 装得下但没余量（OS + page cache + 构建期峰值 ×1.6 会直接 OOMKill）
   ⇒ 8 分片 × 42~48 GB 是常见落点
   量化后（IVF-PQ96，不留图）：
     码本 = 96 × 256 × 8 × 4 B = 786 KB（可忽略）；PQ 码 1e8 × 96 B = 9.6 GB
     id 映射 1e8 × 8 B = 0.8 GB ⇒ ≈ 10.4 GB（相对 307 GB 是 29.5×）
   「粗筛+精排」变体：9.6 + 76.8(int8 原文) + 0.8 ≈ 87 GB（仍省 3.8×，且召回能救回来）

② 时间账：为什么"必须 ANN"是一道 5 个数量级的算术
   暴力：MAC = 1e8 × 768 = 7.68e10；FLOP = ×2 = 1.54e11 = 154 GFLOP
     算力约束：154 GFLOP / 100 GFLOPs = 1.54 s
     带宽约束：307 GB / 26 GB/s = 11.8 s   ← 真正的瓶颈：一次查询必须把全库搬一遍
   HNSW（ef_search=64）：距离计算 ≈ 500~2,000 次（层 0 扩展 + 上层下降）
     取 2,000 次 ⇒ 2e3 × 768 × 2 = 3.07e6 FLOP = 暴力的 1/50,000
     再加 ~2,000 次随机访存 × 100~300 ns = 0.2~0.6 ms ← HNSW 真正的时间去哪了
     实测口径：P99 1~5 ms，其中纯 FLOPs 只占 10%~20%，其余是访存与分支
   IVF-PQ（nlist=1e5, nprobe=1,000 ⇒ 扫 1e6 条候选）：
     原始向量：1e6 × 3,072 B = 3.07 GB / 26 GB/s = 118 ms
     PQ96    ：1e6 × 96 B = 96 MB / 26 GB/s = 3.7 ms + 查表 ⇒ 约 30×
     ⇒ "1 亿条、P99 十毫秒级"这件事，只在「结构 + 量化」都做对时才成立

③ 构建账：见 §26.7 的完整推导（3e11 次距离计算 → 单核 33 h → 32 线程 1.7~4 h → 分片串行 1~2 天）
   一句话：构建时长 ≈ (N × 3e3 × 0.4 µs) / 并行加速比，与「数据量 × 参数」同时线性

④ 召回悬崖账：w（ef_search）从 64 降到 16
   visited ≈ 1,500~3,000 → 400~800（÷4 左右）；距离计算 ~2,100 → ~500（÷4）
   延迟近似 ÷4；内存完全不变
   召回：落在曲线陡段，本例掉 10~30 个百分点（必须实测，见下表）
```

```python
# sizing.py —— 上面四本账的乘法链，改假设即复算（全部为量级结论，不是承诺值）
N, d, M, THREADS, SPEEDUP = 1e8, 768, 16, 32, 12      # 32 线程实测加速取 12×
M0 = 2 * M
vec_b   = N * d * 4                                    # 307.2e9
graph_b = N * (M0 + M) * 4                             # 19.2e9（M0×2×4 口径则为 25.6e9）
total_b = (vec_b + graph_b) * 1.10
pq_b    = N * (d // 8)                                 # PQ96：m = d/8 段 × 1 B
print(f"向量 {vec_b/1e9:.0f} GB | 图 {graph_b/1e9:.1f} GB | 合计 {total_b/1e9:.0f} GB")
print(f"PQ96 {pq_b/1e9:.1f} GB → 压缩 {vec_b/pq_b:.0f}× | 含图含id {(pq_b+N*8+graph_b)/1e9:.1f} GB")

flop = N * d * 2                                       # 暴力单查 FLOP
print(f"暴力单查 {flop/1e9:.0f} GFLOP → 100GFLOPs 下 {flop/1e11*1000:.0f} ms；"
      f"带宽口径 {vec_b/26e9*1000:.0f} ms")
ann = 2e3 * d * 2                                      # HNSW ef=64：约 2e3 次距离计算
print(f"HNSW 单查 {ann/1e6:.1f} MFLOP → 相对暴力 {flop/ann:.0f}×")

per_insert, per_ns = 3e3, 400                          # 每插入 3e3 次，单次 0.4 µs
single = N * per_insert * per_ns / 1e9 / 3600          # 单核小时数
print(f"构建：单核 {single:.0f} h → {THREADS} 线程 ÷{SPEEDUP} ≈ {single/SPEEDUP:.1f} h（纯建图）")
```

### 召回悬崖的量级（趋势与访问量，召回值必须自己测）

| `ef_search` | 访问节点（相对） | 距离计算次数（量级） | 延迟（相对） | 召回（只给趋势） |
| --- | --- | --- | --- | --- |
| 16 | 1.0 | ~500 | 1.0 | 曲线陡段下沿，本例掉 10~30 个百分点 |
| 32 | ~2.1 | ~1,000 | ~2 | 陡段中部，1 pp 延迟换 3~6 pp 召回 |
| 64 | ~4.3 | ~2,100 | ~4 | 接近平台，边际收益开始衰减 |
| 128 | ~8.5 | ~4,200 | ~8 | 平台段，每翻倍 <1 个百分点 |
| 256 | ~17 | ~8,000 | ~16 | 基本无收益，纯买延迟 |

**四本账合起来的一句话**：这个形态的空间被**维度**主导（307 GB 里 95% 是向量本体），时间被**随机访存**主导（不是 FLOPs），构建被 **`ef_construction` × 并行度**主导，而正确率被 **`ef_search` 与数据量之间的失衡**主导——四个数是四个不同的旋钮，**没有一个能同时改善两个**。

> **数字性质标注**：①②③④ 全部是**量级结论**，假设清单为「`d=768`、float32、`M=16`、`ef_construction=200`、每插入 3e3 次距离计算、单次 0.4 µs、有效算力 100 GFLOPs、内存带宽 26 GB/s、32 线程加速 12×」。换假设会在这条链上原样放大或缩小，**不得当承诺值引用**。

## 26.9 架构边界：ANN 什么时候不该用

| 需求 | ANN 能不能 | 为什么 | 靠什么绕过 |
| --- | --- | --- | --- |
| 「语义相似的前 k 条」 | **能**，这是它的存在理由 | 图/簇把 `N·d` 换成 `ef·d` | — |
| `N` < 10~100 万，且要精确 | **不该用** | 暴力检索 = `N×d×4 / 带宽`：100 万 × 768 × 4 B = 3.1 GB → 118 ms 带宽口径、15 ms 算力口径；10 万条只有 1.5 ms | 直接用 Flat：`recall = 1.0`，零构建、零调参、无墓碑 |
| 要 100% 召回（合规检索、去重、判重） | **不能** | 合约里 p 永远 < 1 | 倒排 + 精确过滤（`→ comp/21`）；或 Flat 兜底做二次校验 |
| 精确 top-1（唯一最近邻、阈值判定） | **不能** | 近似误差恰好落在第一名上 | Flat 或 `ef_search` 拉到极高（那就等于放弃 ANN 的收益） |
| 型号/订单号/错误码等**字面**匹配 | **不能** | 语义召回率往往 < 60%，且不可解释 | 倒排/前缀索引（`→ comp/21`），向量只做补充召回 |
| 过滤选择性 < 1% 的带条件检索 | **能但会崩** | 图遍历走进「邻居全被过滤掉」的死路 | pre-filter 或 separate-filter（`→ comp/27`） |
| 高频更新 / 每秒钟都在删改 | **能但不划算** | 更新 = 删 + 插，墓碑堆积 → 召回缓降 + 内存不释放 | 增量缓冲层 + 定期重建；不可变批次更合适（`→ architect/18`） |
| 需要事务、唯一约束、对账 | **不能** | 它是排序服务，不是数据库 | 权威源在关系库/对象存储，向量索引是派生视图 |

### 带过滤的 ANN：只给结论

**过滤越严，图遍历越容易走进死路**：`ef_search` 的宽度是 `w`，但如果邻居里 99% 被标量条件过滤掉，实际可用的候选只有 `0.01w`——等于把 `ef_search` 悄悄降了两个数量级，直接掉进 §26.3 的悬崖。这条路上「post-filter（先 ANN 后过滤）」在选择性 < 10% 时召回会崩，「pre-filter（先过滤再 ANN）」在选择性 < 1% 时退化成暴力扫描。**三种解法的判定表、混合检索的分层方式、以及过滤条件与分片键的关系，全部在 `→ comp/27`**；本篇只留这一句：**带过滤的 ANN，等价于「有效 `ef_search` = `ef_search` × 过滤通过率」，其余算术与 §26.4、§26.8 完全一样。**

## 26.10 踩坑清单（现象 → 根因 → 定位 → 修复 → 防复发）

| 现象 | 根因（指到物理形态） | 怎么定位 | 怎么修 | 怎么防复发 |
| --- | --- | --- | --- | --- |
| 延迟一路达标，业务说「搜得不对」 | 只测延迟不测召回；`ef_search` 与 `N` 脱钩（事故一） | 1,000 条 query 跑 ground truth（§26.3）；对比 `visited` 的历史基线 | 调 `ef_search` / `M` 后重建；重新签 `(召回, 延迟)` 组合 | 召回 SLO 与延迟 SLO **同看板**；数据量 +20% 自动触发评测 |
| 离线召回 0.96，上线只有 0.7 | **数据泄漏**：建索引的数据与评测 query 有交集，或 query 就是从库里抽的 | 按 `id` 排查 query 与索引的重叠；看 query 是否恰好是库内样本 | 评测集从线上真实日志采样，与索引数据按 id **物理隔离** | 评测流水线里断言「交集 = 0」，否则直接失败 |
| `ef_search` 用了默认值就上生产 | 默认值是「打断点用的」，不是「这个数据集的答案」 | `SHOW hnsw.ef_search` / 请求参数回读（§26.11） | 扫一遍曲线，取业务能签字的点，按请求/按场景下发 | 上线门禁：没提交「`ef_search` ↔ 召回 ↔ P99」三条数据的 PR 不许合 |
| 召回每周掉一点，重建就好 | 删除只标记不物理移除 → 墓碑堆积、图退化 | 墓碑比例、`visited` 上升、`k/(1-t)` 需要更多候选 | 重建索引（`t > 30%` 必须），或实现定期重写 | 把墓碑比例做成告警（>10% 预警）；写路径尽量批量化，减少「删+插」 |
| 新类目/新语种的 query 召回崩了，老的还好 | 分布漂移：IVF 簇心与 PQ 码本是训练那天的快照 | 按类目/时长切分评测集，看分桶召回；簇内点数分布 | 重训 + 重建（要排期，成本见 §26.5） | 每月抽样比对「新数据 vs 训练样本」的分布；embedding 模型升级 = 强制重建 |
| 内存省了 8 倍，但搜索质量不可用 | 量化后没 rerank，把粗筛结果当答案（事故三） | 对比「量化索引召回」与「量化 + rerank 召回」两条曲线 | 加 rerank（top-100~1,000 精排），用 int8 原文兜底 | 量化上线必须带「rerank 开关 + 两条召回曲线」，只有一条曲线的评审不通过 |
| 发布窗口建索引，在线 P99 尖刺 900 ms | 构建与查询抢 CPU / 内存带宽；峰值内存 1.6 倍（事故二） | 构建期 RSS 曲线 + 节点 `load` + 在线 P99 同图叠加 | 构建线程 ≤ 物理核 − 在线余量；错峰；先灌后建 | 把构建当**资源变更**走变更流程，与查询容量预算一起算 |
| 换成本地 embedding 后「结果全错」，召回 ~0 | 距离度量与归一化不一致：索引按 L2 建、查询按 cosine 算，或一边归一化一边没有 | 取同一条向量自比：距离应为 0 / 相似度应为 1；比对索引 `metric_type` 与查询端算子 | 统一度量 + 统一归一化，重建索引 | 把 `metric` 与「是否归一化」写进索引元数据，启动时校验并拒跑 |

## 26.11 观测：指标、拐点与告警

**纪律**：每条都要带**版本 + 开关**。四个实现的指标体系完全不同——`faiss` 是**库**、本身不暴露任何指标（只能在自己 wrapper 里埋点）；`pgvector` 是 PG 扩展、观测落在 PG 的统计视图与 GUC 上；`Milvus`、`Qdrant` 各自暴露 Prometheus 端点但指标名随版本变化。**下面凡是标「以目标版本为准」的，都不许照抄——去 `/metrics` 或导出器里核对字段名。**

| 观测项 | 为什么它先报警（拐点怎么来） | 拐点 | 版本 + 开关前提 |
| --- | --- | --- | --- |
| **离线召回 `recall@k`**（对暴力 ground truth） | 唯一能反映「结果对不对」的指标；延迟面板对它完全无感 | 跌破目标 −2 pp，或 7 天内单调下滑 >3 pp | 不自带：faiss 无指标；Milvus / Qdrant / pgvector 都要**自己跑离线评测任务**并把结果上报为 gauge。评测脚本见 §26.3 |
| **每次查询访问的节点 / 簇数**（`visited`） | 悬崖前置信号：`ef_search` 被改小 → `visited` 掉；墓碑/图退化 → `visited` 暴涨而召回掉 | 与 7 日基线偏差 > 30% | faiss 需 wrapper 埋点；pgvector 只能从 `EXPLAIN (ANALYZE)` 的 rows 间接看（**以目标版本为准**）；Milvus/Qdrant 以各自 `/metrics` 输出为准 |
| **`ef_search` / `nprobe` 实际生效值** | 配置漂移：应用侧 `SET` 没落到这个连接、客户端多版本互相覆盖 | 与期望值不等（哪怕差一次） | pgvector：`SHOW hnsw.ef_search`（会话级 GUC，**0.5+ 才有 HNSW**，具体参数名以目标版本为准）；Milvus：search params 里的 `ef`/`nprobe`；Qdrant：请求参数 `hnsw_ef` / `params`。**三者名称差异大，以目标版本文档为准** |
| **索引构建进度与耗时** | 构建超时 = 下一次事故；HNSW **无断点续建**，进度归零 | 已用时间 > 预算窗口 × 0.7 | pgvector：`pg_stat_progress_create_index`（PG 12+）；Milvus：index task 状态（走控制面 API，以目标版本为准）；faiss：只能自己打日志（无内置进度） |
| **索引常驻内存** | 「向量 + 图」装不下就是 OOMKill + 分片重放 | 常驻 > 节点内存 × 70%（构建期另留 1.6 倍峰值） | 一律用容器 `working_set` 采（库自报的「索引大小」各版本口径不一，含不含图/码本/墓碑经常不清楚） |
| **tombstone 比例** | 图退化的直接量，也是「内存不释放」的证据 | >10% 预警；>30% 强制重建 | HNSW 删除是各实现自己的事（Qdrant 走删除位图 + optimizer 定期重建；Milvus 走 compact 任务）——**口径以目标版本为准**，别跨版本比 |
| **P99 / QPS** | 延迟账，但必须按「召回达标前提」读 | P99 破 SLO，或 QPS 掉 >20%（同参数下） | 网关/OTel 层统一采最可靠（比库自带计数器一致），且能与召回曲线对齐时间轴 |

因果链值得单独记一句：**`visited` 偏离基线 → 召回掉（这一步没人看）→ P99 反而变好（有人看，还以为优化了）→ 客诉**。构建期是另一条链：**RSS 涨 → P99 尖刺 → OOMKill → 分片重放 → P99 再涨**。

```yaml
  rules:

  - alert: AnnRecallDropped
```

## 26.12 一页速记

| 问题 | 答案 |
| --- | --- |
| ANN 的合约是什么 | 把「返回的一定是最近邻」换成「以概率 p 返回真实 top-k 的一部分」；p 是产品参数，必须写进接口、周期复测 |
| 召回率怎么测 | 暴力检索造 ground truth + 采样 1,000 条真实 query；1,000 条的分辨力约 ±2 pp，想看 1 pp 要 3,500 条 |
| 为什么延迟达标不等于检索正确 | 召回随 `N`、分布漂移、墓碑、`ef_search` 变，而这四个量都不在延迟面板上 |
| HNSW 的数据长什么样 | 分层邻接表：层 0 每点 ≤ `M0 = 2M` 条出边，往上按 1/M 抽样；查询 = 逐层贪心下降 + 层 0 宽度 `ef_search` 的 best-first |
| HNSW 内存怎么算 | `N × (4d + 150~400 B)`；`d=768, M=16` ⇒ 307 GB 向量 + 19~26 GB 图 ⇒ ×1.10 ≈ 330~380 GB |
| HNSW 三个崩点 | `ef_search` 太小（悬崖）；墓碑堆积（图退化 + 内存不释放）；内存装不下（只能分片/量化/上磁盘） |
| IVF 怎么建怎么查 | k-means 出 `nlist` 个簇心 → 每簇一个倒排桶；查只扫最近 `nprobe` 簇，扫描量 = `N·nprobe/nlist` |
| `nlist` 怎么定 | 经验区间 `4√N ~ 16√N`（faiss 指南，demo 数据集口径）⇒ `1e8` 时 4 万~16 万；**以实测为准**，且训练成本 ∝ `nlist×样本×迭代` |
| 量化的四档 | 不量化 1×／SQ8 4×／PQ96 32×／二值 32×；PQ 与二值**必须** rerank，SQ8 多数可省 |
| 为什么「先灌后建」 | 构建是满核 + 随机访存 + 1.6 倍内存的资源事件；IVF/PQ 码本必须代表最终分布；且 HNSW 无断点续建 |
| 1 亿 × 768 的构建时长 | `1e8 × 3e3 × 0.4 µs ≈ 33 h/单核` ÷ 加速比(8~20) ≈ 1.7~4 h（纯建图）⇒ 分片串行 1~2 天 |
| 一条纪律 | **召回 SLO 与延迟 SLO 同看板、同一次评审；量化必须带 rerank 与两条召回曲线** |

<details>
<summary>看答案</summary>

顺序：① 立刻用 1,000 条线上真实 query 跑离线 ground truth，算出当前 `recall@10`（这是唯一能确认「不准」的量）；② 查 `ef_search` 的**实际生效值**（不是配置文件里的值）；③ 查数据量曲线与墓碑比例；④ 查评测集是否与索引数据有交集（否则你在测数据泄漏）。

延迟面板看不出来的原因是物理的：`ef_search` 固定 ⇒ 层 0 的候选队列宽度固定 ⇒ **距离计算次数大致不变** ⇒ CPU、内存、延迟全部稳定。变的是「这个宽度能覆盖多大范围的图」——图直径随 `N` 增长而变长，同样宽度能跳的步数相对变少，于是召回单调下滑。所以这是一个**结构上不可能被延迟指标发现**的失效（§26.1 事故一）。

</details>

**Q2**：`N = 1e8`、`d = 768`、float32，为什么说「装进内存」这件事是被维度决定的，而不是被图结构决定的？给出两条定量证据。

<details>
<summary>看答案</summary>

证据一（占比）：向量本体 `1e8 × 768 × 4 B = 307 GB`；HNSW 图 `1e8 × (32+16) × 4 B ≈ 19 GB`（`M=16`）。图只占 6%，**把 `M` 从 16 调到 32 只多 19 GB（+6%），却要重建、且构建时间近似翻倍**——这是性价比最差的一刀。

证据二（杠杆）：`SQ8` 把 307 GB 直接变 76.8 GB（4×），`PQ96` 变 9.6 GB（32×）。同样一笔内存，砍维度/量化能省的数量级是「10~30 倍」，动 `M` 只能省「几个百分点」。

推论：省内存的顺序是**先量化 → 再降维 → 最后才动 M**；而动 `ef_search` 对内存是零影响（§26.8 ②）。

</details>

**Q3**：团队用 `nlist = 1e5` 建了 IVF，一年后数据从 3,000 万涨到 2 亿，`nprobe` 没动，为什么召回掉了、而且扫描量还变大了？该怎么修，修的时候要付什么代价？

<details>
<summary>看答案</summary>

簇数没变而数据涨了 6.7 倍 ⇒ 每簇点数从 300 涨到 2,000。召回掉的机制是：真实近邻落在「没扫的簇」里的概率上升（簇边界更粗糙），而 `nprobe` 覆盖的**簇比例**没变但每簇更大、桶内近似排名更不可靠。

扫描量变大是因为 `扫描量 = N × nprobe/nlist`：`nlist` 不动、`N` 涨 6.7 倍 ⇒ 扫描量也涨 6.7 倍；想要同样的覆盖比例，`nprobe` 还得跟着涨，于是再乘一次。

修：`nlist` 按 `4√N~16√N` 提到 3 万→（`√2e8 ≈ 1.4e4`）5.6 万~22 万，**必须重建**。代价有两笔：① 重建窗口（训练 + 全量重灌，见 §26.7）；② k-means 训练成本 ∝ `nlist × 样本 × 迭代`，`nlist` 涨 5 倍，训练时间大致涨 5 倍（§26.5 的 4e16 FLOP 量级推导）——所以这件事要排期，而不是随手改个参数。

</details>

**Q4**：为什么 PQ 把内存压到 1/32 之后，反而必须**多存一份** int8 原文？那到底还省了多少？

<details>
<summary>看答案</summary>

PQ 的距离是「96 次查表 + 累加」的近似值，误差专门打乱 top-k **边界上**的顺序：真正最近的 200 条大概率都在候选里，但名次是错的。不做 rerank 就等于把粗筛当答案（§26.1 事故三，CTR −11%）。rerank 需要原始（或近似原始）向量参与精确距离计算，所以必须留一份原文。

省了多少（`N=1e8`）：只存 PQ96 = `96 B + 8 B(id) = 10.4 GB`（32×）；PQ96 + int8 原文 = `96 + 768 + 8 = 872 B` ⇒ 87 GB，**相对 340 GB 全量仍省 3.8 倍**。也就是说「PQ 的 32×」和「实际能拿到的 3.8×」之间差的那 8 倍，就是 rerank 的价钱。想连这份也省掉，只能接受召回明显下滑，或改用「SQ8 + HNSW」这种 4× 但几乎不损召回的档位。

</details>

**Q5**：发布窗口要重建 1.4 亿向量的 HNSW，计划 6 小时。请列出至少四条必须写在方案里的约束，并说明每条不写会发生什么。

<details>
<summary>看答案</summary>

① **构建线程数 ≤ 物理核 − 在线余量**：不写就是事故二——在线 P99 从 20 ms 到 900 ms。
② **内存峰值 = 常驻 × 1.6 并做预检**：不写就是 OOMKill → 分片被踢到别的节点重放 → 与剩余节点的构建叠加，雪崩。
③ **HNSW 无断点续建 ⇒ 必须有影子索引 + 别名切换，且失败可整体重来**：不写就是「做到 90% 崩了等于 0」。
④ **构建时长按 `(N × 3e3 × 0.4 µs) / 加速比` 复算，并留 2~3 倍余量**：不写就是「6 小时窗口」的假设从来没被验算过（§26.7 的推导给出单分片 2~6 h）。

⑤（附加）**码本/参数必须与最终数据分布一致 ⇒ 先灌完数据再建**：不写就是后半段数据量化误差整体偏大，且重训=再重建一次。
⑥（附加）**构建期间在线服务的降级预案**（只走倒排 / 只返回缓存），以及构建结束后必须重跑一次 1,000 条 query 的召回评测再切流量——否则你会切上一个「更准的图、更差的 `ef_search`」。

</details>
