## 40.1 引子：三起「连接看起来没问题，请求就是慢 / 打不过去」的事故

RPC 层的事故有一个共同形状：**连接数是绿的、端口没满、CPU 也不高**。它表现成「P99 突然从 8 ms 变成 900 ms」「某个接口超时但下游日志里根本没收到」「发布之后错误率自己好了」。根因往往不在业务代码，而在三件事的接缝上：**一条连接上放了多少流、流控窗口给了多大、失败之后重试了几次**。

### 事故一：连接池 × 实例数 = 端口耗尽，重试把「慢」变成「连不上」

某交易系统，订单服务 500 个 Pod，每个 Pod 到库存服务的连接池上限 200。库存服务 40 个实例，客户端用短连接（每次请求新建 TCP），平均 QPS 8,000，P99 延迟 40 ms。

| 时刻 | 事件 | 现象 |
| --- | --- | --- |
| 10:00 | 库存服务一次 GC 把 P99 从 40 ms 抬到 300 ms | 客户端并发连接数从 500 × 200 的池上限附近继续上涨 |
| 10:03 | 客户端超时 1 s，开始重试；重试请求又占新连接 | 连接建立速率从 8,000/s 涨到 26,000/s |
| 10:05 | 客户端所在节点的 `ip_local_port_range` 耗尽，`connect()` 返回 `EADDRNOTAVAIL` | 业务侧看到的是「连接超时」，不是「下游 5xx」 |
| 10:08 | 运维扩容库存服务到 60 个实例 | **更糟**：每个客户端要连的地址更多，端口消耗更快 |
| 10:20 | 把短连接改成 keepalive 池 + 限制重试次数 | 连接建立速率回到 8,000/s，P99 恢复 |

这一起的教训不是「池越大越好」，而是：**连接是一种有上限的资源，而重试是它的乘数**。池上限 200 的意思是「最多同时 200 条」，不是「每秒可以建 200 条」；短连接形态下，后者才是端口的真实消耗。

### 事故二：HTTP/2 单连接上，一个 20 MB 响应把小请求全堵住

某搜索网关用 gRPC 连后端，客户端为了「省连接」把 `grpc.WithMaxConcurrentStreams` 之外的所有连接都收成 1 条（每个后端地址 1 条 HTTP/2 连接）。平时 P99 8 ms；一次运营后台拉「全量商品快照」，单响应 20 MB。

| 时刻 | 事件 | 小请求 P99 |
| --- | --- | --- |
| 14:00 | 快照请求开始，服务端分块写 20 MB | 8 ms |
| 14:00:02 | 连接级流控窗口被快照占满，后续 DATA 帧排队 | 40 ms |
| 14:00:05 | 同一连接上的搜索请求只能等窗口更新 | 900 ms |
| 14:00:12 | 客户端把超时从 1 s 调到 3 s | 900 ms（超时没解决排队） |
| 14:01 | 把大响应接口拆到独立连接池 / 改成流式分页 | 小请求回到 9 ms |

HTTP/2 的「多路复用」只保证**帧可以交错**，不保证**带宽可以平分**。一条连接上的流控窗口是共享的；大响应把窗口吃满，小请求的 HEADERS 能过去，DATA 却要排队。

### 事故三：`retries=3` 把 20% 的超时放大成 1.6 倍流量

某订单创建接口，Dubbo 配置 `retries=2`、`timeout=1000ms`。下游在高峰期有 20% 的请求超过 1 s（不是失败，只是慢）。

| 轮次 | 到达下游的请求 | 说明 |
| --- | --- | --- |
| 原始 | 10,000/s | 业务真实请求 |
| 第 1 次重试 | +2,000/s | 20% 超时的那部分 |
| 第 2 次重试 | +400/s | 重试里又有 20% 超时 |
| 合计 | **12,400/s** | 下游负载 +24%，而它本来就已经在慢 |

如果重试没有退避、没有预算，且所有客户端在同一时刻超时，实际到达会是「同一秒内 10,000 + 2,000 + 400」的脉冲；下游的队列深度瞬间翻倍，慢的变得更慢——**重试不是「再试一次」，是「给已经过载的系统再加一份负载」**。

> 🩸 三起事故的共同点：**没有一处业务逻辑写错**。① 是连接资源的乘数；② 是共享流控窗口；③ 是重试的乘数。它们都发生在「连接复用」这个抽象漏出来的地方。

## 40.2 一句话定位与唯一真问题

**RPC 的本质不是「像调本地方法一样调远程」，而是「把一次请求编码成字节，放进一条有容量上限的连接，再等一个可能永远不来的响应」。**

> **唯一真问题：一条 TCP 上复用并发流，把「连接数」问题换成了「流控 + 队头阻塞 + 重试放大」问题。**

这句话可以拆成三句可验证的推论：

1. **复用连接省掉的是握手与端口，不是带宽**：一条 1 Gbps 的连接不会因为跑 100 个流就变成 100 Gbps；流越多，每个流分到的窗口越小。
2. **复用的粒度决定故障的粒度**：HTTP/1.1 的 keepalive 是「一条连接一次一个请求」，HTTP/2 是「一条连接多个流」，Dubbo 是「一条连接多个请求 id」——粒度越细，单流故障越容易波及同连接上的其他流。
3. **重试是复用的反向操作**：复用把 N 个请求压到 1 条连接上，重试把它们重新放大成 N × attempts 个请求；两者必须在同一个预算里算。

### 解剖卡八问（RPC 版）

| # | 问题 | 本篇的回答（一句话） |
| --- | --- | --- |
| ① | 物理形态 | 一条 TCP + 帧/流（HTTP/2）或请求 id（Dubbo）+ 连接池 |
| ② | 读/写链路 | 序列化 → 帧化 → 流控窗口 → 内核 socket → 对端拆帧 → 反序列化 |
| ③ | 并发模型 | 每连接多流；流的并发上限由 `MAX_CONCURRENT_STREAMS` 与窗口共同决定 |
| ④ | 一致性/语义 | 至多一次、至少一次、恰好一次取决于超时 + 重试 + 幂等键，不在 RPC 本身 |
| ⑤ | 扩展维度 | 加连接（水平）、加流（单连接内）、加实例（服务端）；三者代价不同 |
| ⑥ | 系统级失效 | 慢（流控排队）、满（端口/fd/窗口）、脑裂（注册表旧视图）、假活（连接在但流不通）、语义漂移（超时重试导致重复） |
| ⑦ | 三本账 | 连接内存、并发流上限、重试放大 |
| ⑧ | 换零件信号 | 单连接流控等待成为 P99 主项、端口/fd 成为瓶颈、重试率 > 5% |

## 40.3 连接复用的谱系：从「每请求一条」到「一条多流」

### 五种形态

| 形态 | 一条连接上同时几个请求 | 握手成本 | 队头阻塞 | 典型实现 |
| --- | --- | --- | --- | --- |
| **短连接** | 1 | 每请求 1 次 TCP + TLS | 无（每条独立） | 早期 HTTP、`Connection: close` |
| **keepalive 池（HTTP/1.1）** | 1（pipelining 理论上多，实际几乎不用） | 摊到 N 个请求 | 有（同连接串行） | Nginx upstream keepalive、HttpClient 池 |
| **HTTP/2 多路复用** | 多（stream） | 一条连接一次 | 有（TCP 层丢包 + 流控窗口） | gRPC、Envoy、Nginx `http2` |
| **gRPC 流式** | 多（stream，且可双向） | 同上 | 同上 + 应用层消息顺序 | gRPC unary/server/client/bidi stream |
| **Dubbo 单连接多路复用** | 多（request id） | 一条连接一次 | 有（TCP 层 + 线程池） | Dubbo `connections=1` 默认 |

```text
短连接（每请求一条）
  req1 ──TCP+TLS──► 处理 ──► 关闭
  req2 ──TCP+TLS──► 处理 ──► 关闭        ← 端口与握手成本 × N

keepalive 池（每连接串行）
  conn1: req1 ──► resp1 ──► req2 ──► resp2
  conn2: req3 ──► resp3
  conn3: req4 ──► resp4                 ← 连接数 = 并发请求数

HTTP/2 / gRPC（一条连接多流）
  conn1: ├─ stream1(HEADERS/DATA) ─┤
         ├─ stream3(HEADERS) ──────┤      ← 帧交错，但共享连接窗口
         └─ stream5(DATA) ─────────┘
```

### 为什么不是「一条连接越少越好」

一条连接能承载的并发流有上限：服务端 `MAX_CONCURRENT_STREAMS`（常见 100–1,000，取决于实现）、连接级流控窗口（默认 65,535 B，通常调到 MB 级）、以及单条 TCP 的拥塞窗口。把 10,000 QPS、P99 50 ms 的流量压到 1 条连接上，需要的并发流 = `QPS × 延迟 = 500`；如果服务端只允许 100 条流，剩下 400 个请求只能排队。

**正确的算式是：**

```text
所需并发流 ≈ QPS × P99 延迟
连接数 ≈ ceil(所需并发流 ÷ 每连接流上限) × 安全系数
```

安全系数通常取 1.5–2，用于覆盖突发与单连接故障；不是越大越好，因为每条连接都要占 fd、内存与 TLS 状态。

## 40.4 gRPC / HTTP/2 的物理形态

### 帧、流与连接

HTTP/2 把一条 TCP 切成三种东西：

- **连接（connection）**：一条 TCP + TLS，所有流共享。
- **流（stream）**：一个请求/响应，奇数 id 由客户端发起，偶数保留。
- **帧（frame）**：9 字节头 + 负载；类型包括 `HEADERS`、`DATA`、`SETTINGS`、`WINDOW_UPDATE`、`RST_STREAM`、`PING`、`GOAWAY`。

```text
HTTP/2 连接内部

  TCP/TLS
   ├── stream 1  HEADERS ── DATA ── DATA ── (END_STREAM)
   ├── stream 3  HEADERS ── DATA ── (END_STREAM)
   └── stream 5  HEADERS ── RST_STREAM（取消）

  流控两层：
    连接窗口：所有 stream 的 DATA 之和不能超过它
    流窗口：  单个 stream 的 DATA 不能超过它
  窗口更新：接收方发 WINDOW_UPDATE，发送方才能继续发
```

### 六个必须知道的旋钮

| 旋钮 | 它控制什么 | 调小的后果 | 调大的后果 |
| --- | --- | --- | --- |
| `MAX_CONCURRENT_STREAMS` | 单连接同时活跃的流数 | 请求排队，P99 抬升 | 内存与调度压力上升 |
| 连接级流控窗口 | 所有流共享的未确认字节 | 大响应把窗口吃满，小请求被拖 | 接收端内存上升 |
| 流级流控窗口 | 单个流的未确认字节 | 大消息吞吐下降 | 单流可独占更多内存 |
| `MAX_FRAME_SIZE` | 单个 DATA 帧大小 | 帧多、开销大 | 单帧占用大，延迟抖动 |
| keepalive ping 间隔 | 探测连接是否假活 | 假活发现慢 | 心跳流量上升 |
| `GOAWAY` / drain 超时 | 优雅关闭时给在途流多久 | 在途请求被 reset | 旧连接拖住发布 |

### 一个容易忽略的事实：HTTP/2 没有消灭 TCP 队头阻塞

HTTP/2 解决的是**应用层**的队头阻塞（一个慢响应不再挡住后面的请求），但所有 stream 仍然跑在同一条 TCP 上。一旦有一个 TCP 段丢失，内核的重传会阻塞**整个连接**的字节流——所有 stream 一起等。这就是为什么「一条连接多流」在弱网/跨 AZ 场景下，反而不如「多条连接」稳。

**判定**：同机房、低丢包、请求大小均匀 → 单连接多流更省；跨地域、丢包率 > 0.1%、有大响应 → 按请求类型分池，甚至回到多连接。

## 40.5 Dubbo 的物理形态：单连接 + 请求 id

Dubbo 的默认形态与 gRPC 不同：**consumer 到每个 provider 默认只建一条长连接**（`connections=1`），所有请求复用这条连接，用自增的请求 id 做多路复用；响应按 id 匹配回对应的 Future。

| 维度 | gRPC / HTTP/2 | Dubbo（默认） |
| --- | --- | --- |
| 复用单位 | stream（有独立流控） | 请求 id（无独立流控） |
| 流控 | 连接级 + 流级窗口 | 主要靠 TCP 与线程池队列 |
| 多路复用 | 协议内建 | 协议内建（id 关联） |
| 典型序列化 | protobuf | hessian2 / protobuf / json |
| 连接数 | 每目标地址 1 条（可配多） | 每 provider 1 条（`connections` 可调） |
| 超时/重试 | deadline + retry policy | `timeout` + `retries`（集群容错） |
| 队头阻塞 | TCP 层 + 流控窗口 | TCP 层 + 线程池队列 |
| 适用 | 多语言、流式、云原生 | Java 生态、内部服务、成熟治理 |

```java
// Dubbo consumer 侧的关键配置（语义示意，具体默认值以目标版本文档为准）
@Reference(
    timeout = 1000,          // 单次调用超时；不是总预算
    retries = 2,             // 失败重试次数；下游慢时会放大流量
    cluster = "failover",    // 失败切换
    connections = 1,         // 到每个 provider 的连接数
    loadbalance = "leastactive"
)
private InventoryService inventoryService;
```

**Dubbo 的隐藏瓶颈是线程池**：请求在多路复用连接上回来之后，要在 consumer 的线程池里执行回调/业务；provider 侧也有业务线程池。连接数很少，但线程池队列可能很长——**「连接没满」不等于「没有排队」**。

---

### Dubbo 的线程池账：连接没满，线程池可能已经满了

Dubbo 的 provider 侧默认用固定大小线程池处理请求；consumer 侧的回调也要占线程。连接只有一条，但请求在这条连接上回来之后，仍然要排队进线程池。于是会出现「连接空闲、线程池队列很长」的假象。

| 项 | 公式 | 例（QPS 8,000、P99 50 ms） |
| --- | --- | --- |
| 需要的并发线程 | `QPS × 处理时长` | 8,000 × 0.05 = **400** |
| 线程池大小 | 通常 200（默认量级，以目标版本为准） | 200 < 400 ⇒ **排队** |
| 队列长度 | `到达速率 × (1/服务速率 − 1/到达速率)` 的稳态近似 | 队列会持续增长，直到超时 |
| 现象 | 连接数 1、CPU 不高、P99 飙升 | 误判为「网络问题」 |

**修法不是加连接，而是加线程/异步化/限流**：连接复用只解决了传输层，不解决执行层的并发。把阻塞调用放到独立线程池、或改成 CompletableFuture 异步，才是对症的。

## 40.6 超时与重试：把「再试一次」算成一笔流量账

### 三个时间概念不要混

| 概念 | 含义 | 典型配置 | 错了会怎样 |
| --- | --- | --- | --- |
| 连接超时 | 建连/握手最长等多久 | 200–1,000 ms | 太短：网络抖动就失败；太长：故障时线程被占住 |
| 单次请求超时 | 一次 RPC 从发出到响应的上限 | 与下游 P99 挂钩 | 太短：正常慢请求被重试；太长：故障发现慢 |
| 总预算（deadline） | 整条调用链允许花多久 | 由入口倒推 | 不传：每层都按自己的超时等，尾部叠加 |

**deadline 必须向下传播**：入口给 800 ms，网关扣掉 50 ms，服务 A 给 B 600 ms，B 给 C 400 ms；否则 C 还在等，A 已经超时重试，C 做了两遍。

### 重试放大公式

设原始 QPS 为 `Q`，单次失败/超时概率为 `p`，最多重试 `r` 次，且每次重试的失败概率仍为 `p`（最坏情况，下游没恢复）：

```text
期望到达下游的请求 = Q × (1 + p + p² + … + p^r)
                  = Q × (1 − p^(r+1)) / (1 − p)     （p < 1）

同步重试的瞬时脉冲 = Q × (r + 1)                    （所有客户端同时超时时）
```

| p | r=0 | r=1 | r=2 | r=3 |
| --- | --- | --- | --- | --- |
| 1% | 1.00× | 1.01× | 1.01× | 1.01× |
| 10% | 1.00× | 1.10× | 1.11× | 1.11× |
| 20% | 1.00× | 1.20× | 1.24× | 1.25× |
| 50% | 1.00× | 1.50× | 1.75× | 1.88× |

**但同步重试的脉冲是另一本账**：如果 20% 的请求在同一秒超时，且客户端立刻重试，那么这一秒到达下游的是 `Q + 0.2Q + 0.04Q = 1.24Q`；如果重试没有抖动，所有客户端会在同一毫秒一起重试，形成 `1.24Q` 的尖峰。**平均放大只有 1.24 倍，瞬时尖峰却可能是 3 倍**——这就是「重试把下游打垮」的真实机制。

### 三条纪律

1. **只对可重试错误重试**：连接失败、明确的 5xx、超时（且幂等）；不要对参数错误、鉴权失败重试。
2. **重试必须有预算**：`retry budget`（例如成功请求的 10%）+ 指数退避 + 抖动；预算耗尽就快速失败。
3. **重试必须配幂等**：至少一次 + 重试 = 可能重复；用业务唯一键/去重表兜底（→ [eng/24 投递语义](../eng/24-delivery-semantics.md)）。

## 40.7 连接池与负载均衡：池大小不是拍脑袋

### 池大小的算式

```text
并发请求数 C ≈ QPS × P99 延迟（Little 定律）
每连接可承载的并发流 S = min(MAX_CONCURRENT_STREAMS, 窗口允许的流数)
连接数 N = ceil(C ÷ S) × 安全系数（1.5–2）
```

例：QPS 8,000、P99 50 ms ⇒ C = 400；S = 100 ⇒ N = 4，安全系数 2 ⇒ 8 条/目标地址。**不是 200 条**。200 条的意思是把 400 个并发摊到 200 条连接上，每条只有 2 个流——既浪费 fd 与内存，又让负载均衡更粗糙。

### 负载均衡策略

| 策略 | 依据 | 适合 | 坑 |
| --- | --- | --- | --- |
| pick_first | 第一个可用地址 | 单实例/调试 | 不均衡 |
| round_robin | 轮询 | 同构实例 | 不感知慢实例 |
| least_request | 当前活跃请求最少 | 长尾明显 | 需要全局/子通道视图 |
| ring_hash | 请求键哈希 | 需要会话粘性 | 扩容会重排 |
| EWMA | 延迟指数加权 | 异构机器 | 冷启动抖动 |

**连接池 + 负载均衡的组合陷阱**：池是「按目标地址」建的，如果地址列表变化（注册中心推送），旧池不会自动缩容；滚动发布时会出现「新地址池空、旧地址池满」的短窗口。

---

### 连接池的三个时间常数

池不是「建好就完事」，它有三个时间常数，配错任何一个都会在发布或故障时出事：

| 常数 | 含义 | 常见值 | 配错的现场 |
| --- | --- | --- | --- |
| `idle_timeout` | 连接空闲多久回收 | 60–300 s | 比服务端 keepalive 长 → 拿到已被对端关闭的连接，首请求失败 |
| `max_lifetime` | 连接最长活多久 | 10–30 min | 不设 → DNS/地址变更后一直连旧 IP |
| 建连超时 | 新建连接最多等多久 | 200–1,000 ms | 太长 → 故障时线程被占住；太短 → 抖动即失败 |

**一条纪律**：客户端的 `idle_timeout` 必须**小于**服务端/中间设备的 idle 超时，`max_lifetime` 必须**大于**一次典型的滚动发布窗口。顺序反了，就会周期性出现「每隔几分钟一批首请求失败」——这类故障最难查，因为它看起来像随机抖动。

### 重试预算怎么定

重试预算不是「重试几次」，而是「允许多少比例的额外流量」：

**重试预算的算式**：`retry_budget = 重试请求数 ÷ 成功请求数`，建议 5%–10%；预算耗尽后，新失败请求直接快速失败并打点——用「快速失败」换「不打垮下游」。例：10,000 QPS、成功率 99%，预算 10% ⇒ 允许 100 次/s 的重试；失败率涨到 5% 时，重试请求 500/s 超过预算，超出的 400/s 直接失败。它与熔断是两件事：熔断看失败率，预算看额外流量。

## 40.8 队头阻塞：三种不同的「排队」

| 层次 | 阻塞原因 | 表现 | 解法 |
| --- | --- | --- | --- |
| TCP 层 | 丢包重传 | 同连接所有流一起等 | 多连接、减少跨 AZ、调大拥塞窗口 |
| HTTP/2 流控 | 连接窗口被大响应占满 | 小请求 DATA 排队 | 按响应大小分池、调大窗口、流式分页 |
| 应用层 | 服务端线程池/队列满 | 连接正常但响应慢 | 隔离线程池、限流、异步化 |

```text
一条连接上的时间线（连接窗口 = 64 KB）

t0  ├─ stream1: DATA 48 KB ────────────────┤  大响应占 75% 窗口
t1  ├─ stream3: HEADERS ── DATA 16 KB ─────┤  小请求只能拿剩下的 25%
t2  ├─ stream5: HEADERS ── 等 WINDOW_UPDATE ────────► 900 ms
                                      ▲
                                      └─ 不是服务端慢，是窗口被占满
```

**最实用的修法不是调窗口，而是分流**：把「大响应/流式/导出」接口放到独立的连接池甚至独立的客户端实例；搜索、下单这类小请求用另一个池。池隔离的代价是连接数多一点，收益是故障域隔离。

---

### 把一次跨 AZ 调用拆开：时间到底花在哪

很多人把「RPC 慢」直接归因于「服务端慢」，但一次跨 AZ 调用的固定开销可以拆成六段：

| 段 | 典型量级 | 什么时候会变大 | 能不能省 |
| --- | --- | --- | --- |
| 应用序列化 | 0.1–0.5 ms | 大对象、反射式序列化 | 换 protobuf、缩小消息 |
| 本机到 sidecar/代理 | 0.05–0.2 ms | iptables 规则多、Unix socket 未启用 | 本地直连、eBPF |
| 连接/TLS 握手 | 同 AZ 0.5–2 ms；跨 AZ 4–10 ms | 新连接、会话不复用 | keepalive、session ticket |
| 代理排队 | 0–5 ms | 线程池满、上游连接池空 | 调池、隔离线程池 |
| 服务端处理 | 业务决定 | 下游依赖慢 | 异步化、缓存 |
| 响应回程 + 反序列化 | 0.2–1 ms | 大响应、压缩比低 | 压缩、分页 |

**这张表最有用的一行是「连接/TLS 握手」**：同 AZ 只要 0.5–2 ms，跨 AZ 要 4–10 ms；如果 QPS 高且不复用连接，握手开销会直接变成 CPU 与 P99 的主项。这也是「为什么内网也要 keepalive」的定量理由。

### 一个可运行的 gRPC 客户端骨架

```go
// gRPC 客户端：连接复用 + 流上限 + keepalive + 重试预算（骨架，参数以目标版本为准）
conn, err := grpc.DialContext(ctx, target,
    grpc.WithTransportCredentials(creds),
    grpc.WithDefaultServiceConfig(`{
      "loadBalancingConfig": [{"round_robin": {}}],
      "methodConfig": [{
        "name": [{"service": "inventory.Inventory"}],
        "timeout": "0.8s",
        "retryPolicy": {
          "maxAttempts": 3,
          "initialBackoff": "0.05s",
          "maxBackoff": "0.5s",
          "backoffMultiplier": 2,
          "retryableStatusCodes": ["UNAVAILABLE", "DEADLINE_EXCEEDED"]
        }
      }]
    }`),
    grpc.WithKeepaliveParams(keepalive.ClientParameters{
        Time:                30 * time.Second, // 空闲多久发 ping
        Timeout:             5 * time.Second,  // ping 等多久算断
        PermitWithoutCalls:  false,            // 没有活跃 RPC 时不 ping（省流量）
    }),
)
if err != nil { return err }
defer conn.Close()
```

这段配置里有三个容易被忽略的点：① `maxAttempts=3` 是**总尝试次数**，不是「重试 3 次」；② `initialBackoff` 必须有抖动，否则所有客户端同时重试；③ `PermitWithoutCalls=false` 会让空闲连接不被 ping，NAT 超时后第一次请求才发现连接已死。

## 40.9 三本账：连接内存、并发流、重试放大

### 账一 · 连接内存 = 连接数 × 每连接开销

假设：每条 HTTP/2 连接在客户端占 socket 缓冲 16 KB、TLS 状态 16 KB、HTTP/2 流表与 HPACK 动态表 8 KB，合计约 40 KB；服务端每连接另有请求对象与 buffer，约 30 KB。

| 连接数 | 客户端内存 | 服务端内存 | 结论 |
| --- | --- | --- | --- |
| 1,000 | 40 MB | 30 MB | 无感 |
| 10,000 | 400 MB | 300 MB | 需要关注 fd |
| 100,000 | 4 GB | 3 GB | 必须先做连接复用 |

> **量级结论（非承诺值）**。假设：① 每连接客户端 40 KB、服务端 30 KB；② 不含 TLS 会话缓存与应用层对象；③ fd 上限按 `ulimit -n` 单独核算。**换 gRPC 的 `initial_window_size` 或 `MAX_FRAME_SIZE` 会改变每连接缓冲，但「连接数 × 几十 KB」这个形状不变。**

### 账二 · 并发流上限 = 连接数 × 每连接流上限

假设：8 条连接/目标、每连接 `MAX_CONCURRENT_STREAMS=100`、P99 延迟 50 ms。

```text
可用并发流 = 8 × 100 = 800
可承载 QPS = 800 ÷ 0.05 s = 16,000
若 QPS = 20,000 ⇒ 需要 1,000 个流 ⇒ 至少 10 条连接（或调大流上限）
```

| 参数 | 值 | 可承载 QPS（P99=50 ms） |
| --- | --- | --- |
| 4 连接 × 100 流 | 400 | 8,000 |
| 8 连接 × 100 流 | 800 | 16,000 |
| 8 连接 × 500 流 | 4,000 | 80,000 |

> **量级结论（非承诺值）**。假设：① 流是均匀的，没有大响应独占；② 服务端真的允许这么多流；③ 延迟不随并发上升。**现实里延迟会随并发上升，所以这个上限是「天花板」，不是「工作点」；工作点要留 2 倍余量。**

### 账三 · 重试放大 = 原始 QPS × 期望尝试次数

假设：QPS 10,000、失败率 20%、`retries=2`、重试无退避（最坏）、每次重试仍有 20% 失败。

| 项 | 公式 | 结果 |
| --- | --- | --- |
| 期望尝试次数 | `(1 − 0.2³) / (1 − 0.2)` | **1.24 次/请求** |
| 平均到达下游 | `10,000 × 1.24` | **12,400/s** |
| 同步脉冲（同一秒全超时） | `10,000 × 3` | **30,000/s** |
| 下游容量 12,000/s 时 | 平均已过载，脉冲直接打崩 | 队列深度爆炸 |

> **量级结论（非承诺值）**。假设：① 失败独立同分布；② 重试次数固定；③ 下游没有熔断。**这张账的结论是：平均放大看起来温和（1.24×），真正杀死系统的是同步脉冲（3×）。所以退避 + 抖动 + 预算比「少重试一次」更重要。**

```python
# 三本账复算：改任一假设直接重跑
def conn_mem(n, client_kb=40, server_kb=30):
    return n * client_kb / 1e6, n * server_kb / 1e6   # GB

def stream_capacity(conns, streams_per_conn=100, p99_s=0.05):
    return conns * streams_per_conn, conns * streams_per_conn / p99_s

def retry_amp(qps, p=0.2, retries=2):
    attempts = (1 - p ** (retries + 1)) / (1 - p)
    return attempts, qps * attempts, qps * (retries + 1)

for n in (1_000, 10_000, 100_000):
    c, s = conn_mem(n)
    print(f"{n:>7} 连接 → 客户端 {c:.1f} GB / 服务端 {s:.1f} GB")

print("8×100 流可承载 QPS:", stream_capacity(8))
print("重试放大:", retry_amp(10_000))
```

## 40.10 架构边界：RPC 能保证什么、不能保证什么

| 你想要的保证 | RPC 给不给 | 物理原因 | 正确落点 |
| --- | --- | --- | --- |
| 请求一定送达 | ❌ | 连接断了、对端进程崩了，发送方只能看到超时 | 重试 + 幂等 + 对账 |
| 恰好执行一次 | ❌ | 超时后无法区分「没执行」与「执行了但响应丢了」 | 业务幂等键（→ [eng/24](../eng/24-delivery-semantics.md)） |
| 顺序 | ⚠️ 单连接内可近似 | 多连接/多实例/重试都会乱序 | 业务序列号/单分区 |
| 低延迟 | ⚠️ 取决于复用形态 | 一条连接多流会共享窗口；跨 AZ 有 RTT | 同 AZ、连接池、分流 |
| 高吞吐 | ✅ 加连接/加实例 | 受端口、fd、流上限约束 | 水平扩容 + 连接复用 |
| 故障隔离 | ❌ | 同连接/同池的流会互相影响 | 按接口/大小分池、熔断 |

**选型判定表**：

| 场景 | 建议 | 理由 |
| --- | --- | --- |
| 内部 Java 生态、治理成熟 | Dubbo | 注册/路由/容错一体化 |
| 多语言、流式、云原生 | gRPC | HTTP/2 + protobuf + 跨语言 |
| 浏览器/第三方 | HTTP/1.1 或 HTTP/2 JSON | 兼容性优先 |
| 大文件/导出 | 独立连接池 + 流式分页 | 避免占满共享窗口 |
| 极低延迟、同机 | Unix domain socket / 共享内存 | 跳过 TCP 栈 |

**还有一条边界：RPC 不是消息队列。** 它假设「调用方在等结果」，所以没有持久化、没有消费位点、没有重放；把长任务塞进 RPC，会得到「超时—重试—重复执行」三件套。长任务应该走任务队列，RPC 只负责「提交任务」这一跳。

---

### 一个常被忽略的边界：RPC 不是服务发现

RPC 框架通常自带「地址列表 + 负载均衡」，但那是**客户端侧的静态/半静态视图**，不是服务发现：地址从哪来、多久刷新、实例死了多久被发现，仍然由注册中心与健康检查决定（→ [38 注册中心](38-registry-and-config.md)）。把 RPC 的地址列表当成真值，会得到两个经典故障：① 注册中心已经摘除的实例，RPC 客户端缓存里还在，继续打过去；② 新扩容的实例，RPC 客户端几分钟后才看到，流量全压在老实例上。

正确的分层是：**注册中心负责「谁活着」，RPC 负责「怎么连、怎么分、怎么重试」**。两者之间的缓存刷新周期，就是「发布/扩容后多久真正生效」的时间常数；这个常数必须写进变更手册，而不是藏在 SDK 默认值里。

## 40.11 踩坑清单（现象 → 根因 → 定位 → 修复 → 防复发）

| 现象 | 根因（物理形态） | 定位 | 修复 | 防复发 |
| --- | --- | --- | --- | --- |
| `EADDRNOTAVAIL` / 连接超时 | 短连接 × 重试耗尽本地端口 | `ss -s`、`netstat -an | grep TIME_WAIT` | 改 keepalive 池、限制重试、扩端口范围 | 连接建立速率纳入告警 |
| P99 周期性尖刺 | HTTP/2 连接窗口被大响应占满 | 看单连接 stream 数与窗口等待 | 大响应分池/流式 | 按响应大小路由 |
| 下游 5xx 不多但延迟翻倍 | 重试脉冲把队列打满 | 对比原始 QPS 与下游到达 QPS | 退避 + 抖动 + 预算 | 重试率 > 5% 告警 |
| 发布时错误率尖刺 | GOAWAY/drain 期间在途流被 reset | 看 GOAWAY 计数与发布时间 | 调大 drain、客户端重试 | 发布窗口与 drain 演练 |
| 连接数正常但吞吐上不去 | 流上限/线程池队列满 | 看活跃流、队列深度 | 调流上限/隔离线程池 | 容量按流数算，不按连接数 |
| 跨 AZ 调用偶发超时 | TCP 丢包导致所有流一起等 | 看重传率、RTT | 多连接/同 AZ 优先 | 跨 AZ 链路单独监控 |
| 客户端内存涨 | 连接数 × 缓冲 + HPACK 表 | heap/连接数曲线 | 降连接数、调窗口 | 连接内存纳入容量模型 |

## 40.12 观测：五个数覆盖 90% 的 RPC 故障

| 指标 | 看什么 | 拐点 | 前提 |
| --- | --- | --- | --- |
| 活跃连接数 / fd 使用率 | 连接泄漏、端口耗尽 | fd > 80% | 按进程统计 |
| 活跃流数 / `MAX_CONCURRENT_STREAMS` | 流上限是否成为瓶颈 | > 70% | 需要客户端/服务端都暴露 |
| 流控等待时间 | 大响应是否挤占窗口 | P99 > 10 ms | HTTP/2 指标 |
| 重试率 / 重试放大 | 下游是否被重试打爆 | > 5% | 客户端埋点 |
| GOAWAY / RST_STREAM 数 | 发布/超时/取消 | 发布窗口内突增 | 代理与客户端都要看 |

> 指标必须带版本与开关前提：`MAX_CONCURRENT_STREAMS` 的默认值随 gRPC/Envoy 版本变化；`grpc.keepalive_permit_without_calls` 不开时，空闲连接不会被 ping。**不要拿别处的默认值当自己的 SLO。** 另外，连接数与活跃流数要按「目标地址」拆开看：总量正常不代表没有单地址被打满，单地址的流上限才是重试与超时最先爆的地方。最后，所有 RPC 指标都要和「业务 QPS」对照看：QPS 没涨而流数涨，说明延迟在变长。

## 40.13 一页速记

| 问题 | 一句话答案 |
| --- | --- |
| 连接复用省什么 | 握手、端口、TLS 状态；不省带宽 |
| 一条连接能跑多少流 | `min(MAX_CONCURRENT_STREAMS, 窗口允许)` |
| 需要几条连接 | `ceil(QPS × P99 ÷ 每连接流上限) × 1.5–2` |
| 为什么大响应会堵小请求 | 连接级流控窗口是共享的 |
| 为什么丢包会堵所有流 | 所有 stream 共享一条 TCP |
| 重试的平均放大 | `(1 − p^(r+1)) / (1 − p)` |
| 重试的瞬时放大 | `r + 1`（同步、无抖动时） |
| 什么时候该分池 | 响应大小差异大、跨 AZ、流式接口 |
| RPC 能保证恰好一次吗 | 不能；要靠幂等键 |
| RPC 能当消息队列吗 | 不能；没有持久化、位点与重放 |
| 最该监控的两个数 | 活跃流/上限、重试率 |

## 40.14 自检题（5 题，答案要点）

**1. QPS 20,000、P99 50 ms、每连接 100 流，需要几条连接？安全系数取 2。**

所需并发 = 20,000 × 0.05 = 1,000 流；1,000 ÷ 100 = 10 条；×2 = **20 条/目标地址**。如果只配 4 条，400 个流的上限会让 600 个请求排队，P99 会被队列拉长，而不是被下游拉长。

**2. 为什么 HTTP/2 的多路复用没有消灭队头阻塞？**

因为它只在应用层把帧交错；所有 stream 仍然共享一条 TCP。一个 TCP 段丢失，内核重传会阻塞整条连接的字节流，所有 stream 一起等。跨 AZ/弱网下，多连接反而更稳。

**3. `retries=2`、失败率 20%，平均放大多少？瞬时脉冲多少？**

平均 `(1 − 0.2³)/(1 − 0.2) = 1.24×`；同步无抖动时 `3×`。所以「平均看起来没事」不代表发布窗口不会崩。

**4. 为什么短连接 + 重试会耗尽端口，而 keepalive 池不会？**

短连接每请求一次 `connect()`，端口在 `TIME_WAIT` 期间不能复用；重试把建连次数再乘 `r+1`。keepalive 池把连接复用，端口消耗从「每请求」降到「每池」。

**5. 什么情况下应该把大响应接口拆到独立连接池？**

响应体远大于普通请求（例如 > 1 MB）、或流式/导出接口；它们会占满连接级流控窗口，让同连接的小请求排队。拆池用一点连接数换故障域隔离。
