## 49.1 引子：三起「加了 GPU 反而更慢」的故障

推理服务的事故有个共同点：**GPU 利用率面板不是 100%（是 12%），少样本全绿，错误日志干净，但用户说"卡"**。因为瓶颈不在算力，利用率这个指标从一开始就测错了地方。

### 事故一：把并发从 8 调到 64，P99 从 800 ms 涨到 6.2 s（2025-08-19）

客服 Copilot，8 × A100 80GB，单模型 Qwen2.5-7B fp16，`--max-model-len=8192`、`--gpu-memory-utilization=0.90`、`--max-num-seqs=256`（默认值，没人动过）。日常并发 8，TTFT P99 800 ms，好评。

大促前压测报"并发能力不足"，一位工程师看到 `--max-num-seqs=256` 就认为"上限是 256，远远没到"，于是把网关侧的并发信号量从 8 改成 64。他改的是**入口**，没有改任何引擎参数——**但引擎从来没被限制在 8，是 KV 显存把它限制在 8**。

| 时间 | 事件 | 在途请求 | `gpu_cache_usage_perc` | 抢占次数/min | TTFT P99 | 输出 TPOT P99 |
| --- | --- | --- | --- | --- | --- | --- |
| 08-19 10:00（改前） | 稳态，8 并发，平均上下文 3.5K | 8 | 0.34 | 0 | 800 ms | 42 ms |
| 08-19 10:07 | 网关并发 8 → 64 | 9 → 61 | 0.34 → 0.91 | 0 → 17 | 1,200 ms | 90 ms |
| 08-19 10:15 | KV 池满，开始 swap 到 CPU（`--swap-space=8`） | 61 | 1.00 | 48 | 2,400 ms | 310 ms |
| 08-19 10:31 | swap 空间 8 GB 也满，转 recompute | 61 | 1.00 | 210 | 4,100 ms | 890 ms |
| 08-19 11:05 | 请求互相饿死，重试把在途推到 96 | 96 | 1.00 | 420 | **6,200 ms** | 1,700 ms |
| 08-19 11:12 | 回滚网关信号量到 8 | 8 | 0.34 | 0 | 800 ms | 42 ms |
| 08-19 复盘 | 客诉 2,100 单，8 卡 × 4.5h × $2/h = $72 的卡时，换来 3.5 天工程时间与一次事故复盘 | — | — | — | — | — |

账其实很简单：7B fp16 每 token 每序列 512 KiB（§49.3 推导），平均上下文 3.5K → **单序列 1.75 GiB**；单卡 KV 池 52 GiB → **上限就是 29 条**。改到 64 不是"提高并发"，是**主动要求引擎做 35 条它放不下的序列**，引擎的应对只能是抢占：把别人的 KV 块换出去、或者丢掉重算。

一次 recompute 的代价可以直接算：重算 3.5K token 的 prefill = `2 × 7e9 × 3500 = 4.9e13 FLOP`，A100 单卡有效算力按 40% MFU 取 125 TFLOPS → **0.39 s**。P99 从 800 ms 到 6.2 s，中间是十几轮抢占与重算的叠乘。**加机器能解决排队，解决不了"每卡能装几条"。**

### 事故二：`max_model_len` 从 8K 改成 32K，单卡只剩 2 并发（2025-11-03）

代码助手，用户抱怨"贴不进大文件"，产品要求"支持 32K 上下文"。运维把一个环境变量 `MAX_MODEL_LEN` 从 8192 改成 32768，理由是"模型的 context window 就是 128K，32K 肯定支持"。

这套服务是自研的 Python 推理壳（HF `generate` + 静态批），**显存按 `max_model_len` 逐序列预留**：每条序列开工前先占满 32K 的 KV 位置。

| 项 | 改前（8K） | 改后（32K） | 算式 |
| --- | --- | --- | --- |
| 单序列 KV 预留 | 4 GiB | 16 GiB | `32768 × 512 KiB = 16 GiB` |
| 单卡 KV 池 | 52 GiB | 52 GiB | `72 − 14（权重） − 6（激活/图/碎片）` |
| 理论并发 | 13 | 3 | `52 ÷ 16 = 3.25` |
| 实际并发（留 1 条余量） | 12 | **2** | 留一条给突发 |
| 端到端 QPS | 9.1 | **1.4** | 并发 ÷ 单请求时长 |
| TTFT P99 | 900 ms | **21 s** | 排队 = 在途 ÷ 2 |

第一反应是加卡。加了 4 张卡，QPS 从 1.4 涨到 2.1，因为**这套配置被原样复制到了新卡上**。真正的修复是换成按需分页的引擎（§49.5）：同样的 52 GiB 池，32K 上下文下能跑 **3 条真实 32K 序列**，但如果 95% 的请求只有 2K，分页方案能跑 52 条、静态方案只能跑 3 条——**差别不在显存多大，在"按最坏情况预留"还是"按实际用了多少算"**。

代价：5 天里算了 4 次"要加几张卡"，多买了 1 台 8 卡机器（$2/h × 8 × 24 × 30 ≈ $11,520/月，其中 70% 无效），工程时间 3 天。

### 事故三：网关 60 s 掐断流式连接，GPU 显存不释放（2026-01-12）

Agent 平台。一轮 Agent 循环里有工具调用，工具执行 90 s，模型输出 800 token。SSE 连接会在这 90 s 里**一个字节都不发**。ALB 的 `idle_timeout` 是默认 60 s，于是连接被切断。

客户端收到断开，前端显示"出错了，请重试"。用户点了重试。**服务端完全不知道第一次的那条序列已经没人要了**：它继续 decode，直到 `max_tokens=4096` 跑完。

| 时刻 | 现象 | `num_requests_running` | 实际在线会话 | `gpu_cache_usage_perc` |
| --- | --- | --- | --- | --- |
| 01-12 14:00 | 正常 | 11 | 11 | 0.41 |
| 01-12 16:30 | 连接开始被掐，但生成继续 | 12 → 38 | 11 | 0.41 → 0.88 |
| 01-12 17:20 | 幽灵序列占满 KV 池，新请求排队 | 40 | 11 | 1.00 |
| 01-12 18:00 | 值班同学重启全部 Pod，"立刻恢复" | 0 → 12 | 12 | 0.42 |
| 01-13 复盘 | 每天 14:00–18:00 复发；浪费 31% 的 GPU 小时 = 8 卡 × 31% × $2 × 24 = $119/天 ≈ $3,570/月 | — | — | — |

根因链有两段，只修一段都无效：**① 网关 `idle_timeout` 60 s 小于工具执行时间**（心跳或 keepalive 事件可以解决）；**② HTTP handler 到推理引擎之间没有"请求取消"的传播**——客户端断开后，引擎里的 `abort` 从未被调用，序列会一直跑到 `max_tokens` 或 `stop` 才归还 KV。第二段是推理引擎侧最常见的显存泄漏：它不是内存泄漏，是**语义泄漏**。

三次事故对应本篇三大节：**KV 的字节账（§49.3）、分页与批处理（§49.5–49.6）、取消与观测（§49.10–49.11）**。

## 49.2 一句话定位与唯一真问题

**定位**：推理引擎 = 一个「把 GPU 显存切成块、把请求编成批、把 token 流出去」的调度器。它**不是**模型本身，也**不是**推理加速库（kernel 优化只决定单步快 20%，调度决定成本差 10 倍）。

三个"不是"：

| 它常被误认为 | 它实际是什么 | 差在哪 |
| --- | --- | --- |
| 模型服务框架（"把模型包成 HTTP"） | 显存调度器 + 批处理器 | 包 HTTP 只需要 200 行；决定成本的是块管理和迭代级调度 |
| 推理加速器（"换 vLLM 就快 5 倍"） | 吞吐放大器 | 快 5 倍只在"高并发 + 有共享前缀"时成立；单流短请求上 vLLM 和 HF 差不到 15% |
| 一个无状态服务 | 有状态、显存即状态 | 它的"内存"是 KV cache，重启等于全部在途请求丢失，所以扩缩容比 CPU 服务贵一个数量级 |

### 唯一真问题

> **LLM 推理的瓶颈不是算力，是显存里的 KV cache：分页、连续批处理、前缀复用这三件事，决定了你的成本与首 token 延迟的下限。**

展开这个论断，它有四个必须一起看的推论：

1. **KV cache 的大小是算术，不是经验**：`2 × layers × kv_heads × head_dim × dtype_bytes × 序列长度`。乘出来之后，"这张卡能跑几条"就没有争论空间了（§49.3）。
2. **decode 阶段每生成一个 token，都要把整个 KV cache 和权重从 HBM 读一遍**——所以它的成本单位是"GB 访存/秒"，不是"FLOPS"。这就是为什么单流看似 GPU 空闲（算力利用率 0.44%），而加并发几乎不增加单步耗时（§49.4）。
3. **把显存当虚拟内存分页，才能让"预留最长"变成"按需占用"**。这一步把并发从 `显存 ÷ max_model_len` 提到 `显存 ÷ 实际长度`，典型 3–10 倍（§49.5）。
4. **请求之间的 KV 前缀可以共享**，因为 Agent 场景的 prompt 80% 是固定前缀（system + 工具 schema）。共享块让首 token 从 426 ms 掉到 190 ms，而这一切的前提是**块哈希从第一个 token 开始就能对上**（§49.7）。

从这一个矛盾推出的全部设计：

| 从矛盾推出的约束 | 推出的设计 / 纪律 |
| --- | --- |
| 每 token 的 KV 字节数与层数、头数成正比 | 选模型时先算 KV 账：MHA 的 70B 每 token 5 MiB，8K 上下文根本放不下 → 这就是 GQA 存在的唯一理由 |
| decode 是访存受限，不是算力受限 | 优化的第一优先级是"减少每步要读的字节"，而不是"提高 FLOPS 利用率" |
| KV 必须在请求间不连续存放 | 分页 + 块表；`--block-size` 是内部碎片与查表开销的折中 |
| 一条序列结束才能腾出槽位 → 静态批浪费 | 迭代级调度（continuous batching），每步重新组批 |
| 长 prefill 会独占一步的算力 | chunked prefill：把 32K 切成 2K 一块，与 decode 交错 |
| 显存是唯一稀缺资源，且是每步的带宽负担 | 容量规划必须从"并发数 = KV 池 ÷ 单序列 KV"正推，不能从 QPS 倒推后拍脑袋加卡 |
| 前缀可复用 → 不必重复 prefill | 块哈希 + 引用计数 + COW；但前缀一旦不稳定，命中率归零 |

### 解剖卡八问对照（本篇哪里答哪一问）

## 49.3 物理形态：权重、KV cache 与显存布局

一张推理卡上的显存只有四类住户，其中**只有最后一类是可被"并发"瓜分的**：

```
图 1 · A100 80 GiB 上一台 7B fp16 服务的显存布局（--gpu-memory-utilization=0.90）

物理 80 GiB ────────────────────────────────────────────────────────────┐
│ 0.5 GiB   CUDA context + 驱动 + NCCL 缓冲                              │ 常驻，不随负载变
├────────────────────────────────────────────────────────────────────────┤
│ 14.0 GiB  权重：7e9 参数 × 2 B（fp16）                                  │ 常驻，加载后不变
├────────────────────────────────────────────────────────────────────────┤
│ ~5.5 GiB  CUDA Graph 捕获 + 激活峰值 + 分配器碎片                        │ 随 max_num_seqs 与
│           （batch 档位越多、max_num_batched_tokens 越大，这块越大）      │ max_num_batched_tokens 涨
├────────────────────────────────────────────────────────────────────────┤
│ 52.0 GiB  KV cache 池 —— 6,656 个 16-token 物理块，每块 8 MiB           │ ★ 唯一能被并发瓜分的
│  ┌─────┬─────┬─────┬─────┬─────┬─────┬─────┬─────┬─────┬─────────┐    │
│  │blk 0│blk 1│blk 2│blk 3│blk 4│blk 5│blk 6│blk 7│ ... │已用/空闲 │    │
│  └─────┴─────┴─────┴─────┴─────┴─────┴─────┴─────┴─────┴─────────┘    │
│  总容量 = 52 GiB ÷ 8 MiB × 16 token = 106,496 token                    │
├────────────────────────────────────────────────────────────────────────┤
│  8.0 GiB  预算外余量（80 − 72）+ CPU 侧 --swap-space=8 GiB               │ 吸收尖峰，别指望它救火
└────────────────────────────────────────────────────────────────────────┘
   预算 72 GiB = 80 × 0.90；权重 14 + 非 KV 开销 6 + KV 池 52 = 72 ✓
```

### 核心算式：每 token 每序列的 KV 字节数

这一行是本篇唯一需要背下的公式，后面所有显存数字都由它推出来：

```
KV_bytes_per_token = 2 × layers × kv_heads × head_dim × dtype_bytes
                     ↑ K 和 V 各存一份

【7B 档】32 层 / 32 头 / head_dim 128 / fp16
  每 token = 2 × 32 × 32 × 128 × 2 = 524,288 B = 512 KiB ≈ 0.5 MiB
  × 2,048 token  = 1,073,741,824 B = 1 GiB（精确等于 1 GiB 不是巧合：
                   32 × 32 × 128 × 2 × 2 = 2^19，再乘 2048 = 2^30）
  × 8,192 token  = 4 GiB          × 32,768 token = 16 GiB

【容量】A100 80GB，gpu_memory_utilization = 0.90
  预算   = 80 × 0.90                              = 72.0 GiB
  减权重 = 7e9 × 2 B                              = 14.0 GiB
  减其他 = CUDA ctx + CUDA Graph + 激活峰值 + 碎片 =  6.0 GiB
  KV 池  = 72 − 14 − 6                            = 52.0 GiB
  → 并发上限 = KV 池 ÷ 单序列 KV：2K → 52 条 ｜ 4K → 26 ｜ 8K → 13 ｜ 32K → 3

【70B 档】80 层 / kv_heads 8（GQA）/ head_dim 128 / fp16
  每 token = 2 × 80 × 8 × 128 × 2 = 327,680 B = 320 KiB；8K 序列 = 2.5 GiB
  若同一模型改用 MHA（kv_heads 64，2023 年那批的形状）：
  每 token = 2 × 80 × 64 × 128 × 2 = 5,242,880 B = 5 MiB；8K 序列 = 40 GiB ← 装不下

【TP=8】8 个 kv 头分到 8 张卡，每卡 1 个
  单卡每 token = 2 × 80 × 1 × 128 × 2 = 40,960 B = 40 KiB
  单卡权重 140 ÷ 8 = 17.5 GiB；单卡 KV 池 = 72 − 17.5 − 5 = 49.5 GiB
  8K 序列每卡占 8,192 × 40 KiB = 320 MiB → 单卡 158 条；集群总 KV = 396 GiB
```

> **单位约定**：本篇显存数字一律按 GiB 计，且把 `参数量 × 2 B` 得到的 GB 数直接当 GiB 用（1 GB = 0.931 GiB，偏差 7%，方向是**高估权重、低估 KV 池**，落在保守一侧）。要精确值就乘 0.931，所有结论不变。

> 🩸 注意那组并发上限：**同一张卡、同一个模型，从 52 掉到 13 只因为上下文从 2K 变成 8K**。所以"我的服务能跑多少并发"这个问题，不带上"上下文多长"就没法回答——这是容量评审上第一个该问的问题。

**GQA 不是为了让模型变快，是为了让 KV cache 能装进显存。** 70B 那两行数字放在一起看：每 token 从 5 MiB 降到 320 KiB，是 16 倍容量差，直接翻译成 16 倍的并发或 16 倍的上下文。2024 年之后发布的长上下文模型几乎全部在这个参数上做了同样选择——这不是精度取舍，是显存可行性。

### 模型谱系容量表

统一假设：单卡 A100 80GB、`gpu_memory_utilization=0.90`、fp16 权重、非 KV 开销 6 GiB（70B 因 TP 通信缓冲取 5 GiB/卡）。

| 模型档 | 层 / kv_heads / head_dim | 每 token KV | 8K 单序列 | 权重(fp16) | 部署 | KV 池 | 2K 并发 | 8K 并发 | 32K 并发 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 7B MHA | 32 / 32 / 128 | 512 KiB | 4 GiB | 14 GiB | 1 卡 | 52 GiB | 52 | 13 | 3 |
| 8B GQA | 32 / 8 / 128 | 128 KiB | 1 GiB | 16 GiB | 1 卡 | 50 GiB | 200※ | 50 | 12 |
| 13B MHA | 40 / 40 / 128 | 800 KiB | 6.25 GiB | 26 GiB | 1 卡 | 40 GiB | 25 | 6 | 1 |

## 49.4 一次请求的完整链路（prefill → decode → 流式返回，逐跳耗时）

### 两阶段解码：为什么 prefill 与 decode 是两种完全不同的负载

| 阶段 | 输入 | 每步算什么 | 受限因素 | 单次耗时量级（7B/A100） |
| --- | --- | --- | --- | --- |
| **prefill** | 全部 n 个 prompt token | 一次前向算出全部 KV，产出第 1 个 token | **算力**（大矩阵乘，可打满 Tensor Core） | n/8,928 tok/s |
| **decode** | 1 个新 token | 只算 1 个 token，但要读全部权重 + 该序列全部 KV | **访存**（HBM 带宽） | 10–45 ms/步 |

用 roofline 的直觉（不推公式，只用一个比值）：**每生成 1 个 token，需要 14 GFLOP 的算力，同时需要读出 14 GiB 的权重 + 该序列全部 KV。** A100 的算力/带宽比是 `312 TFLOPS ÷ 1.6 TB/s ≈ 195 FLOP/B`。而单流 decode 的算术强度是 `14e9 ÷ (14 + 1) GiB ≈ 0.87 FLOP/B`——**比拐点低两百多倍**。所以：

- **单流 decode 时，A100 的算力只用了 `14 GFLOP ÷ 10.1 ms = 1.4 TFLOPS = 峰值的 0.44%`。** 这就是"看着 GPU 利用率很低"的全部真相：不是没活干，是活都堵在 HBM 带宽上。
- **加并发几乎不增加单步耗时**，因为权重只读一次可以被 8 条、52 条序列共享。批处理把那次 14 GiB 的读数摊掉了——**这就是成本能被摊薄的唯一机制**。

### 摊薄账：同一张卡，并发从 1 到 52

每步访存 = `权重 14 GiB + Σ(各序列 KV)`（2K 上下文，每序列 1 GiB）；A100 有效 HBM 带宽按 1.6 TB/s；卡价 $2.0/h。

| 并发 B | 每步访存 | 每步耗时 = 访存 ÷ 1.6 TB/s | TPOT | 单卡输出吞吐 | $/百万 output token |
| --- | --- | --- | --- | --- | --- |
| 1 | 14 + 1 = 15 GiB | 10.1 ms | 10.1 ms | 99 tok/s | $5.61 |
| 8 | 14 + 8 = 22 GiB | 14.8 ms | 14.8 ms | 540 tok/s | $1.03 |
| 24 | 14 + 24 = 38 GiB | 25.5 ms | 25.5 ms | 941 tok/s | $0.59 |
| 52 | 14 + 52 = 66 GiB | 44.3 ms | 44.3 ms | 1,174 tok/s | $0.47 |

算式：`$/M = 2.0 ÷ (tok/s × 3,600) × 1e6`，例：`2.0 ÷ (1174 × 3600) × 1e6 = $0.473`。

> 这张表是全篇最重要的一张：**并发从 1 到 52（满了），单卡吞吐涨 11.9 倍、成本降到 1/11.9，而单个用户的 TPOT 只从 10.1 ms 涨到 44.3 ms（仍是 22 tok/s，可读速度）。** continuous batching 的整个价值就在这 12 倍里；而 §49.1 事故一说明它的边界——第 53 条序列进来时，收益立刻变成负的。

顺便把 input 侧也算清：prefill 是算力受限，`125 TFLOPS ÷ 14 GFLOP/token = 8,928 tok/s`，`$/M input = 2.0 ÷ (8928 × 3600) × 1e6 = $0.062`。**输入比输出便宜 7.6 倍**——这就是为什么各家 API 的输入定价普遍是输出的 1/5 到 1/8，不是商业策略，是物理。

### 逐跳耗时分解（一次 3.8K 输入、450 输出的 Copilot 请求）

| # | 跳 | 典型耗时 | 随什么放大 | 备注 |
| --- | --- | --- | --- | --- |
| 1 | 客户端 → 网关（复用连接） | 0.5–1 ms | 新建连接 ×3–10 | TLS 握手是最贵的一跳，所以必须 keep-alive |
| 2 | 网关鉴权 + 配额 + 计量 | 2–5 ms | 每次都算 | `→ comp/50` |
| 3 | 网关 → 引擎（HTTP/2 复用） | 0.3–1 ms | — | 同机房 |
| 4 | tokenize | 1.9 ms | **输入长度** | 3,800 ÷ 2M tok/s ≈ 1.9 ms |
| 5 | 排队（等 KV 块与槽位） | 0 → 秒级 | 在途数 ÷ 并发上限 | **这里才是 P99 的真凶**（§49.1 事故一） |
| 6 | **prefill** | 3800 ÷ 8928 = **426 ms** | 输入长度，且注意力项 O(n²) | 32K 时升到 ~5.9 s（见下） |
| 7 | 首 token 采样 + detokenize | 1–2 ms | 词表大小 | — |
| 8 | **decode**（每 token 一步） | 10.1 ms（B=1）→ 18.7 ms（B=7） | 并发 × 上下文 | TPOT 就是这个数 |
| 9 | SSE 帧封装 + 下发 | 30–80 µs/帧 | 帧数 | 450 帧共约 20 ms |

首 token 延迟 TTFT ≈ 跳 1–7 之和 = `1 + 3 + 0.5 + 1.9 + 排队 + 426 + 1.5 ≈ 434 ms + 排队`。端到端 = `TTFT + 450 × TPOT`。

### 采样参数改的不是"质量"，是"停在哪"——以及账单

工程上最容易忽略的一点：采样参数直接决定输出长度分布，而输出长度线性决定 GPU 时间。

| 参数 | 它实际改变什么 | 对成本/延迟的影响 | 什么时候会咬人 |
| --- | --- | --- | --- |
| `max_tokens` | 硬上限，不是目标 | 只影响最坏情况与预算上限 | 设成 4096 而业务只要 200 token → 取消不及时就白烧（§49.1 事故三） |
| `temperature` | 分布锐度 | 高温 → 更容易跑偏、更晚遇到 stop → 输出更长 | >1.2 时输出长度方差翻倍，Token 预算失控 |
| `top_p` / `top_k` / `min_p` | 截断候选集 | 几乎不影响延迟（采样是 μs 级） | 设得过窄 → 重复循环，反而拖长输出 |
| `stop` / `stop_token_ids` | 决定何时提前结束 | **最便宜的一个参数**：多给一个准确 stop，平均省 10–30% 输出 token | 只靠 max_tokens 兜底是典型的浪费 |
| `repetition_penalty` / `frequency_penalty` | 压低已出现 token | 间接缩短输出 | 过高会破坏结构化输出（JSON 括号重复） |
| `n` / `best_of` | 一次出多条候选 | **成本 ×n**，但前缀块可共享（§49.5 的 COW） | Agent 里用 `n=5` 做自洽投票 = 直接 5 倍账单 |
| `logprobs` / `top_logprobs` | 返回每步分布 | 网络字节 ×(k+1)，GPU 几乎无感 | 高 QPS 下成为带宽与序列化瓶颈 |
| `seed` | 固定采样 | 不改变成本，但让"复现"成为可能 | 没有 seed 的线上 badcase 无法归因 |

### 两端客户端：取消语义必须能从浏览器传到 KV 块

链路表里最容易被跳过的两跳是"服务端 handler"和"客户端"。它们决定了 §49.1 事故三会不会复发：**只有 `ctx` 真的被取消、`body` 真的被关闭，引擎才会收到 abort、才会提前归还 KV 块。**

```go
package main

import (
	"bufio"
	"context"
	"encoding/json"
	"fmt"
	"net/http"
	"strings"
	"time"
)

// 手撸 SSE：取消语义必须自己看得见——ctx 要真的传到服务端，取消才会变成引擎侧的 abort
func stream(ctx context.Context, prompt string, onToken func(string)) error {
	body := fmt.Sprintf(`{"model":"qwen2.5-7b","stream":true,"max_tokens":1024,`+
		`"messages":[{"role":"user","content":%q}]}`, prompt)
	req, _ := http.NewRequestWithContext(ctx, "POST", "http://vllm:8000/v1/chat/completions", strings.NewReader(body))
	req.Header.Set("Content-Type", "application/json")
	req.Header.Set("Accept", "text/event-stream")
	// prefill 排队是秒级、TPOT 是百毫秒级 —— 这两层超时不是同一个数
	hc := &http.Client{Transport: &http.Transport{ResponseHeaderTimeout: 15 * time.Second}}
	resp, err := hc.Do(req)
	if err != nil { return fmt.Errorf("open: %w", err) }
	defer resp.Body.Close() // 少了这行，KV 块会一直挂到 max_tokens 才还（事故三）
	if resp.StatusCode != http.StatusOK { return fmt.Errorf("status %d", resp.StatusCode) }
	sc := bufio.NewScanner(resp.Body)
	for sc.Scan() {
		data, ok := strings.CutPrefix(sc.Text(), "data: ")
		if !ok { continue }
		if data == "[DONE]" { return nil }
		var ev struct{ Choices []struct{ Delta struct{ Content string } } }
		if json.Unmarshal([]byte(data), &ev) != nil || len(ev.Choices) == 0 { continue }
		if t := ev.Choices[0].Delta.Content; t != "" { onToken(t) }
	}
	return sc.Err()
}
```

```java
// Reactor 流式消费：超时、取消、观测都在 Flux 操作符上声明，别藏在 SDK 里
public Flux<String> stream(String prompt) {
    Map<String, Object> body = Map.of(
        "model", "qwen2.5-7b", "stream", true, "max_tokens", 1024,
        "messages", List.of(Map.of("role", "user", "content", prompt)));

    return webClient.post().uri("/v1/chat/completions")
        .contentType(MediaType.APPLICATION_JSON)
        .accept(MediaType.TEXT_EVENT_STREAM)
        .bodyValue(body)
        .retrieve()
        .bodyToFlux(String.class)                       // SSE 帧已按 data: 切好
        .takeUntil("[DONE]"::equals)                    // 服务端显式结束
        .map(this::extractDelta)                        // 取 choices[0].delta.content
        .filter(s -> !s.isEmpty())
        .timeout(Duration.ofSeconds(20))                // 任意两帧间隔上限 → 触发 cancel
        .doOnCancel(() -> Metrics.cancelled.increment()) // 取消率是显存回收的先行指标
        .doOnError(e -> Metrics.streamError.increment());
}
```

两端共同的三个硬约束：① **超时要分层**——`ResponseHeaderTimeout` 覆盖 prefill 排队（秒级到 15 s），帧间隔超时覆盖 TPOT（百毫秒级），两者不是同一个数；② **取消要能落到 TCP**，`ctx` / `Flux.cancel` 必须一路传到 `Close()`，否则引擎侧的 abort 永远不来；③ **`max_tokens` 要设小**，它是"取消失效时的损失上界"，不是"希望输出多长"。

## 49.5 PagedAttention：把显存当虚拟内存使

### 先算"预分配最大长度"到底浪费多少

朴素方案：每条序列开工时，按 `max_model_len` 连续预留一段显存。假设 `max_model_len = 2,048`，实测请求长度分布 P50 = 420 token、均值 512 token：每序列预留 2,048、实际用 512，**浪费率 = 1 − 512/2,048 = 75%**。同一份分布，若把 `max_model_len` 设成 32,768（为了"支持大文件"）：**浪费率 = 1 − 512/32,768 = 98.4%**，并发上限从 52 条掉到 `52 GiB ÷ 16 GiB = 3` 条——这就是 §49.1 事故二。

行业实测（vLLM 论文口径）是 60%–80% 的 KV 显存在这类系统里被浪费掉。而且浪费的不只是"没用到的空间"，还有**外部碎片**：请求长短不一，释放后留下的空洞未必塞得下下一个请求，于是明明总空闲 20 GiB，却凑不出一段连续的 4 GiB。

### 分页：逻辑连续，物理离散

PagedAttention 借用操作系统的虚拟内存：**序列看到的是连续的逻辑块，物理块可以散在显存任何位置**，靠每序列一张块表（block table）翻译。

```
图 2 · 逻辑块 → 物理块映射、跨请求共享与写时复制

块表本身很轻：每序列每 16 个 token 占一条记录（逻辑号 + 物理号 + 引用计数）。一条 32K 序列的块表 = `32768 ÷ 16 = 2,048` 条，按每条 16 B 算 ≈ 32 KiB，相对于 16 GiB 的 KV 可以忽略。

### 内部碎片：块大小 16 的代价是"最多 15 个 token"

| 块大小 | 每序列最坏内部碎片 | 2K 序列的浪费率 | 短对话（平均 200 token）的浪费率 | 块表条目数（32K 序列） |
| --- | --- | --- | --- | --- |
| 8 token | 7 token | 7/2048 = 0.34% | 7/200 = 3.5% | 4,096 |
| **16 token（默认）** | **15 token** | **15/2048 = 0.73%** | **15/200 = 7.5%** | **2,048** |
| 32 token | 31 token | 1.5% | 15.5% | 1,024 |

块小 → 碎片小但查表与 kernel 启动次数多（每块一次 gather）；块大 → 查表少但短请求的碎片率飙升。默认 16 是"长上下文主导"场景的折中；**如果你的流量 80% 是 <300 token 的短问答，把块调到 8 能省 4% 显存，但吞吐可能掉 3–5%**——这是唯一值得实测的块大小决策。

对比一下总量级：预分配方案的浪费是 **75%–98%**，分页方案的内部碎片是 **0.7%–7.5%**。**同一张卡，可用并发在这一步上差 3–10 倍。**

### 跨请求共享：三种天然可共享的场景

| 场景 | 共享什么 | 共享比例（典型） | COW 发生在哪 |
| --- | --- | --- | --- |
| **Agent / RAG 的固定前缀** | system prompt + 工具 schema + few-shot | 1,200–4,000 token 完全相同 | 几乎不发生（前缀只读） |
| **多轮对话** | 前 k−1 轮的完整历史 | 轮次越靠后比例越高，第 8 轮可共享 90% | 不覆盖，只追加 → 只在追加新块时分配 |
| **beam search / `n>1` 采样** | 分叉前的全部 KV | beam 数 k 时省 `(k−1)/k` 的分叉前显存 | **每条 beam 走不同分支的块**，写时才复制 |
| 批量任务（同模板跑 1 万个输入） | 模板部分 | 视模板长度 30–60% | 不发生 |

> 🩸 共享块是**只读**的。任何写入必须先检查 `ref_cnt`，大于 1 就复制。这条规则如果实现错，症状不是崩溃而是**"两个用户互相串话"**——A 的续写被写进了 B 的上下文里。这类 bug 在压测中几乎不可能发现，因为它只在"共享块 + 同时续写"时触发。

## 49.6 continuous batching 与调度：吞吐从哪来，抖动从哪来

### 静态批为什么浪费：一个必须结束才能腾位的调度

```

静态批的 55% 不是极端案例，是**长度分布不均时的常态**。而 LLM 输出长度天然长尾（P50 420、P99 3,000+），所以静态批的有效利用率通常就在 40%–60%。**换到迭代级调度，这一步就是 1.5–2 倍吞吐，不需要任何硬件投入。**

### 两个参数，一场零和：`max_num_seqs` 与 `max_num_batched_tokens`

| 参数 | 定义 | 它限制的是 | 调大的收益 | 调大的代价 |
| --- | --- | --- | --- | --- |
| `--max-num-seqs` | 一个 batch 里最多几条**序列** | 并发槽位数（逻辑上限） | 吞吐上升（摊薄权重访存） | TPOT 线性变差；KV 块需求线性上升 → 抢占风险 |
| `--max-num-batched-tokens` | 一步里最多处理几个 **token**（prefill token + decode token 合计） | 单步的计算预算 | prefill 更快（TTFT 下降） | 单步变长 → TPOT 抖动；激活峰值变高 → 显存紧张 |

两者的关系是一个零和分配：**一步的 token 预算 = `max_num_batched_tokens`，先被 decode 占掉"当前并发数"那么多（每条序列每步 1 个 token），剩下的才轮给 prefill。**

- `max_num_batched_tokens = 8,192`、并发 96 → prefill 每步最多 `8,192 − 96 = 8,096` token，一个 32K 的 prompt 4 步就切完（chunk ≈ 8,096）。
- `max_num_batched_tokens = 1,024` 而并发 96 → prefill 每步只剩 928 token，32K prompt 要 `32768 ÷ 928 = 35` 步才切完，TTFT 恶化 9 倍；但每一步都很短，TPOT 极其平稳。

> 🩸 `max_num_batched_tokens < max_num_seqs` 是纯粹的配置错误：一步的预算连"每条在跑的序列各出 1 个 token"都不够，引擎会退化成每步只能批一部分。看到这个组合，先别调别的。

### 长 prefill 为什么会把 decode 卡住 5.9 秒

prefill 的算力可以算得很准。对 7B、32K prompt：线性项（QKV/MLP，与 n 成正比）= `2 × 7e9 × 32,768 = 4.59e14 FLOP = 459 TFLOP`；注意力项（与 n² 成正比，因果掩码再减半）= `4 × 32 层 × 32,768² × 4,096 ÷ 2 = 2.81e14 FLOP = 281 TFLOP`；合计约 740 TFLOP，除以 `312 TFLOPS × 40% MFU = 125 TFLOPS` → **5.9 秒**。（顺带解释了这个标题：3.67 s 是只算线性项的常见误估，把 O(n²) 的注意力项加回去才是真值。）

**这 5.9 秒里，所有在跑的序列一个 token 都出不来。** 如果这批里有 90 条 decode 正在流式输出，用户的感受是"打字机卡住 6 秒"。这就是 TPOT P99 抖动的唯一物理来源。

分块之后：`chunk = 2,048` → 每块 `740e12 ÷ 16 ≈ 46 TFLOP` → **每步多花 0.37 s**。仍然可观，所以 chunk 要配合"每步至少保留一部分 decode 预算"。极端情况下 chunk 设为 512 → 每步多花 92 ms，抖动基本感知不到，代价是这个 32K prompt 的 TTFT 从 5.9 s 涨到（64 块 × 每步固定开销 ≈ 17 ms）约 7 s。

**这是一个明确的交换：chunk 越小，TPOT 越稳、TTFT 越差。** 没有免费的中间值，只能按 SLO 挑。

### 抢占：KV 用完时的两种还债方式

当调度器发现"放不下新请求"，它必须让某个已有序列让出 KV：

| 策略 | 做什么 | 单次代价（3.5K 上下文 / 1.75 GiB KV） | 什么时候更划算 | vLLM 现状 |
| --- | --- | --- | --- | --- |
| **swap（换出）** | 把 KV 块拷到 CPU 内存，需要时再拷回 | `2 × 1.75 GiB ÷ 20 GB/s（PCIe） ≈ 175 ms` | 序列快回来了、上下文很长（重算比拷贝更贵） | 0.6–0.8 支持（`--swap-space`）；v1 之后基本去掉 |
| **recompute（重算）** | 直接丢弃 KV，轮到时重新 prefill | `2 × 7e9 × 3500 ÷ 125e12 = 392 ms`（纯算力，占 GPU） | 上下文短、并发高（反正要重排批） | v1 起的默认 |

判据一行：**`swap` 划算 ⟺ `L × b ÷ PCIe带宽 < 2 × N × L ÷ 有效算力`**，代入得 `1.75 GiB/20 GB/s = 87 ms/次 < 392 ms/次`——纸面上 swap 更便宜，但它占的是**主机内存**且要碎片整理，而且 87 ms 的拷贝本身也在抢 PCIe（P2P 通信、数据加载共用）。**无论哪种，代价都直接落在 TTFT/P99 上。真正的解法不是选策略，是不让 KV 池满**：把 `--max-num-seqs` 与上下文预算对齐（§49.8）。

## 49.7 前缀复用与量化：两种"不加机器也降本"的手段

### 前缀缓存：块哈希怎么工作，为什么会失效

前缀缓存（prefix caching）不缓存文本，缓存的是**已经算完的 KV 块**。索引键是块哈希：

> `block_hash[i] = hash( block_hash[i-1] ‖ 本块 16 个 token 的 id 序列 )`——父块哈希在前，只对本块内容做摘要。
> 含义：第 i 块的哈希，唯一确定了"从第 0 个 token 到第 i 块末尾"的全部前缀内容。

这一个链式结构决定了它的全部行为：

- **好处**：任何一个 token 变了，从它所在的块往后，**所有**哈希都变——不会误命中。
- **代价**：任何一个 token 变了，从它所在的块往后，**所有**块都失效——**包括你精心准备的那 2,000 token 的 system prompt，只要它在最前面被污染，后面全部白算**。

### Agent 会话的 prompt 结构天生适合前缀缓存

一个典型 Agent 请求的 prompt 布局：

```
┌──────────────────────────────────────────────────────────┐
│ system prompt（人设 + 规则 + 输出格式）   1,200 token      │ ← 逐字不变，命中
├──────────────────────────────────────────────────────────┤
│ 工具 schema（JSON Schema 列表）             900 token      │ ← 逐字不变，命中
├──────────────────────────────────────────────────────────┤
│ few-shot 示例                               600 token      │ ← 逐字不变，命中
├──────────────────────────────────────────────────────────┤
│ 历史轮次（第 1..k-1 轮）                  1,000 token      │ ← 只追加，命中到上一轮末尾
├──────────────────────────────────────────────────────────┤
│ 本轮用户输入 + 工具返回                     100 token      │ ← 只有这里变
└──────────────────────────────────────────────────────────┘
   总计 3,800 token，其中 2,700 是稳定前缀 → 理论命中率 71%
```

命中后省下来的是 **prefill 时间**（直接反映在 TTFT 上）和 **prefill 算力**（反映在成本上）：未命中时 prefill `3,800 ÷ 8,928 tok/s = 426 ms`，成本 `3,800 × $0.062/M ≈ $0.00024`；命中 71% 后只算 `1,100 ÷ 8,928 = 123 ms`，**省 303 ms，TTFT 降 71%**，成本只剩 1,100 token 的算力加一次微秒级的哈希查表。

TTFT 从 426 ms 降到 123 ms，**是这套机制里唯一"零风险、纯收益"的一项**——因为 KV 块本来就是同样的数值，只是没有被复用。

### 什么会打破前缀（每一条都以"重启整段 prefill"的形式收费）

| 反模式 | 为什么致命 | 正确做法 | 命中率 |
| --- | --- | --- | --- |
| 把时间戳/`request_id`/`trace_id` 拼在 system prompt **最前面** | 第 1 块的哈希变了 → 后面每一块全变 → 命中率归零 | 时间戳放**最后**（用户消息之后），或干脆不进 prompt | 0% → 71% |
| 把用户昵称、租户名放在最前 | 每个用户一个独立前缀，缓存条目数 = 用户数，但每个只被用一次 | 租户相关信息放最后；或**按租户分组路由**（`→ llm/26`） | 0% → 71% |
| 工具列表按 `map` 遍历序拼接 | 同一个集合每次序列化顺序不同 → 哈希抖动 | 工具列表**排序后**序列化；JSON key 固定顺序 | 30–70% 抖动 → 稳定 71% |
| 每轮把历史重新渲染成带"当前时间"的相对时间戳 | 历史文本被改 → 整段失效 | 相对时间在生成时一次性落库，之后不再改 | 0% |
| 多副本部署，请求随机打到任意 Pod | 每个 Pod 的块缓存独立，命中率 ÷ 副本数 | 一致性哈希 / 前缀感知路由（`→ llm/26`） | 71% → 71/N |
| `n>1` / beam 未开共享 | 分叉前完全重复 prefill | 开 beam search 共享 + COW（§49.5） | — |

> 🩸 一行铁律：**prompt 的字节级前缀必须对"同一类请求"完全稳定，从第 0 个 token 开始。** 想让某个字段逐请求变化，就把它放到最后。这条纪律的收益是 TTFT 降 70%，成本是"排字段顺序"这么简单的事，而它在 90% 的系统里没被遵守。

### 量化：显存 ÷2 换多少正确率风险

| 形态 | 权重字节/参数 | 7B 权重 | 70B 权重 | 单卡 80G 能装 70B | 相对 fp16 吞吐 | 典型正确率变化 | 什么时候能接受 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| **BF16 / FP16** | 2.0 | 14 GiB | 140 GiB | 否（需 TP≥4） | 1.0×（基线） | 基线 | 精度验收、小模型、评测基准 |
| **FP8（W8A8，E4M3）** | 1.0 | 7 GiB | 70 GiB | 勉强（KV 所剩无几） | 1.6–2.0×（需 H100/L40S 原生 fp8） | 掉 0.2–0.8 点 | 有 GPU 原生 fp8；A100 上无收益，别上 |
| **INT8（W8A8，SmoothQuant）** | 1.05 | 7.4 GiB | 73.5 GiB | 勉强 | 1.3–1.6× | 掉 0.3–1 点 | A100 也能跑，保守场景首选 |
| **INT4 AWQ / GPTQ（W4A16）** | 0.55 | 3.85 GiB | 38.5 GiB | **能（38.5 + KV 够）** | 1.8–2.4×（受 KV 带宽限制，到不了 3×） | 掉 1–3 点；长链推理/代码掉得更多 | 对话、摘要、RAG 问答；**不要用于数学推理与长代码生成** |
| **KV cache FP8** | KV 减半 | — | — | —（权重不变） | 1.2–1.6×（每步 KV 读取减半，并发 ×2） | ctx≤8K 几乎无感；ctx>16K 掉点明显 | 长上下文 + 并发不足时的第一选择 |

**判断表：显存 ÷2，换的是什么风险**

| 你现在缺什么 | 先做什么 | 显存收益 | 付出什么 | 红线（不能碰） |
| --- | --- | --- | --- | --- |
| 缺**并发**（KV 池满、一直抢占） | ① 开前缀缓存（零风险）→ ② KV FP8 | 命中率 70% ≈ KV ÷1.7；KV FP8 = ÷2 | ②只在长上下文掉点 | 法务/医疗/金融的推理链输出，别动 KV 精度 |
| 缺**单卡装得下**（70B 上不了单卡） | 权重 INT4（AWQ） | 权重 ÷3.6（140 → 38.5 GiB） | 掉 1–3 点；长输出更易漂移 | 需要 95%+ 基线正确率的抽检场景 |
| 缺**吞吐**（GPU 打满但 token/s 不够） | FP8 权重 + chunked prefill + 调 `max_num_seqs` | 1.6–2.0× | 掉 0.2–0.8 点 | — |
| 缺**上下文长度** | KV FP8 + 分页（§49.5）+ 前缀缓存 | 上下文 ×2 | 长上下文掉点 | 需要精确引用长文中间段落的场景（召回先掉） |
| 什么都缺，且预算充足 | 换硬件（H100：带宽 3.35 TB/s，是 A100 的 2.1×） | 吞吐 2.1× | 单价 1.7×，$/M token 降 20% | — |

量化的收益要诚实结算：**它省的是显存与权重访存，不省 KV 访存**。所以 AWQ 在短上下文高并发下能到 2.4×（权重访存占比高），但在 8K 上下文下只有 1.3×（KV 访存成了大头，量化权重没用）。看到"INT4 提速 3 倍"的宣称，先问它测的上下文多长。

## 49.8 容量规划：从并发数反推显存与机器数

### 四个必须自己算的参数

| 参数 | 它改变了哪条物理路径 | 设太大的后果 | 设太小的后果 | 建议 |
| --- | --- | --- | --- | --- |
| `--gpu-memory-utilization` | 引擎向显存申请的比例，剩下的自动全给 KV 池 | 0.95 → 只剩 4 GiB 余量；激活尖峰或 CUDA Graph 捕获超了就 **OOM 崩进程**（不是降级，是重启） | 0.70 → KV 池少 16 GiB ≈ 少 16 条 2K 并发 | **0.85–0.90**；只有在压测确认激活峰值 < 3 GiB 时才用 0.95 |
| `--max-model-len` | 单请求上下文上限，并顶高 `max_num_batched_tokens` 的允许值 | 设成模型最大值 → 允许超长 prefill 独占一步（TPOT 抖动）+ 校验期 OOM | 用户的大文件直接 400 | **= 业务的 P99.9 输入长度上限**，不是模型上限，也不是"最大文件大小" |
| `--swap-space` | KV 换出到 CPU 的内存配额 | 太大 → 主机内存被吃，换出换入争 PCIe | 0 → 一缺 KV 就 recompute，P99 直接涨 | 8–16 GiB；**它是保险丝，不是容量** |
| `--tensor-parallel-size` | 把每一层的权重与 KV heads 切到 N 张卡 | 超过单机 NVLink 域（>8）→ 跨机 TP，通信成瓶颈，吞吐反而掉 | 70B 装不进单卡 | 让权重 + KV 装下所需的最小 TP；A100 上 ≤8；70B 通常 TP=4 或 8 |

### 完整算例：从"业务的 QPS"走到"几张卡"

**业务参数**：日活 4 万，人均 12 轮；每轮输入 3,800 token、输出 450 token；工作时间 10 小时承载 60% 流量，峰值系数 2.5；SLO = TTFT P95 ≤ 1.5 s、TPOT P95 ≤ 50 ms。

```
【第一步 · 并发上限 = KV 池 ÷ 单序列 KV 需求】
  模型 7B fp16，每 token KV = 512 KiB
  平均上下文 3,800 token → 单序列 KV = 3800 × 512 KiB = 1.86 GiB
  单卡 KV 池（A100 80G / 0.90 / 1 卡）= 72 − 14 − 6 = 52 GiB
  → 并发上限 = floor(52 ÷ 1.86) = 27 条

【第二步 · 单卡吞吐上限 = 带宽 ÷ 每 token 需读的字节】
  并发 27 时每步访存 = 权重 14 GiB + 27 × 1.86 GiB = 64.2 GiB = 68.9 GB
  每步耗时 = 68.9 ÷ 1.6 TB/s = 43.1 ms  → TPOT = 43.1 ms ✓（< 50 ms SLO）
  单卡输出吞吐 = 27 ÷ 0.0431 = 626 tok/s

【第三步 · 从 QPS 反推卡数】
  日轮次 = 4e4 × 12 = 480,000
  峰值轮次/s = 480,000 × 60% ÷ (10 × 3600) × 2.5 = 20 轮/s
  每轮 GPU 时间 = 3,800 ÷ 8,928（prefill） + 450 ÷ 626（decode） = 0.426 + 0.719 = 1.145 s
  （注意 decode 那一项用的是"该卡当时实际并发下的 tok/s"，不是满负荷值）
  吞吐估算 @100% = 20 × 1.145 = 22.9 卡当量
  目标利用率 70% → ceil(22.9 ÷ 0.70) = 33 卡（未计故障余量）
  若按 8 卡节点留 1 整节点，节点数 = ceil(33 ÷ 8) + 1 = 6；AZ 容灾另算

【第四步 · 核对假设，而不是用单步估算验收 SLO】
  27 路是只按输入时点算出的 KV 上限；生成时序列还会增长。
  若当步实际只有 11 路：每步约 34.5 GiB，约 23.1 ms；整卡约 476 tok/s。
  单请求每步更快，但比 27 路时的整卡吞吐更低，不能仍用 626 tok/s 定容。
  → 用实际混合负载复测批大小、显存、输出吞吐、TTFT 与 TPOT 分位数；不声称 33 卡已达标。

【第五步 · 对照：把上下文从 3.8K 改成 32K，同一个业务】
  prefill 时间 = 线性项 2×7e9×32768 = 459 TFLOP + 注意力项 O(n²) ≈ 281 TFLOP
               = 740 TFLOP ÷ 125 TFLOPS = 5.9 s          ← 单这一项就涨 13.8 倍
  单序列 KV    = 32,768 × 512 KiB = 16 GiB
  单卡并发上限 = floor(52 ÷ 16) = 3 条
  此时每步访存 = 权重 14 + 3 × 16 = 62 GiB = 66.6 GB → 步时 41.6 ms
  单请求 decode 墙钟时间 ≈ 450 × 41.6 ms = 18.7 s
  整卡输出吞吐 ≈ 3 ÷ 0.0416 = 72 tok/s；每请求 decode 折合 GPU 时间 ≈ 6.24 s
  每轮 GPU 时间 ≈ 5.9 + 6.24 = 12.14 s
  仅按吞吐 @70% = ceil(20 × 12.14 ÷ 0.70) ≈ 347 卡（同一简化模型，未计余量）
```

**同一简化模型里，吞吐卡数约从 33 到 347（约 10.5 倍），但后者不是容量承诺。** 假设满批、固定吞吐和阶段耗时，仅供量级比较。[vLLM 的指标](https://docs.vllm.ai/en/latest/benchmarking/cli/)把整卡输出吞吐与单请求 TPOT 分开。更关键的是，这一路的单请求 Prefill 估算就约 5.9 s，已超首 Token 1.5 s 的目标；单纯横向扩容减排队，不能缩短这次计算。需要缩短或复用输入、改变模型或执行形态，再用实际请求分布验证 SLO。

### 容量卡模板（贴进评审材料）

| 字段 | 填法 | 本例 |
| --- | --- | --- |

## 49.9 架构边界：推理引擎能做什么、不能做什么

| 它解决的问题 | 它**不**解决的问题 | 你该去哪 |
| --- | --- | --- |
| 把显存按块分页，按需占用而非按最坏预留 | **上下文变长的 O(n) 算力**：32K 的 prefill 是 5.9 s，分页一分钱都不省 | 缩短 prompt、摘要压缩、语义缓存 → `comp/50` |
| 迭代级批处理，把权重访存摊到 N 条序列 | **多模型路由与配额**：一个引擎进程 = 一个模型，跨模型它一无所知 | `→ llm/26`、`→ comp/50` |
| 前缀块复用，省掉重复 prefill | **长任务持久化**：引擎重启 = 所有在途请求与 KV 一起消失 | `→ llm/12`（持久化执行） |
| 抢占/重算，保证不 OOM 而只是变慢 | **冷启动与池化**：加载 70B 权重 94 秒，扩容速度是"分钟级"，HPA 救不了 | `→ llm/46` |
| 量化的算子与显存核算 | **计费与成本归集**：它只报 token 数，不知道这 token 属于哪个租户 | `→ llm/47` |
| OpenAI 兼容的流式输出 | **网关层的超时链、重试放大、客户端取消语义** | `→ llm/36`、`→ comp/39`、`→ comp/50` |
| 单机内的 TP 并行 | **跨机训练与 NCCL 并行策略**（本篇只讲推理侧） | 不在本套范围 |
| 请求级调度（FCFS/优先级） | **公平性与多租户隔离**：一个狂暴租户能占满整个 KV 池 | `→ comp/50` 的配额与队列 |

三条边界值得单拎出来说，因为它们最常被"换个引擎参数"这种思路误判：

1. **它是"显存调度器"，不是"上下文压缩器"。** 上下文从 8K 到 32K，引擎能做的只有"分页让你不至于爆"，不能把 5.9 s 的 prefill 变成 1 s。要降低这个成本，只能在 prompt 层面动手（RAG 剪枝、历史摘要、结构化压缩）。
2. **它是单模型的。** 一个进程一个权重集。多模型 = 多个 Deployment，谁来做流量分配、谁来做降级、谁来做配额，全部在网关层（`→ llm/26`）。引擎甚至连"这个租户是不是超了"都不知道。
3. **它的"有状态"让弹性很难。** CPU 服务扩一个副本是 20 秒；它扩一个副本是"下载或挂载几十 GB 权重 + 加载 + 图捕获 + 预热"，5–10 分钟起（`→ llm/46`）。所以它的容量规划必须按周预留，不能按 QPS 峰值自动伸缩。

## 49.10 踩坑清单（现象 → 根因 → 定位 → 修复 → 防复发）

### ① TTFT 高，但吞吐看起来正常

| 项 | 内容 |
| --- | --- |
| **现象** | 输出 token/s 总量达标，GPU「利用率」不低，但 TTFT P95 从 900 ms 涨到 6 s；用户感觉"点了没反应，然后哗哗出字" |
| **根因（指到物理形态）** | prefill 与 decode 在抢同一步的 token 预算。`max_num_batched_tokens` 偏小 + `max_num_seqs` 偏大 → decode 每步占掉大量预算，prefill 被切得极碎，一个 3.8K 的 prompt 要十几步才排完；排队时间全部计入 TTFT，而 decode 吞吐不受影响 |
| **定位** | ① 看 `num_requests_waiting` 是否长期 > 0；② 对比 `request_prompt_tokens` 分位与 TTFT 分位是否同向；③ 查 `max_num_batched_tokens` 与 `max_num_seqs` 的比值（< 4 就要怀疑）；④ 关掉 chunked prefill 对比一次 |
| **修复** | 把 `max_num_batched_tokens` 提到 `4 × max_num_seqs` 以上（如 8192 / 22）；chunk 上限设 2,048；若 P99.9 输入很长，给长 prompt 单独一个 Deployment（不同 `max-model-len`） |
| **防复发** | TTFT 与 TPOT 分开设 SLO、分开告警；在容量卡里把 `max_num_batched_tokens ≥ 4 × max_num_seqs` 写成硬约束（§49.8 模板） |

### ② TPOT 抖动，P99 是 P50 的 8 倍

| 项 | 内容 |
| --- | --- |
| **现象** | 平均 45 ms/token 很漂亮，但每隔几分钟有一段 800 ms–3 s 的"打字机卡住" |
| **根因** | 长 prefill 独占一步。没开 chunked prefill，或者 `max_model_len` 设得极大（32K），一个用户贴了大文件就把整个 batch 卡住 5.9 s（§49.6 的算式） |
| **定位** | ① TPOT 直方图应该是双峰（正常峰 + 长尾峰），看长尾与 `request_prompt_tokens` 的 >P99 桶是否同时出现；② 抓一次 `--max-num-batched-tokens` 与单步 prefill token 数的关系；③ `nvidia-smi` 每步耗时打点 |
| **修复** | 开 `--enable-chunked-prefill`，chunk 上限 ≤ 2,048；`--max-model-len` 降到业务真实上限；把"贴大文件"类请求路由到独立部署（`→ comp/50`） |
| **防复发** | 上线前压测必须包含"1 个 32K 请求 + 50 个正常请求"的混合场景，看 TPOT P99；把"单步 prefill token 数"做成指标 |

### ③ 突然 OOM（进程直接重启，不是变慢）

| 项 | 内容 |
| --- | --- |
| **现象** | 跑了三周没事，某天开始每几小时 Pod `OOMKilled` 或 `Worker died`；重启后正常，但流量高峰必崩 |
| **根因** | `--gpu-memory-utilization=0.95` + `--max-model-len` 设到模型最大值。只剩 4 GiB 余量，而"激活峰值 + CUDA Graph 捕获 + 分配器碎片"会随 `max_num_seqs` 与 batch token 数波动，尖峰超过 4 GiB |
| **定位** | ① 看 OOM 是否与流量高峰同时出现（是 → 激活尖峰）；② 用 0.85 重启一次，若不再 OOM 则确认是余量不足；③ 查是否有人近期调大过 `max_num_seqs` / `max_num_batched_tokens` / 加了长 prompt 的路由 |
| **修复** | 降到 0.85–0.88；`max_model_len` 按 P99.9 收入长度设；`--swap-space` 给足（它救不了激活 OOM，但能救 KV 挤压） |
| **防复发** | 显存余量 ≥ 8 GiB 作为上线准入项；把这些参数纳入配置管理并做变更评审——**它们不是"调优参数"，是容量契约** |

### ④ 并发上不去（加机器也没用）

| 项 | 内容 |
| --- | --- |
| **现象** | 压测时不管打多少并发，`num_requests_running` 卡在 20 出头；加卡后总吞吐涨了，但单卡并发还是 20 |
| **根因** | KV 池 ÷ 单序列 KV = 27（§49.8），而 `max_num_seqs` 要么设成了 8/16，要么被默认值之外的某个值卡住；或者上下文比估计的长（实际 P95 是 8K 不是 2K），单序列 4 GiB 而不是 1.86 GiB |
| **定位** | ① `gpu_cache_usage_perc` 如果 < 0.7 而 `num_requests_running` 已达 `max_num_seqs` → 是**参数**卡的；② 如果 `gpu_cache_usage_perc` = 1.0 → 是**显存**卡的；③ 打印实际 `request_prompt_tokens` 分位，别用产品说的"平均 2K" |
| **修复** | 参数卡 → 按 `KV 上限 × 0.85` 设 `max_num_seqs`；显存卡 → 开前缀缓存（省 70% 前缀）、KV FP8（÷2）、缩短上下文、或加卡 |
| **防复发** | 把"并发上限"算成公式写进容量卡，任何"并发上不去"的工单第一句话就问这三个数：KV 池、P95 上下文、`max_num_seqs` |

### ⑤ 流式被客户端/网关取消后显存不回收

| 项 | 内容 |
| --- | --- |
| **现象** | 晚高峰后 `gpu_cache_usage_perc` 长期 0.9+ 不降，`num_requests_running` 远大于真实在线会话数；重启立刻恢复（§49.1 事故三） |
| **根因** | 断链没有传播成"取消"。要么网关 `idle_timeout` 短于工具执行时间把连接掐了，要么应用层 handler 在 `resp.Body.Close()` / `Flux` cancel 处没有调用引擎的 abort，序列继续跑到 `max_tokens` |
| **定位** | ① 对比 `num_requests_running` 与网关侧活跃会话数，差值稳定 → 幽灵序列；② 查网关 `idle_timeout` 与工具平均耗时的关系；③ 在 handler 里加 `defer cancel()` 与 `doOnCancel` 计数，看取消率是否为 0（为 0 就是没传播） |
| **修复** | 网关 `idle_timeout` > 最长工具耗时（或发 SSE 心跳/注释帧保活）；客户端 `req.WithContext(ctx)` / Reactor `timeout()` + cancel 传播到引擎；对超长 `max_tokens` 的请求加"空闲超时" |
| **防复发** | 把"取消率"做成指标并设下限告警；`max_tokens` 默认值下调；上线压测必须包含"建连 3 秒后主动断开 1,000 次"的用例 |

### ⑥ 前缀缓存命中率接近 0

| 项 | 内容 |
| --- | --- |
| **现象** | 开了 `--enable-prefix-caching`，TTFT 毫无改善；命中率指标在 0–5% 徘徊 |
| **根因** | prompt 前缀不稳定。最常见三种：时间戳/请求 id 拼在最前面；工具 schema 按 map 遍历序序列化；多副本随机路由导致每个 Pod 各自冷启动 |
| **定位** | ① 抓 10 条真实 prompt 做逐字节 diff，看"第一个不同字节出现在第几个 token"——如果是第 3 个 token，问题在最前面；② 看命中率是否 ≈ 71% ÷ 副本数（是 → 路由问题）；③ 看同一用户连续两轮的命中率是否 > 0（是 → 只有跨用户共享失效） |
| **修复** | 把变化字段移到最后；工具列表排序 + 固定 key 序；前缀感知路由或一致性哈希（`→ llm/26`） |
| **防复发** | prompt 模板纳入单测：同一类请求渲染 100 次，断言"前 N 个字节完全一致" |

## 49.11 观测：指标、拐点与告警

| 指标 | 含义 | 健康值 | 拐点 / 告警阈值 | 它提前告诉你的坏事 |
| --- | --- | --- | --- | --- |
| `vllm:gpu_cache_usage_perc` | KV 物理块占用率（0–1） | < 0.75 | > 0.85 持续 5 min | 再涨就开始抢占 → P99 阶梯式恶化 |
| `vllm:num_requests_waiting` | 已到达但没排进 batch 的请求数 | 0 | 持续 > 0 且 TTFT P95 破 SLO | 容量不足，或 `max_num_seqs` 太保守 |
| `vllm:num_requests_running` | 正在 batch 里的序列数 | ≈ 在途请求数 | / `max_num_seqs` > 0.95 | 槽位饱和，新请求要排队 |
| `vllm:num_preemptions_total` | 抢占累计次数（counter） | **0** | `rate(...[5m]) > 0` | 并发目标 > KV 能给；任何非零都该查 |
| TTFT 直方图 | 首 token 延迟 | P95 ≤ SLO（如 1.5 s） | P95 > 2×SLO | prefill 排队 / 前缀缓存失效 |
| TPOT / inter-token 直方图 | 每 token 间隔 | P95 ≤ SLO（如 50 ms） | P99 > 3×P50（双峰） | 长 prefill 打断 decode |
| 前缀缓存命中率 | 命中 token ÷ 查询 token | > 60%（Agent 场景） | < 30% | prompt 前缀不稳 → 白付 prefill |
| `request_prompt_tokens` 分位 | 输入长度分布 | 稳定 | P99 突增 2× | 有人塞了长 prompt / 工具 schema 膨胀 |

```promql
# ① KV 块占用：最该先看的数，>0.85 就预警，别等 OOM
vllm:gpu_cache_usage_perc

# ② 抢占速率：任何非零都说明"期望并发 > KV 能给"，是 P99 恶化的直接前兆
sum by (instance) (rate(vllm:num_preemptions_total[5m]))

# ③ 前缀缓存命中率（token 口径，不是请求口径）
sum(rate(vllm:prefix_cache_hits_total[5m]))
  / clamp_min(sum(rate(vllm:prefix_cache_queries_total[5m])), 1)

# ④ 槽位饱和 vs KV 饱和 —— 两者一起看才知道该调参数还是加卡
vllm:num_requests_running
vllm:num_requests_waiting
#   running 到顶 + cache_usage < 0.8  → 参数卡住（调 max_num_seqs）
#   cache_usage = 1.0 不管 running     → 显存卡住（前缀缓存/KV FP8/加卡）

# ⑤ 分位延迟（直方图分桶，别用平均值；标签务必只打 model + instance，别打 user_id）
histogram_quantile(0.95, sum by (le) (rate(vllm:time_to_first_token_seconds_bucket[5m])))
histogram_quantile(0.99, sum by (le) (rate(vllm:inter_token_latency_seconds_bucket[5m])))
```

> 🩸 指标名随版本变（0.6/0.8 与 v1 引擎有差异），上线第一件事是 `curl :8000/metrics | grep vllm:` 把真实名字抄下来。另外：**这些直方图绝不要打 `user_id` / `request_id` 标签**——一次事故里，标签基数比推理本身先压垮监控库（`→ comp/48`）。

## 49.12 一页速记

**五个数，背下来就能在评审上算账**

| 数 | 值 | 出处 |
| --- | --- | --- |
| 每 token KV（7B MHA / fp16） | `2×32×32×128×2 = 512 KiB` | §49.3 |
| 每 token KV（70B GQA / fp16） | `2×80×8×128×2 = 320 KiB` | §49.3 |
| KV 池（A100 80G，0.90） | `72 − 14（权重） − 6（开销）= 52 GiB` | §49.3 |
| decode 每步速度下限 | `权重 14 GiB ÷ 1.6 TB/s = 10.1 ms`（与并发几乎无关） | §49.4 |
| prefill 吞吐 | `125 TFLOPS ÷ 14 GFLOP = 8,928 token/s` | §49.4 |

**五条铁律**

1. **并发上限 = KV 池 ÷ 单序列 KV**。答不出这个除法，就没资格谈并发。
2. **decode 是访存受限**：单流 GPU 算力利用率只有 0.44%，加并发是把权重那次读取摊掉，不是"用上更多算力"。
3. **预分配 vs 分页差 3–10 倍**：按 `max_model_len` 预留的浪费率 75–98%，分页的内部碎片只有 0.7–7.5%。
4. **前缀缓存的收益全部取决于"第 0 个 token 起是否稳定"**。时间戳放最前面 = 命中率 0 = 白付一遍 prefill。
5. **`max_model_len` 不是一个"能力开关"，是容量契约**：设成 32K，可能让单卡并发从 27 掉到 3，同时让 TPOT 抖动从 45 ms 变成 5.9 s。

**一句边界**：它把显存与批处理做到接近最优，但**上下文变长的 O(n) 算力、多模型路由、长任务持久化，三件事它一件也解决不了**。

## 49.13 自检题

**Q1.** 一张 A100 80GB 跑 13B fp16（40 层、40 头、head_dim 128），`gpu_memory_utilization=0.90`，业务上下文 P95 = 6,000 token。问：单卡能跑几条并发？如果此时 P99 出现抢占，你先改哪个参数、为什么？

<details><summary>答案</summary>

每 token KV = `2 × 40 × 40 × 128 × 2 = 819,200 B = 800 KiB`。
单序列（6K）= `6000 × 800 KiB = 4.58 GiB`。
KV 池 = `80×0.90 − 26（13B 权重 13e9×2B）− 6 = 72 − 32 = 40 GiB`。
并发上限 = `floor(40 ÷ 4.58) = 8 条`。

抢占说明"被要求跑的序列 > 8"。第一优先不是加卡，而是**开前缀缓存**（Agent 场景 70% 前缀命中 ≈ 把 4.58 GiB 的有效需求降到 1.5 GiB 量级），其次才是 KV FP8（÷2）。因为若 6,000 token 里有 4,000 是 system + 工具 schema，这部分根本不该重复占 KV。若两者都做完仍抢占，才轮到加卡——但先要确认 `max_num_seqs` 没有被设成大于 8 的值（否则等于主动要求引擎抢占）。
</details>

**Q2.** 为什么单流 decode 时 GPU 算力利用率只有 0.44%，但把并发加到 52 后单步耗时只从 10.1 ms 涨到 44.3 ms，而不是涨 52 倍？

<details><summary>答案</summary>

因为 decode 每步的瓶颈是 **HBM 访存**，不是算力。每步必须读：权重 14 GiB（**一次，被整批共享**）+ 每条序列自己的 KV（1 GiB × 并发）。
B=1：15 GiB ÷ 1.6 TB/s = 10.1 ms；B=52：66 GiB ÷ 1.6 TB/s = 44.3 ms。
耗时只涨 4.4 倍，而产出 token 涨 52 倍 → 单 token 成本降到 1/11.9。算力利用率 0.44% 的算式是 `14 GFLOP ÷ 10.1 ms = 1.4 TFLOPS ÷ 312 TFLOPS`，它低正是因为"算得少、读得多"。
</details>

**Q3.** 一个 32K prompt 的 prefill 要多久？为什么它会让已经在线上的 90 条流式输出同时"卡住"？chunked prefill 把什么换成了什么？

<details><summary>答案</summary>

7B / 32K：线性项 `2×7e9×32768 = 459 TFLOP`；注意力项 O(n²)（因果掩码减半）≈ 281 TFLOP；合计 740 TFLOP ÷ 125 TFLOPS（40% MFU）= **5.9 s**。
调度器是"一步一个 batch"，这一步的算力被这个 prefill 独占，batch 里其他 90 条序列在这一步里得不到执行 → 用户看到打字机停 5.9 s（TPOT P99 尖刺）。
chunked prefill 把"一次 5.9 s 的长阻塞"换成"16 次 ~0.37 s 的短阻塞"：**用 TTFT 变差（5.9 s → 约 7 s，多了每步固定开销）换 TPOT 平稳**。
</details>

**Q4.** 你们把时间戳拼在 system prompt 最前面。开了前缀缓存后 TTFT 没有任何改善，为什么？如果你必须把时间戳传给模型，怎么放？

<details><summary>答案</summary>

块哈希是链式的：`hash[i] = hash(hash[i-1] ‖ 第 i 块 16 个 token)`。时间戳在最前面 → 第 0 块哈希就变 → 其后**每一块**哈希都变 → 整段前缀无一块命中，命中率 0%，TTFT 与不开缓存完全相同。
正确做法：把时间戳放到 **prompt 的最末尾**（用户当前消息之后，或作为一个单独的末尾字段），使变化只影响最后 1 个块；更彻底的做法是不把时间戳放进 prompt，而是让模型通过工具调用取时间。
</details>

**Q5.** 产品要求把上下文从 8K 提到 32K，"卡数应该只多一点点吧"。用本篇的算账方式给出答复（7B fp16，A100 80G，等 QPS）。

<details><summary>答案</summary>

三笔账同时变差：
① **并发**：单序列 KV `8K×512KiB=4 GiB` → `32K×512KiB=16 GiB`，单卡并发 `52÷4=13` → `52÷16=3`（少 4.3 倍）。
② **prefill**：8K = 线性 `2×7e9×8192=115 TFLOP` + 注意力 `4×32×8192²×4096÷2=17.6 TFLOP` = 133 TFLOP ÷ 125 = **1.06 s**；32K = 459+281 = 740 TFLOP ÷ 125 = **5.9 s**，慢 5.6 倍（注意力的 n² 项在 32K 时占比从 13% 涨到 38%）。
③ **decode**：并发只有 3，权重摊不薄。每步访存 `14 + 3×16 = 62 GiB` → 41.6 ms/步 → 单卡 72 tok/s → `$2.0 ÷ (72×3600) × 1e6 = $7.7/M`，而 2K 满并发时是 $0.47/M（贵 16 倍）。
综合：按 §49.8 同一简化账，8K 满 13 路时每步约 44 ms，单卡约 295 tok/s；每请求折合 `1.06 + 450/295 ≈ 2.59` GPU 秒。保持每秒 20 个请求、70% 利用率，约从 74 卡到 347 卡（约 4.7 倍），不是生产定容结果。32K 的单请求 Prefill 已超上述首 Token 目标；要改请求或执行路径，不是只买更多同样的副本。
</details>
