## 43.1 引子：三起「加了事务组件，反而更不一致」的事故

这一节的三起事故有一个共同形状：**业务代码里一行 `@Transactional` 都没少，事务组件也在正常跑，监控面板上全是绿的**。出事的是三件从未被当作「容量与语义」对待的东西——**协调者崩了之后那些已经 prepare 的分支归谁、undo_log 里的行镜像还能不能代表当前行、Try 与 Cancel 谁先到**。它们都不是业务逻辑，所以从来没人给它们做过设计评审。

### 事故一：XA 的 prepare 成功、协调者挂掉，2,317 个分支锁住了积分库

某会员系统 2026-03-11 21:04。订单库与积分库分属两个 MySQL 8.4 实例，半年前上了 XA，理由很正当：**积分是钱，不能凭空多出来**。协调者是订单服务 JVM（`TM`），两个库是 `RM`。

| 时刻 | 事件 | 现象 / 代价 |
| --- | --- | --- |
| 21:04:10 | 订单库 `XA START` / `XA END` / `XA PREPARE` 成功，积分库同样三步成功 | 两个分支都进入 `PREPARED`，**行锁仍在持有** |
| 21:04:11 | 协调者在写全局 commit 记录前被 K8s 滚动发布 `SIGKILL` | 全局决议从未落盘 |
| 21:04:12 | 积分库上 `XA RECOVER` 列出 **2,317 个** in-doubt 分支 | 每个分支锁住一条 `t_points` 行 + 一个 undo 段 |
| 21:05 | 积分查询接口 P99 从 12 ms 涨到 8.4 s | 被锁行的读走一致性快照还能读，`SELECT ... FOR UPDATE` 与「扣分」全部排队 |
| 21:09 | 积分库连接池 200 条里 **187 条**被这些分支的会话占住 | 新请求连不上，报错率 34% |
| 21:22 | 人工按订单号逐条比对后 `XA COMMIT` / `XA ROLLBACK` | 其中 **319 个**分支已被 `wait_timeout` 断开、库里状态与协调者日志不一致 |
| 21:47 | 恢复 | 43 分钟，8.9 万笔下单失败，1,104 个会员的积分需要人工修数 |

这一起的教训不是「XA 有 bug」，而是：**XA 把「原子提交」实现成了「跨网络的长时间锁」**。一阶段结束时每个库都持有本地锁与 undo 段，而释放它们需要一个已经死掉的进程回来做决定。`PREPARED` 状态下的事务既不能回滚也不能提交，它是**一个只等外部信号的悬挂资源**——这正是二阶段提交被称作 **blocking protocol** 的字面含义（→ eng/8 §8.4.1 给了同一机制的方案层结论，本篇只算它的锁账）。

### 事故二：AT 的 undo_log 与业务表已经不一致，回滚把别人刚写的数据覆盖掉

某积分商城 2026-05-22 10:31。用了 Seata AT，业务代码只有一行 `@GlobalTransactional`，看起来最省事。

一笔「下单扣积分」的全局事务里，分支 A 执行 `UPDATE t_points SET points = points - 100 WHERE uid = 42`，一阶段把行镜像写进了 `undo_log`：

| 字段 | 一阶段写入的值 |
| --- | --- |
| `before_image` | `points = 1,000` |
| `after_image` | `points = 900` |
| `rollback_info` | 表名 `t_points`、主键 `uid=42`、仅这两列 |

一阶段本地事务立刻提交（这是 AT 的定义：**本地先提交**），积分行对外已经是 900。10:31:07，另一个业务（签到奖励）把这行改成 950 并提交。10:31:09，全局事务因分支 B 失败而需要回滚，RM 用 after image 作校验生成反向 SQL：

| 生成的反向 SQL | 执行结果 | 后果 |
| --- | --- | --- |
| `UPDATE t_points SET points=1000 WHERE uid=42 AND points=900` | **影响 0 行** | 若校验开着 → 抛 `BranchRollbackFailed`，全局事务卡在回滚中重试；若校验被关掉 → 下一行 |
| `UPDATE t_points SET points=1000 WHERE uid=42`（校验关闭或 after image 缺失） | 影响 1 行 | **签到奖励的 +50 被吞掉**，用户凭空少 50 分 |

这次事故一共 71 笔全局事务落在这条路径上，其中 12 笔把并发写入覆盖，涉及 5,340 积分；**发现它靠的是三天后运营手工对账**，而不是任何告警。

根因必须指到物理形态上：**undo_log 里的行镜像只是一阶段那一刻的快照，它靠「after image 与当前行相等」这个乐观校验来保护，校验一关，反向 SQL 就变成了无条件覆盖**。另外两个同源坑：① 每个业务库都必须有 `undo_log` 表（多数据源漏建一个，二阶段直接失败）；② `undo_log` 是会被定时任务清理的（Seata 的 `undo.log.save.days` 是**天级保留策略**，具体默认值与版本相关，以目标版本文档为准），全局事务拖得比保留窗口更长，二阶段就找不到镜像、只能进人工。

### 事故三：TCC 的空回滚、悬挂、幂等三件套缺了两件，重复扣款 5.1 万元

某钱包系统 2026-08-03 15:12。账户服务自己实现了 TCC：`Try` 冻结 100 元，`Confirm` 扣减，`Cancel` 解冻。三张表都没建，靠「冻结金额存在 `t_account` 的一列里 + 状态字段」硬做。

| 时刻 | 事件 | 库里的结果 |
| --- | --- | --- |
| 15:12:00 | 交易服务 `Try`（冻结 100）：请求到达账户服务，DB 执行成功但响应在网络上丢了 | 冻结 100 已落库，交易服务看到超时 |
| 15:12:02 | TC 判定 Try 超时，发起 `Cancel` | — |
| 15:12:02 | `Cancel` 先于 `Try` 的**第二次重试**到达 | 查不到冻结记录 → 直接 `return SUCCESS`（**空回滚**） |
| 15:12:03 | 交易服务重试的 `Try` 落库成功 | 冻结 100，且**再没有任何 Cancel 会来**（**悬挂**） |
| 15:12:05 | 另一笔：`Try` 成功后 `Cancel` 被重投 2 次，`Cancel` 没有幂等判断 | 解冻执行了 3 次 → **余额凭空多 200**（**重复解冻**） |

当天对账结果：**43 笔悬挂冻结（永久占用 4,300 元可用余额）、8 笔重复解冻（多出 1,500 元）**，另有 39 笔只冻结没扣减的中间态，合计 5.1 万元差异，全部要人工介入。

> 🩸 三起事故的共同点：**没有一处业务逻辑写错**。① 是协调者崩在二阶段门口；② 是行镜像与当前行的时差；③ 是分支决议的到达顺序。它们都发生在「事务组件把协调工作搬出业务代码」这个抽象漏出来的地方：搬走的是**代码**，没搬走的是**状态**——而状态一旦落在中间件与多个库之间，就有了「谁先到、谁还活着、谁的快照还算数」这三个新问题。

## 43.2 一句话定位与唯一真问题

**定位**：事务组件（XA 驱动、Seata/DTM 类框架、自研 TCC 骨架）是**协调者**，不是**执行者**。真正让数据落盘的仍然是各参与方自己的本地事务（MySQL 的 redo/undo、Redis 的 Lua 原子执行、MQ 的半消息），组件做的只有三件事：

| 组件只做这三件事 | 物理落点 | 不做什么 |
| --- | --- | --- |
| **协调（coordinate）** | TM 决定全局 commit/rollback，TC 记录决议并通知各 RM；通知是**RPC**，所以会丢、会重、会乱序 | 不替任何参与方执行写操作 |
| **记录（record）** | 全局事务表 + 分支表 + 锁表/undo_log：把「决议」与「每个分支到哪一步」持久化 | 不保证记录与业务数据的原子性（它把这件事变成了「同库同事务写」） |
| **重试（retry）** | 二阶段失败 → TC 按退避重试 → 超上限 → 告警 + 人工/对账兜底 | 不产生幂等，幂等仍然由业务的分支状态机提供 |

### 唯一真问题

> **分布式事务组件不产生原子性，只是把协调工作搬出业务代码；AT 的 undo_log 是用反向 SQL 换无侵入。**

这句话可以拆成四条可验证的推论，全篇都在给它们找证据：

1. **原子性的下限永远是「本地事务」**。一个全局事务由 N 个本地事务组成，组件的贡献只是让这 N 个本地事务**要么都保留、要么都被撤销**；它没有任何办法让两个库在物理上同时提交。所以「全局事务的原子性」= **决议的持久性** + **撤销路径的可靠性**，两项都在组件侧，而不在数据库侧。
2. **把协调搬出代码，等于把状态搬进中间件**。业务代码里原本只有一份数据库状态，现在多了三份：全局事务表、分支表、undo_log / 冻结记录。**任何一份对不上，故障就从「数据错」变成「数据错且查不出原因」**（事故二的 71 笔里 12 笔是这么来的）。
3. **无侵入一定有代价，只是账单记在别处**。AT 让业务零改动，代价是：一阶段本地提交（全局层面读未提交）、每条 SQL 都要被解析成行镜像、每个库都要有 undo_log、回滚只能做「反向 SQL」这一种语义。**你省下的是代码，付出的是隔离性、存储与解析能力边界。**
4. **三者兜底的东西不同**。XA 靠数据库的 `PREPARED` 状态兜底；AT 靠 undo_log 的分支回卷兜底；TCC 靠**业务自己的状态机 + 幂等 + 防悬挂**兜底。所以 XA 是「数据库替你记住」，AT 是「框架替你记住」，TCC 是「你替自己记住」——**能不能兜住，只取决于那份记录有没有被同一个本地事务写下去**。

### 解剖卡八问（事务组件版）

| # | 问题 | 本篇的回答（一句话） |
| --- | --- | --- |
| ① | 承诺什么 | 承诺「决议一旦持久化，所有分支最终会收敛到它」；**不承诺**「中途别人看不到中间态」，也不承诺「补偿一定成功」 |
| ② | 数据长什么样 | XA：库内 `PREPARED` 事务 + undo 段 + 行锁；AT：`undo_log` 行（before/after image）；TCC：业务状态机 + 冻结行 + 分支流水 |
| ③ | 一次读写走哪条路 | 业务 SQL →（AT：解析出镜像 + 申请全局锁）→ 本地事务提交 → RPC 上报 TC → 二阶段 RPC 回来 → 提交/反向 SQL |
| ④ | 并发与一致 | 全局锁（AT）、行锁与 undo 段（XA）、分支状态机（TCC）；失效窗口全在「本地已提交、全局未决议」这一段 |
| ⑤ | 扩展维度 | **只有一条：减少全局事务的数量与时长**。TC 可以加节点、DB 可以换，但全局事务本身不可横向扩展——它是串行化的 |
| ⑥ | 系统级失效 | 满（in-doubt 事务占住行锁与连接）、慢（二阶段 RPC 与重试）、脑裂（启发式决议）、假活（TC 在但分支不收敛）、语义漂移（回滚错数据） |
| ⑦ | 看哪几个指标 | 全局事务数/时长、回滚率、undo_log 体积与清理延迟、全局锁等待、二阶段重试次数（43.11） |
| ⑧ | 换掉它的信号 | 全局事务 QPS 撑不住/时长进入秒级、热点行冲突率上升、需要跨库 JOIN 或非事务型资源 → 换形态（43.9） |

## 43.3 XA / 2PC：原子性靠数据库的 `PREPARED` 状态，代价是跨网络的锁

### 两个角色，一个 XID

XA 是**接口规范**（X/Open DTP 模型），2PC 是**协议**（两阶段提交）。工程上没人分开说，因为它们必须一起用。

| 角色 | 谁扮演 | 干什么 | 挂了会怎样 |
| --- | --- | --- | --- |
| **TM**（Transaction Manager，协调者） | 业务进程里的 XA 驱动、Seata TC、MQ 的事务协调器 | 分配全局 `XID`、发 prepare、收集投票、落全局决议、发 commit/rollback | **已 prepare 的分支全部悬挂**（事故一） |
| **RM**（Resource Manager，参与者） | 每个数据库实例 | 执行 `xa start/end/prepare/commit/rollback`、把分支状态与锁持久化 | 该分支无法决算，全局事务只能等它回来或人工处理 |

全局事务的身份是 **XID**：由 `formatID + gtrid（全局事务 id）+ bqual（分支限定符）` 三段组成，每个分支一个唯一的 `bqual`。**这个 id 是贯穿两阶段的唯一线索**，它必须出现在业务库的行锁、undo 段、二进制日志、以及 TM 的日志里——事故一里那 2,317 个 in-doubt 分支能被找回来，靠的就是 `XA RECOVER` 能把这个 XID 及其 `bqual` 打印出来。

### 一条命令序列，逐句看它做了什么

```sql
-- 一个 XA 全局事务在单个 MySQL 8.4 RM 上的完整生命周期（示例）
XA START 'gtrid-20260311-0001', 'branch-order-db', 1;   -- 开启分支，登记 XID
UPDATE orders SET status = 'PAID' WHERE id = 88012;      -- 业务 SQL：此时持行锁
XA END   'gtrid-20260311-0001', 'branch-order-db', 1;    -- 语句结束，事务进入 idle
XA PREPARE 'gtrid-20260311-0001', 'branch-order-db', 1;  -- ★ 落盘为 PREPARED：写 undo + 持锁等决议
-- ……等 TM 的全局决议（这一等可以很长，锁一直不释放）……
XA COMMIT 'gtrid-20260311-0001', 'branch-order-db', 1;   -- 或 XA ROLLBACK
```

`XA PREPARE` 是整个模型的关键点：**它把「本地已做完」和「本地已可见」这两件事拆开了**。执行完之后，事务占着一个 undo 段（供回滚用）、持着所有修改行的锁、并且**在数据库重启后依然存在**——这正是崩溃恢复能找回它的原因，也是它锁住资源的原因。恢复与人工介入都从同一个视图出发：先 `XA RECOVER;`（需要十六进制形式的 XID 时用 `XA RECOVER CONVERT XID;`），输出里带着 formatID、gtrid 长度、gtrid、bqual 长度与 bqual——据此定位到「哪个全局事务的哪个分支」；裁决之后再执行 `XA COMMIT 'gtrid-20260311-0001', 'branch-order-db', 1;`（或同参数的 `XA ROLLBACK`）。**注意 `XA RECOVER` 只列出当前实例上仍处于 `PREPARED` 的分支，它不告诉你该提交还是该回滚**——那个决定在 TM 的日志里，而 TM 的日志恰恰是事故一里最先丢的东西。

### 物理形态：`PREPARED` 到底占了什么

```text
XA 分支在 MySQL 里占用的东西（一个 in-doubt 分支）

  InnoDB
   ├── 一个活跃事务对象，状态 = PREPARED（不是 ACTIVE，也不是 COMMITTED）
   ├── undo 段：保留全部被改行的前像（回滚必须能原样倒回去）
   ├── 行锁：所有 UPDATE/DELETE 涉及的行 + 相关间隙锁，全部仍持有
   └── redo：PREPARE 时已落盘（崩溃能恢复出这个状态）

  连接层
   ├── 一条会话连接被这个分支绑住（除非显式 DETACH，见下）
   └── 该连接的 wait_timeout 到点会断，但事务不因此回滚——它变成「无人认领」

  二进制日志
   └── 分支日志的完整性由库内部 2PC 协同（→ comp/08），
       外部 XA 分支在 binlog 里的记录形态与版本相关，以目标版本文档为准
```

两个版本/开关前提必须记住：

- **MySQL 8.0.30+ 支持 `XA DETACH` / `XA REATTACH`**：可以把一个 `PREPARED` 分支从原连接上摘下来，让连接先还给池子。它解决的是「连接被占住」，**不解决「锁被占住」**——锁仍然跟着事务走。
- **PostgreSQL 必须显式打开 `max_prepared_transactions`（默认 `0` = 禁用 prepared transaction）**。默认配置下 `PREPARE TRANSACTION` 直接报错，这不是排错问题，是前提没开。XA 相关的另外两个常见开关：`innodb_support_xa` 在 MySQL 8.0 已移除（恒为开启状态），不要再按 5.7 的老参数去配。

### 为什么 prepare 之后协调者挂掉，资源就被锁住

```text
二阶段提交的时间线（协调者在倒数第二步挂掉）

 TM(订单服务)        RM-A(订单库)          RM-B(积分库)          TC/日志
     │                  │                     │                    │
     │── xa start ─────►│                     │                    │
     │── UPDATE ───────►│ 持行锁              │                    │
     │── xa prepare ───►│ ✅ PREPARED 持锁    │                    │
     │── xa start ──────────────────────────►│                    │
     │── UPDATE ────────────────────────────►│ 持行锁              │
     │── xa prepare ────────────────────────►│ ✅ PREPARED 持锁    │
     │                  │                     │                    │
     │── 全局 commit 决定 ───────────────────────────────────────►│（写日志…）
     ✗ 进程被 SIGKILL / OOM / 发布终止
     │                  │                     │                    │
     │             ⏳ 锁不释放            ⏳ 锁不释放                 │
     │         （只能等 XA RECOVER 后人工裁决，或全局超时回滚）
     │                  │                     │                    │
     ▼                  ▼                     ▼                    ▼
  决议从未持久化 ⇒ 两个分支都永远不知道该往哪走 ⇒ 行锁 + undo 段 + 连接 一起悬挂
```

**这张图就是「XA 慢」的全部原因**：不是 prepare 慢，是 `PREPARED` 这一段的**持锁时长 = 全局最慢分支的耗时 + 两次网络往返 + 协调者的存活时间**，而它无法被本地事务的任何优化缩短。第二层代价是**连接**：每个 in-doubt 分支通常绑着一条会话，于是「锁住行」会涨成「锁住行 + 占满连接池」（事故一 187/200）。

### 启发式决议：唯一能让数据库自己动手的地方，也是最脏的地方

如果某个 RM 等了太久（应用侧 `xa_timeout` 或 DBA 手工介入），它可能**自作主张**提交或回滚分支——这叫**启发式提交 / 启发式回滚**（heuristic commit / rollback）。后果是全局一致性彻底破产：

| 情形 | 现场 | 你怎么知道 |
| --- | --- | --- |
| A 启发式 commit、B 已 rollback | 订单有了、积分没扣（或反之） | 只有对账能发现（→ eng/14） |
| 两个 RM 都启发式决定，方向相反 | 全局事务**永久分裂** | `XAER_HEURHAZ`（heuristic hazard）——驱动会把错误码抛给你 |
| 一个 RM 启发式、另一个还在等 | 一边已定、一边悬挂 | `XA RECOVER` 里只剩一半分支 |

**纪律只有一条：永远不要用「给 XA 配一个很短的超时让它自己回滚」来治悬挂**。启发式决议把「不确定」变成了「确定但可能错」，而确定错比不确定更难查——不确定至少 `XA RECOVER` 会告诉你还差谁。

### 只读分支与性能优化（少写两行，少两次 RPC）

XA 允许把一个分支标成只读：`XA END ... , XA PREPARE` 之前的 `XA START ... READ ONLY`。只读分支在二阶段**不需要 commit/rollback 通知**（没有改动要落盘），于是省掉一次往返。这在读多写少、跨库校验类事务里能省掉可观的一笔——但它**不改变热点写分支的持锁时间**，是优化不是解法。

## 43.4 Seata AT：一阶段本地提交，二阶段用 undo_log 做反向补偿

### 三角色：TC 是新的单点，TM 在业务进程里

| 角色 | 部署位置 | 职责 | 失效后果 |
| --- | --- | --- | --- |
| **TC**（Transaction Coordinator） | Seata Server 集群（独立进程，状态落 DB 或文件） | 生成 `XID`、维持 `global_table`/`branch_table`/`lock_table`、驱动二阶段、管全局锁与超时 | 全局事务无法推进：一阶段照常提交，**但没有决议方**，二阶段全部悬空 |
| **TM**（Transaction Manager） | 业务进程（`@GlobalTransactional` 注解所在处） | 开全局事务、把 `XID` 带进调用链、向 TC 发起全局提交/回滚 | 事务悬挂（与 XA 同病） |
| **RM**（Resource Manager） | 每个业务库的代理（数据源代理 / JDBC 代理） | 解析 SQL 生成行镜像、写 `undo_log`、注册分支、申请全局锁、执行二阶段 | 该库分支无法决算 |

关键差别在这里：**XA 的 RM 是数据库自己，AT 的 RM 是「数据源代理层」**——所以 AT 必须能**解析你的 SQL**，这是它一切能力与一切边界的来源。

### 两阶段的真实时序

```text
AT 的两阶段（一阶段本地就已提交，这是与 XA 最本质的差别）

 业务线程                 RM(数据源代理)              TC              业务库
    │                        │                        │                 │
    │── UPDATE t_points ────►│                        │                 │
    │                        │─ 解析 SQL，生成 before/after image       │
    │                        │─ 申请全局锁 ──────────►│ lock_table 插入  │
    │                        │◄──── 授予 ─────────────│                 │
    │                        │─ 本地事务：业务 SQL + INSERT undo_log ───►│ ✅ 提交
    │                        │─ 注册分支/上报状态 ───►│ branch_table     │
    │◄── 返回（业务已经"成功"了，但全局还没定） ───────│                 │
    │                        │                        │                 │
    │  —— 其它分支全部成功 —— │                        │                 │
    │                        │◄── 二阶段 commit 通知 ─│（异步，可重试）  │
    │                        │─ 删除 undo_log ───────────────────────►│
    │                        │─ 释放全局锁 ──────────►│                 │
    │                        │                        │                 │
    │  —— 有一个分支失败 ——   │                        │                 │
    │                        │◄── 二阶段 rollback ────│                 │
    │                        │─ 读 undo_log → 校验 after image           │
    │                        │─ 生成反向 SQL 并执行（本地事务）────────►│
    │                        │─ 删除 undo_log / 释放锁                  │
```

三个必须记住的事实：

1. **一阶段结束，数据对所有人可见**（本地已提交）。所以 AT 的全局隔离级别是**读未提交**级别的：别人能在二阶段之前读到「可能被回滚」的数据。
2. **写隔离靠全局锁**：同一行要被两个全局事务写时，第二个必须等第一个全局事务彻底结束（包括二阶段）。这换来了「不脏写」，代价见 43.8 账一。
3. **二阶段是异步的、可重试的**：commit 分支只是删 `undo_log`（很便宜）；rollback 分支要真的跑反向 SQL（很贵，而且要处理并发覆盖）。

### undo_log 的物理形态与反向 SQL 的生成规则

```sql
-- 每个参与 AT 的业务库里都必须有这张表（Seata 官方 DDL 结构，字段以目标版本为准）
CREATE TABLE undo_log (
  branch_id     BIGINT       NOT NULL COMMENT '分支事务 id',
  xid           VARCHAR(128) NOT NULL COMMENT '全局事务 id',
  context       VARCHAR(128) NOT NULL COMMENT '序列化上下文（如 serializer=jackson）',
  rollback_info LONGBLOB     NOT NULL COMMENT 'beforeImage + afterImage + tableMeta',
  log_status    INT          NOT NULL COMMENT '0=normal，1=global finished（二阶段完成的占位，用于防悬挂）',
  log_created   DATETIME(6)  NOT NULL,
  log_modified  DATETIME(6)  NOT NULL,
  UNIQUE KEY ux_undo_log (xid, branch_id)
) ENGINE = InnoDB;

-- 逆向 SQL 的生成规则（示意）：用 after image 作条件，用 before image 作新值
-- 原始： UPDATE t_points SET points = points - 100 WHERE uid = 42
-- 前像： points=1000 ；后像： points=900
UPDATE t_points SET points = 1000 WHERE uid = 42 AND points = 900;
--                                                        ^^^^^^^^^^^^ 乐观校验：不匹配就报冲突
```

`rollback_info` 里装的是**行镜像（before image + after image）**加 `tableMeta`（表名、主键列、列类型）。反推逻辑很朴素：**把每行改回 before image；把 after image 当条件，用来发现「这行已经被别人动过了」**。于是三条边界直接推出来：

| 场景 | AT 能不能自动回滚 | 物理原因 |
| --- | --- | --- |
| 单表按主键 `UPDATE`/`DELETE` | ✅ | 能定位到具体行与主键 |
| `UPDATE ... WHERE` 命中多行、无主键条件 | ⚠️ | 前像按**实际命中的行**记录，能回滚；但无主键表会把全表列都塞进镜像，体积爆炸 |
| 批量 `INSERT` | ✅（生成 DELETE） | 前像为空、后像为插入值 |
| 跨库 `JOIN` 更新、子查询改其它表 | ❌ | 代理只能解析出本连接上的一条语句 |
| 动态表名 / 分表在 SQL 里拼接 | ⚠️ | 表名与 `tableMeta` 绑定，改表结构或换分片后镜像失效 |
| `DDL`（`ALTER TABLE`）夹在全局事务里 | ❌ | MySQL DDL 隐式提交，`undo_log` 与业务表不在同一事务里，回滚无从谈起 |
| 非事务型资源（Redis、HTTP 调用） | ❌ | 没有 `undo_log` 可写，只能靠 TCC / Saga 的业务补偿 |

### 一阶段代码：无侵入的代价是「所有前提都藏在注解后面」

```java
// TM 侧：一个全局事务（Spring Boot + Seata AT，参数以目标版本文档为准）
@GlobalTransactional(name = "create-order", timeoutMills = 30_000, rollbackFor = Exception.class)
public void createOrder(OrderCmd cmd) {
    orderMapper.insert(cmd.toOrder());                    // 分支 1：订单库
    pointsService.deduct(cmd.getUid(), cmd.getPoints());   // 分支 2：积分库（RPC，XID 随调用链传播）
    couponService.lock(cmd.getCouponId());                 // 分支 3：券库
}

// RM 侧：AT 挡不住的读，要用全局锁把行"钉住"（等价于给读加一把跨全局事务的锁）
@GlobalLock
@Transactional
public Points queryForUpdate(long uid) {
    return pointsMapper.selectForUpdate(uid);   // SELECT ... FOR UPDATE，靠全局锁 + 行锁双保险
}
```

这段代码里有三个容易忽略的前提：① `timeoutMills` 是**全局超时**，到点 TC 会主动发起回滚——它必须大于所有分支的最长耗时，否则正常业务也会被回滚；② 分支 2 是 RPC，**`XID` 必须通过调用链透传**（Seata 的 `RootContext` 用 RPC 拦截器做，跨语言/跨框架时最容易丢）；③ `@GlobalLock` 只挡**写锁冲突**，它不提供快照隔离，读到的仍然是「别人一阶段已提交、全局未定」的数据。

### 隔离缺口：AT 的「读未提交」到底漏在哪

| 缺口 | 现场 | 补法 | 补法的代价 |
| --- | --- | --- | --- |
| **全局脏读** | 全局事务 T1 把积分从 1000 改成 900，二阶段回滚了；期间 T2 读到 900 | 业务上禁止读「参与全局事务的行」，或读也加 `@GlobalLock + FOR UPDATE` | 加锁读 → 全局锁等待进 P99（账一） |
| **本地脏写可见** | 两个全局事务改同一行：第二个卡在全局锁上，但它**已经读了**旧值做业务判断 | 用 `SELECT ... FOR UPDATE` 提前拿行锁 | 死锁率上升（锁顺序问题 → comp/07） |
| **镜像校验关闭** | `undo_log` 的 after image 校验被关掉/缺失 → 反向 SQL 变成无条件覆盖（事故二） | 保持校验开启（`client.rm.reportSuccessEnable`、undo 数据校验相关开关按目标版本核对） | 冲突时回滚失败，进人工 |
| **长事务 vs undo_log 保留** | 全局事务比 `undo.log.save.days` 活得更久，镜像被清理 | 全局事务时长必须远小于保留窗口；监控最长全局事务 | 需要定期核对清理任务的删除边界 |

> 一句话总结 AT：**它把「不动业务代码」换成了「动数据」，而动的这份数据（undo_log）恰好不在业务库的一致性视野里**——所以 AT 的正确用法是「短事务 + 单表按主键 + 关闭期间不做 DDL + 有对账」，而不是「什么都能兜」。

## 43.5 TCC：把「预留资源」写进业务表，于是三坑全归你自己

### Try / Confirm / Cancel 到底各干什么

| 阶段 | 语义 | 失败时谁负责 | 幂等要求 | 关键约束 |
| --- | --- | --- | --- | --- |
| **Try** | **预留**资源：冻结、锁库存、占额度。不改「已用余额」，只改「可用」 | 超时 → TC 会发 Cancel | 可重试 | 必须能识别「已经 Cancel 过了」（防悬挂） |
| **Confirm** | **确认**预留：冻结转实扣。**必须成功** | TC 无限重试直到成功 | **必须幂等** | 不允许业务性失败（余额不足之类必须前置到 Try） |
| **Cancel** | **释放**预留：解冻、退回额度 | TC 重试 | **必须幂等** | 必须能处理「Try 从没执行过」（空回滚） |

与 AT 最本质的差别：**TCC 的一阶段改的是「你自己设计的中间状态」**，所以没有 SQL 解析、没有行镜像、没有全局锁，隔离性由你的表结构直接给出（冻结金额与已用金额分列存储，天然隔离）。代价是：**状态机、幂等、防悬挂三件事必须你自己做对**。

### 三个坑的时序：为什么「先到」比「做对」更难

```text
三坑的时序（TC 的重试 + 网络的不确定 = 全部根源）

 正常：      Try ──► Confirm                 Try ──► Cancel
                                                  │
 空回滚：                 Cancel ──►（找不到 Try 记录）──► 返回成功
            Try ──────────────────────► 落库（从此再没人来 Cancel）  ← 悬挂

 悬挂（时序）：  TC 判 Try 超时 ──► Cancel 到达（Try 还在网络里）
                                     Cancel 完成后 Try 才落库 ──► 冻结永远不解

 幂等：      Confirm/Cancel 被重投 N 次 → 执行 N 次 → 多扣 / 多解冻
```

三个坑的定义必须记准，因为它们各自要一张不同的「证据行」：

| 坑 | 定义 | 唯一可靠的防法 | 证据落在哪 |
| --- | --- | --- | --- |
| **空回滚** | Cancel 在 Try **从未执行成功**时到达，Cancel 又「顺手」做了释放 → 释放了不存在的预留 | Cancel 先落一条**占位记录**（标记「此 xid 已 Cancel」），再去动业务 | 分支表 / 冻结表的 `xid` 唯一键 |
| **悬挂** | Cancel 先到并成功，Try 后到并生效 → 预留永久悬空 | Try 落库前先查「该 xid 是否已被 Cancel」，是则**直接拒绝并返回成功** | 同上：占位记录 + 唯一键 |
| **幂等** | 同一 `xid + branch` 的 Confirm/Cancel 被执行多次 | 用**状态机条件更新**（`WHERE status = 期望值`），影响行数 0 就视为已处理 | 分支表的 `status` + 次数列 |

### 三张表就够（不要一上来就上框架）

```sql
-- ① 全局事务：一笔业务一条，biz_id 唯一键让"重复下单"在入口就被拦掉
CREATE TABLE t_tcc_transaction (
  xid         VARCHAR(128) NOT NULL PRIMARY KEY,
  biz_type    VARCHAR(64)  NOT NULL,
  biz_id      VARCHAR(64)  NOT NULL,
  status      VARCHAR(16)  NOT NULL COMMENT 'TRYING/TRIED/CONFIRMED/CANCELLED',
  amount      BIGINT       NOT NULL,
  gmt_create  DATETIME(3)  NOT NULL,
  gmt_modified DATETIME(3) NOT NULL,
  UNIQUE KEY ux_biz (biz_type, biz_id)          -- 入口幂等
);

-- ② 分支：每个参与方一条；confirm_count/cancel_count 让"执行了几次"可见
CREATE TABLE t_tcc_branch (
  xid          VARCHAR(128) NOT NULL,
  branch_id    VARCHAR(64)  NOT NULL,
  status       VARCHAR(16)  NOT NULL COMMENT 'TRIED/CONFIRMED/CANCELLED/EMPTY_ROLLBACK',
  confirm_count INT         NOT NULL DEFAULT 0,
  cancel_count  INT         NOT NULL DEFAULT 0,
  gmt_modified DATETIME(3)  NOT NULL,
  PRIMARY KEY (xid, branch_id)
);

-- ③ 资源预留（账户服务侧）：xid 唯一键同时承担"防悬挂"与"幂等"两件事
CREATE TABLE t_account_freeze (
  id       BIGINT      NOT NULL AUTO_INCREMENT PRIMARY KEY,
  xid      VARCHAR(128) NOT NULL,
  uid      BIGINT      NOT NULL,
  amount   BIGINT      NOT NULL,
  status   VARCHAR(16) NOT NULL COMMENT 'FROZEN/CONFIRMED/CANCELLED',
  UNIQUE KEY ux_xid (xid)                        -- ★ 悬挂与空回滚都靠它
);
```

### 一个能直接抄的 Cancel / Try 骨架（Go）

```go
// Cancel：幂等 + 空回滚占位；Try：防悬挂。两个函数共用 t_account_freeze.xid 唯一键
func (s *Svc) Cancel(ctx context.Context, xid string, uid, amt int64) error {
    return s.inTx(ctx, func(tx *sql.Tx) error {
        // 1) 幂等：已终态直接返回成功（0 行影响即视为已处理）
        if n, err := tx.Exec(`UPDATE t_account_freeze SET status='CANCELLED'
                WHERE xid=? AND status='FROZEN'`, xid); err != nil {
            return err
        } else if n > 0 { return s.markBranch(ctx, tx, xid, "CANCELLED") }
        // 2) 空回滚：没有冻结行 → 落一条占位行（status=CANCELLED），让迟到的 Try 撞唯一键
        _, err := tx.Exec(`INSERT INTO t_account_freeze(xid,uid,amount,status)
                VALUES(?,?,?,'CANCELLED') ON DUPLICATE KEY UPDATE status=status`, xid, uid, amt)
        return err
    })
}

func (s *Svc) Try(ctx context.Context, xid string, uid, amt int64) error {
    return s.inTx(ctx, func(tx *sql.Tx) error {
        // 防悬挂：若该 xid 已有 CANCELLED 占位行，Try 必须失败（或直接被忽略），绝不落冻结
        var st string
        _ = tx.QueryRow(`SELECT status FROM t_account_freeze WHERE xid=? FOR UPDATE`, xid).Scan(&st)
        if st == "CANCELLED" { return nil }   // 决议已定，静默成功
        _, err := tx.Exec(`INSERT INTO t_account_freeze(xid,uid,amount,status)
                VALUES(?,?,?,'FROZEN')`, xid, uid, amt)
        return err
    })
}
```

这段代码值得逐行看：`Cancel` 的 `UPDATE ... WHERE status='FROZEN'` 是**幂等**（第二次影响 0 行）；没有命中时的 `INSERT ... ON DUPLICATE KEY` 是**空回滚占位**；`Try` 里先 `FOR UPDATE` 查状态是**防悬挂**（唯一的坑在于占位行与冻结行共用同一个唯一键——这正是它同时管住三件事的原因）。

> TCC 的边界要说清：**Confirm 不允许失败**。凡是可能失败的业务判断（余额不足、库存不足、风控拒绝）都必须在 Try 阶段做完；Confirm 只能做「冻结→实扣」这种不会失败的动作。一旦把校验放进 Confirm，你就有了一笔「Try 成功、Confirm 永远失败」的悬挂，TC 会重试到天荒地老。

## 43.6 Saga / 本地消息表 / Outbox：只给一句结论 + 锚点

这三个方案的机制、补偿写法、三坑细节在 `eng/` 已经写透，本篇不重写，只给「它是靠什么兜底」的一句话，方便和 XA/AT/TCC 放在同一张桌上看：

| 方案 | 一句话结论（它靠什么兜底） | 锚点 |
| --- | --- | --- |
| **Saga** | 每个正向步骤配一个补偿步骤；兜底靠**补偿链可重放**，没有隔离性，中间态对外可见 | → eng/8 §8.4.3、→ eng/12 |
| **本地消息表 / Outbox** | 把「发消息」变成「写本地表」，与业务同库同事务；兜底靠**relay 的轮询与重放** | → eng/8 §8.4.5、→ eng/10 |
| **可靠消息 / 事务消息** | 半消息 + 回查；兜底靠**MQ 的回查接口**（本质是让 broker 当 TC） | → eng/8 §8.4.4、→ eng/11 |
| **最大努力通知** | 只承诺「尽力 + 可查 + 可补」；兜底靠**对方主动查 + 你对账** | → eng/8 §8.4.6 |
| **Saga 三坑**（空补偿/悬挂/幂等） | 与 TCC 三坑同源，只是作用在业务补偿上 | → eng/13 |
| **方案怎么选** | 决策树与四类场景的完整推演 | → eng/9 事务决策树 |

**本篇与它们的唯一接口**：Saga / Outbox / 消息 都是「**补偿类**」方案——**它们和 TCC 一样，把状态机与幂等压在业务侧**；XA / AT 是「**决议类**」方案——把状态机搬进中间件。这条分界线决定了你在 43.10 会踩哪一半的坑。

## 43.7 可靠性：TC 自己就是个分布式组件，兜底只能靠「记录 + 重试 + 告警 + 对账」

### TC 的高可用与事务日志

| 项 | AT（Seata） | XA | TCC（自研） |
| --- | --- | --- | --- |
| 决议落哪 | TC 的 `global_table`/`branch_table`/`lock_table`（DB 或 file 模式） | RM 的 `PREPARED` 状态 + TM 的应用日志 | 你自己的 `t_tcc_transaction` / 分支表 |
| TC/协调者高可用 | Server 集群 + **共享同一个 DB**；`file` 模式只能单机 | 无独立 TC：靠应用侧 TM 的日志持久化（这恰恰最脆） | 你自建（通常也是 DB + 集群） |
| 关键风险 | 多个 TC 同时在跑 → 对同一 xid 重复驱动二阶段（要求二阶段幂等） | 协调者无状态持久化 → in-doubt 分支只能人工裁决 | 表所在库成为新单点 |
| 恢复动作 | 重启后扫未终态全局事务继续驱动 | `XA RECOVER` 后人工 commit/rollback | 扫 `TRYING/TRIED` 超时行，按决议补齐 |

**一句话**：TC 的可用性等于**它背后那张 DB 的可用性**，而不是它自己有几个节点。所以别把「TC 部署三个实例」当成高可用方案——三个实例连同一个库，库挂了照样不推进二阶段。

### 超时、重试与人工干预：三段账要分清

| 阶段 | 谁在计时 | 到点发生什么 | 配错的现场 |
| --- | --- | --- | --- |
| **分支本地事务超时** | 数据库 / 连接池 | 本地事务回滚，分支失败 | 配短了：正常慢 SQL 被判失败 → 全局回滚率上升 |
| **全局事务超时** | TM/TC（如 `timeoutMills`） | TC 主动发起全局回滚 | 配短了：业务还没做完就被回滚；配长了：悬挂窗口变长、锁持有变长 |
| **二阶段重试** | TC 的重试策略（次数/退避） | 反复驱动 commit/rollback | 无上限无告警 → 无限循环打日志；太早放弃 → 数据永久歪 |

**纪律**：全局超时必须**大于 P99.9 的分支耗时**、**小于**业务可接受的「不确定窗口」；二阶段重试必须有**上限 + 退避 + 每次失败打点**，并且「超过上限」必须落成一个**待人工处理队列**，而不是静默丢弃。

### 「补偿失败」必须配告警与对账（这条比前面全部加起来更重要）

补偿类方案（TCC / Saga / AT 二阶段）有一个共同的物理事实：**二阶段是一条 RPC，它可能永远失败**。所以任何一套事务组件的完备形态都是三件套：

| 防线 | 作用 | 缺了会怎样 |
| --- | --- | --- |
| **告警**（二阶段失败数、in-doubt 事务数、超时未终态事务数） | 让「补偿失败」在分钟级被人看见 | 差异静静积累到对账日才爆（事故二 3 天后才发现） |
| **对账**（两个独立记录源交叉验证） | 让「补偿错了」也能被发现，而不只是「补偿没做」 | 只能发现 A 少了，发现不了 A 少了同时 B 多了（→ eng/14） |
| **人工干预入口**（按 xid 查询 + 强制决议 + 审计日志） | 悬挂与启发式决议的唯一出路 | 只能改库，改完没有审计 |

## 43.8 三本账：全局锁的时间、undo_log 的体积、TC 的 TPS

三本账对应三个「你上了组件之后才发现要付的钱」：**锁的时长**（AT 与 XA 都要付）、**镜像的体积**（AT 独有）、**协调者的吞吐**（三者都要付，TCC 更贵因为全在业务库）。

### 账一 · 全局锁持有时间 = 分支事务时长 + 网络

AT 的全局锁不是在行上加的，而是 TC 里一条 `lock_table` 记录；但它**覆盖的时间窗**是「一阶段本地提交之前 → 二阶段完成之后」。这段时间里，同一个热点行上的第二个全局事务必须等。**乘法链**：`T_lock ≈ Σ(分支本地事务时长) + N × 2 × RTT(业务 ↔ TC) + 二阶段驱动延迟`；由此得 `热点行上限 TPS = 1,000 ÷ T_lock(ms)`，且第 M 个并发全局事务的排队时长 ≈ `(M − 1) × T_lock`。

**算例：一笔下单全局事务 3 个分支，其中一个落在热点券库存行上。**假设：① 每个分支本地事务 8 ms（单表按主键更新 + 写 undo_log）；② 业务与 TC 同 AZ，RTT = 0.8 ms；③ 二阶段 commit 是异步删除 undo_log，不计入锁窗；④ 不考虑死锁与重试。

按上式：`T_lock = 3 × 8 ms + 3 × 2 × 0.8 ms = 24 + 4.8 = 28.8 ms`，热点行上限 `1,000 ÷ 28.8 ≈ 34.7 全局事务/秒`；对照不加全局锁的本地事务上限 `1,000 ÷ 8 = 125 行更新/秒`，**上限降到 1/3.6**。并发 50 个全局事务打到同一热点行时，最后一个要等 `49 × 28.8 ≈ 1.41 秒`——这就是「上了 AT 之后 P99 突然变成秒级」的算术来源。

| 分支本地事务 | N=2 | N=3 | N=5 |
| --- | --- | --- | --- |
| 5 ms | 13.2 ms（76/s） | 19.8 ms（51/s） | 33.0 ms（30/s） |
| 8 ms | 19.2 ms（52/s） | 28.8 ms（34/s） | 48.0 ms（21/s） |
| 20 ms | 43.2 ms（23/s） | 64.8 ms（15/s） | 108.0 ms（9/s） |

> **量级结论（非承诺值）**。假设清单：① 分支数 N 即「参与的独立数据源个数」；② RTT 取同 AZ 0.8 ms，跨 AZ 取 4–10 ms 会把 T_lock 直接抬到 40–90 ms；③ 热点行串行化，与总 QPS 无关——**非热点行可以并行，热点行不行**；④ 忽略锁等待超时与重试。**换假设可复算：把 8 ms 换成 3 ms，N=3 时上限从 34/s 升到约 72/s，结论形状（「上限 = 1000 ÷ (N×本地事务 + 网络)」）不变。**

### 账二 · undo_log 体积 = 行镜像 × 变更行数 × 保留窗口

AT 的隐藏写放大在这里。每行被改的列会同时被记进 before image 与 after image，外面还套一层序列化（默认 JSON 类序列化）与 `tableMeta`。**乘法链**：`单行镜像 ≈ (列值字节 × 2) × 序列化开销 + 列名/类型元数据` → `单事务 undo_log ≈ 单行镜像 × Σ(各分支变更行数)` → `每日体积 = 单事务体积 × 全局事务 QPS × 86,400` → `占用 = 每日体积 × 保留天数 × (1 + 索引与页碎片系数)`。

**算例**：假设 ① 单行 20 列、每列值平均 20 B ⇒ 行数据 400 B；② before + after 两份 + 序列化开销约 1.8× ⇒ 单行镜像 ≈ 1.6 KB；③ 每全局事务 3 分支 × 每分支 20 行 = 60 行；④ 全局事务 30 /s；⑤ 保留 3 天；⑥ 页碎片与二级索引系数 1.3。

| 项 | 算式 | 结果 |
| --- | --- | --- |
| 单事务 undo_log | `1.6 KB × 60` | 96 KB |
| 每日新增 | `96 KB × 30 × 86,400` | ≈ 249 GB/天 |
| 占用（3 天 + 碎片 1.3） | `249 GB × 3 × 1.3` | ≈ 971 GB（≈ 0.95 TB） |
| 同期业务数据净增 | `400 B × 60 × 30 × 86,400` | ≈ 62 GB/天 |
| **写放大** | `249 ÷ 62` | **≈ 4.0 倍** |

| 变更行数/事务 | 全局事务 10/s | 30/s | 100/s |
| --- | --- | --- | --- |
| 20 行 | 27 GB/天 | 83 GB/天 | 276 GB/天 |
| 60 行 | 83 GB/天 | 249 GB/天 | 830 GB/天 |
| 200 行 | 276 GB/天 | 830 GB/天 | 2.8 TB/天 |

> **量级结论（非承诺值）**。假设清单：① 行宽与列数决定镜像大小，宽表（`TEXT`/`BLOB`）会让它爆炸；② 「保留」由清理任务决定（`undo.log.save.days` 语义为天级，默认值以目标版本文档为准），**清理任务本身也会产生删除压力与主从延迟**；③ 未计入 undo_log 表上的唯一索引写与 purge。**这条账的真正用途是容量评审：AT 的存储成本不是「业务数据的副本」，而是「4 倍左右的写入放大量」，宽表与批量更新是它的头号杀手。**

### 账三 · TC 的 TPS = 全局事务数 ÷ 平均时长（反推连接与线程）

协调者的吞吐由两件事决定：**它每秒要写多少行决议记录**、**它能同时推进多少个全局事务**。**乘法链**：`并发全局事务数 C ≈ 全局 TPS × 平均全局事务时长`（Little 定律）→ `TC 侧写入行数/秒 ≈ 全局 TPS × (1 + 2N)`（每个全局事务 1 行 global + N 行 branch + N 行 lock）→ `TC 上限 ≈ TC 的 DB 写能力 ÷ (1 + 2N)`；另一侧 `RM 并发连接 ≈ 全局 TPS × (分支本地事务时长 + 两次 RTT) × 安全系数`。

**算例**：假设 ① 全局 TPS = 300；② 平均全局事务时长 = 40 ms；③ N = 3 分支；④ TC 的 DB（关系库）可持续 5,000 行写/s；⑤ 分支本地事务 8 ms + 两次 RTT 2 ms = 10 ms，安全系数 2。

| 项 | 算式 | 结果 |
| --- | --- | --- |
| 并发全局事务（TC 同时在推的事务数） | `300 × 0.04 s` | 12 |
| TC 侧决议写入 | `300 × (1 + 2×3)` | 2,100 行/s（占 DB 能力 42%） |
| TC 上限（按 DB 容量） | `5,000 ÷ 7` | ≈ 714 全局事务/s |
| RM 侧并发连接 | `300 × 0.010 s × 2` | 6 条/分支库（远小于池上限 200） |

| 全局 TPS | 平均时长 | 并发全局事务 | TC 写入行/s（N=3） | 结论 |
| --- | --- | --- | --- | --- |
| 100 | 40 ms | 4 | 700 | 轻松 |
| 300 | 40 ms | 12 | 2,100 | TC DB 用到 42% |
| 1,000 | 40 ms | 40 | 7,000 | **TC 的 DB 先到上限** |
| 1,000 | 400 ms | 400 | 7,000 | 连接与线程开始排队，和 DB 一起打满 |

> **量级结论（非承诺值）**。假设清单：① 决议记录与业务数据**不同库**（同库会互相拖慢，这是最常见的部署失误）；② 二阶段 commit 只删 undo_log、不写决议；③ N 为平均分支数，热点场景下**真正先到上限的是账一的热点行串行化**（34/s），而不是 TC 的 DB 容量——**两本账要一起看**；④ 每次二阶段驱动的重试会额外放大 TC 写入，重试率高时把 (1+2N) 再乘重试次数。

```python
# 三本账复算：改任一假设直接重跑（Python 3.9+）
def lock_window(n, local_ms=8, rtt_ms=0.8):
    return n * local_ms + n * 2 * rtt_ms, 1000 / (n * local_ms + n * 2 * rtt_ms)

def undo_volume(rows_per_txn=60, kb_per_row=1.6, tps=30, days=3, frag=1.3):
    per_txn = kb_per_row * rows_per_txn                 # KB
    per_day_gb = per_txn * tps * 86400 / 1e6
    return per_txn, per_day_gb, per_day_gb * days * frag

def tc_capacity(global_tps, avg_ms=40, n=3, tc_rows_per_s=5000):
    rows = global_tps * (1 + 2 * n)
    return global_tps * avg_ms / 1000, rows, tc_rows_per_s / (1 + 2 * n)

for n in (2, 3, 5):
    ms, tps = lock_window(n)
    print(f"N={n}: T_lock={ms:.1f} ms → 热点上限 {tps:.1f}/s")

print("undo_log: 单事务 %.0f KB / 每日 %.0f GB / 占用 %.0f GB" % undo_volume())
print("TC: 并发=%.0f 写入=%d 行/s 上限=%.0f 全局事务/s" % tc_capacity(300))
```

## 43.9 边界：什么时候根本不需要分布式事务，什么时候用哪一档

### 第一张表先做减法：这六种情况根本不用上组件

| 你以为需要分布式事务的场景 | 为什么不需要 | 正确做法 |
| --- | --- | --- |
| **同一个库、多张表** | 本地事务已经给出原子性，跨表就是一个 `BEGIN...COMMIT` | 直接本地事务（→ comp/05、→ comp/08） |
| 同一个实例、分库分表但**同一次操作落在同一分片** | 一个分片内就是本地事务 | 分片键设计得当（→ comp/36） |
| **只写一个库 + 发一条 MQ** | 这是双写，不是分布式事务；上 AT 只会多一份 undo_log 与全局锁 | Outbox / 事务消息（→ eng/10、→ eng/11） |
| 允许秒级/分钟级最终一致，且**能容忍重复** | 补幂等键 + 重试 + 对账即可，不需要 2PC | 幂等 + 重试 + 对账（→ eng/14） |
| 一方是**外部不可控系统**（第三方支付、银行、短信） | 对方不会配合你的 prepare，物理上做不到 | 最大努力通知 + 状态查询 + 对账（→ eng/8 §8.4.6） |
| 只是为了「回滚方便」而包了一层大事务 | 长事务会锁住行与 undo 段，把故障域从「一个请求」扩到「一个库」 | 拆小事务 + 补偿（→ comp/06 长事务的代价） |

> **判据一句话**：**能用一个本地事务解决的，任何分布式事务组件都是净成本。** 这句话在评审上最有用，因为绝大多数「我们需要分布式事务」的真实情况，是「我们的库选错了或者分片键选错了」。

### 第二张表做选择：三种机制的硬对照

| 维度 | **XA / 2PC** | **Seata AT** | **TCC** | **Saga / Outbox** |
| --- | --- | --- | --- | --- |
| 一致性 | 强（提交前外部不可见） | 弱强一致（一阶段本地可见） | 强（预留期资源被隔离） | 最终一致 |
| 业务侵入 | 零（只改数据源配置） | 一行注解（**但不等于零成本**） | 高（Try/Confirm/Cancel 三套接口 + 状态机） | 中（补偿 + 幂等 + 去重） |
| 全局隔离 | 由数据库行锁给出 | **读未提交**级别，写靠全局锁 | 由你的表结构（冻结/可用分列）给出 | 无 |
| 回滚语义 | 数据库 undo（**物理精确**） | 反向 SQL（**行镜像校验**） | 业务逆操作（**必须自己写对**） | 业务补偿 |
| 性能成本 | 持锁跨网络（`PREPARED` 期间不释放） | 全局锁 + undo_log 写放大（约 4×） | 无全局锁、无镜像，但多两次 RPC | 无锁，靠异步 |
| 资源要求 | 数据库支持 XA（PG 需开 `max_prepared_transactions`） | 每库一张 `undo_log` 表 + TC 高可用 | 每服务一套状态表 | 消息可靠 + 消费幂等 |
| 最怕什么 | 协调者挂 + 热点行 | 长事务 + DDL + 关校验 | 三坑没做全 | 补偿失败没人管 |
| 适用 | 低频、跨异构资源、必须强一致（对账/资金调账） | 短事务、单表按主键、存量系统改造 | 高并发、有明确预留语义（库存/余额/额度） | 长流程、跨公司、可接受中间态 |

### 决策表：按顺序排除，五步走完

| 步 | 问 | 是 → | 否 → |
| --- | --- | --- | --- |
| 1 | 能不能塞进**一个本地事务**（同库/同分片）？ | 本地事务，结束 | 下一步 |
| 2 | 参与方里有没有**不配合 2PC 的资源**（MQ、Redis、HTTP）？ | 走**补偿类**（TCC / Saga / Outbox），跳到 5 | 下一步 |
| 3 | 有没有**明确的预留语义**（冻结、锁库存、占额度）且是**热点写**？ | **TCC** | 下一步 |
| 4 | 全局事务是不是**短**（< 100 ms）、**单表按主键**、团队无力写状态机？ | **Seata AT** | 下一步 |
| 5 | 只剩**低频、强一致、跨库**的少量场景？ | **XA**（并给每一笔配人工裁决入口） | TCC / Saga + 对账 |

**这张表的用法**：从 1 往下走，**遇到的第一个「是」就是答案**，不要回头比优劣。绝大多数团队的正确答案落在第 1 步或第 5 步之外的补偿类——这也是为什么大厂主推最终一致（→ eng/8 §8.4.7），而不是因为 XA「技术落后」。

## 43.10 踩坑清单（现象 → 根因 → 定位 → 修复 → 防复发）

| 现象 | 根因（指到物理形态） | 定位 | 修复 | 防复发 |
| --- | --- | --- | --- | --- |
| 某几张表突然大面积锁等待，连接池打满 | XA 分支停在 `PREPARED`，行锁 + undo 段 + 会话全被占 | `XA RECOVER`；查 `information_schema.innodb_trx` 里 `trx_state='PREPARED'` | 按全局日志裁决 commit/rollback；必要时 `XA DETACH` 先还连接 | 协调者优雅停机、全局超时、in-doubt 数告警 |
| 应用重启后出现「一半成功一半失败」的数据 | TM 未持久化全局决议就崩了，部分分支被启发式处理 | 对比两库同一 biz_id 的记录；看驱动是否抛 `XAER_HEURHAZ` | 人工修数 + 记录审计 | 不要在应用进程里做 TM；给悬挂分支配人工入口 |
| AT 回滚后数据比预期「多」或「少」 | 反向 SQL 的 after image 校验被关掉/缺失，覆盖了并发写 | 查该 xid 的 `undo_log.rollback_info`；比对 `log_modified` 与业务行更新时间 | 打开校验开关；冲突的分支转人工 | 禁止在 AT 覆盖范围内关校验；对热点行加 `@GlobalLock` |
| 二阶段一直失败、日志刷 `BranchRollbackFailed` | 行镜像与当前行不匹配（别人先改了），或 `undo_log` 已被清理 | 按 xid 搜 undo_log（可能已不存在）；看清理任务删除边界 | 人工按业务语义修数；必要时扩展保留窗口 | 全局事务时长 << undo_log 保留窗口；清理任务打点 |
| 某个库的分支永远回滚不了 | 该库缺 `undo_log` 表，或多数据源漏配代理 | 报错含表不存在/数据源未代理 | 补表、补代理配置 | 上线检查清单里加「每个参与库都有 undo_log」 |
| 全局事务里夹了 DDL，回滚后表结构与数据都不对 | MySQL DDL 隐式提交，undo_log 与业务 DDL 不同事务 | 看 binlog 时间点与全局事务时间窗重叠 | 拆开：DDL 独立窗口执行 | 变更窗口与全局事务互斥 |
| TCC 出现「冻结永远不解」，用户余额少了 | 悬挂：Cancel 先到并完成，Try 后落库 | 查冻结表里 `status=FROZEN` 且全局事务已 `CANCELLED` 的行 | 按 xid 人工解冻 + 补偿 | Cancel 必须落占位行；Try 必须查占位行 |
| TCC 重复解冻，余额凭空多 | Cancel/Confirm 没有幂等（无条件 UPDATE） | 分支表 `cancel_count > 1`；冻结行状态流转异常 | 用状态机条件更新重写补偿接口 | 所有补偿接口必须 `WHERE status = 期望值` |
| 空回滚把别人的冻结解掉了 | Cancel 无 Try 时按「uid + 金额」模糊匹配到了旧记录 | 补偿 SQL 的 `WHERE` 条件 | 补偿必须按 `xid` 精确匹配 | 冻结表 `xid` 唯一键 |
| TC 在、但事务永远不推进 | TC 的 DB 挂了或锁表冲突，二阶段驱动失败 | TC 日志 + `global_table` 里 `status` 长期不变 | 恢复 TC 的 DB；补驱动 | TC 的 DB 独立部署 + 未终态事务数告警 |
| 上线 AT 后 P99 翻倍 | 全局锁把热点行串行化（账一） | 全局锁等待时间、热点行冲突次数 | 拆小全局事务、减少分支数、非核心链路降级为最终一致 | 容量模型按「热点行 TPS = 1000 ÷ T_lock」算 |

## 43.11 观测：五个数覆盖 90% 的分布式事务故障

| 指标 | 看什么 | 拐点阈值 | 版本 / 开关前提 |
| --- | --- | --- | --- |
| **全局事务数与平均时长** | 事务量是否上升、时长是否变长（时长涨 = 悬挂前兆） | 平均 > 100 ms 或 P99 > 1 s 告警 | AT 取自 TC 的 `global_table` 统计；XA 需自己在 TM 侧埋点 |
| **回滚率**（rollback / 全局事务数） | 失败分支是否在放大（回滚率涨 → 全局锁与 undo_log 都涨） | > 1% 关注，> 5% 告警 | 与业务错误率联看，别只看绝对值 |
| **in-doubt / 未终态事务数** | 有没有悬挂（XA 的 `PREPARED`、AT 的 `TRYING`、TCC 的 `TRIED`） | > 0 持续 5 分钟即告警 | MySQL 侧用 `XA RECOVER` 或 `innodb_trx.trx_state`；注意 `XA RECOVER` 需相应权限 |
| **undo_log 体积与清理延迟** | 账二的增长、磁盘水位、清理任务是否跟上 | 日增长 > 预算 120%，或清理滞后 > 1 天 | 依赖 `undo.log.save.days` 一类保留配置，默认值以目标版本文档为准；清理是定时任务，要单独打点 |
| **全局锁等待 / 热点行冲突** | 账一是否成为 P99 主项 | 等待 P99 > 10 ms | Seata 侧看 `lock_table` 冲突与重试；需要打开 TC 的指标端点 |
| **二阶段重试次数与失败数** | 补偿能不能收敛（最该告警的一条） | 连续失败 > 3 次即告警 | 重试策略（次数/退避）随版本变化，不能拿别处默认值当自己的 SLO |

> 指标纪律：**全局事务数一定要与业务单量对照看**。单量没涨而全局事务数涨 ⇒ 有链路在重复提交（客户端重试把同一个业务动作包成了多个全局事务）；单量涨而回滚率涨 ⇒ 热点行冲突或超时配置不对。另外，把「未终态事务数」当成第一指标：它是唯一能同时抓到 XA 悬挂、AT 卡回滚、TCC 悬挂的一个数。

## 43.12 一页速记

| 问题 | 一句话答案 |
| --- | --- |
| 事务组件产生原子性吗 | **不产生**；原子性来自各参与方的本地事务，组件只做协调、记录、重试 |
| XA 慢在哪 | `PREPARED` 期间持锁 + 占连接，等一个可能已经死掉的协调者 |
| prepare 后协调者挂了会怎样 | 分支悬挂：锁不释放、连接被占、只能 `XA RECOVER` 后人工裁决 |
| 启发式提交能用吗 | 不能用来治悬挂；它把「不确定」变成「确定但可能错」 |
| AT 的一阶段做了什么 | 解析 SQL 生成行镜像 → 申请全局锁 → 本地事务写业务 SQL + `undo_log` → 上报 TC |
| AT 的回滚是什么 | 用 before image 生成反向 SQL，用 after image 做乐观校验 |
| AT 的隔离级别 | 全局层面近似读未提交；写隔离靠全局锁，读要自己加 `@GlobalLock + FOR UPDATE` |
| AT 能不能回滚任何 SQL | 不能：跨库 JOIN、动态表名、DDL、非事务资源都不行 |
| TCC 三坑 | 空回滚、悬挂、幂等——一件证据行（`xid` 唯一键 + 状态机）能同时管住 |
| Confirm 里能做校验吗 | 不能；Confirm 不允许失败，校验必须前置到 Try |
| 热点行上限怎么算 | `1,000 ÷ (N × 分支本地事务 ms + N × 2 × RTT ms)` |
| undo_log 有多大 | 约 4 倍写放大：`行镜像 × 变更行数 × 事务数 × 保留天数` |
| 什么时候不用分布式事务 | 能塞进一个本地事务、能接受最终一致 + 幂等 + 对账 |
| 最该监控的两个数 | 未终态事务数、二阶段失败数 |

## 43.13 自检题（5 题，答案要点）

**1. 一笔全局事务 3 个分支、每个分支本地事务 8 ms、同 AZ RTT 0.8 ms，热点行每秒最多跑多少个全局事务？为什么不是 125？**

`T_lock = 3 × 8 + 3 × 2 × 0.8 = 28.8 ms`，上限 ≈ `1,000 ÷ 28.8 ≈ 34.7/s`。125/s 是「只算一次本地事务」的算法，它忽略了：① 三个分支的本地事务都发生在同一个全局锁窗口内；② 全局锁要到二阶段完成才释放；③ 每次与 TC 的两趟往返也在这个窗口里。**热点行的上限由「全局事务的完整时间窗」决定，不由单条 SQL 的执行时间决定。**

**2. AT 的一阶段已经把数据提交了，那它凭什么说能回滚？回滚会不会回错？**

凭 `undo_log` 里的 before/after 行镜像：二阶段用 before image 生成反向 SQL，用 after image 作条件做乐观校验。**会回错**，条件就是：① after image 校验被关掉或缺失 → 变成无条件覆盖（事故二）；② 中间有人改了这行 → 校验失败，回滚报冲突，只能人工。所以 AT 的「能回滚」是有前提的：短事务 + 行镜像完整 + 校验开启 + 有对账。

**3. TCC 的「空回滚」和「悬挂」到底差在哪？为什么一张 `xid` 唯一键能同时治住两者？**

空回滚是 **Cancel 先到、Try 根本不存在**；悬挂是 **Cancel 先完成、Try 后到并生效**。两者的共同点是「Cancel 与 Try 的顺序错了」。在冻结表上给 `xid` 建唯一键后：Cancel 找不到记录时先插一条 `status=CANCELLED` 的占位行；后来 Try 想插入同 `xid` 的冻结行就会撞唯一键（或读到占位状态），于是拒绝落库——**一次写入同时解决了「Cancel 要留痕」和「Try 不许生效」**。

**4. 为什么说 TC 部署三个节点不等于高可用？**

TC 的决议状态（`global_table`/`branch_table`/`lock_table`）落在它背后的 DB 里。三个节点连同一个库，库不可用或写不动时，三个节点都推不动二阶段——**可用性等于那张 DB 的可用性**。真正的高可用配置是：TC 的库与业务库分离、库本身有主从/切换、二阶段驱动是幂等的（多节点重复驱动不出错）、以及未终态事务数有告警。

**5. 一笔业务要不要上分布式事务组件？请用五步决策表走一遍「下单扣库存 + 扣积分」。**

① 能塞进一个本地事务吗？库存与积分在不同库 ⇒ 不能。② 有不可配合的资源吗（MQ/HTTP）？若还要发消息 ⇒ 有，走 Outbox（→ eng/10）；若只是两个库 ⇒ 没有。③ 有明确的预留语义且是热点写吗（库存冻结）⇒ **是** ⇒ TCC。④ 若团队无力写状态机、且全局事务很短（< 100 ms）、单表按主键 ⇒ 退一步用 AT。⑤ 若只剩极少量强一致调账场景 ⇒ XA + 人工裁决入口。**结论：主链路用 TCC 或「本地事务 + Outbox + 对账」，XA 只留给调账与对账工具。**
