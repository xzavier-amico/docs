# 《存储与中间件剖析：内核形态决定架构边界》· 总纲

> **一句话**：前面五套讲「该选哪个零件」和「零件装上去会怎么炸」，这一套把零件**拆开**——讲清它的数据在磁盘和内存里长什么样、一次读要碰几层、一次写要落几份日志，于是「它为什么快」「它为什么做不到」「它什么时候必须换掉」全部变成推论，而不是经验。
>
> 读者画像：能背出「加 Redis 做缓存、上 Kafka 解耦、用 ES 做搜索、用 vLLM 起个推理服务」这句话，但被追问「ES 的倒排到底怎么找到 doc」「acks=all 到底保证了什么」「MySQL 可重复读怎么看到旧数据」「PagedAttention 到底分页了什么」时只能答「就是那样的」的后端与架构师。

| 项 | 说明 |
| --- | --- |
| 定位 | **内核机制 → 架构边界**。每篇只回答一个「这个零件为什么只能这样」的问题 |
| 篇幅规划 | 11 个部分 · **53 篇** · 每篇 1 个文件 · 单篇 1.2 万–2.5 万字 |

## 0.1 这套书要解决的那个问题

架构评审上的四句话，正好对应四种「知其然不知其所以然」：

```
「ES 查一下就行」          → 不知道倒排是「不可变段 + 近实时」，搜不到刚写的数据不是 bug
「Kafka 保证不丢」         → 不知道 acks/ISR/HW 怎么组合才叫不丢，unclean 选举买的是什么
「MySQL 可重复读没问题」    → 不知道快照是「undo 版本链 + Read View」，不知道长事务会撑爆什么
「起个 vLLM 就行」         → 不知道 KV cache 决定显存上限与并发数，于是「为什么只跑到 8 并发」永远算不出来
```

`eng/` 讲这些功能的**实现与坑**，`architect/` 讲**形态决策与换挡**，`llm/` 讲平台侧**治理策略**。缺的那一层是：**零件的内部结构本身**。而恰恰是这一层决定了上面三套的结论能不能成立。

**一个论断先立在这里**（全篇反复回到它）：

> **每一个组件的能力上限，都是它「数据物理形态」的直接推论。**
> 段不可变 ⇒ ES 只能近实时，更新等于删+写，分片数定错只能重建；
> 只追加日志 ⇒ Kafka 快得不讲道理，但删除与随机改必须绕着走；
> 旧版本挪进 undo ⇒ InnoDB 回滚快、但长事务会把 undo 表空间和 purge 拖死；
> KV cache 按页管理 ⇒ 推理服务的并发数由显存与序列长度算术决定，不是由 GPU 算力决定。
> 你背下的每一条「最佳实践」，都能在物理形态里找到它的出生证明；找不到的那些，通常是过时的。

## 0.4 解剖一个组件的八问（全系列统一的尺子）

每篇都按同一张卡展开，**缺一问不算讲透**：

```
① 它承诺什么        一句话契约 + 明确不承诺什么（给反例：什么不叫"实时"、什么不叫"不丢"）
② 数据长什么样      磁盘/内存里的物理形态（页 / B+ 树节点 / 段 / 日志分段 / 对象 / 槽 / KV 块）
③ 一次读写走哪条路  链路图 + 每一跳的耗时量级（μs / ms / 跨机 RTT），不许只写"较快"
④ 并发与一致        锁 / 版本链 / 共识协议 / 提交位点 / 租约 / quorum，以及它们的失效窗口
⑤ 扩展维度          四选一写清：分片 / 副本 / 垂直切 / 批处理摊薄；
                    若四者都不成立，就明说「它不可横向扩，只能换零件」——不许硬凑
⑥ 会在哪崩          只写**系统级失效**：集群不可用 / 数据不一致 / 成本失控（慢·满·脑裂·假活·语义漂移，见 52 篇）；
                    使用级错误（索引建错、参数设错）归 ⑦ 踩坑清单，两节不许互相稀释
⑦ 看哪几个指标      3–5 个能提前十分钟报警的数字 + 拐点 + **版本与开关前提**
⑧ 换掉它的信号      什么阈值越过后它不再是正确选择（对应 architect 的换挡表）
```

> ⑤ 第六问经 5 篇试水后改过口径：原「怎么横向扩」对单机组件（InnoDB、推理引擎单卡）是硬套，会写出别的套里已有的废话；改成「**扩展维度**」后，答案是「分片 / 副本 / 垂直切 / 批处理摊薄四选一，或者直说不行」。⑥ 同步收紧为系统级失效，与踩坑清单分工。

### 三本放大账（选型时真正在比的东西）

| 账 | 定义 | 典型受害者 |
| --- | --- | --- |
| **写放大** | 你写 1 字节，磁盘实际写多少 | LSM（compaction 反复重写）、ES（merge）、InnoDB（页分裂 + 双写 + 三份日志）、Flink checkpoint |
| **读放大** | 你读 1 行，实际碰了多少页/段/层 | LSM（每层都要看）、二级索引回表、ES 多段查询、ANN 走图、带过滤的向量检索 |
| **空间放大** | 逻辑数据 1 GB，占盘/占显存多少 | MVCC 旧版本（PG 表膨胀、InnoDB undo）、LSM 多层冗余、副本数、ES 的 `.del`、KV cache |

> **选组件从来不是"哪个更好"，而是"你愿意在哪一本账上付钱"。** 本套每一篇都会把这三本账算一遍。

## 0.6 各篇清单与「唯一真问题」

### Part I · 地基（4 篇）

| 编号 | 标题 | 唯一真问题 |
| --- | --- | --- |
| 01 | 怎么解剖一个组件：八问卡与三本放大账 | 读懂组件不是记住配置项，而是能画出「数据长什么样、一次读碰几层」，其余都是推论 |
| 02 | 存储引擎三形态：B+ 树、LSM 与列存 | 三种引擎的写放大/读放大/空间放大不可能同时小，**选引擎就是选在哪一栏付钱** |
| 03 | WAL、缓冲池与崩溃恢复 | 「已提交不丢」靠的不是立刻刷数据页，而是**先写日志、再改页、能重放**这个顺序 |
| 04 | 索引的本质：B+ 树页、回表与最左前缀 | 索引不是加速器，是**用一份额外的有序数据换一次少扫**；每建一个都要在写入上还债 |

### Part II · 关系库与事务内核（7 篇）

| 编号 | 标题 | 唯一真问题 |
| --- | --- | --- |
| 05 | InnoDB 的页与行：聚簇索引、行格式与溢出 | 「表」其实是**一棵以主键为键的 B+ 树**，这一条事实推出全部索引与主键设计纪律 |
| 06 | MVCC 与隔离级别：undo 版本链与 Read View | 可重复读不是「锁住了」，是**给你一个旧版本视图**；快照活多久决定 undo 会不会涨爆 |
| 07 | 锁：行锁、间隙锁、意向锁与死锁 | InnoDB 的锁加在**索引**上不是行上，「以为锁一行，其实锁一段区间」是所有超时与死锁的根 |
| 08 | redo / undo / binlog 与内部两阶段提交 | 一次提交要落三份日志，而「binlog 与 redo 一致」只能靠**内部 2PC + 组提交**用吞吐换 |
| 09 | 优化器与执行计划：索引为什么会「失效」 | 索引失效九成不是没建索引，是**优化器算完全表扫更便宜**；不懂成本模型就只能猜 |
| 10 | 主从复制与高可用：半同步、并行回放与 MGR | 复制延迟不是网络慢，是**并行回放度 + 大事务**；读到旧数据的代价必须由业务定价 |
| 11 | PostgreSQL 对照：堆表、xmin/xmax 与 VACUUM | 同为 MVCC：PG 把旧版本留在表里，InnoDB 挪进 undo —— 于是**一个表膨胀，一个 undo 膨胀** |

### Part III · 内存与无主 KV（5 篇）

| 编号 | 标题 | 唯一真问题 |
| --- | --- | --- |
| 12 | 单线程的真相：事件循环、为什么快、多线程在哪 | 快不是因为单线程，而是**内存 + 无锁 + 一次 epoll 批处理**；单线程意味着一个慢命令停掉所有人 |
| 13 | 数据结构与底层编码：ziplist、listpack、skiplist | 每个结构都有「小数据用紧凑编码、大了换真结构」的**阈值**，大 key 与 O(N) 灾难都长在这条线上 |
| 14 | 持久化与主从同步：fork、COW 与 replication backlog | fork+COW 决定「内存越大，快照越像一次心跳停跳」；全量同步决定你何时被一次重启打爆带宽 |
| 15 | Cluster：16384 槽、MOVED/ASK 与扩容迁移 | Cluster 只解决**分片**不解决**一致性**；槽迁移期间的 ASK 重定向是多 key 与事务失效的根 |
| 16 | 一致性哈希与 quorum：Dynamo 家族的 N/R/W | 无主架构把一致性交给**副本数算术**：`R+W>N` 买到的是「读得到最新」，买不到「不会冲突」 |

### Part IV · LSM 族与分析（4 篇）

| 编号 | 标题 | 唯一真问题 |
| --- | --- | --- |
| 17 | MongoDB：BSON、WiredTiger 与 oplog | 「文档级原子」只保**单文档**，跨文档一致性得自己在应用层补；oplog 是重放幂等的唯一依据 |
| 18 | HBase：LSM、Region 与 RowKey 设计 | 性能不是调优出来的，是 **RowKey 设计**出来的：单调递增的键会把整个集群压在一个 Region |
| 19 | RocksDB 与 TiKV：可嵌入 LSM + Raft + PD | NewSQL = **一个能嵌进进程的 LSM + 一层共识 + 一个全局调度器**；看懂这三件的组合，就懂分布式事务为什么敢便宜 |
| 20 | ClickHouse / MergeTree：列存为什么快、为什么不能当主库 | 列存用「连续 + 向量化 + 稀疏索引」换扫描吞吐，代价是**点更新与事务几乎不存在** |

### Part V · 检索与向量（7 篇）

| 编号 | 标题 | 唯一真问题 |
| --- | --- | --- |
| 21 | 倒排索引的物理结构：一个 term 怎么找到 doc | 倒排 = **词典(FST) + 有序倒排表 + 跳表 + 位置信息**，「全文搜索为什么快」的答案全在「有序」两个字 |
| 22 | 段：不可变、refresh、flush 与 merge | 段不可变是 ES 的宪法：可见性靠**新开段**，更新其实是**删一条 + 写一条**，删除只在 merge 时才真正消失 |
| 23 | 集群形态：分片、副本、路由与 master 选举 | 一次写是「协调节点按 _routing 选分片 → 主 → 副本」，一次查是「扇出再归并」，**分片数定错只能重建** |
| 24 | 查询执行：query vs filter、BM25、scroll 与深分页 | 算分与筛选是**两条执行路径**，90% 条件该进 filter；`from+size` 在分布式下必然爆，才有 scroll/search_after |
| 25 | 容量与故障：mapping 爆炸、堆、merge 与零停机重建 | ES 的 SLO 不是「查询快」，是**段数、字段数、堆占用**三条线不失控，破了之后救回来等于重建 |
| 26 | 向量索引内核：HNSW 图、IVF 与 PQ 码本 | ANN 是**用正确率换延迟**的合约，每种结构都有崩盘点：召回悬崖、内存上限、构建超时 |
| 27 | 向量库的工程形态：Milvus / Qdrant / pgvector 与混合检索 | 向量检索真正的难点是**带标量过滤的 ANN**：过滤越严，图遍历越容易走进死路，pre-filter/post-filter 各有代价 |

### Part VI · 消息、流与定时（9 篇）

| 编号 | 标题 | 唯一真问题 |
| --- | --- | --- |
| 28 | Kafka 的日志：segment、稀疏索引与零拷贝 | 快的真实原因是**只追加 + 顺序 IO + page cache + sendfile**，这也解释了为什么它不能删、不能改 |
| 29 | 复制与一致性：ISR、HW、LEO 与 acks | 「不丢」是一组参数的联合体；unclean 选举是**拿丢数据换可用**，而这个选择必须写进业务预案 |
| 30 | 消费组与 rebalance：协议、位点与积压 | rebalance 是「所有人停下重分家务」，位点提交时机**就是**语义；积压不是容量问题，是并行度问题 |
| 31 | 消息族谱：RocketMQ / Pulsar / RabbitMQ / NATS | 队列的差异不在吞吐，在**语义形状**：事务消息、延迟等级、推 vs 拉、存算分离，选错就得在业务里补一层 |
| 32 | 任务队列语义：SQS、Redis Streams、可见性超时与死信 | 「被取走但没做完」这个状态没有任何队列能替你解决，**可见性超时 + 幂等 + 死信**才是完整答案 |
| 33 | CDC：Debezium / Canal 与「快照 + 增量」衔接 | CDC 的难点不是解析 binlog，是**全量快照与增量的位点衔接**，以及 schema 变更把消费者打死 |
| 34 | Flink：checkpoint、watermark、状态后端与背压 | 流处理正确性靠**状态 + 对齐 checkpoint**，而延迟与正确性在 watermark 上直接对赌 |
| 35 | Iceberg / 表格式：快照、清单与 COW vs MOR | 数据湖从「一堆文件」变成「一张表」靠的是元数据快照；**小文件与频繁更新**是它永远在还的债 |
| 36 | 定时与延迟：时间轮、延迟队列与事务消息回查 | 定时不是「到点执行」，是**到点能被发现**；三种实现对应三种精度与代价 |

## 0.7 每篇固定骨架（写作公约）

```
① 引子        2–3 起「没人报错」的故障，带时间线与代价（金额/条数/小时）
② 唯一真问题   一句话。说不出来不许动笔
③ 物理形态     磁盘/内存结构图（ASCII），标尺寸与量级
④ 一次读写链路  逐跳 + 耗时分解表（μs/ms/RTT），标出每一步的放大倍数
⑤ 架构边界     能做什么 / 不能做什么 / 靠什么绕过（三列对照）
⑥ 踩坑清单     现象 → 根因（指到物理形态）→ 怎么定位 → 怎么修 → 怎么防复发
⑦ 观测          3–5 个指标 + 拐点阈值 + 告警表达式骨架
⑧ 一页速记 / 自检题 / 延伸阅读（锚点式引用，禁写"上文/上一篇"）
```

**纪律**：
1. **数字纪律**：所有延迟、QPS、容量、放大倍数必须给推导式，禁止「很快」「大量」「一般」。
2. **锚点引用**：`→ architect/17 §17.3`、`→ eng/24`，编号一旦发布冻结。
3. **只讲机制不堆参数**：配置项只出现在「它改变了哪条物理路径」的上下文里。
4. **代码纪律**：单段 ≤ 40 行，客户端骨架为主；不贴 JDK/内核/框架源码，最多贴结构体定义。
5. **无占位**：任何 `TODO`、「待补充」不许进仓库（`check.sh` 会拦）。

**试水批（05/06/21/22/49）复盘后追加的三条**，违反即返工：

6. **版本常量纪律**：一切"恒定值"只允许两种写法——**引用源码常量名**（如 `REC_MAX_DATA_SIZE = 8126`）或**给区间并说明自适应**（如 BlockTree block 内有 25~48 项）。**禁止编造分项拆分**：8,126 = 「5 B 记录头 + 61 B 各项」这种对不上公开资料的拆法，是给评审送把柄；宁可写"引擎常量，注释即半页"。
7. **指标纪律**：每条指标必须带 **版本 + 开关前提**。反例：`Innodb_history_list_length` 在 8.0 需先 `innodb_monitor_enable`；`innodb_undo_tablespaces` 在 8.0 已弃用，改为在线 `CREATE/DROP UNDO TABLESPACE`；`Seconds_Behind_Master` 在并行复制下会撒谎。写错一个指标名，读者就会认为全篇没验证过。
8. **数字性质纪律**：每个大算例末尾标一行——**「量级结论」还是「承诺值」**。量级结论必须附假设清单，让人能换假设复算（例：49 篇的「上下文 3.8K→32K，卡数涨约 19 倍」是量级结论，换 MFU 假设会在 10–25 倍浮动，不得当承诺值引用）。
