## 38.1 引子：三起「注册中心 / 配置中心自己成了故障源」的事故

这一节的三个故事有一个共同形状：**基础件本身没有挂**。三个集群的进程都在、CPU 之前都不高、控制台上没有一条红色告警。出事的是三件从未被当成「容量与语义」对待的东西——**一次变更要发多少条推送、一次检查超时意味着什么、一次配置发布同时命中多少实例**。它们都不是功能，所以没人给它们做设计评审。

### 事故一：一次平台级发布触发全量实例推送，注册中心 CPU 打满，业务 P99 跟着抬（2026-02-18）

某零售中台：**10,000 个服务实例**（Java 为主，Spring Cloud + Dubbo 混跑）、**500 个服务**，注册中心是 Nacos 2.x 三节点集群（每节点 16 vCPU / 32 GB，客户端走 gRPC 长连接）。订阅关系是历史包袱的形状：普通实例平均订阅 30 个服务；另有 **1,000 个网关/聚合层实例在启动时一次订阅全部 500 个服务**（本地要维护「全量路由表」）。

02-18 20:00，平台组一次性升级 12 个基础 SDK（注册中心客户端、日志 agent、监控 agent 同一个版本），触达全部 8,000 个业务实例重启。每次重启 = 1 次注销 + 1 次注册 = 2 个变更事件。

| 时刻 | 事件 | 关键数字 |
| --- | --- | --- |
| 20:00 | 平台级发布开始，8,000 实例滚动重启 | 8,000 实例 → 16,000 事件 |
| 20:00–20:30 | 变更事件摊到 500 个服务 ≈ **每服务每 56 秒一个事件**；合并窗口（默认百毫秒级）完全帮不上 | 9.6e6 条推送 |
| 20:04 | 客户端 `subscribe` 回调里做的是「标脏 + 回源 `selectInstances`」，不是「用推送体更新缓存」 | 每实例 30 次回源 |
| 20:06 | 注册中心 QPS 从 4,000 涨到 **16 万**（≈ 9.6e6 推送 × 30 次回源 ÷ 1,800 s） | 40 倍 |
| 20:09 | 三节点 CPU 打满，单次 `selectInstances` P99 从 5 ms 到 **8.4 s**；客户端 read timeout 3 s → 失败重试 ×3 | 超时率 62% |
| 20:10–20:25 | 重试把回源 QPS 再叠 3 倍；服务端 young GC 从 40 次/分涨到 380 次/分（每次推送 5 KB 序列化 + gzip） | GC 时间占比 41% |
| 20:12 | **业务侧跟着崩**：每个实例 25 分钟里多分配约 1.2 GB 垃圾（接收 + 解析推送体），业务 P99 从 40 ms 到 780 ms | 12 个服务 SLO 破 |
| 20:31 | 止血：把网关的全量订阅降为按需订阅 + 客户端改「用推送体更新缓存」+ 服务端限速 | 25 分钟 |
| 复盘 | 下单失败 12.6 万次、客诉 380 单；修复把回源 QPS 拉回 4,000 用时 4 天 | ≈ 46 万元 |

**乘法链**：`16,000 事件 × 600 平均订阅者 = 9.6e6 条推送 → 每条 5 KB（20 实例 × 250 B）= 48 GB 出方向 → 客户端每收到一条就回源 30 次 → 2.9e8 次查询 ÷ 1,800 s = 16 万 QPS → 每次查询 0.3 ms CPU = 48 core`，正好等于集群总核数 3 × 16。**推送不是终点，推送是「让客户端再来一次查询」的扳机**——这一点在事故复盘会上被反复确认：真正的放大倍数是「推送条数 × 每客户端的回源次数」，不是推送条数本身。

### 事故二：健康检查超时被当成「实例死了」，9 秒摘掉 80% 实例，38 分钟全站不可用（2026-05-09）

同一个中台的核心交易服务 `order-api`：400 个实例，健康检查配置是 `interval=3s`、`timeout=2s`、`连续失败 3 次判不健康`（≈ 9 秒生效）。检查端点 `/healthz` 里除了「进程活着」，还做了三件事：**查一次数据库 `SELECT 1`、ping 一次 Redis、对一个下游做一次 HTTP 探测**——因为「探针要反映真实可用性」是上一任架构师留下的原则。

05-09 20:14，MySQL 主库因为一次统计任务把 `innodb_buffer_pool` 扫穿，查询 P99 从 8 ms 涨到 2.6 s。

| 时刻 | 事件 | 关键数字 |
| --- | --- | --- |
| 20:14:02 | 统计任务开跑，DB 查询 P99 抬到 2.6 s | — |
| 20:14:05 | `/healthz` 里的 `SELECT 1` 排队超时：**400 实例 ÷ 3 s = 133 QPS 的探针查询压在已经变慢的库上** | 额外 133 QPS |
| 20:14:09 | 第一轮失败率 84%（探针 timeout 2 s < DB P99 2.6 s） | 84% |
| 20:14:14 | 连续 3 次失败 → 摘除 336 个实例；注册中心只剩 64 个健康实例 | 摘除 84% |
| 20:14:16 | 剩余 64 实例承接全部流量（每实例 QPS ×6.25），连接池打满 → 它们也探针超时 | 第二波摘除 |
| 20:14:40 | 健康实例降到 12 个；`order-api` 事实上不可用（且这 12 个正在被打死） | 可用实例 3% |
| 20:20 | 值班发现「注册实例数没变、健康实例数塌了」，误判为「Nacos 出问题」，重启注册中心 → 客户端全量重连，情况更糟 | 无效动作 |
| 20:52 | 修：探针只判进程与端口（`liveness` 与 `readiness` 分离）+ 打开保护阈值 0.6 + 把 `SELECT 1` 从探针里删掉 | 恢复 38 分钟 |
| 复盘 | 全站不可用 38 分钟，赔付与补偿 310 万元；事后统计「摘除的 336 个实例里 **一个都没死**」 | ≈ 310 万元 |

**这起事故的技术核心只有一句：`timeout=2s` 判的不是「实例死了」，判的是「这一刻本机探针拿不到应答」。** 而探针和业务共用同一个被压垮的依赖（DB），于是「依赖慢」被翻译成「实例死」，注册中心的摘除逻辑忠实地执行了这个错误结论。更糟的是**摘除会重新分配流量**，它把「慢」升级成「过载」，过载又让剩下的实例探针超时——这是一个正反馈，跑完只要 26 秒。

### 事故三：配置没有灰度，一次推全量让 5,000 个实例同时重建连接池（2026-07-21）

某 SaaS 平台用 Apollo 管配置，客户端 5,000 个实例（K8s 上的 1,250 个 Pod × 4 副本），配置模型 `AppId=order-svc / Cluster=default / Namespace=application`。7 月做「连接池扩容专项」，把 `db.pool.max` 从 `20` 改成 `200`（生产库 `max_connections=2,000`），走的是**标准发布流程**：Portal 提交 → 审批 → 发布 → 客户端长轮询 3 秒内收到。

| 时刻 | 事件 | 关键数字 |
| --- | --- | --- |
| 21:10:00 | 发布 `db.pool.max=200`，Apollo 写入 `ReleaseMessage`，Config Service 1 秒内扫到并通知 | 1 次发布 |
| 21:10:03 | 5,000 个实例全部收到通知并回源拉取（5,000 × 40 KB = 200 MB 出方向） | 3 秒内全量 |
| 21:10:05 | 连接池重建开始：`5,000 实例 × 200 = 100 万` 期望连接 vs 库端 `2,000` | 500 倍超配 |
| 21:10:06–21:10:09 | MySQL 拒绝连接，报 `Too many connections`；已有连接被挤掉，连接风暴自我强化 | 建连失败率 99.8% |
| 21:10–21:32 | 所有写接口 500；业务侧重试把读流量放大 4 倍，主库 CPU 100% | 22 分钟 |
| 21:32 | 回滚配置（Apollo 支持回滚到上一个 Release），但**回滚也是全量推**，第二次风暴 | 再 6 分钟 |
| 21:38 | 人工摘掉一半实例的流量、分批放量恢复 | 恢复 |
| 复盘 | 写入失败 116 万笔，客诉 2,100 单；「如果只推 1%（50 个实例），最坏损失是 50 个 Pod 的连接数」 | ≈ 180 万元 |

**注意 21:32 那一行**：回滚动作和被回滚的发布**形状完全一样**——都是一次全量推送。**没有灰度的配置中心，连「撤销」都是一次全量变更**，这是它比其他基础件更危险的地方：你可以在一分钟内把一个错误的参数推给所有实例，而把它收回来同样是一分钟内的第二次全量命中。

> 🩸 **三起事故的共同点**：没有一次是「注册中心挂了」。事故一是**推送的放大倍数没人算过**（推送 → 回源 → 重试，三层乘起来是 120 倍）；事故二是**检查超时的语义被误读**（探针的可用性 ≠ 实例的可用性）；事故三是**变更的作用域没有中间档**（要么 1 个 Pod，要么 5,000 个）。这三件事分别对应本篇的三本账、健康判断链、配置发布模型，也是**本篇的唯一真问题**。
>
> **一句反直觉的结论先放这里**：注册中心与配置中心是极少数「**越重要，越只能用弱保证**」的组件。它们的数据必须能被客户端缓存（否则它们自己变成单点），缓存又必须允许过期（否则它们成为强一致瓶颈）。于是所有真正的防线都不在服务端，而在三处：**客户端的缓存与降级、服务端的限速与保护阈值、发布流程的灰度与回滚**。

## 38.2 一句话定位与唯一真问题

**定位**：注册中心（Nacos naming、Consul catalog、Eureka 类）与配置中心（Nacos config、Apollo、Consul KV）在工程上经常被同一个进程、同一套运维托管，但它们是**两种不同的数据**：注册中心存的是「**谁现在活着**」（高频写、短生命周期、允许丢一点、必须随时可读），配置中心存的是「**应该是什么**」（低频写、长生命周期、不允许丢、必须能追溯版本）。这两种数据的形状决定了它们的一致性选择、推送方式和失败形态完全不同。

### 唯一真问题

> **它被所有服务依赖却只能尽力而为：推送风暴、健康检查误判、配置没有灰度，三件事各自能打垮集群。**

拆成四条推论，全篇都在给它们找证据：

1. **「被所有服务依赖」意味着它的每一次错误都乘以全站。** 一个 10,000 实例的注册中心做错一次推送，等价于 10,000 个进程同时做错一件事。所以它的**单位成本不是「一次请求」，而是「一次请求 × 订阅者数」**——这是 §38.7 与 §38.9 账二的全部内容。
2. **「尽力而为」不是实现质量问题，是设计前提。** 注册中心必须选 AP（分区时继续可读），因为它的读方是「正在启动的实例」，读不到就没法启动；配置中心必须能返回「上一个版本」，因为它的写方是人。**这两条都不是缺陷，而是它存在的理由**（§38.6）。
3. **三件事的故障形态都是「假活」与「雪崩」，而不是「宕机」。** 推送风暴表现为注册中心「活着但答得慢」；健康检查误判表现为「实例活着但被摘掉」；配置无灰度表现为「配置正确但一次全量命中」。它们都落在「假活 / 语义漂移」一类（→ comp/52），也都不会被「进程存活」告警抓到。
4. **每一处真正的防线都在客户端。** 客户端缓存（本地文件 / 内存快照）、客户端降级（拿不到就用旧的）、客户端退避（失败不立即重试）、客户端白名单（不接受的配置不生效）。**服务端能做的只有「别把放大器做进去」**——限速、合并、增量、保护阈值、灰度。

### 共同点与不同点（一张表读完两代基础件的分工）

| 维度 | 注册中心（Nacos naming / Consul catalog） | 配置中心（Nacos config / Apollo / Consul KV） |
| --- | --- | --- |
| **数据内容** | 服务名 → 实例列表（IP:Port、权重、元数据、健康状态） | 键值 / 文件（连接串、开关、阈值、限流额度） |
| **谁写** | 机器（每个实例启动时注册、退出时注销、周期性心跳） | 人（发布流程、审批、回滚）与自动化（发布系统） |
| **写频率** | **高**：心跳与状态翻转是常态流量（§38.9 账一） | **低**：一天几次到几百次 |
| **生命周期** | 秒级到分钟级（实例重启即变） | 天级到永久（版本要能回滚到三个月前） |
| **一致性选择** | **AP**：宁可短时间不一致，也必须能读（有客户端缓存兜底） | **CP 或「先持久化再广播」**：不允许丢一个版本，但允许迟到几秒（§38.6） |
| **推送语义** | 「**状态变了**」，晚到一条会被下一条覆盖 | 「**有新版了**」，每一条都必须被某个实例最终看到（否则版本永久滞后） |
| **丢了会怎样** | 短暂路由到已下线实例（客户端缓存 + 重试兜底） | 某批实例永远跑旧配置（**没有兜底，只能靠版本差监控**） |
| **典型的打垮方式** | 推送风暴把 CPU 打满 / 健康检查误判摘除有效实例 | 一次全量发布让所有实例同时做同一件事 |
| **第一道防线** | 客户端本地缓存 + 保护阈值 | 灰度 + 版本可回滚 + 客户端「坏配置不生效」 |
| **绝对不能拿来做什么** | 存业务数据（§38.10） | 当服务发现用（没有健康语义，§38.10） |

**这张表的用法**：任何一次「注册中心/配置中心要挂」的争论，先问「你说的是哪一类数据」。**把它们合并在同一个产品里（Nacos）不会让它们的语义合并**——Nacos 的 naming 走 Distro（AP）、config 走「持久化 + 通知」（§38.6），两条路径的失败形态完全不同，运维面板上却只写着一个「Nacos 集群」。

### 解剖卡八问落点（本篇答案）

| 问 | 落在哪节 | 一句话答案 |
| --- | --- | --- |
| ① 承诺什么 | §38.2、§38.10 | 注册中心承诺「**尽力**给你一份可用的实例列表」，配置中心承诺「**你发布的每个版本都能被找回**」；两者都不承诺「你拿到的一定是此刻的最新」 |
| ② 数据长什么样 | §38.3、§38.5 | 服务名 → 实例集合（内存 map + 可选持久化）；配置 = `dataId/group/namespace` → 版本化记录（DB 行 + 发布历史） |
| ③ 一次读写走哪条路 | §38.3、§38.4、§38.5 | 注册 = 客户端 → 任一节点 → Distro 异步复制（1 s 级）或 Raft 多数派；订阅推送 = 长连接/长轮询上的**一条通知**，正文由客户端回源拉（这是唯一能把放大做小的设计） |
| ④ 并发与一致 | §38.6 | 临时实例 Distro（AP，异步、可脑裂）、持久实例 JRaft（CP）；Consul catalog 全量 Raft（CP，代价是失去多数派就写不进注册）；配置 = 先落库再广播（顺序发布 + 版本号） |
| ⑤ 扩展维度 | §38.7、§38.9 | **只有一条：压小「每变更的订阅者数 × 回源次数」**。注册中心的节点数可以加，但推送量由订阅边决定，加节点不改变边的总数 |
| ⑥ 系统级失效 | §38.7、§38.8、§38.10 | 推送风暴（CPU/GC/网卡）、健康检查误判（假活与雪崩）、配置全量命中（同版本一次打死）、注册中心当数据库（写放大到爆炸） |
| ⑦ 看哪几个指标 | §38.12 | 注册实例数 vs 健康实例比例、推送延迟/推送条数、长轮询 hold 数与 304 比例、**配置版本差**（客户端 releaseKey 与服务端最新版的差） |
| ⑧ 换掉它的信号 | §38.10 | 需要跨机房强一致注册表 / 需要配置的审批与审计做到字段级 / 实例数进入 10 万级而推送模型不变 → 换形态而不是换参数 |

## 38.3 物理形态三家对照：Nacos 的双通道、Consul 的 agent+server、Apollo 的三段式

三家的差别不在 API，在**「变更从发生到被客户端看见，中间经过哪几个物理位置」**。下面这张图是全篇的地基，后面每一节都在拆它的一段。

```text
                     ┌──────────────── 订阅者（消费者侧）────────────────┐
                     │ 本地缓存: 内存快照 + (配置)磁盘文件                │
                     │ 兜底: 缓存过期也先用旧的；失败指数退避              │
                     └───────▲───────────────────────────▲──────────────┘
        ① 极小的「有变更」通知 │                           │ ② 回源拉正文（订阅者自己来取）
        （几十~几百字节）      │                           │   （注册表实例列表 / 配置全文）
                     ┌───────┴───────────────────────────┴──────────────┐
                     │            注册/配置中心服务端（集群）              │
                     │  Nacos: Distro(AP,临时实例) + JRaft(CP,持久实例)   │
                     │  Consul: 全量走 Raft 的 catalog + 本机 agent 缓存  │
                     │  Apollo: Config Service(读) ← DB ← Admin Service(写)│
                     └───────▲───────────────────────────────────────────┘
        ③ 注册/心跳/发布       │
   ┌─────────────────┬────────┴─────────┬──────────────────────────┐
   │ 提供者实例启动     │ 每 5 s 心跳(Nacos│ 人在 Portal 点「发布」     │
   │ register(ip,port)│ 1.x)/长连接保活   │ (Apollo: 写 Release 表)   │
   └─────────────────┴──────────────────┴──────────────────────────┘

关键分界线（记住这条）：
  ① 通知永远很小（不变量级），② 正文永远由客户端主动来拉。
  ⇒ 所以「推送风暴」的真实成本 = 通知数 × 客户端回源次数 × 回源体积，
     而不是「通知数 × 通知体积」。§38.9 账二、账三 全部建立在这条分界线上。
```

### Nacos：两套一致性协议并列在同一进程里

Nacos 的 naming 模块最反直觉的地方是：**同一个集群里同时跑着 AP 和 CP 两条路，选哪条由「实例是不是临时」决定，而不是由你配置决定**。

| 形态 | 触发条件 | 一致性路径 | 复制单位与延迟 | 失败时的表现 |
| --- | --- | --- | --- | --- |
| **临时实例**（`ephemeral=true`，业务微服务默认） | 客户端上报心跳保活（Nacos 1.x：默认 5 s 心跳 / 15 s 判不健康 / 30 s 摘除；Nacos 2.x 改为 gRPC 长连接保活，心跳语义由连接承载——**具体以目标版本文档为准**） | **Distro（AP）**：每个节点负责一部分服务的全量数据，变更后异步推给其他节点（延迟任务约 1 s 级，无多数派确认） | 按「服务」分片归属；复制是**最终一致**，可短时脑裂 | 节点间可短时不一致；客户端本地缓存兜底；节点挂掉后其负责的数据由其他节点接管 |
| **持久实例**（`ephemeral=false`，MySQL/Redis 这类） | 服务端主动探测（TCP/HTTP 探活，探测间隔与超时以目标版本为准），客户端不上报心跳 | **JRaft（CP）**：多数派写入 + 数据落库（生产用外置 MySQL） | 强一致，写代价 = 一次多数派提交 | 失去多数派 → **写不进去**；不健康只会被标 `healthy=false`，**不会自动摘除**（这是特性：给运维看见故障节点） |
| **元数据/服务注册表快照** | — | 2.x 用长连接与连接级订阅关系维护「谁关心谁」 | — | 连接重建成本 = 全量重订阅（事故一的放大器之一） |

两个必须记住的 Nacos 细节：

1. **「不健康」和「被摘除」是两种状态。** 临时实例走「15 s 判不健康 → 30 s 删除」，持久实例走「探针失败 → 永远只标不健康」。所以事故二里如果把 `order-api` 改成持久实例，**后果会反转**：实例不会被摘掉，但流量会持续打到坏节点上（这是另一类事故：健康状态没人消费）。
2. **保护阈值（`protectThreshold`，0~1）** 是 Nacos 唯一的内建「反雪崩」开关：当 `健康实例数 / 总实例数 < 阈值` 时，Nacos **返回全部实例（含不健康）**，把选择权交回客户端。默认是 0，等于关闭——事故二里如果提前设成 0.6，摘到 60% 就会停止「只返回健康实例」，雪崩链条在第 5 步就被切断。

### Consul：一切写入都过 Raft，读靠 agent 本地缓存

Consul 把「注册」和「健康」拆成两个物理位置，理解这一点就理解了它所有的优点与代价：

- **agent（每台机器/每个 Pod 一个）**：执行健康检查（script / HTTP / TCP / gRPC / TTL 等，默认超时 script 30 s、HTTP 与 TCP 10 s 量级，`interval` 必填）、提供 DNS 与 HTTP 接口、**在本地缓存 catalog**。DNS 查询基本由 agent 回答，不打到 server。
- **server（3 或 5 台，Raft 组）**：catalog 是**全量 Raft 复制的**——注册、注销、健康状态变更都是 Raft 日志条目。**写需要多数派。**
- **gossip（Serf）**：membership 与故障检测，走 UDP/TCP 的 LAN/WAN 两个池；它与 Raft 是两套机制，**member 被 gossip 标记失败 ≠ 其服务从 catalog 消失**（依赖 anti-entropy 与 `deregister_critical_service_after`）。
- **读路径**：客户端用 **blocking query**（`?index=X&wait=5m`）做长轮询，`wait` 默认 5 分钟、上限 10 分钟，服务端还会加 `wait/16` 量级的随机抖动来打散同时唤醒；没有变更就超时返回同 index。

代价很直白：**失去多数派的 Consul 集群会停止接受注册与健康更新**（catalog 写不进去），但已经缓存了实例列表的客户端**仍然能正常调用**——这是「CP 的注册中心」在故障时的标准形状：**控制面死了，数据面活着**。所以 Consul 事故里最常见的误判是「Consul 挂了所以要全站停服」，而正确的判断是「控制面停摆，数据面还能撑 N 分钟（直到有人重启实例需要注册）」。

### Apollo：三段式，写路径与读路径物理隔离

Apollo 的形态是「**写走一条路，读走另一条路，中间用数据库当消息队列**」：

| 组件 | 职责 | 物理事实 |
| --- | --- | --- |
| **Portal** | 人操作界面（发布、回滚、灰度、权限） | 只调 Admin Service，自己不碰配置内容 |
| **Admin Service** | 写：生成 Release、写 `Release` 与 `ReleaseHistory`、向 `ReleaseMessage` 表插一条消息 | **发布 = 一次 DB 事务**；`ReleaseMessage` 就是「变更事件总线」 |
| **Config Service** | 读：`/configs/{appId}/{cluster}/{namespace}` 返回配置全文；`/notifications/v2` 做长轮询 | 无状态，可水平扩；内存缓存 + 每秒扫 `ReleaseMessage`（批量约 500 条量级） |
| **Client** | 长轮询 + 内存 + 本地文件缓存；兜底定时全量拉取（默认 5 分钟量级，`apollo.refreshInterval` 可覆盖） | **断网也能启动**（读本地缓存文件），这是它最重要的运维属性 |

长轮询的形状（Apollo 的公开设计，版本间细节以目标版本文档为准）：客户端带着每个 namespace 的 `notificationId` 请求 `/notifications/v2`；服务端用 `DeferredResult` 把请求**挂起 60 秒**；60 秒内无变更 → 返回 `304`；有变更 → 立刻返回变化的 namespace 与新的 `notificationId`，客户端**再去拉配置正文**。

**这就是 §38.3 开头那条分界线的原型：通知只有几十字节，正文由客户端来取。** Apollo 的 60 s hold 直接决定 §38.9 账三的基线 QPS（客户端数 ÷ 60 s），也决定了一个常被忽略的容量事实：**Config Service 的并发瓶颈不是 QPS，而是「同时挂起的连接数」**（5,000 客户端 = 5,000 个挂起的 HTTP 请求，每个占一个 servlet 异步结果对象）。

### 决策表：什么场景选哪一家

| 你的处境 | 选择 | 为什么不选另外两家 | 必须自己补的那一层 |
| --- | --- | --- | --- |
| Spring Cloud / Dubbo 体系，注册 + 配置想用一套产品一套运维 | **Nacos**（临时实例 + config） | Consul 的 catalog 是 CP，注册侧在失去多数派时不可写；Apollo 只管配置不做注册 | 客户端缓存降级、保护阈值、配置灰度（Nacos 有 beta/标签灰度，但**默认流程是全量**，要显式用） |
| 已有多语言栈（Go/Java/Node 混跑）、要 DNS 接口、要服务网格底座 | **Consul** | Nacos 的多语言客户端成熟度与 DNS 语义弱于 Consul | 「catalog 是 CP」带来的容量与故障预案；健康检查的 `deregister_critical_service_after` 要显式配 |
| 配置要审批、要审计到人、要按环境/集群分层、要灰度到 IP | **Apollo** | Nacos config 的权限与审计粒度较粗；Consul KV 没有发布与回滚语义 | 灰度必须配（`GrayReleaseRule` 按 IP 列表），否则就是事故三 |
| 只是想存「动态开关」，量很小 | **不用配置中心**：进程内开关 + 一个低频拉取的 KV | 引入一整套发布/推送/长轮询的运维面，换来一年几十次的变更 | 一个 `/flags` 接口 + 30 s 缓存即可（这也是 §38.10 的边界） |
| 需要 Kubernetes 原生服务发现 | **不用这三个**：Service/DNS + EndpointSlice | 三者都要多维护一层；kube-proxy/Ingress 已消费 Endpoint | 只在「跨集群/跨 VM 的注册」时才引入外部注册中心 |

> **一句话**：Nacos 卖「一套产品两种数据」，Consul 卖「CP 的 catalog + DNS 事实标准」，Apollo 卖「配置的发布流程与审计」。选错的代价不在功能，在**你被迫接受的那条一致性路径的失败形态**（§38.6）。

## 38.4 服务注册与发现：注册、心跳、检查、摘除、恢复

「服务能互相调通」需要五个动作**同时**正确，任何一个错都能让整条链路断掉：注册（实例进来）、保活（证明还活着）、检查（判断健康）、摘除（把坏的移出）、推送（让调用方知道）。三家产品的差异全部落在这五个动作的**执行者是谁**上。

### 实例的一生：一个被摘掉的实例会经过哪些状态

```text
                     ┌──────────────┐
   进程启动 ────────►│  STARTING    │  本地缓存(空) → 拉全量注册表
                     └──────┬───────┘
                            │ register(ip, port, metadata, ephemeral?)
                     ┌──────▼───────┐        心跳/连接正常
                     │ REGISTERED   │◄──────────────────────┐
                     │ healthy=true │                       │
                     └──────┬───────┘                       │
        15 s 无心跳(Nacos 1.x)│ 或连续 3 次探测失败(见 §38.8)   │
                     ┌──────▼───────┐      心跳恢复/探测通过   │
                     │  UNHEALTHY   │───────────────────────┘
                     │ healthy=false│   ← 调用方已经拿不到它（除非触发保护阈值）
                     └──────┬───────┘
        再 15 s 无心跳(累计 30 s)│            ┌─────────────────────────┐
                     ┌──────▼───────┐        │ 持久实例(ephemeral=false)│
                     │  REMOVED     │        │ 永远停在 UNHEALTHY 不删除 │
                     │ 从注册表删除   │        └─────────────────────────┘
                     └──────┬───────┘
                            │ 进程真正退出前主动 deregister（优雅下线，§38.8 末）
                     ┌──────▼───────┐
                     │  GONE        │  调用方缓存里还残留 TTL（数十秒级）
                     └──────────────┘

读这张图的三个要点：
  ① UNHEALTHY 是「注册中心不再返回你」，不是「实例死了」——两者中间隔着一个判断阈值。
  ② 从 UNHEALTHY 到 REMOVED 的这段窗口，是「假活」与「已死」共存的区间，所有误判事故都在这里。
  ③ GONE 之后调用方还有一段本地缓存（Nacos 客户端订阅缓存 / Apollo 本地文件），
     所以「摘除」的实际生效时间 = 服务端摘除 + 客户端缓存刷新，两段相加才是事故时长。
```

### 三种健康判断：执行者不同，误判根因就不同

| 判断方式 | 谁执行 | 判断依据（物理事实） | 时间尺度 | 典型误判根因 |
| --- | --- | --- | --- | --- |
| **客户端上报心跳 / TTL** | 被检查的实例自己 | 「我还能连上注册中心，并且我愿意说话」 | Nacos 1.x：5 s 心跳 / 15 s 不健康 / 30 s 摘除；Consul TTL check：`ttl` 内没等到 `pass` 即 critical | **本机线程/GC/CPU 被业务占满** → 心跳线程没被调度（实例完全健康但被判死）；容器 CPU throttling 是最大来源 |
| **服务端主动探测** | 注册中心或本机 agent | 「从探测点能建 TCP / 拿到 HTTP 200 / gRPC 健康协议通过」 | 探测间隔（Nacos 持久实例与 Consul check 的 `interval`，常见 5–20 s）+ 超时（Consul 默认 HTTP/TCP 10 s、script 30 s 量级） | **探测点自身资源不足**、网络中间设备（NAT 表满 / LB 抖动）、**检查端点内部查了下游**（事故二：把下游慢翻译成实例死） |
| **调用方统计（熔断/剔除）** | 调用者进程 | 「我最近调它的失败率/超时率」 | 滑动窗口（秒级到十秒级）+ 本地剔除（如客户端侧的 outlier detection） | 最贴近真相但**最慢**，且每个调用方各有一份判断，容量与一致性代价高 |

> **为什么这三种都不可省**：心跳最快（秒级），但会被业务压垮；探测最客观（不依赖被检查者配合），但会把依赖故障当成实例故障；调用方统计最准，但只在「已经打了流量」之后才有效。**生产上的正确组合是：心跳/连接做 `liveness`（进程在不在），端口探测做 `readiness` 的第一层（能不能接流量），真正的依赖健康交给熔断与降级，永不进注册中心的健康判定。** 这一条是事故二的全部教训。

### 推送 / 拉取 / 长轮询：hold 时间到底在调什么

| 机制 | 谁发起 | hold 时间（量级） | 变更加到生效的延迟 | 空转成本 | 失效后的表现 |
| --- | --- | --- | --- | --- | --- |
| **UDP 推送**（Nacos 1.x 临时实例） | 服务端 | 无（发完不管） | 毫秒–几十毫秒，但**不可靠** | 零 | 丢包 → 客户端只能等下一轮；因此必须配「定时全量拉取」兜底（Nacos 1.x 是 10 s 量级） |
| **长连接推送**（Nacos 2.x gRPC） | 服务端（连接由客户端建） | 连接级 keepalive | 毫秒级 | 连接数 = 客户端数（服务端要为每个连接维护订阅关系） | 连接重建 = 全量重订阅（事故一的放大器）；服务端内存与 fd 上限成为容量瓶颈 |
| **长轮询 / blocking query**（Consul、Apollo） | 客户端 | Consul：`wait` 默认 5 分钟、上限 10 分钟（服务端另加 `wait/16` 抖动）；Apollo `/notifications/v2`：**60 s** | 有变更时立即返回（毫秒级）；无变更则到 hold 结束返回「无变化」 | 每客户端一条挂起请求；QPS ≈ 客户端数 ÷ hold（§38.9 账三） | 服务端重启 → 所有挂起请求断开 → **同时重连**（惊群）；客户端 timeout 必须 > 服务端 hold，否则每次都超时重发 |
| **定时全量拉取**（兜底） | 客户端 | 周期：Apollo 默认 5 分钟量级（`apollo.refreshInterval`）、Nacos 1.x 10 s 量级 | 最坏 = 一个周期 | QPS ≈ 客户端数 ÷ 周期 | 这是唯一「一定有效」的路径，也是最后一道防线 |

**这张表最重要的一行是 hold 的语义**：hold 时间**不决定推送延迟**（有变更时请求立刻返回），它只决定两件事——**空转 QPS**（客户端数 ÷ hold）与**同时挂起的连接数**（≈ 客户端数）。把 hold 从 60 s 调到 5 s 不会让配置更快生效，只会把空转 QPS 抬 12 倍；反过来把 hold 调到 10 分钟，则客户端的上限吞吐（每秒能重连的客户端数）与「服务端重启后的惊群规模」同时变差。**所以 hold 是容量旋钮，不是延迟旋钮。**

### 订阅关系是 N×M 的边，不是一张列表

服务端真正维护的不是「一份注册表」，而是**订阅边**：`(订阅者实例) × (被订阅的服务)`。10,000 实例 × 平均 30 个服务 = 30 万条边；如果再加上 1,000 个「全量订阅」的网关 × 500 服务 = 50 万条边，**边数比实例数大 80 倍**——这就是 §38.7 的几何基础。

推送内容有三种档位，成本与正确性完全不同：

| 档位 | 推什么 | 每次推送字节 | 正确性风险 | 什么时候用 |
| --- | --- | --- | --- | --- |
| **全量推送** | 该服务的完整实例列表 | 实例数 × 250 B（300 实例 ≈ 75 KB） | 无（自带校准） | 服务很小、变更很稀疏 |
| **增量推送** | 只推变更的实例（新增/下线/权重/元数据） | 一条 diff 几十到几百字节 | **丢一条就永久不一致** | 大服务、高频变更；必须配周期全量校准 |
| **仅通知**（notify only） | 只推「这个服务变了」 | 几十字节 | 无（客户端自己拉） | 客户端能承受回源；**这是 Apollo 的做法，也是成本最低的一档** |

**「增量推送 + 周期全量校准」是标配，纯增量不存在。** 因为推送通道（UDP/长连接）与客户端进程都会丢事件：客户端 GC 停 2 秒、连接闪断、服务端限速丢弃，任何一种都会让客户端永久停在旧版本。这就是为什么 Nacos 1.x 有「10 s 定时全量拉取」、Consul 有 anti-entropy、Apollo 有「5 分钟兜底拉取」——**它们不是冗余，它们是增量的正确性前提**。

```java
// Nacos 客户端骨架：注册 + 订阅 + 本地缓存降级（Spring Cloud Alibaba 形态，方法名以目标版本为准）
public class DiscoverySkeleton {
    private final NamingService naming;          // 由 NacosFactory.createNamingService(props) 构造
    private volatile List<Instance> cached = Collections.emptyList();  // 唯一可信读源：先读它
    private volatile long cachedAt = 0L;

    public void start(String svc, String ip, int port) throws NacosException {
        Instance self = new Instance();
        self.setIp(ip); self.setPort(port);
        self.setWeight(1.0); self.setHealthy(true);
        self.setEphemeral(true);                 // 临时实例 → Distro(AP)；改 false 会走 JRaft(CP) 且不会被自动摘除
        naming.registerInstance(svc, "DEFAULT_GROUP", self);

        // 1) 订阅：回调里只做「取数 + 替换引用」，绝不做回源/重建连接池（事故一的根因）
        naming.subscribe(svc, "DEFAULT_GROUP", event -> {
            if (event instanceof InstancesChangeEvent) {
                List<Instance> fresh = ((InstancesChangeEvent) event).getHosts();
                if (fresh != null && !fresh.isEmpty()) { cached = fresh; cachedAt = System.currentTimeMillis(); }
            }
        });

        // 2) 冷启动兜底：订阅之前先全量拉一次，避免「订阅成功但从未收到推送」的窗口
        cached = naming.selectInstances(svc, "DEFAULT_GROUP", true);
    }

    // 3) 读路径永不阻塞在注册中心上：取最近的快照，过期也照用（注册中心是软依赖）
    public Instance pick() {
        List<Instance> snapshot = cached;
        if (snapshot.isEmpty() || System.currentTimeMillis() - cachedAt > 60_000L) {
            // 只在明显过期时才异步刷新，且加退避；不要在这里同步调用 selectInstances
            return snapshot.isEmpty() ? null : snapshot.get(ThreadLocalRandom.current().nextInt(snapshot.size()));
        }
        return snapshot.get(ThreadLocalRandom.current().nextInt(snapshot.size()));
    }
}
```

> 这段骨架的每一行都在防一个具体事故：`ephemeral=true` 防「改错成持久实例导致坏节点永不被摘」（真实事故形态）；回调只换引用防事故一；先全量再订阅防启动窗口；读路径不阻塞防「注册中心抖动 → 业务全线超时」。

## 38.5 配置中心：配置模型、版本、灰度、回滚、监听

配置中心与注册中心最大的差别是：**配置的每一次写入都是「一个人的意图」，因此它必须可追溯、可分档生效、可撤销**。这六个能力缺一个，它就只能算一个「带推送的 KV」。

### 三家配置模型对照

| 维度 | Nacos config | Apollo | Consul KV |
| --- | --- | --- | --- |
| **寻址四元组** | `namespace(tenant) + group + dataId`（还可带 `tag`） | `AppId + Env + Cluster + Namespace` | `(datacenter) + key path` |
| **内容形态** | 文本（properties/yaml/json…），服务端按 `md5` 比对 | properties / yaml / json / xml，按 namespace 存一条 `Release` | 任意字节（通常 JSON/YAML 整块） |
| **版本与历史** | 有历史表（`his_config_info`），可查可回滚 | **一等公民**：`Release` + `ReleaseHistory`，每次发布一个 `releaseKey` | **无内建版本**（要靠 `ModifyIndex` 与外部备份） |
| **灰度** | beta 发布（按 IP 列表）/ 标签灰度（按客户端标签） | `GrayReleaseRule`：按实例 IP 列表；支持「灰度规则 → 全量」的二次发布 | **无** |
| **审批与权限** | 命名空间级鉴权（较粗） | AppId/Namespace 级权限 + 发布审批 + 操作审计 | ACL policy/token（无审批流） |
| **推送机制** | 长轮询（1.x/2.x 均保留；2.x 另有连接通道，细节以目标版本文档为准） | HTTP 长轮询 60 s hold + 5 分钟兜底拉取 | blocking query（`?index=&wait=`） |
| **客户端离线** | 本地快照文件（`~/nacos/config` 一类路径） | 本地缓存文件（`apollo.cacheDir`），断网可启动 | 无内建离线缓存（要自己写） |

**这张表的结论**：如果你需要「谁在几点把 `db.pool.max` 从 20 改成 200，谁批的，什么时候能回滚」这套答案，**只有 Apollo 把它做进了模型**；Nacos 有历史表但没有一等公民的审批流；Consul KV 是「一个能长轮询的 KV」，把版本治理的责任全留给你。

### 六个能力：缺一个就只是「带推送的 KV」

| 能力 | 为什么必须有 | 没有它会怎样 |
| --- | --- | --- |
| **版本** | 回答「现在生效的是哪一版」，是排查的第一步 | 出事时无法确认「是不是这次发布」，只能猜 |
| **原子发布** | 一个 namespace 的多项改动必须一起生效 | 客户端看到「一半新一半旧」的中间态（连接串换了但池大小没换）→ 极难复现的故障 |
| **灰度** | 把「全站同时命中」变成「1% 命中」 | 事故三：5,000 实例同时重建连接池 |
| **回滚** | 一分钟内把一个错误的版本推回去 | **回滚也要能以灰度方式执行**，否则撤销本身是第二次全量变更 |
| **监听（变更通知）** | 让配置改动不用重启生效 | 只能重启发布，配置变更退化成「又一次应用发布」 |
| **加密 + 权限 + 审计** | 配置里必然有密码、token、内网地址 | 凭据泄露在配置中心里「明文 + 全员可见 + 无审计」（凭据治理的解法在 `→ comp/47`） |

### 「配置即代码」到底在说什么

「配置即代码」不是「配置存成 yaml」，而是**三件事同时成立**：

1. **配置有仓库**：生产配置的每一版都在版本控制里（或至少有 `ReleaseHistory` 可导出），可以 `diff`；
2. **发布有流水线**：配置变更与代码变更走同一条变更评审（变更分级、影响面、回滚预案，见 [architect/07 变更治理](../architect/07-change-governance.md)）；
3. **审计能定位到人**：`SELECT operator, release_time, old_value, new_value FROM release_history WHERE app_id=? AND namespace=?` —— **控制台的滚动日志不算审计**，它不保证留存、不能 join、不保证完整。

一个可用的审计查询长这样（Apollo 形态，字段名以目标版本表结构为准）：

```sql
-- 某 namespace 最近 30 天的发布：谁、何时、从哪版到哪版、是否灰度
SELECT r.Id            AS release_id,
       r.ReleaseKey,
       r.Operator,
       r.ReleaseTime,
       r.IsAbandoned,                      -- 是否被放弃（灰度态）
       r.PreviousReleaseId,                -- 上一版 → 回滚的目标
       COUNT(h.Id)     AS config_items     -- 本次涉及多少个 key
FROM   Release r
LEFT   JOIN ReleaseHistory h ON h.ReleaseId = r.Id
WHERE  r.AppId = 'order-svc' AND r.ClusterName = 'default' AND r.NamespaceName = 'application'
  AND  r.ReleaseTime > DATE_SUB(NOW(), INTERVAL 30 DAY)
GROUP  BY r.Id, r.ReleaseKey, r.Operator, r.ReleaseTime, r.IsAbandoned, r.PreviousReleaseId
ORDER  BY r.ReleaseTime DESC;
```

> 这条查询的价值不在于「查得到」，而在于它证明了一件事：**「回滚」必须有明确的落点（`PreviousReleaseId`），否则事故时的「回滚」只是又发布了一次**。

### 灰度必须回答的三个问题

灰度不是「分批推送」这个词，它是三个必须写清楚的决定：

| 问题 | 可选答案 | 代价 / 陷阱 |
| --- | --- | --- |
| **选谁先进** | ① 指定 IP 列表（Apollo `GrayReleaseRule`、Nacos beta `betaIps`）② 按客户端标签（Nacos tag / 金丝雀 Pod）③ 按比例（需要客户端支持「随机 1% 自我选择」） | IP 列表最精确但**会随实例漂移失效**（K8s 上 Pod IP 天天变）→ 灰度名单必须由发布系统动态生成；按比例需要客户端配合，否则永远命中同一批 |
| **观察多久** | 至少一个业务周期（下单类 ≥ 10 分钟；对账类 ≥ 1 天） | 观察窗口 = 0 的灰度等于没灰度；必须定「看哪 3 个指标」（错误率、P99、业务核心指标） |
| **怎么退** | 只回滚灰度组（保持灰度名单）/ 整体回到上一版 | 若只能整体回滚，则「灰度 + 回滚」= 两次全量变更（事故三的 21:32 行）；**灰度名单必须独立于配置版本存在** |

```yaml
# 一次「可分档生效」的配置变更：把灰度名单、版本、回滚点写进同一份变更记录（字段为示意，按你的平台落地）
change:
  id: CHG-20260721-014
  app: order-svc
  namespace: application          # 一个 namespace = 一个原子发布单元
  diff:
    - key: db.pool.max
      from: 20
      to: 200
      effect: restart-required    # 关键字段：需要重启 vs 热生效，必须分开 namespace（§38.10）
    - key: db.pool.minIdle
      from: 5
      to: 20
      effect: hot
  rollout:
    - step: 1
      targets: canary-pods       # 由发布系统注入当前 Pod IP 列表，不写死
      percent: 1
      watch: 600s
      abort_if: { error_rate: ">0.5%", p99_ms: ">300" }
    - step: 2
      percent: 10
      watch: 900s
    - step: 3
      percent: 100
      watch: 1800s
  rollback:
    target: previous-revision     # 明确落点，等价于 Release.PreviousReleaseId
    scope: gray-group-only        # 只退灰度组，避免「回滚 = 第二次全量」
```

> 这个文件的重点是 `effect: restart-required` 与 `scope: gray-group-only` 两行：**前者防止「热配置和需要重启的配置挤在同一个 namespace 里一起生效」，后者防止「回滚本身成为第二次全量变更」**。事故三的两个放大器就是这两处缺失。

## 38.6 一致性取舍：注册中心为什么通常选 AP，配置为什么必须有版本

### 注册中心选 AP 的三条硬理由

| 理由 | 物理事实 | 如果选 CP 会发生什么 |
| --- | --- | --- |
| **读方是「正在启动的实例」** | 实例启动第一件事是拿注册表；拿不到就无法提供服务（或无法选下游） | 失去多数派时，**扩容/滚动发布/重启全部失败**——控制面故障直接变成发布通道故障 |
| **写可以被心跳补偿** | 注册不是「一次性事实」，而是被心跳周期性重申的意图；丢一次注册，5 s 后心跳会把它补回来 | CP 的多数派提交是「每一次注册都要付出共识代价」，而这一条恰恰**不需要那么强**——这是 Nacos 官方论证 Distro 适合临时实例的核心一句 |
| **客户端有缓存，短时不一致不致命** | 消费者手里有一份实例列表快照，晚 1 s 更新等价于「多打了 1 s 的旧副本」 | AP 的反面不是「正确」，是「可能路由到已下线实例」；而这件事用重试 + 熔断就能兜住 |

**Distro 的形状**（Nacos 临时实例）：每个节点负责一部分服务的全量数据（按服务分片归属），写入先落本地内存并立即返回成功，然后由延迟任务（1 s 量级）异步复制到其他节点；节点挂掉后，其他节点通过健康检查机制接管它负责的那部分。**它的不一致窗口是「秒级 + 一个服务的范围」**，而不是「整个集群」——这是分片型 AP 协议比「全量 gossip」更好的地方（消息冗余小，见 §38.3）。

### 持久实例为什么走 CP：因为它无法被心跳补偿

`ephemeral=false` 的实例（MySQL、Redis、DNS 这类）**不会上报心跳**，所以「注册」是它存在的唯一证明——丢一次就是永久丢，没有补偿机制。这时 CP 的代价是必须付的：Nacos 用 JRaft 多数派写 + 落库，Consul 的整个 catalog 本来就是 Raft。

| 对比项 | 临时实例（Distro / AP） | 持久实例（JRaft / CP） | Consul catalog（Raft / CP） |
| --- | --- | --- | --- |
| **写延迟** | 本地内存写 + 异步复制 ⇒ 亚毫秒到毫秒 | 多数派提交 ⇒ 1 个 RTT + 落盘（毫秒级） | 多数派提交 ⇒ 毫秒级，随批次摊薄 |
| **写吞吐量级** | 万级/秒（分片归属，无共识） | 千级/秒（受 Raft apply 与 DB 写约束） | 千级/秒（受 Raft apply 约束；健康状态翻转也算写） |
| **节点重启后的数据** | **内存数据消失**，靠客户端重新注册/心跳补回 | 落库，重启不丢 | 落盘 + 快照，重启不丢 |
| **脑裂时** | 各节点都能写、短时不一致，恢复后靠校验收敛 | 少数派**拒绝写** | 少数派**拒绝写**（客户端仍可用旧缓存） |
| **适合谁** | 业务微服务（会心跳、会重启、要弹性扩容） | 中间件/数据库/DNS（不会心跳、要看得见故障） | 多语言栈、DNS 发现、网格底座 |

### 配置中心为什么需要「版本 + 原子发布」而不是「AP 或 CP」

配置的写入是低频的（一天几次到几百次），所以**它不需要用 AP 换吞吐**；但它有一个注册中心没有的要求：**必须能回答「此刻的意图是什么」**。于是它的正确形态是第三条路——**先持久化，再异步广播**：

```text
  发布：  Portal/Admin ──► DB 事务（写 Release + ReleaseHistory + ReleaseMessage）──► 返回成功
                              │
                              └─ 这是唯一的真相来源（single source of truth）
  广播：  Config Service 每秒扫 ReleaseMessage ──► 挂起的长轮询立刻返回 ──► 客户端回源拉正文
                              │
                              └─ 可丢、可重、可延迟：丢了还有 5 分钟兜底拉取
```

这条路把「一致性」拆成两半：**真相的一致性交给数据库（单点写、事务、版本号），可见性的一致性交给「通知 + 兜底拉取」**。它买的正是事故三最需要的东西：

1. **版本号（`releaseKey` / `md5` / `notificationId`）让「滞后」变成可观测的量**（§38.12 的「配置版本差」）；
2. **原子发布**让一个 namespace 内多项改动同时生效，不会出现「半新半旧」；
3. **回滚 = 回到某个已知的 `releaseKey`**，而不是「再发布一次我把值改回去」。

> 🩸 **一致性这一节的判决句**：**注册中心用「可用性 + 客户端缓存」换即时性，配置中心用「版本 + 原子发布 + 兜底拉取」换可追溯性。** 把两者搞反（用 CP 的注册中心 + 无版本的配置中心）就同时得到两个最坏的组合：注册中心一失去多数派就没人能上线，配置一出事就没人知道上一版是什么。

```go
// Consul blocking query 骨架：三个细节 ① 保留 index ② wait 超时不是错误 ③ 出错必须退避
type entry struct {
	Service struct{ Address string; Port int } `json:"Service"`
}

func WatchService(ctx context.Context, addr, name string, fn func([]string)) error {
	var index uint64
	backoff := 500 * time.Millisecond
	for ctx.Err() == nil {
		u := fmt.Sprintf("http://%s/v1/health/service/%s?passing=true&index=%d&wait=5m", addr, name, index)
		req, _ := http.NewRequestWithContext(ctx, http.MethodGet, u, nil)
		resp, err := http.DefaultClient.Do(req)
		if err != nil { // 绝不立即重试：服务端重启时全体客户端会同时回来（惊群）
			time.Sleep(backoff)
			if backoff < 30*time.Second {
				backoff *= 2
			}
			continue
		}
		if v, e := strconv.ParseUint(resp.Header.Get("X-Consul-Index"), 10, 64); e == nil && v > index {
			index = v // 只在拿到更大的 index 时前进，防止回退
		}
		var entries []entry
		err = json.NewDecoder(resp.Body).Decode(&entries)
		resp.Body.Close()
		if err != nil {
			time.Sleep(backoff)
			continue
		}
		backoff = 500 * time.Millisecond // 成功一次就把退避清回去
		addrs := make([]string, 0, len(entries))
		for _, e := range entries {
			addrs = append(addrs, net.JoinHostPort(e.Service.Address, strconv.Itoa(e.Service.Port)))
		}
		fn(addrs) // blocking query 返回 ≠ 有变更：可能只是 wait 超时
	}
	return ctx.Err()
}
```> 最后一行注释是新手最常踩的坑：**blocking query 的超时返回是正常路径，不是错误**。把「返回」当成「变更」会写出「每 5 分钟抖一次全量刷新」的客户端；把「超时」当成「错误」并立即重试，则会在服务端重启时制造惊群。

## 38.7 推送风暴与惊群：N×M 的订阅关系如何把一次发布放大成一次雪崩

推送风暴不是一个 bug，是一个**几何事实**：注册中心要维护的不变量是「订阅边」，而每一次变更都要沿着**所有相关边**发一条消息。边数是实例数与订阅数的乘积，所以「加实例」和「加服务」都会让推送量以乘积方式增长——而容量规划通常只按「实例数」做。

### 三个放大器，缺一个都成不了事故

```text
 ① 几何放大器：订阅边数 = 实例数 × 平均订阅服务数（+ 全量订阅者的服务数）
    10,000 × 30 = 30 万边   ＋   1,000 网关 × 500 服务 = 50 万边   ⇒  80 万边 / 1 万实例 = 80×

 ② 合并放大器：事件级推送 → 每条变更一条消息
    8,000 实例重启 = 16,000 事件；若摊在 30 分钟，合并窗口（百毫秒级）几乎合并不到东西
    ⇒ 推送条数 ≈ 事件数 × 订阅者数 = 16,000 × 600 = 9.6e6

 ③ 回源放大器：客户端把「收到通知」当成「缓存失效」，立刻回源
    9.6e6 × 30 次回源 = 2.9e8 次查询 ÷ 1,800 s = 16 万 QPS  ← 事故一真正打死服务端的那一项

 总放大倍数 = 80 × 16,000 × 30 ÷ (10,000) ≈ 3,840 倍（相对「一次纯本地缓存更新」）
```

**为什么「合并窗口」救不了事故一**：合并（coalescing）只在**同一个 key 在短窗口内被反复更新**时有效。事故一的 16,000 个事件摊在 30 分钟、跨 500 个服务，平均每个服务每 56 秒才变一次——**任何百毫秒级的窗口都合并不到东西**。这是推送风暴最反直觉的一点：

| 变更的时间形状 | 合并窗口是否有效 | 正确的闸门 |
| --- | --- | --- |
| **突发型**（一次滚动发布 200 实例 × 2 事件在 2 分钟内） | **有效**：窗口 500 ms 可把 80 条合并成 ~8 条（10 倍） | 合并窗口 + 每服务限速 |
| **分散型**（500 个服务各有零星变更，持续 30 分钟） | **几乎无效**（合并率 < 5%） | 增量推送 + 仅通知（notify-only）+ 客户端回源退避 |
| **全表抖动型**（网络抖动让 10% 实例心跳超时，随后又全部恢复） | 无效（抖动本身跨分钟级） | **抑制翻转**：健康状态变更加「滞回」（连续 N 次才翻转）+ 抖动期暂停推送 |
| **重连型**（服务端重启，全部客户端重连并重订阅） | 无效（一次性） | **重连退避 + 抖动**：客户端随机 0–30 s 错开；服务端限并发 |

### 「一次发布，5,000 实例同时拉全量」的乘法链

这是最常见的形态：**客户端把「订阅」实现成「每次启动拉全量注册表」**（因为历史原因，「全量可见」曾经是个需求）。

| 步 | 项 | 推导 | 结果 |
| --- | --- | --- | --- |
| 1 | 一次发布触达的实例数 | 5,000 个实例滚动重启 | 5,000 |
| 2 | 每个实例启动时的查询数 | 全量拉取 = 500 个服务各查一次 | 5,000 × 500 = **2.5e6 次查询** |
| 3 | 压缩到多长的窗口 | 若发布用「先停后起」且无批次间隔，集中在 60 s 内 | 2.5e6 ÷ 60 = **41,667 QPS** |
| 4 | 单次查询的 CPU | 遍历该服务实例集合 + 序列化 5 KB JSON + 校验 ≈ 0.3 ms | 41,667 × 0.3 ms = **12.5 core·s/s** |
| 5 | 再加推送本身 | 16,000 事件 × 600 订阅者 × 5 KB × 15 ns/B ≈ 0.4 core | 合计 ≈ **13 core** |
| 6 | 服务端可用核数 | 3 节点 × 16 vCPU（其中一半用于 GC 与网络） | **24 core 有效** |
| 7 | 结论 | 13 vs 24 —— 看着有余量，但**队列一旦积压，P99 从 5 ms 变 8 s**，客户端 3 s 超时 → 重试 ×3 | **有效 QPS 需求 ×3 = 39 core > 24 core ⇒ 打满** |

**第 7 步是整个算例的关键**：CPU 利用率 54% 的系统，在「同步请求 + 客户端重试」的组合下会自己把负载放大 3 倍。**任何按 CPU 余量做容量规划的人都会在这里翻车**——正确的口径是「P99 是否已经接近客户端 timeout 的 1/3」，而不是「CPU 是否到 80%」（同源纪律见 [eng/22 压测与容量](../eng/22-load-test-capacity.md)）。

> **量级结论（非承诺值）**。假设：① 500 服务、5,000 实例、平均 20 实例/服务、实例条目 250 B；② 客户端启动时全量拉取（不是按需订阅）；③ 单次 `selectInstances` 0.3 ms CPU（含序列化 5 KB JSON）；④ 事件数 16,000、平均订阅者 600；⑤ 每节点 16 vCPU、半数可用于业务线程；⑥ 客户端 timeout 3 s、失败重试 3 次。**换掉第 ② 项（改为按需订阅 30 个服务）需求直接降 16 倍（2.5e6 → 1.5e5 次查询），事故不会发生**——这就是为什么「订阅粒度」是推送风暴的第一道闸门，比任何服务端限流都便宜。

### 五道闸门：从便宜到贵

| 闸门 | 在哪一侧 | 典型收益 | 代价 | 什么时候必须上 |
| --- | --- | --- | --- | --- |
| **① 缩小订阅粒度**（按需订阅，不全量可见） | 客户端 | 10–16 倍 | 产品/架构要接受「看不到全量路由表」 | 实例数 > 1,000 或服务数 > 100 |
| **② 仅通知 + 客户端回源退避** | 协议 | 5–50 倍（推送体积从 KB 级降到几十字节） | 回源 QPS 上升，需退避与本地缓存 | 大服务（> 100 实例）或不规则变更多的场景 |
| **③ 增量推送 + 周期全量校准** | 服务端 | 5–20 倍（推送体积） | 丢一条就永久不一致 → 必须有校准周期 | 服务实例数大且变更频繁 |
| **④ 合并窗口 + 每服务/每连接限速** | 服务端 | 突发场景 5–10 倍 | 变更可见延迟 + 一个窗口（百毫秒级） | 存在批量发布/扩容 |
| **⑤ 健康状态滞回（连续 N 次才翻转）+ 抖动期抑制推送** | 服务端 | 把「全表抖动」这一类直接消掉 | 发现真故障慢 N 个周期 | 实例数 > 1 万（抖动是必然的） |

> **一句总结**：**推送风暴的解法不是「更快的注册中心」，而是「更少的推送」**。所有有效的闸门都在减少「每条变更要发多少条消息」，而所有无效的手段（加节点、调大堆、加带宽）都只是在为同一个几何事实多买一点时间。

## 38.8 健康检查误判：为什么「检查超时」不等于「实例死了」

事故二的技术核心可以压缩成一句话：**探针测的是「从探测点看，这个实例此刻能不能应答」，而摘除逻辑把它当成了「这个实例是否还活着」。** 两者之间隔着三层翻译：探针的实现方式、超时与阈值的语义、以及摘除后的流量再分配。

### 三种检查方式的量级与盲区

| 方式 | 粒度 | 单次成本 | 能发现 | 看不见 | 误判主因 |
| --- | --- | --- | --- | --- | --- |
| **TCP 端口探测** | 「端口在 listen」 | 一次握手（本地几十 μs，跨机 1 RTT） | 进程崩了、端口没起来 | 进程活着但死锁、线程池满、连上但不处理 | 几乎不会误判；但**也几乎发现不了「假活」**（最危险的一类） |
| **HTTP `/healthz`** | 「业务能返回 200」 | 一次 HTTP 往返 + 端点内的逻辑 | 大部分假活 | 端点没覆盖到的依赖 | **端点内部查下游** → 把下游抖动翻译成实例死亡（事故二）；端点本身慢 → 超时误判 |
| **gRPC health checking 协议** | 「`Check()` 返回 SERVING」 | 一次 RPC（长连接上很便宜） | 与 HTTP 类似，语义更标准 | 同 HTTP | 同 HTTP；另加「连接复用导致探针看不出新建连接受阻」 |
| **客户端上报 / TTL** | 「实例自愿说话」 | 一条心跳（§38.9 账一） | 进程死、网络断 | 进程活着但心跳线程被饿死 | **GC / CPU throttling / 线程池满** → 心跳没发出去 |

### 阈值法的失效条件：它假设了「失败互相独立」

「连续 3 次失败才摘」是所有人都在用的配置，它的数学前提是**每次检查的失败互相独立**：单次失败概率 `p`，连续 3 次失败概率 `p³`（p=10% 时是 0.1%）。但集群级故障有一个要命的性质：**失败是高度相关的**——所有实例的探针在同一时刻查同一个数据库、跑在同一批宿主机上、走同一条网络路径。于是：

| 情形 | 单次失败概率 p | 三次独立假设下的摘除比例 | 真实摘除比例（完全相关） |
| --- | --- | --- | --- |
| 单个实例 GC 卡顿 | 0.02 | 0.0008% | 该实例 100%，其余 0%（一致，无害） |
| **共享依赖变慢**（DB P99 2.6 s > timeout 2 s） | **0.84** | 59%（p³） | **84%（p，因为相关性 ≈ 1）** |
| 宿主机 CPU throttling（同宿主机 20 个 Pod） | 0.5 | 12.5% | 该宿主机上 100%，全局 20% |

**所以「把阈值从 3 调到 5」在集群级误判里几乎不改变结论**（0.84³=59% 与 0.84⁵=42% 都远高于「正常运行」），却会让真故障的发现时间从 9 s 变成 15 s。**阈值是给「独立随机失败」用的旋钮，不是给「相关性故障」用的**——这是事故二里最贵的一课。

### 正反馈环：摘除本身会制造更多失败

```text
   DB/依赖变慢（P99 8ms → 2.6s）
        │
        ▼
   探针 /healthz 内部查 DB → 400 实例 ÷ 3 s = 133 QPS 探针查询压上去（放大 133 QPS）
        │
        ▼
   连续 3 次超时 → 9 s 后摘除 84%
        │
        ▼
   剩余 64 实例承接 100% 流量（每实例 QPS ×6.25，连接池打满）
        │
        ├──► 这些实例的业务线程被占满 → 探针排队 → 也超时 → 第二波摘除
        │
        └──► 上游重试 + 熔断阈值未触发（因为「失败率」还没到）→ 流量继续压在 64 个实例上
        │
        ▼
   健康实例 3% → 事实上不可用（而原始故障 "DB 慢" 只是让 P99 从 8ms 到 2.6s，本可降级扛过）

四道可以切断这个环的闸门（任意一道生效，事故就停在这里）：
  ① 探针不查下游（liveness 只判进程/端口）——切在最上游，最便宜
  ② 保护阈值（Nacos protectThreshold）——摘到 60% 就停止「只返回健康实例」
  ③ 摘除比例上限（一次事件最多摘 10%，超出即告警并暂停摘除）——平台侧策略
  ④ 上游熔断/降级：失败率触发后进入降级返回，而不是继续把流量压给幸存者（→ eng/18、eng/17）
```

### 优雅下线：把「摘除」从被动变主动

被动摘除（心跳超时 / 探测失败）永远有误判风险；主动下线能把「误判窗口」换成「确定的排空窗口」。五个阶段，缺一段就掉请求：

| 阶段 | 动作 | 等待多久 | 掉请求的原因（若跳过） |
| --- | --- | --- | --- |
| ① 反注册 | 先 `deregister`（Nacos `registerInstance` 的反操作 / Consul `/agent/service/deregister`），**再**停进程 | 立即 | 不反注册 → 调用方要等心跳超时（15–30 s）才知道你不在了 |
| ② 等缓存过期 | 等调用方缓存/负载均衡刷新 | ≥ 一个「客户端缓存刷新周期」，Nacos 客户端约 10 s 量级、Consul blocking query 立即但网关侧可能另有 5–30 s 缓存 | 缓存没刷新就还在给你发流量 → 连接被 reset |
| ③ 停止接新请求 | 把 `readiness` 置 false（HTTP 503），但 `liveness` 保持 true | 立即 | 直接停进程 = 在途请求被砍（K8s 侧见 [go/52](../go/52-deployment-sre.md)） |
| ④ 排空在途 | 等待进行中的请求完成（`preStop` sleep 或连接排空） | ≥ P99 请求时长 × 2（长连接场景要看流式请求） | 排空不足 → 5xx 集中在发布期间 |
| ⑤ 关闭 | 关闭线程池/连接池，退出 | — | 先关连接池再排空 → 排空阶段全部失败 |

> **一条经验换算**：「优雅下线等 30 s」在 K8s 上是 `terminationGracePeriodSeconds` 与 `preStop` 的和；如果你的**客户端缓存刷新值是 10 s、网关侧缓存是 30 s**，那 30 s 的排空只够覆盖第一层，**网关那一层会把流量再发给你 0–30 s**。所以排空窗口 = max(各层缓存刷新周期) + P99 请求时长，而不是「一个凭感觉的 30 s」。

## 38.9 三本账：心跳账、推送账、拉取账

本节三个算例都按「乘法链 + 假设清单 + 量级结论」写，任何一条假设都能替换后重算（复算脚本在本节末）。

### 账一 · 心跳 QPS = 实例数 ÷ 心跳间隔（**这笔账通常是最小的一笔**）

| 步 | 项 | 推导 | N=2,000 | N=10,000 | N=50,000 |
| --- | --- | --- | --- | --- | --- |
| 1 | 心跳 QPS | `N ÷ 5 s`（Nacos 1.x 默认 5 s；2.x 由长连接保活替代，此账归零但连接数 = N） | 400 | 2,000 | 10,000 |
| 2 | 入向带宽 | `QPS × 300 B`（一条心跳请求含 header 的量级） | 120 KB/s | 600 KB/s | 3 MB/s |
| 3 | 服务端 CPU | `QPS × 60 μs`（解析 + map 更新 + TTL 刷新） | 0.024 core | 0.12 core | 0.6 core |
| 4 | **状态翻转的放大** | 抖动率 1% ⇒ 翻转 `N × 1% ÷ 5 s`，每次翻转 2 个事件 | 8 事件/s | 40 事件/s | 200 事件/s |
| 5 | 翻转引发的推送 | `事件/s × 订阅者 600 × 5 KB` | 24 MB/s | **120 MB/s** | **600 MB/s** |
| 6 | 结论 | 第 3 步 vs 第 5 步 | — | **推送是心跳的 1,000 倍量级** | 网卡先于 CPU 撞墙 |

**这张账的全部意义在于第 6 步**：**心跳 QPS 从来不是注册中心的瓶颈，心跳抖动引发的推送才是。** 所以「心跳间隔从 5 s 调到 10 s」能省的 CPU 是 0.06 core（可以忽略），但把「1% 抖动」的概率降低一半的收益是 60 MB/s 的推送量。**调参的方向永远应该是「减少状态翻转」，不是「减少心跳」。**

> **量级结论（非承诺值）**。假设：① 心跳 300 B、服务端 60 μs/条；② Nacos 1.x 的 5 s 心跳（2.x 长连接下本账第 1–3 步不再适用，但连接数与 fd 成为新约束）；③ 抖动率 1%（网络/GC/宿主机噪声导致心跳延迟跨过 15 s 阈值的比例，需要实测，1% 在中大型集群是常见量级）；④ 订阅者 600、列表 5 KB。**Consul 形态下本账的归属不同**：健康检查由**本机 agent 执行**（`interval` 常见 5–20 s），因此服务端只收到「状态变化」而不是每次检查——**Consul 把心跳账摊到了每个 agent 的 CPU 上，代价是 agent 与 server 之间要同步 catalog**。

### 账二 · 推送字节 = 订阅者数 × 变更次数 × 配置大小

| 步 | 项 | 推导 | 结果 |
| --- | --- | --- | --- |
| 1 | 一次发布的「通知」字节 | `客户端数 × 200 B`（Apollo 的 `notificationId` / Nacos 的 md5 通知，不含正文） | 5,000 × 200 B = **1 MB** |
| 2 | 一次发布的「正文」字节 | `客户端数 × 配置大小`（40 KB 的 `application` namespace） | 5,000 × 40 KB = **200 MB** |
| 3 | 通知 : 正文 | 第 1 步 vs 第 2 步 | **1 : 200**（这就是「仅通知」设计的全部价值） |
| 4 | 客户端拉错范围的放大 | 客户端把 8 个 namespace 全拉（而不是只拉变更的 1 个） | 200 MB × 8 = **1.6 GB / 次发布** |
| 5 | 一天的出方向 | 每天 200 次发布（含误操作重发与回滚） | 40 GB/天 → 拉错范围则 **320 GB/天** |
| 6 | 三家的量级差异 | 注册表推送（账一第 5 步）与配置推送是同一本账的两个投影 | 注册表变更频率是配置的 **100–1,000 倍** |
| 7 | 灰度能省多少 | 分批不改变总字节（5,000 客户端最终都要收到），但把**峰值命中**从 `200 MB / 3 s` 变成 `2 MB / 3 s` | 峰值降 **100 倍**，总量不变 |

> **量级结论（非承诺值）**。假设：① 5,000 客户端、每次发布 1 个 namespace、正文 40 KB；② 每天 200 次发布；③ 客户端只用长轮询（不含 fallback 全量拉取）；④ 不计 TLS 与压缩（gzip 对 yaml 通常 3–5 倍，会显著改善第 2 步）。**关键推论**：**灰度不省带宽，灰度省「同时命中」**——所以能用灰度解决的事，不要指望用带宽或限流解决；反过来，带宽账要按「全量最终送达」算，不能按「灰度第一批」算。

### 账三 · 配置拉取 QPS = 客户端数 ÷ 长轮询周期

| 步 | 项 | 推导 | 结果 |
| --- | --- | --- | --- |
| 1 | 基线空转 QPS | `客户端数 ÷ hold`（Apollo hold 60 s；Consul `wait` 默认 5 分钟） | 5,000 ÷ 60 = **83 QPS**（Consul：≈ 17 QPS @ wait=5m） |
| 2 | 同时挂起的连接数 | ≈ 客户端数（每个客户端一条挂起请求；Apollo 一个实例一条长轮询连接） | **5,000 条**（这才是真瓶颈） |
| 3 | hold 配错的代价 | hold 改 5 s | 83 → **1,000 QPS**（延迟并没有变快，只是空转多了 12 倍） |
| 4 | fallback 全量拉取的背景流量 | `5,000 ÷ 300 s`（Apollo 默认 5 分钟量级） | 17 QPS × 40 KB = **680 KB/s 常态** |
| 5 | 服务端重启的惊群 | 全部客户端同时重连，若客户端无退避 | **5,000 QPS 瞬时** × 平均 40 KB = **200 MB/s**，3 秒内打满（事故一的同类机制） |
| 6 | 单台 Config Service 的容量口径 | 按「挂起连接数」而不是 QPS 定：4C8G 量级实测万级连接（Apollo 公开数据，**以目标版本与你自己的压测为准**） | 5,000 客户端 → 建议 **3 台 × ≤ 2,500**，留一台冗余 |

> **量级结论（非承诺值）**。假设：① 5,000 客户端各一条长轮询连接；② Apollo 服务端 hold 60 s、客户端 timeout 90 s（必须 > 服务端 hold，否则每次都超时）；③ fallback 全量拉取 300 s 一次；④ 正文 40 KB。**第 2 步是全篇最重要的容量口径**：配置中心的扩容依据是**并发挂起连接数**，不是 QPS。用 QPS 做容量规划的人会在「QPS 只有 83、CPU 5%」的时候突然遇到连接耗尽（fd / 内存 / 异步结果对象），而这类故障的症状是客户端集体超时重连——**看起来像网络问题，实际是连接数天花板**。

```python
# 三本账复算脚本：改任一假设直接重跑（Python 3.9+）
def heartbeat(n, interval_s=5, req_bytes=300, cpu_us=60):          # 账一
    qps = n / interval_s
    return qps, qps * req_bytes * 8 / 1e6, qps * cpu_us / 1e6

def flap_push(n, flap_rate=0.01, interval_s=5, subscribers=600,     # 账一第 4–5 步
              list_bytes=5120, ns_per_b=15):
    events = n * flap_rate / interval_s * 2                          # 翻转 = 不健康 + 恢复
    pushes = events * subscribers
    return events, pushes, pushes * list_bytes / 1e6, pushes * list_bytes * ns_per_b / 1e9

def config_push(clients, config_bytes=40 * 1024, notify_bytes=200):  # 账二
    notify, body = clients * notify_bytes, clients * config_bytes
    return notify / 1e6, body / 1e6, body / notify

def long_poll(clients, hold_s=60, fallback_s=300, config_kb=40):     # 账三
    return clients / hold_s, clients, clients / fallback_s * config_kb / 1000

def burst(instances, services=500, cpu_ms=0.3, window_s=60, cores=24):  # §38.7
    qps = instances * services / window_s
    return qps, qps * cpu_ms / 1000, qps * cpu_ms / 1000 / cores

hq, mb, cores = heartbeat(10_000)
ev, pu, mbps, gj = flap_push(10_000)
nm, bm, ratio = config_push(5_000)
idle, conns, fb = long_poll(5_000)
bq, bcore, bratio = burst(5_000)
print(f"心跳 {hq:.0f} QPS / {mb:.1f} Mbps / {cores:.2f} core")
print(f"抖动 {ev:.0f} 事件/s → {pu:.0f} 推送/s = {mbps:.0f} MB/s ≈ {gj:.1f} core")
print(f"配置：通知 {nm:.1f} MB vs 正文 {bm:.0f} MB（1:{ratio:.0f}）")
print(f"长轮询：空转 {idle:.0f} QPS / 挂起 {conns} 连接 / 兜底 {fb:.2f} MB/s")
print(f"惊群 {bq:,.0f} QPS 需 {bcore:.1f} core（容量 24），{bratio:.2f}x")
```

> 脚本输出的量级与本节三张表一致：**心跳 2,000 QPS 只值 0.12 core；抖动推送 120 MB/s 才是墙；配置正文是通知的 200 倍；长轮询的真瓶颈是 5,000 条挂起连接；全量惊群的需求是容量的 1.6 倍。** 五个数字解释了本篇三起事故里的两起。

## 38.10 架构边界：注册中心不能当配置中心，配置中心不能当服务发现

| 它能做什么（且只有它能做） | 它做不到（物理原因） | 常见的错误替代 | 靠什么绕过 |
| --- | --- | --- | --- |
| 把「活着的实例」聚合成一份可读列表，并用推送/长轮询让调用方尽快知道 | **存业务数据**：Distro 是内存分片 + 异步复制，重启即丢；Consul catalog 每次写都要过 Raft（千级写/s 量级），业务写入会直接撞穿共识层 | 用注册中心做「服务 → 配置」字典、做「路由规则库」、做「限流额度下发」 | 配置走配置中心；额度走专门的配额服务或网关（→ comp/50）；路由走控制面（`→ comp/41`） |
| 提供「尽力而为」的可用实例列表 + 客户端缓存兜底 | **强一致的成员视图**：AP 下必然存在「A 认为 B 活着、C 认为 B 死了」的窗口 | 拿注册表当真值做「实例数统计/计费/容量报表」 | 真值走 CMDB / 指标系统（→ comp/48 文本锚点）；注册表只用于路由 |
| 用版本 + 发布历史回答「现在生效的是哪一版」 | **发现与健康语义**：KV 没有健康检查，`index` 变化不代表实例可用 | 用配置中心的 KV 存「服务地址列表」做服务发现（Consul KV 上极常见） | 用 catalog / naming 模块；KV 只存配置 |
| 灰度、回滚、审批、审计 | **配置的原子性之外的东西**：一次配置发布不能保证「业务语义正确」，只有灰度和观察能 | 用配置中心的审批流代替发布评审 | 配置变更纳入变更治理（[architect/07](../architect/07-change-governance.md)），灰度只是其中一道闸门 |
| 跨机房/多活的**单机房内**注册与配置 | **跨机房强一致注册表**：跨地域 RTT 使多数派写延迟进入 10 ms 量级，等于把注册变成慢操作 | 两个机房共用一个注册中心集群（跨城 Raft） | 每机房独立注册中心 + 客户端本地优先 + 异步同步元数据（[architect/10 多活与单元化](../architect/10-multi-active-and-cell.md)） |

**多活的一条纪律**：注册中心的多活是「**每单元各自注册、各自发现**」，不是「一份注册表跨城复制」。因为它的数据是**会自己过期的**：跨城复制的实例列表在分区时无法判断对端实例死活，只能靠本地心跳与本地健康检查。同理配置中心的多活是「**每单元一份可写的配置库 + 单向同步单向发布**」，不是「多地同时可写」（同时可写就没有「版本」了）。

## 38.11 踩坑清单（现象 → 根因 → 定位 → 修复 → 防复发）

| 现象 | 根因（指到物理形态） | 怎么定位 | 怎么修 | 怎么防复发 |
| --- | --- | --- | --- | --- |
| 发布窗口注册中心 CPU 打满、查询 P99 从 5 ms 到秒级 | 推送 → 客户端回源 → 超时重试，三层连乘（§38.7 账） | 同时看「推送条数/秒」「`selectInstances` QPS」「客户端 timeout 率」；QPS 涨幅 ≈ 事件数 × 订阅者 × 回源次数 | 客户端改为「用推送体更新缓存」；把全量订阅改为按需订阅；服务端加合并与限速 | 客户端订阅回调里禁止任何回源/RPC；发布批次间隔 ≥ 合并窗口 |
| 注册中心重启后全体客户端同时重连，起来就再挂 | 长连接/长轮询的**惊群**：无退避的立即重连 | 看连接建立速率曲线是否是一个垂直的墙，而不是指数上升 | 客户端加「随机 0–30 s 抖动 + 指数退避」；服务端限并发接入 | 客户端 SDK 的退避策略纳入基线检查 |
| 实例数正常但「健康实例比例」突然塌到 5% | 探针查下游 → 把依赖慢翻译成实例死（事故二） | 对比「注册实例数」「健康实例数」「上游 5xx 率」三条曲线：若前两条塌而进程数不变 → 误判 | 立刻关掉「只返回健康实例」（保护阈值调到 0.3–0.6）或临时把探针改回只判端口 | `liveness` 只判进程/端口；下游健康交给熔断 |
| 心跳正常但实例被摘 | 实例 GC/CPU throttling 让心跳线程没被调度（进程活着，心跳发不出） | 看实例侧 GC 日志与 CPU throttling 指标；看摘除时间点是否与该实例 GC 峰值重合 | 提高实例 CPU limit、缩小堆、把心跳线程与业务池隔离 | 容器 CPU limit 与 JVM 堆的匹配纳入容量评审 |
| 持久实例改错成临时实例（或反之），故障形态反转 | `ephemeral` 决定「会不会被自动摘除」，不是「重不重启」 | 看注册类型与「实例下线后是否留在列表里」 | 业务服务一律 `ephemeral=true`；只有不会心跳的中间件用 `false` | 注册类型写进服务模板，禁止手工改 |
| 配置改完只有一部分实例生效，且长期不收敛 | 增量推送丢事件 / 客户端长轮询断开后没重连 | 统计客户端上报的 `releaseKey`/md5 与服务端最新版的差（§38.12） | 让客户端重启或强制刷新；检查长轮询连接数与 304 比例 | 必须有兜底定时拉取；必须有「配置版本差」告警 |
| 配置回滚后故障继续，甚至扩大 | **回滚也是一次全量推送**，且 `previousRelease` 可能已经过期/被覆盖 | 对比回滚前后的 releaseKey 与客户端分布 | 回滚只针对灰度组；回滚前确认目标版本的完整内容 | 灰度名单独立于版本；回滚演练纳入季度演练 |
| 一次配置发布导致所有实例同时重建连接池/重启 | 没有灰度 + 「需要重启的配置」和「热生效的配置」挤在同一 namespace | 看出问题时间点与发布时间的差（秒级即全量 → 无灰度） | 拆 namespace（`hot` / `restart-required`）；按 IP 或标签灰度 | 发布流程强制第一步灰度为 1%，观察窗口不可填 0 |
| 注册中心变成「服务间调用的必经同步依赖」，注册中心抖 → 全站抖 | 客户端把「取实例」写成同步强依赖，丢了本地缓存的兜底 | 看注册中心故障时的业务成功率：若归零 → 客户端没兜底 | 客户端加本地快照 + 过期也先用 + 异步刷新 | 架构评审表里加一项「基础件不可用时业务是否降级」 |
| Consul 集群失去多数派后所有发布失败 | catalog 是 CP：注册/健康更新都要 Raft 多数派 | 看 `consul_raft_leader` 与 apply 延迟 | 恢复 server 数量（重启失败的 server 或补节点）；期间禁止发布 | server 数 3/5，跨 AZ 部署，避免同批重启 |
| 服务摘除后流量仍打到已下线实例，报连接拒绝 | 客户端缓存 + 上游负载均衡缓存没刷新（多层缓存） | 看错误类型：`connection refused` 集中在少数 IP | 优雅下线：反注册 → 等 max(各层刷新周期) → 停进程 | 排空窗口按「最慢一层缓存」定，不按经验值 |
| 配置中心连接数耗尽（QPS 很低却挂了） | 瓶颈是**并发挂起连接数**而非 QPS（§38.9 账三） | 看 fd 数、挂起请求对象数、GC 与线程栈 | 扩 Config Service 实例；检查客户端 timeout 是否 < 服务端 hold（会放大重连） | 容量按客户端数（连接数）而不是 QPS 规划 |
| 注册表里出现大量「幽灵实例」（早已下线） | 持久实例不会被自动摘除；或客户端进程被杀没反注册 | 按实例的 `lastBeat`/`ModifyIndex` 时间排序，看尾部 | 手工注销 + 让健康检查生效 | 业务服务禁用持久实例；部署模板强制优雅下线 |
| 配置里的密码/密钥长期明文可读 | 配置中心不是密钥管理系统；权限粒度到 namespace 不等于「按字段加密」 | 审计配置内容里的敏感字段与访问记录 | 敏感项改成「引用 + 客户端取密钥」（`→ comp/47`） | 配置模板禁止出现明文凭据，CI 里加扫描 |
| 大促前扩容，扩容的实例起不来 | 启动时全量拉注册表 → 把正在承受大促流量的注册中心压垮 | 看扩容时段注册中心 QPS 与启动耗时 | 扩容前预热注册表缓存；分批扩容 | 「扩容本身是一次注册中心流量事件」写进大促预案 |

## 38.12 观测：五个能提前十分钟报警的数字

**每条指标都带版本与开关前提**；名称以「官方端点/常见 exporter 输出」的形态给出，**具体名称以目标版本的输出为准**（Nacos 用 `/nacos/metrics` 的 `nacos_monitor{name="..."}` 一类；Consul 用 `consul_*` telemetry；Apollo 的自带指标随版本差异较大，往往需要自建探针）。

| 指标（形态） | 版本 / 开关前提 | 拐点（越线就动手） | 它度量的是哪件物理事实 |
| --- | --- | --- | --- |
| **注册实例数 / 健康实例数 / 健康比例** | Nacos `nacos_monitor{name="serviceCount"/"instanceCount"}` 一类；健康比例需自建（按订阅接口统计） | 健康比例 < 90% 告警，< 60% 立即怀疑「探针/依赖」而不是「实例」 | 摘除是否在发生；事故二的唯一直接信号 |
| **变更事件速率与推送条数/秒** | 服务端需开指标或自建（2.x 的连接推送计数） | 推送条数 > 基线 5 倍，或事件速率 > 基线 10 倍 | 推送风暴的起因量（§38.7 的几何放大入口） |
| **查询 QPS + P99（`selectInstances` / 配置读取）** | 客户端侧 + 服务端侧都要 | P99 > 客户端 timeout 的 1/3 即危险（不是等超时） | 「答得慢」比「挂了」更早出现，且会引发重试放大 |
| **长轮询挂起连接数 + 304 比例** | Apollo 需自建（`DeferredResult` 计数）；Consul 看 blocking query 的连接 | 挂起连接接近单机上限；304 比例骤降 = 变更在暴涨 | 配置中心的真容量口径（§38.9 账三第 2 步） |
| **配置版本差（客户端 releaseKey/md5 vs 服务端最新）** | 客户端上报 + 服务端比对，自建 | 滞后客户端比例 > 1% 持续 10 分钟 | 配置是否真的「全量生效」；回滚是否真的落地 |

**三条判读纪律**：① **先看比例，不看绝对值**——「注册实例数 8,000」本身无害，「健康比例从 99% 到 41%」是事故；② **先看「谁在变」再看「变了多少」**——推送风暴的曲线特征是「推送条数涨、但注册实例数没涨」（只是重启），而真实容量增长的曲线是两者同步涨；③ **配置中心的告警必须包含「版本差」**，否则你永远只能从业务报错里发现「有一批实例跑的是旧配置」。

## 38.13 一页速记

| 记什么 | 具体结论 |
| --- | --- |
| **唯一真问题** | 被所有服务依赖却只能尽力而为；三件事各自能打垮集群：推送风暴（N×M 放大）、健康检查误判（假活）、配置无灰度（全量命中） |
| **两种数据的区别** | 注册中心存「谁活着」（高频写、AP、可丢一点）；配置中心存「应该是什么」（低频写、要版本、不能丢） |
| **Nacos 双通道** | 临时实例 → Distro（AP，分片归属 + 1 s 级异步复制）；持久实例 → JRaft（CP，多数派 + 落库）；保护阈值是唯一内建反雪崩开关（默认 0 = 关） |
| **Consul 的形状** | agent 本机执行检查 + 本地 catalog 缓存；server 走 Raft（catalog 是 CP）；blocking query `wait` 默认 5 分钟/上限 10 分钟 + `wait/16` 抖动 |
| **Apollo 的三段** | Admin 写 DB + `ReleaseMessage`；Config Service 每秒扫表 + 60 s 长轮询 hold；客户端本地文件可离线启动 + 5 分钟兜底拉取 |
| **推送的分界线** | 通知永远很小，正文永远客户端自己拉；所以成本 = 通知数 × 回源次数 × 回源体积 |
| **三个放大器** | 订阅边数（实例 × 订阅数，常被低估 80 倍）、无合并（分散型变更合并率 < 5%）、回源（事故一真凶） |
| **阈值法的前提** | 「连续 N 次失败才摘」假设失败独立；集群级故障下失败完全相关 → 调大阈值几乎无效，只让真故障发现变慢 |
| **三本账** | 心跳 ≈ `N ÷ 5 s`（不是瓶颈）；推送字节 = 订阅者 × 变更 × 大小（通知:正文 ≈ 1:200）；配置拉取 QPS = 客户端数 ÷ hold（真瓶颈是挂起连接数） |
| **灰度不省带宽** | 灰度把「同时命中」从 200 MB/3 s 变成 2 MB/3 s（峰值 100 倍），但总字节不变；回滚也必须有灰度落点 |

**如果只记五句：**

1. **推送风暴的成本不是「推送条数」，是「推送条数 × 客户端回源次数」。** 减少订阅粒度与去掉回源，比加节点有效 10 倍。
2. **「连续 N 次失败」挡不住集群级误判**，因为失败是相关的。探针只判进程与端口，下游健康交给熔断。
3. **摘除会重新分配流量**，所以误判不是「少几个实例」，是「把幸存者压死」——保护阈值与摘除比例上限必须开。
4. **配置中心的核心不是推送，是版本 + 灰度 + 可回滚**；没有这三样，回滚就是第二次全量变更。
5. **注册中心只承诺给一份「尽力而为」的列表**，所以每一处防线都在客户端：本地缓存、过期也用、失败退避、坏配置不生效。

## 38.14 自检题（5 题）

**Q1.** 一个注册中心集群 3 节点 × 16 vCPU，10,000 实例、500 服务，客户端平均订阅 30 个服务。某次发布 8,000 实例重启，注册中心 CPU 打满、查询 P99 到 8 s。运维的两个动作是「加 2 个节点」和「把堆从 16 GB 调到 32 GB」。分别判断是否有效，并给出正确的三处修改。

<details><summary>答案</summary>

**两个动作都基本无效：**

- **加节点**：代价在「查询与推送条数」，而推送条数 = 事件数 × 订阅者数，与节点数无关；加节点只摊薄 CPU，但**客户端连接与订阅关系还要重新分配**（2.x 长连接下加节点会触发一批连接重连与重订阅，短期内更糟）。若瓶颈在「单节点 CPU 全在线程池」则加节点能线性改善——但事故一的 QPS 是「回源放大」造出来的，加节点只是把 16 万 QPS 摊到 5 台，客户端 timeout 依旧。
- **调大堆**：事故一的 GC 压力来自「每次推送 5 KB 序列化 + gzip 的短命对象」，调大堆会让 young GC 频率下降但**单次停顿变长**，P99 更差；老年代如果被客户端订阅关系与缓存吃掉，反而更快触发 full GC。

**正确的三处修改（按收益排序）：**

1. **客户端去掉回源**：订阅回调里只用推送体更新缓存引用（事故一里回调做了 `selectInstances`）→ 16 万 QPS 直接回到数千。
2. **缩小订阅粒度**：1,000 个网关从「订阅全部 500 个服务」改为按需订阅（它们占了 50 万条边里的 96%）。
3. **服务端加合并 + 限速**：对同一服务在同一窗口内的多次变更合并为一条，并对每连接限速；同时在发布侧加批次间隔（避免 8,000 实例在同一分钟里全重启）。

**为什么不是「换更强的注册中心」**：几何事实（边数 × 回源次数）不随产品改变，换产品只会把同一个倍数搬到另一台机器上。

量级结论，非承诺值；假设同 §38.7 乘法链。
</details>

**Q2.** `/healthz` 里做了 `SELECT 1` 和一次下游 HTTP 探测，`interval=3s / timeout=2s / 连续 3 次失败摘除`。DB 慢 38 秒导致 80% 实例被摘。问：① 为什么「把阈值改成 5 次」几乎没用？② 列出四道能切断正反馈的闸门；③ 哪些证据能证明「实例没死只是慢」？

<details><summary>答案</summary>

**① 阈值无效的原因**：阈值法的数学前提是「每次检查的失败互相独立」（p³）。但 400 个实例的探针在同一时刻查**同一个变慢的 DB**，失败概率高度相关（相关性 → 1），此时摘除比例 ≈ 单次失败概率 p = 84%，而不是 p³。改成 5 次，p⁵ = 42% —— 依然是「半站被摘」，只是真故障的发现时间从 9 s 变成 15 s。

**② 四道闸门**：① 探针不查下游（`liveness` 只判进程/端口，`readiness` 只看本机能接流量）；② Nacos 保护阈值（健康比例 < 阈值即返回全部实例）；③ 平台侧「单次事件摘除比例上限」（超 10% 即告警并暂停摘除）；④ 上游熔断/降级（失败率触发降级，而不是把流量继续压给幸存实例）。

**③ 证据链**：进程存活（`ps`/容器状态 running）+ 端口可连（`nc -z` 成功）+ 线程栈里是「等 DB 连接」而不是死锁 + 日志仍在按速率输出 + 该实例的 CPU 不低（在干活）—— 四条同时成立即可判定「慢」而不是「死」。反过来，若端口不通、线程栈空转、日志停止，才是真死。

量级结论，非承诺值；假设单次失败概率 0.84 由「DB P99 2.6 s > 探针 timeout 2 s」推出。
</details>

**Q3.** 5,000 个客户端、Apollo 服务端 hold 60 s。运维发现 Config Service 的 QPS 只有 83、CPU 5%，但每天有几次「客户端集体超时重连」。给出三个可能原因，并说明为什么「扩容 QPS 容量」解决不了。

<details><summary>答案</summary>

**容量口径错了**：配置中心的瓶颈是**并发挂起的连接数**（≈ 客户端数 5,000），不是 QPS（83）。所以三个原因都指向连接层：

1. **fd / 内存 / 异步结果对象上限**：每客户端一条挂起请求 = 一个 `DeferredResult` + 连接占用；单机容器 fd 上限（常见 65,535 但被线程与文件分摊）或堆里挂起对象过多 → 新连接被拒。
2. **客户端 timeout ≤ 服务端 hold**：若客户端 timeout 设成 30 s < 服务端 60 s，则每次都在服务端返回前超时 → 客户端重发 → 挂起连接翻倍堆积（假象是「QPS 83」但连接 10,000）。
3. **服务端重启/GC 停顿导致整批断开**：所有客户端同时重连，无抖动退避 → 瞬时 5,000 QPS 打上来 → 又是「QPS 很低但连接数爆」。

**为什么扩容 QPS 容量没用**：QPS 不是约束项，5% CPU 说明算力富余；需要的是「更多实例来分摊 5,000 条挂起连接」+「客户端 timeout > 服务端 hold」+「重连抖动退避」。扩容实例数有效（因为连接被分摊），扩容单机算力无效。

量级结论，非承诺值；假设 5,000 客户端各一条长轮询连接。
</details>

**Q4.** 一个配置发布把 `db.pool.max` 从 20 改成 200（库端 2,000 连接上限），3 秒内 5,000 实例全部生效，全站写失败 22 分钟。请给出：① 用像素级的乘法链说明为什么必炸；② 一个「即使值错了也不炸」的灰度设计（含观察指标与回滚落点）；③ 为什么「回滚」本身也可能是第二次事故。

<details><summary>答案</summary>

**① 乘法链**：`5,000 实例 × 200 连接 = 100 万期望连接` vs 库端 `2,000` → **超配 500 倍**。前 2,000 个连接建立成功后，第 2,001 个开始报 `Too many connections`；而连接池的失败重试（每 30 s 一次尝试 × 5,000 实例）持续压库，使「已有连接被挤掉」→ 重连 → 更挤。22 分钟里写入失败 116 万笔。

**② 灰度设计**：第 1 步只对 1%（50 个 Pod，由发布系统动态注入 IP，不写死）→ 观察 10 分钟看三个指标：**DB 侧 `Threads_connected`/`Max_used_connections` 水位**、应用侧连接获取等待 P99、写接口错误率；水位 < 库上限 40% 才进入 10% → 50% → 100%，每步都带 `abort_if`。回滚落点必须是 `previousReleaseId`（明确的版本），且 `scope: gray-group-only`。

**③ 为什么回滚是第二次事故**：因为回滚与发布**形状相同**——都是一次全量推送。事故三里 21:32 的回滚把 5,000 实例又整体重置了一次连接池，等于在崩塌中再压一次。只有「回滚只作用于灰度组」+「灰度名单独立于版本存在」时，回滚才是真正的止损动作。

量级结论，非承诺值；假设每实例一个连接池、连接按需创建、库端 `max_connections=2000`。
</details>

**Q5.** 有人主张「我们直接把 Nacos 的持久实例用在所有业务服务上，这样实例挂了还能在控制台看到故障节点，运维体验更好」。用本篇的三个机制说明这句话错在哪，并给出正确的做法。

<details><summary>答案</summary>

**错在三处：**

1. **持久实例走 CP（JRaft）：写要多数派 + 落库。** 把 10,000 个会随发布重启的业务实例变成 CP 写，注册吞吐从「万级/秒」掉到「千级/秒」，且**失去心跳补偿**——一次写失败就是永久缺失，只能靠人补。
2. **持久实例不会被自动摘除（只会标不健康）。** 这意味着默认的实例列表里**包含已死的节点**，调用方会持续打到坏节点上（事故二的反面形态），比「被摘除」更危险；Nacos 之所以这么设计，是因为持久实例（MySQL/Redis）通常没有客户端心跳、且需要运维看见故障。
3. **健康检查语义变了**：持久实例由服务端主动探活，探活周期比心跳长得多（秒级到十秒级），**故障发现更慢**；而业务服务本身有完整的心跳能力，用探活是浪费并放大误判面（§38.8 的服务端探测盲区）。

**正确做法**：业务服务一律 `ephemeral=true`（临时实例 + Distro），把「运维要看到故障节点」的需求交给指标与日志（→ comp/48 文本锚点 / [eng/20 指标体系](../eng/20-metrics-system.md)），把「不要打到坏节点」交给保护阈值 + 优雅下线；只有不会心跳的中间件（MySQL/Redis/DNS）才用持久实例。

量级结论，非承诺值。
</details>
