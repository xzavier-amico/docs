## 45.1 引子：三起「ID 重复 / 乱序 / 跳号」的事故

这一节的三起事故有一个共同形状：**业务代码里没有一行写错，发号器也在正常返回一个 64 位整数**。出事的是三件从未被当作「容量与语义」对待的东西——**这台机器的时钟刚才往回跳了多少、这个 worker 号是不是还有别人在用、这一次预取走了多少个还没有发出去的号**。它们都不是业务逻辑，所以从来没人给它们做过设计评审；而它们的共同后果是同一个：**ID 不再唯一，或者不再有序**——一个所有下游表、所有幂等键、所有对账任务都默认成立的前提，悄悄失效了。

### 事故一：NTP 步进回拨 2.4 秒，序列回绕吐出 801 个重复 ID

某出行平台 2026-03-02 02:10。发号器是标准的 41/10/12 位 Snowflake，跑在容器里，**容器共享宿主机时钟**。凌晨运维切换 NTP 源，新源比旧源快 2.4 秒，chrony 判定偏移超过阈值后直接**步进（step）**而不是渐进（slew）——时钟瞬间往回跳了 2,400 ms。

发号器里那段回拨处理是几年前抄来的经典写法：

```java
if (now < lastTs) { now = lastTs; }   // 时钟回拨？那就继续用上一个毫秒
```

| 时刻 | 事件 | 后果 |
| --- | --- | --- |
| 02:10:07.000 | 该毫秒内已发出 801 个号（`seq` 走到 800） | `lastTs` = 02:10:07.000 |
| 02:10:07.005 | NTP 步进落地，系统时钟回到 02:10:04.605 | 发号器**察觉不到**，只有下一次 `now < lastTs` 时才发现 |
| 02:10:07.006 | 第一次检测到回拨，走「继续用上一个毫秒」分支 | `now` 被钉在 02:10:07.000，**2.4 秒内所有号都长在这个毫秒里** |
| 02:10:07.006 起 | 200 个 pod 各按 2,000 ID/s 继续发号，共 4,800 个号挤进同一毫秒 | 单毫秒序列只有 4,096 个槽位 → **`seq` 回绕一次** |
| 02:10:09.4 | 时钟追上 `lastTs`，发号恢复"正常" | 回绕后重发的 `seq` 0~1,503 与回拨前已用的 0~800 撞车 → **801 个 ID 重复** |
| 02:11 | 订单表主键冲突开始报 `Duplicate entry` | 801 笔下单直接失败，业务侧重试后拿到新号 |
| 02:14 | 埋点表（无唯一索引）静默写入 801 对同 ID 记录 | 按 ID 聚合的转化率报表当天全错 |
| 02:53 | 定位完成（先怀疑分库分表中间件，最后才想到时钟） | 43 分钟，2 名值班，801 条订单 + 1 张报表返工 |

这一起的教训不是「NTP 有毒」，而是：**把时间戳放进 ID，等于把一个可以被外部系统任意调整的变量，变成了唯一性的一个因子。** 而那个「继续用上一个毫秒」的分支，看起来是"优雅降级"，实际上是把「回拨窗口时长」直接乘进了「同一毫秒的序列消耗速率」——4,800 个号挤进 4,096 个槽位，回绕是必然的算术，不是运气。**回拨本身不可怕，可怕的是回拨期间发号器仍然以每秒数千的速度在同一个毫秒里盖章。**

### 事故二：副本从 60 扩到 300，`序号 % 256` 的 workerID 撞了 36,000 次

某零售中台 2026-06-18 00:20，大促前扩容。发号器的 `workerId` 取法写死在启动脚本里：`workerId = $POD_ORDINAL % 256`。平时 60 个副本，撞不上；这次为了扛峰值把 StatefulSet 扩到 300 个副本，滚动发布又开着 `maxSurge = 25%`，于是**新旧两代 pod 并存了 15 分钟**。

| 环节 | 算术 | 结果 |
| --- | --- | --- |
| 槽位冲突 | 300 个序号塞进 256 个槽位 | **44 个 pod 与已存在的 pod 同号**，且新旧代并存期同号双方都在发号 |
| 单 worker 发号速率 | 200 ID/s = 0.2 个/ms | 每个毫秒有 20% 概率发出 1 个号 |
| 两个同号 worker 在同一毫秒都发号 | `0.2 × 0.2` = 4% | 900,000 个毫秒 × 4% = **36,000 次撞车** |
| 撞车的后果 | 同 worker 位 + 同毫秒 + 同 `seq`（每毫秒都从 0 起） | **36,000 个完全相同的 ID** |
| 落地 | 订单主键有唯一索引 → 12,400 条冲突被挡；消息表与埋点表没有 | 12,400 条订单事件被下游"按 ID 去重"当成重复消息**丢弃** |
| 06:40 | 库存服务与订单服务对账不平 | 对账 3 天，人工补 12,400 条，2 个 SKU 超卖 |

这里的机制值得单独说：**Snowflake 的唯一性 = 「worker 位互不相同」∧「同一 worker 的 (ms, seq) 单调」**。前一个条件是有前提的，而"序号取模"这个前提在**副本数超过模数**、**新旧代并存**、**pod 重建复用序号**三种情况下同时失效。更阴的一点是：撞车产生的是**完全相同的 ID**，它们在主键表上会被挡住（看起来像"偶发重复键"），在没唯一索引的地方则变成静默的"两条记录一个身份"——后者才是真正要赔钱的那种。

### 事故三：为了抗抖动把步长调到 50 万，重启一天跳掉 21.9 亿个号

某本地生活平台 2026-11-09 大促当天的复盘数据。号段模式（DB 双 buffer），原本 `step = 5,000`。双 11 前有人算了一笔"DB 抖一下怎么办"的账，结论是把步长放大 100 倍到 `500,000`——"这样每次取号能扛 100 倍的 DB 抖动"。

| 项 | 算式 | 结果 |
| --- | --- | --- |
| 每次进程重启丢弃的号 | 当前段剩余（≈0.9 step）+ 已预取的下一段（1 step） | **≈ 1.9 × 500,000 ≈ 950,000 个** |
| 当天重启次数 | HPA 扩缩容 1,400 次 + 崩溃/发布 900 次 | **2,300 次** |
| 当天跳号空洞 | `2,300 × 950,000` | **≈ 2.19 × 10⁹（21.9 亿）** |
| 当天真实发出的 ID | 订单量 | **4,200 万** |
| 有效利用率 | `4.2 × 10⁷ ÷ (2.185 × 10⁹ + 4.2 × 10⁷)` | **≈ 1.9%**：每发出 1 个号，水位往前走 ≈ 53 个 |
| 连带炸点一 | 按「每 1,000 万一个分片」做的路由 | 一天开出 **218 个分片**，路由表与 DDL 失控 |
| 连带炸点二 | 对账任务用「ID 连续」判断漏单 | 误报 **2.1 亿条**缺失，把值班按在地上摩擦 |
| 连带炸点三 | 前端展示「订单号：8 位起」 | 水位数在 3 小时内从 8 位跳到 10 位，两个老客户端字段截断 |

06:00 报警，13:40 把步长降回 5,000 并把水位手工拉回真实值附近，8 名值班 + 3 名 DBA 工时 6 小时。**这起事故的本质是「步长」被当成了一个纯性能参数，而它其实同时是「抗故障窗口」和「重启丢号量」的同一个旋钮**——把旋钮往一个方向拧，另一头立刻要你付钱（45.5 会把这条拧成一个不等式）。

> 🩸 三起事故的共同点：**没有一处业务逻辑写错**。① 是时钟被外部调了；② 是身份号被复用；③ 是预取了没发完的号。它们都发生在「发号器把唯一性编码进一个整数」这个抽象漏出来的地方：它编进去的是**时间**、**身份**、**一段预留的号空间**——三样东西都需要持续的、有人维护的外部前提，而**唯一性本身不产生任何报错**，直到下游开始按 ID 对齐。

## 45.2 一句话定位与唯一真问题

**定位**：分布式 ID 生成器（Snowflake 类、号段类、UUID 类、Redis/DB 序列类）不是「发号器」，它是一个**把「时间」和「身份」编码进固定位宽的编码器**。它承诺两件事：**ID 全局唯一**、**ID 大致按时间递增**；它不承诺：**连续**、**无空洞**、**能反推真实生成时刻**、**换号不变**。

| 它承诺什么 | 它明确不承诺什么 | 反例（什么不叫"有序"） |
| --- | --- | --- |
| 同一命名空间内 ID 不重复（前提：worker 位隔离 + 时钟不回退 + 序列不溢出） | 不承诺连续：号段、重启、回滚都会挖洞 | 「ID 递增」≠「第 N 号和第 N+1 号属于同一秒」 |
| 趋势递增：后发的号一般更大，按 ID 排序≈按时间排序 | 不承诺**严格**全局有序：同毫秒内跨 worker 会乱序 | 两个 worker 在同 1 ms 内发的号，大小顺序与真实先后无关 |
| 单发号者内单调（后发的一定更大） | 不承诺跨发号者单调，也不承诺跨机房单调 | 换 worker / 回拨后借号，新号可能小于旧号 |
| 位宽固定、可解析（时间/机器位可拆出来） | 不承诺不可解析：它的可解析性就是泄露风险（45.8） | 「ID 看不出业务量」这句话对 Snowflake 不成立 |

### 唯一真问题

> **唯一真正的敌人是时钟与重启；「有序、单调、可用」这个三角只能挑两个半。**

这句话可以拆成四条可验证的推论，全篇都在给它们找证据：

1. **唯一性不是免费的，它的两个因子都被外部托管。** 「不重复」= `worker 位不撞` ∧ `(毫秒, 序列) 不回头`。worker 位来自你的部署系统（K8s 序号、配置、注册中心），时钟来自你的时间同步（NTP/chrony/宿主）。**这两个都是别人的系统在正常运行**——所以唯一性事故永远发生在"别人的系统刚好动了一下"的那个窗口（事故一、事故二）。
2. **「重启」是分布式 ID 的第二个敌人，因为它会同时清掉两样东西**：内存里"已经用过哪一段号"的知识，以及"我这个 worker 号是不是还在租期内"。号段模式丢的是**未发完的号**（事故三），Snowflake 丢的是**上一次的时间戳**（重启后 `lastTs` 归零，回拨检测失效）。
3. **三角里能拿满的只有两个，第三个只能拿半个。** 想要「单调 + 有序」就必须**等时钟追上**，付可用性；想要「单调 + 可用」就必须**换身份或借未来时间**，ID 不再反映真实时间，付有序性；想要「有序 + 可用」就必须允许**跨发号者乱序**，付严格单调。所谓"半个"，是指第三个属性**降级为"趋势/局部/单机"**，而不是完全没有。
4. **下游把 ID 当什么用，决定了你能放弃哪个半。** 当主键/分片键 → 只需要"趋势递增"（B+ 树就吃这一口，45.6）；当幂等键/事件排序键 → 需要"单机单调"；当对账序号/发票号 → 需要"连续"，而连续恰恰是三者都换不来的东西（45.6 末段）。

### ID 的四个属性（先定义，再谈取舍）

| 属性 | 精确定义 | 谁来保证 | 做不到的现场后果 |
| --- | --- | --- | --- |
| **唯一** | 一个 ID 永不指向两个实体 | worker 位隔离 + 序列不溢出 + 时钟不回退 | 幂等键串味、错发货、对账永远不平（事故一、二） |
| **有序** | 按 ID 排序 ≈ 按**真实时间**排序 | 高位时间戳 + 时钟同步（跨机偏差 100 μs~10 ms 量级） | 增量同步、按 ID 分页、按 ID 扫表会漏/重 |
| **单调** | 同一发号者后发的 ID 一定更大 | 本地 `lastTs` + 序列 + 拒绝对外回退 | 游标回退、fencing token 失效（→ comp/46） |
| **可用** | 任何时刻都能发出号，不退让、不等外部 | 无同步外部依赖（或本地缓存够长） | 发号中心抖一下 → 全站写入失败 |

### 不可能三角：为什么是「两个半」

```text
                    唯 一（入场券，不可交易）
                            ▲
                            │
              全局有序 ◄────┼────► 严格单调
                  │         │         │
                  │   ┌─────┴─────┐   │
                  └───┤ 只能同时  ├───┘
                      │ 拿满两个  │
                      │ 第三个降级 │
                      └─────┬─────┘
                            │
                          可 用

  A 单调 + 有序 : 回拨时「等」        → 牺牲可用（窗口内排队/超时）
  B 单调 + 可用 : 回拨时「换 worker」  → 牺牲有序（新号可小于旧号，不反映真实时间）
  C 有序 + 可用 : 各发号者独立、允许乱序 → 牺牲严格单调（只剩"趋势递增"）
  第三个属性永远只能拿「半个」：降级为趋势 / 单机 / 局部有效
```

| 想要拿满的两个 | 必须放掉的那半个 | 实现机制 | 账记在谁头上 |
| --- | --- | --- | --- |
| 唯一 + 单调 + 有序 | **可用**（回拨就阻塞） | 自旋/睡眠等时钟追上；超阈值直接拒服 | 回拨窗口内到达的请求：延迟 = 回拨量（45.7 账三） |
| 唯一 + 单调 + 可用 | **有序**（ID 不再等于真实时间） | 换 workerID 租约 / 借未来时间 / 逻辑时钟扩位 | 可观测性与排序语义 + 一份外部租约依赖 |
| 唯一 + 有序 + 可用 | **严格单调**（跨发号者） | 每个发号者各自单调，全局只保证趋势 | 同毫秒乱序、游标必须去重、跨机房不可比 |
| 唯一 全部 | 别的都要谈 | 纯 UUIDv4 | B+ 树随机插：分裂 128 万次、写放大 3.7×（→ comp/05 §05.5） |

### 解剖卡八问（分布式 ID 版）

| # | 问题 | 本篇的回答（一句话） |
| --- | --- | --- |
| ① | 承诺什么 | 全局唯一 + 趋势递增；**不承诺**连续、无洞、跨机严格有序、不可解析 |
| ② | 数据长什么样 | 一个 64 位整数，内部是「时间位 ⌄ 机器位 ⌄ 序列位」；号段模式的"数据"是 DB 里一行水位 + 进程内两段缓冲 |
| ③ | 一次发号走哪条路 | Snowflake：纯内存 ~100 ns；号段：绝大多数请求命中内存段（~100 ns），1/step 概率走一次 DB 往返（0.5~3 ms） |
| ④ | 并发与一致 | 进程内一把锁/原子变量（单机单调）；跨机一致性靠 **worker 位不撞** + **时钟不倒退**；号段的跨机一致性靠**DB 行锁** |
| ⑤ | 扩展维度 | 只有一条：**扩 worker 位宽的「不重叠分区」**。发号器本身不可"加副本"，因为副本之间不共享状态——加副本等于加 workerId，必须外部划分 |
| ⑥ | 系统级失效 | 假活（发号正常但时钟已错）、脑裂（同 workerId 双活）、满（`seq` 用尽/号段枯竭）、语义漂移（ID 被当业务键用） |
| ⑦ | 看哪几个指标 | 时钟回拨次数、号段剩余、worker 租约冲突、序列耗尽次数、重复 ID 检出（45.11） |
| ⑧ | 换掉它的信号 | 发号 QPS 逼近 4,096/ms/节点、回拨频率 > 次/周、跳号率进业务可见范围、需要"连续号"（45.6） |

## 45.3 物理形态：64 位里塞了什么，一行水里藏了什么

### Snowflake：41 / 10 / 12 的来历

```text
Snowflake 64 bit（Twitter 2010 版；Java long = 有符号 64 位）

  63    62                                22 21            12 11              0
 ┌────┬────────────────────────────────────┬────────────────┬──────────────────┐
 │ 0  │        41 bit 毫秒时间戳            │  10 bit 机器位  │  12 bit 序列      │
 └────┴────────────────────────────────────┴────────────────┴──────────────────┘
   │                  │                            │                  │
   │                  │                            │                  └─ 同毫秒内第 N 个：0~4095
   │                  │                            │                     即 4,096 个/ms/发号者 = 4.096M/s
   │                  │                            └─ Twitter 拆成 5 bit 数据中心 + 5 bit 机器
   │                  │                               = 1,024 个互不重叠的发号者
   │                  └─ 从自定义 epoch 起算的毫秒数 → 2^41 ms ≈ 69.7 年
   └─ 恒 0：保证 ID 落到正数区间（有符号 long），顺手吃掉 1 bit 容量

 拼装： ((now - epoch) << 22) | (workerId << 12) | seq
 解码： ts = (id >> 22) + epoch ；worker = (id >> 12) & 0x3FF ；seq = id & 0xFFF
```

三个位宽不是随便切的，每一个都对应一个**必须在评审里写明的容量假设**：

| 位段 | 宽度 | 容量 | 什么时候会用尽 | 用尽时怎么办 |
| --- | --- | --- | --- | --- |
| 时间 | 41 bit（ms） | 2,199,023,255,552 ms ≈ **69.7 年** | epoch 起点决定：Twitter 原版 epoch ≈ 2010-11-04，到 2080 年左右 | 换 epoch（会与旧 ID 冲突）或加宽位段（换格式） |
| 机器 | 10 bit | **1,024** 个互不重叠的发号者 | 副本数/单元数/机房数乘积超 1,024（事故二） | 用租约分配、按机房切段、或牺牲序列位换机器位 |
| 序列 | 12 bit | **4,096 个/毫秒/发号者** = 4.096M ID/s/发号者 | 单进程发号速率超 4,096/ms（单机 400 万 QPS） | 自旋等到下一毫秒（吞吐天花板）或换 13/14 位变体 |

**一个必须纠正的常见误解**：Snowflake 的吞吐上限 4.096M/s 是**单发号者**的上限，不是系统上限；系统上限是 `1,024 × 4.096M`。真实系统打不到那个数，因为**先到上限的永远不是位宽，而是时钟精度与锁**（45.7 账三）。

### 五个形态的物理对照

| 形态 | 唯一性来源 | 有序性档位 | 单号延迟（含摊销） | 单发号者吞吐 | 外部依赖 |
| --- | --- | --- | --- | --- | --- |
| **Snowflake**（41/10/12） | 位切分 + 单调时钟 | 全局趋势递增 | ~50–200 ns（纯 CPU） | 4,096/ms = 4.096M/s | 无（但依赖时钟质量与 workerID 分配） |
| **号段**（DB 双 buffer） | DB 行锁 + 步长互斥 | 段内严格递增，跨段趋势递增 | ~100 ns（内存）；每 step 个号摊一次 0.5–3 ms | 受 DB 行锁：**数百–2,000 次取号/s** | 关系库（一行） |
| **UUIDv7 / ULID** | 62 / 80 bit 随机 + 时间前缀 | 时间前缀可排序，同毫秒可乱序 | 0.5–2 μs（随机数 + 格式化） | 百万级/s（本地） | 无 |
| **Redis `INCR`** | 单线程原子自增 | 全局严格递增（单 key） | 1 次 RTT：0.2–1 ms | 单实例 10 万+/s（pipeline 摊薄） | Redis（持久化与主从切换是坑） |
| **DB `AUTO_INCREMENT`** | 单库单表 | 单表严格递增 | 1 次提交：1–5 ms（含 fsync） | 数百–数千/s（组提交可再高） | 单个主库（写不进去就发不出号） |

### 号段的物理形态：一行水位 + 两段内存

```text
号段模式的内存与 DB 关系（双 buffer）

  DB：id_segment（一行一个业务）                    进程内存（每个实例各自持有）
  ┌────────────────────────────┐                  ┌───────────────────────────────┐
  │ biz_tag  │ max_id          │                  │ cur: [1001 .. 2000]           │◄─ 正在发
  │ order    │ 3000  ◄─────────┼─── UPDATE +step ─┤      next_ptr 已发到 1,830     │
  │ step     │ 2000           │      （行锁）      ├───────────────────────────────┤
  └────────────────────────────┘                  │ nxt: [2001 .. 3000]           │◄─ 已预取待启用
                                                   └───────────────────────────────┘

  预取触发点：cur 消耗到 90%（Leaf-segment 的默认行为；阈值随实现/版本，以目标文档为准）
  段耗尽的坏路径：nxt 尚未到位 → 这一次发号同步等 DB（P99 就死在这里）
  重启的代价：cur 剩余 + nxt 整段一起丢 → 空洞上界 ≈ 1.9 × step（事故三）
```

号段模式的"数据"有两份，这是理解它全部行为的关键：**DB 里那份（`max_id`）是"这个故事讲到哪儿了"的公开水位，进程内存里那份是"我手上有哪些号"的私货**。两份之间必然有缝隙——缝隙就是跳号空间的来源，也是它抗 DB 故障能力的来源，同一个东西。

### UUIDv7 / ULID：把时间塞进 128 位

| 方案 | 位布局 | 长度 | 排序性 | 单调性 | 存储 |
| --- | --- | --- | --- | --- | --- |
| **UUIDv4** | 122 bit 纯随机 | 128 bit / 36 字符 | 无 | 无 | 必须 `BINARY(16)`，绝不能 `CHAR(36)`（→ comp/05 §05.5 二级索引 25.5 GB） |
| **UUIDv7**（RFC 9562） | 48 bit ms 时间 + 4 bit 版本 + 12 bit `rand_a`（可用作计数器）+ 2 bit variant + 62 bit 随机 | 128 bit | 按时间可排序 | 同毫秒内**只有把 `rand_a` 当计数器才单调**；纯随机则同毫秒乱序 | `BINARY(16)` |
| **ULID** | 48 bit ms 时间 + 80 bit 随机 | 128 bit / 26 字符 Crockford Base32 | 按时间可排序（字符串序 = 时间序） | 同上：需同毫秒单调计数器 | `BINARY(16)` 或 26 字符 |
| **Snowflake** | 41+10+12（见上） | 64 bit | 趋势递增 | 单发号者严格单调 | `BIGINT` 8 B |

一张表说清取舍：**UUIDv7/ULID 用 128 位买到了"无协调的全局有序"**，代价是主键从 8 B 变 16 B——按 comp/05 的账，聚簇键从 8 B 变 16 B 会让每个二级索引条目多 8 B，3 个二级索引 × 5,000 万行的体积从 5.1 GB 涨到 6.3 GB（+24%），同时 16 B 随机尾部的页内比较也更贵。**所以「UUIDv7 能不能当主键」的正确答案是：能，但只在"你无法维护 workerId"的时候才值这 24%。**

### 一次发号走哪条路：五个形态的逐跳耗时

| 形态 | 第 1 跳 | 第 2 跳 | 第 3 跳 | 合计（量级） |
| --- | --- | --- | --- | --- |
| Snowflake | 取系统时钟 ~20–30 ns | 一把 `synchronized`/CAS ~20 ns | 位拼装 ~5 ns | **~50–100 ns** |
| 号段（命中内存） | 内存段自增 ~10 ns | 边界判断 ~5 ns | — | **~15–100 ns** |
| 号段（取号） | 应用 → DB RTT 0.2–1 ms | `UPDATE` 行锁 + redo（组提交）0.3–2 ms | 回程 + 换段 | **0.5–3 ms，每 step 个号一次** |
| Redis `INCR` | 应用 → Redis RTT 0.2–1 ms | 单线程执行 ~1 μs | 回程 | **0.2–1 ms/号**（pipeline 可摊到 10 μs） |
| DB 自增 | RTT + 解析 0.1 ms | 插入 + fsync 1–5 ms | 提交返回 | **1–5 ms/次提交**（组提交摊薄） |

> 数字纪律：上表全是**量级**，不是承诺值。跨 AZ 的 RTT 从 0.8 ms 起（同 AZ）到 4–10 ms（跨 AZ），取号路径的耗时会被这一项主导——**号段模式的价值就是把这条 RTT 从"每号一次"摊成"每 step 个号一次"**，摊销倍数 = step。

## 45.4 时钟：唯一一个「别人随时能改」的输入

Snowflake 把毫秒时间戳放进了 ID 高位。这句话的等价说法是：**它的唯一性依赖"这台机器的时钟单调不退"这个前提，而这个前提由你的 NTP 配置、你的虚拟化平台、你的运维习惯共同担保。**

### 时间源会怎么坏：五类故障

| 故障 | 机制 | 对发号器的影响 | 典型量级 |
| --- | --- | --- | --- |
| **NTP 步进（step）** | 偏移超阈值，`chronyd`/`ntpd` 直接把时钟跳到正确值 | 时钟**倒退** → `now < lastTs` → 事故一 | 偏移几十 ms 到数秒；阈值随配置（`makestep`、`-g`）而变，**以目标环境配置为准** |
| **NTP 渐进（slew）** | 以受控速率调整，最大 **500 ppm = 0.5 ms/s** | 时钟变慢但不倒退 → 单调性保住，但**发号速率被限** | 修正 800 ms 需 `800 ÷ 0.5 = 1,600 s ≈ 27 分钟` |
| **闰秒** | 插入或删除 1 秒；部分实现让 `23:59:59` 重复一次 | 时钟**倒退 1 秒**（回退闰秒）或跳前 1 秒 | 1,000 ms；用 leap smear 摊到 24 h 则是 11.6 ppm |
| **VM 暂停 / 快照恢复** | 宿主机把 guest 冻住，恢复后 guest 时钟落后于宿主真实时间 | 恢复瞬间 guest 时钟**跳前**（安全）或随后被 NTP **拉回**（危险） | 暂停时长，秒级到分钟级 |
| **VM 迁移（vMotion 类）** | TSC/时钟源切换导致 guest 时钟漂移 | 迁移后 guest 时钟可能快于真实，随后被 NTP step 拉回 | 数十至数百 ms |

容器是把这件事放大 100 倍的地方：**同一台宿主机上的所有 pod 共享同一个时钟**。一次宿主 NTP 调整，等于**一次性让一个可用区的所有发号者同时回拨**——事故一里 200 个 pod 一起中招，不是巧合，是架构决定的。

### Snowflake 遇到回拨的三种处置，与各自的代价

| 处置 | 怎么做 | 可用性 | 单调 | 有序 | 代价（谁付账） | 适用 |
| --- | --- | --- | --- | --- | --- | --- |
| **① 等** | 自旋/睡眠到 `lastTs + 1`，再继续发号 | 窗口内**阻塞**：延迟 = 回拨量 | ✅ 保住 | ✅ 保住 | 回拨窗口内到达的请求全部排队，`deadline` 短的链路成片超时（45.7 账三） | 回拨小（≤ 2~5 ms）、QPS 不高、上游有充足超时 |
| **② 抛** | 立即抛异常，让上游重试/降级 | 窗口内**全 5xx** | ✅ 保住 | ✅ 保住 | 错误率尖峰 + 重试放大（重试 3 次 = 4 倍流量打回来，→ comp/40 的超时链） | 有成熟重试与降级、且宁失败不可重复 |
| **③ 换 workerID** | 向租约中心借一个"未被使用且代次更新"的 worker 号，换身份继续发 | ✅ 几乎无损 | ❌ **丢**：新号可能小于此前发出的号 | ❌ 丢 | 多一个外部依赖（ZK/etcd/DB）+ 一个备用 worker 池 + 一个"租约过期未回收"的新失败模式 | 回拨大（> 数秒）、不可停服、下游能容忍局部乱序 |
| ④ 扩位/借未来时间 | 从更高位或逻辑时钟吸收回拨（如 RingBuffer 预生成"未来号"） | ✅ 无损 | 单机 ✅ | 局部 ⚠️ | 位宽预算被吃掉；预生成的号在重启时全废（又回到"重启"敌人） | 超高 QPS 且自研发号器有充分测试 |

**实践里的组合拳（这才是要背的）**：把回拨量分三档，阈值都写进配置而不是常量。

| 回拨量 Δ | 处置 | 理由 |
| --- | --- | --- |
| Δ ≤ 2 × 发号间隔（例如 ≤ 5 ms） | **自旋等** | 等待时间小于一次网络往返，业务无感 |
| 5 ms < Δ ≤ 5 s | **换 workerID**（③），换不到则**抛**（②） | 等 5 s 等于停服；租约换身份是唯一"无损"路径，但要留好退路 |
| Δ > 5 s | **拒服 + 告警 + 人工** | 这么大的回拨意味着时间源本身坏了，换身份继续发号只是把问题藏起来 |

**还有一条比上面三条都重要、却最常被漏掉的**：**重启时必须校验"上次的时间戳"与"这个 workerID 的归属"**。Snowflake 的 `lastTs` 在内存里，进程一重启就归零，所有的回拨检测逻辑都失效了——新进程的第一号可能比它重启前发的最后一号还小。工业实现的做法是把 `workerID` 与最后一次时间戳落到本地文件/注册中心，启动时比对，**宁可拒绝启动也不冒重复的风险**（Leaf-snowflake 一类实现即此思路，具体行为以目标版本为准）。

```java
// 回拨处置骨架：分档 + 只对"小回拨"退让 + 大回拨直接拒服
public synchronized long nextId() {
    long now = System.currentTimeMillis();
    if (now < lastTs) {
        long back = lastTs - now;
        clockBackwardTotal.increment();                    // 先记账：回拨次数是头号观测项
        if (back <= tolerateMs) {                          // 档 1：等
            now = spinUntil(lastTs);
        } else if (canBorrowWorker(back)) {                // 档 2：换身份（可能失败）
            switchWorker(workerLease.borrow(back));        // 换完 workerId，lastTs 允许回落到 now
            now = System.currentTimeMillis();
        } else {                                           // 档 3：拒服
            throw new ClockBackwardException(back);
        }
    }
    if (now == lastTs) {
        seq = (seq + 1) & MAX_SEQ;
        if (seq == 0) {                                    // 本毫秒 4,096 个用尽：等下一毫秒
            seqExhaustedTotal.increment();
            now = spinUntil(lastTs + 1);
        }
    } else {
        seq = 0;                                           // 新毫秒：序列归零（靠这把锁保证安全）
    }
    lastTs = now;
    return ((now - EPOCH) << 22) | (workerId << 12) | seq;
}

private long spinUntil(long target) {                      // 忙等 + 让出，不阻塞线程调度
    long n;
    while ((n = System.currentTimeMillis()) < target) { Thread.onSpinWait(); }
    return n;
}
```

> 注意最后那个 `spinUntil`：**等待是有 CPU 代价的**。回拨 800 ms、每个 pod 一个发号线程自旋，等于这 800 ms 里每个 pod 烧满一个核——如果回拨量大又选"等"，你的监控会先看到 CPU 打满，然后才是发号超时。这也是"档 2 换身份"存在的另一半理由。

### workerID：唯一性的另一半，而它是部署系统的函数

| workerID 来源 | 唯一性由谁保证 | 失效场景 | 成本 |
| --- | --- | --- | --- |
| 配置文件 / 环境变量 | 人 | 复制粘贴、扩缩容、机房克隆（**最危险的那一档**） | 0 |
| `pod 序号 % 1024` | 序号唯一 | 副本数 > 1024、新旧代并存、pod 重建复用序号（事故二） | 0 |
| IP 末段 / MAC 哈希 | IP 唯一 | 容器 IP 复用、跨网段、10 bit 装不下 | 低 |
| 注册中心顺序节点 + 本地缓存 | ZK/etcd 的顺序性 | 注册中心不可用 → 拒绝启动（**用可用性换唯一性**） | 中 |
| 号段式 workerID（DB 租约） | DB 行锁 | 租约过期被回收而旧进程还活着 | 中 |
| 启动时持久化 + 代次校验 | 本地磁盘 + 注册中心 | 无状态容器、磁盘丢失 | 低 |

**冲突概率要算，不能感觉。** k 个发号者随机占 N = 1,024 个槽位，至少一对冲突的概率 ≈ `1 − exp(−k(k−1) / 2N)`：

| 发号者个数 k | 冲突概率 | 结论 |
| --- | --- | --- |
| 20 | **16.9%** | 已经不能靠"运气好"过日子 |
| 50 | **69.8%** | 事故二的规模就在这一档 |
| 100 | **99.2%** | 必然撞 |
| 300 | ≈ 100% | 按 `% 256` 取号时 44 个必然同号 |

> **量级结论（非承诺值）**。假设清单：① workerID 在槽位里**均匀随机**分配（按序号取模时它不是随机，是**确定的冲突**，比随机更糟）；② 不考虑新旧代并存的重叠期（叠加后冲突率再翻倍）；③ 冲突**不等于**重复 ID——重复需要"同 worker 位 + 同毫秒 + 同序列"，概率与发号速率成正比（事故二的 4% 就是这么来的）。

## 45.5 号段：步长是同一个旋钮，拧三头

### 取一次号做了什么

```sql
-- 号段表：一行一个业务。biz_tag 是热点行，UPDATE 天然串行
CREATE TABLE id_segment (
  biz_tag    VARCHAR(64) NOT NULL,
  max_id     BIGINT      NOT NULL,        -- 已分配出去的水位（= 最后一段的段尾）
  step       INT         NOT NULL,        -- 一次预取多少个
  updated_at DATETIME(3) NOT NULL,
  PRIMARY KEY (biz_tag)
) ENGINE=InnoDB;

INSERT INTO id_segment VALUES ('order', 3000, 2000, NOW(3));

-- 取号：两条语句一次往返；LAST_INSERT_ID(expr) 把新水位塞进会话变量，省掉再查一次
START TRANSACTION;
UPDATE id_segment
   SET max_id = LAST_INSERT_ID(max_id + step), updated_at = NOW(3)
 WHERE biz_tag = 'order';                  -- ★ 行锁持有到 COMMIT：步长越大，锁的**次数**越少
SELECT LAST_INSERT_ID();                   -- 段尾；本段 = [段尾 - step + 1, 段尾]
COMMIT;

-- 前提与变体：
-- ① 这是普通表，不是 AUTO_INCREMENT，与 innodb_autoinc_lock_mode 无关；
-- ② PostgreSQL 用 UPDATE ... RETURNING max_id 一条搞定（隔离级别 READ COMMITTED 即可）；
-- ③ 行锁争用上限 ≈ 1 / 单次 UPDATE 耗时，与 step 无关——把 step 加大只降**次数**，不降**时长**。
```

### 步长的三侧夹逼（本节唯一值得背的不等式）

`step` 同时被三个方向夹住，而三个方向的"想要"完全不同：

| 方向 | 约束 | 形式化 | 谁在推 |
| --- | --- | --- | --- |
| **取号频率**（越少越好） | 每次取号都付一次 DB RTT + 行锁；step 越大，DB 往返次数越少 | `step ≥ 单机QPS × 目标取号间隔` | 想降低号段表的压力 |
| **重启丢号**（越小越好） | 重启丢弃 cur 剩余 + nxt 整段 ≈ 1.9 step | `step ≤ 日ID量 × 可容忍跳号率 ÷ 每日重启次数` | 想让 ID 看起来连续 |
| **抗 DB 故障**（越大越好） | DB 不可用时，只能用已有的号撑 | `step × buffer数 ≥ 单机QPS × DB 恢复时间` | 想让发号器扛过 DB 抖动 |

**算例：单机 5,000 ID/s、日订单 5,000 万、可容忍跳号 1%、每日重启 1,200 次、要求扛 10 s 的 DB 抖动。**假设：① 双 buffer（重启丢 1.9 step）；② 取号间隔目标 200 ms；③ 跳号预算只算"高位跳空"，不算业务回滚。

| 约束 | 算式 | 结果 |
| --- | --- | --- |
| 取号频率下界 | `5,000 × 0.2 s` | **step ≥ 1,000** |
| 跳号预算上界 | `5e7 × 1% ÷ 1,200` | **step ≤ 416** |
| 抗抖动下界 | `5,000 × 10 s ÷ 2` | **step ≥ 25,000** |
| **可行域** | `[25,000, +∞) ∩ (−∞, 416]` | **空集：这个配置下号段模式无解** |

这就是事故三的"算术真相"：**调大 step 解决的是第三个约束，同时把第二个约束踢爆**。可行的出路只有三条，且都要动别的东西：

| 出路 | 动作 | 代价 |
| --- | --- | --- |
| 减少重启次数 | 把 1,200 次降到 ~50 次：`step ≤ 5e7 × 1% ÷ 50 = 10,000` | 冻结发布窗口、改 HPA 策略、给发号实例单独的稳定部署 |
| 提高跳号容忍 | 把 1% 提到 60%：`step ≤ 25,000` | 接受"ID 只是游标，不是业务序号"（45.8） |
| 归还号段 | 优雅停机时把 `cur` 未用完的部分写回 `max_id` | 崩溃仍丢；写回本身要抢行锁；只把 1.9 step 降到 ~1 step |
| **换形态** | 用 Snowflake 当前缀、号段只用来分配 workerID（Leaf 的混合思路） | 引入时钟依赖（45.4）——敌人的另一半 |

### 双 buffer：把 P99 从"DB 往返"挪到"DB 往返 × 1/step"

单 buffer 的号段分配器有一个致命尾延迟：**段耗尽的那一刻才发现要取号，这次发号就要等 0.5–3 ms**。双 buffer 的全部价值就是把这个事件提前——**在还有 10% 的时候就异步去取下一段**。

```go
type Seg struct{ lo, hi int64 }        // 半开区间 [lo, hi)

type Alloc struct {                    // 每个实例一份：cur/nxt 就是"手上还没发完的号"
	mu       sync.Mutex
	cur, nxt Seg
	base     int64                                  // 当前段段首，用来算消耗比例
	fetching bool
	fetch    func(ctx context.Context) (Seg, error) // 内部：UPDATE 水位 + SELECT 段尾
}
func (a *Alloc) Next(ctx context.Context) (int64, error) {
	a.mu.Lock()
	if a.cur.lo >= a.cur.hi {          // 当前段耗尽
		if a.nxt.hi != 0 {             // 已预取：无缝切段（正常路径，不碰 DB）
			a.cur, a.nxt, a.base = a.nxt, Seg{}, a.nxt.lo
		} else {                       // 没预取到：同步取，P99 就死在这条路上
			seg, err := a.fetch(ctx)
			if err != nil {
				a.mu.Unlock()
				return 0, err
			}
			a.cur, a.base = seg, seg.lo
		}
	}
	id := a.cur.lo
	a.cur.lo++
	need := a.nxt.hi == 0 && !a.fetching && (a.cur.lo-a.base)*10 >= (a.cur.hi-a.base)*9
	a.mu.Unlock()
	if need {                          // 消耗到 90%：异步预取（Go 1.21+ 的 WithoutCancel）
		a.fetching = true
		go func() {
			defer func() { a.fetching = false }()
			if seg, err := a.fetch(context.WithoutCancel(ctx)); err == nil { // 失败不致命
				a.mu.Lock()
				a.nxt = seg
				a.mu.Unlock()
			}
		}()
	}
	return id, nil
}
```

**双 buffer 的代价要写清楚**：它把"重启丢号"从 `0.9 step` 抬到 `1.9 step`（多丢一整段），并让"消耗到 90% 的时刻"成为一次不确定的 DB 压力小尖峰。**换句话说，双 buffer 用 1 个 step 的跳号预算，买到了尾延迟的稳定。**

## 45.6 有序性：为什么「趋势递增」够用，「严格连续」不可得

### 五档有序性，各自要什么机制

| 档位 | 定义 | 需要的机制 | 吞吐上限（量级） | 典型用途 |
| --- | --- | --- | --- | --- |
| **严格连续**（1,2,3,…，无洞） | 每一号都发出去且不重复、不跳过 | 单行锁 + 同步落盘 + 失败即阻塞 | **≈ 1 / fsync ≈ 数百–1,000/s** | 发票号、财务流水（还得配人工） |
| **无空洞**（可乱序但不可缺） | 不跳号，但顺序不保证 | 号段 + 优雅停机归还 | 千级/s | 极少见，代价常被低估 |
| **单机单调** | 同一发号者后发的一定更大，可有洞 | 本地 `lastTs`/计数器 | 数百万/s | 幂等键、游标分页、fencing token（→ comp/46） |
| **全局趋势递增** | 按 ID 排序 ≈ 按时间排序（同毫秒可乱序） | 高位时间戳 + 时钟同步 | 数百万/s × 节点数 | **主键、分片键、消息 key（本套的主战场）** |
| **无序唯一** | 只保证不重复 | 纯随机 | 无限（本地） | 无信息量的对象名、token |

### 为什么「趋势递增」对 B+ 树已经足够

这一条不需要重算，引用 [05](05-innodb-page-and-row.md) 的结论即可（→ comp/05 §05.5 账一、§05.6 三种主键）：自增主键填充率 93.75%、分裂 ≈ 0；**雪花/号段填充率 90~94%、分裂"少量"、写放大 1.1~1.3×**；随机 UUID 填充率收敛到井 69.3%（`ln 2`）、5,000 万行 128 万次分裂、仅分裂一项写放大 3.7×。

真正要回答的是**为什么"少量乱序"不会把雪花退化成 UUID**。算一笔：

**算例**：单机 5,000 ID/s，跨可用区时钟偏差上限 10 ms，叶子页 78 行（→ comp/05 §05.5 步骤 0）。假设：① 乱序窗口 = 时钟偏差 + 同毫秒跨 worker 抖动 ≈ 10 ms；② 尾页热区是"最近 30 天 300 万行"，占约 3.8 万页；③ 忽略二级索引。

| 步 | 推导 | 结果 |
| --- | --- | --- |
| 0 | 乱序窗口内的号量 = `5,000 × 0.01 s` | **50 个号** |
| 1 | 转换为叶子页 = `50 ÷ 78` | **≈ 0.64 页** |
| 2 | 这 50 个号可能落在的页范围 | **最后 1~2 个叶子页**（而不是整棵树） |
| 3 | 打到"最后 2 页"的随机命中率 | `2 ÷ 38,000` ≈ **0.005%**（对比 UUID 的 74% 全树命中率） |
| 4 | 结论：乱序导致的额外分裂 | 量级上是 UUID 的 `1/100` 以下，对应 comp/05 的"1.1~1.3× 写放大" |

> **量级结论（非承诺值）**。假设清单：① 时钟偏差来自 NTP 稳态（同机房 100 μs~1 ms，跨 AZ 1~10 ms，**跨地域可到数十 ms，这时乱序窗口会扩大 10 倍，但相对 3.8 万页仍是千分之一量级**）；② 发号速率与写入速率同阶；③ 业务不是"按 ID 反向高频更新"的形态。**这条算例的真正用途是：让评审接受"趋势递增"而不是追求"严格递增"——后者要付的账在下一张表里。**

### 为什么「严格连续」不可得

四条独立的理由，任何一条成立就足够否决：

| 理由 | 机制 | 数量级 |
| --- | --- | --- |
| **重试天生挖洞** | 拿到号但事务回滚/超时/客户端断开 → 号已消耗、记录不存在 | 跳号率 ≈ 业务失败率 + 超时率 |
| **预取天生挖洞** | 号段/双 buffer 只要有内存缓冲，重启就丢（事故三） | 每次重启 ≈ 1.9 step |
| **连续要求单点或共识** | 要么一个库一行锁（写不进去就发不出号），要么每个号走一次 Raft/2PC（→ comp/43） | 千级/s，且共识组件挂了就停服 |
| **连续 = 可预测 = 可枚举** | 连续 ID 让你能算出别人的单号、单量、增速（45.8） | 安全账，不是性能账 |

**一句能直接进评审的话**：**要连续号的业务，要的不是 ID，是"对账序号"——它应该由财务口径在对账时生成，而不是由发号器在线生成。**

## 45.7 三本账

三本账对应三个"上完线才会来讨的钱"：**号段的 DB 往返**（决定号段表是不是新瓶颈）、**41 位时间戳的年限**（决定这套格式的"保鲜期"）、**回拨窗口**（决定一次时钟事故的爆炸半径）。

### 账一 · 号段 QPS 关系：取号间隔 = 步长 ÷ 单机 QPS

**乘法链**：`单机取号频率 = 单机QPS ÷ step` → `全集群取号次数/s = 单机QPS × 节点数 ÷ step` → `号段表行锁上限 ≈ 1,000 ÷ 单次UPDATE耗时(ms)` → **可行性判据：`全集群取号次数/s < 行锁上限`**。

上一条链里唯一不那么显然的是最后一步：**号段表只有一行，所以全集群所有发号实例的取号操作都在这同一行上串行**。这是号段模式最容易被打爆的地方——它不在"取号慢"，而在"取号的次数乘以实例数"。

**算例：40 个发号实例，单机 QPS 从 5,000 到 50,000，step 取 1,000 / 10,000 / 100,000。**假设：① 单次 `UPDATE` 含 RTT 与 redo 组提交 ≈ 1.5 ms → 行锁上限 ≈ **666 次/s**；② 实例数不变；③ 忽略双 buffer 预取（预取次数已包含在取号次数里）。

| 单机 QPS | 集群总 QPS | step = 1,000 | step = 10,000 | step = 100,000 |
| --- | --- | --- | --- | --- |
| 5,000 | 20 万/s | 200 次/s（30% 行锁） | 20 次/s（3%） | 2 次/s |
| 20,000 | 80 万/s | **800 次/s（超限 ❌）** | 80 次/s（12%） | 8 次/s |
| 50,000 | 200 万/s | **2,000 次/s（超限 ❌）** | **200 次/s（30%）** | 20 次/s（3%） |

| step | 单机取号间隔 @5,000 QPS | 重启丢号（1.9 × step） | 抗 DB 故障时长（单 buffer） |
| --- | --- | --- | --- |
| 1,000 | 200 ms | 1,900 个 | **0.2 s** |
| 10,000 | 2 s | 19,000 个 | 2 s |
| 100,000 | 20 s | 190,000 个 | 20 s |
| 500,000 | 100 s | 950,000 个（事故三） | 100 s |

> **量级结论（非承诺值）**。假设清单：① 行锁耗时以 1.5 ms 计（同 AZ、组提交开启），跨 AZ 拉到 4–10 ms 会把上限压到 100–250 次/s；② 号段表与业务表同库时，行锁会被业务写挤压，**必须独立库/独立实例**；③ 表里"抗 DB 故障时长"是 `step ÷ 单机QPS`，双 buffer 可乘 2。**这张表的价值是让"step 调大"这个动作当场暴露三项代价，而不是只看到"DB 压力下降"这一项收益。**

### 账二 · 41 位时间戳的年限 = 2^41 毫秒

**乘法链**：`2^41 = 2,199,023,255,552 ms` → `÷ 86,400,000 = 25,451.7 天` → `÷ 365.25 ≈ 69.7 年`。

| 时间位宽 | 毫秒精度可用年限 | 从 2025 年 epoch 起算到期 | 微秒精度可用年限 | 结论 |
| --- | --- | --- | --- | --- |
| 39 bit | 17.4 年 | 2042 年 | 6.4 天 | 只够做 10 ms 精度的变体（Sonyflake 类） |
| **41 bit** | **69.7 年** | **2095 年** | 25.5 天 | **毫秒精度的标准选择** |
| 42 bit | 139.4 年 | 2164 年 | 51 天 | 多 1 bit 换 70 年，但吃掉 1 bit 序列或机器位 |
| 48 bit | 8,925 年 | 10950 年 | 8.9 年 | UUIDv7 的选择（128 位不在乎） |

> **承诺值（可用年限本身是算术恒等式，不是估算）**：2^41 ms = 69.73 年，这是精确值。但"哪一年到期"取决于 epoch，而 **epoch 是不可回退的选择**：把 epoch 从 1970 换成 2025，等于把到期年从 2080 推到 2095，代价是"2025 年之前的业务时间戳无法编码"——所以**迁移时必须整列重发号，不能只改常量**。用微秒精度的那一列是反例警告：**把时间精度提高 1,000 倍，等于把可用年限砍到 1/1,000**，41 位微秒只有 25 天。

### 账三 · 回拨窗口 = 检测延迟 + 等待时间

**乘法链**：`检测延迟 ≈ 相邻两次发号的间隔 = 1 / 单机QPS` → `等待时间 = 回拨量 Δ（选"等"时）` → `受影响请求数 = 单机QPS × (检测延迟 + 等待时间)` → `超时失败数 = 单机QPS × max(0, 窗口 − 请求deadline)`。

**算例：单机 5,000 ID/s，NTP 步进回拨 800 ms，上游请求 deadline 300 ms。**假设：① 请求均匀到达（泊松近似）；② 时序是"等"（档 1 策略，但阈值没设好）；③ 等待期间请求占着连接与线程（同步调用）；④ 不考虑上游重试放大。

| 项 | 算式 | 结果 |
| --- | --- | --- |
| 检测延迟 | `1 ÷ 5,000` | **0.2 ms** |
| 等待时间 | Δ | **800 ms** |
| 不可用窗口 | `0.2 + 800` | **800.2 ms** |
| 受影响请求 | `5,000 × 0.8002` | **≈ 4,001 个** |
| 其中超过 300 ms deadline 的 | `5,000 × (0.8002 − 0.300)` | **≈ 2,501 个失败** |
| 若改选"抛"：5xx 数 | ≈ 4,001 个，上游重试 3 次 → **12,003 请求**打回本服务 | 错误率 100% → 雪崩风险 |

| 回拨量 Δ | 检测延迟 0.2 ms | 受影响请求（5,000 QPS） | 等 vs 抛 vs 换 |
| --- | --- | --- | --- |
| 5 ms | 0.2 ms | 26 个 | 等（业务无感） |
| 50 ms | 0.2 ms | 251 个 | 等（若 deadline ≥ 100 ms） |
| 800 ms | 0.2 ms | 4,001 个（2,501 失败） | **换 workerID** |
| 5 s | 0.2 ms | 25,000 个 | 换；换不到就拒服 |

> **量级结论（非承诺值）**。假设清单：① 检测延迟取 `1/QPS`——**低 QPS 的发号器检测得反而更晚，但窗口内请求少，危害更小**（危害 = QPS × 窗口，不是窗口本身）；② 等待期间线程被占住（自旋更糟：占 CPU）；③ 上游有重试则"抛"策略的流量放大倍数 = 重试次数 + 1（→ comp/40）；④ 若用 slew 而非 step，窗口会被拉长到 `Δ ÷ 0.5 ms/s`（800 ms → 27 分钟），但**单调性保住、不需要拒服**——这是 slew 唯一比 step 友好的地方。

```python
# 三本账复算（Python 3.9+）：改任一假设直接重跑
def seg_fetch(qps_node, step, nodes=40, upd_ms=1.5):
    interval_ms = step / qps_node * 1000              # 取号间隔 = 步长 ÷ 单机 QPS
    total_fetch = qps_node * nodes / step             # 全集群取号次数/秒
    return interval_ms, total_fetch, 1000 / upd_ms    # 最后一项 = 行锁上限

def horizon(bits=41, unit="ms"):
    seconds = 2 ** bits / (1000 if unit == "ms" else 1e6)   # 毫秒精度 vs 微秒精度
    return seconds / 86400 / 365.25, seconds / 86400        # (可用年, 可用天)

def backward(offset_ms, qps_node, deadline_ms):
    window = offset_ms + 1000 / qps_node              # 检测延迟 + 等待时间
    hit = qps_node * window / 1000
    lost = qps_node * max(0.0, window - deadline_ms) / 1000
    return window, hit, lost

def step_range(qps_node, restart_day, tolerate, daily_ids, fetch_interval_ms, db_outage_s):
    lower = max(qps_node * fetch_interval_ms / 1000, qps_node * db_outage_s / 2)  # 双 buffer
    upper = daily_ids * tolerate / restart_day
    return lower, upper, lower <= upper

print("账一 5k/2k:", "间隔 %.0f ms, 取号 %.0f 次/s, 行锁上限 %.0f 次/s" % seg_fetch(5000, 2000))
y_ms, _ = horizon(41)
_, d_us = horizon(41, "us")
print("账二 41 bit ms = %.1f 年；41 bit μs = %.1f 天" % (y_ms, d_us))
print("账三 回拨 800 ms:", "窗口 %.1f ms, 受影响 %.0f, 失败 %.0f" % backward(800, 5000, 300))
lo, hi, ok = step_range(5000, 1200, 0.01, 5e7, 200, 10)
print("步长可行域 [%.0f, %.0f] → %s" % (lo, hi, "可行" if ok else "空集：先减重启次数或换形态"))
```

## 45.8 边界：ID 不是业务键，更不是凭证

| 想做的事 | 能做吗 | 为什么（指到机制） | 正确做法 |
| --- | --- | --- | --- |
| 用 Snowflake ID 当主键/聚簇键 | ✅ 首选 | 8 B + 趋势递增 → 尾页插入（→ comp/05 §05.6） | `id BIGINT PRIMARY KEY`，业务号另建列 |
| 用 ID 当**对外的单号**（展示给用户） | ⚠️ 勉强 | 可解析：时间位泄漏下单时刻、机器位泄漏容量（→ comp/05 表"对外可暴露"行） | 另建 `order_no`（随机 6 位前缀 + 日期 + 校验位）并建唯一索引 |
| 用 ID 当**连续流水号**（发票、财务） | ❌ 不可得 | 连续需要单点/共识，吞吐千级且必阻塞（45.6） | 财务口径离线生成 + 对账 |
| 用 ID 当**安全凭证**（下载链接、API 资源标识） | ❌ 禁止 | 相邻 ID 可枚举：`id+1` 就是别人的资源 → IDOR 越权；增长速度还泄漏业务量 | 不透明 token（HMAC 签名或随机 128 bit）+ **服务端每次鉴权** |
| 用 ID 当**幂等键** | ✅ 但要单机单调 | 幂等键要的是"同一请求拿到同一值"，需要稳定的请求标识 | 客户端生成 UUIDv7/ULID，或"业务键 + 发号" |
| 用 ID 做**分片路由** | ✅ 注意高位 | 分片键取 ID 高位 = 取时间 → 新数据全落在最后一个分片（热点） | 取低位或哈希，或直接用业务键分片（→ comp/36） |
| 跨机房双活各发各的号 | ✅ 有前提 | 唯一性 = worker 位段按机房隔离；**全局有序不可得**（时钟域不同） | 10 bit 里切 2~3 bit 给机房/单元，worker 位降到 7~8 bit（128~256 节点上限） |
| 换一代 ID 格式（比如 UUIDv7 → Snowflake） | ⚠️ 一次性成本极高 | 旧 ID 与新型号可能撞在同一个列上；排序语义也变了 | 保留"代次位"或用独立的列/表；迁移期双写 |

**三句话总结 45.8**：① **ID 是存储位置与排序锚点，业务标识应该另起一列**；② **凡是能被猜到的 ID 都不能当权限**——这条与 ID 生成算法无关，与授权校验有关；③ **多活把"有序"从全局降级为"每机房"，却不会把"唯一"降级**——所以多活的代价永远落在 `worker` 位宽和可观测性上，而不是落在唯一性上。

## 45.9 决策表：按顺序排除，五步选出发号器

评审上最有效的问法是**从最便宜的方案开始排除**，而不是比较优劣。下表从上往下走，**遇到的第一个"是"就是答案**。

| 步 | 问 | 是 → | 否 → |
| --- | --- | --- | --- |
| 1 | 发号量在**单表单库可控**范围（< 数千 ID/s），且允许单点？ | `AUTO_INCREMENT` / DB 序列（最简单，别过度设计） | 下一步 |
| 2 | 业务真的需要**连续号**（发票、财务流水、监管报送）？ | 离线"财务序号" + 对账；**不要**用在线发号器硬撑连续 | 下一步 |
| 3 | 能**稳定维护 workerID**（副本数 < 1,024、能杜绝新旧代并存）？ | **Snowflake**（首选：8 B、趋势递增、无外部依赖） | 下一步 |
| 4 | 无法维护 workerID，但能接受 16 B 主键（+24% 二级索引体积）？ | **UUIDv7 / ULID**（无协调、时间可排序、需同毫秒计数器才单调） | 下一步 |
| 5 | 已有关系库且要"趋势递增 + 段内连续 + 抗发号网关故障"，且能在 45.5 的夹逼不等式里解出 step？ | **号段模式**（DB 双 buffer；配优雅停机归还） | 回退到 3 步，用租约式 workerID 硬撑 Snowflake |

| 场景 | 推荐形态 | 一句话理由 | 必须同时配的三件事 |
| --- | --- | --- | --- |
| 单库单表的中小系统 | DB 自增 | 没有比它更省事的 | 对外另建业务号；跳号写进规范 |
| 分库分表的订单/用户主键 | Snowflake（租约式 workerID） | 8 B + 趋势递增 = B+ 树尾页插入 | 三档回拨策略、启动校验、回拨次数告警 |
| 日志/事件/对象名的唯一 key | UUIDv7 / ULID | 无协调、可排序、跨系统不冲突 | 存 `BINARY(16)`；同毫秒单调计数器 |
| 短链、票号类"要短要递增" | Redis `INCR` + 号段预分配 | 单线程原子、吞吐高 | 号段式预分配（别让它成为唯一真相）、AOF 策略 |
| 2,000+ pod、多可用区 | Snowflake（机房位 + 租约 workerID） | 槽位不够就切位宽，不能靠"取模碰运气" | 机房位切分、workerID 基数巡检 |
| 完全不能受时钟影响 | 号段（+ 回拨无关） | 唯一性来自 DB 行锁，不来自时钟 | 解出 step 的夹逼不等式、独立号段库 |

> **这张表的用法**：先做减法（1、2 步），再谈形态。绝大多数团队的正确答案是第 1 步或第 3 步；**"我们要上分布式 ID 服务"这个需求里，真正需要分布式 ID 的比例远低于需要重写分片键的比例**（→ comp/36）。而第 5 步之所以放在最后，是因为号段模式的 `step` 在真实系统里常常**无解**（45.5 的三侧夹逼），它看起来最简单、算起来最刻薄。

## 45.10 踩坑清单（现象 → 根因 → 定位 → 修复 → 防复发）

| 现象 | 根因（指到物理形态） | 定位 | 修复 | 防复发 |
| --- | --- | --- | --- | --- |
| 某段时间大量 `Duplicate entry` 主键冲突 | 时钟回拨 + 序列回绕（同一毫秒被挤进 > 4,096 个号），或 workerID 撞车 | 查 `node_timex_offset_seconds` 的历史曲线；解码重复 ID 的 `(ts, worker, seq)` 看是否同 worker | 换 workerID 或拒服；把重复区间内的记录人工对齐 | 回拨三档策略（45.4）+ workerID 租约 |
| 报错停止了，但报表里出现"两条记录同一个 ID" | 撞车的表**没有唯一索引**，静默写入 | 在无唯一索引的表上跑 `GROUP BY id HAVING COUNT(*)>1` 抽样 | 补唯一索引（先清洗）+ 修数 | 所有"实体表"必须有 ID 唯一约束；埋点表用 `(id, 时间)` 复合唯一 |
| ID 突然跳了一大段（几万到几亿） | 号段重启丢段（1.9 × step），或 step 被调大 | 对比 `id_segment.updated_at` 与实际发出量；数发布/扩缩容次数 | 降 step、优雅停机归还号段 | 把 step 纳入容量评审（45.5 三侧夹逼）；对账不要依赖 ID 连续 |
| 发号延迟 P99 每隔几秒抖一次 | 段耗尽时同步取号（双 buffer 没生效或 90% 阈值没触发） | 打点"同步取号次数"；看抖动周期是否 ≈ step ÷ QPS | 修正预取阈值与 `fetching` 标志 | 观测项里加"同步取号次数/s" |
| 号段表所在库 CPU 打满、慢查询排队 | 40 个实例 × 高 QPS ÷ 小 step = 每秒上千次 `UPDATE` 同一行 | `SHOW ENGINE INNODB STATUS` 看行锁等待；`performance_schema` 看该 SQL 的 `COUNT_STAR` | 提高 step 或把号段表迁到独立实例 | 账一写成容量模型（行锁上限 1,000 ÷ 1.5 ms） |
| 大促扩容后 ID 开始重复 | 副本数超过 worker 槽位数，或新旧代并存 | 统计在线实例的 `workerId` 基数（应等于实例数） | 扩到租约式分配；拆机房位段 | 扩缩容检查项：`workerId 基数字段 == 实例数` |
| 服务重启后第一批号比重启前小 | `lastTs` 在内存，重启归零；回拨检测失效 | 对比重启前后的 ID 序列 | 持久化 `(workerId, lastTs)`，启动时校验 | 启动自检：无法校验就拒绝启动 |
| Redis `INCR` 出来的号重复 | 主从切换丢写（异步复制）或 RDB 恢复回退 | 看 `INFO replication` 的切换时间点与号段区间 | 号段式预分配（每 N 个号才落一次），把回退窗口缩到 N | 别把 Redis 当"严格递增"的唯一来源；AOF `appendfsync always` 的吞吐代价要先算 |
| `AUTO_INCREMENT` 重启后号跳了 | 8.0 起计数器已持久化，但**批量插入预留**仍会跳；更早版本重启回退 | 对比 `SHOW TABLE STATUS` 的 `Auto_increment` 与 `MAX(id)` | 接受跳号；要连续就另建业务号 | 把"跳号"写进业务规范，别让前端依赖位数 |

## 45.11 观测：五个数覆盖 90% 的 ID 故障

| 指标 | 看什么 | 拐点阈值 | 版本 / 开关前提 |
| --- | --- | --- | --- |
| **时钟偏移与同步状态** | 本机与上游时间源的偏移、是否处于同步状态 | 偏移 > 50 ms 关注，> 128 ms 高危（NTP 常见 step 阈值附近） | `node_exporter` 的 timex collector：`node_timex_offset_seconds`、`node_timex_sync_status`、`node_timex_maxerror_seconds`；**需采集器版本支持 timex**，容器内采集需挂载宿主 `timex` |
| **回拨次数** `id.clock_backward_total` | 每次检测到 `now < lastTs` 记一笔，带 `back_ms` 标签分桶 | **> 0 持续 5 分钟即告警**（正常稳态应为 0） | 自埋点；桶边界建议 `≤5ms / ≤5s / >5s`，与三档策略对齐 |
| **号段剩余**（`remaining` = 当前段剩余 + 下一段） | 还能撑多久：`remaining ÷ QPS` | 秒级余量告警（`remaining/QPS < 10 s`） | 自埋点；Leaf 类实现自带 `/monitor` 端点，字段以目标版本为准 |
| **同步取号次数** / 取号失败率 | 双 buffer 是否生效、DB 是否抖动 | > 1 次/分钟 或失败率 > 0.1% | 自埋点（Go 版看 `fetching` 标志与 `fetch` 错误） |
| **workerId 基数 vs 实例数** | 是否撞号：两者应相等；再用 `(id >> 12) & 0x3FF` 反解实际发号的 worker 集 | **不相等即故障前兆** | 需要注册中心里有实例列表；或从 ID 反解做离线巡检 |
| **序列耗尽次数** `id.seq_exhausted_total` | 单机是否逼近 4,096/ms | > 0 持续出现说明速率逼近上限或时钟被 slew 限速 | 自埋点；`slew` 期间会更频繁，属预期 |
| **重复 ID 检出** | 无唯一索引的表也要能查 | 每日巡检 > 0 即工单 | SQL 见下；**注意全表 `GROUP BY` 很贵，按时间窗抽样** |

```sql
-- 重复 ID 巡检：真正有效的不是"查主键重复"（主键会挡住），而是"解码时间位找死区"
SELECT worker_id, COUNT(*) AS suspicious
FROM (
  SELECT (id >> 12) & 1023                 AS worker_id,
         (id >> 22) + 1735689600000        AS id_ts_ms,      -- epoch = 2025-01-01T00:00:00Z
         UNIX_TIMESTAMP(created_at) * 1000 AS row_ts_ms
  FROM t_order
  WHERE created_at >= NOW() - INTERVAL 1 HOUR
) t
WHERE id_ts_ms > row_ts_ms + 50            -- ID 时间比落库时间还新 50 ms：时钟跑快/回拨后借号
   OR id_ts_ms < row_ts_ms - 5000          -- ID 比落库早 5 s 以上：写入链路在排队/重试
GROUP BY worker_id
HAVING suspicious > 0;
```

> 指标纪律：**"回拨次数"必须与"号段剩余"放在同一块看板上**。回拨次数上涨 + 号段剩余下降快 = 时钟与容量同时在恶化；只有回拨次数涨、号段不动 = 大概率是宿主 NTP 换源，全站 pod 一起中招（事故一）。另外，所有"自埋点"的计数必须带**分桶标签**（`back_ms` 的区间），否则你只知道"回拨过"，不知道"该选档 1 还是档 3"。

## 45.12 一页速记

| 问题 | 一句话答案 |
| --- | --- |
| Snowflake 64 位怎么切 | 1 符号（恒 0）+ 41 ms 时间 + 10 机器 + 12 序列；`((ts-epoch)<<22)|(wid<<12)|seq` |
| 41 位能用到什么时候 | `2^41 ms ≈ 69.7 年`；epoch 决定到期年，换 epoch 必须整列重发号 |
| 单发号者吞吐上限 | `4,096/ms = 4.096M/s`（序列位宽决定的算术上限） |
| 唯一性的两个因子 | worker 位不撞 ∧ (ms, seq) 不回头；两者都由**别人的系统**担保 |
| 回到回拨了怎么办 | 分三档：≤5 ms 等；≤5 s 换 workerID；>5 s 拒服 + 告警 |
| 「等」的代价 | 窗口内 `QPS × Δ` 个请求排队，超过 deadline 的成片失败 |
| 「抛」的代价 | 事件率尖峰 + 上游重试放大 `(重试次数+1)` 倍 |
| 「换」的代价 | 多一个外部依赖；**单调性丢了**（新号可小于旧号） |
| 号段 QPS 关系 | 取号间隔 = `step ÷ 单机QPS`；全集群取号次数 = `单机QPS × 节点数 ÷ step` |
| 号段表的真瓶颈 | 那一行的行锁：上限 ≈ `1,000 ÷ 单次 UPDATE 耗时(ms)` |
| 步长怎么定 | 三侧夹逼：取号频率下界、跳号预算上界、抗抖动下界——常常是空集 |
| 重启丢多少号 | `≈ 1.9 × step`（cur 剩余 0.9 + nxt 整段 1） |
| 为什么趋势递增够 B+ 树用 | 乱序窗口 10 ms × 5,000/s = 50 行 ≈ 0.64 页，只影响最后 1~2 页（→ comp/05 §05.5） |
| 为什么严格连续不可得 | 重试挖洞 + 预取挖洞 + 连续要单点/共识（千级/s）+ 连续即可枚举 |
| workerId 撞车概率 | `1 − exp(−k(k−1)/2N)`；k=50, N=1,024 → **69.8%** |
| ID 能不能当权限 | 不能：相邻 ID 可枚举 → IDOR；要 token + 服务端鉴权 |
| 最该监控的两个数 | 回拨次数（分桶）、号段剩余（换算成秒） |

## 45.13 自检题（5 题，答案要点）

**1. NTP 回拨 800 ms，为什么「继续用上一个毫秒」这个分支会导致重复 ID？换成「抛异常」就没有问题了吗？**

因为发号器并没有停下来：回拨期间它仍然以每秒数千的速率把号盖在**同一个毫秒**里，而单毫秒只有 4,096 个序列槽位，**挤满就回绕**，回绕后重发的 `seq` 与回拨前该毫秒已用的 `seq` 撞车（事故一：4,800 个号挤进 4,096 个槽位，回绕一次，重复 801 个）。「抛异常」确实能保住唯一性（因为不发号就不会重复），但代价是把 800 ms 内的 `QPS × 0.8` 个请求变成 5xx，并被上游重试放大 `(重试次数+1)` 倍。**正确做法是分档：小回拨等、中回拨换 workerID、大回拨拒服。**

**2. 40 个发号实例、单机 20,000 ID/s、step = 1,000，号段表撑得住吗？讲讲你算的那一步。**

撑不住。`全集群取号次数 = 20,000 × 40 ÷ 1,000 = 800 次/s`，而号段表只有一行，`单次 UPDATE`（含 RTT + redo 组提交）约 1.5 ms → 行锁上限 `1,000 ÷ 1.5 ≈ 666 次/s`。**800 > 666，已经超限**。把 step 提到 10,000 就降到 80 次/s（12% 利用率），代价是重启丢号从 1,900 涨到 19,000、抗 DB 故障时长从 0.2 s 涨到 2 s。**关键认知：step 加大只降低取号"次数"，不缩短单次"时长"；号段表的瓶颈是次数 × 实例数。**

**3. 号段模式里，「调大步长抗 DB 抖动」和「跳号量」为什么是同一个旋钮？给出夹逼不等式。**

因为抗抖动的本质是"本地缓存更多号"，缓存的量就是 `step × buffer 数`；而重启时这些缓存全部作废，丢弃量 ≈ `1.9 × step`。于是同时要满足：`step ≥ 单机QPS × 目标取号间隔`（取号频率）、`step ≥ 单机QPS × DB恢复时间 ÷ buffer数`（抗抖动）、`step ≤ 日ID量 × 可容忍跳号率 ÷ 每日重启次数`（跳号预算）。**当每日重启次数很大时三条无交集**（事故三的配置下可行域是空集），出路只有减少重启、提高跳号容忍、优雅停机归还号段，或者换形态。

**4. 为什么说「趋势递增」对 B+ 树够了，「严格连续」却换不来？**

B+ 树只关心"新插入是否集中在树尾"：10 ms 的乱序窗口 × 5,000/s = 50 个号 ≈ 0.64 个叶子页，只影响最后 1~2 页，相对 3.8 万页的热区命中率是 99.995%（→ comp/05 §05.5 的分裂账里，雪花/号段就是 1.1~1.3× 写放大，而随机 UUID 是 3.7×）。而"严格连续"要求**每一号都必须发出去且不重复**，这在分布式下只有两条路：单点串行（写不进去就停服）或每号一次共识（吞吐降到千级/s）；再加上重试与预取天生挖洞，以及"连续即可枚举"的安全问题——**连续号是财务序号的需求，不是 ID 的需求。**

**5. 你现在要给一个 2,000 pod、跨 3 个可用区的电商系统做发号器，选什么？说出你的排除过程。**

① 需要"连续号"吗？不需要 → 排除"DB 序列 + 连续"方案。② 能维护 workerID 吗？2,000 pod > 1,024 槽位 → **单层 10 bit 装不下** → 排除"配置/序号取模"（撞车概率 100%）。③ 时钟可信吗？三可用区独立 NTP，跨 AZ 偏差 1–10 ms → Snowflake 可用，但必须配三档回拨策略 + 启动校验。④ 结论：**主链路用 Snowflake + 租约式 workerID（注册中心顺序节点/号段租 workerId），并把 10 bit 切成 2 bit 机房 + 8 bit worker（256/机房，够用且方便运维）**；对"绝对不能受时钟影响"的场景（如资金流水）加一层号段模式兜底，跳号用对账吸收。**排除项：纯号段（2,000 pod 的取号次数会把那一行打死：`2,000 × QPS ÷ step` 轻松上千次/s）；UUIDv4 当主键（3.7× 写放大）；Redis `INCR` 当唯一来源（主从切换丢写）。**
