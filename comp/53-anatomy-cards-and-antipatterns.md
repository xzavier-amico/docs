## 53.1 引子：三起「换了零件，没换掉问题」的事故

收口篇的三起事故，形状和前面 52 篇都不一样：**它们不是某个组件崩了，而是「判断」崩了**。第一起花了两笔钱买新零件，故障只换了皮肤；第二起所有仪表都是绿的，只有账单在涨；第三起同一条故障连续发生三次，每次的修法都只在上一版参数上加了个零。三起事故的共同点是：**团队都在解决问题，但解决的是「现象所在的层」，不是「根因所在的形态」。**

三起事故分别打在三个不同位置：**换形态不换访问契约（§53.3）**、**指标与账本不同源（§53.7）**、**用参数修补结构缺陷（§53.4 第 10 条）**。

### 事故一：两次「换检索组件」，深翻页的病一次都没治（2026-01-14 至 2026-02-09）

某电商商品搜索，索引 2.4 TB、12 个主分片（每分片 200 GB、各 1 副本，即 24 份分片数据）。前端列表页支持「跳到第 100 页」，接口实现是 `from=2000&size=20`。P99 从 1.4 s 缓慢抬到 1.9 s 后，团队做了第一次「换零件」的动作。

| 时刻 | 动作 | 关键数字 |
| --- | --- | --- |
| 01-14 | 现状：12 分片 × 200 GB，`from=2000&size=20`，P99 1.9 s | 候选行 = 12 × 2,020 = **24,240**，客户端只要 20 条 |
| 01-15 | 判断：「分片太少不够并行」→ 分片 12 → 60，节点 6 → 12 | 每分片降到 40 GB（方向对） |
| 01-15 | 首次压测：P99 反而从 1.9 s 涨到 11 s | 扇出核时 60 × 0.8 ms = **48 ms/查询**（原 9.6 ms） |
| 01-16 | 继续判断：「机器不够」→ 单节点 32C → 64C，副本 1 → 2 | 候选行 60 × 2,020 = **121,200**，丢弃率 99.98% |
| 01-20 | 一次节点重启触发副本重建：单分片 40 GB @ 40 MB/s ≈ 17 min，但 60 分片同时迁移 | relocation 自造 IO 风暴，P99 到 14 s |
| 02-03 | 第二次「换零件」：引入独立向量检索做语义召回（新组件） | 接口契约原样搬过去：`page=100, size=20` |
| 02-09 | 新组件上同一故障复现：每页要跑 100 次「取 20 条」的图遍历，单请求 2.4 s | 计算量 ≈ 100 × 基线，与分片无关 |
| 02-10 | 真正修法：`search_after` + PIT 替代 `from+size`；单分片控制到 ≤ 40 GB | 候选行 = 2,020（与分片数**解耦**），P99 210 ms |

账只有一条**乘法链**，从头到尾没变过：

- 候选行数 = `分片数 × (from + size)`：改前 `12 × 2,020 = 24,240`，改后 `60 × 2,020 = 121,200`（**放大 5 倍，与分片数同比例**）。
- 相对返回 20 条的有效放大：`24,240 ÷ 20 = 1,212×` → `121,200 ÷ 20 = 6,060×`。
- 扇出固定核时 = `分片数 × 0.8 ms`（量级取自 [23](23-es-cluster-shards-replicas.md) §23.5 的每片核时）：`9.6 ms → 48 ms`，单核 QPS 上限 `104 → 20.8`（**同上，掉 5 倍**）。
- 向量检索那一侧的等价乘法：单请求计算量 ≈ `页深 × 每页候选预算 ÷ 基线` = `100 × 20 × ef ÷ 基线`，与分片数无关，因此「扩分片」这个动作在新组件上连方向都不对。

**假设清单**：每片固定核时 0.8 ms 为量级值（随版本、字段数、filter 命中率浮动 2–3 倍）；`from+size` 的归并与 fetch 两阶段成本按 [24](24-es-query-execution.md) §24.6 的口径；向量侧按 HNSW `ef_search` 常数预算、无量化。**量级结论**：把 `from+size` 换成 `search_after` 收益是「分片数不再进乘法」，在本例是 5–10 倍；换组件收益为 0，因为乘法链里没有「组件」这一项。

> **这一起事故的教训一句话**：换零件换的是**形态**，换不掉**访问契约**里的病。分页深度、字段基数、保留天数这些都是契约，它们跨组件不变——先改契约，再谈换零件。

### 事故二：指标全绿，Kafka 存储账单从 $6.3k/月涨到 $17.3k/月（2025-08-11 至 2025-12-01）

某风控平台有 12 个 topic、总写入 62.4 MB/s（跨 3 个可用区，RF 原本 = 2，`retention.ms` = 3 天）。半年里做了三个「完全合理」的变更：

1. 作日保留从 3 天延到 7 天（合规要求能回查一周）；
2. RF 从 2 提到 3（一次磁盘损坏丢了一个副本，事故复盘要求三副本）；
3. 新增 4 个下游消费者，全部从最早的位点各回放一份历史（因此 `retention` 不能提前缩）。

半年后月度存储账单 $6,347 → $17,277。而同期**所有 SLO 面板都是绿的**：

| 指标 | 读数 | 为什么它证明不了问题 |
| --- | --- | --- |
| Consumer lag | 0（偶发 < 1 万条，30 s 内归零） | lag 是「消费是否跟上」，与「盘上存了多久」无关 |
| `UnderReplicatedPartitions` | 0，持续 | ISR 满说明复制健康，不代表副本数经济 |
| 生产 P99 | 12 ms，无变化 | 只追加路径对保留期完全不敏感 |
| Broker CPU | 41% | 磁盘成本与 CPU 无因果关系 |
| 盘水位 | 61% | **半年前为这个项目扩过一轮盘，水位被"藏"住了** |
| 月度账单 | $17,277，日环比 +0.4% | 从来没人把「GB·月」当指标发出去 |

没有一条指标是「错」的；错的是**没有一个指标在算这本账**。把 [28](28-kafka-log-segments.md) §28.7 的存储公式写成乘法链，这件事在变更前 3 分钟就能算出来：

- 每日新增逻辑字节 = `62.4 MB/s × 86,400 s = 5.39 TB/天`。
- 盘占用 = `速率 × 保留天数 × RF × 1.15`（1.15 为索引文件 + 段粒度滞后的量级系数，取自 [28](28-kafka-log-segments.md) §28.7）。
- 变更前：`5.39 × 3 × 2 × 1.15 = 37.2 TB`；变更后：`5.39 × 7 × 3 × 1.15 = 130.2 TB`；**倍率 = (7/3) × (3/2) = 3.50×**。
- 盘钱（gp3 类 $0.08/GB·月，以厂商当期价目为准）：`37.2 TB = 38,093 GB → $3,047/月`；`130.2 TB = 133,120 GB → $10,650/月`。
- 跨 AZ 复制流量（$0.02/GB，量级）：变更前 `5.39 TB/天 = 5,520 GB/天 → $110/天 ≈ $3,300/月`；变更后 `10.78 TB/天 = 11,040 GB/天 → $221/天 ≈ $6,627/月`。
- 合计：`$6,347 → $17,277`，**集群总账单 `$18.0k → $28.9k`**（该项占比 35% → 60%）。

**假设清单**：62.4 MB/s 为稳态均值，峰值 1.8 倍（容量应按峰值的 1.2 倍另外加余量）；gp3 单价与跨 AZ 单价随区域与合同浮动 ±30%；未计请求费与 tiered storage 分层；1.15 为量级系数，不同消息大小下实测 1.10–1.25。**量级结论**：这一起事故的成本是「保留天数 × 副本数」的**乘积**，两个动作单独看都是 1.5–2.3 倍，叠加就是 3.5 倍；而它们没有任何一个会触发 SLO 告警。

> **这一起事故的教训一句话**：**指标衡量的是「系统是否健康」，账本衡量的是「这笔钱值不值」**。三本账（→ [01](01-component-anatomy-method.md) §01.3）必须有自己的看板；否则「指标全绿 + 成本翻倍」是一种必然，不是巧合。

### 事故三：同一个故障第三次发生，每次修的都是参数（2024-11 / 2025-06 / 2026-03）

某营销平台有一个「每天 10:00 发一批优惠券」的定时任务。三次事故，同一个结构：

| 次 | 日期 | 触发 | 重复量 | 当时的修法 | 修的是哪一层 |
| --- | --- | --- | --- | --- | --- |
| 一 | 2024-11-11 | 发版滚动更新，两个 Pod 同时跑（单机 cron，无互斥） | 3.2 万张 × 20 元 = 64 万元 | 加 Redis 锁：`SET NX PX 300000`（TTL 5 min） | 加了 L1（原子互斥），没有 L2/L3 |
| 二 | 2025-06-18 | 券量涨 4 倍，任务跑 8 min > TTL 5 min，锁自动释放后被第二个实例拿走 | 5.6 万张 × 20 元 = 112 万元 | **把 TTL 从 5 min 调到 30 min** | 只改了参数 |
| 三 | 2026-03-03 | 任务改 8 分片并行；分片元数据在 ZK，会话 5 s 过期；Pod GC 停顿 6.1 s 被判死，分片被重新分配 | 12.7 万张 × 20 元 = 254 万元 | 会话 5 s → 10 s，并「加了两台机器」 | 又是只改参数 |

三次修复的**共同错误**：把「锁的可靠性」当成目标，而真正的目标是「旧主人能不能被挡住」（→ [46](46-distributed-lock-and-leader-election.md) §46.4）。第三次的账可以写成一条不等式：

- 误判条件：`停顿 P > TTL − 续租间隔`。TTL 30 min、续租每 30 s 一次 ⇒ 要停顿 29.5 min 才误判——所以第三次不是锁 TTL 的问题，是**分片元数据用了另一个更短的会话（5 s）**，**同一个系统里存在两个不同量级的「死亡判定时钟」，而任务同时依赖两者**。
- 重复量上界 = `重复窗口 × 发放速率` = `6.1 s（够不够跑完一批）× 每小时 7.5 万张 ≈ 127 张/秒 × 6.1 s ≈ 775 张`——**但实测 12.7 万张**，说明真正的机制不是「两个实例同时跑一段」，而是「两个实例各跑完了整批的不同切片、且切片归属被无痕改写」。这类事故的重复量**不能用窗口 × 速率估**，只能用唯一键对账量。
- 如果按 `(券 ID, 批次号, fence)` 建唯一索引，并且 fence 来自单调递增的租约版本（etcd `revision` 或 Redis `INCR`），那么第三次事故的重复量上界是 **0**——与 TTL 取 5 s 还是 30 min 无关。

**假设清单**：面额 20 元、单批 12.7 万张为业务实际值（非估算）；GC 停顿 6.1 s 取自容器 `P99` 与 `jvm_gc_pause_seconds`；「重复量上界 = 0」成立的前提是**唯一键落在被保护的数据上**（发券记录），而不是落在锁服务上——这条前提是 46 篇的整个论点。**承诺值**：「加了唯一键之后上界为 0」是结构结论（不是概率结论），可承诺；「TTL 调到 30 min 后不再复发」是概率结论，不可承诺。

> **这一起事故的教训一句话**：同一类故障第二次发生时，你面对的已经不是一个 bug，而是一个**结构缺口**；此时任何参数调整都只是把下一次事故的日期往后推（§53.4 第 10 条）。

## 53.2 定位与唯一真问题

**唯一真问题**：把 53 个组件压成一张可背的表——**什么场景先查哪本账、什么指标出现就该换零件。**

这句话里有两个动词，对应本篇的两半：

- **「先查哪本账」**是**定位**：给一个现场（慢 / 满 / 不一致 / 结果错），在 §53.3 找到对应组件行，看它的「物理形态一句话」，就能推出它一定在哪一本放大账上付钱（→ [01](01-component-anatomy-method.md) §01.3）。
- **「该换零件」**是**决策**：§53.5 给出五类信号的具体阈值，§53.6 给出六类场景的换挡条件。判据只有一条：**当「加机器/加参数」这个动作对指标的一阶导数趋近 0 时，就该换零件了。**

```text
┌──────────────────── 查一张卡的四步 ────────────────────┐
│ ① 现场是什么？ 慢 / 满 / 脑裂 / 假活 / 语义漂移          │
│         │                                                │
│         ▼                                                │
│ ② 查 §53.5 拿到「第一个该看的数」与阈值                   │
│         │                                                │
│         ▼                                                │
│ ③ 查 §53.3 找到组件的「物理形态一句话」                   │
│         │                                                │
│         ▼                                                │
│ ④ 查 §53.7 算它付的是哪本账 → 判断加参数有没有用          │
│         │                                                │
│         └── 一阶导数 ≈ 0 ──► 换零件（§53.6）             │
└──────────────────────────────────────────────────────────┘
```

### 三条主线：把 52 篇的结论压成三条
| 主线 | 一句话 | 用来回答 | 关键锚点 |
| --- | --- | --- | --- |
| **形态决定边界** | 每一个能力上限都是数据物理形态的直接推论 | 「它为什么做不到这件事」——若答案是「物理形态不允许」，就不要试图调参 | [01](01-component-anatomy-method.md) §01.2 / [02](02-storage-engine-three-shapes.md) §02.3 |
| **三本账** | 写放大 / 读放大 / 空间放大不可能同时小；选组件就是选在哪一栏付钱 | 「成本为什么涨」「换完哪本变小、哪本变大」 | [01](01-component-anatomy-method.md) §01.3 / §53.7 |
| **五类失效** | 慢 / 满 / 脑裂 / 假活 / 语义漂移，各有固定的信号与第一动作 | 「这是什么故障」「先动谁」 | 52 篇 §52.3 → §53.8 |

```text
  ① 形态（数据长什么样：页 / 段 / 日志分段 / 槽 / KV cache / granule）
        └─ 决定 ─→ ② 三本账（在哪一栏付钱：写放大 / 读放大 / 空间放大 / 时间账）
                        └─ 决定 ─→ ③ 五类失效（怎么坏、坏得像什么）
                                        └─ 决定 ─→ 换零件信号（"加参数/加机器"的一阶导数 ≈ 0）

  反向用法（这才是评审席上的用法）：
       说不出形态 → 算不出账 → 只能背"最佳实践" → 下一次事故必然同形复发

  五类失效的一句话（细节在 §53.5 / §53.8）：
       · 慢      = 排队沿链放大（L = λW，唯一线性项在谁身上）
       · 满      = 有限资源到顶（水位 / 配额 / 基数 / 连接数）
       · 脑裂    = 两个合法写者（缺 fencing，与锁服务可靠性无关）
       · 假活    = 活着不干活（心跳有、进度无）
       · 语义漂移 = 不报错但结果错（没有指标能测，只能靠对账）
```

三条主线各自的**验收标准**（也就是 §53.10 的判分依据）：

1. **形态主线**：能对着任何一个组件，说出「它不做哪件事，以及为什么不做」——说不出就说明你记住的是配置而不是机制。
2. **账本主线**：能对任何一个变更（改保留期、改副本数、改刷新频率、改索引数）写出**一条乘法链**，并说出哪一项是乘数、哪一项是常数（§53.7 给了每个组件的最坏量级）。
3. **失效主线**：能对任何一个现场说出「第一个该看的数」，且这个数必须在**不查日志**的前提下就能拿到（§53.5 每条都带阈值与前提）。

## 53.3 53 张解剖卡合订

**读表方法**（三句话）：

1. 先在左两列找到组件，读第三列「物理形态一句话」——这是它所有能力的出生证明，也是它所有限制的出生证明。

3. **第五列「第一本账」是这张表的真正用途**：现场变慢/变贵时，先查这一列。第六列是「换掉它的信号」，与 §53.5 的阈值一一对应；**两列的任何一个条件成立，都意味着继续调参的收益已经低于重做的成本。**

## 53.5 换零件信号表：五类失效 × 指标阈值 × 建议动作

这一节是值班时唯一需要打开的表。它按 52 篇的五类失效分组（→ [52 组件故障谱](52-component-failure-map.md) §52.2 总表、§52.3–§52.7 分节），每行给「信号 / 阈值 / 前提 / 第一动作」。**「第一动作」一列已经按「先扩、先修、先换」排序**：凡是写着「换」的，都意味着继续在这个零件上调参，收益的**一阶导数已经接近 0**（§53.2 的判据）。

### 慢（S）· 排队沿链放大

| 信号（指标） | 阈值 | 前提（版本 + 开关） | 第一动作 |

| 任意一层的队列长度持续 > 0 | 5 分钟内均值 > 0 即算 | `L = λW`；指标名与口径必须先确认（ES 是 `thread_pool.write.queue`，MySQL 是 `Innodb_row_lock_current_waits`，Kafka 是 `RequestQueueSize`） | 按「资源层 → 组件层 → 语义层」三段式定位（→ [01](01-component-anatomy-method.md) §01.6），**不要在入口加重试** |
| 单命令 P99 抬升而 QPS 不变 | P99 > 3× 基线 | Redis 7.x 需先开 `latency-monitor-threshold`（默认 0 = 关） | 查 `SLOWLOG` 与大 key；确认是不是单线程被一个 O(N) 占用 |
| fsync P99 | > `1 / 目标 TPS` | MySQL 8.4 且 `innodb_flush_log_at_trx_commit=1`；云盘要看 IOPS 配额而非容量 | 上组提交或换盘；**加 CPU 无效**（[03](03-wal-bufferpool-crash-recovery.md) §03.9） |
| 上游 P99 − 下游 P99 ≈ 上游串行段 | 差值 > 下游总线耗时的 3 倍 | 需 trace 采样率固定 | 找唯一线性项：`分片数 × 每片核时`、`行数 × 每行 µs`、`N × RTT` 三者之一 |
| 每请求尝试数 | > 1.3 | 网关 / 网格任一处有重试配置 | 归一重试到一处，并加预算；429 单独熔断（[50](50-llm-gateway-and-quota.md) §50.6） |
| 活跃流 / 连接上限 | > 70% | gRPC `MAX_CONCURRENT_STREAMS` + 连接级窗口共同决定 | 先分池（按响应大小/区域），再谈加连接（[40](40-rpc-and-connection-reuse.md) §40.6） |

### 满（F）· 有限资源到顶

| 信号（指标） | 阈值 | 前提（版本 + 开关） | 第一动作 |
| --- | --- | --- | --- |
| 盘水位 | > 70% 预警；85 / 90 / 95 三档硬线 | ES 的 `cluster.routing.allocation.disk.watermark.*` 默认 85/90/95；Kafka 无内建水位，要自己算 | **先冻结分配再修容量**：水位触发的 relocation 会自造 IO 风暴（[23](23-es-cluster-shards-replicas.md) §23.8） |
| `checkpoint age / redo capacity` | > 75% | MySQL 8.0.30+ 由 `innodb_redo_log_capacity` 统一管理（旧的 `innodb_log_file_size` 已弃用） | 增容量或降写入速率；**重启刷脏只会让问题晚 5 分钟回来** |
| L0 文件数 / pending compaction bytes | 越过 slowdown 线并持续 2 分钟 | RocksDB / HBase 需打开 `statistics`；HBase 另看 `blockingStoreFiles` | 降写或用 tiered compaction 换空间；先确认「写放大 × 层数」这笔账（[02](02-storage-engine-three-shapes.md) §02.5） |
| active part 数 / mutation 积压 | part > 100；mutation 未完成 > 50 | ClickHouse 24.x `system.parts`、`system.mutations` | 先把写入批量化（part 数 = 写入**批数**），再谈 merge 参数（[20](20-clickhouse-mergetree.md) §20.7） |
| series 数 | > 可用内存 ÷ 2.2 KB | Prometheus 2.x；每 series 2.2 KB 为量级值（1.7–2.6） | 降基数（预聚合 / labeldrop / 折叠），或拉长 interval；**加内存买的是死亡线**（[48](48-observability-backend.md) §48.5） |
| 连接数 | `Pod 数 × 池大小` > 0.8 × `max_connections` | MySQL 8.4 / PG 各自的 `max_connections`、`wait_timeout` | 上连接代理（PgBouncer / ProxySQL）；注意 transaction 模式下会话状态失效（[44](44-connection-pool-and-client.md) §44.9） |
| `History list length` / 表膨胀 | undo 单调涨 30 分钟；PG 膨胀 > 2× | MySQL 8.0 需 `innodb_monitor_enable` 才能看部分 undo 指标；PG 用 `pgstattuple` | 杀长事务或分批提交；**清理 undo 表空间不能治边界**（[06](06-mvcc-and-isolation-levels.md) §06.9） |
| 位点有效期剩余 | < 3× 快照时长 | Debezium / Canal 的 offset 保留；PG 还要看 slot `retained` | 先扩保留窗口，再改位点；位点过期只能重做全量（[33](33-cdc-snapshot-incremental.md) §33.9） |

### 脑裂（B）· 两个合法写者

| 信号（指标） | 阈值 | 前提（版本 + 开关） | 第一动作 |
| --- | --- | --- | --- |
| ISR 与 `min.insync.replicas` 的余量 | 余量 = 0 | Kafka 3.9（KRaft）；`min.insync.replicas` 默认 1，必须显式设 2 | 直接停写而不是等它恢复；`NotEnoughReplicas` 是**保护**不是故障（[29](29-kafka-replication-isr.md) §29.9） |
| `fence_reject_total` > 0 | 任意增量 | 前提是**已经有** fencing token；没有这个指标说明你还没有 L3 | 有僵尸主人：先查它为什么还活着，**禁止自动抢回**（[46](46-distributed-lock-and-leader-election.md) §46.10） |
| cluster state 更新耗时 / master 变更次数 | > 1 s 或 10 分钟内变更 > 2 次 | ES 7.x+ 投票配置自动维护 quorum（`minimum_master_nodes` 已删；8.0 移除 `discovery.zen.*`） | 先停 mapping/模板批量变更（元数据面是全量广播 + 等 ack） |
| 双主写入（两台都能写） | 任一瞬间 > 1 个写者 | MySQL 需 `super_read_only=ON` + 网络层阻断**两层都有**；缺一层就等于没有 | 立刻加只读墙，再排主；切换 RTO 与 RPO 是预案里的两个数（[10](10-replication-and-ha.md) §10.11） |
| quorum 构型 = 2 | 容错 0 | ZK / etcd 集群规模；2 台是最差构型（quorum 也是 2） | 改成 3 或 5，或退回单点（并接受停机） |

### 假活（Z）· 活着不干活

| 信号（指标） | 阈值 | 前提（版本 + 开关） | 第一动作 |
| --- | --- | --- | --- |
| lag > 0 且 10 分钟内速率 = 0，但心跳正常 | 心跳正常 + 进度为 0 | Kafka 3.9 `consumer_group_lag`；不能只看总量，要看**分区 max** | 摘流量重试：副本/实例也在假活时，加副本无效（[30](30-consumer-groups-rebalance.md) §30.12） |
| checkpoint 时长 / timeout | > 0.5 | Flink 1.20；默认 `tolerable-failed-checkpoints=0` ⇒ 一次抖动 = 一次 failover | 先查反压（`inPoolUsage`），再加资源；反压与 checkpoint 共用同一条 channel（[34](34-flink-checkpoint-watermark.md) §34.9） |
| `synced_followers` 掉 + txnlog 水位涨 | 任一 follower 落后 > 30 s | ZooKeeper 3.8/3.9；另配 `autopurge.purgeInterval`（默认 0 = 不清理） | 查 JVM GC 停顿与磁盘；ZK 的 txnlog 会写满盘（[37](37-zookeeper-vs-etcd.md) §37.8） |
| `thread_pool.write.rejected` > 0 | 任意增量 | ES 7.x/8.x；队列买的是 25 秒缓冲，不是吞吐 | 降 bulk 并发或先 `refresh_interval: -1` 灌数；**这就是写侧 SLO**（[25](25-es-capacity-and-failure.md)） |
| 假活从库计入可用副本 | — | Redis 5.0+ `min-replicas-to-write` / `min-replicas-max-lag`，**两个必须成对设** | 成对设置；否则「有几个从库」和「有几个活得从库」不是同一件事（[14](14-persistence-and-replication.md) §14.13） |
| 探针全绿但用户 100% 失败 | — | 入口 / mesh 需要有**端到端合成探针** | 加业务级探针；健康检查只判进程与端口（[39](39-gateway-and-load-balancing.md) §39.10） |

### 语义漂移（D）· 不报错但结果错

| 信号（指标） | 阈值 | 前提（版本 + 开关） | 第一动作 |
| --- | --- | --- | --- |
| 候选取空率 `candidate_short_ratio` | > 5% | 向量库需自己埋点（2.x 各实现字段名不同，以目标版本为准） | 先上对账并降低过滤选择性；**扩容会掩盖漂移**（[27](27-vector-db-engineering.md) §27.9） |
| 业务对账差（产出/输入） | 非 0 且持续 2 个周期 | 需要对账任务本身是幂等的、且覆盖全量键 | 冻结写入路径的变更，从「位点 + 幂等键」两头查（[32](32-task-queue-semantics.md) §32.10） |
| 重复率 `Received ÷ Sent` | > 1.05 | SQS / RabbitMQ / Streams 各自的在途口径不同 | 查可见性超时 vs 处理时长分布，不要先加消费者（[32](32-task-queue-semantics.md) §32.6） |
| 三口径计量差（预扣/结算/账单） | > 1% | LLM 网关；`usage` 字段需供应商原样返回 | 以账单为月度基准、以 `usage` 为单次基准、tokenizer 只做预扣（[50](50-llm-gateway-and-quota.md) §50.7） |
| 同名字段在不同文档里类型不同 | 任一条 | ES `dynamic: true` 下会发生；`dynamic: false` 是静默失败 | 立刻切 `strict`，并对历史数据做类型审计（[25](25-es-capacity-and-failure.md) §25.5） |
| `filtered=100` / `rows` 与实际差 10× | 误差 > 10× | MySQL 8.0 `EXPLAIN` 的 `rows × filtered` 口径 | 刷统计、建直方图；不要先加索引（[09](09-optimizer-and-explain.md) §09.7） |

```text
看到告警，按顺序问五个问题（问到一个「是」就停止，不要往下问）

  ① 有没有「不报错但结果错」的证据？  对账差 / 候选取空 / 重复率 / 计量三口径差
       是 → 语义漂移（D）   第一动作：上对账、冻结变更；禁止扩容
  ② 资源在涨吗？  CPU / 盘 / 内存 / 配额 / series 数
       是 → 满（F）        第一动作：先算乘法链，再删/扩/分层；先冻结自动再平衡
  ③ 队列在涨吗？  L = λW 的任意一层（连接池 / 线程池 / 分区 lag / 网络缓冲）
       是 → 慢（S）        第一动作：找唯一线性项；若「资源平 + 队列涨」⇒ 不可扩，只能换
  ④ 有没有两个写者？  ISR 余量 = 0 / fence 拒绝 / cluster state 抖动 / 双主可写
       是 → 脑裂（B）      第一动作：先加只读墙 + 存储侧 fence 比较
  ⑤ 心跳在、进度为 0？  lag 不降 / checkpoint 卡在 0.5 以上 / synced_followers 掉
       是 → 假活（Z）      第一动作：摘流量重试；别加副本（副本也在假活）
  以上都不是 → 继续观察：为了「做点什么」而改配置，正是本文三起事故的共同起点。
```



三条查询可以直接贴进告警系统（**指标名以目标版本 `/metrics` 输出为准**，Prometheus 2.x + 对应 exporter 的命名在 MySQL 8.4 / Kafka 3.9 / ES 8.x 之间并不统一）：

```promql
# ① 加机器还有用吗：资源平而队列涨 ⇒ ⑤ = 不可扩，只能换
sum(rate(innodb_row_lock_waits_total[5m]))
  / clamp_min(sum(rate(innodb_rows_updated_total[5m])), 1)
# 判据：该比值单调上升且 CPU 不涨 → 是锁/串行度在挡，不是算力不足

# ② 第一本账在谁身上：物理写字节 ÷ 逻辑写字节
sum(rate(node_disk_written_bytes_total{job="db"}[5m]))
  / clamp_min(sum(rate(mysql_global_status_bytes_received[5m])), 1)
# 判据：> 8 说明双写/日志/分裂已经在收租；此时换盘只降分母不动分子

# ③ 有没有「在正常工作但工作错了」：成功响应数 ÷ 业务事实数
sum(rate(http_requests_total{code=~"2.."}[5m]))
  / clamp_min(sum(rate(order_created_total[5m])), 1)
# 判据：偏离基线（不是 1 也没关系，稳定就行）——偏移即漂移，立刻上对账
```

阈值落成告警时，**每组都必须带版本与开关前提**，否则下一个人会照着一条不适用的规则值班：

```yaml

# ES 8.x；指标名与标签以目标版本 /metrics 输出为准，任何一条上线前都要先在测试环境 dry-run）
groups:
  - name: comp53-replace-signal
    rules:
      - alert: CantScaleOutSlower            # 慢：加机器无效 → 该换零件
        expr: rate(innodb_row_lock_waits_total[5m]) > 20
        for: 10m
        labels: { class: "S", action: "垂直切或换形态，不要加副本" }
      - alert: CapacityLedgerBroken          # 满：第一本账已经付不起
        expr: kafka_log_size_bytes / kafka_log_size_max_bytes > 0.80
        for: 30m
        labels: { class: "F", action: "先算 速率×天数×RF×1.15，再决定删/扩/分层" }
      - alert: SplitBrainRisk                # 脑裂：没有 fencing 就不叫切换
        expr: increase(fence_reject_total[5m]) > 0
        labels: { class: "B", action: "查僵尸主人；禁止自动抢回" }
      - alert: FalseAliveConsumer            # 假活：心跳在，进度为 0
        expr: kafka_consumergroup_lag{partition="__max__"} > 1e6
              and rate(kafka_consumergroup_current_offset[10m]) == 0
        for: 10m
        labels: { class: "Z", action: "摘流量重试；副本也在假活时加副本无效" }
      - alert: SemanticDrift                 # 漂移：不报错但结果错
        expr: vector_candidate_short_ratio > 0.05
        for: 15m
        labels: { class: "D", action: "上对账，冻结扩容与索引变更" }
```

## 53.6 选型速查：六类场景「先查哪本账、什么情况下必须换」

每张表只回答两个问题：**① 这个场景打开时，第一本要算的账是什么；② 出现什么条件就必须换零件（而不是调参）。** 「必须换」一列的判据统一为：**这个条件成立后，「加机器 / 加参数」对目标指标的一阶导数 ≈ 0。**

### 存储类

| 场景 | 首选形态 | 先查哪本账 | 什么情况下必须换 |
| --- | --- | --- | --- |
| OLTP 事务 + 强一致 | MySQL 8.4 / InnoDB（→ [05](05-innodb-page-and-row.md)） | **写放大**：`Innodb_data_written ÷ 逻辑写字节`，冷口径含双写可达 5–8× | 单表行数 × 行足迹已让树高 +1 且热数据放不进池；或必须跨地域写（→ 换 NewSQL/分片） |
| 表膨胀敏感、复杂查询多 | PostgreSQL（→ [11](11-postgresql-heap-and-vacuum.md)） | **空间放大**：死元组占比与 freeze 窗口 | freeze 窗口 < 24 h 且无法把 autovacuum 抬上去；或单表 > 数十 TB |
| 热点读缓存 / 会话 | Redis（→ [12](12-redis-single-thread.md)） | **时间账**：单核 `QPS × 单命令 µs` 是否逼近 100% | 单 key 写 > 10 万/s；数据 > 25 GB 且 `latest_fork_usec` > 300 ms；要跨 key 事务 |
| 半结构化文档 | MongoDB（→ [17](17-mongodb-bson-wiredtiger-oplog.md)） | **空间放大**：字段名重复付费 + update chain 与 cache 地板 | 跨文档事务成为常态；`totalDocsExamined/nReturned` > 10 且索引已穷尽 |
| 超宽表 + 强 RowKey 前缀扫 | HBase（→ [18](18-hbase-lsm-region-rowkey.md)） | **写放大**：compaction 4–8× × 副本 3 | RowKey 单调且无法加盐；Region 数 > 1 万且分配吞吐成瓶颈 |
| 需要跨行事务的分布式 KV | TiKV / NewSQL（→ [19](19-rocksdb-and-tikv.md)） | **写放大**：LSM 46× × 3 副本 + raft log ≈ 144× | 单 Region 热点 > 10⁴ QPS（打散也不行）；PD/TSO 成为全库写单点 |
| 分析与宽表聚合 | ClickHouse（→ [20](20-clickhouse-mergetree.md)） | **读放大**：列裁剪收益 vs granule 8,192 放大 | 点查占比 > 20%；需要唯一约束/行级更新/事务——**这三件事它永远做不到** |
| 大对象、日志、备份、湖 | 对象存储 + 表格式（→ [42](42-object-storage-and-cloud-disk.md)、[35](35-iceberg-table-format.md)） | **请求账**：文件数 × 请求单价 × 查询次数（与数据量无关） | 需要 rename / append / 文件锁 / mmap；平均对象 < 1 MB 且被反复读且拒绝合并 |
| 语义检索 / RAG | pgvector（≤ 千万行）或独立向量服务（→ [27](27-vector-db-engineering.md)） | **空间放大**：`N × (4d + 图开销)` × 副本数 | 过滤选择性 < 1% 且无法分区；升级需重建图的机时 > 可接受窗口 |

### 消息类

| 场景 | 首选形态 | 先查哪本账 | 什么情况下必须换 |
| --- | --- | --- | --- |
| 高吞吐日志流、多下游各自回放 | Kafka（→ [28](28-kafka-log-segments.md)） | **空间放大**：`速率 × 天数 × RF × 1.15` | 需要「删一条/改一条/按 key 只留最新」——这是形态禁区，不是调参问题 |
| 事务消息、定档延迟 | RocketMQ（→ [31](31-message-family.md)） | **读放大**：CQ 同页命中率 K 决定 1.0–4.0× | 需要任意精度延迟（4.x 只有 18 档）；多 group 全量回放成为主场景 |
| 存算分离、多租户隔离 | Pulsar（→ [31](31-message-family.md)） | **写放大**：entry + journal 各 3 份 ≈ 6.2× | bookie 慢盘成为 P99 决定项且不可替换；扩容后重分布窗口不可接受 |
| 复杂路由、单条精细 ack | RabbitMQ（→ [31](31-message-family.md)） | **内存账**：1 亿条 ≈ 10 GB 元数据（先撞内存墙） | 单队列持续 > 千级 msg/s；需要长期堆积与回溯 |
| 亚毫秒、轻量扇出 | NATS / JetStream | **时间账**：core 无持久化，JetStream 的 stream 数 = Raft 组数 | 需要分区与历史回放（→ 换 Kafka）；需要严格一次（→ 内核不给） |
| 任务队列 / 后台作业 | SQS 或 Redis Streams（→ [32](32-task-queue-semantics.md)） | **时间账**：可见性超时 vs 处理 P99.9 | 需要 > 12 h 的可见性超时或 > 15 min 的单条延迟；需要「恰好一次」（内核永远不给） |
| 定时 / 延迟触发 | 时间轮 / 延迟队列 / 事务消息回查（→ [36](36-timing-delay-queue.md)） | **时间账**：精度 = 扫描频率 × 实例数 | 需要「到点即执行」（不可能）；需要跨实例严格单次（→ 租约 + fencing + 幂等三层） |

### 检索类

| 场景 | 首选形态 | 先查哪本账 | 什么情况下必须换 |
| --- | --- | --- | --- |
| 全文检索 + 相关性排序 | Lucene / ES（→ [21](21-inverted-index-anatomy.md)） | **空间放大**：posting 1.2 B/doc，开 positions ×2.6 | 需要事务与实时更新（段不可变 ⇒ 只能近实时）；字段类型/analyzer/分片数要改 |
| 精确过滤 + 聚合 | ES 的 filter + doc_values（→ [24](24-es-query-execution.md)） | **读放大**：分片数 × 每片核时 | 分片数无法再降（单分片 > 50 GB）且聚合已成常态负载 |
| 语义召回（带标量过滤） | 向量库（→ [26](26-vector-index-internals.md)、[27](27-vector-db-engineering.md)） | **空间放大**：向量 + 图 + 标量 × 副本 | 召回悬崖无法用 `ef_search` 换回；内存放不下且量化 + rerank 也救不回来 |
| 混合检索（BM25 + 向量） | ES 向量字段 或 双路召回 + 融合 | **读放大**：两路结果的归并倍数 | 两路各自都到瓶颈（一份数据两种索引，成本 2×）——先合并候选再谈换 |

### 协调类

| 场景 | 首选形态 | 先查哪本账 | 什么情况下必须换 |
| --- | --- | --- | --- |
| 选主、分布式锁、小元数据 | etcd（强一致读）或 ZK（→ [37](37-zookeeper-vs-etcd.md)） | **空间放大**：按「写次数 × 保留窗口」算，不按数据量算 | 写入常驻 > 数千 txn/s；keyspace > 数 GB；ZK 的 txnlog 已写满过一次盘 |
| 服务注册（高频写、可丢一点） | Nacos 临时实例（Distro，AP） | **读放大**：通知数 × 回源次数 × 体积 | 订阅边数 > 10 万；推送风暴无法靠合并与去回源解决 |
| 配置管理（低频写、要版本） | Apollo / Nacos 持久实例（CP） | **时间账**：长轮询挂起连接数 | 需要灰度 + 版本 + 一键回滚而当前组件没有 |
| 健康检查判活 | 探针只判进程与端口（→ [38](38-registry-and-config.md)） | **不查账**：失败相关性是集群级的 | 「连续 N 次失败才摘」被当作反雪崩方案时——它挡不住相关故障 |

### 入口类

| 场景 | 首选形态 | 先查哪本账 | 什么情况下必须换 |
| --- | --- | --- | --- |
| 纯四层转发、极高 pps | LVS DR / ECMP（→ [39](39-gateway-and-load-balancing.md)） | **时间账**：调度单位是连接，不是请求 | 需要按 Path/Header 路由、HTTP 语义重试、主动摘除、gRPC 多路复用 |
| 七层路由 + 静态文件 + 简单重试 | Nginx | **时间账**：`proxy_buffering` 与超时链 | 需要动态配置（xDS）、per-request 熔断、按请求灰度 |
| 服务间治理、统一策略 | Envoy + xDS（→ [41](41-service-mesh-and-xds.md)） | **时间账**：两跳串联 + 在途 ×2 + CFS 限流 | 延迟预算 < 1 ms；语言单一、规模小；没人能值班控制面 |
| 东西向 RPC | gRPC(HTTP/2) + 分池（→ [40](40-rpc-and-connection-reuse.md)） | **时间账**：流控窗口 + 队头阻塞 + 重试放大 | 需要持久化/位点/重放（RPC 永远不是队列）；响应大小差异大且无法分池 |

### Agent 栈

| 场景 | 首选形态 | 先查哪本账 | 什么情况下必须换 |
| --- | --- | --- | --- |
| 自托管推理 | vLLM（→ [49](49-inference-engine-vllm.md)） | **空间放大**：KV 池 ÷ 单序列 KV = 并发上限 | 需要多模型路由、长任务持久化、跨卡外推上下文——三件事它一件也不解决 |
| 多供应商 + 配额 + 计费 | LLM 网关（→ [50](50-llm-gateway-and-quota.md)） | **时间账**：`(1+r) × P` 的重试放大 | 需要「保证供应商 SLA」或「替模型推理」——这两件它绝对做不到 |
| 不可信代码执行 | microVM / gVisor（强隔离）或 WASM（高频短任务）（→ [51 执行面](51-execution-sandbox.md)） | **时间账**：冷启动 + 池化复用率 | 既要强隔离又要高复用；浏览器池需要「有状态 + 吃内存 + 会崩」的特殊池化 |
| 凭据签发与轮转 | Vault + KMS 包 DEK（→ [47](47-secrets-and-credentials.md)） | **时间账**：续租尖刺 = 凭据数 ÷ 桶宽 | 续租 QPS 逼近 Vault 写能力；签发 DDL 打爆目标库；KMS 无法缓存 |
| 指标与追踪底座 | Prometheus TSDB + OTel Collector（→ [48](48-observability-backend.md)） | **空间放大**：series × 2.2 KB | series 撞内存；需要长期存储与高基数下钻（→ 换块存储 + 预聚合形态） |
| 会话 / 事件存储 | Redis（热）+ PostgreSQL（冷）| **空间放大**（Redis 2–5×）+ **写放大**（PG 日志） | 会话要跨地域强一致；或单 key 写入超过单核上限 |

## 53.7 三本账合订：各组件最坏量级

三本账的定义式在 [01](01-component-anatomy-method.md) §01.3：`WA = 物理字节 ÷ 逻辑字节`、`RA = 实际触碰页段数 ÷ 最少记录数`、`SA = 物理占用 ÷ 逻辑字节`。下面是 52 篇里出现过的**最坏值**——用它可以做「换零件前的第一轮估算」，误差通常在 3 倍以内（八问的验收标准之一是「能算，误差 < 3 倍」，→ [01](01-component-anatomy-method.md) §01.9）。

### 写放大（你写 1 字节，磁盘实际写多少）

| 组件 | 最坏量级 | 乘法链 | 什么时候会到最坏值 |
| --- | --- | --- | --- |
| InnoDB 单机 | 5–8×（含三份日志） | 页分裂 3.7× × 双写 2 × 日志 2 | 主键随机、填充率 69.3%、每事务 1 行提交 |
| InnoDB 尾插（对照） | 2.0× | 分裂项 → 1.0，只剩双写 × 日志 | 主键单调、K=48、批量提交 |
| RocksDB / HBase（leveled） | 46–57× | `1 + 1 + (L−1)(1+T)`，T=10、L=7 → 68（量级与 46–57 同阶，差在 T 实测值） | 数据量增长（L 涨）；T 由 `max_bytes_for_level_multiplier` 决定 |
| RocksDB tiered（universal） | ≈ 7× | 交换：写放大 57 → 7，空间放大 1.1× → 10× | 你能接受 10 倍空间冗余时 |
| TiKV 端到端 | ≈ 144× | LSM 46× × 3 副本 + raft log | 任何「一次逻辑写」在 NewSQL 上都按这个数买盘带宽 |
| ES（更新为主） | 16× | 更新 = 删 + 写（2×）× merge 层数 4 × 副本 2 | 高频原地更新；用 `_update` 而非整文档覆盖 |
| ClickHouse（mutation） | 与「改了几行」无关 | 触及 part 数 × 受影响列字节 | 频繁 `ALTER UPDATE`/`DELETE`（形态禁区） |
| Iceberg COW | `1 ÷ 命中文件比例` | 稀疏更新时趋近「重写全表」 | 每小时全表更新 1% 的行 |
| Iceberg MOR | 写极小 | 代价搬到读侧 3–5×，且**复利计息** | 长期不跑 `rewrite_data_files` |
| Flink checkpoint | 状态 ÷ 上传带宽 + 对齐等待 | 状态 = key 数 × 每 key × LSM 开销 × 版本数 | 反压时对齐时间主导（此时与状态大小无关） |
| Seata AT `undo_log` | ≈ 4× | 行镜像 × 变更行数 × 事务数 × 保留天数 | 大事务 + 长保留期 |
| Pulsar | ≈ 6.2× | entry 3 份 + journal 3 份 | 每次 ack 都要等 bookie fsync |
| Kafka（复制侧） | RF × 1.15 | 客户端 200 MB/s + 复制 400 MB/s（RF=3）= 3× 网络 | 跨 AZ 时这笔钱按 GB 计价 |

### 读放大（你读 1 行，实际碰了多少页 / 段 / 层）

| 组件 | 最坏量级 | 乘法链 | 什么时候会到最坏值 |
| --- | --- | --- | --- |
| B+ 树二级索引点查 | `2h` 页（h=3 → 6 页） | 索引树 h + 回表 h | 低基数列建索引；命中比例低于 `p* = 1/(R×r)`（R=160、r=4 ⇒ 0.16%） |
| LSM 点查（无 bloom） | 10 个文件（240 GB） | `1 + (max_write_buffer_number−1) + L0 文件数 + (L−1)` | L0 堆积、memtable 数多 |
| LSM 点查（有 bloom） | 1.08 个 block | 假阳性 0.82%（10 bit/key） | bloom 只能挡点查，**挡不住范围扫** |
| 列存点查 | 8,192× | `index_granularity` 一个 granule（默认 8,192 行） | 用列存做点查（形态禁区）；InnoDB 一页只 48 KB 量级 |
| 倒排遍历 | `df × 0.5 ns` | 唯一线性项；df = 3,000 万 → 15 ms | 精确 term + 超大 df；此时位图 AND 反而快 270 倍 |
| ES 查询扇出 | 分片数 × 800 µs | 固定核时，与命中多少无关 | 分片数 5 → 50（QPS 上限掉 10 倍） |
| ES 深分页 | 分片数 × `from` | 归并 `N × (from+size)` 条 | `from+size` 当翻页 API（§53.1 事故一） |
| HNSW 检索 | 候选 ≈ `ef_search × 每点出边` | 层 0 宽度 `ef_search` 的 best-first | 带过滤时图断裂，成本 ≈ `1/s × 基线` |
| Kafka 定位 | ≈ 15 µs | 选段二分 1 µs + 索引二分 2–10 µs + 顺序扫 4 KB | 只能 seek 后顺序推进，**不能随机读** |
| RocketMQ | 1.0–4.0× | 由 ConsumeQueue 同页内本队列消息数 K 决定 | topic 数多、单 topic 流量小 |
| 对象存储（湖表规划） | 文件数 × 30 ms | 打开罚与请求计费都与**数据量无关** | 小文件 + 高频提交 |
| 注册中心推送 | 通知数 × 回源次数 × 体积 | 通知:正文 ≈ 1:200 | 分散型变更（合并率 < 5%）+ 客户端回源 |

### 空间放大（逻辑 1 GB，占盘 / 占显存多少）

| 组件 | 最坏量级 | 乘法链 | 什么时候会到最坏值 |
| --- | --- | --- | --- |
| InnoDB undo（MVCC） | 28.8 GB / 半小时 | 更新行/s × 每行 undo 字节 × 时长（2 万行/s × 1,800 s × 800 B ≈ 28.8 GB） | 长事务 + 高更新率；只读事务一样钉住 purge |
| PostgreSQL 表膨胀 | 4.3×（30 天不 VACUUM） | 日更 10% × 300 B × 1 亿行 = 3.3 GB/天 | `idle in transaction`、prepared xact、复制槽四颗钉子 |
| LSM 空间放大 | 1.1×（leveled）/ 10×（tiered） | tiered 用空间换写放大 | 选 universal 且不做 FIFO 淘汰 |
| 副本数 | 3.0× | 三副本；RS(10,4) 可到 1.4× | 副本是第一个乘数，EC 是唯一能拆它的手段 |
| Redis 编码开销 | 2–5× | dictEntry + key SDS + robj + value SDS（容器再乘一份指针） | 大量小 key / 短 TTL / 容器跨阈值后不回退 |
| ES 段与删除 | 段元数据 ≈ 1 KB + 字段数 × 30 B / 段 | 10 万段 × 3,000 字段 ⇒ 29% 堆 | 段数 > 300/分片；删除率 > 30% |
| HBase 端到端 | 36–45×（major 峰值 53×） | 逻辑 10 TB → 写入放大 × 三副本 × 版本数 | 版本数 > 1、TTL 未设、major 未调 |
| KV cache（推理） | 200 GiB | 并发 × 序列长 × 每 token KV（7B MHA/fp16 = 512 KiB）→ `100 × 4,096 × 0.5 MiB` | `max_model_len` 设得比真实用到的长 4–8 倍 |
| 向量索引 | `N × (4d + 150~400 B) × 1.10` × 副本 | 1 亿 × 768 ≈ 346 GB → 2 副本 797 GB | 不量化；量化必须配 rerank 与两条召回曲线 |
| BSON 字段名 | 10.8 GB（1 亿文档 × 12 字段 × 9 B） | 每字段 `1 + len(name) + 1` B；数组里每个元素重复一遍 | 长字段名 + 深嵌套 + 大数组 |
| TSDB series | 每 series ≈ 2.2 KB | 可承载 ≈ 可用内存 ÷ 2.2 KB；interval ÷3 ⇒ 内存 ×3 | 毒标签（`pod_name`/`user_id`/`path`）进 schema |
| 注册中心 txnlog | 1.17 TB（300 txn/s × 180 天） | 写次数 × 保留窗口（不是数据量） | `autopurge.purgeInterval` 留默认 0 |

把上面三张表落成一个可跑的复算器——**换任何假设都能立刻重算**，这是本篇对「数字纪律」的最终交付（→ [0-summary.md](0-summary.md) §0.7 第 1、8 条）：

```python
# comp53 §53.7 · 三本账复算器（01 篇定义式 → 可跑的乘法链）
# 全部为「量级结论」，不是承诺值；系数取自 01–52 各篇，换假设即可复算
def wa_lsm(T=10, L=7):            # 写放大：1 + 1 + (L-1)(1+T)  ≈ T×L
    return 1 + 1 + (L - 1) * (1 + T)

def wa_btree(R=48, dw=2, log=2):  # 写放大：分裂项 (R/2 次插入写 3 页) × 双写 × 日志
    return (1 + 3 / (R / 2)) * dw * log

def ra_secondary(h=3):            # 读放大：二级索引 = h 页索引 + h 页回表
    return 2 * h

def ra_column(granule=8192):      # 读放大：列存点查至少读一整个 granule
    return granule

def sa_undo(rows_per_s=20000, bytes_per_row=800, minutes=30):
    return rows_per_s * bytes_per_row * minutes * 60 / 1e9     # GB（十进）

def sa_kv_cache(conc=100, seq=4096, kib_per_token=512):
    return conc * seq * kib_per_token / 2**20                  # GiB

def sa_kafka(mb_per_s=62.4, days=7, rf=3, factor=1.15):
    return mb_per_s * 86400 * days * rf * factor / 1e6         # TB（十进）

# 默认假设下的一行结果（可直接贴进评审记录）
print(f"LSM 写放大      T=10,L=7 : {wa_lsm():.0f}x      (≈ T×L = 70)")
print(f"B+ 树写放大     R=48     : {wa_btree():.1f}x")
print(f"二级索引点查    h=3      : {ra_secondary():.0f} 页")
print(f"列存点查读放大           : {ra_column():.0f}x")
print(f"undo 半小时    2万行/s   : {sa_undo():.1f} GB")
print(f"KV cache 100并发 4K      : {sa_kv_cache():.0f} GiB")
print(f"Kafka 盘占用   7天 RF=3  : {sa_kafka():.0f} TB")
```

## 53.8 五类失效合订：信号 → 第一动作

这一节与 52 篇直接呼应：[52 组件故障谱](52-component-failure-map.md) §52.2–§52.7 讲「怎么认」、§52.9 给出兜底招式的**次序**（限流 > 隔离 > 降级 > 扩容 > 重启），本节只补一件它没重复的事——**每一类的触发条件与「此刻不该做什么」**。**原则只有一条：先做「让损失停止增长」的动作，再做「让系统恢复健康」的动作，最后才做「让它下次不再犯」的动作**——三者顺序反过来，就是本文开头三起事故的共同形状。

| 类 | 一句话判据（30 秒内可判） | 关键信号（可抄进告警） | 第一动作 | 此刻**不该**做什么 |
| --- | --- | --- | --- | --- |
| **慢** | 资源平而队列涨 → 有锁或单线程在挡 | 任意层 `queue > 0`；单命令 P99 > 3× 基线；fsync P99 > `1/TPS` | 找**唯一线性项**（`分片数 × 每片核时` / `行数 × 每行 µs` / `N × RTT`），把它移出热路径 | 加重试、加副本、加连接（三者都在给唯一的线性项乘系数） |
| **满** | 某个有限资源到顶，且水位不是"看起来还有" | 盘 85/90/95；`checkpoint age/capacity` > 75%；active part > 100；series > 内存/2.2 KB | 先算**乘法链**（速率 × 天数 × RF × 系数），决定删 / 扩 / 分层三选一，并**先冻结自动再平衡** | 直接扩容（会触发 relocation 自造 IO 风暴）；调大限额（只是把墙后移） |
| **脑裂** | 存在两个自认为合法的写者 | ISR 余量 = 0；`fence_reject_total` > 0；cluster state 更新 > 1 s；双主可写 | 先加**只读墙**（`super_read_only` + 网络阻断 + 存储侧 fence 比较），再排主 | 自动抢回、自动 `unclean` 选举、相信「锁服务可靠」 |
| **假活** | 心跳在、进度为 0 | lag > 0 且 10 分钟速率 0；checkpoint 卡在 0.5 以上；`synced_followers` 掉；`write.rejected` > 0 | 摘流量重试，让健康实例接管；**同时确认"健康"的定义是业务吞吐而不是心跳** | 加副本（副本也可能在假活）；调大超时（只让发现变慢） |
| **语义漂移** | 不报错，但对账对不上 | 候选取空率 > 5%；产出/输入 ≠ 基线；重复率 > 1.05；三口径计量差 > 1% | 立刻上**对账**（幂等、覆盖全量键、按周期跑），并冻结写入路径的一切变更 | 扩容（会稀释证据）、改参数（会让下一次更难复现） |

```go
// comp53 §53.8 · 第一动作判定：把「信号 → 第一动作」落成可灰度上线的决策函数
// 前提：五类信号由 48 篇的指标体系提供；本函数只决定「先动谁」，不替代根因分析
type Signal struct {
	Kind      string  // "慢" | "满" | "脑裂" | "假活" | "语义漂移"
	Value     float64
	Threshold float64
	AgeMin    int // 持续时长：所有阈值都必须带「持续」条件，否则会被尖刺误导
}

// priority 越小越先动：脑裂会污染数据，漂移会让证据消失，两者都必须在扩容之前处理
var priority = map[string]int{"脑裂": 0, "语义漂移": 1, "满": 2, "假活": 3, "慢": 4}

var action = map[string]string{
	"脑裂":   "先加只读墙 + 存储侧 fence 比较，禁止自动抢回",
	"语义漂移": "先上对账并冻结变更，禁止扩容",
	"满":    "先算乘法链再删/扩/分层，先冻结自动再平衡",
	"假活":   "摘流量重试，别加副本",
	"慢":    "找唯一线性项；资源平而队列涨则判定「不可扩，只能换」",
}

func FirstAction(sigs []Signal) string {
	best, hit := 99, false
	for _, s := range sigs {
		if s.Value <= s.Threshold || s.AgeMin < 5 {
			continue
		}
		if p, ok := priority[s.Kind]; ok && p < best {
			best, hit = p, true
		}
	}
	if !hit {
		return "无类别越线：继续观察，禁止为了「做点什么」而改配置"
	}
	for k, p := range priority {
		if p == best {
			return action[k]
		}
	}
	return "unknown"
}
```

```text
┌───《存储与中间件剖析》· 20 条收口卡──────────────────────────────────────────────┐
│ 1 形态是一切的出生证明：说不出「一条记录落在哪几个字节区间」，其余七问只能靠背。 │
│ 2 三本账不可能同时小；选组件不是选更好的，是选在哪一栏付钱。                     │
│ 3 第⑤问只有四个答案：分片 / 副本 / 垂直切 / 批处理摊薄；都不成立就写「只能换」。 │
│ 4 「快」永远是从另一栏借的：LSM 借空间与读放大，列存借更新，对象存储借语义。     │
│ 5 一次提交三份日志；「返回 OK 就不丢」只在 flush=1 且 sync_binlog=1 那一格成立。 │
│ 6 恢复的瓶颈是随机页 IOPS，不是 redo 大小；池越大 → redo 越大 → 重启越慢。       │
│ 7 可重复读是给你旧版本视图，不是锁；快照活多久决定 undo 涨多快。                 │
│ 8 锁加在索引上；只有「唯一索引全列等值命中」才是 1 行锁，其余都可能锁一段区间。  │
│ 9 索引失效多是优化器算全扫更便宜；全扫 87–96% 在 CPU，换盘救不了。               │
│ 10 复制延迟是并行回放度与大事务；Seconds_Behind_Master 会撒谎。                  │
│ 11 PG 怕表胀、InnoDB 怕 undo 胀——两者都怕长事务，选哪边都是运维负债。            │
│ 12 Redis 快在内存 + 无锁 + 批处理；一个 O(N) 命令停掉所有人，阈值是单向门。      │
│ 13 段不可变是 ES 的宪法：更新 = 删 + 写；分片数定错只能重建。                    │
│ 14 别名是唯一的切流开关：回滚 = 改一次指针 = 1 秒；代码里出现物理索引名即违规。  │
│ 15 ANN 是用正确率换延迟的合约；带过滤的 ANN 才是真难点，选择性决定策略且改不动。 │
│ 16 Kafka 快是因为「不做」；删除的最小单位是段，保留窗口是乘法不是加法。          │
│ 17 「不丢」是四个参数的一次联署；unclean 选举签的是业务的风险额度。              │
│ 18 rebalance 是协议成本，位点提交时机就是语义，积压是并行度算术（min(C,P)）。    │
│ 19 定时不是到点执行，是到点能被发现；协调组件的通知是事件不是状态。              │
│ 20 锁的安全不在锁服务，在旧主人能不能被挡住；凭据的价值在它多久会自己死。        │
└──────────────────────────────────────────────────────────────────────────────────┘
```

## 结语

> **收口**：这套书的全部结论可以压成一句话——**读懂组件的物理形态，你就同时读懂了它为什么快、它为什么做不到、以及它什么时候必须被换掉**。前 52 篇在证明这半句话；本篇在教你怎么在 10 分钟内把它用出来。第 53 张卡（本篇自己）的唯一用途是：**下次评审时，你能指着表说「这一栏的账已经付不起了，换零件」，而不是说「感觉这样更好」。**
