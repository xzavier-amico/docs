## 15.1 引子：三起「只挂一个分片，全站写不进」的故障

单机 Redis 的故障是「一个实例慢下来」；Cluster 的故障是「一个分片的坏消息扩散成整个集群的坏消息」。三起事故分别对应本篇三条主线：**槽不可用 → 集群不可用（§15.7）**、**迁移阻塞（§15.8 账二）**、**跨槽多 key 被应用层用 N 次单 key 绕过（§15.6）**。

### 事故一：一台宿主机掉盘，全站下单 100% 失败 11 分钟（2026-04-08）

`order-cache`：3 主 3 从共 6 个 `redis-server` 进程，部署在 3 台虚拟机上。反亲和做错了——`vm-1` 上跑 `master-1` 与 `replica-3`，`vm-2` 上跑 `master-2` 与 `replica-1`，`vm-3` 上跑 `master-3` 与 `replica-2`。`cluster-require-full-coverage` 是默认的 `yes`。

| 时间 | 事件 | 可用槽 / 下单成功率 |
| --- | --- | --- |
| 20:41:07 | `vm-2` 的存储阵列掉盘，其上 `master-2` 与 `replica-1` 同时失联 | 16384 / 16384，100% |
| 20:41:22 | `master-1`、`master-3` 各自把 `master-2` 记为 PFAIL 并在 gossip 里扩散，多数主节点达成一致 → **FAIL** | 10923 / 16384，**成功率先塌到 0** |
| 20:41:23 | 所有客户端收到 `CLUSTERDOWN The cluster is down`——**不是只有那 5461 个槽的请求失败** | 0% |
| 20:44 | 值班按「Redis 挂了」重启两个存活节点（无效，集群状态由槽覆盖率决定，重启不能变出槽） | 0% |
| 20:52 | DBA 逐节点 `CONFIG SET cluster-require-full-coverage no` | 约 67% 的 key 能命中 |
| 20:52–21:30 | 未命中的 1/3 流量打到 MySQL，QPS 4,200 → 27,000，连接池打满，接口大面积 5xx | 部分失败 |
| 复盘 | 11 分钟下单 100% 失败（4.1 万单），之后 38 分钟部分失败；GMV 损失约 620 万元 | — |

根因不是「Redis 不抗故障」，而是**「槽不可用」这个局部事实被一个默认参数放大成了「集群不可用」这个全局事实**：`cluster-require-full-coverage yes` 的含义是「16384 个槽必须全部有人服务，否则拒绝一切请求（含读）」。正确做法是先在架构上把「一槽不可用」的爆炸半径限制住——主从反亲和、`cluster-require-full-coverage no` 加业务降级、副本与主不在同一故障域——而不是出事时去改参数。这与「集群按分片切开后，任何一个分片的失败半径应该是 1/3，而不是 100%」的直觉正好相反，§15.7 专门算这笔账。

### 事故二：双十一前扩容，一个大 key 让一个分片卡 4.3 秒，订单超时 8.1 万笔（2026-10-31）

大促前把 3 主扩到 4 主，特意选了 02:10（「低峰」），跑 `redis-cli --cluster reshard`。

| 时间 | 事件 | 该分片 ops/s |
| --- | --- | --- |
| 02:10 | 扩容开始，4,096 槽待迁 | 12 万 |
| 02:11–02:22 | 平稳迁完 3,920 槽，每槽 200–800 个 key | 11.8 万 |
| 02:23:14 | 迁到第 3,921 槽，遇到 `feature:{all}:vectors`——一个 480 MB、约 380 万 field 的 hash | 12 万 |
| 02:23:14 → 02:23:18.4 | 源端主线程在 `MIGRATE` 内部**阻塞 4.3 秒**（序列化 + 传输 + 等目标端 `RESTORE-ASKING` 回 OK） | **0** |
| 02:23:14.8 | 订单服务 300 ms 超时，开始 3 次重试；排队请求从 12 万（1 秒的量）涨到 40 万以上 | 0 |
| 02:23:18.4 | `MIGRATE` 返回 OK，积压命令 2 秒内排空 | 12 万 |
| 复盘 | 4.3 s 内经过该分片的请求全部超时，**8.1 万笔订单失败**，损失约 210 万元；随后压测基线全部失真 | — |

4.3 秒不是巧合：`480 MB × 8 ÷ 1,000 = 3.84 s`（1 Gbps 传输）+ 序列化约 0.3 s + 目标端重建约 0.2 s。**其中任何一项都发生在某一台机器的唯一执行线程上**（源端是序列化与等待，目标端是 `RESTORE` 的重建）。也就是说：**「低峰」只降低了受害请求的绝对数量，没有降低阻塞时长本身**；一个 480 MB 的 key 走到哪，哪就停 4 秒。

### 事故三：`MGET` 报 CROSSSLOT，改成 200 次单 key `GET`，P99 从 12 ms 到 210 ms 且五天没人发现（2026-06-17）

商品详情聚合接口原来一次 `MGET` 取 200 个 key（详情、价格、库存、标签、推荐位……）。分片上线后 `MGET` 直接报 `CROSSSLOT Keys in request don't hash to the same slot`。改动只有一行：把 `MGET k1..k200` 换成 `for` 循环 200 次 `GET`——理由是「不想动 key 设计」。

| 时间 | 事件 | 接口 P99 / Redis 侧信号 |
| --- | --- | --- |
| 06-17 发布 | 1 次 `MGET` → 200 次串行 `GET`；该接口 400 QPS × 200 = **8 万 QPS 增量** | 12 ms |
| 06-17 12:00 | 200 × (RTT 0.9 ms + 执行 0.05 ms + 客户端分派 0.1 ms) ≈ **210 ms** | Redis CPU、连接数、命中率**全部正常** |
| 06-17 → 06-22 | 监控只盯着 Redis 的分命令耗时（`GET` 仍是 1.5 μs），没人看这个接口 | 无告警 |
| 06-22 压测 | 发现 P99 已经 210 ms；改成 `{detail:12345}:*` hash tag + 一次 `HMGET` | 14 ms |
| 复盘 | 5 天，P99 慢 17 倍，转化率掉 1.9 个百分点；**根因不是 Redis 慢，是 200 次往返换 1 次** | — |

## 15.2 一句话定位与唯一真问题

**定位**：Redis Cluster 是**「客户端驱动的槽分片 + 每槽主从 + gossip 心跳」**。它对外承诺的是：**单个 key 的读写被路由到唯一一个主节点，并在主节点故障后由副本接替**；它不承诺跨槽多 key 原子、不承诺切主不丢（异步复制）、不承诺「部分槽不可用时其余槽仍可用」（默认配置下恰好相反）。它甚至不提供真正的服务端路由——**重定向是服务端给客户端的「你自己去找」**，客户端必须自己维护槽表。缓存失效语义与热点治理仍属 `architect/04`。

### 唯一真问题

> **Cluster 只解决分片，不解决一致性——它把「一个 Redis」变成「16384 个槽的主从组」，于是你换来的每一点容量，都用「多 key 操作失效 + 槽迁移期间的重定向与停等」来支付。**

这句话有三截，全篇都在展开它们：

1. **「只解决分片」**：分片单位是槽，槽的归属由 `CRC16(key) mod 16384` 决定，而这个映射是**写死在客户端与所有节点上的常量**。于是任何「多个 key 必须一起原子」的语义，都必须先解决「它们在同一个槽吗」。
2. **「不解决一致性」**：每个槽是独立的主从组，复制异步、故障判定靠多数派心跳。跨槽不存在任何事务边界，切主窗口内旧主仍可接受写（脑裂）。Cluster 的一致性天花板 = 单槽主从的一致性天花板，而后者已经是「异步复制、可能丢 1 s」。
3. **「用重定向与停等支付」**：迁移一个槽就是把它的 key 一个一个 `MIGRATE` 出去，而 `MIGRATE` 是**同步阻塞命令**（`→ comp/12` §12.6）。迁移期间「源端有」的 key 本地执行、「源端已无」的 key 回 `ASK`、多 key 命令可能被 `TRYAGAIN` 打回——**每一次重定向都是客户端的一次额外往返，每一次失败重试都可能是 QPS 的放大器**。

### 八问卡（Cluster 版，密度对齐 `01-component-anatomy-method.md` §01.4）

| 问 | 一句话答案 | 数字 / 边界 |
| --- | --- | --- |
| ① 承诺 | 单 key 被路由到唯一主节点；主节点故障由副本接替 | 不承诺跨槽原子、不承诺切主不丢、默认不承诺「部分槽坏了其余可用」 |
| ② 数据 | 键空间被 `CRC16(key) & 0x3FFF` 切成 16384 份，槽是分配与迁移的最小单位 | 源码常量 `CLUSTER_SLOTS = 16384`；心跳里用 2048 B bitmap 表示归属（§15.3） |
| ③ 链路 | 客户端查本地槽表 → 直连主节点；错则服务端回 `MOVED`/`ASK` | 命中槽表时与单机一致；一次重定向 = +1 次 RTT（0.2–1 ms） |
| ④ 并发与一致 | 每槽一个主从组，复制异步，故障靠多数派主节点判 FAIL | 丢数据窗口 = 异步复制延迟（同机架常 1–50 ms，`→ comp/14`） |
| ⑤ 扩展维度 | **分片**（主答案）+ 副本（只扩读与可用性）+ 垂直切（按用途拆集群）+ 批处理摊薄 | 写容量 ∝ 主节点数；单 key 写仍受单核限制（`→ comp/12`） |
| ⑥ 会在哪崩 | 满 → 单节点先满（倾斜）；慢 → 迁移阻塞与重定向风暴；脑裂 → 分区两侧各有主 | 见 §15.7、§15.8 |
| ⑦ 指标 | `cluster_state`、`cluster_slots_assigned`、`total_error_replies` 里的重定向计数、节点内存倾斜、`LATENCY HISTORY command` | 每条带版本与开关，见 §15.11 |
| ⑧ 换掉它的信号 | 需要跨槽多 key 原子；单 key 写 > 10 万/s；槽布局频繁变（频繁 reshard） | 见 §15.9 换挡表 |

## 15.3 物理形态：16384 个槽与心跳里的 bitmap

Cluster 里没有「分片表文件」，也没有中心元数据服务。**槽的归属是一份每个节点自己维护的 bitmap，靠每秒都在发的 PING/PONG 交叉确认**。理解这一点，才能理解后面所有结论：为什么迁移要给两端都发命令、为什么交接完成后要等 gossip 传播、为什么客户端会被允许「拿着过期的槽表」继续发请求。

```text
一次 PING/PONG 报文（cluster.h 的 clusterMsg）里，决定「谁拥有哪个槽」的就是这一块
                                                     源码常量 CLUSTER_SLOTS = 16384
┌──────────────────────────────────────────────────────────────────────────────┐
│ 固定头：sig / totlen / type / count / currentEpoch / configEpoch / port …     │
├──────────────────────────────────────────────────────────────────────────────┤
│ myslots[CLUSTER_SLOTS / 8]  =  16384 bit = 2048 B   ← 一个节点「自称」的槽位图 │
│                                                                              │
│  slot#:   0                5461              10923               16383       │
│           ├─────────────────┼──────────────────┼──────────────────┤          │
│  node A:  ██████████████████░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░          │
│  node B:  ░░░░░░░░░░░░░░░░░░██████████████████░░░░░░░░░░░░░░░░░░░░░          │
│  node C:  ░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░██████████████████████          │
│                                                                              │
│  取位方式：myslots[slot >> 3] & (1 << (slot & 7))                             │
│            16384 = 2^14，于是「槽号 → 字节/位」是两次移位，没有除法          │
├──────────────────────────────────────────────────────────────────────────────┤
│ gossip 段：若干条其他节点的 node id / ip / port / flags / ping / pong 时间     │
│            条数随集群规模自适应——不是全量广播，否则 O(N²) 心跳               │
└──────────────────────────────────────────────────────────────────────────────┘
```

### 键 → 槽：`CRC16(key) mod 16384`

一次请求落到哪个槽，只有这一个公式：`slot = CRC16(<hash tag 或整个 key>) & 0x3FFF`（16384 = 2^14，所以 `mod 16384` 等价于按位与）。

三件事必须记牢：

1. **用的不是 MD5/SHA，是 CRC16**（XMODEM 变体）。它足够快（几十纳秒），分布够均匀，但**没有抗碰撞能力**——所以槽的负载均衡永远是「概率意义上的均匀」，不是「保证均匀」。16384 个槽对 3 主 3 从来说每主 5461 槽，但**每槽的 key 数量可以差几个数量级**，这就是 §15.8 里「倾斜」的物理来源。
2. **`CLUSTER KEYSLOT key` 在任何节点上都能算**，因为这是一个纯函数。所以「这个 key 在哪个槽」不需要查表，只有「这个槽归谁」才需要查表。
3. **槽表是客户端持有的**。Redis Cluster 不做代理，客户端第一次连接时用 `CLUSTER SLOTS`（7.0+ 起也可用 `CLUSTER SHARDS`）拉一份「槽区间 → 节点」的映射并缓存在本地；此后直连主节点，只在收到 `MOVED` 时才更新。

### 为什么是 16384，不是 65536

这是评审最爱问的一句，答案不在「哈希均匀性」上（16384 已经足够均匀），而在**心跳报文里那张 bitmap 的大小**：

| 项 | 16384 槽 | 65536 槽 |
| --- | --- | --- |
| bitmap 大小（`CLUSTER_SLOTS / 8`） | **2 KB** | **8 KB** |
| 100 节点集群、节点间每秒一次 PING 的接收量 | 约 `100 × 2 KB = 200 KB/s` | 约 `100 × 8 KB = 800 KB/s` |
| 3 主 3 从（6 节点） | 约 12 KB/s | 约 48 KB/s |
| 全网心跳带宽（100 节点两两互发量级） | 20 MB/s 量级 | **80 MB/s 量级** |
| 每个节点保存「每个已知节点的槽位图」的内存 | 2 KB × N | 8 KB × N |
| 能支撑的集群规模上限 | 1,000 个主节点的量级已足够 | 收益只在「超过 1,000 主」时才出现 |

结论是一条很实的工程交易：**bitmap 是心跳的固定开销，而心跳每秒都在发、且和业务 QPS 无关**。16384 已经能支撑到 1,000 个主节点这一量级（远超绝大多数集群的实际规模），再往上加只会让每个节点每秒多收发几倍的心跳字节，换来的只是「槽更细一点、迁移更平滑一点」。65536 位 = 8 KB 的代价是**每节点每秒多几百 KB 的纯运维流量**，这笔钱买不到任何业务收益。

顺带一个副作用值得记住：**槽越粗，「重平衡」时一次动的数据越多**。16384 槽 / 100 节点 ≈ 164 槽每节点，单次迁移粒度就是「164 槽的 keyspace」；如果有人把槽数当成「可以随便调的旋钮」，那他已经误解了这个常量——它是协议常量，改它等于换一个不兼容的集群实现。

### `hash tag {…}`：把多 key 钉在同一个槽

规则很短：key 里**第一个 `{` 与它后面第一个 `}` 之间若有内容，则只用这段内容算 CRC16**；否则用整个 key。

| key | 参与哈希的部分 | 槽 |
| --- | --- | --- |
| `user:1000:name` | `user:1000:name` | CRC16(整个 key) |
| `{user:1000}:name` | `user:1000` | 与下一行**同槽** |
| `{user:1000}:cart` | `user:1000` | 与上一行**同槽** |
| `{}:name` | 整个 key（花括号内为空 → 退回整 key） | 与 `user:1000:name` 无关 |
| `order{{x}}:1` | `{x`（第一个 `{` 到其后第一个 `}` 之间） | 反例：嵌套写法会给出反直觉的 tag |

`hash tag` 是 Cluster 下「多 key 操作」的**唯一**服务端解法（§15.6），它没有替代品：要想 `MGET`/`MULTI`/Lua 一次用多个 key，它们必须同槽；要同槽，就得有一个共同的 tag。代价也在同一处：**同 tag 的所有 key 永远住在一个主节点的一个线程上**——`{order}` 当 tag，全站订单就落进一个槽（§15.10 有真实形态）。

## 15.4 一次请求的四种结局：本地、MOVED、ASK、TRYAGAIN

Cluster 的重定向不是「路由」，而是**服务端对客户端的拒绝 + 指路**。一次请求的结局只有五种：**本地执行**（唯一正常的一种），以及 `MOVED`、`ASK`、`TRYAGAIN`、`CLUSTERDOWN` 四种「你必须自己处理」的回复——本节标题里的「四种结局」指的就是后四种。前一种是常态，后四种处理不当，构成了本篇一半的事故。

| 结局 | 服务端什么时候回 | 客户端必须做什么 | 重试不当会怎样 |
| --- | --- | --- | --- |
| **本地执行** | 槽归自己，且（若 MIGRATING）key 仍在本地；或（若 IMPORTING）已收到 `ASKING` | 无 | — |
| **`MOVED <slot> <host:port>`** | 槽的归属已不在本节点（含「迁移交接完成」之后的一切请求）。**永久性** | 更新本地槽表中**该槽**的归属，然后重试一次（多 key 要多槽一起更新） | 只重试不更新槽表 → 每次请求都多一次往返；永不更新 → 无限重试 |
| **`ASK <slot> <host:port>`** | 本节点正 MIGRATING 该槽，且**该 key 已不在本地**。**临时性：只对这一个 key 有效** | 向目标节点先发 `ASKING`，**再发原命令，且必须同一条连接**；**不要**改槽表 | 省掉 `ASKING` → 目标节点回 `MOVED` 指回源端 → 两端互指的死循环（见下图） |
| **`TRYAGAIN`** | 多 key 命令撞上迁移：一部分 key 还在源端、一部分已迁到目标端 | 等待极短时间（毫秒级）后重试同一条命令 | 立即重试 → 撞上的还是同一批在途 key；重试无上限 → QPS 放大 |
| **`CLUSTERDOWN …`** | `cluster_state:fail`（有槽无人服务，且 `cluster-require-full-coverage yes`），或某槽确实无人服务 | 不重试，快速失败并降级；重试只会把不可用放大成容量问题 | 每层都重试 → 故障期间 QPS 变成原来的 3–10 倍，恢复瞬间反被打爆 |

```text
                      客户端本地槽表：slot 3999 → node A
                                  │
                     GET {user:1}:cart   （CRC16 → slot 3999）
                                  ▼
                   ┌──────────────────────────────────┐
                   │ node A：槽 3999 的当前归属者       │
                   └──────────────────────────────────┘
                        │                              │
     槽正常（含 key 还在 A 上）        槽在 MIGRATING，且这个 key 已迁到 B
                        │                              │
                        ▼                              ▼
                  本地执行               ┌───────────────────────────────────────┐
                  （零重定向）            │ -ASK 3999 10.0.0.12:6379              │ ← 临时
                                         │ -MOVED 3999 10.0.0.12:6379            │ ← 永久
                                         └───────────────────────────────────────┘
                                                       │
                        ASK 的正确姿势（不刷槽表）        │
              ┌────────────────────────────────────────┴──────────────┐
              │  C → B:  ASKING                                         │
              │  C → B:  GET {user:1}:cart     ← 必须同一条连接、紧邻    │
              │  B → C:  "…"                                            │
              └────────────────────────────────────────────────────────┘
                                                       │
                        省掉 ASKING 的后果：重定向循环      │
              ┌────────────────────────────────────────┴──────────────┐
              │  C ──GET──► A ──ASK──► C ──GET(无 ASKING)──► B          │
              │  B ──MOVED──► C ──GET──► A ──ASK──► …                   │
              │  每绕一圈 = 1 次 RTT + 1 条错误回复；只有重试上限能停它   │
              └────────────────────────────────────────────────────────┘
```

**`MOVED` 与 `ASK` 的区别值得单独背下来**：`MOVED` 说的是「**槽**已经换主人了，你以后都去那边」（永久、可缓存、可批量更新槽表）；`ASK` 说的是「**这个 key** 已经在路上了，这次去那边，但槽还没换主人，你不许改表」（临时、一次性、必须配 `ASKING`）。把 `ASK` 当 `MOVED` 处理，客户端会把一个「迁移中的临时状态」写成永久槽表，随后每个请求都被新主人用 `MOVED` 打回——**这就是「槽表缓存过期 + 重定向循环把 QPS 放大 3 倍」的具体机制**（§15.8 账三）。

### 客户端骨架：槽表 + 重定向 + 重试上限

```go
// 只演示「槽表 + 重定向」这一层。生产用 go-redis / lettuce，它们内部就是这段逻辑
type slotTable struct {
	mu    sync.RWMutex
	owner map[uint16]string // slot → "host:port"
}

func slot(key string) uint16 { return crc16.Hash(hashTag(key)) & 0x3FFF } // 16384 = 2^14

const maxRedirect = 3 // 上限必须有：没有上限的重定向就是无限循环

func (t *slotTable) do(ctx context.Context, key string, cmd func(addr string, asking bool) error) error {
	addr, asking := t.pick(slot(key)), false
	for i := 0; i < maxRedirect; i++ {
		err := cmd(addr, asking) // asking=true 时必须与命令走同一条连接（在池里绑定）
		switch kind(err) {
		case moved: // 永久：更新该槽归属后重试
			addr, asking = redirectAddr(err), false
			t.set(slot(key), addr)
		case ask: // 临时：不改槽表，下一次先发 ASKING
			addr, asking = redirectAddr(err), true
		case tryAgain: // 迁移中多 key 冲突：毫秒级退避
			time.Sleep(time.Duration(i+1) * 2 * time.Millisecond)
		case clusterDown: // 不重试：快速失败，交给上层降级
			return err
		default:
			return err
		}
	}
	return fmt.Errorf("cluster: slot %d 重定向超过 %d 次", slot(key), maxRedirect)
}
```

这段骨架的四个要点就是四条纪律：**槽表按槽更新而不是全量重拉**、**`ASK` 不写槽表**、**`ASKING` 与命令必须同连接**（连接池里必须把这两条绑成一个不可拆的单元，否则会出现「ASKING 发到连接 1、命令发到连接 2」的诡异失败）、**重试必须有上限且必须区分错误类型**（把 `CLUSTERDOWN` 也当可重试错误，就是在故障期间给集群加压）。

## 15.5 槽迁移的七步与那个双写窗口

迁移一个槽，Redis 不提供「一条命令搞定」。它提供的是三个原语，让你自己编排：`CLUSTER SETSLOT <slot> IMPORTING|MIGRATING|NODE|STABLE`、`CLUSTER GETKEYSINSLOT`、`MIGRATE`。`redis-cli --cluster reshard` 做的就是下面这七步。

```text
时间 ──────────────────────────────────────────────────────────────────────────────►
  目标端 T：CLUSTER SETSLOT 3999 IMPORTING <S-id>
  源端   S：CLUSTER SETSLOT 3999 MIGRATING <T-id>
        │
   ①  状态置位。注意：**槽的归属没有变**，仍属 S；只有两端各自多了一个标记
        │   S = MIGRATING：仍服务该槽，但「已迁走的 key」会回 ASK
        │   T = IMPORTING：只接受「先发过 ASKING」的请求，否则回 MOVED 指向 S
        │
   ②  S: CLUSTER GETKEYSINSLOT 3999 100        → 返回该槽下的最多 100 个 key
        │
   ③  S: MIGRATE 10.0.0.12 6379 "" 0 5000 KEYS k1 … k100 REPLACE
        │   └─ **阻塞**：DUMP 序列化 + 建连接/复用连接 + 发送 + 等 T 回 +OK
        │      期间 S 的唯一执行线程不处理任何别的命令（§15.8 账二）
        │      T 也在阻塞：RESTORE-ASKING 要把这 100 个 key 建出来
        │
   ④  循环 ②③，直到 CLUSTER COUNTKEYSINSLOT 3999 == 0
        │   ← 这一步的「0」是乐观的：如果此刻正好有新 key 写进来，它会被算进下一轮
        │
   ⑤  T: CLUSTER SETSLOT 3999 NODE <T-id>      ← 先给目标端
   ⑥  S: CLUSTER SETSLOT 3999 NODE <T-id>      ← 再给源端，两者之间窗口越短越好
        │   ⚠ ⑤ 与 ⑥ 之间：T 认为自己是主人，S 仍以为自己服务该槽
        │     —— 这是整个协议里**唯一真实存在的双写窗口**
        │
   ⑦  其余主节点在 1–2 个心跳周期内通过 gossip 更新；客户端下一次访问该槽时
       收到 MOVED 并刷新本地槽表。在此之前，客户端「拿着旧表继续发」是合法的
```

### 迁移中与交接后的五种状态

| key 的状态 | 请求打到源端 S | 请求打到目标端 T | 客户端该走哪 |
| --- | --- | --- | --- |
| 仍在 S（未迁） | **本地执行** | 未 `ASKING` → `MOVED` 回 S（已 `ASKING` 也找不到 key，回空/写入 T 的一份孤立副本） | S |
| 已迁到 T | **`ASK` 到 T**（临时） | 需 `ASKING` 才能执行 | 先 `ASKING` 再命令 |
| 多 key 命令，全部在 S | 本地执行 | — | S |
| 多 key 命令，跨 S 与 T | **`TRYAGAIN`**（拒绝执行，稍后重试） | — | 退避后重试 |
| 交接完成后（步骤⑥之后） | **`MOVED` 到 T**（永久） | 本地执行 | 更新槽表后重试 |

这张表是「`ASK` 是临时的、`MOVED` 是永久的」这句话的完全展开：**`ASK` 只在迁移窗口内、只针对已经被搬走的那些 key 出现；一旦 `SETSLOT NODE` 落地，同一个 key 立刻改由 `MOVED` 指路**。把两者混为一谈的客户端，要么在迁移时疯狂刷槽表（把临时状态写成永久），要么在交接后一直拿着旧表打转。

### 那个双写窗口：⑤ 与 ⑥ 之间的几十毫秒

为什么顺序是「先目标端、后源端」？因为两种顺序的失败形态不一样：

| 交接顺序 | 窗口内发生什么 | 后果 |
| --- | --- | --- |
| **T 先、S 后**（推荐） | T 认为自己是主人并开始服务；S 仍以 MIGRATING 状态服务它手上还留着的 key | 极短时间内**同一批 key 可能被两个节点接受写**：写到 T 的是权威值，写到 S 的会变成孤儿——直到有人把这块键空间再迁回来才会「复活」成脏数据 |
| **S 先、T 后** | S 已停止服务该槽，客户端被告知槽属于 T；但 T 还在 IMPORTING（只认 `ASKING`） | 客户端收到 `MOVED` → 到 T → 因无 `ASKING` 被 `MOVED` 回来 → **重定向循环**，直到 T 的 `SETSLOT NODE` 落地 |
| 只给一端发 | 另一端永远保持 MIGRATING/IMPORTING 标记 | 该槽长期处在「半迁移」状态：单 key 靠 ASK 能跑，多 key 与 Lua 长期 `TRYAGAIN`/失败 |

所以工程纪律是三条：**两端都要发、目标端先发、中间不要停手**（不要让 `SETSLOT NODE` 落在一次发布或一次脚本 sleep 之后）。这个窗口最坏的长度不是毫秒，而是**「你两步之间的距离」**——手工运维时见过 20 分钟的，那 20 分钟里该槽所有写入都是「谁最后写谁赢，且输家那份会变成孤儿」。

### 迁移期间「源端已无」的 key：为什么可以放心

有人担心「key 已经搬到 T，但 S 还自称拥有这个槽，此时写入会写到哪」。答案在 §15.4 的表里：**S 在 MIGRATING 状态下发现 key 不在本地，会回 `ASK` 指向 T**。也就是说，新 key 的创建与老 key 的更新都会被重定向到 T，不会在 S 上凭空重建——**前提是客户端正确处理 `ASK`**。这条前提恰恰是最脆弱的环节：自研客户端把 `ASK` 当普通错误、或者把「缓存写失败」降级为「只打日志」，就会在 S 上留下孤儿副本，交接完成后表现为「数据消失」（§15.10）。

```bash
# 手工迁一个槽（工具做的就是这些；手做一遍才看得懂上面七步）
T=10.0.0.12; S=10.0.0.11; SLOT=3999
TID=$(redis-cli -h $T CLUSTER MYID); SID=$(redis-cli -h $S CLUSTER MYID)

redis-cli -h $T CLUSTER SETSLOT $SLOT IMPORTING $SID     # ① 目标端：IMPORTING
redis-cli -h $S CLUSTER SETSLOT $SLOT MIGRATING $TID     # ① 源端：MIGRATING

# ②③ 逐批搬迁：批越大单次阻塞越久，100 是常见折中；REPLACE 让重试可幂等
keys=$(redis-cli -h $S CLUSTER GETKEYSINSLOT $SLOT 100 | tr '\n' ' ')
[ -n "$keys" ] && redis-cli -h $S MIGRATE $T 6379 "" 0 5000 KEYS $keys REPLACE

redis-cli -h $S CLUSTER COUNTKEYSINSLOT $SLOT            # ④ 必须为 0 才能交接
redis-cli -h $T CLUSTER SETSLOT $SLOT NODE $TID          # ⑤ 先目标端
redis-cli -h $S CLUSTER SETSLOT $SLOT NODE $TID          # ⑥ 再源端（窗口越短越好）
# 回滚：redis-cli -h $S CLUSTER SETSLOT $SLOT STABLE
```

## 15.6 多 key、事务与 Lua：为什么必须同槽

槽是**分区单位**，而原子性只能在单个主线程内成立（`→ comp/12` §12.6）。两条事实相乘，就有了这条硬边界：**凡是「一次命令操作多个 key」的语义，在 Cluster 下都要求这些 key 落在同一个槽**，否则服务端连执行都不执行，直接回 `CROSSSLOT`。

| 命令 / 机制 | 什么时候报 `CROSSSLOT` | 注解 |
| --- | --- | --- |
| `MGET` / `MSET` / `DEL k1 k2 …` / `EXISTS` 多 key | 多 key 不同槽 | 单 key 形式永远合法 |
| `SUNION` / `SINTER` / `SDIFF` / `*STORE` / `ZUNIONSTORE` | 参与运算的集合/有序集合不同槽 | 结果集也落回目标 key 所在槽 |
| `RPOPLPUSH` / `LMOVE` / `BLMOVE` / `BITOP` / `PFCOUNT` / `PFMERGE` | 源与目标不同槽 | 「搬数据」类命令天生跨 key |
| `MULTI` / `EXEC` | 事务里第一个不同槽的 key 就报错（整个事务不可用） | `MULTI` 无回滚这一条在 Cluster 下依然成立（`→ comp/12`） |
| `EVAL` / `EVALSHA` / `FCALL` | `KEYS[]` 里不同槽；Lua 里 `redis.call` 访问了非本地槽的 key | 7.0+ 的报错文案更明确；脚本内跨槽访问直接抛错而非重定向 |
| `SCAN` / `KEYS` / `DBSIZE` / `FLUSHALL` | 不报错，但**只作用于当前节点** | 「扫全库」在 Cluster 里不存在写好的单命令（§15.10） |
| `WATCH` | 只对同槽的 key 有意义 | 乐观锁的粒度天然被槽切开 |

### 唯一的解法：`hash tag`，以及它的账单

```text
反例（写起来最自然，跑起来最贵）                正解（一个 tag 换一次往返）
  MGET cart:1000 price:1000 stock:1000          MGET {u:1000}:cart {u:1000}:price {u:1000}:stock
   → CROSSSLOT，三条命令各回各的槽                → 全部落在 CRC16("u:1000") 的槽
   ↓ 应用层改成循环 3 次单 key GET                 ↓ 一次往返（事故三的 200 倍差）
   延迟 = N × RTT，Redis 侧 QPS = N × 业务 QPS     延迟 = 1 × RTT
```

`hash tag` 的代价必须写在设计文档里，它有四条：

1. **并发被压到同一个槽**。同 tag 的 key 只能住在一个主节点的一个线程上——`{order}` 做 tag，全站订单的读写就都进了 1/16384 的键空间。此时加机器**完全没有用**，因为你把分片键设计成了常量。
2. **单节点倾斜**。tag 的基数决定分布：`{tenant:42}:*` 有 1 万个租户就是 1 万个 tag（可接受）；`{all}:*`、`{global}:*`、`{config}:*` 全是热点槽（一次倾斜足以让某台机器的内存与 CPU 先到顶，于是 `require-full-coverage` 之外又多了「木桶效应」）。
3. **键名变长**。每个 key 多出 `{}` 与 tag 本身的字节，按 `→ comp/13` §13.8 账二的口径，键名每多 1 B，1 亿 key 就是 100 MB 起。tag 通常 8–20 B，属于「白送 10–20% 键空间开销」。
4. **它是设计期决策**。改 tag 等于改槽归属，等于要迁移数据。事后补 tag 是一次全量 reshard + 双写（§15.8）。

### 如果实在需要跨实体原子

只有三条路，且都必须显式付出代价：

| 方案 | 做法 | 代价 |
| --- | --- | --- |
| **把数据塞进一个 key** | `{order:123}` 一个 hash 装「状态 + 明细摘要」 | 单 key 变大，撞 `→ comp/13` 的编码阈值；全量读变成 O(N) |
| **单槽目录 + 客户端协调** | 用一个 tag 圈住「必须一起操作的那几个 key」 | 牺牲分布均匀性（即上面的代价 1、2） |
| **换形态** | 跨实体事务放到关系库/NewSQL（`→ eng/36` 讲分库分表的拐点，`→ comp/19` 讲 Raft 那一路） | 延迟从 μs 到 ms 级，架构多一层 |

**没有第四条**。说「用 Lua 保证原子」的人往往忽略了：Lua 的原子性同样被槽切开，脚本里的 `KEYS[]` 跨槽照样失败。

## 15.7 故障判定与「一槽不可用即全站不可用」

### 拓扑怎么长出来：`CLUSTER MEET` 一句话，其余交给 gossip

Cluster 没有元数据中心，也没有「建集群」的服务端命令。一个集群的诞生只有四步：

| 步 | 动作 | 发生什么 / 报什么错 |
| --- | --- | --- |
| ① | 在 A 上执行 `CLUSTER MEET <B-ip> <B-port>` | A 与 B 握手互换 node id，双方都认识彼此；**只建立连接，不分配任何槽** |
| ② | gossip 扩散 | B 把 A 介绍给它已知的节点，A 把 B 介绍给自己的；每轮都带上「我知道谁活着、谁拥有哪些槽」，1–2 轮心跳内全网收敛 |
| ③ | `CLUSTER ADDSLOTS` / `CLUSTER ADDSLOTSRANGE`（通常由 `redis-cli --cluster create` / `add-node` 代劳） | 槽被**显式**指派给某节点：没有中心分配器，「谁声称谁负责」；已被别人拥有的槽会被拒绝（`Slot … is already busy`） |
| ④ | 收敛检查 | 三个数对上才算建完：`cluster_known_nodes` = 节点数、`cluster_slots_assigned` = 16384、`cluster_size` = 主节点数 |

**「集群建好了但 `cluster_state:fail`」最常见的两个原因就在 ③④**：`MEET` 成功只是「互相认识」，槽没分完（`cluster_slots_assigned < 16384`）集群就永远是 fail；给同一个槽指派两次，后到者的命令直接报错。同理，`reshard` 必须严格按 §15.5 的顺序「先 `SETSLOT` 状态、再搬 key、最后 `SETSLOT NODE`」——顺序反了就是两个节点同时声称拥有同一个槽。

### 故障判定：PFAIL → FAIL → 副本选举

Cluster 的故障判定是**纯 gossip + 多数派**，没有外部裁判（这是它与 Sentinel、与 `→ comp/16` 的 quorum 体系最像又最不像的地方）：

1. 每个节点在 `clusterCron` 里定期 PING 随机/可疑节点；**超过 `cluster-node-timeout`（默认 15,000 ms）没收到 PONG** → 记本地 `PFAIL`。
2. PFAIL 通过 gossip 扩散成「FAIL 报告」；当**持有槽的主节点中的多数**都报告某个节点不可达 → 该节点被标记 `FAIL`（`CLUSTER NODES` 里出现 `fail`）。
3. FAIL 节点的副本发起选举，需要**多数主节点的投票**；同时做数据新鲜度检查：若副本与主节点最后一次交互距今超过 `cluster-node-timeout × cluster-replica-validity-factor`（默认 15 s × 10 = 150 s），该副本**放弃参选**（`cluster-replica-validity-factor 0` 表示不看新鲜度，用「更旧的数据」换「更快的恢复」）。
4. 当选副本提升为主节点，接管那些槽；`currentEpoch` 增加，gossip 把新主人传播出去。

### 六个参数，各自改变哪条物理路径

| 参数（括号为默认） | 改的是什么 | 代价落在谁身上 |
| --- | --- | --- |
| `cluster-node-timeout`（15,000 ms） | 判 PFAIL 的等待时长，决定「抖动」与「恢复慢」的平衡点 | 太短：一次网络抖动/GC 停顿就切主（多一次全量同步，`→ comp/14`）；太长：故障恢复慢，且**默认 15 s 意味着任何一次主节点故障都要先死 15 s** |
| `cluster-require-full-coverage`（`yes`） | 只要有 1 个槽无人服务，**整个集群拒绝一切命令** | 单分片故障 → 全站不可用（事故一）；改 `no` 则退化为「部分 key 不可用」 |
| `cluster-replica-validity-factor`（10） | 副本参选的最大「数据落后时长」= timeout × factor | 调大：更容易选出落后副本（丢更多数据）；调 0：最快恢复、最多丢 |
| `cluster-migration-barrier`（1） | 一个主节点至少要有几个健康副本，它的副本才允许「迁移」去补没有副本的主节点 | 调大：副本不会被抽走，故障域更均衡但修复能力差 |
| `cluster-allow-replica-migration`（`yes`） | 是否允许副本自动迁移到无副本的主节点 | 关掉：拓扑完全静态，孤儿主节点长期裸奔 |
| `cluster-allow-reads-when-down`（`no`，5.0+） | 集群 `fail` 时是否仍允许读已分配的槽 | 开了：故障期间读能救一部分；代价是「读到的东西可能比你以为的旧」 |

### 3 主 3 从 vs 6 主：同样 6 台机器，两种完全不同的东西

最常见的容量评审误区是「6 台机器 = 6 份容量」，然后在「要冗余还是要容量」之间凭感觉选。把账摆出来：

| 维度 | 3 主 3 从（6 节点） | 6 主（6 节点） |
| --- | --- | --- |
| 有效可写内存 | 3 台的量（另 3 台是副本） | 6 台的量 |
| 单节点故障 | 副本接替；默认配置下该分片约 15–20 s 不可写 | 该分片的 2,731 槽**永久**不可用（无副本可接替） |
| 上面的故障对全站的影响 | `require-full-coverage yes` 时：**切换窗口内全站不可用**；切完恢复 | `require-full-coverage yes` 时：**全站一直不可用**，直到人工处理 |
| 双故障（主 + 其副本） | 1/3 键空间永久丢失（含数据） | 任意两节点故障 = 2/6 键空间丢失 |
| 读扩展 | 副本可承担读（需客户端 `READONLY`） | 无副本，读也只能打主 |
| 写扩展上限 | 3 个核（= 3 个主线程） | 6 个核 |
| 同硬件下的「成本」 | 容量减半，换可用性 | 容量全用，零冗余 |
| 什么时候选它 | 缓存/会话等「不能整体丢」的场景（绝大多数） | 纯可重建数据 + 明确接受「节点故障 = 部分功能不可用」 |

**这张表最该被记住的一行是「切换窗口内全站不可用」**：`cluster-node-timeout` 默认 15 s，加上选举与传播，一次主节点故障到副本接管通常要 15–20 s；而这 15–20 s 里，如果 `cluster-require-full-coverage yes`，**16384 个槽全部拒绝服务**——不是你挂掉的那个分片拒绝服务。所以「上一次主从切换，全站抖了 20 秒」不是故障转移慢，是**默认参数下「部分失败」被配置成了「整体失败」**。

## 15.8 三本账：扩容带宽、大 key 阻塞与重定向放大

三本账共用一套前提：**迁移吞吐受三件事共同限制——源端主线程的序列化速度、两端之间的网络、目标端 `RESTORE` 的重建速度**；而这三者都在单线程里，所以「并行」只能靠「多个源端同时迁」来获得，不能靠「一个源端多线程」。

### 账一：从 3 主扩到 4 主要多久

**场景与假设**：3 主 3 从，每主 10 GB（总 30 GB）；扩到 4 主 4 从；数据在槽上均匀分布；单 key 平均 1 KB；同机房 RTT 0.2 ms；1 Gbps 网卡；业务低峰且源端不做限速。新节点要接管 `16384 / 4 = 4,096` 槽，即 **25% 的键空间**。

| 步 | 推导 | 结果 |
| --- | --- | --- |
| 1 | 待迁移槽数 = `16384 / 4` | **4,096 槽** |
| 2 | 待迁移数据量 = 总数据 × 槽占比 = `30 GB × 4096 / 16384` | **7.5 GB**（每台老主各让出 `4096/3 ≈ 1,366` 槽 ≈ 2.5 GB） |
| 3 | 待迁移 key 数 ≈ `7.5 GB ÷ 1 KB` | **约 750 万 key** |
| 4 | 串行 `MIGRATE`（一次 1 个 key）：每次 `RTT 0.2 ms + 序列化 2 μs + 目标端 5 μs ≈ 0.21 ms` | **约 4,800 key/s** |
| 5 | 批 10 + 批间流水（`redis-cli --cluster-pipeline` 默认 10）：`10 key / (0.2 ms 摊薄 + 20 μs)` | **约 8 万 key/s** |
| 6 | 网络天花板：`1 Gbps = 125 MB/s ÷ 1.08 KB/key`（含键名与协议头） | **约 11.6 万 key/s**，8 万约为其 70% |
| 7 | 时间（串行）= `750 万 ÷ 4,800` | **约 1,560 s ≈ 26 分钟** |
| 8 | 时间（批 10、流水）= `750 万 ÷ 8 万` | **约 94 s ≈ 1.6 分钟**（纯吞吐下限） |
| 9 | 时间（批 100 + 万兆）：受目标端 `RESTORE` 约 5 μs/key 限制 → 20 万 key/s 上限 | `750 万 ÷ 20 万 ≈ 38 s` |
| 10 | 实际观测区间（含 `GETKEYSINSLOT` 往返、槽表刷新抖动、监控采样、偶发大 key） | **5–30 分钟**（1 Gbps 下，取决于批大小与是否流水） |

**量级结论**（非承诺值）。**假设清单**：数据在槽上均匀（真实分布可能 2–3 倍倾斜，最坏槽要单独迁）、key 平均 1 KB（大 key 会局部拖慢，见账二）、`MIGRATE` 走批与流水、网络独占 1 Gbps、目标端空闲、业务低峰。换成 10 GB 单 key 的长尾分布或跨机房链路（RTT 1–5 ms），时间会按比例放大；换成万兆 + 批 100，可压到 1 分钟以内但受目标端重建速度限制。

这张表最该带走的一句话：**扩容时间 ≈ 总数据量 × 新增节点占比 ÷ 有效迁移吞吐**，而「有效吞吐」在串行脚本里只有 4,800 key/s 的量级——**同一次扩容，脚本写得糙一点就是 26 分钟，写好一点是 2 分钟，差 15 倍**。这也是为什么 `MIGRATE` 的批大小（以及是否流水）值得写进运维手册，而不是交给手写的 `for` 循环。

**缩容是同一笔账反过来**：从 4 主缩到 3 主，要迁出的同样是 `16384 / 4 = 4,096` 槽、同样的 7.5 GB，只是方向相反（先把待下线节点的槽迁空，再 `CLUSTER FORGET` 并关机）。差别只在最后一步：缩容多了一个**不可逆动作**——节点下线。所以它的必要条件比扩容严格：`CLUSTER COUNTKEYSINSLOT` 必须对每个槽都为 0（§15.10 第九行）。

### 账二：`MIGRATE` 一个大 key 会阻塞多久

`MIGRATE` 的物理路径是：**源端在主线程里 `DUMP` 序列化这个 value → 发送 → 等目标端 `RESTORE` 回 OK → 删除本地 key**。全程同步、不 yield、不并行（`→ comp/12` §12.6 的阻塞清单里，它和 `DEL bigkey` 是同一类东西）。

**算例**：一个 50 MB、50 万 field 的 hash（平均 value 100 B），1 Gbps 链路。

| 阶段 | 发生在谁的线程上 | 推导 | 耗时 |
| --- | --- | --- | --- |
| 序列化（`DUMP` → RDB 编码 payload） | 源端主线程 | 50 MB 写入内存缓冲约 25–50 ms + 50 万次逐 field 编码 ≈ 50 ms | **75–100 ms** |
| 传输 | 网卡 | `50 MB × 8 ÷ 1,000 Mbps` | **400 ms** |
| 目标端 `RESTORE-ASKING` 重建 | **目标端主线程** | 50 万 field 逐项插入 + 分配（一定是 hashtable 编码，`→ comp/13` §13.5） | **80–150 ms** |
| 等待 OK 的 RTT | 源端主线程 | 同机房往返 | **≈ 1 ms** |
| **源端阻塞合计** | 源端主线程 | 序列化 + 传输 + 等 OK | **约 0.5 s**（10 Gbps 时约 0.12 s） |

所以：**一个 50 MB 的 key，`MIGRATE` 一次 = 该分片停 0.12–0.5 秒；一个 480 MB 的 key = 约 4.3 秒**（`480 × 8 ÷ 1,000 = 3.84 s` 传输 + 0.3 s 序列化 + 0.2 s 重建，即事故二）。把 Little 定律接上（`→ comp/12` §12.6），受害面立刻可算：

```text
t=0         MIGRATE 开始，源端主线程进入序列化 → 该分片其它命令全部排队
t=0–0.5 s   50 万 field 编码、400 ms 传输、等目标端 OK
t=0.3 s     订单服务 300 ms 超时到点，第一批重试到达 —— 排在队尾，把队列从
            QPS × T_block 抬到 QPS × T_block × (1 + 重试次数)
t=0.5 s     MIGRATE 返回 OK；积压命令开始执行（若有一个 480 MB 的 key，这是 t=4.3 s）
            超时数 = 分片 QPS × max(0, T_block − 客户端超时)
              = 120,000 × (0.5 − 0.3) = 24,000 条（50 MB key）
              = 120,000 × (4.3 − 0.3) = 480,000 条（480 MB key，其中订单占 8.1 万笔）
```

| key 形态 | `T_block`（1 Gbps） | 分片 12 万 QPS、客户端超时 300 ms 时的超时数 | 结论 |
| --- | --- | --- | --- |
| 1 KB string | 约 0.2 ms | 0 | 批量迁移是一堆微秒级小停顿，感知不到 |
| 1 MB hash | 约 10 ms | 0（但 P99 抬起） | 单条 10 ms 能吃掉 1% 的主线程时间片 |
| 50 MB hash | 约 0.5 s | 约 2.4 万条 | 已经是一次事故 |
| 480 MB hash | 约 4.3 s | 约 48 万条 | 双十一前扩容的翻车形态 |

**量级结论**（非承诺值）。**假设清单**：链路 1 Gbps 且无丢包重传、value 不可压缩（`DUMP` 不做压缩）、目标端空闲且内存充足、批大小为 1（批 N 个 key 时阻塞近似为 N 倍序列化 + 一次性传输，因此**大 key 必须单独迁**）、无 swap。换 10 Gbps 阻塞降为 1/8 到 1/4；换跨机房链路则传输项线性放大。**这就是「扩容必须低峰做」的物理原因**：低峰不是为了让机器更闲，而是为了让「一个 key 静默拖死一个分片 4 秒」这件事发生时，受害请求足够少。真正的解法是**事前把大 key 拆掉**（`→ comp/13` §13.9），让每个 `MIGRATE` 的 `T_block` 都停在 10 ms 以下。

### 账三：一次 `MOVED` 风暴把 QPS 放大几倍

重定向的成本结构很简单：**每个被重定向的请求 = 1 次失败的往返 + 1 次成功的重试**，如果客户端还有应用层重试，再乘上去。写成式子就是 `放大倍数 ≈ 1 + p × R`，其中 `p` = 命中「需要重定向」的比例（迁移窗口里等于「槽已迁或已交接、但客户端槽表未更新」的请求占比），`R` = 客户端的重定向重试上限（超过就报错，不会无限循环）。

| 场景 | `p` | `R` | 放大倍数 | 现场表现 |
| --- | --- | --- | --- | --- |
| 稳态、槽表准确 | 0 | 3 | 1.0× | 正常 |
| 迁移中，客户端及时刷表 | 3–5% | 1 | 1.03–1.05× | 每秒多几十次往返，无感 |
| 大批量迁移 + 客户端只在「整表过期」时刷新 | 25% | 3 | **1.75×** | P99 抬 2 倍，`total_error_replies` 明显抬升 |
| 客户端把 `ASK` 当 `MOVED`（写坏槽表） | 60% 以上 | 3 | **约 2.8–3×** | 重定向循环，QPS 与错误数同时放大，恢复要重启客户端 |
| 应用层再套一层重试（3×） | 同上 | 3 × 3 | **6–9×** | 迁移期间把 Redis 打满，迁移本身更慢（正反馈） |
| 迁移窗口里所有客户端同时失效并全量拉 `CLUSTER SLOTS` | — | — | 额外 N 次元数据请求 | 3,000 个客户端各拉一次 = 3,000 次 `CLUSTER SLOTS` 打到同一个节点 |

**「放大 3 倍」的那一行的推导**：`1 + 0.6 × 3 = 2.8`，即每个业务请求实际产生 2.8 个到达服务端的请求。它通常与「应用层把 `CLUSTERDOWN` 也当可重试错误」叠加——故障期间本应快速失败，结果变成稳定地乘 3–9 倍加压。

**量级结论**（非承诺值）。**假设清单**：客户端独立维护槽表且不做跨实例共享、重试为立即重试（无指数退避）、`CLUSTER SLOTS` 回复足够小（几 KB 量级，槽区间聚合后与节点数成正比）、迁移窗口内槽表刷新策略一致。若客户端实现了指数退避 + 抖动，放大倍数会显著低于上表——**这是「重试策略」比「重试次数」更值钱的地方**。

### 扩容带宽估算脚本（可直接换假设复算）

```python
def reshard(total_gb: float, old_masters: int, keys_per_sec: int,
            key_bytes: int = 1024, nic_gbps: float = 1.0):
    slots = 16384 // (old_masters + 1)              # 扩到 old_masters+1 后每主分到的槽
    moved_gb = total_gb * slots / 16384             # 假设 key 在槽上均匀分布
    moved_keys = moved_gb * 1e9 / key_bytes
    wire = key_bytes + 80                           # 键名/过期/协议头的量级估计
    nic_ceiling = nic_gbps * 1e9 / 8 / wire         # 网卡能搬多少 key/s
    effective = min(keys_per_sec, nic_ceiling * 0.7)  # 实测通常只跑到网卡 60–75%
    return slots, moved_gb, moved_keys, nic_ceiling, moved_keys / effective

for name, kps, gbps in [("串行 MIGRATE（1 key/次）", 4_800, 1),
                        ("批 10 + 流水", 80_000, 1),
                        ("批 100 + 万兆", 200_000, 10)]:
    slots, gb, keys, ceil_, sec = reshard(30, 3, kps, 1000, gbps)
    print(f"{name:22s} 迁 {slots} 槽 / {gb:.1f} GB / {keys/1e4:.0f} 万 key "
          f"→ 网卡上限 {ceil_/1e4:.1f} 万 key/s，实取 {sec/60:.1f} 分钟")

# 实际输出（与账一第 6–9 行一致）：
# 串行 MIGRATE（1 key/次）  迁 4096 槽 / 7.5 GB / 750 万 key → 网卡上限 11.6 万 key/s，实取 26.0 分钟
# 批 10 + 流水             迁 4096 槽 / 7.5 GB / 750 万 key → 网卡上限 11.6 万 key/s，实取 1.6 分钟
# 批 100 + 万兆            迁 4096 槽 / 7.5 GB / 750 万 key → 网卡上限 115.7 万 key/s，实取 0.6 分钟
```

**这段脚本的用法**：把 `total_gb`、`key_bytes`、`nic_gbps` 换成你的真实值，就能得到「本次扩容要占多少分钟的网络与主线程」。**注意它只算传输与限速，不算大 key 的停顿**——大 key 必须单独列出来按账二逐个算。

## 15.9 架构边界：Cluster 能保证什么、不能保证什么

### 三列对照

| 能做（在什么前提下） | 不能做（物理原因） | 靠什么绕过 |
| --- | --- | --- |
| 写容量随主节点数线性扩展（前提：key 分布均匀） | 单 key 写吞吐超过 10 万/s——同一个 key 永远只在一个主线程上 | 本地缓存挡热点、把 key 拆成多个分片键（`→ comp/12` §12.10） |
| 单 key 主节点故障后自动接管 | 切换窗口内零影响——`node-timeout` 默认 15 s 起，配置 `require-full-coverage yes` 时全站都受影响 | 降 `cluster-node-timeout`、`require-full-coverage no` + 业务降级 |
| 跨槽的读可以并行打到不同节点 | 跨槽的多 key 原子——`MGET`/`MULTI`/Lua 一律要求同槽 | `hash tag` 圈住必须一起操作的 key；或换形态（`→ eng/36`） |
| 在线扩容/缩容（不停机搬槽） | 扩容不产生任何停顿——`MIGRATE` 是阻塞命令，大 key 会让分片停几百毫秒到几秒 | 低峰 + 拆大 key + 分批 + 限速 |
| 客户端可以水平扩展（无代理） | 客户端简单——每个客户端都要实现槽表 + `MOVED`/`ASK`/`TRYAGAIN`/重试上限 | 用成熟客户端；自研必须把这套逻辑测成「迁移中也能跑」 |
| 键空间按槽均匀切分（概率上） | 负载天然均衡——CRC16 只保证 key 数均匀，不保证访问量均匀；`hash tag` 会主动制造倾斜 | 监控节点内存/CPU 倾斜度；tag 设计期评审 |

### 与无主架构的对照（只对照，不展开）

Cluster 是**有中心的槽分片**（中心不是一台机器，而是一份「每个节点都持有副本的槽表」，且每次变更都要两端确认 + gossip 传播）；Dynamo 家族是**一致性哈希 + quorum 无主**（任何副本都能接受写，冲突靠版本向量/timestamp 解决）。两者的差别不是「谁更好」，而是「你把哪笔账记在了哪个科目」：

| 体系 | 分片单位 | 读写路由 | 故障判定 | 丢数据窗口 | 扩容影响面 | 何时选它 |
| --- | --- | --- | --- | --- | --- | --- |
| **Redis Cluster** | 16,384 个**固定**槽，槽数是协议常量 | 客户端持槽表直连主节点，错则服务端回 `MOVED`/`ASK` | gossip + 多数主节点判 FAIL，副本选举接管 | 异步复制窗口（无 `WAIT` 时）；脑裂期间旧主继续收写 | 逐槽 `MIGRATE`，**阻塞源端与目标端主线程** | 需要微秒级读、数据结构丰富、能接受「同槽才原子」 |
| **Dynamo 家族**（Cassandra / DynamoDB） | 一致性哈希环 + 虚拟节点（vnode），可随时调整 | 客户端任意节点均可接受请求，由协调者转发给 N 个副本 | 心跳 + φ 值/怀疑机制，无中心主；写永远可写 | 由 `R + W > N` 与读修复/反熵决定，冲突要业务合并 | 加节点即改环，只搬相邻区间；**无阻塞式搬迁** | 需要多地域写、单点写不停、能接受最终一致与合并逻辑 |

一句话对照：**Cluster 用「同槽原子 + 低延迟」换掉了「无主写的高可用与柔性扩容」；Dynamo 家族反过来，用「任何副本都能写」换掉了「读立即一致」。** 细节在 `→ comp/16`。

### ⑤ 扩展维度 / ⑥ 系统级失效 / ⑧ 换掉它的信号

- **⑤ 扩展维度**：Cluster 的答案是**分片（主答案）+ 副本（只扩读与可用性）+ 垂直切（缓存/会话/队列分集群）+ 批处理摊薄（pipeline/MGET 摊 RTT）**。四者都不是的场合（要求单 key 写超 10 万/s）——它不可横向扩，只能换零件。
- **⑥ 系统级失效**：**慢**（大 key `MIGRATE` 阻塞、重定向风暴）；**满**（倾斜导致单节点先满 → 该槽写入报 OOM 或开始逐出）；**脑裂**（网络分区两侧各自选中主节点，恢复后一侧数据被丢弃）；**语义漂移**（跨槽多 key 被应用层改成循环单 key，功能「对」了但延迟与 QPS 结构全变）。
- **⑧ 换掉它的信号**：

| 信号 | 阈值 | 为什么这条线之后它不再是正确选择 |
| --- | --- | --- |
| 跨槽多 key 需求 | 任何「必须一起原子」的核心链路 | 只能靠 `hash tag` 牺牲分布，或换形态 |
| 槽布局变更频率 | 每月 > 1 次 reshard | 每次都是一次「阻塞 + 重定向 + 人工值守」的组合 |
| 单 key 写 QPS | > 10 万/s 持续 | 单核串行的物理上限（`→ comp/12`） |
| 单分片内存 | > 25 GB 且 `latest_fork_usec` > 300 ms | fork 停顿吃掉垂直收益，需要更细的分片或换持久化形态 |
| 需要的 db 数 | 想用 `SELECT 1` | 集群模式只有 `db0`，没有第二个库 |
| 需要全库遍历 | 依赖 `KEYS`/`SCAN` 扫全量 | 集群里每个节点只扫自己那份（§15.11） |

## 15.10 踩坑清单（现象 → 根因 → 定位 → 修复 → 防复发）

| 现象 | 根因（指到物理形态） | 定位 | 修复 | 防复发 |
| --- | --- | --- | --- | --- |
| 只挂一个分片，全站 100% 写失败 | `cluster-require-full-coverage yes`：只要有槽无人服务，整个集群拒绝命令 | `CLUSTER INFO` 的 `cluster_state:fail` + `cluster_slots_assigned < 16384` | 存活节点逐台 `CONFIG SET cluster-require-full-coverage no`（先确认业务能承受 1/3 miss）；修好故障节点后改回 | 默认值改成 `no` 并写进配置基线；主从跨故障域；演练「一槽消失」 |
| `MGET` 报 `CROSSSLOT` 后改成循环单 key，P99 涨 17 倍 | 每次单 key 都是独立往返；Cluster 没有跨槽批量 | 接口耗时 ≈ N × RTT；Redis 侧 `GET` 的 `usec_per_call` 完全正常 | `hash tag` + `MGET`/`HMGET`；或把 N 个 key 合成一个 hash | key 设计评审必须给出「哪些 key 会被一次命令操作」；SDK 禁止在循环里发单 key 读 |
| 迁移中「数据消失」：读目标端读不到刚写的值 | 客户端不处理 `ASK`（当作错误重试/降级），写在源端留下孤儿副本；或 ⑤⑥ 之间双写 | `CLUSTER COUNTKEYSINSLOT` 为 0 却仍读不到；对比两端 `EXISTS` | 迁移结束后做一次 key 数对账；孤儿 key 手工搬回；升级客户端 | 客户端必须通过「迁移中读写」测试；禁止把 `ASK`/`TRYAGAIN` 归入「未知错误」分支 |
| 迁移期间 QPS 涨 3 倍、错误数暴涨、迁移越迁越慢 | 重定向放大 `1 + p × R`：`ASK` 当 `MOVED` 写坏槽表 → 循环重试 → 服务端更忙 → 迁移更慢 | `INFO stats` 的 `total_error_replies` 增量；客户端重试计数 | 修客户端的重定向分支；迁移降速（减小批、加 sleep） | 重定向逻辑单测覆盖 `MOVED`/`ASK`/`TRYAGAIN`/`CLUSTERDOWN` 四种；重试上限 + 退避 |
| 某个分片内存是别人的 3 倍，先 OOM | CRC16 只保证 key 数均匀，不保证字节数均匀；或 `hash tag` 用了低基数 tag | 各节点 `INFO memory` 的 `used_memory`；`CLUSTER COUNTKEYSINSLOT` 逐槽抽 | 迁移热点槽出去；重构低基数 tag | 倾斜度（max/avg）进监控；tag 设计期审「基数」 |
| `{order}` 当 tag，全站订单落一个槽，加机器无效 | `hash tag` 把并发压到 1/16384 键空间、单主线程 | `CLUSTER KEYSLOT {order}:1` 与 `{order}:999` 相同 | 改成 `{order:12345}`（订单号做 tag），或去掉 tag 改设计 | 评审硬规则：tag 必须是「实体 id」而不是「实体类型」 |
| 用 `KEYS`/`SCAN` 遍历「全库」，只返回 1/3 | 它们在集群里只作用于**当前节点** | 结果数 ≈ `DBSIZE`（单节点） | 逐节点扫描后客户端归并；或维护一份索引 key | 禁用 `KEYS`；把「全库遍历」需求写进架构评审（通常说明该数据不该放 Redis） |
| 网络抖动一次就切主，或故障后 20 秒才恢复 | `cluster-node-timeout` 太短（抖动即 PFAIL）/ 太长（恢复慢） | `CLUSTER NODES` 的 `fail?`/`fail` 时间戳；节点日志里的 failover 记录 | 短抖动 → 调大到 15,000–30,000；恢复慢 → 配合 `cluster-allow-reads-when-down` | 把「一次切换 = 全站 15–20 s（若 full-coverage=yes）」写进 SLA；演练切换 |
| 缩容直接把节点下线，槽永久丢失 | 没先迁槽就 `CLUSTER FORGET`/关机：那 4,096 个槽无人服务 | `CLUSTER INFO` 的 `cluster_slots_assigned` 掉到 12288 | 恢复该节点，先 `reshard` 把槽迁空，再下线 | 缩容 runbook 第一步永远是「迁槽到 0」，并 check `COUNTKEYSINSLOT` |
| 客户端连上后一直 `MOVED`，重启才恢复 | 客户端把 `ASK` 的临时目标写进了长期槽表（§15.4） | 抓包看客户端是否每次先发 `ASKING`；日志里 `MOVED` 与 `ASK` 交替出现 | 重启客户端重建槽表；升级客户端版本 | 客户端库版本纳入基线；`ASK` 分支禁止写槽表 |
| 同一个账号 `SELECT 1` 报错 | 集群模式只有 `db0` | 报错原文 `ERR SELECT is not allowed in cluster mode` | 把多 db 用法改成 key 前缀 | 集群化改造 checklist 里必须有「有无 `SELECT`」一项 |

这张表里前四行占了线上 Cluster 事故的绝大多数，它们的共同点是：**每个节点的 `INFO` 都「看起来正常」**——`used_memory` 正常、`connected_clients` 正常、分命令耗时正常，只有 `cluster_state`、`total_error_replies` 与「节点间内存差值」这三处异常。所以 §15.11 的观测必须带**集群维度**，否则永远抓不到「一个槽坏了全站坏」这类事实。

## 15.11 观测：指标、拐点与告警

### 指标表（每条标版本 + 开关）

| 指标 | 取法 | 版本 / 开关前提 | 拐点 | 它说明什么 |
| --- | --- | --- | --- | --- |
| `cluster_state` | `CLUSTER INFO` | 3.0+，全版本；`cluster-enabled yes` 才有 | 任何非 `ok` | **第一指标**：`fail` = 有槽无人服务，配合 `require-full-coverage yes` 即「全站不可用」 |
| `cluster_slots_assigned` | `CLUSTER INFO` | 同上 | < 16384 | 有槽没分配/节点掉线；等于 `12288` 通常意味着 4 主里丢了 1 个 |
| `cluster_known_nodes` / `cluster_size` | `CLUSTER INFO` | 同上 | `known_nodes` 与拓扑不符；`cluster_size` 变小 | 有人被 `FORGET`、或节点长期失联未归队 |
| `cluster_slots_pfail` / `cluster_slots_fail` | `CLUSTER INFO` | 同上 | 任何非 0 且持续 | 故障判定的早期信号（PFAIL 早于 FAIL 一个 `node-timeout`） |
| `CLUSTER NODES` 的 flags | `CLUSTER NODES` | 全版本；输出格式随版本略有差异 | 出现 `fail?` / `fail` / `noaddr` | 定位「是谁、从什么时候起」；第 9 列是该节点的槽范围/迁移标记 |
| 结构化拓扑 | `CLUSTER SHARDS` | **7.0+ 新增**；同时 `CLUSTER SLAVES` 在 7.0 弃用，替代品是 `CLUSTER REPLICAS` | 与 `CLUSTER NODES` 交叉验证 | 更易解析（每分片的主 + 副本 + 槽区间），适合写进巡检脚本 |
| `cluster_enabled` | `INFO cluster` | 全版本 | 与预期不符 | 排查「以为连的是集群、其实是单机」的第一条 |
| `total_error_replies` | `INFO stats` | **6.2+**；累计值，看导数 | 5 分钟增量 > 基线 3 倍 | 汇总了 `MOVED`/`ASK`/`TRYAGAIN`/`CROSSSLOT`/`CLUSTERDOWN`/`OOM` 等错误回复；**重定向风暴的第一信号** |
| `cmdstat_migrate` 的 `calls` / `usec_per_call` | `INFO commandstats` | 全版本；`CONFIG RESETSTAT` 会清零 | 迁移窗口内 `usec_per_call` > 10 ms | 直接看到 `MIGRATE` 把主线程占了多少（`→ comp/12` 的「累计占用」口径） |

| 各节点 `used_memory` 倾斜度 | 逐节点 `INFO memory` | 全版本 | `max / avg > 1.3` | 倾斜（槽分布或 `hash tag` 设计问题）的第一信号 |
| `CLUSTER COUNTKEYSINSLOT <slot>` | 逐槽 | 3.0+ | 迁移中应单调递减到 0 | 迁移进度；缩容前必须为 0 才能下线节点 |
| `cluster_stats_messages_sent/received`、`total_cluster_links_buffer_limit_exceeded` | `CLUSTER INFO` | 后者 **7.0+** | 心跳数突降 / 超限计数 > 0 | 心跳链路拥塞或被限流，会拖慢故障判定与 gossip 传播 |

### 采集命令

```bash
# ① 先看集群整体：cluster_state 是唯一能一句话判断「全站是否不可用」的字段
redis-cli -h 10.0.0.11 CLUSTER INFO | grep -E \
  'cluster_state|cluster_slots_assigned|cluster_slots_fail|cluster_known_nodes|cluster_size'

# ② 拓扑与槽范围（第 9 列形如 0-5460 / [3999->-<id>] 表示迁移中）
redis-cli -h 10.0.0.11 CLUSTER NODES | awk '{printf "%-8s %-22s %-12s %s\n", substr($1,1,8), $2, $3, $9}'

# ③ 7.0+ 的结构化视图，适合替代文本解析（CLUSTER SLAVES 在 7.0 已弃用）
redis-cli -h 10.0.0.11 --json CLUSTER SHARDS

# ④ 重定向/错误的整体速率：累计值，必须取导数
redis-cli -h 10.0.0.11 INFO stats | grep -E 'total_error_replies|instantaneous_ops_per_sec'

# ⑤ 迁移在吃主线程多少时间
redis-cli -h 10.0.0.11 INFO commandstats | grep '^cmdstat_migrate'

# ⑥ 节点内存倾斜：max/avg > 1.3 就要查槽分布
for h in 10.0.0.11 10.0.0.12 10.0.0.13; do
  printf '%-12s ' $h; redis-cli -h $h INFO memory | awk -F: '/^used_memory:/{print $2}'
done

# ⑦ 迁移/缩容的前提：槽必须空
redis-cli -h 10.0.0.11 CLUSTER COUNTKEYSINSLOT 3999

# ⑧ 集群模式只有 db0：这条命令一定报错，是排查「以为能用多库」的最快证据
redis-cli -h 10.0.0.11 -n 1 PING   # ERR SELECT is not allowed in cluster mode
```

### 告警表达式骨架

```yaml
# ① 集群状态：require-full-coverage=yes 时这一条等价于「全站不可写」
- alert: RedisClusterDown
  expr: redis_cluster_state == 0          # cluster_state:ok 为 1
  for: 30s

# ② 槽覆盖率：掉下来就说明有节点长期离队
- alert: RedisClusterSlotUnassigned
  expr: redis_cluster_slots_assigned < 16384
  for: 1m

# ③ 重定向风暴 / CLUSTERDOWN 重试：错误回复的增速比绝对值有用
- alert: RedisClusterErrorRepliesHigh
  expr: rate(redis_total_error_replies[5m]) > 3 * avg_over_time(rate(redis_total_error_replies[1h] offset 1h)[5m])
  for: 5m

# ④ 迁移正在进行：只是「有事发生」的信号，阻塞量要配 LATENCY HISTORY command 看
- alert: RedisMigrateActive
  expr: increase(redis_command_calls_total{cmd="migrate"}[5m]) > 0
  for: 1m
```

指标名随 exporter 版本可能不同（`redis_cluster_state` 与 `redis_cluster_info` 在不同版本间有差异）；**采集不到就退回 `CLUSTER INFO` 的文本解析——「集群状态」这个事实不能没有告警**。第 ④ 条只是「迁移正在发生」的信号，真正的阻塞量要配 `LATENCY HISTORY command` 一起看。

## 15.12 一页速记

| 关键词 | 一句话结论 |
| --- | --- |
| 槽 | `slot = CRC16(tag或key) & 0x3FFF`；源码常量 `CLUSTER_SLOTS = 16384`，是协议常量不是调优旋钮 |
| 为什么 16384 | 心跳里用 bitmap 表示槽归属：16384 bit = 2 KB，65536 bit = 8 KB，而心跳每秒都在发；16384 已够 1,000 主规模 |
| 槽表 | 客户端持有；服务端只回 `MOVED`/`ASK` 让客户端自己去找，Cluster 没有代理 |
| `MOVED` | 槽已换主人，**永久**；更新槽表该槽后重试 |
| `ASK` | 槽在迁移中、**这一个 key** 已迁走，**临时**；先发 `ASKING` 再发命令，**同一条连接**，不刷槽表 |
| `TRYAGAIN` | 多 key 命令撞上迁移（一部分 key 已迁）；毫秒级退避后重试 |
| `CLUSTERDOWN` | 有槽无人服务（`require-full-coverage yes` 时全集群拒绝）；不重试，快速失败降级 |
| 迁移七步 | `SETSLOT IMPORTING` → `SETSLOT MIGRATING` → 循环（`GETKEYSINSLOT` + `MIGRATE`）→ `SETSLOT NODE`（目标先、源后）→ gossip 传播 |
| 双写窗口 | ⑤⑥ 之间；窗口长度 = 你两步之间的距离，手工运维可以长到分钟级 |
| 同槽要求 | `MGET`/`MSET`/`SUNION`/`MULTI`/`EVAL` 全部要求同槽，否则 `CROSSSLOT`；唯一解法是 `hash tag` |
| `hash tag` 代价 | 并发压到一个槽、可能单节点热点、键名变长、事后改等于全量 reshard |
| `MIGRATE` 的代价 | **阻塞源端主线程**：50 MB key 约 0.1–0.5 s，480 MB key 约 4.3 s；目标端 `RESTORE` 同样阻塞 |
| 扩容时间 | ≈ 总数据 × 新增节点占比 ÷ 有效吞吐；串行 4,800 key/s（26 分钟）vs 批 10 + 流水 8 万 key/s（1.6 分钟） |
| 重定向放大 | `1 + p × R`；p = 需重定向比例，R = 重试上限；p=60%、R=3 即约 3 倍 |
| 故障判定 | PFAIL（本地，超 `cluster-node-timeout`）→ FAIL（多数主节点报告）→ 副本选举（多数票 + 新鲜度检查） |
| 默认 15 s 的含义 | 任何一次主节点故障，先死 15 s；`require-full-coverage yes` 时这 15 s 是**全站** |
| 一槽坏即全站坏 | `cluster-require-full-coverage yes`（默认）→ 改成 `no` 才能把爆炸半径限回 1/N |
| 只有 db0 | 集群模式 `SELECT` 不可用；`KEYS`/`SCAN` 只作用于当前节点 |
| 一句话 | **Cluster 把「一个 Redis」变成「16384 个槽的主从组」：容量买到了，跨 key 原子与平滑扩容没了。** |

## 15.13 自检题（5 题）

**1. 为什么 Cluster 选 16384 个槽而不是 65536？如果有人说「65536 更均匀、扩容更平滑」，怎么反驳？**
<details><summary>答案</summary>

槽位的归属不是靠一张中心表，而是靠每个节点在 PING/PONG 里携带的 bitmap（`myslots[CLUSTER_SLOTS/8]`）互相确认。16384 bit = **2 KB**，65536 bit = **8 KB**，而这 2 KB/8 KB 是**每秒都在发**的心跳固定开销：100 节点规模下，前者约 200 KB/s、后者约 800 KB/s 的纯运维流量，全网量级差 4 倍。而 16384 槽已经能支撑 1,000 个主节点这一量级，远超绝大多数集群（3–20 主）的实际需要。

反驳三点：① 均匀性不由槽数决定，由 CRC16 与 key 分布决定——16384 槽下每主 5,461 槽，`sqrt(5461)` 量级的统计波动早就被「大数定律」抹平了，真正导致倾斜的是 `hash tag` 与热点 key，不是槽太粗。② 槽越细，重平衡时单次迁移的**粒度越细但总次数越多**，每次迁移都有一次阻塞与一次重定向，总开销反而更高。③ 16384 是**协议常量**：改成 65536 等于换一个不兼容的实现，所有节点与客户端都必须一致改，收益为零、风险极大。
</details>

**2. 一次 `MGET k1 k2` 在迁移窗口里可能收到哪三种回复？客户端各自该怎么处理？为什么 `ASK` 之后必须发 `ASKING`？**
<details><summary>答案</summary>

三种：① **本地执行**——该槽仍在源端且两个 key 都在本地；② **`TRYAGAIN`**——槽在 MIGRATING，`k1` 还在源端、`k2` 已迁到目标端（多 key 命令不允许「一半本地一半远端」），客户端应毫秒级退避后重试同一条命令；③ **`ASK <slot> <target>`**——该槽在 MIGRATING 且**两个 key 都已不在源端**，服务端让客户端去目标端要；如果槽已交接完成（`SETSLOT NODE` 落地），则改为 **`MOVED`**。

`ASKING` 的原因：目标端此刻处于 `IMPORTING` 状态，它自己并不认为这个槽属于自己（槽的归属还是源端），因此**默认会对该槽的请求回 `MOVED` 指回源端**。`ASKING` 是一个一次性的会话标记，含义是「我这次是按 ASK 指路来的，请破例服务这一个 key」。所以顺序必须是 `ASKING` → 命令，且必须**同一条连接**（`ASKING` 的标记挂在连接上，连接池里拆成两条连接就失效）。省掉 `ASKING` 的结果就是两端互指：源端 `ASK` → 目标端 `MOVED` → 源端 `ASK` …，只有客户端重试上限能停下它。
</details>

**3. 3 主 3 从扩到 4 主 4 从，每主 10 GB、单 key 1 KB、1 Gbps。要迁多少数据、多久？如果把 `MIGRATE` 写成「一个 key 一条命令」的 `for` 循环，会变成多久？**
<details><summary>答案</summary>

要迁 `16384 / 4 = 4,096` 槽 = 25% 键空间 = `30 GB × 0.25 = 7.5 GB` ≈ 750 万 key（每台老主让出约 1,366 槽 ≈ 2.5 GB）。

- 批 10 + 批间流水：约 8 万 key/s（网络上限 `1 Gbps = 125 MB/s ÷ 1.08 KB ≈ 11.6 万 key/s`，8 万约为其 70%）→ `750 万 ÷ 8 万 ≈ 94 s`，**约 1.6 分钟**。
- 一个 key 一条 `MIGRATE`：每次成本 ≈ `RTT 0.2 ms + 序列化 2 μs + 目标端 5 μs ≈ 0.21 ms` → 约 4,800 key/s → `750 万 ÷ 4,800 ≈ 1,560 s`，**约 26 分钟**。

差 15 倍。真实观测还要加上 `GETKEYSINSLOT` 往返、客户端槽表刷新抖动、监控开销与偶发大 key，1 Gbps 下常见区间是 5–30 分钟。**前提**：数据在槽上均匀、目标端空闲、业务低峰（量级结论，换 key 大小与网卡会移动）。
</details>

**4. `MIGRATE` 一个 50 MB 的 hash（50 万 field）在主线程上要多久？为什么「扩容选在低峰」不能解决这个问题？**
<details><summary>答案</summary>

`MIGRATE` 是同步阻塞命令，路径是「源端 `DUMP` 序列化 → 传输 → 目标端 `RESTORE` 重建 → 源端删 key」，源端与目标端**各自的主线程**都被占住：

- 序列化 50 MB + 50 万次逐 field 编码 ≈ 75–100 ms；
- 传输 `50 MB × 8 ÷ 1,000 Mbps = 400 ms`（1 Gbps）；
- 目标端 `RESTORE-ASKING` 重建 50 万 field ≈ 80–150 ms（同时也是它自己的阻塞）。

源端阻塞合计约 **0.5 s**（10 Gbps 时约 0.12 s）。期间该分片所有请求排队：`超时数 = 分片 QPS × max(0, T_block − 客户端超时)`，12 万 QPS、300 ms 超时 → `120,000 × 0.2 = 24,000` 条。

「低峰」不能解决它，因为**低峰只减少受害者数量，不缩短阻塞时长**。`T_block` 由 key 的字节数与链路带宽决定，与业务量无关。真正的解法是**事前把大 key 拆掉**（让每个 key 控制在「`MIGRATE` < 10 ms」的量级），并对已知大 key 单独排期、单独迁、迁移前后各做一次对账。
</details>

**5. 生产上「只挂了一个分片，但全站都写不进」，最可能的两个原因是什么？各自的止血动作与根治动作是什么？**
<details><summary>答案</summary>

原因一：`cluster-require-full-coverage yes`（默认）。只要有 1 个槽无人服务，整个集群 `cluster_state:fail`，所有节点对所有命令回 `CLUSTERDOWN`——**故障半径不是 1/N 而是 100%**。止血：确认业务能承受 1/N 的 miss 后，逐台 `CONFIG SET cluster-require-full-coverage no`。根治：默认值改为 `no` + 业务侧对 miss 做降级/回源；主从跨故障域（事故一里主从同宿主机，一台机器带走了主与另一个副本）。

原因二：故障节点其实「还在」，但被判定 `fail` 而不是真的消失——例如网络分区导致多数派把某主节点踢出、或缩容时**没迁槽就下线**（`cluster_slots_assigned` 从 16384 掉到 12288）。止血：`CLUSTER INFO` 看 `cluster_slots_assigned` 与 `CLUSTER NODES` 的 `fail` 标记；把节点拉回或对空槽做 `SETSLOT NODE` 指派。根治：缩容 runbook 第一步永远是「`COUNTKEYSINSLOT` 迁到 0 再下线」；把 `cluster_state`、`cluster_slots_assigned` 做成双指标告警（§15.11）。

排查顺序固定三步：`CLUSTER INFO`（`cluster_state` / `cluster_slots_assigned` / `cluster_slots_fail`）→ `CLUSTER NODES`（谁 `fail`、槽范围是否残缺）→ 逐节点 `INFO memory` / `INFO replication`（是节点死了，还是仅被判死）。
</details>
