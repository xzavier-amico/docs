## 18.1 引子：一次 42 轮的对话，账单从 $0.8 变成 $14

Aurora 有个做 ERP 的租户，客服场景里出现了"超长工单排查"：用户和 Agent 来回 42 轮，中间调了 11 次工具（查日志、查配置、查工单历史），每次工具返回 2~6k token 的 JSON。

第 1 轮的输入是 3.2k token，成本 $0.01。
第 42 轮的输入是 **96k token**，单次成本 $0.29。
这一个会话的总成本：**$14.3**。而这个租户的套餐单价是每次会话 $0.6。

拆开看第 42 轮的 96k 里有什么：

| 内容 | token | 占比 | 有多少是"本来可以不要"的 |
| --- | --- | --- | --- |
| system + 角色卡 + 工具 schema | 8.4k | 8.8% | 0（全要，但可以缓存） |
| 历史 41 轮原文 | 51k | 53.1% | 约 70%（前 30 轮已被后续结论覆盖） |
| 工具返回原文 | 28k | 29.2% | 约 80%（12 份日志里有 9 份是同构的） |
| 检索片段 | 6.2k | 6.5% | 约 40%（有 2 篇重复命中） |
| 本轮输入 | 2.4k | 2.5% | 0 |

**"本来可以不要"的部分占 62%。** 也就是说：这一个会话你多花了 $8.9，而且因为上下文里塞了 51k 的历史原文，模型的注意力被严重稀释——我们后来做 A/B 发现，**长上下文里的关键约束（"不能承诺退款"）遵守率从 97% 掉到 78%**。

> 🎯 这一章的两个目标，一个省钱一个保命：
> **压小**（省成本、保注意力）和 **复用**（省成本、省延迟）。
> 而且它们会互相打架：**你压得越频繁、越"聪明"，前缀缓存就越容易被你打穿。**

## 18.2 断崖：不压缩、或者乱压缩，分别怎么炸

| # | 断崖 | 不做的后果 | 量化判据（撞上它的信号） |
| --- | --- | --- | --- |
| 1 | **超窗硬截断** | 最早的约束被截掉，模型开始违规 | 出现 `context_length_exceeded`，或你的代码里有 `if len > max { text = text[len-max:] }` |
| 2 | **成本线性爆炸** | 每轮把历史全带上，成本随轮次超线性增长 | 单会话成本 > 套餐价；日均输入 token 增速 > 日活增速 |
| 3 | **注意力稀释** | 关键指令淹没在噪声里，遵守率下降 | 关键约束遵守率 < 90%（应做 A/B 验证） |
| 4 | **延迟上升** | 输入越长，prefill 越久，TTFT 变差 | TTFT P99 与输入 token 数正相关（画散点图能看到斜线） |
| 5 | **压缩丢约束** | 摘要后"禁止项"消失，行为退化 | 压缩前后跑同一组回归，通过率掉 > 3% |
| 6 | **打穿缓存** | 压缩/重排让前缀每次不同，命中率归零 | 命中率 < 50%，且输入 token 没降 |

### 18.2.1 账本：压缩与缓存的收益上限在哪

先把两个杠杆的量级分开算清楚，否则你会优化错地方。

**杠杆一：压缩。** Aurora 日均输入 4.8B token（第 17 章同一口径），其中历史与工具返回占 55% 左右，理论可压 50%：

```
可压量：      4.8B × 55% × 50% = 1.32B token/天
按 $3/M：     1,320 × 3 = $3,960 / 天 ≈ $119,000 / 月
```

**杠杆二：前缀缓存。** 命中部分按 10% 计价（各家不同，以官方文档为准）：

```
若命中率从 12% 提到 89%：
有效系数： (1-0.12)×1.25 + 0.12×0.10 = 1.112   ← 比不缓存还贵！
           (1-0.89)×1.25 + 0.89×0.10 = 0.227
日均输入成本： 4.8B × $3/M = $14,400/天
从 $16,013/天 → $3,269/天，省 $12,744/天 ≈ $382,000/月
```

两个结论都很硬：

1. **缓存的杠杆比压缩大 3 倍，而且改造成本低一个数量级**。第 1 章给的优化顺序（缓存 → 路由 → 瘦身 → 压缩）在这里得到了数字验证。
2. **命中率 12% 时你比不缓存更贵**——因为你付了 `1.25×` 的缓存写入溢价却几乎没读到。**这是个反直觉但极重要的事实：缓存不是"开了就省"，它有个盈亏平衡点。**

盈亏平衡点算一下（设读 `0.10×`、写 `1.25×`）：

```
(1-H)×1.25 + H×0.10 < 1.0
→ 1.25 - 1.15H < 1.0
→ H > 21.7%
```

**命中率低于 21.7%，前缀缓存是亏的。** 这个数请记住，它决定了你该不该给某类租户开缓存。

**这张图只有一条主线：上下文要按"稳定度"分区，压缩只能动不稳定的那部分。**

把这条线写反的例子（真实发生过）：

- 把"当前时间"拼在 system prompt 开头 → P0 每次都变 → 命中率 0。
- 把检索片段放进 system message → P2 污染 P0 → 全平台命中率从 90% 掉到 15%。
- few-shot 每次按查询动态挑 5 个 → P1 每次都变 → 少省 15 个点。

## 18.4 关键设计

### 18.4.1 命中率算式与成本模型

```text
定义：
  T_in      本次请求输入 token 总数
  T_hit     命中缓存的前缀 token 数（按最长公共前缀计）
  p_read    缓存读单价系数（相对基础输入价，通常 0.1）
  p_write   缓存写单价系数（通常 1.25）
  H = T_hit / T_in                          ← 命中率
  有效输入成本系数 C(H) = (1-H)·p_write + H·p_read

Aurora 参数：p_read = 0.10，p_write = 1.25
  C(0)    = 1.250   ← 全写，最贵
  C(0.217)= 1.000   ← 盈亏平衡点
  C(0.58) = 0.583
  C(0.89) = 0.227
```

关键推论：**命中率是可优化的，但"写"的成本必须付**。所以：

1. **不要给低频会话开缓存**。一个租户日均 10 次调用、每次前缀都不同，命中率 0 → `C=1.25`，纯亏 25%。缓存要按租户/场景开关（第 24 章）。
2. **缓存 TTL 要算**。各家缓存有效期通常是分钟级到小时级（Anthropic/OpenAI 都有 TTL 概念，具体以官方文档最新版为准）。如果你的调用频率是每 10 分钟一次，缓存早过期了，你只是在付写溢价。判据：**同一前缀的调用间隔 < TTL 的 1/3，才值得开**。
3. **命中率要按 `prefix_hash` 分桶看**。全局 89% 可能藏着 3 个前缀是 20%。第 17 章的 `PrefixHash` 就是为这个准备的。

### 18.4.2 五种压缩手法：适用、压缩比、是否打穿缓存

| 手法 | 适用对象 | 压缩比 | 信息损失 | 边际成本 | 是否打穿缓存 | 可复现 |
| --- | --- | --- | --- | --- | --- | --- |
| **去重** | 重复检索、同构工具返回 | 2:1~5:1 | 无 | ~0（哈希） | 否（结果确定） | ✅ |
| **结构化抽取** | 工具返回 JSON、表单、日志 | 10:1~30:1 | 低（丢格式不丢字段） | 规则 + 小模型 | 否（同输入同输出） | ✅ |
| **引用折叠** | 长文档、RAG 片段 | 10:1~50:1 | 中高（需可回查） | ~0 | 否 | ✅ |
| **递进摘要** | 多轮历史 | 5:1~10:1 | **中（最容易丢约束）** | 一次 LLM 调用 | **是** | ❌（除非常温=0+缓存） |
| **滑动窗口** | 闲聊、无状态问询 | 极高 | 高（丢早期一切） | ~0 | **是**（窗口一动前缀就变） | ❌ |

一条排序原则（这条比具体手法重要）：

> **确定性可复现的压缩优先，模型生成的压缩最后；只在超过阈值时压，不要每轮都压。**

原因很直接：摘要靠模型生成，模型有随机性 → 同输入两次摘要不同 → **前缀变化 → 缓存全废**。你把 8k 压到 1k 省了 7k，但打穿了后面 20k 的缓存，净亏。

### 18.4.3 压缩管道（Go）

```go
// ctxeng/compress.go
type Seg struct {
    Name      string // system|tools|persona|fewshot|memory|history|retrieval
    Stability int    // 0=P0稳定 1=P1半稳定 2=P2会话 3=P3易变
    Text      string
    Pinned    bool   // 钉子区：永不压缩（约束、合同条款、红线）
    Tokens    int
}

// Compress 按稳定度倒序压缩：先压易变区，实在不够才动会话区，P0/P1 一律不动。
func Compress(segs []Seg, budget int) ([]Seg, error) {
    total := Sum(segs)
    if total <= budget {
        return segs, nil
    }
    out := slices.Clone(segs)

    // ① 无损阶段：去重 + 结构化抽取 + 引用折叠，只处理 P2/P3
    for i := range out {
        if out[i].Stability < 2 || out[i].Pinned {
            continue
        }
        switch out[i].Name {
        case "retrieval":
            out[i] = FoldCitations(DedupByHash(out[i]))  // → doc_id + 摘要 + 指针
        case "history":
            out[i] = ExtractStructured(out[i])           // → 事实卡，保留数字/ID/约束
        }
    }

    // ② 有损阶段：只对 history 做摘要，且有代数上限
    if total = Sum(out); total > budget {
        for i := range out {
            if out[i].Name != "history" || out[i].Pinned {
                continue
            }
            // 只以「原文」为基准摘要，不以旧摘要为基准（防误差累积）
            s, err := Summarize(OriginalOf(out[i]), SummarizeOpts{
                Temp: 0, Generation: MaxGeneration, // 最多叠 2 代
                MustKeep: PinnedFacts(out[i]),      // 约束/数字/金额/ID 钉死
                TargetTokens: budget / 4,
            })
            if err != nil {
                return nil, fmt.Errorf("summarize history: %w", err) // 失败不降级为截断
            }
            out[i] = s
        }
    }

    // ③ 仍然超预算：拒绝执行，让上层降级（换小模型/拆任务/明确告知）
    if Sum(out) > budget {
        return nil, ErrBudgetExceeded{Budget: budget, Actual: Sum(out)}
    }
    return out, nil
}
```

三个设计点，每个都能独立展开：

1. **失败不降级为截断**。`Summarize` 失败就返回错误，绝不 `text[:max]`。截断是最危险的操作——它**静默地删掉了你无法预知的东西**，而模型会装作没看见继续答（第 1 章断崖 4 的变种）。宁可让上层降级（换成"任务太复杂，我分步来"，第 25 章降级阶梯）。
2. **`MustKeep` 是钉子区**。压缩时必须显式传入"不许动的部分"：数字、金额、日期、ID、约束条款。经验值：**约束类内容的丢失是压缩事故的头号原因**，而它们在原文里往往只占 3~5%。
3. **摘要只基于原文**。`OriginalOf` 保证不拿旧摘要当输入。递进摘要叠 3 代以上，语义会崩坏成"一段听起来合理但没有信息的话"——这是最容易骗过验收测试的失败模式。

### 18.4.4 缓存友好的排序校验（CI 里跑）

```go
// ctxeng/layout_test.go
// 把「顺序约束」变成单元测试：任何人在拼装代码里插一段动态内容到前面，
// CI 立刻红，而不是等到月底看账单。
func TestLayoutStableFirst(t *testing.T) {
    for _, tc := range goldenAssemblies() {
        segs := Assemble(tc.Ctx)
        var lastStability = -1
        for _, s := range segs {
            if s.Stability < lastStability {
                t.Fatalf("%s: segment %q (stability=%d) 排在 stability=%d 之后，"+
                    "会打穿前缀缓存", tc.Name, s.Name, s.Stability, lastStability)
            }
            lastStability = s.Stability
        }
        // 禁止动态内容出现在 P0 段
        for _, s := range segs[:2] {
            if strings.Contains(s.Text, "{{now}}") || strings.Contains(s.Text, "request_id") {
                t.Fatalf("%s: P0 段出现动态变量 %q", tc.Name, s.Name)
            }
        }
        // 工具 schema 必须按名称排序（Go 的 map 迭代顺序是随机的！）
        if !sort.IsSorted(toolNames(segs)) {
            t.Fatalf("%s: 工具 schema 未排序，每次请求前缀不同", tc.Name)
        }
    }
}
```

> 🩸 最后那条断言救过 Aurora 一次：某个服务把工具 schema 从 `map[string]Tool` 直接 `range` 序列化，Go 的 map 迭代顺序是**随机的**，导致每次请求的工具列表顺序都不同 → **前缀在 300 token 处就开始分叉 → 命中率 0**，而且代码 review 看不出来（本地跑一次永远是"对的顺序"）。这个 bug 活了 11 天，多花了约 $38,000。

### 18.4.5 什么该放前面，什么会打穿缓存

| 内容 | 建议位置 | 稳定性 | 放错的代价 |
| --- | --- | --- | --- |
| 工具 schema（**必须排序**） | P0 最前 | 极高 | 顺序抖动 → 命中率归零 |
| 角色卡 L1 身份 / L2 边界 / L4 禁止项 | P0 | 高 | 放中段 → 改语气就打穿 |
| 输出契约 L5 | P0 尾部 | 高 | — |
| 角色卡 L3 风格 | P0 最后（或 P3） | 中 | 放最前 → 改语气打穿全平台 |
| few-shot（**按桶固定**） | P1 | 中 | 动态选 → 少省 15 点 |
| 会话摘要 + 事实卡 | P2 | 低 | 放 P0 → 每 N 轮打穿一次 |
| 检索片段 | P3 | 无 | 放 system → 灾难 |
| 当前时间、request_id、用户昵称 | **P3 或用户消息里** | 无 | 放最前 → 命中率 0，成本 ×5 |
| 工具调用结果（历史） | P2（抽取后） | 低 | 保留原文 → 占 30% 预算 |

### 18.4.6 对比实验：五个方案的命中率与成本

Aurora 在同一个客服场景（60 万 Run/天，日均输入 4.8B token）上做了 5 组对照，每组跑 7 天：

| 方案 | 做法 | 命中率 H | 有效系数 C(H) | 日均输入成本 | 相对基线 |
| --- | --- | --- | --- | --- | --- |
| **A 基线（无优化）** | 时间戳在 system 开头、动态 few-shot、工具 map 乱序、历史全带 | 12% | 1.112 | $16,013 | 1.00 |
| **B 稳定前缀** | 动态内容挪到尾部，P0 固定 | 58% | 0.583 | $8,395 | 0.52 |
| **C B + 工具排序** | schema 按名排序 + 序列化字段序固定 | 71% | 0.434 | $6,250 | 0.39 |
| **D C + few-shot 分桶** | 按 intent 桶固定，不逐请求挑 | 84% | 0.284 | $4,090 | 0.26 |
| **E D + 会话摘要复用** | 摘要按 (session, gen) 缓存，不重复生成 | 89% | 0.227 | $3,269 | 0.20 |
| **F E + 全量压缩** | 额外开激进摘要（每轮压） | **61%** | 0.502 | $7,229 | 0.45 |

**最值钱的信息在 F 行**：加了"更激进的压缩"之后，成本反而涨了 2.2 倍。原因：每轮摘要都在变 → P2 及其后的前缀全变 → H 从 89% 掉到 61% → 省下的 token 抵不过打穿的缓存。**这就是"压缩和缓存互相打架"的实测代价。**

同时必须承认：F 方案的质量指标是**上升**的（长上下文关键约束遵守率从 78%→94%）。所以正确做法不是"别压缩"，而是：

> **压缩要发生在"换轮次"这种本来就要变前缀的时刻，而不是"每次请求"。**
> 具体说：**在会话的第 10、20、30 轮各压一次**，而不是每轮压。这样 P2 的变化次数从 42 次降到 4 次。

改完之后（方案 G，没进上表）：H = 86%，成本 $3,600/天，约束遵守率 93%。**这才是工程上的最优解——质量和成本同时拿到，靠的是"把变化对齐到缓存边界"。**

## 18.5 压缩的失败模式

| 失败模式 | 现象 | 根因 | 兜底 |
| --- | --- | --- | --- |
| **约束丢失** | 压缩后开始承诺退款、越过边界 | 摘要器把"禁止"当语气词删了 | 钉子区（`Pinned`）+ 压缩后跑 persona 回归（第 17 章） |
| **数字漂移** | 30 天变 3 天、¥500 变 ¥50 | 摘要重写数字（模型会"顺手取整"） | 数字/金额/日期/ID 走**结构化抽取**，绝不进摘要 |
| **摘要套摘要** | 3 代之后语义崩坏但"读起来通顺" | 误差累积 | 只以原文为基准 + 代数上限 2 |
| **指针失效** | 引用了不存在的 doc_id | 折叠后文档被更新/删除 | 折叠指针带版本号，失效时降级为"无引用"并标低置信 |
| **压缩抖动** | 同一会话两次请求摘要不同 | `temperature > 0` 或无幂等键 | 摘要落库 + `(session_id, gen)` 幂等 + temp=0 |
| **成本倒挂** | 压缩调用比省下的还贵 | 每次都压 / 压得太小 | 阈值触发：待压内容 > 3k token 才压 |

成本倒挂的算式（这条值得背下来）：

```
压缩一次：8k 输入 + 0.6k 输出，用小模型（$0.3/M in, $1.2/M out）
  = 8,000×0.3/1e6 + 600×1.2/1e6 = $0.0024 + $0.0007 ≈ $0.0031
省下的：8k token × 4 步 × $3/M = $0.096
净收益：31 倍  ✅

若只压 1.5k token：
  省 1.5k × 4 × $3/M = $0.018，净收益 5.8 倍   ← 还行
若只压 400 token：
  省 400 × 4 × $3/M = $0.0048 < $0.0031+缓存损失   ← 亏
```

**阈值结论：待压内容 < 3k token 不要压。** 小步压缩是典型的"优化了个寂寞"。

## 18.6 Java / 分布式经验对照

| 你熟悉的东西 | 上下文压缩/缓存里的对应物 | 会咬人的差异 |
| --- | --- | --- |
| HTTP 缓存 / `ETag` / 304 | 前缀缓存 | 缓存键不是 URL，是**token 序列的最长公共前缀**；差一个 token 全废 |
| CDN 分层缓存 | P0/P1/P2/P3 四层 | 这里没有"失效通知"，只有 TTL 自然过期 |
| `gzip` 压缩 | 语义压缩 | 这是**有损**压缩，且损失不可验证（解压不回来） |
| 冷热数据分层归档 | 摘要 + 引用折叠 | 归档数据能回查；摘要回查不了，所以折叠必须带指针 |
| 消息队列的幂等消费 | 摘要的幂等键 | 摘要是个"非确定性函数"，你得把它**改造成纯函数**（temp=0 + 落库） |
| `HashMap` 遍历 | 工具 schema 序列化 | Go 的 `map` 迭代顺序**随机**；Java 的 `HashMap` 顺序稳定但不保证——两边都别赌 |
| 分库分表的"路由键" | 缓存分层键（prefix_hash） | 路由键错了数据错，这里缓存键错了只是慢……**但账单会告诉你** |

三条会咬人的：

1. **"压缩是纯函数"这个错觉**。Java 工程师本能地认为 `compress(x)` 两次结果一样。这里不一样，除非你把 `temperature` 钉死并把结果落库。**所以摘要必须带幂等键，跟支付一样。**
2. **"配置顺序无所谓"**。JSON/YAML 序列化在很多库里字段顺序不定（Go 的 `map`、Java 的 `HashMap`、某些 JSON 库的 `omitempty` 行为）。**上下文拼装里任何"集合"都必须显式排序**——这是 `TestLayoutStableFirst` 存在的全部理由。
3. **"截断兜底"**。传统系统里截断日志字段是常规操作；这里截断上下文 = 静默删掉约束 = 生产事故。**要报错，不要截断。**

## 18.7 开源坐标

| 能力 | 开源/产品里的对应物 | 能抄什么 | 缺什么 |
| --- | --- | --- | --- |
| 前缀缓存 | Anthropic 的 prompt caching（显式 `cache_control` 断点）、OpenAI 的自动 prompt caching（≥1024 token 前缀自动命中） | 断点标记的位置策略、最小长度、TTL | 没有"命中率归因到段"的能力，得自己埋点 |
| 压缩策略 | LangChain 的 `ConversationSummaryMemory` / `ConversationSummaryBufferMemory` 一类实现 | 摘要 + 缓冲窗口的组合思路 | 没有钉子区、没有代数上限、没有缓存友好排序 |
| 语义压缩 | LLMLingua 系列（token 级压缩） | 极致压缩比的做法 | 可读性/可审计性差，且会打穿缓存 |
| 引用折叠 | 各类 RAG 框架的 `citation` 机制（RAGFlow 等） | doc_id + 片段 + 溯源 | 缺"折叠后按需展开"的工具化闭环 |
| 命中率观测 | Langfuse / OpenTelemetry GenAI 语义约定里的 cache token 字段 | 字段命名（cached tokens / cache read / cache write） | 缺按 prefix_hash 的分桶看板 |

> 一致的判断：**缓存机制是厂商给你的，缓存命中率是你自己挣的**。厂商只保证"前缀相同就命中"，它不知道你的前缀为什么每次都不同。

## 18.8 事故清单

- [ ] **事故 A：工具 schema 用 `map` 直接序列化，顺序随机 → 命中率 0，11 天多花 $38,000。**
      兜底：显式排序 + `TestLayoutStableFirst` 进 CI。
- [ ] **事故 B：把"当前时间"拼在 system prompt 第一行 → 全平台命中率 0。**
      兜底：P0 段禁止动态变量（同一条测试断言）。
- [ ] **事故 C：检索片段注入 system message → 命中率从 90% 掉到 15%。**
      兜底：检索永远走 P3，独立 message role，压测环境加命中率断言。
- [ ] **事故 D：摘要器把"不得承诺退款"摘要掉了 → 一周内 3 起越界承诺。**
      兜底：钉子区 + 压缩后跑 persona 回归（通过率掉 >3% 阻断发布）。
- [ ] **事故 E：为了"省成本"改成每轮摘要 → 成本涨 2.2 倍（方案 F）。**
      兜底：压缩对齐到缓存边界（每 N 轮一次）+ 压缩前后都记命中率。
- [ ] **事故 F：长文档直接截断 → 模型基于半篇文档给出了相反的结论。**
      兜底：超预算时返回错误走降级，绝不静默截断；或改成引用折叠 + 按需展开。

## 18.9 一页速记

| 关键词 | 必须记住的结论 |
| --- | --- |
| **两个杠杆的量级** | 缓存省 $382k/月，压缩省 $119k/月；先做缓存 |
| **盈亏平衡点** | `H > 21.7%` 缓存才不亏（读 0.1×、写 1.25× 时）；低频场景别开缓存 |
| **有效系数** | `C(H) = (1-H)×1.25 + H×0.1`；H=12% 时比不缓存贵 11% |
| **分区原则** | P0 稳定 / P1 半稳定 / P2 会话 / P3 易变；**压缩只动 P2/P3** |
| **压缩排序** | 确定性压缩（去重/抽取/折叠）在前，模型生成（摘要）在后 |
| **对齐缓存边界** | 压缩发生在"换轮次"时，不是"每次请求"；每轮压会让成本涨 2.2 倍 |
| **阈值** | 待压内容 < 3k token 不要压，净收益为负 |
| **钉子区** | 数字/金额/日期/ID/约束走结构化抽取，绝不进摘要 |
| **绝不截断** | 超预算要报错走降级；静默截断 = 静默删约束 = 事故 |
| **排序进 CI** | 任何"集合"都要显式排序；Go map 顺序随机，代价是 $38k |
| **摘要即纯函数** | temp=0 + `(session_id, gen)` 幂等 + 落库，否则抖动打穿缓存 |

## 18.10 自检题

1. **你的命中率从 88% 掉到 62%，成本涨了 40%，但输入 token 总量没变。最可能的三个原因？**
   > 要点：① 有人往 P0 段插了动态内容（时间戳/昵称/request_id）；② 集合类内容（工具 schema、few-shot）顺序不稳定；③ 有人在会话中段加了"每轮摘要"，让 P2 每次都变。排查方法：按 `prefix_hash` 分桶看命中率，再按段打点算"每段的前缀复用长度"。

2. **老板说"上下文太长，全压成摘要吧，反正模型能理解"。你怎么反驳（要给数字）？**
   > 要点：① 摘要会丢约束、漂移数字，约束遵守率从 97% 掉到 78% 的真实数据；② 每轮摘要会让命中率从 89% 掉到 61%，成本反涨 2.2 倍；③ 正确做法是分层压缩——无损三件套（去重/抽取/折叠）处理 62% 的冗余，摘要只在换轮次时做，P0/P1 一 token 不动。

3. **怎么证明"我们的压缩没有伤害质量"？**
   > 要点：① 压缩前后跑同一组 ≥200 条回归（第 40 章），通过率下降 > 3% 阻断；② 单独测"约束遵守率"和"数字准确率"两个专项指标（这两类最容易被压坏）；③ 线上按压缩代数分桶看投诉率，代数 ≥2 的会话投诉率应无显著差异。
