## 5.1 引子：48 小时，$212,000

一个做 AI 笔记 App 的团队，把模型调用放在了客户端。理由很正当：「少一跳，延迟低 80ms，还能省服务端成本。」

他们的 API Key 是用字符串混淆写在 iOS 包里。上线第 4 个月，有人在 Telegram 频道发了他们的 Key。48 小时之内：

```
单个 Key 的速率上限 10,000 RPM
每次请求平均 2,000 in + 500 out token
按当时价格 $3/M in、$15/M out：
  10,000 × (2,000×3/1e6 + 500×15/1e6)
= 10,000 × (0.006 + 0.0075)
= 10,000 × $0.0135 = $135 / 分钟
                       = $8,100 / 小时
48 小时理论上限 = $388,800
实际账单（多 Key 轮换 + 部分时段被打满） = $212,000
```

他们最后做了三件事：吊销所有 Key、给 provider 打电话求减免（拿回了 30%）、把架构改成「客户端不持有任何密钥」。**第三件事花了 6 周，而前两件事花了两天。** 这个顺序很典型。

但这个故事真正的教训不是「别把 Key 放客户端」——那是常识。真正的教训是：**他们没有一条可以被强制执行的边界。** 移动端团队要低延迟，服务端团队要安全，两边都「讲道理」，最后赢的是排期紧的那个。

> 🎯 本章的核心命题：**Client 与 Server 的分离，不是部署问题，是「谁能被信任」的问题。** 一旦你把「不可信执行环境」和「可信执行环境」画开，职责归属就变成了一道有唯一答案的题，而不是一场谈判。

## 5.2 断崖：不分离的六种死法

| # | 死法 | 现象 | 量化判据 | 根因 |
| --- | --- | --- | --- | --- |
| 1 | **密钥泄露被薅** | 账单暴涨、provider 告警 | 客户端二进制里能 `strings` 出 `sk-` | 凭证下发到了不可信环境 |
| 2 | **无法治理** | 无法限流、无法计费、无法审计 | 你说不出「哪个用户今天花了多少钱」 | 计量点在客户端（可伪造） |
| 3 | **迭代速度塌陷** | 改一句提示词要发版 | 端上迭代周期 / 服务端迭代周期 > 100 倍 | 行为定义在客户端 |
| 4 | **多端不一致** | Web 能做的事 App 不能 | 同一个 Agent 有 N 份实现 | 逻辑复制到每个端 |
| 5 | **断线即失忆** | 电梯里出来，回答没了 | 30 秒 Run 在移动网络下的断连率 8~15% | 状态在客户端内存 |
| 6 | **无法灰度与回滚** | 出了问题只能等下个版本 | 回滚时间 = 发版时间（小时~天） | 没有服务端开关 |

第 3 条值得单独算一遍，因为它是「技术决策被产品节奏反向绑架」的典型：

```
端上迭代：改提示词 → 打包 → 提审（iOS 1~3 天）→ 灰度 7 天 → 全量
         合计 ≈ 10 天
服务端迭代：改提示词 → 评测门禁（20 分钟）→ 灰度 1% → 观察 2 小时 → 全量
         合计 ≈ 3 小时 ≈ 0.125 天
比值 = 80 倍
```

**当你的 Agent 还在快速迭代期（前 18 个月一定是），80 倍的迭代差就是生与死的差别。** 这就是为什么「行为必须住服务端」不是洁癖，是节奏问题。

第 5 条也要算：Aurora 的移动端数据显示，一次 30 秒的 Run 在 4G/5G 切换、进电梯、切后台这些场景下，**断连率 11.4%**。如果状态只在客户端内存里，这 11.4% 的用户看到的是一个半截回答 + 一个无法恢复的界面。分离之后，这个数字变成「断连后 1.2 秒内自动续上」（第 7 章的 `Last-Event-ID`）。

### 5.3.1 一条按「可信度」切的边界

```

│  用户授权采集（一次一授权）                                     │
│                                                              │
│  ✗ 不持有：模型密钥、系统提示词全文、计费逻辑、配额、审计判定     │

                            │  协议（不是函数调用）
                            │  · 控制面：REST/JSON
                            │  · 事件面：SSE 单向流
                            │  · 命令面：WebSocket/gRPC 双向
                            │  · 工具面：客户端工具回调
┌───────────────────────────▼──────────────────────────────────┐
│                    可信域（Server）                            │
│                                                              │
│  模型调用与路由 · 密钥 · 系统提示词 · 上下文装配 · 记忆          │
│  配额/限流/计费/账本 · 审计与哈希链 · 输出审核与撤回             │
│  Run 状态机 · 事件真相源 · 灰度与开关 · 评测                    │
│                                                              │

└──────────────────────────────────────────────────────────────┘
```

这条边界有一句判据，可以背下来：

> **凡是「伪造了会让人赚钱或让别人受损」的东西，必须在服务端；凡是「离开这台设备就没有意义」的东西，必须在客户端。**

## 5.4 关键设计

### 5.4.1 职责边界表（24 项能力的归属）

| # | 能力 | Client | Server | 判据 |
| --- | --- | --- | --- | --- |
| 1 | 渲染与增量更新 | ✅ 独占 | — | 只有它知道屏幕 |
| 2 | 输入法 / 语音采集 | ✅ 独占 | — | 设备能力 |
| 3 | 事件缓冲与重放 | ✅ | ✅ | 端做乐观 UI，服务端是真相源 |
| 4 | 断线重连决策 | ✅ | — | 只有端知道网络状态 |
| 5 | 本地工具执行（读写本地文件/跑命令） | ✅ 执行 | ✅ 声明与审计 | 数据不出端，但**调用意图**要上报 |
| 6 | 工具结果的可信性判定 | — | ✅ | 客户端可被改，结果要校验 |
| 7 | 模型选择 | ❌ | ✅ | 涉及成本与配额 |
| 8 | 模型密钥 | ❌ **绝不** | ✅ 独占 | 泄露 = 直接资损 |
| 9 | 系统提示词全文 | ❌ | ✅ | 泄露 = 资产损失（第 32 章） |
| 10 | 角色卡 / 人格 | ❌ | ✅ | 品牌一致性 + 不可篡改 |
| 11 | 上下文装配 | ❌ | ✅ | 涉及检索权限与租户隔离 |
| 12 | 检索与 RAG | ❌ | ✅ | 数据权限必须在服务端 |
| 13 | 记忆读写 | ⚠️ 只读缓存 | ✅ 写入与裁决 | 冲突裁决要全局视野 |
| 14 | 配额 / 限流 | ⚠️ 只读提示 | ✅ | 可伪造的计量无意义 |
| 15 | 计费与账本 | ❌ | ✅ | 同上 |
| 16 | 审计与哈希链 | ❌ | ✅ | 客户端写的审计不是审计 |
| 17 | 输出审核 | ⚠️ 展示提示 | ✅ 判定 | 判定逻辑不可下放 |
| 18 | 撤回 / 更正 | ✅ 执行替换 | ✅ 决策 | 决策在服务端，执行在端 |
| 19 | 灰度开关 | ⚠️ 只读缓存 | ✅ | 端只是开关的执行者 |
| 20 | 评测与质量指标 | ❌ | ✅ | 需要全量视角 |
| 21 | 多轮会话状态 | ⚠️ 展示用快照 | ✅ 真相源 | 见 §5.4.4 |
| 22 | 用户身份与租户归属 | ❌ | ✅ | 端只能提供凭据，不能声明身份 |
| 23 | 附件解析（PDF/图片） | ⚠️ 预压缩 | ✅ 解析与脱敏 | 解析器更新频繁且要在可信侧 |
| 24 | 人机审批（弹窗） | ✅ 交互 | ✅ 判定与留痕 | 见第 34 章 |

**这张表里唯一看起来有争议的是第 5 项：客户端工具。** 它恰恰是最重要的设计点，单独说：

> **工具的执行位置，应该由「数据在哪里」决定，不是由「代码方便」决定。**
>
> - 数据在用户设备上（本地文件、本地 DB、剪贴板）→ **端侧执行**，服务端只做「意图声明 + 结果校验 + 审计」。Claude Code 就是这个形态的极端版：CLI 在你机器上，`Bash`/`Read`/`Edit` 全在本地跑，模型在云端。
> - 数据在服务端（订单、知识库、内部 API）→ **服务端执行**，凭证不出服务端。
> - 需要用户在场授权（摄像头、支付确认）→ **端侧执行 + 服务端留痕**。

### 5.4.2 四种部署形态的取舍矩阵

| 维度 | ① 同进程 SDK | ② 边车 Sidecar | ③ 独立集群 | ④ Serverless |
| --- | --- | --- | --- | --- |
| 首次接入成本 | **最低**（加个依赖） | 中（改部署描述） | 高（要对接协议） | 低 |
| 单跳延迟 | **0** | +0.3~0.8 ms（localhost） | +2~8 ms（跨 AZ） | +20~80 ms（冷启动除外） |
| 多租户隔离 | ❌ 无 | ⚠️ 弱（每人一套配置） | ✅ 强 | ⚠️ 平台能力决定 |
| 限流 / 配额 | ❌ 靠自觉 | ✅ 本地 + 中心 | ✅ | ✅（网关层） |
| 计费与账本 | ❌ | ✅ | ✅ | ✅ |
| 审计 | ❌ | ✅ | ✅ | ⚠️ 受执行时长限制 |
| 密钥保护 | ❌ **最大风险** | ✅ | ✅ | ✅ |
| 统一升级 / 灰度 | ❌ 各自为政 | ✅ | ✅ | ✅ |
| 冷启动 | 无 | 无 | 无 | **50 ms ~ 3 s** |
| 长任务（>30 min） | ⚠️ 受自身进程限制 | ⚠️ | ✅ | ❌ 基本不行 |
| 流式长连接 | ⚠️ 自己扛 | ✅ | ✅ | ⚠️ 有执行时长上限 |
| 单位成本（相对） | 1.0× | 1.15× | 1.3× | 0.6~1.8×（看流量形态） |
| 适用场景 | **本地工具、原型、单租户私有部署** | 已有 K8s 体系、想最小改造 | **SaaS 主形态** | 突发流量、边缘轻任务 |

选择判据只有三条，按顺序问：

```
Q1 这个 Agent 会碰「多租户 + 钱 + 合规」中的任意一项吗？
   ├─ 是 → 必须 ②③④，排除 ①
   └─ 否 → ① 可用（例如：私有化单租户部署、内部工具、纯本地助手）

Q2 单次 Run 会超过 5 分钟吗？
   ├─ 是 → 必须 ③（或 ②+③ 混合），排除 ④
   └─ 否 → 继续

Q3 你能承受 50ms~3s 的冷启动吗？流量是否高度突发？
   ├─ 突发且能忍 → ④，但长连接与流式要另设网关
   └─ 稳态 → ③
```

**Aurora 的选择是 ③ + ②的混合**：对外的 SaaS 走 ③ 独立集群；对「客户私有化部署」这个形态提供 ② 边车（客户自己的 K8s 里跑我们的 proxy，模型凭证由我们签发短 TTL token）；本地 IDE 插件类场景提供 ①（但只放开「本地工具 + 只读检索」，模型调用仍走 ③）。

### 5.4.3 Go：协议契约与重连

```go
// proto/v1/run.go —— Agent-Server 对外协议（本平台定义，非任何厂商 API）
package v1

type CreateRunRequest struct {
	SessionID string   `json:"session_id,omitempty"` // 空 = 新会话
	Agent     AgentRef `json:"agent"`                // {name, version}
	Input     Input    `json:"input"`
	Stream    bool     `json:"stream"`
	Client    Caps     `json:"client"`               // 客户端能力声明
	// Idempotency-Key 从 HTTP header 取，不进 body（避免被日志打出来）
}

type Caps struct {
	ProtocolVersion string   `json:"protocol_version"` // "2026-01-15"
	LocalTools      []string `json:"local_tools"`      // 端能执行的工具名
	MaxEventBatch   int      `json:"max_event_batch"`  // 端能接受的合批大小
	ResumeSupported bool     `json:"resume_supported"`
}

type CreateRunResponse struct {
	RunID     string `json:"run_id"`
	EventURL  string `json:"event_url"`  // 相对路径，SSE
	CancelURL string `json:"cancel_url"`
	ExpiresAt int64  `json:"expires_at"` // 事件保留窗口，超过无法续传
}

// ToolResult 是客户端工具回传。注意：服务端必须校验，不能信任。
type ToolResult struct {
	RunID     string          `json:"run_id"`
	StepID    string          `json:"step_id"`
	CallID    string          `json:"call_id"`
	OK        bool            `json:"ok"`
	Payload   json.RawMessage `json:"payload"`
	DurationMS int64          `json:"duration_ms"`
	// 客户端签名：证明结果来自被授权的那个客户端实例
	ClientSig string          `json:"client_sig"`
}
```

```go
// client/reconnect.go —— 断线续传是 Client 的职责，但要 Server 配合
func (c *Client) followEvents(ctx context.Context, runID, eventURL string) error {
	var lastID string
	backoff := 200 * time.Millisecond

	for attempt := 0; attempt < 8; attempt++ {
		req, _ := http.NewRequestWithContext(ctx, "GET", eventURL, nil)
		req.Header.Set("Accept", "text/event-stream")
		if lastID != "" {
			req.Header.Set("Last-Event-ID", lastID) // ← 服务端从 lastID+1 继续发
		}
		resp, err := c.hc.Do(req)
		if err != nil || resp.StatusCode != 200 {
			time.Sleep(jitter(backoff))
			backoff = min(backoff*2, 8*time.Second) // 指数退避 + 抖动，防重连风暴
			continue
		}
		// 读到 EOF 说明服务端关闭（滚动更新/超时），同样走续传
		if id, err := c.consumeSSE(resp.Body); err == nil && id != "" {
			lastID = id
			attempt = 0
		} else {
			lastID = c.lastSeen
		}
	}
	return ErrGiveUp
}
```

### 5.4.4 协议形态：两种状态模型的抉择

这是协议设计里唯一真正难的选择，也是 OpenAI 和 Anthropic 走了两条不同路的地方：

| 模型 | 代表 | 每次传输量 | 前缀缓存友好度 | 服务端治理成本 | 断线续传 | 合规删除 |
| --- | --- | --- | --- | --- | --- | --- |
| **服务端持有状态** | OpenAI Responses API（`store` + `previous_response_id`，`background` 支持长任务） | 只传增量 | ✅ 好（服务端拼前缀） | 高（要存、要过期、要被删） | ✅ 易 | 要级联删 |
| **客户端持有全量** | Anthropic Messages API（每次传完整 `messages` 数组） | 每轮全量 | ⚠️ 依赖客户端保持前缀字节级稳定 | 低（服务端无状态） | ⚠️ 要客户端持久化 | 易（不存就没有） |
| **混合（Aurora 选这个）** | 客户端持有 + 服务端存事件快照 | 增量 + 校验指针 | ✅ | 中 | ✅ | 有明确删除路径 |

算一下「客户端持有全量」在 Aurora 规模的带宽账：

```
44,000 token，中文为主按 2.4 字节/token ≈ 105 KB
第 2~5 轮全量重传 = 105 × 4 ≈ 420 KB 冗余 / Run
日均 216 万 Run × 420 KB ≈ 907 GB / 日 的纯重复上行
```

**接近 1 TB/日的重复流量，换来的只是「服务端无状态」这一个好处。** 这就是 Aurora 选混合模型的原因：上下文由服务端从事件重建（省带宽、保缓存），但客户端持有一个 `context_version` 指针，用来做一致性校验和断线续传。

```yaml
    credentials: server_issued_short_lived   # 短 TTL (15min) token，不下发模型 key
    quota: center_ledger
    streaming: { transport: sse, resume: true, event_ttl_hours: 24 }

  on_prem_enterprise:                # 私有化：边车
    form: sidecar
    sidecar:
      image: registry.aurora.example/agent-proxy:2026.02
      listen: 127.0.0.1:18080
      upstream: https://gw.aurora.example
      local_limits: { qps: 500, inflight: 200 }   # 本地桶，允许超发 5%
    credentials: short_lived_token    # 由客户 K8s 里的 agent-proxy 轮换

  ide_plugin:                        # IDE 插件：SDK + 本地工具
    form: in_process_sdk
    allowed_tools: [read_file_local, grep_local, run_local_command]
    model_calls: via_saas             # 关键：模型调用仍走独立集群，SDK 不持有 key
    max_run_seconds: 600

  edge_light:                        # 边缘轻任务：Serverless
    form: serverless
    runtime: edge_worker
    max_run_seconds: 25               # 硬限制，超时强制转异步
    streaming: { transport: sse, resume: false }  # 边缘不支持续传
```

注意 `ide_plugin` 那一段的 `model_calls: via_saas`——**「同进程 SDK」不等于「凭证在本地」**。形态和凭证策略是两个正交的维度，很多团队把它们混为一谈，结果就是 §5.1 那个账单。

## 5.5 Java / 分布式经验对照

| 你的经验 | 迁移判断 | 会咬人的地方 |
| --- | --- | --- |
| BFF 模式（Backend for Frontend） | 🟢 几乎同构 | BFF 聚合的是数据；Agent-Server 还要「持有状态 + 推事件」 |
| 客户端 SDK vs 服务端 SDK | 🟢 直接可用 | 但 Agent 的「客户端 SDK」往往要承担**工具执行**，等于半个 runtime |
| 前后端分离（REST） | 🟡 要改造 | 一次 Run 30 秒，REST 的「请求-响应」模型不成立，必须事件流（第 7 章） |
| 移动端「无状态 + token 刷新」 | 🟢 直接可用 | token 要绑定 `client_instance_id`，且要能单独吊销（第 32 章） |
| 「本地缓存 + 乐观更新」 | 🟢 直接可用 | 但 Agent 的「乐观更新」可能是错的（模型会撤回），必须有 correction 事件（第 37 章） |
| 灰度按「版本 + 用户分桶」 | 🟡 要改造 | 端侧无法保证同一用户始终命中同一版本 → 灰度必须由服务端在 Run 级决定 |
| 单点登录 / OAuth | 🟢 直接可用 | 但「用户身份」和「Agent 代表用户能做什么」是两层（能力令牌，第 30 章） |

有一条特别值得单拎出来：**Java 世界里「客户端只是展示层」的假设，在 Agent 场景会被打破。** 因为客户端持有**数据和执行能力**（本地文件、本地命令），它不是哑终端，是**有能力的主体**。所以协议里必须有一种「服务端请求客户端执行某个动作」的消息——这在你熟悉的前后端分离里是不存在的。

## 5.6 开源坐标

| 参照 | 形态 | 它做对了什么 | 它把什么留给你 |
| --- | --- | --- | --- |
| **OpenAI Responses API** | 独立服务 + 服务端持有状态 | 把 Run 建成**资源**（可查、可取消、可 `background`），`previous_response_id` 让客户端不用重传全量；事件流有明确的事件名与顺序 | 多租户、配额、审计、私有部署 |
| **Anthropic Messages API** | 纯无状态 | 协议极简、客户端完全掌控上下文，天然适合「上下文工程」自己做 | 状态管理全在你这（要自己存 `messages` 并保证前缀稳定才能吃到 cache） |
| **Cursor** | 混合（IDE 客户端 + 后端） | 本地做索引与编辑（数据不出端），模型调用走自己的后端（密钥不出服务端）——**教科书式的正确切分** | 编排、工具治理 |
| **Claude Code** | CLI 宿主 + 云端模型 | 工具（`Bash`/`Read`/`Edit`）全在本地执行，权限提示在本地，模型在云端；**「数据不出端」做到了极致** | 企业级统一审计、跨设备续传 |
| **MCP** | 协议层 | 用 JSON-RPC 2.0 统一了「工具在哪」：server 可以在本地（stdio）也可以在远端（Streamable HTTP），**位置对调用方透明** | 权限、配额、审计仍要自己加 |
| **AG-UI** | 前端事件协议 | 定义了「Agent 与前端之间的事件类型」（文本增量、工具调用、状态） | 服务端治理 |

> 🎯 一个判断：**这五个参照里，没有一个同时解决了「不可信客户端 + 多租户 + 可审计」三件事。** 因为它们各自的定位不同：Responses API 是模型厂商的接口，Cursor/Claude Code 是产品，MCP 是协议。三件事同时成立，只能是平台自己设计——这就是本章后面几章（第 6-9 章）要做的。

## 5.7 事故清单

- [ ] **事故 1：Key 打进客户端。** 现象：§5.1 的 $212k。→ 根因：无强制边界。→ 兜底：客户端只拿短 TTL（15 min）的**代理 token**，模型 key 永不出服务端；token 绑定 `client_instance_id` + 设备指纹，可单点吊销；出站流量按「非代理」告警。
- [ ] **事故 2：客户端工具结果被伪造。** 现象：用户用抓包工具把「删除文件」的结果改成「成功」，Agent 继续执行下一步。→ 根因：服务端信任了客户端。→ 兜底：工具结果必须带客户端签名 + 服务端对高危工具做二次确认（第 34 章）。
- [ ] **事故 3：重连风暴。** 现象：一次反代抖动，8 万客户端同时重连，网关被打挂。→ 根因：无退避、无抖动、无 `Last-Event-ID` 服务端限流。→ 兜底：指数退避 + 抖动（§5.4.3）；服务端按 `run_id` 做重连令牌桶；续传请求优先级低于新建。
- [ ] **事故 4：边车版本漂移。** 现象：私有化客户的边车还是 8 个月前的版本，接口不兼容。→ 根因：形态分离后缺少版本协商。→ 兜底：协议版本进 `Caps.ProtocolVersion`；服务端支持 N-2 个版本；边车启动时自检并上报版本。
- [ ] **事故 5：Serverless 长任务被截断。** 现象：数据分析 Agent 在边缘跑了 28 秒被强制终止。→ 根因：形态与任务时长不匹配。→ 兜底：`max_run_seconds` 硬限制 + 超时自动转「异步 Run + 事件推送」，客户端无感。
- [ ] **事故 6：多端行为不一致。** 现象：Web 上能审批，App 上审批按钮不出现，Run 一直挂着。→ 根因：能力协商缺失。→ 兜底：`Caps` 里声明能力，服务端按能力裁剪事件与动作；缺能力时给「请到 Web 完成」的明确提示，而不是静默挂起。

## 5.8 一页速记

| 关键词 | 必须记住的结论 |
| --- | --- |
| 分离的本质 | 不是部署问题，是「谁能被信任」的问题 |
| 一句判据 | 伪造了能赚钱/害人的 → 服务端；离开设备没意义的 → 客户端 |
| 密钥 | 永不进客户端；客户端只拿 15 分钟短 TTL 的代理 token |
| 行为定义 | 提示词、角色卡、路由、配额全部住服务端；否则迭代慢 80 倍 |
| 工具归属 | 由「数据在哪」决定，不由「代码方便」决定 |
| 四形态 | 同进程 SDK（延迟 0 / 无治理）、边车（+0.5ms / 可治理）、独立集群（+5ms / 全治理）、Serverless（+50ms~3s / 长任务不行） |
| 选择顺序 | 多租户+钱+合规? → 长任务? → 突发行? 三问定形态 |
| 状态模型 | 服务端持有（省带宽、易续传）vs 客户端持有（无状态、难续传）；Aurora 选混合 |
| 带宽账 | 客户端全量重传 = 907 GB/日 的纯浪费 |
| 一句话 | **客户端是「有能力的主体」，不是哑终端——协议里必须有「服务端请客户端执行」这条路。** |

## 5.9 自检题

1. **「我们做的是 IDE 插件，Agent 跑在用户机器上，所以不需要 Agent-Server。」这句话对不对？**
   > 要点：要看三件事。① 模型密钥在哪？在插件里 → 错，必须走服务端代理。② 配额与计费在哪？在本地 → 可伪造，等于没有。③ 提示词与角色卡在哪？在插件包里 → 泄露且不可灰度。Claude Code 的正确姿势是「工具在本地、模型在云端」：数据不出端（合规），凭证不出服务端（安全）。所以答案是：**Agent 可以在本地跑，但「可信域」必须有一块在服务端。**

2. **四种部署形态，为什么「独立集群」几乎总是 SaaS 的最终形态？**
   > 要点：因为治理能力（限流/配额/账本/审计/灰度）只有在**请求必经之地**才能实施。同进程 SDK 没有必经之地；边车有但每客户一套、版本会漂移；Serverless 有但受执行时长与长连接限制。独立集群是唯一能同时满足「统一治理 + 长任务 + 流式长连接 + 集中灰度」的形态。代价是多一跳（2~8 ms）——相对于 30 秒的 Run，这一跳不到 0.03%。

3. **为什么「客户端持有全量上下文」在 Aurora 被否决，但在 Anthropic Messages API 里是默认？**
   > 要点：因为约束不同。Messages API 是**无状态协议**，它把状态管理的责任交给调用方——这对单租户、单机、自己做上下文工程的场景是最灵活的（你能完全控制前缀字节，从而吃满 prompt cache）。而 Aurora 是多租户平台：216 万 Run/日 × 420 KB 冗余 ≈ 907 GB/日 的纯重复上行；且要支持断线续传、合规删除、跨设备切换——这些都需要服务端有状态。所以 Aurora 选混合：**服务端从事件重建上下文，客户端只持一个版本指针。**
