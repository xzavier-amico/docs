## 24.1 引子：一条被缓存了 6 小时的错误答案

周三 11:02，Aurora 客服租户「星辰零售」的投诉群里炸了。截图是这样的：

```
用户：我买的耳机退款能退多少？
客服 Agent：退款将在 3-5 个工作日内原路退回，请耐心等待。
用户：我问的是**金额**，不是时间。
客服 Agent：退款将在 3-5 个工作日内原路退回，请耐心等待。
```

第一次是模型答偏了；第二次是**缓存命中**——把上一个用户问「退款多久到账」的答案，返回给了一个问「退多少钱」的用户。语义相似度 **0.94**，超过阈值 0.92，缓存认为「同一个问题」。

这还算轻的。同一周另一个更吓人的 case：

```
用户 A（租户甲）：帮我查下我最近那笔订单到哪了
  → 工具结果被缓存，key = hash("查下最近订单物流")
用户 B（同一租户，另一个账号）：同样的问题
  → 命中缓存，看到了用户 A 的订单号、收货地址、手机号后四位
```

**这是数据泄露，不是 bug。** 根因只有一个：缓存 key 里没有 `user_id`，也没有 `tenant_id` 之外的权限上下文。

两件事的成本账完全不同：

| 事件 | 发生量 | 单次代价 | 日损失 |
| --- | --- | --- | --- |
| 语义误命中（答非所问） | 语义命中 17% × 误命中 0.6% × 80 万 Run | 重跑 + 工单 ≈ $2.5 | **≈ $2,040/天** |
| 跨用户缓存泄露 | 只要 key 设计错，就是 100% | 合规事故，不可计价 | 一次性事故 |
| 而缓存带来的收益 | 命中率 20% | 每 Run 省 $0.078 | **$12,480/天** |

> 🎯 这就是本章的全部张力：**缓存一天省 1.2 万美元，也能一天赔掉一个客户。** 所以缓存设计的重点不是「怎么提高命中率」，而是「**命中的时候，我凭什么确定这是同一个人、同一个问题、同一个版本的答案**」。

## 24.2 断崖：四层缓存，四种不同的失败方式

| 层 | 缓存什么 | 典型命中率 | 省什么 | 失败方式 | 严重度 |
| --- | --- | --- | --- | --- | --- |
| **L1 精确缓存** | 完全相同的请求（规范化后 hash 相等） | 8~12% | 整次 LLM 调用 | key 少字段 → 串话 | 🔴 泄露级 |
| **L2 语义缓存** | 语义相近的问题 → 复用答案 | 10~25% | 整次 LLM 调用 | **误命中** → 答非所问 | 🟠 质量级 |
| **L3 前缀 KV** | system + tools + 历史前缀的 KV | 40~80% | 输入 token 的 90% | 前缀被打穿 → 命中率归零 | 🟡 成本级 |
| **L4 工具结果** | 读工具返回（订单/商品/物流） | 20~60% | 工具延迟 + 上下文 token | 数据过期 / 跨用户 | 🔴 正确性级 |

四层里，**L3 是唯一「几乎没有风险、收益又最大」的**，L2 是「收益中等、风险最高」的，L1 和 L4 的风险全部来自 key 设计。

先给结论，后面展开：

```
ROI 排序（先做哪个）：
  L3 前缀 KV（改提示词结构，零风险）      ★★★★★
  L1 精确缓存（key 设计对就行）            ★★★★
  L4 工具结果（TTL 短、只缓存只读）        ★★★
  L2 语义缓存（默认关，白名单开）           ★★
```

## 24.4 关键设计

### 24.4.1 缓存键规范：七个字段，少一个就是事故

这是全章最该背下来的一张表。**key 不是「请求的 hash」，是「所有能让答案不同的因素的 hash」。**

| # | 字段 | 为什么必须在 key 里 | 漏了会怎样 |
| --- | --- | --- | --- |
| 1 | `tenant_id` | 多租户隔离 | **跨租户数据泄露**（合规事故） |
| 2 | `user_id` / 权限上下文 | 同租户不同用户看到的数据不同 | 同租户跨用户泄露（本案 24.1） |
| 3 | `agent_id` + `persona_version` | 角色卡变了，语气/边界都变了 | 客服角色返回销售角色的口径 |
| 4 | `model_family` + `model_version` | 换模型后答案分布不同 | 灰度期新旧模型互相污染 |
| 5 | `prompt_version`（system+template） | 提示词改了，答案必须重算 | 改了 prompt 但答案没变（最迷惑的 bug） |
| 6 | `tools_version` | 工具集/工具 schema 变了 | 缓存的答案引用了已下线工具 |
| 7 | `retrieval_index_version` | 知识库更新了 | 旧政策答案持续命中（政策类事故） |

```go
// cache/key.go —— 唯一允许构造缓存 key 的地方
type KeyInput struct {
    TenantID       int64
    UserScope      string // user:<id> 或 role:<id>，匿名用户用 device 指纹
    AgentID        string
    PersonaVersion string
    ModelFamily    string
    ModelVersion   string // 精确版本号，不是 "latest"
    PromptVersion  string
    ToolsVersion   string
    IndexVersion   string
    PolicyVersion  string // 退款/合规政策版本，政策变了必须全失效
    NormalizedQ    string // 规范化后的查询（去空白、统一大小写、去标点）
    Params         string // temperature/max_tokens/top_p 等影响输出的参数
}

func (k KeyInput) L1Key() string {
    // 用长度前缀拼接，避免 "ab"+"c" 与 "a"+"bc" 碰撞
    var b strings.Builder
    for _, f := range []string{
        "v2", strconv.FormatInt(k.TenantID, 10), k.UserScope, k.AgentID,
        k.PersonaVersion, k.ModelFamily, k.ModelVersion, k.PromptVersion,
        k.ToolsVersion, k.IndexVersion, k.PolicyVersion, k.Params, k.NormalizedQ,
    } {
        b.WriteString(strconv.Itoa(len(f)))
        b.WriteByte(':')
        b.WriteString(f)
        b.WriteByte('|')
    }
    sum := sha256.Sum256([]byte(b.String()))
    return "c1:" + hex.EncodeToString(sum[:16]) // 128bit 足够，且省内存
}
```

三条硬规矩：

1. **key 只能由 `KeyInput` 构造，禁止任何地方手拼字符串**。手拼是漏字段的唯一来源。
2. **`ModelVersion` 必须是精确版本**（`gpt-x-2026-01-15`），不能是 `latest`。用 `latest` 意味着供应商静默升级会污染缓存（第 42 章）。
3. **key 前缀带 schema 版本**（`c1:`）。key 结构升级时改前缀，等于一键全量失效。

### 24.4.2 前缀 KV：不是「缓存」，是「别把前缀写坏」

L3 跟 L1/L2 完全不是一类东西：它不需要你存任何东西，**你只需要保证每次请求的前 N 个 token 字节级相同**。命中后输入 token 按折扣计费（Anthropic 的 `cache_control` 是显式标记，OpenAI 是自动前缀匹配，具体规则以各自官方文档最新版为准）。

前缀缓存有 **三个杀手**，全是「无意的字节差异」：

| 杀手 | 现象 | 为什么致命 | 修法 |
| --- | --- | --- | --- |
| **时间戳放在最前** | `当前时间：2026-05-01T10:23:41Z` 写在 system 第一行 | 每秒都不同 → 命中率 **0%** | 时间放最后，或只精确到「日」 |
| **map 遍历顺序不定** | Go 的 `range map` 顺序随机 → 工具定义 JSON 每次字段序不同 | 前缀看似一样，hash 不同 → 命中率 **0%** | 工具/schema 用**切片**保序，JSON 用有序编码 |
| **动态内容提前** | 用户信息、检索片段插在 history 前面 | 每次请求都不同 → 只有 system 那 300 token 命中 | 固定顺序：system → tools → persona → few-shot → **然后**才动态 |

第二条是 Go 团队最容易踩的，因为 Java 的 `HashMap` 至少在同一个 JVM 里顺序稳定，而 Go 的 map 迭代顺序是**故意随机化**的：

```go
// ❌ 灾难：每次序列化的字段顺序不同，前缀缓存永远打不中
type ToolSet map[string]ToolSpec

// ✅ 正确：切片保序 + 显式字段顺序
type ToolSet struct {
    Tools []ToolSpec `json:"tools"` // 注册时按 name 排序后固化
}

func (ts ToolSet) CanonicalJSON() []byte {
    sort.Slice(ts.Tools, func(i, j int) bool { return ts.Tools[i].Name < ts.Tools[j].Name })
    b, _ := json.Marshal(ts) // 结构体字段顺序由定义决定，稳定
    return b
}
```

实测数据（Aurora 客服场景，同一天）：

| 配置 | 前缀命中率 | 单 Run 输入成本 |
| --- | --- | --- |
| 时间戳在首位 + map 序列化 | 3% | $0.069 |
| 只修时间戳位置 | 41% | $0.043 |
| 再修 map 顺序 + 固定拼接顺序 | **78%** | **$0.029** |

**只改代码结构、零业务风险，成本降 58%。** 这是全书 ROI 最高的一次改动。

### 24.4.3 语义缓存：阈值实验（这一节请务必自己重跑一遍）

语义缓存的基本假设是「相似的问题有相同的答案」。这个假设在 **FAQ** 上成立，在**带实体、带条件、带数字**的问题上不成立。

Aurora 上线语义缓存（阈值 0.92）两周后，我们做了一次严格的抽样：每周随机抽 500 条语义命中，人工判定「答案是否适用于新问题」。结果：

| 阈值 | 语义命中率 | 误命中率（人工抽样） | 每 Run 净收益 | 结论 |
| --- | --- | --- | --- | --- |
| 0.90 | 31% | **4.8%** | 0.31×0.078 − 0.048×2.5 = **−$0.096** | 亏钱，且投诉 |
| 0.92 | 24% | 1.9% | 0.0187 − 0.0475 = **−$0.029** | 亏钱（当时就是这个） |
| 0.95 | 17% | 0.6% | 0.0133 − 0.015 = **−$0.002** | 打平，不值得 |
| 0.96 | 14% | 0.3% | 0.0109 − 0.0075 = **+$0.003** | 微赚 |
| 0.97 | 11% | 0.15% | 0.0086 − 0.0038 = **+$0.005** | 赚 |
| 0.99 | 4% | 0.02% | 0.0031 − 0.0005 = +$0.003 | 赚但量太小 |

（收益按「每次命中省 $0.078 / 每次误命中损失 $2.5（重跑 + 工单 + 信任折损）」计。）

看这张表你会得出一个反直觉的结论：**语义缓存的甜点区极窄，而且默认应该是关的。** 因为误命中的代价是命中的 32 倍（2.5 / 0.078），所以误命中率必须压到 1/32 以下才有正收益——这要求阈值高到 0.96 以上，而那时候命中率只剩 14%。

所以我们的最终形态是 **「按场景白名单 + 高阈值 + 答案可验证」**：

```yaml
# policy/semantic_cache.yaml
semantic_cache:
  default: off                     # 全局默认关闭
  whitelist:                       # 只在这些 intent 上开启
    - intent: faq_shipping_time   # 「发货多久到」——同义改写高频、答案稳定
      threshold: 0.97
      max_answer_tokens: 200       # 答案越长，误命中越贵
      ttl: 24h
      require_entities_match: []   # 无实体，安全
    - intent: faq_return_policy
      threshold: 0.97
      ttl: 24h
      require_entities_match: [product_category]   # 类目不同的政策不同！
  blacklist:                       # 绝对不缓存
    - any_with_entity: [order_id, user_id, amount, date]  # 带实体的问答永不语义缓存
    - intent: refund_amount        # 退款金额（24.1 的事故）
    - any_write_action: true       # 任何会导致写操作的
  verify_hit: sample_rate 0.05     # 5% 命中抽样进人工复核队列
```

`require_entities_match` 是关键：两个问题相似度 0.98，但一个问「iPhone 的退货政策」、一个问「生鲜的退货政策」——实体不同，答案必须不同。**实体抽取比对，比相似度阈值可靠得多。**

> ⚠️ 另外一条：**误命中率必须人工测，不能让模型自评。** 用 LLM 判断「这个答案适用吗」，它倾向于说「适用」（因为答案看起来很合理），实测会把 4.8% 的误命中率报成 0.9%。

### 24.4.4 失效与一致性：用「版本」失效，别用「删除」

传统缓存靠 TTL + 主动删除。Agent 平台里，**版本号驱动失效比删除可靠一个数量级**：

| 变更 | 失效方式 | 为什么不用删除 |
| --- | --- | --- |
| 提示词改版 | `prompt_version` v37→v38 → key 天然不同 | 删除要遍历所有 key，10 万租户 × N 场景根本删不干净 |
| 模型升级 | `model_version` 固定到日期版本 | 同上；且旧 key 留着做双跑对比更有价值 |
| 知识库更新 | `index_version` bump | 增量索引期间新旧并存是特性，不是 bug |
| 政策变更（退款规则） | `policy_version` bump + **全量强制失效** | 这一条必须删，因为要「立刻生效」 |
| 用户数据变更 | TTL（30s~5min） | 无法枚举依赖，只能靠短 TTL |

TTL 分层（拍脑袋定 TTL 是最常见的错误）：

| 层 | 数据特征 | TTL | 理由 |
| --- | --- | --- | --- |
| L1 对话内 | 多轮追问，秒级 | 5 min | 用户改一个字就 miss，长 TTL 无收益 |
| L1 FAQ | 无实体、政策类 | 24 h + `policy_version` | 政策变更时靠版本失效 |
| L2 语义 | 同 L1 FAQ | 1~24 h | 同上 |
| L4 商品/物流 | 会变但可容忍 | 30 s ~ 5 min | 用户查物流希望是「刚才的」 |
| L4 用户资料 | 强一致要求 | **不缓存** | 权限相关，宁可不省 |

**TTL 必须加抖动**（`ttl × (0.9 + rand×0.2)`），否则 80 万 Run/天在整点集中过期 → 缓存雪崩 → 瞬时全量打模型（第 25 章的重试风暴同源）。

### 24.4.5 三个经典穿透问题的 Agent 版

| 问题 | 传统解法 | Agent 版要加什么 |
| --- | --- | --- |
| **击穿**（热点 key 过期瞬间） | singleflight / 分布式锁 | 加「请求合并 + 排队」，因为一次 LLM 调用 3~8 秒，合并收益极大 |
| **穿透**（查不存在的 key） | 空值缓存 | 空值也要**带租户**，且 TTL ≤ 60s（模型可能刚学到新知识） |
| **雪崩**（大批 key 同时过期） | TTL 抖动 + 多级缓存 | 加「缓存预热」：灰度发布前预热 top 1,000 高频问题 |

```go
// 击穿防护：同一 key 的并发请求只放一个到模型，其余等结果
var g singleflight.Group

func (c *Cache) GetOrFill(ctx context.Context, key string, fill func() (Answer, error)) (Answer, error) {
    if v, ok := c.redis.Get(ctx, key); ok { return v, nil }
    v, err, _ := g.Do(key, func() (any, error) {
        if v, ok := c.redis.Get(ctx, key); ok { return v, nil } // 双检
        a, err := fill()
        if err != nil { return Answer{}, err }
        c.redis.SetEX(ctx, key, a, jitter(5*time.Minute)) // 抖动 ±10%
        return a, nil
    })
    if err != nil { return Answer{}, err }
    return v.(Answer), nil
}
```

> 🩸 注意 `singleflight` 是**进程内**的。1.8 万并发 Run 分布在 80 个副本上，跨副本仍需分布式锁或「只允许 1 个副本回源」（对超热 key 才值得）。别为了一个 key 的击穿引入全局锁——那是拿一个 0.1% 的问题换一个 100% 的单点。

### 24.4.6 命中率-成本的数学关系

把四层串起来，单 Run 期望成本：

```
E[C] = (1 - h₁)(1 - h₂) · [ c_in · (1 - h₃·d) + c_out ]

  h₁ = L1 精确命中率          h₂ = L2 语义命中率
  h₃ = 前缀命中率（占输入 token 比例）   d = 前缀折扣（Anthropic 约 0.9，即只付 10%）
  c_in  = 输入成本 = tokens_in  / 1e6 × 输入单价
  c_out = 输出成本 = tokens_out / 1e6 × 输出单价
```

代入 Aurora 客服（`tokens_in=28k`、`tokens_out≈1,100`（800 汉字）、输入 $2.5/M、输出 $10/M）：

```
c_in  = 28,000/1e6 × 2.5  = $0.070
c_out = 1,100/1e6 × 10    = $0.011
基线（无缓存）= 0.070 + 0.011 = $0.081

只开 L3，h₃=0.78：
  c_in_eff = 0.070 × 0.78 × 0.1 + 0.070 × 0.22 = 0.0055 + 0.0154 = $0.0209
  E[C] = 0.0209 + 0.011 = $0.0319          → 降 61%

再开 L1(h₁=0.10) + L2(h₂=0.14)：
  E[C] = 0.9 × 0.86 × 0.0319 = $0.0247     → 降 69%

日账（80 万 Run）：
  无缓存  80万 × 0.081 = $64,800/天
  四层全开 80万 × 0.0247 = $19,760/天     → 省 $45,040/天 ≈ $135 万/月
```

两个可以直接拿去用的判据：

1. **每提升 1 个百分点的前缀命中率，省约 `0.070 × 0.01 × 0.9 = $0.00063/Run`**，即日省 **$504**。这就是为什么「修 map 顺序」这种小事值得做。
2. **`h₁ + h₂` 每提升 1 个百分点，省 `0.032 × 0.01 = $0.00032/Run`**，只有前缀缓存的一半。**先做 L3，再做 L1，最后才纠结 L2。**

## 24.5 Java / 分布式经验对照

| 你的经验 | AgentOS 对应物 | 判断 | 会咬人的地方 |
| --- | --- | --- | --- |
| Redis + `@Cacheable` | L1 精确缓存 | 🟢 直接迁移 | key 必须含 7 个版本/权限字段，Spring 的 `key="#id"` 是灾难 |
| Caffeine 本地缓存 | L1 前置于 Redis | 🟢 直接迁移 | 本地缓存无法主动失效 → 只能放「不可变 + 版本化」的数据 |
| 缓存穿透/击穿/雪崩三件套 | 同 | 🟢 直接迁移 | LLM 回源 3~8 秒，合并收益比 DB 回源（5ms）大 1000 倍 |
| Guava `hash` 拼 key | key 构造 | 🟡 要改造 | 必须防拼接碰撞（`"ab"+"c"` vs `"a"+"bc"`），用长度前缀 |
| HashMap 序列化做 key | schema 序列化 | 🔴 **负债** | Go 的 map 顺序随机；Java 里换了字段/版本也会漂移 |
| 「缓存不一致就删 key」 | 失效策略 | 🟡 要改造 | 版本化 key 比删除可靠；删除只用于「必须立刻生效」的政策类 |
| 语义缓存（新东西） | L2 | 🔴 **高危** | 传统缓存不会「相似就命中」；这里的误命中是概率性的、批量性的 |
| CDN / 多级缓存 | L3 前缀 KV | 🟡 概念同构 | 但 L3「缓存」的是 KV 块，命中条件苛刻到字节级 |

## 24.6 开源坐标

| 项目 | 对应 | 能用 | 缺什么 |
| --- | --- | --- | --- |
| **Anthropic prompt caching**（`cache_control`）/ **OpenAI 自动前缀缓存** | L3 | ✅ 直接开，收益立刻可见 | 规则/最小块大小/折扣以官方文档最新版为准；你控制不了它的淘汰 |
| **vLLM prefix caching**（自建推理） | L3 | ✅ 自建模型时必开 | 需要自己算命中率与调度影响（第 14 章） |
| **GPTCache** | L2 语义缓存 | ⚠️ 概念参考 | 阈值/误命中治理几乎不管；embedding 与向量库要自建 |
| **Redis**（Redis Stack / 向量检索） | L1 + L2 存储 | ✅ 首选 | 向量检索性能与规模有限，大库要独立向量库（第 45 章） |
| **Helicone / Langfuse** | 命中率观测 | ✅ 能看到 hit/miss | 不提供 key 设计约束，误命中也测不出来 |
| **LiteLLM**（`caching` 配置） | L1 简单缓存 | ⚠️ 可做原型 | key 维度少，多租户与版本维度要自己加 |

> 🎯 一句话：**L3 直接用供应商能力（改结构就行），L1 自己写（key 必须自己控），L2 谨慎开（收益被误命中吃掉），L4 一定要带用户维度（否则是泄露）。**

## 24.7 事故清单

- [ ] **A. 语义误命中**：阈值 0.92，把「退款多久」的答案给了「退多少钱」。→ 根因：阈值过低 + 未做实体比对。→ 兜底：阈值 ≥0.96 + 白名单 + 实体匹配 + 5% 人工抽检。
- [ ] **B. 跨用户泄露**：L4 工具结果缓存 key 无 `user_id`，B 看到 A 的订单。→ 根因：key 设计缺权限维度。→ 兜底：KeyInput 强制字段 + 代码评审门禁 + 审计比对。
- [ ] **C. 前缀命中率归零**：时间戳写进 system 首行 + Go map 序列化。→ 根因：不知道前缀是字节级匹配。→ 兜底：固定拼接顺序 + 有序结构 + 上线前的「前缀稳定性」单测。
- [ ] **D. 缓存雪崩**：整点集中过期 → 瞬时 8 万 QPS 打模型 → 供应商 429。→ 根因：无 TTL 抖动。→ 兜底：抖动 ±10% + singleflight + 限流兜底（第 23 章）。
- [ ] **E. 灰度污染**：新模型灰度 5%，但缓存 key 用了 `latest` → 老模型命中新模型答案。→ 根因：`ModelVersion` 未精确化。→ 兜底：精确版本号进 key + 双跑隔离命名空间。
- [ ] **F. 政策变更未生效**：退款政策改了，旧答案继续被缓存命中 6 小时。→ 根因：只靠 TTL。→ 兜底：`policy_version` bump 触发全量强制失效（唯一必须「删」的场景）。

## 24.8 一页速记

| 关键词 | 必须记住的结论 |
| --- | --- |
| ROI 排序 | L3 前缀（零风险）> L1 精确 > L4 工具 > L2 语义（默认关） |
| key 七字段 | 租户/用户/角色卡/模型版本/提示词版本/工具版本/索引版本，少一个就是事故 |
| 前缀是字节级 | 时间戳前置、Go map 顺序、动态内容提前——三个杀手让命中率归零 |
| 修 map 顺序 | 命中率 3%→78%，单 Run 成本 $0.069→$0.029，纯代码改动 |
| 语义甜点区窄 | 误命中代价是命中的 32 倍，阈值必须 ≥0.96，命中率只剩 14% |
| 白名单 | 只在 FAQ（同义高频、答案短、无实体）开启；带 order_id/amount 的永不语义缓存 |
| 误命中要人工测 | LLM 自评会把 4.8% 报成 0.9% |
| 失效靠版本 | 改 `prompt_version` 而不是删 key；只有政策变更需要强制删 |
| TTL | 分层 + ±10% 抖动；权限相关数据不缓存 |
| 数学 | h₃ 每 +1pp 省 $504/天；h₁+h₂ 每 +1pp 只省 $252/天 |
| 一句话 | **缓存省的是钱，赌的是「这真的是同一个问题」——赌错一次，省的钱全赔进去。** |

## 24.9 自检题

1. **你的缓存命中率是 35%，老板问为什么不是 80%。你会先查哪三件事？**
   > 要点：① 前缀是否字节级稳定（时间戳位置、map 序列化顺序、动态内容是否提前）；② key 里是否混入了「每次请求都变」的字段（trace_id、时间戳、session_id、随机排序的检索片段）；③ 流量结构本身（长尾问题占比高、每用户个性化强，命中率天花板就低）。顺序很重要：先查可控的前两项，再谈业务天花板。

2. **语义缓存阈值调到 0.95 时命中率 17%、误命中 0.6%。这个配置赚钱吗？为什么？**
   > 要点：收益 0.17×$0.078=$0.0133，损失 0.006×$2.5=$0.015，**净亏**。因为误命中的代价是命中收益的 32 倍，误命中率必须 <1/32（约 3%）才打平——这需要阈值 ≥0.96 且加实体比对。结论：语义缓存不是「调阈值」的问题，是「选场景」的问题（白名单 + 答案可验证）。

3. **为什么说「删 key」在 Agent 平台里是最后手段？请给出一个必须删的场景。**
   > 要点：因为 key 由 7 个维度组成，10 万租户 × 多场景的 key 空间无法枚举，删除必然删不干净；版本化 key（改 `prompt_version`）让旧 key 自然失效。唯一必须「删」的是**政策/合规变更**——要求立即生效、不能等 TTL，此时用 `policy_version` bump + 按前缀批量 purge。
