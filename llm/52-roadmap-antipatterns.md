## 52.1 引子：一年后回看第一版路线图，三个决定是错的

Aurora 的第一版路线图（12 个月，16 人）长这样，当时所有人都觉得合理：

```
M1-M2  多 Agent 框架（supervisor + handoff + 辩论）
M3-M4  低代码搭建平台（拖拽 + DSL + 模板市场）
M5-M6  计费与套餐
M7-M8  可观测与看板
M9-M10 评测体系
M11-M12 安全与合规
```

12 个月后复盘，三个决定被证明是错的，而且**每一个都让我们多花了两个月**：

| 决定 | 当时的理由 | 实际发生了什么 | 正确的顺序 |
| --- | --- | --- | --- |
| **先做多 Agent** | 「这是差异化，客户会为复杂编排付钱」 | 单 Agent 的 Run 成功率只有 91%，多 Agent 把它变成 84%（错误会相乘）。**客户根本不关心你有几个 Agent，只关心答对率** | 先把**单 Run 的稳定性**做到 99.5%，多 Agent 放到 M9 之后 |
| **先做低代码** | 「业务自助能 scale 交付」 | 业务不用——因为**没有 trace，配错了看不出来**。平台组变成了「YAML 客服」，比写代码还累 | 先做 trace 与评测（M2-M3），低代码放 M6 |
| **评测放最后** | 「先把功能做出来，评测是锦上添花」 | 前 8 个月所有「效果变好了」的判断全靠感觉。M9 建评测集时发现：**过去 6 次提示词改版里有 4 次实际是变差的** | 第 2 个月就要有 100 条评测集，M3 到 200 条并接进 CI |

还有一件当时没想到的：**最大的工作量不在功能，在「治理」**。12 个月的实际投入分布：

```
功能开发（编排/低代码/多 Agent）      ████████            26%
治理（限流/降级/幂等/灰度/权限）      █████████████       34%
数据闭环（trace/评测/回流/看板）      ███████             22%
安全合规（沙盒/审计/防注入）          ████▌               11%
运维与救火                            ██▌                  7%
```

> 🩸 **本章的第一条判断**：**路线图最容易犯的错，是按「功能的有无」排序，而不是按「风险的暴露顺序」排序。** 正确顺序是：**先让一次 Run 可观测、可复现 → 再让它稳定 → 再让它便宜 → 最后才让它聪明**。反过来做，你会在一个有 12 个功能但成功率 91% 的系统上，花双倍时间补课。

## 52.2 三阶段路线图：能用 / 能扛 / 能赚

### 阶段一（M1-M3）：能用——「一个场景，一万次 Run，不出丑」

| 项 | 内容 |
| --- | --- |
| **唯一目标** | 一个真实场景（选**客服**或**内部知识问答**，别选编码）跑通，日 1 万 Run，**能对外演示且不出丑** |
| **P0 必做** | ① `Session/Run/Step/Event` 事件模型 + 落库（第 6 章）<br>② 流式输出（SSE）+ 首 token 指标（第 7、36 章）<br>③ **trace 三件套**：`llm.call` / `tool.call` / `retrieval` span，带模型版本、token、耗时（第 39 章）<br>④ 工具分级（读/写/高危）+ 写操作幂等键（第 22 章）<br>⑤ 前处理闸门（长度/编码/注入预检）+ 输出审核（第 35、30 章）<br>⑥ 超时预算表 + 最基础降级（大模型 → 兜底话术）（第 25 章）<br>⑦ **100 条评测集** + 手工跑（第 40 章）<br>⑧ 成本埋点（每个 Run 记 token 与成本，先不要求归因）（第 47 章） |
| **明确不做** | 多 Agent、低代码、语义缓存、自建推理、多租户计费、审计哈希链 |
| **验收指标** | Run 成功率 ≥ 95%（人工抽检 50 条）；TTFT P95 < 2.5s；P99 端到端 < 45s；单 Run 成本已知且稳定（波动 < 15%）；**任意一次 Run 能在 5 分钟内复盘**（有完整 trace） |
| **人力** | 6~8 人（后端 4、前端 1、算法/提示词 1、SRE 1） |
| **交付物** | 一份可评审的「一次 Run 的完整解剖」文档 + 3 篇 ADR |

> ⚠️ **阶段一最容易被跳过的是 ③ 和 ⑦**。没有 trace，你在阶段二会瞎；没有评测集，你在阶段三会漂。这两个东西越早做，复利越大——**它们是唯一「越晚做越亏」的投入**。

### 阶段二（M4-M6）：能扛——「百万 Run，坏天气不倒」

| 项 | 内容 |
| --- | --- |
| **唯一目标** | 3 个场景、日 100 万 Run、峰值 1,000 QPS，**在下游抖动、流量突增、灰度翻车时都不塌** |
| **P0 必做** | ① 队列与调度：优先级（交互 > 批 > 离线）+ 租户公平（第 11 章）<br>② 五维限流 + 四种算法 + 三种出口（排队/降配/降级）（第 23 章）<br>③ 降级阶梯（大 → 小 → 模板 → 兜底 → 明确失败）与开关带 TTL（第 25、43 章）<br>④ 熔断按 `provider × model × region`，加全抖动退避 + 重试预算（第 25 章）<br>⑤ 幂等三处：Run 创建、工具调用、计费结算（第 8 章）<br>⑥ **事件溯源 + 检查点**，多副本不丢状态（第 6、12 章）<br>⑦ 多租户：租户 ID 贯穿 trace/缓存/存储/计费 + 配额（第 44 章）<br>⑧ 计费：预扣—结算—对账三段式 + 每日与厂商对账（第 27 章）<br>⑨ 灰度：按租户/流量/场景 + 一键回滚（第 42 章）<br>⑩ 评测进 CI，200 条 + 发布门禁（第 40、48 章） |
| **明确不做** | 低代码自助、语义缓存、多 Agent 协作、跨区域多活 |
| **验收指标** | 可用性 ≥ 99.9%（月停机 ≤ 43.2 分钟）；Run 成功率 ≥ 99%（不含用户取消）；TTFT P95 < 1.5s；**混沌演练 9 项全过**；计费准确率 ≥ 99.9%（对账差额 < 0.5%）；灰度回滚 < 5 分钟 |
| **人力** | 12~14 人（+评测 2、+数据 1、+安全 0.5） |
| **交付物** | 限流矩阵、降级阶梯、容量模型（能算清 5k QPS 要几副本）、对账日报 |

| 项 | 内容 |

## 52.3 团队分工：四个组，边界比人数重要

| 组 | 人数 | 负责 | **不负责**（重要） | 关键产出 |
| --- | --- | --- | --- | --- |
| **平台组** | 5~6 | 运行时、队列调度、网关、限流降级、存储、计费账本、低代码引擎 | 具体业务场景的提示词 | 平台 SLA、容量模型、计费准确率 |
| **应用组** | 3~4 | 头部 3 个 Agent 的场景逻辑、提示词、工具接入、角色卡 | 平台内核、基础设施 | 场景成功率、客诉率 |
| **评测与数据组** | 3~4 | 评测集、判定器校准、badcase 聚类、数据回流、成本归因报表 | 改业务代码（只提 issue 和建议） | 「发布门禁」的独立裁判权 |
| **SRE / 值班** | 2 | SLO、告警、容量、混沌演练、事故指挥、变更管控 | 业务逻辑 | 可用性、MTTR、事故复盘 |
| **安全与合规** | 0.5~1 | 红队、审计、数据驻留、许可证合规 | — | 零逃逸、取证 ≤2h |

> 💡 **最容易被忽略的一条**：**评测组必须独立**，不能挂在应用组下面。因为它的职责是「说不」——如果它的绩效和应用组的「上线速度」绑定，它就会变成盖章机。Aurora 的做法是评测组向 CTO 虚线汇报，且**拥有一条硬权限：它可以阻断发布，不需要任何人同意**。

### 52.3.1 SLO 与错误预算

```yaml
# slo/aurora.yaml —— 每个季度 review 一次，改之前要开会
service: aurora-agent-platform
window: 30d
slos:
  - name: availability
    sli: "成功 Run 数 / 总 Run 数（不含用户取消）"
    target: 0.9995            # 99.95% → 月停机 21.6 分钟
    error_budget: 21.6m
    burn_rate_alerts:         # 多窗口燃烧率，比静态阈值灵敏得多
      - { window: 1h,  factor: 14.4, severity: page }   # 1 小时烧掉 2% 月预算
      - { window: 6h,  factor: 6,    severity: page }
      - { window: 3d,  factor: 1,    severity: ticket }
  - name: ttft
    sli: "首 token 延迟的 P95"
    target: 1500ms
  - name: run_latency
    sli: "端到端 P99（交互场景）"
    target: 60000ms
  - name: billing_accuracy
    sli: "1 - |我方计量 - 厂商账单| / 厂商账单"
    target: 0.999             # 差额 < 0.1%
    error_budget: 0.001
  - name: retraction_rate
    sli: "撤回消息数 / 总消息数"
    target_max: 0.005         # 这是「反向 SLO」：超过说明质量崩了
policy:
  - "错误预算耗尽 → 冻结所有非修复类变更（含配置发布）"
  - "连续两个季度预算剩余 > 50% → 说明 SLO 定松了，加需求或收紧指标"
```

**值班与升级**：

```yaml
# oncall/escalation.yaml
rotation: weekly            # 周一 10:00 交接，交接必须有书面 handoff
tiers:
  - { level: 1, who: 平台组轮值, ack_within: 5m,  scope: "告警 triage + 已知问题手册" }
```

## 52.4 10 个事故复盘

**格式统一**：现象 → 时间线 → 根因（技术 + 组织）→ 损失 → 修复动作 → **制度化产出**（这一栏最重要：事故的价值在于它改变了什么流程）。

| # | 事故 | 怎么发现的 | 根因一句话 | 损失 | 制度化产出 |
| --- | --- | --- | --- | --- | --- |
| 1 | **计费漏单** | 与厂商对账差额 4.3% | 流式断连时没有结算路径，只有预扣 | 11 天 / 42 万 Run / $118k | 结算改「预扣必写 pending + TTL 扫描器强制结算」；对账阈值 4.3% → 0.3% |
| 2 | **缓存错配** | 客诉 210 起 | 语义缓存键漏了政策版本 | 3 天 / 8,400 次错答 / 赔偿 ¥260k + 监管问询 | 「事实类答案禁止进语义缓存」白名单；键必须含 `policy_ver` |
| 3 | **重试风暴** | provider 发来警告邮件 | 重试无退避无抖动，且 429 也重试 | 4 小时降级到最低配额 | 全抖动退避 + 全局重试预算 5% + 429 优先降档 |
| 4 | **上下文爆窗** | 用户投诉「等了 90 秒 500」 | 截断只在单条消息上做；不可重试错误被重试 | 2 小时 / 3,100 次失败 | 错误分类表（可重试/不可重试）；上下文预算在装配层强制 |
| 5 | **沙盒逃逸** | EDR 告警（容器内读 `/etc/shadow`） | 容器 + 默认 seccomp，撞上内核 CVE | 1 个节点 / 无数据外泄 | 换 gVisor；默认无 egress；一次性沙盒；季度红队 |
| 6 | **灰度翻车** | 客诉「同一个客服一会儿一个样」 | 分桶键用 `user_id`，跨设备会话被分到不同桶 | 6 小时 / 2.4 万会话 | 分桶键必须 `session_id`/`tenant_id` 稳定哈希；灰度维度矩阵 |
| 7 | **系统提示泄露** | 竞对产品文案高度相似 | system prompt 含全部规则，无分层、无 canary | 资产损失不可估 | 分层披露；canary token；输出侧回显检测；关键规则进代码 |
| 8 | **撤回失败** | 用户截图「前后矛盾」 | correction 事件被前端当新消息追加；IM 渠道不可编辑 | 1 次舆情 / 3,000 次曝光 | 统一事件协议 + 前端 `replace` 语义；IM 用引用回复 + 标注 |
| 9 | **队列雪崩** | P99 从 12s → 900s | 批处理与交互同优先级，200 万任务堵死队列 | 3 小时 / 交互成功率 62% | 优先级硬隔离；每租户队列配额；大客户专属队列 |
| 10 | **审计日志被改** | 月度哈希链校验失败 | 内部人员有 UPDATE 权限，为掩盖越权操作 | 1 次内部违规 / 取证中断 | DB 只授 INSERT；哈希链日锚定到 WORM；运维通道双人审批 |

### 深挖 1：计费漏单（#1）——最贵的一课

```
D1 10:00  上线新流式客户端（支持用户随时打断）
D1-D11   一切正常，看板上「收入」曲线平滑
D12 09:00 财务对账：厂商账单 $2.59M，我方计量 $2.48M，差 4.3%
D12 11:00 定位：客户端 abort 时，服务端收不到 finish_reason
          → 走的是 `defer` 里的清理逻辑，只写了「预扣」没写「结算」
          → 11 天累计 42 万次 Run 处于「已预扣、未结算」的悬挂态
D12 18:00 补偿脚本按「最后一次 usage 增量」结算，回收 $118k
D13        上线 TTL 扫描器 + 断连时的增量结算
```

**根因有两层**：技术上，**结算的触发点绑在了「正常结束」这个事件上**，而不是「Run 进入终态」；组织上，**计费是最后一个模块，没有 owner**，上线时没人 review 它的状态机。

**修复后的三条规矩**（现在写进了发布 checklist）：

1. **预扣与结算必须成对，且结算的触发条件是「状态机进入终态」**，不是「HTTP 响应正常结束」。终态包括：正常完成、用户取消、超时、崩溃恢复。
2. **每天 02:00 跑 TTL 扫描器**：任何 `pending` 超过 1 小时的预扣，强制按「最后一次已知 usage」结算并打标 `estimated=true`。
3. **对账差额阈值 0.3%，触发 P2 告警**；差额 > 1% 直接 P1。

### 深挖 2：缓存错配（#2）——语义缓存的反噬

```
9/01  知识库更新：退款政策从「30 天无理由」改为「7 天无理由」
9/01  语义缓存未失效（键里没有 policy_ver）
9/01-9/03  8,400 次答复仍在说「30 天」，命中率还上升了（因为答案稳定）
9/03  客诉爆发：客户拿着「30 天」的答复要求退款
9/03  紧急下线语义缓存（全量回源），P99 从 12s 涨到 19s
9/05  修复上线：键加 policy_ver + 政策变更触发 namespace 失效
9/08  监管问询：需提供「错误答复的影响范围与补救措施」
```

**最扎心的一点**：**上线后三天，缓存命中率指标是「变好」的**——因为错误的答案被反复命中。**这说明缓存指标必须和「答案正确性」绑定看**，单独看命中率会骗你。

**制度化产出**：一份「什么内容可以进语义缓存」的白名单——

| 可缓存 | 不可缓存 |
| --- | --- |
| 产品功能说明（政策版本锁定） | 含订单/账户个性化数据 |
| 常见操作步骤（版本化） | 涉及金额、时效、法律条款 |
| 术语解释、话术模板 | 政策类答案（必须实时回源，或带 `policy_ver`） |

### 深挖 3：重试风暴（#3）——一个 SDK 默认值引发的四小时

```
14:02  provider 区域抖动，429 比例 8%
14:03  SDK 默认重试 3 次（无退避），5k QPS → 15k QPS
14:05  provider 触发更严格限流，429 比例 40%
14:08  重试放大 → 实际出站 22k QPS
14:20  我方被降级到最低配额（约 500 QPS），全平台成功率 31%
14:39  IC 下令：关闭重试，改为「429 直接降档到小模型」
14:45  成功率回到 82%
18:10  配额恢复，成功率 99%
```

**根因**：`MaxRetries: 3` 一个默认值，在 5k QPS 下等于给下游打了 3 倍的拳。**而且 429 是「明确的限流信号」，最不该重试的错误类型**。

**修复**：

```go
// 重试策略：分类 + 退避 + 全抖动 + 全局预算
func ShouldRetry(err error, attempt int) bool {
    switch {
    case errors.Is(err, ErrRateLimited):   return false // 429：立刻降档，不重试
    case errors.Is(err, ErrContextLength): return false // 不可重试
    case errors.Is(err, ErrInvalidRequest):return false // 不可重试
    case errors.Is(err, ErrServerError), errors.Is(err, ErrTimeout):
        return attempt < 2                              // 只重试 2 次
    }
    return false
}

// 全抖动：sleep = random(0, min(cap, base*2^attempt))
// 关键：不是「固定退避」，是「随机」——否则所有客户端会在同一毫秒一起重试
func backoff(attempt int) time.Duration {
    ceiling := min(8*time.Second, 200*time.Millisecond<<attempt)
    return time.Duration(rand.Int63n(int64(ceiling)))
}

// 全局重试预算：重试请求数不得超过总请求的 5%（超了就整体放弃重试）
if retryBudget.Exhausted() {
    return ErrRetryBudgetExhausted // 直接走降级阶梯
}
```

### 深挖 4：沙盒逃逸（#5）——「假设它一定会被骗」的验证

```
03:12  EDR 告警：容器内进程尝试读取 /etc/shadow
03:14  安全值班确认：代码执行沙盒里有一个进程在做提权探测
03:15  隔离该节点，抓取容器镜像与进程树
03:40  确认：容器 + 默认 seccomp profile，撞上一个未修补的内核漏洞
04:10  确认无数据外泄（egress 被网络策略默认拒绝，只允许 3 个白名单域名）
09:00  决策：沙盒从「容器」升级到「gVisor 用户态内核」
```

**如果当时没有那三条网络策略**，这就是一次数据外泄事故。**沙盒的价值 90% 在「默认拒绝」这四个字上**：无 egress、只读 rootfs、无特权、每会话一次性。

**制度化产出**：每季度红队演练，固定 12 个逃逸/越权样本，必须全部拦住，且**审计日志里能查到每一次尝试**。

## 52.5 十条反模式（都是我们真实踩过的）

| # | 反模式 | 为什么诱人 | 后果 | 替代做法 |
| --- | --- | --- | --- | --- |
| 1 | 先做多 Agent | 「看起来高级」 | 错误相乘，成功率从 91% 掉到 84% | 先做单 Run 稳定 |
| 2 | 评测最后做 | 「功能优先」 | 6 次改版里 4 次是变差的，且无人知晓 | 第 2 个月就有 100 条 |
| 3 | 先做低代码 | 「业务自助」 | 没有 trace，配错了看不出来，平台组变客服 | trace 先行 |
| 4 | 用日志当 trace | 「有日志就够了」 | 出事只有一行 `duration=12.4s` | `llm.call` / `tool.call` span |
| 5 | 重试解决一切 | 「加个重试就好」 | 重试风暴，4 小时降级 | 分类重试 + 全抖动 + 预算 |
| 6 | 缓存先上线再想 key | 「先跑起来」 | 跨租户数据泄露 / 政策错配 | 键先设计，阈值先实验 |
| 7 | 计费最后接 | 「先免费跑」 | 漏单 $118k，且无法归因 | 阶段一就记 token |
| 8 | 灰度 = 发版 | 「发了就是灰了」 | 一次翻车影响 2.4 万会话 | 按租户/会话稳定分桶 |
| 9 | 安全 = 审核模型 | 「接个审核 API 就行」 | 系统提示泄露，无 canary | 分层披露 + 输出侧检测 |
| 10 | 用 HPA 解决 LLM 限流 | 「K8s 会自己扩」 | 扩出来的 Pod 一样被 429 | 限流在网关，扩容看 token 速率 |

## 52.6 Java / 分布式经验对照：带过去什么，扔掉什么

| 带过去（资产） | 扔掉（负债） |
| --- | --- |
| 幂等键、复式记账、对账（支付系统经验） | 「同步 HTTP + 重试 3 次」的肌肉记忆 |
| 熔断/限流/舱壁（Sentinel/Resilience4j） | 「一次请求一次响应」的延迟预期 |
| 最终一致、Saga、Outbox | 「配置只是阈值」的认知（配置会改变模型行为） |
| 灰度、金丝雀、回滚 | 「测试靠断言相等」的习惯 |
| 分层架构、防腐层（六边形） | 「先跑通再说」的交付节奏 |
| SLO、错误预算、值班、复盘 | 「日志 = 可观测」的偷懒 |

> 💡 一句话：**你的分布式经验能覆盖 40%，剩下 60% 是「不确定性 + 成本 + 内容责任」带来的新东西。** 而这 60%，恰好就是这本书的全部内容。

## 52.7 上线前的 20 条检查清单

- [ ] 每个 Run 有 `trace_id`，含 `llm.call` / `tool.call` / `retrieval` span
- [ ] Run 元数据含五个版本号：模型 / 提示词 / 角色卡 / 工具集 / 索引（+ 配置版本）
- [ ] 任意一次 Run 能在 5 分钟内复盘（上下文快照可查）
- [ ] 流式输出有 `Last-Event-ID` 断点续传
- [ ] 超过 30 秒的 Run 走异步 + 事件推送
- [ ] Run 状态外置（事件溯源 + 检查点），滚动更新不丢
- [ ] 工具分级（读/写/高危），写操作有幂等键 + 审批
- [ ] 错误分类表（可重试/不可重试），429 不重试
- [ ] 重试有全抖动 + 全局重试预算（≤5%）
- [ ] 熔断按 `provider × model × region`，半开有抖动
- [ ] 降级阶梯完整（大→小→模板→兜底→明确失败），开关带 TTL
- [ ] 五维限流 + 三种出口，付费层只降级不拒绝
- [ ] 缓存键含租户/场景/模型档/提示词版本/索引版本
- [ ] 语义缓存有实体对齐护栏 + 阈值经过对照集实验
- [ ] 计费：预扣—结算—对账，pending 有 TTL 扫描
- [ ] 成本看板能出「每 Run 成本 / 每千 token 毛利」
- [ ] 前处理闸门 + 输出审核 + 撤回通道（统一事件协议）
- [ ] 审计日志 append-only + 哈希链 + 日锚定
- [ ] 沙盒默认无 egress、只读 rootfs、一次性
- [ ] 评测集 ≥200 条 + 发布门禁 + 灰度 1% 起

> 20 条里过不了 15 条，别接付费客户。

## 52.8 一页速记

| 关键词 | 必须记住的结论 |
| --- | --- |
| 排序原则 | **可观测 → 稳定 → 便宜 → 聪明**。反过来做，你要花双倍时间补课 |
| 三个月 | 一个场景、日 1 万 Run、trace + 100 条评测 + 成本埋点；**只做这四件** |
| 六个月 | 日 100 万 Run、99.9%、限流+降级+幂等+计费+灰度+评测门禁 |
| 一年 | 10 万租户、99.95%、毛利率 ≥40%、业务自助 ≥60% |
| 团队 | 评测组必须独立，且拥有**无需同意的阻断权** |
| SLO | 99.95% = 21.6 分钟/月；用多窗口燃烧率告警，不用静态阈值 |
| 值班 | 15 分钟内有人认领 IC；IC 不做技术操作；没有 runbook 的告警不准上线 |
| 事故价值 | 看「制度化产出」，不看「修复了什么 bug」 |
| 最贵的四个事故 | 计费漏单、缓存错配、重试风暴、审计被改 |
| 反模式 | 先多 Agent、评测最后、日志当 trace、计费最后接、HPA 治限流 |
| 一句话 | **Agent 平台的成熟度，不看它能做什么，看它崩了之后能不能说清楚为什么。** |

## 52.9 自检题

1. **你只有 6 个人、3 个月，要上线一个能对外收费的 Agent 产品。路线图怎么砍？**
   > 要点：**只做一条链路 + 四个底座**。一条链路：一个场景、单 Agent、3 个工具、1 个知识库。四个底座：① Run/Event 状态外置（否则滚动更新就丢）；② trace（否则永远瞎）；③ 工具分级 + 幂等（否则重复副作用）；④ 成本埋点（否则定价靠猜）。**砍掉**：多 Agent、低代码、语义缓存、自建推理、复杂角色卡矩阵、多币种计费。**保留一件看似奢侈的事**：100 条评测集——因为它决定了你后面 9 个月是「迭代」还是「赌博」。

2. **「错误预算耗尽就冻结变更」这条规则，为什么对 Agent 平台特别重要？**
   > 要点：因为 Agent 平台的**变更来源是双份的**：代码（4 次/天）+ 配置（210 次/天）。传统的「代码冻结」在这里几乎无效——业务改一句提示词就能让成功率掉 5 个点。错误预算是一个**跨代码与配置的统一刹车**：它不判断「你改的是什么」，只判断「你有没有资格再改」。没有这条，你会在一个已经很脆弱的系统上继续加速，直到它以你无法归因的方式崩掉。

3. **一次 P1 事故复盘，怎么判断它是不是「真复盘」？**
   > 要点：看三个东西。① **有没有「组织根因」**：只写「工程师忘了加判断」是假复盘，真复盘会问「为什么流程允许一个人不加判断就上线」。② **有没有「制度化产出」**：至少一条改变了流程/权限/CI/告警的产出，且**有 owner 和截止日期**；没有产出的复盘会在 6 个月后重演（Aurora 的 #1 和 #3 就重演过一次）。③ **有没有「如果重来一次」的时间线推演**：把「本可以在第几分钟发现」写出来——这个数字直接告诉你观测与告警的缺口在哪。

## 52.10 结语与延伸阅读

写到这一章，全书该说的都说了。最后留三句话：

1. **框架会换，模型会换，供应商会换；事件模型、幂等键、账本、审计、trace——这些不会换。** 把时间投在后者。
2. **每个「不做会怎样」的问题，答案都是一个数字。** 算不出来，就说明你还没想清楚。
3. **Agent 平台最终交付的不是「智能」，是「可被信任的自动化」。** 信任来自可解释、可撤回、可追责——这三样，没有一样是模型给的。
