# 《AgentOS 工程架构：从编排框架到生产级 Agent 平台》· 总纲

> **一句话**：市面上 90% 的 Agent 教程在教你「怎么用 LangChain 串一个能跑的 Demo」；这本书讲的是**剩下那 90% 真正决定你能不能上线的工程**——前处理、流式、审计与撤回、限流、缓存、降级、计费、沙盒、防御、记忆、可观测、数据回流、灰度、多策略、低代码装配。
>
> **核心立场（全书反复锤的一件事）**：
> **编排框架（LangChain / LangGraph / eino / Dify）在生产 Agent 系统里只占 10~12%，它是「控制流 DSL」；剩下 88% 是平台工程，而且是那种「少写一行就亏钱 / 少兜一次就雪崩 / 说错一句话就收不回」的工程。**

| --- | --- |

## 0. 方法论：先算账，再画图，最后给清单

Agent 平台的架构决策，本质上都是**三本账**的平衡：

```
质量账（回答得对不对）  ×  成本账（每次多少钱）  ×  时间账（多久出第一个字）
                    ↑ 三者互斥，这就是架构的全部张力 ↑
```

所以每一章都走同一套骨架：

```
① 场景账本   先算：不做这件事，会在什么规模上炸？炸成什么样？（带数字）
② 结构图     控制面 / 数据面 / 运行时 / 治理面 / 管道，画清楚谁调谁
③ 关键设计   字段、状态机、协议、幂等键、失败模式（给 schema 与伪代码）
④ Java 对照  跟你熟的 Spring Cloud / Sentinel / RocketMQ / Temporal 对应关系（同构点与坑）
⑤ 开源坐标   LangGraph / LiteLLM / Temporal / Langfuse / vLLM / Dify 里对应哪一块，能抄什么
⑥ 事故清单   这个模块上线后最可能怎么炸 + 兜底预案
⑦ 一页速记   表格 + 5 条硬结论
```

**反冗余公约**：一个概念只在一处深挖，其余只给结论 + `详见第 N 章`。先说「为什么必须有这一层」，再说「怎么实现」。

## 1. 全书最重要的那张图：把 LLM 当 CPU，你其实在造一台操作系统

这是理解 AgentOS 最快的路径。**LLM 不是「一个 API」，它是一颗又慢又贵、还会随机出错、还会被社会工程学骗的 CPU**；一旦你这么看，Agent 平台要造的东西就全都对上了：

| 操作系统里的东西 | AgentOS 里的对应物 | 为什么必须有 | 本书章节 |
| --- | --- | --- | --- |
| 进程 / 线程 | **Run / Step / Event** | 一次对话不是一次请求，是一串可恢复的状态迁移 | 6, 10, 12 |
| 调度器 | **准入 + 队列 + 优先级 + 公平调度** | 5k QPS、单 Run 30 秒，不排队就是集体超时 | 11, 14 |
| 内存管理 / 分页 | **上下文窗口 + 记忆分层 + 压缩 + 前缀复用** | 上下文是唯一稀缺资源，超了就丢信息、涨成本 | 15, 18, 19 |
| **系统调用入口检查（seccomp）** | **前处理闸门：规范化 / 注入预检 / 审核 / 路由前置** | 脏输入不该浪费最贵的 CPU（token），也不该进内核 | 35 |
| **终端行缓冲与 flush** | **流式输出 + 撤回窗口** | 一旦 flush 到用户屏幕就收不回，所以要设计缓冲与更正 | 36, 37 |
| 文件系统 | **会话库 / 事件库 / 向量库 / 对象存储** | 可回放、可审计、可训练 | 45 |
| 设备驱动 | **模型适配层（多 provider、多版本）** | 模型换得比框架快，驱动层必须能热插拔 | 26, 51 |
| 系统调用 | **工具调用 / MCP** | Agent 与外部世界的唯一合法接口 | 22 |
| 权限 / 用户态-内核态 | **沙盒 / ACL / 审计 / 租户隔离** | 让模型拿到执行权，就必须假设它会被骗 | 29, 30 |
| 内核日志 ring buffer（不可篡改） | **审计日志（append-only + 哈希链）** | 出事时要能证明「当时到底发生了什么」 | 31 |
| 反调试 / 反注入 / 密钥保护 | **防御工程：防破解、防薅羊毛、防蒸馏** | 你的对手不只是用户，还有灰产和竞对 | 32 |
| cgroup 限额 | **配额 / 限流 / 预算刹车** | 一个失控循环能烧掉一个月预算 | 23, 27 |
| 页缓存 / 缓存层级 | **语义缓存 / 前缀缓存 / 结果缓存** | 缓存是唯一能把成本降一个数量级的手段 | 24 |
| 监控与 dmesg | **Trace / 指标 / 日志 / 成本看板** | 没有 trace 的 Agent 等于不可调试的分布式系统 | 39 |
| 内核模块热更新 | **模型与提示词灰度、双跑、回滚** | 你在持续上线「会改变行为的配置」 | 42, 43 |
| Shell 与脚本 | **低代码配置层（Agent Builder / DSL）** | 让业务自己搭，平台只提供安全的原语 | 49 |

> 💡 **一句记住的话**：所有 Agent 平台的复杂度，都来自「CPU 变贵了、变慢了、还会说谎、还会被说服」。传统后端的「一次请求一次响应」模型在这里彻底失效——**这就是为什么 Agent-Server 必须独立成一个架构（第 5 章），为什么流式输出必须有撤回机制（第 37 章）。**

## 2. 全局地图：四层 + 一条管道 + 三翼

```
                    ┌────────────────────────────────────────────┐
                    │  ③ 治理面 Governance                        │
                    │  限流配额 · 计费账本 · 多租户 · 策略中心     │
                    │  灰度发布 · 审计合规 · 成本归因             │
                    ├────────────────────────────────────────────┤
   ② 运行时 Runtime  │  ⑤ 执行内核（Kernel）                       │
   ───────────────── │  Run 状态机 · 队列调度 · 沙盒 · 工具/MCP     │
   上下文工程 · 记忆  │  多 Agent 协作 · 中断恢复 · 长任务持久化     │
   角色卡 · RAG      │  低代码装配（DSL → 图）                      │
   SKILL · 工具      ├────────────────────────────────────────────┤
                    │  ④ 数据闭环 Data Loop                       │
                    │  Trace · 评估 · 离线回流 · 训练数据          │
                    └────────────────────────────────────────────┘

  ① 接入面 Edge：Agent-Client（Web/IDE/IM/App）⇄ 协议 ⇄ Agent-Server
  ⑦ 管道 Pipeline：前处理闸门 → 上下文装配 → 流式输出 → 输出审计/撤回 → 后处理
  ⑧ 三翼（横切所有层）：可观测 · 缓存与降级 · 安全与防御
```

**四条数据流 + 一条回流，画清楚就不会乱**（全书反复回到这张图）：

```
用户 ──①请求──▶ 接入网关 ──②前处理闸门──▶ 准入/配额 ──▶ 队列 ──▶ Run 执行
                    │(规范化/注入预检/审核/路由前置)                  │
                    ▼                                               │
   ④流式事件（delta/tool/status/correction）◀────────┬──────────────┘
                    │                                │
   ⑤输出审计（判定/撤回） + ⑥计费结算 + ⑦Trace 落库 ─┘
                    │
   ⑧离线回流：样本 → 评估集 → 提示词/角色卡/模型/路由 → 灰度上线 → 回到②
```

### 第七部分 · 输入输出管道：前处理 → 流式 → 审计 → 后处理（35-38）

> 这一部分是**最容易被跳过、也最容易出事故**的一段：一边是「进模型的脏东西」，一边是「出模型的话」。前者决定成本与安全，后者决定用户体验与法律风险。
> **一个反直觉的事实**：流式输出让「撤回」成了一个分布式一致性问题——字已经吐到用户屏幕上了，你怎么收回？

| --- | --- | --- | --- |
| 35 | **前处理层：把脏输入挡在花 token 之前** | 输入规范化（编码/语言/长度/格式/乱码/重复）；**输入侧审核与注入预检**（在消耗 token 前拦截，成本从「按 token」降到「按规则」）；**意图识别与路由前置**（省钱的第一个闸门：能不走大模型就不走）；附件与多模态解析（PDF/图片/表格 → 结构化）；入站 PII 识别与脱敏；会话状态修复（历史不一致、超长、断裂的工具消息）；多语言与本地化预处理；前处理失败时的兜底话术；**前处理的可观测**（拦了多少、拦对了多少） | Guardrails、Presidio、Tika/Unstructured |

| 37 | **输出审计与「撤回已说出去的话」** | 为什么必须能退回：审核滞后、模型幻觉、政策变更、用户投诉、上游数据撤稿；**四种撤回机制**（截断停机 / 追加更正事件 / 全量重发 rebase / 会话级撤销 + 道歉话术）与各自的用户体验代价；**双通道设计：草稿流 + 确认流**（用 300~800ms 延迟窗口换安全）；分级延迟策略（敏感场景慢一点没关系）；审计链设计（每个输出片段绑定上下文快照、模型版本、判定结果、审核人）；前端契约（correction 事件、版本号、幂等重放、已渲染内容的替换语义）；事后召回与批量下线通知；「已读撤回」的法律与体验权衡；撤回指标（撤回率、误撤回率、投诉率） | 事件溯源、内容审核系统、工单系统 |
| 38 | 后处理层：把「差不多」变成「能交付」 | 结构化输出校验与修复、幻觉过滤与引用核对、脱敏与格式化、多候选融合与打分、拒答策略、品牌与合规话术；**后处理是质量的最后一道闸**，也是幻觉的主要拦截点；后处理与流式的冲突（已经发了还能改吗 → 见第 37 章） | Guardrails、Outlines、JSON Schema |

## 4. 全书最想让你接受的一个判断：编排只占 12%

把一次真实的生产 Run 拆开看（一次客服 Agent、5 轮工具调用、30 秒、输出 800 字）：

| 组成 | 占比 | 归属层 | 编排框架能帮你做吗 |
| --- | --- | --- | --- |
| 控制流：什么时候调模型、什么时候调工具、循环退出 | ~12% | 编排层 | ✅ 这就是 LangGraph 们在做的事 |
| 接入与协议：鉴权、多端、流式、断线续传 | ~10% | 接入面 | ❌ 基本不碰 |
| 上下文工程：角色卡、预算、检索、压缩、记忆 | ~18% | 上下文层 | ⚠️ 只给你接口，策略全靠自己 |
| **输入管道：规范化、注入预检、审核、路由前置** | ~6% | 管道 | ❌ 没有 |
| 稳定性：限流、队列、超时、熔断、降级、重试 | ~14% | 治理面 | ❌ 几乎为零 |
| 成本与计费：路由、缓存、token 计量、账本 | ~12% | 治理面 | ❌ 没有 |
| **输出管道：流式渲染、结构化、审计与撤回、后处理** | ~10% | 管道 | ❌ 没有 |
| 可观测、评估与数据回流：trace、指标、评测、样本 | ~10% | 数据闭环 | ❌ 有钩子，没有体系 |
| 安全、防御与合规：注入、防破解、审计取证 | ~8% | 运行时 + 治理面 | ❌ 没有 |

> 🎯 **结论**：编排框架解决的是「怎么把模型和工具串起来」，它值得用、也应该用（省你两个月）；但如果你以为「选对框架 = 架构完成」，那你会在上线第三个月开始，用十倍的时间还这笔债。
> **本书的目标就是把这 88% 一块一块讲清楚，让你在做技术选型与架构评审时，能明确说出「这块我们自研、那块买、那块先用开源顶住」。**

## 5. Java 架构师的对照速查（你已有的经验，80% 可以直接迁移）

| 你熟悉的东西 | AgentOS 对应物 | 关键差异（会咬人的地方） |

| Spring Cloud Gateway / Nginx | Agent 接入网关 | 多了「流式响应」和「长连接断开续传」 |
| 网关过滤器（PreFilter/PostFilter） | **前处理层 / 后处理层** | 过滤器链是同步无状态的；这里要「花 token 前拦截」与「已输出后撤回」 |
| Sentinel / Hystrix / Resilience4j | 限流、熔断、降级 | 多了「按 token 计费的成本熔断」 |
| RocketMQ / Kafka | 事件管道与长任务队列 | 多了「一次 Run 的事件流必须有序且可回放」 |
| Redis | 会话缓存、分布式限流、语义缓存 | 语义缓存有**误命中**风险，传统缓存没有 |
| Temporal-Java | 长任务持久化执行 | 同一个思路；Agent 侧还要处理「非确定性模型输出」 |
| ShardingSphere | 多租户数据分区 | 多了租户级配额与账单 |
| ELK / Prometheus / SkyWalking | Trace + 指标 + 成本看板 | span 里多了模型、提示词版本、角色卡版本、token 数 |
| Spring 配置中心（Nacos/Apollo） | 策略中心 | 配置项从「阈值」变成「会改变模型行为的提示词与路由」 |
| 支付系统的账本 | Agent 计费账本 | 多了「流式场景下的用量未知」与「缓存折扣」 |
| 审计日志（binlog / 操作日志） | **合规审计（append-only + 哈希链）** | 多了「AI 生成内容标识」与「监管协查取证」 |
| 风控系统（设备指纹、行为评分） | **防御工程** | 对手从「刷单团伙」变成「越狱玩家 + 逆向工程师 + 竞对爬虫」 |
| CMS / 低代码平台（表单引擎、流程引擎） | **Agent Builder（DSL + 可视化）** | 配置项是「会思考的流程」，必须带评测门禁与沙箱 |
| JVM 沙盒 / 容器 | Agent 代码沙盒 | 强得多：模型会给它任意代码 |
| DDD 分层 | Agent 平台分层 | 分层依据从「业务」变成「控制面/数据面/运行时/管道」 |

## 8. 写作与仓库约定

- **交叉引用**：`详见第 N 章`；与 Go 系列的关联写成「见 `../go/23-memory-model.md`」这类形式。
- **状态标记**：每章开头 `> 状态：待撰写 / 已完成（初稿）`。
- **提交规范**：`docs(llm): 第 N 章 <主题>`，一章一提交。
