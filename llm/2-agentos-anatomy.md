# 2. AgentOS 解剖：把 LLM 当 CPU 造操作系统

> **状态**：`已完成（初稿）` ｜ **所属**：第一部分 · 认知篇：为什么「套个框架」一定会失败 ｜ **编号**：2 / 52
> **本章定位**：把「LLM 是一颗又慢又贵、会随机出错、还会被社会工程学骗的 CPU」这个隐喻，落成一张能评审的模块清单：七个内核模块、一条系统调用边界、一张「什么必须平台统一 / 什么必须放给业务」的判定表。

## 2.1 引子：四十个微服务，四十套私货

Aurora 的第一次架构评审，我把 12 个团队画的图叠在一起，看到了这样一份「同一个平台里的不同世界」：

| 能力 | 各团队的实现数 | 后果 |
| --- | --- | --- |
| 上下文裁剪 | 5 种策略（截断 / 摘要 / 丢工具结果 / 丢历史 / 不裁） | 同一个问题在两条链路里答案不同 |
| 重试 | 3 层各写一遍（SDK 层 3 次 × 网关层 2 次 × 服务层 3 次） | 最坏 18 次重复工具调用 |
| token 计数 | 每服务自己 `len(text)/4` 估 | 与账单对账差 **11.3%** |
| 限流 | 只有一个服务做了，其它靠「上游会限」 | 一次洪峰打穿全部 |
| trace | 各服务 span 命名自由 | 无法拼出一次 Run 的全貌 |

然后事故来了。一个租户的 Agent 在「查订单」和「查物流」两个工具之间来回跳，**22 分钟、没有步数上限、没有预算刹车**，烧掉 1.4 亿 token（按当季均价约 **$2,100**）。更要命的是它挤占了共享的模型配额——同一时刻集群里有 **3,200 个 Run** 因为排队超时而失败，其中 2,900 个跟这个租户毫无关系。

复盘会上有人说：「微服务拆分拆错了。」不对。**拆分没错，错的是你把操作系统的职责，切碎了分给每个业务进程各写一遍。**

想想你在 K8s 上的习惯：你会让每个业务 Pod 自己实现一遍内存分配、自己实现一遍 CPU 调度、自己实现一遍文件权限吗？不会——这些是内核的事。可今天绝大多数 Agent 平台，正在让每个业务代码自己实现「上下文分配、配额、工具权限、token 计量」。**这就是本章要收回去的七件事。**

> 🩸 一句话记住：**一个没有内核的 Agent 平台，不是「平台」，是「一堆共享数据库的脚本」。**

## 2.2 断崖：七个模块，缺一个漏一个洞

先给账。下表每一行都是「Demo 阶段完全不存在、规模化后必然遇到」的东西，量化判据是你能拿去开会拍桌子的数字：

| # | 内核模块 | 缺失时的症状 | 量化判据（撞上就说明缺了） | 谁在替你承担 | 详见 |
| --- | --- | --- | --- | --- | --- |
| ① | **调度** | 洪峰时全员超时，不是模型慢，是你的进程在同步等 | 在途 Run 数 > 单实例 goroutine 安全线，或 P99 随 QPS 线性劣化 | 用户（看不到兜底） | 11、14 |
| ② | **上下文** | 同一模型同一提示词，效果时好时坏 | 你说不出「第 3 步时上下文里有哪 7 段内容、各占多少 token」 | 质量与成本同时 | 15、18 |
| ③ | **记忆** | 「它忘了我们刚说过什么」 | 跨 Pod 复现率 < 100%，或记忆写入无裁决导致自相矛盾 | 用户信任 | 19 |
| ④ | **存储** | 出事无法复盘，计费无法对账 | 无法回答「昨天 10:23 那次 Run 的每一步」= 不可运维 | 法务与财务 | 6、45 |
| ⑤ | **工具** | 重复下单、重复发邮件、越权读数据 | 工具调用无幂等键，或写操作无分级 | 客户与公司 | 22、29 |
| ⑥ | **权限** | 一个被注入的提示词就能让 Agent 读别人的合同 | 权限判定在业务代码里 `if role == "admin"` | 合规 | 30、44 |
| ⑦ | **计量** | 账单算不准，毛利说不清 | 计费与 provider 账单差异 > 0.1% | 财务 | 27 |

这七件事有一个共同特征：**它们必须「对所有租户、所有 Agent 同时成立」，而且「业务代码绕过它就会出事」。** 这个特征，就是「内核态」的定义。

## 2.3 结构图：一条系统调用边界

### 2.3.1 内核的疆域

```
┌──────────────────────────────────────────────────────────────────────┐
│  用户态 User Mode（租户 / 业务团队自己写，平台不碰）                    │
│                                                                      │
│   ┌────────────┐  ┌────────────┐  ┌────────────┐  ┌──────────────┐   │
│   │ 客服 Agent │  │ 编码 Agent │  │ 数据 Agent │  │ 租户自建 DSL │   │
│   └────────────┘  └────────────┘  └────────────┘  └──────────────┘   │
│        角色卡 · 提示词 · 流程编排 · 工具白名单 · 输出格式 · 前端        │
└───────────────────────────┬──────────────────────────────────────────┘
                            │  系统调用（唯一合法入口，不可绕过）
════════════════════════════╪══════════════════════════════════════════
┌───────────────────────────▼──────────────────────────────────────────┐
│  内核态 Kernel Mode —— AgentOS Kernel                                 │
│                                                                      │
│   ① 调度器       ② 上下文管理器   ③ 记忆层      ④ 存储/事件日志        │
│   ─────────      ──────────────   ─────────     ─────────────────    │
│   ⑤ 工具网关     ⑥ 权限/沙盒      ⑦ 计量与账本                        │
├──────────────────────────────────────────────────────────────────────┤
│  设备驱动层（可热插拔，模型换得比框架快）                                │
│   模型驱动 │ 工具驱动 │ 检索驱动 │ 向量/对象存储驱动 │ 审计/WORM 驱动    │
└──────────────────────────────────────────────────────────────────────┘
```

这套分层只有一个硬约束：**用户态拿不到「能直接产生副作用或费用」的凭证**。凭证只在内核的驱动层里。这跟 seccomp 是一个思路——不是说「请大家文明」，而是**从能力上就不可能**。

> ⚠️ 最常见的假内核：平台提供了一份「推荐的工具调用 SDK」，但业务代码里 `http.Post("https://api.openai.com/...")` 照样能跑。**只要网络出口和 API Key 没被收走，你的内核就是一份建议书。**

### 2.3.2 一次 Run 的内核路径

```
业务代码                     Kernel                        驱动层
   │                            │                             │
   ├─ Admit(req) ──────────────▶│ 准入：配额/限流/优先级        │
   │◀───────────── Admission ───┤ （拿不到就不发 token）        │
   │                            │                             │
   ├─ Reserve(est) ────────────▶│ 预扣 8000 token 预算          │
   │                            │                             │
   ├─ AllocContext(spec) ──────▶│ 预算切分 → 裁剪/压缩/检索      │
   │◀──────────── ContextView ──┤                             │
   │                            │                             │
   ├─ Invoke(ToolCall) ────────▶│ 幂等键 → 权限 → 沙盒 ────────▶│ 执行
   │◀──────────── ToolResult ───┤ 审计事件 + 计量事件 ◀─────────┤
   │                            │                             │
   ├─ Append(events...) ───────▶│ 序号分配 → 不可变追加          │
   │                            │                             │
   ├─ Settle(res, usage) ──────▶│ 预扣 - 实际 = 退/补           │
   │                            │                             │
```

注意这条路径的顺序：**预扣在花 token 之前，结算在最后一个 token 之后**。中间任何一步失败，账都是平的。这就是第 27 章那套「预扣—结算—对账」在内核里的位置。

## 2.4 关键设计

### 2.4.1 七个模块的「系统调用表」

| 模块 | OS 对应物 | 内核提供的系统调用（本平台的接口草案） | 强制点（不做就不能上线） |
| --- | --- | --- | --- |
| ① 调度 | 进程调度器 + CFS | `Admit` / `Enqueue` / `Preempt` / `FairShare` | 无准入就没法做 SLO；单租户可打穿全局 |
| ② 上下文 | 内存管理 + 分页 | `AllocContext` / `Compact` / `PinPrefix` | 超窗=丢信息+涨成本，两边都不可控 |
| ③ 记忆 | swap + 页缓存 | `Recall` / `Commit` / `Forget` | 写入无裁决 → 记忆自相矛盾且不可删（GDPR） |
| ④ 存储 | 文件系统 + ring buffer | `Append` / `Snapshot` / `Replay` | 没有事件就没有真相源，审计/计费/回放全塌 |
| ⑤ 工具 | 系统调用 + 驱动 | `Invoke` / `Cancel` / `Stream` | 幂等键与分级必须在网关，不能靠每个工具自觉 |
| ⑥ 权限 | 用户态/内核态 + 能力 | `Authorize` / `IssueCap` / `Revoke` | 权限判定下放到业务 = 越权是时间问题 |
| ⑦ 计量 | cgroup + 记账 | `Reserve` / `Settle` / `Refund` | 计量在业务侧 = 对账差 11%（见 §2.1） |

### 2.4.2 Go：内核接口的骨架

```go
// kernel/kernel.go —— 平台内核对外唯一入口（本平台自研接口草案，非任何开源 API）
package kernel

type Kernel interface {
	// ① 调度：拿不到 Admission 就不许调模型
	Admit(ctx context.Context, req *RunRequest) (*Admission, error)

	// ② 上下文：由内核按预算装配，而不是让业务自己拼字符串
	AllocContext(ctx context.Context, spec ContextSpec) (*ContextView, error)

	// ③ 记忆：读随意，写要裁决（冲突检测 + TTL + 合规删除）
	Recall(ctx context.Context, q MemoryQuery) ([]MemoryItem, error)
	Commit(ctx context.Context, w MemoryWrite) (MemoryID, error)

	// ④ 存储：追加事件是唯一写路径；Update 不存在
	Append(ctx context.Context, evs ...Event) ([]Seq, error)

	// ⑤ 工具：所有副作用必须过这里（幂等键 + 分级 + 审计 + 计量）
	Invoke(ctx context.Context, call ToolCall) (*ToolResult, error)

	// ⑥ 权限：能力令牌，短 TTL，绑定 run_id
	Authorize(ctx context.Context, cap CapabilityToken, act Action) error

	// ⑦ 计量：先预扣，后结算，差额退回
	Reserve(ctx context.Context, est CostEstimate) (*Reservation, error)
	Settle(ctx context.Context, r *Reservation, actual Usage) error
}
```

这个接口叫 `Kernel` 而不是 `Client`/`SDK` 不是文字游戏。**`Client` 暗示「你可以不用它」；`Kernel` 暗示「你绕不过它」。** 一个平台团队最重要的政治工作，就是把自己从前者变成后者。

### 2.4.3 内核态 vs 用户态：四条判据

这是本章最该被抄走的东西。任何能力，问四个问题，**前三个任一是「是」→ 必须内核态**：

| 判据 | 问题 | 为「是」时归属 | 反例（踩过的） |
| --- | --- | --- | --- |
| ① 爆炸半径 | 它出错会波及其他租户吗？ | **内核态** | 共享配额、全局限流、公共缓存 |
| ② 可计量性 | 它会产生费用或影响账本吗？ | **内核态** | token 计数、工具计费、缓存命中折扣 |
| ③ 责任归属 | 出事时平台要对外负责吗？ | **内核态** | 审计留痕、内容合规、PII 脱敏、密钥 |
| ④ 变更频率 | 它每周都要改，且前三条都不成立吗？ | **用户态/租户态** | 提示词措辞、角色语气、输出示例、工具排序 |

用代码表达就是一次分类：

```go
type Scope int

const (
	ScopeKernel Scope = iota // 平台强制，业务不可覆盖
	ScopeTenant              // 平台提供原语，租户可配置（有边界与灰度）
	ScopeApp                 // 完全放给业务，平台只观测不干预
)

// Classify 决定一个能力的归属。任何一条「是」都升级到内核态。
func Classify(c Capability) Scope {
	switch {
	case c.CrossTenantImpact:      // ① 爆炸半径
		return ScopeKernel
	case c.Metered || c.AffectsLedger: // ② 可计量性
		return ScopeKernel
	case c.Regulated || c.Auditable:   // ③ 责任归属
		return ScopeKernel
	case c.ChangeFreqPerWeek >= 1:     // ④ 高频变更 → 下沉给业务
		return ScopeTenant
	default:
		return ScopeApp
	}
}
```

把它套到真实的 18 项能力上，你会得到这张表（**这张表就是平台与业务的「宪法」**）：

| 能力 | 归属 | 理由（对应判据） | 业务能改到什么程度 |
| --- | --- | --- | --- |
| 上下文窗口预算总量 | 内核 | ①③ | 只能申请，不能超 |
| 上下文内部七份预算的**比例** | 租户 | ④ | 可在区间内调，超区间要走审批 |
| 具体提示词文本 | 业务 | ④ | 完全自由（走版本与灰度） |
| 角色卡（人格/边界） | 租户 | ④ | 可配，但禁止项由内核注入 |
| 工具**是否可用** | 内核 | ⑥ | 只能从白名单里选 |
| 工具**调用参数** | 业务 | ④ | 自由（受 schema 校验） |
| 写操作的审批策略 | 内核 | ③ | 只能加严，不能放宽 |
| 模型选择（在允许集合内） | 租户 | ② | 可配，但受配额与路由约束 |
| 单 Run 成本上限 | 内核 | ② | 只能调低 |
| 重试次数 / 退避 | 内核 | ①② | 只读 |
| 缓存开关 | 内核（键含租户） | ①②③ | 只读 |
| 输出格式 schema | 业务 | ④ | 自由 |
| 流式分段粒度 | 租户 | ④ | 三档可选 |
| 记忆保留期 | 内核 | ③ | 只能调短 |
| 数据驻留区域 | 内核 | ③ | 只读（合规） |
| trace 采样率 | 内核 | ② | 只读 |
| 子 Agent 拓扑 | 租户 | ④ | 可选模板，禁自环 |
| 沙盒资源配额 | 内核 | ①③ | 只能调小 |

> 💡 **一条可以拿去吵架的原则**：**凡是「改坏了会烧到别人」的配置，都不该有 UI。** 你在低代码平台上给业务开了一个「最大并发」输入框，就等于把内核态判据 ① 卖了。

### 2.4.4 YAML：内核策略的可执行版本

判定表要能落到配置里才算数。Aurora 用的是「内核默认 + 租户覆盖 + 硬上限」三层合成（合成逻辑详见第 43 章策略中心）：

```yaml
# kernel-policy.yaml —— 平台级，租户不可覆盖（改动走双人审批 + 灰度）
kernel:
  admission:
    max_inflight_runs_global: 4000        # 稳态 750 的 5.3 倍，突发靠队列吸收
    max_inflight_runs_per_tenant: 200     # 单租户不得超过全局 5%
    priority_classes: [interactive, batch, offline_eval]
    # 交互类保底：即使全局排队，也给 30% 的槽位
    reserved_slots: {interactive: 0.30}
  context:
    window_tokens: 128000
    hard_reserve_output: 4096             # 输出预留，不可被输入挤占
    compact_trigger_ratio: 0.72           # 到 72% 触发压缩
  tools:
    require_idempotency_key: [write, high_risk_write]
    approval_required: [high_risk_write]
    max_calls_per_run: 40                 # 失控循环的硬刹车
  budget:
    max_cost_per_run_usd: 0.80            # ≈ 单 Run 均值的 36 倍
    max_tokens_per_run: 400000
    reserve_ratio: 1.15                   # 预扣 = 估算 × 1.15
  memory:
    default_ttl_days: 90
    hard_max_ttl_days: 365                # 合规上限，租户只能调短
  audit:
    hash_chain: required                  # 审计事件必须进哈希链
    retention_days: 1095                  # 3 年
```

注意 `max_calls_per_run: 40` 和 `max_cost_per_run_usd: 0.80` —— **这两行如果一年前就在，§2.1 那次 $2,100 的事故不会发生**。内核的价值，往往就是把三个数字写进一个没人能改的 YAML。

## 2.5 Java / 分布式经验对照：哪些直觉直接可用，哪些会骗你

| 你的经验 | 迁移判断 | 会咬人的差异 |
| --- | --- | --- |
| 网关统一鉴权（Spring Cloud Gateway） | 🟢 直接可用 | 但 Agent 网关还要管**流式长连接**与**断线续传**（第 7 章） |
| Sentinel 全局限流 | 🟢 直接可用 | 多一个维度：**按 token / 按成本**限流（第 23 章） |
| 分库分表（ShardingSphere） | 🟢 直接可用 | 分片键从 `user_id` 变成 `tenant_id`，且要防「跨租户召回」（第 44 章） |
| 分布式事务（Seata/Saga） | 🟡 要改造 | 工具副作用不可回滚，只能**补偿**；且模型调用本身不可补偿（第 12 章） |
| 「无状态服务 + Redis」 | 🔴 会骗你 | Redis 存会话状态 = 丢可回放性；状态必须是**事件流**（第 6 章） |
| 中间件团队维护公共 SDK | 🟢 直接可用 | 但 SDK 不够，要**能力收口**（凭证与出口唯一）——SDK 是建议，内核是强制 |
| JVM 沙盒 / SecurityManager | 🔴 已淘汰 | 模型会给你任意代码，要真隔离（第 29 章） |
| DDD 分层（domain/application） | 🟡 要改造 | 分层依据从「业务边界」变成「控制流 vs 数据流 vs 强制点」 |
| 「先定接口，后补实现」 | 🟢 直接可用 | 内核接口一旦发布，**改一次要迁移几万个 Agent**；宁丑勿变 |

有一条特别值得单独说：**Java 世界里「框架帮你兜住 90% 约定」的经验，在 Agent 平台会失效。** Spring 的事务传播、连接池、线程池，都是「你用了就自动对」。而 Agent 的「上下文一致性」「预算一致性」**没有任何框架会自动帮你**——你必须把它做成不可绕过的入口。这是 §2.4.2 那个 `Kernel` 接口存在的原因。

## 2.6 开源坐标：这块别人做到哪了

| 层 | 开源/研究对应物 | 它替你做了什么 | 它把什么留给你 |
| --- | --- | --- | --- |
| 整体隐喻 | **AIOS**（LLM Agent Operating System 方向的研究工作，提出把 LLM 当内核、以调度/上下文/存储/工具为内核服务） | 给了很好的概念框架与模块划分 | 没有一个能直接上生产的多租户实现；学术原型 |
| 调度 | K8s（Pod 调度）、vLLM（continuous batching） | 资源级调度成熟 | **Run 级**调度（30 秒、可中断、按 token 计费）没人给你 |
| 上下文 | 各家 provider 的 prefix cache | 缓存命中就便宜 | 预算切分、压缩策略、命中率优化要自己做（第 15、18 章） |
| 存储 | Temporal / Kafka / Postgres | 事件日志能力成熟 | Agent 特有的事件语义（tool_call / correction / audit）要自己定（第 6 章） |
| 工具 | MCP（JSON-RPC 2.0，`tools/list`、`tools/call`）+ 各 SDK | 协议标准化做完了 | 幂等、分级、配额、审计要自己加（第 22 章） |
| 权限 | K8s RBAC / OPA | 策略语言成熟 | 要建模到「某个 Run 的某个工具调用」粒度（第 30 章） |
| 计量 | LiteLLM（统一计价与 fallback） | 有价格表与用量统计 | **账本**（预扣/结算/对账/退款）没有（第 27 章） |

> 🎯 结论：**AIOS 那类研究已经把「该有哪些内核模块」想清楚了，开源把「每个模块的零件」做齐了，但把它们缝成一个「业务绕不过去的强制层」，是你的活。**

## 2.7 事故清单

- [ ] **事故 1：旁路调用。** 现象：计费差异 11%，某业务直接用 provider SDK 调模型。→ 根因：凭证下发到了业务侧，网络出口未收口。→ 兜底：Key 只存在于模型驱动；业务 Pod 无外网 egress（NetworkPolicy）；出站流量按 SNI 审计，非白名单直接告警。
- [ ] **事故 2：假限流。** 现象：限流配了 5k QPS，洪峰仍超时。→ 根因：限的是「HTTP 请求」不是「在途 Run」，一次 Run 30 秒产生几十个请求。→ 兜底：双维度限流（请求 QPS + 在途 Run 数），后者才是真正的容量约束（第 23 章）。
- [ ] **事故 3：内核升级翻车。** 现象：改了 `AllocContext` 的裁剪顺序，全平台效果集体下滑 6%。→ 根因：内核是「行为定义者」，改动等于全量换模型。→ 兜底：内核变更必须双跑 + 按租户灰度 + 一键回滚（第 42 章）。
- [ ] **事故 4：模块职责渗漏。** 现象：业务为了「临时解决」直接写了数据库，绕过事件日志。→ 根因：内核接口不好用，业务就会挖洞。→ 兜底：内核要有「逃生舱」设计（受审计的 raw 通道）；同时用 CI 检查禁止 import 存储层。
- [ ] **事故 5：判定表被侵蚀。** 现象：低代码平台给租户开了「最大并发」配置，某大客户填 10000，压垮集群。→ 根因：§2.4.3 判据 ① 被绕过。→ 兜底：配置项分级（内核锁定项在 UI 上根本不存在）+ 服务端二次校验（前端不可信）。

## 2.8 一页速记

| 关键词 | 必须记住的结论 |
| --- | --- |
| 核心隐喻 | LLM = 慢、贵、会随机、会被骗的 CPU；所以你需要的不是「客户端」，是「内核」 |
| 强制力来源 | 不是文档约定，是**凭证与网络出口的唯一性**；旁路能跑，内核就只是建议书 |
| 七个模块 | 调度 / 上下文 / 记忆 / 存储 / 工具 / 权限 / 计量；缺任何一个，其余六个都在替它背锅 |
| 内核态判据 | 爆炸半径 > 1 租户、产生费用、平台担责——任一成立即内核态 |
| 用户态判据 | 每周都改、且不跨租户、不计费、不担责 → 放给业务 |
| 一条铁律 | **凡是「改坏了会烧到别人」的配置，都不该有 UI** |
| 内核接口 | 一次发布、长期兼容；改了要迁移几万个 Agent，宁丑勿变 |
| 三个必写死的数字 | 最大步数、单 Run 成本上限、单租户在途 Run 上限 |
| 与微服务的边界 | 微服务拆的是**业务能力**；内核收的是**强制点**，两者不冲突 |
| 一句话 | **平台不是「提供了 SDK」，是「你绕不过去」。** |

## 2.9 自检题

1. **你的平台提供了一份很好用的「Agent SDK」，业务团队都在用。这算不算有了内核？**
   > 要点：不算。SDK 是「建议」，内核是「强制」。判据：把 SDK 删掉，业务能不能自己 `http.Post` 到 provider？如果能，说明凭证或出口没收口。真正的内核要有三件事：凭证只在驱动层、业务无外网出口、所有副作用经工具网关。SDK 只是内核的「友好外壳」。

2. **「提示词」应该放内核态还是用户态？「禁止项（不许承诺退款）」呢？**
   > 要点：提示词全文放用户态（变更频率高、不跨租户）；但**禁止项片段必须由内核注入**且业务不可删——因为它连合规责任（判据 ③）。实现上：内核在装配 system prompt 时按固定顺序追加 `policy_block`，并在 trace 里记录其哈希，业务改不了、删不掉、还能被审计。

3. **为什么「限流 5k QPS」不等于「能扛 5k QPS」？**
   > 要点：Agent 的一次 Run 持续 30 秒、产生几十个 HTTP 请求。限请求 QPS 只约束了入口速率，真正决定容量的是**在途 Run 数**（L = λW）。5k 请求 QPS 折算成新建 Run 可能只有 120 QPS，但在途 Run 是 120×30 = 3,600 个。必须以「在途 Run」为容量与限流的主维度，否则洪峰时全员超时（第 11、23 章）。
