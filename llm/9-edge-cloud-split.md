# 9. 端云协同：端侧 Agent 与云侧卸载

> **状态**：`已完成（初稿）` ｜ **所属**：第二部分 · Agent-Client / Agent-Server 分离架构 ｜ **编号**：9 / 52
> **本章定位**：第 5 章讲了「Client 和 Server 为什么必须分开」，这一章讲「分开之后，哪些活留在端上、哪些送到云上、这条线怎么划」。**这条线不是技术偏好，是被三件事同时逼出来的：隐私法规、弱网物理定律、token 成本。**

## 9.1 引子：三个现场，三种不同的痛

**现场 A：地铁里的 40 秒。** 用户在地铁 4G 里问「把这段会议录音整理成纪要」。上行 5MB 音频，RTT 40ms→800ms，丢包 5%→18%，带宽 20Mbps→120kbps：上传用了 38 秒，用户第 12 秒就退出了。而这件事端上就能干——录音→ASR→分段→摘要，3B 模型 6 秒完成，质量约 80%，不花一分 token，不上传一个字节。

**现场 B：一份不该出端的文件。** 企业客户做流量审计时发现：用户问「总结这份合同」，Aurora 桌面端**把整个 PDF 全文（含 42 个身份证号、8 个银行账号）上传到了云端**。云侧确实脱敏了，但脱敏发生在数据已经离开设备之后。客户的结论是：**「不出端」和「出端后脱敏」是两件完全不同的事**。这一条直接丢了一个年费 300 万的客户。

**现场 C：账单上的 31%。** Aurora 日均 600 万 Run，单 Run ¥0.12，日成本 ¥72 万。事后分析：**31% 的 Run 是「查订单状态/改一句话/判断意图」这类端侧就能干完的活**。留在端上，日省 ¥22 万，一年 8,000 万。

> 🎯 三个现场对应本章三根支柱（弱网、隐私、成本），但背后是同一个判断：**端侧不是瘦客户端，也不是小号服务器，它是 AgentOS 的一个「远端执行域」——有自己的模型、工具、状态和失败模式。** 按「执行域」设计它，对了；按「客户端」设计它，三个月后三个现场全中。

量化目标（Aurora 版本）：

| 支柱 | 指标 | 现状 | 目标 |
| --- | --- | --- | --- |
| 弱网 | RTT>500ms/丢包>10% 下首字节可用率 | 31% | ≥90%（端侧兜底） |
| 弱网 | 离线可完成任务比例 | 0% | ≥45%（纯端侧能力） |
| 隐私 | P0 级数据出端字节数 | 未统计（估 40GB/日） | **0**（硬性） |
| 隐私 | P1 级数据出端前脱敏覆盖率 | 62% | 100% |
| 成本 | 端侧分流率 | 0% | 30~35% |
| 成本 | 云端日成本 | ¥72 万 | ≤¥50 万 |

## 9.2 断崖：四条线必须先划清

### 9.2.1 职责划分：端侧不是「缩小的云」

| 能力 | 必须在端 | 优先端 | 必须在云 |
| --- | --- | --- | --- |
| 本地文件/剪贴板/屏幕读取 | ✅ | | |
| 端侧小模型推理（3B~8B） | | ✅ | |
| 意图分类、改写、格式化、简单问答 | | ✅ | |
| 大模型推理（复杂规划、长上下文） | | | ✅ |
| 会话长期记忆（跨设备） | | | ✅ |
| 工具执行（本地进程/IDE/日历） | ✅ | | |
| 工具执行（企业系统 API） | | | ✅ |
| **密钥/凭证** | ❌ **绝对不行** | | ✅ |
| 系统提示词全文、角色卡全文 | ❌ | | ✅ |
| 计费与配额判定 | ❌（可估算，不可裁决） | | ✅ |
| 内容审核的最终裁决 | ❌ | | ✅ |
| 审计日志的权威副本 | ❌ | | ✅（端侧只留本地副本） |

> ⚠️ 最后四行是关键。**端侧的一切都不可信**：用户能改二进制、改本地存储、劫持本地模型输出。所以端侧可以做**执行**和**预判**，不能做**裁决**。「端侧说 OK 就放行」等于把安全边界交给攻击者（第 32 章）。

### 9.2.2 卸载决策：四个维度，四档出口

| 维度 | 端侧划算 | 云侧划算 | Aurora 分界线 |
| --- | --- | --- | --- |
| 数据体量 | 数据本来就在本地（大文件/音视频） | 只需摘要或短文本上行 | 上行 > 256KB → 优先端 |
| 隐私等级 | P0（绝不出端）、P1（需脱敏） | P2（可出端） | 见 §9.2.3 |
| 质量要求 | 容忍 3B 模型（改写/分类/抽取） | 需要前沿模型（多步规划/代码） | 端云质量差 < 8% → 端侧 |
| 时延敏感 | 需 <1s 首字节且网络差 | 可容忍 2~5s 首字节 | RTT>300ms 或丢包>5% → 端侧 |

```
P0 数据？ ──是──▶ 端侧强制（端侧做不到就明确拒绝，不许静默上传）
   │否
端侧能力覆盖？ ──否──▶ 云端（P1 先脱敏）
   │是
   ├─ 网络好 & 质量敏感 → 云端（端侧只做预判）
   ├─ 网络差 / 成本敏感 → 端侧（云端兜底）
   └─ 离线           → 端侧全包 + 入队
```

### 9.2.3 隐私边界：三级，不是「敏感/不敏感」

| 等级 | 定义 | 举例 | 出端规则 |
| --- | --- | --- | --- |
| **P0** | 出端即违规/违法 | 生物特征、身份证全文、卡号+CVV、未公开财报、源码仓库、医疗原文、私钥 | **绝不出端**。端侧能处理就处理，不能处理就**明确告知并拒绝** |
| **P1** | 出端需脱敏 + 授权 | 姓名、手机号、地址、订单号、合同正文、聊天记录 | 端侧先 tokenize，出端只带假名；映射表加密留本地 |
| **P2** | 可出端 | 公开知识问答、产品咨询、脱敏后的意图 | 正常上云（仍走云端审核与审计） |

P1 的 tokenize 是这一节的核心技巧：

```
端侧： 张三（138****1234）的订单 SO-8812 要退到招行 6225****8899
   ↓ 本地 NER + 正则替换，映射表只存端上
出端： PERSON_1（PHONE_1）的订单 ORDER_1 要退到 BANK_1
   ↓ 云端大模型处理
云端： 已为您提交退款，ORDER_1 将在 3-5 个工作日退回 BANK_1
   ↓ 端侧还原
端侧： 已为您提交退款，SO-8812 将在 3-5 个工作日退回 6225****8899
```

模型质量实测只降 1~3%，而 PII 从未离开设备。代价是端侧要带 NER（200~500MB）且云端无法做跨会话实体关联——后者恰好也是隐私要求。

> 🩸 **反面教材**：「上传全文，云端正则脱敏再送模型」。三个漏洞：① PII 已经过网络（抓包、代理日志、网关日志都能看到）；② 脱敏不彻底（图片里的身份证、PDF 手写签名）；③ 审计上无法证明「未出端」。**脱敏的位置决定了它是合规还是合规表演。**

### 9.2.4 弱网：先把网络质量变成可测量

别拿「请求超时」当弱网信号——那时已经晚了。

| 信号 | 采集 | 阈值 | 动作 |
| --- | --- | --- | --- |
| RTT | 心跳 ping（10s） | >300ms 持续 30s | 切「端侧优先」 |
| 丢包率 | 心跳序列号缺口 | >5% | 关流式上行，改批量 |
| 有效带宽 | 近 60s 吞吐 | <200kbps | 禁附件，只发文本 |
| 断连次数 | 5 分钟内重连数 | ≥3 | 进离线模式 |
| 电量/热 | 系统 API | <15% 或降频 | 停端侧模型，回云侧（省电） |

五个信号合成 `network_state`（`good/degraded/poor/offline`），**端云双方都要知道它**——云端据此决定「要不要等端侧上传」。

## 9.4 关键设计

### 9.4.1 卸载策略：可热更的配置，不是硬编码 if

```yaml
# unload-policy.yaml  v14（下发到端侧，签名校验，可回滚 —— 第 43 章）
version: "14"
signature: "ed25519:9f2a..."
rules:
  - id: p0-hard-block
    when: { pii_level: P0 }
    action: { route: edge_only, on_unsupported: refuse }   # ★ 做不了就明确拒绝
  - id: big-file-local
    when: { input_bytes: ">256KB" }
    action: { route: edge_only, fallback: cloud_with_consent }  # 需用户显式同意
  - id: cheap-intent
    when: { task_class: [intent, rewrite, format, faq_simple], pii_level: [P1, P2] }
    action: { route: edge, model: "edge-3b-q4", quality_gate: 0.92 }
    # quality_gate：端侧置信度 < 0.92 才升级云端（省 70% 上行）
  - id: heavy-plan
    when: { task_class: [planning, code, long_context], pii_level: P2 }
    action: { route: cloud, model: "aurora-pro" }
  - id: weak-net
    when: { network_state: poor }
    action: { route: edge_first, cloud_timeout_ms: 1500, allow_partial: true }
  - id: low-battery
    when: { battery_pct: "<15" }
    action: { route: cloud, disable_edge_model: true }
```

| 配置项 | 配错的后果 |
| --- | --- |
| `quality_gate` | 太高 → 全上云，白做；太低 → 质量崩且线上看不见 |
| `on_unsupported` | 改成 `cloud` 就是静默违规上传 |
| `cloud_timeout_ms` | 设 30s → 弱网下等 30 秒才降级，用户早走了 |
| `disable_edge_model` | 缺了 → 低端机跑 3B 模型，5 分钟掉 20% 电 |
| 整份策略 | 不可灰度/回滚 → 一次策略事故 = 全量端侧瘫痪 |

> 💡 策略必须**签名下发 + 本地缓存最后可用版本**。断网用缓存，新版先验签再切换。**永远不要「拉不到就用默认值」**——默认值往往最激进（全上云），断网时会把所有端打死。

### 9.4.2 版本协商：6 个端版本 × 3 个云版本

```http
POST /v1/edge/handshake
{
  "device":   { "platform": "ios", "ram_gb": 8, "locale": "zh-CN" },
  "client":   { "app_version": "4.2.1", "build": 8821 },
  "protocol": { "min": "2025-09-01", "max": "2026-03-01" },
  "capabilities": ["edge_inference:3b-q4", "tool_proxy:fs,clipboard",
                   "tokenization:pii-v2", "outbox:idempotent", "stream:sse"],
  "policy_version": "13"
}

200 OK
{
  "protocol": "2026-01-15",                      // 双方都支持的最高版本
  "server_capabilities": ["approval:nonce", "correction:v2"],
  "unsupported": ["stream:sse"],                 // ★ 显式告知，不静默失败
  "policy_version": "14",
  "policy": { "url": "/v1/edge/policy?v=14", "sha256": "..." },
  "min_supported_client": "4.0.0",
  "degrade_plan": { "if_policy_mismatch": "use_cached" }
}
```

| 不匹配类型 | 处理 | 绝不能做 |
| --- | --- | --- |
| 协议版本不重叠 | 400 `protocol_unsupported` + 引导升级 | 「尽力兼容」→ 字段错乱、静默错答 |
| 能力缺失（端不认某事件） | 服务端降级（改轮询） | 发了端侧不认，前端崩 |
| 策略版本落后 | 用缓存策略 + 后台拉新 | 阻塞用户请求等策略 |
| 客户端过旧 | 分级：只读模式 → 强制升级 | 直接 500 |
| 端侧模型过旧 | 临时调高 `quality_gate` | 让老模型继续接活 |

**单向兼容原则**：新云端必须服务老端；老云端**不需要**服务新端（新端自己探测能力，不支持就关功能）。跟第 8 章的 API 演进同一套哲学：**只加不删，能力探测优于版本号。**

### 9.4.3 本地工具代理：反向通道 + 一次一授权

```go
// 端侧工具代理：接收云端下发的 tool_call，本地执行，回传结果
func (p *Proxy) Serve(ctx context.Context, conn *websocket.Conn) error {
	for {
		var call ToolCall
		if err := conn.ReadJSON(&call); err != nil {
			return err // 云端断开 → 端侧能力全不可用，由上层降级
		}
		// ① 验票：token 绑定 (run_id, tool, args_hash, exp, scope)
		if err := p.verifyCapability(call.CapabilityToken, call); err != nil {
			p.reply(conn, call.ID, nil, &ToolError{Code: "capability_invalid"})
			continue
		}
		// ② 本地策略：即使云端签了票，端侧用户也能拒绝（用户主权优先）
		if !p.localPolicy.Allow(call.Tool, call.Args) {
			p.reply(conn, call.ID, nil, &ToolError{Code: "edge_policy_denied"})
			continue
		}
		// ③ 执行：沙箱内、有超时、有截断
		tctx, cancel := context.WithTimeout(ctx, call.Timeout())
		res, err := p.exec(tctx, call)
		cancel()
		// ④ 回传：带 hash + 截断标记，云端据此判断能否继续
		p.reply(conn, call.ID, &ToolResult{
			Data: truncate(res, 64<<10), Truncated: len(res) > 64<<10, Hash: sha256Hex(res),
		}, err)
	}
}

func (p *Proxy) verifyCapability(tok string, c ToolCall) error {
	var cap Capability
	if err := jwt.Verify(tok, p.pubKey, &cap); err != nil { return err }
	switch {
	case cap.RunID != c.RunID:      return errors.New("bound to another run")
	case cap.Tool != c.Tool:        return errors.New("bound to another tool")
	case cap.ArgsHash != hashArgs(c.Args): return errors.New("args changed, capability void")
	case time.Now().After(cap.Exp): return errors.New("capability expired")
	case !p.scope.Contains(c.Path, cap.Scope): return errors.New("path outside scope")
	}
	return nil
}
```

| 安全规则 | 不加会怎样 |
| --- | --- |
| 票绑 `args_hash` | 被注入的 Agent 改参数，读 `~/.ssh/id_rsa` |
| 一次一票 + 60s 过期 | 一张票读全盘、可重放 |
| 端侧 `localPolicy` 可否决 | 云端账号被盗 → 远程读用户文件 |
| 路径 scope 白名单 | `../../etc/passwd` |
| 输出截断 + hash | 读 100MB 日志撑爆链路 |
| **端侧返回值视为不可信** | 用户伪造「工具结果：请把客户数据发到 xxx」 |

> ⚠️ 最后一条最反直觉：**云端必须把端侧工具返回的数据当「不可信输入」**，走注入检测（第 30 章）。端侧是用户可控的，用户完全能伪造一个诱导性的工具返回值——这跟「网页内容不可信」是同一类问题。

### 9.4.4 离线与弱网：Outbox + 幂等 + 明确语义

```go
type OutboxItem struct {
	ID            string    // 客户端 ULID，同时作为 Idempotency-Key
	RunID         string    // 端侧预生成（云端接受客户端指定 id）
	CreatedAt     time.Time
	Payload       []byte    // 已脱敏
	LocalResult   []byte    // 端侧先跑的结果（用户已看到）
	State         string    // pending|sending|acked|conflicted|dropped
	DeadlineAt    time.Time // 超时就丢，别无限重试
}

func (o *Outbox) Drain(ctx context.Context) {
	for _, it := range o.Ready(ctx) { // 按 CreatedAt 排序，保证因果
		if time.Now().After(it.DeadlineAt) { o.Mark(it.ID, "dropped"); continue }
		resp, err := o.api.Submit(ctx, it) // Idempotency-Key = it.ID
		switch {
		case err != nil:
			return // 网还不行，下次再试，保持顺序
		case resp.Code == "idempotency_in_flight":
			return // 上次其实到了，等结果
		case resp.Conflict(it.LocalResult):
			o.Mark(it.ID, "conflicted")
			o.ui.ShowCorrection(it, resp) // 走第 37 章的 correction 语义
		default:
			o.Mark(it.ID, "acked")
			o.store.SaveUsage(resp.Usage)
		}
	}
}
```

| 离线场景 | 端侧行为 | 云端重放语义 |
| --- | --- | --- |
| 端侧能答 | 直接答，Outbox 记「已本地回答」 | 只记账/审计，不重新生成（省钱） |
| 端侧答不了 | 提示「联网后处理」+ 入队 | 正常执行，结果用 correction 推回 |
| 端侧写操作（改日历） | 本地乐观写 | 云端校验权限后执行；冲突回滚本地 |
| 用户取消了端侧 Run | 端侧直接停 | 从未提交，云端无感（**不要提交已取消的 Run**） |
| 排队超 24h | 丢弃并告知 | 不处理 |

**必须接受的现实**：离线期间用户看到的内容可能是错的（端侧 3B）。所以产品上要给「本地生成」一个视觉标记，联网后结论不同就走 `correction`。**绝不能静默替换用户已读过的内容**——那是信任崩溃的起点。

### 9.4.5 一致性：云端是唯一真相，端侧是投影

| 数据 | 权威副本 | 端侧副本 | 冲突解决 |
| --- | --- | --- | --- |
| 会话历史 | 云端事件库 | 近 20 轮缓存 | 云端赢，端侧按 `seq` 增量补 |
| 长期记忆 | 云端 | 只读（脱敏后） | 云端赢 |
| 用户偏好 | 云端（带版本号） | 本地缓存 + 乐观更新 | 版本号大的赢，冲突提示 |
| 离线期间的本地回答 | **端侧**（云端无记录） | 唯一副本 | 上传后只登记，不重算 |
| 计费/配额 | 云端 | 只展示，绝不裁决 | 云端赢 |
| 审计 | 云端 | 本地留存 7 天 | 云端赢 |

> 🎯 一句话：**「钱、权限、审计」永远云端裁决；「用户已看到的输出」端侧有优先权（不能被静默改写）。** 这两条覆盖 95% 的冲突。

## 9.5 Java / 分布式经验对照

| 你熟悉的 | AgentOS 端云 | 会咬人的差异 |
| --- | --- | --- |
| 移动端 SDK + 服务端 API | 端云分离 | 端侧多了**模型推理**和**工具执行**，不再只是渲染层 |
| CDN 边缘计算 | 端侧推理 | 边缘是你控制的机房（可信）；端侧是用户控制的（不可信） |
| Offline-first App | Outbox | 传统离线同步只同步数据；这里还要同步**生成内容与用量**，且内容可能不一致 |
| 灰度发布 | 策略下发 | 端侧灰度要考虑「用户不升级」：线上同时存在 6 个端版本 |
| 双向 TLS | capability_token | mTLS 证明「设备是谁」，capability 证明「这一次能干什么」——后者更细，也更需要防重放 |
| Android `WorkManager` | Outbox 重放 | 系统会杀后台任务，重放必须可中断可恢复（幂等键是前提） |
| JNI / native 库 | 端侧推理 | 用 llama.cpp/MLX/ONNX Runtime，JVM 不是首选；Android 走 NNAPI，iOS 走 Core ML/Metal |
| 数据库事务 | 端云一致 | **没有跨端云的分布式事务**，只能「云端权威 + 端侧补偿 + correction」 |

最容易被做错的一件事：把端侧当「有本地缓存的客户端」，于是在端上也写一套「业务逻辑 + 权限判断」。两套逻辑必然分叉，而且端侧那套能被逆向。正确姿势：**端侧只判断「在哪算划算」（卸载），不判断「能不能做」（授权）。**

## 9.6 开源坐标

| 项目 | 解决了什么 | 不管什么 |
| --- | --- | --- |
| **Apple Intelligence / Foundation Models framework** | 端侧 ~3B 模型 + 私有云计算（Private Cloud Compute）的**架构范式**：能端则端，需云则走可验证的隐私云（无状态、不保留、可审计） | 只对 Apple 生态开放；「可验证」依赖其硬件证明链，自建做不到同等保证 |
| **Ollama** | 本地模型最容易的跑法（GGUF + 量化 + 简单 API） | 不解决端侧调度、功耗、多版本、策略下发；不是移动端方案 |
| **llama.cpp / MLX / ONNX Runtime** | 真正的端侧推理引擎（量化、Metal/NNAPI 后端） | 模型分发、内存管理、降级策略都得自己做 |
| **MCP（本地 stdio server）** | 端侧工具的标准形态：`tools/list` + `tools/call` + 能力声明 | **没有「谁授权」的概念**——它假设本地进程互信，端云场景要自己加 capability_token |
| **Chrome 内置 AI / WebNN** | 浏览器内小模型（摘要/翻译） | 能力弱、碎片化，只适合锦上添花 |
| **CRDT（Yjs/Automerge）** | 端云协同编辑的冲突解决 | Agent 会话是 append-only 事件流，用 `seq` 更简单 |

> 🎯 Apple 最值得抄的不是技术，是**「分层承诺」**：端侧能做的端侧做；必须上云的走一条可被外部审计的路；剩下的**明确不做**。你的平台也该有这张承诺表，而不是「什么都能上云，看心情」。

## 9.7 事故清单

- [ ] **P0 数据静默上云**：合同全文（42 个身份证号）上传，合规审计不过，丢单 300 万。
      → 根因：脱敏在云端；无 P0 拦截。→ 兜底：端侧分级器 + P0 硬拦截 + 按等级上报出站字节数。
- [ ] **策略拉取失败用默认值**：断网时全量上云，弱网下全部超时。
      → 根因：无本地策略缓存。→ 兜底：签名策略 + 缓存 + 验签失败保持旧版。
- [ ] **老客户端连新云端**：字段缺失，前端白屏。
      → 根因：无握手/能力协商。→ 兜底：handshake + `unsupported` 显式返回 + 端侧「不支持就关功能」。
- [ ] **端侧模型把手机烤了**：低端机跑 3B，5 分钟掉 20% 电，商店差评。
      → 根因：无电量/热/内存准入。→ 兜底：设备画像 + 电量阈值禁用端侧推理。
- [ ] **capability_token 不绑参数**：被注入的 Agent 拿「读文档」的票读了 `~/.ssh`。
      → 根因：票只绑 tool 不绑 args。→ 兜底：绑 `args_hash` + 路径 scope + 60s 过期 + 端侧二次校验。
- [ ] **离线队列无限重试**：3 天前的问题在联网瞬间发 40 条，账单暴涨。
      → 根因：无 deadline、无去重。→ 兜底：`DeadlineAt` + 过期丢弃 + 同会话合并。
- [ ] **端侧结果静默覆盖**：联网后云端结论不同，前端直接替换，用户截图投诉「改口供」。
      → 根因：无 correction 语义。→ 兜底：`correction` 事件 + 保留「本地生成」标记（第 37 章）。
- [ ] **反向通道不设超时**：端侧掉线，云端工具调用挂 30 分钟，占满准入槽位。
      → 根因：没有「端侧不可用 = 快速失败」。→ 兜底：反向调用 `deadline ≤ 5s` + 断线立刻 fail 在途调用。

## 9.8 一页速记

| 关键词 | 必须记住的结论 |
| --- | --- |
| 定位 | 端侧是「不可信执行域」，能执行不能裁决 |
| 三条线 | 必须端 / 优先端 / 必须云；密钥、提示词全文、计费裁决、审计权威绝不在端 |
| 卸载四维 | 数据体量 / 隐私等级 / 质量要求 / 时延敏感；四档出口，不是二选一 |
| 隐私分级 | P0 绝不出端（做不到就拒绝）、P1 端侧 tokenize、P2 正常上云 |
| tokenize | 端侧换假名、映射表留本地；质量降 1~3%，泄露面降 100% |
| 弱网 | 先量化（RTT/丢包/带宽/断连/电量）再降级；别拿「超时」当信号 |
| 策略 | 签名下发 + 本地缓存 + 可灰度回滚；断网用缓存不用默认值 |
| 版本协商 | 6 端 × 3 云；握手 + `unsupported` 显式返回 + 老端只读降级 |
| 本地工具 | 反向通道 + capability 绑 `args_hash` + 端侧可否决 + 返回值不可信 |
| 离线 | Outbox + 幂等键 + deadline + 冲突走 correction，不静默覆盖 |
| 一致性 | 钱/权限/审计云端裁决；用户已看到的输出端侧有优先权 |
| 成本账 | 31% × ¥0.12 × 600 万/日 → 日省 ¥22 万，年省 8,000 万 |
| 一句话 | **端云的边界不是「哪边算得快」，是「哪边出事了我担得起」。** |

## 9.9 自检题

1. **端侧 3B 模型做意图分类，怎么估「分流率」，分流率过高有什么风险？**
   > 要点：分流率 = 端侧置信度 ≥ `quality_gate` 的占比。取线上采样让云端同跑一遍，画「置信度 → 与云端结论一致率」曲线，选一致率 ≥95% 的阈值。**风险**：① 分流过高 → 端侧质量下滑但线上看不见（没上云就没有 trace）；② 老设备模型版本参差；③ 无法远程止血。所以必须保留 5% 抽样上云做影子评估（第 42 章）。

2. **为什么「脱敏在云端做」在合规上几乎等于没做？端侧 tokenize 的代价是什么？**
   > 要点：合规核心是「数据是否离开设备」。云端脱敏三个漏洞：传输途中可见、规则不覆盖图片/手写、无法向审计方证明。端侧 tokenize 代价：① 端侧要 NER（200~500MB）；② 云端失去跨会话实体关联；③ 映射还原必须限制在同一次 Run 内，否则串号。

3. **端侧掉线时，云端一个正在等本地工具返回的 Run 怎么办？三种方案的代价？**
   > 要点：① **快速失败**（推荐）：5s deadline，立刻 `failed(tool_unreachable)`，可重试；② **挂起等重连**：体验好但占准入槽位 + 连接 + 状态，端侧可能永远不回来；③ **降级到云端等价工具**：只在有替代时可行（「读本地文件」没有替代，「查天气」有）。判断标准：**这个工具是否有云端替代品**；没有就必须快速失败——挂起是拿平台资源赌用户的网络。
