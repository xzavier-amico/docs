## 28.1 引子：副本从 40 扩到 200，P99 从 1.2s 涨到 14s

2026 年 4 月，Aurora 出现了一次「扩容反而更慢」的事故。时间线：

```
10:02  P99 从 1.2s 涨到 4s，触发告警
10:05  值班同学判断「负载高」，HPA 开始扩容（CPU 阈值 60%）
10:09  副本 40 → 120。P99 = 6.8s（更慢了）
10:12  手动把 maxReplicas 调到 200，副本 → 196。P99 = 14s，错误率 3%
10:18  CPU 利用率只有 31%，扩容完全无效，开始人工介入
10:31  定位到根因，回滚扩容 + 关掉批处理池 → P99 回到 1.5s
```

四个根因，全都是「传统扩容思路在 Agent 场景下失效」：

| # | 根因 | 现象 | 为什么扩容没用 |
| --- | --- | --- | --- |
| 1 | **上游有硬并发配额** | 196 个副本共用同一个 provider API Key，上游限「每 key 500 并发」 | 副本越多，429 越多；重试又放大 3 倍请求 → 雪崩 |
| 2 | **NAT 网关 conntrack 表打满** | 每副本 60 条长连接 × 196 = 11,760，但 NAT 网关 conntrack 上限 65,536，且短请求也走同一个出口 | 新建连接被静默丢弃，表现为「偶发超时」 |
| 3 | **限流计数器热 key** | 所有副本事先读同一个 Redis key 判断配额 | 单分片被打到 92%，Redis 延迟从 0.3ms 涨到 18ms |
| 4 | **HPA 指标选错了** | 用 CPU 扩容，但瓶颈是「在途长连接数」和「上游配额」 | CPU 31%，扩了也没用，反而放大了 #1 #2 |

> 🎯 **本章的核心命题**：
> **Agent 平台的容量单位不是「QPS」，是「并发的、活着的时间」——`并发 Run 数 × Run 时长`。**
> 你扩的是「处理请求的能力」，但你缺的是「同时挂住 1.2 万个 30 秒长连接、并且每个都在匀速消耗上游配额」的能力。这两件事的瓶颈完全不同，用 CPU 做指标必然失效。

## 28.2 为什么长连接 + 流式换了一套容量模型

### 28.2.1 三本账：QPS 账、连接账、Token 账

| 维度 | 传统无状态 API | Agent 流式平台 | 差的量级 |
| --- | --- | --- | --- |
| 请求时长 | 50~200ms | 首 token 2~8s，整体 30s | **×150** |
| 同时在线请求 | QPS × 0.1s ≈ 500 | QPS × 30s ≈ **12,000** | ×24 |
| 连接语义 | 短连接/keep-alive，可复用 | 一条连接绑一个 Run，**不可复用** | 连接数 = 并发数 |
| 内存 | 每请求 KB 级、随请求释放 | 每连接常驻 16~64KB 缓冲，跨 30s | ×30 的持有时间 |
| 失败模式 | 重试一次就好 | 重连意味着**重新拉上下文重算**（成本 ×N） | 重试是最贵操作 |
| 关键指标 | QPS、P99 延迟 | **TTFT P99、并发 Run 数、token/s、断连率** | 指标集不同 |
| 扩缩容信号 | CPU / RPS | 并发连接数 + 上游配额余量 | 完全不同的 HPA 指标 |

**Little's Law 是本章唯一必须记住的公式**：

```
L = λ × W

L = 系统内平均并发数（并发 Run 数）
λ = 到达率（Run 创建速率，不是 HTTP QPS）
W = 平均停留时间（Run 时长）

Aurora 峰值：λ = 400 Run/s，W = 30s
L = 400 × 30 = 12,000 条并发流式连接
```

所以那个「5k QPS」要拆开看：

```
入口 HTTP 请求 5,000 QPS
  ├── Run 创建           400 QPS  → 产生 12,000 并发长连接（×30s）
  ├── Run 状态轮询/心跳  3,200 QPS → 短请求，但每条都读 Redis
  ├── 会话/历史查询       900 QPS  → 短请求，读 PG/CH
  └── 附件上传/下载       500 QPS  → 带宽型，单独池
```

> 💡 **这个拆分决定了你 HPA 该用哪个指标**：短请求看 QPS + CPU；Run 创建看**并发连接数**和**上游配额占用**。混在一个 Deployment 里，你就只能选一个指标，另一个必然失控。**这是 §28.4 舱壁模式存在的第一个理由。**

### 28.2.2 连接账：把 fd、内存、TIME_WAIT 算成钱

```
单副本目标承载 2,000 条并发 SSE 连接
├── fd：2,000（客户端）+ 2,000（上游模型 HTTP 连接池）= 4,000
│        加日志/监控/健康检查 ≈ 4,100 → ulimit -n 必须 ≥ 8192，建议 65536
├── 内存：2,000 × (读缓冲 4KB + 写缓冲 8KB + 请求上下文 12KB) ≈ 48MB
│        加 Go runtime + 堆，实际 RSS ≈ 220MB（P99 请求上下文可能 100KB+）
├── goroutine：2,000 × 3（读/写/心跳） = 6,000，栈初始 8KB → 48MB 虚拟内存
└── 关闭成本：每条连接关闭产生 1 个 TIME_WAIT（主动关闭方），持续 60s
        如果 QPS 波动导致每秒关 500 条 → 30,000 个 TIME_WAIT 堆积在客户端侧
        → 客户端端口耗尽（ephemeral port 范围默认 32768~60999，约 28,000 个）
```

**TIME_WAIT 那条最容易被忽略**：用户在 30 秒里刷新了 5 次页面，每次都是「客户端主动断开」，但如果是**服务端**因为超时/优雅关停主动断开，TIME_WAIT 就堆在服务端。滚动更新时 196 个副本同时断开几万条连接，会让出口 SNAT 端口耗尽——表现是「服务明明健康，但连不上」。

缓解手段（都不是银弹，要组合）：
- 服务端不要主动关（除非超时）；
- `SO_REUSEADDR` + `tcp_tw_reuse=1`（仅对出向连接有效）；
- 优雅关停时**先停止接受新连接，再等在途 Run 自然结束**（第 46 章）；
- 长连接用 WebSocket 而不是「短轮询 + 反复重建」（第 7 章）。

## 28.3 压测的特殊性：四种「假压测」和它们掩盖的事故

大部分团队的压测结论是「能扛 8k QPS」，上线后 3k QPS 就崩。原因是压测模型和真实流量不是同一个东西。

| # | 假压测做法 | 掩盖了什么真实事故 |
| --- | --- | --- |
| 1 | **只压 API，不读流** | 压测客户端收到 header 就断开 → 服务端写事件时对端已 RST → 真实的写阻塞/背压问题完全没测到 |
| 2 | **消费者读得飞快** | 真实用户网络慢（3G/弱网），写缓冲堆积 → 内存涨到 OOM。压测里消费者 10ms 读完一个 chunk，永远不触发背压 |
| 3 | **不测断连与重连** | 真实场景 5%~15% 的 Run 会断连重试（切后台、地铁、Wi-Fi 切换）→ 重连风暴 + 上下文重算成本 |
| 4 | **恒定速率，无尖峰** | 真实流量是「早 9 点集体上班」的阶跃：1 分钟内从 800 涨到 5,000 QPS → 排队、冷启动、连接风暴全在这一分钟 |

### 28.3.1 该压什么指标

| 层 | 指标 | Aurora 目标 | 为什么是它 |
| --- | --- | --- | --- |
| 接入 | 连接建立成功率、建连 P99 | > 99.9%、< 50ms | 建连失败是最难排查的故障（表现为「偶发超时」） |
| 流式 | **TTFT P50 / P95 / P99** | 2s / 4s / 8s | 用户感知的唯一指标 |
| 流式 | 事件间隔 P99 | < 500ms | 超过 500ms 用户会觉得「卡住了」 |
| 吞吐 | token/s（每副本、全局） | 单副本 ≥ 80k token/s 转发 | 这才是流式服务的真实产能 |
| 稳定 | 并发连接数 / 峰值 / 增长速率 | 12,000 / 30,000 / 1,000/s | 决定 HPA 与限流 |
| 质量 | 断连率、重连成功率 | < 3%、> 99% | 断连 = 重算 = 成本与延迟双杀 |
| 上游 | 429 率、上游配额占用率 | < 0.5%、< 70% | 上游配额是**最硬的墙**，副本数不能突破它 |
| 资源 | fd 使用率、SNAT 端口使用率 | < 60%、< 50% | 这两个满了，一切健康检查都显示正常 |

### 28.3.2 一个能测出真问题的压测器（Go）

关键不是并发数，是**模拟真实的慢消费者 + 断连 + 尖峰**。

```go
// loadgen/sse.go —— 只保留关键部分
type Scenario struct {
    PeakQPS      int           // 5000
    RampUp       time.Duration // 60s，阶跃增长，不是线性
    RunDurP50    time.Duration // 30s，实际用对数正态分布采样
    SlowClientP  float64       // 0.25：25% 的客户端是慢消费者
    SlowReadRate time.Duration // 每 400ms 读一次（模拟 3G）
    DropP        float64       // 0.08：8% 的客户端中途断开
}

func (s *Scenario) oneRun(ctx context.Context, c *http.Client) error {
    req, _ := http.NewRequestWithContext(ctx, "POST", s.URL, body())
    req.Header.Set("Accept", "text/event-stream")
    resp, err := c.Do(req)
    if err != nil { return err }
    defer resp.Body.Close()

    // 关键 1：不要用 bufio.Scanner 默认缓冲（64KB），要模拟真实读速
    br := bufio.NewReaderSize(resp.Body, 4096)
    slow := rand.Float64() < s.SlowClientP
    dropAfter := time.Duration(0)
    if rand.Float64() < s.DropP {
        dropAfter = time.Duration(rand.Int63n(int64(15 * time.Second)))
    }
    start := time.Now()

    for {
        if dropAfter > 0 && time.Since(start) > dropAfter {
            resp.Body.Close()      // 关键 2：模拟真实断连（不是读完再关）
            metrics.Dropped.Inc()
            return nil
        }
        if slow {
            time.Sleep(400 * time.Millisecond)   // 关键 3：慢消费者 → 触发服务端背压
        }
        line, err := br.ReadString('\n')
        if err != nil { return nil }
        if strings.HasPrefix(line, "data:") {
            metrics.Tokens.Inc()      // 记录 token/s，而不是「请求数」
        }
        if strings.HasPrefix(line, "event: done") { return nil }
    }
}
```

> ⚠️ **压测器本身要先被压测**。Go 写的压测器在单机上跑到 5k QPS × 30s 并发 = 15 万 goroutine 时会自己先 OOM。至少 3 台压测机，每台报自己的时间戳，用 PTP/NTP 对齐，否则你没法算端到端 P99。

### 28.3.3 尖峰与「冷启动惩罚」

早 9 点的流量阶跃是最危险的时刻，因为三件事同时发生：

```
09:00:00  流量 800 QPS → 5,000 QPS（1 分钟内）
          ├── 连接建立速率 1,000/s，需要新开 12,000 条连接
          ├── 新 Pod 冷启动：镜像拉取 15s + 连接池预热 8s + JIT/GC 预热
          └── 上游 provider 也在这个时间点被全网打满（它也有早高峰）
```

对策是**提前扩容而不是响应式扩容**：按历史曲线在 08:45 预热到目标副本的 80%（CronHPA / KEDA 定时触发器），把「响应式」留给真正的异常。响应式扩容的最快反应时间也要 30~90 秒（指标采集 + 决策 + 调度 + 就绪），对 1 分钟阶跃来说太慢了。

## 28.4 舱壁模式：把「一起死」拆成「轮流死」

舱壁（Bulkhead）的名字来自船体分舱：一个舱进水，船还能开。在 Agent 平台里它是**唯一能阻止「一个租户/一个模型/一类请求拖死全部」的结构性手段**。

### 28.4.1 四层舱壁

```
                        ┌─────────────────────────────────────┐
                        │          入口网关（无状态）           │
                        │   只做鉴权 / 路由 / 连接管理          │
                        └───────┬──────────┬──────────┬───────┘
                                │          │          │
              ┌─────────────────▼──┐  ┌────▼─────┐  ┌─▼──────────────┐
              │  池 A：交互流量     │  │ 池 B：批处理│  │ 池 C：大租户独占 │
              │  60% 容量           │  │ 20% 容量   │  │ 20% 容量         │
              │  SLO: TTFT<4s      │  │ SLO: 无    │  │ SLO: 合同约定     │
              ├────────────────────┤  ├───────────┤  ├──────────────────┤
              │ 子舱 A1..A8        │  │ 子舱 B1   │  │ 每租户一个子舱     │
              │ 按 tenant_hash%8   │  │ 低优先级  │  │ T-0001 … T-0020   │
              │ 每子舱独立信号量    │  │ 可被抢占  │  │ 独立配额+独立 key  │
              └────────────────────┘  └───────────┘  └──────────────────┘
                        │                   │                   │
              ┌─────────▼───────────────────▼───────────────────▼──────┐
              │        上游配额池（按 provider + model 分舱）            │
              │  provider-A: 500 并发 / provider-B: 800 并发            │
              │  ★ 每个上流舱有独立信号量，副本数不能突破它 ★            │
              └────────────────────────────────────────────────────────┘
```

四个维度，每个都要有**独立的并发信号量**（不是 QPS 限流，是并发数）：

| 维度 | 隔离手段 | 崩了会怎样（不做） | 成本代价 |
| --- | --- | --- | --- |
| **请求类型** | 交互/批处理/后台评估 分池，批处理可被抢占 | 客户 A 的批量数据清洗跑满配额，全部 C 端用户 TTFT 从 2s 涨到 15s | 资源利用率 75% → 60% |
| **租户** | Top N 大租户独占子池；小租户共享池 + 每租户信号量 | 一个大客户跑批打挂全平台（噪声邻居） | 池化率下降，成本 ×1.2~1.4 |
| **模型** | 每个 provider/model 独立连接池 + 独立信号量 | 某一个 provider 慢，把共享连接池占满，其他模型也一起超时 | 连接数变多，内存 +10% |
| **工具/沙盒** | 沙盒执行独立节点池，不与 API 节点混部 | 沙盒里的死循环把 API 节点的 CPU 抢光 | 节点数 +15%（见第 29 章） |

**成本怎么算**（这句话能帮你过预算评审）：

```
池化部署：资源利用率 75% → 有效容量 = 物理容量 × 0.75
分舱部署：资源利用率 55% → 有效容量 = 物理容量 × 0.55
成本倍数 = 0.75 / 0.55 = 1.36

用 36% 的机器钱，买「一个大客户打不挂全平台」。
反过来说：如果这个客户一年付的钱 < 36% 的机器成本，那你就该让他挂，
或者给他单独报价（第 44 章的多租户隔离三档）。
```

### 28.4.2 每租户并发信号量（Go，带公平性）

```go
// bulkhead/tenant.go
// 目标：单租户最多占 maxPerTenant 个并发；总容量满时不是无脑拒绝，而是按租户排队
type Gate struct {
    total    chan struct{}                 // 全局并发上限
    perT     sync.Map                      // tenantID -> chan struct{}
    maxPerT  int
    waitQ    *fairQueue                    // 每租户最多排队 N 个，防队列本身被占满
}

func (g *Gate) Acquire(ctx context.Context, tenant string) (release func(), err error) {
    sem, _ := g.perT.LoadOrStore(tenant, make(chan struct{}, g.maxPerT))
    s := sem.(chan struct{})

    select {
    case s <- struct{}{}:                  // 先抢租户名额（最便宜，本地内存）
    default:
        return nil, ErrTenantConcurrencyExceeded   // 立刻拒，不要排队（排队会放大延迟）
    }

    select {
    case g.total <- struct{}{}:            // 再抢全局名额
        return func() { <-g.total; <-s }, nil
    case <-ctx.Done():
        <-s
        return nil, ctx.Err()
    case <-time.After(g.queueTimeout):     // 全局满 → 短排队（200ms），超时即拒
        <-s
        return nil, ErrPlatformBusy
    }
}
```

> 💡 **为什么「租户满」立刻拒、「全局满」短暂排队**：租户自己打满自己的配额，是它的策略问题，让它立刻收到 429（它自己会退避）；全局满说明平台压力大，短暂排队能吸收抖动，但排队超过 200ms 就没意义了（用户已经感知卡顿）。**这两条是不同的产品语义，不要用同一个超时。**

## 28.5 热 key 与大租户降噪

### 28.5.1 一次请求打了多少次 Redis

```
一次 Run 创建的路径：
  鉴权 / API Key 校验      1 op
  配额检查（令牌桶）        3 op（读桶、写桶、读租户余额）
  租户配置/模型路由表       2 op
  余额查询                 2 op
  语义缓存查询（可选）      2 op
────────────────────────────────
合计                     10 op / 请求
峰值 5,000 QPS × 10 = 50,000 ops/s
```

50k ops/s 对 3 分片的 Redis 集群（约 300k ops/s 能力）只占 17%，看起来毫无压力。**但热 key 不看平均**：

| 热 key | 谁在读 | 打爆方式 | 解法 |
| --- | --- | --- | --- |
| `tenant:cfg:{tid}` | 该租户每个请求 | Top 租户 456 QPS × 1 = 456 ops/s（还不算热），但**如果 TTL=1s，每秒回源 DB 456 次** | 本地 LRU + 30s TTL + 变更走 pub/sub 失效 |
| `limit:{tid}` 令牌桶 | 该租户每个请求 | 大租户 456 QPS × 3 = 1,368 ops/s 全在**一个分片的一个 key** 上 | 本地令牌桶（预分配 1/N 配额）+ 每秒从 Redis 同步一次 |
| 大模型的路由表 | 全平台 | 5,000 QPS × 2 = 10,000 ops/s 单 key → 单分片 10% | 全量内存 + 版本号轮询 |
| 语义缓存的 embedding 索引 | 全平台 | 每个请求一次向量检索 | 分片 + 本地热点缓存（前 1 万个高频 query 命中率可到 40%） |

### 28.5.2 本地令牌桶：用误差换吞吐

```go
// ratelimit/local_bucket.go
// 每个 Pod 只拿 1/N 的配额，本地的，不查 Redis。误差 = 一个同步周期 × 速率
type LocalBucket struct {
    capacity float64
    tokens   float64
    rate     float64      // 每秒补充 = 租户总配额 / 副本数
    last     time.Time
}

func (b *LocalBucket) Allow(n float64) bool {
    now := time.Now()
    b.tokens = math.Min(b.capacity, b.tokens+now.Sub(b.last).Seconds()*b.rate)
    b.last = now
    if b.tokens >= n { b.tokens -= n; return true }
    return false
}

// 每 1s 从 Redis 同步「租户总剩余配额」，重算本地 rate
// 精度损失：最坏情况下 N 个 Pod 各自多放行 1 秒的量 → 超发 N × rate × 1s
// 如果租户配额 456 QPS、36 个副本 → 最坏超发 456 个请求（1 秒的量），可接受
```

> ⚠️ **超发是可接受的，Redis 被打爆不可接受**。这是限流系统里最重要的一次取舍取舍：**限流的目的不是「精确」，是「保护下游」**。为了保护下游而把限流器自己变成瓶颈，是典型的反向优化。

### 28.5.3 大租户降噪的四个动作

| 动作 | 做法 | 效果 |
| --- | --- | --- |
| **准入分层** | 大租户单独 API Key + 单独上游配额 + 单独子池 | 完全避免抢公共池 |
| **请求合并** | 同租户同秒内的重复请求（比如同一个仪表盘刷新）合并成一次 | 头部租户常有 20%~40% 的重复请求 |
| **缓存优先级** | 大租户的 prompt 前缀缓存命中最优（它们的历史稳定） | 命中率高 → 成本低 → 上游压力小 |
| **错峰引导** | 批处理 API 给「夜间折扣价」 | 把 30% 的批处理流量挪出峰值时段 |

## 28.6 容量规划：从 P99 和 token 速率反推副本与限流值

这一节是本章唯一「必须动笔算」的部分。所有数字都是 Aurora 的实际参数，你可以替换成自己的。

### 28.6.1 副本数：从并发与 CPU 两个方向算，取大者

**方向一：CPU / 处理能力**

```
峰值短请求 λ = 5,000 req/s
单请求 CPU 时间 S = 8ms（JSON 解析 2ms + 鉴权/限流 2ms + 组装请求 3ms + 日志 1ms）
每副本核数 c = 4
目标利用率 ρ = 0.6（留 40% 给突发与长尾）
─────────────────────────────────────────────
N = ceil( λ × S / (c × ρ) )
  = ceil( 5000 × 0.008 / (4 × 0.6) )
  = ceil( 40 / 2.4 ) = 17 副本
```

**为什么 ρ 只能取 0.6**——用排队论算一下等待时间（M/G/1 近似，`Wq = S × ρ/(1-ρ)`）：

| ρ | 队列等待 Wq | 端到端影响（S=8ms） |
| --- | --- | --- |
| 0.5 | 8ms | 可忽略 |
| 0.6 | 12ms | 可忽略 |
| 0.75 | 24ms | 开始可见 |
| 0.85 | 45ms | 明显 |
| 0.95 | **152ms** | 长尾爆炸，P99 直接翻倍 |

**方向二：长连接 / 内存**

```
并发连接 L = 12,000（§28.2.1）
单副本目标承载 2,000 条 → 需要 6 副本
单副本内存：2,000 × 24KB = 48MB 缓冲 + 200MB 基础 = 250MB
→ 不是瓶颈
```

**方向三：上游配额（最容易被忽略，也最硬）**

```
provider-A 每 API Key 500 并发；Aurora 只用 1 个 Key（企业协议）
→ 走 provider-A 的并发 Run 不能超过 500
→ 若 40% 流量走 A：12,000 × 40% = 4,800 并发需求 vs 500 可用
→ 必须多 Key（向厂商申请 10 个 Key，共 5,000 并发）或分流
→ 这个数字如果算错，扩容到 200 副本只会让 429 变成 40%（§28.1 事故）
```

**方向四：AZ 容灾**

```
单 AZ 故障时，剩余容量必须 ≥ 峰值 × 60%（剩 40% 靠降级撑）
N_final = max(17, 6) × 2（N+1 冗余）= 34
按 3 AZ 均分 → 36 副本（每 AZ 12）
单 AZ 故障：剩 24 副本 / 17 需求 = 1.41 倍余量 ✅
```

### 28.6.2 token 速率：如果自建推理，要多少卡

```
峰值并发 Run = 12,000
单 Run 输出速率 = 1,200 token / 30s = 40 token/s
全局输出速率 = 12,000 × 40 = 480,000 token/s
────────────────────────────────────────────
自建 vLLM（H100 + 8B 模型，continuous batching）：
  单卡 decode 吞吐 ≈ 3,000 token/s（示例值，必须实测）
  所需卡数 = 480,000 / 3,000 = 160 卡

输入侧 prefill：
  每 Run 12,000 输入 token，30s 内 5 次调用 → 2,400 token/次
  全局输入速率 = 12,000 × 40 × ... → 简化为 400 Run/s × 12,000 = 4,800,000 token/s
  单卡 prefill 吞吐 ≈ 25,000 token/s
  prefill 卡数 = 4,800,000 / 25,000 = 192 卡

合计 ≈ 352 卡；若 80% 流量走第三方 API → 自建只需 70 卡
```

> 💡 **这个算式最重要的用途不是「买多少卡」，而是让你发现**：**prefill 和 decode 的卡数在同一个量级**，而不是「decode 是大头」。很多团队的容量模型只算 decode，上线后发现 TTFT 崩了——因为 prefill 才是首 token 延迟的主导项。**这正是第 18 章要死磕前缀缓存的原因：缓存命中能直接砍掉 prefill。**

### 28.6.3 限流值：从容量反推，而不是拍脑袋

```
平台安全容量 = 峰值 × 1.3 = 6,500 QPS（30% 余量吸收突发）

规则 1（防单点压垮）：任何单租户配额 ≤ 平台安全容量 × 25% = 1,625
规则 2（按历史定基线）：配额 = max( 最近 30 天 P99 × 1.2, 套餐下限 )
规则 3（总配额可以超卖）：Σ 所有租户配额 ≈ 3 × 安全容量
     —— 因为所有租户同时打满的概率约为 0（实际并发峰值只有配额的 1/3）
规则 4（必须有全局兜底）：不管租户配额怎么配，全局并发信号量硬上限 = 15,000
     —— 这一条是防止「规则 3 超卖失效」的最后一道闸
```

**一个必须接受的事实**：配额总和一定会超过容量。这不是 bug，是**统计复用**（和运营商卖 1000 户共享 100 条电话线是同一个原理）。但前提是你有 `规则 4` 这个硬闸，以及 §28.7 的熔断预案。

### 28.6.4 容量模型一页表

| 参数 | 符号 | Aurora 值 | 怎么得到 |
| --- | --- | --- | --- |
| 入口峰值 QPS | λ_http | 5,000 | 业务预测 / 历史 × 1.5 |
| Run 创建速率 | λ_run | 400 /s | 埋点统计（占入口 8%） |
| 平均 Run 时长 | W | 30s | 埋点 P50，注意长尾要用 P90 算资源 |
| 并发 Run 数 | L = λW | 12,000 | Little's Law |
| 单请求 CPU | S | 8ms | pprof / 火焰图 |
| 单副本核数 | c | 4 | 规格 |
| 目标利用率 | ρ | 0.6 | 排队论，见上表 |
| 副本数 | N | 36 | `ceil(λS/cρ) × 2`，AZ 均分 |
| 单副本连接上限 | — | 2,000 | 内存与 fd 反推 |
| 全局输出 token 速率 | — | 480k/s | `L × 40` |
| 单租户配额上限 | — | 1,625 QPS | `容量 × 25%` |
| 配额超卖倍数 | — | 3× | 统计复用，靠全局闸兜底 |

## 28.7 灰度放量与熔断预案

### 28.7.1 灰度：按「流量形态」分阶段，不按百分比无脑放

Agent 平台的灰度有个特殊要求：**新版本的行为变化可能在低流量下看不出来，在高流量下才炸**（排队、缓存命中率、上游配额）。所以灰度要**同时控制流量比例和流量形态**。

| 阶段 | 流量 | 时长 | 观察指标 | 通过条件 |
| --- | --- | --- | --- | --- |
| 0 内部 | 员工账号 + 影子流量 | 24h | 错误率、TTFT、成本/次 | 错误率 < 0.1% 且成本偏差 < 5% |
| 1 小租户 | 5%，且**排除 Top 50 租户** | 12h | 同上 + 工具成功率 | 全部达标 |
| 2 中租户 | 20%，仍排除 Top 50 | 24h | + P99、断连率 | 全部达标 |
| 3 含大租户 | 50%，含 Top 50 中的 5 个 | 24h | + 上游 429 率、队列深度 | 429 < 0.5% |
| 4 全量 | 100% | — | 全指标 | — |

**为什么要「排除 Top 50」**：大租户的流量特征（高并发、长上下文、高缓存命中）与长尾完全不同。先用小租户验证「逻辑对不对」，再用大租户验证「容量扛不扛得住」。反过来做，你会在第 1 小时就被一个大客户打回滚。

### 28.7.2 熔断预案：三类阈值，三种动作

```yaml
# policy/breaker/2026-04.yaml
version: "2026-04-15"
breakers:
  - name: provider_a_health
    scope: upstream            # 上游 provider 级
    window: 30s
    conditions:
      error_rate_5xx: { threshold: 0.05, for: 30s }
      latency_p99:    { threshold: 20s,  for: 60s }
    action: open               # 打开熔断器，切到 provider_b
    half_open: { after: 60s, probes: 20, success_rate: 0.9 }

  - name: ttft_degradation
    scope: slo                  # SLO 级：不是错误，是变慢
    window: 5m
    conditions:
      ttft_p99: { threshold: 8s, for: 2m }
    action: degrade             # 不熔断，降级：交互池→小模型，批处理池→暂停
    degrade_steps:
      - { target: batch_pool,  action: pause }
      - { target: interactive, action: route_to_small_model, max_ratio: 0.4 }
      - { target: interactive, action: disable_semantic_cache }   # 缓存也会成为瓶颈

  - name: global_concurrency
    scope: platform
    conditions:
      inflight_runs: { threshold: 15000, for: 10s }
    action: shed               # 甩负载：新 Run 直接 503 + Retry-After
    shed_priority: [batch, background_eval, free_tier, paid_tier]
```

**三类动作的区别，团队必须达成共识**（否则每次事故都在争论「为什么不熔断」）：

| 动作 | 语义 | 用户体验 | 什么时候用 |
| --- | --- | --- | --- |
| `open`（熔断） | 切断，换路 | 无感（如果有备份） | 上游明确故障 |
| `degrade`（降级） | 继续服务，但质量下降 | 可感知（答案变短/变笨） | 上游变慢但仍可用 |
| `shed`（甩负载） | 明确拒绝 | 明确失败 + 可重试 | 平台自身到极限 |

### 28.7.3 熔断的「假恢复」陷阱

半开状态（half-open）放 20 个探针请求，全部成功就闭合——这个做法在 Agent 场景有个坑：**上游恢复通常是「渐进的」**，探针 20 个成功不代表能接 12,000 并发。

```
t=0    熔断（错误率 40%）
t=60   半开，放 20 个探针 → 全成功
t=61   闭合，瞬间接 12,000 并发
t=63   上游再次被打满 → 又熔断
t=124  再半开 → 再闭合 → 再熔断  ← 震荡，每 60 秒一个周期
```

修法是**渐进恢复**：闭合后先接 10% 流量，每 30 秒加 10%，同时监控上游延迟。这本质上是 TCP 的慢启动，只不过对象是「上游配额」。

## 28.8 Java / 分布式经验对照

| 你熟悉的 | Agent 平台里 | 会咬人的差异 |
| --- | --- | --- |
| Tomcat 线程池 + `maxThreads=200` | 「并发」= 12,000 | 🔴 线程模型根本对不上；必须 Go/异步或 WebFlux，阻塞模型下 12,000 并发 = 12,000 线程 = 24GB 栈 |
| HPA 按 CPU 扩容 | 按「并发连接数 + 上游配额余量」扩容 | 🔴 用 CPU 扩容在 §28.1 事故里是直接元凶；要暴露自定义指标（KEDA / Prometheus Adapter） |
| Sentinel 的 QPS 限流 | 需要**并发数**限流（信号量）+ 成本限流 | 🟡 QPS 限不住长连接：400 QPS 进来就是 12,000 并发，限 QPS 完全没保护作用 |
| Hystrix 舱壁（线程池隔离） | 每租户/每上游一个信号量 | 🟢 思路完全一致，只是别用线程池（goroutine 更便宜） |
| Nginx `proxy_read_timeout` | SSE 必须调大（≥ 300s）且关 buffering | 🔴 默认 60s + `proxy_buffering on` 会把流攒起来，TTFT 从 2s 变 30s |
| `keepalive` 连接池 | 上游 HTTP 连接池要按并发数配 | 🟡 `MaxIdleConnsPerHost` 默认 2，12,000 并发下会疯狂建连（这是最经典的 Go 踩坑） |
| 压测用 JMeter | 需要能读 SSE、能模拟慢消费者 | 🔴 JMeter 的 SSE 支持弱且吃内存；建议自研 Go 压测器（§28.3.2） |
| 容量评审交「峰值 QPS」 | 要交「并发 Run 数 × 时长 × token 速率」 | 🔴 只报 QPS 的容量评审等于没评审 |

## 28.9 开源坐标

| 项目 | 对应什么 | 缺什么 |
| --- | --- | --- |
| **K8s HPA / KEDA** | 扩容；KEDA 支持 Prometheus 自定义指标与 cron 触发器 | 默认不支持「并发连接数」指标，要自己 expose（Prometheus Adapter）；且反应时间 30~90s，处理不了 1 分钟阶跃 |
| **Chaos Mesh** | 注入网络延迟、Pod 故障、DNS 故障 | 不模拟「上游 429」「慢消费者」这类 Agent 特有故障，要写自定义 Chaos |
| **k6** | HTTP/WS 压测，脚本化，有 SSE 支持（以官方文档为准，能力仍在演进） | 大规模长连接压测单机跑不动；需要分布式执行器 |
| **vegeta** | 恒定速率 HTTP 压测，简洁 | 不解析流式响应，测不了 TTFT 和 token/s |
| **Envoy / Nginx** | 连接管理、限流、熔断 | ⚠️ 必须为 SSE 关 buffering；Envoy 的 `stream_idle_timeout` 默认 5 分钟，长 Run 会被切 |
| **Sentinel / Resilience4j（Java 栈）** | 限流熔断 | 没有「按租户公平队列」和「并发信号量按租户」的原语，要自己包一层 |
| **vLLM / SGLang** | 自建推理的 continuous batching 与吞吐 | 它们的指标（`num_running_reqs`、`kv_cache_usage`）才是你该接的容量信号，而不是 GPU 利用率 |

## 28.10 事故清单

- [ ] **事故 A：用 CPU 做 HPA 指标** → 现象：扩容 5 倍，P99 从 4s 涨到 14s。→ 根因：瓶颈是上游配额与连接数。→ 兜底：HPA 换 KEDA + 自定义指标（`inflight_runs`、`upstream_quota_used_ratio`），CPU 只做下限保护
- [ ] **事故 B：副本数突破上游并发配额** → 现象：429 率 40%，重试 3 次后放大成雪崩。→ 兜底：上游配额做成「带信号量的资源池」，副本抢不到就排队/降级；429 率单独告警
- [ ] **事故 C：NAT conntrack / SNAT 端口打满** → 现象：服务健康，但 5% 请求「偶发超时」。→ 兜底：监控 `conntrack_count / nf_conntrack_max` 与 SNAT 端口使用率；长连接走独立出口 IP
- [ ] **事故 D：压测客户端读得飞快** → 现象：压测能扛 8k QPS，上线 3k 就 OOM。→ 根因：没测背压，写缓冲堆积。→ 兜底：压测场景必须包含 25% 慢消费者 + 8% 随机断连（§28.3.2）
- [ ] **事故 E：Nginx 开了 `proxy_buffering`** → 现象：TTFT 从 2s 变成 25s（等于流式失效）。→ 兜底：`proxy_buffering off` + `X-Accel-Buffering: no`，并在发布门禁里加「流式端到端 TTFT 测试」
- [ ] **事故 F：灰度直接放到含大租户的全量池** → 现象：第 1 小时一个大客户把新版本打挂，全量回滚。→ 兜底：灰度阶段先排除 Top 50（§28.7.1）
- [ ] **事故 G：熔断半开震荡** → 现象：每 60 秒熔断-恢复一次，用户看到间歇性失败。→ 兜底：渐进恢复（10% → 100%，每 30s 加 10%）
- [ ] **事故 H：尖峰时冷启动** → 现象：早 9 点 1 分钟内流量涨 6 倍，新 Pod 还没就绪。→ 兜底：CronHPA 提前 15 分钟预热到 80%，镜像预热（DaemonSet 预拉）

## 28.11 一页速记

| 关键词 | 必须记住的结论 |
| --- | --- |
| 容量单位 | 不是 QPS，是 `并发 Run 数 = 到达率 × Run 时长`（Little's Law） |
| 三本账 | QPS 账、连接账（fd/内存/TIME_WAIT）、token 账，三者瓶颈完全不同 |
| 副本公式 | `N = ceil(λ×S / (c×ρ)) × 冗余`，ρ 取 0.6（0.95 时队列等待是 0.6 时的 12 倍） |
| 上游配额 | 最硬的墙，副本数不能突破它；否则扩容等于加速雪崩 |
| 压测 | 必须模拟慢消费者 + 断连 + 阶跃尖峰，否则测出的数字没有意义 |
| 关键指标 | TTFT P99、并发连接数、token/s、断连率、429 率、fd/SNAT 端口使用率 |
| 舱壁 | 四层：请求类型 / 租户 / 模型（上游）/ 工具沙盒；成本 +36%，买「不一起死」 |
| 热 key | 限流器本地化（超发 1 秒的量可接受，Redis 被打爆不可接受） |
| 配额超卖 | 总配额 ≈ 3× 容量是正常的，但必须有全局并发硬闸兜底 |
| 灰度 | 按「流量形态」分阶段，先排除 Top 50 大租户 |
| 熔断 | 三类动作要分清：`open` / `degrade` / `shed`；恢复要渐进（慢启动） |
| 一句话 | **扩容解决「处理不过来」，不解决「挂不住」和「上游不给」。** |

## 28.12 自检题

1. **你的服务峰值 5,000 QPS，平均响应 30 秒，你能算出需要多少副本吗？还缺什么信息？**
   > 要点：先拆分流——5,000 QPS 里真正产生 30 秒长连接的只有 Run 创建（假设 400/s），其余是短请求。并发 Run = 400 × 30 = 12,000。副本数要同时满足三个约束：① 短请求 CPU：`ceil(5000×8ms/(4核×0.6)) = 17`；② 长连接：12,000 / 单副本 2,000 = 6；③ 上游配额：12,000 × 走该 provider 的比例 ≤ 该 provider 并发上限。取 max 再乘 AZ 冗余。**只说「5000 QPS 要多少副本」而不拆分，是没法算的。**

2. **为什么在 Agent 平台里，Sentinel 那种「按 QPS 限流」几乎不起保护作用？**
   > 要点：QPS 限的是「入口速率」，但资源占用是「并发数 × 时长」。400 QPS 的 Run 创建就是 12,000 条同时活着的连接，限 QPS 到 400 一点没减少并发压力。必须用**并发信号量**限流，并且按租户/按上游分别设信号量。另外还需要「成本限流」（预算令牌，第 33 章），因为一次 Run 的成本能差 100 倍。

3. **熔断器从半开恢复后立刻闭合，为什么在 Agent 场景特别危险？正确做法是什么？**
   > 要点：上游（模型 provider）的恢复是渐进的，20 个探针成功只证明「能接 20 个并发」，不证明「能接 12,000 个」。立刻闭合会导致「熔断-打满-再熔断」的震荡，用户看到周期性失败。正确做法是渐进恢复：闭合后先接 10% 流量，每 30 秒加 10%，同时监控上游 P99 与 429 率，任何一项恶化就退回上一档。这本质上是给上游做 TCP 慢启动。
