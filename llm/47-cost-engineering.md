## 47.1 引子：一封把 CTO 叫进会议室的邮件

季度经营会前一天，CFO 发来一封邮件，只有一张表：

| 月份 | Run 量（万/月） | 模型账单 | 订阅收入 | 毛利率 |
| --- | --- | --- | --- | --- |
| 7 月 | 5,400 | $1.71M | $1.35M | **-27%** |
| 8 月 | 6,800 | $2.14M | $1.58M | **-35%** |
| 9 月 | 8,200 | $2.59M | $1.92M | **-35%** |

邮件的正文是：「你们说这是 SaaS 生意，SaaS 的毛利率应该是 70%。我们连续三个月是负数，而且**Run 量涨 21%，账单涨 21%，收入只涨 21%——你们卖一个亏一个**。」

CTO 把平台组叫来，三个小时后查清了原因。**不是模型涨价，是三件自己人干的蠢事**：

1. **提示词改版没人算账**。8 月中旬为了让回答「更周全」，有人在客服 Agent 的系统提示里把 few-shot 示例从 6 条加到 14 条，单次调用输入从 4.2k token 涨到 8.0k。一次 Run 有 5 次调用，等于每次 Run 多付 19k 输入 token。**仅这一项，月账单 +$610k。**
2. **路由被关掉忘了恢复**。8 月 3 日一次事故中，值班同学把「简单问题走小模型」的路由策略整体切到「全量走大模型」做兜底，事后没人回滚。到 9 月底，78% 的调用走了最贵的档。**这一项，月账单 +$480k**——而混合均价从 $1.05/M 涨到 $2.41/M，翻了 2.3 倍。
3. **免费额度被刷**。9 月新增注册账号 4.1 万个（8 月是 9,200 个），其中 1,200 个账号用同一批手机号段、同一批 UA、跑同一套 prompt 模板，白嫖掉 61 万次 Run。**成本 $19k，收入 $0**——金额不大，但它说明你的额度策略是敞开的。

三件事叠加，把 8% 的毛利打成了 -35%。而它们**没有一件是「模型太贵」**：

> 🩸 **本章的第一条判断**：Agent 平台的成本问题，90% 不是「单价贵」，而是**「用错了档」「算不清账」「没人为用量负责」**。前两个是工程问题，第三个是组织问题——而工程问题的解法通常便宜得多。

再看一个更根本的数字。我们把 9 月的账倒过来算：8,200 万次 Run，收入 $1.92M，**平均每次 Run 收入 $0.0234**；成本 $2.59M，**平均每次 Run 成本 $0.0316**。每个 Run 净亏 0.82 美分，乘以 8,200 万，就是每月 $670k 的窟窿。

**成本工程的全部目标，就是把这两个数字的关系反过来，并且让它稳定。** 这一章讲怎么做到。

## 47.2 单位经济模型：先把口径钉死，再谈优化

### 47.2.1 四层口径：为什么「一次对话花了多少钱」是个没法回答的问题

「一次对话花了多少钱」这句话里藏了四个不同的东西。**平台上线第一年最常见的争议，全部来自这几个口径混用**：

| 口径 | 定义 | 谁会问 | 常见错法 |
| --- | --- | --- | --- |
| **模型调用（LLM call）** | 一次 `messages → completion`，含 token 与单价 | 工程师调 prompt | 只看 `prompt_tokens`，不算缓存折扣与推理 token |
| **Step** | 一次「模型调用 + 可能的工具/检索」原子步骤 | 排查「哪一步贵」 | 把并行工具算成一个 step，成本摊错 |
| **Run** | 用户提交的一个任务，含 N 个 Step、重试、失败调用 | 产品定价、SLO | 只算成功 Run，把失败与重试的成本漏掉（漏掉的通常是 8~15%） |
| **Session / 会话** | 一段时间内同一用户的多轮 Run | 客户成功、ARPU | 把「会话」当成「一次对话」，跨天多轮没合并 |

> ⚠️ **最贵的一个错法**：成本只算成功 Run。Aurora 实测，失败 Run（含超时、模型错误、被用户取消）平均成本是成功 Run 的 **0.62 倍**，但它们在总成本里占 **12%**。你不算它，你的单位成本就系统性低估 12%，然后你的定价就系统性亏 12%。

本书统一用 **Run 口径做单位经济**（因为它是计费和 SLO 的边界），用 **Step 口径做优化**（因为它是可动手的粒度）。

### 47.2.2 每 Run 成本的完整算式

先给价目表（示例，**真实价格以厂商官方价格页为准**；这里只取结构，不取具体数字）：

| 档位 | 输入 $/M token | 缓存命中输入 $/M | 输出 $/M | 典型用途 |
| --- | --- | --- | --- | --- |
| 大模型（旗舰） | 2.50 | 0.25（约 1 折） | 10.00 | 规划、成文、复杂推理 |
| 中模型 | 0.80 | 0.08 | 3.20 | 常规工具决策 |
| 小模型（快） | 0.15 | 0.015 | 0.60 | 意图识别、改写、摘要、判定 |

> 💡 [Anthropic 的缓存计价](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)按读、写和有效期拆分；例如 5 分钟缓存写入为普通输入的 **1.25×**，不是在普通价之外再收 1.25×。其他厂商与模型有自己的档位；按实际计价表归类。

**单次 Run 成本**：

```
C_run = Σ_{i=1..N} [ T_normal,i × p_in(model_i)
                   + T_read,i   × p_cache_read(model_i)
                   + T_write,i  × p_cache_write(model_i)
                   + T_out,i    × p_out(model_i) ]
      + Σ_j C_tool_j
      + C_infra_run
```

- 普通输入、缓存读取和缓存写入是互斥的计费桶。若 `T_in` 是包含三类的总输入，`T_normal = T_in − T_read − T_write`；若厂商已拆桶，就直接映射。若输出另有独立计价的桶，也先拆成互斥类别再求和，不把输出的明细字段重复计费。
- `C_tool_j`：第 j 次工具调用的外部成本（三方 API 按次计费、沙盒按秒计费）
- `C_infra_run`：CPU/内存/带宽/存储/向量检索按 Run 摊销的基础设施成本

Aurora 的一次客服 Run 示意（5 次模型调用 + 3 次工具，表中未发生单独计价的缓存写入；`T_in` 包含命中的输入）：

| # | 步骤 | 模型档 | T_in | 其中缓存 | T_out | 成本 |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | 意图识别 + 路由 | 小 | 1,800 | 1,500 | 60 | $0.0001035 |
| 2 | 规划（选工具） | 大 | 6,500 | 6,000 | 300 | $0.00575 |
| 3 | 工具决策（查订单） | 大 | 7,200 | 6,000 | 420 | $0.00870 |
| 4 | 检索结果摘要 | 小 | 9,000 | 0 | 250 | $0.00150 |
| 5 | 成文（800 字） | 大 | 8,400 | 6,000 | 480 | $0.01230 |
| — | 工具 × 3 | — | — | — | — | $0.00060 |
| — | 基础设施摊销 | — | — | — | — | $0.00260 |
| | **合计** | | **32,900** | **19,500** | **1,510** | **$0.0315535（约 $0.0316）** |

```
Run 成本 $0.0316 的构成（Aurora 优化前）

普通输入           ███████████████▏  37%   $0.011645
命中缓存的输入     █████▋            14%   $0.0045225
输出 token         ████████████████  39%   $0.012186  ← 本算例输出单价是普通输入的 4 倍
工具（三方 API）   ▊                  2%   $0.0006
基础设施           ███▎               8%   $0.0026
                                     ─────
                                     100%   $0.0315535（约 $0.0316）
```

**这张图要教你的第一件事**：输出 token 只占用量约 4.4%，却占成本约 39%。在本例，同模型少生成一个 token 比少读一个普通输入 token 省得更多；究竟优化哪一桶，还要看能删多少、实际价格以及对质量的影响。

### 47.2.3 每千 token 毛利：把成本换算成「单位经济学」

投资人和财务不看 Run，他们看两个数：**每千 token 的收入/成本比**、**每租户毛利**。

```
毛利_per_1k_token = ( R_run / T_total ) × 1000 − ( C_run / T_total ) × 1000
毛利率            = 1 − C_run / R_run
```

Aurora 9 月实况（T_total = 34.4k token/Run）：

| 指标 | 优化前（9 月） | 优化后（目标） | 说明 |
| --- | --- | --- | --- |
| 每 Run 收入 | $0.0234 | $0.0234 | 定价没动 |
| 每 Run 成本 | $0.0316 | $0.0142 | -55%（§47.6 的清单） |
| 每 Run 毛利 | **-$0.0082** | **+$0.0092** | 从亏到赚 |
| 毛利率 | **-35%** | **+39%** | |
| 每千 token 收入 | $0.00068 | $0.00068 | |
| 每千 token 成本 | $0.00092 | $0.00041 | |
| 每千 token 毛利 | **-$0.00024** | **+$0.00027** | 行业习惯按百万口径看，×1000 即 -$0.24/M → +$0.27/M |

> 🎯 **必须记住的一条线**：假设你要 60% 毛利率，`C_run ≤ 0.4 × R_run = $0.0094`——也就是要在 $0.0316 的基础上砍 **70%**。**单靠工程优化砍不到 70%（现实天花板是 -50~-55%）。剩下的必须靠「提价」或「套餐分档」。**
> 这就是 FinOps 的另一半：**成本工程不是无限降本，而是找到「哪些场景值得用贵模型、哪些必须走便宜档」的分界线，然后把它变成产品定价。**

## 47.3 结构：成本归因管道

成本数据不是「财务拉个账单」能解决的，它必须是一条**在线埋点 → 离线核算 → 归因 → 对账 → 反哺优化**的管道：

```
  ┌───────────── 在线（每个 Step 都要做，延迟 < 1ms） ─────────────┐
  │                                                              │
  │  LLM 调用返回 usage ──▶ ① 计量 Metering                       │
  │  (input/output/cache  │   tokens, model, price_card_version  │
  │   /reasoning tokens)  │   流式：先按预估写，结束按实际覆盖       │
  │                       ▼                                      │
  │  ② 计价 Rating ──▶ 读价目表（版本化），算 micro-USD，整数运算   │
  │                       ▼                                      │
  │  ③ 归因打标 Attribution ──▶ tenant/scene/agent/model/step/     │
  │                            prompt_ver/role_card_ver/plan      │
  └───────────────────────────┬──────────────────────────────────┘
                              ▼
  ┌──────────── 近线（分钟级） ────────────┐   ┌──── 离线（日级） ────┐
  │ ④ 成本流水 cost_fact（幂等写入）        │   │ ⑦ 供应商对账         │
  │ ⑤ 实时聚合 → 看板 / 预算熔断            │──▶│   usage API vs 我们  │
  │ ⑥ 预算刹车（超限降档/拒绝）             │   │   差额 > 0.5% 告警   │
  └───────────────┬────────────────────────┘   └──────────┬───────────┘
                  │                                       │
                  ▼                                       ▼
     ⑧ 优化回路：单位成本 Top-N 场景 → 提示词瘦身 / 路由 / 缓存 / 压缩 / 蒸馏
                  │
                  ▼
     ⑨ 产品回路：成本结构 → 定价、套餐、免费额度、SLA 档位
```

**这条管道里最重要的设计决策是：计量与计价必须在线做，聚合与归因允许离线。** 因为在线做才能**在烧穿之前刹车**（第 23 章的预算令牌、第 27 章的预扣），离线做只能事后心疼。

## 47.4 关键设计

### 47.4.1 计量与计价：整数、版本化、可重放

成本计算有三条铁律，违反任何一条都会在半年后变成对不上的账：

1. **不用浮点**。用 `int64` 存 micro-USD（1e-6 美元），或用定点数。`0.1 + 0.2 != 0.3` 在百万级流水上会累积成真实的钱。
2. **价目表版本化**，并且**按「事件发生时刻」的版本计价**，不是按「结算时刻」。否则厂商 10 月调价，你 9 月的账会全部重算。
3. **可重放**：给一条 `cost_fact` 记录 `(usage, price_card_version, model_id)`，任何时候能重算出同一个数。

```go
// cost/pricecard.go —— 价目表（只读，随配置中心下发，带版本号）
type PriceCard struct {
    Version    string // 如 "2026-09-01"，必须写进每条成本流水
    ModelID    string
    InMicro    int64  // 每 1M token 的 micro-USD
    CacheMicro int64  // 命中缓存的输入单价
    OutMicro   int64
    ReasonMicro int64 // 仅用于独立计价、已从普通输出剔除的推理 token
    CacheWriteMicro int64 // 缓存写入的全价，按命中的写入档位配置
}

// cost/rating.go
type Usage struct {
    NormalIn, CacheRead, CacheWrite, NormalOut, Reason int64 // 互斥桶
}

// Micro 返回本次调用的成本，单位 micro-USD（1e-6 USD）
// 教学版：输入已校验且乘加不溢出；最后按 micro-USD 向下取整
func (p PriceCard) Micro(u Usage) int64 {
    total := u.NormalIn*p.InMicro +
        u.CacheRead*p.CacheMicro +
        u.CacheWrite*p.CacheWriteMicro +
        u.NormalOut*p.OutMicro +
        u.Reason*p.ReasonMicro

    return total / 1_000_000
}
```

> ⚠️ 归一化放在厂商适配层。Anthropic 的原生 `input_tokens` 不含 `cache_read_input_tokens` 和 `cache_creation_input_tokens`，不再扣减；以总量上报的厂商，先做互斥拆分。若分桶对不上总量，不截成零继续扣款：保留原始用量并转对账。推理 token 若已含在输出且按相同单价收费，不另计。单测至少覆盖普通输入、全写入、全命中、混合、总量冲突与推理明细；多个写入档位分别计价。生产还要按合同处理溢出、舍入和舍入层级。见第 27 章。

### 47.4.2 归因：把成本打到四个维度上

归因的意义不是「知道贵」，而是「知道**该找谁改**」。Aurora 的 `cost_fact` 表：

```sql
CREATE TABLE cost_fact (
    run_id            text        NOT NULL,
    step_no           smallint    NOT NULL,
    attempt           smallint    NOT NULL DEFAULT 1,  -- 重试次数，重试成本也要归因
    call_id           text        NOT NULL,

    -- 归因维度（缺一不可，缺了就没法切片）
    tenant_id         text        NOT NULL,
    project_id        text,
    scene             text        NOT NULL,  -- customer_service / coding / analytics
    agent_id          text        NOT NULL,
    model_id          text        NOT NULL,
    model_tier        text        NOT NULL,  -- flagship / mid / small
    prompt_ver        text        NOT NULL,
    role_card_ver     text        NOT NULL,
    route_policy_ver  text        NOT NULL,
    config_ver        text,                  -- 低代码配置版本（第 49 章）

    -- 用量与金额（整数 micro-USD）
    tokens_in         int         NOT NULL,
    tokens_cache_read int         NOT NULL DEFAULT 0,
    tokens_out        int         NOT NULL,
    tokens_reason     int         NOT NULL DEFAULT 0,
    price_card_ver    text        NOT NULL,
    cost_llm_micro    bigint      NOT NULL,
    cost_tool_micro   bigint      NOT NULL DEFAULT 0,
    cost_infra_micro  bigint      NOT NULL DEFAULT 0,
    saved_by_cache_micro bigint   NOT NULL DEFAULT 0, -- 假设未命中的成本 − 实际成本

    -- 生命周期
    is_failed         boolean     NOT NULL DEFAULT false,
    is_billable       boolean     NOT NULL DEFAULT true,  -- 免费额度/内部测试为 false
    created_at        timestamptz NOT NULL,
    PRIMARY KEY (run_id, step_no, attempt, call_id)       -- 幂等：重复写入直接冲突
);

-- 按场景×模型档的日聚合（物化视图，供看板与告警）
CREATE MATERIALIZED VIEW cost_daily_scene AS
SELECT date_trunc('day', created_at) d, tenant_id, scene, model_tier,
       sum(tokens_in) tin, sum(tokens_out) tout,
       sum(cost_llm_micro + cost_tool_micro + cost_infra_micro) micro,
       sum(saved_by_cache_micro) saved,
       count(*) FILTER (WHERE is_failed) failed_calls,
       count(*) calls
FROM cost_fact GROUP BY 1,2,3,4;
```

**归因的三个坑**（每个都真实发生过）：

| 坑 | 错法 | 后果 | 正解 |
| --- | --- | --- | --- |
| **共享成本** | 检索、rerank、缓存写入、评估调用的成本不归因 | 8~15% 成本「不知去向」，毛利永远算不平 | 三层摊法：直接归因（LLM/工具）→ 按用量摊销（检索/rerank）→ 平台管理费（评估/离线，按 Run 数摊） |
| **失败与重试** | 只归因成功的调用 | 单位成本低估 12% | 失败调用归给**发起它的租户**（我们的 bug 我们认，用户的坏输入用户付），`is_failed=true` 单独统计 |
| **缓存收益** | 只记实际成本，不记节省额 | 优化没有正反馈，没人愿意做缓存 | 显式记 `saved_by_cache_micro`，看板上和成本并列展示 |

### 47.4.3 优化优先级清单：按 ROI 排序，别按喜好排序

这是全章最该被打印出来贴在墙上的表。**顺序不能变**，因为前面的几项「改动小、见效快、可回滚」，后面的「改动大、周期长、有质量风险」。

| 优先级 | 手段 | 预估节省（占总成本） | 改动成本 | 见效 | 主要风险 | 详见 |
| --- | --- | --- | --- | --- | --- | --- |
| **P0** | **前缀缓存 / 精确缓存** | **18~35%**（输入部分 -30~-60%） | 1~2 周 | 立即 | 前缀顺序错了就 0 命中；缓存键漏租户 = 泄露 | 24、18 |
| **P1** | **模型路由（分档）** | **20~40%** | 2~4 周 | 2 周 | 路由判错 → 质量掉；要有兜底升档 | 26 |
| **P2** | **提示词瘦身** | **8~18%** | 1 周 + 评测 | 1 周 | 删掉示例可能掉点，必须过评测门禁 | 16、40 |
| **P3** | **上下文压缩 / 引用折叠** | **10~25%** | 3~6 周 | 1 个月 | 丢关键约束 → 幻觉率上升 | 18、19 |
| **P4** | **语义缓存** | **5~20%** | 3~4 周 | 1 个月 | **误命中是真事故**，阈值必须 A/B | 24 |
| **P5** | **批处理 / 错峰**（Batch API、离线队列） | **3~8%** | 1~2 周 | 立即 | 只适用于非交互场景 | 11 |
| **P6** | **蒸馏 / 微调小模型** | **40~60%**（对应场景） | 3~6 个月 | 半年 | 泛化差、维护成本、能力退化 | 41、42 |

**一个真实的串联账**（Aurora 从 $0.0316 走到 $0.0142，-55%）：

```
起点                        $0.0316   ────────────────────────
P0 前缀缓存（命中率 24%→62%） -0.0042   输入贵的那部分被压掉
P1 路由（78% 降档）          -0.0068   大模型调用从 3 次降到 1.2 次
P2 提示词瘦身（-38% 输入）    -0.0026   few-shot 14 条 → 6 条 + 结构化约束
P3 上下文压缩（历史摘要）     -0.0021   多轮场景，第 5 轮起收益最大
P4 语义缓存（阈值 0.93）      -0.0014   仅客服场景，命中 11%
P5 批处理（离线评估走 batch）  -0.0003
                          ────────
优化后                      $0.0142   （-55.1%）
```

> 💡 **为什么 P0 是缓存而不是「换便宜模型」**：缓存是**唯一不需要拿质量换成本**的手段——命中的是同一个答案。而路由会掉点、压缩会丢信息、蒸馏会泛化差。**先做不损失质量的事，再做需要拿质量换的事**，这是排序的唯一标准。

### 47.4.4 免费额度与滥用防护：给的是额度，不是漏洞

免费额度是获客手段，也是**最大的成本敞口**——因为它的边际成本是真实的，收入是 0。

**先算一条红线**：

```
每个免费账号的最大成本 = 额度 Run 数 × C_run ≤ 0.3 × CAC
Aurora: CAC ≈ $180 → 上限 ≈ $54
若 C_run = $0.0316 → 最多给 1,700 次 Run；若优化到 $0.0142 → 可给 3,800 次
```

给 5,000 次免费 Run 而不做防护，等于每个注册送 $158——**灰产会帮你把它变成 100 万美元的账单**。

**额度分层**（不是「一注册给 500 次」）：

| 层级 | 触发条件 | 额度 | 防护 |
| --- | --- | --- | --- |
| 匿名 / 未验证 | 邮箱注册 | 20 Run/天，仅小模型 | 强制人机验证、出口 IP 频控 |
| 观察期 | 手机/企业邮箱验证 | 200 Run/月 | 单 IP ≤ 3 账号，设备指纹去重 |
| 转正 | 绑定支付方式 | 1,000 Run/月 | 正常风控 |
| 企业试用 | 销售审批 | 20,000 Run/30 天 | 单一域名、合同约束 |

**滥用形态与对策**：

| 形态 | 特征信号 | 对策 |
| --- | --- | --- |
| 批量注册 | 同 IP 段/同 UA/注册时间聚集 | 设备指纹 + 图聚类 + 延迟发放额度 |
| 免费额度当 API 用 | 请求模板高度相似（prompt 指纹） | 相似度聚类，超阈值转付费 |
| 长上下文塞满 | 单 Run 输入 > p99 × 3 | 按 token 而非按次数计额度（关键！） |
| 拿平台当免费算力 | 代码执行/工具调用占比异常 | 工具调用单独计数与限额 |
| Key 泄露被薅 | 地域突变、QPS 突变、模型偏好突变 | Key 分级 + 异常速率熔断 + 强制轮换 |

> 🎯 **一条设计原则**：**免费额度必须按「token + 工具调用 + 沙盒秒数」的复合单位计，不能按「次数」计。** 按次数计，用户会用 20 次把 200 万 token 塞进来；按复合单位计，你天然免疫长上下文攻击。这条和第 23、32 章是一套东西。

### 47.4.5 成本看板字段与预算告警规则

看板不要做「总花费折线图」——那个数字没人能据此做决策。**要做的是「单位成本 × 归因切片」**：

| 看板区块 | 必含字段 | 回答什么问题 |
| --- | --- | --- |
| 单位经济 | `cost_per_run`、`revenue_per_run`、`gross_margin`、`cost_per_1k_tokens` | 我们卖一个赚不赚钱 |
| 归因 Top-N | 按 `tenant` / `scene` / `agent` / `model_tier` / `step_no` 的成本排名 + 环比 | 钱花在哪，谁的锅 |
| 缓存效率 | `cache_hit_ratio`（按前缀/精确/语义分列）、`saved_by_cache_micro` | 缓存值不值得继续投 |
| 路由分布 | 各 `model_tier` 的调用占比与平均成本 | 路由有没有被绕过/关掉 |
| 异常 | `cost_anomaly_score`、单 Run 成本 p50/p99/p99.9 | 有没有失控循环、被刷 |
| 对账 | 我方计量 vs 厂商账单的差额与差额率 | 账算得对不对 |

预算与告警规则（可直接落成配置）：

```yaml
# finops/budgets.yaml —— 由策略中心下发（第 43 章），热更、可回滚
version: finops-v12
currency: USD

budgets:
  - id: platform-monthly
    scope: platform
    window: month
    limit_micro: 300_000_000_000        # $300k 软上限（示例，按实际盘）
    actions:
      - at: 0.80
        do: notify          # 通知 FinOps + 平台负责人
      - at: 1.00
        do: degrade         # 全平台路由强制降一档（大→中）
      - at: 1.20
        do: shed            # 拒绝非付费租户的新 Run，返回 429 + 明确文案
  - id: tenant-daily
    scope: tenant
    window: day
    limit_micro: 50_000_000            # $50/天/租户，超出走套餐外计费
    actions:
      - at: 0.90
        do: notify
      - at: 1.00
        do: require_prepay  # 转预付费，不预扣不放行（第 27 章）
  - id: run-guardrail
    scope: run
    limit_tokens: 300_000              # 单 Run token 硬上限（含重试）
    limit_wall_clock_s: 300
    limit_tool_calls: 40
    actions:
      - at: 1.00
        do: kill_and_report # 立即终止 + 明确错误码 + 记入异常样本
alerts:
  - name: CostPerRunSpike
    expr: histogram_quantile(0.99, sum by (le,scene)(rate(agent_run_cost_micro_bucket[1h]))) / 1e6 > 0.12
    for: 10m
    severity: page
    runbook: "单 Run 成本 P99 超 $0.12：查失控循环（step>20）、查提示词版本变更、查路由是否被切全量大模型"
  - name: CacheHitDrop
    expr: avg_over_time(agent_cache_hit_ratio[30m]) < avg_over_time(agent_cache_hit_ratio[7d] offset 1h) - 0.15
    for: 15m
    severity: ticket
    runbook: "命中率掉 15pt：多半是有人改了 system prompt 前缀顺序或加了时间戳变量"
  - name: MarginBreach
    expr: sum(rate(cost_llm_micro[1d])) / sum(rate(revenue_micro[1d])) > 0.6
    for: 2h
    severity: page
```

## 47.5 Java / 分布式经验对照：会计和计费不是一件事

| 你熟悉的东西 | Agent 成本工程的对应物 | 会咬人的差异 |
| --- | --- | --- |
| `BigDecimal` 算钱 | `int64` micro-USD + 定点乘除 | Go 里 `float64` 更诱人，但**必须忍住**；Java 用 `long` 存 micros，别用 `BigDecimal` 进热路径（一次 Run 5 次调用 × 5k QPS，`BigDecimal` 的分配与 GC 很诚实） |
| 话单（CDR）计费 / rating engine | 计价器（Rating）+ 价目表版本 | 传统计费「用量已知、单价固定」；这里**用量在流式过程中逐步确定、单价随厂商随时变、还有缓存折扣与推理 token** |
| 财务月结、`account_move` | 预扣—结算—对账三段式（第 27 章） | 传统账本「一天一结」；这里**一次 Run 结束就得结算**，且用户随时可能断连导致「已花未结」 |
| 支付对账（渠道账单 vs 内部流水） | 厂商 usage API vs 我方 `cost_fact` | 厂商账单**滞后 24~48h**，且可能事后修正；所以对账要「按天滚 7 天」，不是只看昨天 |
| 幂等键（支付订单号） | `(run_id, step_no, attempt, call_id)` | 传统幂等键是业务生成的；这里的 `call_id` 由网关生成，**模型侧重试会产生新 call_id**，要小心重复计费 |
| Hystrix/Sentinel 熔断 | 成本熔断（按 token/金额） | 传统熔断看错误率；这里要看**金额速率**（$/min），因为一次失控 Run 的错误率是 0 |
| Prometheus + Grafana | 同上，但指标维度要加 `tenant/scene/model` | 维度基数（cardinality）会炸：10 万租户 × 6 场景 × 5 模型 = 300 万序列。**租户维度只进 Top-N 聚合与日志，不进指标标签** |

> 🩸 最经典的一课：**Java 团队做计费，第一版通常会给每个租户打指标标签**，然后在 3 万租户时把 Prometheus 打成 OOM。解法是「指标只留 `scene/model_tier` 低基数维度，租户级走 ClickHouse 明细查询」。

## 47.6 开源坐标：这块开源能给你什么

| 能力 | 代表项目 | 它能给你 | 它给不了 / 会咬你 |
| --- | --- | --- | --- |
| 代理层用量与预算 | **LiteLLM**（Proxy） | virtual key、按 key/user 的 `max_budget`、spend tracking、模型价格表 | 预算只管到「key」，管不到「租户/场景/步骤」；没有复式账本、没有对账、没有定价与开票；价格表要你自己维护 |
| 单次调用的成本观测 | **Langfuse** | 每个 generation 的 token 与 cost、模型价格定义、按 trace/用户聚合 | 是「观测」不是「账本」：可被采样、可丢弃、不可作为结算依据 |
| 网关层可观测与缓存 | Helicone、Portkey | 请求级成本、缓存、限流 | 同上是观测口径；缓存 key 设计仍要自己做 |
| 基础设施成本分摊 | **OpenCost / Kubecost** | K8s 维度的 CPU/内存/存储成本，按 namespace/label 分摊 | 只覆盖 `C_infra_run` 那 8%；对 token 成本一无所知 |
| 云账单真相 | AWS CUR / GCP Billing Export / 阿里云账单 | 最终账单，SKU 粒度 | 滞后 24~48h，粒度到 SKU 不到租户；**只能用来对账，不能用来运营** |
| 单位经济建模 | 无（Spreadsheet 为主） | — | 这块没有开源方案，因为它是你的商业模式 |

> 🎯 **判断**：开源的「计量（metering）」很成熟，「核算 + 归因 + 预算强制执行 + 对账」的组合**没有**。LiteLLM + Langfuse 能让你在两周内看到「大概花了多少」，但要回答「这个租户这个场景这一步为什么贵、该找谁改」，你必须自己建 `cost_fact`。

## 47.7 事故清单：成本工程上线后最可能怎么炸

- [ ] **事故 A：价目表硬编码，厂商调价后全线错账。** 现象：10 月 1 日厂商降价 40%，你的成本看板纹丝不动，毛利报表全是假的。→ 根因：价格写在代码常量里。→ 兜底：价目表进配置中心 + 版本号进 `cost_fact` + 每月自动比对厂商价格页。
- [ ] **事故 B：缓存写入被重复计费。** 现象：账单比预想高 8%，查出来 `cache_creation_input_tokens` 没算，或者算了两次。→ 根因：不同厂商字段名不同、口径不同。→ 兜底：为每个 provider 写口径适配器 + 契约测试（第 48 章）+ 与厂商 usage API 每日对账。
- [ ] **事故 C：路由被临时关闭后再没恢复。** 现象：三个月后发现 78% 调用走了最贵档，多花 $1.4M。→ 根因：降级开关没有 TTL、没有到期告警。→ 兜底：所有「兜底型开关」强制带 `expires_at`，到期自动回滚并通知（第 43 章）。
- [ ] **事故 D：成本熔断把正常业务杀了。** 现象：月末最后一天全平台大面积 429，付费客户投诉。→ 根因：预算按「月」设，前 29 天跑太猛，最后一天触发 `shed`。→ 兜底：预算要按「日配额 × 剩余天数」平滑，且 `shed` 只对免费层生效，付费层走 `degrade`。
- [ ] **事故 E：免费额度被刷穿。** 现象：一夜之间 4 万注册、60 万次 Run、成本 $19k、收入 $0。→ 根因：按次数计额度 + 无设备指纹。→ 兜底：复合单位额度 + 观察期 + 相似 prompt 聚类。
- [ ] **事故 F：看板自己把数据库打挂。** 现象：成本看板每 10 秒扫一遍 `cost_fact` 全表，PG CPU 100%，主业务受影响。→ 根因：明细表直接做 BI 查询。→ 兜底：明细进 ClickHouse / 物化视图预聚合，看板只查聚合表（第 45 章）。

## 47.8 一页速记

| 关键词 | 必须记住的结论 |
| --- | --- |
| 根本问题 | 成本问题 90% 不是单价贵，是「用错档 + 算不清 + 没人负责」 |
| 口径 | 四层口径（call/step/run/session）；**失败 Run 成本占 12%，不算是自欺** |
| 算式 | `C_run = Σ(未命中×p_in + 命中×p_cache + out×p_out) + 工具 + 基建` |
| 结构 | 示例中输出约占 4% 用量、39% 成本；按可减少的量、价格和交付质量选优化点 |
| 计算纪律 | 整数 micro-USD、价目表版本化、按事件时刻计价、可重放 |
| 归因 | 四维（租户/场景/模型/步骤）+ 共享成本三层摊 + 失败成本归发起方 + 记 `saved_by_cache` |
| 优化顺序 | **缓存 > 路由 > 瘦身 > 压缩 > 蒸馏**（先做不掉质量的） |
| 天花板 | 工程优化天花板 ≈ -55%；要到 60% 毛利必须动定价与套餐 |
| 免费额度 | 单账号额度成本 ≤ 0.3×CAC；**按 token/工具/沙盒秒计，不按次数计** |
| 预算刹车 | 平台/租户/Run 三级；付费层降档、免费层拒绝；兜底开关必须带 TTL |
| 一句话 | **不能算出「每 Run 赚几分钱」的平台，不配谈规模化。** |

## 47.9 自检题

1. **你的月账单从 $840k 涨到 $2.86M，Run 量只涨 18%。请给出你的排查顺序。**
   > 要点：先分解「量 × 价 × 结构」：① 混合均价（$/M token）是否变了 → 查路由分布与是否有人关了降档；② 每 Run token 是否变了 → 查提示词版本 diff、上下文预算、历史是否全量带上；③ 失败率/重试率是否变了 → 查失控循环（step>20）；④ 免费层占比是否变了 → 查注册异常。这四步能在 2 小时内定位 90% 的账单异动，**不要先去怀疑厂商涨价**。

2. **为什么「缓存」排在「模型路由」之前？**
   > 要点：缓存是唯一**不拿质量换成本**的手段（命中的是同一个答案，质量零损失、可回滚、改动 1~2 周）；路由会掉点、需要评测兜底、需要兜底升档策略。优化排序的判据不是「省多少」，而是**「省这些钱要不要用质量换」**——先做免费的午餐。

3. **你的平台有 10 万租户、300 万 Run/天。请设计「成本熔断」的三个层级，并说明各自的动作。**
   > 要点：① Run 级（token/步数/墙钟硬上限，超限 kill，防失控循环）；② 租户级（日预算，超限转预付费或降档，防单租户烧穿）；③ 平台级（月预算，80% 通知、100% 全平台降一档、120% 只拒免费层）。关键是**付费层永远走「降级」不走「拒绝」**，且所有兜底型开关带 `expires_at` 自动回滚。
