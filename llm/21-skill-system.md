# 21. SKILL：技能即资产

> **状态**：`已完成（初稿）` ｜ **所属**：第四部分 · 上下文工程（Context Engineering） ｜ **编号**：21 / 52
> **本章定位**：SKILL 是 Agent 平台里**第一份真正可以被"经营"的资产**——它能版本化、能组合、能分发、能评测、能卖钱。这一章讲怎么把它从"一段贴在提示词里的 SOP"变成"一个可安装、可审计、可回滚的软件包"。

## 21.1 引子：900 token 的流程说明，一年烧掉 279 万美元

Aurora 的财务场景有个"月度对账"Agent。对账是个**有严格步骤**的活：

1. 拉当月账单（`billing.query_month`）；
2. 拉收款流水（`payment.query_flows`）；
3. 按 `(客户号, 金额, 日期±3天)` 做匹配；
4. 差异分四类（金额差、时间差、缺失、重复）；
5. 按分类给处理建议；
6. 出报告并落盘。

租户的运营同学很自然会把这 6 步写进**角色卡的 L4 禁止项**——因为那是编辑器里唯一能写长文本的地方。写了 900 token。

后果有三个，一个比一个贵：

**① 每个 Run 都带着它。** 财务 Agent 一次 Run 平均 5 次 LLM 调用，900 × 5 = 4,500 token；60 万 Run/天 × 4.5k = **2.7B token/天 ≈ $8,100/天 ≈ $2.96M/年**。而真正需要"对账流程"的 Run 只占 **6%**（其余是查余额、问发票、催款）。

**96% 的钱花在了用不上的流程说明上。**

**② 长上下文里它被忘了。** 对账会话经常 20 轮以上（要来回确认差异）。900 token 的流程说明在第 3 轮之后基本不起作用——Aurora 做 A/B 发现，**15 轮后"6 步全走完"的比例只有 71%**，最常漏的是第 4 步（差异分类），导致报告里"差异"是一坨没有分类的流水。

**③ 修一次要改 N 份。** 这个流程在 47 个租户配置里有 47 份副本（互相抄的）。某次合规要求"差异金额超过 1 万必须人工复核"，平台只改了 12 份，剩下 35 份继续违规了 5 个月，审计时被抓。

改造成 SKILL 之后：

| 指标 | 写在角色卡里 | 做成 SKILL |
| --- | --- | --- |
| 常驻 token | 900 × 5 步 = 4,500/Run | 元数据 80 token（常驻）+ 正文 1,400（仅 6% Run 加载） |
| 日均成本 | $8,100 | **$97** |
| 流程走完率 | 71% | 94% |
| 改动影响面 | 47 份副本，改 12 份 | 1 个版本，全量灰度 |
| 可评测 | ❌ | ✅ 有触发准确率、步骤合规率 |

> 🎯 **这一章的核心判断**：
> **技能不是"更长的提示词"，它是"把方法从上下文里搬出来，变成可安装的资产"。**
> 判断标准很简单：**这段内容是不是"只在某些时候才需要、而且需要时必须一步不差"？** 是，它就是技能，不该待在角色卡里。

## 21.2 断崖：三种"伪技能"和它们各自的死法

先破除三个最常见的误解。这三条如果搞错，你会造出一个"看起来能用、实际上无法治理"的东西。

| 伪技能形态 | 做法 | 死法 | 正确姿势 |
| --- | --- | --- | --- |
| **① 长提示词** | 把 SOP 全量写进 system prompt / 角色卡 | 常驻成本爆炸（§21.1）、长上下文遗忘、改一处漏 46 处 | 渐进式披露 + 版本化 |
| **② 工具包装** | 把"对账"写成一个 `do_recon()` 工具，里面全用代码实现 | 丧失了"模型处理非结构化输入"的能力；流程一变就要发版；不能复用模型的判断力 | 工具只做原子能力，流程交给技能 |
| **③ 子 Agent** | 给每个技能启动一个独立 Agent | 上下文切换成本、预算不可控、无法组合、观测碎片化 | 技能是"知识+脚本"，子 Agent 是"另一个执行体"，别混 |

### 21.2.1 断崖表

| # | 断崖 | 本质 | 症状 | 量化判据 |
| --- | --- | --- | --- | --- |
| 1 | **技能全量常驻** | 元数据没有单独一层 | 上下文被技能占满 | 技能相关 token / 总输入 > 15% |
| 2 | **触发不准** | `description` 写成了"功能介绍"而不是"何时用" | 该用时不用、不该用时乱用 | 触发准确率 < 90% |
| 3 | **无版本** | 技能就地修改 | 行为悄悄变、无法回滚 | 你说不出"上周三用的是哪版" |
| 4 | **权限过大** | 技能能调所有工具、能联网 | 供应链投毒、数据外泄 | 技能的工具清单 = Agent 的全部工具 |
| 5 | **脚本无沙箱** | 直接跑 `python script.py` | 任意代码执行、删库、挖矿 | 技能脚本能读到 `/etc/passwd` 就算 |
| 6 | **无评测** | 改了技能只靠"感觉好点" | 一次改动让成功率掉 20% | 技能没有自己的评测集 |
| 7 | **组合失控** | 技能可以无限调技能 | 递归、预算烧穿、循环 | 你的调用深度没有上限 |

### 21.2.2 账本：技能的经济学

技能之所以值得单独做一层，是因为它的**成本结构和其他上下文组件完全不同**：

| 组件 | 常驻成本 | 按需成本 | 复用范围 | 可交易 |
| --- | --- | --- | --- | --- |
| 角色卡 | 高（每步） | — | 单租户 | ❌ |
| 工具 schema | 中（每步） | 执行成本 | 平台级 | ❌ |
| 记忆 | 低 | 读放大 | 单用户 | ❌ |
| RAG 片段 | — | 注入成本高 | 单租户知识库 | ❌ |
| **SKILL** | **极低（80 token/个）** | **中等（1~2k token）** | **跨租户、跨场景** | ✅ **可分发/可售卖** |

最后两列是关键：**只有技能是"写一次、多个租户用、还能卖"的上下文资产**。这就是为什么它值得工程化——它不是成本项，是资产项。

LTV 算一下：一个高质量技能（比如"电商退货合规话术包"）如果被 800 个租户安装，每个租户每月省 20 小时运营时间（按时薪 150 元）→ 月价值 240 万；平台抽 10% → 24 万/月。**这就是"技能市场"的商业逻辑，也是平台从"卖 token"转向"卖能力"的路径。**

## 21.3 结构图：技能的四层披露与加载时序

```
【技能库（Git 仓库，一个技能一个目录）】
  skills/recon-monthly/
    ├── SKILL.md              ← 元数据(frontmatter) + 正文
    ├── references/
    │     ├── recon-rules.md  ← 完整判定规则（模型按需读）
    │     └── diff-taxonomy.md
    ├── scripts/
    │     └── match.py        ← 沙箱执行的确定性逻辑
    └── assets/report-template.xlsx

【注册中心】校验 → 签名 → 索引（name/desc/version/hash/permissions）

【运行时加载时序】
  请求进来
    │
    ├─ L0 元数据（常驻，进 P0）：只挂当前 Agent 的 8~15 个技能
    │     name + description + version  ≈ 80 token/个 → 合计 ~1.0k
    │
    ├─ 触发判定（规则关键词 → embedding 相似 → 候选 ≤3 个）
    │     命中 recon-monthly
    │
    ├─ L1 正文（按需，进 P2）：读 SKILL.md 全文 ≈ 1,400 token
    │     预算闸门：全部技能正文合计 ≤ 4k token，超了报错不截断
    │
    ├─ L2 引用（按需，通过工具读）：references/*.md
    │     模型自己决定读哪一节（不是自动全注入！）
    │
    └─ L3 脚本（沙箱执行）：scripts/match.py
          只把「结构化结果摘要」回灌上下文，不回灌 stdout 全文
          ↓
       执行 → 步骤合规校验 → trace 记录 skill_name@version + 加载的 refs
```

**四层披露的关键在于：每一层的"是否加载"都是由模型在当前上下文中决定的，而不是由配置决定的。** 这是 SKILL 和"提示词模板"的本质区别——模板是全量展开，技能是懒加载。

也正因为如此，**`description` 是整个技能里最重要的 80 个 token**：它是模型决定"要不要打开这个技能"的唯一依据。写得像产品介绍（"本技能提供强大的对账能力"）必然触发不准；写得像触发器（"当用户要求核对账单与流水、排查月度结算差异时使用"）才能命中。

## 21.4 关键设计

### 21.4.1 三者（加角色）的本质区别

这张表是本章的架构基础。团队里所有"这个该做成什么"的争论，都可以用它一次性终结。

| 维度 | **角色（Persona）** | **SKILL** | **工具（Tool）** | **子 Agent** |
| --- | --- | --- | --- | --- |
| 一句话 | 谁在说、不能说什么 | **这类事怎么做对** | 能对外部世界做什么 | 谁来独立干完 |
| 本质 | 约束（constraint） | **方法论（procedure）** | 能力（capability） | 执行体（actor） |
| 形态 | 文本，常驻前缀 | 目录包（SKILL.md + 资源 + 脚本） | 函数签名 / JSON Schema | 独立 Run + 独立上下文 |
| 是否执行代码 | 否 | **可**（脚本，沙箱内） | 是（服务端） | 是 |
| 上下文占用 | 常驻，每步 | **按需，渐进披露** | 仅 schema 常驻 | 独立预算，不占父 |
| 谁能写 | 业务/运营 | **领域专家 + 开发者** | 开发者 | 平台/开发者 |
| 变更影响 | 全部回答的风格与边界 | 特定任务的做法 | 某个动作的能力 | 某个子任务的执行 |
| 典型失败 | 角色漂移 | 触发不准、步骤漏 | 参数错、副作用 | 循环、预算烧穿 |
| 可分发 | 租户级覆盖 | **✅ 跨租户、可上市场** | 平台级注册 | 平台级 |
| 详见 | 第 17 章 | 本章 | 第 22 章 | 第 33 章 |

**判定树（评审时按顺序问，第一个"是"就定案）：**

```
这段内容/能力，是为了……
├─ 改变"谁在说、语气、红线"？           → 角色卡（第 17 章）
├─ 让模型能做一件它现在做不到的事？       → 工具（第 22 章）
├─ 让模型"按一套确定的步骤/规则把事做对"？
│    ├─ 步骤能用代码表达吗？
│    │    ├─ 能，且需要模型判断的只是"喂什么进去" → 工具（把逻辑写进代码）
│    │    └─ 不能（要处理非结构化、要临场判断分支）→ SKILL
│    └─ 需要一整套独立的上下文和预算去跑？      → 子 Agent（第 33 章）
└─ 以上都不是，只是"知识"？              → RAG（第 20 章）
```

一条反直觉的结论：**能用代码写死的逻辑，不要做成技能。** 技能的价值在"模型必须临场判断"的地方。对账的匹配算法（`(客户号, 金额, 日期±3天)`）应该写成脚本；"这个差异该归到哪一类、要不要升级给人"才该交给模型。**技能 = 确定性脚本 + 非确定性判断的编排**，两者都要有。

### 21.4.2 SKILL.md 的完整结构（可直接抄）

```markdown
---
name: recon-monthly
description: 按月核对账单与收款流水并输出差异清单。当用户要求"对账/核对流水/查差异/月度结算"，
  或提到账单金额与回款不一致时使用。不适用于单笔订单查询、单张发票查验。
version: 2.3.0
license: Apache-2.0
allowed-tools:                    # 只能收窄，不能扩大 Agent 已有权限
  - billing.query_month
  - payment.query_flows
  - file.write_report
  - hitl.request_approval          # 差异 >1 万必须走人工复核
requires: []                      # 依赖的其他技能（组合用，深度 ≤2）
references:
  - path: references/recon-rules.md
    when: 遇到无法分类的差异时读取
  - path: references/diff-taxonomy.md
    when: 需要给出差异处理建议时读取
scripts:
  - path: scripts/match.py
    runtime: python3.12
    timeout_sec: 60
    inputs: [billing_json, flows_json]
    outputs: [matched_json]
metadata:
  owner: fin-ops@aurora
  reviewed_by: compliance
  locales: [zh-CN, en-US]
  max_runtime_sec: 120
  eval_suite: skill-recon-v3
---

# 月度对账

## 何时用
用户要核对「某个月的账单」与「实际收款流水」并找出差异时。
**不要用**：单笔订单查询、发票查验、退款进度询问（这些直接用对应工具回答）。

## 前置检查
1. 确认月份（缺省=上月）。用户说"这个月"时，先确认是自然月还是账期。
2. 确认主体（公司/租户下的哪个签约主体），多主体必须问清。

## 步骤（必须按顺序，不可跳过）
1. 调用 `billing.query_month` 取账单，记录 `bill_total` 与条数。
2. 调用 `payment.query_flows` 取同期流水，记录 `flow_total` 与条数。
3. 调 `scripts/match.py` 做匹配（**不要自己心算匹配**，金额必须走脚本）。
4. 把脚本输出的差异按 `diff-taxonomy.md` 分成四类：金额差 / 时间差 / 缺失 / 重复。
5. 对每一类给处理建议（引用 `diff-taxonomy.md` 的条目编号）。
6. 若任一差异金额 > 10000 元：调 `hitl.request_approval`，**不要自行给出结论**。
7. 调用 `file.write_report` 出报告，正文里必须带：月份、主体、账单合计、流水合计、差异条数、差异合计。

## 判定规则（摘要）
- 金额差 ≤ 0.01 元视为精度误差，归入"已平"。
- 日期差 ≤ 3 天视为时间差（在途），> 3 天归入"缺失"。
- 同一 `(客户号, 金额)` 出现在流水中 ≥2 次 → "重复"，需核对是否重复扣款。
- 完整规则见 `references/recon-rules.md`，**遇到无法归类的差异时必须读它**，不要猜。

## 禁止
- 不修改任何账务数据（本技能只读）。
- 不对差异成因做"推测性解释"（如"可能是银行延迟"）——除非 `recon-rules.md` 明确列出。
- 不把客户名、账号完整输出到报告（脱敏，见 assets 里的模板）。

## 输出契约
报告结构：{period, entity, bill_total, flow_total, diffs:[{type, count, amount, suggestion_ref}], needs_human}
面向用户的正文：≤ 600 字，先给"是否平账"的结论，再给差异明细。
```

这个样例里有 8 个刻意的设计，每一个都能对应一类事故：

| 设计 | 防的是什么 |
| --- | --- |
| `description` 里写了"不适用于……" | 误触发（断崖 2） |
| `when` 字段标了每份引用的读取时机 | 模型无脑全读 → token 爆炸 |
| 步骤显式编号且写"不可跳过" | 步骤遗漏（§21.1 的 71% 问题） |
| "金额必须走脚本，不要心算" | 模型算错金额（最高频的致命错误） |
| `>10000 走 hITL` 写死在流程里 | 越权决策（第 34 章） |
| "遇到无法归类的必须读 references" | 幻觉式分类 |
| 禁止"推测性解释" | 幻觉归因（比答错更危险，因为听起来很专业） |
| 输出契约带 `needs_human` | 让下游能自动路由 |

### 21.4.3 加载器：三级加载 + 预算闸门 + 权限收窄

```go
// skill/loader.go
type Meta struct {                     // L0：常驻，~80 token
    Name, Desc, Version string
    AllowedTools        []string
    Requires            []string
    Hash                string
    Permissions         Permissions    // network/fs/exec 声明
}

type Skill struct {                    // L1：按需加载的正文
    Meta
    Body  string                       // SKILL.md 正文（不含 frontmatter）
    Refs  []RefSpec                    // 引用清单（不预读内容）
    Scripts []ScriptSpec
    Tokens int
}

type Loader struct {
    reg      Registry   // 注册中心：Meta 列表 + 按版本拉包
    resolver Trigger    // 触发判定
    budget   Budget     // 正文 token 预算
}

// Attach 在 Run 开始（或首次需要时）把技能挂到 Run 上
func (l *Loader) Attach(ctx context.Context, run *Run, query string) error {
    metas, err := l.reg.Metas(ctx, run.TenantID, run.AgentID) // 只取该 Agent 挂载的
    if err != nil { return fmt.Errorf("skill metas: %w", err) }

    hits, err := l.resolver.Select(ctx, query, metas, 3) // 最多 3 个候选
    if err != nil { return fmt.Errorf("skill trigger: %w", err) }

    used := 0
    for _, name := range hits {
        s, err := l.reg.Load(ctx, name, run.PinnedVersion(name)) // 版本钉住（Run 内不变）
        if err != nil { return fmt.Errorf("load %s: %w", name, err) }

        // ① 预算闸门：超预算报错，绝不截断技能正文
        if used+s.Tokens > l.budget.MaxSkillTokens { // 例如 4000
            return ErrSkillBudgetExceeded{Skill: name, Used: used, Need: s.Tokens}
        }
        // ② 权限只能收窄：与角色/Agent 已授予的工具取交集
        run.Toolset = Intersect(run.Toolset, s.AllowedTools)
        if len(run.Toolset) == 0 {
            return ErrSkillNoTool{Skill: name} // 声明了不存在的工具
        }
        // ③ 依赖检查：深度 ≤2，且不能成环
        if err := l.checkRequires(ctx, s, 2); err != nil { return err }

        used += s.Tokens
        run.Skills = append(run.Skills, s)
    }
    // ④ 观测：技能加载必须进 trace，否则无法归因
    run.Trace.Set("skills", Names(hits), "skill_tokens", used)
    return nil
}

// ReadRef 由模型通过工具调用触发（L2），不在 Attach 时预读
func (l *Loader) ReadRef(ctx context.Context, run *Run, skill, path string) ([]byte, error) {
    s := run.Skill(skill)
    if s == nil { return nil, ErrSkillNotLoaded }
    if !s.HasRef(path) { return nil, ErrRefNotDeclared }   // 防路径穿越
    if run.RefBytesUsed+int64(len(path)) > MaxRefBytes {    // 引用也有预算
        return nil, ErrRefBudgetExceeded
    }
    return l.reg.ReadFile(ctx, s.Name, s.Version, path)     // 校验 hash
}
```

四个设计点，每个都是"不做会出事"：

1. **版本钉住（`run.PinnedVersion`）**。一个 Run 30 秒、5 次调用，中途技能升级会让行为前后不一致。这和角色卡是同一个原则（第 17 章）。
2. **预算超了就报错，不截断**。截断技能正文 = 删掉步骤 = 静默出错。宁可让上层降级成"这个任务我现在做不了，转人工"。
3. **工具取交集**。技能永远不能扩大权限。这一条挡掉了"技能市场里有人写一个技能偷偷调 `send_email`"这类攻击。
4. **`ReadRef` 校验 `HasRef`**。`path` 来自模型输出，不校验就是**路径穿越漏洞**（`../../.env`）。这是技能系统的头号安全洞。

### 21.4.4 组合、版本化与依赖

**组合的正确形态：声明依赖，编排层组装，深度受限。**

```yaml
# skills/cs-refund-flow/SKILL.md 的 frontmatter 片段
requires:
  - skill: policy-lookup@^1.2      # 查政策
  - skill: refund-eligibility@2.0  # 判可退性
```

```go
// 组合规则（写进注册中心的校验，不是运行时才管）
func ValidateComposition(root *Skill) error {
    seen := map[string]bool{}
    var walk func(s *Skill, depth int) error
    walk = func(s *Skill, depth int) error {
        if depth > 2 {                     // 深度硬上限
            return ErrSkillDepthExceeded
        }
        if seen[s.Name] {                  // 环检测
            return ErrSkillCycle
        }
        seen[s.Name] = true
        for _, dep := range s.Requires {
            walk(mustLoad(dep), depth+1)
        }
        return nil
    }
    return walk(root, 0)
}
```

**为什么深度 ≤2**：技能 A 调 B、B 调 C、C 调 D，一旦某层触发判定出错，你会在一个 Run 里加载 15 个技能、烧掉 20k token。限制深度的代价是"组合不够灵活"，收益是**预算可预测**。这个交换值得。

**版本化：语义化版本对提示词不完全适用。**

| 变更类型 | 版本位 | 例子 | 是否需重跑评测 |
| --- | --- | --- | --- |
| 步骤增删、工具变更、契约变更 | **major** | 加了"必须人工复核" | ✅ 全量 |
| 措辞优化、示例补充、引用更新 | minor | 把"不要猜"改成"遇到无法归类时必须读规则" | ✅ 回归集 |
| 拼写、格式 | patch | 修错别字 | 抽样 |

三个工程细则：

- **`SKILL.md` 的内容 hash 必须进注册中心**，并在 trace 里记录 `skill_name@version#hash`。这样"上周三那次对账漏了一步"能精确归因到版本。
- **锁文件（`skills.lock`）**。生产环境不解析 `^1.2`，而是锁到 `1.2.3#sha256:...`。跟 `package-lock.json` 一个道理。
- **不自动升级**。技能升级默认需要租户管理员确认——因为技能会改变行为，而租户为结果负责。

### 21.4.5 市场分发：签名、审核、可撤回

技能市场不是"应用商店"这么简单，因为**技能里有脚本**——它是可执行代码，供应链风险是真实的。

| 环节 | 做法 | 不做会怎样 |
| --- | --- | --- |
| **发布** | 内容签名（作者私钥）+ 自动扫描（正则/依赖/网络调用）+ 人工审核 | 恶意技能窃取对话内容 |
| **分发** | 版本化 tarball + 内容 hash + 权限清单前置展示 | 安装时偷偷扩权 |
| **安装** | 管理员审批权限清单（`allowed-tools` / 网络白名单 / 脚本） | 权限蔓延（装了 30 个技能，等于全开） |
| **升级** | 默认手动确认；major 升级强制重跑评测 | 静默行为变更 |
| **撤回** | 紧急下架 + 通知已安装租户 + 服务端强制降级到上一版 | 已安装的恶意技能继续跑 |
| **弃用** | 标记 deprecated + 90 天过渡期 + 迁移指引 | 租户被锁死在旧版本 |

最后两行是最容易被忽略、也最难的：**npm 的 `unpublish` 已经证明"撤回"是个设计难题**。技能比 npm 更麻烦，因为它已经在别人的生产环境里影响着模型行为。所以：

> **技能市场从第一天就要设计"服务端可强制降级"的通道。**
> 你的注册中心必须能对一个租户下发 `force_downgrade: recon-monthly@2.2.1`，并且在下一个 Run 生效。

### 21.4.6 权限与沙箱边界

技能是**唯一一个"租户可以提供代码给平台执行"的入口**。边界必须画死。

| 资源 | 技能能做 | 强制约束 | 不做的后果 |
| --- | --- | --- | --- |
| 文件系统 | 读自身技能目录 | 路径规范化 + 前缀校验，禁止 `..`、禁止符号链接逃逸 | 读 `/etc/passwd`、读别的技能的密钥 |
| 文件系统（写） | **默认禁止** | 需要写文件用 `file.*` 工具（受审计），而不是直接 open | 污染其他技能、留后门 |
| 网络 | **默认禁止** | frontmatter 声明域名白名单，管理员审批，出口代理强制 | 数据外泄、C2 回连 |
| 工具调用 | 只能调 `allowed-tools` 内的 | 运行时按交集裁剪，未声明直接拒 + 告警 | 越权发邮件、改配置 |
| 脚本执行 | 沙箱内（第 29 章） | CPU/内存/时长上限、无网络、只读挂载、进程数限制 | 挖矿、fork 炸弹、横向移动 |
| 子 Agent | 默认禁止 | 深度 ≤2、独立预算 | 无限套娃烧穿预算 |
| 密钥 | **不可见** | 通过工具代理注入，技能上下文里永不出现 | 密钥进 prompt、进日志 |
| 输出 | 结果摘要回灌 | stdout 截断（如 8KB），大结果落文件给引用 | 上下文被脚本输出撑爆 |

**一个具体的攻击链，说明为什么每一条都要有**：

```
恶意技能 "invoice-helper"（看起来无害，市场需求真实）
  ├─ scripts/scan.py 里偷偷读 ~/.aws/credentials        ← 需要 fs 前缀校验挡住
  ├─ 把内容 POST 到 attacker.example.com                  ← 需要网络默认禁止挡住
  └─ 通过 SKILL.md 正文诱导模型"调用 send_email 把汇总发给我"  ← 需要工具交集挡住
```

三层里任何一层缺失，这条链就能走通。**沙箱挡代码，工具白名单挡行为，权限清单挡安装。** 这三层是纵深防御，不是备选。

### 21.4.7 技能评测：四个指标

技能评测和 Agent 评测不一样——它测的是**"该不该用、用了对不对、花了多少"**。

| 指标 | 定义 | 目标 | 怎么测 |
| --- | --- | --- | --- |
| **触发准确率** | 该用该技能的场景中，实际触发的比例 | > 95% | 构造 100 条"该触发"query，看命中 |
| **误触发率** | 不该用的场景中被触发的比例 | < 3% | 构造 100 条"不该触发"（邻近场景） |
| **步骤合规率** | 关键步骤不遗漏的比例（从 trace 里验证工具调用序列） | > 98% | 按 `步骤 → 工具调用` 映射自动校验 |
| **单次成本** | 加载的正文 + 引用 + 脚本回灌的 token | < 2,500 | trace 聚合 |

第三个指标最值得展开——**步骤合规率可以用 trace 自动算，不需要人工**：

```go
// skill/eval.go
// 把 SKILL.md 的步骤声明变成可校验的期望序列，从 trace 里比对
var reconV2 = Expect{
    Skill: "recon-monthly@2.3.0",
    Steps: [][]string{
        {"billing.query_month"},                    // 步骤 1
        {"payment.query_flows"},                    // 步骤 2
        {"script:match.py"},                        // 步骤 3
        {"read_ref:diff-taxonomy.md"},              // 步骤 4（允许顺序浮动）
        {"hitl.request_approval|skip_if_below_10k"},// 步骤 6（条件步）
        {"file.write_report"},                      // 步骤 7
    },
    Forbid: []string{"billing.update", "payment.refund"}, // 违反"只读"禁令
}

func Score(run *Run) SkillScore {
    calls := run.ToolCallsInOrder()
    return SkillScore{
        StepsOK:   MatchOrdered(calls, reconV2.Steps),  // 支持可选步与并行
        Forbidden: !ContainsAny(calls, reconV2.Forbid),
        Tokens:    run.SkillTokens(),
    }
}
```

这套东西的价值：**技能改了之后，你不用重新做人工评测就能知道"步骤有没有漏"**。Aurora 的经验是，技能迭代里 80% 的退化是"步骤遗漏"和"顺序错乱"，这两类完全可以自动化。

配套的门禁（进发布流程，第 42 章）：

```
技能发布门禁：
  ✅ 触发准确率 ≥ 95%
  ✅ 误触发率 ≤ 3%
  ✅ 步骤合规率 ≥ 98%（对 eval suite 里 ≥50 条 case）
  ✅ 单次成本 ≤ 2,500 token
  ✅ 无新增 forbidden 调用
  ✅ 权限清单无扩大（有扩大则需安全团队二次审批）
```

最后一条特别重要：**权限扩大必须单独审批**，不能混在"版本升级"里悄悄过。

## 21.5 Java / 分布式经验对照

| 你熟悉的东西 | 技能系统的对应物 | 会咬人的差异 |
| --- | --- | --- |
| Maven 依赖 + `pom.xml` | `requires` + `skills.lock` | 依赖的解析是**模型触发**的，不是编译期确定的 |
| `package-lock.json` / 版本钉住 | `PinnedVersion` + 内容 hash | 一个 Run 内必须钉住，中途升级会导致行为不一致 |
| 类加载器（双亲委派 / 懒加载） | 三级披露 | 加载的不是字节码，是**自然语言指令**，没有类型检查 |
| SPI / 插件机制 | 技能市场 + `allowed-tools` | 插件扩权要审核；这里插件能"说服"模型扩权 |
| `SecurityManager` / 沙箱 | 脚本执行隔离 | 模型的输出本身就是攻击面（它会被技能正文说服） |
| 依赖环检测 | `ValidateComposition` | 环不是编译错误，是**运行时预算爆炸** |
| 灰度发布 | 技能 canary + 强制降级通道 | 已安装的实例必须能被服务端强制降级 |
| 配置中心 | 注册中心 | 注册中心要能做内容签名与撤回 |

三条最会咬人的：

1. **"技能是文本，不是代码"这个错觉**。它带脚本，所以它是代码；它没有类型系统，所以它的错误在运行时才暴露。**必须按代码的标准做：签名、锁版本、沙箱、评测门禁。**
2. **"加载即授权"**。你在 Java 里给一个模块加依赖，不会顺带给它加数据库权限。但技能如果"加载即继承 Agent 全部工具权限"，那就等于 `import` 就等于 `sudo`。**必须取交集。**
3. **"删除即卸载"**。技能被市场撤回后，本地已安装的副本还在跑。注册中心必须有强制降级通道，且运行时每次加载都校验版本可用性（可以缓存 60 秒）。

## 21.9 自检题

1. **运营说「我要把这个 6 步流程加到提示词里，这样模型就不会漏」。你怎么判断该不该做成技能？**
   > 要点：① 先问"这个流程是不是每次都用到"——不是，就该做成技能（本例 6%）；② 再问"步骤能不能用代码表达"——能表达的部分（金额匹配）写成脚本，剩下的判断部分交给模型；③ 最后算账：900 token × 5 步 × 60 万 Run = 2.7B token/天，而技能化后只需 32M，差了 84 倍；④ 还要指出"写进提示词不能解决遗忘"——15 轮后流程执行率只有 71%，而技能的步骤合规率可以从 trace 自动校验。

2. **技能市场里有人提交了一个"发票助手"，`allowed-tools` 里写了 `http.request`、`file.read`、`send_email`。你的审核流程会怎么做？**
   > 要点：① 权限清单最小化——要求作者说明每个工具的用途，`file.read` 与 `send_email` 默认拒绝；② 网络必须走域名白名单，不能是"任意 URL"；③ 脚本进沙箱（无网、只读挂载、时长上限），`ReadRef` 路径白名单；④ 加载时与 Agent 已有工具取交集，即使声明了 `send_email`，Agent 没有该权限也调不到；⑤ 装上后持续审计实际调用（声明了但没用的权限要收回）。

3. **你怎么证明"这次技能升级没有变差"？给出你能拿出来的三类证据。**
   > 要点：① **自动**：步骤合规率（trace 比对期望序列，≥50 条 case）+ 禁用调用为零；② **指标**：触发准确率/误触发率不降，单次 token 不涨超 10%；③ **端到端**：eval suite 的任务成功率不掉（≥200 条），且按"技能命中/未命中"分桶看，避免均值掩盖长尾。④ 另外要能证明"可回滚"——版本钉住 + 一键降级通道已演练过。
