## 25.1 引子：供应商没挂，你的平台挂了 47 分钟

周四 14:02，Aurora 开始大面积超时。第一反应是查模型供应商——状态页绿油油，错误率 **2%**。

真实情况是：供应商 A 的 **P99 从 3.5 秒涨到了 40 秒**。它没报错，只是变慢了。而你的熔断器配的是：

```yaml
# 出事前的配置
circuit_breaker:
  failure_rate_threshold: 0.5    # 错误率 50% 才熔断
  wait_duration: 30s
```

错误率 2% < 50%，熔断器**永远不会触发**。于是：

- 每个 Run 的 LLM 调用都卡 40 秒，而 Run 总预算是 30 秒 → 100% 超时；
- 超时的 Run 触发「重试 2 次」→ 5,000 QPS 变成 **15,000 QPS**；
- 15,000 QPS 打到备用供应商 B，B 的并发额度是 1,200 → 排队 → B 也变慢；
- 用户端看到的是「一直转圈」，前端自动重连又把入站 QPS 顶到 8,000。

47 分钟，**210 万次**失败 Run，两个供应商同时被拖垮。复盘时最扎心的一句话是：

> 「我们做了熔断，但熔断器只认『错』，不认『慢』。可 Agent 的死法，90% 是慢死。」

三个盲区，本章逐个拆：

| 盲区 | 你以为 | 实际 | 代价 |
| --- | --- | --- | --- |
| 只看错误率 | 慢是「性能问题」 | 慢会耗尽预算 → 变成 100% 超时 | 47 分钟全站故障 |
| 超时是单点参数 | 每个调用配 10s 就行 | 10 个 10s = 100s > 用户耐心 | 串联放大（见第 1 章） |
| 重试是「提高成功率」 | 重试 2 次更可靠 | 故障时重试 = 给快死的人加重物 | 3 倍流量打崩备用 |

## 25.2 断崖：超时必须是预算，且必须分层

### 25.2.1 一张必须存在的表

Aurora 的延迟预算表（单 Run 30 秒，P50 12s / P99 45s 的实测分布逼出来的）：

| 层级 | 预算 | 超时后的动作 | 谁兜底 |
| --- | --- | --- | --- |
| **L0 网关（HTTP/SSE）** | 35s | 主动断流 + 发 `error` 事件 | 网关 |
| **L1 Run 总预算** | 30s | 中止 + 返回已有部分输出 + `finish_reason=timeout` | 执行内核 |
| **L2 Step 预算** | 8s | 该 Step 失败，进下一 Step 或降级 | 编排器 |
| **L3 LLM 单次调用** | 6s（首 token 3s） | 中断 + 换模型/failover | 模型网关 |
| **L3' 工具单次调用** | 3s | `is_error: true` 回灌模型 | 工具网关 |
| **L4 检索（含 rerank）** | 1.5s | 降 top-k 或走缓存 | RAG 服务 |
| **L5 前处理** | 0.8s | 跳过二次审核，记风险标记 | 前处理 |
| **L5' 后处理** | 0.5s | 跳过非必需校验（脱敏不可跳！） | 后处理 |

三条规则，缺一条这张表就是废纸：

1. **子预算之和 < 父预算**，且必须留「储备」（reserve）。L1=30s，而 L2 最多串 3 步 × 8s = 24s，留 6s 给收尾/审计/计费。
2. **预算是传递的，不是并列的**。第 3 步开始时要用的不是 8s，而是 `min(8s, 剩余预算 - 储备)`。
3. **L0 必须大于 L1**。反过来就会出现「服务还在生成，网关已经断了」——用户看到截断，你却以为成功（第 36 章的流式坑）。

### 25.2.2 串行放大：为什么 6 秒的 LLM 超时还不够

```
单次调用 P99 = 6s，看似安全。

但一个 Run 平均 6 次 LLM 调用 + 5 次工具调用，串行最坏情况：
  6 × 6s + 5 × 3s = 51s  ≫ 30s 预算

所以真正的算法不是「每次给多少」，而是：
  允许的慢调用次数 = ⌊(30s - 已用) / 单次超时⌋
  一旦剩余预算 < 最小可用时间(2s)，必须立刻收口：用已有信息作答 + 标记 partial
```

**这是 Agent 与传统 RPC 的核心区别**：传统 RPC 一次失败 = 一次 500；Agent 一次慢 = 后面所有步骤都没预算了。所以「余量检查」必须写进循环，不能只靠 ctx deadline 兜底（deadline 到点才报错，来不及生成半截答案）。

## 25.4 关键设计

### 25.4.1 熔断：错误率与慢调用率，两个都要

慢调用熔断是本章的第一优先级。判定条件（Resilience4j 的语义最清晰，可以直接借）：

| 参数 | Aurora 取值 | 推导 |
| --- | --- | --- |
| `failure_rate_threshold` | 0.5 | 错误率（5xx / 超时 / 解析失败） |
| `slow_call_duration_threshold` | 6,000 ms | = L3 LLM 调用预算；超过就没意义了 |
| `slow_call_rate_threshold` | **0.5** | 一半的调用超过 6s 就熔断 |
| 窗口类型 | 时间窗 60s / 最小 20 次调用 | 低流量下样本不足，用 count 窗兜底 |
| `wait_duration_in_open` | 30s（退避翻倍，上限 5min） | 太短会反复冲击下游 |
| `permitted_calls_in_half_open` | 5（≥3 成功才闭合） | 单次探测成功可能是巧合 |
| 粒度 | provider / model / **依赖分组** | `search_orders` 和 `send_email` 共用一个 DB 时要一起熔断 |

**为什么慢调用阈值必须 ≤ 调用预算**：如果 LLM 预算是 6s，而慢调用阈值设 10s，那么所有「能触发熔断的慢调用」早就已经让 Run 超时了——熔断器永远慢半拍。这是 25.1 事故的直接技术原因。

```go
// breaker/budget.go —— 预算传递 + 慢调用熔断的联合判定
func (e *Engine) callLLM(ctx context.Context, step Step, budget Budget) (Resp, error) {
    remain := budget.Remaining()
    if remain < minUseful { // 2s：不够生成有意义的内容
        return Resp{}, ErrBudgetExhausted // ← 上层收口为 partial 输出
    }
    timeout := min(e.cfg.LLMTimeout, remain-budget.Reserve) // 预留收尾时间
    cctx, cancel := context.WithTimeout(ctx, timeout)
    defer cancel()

    start := time.Now()
    resp, err := e.route.Call(cctx, step) // 内部含 failover
    elapsed := time.Since(start)

    e.breaker.Record(step.Provider, breaker.Outcome{
        Err:  err,
        Slow: elapsed >= e.cfg.SlowThreshold, // ← 关键：慢也记为「坏结果」
        Cost: resp.Cost,
    })
    return resp, err
}
```

> ⚠️ 别忘了第三种熔断：**成本熔断**。单 Run 成本超 $0.5、或单租户 1 分钟成本超预算 → 立刻中止并告警。这是 Agent 独有的（传统服务没有「一次请求烧掉 500 块」这种事），详见第 27 章。

### 25.4.2 多供应商 failover：同构好切，异构要命

| 类型 | 例子 | 切换成本 | 要改什么 |
| --- | --- | --- | --- |
| **同构 failover** | 同一供应商的不同 region / 不同部署 | 低（换 endpoint） | 几乎不用改 |
| **同模型跨云** | 同一开源模型在两家托管 | 中 | tokenizer 差异 → 计费口径（第 27 章） |
| **异构 failover** | OpenAI ↔ Anthropic ↔ 自建 | **高** | 提示词、tool call 格式、流式事件、停止词全不同 |

异构 failover 的四个必改点（每个都是真实踩过的）：

| 差异点 | 具体表现 | 不改的后果 |
| --- | --- | --- |
| 提示词适配 | 一个模型对 system 长度/结构敏感，另一个不敏感 | failover 后质量掉 10~20 分，比不切还糟 |
| 工具调用格式 | `tools[].function.arguments`（JSON 字符串） vs `tool_use` block（对象） | 解析失败 → 工具调用全挂 |
| 流式事件 | delta 结构、结束标记、用量上报时机不同 | 前端渲染错乱 / 计费漏单 |
| 停止条件 | `stop_sequences` 支持度、`max_tokens` 语义（含不含思考 token） | 输出被截断或超长 |

**结论**：failover 必须**按 provider 维护提示词变体**（第 42 章的版本矩阵里，`prompt_version` 要带 provider 维度），并且**每个 provider 都要跑评测集**——没跑过评测的 failover 路径，等于没有。

对冲请求（hedging）是另一个便宜手段：

```
正常：  请求 A ──────────────── 3.5s ──▶ 返回
对冲：  请求 A ────────── 2.0s（P95 触发）
        请求 B ────────────────── 3.2s ──▶ 先到的赢
收益：P99 45s → 18s（-60%）；成本 +6%（只有 4% 的请求触发对冲）
```

### 25.4.3 降级阶梯：五级台阶，每一级都要有「产品定义」

这是全章最该被产品经理看到的一张表。**降级不是技术兜底，是产品决策。**

| 级别 | 动作 | 质量 | 成本 | 延迟 | 触发条件 | 用户感知 |
| --- | --- | --- | --- | --- | --- | --- |
| **L0** | 大模型 + 全工具 + 全检索 | 92 分 | 100% | 12s | 正常 | 无 |
| **L1 降配** | 小模型 / top-k 8→3 / 关非必要工具 | 89 分 | **40%** | 6s | 租户配额紧、供应商慢调用 >30% | 「答案略简」 |
| **L2 简化** | 单步直答，跳过工具循环 | 78 分 | 25% | 3s | 工具大面积故障 / Step 预算反复耗尽 | 「信息可能不全」 |
| **L3 模板** | 检索式回答，不走生成（FAQ 命中原文） | 70 分 | **5%** | 0.5s | 模型全挂 / 成本熔断 | 「标准答案」 |
| **L4 兜底话术** | 固定话术 + 转人工 + 记录工单 | 55 分 | 0.5% | 0.2s | 全部失败 | 「已为您转人工」 |
| **L5 明确失败** | 503 + 人话解释 + 补偿（退款/重试券） | — | 0 | 即时 | 连兜底都无法保证 | 「服务不可用，已补偿」 |

决策表（值班时直接查这张表，不要临场想）：

| 现象 | 判定 | 落到哪级 | 谁触发 | 恢复条件 |
| --- | --- | --- | --- | --- |
| 主供应商 P99 > 20s，错误率 < 5% | 慢而不错 | **L1**（换小模型 / 切 B） | 自动（慢调用熔断） | P99 < 8s 持续 5min |
| 供应商错误率 > 50% | 硬故障 | **L1 → failover** | 自动 | 半开探测 5 次 ≥3 成功 |
| 两家供应商全挂 | 全面故障 | **L3**（模板） | 自动 | 任一家 CLOSED |
| 单租户成本超预算 3 倍 | 成本失控 | **L2**（该租户） | 自动（成本熔断） | 次日 0 点或充值 |
| 工具依赖 DB 故障 | 单点故障 | **L2**（跳工具循环） | 自动 | DB 恢复 |
| 发布引发质量下跌 | 人为故障 | **L1** + 回滚 | 手动（开关） | 版本回滚完成 |

三条硬规矩：

1. **每一级都必须预先实现并演练过**。L3 模板降级如果从没跑过，真到那天你会发现模板库里是两年前的文案。
2. **降级要「保语义」，不只「保可用」**。返回一句「系统繁忙」是保可用；返回「我暂时查不到物流，但你的订单已发货，预计 5 月 3 日到」是保语义。后者要提前准备，前者不用——这也是 90% 的团队只做到了 L4/L5 的原因。
3. **降级必须被观测**。每次降级发一个 `degrade.level` 指标 + 进 trace。否则你会看到「成功率 99.9%，但 NPS 掉了 20 分」这种鬼故事（第 39 章）。

### 25.4.4 开关管理：自动触发 + 人工兜底 + 防抖

降级开关是最容易变成「配置事故」的地方（第 43 章）。三层设计：

| 层 | 谁改 | 生效范围 | 例子 | 回滚 |
| --- | --- | --- | --- | --- |
| **自动开关** | 熔断器 / 限流器 | 全局或按 provider | A 供应商 OPEN → 全量切 B | 半开探测自动恢复 |
| **人工开关** | 值班 / SRE | 全局 / 租户 / 场景 | 「客服场景降到 L2」 | 一键还原 + 审计 |
| **租户级开关** | 客户成功 | 单租户 | 大客户临时提到 L0 | 到期自动失效 |

```yaml
# policy/degradation.yaml（策略中心热更，第 43 章）
version: 2026-05-06-3
ladder:
  l1_degrade:
    auto: true
    trigger:
      slow_call_rate_gt: 0.30      # 30% 慢调用
      window: 60s
      min_requests: 50
    action:
      model_tier: small            # 大 → 小
      retrieval_top_k: 3           # 8 → 3
      disable_tools: [web_search, crm_lookup]
  l3_template:
    auto: true
    trigger: { all_providers_open: true }
    action: { mode: retrieval_only }
guardrails:
  debounce: 30s          # 状态抖动 30s 内不来回切（防抖！）
  max_level_per_hour: 3  # 一小时内最多升降 3 次，超过需人工确认
  never_degrade:         # 无论多糟都不许降的
    - pii_masking         # 脱敏不可降
    - approval_gate       # 高危写审批不可降
```

**防抖是必须的**：没有 `debounce`，熔断器在临界点会以秒级频率在 CLOSED/OPEN 之间抖，结果是「一半请求走 L1、一半走 L0」，质量分布变成双峰，评测完全失真。

### 25.4.5 重试：唯一正确的姿势是「几乎不重试」

先把放大的数学写清楚：

```
有效负载 = QPS × (1 + p·r)
  p = 失败率, r = 重试次数

p=0.02, r=2 → 1.04×  （无害）
p=0.10, r=2 → 1.20×
p=0.30, r=2 → 1.60×  ← 此时下游已经很难，你再加 60%
p=0.50, r=3 → 2.50×  ← 这就是重试风暴
```

**重试的问题不是「多打了请求」，而是「在最糟的时刻加最多的负载」** —— 失败率和流量天然正相关。

五条规矩：

| 规矩 | 做法 | 不做会怎样 |
| --- | --- | --- |
| 只重试幂等操作 | `read` 工具、LLM 调用（无副作用）、幂等写 | 重复发邮件（第 22 章） |
| 只重试「可恢复」错误 | 429 / 502 / 503 / 超时；**不重试** 400 / 401 / 内容审核拒绝 | 重试一个语法错 100 次也不会成功 |
| 指数退避 + 全抖动 | `sleep = rand(0, min(cap, base·2^n))` | 同步重试 → 齐步走 → 二次峰值 |
| 重试预算（Retry Budget） | 重试请求 ≤ 正常请求的 10%（令牌桶） | 上面那个 2.5× 放大 |
| 只在「预算够」时重试 | `remaining > timeout × 2` 才允许 | 重试必然超时，纯浪费 |

```go
// retry/budget.go —— 重试预算：全局令牌桶，容量 = 正常流量的 10%
type Budget struct{ tb *rate.Limiter } // tb: rate=0.1×QPS, burst=50

func (b *Budget) AllowRetry() bool { return b.tb.Allow() }

// 带抖动与预算的退避
func Backoff(attempt int, base, cap time.Duration) time.Duration {
    d := base << attempt                    // 100ms, 200ms, 400ms...
    if d > cap { d = cap }
    return time.Duration(rand.Int63n(int64(d))) // 全抖动：0 ~ d
}
```

> 💡 一个反直觉但有效的做法：**把「重试」换成「对冲 + failover」**。重试是「等同一个坏掉的东西好起来」，对冲是「同时问另一个」——前者放大下游压力，后者只是多花 6% 成本。在 Agent 场景（单次调用贵、延迟长）里，对冲的性价比远高于重试。

## 25.5 Java / 分布式经验对照

| 你的经验 | AgentOS 对应物 | 判断 | 会咬人的地方 |
| --- | --- | --- | --- |
| Resilience4j CircuitBreaker | 熔断（错误率 + 慢调用） | 🟢 **直接迁移** | 一定要配 `slowCallRateThreshold`，只配 `failureRate` 就是 25.1 |
| Sentinel 熔断（慢调用比例） | 同上 | 🟢 直接迁移 | 规则要按 provider/model/工具分组下发 |
| Hystrix 降级 fallback | 降级阶梯 | 🟡 要扩展 | fallback 不能只返回常量，要**保语义**（L1/L2 仍走模型） |
| Spring Retry / `@Retryable` | 重试 | 🔴 **高危** | 默认无预算、无抖动、默认重试所有异常 |
| Feign + Ribbon 超时 | 分层超时 | 🟡 要改造 | 必须做预算传递，不能每层独立配 |
| Ribbon 负载均衡 | 多供应商 failover | 🟡 要改造 | 异构 provider 要提示词变体 + 评测，不是「换个地址」 |
| Hystrix 线程池隔离 | 舱壁 | 🟢 直接迁移 | 见第 28 章 |
| 无「成本熔断」概念 | 成本熔断 | 🔴 **新东西** | 一次 Run 烧 $0.5 必须能自动刹住 |
| 无「降级要保语义」 | 降级阶梯 L1/L2 | 🔴 **新东西** | 只做 L4 兜底话术 = 用户体验直接归零 |

## 25.6 开源坐标

| 项目 | 对应 | 能用 | 缺什么 |
| --- | --- | --- | --- |
| **Resilience4j** | 熔断、限流、重试、舱壁（Java） | ✅ 语义最清晰的参考实现 | 无 Go 版；无成本维度 |
| **Sentinel** | 熔断（慢调用比例）、系统自适应保护 | ✅ 概念齐全 | 无 token/成本维度 |
| **LiteLLM Router** | `fallbacks` / `retries` / `cooldown` / 上下文窗口 fallback | ✅ 多供应商 failover 最快的落地方式 | 无预算概念；提示词变体要自己做 |
| **OpenRouter** | 多模型聚合 + 自动路由 + 价格排序 | ⚠️ 便利 | 治理与审计不在你手里（第 31 章） |
| **Envoy**（outlier detection / retry budget） | 连接级熔断与重试预算 | ✅ 基础设施层直接可用 | 不理解 LLM 语义（慢 vs 错） |
| **`golang.org/x/time/rate`** | 重试预算令牌桶 | ✅ 20 行实现 | 无分布式能力 |

> 🎯 判断：**熔断用现成的（Resilience4j/Sentinel 的思路照搬），failover 用 LiteLLM 起步，降级阶梯必须自研**——因为阶梯的每一级都是业务语义，开源给不了。

## 25.7 事故清单

- [ ] **A. 慢而不错，熔断不触发**：P99 3.5s→40s，错误率仅 2% → 全站超时 47 分钟。→ 根因：只配错误率熔断。→ 兜底：加慢调用率（50% / 6s）+ 阈值 ≤ 调用预算。
- [ ] **B. 重试风暴**：5,000 QPS 重试 2 次 → 15,000 QPS 打备用供应商 → 备用也挂。→ 根因：无重试预算、无抖动。→ 兜底：重试 ≤10% 令牌桶 + 全抖动 + `retry_after`。
- [ ] **C. 异构 failover 质量暴跌**：切到 B 后工具调用全失败（格式不同）→ 成功率 92%→61%。→ 根因：未按 provider 维护提示词/工具适配层。→ 兜底：provider 维度版本矩阵 + 每个 provider 跑评测集。
- [ ] **D. 降级开关抖动**：临界点来回升降，一半请求 L1 一半 L0 → 评测双峰失真。→ 根因：无防抖/无升降次数上限。→ 兜底：30s debounce + 每小时 ≤3 次 + 人工确认。
- [ ] **E. 只有 L4 兜底**：出故障就回「系统繁忙」，用户直接流失。→ 根因：只实现了最后一级。→ 兜底：L1/L2/L3 全部预置 + 季度演练。
- [ ] **F. 降级不可见**：成功率 99.9%，但 30% 请求走了小模型，NPS 掉 20 分。→ 根因：降级没有指标与 trace 标记。→ 兜底：`degrade.level` 进指标与 trace + 质量看板按 level 切片。

## 25.8 一页速记

| 关键词 | 必须记住的结论 |
| --- | --- |
| 死法 | Agent 90% 是慢死，不是错死；只认错误的熔断器等于没有 |
| 超时 | 超时是**预算**：L0 35s > L1 30s > L2 8s > L3 6s > 工具 3s，子预算之和必须小于父 |
| 余量检查 | `remaining < 2s` 立刻收口出 partial，别等 deadline 报错 |
| 熔断参数 | 错误率 50% **与** 慢调用率 50%（阈值 6s = 调用预算），窗口 60s，最小 20 次 |
| failover | 同构便宜、异构要命；必须按 provider 维护提示词变体 + 跑评测 |
| 对冲 | P95 触发第二家，P99 45s→18s，成本只 +6%，比重试划算 |
| 阶梯 | L0 → L1 降配 → L2 简化 → L3 模板 → L4 兜底 → L5 明确失败，每级都要实现并演练 |
| 降级要保语义 | 「查不到物流但已发货，预计 5/3 到」 ≫ 「系统繁忙」 |
| 重试 | 有效负载 = QPS×(1+p·r)；p=0.5,r=3 就是 2.5×；重试预算 ≤10% |
| 抖动 | 全抖动 `rand(0, min(cap, base·2^n))`，否则齐步走 |
| 防抖 | 降级状态 30s 内不来回切，每小时 ≤3 次 |
| 一句话 | **别追求「不挂」，追求「挂着也能交付 70 分」——这是 Agent 平台和普通服务的分水岭。** |

## 25.9 自检题

1. **供应商错误率 2%、P99 从 3.5 秒涨到 40 秒。你的熔断器会不会触发？为什么这是最危险的故障形态？**
   > 要点：不会——只配 `failure_rate_threshold` 的熔断器只看「错」，不看「慢」。这种故障最危险，因为：① 所有监控都是绿的（错误率低）；② 但每个 Run 都超预算，实际成功率是 0；③ 重试会把备用供应商一起拖垮。修法：`slow_call_duration_threshold` 设为**调用预算（6s）**，`slow_call_rate_threshold` 50%。

2. **你有 5,000 QPS，失败率 30%，重试 2 次。下游实际承受多少？应该怎么改？**
   > 要点：`5000 × (1 + 0.3×2) = 8,000 QPS`，+60%，而且是在下游最脆弱时。改法：① 重试预算令牌桶（≤10% 正常流量）；② 指数退避 + 全抖动（避免齐步走）；③ 只重试可恢复错误（429/502/503/超时）；④ 预算不足（`remaining < 2×timeout`）不重试；⑤ 更好的是用**对冲 + failover 替代重试**。

3. **「降级就是返回一句『系统繁忙，请稍后再试』」——这句话错在哪？请给出三级更好的降级。**
   > 要点：错在只保「可用」不保「语义」。三级更好：**L1 降配**（小模型/top-k 缩减/关非必要工具，质量 89 分、成本 40%）；**L2 简化**（跳过工具循环单步直答，78 分）；**L3 模板**（检索原文直出，70 分、0.5s）。核心判据：降级后用户是否还能拿到「可行动的信息」，而不只是「系统在工作」。
