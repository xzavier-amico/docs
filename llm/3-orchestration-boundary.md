# 3. 编排框架的真实边界：LangChain/LangGraph 只是控制流 DSL

> **状态**：`已完成（初稿）` ｜ **所属**：第一部分 · 认知篇：为什么「套个框架」一定会失败 ｜ **编号**：3 / 52
> **本章定位**：把一次生产 Run 拆成九块，逐块问「编排框架能不能帮我做」——你会得到 12% 这个数字。然后给出一张判定表，让「这块用框架 / 那块自研」变成可评审的决策，而不是个人偏好。

## 3.1 引子：一次「框架迁移」的三个月

去年有个团队做了件很典型的事：把自研的 Agent 循环迁到 LangGraph，理由是「有 checkpoint、有 interrupt、图能可视化」。三个人的小分队，干了三个月，迁完了。第一天上线，评测通过率从 91.2% 掉到 90.8%——可以接受。

然后第二周开始，问题不在框架里，全在框架外：

- 用户说「它回答到一半卡住了」。查下去发现是**网关的 `proxy_read_timeout` 60 秒**，而图的最后一步跑得慢，SSE 被反代掐了。框架不管这事。
- 财务说「这个月的账对不上，差 7.4%」。查下去发现**框架的 token 回调只覆盖 `llm.call`，工具内部的模型调用（代码解释器里跑的）没被计量**。
- 客服主管说「上次说能退款，现在不认了」。你想回放那次 Run，`checkpointer` 里的确是状态快照——**但快照只有最新一版，你无法回答「第 3 步时上下文里到底有哪 7 段内容」**。
- 大客户投诉「我们被限流了，别人没被限」。因为**限流是网关按 API Key 做的，框架层根本没有租户概念**。
- 灰度想「把这个租户切到新的提示词」，发现**提示词是写在图的节点代码里的常量**，改它要发版。

三个月迁移，把「怎么写控制流」这件事做好了。但那次迁移没有解决上面任何一个问题，因为**上面五个问题，一个都不在编排框架的职责范围内**。

> 🎯 本章要建立的判断：**编排框架是一个 DSL，不是一个运行时，更不是一个平台。** 它把「什么时候调模型、什么时候调工具、循环什么时候退出」这几行 if-else 变得优雅、可持久化、可可视化——这值两个月。但它跟「一个租户能不能烧穿你的账单」毫无关系。

## 3.2 账本：一次生产 Run 的九块成本

我们拿 Aurora 的一次客服 Run 来拆：单次 30 秒、5 步模型调用、4 次工具调用、输出 800 字（约 530 token，含工具 JSON 与实际计费 token 约 1,200）。

| # | 组成 | 占比 | 归属层 | 框架能帮你做吗 | 不做的后果（可量化） |
| --- | --- | --- | --- | --- | --- |
| 1 | 控制流：何时调模型/工具、循环退出、分支 | **12%** | 编排层 | ✅ **这就是框架在做的事** | 自己写状态机，多花 2 人月 |
| 2 | 接入与协议：鉴权、多端、流式、断线续传 | 10% | 接入面 | ❌ 基本不碰 | 弱网下 8~15% 的流断掉且无法续 |
| 3 | 上下文工程：角色卡、预算、检索、压缩、记忆 | 18% | 上下文层 | ⚠️ 只给接口，策略全靠自己 | 同模型效果差 3 倍、成本差 5 倍 |
| 4 | 输入管道：规范化、注入预检、审核、路由前置 | 6% | 管道 | ❌ 没有 | 脏输入按 token 计费；注入在花 token 后才拦 |
| 5 | 稳定性：限流、队列、超时、熔断、降级、重试 | 14% | 治理面 | ❌ 几乎为零 | 一次洪峰 → 3,200 个 Run 连锁超时 |
| 6 | 成本与计费：路由、缓存、token 计量、账本 | 12% | 治理面 | ❌ 没有 | 对账差 7~11%，毛利不可知 |
| 7 | 输出管道：流式渲染、结构化、审计与撤回 | 10% | 管道 | ❌ 没有 | 说错的话收不回，一次投诉变一次事故 |
| 8 | 可观测、评估与回流：trace、指标、评测、样本 | 10% | 数据闭环 | ⚠️ 有钩子，没有体系 | 故障定位以小时计，迭代靠感觉 |
| 9 | 安全、防御与合规：注入、防破解、审计取证 | 8% | 运行时+治理面 | ❌ 没有 | 取证失败 = 无法向监管证明「当时做了什么」 |
| — | **合计** | **100%** | — | **框架覆盖 12%** | — |

### 3.2.1 把「12%」换成三种货币

数字只有换成钱和人力才会被记住。

**（A）工程量账**。一个中型 Agent 平台（Aurora 规模）从 0 到能扛，约 **100 人月**：

| 层 | 人月 | 其中框架省掉的 |
| --- | --- | --- |
| 编排层 | 12 | 框架省 8（约 2 人月 × 4 人） |
| 接入与协议 | 10 | ≈ 0 |
| 上下文工程 | 18 | ≈ 1（只省了「多轮消息拼接」这点样板代码） |
| 输入/输出管道 | 16 | ≈ 0 |
| 稳定性 | 14 | ≈ 0 |
| 计费与账本 | 12 | ≈ 0 |
| 可观测与评测 | 10 | ≈ 1（trace 钩子） |
| 安全防御合规 | 8 | ≈ 0 |
| **合计** | **100** | **≈ 10 人月（10%）** |

也就是说：**框架给你省了 10 人月，但你还有 90 人月要干，而且那 90 人月才是决定能不能上线的部分。** 这不是说框架不值——2 人月换 10 人月，ROI 很好。它说的是：**你不能把架构决策的思考成本，外包给一个库。**

**（B）事故账**。Aurora 上线后 12 个月，P0/P1 事故 23 起，归因：

| 归因 | 起数 | 其中最典型的一起 |
| --- | --- | --- |
| 限流/配额/隔离 | 6 | 大租户跑批把公共配额吃光，小客户全超时 40 分钟 |
| 计费与账本 | 4 | 流式场景下用量未知导致漏单，月结差 7.4% |
| 缓存/前缀 | 3 | 缓存 key 漏了 `prompt_version`，旧提示词答案被复用 |
| 上下文爆窗 | 3 | 检索注入 6 篇文档把输出挤掉 |
| 流式/连接 | 3 | 反代缓冲导致「假流式」，TTFT 从 1.2s 变 12s |
| 撤回失败 | 2 | 已 flush 到屏幕的错误结论无法收回 |
| 编排/控制流 | **0** | — |

**编排层贡献 0 起 P0/P1。** 这就是「12%」这个数字最锋利的地方：**它对应的不是 12% 的价值，而是 0% 的 P0 事故。** 你花三个月纠结选 LangGraph 还是 eino，其实在优化一个从不出事的模块。

**（C）成本账**。每 Run 的 token 账单，各层能省多少：

```
基线（无任何优化）        44,000 in + 1,200 out
  ├─ 提示词瘦身            -18%     （上下文层）
  ├─ 前缀缓存命中 68%      -61%     （上下文层 + 模型驱动）
  ├─ 上下文压缩（72% 触发） -22%     （上下文层）
  ├─ 路由（72% 走小模型）   -63%     （治理面）
  └─ 结果/语义缓存 9%命中   -9%      （治理面）
最终计费等效 ≈ 17,100 in + 1,200 out
```

注意：**上面四条杠杆，没有一条在编排层。** 编排层能省的只有「少调一次模型」——但那通常意味着质量下降，是最不划算的省法。

这张图解释了为什么「迁到 LangGraph 之后问题还在」：**框架住在中间那条窄缝里，而所有事故都发生在缝的外面。**

### 3.3.1 框架的两个抽象泄漏点

框架不是没用，是它的抽象在**两个地方会漏**，你必须提前知道：

| 泄漏点 | 现象 | 根因 | 应对 |
| --- | --- | --- | --- |
| **状态** | checkpoint 存的是「最新状态快照」，不是「事件历史」 | 图的状态是覆盖写的，为「恢复执行」设计，不为「审计/回放/计费」设计 | 快照 + 事件双写；真相源在事件库（第 6 章） |
| **流式** | 框架 yield 的是「节点事件」，不满足前端渲染契约 | 框架的流是「执行进度」，产品要的是「token 增量 + correction」 | 在框架外做事件规范化层（第 36、37 章） |

## 3.4 关键设计

### 3.4.1 判定表：「框架内建 = 原型，平台自研 = 生产」

这是本章的主交付物。**任何能力，问六个问题；任何一个「是」，就必须自研（或在框架外做一层）。**

| # | 判据 | 问自己 | 为「是」时的结论 |
| --- | --- | --- | --- |
| 1 | **跨租户** | 它出错会波及别的租户吗？ | 自研（框架没有租户概念） |
| 2 | **钱** | 它决定收多少钱吗？ | 自研（框架没有账本） |
| 3 | **责** | 出事平台要对外担责吗？ | 自研（框架没有审计链） |
| 4 | **真相** | 它是不是「发生了什么」的唯一记录？ | 自研（框架的 checkpoint 不是真相源） |
| 5 | **SLO** | 它的 P99 是你承诺给客户的那个数吗？ | 自研（框架不含超时预算与降级） |
| 6 | **热更** | 不重启、不发版能改吗？ | 自研（框架的图在代码里） |

套到具体的 14 项能力上：

| 能力 | 六判据命中 | 结论 | 用什么 |
| --- | --- | --- | --- |
| 图的拓扑（节点/边/分支） | — | ✅ 用框架 | LangGraph / eino / 自研状态机 |
| 单 Agent 内循环与最大步数 | 6（要求配置化） | ⚠️ 框架做循环、上限由内核注入 | 框架 + 内核 YAML |
| checkpoint 恢复执行 | 4 | ⚠️ 用框架的，但**并存事件日志** | 框架 checkpointer + 事件库 |
| interrupt / 人工审批 | 3,4 | ⚠️ 框架做中断，审批流自研 | 框架 + 审批服务（第 34 章） |
| 多 Agent handoff | 1（预算要跨 Agent） | ⚠️ 框架做消息路由，预算自研 | 框架 + 预算令牌（第 33 章） |
| 上下文装配 | 5 | ❌ 自研 | 上下文管理器（第 15 章） |
| 检索与重排 | — | ⚠️ 用现成库，权限下推自研 | Qdrant/pgvector + 过滤（第 20 章） |
| 模型调用与重试 | 1,2,5 | ❌ 自研 | 模型网关/驱动（第 26 章） |
| 限流与准入 | 1,5 | ❌ 自研 | 第 23 章 |
| token 计量与账本 | 2 | ❌ 自研 | 第 27 章 |
| 流式事件协议 | 5,6 | ❌ 自研 | 第 7、36 章 |
| 输出审计与撤回 | 3 | ❌ 自研 | 第 37 章 |
| trace 与成本归因 | 2,5 | ⚠️ 用 OTel 语义约定，采集自研 | 第 39 章 |
| 提示词版本与灰度 | 6 | ❌ 自研 | 第 16、42 章 |

**14 项里，只有 1 项是「放心用框架」，4 项是「框架做一半」，9 项是「必须自研」。** 这就是 12% 那张表的能力版。

### 3.4.2 把框架关进盒子里：适配器模式

既然框架会换（三年内你大概率会换一次），唯一正确的姿势是：**框架不许出现在业务代码里，只许出现在一个适配器实现里。**

```go
// orchestrator/port.go —— 平台定义的端口（稳定）
package orchestrator

type Graph interface {
	Nodes() []NodeSpec
	Start() NodeID
	Next(from NodeID, res NodeResult) (NodeID, bool) // bool=false 表示终止
}

// Engine 是平台唯一的执行业务入口。注意：它不做治理，治理由包裹层做。
type Engine interface {
	Run(ctx context.Context, g Graph, in Input, emit EventSink) (Output, error)
	Resume(ctx context.Context, runID RunID, sig Signal) (Output, error)
}
```

```go
// orchestrator/langgraph_adapter/adapter.go
// 框架的全部痕迹都被关在这一个包里。业务代码见不到 lg.* 任何符号。
package langgraph_adapter

type adapter struct{ cli *lg.Client } // 若是 Hosted 版；嵌入式则是 python/go 进程桥

func (a *adapter) Run(ctx context.Context, g orchestrator.Graph, in orchestrator.Input,
	emit orchestrator.EventSink) (orchestrator.Output, error) {

	// 1) 平台图 → 框架图的翻译（拓扑、条件边）
	compiled := a.translate(g)

	// 2) 框架的执行流事件 → 平台事件（这是最脏的一层，要写足测试）
	stream := compiled.StreamEvents(ctx, in, emit.RunID())

	for ev := range stream {
		switch ev.Kind {
		case "node_start":
			emit.Status(ev.Node, StatusRunning)
		case "node_end":
			emit.StepDone(ev.Node, ev.Output)
		case "interrupt":
			// 框架的中断只是「暂停」；审批、通知、超时由平台负责（第 34 章）
			return orchestrator.Output{}, ErrSuspended{Node: ev.Node, Payload: ev.Payload}
		}
	}
	return emit.Final(), nil
}
```

```java
// 对照：Java 侧同样的判断——不要继承框架基类，只实现自己的端口
public interface AgentEngine {
    RunResult run(GraphSpec spec, RunInput in, EventSink sink) throws SuspendException;
    RunResult resume(RunId id, Signal sig);
}
// Spring 里用 @ConditionalOnProperty 切实现：
//   agent.engine=langgraph | eino | native
// 业务 Bean 只依赖 AgentEngine，永不 import 任何框架包。
```

这里的关键不是代码，是**依赖方向**：

```
业务代码 ──▶ Engine 接口（平台）
                ▲
                └── langgraph_adapter / eino_adapter / native 实现
                        └── 第三方框架（唯一允许 import 它的地方）
```

再加一条 CI 规则 **就闭环了：业务模块的 `go.mod` 里不许出现框架仓库；出现即 fail**。这条规则的价值，会在你第二年换框架时体现出来。

### 3.4.3 编排逻辑本身有多小

很多人以为「编排」很重。把它写出来看看——**一个生产级 step 执行器的核心判断，真的只有 40 行左右**：

```go
func (e *executor) step(ctx context.Context, r *Run) (next RunState, err error) {
	// 治理前检查（都不属于编排，但必须在这里做，因为只有这里有全局视野）
	if err = e.gate.Admit(ctx, r); err != nil { return "", err }
	if r.Steps >= e.limit.MaxSteps { return StateBudgetExceeded, nil }
	if r.CostUSD >= e.limit.MaxCostUSD { return StateBudgetExceeded, nil }
	if ctx.Err() != nil { return StateCancelled, nil }

	// 上下文装配（内核）
	view, err := e.kctx.Alloc(ctx, r.ContextSpec())
	if err != nil { return "", err }

	// —— 以下才是「编排」，10 行 ——
	out, err := e.model.Complete(ctx, view, r.Tools)
	if err != nil { return "", err }
	if len(out.ToolCalls) == 0 {
		return StateCompleting, nil          // 没有工具调用 → 该收尾了
	}
	for _, tc := range out.ToolCalls {       // 有工具 → 并行/串行执行后回到本步
		if _, err := e.kernel.Invoke(ctx, tc); err != nil { return StateToolFailed, nil }
	}
	return StateRunning, nil
}
```

数一下：真正属于「编排」的只有 `len(out.ToolCalls) == 0` 这个判断和那个 for 循环。**剩下的每一行都是治理。** 而你在选型会议上花的时间，全在讨论「这个判断该用哪个框架的语法写」。

> 💡 一个反直觉的结论：**当你的平台成熟后，「换编排框架」的成本会趋近于零（因为它在适配器后面），而「换掉一个治理决策」的成本会趋近于无穷（因为它在跑着的几十万个 Run 里）。** 所以架构评审的重点，应该从「选框架」挪到「定治理」。

## 3.5 Java / 分布式经验对照：三个必须忘掉的直觉

| 你的经验 | 迁移判断 | 会咬人的地方 |
| --- | --- | --- |
| 「用 Spring 就不用管事务传播了」 | 🔴 **必须忘掉** | 没有任何框架会自动帮你处理「上下文一致性」「预算一致性」；你不管就一定错 |
| BPMN / Camunda 做流程引擎 | 🟡 像但不同 | BPMN 假设**每个节点是确定性的、可回滚的**；Agent 的节点是非确定性模型调用，不可回滚、只能补偿。硬套 BPMN 会得到一个「无法重放的流程引擎」（第 12 章） |
| 「选个成熟框架省得造轮子」 | 🟢 依然成立 | 但轮子的边界要算清：省 10 人月，剩 90 人月才是主线 |
| 状态机（Spring StateMachine） | 🟢 直接可用 | 状态要外置成事件，不能放进程内（第 6 章） |
| 依赖注入管理组件 | 🟢 直接可用 | 用它来做「引擎可替换」（§3.4.2 的 `agent.engine` 开关） |
| 微服务「每个服务选自己的技术栈」 | 🔴 **必须忘掉** | 编排可以各异；**上下文装配、计量、审计必须统一**，否则账对不上（第 2 章判定表） |

| **LangGraph** | 图（节点 + 条件边）+ 可持久化执行 | `thread_id` + checkpointer（快照） | Python / JS；可自托管或托管平台 | **interrupt/resume 与 checkpoint 做得最顺**；生态与文档最厚 | 无租户概念；流式事件是「执行进度」不是「渲染契约」；图写在代码里，热更难 | **控制流 DSL，成熟度最高** |
| **eino**（CloudWeGo） | Graph / Chain 组合 + 中断恢复 | checkpoint store | **Go** | Go 团队的「两个月」；与 CloudWeGo 生态同源，性能与部署模型符合后端习惯 | 生态比 LangGraph 小；Agent 之外的平台能力同样为零 | **Go 版控制流 DSL** |
| **Dify** | 可视化 Chatflow/Workflow + 知识库 + 应用管理 | 会话 + 工作流运行记录 | 平台型（自托管/云） | 开箱即用的**低代码装配**与运营界面；DSL 可导出 | 它是「一层」不是「底座」：多租户计费、限流、审计深度不够；定制深了要 fork | **平台的一个 UI 层，不是平台本身** |
| **OpenAI Agents SDK** | Agent + handoff + guardrails + tracing | 以 `Runner` 为中心，状态较轻 | Python / JS | 把「单个 Agent 的循环、交接、护栏、trace」写得非常干净 | 与自家模型体系耦合最深；跨 provider 与治理仍要自建 | **Agent loop 的参考实现** |
| **DSPy** | Signature + Module + 优化器 | 无运行时状态 | Python | 把「提示词怎么写」变成**可编译、可优化**的问题 | **它不是编排框架**，跟运行时正交；线上热路径不用它 | **提示词编译器，不是执行器** |

### 3.6.1 三个容易被误判的点

**① LangGraph 的 checkpointer ≠ 事件溯源。** 它保存的是「图的状态」，语义是「从这继续跑」。你要的「第 3 步时上下文里有什么、花了多少钱、谁批的」它不提供。这两者要并存，详见第 6 章。

**② Dify 不是你的竞争对手，是你的「租户侧 UI」。** 很多团队的路线是「先自研底座，再在底座上做一个 Dify 式的装配界面」。反过来（拿 Dify 当底座）会在第 4 个月撞墙：计费、限流、审计、租户隔离都要 fork 进去，而那正是 88% 的部分。第 49 章讲低代码层该怎么做。

**③ DSPy 与编排不冲突。** 它在离线阶段优化「哪个提示词/示例组合最好」，产出物是一份提示词资产；线上阶段它不参与。把它和 LangGraph 并列讨论，是把「编译期」和「运行期」混为一谈。

> ⚠️ 以上项目的 API 与能力边界演进很快，**具体类名与方法以官方文档最新版为准**；本书只承诺「定位判断」不会过时。

## 3.7 事故清单

- [ ] **事故 1：框架升级破坏抽象。** 现象：升级后 `stream` 事件类型改名，前端渲染全乱。→ 根因：业务代码直接消费了框架事件。→ 兜底：§3.4.2 的适配器 + 平台事件协议冻结；框架版本锁定 + 升级前跑录制回放（第 48 章）。
- [ ] **事故 2：checkpoint 当审计用。** 现象：监管来查「为什么拒了这笔退款」，你只能给出最新状态。→ 根因：把「恢复执行」当成了「真相记录」。→ 兜底：事件日志双写（第 6 章）+ 审计哈希链（第 31 章）。
- [ ] **事故 3：图里写死提示词。** 现象：改一句话要发版，发版窗口一周一次，业务方等不起。→ 根因：配置与代码边界错了。→ 兜底：提示词资产化 + 按租户热更 + 灰度（第 16、43 章）。
- [ ] **事故 4：框架自带重试覆盖了你的重试。** 现象：写工具被调用 3 次，客户收到 3 封邮件。→ 根因：两层重试叠加，且都没幂等键。→ 兜底：全局只允许一层重试（内核），写操作强制幂等键（第 22 章）。
- [ ] **事故 5：「框架支持流式」被当成「流式做完了」。** 现象：TTFT 12 秒，用户以为卡死。→ 根因：反代缓冲 + 框架事件粒度太粗。→ 兜底：`X-Accel-Buffering: no`、分段 flush、TTFT 进 SLO（第 36 章）。
- [ ] **事故 6：多 Agent 预算失控。** 现象：一个 supervisor 起了 6 个子 Agent，全会话成本 $14。→ 根因：handoff 只传消息不传预算。→ 兜底：预算令牌随 handoff 一起传，子 Agent 花完即停（第 33 章）。

## 3.8 一页速记

| 关键词 | 必须记住的结论 |
| --- | --- |
| 12% | 编排只占一次生产 Run 的 12%；它贡献 0 起 P0，却占了 80% 的选型讨论时间 |
| 工程量 | 框架省约 10 人月；你还剩 90 人月才是主线 |
| 本质 | 框架是**控制流 DSL**，不是运行时、不是平台、不含租户/账本/审计 |
| 六判据 | 跨租户 / 钱 / 责 / 真相 / SLO / 热更——任一为「是」，就必须自研 |
| 14 项 | 1 项放心用、4 项用一半、9 项必须自研 |
| 适配器 | 框架只许出现在 adapter 包里；CI 禁止业务模块 import 框架 |
| 编排有多小 | 一个生产级 step 执行器，纯编排逻辑约 10 行，其余全是治理 |
| 换框架 vs 换治理 | 换框架成本趋近 0（在适配器后）；改治理决策成本趋近无穷（在跑着的 Run 里） |

| 一句话 | **选框架决定你两个月后能不能跑；定治理决定你两年后还在不在。** |

## 3.9 自检题

1. **团队说「我们用了 LangGraph 的 checkpoint，所以状态问题解决了」。这句话哪里不对？**
   > 要点：checkpoint 解决的是「从哪继续跑」，不解决「发生过什么」。三件事它做不到：① 审计取证（只保留最新快照）；② 精确计费（缺每一步的 token/成本明细）；③ 跨版本回放（快照里的对象结构随代码版本变化）。正确姿势是事件日志为真相源 + 周期性快照加速恢复，详见第 6 章。

2. **如果只能自研一块，你选自研哪块？为什么？**
   > 要点：按「六判据命中数 × 事故史」排序，优先级是：① 计量与账本（钱，错了收不回）→ ② 限流与准入（跨租户，爆炸半径最大）→ ③ 事件模型（真相源，其它一切的地基）→ ④ 上下文装配（质量与成本的主战场）。编排层永远排最后，因为它可以换、且有现成的。

3. **老板问「既然编排只占 12%，那我们干脆不用框架，全自己写行不行？」怎么答？**
   > 要点：技术上可行，经济上不划算。框架省的是 10 人月的「已经踩过的坑」（中断恢复、条件边、事件流语义），而你自己写第一版一定会踩一遍。正确回答是：**用框架、但把它关在适配器里**；把省下的 10 人月投到那 90 人月上。判据是「这块属于六判据中的哪一条」——不属于就买/用，属于就必须自研。
