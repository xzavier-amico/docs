# 35. 前处理层：把脏输入挡在花 token 之前

> **状态**：`已完成（初稿）` ｜ **所属**：第七部分 · 输入输出管道 ｜ **编号**：35 / 52
> **本章定位**：前处理是整条链路里**唯一能在花钱之前做决定的地方**。它的投入产出比是全平台最高的——但它也是最容易被写成「一堆正则散落在 handler 里」的地方，然后就永远没人敢动。
> **读法**：先看 §35.2 的账（省下来的钱是具体的），再看 §35.3 的管道结构。§35.5 给了一份可以直接改成生产的 pipeline 骨架。**顺序很重要：便宜的先跑，贵的短路。**

## 35.1 引子：一天 $30,000 花在「不该进模型的东西」上

Aurora 上线第 4 个月，成本看板出现一个奇怪的形状：

```
日均 Run：120 万次
日均成本：$18,400
单次平均：$0.0153
──────────────────────────────
但成本分布极度倾斜：
  Top 0.8% 的 Run（约 9,600 次）      吃掉 $14,200（77%）
  其中最大的 1,200 次              单次 $0.19 ~ $0.31
```

点进去看那 1,200 次，全都是同一类：**用户上传了一份巨大的文档，然后问一句话**。

```
用户：帮我看看这份手册里关于退换货是怎么规定的
附件：product-manual-v9.pdf  ← 812 页，8.4 万字，约 6.5 万 token
→ 前处理：没有解析，直接把 base64 塞进 message（因为「多模态支持」）
→ 输入 65,000 token × $2.5/M = $0.16
→ 模型还超了上下文，被截断，答错了
→ 系统自动重试一次（带完整上下文）→ 又 $0.16
→ 用户不满意，重问一次 → $0.16
──────────────────────────────
单次会话：$0.48，得到的是一个错误答案
```

同一天还有两笔账在流血：

- **21.6 万次垃圾请求**（广告、乱码、越狱话术、单字「在吗」）——全部进了模型，平均每次 $0.009，**$1,944/天**。
- **3.2% 的会话因为历史里有「断裂的工具消息」被模型 API 拒绝**（400 `messages: tool_call_id not found`），然后走重试 → 重试还是失败 → 最后降级到「通用话术」。用户觉得「它突然变笨了」。

三个问题指向同一件事：**你在最贵的地方（模型）做最脏的活（清洗、判断、修复）。**

> 🎯 **本章要建立的第一个共识**：
> **前处理每多花 1 毫秒，就可能省下 100 毫秒的模型时间和 100 倍的 token 钱。** 判断依据是成本量级差，不是「架构洁癖」。

## 35.2 账本：钱是在哪里漏的

### 35.2.1 四类「不该进模型」的输入

| 类型 | 占入站比例 | 单次成本（不处理） | 处理方式 | 单次成本（处理后） | 日节省 |
| --- | --- | --- | --- | --- | --- |
| **垃圾/滥用**（广告、乱码、越狱、无意义） | 18% | $0.009 | 规则 + 小模型拦截 | $0 | **$1,944** |
| **超大输入**（>32k token 的附件/粘贴） | 1.2% | $0.25（还常答错） | 附件旁路解析 + 检索/摘要 | $0.03 | **$3,168** |
| **简单意图**（FAQ、问候、状态查询） | 38% | $0.015 | 路由前置：模板/工具直调/小模型 | $0.004 | **$5,016** |
| **脏会话历史**（断裂/超长/乱序） | 3.2%（触发重试） | ×1.8（重试放大） | 会话状态修复 | ×1.0 | **$1,060** |

四类加起来的**名义节省是 56%**，实测总成本降 **43%**（$18,400 → $10,500/天）——差额是因为重叠：一个超大输入往往同时也是简单意图，你不能省两次。

> 💡 **这张表最该记住的不是数字，是顺序**：**垃圾拦截（几乎零成本）→ 超大输入（贵但省得多）→ 路由前置（要维护规则）→ 会话修复（要改数据模型）**。按这个顺序做，第一周就能看到账单变化。

### 35.2.2 前处理的延迟预算

前处理不是免费的，它吃的是 TTFT（第 36 章）。Aurora 的预算表：

| 阶段 | P50 | P99 预算 | 超标后果 |
| --- | --- | --- | --- |
| 解码 + 规范化 | 1ms | 4ms | 首字慢，用户无感 |
| 长度/重复/乱码判定 | 0.3ms | 2ms | — |
| 注入规则预检 | 2ms | 8ms | — |
| PII 识别 | 6ms | 20ms | 吃掉 TTFT 的 2.5% |
| 意图分类（小模型） | 14ms | 40ms | **必须可跳过**（超时即放行） |
| 会话状态修复 | 3ms | 10ms | — |
| 路由决策 | 1ms | 3ms | — |
| **合计** | **27ms** | **90ms** | TTFT 预算 800ms 的 **11%** |

三段铁律：

1. **整条链 P99 ≤ 90ms，超过就必须短路放行**（带 `degraded=true` 打标）。前处理慢到 300ms，你省下的钱还不如流失的用户值钱。
2. **任何需要外部 RPC 的 stage 必须有本地兜底**（PII 服务挂了 → 用正则兜底 → 再不行放行并打标）。
3. **附件解析永远是旁路（async）**。PDF/图片解析 200ms~5s，绝不能同步等在请求里（见 §35.4.5）。

## 35.3 结构图：九站管道 + 三条出口

```
入站请求（原始 bytes + 元数据）
   │
   ▼
┌──────────────────────────────────────────────────────────────────────┐
│ ① 解码与规范化      UTF-8 修复 · NFC · 零宽剥离 · 全角转半角 · 去控制符 │  1ms
├──────────────────────────────────────────────────────────────────────┤
│ ② 结构校验          长度上限 · 重复率 · 乱码比 · 语言检测              │  0.3ms
├──────────────────────────────────────────────────────────────────────┤
│ ③ 注入/越狱预检     规则(AC自动机) → 小模型 → (2%不确定)大模型判定      │  2~40ms
├──────────────────────────────────────────────────────────────────────┤
│ ④ 入站 PII          识别 → 可逆 tokenize（占位符 + 加密映射）           │  6ms
├──────────────────────────────────────────────────────────────────────┤
│ ⑤ 会话状态修复      断裂工具消息 · 超长历史 · 乱序 · 空 assistant       │  3ms
├──────────────────────────────────────────────────────────────────────┤
│ ⑥ 意图识别与路由    规则/小模型 → {直答·工具直调·小模型·大模型·需澄清}   │  14ms
├──────────────────────────────────────────────────────────────────────┤
│ ⑦ 多语言预处理      语言归一 · 翻译补齐 · 术语表注入                    │  2ms
├──────────────────────────────────────────────────────────────────────┤
│ ⑧ 附件旁路（async） 解析 → 结构化 → 切片入索引，主链只等 150ms 拿摘要  │  旁路
└──────────────────────────────────────────────────────────────────────┘
   │
   ├──▶ 出口 A：拦截（block）        → 兜底话术 + 风控记分（零 token）
   ├──▶ 出口 B：直答（short-circuit）→ 模板/工具直调/小模型（省 100% 大模型）
   └──▶ 出口 C：入模型（continue）   → 需要澄清则先反问（也是省钱）

                                   ▲
   失败兜底：任何 stage 超时/异常 → 按 stage 的 fail 策略决定放行或拒绝
             （矩阵见 §35.6，不是「一律放行」也不是「一律拒绝」）
```

**三条出口是这个管道最重要的事**。很多实现只有一个出口（continue），于是「拦截」变成了「在 prompt 里骂模型一顿」，白花 token。**短路（short-circuit）是一等公民，它的返回值是一个完整的响应，不是 error。**

## 35.4 各站设计要点

### 35.4.1 规范化：不是修饰，是防绕过

规范化看起来是「清洗数据」，实际上是**安全前置**。你所有的正则、AC 自动机、分类器都是在规范化之后的文本上工作的——**规范化漏一步，后面所有检测都被绕过**。

必须做的六件事：

| 操作 | 为什么 | 漏了会怎样 |
| --- | --- | --- |
| UTF-8 替换非法字节 | 客户端可能发 GBK/截断的多字节 | 后续正则崩在非法序列上 |
| **Unicode NFC 归一化** | `é` 有 `U+00E9` 和 `e+U+0301` 两种写法 | 关键词匹配半失效 |
| **剥离零宽字符**（U+200B/200C/200D/FEFF） | 攻击者用零宽字符切碎关键词 | 「忽\u200b略\u200b以\u200b上」绕过所有规则 |
| **全角转半角**（U+FF01~FF5E） | `ｉｇｎｏｒｅ ａｌｌ` 全角写法 | 英文关键词规则全废 |
| 剥离控制字符（除 `\n\t`） | 终端转义、日志注入 | 前端渲染被劫持 |
| 去 ANSI 转义 | 从终端/日志粘贴 | 显示乱码 |

> ⚠️ **不要在这里做「去标点」「去空格」这类激进归一化**。它会让「3.5」和「35」变成同一个东西，模型答错数学题，而你永远查不出来。

### 35.4.2 长度、重复、乱码：最便宜的三道闸

```go
// pre/structure.go —— 三项 O(n) 判定，合计 <0.5ms，能挡掉大量浪费
func StructuralCheck(raw []byte, text string, cfg Limits) Issue {
	// 1) 硬长度（按字节，不是按 token —— 算 token 就贵了）
	if int64(len(raw)) > cfg.MaxBytes { // Aurora: 2MB 原始 / 200KB 文本
		return Issue{Kind: "too_large", Action: "reject_413"}
	}
	// 2) 重复率：同一句话刷 500 遍是常见攻击（刷 token 也刷缓存）
	if rep := repetitionRatio(text, 50); rep > 0.85 { // 50 字符滑窗
		return Issue{Kind: "high_repetition", Action: "compress_or_block"}
	}
	// 3) 乱码/低信息量：可打印字符比 + 词元熵
	if !plausibleText(text) {
		return Issue{Kind: "gibberish", Action: "clarify"} // 让它「请描述得更清楚些」
	}
	return Issue{}
}
```

三者的共同点：**不需要模型、不需要外部服务、纯 O(n)**。这类检查应该 100% 覆盖，且永不放行失败（它们不会误伤到能解释不清的程度）。

### 35.4.3 注入预检：三级漏斗，把「按 token 付费」变成「按规则付费」

这是本章最能体现「成本思维」的一节。三种做法对比：

| 方式 | 单次成本 | 延迟 | 召回 | 适合 |
| --- | --- | --- | --- | --- |
| **规则（AC 自动机 + 正则）** | ~$0（CPU 2ms） | 2ms | 中（已知模式） | 第一级，覆盖 80% 的已知攻击 |
| **小模型分类器**（如 100M 级微调分类器/嵌入+LR） | $0.00002 | 14ms | 高（泛化好） | 第二级，处理规则的漏网 |
| **大模型判定**（LLM-as-judge） | $0.003 | 600~1200ms | 最高（能理解语义） | 第三级，只处理不确定样本 |

直接全用大模型判定：120 万次 × $0.003 = **$3,600/天**，比被攻击的损失还大。所以必须漏斗：

```
120 万次/天
   │
   ├─ 规则判定（2ms, $0）──── 明确恶意 21.6 万（18%）──▶ 拦截  ✅ 零成本
   │                      └─ 明确无害 83 万（69%）────▶ 放行
   │
   └─ 灰色 15.4 万（13%）
        │
        ├─ 小模型（14ms, $0.00002）── 明确 92% ──▶ 拦截/放行
        │
        └─ 不确定 1.2 万（1%）
             │
             └─ 大模型判定（$0.003）──▶ $36/天
────────────────────────────────────────────
总成本：$36/天（对比全用大模型 $3,600/天，省 99%）
```

> 💡 **漏斗的分界点是「不确定性」，不是「分数」**。规则层要输出三态（恶意/无害/不确定），而不是一个 0~1 的分数——分数阈值调参是无底洞，三态设计能让每一级的职责清晰。

### 35.4.4 意图识别与路由前置：第一个省钱闸门

38% 的请求根本不需要大模型。典型分布（Aurora 客服场景，120 万次/天抽样）：

| 意图类别 | 占比 | 正确路径 | 成本 |
| --- | --- | --- | --- |
| 打招呼/感谢/告别 | 11% | **模板直答**（随机变体） | ~$0 |
| FAQ 精确命中（「几点上班」「怎么开发票」） | 14% | **知识库直出**（不算模型） | ~$0 |
| 状态查询（「我的订单到哪了」） | 9% | **工具直调 + 模板渲染** | ~$0 |
| 闲聊/情绪安抚 | 4% | 小模型 | $0.002 |
| 需要推理/多步 | 52% | 大模型（可能要工具/检索） | $0.02 |
| 需要澄清（信息不足） | 10% | **先反问一句**（省一次大模型调用） | $0.001 |

两个关键设计：

1. **分类器必须便宜且可解释。** 用「规则优先 + 小模型兜底」，而不是「用大模型先分类」（那是花大钱省小钱）。规则：关键词、正则、槽位、租户配置的快捷指令。
2. **「需要澄清」也是一个省钱出口。** 信息不足时先反问（「您说的是哪个订单？」），比带着猜测跑 8 步工具 + 大模型便宜 20 倍，而且体验更好。

```go
// pre/route.go —— 路由前置：输出的是「路径」，不是「意图标签」
type Route struct {
	Path      string  // template | faq | tool_direct | small_model | large_model | clarify
	Confidence float64
	Reason    string  // 进 trace，用于后续离线分析「为什么走了这条路」
	CostEst   int64   // 预估微美元，进预算令牌（第 33 章）
}

func Decide(in *Input) Route {
	// ① 租户显式快捷指令（最高优先级，业务知道自己要什么）
	if r, ok := matchTenantShortcut(in); ok {
		return r
	}
	// ② 极短输入 + 命中寒暄词表
	if len(in.Text) <= 12 && isSmallTalk(in.Text) {
		return Route{Path: "template", Confidence: 0.95, Reason: "smalltalk"}
	}
	// ③ FAQ 精确/近精确命中（向量相似度 > 0.92 且答案有版本）
	if faq := lookupFAQ(in); faq != nil {
		return Route{Path: "faq", Confidence: faq.Score, Reason: "faq:" + faq.ID}
	}
	// ④ 单槽位工具查询（正则抽出订单号/单号 + 动词）
	if tool, args, ok := matchToolPattern(in); ok {
		return Route{Path: "tool_direct", Confidence: 0.9, Reason: "pattern:" + tool}
	}
	// ⑤ 小模型分类（超时 40ms 即放弃，落到 large_model）
	if r, ok := smallClassifier.Classify(in, 40*time.Millisecond); ok && r.Confidence > 0.8 {
		return r
	}
	// ⑥ 信息不足（缺少关键槽位）→ clarify
	if needClarify(in) {
		return Route{Path: "clarify", Confidence: 0.7, Reason: "missing_slot"}
	}
	return Route{Path: "large_model", Confidence: 0.5, Reason: "default"}
}
```

> ⚠️ **路由前置最大的风险是「错路由」**，不是「没路由」。一个本该走大模型的复杂问题被送到 FAQ，用户会得到答非所问的答案，而他不会告诉你——他直接走了。所以：**路由必须可回归测试**（第 40 章），且低置信度一律走大模型。**宁可多花 1 美分，不要少答一个真问题。**

### 35.4.5 附件与多模态：永远旁路

附件的本质是「一个可能要 5 秒的解析任务」，而你的请求预算只有 800ms。所以架构上必须分开：

```
同步主链（必须 <150ms）：
   附件元信息校验（大小/类型/页数）→ 若已有解析缓存则取摘要
   → 否则返回「正在解析，请稍候」的 status 事件 + 建异步任务
                                  │
异步旁路（SLA 30s，P99 2 分钟）：  ▼
   下载 → 类型识别 → 解析（Tika/Unstructured/OCR）→ 结构化
   → 切片 → 入向量索引（带 tenant/permission，第 20 章）
   → 更新 Run 的上下文可引用集合 → 唤醒 Run 继续
```

| 附件类型 | 解析器 | 陷阱 |
| --- | --- | --- |
| PDF（文本层） | pdfium / Tika | 扫描件无文本层 → 必须判空后转 OCR |
| PDF（扫描） | OCR（PaddleOCR/Tesseract） | 表格结构丢失 → 视觉模型或专用表格抽取 |
| Word/Excel | Tika / 专用库 | 合并单元格、批注、隐藏行 |
| 图片 | 视觉模型 | **图片里的文字也可能是指令**（间接注入，第 30 章）→ OCR 后的文本也要过注入预检 |
| CSV | 采样 + 列类型推断 | 4 万行不能全进上下文（§33.1 的事故）→ 只给 schema + 统计 + 按需查询 |
| 网页链接 | 抓取 + 正文抽取 | **最危险的输入**：外部内容天然是攻击载荷（间接注入）→ 剥标签 + 注入预检 + 隔离标记 |

**成本对比（这是 §35.1 那笔 $0.25 的解法）**：

```
不处理：65,000 token 全塞上下文 → $0.16/次，还答错
处理后：解析出 412 个切片 → 检索 top-8（约 2,800 token）+ 文档摘要（200 token）
        → $0.0075/次，准确率反而更高
省：95% 成本，且答案更好
```

### 35.4.6 入站 PII：两种脱敏，用途完全不同

| 方式 | 做法 | 什么时候用 | 代价 |
| --- | --- | --- | --- |
| **不可逆脱敏** | 识别 → 替换成 `«PHONE»` | 日志、trace、给第三方 MCP server 的参数 | 模型无法在答案里回填真实值 |
| **可逆 tokenize** | 识别 → 替换成 `«PII_7f3a»` + 加密映射表（存在服务端，TTL = 会话） | 需要模型「引用但不看到」真实值；答案生成后回填 | 映射表是新的敏感资产，必须加密 + 审计 |

关键判断：**入站 PII 脱敏不是为了「防模型」，是为了「防日志、防第三方、防训练数据」**。模型本身要不要看到真实手机号，取决于业务——客服场景通常需要，那就只做「日志/trace/第三方出口」的脱敏。

> 🩸 最容易漏的一处：**工具调用参数里的 PII 会被写进 trace**。你把 user message 脱敏了，但工具调用 `send_sms(phone="138...")` 的参数原样进了日志。**脱敏必须在「出口」做（日志/trace/MCP/训练集），而不是只在「入口」做。**

### 35.4.7 会话状态修复：不修就会 400

这一站最不起眼，但它决定了你的 4xx 率。脏数据的形态是有限的，穷举即可：

| 脏形态 | 症状 | 修复策略 |
| --- | --- | --- |
| **孤儿工具结果**（有 `tool` 消息，没有对应的 `assistant.tool_calls`） | API 400 | 丢弃该消息，记 `repair:orphan_tool_result` |
| **缺失工具结果**（有 `tool_calls`，没有 `tool` 回复） | API 400（OpenAI 严格） | 补一条 `tool_result: {"error":"interrupted"}`，或整段回退到调用前 |
| **assistant 空内容**（`content=""` 且有 tool_calls） | 部分供应商 400 | 允许（合法），但要有 `content: null` 的正确写法 |
| **历史超长**（> 模型上下文 80%） | 截断/400/成本爆炸 | 压缩 + 滑动窗口（第 18 章），并保证不切断 tool 对 |
| **时间戳乱序** | 模型理解错因果 | 按 `created_at` 重排，同序保持插入顺序 |
| **重复用户消息**（网络重发） | 模型重复回答 | 按 `(role, content_hash, 5s 窗口)` 去重 |
| **跨模型不兼容字段**（`reasoning_content`、`cache_control`） | 换模型后 400 | 按目标模型的能力矩阵裁剪字段（第 26 章） |
| **被用户打断的 tool_calls** | 半截工具链 | 标记 `interrupted`，让模型知道「上次没查完」 |

**核心原则：修复必须是「确定性的、幂等的、可观测的」。** 同一份脏历史修复两次结果必须一样（否则事件重放会漂移），每次修复记一条 `repair` 事件（否则你永远不知道它在偷偷改数据）。

### 35.4.8 多语言预处理

| 问题 | 处理 | 注意 |
| --- | --- | --- |
| 语言检测错误（短文本、混排） | 用「字符集 + 停用词 + 小模型」三票制；低于置信度就不检测 | 中英混排很常见，不要强行归一 |
| 低资源语言 | 先翻译成主语言 → 处理 → 翻回（质量换成本） | 翻译本身也是模型调用，要计入预算 |
| 术语表 | 按租户注入「术语 → 译法」表 | 术语表进 prompt 会打穿前缀缓存（第 24 章）→ 放 suffix 或工具 |
| 全角/半角、繁简 | 归一化（可配置：繁体用户不强转） | 繁简转换会改人名/品牌名 |
| RTL（阿拉伯语/希伯来语） | 双向文本隔离符要剥离 | 否则拼接后渲染错乱 |

## 35.5 完整的 pipeline 骨架（Go）

```go
// pre/pipeline.go —— 九站管道：短路优先、逐站超时、失败按策略降级
package pre

import (
	"context"
	"errors"
	"time"
)

// 短路：不是错误，是一个完整响应
type ShortCircuit struct {
	Response Response // 直接返回给用户的内容
	Reason   string   // 进 trace + 指标
	Stage    string
}

func (s *ShortCircuit) Error() string { return "short_circuit:" + s.Stage + ":" + s.Reason }

// FailPolicy 决定某站失败时放行还是拒绝 —— 必须逐站配置，不能全局一刀切
type FailPolicy int

const (
	FailOpen  FailPolicy = iota // 失败即放行（带 degraded 打标）
	FailClose                   // 失败即拒绝（安全优先）
)

type Stage interface {
	Name() string
	Budget() time.Duration
	FailPolicy() FailPolicy
	// Run 修改 in；返回 *ShortCircuit 则终止管道
	Run(ctx context.Context, in *Input) error
}

type Pipeline struct {
	stages  []Stage
	metrics Metrics
}

func (p *Pipeline) Execute(ctx context.Context, in *Input) (*Input, error) {
	chainStart := time.Now()
	for _, st := range p.stages {
		sctx, cancel := context.WithTimeout(ctx, st.Budget())
		err := st.Run(sctx, in)
		cancel()

		p.metrics.ObserveStage(st.Name(), time.Since(chainStart), err)

		var sc *ShortCircuit
		switch {
		case err == nil:
			continue
		case errors.As(err, &sc):
			p.metrics.IncShortCircuit(st.Name(), sc.Reason)
			in.ShortCircuit = sc
			return in, nil // ★ 正常返回，带短路响应
		case errors.Is(err, context.DeadlineExceeded):
			if st.FailPolicy() == FailOpen {
				in.Degraded = append(in.Degraded, st.Name()+":timeout")
				continue // 超时放行（绝大多数 stage 都应该这样）
			}
			return nil, err
		default:
			if st.FailPolicy() == FailOpen {
				in.Degraded = append(in.Degraded, st.Name()+":error")
				continue
			}
			return nil, err
		}
	}
	p.metrics.ObserveChain(time.Since(chainStart), len(in.Degraded) > 0)
	return in, nil
}

// 装配顺序 = 成本顺序（便宜的在前，贵的在后，能短路的尽量前）
func Build(cfg Config, deps Deps) *Pipeline {
	return &Pipeline{stages: []Stage{
		&NormalizeStage{},                                               // 1ms  FailClose（规范化失败=输入不可解析）
		&StructureStage{Limits: cfg.Limits},                             // 0.3ms FailClose
		&InjectionStage{Rules: deps.Rules, Small: deps.SmallClf, FailOpen: true}, // 2~40ms FailOpen
		&PIIStage{Detector: deps.PII, Mode: cfg.PIIMode},                // 6ms  FailOpen + 打标
		&SessionRepairStage{Store: deps.Store},                          // 3ms  FailClose（不修就没法调）
		&IntentRouteStage{Small: deps.SmallClf, FAQ: deps.FAQ},          // 14ms FailOpen
		&I18nStage{Tenant: cfg.Tenant},                                  // 2ms  FailOpen
	}}
}
```

三条从踩坑里提炼的规则：

1. **短路返回 nil error**。如果短路走 error 路径，你的错误率看板会被「正常的拦截」污染，真正的故障被淹没（和第 33 章「预算耗尽不是 error」是同一个道理）。
2. **FailPolicy 逐站配置**。规范化/结构/会话修复 → `FailClose`（这几种修不好就一定调不通）；注入/PII/意图 → `FailOpen` + 打标（宁可放过，不能全站挂）。
3. **`Degraded` 列表必须进 trace**。它是你唯一的证据链：用户投诉答得差，你要能看出「这次 PII 检测超时了，所以没脱敏就放行了」。

## 35.6 失败兜底矩阵

| Stage 失败 | FailOpen 后果 | FailClose 后果 | Aurora 选择 | 理由 |
| --- | --- | --- | --- | --- |
| 规范化 | 后续规则可能崩 | 用户看到 400 | **FailClose** | 不可解析的输入没有处理意义 |
| 结构校验 | 超大输入进模型（贵） | 拒绝大文件 | **FailClose**（但给明确提示 + 上限说明） | 成本事故的主要来源 |
| 注入预检 | 可能放过注入 | 全站不可用 | **FailOpen + 输出侧兜底**（第 30/37 章） | 注入检测永远有漏，不能靠它做唯一防线 |
| PII 识别 | PII 进日志/第三方 | 客服无法工作 | **FailOpen + 强制日志脱敏兜底（正则）** | 可用性优先，但出口侧必须硬脱敏 |
| 会话修复 | 400 错误 | 用户被拒 | **FailClose + 优雅降级话术**（「会话需要刷新」） | 修不好就调不通，但话术要好 |
| 意图路由 | 全走大模型（贵但正确） | 拒绝 | **FailOpen** | 贵一点可以接受，答不了不行 |
| 附件解析 | 主链拿不到摘要 | 附件不可用 | **FailOpen + 异步重试 + 告知用户** | 附件是旁路，不该阻塞主链 |

兜底话术的设计原则：**说清「发生了什么」+「下一步做什么」+ 不要暴露内部结构**。

```
❌ 「前处理失败：PIIStage timeout」          —— 内部信息泄露
❌ 「系统错误，请稍后再试」                   —— 用户不知道能做什么
✅ 「这个文件太大了（上限 20MB / 200 页），你可以压缩后重发，或者直接告诉我你想查哪部分」
```

## 35.7 可观测：拦了多少、拦对了多少

前处理最大的风险是「静默错误」——它一直在拦，但拦错了，而你看不出来（用户直接走了）。所以指标必须包含**质量**，不只是**数量**。

| 指标 | 定义 | 目标 | 怎么算 |
| --- | --- | --- | --- |
| **拦截率** | blocked / inbound | 15%~25%（高于 30% 说明规则太狠） | 计数器 |
| **短路率** | short_circuit / inbound | 30%~45% | 计数器 |
| **误拦率** | 被拦但人工判定应放行 / 抽检量 | **< 2%** | 每日抽 500 条人工标注 + 用户申诉回流 |
| **漏拦率** | 放行但下游判定应拦 / 抽检量 | < 8% | 从输出侧审核与投诉回溯 |
| **前处理 P99** | 整链耗时 | < 90ms | Histogram |
| **Stage P99 分布** | 每站耗时 | 见 §35.2.2 | Histogram per stage |
| **FailOpen 率** | degraded=true / inbound | < 0.5% | 计数器 |
| **路由准确率** | 抽样人工判定「该路径是否合适」 | > 92% | 每周 300 条抽检 |
| **意图分布漂移** | 各 path 占比的 7 日变化 | 漂移 < 10% | 对比看板 |
| **单次平均 token（按 path）** | 分路径的 token 均值 | 大模型 path 不涨 | 与计费联动 |

看板字段（Prometheus 命名）：

```yaml
# 前处理看板必备 12 个面板
pre_requests_total{stage, result}                 # 每站计数：ok/short_circuit/timeout/error
pre_chain_duration_seconds{quantile}              # 整链 P50/P95/P99
pre_stage_duration_seconds{stage, quantile}       # 每站耗时
pre_short_circuit_total{stage, reason}            # 短路按站/原因
pre_degraded_total{stage}                         # fail-open 次数
pre_route_total{path}                             # 路由分布（template/faq/tool/small/large/clarify）
pre_route_confidence_bucket{path}                 # 置信度分布（低置信度多了=分类器退化）
pre_pii_entities_total{type, action}              # PII 识别量（突然变化=攻击或客户端 bug）
pre_session_repair_total{kind}                     # 修复类型（orphan_tool/missing_result/...）
pre_injection_total{level, verdict}                # 三级漏斗各层判定
pre_tokens_saved_estimate_total{path}              # 估算省下的 token（用于证明 ROI）
pre_false_block_ratio                             # 人工抽检回填（离线任务写回）
```

> 💡 **`pre_tokens_saved_estimate_total` 这个指标决定了你这条管道能不能继续投人**。没有它，前处理永远是「看不见的基建」，预算评审时第一个被砍。

## 35.8 Java / 分布式经验对照

| 你的 Java 经验 | 前处理里对应 | 会咬人的地方 |
| --- | --- | --- |
| Spring Cloud Gateway 的 GlobalFilter / PreFilter | 前处理的 Stage 链 | 那边是「无状态、几毫秒、失败即 500」；这里必须**逐站 fail 策略 + 短路返回正常响应** |
| Servlet Filter 的 `chain.doFilter` | 管道执行 | 短路在 Filter 里是「不调 doFilter」，但你需要**返回一个完整响应**，这在 Filter 模型里很别扭 → 用责任链 + 显式 Result |
| 责任链模式（GoF） | Stage 链 | 同构，但要注意「每站超时」——Java 里给每站加超时要么靠 `CompletableFuture.orTimeout`，要么靠虚拟线程 + 中断 |
| Sentinel 的「热点参数」 | 结构校验（长度/重复） | 类似，但这里的判定结果不是「限流」而是「短路 + 提示」 |
| 反垃圾/内容安全的既有系统 | 注入预检 | 可直接复用**规则引擎**，但「三态输出」需要改造（老系统通常只给分数） |
| 数据清洗 ETL | 规范化 | ETL 可以慢、可以批；这里是 2ms 的在线路径，**不能做任何 IO** |
| 虚拟线程（Java 21） | 附件旁路解析 | 很适合：解析交给虚拟线程，主链不阻塞；但要注意 CPU 密集型的 OCR 会占满 carrier 线程 |
| MDC / traceId | 前处理的 trace 上下文 | 必须把 `degraded`、`route.path`、`repair` 全塞进 span，否则事后无法归因 |

> 🩸 **最典型的错误**：把前处理写成 `@Async` 或消息队列，然后「并行执行所有 stage」。看起来更快，实际上**破坏了顺序语义**——PII 脱敏必须在注入检测之后（否则占位符会打乱检测），会话修复必须在意图识别之前（否则历史不一致会让分类器误判）。**这条链是有序的，能并行的只有「互不依赖的检查」**（长度 + 语言检测可以并行）。

## 35.9 开源坐标

| 能力 | 开源/产品 | 给你什么 | 缺什么 |
| --- | --- | --- | --- |
| 输入输出护栏 | Guardrails AI、NeMo Guardrails | 声明式 rail、格式校验、可组合 | 缺「成本分层漏斗」，也缺「短路返回完整响应」的语义 |
| PII 识别 | Microsoft Presidio | 可扩展 recognizer、匿名化算子 | 中文召回一般；**可逆 tokenize + 映射表审计**要自己做 |
| 文档解析 | Apache Tika、Unstructured | 格式覆盖广、输出结构化 | 扫描件/复杂表格质量有限；**旁路调度与 SLA** 要自己做 |
| 敏感词/规则 | Aho-Corasick 实现（各语言都有） | 毫秒级多模式匹配 | 只解决「已知模式」，泛化为零 |
| 意图分类 | 各家的小模型 / 嵌入 + 分类头 | 便宜、快 | 需要自建标注集；**「路径」而不是「意图」的建模要自己做** |
| 文档切片/索引 | RAGFlow、Unstructured + 向量库 | 切片策略、增量索引 | 与「附件旁路 → 唤醒 Run」的编排要自己做（第 20 章） |
| 会话状态 | 无标准开源 | — | **这块几乎必须自研**（因为脏数据的形态取决于你的历史版本） |

> **一句话**：**开源给了你「识别器」，没给你「管道」。** 而前处理 80% 的价值在管道的顺序、短路、超时与 fail 策略上——这些东西没有库能替你决定。

## 35.10 事故清单

- [ ] **事故 A：8 万字手册直塞上下文** —— 现象：单次 $0.48，答错还重试。→ 根因：附件没走旁路解析。→ 兜底：附件异步解析 + 检索 top-k + 硬上限。
- [ ] **事故 B：零宽字符绕过所有规则** —— 现象：注入话术带 `\u200b` 全部通过。→ 根因：规则跑在原始文本上。→ 兜底：规范化必须前置，且进回归集。
- [ ] **事故 C：意图错路由** —— 现象：复杂问题被送进 FAQ，答非所问，用户流失。→ 根因：分类器阈值调太低 + 无回归测试。→ 兜底：低置信度走大模型；路由准确率纳入发布门禁。
- [ ] **事故 D：PII 检测超时导致日志泄露** —— 现象：trace 里出现完整手机号。→ 根因：PII stage fail-open 后没有任何兜底。→ 兜底：fail-open 时启用「正则兜底的日志脱敏」（出口侧强制）。
- [ ] **事故 E：会话修复不幂等** —— 现象：断线重连后历史出现两条 `interrupted` 工具结果，模型行为漂移。→ 根因：修复每次追加而不判重。→ 兜底：修复用确定性规则 + 以 `repair_id` 去重。
- [ ] **事故 F：前处理拖垮 TTFT** —— 现象：TTFT P95 从 900ms 涨到 1.6s。→ 根因：意图分类器换成大模型判定。→ 兜底：整链 P99 预算硬门禁 + 超时短路。
- [ ] **事故 G：附件解析阻塞连接池** —— 现象：高峰期全站超时，但 CPU 不高。→ 根因：PDF 解析同步在请求 goroutine 里跑。→ 兜底：旁路 + 独立 worker 池 + 并发上限。
- [ ] **事故 H：规范化太激进** —— 现象：模型算错「3.5 万」和「35 万」。→ 根因：去标点/去空格。→ 兜底：只做安全类归一化，语义类一律不做。

## 35.11 一页速记

| 关键词 | 必须记住的结论 |
| --- | --- |
| 定位 | 唯一能在花钱前做决定的地方；每 1ms 前处理可能省 100ms 模型时间 |
| 顺序 | 便宜的先跑（规范化 1ms → 规则 2ms → 小模型 14ms → 大模型只在 1% 上用） |
| 三条出口 | 拦截 / 短路直答 / 入模型——**短路是一等公民，返回完整响应而非 error** |
| 延迟预算 | 整链 P99 ≤ 90ms（TTFT 的 11%）；超时即短路放行 + 打标 |
| 规范化 | 零宽/全角/NFC 必做，**语义类归一化一律不做** |
| 注入漏斗 | 规则 → 小模型 → 大模型，$36/天 vs $3,600/天 |
| 路由前置 | 38% 请求不该进大模型；「需要澄清」也是省钱出口；低置信度一律走大模型 |
| 附件 | 永远旁路；主链只等摘要；解析结果进索引按需检索 |
| PII | 脱敏在**出口**做（日志/trace/MCP/训练集），不只在入口 |
| 会话修复 | 8 种脏形态穷举；修复必须确定性 + 幂等 + 记事件 |
| 失败 | 逐站 FailPolicy：规范化/结构/修复 FailClose，注入/PII/意图 FailOpen + 打标 |
| 指标 | 拦截率、**误拦率**、漏拦率、短路率、FailOpen 率、路由准确率、省下的 token |
| 一句话 | **前处理的价值不在「拦了多少」，而在「用几微秒的规则，替掉几美分的 token」。** |

## 35.12 自检题

1. **你的注入检测用大模型做，120 万次/天，合规吗？**
   > 要点：技术上能跑，经济上是灾难——$0.003 × 120 万 = **$3,600/天**，比被攻击的损失还大。正确做法是三级漏斗：规则（$0，覆盖 80%）→ 小模型（$0.00002，覆盖剩余 92%）→ 大模型（只处理 1% 不确定样本），总成本约 $36/天。关键是**规则层输出三态（恶意/无害/不确定）而不是分数**。

2. **为什么前处理的顺序不能随便调？举两个例子。**
   > 要点：① 规范化必须在所有检测之前——否则零宽字符/全角能绕过全部规则；② PII 脱敏必须在注入检测之后——否则占位符（`«PHONE»`）会打乱关键词匹配；③ 会话修复必须在意图识别之前——历史不一致会让分类器误判。能并行的只有互不依赖的检查（长度 + 语言检测）。

3. **「误拦率」怎么测？为什么它比「拦截率」重要？**
   > 要点：测法 = 每日抽 500 条被拦样本人工判定 + 用户申诉回流 + 从下游投诉回溯。重要性在于：**拦截率是内部指标（想高就能高），误拦率是外部效果（用户直接流失、你却以为一切正常）**。误拦率 > 2% 时，加防御的净收益可能是负的——你把真实客户挡在门外，只剩下攻击者在研究你的规则。
