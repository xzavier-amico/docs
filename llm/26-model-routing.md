## 26.1 引子：账单里 64% 是可以省掉的，但你不敢省

Aurora 上线第 4 个月，财务发来一张表：模型成本 **$1.86M/月**，占 COGS 的 71%。你拉了 3 天流量做归因，发现一个刺眼的事实：

| 请求类型 | 流量占比 | 用小模型的质量 | 当前用的模型 | 单 Run 成本 |
| --- | --- | --- | --- | --- |
| 「我的快递到哪了」类查询 | 45% | 96.2%（vs 大模型 97.1%） | 大模型 | $0.081 |
| 多轮工单处理 / 改地址 | 38% | 88.4%（vs 91.0%） | 大模型 | $0.081 |
| 退款判定 / 合规口径 / 投诉安抚 | 17% | 61.3%（vs 92.5%） | 大模型 | $0.081 |

第一行那 45% 的流量，用小模型只掉 **0.9 个百分点**的质量，成本却能降到 **$0.0049**（1/16）。第二行掉 2.6 个点，降到 $0.0257（1/3）。第三行掉 31 个点——**绝对不能动**。

于是你兴冲冲上了路由：按「问题长度 + 是否含订单号」硬编码。第一周成本降了 58%，第二周投诉涨了 3 倍。原因是：

```
用户：我要退这个订单，但我之前那个地址填错了，能不能先改地址再退？
路由判定：含"订单"、长度 28 字 → 简单 → 小模型
小模型：可以，请提供新地址。（漏了"已发货订单不能改地址"这条硬规则）
结果：用户改了地址，退款被拒，投诉到监管平台。
```

**这就是路由的本质矛盾**：它用「平均质量」做决策，但事故发生在「那一个不该被降级的 case」上。所以路由的第一原则不是「省钱」，而是**「什么情况下绝对不许省」**。

本章的三层防线：

| 层 | 作用 | 手段 |
| --- | --- | --- |
| 硬规则（不可越过） | 挡住「绝不能省」的场景 | 意图黑名单、租户等级、合规标签、风险分 |
| 打分（省钱的战场） | 在合格模型里挑性价比最高的 | 质量/成本/延迟三目标打分 |
| 探索（长期最优） | 发现「其实小模型也行」的新场景 | A/B、bandit、影子流量 |

## 26.2 断崖：路由做错的五种方式

| # | 错误做法 | 典型动机 | 后果 | 量级 |
| --- | --- | --- | --- | --- |
| 1 | 按价格排序，取最便宜的 | 「成本降 90%」 | 质量塌方，投诉/退款 | 质量 92→61 分 |
| 2 | 按问题长度/关键词硬编码 | 上手最快 | 长尾漏配，新意图默认走错 | 覆盖率 60%，误判 8~15% |
| 3 | 只看单次调用成本 | 算账偷懒 | 忽略重试与重算的**期望成本** | 小模型失败率高 → 实际省不到 50% |
| 4 | 路由配置没有版本与回滚 | 「就改一行 YAML」 | 一次配置事故 = 全站质量事故 | 分钟级影响 5,000 QPS |
| 5 | 不区分「可降级」与「不可降级」 | 一刀切 | 合规/高危场景被降级 | 1 次 = 监管事故 |

第 3 条要展开，因为它是「省了钱但账不对」的根源。路由的真实成本是**期望成本**，不是单价：

```
E[cost(m)] = c(m) + p_fail(m) · (c(m) + c_escalate)

  p_fail = 小模型答不好 → 触发重试/升级大模型/人工介入的概率
  c_escalate = 升级成本（≈ 大模型单价 + 0.3s 额外延迟的价值）

例：M-small 单价 $0.0049，但 12% 需要升级：
  E = 0.0049 + 0.12 × (0.0049 + 0.081 + 0.002) = 0.0049 + 0.01055 = $0.0155
  比 M-medium 的 $0.0257 还便宜，但只便宜 40%，不是 81%
```

**如果你只按单价算，会高估 2~3 倍的节省**——这直接导致「预算批了、效果没到」的尴尬。

## 26.3 结构图：四层漏斗，越往下越贵

```
 请求（含 tenant / agent / intent 候选 / 上下文特征）
   │
   ├─▶ ① 硬规则层（<0.05ms，纯内存查表，不可越过）
   │      · 合规标签命中 → 强制 M-large
   │      · 租户等级 = Enterprise 且 SLA 承诺 → 强制 M-large
   │      · 意图 ∈ {refund_decision, legal, medical} → 强制 M-large
   │      · 风险分 > 0.7（注入/越权嫌疑）→ 强制 M-large + 审核
   │      └─ 命中即返回，**不进入打分**
   │
   ├─▶ ② 任务分类层（2~8ms）
   │      · 规则（关键词/正则/长度）覆盖 ~55%
   │      · 小分类模型（embedding + LR/GBDT）覆盖剩余，置信度 <0.7 → 走默认池
   │      · 输出：intent（32 类）+ confidence + 所需能力（工具/长上下文/结构化）
   │
   ├─▶ ③ 打分层（<0.1ms，纯计算）
   │      S(m|t) = wq·q̂(m,t) − wc·ĉ(m) − wl·l̂(m)
   │      硬约束：q̂ ≥ q_min(t)、l̂ ≤ l_max(t)、上下文窗口够、工具支持齐
   │      → 取 argmax，平局取更便宜的
   │
   └─▶ ④ 探索层（10% 流量，异步决策）
          · A/B：固定分流（可解释、可回滚）
          · Bandit：Thompson sampling（自适应，但要护栏）
          · 影子：5% 双跑，只观测不对外

  所有决策都写一条 route 记录：
    {trace_id, route_version, intent, chosen_model, score, reason, fallback_chain}
```

## 26.4 关键设计

### 26.4.1 打分函数：三目标必须归一化，否则权重毫无意义

最朴素的写法是 `score = w1·质量 - w2·成本 - w3·延迟`。问题是三个量的单位不同（质量是 0~1，成本是 $0~0.08，延迟是 0~40s），直接加权等于让「成本」这一项被数字大小主导。

必须先归一化到同一个尺度——**以「最贵的基线模型」为 1**：

```
S(m | t) = wq · q̂(m, t)  −  wc · ĉ(m)  −  wl · l̂(m)

其中：
  q̂(m,t) = quality(m, t) / 1.0                质量分 0~1（离线评测集实测）
  ĉ(m)    = E[cost(m)] / E[cost(M_large)]      期望成本（含升级概率）
  l̂(m)    = p99_latency(m) / p99_latency(M_large)
  wq + wc + wl = 1

硬约束（不满足直接淘汰，不进打分）：
  q̂(m,t) ≥ q_min(t)          # 该意图的质量下限，如退款判定 0.90
  l̂(m)   ≤ l_max(t)          # 该场景的延迟上限，如交互式 1.0（=大模型 P99）
  context_window(m) ≥ 需要的 token
  supports_tools(m) = true   # 该任务需要工具调用时
```

Aurora 的权重与结果（客服场景，`wq=0.60, wc=0.25, wl=0.15`）：

| 模型 | 单价(in/out) | 单 Run 期望成本 | 成本归一 | P99 | 延迟归一 | 简单任务质量 | **S（简单）** | 复杂任务质量 | **S（复杂）** |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| M-large | $2.5/$10 | $0.081 | 1.00 | 9.0s | 1.00 | 0.95 | 0.170 | 0.92 | 0.152 |
| M-medium | $0.8/$3 | $0.0257 | 0.32 | 4.0s | 0.44 | 0.90 | **0.394** | 0.80 | 0.334 |
| M-small | $0.15/$0.6 | $0.0049 | 0.06 | 1.8s | 0.20 | 0.86 | **0.471** ✅ | 0.61 | 0.321 ❌ |

看最后一行：复杂任务里 M-small 的分数 0.321 比 M-medium 的 0.334 只低一点——**如果没有硬约束，它会经常赢**。这就是为什么约束比权重重要：

```
复杂任务设 q_min = 0.85 →
  M-small 0.61 被淘汰；M-medium 0.80 被淘汰；只剩 M-large。
```

```go
// router/score.go
type ModelStat struct {
    Name       string
    Cost       float64 // E[cost]，含升级概率
    CostNorm   float64
    P99        time.Duration
    LatencyNorm float64
    Quality    map[string]float64 // intent -> 0~1，来自离线评测
}

func (r *Router) Score(m ModelStat, intent string, w Weights) (float64, bool) {
    q, ok := m.Quality[intent]
    if !ok { return 0, false } // 没测过 = 不许用（见 26.4.4）
    c := r.cfg.Constraints[intent]
    if q < c.MinQuality || m.LatencyNorm > c.MaxLatency {
        return 0, false
    }
    return w.Quality*q - w.Cost*m.CostNorm - w.Latency*m.LatencyNorm, true
}
```

> ⚠️ **`Quality` 表里没有的 intent，一律不许路由过去**。这条规则救过我们：新上线的意图没有评测数据，打分函数默认给它 0.9（"应该差不多"），结果它 100% 走了小模型，两周后才发现质量是 0.7。

### 26.4.2 任务分类：便宜的规则 + 更便宜的模型

分类器的预算很紧：**分类成本必须 < 单次请求成本的 1%**，且延迟 <10ms。所以不要一上来就用 LLM 做分类。

| 手段 | 覆盖率 | 延迟 | 成本 | 准确率 | 用法 |
| --- | --- | --- | --- | --- | --- |
| 规则（关键词/正则/长度/是否带 ID） | ~55% | <0.05ms | 0 | 91% | 先跑，命中即用 |
| 意图分类小模型（embedding + GBDT） | 剩余 45% 的 ~80% | 4~8ms | ~$0.00002 | 88% | 第二道 |
| LLM 分类（小模型 few-shot） | 剩余 | 300~800ms | $0.0004 | 94% | 只用于高价值/低置信 |
| 默认池（不分类） | 兜底 ~8% | 0 | 0 | — | 置信度 <0.7 时 |

注意最后一行：**置信度低时路由到「默认池」而不是「猜一个」**。默认池 = M-medium，是「不会太贵也不会太差」的安全选择。

意图表（Aurora 客服，节选）：

| intent | 流量占比 | 模型池 | q_min | 备注 |
| --- | --- | --- | --- | --- |
| `logistics_query` | 31% | M-small | 0.80 | 有工具，答案结构化，最好路由 |
| `order_modify` | 14% | M-medium | 0.85 | 写操作，要过审批（第 34 章） |
| `faq_policy` | 12% | M-small（+ 语义缓存） | 0.85 | 答案是固定政策，缓存优先（第 24 章） |
| `complaint_handling` | 9% | M-large | 0.90 | 情绪+合规，绝不能降 |
| `refund_decision` | 6% | **M-large（硬规则锁定）** | 0.92 | 金额判定，事故高发 |
| `multi_step_task` | 8% | M-medium | 0.86 | 3 步以上工具循环 |
| 其他/未知 | 20% | 默认池 M-medium | 0.84 | 置信度低时不猜 |

### 26.4.3 A/B 与 bandit：一个用来证明，一个用来赚钱

两者的目的完全不同，别混用：

| 维度 | A/B 测试 | 多臂老虎机（bandit） |
| --- | --- | --- |
| 目的 | **证明**「新策略更好」 | **在探索中最大化累计收益** |
| 分流 | 固定比例（如 50/50），全程不变 | 动态调整，好的多给流量 |
| 统计 | 需要样本量计算、显著性检验 | 不需要预先定样本量 |
| 适合 | 上线前验证、合规要求可解释 | 长期在线优化（如「这个 intent 到底该用哪个模型」） |
| 风险 | 低（比例固定可回滚） | 中（可能短时间内偏向一个坏臂） |
| 周期 | 3~7 天（要覆盖工作日/周末） | 持续运行 |

Aurora 的做法是 **「A/B 定生死，bandit 做微调」**：

```
① 新模型/新策略上线：A/B 10% 流量，跑 7 天，看质量 + 成本 + 延迟三指标
② 通过后：进入 bandit 池，per-intent 独立跑 Thompson sampling
③ bandit 有护栏：任一臂的 1 小时质量低于基线 2 个点 → 立刻冻结该臂
```

Thompson sampling 的实现要点（Beta-Bernoulli，成功/失败二值化）：

```go
// router/bandit.go
type Arm struct{ Alpha, Beta float64 } // 先验 Beta(1,1)，成功/失败计数

func (b *Bandit) Pick(intent string) string {
    best, bestSample := "", -1.0
    for name, a := range b.arms[intent] {
        s := rand.New(rand.NewSource(time.Now().UnixNano())).Float64()
        // Beta 采样（Go 标准库无 Beta 分布，用两个 Gamma 或近似）
        x := betaSample(a.Alpha, a.Beta)
        _ = s
        if x > bestSample { best, bestSample = name, x }
    }
    return best
}

func (b *Bandit) Update(intent, arm string, ok bool) {
    a := b.arms[intent][arm]
    if ok { a.Alpha += 1 } else { a.Beta += 1 }
    b.arms[intent][arm] = a
}
```

四个必须加的护栏（裸 bandit 在生产里很危险）：

| 护栏 | 参数 | 为什么 |
| --- | --- | --- |
| 最小样本 | 每臂 ≥200 次/天 | 否则先验主导，等于随机 |
| 探索上限 | 非最优臂 ≤10% 流量 | 防止长期把 30% 流量浪费在差模型上 |
| 冷启动保护 | 新臂前 50 次强制走 A/B 固定比例 | 避免新臂因运气好被瞬间放量 |
| 质量护栏 | 1h 窗口质量低于基线 2pt → 冻结 | bandit 只看「奖励」，会忽略长尾质量 |

> 💡 bandit 的奖励函数（reward）不要只用「用户没投诉」。我们用 `reward = 1 if (judge_score ≥ 4/5 and 无重试 and 无投诉) else 0`，把「省钱」放在约束里而不是奖励里——否则 bandit 会学出「全用最便宜的模型」这种局部最优。

### 26.4.4 影子流量：唯一能回答「新模型会不会更差」的手段

上线新模型前，最安全的方式是**双跑**：真实流量 100% 走现网，同时镜像 5% 到候选模型，只比较、不对外。

```
用户请求 ──┬──▶ 现网模型 M-large ──▶ 返回给用户（100%）
           │
           └──▶ 影子：候选 M-new（5%）──▶ 只落库，比对，不返回
                                            │
                        比对维度：judge 分数 / 工具调用正确率 / 延迟 / 成本
                        门槛：judge ≥ 基线 - 0.5pt，工具正确率 ≥ 基线 - 1pt
```

成本与收益：

| 项 | 数值 |
| --- | --- |
| 额外成本 | 5% × 80 万 Run × $0.081 ≈ **$3,240/天** |
| 避免的损失 | 一次「新模型质量掉 8 分」的全量事故 ≈ 客诉 + 回滚 + 信誉，远超此数 |
| 发现能力 | 能在 24 小时内发现 1pt 级别的质量差异（1 万样本） |
| 局限 | 只能看「答案好不好」，看不到「多轮对话的体验」 |

影子流量的三个坑：

1. **影子请求不能有副作用**。所有写工具（发邮件、改订单）必须 mock 或 dry-run，否则你会给用户发两封邮件。这是最容易出的事故。
2. **影子请求要独立限流**。它不应该抢现网配额，否则高峰期影子把主链路拖慢（第 23 章）。
3. **比对要有基线漂移意识**。judge 分数本身会随日期波动（用户问题分布变化），要比「同期同 intent 的现网结果」，不要比「上周的绝对值」。

### 26.4.5 配置化与回滚：路由是「会改变行为的配置」

路由策略必须满足三个条件，否则一次改配置就是一次事故：

1. **可预览**（dry-run）：拿昨天 24 小时的流量回放，输出「新策略会怎么分流、成本变化多少、多少请求会跌破质量下限」。
2. **可灰度**：按租户/意图/比例逐步放量（1% → 5% → 20% → 100%）。
3. **可回滚**：≤60 秒生效，且回滚本身不需要发版。

```yaml
# policy/routing.yaml（策略中心热更，见第 43 章）
version: route-2026-05-06.3
weights: { quality: 0.60, cost: 0.25, latency: 0.15 }

hard_rules:                      # ① 硬规则：先执行，命中即返回
  - when: { intent_in: [refund_decision, legal_advice, medical] }
    force: m-large
  - when: { tenant_tier: enterprise, sla: platinum }
    force: m-large
  - when: { risk_score_gt: 0.7 }
    force: m-large
    add_flags: [human_review]

intents:
  logistics_query:
    pool: [m-small, m-medium]
    q_min: 0.80
    max_latency_norm: 0.6
    explore: { type: thompson, max_off_policy: 0.10 }
  multi_step_task:
    pool: [m-medium, m-large]
    q_min: 0.86
  unknown:
    pool: [m-medium]             # 默认池：不猜
    q_min: 0.84

guardrails:                      # ② 护栏：自动回滚条件
  auto_rollback:
    - metric: judge_score
      window: 1h
      drop_gt: 0.02              # 掉 2 个点
      action: rollback_to_previous
    - metric: p99_latency
      window: 15m
      rise_gt: 0.30
      action: freeze_exploration

shadow:                          # ③ 影子流量
  enabled: true
  sample_rate: 0.05
  candidate: m-new-2026-05
  side_effects: dry_run          # 绝不产生真实副作用
```

dry-run 的输出必须是「可读的账」，否则没人敢点发布：

```
$ router preview --config policy/routing.yaml --replay 2026-05-05
 回放 812,441 个 Run（24h）
 分流：m-small 44.8% | m-medium 37.1% | m-large 18.1%（当前：m-large 100%）
 成本：$65,808 → $24,110  (-63.4%)
 预判质量：92.1 → 90.7（-1.4pt），跌破 q_min 的请求：1,204 个（0.15%）
 延迟 P99：9.0s → 4.1s
 ⚠️  警告：intent=faq_policy 的 q_min 未设置，建议补 0.85
```

### 26.4.6 什么时候**不该**做路由

这是本章最容易被跳过、但最省你时间的一节。路由有固定成本：

| 成本项 | 量级 |
| --- | --- |
| 分类器开发 + 维护 | 2~3 人周 + 持续标注 |
| 每个 (模型, 意图) 的质量评测 | 3 个模型 × 32 意图 × 200 样本 = 1.92 万条标注 |
| 影子/AB 的额外推理成本 | 5~10% |
| 路由本身的可观测与回滚 | 1 人周 |
| **误路由的事故成本** | 一次 = 数万次错误回答 |

判据：

```
若 月模型成本 < $20,000  → 别做路由，用「一个大模型 + 缓存」就够（第 24 章）
若 意图分布极度集中（Top1 意图 > 70%） → 直接 hardcode，不需要分类器
若 质量差异 < 3pt 且 成本差异 < 30% → 不值得，边际收益低于维护成本
```

Aurora 的日 Run 80 万、月成本 $1.86M，路由省 63% ≈ **$1.17M/月**——这个量级才值得投入 6 人月。

## 26.5 Java / 分布式经验对照

| 你的经验 | AgentOS 对应物 | 判断 | 会咬人的地方 |
| --- | --- | --- | --- |
| Spring Cloud Gateway `Predicate` + `Route` | 路由规则 | 🟡 要改造 | 网关路由是**确定性**匹配；模型路由是**概率 + 打分**，同一请求可能走不同模型 |
| Ribbon / LoadBalancer 加权轮询 | 多模型分流 | 🟡 要改造 | 负载均衡的目标是「均摊」，路由的目标是「按任务匹配」，不能均摊 |
| Nginx `split_clients`（按比例分流） | A/B | 🟢 直接迁移 | 分流键要含 `user_id`/`tenant_id`，否则同一会话在模型间漂移 |
| Nacos/Apollo 配置中心 | 路由策略配置 | 🟢 直接迁移 | 必须加 dry-run 与自动回滚，因为改的是「模型行为」 |
| 灰度发布（按流量比例） | 影子流量 | 🟡 要扩展 | 影子请求必须无副作用（写工具 dry-run） |
| 无「A/B + bandit」经验 | 在线探索 | 🔴 **新东西** | bandit 会忽略长尾质量，必须有护栏 |
| 熔断后切备用 | failover | 🟢 同构 | 但那不是路由（第 25 章）：路由是主动选，failover 是被动逃 |

## 26.6 开源坐标

| 项目 | 对应 | 能用 | 缺什么 |
| --- | --- | --- | --- |
| **LiteLLM Router** | 多模型分组、`routing_strategy`（simple-shuffle / least-busy / latency-based / cost-based）、fallbacks、cooldown | ✅ 最快的落地起点 | 不是「按任务质量」路由；无 dry-run；无 bandit |
| **RouteLLM**（开源研究项目） | 学习式路由（相似度加权、矩阵分解、BERT 分类器） | ✅ 方法论参考，可复现 | 面向「强/弱两个模型」，多模型与业务约束要自己加 |
| **OpenRouter** | 多模型聚合 + 价格/可用性排序 | ⚠️ 便利 | 路由决策与数据不在你手里（审计/合规风险，第 31 章） |
| **Martian / NotDiamond**（商业） | 商业路由器，按任务打分选模型 | ⚠️ 可评估 | 黑盒，无法解释「为什么选它」（评审过不了） |
| **vLLM / SGLang** | 自建模型池的调度 | ✅ 底层 | 不做业务路由 |
| **Langfuse / LangSmith** | 按模型切片看质量与成本 | ✅ 必接 | 不提供路由决策 |

> 🎯 判断：**LiteLLM 做「执行层的多模型调度」，自研做「决策层的任务路由」**。开源给的是「怎么把请求发给模型 B」，给不了「这个请求该不该发给模型 B」。

## 26.7 事故清单

- [ ] **A. 硬编码路由漏配**：新意图「改地址+退款」被判简单 → 小模型漏掉硬规则 → 监管投诉。→ 根因：关键词规则 + 无 q_min。→ 兜底：分类器 + 置信度低走默认池 + 退款类进硬规则黑名单。
- [ ] **B. 只按单价算账**：以为省 81%，实际省 40%（12% 需升级重跑）。→ 根因：用 `c(m)` 而非 `E[cost(m)]`。→ 兜底：成本模型含 `p_fail × (c + c_escalate)`。
- [ ] **C. 无约束的 bandit**：复杂任务被分到小模型，因为短期内「没投诉」。→ 根因：奖励函数只看短期信号。→ 兜底：`q_min` 硬约束 + 质量护栏（1h 掉 2pt 冻结）。
- [ ] **D. 影子流量产生副作用**：双跑时重复执行了 `send_email` → 用户收到 2 封。→ 根因：未对写工具 dry-run。→ 兜底：影子上下文强制 `side_effects: dry_run`，写工具直接返回 mock 结果。
- [ ] **E. 配置事故**：运维把 `unknown` 意图的池改成 `[m-small]` → 20% 流量质量塌方。→ 根因：无 dry-run、无灰度、无自动回滚。→ 兜底：回放预览 + 1%→100% 灰度 + 护栏自动回滚。
- [ ] **F. 路由不可归因**：成本降了但没人说得清「哪些请求走了哪个模型」。→ 根因：`route_version`/`chosen_model` 未进 trace。→ 兜底：每次决策落 `{intent, model, score, reason}`（第 39 章）。

## 26.8 一页速记

| 关键词 | 必须记住的结论 |
| --- | --- |
| 第一原则 | 路由先回答「什么绝对不能省」，再回答「怎么省」 |
| 三层 | 硬规则（不可越过）→ 打分（省钱战场）→ 探索（长期最优） |
| 打分式 | `S = wq·q̂ − wc·ĉ − wl·l̂`，必须归一化到「基线模型 = 1」 |
| 约束 > 权重 | `q_min` 淘汰掉「分数不低但绝对不该用」的模型；复杂任务 q_min=0.85 直接排掉 0.61/0.80 |
| 期望成本 | `E[cost] = c + p_fail·(c + c_escalate)`；只按单价算会高估 2~3 倍节省 |
| 未测过的意图 | `Quality` 表里没有 → **禁止路由过去**（默认 0.9 是自杀） |
| 分类 | 规则（55%，0 成本）→ 小模型（4~8ms）→ 置信度<0.7 走默认池，不猜 |
| A/B vs bandit | A/B 用来证明（固定比例、7 天）；bandit 用来赚钱（动态、带护栏） |
| bandit 护栏 | 最小 200 样本 / 非最优臂 ≤10% / 冷启动 50 次 / 1h 掉 2pt 冻结 |
| 影子 | 5% 双跑，$3,240/天，能做 1pt 级发现；**写工具必须 dry-run** |
| 可回滚 | dry-run 回放 24h → 1% 灰度 → 护栏自动回滚 ≤60s |
| 别做路由 | 月模型成本 <$20k、Top1 意图 >70%、质量/成本差异小 → 不值得 |
| 一句话 | **路由省的是平均成本，赔的是长尾质量——所以护栏比打分重要。** |

## 26.9 自检题

1. **你的打分函数是 `score = 0.6×质量 − 0.25×成本 − 0.15×延迟`，其中成本单位是美元（0~0.08）、延迟是秒（0~40）。这个函数有什么问题？**
   > 要点：量纲不一致。延迟的取值范围比成本大 500 倍，`0.15×40=6` 会完全压过 `0.25×0.08=0.02`，实际效果等于「只按延迟选模型」。必须先归一化：成本除以基线成本（0~1）、延迟除以基线 P99（0~1）、质量本身就是 0~1，这样权重才有意义。

2. **A/B 测试显示新路由质量 90.2（基线 90.5），但成本降了 60%。你能上线吗？还需要什么信息？**
   > 要点：不能只看均值。需要：① 差异是否显著（样本量、置信区间，-0.3pt 可能落在噪声里）；② 是否集中在某些 intent（比如只在 `refund_decision` 上掉了 6 个点，其余持平，均值被摊薄）；③ 长尾事故率（投诉/重试/人工介入）；④ 延迟是否改善到足以补偿（若 P99 从 9s 降到 4s，超时率下降可能反而提升任务成功率）。结论：要按 intent 切片看，不是看总分。

3. **为什么说「影子流量只能看，不能说」？它的两个最容易踩的坑是什么？**
   > 要点：影子流量不返回给用户，所以无法测量真实用户反应（满意度、追问答率、投诉），它只能比较「离线可判定的质量」。两个坑：① **副作用**——写工具（发邮件/改订单）必须在 dry-run 下 mock，否则用户收到双份；② **资源竞争**——影子请求要独立限流池，否则高峰期抢主链路配额，把「观测」变成「事故」。
