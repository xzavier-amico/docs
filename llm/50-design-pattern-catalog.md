## 50.1 引子：两个团队，同一个季度，两种死法

**A 团队**（客服 Agent，日 40 万 Run）。他们读了一篇讲「Reflection 让 Agent 变聪明」的文章，给每个 Agent 都加了「自我反思 + 修正」：生成答案 → 让模型自评 → 不满意就重写。上线一周后：

```
单 Run LLM 调用      5 次 → 8 次
单 Run 成本          $0.0316 → $0.0512   (+62%)
P50 延迟             12.1s → 19.8s
评测通过率           88.4% → 89.6%       (+1.2pt)
客诉率               持平
```

**多花 62% 的钱，换来 1.2 个点的通过率，客诉一点没降。** 因为客服场景的错误主要来自**知识库内容过时**和**工具返回不准**，而不是「模型没想清楚」。反思治的是「推理草率」，治不了「事实错误」——**它在错的层上加了一层。**

**B 团队**（数据分析 Agent，日 3 万 Run）。他们很谨慎，给每一次 LLM 调用都套了 Circuit Breaker（错误率 > 50% 就熔断 30 秒），理由是「模型供应商不稳定」。上线第三天，模型侧一次区域性抖动（错误率 12%，持续 90 秒），触发了 **300 多个独立的断路器**，其中 40% 在抖动结束后没有正确半开，导致：

```
整体成功率      99.1% → 71.4%
恢复时间        90 秒的抖动 → 27 分钟才回到 98%
```

因为熔断的粒度选错了：**断路器应该按「provider × 模型 × 区域」建，不是按「每次调用」建**。按调用建，你得到的是 300 个互相独立、各自为政的悲观者。

> 🩸 **本章的第一条判断**：**设计模式不是积木，是有失败模式的工程决策。** 每个模式的「何时用」都写在博客里，但「何时别用」和「它自己怎么坏」几乎没人写——而后者才是你半夜被叫起来的原因。

## 50.3 编排类（6 个）

| # | 模式 | 意图 | 何时用 | **何时别用** | **失败模式** | 章 |
| --- | --- | --- | --- | --- | --- | --- |
| ① | **Router** | 用最小代价判断「这是什么请求」，把请求分流到专用处理链 | 场景 ≥ 3 类且成本/质量要求差异大；简单问题占 60%+ | 分类边界模糊、类别会漂移；单次分类成本 > 省下的钱 | **误路由**：把退款请求路由到闲聊链 → 客户被敷衍。**分类器漂移**：新意图全落到 `other` 兜底 | 26、35 |
| ② | **Orchestrator-Worker** | 一个主 Agent 拆解任务，分派给多个专职 Worker，汇总结果 | 任务可分解且子任务独立（多文档分析、多仓库检索） | 子任务强依赖、需要全局一致视图；Worker 数量 < 3（不如串行） | **扇出爆炸**：拆出 40 个子任务，成本 ×40。**汇总丢失**：Worker 结论矛盾，主 Agent 编一个折中 | 33 |
| ③ | **Reflection** | 生成后自评/互评，再修正一轮 | **高价值 + 可判定**场景：代码生成（能跑测试）、SQL（能执行）、数学（能验算） | 事实性错误为主（知识库过时）；延迟敏感；成本敏感 | **同质化偏误**：模型评自己的答案永远「看起来不错」。**过度修正**：把对的改错。**成本 +62% 换 +1.2pt**（§50.1 A 团队） | 38、40 |
| ④ | **Plan-and-Execute** | 先产出结构化计划（步骤数组），再逐步执行，可中途修订 | 步数 ≥ 5 的长任务；需要人审计划；需要断点续跑 | 步数 ≤ 3；环境高度动态（计划一出就过期） | **计划幻觉**：编出不存在的工具/步骤。**计划僵化**：执行中发现前提错误却不重规划。**计划即攻击面**：注入让计划多出「导出全部客户数据」一步 | 12、33 |
| ⑤ | **Fan-out / Gather** | 并行发起 N 个独立调用（检索、工具、子 Agent），再聚合 | 延迟敏感且子任务互不依赖；多路召回需要融合（RRF） | 有共享可变状态；下游有 QPS 限制（并行会打爆它） | **尾延迟放大**：N 个并行，P99 = max(所有 P99)。**部分失败处理缺失**：一个失败就整体失败，浪费其余 4 个的钱 | 14、20 |
| ⑥ | **Loop Guard** | 给所有循环加三道闸：步数、预算、重复状态检测 | **无条件必用**。任何带循环的 Agent | 无（这是唯一一个「不用就是错」的模式） | **闸设在错的地方**：只限步数不限 token，20 步 × 30k 上下文照样烧穿。**闸后无告知**：直接静默截断，用户看到半句话 | 12、27 |

> ⚠️ **编排类最常见的一个误判**：把「模式多」当「架构好」。Aurora 的三个头部场景里，客服只用了 ①⑥，编码用了 ②③⑥，数据分析用了 ④⑤⑥。**没有一个场景同时用超过 4 个模式**——每多一个模式，你就多一个失败模式、多一份延迟、多一笔成本。模式是药，不是饭。

## 50.4 数据类（4 个）

| # | 模式 | 意图 | 何时用 | **何时别用** | **失败模式** | 章 |
| --- | --- | --- | --- | --- | --- | --- |
| ⑦ | **Event Sourcing** | 只追加事件，状态由重放得出；天然可审计、可回放 | Agent 平台**默认选择**：一次 Run 是多步状态迁移，中间态不可重算 | 纯查询型、无状态的服务；事件量极大且无需回放的场景 | **事件 schema 演进失控**：v3 的消费者读不懂 v1 事件。**重放不确定**：重放时模型版本变了，结果不一致（必须锁版本）。**快照缺失**：10 万事件的 Run 重放一次 40 秒 | 6 |
| ⑧ | **Outbox** | 业务事务内写一条 outbox 记录，由投递器异步发出，保证「改库」与「发事件」原子 | 任何「改了状态还要通知别人」的地方：结算后发账单、审批后恢复 Run | 事件可以丢（纯埋点、非关键通知） | **投递器重复发**：至少一次语义下没有幂等键 → 重复计费。**Outbox 表无限增长**：没做归档，一年后 8 亿行 | 13 |
| ⑨ | **CQRS** | 写侧是事件流，读侧是投影（会话列表、成本看板、审计视图） | 读写负载差异大；读侧需要多视图（列表页 vs 统计页） | 小规模系统（直接查主表就行）；强一致读需求 | **投影延迟**：用户发完消息刷新列表看不到（读到滞后投影）。**投影重放成本**：加一个字段要全量重放 3 天 | 45 |
| ⑩ | **Checkpoint / Replay** | 每步后存快照（状态 + 上下文 + 版本），崩溃从最近快照恢复 | 长任务（> 30 秒）、有副作用的工具链、需要断点续传 | 短任务；状态极小（重算更快） | **重放副作用**：从检查点恢复时又把邮件发了一遍（必须记录「哪些副作用已完成」）。**快照含密钥**：上下文快照里带了 API Key，落进对象存储 | 12 |

## 50.5 稳定性类（5 个）

| # | 模式 | 意图 | 何时用 | **何时别用** | **失败模式** | 章 |
| --- | --- | --- | --- | --- | --- | --- |
| ⑪ | **Bulkhead** | 按维度切资源池（租户/模型/工具/场景），一个池满不拖垮别的池 | 多租户；有「大客户 + 长尾」结构；工具会慢 | 池总数 × 每池最小副本 > 集群容量（过度切分） | **池化浪费**：40 个池各留 2 个副本，利用率 30%。**池选错维度**：按租户切了，但真正的热点是「某个工具」 | 28 |
| ⑫ | **Circuit Breaker** | 下游错误率高时快速失败，给下游恢复时间 | 模型 provider 抖动；三方工具不稳定 | **粒度 = 单次调用**（见 §50.1 B 团队）；下游只有一个实例 | **粒度错误**：300 个独立断路器各自熔断 → 整体成功率 71%。**半开风暴**：全部同时半开，二次打崩下游。**熔断成本**：熔断后全走降级话术，用户体感「变傻了」 | 25 |
| ⑬ | **Backpressure** | 消费端跟不上时，让生产端减速（令牌、窗口、拉模式） | 流式输出给慢消费者；工具结果批量回传 | 请求-响应短链（天然有背压） | **无界缓冲**：用 channel/queue 缓冲，内存涨到 OOM。**背压传导成超时**：整条链一起变慢，用户以为卡死 | 7、36 |
| ⑭ | **Load Shedding** | 过载时**主动**丢掉一部分请求，保整体成功率 | 峰值 > 容量 1.3 倍；有免费层可牺牲 | 请求不可丢（支付、审批提交） | **丢错对象**：把付费客户丢了，留下免费爬虫。**抖动**：阈值附近反复开关，成功率锯齿 | 23、28 |
| ⑮ | **Saga / Compensation** | 长事务拆成多步，失败时执行补偿动作（而非回滚） | 跨服务写操作（下单 + 扣款 + 发通知）；工具副作用无法回滚 | 有真正的事务（单库）；补偿动作本身有副作用（退款再退款） | **补偿失败**：补偿也要重试，进入「补偿的补偿」。**补偿顺序错**：先解冻资金再取消订单，中间态被读到 | 12、34 |

**算一笔账，看 ⑭ 为什么必须有**：

```
峰值 5k QPS，容量 4k QPS（P99 已到 30s）
不做 shed：5k 全部进队列 → 平均等待 25s → 全部超时 → 成功率 0%
做 shed（丢 20%）：4k 处理（P99 18s，成功率 99%）+ 1k 快速失败（50ms 返回 429）
                  → 整体成功率 79%，但**付费租户 99%、免费层 0%**
```

**「整体成功率 79%」比「100% 全挂」好得多**——而且你可以把 79% 里的 99% 留给付钱的人。这是有损服务的核心价值。

## 50.6 成本类（4 个）

| # | 模式 | 意图 | 何时用 | **何时别用** | **失败模式** | 章 |
| --- | --- | --- | --- | --- | --- | --- |
| ⑯ | **Reserve-Settle-Reconcile** | 调用前预扣额度，结束后按实际结算，日终与厂商对账 | 有预付费/额度/免费层；账单不能错 | 纯内部工具（成本不重要） | **漏单**：流式中途断连，预扣了没结算，钱悬着。**重单**：重试没有幂等键，扣两次。**对账差额>0.5% 无人看**：三个月后差出 $40k | 27 |
| ⑰ | **Semantic Cache + Guard** | 语义相似即命中，省下整次调用 | 高频重复问法（客服 FAQ 占 40%+） | 答案含个性化数据（订单、账户）；政策频繁变更 | **误命中**：阈值 0.85 时误命中 6.3%，其中 1.1% 造成实质错误答复（答了**别的租户**的退款政策）。**陈旧**：命中三个月前的答案 | 24 |
| ⑱ | **Budget Token** | 预算像令牌一样在主 Agent → 子 Agent 间传递，父收回子未用完的 | 多 Agent 协作；长任务；需要「谁花的钱」可归因 | 单 Agent 单步 | **子 Agent 烧穿全会话**：session 预算 $0.5，4 个子 Agent 各分 $0.3 → 实花 $1.2（2.4×）。**令牌泄露**：子 Agent 把令牌传给孙 Agent，父无法回收 | 27、33 |
| ⑲ | **Prefix Layering** | 上下文分层布局：稳定内容（system/角色卡/工具 schema）在前，易变内容（用户输入/检索）在后 | **所有场景**。缓存命中率从 24% → 62% 就靠这个 | 无（但要注意别把时间戳/随机 ID 放进前缀） | **前缀被打穿**：有人在 system prompt 里塞了「当前时间 2026-09-01 10:23:41」→ 命中率归零。**工具顺序随机**：每次序列化 tools 顺序不同 → 缓存全 miss | 18 |

**⑰ 的护栏必须写进代码**（这是全书最容易被抄错的一段）：

```go
// cache/semantic.go —— 带护栏的语义缓存：宁可少命中，不可错命中
type GuardedSemanticCache struct {
    idx        VectorIndex
    threshold  float32       // 生产值 0.95+，不是 0.85
    negTTL     time.Duration // 负缓存：明确「答不了」的结论也要缓存
}

func (c *GuardedSemanticCache) Get(ctx context.Context, q Query) (Answer, bool) {
    // ① 键必须含租户 + 场景 + 模型档 + 提示词版本 + 索引版本
    //    少任何一个，都是数据泄露或答非所问
    ns := cacheNS(q.TenantID, q.Scene, q.ModelTier, q.PromptVer, q.IndexVer)

    hits := c.idx.Search(ns, q.Embedding, 3)
    for _, h := range hits {
        // ② 阈值 + 内容一致性双重校验
        if h.Score < c.threshold {
            continue
        }
        // ③ 硬护栏：数字/订单号/日期/金额必须逐个对齐，否则不命中
        //    语义相似 ≠ 事实相同。"退款 3 天" 和 "退款 30 天" 的 embedding 距离极小
        if !entitiesMatch(h.Question, q.Text) {
            metrics.CacheRejectedEntityMismatch.Inc()
            continue
        }
        if h.Expired() || h.PolicyVer != q.PolicyVer {
            continue
        }
        return h.Answer, true
    }
    return Answer{}, false
}
```

> 💡 **一条经验值**：语义缓存的阈值不要拍脑袋。Aurora 用 800 条「同义问法 + 近义但不同答案」的对照集扫了一遍阈值：`0.85 → 误命中 6.3%`，`0.93 → 1.4%`，`0.96 → 0.2%（命中率从 31% 掉到 19%）`。**最终选 0.94 + 实体对齐护栏**，命中 22%，误命中 0.3%。

## 50.7 管道类（3 个）

| # | 模式 | 意图 | 何时用 | **何时别用** | **失败模式** | 章 |
| --- | --- | --- | --- | --- | --- | --- |
| ⑳ | **Dual-Channel Draft/Commit** | 主通道先吐「草稿」（可被替换），确认通道在 300~800ms 后提交终稿 | 内容有合规/事实风险；需要「已渲染内容可被替换」 | 纯创意写作；延迟极度敏感（< 500ms 首字） | **双写不一致**：草稿和终稿差太多，用户看到「换了一段话」。**确认流超时**：草稿已发，确认没来，前端不知道该等还是该显示 | 37 |
| ㉑ | **Pre-flight Gate** | 花 token 之前拦截：规范化、注入预检、审核、路由前置、配额预扣 | **所有入口**。这是成本与安全的第一道闸 | 无（但要控制延迟，目标 < 50ms） | **误杀**：正常问法被审核拦掉，用户莫名被拒。**延迟超标**：串了 6 个外部审核服务，前处理 800ms | 35 |
| ㉒ | **Retraction & Correction** | 已输出内容可被更正/撤回：截断、追加更正事件、整段 rebase、会话级撤销 | 流式输出 + 有审核滞后；政策变更；用户投诉 | 不可撤回的场景（已执行的转账）——那时要的是 ⑮ 补偿，不是撤回 | **撤回失败**：前端不支持 `correction` 事件，用户看到两段矛盾的话。**撤回率失控**：撤回率 4% 说明上游质量崩了，但没人看这个指标 | 37 |

**⑳㉒ 的耦合点（很多人做错的地方）**：草稿流和更正事件**必须是同一套事件协议里的不同类型**，不能是两套 API。否则前端的渲染状态机会变成意大利面：

```go
// 一套事件协议，三种语义
type StreamEvent struct {
    Type     string  // delta | commit | correction | error
    Seq      int64   // 单调递增，前端据此保证顺序
    MsgID    string  // 同一条消息的所有事件共享
    Text     string
    // 仅 correction 使用
    ReplaceFrom int   // 从第几个字符开始替换；-1 表示整段替换
    Reason      string // "audit" | "fact_fix" | "policy"
}
```

## 50.8 协作类（3 个）

| # | 模式 | 意图 | 何时用 | **何时别用** | **失败模式** | 章 |
| --- | --- | --- | --- | --- | --- | --- |
| ㉓ | **Handoff** | 把会话连同状态、上下文、预算一起交给另一个 Agent | 专业分工（售前 → 售后 → 技术支持） | 只是换个人格（用角色卡切换，不用 Handoff） | **状态切片丢失**：交接后新 Agent 不知道用户已经说过订单号。**乒乓**：两个 Agent 互相转交，用户被踢来踢去 | 33 |
| ㉔ | **Supervisor** | 一个监督者分配任务、收集结果、控制预算与终止 | 子任务 ≥ 3，且需要统一裁决 | 子任务串行依赖强；只有一个子 Agent | **预算烧穿**（§50.6 ⑱）。**死循环**：supervisor 反复要求「再试一次」。**裁决失效**：子 Agent 结论矛盾，supervisor 编一个 | 33 |
| ㉕ | **Blackboard** | 共享状态板，多个 Agent 读写同一份结构化状态 | 需要多方协作且无固定调用顺序（多轮辩论、协同编辑） | 有明确 DAG；写冲突频繁 | **写冲突覆盖**：两个 Agent 同时改同一字段，后者覆盖前者。**状态污染**：一个 Agent 写入错误结论，后续全部基于它推理。**不可审计**：不知道是谁写的 | 33 |

**㉔ 的预算必须显式回收**（这是 §50.1 那个「烧穿」事故的直接修复）：

```go
// collab/budget.go —— 层级预算令牌：父分给子，子未用完的必须还给父
type Budget struct {
    Total, Used int64      // micro-USD
    mu          sync.Mutex
    children    []*Budget
}

// Fork 给子 Agent 分配预算（不是「复制」，是「从父的剩余里切出去」）
func (b *Budget) Fork(share int64) (*Budget, error) {
    b.mu.Lock()
    defer b.mu.Unlock()
    left := b.Total - b.Used
    if share > left {
        return nil, fmt.Errorf("budget exhausted: want %d, left %d", share, left)
    }
    // 预扣：立刻从父的可用额里扣掉，防止 4 个子 Agent 各自 fork 时都看到同一个 left
    b.Used += share
    child := &Budget{Total: share}
    b.children = append(b.children, child)
    return child, nil
}

// Reclaim 子 Agent 结束后，把没用完的还给父（supervisor 必须调这个）
func (b *Budget) Reclaim(child *Budget) {
    child.mu.Lock()
    rest := child.Total - child.Used
    child.mu.Unlock()

    b.mu.Lock()
    b.Used -= rest              // 还回去
    b.mu.Unlock()
}
```

> 🩸 不做 `Fork` 时的预扣、不做 `Reclaim`，你就会得到「4 × $0.3 = $1.2 花掉一个 $0.5 的会话」——而且**没有任何一个子 Agent 觉得自己超支了**。

## 50.9 三个横切模式：Loop Guard 的实现

编排表里的 ⑥ 值得单独给代码，因为它是唯一「不用就是错」的模式：

```go
// runtime/loopguard.go
type Guard struct {
    MaxSteps    int
    MaxCost     int64         // micro-USD
    MaxWallClock time.Duration
    Repetition  int           // 同一状态连续出现几次就判死循环
}

type State struct {
    Step     int
    Cost     int64
    Started  time.Time
    LastSig  string
    SameCount int
}

// Check 在每个 step 之前调用；返回 error 即终止 Run（并给出可解释的原因）
func (g *Guard) Check(s *State) error {
    if s.Step >= g.MaxSteps {
        return ErrStepLimit        // → 降级到兜底话术，而不是 500
    }
    if s.Cost >= g.MaxCost {
        return ErrBudgetExceeded
    }
    if time.Since(s.Started) > g.MaxWallClock {
        return ErrWallClock
    }
    // 重复状态检测：把 (当前工具名, 参数 hash, 上一步输出 hash) 当签名
    // 连续 3 次相同 = 模型在两个工具间来回跳（典型的失控循环）
    if s.SameCount >= g.Repetition {
        return ErrLoopDetected
    }
    return nil
}
```

**三件必须配套的事**（否则 Loop Guard 会变成「静默截断」这个新事故）：

1. **终止要给用户可读的原因**，不是 `internal error`。
2. **终止必须记指标**（`run_terminated_total{reason}`）并进告警——`loop_detected` 突然涨 10 倍，说明某次提示词改动让模型开始打转。
3. **被判死的 Run 要进异常样本池**（第 41 章），这是最有价值的评测素材。

## 50.10 Java / 分布式经验对照：这 25 个里，哪些是你已经会的

| 模式 | 你熟悉的对应物 | 迁移难度 | 会咬人的差异 |
| --- | --- | --- | --- |
| ⑦ Event Sourcing | Kafka + 事件表、Temporal 事件历史 | 🟢 低 | 重放要锁「模型版本」，否则重放不确定 |
| ⑧ Outbox | Debezium / 本地消息表 | 🟢 低 | 幂等键要含 `run_id + step`，不只是业务 ID |
| ⑨ CQRS | 读写分离 / ES 物化视图 | 🟢 低 | 投影里要含成本与版本字段，否则看板做不了 |
| ⑩ Checkpoint | Temporal / 状态机持久化 | 🟡 中 | 要额外记「哪些副作用已执行」，防重放副作用 |
| ⑪ Bulkhead | Hystrix 线程池隔离 / K8s 资源配额 | 🟢 低 | 多一个维度：**按 token 预算切池** |
| ⑫ Breaker | Sentinel / Resilience4j | 🟡 中 | **粒度必须按 provider×模型×区域**，不能按调用 |
| ⑬ Backpressure | RxJava / Reactor `request(n)` | 🟡 中 | 流式 SSE 没有天然背压，要自己做窗口与丢弃策略 |
| ⑭ Load Shedding | Sentinel 的匀速排队 + 快速失败 | 🟢 低 | 要按「付费/免费」分级牺牲，不是随机丢 |
| ⑮ Saga | Seata / 自研补偿 | 🟡 中 | 补偿动作可能触发**新的模型调用**（要算钱） |
| ⑯ 预扣结算 | 支付预授权 + 清算 + 对账 | 🟡 中 | 流式下「用量未知」，要先估后结（第 27 章） |
| ⑰ 语义缓存 | Redis + 布隆过滤器 | 🔴 高 | 传统缓存**没有误命中**；这里误命中 = 答错 + 泄露 |
| ⑱ Budget Token | 分布式配额的子配额 | 🟡 中 | 传统配额是「拒绝」，这里是「父必须能回收」 |
| ⑲ Prefix Layering | HTTP 缓存 / CDN 分层 | 🟡 中 | 缓存键是**前缀 token 序列**，改一个字全失效 |
| ①③④⑤ 编排类 | 无直接对应（像 BPMN 但非确定） | 🔴 高 | 节点返回是概率的，分支要能兜「模型没按格式输出」 |
| ⑳㉒ 管道类 | 无（这是 Agent 特有的） | 🔴 高 | 「已 flush 到屏幕」的内容要能替换，是分布式一致性问题 |

> 💡 一句话总结：**你会的 12 个能直接迁移，5 个要改粒度，8 个是新的。** 新的那 8 个恰好就是本书第七、八部分——所以「Agent 平台 88% 是新东西」这个判断，在模式层面也成立。

## 50.11 开源坐标

| 模式 | 开源实现 | 能直接用吗 | 缺什么 |
| --- | --- | --- | --- |
| ⑥ Loop Guard | LangGraph 的 `recursion_limit`、OpenAI Agents SDK 的 `max_turns` | 🟢 部分 | 只管步数，不管**成本**与**重复状态**；终止原因不可读 |
| ⑦ Event Sourcing / ⑩ Checkpoint | **Temporal**、LangGraph Checkpointer、Restate | 🟢 部分 | Temporal 假设「活动是确定性的」，模型调用不是；要包一层「记录—重放」 |
| ⑧ Outbox | Debezium、`pgoutbox` 类库 | 🟢 可以 | 与 Agent 事件 schema 的版本演进要自己管 |
| ⑪⑫⑭ 稳定性 | Resilience4j（Java）、`sony/gobreaker`、`golang.org/x/time/rate`、Sentinel | 🟢 可以 | 都是「单进程」原语；分布式语义（全局配额、跨实例熔断）要自己接 Redis |
| ⑯ 预扣结算 | LiteLLM 的 `max_budget` / virtual key | 🟡 部分 | 没有复式账本、没有对账、没有退款 |
| ⑰ 语义缓存 | GPTCache、Redis Vector、`langchain` 的语义缓存 | 🔴 慎用 | 大多没有「实体对齐护栏」与「租户命名空间」，**默认配置会出事** |
| ⑱ Budget Token | LangGraph 无；需自研 | 🔴 无 | 层级预算 + 回收机制，开源里基本没有 |
| ①②③④⑤㉓㉔㉕ 编排协作 | **LangGraph**（graph + supervisor 示例）、AutoGen、CrewAI | 🟢 可以学结构 | 都不带预算、终止保证、跨租户隔离；照抄会缺治理 |
| ⑳㉒ 管道 | 无 | 🔴 无 | 双通道草稿流 + 撤回事件协议，是平台自研的核心资产 |

> 🎯 **判断**：25 个模式里，**开源能给你 9 个的半成品**，剩下 16 个必须自己写。而这 16 个里，有 6 个（⑥⑯⑰⑱⑳㉒）是「不做就会出事」的——它们构成了本书第 5、7、8 部分的骨架。

## 50.12 事故清单

- [ ] **事故 A：给所有 Agent 加 Reflection，成本 +62%，质量 +1.2pt。** → 根因：模式与失败类型不匹配（事实错误用推理修正治）。→ 兜底：上任何模式前，先做「失败归因」——把 badcase 聚类，看错误来自知识、工具、推理还是格式。**只有推理类错误值得 Reflection。**
- [ ] **事故 B：断路器按调用建，一次抖动打成 27 分钟故障。** → 根因：粒度错误 + 半开无退避。→ 兜底：按 `provider × model × region` 建；半开加随机抖动（避免同步半开风暴）。
- [ ] **事故 C：语义缓存误命中，答了别的租户的政策。** → 根因：缓存键漏 `tenant_id` + 阈值 0.85。→ 兜底：键含租户/场景/模型档/提示词版本/索引版本；阈值 ≥0.94 + 实体对齐；上线前跑对照集。
- [ ] **事故 D：Supervisor 的 4 个子 Agent 把 $0.5 的会话烧到 $1.2。** → 根因：预算「复制」而非「切分」，且无回收。→ 兜底：`Fork` 时预扣、`Reclaim` 时归还、父级硬杀。
- [ ] **事故 E：从 Checkpoint 恢复，邮件又发了一遍。** → 根因：快照只存状态不存「副作用已执行」标记。→ 兜底：每个副作用记 `(step, tool, idem_key, status)`，恢复时跳过已完成。
- [ ] **事故 F：Load Shedding 把付费客户丢了。** → 根因：丢弃策略是随机的，没分级。→ 兜底：按「租户等级 × 请求类型」排序丢弃；付费层只降级不拒绝。
- [ ] **事故 G：撤回事件前端不认，用户看到两段矛盾的话。** → 根因：草稿流与更正流是两套协议。→ 兜底：统一 `StreamEvent`（`delta/commit/correction`）+ `MsgID` + `Seq`，前端状态机只认一套。

| 症状（你观察到的） | 该用的模式 | 别用错 |
| --- | --- | --- |

| --- | --- |
| 数量 | 25 个模式，6 类；**没有一个场景该同时用超过 4 个** |
| 排序 | 先上 ⑥⑯⑰⑲㉑（不损失质量的），再上 ①②（要评测兜底的），最后才上 ③④㉔ |

## 50.14 自检题

1. **一个团队说：「我们上了 Orchestrator-Worker + Reflection + Supervisor，架构很先进。」你会问哪三个问题？**
   > 要点：① **预算谁管？**（子 Agent 的预算是否从父切分并可回收，否则会话预算形同虚设）；② **终止怎么保证？**（supervisor 反复「再试一次」时，靠什么停下——步数？预算？重复状态？）；③ **失败归因做了吗？**（如果 80% 的 badcase 是知识库过时，这三个模式一个都治不了，你只是把成本乘了 3）。三个问题答不上来两个，这个架构就是在给未来写事故报告。

2. **为什么 Circuit Breaker 的粒度必须按「provider × 模型 × 区域」，而不是按「每次调用」？**
   > 要点：熔断的本质是「用一个共享的失败信号，替代 N 次独立探测」，目的是**保护下游并快速失败**。按调用建，每个调用都是独立探测，等于没有共享信号——300 个调用各自熔断、各自半开，制造的是**振荡**而不是保护。而且模型故障有强相关性（同一区域同时坏），按 provider×模型 建能把相关性利用起来；同时避免「一个小模型慢」把「大模型正常」也熔断（隔离）。

3. **语义缓存的阈值你打算怎么定？给一个可执行的实验设计。**
   > 要点：① 构造对照集：800 条 = 「同义问法对」（应命中）+「近义但答案不同对」（不应命中，如「退款 3 天」vs「退款 30 天」、「7 天无理由」vs「7 天质保」）；② 扫阈值 0.85~0.98，画两条曲线（命中率 vs 误命中率）；③ 选「误命中率 ≤ 0.5%」的最低阈值，再加**实体对齐护栏**（数字/订单号/日期/金额必须逐字匹配）把误命中压到 0.1% 以下；④ 上线后按场景监控 `cache_rejected_entity_mismatch`——这个指标涨，说明有人在缓存个性化答案。
