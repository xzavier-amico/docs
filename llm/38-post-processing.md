# 38. 后处理层：把「差不多」变成「能交付」

> **状态**：`已完成（初稿）` ｜ **所属**：第七部分 · 输入输出管道 ｜ **编号**：38 / 52
> **本章定位**：模型输出的是「草稿」，产品要交付的是「成品」。中间这层就是后处理——**它是幻觉的主要拦截点，也是质量与成本之间最后一处可以调旋钮的地方**。
> **读法**：先看 §38.2 的「pre-commit / post-commit」分界线，它决定了哪些事还能做、哪些事只能交给第 37 章；然后 §38.4 的处理器矩阵可以直接当设计清单用。

## 38.1 引子：一个「完全正确」的回答被打回

Aurora 的数据分析 Agent 给运营同学输出了一段分析：

```
本月 GMV 环比增长 12.3%，主要来自华东区的促销拉动。退款率从 2.1% 
上升到 2.4%，但仍在健康区间内。建议下月继续加大投放。

```json
{ "gmv_mom": 0.123, "refund_rate": 0.024, "region_top": "east" }
```
```

三分钟后，运营把这段贴进了周报。然后财务来问：数据不对，10 月的 GMV 口径是含税的，11 月是不含税的，你算的 12.3% 里有一半是口径差。而且退款率 2.4% 已经超过了公司的 2.0% 红线。

**模型没有幻觉，它算得很准——它只是用了两个不该混的口径，并且不知道有一条阈值规则。**

这就是后处理层的战场：**模型负责「生成得像」，后处理负责「交付得了」**。它要管的不是「模型会不会说话」，而是这五件事：

| 后处理职责 | 不做会怎样（Aurora 实测） |
| --- | --- |
| **结构化校验** | 下游系统按 JSON 解析失败率 6.8%，每天 3.2 万次工具调用报错 |
| **幻觉过滤与引用核对** | 事实性错误片段 0.9%，其中 12% 带「承诺」性质 |
| **脱敏与格式化** | 输出里带用户手机号/身份证，一次泄露 = 一起合规事件 |
| **多候选融合打分** | 单候选的「最差那 20%」直接进用户视野，投诉集中在尾部 |
| **拒答与合规话术** | 被诱导扮演医生给出用药建议；品牌语气被模型自由发挥 |

## 38.2 断崖：后处理的预算不是免费的

先讲一个必须接受的现实：**后处理是「额外的模型调用」，它会把成本结构改写一遍。**

```
一次客服 Run 的成本拆解（Aurora，模型单价 $0.6/M in, $2.4/M out）

生成：25k 输入 + 1.2k 输出        ≈ $0.0180
后处理全套：
  ├─ schema 校验（纯代码）         ≈ $0.0000   2ms
  ├─ 引用核对（3 条 claim 批判）    ≈ $0.0045   90ms
  ├─ 脱敏（正则 + NER 小模型）      ≈ $0.0003   18ms
  ├─ 品牌语气打分（小模型）         ≈ $0.0012   45ms
  └─ 合规话术重写（命中时 8%）      ≈ $0.0010   60ms
                                  ──────────
后处理合计                        ≈ $0.0070   ~215ms
                                   = 生成成本的 39%

多候选（n=3）：生成成本 × 3 = $0.0540
```

> 🩸 **结论：后处理不是「加一点校验」，它是把单次成本抬高 40%，多候选方案能把成本抬 4 倍。** 所以后处理必须**分级**——这跟第 37 章的延迟分级是同一个道理：**不是所有流量都值得全套体检。**

### 五种「后处理缺失」的死法

| # | 场景 | 症状 | 量化 | 该由谁兜 |
| --- | --- | --- | --- | --- |
| 1 | 结构化输出崩了 | 下游 `json.Unmarshal` 报错，工具参数丢失 | 失败率 6.8%，日均 3.2 万次 | schema 校验 + 修复 + 约束解码 |
| 2 | 编了个数字 | 「退款 3 个工作日到账」（实际 5~7） | 幻觉率 0.9%，承诺型占 12% | claim 级引用核对 |
| 3 | 泄了 PII | 输出里回显了用户的身份证号 | 每 10 万片段 2~4 次 | 输出侧脱敏（双轨，第 30 章） |
| 4 | 语气崩了 | 对投诉用户用了「亲~」；对法务函用了 emoji | 品牌投诉占比 17% | 品牌话术库 + 语气打分 |
| 5 | 该拒不拒 | 被问「我该吃多少毫克」还认真回答了 | 每月 20~60 次 | 拒答策略 + 前置意图分类 |

### 关键分界线：pre-commit 与 post-commit

**这是本章与第 37 章的分工线，也是很多团队设计崩掉的地方：**

```
                        ┌──────────────────────────────┐
  LLM 输出 ────────────▶│  pre-commit 后处理            │
                        │  ✅ 能改、能重写、能丢弃       │
                        │  预算：200ms（非流式）        │
                        │        40ms/片段（流式）      │
                        └───────────┬──────────────────┘
                                    │ commit（已 flush 到屏幕）
                                    ▼
                        ┌──────────────────────────────┐
                        │  post-commit 后处理           │
                        │  ⚠️ 只能标注 / 追加更正        │
                        │  → 全部交给第 37 章的 correction│
                        └──────────────────────────────┘
```

| 能力 | pre-commit 能做 | post-commit 只能 |
| --- | --- | --- |
| 改错别字 | ✅ 直接改 | ❌ 发 correction |
| 补一个缺失的 JSON 字段 | ✅ 重生成 / 补全 | ⚠️ 追加补丁片段 |
| 删掉一段幻觉 | ✅ 静默剔除 | ⚠️ 划删除线 + 更正块 |
| 脱敏 | ✅ 替换为 `***` | ⚠️ 更正 + 通知（已泄露） |
| 拒答 | ✅ 整段换成拒答话术 | ❌ 太晚了 |

> 💡 **所以后处理的第一条设计原则是：把越多的检查前移到 pre-commit，你的质量上限就越高。** 而 pre-commit 的时间预算有多长，取决于第 37 章 §37.4.2 的 `hold_ms`——敏感场景 800ms，你能做的事比 0ms 多得多。

### 三种时序：后处理放在流式的哪个位置

```
(A) 先发后校（draft 直发）—— 92% 流量
    LLM ────delta────▶ 用户        后处理异步跑，出问题走 R2 更正
    延迟：0ms   质量闸：事后
    适用：闲聊、摘要、解释类

(B) 边发边校（分段）—— 6% 流量
    LLM ──seg1──▶[校验 40ms]──▶ 用户
          ──seg2──▶[校验 40ms]──▶ 用户
    延迟：+40ms/段  质量闸：片段级
    适用：含少量事实陈述的客服回答

(C) 先校后发（hold 全量）—— 2% 流量
    LLM ────全文───▶[全量校验 200~800ms]──▶ 用户
    延迟：+800ms   质量闸：最强
    适用：报价、合同条款、医疗/法律建议、结构化输出
```

## 38.4 关键设计

### 38.4.1 结构化校验与修复：五级阶梯

结构化输出的失败不是二元的，是一个阶梯。**别一失败就重生成**，那是最贵的做法：

| 级别 | 手段 | 延迟 | 成功率 | 成本 | 何时用 |
| --- | --- | --- | --- | --- | --- |
| L0 | 约束解码（JSON Schema → FSM/grammar） | 0ms | 消除 90% 语法错 | 0 | **默认开启**（vLLM/SGLang 支持 guided decoding，Outlines 同思路） |
| L1 | 纯代码修复（补尾括号、单引号转双、去尾逗号、`NaN`→`null`） | <2ms | 修掉 60% 残留 | 0 | L0 失败后必跑 |
| L2 | 类型强制与默认值填充（缺失字段填 default，超长截断） | <2ms | 修掉 25% 残留 | 0 | 字段可缺省时 |
| L3 | 定向修复（只把坏的那段发给模型，附错误信息） | 300ms | 修掉 80% 剩余 | 0.15× | L1/L2 失败 |
| L4 | 整段重生成（换温度、追加「必须严格输出 JSON」） | 1× | 修掉 90% 剩余 | 1.0× | L3 失败或连续两次坏 |
| L5 | 兜底降级（返回模板对象 + 明确告知「结构化解析失败」） | 0ms | 100% | 0 | L4 仍失败（必须终止，否则死循环） |

```
实测漏斗（Aurora，n=100 万次结构化输出请求）：
  原始语法错        6.8 万  (6.8%)
  L0 约束解码后     0.68 万 (0.68%)
  L1 代码修复后     0.27 万
  L2 类型填充后     0.20 万
  L3 定向修复后     0.04 万
  L4 重生成后       0.004 万  ← 4 次/万次，可以忽略
  L5 兜底           0.0001 万
```

> ⚠️ **L5 必须有 `max_attempts`**。我们见过一个团队写了「失败就重试直到成功」，配合模型偶发的格式漂移，单次请求打了 17 次模型，烧掉 ¥3.2——这是一次真实事故，不是虚构。

### 38.4.2 幻觉过滤与引用核对

幻觉不能靠「感觉」，要靠**逐 claim 的蕴含判定**。核心工作流：

```
1. claim 抽取
   把回答切成原子主张（一句一 claim，含数字/日期/专有名词的优先）
   800 字回答 → 约 10~14 个 claim

2. claim 分级（关键，决定成本）
   ├─ 事实型（含数字、日期、条款、专有名词）  → 必判（约占 25%）
   ├─ 承诺型（"可以/将会/保证/3 个工作日内"） → 必判 + 高风险权重
   └─ 观点型/寒暄型                           → 跳过

3. 蕴含判定（grounding）
   输入：claim + 检索到的 context 片段（带 doc_id@version）
   输出：{entailed | contradicted | not_found, evidence_span}

4. 处置
   contradicted → 剔除该句 / 或整段走 L4 重生成
   not_found    → 降级表述（"根据公开资料"）+ 打 risk 标记
   entailed     → 放过，并把 evidence 写进 citation
```

**成本优化**（这是工程重点）：3 条 claim 打包成一次调用，而不是 3 次调用。

```
朴素做法：3 次 × 350ms = 1050ms, 3 × 500 token = 1500 token
打包做法：1 次 × 380ms = 380ms,  1 × 900 token = 900 token
→ 延迟降 64%，成本降 40%
```

判定用小模型就够（这是分类任务，不是生成任务）：Aurora 用 8B 级模型做蕴含判定，与 70B 判定的 Kappa 一致率 0.81，成本是 1/9。

**几个必须固化的规则**：

| 规则 | 为什么 |
| --- | --- |
| `evidence_span` 必须能定位到 context 的具体字符区间 | 否则「有证据」是模型自己说的，等于没核 |
| context 里没有的**数字**一律降级 | 数字是幻觉最高发区，且后果最重 |
| 同一 claim 两次判定不一致 → 送人工 | 判定器自身的不确定性要暴露出来 |
| 引用必须做 **doc_id@version** 级校验 | 只校验「文档存在」不够，过期版本一样是错的（这是 §37.1 引子的根因） |

### 38.4.3 处理器矩阵：职责、延迟、成本、失败模式

这张表应该直接变成你代码里的 processor 注册表：

| Processor | 输入 | 输出 | 延迟 P99 | 成本/次 | 失败模式（要兜的） |
| --- | --- | --- | --- | --- | --- |
| `schema` | 原始文本 | 结构化对象 | 2ms | 0 | 半截 JSON、类型错、缺字段 |
| `repair` | 坏 JSON + 错误 | 修好的 JSON | 300ms | 0.15× | 修出新错误（必须再校验一遍） |
| `grounding` | claims + ctx | 保留/剔除 claims | 400ms | $0.0045 | 判定器自己幻觉 → 误杀正确内容 |
| `pii_out` | 文本 | 脱敏文本 | 20ms | $0.0003 | 过度脱敏（把订单号也当手机号） |
| `safety_out` | 文本 | verdict + 改写 | 150ms | $0.0018 | 漏放 / 过度拦截 |
| `brand_tone` | 文本 + 角色卡 | 分数 + 建议 | 45ms | $0.0012 | 把专业术语当"语气不好" |
| `length` | 文本 | 截断/扩写 | 0ms | 0 | 截断在句子中间 |
| `refusal` | 意图 + 文本 | 拒答 or 原文 | 30ms | 0 | 该拒的没拒 / 不该拒的拒了 |
| `fuse` | n 个候选 | 最优候选 | 3ms | 0 | 打分函数偏科 |

### 38.4.4 多候选融合打分

当质量不够时，「生成 3 个选 1 个」是最直接的提升手段。但**选错比不选更糟**，所以打分函数要显式、可解释、可调：

```
score(c) = 0.30 · grounded(c)        # 引用核对通过率（必须最高权重）
         + 0.20 · schema_ok(c)       # 结构化校验通过
         + 0.15 · intent_fit(c)      # 是否回答了用户真正问的
         + 0.15 · tone(c)            # 角色一致性 / 品牌语气
         + 0.10 · completeness(c)    # 覆盖了多少子问题
         - 0.25 · risk(c)            # 安全风险（做惩罚项，不给正分）
         - 0.05 · cost_norm(c)       # 成本归一化（避免总选最长的）

阈值：max(score) < 0.55 → 不交付，走 L4 重生成或拒答
      max(score) - second(score) < 0.03 → 两个候选打平，取更短的那个（经验规则：
                                           打平时短答案的用户满意度更高）
```

> 💡 为什么 `grounded` 给 0.30？因为另外四项都可以「看起来不错」，只有引用核对是**外部事实约束**。Aurora 调参结论：`grounded` 权重从 0.2 提到 0.3，能让「用户点踩率」降 1.8pp，而 `tone` 权重提高只降 0.4pp。

### 38.4.5 拒答策略：拒答也要设计，不能靠模型自觉

三类拒答，话术与触发完全不同：

| 类型 | 触发 | 例子 | 话术原则 | 是否计费 |
| --- | --- | --- | --- | --- |
| **能力外** | 意图分类器判定超出 Agent 能力域 | 「帮我写个爬虫绕过验证码」 | 说明边界 + 给替代路径 | 不计费 |
| **权限外** | 数据权限校验失败（订单不属于该用户） | 「查一下订单 A123」 | **不说「无权限」**，说「没找到」 | 计费 |
| **风险外** | 命中合规红线（医疗/法律/金融建议） | 「我这个剂量该吃多少」 | 明确不给建议 + 引导专业渠道 | 不计费 |

```yaml
# 拒答话术库（品牌合规话术，随策略中心热更，见第 43 章）
refusal_profiles:
  out_of_scope:
    template: |
      这件事我做不到——{capability}不在我的能力范围内。
      如果你的目标是 {inferred_goal}，可以试试：{alternatives}
    max_len: 120
    never_say: ["我不能", "无法回答"]        # 硬禁止的措辞
    must_say: ["可以试试", "建议联系"]
  no_permission:
    template: "我没找到相关的{object}。如果确认信息无误，可以联系{ticket_channel}。"
    rationale: "不暴露资源存在性，避免枚举攻击（第 32 章）"
  regulated:
    template: |
      这属于{domain}问题，我不能给出具体建议。
      请咨询{professional}；如果你需要，我可以帮你整理要问的问题。
    escalate: true                            # 同时创建人工工单
```

> ⚠️ 三个坑：① 拒答话术里**别暴露系统内部信息**（「我的知识库没有这篇文档」= 泄露架构）；② 拒答要**带替代路径**，纯拒绝的满意度比带路径低 30%+；③ 拒答**必须有兜底**——分类器误判时，用户要能一键「转人工」，否则就是死路。

### 38.4.6 品牌语气：约束在前，校正在后

品牌一致性最好在前置（角色卡 + few-shot，第 17 章）解决，后处理只做**兜底校正**。分工：

| 层 | 手段 | 效果 | 成本 |
| --- | --- | --- | --- |
| 前置 | 角色卡 + 语气示例 + 禁止词表 | 解决 85% | 0（在 prompt 里） |
| 后置 | 禁用词表命中 → 定向重写；语气打分 → 打标 | 修 10% | 低 |
| 事后 | 抽检发现系统性偏差 → 改角色卡 | 修剩余 | 人力 |

**禁用词表是最高 ROI 的一个后处理**：纯正则，0 延迟，0 成本，能挡掉「亲~」「么么哒」「100% 保证」「绝对安全」这类必然惹事的表达。

```go
// 后处理链的骨架：顺序固定、可短路、预算硬约束
type Processor interface {
    Name() string
    // 返回 Drop=true 表示这个候选不可交付
    Apply(ctx context.Context, c *Candidate) (Drop bool, err error)
}

type Chain struct {
    procs  []Processor
    budget time.Duration   // 硬预算，超了就走降级
}

func (ch *Chain) Run(ctx context.Context, c *Candidate) (*Candidate, error) {
    ctx, cancel := context.WithTimeout(ctx, ch.budget)
    defer cancel()

    for _, p := range ch.procs {
        drop, err := p.Apply(ctx, c)
        if err != nil {
            // 单个 processor 失败不阻断主链路：记录 + 打标 + 继续
            // 唯一例外是 safety 与 pii —— 它们失败必须 fail-closed
            if p.Name() == "safety_out" || p.Name() == "pii_out" {
                return nil, fmt.Errorf("%s fail-closed: %w", p.Name(), err)
            }
            c.Flags = append(c.Flags, "degraded:"+p.Name())
            continue
        }
        if drop {
            c.DroppedBy = p.Name()
            return c, nil
        }
        if ctx.Err() != nil {
            c.Flags = append(c.Flags, "budget_exceeded")
            return c, ctx.Err()   // 交给上层：降级交付 or 走 R2 更正
        }
    }
    return c, nil
}
```

> 🩸 **`safety_out` 和 `pii_out` 必须 fail-closed（失败即拦截），其他 processor 一律 fail-open（失败即跳过）。** 这个区别写错一次，就是一次内容事故。

### 38.4.7 后处理的可观测：拦截率与误杀率

后处理自己也要被观测，否则你不知道它是「在保护质量」还是「在无差别伤害体验」（第 39 章展开 trace）：

```sql
-- 后处理拦截效果：每个 processor 的拦截率 / 人工复核误杀率
SELECT
    processor,
    count()                                                        AS invocations,
    countIf(dropped)                                               AS dropped,
    round(dropped / invocations, 4)                                AS drop_rate,
    countIf(dropped AND review_verdict = 'should_pass')            AS false_kill,
    round(false_kill / nullIf(dropped, 0), 4)                      AS false_kill_rate,
    quantile(0.99)(latency_ms)                                     AS p99_ms,
    sum(cost_usd) / count()                                        AS cost_per_call
FROM postproc_events
WHERE ts >= now() - INTERVAL 1 DAY
GROUP BY processor
ORDER BY false_kill_rate DESC;
```

经验红线：**任何 processor 的 `false_kill_rate > 15%` 就必须重新校准**，否则你在用「过度严格」换「看起来安全」，实际是在逼用户放弃产品。

## 38.5 Java / 分布式经验对照

| 你熟悉的东西 | 后处理层的对应物 | 会咬人的差异 |
| --- | --- | --- |
| Servlet Filter / Spring Interceptor 链 | Processor Chain | Filter 是确定性的、可无限重试；后处理里有模型调用，**每次结果可能不同** |
| Bean Validation（JSR-303） | Schema 校验 | 那个是「拒绝非法请求」，这个是「修好它再放行」——修复逻辑比校验逻辑复杂 10 倍 |
| 网关响应改写（PostFilter） | 脱敏 / 话术替换 | 网关改写是无状态的；这里要带角色卡、租户、场景上下文 |
| 幂等重试 | L3/L4 修复 | 重试会改成本；必须有 `max_attempts` 与预算 |
| DTO 转换 / Assembler | 结构化输出映射 | 源不是可靠对象，是一个可能半截的 JSON 字符串 |
| AOP 切面 | Processor | 切面失败一般不影响主流程；`safety`/`pii` 失败必须阻断 |
| 流式 API 的 `Flush` | pre/post-commit 分界 | 一旦 flush 就没有「后处理」了，只剩「更正」（第 37 章） |

最大的思维切换：**传统后端的过滤器链是「校验 → 拒绝」，Agent 的后处理链是「校验 → 修复 → 兜底 → 更正」。** 你有四次机会，别在第一次失败时就放弃。

## 38.6 开源坐标

| 项目 | 能给你什么 | 缺什么 |
| --- | --- | --- |
| **Guardrails AI** | `Guard` + validator 体系、RAIL 规格、失败后 `reask`（重新提问）机制 | 没有流式语义；validator 是规则为主，claim 级 grounding 要自己写 |
| **NeMo Guardrails** | 对话流（Colang）层面的护栏，输入/输出/对话三处可插 | 偏「对话策略」，不擅长结构化修复 |
| **Outlines** | 约束解码：JSON Schema / 正则 → FSM，从生成源头消除语法错 | 只管语法不管语义；对已生成文本无能为力 |
| **JSON Schema / Pydantic** | 校验与类型模型，事实标准 | 不会「修复」，需要 `repair` 层 |
| **LiteLLM** | 统一的多 provider 调用 + fallback（可用作 L4 重生成） | 不含后处理逻辑 |
| **Ragas** | `faithfulness` 等指标，可作为 grounding 的离线评估 | 是评估框架，不是在线拦截器（延迟不适合在线） |
| **Presidio** | PII 识别（正则 + NER） | 中文/行业实体需自定义 recognizer |

> 🎯 结论：**结构化校验有成熟方案可抄（约束解码 + 阶梯修复），幻觉过滤基本要自研。** 因为 grounding 的判定标准跟你的业务强相关——「什么算有证据」这件事，开源框架没法替你定义。

## 38.7 事故清单

- [ ] **事故 A：修复阶梯死循环**。现象：某个请求打了 17 次模型，单次成本 ¥3.2。
  → 根因：`repair` 失败后无条件重试，没有 `max_attempts`。
  → 兜底：L0~L5 阶梯硬编码，最多 2 次模型调用，超了走 L5 兜底。
- [ ] **事故 B：过度脱敏**。现象：订单号被当手机号打码，客服无法核对。
  → 根因：正则过宽 + 没有上下文白名单。
  → 兜底：脱敏规则带 `context_allow`（如 `order_id` 字段内不脱敏），并统计误杀率。
- [ ] **事故 C：grounding 误杀正确内容**。现象：正确回答被判 `not_found` 剔除，拒答率从 4% 涨到 19%。
  → 根因：判定器用的是小模型，对长 context 里的隐含信息不敏感。
  → 兜底：`not_found` 只降级表述不删除；`contradicted` 才删；并用人工抽检校准判定器。
- [ ] **事故 D：后处理超预算拖垮整条链**。现象：P99 从 12s 涨到 21s。
  → 根因：`grounding` 换了大模型，单次 2.4s，且串行。
  → 兜底：每个 processor 独立超时 + chain 总预算 + 并行化（`pii`/`brand` 可并发）。
- [ ] **事故 E：safety 失败被 fail-open 放过**。现象：一次审核服务超时，不当内容直接出了。
  → 根因：统一错误处理把所有 processor 都当成「跳过继续」。
  → 兜底：白名单式 fail-closed（`safety_out` / `pii_out` 失败即拦截，返回兜底话术）。
- [ ] **事故 F：拒答暴露内部信息**。现象：用户从拒答话术里推断出知识库文档名，进而社工。
  → 根因：话术模板用了 `${doc_name}`。
  → 兜底：话术模板变量白名单，禁止注入内部标识（第 32 章）。

## 38.8 一页速记

| 关键词 | 结论 |
| --- | --- |
| 定位 | 模型输出是草稿，后处理把它变成可交付成品；幻觉的主要拦截点 |
| 成本 | 全套后处理 ≈ 生成成本的 40%；多候选 n=3 → 总成本 4×，必须分级 |
| 分界线 | pre-commit 能改，post-commit 只能更正（第 37 章）——检查要尽量前移 |
| 结构化 | L0 约束解码 → L1 代码修复 → L2 类型填充 → L3 定向修复 → L4 重生成 → L5 兜底；**必须有 max_attempts** |
| 幻觉 | claim 抽取 → 分级（只判事实型/承诺型）→ 打包批判 → 只删 `contradicted`，`not_found` 只降级 |
| 引用 | 校验到 `doc_id@version`，只校验「文档存在」等于没校验 |
| 脱敏 | 输出侧必须独立做一遍，别信输入侧；规则要带上下文白名单 |
| 多候选 | 打分函数显式化，`grounded` 权重最高；打平取更短的 |
| 拒答 | 三类（能力外/权限外/风险外），话术要带替代路径，权限外说「没找到」不说「无权限」 |
| 失败语义 | `safety`/`pii` fail-closed，其余 fail-open + 打标 |
| 真话 | **后处理不是加个校验，它是把成本抬 40%、把质量抬一个档的独立子系统。** |

## 38.9 自检题

1. **你的 JSON 输出解析失败率 6.8%，团队的第一反应是「在 prompt 里再加一句『必须输出合法 JSON』」。这个方案的问题是什么？**
   > 要点：① 提示词约束是概率性的，永远有残留；② 它不解决模型"忘了"的情况；③ 更重要的是——它把成本加在了每次调用的输入 token 上。正确顺序是：先开约束解码（L0，从生成源头消除），再加代码修复阶梯（L1/L2），最后才用 prompt 加强。实测 L0 就能把 6.8% 打到 0.68%。

2. **grounding 判定为 `not_found` 时，为什么不该直接删掉这句话？**
   > 要点：因为判定器会把「隐含在 context 里但没直说」的内容误判为 `not_found`。直接删会导致拒答率暴涨（Aurora 实测 4%→19%）。正确做法：`contradicted`（明确矛盾）才删，`not_found`（找不到证据）降级表述 + 打 risk 标记 + 进人工抽检队列。这本质上是「假阴性比假阳性更贵」的场景判断。

3. **后处理链里，为什么只有 `safety_out` 和 `pii_out` 应该 fail-closed？**
   > 要点：因为它们的失败后果是「不可逆的外部伤害」（违规内容出街、PII 泄露），而其他 processor 的失败后果是「质量下降」。fail-closed 的代价是可用性（服务挂了就全拒），只有当「失败后果 > 拒服务代价」时才值得。把 `brand_tone` 也设成 fail-closed，结果就是一次小模型抖动导致全站拒答。
