## 1.1 引子：一个真实的时间账

假设你是一个 8 年经验的 Java 架构师，接到任务：「三个月内做一个企业级客服 Agent 平台」。

**第 1 周**：你花两天跑通了 LangChain/LangGraph 的官方示例——模型会调工具、会循环、会回答。你甚至接了个知识库，效果惊艳。周五你在周会上说：「核心链路已通，剩下是工程化。」

**第 3 周**：你接入了真实业务。第一天就出事：
- 有用户发一段 2 万字的产品手册，请求直接超上下文；
- 同一个问题问两遍，答案不一样，客服主管质疑「这玩意儿能用？」；
- 有人让它「把刚才的对话导出成邮件发给客户」，它真的调了发邮件工具，发给了错误的人；
- 高峰期一到，接口大面积超时，但不是模型慢——是你的服务在等模型时把线程/连接占满了；
- 老板问「今天这 3000 次对话花了多少钱」，你答不上来；
- 客户投诉「它刚才说能退款，现在又不认了」，而你想复现那次对话，发现日志里只有一行 `request completed in 12.4s`。

**第 12 周**：你发现真正的工作量分布是这样的——

```
你以为的进度条：
[LangChain 跑通 ████████████████████] 100%  ← 第 1 周
                ↑ 然后剩下的 11 周都在补下面的东西

实际的进度条：
编排逻辑         ██▌                     12%   ← 第 1 周就做完了
接入与协议       ██▏                     10%
上下文工程       ███▊                    18%
前处理闸门       █▎                       6%
稳定性           ███                      14%
成本与计费       ██▌                     12%
输出管道与审计   ██▏                     10%
可观测与评测     ██▏                     10%
安全防御合规     █▋                       8%
                                    ──────
                                     100%
```

> 🎯 **本章要建立的第一个共识**：
> **Agent 的难点不在「让它能跑」，而在「让它能一直跑、跑得起、跑错了能查、跑坏了能收」。**
> 前者是 1 周的事，后者是 6 个月的事，而且**两者用的几乎是完全不同的技术栈**。

## 1.2 断崖总览：它们分别杀死什么

先用一张表把 10 个断崖钉在墙上。**每一行都对应一个「Demo 阶段完全不存在、生产阶段必然遇到」的问题**：

| # | 断崖 | 一句话本质 | 典型症状 | 主要杀伤 | 详见 |
| --- | --- | --- | --- | --- | --- |
| 1 | **不确定性** | 同一个输入，输出不同 | 无法回归测试、客服质疑稳定性 | 质量 | 40 |
| 2 | **延迟** | 多步串行 + 长输出 = 30 秒 | 用户等不到首 token 就关页面 | 体验 | 10、36 |
| 3 | **成本非线性** | 重试、膨胀、循环让成本爆炸 | 账单超预算 10 倍 | 商业 | 24、26、47 |

| 5 | **副作用** | 工具真的改了外部世界 | 重复下单、重复发邮件 | 事故 | 8、22 |
| 6 | **黑盒** | 出了问题说不出为什么 | 无法定位、无法复盘 | 运维 | 39 |
| 7 | **多租户** | 共享资源 + 共享数据 | 噪声邻居、越权、账单错 | 商业 + 合规 | 44 |

| 10 | **人机边界** | 谁有权做决定、谁担责 | 越权操作、无法追责 | 法律 | 31、34 |

## 1.3 断崖 1：不确定性——你没法给它写单元测试

### 现象

```java
// 你在 Java 里习惯的写法
assertEquals("退款需要 3-5 个工作日", agent.answer("退款多久到账？"));
// 第一次跑：通过
// 第二次跑：失败，它答的是「通常 3 到 5 个工作日，具体看银行」
// 第三次跑：失败，它答了「3-5 工作日（不含节假日）」
```

同一个 prompt、同一个模型、temperature=0，**输出仍然可能不一样**（浮点非确定性、批处理顺序、模型侧版本灰度、上下文里时间戳变化）。

### 量化判据

- 你的测试里有 `assertEquals(modelOutput, expected)` → 你已经踩上了。
- 你的 CI 里 Agent 相关测试会「偶发失败」，团队开始习惯性点 retry → 你正在为它付利息。

### 根因

| 层次 | 为什么不确定 |
| --- | --- |
| 模型层 | 采样、浮点累加顺序、推理批处理 |
| 上下文层 | 注入的时间、检索结果顺序、记忆写入时点 |
| 系统层 | 重试导致重复调用、缓存命中/未命中走了不同分支、模型版本滚动更新 |

### 解法方向（三个动作，缺一不可）

1. **断言从「字符串相等」换成「判定式断言」**：结构化字段校验、关键实体存在性、禁止项不存在（`assertFalse` 而非 `assertEquals`）。
2. **可复现性工程**：把「模型版本 + 提示词版本 + 角色卡版本 + 工具集版本 + 检索快照」全部记进 Run 的元数据，做到「一次 Run 可以被精确重放」。
3. **统计式验证**：单次通过不算通过，跑 N=20 次看通过率（如 ≥18/20），把「概率」变成可管理的指标。

> 详见第 40 章（评估体系）、第 42 章（版本矩阵）、第 48 章（测试策略）。

## 1.4 断崖 2：延迟——从 200ms 到 30 秒，架构要换一遍

### 现象

传统 API 的 P99 目标是 200ms，Redis 慢 10ms 你就报警。而 Agent：

```
一次客服 Run 的延迟构成（Aurora 实测中位数）

意图识别            0.3s
检索（2 路 + rerank）0.8s
LLM 第 1 步（规划）  2.1s
工具调用（查订单）   0.4s
LLM 第 2 步（生成）  3.5s   ← 首 token 在这里才出现
工具调用（查物流）   0.6s
LLM 第 3 步（成文）  4.2s
后处理（校验+脱敏）  0.2s
─────────────────────────
总计               12.1s   首 token 延迟 ≈ 6.5s
```

**12 秒意味着什么**：你的网关超时是 5s、Nginx `proxy_read_timeout` 是 60s 但用户 3 秒就关了页面、移动端弱网下连接被运营商掐断、K8s 的 readiness 探针在滚动更新时把正在跑的 Run 杀掉。

### 量化判据

- 单次 Run 超过 **3 秒** → 必须上流式（否则用户以为卡死）。
- 单次 Run 超过 **30 秒** → 必须上「异步任务 + 事件推送」模型，同步 HTTP 撑不住。
- 首 token 延迟（TTFT）超过 **2 秒** → 转化率明显下降，要把「先说一句废话」做成产品能力（「让我查一下…」）。

### 根因：延迟是**加性**的，而且每一步都有长尾

```
P50:  0.3 + 0.8 + 2.1 + 0.4 + 3.5 + 0.6 + 4.2 = 11.9s
P99:  1.2 + 3.5 + 9.0 + 2.1 +12.0 + 2.8 +15.0 = 45.6s   ← 尾部叠加放大
```

10 个步骤，每步都可能偶发慢（模型排队、GC、网络重传）。**串联结构会把长尾叠成灾难**——这是分布式系统的常识，但 Agent 把它放大了 10 倍，因为每一步都很贵。

### 解法方向

1. **流式输出**：让「第一个字」尽早出现，用感知延迟换真实延迟（第 36 章）。
2. **并行化**：能并行的工具调用/检索必须并行（第 14 章、第 33 章）。
3. **延迟预算表**：给每一站分配超时预算，超预算就降级，而不是让整条链一起等（第 10 章）。
4. **异步化**：超过 30 秒的 Run 改用「提交任务 + 事件订阅」，把 HTTP 连接解放出来（第 7、12 章）。

## 1.5 断崖 3：成本非线性——账单不是线性的，是指数的

### 现象

你在 Demo 阶段算过账：一次对话 2000 token 输入 + 500 token 输出，成本几分钱。上线后：

| 场景 | token 放大倍数 | 原因 |
| --- | --- | --- |
| 多轮对话 | ×3~8 | 每轮都把历史全带上 |
| 工具循环 | ×2~5 | 每步都要重发完整上下文 |
| 检索注入 | ×2~4 | 检索片段全塞进去 |
| 重试 | ×1.5~3 | 失败重试还带着原上下文 |
| 缓存未命中 | ×1.2 | 前缀变化导致 KV cache 全失效 |
| **失控循环** | **×50+** | 模型在两个工具间来回跳，没有步数上限 |

一次「设计良好」的 Demo 是 2.5k token；一次真实的多轮+工具+检索是 25k token；一个失控 Run 能干到 500k token。**而你可能只按 Demo 的 2.5k 做过预算。**

### 量化判据

- 你说不出「一个活跃用户的日均成本」→ 你无法定价。
- 你的 `max_tokens` 和「最大步数」没有硬上限 → 迟早有一次账单事故。
- 你的缓存命中率 < 20% → 你在为重复的上下文付全价。

### 解法方向（按 ROI 排序，这是本书的核心优化顺序）

```
① 缓存（前缀缓存 + 精确/语义缓存）   ← 通常省 30~60%，改动最小
② 路由（简单问题走小模型）           ← 省 20~40%
③ 提示词瘦身（去掉没用的示例）       ← 省 10~30%
④ 上下文压缩（摘要/裁剪/引用折叠）    ← 省 10~40%
⑤ 蒸馏/微调（把常用场景固化）        ← 省 50%+，但周期长
```

> 详见第 24 章（缓存）、第 26 章（路由）、第 47 章（FinOps）、第 18 章（压缩）。

## 1.6 断崖 4：状态——一次对话不是一次请求

### 现象

Java 后端的肌肉记忆是「无状态服务 + 会话放 Redis」。Agent 把这个假设打穿了：

```
用户：帮我查下订单，然后按上次那个地址改一下收货人
```

这一句话里隐含了：**上一轮的地址**（记忆）、**当前订单**（工具）、**改收货人**（写操作，需要审批）、**跨轮次的工具调用结果引用**。

如果你把状态放在进程内存里，那么：
- 用户的第 2 条消息打到另一个 Pod → 上下文丢失；
- 滚动更新把 Pod 干掉 → 正在跑的 Run 直接消失；
- 用户刷新页面重连 → 不知道刚才输出到哪了。

### 量化判据

- 你的 Run 状态在 `sync.Map` / `ConcurrentHashMap` 里 → 单实例玩具。
- 你的多副本部署下偶发「它忘了我们刚说过什么」→ 你已经在踩了。
- 你没法回答「第 3 步时上下文里到底有什么」→ 你没有状态快照。

### 根因

Agent 的执行是**长事务**：几十秒到几十分钟，跨多次模型调用和工具调用，且**中间状态不可重算**（模型输出不可逆推）。这跟传统 Web 的短事务完全不是一个物种。

### 解法方向

1. **事件溯源（Event Sourcing）**：把 Run 的每一步落成不可变事件，状态由事件重放得出（第 6 章）。
2. **检查点（checkpoint）**：每步之后存快照，崩溃从最近快照恢复，不重放副作用（第 12 章）。
3. **状态外置**：会话、记忆、工具结果全部落库，服务本身保持无状态（第 45 章）。

## 1.7 断崖 5：副作用——工具是真的会改世界的

这是**最容易被低估、后果最严重**的一个。

### 现象

```
用户：把这次售后处理结果整理成邮件，发给客户
Agent：（调用 send_email × 3 次，因为前两次超时重试）
```

如果 `send_email` 不幂等，客户收到 3 封一样的邮件；如果它发了错误的人，那就是数据泄露。更常见的：

| 副作用 | 事故形态 |
| --- | --- |
| 写数据库 | 重试导致重复插入，订单重复 |
| 发消息/邮件 | 重复发送、发错对象 |
| 调第三方 API | 重复扣款、重复下单 |
| 执行代码 | 删库、死循环、挖矿 |
| 修改配置 | 线上故障 |

### 量化判据

- 你的工具调用**没有幂等键**（`idempotency-key` / 业务唯一键）→ 必然重复。
- 你的重试策略是「无条件重试 3 次」→ 你在放大事故。
- 你的工具**没有分级**（读 vs 写 vs 高危写）→ 迟早有一次「它自己决定发了一封邮件」。

### 解法方向

1. **工具分级**：读（可自由重试）→ 写（幂等键 + 有限重试）→ 高危写（强制审批）（第 22、34 章）。
2. **幂等设计**：以 `(run_id, step_id, tool_name, args_hash)` 作为幂等键，服务端做去重（第 8 章）。
3. **补偿与回滚**：写操作配套补偿动作（Saga），失败要能撤回（第 12 章）。

## 1.8 断崖 6：黑盒——出问题时你什么都看不见

### 现象

用户投诉：「它刚才说能给我全额退款，现在又不认了。」

你的日志：

```
2026-05-01T10:23:41Z INFO request completed duration=12.4s status=200
```

**你想知道的全部在这行日志之外**：当时 context 里有什么？检索到了哪三篇文档？模型为什么认为可以退款？是提示词没写清楚，还是知识库里有旧政策？

### 量化判据

- 你不能在 5 分钟内回答「这次 Run 每一步的输入输出、花了多少钱、用了哪个模型版本」→ 你的平台不可运维。
- 你的 trace 只有 HTTP span，没有 `llm.call` / `tool.call` span → 你只看到了壳。
- 你没法按「提示词版本」切片看成功率 → 你无法做迭代。

### 解法方向

一次 Run 的完整可观测模型（第 39 章会展开）：

```
Run (trace_id)
├── Step 1
│   ├── preprocess     规范化/审核/注入检测 → 判定结果
│   ├── retrieve       query, top-k, 命中文档 id, 分数
│   ├── llm.call       model, prompt_version, role_card_version,
│   │                  tokens_in/out, cost, ttft, latency
│   └── tool.call      name, args(hash), result_size, latency, idempotency_key
├── Step 2 …
└── output
    ├── audit          审核判定、风险分、是否撤回
    └── billing        用量明细、预扣/结算
```

## 1.9 断崖 7：多租户——共享的东西全都变成隔离问题

### 现象

单租户时一切都好；接了 100 个租户之后：

| 冲突点 | 症状 |
| --- | --- |
| 模型配额 | 大客户跑批把公共配额吃光，小客户全超时 |
| 缓存 | A 租户的检索结果被 B 租户命中（**缓存键没带租户 ID**）→ 数据泄露 |
| 向量库 | 相似度检索跨租户召回 → 越权 |
| 记忆 | 会话 ID 冲突 → 张冠李戴 |
| 账单 | 计量粒度不对 → 算不清谁花的钱 |

### 量化判据

- 你的缓存 key 里没有 `tenant_id` → **这是数据泄露，不是 bug**。
- 你的向量检索没有租户过滤条件（而是「查完再过滤」）→ 越权 + 性能双杀。
- 你说不出「哪个租户贡献了 80% 的成本」→ 你没法做配额运营。

### 解法方向

第 44 章（多租户）会给出三档隔离（共享/池化/独占）、租户 ID 贯穿全链路（trace/缓存/存储/计费）、配额与噪声邻居治理。

## 1.10 断崖 8：评测缺失——没有标尺，改什么都靠猜

### 现象

典型的一天：

- 你改了一句提示词，在线问感觉「好像好了点」；
- 产品说「能不能再礼貌些」，你加了两个形容词，结果工具调用成功率掉了 8%（你不知道）；
- 模型厂商发了新版本，你切过去，看起来更快了，但幻觉率翻倍（你也不知道）；
- 老板问「我们这个月比上个月好多少」，你答不出来。

### 量化判据

- 你没有 **≥200 条**的真实场景评测集 → 你无法做任何有意义的迭代。
- 你的发布流程里没有「评测门禁」→ 你每次上线都是赌博。
- 你不能把线上 badcase 自动变成评测样本 → 你的评测集会越来越过时。

### 解法方向

第 40 章给完整方案：离线集构建（真实采样 + 合成 + 对抗）、LLM-as-judge 与校准、人工标注一致性、回归门禁、线上采样评估；第 41 章讲怎么把线上数据自动回流成评测集。

## 1.11 断崖 9 & 10：版本爆炸与人机边界

### 断崖 9：版本矩阵爆炸

一次 Run 的实际依赖是**五维矩阵**：

```
模型版本（gpt-x-2026-01 / claude-y / qwen-z）
  × 系统提示词版本（v37）
  × 角色卡版本（v12）
  × 工具集版本（tools-v5，含 MCP server 版本）
  × 路由策略版本（route-v8）
  × 检索索引版本（index-2026-05-01）
= 组合数：几十万种「可能的线上状态」
```

**如果你不把这些版本号写进每次 Run 的元数据，那么「线上效果无法复现」是必然的**，而不是偶然的。第 42、43 章讲版本注册、灰度、双跑与回滚。

### 断崖 10：人机边界与责任

```
Agent 决定：拒绝用户退款 → 用户投诉
Agent 决定：批准退款 500 元 → 财务质问谁批的
Agent 决定：把客户资料发给「同事」 → 数据泄露
```

技术上能做的（第 34 章）：**动作分级 + 审批流 + 中断恢复 + 全程审计**。但更重要的是**产品与法务的决定**：哪些动作必须人批、审批记录保存多久、出事后如何取证。

而「取证」这件事，直接连着第 31 章：**审计日志必须 append-only、带哈希链、不可篡改**——否则你无法向监管或法院证明「当时系统到底做了什么」。

## 1.15 事故清单：这一章对应的真实事故形态

- [ ] **事故 A**：无步数上限 + 两个工具互相调用 → 单次 Run 消耗 200 万 token，账单飙升。→ 防：最大步数 + 预算刹车（第 27 章）

- [ ] **事故 D**：模型厂商静默升级 → 工具调用格式变化，成功率从 96% 掉到 71%，两天后才发现。→ 防：版本锁定 + 评测门禁（第 42 章）
- [ ] **事故 E**：滚动更新杀掉了正在流式输出的 Run → 用户看到半句话，重启后无法续传。→ 防：优雅关停 + 断点续传（第 7、46 章）

## 1.16 一页速记

| 关键词 | 必须记住的结论 |
| --- | --- |
| 工作量分布 | 编排 12%，平台工程 88%；第 1 周和第 6 个月做的完全不是一件事 |
| 不确定性 | 断言必须从「字符串相等」升级为「判定式 + 统计式」 |
| 延迟 | 串联结构放大长尾；>3s 上流式，>30s 上异步 |
| 成本 | 非线性，失控循环可放大 50 倍；优化顺序：缓存 > 路由 > 瘦身 > 压缩 > 蒸馏 |
| 状态 | 一次对话 = 长事务；事件溯源 + 检查点 + 状态外置 |
| 副作用 | 工具必须分级 + 幂等键；无条件重试是负债 |
| 黑盒 | 没有 llm.call/tool.call span 就没有平台 |
| 多租户 | 缓存 key 和检索过滤必须带租户 ID，这是泄露级问题 |
| 版本 | 五维版本矩阵必须进 Run 元数据，否则无法复现 |
| 边界 | 高危动作必须审批；审计日志必须不可篡改 |
| 一句话 | **Demo 验证的是「模型行不行」，生产验证的是「工程兜不兜得住」。** |

## 1.17 自检题

1. **你的 Agent 服务在滚动更新时，一个正在流式输出的 Run 会发生什么？**
   > 要点：默认会被 SIGTERM 杀掉，用户看到截断的输出且无法恢复。正确做法：`preStop` 摘流量 + `Shutdown(ctx)` 等待在途 Run + Run 状态外置支持重连续传。

2. **为什么「重试 3 次」在 Agent 平台里可能是灾难？**
   > 要点：① 重试携带完整上下文 → 成本 ×3；② 写工具重试 → 重复副作用；③ 重试叠加下游已经很慢的模型 → 重试风暴。正确做法：分类重试（只重试幂等读操作）+ 退避抖动 + 预算上限。

3. **你说「我们的 Agent 效果不错」，请给出三个可以量化的证据。**
   > 要点：任务成功率（评测集 N≥200 且发布前必跑）、工具调用正确率、幻觉率/投诉率；再补上单位成本与 TTFT，才算完整。
