## 51.1 引子：9 个开源组件，2.7 人年的隐性账单

一个 12 人的团队做 Agent 平台，选型会开了两周，最后定下来这套（很典型，几乎每个团队都会拼出类似的一张图）：

```
编排      LangGraph（Python）        ← 团队是 Go/Java 背景
网关      LiteLLM（Python Proxy）
长任务    Temporal（Go + Java SDK）
可观测    Langfuse（TypeScript + ClickHouse）
向量库    Qdrant（Rust）
RAG       RAGFlow（Python）
沙盒      E2B（自托管）
模型服务  vLLM（Python + CUDA）
鉴权      Keycloak（Java）
```

看起来很美：每个都是该领域最好的开源项目。**6 个月后的真实状态**：

| 组件 | 6 个月后的状态 | 发生了什么 |
| --- | --- | --- |
| LangGraph | 只用了 20% 的功能，被包了一层 Go 的 HTTP 适配器 | 团队不会 Python，只能在旁边再起一个服务；调试要跨语言看两个 trace |
| LiteLLM | 在生产改了 3 处源码（打 patch） | 需要「租户级预算 + 自定义价目表」，上游不支持 |
| Temporal | 用得很爽，但没人会调优 | 事件历史涨到 4GB，一次 worker 重启要回放 8 分钟 |
| Langfuse | 弃用，改自研 | 采样率一开就丢关键数据；成本字段口径和内部账本对不上 |
| Qdrant | 正常 | — |
| RAGFlow | 只用了它的解析器，其余全部绕开 | 多租户权限下推不支持；切分策略不可控 |
| E2B | 自托管踩了 5 个坑，最后只用于非核心场景 | 网络策略、镜像预热、配额打通都要自己写 |
| vLLM | 正常，但 GPU 利用率只有 41% | 没人做 continuous batching 的参数调优 |
| Keycloak | 正常 | 只是「能跑」，OIDC 与租户模型对不齐，多写了 3 周适配 |

团队自己算了一笔账（**这个算式你应该抄回去算一遍**）：

```
每个组件的隐性成本（中型团队经验值）：
  学习 + 摸清边界        2 人周
  集成 + 适配内部模型     3 人周
  长期运维（0.2 FTE/年）  0.2 × 48 周 = 9.6 人周/年
  升级 + 打补丁           1.5 人周/年（有过 patch 的翻倍）
  ─────────────────────────────────
  单个组件首年 ≈ 16 人周

9 个组件 × 16 人周 ≈ 144 人周 ≈ 2.8 人年
12 人的团队，一年有 576 人周 → 拼装成本吃掉 25% 的产能
```

而更贵的是**升级节奏的乘法**：9 个组件，每个每年 1~3 次破坏性变更，就是**每年 15~27 次「你必须跟着动」**。这些变更不挑时间，经常在你冲刺交付的那两周来。

> 🩸 **本章的第一条判断**：**拼装的开源成本不是 License（基本都是 0），而是「认知负担 × 升级节奏」。** 一个组件的真实成本 ≈ 16 人周/首年，所以**每引入一个组件，你都要问：它替我省下的那部分，值不值 16 人周？**

反过来说，也有团队只拼了 4 个组件，剩下全自研，同样翻车——因为他们自研了「向量数据库」和「分布式任务调度」。**判断标准不是「自研好」或「开源好」，而是「这块的差异化在哪」。**

## 51.2 分层盘点：九层，每层的成熟度与咬点

**成熟度**：🟢 生产可用（有人在 5k QPS 上跑）/ 🟡 可用但要自己补治理 / 🔴 慎用（变更快或边界不清）

| 层 | 代表项目 | 成熟度 | 建议 | 它给你什么 / **会在哪咬你** |
| --- | --- | --- | --- | --- |
| **编排** | LangGraph、**eino**（字节，Go）、OpenAI Agents SDK、DSPy | 🟡 | **用**（但要包一层） | 给你图/状态/检查点/流式回调。咬你：**语言绑定**（LangGraph 是 Python/JS，Go 团队要跨进程）；**状态模型和你的 Run/Event 不一致**，要写适配；**没有多租户、没有预算、没有终止保证** |
| **低代码** | **Dify**、Coze（开源版）、n8n、Flowise、Langflow | 🟡 | 用骨架，补治理 | 给你 DSL + 画布 + 节点库（省 3 个月）。咬你：**软多租户**、配置无版本化无门禁、代码节点跑在应用进程里、License 附加条款（详见第 49 章） |
| **网关 / 路由** | **LiteLLM**、OpenRouter（SaaS）、Higress、Envoy AI Gateway | 🟢 | **用** | 给你多 provider 抽象、重试/失败转移、virtual key、spend tracking。咬你：预算只到 key 不到租户；**价目表要自己维护**；改源码打 patch 后升级很痛 |
| **持久化执行** | **Temporal**、Restate、DBOS、Inngest | 🟢 | **用**（长任务必用） | 给你确定性重放、活动重试、signal、定时器。咬你：**「确定性」假设与模型调用冲突**（模型输出不可重放，要包一层记录）；事件历史膨胀；运维门槛高 |
| **记忆** | **Letta**（MemGPT）、Zep、Mem0 | 🟡 | 先自研简单的，再考虑 | 给你记忆抽取、分层、检索。咬你：**写入策略是黑盒**（写错了你不知道为什么）；多租户隔离弱；**记忆 = 长期数据，迁移成本极高**，选错等于锁死 |
| **RAG** | **RAGFlow**、LlamaIndex、Qdrant / Milvus / pgvector | 🟢（库）/ 🟡（平台） | 库用开源，平台自研 | 给你切分、混合检索、rerank、向量索引。咬你：**权限下推**基本都要自己加（「查完再过滤」= 越权 + 性能双杀）；切分策略不可控；增量索引与去重 |
| **可观测** | **Langfuse**、Phoenix（Arize）、OpenTelemetry GenAI semconv | 🟢 | **用**（但要定 schema） | 给你 trace/span/成本/评测/标注。咬你：**采样即丢证据**（审计场景不能采样）；成本口径与账本不一致；**别指望它当审计日志**（第 31 章要求 append-only + 哈希链） |
| **沙盒** | **E2B**、Firecracker、gVisor、wazero | 🟢（底层）/ 🟡（产品） | 底层用开源，产品层自研 | 给你 microVM/用户态内核/WASM 隔离。咬你：冷启动（Firecracker ~125ms，但镜像拉取另算）、网络出口策略、**与配额/计费打通是你的事** |
| **模型服务** | **vLLM**、SGLang、TGI、llama.cpp | 🟢 | **用**（自建推理时） | 给你 continuous batching、PagedAttention、投机解码。咬你：**吞吐调优是玄学**（GPU 利用率 40% 很常见）；多模型混部；版本升级会改 API |

**读完这张表，你应该能看出一个规律**：

> 🎯 **开源把「能力」做完了，把「治理」留给了你。**
> 每一行的「咬你」栏，内容惊人地一致：**多租户、配额、审计、计费、灰度、回滚**。这不是巧合——因为这些是**你的商业模式和你的合规责任**，没人会替你写。这也正好解释了为什么第 1 章说「编排只占 12%，88% 是治理」。

**这张图有三条边界规则，值得抄**：

1. **凡是「会改变模型行为」的东西，一律自研**（提示词资产、上下文装配、路由策略、评测门禁）——因为它们是你的核心资产，且变更最频繁。
2. **凡是「无状态、可替换、有清晰接口」的东西，一律买/用开源**（向量库、推理引擎、长任务、可观测后端）——因为替换成本低。
3. **凡是「跨租户/跨账单/跨审计」的东西，一律自研**（配额、账本、审计、成本归因）——因为开源不背你的法律责任。

第 2 条有个前提：**必须有防腐层（Anti-Corruption Layer）**。Aurora 对每个开源组件都包一层自己的接口，让「换掉它」的成本 ≤ 2 人周：

```go
// port/vector.go —— 防腐层：上层只依赖这个接口，不依赖 Qdrant 的 SDK
type VectorStore interface {
    Upsert(ctx context.Context, ns Namespace, docs []Doc) error
    Search(ctx context.Context, ns Namespace, q Query) ([]Hit, error)
    Delete(ctx context.Context, ns Namespace, ids []string) error
    // 关键：Namespace 里必须含 TenantID，强制权限下推（第 20、44 章）
}

type Namespace struct {
    TenantID  string
    IndexID   string
    IndexVer  string // 索引版本进 key，方便灰度与回滚
}
```

> 💡 **判断要不要防腐层的最快方法**：问「如果这个项目明天宣布停止维护，我们要多久换掉它？」如果答案 > 1 个月，就必须有防腐层。**没有防腐层，你就不是「在用开源」，你是「被开源锁定」。**

**用 Aurora 的三个真实决策过一遍这棵树**：

| 决策 | Q1 | Q2 | Q3 | Q4 | Q5 | 结论 |
| --- | --- | --- | --- | --- | --- | --- |
| 向量库 | 通用 | 能（`Upsert/Search/Delete`） | 不够（缺权限下推） | 会（但可做主备） | 补的成本 1 人周 < 自研 16 人周 | **用 Qdrant + 自研 Namespace 层 + 主备** |
| 计费账本 | 差异化（且是法律责任） | 不能（复式记账 + 对账深度耦合业务） | — | — | — | **自研** |
| 长任务运行时 | 通用 | 能（活动/工作流） | 够 | 会（集群级） | — | **用 Temporal + 冗余 worker + 活动幂等** |
| 低代码 DSL | 差异化（业务自助是卖点） | 不能（配置是控制流） | — | — | — | **自研 DSL，参考 Dify 的节点设计** |
| 模型网关 | 通用 | 能（`Chat()`） | 不够（无租户预算） | 会 | 补 2 人周 | **用 LiteLLM + 外层自研预算层** |

### 51.4.1 选型评分表（打分比争论快）

给候选方案打分，**权重必须提前定，不能边看边改**：

```yaml
# rfc/0007-vector-store.yaml —— 选型评分卡（权重合计 = 100）
candidates: [qdrant, milvus, pgvector, weaviate]
weights:
  fit:            25   # 功能匹配度（我们真正需要的功能，不是它宣传的功能）
  ops_burden:     20   # 运维负担（是否有托管、备份、扩缩容、监控）
  governance:     20   # 多租户/权限/审计/配额 的支持程度
  maturity:       15   # 生产案例、issue 响应、版本稳定性（≥2 年 1.0）
  license:        10   # 许可证风险（见 §51.6）
  escape_cost:    10   # 换掉它的成本（有标准协议/SDK 抽象 = 高分）
scoring: "1~5 分，总分 = Σ(score/5 × weight)"
gate:
  - "license 必须 ≥ 4 分，否则一票否决"
  - "maturity 必须 ≥ 3 分（没有 1.0 的项目不进生产）"
  - "总分 < 60 的不进 POC"
```

| 候选 | fit | ops | gov | mat | lic | esc | 总分 | 结论 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| Qdrant | 4 | 4 | 3 | 4 | 5 | 5 | **82** | ✅ 选 |
| Milvus | 5 | 2 | 3 | 4 | 5 | 4 | 76 | 备选（运维重） |
| pgvector | 3 | 5 | 4 | 5 | 5 | 5 | **86** | ✅ 选（< 5 亿向量时） |
| Weaviate | 4 | 3 | 3 | 3 | 4 | 4 | 70 | 淘汰 |

> 💡 **最后一列才是关键**：pgvector 总分更高，因为它「运维负担 5 + 逃逸成本 5」。Aurora 的结论是 **< 5 亿向量用 pgvector，超过再上 Qdrant**——**先选那个「以后换掉最便宜」的**，而不是「功能最多的」。这是选型里最反直觉、也最省钱的一条。

### 51.4.2 依赖预算：把「组件数」变成 CI 里的一条红线

```go
// tools/depbudget/main.go —— 在 CI 里跑，超预算直接失败
// 规则：直接第三方依赖 ≤ 25 个；新增依赖必须在 allowlist 里；每个依赖必须有 owner
func main() {
    mods := parseGoMod("go.mod")
    direct := filterDirect(mods)

    if len(direct) > 25 {
        fail("直接依赖 %d 个，超过预算 25。加依赖前先删一个。", len(direct))
    }
    for _, m := range direct {
        if !inAllowlist(m.Path) {
            fail("%s 不在 allowlist。请提 RFC，注明：\n"+
                "  1) 它替我省下多少人周  2) 它的 owner 是谁\n"+
                "  3) 换掉它的成本  4) 许可证类型", m.Path)
        }
        if ownerOf(m.Path) == "" {
            fail("%s 没有 owner。没有 owner 的依赖 = 没人升级 = 明年变成技术债", m.Path)
        }
    }
}
```

## 51.5 Java / 分布式经验对照

| 你熟悉的 | Agent 生态的对应物 | 会咬人的差异 |
| --- | --- | --- |
| Spring Cloud 全家桶（一站式） | **没有一站式**。Agent 生态是「一堆单点最优 + 没有集成标准」 | Java 世界有 Spring Boot 提供「默认一致」；这里每个组件的租户模型、ID 体系、时间语义都不一样，**集成成本远高于 Java 生态** |
| Maven BOM / 依赖收敛 | 没有 BOM | Python/Go 生态版本约束弱（尤其 Python），同一个进程里两个包要求不同版本的 `pydantic` 是常态。**Go 反而好，模块系统严格** |
| Dubbo/Feign 的接口契约 | 无统一 IDL | MCP 是目前最接近的（工具层），但编排层、记忆层没有标准协议 |
| 中间件选型（RocketMQ vs Kafka） | Temporal vs 自研状态机 | 传统 MQ 选型看吞吐/可靠；这里还要看**「确定性重放」与「模型调用非确定性」的冲突** |
| 内部 SDK / starter | 自研防腐层 | Java 用 starter 收敛配置；这里要用 **port/adapter**（六边形架构）收敛，因为上游 API 变化快 |
| 灰度（Argo Rollouts） | 多数组件不支持 | 开源组件升级没有灰度概念，你只能「新老并行 + 双写对账」 |
| License 合规（法务扫一遍） | **必须前置** | Java 生态 AGPL 相对少见；AI 生态里 AGPL / SSPL / ELv2 / BSL / 「Apache + 附加条款」非常密集（见 §51.6） |

## 51.6 「开源能用，但会在哪咬你」：六类咬点

| # | 咬点 | 真实形态 | 你怎么防 |
| --- | --- | --- | --- |
| **1** | **许可证** | ① Grafana / MinIO / Redis(旧版) 是 **AGPL-3.0**——你改了它并通过网络提供服务，可能要开源你的修改；② MongoDB **SSPL**、Elastic **SSPL/ELv2**——云厂商几乎不可用；③ n8n 是 **Sustainable Use License**（非 OSI），限制「对外提供商业服务」；④ Phoenix 是 **ELv2**；⑤ Dify 是 **Apache 2.0 + 附加条款**（logo 保留、多租户 SaaS 需商业授权）；⑥ Restate 等服务端/客户端许可分层 | **选型前置法务**；CI 里跑 license 扫描；AGPL 组件只做「独立进程 + 不改源码」的用法；商业条款类必须拿到书面授权 |
| **2** | **软多租户** | 「workspace / project / org」只是逻辑分组，底层共享表、共享索引、共享队列；一个 `WHERE tenant_id` 漏写就是越权 | 在外层强制租户上下文（middleware 注入 + 查询构造器强制拼接）；关键路径做「跨租户访问 = 500 并告警」的熔断测试 |
| **3** | **没有治理钩子** | 组件不提供「配额、计费、审计、灰度」的扩展点，只能在它外面套一层 | 在**入口**做治理（网关层），而不是在组件内部；用防腐层隔离 |
| **4** | **升级破坏性变更** | 小版本改 API、改默认值（尤其 0.x 的 Python 项目）；一次升级要改 30 处调用 | 锁版本（`go.mod` / lockfile）；订阅 release notes；每个组件指定 owner；**升级前跑录制回放 + 评测**（第 48 章） |
| **5** | **性能陷阱** | vLLM 默认参数下 GPU 利用率 40%；Temporal 事件历史膨胀到 4GB；向量库在「先过滤后检索」vs「先检索后过滤」上差 100 倍 | **上线前必须压测**；每个组件记录「已知性能悬崖」到一个 `PERF_NOTES.md` |
| **6** | **单点维护者 / 商业转向** | 核心维护者 1~2 人；公司转向闭源（历史上有多次）；某个版本后不再更新 | 看贡献者分布（>3 家公司的项目更安全）；准备 B 计划；**关键路径必须有替代方案**（这就是防防腐层的价值） |

**几条具体的「已经在咬人」的事实**（以各项目官方 LICENSE 与文档最新版为准）：

| 项目 | 许可 | 商用注意 |
| --- | --- | --- |
| Grafana | AGPL-3.0 | SaaS 分发需评估；可考虑只在内网用 |
| MinIO | AGPL-3.0 | 对象存储替代：S3 / R2 / SeaweedFS / Garage |
| Redis（8.x 起） | AGPL-3.0（此前 RSALv2/SSPL） | 可用 **Valkey**（BSD）规避 |
| n8n | Sustainable Use License | 不能直接拿它做对外商业服务 |
| Dify | Apache 2.0 + 附加条款 | 多租户 SaaS 与 logo 需读 LICENSE |
| Phoenix (Arize) | Elastic License 2.0 | 不是 OSI 开源，注意「不能提供托管服务」条款 |
| LangGraph / eino / vLLM / Qdrant / pgvector / Temporal | MIT / Apache 2.0 / PostgreSQL | 最安全的一档 |

## 51.7 事故清单

- [ ] **事故 A：AGPL 组件被 SaaS 化，法务在融资尽调时发现。** 现象：DD 清单里要求「证明所有组件的许可证合规」，一次性换掉 2 个组件，延期 6 周。→ 兜底：选型 RFC 里必须有 license 字段 + CI 扫描 + 法务签字。
- [ ] **事故 B：改源码打 patch，升级时全部丢失。** 现象：LiteLLM 改了 3 处，升级到新版后预算功能静默失效，超支 $22k。→ 兜底：**优先用扩展点（hook/plugin）而不是改源码**；必须改时，patch 文件进仓库 + 升级 checklist 里逐条验证 + 加一条集成测试。
- [ ] **事故 C：升级小版本，流式解析全挂。** 现象：某 SDK 0.28 → 0.29 改了 tool_call 的分片格式，线上 30% 的 Run 报错。→ 兜底：锁版本 + 升级走「录制回放 + 1% 灰度」（第 48 章）。
- [ ] **事故 D：Temporal 事件历史爆掉。** 现象：单工作流历史 4GB，worker 重启回放 8 分钟，期间任务全卡。→ 兜底：设 `WorkflowExecutionTimeout`、用 `continue-as-new` 分段、大 payload 存对象存储只传引用。
- [ ] **事故 E：向量库「先查后过滤」导致越权。** 现象：跨租户召回了 3 条文档（虽然被应用层过滤掉了，但已经进了上下文）。→ 兜底：权限下推到查询层（`namespace` / `filter` 必传），并在返回前再做一次租户校验。
- [ ] **事故 F：依赖 214 个，没人知道哪个在引入 CVE。** 现象：安全扫描报 47 个高危，团队花两周逐个排查。→ 兜底：依赖预算（≤25 直接依赖）+ 每个依赖有 owner + 每周自动扫描 + SBOM 落库。
- [ ] **事故 G：核心组件只有一个维护者，他离职了。** 现象：某个自研封装的 adapter 没人懂，出问题只能回滚。→ 兜底：关键适配层「双人负责制」+ 文档 + 每季度做一次「如果他明天离职」的演练。

## 51.8 一页速记

| 关键词 | 必须记住的结论 |
| --- | --- |
| 真实成本 | 每个开源组件 ≈ 16 人周/首年；9 个组件 = 2.8 人年 = 25% 产能 |
| 乘法风险 | 升级节奏会乘起来：9 个组件 × 1~3 次破坏性变更/年 = 15~27 次「必须跟着动」 |
| 开源真相 | **开源把能力做完了，把治理留给你了**；每层的「咬你」都是多租户/配额/审计/计费/灰度 |
| 三条边界 | 改模型行为的 → 自研；无状态可替换的 → 开源；跨租户/跨账/跨审计的 → 自研 |
| 决策树 | 差异化？→ 接口可抽象？→ 治理够？→ 会成瓶颈？→ 补治理 < 自研？ |
| 选型顺序 | **先选「以后换掉最便宜的」，而不是「功能最多的」**（pgvector > Milvus 的例子） |
| 防腐层 | 没有防腐层 = 被锁定。判定：换掉要多久，> 1 个月就必须有 |
| 许可证 | AGPL/SSPL/ELv2/SUL/「Apache+附加条款」密集；**法务前置 + CI 扫描**，不是上线后再补 |
| 依赖预算 | 直接依赖 ≤ 25；每个依赖必须有 owner + allowlist；SBOM 落库 |
| 升级 | 锁版本；升级跑录制回放 + 1% 灰度；patch 必须进仓库并有验证清单 |
| 一句话 | **你不需要最好的开源，你需要「最容易被换掉」的开源。** |

## 51.9 自检题

1. **团队想引入一个「全能 Agent 平台」（Dify 这一类）作为底座。请给出你的评估清单（至少 5 项，每项给判据）。**
   > 要点：① **许可证**：能否用于多租户 SaaS、能否去 logo（拿 LICENSE 原文 + 法务签字）；② **多租户是硬还是软**：能否做到「跨租户查询在 SQL 层就不可达」，而不只是 UI 分组；③ **配置治理**：有没有 draft/publish/diff/rollback/审批，能不能把 `config_ver` 打进 trace；④ **执行隔离**：代码节点是不是跑在应用进程里（是 → 你必须沙箱化）；⑤ **评测门禁**：发布 API 前能不能挂一个外部评测阻断；⑥ **逃逸成本**：DSL 能否导出成标准格式（YAML/JSON），导出后能不能在别处执行。**五项里三项不过，它就只能当 POC 工具，不能当底座。**

2. **为什么 Aurora 在向量库上选了「总分更低」的 pgvector 而不是 Milvus？这个判断在什么条件下会翻转？**
   > 要点：因为选型的核心变量不是「功能匹配」，而是「运维负担 + 逃逸成本」——pgvector 与 PG 同生命周期（备份/监控/扩缩容都复用），换掉它的成本接近 0；Milvus 功能更强但引入一个需要专职运维的分布式系统。**翻转条件**：向量规模 > 5 亿、或 QPS > 2k 且 P99 要求 < 20ms、或需要多向量混合检索的高级特性。**判断方法是压测出拐点，而不是猜。**

3. **你接手一个平台，发现 `go.mod` 里有 68 个直接依赖，其中 12 个没人知道是干什么的。你的 30 天动作是什么？**
   > 要点：① 先做**依赖图谱**（谁引谁、哪个是根），把 12 个不明的标记；② 跑 license 扫描 + CVE 扫描，把「restricted/forbidden」的挑出来（这是法务风险，优先级最高）；③ 给每个依赖指定 owner（找不到 owner 的就地评估「能否删除」，通常能删掉 5~8 个）；④ 设**依赖预算**并在 CI 里强制（新增必须 RFC）；⑤ 对 3 个最关键的做「如果他明天消失」的替代方案评估。**顺序不能反：先清法务风险，再清认知负担，最后才立规矩。**
