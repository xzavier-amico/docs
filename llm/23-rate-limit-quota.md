## 23.1 引子：一个大客户的压测，打崩了 10 万个租户

周二上午 10:40，Aurora 监控开始报警。现象很奇怪：

- 全局 QPS 只有 **4,200**，远低于 5,000 的设计水位；
- 但全平台 P99 从 6.5 秒涨到 **28 秒**，Run 超时率从 0.4% 冲到 **18%**；
- 报警集中在「模型网关排队」，可模型供应商的状态页是绿的。

查了 20 分钟才找到：某个企业租户把**压测环境指到了生产**，单租户持续 **200 QPS**（平时全平台 Run 提交峰值才 600 QPS）。他们的压测脚本只发「最简单的单轮问答」，所以全局 QPS 没打满；但每一次请求都要占并发、占模型配额、占连接，排队一长，**别人的 30 秒 Run 预算全被吃光**。

你的限流配置是这样的：

```yaml
# 出事前的配置（典型的「按接口限流」）
routes:
  - path: /v1/runs
    limit: 5000        # 全局 QPS
```

这个配置在单租户时代是对的，在多租户时代**等于没配**——因为 5,000 是给「所有租户加起来」的额度，任何一个租户都可以合法地用掉全部。

修复只用了三行配置（把租户维度和并发维度加上），但代价是 40 分钟的故障、约 **3.2 万次**失败 Run，以及一个要求赔偿的大客户。

> 🩸 **第一课**：限流的维度选错，比不限流更危险——因为你有仪表盘，看着数字「没超」，于是失去了警觉。

## 23.2 断崖：限流做错的五种方式

| # | 错误配法 | 为什么会犯 | 后果 | 量级 |
| --- | --- | --- | --- | --- |
| 1 | 只有全局阈值 | 单租户时代留下的习惯 | 一人吃饱、全家饿死 | 单租户 200 QPS 即可打崩全平台 |
| 2 | 只限 QPS，不限并发 | 传统 API 是「一次请求一次响应」 | 30 秒的 Run 会堆积：5,000 QPS × 30s = **15 万在途** | 连接/fd/内存三杀 |
| 3 | 只在入口限流 | 以为内部调用可信 | 重试、扇出、子 Agent 绕过闸门 | 重试 3 次 × 5,000 = **2 万 QPS** 打下游 |
| 4 | 限流即拒绝（429） | 教科书只教了这一种 | 高峰期错误率断崖，用户直接流失 | 从 0.4% → 18% |
| 5 | 配额与计费脱节 | 限流和账本是两个团队 | 超卖、白用、对不上账 | 免费额度被刷走 **月成本 7%** |

第二条值得展开，因为它是 Agent 平台独有的：**QPS 是速率，并发才是水位**。按 Little 定律：

```
并发 = 到达速率 × 平均驻留时间
     = 600 QPS × 30 s = 18,000 个在途 Run   ← 峰值常态
     = 5,000 QPS × 30 s = 150,000 个在途 Run ← 如果你真按 5000 放行
```

15 万个在途 Run，每个持有 1 条 SSE 连接 + 平均 28k token 的上下文快照 ≈ **4.2 TB 内存**。所以限流必须同时限**速率**（每秒进多少）和**并发**（同时有多少），这是两个不同的闸门。

## 23.3 结构图：三道闸 + 五维度

```
                       入站 5,000 QPS（Run 提交 600 QPS）
                                    │
┌───────────────────────────────────▼────────────────────────────────────┐
│ 闸①  边缘层（网关 / 每 Pod 本地）                                        │
│   算法：令牌桶（本地，微秒级）  维度：IP · APIKey · 平台总水位             │
│   作用：挡住突发与恶意刷；本地桶允许 1.2 倍瞬时突发                        │
└───────────────────────────────────┬────────────────────────────────────┘
                                    │ 通过 ~4,600 QPS
┌───────────────────────────────────▼────────────────────────────────────┐
│ 闸②  准入层（全局限流服务，Redis + Lua）                                  │
│   算法：令牌桶(QPS) + 并发信号量 + 滑动窗口(日配额)                        │
│   维度：租户 > 用户 > 项目（取最严）                                      │
│   作用：多租户公平、套餐额度、成本预算（$ / token）                        │
└───────────────────────────────────┬────────────────────────────────────┘
                                    │ 通过 ~600 QPS 提交
┌───────────────────────────────────▼────────────────────────────────────┐
│ 闸③  调度层（模型池 / 工具网关）                                          │
│   算法：并发信号量 + 漏桶（平滑下游）                                      │
│   维度：模型 · 供应商 · 工具 · 下游依赖                                    │
│   作用：保护上游供应商与内部服务，防止重试风暴                              │
└───────────────────────────────────┬────────────────────────────────────┘
                                    ▼
                              执行 / 排队 / 降配 / 降级

  横切：所有闸的判定结果都发一条 metric（allowed/denied/dimension/reason），
        并落一条审计（谁被限、限了多少、出口是什么）——限流必须可解释。
```

**为什么是三道而不是一道**：本地桶扛住 99% 的流量（不做网络调用，P99 < 5µs）；全局限流器只处理「本地桶额度耗尽」的那一小部分；调度层限流和业务语义绑定（模型配额、工具配额）。三级串联后，全局 Redis 的调用量从 **2 万次/秒**（5k × 4 维）降到 **500 次/秒**左右——这是能扛住的技术方案，见 23.4.2 的 lease 机制。

## 23.4 关键设计

### 23.4.1 五维度 × 四算法：一张能直接抄的矩阵

| 维度 \ 算法 | 令牌桶（速率） | 漏桶（平滑） | 滑动窗口（配额） | 并发信号量（水位） | 超限后的出口 |
| --- | --- | --- | --- | --- | --- |
| **平台** | 5,000 QPS 总水位 | — | 日预算 $60k | 20 万在途 Run | 排队 + 拒绝新租户 |
| **租户** | 默认 20 QPS，企业版 200 | — | 套餐月 token / 日 $ | 租户并发 2,000 | 排队 → 降配 |
| **用户** | 5 QPS | — | 日 500 次 | 单用户 3 个在途 | 排队（短）→ 提示 |
| **模型** | 供应商 RPM/TPM | 出站平滑（防突发） | — | 供应商并发 800 | failover（第 25 章） |
| **工具** | 工具 QPS（如 200） | — | 日调用上限 | 工具并发 64 | 降级/跳过该工具 |

四算法的选择不是口味问题，是**语义问题**：

| 算法 | 语义 | 用在哪 | 实现成本 | 坑 |
| --- | --- | --- | --- | --- |
| 令牌桶 | 允许突发（有存量） | 边缘、租户 QPS | 低（`x/time/rate`） | burst 配大 = 允许瞬时打穿下游 |
| 漏桶 | 强制匀速 | 出站到供应商 | 低 | 会人为增加延迟（排队） |
| 滑动窗口 | 「最近 60 秒内不超过 N」 | 日/月配额、计费前置 | 中（Redis ZSET 或分桶） | 固定窗口有 2 倍边界突刺 |
| 并发信号量 | 「同时最多 N 个」 | Run 在途、工具并发 | 低（带 TTL 的计数器） | **必须处理泄漏**（进程崩溃不释放） |

> ⚠️ 并发信号量最大的坑是**泄漏**：进程被 kill 时不释放，计数器只增不减，最后永久限流。必须给每个信号量带 TTL（如 Run 最大时长 + 60 秒）并由巡检任务回收。这条我们在第 28 章还会碰到。

### 23.4.2 本地桶 + 全局 lease：把 Redis 从 2 万 QPS 降到 500 QPS

纯 Redis 限流在 5k QPS × 4 维度下是 2 万次 Lua 调用/秒。单 Redis 分片跑简单命令能到 10 万 QPS，但带 Lua 脚本的实测上限在 **5 万/秒**量级，还要留余量给缓存和会话——不划算，且每次多 0.5~1ms 网络往返。

Aurora 的做法是**两级桶 + lease（批量预领）**：

```go
// limiter/lease.go —— 本地令牌桶 + 周期性批量领取
type LeaseLimiter struct {
    local  *rate.Limiter   // 本地桶，理论速率 = 配额/副本数
    remote RemoteQuota     // Redis 侧的真实配额
    mu     sync.Mutex
    lease  float64         // 当前已领到但未用完的额度
    lastAt time.Time
}

// Allow 快路径：本地桶有额度就直接放行，零网络调用（P99 ~2µs）
func (l *LeaseLimiter) Allow(ctx context.Context, n int) (bool, error) {
    if l.local.AllowN(time.Now(), n) { return true, nil }

    // 慢路径：向 Redis 批量领 batch 个额度（默认 batch=50）
    // Redis 调用次数 ≈ 实际QPS / batch，2万 → 500 次/秒
    ok, got, err := l.remote.Take(ctx, n, leaseBatch)
    if err != nil {
        return l.failOpen(), err // ← 关键：限流器故障时放行还是拒绝？见下
    }
    if ok { l.local.ReserveN(time.Now(), got-n); return true, nil }
    return false, nil
}
```

三个参数必须一起调：

| 参数 | 取值 | 推导 |
| --- | --- | --- |
| `leaseBatch` | 50 | Redis 压力 = QPS/batch；50 已把 2 万降到 400~500 |
| 误差上限 | batch × 副本数 | 80 副本 × 50 = **4,000 token 的超发窗口**，即配额 20% 需留安全边际 |
| Redis 故障策略 | **fail-open + 本地兜底** | 限流器挂了不能把全平台挂掉；本地桶仍以「保守速率」放行 |

> 💡 `leaseBatch` 是「精度 ↔ Redis 压力」的旋钮。batch=1 是精确限流（2 万 Redis QPS）；batch=50 是 500 Redis QPS + 最多 4,000 token 超发。多数平台选中间值，并接受**配额超发 5~20%**——这比「限流器成为单点」便宜得多。

### 23.4.3 Redis + Lua：令牌桶（原子、单往返）

```lua
-- rate_limit_token_bucket.lua
-- KEYS[1] = bucket key（如 rl:t:88231:runs）
-- ARGV[1]=rate(个/秒) ARGV[2]=burst ARGV[3]=now_ms ARGV[4]=cost
-- 返回 {allowed(0/1), 剩余额度, 建议重试毫秒}
local key   = KEYS[1]
local rate  = tonumber(ARGV[1])
local burst = tonumber(ARGV[2])
local now   = tonumber(ARGV[3])
local cost  = tonumber(ARGV[4])

local t = redis.call('HMGET', key, 'tokens', 'ts')
local tokens = tonumber(t[1])
local ts     = tonumber(t[2])
if tokens == nil then tokens = burst; ts = now end

-- 补水：按流逝时间补充，上限 burst
local delta = math.max(0, now - ts) / 1000.0
tokens = math.min(burst, tokens + delta * rate)

local allowed, retry = 0, 0
if tokens >= cost then
  tokens  = tokens - cost
  allowed = 1
else
  -- 还要等多久才能攒够 cost 个令牌
  retry = math.ceil((cost - tokens) / rate * 1000)
end

redis.call('HMSET', key, 'tokens', tokens, 'ts', now)
redis.call('PEXPIRE', key, math.ceil(burst / rate * 1000) + 1000)
return {allowed, math.floor(tokens), retry}
```

四点说明（都是踩过的）：

1. **`now` 由客户端传入**，不要用 `redis.call('TIME')`——集群/主从下时钟与脚本确定性都更麻烦。代价是容忍副本间 **≤50ms** 的时钟偏差（NTP 保证），对 QPS 限流完全够。
2. **必须返回 `retry`**。没有它，你的 429 和客户端的重试就是一场同步风暴（所有客户端在同一毫秒重试）。
3. **`PEXPIRE` 必须设**，否则 key 永不回收，10 万租户 × 5 维的 key 会长期占内存（约 50~80 MB，不致命但会随维度组合爆炸）。
4. **一个脚本只做一件事**。把「租户 + 用户 + 工具」三个维度塞进一个脚本，会让单次执行从 40µs 涨到 150µs，且无法按维度单独降级。

### 23.4.4 成本维度：QPS 限得住，钱限不住

Agent 平台与传统 API 最大的区别是：**同样的 QPS，成本差 100 倍**。一次 2k token 的单轮问答 ≈ $0.006；一次 25 步工具循环 ≈ $0.6。只按 QPS 限流，等于允许一个租户用 20 QPS 烧掉 $12/秒。

所以维度里必须加两个「钱」的闸：

| 闸 | 键 | 窗口 | 超限出口 |
| --- | --- | --- | --- |
| TPM（token/分钟） | `q:t:{tenant}:tpm` | 60s 滑窗 | 排队（等窗口滑过）或降配到小模型 |
| 日预算 | `q:t:{tenant}:usd:{yyyymmdd}` | 自然日 | 硬停 + 通知（企业版走「自动扩容 + 事后结算」） |

实测修正系数：`tokens ≈ 字数 × 1.6`（中文），`单 Run 成本 ≈ 输入token/1e6 × $2.5 + 输出token/1e6 × $10`。按单 Run 28k 输入 + 800 字输出 ≈ **$0.078**，日 80 万 Run ≈ **$62k/天**——所以日预算闸的默认值定在「套餐额度 × 1.05」（5% 超卖容忍），超过就软停并要求充值。

### 23.4.5 限流 ≠ 拒绝：三个出口

这是本章最容易被忽略、但对体验影响最大的一节。**429 是最后手段，不是第一反应。**

```
                    请求到达 → 判定
                              │
        ┌─────────────────────┼─────────────────────┐
        │ 额度充足             │ 短时不足(<2s)        │ 持续不足
        ▼                     ▼                     ▼
     正常执行            ┌─────────┐          ┌──────────────┐
                        │ ① 排队   │          │ ② 降配        │
                        │ 优先队列 │          │ 小模型/少检索  │
                        │ 回传位置 │          │ 关非必要工具   │
                        └────┬────┘          └──────┬───────┘
                             │ 排队超时              │ 仍不足
                             ▼                      ▼
                        ┌──────────────────────────────────┐
                        │ ③ 降级（第 25 章降级阶梯）         │
                        │ L2 模板回答 / L3 兜底话术          │
                        └──────────────┬───────────────────┘
                                       ▼
                        ┌──────────────────────────────────┐
                        │ ④ 明确失败：429/402 + retry_after │
                        │    + 人话解释 + 升级引导           │
                        └──────────────────────────────────┘
```

| 情况 | 出口 | 具体动作 | 用户感知 | 成本影响 |
| --- | --- | --- | --- | --- |
| 瞬时突发（预计 <2s） | **排队** | 进优先级队列，SSE 回 `status: queued` + 位置 | 多等 1~2 秒 | 0 |
| 中时拥堵（2~10s） | **降配** | 路由到小模型、检索 top-k 从 8→3、关掉 3 个非必要工具 | 答案略糙但可用 | ↓ 60% |
| 长时过载 / 供应商故障 | **降级** | 走降级阶梯（第 25 章） | 「当前较忙，给出简版」 | ↓ 80% |
| 配额耗尽（钱/额度） | **明确失败** | `402` + 充值链接 + 剩余额度 | 明确、可行动 | 0 |
| 恶意/超速（风控命中） | **拒绝** | `429` + `retry_after` + 上报风控 | 明确 | 0 |

> 💡 判据很简单：**「这个用户等 2 秒能不能接受？」** 能 → 排队；「降配后的答案还能不能交付？」能 → 降配。两个都否，才轮得到 429。我们在客服场景实测：把 62% 的 429 换成「排队 + 降配」后，高峰期错误率从 18% 降到 **2.1%**，而成本反而降了 9%。

### 23.4.6 配额运营：套餐、充值、超卖容忍

配额不是技术参数，是**商业参数**。它必须和计费账本（第 27 章）用同一套计量，否则一定对不上账。

| 套餐 | 月含 token | 峰值 QPS | 并发 Run | 软限行为 | 超限行为 |
| --- | --- | --- | --- | --- | --- |
| Starter | 500 万 | 2 | 10 | 80% 时邮件提醒 | 硬停，次日恢复 |
| Pro | 5,000 万 | 20 | 200 | 100% 时降配 24h | 按量计费（1.3× 单价） |
| Enterprise | 合同 | 200 | 2,000 | 105% 软限，24h 内不打断 | 自动扩容 + 事后结算 |
| 内部/压测 | 独立池 | — | — | — | 独立资源池，不进生产配额 |

三条运营铁律：

1. **软限必须有**（80% 提醒、100% 降配、105% 硬停）。直接硬停会让客户在业务高峰掉线，这是最贵的客诉。
2. **超卖要显式**。`leaseBatch=50 × 80 副本 = 4,000 token` 的超发窗口必须写进合同或 SLA 说明，否则对账时你会发现「卖出 100 万，用了 104 万」。
3. **配额变更要审计 + 可回滚**。运维手改一个租户的 QPS 从 20 到 2000，等于给了一次 DDoS 的授权。所有变更进策略中心（第 43 章），带审批与生效时间。

| 项目 | 对应 | 能用 | 缺什么 |

| **Sentinel**（Java/Alibaba） | 流控、熔断、热点参数、集群流控 | ✅ 概念最全，规则模型可直接借鉴 | 无「token/$」成本维度；Go 生态弱 |
| **`golang.org/x/time/rate`** | 单机令牌桶 | ✅ 本地闸首选，无依赖 | 无分布式能力 |
| **Redis Cell**（`CL.THROTTLE`） | Redis 模块级 GCRA 限流 | ⚠️ 需自建模块，运维成本高 | 不支持多维度组合、返回信息少 |
| **Envoy rate limit**（gRPC 服务） | 边缘/服务网格限流 | ✅ 有现成 gRPC 协议 | 配额语义简单，做不了套餐/账本 |
| **LiteLLM**（`rpm`/`tpm`/`max_budget`） | 模型层配额 | ✅ 上手最快 | 多租户层级弱，超卖与对账不管 |
| **Redis + Lua**（自研） | 全局限流服务 | ✅ 唯一能同时满足「多维 + 成本 + 可解释」 | 要自己写脚本、压测、做降级 |

> 🎯 结论：**边缘用 Envoy/Nginx，本地用 `x/time/rate`，全局用 Redis+Lua 自研，模型层用 LiteLLM 兜底**。四层各司其职，别指望一个组件全包。

## 23.7 事故清单

- [ ] **A. 全局阈值打崩全平台**：单租户 200 QPS 压测 → 全平台 P99 6.5s→28s。→ 根因：缺租户维度。→ 兜底：租户/用户维度 + 并发信号量 + 大租户独立池。
- [ ] **B. 重试风暴**：下游超时 → 客户端重试 3 次 → 5,000 QPS 变 2 万 QPS → 下游彻底挂。→ 根因：无 `retry_after` + 无抖动 + 无重试预算。→ 兜底：返回 `retry_after`、指数退避 + 抖动、重试总额上限（第 25 章）。
- [ ] **C. 并发信号量泄漏**：Pod 被 OOMKill，计数器不释放 → 该租户永久限流。→ 根因：无 TTL。→ 兜底：信号量带 TTL + 巡检回收 + 以「Run 状态」为准对账。
- [ ] **D. 限流器成为单点**：Redis 主从切换 8 秒 → 所有请求 500。→ 根因：fail-close。→ 兜底：fail-open + 本地桶保守速率 + 熔断降级。
- [ ] **E. 配额与账本打架**：限流按「次」，计费按 token，客户看到「还有额度」但账单爆了。→ 根因：两套计量。→ 兜底：统一计量口径（第 27 章），配额消费以计费流水为准。
- [ ] **F. 免费额度被刷**：注册即送 100 万 token，黑产 3 天刷走 7% 月成本。→ 根因：只有总量限，没有速率/设备维度。→ 兜底：用户维度 5 QPS + 设备指纹 + 新账号额度递减（第 32 章）。

## 23.8 一页速记

| 关键词 | 必须记住的结论 |
| --- | --- |
| 维度 | 五维：平台/租户/用户/模型/工具；**缺租户维度 = 没限流** |
| 速率 vs 并发 | QPS 是进的速度，并发是水的深度；600 QPS × 30s = 1.8 万在途 |
| 三道闸 | 边缘本地桶（µs）→ 全局 Redis（ms）→ 调度层（供应商/工具） |
| 降 Redis 压力 | lease 批量预领：batch=50 把 2 万 Redis QPS 降到 500，代价 5~20% 超发 |
| 成本维度 | 必须限 TPM 与日预算；同一 QPS 成本差 100 倍 |
| 超限出口 | 排队 → 降配 → 降级 → 明确失败；**429 是最后手段** |
| 硬指标 | 62% 的 429 换成排队+降配后，错误率 18% → 2.1%，成本 ↓9% |
| 算法选择 | 突发用令牌桶、平滑用漏桶、日额度用滑窗、在途用信号量（带 TTL） |
| fail 策略 | 限流器故障 **fail-open** + 本地兜底，不能 fail-close |
| 配额运营 | 80% 提醒 / 100% 降配 / 105% 硬停；超卖额度必须显式写进 SLA |
| 一句话 | **限流的目的是「让平台活着把大部分请求做完」，不是「把超出的请求扔回去」。** |

## 23.9 自检题

1. **你的全局限流配置是 5,000 QPS，为什么还会被一个 200 QPS 的租户打崩？请给出两个你应该加上的维度。**
   > 要点：全局阈值是「所有租户共享的总额度」，单租户可以合法吃掉全部。必须加：① **租户维度**（默认 20 QPS，企业版 200）；② **并发信号量**（租户并发 2,000、平台在途 20 万），因为 600 QPS × 30s 就有 1.8 万在途，速率合规不代表水位合规。

2. **纯 Redis 限流在 5k QPS × 4 维度下要扛 2 万次 Lua/秒，你怎么降一个数量级？代价是什么？**
   > 要点：本地令牌桶 + lease 批量预领（batch=50）→ Redis 调用降到 ~500 次/秒。代价：① 最多 `batch × 副本数`（80×50=4,000 token）的超发窗口；② 配额精度下降 5~20%，必须在 SLA/合同里显式说明；③ 需要 Redis 故障时的 fail-open 与本地保守兜底。

3. **高峰期你的接口返回了大量 429，运维说「这是限流在保护系统」。这句话哪里不对？应该怎么做？**
   > 要点：429 只保护了系统，没有保护业务。正确做法是分场景选出口：预计 <2s 的拥堵 → 排队（回传位置）；2~10s → 降配（小模型/少检索/关非必要工具）；持续过载 → 降级阶梯；只有配额耗尽与恶意流量才 429/402。并保证 429 一定带 `retry_after`，否则会引发同步重试风暴。
