## 20.1 引子：recall@10 是 0.94，答对率是 61%

Aurora 一个电商租户的知识库里有 12 万份文档、约 480 万个 chunk。上线第一周，客服 Agent 的检索指标很漂亮：**recall@10 = 0.94**。但人工评测的答对率只有 **61%**。

最典型的一类错：用户问「无理由退货是几天？」

- 知识库里有 3 份政策文档：`退货政策-2024.pdf`（30 天）、`退货政策-2025.pdf`（15 天）、`退货政策-2026.pdf`（7 天）。
- 切分后每个 chunk 只有正文那几百字，**没有文档名、没有生效日期**。
- rerank 给 2024 版打的分最高（它写得最详细、最"像"答案）。
- 模型拿着 30 天，答得斩钉截铁。

这一条错误在 7 天里出现了 **1,100 次**，其中 84 次造成实际退款损失。

而 recall 指标完全正常——**因为 2024 版确实是"相关文档"，检索器没错，错的是"相关"的定义里缺了"当前有效"这个维度。**

> 🩸 这一章的第一个、也是最重要的判断：
> **RAG 的质量问题，90% 不是"没检索到"，而是"检索到了不该用的东西"或者"检索到的东西缺了上下文"。**
> 你的评测指标如果没有"正确率"，你会一直以为自己做得不错。

## 20.2 断崖：RAG 会从七个方向错

| # | 断崖 | 本质 | 典型症状 | 量化判据 |
| --- | --- | --- | --- | --- |
| 1 | **切分破坏上下文** | chunk 脱离文档就失去意义 | 命中"7 天"但不知是哪份政策 | chunk 里没有标题/章节/日期 |
| 2 | **版本共存** | 新旧政策同时在库里 | 答旧政策、答已废止条款 | 同一主题有 >1 份文档生效期重叠 |
| 3 | **纯向量召回漏术语** | 型号、SKU、错误码语义检索差 | "ERR_4021"召回不到 | 含 ID/型号类查询的召回率 < 60% |
| 4 | **排序错** | 相关的排在第 11~50 名 | 只取 top-5 时答错 | nDCG@10 < 0.7 |
| 5 | **权限下推缺失** | 先检索后过滤 | **A 租户看到 B 租户文档** | 你的 SQL 里过滤条件在应用层而不在 WHERE 里 |
| 6 | **索引不增量** | 文档更新后索引陈旧 | 新政策上线 3 天还在答旧的 | 文档更新到可检索的延迟 > 10 分钟 |
| 7 | **没有归因** | 答错时不知道错在哪一环 | 只会"多加点文档试试" | 你说不出失败案例的归因分布 |

### 20.2.1 先建立"失败归因"这个习惯

Aurora 每季度抽 500 条 RAG 失败案例做人工归因，这是投入产出比最高的一件事——**它告诉你该修哪里，而不是让你凭感觉加 chunk size**。

| 归因类别 | 判据（怎么判断是这一类） | Aurora 占比 | 对应修法 |
| --- | --- | --- | --- |
| **切分破坏上下文** | 命中 chunk 里确实有答案片段，但缺主语/条件/日期 | 24% | 面包屑 + 父子块 |
| **版本冲突** | 命中了非当前生效版本 | 21% | 生效期过滤 + 版本权重 |
| **未召回（知识缺失）** | 正确答案根本不在库里 | 18% | 补数据 + 增量索引 |
| **生成幻觉** | 上下文里有正确答案，模型答错 | 16% | 引用校验 + 提示约束（第 38 章） |
| **排序错** | 相关文档在 11~50 名 | 15% | rerank |
| **权限过滤过度** | 有权限的文档被 ACL 误过滤 | 4% | ACL 映射修正 |
| **权限下推缺失** | 越权召回（安全事故，不是质量问题） | 2% | WHERE 下推 + 测试用例 |

**这张表最反直觉的一行是"生成幻觉 16%"**：即使你把检索做到完美，还有 16% 的错误发生在生成侧。所以"RAG 答错就调检索"是个错误的条件反射——**先归因，再动手**。

### 20.2.2 账本：检索的 token 与延迟预算

RAG 的成本不在检索，在**注入**。

| 项 | 量级（Aurora） | 说明 |
| --- | --- | --- |
| 日检索次数 | 120 万次 | 60 万 Run，50% 需要检索，平均 4 次/会话 |
| 注入 token | 每次 3,200 token（8 个 chunk × 400） | 占单次输入 25k 的 12.8% |
| 日均注入 | 120 万 × 3,200 = 3.84B token | 按 $3/M = **$11,520/天** |
| 检索自身成本 | embedding + ANN + rerank ≈ $0.0006/次 | 120 万 × 0.0006 = $720/天 |
| **延迟预算** | 总 800ms | 见下表 |

**关键结论：注入成本是检索成本的 16 倍。** 所以优化的重点不是"检索快一点"，而是"**少注入、注入对的**"——8 个 chunk 里如果 3 个是冗余的，你每天在为一个没用的 chunk 付 $4,300。

延迟预算拆解（第 1 章给的 0.8s 怎么花）：

```
query 改写（可选，小模型）      40ms
embedding（query）             30ms
向量召回 top-50                15ms
BM25 召回 top-50               10ms
RRF 融合                       1ms
rerank top-20 → top-8          90ms
权限二次校验 + 组装             10ms
────────────────────────────────
合计                          196ms   （预算 800ms，余量 4 倍）
```

留这么多余量是有意的：**检索是在线链路上最容易受"知识库规模增长"影响的环节**。文档从 12 万涨到 50 万时，你的向量索引会变慢、rerank 候选会更杂。别把预算吃满。

## 20.3 结构图：离线索引管道 + 在线检索管道

```
【离线】索引管道（事件驱动，目标延迟 <10 分钟）
  文档上传/变更 (S3 事件 / CDC)
        │
        ▼
  ① 解析（PDF/HTML/DOCX/表格 → 结构化文本 + 标题层级）
        │  失败不静默：进 dead-letter，人工看
        ▼
  ② 切分（结构感知优先 → 父子块 → 面包屑注入）
        │  每个 chunk 带 {doc_id, 标题路径, 生效期, 版本, acl_groups, lang, content_hash}
        ▼
  ③ 去重（content_hash 相同不再算 embedding，直接复用向量）
        │
        ▼
  ④ embedding（批量，按模型版本分桶！）
        │
        ▼
  ⑤ 原子切换（别名 alias 指向新版本索引；旧版本保留 24h 供回滚）
        │
        ▼
  索引：chunk 表（向量 + tsvector + ACL 数组 + 生效期）

【在线】检索管道
  用户 query
        │
        ├─▶ ① 改写/扩展（可选，只在短 query / 多轮指代时启用）
        │
        ├─▶ ② 并行双路召回 ──┬─ 向量 ANN top-50（带 tenant_id + ACL 过滤）
        │                     └─ BM25 top-50（同样的过滤条件）
        │
        ├─▶ ③ RRF 融合 → top-20
        │
        ├─▶ ④ rerank（cross-encoder）→ top-8
        │
        ├─▶ ⑤ 后置校验：生效期 / 版本 / 权限二次确认（防御性）
        │
        └─▶ ⑥ 组装注入（带 doc_id + 标题路径 + 日期，供引用与审计）
                    │
                    ▼
              LLM（引用 → 后处理校验，第 38 章）
```

两个"看起来多余但必须做"的环节：

- **②的并行双路**：向量召回和 BM25 必须**并行**发，串行会把延迟从 25ms 变成 40ms，且没有意义——它们的输入是同一个 query。
- **⑤ 后置校验**：即使 ② 已经下推了权限，⑤ 还要再查一次。这是**纵深防御**：万一索引的 ACL 字段同步延迟（比如用户刚被移出项目组），后置校验能拦住。成本是 10ms，收益是一次越权事故。

## 20.4 关键设计

### 20.4.1 切分策略：chunk 必须自带"上下文"

这是 RAG 里最被低估的一环。绝大多数"检索到了但答错"，根因都是**chunk 脱离文档后语义不完整**。

| 策略 | 适用 | chunk 大小 | overlap | 优点 | 坑 |
| --- | --- | --- | --- | --- | --- |
| **固定长度** | 通用兜底 | 400~800 token | 10~15% | 简单、可预测 | 切断句子、切断表格、切断条件 |
| **结构感知（标题层级）** | 手册、规范、合同 | 按节，≤1,000 | 0 | 保留逻辑单元 | 某节太长要二次切 |
| **语义切分** | 长文、论文、访谈 | 变长 | 0 | 主题完整 | 成本高、结果不稳定（不可复现） |
| **父子块（small-to-big）** | 需要"精确定位 + 完整上下文" | 子 200 / 父 1,200 | — | 召回准、注入全 | 存两份，存储 ×1.6 |
| **表格/结构化** | 价格表、政策表、参数表 | 行组 + **表头必带** | 表头冗余 | 不破坏表结构 | 表头丢失 = 灾难性错误 |
| **代码** | 技术文档、SDK 文档 | 函数/类级 | — | 完整单元 | 跨文件依赖丢失 |

**无论用哪种，每个 chunk 必须带"面包屑"（breadcrumb）**，这是引子里那个事故的唯一解：

```json
{
  "chunk_id": "c_9f2a1b",
  "doc_id": "d_refund_2026",
  "breadcrumb": "售后政策 > 第二章 退货 > 2.3 无理由退货",
  "content": "自签收之日起 7 个自然日内，商品未拆封且不影响二次销售的，可申请无理由退货……",
  "effective_from": "2026-03-01",
  "effective_to": null,
  "doc_version": "v3",
  "doc_status": "active",
  "acl_groups": ["tenant:t_8f21c0", "role:cs_agent"],
  "lang": "zh",
  "content_hash": "sha256:...",
  "embedding_model": "emb-2026-01"
}
```

面包屑的价值不只是给模型看，**更是给 rerank 看**：一个 chunk 的 `breadcrumb` 里有"2026"和"现行"，cross-encoder 打分会显著不同。Aurora 实测：加面包屑后 nDCG@10 从 0.63 涨到 0.79（同一切分、同一模型）。

**父子块的取舍**：子块（200 token）用于**检索**（精确匹配概率高），父块（1,200 token）用于**注入**（上下文完整）。代价是存储 ×1.6、注入 token ×1.5。经验判据：**当你的失败归因里"切分破坏"占 > 20% 时，父子块的收益就能覆盖它的成本**。

### 20.4.2 混合检索与 RRF：为什么必须两路

纯向量检索在两类查询上系统性失效：

| 查询类型 | 例子 | 向量检索 | BM25 |
| --- | --- | --- | --- |
| 语义近似 | "东西坏了想退" vs "商品质量问题退货" | ✅ 强 | ❌ 弱 |
| 精确术语 | "ERR_4021"、"SKU-88123"、"GB/T 35273" | ❌ 弱（token 化后无意义） | ✅ 强 |
| 型号/编号 | "Aurora-Edge-v2.3.1" | ❌ | ✅ |
| 长句意图 | "我上个月买的那个能退吗，包装拆了" | ✅ | ❌ |

所以两路都要，融合用 **RRF（Reciprocal Rank Fusion）**——它只看排名不看分数，天然免疫两路分数量纲不同的问题：

```
RRF(d) = Σ_i  w_i / (k + rank_i(d))
k = 60（经验值，来自原始论文；工程上 40~80 差别不大）
w_i = 该路的权重（默认 1.0；术语密集场景把 BM25 提到 1.2）
```

**为什么不直接加权分数**：向量相似度是 0~1 的余弦，BM25 是 0~30+ 的无界分。归一化会引入假设，RRF 不需要。

### 20.4.3 混合检索 SQL（pgvector + 全文索引 + RRF，可直接用）

```sql
-- 前提：chunk 表已建
--   CREATE INDEX ON chunk USING hnsw (embedding vector_cosine_ops);
--   CREATE INDEX ON chunk USING gin (tsv);
--   CREATE INDEX ON chunk USING gin (acl_groups);
--   CREATE INDEX ON chunk (tenant_id, doc_id, chunk_index);

WITH q AS (
  SELECT $1::vector(1024)                          AS emb,
         websearch_to_tsquery('simple', $2)        AS tsq,
         $3::text[]                                AS acl,   -- 调用方已算好的可见组
         $4::text                                  AS tenant,
         $5::text                                  AS lang
),
vec AS (
  SELECT c.id,
         ROW_NUMBER() OVER (ORDER BY c.embedding <=> q.emb) AS rnk
  FROM chunk c, q
  WHERE c.tenant_id = q.tenant            -- ① 租户下推
    AND c.acl_groups && q.acl             -- ② 权限下推（数组重叠）
    AND c.lang = q.lang
    AND c.deleted_at IS NULL
    AND c.doc_status = 'active'           -- ③ 版本下推
    AND (c.effective_from <= now())
    AND (c.effective_to IS NULL OR c.effective_to > now())  -- ④ 生效期下推
  ORDER BY c.embedding <=> q.emb
  LIMIT 50
),
kw AS (
  SELECT c.id,
         ROW_NUMBER() OVER (ORDER BY ts_rank_cd(c.tsv, q.tsq) DESC) AS rnk
  FROM chunk c, q
  WHERE c.tenant_id = q.tenant
    AND c.acl_groups && q.acl
    AND c.deleted_at IS NULL
    AND c.doc_status = 'active'
    AND (c.effective_to IS NULL OR c.effective_to > now())
    AND c.tsv @@ q.tsq
  LIMIT 50
),
fused AS (
  SELECT COALESCE(v.id, k.id) AS id,
         COALESCE(1.0 / (60 + v.rnk), 0)
       + COALESCE(1.0 / (60 + k.rnk), 0) AS rrf
  FROM vec v FULL OUTER JOIN kw k USING (id)
)
SELECT f.id, f.rrf, c.doc_id, c.breadcrumb, c.content, c.effective_from
FROM fused f
JOIN chunk c USING (id)
ORDER BY f.rrf DESC
LIMIT 20;   -- 20 进 rerank，最终取 8
```

四个 `WHERE` 条件对应四类事故，**每一条都是"不写就出事"**：

| 条件 | 不写会怎样 |
| --- | --- |
| `tenant_id = q.tenant` | 跨租户召回 = 数据泄露（第 44 章） |
| `acl_groups && q.acl` | 同租户内越权（普通客服看到合同条款） |
| `doc_status = 'active'` | 答废弃文档（引子事故） |
| `effective_to IS NULL OR > now()` | 答过期政策（引子事故） |

> ⚠️ **pgvector 的一个重要工程坑**：HNSW 索引是"近似"检索，加了过滤条件后可能导致候选不足（图遍历时被过滤掉的邻居太多）。表现为"过滤后只返回 3 条，但明明有 50 条符合条件"。解决：调大 `hnsw.ef_search`，或使用新版 pgvector 的迭代索引扫描（iterative scan）能力；Qdrant 这类带 payload filter 的引擎则通过 filterable HNSW 处理。**上线前必须用"大 ACL + 窄过滤"的极端 case 压测**，否则你会发现某些租户的检索质量莫名其妙地差。

### 20.4.4 rerank：花 90ms 买 16 个点的 nDCG

| 阶段 | 候选数 | 延迟 | 边际成本 | 作用 |
| --- | --- | --- | --- | --- |
| 向量召回 | 50 | 15ms | ~0 | 高 recall，低精度 |
| BM25 召回 | 50 | 10ms | ~0 | 术语/型号精确匹配 |
| RRF 融合 | → 20 | 1ms | 0 | 合并两路、去重 |
| **cross-encoder rerank** | 20 → 8 | 90ms | $0.001/次 | **精度大涨，是最划算的一步** |
| LLM 重排 | 10 → 3 | 800ms+ | $0.003 | 只在难例（占 3%）上开 |

算账：rerank 成本 $0.001 × 120 万次/天 = $1,200/天。它带来的收益是"注入的 8 个 chunk 里冗余从 3 个降到 1 个"——省 2 × 400 token × 120 万 = 960M token/天 ≈ $2,880/天。

**净赚 $1,680/天，还顺带把答对率从 71% 提到 84%。** 这是全章最划算的一笔投资。

三个 rerank 的工程细节：

1. **候选数别超过 50**。cross-encoder 是 O(n) 次推理，20 条 → 90ms，50 条 → 220ms。收益在第 20 名之后基本消失。
2. **rerank 必须做超时降级**。超时（比如 300ms）就直接用 RRF 的顺序，**不要失败整条链**。降级后质量掉，但不掉链。
3. **rerank 输入要带 breadcrumb**，不只是 chunk 正文。这是"免费"涨分的地方（见 §20.4.1 的实测数据）。

### 20.4.5 增量索引：三个必须解决的问题

**问题一：只重算变化的 chunk。**

```go
// rag/index.go
func (ix *Indexer) Apply(ctx context.Context, ev DocEvent) error {
    doc := ix.fetch(ev.DocID)
    chunks, err := Split(doc) // 结构感知切分 + 面包屑
    if err != nil { return ix.deadLetter(ev, err) }

    old := ix.loadChunkMeta(ev.DocID)               // content_hash → chunk_id
    var toEmbed []Chunk
    for _, c := range chunks {
        if id, ok := old[c.ContentHash]; ok {        // 内容没变：复用向量
            c.Embedding, c.ID = ix.loadVector(id), id
        } else {
            toEmbed = append(toEmbed, c)
        }
    }
    // 批量 embedding（单次 ≤ 128 条，超时 5s，失败整批重试一次）
    vecs, err := ix.embedder.Embed(ctx, toEmbed, EmbedOpts{Batch: 128, Timeout: 5 * time.Second})
    if err != nil { return ix.deadLetter(ev, err) }

    // 原子切换：写新 partition → 校验数量一致 → 切 alias → 旧版本留 24h
    return ix.atomicSwap(ctx, ev.DocID, chunks, vecs)
}
```

**问题二：删除要删干净。** 文档删除/权限变更时，chunk 的 `doc_status`/`acl_groups` 必须跟着变。漏了这一步，你会得到"用户已撤权但 Agent 还在引用"——这是合规事故，不是质量问题。

**问题三（最狠）：embedding 模型升级必须全量重建。**

```
混用两个模型产生的向量，在同一个 HNSW 索引里 → 空间不可比 → 召回质量塌方式下降
而且它不报错、不告警，只是"有时候检索很准，有时候完全不相关"
```

所以：`embedding_model` 必须作为 chunk 的字段，且**索引按模型版本分桶**（就像 §20.4.3 的 alias 切换）。Aurora 的规则：**新模型上线 = 新索引 + 双跑对比 + 灰度切流，绝不原地重刷**（第 42 章）。

### 20.4.6 多租户权限下推：为什么"查完再过滤"是错的

| 做法 | 后果 | 判定 |
| --- | --- | --- |
| 检索 top-50 → 应用层过滤 ACL | ① 大租户/窄权限场景只剩 3 条，召回骤降；② 越权内容已进入日志、trace、语义缓存 → **泄露已经发生**；③ 白算 47 条 embedding 相似度 | 🔴 禁止 |
| 检索时在 `WHERE` 里下推 | 索引层面就只看得到有权的数据 | 🟢 唯一正确 |
| 独立 collection / 分区表 | 物理隔离，最强；但租户数 >1 万时运维成本高 | 🟡 大客户专属 |

**"查完再过滤"最阴的地方是第二条**：即使你过滤掉了，那 50 条已经进了你的应用内存、可能进了 trace 的 `retrieved_doc_ids` 字段（第 39 章）、可能进了语义缓存的 key（第 24 章）。**只要它进过任何一个持久化介质，你就得按泄露事件处理。**

三档隔离的取舍：

| 档位 | 做法 | 成本 | 适用 |
| --- | --- | --- | --- |
| **共享表 + 行级过滤** | `tenant_id` 进 WHERE + 复合索引 | 最低 | 绝大多数租户（<1 万） |
| **分区表** | 按 `tenant_id` 哈希分区 | 中 | 1 万~10 万租户 |
| **独立索引/collection** | 每租户一个 HNSW | 高（内存 ×N） | 大客户、强合规要求 |

ACL 的建模（`acl_groups`）要注意两件事：

1. **它必须由平台算，不能由文档上传者填**。"这个文档谁能看"是权限系统的问题，不是内容问题。上传者填 ACL = 迟早填错。
2. **ACL 变更要触发索引更新**。用户被移出项目组 → 他的可见组变了 → 所有相关 chunk 的 `acl_groups` 其实不用改（它是文档属性），但**该用户的 `q.acl` 变了**，所以下次查询自动生效。这是 `acl_groups` 设计的精妙处：**把"谁有权"算在查询侧，文档侧只存"属于哪些组"**，避免 N×M 的权限表爆炸。

### 20.4.7 评估：recall@k 不够，要 MRR 和 nDCG

| 指标 | 定义 | 衡量什么 | 适用 |
| --- | --- | --- | --- |
| **recall@k** | 召回的相关文档数 / 全部相关文档数 | 有没有找到 | 知识覆盖率、索引进度 |
| **precision@k** | 召回中相关数 / k | 准不准 | 注入预算控制 |
| **MRR** | `mean(1 / 第一个相关文档的排名)` | **第一个对的排多前** | 单答案问答（客服） |
| **nDCG@k** | `DCG@k / IDCG@k`，`DCG = Σ rel_i / log2(i+1)` | 排序整体质量 | 多答案、有分级相关性 |
| **answer accuracy** | 最终答案对不对（人工/judge） | 端到端 | **唯一真正的指标** |

Aurora 的演进数据（同一评测集，N=500）：

| 阶段 | recall@10 | nDCG@10 | MRR | 答对率 |
| --- | --- | --- | --- | --- |
| 纯向量 top-10 | 0.71 | 0.52 | 0.48 | 58% |
| + BM25 混合（RRF） | 0.84 | 0.63 | 0.61 | 68% |
| + rerank top-20 | 0.84 | 0.79 | 0.77 | 84% |
| + 父子块 | 0.91 | 0.82 | 0.80 | 86% |
| + 面包屑 + 生效期过滤 | 0.93 | **0.88** | **0.86** | **89%** |

**注意第 3 行到第 4 行**：recall 从 0.84 涨到 0.91，答对率只涨 2 个点；而第 5 行 recall 只涨 2 个点，答对率涨了 3 个点——**因为那一行修的是"排序"和"版本"，不是"召回"**。

> 💡 **这张表最想传递的一件事**：recall 是"上游指标"，它到不了 1.0，而答对率才是目标。**别用 recall 汇报 RAG 质量**，它会让整个团队误判。

评估集的构建（详见第 40 章）要点：**从真实 query 采样 + 标注"应该命中哪些 chunk" + 记录当时的知识库版本**。最后这条很重要——知识库变了，评测集的金标就过期了，评测结果不可比。

## 20.5 Java / 分布式经验对照

| 你熟悉的东西 | RAG 里的对应物 | 会咬人的差异 |
| --- | --- | --- |
| Elasticsearch 倒排检索 | BM25 那一路 | 你熟悉的那套只覆盖了"一半" |
| 分库分表 + 路由键 | `tenant_id` 下推 | 路由错了是数据错；这里错了是**越权** |
| 索引重建 + alias 切换 | 增量索引与原子切换 | 多了"embedding 模型版本"这个维度，混用即废 |
| 消息队列的 at-least-once | 文档变更事件 | 重复事件必须幂等（`content_hash` 去重） |
| 缓存一致性 | ACL 变更后的可见性 | ACL 算在查询侧，文档侧不变 → 天然一致 |
| 慢查询治理 | 检索延迟预算 | 900ms 的预算里，rerank 独占 90ms，必须做降级 |
| 数据仓库的分层 | 父子块（ODS/DWD 类比） | 存储翻倍换召回精度 |
| 权限系统（RBAC） | `acl_groups` 下推 | **绝不能"查完再过滤"**，这是泄露级判断 |

三条最会咬人的：

1. **"我做了权限过滤" ≠ "我做了权限下推"**。前者在应用层，后者在 `WHERE` 里。区别在于泄露是否已经发生。
2. **embedding 模型是一个"隐式 schema"**。你在 Java 里换个序列化框架会立刻报错；这里换个 embedding 模型不会报错，只会让召回质量悄悄下降 40%。
3. **chunk 是有状态的**。你改了切分策略，历史 chunk 不会自动更新。必须有"重新切分"的运维能力（按 doc 批量重建），否则你会长期维护两套切分逻辑。

## 20.6 开源坐标

| 项目 | 它做了什么 | 能抄什么 | 你要自己补什么 |
| --- | --- | --- | --- |
| **RAGFlow** | 文档解析（版面分析、表格识别）+ 可视化切分配置 + 引用溯源 | 解析层的工程化（比你手写的 PDF 解析强得多）、chunk 可视化的产品形态 | 多租户 ACL 下推、增量索引编排 |
| **Qdrant** | 向量库 + payload filter（filterable HNSW）+ 混合检索 API | 过滤与向量检索在索引层融合的做法 | ACL 语义（哪些组可见）要自己建模 |
| **pgvector**（PostgreSQL） | `vector` 类型 + HNSW/IVFFlat + 与 SQL 的天然结合 | 一条 SQL 搞定"向量 + 过滤 + 业务表 JOIN" | 大规模下的过滤召回退化，要调 `ef_search` 或迭代扫描 |
| **Cohere Rerank** | 托管 cross-encoder 重排 | 直接买，别自己训 | 数据出境与延迟（第 31 章） |
| **Elasticsearch / OpenSearch** | BM25 + 近年加向量（kNN） | 混合检索的一体化方案 | 向量侧性能弱于专用库 |
| **Ragas** | RAG 评估指标（context recall/precision、faithfulness） | 评估指标定义与实现 | 金标要自己做，且要版本化 |

> 一致的判断：**解析和切分可以买，权限和评估必须自己建。** 前者是通用工程，后者是你的业务与合规。

## 20.7 事故清单

- [ ] **事故 A：三份版本政策共存、chunk 无生效期 → 答 30 天（实际 7 天），1,100 次错误。**
      兜底：面包屑 + `effective_from/to` 下推到 SQL + `doc_status` 字段 + 上线前"多版本共存"测试用例。
- [ ] **事故 B：应用层过滤 ACL → 越权内容进了 trace 与语义缓存。**
      兜底：`WHERE` 下推 + 后置二次校验 + trace 里 `retrieved_doc_ids` 只记过滤后的。
- [ ] **事故 C：embedding 模型升级原地重刷 → 新旧向量混在一个索引，召回质量塌方且不报错。**
      兜底：`embedding_model` 入库 + 按版本分桶 + 新索引双跑 + 灰度切流。
- [ ] **事故 D：HNSW 加过滤后候选不足，某几个租户检索质量莫名很差。**
      兜底：调 `ef_search` / 用迭代扫描；上线前用"大 ACL + 窄过滤"压测；监控"过滤后候选数"这个指标。
- [ ] **事故 E：文档更新后 3 天还在答旧内容。**
      兜底：变更事件驱动索引 + "文档更新到可检索"延迟 SLO（<10 分钟）+ 告警。
- [ ] **事故 F：rerank 服务超时，整条检索链失败 → 全站 5xx。**
      兜底：rerank 超时降级为 RRF 顺序（300ms 硬超时），检索链永不因单点失败整体挂掉。

## 20.8 一页速记

| 关键词 | 必须记住的结论 |
| --- | --- |
| **归因优先** | 切分 24% / 版本 21% / 缺失 18% / 幻觉 16% / 排序 15%；先归因再动手 |
| **recall 是上游指标** | 别用它汇报质量；答对率才是目标（recall 0.93 对应答对 89%） |
| **面包屑** | chunk 必须带标题路径 + 生效期 + 版本；nDCG 从 0.63→0.79 |
| **四当下推** | 租户 / ACL / 版本状态 / 生效期，四条不进 WHERE 就出事 |
| **查完再过滤 = 泄露** | 过滤掉的 50 条已进内存与 trace，按泄露事件处理 |
| **RRF 不用分数** | `Σ 1/(60+rank)`，免疫量纲差异；权重按场景调 |
| **rerank 最划算** | $1,200/天成本，省 $2,880/天注入 + 答对率 +16 点 |
| **注入成本是检索的 16 倍** | 优化重点在"少注入、注入对的"，不是"检索快一点" |
| **embedding 是隐式 schema** | 换模型必须全量重建 + 分桶，混用不报错但会废 |
| **父子块** | 失败归因里"切分破坏" >20% 时上，存储 ×1.6 换召回精度 |
| **增量索引三段** | 复用未变 chunk 的向量 / 删除要干净 / 模型升级全量重建 |
| **延迟预算** | 全链 196ms，预算 800ms，余量留 4 倍给规模增长 |

## 20.9 自检题

1. **用户问「最新的退款政策是什么」，你的 RAG 答了旧政策，但 recall@10 = 0.95。你怎么定位？**
   > 要点：① recall 高说明"找到了相关文档"，问题在"相关"没包含"现行"；② 检查 chunk 是否有 `effective_from/to` 与 `doc_status`，以及这两条是否下推到 SQL；③ 检查面包屑是否进 rerank 输入（没有的话 rerank 只看到正文，分不出新旧）；④ 修完后做一条回归用例："同一主题多版本共存"必须作为固定测试场景。

2. **老板说「rerank 一次 90ms，太慢了，去掉吧」。你的反驳里要有哪三个数字？**
   > 要点：① nDCG@10 从 0.79 掉到 0.63，答对率从 84% 掉到 68%；② 去掉后注入冗余 chunk 增加，多花 $2,880/天 vs rerank 成本 $1,200/天，净亏；③ 90ms 占 800ms 预算的 11%，且它可以硬超时降级（300ms），去掉才是真的"没有兜底"。

3. **你说"我们的 RAG 做了多租户隔离"，请给出可验证的证据。**
   > 要点：① SQL 里 `tenant_id` 与 `acl_groups` 在 `WHERE` 而非应用层；② 有一个测试用例：构造 B 租户的文档，用 A 租户的身份检索 1000 次，命中 0 次；③ trace 里 `retrieved_doc_ids` 全部属于本租户（可离线审计）；④ 缓存 key 含 `tenant_id`（第 24 章），否则语义缓存会跨租户命中。
