## 4.1 引子：三张拼不起来的架构图

Aurora 立项第四个月，我们做了一次很尴尬的评审。三个角色各画了一张图：

- **业务架构师**画的是「客服 / 编码 / 数据 三类 Agent，共用一套知识库和工具平台」——很干净，但没有任何一个框里写着「钱怎么算」。
- **SRE** 画的是「网关 → 服务 → 数据库」——很标准，但 30 秒的 Run 在他图里是一条竖直的箭头，看不出「中间断了怎么办」。
- **财务** 画的是「用量 → 计量 → 账单 → 收款」——很清楚，但完全看不出「缓存命中该打几折」。

三张图各自都对，合起来是错的。因为**它们描述的是同一套系统的三个不同切面，而这套系统没有一张统一的「面」的定义**。结果就是：

- 业务加了「语义缓存」提性能，没人告诉财务 → 缓存命中按全价计费，客户投诉多收钱；
- SRE 为了降 P99 把长任务挪到低优先级队列 → 业务不知道，编码 Agent 的用户以为卡死；
- 财务要求「实时看到成本」→ 业务侧才发现流式场景下 token 数是边生成边知道的，实时成本根本算不准。

> 🎯 本章要交付的东西：**一套「面」的定义（谁负责什么、谁能调谁），加一份能算数的 Aurora 参数表。** 有了它，上面三个角色画的图会变成同一张图的三层视图。

## 4.2 贯穿案例 Aurora：完整参数设定

**Aurora** 是企业级多租户 Agent 平台，三类 Agent（客服 / 编码 / 数据分析），三种交付形态（Web / IDE 插件 / IM 机器人）。

### 4.2.1 基准参数（全书复用）

| 参数 | 取值 | 说明 / 推导 |
| --- | --- | --- |
| 注册租户数 | **100,000** | 合同口径；其中日活租户 12,000（12%） |
| 接入面峰值请求 | **5,000 QPS** | 见 §4.2.2 的端点分布，**不是 Run 数** |
| 新建 Run 峰值 | **120 /s** | 占接入面 2.4%；这是真正决定容量的数字 |
| 新建 Run 稳态 | **25 /s** | 日均 216 万 Run（25 × 86,400） |
| 单 Run 平均时长 W | **30 秒** | 客服 12s / 编码 180s / 数据 60s 的加权平均 |
| 单 Run 输出 | **800 字**（≈530 token） | 计费口径含工具 JSON ≈ 1,200 token |
| 单 Run 输入 | 原始 **44,000 token** | 5 步模型调用，历史逐步累积 |
| 前缀缓存命中率 | **68%** | 计费等效输入降到 17,100 token |
| 路由比例 | 小模型 72% / 大模型 28% | 按任务复杂度与质量门禁 |
| 单 Run 成本 | **$0.0218** | 见 §4.2.3 算式 |
| 日均成本 | **$47.1k**（≈ $1.41M/月） | 216 万 × $0.0218 |
| 在途 Run（稳态） | **750** | L = λW = 25 × 30 |
| 在途 Run（峰值） | **3,600** | 120 × 30（假设全部放进来） |
| 每 Run 事件数 | **42** | 见第 6 章事件清单 |
| 日均事件 | **9,072 万条** | 216 万 × 42 |
| 模型供应商 | 2 家 API + 1 套自建 vLLM | 自建承载小模型的 30% 流量 |
| 部署 | 3 可用区，单区双机房 | 数据驻留：CN / EU 两套 |

> ⚠️ 这里有一个必须纠正的直觉：**「峰值 5k QPS」不等于「每秒 5,000 次 Run」。** 两者差 41.7 倍。90% 的容量估错，都来自把网关请求数当成业务吞吐量。

### 4.2.2 5,000 QPS 打在哪

| 类别 | 端点 | QPS | 占比 | 归属面 |
| --- | --- | --- | --- | --- |
| 写 | `POST /v1/runs` | 120 | 2.4% | 接入 → 运行时 |
| 写 | `POST /v1/runs/{id}/tool_results` | 400 | 8.0% | 接入 → 工具网关（客户端工具回传） |
| 写 | `POST /v1/runs/{id}/cancel`、`/approve` | 30 | 0.6% | 接入 → 运行时 |
| 读 | GET 状态 / 历史 / 列表 / 附件签名 | 1,050 | 21.0% | 接入（只读，可缓存） |
| 读 | `GET /v1/runs/{id}/events`（SSE 建连） | 80 | 1.6% | 接入 → 流式编码 |
| 流写出 | SSE 事件包写出 | 3,120 | 62.4% | 流式编码（5,040 连接 × 0.62 包/s） |
| 其它 | healthz / token 刷新 / CORS 预检 | 200 | 4.0% | 接入 |
| — | **合计** | **5,000** | 100% | — |

结论很清楚：**接入面 62% 的负载是「把事件写出去」，8% 是「客户端工具回传」。** 这两块决定了你的网关长什么样（第 5、7 章），而编排框架跟它们一点关系都没有。

### 4.2.3 单 Run 成本算式

```
原始输入 44,000 tok，前缀命中 68%
计费等效输入 = 44,000 × (0.32 + 0.68 × 0.10) = 44,000 × 0.388 ≈ 17,100 tok
输出 = 1,200 tok

小模型（72%）：$0.15/M in, $0.60/M out
  = 17,100 × 0.15/1e6 + 1,200 × 0.60/1e6
  = 0.00257 + 0.00072 = $0.00329

大模型（28%）：$3.00/M in, $15.00/M out
  = 17,100 × 3.00/1e6 + 1,200 × 15.00/1e6
  = 0.05130 + 0.01800 = $0.06930

加权 = 0.72 × 0.00329 + 0.28 × 0.06930 = 0.00237 + 0.01940 = $0.0218 / Run
```

注意这个数字的杠杆点：**28% 的流量吃掉了 89% 的钱**（0.0194 / 0.0218）。所以第 26 章的「路由」和第 24 章的「缓存」，比第 3 章的任何优化都值钱 100 倍。

### 4.2.4 三类 Agent 的差异如何改变架构

这是本章最实用的一张表——**它直接决定了你必须做「舱壁」而不是「一套逻辑通吃」**：

| 维度 | 客服 Agent | 编码 Agent | 数据分析 Agent |
| --- | --- | --- | --- |
| 单 Run 时长 P50 / P99 | 12s / 45s | **180s / 25min** | 60s / 8min |
| 步骤数 | 3~8 | **20~80** | 5~15 |
| 工具形态 | 只读查询 + 少量写（退款） | 文件读写 / Bash / Git | SQL 执行 / 绘图 |
| 沙盒 | 不需要 | **必须**（任意代码） | **必须**（SQL + 数据权限） |
| 审批 | 写操作强制 | 危险命令强制 | 大额查询 / 导出强制 |
| 流式 | 逐字（强） | 状态为主（中） | 进度 + 结果表（中） |
| 主 SLO | TTFT + 成功率 | **长任务不丢 + 隔离** | 查询正确性 + 权限 |
| 成本量级 | $0.004/Run | $0.82/Run | $0.15/Run |
| 对架构的硬要求 | 交互队列优先、低 TTFT | 独立异步队列 + 持久化 + 沙盒池 | 只读副本 + 权限下推 + 结果截断 |
| 失败代价 | 一次投诉 | 一次误删 / 误提交 | 一次数据泄露 |

从这张表能直接推出三条架构决策：

1. **队列必须分类**。编码 Agent 的 25 分钟 Run 绝对不能进交互队列，否则一次 `git push` 排队就把客服全堵死（第 11 章）。
2. **沙盒必须是共享池，不是每请求一个**。编码 + 数据分析占 34% 流量，冷启动 2~8 秒，按请求创建等于把 P99 拉爆（第 29 章）。
3. **SLO 必须分类**。你不可能给 25 分钟的 Run 承诺 99.5% 成功率，那是另一个成本量级。

| # | 依赖铁律 | 为什么 | 违反后的具体故障 |
| --- | --- | --- | --- |
| R1 | **依赖只能向下** | 保证每层可独立扩缩容与发布 | 运行时↔管道互调 → 循环依赖 → 扩管道要连带扩运行时 |
| R2 | **运行时不得同步 RPC 控制面** | 控制面是低频强一致系统，不该在秒级路径上 | 控制面发布 → 全站 Run 失败（最经典的架构事故） |
| R3 | **管道不得直连存储** | 所有写必须经事件追加，否则失去真相源 | 计费漏单、无法回放（第 6、27 章） |
| R4 | **治理面只被调用，不调用业务** | 否则治理成为单点与循环依赖 | 账本服务挂了 → 业务全挂 |
| R5 | **内核/运行时不得 import 业务包** | 内核要能独立发布与灰度 | 内核升级要连带几十个业务服务一起发 |

这五条可以写成 CI 检查，成本极低，收益极大：

```go
// tools/archcheck/main.go —— 放进 CI，违反即 fail build
package main

var rules = []Rule{
	// R1/R3：管道包不得 import 任何存储驱动
	{From: "internal/pipeline/...", Deny: []string{"internal/store/...", "internal/queue/..."}},
	// R2：运行时不得 import 控制面客户端
	{From: "internal/runtime/...", Deny: []string{"internal/controlplane/client/..."}},
	// R4：治理面不得 import 业务包
	{From: "internal/governance/...", Deny: []string{"internal/agent/..."}},
	// R5：内核不得 import 业务包
	{From: "internal/kernel/...", Deny: []string{"internal/agent/...", "internal/pipeline/..."}},
}

func main() {
	violations := check(rules) // 用 go list -deps 拿包依赖图
	if len(violations) > 0 {
		for _, v := range violations {
			fmt.Printf("ARCH VIOLATION %s: %s -> %s\n", v.Rule, v.From, v.To)
		}
		os.Exit(1)
	}
}
```

> 💡 这张依赖图真正的价值不在「好看」，在 **R2 那一条**：它决定了「控制面挂了，Aurora 还能不能回答用户」。答案必须是「能」——控制面挂掉只是不能改配置，已经在跑的 Agent 用本地快照继续跑。这条设计每年至少救一次发布事故。

## 4.4 关键设计

### 4.4.1 五个面的职责边界

| 面 | 职责 | 有状态? | 峰值副本 | 可用性目标 | 挂了会怎样 |
| --- | --- | --- | --- | --- | --- |
| ① 接入面 | 鉴权、限流首跳、协议转换、SSE 编码、多端适配 | 无 | 5 | **99.95%** | 全站不可用（最高危） |
| ② 数据面 | 存储、队列、模型服务、向量、对象 | 是 | 按组件 | 99.9% | 读写失败，可降级读缓存 |
| ③ 运行时 | Run 状态机、调度、worker、工具网关、沙盒 | 进程无状态 | 6 | 99.9% | Run 卡住但可恢复（状态在库） |
| ④ 治理面 | 限流、配额、账本、审计、风控 | 账本有状态 | 3（+分片） | 99.95% | **不能拒绝服务**：降级为「本地预算 + 事后补账」 |
| ⑤ 控制面 | 租户、Agent 注册、策略、灰度 | 强一致 | 3 | 99.95% | 不能改配置，业务继续跑（设计目标） |
| ⑥ 数据闭环 | trace、指标、评估、回流 | 是 | — | 99.5% | 不影响线上，只影响迭代速度 |
| ⑦ 管道 | 前处理 → … → 后处理 | 无 | 按阶段 | 99.9% | 前处理挂 → 走降级直通（有风险开关） |
| ⑧ 三翼 | 可观测 / 缓存降级 / 安全防御 | 组件级 | — | — | 必须「降级而非停摆」 |

**这张表里最容易被做错的是④治理面**。很多团队把「配额服务」做成同步强依赖：配额服务一抖，全站 503。正确做法是**双层配额**：本地令牌桶（进程内，最终一致）+ 中心配额（权威账本，异步校准）。本地桶允许超发 5%，用事后补账收敛——**宁可少收 5% 的钱，也不能因为账本抖动拒绝服务**。

### 4.4.2 SLO 与错误预算

SLO 不是「越高越好」，是**用错误预算换发布速度**。Aurora 的线上 SLO：

| 类别 | SLI | 目标 | 错误预算（月） | 预算耗尽后 |
| --- | --- | --- | --- | --- |
| 可用性 | 接入面成功响应率 | 99.95% | 21.6 分钟不可用 | 冻结发布，只允许修复 |
| 交互质量 | 交互类 Run 成功率（排除用户取消） | **99.5%** | 32.4 万次失败 | 停止灰度，回滚最近一次 |
| 延迟 | TTFT P95 | **≤ 1.5s** | 5% 请求可超 | 路由降级到小模型 + 缩短上下文 |
| 延迟 | TTFT P99 | ≤ 3.0s | — | 告警（不冻结） |
| 延迟 | 端到端事件延迟 P99（产生→客户端可见） | ≤ 300ms | 1% 可超 | 检查反代与合批参数 |
| 取消 | 取消生效 P95 | ≤ 1s | — | 检查状态机与 worker 抢占 |
| 计费 | 计费差错率 | **≤ 1e-5** | 每百万笔 ≤ 10 笔 | P0，账本逻辑回滚 + 人工补账 |
| 审计 | 审计事件完整率 | **100%** | 零容忍 | P0，立即熔断相关写入路径 |
| 批处理 | 批处理类 Run 成功率 | 99.0% | 65 万次 | 允许，可延后修 |
| 回放 | 任意 Run 可完整回放率 | ≥ 99.99% | 216 次/月 | P1，检查事件缺口 |


### 4.4.3 容量算式：从 SLO 反推副本数

不要「先定副本再试」，要**用 Littles 定律先算，再用压测校准**：

```go
// capacity/calc.go
package capacity

import "math"

type Peak struct {
	RunRPS            float64 // 新建 Run 速率 /s
	RunDurationS      float64 // 平均 Run 时长
	LLMTimeRatio      float64 // Run 时间中「等模型」占比
	EventsPerRun      float64
	InflightPerReplica float64 // 单副本可安全承载的在途 Run
	N2                int     // N+2 冗余
	SelfHostRatio     float64 // 自建模型承载比例
	OutTokensPerRun  float64
	DecodeTokPerGPU  float64
	PrefixHitRatio   float64
	PrefillTokPerGPU float64
}

func Compute(p Peak) map[string]float64 {
	inflight := p.RunRPS * p.RunDurationS                 // Littles: L = λW
	inflightLLM := inflight * p.LLMTimeRatio              // 并发模型调用
	eventRate := inflight * p.EventsPerRun / p.RunDurationS
	runtimeReplicas := math.Ceil(inflight/p.InflightPerReplica) + float64(p.N2)

	// GPU：decode 按输出 token 速率，prefill 按未命中前缀的输入 token 速率
	decodeGPU := p.SelfHostRatio * p.RunRPS * p.OutTokensPerRun / p.DecodeTokPerGPU
	prefillTokPS := p.SelfHostRatio * p.RunRPS * 44000 * (1 - p.PrefixHitRatio)
	prefillGPU := prefillTokPS / p.PrefillTokPerGPU

	return map[string]float64{
		"inflight_runs":    inflight,        // 3600
		"inflight_llm":     inflightLLM,     // 1980
		"events_per_sec":   eventRate,       // 5040
		"runtime_replicas": runtimeReplicas, // 6
		"gpu_decode":       decodeGPU,       // ~17
		"gpu_prefill":      prefillGPU,      // ~25
	}
}
```

代入 Aurora 峰值参数（`120, 30, 0.55, 42, 3000, 2, 0.30, 1200, 2500, 0.68, 20000`），得到：

| 指标 | 结果 | 结论 |
| --- | --- | --- |
| 在途 Run（峰值） | **3,600** | 这是容量规划的第一性数字 |
| 并发模型调用 | **1,980** | 决定模型网关连接池与 provider 配额申请量 |
| 事件写出速率 | **5,040 /s** | 决定 Kafka 分区数与 ClickHouse 写入批大小 |
| 运行时副本 | `ceil(3600/3000) + 2 = 4` → 再留滚动更新裕度 → **6** | 单副本 3,000 在途 Run 是压测得出的安全线 |
| GPU（decode，自建 30%） | `0.3 × 120 × 1,200 / 2,500 ≈` **17 卡** | 输出 token 速率 = 到达率 × 每 Run 输出；单卡 ~2,500 tok/s |
| GPU（prefill，自建 30%） | `0.3 × 120 × 44,000 × 0.32 / 20,000 ≈` **25 卡** | 前缀命中 68% 直接把 prefill 算力砍掉约三分之二 |
| GPU 合计（峰值 + 30% 余量） | `(17 + 25) × 1.3 ≈` **55 卡** | 与第 46 章的 GPU 池化方案对齐 |

> 🩸 **一个必须记住的容量陷阱**：上面所有数都是「按平均值算的」。而 SLO 是 P99。**平均值只能用来算钱，不能用来算副本。** 实际副本数要在算出来的基础上乘 P99/P50 的比值（Aurora 是 45s/12s ≈ 3.75 倍），再靠队列削峰——这就是第 11 章存在的理由。

### 4.4.4 存储量账（决定第 45 章的选型）

| 数据 | 日增量 | 压缩/折算后 | 保留期 | 存放 |
| --- | --- | --- | --- | --- |
| 事件（42 条/Run） | 9,072 万条，约 109 GB | ClickHouse + zstd ≈ **13.6 GB/日** | 90 天热 | ClickHouse |
| Run 主表 | 216 万行 | ≈ 2.1 GB/日 | 永久（冷归档） | Postgres（按月分区） |
| 上下文快照 | 216 万 × 40 KB = 86 GB | 只对 5% 采样存全量 | 30 天 | S3 |
| 审计哈希链事件 | 约 600 万条 | append-only，不压缩 | **3 年** | 对象存储 WORM |
| Trace span | 216 万 × 14 span | 采样 20% | 14 天 | ClickHouse / 第三方 |
| 附件 | 平均 3% Run 带附件 | — | 90 天 | S3 |

算一下热存总量：`13.6 GB × 90 + 2.1 GB × 90 + 审计 ≈ 1.4 TB`。**这个量级用 ClickHouse 单集群完全撑得住，不需要上湖仓**——很多团队在这一步过度设计了。

## 4.5 Java / 分布式经验对照：五个面的映射

| 你的经验 | Aurora 对应面 | 关键差异 |
| --- | --- | --- |
| Spring Cloud Gateway + Nginx | ① 接入面 | 多了 SSE 流式编码、断线续传、`Last-Event-ID` |
| Spring Cloud Config / Nacos | ⑤ 控制面 | 配置项从「阈值」变成「会改变模型行为的提示词与路由」；**必须支持快照离线** |
| Sentinel 控制台 + Dashboard | ④ 治理面 | 多了账本（钱）与审计（责）；且治理面**不能被业务同步强依赖** |
| 业务微服务 | ③ 运行时 | 进程无状态，状态必须是事件流（不能是 Redis KV） |
| MySQL/Redis/Kafka | ② 数据面 | 多了一个「模型服务」——它是有配额、有版本、会滚动的外部依赖 |
| ELK + SkyWalking | ⑥ 数据闭环 | span 语义多了 `gen_ai.*`（模型、token、成本、提示词版本） |
| 单元测试 + 集成测试 | ⑦ 管道 | 管道是「有副作用的过滤器链」，且能撤回已输出内容 |

## 4.6 开源坐标：平台架构这一层，开源给了什么

| 层 | 开源对应 | 能抄什么 | 抄不到什么 |
| --- | --- | --- | --- |
| 整体平台形态 | **Dify**（应用/工作流/知识库/运营界面）、**Coze**（Bot 编排 + 插件市场） | 应用装配的产品化思路、DSL 设计、界面信息架构 | 多租户计费深度、审计合规、Run 级调度；它们更像「平台的一个 UI 层」 |
| 接入/协议 | OpenAI Responses API 的资源模型 | `runs` 作为资源、`previous_response_id` 的状态语义 | 你的多租户配额、灰度、审计 |
| 运行时 | Temporal / Restate / DBOS | 持久化执行、确定性重放的工程细节 | 「模型非确定性」下的重放策略（第 12 章） |
| 数据面 | ClickHouse / Postgres / Kafka / Qdrant | 成熟组件直接用 | 事件 schema 与分区键要自己设计（第 45 章） |
| 治理 | LiteLLM（计价与 fallback）、Sentinel（限流） | 价格表、路由与 fallback 策略 | 账本、对账、退款（第 27 章） |
| 可观测 | Langfuse / Phoenix / OTel GenAI | Trace 模型与 `gen_ai.*` 约定 | 审计级不可篡改（第 31 章） |

> 🎯 一句话：**开源能给你「平台长什么样」，给不了「平台怎么不死」。** Aurora 这套五面划分，本质是把「不死」的部分单独划出来当一等公民。

## 4.7 事故清单

- [ ] **事故 1：控制面依赖在线路径。** 现象：配置中心发布，全站 Run 失败 8 分钟。→ 根因：违反 R2。→ 兜底：运行时只读本地快照；控制面变更走订阅推送，推送失败降级为「下个周期拉取」。
- [ ] **事故 2：容量按 QPS 估。** 现象：按 5k QPS 压测通过，上线后 3,600 在途 Run 时 P99 从 12s 涨到 90s。→ 根因：压的是短请求，不是 30 秒长 Run。→ 兜底：压测脚本必须模拟真实 Run 时长分布与流式；容量指标用「在途 Run」。
- [ ] **事故 3：SLO 一刀切。** 现象：给编码 Agent 承诺 99.5% 成功率，为了达标堆了 3 倍资源，毛利转负。→ 根因：没按 Agent 类分类 SLO。→ 兜底：三类 Agent 三套 SLO；长任务用「不丢 + 可续」代替「成功率」。
- [ ] **事故 4：治理面同步强依赖。** 现象：配额服务抖动 → 全站 503。→ 根因：单层配额 + 同步校验。→ 兜底：本地令牌桶 + 中心账本异步校准，允许 5% 超发。
- [ ] **事故 5：数据闭环写回在线路径。** 现象：离线评估任务把 ClickHouse 打满，线上查询超时。→ 根因：资源未隔离。→ 兜底：读副本 + 独立资源池（舱壁，第 28 章）。
- [ ] **事故 6：存储过度设计。** 现象：为了 1.4 TB 事件上了湖仓一体，半年没跑通。→ 根因：没算量就选型。→ 兜底：先算 §4.4.4 那张表，再选型。

## 4.8 一页速记

| 关键词 | 必须记住的结论 |
| --- | --- |
| 基准参数 | 10 万租户 / 日活 1.2 万 / 接入 5k QPS / 新建 Run 120 QPS / 单 Run 30s / 800 字 |
| 最重要的换算 | 5,000 接入 QPS = **120 Run/s**，两者差 41.7 倍；容量看「在途 Run」不看 QPS |
| 成本关键 | 28% 的大模型流量吃掉 89% 的钱 → 路由与缓存优先于一切 |
| 五个面 | 接入 / 数据 / 运行时 / 治理 / 控制 + 管道 + 三翼 + 数据闭环 |
| 依赖铁律 | 只能向下；**运行时不得同步依赖控制面**；管道不得直连存储 |
| 最易做错 | 把配额/账本做成同步强依赖 → 治理面抖一下全站 503 |
| SLO 分类 | 交互 99.5% / 批处理 99.0% / 计费差错 1e-5 / 审计 100% |
| 容量方法 | 先 Littles 定律算，再乘 P99/P50 比，最后靠队列削峰 |
| 存储量级 | 事件 13.6 GB/日（压缩后），90 天 1.4 TB，单集群够，别过度设计 |
| 一句话 | **架构图的价值不在框，在箭头的方向和「禁止」的那几条。** |

## 4.9 自检题

1. **Aurora 峰值 5,000 QPS，你的同学说「我们按 5k QPS 设计服务端，单实例 2k QPS，3 个副本够了」。错在哪？**
   > 要点：三处错。① 5k QPS 里 62% 是流式事件写出，需要长连接与不同容量模型；② 真正约束容量的是 3,600 个在途 Run（含 30 秒生命周期与内存/goroutine 占用），不是瞬时 QPS；③ 没算 N+2 与滚动更新裕度。正确算法：在途 Run → 单副本安全并发 → `ceil(3600/3000)+2`。

2. **为什么说「控制面挂掉时业务必须继续跑」是一条架构铁律，而不是一句口号？**
   > 要点：因为控制面的可用性必然低于数据面（它要发版、要迁移 schema、要做审批），如果在线路径同步依赖它，就把控制面的故障率乘到了每一次 Run 上。实现手段是「配置快照 + 增量订阅 + 本地缓存」，故障时的行为是「不能改配置，但已有 Agent 正常运行」。这也是 K8s 里 ConfigMap 挂载 vs API Server 调用的区别。

3. **三类 Agent 为什么不能共用一套 SLO 与队列？给出至少两个会炸的具体场景。**
   > 要点：场景一：编码 Agent 的 25 分钟 Run 进交互队列 → 队列深度暴涨 → 客服 TTFT 从 1.2s 到 30s。场景二：给 25 分钟 Run 承诺 99.5% 成功率 → 需要 3 倍冗余与热备沙盒 → 单 Run 成本从 $0.82 到 $2.4，毛利转负。结论：队列分类（优先级 + 独立并发池）+ SLO 分类（长任务用「不丢 + 可续传」而非「成功率」）。
