## 14.1 引子：把并发从 100 调到 500，P99 从 4 秒变成 40 秒

一个很典型的下午。你的 Agent-Server 在压测里表现良好：100 并发，TTFT P99 = 4s。产品说「能不能再快点」，运维说「CPU 才 30%，扩一倍吧」。你把 worker 池从 100 调到 500。

结果：

```
并发 100 → 500 之后
吞吐（Run/s）：  42  →  46      （+9.5%，几乎没动）
TTFT P50：      0.9s → 3.8s     （×4.2）
TTFT P99：      4.0s → 41.0s    （×10.3）
上游 429 率：    0.1% → 18%     （×180）
CPU 使用率：     30%  →  34%    （几乎没动）
```

**CPU 没动、吞吐没涨、延迟爆了 10 倍。** 这就是最典型的「把并发度当旋钮拧」的后果。

根因只有一句话：**你增加的不是「并行能力」，是「排队人数」**。模型服务那边的处理能力是一个固定值，你多塞进去的 400 个并发请求，全都在模型侧的队列里等——而它们**占着你的 goroutine、占着你的内存、占着你的连接**，把本来能快速返回的那 100 个请求也一起拖慢了。

> 🩸 这里有个新手一定会犯的直觉错误：**「CPU 利用率低 = 还有余量」**。在 Agent 系统里，CPU 利用率低恰恰是常态（你在等网络），它是**最没有信息量的指标**。用 CPU 做扩缩容决策，等于闭着眼睛开车。

## 14.2 三层并发度：你只能控制中间那层

| 层 | 你控制的参数 | 上限由谁决定 | Aurora 典型值 | 超了会怎样 |
| --- | --- | --- | --- | --- |
| **L1 接入并发** | 长连接数、单连接 QPS、网关 worker 数 | fd、内核参数、内存 | 10 万 SSE 长连接 | `EMFILE`、`TIME_WAIT` 堆积、网关 OOM |
| **L2 服务并发** | goroutine / 信号量 / 队列深度 | **你的内存 + 下游配额** | 4,800 in-flight Run | 内存暴涨、GC 停顿、排队雪崩 |
| **L3 模型并发** | `max_num_seqs`、TPM/RPM 配额 | 引擎显存 / 供应商合同 | 2,890 并发 LLM 调用 | 429、引擎 OOM、TTFT 爆 |
| **L3' 工具并发** | 工具侧信号量 | 第三方 API 限流 | 800 | 工具超时、熔断、级联失败 |

**核心结论**：L1 是运营问题，L2 是**你能自由调的**，L3 是**你必须服从的**。调度器的全部工作，就是让 L2 始终贴着 L3 的容量跑，而不是超过它。

### 账本：8760 个在途 Run 是怎么算出来的，以及它为什么不可能被满足

先按 Littles 定律算需求上限：

```
峰值 Run 创建速率 λ = 300 Run/s
平均 Run 时长 W = 30s
→ 稳态在途 Run = 300 × 30 = 9,000 个
```

单 Run 里「等模型」的时间占比约 60%（6 次调用 × 3s 平均响应 / 30s），所以：

```
需要并发 LLM 调用 = 9,000 × 0.6 = 5,400
```

现在算模型侧到底能给多少：

```
自建池：10 引擎 × max_num_seqs 256 × 目标利用率 0.85 = 2,176 槽位
外部 provider：TPM 配额 60,000,000，平均单次调用 8,400 token(in+out)，W_llm = 6s
  C_api = TPM × W_llm / (60 × avg_tokens)
        = 60e6 × 6 / (60 × 8,400)
        = 714 并发
合计 C_model = 2,176 + 714 = 2,890
```

**5,400 的需求 vs 2,890 的供给，缺口 47%。**

这个缺口不是「加机器」能解决的（加 10 个引擎要多 10 张 H100），它只有三条出路：

| 出路 | 手段 | 代价 |
| --- | --- | --- |
| ① 削峰 | 准入限流 + 排队，把 L2 压在 4,800 | 用户等待，需排队位置回传（第 11 章） |
| ② 提密度 | 路由到小模型 / 缩短输出 / 打穿前缀缓存 | 质量下降，需要评测门禁（第 26 章） |
| ③ 降级 | 非核心场景走模板 / 异步化 | 体验降级，要有降级阶梯（第 25 章） |

> 💡 **反推出来的工程结论**：`C_run = C_model / llm_time_ratio = 2,890 / 0.6 = 4,817`。这个 4,817 就是你 L2 的硬上限。**调度器的任务不是让 9,000 个 Run 都跑起来，而是让 4,817 个跑得漂亮、剩下的 4,183 个有序排队而不是一起超时。**

## 14.4 关键设计

### 14.4.1 自适应并发闸门

```go
// Gate：可动态调整上限的并发闸门。
// 注意：sync.Cond 不支持 ctx 取消，生产实现建议用 buffered chan + 定时重试，
// 或在等待处包一层 select 轮询（本例为可读性做简化）。
type Gate struct {
	mu      sync.Mutex
	cond    *sync.Cond
	limit   int
	inUse   int
	metrics *Metrics
}

func NewGate(initial int, m *Metrics) *Gate {
	g := &Gate{limit: initial, metrics: m}
	g.cond = sync.NewCond(&g.mu)
	return g
}

func (g *Gate) Acquire() {
	g.mu.Lock()
	for g.inUse >= g.limit {
		g.metrics.GateWaitTotal.Inc()
		g.cond.Wait()
	}
	g.inUse++
	g.mu.Unlock()
	g.metrics.Inflight.Inc()
}

func (g *Gate) Release() {
	g.mu.Lock()
	g.inUse--
	g.cond.Signal()
	g.mu.Unlock()
	g.metrics.Inflight.Dec()
}

// AIMD 调参：加性增、乘性减。这是 TCP 拥塞控制借过来的，用在模型侧配额上极其合适。
func (g *Gate) Tune(ttftP95, target time.Duration, rate429 float64, cMin, cMax int) {
	g.mu.Lock()
	defer g.mu.Unlock()
	switch {
	case rate429 > 0.01: // 上游开始 429，立刻乘性减
		g.limit = max(cMin, int(float64(g.limit)*0.7))
	case ttftP95 > target*3/2: // 延迟明显超标，温和减
		g.limit = max(cMin, g.limit-g.limit/10)
	case ttftP95 < target: // 有余量，加性增（每次 +5，避免震荡）
		g.limit = min(cMax, g.limit+5)
	}
	g.cond.Broadcast()
}
```

三个设计要点，抄的时候别丢：

1. **`cMax` 必须设成一个硬上限**（本例 4,817），否则模型侧偶发变快时闸门会一路涨过头，然后被 429 打回来，形成锯齿。
2. **减要快、加要慢**。乘性减（×0.7）+ 加性增（+5）是经过 40 年验证的稳定组合；反过来（快增慢减）必然震荡。
3. **`Tune` 里要 `Broadcast`**，否则调大上限后等待者不会被唤醒，白调。

### 14.4.2 流式任务的调度特殊性：槽位占用时长不是常数

这是 Agent 调度和传统 Web 调度最本质的差别：

| 维度 | 传统 Web 请求 | 流式 LLM 请求 |
| --- | --- | --- |
| 占用时长 | 近似常数（10~200ms） | **∝ 输出 token 数**（400 token ≈ 8s，4000 token ≈ 80s） |
| 中断代价 | 丢弃即可 | **已 flush 到前端的内容收不回**（第 37 章） |
| 重试语义 | 无状态，可重放 | 断点续写或重开，不能「重发已发出的字节」 |
| 槽位泄漏 | 随连接关闭自然回收 | **必须显式 abort 到引擎**，否则槽位永久占住 |
| 首字节时间 | 可忽略 | **TTFT 就是产品体验本身** |

**槽位泄漏的账**（这是流式系统最隐蔽的杀手）：

```
10 引擎 × 256 槽位 = 2,560 个槽位
平均占用 6s → 稳态需要 2,560/6 = 427 请求/s 才能占满
客户端断开率 0.1%（移动端切后台、弱网、用户关页面）
调用速率 900/s → 每分钟泄漏 900 × 60 × 0.001 = 54 个槽位
2,560 / 54 ≈ 47 分钟 → 引擎彻底无槽位可用，全部请求排队
```

**0.1% 的断开率，47 分钟后整个引擎静默死亡。** 而且监控上你只会看到「TTFT 缓慢上升」，看不出任何错误率异常——因为请求根本没失败，只是在等。

所以流式调度必须做三件事：

```go
// ① ctx 必须一路传到 HTTP client，断连即 cancel
func (c *Client) Stream(ctx context.Context, req Request, onDelta func(string)) error {
	httpReq, _ := http.NewRequestWithContext(ctx, "POST", c.url, body)
	resp, err := c.http.Do(httpReq) // ctx 取消 → 底层 TCP 关闭 → 上游感知 → 引擎 abort
	if err != nil {
		return err
	}
	defer resp.Body.Close()
	// ...
}

// ② 上层要有兜底看门狗：超过预期生成时长 3 倍仍未结束，强制 cancel
func (w *Worker) runWithWatchdog(ctx context.Context, fn func(context.Context) error) error {
	ctx, cancel := context.WithTimeout(ctx, w.maxStreamDuration) // 例如 180s
	defer cancel()
	return fn(ctx)
}

// ③ 引擎侧指标必须暴露：running / waiting / kv_cache_usage
//    如果 running 持续等于 max_num_seqs 而 waiting 也在涨 → 不是流量问题，是泄漏
```

**第二条的 `maxStreamDuration` 不能拍脑袋**：按 `max_tokens / 最小生成速率` 算。`max_tokens=4096`、最慢 15 tok/s → 273s。设成 300s 是安全的；设成 60s 会误杀正常的长回答。

### 14.4.3 continuous batching 的拐点：加并发不等于加吞吐

这是本章最反直觉的一张表（**数量级示意，具体数字必须用你自己的流量 profile 实测**，模型、卡型、输入长度分布都会让拐点移动 2~3 倍）：

| 引擎内并发槽位 | 单请求输出 tok/s | 聚合吞吐 tok/s | TTFT P50 | TTFT P99 | 状态 |
| --- | --- | --- | --- | --- | --- |
| 32 | 95 | 3,040 | 0.18s | 0.35s | 远未饱和，浪费显存 |
| 64 | 78 | 4,992 | 0.25s | 0.60s | 线性区，性价比最高 |
| 128 | 52 | 6,656 | 0.42s | 1.3s | 开始拐弯 |
| 192 | 38 | 7,296 | 0.65s | 2.1s | 接近饱和 |
| **256** | **31** | **7,936** | **0.85s** | **3.2s** | **吞吐饱和点** |
| 512 | 17 | 8,704 | 2.1s | 9.5s | 过载，吞吐仅 +9.7%，P99 ×3 |

从 256 到 512：**吞吐只涨 9.7%，TTFT P99 涨了 197%**。这就是拥塞崩溃（congestion collapse）的形状——你付出的延迟是线性的，换回的吞吐是对数的。

**对你调度器的三个直接推论**：

1. **`max_num_seqs` 不要设成显存允许的最大值**。设成「吞吐饱和点」（本例 256），把剩下的显存留给 KV cache 和长上下文请求。
2. **超载时优先「拒绝」而不是「排队」**。过载区里多排一个请求，会让所有在跑的请求都变慢，是负和博弈。第 11 章的准入控制在这里不是体验优化，是**生存必需**。
3. **交互流量和批处理流量不能用同一个引擎**。批处理请求的 `W` 是交互的 10 倍（长输出），会长期霸占槽位，把交互请求压在过载区。

### 14.4.4 抢占与优先级反转

**优先级反转在 Agent 系统里有两种形态**，第二种几乎没人提：

| 形态 | 现象 | 根因 |
| --- | --- | --- |
| ① 经典反转 | 低优的长任务占着槽位，高优请求在队列里等 | 槽位持有时间 ∝ 输出长度，长任务天然占优 |
| ② 引擎内反转 | 你的队列严格按优先级出队了，但高优请求在引擎里仍然排在低优之后 | **你的调度器管不到引擎内部的 batch 组成**；引擎侧 `running` 队列对它一视同仁 |

形态 ② 是真正难缠的：你做了完美的优先级队列，一测发现 P99 没变好。原因是引擎的 batch 里同时有 200 个低优请求，高优请求进去只是多了一个 token 的算力份额。

**解法只有一条：物理分池。**

```
┌──────────────────────────────────────────────────────────┐
│ 交互池（Interactive）                                     │
│  6 引擎 × max_num_seqs 192，SLA: TTFT P95 < 1.2s          │
│  只接 priority=high 的请求                                │
├──────────────────────────────────────────────────────────┤
│ 批处理池（Batch）                                         │
│  3 引擎 × max_num_seqs 256，SLA: 完成时间 < 10min         │
│  接 priority=low，允许抢占、允许排队                      │
├──────────────────────────────────────────────────────────┤
│ 离线池（Offline）                                         │
│  1 引擎 × max_num_seqs 128，跑评测、蒸馏、回流            │
│  可被随时 kill，K8s PriorityClass=preemptible             │
└──────────────────────────────────────────────────────────┘
```

代价是多 1 个引擎（约 10% 成本），收益是交互 P99 从 41s 回到 1.1s。**这笔账怎么算都值。**

**抢占矩阵**——不是所有东西都能抢：

| 被抢占对象 | 可抢占？ | 代价 | 策略 |
| --- | --- | --- | --- |
| 队列中等待的 Run | ✅ | 0 | 直接丢弃，保留 Run 状态，稍后重排 |
| 已派发但未进模型 | ✅ | 0 | abort 请求，槽位归还 |
| 模型生成中（交互） | ⚠️ 技术上可 | 已生成 token 全废 + 用户看到截断 | **不抢** |
| 模型生成中（离线） | ✅ | 重算成本 = 已消耗 token 的 100% | 抢，但限频率（≥30s 一次）避免抖动 |
| 工具执行中（只读） | ✅ | 0 | abort |
| 工具执行中（写） | ❌ | **副作用已发生** | 等它完成，失败走补偿（第 12 章） |
| 流式中已 flush 300 字 | ❌ | 无法撤回（第 37 章） | 只能等，或用 correction 事件收尾 |

> ⚠️ 「模型生成中可以 abort」在技术上成立（取消 HTTP 连接或调引擎的 abort 接口），但**已消耗的 token 你照样要付钱**。所以对交互流量抢占是纯亏损：赔了钱、赔了体验，什么都没换到。抢占只能用在「反正要重算」的离线任务上。

### 14.4.5 扩容：HPA 不能用 CPU

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: agent-run-worker
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: agent-run-worker
  minReplicas: 12
  maxReplicas: 64            # ← 硬上限：必须 ≤ 模型侧能承受的并发 / 单 Pod 并发
  metrics:
    - type: Pods
      pods:
        metric:
          name: agent_inflight_runs_per_pod
        target:
          type: AverageValue
          averageValue: "500"      # 4800 / 500 ≈ 10 Pod，留余量到 12
    - type: Pods
      pods:
        metric:
          name: agent_gate_wait_p95_seconds
        target:
          type: AverageValue
          averageValue: "2"        # 排队超过 2s 说明闸门在卡，需要更多 Pod 分担
  behavior:
    scaleUp:
      stabilizationWindowSeconds: 30
      policies:
        - type: Percent
          value: 50
          periodSeconds: 60
    scaleDown:
      stabilizationWindowSeconds: 600   # 10 分钟稳定窗口，防止抖动
      policies:
        - type: Pods
          value: 4
          periodSeconds: 60
```

四个必须写对的字段：

| 字段 | 为什么 | 不写会怎样 |
| --- | --- | --- |
| `maxReplicas` | 必须 ≤ 模型侧可承受并发 / 单 Pod 并发 | HPA 一路扩到 200 Pod，全部在模型侧排队，延迟雪崩 |
| `scaleDown.stabilizationWindowSeconds` | Agent 的负载有强自相关性（一个租户的批任务持续 40 分钟） | 每 2 分钟缩一次、扩一次，Pod 反复启动，SSE 连接全断 |
| 指标选 `inflight` 而不是 CPU | CPU 在等网络时是 5% | 永不扩容 |
| 指标加 `gate_wait_p95` | 区分「真的忙」和「被模型卡住」 | 两种情况都扩 Pod，第二种纯浪费 |

> 🩸 **一个真实的事故形态**：HPA 用 CPU 指标，Agent-Server 在等模型时 CPU 稳定在 4%，HPA 判定「空闲」缩到 `minReplicas=2`，然后 2 个 Pod 扛 900 并发，队列爆掉，延迟打穿，用户全量投诉。**整个过程 HPA 都觉得自己在正确工作。**

## 14.5 并发度自动标定：可以直接贴进设计文档的公式

```
① Little's 定律（需求侧）
   in_flight = λ × W
   λ = 峰值 Run 创建速率（个/s）
   W = 平均 Run 时长（s）——★ 用 P95 而不是均值，否则你会长期欠容量

② 模型侧等效并发上限（供给侧）
   自建：C_self = Σ_engine ( max_num_seqs_i × util_target )
   外部：C_api  = TPM_quota × W_llm / ( 60 × avg_tokens_per_call )
         （RPM 通常不是瓶颈，TPM 才是；W_llm 用 P95）
   合计：C_model = C_self + C_api

③ 你的 Run 并发上限
   C_run = C_model / llm_time_ratio
   llm_time_ratio = 单 Run 中「等模型」的时间占比（Aurora ≈ 0.6）

④ 需要的引擎数
   N_engine = ceil( C_target_self / ( max_num_seqs × util_target ) )
   例：C_target_self = 2,176 → 2176 / (256 × 0.85) = 10.0 → 10 引擎

⑤ 单 Pod 承载的 in-flight Run
   per_pod = C_run / N_pod
   内存校验：per_pod × 210KB < 容器内存 × 0.5
   例：4800/12 = 400 → 400 × 210KB = 84MB（远小于 2GB，内存不是瓶颈）

⑥ 自适应控制律（AIMD）
   429 率 > 1%           → C ← max(C_min, 0.7C)
   TTFT_p95 > 1.5×target → C ← max(C_min, C − C/10)
   TTFT_p95 < target     → C ← min(C_max, C + 5)
   采样周期 5s，参数每 60s 最多调整一次（加冷却，防抖）
```

代入 Aurora 的完整演算：

```
λ = 300 Run/s, W_p95 = 30s        → in_flight = 9,000
llm_time_ratio = 0.6              → 需要并发 LLM = 5,400
C_self = 10 × 256 × 0.85 = 2,176  → 实际可用
C_api  = 60e6 × 6 / (60 × 8,400) = 714
C_model = 2,890
C_run   = 2,890 / 0.6 = 4,817     ← ★ 这是 L2 的硬上限
缺口    = (5,400 − 2,890) / 5,400 = 46.5%  → 必须靠降级/排队消化
```

**这个 46.5% 就是你的架构必须回答的问题。** 如果答案写不出来（或者写成「多加机器」），说明你还没做容量规划。

## 14.6 Java / 分布式经验对照

| 你的老经验 | Agent 调度里的对应 | 会咬人的差异 |
| --- | --- | --- |
| Tomcat `maxThreads=200` | Gate 并发上限 | 同构。但 Tomcat 的线程是「业务处理」，这里是「等一个 6 秒的外部调用」，比值差 30 倍 |
| Hystrix 线程池隔离 | 交互/批处理/离线三池隔离 | 同构，思路可以直接搬。区别是被隔离的资源是 **GPU 槽位**，不是线程 |
| Sentinel 的 QPS 限流 | 准入控制 | 同构。但 Agent 需要「按 token 计价」的成本维度限流（第 23 章） |
| Semaphore 限并发 | Gate | 同构。差别是你的信号量上限需要**动态调整**，而 `Semaphore` 的实现通常不支持动态扩缩 |
| HPA 按 CPU 扩缩 | 按 inflight / 队列等待扩缩 | **完全不同**：CPU 是 IO-bound 场景里最没用的指标 |
| RocketMQ 消费线程数 | 消费并发 | 同构，还多一个约束：**≤ 分区数**（第 13 章） |
| 线程池队列无界 | Gate 前面的队列必须有界 | 无界队列 = 延迟无限增长 = 用户全超时。必须有界 + 拒绝策略 |
| JVM GC 停顿 | 引擎的 batch 抖动 | 类似但更严重：batch 组成变化会让 P99 波动 3 倍，且不可预测 |

## 14.7 开源坐标

| 项目 | 它解决了什么 | 它不管什么 |
| --- | --- | --- |
| **vLLM** | PagedAttention + continuous batching + `max_num_seqs`/`gpu_memory_utilization`/`enable-chunked-prefill` 等调度参数；部分版本支持请求级优先级 | **它不知道你的业务优先级**，也不感知你的 Run 边界；跨引擎的全局调度要你自己做 |
| **SGLang** | RadixAttention（前缀树复用）+ 更激进的调度策略；多轮对话场景前缀命中率高 | 同上；且前缀复用对「每次上下文都变」的场景收益有限 |
| **K8s HPA / KEDA** | 自定义指标扩缩容、稳定窗口、多指标取 max | 不知道模型侧还有多少余量；扩出来的 Pod 可能只是在排队 |
| **Kueue / Volcano** | K8s 层面的批任务队列与 gang scheduling | 不理解 token 与流式语义，只按 Pod 资源调度 |
| **NVIDIA MPS / MIG** | GPU 层面的隔离与切分 | 粒度粗（MIG 最小 1/7 卡），且会牺牲吞吐 |

> 🎯 **一句话选型**：自建推理用 **vLLM**（生态最成熟、参数最透明）；前缀复用为主的多轮场景值得试 **SGLang**；扩缩容用 **HPA + 自定义指标**，但**必须加 `maxReplicas` 硬上限**把模型侧的容量约束编码进去。

## 14.8 事故清单

- [ ] **事故 A：并发调大反而更慢。** 现象：worker 从 100 扩到 500，吞吐 +9%，P99 ×10，429 率 18%。→ 根因：越过模型侧吞吐饱和点，进入拥塞崩溃区。→ 兜底：`maxReplicas` 硬上限 + AIMD 闸门 + 按 `gate_wait_p95` 而不是按 CPU 扩容。
- [ ] **事故 B：流式槽位泄漏，引擎静默死亡。** 现象：TTFT 从 0.8s 缓慢爬到 12s，错误率 0%，47 分钟后完全不可用。→ 根因：客户端断开后 ctx 没传到 HTTP client，引擎侧不知道要 abort。→ 兜底：ctx 贯穿 + watchdog 强制超时 + 监控 `engine_running / engine_waiting / kv_cache_usage` 三个指标。
- [ ] **事故 C：HPA 按 CPU 把服务缩到最小。** 现象：夜间 CPU 4%，HPA 缩到 2 Pod，早高峰直接不可用。→ 根因：IO-bound 服务 CPU 无信息量。→ 兜底：改 `inflight + queue_wait` 指标；`minReplicas` 按峰值 30% 设置。
- [ ] **事故 D：离线评测把在线 P99 打穿。** 现象：每天 03:00 评测任务启动，在线 TTFT P99 从 1.1s 到 15s。→ 根因：共用引擎池 + 长 prompt 占满 prefill。→ 兜底：物理分池（离线池可被 preempt）；`enable-chunked-prefill` 让长 prompt 不阻塞 decode。
- [ ] **事故 E：优先级反转。** 现象：优先级队列做得很完美，高优请求 P99 依然很差。→ 根因：引擎内 batch 组成不受你控制，高优请求和 200 个低优请求同 batch。→ 兜底：物理分池；或确认引擎支持请求级优先级并显式开启。
- [ ] **事故 F：抢占引发抖动。** 现象：离线任务被反复抢占重算，同一批任务跑了 6 小时还没结束。→ 根因：抢占频率过高，重算成本 > 收益。→ 兜底：抢占冷却 ≥ 30s；对「已生成 > 50%」的请求不抢。
- [ ] **事故 G：无界队列。** 现象：内存 30 分钟涨到 8GB 后被 OOMKill，重启后从零开始又涨。→ 根因：Gate 前面挂了无界 channel。→ 兜底：有界队列 + 满则拒绝（503），排队位置回传给前端。

## 14.9 一页速记

| 关键词 | 必须记住的结论 |
| --- | --- |
| 三层并发 | L1 接入 / L2 服务（你能调）/ L3 模型（你必须服从）；调度器只做「L2 贴住 L3」 |
| 需求侧 | `in_flight = λ × W`，W 用 P95 不用均值 |
| 供给侧 | 自建 `引擎数 × max_num_seqs × util`；外部 `TPM × W / (60 × avg_token)` |
| 反推 | `C_run = C_model / llm_time_ratio`，Aurora = 2,890/0.6 = 4,817 |
| CPU | IO-bound 服务里 CPU 是最没信息量的指标，绝不能用来扩缩容 |
| 拐点 | 256 → 512 槽位：吞吐 +9.7%，TTFT P99 +197%。超载区必须拒绝，不能排队 |
| 流式 | 槽位占用 ∝ 输出长度；断开必须 abort，0.1% 泄漏率 47 分钟杀死引擎 |
| 优先级反转 | 两种：槽位抢占型、引擎 batch 型。唯一解是物理分池 |
| 抢占 | 只抢「离线且在生成中」的；交互流量抢了是纯亏（钱已花、体验已毁） |
| HPA | 用 `inflight + gate_wait_p95`，`maxReplicas` 必须编码模型侧容量上限 |
| 控制律 | AIMD：429 乘性减 0.7，TTFT 达标加性增 +5，5s 采样、60s 冷却 |
| 一句话 | **加并发不是加并行能力，是加排队人数。** |

## 14.10 自检题

1. **你把 worker 并发从 100 调到 500，CPU 使用率几乎没变，为什么？**
   > 要点：因为瓶颈不在你的 CPU，在你下游的模型服务。Agent-Server 的 CPU 占用主要在 JSON 序列化与上下文拼装（毫秒级），99% 的时间在等模型返回。调大并发只是让更多 goroutine 同时阻塞在网络 IO 上——CPU 仍然闲，但你多占了 400 份内存、400 个连接，并把模型侧的队列塞爆。真正的旋钮是 `C_model`（引擎数 × `max_num_seqs` × 利用率，或 TPM 配额），不是 worker 数。

2. **为什么说 `max_num_seqs` 不应该设成显存允许的最大值？**
   > 要点：因为吞吐曲线是对数收敛的。从 256 到 512，聚合吞吐只涨 9.7%，但 TTFT P99 从 3.2s 涨到 9.5s。设成最大值意味着你几乎永远工作在过载区，付出的延迟代价换不回吞吐。正确做法是设在吞吐饱和点（需实测），把剩余显存留给 KV cache 和长上下文请求。

3. **你的优先级队列已经严格按优先级出队了，为什么高优请求的 P99 还是没改善？**
   > 要点：引擎内反转。你的调度器决定「谁进引擎」，但决定不了「引擎 batch 里都有谁」。高优请求进入时，batch 里已经有 200 个低优请求在 decode，它只能分到一个 token 的算力份额。解法是物理分池（交互池/批处理池/离线池各用独立引擎），让高优请求永远不和长任务共享 batch。检查方法：对比「高优请求进引擎时的 running 数」和「全部是交互流量时的 running 数」。
