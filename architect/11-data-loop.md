# 11. 数据闭环：埋点、特征与决策反哺

## 11.1 引子：两个「没人报错」的指标

数据闭环的故障从来不报警。管线没断、表有数、面板是绿的——**只是数字在骗你，而且骗得很有说服力。**

### 事故一：新模型上线，CTR 与通过率双涨，三周后被证明更差（2025-04-08 ~ 04-29）

推荐 + 风控同源升级：模型 v3 只在**置信度 ≥ 0.5** 的样本上输出决策，低于阈值的走规则兜底。兜底请求由规则服务返回，**但规则服务不写 `score` 字段，也不写曝光日志**（曝光日志由打分服务打印）。报表因此只统计了"被打分子集"。

| 时间 | 事件 | 数据 |
| --- | --- | --- |
| 04-08 | v3 灰度 10%，置信阈值 0.5，以下转规则兜底 | 兜底占比 21% |
| 04-15 | 全量，报表 CTR 4.8% → 5.60%，风控通过率 62% → 71% | 双涨，周会点头扩大投入 |
| 04-18 | 大盘 GMV 未动，客诉率 +18%，长尾品类曝光 −9% | 无人把这两件事连起来 |
| 04-22 | 数据分析师人工补数：把兜底请求从网关日志里捞回来 | 兜底 210 万曝光 / 0.5 万点击 = **0.24%** CTR |
| 04-25 | 复算真实全量 CTR | **4.47%**，比旧模型低 6.9% |
| 04-29 | 回滚 v3，恢复旧模型 + 兜底补埋点 | 三周损失广告收入 190 万元 |

对账一下两次口径的差：

| 口径 | 曝光（万） | 点击（万） | CTR | 与旧模型比 |
| --- | --- | --- | --- | --- |
| 旧模型全量 | 1,000 | 48.0 | 4.80% | 基线 |
| v3 报表口径（只含打分子集） | 790 | 44.2 | **5.60%** | **+16.7%** ✅ 假 |
| v3 真实全量（补回兜底） | 1,000 | 44.7 | **4.47%** | **−6.9%** ❌ 真 |

**涨的不是分子，是分母。** 模型把最难判的 21% 样本"外包"给了兜底，又没让这部分进统计——这是教科书级的**幸存者偏差**：只统计被放行的，等于让模型自己决定自己的考卷。风控侧同理：通过率的分母只算模型打分的，人工复核队列的终态从未回流，所以"通过率"其实在衡量"模型敢判的比例"。

### 事故二：埋点 SDK 静默丢包 12%，少收 10.8 万/月且容量规划偏小（2025-11-11 ~ 02-03）

大促峰值，SDK 的本地 ring buffer（8,192 条）写满后 `select default` 分支直接丢弃，只打了一条 `debug` 日志。

| 时间 | 事件 | 数据 |
| --- | --- | --- |
| 11-11 20:00 | 峰值事件 10,000 条/秒/节点，SDK flush 上限 8,800 条/秒 | 缺口 12% |
| 11-11 23:00 | 大盘曲线平滑上升，无异常（丢包发生在采集侧，指标算的是"已上报"） | 无人发现 |
| 11-12 | 失效的 0.3% 告警阈从未覆盖"上报覆盖率"这个指标 | — |
| 01-05 | 财务季度复核：计费流水与客户自查账单差 11.8% | 客诉 47 起 |
| 01-08 | 用网关访问日志（独立链路）与 SDK 上报做双源比对 | **覆盖差 12.3%，且长尾租户 14.2%** |
| 02-03 | 补收采取"按网关日志重算"、容量按真实用量扩 1.25 倍 | 少收 10.8 万/月 × 3 月，容量不足 2 次降级 |

关键在于**丢包不是随机的**：头部租户走服务端埋点（不经过 SDK）几乎不丢，长尾租户 SDK 版本旧、单请求事件密度高、峰值集中，丢 14.2%。**随机丢包可以被平均掉，相关丢包会变成系统性偏差**——这决定了 §11.5 的采样与补采必须按"分层"而不是"总量"设计。

两起事故的共同点：**埋点即真相**这个假设，从未被任何一行代码或任何一个指标验证过。

## 11.2 一句话定位、唯一真问题与七问对照

**定位**：数据闭环 = 「**线上事件 → 特征 → 决策 → 新事件**」这条环路的采集、加工、对齐、校验与回灌。它不是数仓项目，是一个**有反馈的测量系统**。

### 唯一真问题

> **数据从线上回到决策的那条回路会自我强化并污染指标。**
> 它既是系统进化的唯一来源，也是让所有指标一起说谎的最短路径：
> **因为决策本身决定了哪些数据被记录下来**（只记录放行的、只记录打分的、只记录成功的），
> 而记录下来的数据又决定下一轮决策。**回路越顺，偏差放大得越快。**

这条矛盾推出全部设计：

| 从矛盾推出的约束 | 推出的设计 |
| --- | --- |
| 分母必须独立于决策 | **兜底/拒绝/失败的请求也必须有一份记录**；用网关日志做第二数据源 |
| 每个指标必须只有一个定义 | **指标注册表 + 单一计算实现**（编译到流与批），见 §11.12 |
| 训练与线上必须同源 | **特征平台 + 时点正确 join**，见 §11.8 |
| 会自我强化的指标必须有对照 | **随机留出组 + 交错实验**，见 §11.10 |
| 采集可能悄悄少算 | **覆盖率 SLO + 双源对账**，见 §11.5、`eng/14` |
| 数据要能反哺设计而不只是报表 | **三类反哺**：缓存 key / 超时预算 / 配额，见 §11.13 |

### 七问法对照（本篇哪里答哪一问）

| 七问 | 落在哪节 | 一句话答案 |
| --- | --- | --- |
| ① 到底是什么 | §11.2 | 一条**有反馈的测量系统**，不是 ETL |
| ② 唯一真问题 | §11.2 | 回路会自我强化并污染指标 |
| ③ 量级与预算 | §11.3、§11.7 | 100 亿条/天 → 3.2 TB/天原始 → 管道全链 ≈ 9.6 万元/月 |
| ④ 形态怎么选 | §11.4、§11.6 | 三级时效拓扑；Lambda / Kappa / 流批一体的换挡信号 |
| ⑤ 会在哪崩 | §11.9、§11.14 | 四类污染 + 六条反模式，全是"没人报错"的崩法 |
| ⑥ 换挡信号 | §11.4、§11.6、§11.7 | 迟到率 > 2%、回刷成本 > 重算成本、明细查询占比 < 5% |
| ⑦ 怎么验证 | §11.10、§11.15 | 覆盖率对账、A/B、交错实验、反事实评估四道闸 |

## 11.3 量级与预算：一条事件的全生命周期成本

不许拍脑袋。这条推导链评审时要能复述：

```
事件量        5,000 万 DAU × 人均 20 条 = 100 亿条/天
写入 TPS      100e8 / 86400 ≈ 11.6 万/s；大促峰值 ×4 = 46 万/s
单条编码      protobuf（非 JSON）：8 个字符串 + 枚举 + 时间戳，均值 320 B
              同一事件用 JSON 是 780 B —— 这一项就决定 2.4 倍带宽与存储
网络带宽      11.6 万 × 320 B ≈ 37 MB/s；峰值 148 MB/s（单 10GbE 的 12%）
日原始量      100e8 × 320 B = 3.2 TB/天
Kafka 占用    3.2 TB × 3 副本 × 保留 3 天 × 压缩 0.5 ≈ 14.4 TB
落湖压缩      3.2 TB ÷ 5（Parquet + zstd 列存，同类字段相关性高） = 640 GB/天
分析列裁剪    只保 22 个分析列 = 180 B/行 → 1.8 TB/天 ÷ 5 = 360 GB/天
查询并发      40 个 BI 会话 × 6 次/分钟；单次扫 1 天明细 = 360 GB
              → 明细查询占比一旦 >5% 就必须预聚合（§11.7 换挡信号）
```

**三条 SLO，比任何面板都重要**：

| SLO | 定义 | 目标 | 不达标的后果 |
| --- | --- | --- | --- |
| 上报覆盖率 | SDK 上报条数 ÷ 网关访问日志条数 | ≥ 99.5%（计费链路 ≥ 99.99%） | 少收钱、容量偏小（事故二） |
| 端到端时延 | 事件发生 → 可查 | 实时 <1 s / 准实时 <5 min / 离线 T+1 | 决策用了过期数据 |
| 口径一致性 | 同一指标在流与批两条链路的差 | ≤ 0.3% | 两个报表打架（§11.12） |

## 11.4 三级时效拓扑：一次采集，三路消费

**图 1 · 三级时效拓扑（同一份事件，不是三份数据）**

```
                         ┌───────────────────────────────────────────────────┐
   埋点事件（protobuf）───┤ 采集一次、落一次，语义按消费层级"变形"而非"复制"    │
                         └──────┬──────────────────┬──────────────────┬────────┘
                                │                  │                  │
                    ┌───────────▼───────┐ ┌────────▼────────┐ ┌───────▼──────────┐
                    │  实时  <1 s        │ │ 准实时  分钟级   │ │  离线  T+1        │
                    │───────────────────│ │─────────────────│ │──────────────────│
                    │ Flink 无状态+      │ │ 微批 10s~1min    │ │ Kafka → OSS/S3    │
                    │ 24 GB 内存状态     │ │ ClickHouse MV   │ │ Parquet + zstd    │
                    │ Redis 计数/去重位图│ │ 或 Doris 物化视图│ │ dbt / Spark 重算  │
                    │───────────────────│ │─────────────────│ │──────────────────│
                    │ 能答：限流扣减、    │ │ 能答：运营看板、  │ │ 能答：结算、审计、 │
                    │ 实时风控、告警中止  │ │ 漏斗、实验中期读数│ │ 归因、训练集回刷   │
                    │───────────────────│ │─────────────────│ │──────────────────│
                    │ 不能答：任意维度    │ │ 不能答：秒级止损  │ │ 不能答：今天的决策 │
                    │ 回刷、跨月长窗口    │ │ 不能答：跨年回溯  │ │ 不能答：<4 h 交付  │
                    └───────────────────┘ └─────────────────┘ └──────────────────┘
                        成本 ≈ 40×            成本 ≈ 6×           成本 = 1×（基准）
```

成本倍数的推导（不是玄学）：实时链路要**常驻内存状态**（24 GB × 双 AZ）+ 低延迟存储 + 7×24 扩容预留，且每条事件都要走一次网络与序列化；离线链路用列存高压缩 + 批调度把机器利用率打到 70% 以上。**同样一条事件，实时的单位成本约为离线的 40 倍、准实时约 6 倍。**

| 级别 | 技术栈 | 单位成本 | 能回答 | 不能回答 | 典型用途 |
| --- | --- | --- | --- | --- | --- |
| **实时 <1s** | Flink（keyed state）、Redis、Kafka | 40× | 这个用户这条请求现在该不该放行 | 任意维度组合的复盘 | 风控拦截、限流扣减、实时告警 |
| **准实时 分钟级** | 微批 Flink、ClickHouse 物化视图 | 6× | 转化漏斗现在什么形状、AB 能不能提前停 | 秒级止损（来不及） | 运营看板、实验中期读数、库存水位 |
| **离线 T+1** | OSS/S3 + Parquet + dbt/Spark | 1× | 结算多少、模型该怎么训、去年同比 | 今天下午的决策 | 计费结算、特征回刷、训练集、审计 |

> **铁律**：不要让离线链路去回答"现在"，也不要让实时链路去回答"任意维度"。想做"实时看任意维度"，正确的动作是**把离线预聚合粒度做细 + 准实时补一层**，不是把所有查询压到 Flink 上——那是成本失控的标准起手式（→ [01 约束卡与量级估算](01-constraint-card-and-capacity.md)）。

## 11.5 埋点设计：schema、命名、丢失与采样

### 11.5.1 事件 schema（必填字段是契约，不是建议）

| 字段 | 必填 | 说明 | 不填会怎样 |
| --- | --- | --- | --- |
| `event_id` | ✅ | UUID，服务端幂等键 | 重投导致重复计数 |
| `event_name` | ✅ | 命名规范见下，全局唯一 | 无法建指标注册表 |
| `event_ver` | ✅ | schema 版本，只增不改 | 语义悄悄漂移，历史不可比 |
| `ts_client` / `ts_server` | ✅ | 双时间戳 | 客户端时钟错乱无法识别 |
| `tenant_id` | ✅ | 计费与配额的对账锚点 | 事后补不回来，只能认损 |
| `user_key` | ✅ | 加盐哈希，不留明文 | 合规风险 + 无法跨表 join |
| `partition_key` | ✅ | 决定下游保序与分片 | 同一实体的事件乱序 |
| `sample_rate` | ✅ | 本事件所在层的采样率 | 无法回算总量（§11.5.4） |
| `decision_branch` | ✅ | `model / rule_fallback / cache / reject` | **事故一就是漏了它** |
| `model_ver` / `feature_ver` | ✅ | 决策所用逻辑版本 | 无法做版本切片归因 |
| `props` | ⭕ | 业务自定义，禁止放关键字段 | 关键字段进 props = 永远没人查 |

`decision_branch` 与 `model_ver` 这两列，是**在建模期就要埋下的对账与分群锚点**——等出了事故再补，历史数据补不回来（这与 `12 短链 · §12.8` 里"计费锚点必须建模期埋"是同一条纪律）。

### 11.5.2 命名规范

```
<域>.<对象>.<动作>          link.resolve.done / ord.order.paid / risk.decision.made
规则：全小写 + 下划线分隔；动词用过去式（已发生的事实）；禁止 type/data/info 这类泛字段
禁止：click（哪个页面？）、event1、"埋点A"（中文名后期 100% 会撞）
版本：语义变更 → 新 event_name；仅加字段 → event_ver+1，双写 30 天
```

### 11.5.3 丢失与补采：三层兜底，缺一层就等于靠运气

| 层 | 机制 | 挡住什么 | 代价 |
| --- | --- | --- | --- |
| 客户端缓冲 | ring buffer + 磁盘 WAL，flush 失败落盘 | 网络抖动、进程重启 | 移动端耗电与写放大 |
| SDK 背压 | channel 满时**落 WAL 而不是丢弃**，且上报 `track.wal_spill` 指标 | 事故二那种静默丢 | 需要磁盘配额与清理策略 |
| 服务端兜底 | 网关访问日志独立入 Kafka（`billing_raw`），T+1 与 SDK 上报**双源对账** | 采集侧系统性漏采 | 存两份数据（约 +25% 成本） |
| 采集侧监控 | 覆盖率 = 上报数 ÷ 网关数，按 `tenant_id × 版本` 切片 | 相关丢包（长尾租户 14.2%） | 必须做，不能只看总量 |

**只做前三层不做第四层，等于把事故推迟到财务复核那天。** 覆盖率必须按维度切片看：总量 99% 完全可能是"头部 100%、长尾 88%"。

```go
// track/reporter.go —— 批量上报骨架：宁可落盘，不可静默丢弃
// Event 字段：EventID(幂等键) / Name / Ver / TsServer / TenantID / Branch / SampRate / Props
type Reporter struct {
	ch     chan Event // 生产侧 non-blocking 写，满则自行落 WAL
	wal    *WAL
	sdkVer string
}
func (r *Reporter) Loop(ctx context.Context) {
	buf := make([]Event, 0, 500)
	tick := time.NewTicker(time.Second)
	for {
		select {
		case e := <-r.ch:
			buf = append(buf, e)
			if len(buf) >= 500 {
				r.flush(ctx, &buf)
			}
		case <-tick.C:
			r.flush(ctx, &buf)
		case <-ctx.Done():
			r.flush(context.Background(), &buf) // 退出前必须落盘
			return
		}
	}
}

func (r *Reporter) flush(ctx context.Context, buf *[]Event) {
	if len(*buf) == 0 {
		return
	}
	payload, err := proto.Marshal(&pb.Batch{SdkVer: r.sdkVer, Events: *buf})
	if err == nil {
		err = r.send(ctx, payload) // 批量 + 指数退避
	}
	if err != nil {
		r.wal.Append(payload)          // ① 落盘重放，绝不静默丢
		metrics.Inc("track.wal_spill") // ② 该指标 >0 立即告警
	}
	*buf = (*buf)[:0]
}
```

**注意最后几行的分工**：`wal.Append` 保证不丢，`track.wal_spill` 保证"不丢这件事本身可观测"。事故二的根本原因不是没有重试，而是**丢弃动作没有任何指标**——一个连自己丢了多少都不知道的管道，等于没有 SLO。

### 11.5.4 采样：破坏统计的三种采样方式

| 采样方式 | 是否安全 | 原因 |
| --- | --- | --- |
| **按决策单元采样**（同一 user 整体进/出） | ✅ | 漏斗不断裂，可回算 |
| 分层采样（按租户规模/渠道分层，层内随机） | ✅ | 层内无偏，层间用 `sample_rate` 加权回算 |
| 按请求随机采样（同 user 部分进部分出） | ⚠️ | UV 与漏斗失真，只能算"率"不能算"人数" |
| **按结果采样**（只采"被点击的"） | ❌ | CTR 恒等于 100%，这是自我实现的谎言 |
| 按"方便"采样（只采 app 端） | ❌ | 端间差异被当成整体结论 |

> **一条硬规则**：**采样键不能是结果变量，也不能是决策分支。** 一旦按"是否被点击""是否命中模型"采样，你采到的就不再是总体的无偏估计，而是"已经被决策筛过一遍"的子集——这是事故一的采样版。

### 11.5.5 schema 演进

三条纪律，全部来自"历史数据不可重算"这个事实：

1. **只加不删**：删除字段只标 `deprecated=true`，字段名永不复用。
2. **语义变更必须换名**：`ctr` 从"点击/曝光"改成"点击/去重曝光"，这是**新指标**，不是新版本。
3. **双写窗口 ≥ 30 天**：v1 与 v2 同时上报，报表在 v2 稳定后切读，切换点写进变更记录（→ [07 变更治理](07-change-governance.md)）。

## 11.6 管道形态选型：Lambda、Kappa、流批一体

| | **Lambda（批+流双链路）** | **Kappa（纯流）** | **流批一体（Kafka + Flink + Iceberg/Paimon）** |
| --- | --- | --- | --- |
| 一致性 | 两套代码两套语义，**靠人工对齐，差 1~3% 是常态** | 单一代码，天然一致 | 单一表格式，流批读同一份数据 |
| 成本 | 双份计算 + 双份存储（最高） | 只有流，但**回刷要重放历史**，长窗口极贵 | 中：一份存储，回刷走批读 |
| 运维复杂度 | 高：两套血缘、两个口径负责人 | 中：一套代码，但状态管理难 | 高：要维护表格式、小文件合并、快照 |
| 迟到数据 | 批链路天然吸收 | 需 watermark + 允许迟到窗口 | 需 watermark + 增量 upsert |
| 回刷重算 | 简单（重跑批） | **昂贵**（重放 Kafka 或从湖重灌） | 中（按快照/分区重算） |
| 适用场景 | 已有成熟数仓团队，离线报表为主 | 事件天然有序、无长窗口需求 | 新建、明细要既能实时又能回刷 |
| 换挡信号 | 流批差异连续 3 天 > 0.5% | 回刷耗时 > 窗口 3 倍 或 Kafka 保留撑不住 | 小文件数 > 分区数 × 100 或快照元数据打爆 |

**我的默认答案**：新建系统直接上**流批一体**，Lambda 只作为"已有离线数仓、短期不能动"的过渡形态。理由不是技术先进，而是 **Lambda 的双链路是口径分裂的制度化**——你等于在架构上承认"两个数字不一样是正常的"，而 §11.12 会说：那恰恰是事故的源头。

## 11.8 特征平台：离线在线必须同一份逻辑

**这是整篇技术上最容易翻车、也最容易在评审中被追问的一节。**

同一个特征（如 `clicks_7d`）如果训练侧用 Hive SQL 写一遍、线上侧用 Go 再写一遍，你拥有的是**两个同名特征**：窗口边界差 1 天、时区差 8 小时、去重口径差"是否算重复点击"、空值填充 0 vs NULL。它们平时看起来一样，**在特征分布剧烈变化时（大促、故障、新客涌入）分叉**——而这正是模型最需要准确的时刻。

**图 2 · 时点正确 join（point-in-time join）**

```
  时间轴 ────────────────────────────────────────────────────────────────────►
            01-01               01-02 10:00          01-02 23:59    01-03 23:59
              │                     │                    │              │
  样本发生    │                     ● label_ts           │              │
              │                     │                    │              │
  当时真正     clicks_7d = 12 ──────┘                    │              │
  可用的特征   （系统 01-02 03:10 才知道 12）            │              │
                                                        │              │
  事后回刷的                            clicks_7d = 15 ──┘              │
  特征版本                                                clicks_7d = 41 ┘
                                                          ↑ 含 01-03 的暴增
                                                          
  ✅ 正确：ASOF JOIN 取 event_time ≤ label_ts 且 ingest_time ≤ label_ts 的最新一版 → 12
  ❌ 错误 A：JOIN ON stat_date = date(label_ts)                    → 取到 15（多半天）
  ❌ 错误 B：直接取"最新快照"（今天回刷的结果）                        → 取到 41（穿越 1 天）
```

```sql
-- ① 特征表：append-only + 双时间（事件生效 event_time / 系统可知 ingest_time）
CREATE TABLE feature_user_stat (
  user_id String, stat_date Date, clicks_7d UInt32,
  event_time  DateTime,        -- 这个特征值代表的时间点（窗口右边界）
  ingest_time DateTime,        -- 它何时才真正可被线上读到（T+1 03:10 才算完）
  logic_ver   LowCardinality(String)   -- 必须能回答"这两个值算法一样吗"
) ENGINE = MergeTree ORDER BY (user_id, event_time);

-- ② 时点正确 join：只用样本发生时刻"当时已经知道"的特征
SELECT s.sample_id, s.label, f.clicks_7d, f.event_time
FROM samples s
ASOF LEFT JOIN feature_user_stat f
  ON s.user_id = f.user_id AND s.label_ts >= f.event_time
WHERE f.ingest_time <= s.label_ts             -- 剔除晚到的回刷版本 ← 关键
  AND f.event_time  >= s.label_ts - INTERVAL 30 DAY;

-- ③ Python 侧同一逻辑 + 上线前红线检查（CI 里必须跑）
# out = pd.merge_asof(samples, feats, on="label_ts", by="user_id",
#                     direction="backward", tolerance=pd.Timedelta("30D"))
# out = out[out.ingest_time <= out.label_ts]
# assert (out.event_time <= out.label_ts).all(), "leakage: 特征晚于样本"
# assert out.groupby("feature_ver").size().pipe(lambda x: x.index.nunique()) == 1
```

**不用的代价，用数字说**（某推荐模型 2025 年 8 月上线的真实量级）：

| 特征 | 离线 AUC | 线上 AUC | 归因 |
| --- | --- | --- | --- |
| `clicks_7d`（T+1 回刷版） | 0.841 | 0.712 | 把标签发生后的 1 天点击算进了打分时刻 |
| `order_cnt_30d`（含未来退款） | 0.826 | 0.719 | 退款发生在未来，训练时已知 |
| `last_sku_price`（取最新价） | 0.817 | 0.722 | 价格在标签之后变更 |
| 三个特征全部改为时点正确后 | **0.718** | **0.712** | 差 0.006，说明差距**几乎全部来自穿越** |

后果：离线预估转化率 5.8%，上线实际 2.9%，第 4 天回滚，损失 GMV 940 万元。**穿越大模型的特征，会让离线评估变成一场自欺的表演——而且它永远在离线通过。**

## 11.9 反馈回路的四类污染（本篇核心）

**图 3 · 反馈回路如何被污染**

```
        ┌────────────────── 决策层（推荐 / 风控 / 配额 / 定价）──────────────────┐
        │  只对"有把握的"样本打分或放行 → 写日志（有 model_ver、有 branch）          │
        └──────────┬──────────────────────────────────────────┬──────────────────┘
                   │ 放行 / 曝光（有记录）                      │ 兜底 / 拒绝 / 失败
                   ▼                                          ▼
        ┌────────────────────────┐                  ┌────────────────────────┐
        │ 训练样本（有标签）      │                  │ 静默丢弃（无记录、无标签）│
        │ 天然富集"模型已能判的"  │                  └───────────┬────────────┘
        └───────────┬────────────┘                              │
                    ▼                                           │
        ┌────────────────────────┐                              │
        │ 新模型：更自信、阈值更严│                              │
        └───────────┬────────────┘                              │
                    │                                           │
                    └──────────► 下一轮只对更少样本打分 ◄────────┘
                                  ↑ 回路闭合：分母持续萎缩，偏差被放大
   结局：指标↑（分母缩小）· 覆盖面↓ · 长尾用户被永久排除 · 模型越"准"越没用
```

| 污染类型 | 长什么样（可观测症状） | 识别方法 | 防御手段 | 代价 |
| --- | --- | --- | --- | --- |
| **自我强化**（越推越窄） | 推荐品类熵逐月下降；头部 1% 内容占曝光从 40%→72%；新内容冷启曝光 3 天为 0 | 每周算**曝光分布的基尼系数/熵**；统计新 item 的曝光占比 | **随机留出 5% 流量走探索策略**（不进主模型的训练样本，但计入指标分母）；多样性约束进排序 | 短期 CTR −1.5%~3% |
| **幸存者偏差**（只统计被放行的） | 报出 CTR 涨、GMV 不涨（事故一）；通过率涨但人工复核队列变长 | 用**第二数据源**（网关日志/工单）复算分母；比对"有记录 ÷ 应发生" | `decision_branch` 强制埋点；兜底/拒绝也必须产生一条事件；**分母覆盖率进 SLO** | 埋点成本 +15%，存储 +25% |
| **Goodhart 定律**（指标被优化到失真） | 点击率涨但退订率涨；停留时长涨但完播率跌；"人工处理量"涨但问题数没降 | 为主指标配**护栏指标对**（CTR ↔ 退订；通过率 ↔ 欺诈损失；时长 ↔ 次日回访）；护栏指标进发布门禁 | 指标注册表里每个北极星必须绑定 ≥2 个护栏；护栏恶化则回滚，不看主指标 | 优化空间被压缩 20%~30% |
| **训练-服务偏差** | 离线 AUC 0.84 / 线上 0.71（§11.8）；同特征两端分布 KS > 0.1 | 每天抽查 1 万条线上请求，用**训练同版逻辑**重算特征，比对分布（PSI/KS） | 特征平台单一实现（逻辑只写一次，编译到批与流）；`feature_ver` 进日志与训练集 | 平台建设 2~3 人月 |

> **这四类污染的共同结构**：它们都不是"某个算子写错了"，而是**测量过程参与了被测量的对象**。所以修法也不在数据层，在**架构层：加一条与决策无关的观测通道 + 加一组决策管不到的对照流量。**

## 11.10 实验与因果：为什么"上线后指标涨了"不等于模型有效

指标上涨至少有五种解释，只有第一种是"模型有效"：

| # | 解释 | 怎么排除 |
| --- | --- | --- |
| 1 | 真实效应 | A/B 分流随机 + 样本量足够 + 护栏指标不恶化 |
| 2 | 幸存者偏差 / 分母变化 | 复算全量分母（§11.1） |
| 3 | 新奇效应（用户只是看到新鲜东西） | 观察 2~4 周后的衰减曲线；看次日/次周留存 |
| 4 | 季节与外部冲击（大促、竞品、天气） | 保留长期 holdout 组（1%~5%，**永不上线**） |
| 5 | 分流污染（同一用户跨组、共享库存/供给） | 用 `user_key` 哈希分流 + 检查跨组 user 交集 = 0 |

**最小做法三件套**：

| 手段 | 用在哪 | 最小实现 | 不能回答 |
| --- | --- | --- | --- |
| **A/B** | 有稳定分流单元（user/租户） | 哈希分流 50/50，先算最小样本量，跑满 2 个完整周（覆盖周内效应） | 组间干扰强（市场双边、库存）时不可靠 |
| **交错实验（interleaving）** | 排序/召回类，指标是"用户偏好" | 把 A/B 两组结果**混排进同一次展示**，比较来源点击占比 | 有强协同或强疲劳的场景会失真 |
| **反事实评估（IPS / DR）** | 无法做实验（风控拒贷、医疗、定价） | 用倾向得分对历史日志加权，估计新策略收益；必须记录**旧策略的动作概率** | 新策略的支撑集之外（旧策略从未选过的动作）无解 |

> **反事实评估的前提是"当时就要记概率"**——日志里没有 `propensity`（旧策略选择该动作的概率），任何离线策略评估都是假算。这又是一个**建模期不埋、事后永远补不回来**的锚点，与 §11.5 的 `decision_branch` 同类。

**风控/拦截类系统尤其要注意**：被拒的请求没有"如果放行会怎样"的标签，所以必须**随机放行 0.5%~1% 做样本**（并承担这部分风险），否则你的模型永远不知道"自己拒掉的到底是好人还是坏人"。这笔风险预算相当于 0.5% 的欺诈损失，换来的是模型唯一的真相来源。

## 11.11 badcase 回流：把事故变成评测集

数据闭环里"把失败样本变成可执行约束"的完整工序，见 `llm/40`（评测体系）与 `llm/41`（回流管道）。**通用系统的差异只有三点**，但三点都要改：

| 差异 | Agent 侧（llm/41） | 通用系统（本篇） |
| --- | --- | --- |
| 失败信号从哪来 | 点踩、撤回、转人工 | **规则兜底命中、人工改判、客服工单、对账差异、实验护栏恶化** |
| 最小样本单位 | 一个输出片段 + 上下文 | 一次决策 + `模型/规则/特征` 三个版本号 + 真实结果 |
| 最贵的坑 | 删除传播（模型权重） | **分母缺失**（失败请求根本没被记录，连样本都捞不出来） |

通用系统的 badcase 池只需四张最小字段：`样本 id`、`决策上下文快照`、`真实结果（T+n 回填）`、`三个版本号`。**没有回填真实结果的池子只能叫"投诉列表"**——它无法告诉你"这次改对了没有"。

## 11.12 口径与指标平台：两个报表数字不一样，是架构问题

**"两个报表数字对不上" 从来不是数据问题，是"同一个指标被实现了四次"的问题**：埋点侧一次、Flink 一次、dbt model 一次、报表 SQL 一次。四次实现四个口径，差异是**架构的必然而不是数据的偶然**。

### 指标定义必须唯一，且要素齐全

| 要素 | 例：`付费转化率` | 缺了会怎样 |
| --- | --- | --- |
| 分子 | 支付成功的去重订单数 | 与"支付笔数"混用 → 复购场景对不上 |
| 分母 | 当日**有购买意图**的去重用户（进入详情页） | 用"DAU"当分母 → 与投放团队永远吵不清 |
| 去重 | 按 `user_key`，跨端去重 | 移动+PC 双端重复计数 |
| 时间窗 | 自然日，UTC+8，标签口径 `payment_ts` | 用 `event_ts` → 跨日支付错位 |
| 迟到处理 | T+1 补算，允许 6 小时迟到重算，重算覆盖不追加 | 每日数字持续微调，月报对不上 |
| Owner | 谁改口径谁负责，变更需 2 人审批 | 没人对数字负责 |

### 口径变更的兼容与回溯

| 动作 | 做法 | 代价 |
| --- | --- | --- |
| 变更前 | **双跑 ≥ 14 天**：新旧口径同时算，差异率 < 0.3% 才切 | 双份计算成本 |
| 变更时 | 指标名带语义版本 `pay_cvr@v3`；旧版本保留可查 | 面板要标注版本 |
| 变更后 | 保留旧口径 13 个月（覆盖同比周期），同时提供桥接报表 | 存储 + 维护 |
| 回溯 | 只回溯**可重放的部分**（DWD 之上的聚合），ODS 之前不可回溯 | 埋点缺失 → 只能认损（事故二） |

## 11.13 数据反哺架构决策（本篇的独特价值）

绝大多数团队把数据闭环做成"报表工厂"：数据只往上看（给人看），不往回走（改架构）。**但线上日志是唯一能告诉你"架构假设错了"的证据源。** 三个真实反哺案例：

### 案例 A：用访问日志反推缓存 key 与分片键

| 步骤 | 做法 | 发现 |
| --- | --- | --- |
| 观察 | 统计 `slug` 请求分布 + 缓存未命中日志 | Top 0.3% 的 slug 承载 78% 请求（符合预期） |
| 反直觉 | 按**完整 query string** 统计命中率 | 命中率只有 61%，远低于设计值 91% |
| 定位 | 42% 的请求带 `si`（分享渠道）参数，而它**被拼进了缓存 key** | 同一个 slug 被拆成 6 个 key |
| 结论 | 把 `si` 移出 key，改为 value 里打标；热点 slug 再按 `slot % 8` 复制 8 份 | 命中率 61% → 93%，Redis 回源 −82% |
| 分片键反哺 | 按 `tenant_id` 聚合请求 → 头部一家占 31% 流量 | 印证"点查型系统分片键必须选查询条件"，**tenant_id 不可作主库分片键**（→ [03 存储与索引的形态决策树](03-storage-and-index-shape.md)、`12 短链 · §12.5`） |

**这类反哺的价值**：缓存 key 设计是纯设计决策，只有日志能证明它对不对；而分片键一旦选错就再也改不回来，日志是**决策后 24 小时内唯一能验证它的手段**。

### 案例 B：用延迟分布反推超时预算

| 数据 | 值 | 说明 |
| --- | --- | --- |
| P50 / P99 / P999 | 8 ms / 210 ms / 1.2 s | **双峰**：210 ms 峰是下游 GC；1.2 s 峰是跨 AZ 抖动 |
| 朴素做法 | 超时 = 均值 × 3 = 24 ms | 会砍掉 12% 的正常请求 → 重试风暴 |
| 正确做法 | 超时 = P99.9 分位 = **260 ms**，且只对**幂等请求**重试 | 重试率 4.1% → 0.3% |
| 效果 | 端到端 P99 1.4 s → 310 ms；下游被打垮的次数 3 次/周 → 0 | — |

**超时预算不是"拍一个数"，是从延迟分布的分位点读出来的**，而且必须区分"逐步变慢"与"抖动尖峰"两种尾巴——前者该扩容，后者该加超时余量，动作完全不同（→ `eng/21`）。

### 案例 C：用长尾租户分布反推配额

| 数据 | 发现 |
| --- | --- |
| 租户请求量洛伦兹曲线 | 头部 1.2% 租户占 71% 流量 |
| 长尾 6.8 万租户 | 中位数 40 次/天，但 P99 达 12 万次/天（夜间批处理突发） |
| 朴素配额（按每租户峰值 × 租户数） | 需 4,100 核，且 99% 的时间闲置 |
| 正确配额（稳态基线 90% 水位 + 令牌桶突发桶） | 需 960 核，**省 77%**，长尾批处理仍能跑完 |
| 结论 | 配额的形状应该由**分布形状**决定：长尾要"允许短时突发、限制持续占用"（→ [24 多租户 SaaS 底座与配额计费](24-multi-tenant-saas.md)、`09 开放平台`） |

> **三个案例的共同点**：数据闭环真正的产出不是"更准的模型"，而是**"哪个设计假设错了"的答案**。做闭环的团队若只交付报表，等于把最有价值的副产品扔了。

## 11.14 反模式表

| # | 反模式 | 症状 | 为什么致命 | 正解 |
| --- | --- | --- | --- | --- |
| 1 | **埋点即真相** | 面板数字从不被质疑；没人知道上报覆盖率 | 采集侧的偏差被当成业务事实，所有下游推理都建筑在它上面 | 双源对账（网关日志）+ 覆盖率 SLO + 按维度切片 |
| 2 | **指标无口径** | 两个部门为同一指标吵三天；报表天天微调 | 差异永久存在且无法归因，决策层失去信任 | 指标注册表：分子/分母/去重/时窗/迟到/Owner 六要素 |
| 3 | **采样破统计** | "为什么 UV 比昨天少一半"；漏斗断在中间 | 采样键选错，采到的是被决策筛过的子集 | 按决策单元采样；采样键不能是结果变量 |
| 4 | **特征两边各写一套** | 离线 AUC 0.84 / 线上 0.71；大促当天效果骤降 | 训练-服务偏差只在分布漂移时暴露，恰是最需要准确的时刻 | 特征平台单一实现 + 时点正确 join + `feature_ver` 进日志 |
| 5 | **只统计成功请求** | 通过率/成功率涨，但工单量、退款、人工队列同步涨 | 分母被"成功"定义，指标失去测量能力（事故一） | 兜底/拒绝/失败也必须落事件，`decision_branch` 必填 |
| 6 | **只做报表不做反哺** | 数仓很大，架构决策仍靠猜 | 扔掉唯一能验证设计假设的证据源 | 每季度一次"用日志反推三个设计参数"（§11.13） |

## 11.15 十分钟答题卡

被问"你的数据闭环怎么设计"时，按这个顺序讲，不要从"我们用了 Flink"开始：

```
1  真问题   回路会自我强化并污染指标——决策决定哪些数据被记录
2  量级     100 亿条/天 → 11.6 万 TPS → 3.2 TB/天原始 → 全链约 11.4 万/月
3  时效     三级拓扑：实时 40× / 准实时 6× / 离线 1×，各答不同问题
4  埋点     protobuf + 版本化 schema；decision_branch 与 model_ver 必填
5  不丢     ring buffer → WAL → 网关日志兜底 → 覆盖率 SLO 按租户切片
6  采样     按决策单元分层，采样键不能是结果变量、不能是决策分支
7  管道     新建选流批一体；Lambda 等于把口径分裂制度化
8  特征     ASOF JOIN + ingest_time 过滤；离线与线上同一份逻辑
9  污染     自我强化 / 幸存者 / Goodhart / 训练-服务偏差，各配一个护栏
10 因果     A/B + 交错 + 反事实；长期 holdout 与拒放样本是唯一真相源
11 反哺     日志 → 缓存 key、超时预算、配额形状——闭环真正的产出
```
