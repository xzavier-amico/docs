## 26.0 本篇在合订本里的位置

前 25 篇给**答案**（某量级下某形态为什么对），本篇给**判据**（下一个没见过的系统该怎么落到某形态）。只会答案的人会把"短链的解法"套到"活动奖励"上；只会判据的人在评审现场说不出一个具体数字——**所以每节都同时带流程与可复算的数**。

> **可逆性不同的决策，不能用同一种评审强度。** 换缓存产品天级可逆，换分片键半年~一年不可逆，换标识符语义物理上不可逆（→ [12 短链 · §12.4](12-shortlink-system-design.md)）。**所以七步不是从最难的开始，是从最不可逆的开始。**

## 26.1 一页纸设计模板

七步、七个闸门。每步只问三句话，答不出来就停——**停在第三步，比带着错误的分片键跑到第七步强十倍**。

```
 ┌──────────────────────────────┐
 │ 入口：一个新功能 / 一次改造   │
 └──────────────┬───────────────┘
                ▼
① 约束卡     「日请求？读写比？端到端 P99？五年多少 TB？」
                ✗ 停：连"该不该加缓存"都没有输入
                ✓ 七字段约束卡 + 11 行推导链（→ 01 §01.3）
                ▼
② 唯一真问题 「这个量级下最难的那一件事，能一句话说清吗？」
                ✗ 停：没想透，写出来都是套话
                ✓ 一句矛盾 + 5~8 条推论（→ 12 §12.2）
                ▼
③ 领域不变量 「哪些不变量必须同一事务守护？真源在谁手里？」
                ✗ 停：后面所有一致性讨论无处落地
                ✓ 聚合表 + 状态机 + 依赖方向纪律（→ 02 §02.3）
                ▼
④ 存储与分片键「主查询什么形状？键是不是查询条件本身？」
                ✗ 停：唯一押错就回不去的决策（→ 03 §03.3）
                ✓ 决策树出口 + 分片键 + 4096 槽 + 投影
                ▼
⑤ 读写形态   「写完之后有几处视图活着？各靠什么失效、窗口多长？」
                ✗ 停：缓存会变成"命中率很高但值是错的"
                ✓ 五级链路表 + 窗口 W + 回源 QPS（→ 04 §04.7）
                ▼
⑥ 异步与一致性「哪些必须同步？重做挡得住吗？积压多久算事故？」
                ✗ 停：异步是按"允许重做"签的合同（→ 05 §05.4）
                ✓ 判定矩阵 + 幂等键 + Outbox 边界（→ 05 §05.7）
                ▼
⑦ 换挡信号   「哪个指标越过哪个阈值必须换形态？代价？谁按按钮？」
                ✗ 不许上线（"不动"也是决策，但要交付采集与告警）
                └✓ L0–L5 换挡表 + 阈值四件套（→ 06 §06.5）→ §26.10
```

### 26.1.1 每步：问什么 / 答不出来会怎样 / 产出什么文档

| 步骤 | 问什么（按顺序三句） | 答不出来会怎样 | 产出什么文档 |
| --- | --- | --- | --- |
| ① 约束卡 | 日请求与峰值系数 K？读写比？端到端 P99 与五年存储？ | "加个 Redis"没有输入可校验，量级翻倍即翻车（→ 01 §01.1） | 七字段约束卡 + 11 行推导链（每数标假设） |
| ② 唯一真问题 | 最难的一件事是什么？它推得出哪 5 条设计？换量级还成立吗？ | 方案退化成清单，每个决策都不可辩护 | 一句矛盾 + 推论表 + 同构系统对比表 |
| ③ 领域不变量 | 哪些状态必须同一事务写成功？谁真源谁派生？谁能调谁？ | 不变量被撕两半：超卖、重复发放、锚点缺失（→ 02 §02.1） | 聚合/不变量/守护表 + 状态机 + ArchUnit 规则 |
| ④ 存储与分片键 | 主查询是点查/范围/聚合/全文/多跳/语义？键等于查询条件吗？ | 76% 查询变广播；再分片要重写全部查询（→ 03 §03.8） | 决策树路径 + 分片键 + 槽映射 + 投影清单 |
| ⑤ 读写形态 | 有几处视图活着？失效机制与延迟？W 多少？拐点在哪？ | "命中率 99%"掩盖 620 QPS 在读错数据（→ 04 §04.2） | 五级链路表 + W 代入 + 命中率-成本拐点 |
| ⑥ 异步与一致性 | 哪些副作用必须同步？幂等键挂哪个聚合？积压多久扩容？ | 重复扣款、乱序发货、毒消息冻住分区（→ 05 §05.1） | 判定矩阵 + 幂等键清单 + Outbox 边界 |
| ⑦ 换挡信号 | 四件套（指标/采集/阈值与持续/动作）齐吗？回滚谁负责？ | 告警疲劳致真越线被忽略；"量大了再拆"当结论 | 换挡表 + 每级代价 + 复测日期 |

### 26.1.2 七步 × 典型错误

| 步骤 | 评审桌上最常听到的那句话 | 它掩盖了什么 | 一句话补救 | 锚点 |
| --- | --- | --- | --- | --- |
| ① 约束卡 | 「大概十万 QPS 吧」 | 无峰值系数、无重试放大、无扇出 | 让对方当场复述 11 行推导 | → 01 §01.3 |
| ② 唯一真问题 | 「这个系统主要要高性能」 | 说不清难在哪 = 没定位矛盾 | 逼出"X 必须固定、Y 必须可变" | → 12 §12.2 |
| ③ 领域不变量 | 「先按表拆服务，边界以后再理」 | 不变量已被撕开 | 先答"哪条不变量必须同事务" | → 02 §02.3 |
| ④ 存储与分片键 | 「用 MySQL，量大再分库分表」 | 分片键默认成了自增主键 | 先列查询形状再定键，预留 4096 槽 | → 03 §03.7 |
| ⑤ 读写形态 | 「加个 Redis 就好了」 | 失效语义、视图数量、窗口全未定 | 问"写完之后有几处视图还活着" | → 04 §04.2 |
| ⑥ 异步与一致性 | 「上 Kafka 解耦一下」 | 幂等/顺序/背压/可观测四笔账未付 | 先签"允许重做"合同再落幂等键 | → 05 §05.3 |
| ⑦ 换挡信号 | 「先这样，量大了再拆」 | 无阈值、无采集、无 owner | 不动也要交付：指标+告警+复测日 | → 06 §06.13 |

### 26.1.3 为什么顺序不能换

1. **② 依赖 ①**：同一功能在 10 QPS 与 60 万 QPS 下不是同一系统（→ [0 总纲 §0.1]）；没数字，真问题会答成另一量级的版本。
2. **④ 依赖 ③**：分片键之争的答案由聚合边界决定（→ [02]、[03 · §03.7](03-storage-and-index-shape.md)）；先选库再找不变量，必然"一个事务跨两个分片"。
3. **⑥ 依赖 ③⑤**：能不能异步由不变量决定；异步后的窗口用的还是同一张 W 公式（→ 04 §04.7、05 §05.7）。

> 评审纪律：**先问"走到第几步、哪步跳过了"**。跳过 ①④ 的方案半年内以事故补课；跳过 ⑦ 的会永远停在原地直到崩。

| 01 | 约束卡与量级估算 | 决策的输入是数字，而数字必须能被一个人在白板上推出来 | 七字段约束卡 + 11 行连乘推导链，每数标假设 | 620 万 DAU → 入口 4,158 QPS、16 台、23.6 元/百万请求 |

| 05 | 写路径与异步落点 | 异步是「允许重做」的授权书，四项代价必须逐条报价 | 幂等键挂聚合根 + Outbox 同事务 + 看追上时间 | 重复率 0.1% 单价差 250 倍；资金类 T=5 min |
| 06 | 演进纪律与换挡 | 每次重构不是"因为量大"，而是某指标越过某阈值 | 阈值四件套 + expand-contract 四步 + 不许跳级 | L0 1k → L5 千万 QPS；三层树 21.9 GB；该分 4 片非 64 片 |

**一、分片键出现在 11/14 个案例里，且没有一个是"—"——它是最高频、也最不可逆的决策。** 剩下 3 个（19、22、23）降为 ○ 不是不需要分片，而是答案更残忍：推荐的分片维度被"算力分配"替代（→ 19 §19.3），奖励被"一场一库 + 库存分桶"替代（→ 22 §22.15），秒杀干脆没有可分的维度——**单 key 只属于一个 slot，加 200 个节点单 key 的 QPS 一点都不会变**（→ 23 §23.3）。正确读法是：分片键不是"要不要选"，而是**"你有没有一个可用的分片维度"**；没有时必须在漏斗、桶化、改语义三条路里选一条并算清代价。

**二、一致性模型 13/14，是唯一"几乎人人有份"的抽象**：所有形态争论的底层都是同一个问题——允许多大窗口、窗口内谁保证什么（→ 04 §04.7）。评审先问这句，比先问用哪个中间件有效十倍。

**三、查询形态与成本主导项各 12/14，是同一枚硬币的两面**：前者决定读放大几次，后者决定钱花在读取、写入、存储还是算力。而成本主导项**随量级换**——短链 L1 是 DB 成本、L4 变成带宽成本（→ 12 §12.10）；埋点湖做对格式后存储只占 14%、计算占 70%（→ 21 §21.11）。**这一行必须标注量级，否则结论会过期。**

**四、缓存失效只有 2/14 是主角，这是全套最反直觉的结论**：因为最好的失效是**让数据不可变**——13 只存指针、15 日志只追加、18 快照、21 Iceberg 分区，不可变性把"要失效 245 处视图"降维成"换一个 16 字节指针"（→ 04 §04.5）。**看到缓存问题先问"能不能变成不可变版本"。**

**五、配额与租户隔离只见于 4 个案例（17/18/24/25），全是"交给别人用"的系统**（→ 09 §09.2）；**六、按可逆性排序后评审顺序应反过来**：标识符语义 > 分片键 > 一致性模型 > 派生索引 > 缓存形态——③④ 排最前不是因为难，而是**因为贵**。

## 26.5 附录 A：表结构 DDL 全集

MySQL 8.0 可直接执行，每张表注明**分片键**与**索引意图**；原文用其他引擎的（13 的 Cassandra、15 的 Hash 分区）保留键结构与不变量改写为等价形态，`upload_session`（→ 25 §25.7）与 `tenant_route`（→ 24 §24.13）字段见源篇。

```sql
-- A1 short_link（→12 §12.4/§12.5）分片键=hash(slug)，512 片；虚拟槽=hash(slug)%4096
CREATE TABLE short_link (
  slug VARBINARY(16) PRIMARY KEY, -- 唯一索引即不变量：短码永久不复用
  tenant_id BIGINT NOT NULL,
  status TINYINT NOT NULL, -- 6 态：draft/active/suspended/banned/expired/terminated
  current_version INT UNSIGNED NOT NULL, -- 指向 link_version；缓存 i:{slug} 存的就是它
  created_at DATETIME(3) NOT NULL,
  KEY idx_tenant_ct (tenant_id, created_at) -- 仅运营兜底；列表/统计一律走 ES 投影
);

-- A2 link_version（→12 §12.6 原文结构）append-only；与 A1 同分片键：指针与版本同片
CREATE TABLE link_version (
  slug VARBINARY(16) NOT NULL,
  version INT UNSIGNED NOT NULL,
  target VARCHAR(2048) NOT NULL, -- 均值 120B，按 512B 留膨胀（§12.3 行宽账）
  operator_id BIGINT NOT NULL, -- 目标变更必须留痕可回滚
  created_at DATETIME(3) NOT NULL,
  PRIMARY KEY (slug, version) -- 只 INSERT：内容不可变 ⇒ 可无限缓存
);

-- A3 slug_tombstone（→12 §12.4「墓碑独立表且永不清空」、§12.11「墓碑误清」）
CREATE TABLE slug_tombstone (
  slug VARBINARY(16) PRIMARY KEY, -- 分配前必查；日任务扫与主表交集，命中即 P1
  last_tenant BIGINT NOT NULL,
  reason TINYINT NOT NULL, -- 1违规封禁 2合规终止 3租户退租 4审核拒绝
  retired_at DATETIME(3) NOT NULL,
  archived TINYINT NOT NULL DEFAULT 0 -- 只归档，不清空
);

-- A4 inbox（→13 §13.5；原文 Cassandra，此处为 L0–L1 阶段 MySQL 等价形态，键结构不变）
CREATE TABLE inbox (
  user_id BIGINT NOT NULL,
  ts BIGINT NOT NULL, -- 毫秒时间戳，簇键第一位
  post_id BIGINT NOT NULL,
  author_id BIGINT NOT NULL, -- 冗余，用于"拉黑作者"读时过滤
  kind TINYINT NOT NULL, -- 1原创 2转发 3推荐插入
  PRIMARY KEY (user_id, ts, post_id) -- 分片键=user_id；读序 (ts DESC, post_id DESC)
); -- 只存指针(30~50B)：存快照会把删博变 3000 万行

-- A5 msg_log（→15 §15.5 四实体、§15.7 原文；conversation 字段见 §15.5，撤回见 msg_mutation §15.10）
CREATE TABLE msg_log (
  conv_id BIGINT NOT NULL,
  seq BIGINT NOT NULL,
  client_msg_id CHAR(22) NOT NULL, -- 幂等键（客户端生成，重发不变）
  sender_id BIGINT NOT NULL,
  sender_device CHAR(16) NOT NULL,
  server_ts DATETIME(3) NOT NULL, -- 排序不用它，审计用它
  client_ts DATETIME(3) NOT NULL,
  msg_type TINYINT NOT NULL,
  body VARBINARY(1024) NULL, -- ≤1KB 内联，超出走 body_ref
  body_ref VARCHAR(255) NULL,
  reply_to_seq BIGINT NULL,
  PRIMARY KEY (conv_id, seq), -- 发号与追加必须同分片同事务（§15.6）
  UNIQUE KEY uk_idem (conv_id, sender_id, client_msg_id) -- 重发返回原 seq
);

-- A6 upload_part（→25 §25.6/§25.7）
CREATE TABLE upload_part (
  upload_id CHAR(26) NOT NULL, -- ULID，绑定 (tenant,user,objectKey) 防跨用户复用（§25.14）
  part_no INT NOT NULL,
  etag VARCHAR(64) NOT NULL,
  crc32c BIGINT UNSIGNED NOT NULL,
  size INT NOT NULL,
  updated_at DATETIME(3) NOT NULL,
  PRIMARY KEY (upload_id, part_no) -- 幂等键=(uploadId,partNumber)，重传即覆盖

-- A7 tenant（→24 §24.4 四档隔离、§24.15 删除证明）

CREATE TABLE index_alias (
  alias VARCHAR(64) NOT NULL, -- 逻辑名：业务代码里只准出现它
  physical_index VARCHAR(96) NOT NULL, -- products_v1/v2；出现在代码即架构违规
  role TINYINT NOT NULL, -- 1read 2write（读写别名必须同一次切换）
  version BIGINT NOT NULL,
  active TINYINT NOT NULL DEFAULT 1,
  switched_at DATETIME(3) NULL,
  PRIMARY KEY (alias, role), -- 切换=同一请求 remove v1+add v2；回滚=改指针，1 s
  KEY idx_physical (physical_index)
);
```

**四张表覆盖四类不变量**：`slug_tombstone` 守"标识符永久不复用"（→ 12 §12.4，破坏即 1.2 万个已印短码指向赌博站）；`claim.uk_biz` 守"同一 `(activity,user,round)` 只一条成功"（→ 22 §22.4，破坏即 1,370 张重复券）；`upload_part` 主键守"任一片可重做"（→ 25 §25.6，破坏即"长度对、内容错"）；`tenant.level` 决定 owner 库（配 §24.13 路由表）——漏配就写错家。

### 26.6.1 错误码分层（→ 09 §09.6）

| 层 | 谁看 | 可变性 | 例子 | 用途 |
| --- | --- | --- | --- | --- |
| L1 HTTP | 网络/网关/所有人 | 遵循 RFC，永不自定义 | 400/401/403/404/409/422/429/500/503 | 传输语义 |
| L2 业务码 | 接入方的**代码**（唯一允许 `switch`） | **不可变**：只新增、不改语义、不删除 | `ORDER.AMOUNT_MISMATCH`、`PLATFORM.RATE_LIMITED` | 客户端决策 |
| L3 明细 | 人：日志/工单/调试 | **可变**，随时增改文案 | `detail.field`、`detail.request_id` | 排障与提示 |

码段位：`10xxx` 鉴权 / `20xxx` 订单 / `30xxx` 支付 / `40xxx` 平台与配额 / `50xxx` 导入导出；每个 L2 码须有含义、可重试性、客户端动作、何时会变（永不）四件套。

| 客户端三分类 | 典型码 | 必须做 | 绝不能做 |
| --- | --- | --- | --- |
| 可重试 | 429 `PLATFORM.RATE_LIMITED`、503、`PROVIDER.TIMEOUT` | 指数退避+全抖动、尊重 `Retry-After`、复用同一 Idempotency-Key、上限 5 次 | 立即重试/换新幂等键重试 |
| 不可重试 | 400/422 `VALIDATION.*`、401、403、404、`CONFLICT.STATE` | 按 `detail.field` 修调用方 bug | 重试（放大成 5 倍流量且永不成功） |
| 需人工 | `ORDER.AMOUNT_MISMATCH`、`ACCOUNT.RECONCILE_DIFF`、已提交但响应丢失 | 落工单附 `request_id`+幂等键 | 自动补偿（重复扣款并破坏对账口径） |

| recall@k | ANN 买到的正确率，与延迟/内存形成明码标价 | 18 |
| 四级漏斗 | 召回→粗排→精排→重排，逐级用更贵算力给更少候选打分 | 19 |
| 追平 / 停写窗口 | 增量消化到 lag 归零的时间 / 切换时不可并行的冻结时长 | 20 |
| 分区爆炸 | 维度进分区路径导致分区数按基数乘出来，元数据服务先死 | 21 |
| 预扣 / pending | 先扣余量后落账的中间态，必须有 TTL 与扫描释放 | 22 |
| 五口径三恒等式 | budget/deduct/issued/redeemed/redeem_fail 与三条守恒式 | 22 |
| 桶化 | 把单 key 拆成 N 个 key 换吞吐，代价是桶间不均致少卖 | 23 |
| fail-closed | 路由查不到就返回 503，绝不"退回默认库" | 24 |
