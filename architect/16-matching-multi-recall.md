## 16.1 引子：三起「没人报错」的匹配故障

### 事故一：`LIKE '%keyword%'` 撑到 3000 万行（2025-04，某 B2B 商品库）

系统只有三张表：`product(id, title, brand, category)`、`brand`、`category`。搜索框的实现是一句 SQL：

```sql
SELECT id, title FROM product WHERE title LIKE CONCAT('%', ?, '%') LIMIT 20;
```

2022 年数据 80 万行时，这个查询 P99 **20 ms**，评审结论是「够用，别过度设计」。这个结论在当时是对的。

| 时间 | 事件 | 数据 |
| --- | --- | --- |
| 2025-02 | 商品行数越过 2,000 万，搜索 P99 从 20 ms 涨到 4.2 s | 表 8.1 GB |
| 2025-03 | 运营加了 `title` 的普通索引，**毫无作用**（前缀索引对 `%x%` 无效） | 索引 0 命中 |
| 2025-04-08 10:12 | 行数到 3,000 万，大促预热流量 ×3 | 表 12.4 GB |
| 10:14 | 搜索 P99 **40.6 s**，连接池 200 条全被占满 | 单查询扫 3,000 万行 |
| 10:15 | 连接打满 → 商品详情页、下单页一并超时 | 全站成功率 61% |
| 10:52 | 熔断搜索入口，恢复 38 分钟；直接损失约 74 万 GMV | — |
| 05-10 | 改用 2-gram 倒排（bigram 词典 82 万条）+ 后验验证 | P99 **180 ms** |

算一遍就知道这不是"运气差"，是**复杂度差了一个量级**：

```
LIKE '%kw%'：无索引用 → 全表扫 + 每行做一次子串匹配
  扫 12.4 GB @ 400 MB/s ≈ 31 s；加回表与函数调用 → 实测 40.6 s
  行数每翻倍，延迟翻倍 → 3,000 万行 = 4,000 万行的 0.75 倍 ≠ 可接受量级
2-gram 倒排：query 切成 2 个字符的 gram，取交集 + 回原文验证
  命中 gram 的 posting 交集 ≈ 1.2 万候选 → 验证 1.2 万条 × 40 字节 ≈ 0.5 MB 顺序读
  实测 180 ms，且 98.6% 的答案与全表扫一致（剩下的差异是验证规则写漏）
```

**根因不是"没加索引"，是把一种「无索引能力」的匹配形态（任意子串）硬塞给了一个只会「等值 / 前缀 / 范围」的结构（B+ 树）。**

### 事故二：为了「语义匹配」上向量库，精确匹配全线崩（2025-06，某工业品商城）

客服反馈"搜型号搜不到"，产品结论是"要做语义搜索"，于是上了一个向量库，把商品标题、型号、参数全部 embedding，**下线了原来的精确匹配与倒排**。

| 时间 | 事件 | 数据 |
| --- | --- | --- |
| 06-02 | 向量检索上线，取代原精确 + 倒排双通道 | 1,860 万条 |
| 06-05 | 「口语化需求」（"能上飞机带的充电宝"）召回明显变好，NPS +9 | — |
| 06-09 | 客诉"搜 A-1024-B 搜出 A-1025-B"，首批 37 单错发 | top-1 精确命中率 100% → 62% |
| 06-11 | 抽检 200 条精确键查询：`X200` / `X200s`、`ERR-4021` / `ERR-4120` 互为 top-1 | 余弦相似度 0.998 |
| 06-18 | 累计错发 2,100 单，退货与赔付 41 万元；回滚向量主路径 | 3 周 |
| 06-25 | 新形态：精确哈希通道**前置**（命中即返回，不参与排序）+ 倒排 + 向量只做补充召回 | 三路 |

**型号是「离散符号」，embedding 是「连续空间」**——`A-1024-B` 与 `A-1025-B` 在语义上确实"几乎一样"，因为它们本来就几乎一样；而在业务上它们差一个零件号，是两台不能互换的机器。**用连续空间表达离散标识符，等于把"相等"降级成"相似"。**

### 事故三：按文档 ID 分片，前缀补全变成 256 路广播（2025-09，某电商搜索）

倒排按 `hash(doc_id)` 分了 256 片，写入均匀、全文检索也没问题。但搜索框补全（输入 2 个字符就发请求）走的是同一个集群：

| 时间 | 事件 | 数据 |
| --- | --- | --- |
| 09-14 20:02 | 晚高峰补全 QPS 8,700（占总匹配流量的 62%） | 峰值 1.4 万 QPS |
| 20:02 | 每个补全请求 = 广播 256 片取 top-20 → 片内查询总量 | **8,700 × 256 ≈ 223 万次/s** |
| 20:04 | 256 片里 41 片 CPU > 92%，单片 P99 从 8 ms 涨到 210 ms | 扇出后 P99 = 最慢一片 |
| 20:06 | 补全 P99 6.8 s，前端 200 ms 超时 → 全部空下拉 | 错误率 71% |
| 20:13 | 熔断补全，搜索正文也因资源争抢受损 26 分钟 | — |
| 09-20 | 修复：**全局词典副本**（1.2 GB，含品牌与热词）+ 前缀命中后只打到含相关 term 的 3~6 片 | 片内查询量降 98% |

一句话：**前缀查询的"查询条件"不是文档 ID 里的任何东西，所以按文档 ID 分片时它必然退化为广播。** 这是 §16.10 的主题，也是检索系统与 [03 存储与索引](03-storage-and-index-shape.md)「分片键 = 查询条件」原则的那一处**必须例外**。

三起事故分别对应**子串无索引 × 离散符号用连续空间 × 分片键与查询形状错配**——正好是本篇的三套索引与两条边界。

## 16.2 一句话定位与唯一真问题

**定位**：匹配服务回答的是「**给我一批候选，它们与这个查询"有关"**」。这里的"有关"有六种互不相同的严格定义（§16.4），**每一种对应唯一一种正确结构**，并且这六种定义之间**不共享任何索引**。

### 唯一真问题

> **精确前缀、全文、语义三套索引的召回率与延迟不可调和，所以必须分层。**
> 不是一个"更强的索引"同时满足六种匹配，而是**六条通路各自用唯一正确的结构，再把结果融合**——融合不是锦上添花，是这套架构的**主结构**。

三条不可调和的证据，每一条都能用数字击穿"找个万能方案"的幻想：

| 维度 | 证据（1 亿条商品标题的量级） | 结论 |
| --- | --- | --- |
| **内存方向相反** | 哈希 32 B/条 ≈ 3.2 GB；前缀词典 2.6 GB；倒排 4.6 GB；**向量 307 GB（768 维 float32）**，PQ 压缩后 10 GB 但 recall 掉 4~6 点 | 一个结构的内存由它的"比较方式"决定，不可共享 |
| **延迟方向相反** | 精确 0.05 ms / 前缀 0.3 ms / 子串 18 ms / 全文 42 ms / 语义 12 ms | 最慢的那一路决定 P99（§16.8） |
| **召回方向相反** | 词法对同义表述 recall≈0；向量对 `A-1024-B` 与 `A-1025-B` **零区分度**（距离 0.002） | 两者的"相关"定义本身冲突，融合是唯一的调和方式 |

把它和旁边几个常见误解放在同一把尺子上：

| 你以为的 | 真相 | 不做会怎样 |
| --- | --- | --- |
| 「上一个 ES 就全解决了」 | ES 覆盖前缀（词典）+ 全文 + 子串（ngram），**但对精确键无保证，对语义零能力** | 型号搜索仍需独立精确通道（事故二） |
| 「向量是下一代搜索，会取代倒排」 | 向量解决**同义**，倒排解决**精确与可解释**；两者是并列关系 | 上线即丢精确召回（事故二） |
| 「匹配慢就加索引」 | 加索引只对**能落到 B+ 树有序性**的形态有效；子串与语义都不在里面 | 事故一：加了索引，延迟没变 |
| 「多路召回 = 多调几个接口然后拼起来」 | 没有预算、超时与融合规则的"多调几个"= P99 取最慢 × 超时率放大 5 倍 | 路越多越慢，且越不可用 |
| 「召回率越高越好」 | 召回每多 1 个点，延迟从 0.6 ms 涨到 60 ms（§16.8），存在严格停手线 | 为最后 1.5 个点付出 2 倍延迟 |

### 唯一真问题的五个推论（后面每一节都是其中一条）

| 从矛盾推出的约束 | 推出的设计 | 落在哪节 |
| --- | --- | --- |
| 六种匹配形态必须各用唯一正确结构 | 六形态表 + 能力矩阵（没有一行全 ✅） | §16.4 |
| 前缀与多模式匹配要求**内存中的字符级结构** | 双数组 Trie + AC 自动机 + 后缀压缩 + 双缓冲 | §16.5 |
| 全文相关性与子串要求**文档到词的映射** | 倒排 + 整数压缩 + 跳表/位图 + 位置的代价 | §16.6 |
| 多路结果的量纲不同，不能直接比分数 | **RRF**（只用排名）+ 每路预算 + 去重 + 截断 | §16.7 |
| 查询条件不是等值键，分片键无法"即查询条件" | 文档分片 + 每片完整词典副本 + 两阶段路由 | §16.10 |

## 16.3 量级与预算：先算五个数字

不许拍脑袋。**匹配系统的量级推导和 OLTP 完全不同：瓶颈不是行数，是「查询形态 × 词表分支度 × 更新速率」。**

### 数一：数据规模（本篇全部估算的输入）

```
文档         商品 1.0 亿条，平均标题 40 汉字，分词后 12 个 token
词条         品牌与别名 600 万（平均 4.5 字）+ SKU/型号/错误码 8,000 万（平均 14 字符）
             + 中文词 1,050 万 → 合计约 1.0 亿"词条"，去重后唯一 term ≈ 1,050 万
多模式词表   敏感词 12 万条（平均 5.2 字）
原文         1.0 亿 × 40 汉字 × 3 B(UTF-8) ≈ 12 GB（含品牌、类目、卖点短句）

倒排         1.0 亿 × 12 token = 12 亿 posting
             不含位置 1.8 B/posting → 2.2 GB；含位置 3.6 B/posting → 4.3 GB
前缀词典     1.0 亿词条、平均 10 码点、前缀共享率 62% → 状态约 4 亿个
             双数组 + tail 压缩 → 约 2.6 GB
子串 n-gram  2-gram：每文档 39 个 bigram → 39 亿 posting ÷ 4（去重后）≈ 9.8 亿 → 2.9 GB
向量（可选）  1.0 亿 × 768 维 × 4 B = 307 GB → PQ 96 B/条 → 9.6 GB + HNSW 图 12.8 GB
```

> **第一个反直觉结论：1 亿文档的倒排只有 4.3 GB，词典 2.6 GB——单机 64 GB 装得下。** 检索系统的换挡信号从来不是"容量装不下"，而是 §16.13 要讲的 **QPS × 更新速率**。这一点和 [03 存储与索引](03-storage-and-index-shape.md) 里"单表过 300 GB 必须分片"的直觉完全相反，也是很多人给检索系统过早分片的原因。

### 数二：请求量

```
日均匹配     2.0 亿次 → 均值 2.0e8 / 86400 ≈ 2,315 QPS
峰值系数     ×6（晚 8 点 + 大促首日）→ 1.4 万 QPS
渠道分布     补全 62% / 商品搜索 21% / 精确键 14%（SKU、单号、错误码）/ 内容审核 3%
读写比       2.0e8 : 35 ≈ 570 万 : 1  ← 这个数字说明"更新可以很贵"，但要看得见
```

### 数三：延迟预算（P99，逐路给，不给总量）

| 渠道 | 允许走的通路 | P99 预算 | 说明 |
| --- | --- | --- | --- |
| 精确键（14%） | 哈希 / 唯一索引 | **5 ms** | 命中即返回，**不参与融合排序** |
| 补全（62%） | 词典前缀 Trie → top-20 | **20 ms** | 只查词典，不碰倒排 |
| 商品搜索（21%） | 倒排 BM25 + 子串 + 语义（3 路） | **80 ms** | 融合后截断 500 |
| 搜索 + 精排 | 上面 + Cross-Encoder 50 条 | **120 ms** | 精排必须可降级 |
| 内容审核（3%） | AC 自动机单遍扫 | **3 ms / KB** | 纯内存，不落盘 |

**四个渠道的预算是四个数字，不是一个数字。** 把它们压成一个"搜索平均 60 ms"，是匹配系统最典型的度量错误——因为补全的 62% 会掩盖搜索渠道的真实恶化。

### 数四：内存与机器（这是分片数的真正来源）

```
单节点装下   原文投影 6 GB（只存标题+品牌+类目，PDF/详情在对象存储）
             + 倒排(含位置) 4.3 GB + 词典 2.6 GB + 子串 2.9 GB ≈ 16 GB
             → 64 GB 机器留 4 倍余量给 OS page cache 与 merge 峰值
单节点能力   8 核，混合通道 P99 80 ms 时实测 ≈ 800 QPS（CPU 主要花在验证与打分）
分片数       ceil(1.4 万 / 800) = 18 → 取 24 片（2 的幂附近便于路由）
副本         2 副本 → 72 个节点（含每片 1 主 1 从 + 3 个协调节点）
```

### 数五：更新速率（决定 L2→L3 的那个数）

```
日更 300 万条商品（改标题 / 上下架）→ 均值 35 QPS，峰值 300 QPS
一条更新 = 删旧 postings（12 个 term）+ 写新 postings + 更新 n-gram（39 个）+ 可能触发段合并
单节点 merge 吞吐 ≈ 1.2 万文档/s → 300 万条 / 1.2 万 ≈ 250 s/天（4 分钟）看着很轻
但 merge 与查询抢 CPU：合并期单节点有效 QPS 从 800 掉到 520（-35%）
→ 更新速率每翻 10 倍，单节点有效能力掉 18%，这才是 L2→L3 的真实触发
```

> 规律写在这里：**检索系统里"写的成本"不是写 IO，是它把读能力吃掉的那部分**（细节见 [17 搜索系统深窥](17-search-system.md) 的段合并）。

## 16.4 六种匹配形态：拆到「唯一正确结构」为止

这是全篇的字典。**每一行只回答五句话**：唯一正确结构是什么、召回率、延迟量级、内存代价、用错了会怎样。

| # | 匹配形态 | 真实例子 | **唯一正确结构** | 召回率 | 延迟（P99，1 亿量级） | 内存 / 存储代价 | 用错的后果 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 1 | **精确相等** | SKU `A-1024-B`、错误码 `ERR-4021`、订单号、条码 | 哈希表 / B+ 树唯一索引 | **100%**（存在即召回） | 0.05~0.5 ms | 1×（哈希 ≈ 32 B/条 ≈ 3.2 GB） | 用向量：`A-1024-B` 与 `A-1025-B` 距离 0.002 → 错发（事故二） |
| 2 | **前缀** | 搜索框补全、品牌 `Nike` → 全系列、单号前缀查批次 | 双数组 Trie / FST（行数 < 500 万时 B+ 树 `LIKE 'kw%'` 够用） | **100%**（在词典内） | 0.3~1 ms（取 top-20） | 1.8~2.6 倍原文（词典去重后） | 用 `LIKE '%kw%'`：全表扫（事故一） |
| 3 | **任意子串** | 标题含「保暖」、工单含「退款失败」、地址含「朝阳」 | n-gram 倒排（bigram）+ **后验验证**；数据 < 100 万时可后缀数组 | 95~99%（n=2 有假阳性，需验证） | 5~25 ms | **8~15 倍**（9.8 亿 posting ≈ 2.9 GB） | 用 Trie 逐条走 = O(词表 × 词长)，比全表扫更慢 |
| 4 | **多模式同时匹配** | 12 万敏感词扫 1 KB 文本；黑名单批扫 500 万行 | **AC 自动机**（Trie + fail 指针 + 输出链） | **100%**（精确串，含重叠） | 0.2 ms / KB 文本 | 状态数 × 16 B ≈ 6.4 MB（12 万词） | 循环 12 万次 `strings.Contains`：单条文本 40 ms，扫描吞吐掉 200 倍 |
| 5 | **全文相关性** | 「轻薄 防水 登山鞋」按相关度排序 | 倒排 + BM25/BM25F + top-k 堆 | recall@20 **70~85%**（词法上限） | 20~80 ms | 3~5 倍（倒排 + 位置 + 词典） | 用精确哈希：只支持整句匹配，零结果率 60%+ |
| 6 | **语义近似** | 「能上飞机带的充电宝」→ 20,000 mAh 合规款 | 向量索引 HNSW/IVF（→ [18 向量系统](18-vector-system.md)） | recall@10 **85~95%**（相对标注） | 5~15 ms/路 | **最贵**：307 GB，PQ 后 9.6 GB（recall −4~6 pt） | 用它替代精确：编号/型号全错（事故二） |

### 能力矩阵：为什么"没有一个结构能一行全 ✅"

把六种形态当列，结构当行——**这张表就是"必须分层"的全部证明**：

| 结构 | 精确 | 前缀 | 任意子串 | 多模式 | 相关性排序 | 语义 | 增量更新 | 判定 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 哈希表 | ✅ | ❌ | ❌ | ❌ | ❌ | ❌ | ✅ 最便宜 | 只做通道 ① |
| B+ 树 | ✅ | ✅ | ❌ | ❌ | ❌ | ❌ | ✅ | 小数据量的唯一正解（§16.11） |
| 双数组 Trie | ✅ | ✅ | ❌ | ✅（配 AC） | ❌ | ❌ | ⚠️ 要重建 | 通道 ②④ |
| 倒排索引 | ✅ | ✅（词典前缀） | ⚠️（需 n-gram） | ⚠️（慢） | ✅ | ❌ | ⚠️ 段合并 | 通道 ③⑤ |
| 向量索引 | ⚠️（无区分度） | ❌ | ❌ | ❌ | ❌（无语义排序保证） | ✅ | ❌ 最贵 | 通道 ⑥（→18） |
| **组合（本篇）** | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ | — | **用工 4 套索引换 6 个 ✅** |

**没有一行全 ✅。** 这就是唯一真问题的算术版本：**要么接受覆盖不全，要么用工 4 套索引的内存与运维。**

### 一次真实请求往往同时命中 3 种

| 渠道 | 实际同时需要的形态 | 为什么不能只留一种 |
| --- | --- | --- |
| 补全（62%） | ② 前缀 + ⑤ 相关性（按热度排序）+ ⑥ 语义（有时） | 只留前缀 → 用户输入错字/近义词就空下拉 |
| 商品搜索（21%） | ⑤ 全文 + ③ 子串（标题里"含"）+ ⑥ 语义 | 只留全文 → "防水"搜不到"防泼水" |
| 精确键（14%） | ① 精确（**唯一**） | 加任何近似都会引入错误（事故二） |
| 内容审核（3%） | ④ 多模式 | 只留倒排 → 无法报告重叠位置，无法做变形词规则 |

**注意精确键那一行：其他三个渠道都需要"融合"，只有它不允许融合。** 把它拉进融合排序池，等于允许一个近似结果顶掉一个正确答案——这是事故二的唯一修复点，也是 §16.7 的第一条纪律。

## 16.5 Trie 与 AC 自动机：字符级结构，以及它的内存账单

前缀与多模式匹配的共同点：**问题定义在"字符序列"上，而不是"词集合"上**。所以索引必须能在字符之间行走——这是 B+ 树和哈希都做不到的事。

### 结构：双数组 Trie 是怎么把指针省掉的

```
朴素 Trie（指针实现）：每个节点一个 map[rune]child  →  4 亿节点 × 64~80 B ≈ 26~32 GB
双数组 Trie（DAT）：把"树"压成两排 int32

        trie：            root
                         ├─'a'→ n1 ─'p'→ n2 ─'p'→ n3(词尾"app")
                         └─'b'→ n4 ─'a'→ n5 ─'t'→ n6(词尾"bat")

        base[]  check[]       含义：子节点下标 = base[父] + code(字符)
        ┌────┬──────┐
  idx 0 │ 1  │  -1  │  root：base=1，check=-1（根）
  idx 1 │ ?  │   0  │  n1   ：'a' 的 code=1 → 1+1=2…（实际由 base 决定）
  idx 2 │ 4  │   0  │  子节点 = 1 + code
  idx 3 │ -3 │   1  │  base<0 ⇒ 词尾（绝对值=词长，或指向词 ID 表）
  idx 4 │ …  │   0  │
  └────┴──────┘
  查 "app"：状态 s=0 →(a) s=base[0]+1 →(p) s=base[s]+16 →(p) → base[s]<0 ⇒ 命中词 ID
  代价：每字符一次数组随机访问；无指针、无 map、**无 GC 对象**
```

`check[]` 的唯一用途是**验证这次转移是真的**（防止 `base[父]+code` 撞到别的节点的槽位），所以每个状态 8 B 就够。**DAT 的本质是"用一次多余的比较，换掉一个指针字段"，从而把树摊平成两个可 mmap 的数组。**

### 内存估算：1 亿词条要多少内存

| 实现 | 每状态字节 | 状态数 | 总量 | 单机 64 GB 判定 | 备注 |
| --- | --- | --- | --- | --- | --- |
| 指针 Trie（每节点 Go map） | 64~80 B（map header + entry + GC 冗余） | 4.0 亿 | **26~32 GB**（GC 后常报 50 GB+） | ⚠️ 勉强，尾延迟抖动 | 构建期内存峰值 ×2 |
| 指针 Trie（每节点定长 `[256]int32`） | 1 KB | 4.0 亿 | **400 GB** | ❌ 不可能 | 只在学校作业里存在 |
| **双数组（无压缩）** | 8 B，负载因子 0.5 → 实际 16 B | 4.0 亿 | **6.4 GB** | ✅ | 冲突探测使构建耗时 ×2 |
| **双数组 + tail 后缀压缩** | 8 B × 1.7 + tail 1 B/字符 | 1.2 亿 | **2.6 GB** | ✅ 且留出缓存空间 | **本篇默认** |
| FST（MAP 无环自动机，共享后缀） | 更激进的后缀共享 | 1.2 亿 | **1.4~1.8 GB** | ✅ 只读场景首选 | 只能离线构建，不可增删 |

状态数怎么来的（**必须给公式，不许背数字**）：

```
状态数 ≈ 总字符数 × (1 − 前缀共享率)
  1 亿词条 × 平均 10 码点 = 10 亿字符
  前缀共享率 62%（SKU 同前缀 "SKU-<类目>-"、品牌同前缀、编码同前缀）
  → 4.0 亿状态（无压缩）；折叠单链后 → 1.2 亿状态（tail 压缩）
  → 内存 = 状态数 × 8 B ÷ 负载因子 0.5 ≈ 状态数 × 16 B
```

### 三种前缀压缩，各自买什么

| 压缩 | 做什么 | 收益 | 代价 |
| --- | --- | --- | --- |
| **路径压缩**（radix / 压缩前缀树） | 单子节点链折成一个"边标签串" | 状态数降 3~5 倍 | 边走边比字符串，实现复杂 |
| **tail 压缩**（DAT 标准做法） | 保留节点只到"分叉点"，剩余后缀存 tail 数组 | 状态数 4 亿 → 1.2 亿 | 每个状态多一次 tail 比较 |
| **FST / 有限状态转换器** | 无环自动机，**后缀也共享**（suffix sharing） | 再降 40% | 完全只读，构建需全量排序，不支持增量 |

选型口诀：**要增量 + 要快 → DAT + tail；只读 + 要省内存 → FST；词条 < 100 万 → 别压缩，指针 Trie 就够（省下的开发时间比省下的 200 MB 值钱）。**

### 增量构建：为什么"原地插入"是个陷阱

DAT 的 `base[]/check[]` 是一张**全局位移表**。插入一个新词可能要求某个节点的所有子转移整体搬到别处，而"别处"又被别的节点占着——**级联搬迁的复杂度不可控**，一个坏词条可以让构建时间从 4 小时变成 40 小时。所以工程上只有三种做法：

| 策略 | 做法 | 可见延迟 | 构建成本（1 亿词条，8 核） | 适用 |
| --- | --- | --- | --- | --- |
| **全量重建** | 从权威源重新构建整棵 Trie，原子替换 | 重建周期（3~4 h） | 3.5 h | 词典结构变更（换分词器/编码规则） |
| **双缓冲增量** | 内存里维护"基座 + delta 小 Trie"，每 N 分钟把 delta 合入新副本，指针一次替换 | 合并周期（5 min） | 增量合并 12 s/次 | **默认方案** |
| **分段索引** | 多个小 Trie 按时间分段，查询时逐段查再合并 | 秒级 | 每段独立构建 | 关键词表更新极快（黑名单） |

### 并发读写：双缓冲 + 原子指针，别用 RWMutex

```
        ┌─────────── 读路径（无锁，1.4 万 QPS）───────────┐
  请求 ──► load(atomic.Pointer[DAT]) ──► 只读遍历（DAT 构建后完全不可变）
                     ▲
                     │ store(newPtr)  ← 一次指针写，毫秒级完成切换
        ┌────────────┴───────────────┐
        │  写侧：在旧副本基础上合并 delta，构建新 DAT（后台线程）
        │  构建期间旧副本仍在服务；新副本校验通过（词条数 + 抽样 200 词命中）后才替换
        └────────────────────────────┘
```

| 方案 | 读延迟 | 写延迟 | 内存 | 判定 |
| --- | --- | --- | --- | --- |
| `sync.RWMutex` 全局锁 | ✅ | ❌ | 1× | 写一次就阻塞所有读，构建期等于停服 |
| 分段锁（按首字符分 26 段） | ⚠️ 跨段查询要锁两次 | ✅ | 1× | 只在"必须原地改"时用 |
| **copy-on-write + atomic.Pointer** | ✅ 无锁 | 构建期 1 次 | 2×（构建期） | ✅ **默认**；2×2.6 GB 可接受 |
| 双缓冲（两块固定内存交替） | ✅ 无锁 | ✅ | 2×（常驻） | 更新极频繁时用，省掉反复分配 |

> **铁律：构建完成的 DAT 必须被视为不可变对象。** 任何"原地修一个词"的需求，都应该被翻译成"产生一个新副本"——因为一次原地修改会破坏 `base/check` 的全局不变量，而这类 bug 只会在别人的查询上偶发命中错误词。

### AC 自动机：把 12 万次字符串匹配压成一次文本扫描

AC = Trie + **fail 指针**（失配时跳到"最长真后缀"节点）+ **输出链**（把沿途所有词尾攒起来，包括重叠命中）。

```
        fail 指针让"扫一遍文本"就能找出所有模式（含重叠）
        root ─'s'→ s ─'h'→ sh ─'e'→ she*      *=词尾
                     │      └─fail→ h ─'e'→ he* …
                     └─fail→ root
        扫 "ushers"：
          u(失配) s → s h → sh e → she*（命中）
          继续 r：she 无 'r' → fail 到 he → he 无 'r' → fail 到 root …
          s → s h → sh e → she* r → sher? → fail → her? → … → 命中 "hers"
        一次线性扫描 O(文本长度 + 命中数)，与模式数无关
```

| 规模 | 状态数 | 内存（base+check+fail+输出 ≈ 16 B/状态） | 单 KB 文本耗时 |
| --- | --- | --- | --- |
| 1 万敏感词 | 3.4 万 | 0.5 MB | 0.08 ms |
| 12 万敏感词 | 40 万 | **6.4 MB** | 0.2 ms |
| 100 万词 | 350 万 | 56 MB | 0.4 ms |

**AC 的三个真实陷阱**（机制细节见 [17 搜索系统深窥](17-search-system.md) 与 `eng/37`，这里只给形态侧结论）：

| 陷阱 | 长什么样 | 处置 |
| --- | --- | --- |
| 假阳性 | 「色情」命中「彩色情况」 | 必须配**后缀/边界规则**或二次正则校验，AC 只做候选生成 |
| Unicode 归一化 | 全角/半角、繁简、零宽字符绕过 | 扫前统一 NFKC + 去零宽；**不归一化等于漏召** |
| 重叠与长词优先 | 「赌博」与「赌博网站」都命中 | 输出链要给词 ID + 长度，由业务规则决定最长匹配还是全报 |

## 16.6 倒排索引：把「文档里有这个词」翻成「这个人在哪些文档里」

Trie 和 AC 解决的是「**给我一段文本，告诉我命中了哪些词**」。倒排解决的是反方向的问题：「**给我一个词/一组词，告诉我哪些文档该被召回**」。两者的选择由查询方向决定，这是最容易被搞混的一点。

### 结构：词典 + 倒排表，以及两级查找的成本

```
词 → 倒排表（docId 的有序列表）
       │
       ├─ 词典（term dictionary）：有序 + 前缀压缩，落在内存或 mmap
       └─ 倒排表（posting list）：docId 差分编码 + 位图/跳表加速
```

一次「A AND B」查询的真实成本不是「两次查找」，而是**两个有序列表求交**：

| 操作 | 不做优化 | 差分编码 + 跳表 | 位图（Roaring） |
| --- | --- | --- | --- |
| 求交 10 万 × 10 万 | 200 万次比较 | ~2 万次（跳表跳读） | ~1.5 万次（word 级位运算） |
| 内存 | 8 B/docId | 1–2 B/docId | 高频词反而更大 |
| 适用 | ❌ | **默认** | 高基数 + 频繁布尔查询 |

**关键判断**：倒排表的瓶颈从来不是「查词」，而是「**求交/求并的集合大小**」。所以设计倒排时的第一件事不是选压缩算法，而是**砍掉长倒排表**——像「的」「是」这种停用词，以及超高频词（出现率 > 5%），必须单独处理（跳过或用位图），否则一个高频词就能让查询退化成全表扫。

### 位置信息：要不要，决定内存翻几倍

| 需求 | 是否需要位置 | 内存代价 |
| --- | --- | --- |
| 只要「文档含这个词」 | 否 | 基准 |
| 短语查询（"红色 苹果" 相邻） | **是** | ×2–3 |
| 高亮片段 | 是（且要字符偏移） | ×3–4 |

**判断规则**：如果产品只需要「召回相关文档」而不需要短语精确匹配与高亮，就不要存位置信息。很多团队一开始就全字段带位置，结果内存翻三倍，最后发现这个功能无人使用。

## 16.7 多路召回与融合：召回不是一个索引，是一组互补的索引

这是本篇的核心架构结论：**没有单一结构能同时满足精确、模糊、语义三种需求**（§16.4 的能力矩阵已经证明）。所以生产系统永远是「多路召回 + 一次融合」。

### 融合的三种做法

| 融合方式 | 怎么算 | 优点 | 缺点 |
| --- | --- | --- | --- |
| 加权分数融合 | `score = Σ wᵢ · normalize(sᵢ)` | 可控，可解释 | 各路分数量纲不同，归一化是噩梦 |
| **RRF（倒数排名融合）** | `score = Σ 1/(k + rankᵢ)`，k 通常 60 | **不需要归一化**，鲁棒 | 丢掉分数间距信息 |
| 学习排序（LTR） | 用标注数据训练融合模型 | 效果最好 | 需要标注集与训练流水线 |

**默认选 RRF**。它最大的价值是绕过了「不同索引的分数不可比」这个根本问题——BM25 的 12.3 分和向量的 0.87 相似度没有任何可比性，但它们在各自列表里的排名是可以比的。这是本篇最实用的一条工程技巧。

### 每一路该取多少（截断策略）

```
总候选集 1000 条：
  精确匹配路   取 top 200   （高精度，几乎必对，可直接置顶）
  前缀 Trie 路  取 top 300
  倒排 BM25 路  取 top 500
  语义向量路    取 top 300
  ↓ RRF 融合去重 → 裁到 1000 → 交给精排
```

**截断原则**：每一路的截断点应该取「该路召回率曲线的拐点」，而不是固定值。判断方法很简单——把某一路的截断从 100 调到 1000，看最终 top-20 的结果变化了多少；变化 < 2% 就说明截断够了。**大多数系统在这一步浪费了 5 倍算力。**

## 16.8 召回率-延迟曲线：边际收益递减在哪里停手

| 路数 | P99 延迟 | 相对召回（以单路为基准） | 单路新增成本 |
| --- | --- | --- | --- |
| 1 路（倒排） | 18 ms | 100% | — |
| 2 路（+ 精确/前缀） | 24 ms | 118% | +6 ms |
| 3 路（+ 向量） | 41 ms | 137% | **+17 ms** |
| 4 路（+ 图关系/协同） | 55 ms | 143% | +14 ms |
| 5 路（+ 规则兜底） | 58 ms | 145% | +3 ms |

这张表的核心信息：**第 3 路（向量）是性价比的分水岭**——它带来 19 个点的召回提升，代价是延迟翻近一倍。第 4、5 路的边际收益已经降到个位数。

**所以架构上的停手点通常是 3 路**，第 4 路之后要靠「异步补召回」（先返回 3 路的结果，第 4 路如果快就追加）而不是串行等待。这个「**快路先回、慢路追加**」的模式对用户感知延迟几乎零代价，是本篇建议的默认做法。

## 16.9 索引更新：全量重建 vs 增量合并，以及「重建期间怎么办」

| 方式 | 延迟可见性 | 成本 | 适用 |
| --- | --- | --- | --- |
| 全量重建 | 重建期间查旧索引（**必须双索引**） | 高，需双倍资源 | 词典变化大 / 结构变更 |
| 增量合并（LSM 式） | 秒级可见 | 低 | 日常写入 |
| 逻辑删除 + 定期压实 | 删除生效有延迟 | 中 | 删除比例 < 10% |

**双索引切换是唯一正确的重建方式**（与 → [17 搜索系统深窥](17-search-system.md) 的别名切换同构）：

```
1. 影子索引开始构建（全量灌入 + 实时增量双写）
2. 构建完成后做抽样比对（新旧索引对同一批查询的 top-20 差异率 < 1%）
3. 原子切换读指针（1 秒内完成，可回滚就是把指针改回来）
4. 观察 24 h → 摘掉旧索引
```

⚠️ **一个必须提前决定的边界**：第 3 步的切换必须**原子**。如果你有 10 个查询服务实例各自读配置，切到一半时会出现「同一个查询在不同实例上返回不同结果」——用户刷新两次看到两种排序，这在搜索/推荐场景里是直接的信任损失。正确做法是切一个共享的指针（配置中心的一个 key / 一个路由表项），而不是逐个实例重启。

## 16.10 分片与路由：按什么分片，由「查询的前缀」决定

这是本篇第二个不可逆决策（第一个是 §16.4 的结构选择）。

| 分片键 | 前缀查询 | 精确查询 | 范围查询 | 判定 |
| --- | --- | --- | --- | --- |
| **按前缀首字符/哈希段** | ✅ 单分片 | ✅ | ⚠️ 可能跨片 | ✅ **前缀密集型选它** |
| 按文档 ID hash | ❌ **必须广播所有分片** | ✅ 单分片 | ⚠️ | 精确/随机查询型选它 |
| 按时间 | ❌ 全广播 | ❌ | ✅ | 只适合时间序列检索 |
| 按业务维度（租户/类目） | ⚠️ | ✅ | ⚠️ | 多租户隔离型选它 |

**判断方法只有一句**：**看你的查询里最高频的那个前缀/过滤条件是什么，就按它分片。** 如果一个系统里「按 ID 查」和「按前缀查」都是主查询，那它需要**两套索引**（一套按 ID 分片、一套按前缀分片），而不是一套索引硬扛——这正是 → [12 短链 · §12.5](12-shortlink-system-design.md) 里「主库按 slug、运营查询走异构投影」的同一个道理。

跨片查询的合并成本：如果是 top-k 合并，每片取 top-k 再归并是 O(k·n)，线性且可接受；如果是聚合（count/sum），必须全部返回再汇总，延迟由最慢的一片决定——**这是长尾抖动的常见来源**，需要给「每片超时后返回部分结果」的降级。

## 16.11 劝退节：什么时候你根本不需要这些

写这一节是因为**过度设计比缺失设计更常见**。三个判断问题，任何一个答「是」就回到 B+ 树：

1. **数据量 < 500 万行，且查询都是精确相等或前缀？**
   → MySQL 联合索引 + `LIKE 'abc%'`（右模糊可用索引）就够。别上 ES。
2. **匹配规则是「字段等于某值」而不是「文本里含某词」？**
   → 这不是文本匹配，是过滤。用索引 + 位图都行，AC 自动机在这里毫无价值。
3. **召回要求「全命中、不能漏」？**
   → 注意方向：AC/Trie 是**全命中**的（不漏），倒排是**按相关性截断**的（会漏）。如果业务是敏感词审核这类「不准漏」，那么正确结构是 AC 自动机，而不是 ES——用 ES 做审核会漏词，这是很典型的选型错误。

## 16.12 与向量检索的衔接：什么信号出现时才该引入语义召回

不要因为「有 embedding」就上向量。三个信号，出现两个才考虑：

| 信号 | 怎么测 | 含义 |
| --- | --- | --- |
| 长尾查询零结果率高 | 抽样查 top1000 长尾词，命中率 < 60% | 字面匹配覆盖不了表达多样性 |
| 同义词/口语化需求明确 | 人工标注一批「不同说法同一意图」的 query | 倒排结构解决不了 |
| 已有 embedding 可用于其他链路 | 复用同一模型，边际成本低 | 单独为搜索建向量库不划算 |

引入后的正确位置是**作为一路召回，而不是替代**：向量召回擅长「找到相关但用词不同」的，倒排擅长「精确命中与可解释性」，两者用 RRF 融合（§16.7）。细节 → [18 向量系统 · §18.5](18-vector-system.md)。

## 16.13 L0 → L5：每一级换的都是「索引结构」而不是「机器数量」

| 阶段 | 形态 | 数据量 | **换挡信号（硬阈值）** | 代价 |
| --- | --- | --- | --- | --- |
| L0 | MySQL `LIKE '%kw%'` | 10 万行 | 查询 > 1 s / 全表扫 | — |
| L1 | MySQL 联合索引 + 右模糊 | 500 万行 | 需要「任意子串」或相关性排序 | 只能前缀匹配 |
| L2 | 单机倒排（Lucene/ES 单节点） | 5000 万 | 单节点 HEAP > 30 GB / QPS > 2000 | 无高可用 |
| L3 | ES 集群 + 别名 + 多副本 | 10 亿 | 深度聚合打爆 / 分片 > 30 每节点 | 运维复杂度、JVM 调优 |
| L4 | 多路召回（倒排 + 向量 + 规则）+ 融合 | **10 亿+** | 长尾零结果率 > 30% | 多套索引、融合排序、评测体系 |
| L5 | 分层索引（热内存 + 温 SSD）+ 学习排序 | 百亿 | 单群容量上限 / 排序效果进入平台期 | 极度复杂，需要专属团队 |

> **L1→L2 的临界点有误导性**：很多人以为「MySQL 撑不住」是因为数据量，其实真实原因是**查询形态变了**——从「前缀匹配」变成「相关性排序」的那一刻，B+ 树就从根本上不适用了，跟数据量无关。所以判断换挡时，先看查询形态是否变化，再看数据量。

## 16.14 这个形态特有的崩法

| 失效 | 长什么样 | 定位方法 | 预防 |
| --- | --- | --- | --- |
| 长倒排表 | 某个高频词让查询降到 5 s | 按 term 看倒排表长度分布 | 停用词 + 高频词走位图或跳过 |
| 前缀分片选错 | 前缀查询广播所有分片，QPS 放大 N 倍 | 看单查询命中的分片数 | 按前缀分片（§16.10） |
| Trie 内存爆 | 词条涨到千万，进程被 OOM kill | 监控 Trie 常驻内存曲线 | 双数组 + 前缀压缩 + 分片部署 |
| 增量构建写坏索引 | 并发插入导致 Trie 结构损坏，线上查询开始乱返回 | 查询结果与离线校验任务比对 | copy-on-write 双缓冲，禁止原地改 |
| Unicode 未归一化 | 全角/零宽字符绕过敏感词 | 构造绕过样本做回归测试 | 扫前 NFKC 归一 + 去零宽 |
| 多路融合分数量纲错 | 某一路持续霸屏，其他路形同虚设 | 统计各路贡献的 top-20 占比 | RRF 而不是分数加权 |
| 索引重建切换不原子 | 同一 query 刷新两次结果不同 | 多实例结果一致性抽样 | 共享指针原子切换（§16.9） |

## 16.15 砍掉 90% 预算

从 60 台（索引 40 + 融合排序 12 + 向量 8）砍到 6 台、去掉向量路与 LTR：

| 保留 | 砍掉 | 后果 |
| --- | --- | --- |
| 单套倒排 + 前缀 Trie + RRF 融合（两路） | 向量召回、学习排序、分层索引 | 长尾查询零结果率从 12% 升到 30%，精确与前缀需求完全不受影响 |
| 全量重建（夜间）+ 双索引切换 | 实时增量 | 新内容最迟 T+1 可见 |
| 单副本 + 定时快照 | 多副本高可用 | 重建期间不可用，只能靠夜间窗口规避 |

**结论：这个系统的必需品是「一套正确的索引结构 + 正确的分片键 + RRF 融合」。** 向量、LTR、分层索引全是效果与规模驱动，而且在预算被砍时应当**先砍效果、后砍可用性、绝不砍分片键**——分片键错了，那就是重写而不是降级。

## 16.16 十分钟答题卡

```
1  量级    数据量 → 索引类型；QPS → 分片数；更新速率 → 增量 vs 全量
2  真问题  没有单一结构能同时满足精确/模糊/语义 → 必须多路 + 融合
3  形态    六种匹配需求 × 唯一正确结构（能力矩阵表）
4  结构    Trie/AC 做字符级全命中；倒排做相关性截断（方向相反，别搞混）
5  融合    RRF 绕过分数量纲不可比；每路截断取拐点，不是固定值
6  停手    3 路是性价比分水岭，第 4 路起改"异步追加"
7  分片    按最高频的查询前缀分片；两套主查询 = 两套索引
8  重建    双索引 + 原子切换共享指针（不原子 = 刷新两次两种结果）
9  劝退    500 万行以内、过滤型、必须全命中 → 别上这些（§16.11）
10 必需    正确的结构 + 正确的分片键 + RRF；向量/LTR 是效果驱动
```
