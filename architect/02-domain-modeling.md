## 02.1 引子：一次「按表拆服务」，赔了 34 万

**2025-11-10，某电商把「下单」按数据库表拆成两个服务**：`order-service` 管 `orders` / `order_lines`，`stock-service` 管 `stock`，中间用 MQ 事件协同。拆分方案在评审会上全票通过，理由是「订单和库存本来就不是一个东西，各自独立扩缩容」。

上线当天晚上就炸了。

| 时刻 | 事件 | 可观测数据 |
| --- | --- | --- |
| 11-10 20:00 | 下单链路灰度 10%，两服务各写各库，`deduct` 为同步 RPC | 下单峰值 4,200 QPS |
| 11-10 20:30 | 库存库 CPU 84%，`deduct` P99 从 8 ms 涨到 340 ms | 超时率 3.1% |
| 11-10 20:41 | 网关对 `deduct` 超时**自动重试**，请求未带幂等键 | 重复扣减 6,140 次 |
| 11-10 20:47 | 订单库插入撞 `uk_order_no`，事务回滚，异常被 catch 后直接返回失败，**没有调用 `release`** | 1,860 笔「扣了库存没建单」 |
| 11-10 21:05 | 扣减 SQL 只判 `available_qty > 0`，未判「已被预留」 | 62 个 SKU 库存为负 |
| 11-10 21:20 | 超卖订单已支付并发货 | 640 单 |
| 11-11 09:00 | 库存流水 vs 订单表对账，发现差异 | 差异明细 8,000 条 |
| 11-11 ~ 11-13 | 人工冲正、盘库、补偿、赔付 | 见下表 |

| 损失项 | 数量 | 口径 | 金额 |
| --- | --- | --- | --- |
| 超卖订单履约赔付 | 640 单 | 120 元/单 | 7.68 万 |
| 无货取消补偿券 | 2,300 单 | 30 元/单 | 6.90 万 |
| 负库存导致的超卖退款损失 | 62 SKU | 按毛利反算 | 12.50 万 |
| 客服工单 | 4,800 张 | 8 元/张 | 3.84 万 |
| 人工冲正与盘库工时 | 3 天 × 6 人 | 1,800 元/人日 | 3.24 万 |
| **合计** | | | **≈ 34.2 万** |

**复盘的第一版结论是错的**：「分布式事务没做好，上 Seata」。它错在假设问题出在**提交协议**上。

> **真正被撕开的是这条不变量**：
> `库存表.available_qty ≥ 0` 且 `Σ(已预留) ≤ 可售`，**任何时刻**成立。
> 拆分后，前半条由 `stock-service` 的本地事务守，后半条的「已预留」由 `order-service` 的一个字段隐含表达——**没有任何一处代码在每次写入时校验整条断言**。

分布式事务能保证「两个事务一起提交或一起回滚」，但它**不能把一条已经被撕成两半的不变量重新粘起来**：如果连「谁在每次写入时校验它」都找不到，那么无论提交协议多强，中间态都会立刻暴露给真实世界（用户点下支付的那一刻）。

这就是本篇的全部内容：

```
聚合切对  → 不变量有唯一守护者  → 本地事务足够  → 一致性问题是工程问题
聚合切错  → 不变量被撕成两半    → 上什么协议都不够  → 一致性问题变成事故
```

## 02.2 到底是什么：聚合的定义与四个反例

### 定义

> **聚合（Aggregate）= 一个由不变量圈定的一致性边界**：一组对象，它们之间的不变量必须在**同一个本地事务**里被守护；聚合根是外部访问这个边界的唯一入口；聚合的边界同时是**事务边界、校验边界与生命周期边界**。

三件事必须同时成立，才叫一个聚合：

| 维度 | 含义 | 判定的话 |
| --- | --- | --- |
| 事务边界 | 边界内所有写入在同一事务提交 | 「这两个修改，失败一个是否必须一起回滚？」 |
| 不变量 | 边界内有一条恒真的断言，每次写入后都要校验 | 「有没有一句『任何时刻都成立』的话？」 |
| 生命周期 | 边界内对象的生与死绑定在一起 | 「A 删除时 B 是否必须一起消失？」 |

### 聚合边界图：一次下单，三条不变量

```
┌─ Order 聚合（一个本地事务）────────────┐
│ Order ◀── OrderLine × N                │
│ 不变量：Σ行金额 − 优惠 = 应收总额       │
│ 同事务写：outbox(OrderPlaced)           │
└─────────────┬─────────────────────────┘
              │ 事件 OrderPlaced（异步可重放）
    ┌─────────┴──────────┐
    ▼                    ▼
┌ StockReservation ┐ ┌ CouponGrant ─┐
│ 一 SKU 一行       │ │ 一张券一行    │
│ 已预留 ≤ 可售      │ │ 只能用一次    │
└──────────────────┘ └──────────────┘
  ✗ 三聚合进同一个 @Transactional
  ✗ order 直接 UPDATE stock 数量
```

### 四个反例：这些都不是「聚合」

```text
反例 1：「一张表一个聚合」
  orders(status) 与 order_lines 是两张表，但「行金额之和 = 订单总额」是一条不变量。
  按表切 → 总额与明细可以分开提交 → 「总额不等于明细之和」的订单会被真实创建出来。
  同一张表也可能装两个聚合：用户表的「账户」与「登录凭据」各自有不变量、变更频率差 100 倍。

反例 2：「一个实体一个聚合」
  实体是名词，聚合是边界。同一个名词在不同上下文里是不同聚合：
  User 在「认证」上下文里是 Credential（不变量：密码哈希不可逆），
       在「会员」上下文里是 Member（不变量：等级与成长值单调）。
  两处强行共用一个 User 类 → 认证团队改一个字段要会员团队回归。

反例 3：「一个服务一个聚合」
  服务的部署边界由组织与容量决定，聚合边界由不变量决定。
  一个上下文里通常有 3~8 个聚合（订单、库存预留、优惠券核销、账本分录…），
  一个聚合也可能跨两个服务的技术实现（但绝不跨事务）。

反例 4：「整库一个聚合」
  把所有不变量塞进一个事务：库存热点行的锁持有时间从 3 ms 涨到 27 ms，
  同一行的吞吐上限从 333 次/秒掉到 37 次/秒（推导见 §02.3）。
  边界太大 = 用吞吐换一致性，且失败面覆盖全部业务。
```

**贫血模型为什么必然失败**：对象只有 getter/setter，不变量散落在 `Service` 的 `if` 里；只要有多个入口（HTTP + 定时任务 + 运营脚本），必有一处忘写校验。**不变量必须住在有唯一入口的地方**——这就是聚合根存在的理由（反模式见 §02.16）。

## 02.3 唯一真问题与「聚合边界 = 吞吐上限单位」

### 一句话

> **建模的产物不是类图，是「哪些不变量必须由同一个事务守护」。**
> 类图是这句断言画完之后的投影；先画类图再问一致性，一定会画出「图上有、事务里没有」的边。

### 一次下单要碰几个聚合：这是可推导的，不是凭感觉

| 聚合 | 必须同事务？ | 它守护的不变量 |
| --- | --- | --- |
| `Order`（含 `OrderLine`、`Money`） | **是** | Σ行金额 − 优惠 = 应收总额；状态迁移合法 |
| `Outbox`（同库） | **是** | 状态与「已发出的事件」不可分叉（→ `eng/10`） |
| `StockReservation` | 否（预留，可补偿） | 同一 SKU 的已预留量 ≤ 可售量 |
| `CouponGrant` | 否（核销，幂等） | 一张券只能被用一次 |
| `LedgerEntry` | 否（对账收敛） | 借贷平衡，允许延迟 |

### 量级：为什么聚合边界直接决定吞吐

```text
大促下单峰值            4,200 QPS（日常 380）
单次下单写操作          3 次（orders / order_lines / outbox）
头部集中度              0.3% 的 SKU 承担 45% 下单量
  → 单个热 SKU 命中    ≈ 4,200 × 45% / (头部 SKU 数)  ≈ 1,900 次/秒

锁持有时间 vs 吞吐上限（单行，InnoDB 行锁）：
  只锁「库存预留」一行        t = 3 ms   → 上限 = 1000/3  ≈ 333 次/秒
  把库存+优惠券+积分并入订单   t = 27 ms  → 上限 = 1000/27 ≈  37 次/秒
```

**两条结论**：

1. **聚合边界是吞吐的上限单位。** 边界内每多一行被锁的表，热点行的理论吞吐就按倍数下降；这不是「优化问题」，是**边界选错之后的物理后果**。
2. 333 次/秒 也已小于 1,900 次/秒 的现实命中，所以「库存扣减」注定不能是下单主事务的同步一部分——**它要么是独立聚合 + 预留（可补偿），要么在热点 SKU 上分桶**（分桶与异步形态见 `05 写路径形态`）。

> 这正是七问 ③ 的意义：**先算出「必须原子」的那一小段有多小，再决定边界画在哪。** 不变量是逻辑判断，吞吐是物理约束，二者共同裁决边界。

## 02.4 聚合识别的三条判据

### 判据表（评审时逐条念）

| # | 判据 | 问句 | 通过（应合并为同一聚合） | 不通过（应拆开） | 误判代价 |
| --- | --- | --- | --- | --- | --- |
| 1 | **事务边界** | 「这两个写入失败一个，业务是否必须一起回滚？」 | 部分成功会产生不可能的业务状态 | 部分成功只是一个中间态，且能被补偿 | 该合没合 → 需要分布式事务；不该合却合了 → 锁竞争与失败面扩大 |
| 2 | **不变量** | 「有没有一句『任何时刻都成立』的断言？」 | 断言涉及的全部数据都在边界内 | 断言必须扫描边界外数据才能校验 | 边界外的断言永远没人校验 = 本篇引子 |
| 3 | **生命周期一致性** | 「A 删除时 B 是否必须一起消失？」 | 一起创建、一起归档、一起失效 | B 活得比 A 长（或反之） | slug/墓碑类错误：把「永不死的标识符」挂在「会被删的链接」下面 |
| 4（辅助·反向） | **变更频率一致性** | 「两者的写入频率差几个数量级？」 | 同量级 | 差 > 100 倍 | 每次写低价值字段都去锁高价值行（点击计数 vs 链接目标） |
| 5（辅助·反向） | **入口唯一性** | 「有几个入口能改它？」 | 只有一个入口（聚合根方法） | 多个入口（HTTP + 定时任务 + 运营 SQL） | 贫血模型 + 多入口 = 迟早漏一处校验 |

### 判据怎么用：三条要全部通过才合并

```text
合并的必要条件：不变量存在（判据 2）
合并的充分条件：事务边界必须原子（判据 1）
合并的否决条件：生命周期不一致（判据 3）—— 一票否决

例：Order 与 OrderLine
  不变量 ✅（行金额之和 = 总额） 事务 ✅（一起提交） 生命周期 ✅（一起删）→ 合并

例：Order 与 StockReservation
  不变量 ✅（已预留 ≤ 可售）   事务 ❌（允许短暂超预留，靠补偿收敛）
  生命周期 ❌（预留过期而订单还在）→ 拆开，用领域事件 + 对账收敛

例：ShortLink 与 slug 唯一性
  不变量 ✅（全局唯一） 事务 ❌（校验要扫全库） 生命周期 ❌（slug 永不死）→ 拆开（§02.5）
```

## 02.5 反例演示：为什么 slug 唯一性不属于 `ShortLink` 聚合

这是 `12` §12.4 那条论断的完整推理，也是全篇最反直觉的一处。**能复述这个推导的人，不会写出「删除后重建同 slug」的代码。**

### 假设 slug 是 `ShortLink` 的属性，会发生什么

```text
断言写成：∀ 链接 l ∈ ShortLink 集合，l.slug 唯一
校验方式：插入前查询「这个 slug 存在吗？」

问题 1（事务边界不可能）：
  唯一性断言的校验范围 = 整个 ShortLink 集合
  → 若要在事务里校验，事务边界 = 全表 = 全库
  → 结论：这条断言天生不能由一个聚合的本地事务守护

问题 2（生命周期反了）：
  ShortLink 会被删除/归档/租户退租；slug 一旦印在瓶身、二维码、合同上就永不消失
  → 把 slug 挂在 ShortLink 下面，等于说「宿主死了，标识符也死」
  → 于是自然写出「删除后新建同 slug 的链接」
  → = 劫持别人已印刷的流量（12 §12.1 事故一的直接成因）
```

### 正确的切法

| 事实 | 归属 | 守护方式 |
| --- | --- | --- |
| slug 的**分配**与**永不复用** | 独立聚合 `SlugAllocation`（或上下文 `SlugNamespace`） | 唯一索引 + append-only 墓碑表（只归档不清空） |
| slug 的当前目标与状态 | `ShortLink` 聚合 | 版本化 `link_version`，目标变更 = 新增版本（→ `12` §12.6） |
| 「谁在什么时候拿到了这个 slug」 | 与 `SlugAllocation` 同事务的审计记录 | 一租户一时点一 slug 的唯一约束 |

**关键的一句**：

> **slug 不是链接的属性，是命名空间发出去的一张凭证。**
> 凭证的生命周期由签发者决定，不由使用者决定。这就是判据 3（生命周期一致性）的一票否决。

### 顺手用同一套判据处理短链的第二个问题

| 问题 | 判据答案 | 结论 |
| --- | --- | --- |
| 点击计数属于 `ShortLink` 吗？ | 写入频率差 10⁵ 倍（写 58 QPS vs 读 58 万 QPS）、可丢、不需与 target 原子 | 独立（点击流 → 分析面，见 `12` §12.8） |
| 封禁名单属于 `ShortLink` 吗？ | 不变量：封禁必须秒级对全边缘生效，且「谁能封」与「链接怎么建」是不同的权限模型 | 独立聚合 `Policy`，走旁路广播 |

## 02.6 限界上下文：四种错误切法

**限界上下文（Bounded Context）= 一个领域词只有一种含义的范围。** 它与聚合的分工：聚合管「事务边界」，上下文管「语言边界」。四种常见的错切，每一种都能在上线 3 个月内被识别出来。

```
┌───────────────────────────────────────────────────────────────────────────┐
│                        上下文图（正确形态）                                 │
│                                                                           │
│   ┌────────────┐  Partnership   ┌────────────┐                            │
│   │  订单 Order │◀──────────────▶│  支付 Pay   │  同发布节奏、同步接口       │
│   └─────┬──────┘                └─────┬──────┘                            │
│         │ 事件 OrderPlaced             │ ACL                               │
│         ▼                             ▼                                    │
│   ┌────────────┐   Shared Kernel  ┌────────────┐                          │
│   │库存 Inventory│◀── Money/Qty ──▶│  三方渠道    │  银行/物流：防腐层翻译     │
│   └─────┬──────┘                  └────────────┘                          │
│         │ Customer/Supplier                                               │
│         ▼                                                                 │
│   ┌────────────┐   Separate Ways  ┌────────────┐                          │
│   │ 履约 Fulfill │ · · · · · · · ·│ 审计 Audit  │  自己存一份，靠对账        │
│   └────────────┘                  └────────────┘                          │
│                                                                           │
│   禁止：任一上下文直接 import 另一上下文的 domain 类，或直连其数据库          │
└───────────────────────────────────────────────────────────────────────────┘
```

| 错误切法 | 会长成什么样 | 上线 3 个月内必然出现的症状 | 代价 | 正确做法 |
| --- | --- | --- | --- | --- |
| **按技术层切**（controller / service / dao / mq 各成服务） | 四个仓库、四次发布，一个业务需求横跨全部 | 改一个字段要四个 PR、四次上线，联调靠提前两周约 | 变更频率被强制同步；每次发布都全栈回归 | 按业务能力切；技术分层只作为**包内目录**存在（§02.8） |
| **按团队切**（Conway 直接当边界） | 边界跟随汇报线，组织一调整边界就碎 | 每次组织架构调整后一个月内出现「双写」和「两边都能建订单」 | 架构稳定性 = 组织稳定性；跨团队的共享表浓度上升 | 边界从业务能力推导，团队按边界组建（反向 Conway） |
| **按数据库表切**（一张表一个服务） | `orders`、`order_lines`、`coupons` 各一个服务 | 跨表 join 变跨服务调用，N+1 RPC，P99 涨 5~10 倍；不变量被撕成两半 | **本篇引子**：34 万赔偿 | 先定聚合（判据 1/2/3），再定上下文；一个聚合内的多表留在同一服务同一事务 |
| **按 CRUD 切**（读服务 / 写服务按动词拆） | `query-service` + `command-service` 各自持有写权限 | 同一个聚合出现两个写入者，状态互相覆盖；对账时对不上 | 丢失更新（→ `eng/30` §30.4「先查后写」） | 写侧唯一所有者；读侧只能是**投影或只读副本**，不得回写 |

> **一条判据**：切开后的两部分，是否**各自能说清自己守护哪条不变量**？说不清的那一侧不是上下文，只是一个层。

## 02.7 正确的切分方法：能力 → 频率 → 一致性

三个动作，**顺序不能换**：先按业务能力找候选，再用变化频率校验，最后用一致性边界裁决。

```text
① 这个业务里有哪条断言必须「任何时刻都成立」？
│
├─ 没有 ─────────────────────▶ 不需要聚合。用「功能模块 + 读模型」（报表、看板、搜索）
│
└─ 有（记下这条断言）
   │
   ├─ 断言只涉及一个主实体及其子对象
   │     └──▶ 【一个聚合】事务边界 = 主实体 + 子对象 + Outbox
   │
   ├─ 断言跨两个实体，允许「短暂为假、最终收敛」，且有补偿与对账
   │     └──▶ 【两个聚合 + 领域事件】中间态必须可被观测、可被对账
   │
   └─ 断言跨两个实体，且不允许任何时刻为假
         ├─▶ 合并聚合（接受锁竞争，量级必须重算 → §02.3）
         └─▶ 或改业务规则：引入「预留」把「不允许为假」降级成「允许短暂超额 + 补偿」
              ← 电商库存走的就是这一条

② 变化频率校验（反向判据 4）
   同一聚合内两个字段的写入频率差 > 100 倍？→ 高频的那个挪去独立聚合/独立存储
   例：link.target（人工，每天几十次） vs link.hit_count（机器，每秒几十万次）

③ 一致性边界裁决（判据 1）
   合并后，热点行的锁持有时间 × 命中 QPS 是否超过单行吞吐上限？
   超过 → 边界太大，回到 ① 找「预留/分桶」降级方案

④ 语言边界（上下文）按业务能力划，不按技术层划
   判据：同一个词在两侧含义是否不同？「库存」在库存上下文 = 可售数量，
        在下单上下文 = 能否下单的布尔判断 → 含义不同 = 两个上下文
```

| 分析对象 | 业务能力候选 | 变化频率 | 一致性结论 |
| --- | --- | --- | --- |
| 下单 | 订单管理（Order） | 每周 | `Order` 聚合 + Outbox 同库事务 |
| 库存 | 库存管理（Inventory） | 每日（规则）+ 每秒（数量） | `StockReservation` 独立聚合；数量与规则**再拆一层** |
| 优惠 | 营销（Marketing） | 大促前高频，平时冻结 | `CouponGrant` 独立聚合；核销走幂等命令 |
| 报表 | 数据分析 | 随时 | **无聚合**，只有读模型（→ `11 数据闭环`） |

## 02.8 统一语言落地：包结构、命名纪律、词表映射

统一语言不是文档，是**编译期能被强制执行的命名**。下面是 `12` 那套短链控制面的落地目录树（Java 21 + Spring，六边形分层）：

```text
commerce/
├── order/                          ← 限界上下文 = 业务能力，不是技术层
│   ├── domain/                     ← 纯领域：不 import 任何框架
│   │   ├── Order.java              聚合根（唯一入口）
│   │   ├── OrderLine.java          聚合内部实体：无 Repository
│   │   ├── OrderStatus.java        状态枚举 + 迁移守卫
│   │   ├── OrderRepository.java    端口（接口），实现在 adapter 侧
│   │   └── OrderPlaced.java        领域事件（过去式）
│   ├── application/                ← 用例：事务边界在这里，别处不许开事务
│   │   ├── PlaceOrderHandler.java
│   │   └── CancelOrderHandler.java
│   ├── adapter/
│   │   ├── web/OrderController.java       入站：只做参数校验 + 调用用例
│   │   ├── persistence/OrderRepositoryImpl.java
│   │   └── acl/InventoryAcl.java          出站防腐层（§02.10）
│   └── OutboxRelay.java            与聚合同库（→ eng/10）
├── inventory/                      ← 另一个上下文，禁止 import order.domain
└── sharedkernel/                   ← 只允许：Money / Qty / DomainError 三个类
```

| 领域词 | 代码里的名字 | 表 / 列 | 不许出现 |
| --- | --- | --- | --- |
| 订单 | `Order`（聚合根） | `orders` + `order_lines` | `OrderBean`、`OrderDTO` 当聚合用 |
| 订单状态 | `OrderStatus` 枚举 | `orders.status` | `state`、`flag`、`type` 混用 |
| 下单（意图） | `placeOrder()` 命令 | 无（命令不落库） | `insertOrder`、`saveOrder` |
| 已下单（事实） | `OrderPlaced` | `outbox.payload` | `orderCreateMsg`、`OrderMQDTO` |
| 可售量 | `AvailableStock` | `stock.available_qty` | `stock`、`inventory_num`、拼音缩写 |
| 已预留量 | `ReservedQty` | `stock.reserved_qty` | 与 `available_qty` 合并成一个字段 |
| 表名纪律 | — | 复数名词 + 全项目同一风格 | `t_`、`tbl_`、拼音、无主语的缩写 |

**三条命名纪律**（可写进 CI 检查）：

1. **命令用祈使句现在时，事件用过去式**。`ReserveStock` vs `StockReserved`——写错这一个字，就有人把命令当事件广播（§02.12）。
2. **领域层的类名里不许出现 `DTO` / `VO` / `DO` / `Entity` 后缀**。出现即说明该对象是数据容器，不是领域对象（贫血入口）。
3. **同一个词在代码、DDL、API、文档里必须同一拼写**。允许做映射的地方只有一处：`adapter` 层（§02.10）。

## 02.9 上下文映射的五种关系

| 关系 | 含义 | 真实场景 | 代价 | 什么信号说明该换关系 |
| --- | --- | --- | --- | --- |
| **合作 Partnership** | 双方共同演进、同步发布，谁也不能单独改接口 | 订单 ↔ 支付：同一发布窗口，联合回归 | 发布被绑死；一方延期全员延期 | 两侧发布节奏差 > 2 倍 → 退化为一主一从 |
| **共享内核 Shared Kernel** | 一小块模型双方共管共用 | `Money` / `Qty` / 币种 / 统一错误码 | 改一次全线重编译；语义漂移 | 共享包 > 20 个类或出现业务逻辑 → 拆成独立库 + 语义版本 |
| **客户-供应商 C/S** | 下游依赖上游，上游排期、下游接受 | 报表平台依赖订单服务的事件 schema | 下游被上游节奏绑架；需要契约测试 | 下游开始私自读上游库 → 立即升级为 ACL |
| **防腐层 ACL** | 下游建一层翻译，外部模型不进领域 | 三方物流、支付渠道、银行回单 | 一层映射代码 + 一次回归成本 | 三方接口变更频率 > 每月 1 次仍能承受，说明 ACL 有效，别拆 |
| **独立 Separate Ways** | 干脆不集成，各存一份 | 审计/合规自留全量凭证，只靠对账收敛 | 数据重复、口径可能不同 | 对账差异开始影响结算 → 必须有唯一口径方 |

| 反例 | 长什么样 | 后果 |
| --- | --- | --- |
| **大泥球 Big Ball of Mud** | `common` 包被 12 个上下文 import，里面既有 `Money` 也有 `OrderHelper` | 改一个工具类引发全站回归；所有边界名存实亡 |
| **共享数据库当集成** | 两个服务读写同一批表，靠「约定只改自己的列」 | 边界是礼仪性的；一次误写的 `UPDATE` 就跨边界（反模式 §02.16） |

## 02.10 防腐层实战：三方接口变了，领域不该知道

**目标**：外部模型（HTTP 字段、错误码、ID 格式、分页约定）只活在 `adapter/acl` 里，`domain` 包对它一无所知。

### Java：领域层（骨架）

```java
package commerce.inventory.domain;

/** 聚合根：库存预留。不 import 任何框架、任何外部 DTO。 */
public final class StockReservation {
    private final ReservationId id;
    private final Sku sku;
    private ReservedQty reserved;      // 已预留
    private final AvailableQty available; // 可售（来自聚合内快照）

    /** 不变量：已预留 ≤ 可售。每次写入后必须成立。 */
    public static StockReservation reserve(ReservationId id, Sku sku,
                                           AvailableQty available, Qty want) {
        if (want.isNegativeOrZero()) throw new DomainError("QTY_INVALID", want);
        if (available.lessThan(want)) throw new DomainError("STOCK_INSUFFICIENT", sku);
        return new StockReservation(id, sku, ReservedQty.of(want), available);
    }

    public void extend(Qty more) {           // 唯一修改入口
        ReservedQty next = reserved.plus(more);
        if (available.lessThan(next.value())) throw new DomainError("STOCK_INSUFFICIENT", sku);
        this.reserved = next;
    }

    public ReservationId id() { return id; }
    public Sku sku() { return sku; }
}
// 端口：只依赖领域类型；实现在 adapter.persistence
interface ReservationRepository {
    void save(StockReservation r);
    java.util.Optional<StockReservation> bySku(Sku sku);
}
```

### Go：防腐层（骨架）

```go
package acl

// 外部模型镜像：字段名照抄三方文档，只活在本文件里。
type wmsResp struct {
	Code int    `json:"code"`
	Msg  string `json:"message"`
	Data struct {
		Qty int `json:"qty_avail"` // 三方用整数，且可能为负
	} `json:"data"`
}

// 领域只认这个端口
type StockPort interface {
	Available(ctx context.Context, sku string) (domain.AvailableQty, error)
}
type wmsAdapter struct {
	cli  *http.Client
	base string
}

func (a *wmsAdapter) Available(ctx context.Context, sku string) (domain.AvailableQty, error) {
	req, _ := http.NewRequestWithContext(ctx, http.MethodGet,
		a.base+"/v2/stock?sku="+url.QueryEscape(sku), nil)
	resp, err := a.cli.Do(req)
	if err != nil {
		return domain.AvailableQty{}, domain.ErrUpstreamUnavailable // 翻译 1：传输错误
	}
	defer resp.Body.Close()
	var out wmsResp
	if err := json.NewDecoder(resp.Body).Decode(&out); err != nil {
		return domain.AvailableQty{}, domain.ErrUpstreamBadPayload
	}
	if out.Code != 0 { // 翻译 2：三方错误码 → 领域错误码
		return domain.AvailableQty{}, domain.MapUpstream(out.Code, out.Msg)
	}
	if out.Data.Qty < 0 { // 翻译 3：三方脏数据不许污染领域
		return domain.AvailableQty{}, domain.ErrUpstreamBadPayload
	}
	return domain.NewAvailableQty(out.Data.Qty), nil
}
```

### ACL 的三条纪律

| 纪律 | 为什么 | 违反后的样子 |
| --- | --- | --- |
| 外部 DTO **不许**进 `domain` 包 | 三方字段一改，领域对象跟着改，测试全线红 | 「改一个三方字段，编译错误出现在 40 个业务类里」 |
| 外部错误码**必须**翻译成领域错误 | 领域层不该知道「WMS code=5003 是超时」 | 业务代码里出现 `if (code == 5003)`，且散落 7 处 |
| 外部 ID **不许**当聚合根 ID | 三方换供应商时主键全变，历史数据断链 | 主键变成 `wms_warehouse_id`，迁移要重写全部外键 |

> **验证方式**：用三方历史响应样本录制回放。三方改字段时**只有 ACL 测试红，domain 测试必须全绿**——这就是防腐层有效的定义（§02.15）。

## 02.11 状态机：状态属于谁

状态机机制（五要素、三种落库姿势、并发条件更新、迁移日志）在 `eng/30` 讲透，这里**只给建模期的三条结论**。

### 状态 vs 事件 vs 命令：三者不许混

| 类型 | 回答什么问题 | 时态 | 可变性 | 例子 |
| --- | --- | --- | --- | --- |
| **状态 State** | 「现在在哪」 | 现在时 | 可变（但只经受控迁移） | `PAID`、`RESERVED` |
| **事件 Event** | 「已经发生了什么」 | 过去式 | **不可变** | `OrderPaid`、`StockReserved` |
| **命令 Command** | 「请你做什么」 | 祈使 | 可被拒绝 | `PayOrder`、`ReserveStock` |

三者混用的典型病灶：把命令当事件广播（没人能拒绝、没人负责终态，→ `eng/29`）；把状态写成业务字段（`status='REFUND_100_VIP'`，状态数按维度乘积爆炸，→ `eng/30` §30.6）。

### 聚合状态机（本篇的边界视图）

```
              placeOrder            payConfirmed
  [CREATED] ─────────────▶ [RESERVED] ────────────▶ [PAID]
     │  │                      │                     │
     │  │ cancel               │ reserveExpired      │ refundRequested
     │  ▼                      ▼                     ▼
     │ [CANCELLED]◀────────────┘                [REFUNDING]
     │ （终态：吸收）                                  │ refundSucceeded
     │                                               ▼
     └─ 注意：库存预留超时只是「RESERVED → CANCELLED」的一次迁移，
        绝不允许 order-service 直接改 stock 表的数量字段
```

**四条结论**（机制见 `eng/30`，此处只作建模判据）：

1. **终态必须显式且吸收**。没有终态的流程一定会卡；`CANCELLED` 之后还能被改成 `PAID` 的订单系统，账目会对不上。
2. **一次合法迁移必须同时满足四件事**：边被定义过、守卫成立、数据库里的当前状态仍是 `from`、迁移与本地动作同事务。第 3 条最常被忽略——「定义里允许 ≠ 此刻允许」。
3. **幂等迁移是幂等键的落点**。同一事件投递 N 次，只有第一次改变状态；证明方式是 200 并发同一单据推进，成功数 = 1（`eng/30` 的并发测试可直接搬进 CI）。
4. **非法迁移与版本冲突必须区分**。两者在 `UPDATE` 里都返回 0 行，混为一谈会导致「状态不合法」被无限重试。

### 状态该属于聚合内，还是工作流引擎？

| 判据 | 放聚合内（`orders.status`） | 放编排实例（工作流/状态机引擎） |
| --- | --- | --- |
| 迁移依赖什么 | 只依赖聚合自身数据 + 一个事实 | 依赖多个外部参与者的结果 |
| 是否需要「现在到哪一步」的运营视图 | 不需要，一个字段就够 | 需要：客服要查「退款走到哪一步」 |
| 是否有「必须等」 | 无（请求内完成） | 有：等人审批、等三方回调、等定时器 |
| 变更频率 | 低，跟着业务规则走 | 高，跟着促销/审批链变化 |
| 结论示例 | 订单支付状态、库存预留状态 | 退款/理赔/入驻审核流程 |

**三条边界**：

- 引擎只卖三件事：**持久化执行、可靠重试、可视化**（→ `eng/32`）。它不解决业务幂等，也不解决补偿正确性。
- 需要引擎当且仅当：流程里存在**「必须等」或「必须记住」**的东西，且等待超过一次请求的生命周期；否则你只需要一个函数。
- 允许两层并存：聚合内放**业务终态**，编排实例放**流程进度**，但每一层只能有一个决策者（→ `eng/29` 的「一个转移一个决策者」）。

## 02.12 领域事件 vs 命令

| 维度 | 命令 Command | 事件 Event |
| --- | --- | --- |
| 命名 | 祈使现在时 `ReserveStock` | 过去式 `StockReserved` |
| 方向 | 点对点，一个明确执行者 | 广播，0..N 订阅者 |
| 语义 | 请求，**可被拒绝** | 事实，**不可撤回** |
| 失败处理 | 发送方重试/补偿/告警 | 订阅方自己重试，不影响主流程 |
| 载荷重心 | 需要什么就给什么 + 期望值 | 发生了什么 + 聚合 ID + 版本 |
| 唯一键 | 幂等键（客户端生成） | `(aggregateId, version)` |
| 谁负责终态 | 发送方（或编排者） | 没有（所以事件不能承担终态判断） |

**最常见的错误是把命令写成事件**：`order.reserve-requested` 广播出去，等三个服务处理完——谁来判断「都处理完了」？没有人（→ `eng/29` 的无主广播）。

### 事件能不能携带完整状态：判断表

| 载荷内容 | 允许？ | 理由 |
| --- | --- | --- |
| 聚合 ID + 版本号 + 变化字段 + 发生时间 | ✅ **默认形态** | 消费方需要时按版本回查，事实最小化 |
| 只发 ID（不含任何变化字段） | ⚠️ 有条件 | 消费方被迫同步回查 → 上游不可用时下游全堵；只适合有 SLA 的内部同库 |
| 整个实体序列化（含手机号、地址、金额明细） | ❌ | 数据合规风险 + schema 漂移 + 消费者可能读到旧语义字段 |
| 不可变状态快照（带 schema 版本，消费方是分析/投影类） | ✅ 特例 | 投影重建需要全量；仍必须走 Outbox 保证与状态同事务（→ `eng/10`） |
| 嵌套了另一个聚合的实体 | ❌ | 跨聚合耦合进载荷 = 隐形共享内核（反模式 §02.16） |

**两条硬纪律**：事件 schema **只加字段，不改语义、不删字段**；事件投递必须与聚合状态同事务（Outbox），否则状态与事件分叉——这条在建模阶段就落进表结构。

## 02.13 依赖方向守护：什么依赖是架构违规

**判据一句话**：**依赖只能指向「更稳定、更不具体」的一侧。** 领域模型是这套系统里最稳定的东西，所以任何「领域 → 框架/存储/其他上下文」的依赖都是违规。

| 依赖 | 违规？ | 为什么 |
| --- | --- | --- |
| `domain` → `adapter`（Repository 实现、Controller） | ❌ 违规 | 领域被存储与协议绑死；换 ORM 要改业务代码 |
| `domain` → Spring / Jackson / JPA 注解 | ❌ 违规 | 领域单测必须能 `new` 出来，不启容器 |
| `order.domain` → `inventory.domain` | ❌ 违规 | 跨上下文共享模型 = 隐形共享内核，两侧再也无法独立演进 |
| `adapter` → `domain` | ✅ 合法 | 向外依赖向内，是六边形的正方向 |
| `application` → `domain` | ✅ 合法 | 用例编排聚合 |
| `controller` → `XxxRepositoryImpl` | ❌ 违规 | 绕过用例 = 事务边界丢失，且不变量校验被跳过 |
| 所有人 → `common`（且它在长大） | ⚠️ 高危 | 共享内核腐化成大泥球的第一步 |

## 02.14 演进路径：模块化单体 → 微服务

**默认答案是模块化单体。** 微服务的成本不是运维，是**把每一条不变量都变成一次需要补偿与对账的分布式问题**。

### 拆之前必须回答的五个问题

| # | 问题 | 答不上来会怎样 | 通过的样子 |
| --- | --- | --- | --- |
| 1 | 这条不变量拆分后**由谁守护**？跨进程后还成立吗？ | 不变量被撕成两半（§02.1） | 明确写出「改成预留 + 补偿」或「强一致留在同一侧」 |
| 2 | 中间态**对谁可见**？谁能读到半成品？ | 用户看到「已扣库存待支付」且永不恢复 | 中间态有明确读者清单 + 前端状态 + 超时兜底 |
| 3 | **谁负责补偿与对账**？SQL 与报表在哪？ | 差异静静躺着，直到财务发现（→ `eng/14`） | 有 owner、有对账任务、有差异分类与处置 SOP |
| 4 | 超时后**重试的幂等键**是什么？ | 重试即重复扣减（§02.1 的 6,140 次） | 幂等键落在聚合上，且已在 DDL 里（→ `eng/1`–`eng/6`） |
| 5 | 团队能**独立发布与排障**吗？有 trace 吗？ | 故障定位成本 3~10 倍（→ `eng/29`） | 一个 trace_id 串起全部跨服务调用，值班能看懂 |

### 什么时候不该拆

| 信号 | 说明 | 该做什么 |
| --- | --- | --- |
| 单表 < 50 GB 且写 QPS < 2,000 | 单体 + 读写分离足够撑住（→ `03`、`06`） | 先把模块边界（包）做干净，别动部署 |
| 拆完仍需两个聚合**强一致** | 说明聚合还没切对，拆服务只会把逻辑问题变成分布式问题 | 回到 §02.4 重切聚合 |
| 团队 < 3 个（两个比萨以内） | 边界调整成本 > 收益 | 模块化单体 + ArchUnit 强制边界 |
| 没有对账、没有 trace、没有值班 | 微服务的排障成本会直接压垮团队 | 先补可观测，再谈拆分 |
| 拆分的唯一理由是「代码库太大」 | 那是构建问题，不是边界问题 | 多模块构建、增量编译 |

### 演进四步（每步都留退路）

| 阶段 | 形态 | 出问题的信号（换挡阈值） | 可回滚方式 |
| --- | --- | --- | --- |
| M0 | 单体，包内分层 | `domain` 包开始 import 框架 | 引入 ArchUnit（§02.13） |
| M1 | 模块化单体：上下文 = 模块，只通过端口/事件通信 | 跨模块直接调 `XxxRepository` | 依赖规则转红即回滚 |
| M2 | 抽取「变化频率最高或算力最特殊」的一个上下文为独立服务（通常是查询或通知） | 该模块的发布频率 ≥ 全站 50% | 保留同步旁路，双跑一周 |
| M3 | 按一致性边界拆写侧；跨边界走事件 + 对账 | 对账差异 > 0.1% 且无法解释 | 事件重放 + 灰度切回 |

## 02.15 怎么验证：证明边界对了

| 验证项 | 方法 | 通过标准 |
| --- | --- | --- |
| **不变量单测** | 每条不变量至少一个「必须被拒绝」的用例，直接构造非法状态 | 拒绝用例 100% 抛领域错误；覆盖率不要求 100%，不变量要求 100% |
| **事务边界证明** | 在「写状态后、写 Outbox 前」kill 进程 | 重启后要么全成要么全不成，不变量不破 |
| **依赖守护** | §02.13 的 ArchUnit 进 CI | 任何跨边界 import 立刻构建失败 |
| **上下文隔离** | 消费者驱动契约测试 | 上游改 schema 未升版本 → 下游测试红 |
| **ACL 抗变更** | 三方历史响应录制回放 | 三方改字段时只有 ACL 测试红，domain 全绿 |
| **事件兼容** | 用一年前的事件样本喂新消费者 | 只加字段，旧事件仍能消费 |
| **并发幂等** | 同一单据 200 并发推进 | 成功数 = 1（→ `eng/30`） |
| **失效演练** | 人为让下游 30 s 超时 | 不超卖；差异出现在对账报表里而不是用户投诉里 |

> 一句话：**边界的正确性不能靠评审证明，只能靠「越界时机器会红」来证明。** 上表前五项都能进 CI，最后一项进季度演练。

## 02.16 反模式表

| # | 反模式 | 长什么样 | 根因 | 后果 | 修法 |
| --- | --- | --- | --- | --- | --- |
| 1 | **贫血模型** | 对象只有 getter/setter，不变量散落在 Service 的 `if` 里 | 把聚合当数据容器 | 多入口必然漏校验；同一规则 7 处重复 | 不变量进聚合根方法，`Service` 只做编排 |
| 2 | **跨聚合事务** | 一个 `@Transactional` 里写订单 + 库存 + 优惠券三张库表 | 想「省一次补偿」 | 锁竞争、失败面扩大、热点吞吐坍缩（§02.3） | 拆成聚合，用事件 + 预留 + 对账 |
| 3 | **上下文共享数据库** | 两个服务读写同一批表，靠口头约定「只改自己的列」 | 图省事，或拆分时没拆库 | 边界形同虚设；一次 `UPDATE` 跨边界，事故无法归因 | 一上下文一 schema；集成走 API/事件 |
| 4 | **事件里塞实体** | `OrderEvent { order: {...全量...}, user: {...}, coupon: {...} }` | 想让消费方「方便」 | 跨聚合隐式耦合；合规风险；schema 漂移 | 发 ID + 版本 + 变化字段（§02.12） |
| 5 | **状态机散落各处** | `orders.status`、`pay_status`、`fulfill_status` 三套「状态机」各写各的 | 一个聚合没有唯一生命周期字段 | 无人能回答「这单现在什么状态」；三重矛盾（→ `eng/30` §30.1） | 一个聚合一个 `status`；正交维度拆独立聚合/状态机 |
| 6 | **共享内核变公共垃圾场** | `common` 里既有 `Money` 也有 `OrderHelper`、`DateUtils2` | 没有 owner 与准入规则 | 改一处全站回归；边界名存实亡 | 只准放值对象；超 20 个类就独立成库 + 语义版本 |

## 02.17 十分钟答题卡

被问「你怎么做领域建模 / 怎么拆微服务」时，按这个顺序讲，**不要从「我会用 DDD」开始**：

```
1  真问题    建模产物不是类图，是「哪些不变量必须由同一个事务守护」
2  事故      按表拆服务 → 不变量被撕成两半 → 超卖 + 扣库存没建单 = 34 万
3  定义      聚合 = 事务边界 + 不变量 + 生命周期；不是一张表、不是一个实体
4  判据      必须原子？有恒真断言？能一起死？三条全过才合并；生命周期一票否决
5  反直觉      slug 唯一性属于全局命名空间，不属于 ShortLink（凭证 vs 属性）
6  上下文      四种错切：按层/按团队/按表/按 CRUD；后果都是「不变量没事可归」
7  切法       业务能力找候选 → 变化频率校验（差 >100 倍就拆）→ 一致性裁决
8  落地       domain 不 import 框架；命令现在时、事件过去式；ArchUnit 进 CI
9  状态       聚合放业务终态，引擎放流程进度；一个转移只能有一个决策者（eng/29）
10 演进       默认模块化单体；拆前答五问；「仍需强一致」说明聚合还没切对
```
