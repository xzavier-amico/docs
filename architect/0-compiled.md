# 《系统设计实战》合订本总目

> **一句话**：26 篇是分开写的——分开写是为了每篇能独立成文、独立修订；合订本解决的只有分开写解决不了的那一件事：**为什么这几篇必须按这个顺序读，以及你手头的问题该翻哪一页。**
>
> **这份文件不是第 27 篇**，它不产生新内容，只做三件事：定**卷册结构**、给每族写**族首引言**（说明顺序为什么不能打乱）、把散在各篇的索引合并成**三层总索引**。
>
> **不重复公约**：本文件只有导航与顺序论证，所有结论的正文都在各篇里。看到想深挖的点，直接跳链接。

## 0.1 卷册结构：三卷，不是一本

46 万字摊成一本书是灾害——读者找不到入口，作者不敢修订。按「零件 / 现场 / 方法」切成三卷：

| 卷 | 收录 | 解决什么 | 建议读法 |
| --- | --- | --- | --- |
| **卷一 · 零件** | [01](01-constraint-card-and-capacity.md)–[11](11-data-loop.md)（11 篇） | 12 个可复用抽象 + 5 个空白横切能力。**这 11 篇不出现任何具体系统** | 顺序读，别跳。01 是后面所有推导的输入 |
| **卷二 · 现场** | [12](12-shortlink-system-design.md)–[25](25-chunked-upload.md)（14 篇 · 8 族） | 真实系统怎么装配。每篇一个「唯一真问题」 | **按族读，不按篇号读**（族间顺序见 §0.3） |
| **卷三 · 方法** | 本文件 + [26](26-closing-playbook.md)（收口） | 把现场的判断压成流程与清单 | 最后读，然后回头当手册用 |

## 0.2 合订本的三条纪律

分成 26 篇单独发，最大的风险不是重复，是**编号漂移**。三条纪律必须守住：

1. **篇号冻结**：01–26 一旦发布永不变号。修订只改内容，不动编号。所以全库 426 处交叉引用、附录、索引全部指向稳定锚点。
2. **重复只写一次**：第二次出现只给结论 + 链接。比如「至少一次 + 幂等」的机制细节只在 `eng/11`，本套 05 只写「幂等键该属于哪个聚合」。
3. **族首族尾由合订本负责**：单篇不加「上一篇 / 下一篇」，只写「上承什么、下启什么」——因为单篇发出去时，读者可能从任何入口进来。

```bash
# 纪律的自动化检查（改完必跑）
bash check.sh architect
```

## 0.3 六族 + 一参照物：顺序为什么不能打乱

族内顺序不是按篇号排的，是按**决策依赖**排的。每一族下面写的「打乱会怎样」都是真实会发生的后果。

### 族 0 · 参照物：[12 短链](12-shortlink-system-design.md)

它是全篇的标尺，不是案例之一。后面每一篇都会回来跟它比一次：

| 对比维度 | 短链 | 后文里谁在跟它比 |
| --- | --- | --- |
| 读写比 | 2000:1（极端读重） | 23 秒杀是 1:1000 反向（极端写重） |
| 分片键 | 必须是查询条件（slug） | 13 收件箱按 user_id、15 消息按 conversation_id |
| 失效语义 | 版本化 key（换指针） | 04 给了通用理论，17 用别名切换重演一遍 |
| 持久性 | 标识符永久、目标可变 | 25 秒传的哈希永久、文件可变 |

**读法**：先读 12，后面每读完一族，回来对一遍上表。这一条比任何总结都有效。

### 族 A · IM：[13 扇出](13-fanout-push.md) → [14 长连接](14-websocket-fleet.md) → [15 消息存储](15-message-store.md)

**为什么是这个顺序**：先定「推还是拉」（13），才知道**谁需要长连接**——因为拉模式的人根本不需要被推送，只需被通知；再定「连接怎么维护」（14），才知道**消息该按什么粒度补拉**——因为补拉窗口由 `(cid, seq)` 决定，而 seq 的语义在 15 里定。

| 打乱会怎样 | 后果 |
| --- | --- |
| 先读 15 再读 13 | 你会以为"消息都该进收件箱"，于是把大 V 的 3000 万扇出照搬到群聊，存储直接炸 |
| 先读 14 再读 13 | 你会设计一张"用户 → 连接"的路由表，却没意识到大 V 的粉丝大多离线，长连接只覆盖 20% |
| 跳过 13 直接读 14/15 | 两篇都读得懂，但你不知道为什么要分「推送 / 通知 / 拉取」三种形态 |

**族尾对照插页**（本来计划单写，收在这里）：**微信 vs Telegram** 的六维哲学对照，见 [15 · §15.2](15-message-store.md)。一句话概括这一族的收获：**微信把消息当"只追加日志 + 端上真源"，Telegram 把消息当"云端可编辑状态"**——同一个功能，两种真源位置，其余全部差异都是它的推论。

### 族 B · 检索：[16 匹配](16-matching-multi-recall.md) → [17 搜索](17-search-system.md) → [18 向量](18-vector-system.md)

**为什么是这个顺序**：16 回答「**有哪几种索引结构，各自买什么**」，17 回答「**选中一种之后，工程上会被什么咬**」（段合并），18 回答「**最后那一路召回的交易怎么算**」（recall 换延迟）。顺序是「结构 → 实现 → 交易」。

| 打乱会怎样 | 后果 |
| --- | --- |
| 先读 17 | 你会把 ES 当成"搜索的答案"，而 16 会告诉你：敏感词审核用 ES 是**选型错误**（AC 全命中不漏，倒排按相关性截断会漏） |
| 先读 18 | 你会给一个只要前缀匹配的系统上向量库，延迟翻倍、召回还降 |
| 跳过 16 的劝退节 | 500 万行以内的过滤型需求上了 ES 集群——这是全库最高频的过度设计 |

**族尾对照插页**：ES vs 向量库 vs B+ 树 —— 见 [16 · §16.11 劝退节](16-matching-multi-recall.md)。一句话：**先把"匹配方向"搞清楚（全命中还是按相关性截断），再谈用什么索引**。

### 族 C · 推荐：[19](19-recommendation-essence.md)

单篇成族，但**依赖 B 族**：推荐的召回来源就是 16/18 的那几套索引。所以顺序是 B → C。19 不讲算法，只讲「四级漏斗上的算力与延迟预算怎么分配」——因为架构师签的是这一页，不是模型结构。

### 族 D · 数据工程：[20 迁移](20-data-migration.md) → [21 埋点管道](21-telemetry-pipeline.md)

**为什么是这个顺序**：20 处理**存量**（已经存在的数据怎么搬家且不停机），21 处理**增量**（源源不断的数据怎么落地且查得动）。两者的共同点是「一次写入、多种查询、几乎不可回头」，所以放在同一族互为参照。

| 打乱会怎样 | 后果 |
| --- | --- |
| 只读 21 | 你会以为数据的难题是"选格式"，遇到迁移时才发现真正的难题是"可回滚" |
| 只读 20 | 你会用 OLTP 的思路设计日志存储，日 80 亿条直接把成本做到十倍 |

### 族 E · 运营：[22 奖励](22-campaign-reward-system.md) → [23 秒杀](23-seckill-inventory.md)

**为什么是这个顺序**：22 是**正常并发下**的幂等 + 对账（几万 QPS），23 是**极致热点下**的库存（20 万 QPS 打一个 key）。先学会"账不能错"，再学"不崩"，否则你会用秒杀那套（超卖兜底）去设计发券，结果是钱错了。

| 打乱会怎样 | 后果 |
| --- | --- |
| 先读 23 | 你会觉得"一切靠 Redis 预扣"，然后把它套到现金奖励上——23 明确说了：券可超发，**现金不可** |
| 跳过 22 的幂等 | 重试一次就重复发一张券，这是这一族最贵的一条 |

### 族 F · 平台：[24 多租户](24-multi-tenant-saas.md) → [25 分片上传](25-chunked-upload.md)

**为什么是这个顺序**：24 讲**平台怎么隔离资源**（租户），25 讲**平台里最重的那类资源怎么写**（文件，写放大 1000 倍于读）。前者是横向的边界，后者是纵向的极端。

| 打乱会怎样 | 后果 |
| --- | --- |
| 先读 25 | 你会把上传设计成"单租户系统"，等接第二个客户时才发现存储配额、配额计费、越权下载全要重做 |
| 只读 24 | 你有了隔离，但不知道平台里最烧钱的那个子系统会把隔离打穿（一个大租户传 200TB） |

## 0.6 修订规则（写给未来的自己）

1. **只改内容，不改编号**。
2. 新增系统 → 追加到对应族末尾（如 25 之后加 26），不要插在中间。
3. 任何一族的「族首引言」与「族尾对照」改动，必须同步更新本文件 §0.3。
4. 改完必跑 `bash check.sh architect`——断链、占位符、体量、清单一致性四项会一次告诉你哪里漏了。
