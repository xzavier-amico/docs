# 08. 风控与反作弊：一条五层决策漏斗，而不是一个模型

> **状态**：`已完成（初稿）` ｜ **所属**：第二部分 · 空白横切 ｜ **编号**：08 / 26
> **本篇定位**：`eng/` 与 `llm/` 都没有系统讲过的横切能力。它不讲「模型怎么训」，讲**为什么风控必须是一条从设备指纹到人工的分层漏斗、每层的预算与失效边界在哪、以及名单延迟为什么等于攻击窗口**。上承 [07 变更治理]（规则也是一种配置），下启 [09 开放平台]（配额是定价即防御）与 [11 数据闭环]（特征从哪来）。
> **唯一真问题**：风控不是一个模型，是一条 **设备指纹 → 规则 → 名单 → 图关系 → 模型 → 人工** 的分层漏斗；而且它必须**可解释、可申诉**，否则误杀会变成公关事故。
> **读法**：§08.4 的五层漏斗图与 §08.9 的名单同步链路是全文最该抄走的两处；§08.3 的三笔账决定你能给模型多少流量；§08.15 的换挡信号表可直接用于架构评审。

## 08.1 事故引子：两次「没有人报错」的失血

**事故一：5 万份新客券，11 分钟被 800 台设备刷完（2025-05-20）**

「夏季拉新」券池 5 万张、面值 ¥20，规则只有一条：**同一手机号未领过**。上线 11 分 40 秒券池清零，客服收到 430 起「领不到券」投诉——这两件事同时发生，本身就是信号：**真实的领券速度不可能这么快，而真实用户不可能这么少**。

| 时间 | 事件 | 数据 |
| --- | --- | --- |
| 05-20 10:00 | 活动上线，券池 5 万张，唯一限制「手机号未领过」 | — |
| 10:00:00 ~ 10:11:40 | 券池清零 | 5 万张 / 700 秒 |
| 10:12 | 客服涌入「券没了」 | 430 起 |
| 10:40 | 风控看板发现异常：**领券设备数 ≪ 领券账号数** | 800 台 : 5 万个账号 |
| 11:20 | 定位 Top1 设备指纹 | 单台设备下 **4,000 单** = 8% 券量 |
| 11:35 | 追踪号段：92% 手机号来自 4 个号段 | 接码平台 |
| 14:00 | 冻结未核销券 | 追回 9,000 张 |
| 05-21 ~ 05-28 | 渠道核销追讨、公关、法务 | 直接损失 ¥96 万 |

| 项 | 金额 / 数量 | 说明 |
| --- | --- | --- |
| 券池预算 | ¥100 万（5 万 × ¥20） | 立项时的上限 |
| 羊毛党领走 | 4.87 万张 / ¥97.4 万 | 占券量 97.4% |
| 14:00 冻结追回 | 9,000 张 / ¥18 万 | 未核销，券仍在池内 |
| 实际流失（已核销/已转卖） | 3.97 万张 / ¥79.4 万 | 二级市场 ¥8~12 折出清 |
| 真实新客获得 | 1,300 人 | 有效获客率 **2.6%** |
| 公关 + 法务 + 渠道返利 | ¥16.6 万 | — |
| **合计损失** | **¥96 万** | **损失率 = 96% 的预算，ROI ≈ -0.96** |

根因不是「有人作弊」，是三个缺失同时存在：**风控主体是账号而不是设备**（所以 4,000 个假账号天然合法）、**没有任何名单在毫秒内拦住已确认的坏设备**（第 11:20 才定位到，第 14:00 才冻结）、**处置不可回滚**（券被设计成「领取即生效」，事后只能求渠道退）。

**事故二：批量账号投毒短链，7 小时后才下架（2025-08-14）**

内容平台开放「创作者短链」外链跳转。一个设备农场在 40 分钟内注册 2,300 个账号，向 4.2 万个正常帖子下评论投放 1.7 万条赌博/诈骗短链。用户 06:30 开始举报，监管 09:40 巡查发现并通报。

| 时间 | 事件 | 数据 |
| --- | --- | --- |
| 08-14 02:10 | 批量注册（接码平台 + 云手机） | 2,300 账号 / 40 分钟 |
| 02:50 | 首条违规短链上线 | 赌博落地页 |
| 03:00 ~ 09:00 | 持续投放，分散在正常帖子评论区 | 1.7 万条 / 4.2 万个帖子 |
| 06:30 | 用户举报进入人工队列（无优先级） | 210 起，平均排队 4.5 h |
| 09:40 | 监管巡查通报，距首条发布 **6h50m** | 罚款 ¥45 万 |
| 09:55 | 封 2,300 账号，封 1.7 万短链，但名单传播**靠缓存 TTL 过期** | 3 轮全量扫描后仍漏 340 条 |
| 08-15 | 限期整改 90 天 | 无法申诉，也不需要申诉 |

这起事故里最长的一段时间不是「发现」——03:00 的规则其实已经命中了一批异常注册——而是**「命中」到「全边缘生效」之间的 7 小时**。处置延迟就是攻击窗口，这条账会在 §08.9 变成一条硬指标。

## 08.2 到底是什么，以及唯一真问题（七问 ①②）

**精确定义**：风控是**在业务链路的关键点上，用尽可能便宜的证据，把「主体」的行为分成放行 / 降权 / 阻断三类的横切能力**。

三个反例，先划清边界：「不是**一个反欺诈模型**」（单一模型无法解释、无法申诉、无法热修，挂了系统就瞎）；「不是 **WAF/限流**」（限流按次数、WAF 按请求内容，风控按**主体及其历史**，→ `llm/32` §32.12）；「不是**安全团队的事**」（券怎么发、额度按什么主体算，是定价与产品设计问题，→ `llm/32` §32.1）。

### 唯一真问题

> **风控的输出是一个「处置」，而处置同时是三种东西：一个技术判定、一份对用户的承诺、一笔已经发生的钱。**
> 技术判定要求快和准；对用户的承诺要求**可解释**（为什么拦我）；已发生的钱要求**可回滚**（误杀要能还回去）。
> 这三者方向相反：越准的模型越不可解释，越快的处置越不可回滚。

由这一条推出来的全部设计：

| 从矛盾推出的约束 | 推出的形态 |
| --- | --- |
| 越准越不可解释 → 不能让黑盒单独裁决 | **分层漏斗**：便宜且可解释的层先出结论，模型只做最后一档加权 |
| 误杀一定存在 → 处置必须分级可逆 | 冻结 ≠ 作废；处置档位 L0~L5 每档可回退（§08.10） |
| 名单生效慢 = 攻击窗口 | 名单**旁路同步到数据面**，秒级可见，不等 TTL（§08.9） |
| 对手会变异 → 规则会过期 | 规则是**数据不是代码**，可热更、可灰度、可回放（§08.6） |
| 一个模型故障不能拖垮全站 | **每层可独立关闭**，关闭后降级而非拒付（§08.5） |

**一句话对照**：短链篇的矛盾是「标识符永久、目标可变」（→ [12 短链 · §12.2](12-shortlink-system-design.md)），风控篇的矛盾是「判定要快准、处置要可解释可回滚」。二者同构：**不可逆的东西一旦被加进系统，所有设计都要围着它转。**

## 08.3 量级与预算：先算三笔账（七问 ③）

不许拍脑袋。风控评审上最常被跳过、也最该先算的是**三笔账**。

### 第一笔：流量账——每层的分母不同

```
日判定次数        12 亿（DAU 3,000 万 × 人均 40 次关键动作）
均值 QPS          12e8 / 86400              ≈ 1.39 万
峰值系数          ×3（活动开场、晚 8 点）    →  4.2 万 QPS
L1+L2+L3 全量     12 亿次/天（纯内存，必须便宜）
L4 图判           仅「规则分 ≥ 30」的主体 8% → 9,600 万次/天
L5 模型           仅「灰名单 3% + 抽样 1%」  → 4,800 万次/天
L6 人工           日均 1,800 单（高危已冻结，等复核）
```

> **这个漏斗的真正作用是分配算力预算，不是「层层加码」。** 模型只能看到 4% 的流量，因此它可以很贵、很慢、很不解释——因为它不承担主链路的延迟。

### 第二笔：钱账——最贵的一层是人力

| 层 | 单位成本 | 日成本 | 月成本 |
| --- | --- | --- | --- |
| L1 设备指纹（进程内查表） | ¥0.0000002 | ≈ 0 | ¥0 |
| L2 规则引擎（进程内求值） | ¥0.0000006 | ≈ ¥0 | ¥0（CPU 摊在业务节点上） |
| L3 名单（1% 回源 Redis） | ¥0.000004 | ≈ ¥480 | ¥9,000（6 节点 48 GB） |
| L4 图关系（预计算邻域 + Flink 增量） | ¥0.00008 | ≈ ¥770 | ¥3,000 + 计算 ¥6,000 |
| L5 模型（GBDT 200 树，4,800 万次） | ¥0.00003 | ¥1,440 | **¥4.3 万** |
| L6 人工复核（1,800 单 × ¥6） | ¥6 / 单 | ¥1.08 万 | **¥32 万** |
| **合计** | — | — | **≈ ¥37.5 万/月** |

**这张表最反直觉的一行是 L6。** 人工复核成本是模型的 7.5 倍，所以「把复核队列的**精度**做高」比「把模型精度再提 2%」省钱得多：队列命中率提 10% 省 ¥3.2 万/月，而模型提 2% 精度要多花 ¥1 万/月却只让队列缩短 3%。

> **预算上限原则**：风控月成本不应超过它**拦住的损失的 1/5**。事故一单次 ¥96 万、两次/年 → 年损失约 ¥190 万，风控年成本 ¥450 万看似贵，但它同时挡住了内容投毒（罚款 ¥45 万 + 90 天整改）。**评审时先要「去年同期因作弊损失多少」这个数，没有它就没有 ROI 讨论的基础。**

### 第三笔：延迟账——同步 0.65 ms，其余异步

| 环节 | 位置 | P99 |
| --- | --- | --- |
| L1 指纹 / 0.08 ms + L2 规则 / 0.35 ms + L3 名单 / 0.02 ms + L4 图 / 0.20 ms | 同步，全在业务节点本地 | **合计 0.65 ms，预算硬顶 5 ms** |
| L5 模型打分 | **异步**，结论只作用于下一次请求 | 不上主链路 |
| L6 人工 | 24 h 内 | 不阻塞 |

**这是本篇最重要的一条架构决策**：模型永远不上同步主链路——它属于「快判 + 慢判」双层里的慢判（→ `llm/32` §32.12）。理由是事故型的：把风控做成同步 RPC，风控一抖动，全站 P99 立刻从 200 ms 涨到 8 s。

### 五层对照表（评审时逐列追问）

| 层 | 判什么 | 边际召回 | 精度 | P99 | 单位成本 | 可解释性 | 单层故障时的降级 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| **L1 指纹** | 设备是否已确认坏 / 是否改机 | 62% | 41% | 0.08 ms | ~0 | **极高**：可直接出示指纹 ID 与首次出现时间 | 指纹算不出来 → 标 `fp=unknown`，继续走 L2 |
| **L2 规则** | 属性 + 滑动窗口计数 | +24% | 78% | 0.35 ms | ~0 | **高**：`rule_id` + 命中的证据字段 | 单条规则报错 → 只停该条；全引擎失败 → 走名单 |
| **L3 名单** | 白/黑/灰 | +7% | 96% | 0.02 ms | ¥0.000004 | **极高**：名单条目带来源工单号 | 用本地快照（最多旧 10 s），**绝不回源阻塞** |
| **L4 图** | 2 跳内是否连通已知团伙 | +4% | 88% | 3.5 ms | ¥0.00008 | **中**：「与 37 个已封账号同设备同地址」 | 跳过，打标 `graph=skipped`，不阻断 |
| **L5 模型** | 综合风险分 | +2.6% | 92% | 1.8 ms | ¥0.00003 | **低**：必须强制输出 SHAP top-3 才允许用 | 回上一版模型；再不行只用规则结论 |
| **L6 人工** | 争议与高危裁决 | 尾差 | 99.2% | 24 h | ¥6/单 | **最高**：工单 + 双人签 + 全量留痕 | 队列积压 → 按冻结金额排序，先处理高额 |

**边际召回不简单相加**：层间有重叠，实测累计召回 ≈ 96.3%，累计误杀率 0.42%。这两个数字必须在同一个看板上，**只报召回不报误杀的风控看板等于没有看板**。

### 为什么这个顺序不能换

模型放第一层，4,800 万次/天变 12 亿次/天，月成本从 ¥4.3 万涨到 ¥324 万；图放第二层，3.5 ms × 全量直接把主链路预算打爆；名单放第一层，语义上最快，但它只有 7% 的边际召回，等于让 93% 的坏流量走完整个漏斗；去掉人工全靠模型，则申诉失去出口、模型失去标签回流，半年后精度必然衰减。**召回只多 1.8%，成本贵 75 倍——这就是顺序的全部含义。**

## 08.5 分层原则：便宜在前，但每层必须能独立关闭

### 原则一：先过滤 80%，再上重的

算一笔对照账：假设只有「规则 + 模型」两层。

```
方案 A：模型全量        12 亿次 × ¥0.00003 = ¥324 万/月
方案 B：规则先过滤 86%   1.68 亿次 × ¥0.00003 = ¥45 万/月
方案 C：漏斗 + 抽样 4%   4,800 万次 × ¥0.00003 = ¥4.3 万/月
```

**A → C 是 75 倍的成本差，而召回率只从 98.1% 掉到 96.3%。** 这就是分层漏斗的全部经济学。

### 原则二：每层可独立关闭——这是可用性要求，不是优雅

真正的反模式是这样的：**模型服务抖动 → 风控 SDK 抛异常 → 业务侧把异常当「拒绝」→ 全站拒付**。一次模型故障演变成一次全站事故。

所以每层必须有三种状态，且状态本身走配置中心（→ [07 变更治理](07-change-governance.md)）：

| 状态 | 含义 | 触发方式 |
| --- | --- | --- |
| `on` | 正常求值 | 默认 |
| `shadow` | 只算分、只打日志、不处置 | 新规则上线、灰度期 |
| `off` | 跳过该层，继续下一层 | 故障自动降级（错误率 > 5% 持续 30 s）或人工开关 |

三条硬约束：

1. **关闭某层的默认动作是「放行并打标」，不是「拒绝」。** 唯一例外是黑名单层（fail-closed，§08.9）——「已知的坏内容继续流通」比「多拦一次」更不可接受，但这必须按业务显式声明。
2. **降级必须留痕**：每次 `off` 打 `risk_degraded{layer,reason}` 指标。风控静默降级 = 你在裸奔而没人知道。
3. **绝不允许层间同步 RPC**。L1~L4 全部在业务节点本地完成，只有 L5 是远程且异步。

## 08.6 规则引擎：让规则成为数据，不是代码

硬编码规则的下场是可预期的：改一个阈值要发版、发版要回归、回归要一周，而羊毛党 6 小时就换手法。

### 一条规则的完整表示（JSON，含灰度、证据、回滚）

```json
{
  "id": "R-PROMO-114",
  "name": "同设备多账号领新客券",
  "version": 27,
  "owner": "trust-and-safety",
  "priority": 20,
  "status": "gray",
  "gray": { "ratio": 0.1, "bucket_by": "device_id" },
  "expr": "device.accounts_7d >= 5 && account.age_hours < 48 && promo.claims_24h >= 2",
  "score": 55,
  "action": { "level": "L4_FREEZE", "ttl_hours": 24, "reversible": true },
  "evidence": ["device.fingerprint", "account.created_at", "promo.claim_ids"],
  "explain": {
    "zh": "该设备 7 天内关联 5 个以上新账号，且今日已领取 2 次以上新客券",
    "appeal_hint": "家庭/公司共用设备属正常，可在申诉中提交手机号与用券记录"
  },
  "false_positive_note": "网吧、学校机房、家庭共用 iPad；仅当 ip.asn_type != residential 时允许自动冻结",
  "rollback": { "on": "appeal_passed", "ops": ["return_coupons", "unfreeze"] }
}
```

一个字段都不能省：`id/version` 让结论可追溯；`gray` 让上线可灰度；`evidence` 让申诉有据；`explain` 让处置可解释；`rollback` 让处置可逆；`false_positive_note` 是**逼作者写清误伤面**，写不出来的规则不允许上线。

### 表达式 DSL 的四条边界

| 边界 | 规定 | 原因 |
| --- | --- | --- |
| 只能用白名单函数 | 比较、逻辑、`count/sum/distinct/ratio`、时间窗聚合；**禁止**任意代码、循环、外部 IO | 规则是运营写的，等于把脚本注入权交给运营 |
| 必须能静态分析出依赖字段 | 上报依赖的 fact key，缺失即「不可求值」而非「false」 | 缺失当 false = 静默失效（最危险的失败模式） |
| 单条求值上限 200 μs，全链 3 ms | 超时即跳过该条并告警 | 一条正则写错能吃掉整个引擎的预算 |
| 规则之间不许互相调用 | 只有优先级的线性链，无 DAG | 有调用就有环，有环就有「谁先算」的死锁（→ `eng/29`） |

### 热更新与回放验证

| 机制 | 做法 | 验收标准 |
| --- | --- | --- |
| **热更新** | 规则集是**不可变快照**，发布 = 换引用（双缓冲），求值中的请求继续用老快照 | 无需重启；发布到生效 P99 < 5 s |
| **灰度** | 按 `bucket_by` 的稳定哈希分桶（同一设备永远进同一桶） | 分桶里**绝不许含时间戳或随机数**，否则同一用户忽封忽放 |
| **回放** | 近 7 天 FactSet 快照重放新老规则集，diff 命中集合 | 命中量变化 > 1.5 倍必须人工解释；抽检 50 条误伤 < 2% |
| **短路 + 清理** | `priority` 升序求值，`isTerminal()` 即停；`last_hit_at` 90 天零命中进「待下线」 | 封禁类排最前；规则总数硬顶 500，超了先删后加 |

### 骨架：Java 规则链求值（短路 + 预算 + 证据）

```java
// RiskEvaluator.java —— 不可变快照 + 优先级短路 + 时间预算 + 证据留痕
public final class RiskEvaluator {
    private final RuleRepository repo;              // 发布 = 换快照引用，不重启
    private final PredicateFactory predicates;      // DSL 编译后谓词，LRU 缓存

    public Verdict evaluate(FactSet facts, EvalBudget budget) {
        RiskRuleSet set = repo.current();           // 整个请求用同一版本，结论可复现
        List<Evidence> evidence = new ArrayList<>();
        int score = 0;
        for (RiskRule r : set.byPriority()) {       // 升序，同优先级按 id 稳定排序
            if (!r.enabled()) continue;
            if (!r.inGrayBucket(facts.subject(), set.grayRatio())) continue;  // 稳定哈希分桶
            if (budget.exhausted() && !r.mustRun()) continue;   // ★ 预算耗尽只跑必判规则
            long t0 = System.nanoTime();
            boolean hit = predicates.get(r.expr()).test(facts); // 表达式内短路
            budget.consume(System.nanoTime() - t0);
            if (hit) {
                score += r.score();
                evidence.add(new Evidence(r.id(), r.evidenceFields(), r.explainZh()));
                if (r.action().isTerminal()) break;  // ★ 封禁类直接出结论，不再累加
            }
        }
        return Verdict.of(score, evidence, ActionPolicy.grade(score, facts));
    }
}
```

注意 `Verdict.of(score, evidence, ...)`：**证据和分数是同等级别的返回值**。只返回 `score` 的实现，三个月后必然没人敢调阈值——因为没人知道某个分数是怎么来的。

## 08.7 设备指纹与画像：最强的单信号，以及它的合规红线

### 指纹的三段组成

| 段 | 内容 | 稳定性 | 伪造难度 | 用途 |
| --- | --- | --- | --- | --- |
| **不可变属性** | 硬件序列哈希、安全区 ID、Boot ID、GPU/CPU 型号组合 | 高（换机才变） | 高 | 主键，跨账号串接 |
| **可变属性** | OAID/IDFA、系统版本、字体列表、时区、语言、屏幕参数、WebGL Canvas 哈希 | 中（刷机/改机即变） | 中 | 辅助聚类 |
| **服务端口径** | JA3/JA4 TLS 指纹、HTTP header 顺序与大小写、TCP 选项、时钟偏移 | 中 | 中高（要改客户端栈） | **客户端不可绕过**，比 SDK 上报可信 |
| **行为** | 点击轨迹、输入节奏、传感器噪声、请求间隔方差 | 低 | 很高 | 人机判定，不能做身份 |

> **服务端口径 > 客户端口径。** SDK 里的指纹逻辑会被逆向（改机工具 MAGisk/Xposed 就是干这个的），而 TLS 握手特征只能通过换网络栈来伪造——成本高一个数量级（→ `llm/32` §32.6.1）。

### 伪造与对抗

| 手法 | 典型特征 | 反制 |
| --- | --- | --- |
| 改机工具（Xposed/Frida Hook） | 指纹字段互相矛盾（GPU 是旗舰、分辨率是入门机） | **交叉校验**：字段一致性打分，矛盾即高危 |
| 模拟器/云手机 | 传感器序列恒定、电池恒定 100%、CPU 指令集特征 | 环境检测 + 该段指纹降权 |
| 群控（一控多机） | N 台设备请求时间戳极度接近（毫秒级对齐） | 时间同步检测：同 IP 段内 ≥10 台设备请求偏移 < 5 ms |
| 全新设备（一次一机） | 指纹从未见过，设备年龄 = 0 | **新设备是强风险信号**，但绝不能单独封禁（真实新客全是新设备） |

### 隐私边界（合规风险，不是技术选项）

| 红线 | 做法 |
| --- | --- |
| 不存原始硬件标识 | 只存 `HMAC(平台盐, 原始值)` 的不可逆摘要，盐季度轮换 |
| 不跨业务共享指纹本体 | 只共享「风险标签」 |
| 有保留期限、可关闭 | 指纹与行为序列保留 180 天；隐私政策声明 + 提供「不同意设备识别」的降级路径（代价是更多验证码） |

设备指纹在多数司法辖区被视为**个人信息**（可间接识别）。这不是法律意见，但工程上必须做到「**不可逆 + 最小化 + 有期限 + 可解释**」——这四条恰好就是风控的「可解释可申诉」，所以不算额外成本。

### 什么时候用图库，什么时候用离线批处理

| 场景 | 形态 | 判据（→ `eng/38` §38.5） |
| --- | --- | --- |
| **在线判定**「这主体与已知团伙 2 跳内连通吗」 | **预计算邻域表（宽表/闭包表）+ 本地读** | 跳数 ≤ 2、查询固定 → 不需要图库，一张增量维护的邻域表 0.2 ms 搞定 |
| **离线团伙发现**（连通分量、社区发现、资金环路） | Spark GraphX / Flink 批，小时级 | 需要全图算法 → 图库也不擅长，直接上批处理 |
| **运营探索式查询**（「这条资金链还连到谁」） | 图库（Neo4j/Nebula） | 多跳 + 路径 + 关系类型多 → 图的真刚需 |
| **1 跳高频点查**（「这设备还绑了哪些账号」） | Redis 邻接集 | 1 跳 QPS 极高，图库反而更慢 |

**三条必踩的坑**：

1. **超级节点**：一个公共 IP、一个菜鸟驿站地址能连通百万账号，全图立刻糊成一片。**建图前必须做度剪枝**（度 > 10 万的节点降权或剔除），这是反欺诈图第一号性能杀手。
2. **图库当主库**：图库是**索引不是真相**（→ `eng/38` §38.7）。关系真相在订单/支付库，图挂了要能从零重建。
3. **图的误杀率天然更高**（共用地址、家庭共享卡），所以**图的结论只允许触发「冻结 + 人工复核」，不允许自动永久封禁**。

## 08.9 名单体系：名单延迟 = 攻击窗口（本篇最关键的一节）

事故二的 7 小时里，最大的一段不是发现，是**「已判定为坏」到「全边缘生效」的传播**。所以这一段先给结论：

> **名单的端到端生效时间（DB 提交 → 数据面可见）必须 ≤ 3 秒（P99）。超过 1 分钟，就不叫风控，叫事后复盘。**

### 三类名单的语义（语义错了，后面全错）

| 类型 | 语义 | 处置 | 默认行为 | 生命周期 | 谁可以加 |
| --- | --- | --- | --- | --- | --- |
| **白名单** | 已确认「即使命中规则也放行」 | 跳过 L2 及以下的自动处置 | **fail-open**（查不到就正常走流程） | **必须有到期时间**（默认 90 天，最长 180 天） | 双人审批 + 工单号 |
| **黑名单** | 已确认坏，不允许流通 | 立即阻断（410 / 拒付 / 拒绝登录） | **fail-closed**（查不到就拦住） | 长期，但每 180 天复审一次 | 规则自动 + 人工确认 |
| **灰名单** | 可疑，只降权不阻断 | 降配额、加验证码、进模型必判集 | fail-open | TTL 7~30 天，自动过期 | 规则/模型自动 |

**白名单必须过期**，这是最容易被忽视的一条：永久白名单等于给内鬼留了一扇永久的门（事故形态：某客户被加了永久白名单，两年后成了批量套利的通道）。**黑名单必须能复审**，否则一次误杀会永久化。

### 冷热分层

| 层 | 载体 | 容量 | 单次查询 | 假阳性 | 数据新鲜度 |
| --- | --- | --- | --- | --- | --- |
| **L0-a 进程内布隆** | 每 Pod 一份 bitmap（2,000 万条 × 10 bit ≈ 25 MB） | 2,000 万 | 0.008 ms | 0.8% | ≤ 10 s（全量重建）/ ≤ 200 ms（增量） |
| **L0-b 进程内增量集** | Go `sync.Map` / Java `ConcurrentHashMap` | 最近 1 小时新增（≤ 5 万） | 0.005 ms | 0 | ≤ 200 ms（Kafka 消费） |
| **L1 Redis** | Set + 元素 TTL（灰名单靠 TTL 自动过期） | 1.2 亿 | 0.6 ms | 0 | 实时 |
| **L2 DB** | 名单表 + 证据 + 审计（唯一真相） | 全量 | 12 ms | 0 | — |

**布隆的铁律与短链篇相同**：只能有假阳性，不能有假阴性。所以「新增黑名单」的写路径必须是 `写 DB 成功 → 写 outbox → 消费后写 Redis → 推送到进程内`，任何一步漏写都等于名单不存在（→ [12 短链 · §12.6](12-shortlink-system-design.md) 的同一条铁律）。

### 同步到数据面的路径（秒级方案 + 失败兜底）

```
 控制面（Java）                          消息层                    数据面（Go，320 Pod）
┌────────────────────┐                                          ┌──────────────────────────┐
│ 名单变更来源        │                                          │ 进程内布隆 bl:global      │
│  ├ 规则自动         │                                          │ 8 MB~25 MB / Pod          │
│  ├ 人工封禁         │                                          │ + 增量集 sync.Map         │
│  ├ 投诉核实         │                                          └───────┬──────────────────┘
│  └ 监管工单         │                                                  │ 命中 → 410 / 拒付
│        ↓            │                                                  │
│ 写 DB（唯一真相）   │  ① 同事务写 outbox                              │
│ 版本号 ver → ver+1  ├────→ Kafka(topic=blk, 64 分区, key=entity_id) ─②→ 增量订阅 <200 ms
│        ↓            │                                                  │ 追加增量集（含 TTL）
│ 发布版本指针        ├────→ Redis pub/sub（快路径，不保证不丢）──────③→ 应急推送 <50 ms
└────────────────────┘                                                  │
                                                                        │
 兜底四层（必须全有）：                                                  │
 ④ 每 Pod 每 10 s 长轮询 /v1/blocklist/version；版本不等 → 全量重建布隆 ─┘
 ⑤ 全链路口径：DB 提交 → 布隆可见 ≤ 3 s（P99），超时即告警（这是 SLO，不是期望）
 ⑥ Kafka 与 Redis 同时不可用 → 进入「保守模式」：按 region 拉 DB 只读副本，
    单次判定多花 180 ms，但绝不静默放行黑名单
 ⑦ 布隆快照自带 `ver` 与 `build_at`；数据面发现 build_at 超过 60 s → 上报
    "stale_snapshot" 指标并触发保守模式（防「同步链路断了但没人知道」）
```

**七个环节，只有第①步是强一致的，其余全部是最终一致 + 版本号兜底。** 这不是妥协，是设计：名单是**单调递增集合**（大部分情况），所以「晚一点看到」比「阻塞等待」代价小得多；而唯一不可接受的是**永远看不到**，这由④⑦两层兜底覆盖。

### 三档延迟承诺（写进 SLO 表）

| 通道 | 延迟（P99） | 丢消息时 | 适用 |
| --- | --- | --- | --- |
| Redis pub/sub 应急推送 | 50 ms | 丢 → Kafka 通道补 | 监管工单、涉未成年、涉赌 |
| Kafka 增量订阅 | 200 ms | 不丢（至少一次 + 幂等） | 常规封禁 |
| 全量快照重建 / **端到端 SLO** | 10 s / **3 s** | — | 大批量、版本漂移修复；超时即告警 |

### 骨架：Go 数据面黑名单查询（本地产布隆 → 增量 → Redis 兜底）

```go
// blk/guard.go —— 数据面名单判定：本地优先、永不回源阻塞、按名单类型决定失败方向
type Guard struct {
    cur   atomic.Pointer[snapshot] // 全量布隆快照，版本化，整体替换（无锁读）
    delta sync.Map                 // Kafka 增量（<200ms 可见），value = 过期时间
    rdb   *redis.Client            // 仅布隆假阳性后确认，2 ms 超时
}

func (g *Guard) Blocked(ctx context.Context, id string) Decision {
    s := g.cur.Load()
    if s == nil || time.Since(s.buildAt) > 60*time.Second {
        return g.conservative(ctx, id) // ⑥⑦：快照缺失/过期 → 保守模式（查 DB 副本）
    }
    if exp, ok := g.delta.Load(id); ok && time.Now().Before(exp.(time.Time)) {
        return Decision{Block: true, Source: "delta", Ver: s.ver} // ① 最快：增量真命中
    }
    if !s.bloom.TestString(id) {
        return Decision{Block: false, Source: "bloom", Ver: s.ver} // ② 布隆说无 → 一定无
    }
    c, cancel := context.WithTimeout(ctx, 2*time.Millisecond)
    defer cancel()
    ok, err := g.rdb.SIsMember(c, "bl:set", id).Result()
    if err != nil {
        // 黑名单 fail-closed：确认不了就拦住（宁可误拦一次，不可放行已封禁内容）
        return Decision{Block: true, Source: "redis_timeout", Ver: s.ver}
    }
    if ok {
        return Decision{Block: true, Source: "redis", Ver: s.ver}
    }
    return Decision{Block: false, Source: "bloom_fp", Ver: s.ver} // 假阳性，记一次指标
}
```

失败方向要按名单类型分开：**黑名单 fail-closed，白名单/灰名单 fail-open**。把两者写成同一段代码，是这一节最常见的实现错误。

**还要一条反向链路**：数据面每分钟回传命中计数，控制面据此找出「创建至今零命中」的僵尸条目（清理）与「命中量突然暴涨」的新攻击（告警）。没有反向链路的名单库，半年后一定没人敢删任何一条。

## 08.10 误杀与申诉闭环：处置可逆才叫风控

误杀不是「尽量少」，是**必然存在**，所以必须有出口。没有出口的误杀 = 把技术问题升级成公关问题。

### 指标定义（先定义，再看板）

| 指标 | 定义 | 目标 |
| --- | --- | --- |
| **表观误杀率** | 申诉通过数 / 全部处置数 | < 0.3%（但**严重低估**：大部分人被拦了不会申诉） |
| **真实误杀率** | 每周抽 200 条处置样本人工判定 | < 2%（这才是评规则的依据） |
| 申诉率 | 申诉数 / 处置数 | 0.5% ~ 2%（过低说明入口藏太深，过高说明误杀严重） |
| 处置→申诉响应时长 | — | P50 < 4 h，P99 < 24 h |
| 复核 SLA | 高额冻结 4 h 内、其余 24 h 内 | ≥ 98% 达标 |
| 二次投诉率 | 申诉驳回后再次投诉 / 驳回数 | < 5% |

### 申诉闭环

```
 用户被处置（响应体必带：X-Risk-Action / risk_hint / case_id / 申诉链接）
        │
        ▼
┌────────────────────────────────────┐
│ 申诉入口（页面自助 + 客服工单）      │  ← 入口必须在「被拦的那个页面」上，

└───────────────┬────────────────────┘
                ▼
┌────────────────────────────────────┐
│ 分级分流                            │
│ 低额/低危 → 自动核对 + 秒级放行     │  ← 60% 的申诉在这里结束（如验证码通过即解冻）
│ 冻结金额 ≥ ¥50 或涉账号 → 人工队列  │
└───────────────┬────────────────────┘
                ▼
┌────────────────────────────────────┐
│ 人工复核队列（按冻结金额降序）       │
│ 一线判 + 二线抽查 10%（双人签）      │

       ▼                      ▼
┌───────────────────────┐  ┌──────────────────────────────┐
│ ① 解冻：恢复账号/额度  │  │ 记录驳回理由（选模板 + 自由文本）│
│ ② 自动加白（TTL 90 天）│  │ 用户二次申诉 → 升级二线         │
│ ③ 回滚已执行处置：     │  └──────────────────────────────┘
│    · 返还被扣券/额度   │
│      幂等键 = case_id  │  ← 关键：冻结而非作废，才可能返还
│    · 补发权益/致歉券   │
│ ④ 反向打标：           │
│    命中规则记为误报     │
│    → 进规则回放集       │
│    → 进模型训练集       │
└───────────┬───────────┘
            ▼
  真实误杀率回流（周会）→ 调阈值 / 下线规则 / 修 false_positive_note
```

### 三条设计约束

1. **冻结 ≠ 作废。** 券一旦作废就还不了；冻结 24 h 后才能还。这条决定了事故一能不能挽回——事故一的设计正是「领取即生效」，所以 14:00 只能求渠道退。
2. **回滚必须幂等**：`POST /cases/{case_id}/rollback`，幂等键 = `case_id`，重复调用返回同一结果。否则一次重试变成补发两次券（→ `eng/1`）。
3. **申诉通道本身也要防刷**：黄牛会拿申诉当提额通道。申诉次数限流 + 通过率监控（某主体申诉通过率异常高 → 其「误杀」判定本身可疑）。

## 08.11 对抗升级：四个阶段，每阶段该加的不是「更强的模型」

| 阶段 | 对手手法 | 你看到的信号 | 该加什么 | **别**加什么 |
| --- | --- | --- | --- | --- |
| **① 脚本薅** | 单机脚本、固定 UA、同 IP 高频 | 请求间隔方差极小、指纹重复、IP 集中 | IP/设备限流、基础规则、指纹去重 | 别上模型：样本量太少，训出来全是噪声 |
| **② 设备农场 / 云手机** | 改机、群控、接码平台养号 | 指纹多样但**行为同构**、号段集中、注册-使用间隔 < 60 s | 图关系、支付/收货关联、强制真人验证（验证码/人脸） | 别只加规则：对手会调参，规则命中率会在一周内掉一半 |
| **③ 分布式真人众包** | 真人众包、住宅 IP、正常设备，按单结算 | 单看全都正常；只有**资金与收益汇聚**（同收款账户/同物流地址） | 结算侧逆向关联、激励设计（把收益门槛设在「真人真用」上）、收货地址聚类 | 别提高拦截率：这一阶段误杀率会爆炸，因为「正常用户」和「众包」在行为上真的分不开 |
| **④ 内鬼 + 供应链** | 有权限的内部账号、上游数据泄露 | 规则命中率突然下降、封禁名单被「精准避开」、某租户从未被拦 | 规则访问审计、canary 规则（假规则，只用于识别谁在偷看）、按租户差异化策略 | 别相信「内部流量」，也别在文档里写完整规则 |

> **一句必须记的话**：每一阶段的应对不是「更强的模型」，而是**换一种关联维度**——①靠单点特征、②靠设备与账号的关联、③靠**钱**的关联、④靠权限的关联。模型的精度上限由**你手上最强的那个关联维度**决定，不由算法决定。

**阶段③是分水岭**：前两阶段的对手有「技术指纹」可以拦；众包阶段每个执行者都是真人，唯一破绽是**结算必须汇聚**。因为换设备、换 IP、换手机号都便宜，换收款账户贵（→ `llm/32` §32.6）。

## 08.12 实时特征：时效、一致性、缺失（→ [11 数据闭环](11-data-loop.md)）

规则和模型吃的是特征，特征错了前面全错。四件事必须在建模阶段定死：

| 维度 | 要求 | 落法 |
| --- | --- | --- |
| **时效分级** | 活动 1 min（领券数）、账号 24 h、设备 7 d、地址/卡 30 d | 按窗口分三档：Flink 实时聚合、小时批、天批 |
| **在线离线一致** | 同一份定义生成两套计算，不能两拨人各写一遍 | **特征注册表**：一份 DSL → 生成 Flink 作业与离线 SQL，上线前比对两侧 7 天分布 |
| **点时间正确** | 训练集只能用「当时能拿到的特征」 | **point-in-time join**；快照带 `as_of`（否则离线 AUC 0.9、线上 0.6） |
| **缺失兜底** | 特征缺失 ≠ 0 | ①缺失单独作为 `is_missing`；②规则侧「不可求值」不判命中；③模型侧用同主体历史值 → 中位数，且**降权** |

**最常见的自欺**：把「没数据」填成 0，于是「设备从未见过」和「见过 0 次坏行为」变成同一个值，模型学到的第一个特征就是错的。完整治理（特征版本、回溯、反哺）见 → [11 数据闭环](11-data-loop.md)；只给一条结论：**风控对特征一致性的容忍度比推荐系统低一个数量级**——推荐错了掉 1% 点击率，风控错了是钱。

## 08.13 成本控制：给每个请求一个硬预算

| 机制 | 做法 | 数值 |
| --- | --- | --- |
| **每请求总预算** | 同步链路 P99 ≤ 5 ms（实际 0.65 ms），CPU ≤ 0.4 核·ms | 超预算即跳过非必判规则 |
| **三级分流** | 全量 L1+L2+L3（纯内存）；抽样 4% 走 L5 模型；命中后深查 L4 图 + L6 人工 | 见 §08.3 流量账 |
| **预算熔断 + 按主体限流** | L5 错误率 > 5% 持续 30 s → 自动 `off`；同一设备/IP 每分钟查询次数封顶 | 恢复需人工确认；防「用查询本身打爆风控」 |
| **ROI 曲线** | 80% → ¥4 万/月；90% → ¥9 万；**96% → ¥37.5 万**；98.5% → ¥160 万；99.9% → ¥900 万+ | 边际成本每次上一个台阶，误杀率同步上升 |

> **96% 不是技术极限，是经济最优点。** 剩下 4% 的正确做法不是加模型，是**降低单次损失**（冻结而非作废、券分批发、限额）——这又回到 `llm/32` 那句「改定价比加防御有效」。

## 08.14 这个形态特有的崩法（七问 ⑤）

| 失效 | 长什么样 | 定位方法 | 预防 |
| --- | --- | --- | --- |
| **规则无限增长** | 上线一年后 1,800 条规则，单请求求值 12 ms，业务超时 | 看 `risk_eval_ms` 分位与规则数曲线 | 规则总数硬顶 500；90 天零命中自动待下线 |
| **名单同步断流** | 封了但还能访问，或「部分地区已封、部分地区未封」 | 对比 DB 版本号与各 Pod `bloom.ver` | 版本长轮询（10 s）+ `stale_snapshot` 告警 + 保守模式 |
| **模型静默回退** | 分数分布突然偏移但没人发现 | 每日比对线上分数分布与训练分布（PSI） | 分布漂移 > 0.2 告警；模型产物带版本与校验和 |
| **误杀舆情** | 某学校机房/某企业出口 IP 被整体限速，家长投诉上热搜 | 按 ASN/地理/主体类型分桶看处置率 | 分桶评估 + 灰度 + 申诉入口 + 响应体说明原因 |
| **灰度分桶不稳** | 同一用户第一次被拦第二次放行，反复横跳 | 抽样同一主体的 10 次请求看处置一致性 | 分桶哈希**只用稳定字段**，绝不含时间戳 |
| **回放集过期** | 新规则回放通过，上线即误杀 | 回放集的样本时间跨度 | 回放集滚动更新（最近 7 天，每周重建） |
| **处置不可回滚** | 申诉通过了，但券已核销、货已发 | 检查处置动作是否全部 `reversible` | 冻结而非作废；回滚幂等键 = case_id |

## 08.15 换挡信号：L0 → L4（七问 ⑥）

每一次升级都不是「因为量大了」，而是某个具体指标越过了具体阈值。

| 阶段 | 形态 | 容量 | **换挡信号（硬阈值）** | 代价 |
| --- | --- | --- | --- | --- |
| **L0** | IP 限流 + 人工封号 | 1 千 QPS | 出现第一次「券被刷完」事故 | 无 |
| **L1** | 规则引擎（DB 配置）+ 静态黑名单直查 DB | 1 万 | 名单查 DB 让判定 P99 > 20 ms；或名单变更到生效 > 1 min | 每请求一次 DB 查 |
| **L2** | 进程内布隆 + Kafka 增量 + 处置分级 + 申诉入口 | 5 万 | 规则数 > 500 且求值 > 3 ms；或周误杀投诉 > 10 起 | 名单一致性问题开始出现 |
| **L3** | 图关系 + 模型（抽样）+ 回放平台 + 特征注册表 | 20 万 | 团伙规模化（真人众包），单点特征全面失效 | 图的误杀率、模型不可解释 |
| **L4** | 实时特征平台 + 决策中台 + 常态红蓝对抗 + 结算侧关联 | 100 万 | 单地域容量上限 / 跨境特征延迟 > 200 ms | 组织成本（风控要独立团队） |

**多数业务的目标落点是 L3。L2→L3 的临界点最值得说**：当你发现「规则命中率一周内从 62% 掉到 31%」，那不是规则写错了，是**对手从阶段②升到了阶段③**——继续调阈值是自杀（误杀率同步翻倍），正确动作是引入新的关联维度（图/结算）。**也不要跳级**：没有申诉入口（L2）就上模型（L3），等于用不可解释的手段做不可回滚的处置，第一次误杀就是舆情。

## 08.16 怎么验证（七问 ⑦）

| 手段 | 做法 | 通过标准 |
| --- | --- | --- |
| **影子模式** | 新规则/新模型 `shadow` 跑 72 h，只算分只打日志不处置；每周另抽 200 条处置样本人工判定 | 命中量在预期区间；真实误杀率 < 2% |
| **回放 diff** | 用近 7 天 FactSet 快照重放新老规则集 | 命中量变化 < 1.5 倍，或差异全部有人工解释 |
| **名单同步演练** | 每季度 kill Kafka 与 Redis，看数据面是否进入保守模式 | 黑名单仍 100% 拦住；端到端 P99 从 3 s 退化到 8 s 内 |
| **红蓝对抗** | 每月自建「羊毛小队」用真金白银小额打自己（预算 ≤ ¥2,000） | 从攻击发起到被拦截 < 10 min；至少找到 1 个新绕过手法 |
| **灰度 + 漂移** | 1% → 10% → 50% → 100%，每档 24 h；每日比对线上/训练分布 PSI | 申诉率 < 2%，二次投诉 < 5%，PSI < 0.2 |

> **红蓝对抗是唯一能证明「你还活着」的手段。** 所有规则和模型都只能证明「过去的对手被拦住了」。自建一支羊毛小队并给它 ¥2,000 预算，比任何离线评估都值钱——**你自己的小队找到的手法，黑产一定也找到了，只是还没来**。

## 08.17 反模式表

| # | 反模式 | 后果 | 正解 |
| --- | --- | --- | --- |
| 1 | **风控串行阻塞主流程**（同步 RPC 调风控服务） | 风控抖动 → 全站 P99 从 200 ms 到 8 s | 规则/名单/图在业务节点本地求值，模型异步补判 |
| 2 | **模型无兜底** | 模型服务挂了全站拒付或全站放行 | 每层三态（on/shadow/off），关闭即降级 |
| 3 | **黑名单只在 DB** | 每请求一次 DB 查；名单延迟 = 缓存 TTL | 进程内布隆 + Kafka 增量 + Redis pub/sub + 版本长轮询（§08.9） |
| 4 | **误杀无申诉** | 技术问题升级为舆情；模型拿不到误报标签 | 响应体带 case_id + 申诉链接；每周误杀抽检 |
| 5 | **规则无限增长无人清理** | 1,800 条规则 / 12 ms；改一条不知道会不会炸别的 | 硬顶 500 条；90 天零命中待下线；上线必走回放 |
| 6 | **名单靠 TTL 过期生效** | 攻击窗口 = TTL（事故二 = 7 h） | 旁路同步，端到端 ≤ 3 s（§08.9） |
| 7 | **风控主体是账号** | 4,000 个假账号天然合法（事故一） | 主体 = 设备 + 支付 + 地址 |
| 8 | **处置不可回滚**（领取即生效、直接作废） | 误杀无法返还，只能赔钱道歉 | 冻结 → 复核 → 返还；回滚幂等键 = case_id |
| 9 | **灰度分桶含时间戳/随机数** | 同一用户忽封忽放，投诉翻倍 | 只用稳定字段哈希分桶 |
| 10 | **只报召回不报误杀** | 看板一片绿，实际每天误杀上千人 | 召回与误杀必须同屏；误杀用抽样估真值 |

## 08.18 十分钟答题卡

被问「你怎么设计风控/反作弊」时，按这个顺序讲，不要从「我用一个 XGBoost」开始：

```
1  真问题   处置同时是技术判定+对用户的承诺+已经发生的钱 → 必须分层、可解释、可回滚
2  漏斗     指纹→规则→名单→图→模型→人工；便宜在前，只给模型 4% 的流量
3  账       12 亿次/天；模型 ¥4.3 万/月，人工 ¥32 万/月（最贵的是人）
4  延迟     同步 0.65 ms（L1~L4 本地），模型异步只作用于下一次请求
5  规则     表达式 DSL + 白名单函数；快照热更新；灰度按稳定字段分桶；上线必回放
6  名单     白/黑/灰 + 布隆→Redis→DB；DB 提交到数据面可见 ≤ 3 s；
           黑名单 fail-closed，白/灰 fail-open；四层兜底 + 保守模式
7  图       2 跳内用预计算邻域表（不必上图库）；全图算法走离线批；先做度剪枝
8  误杀     冻结而非作废；申诉入口在被拦页面上；60% 自动秒解；通过后加白+幂等返还
9  对抗     脚本→农场→真人众包→内鬼；每阶段换关联维度，不是换更强的模型
10 换挡     规则数 > 500 或求值 > 3 ms → 名单下沉；命中率一周腰斩 → 上图和结算关联
11 验证     影子 72h、回放 diff、季度 kill 消息层、每月 ¥2,000 自建羊毛小队
12 停止点   拦到 96% 就停手，剩下的靠「降低单次损失」，不靠加模型
```
