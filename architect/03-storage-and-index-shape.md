## 03.1 事故引子：两次「拆完才发现下不了车」的故障

### 事故一：按 `user_id` 分片，主查询却是订单号（2025-04，某订单中台）

`t_order` 8.2 亿行、1.9 TB，2025-04 按 `user_id` 哈希拆成 **32 库 64 表**。选它的理由只有一个，而且听起来无懈可击：「订单属于用户」。但客服、风控、对账三个系统、以及 App 的「我的订单」详情页，全部是 `WHERE order_no = ?`。

| 时间 | 事件 | 数据 |
| --- | --- | --- |
| 04-08 02:00 | 完成双写切换，读全部走新分片路由 | 64 片 |
| 04-08 09:02 | 客服「按订单号查」沿用旧 SQL，路由层拿不到分片键 → **广播 64 片** | 单次 22 ms → 1.4 s |
| 04-08 09:14 | 客服并发 260，连接池 64×20=1,280 被打满 | 池利用率 100% |
| 04-08 09:19 | 广播查询压满 32 个从库，CPU 88%；下单链路 P99 3.6 s | 成功率 71% |
| 04-08 09:26 | 超时重试把放大倍数从 64 抬到 147，雪崩自持 | 重试 ×2.3 |
| 04-08 09:41 | 熔断「按订单号查」入口，下单恢复；客服不可用 **39 分钟** | 积压工单 2,150 张 |
| 04-08 ~ 04-30 | 只做了一件事：给 `order_no` 建全局冗余索引表，回填 8.2 亿行 | 19 天，返工 6 人月 |

放大倍数必须算出来，否则复盘的结论会停在「要加机器」：

```
一次「按订单号查一单」
= 路由层无分片键 → 广播 64 片
→ 64 × 22 ms（并发发起，但 P99 由最慢一片决定）≈ 1.4 s
→ 超时重试 2.3 倍 → 实际分片查询数 ≈ 147 次 / 一个用户请求
→ 连接占用 147 × 并发 260 ≈ 3.8 万连接次/秒，池内只有 1,280
→ 关键结论：分片数乘以重试系数，才是真实的放大倍数；64 这个数字骗人，147 才骗不了人
```

**根因不是选错了库（MySQL 完全够用），而是把一个"数据归属"键当成了"查询入口"键。** 而分片键是全系统唯一一个**改一次要全员返工**的决策。

### 事故二：按时间分片后，随机点查全部挤在热片（2025-07，某账单系统）

某账单系统按 `created_at` 建 32 张月表（循环表名），选它的理由是「归档方便、范围查询快」。真实业务是：96% 的点查发生在最近 7 天，100% 的写发生在当月。

| 时间 | 事件 | 数据 |
| --- | --- | --- |
| 07-15 10:00 | 月度出账，当月表写入 1,180 万行 | 100% 写在 1 张表 |
| 07-15 10:20 | 当月表缓冲池命中率 97.2%，P99 从 12 ms → 210 ms | 其余 31 张表 100% 命中 |
| 07-15 10:35 | 用户端「查上月账单」不带时间条件 → 32 路 fan-out | 单次 2.6 s |
| 07-15 11:10 | 当月表磁盘 IO util 100%，从库延迟 47 s | 收支核对读到旧数据 |
| 07-15 12:30 | 临时把最近 3 个月合并到一张「热表」，问题缓解 | 架构改动 0，配置改动 1 |

```
均匀分 32 片时，每片应承担全局负载 1/32 ≈ 3.1%
实际最新月表 = 100% 写 + 96% 点查 → 相对平均片放大 ≈ 1.96 / 0.0625 ≈ 31 倍
等价结论：32 片只能当 1 片用，另外 31 片是一堵"备份墙"——不扛流量，只扛备份时间
```

### 安静的第三种：索引错了，但没人把它归因到"形态"

一张 11 个索引、210 GB 的短链表，一次运营 `ORDER BY created_at DESC LIMIT 100000,20` 把 IO 打满，跳转 P99 从 8 ms 涨到 1.9 s（→ [12 短链 · §12.1](12-shortlink-system-design.md) 事故三）。没有分片键错误、没有选错库，只是**索引形状与查询形状不匹配**——深分页在分片前是慢，在分片后是 64 倍慢。三起事故因此分别对应 **分片键错 × 分区维度错 × 索引形状错**，正好是本篇的三节。

## 03.2 ① 到底是什么：形态 = 四件事的打包 + 一个键

**定义**：一个存储形态由四件事共同决定——**数据模型**（行/文档/键值/点边/时序/倒排/向量/对象）、**访问路径**（允许怎么查、靠什么索引、能否 join 与多跳）、**一致性模型**（写完何时被谁看到、能否跨实体原子）、**扩展单元**（加机器时按什么切）。产品只是这四件事的打包（判据与九类后悔案例见 `eng/35 §35.2`、`§35.4`，本篇不重写）。

本篇只补第五件事，也是 `eng/` 没有的那一件：

> **扩展单元里的那个键（分片键 / 分区键 / 一致性哈希键）本身就是形态的一部分。**
> 它不是"实现细节"，而是**一份对全系统的查询契约**：从它写进 DDL 那天起，所有不带它的查询都从"一次点查"退化为"一次 N 路广播"。

先钉死四个误解，每一个都能用本篇后面的算账击穿：

| 你以为的 | 真相 | 不做会怎样 |
| --- | --- | --- |
| 「选型 = 选产品」 | 产品决定了你**只能**怎么建模、怎么查 | 选了分片键不支持双维度的产品，业务改造工期翻倍 |
| 「分片键是 DBA 的事」 | 它等价于宣布「哪些查询是一等公民」 | 上线后 76% 的流量变成广播（事故一） |
| 「先建表，查询以后再优化」 | 查询形状决定索引，索引形状决定分片键，顺序反了就是重建 | 加索引能救慢 SQL，救不了分片键 |
| 「水平扩展 = 能加分片」 | 分片只解决"单机装不下 / 写不动"，不解决查询维度 | 64 片里 63 片在空转，热点还在那一片 |

## 03.3 ② 唯一真问题

> **分片键是唯一一个"押错就再也回不去"的架构决策。**

把它和旁边几个决策放在同一把尺子上量，差距立刻出来：

| 决策 | 换掉的方式 | 时间尺度 | 可逆性 |
| --- | --- | --- | --- |
| 换缓存产品（Redis → Memcached） | 换客户端 | 天级 | ✅ 完全可逆 |
| 换 / 加索引 | 在线 DDL（gh-ost） | 小时级 | ✅ 可回滚 |
| 换存储引擎（MySQL → TiDB） | 双写 + 迁移，SQL 兼容 | 季度级 | ⚠️ 有路径，疼痛但可控 |
| 换分片键 | 全量重分布 + 所有查询重写 + 双跑 | 半年~一年 | ❌ 事实不可逆 |
| 换标识符语义（短码复用/长度） | —— | 不可能 | ❌ 物理世界已印 |

所以本篇的判断标准不是「这个库好不好」，而是两句话：

1. **形态是"选"，分片键是"押"。** 形态选错了，你在评审上丢一次脸；分片键押错了，你在半年后丢一次团队。
2. **形态决定下界，分片键决定天花板。** 形态决定了你 3 年能不能装下；分片键决定了你装下之后还能不能查。

## 03.4 ③ 量级与预算：先算三个数，再打开任何产品文档

不许拍脑袋。形态选型只需要三个数字，全部可推。

**数一：容量与分片数**（事故一那套系统，真实量级）

```
日新增     60 万单 → 年 2.19 亿 → 3 年 6.6 亿行（囤积存量 8.2 亿，迁移后归档回收）
裸行宽     500 B（热字段 + 状态 + 金额 + 时间）
索引开销   ×1.6（推导见 §03.11）→ 800 B/行
物理容量   6.6e8 × 800 B ≈ 528 GB（data + index）
峰值写     4,200 TPS（大促系数 ×3）
点查峰值   8.6 万 QPS（读写比 ≈ 20:1）

分片数 = max( 容量维 ceil(528/200)=3 → 取 4 , 写维 ceil(4200×1.5/5000)=2 ) = 4
虚拟槽 4096 预留 → 每槽 ≈ 129 MB（这个数是 §03.10 全部时间的分子）
```

注意读的 8.6 万 QPS **没有进分片数**：读靠从库 + 缓存（→ [04 读路径形态](04-read-path-and-cache-shape.md)），把读流量算进分片数是最常见的过度设计（`eng/36 §36.4.2`）。

**数二：查询形状分布**——选分片键的唯一输入，必须按 QPS 加权，不许按"业务感"排。

| 查询 | 占比 | QPS | 按 `user_id` 分片时带键？ | 按 `order_no` 分片时带键？ |
| --- | --- | --- | --- | --- |
| 按订单号点查（客服/风控/对账/详情页） | 76% | 6.5 万 | ❌ 广播 64 片 | ✅ 单片 |
| 按用户查订单列表 | 13% | 1.1 万 | ✅ 单片 | ❌ 需投影 |
| 按商家 / 活动维度 | 7% | 6,000 | ❌ | ❌ |
| 运营多维筛选 | 3% | 2,600 | ❌ | ❌ |
| 报表聚合 | 1% | 860 | ❌ | ❌ |

> **结论直接摆在这里：分片键必须选 `order_no`。** 「订单属于用户」是数据归属直觉，「76% 的查询在 WHERE 里放 order_no」是查询直觉——**分片键跟查询走，不跟实体走**。这就是事故一的全部根因，也是本篇唯一真问题的第一推论。

**数三：写放大**（索引形状买单）

```
一次 UPDATE status = 1 行聚簇索引 + status 索引 + updated_at 索引 + redo/binlog 双写影像
索引数 6 时实测放大 ≈ 2.8 倍；binlog 行影像 → 复制流量 ×3
换算：4,200 TPS × 2.8 ≈ 11,760 等效写 IOPS —— 这才是选盘的真实输入（推导见 §03.11）
```

## 03.5 ④ 形态怎么选：十一类存储的「唯一正确条件 / 代价 / 该换掉的信号」

这张表是本篇的字典：**每行只回答三句话**——什么条件下它是唯一正确选择（不是"适合"，是"唯一"）、必须显式买单的代价、出现什么信号该换掉。机制细节一律引 `eng/35`–`eng/38`。

| 形态 | 唯一正确的条件 | 代价（必须显式买单） | 换掉它的信号 |
| --- | --- | --- | --- |
| **关系型** MySQL/PG | 写集合能被**一个事务**覆盖，查询维度 ≤4，且需要约束/对账 | 水平扩写要人工分片；单表有容量天花板；DDL 有复制延迟代价 | buffer pool 命中率 <99%；单表 >300 GB；DDL 超低峰窗口；写 TPS >8k（`eng/36 §36.4`） |
| **KV** Redis/etcd | 只需「按 key 取整块」，**且丢了能从别处重建** | 内存单价是 SSD 的 40~80 倍；无查询无事务；主从切换可能丢几十分钟 | 命中率 <85%（该换形态而不是加内存）；单 key >10 MB；出现二级查询需求（`eng/37 §37.5`） |
| **文档** Mongo | 一次读写**一个完整聚合**，且聚合不跨文档原子 | 跨文档事务有 60 s / 16 MB 限制；`$lookup` 递归即自杀 | 出现跨集合 join、事务超时、`totalDocsExamined`≈全表（`eng/35 §35.4.2`） |
| **宽列** Cassandra/HBase | 能**提前枚举全部查询**，且每条落「一个分区 + 一个 clustering 范围」 | query-first 的反向设计成本；无 join、聚合弱；tombstone 与 compaction 写放大 | 出现 `ALLOW FILTERING`；单分区 >100 MB；需要跨分区聚合（`eng/37 §37.4.3`） |
| **列式** ClickHouse | **扫大量行的少数列做聚合**，且写入是批量 | 点查要扫一个 granule（8192 行）；mutation 异步；单条 insert 报 Too many parts | 出现高频点查、单条写、按主键更新（`eng/37 §37.4.5`） |
| **搜索** ES | 要**相关性排序或多维任意组合**，且能接受秒级可见 | 近实时 1 s；倒排写放大最高（段合并）；深分页堆内存 | 有人拿 ES 写成功当业务成功；需要"写完立刻读"（`eng/37 §37.3` 三条铁律） |
| **图** Neo4j/Nebula | **≥4 跳**或需要路径/环路检测，且关系本身就是答案 | 写入放大、超级节点即性能杀手、运维重、缺成熟事务与备份 | 90% 查询是 1 跳点查；节点仅几万（`eng/38 §38.5` 判据表） |
| **向量** Milvus/Qdrant | 语义 top-k 是**主查询**，且能接受近似召回与删除延迟 | 内存最贵；删除是软删 + compaction；embedding 版本漂移 | 过滤条件变多（pre/post filter 崩塌）；需要精确匹配 |
| **时序** InfluxDB/Timescale | append-only + 查询**永远带时间窗** + 要 TTL/降采样 | tag 高基数即 OOM；乱序写差；更新删除难 | tag 基数 >10 万；需要与业务表 join（`eng/35 §35.4.3`） |
| **对象存储** S3/OSS | 单对象 **≥1 MB**、只按 key 存取、要 CDN/直传/生命周期 | 无查询、list 很慢、延迟 20~200 ms | 要按元数据检索（→ 建索引表/ES）；对象普遍 <64 KB |
| **文件/本地盘** | 单机、单写者、**可重建**的中间产物（WAL、上传临时文件、索引段） | 无副本、无迁移、机器一换就没 | 被第二台机器需要；需要跨重启持久 |

**读这张表的正确姿势**：不要横向比"谁快"，纵向看**"该换掉的信号"那一列**——那才是评审时真正会用到的一列。

## 03.6 ④ 形态决策树：四个入口，一问否决

```
                 ┌── 入口① 数据形状：一行/一聚合多宽？嵌套多深？有大对象吗？
   业务数据 ─────┼── 入口② 查询形状：点查 / 范围 / 聚合 / 全文 / 多跳 / 语义 top-k
                 ├── 入口③ 一致性：写完必须立刻读到？要跨实体原子？
                 └── 入口④ 规模：3 年多少 TB？峰值写 TPS？单机装得下吗？

入口② 查询形状（必须第一个答，因为它决定索引与分片键）
│
├─ 点查为主（>80% QPS 带唯一键）
│    ├─ 要事务/约束/对账 ─────────────────────► 关系型（单库 → 按查询键分片）
│    ├─ 可重建、要亚毫秒 ─────────────────────► KV（缓存，不是权威源）
│    └─ 单值 >1 MB 或要直传 ──────────────────► 对象存储 + 元数据表
│
├─ 范围为主（时间窗 / ID 区间 + 排序）
│    ├─ append-only + 必带时间窗 + 要 TTL ────► 时序
│    ├─ 单机装得下、要 join ──────────────────► 关系型（B+ 树聚簇，范围即顺序）
│    └─ 十 TB 以上、写吞吐优先 ───────────────► 宽列（分区键 = 范围边界）
│
├─ 聚合为主（group by 几维度、扫百万行）
│    ├─ 明细还要点查 ────────────────────────► 关系型存明细 + 列式存聚合（双写）
│    └─ 只要聚合结果 ────────────────────────► 列式
│
├─ 全文 / 多维任意组合
│    └─ 一律派生：权威源 → CDC → 搜索（ES 永不作为权威源）
│
├─ 多跳（路径 / 环路 / 影响面）
│    ├─ 1~3 跳且跳数固定 ────────────────────► 关系型邻接表 / 闭包表
│    └─ ≥4 跳或要路径 ───────────────────────► 图（作为索引，不是真相）
│
└─ 语义 top-k ───────────────────────────────► 向量（原文必须在对象存储）

入口③ 一致性 = 一票否决层（不选产品，只排除）
   要跨实体原子      → 排除 KV / 宽列 / 搜索 / 对象；图与向量只能做派生
   写完必须立刻读到  → 排除搜索 / 列式 / 宽列（读己之写不成立）
   可容忍秒级        → 全部可选，回到入口② 选

入口④ 规模 = 只决定「单体还是分片」，不决定「哪个产品」
   3 年 <1 亿行且热数据进 buffer pool → 单库，别分
   装不下 / 写不动 → 先归档 + 分区 + 大字段外置 + 读写分离，买回 18 个月
   仍然不够 → 分片，分片键 = 入口② 的主查询条件（§03.7）

入口① 数据形状的否决权：行宽 >4 KB 或含 >64 KB 大字段
   → 大字段外置对象存储，DB 只存 uri + sha256 + size
   （否则行溢出页让每次点查多一次 IO，buffer pool 有效容量降一个量级）
```

这张树的用法是**从上往下走，但允许入口③ 否决入口② 的结论**。典型降级：业务要「语义搜索 + 强事务」，答案是**权威源关系型 + 向量派生索引**，而不是"找个能做事务的向量库"。

## 03.7 ④ 分片键四原则：每一条都给正反例

先声明边界：`eng/36 §36.5` 给的是**键的合格性**（查询必带、基数高、分布均匀），本篇给的是**键应该表达什么**——前者是体检，后者是选人。

| # | 原则 | 一句话判据 | 键取谁 | 正例 | 反例（后果） |
| --- | --- | --- | --- | --- | --- |
| 一 | **点查型 = 查询条件** | 「QPS 最高的那条 SQL 的 WHERE 里放什么？」 | 主查询的等值条件 | 短链 `WHERE slug=?` → `hash(slug)`；订单 76% 按 `order_no` → `hash(order_no)` | 按 `tenant_id` 分片做跳转（URL 里没有租户）；按 `user_id` 分片做订单号查询 → 事故一，147 倍放大 |
| 二 | **范围型 = 范围边界** | 「查询是否**永远**带一个时间/ID 区间？」 | 区间的下界字段 | 账单按月：`PARTITION BY RANGE(created_at)`，查询必带月份 | 无时间条件的随机点查 → 32 路 fan-out；事故二，31 倍倾斜 |
| 三 | **聚合型 = 聚合维度** | 「group by 的维度是哪个？」 | 聚合维度 | 按租户出账/配额：`hash(tenant_id)`，单分片完成聚合 | 把点查系统按聚合维度分片 → 点查全废（→ [12 短链 · §12.5](12-shortlink-system-design.md) 中 `tenant_id` 的 ❌ 判定） |
| 四 | **写入型 = 打散热点** | 「热点是**一个 key** 还是一个**区间**？」 | key + salt / 分桶 | 计数器 `uid%64` 分桶后求和；秒杀库存按 `item_id%N` 加盐 | 为"均匀"按随机 UUID 分片 → 点查失去条件，N 路广播（§03.15 反模式 2） |

### 四条原则冲突时怎么办：优先级是硬序

```
点查 > 范围 > 聚合 > 写入
```

理由是一条经济学判断：**写入热点可以在分片内部解决（加盐子表、请求合并、批量提交）；点查废了没有内部解法**（只能新增一张全局索引表，等于把事故一的 19 天返工重来一遍）。反过来，如果一个系统聚合需求压过点查需求，那它根本不该用这个形态——它该是「关系型存明细 + 列式存聚合」的双写（§03.6 入口②）。

### 一个让原则一和原则三同时成立的技巧

订单号在生成时就嵌入分片位：`order_no = 槽位编号(4 位) + 时间(YYYYMMDDHHmmss) + 序列(4 位)`。

于是 `hash(order_no)` 与 `hash(user_id)` 被**人为对齐到同一槽**，`t_order`（按 order_no）与 `t_order_by_user`（按 user_id）落在同一个物理库 → 下单事务可以**本地事务**同时写两张表，不需要 Outbox。

代价必须写明：① 订单号结构暴露分片信息（对外单号需脱敏或改为可逆编码）；② 槽位编号必须用**虚拟槽号而不是物理库号**，否则扩容后所有历史订单号的分片位全部失效——这条约束直接把 §03.10 的虚拟槽设计变成前置条件，而不是后置优化。

## 03.8 ⑤ 会在哪崩：分片键选错的三个不可逆后果

这不是"性能问题"，是"能力问题"——性能可以加机器，能力只能改业务。

| # | 后果 | 机制 | 放大倍数（可算） | 唯一补救 |
| --- | --- | --- | --- | --- |
| 1 | **跨片查询全废，只能扫全片** | 无分片键 → N 路 fan-out，P99 由最慢一片决定，再乘以重试系数 | 64 片 × 22 ms × 重试 2.3 ≈ 147 次分片查询 / 3.8 万连接次每秒 | 冗余表或异构投影（成本随查询维度**线性增长**，每加一个维度 = 一次全量回填） |
| 2 | **热点无法拆分，同一片永远热** | 分片键含业务分布不均（大租户/大商家/最新时间段），最热片恒为同一物理片 | 头部租户 18% 流量 → 倾斜度 max/avg ≈ 3.6 → 分片翻倍只换来 **1.15 倍**有效容量 | 加盐子表（查询变 N 路归并，等于自造跨片查询）或热点单独成库（多一套路由与运维） |
| 3 | **再分片成本指数上升** | 若键里含"语义边界"（时间段、租户段），迁移单元不是 key 而是业务对象，必须停写窗口 | 按 key 迁移可在线（虚拟槽，搬 50% 数据 ≈ 1.5 h）；按语义边界迁移必须离线（数小时停写 + 全量校验） | 一开始就预留虚拟槽（§03.10），且键里不放任何业务语义 |

三条后果有一个共同结构：**它们都在"上线之后"才显形，而修复窗口在"上线之前"。**

## 03.9 ⑤ 标准案例：短链为什么必须是 `slug hash`

短链的分片键之争已经由 [12 短链 · §12.5](12-shortlink-system-design.md) 定案，本篇只复述结论 + 补上那篇没展开的一件事（租户维度怎么办）。

| 候选键 | 优点 | 致命问题 | 判定 |
| --- | --- | --- | --- |
| **`slug hash`** | 跳转点查天然单分片、天然均匀 | 租户视角的列表/统计必须扫全部分片 | ✅ 主库只能选它 |
| `tenant_id` | 租户隔离天然、运营查询单分片 | 大租户成热点分片；且**跳转必须带租户信息**（URL 里没有） | ❌ |
| 时间（月表） | 归档容易 | 跳转是随机访问，按月分片等于把热数据打散到 32 片 | ❌ |

一句判据：**99.99% 的查询是 `WHERE slug = ?`，所以分片键只能是 slug。** 这正好是 §03.7 原则一。

### 那"按租户查列表"怎么办：三档异构投影，按一致性要求选

| 档 | 形态 | 一致性 | 代价 | 什么时候用 |
| --- | --- | --- | --- | --- |
| 一 | 冗余索引表 `link_by_tenant(tenant_id, created_at, slug)`，按 `tenant_id` 分片 | 秒级（Outbox），或强一致（用 §03.7 的槽位对齐技巧让两表同库） | 多一张表、多一份存储 | 运营后台的**主流程**：按租户翻列表 |
| 二 | ES 投影，支持 tenant / activity / domain / status 多维筛选 + 游标分页 | 秒级 | 一个要运维的集群 | 多维筛选、模糊搜索 |
| 三 | 列式预聚合（ClickHouse），按租户 × 天 | 分钟级 | 又一套存储 | 报表、计费口径核对 |

三条铁律（`eng/37 §37.3`）：**写成功只由主库判定；投影必须可重建；读路径允许降级**。重建脚本每季度真跑一次——没跑过的重建脚本等于不存在（→ [21 埋点管道与数据湖](21-telemetry-pipeline.md)）。

**反例故事**：某团队为了让"按租户查列表"快，把主库改成 `tenant_id` 分片。结果跳转必须带租户（URL 里没有），被迫加一张 `slug → tenant` 的全局索引表；这张表又成了新的单点与热点，最终整体回滚，损失 8 周。一句话：**用主库去满足非主查询，等于用分片键付账。**

## 03.10 ⑥ 再分片路径：4096 虚拟槽 + 五阶段在线迁移

### 为什么必须是虚拟槽，而不是 `hash % 分片数`

```
直接取模：shard = hash(key) % 4  → 扩到 8 片时，每个 key 的归属几乎全变 → 必须全量搬 528 GB
虚拟槽：  slot = hash(key) % 4096 ; slot → shard 的映射放配置中心（带版本号）
         4 → 8 片时每片让出一半槽 → 只需搬 264 GB（50%），且迁移单元是"槽"而不是"表"
单槽容量 = 528 GB / 4096 ≈ 129 MB；按 50 MB/s 限速搬 264 GB ≈ 1.5~2 小时
```

若希望只搬 1/N，则不能靠取模，要用**槽组 + 一致性哈希环**（代价：映射表变大、可读性下降）。但多数系统停在"搬 50% 且可在线"就够了——**可回滚比搬得少更重要**。

→ [01 约束卡](01-constraint-card-and-capacity.md) 定容量，→ [20 海量数据迁移与拆分](20-data-migration.md) 讲完整迁移工程，这里是形态侧的最小闭环。

```
        ┌──────────── 阶段 1：双写（读老写双） ────────────┐
写请求 ─►│ 路由：slot → shard（映射版本 v1）                 │
        │        ├─► 老库（权威）                          │
        │        └─► 新库（影子槽，失败入"待补队列"）        │
        └───────────────────┬─────────────────────────────┘
                            ▼
   阶段 2：按槽全量搬 + 追增量 → 槽级 checksum 比对 → 差异重放
                            ▼
   阶段 3：影子读（1% 请求双读、只比对不返回）→ 比对 payload hash
                            ▼
   阶段 4：按槽灰度切读 [0-1023]v2 → 校验 → [1024-2047]v2 → ……（同一槽必须原子切）
                            ▼
   阶段 5：切写 → 观察 7 天 → 摘从库 → 摘老库（保留快照 30 天）
                            ▼
              映射表版本历史 v1 → v2 → v3 ……（回滚 = 切回上一个版本）
```

| 阶段 | 动作 | 时长（528 GB 量级） | 校验方式 | 可回滚方式 |
| --- | --- | --- | --- | --- |
| 1 双写 | 写老库 + 写新库（新库失败进待补队列，不阻塞业务） | 上线即生效，跑 24 h | 双写差异率 <0.01% | ✅ 关双写开关（新库数据整体作废） |
| 2 全量 + 增量 | 按槽分批搬（每批 20 万行），搬完持续追 binlog 增量 | 1.5~2 h + 追增量 | 每槽 `COUNT(*)` + `CHECKSUM TABLE` 双校验 | ✅ 删除新库对应槽数据，老库全程未动 |
| 3 影子读 | 1% 流量双读，只比对不返回 | 24 h | 不一致率 = 0 且持续 24 h | ✅ 关影子开关（不影响线上返回） |
| 4 按槽灰度切读 | 按 512 槽为一组放量：5% → 25% → 100% | 3 天 | 切读槽 P99 / 错误率 / 结果比对 | ✅ 回滚映射表版本（**必须整槽原子**） |
| 5 切写 → 摘库 | 新库成为权威，摘从库、摘老库 | 观察 7 天 | 新库写入成功率 / 复制延迟 | ⚠️ 只剩快照，恢复是小时级不是秒级 |

**第 4 阶段有一条铁律**：同一个 slot 的所有 key 必须**原子切换**。否则同一实体的两次读取落在两个库上，而新库还没追到最新写入 → 用户看到"数据回退了"。这不是缓存脏，是数据不一致，且极难定位。

### 骨架代码一：分片路由（Go，槽级原子切读）

```go
package shard

import (
	"hash/crc32"
	"sync/atomic"
)

const SlotCount = 4096

// Router: slot = hash(key) % 4096；slot → shard 映射来自配置中心，带版本号
type Router struct {
	slots atomic.Pointer[[SlotCount]uint16] // 整表不可变，替换即生效 → 同槽必然原子切换
}

func (r *Router) Slot(key string) uint16 {
	return uint16(crc32.ChecksumIEEE([]byte(key)) % SlotCount)
}

// Locate 返回本次查询必须访问的分片：命中分片键时恰好 1 片
func (r *Router) Locate(key string) (uint16, bool) {
	if key == "" {
		return 0, false // 绝不允许隐式广播；调用方必须走投影表或显式 FanOut
	}
	return (*r.slots.Load())[r.Slot(key)], true
}

// Apply 灰度切读的落点：调用方在副本上改若干槽，再整表替换一次
func (r *Router) Apply(next *[SlotCount]uint16) { r.slots.Store(next) }

// FanOut 仅限低频后台任务，且调用方必须带条数上限与超时
func (r *Router) FanOut() []uint16 {
	m := r.slots.Load()
	seen := make(map[uint16]struct{}, 16)
	out := make([]uint16, 0, 16)
	for _, s := range m {
		if _, ok := seen[s]; !ok {
			seen[s] = struct{}{}
			out = append(out, s)
		}
	}
	return out
}
```

### 骨架代码二：虚拟槽映射与按槽灰度（Java / Spring）

```java
@Component
public class SlotRouter {
    public static final int SLOT_COUNT = 4096;
    private volatile short[] slotToShard = new short[SLOT_COUNT]; // slot -> 物理分片序号
    private volatile long version;                                 // 映射版本，回滚靠它

    public int slotOf(String shardKey) {
        int h = Hashing.murmur3_32_fixed().hashUnencodedChars(shardKey).asInt();
        return Math.floorMod(h, SLOT_COUNT);
    }

    /** 点查：恰好命中一片；缺分片键直接抛错，禁止隐式广播 */
    public String locate(String shardKey) {
        if (shardKey == null || shardKey.isEmpty()) {
            throw new IllegalArgumentException("shardKey required: use projection table, not broadcast");
        }
        return "db_" + String.format("%02d", slotToShard[slotOf(shardKey)]);
    }

    /** 一次替换整张表 → 同一 slot 下的所有 key 原子切库（阶段 4 的铁律） */
    public synchronized void apply(short[] next, long nextVersion) {
        if (next.length != SLOT_COUNT) {
            throw new IllegalArgumentException("slot table size mismatch: " + next.length);
        }
        this.slotToShard = next.clone();
        this.version = nextVersion;
        log.info("slot map applied, version={}", nextVersion);
    }

    /** 灰度切读：只切连续 512 个槽（128 槽一组共 4 组），在副本上改，再整表替换 */
    public synchronized void cutoverSlots(int fromSlot, short targetShard, long nextVersion) {
        short[] next = slotToShard.clone();
        for (int s = fromSlot; s < fromSlot + 512 && s < SLOT_COUNT; s++) {
            next[s] = targetShard;
        }
        apply(next, nextVersion);
    }

    public long currentVersion() {
        return version;
    }
}
```

## 03.11 ⑥ 索引形态：最左前缀、覆盖、区分度、×1.6 与冗余

分片键决定"数据去哪一片"，索引决定"在片内怎么找"。两者的失败模式不同：分片键错是能力缺失，索引错是成本失控。

### 最左前缀：可用的三种，不可用的三种

| 索引 | 查询 | 用到几列 | 说明 |
| --- | --- | --- | --- |
| `idx(user_id, status, created_at)` | `user_id=? AND status IN(10,20) ORDER BY created_at DESC` | 3 列全用 | ✅ 等值→IN→排序 |
| 同上 | `user_id=? AND created_at>?` | 只用到 `user_id` | ⚠️ `status` 缺失 → 后续列退化为过滤 |
| 同上 | `status=?` | 0 列可用 | ❌ 违反最左前缀，等于没有 |
| `idx(status, created_at)` | 运营「按状态查最近订单」 | 2 列 | ⚠️ `status` 仅 ≈5 个值，接近全表扫 |
| `idx(created_at)` | `ORDER BY created_at DESC LIMIT 100000,20` | 2 列 | ❌ 每片扫 100,020 行（§03.1 第三种事故） |

规则只有三句话：**等值列在前、范围列在后、排序列紧跟范围列；范围列之后的所有列只能过滤不能定位。**

### 覆盖索引：免回表，但索引会变宽

`SELECT slug, target FROM short_link WHERE slug=?` 若索引含 `(slug, target)`，执行计划出现 `Using index`，省掉一次回表随机 IO。代价常被低估：**二级索引每行都隐含主键（InnoDB 6~8 B）+ 页指针**，覆盖列越多 → 页越少装 → 树越高 → IO 反而变多。

纪律：**只为 Top 3 高频查询建覆盖索引，覆盖列 ≤2 个**。第 4 个查询该做的是改 SQL 或换投影。

### 区分度：先算再建，不要靠感觉

```sql
-- 建索引前必跑：三个候选列的区分度（distinct/total）
SELECT COUNT(DISTINCT status)    / COUNT(*) AS sel_status,
       COUNT(DISTINCT user_id)   / COUNT(*) AS sel_user,
       COUNT(DISTINCT DATE(created_at)) / COUNT(*) AS sel_day,
       COUNT(*) AS total_rows
FROM order_db.t_order;
```

判据：`区分度 >0.1` 才有独立索引价值；`<0.01` 的列（status、is_deleted、type）单独建索引基本白建，只能作为联合索引里的**过滤列**，且排在等值高区分列之后。

### 索引开销 ×1.6 是怎么来的

```
裸行 500 B
+ 3 个二级索引（每行含主键 8 B + 索引列 + 页指针，平均 45 B 有效） ≈ +135 B
= 逻辑 635 B；InnoDB 页填充率约 70%、碎片约 8%
→ 物理 ≈ 635 / 0.7 × 1.08 ≈ 980 B
980 / 500 ≈ 1.96（3 索引的上限情形）
工程上统一按 ×1.6 估算，再用 information_schema 的 data_length/index_length 实测校准
（§03.4 的 528 GB 就是这么来的）
```

### 写放大：索引不是免费的读

**一次 `UPDATE` 要改「1 行聚簇索引 + 所有被更新列涉及的索引」**：索引数 k、更新 c 个被索引列时，等效写次数 ≈ `1 + c`（再加 redo/binlog 各一份影像）。6 索引的表改 `status` 实测放大 ≈ 2.8 倍，binlog 复制流量 ×3。所以"为省空间不建索引"与"给每个查询都建索引"同样错：前者省 30% 存储换来 38 分钟停摆（`eng/35 §35.1`），后者把写路径 P99 从 4 ms 推到 15 ms。

### 冗余索引识别：一条可执行的 SQL

找出「某个索引的所有列，恰好是另一个索引的前缀」——这类索引永远不需要独立存在：

```sql
SELECT a.TABLE_NAME                                        AS tbl,
       a.INDEX_NAME                                        AS redundant_index,
       GROUP_CONCAT(a.COLUMN_NAME ORDER BY a.SEQ_IN_INDEX)  AS redundant_cols,
       b.INDEX_NAME                                        AS covered_by,
       GROUP_CONCAT(b.COLUMN_NAME ORDER BY b.SEQ_IN_INDEX)  AS covering_cols
FROM information_schema.STATISTICS a
JOIN information_schema.STATISTICS b
  ON  a.TABLE_SCHEMA = b.TABLE_SCHEMA
  AND a.TABLE_NAME   = b.TABLE_NAME
  AND a.INDEX_NAME  <> b.INDEX_NAME
  AND a.COLUMN_NAME  = b.COLUMN_NAME
  AND a.SEQ_IN_INDEX = b.SEQ_IN_INDEX
WHERE a.TABLE_SCHEMA = 'order_db'
GROUP BY a.TABLE_NAME, a.INDEX_NAME, b.INDEX_NAME
HAVING COUNT(*) = (SELECT COUNT(*) FROM information_schema.STATISTICS s
                   WHERE s.TABLE_SCHEMA = a.TABLE_SCHEMA
                     AND s.TABLE_NAME   = a.TABLE_NAME
                     AND s.INDEX_NAME   = a.INDEX_NAME);
```

配套两条：`SELECT * FROM sys.schema_unused_indexes` 找连续 30 天零使用的索引；`pt-duplicate-key-checker` 做上线前门禁。**冗余索引的代价不是空间，是每次写入多一次的页修改与复制流量。**

## 03.12 ⑥ 单表容量上限：先算 B+ 树，再谈"经验值"

### 层高与 IO 次数

InnoDB 页 16 KB，非叶节点一条索引项约 14 B（8 B 主键 + 6 B 页指针）→ 每页约 **1,170** 条；叶子页装行。

```
3 层 B+ 树容量 ≈ 1170 × 1170 × (16 KB / 行宽) = 136.9 万叶子页 × 每叶行数
  行宽 500 B → 每叶 32 行 → 4,380 万行
  行宽 1 KB  → 每叶 16 行 → 2,190 万行
  行宽 4 KB  → 每叶  4 行 →   547 万行
4 层 B+ 树 → 容量 ×1170，但点查 IO 次数从 3 次变 4 次（NVMe 上 P99 +33%）
点查延迟 ≈ 树高 × 随机 IO（0.1~0.2 ms）→ 3 层 0.3~0.6 ms，4 层 0.4~0.8 ms
```

**但真正崩的从来不是 IO 次数，是 buffer pool 装不下**：非叶节点 + 所有二级索引的工作集一起膨胀，命中率从 99.6% 掉到 91%，此时"多一层树"只是压垮它的最后一根稻草。

### 50 GB / 200 GB / 300 GB 三个阈值的来历

| 阈值 | 它到底是什么 | 推算 | 越过后的动作 |
| --- | --- | --- | --- |
| **50 GB** | **命中率拐点**：32C64G 实例 buffer pool 通常 48 GB，单表（含索引）50 GB 时"非叶 + 热叶 + 3 个索引工作集"开始换出 | 50 GB 表热数据（Top 20%）≈ 10 GB，加上索引与其它表，逼近 48 GB | 归档冷数据 / 分区，先别分片 |
| **200 GB** | **运维拐点**：一次 gh-ost DDL、一份逻辑备份、一次恢复演练都开始超出低峰窗口 | 200 GB ≈ 6~8 h DDL；4.2 亿行曾跑出 19 h 与 1.2 TB binlog 堆积（`eng/36 §36.1`） | 分区 + 归档；准备分片方案 |
| **300~500 GB** | **硬阈值**：任何一条缺索引的 SQL、一次 `COUNT(*)` 都能打满 IO，故障域失控 | `eng/36 §36.4` 的单表物理大小信号 | 必须分片或换分布式库 |

### 行数区间 → 该做什么

| 行数（行宽 1 KB） | 树高 | 结论 | 动作 |
| --- | --- | --- | --- |
| <1,000 万 | 3 层 | 舒适区 | 单表，只保证索引正确 |
| 1,000 万~5,000 万 | 3 层 | 可用 | 单表 + 归档（保留期从 5 年压到 18 个月） |
| 5,000 万~2 亿 | 3 层临界 / 4 层 | 开始疼 | 按月 RANGE 分区 + 冷热分离 |
| 2 亿~10 亿 | 4 层 | 必须动 | 分片，或换分布式库（`eng/36 §36.8`） |
| >10 亿 | 4 层且 DDL/备份不可行 | 已失控 | 分片 + 冷数据出库 + 明细进列式 |

### 什么时候"必须分"：先做完这四件事

分片是最后一张牌，前面四件事每一件都能买回 12~18 个月：

1. **归档**：保留期从 5 年压到 18 个月，常直接砍掉 80% 行数（6.6 亿 → 1.3 亿）；
2. **分区**：按月 RANGE 分区，删除变 `DROP PARTITION`（秒级，不再跑 19 小时 DELETE）；
3. **大字段外置**：行宽从 4 KB 降到 500 B，容量直接降一个数量级；
4. **读写分离 + 覆盖索引**：读 QPS 不进分片决策。

四件做完仍命中 §03.12 的三个阈值 → 分，且分片键按 §03.7 选。五条"不该拆"的判据见 `eng/36 §36.4.3`。

## 03.13 ⑥ 冷热分离：把 85% 的死数据请出主库

### 热数据判定：频次阈值 + 时间窗，双阈值

```
热 =  近 30 天内有写  或  近 30 天内读 ≥3 次
温 =  近 90 天内读 ≥1 次（且非热）
冷 =  近 90 天零读  且  近 180 天零写
```

双阈值而不是单阈值的理由：**进冷容易、出冷要重新热起来**。用「90 天零读」进冷，用「30 天 3 次读」回热，中间留缓冲区，避免审计季把整个冷库打活。处置：热 → 主库 buffer pool 内；温 → 主库分区表的近期分区；冷 → 归档库 / 列式 / 对象存储（Parquet）。

### 迁移任务：五个必须写进 runbook 的细节

1. 按**主键游标**分批扫（每批 5,000 行），不许 `LIMIT offset`；
2. 双写窗口内"边写边迁"，只搬 `updated_at < 水位` 的行，否则会把正在改的数据搬走；
3. 迁完做**行数 + checksum 双对账**，不一致的那批重放而不是"大概齐"；
4. 校验通过后老数据只置 `archived=1`，**保留 30 天不物理删除**（唯一可回滚窗口）；
5. 判定水位取「迁移时刻 − 30 天」这个**固定值**，不用 `now()`，否则跑批跨零点时边界日的数据会同时被判热和判冷。

### 冷存储的查询代价：必须提前告诉业务方

| 冷存形态 | 点查延迟 | 范围/全扫 | 单 GB 成本 | 适用 |
| --- | --- | --- | --- | --- |
| 同库归档表（分区） | 0.5~2 ms | 可接受 | 与主库同价 | 只降行数，不降成本 |
| 列式（ClickHouse） | 50~500 ms | 极好 | 0.5~1.5 元/月 | 报表、审计、计费核对 |
| 搜索冷节点（ES） | 10~100 ms | 好 | 1.5~4 元/月 | 检索型冷数据 |
| 对象存储（Parquet） | 秒级~分钟级 | 极好 | 0.033~0.12 元/月 | 合规留存、T+1 重算 |

（单价量级参考 `eng/37 §37.6`。）

### 冷热一致性：四个必然遇到、必须提前回答的问题

| 问题 | 长什么样 | 解法 |
| --- | --- | --- |
| 迁走后仍写入 | 冷库有、主库也改了，两边不一致 | 迁走即置**只读**（业务上"归档 = 只读"最省事），或双写校验 |
| 热点回迁 | 审计季一次性查全量冷数据，打挂冷库 | 冷查询限流 + 结果缓存 + 只允许导出任务访问 |
| 键不一致 | 冷数据按租户归档，但主库按 `slug/order_no` 分片 → 跨存储 join | 归档时**保留分片键与查询键两列**，让冷存储自己可查 |

## 03.14 ⑦ 怎么验证：七个能跑的检查，全部有通过标准

| 检查项 | 怎么跑 | 通过标准 | 不通过说明什么 |
| --- | --- | --- | --- |
| 分片键正确性 | 30 天慢查询日志按 QPS 加权，统计"不带分片键的查询占比" | <1%，且每条都在白名单内 | 分片键选错，或核心链路存在隐藏广播 |
| 倾斜度 | 各分片 `COUNT(*)` / CPU / QPS，算 `max/avg` | <1.5 | 键分布不均或热点未拆（`eng/36 §36.11`） |
| 索引有效性 | `rows_examined / rows_sent` | <100 | 最左前缀写错、区分度不足、索引缺失 |
| 冗余索引 | §03.11 的 SQL + `sys.schema_unused_indexes` | 0 条冗余、0 条 30 天未用 | 只为"可能会查"建的索引在收写放大的税 |
| 容量水位 | `(data_length+index_length)` / 200 GB；buffer pool 命中率 | <60% / >99% | 该归档或该分了 |
| 再分片演练 | 预发 1/10 数据跑完 §03.10 五阶段，记录每阶段耗时 | 总时长 <维护窗口，回滚 <5 分钟 | 没演练过的扩容方案等于没有方案 |
| 冷热有效性 | 抽 100 条冷数据点查 + 一次批量回捞 | 都能查到、延迟可接受、冷库不被打挂 | 迁移任务或判定水位有洞 |

再加一条评审时最好用的**「删键测试」**：把主查询清单逐条标注"落在几个分片"，任何一条 `>1` 且流量 `>1%` 的都是设计缺陷——不用压测，看清单就能判死刑。

## 03.15 反模式表

| # | 反模式 | 长什么样 | 为什么错 | 正解 |
| --- | --- | --- | --- | --- |
| 1 | **按时间分片的点查** | 月表/日表，但查询不带时间条件 | 100% 写 + 96% 点查压在一张表，放大 31 倍；无时间条件 32 路 fan-out | 时间只做 `PARTITION`（还是同一张表、同一个键），不做分表；分片键取查询条件 |
| 2 | **UUID v4 作主键** | `CHAR(36)` 或随机 `BINARY(16)` | 随机插入 → 页分裂、索引膨胀 1.5~2 倍、写入变随机 IO、buffer pool 有效容量下降 | 雪花 / 号段 / UUIDv7（时间有序，`UUID_TO_BIN(?,1)`）（`eng/36 §36.7`） |
| 3 | **为省空间不建索引** | 「这张表写多读少，先不加」 | 省 30% 存储，换来一次缺索引的 `COUNT(*)` 打满主库 38 分钟、连带 GMV 210 万（`eng/35 §35.1`） | 索引按查询建；用覆盖索引替代"补偿性索引"；用区分度淘汰低价值索引 |
| 4 | **一个库放多个业务** | 订单、用户、活动、日志同实例同库 | 故障域 / DDL / 连接池 / buffer pool 互相污染，一次运营大查询打挂所有业务 | 一业务一库（至少一业务一实例 + 独立连接池 + 独立慢查询门禁） |
| 5 | **大字段与热字段同表** | 详情 JSON、正文、附件 base64 塞在订单表 | 行溢出页让每次点查多一次 IO；备份体积翻倍；DDL 重写时间翻倍 | >4 KB 字段外置对象存储，DB 只存 `uri + sha256 + size`（`eng/35 §35.4.1`） |
| 6 | **无分片键查询进核心链路** | 详情页/客服入口直接 `WHERE order_no=?` | 一次用户请求 = N 路 fan-out × 重试系数（事故一，147 倍） | 路由层对缺失分片键**直接抛错**（见 §03.10 两段骨架代码），不允许"默认广播" |
| 7 | **分片后靠广播补查询维度** | 「反正后台 QPS 低，广播一下」 | 后台 QPS 低但连接占用高，且会与在线链路共享连接池 | 三档异构投影（§03.9），广播只允许出现在离线任务里 |

## 03.16 十分钟答题卡

被要求"设计一个 XX 系统，数据怎么存"时，按这个顺序讲，**不要从"我用 MySQL"开始**：

```
0  先反问三句   读写比多少？主查询的形状（点查/范围/聚合/全文/多跳/语义）？
                3 年多少 TB、峰值写 TPS 多少？
1  算量级       行数 = 日增 × 365 × 年；容量 = 行数 × 行宽 × 1.6；
                分片数 = max(容量维 ceil(总量/200GB), 写维 ceil(峰值写×1.5/5000))，读写分离不进这个公式
2  立真问题     分片键选的不是"数据归谁"，是"查询从哪进"——换库可以，换键不行
3  选形态       按查询形状走决策树（§03.6）；一致性做一票否决；规模只决定"单体还是分片"
4  定分片键     点查=查询条件 / 范围=范围边界 / 聚合=聚合维度 / 写入=打散热点；
                冲突时优先级是硬序：点查 > 范围 > 聚合 > 写入
5  收非主查询   一律异构投影（冗余表 → ES → 列式），按一致性要求选档，广播只准出现在离线任务
6  定索引       最左前缀（等值→范围→排序）；只为 Top3 建覆盖索引（列 ≤2）；
                区分度 >0.1 才独立建；冗余索引用一条 SQL 扫；索引开销按 ×1.6 估
7  定上限       1 KB 行宽 3 层树 = 2,190 万行；50 GB 命中率拐点 / 200 GB 运维拐点 / 300 GB 硬阈值
8  拆冷热       双阈值判定 + 归档即只读 + 判定水位固定 + 冷查询限流
9  留扩容器     4096 虚拟槽（slot = hash(key) % 4096）；双写 → 迁移 → 影子读 →
                按槽原子切读 → 切写 → 摘库；回滚靠映射表版本号
10 说验证       不带分片键查询 <1%、倾斜度 <1.5、rows_examined/rows_sent <100、扩容演练过
```

现场被追问时最值钱的三句：

- 「**这个分片键会让 76% 的查询变成广播**，我们先看查询形状分布再定键。」
- 「**分片键是唯一不可逆的决策**，所以我们预留 4096 虚拟槽，扩容只搬槽不改代码。」
- 「**索引开销按 ×1.6 算进容量**，所以 528 GB 是含索引的真实占用，不是裸数据。」
