# 《系统设计实战：从约束到形态到真实系统》· 总纲

> **一句话**：`eng/` 讲「零件装上去会怎么炸」，这套讲「**为什么是这几个零件、装配顺序为什么不能错、换成量级之后哪些零件必须换**」。
>
> 读者画像：能画出一张架构图，但被追问「为什么不用 XX」「为什么现在就分库」「换成十倍量级你改哪三个地方」时答不上来的后端与架构师。

| 项 | 说明 |
| --- | --- |
| 定位 | **形态决策 + 真实系统装配**。每篇必须回答「这个量级下唯一真正难的那一件事是什么」 |
| 篇幅规划 | 4 部分 · **26 篇** · 每篇 1 个文件 · 单篇 1.5 万–3 万字 |
| 代码 | Go 与 Java(Spring) 双栈，只给**骨架级**（单段 ≤ 40 行），完整 DDL 收进附录 |
| 风格 | 事故引子 + 算账 + 决策表 + ASCII 图；**每个结论必须带「代价」和「什么信号出现时该重构」** |
| 与 `eng/` 的边界 | 机制实现、失效模式、排障手册 → 一律引 `../eng/NN-xxx.md`；本套不重写 |

## 0.1 这套书要解决的那个问题

架构评审上最常见的三句话，正好对应三个层次的无知：

```
「这里加个 Redis 就好了」        → 不知道缓存的失效语义与一致性代价   （形态的内部）
「上 Kafka 解耦一下」           → 不知道消息语义决定了整个系统的一致性模型（形态的选型）
「先这样，量大了再拆」          → 不知道「量大了」的具体阈值在哪       （形态的演进）
```

`eng/` 解决第一层的**实现**，`llm/` 解决平台侧的**治理**，这套解决**第二层与第三层的判断**。

**一个论断先立在这里**（全篇反复回到它）：

> **同一个功能在不同量级下不是"同一套架构加机器"，而是不同的系统。**
> 10 QPS 的短链和 60 万 QPS 的短链，共享的只有领域模型和 API 契约，**存储形态、缓存形态、一致性模型、部署拓扑全部换掉**。所以"设计"这件事的产物不是架构图，而是**「量级 → 形态」的对照表 + 换挡信号**。

### Part I · 基础（6 篇）

| 编号 | 标题 | 唯一真问题 |
| --- | --- | --- |
| 01 | 约束卡与量级估算 | 所有架构决策的输入是数字，而这些数字必须**能被一个人在白板上推出来** |
| 02 | 领域建模：聚合、不变量与上下文 | 建模的产物不是类图，是**「哪些不变量必须由同一个事务守护」** |
| 03 | 存储与索引的形态决策树 | 选型的失败 90% 不在"选了错的库"，而在**"分片键选错"** |

| 05 | 写路径形态：异步、事件与幂等落点 | 异步不是解耦，是**把「必须一次做成」改成「允许重做」**，代价必须显式买单 |
| 06 | 演进纪律：六次重构与换挡信号 | 每一次重构都不是"因为量大"，而是**某个具体指标越过了具体阈值** |

## 0.4 每篇必须回答的七问

`eng/` 用五问法讲机制，本套用**七问**讲设计——多出的是「形态」与「换挡」两问：

```
① 到底是什么      给出精确定义 + 反例（什么不是最终一致、什么不叫水平扩展）
② 这个量级下唯一真问题是什么
                  一句话。说不出来就说明还没想透，不许动笔
③ 量级与预算       QPS / 存储 / 连接数 / 成本，全部给出推导过程，不许直接给结论
④ 形态怎么选       3~5 种方案对比：原理 / 代价 / 边界 / 更换的信号
⑤ 会在哪崩         这个形态特有的失效点（不是通用的"高可用"套话）
⑥ 换挡信号         什么指标越过什么阈值时，必须换成下一个形态
⑦ 怎么验证         压测怎么打、影子怎么比、什么叫做"证明它对了"
```

**案例篇额外加一节「砍 90% 预算」**：把成本和机器砍到十分之一，还能不能跑？只能保留哪三件事？这一节最能暴露「什么是必需品、什么是架构虚荣」。

## 0.5 双栈分工：不是偏好，是压力特征决定的

| 层 | 语言 / 框架 | 判定依据 |
| --- | --- | --- |
| 跳转解析热路径、连接网关、限流器、布隆/位图 | **Go**（net/http 或 fasthttp、gRPC） | 百万 QPS、单请求亚毫秒预算、GC 停顿不可接受 |
| 领域建模、开放 API、运营后台、Saga 编排、计费多租户 | **Java 21 + Spring Boot / Cloud Gateway / ShardingSphere / MyBatis-Plus** | 长流程、复杂状态机、企业集成生态 |
| 两侧共享 | protobuf 契约、错误码表、领域事件 schema、SLO 定义 | 契约先行，双栈各自生成代码 |

> 关键论断（第 12 篇详细展开）：**短链这类系统天然是两个系统**——一个「查表 + 302」的极简**数据面**，一个「带状态、带审批、带计费」的**控制面**。用一套技术栈硬装两个，是本套反复警告的第一个反模式。

## 0.7 写法公约（子 Agent 与合订本都必须遵守）

1. **锚点式引用**：交叉引用一律写 `→ [12 短链 · §12.6]` 或 `→ eng/14`，**禁写"上一篇/上文"**。合订时锚点才能自动变成章内引用。
2. **重复只写一次**：第二次出现只给结论 + 锚点，合订时锚点展开为摘要框。
3. **编号冻结**：篇号一旦发布不再变。单篇修订不得影响其他篇的引用。
4. **族合订本补两端**：族首加引言（把几篇串成一条决策链，只写"为什么必须按这个顺序读"），族尾加对照收束。
5. **每篇开头 200 字位置说明**：说清"本篇在合订本第几章、上承什么、下启什么"。
6. **代码纪律**：单段 ≤ 40 行，只给骨架；完整 DDL / 契约 / 配置进 `26` 篇附录。
7. **数字纪律**：所有 QPS、容量、成本必须给推导式，禁止"大约""很高"这类无信息表述。

## 0.9 明确不写什么（防膨胀纪律）

- 分布式事务理论证明、共识算法论文推导 → 只在 `eng/8` 给结论

- 「最佳实践」清单 → 只写「在这个约束下为什么是它、代价是什么」
