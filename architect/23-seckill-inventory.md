## 23.1 引子：三个「监控全绿」的故障

### 事故一：Redis 扣了，DB 没扣，超卖 340 件（2026-06-18 20:00）

某电商 618「半价旗舰机」，库存 2,000 件，预约 120 万人，秒杀价 2,499 元（日常 4,999 元）。

| 时间 | 事件 | 数据 |
| --- | --- | --- |
| 20:00:00 | 开抢，Redis Lua 预扣 QPS 冲到峰值，Lua P99 由 0.4 ms 涨到 31 ms | 24 万 QPS |
| 20:00:03 | 落库消费者所在节点的 DB 连接池打满，Kafka 积压开始爬升 | 积压 0 → 18 万条 |
| 20:00:41 | 消费者重试 3 次后把 **1,180 条预扣**投入 DLQ；DLQ 无告警、无面板、无人订阅 | 1,180 条 |
| 20:00:52 | Redis 可用量归零，前端显示"已售罄" | 可用 0 |
| 20:02:10 | 运营看后台：**DB 可用量还是 2,000**（因为 1,180 条没落库），判定"Redis 坏了" | DB = 2,000 |
| 20:02:26 | 在后台点「补货 +1,000」，又手动把 Redis key 重新初始化成 DB 的 3,000 | Redis = DB = 3,000 |
| 20:03–20:09 | 第二波成交 1,340 单（Redis 扣、DB 也扣，DB 确实"有货"） | 累计 2,340 单 |
| 20:20 | 仓储按 2,000 件备货，缺口 340 件无法发货 | **超卖 340** |
| 20:20–23:00 | 逐单电话通知 + 缺货赔付 | 客诉 1,240 通 |

赔付明细（这笔账必须自己会算，评审时一定会被追问）：

```
340 单无法发货
  缺货赔付（订单金额 30%：2,499 × 30% = 750 元/单）   340 × 750   = 25.5 万
  紧急调货 120 件（渠道溢价 420 元/件）               120 × 420   =  5.0 万
  其余 220 单换购引导（券 + 客服 1,240 通 × 18 元）   1,240 × 18  =  2.2 万
  ────────────────────────────────────────────────────────────────────────
  直接损失 ≈ 32.7 万元
```

根因不是"Redis 不可靠"，是三件事叠在一起：**预扣没有落成可恢复的事实（DLQ 静默丢）、运营后台允许"覆盖写"库存、DB 侧根本没做 `available >= 0` 的兜底校验**。三条里修任何一条，340 都不会发生。

### 事故二：一个 key 打满，把集群里别人的活动一起拖死（同日 20:00）

同一个 Redis 集群跑着 37 个活动。手机活动的库存 key 打满单分片 CPU 后，**同分片上另外 6 个活动的库存读写 P99 从 0.6 ms 涨到 480 ms**，其中 3 个活动直接挂在下单接口上。事故一的超卖是"数据错"，事故二是"单 key 的热扩散"——**你以为的热点是"一个活动很热"，实际的热点是"一把 CPU 很热"**。当晚连带损失约 210 万 GMV。

### 事故三：网关没限流，秒杀把全站下单接口打死（2025-11-11 00:00）

未做请求漏斗的活动，按钮点击直连下单服务。下单服务与商品详情共享线程池，2 分钟内线程池 100% 耗尽，**非秒杀商品的普通下单也一起失败**，持续 6 分钟，影响 1.9 万单，损失约 96 万元。教训只有一句：**热点流量必须限制在"它自己能消化的那一层"之内，泄漏出去就是全站事故。**

三起事故分别对应**一致性取舍缺失 × 单 key 物理上限 × 请求漏斗缺位**，正好是本篇 §23.2、§23.3、§23.8 三节。

## 23.2 一句话定位与唯一真问题

**定位**：秒杀是「**库存这个标量的值远小于同时想改它的并发数**」的系统。2,000 件 vs 24 万 QPS —— 数值比 1:120，而这个比例本身就是全部难度。

### 唯一真问题

> **在极致热点下，「绝不超卖」与「绝不宕机」只能二选一。**
> 想绝不超卖，就必须让库存裁决点唯一、串行（一行 DB 或一个单分片），而它的吞吐天花板是几千 TPS；想绝不宕机，就必须让裁决点并行、可缓存（Redis / 桶化 / 令牌），而并行必然带来一致性窗口。
> **架构师的本职不是把两者都说成"可以"，而是把"选哪一个、损失多少钱"算清楚，并把它变成一行能写进 PRD 的决策。**

这条矛盾推出了全部设计：

| 从矛盾推出的约束 | 推出的设计 |
| --- | --- |
| 裁决点必须唯一且快 | Redis Lua 原子脚本做**裁决点**，DB 做**权威源** |
| 裁决点一旦并行就有一致性窗口 | **预扣流水**把窗口内的每一步落成可恢复的事实 |
| 窗口内的偏差方向不可控 | 设计成**只允许"少卖"方向偏差，禁止"超卖"方向偏差** |
| 裁决点吞吐有物理上限 | 请求漏斗 + 排队令牌把 QPS **削到上限的 30%** |
| 库存数值小、热点必然集中 | 售罄即熔断（把"卖完"变成最快的拒绝）+ 候补队列兜少卖 |
| 超卖一定会在某个量级发生 | **四方对账** + 自动回补 + 线下赔付预案 |

对比一下就知道这条矛盾有多特殊：

| 系统 | 冲突双方 | 权衡结果 |
| --- | --- | --- |
| 普通下单 | 一致性 vs 延迟 | 单行事务，1,000 TPS 够用 |
| 秒杀（本篇） | **绝不超卖 vs 绝不宕机** | 必须显式选边 |
| 火车票/座位 | 同一座位不能卖两次 | 选"绝不超卖"，宁可达峰后大面积失败 |
| 优惠券 | 多发一张 = 亏 1 张毛利 | 可选"超卖"，因为超卖成本 < 宕机成本 |
| 短链（[12]） | 标识符永久 vs 目标可变 | 版本化 key，不涉及并发裁决 |

**同类不同解的原因只有一个：超卖一单的代价与宕机一分钟的代价，哪个贵。** §23.10 给出完整的品类对照表。

### 把"二选一"算成钱：三种取舍档位

假设：库存 2,000 件、峰值 24 万 QPS、超卖单件赔付 750 元、宕机 1 分钟的损失按当日 GMV 折算 = 160 万元/分钟。

| 档位 | 做法 | 超卖期望 | 宕机（或用不了）范围 | 期望损失 |
| --- | --- | --- | --- | --- |
| A 绝不超卖 | DB 单行条件更新，一请求一事务 | **0 件** | 单 SKU 上限 ≈ 1,250 TPS，95% 请求 3 s 超时 → 用户视角"系统崩了 3 分钟" | 0 + 体验损失（约 18 万 GMV + 客诉） |
| B 绝不宕机 | Redis 预扣 + 异步落库（本篇主线） | 期望 = 窗口内失败预扣数 × 落库失败率 ≈ 1,180 × 0（有流水兜底）= **0~340 件** | 几乎无（漏斗把 QPS 压到单实例 30%） | 若无流水：340 × 750 ≈ 25.5 万；**有流水 + 对账：≈ 0** |
| C 换个玩法 | 预约制/抽签，把"抢"改成"异步抽" | 0（抽签在 DB 一次事务内定结果） | 无 | 0 技术损失，但**运营策略变了**：从"拼手速"变"拼运气"，参与率通常掉 30–50% |

**这张表的用法不是选一行，而是告诉业务方：「A 档你要接受 3 分钟下不了单，B 档你要接受 0.03% 的超卖概率并配 33 万赔付预算，C 档你要接受玩法改变」。** 说清楚才能签字。本篇交付的是 B 档的完整形态，且把钱花在把 B 档的超卖期望压到 0 附近（预扣流水 + 四方对账），因为这是**唯一一种"技术成本换掉业务风险"的交易**。

### 什么不是本篇的问题（反例）

| 看起来像 | 实际是什么 | 去哪 |
| --- | --- | --- |
| "库存不一致就是分布式事务问题" | 是**裁决点与权威源分离**的窗口问题，用补偿而不是 2PC 解 | `eng/12`、本篇 §23.6 |
| "秒杀要防刷单" | 是风控漏斗问题，与库存裁决正交 | [08 风控与反作弊](08-risk-and-antifraud.md) |
| "库存要放 Redis 提高命中率" | 库存不是读缓存，是**写裁决点**；命中率思维在这里是错的 | [04 读路径形态](04-read-path-and-cache-shape.md) |
| "加 Redis 分片就能扛" | 单 key 只能落一个 slot，**加分片对单 key 无效** | 本篇 §23.3 |

## 23.3 热点到底是什么：单 key 的物理上限

不许拍脑袋。先算清楚"热"到什么程度，再看单实例能扛多少。

### 请求量推导

```
预约人数            120 万
活动库存            2,000 件（即 99.83% 的参与者注定失败）
开抢瞬时集中度      60% 的请求落在 T0 后 3 秒内（来自上一场活动埋点）
无漏斗峰值 QPS      120 万 × 60% ÷ 3 s = 24 万 QPS
用户命中比例        全部落在单个 key：stock:{sku:1001}
有效读写比          1 次预扣 : 0 次查询（查询走本地快照）
```

### 单 Redis 实例能扛多少：实测式数字

环境：16C32G、Redis 7.2、单 key、无 pipeline、同机房 RTT 0.2 ms、`appendfsync everysec`。

| 命令形态 | 单实例 QPS | 边际瓶颈 |
| --- | --- | --- |
| `GET`/`SET`（值 < 100 B） | 92,000 | **单线程事件循环的协议解析**；8 核以上继续加核无效 |
| `INCRBY` | 87,000 | 同上 |
| `EVALSHA`（3 行 Lua，1 次 `DECRBY`） | 56,000 | Lua 解释开销约吃掉 35% |
| `EVALSHA`（判空 + `DECRBY` + `HSET` 预扣标记） | **41,000** | 写两个 key，本篇的实际形态 |
| 上述 + AOF `everysec` | 33,000 | fsync 抖动，P99 出现 8–20 ms 尖刺 |
| `ZADD`/`ZRANGE`（排队序号） | 28,000 | O(logN) |

**带宽先排除**：单请求 ~120 B、响应 ~40 B，24 万 QPS × 160 B ≈ 38 MB/s ≈ 307 Mbps，25 GbE 网卡的 1.2%。**所以秒杀的热点瓶颈从来不是网络，是 Redis 单线程 CPU 和它的 fork 抖动。**

**利用率与延迟的非线性**（这才是"打满就雪崩"的原因）：

| 单实例负载 | P99 延迟 | 现象 |
| --- | --- | --- |
| 30% | 0.4 ms | 健康 |
| 60% | 0.9 ms | 健康 |
| 80% | 3 ms | 开始有尾延迟 |
| 100% | 40 ms | 请求在 socket 缓冲区排队，客户端 500 ms 超时触发重试 |
| **580%**（24 万 / 4.1 万） | **> 300 ms** | 重试使有效 QPS ×1.6 → **自我强化，回不来了** |

### 一个必须记住的物理事实

> **Redis Cluster 的单 key 只能属于一个 slot、一个主节点。给它加 32 个分片、加 200 个节点，单 key 的 QPS 上限一点都不会变。**

这条事实决定了"扩容"在秒杀场景的失效：横向扩容解决的是**很多 key 各热一点**（事故二里的 37 个活动本该被分散），不解决**一个 key 极热**。所以对单 key 只有三条出路：

| 出路 | 手段 | 倍数 | 代价 |
| --- | --- | --- | --- |
| 削请求 | 请求漏斗 + 排队令牌 | **10–50×** | 大部分用户拿不到货/要排队，体验受损 |
| 拆 key | 库存桶化（2,000 拆 20 桶 × 100） | N×（N=桶数） | 桶间不均 → 少卖；跨 slot → 回补逻辑复杂度翻倍 |
| 改语义 | 预约/抽签/分时段放量 | ∞（并发归零） | 玩法改变，运营要重新设计 |

**本篇主线选"削请求"，把桶化留给 L4（见 §23.13），把改语义作为终极出口。** 因为削请求的代价是**可解释的**（用户可以被告知"你没抢到"），桶化的代价是**不可解释的**（库存明明还有 3 件，但你的桶空了）。

### 安全水位公式

```
单实例安全 QPS = min(命令上限 4.1 万 × 0.5, 网卡 PPS × 0.6, 连接数 × 单连接命令率)
               ≈ 2 万 QPS   （留 50% 给突发、主从同步、AOF fork）
令牌发放速率   = 5,000/s → 占安全水位的 25%，2,000 件在 0.4 s 内售罄
```

**这就是为什么"排队令牌"不是体验优化，而是容量工具**：它把打到 Redis 的 QPS 从 24 万降到 5,000，降幅 48 倍，比任何缓存优化都便宜。

## 23.4 领域与边界：库存的不变量属于谁

```
┌─────────────────────────────────────────────────────────────────────┐
│  裁决层 Adjudicator（Redis，Go 侧访问）  「还能不能卖」的唯一答案     │
│  ─ stock:{sku} 可用量   ─ rsv:{sku} 预扣标记   ─ 售罄熔断标志        │
├─────────────────────────────────────────────────────────────────────┤
│  权威层 Authority（MySQL，Java 侧）      「到底卖了多少」的唯一事实   │
│  ─ sku_stock(available, sold)   ─ stock_reservation   ─ seckill_order │
│  ─ payment                                                            │
├─────────────────────────────────────────────────────────────────────┤
│  观测层 Observe（对账 + 大盘）  Redis / DB / 订单 / 支付 四方比对      │
└─────────────────────────────────────────────────────────────────────┘
        裁决层可以重建（从流水），权威层不可重建 → 所以流水必须落权威层
```

**这条依赖方向是硬约束**：权威层 → 裁决层的方向只能"重建/回补"，**不能在请求路径上同步写 DB**，否则 DB 一慢，24 万 QPS 的裁决点立刻变 40 ms。

### 聚合与不变量

| 聚合 | 不变量 | 守护方式 |
| --- | --- | --- |
| `SkuStock` | `available ≥ 0` 且 `available + sold = total`（活动期内） | Redis Lua 原子判断（请求路径）+ DB `CHECK(available >= 0)`（兜底，见 §23.7） |
| `SkuStock` | 每一次扣减必须在权威层留痕 | **预扣流水** `stock_reservation`，PK = `reservation_id` |
| `SeckillOrder` | 同一 user 对同一 sku 最多 1 单 | 唯一键 `uk(activity_id, sku_id, user_id)` |
| `SeckillOrder` | 一个预扣最多生成一个订单 | 唯一键 `uk(reservation_id)` |
| `Payment` | 支付成功 ⇒ 订单存在且库存终态为 `sold` | 支付回调幂等 + 四方对账 |
| `StockRelease` | 一次预扣最多被回补一次 | 回补 CAS（DB）+ 预扣标记 `HDEL` 返回 1 才 `INCRBY`（Redis） |

**最容易写错的是最后一条**：库存在两个地方各有一次"加法"（DB 回补、Redis 回补），任何一次重放都会让库存变多，也就是超卖。所以**回补必须是双幂等的**——不是"设计得体面一点"，而是"同一份库存加两次，就等于超卖两件"。

### 状态机

```
        ┌──────────┐  落库成功   ┌────────────┐   支付成功   ┌────────┐
        │ reserved │ ──────────→ │ db_committed│ ──────────→ │  paid  │
        └────┬─────┘             └──────┬─────┘             └────────┘
   Redis扣成功│                         │ 30 min 未支付
   但落库失败 ↓                         ↓
        ┌────────────┐            ┌───────────┐
        │  orphan    │  定时补偿   │ released  │ → DB 与 Redis 各回补一次（双幂等）
        │(只在D L Q) │ ─────────→ │           │
        └────────────┘            └───────────┘
```

`orphan` 这个状态是事故一的修复点：**集群里有一条"Redis 上发生过、权威层不知道"的路径，它必须有名字、有面板、有补偿任务。**

## 23.5 三种库存形态：一张决定性的对比表

| 维度 | **A · DB 乐观锁** | **B · Redis 预扣 + DB 落库**（本篇） | **C · 队列串行化** |
| --- | --- | --- | --- |
| 形态 | `UPDATE sku_stock SET available=available-1 WHERE sku_id=? AND available>=1` | Redis Lua 原子扣减 → MQ → DB 事务落库 | 请求进单分区队列，消费端串行扣 |
| **吞吐上限** | **~1,250 TPS/单 SKU**（单行持锁 0.8 ms 串行化） | **41,000 QPS/单 key**（受 Lua 单实例），配漏斗后可覆盖 24 万入口 | **2,000–8,000 TPS/单分区**（取决于落库事务耗时 0.12–0.5 ms） |
| **超卖风险** | **零**（DB 条件更新是最终真相） | **存在一致性窗口**（毫秒~秒），但可用流水 + 对账压到 ≈0 | **零**（严格串行，一条一条卖） |
| 少卖风险 | 低 | 中（Redis 丢数据/回补漏 → 售罄提前） | 中（队列延迟 > 活动时长 → 用户放弃） |
| 实现复杂度 | **低**（一个 SQL） | **高**（Lua + 流水 + 消费者 + 补偿 + 四方对账） | 中高（分区顺序、消费幂等、积压背压） |
| 失败模式 | 库存行锁竞争 → 连接池打满 → **全站一起死**（含非秒杀业务） | Redis/DB 不一致（事故一）、DLQ 静默丢、消费者积压 | 积压导致"看得到买不到"，队列本身就是热点单点 |
| 用户感知 | 3 s 超时占 95%，等同宕机 | 0.4 s 卖完，其余走候补/告知售罄 | 排队 5–60 s，放弃率高 |
| 适合量级 | 库存 > 10 万件 且 QPS < 1,000（日常券、普通商品限购） | **1 千~10 万件的活动型秒杀（主流）** | 票务/选座/强一致场景，库存几千以内 |
| 换挡信号 | 冲突重试率 > 30% 或 P99 > 300 ms → 升 B | Redis 单实例 CPU > 60% 或对账差异日增 > 0 → 升 C 的令牌部分或桶化 | 消费延迟 P99 > 15 s → 降级为 B |

**三条判断口诀**：

1. **裁决点必须唯一**：库存的"能不能卖"只能有一个答案来源。A 的答案是 DB 行，B 的答案是 Redis key，C 的答案是队列位置。**任何"两个答案都能回答"的设计都会在并发下打架**。
2. **胜出的是"延迟最低的那个唯一裁决点"**，不是"最准的那个"。B 之所以赢，是因为 Redis 的 0.4 ms 让 24 万 QPS 有地方排队，而 DB 的 0.8 ms 只够 1,250 个。
3. **C 是最强的、也是最脆的**：它把并发问题变成了排队问题，代价是"排队时长必须小于用户耐心"，而这个耐心只有 10 秒（见 §23.9）。

> 落地推荐不是"三选一"，而是 **B 为骨架 + C 的令牌放在 B 前面 + A 的 SQL 作为最后一道墙**。§23.6 给的完整分层就是这个组合。

## 23.6 分层实现：预扣 → 落库 → 回补

### 分层与回补链路

```
                  ┌───────────────────────── 用户复访/补货 ◄──────┐
                  │                                                │
 ① 库存快照        ② Redis 预扣        ③ 预扣流水落库     ④ 订单     ⑤ 支付        ⑥ 超时回补
 (本地只读)        (Lua 原子裁决)       (异步,权威化)      (pending)   (paid)        (双向幂等)
┌──────────┐    ┌──────────────┐   ┌──────────────┐  ┌────────┐  ┌────────┐  ┌──────────────┐
│ snapshot │───→│ stock:{sku}  │──→│ Kafka:rsv    │─→│ order  │─→│ payment│  │ delay 30 min │
│ :{sku}   │    │ DECRBY + HSET│   │ → DB 事务:   │  │ uk     │  │ 回调   │  │ TTL 到期 →   │
│ 命中即返回│    │ rsv:{sku}    │   │ stock -= n   │  │(act,   │  │ 幂等   │  │ CAS cancel   │
│ 售罄/未开始│    │ 返回剩余量    │   │ rsv + order  │  │sku,usr)│  │        │  │ → DB+Redis   │

                       └─ 直接返回失败 ───┘                                          │
                             （绝不 GET+DECR 兜底）        ⑦ 四方对账：R / D / 订单 / 支付
                                                          差异 → 自动回补或冻结活动 ←──┘
```

### 每一步的幂等键与失败恢复

| 步骤 | 幂等键 | 重复时行为 | 失败恢复 |
| --- | --- | --- | --- |
| ② 预扣 | `(activity_id, sku_id, user_id)` 由网关算出 `reservation_id`（HMAC） | Lua 内 `HSET rsv NX` 已存在 → 直接返回同一 `reservation_id`，不再扣 | 客户端重试安全；Redis 丢数据由 ⑦ 重建 |
| ③ 落库 | `reservation_id`（PK） | 唯一键冲突 → 视为已成功，ack 掉 | DLQ 定时重放；`orphan` 扫描补偿 |
| ④ 下单 | `uk(reservation_id)` + `uk(activity,sku,user)` | 冲突 → 返回已有订单号 | 重试安全；订单号由发号器预分配 |
| ⑤ 支付回调 | `pay_no` 唯一键 + 订单状态 CAS | 二次回调返回成功，不加库存 | 支付侧按 T+1 对账补推 |
| ⑥ 回补 | DB：`UPDATE order SET status=cancelled WHERE status=pending`；Redis：`HDEL rsv` 返回 1 才 `INCRBY` | 任一方已处理 → 跳过 | 定时扫 `pending` 且超 35 min 的订单 |

### Java 侧骨架：落到权威层 + 超时释放

```java
@Transactional
public long commit(Reservation rsv) {                       // ③ 落库：一个本地事务
    if (stockMapper.deductIfEnough(rsv.skuId(), rsv.qty()) == 0) {
        throw new SoldOutException();                       // WHERE available >= ? 的最后一道墙
    }
    rsvMapper.insert(rsv);                                  // PK = reservation_id，重放即幂等
    SeckillOrder o = SeckillOrder.pendingOf(rsv);
    orderMapper.insert(o);                                  // uk(activity,sku,user) 兜住限购
    outboxMapper.insert(Outbox.of("order.created", o));     // 发延迟消息走 Outbox（eng/10）
    return o.id();
}

@RabbitListener(queues = "order.release.delay")             // ⑥ 30 分钟后触发
public void onRelease(String orderId) {
    if (orderMapper.casStatus(orderId, PENDING, CANCELLED) == 0) return; // 已支付/已释放 → 幂等退出
    SeckillOrder o = orderMapper.get(orderId);
    stockMapper.release(o.skuId(), o.qty());                // DB 回补（条件：status=cancelled）
    stockClient.release(o.skuId(), o.reservationId(), o.qty()); // Redis 回补，脚本内 HDEL 守卫
}

@RabbitListener(queues = "order.commit.dlq")               // 事故一的修复点：DLQ 必须有人听
public void onDlq(Reservation rsv) {
    if (rsvMapper.exists(rsv.id())) return;                 // 已落库 → 丢弃重复消息
    orphanAlert.raise(rsv);                                 // 打点 + 告警 + 落 orphan 表，等补偿扫描
}
```

**为什么预扣流水是整个架构的承重墙**：Redis 的 AOF `everysec` 在主从切换时可以丢最多 1 秒数据。如果"扣了 Redis"这件事只存在于 Redis 里，那么**主从切换的那一刻，已经卖掉的 3,000 件会凭空回来 → 二次开抢 → 超卖**（这是比事故一更糟的形态，因为用户已经付钱了）。把预扣落成权威层的行，才能做到"Redis 可以丢，账不能丢"。

### 失败恢复的三个场景（必须演练）

| 场景 | 现象 | 恢复动作 | 允许的偏差方向 |
| --- | --- | --- | --- |
| 消费者挂/积压 | Redis 已售罄，DB 还有货，用户下单失败 | 重启消费者 + DLQ 重放；期间**禁止运营"按 DB 补货"**（事故一的操作） | 少卖（可补货） |
| DB 不可用 | 预扣成功但落库全失败 | 预扣返回"排队中"而不是"成功"；DB 恢复后重放 | 少卖 |
| Redis 主从切换丢 1 s | 可用量回升 | **以流水为准重建** `R = total − count(unreleased reservation)`，重建期间活动只读 | 少卖 |

**统一原则：所有恢复动作只允许把库存往"少"的方向修，往"多"的方向修一律要人工二次确认。** 这一条写进 runbook，比任何代码都值钱。

## 23.7 Redis 扣减的正确写法

### 先看错误写法（事故一的前身）

```text
v := GET stock:{sku}          -- t1：读到 1
if v > 0 { DECR stock:{sku} } -- t2：两个请求都通过了判断
                              -- t3：DECR 各减 1 → 可用量变成 -1
```

`GET` 与 `DECR` 之间是**两个 RTT 的窗口**，窗口内所有并发请求都看到同一个旧值。这一条在 24 万 QPS 下等于必炸。同理，`INCRBY -1` 本身也不检查下界，**Redis 里没有"非负"这个概念，只有你写进 Lua 的那行判断**。

### Lua 脚本：把"判断 + 扣减 + 留痕"压成一次原子执行

```lua
-- KEYS[1]=stock:{sku}  KEYS[2]=rsv:{sku}   ARGV[1]=qty  ARGV[2]=reservation_id
if redis.call('HEXISTS', KEYS[2], ARGV[2]) == 1 then return -3 end  -- 幂等：已扣过，返回原结论
local cur = tonumber(redis.call('GET', KEYS[1]))
if cur == nil then return -1 end                    -- 冷 key：回源重建，绝不凭空造库存
if tonumber(ARGV[1]) <= 0 then return -2 end         -- 负数 = 偷偷加库存
if cur < tonumber(ARGV[1]) then return 0 end         -- 售罄
redis.call('DECRBY', KEYS[1], ARGV[1])
redis.call('HSET', KEYS[2], ARGV[2], ARGV[1])
return cur - tonumber(ARGV[1])                       -- 返回剩余量，前端直接显示
```

回补脚本必须与它对称（**只有 `HDEL` 成功的那一方才能加库存**）：

```lua
if redis.call('HDEL', KEYS[2], ARGV[2]) == 0 then return 0 end  -- 别人已经回补过
redis.call('INCRBY', KEYS[1], ARGV[1])
return 1
```

### Go 侧骨架（数据面，含 hash tag 与降级纪律）

```go
// KEYS 必须同 slot：用 hash tag {sku}，否则 Cluster 直接 CROSSSLOT
var deductScript = redis.NewScript(`...上面的 Lua...`)

func (s *StockSvc) Deduct(ctx context.Context, sku, rid string, qty int) (int64, error) {
	keys := []string{"stock:{" + sku + "}", "rsv:{" + sku + "}"}
	left, err := deductScript.Run(ctx, s.rdb, keys, qty, rid).Int64()
	switch {
	case err != nil:
		return 0, fmt.Errorf("lua deduct: %w", err) // 不降级成 GET+DECR，直接失败
	case left == -1:
		if err := s.reloadOnce(ctx, sku); err != nil { // singleflight 回源，只重试一次
			return 0, err
		}
		return s.Deduct(ctx, sku, rid, qty)
	case left == 0:
		s.markSoldOut(ctx, sku) // 售罄熔断：后续请求在本地快照就挡掉
		return 0, ErrSoldOut
	case left == -2:
		return 0, ErrBadQty
	case left == -3:
		return s.lastAnswer(ctx, rid) // 幂等重放：返回同一结论
	}
	s.emitReservation(ctx, sku, rid, qty) // 写本地 ring buffer → Kafka，异步落库
	return left, nil
}
```

### 这段脚本的四个边界（每一条都有人踩过）

| 边界 | 现象 | 处理 |
| --- | --- | --- |
| **集群跨 slot** | `CROSSSLOT Keys in request don't hash to the same slot` | 两个 key 必须用同一个 hash tag `{sku}`；也意味着桶化时 tag 要写 `{sku:1001:b3}` 里的 `sku:1001` 才能同桶 |
| 脚本里取时间/随机数 | 主从复制出现数据漂移（历史上的 `TIME`/`RANDOMKEY` 类事故） | 时间从参数传进来（`ARGV[3]`），脚本内只用确定性命令 |
| 脚本阻塞主线程 | 一个慢脚本卡死整个实例（事故二的同类） | 只用 O(1) 命令；配 `lua-time-limit`；禁止脚本内 `KEYS`/`SMEMBERS` 大集合 |
| 主从切换/across-AZ 延迟 | 扣减结果丢 → 可用量回升 → 二次开抢 | ① 预扣流水兜底（§23.6）；② **偏差只允许"少卖"方向** |

> **这条设计纪律值得单独抄走**：任何在主从/分区切换时**可能让库存变多**的实现都禁止上线；可能让库存变少的实现可以上线，但必须配售罄告警和补货弹窗。**这就是"宁可少卖"在代码级的样子。**

### 每层的拦截比例、实现与失效后果

| 层 | 进入 | 通过 | 拦截率 | 实现要点 | 这层失效的后果 |
| --- | --- | --- | --- | --- | --- |
| ① CDN | 120 万 PV | 边缘命中 96% | 96% | 静态化 + 短 TTL + 预热；库存**不放**静态页 | 回源 120 万 → 源站先死 |
| ② 前端 | 78 万点击 | 24 万 | 69% | 服务端下发的"开抢时间戳"做倒计时；按钮在拿到 429 后延长置灰 | 无效请求 3 倍，全靠后端扛 |
| ③ 网关限流 | 24 万 QPS | 5 万 | 79% | 令牌桶按活动维度；限流值 = 单实例安全线 × 实例数（[eng/15] 的公式） | Redis 5.8 倍过载 → 全站抖动（事故二） |
| ④ 人机校验 | 5 万 QPS | 1.2 万 | 76% | 答题前置（先答后抢）、题库随机、2 秒摩擦；名单与设备指纹引 [08] | 脚本 1 人 1 万请求 → 库存被机器吃掉 |
| ⑤ 排队令牌 | 1.2 万 QPS | 5,000 | 58% | 匀速发放器 + 令牌签名 + 30 s TTL | 无令牌 → Redis 直面 1.2 万 QPS（仍超安全线） |
| ⑥ 预扣 | 5,000 QPS | 2,000 单 | 库存决定 | Lua 原子 + 售罄熔断 + 候补登记 | 超卖或宕机 |

**漏斗的价值不是"提高成功率"，而是把"注定失败的请求"挡在产生任何持久化副作用之前。** 24 万 QPS 里 99.17% 注定失败，如果这 99.17% 都进了 Redis / DB / 支付通道，系统卖 2,000 件货要为 24 万次请求付钱。**这是秒杀架构里最容易算、也最容易被忽略的一笔账。**

### 每一层的成本对照（为什么漏斗要在最外层做）

| 层 | 单次请求成本 | 24 万 QPS 下的月成本量级 |
| --- | --- | --- |
| 边缘（CDN） | ~0.0002 分 | 千元级 |
| 网关限流（本地令牌桶） | ~0.0005 分 | 千元级 |
| 人机校验（第三方） | ~0.02 分 | 十万元级 |
| Redis 预扣 | ~0.03 分（含实例+运维） | 百万元级 |
| DB 落库 + 支付通道 | ~0.3 分 | 千万元级 |

**成本差 3 个数量级，所以漏斗必须"从外往里、从便宜往贵"逐级收窄。** 反过来（先到 DB 再拦）是事故三的直接原因。

## 23.9 排队系统：令牌、通知与放弃率

### 排队与通知链路

```
   拿不到令牌的用户（约 19 万）                     拿到令牌的用户（5,000/s）
        │                                                    │
        ↓                                                    ↓
 ┌──────────────┐   ① 登记排队序号（Redis ZSET，score=入队时间）
 │ 排队页(静态) │──→ 返回 {position, eta, token_poll_key}
 └──────────────┘
        │
        ├─② 主通道：WebSocket 长连推送（"轮到你 / 已售罄"）── 连接数 20 万
        │      引 [14 海量 WebSocket 连接维护]，路由表 + 心跳
        │
        ├─③ 降级通道：分级轮询（第 1 分钟 2 s 一次，之后 10 s 一次）
        │      结果按 {activity, seq/100} 聚合缓存 500 ms → 边缘命中 95%
        │
        └─④ 终结事件（必须给确定性，不许无限等）
               ├─ 拿到令牌 → 30 s 内必须下单成功，否则令牌作废、库存回补
               ├─ 售罄     → 「已售罄，登记候补」按钮（§23.10）
               └─ 活动结束 → 「下次开抢时间」
```

### 令牌发放器：按 QPS 匀速

```
发放速率 = min(Redis 单实例安全线 × 0.25, 库存 ÷ 目标售卖时长)
        = min(20,000 × 0.25, 2,000 ÷ 0.4 s) = min(5,000, 5,000) = 5,000/s
实现：时间片配额  slot = floor(now_ms / 100)  → 每 100 ms 一个槽，每槽 500 个
      槽号与余量存 Redis（INCR + EXPIRE 2s），发放器本身无状态可横向扩
令牌 = base64(activity_id, seq, exp, HMAC(server_secret))
```

**注意令牌必须"少发不可多发"**：多发一个令牌不超卖（Redis 还有库存判断），但会让 Redis 多承受一次无意义的写并加剧排队拥堵；而少发就直接变成少卖。**所以发放器故障时的默认动作是"停发 + 排队页告知"，不是"全放行"。** 这与 [eng/17] 的结论一致：限流器/发放器自己也是服务，必须预先写死"故障时放行还是固定阈值"。

### 轮询 vs 长连：算清成本再选

| 方式 | 20 万等候者的成本 | 感知延迟 | 结论 |
| --- | --- | --- | --- |
| 1 s 轮询 | 20 万 QPS 打到排队接口 → **本身就是一个新的秒杀热点** | 中位数 0.5 s | ❌ 不可直接做 |
| 10 s 轮询 | 2 万 QPS，加边缘缓存 500 ms → 回源 2,000 QPS | 中位数 5 s | ✅ 可作降级 |
| 长连推送 | 20 万 WebSocket（单机 5 万连接 × 4 台） | < 200 ms | ✅ 主通道，成本是连接维护 |
| 长连 + 轮询兜底 | 长连覆盖 90%，其余轮询 | 好 | ✅ **推荐** |

**排队页是"二次热点"**：它承接的 QPS 比秒杀本身还高（19 万 vs 24 万），如果它自己需要查 Redis，就是把刚限流掉的流量又放回来。所以排队页必须是"静态页 + 边缘缓存 + 长连"的组合，**排队长度的读取绝不能每请求一次回源**。

### 排队超时与放弃率

| 等待时长 | 实测放弃率 | 该做什么 |
| --- | --- | --- |
| < 3 s | 12% | 正常排队 |
| 3–10 s | 31% | 显示"第 N 位 / 预计 X 秒"，给确定性 |
| 10–30 s | 58% | 已不可接受：应改为"售罄告知 + 候补"，停止虚假希望 |
| > 30 s | 81% | 排队系统已成负资产 |

> **排队窗口的硬上限是 10 秒。** 推导：库存 2,000 件、发放 5,000/s → 只需 0.4 s 售罄；即便库存 5 万件，10 秒也就卖完了。**任何需要用户排 30 秒的秒杀，本质是库存或令牌速率算错了。**

**排队系统最危险的实现是"同步阻塞式排队"**：在网关里 `sleep 200ms` 后重试库存。24 万 QPS × 0.2 s = 48,000 个并发线程 —— 这比不限流更糟，它把"排队"变成了"线程池耗尽"（事故三的机制）。

## 23.10 超卖与少卖：两个方向都必须买单

### 先定方向：按品类算

| 品类 | 超卖 1 单的代价 | 少卖 1 单的代价 | 结论 |
| --- | --- | --- | --- |
| 实物限量（手机/球鞋） | 750 元赔付 + 客诉 + 舆情 | 少赚毛利 2,500 元（可转下一场） | **宁可少卖** |
| 虚拟权益（券/会员） | 多发 1 张，成本 = 面额 × 核销率（约 15 元） | 少发 1 张，用户不满 | 可超卖（赔付 < 技术成本） |
| 票务/选座 | **同一座位卖两次 = 合同违约** | 空座 | **绝对不超卖**（选形态 C） |
| 稀缺资格（预约码/资格券） | 超发可事后按订单号截断 | 少发损失小 | 可轻微超发（把截断做在核验端） |

**判断公式（评审时直接算）**：

```
选"绝不超卖"的条件：  超卖单件代价 × 期望超卖件数  >  宕机 1 分钟的损失 × 宕机分钟数
本例：750 × 340 = 25.5 万   vs   160 万 × 3 = 480 万
     → 25.5 万 << 480 万，所以纸面上应选"绝不宕机"（B 档）
     → 但我们仍然要把期望超卖件数从 340 压到 0，因为 B 档做到 0 的成本只有一套流水 + 对账
```

**这张算式的意义在于：它不是让你选"容忍超卖"，而是让你把"容忍额度"变成一个被监控的数字。** 定了额度，才有"超卖 340 件 vs 超卖 3 件"的差别；没定额度，340 和 3 都只是"出事了"。

### 少卖的补救：三条路，按用户感知排序

| 补救 | 机制 | 效果（实测） | 幂等/公平要求 |
| --- | --- | --- | --- |
| **候补队列** | 售罄后按钮变"登记候补"，唯一键 `(activity, sku, user)`，补货/超时回补的库存按登记时间 FIFO 发令牌 | 补货转化率是"下次再来"的 3–5 倍 | 一人一名额；发令牌时 CAS 标记 `notified` |
| 补货弹窗 | 运营补货后，对"点击过抢购但未成功"的用户定向推送（30 分钟窗口） | 召回 8–15% | 按 `(activity, sku, user)` 去重推送 |
| 二次开抢 | 对账发现残差 > 0（有未售出的碎库存）→ 立即开第二场 | 回收 0.1–2% 的库存 | 场次独立库存 key，避免与首场串账 |

**候补队列是"少卖"这个决策唯一体面的收尾**：既然你选了宁可少卖，就必须给"没买到的人"一个确定的位置，否则少卖在用户眼里等同于"系统坏了"。这也是 §23.2 档位表里"体验损失"那一栏的具体填法。

### 已经超卖了怎么办（止血顺序不能错）

```
1. 止血（1 分钟内）   停发令牌 → 冻结活动库存 key（标记 frozen，Lua 直接返回售罄）
                      → 关闭「运营补货/覆盖写」入口（事故一的直接触发器）
2. 定损（10 分钟内）   跑 §23.11 四方对账，算出真实缺口 = 支付数 − 总量
3. 分流（当天）       缺口 ≤ 5%：紧急调货 + 30% 赔付券（保住履约口碑）
                      缺口 > 5%：统一赔付 + 优先购买权 + 主动公告（别等客诉）
4. 回写（当天）       把本次缺口与赔付金额写进活动复盘，作为下一场"档位选择"的输入
```

**第 1 步里"关闭运营覆盖写"比任何技术手段都重要**：事故一里 340 件超卖，直接触发动作是运营点了「补货 +1,000」。**任何允许人工"设置库存绝对值"的后台按钮，在秒杀场景里都必须是"增量 + 审批 + 二次确认"，并且要禁止在活动进行中修改。**

## 23.11 库存对账：四者对齐

### 四个数字与它们的关系

```
R = Redis 可用量        D = DB 可用量
P = 未回补的预扣数      O = 已落库订单数（不含取消）      Pay = 支付成功数
T = 活动总量            （全部按 (activity_id, sku_id) 维度统计）

恒等式（正常态）：
   R = T − P − 已裁决未落库的预扣（窗口内，应 < 阈值）
   D = T − O
   O = P            （预扣都落库了）
   Pay ≤ O ≤ T      （超卖 ⟺ O > T 或 Pay > T）
```

### 六种差异形态与处置

| 差异 | 含义 | 危险度 | 处置 |
| --- | --- | --- | --- |
| `R < D` | Redis 少（**少卖方向**，安全） | 低 | 按 `R = T − P` 重建 Redis；查是否回补漏执行 |
| `R > D` | Redis 多（**超卖方向，危险**） | **高** | 立即冻结活动 → 切 DB 直扣（降级到 A 档）→ 人工核定 |
| `P` 中超过 60 s 未落库 > 50 条 | 消费者异常/DLQ 堆积 | 高 | 告警 + 重放；期间禁止运营补货 |
| `O − Pay` 大且不收敛 | 支付回调丢失或用户大面积放弃 | 中 | 主动查支付网关订单；30 min 后走超时回补 |
| `Pay > T` | **真超卖** | 极高 | 走 §23.10 止血流程；同时核对是否"回补重复"导致 |
| `R = 0` 但 `D > 0` 持续 10 min | 售罄但权威层有货 → 少卖 | 中 | 差值为"未回补预扣"，核对后自动回补 |

### 自动回补的两条扫描（必须幂等）

| 扫描 | 条件 | 动作 | 幂等保证 |
| --- | --- | --- | --- |
| 孤儿预扣补偿 | `stock_reservation.status=reserved` 且 `created_at < now-90s` 且 DB 无订单 | 补写订单或标记 `released` 并双向回补 | `reservation_id` 唯一键 + 状态 CAS |
| 超时订单释放 | `order.status=pending` 且 `created_at < now-30min` | CAS 改 `cancelled` → DB 回补 → Redis 回补（`HDEL` 守卫） | 状态 CAS 让只有一方成功 |

**对账锚点必须在建模阶段埋，不能事后补**（与 [22] 共享结论，实现细节见 `eng/14`）：`reservation_id` 要一路带进 Redis、DB、Kafka 消息、订单号、支付回调、对账文件。**等出账差再回头补字段，历史数据补不回来，只能认损**（事故一的 1,180 条就是没有 `reservation_id` 落库，只能靠人工翻 Kafka 消息）。

## 23.12 相邻的三个问题（只给结论 + 锚点）

### 1. 同一用户限购 1 件的幂等

**唯一正确解：唯一键，不是"先查再插"。**

```sql
ALTER TABLE seckill_order ADD UNIQUE KEY uk_user (activity_id, sku_id, user_id);
```

| 做法 | 是否保证 | 说明 |
| --- | --- | --- |
| `SETNX user:limit:{aid}:{uid}` in Redis | ❌ 只是"减少无效请求" | Redis 可能被清、可能丢、可能主从切换回滚 |
| `SELECT` 后 `INSERT` | ❌ | 并发下两个请求都查到 0 行（经典的 write skew） |
| **DB 唯一索引** | ✅ **最终防线** | 冲突 → 转成"你已抢到"提示，用户视角是一次成功的幂等重放 |
| 预扣前 `SETNX` + DB 唯一索引 | ✅ 推荐 | 前者省 Redis 扣减成本（24 万 → 少量），后者保正确性 |

> **判断标准一句话**：一个"限购"如果只靠 Redis 实现，那么它的强度等于"Redis 不丢数据"，而 Redis 不保证这件事。

### 2. 恶意刷单与脚本抢购

只给结论（完整漏斗在 [08 风控与反作弊](08-risk-and-antifraud.md) §08.4）：**秒杀场景的攻击不是"支付刷单"，而是"抢资格"**——脚本以 1 人 10 万 QPS 的速度抢走库存，把真实用户挤出去。五层防御的定位是：

```
设备指纹（同设备多账号）→ 频率（IP/UID/指纹三维滑动窗口）→ 答题（成本最低的强摩擦）
→ 名单（黑/灰/白，秒级生效）→ 事后（订单图谱 + 收货地址聚类，命中则取消）
```

关键点：**答题必须前置在库存扣减之前**（§23.8 第④层），放在之后等于库存已被脚本吃掉；**名单同步必须是秒级**，否则名单延迟就等于攻击窗口。

### 3. 缓存击穿：开抢瞬间的"第二次热点"

只给结论（失效语义全谱在 [04 读路径形态](04-read-path-and-cache-shape.md)）：活动页、商品详情、库存快照的 TTL 如果都在 T0 前后到期，24 万 QPS 会在第一秒同时回源。三条措施缺一不可：

| 措施 | 做法 |
| --- | --- |
| 预热 | T0 前 10 分钟主动加载到 Redis + 各实例本地快照，**TTL 设为"活动结束 + 1 h"** |
| 打散 | 同类 key 的 TTL 加 `±120 s` 抖动，避免同一秒集体过期 |
| 逻辑过期 | 值里带 `expireAt`，过期后**异步刷新、旧值继续服务**，绝不阻塞请求 |

## 23.13 L0 → L5：库存 100 件到 100 万件

| 阶段 | 库存 | 峰值 QPS | 形态 | **换挡信号（硬阈值）** | 代价 |
| --- | --- | --- | --- | --- | --- |
| L0 | 100 件 | 1,000 | 单机 + DB 乐观锁（`WHERE available>=?`） | 库存行更新冲突率 > 10% / P99 > 100 ms | — |
| L1 | 1,000 件 | 1 万 | DB 乐观锁 + 网关限流 + 前端置灰 | 冲突重试率 > 30% / 连接池等待 > 50 ms | 部分用户被限流 |
| L2 | 1 万件 | 5 万 | **Redis Lua 预扣 + 同步落库**（一阶段，无 MQ） | 同步落库使 Lua→返回 P99 > 200 ms / Redis CPU > 50% | 引入毫秒级不一致窗口 |
| L3 | 10 万件 | **24 万** | Redis 预扣 + **异步落库** + 令牌排队 + 四方对账（本篇主线） | 单 key CPU > 60% / 落库延迟 > 5 s / 对账日差异 > 0 | 补偿与对账成为日常工作 |
| L4 | 100 万件 | 100 万 | + **库存桶化**（N=20~100 桶）+ 活动级单元化 + 边缘令牌 | 单 key 无法再降；跨桶不均衡导致少卖 > 1% | 桶间不均 → 少卖；回补与对账复杂度 ×N |
| L5 | 千万件 / 跨地域 | 千万 | **改语义**：预约制 + 抽签 + 分时段放量 | "抢"这个语义本身成为瓶颈（任何加机器都不降并发） | 玩法改变；运营与用户都要重新教育 |

**重点说 L3 → L4 的临界点。** L3 之后你会本能地想"再加 Redis 分片"，但 §23.3 已经证明**单 key 加不了分片**，所以你只剩两条路：桶化（把 1 个 key 拆成 20 个 key，单 key QPS ÷20）与改语义。桶化看起来很美，代价是：

- 桶间不均 → 有人抢的是空桶 → **少卖**（必须做"死桶回收"：每 500 ms 扫一次各桶余量，把余量 < 5% 的桶合并）
- 跨桶的"剩余总量"查询变成 N 次 GET（MGET 或聚合缓存），前端的"仅剩 N 件"开始有延迟
- 回补要回补到"原来那个桶"，`reservation_id` 必须记 `bucket_id`，否则回补错桶 → 有的桶多、有的桶空

**所以桶化不是"性能优化"，是"用少卖换吞吐"的又一次显式交易** —— 在做之前，先把 §23.2 的那张表重新填一遍。

> **不要跳级**：没有预扣流水就直接上桶化，等于把"一个 key 的不一致"放大成"20 个 key 各自不一致"，对账根本算不出来。

## 23.14 这个形态特有的崩法

不是"高可用"套话，是秒杀这个形态自己的失效点：

| 失效 | 长什么样 | 定位方法 | 预防 |
| --- | --- | --- | --- |
| **Redis 扣了 DB 没扣** | 支付回调全过，发货时发现没货（事故一） | 四方对账 `R < D` 且 `P` 有积压 | 预扣流水 + DLQ 面板 + 禁止运营覆盖写 |
| **主从切换丢预扣** | 售罄后又变有货，二次开抢 | 对比 `D` 与 `R`，查切换时间点 | 以流水重建；偏差只许"少卖"方向 |
| **单 key 打满拖垮同分片** | 别的活动的库存读也变 480 ms（事故二） | 按 key 聚合慢日志 + 分片 CPU 分维度看 | 令牌把单 key 压到安全线 30% 以下；活动分片隔离 |
| **消费者积压 → "看得到买不到"** | Redis 售罄、DB 有货、用户被拒 | 落库延迟 P99 > 5 s、DLQ 条数 > 0 | 消费端批量 + 背压 + 售罄熔断 |
| **排队页成为第二热点** | 排队接口 QPS 反超秒杀 | 排队接口 QPS / 边缘命中率 | 静态页 + 结果聚合缓存 + 长连推送 |
| **回补重复** | 库存越卖越多，`R` 单调上升 | `sum(released) > sum(pending)` | `HDEL` 守卫 + 状态 CAS 双幂等 |
| **限购失效** | 同用户多单 | 唯一键冲突计数 | DB 唯一索引兜底（§23.12） |
| **活动结束后回补串场** | 下一场开抢时库存凭空多出 | 每日总量校验 | 库存 key 带 `activity_id`；结束即冻结 |
| **令牌发放器故障** | 要么全放行（打穿 Redis），要么全停发（少卖） | 发放速率与排队长度背离 | 事故前写死"停发 + 告知"，绝不全放行（[eng/17]） |

## 23.15 砍掉 90% 预算还能不能跑

机器从 200 台砍到 20 台、Redis 从 12 节点砍到 2 节点主从、Kafka 停用、对账平台停用：

| 保留 | 砍掉 | 后果 |
| --- | --- | --- |
| **Redis Lua 原子预扣**（含 hash tag 同 slot） | 库存桶化、单元化 | 单活动上限 5,000 QPS；库存 > 5 万件的活动做不了 |
| **预扣流水（可重建）** — 改为直写 DB + 本地重试表 | Kafka、独立消费者 | 落库延迟从 5 ms 变 80 ms，Redis→返回 P99 上升，但账还是能对上 |
| **限流漏斗（网关令牌桶 + 前端置灰）** | 人机校验（第三方）、长连推送、候补队列 | 脚本抢购比例上升；排队页退化为 10 s 轮询 |
| 四方对账退化为"每日单表核对脚本" | 自动回补平台、实时差异面板 | 差异从"分钟级发现"变"次日发现"，超卖赔付窗口变长 |

**结论：这套系统的必需品只有三样——Lua 原子裁决（含同 slot 约束）、预扣流水（可重建）、把 QPS 压到安全线以下的漏斗。** 其余（桶化、单元化、自动对账、候补、长连）全是量级或体验驱动的优化。这个结论在评审时最有用：**它能把"我们也要上单元化"这类提案里的架构虚荣砍掉一半。**

## 23.16 十分钟答题卡

被要求现场设计秒杀时，按这个顺序讲，不要从"我用 Redis"开始：

```
1  量级    120 万预约 → 24 万 QPS 落单 key；库存 2,000；留存率 0.83%
2  真问题  「绝不超卖」与「绝不宕机」只能二选一 → 先把档位与赔付算出来
3  物理上限 单实例 Lua 4.1 万 QPS，单 key 不可分片 → 加机器无效
4  形态    B 档骨架：Redis 预扣 → 异步落库 → 超时回补；A 的 SQL 做最后一道墙
5  原子性  一条 Lua（判空+幂等+扣减+留痕），hash tag 同 slot，禁 GET+DECR
6  承重墙  预扣流水：Redis 可以丢，账不能丢；偏差只许"少卖"方向
7  漏斗    CDN 96% → 前端 69% → 网关 79% → 答题 76% → 令牌 58% → 库存裁决
8  排队    令牌 5,000/s；长连为主轮询为备；排队窗口硬上限 10 s；禁同步阻塞
9  对账    R/D/订单/支付 四方，6 种差异，两种扫描，全部双幂等
10 换挡    L3 单 key CPU>60% / 落库>5s；L4 桶化（用少卖换吞吐）；L5 改语义
11 必需    原子裁决 + 预扣流水 + 漏斗 —— 其余都是量级与体验驱动
```

**被追问时的三句标准答案**：

- 「为什么不直接在 DB 上扣？」→「单行 UPDATE 的绝对上限是 1/0.8 ms ≈ 1,250 TPS，24 万 QPS 下 95% 请求超时，用户看到的是宕机。这不是性能问题，是算术。」
- 「Redis 挂了会不会超卖？」→「不会超卖，只会少卖。因为预扣流水在 DB，Redis 丢了就按流水重建，重建期间活动只读。」
- 「怎么保证不超卖？」→「不能保证，只能把期望压到 0：一条 Lua 保证裁决点唯一，一份流水保证可恢复，一套对账保证异常 5 分钟内可见，一个赔付预算保证即使发生也不失控。」
