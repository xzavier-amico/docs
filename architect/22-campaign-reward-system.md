## 22.1 引子：11 分钟，5 万张券清零，1370 张重复发放

**事故：「秋季家装节」券池 11 分钟被同一批设备刷空，且重试把券发了两遍（2025-10-15）**

券池 5 万张、面值 ¥50（预算 ¥250 万），另有现金红包池 ¥200 万。领取规则只有一条：**同一手机号限领一张**。上线时的「幂等」实现是「券码唯一索引」——券码由服务端生成。

| 时间 | 事件 | 数据 |
| --- | --- | --- |
| 10:00:00 | 活动开抢，页面秒进 | 预扣 QPS 峰值 21 万 |
| 10:11:12 | 券池清零，全程 671 秒 | 5 万张 / 700 秒 ≈ 74 张/秒 |
| 10:13 | 客服涌入「领不到券」 | 1,420 起 |
| 10:20 | 发奖接口 P99 从 80 ms 涨到 4.2 s，超时率 6.8%，网关自动重试 ×3 | — |
| 10:26 | 重复发放告警：同一 `(activity, user)` 存在多条成功 claim | **1,370 张** |
| 10:40 | 风控看板：领券设备数 ≪ 领券账号数 | 620 台设备 : 4.83 万账号 |
| 11:30 | 按设备指纹冻结未核销券 | 追回 1.10 万张 / ¥55 万 |
| 10-16 | 重复发放的 1,370 张中已核销 928 张 | 直接损失 ¥4.64 万 |
| 10-16 ~ 10-22 | 日终预算对账：账面「已发」与财务实付差 **¥18.7 万**，且**无法逐笔定位** | 只能整体认损 |

**金额核算**

| 项 | 金额 / 数量 | 说明 |
| --- | --- | --- |
| 券池预算 | ¥250 万（5 万 × ¥50） | 立项上限 |
| 羊毛党领走 | 4.83 万张 / ¥241.5 万 | 占券量 **96.6%** |
| 11:30 冻结追回 | 1.10 万张 / ¥55 万 | 未核销，可作废 |
| 实际流失（已核销/已转卖） | 3.61 万张 / ¥180.5 万 | 二级市场 8 折出清 |
| 重复发放 | 1,370 张，**重复发放率 = 1,370 / 50,000 = 2.74%** | 其中 928 张已核销 |
| 对账无法定位的差异 | ¥18.7 万 | 缺 `channel_txn_id`，历史补不回来 |
| 真实新客获得 | 1,240 人 | **有效获客率 2.5%** |
| **合计损失** | **≈ ¥203.8 万** | ROI ≈ -0.81 |

**三个根因，正好对应本篇三节：**

1. **幂等键选在了「发放产物」上**（券码），而券码每次重试都重新生成 → 唯一索引形同虚设，2.74% 的重复发放全部合法穿过（→ §22.6）。
2. **预扣成功但发奖超时，没有回补也没有 pending 状态**，超时重试又走一遍完整链路 → 库存与发放两条账各走各的（→ §22.7 / §22.8）。
3. **claim 表没有存外部渠道流水号**，五层口径之间没有共同的锚点 → 18.7 万差异在建模阶段就注定无法定位（→ §22.11）。

**注意：这三个根因里没有一个在「发钱」上。** 发钱是 12 行代码调一个 HTTP 接口；出事的是围绕它的键设计、状态与锚点。

## 22.2 一句话定位与唯一真问题

**定位**：奖励系统是**「把一笔预算，按一组可解释的规则，在确定的时刻，发给确定的人，并且事后能逐笔证明」**的运营基础设施。它同时是三样东西：一个库存系统（券有量）、一个账务系统（钱要平）、一个风控系统（人不该错）。

### 唯一真问题

> **发钱是最简单的一步，幂等、防刷、对账才是本体。**
> 一次领奖请求有 **9 个时序分支**（下表），其中 8 个与「发钱」无关；而**每一个分支出错，表现都是「钱多了或少了」，且全部不能靠「再写一个 if」修好**。

| # | 分支 | 量级（单场 1,000 万参与） | 谁负责防它 | 没防住的后果 |
| --- | --- | --- | --- | --- |
| 1 | 正常成功 | ≈ 96% | 发奖逻辑 | — |
| 2 | 用户连点 / 脚本重复提交 | ≈ 3% | 业务唯一键 | 重复发放 |
| 3 | 网关 / RPC 自动重试 | 0.8% | 幂等键 + 结果回放 | 重复发放（事故 = 1,370 张） |
| 4 | 发奖超时、结果未知 | 0.1% | UNKNOWN 状态 + 查状态（不重发） | 重复发放 + 少发同时发生 |
| 5 | 渠道明确失败（券池空/限购/余额不足） | 0.5% | 回补 + 降级奖品 | 库存泄漏（预扣不释放） |
| 6 | 渠道成功但回调丢 | 0.05% | 对账 + 主动查询 | 我们不知道发了，用户说没收到 |
| 7 | worker 在两次写之间挂掉 | 0.01% | pending TTL + 扫描释放 | 僵尸预扣，券池假性售罄 |
| 8 | 活动中途被叫停 | 极少 | 三种「停止」语义 | 半成品数据（停在非法状态） |
| 9 | 回补重复执行 | 常见 | DB 状态机裁决 | 一张券回补两次 = 超发 |

> **智力上真正难的只有一件事**：这 9 个分支的**任意组合**都可能同时发生（重试 + 超时 + 活动叫停 + 回补重复）。所以设计不能按「正常路径 + 几个异常」来做，必须按**状态机 + 幂等键 + 对账锚点**这三个不变量来做。

### 从这条矛盾推出的全部设计

| 从矛盾推出的约束 | 推出的形态 |
| --- | --- |
| 幂等键必须与「业务意图」同生命，不能与「发放产物」同生命 | 键 = `(activity_id, user_id, round)`；**绝不是券码**（§22.6） |
| 重复一定发生（重试 / MQ / 回调 / 人工补发） | 唯一索引裁决 + 状态机前置 + 回补幂等，三件套缺一不可 |
| 库存必须比钱先扣，否则一定超发 | **Redis 预扣先于发奖**，DB 落账后于预扣（§22.7） |
| 预扣与发放之间必然存在窗口（秒级） | **`pending` 是一等公民**：有 TTL、有扫描、有指标、有告警（§22.8） |
| 一定出现「不知道发没发」 | `UNKNOWN` 状态 + **查状态而不是重发** + 对账兜底（§22.9） |
| 账差一定出现，且**历史不可重建** | 建模期就把 `claim_id` / `channel_txn_id` 埋成五层口径的共同锚点（§22.11） |
| 作弊的边际成本低于防御的边际成本 | 用**主体聚合上限**（产品定价）兜底，不是靠规则堆叠（§22.10） |
| 钱不可逆，券可逆 | 超发/少发的取舍按「可追回性」分裂（§22.7 判定表） |

与 [12 短链 · §12.2](12-shortlink-system-design.md) 同构：短链的矛盾是「标识符永久、目标可变」，本篇的矛盾是「**钱必须只发一次、但系统只能保证至少一次**」。两者的解法也同构——**把不可逆的那一面做成唯一索引与状态机，把可变的那一面做成可重放的流程**。

## 22.3 量级与预算：全部推导一遍

### 请求量

```
活动参与            1,000 万人（MAU 8,000 万 × 活动触达 12.5%）
人均动作            3 次（进活动页 / 点领奖 / 刷新余量）
总请求              1,000 万 × 3 = 3,000 万次
开抢集中度          80% 落在开抢 60 s 内 → 2,400 万 / 60 s ≈ 40 万 QPS
瞬时峰值（前 10 s） 40 万 × 0.5 = 20 万 QPS          ← 本篇所有容量按这个数算
过前置闸门的比例    35%（其余是重复点击、无资格、余量刷新）
预扣写入            20 万 × 35% = 7 万 QPS；券池 5 万张 ⇒ 有效预扣 ≤ 5 万次
余量读              20 万 × 60% = 12 万 QPS（本地缓存 + Redis 单 key 读）
发奖渠道            5 万 / 60 s ≈ 833 TPS，峰值 2,000 TPS（渠道限流 5,000 TPS）
```

> **1,000 万参与 vs 5 万张券是 200:1**。这个比例决定了整篇的重心：**99.5% 的请求注定领不到**，所以「快速、体面、可解释地失败」和「成功发放」同等重要——事故一里 1,420 起「领不到券」投诉，有一半是系统在券已售罄后仍在让请求走完整个链路造成的。

### 存储量

```
claim 单体              ≈ 420 B（17 字段 + 2 个二级索引开销）
单场 claim              1,000 万 × 420 B ≈ 4.2 GB
90 天 30 场             126 GB → 按 activity_id 分表（一场一表，活动结束即转冷）
stock_ledger 流水       1,500 万条（含回补）× 180 B ≈ 2.7 GB / 场
幂等/去重表             单场 1,000 万 insert，集中 10 分钟 → 均值 1.6 万 TPS、峰值 8 万 TPS
单机 MySQL 写入能力     5,000 ~ 15,000 TPS（→ eng/1 · §1.13 争议二）
                        ⇒ 8 万 TPS 必须分 8 表（按 claim_id hash）或先由 Redis 挡掉重复
对账流水                日 1,000 万 × 90 天 = 9 亿行 → ClickHouse（→ eng/14 · §14.4.7）
```

### 预算账（不只是钱，这是对账的分母）

| 奖品 | 数量 | 单价 / 面值 | 预算 | 可超发 | 可作废 |
| --- | --- | --- | --- | --- | --- |
| 满减券 | 5 万张 | ¥50 | ¥250 万 | ✅ ≤ 1% | ✅ 未核销可作废 |
| 现金红包 | 2 万份 | ¥100 | ¥200 万 | ❌ 0 | ❌ 不可逆 |
| 积分 | 1,000 万 | 50 分（成本 ¥0.005） | ¥5 万 | ✅ ≤ 2% | ✅ 可扣回 |
| 实物礼品 | 2,000 份 | ¥80（含运费 ¥12） | ¥18.4 万 | ❌ 0 | ❌ 已发货不可逆 |
| **合计** | — | — | **¥473.4 万 / 场** | — | — |

> 风控预算上限用 [08 风控与反作弊 · §08.3](08-risk-and-antifraud.md) 的判据：**风控月成本 ≤ 它拦住的损失的 1/5**。本场羊毛损失上限按 ¥120 万估，则风控年成本预算 ≈ ¥288 万——这个数字决定了 §22.10 里「主体上限」这类零成本手段必须优先于「图关系 + 模型」。

### 延迟预算（领奖同步链路）

| 环节 | P99 预算 | 说明 |
| --- | --- | --- |
| 网关限流 + 排队判定 | 3 ms | 超出令牌桶直接返回「排队中」，不进后端 |
| 活动闸门（态 / 时间窗 / 资格） | 2 ms | 规则快照在进程内（→ 08 · §08.6） |
| 风控本地求值（L1~L4） | 5 ms | 硬顶；模型异步补判（→ 08 · §08.3） |
| Redis Lua 预扣 | 4 ms | 单 key 热点，分桶后 ≤ 2 ms |
| claim 落账（本地事务 + Outbox） | 12 ms | 一次 insert + 一次 update |
| **同步链路合计** | **≤ 26 ms** | 发奖**不同步**：返回 `claim_id` + 「发放中」 |

### 聚合、不变量、守护方式

| 聚合根 | 包含 | 不变量（必须由同一个事务守护） | 守护方式 | 破坏后果 |
| --- | --- | --- | --- | --- |
| **`Claim`** | status、`channel_txn_id`、`rule_ver`、快照价格 | **同一 `(activity_id, user_id, round)` 只能有一条成功 claim** | DB **唯一索引**（不是先查后插） | 2.74% 重复发放（事故①） |
| **`Claim`** | 同上 | 一张 claim 只有一条终态路径，状态单调不可回退 | 状态机 `UPDATE ... WHERE status=?` | 一张单发两次 / 回补两次 |
| **`Stock`** | total / left / pending / issued / refunded | `issued + pending ≤ total + 容差`（券 1%、现金 0） | Redis Lua 原子 + DB 条件 UPDATE + 对账 | 超发穿透预算 |
| **`Stock`** | 同上 | 每次预扣、发放、回补都必须有 `stock_ledger` 流水 | 同事务双写（业务 + 流水） | 库存与账不平，无法定位 |
| **`Activity`** | status、时间窗、`budget_id` | 只有 `ACTIVE` 且在时间窗内可领；预算耗尽必须硬阻断 | 闸门前置校验 + 状态机 | 活动外发放（合规事故） |
| **`prize` 号段** | `coupon_code` 全局空间 | 券码全局唯一、永不复用 | 号段发号 + 唯一索引 + 墓碑表 | 撞码 → 同一张券被两人核销 |
| **`Participation`** | activity + user + seq | **无强不变量**（只追加日志） | 无 | 仅影响归因，不影响钱 |

**三个反直觉点，评审时会被追问：**

1. **「同一用户同一活动只能领一次」属于 `Claim`，不属于 `Participation`，也不属于 `Activity`。** 因为只有 `Claim` 是「钱」的载体；把它挂在活动上，你会自然写出「活动级计数」，而计数天然有窗口（→ §22.6 的窗口图）。
2. **`rule` 不是聚合，是 `Activity` 内的不可变快照（`rule_ver`）。** 规则会热更，但**一次领奖必须用同一版本的规则从头走到尾**——否则「按 10% 概率中奖」的判定会在重试时换成一个版本，用户看到的和账上记的不是一回事（同 [08 · §08.6](08-risk-and-antifraud.md) 的不可变快照纪律）。
3. **`coupon_code` 的唯一性属于「全局命名空间」，不属于 `Claim`**——与 [12 短链 · §12.4](12-shortlink-system-design.md) 的 slug 完全同构。把它当成 claim 的属性，你就会写出「失败后释放券码、下次重发同一码」，而那在物理世界里等于**把已经印出去的券收回再给别人**。

## 22.5 领奖状态机：每个状态的幂等要求

```

        │
        ▼
   ┌──────────┐  唯一索引冲突（同一 user+activity 已存在）

 │ REVOKED  │        │ UNKNOWN  │──────────────────┘
 └──────────┘        │ 超时未知 │─ 查询确认成功 → SUCCESS
                     └──────────┘─ 查询确认不存在 → FAILED → 回补
```

### 状态迁移表（每个状态的幂等要求是硬约束）

| 状态 | 进入条件 | 允许迁出 | **幂等要求** | 是否占用库存 |
| --- | --- | --- | --- | --- |
| `INIT` | 唯一索引插入成功 | DEDUCTING / REJECTED / SOLD_OUT | 重复请求**回放当前状态**，绝不新建第二条 | 否 |
| `DEDUCTING` | 调用 Lua 之前 | DEDUCTED / SOLD_OUT | 重入前必须先查 `claim_set`（Lua 内幂等集合），否则同一 claim 扣两次 | 预备 |
| `DEDUCTED` | Lua 成功 + claim 落账同事务提交 | DISPATCHING / REFUNDING | 回补以 `UPDATE ... WHERE status='DEDUCTED'` **行数=1** 裁决 | 是 |
| `DISPATCHING` | CAS 成功 | SUCCESS / FAILED / UNKNOWN | 同一 claim 只允许一次 CAS 成功；重复消费者读到 0 行即跳过 | 是 |
| `UNKNOWN` | 渠道超时无响应 | SUCCESS / FAILED | **只查询、不重发**；查询结果必须落 `channel_txn_id` | 是 |
| `SUCCESS` | 渠道返回成功 + 拿到流水号 | REVOKED | 终态；重复写只允许「补空字段」（CAS 带 `channel_txn_id IS NULL`） | 转为已发 |
| `FAILED` | 渠道明确失败 | REFUNDING | 终态；**不得从 FAILED 回到 DISPATCHING** | 是（回补后释放） |
| `REFUNDED` | 回补 Lua 成功 | — | 幂等键 `claim_id`；重复回补 0 行 | 否 |
| `REJECTED` / `SOLD_OUT` | 前置拒绝 | — | 无副作用、不占库存，可自由重试（每次重新裁决） | 否 |
| `REVOKED` | 作弊/合规作废 | — | 只对可作废奖品；现金不可 `REVOKED` | — |

> **一条不可协商的纪律**：**状态迁移的 0 行返回必须回查，不能当成功。** 这是 [05 写路径形态 · §05.7](05-write-path-and-async-shape.md) 与 `eng/2` §2.9 反复强调的——`UPDATE ... WHERE status='DEDUCTED'` 返回 0 行，可能是「别人已经推进了」（正常），也可能是「这条 claim 根本不存在」（异常）。一律当成功，等于把回补的重复执行变成超发。

## 22.6 幂等：三种实现，为什么必须靠唯一索引

### 三种实现的边界

| 方案 | 幂等键 | 裁决点 | 能防什么 | **防不住什么** |
| --- | --- | --- | --- | --- |
| **① 券码唯一** | `coupon_code`（服务端生成） | 券表唯一索引 | 同一张券重复入账 | **一次意图两次发券**（每次重试新券码）← 事故①根因 |
| **② 业务唯一键** | `(activity_id, user_id, round)` | claim 表唯一索引 | 同人同活动重复领奖（全部 9 个分支） | 一轮活动多次领取（需子键 `round`/`item_id`） |
| **③ 状态机前置** | `claim_id` + `status` | `UPDATE ... WHERE status=?` | 发奖、回补、作废的重复推进 | 重复**创建**（它只防状态重复迁移） |
| 补充：前端 token | 客户端 `request_id` | Redis `SET NX` + DB 落账 | 用户连点（分支 2） | Redis 丢数据即失效，只能做**前置去重**不能当权威（→ `eng/5` §5.4.5） |
| 补充：请求指纹 | `hash(user, activity, ts_bucket)` | hash | 无业务键的兜底 | 参数/时间桶微变即漂移（→ `eng/1` §1.8） |

### 为什么「同一用户同一活动只能领一次」必须靠唯一索引

先看「先查后插」的窗口：

```
T0   A: SELECT count(*) FROM claim WHERE activity_id=1 AND user_id=U   → 0
T1   B: SELECT count(*) FROM claim WHERE activity_id=1 AND user_id=U   → 0     ← 窗口在这里
T2   A: INSERT claim(1, U, ...) ; COMMIT                               → 成功
T3   B: INSERT claim(1, U, ...) ; COMMIT                               → 第二条
```

**窗口大小 = T1 到 T2 的时间**。单机 1 ms、走从库 800 ms、跨机房 30 ms——只要窗口 > 0，并发就一定能踩中。算一下事故场景：20 万 QPS 里 7 万落在预扣上，**1 ms 的窗口内有约 70 个并发请求同时通过检查**。唯一索引把 T2/T3 合并成一次原子裁决，窗口才消失——这是 `eng/2` §2.3 那张结构图的全部含义，本篇只引用结论，不重写。

| 结论（→ `eng/1`~`eng/6`） | 在领奖场景的落法 |
| --- | --- |
| 幂等 = **幂等键 + 原子裁决点 + 结果存储**，缺一不可 | 键 `(activity,user,round)` + claim 唯一索引 + `claim.status` |
| 唯一索引是**兜底**，不是全部 | 还要 ① 键不能被客户端/服务端重造（券码 ❌）② 副作用后置（先落库再发奖）③ 可观测（重复率指标） |
| 键必须「唯一、稳定、可定位」，**不能含时间戳/随机数** | `round` 用活动配置里的轮次号，不用「当前时间分桶」 |
| 冲突后必须**读回赢家结果**，不能空手返回成功 | `catch DuplicateKeyException → load(claimId).toResult()` |
| 只有「至少一次」的投递下，**消费端幂等是唯一出路** | 发奖走 MQ + Outbox → 消费端按 `claim_id` 幂等（→ `eng/10`、`eng/11`） |
| Redis 只能做前置去重 | `SETNX` 挡连点，权威裁决仍在 DB 唯一索引 |

> **必须写进 PR 模板的一句话**：新增任何「发东西」的接口，评审时先问「你的幂等键是业务意图还是发放产物？」——如果是后者（券码、订单号、流水号），直接打回。

## 22.7 库存扣减：Redis 预扣 + DB 落账 + 失败回补

### 完整流程（一次领奖的写路径）

```
        20 万 QPS 请求
             │
  ① 前端限流 + 按钮置灰（同人 1 次/秒）
             ▼
  ② 服务端闸门：activity.status + 时间窗 + 资格 + 频控（进程内，≤2 ms）
             │ 不通过 → REJECTED / SOLD_OUT（不触库存）
             ▼
  ③ ┌─────────────────────────────────────────────┐
    │ Redis Lua 原子预扣（单脚本内完成 5 件事）    │
    │   left ≥ 1 ?  left−1 ; pending+1 ;          │
    │   ZADD pd:{act} {now+30s} claim_id ;        │
    │   SADD claim_set {claim_id}                 │
    └─────────────────┬───────────────────────────┘
             返回余量  │ 返回 −1
                      ▼
  ④ claim 落账（同一本地事务）：INSERT claim(DEDUCTED) + INSERT stock_ledger(deduct) + Outbox
                      │ 事务失败 → 由 pending TTL 兜底释放（§22.8）
                      ▼
  ⑤ 异步发奖 worker：CAS → DISPATCHING → 调渠道（幂等键 = claim_id）
             ┌────────┴─────────┬──────────────────┐
        SUCCESS            DEFINITE_FAIL         UNKNOWN
             │                 │                   │
     claim→SUCCESS      claim→FAILED         claim→UNKNOWN
     pending−1 issued+1        │             10 s 后查渠道
     ledger(issue)             ▼                   │
                       ⑥ 回补 Lua（幂等 by claim_id）：        ▼
                          left+1 ; pending−1 ;          确认成功→SUCCESS
                          refunded+1 ; ZREM ;           确认缺席→FAILED→回补
                          SADD claim_refunded
                          claim→REFUNDED（DB 状态机裁决）
```

### 超发与少发：取舍必须按「可追回性」分裂

**这是本篇最该背下来的一张表。** 超发与少发不是「精度问题」，是**两种不同的损失**：超发是「不可追回的钱」，少发是「可补偿的体验」。

| 奖品类型 | 可超发 | 容差 | 判定依据 | 少发怎么办 |
| --- | --- | --- | --- | --- |
| **现金红包** | ❌ **绝对不可** | **0（按分核）** | 打出去不可追回；涉及个税与资金凭证（§22.14） | 立刻回补库存 + 发致歉券 + 客服话术 |
| **实物礼品** | ❌ 不可 | 0 | 物流成本 + 已发货不可逆 + 舆情 | 缺货则降级为等值券（用户可拒） |
| **自有券（未核销）** | ✅ 可 ≤ 1% | 1% | **未核销可作废、可回收**，超发成本 = 面值 × 超发率 × 核销率 | 无需补偿，账上记 `over_issued` 并作废多余 |
| **第三方券码** | ⚠️ 视合同 | 0.1% | 超发要按合同赔付，且渠道有上限 | 走渠道补发工单 |
| **积分** | ✅ 可 ≤ 2% | 2% | 内部负债，可扣回、可调账 | 自动补齐 |

**判据公式（评审时直接给这个）**：

```
允许超发上限 = 单次可回收成本 ÷ 面值
  券：可作废 ⇒ 单次回收成本 ≈ ¥0.2（作废 + 通知） ⇒ 面值 ¥50 时容差 ≫ 1%，取 1% 是保守值
  现金：不可回收 ⇒ 回收成本 = ∞ ⇒ 容差 = 0
```

> **所以「绝不超卖」与「绝不宕机」在券类上不必二选一**——券可作废，允许 1% 超发换取「绝不把用户的成功请求变成失败」。而现金侧必须反过来：**宁可少发（返回「发放中，稍后到账」），也绝不多发一分**。这条与 [23 秒杀与库存扣减](23-seckill-inventory.md) 的「绝不超卖 vs 绝不宕机」是同一枚硬币：**能不能退让，取决于退让的代价是否可回收**。

### 为什么不全用 DB 条件 UPDATE？

```
DB 方案：UPDATE stock SET left=left-1 WHERE prize_id=? AND left>0
  单行 7 万 TPS 峰值 —— 单行热点锁，实测上限约 3,000~5,000 TPS（InnoDB 行锁排队）
  ⇒ 20 万 QPS 直接打穿，且锁等待会把连接池占满（→ eng/36）
Redis 方案：Lua 单分片 2.5~3 万 QPS，按 bucket 分 16 桶 ⇒ 40 万 QPS 余量
```

DB 仍然是**账的权威**（`stock_ledger` 只追加、可重算），Redis 只是**扣减的裁决点**。两者靠对账对齐（§22.11）——这正是「Redis 不能当权威，但可以当闸门」的分工（同 [04 读路径形态](04-read-path-and-cache-shape.md) 的缓存定位）。

## 22.8 预扣与回补的时序问题：两个必须显式回答的追问

### 追问一：预扣成功了，但服务挂了，券是不是永远消失了？

会。这就是**僵尸预扣**（orphan deduct），表现为「库存显示售罄，但发放量远小于预扣量」。

处理机制是**超时释放**，四个参数必须一起设计：

| 机制 | 设计 | 取值依据 |
| --- | --- | --- |
| **pending 带 TTL** | Lua 内 `ZADD pd:{act} now+30000 claim_id`（毫秒时间戳作 score） | TTL ≥ 发奖链路 P99（2 s）× 10 = 20 s，取 30 s |
| **扫描释放** | 每 10 s 扫 ZSET `< now` 的成员，逐个查 claim 状态；仍为 `DEDUCTING`（无落账）→ 回补 | 扫描 QPS ≈ 在途 claim / 30 s，可忽略 |
| **落账即消解** | `claim` 事务提交后立刻 `ZREM pd:{act} claim_id` | 事务与 ZREM 之间挂掉 → 落到扫描器兜底 |
| **指标** | `orphan_deduct_total`、`deduct_issued_gap`（Σdeduct − Σissued − Σpending） | gap > 0.1% 即告警（§22.11 差异表第 2 行） |

> **TTL 不能太短**：短于发奖链路 P99 会把**正在正常发奖**的 claim 回补掉，于是「回补 + 原发奖又成功」= 超发。这是最隐蔽的一类超发，来源不是并发而是**超时参数定错**。这正是 `eng/5` §5.1 事故二的形态（24 h 的 TTL 撞上 26 h 的补发）。

### 追问二：回补重复执行了怎么办？

回补是 `Cancel`，它有三个经典坑（空回滚、悬挂、补偿失败），结论全部在 `eng/13`，本篇只说**在领奖场景里该怎么防**：

| 坑 | 领奖场景的形态 | 防护 |
| --- | --- | --- |
| **空回滚** | 回补先到（Lua 从没扣过），「成功」但没释放任何东西；随后 Try 补上 → 库存永久 −1 | 回补前查 `claim` 是否存在；Lua 里检查 `claim_set` 是否存在该 claim_id，不存在则记 `refund_noop` 不计数 |
| **悬挂** | 回补已执行，延迟的预扣请求才到（重试）→ 库存扣了但已无可回补的 claim | `claim` 表 `CANCELLED/REFUNDED` 是墓碑；预扣落账用 `INSERT ... WHERE NOT EXISTS(是否已回补)`，命中墓碑直接丢弃 |
| **补偿失败** | 回补 Lua 因 Redis 抖动失败，claim 卡在 `REFUNDING` | `REFUNDING` 是**可重入中间态**：由定时任务按 claim_id 重试，退避 1s/5s/30s/5min，超 5 次进人工工单 |

**回补幂等的三段裁决（顺序不能换）**：

```
① Redis 快判：SADD claim_refunded {claim_id} → 返回 0 表示已回补，直接返回成功（不重复加库存）
② DB 裁决：UPDATE claim SET status='REFUNDED' WHERE claim_id=? AND status IN ('DEDUCTED','FAILED','UNKNOWN')
          → 行数 = 1 才继续做 ③；行数 = 0 说明别人已回补 → 无效返回
③ Lua 落账：left+1 ; pending−1 ; refunded+1 ; ledger(refund)
```

> **关键顺序**：**幂等权威在 DB 状态机，Redis 只是快判。** 反过来（Redis 当权威）会在 Redis 丢数据/主从切换后产生重复回补——而重复回补 = 超发，且超发的是**券**（可作废，尚可救）或**现金**（不可救）。这条与 `eng/13`「先补状态（墓碑 + 防悬挂标记），再修数据」的修复顺序完全一致。

## 22.9 发奖的异步与补偿：三种失败，三种策略

发奖必须是异步的（同步调一个 P99 4 s 的渠道接口，会把 20 万 QPS 的领奖链路直接拖死），而异步必然带来「结果未知」。**外部发奖只有三种失败，但它们的正确处理方式完全不同。**

| 现象 | 真实语义 | 处理策略 | 幂等依据 | 严禁动作 |
| --- | --- | --- | --- | --- |
| **① 超时未知**（连不上、读超时、网关 504） | **结果未知**：可能成了、可能没成 | 进 `UNKNOWN`；10 s / 30 s / 2 min 三次**主动查状态**；确认成功 → SUCCESS；确认不存在 → FAILED → 回补 | 外部请求带 `out_request_id = claim_id`，让对方去重 | **盲目重发**（这是重复发放的头号来源） |
| **② 明确失败**（余额不足、券池空、限购、参数非法） | 确定没成 | 立即 `FAILED` → 回补；可按降级链换低档奖品（重新走一次库存预扣） | `claim_id` + 错误码分类 | 无限重试（打爆渠道，正常请求也失败） |
| **③ 成功但回调丢** | 实际成了，我们不知道 | 靠**对账**兜底：L1 实时明细（claim_id 逐笔 ≤5 s）+ T+1 全量；对账补记 `channel_txn_id` | 渠道流水 vs 我方 claim | 重新发一次「补偿」 |
| ④ 渠道返回成功但字段缺失（无流水号） | 疑似成功，缺凭证 | 进 `SUCCESS_PENDING_TXN`，**不得进 SUCCESS**（对账锚点缺失等于账废了） | `channel_txn_id IS NULL` 的 CAS 补写 | 手工补一个假流水号 |

**降级链**（明确失败时的唯一合法重试形态）：

```
主奖品不可用 → 同价值替代（券 A → 券 B）→ 低一档（¥50 → ¥20 券）→ 积分等价 → 无条件致歉券
每一跳都必须：重新预扣（新 claim 子单）→ 唯一键 (activity,user,round,attempt) → 幂等
不允许：在同一个 claim 上换奖品（会破坏「一张 claim 一条终态」的不变量）
```

### 双栈骨架 ①：Java 领奖 Saga（Try / Confirm / Cancel，每步可重入）

```java
// ClaimSaga.java —— 领奖编排：唯一索引裁决 → 闸门 → 预扣 → 落账 → Outbox；发奖异步可重入
@Transactional
public ClaimResult claim(ClaimCmd cmd) {
    String claimId = ClaimId.of(cmd.activityId(), cmd.userId(), cmd.round()); // ★ 业务唯一键，非随机
    try {
        claimRepo.insertIfAbsent(claimId, cmd);              // ① 唯一索引即裁决点
    } catch (DuplicateKeyException e) {
        return claimRepo.load(claimId).toResult();           // ② 重复请求 → 回放第一次结果
    }
    if (!gate.pass(cmd))            return claimRepo.fail(claimId, Reason.NOT_ELIGIBLE);
    if (risk.verdict(cmd).reject()) return claimRepo.fail(claimId, Reason.RISK_REJECT);
    long left = stock.deduct(cmd.prizeId(), bucket(cmd), claimId); // ③ Try：Redis Lua 原子预扣
    if (left < 0)                   return claimRepo.fail(claimId, Reason.SOLD_OUT);
    claimRepo.markDeducted(claimId);                     // ④ 落账 + stock_ledger，同一事务
    outbox.publish("claim.deducted", claimId);           // ⑤ 同事务写 Outbox（eng/10）
    return ClaimResult.pending(claimId);
}

// 异步消费者：可重入，重复消费只推进一次
public void onDeducted(String claimId) {
    Claim c = claimRepo.load(claimId);
    if (!c.status().canDispatch()) return;                     // ★ 已终态：直接跳过
    if (!claimRepo.cas(claimId, DISPATCHING)) return;          // UPDATE ... WHERE status='DEDUCTED'，0 行即跳过
    ChannelResp r = channels.of(c.prizeType()).issue(c.claimId(), c.toIssueReq()); // 外部幂等键 = claim_id
    switch (r.kind()) {
        case SUCCESS       -> { claimRepo.cas(claimId, SUCCESS, r.txnId()); stock.markIssued(c); } // 记 channel_txn_id
        case DEFINITE_FAIL -> { claimRepo.cas(claimId, FAILED, r.code()); stock.compensate(c); }   // 立即回补
        case UNKNOWN       -> claimRepo.cas(claimId, UNKNOWN, null);   // 10 s 后查状态，绝不重发
    }
}
```

> 注意 `ClaimId.of(activityId, userId, round)`：**幂等键在方法第一行就算出来，且不含 `now()` / `UUID.randomUUID()`**。事故一里券码是 `UUID`，重试一次就是一张新券——`eng/1` §1.8 的三条要求（唯一、稳定、可定位）一条都没满足。

### 双栈骨架 ②：Go 库存预扣 Lua（预扣 + 回补双向幂等）

```go
// stock/store.go —— 预扣与回补同一个 Lua 家族：原子、幂等、带超时释放锚点
const deductLua = `
local st, pd, cs = KEYS[1], KEYS[2], KEYS[3]      -- 库存桶 / pending ZSET / 幂等集合
local cid, ttlMs = ARGV[1], tonumber(ARGV[2])
if redis.call('SISMEMBER', cs, cid) == 1 then return -2 end   -- 已扣过：幂等返回（不是错误）
local left = tonumber(redis.call('HGET', st, 'left') or '0')
if left <= 0 then return -1 end                                -- 售罄：正常返回，不重试
redis.call('HINCRBY', st, 'left', -1)
redis.call('HINCRBY', st, 'pending', 1)
redis.call('SADD', cs, cid)
redis.call('ZADD', pd, redis.call('TIME')[1]*1000 + ttlMs, cid)  -- 超时释放锚点
return left - 1
`

const refundLua = `
local st, pd, cs = KEYS[1], KEYS[2], KEYS[3]
local cid = ARGV[1]
if redis.call('SISMEMBER', cs, 'r:'..cid) == 1 then return 0 end   -- 已回补：幂等返回
redis.call('HINCRBY', st, 'left', 1)
redis.call('HINCRBY', st, 'pending', -1)
redis.call('HINCRBY', st, 'refunded', 1)
redis.call('SADD', cs, 'r:'..cid)
redis.call('ZREM', pd, cid)
return 1
`

// Deduct 返回：>=0 余量 / -1 售罄 / -2 重复（调用方一律按「已受理」处理）
func (s *Store) Deduct(ctx context.Context, actID, prizeID string, bucket int, cid string) (int64, error) {
	keys := []string{fmt.Sprintf("st:%s:%d", prizeID, bucket), "pd:" + actID, "cs:" + actID}
	return s.rdb.EvalSha(ctx, s.deductSha, keys, cid, "30000").Int64() // TTL 30 s = 发奖 P99 × 10
}

func (s *Store) Refund(ctx context.Context, actID, prizeID string, bucket int, cid string) (int64, error) {
	keys := []string{fmt.Sprintf("st:%s:%d", prizeID, bucket), "pd:" + actID, "cs:" + actID}
	return s.rdb.EvalSha(ctx, s.refundSha, keys, cid).Int64()
}
```

> 三个细节值得抄走：① **售罄返回 `-1` 而不是 `error`**——把正常业务结果当异常抛，会触发上层重试，把 20 万 QPS 放大成 60 万；② **`return -2`（重复）也当受理**，因为客户端可能只是没收到上一次的响应；③ `EvalSha` 而非 `Eval`，脚本常驻 Redis，单次网络往返 1.5 ms → 0.9 ms。
>
> **Lua 脚本里的 `TIME` 要在同一脚本内取**，不要在客户端算 `now` —— 客户端时钟漂移 30 s，超时释放就会整体错位。

## 22.10 防刷：只给架构接口，规则去 08

防刷在本篇只回答一件事：**奖励系统要在哪里留口子，才能让风控插进来而不重写业务。** 规则、模型、指纹、名单、图关系的全部内容在 [08 风控与反作弊](08-risk-and-antifraud.md)，此处不重写。

| 接口 | 调用时机 | 输入 | 输出 | 预算 |
| --- | --- | --- | --- | --- |
| `verdict(subject, activityId, facts)` | 预扣之前（同步，SDK 本地求值） | 设备/支付/地址/账号 + 活动维度计数 | `PASS` / `DOWNGRADE`（加验证码）/ `REJECT(case_id)` | P99 ≤ 5 ms，硬顶；模型异步补判（→ 08 · §08.3） |
| `report(claimId, subject, result, prize)` | 发奖之后（异步） | claim 结果 + 奖品价值 | — | 反向链路：供 08 做名单清理与命中统计（→ 08 · §08.9） |
| `ruleSnapshot(ver)` | 服务启动 / 热更 | 版本号 | 不可变规则快照（含 `gray.ratio`、`bucket_by`） | 发布到生效 P99 < 5 s |
| `subjectKey(cmd)` | 每一次判定 | 请求上下文 | 稳定主体键（设备优先，账号是维度之一） | 绝不含时间戳/随机数 |

**三条来自 08 的硬结论，奖励系统必须配合**：

1. **主体 = 设备 + 支付 + 地址，账号只是其中一个维度。** 事故一里 620 台设备 × 78 个账号 = 4.83 万单，每一单在「账号视角」下都是合法新客（→ 08 · §08.14 反模式 8）。
2. **处置必须分级可逆**：`冻结` ≠ `作废`。券被设计成「领取即生效」，才导致 11:30 只能冻结未核销的 1.1 万张（→ 08 · §08.10）。奖励系统的配合动作是：**券发放后留 `freezeable` 标记 + 冻结 24 h 缓冲期**。
3. **额度按主体聚合是产品定价问题，不是风控补丁。** 这一条最省钱，且评审时最容易被跳过：

```
假设：单设备 24 h 最多领 3 单、单支付账户最多 5 单
事故一：620 台设备 × 78 单 → 上限后 620 × 3 = 1,860 单 = ¥9.3 万（损失的 3.7%）
成本：一个 Redis 计数 + 一条配置，0 元
对比：图关系 + 模型（→ 08 · §08.3）月成本 ¥10 万+
```

> **架构接口的验收标准**：把 `08` 的规则引擎整体替换掉，奖励系统**一行代码都不用改**。做不到，说明风控被硬编码进了业务（→ 08 · §08.6「规则是数据不是代码」）。

## 22.11 对账闭环（核心）：五个口径，一个锚点

这是本篇的核心。幂等与库存解决「不发错」，对账解决**「怎么证明没发错，以及错了怎么找回来」**。`eng/14` 给全部机制，这里只给**活动奖励场景的五个口径与差异矩阵**。

### 五个口径

| 口径 | 数据源（必须是独立记录源） | 记录者 | 粒度 | 更新频率 | 残差的业务含义 |
| --- | --- | --- | --- | --- | --- |
| **① 预算 budget** | 财务审批单（双人签，不可变） | 财务系统 | 活动 × 奖品 | 上线前一次性 | 上限，不可被穿透 |
| **② 预扣 deduct** | Redis 余量 + `stock_ledger(deduct)` | 领奖服务 | `claim_id` | 实时 | 已承诺、未兑现 |
| **③ 实际发放 issued** | `claim(status=SUCCESS)` + 渠道流水 | 领奖服务 + 渠道 | `claim_id` | 实时 / T+1 | 真金白银已出门 |
| **④ 核销 redeemed** | 券中台核销流水 / 支付回调 | 券与营销中台 | `coupon_code` | T+0 准实时 | 用户真的用了 |
| **⑤ 核销失败 redeem_fail** | 渠道退单 / 过期回收 | 渠道 | `coupon_code` | T+1 | 可回收的部分 |

### 三条恒等式（不成立就是事故，不是「差异」）

```
① budget  ≥ Σdeduct − Σrefunded                    预算不被穿透（穿透 = 财务事故）
② Σdeduct = Σissued + Σpending + Σrefunded        预扣守恒（pending 是一等公民）
③ Σissued = Σredeemed + Σunredeemed + Σredeem_fail 发放守恒（券不能凭空消失）
```

### 对账闭环图

```
 ① 预算审批（财务双人签 · 不可变 · budget_id）
        │  ¥473.4 万 / 场
        ▼
 ② 预扣 deduct ──── Redis Lua + stock_ledger ────→ Σdeduct
        │  pending（TTL 30 s）  ⇄ 回补（幂等 by claim_id）
        ▼
 ③ 实际发放 issued ── claim(SUCCESS) + 渠道流水 ──→ Σissued
        │  必须带 channel_txn_id ★（五层的唯一共同锚点）
        ▼
 ④ 核销 redeemed ─── 券中台核销流水 ─────────────→ Σredeemed
        │
        ▼
 ⑤ 核销失败 redeem_fail ── 渠道退单 / 过期回收 ───→ Σredeem_fail
        │
   ┌────┴──────────────────────────────────────────────────┐
   │  三层对账（eng/14 结论，机制不重写）                    │
   │  L1 实时明细：claim_id 逐笔，≤5 s   → 抓「发了没记/记了没发」│
   │  L2 准实时汇总：活动×奖品×分钟 count+sum+checksum → 抓漂移 │
   │  L3 T+1 全量：渠道文件 vs 我方账本  → 抓迟到、跨日、历史遗漏 │
   └────┬──────────────────────────────────────────────────┘
        ▼
   reconciliation_diff（差异表：有唯一主键 + 分类 + 责任方）
        ├→ 自动冲正（我方漏记/重复）      ├→ 自动补记（渠道有、我方无）
        └→ 人工工单（金额不一致、超阈值）
        ▼
   财务凭证：发票 / 个税申报 / 审计留痕（§22.14）
```

### 差异矩阵：每一种差都要有名字和处置

| # | 差异形态 | 触发阈值 | 最可能原因 | 处置 | 责任方 |
| --- | --- | --- | --- | --- | --- |
| 1 | `budget − Σissued` 突然停滞 | 10 min 无新增 | 渠道故障、券池空、活动被停 | 查渠道健康 + 活动状态；告警 | 平台 |
| 2 | `Σdeduct − Σissued − Σpending > 0` | > 0.1% | **僵尸预扣**（服务挂、回补失败） | 扫 pending → 回补；`orphan_deduct` 指标 | 领奖服务 |
| 3 | `Σissued − 渠道流水 ≠ 0` | 任意单笔 | 成功但回调丢 / 假成功 / 重复发 | **以渠道为准**；claim 打 `channel_mismatch` 进工单 | 渠道 + 我方 |
| 4 | `Σredeemed > Σissued` | 任意 | **券码复用 / 伪造 / 重复入账**（最严重） | 立即冻结券池 + 安全排查 + 报警 | 安全 |
| 5 | `Σredeemed + Σunredeemed + Σfail ≠ Σissued` | > 0.01% | 券中台漏记、时区/币种错 | L1 逐笔对齐；补记 | 券中台 |
| 6 | `Σissued > budget × (1 + 容差)` | 券 1% / 现金 0 | **超发穿透预算**（Lua 与 DB 双扣） | 硬阻断发放 + 追责 + 修 Lua | 领奖服务 |
| 7 | 财务实付 − 账面 `Σissued` | 任意 | 未入账发放、退款未回冲、跨月 | T+1 日终差异工单，**禁止手工改数** | 财务 |
| 8 | `channel_txn_id IS NULL` 的 SUCCESS 数 | > 0 | **对账锚点缺失**（事故①的 18.7 万） | 建模缺陷：补字段 + 历史只能认损 | 架构 |

> **事故①的 ¥18.7 万为什么找不回来**：claim 表没有 `channel_txn_id`，而渠道流水的唯一键是它自己的单号。两个记录源之间**没有业务主键可对齐**，就只能核总数，而核总数会漏掉「一多一少相互抵消」（→ `eng/14` · §14.2 第一个误解）。**这不是对账做晚了，是建模时没埋锚点——历史数据补不回来。**

### 从 eng/14 抄来的四条结论（不重写机制）

| 结论 | 在奖励场景的落法 |
| --- | --- |
| 对账 = **两个独立记录源**按业务主键交叉验证，同源必平（假平） | `claim` 与渠道流水必须独立写入，不能由同一个 MQ 消费者同时写两边 |
| **核总数会漏一多一少**，必须逐笔 + 汇总双跑 | L1 逐笔（`claim_id`）+ L2 汇总（`activity × prize × 分钟`）同时跑 |
| 幂等/事务是**事前防**，对账是**事后查**；两者不可替代 | 幂等挡重复、事务挡半成品、对账挡漏写/错写/金额算错 |
| 日终差异率长期 > 0.05% → **回去修 L0（幂等、状态机）**，别加人对账 | 券类日终差异 > 0.05% 时冻结下一场活动上线，先修幂等 |

## 22.12 峰值应对：20 万 QPS 的漏斗

```
1,000 万参与者 × 3 次点击 = 3,000 万请求，80% 集中在开抢 60 s
                          │  40 万 QPS
┌─────────────────────────┴───────────────────────────┐
│ ① 边缘层：活动页静态化 + CDN + 余量接口 1 s 缓存      │ ×0.6
│   按钮置灰 + 前端 1 次/秒/人（挡掉 60% 的连点）        │ → 24 万
├─────────────────────────────────────────────────────┤
│ ② 网关：令牌桶 20 万 QPS + 排队（返回 ticket，非 502）│ 
│   超出部分返回「排队中，第 N 位」，前端 2 s 后重试     │ → 20 万
├─────────────────────────────────────────────────────┤
│ ③ 服务端闸门（进程内，≤2 ms）：活动态 + 资格 + 频控    │ ×0.35
│   这里砍掉的是「注定领不到的人」，越早砍越省钱         │ → 7 万
├─────────────────────────────────────────────────────┤
│ ④ Redis Lua 预扣：16 桶 × 2.5 万 QPS = 40 万 余量     │
│   券池 5 万张 ⇒ 第 5 万次之后全部返回 -1（售罄）      │ → ≤5 万
├─────────────────────────────────────────────────────┤
│ ⑤ Kafka（8 万 TPS / 8 分区，key=claim_id）+ Outbox    │
│   异步发奖 worker 2,000 TPS × 8 实例 = 1.6 万 TPS     │ → 5 万（约 3 s 消化完）
└─────────────────────────────────────────────────────┘
        全程同步链路 ≤ 26 ms；用户看到「领取成功，发放中」
```

**四个必须算对的地方：**

| 点 | 算错的样子 | 算对了 |
| --- | --- | --- |
| **Redis 分桶** | 5 万张券放单 key，单分片 2.5 万 QPS 上限 → 打满后 P99 从 2 ms 涨到 300 ms | 16 桶（`hash(user)%16`），每桶 3,125 张，单桶 ≤ 1.2 万 QPS |
| **排队 vs 拒绝** | 超限直接 502 → 用户重试把 QPS 放大 3 倍（重试风暴） | 令牌桶 + ticket + 退避重试，超限量 ≈ 0 次重复请求 |
| **售罄的返回形态** | 券发完后仍让请求走完整链路（闸门 → 风控 → 预扣）→ CPU 空转 | 券余量为 0 时**闸门直接短路**（本地 1 s 缓存余量），永不进后端 |
| **异步发奖的背压** | Kafka 积压 → 用户等 5 分钟没收到券 → 客服爆炸 | 发奖 TPS ≥ 峰值预扣 TPS（1.6 万 vs 7 万？见下） |

> **⑤ 里那个 7 万 vs 1.6 万的差额必须解释清楚**：预扣峰值 7 万 QPS 只持续约 1 s（券池 5 万张），总量 ≤ 5 万条；发奖 1.6 万 TPS 在 3 s 内消化完，**用户感知的延迟 = 队列等待 ≈ 3 s**。若券池换成 50 万张（大促），则预扣持续 7 s、发奖需要 31 s——这时必须提高 worker 并发或改为「先发券码后置通知」。**这就是 [23 秒杀与库存扣减](23-seckill-inventory.md) 与本篇的分界点：券池越大、越接近纯库存问题；奖品越杂、越接近对账问题。**

## 22.13 紧急停止与灰度发放：怎么在「发了一半」时停下来

### 「停止」有三种语义，对应三种完全不同的处理

| 语义 | 动作 | 在途数据 | 可恢复性 | 适用场景 |
| --- | --- | --- | --- | --- |
| **① 闸门停止**（停新请求） | `activity.status → PAUSED`；闸门拒绝新 claim | **无半成品**：在途 claim 继续走完（≤3 s 内清空） | ✅ 改回 `ACTIVE`，秒级恢复 | **首选，覆盖 90% 场景**（超发苗头、渠道抖动、舆情） |
| **② 冻结发奖**（停发，保留 claim） | `dispatch_enabled=false`；worker 消费到 claim 时**不调渠道**，停在 `DEDUCTED` | **有 pending，但可恢复**：claim 有状态、库存有 pending ZSET | ✅ 打开开关继续发 | 渠道大面积故障、发现刷单需先甄别、预算审批临时冻结 |
| **③ 作废回滚**（收回已发） | 券侧批量冻结/作废 + `claim → REVOKED` | **不可逆**：券已出门，回收率取决于核销率 | ❌ 只能补偿 | 已确认作弊、监管要求、严重算错价 |

> **铁律：停机只能停在「状态机的一个合法状态」上，不能停在中间。**
> 所以 `DISPATCHING` 必须是一个**可恢复的持久状态**（先 CAS 进 `DISPATCHING`，再调渠道），而不是内存里的一个布尔。worker 在 `DISPATCHING` 挂掉后，由扫描器按 `claim_id` **反查渠道状态**（不是重发）——这就是 §22.5 里那句「worker 挂在这里」的含义。**停机能力不是运维功能，是状态机的完备性。**

### 三种语义的组合用法（事故①的正确处置顺序）

```
10:26 发现重复发放（分支 3）
  → ① 闸门停止（停新请求）          在途 3 s 内清空，不产生半成品
  → 修复幂等键（券码 → 业务唯一键）   代码 + 数据（把已重复的 442 张标记出来）
  → ② 冻结发奖（在途 claim 先不发）  等对账把「已发 / 应发 / 预扣」对齐
  → 对账通过后打开 dispatch_enabled  继续发，逐笔可追溯
  → ③ 作废回滚                       只对已确认作弊的 4.83 万张
```

### 灰度发放：钱比流量更该灰度

| 灰度对象 | 做法 | 每档观察 | 停止条件（硬阈值） |
| --- | --- | --- | --- |
| **人群桶** | `hash(user_id) % 1000 < ratio`，1% → 10% → 50% → 100% | 24 h | 重复发放率 > 0.01% / 申诉率 > 2% |
| **预算额度** ★ | 先只放 5,000 张额度（预算的 10%），观察完再放 100% | 24 h | `Σissued − 渠道流水 ≠ 0` 任一笔 |
| **奖品档位** | 先只发低档奖（¥20 券），高档奖最后开 | 6 h | 渠道错误率 > 2% |
| **渠道** | 双渠道并行（新渠道 1%），比对成功率与时延 | 6 h | 成功率差 > 5% |
| **概率配置** | 发布即**新版本** + 公示（不可热改，见 §22.14） | — | 冲突即回滚版本 |

> **预算灰度是最便宜的风险控制**：事故一若先放 10% 额度（5,000 张），损失从 ¥180.5 万降到 ¥18 万——**同样的代码，10 倍的差距**。这与 [07 变更治理](07-change-governance.md) 的「灰度对象错了，比例对了也没用」是同一条：**活动的灰度对象不是流量比例，是预算额度。**

## 22.14 合规与对账凭证：钱出了门，凭证没留 = 事故

| 事项 | 硬要求 | 落法 | 缺失的后果 |
| --- | --- | --- | --- |
| **预算审批** | 双人签 + `budget_id` + 不可变审批单 | 审批单与 `activity` 强绑定；**超预算发放必须硬阻断**（不是告警） | 超支无授权，审计不通过 |
| **发票** | 券/实物的采购发票与**发放量**匹配 | T+1 用 `Σissued` 与发票数量对账 | 成本无法入账，税前扣除风险 |
| **税务（个税）** | 现金红包/实物属**偶然所得**，需代扣代缴 | 发奖前算税（`tax_withhold` 流水），批量申报；`claim` 表存税额字段 | 补税 + 滞纳金 + 罚款 |
| **资金凭证** | 现金发放必须有银行/三方流水号 | `channel_txn_id` 为对账主键，**缺失不入账** | 账实不符（事故① 18.7 万） |
| **审计留痕** | 谁改了规则/预算/库存/状态，全部 append-only | `activity_audit`：操作人 + 时间 + 前后值 + 理由；保留 ≥ 3 年 | 无法追溯，责任不清 |
| **概率公示** | 抽奖概率必须公示，**不可事后调** | 概率随 `rule_ver` 快照固化；改动 = 新版本 + 重新公示 | 不正当竞争/消费者权益风险 |
| **个人信息** | 中奖名单含手机号/地址，属个人信息 | 加密存储 + 最小化 + 保留期限（同 [08 · §08.7](08-risk-and-antifraud.md) 的四条红线） | 合规处罚 |
| **反套现** | 券不得变相兑现，需监控异常核销 | 核销时段/地点/商品簇异常 → 风控（→ 08） | 平台被渠道套利 |

> **一条工程纪律**：`budget_id`、`channel_txn_id`、`rule_ver`、`tax_amount` 这四个字段必须在**第一版 DDL 里**，不能等财务来要。它们都是**事后不可重建**的历史事实——同 §22.11 的锚点纪律，也是 [12 短链 · §12.8](12-shortlink-system-design.md) 那条「等出了账差再补字段，只能认损」的重复。

## 22.15 换挡与崩法：L0 → L5（1 万 → 1,000 万参与）

| 阶段 | 形态 | 参与规模/场 | **换挡信号（硬阈值）** | 代价 |
| --- | --- | --- | --- | --- |
| **L0** | 单库单表 + 同步发奖 + 券码唯一索引 | 1 万 | 第一次重复发放；或券池 5 分钟内被刷完 | 无（但 1 万就该有唯一键） |
| **L1** | **业务唯一键 + 状态机 + 库存 DB 条件 UPDATE + 幂等键** | 10 万 | ① 预扣与发放差 > 0.1%；② 发奖 P99 > 2 s | 状态机复杂度；DB 行锁 |
| **L2** | **Redis 预扣 + 异步发奖 + pending TTL 释放 + 幂等回补** | 50 万 | ① 开抢 QPS > 3 万；② 单 key Redis CPU > 70% | 最终一致，必须有对账 |
| **L3** | 库存分桶 16 + 网关排队 + 活动分库（一场一库） | 200 万 | ① 用户可见「重复/少发」> 0.05%；② 账差 1 h 内定位不了 | 分桶带来少发尾巴 |
| **L4** | **预算中心 + L1 实时对账 + 风控闸门 SDK + 预算灰度** | **1,000 万** | ① 单场 > 1,000 万参与；② 多活动共享预算池；③ 渠道 ≥ 5 家 | 对账成本、组织（需独立资金团队） |
| **L5** | 单元化 + 全局额度中心 + 多活动并发抢同一预算 | 千万+ | 单地域容量上限 / 跨地域预算一致性（→ [10 多活与单元化](10-multi-active-and-cell.md)） | 脑裂与写冲突 |

> **当前多数业务的落点是 L3。** 重点说 **L2 → L3 的临界点**：L2 之后你会发现 Redis 单 key 与「活动分库」成了两个新瓶颈——不是因为量大，而是因为**单场活动的所有请求天然指向同一个 `activity_id`**（超级热点）。这时正确的动作是**分桶（把物理热点打散）**，不是加机器。而分桶会带来「某桶余量为 0、别的桶还有货」的**少发尾巴**，必须配「跨桶再取一次」的兜底，否则用户看到「售罄」而实际还有 3,000 张。
>
> **不要跳级**：没有 `pending` 超时释放（L2）就上库存分桶（L3），僵尸预扣会在每个桶里累积，**最后的表现是「全部售罄但账上只发了 62%」**——这是最难查的一类事故，因为所有日志看起来都正常。

### 这个形态特有的崩法（不是「高可用」套话）

| 失效 | 长什么样 | 定位方法 | 预防 |
| --- | --- | --- | --- |
| **幂等键选在发放产物上** | 单用户多张券、券码各不相同、claim 各一条 | 按 `(activity,user)` group by having count>1 | 键 = 业务意图；PR 模板强制追问 |
| **僵尸预扣堆积** | 显示售罄但 `Σissued` 远小于 `Σdeduct` | `pending` ZSET 长度、`deduct−issued` 差 | pending TTL + 扫描释放 + `orphan_deduct` 告警 |
| **回补风暴** | 渠道故障 → 全量回补 → 恢复后重发 → 来回震荡 | `compensate` QPS 尖峰 + 库存曲线锯齿 | 回补也限流 + 故障期「冻结不发、不回补」 |
| **超发穿透预算** | 账上发放 > 预算 | 日终 `Σissued` vs `budget` | 预算预扣 + 超发硬阻断 + Lua/DB 双写校验 |
| **券码复用** | 同一券码两次核销 | 核销流水 `group by coupon_code having count>1` | 号段发号 + 唯一索引 + 墓碑 |
| **对账锚点缺失** | 有差异但无法逐笔定位 | `channel_txn_id IS NULL` 的 SUCCESS 计数 | 建模期埋 4 个字段（§22.14） |
| **活动停了队列还在发** | 活动 `ENDED` 但用户陆续收到券 | 队列消费延迟 vs 活动状态时间 | 消费端二次校验活动态 + 幂等 |
| **概率版本漂移** | 用户投诉「说好 10%」，实际 6% | `claim.rule_ver` 分布 vs 公示版本 | 概率随版本固化；改即新版本 |
| **降级链破坏不变量** | 同 claim 换了奖品，`stock_ledger` 出现两条 issue | ledger 按 claim 聚合看流水数 | 降级 = 新 claim 子单，不允许改本单 |

### 砍掉 90% 预算还能不能跑

机器从 60 台砍到 6 台、Redis 从 16 桶砍到 1 key、对账从实时砍到 T+1：

| 保留 | 砍掉 | 后果 |
| --- | --- | --- |
| **业务唯一键 + 状态机（含回补）** | 实时对账、预算中心、风控闸门 SDK | 账差从 5 s 发现变成 T+1 发现，认损上限升高 |
| **Redis 预扣 + pending TTL** | 16 桶、网关排队、发奖多实例 | 单 key 打满 → 开抢 30 s 内大面积 502，但**账不乱** |
| **channel_txn_id 锚点** | 图关系、模型、灰度发放 | 刷单靠「单主体上限 3 单」兜底（损失可控在 4%） |
| 券类 1% 超发容差 | 实物/现金的多渠道降级 | 用户能领到，财务侧偶有作废 |

> **结论：这个系统的必需品只有三样——业务唯一键、状态机（含幂等回补）、对账锚点。** 其余全是峰值、渠道数或成本驱动的优化。每次评审都问一遍「哪三个是必需品」，能砍掉一半的架构虚荣：**限流、排队、分桶、图关系、模型，全都不是必需品——它们只决定「用户体验」和「拦截率」，而唯一键/状态机/锚点决定「账对不对」。**

## 22.16 十分钟答题卡

被要求现场设计「活动领券/发红包/积分奖励」时，按这个顺序讲，**不要从「我用 Redis 扣库存」开始**：

```
1  量级    1,000 万参与 / 3,000 万请求 / 开抢 20 万 QPS / 券池 200:1 的命中比
2  真问题  幂等 + 防刷 + 对账三件事；9 个时序分支里 8 个与发钱无关
3  领域    六实体；Claim 是幂等主体（唯一键），Stock 是库存不变量，Activity 是闸门
4  幂等    键 = (activity, user, round) 唯一索引裁决；★ 券码不能当键；状态机前置防重复推进
5  库存    Redis Lua 预扣（-1 售罄 / -2 重复都算受理）→ DB 落账 + ledger → 幂等回补
6  取舍    现金/实物不可超发（容差 0），券可超 1%，积分可超 2%——按「可追回性」分裂
7  时序    预扣挂掉 → pending TTL 30 s 扫描释放；回补 → DB 状态机行数=1 裁决幂等
8  发奖    超时未知→查状态不重发；明确失败→立回补+降级链（新子单）；回调丢→对账兜底
9  防刷    只给 verdict/report/snapshot 三个接口，规则去 08；单主体上限是产品决策（省 96%）
10 对账    预算/预扣/发放/核销/核销失败 五口径 + 三条恒等式 + claim_id 与 channel_txn_id 贯穿
11 停机    闸门停 / 冻结发奖 / 作废回滚；★ 只能停在合法状态（DISPATCHING 必须持久化）
12 必备    业务唯一键、状态机含幂等回补、对账锚点——其余都是量级驱动
```
