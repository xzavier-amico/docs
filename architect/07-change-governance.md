## 07.1 引子：两次「没人提交代码」的故障

### 事故一：把超时从 3s 改成 300ms（2026-05-14）

大促前第二次演练。值班同学发现结算下游的 P99 抖到 800ms，判断是「某个慢依赖拖住了整条链路」，于是在配置中心把 `rpc.client.default.timeout` 从 `3000ms` 改成 `300ms`——**语义上完全正确的一次操作**：让慢的快点失败，别拖垮线程。

问题在于这个 key 是**全局默认**，被 37 个服务引用；300ms 低于库存服务在大促水位下的真实 P99（620ms）；而库存服务的 5xx 只从 0.2% 涨到 31%，因为**超时后重试成功的请求被记账为成功**，所以最先报警的不是它。

| 时间 | 事件 | 数据 |
| --- | --- | --- |
| 20:41:00 | 改 `rpc.client.default.timeout` 3000ms → 300ms，单条配置**无灰度、无预演**直接发布 | 1 个 key，37 个服务引用 |
| 20:41:06 | SSE 推送全量生效，无分段、无观察窗口 | 2,140 个实例 |
| 20:43 | 库存服务 5xx 0.2% → 31%，客户端重试把请求放大 2.4 倍 | 库存 QPS 4.2 万 → 10.1 万 |
| 20:47 | 订单创建失败率 3% → 44%，加购大面积失败 | 每分钟 4,800 单失败 |
| 20:52 | SLO 燃尽告警：订单创建成功率跌破 99%，SRE 开始翻**发布记录** | 代码侧当天 0 次发布 |
| 21:08 | 有人怀疑配置，做配置快照 diff（28 个快照逐条比对） | 定位耗时 16 分钟 |
| 21:09 | 回滚配置快照，6 秒生效；但积压的 11 万重试请求排队排了 11 分钟 | — |
| 21:20 | 指标恢复 | 全程 **39 分钟** |

| 受影响项 | 数值 | 算式 |
| --- | --- | --- |
| 失败订单 | 18.7 万 | 4,800 单/分 × 39 分 |
| 失败加购 | 41 万次 | — |
| 被放大的下游调用 | 1,900 万次 | 18.7 万 × 重试 2.4 次链式放大 |
| 连带超时的业务线 | 6 条 | 共用同一份 client 默认配置 |
| 客诉 / 券补偿 | 1,340 单 / 约 180 万元 | — |

**根因不是「改错了值」，是四条护栏同时缺失**：① 配置没有分段（一次推送即 100%）；② 没有语义校验（新值低于下游实测 P99 的 1/2 应当拦截或强确认）；③ 没有爆炸半径预演（37 个引用方在发布界面上不可见）；④ 配置变更没有进「发布看板」，定位只能靠人肉 diff。对照 `llm/43 · §43.3` 的七道关：这次变更只走了「写入 → 推送」两道。

### 事故二：一个两年没人敢关的开关（2026-04）

`enable_pricing_v2` 建于 2024-03，本意是一个为期两周的发布开关。

| 时间 | 事件 | 状态 |
| --- | --- | --- |
| 2024-03-18 | 新计价引擎上线，开关灰度 5% → 100%，12 天走完 | 双分支并存 |
| 2024-04-02 | 全量后保留开关「以防万一」 | `flag=true` 全局 |
| 2024-09-11 | 一个大客户投诉计价异常，值班把该租户单独置 `false` 回退旧算法，**事后没改回来** | 1 个租户 = 3.4% GMV |
| 2025-06 | 代码规范新增「v1 分支禁止改动」（因为没人敢碰），v1 成为 1,412 行不可读的禁区 | 两套逻辑永久分叉 |
| 2026-04-08 | 合规需求「跨境订单新增税费口径」，开发只改了 v2 分支 | 测试也只在 v2 上跑 |
| 2026-04-19 | 财务对账发现该租户 11 天税费少计 | **320 万元** |
| 2026-04-20 | 决定关闭开关统一 v2，发现 v2 从未在「先款后货」场景验证过，无人敢签 | 开关关不掉 |

| 受影响项 | 数值 |
| --- | --- |
| 开关存活时长 | 738 天（设计寿命 14 天，超期 52 倍） |
| 受影响租户 | 1 个（占 GMV 3.4%，但占高客单订单 11.2%） |
| 错账窗口 | 11 天，税费少计 320 万元 + 更正申报成本 |
| 双分支代码 | v1 1,412 行 + v2 1,690 行，其中 61% 逻辑重复但不完全等价 |
| 该服务现存开关 | 37 个，其中 11 个已过 `expires_at` |

两次事故正好是本篇的两半：**第一半是"变更没有分段"，第二半是"变更没有退场"**。前者靠灰度与校验解决，后者靠开关的寿命管理解决，而它们共同的敌人是同一个幻觉——「这次改动很小」。

## 07.2 到底是什么：四个属性，缺一个就不叫变更治理

**精确定义**：变更治理是一套让线上行为的改变同时具备四个属性的机制。

| 属性 | 判据（可验收） | 反例（看起来像，其实不是） |
| --- | --- | --- |
| **可枚举** | 能回答「昨天 14:03 线上是哪一版」——变更单号、改前值、改后值、操作人、影响对象清单 | 「有审计日志」但只记 `updated policy`，不记改前改后 |
| **可分段** | 变更能只作用于一部分对象，且扩量不改分流结果 | 蓝绿部署：两套并存，但没有「先 5% 观察」的能力 |
| **可观测** | 分段内外的指标能在同一窗口对比 | 有新版本看板，但没有同窗口的对照组基线 |
| **可撤销** | 撤销耗时 ≪ 发现耗时（经验值：≤ 1/10） | 「回滚 = 再发一版」，25 分钟；而发现问题用 3 分钟 |

四个反例再点一次，因为它们最常被当成治理**已具备**：**蓝绿不是治理**（它是部署形态，缺分段观测）；**回滚脚本不是回滚**（若依赖重新部署，它就退化成一次新变更）；**开关不是治理**（无主无期的开关就是本篇事故二）；**审批不是治理**（审批只防「乱改」，完全不防「改错」——事故一的值是审批人自己批准的）。

### 唯一真问题

> **最容易出事的变更是配置和 schema，不是代码；而灰度最难的不是比例，是"灰度对象选错了"——比例 5% 也可能命中 100% 的核心客户。**

这句话有两半，各自推出的设计完全不同：

| 从真问题推出的约束 | 推出的设计 |
| --- | --- |
| 配置和 schema **没有编译期**，错误只能在运行时暴露 | 校验前移（静态 + 语义 + 影响面预演）+ 分段观测，见 §07.4 |
| 爆炸半径由**引用关系**决定，不由「改了几行」决定 | 每次变更先算受影响对象清单，见 §07.4、§07.13 |
| 风险的计量单位是**客户/业务对象**，不是 QPS | 分流键必须选业务对象维度，禁用随机与地域，见 §07.5 |
| 一个业务对象**不能横跨两侧**，否则账永远对不平 | 灰度 token 全链路透传 + 写入时落章，见 §07.6 |
| 回滚必须快于发现，否则护栏只是心理安慰 | L1 改路由/开关秒级生效，禁止用部署做回滚，见 §07.8 |

## 07.3 量级与预算：变更本身就是一笔可算的账

不许用「变更很危险所以要少变更」这种无信息表述。先把变更量、事故占比、延迟账算出来。

```
【变更频率（某交易平台 2026 Q1 实测，按变更单计）】
  代码发布        34 次/天   （其中 61% 是"只改配置/常量"的 commit）
  配置推送       312 次/天   ← 是代码的 9.2 倍
  策略规则        41 次/天   （风控名单、限流阈值、路由权重）
  依赖版本         1.3 次/天
  DB schema        0.7 次/天
  基础设施         1.8 次/天

【事故归因（2025 全年 187 起 P1/P2）】
  与变更相关      141 起（75.4%）
  ├ 配置类         61 起（32.6%）← 最高
  ├ 代码类         47 起（25.1%）
  ├ schema 类      18 起（ 9.6%）
  └ 依赖/基础设施  15 起（ 8.0%）

【三个延迟的实测中位数】
  发现延迟   配置 7 分钟 / 代码 14 分钟（配置没有发布看板反而靠告警更快？不，是配置类事故更"响"）
  定位延迟   配置 22 分钟 / 代码  9 分钟 ← 关键差异：代码有镜像 diff 与发布记录
  回滚延迟   配置 6 秒   / 代码 17 分钟（含构建、滚动、探针稳定）
```

于是损失可以用一条式子估：

```
损失 ≈ 受影响对象数 × 单对象期望损失 × (发现 + 定位 + 回滚) 时长 × 退化幅度
```

代入事故一：`18.7 万单 × 9.6 元/单 ≈ 180 万`（券补偿口径）。若同样的变更**先 5% 灰度、观察 15 分钟**：

```
受影响订单 = 4,800 单/分 × 5% × 15 分 ≈ 3,600 单   → 约 3.5 万元，差 51 倍
```

> 所以本篇的第一个结论是反直觉的：**配置类变更的正确策略不是"加审批让它变慢"，而是"加校验让它变准 + 加分段让它变小"**。审批拦不住事故一（值班有权批），而语义校验（`300ms < 库存 P99 620ms × 0.5` → 拒绝）能拦住。

另一笔必须算的账是**治理强度与变更频率的倒挂**，这是所有团队的默认状态：

| 变更类别 | 频次 | 现有护栏 | 常缺的护栏 | 一次错误的平均代价 |
| --- | --- | --- | --- | --- |
| 代码 | 34/天 | CI、review、单测、金丝雀、镜像回滚 | 无 | 中 |
| **配置** | **312/天** | 一条审计日志 | 校验、预演、灰度、回滚演练 | **高（全站瞬时）** |
| 策略规则 | 41/天 | 双人复核 | 离线回放、误杀率指标 | 高（影响准入与钱） |
| DB schema | 0.7/天 | DBA review、变更窗口 | 影子读、校验和、回滚 DDL 预案 | 极高且不可逆 |
| 依赖版本 | 1.3/天 | 安全扫描 | 传递依赖 diff、预热环境 | 中 |

**倒挂的判据：护栏最少的那个类别，恰好是频次最高、爆炸半径最大的那个。** 这就是本篇要修的东西。

## 07.4 形态怎么选①：变更分类矩阵（本篇核心表）

不要用一张「上线 checklist」通吃所有变更。八类变更的爆炸半径与可逆性差两个数量级，护栏必须分档。

| 变更类别 | 爆炸半径 | 可回滚性 | 验证手段 | 审批级别 | 最常见的崩法 |
| --- | --- | --- | --- | --- | --- |
| **代码**（业务逻辑） | 按流量口径，可 5%→25%→100% 收敛 | 镜像回滚 8~25 分钟（→ `llm/46`） | 单测 + 集成 + 灰度护栏 + 影子 | 单人（发布负责人）；涉钱涉权双人 | 分支叠加后语义不等价 |
| **配置**（阈值/超时/开关/路由） | **全站瞬时**——默认推送即 100% | 秒级（改回快照 5~6s）；已发生的请求不可撤回 | 静态校验 + 语义校验（漂移倍数）+ 影响面预演 + **配置灰度 10%→50%→100%** | 高风险项双人 + 变更单；超时/限流/费率类**强制预演签字** | 单位错、全局 key 被 N 个服务共享 |
| **DB schema**（DDL/索引/类型/约束） | 全表 → 全库 → 全链路 | **不可撤**：回滚是新一次 DDL（15 分钟~数小时），数据不会自己回来 | expand-contract 双写 + 影子读 + 迁移校验和（→ [20 迁移](20-data-migration.md)） | 强制变更单 + DBA + 双人 + 排期窗口 | 直接加 `NOT NULL`、改类型、删索引 |
| **模型与 prompt** | 全租户，且**行为不可 diff** | 秒级（换 `release_id`） | 切片门禁 + 影子双跑 + 一致性率（→ `llm/42 · §42.4`） | 平台 + 业务双签；支付/合同场景与铂金租户单独签字 | 只测总体通过率；不锁快照 |
| **策略规则**（风控/限流/计费/权限） | 全站或全租户，直接作用在「钱」与「准入」 | 秒级可撤，但**误判已造成的拒绝/放行要人工修** | 历史流量离线回放 + 按租户灰度 + 拦截率与误杀率双指标（→ [08 风控](08-risk-and-antifraud.md)） | 双人 + 安全/财务会签 | 只看拦截率，不看误杀率 |
| **缓存 key 结构 / TTL / 序列化** | 所有命中该 key 的读路径；失效瞬间回源 | **不可撤**（旧格式数据已不存在），只能双 key 并行 | 双写 + 影子读比对 + 回源 QPS 压测（→ [04 读路径](04-read-path-and-cache-shape.md)） | 双人 + 必须提交「穿透预算」（回源 QPS ≤ 分片容量 × 0.6） | 单 key 混存两种格式 → 反序列化炸 |
| **依赖版本**（SDK/中间件/基础镜像） | 全实例，重启才生效 | 分钟级（重新部署），而重启本身是一次变更 | 预热环境 + 按实例灰度 + 传递依赖 diff | 双人 + 安全扫描前置 | 传递依赖静默升级、默认超时/连接数变了 |
| **基础设施**（网关/LB/K8s/网络策略/证书） | 全站，可能是「整体不可用」级别 | 分钟级~**不可撤**（证书吊销不可撤） | 变更演练 + 分 AZ 灰度 + 独立探针 | 强制变更单 + SRE + 双人 + 只在变更窗口执行 | 一次全 AZ 生效；探针配置错导致全摘流量（→ `llm/46 · §46.7`） |

### 变更风险矩阵：治理强度必须配在右上角

```
                              可撤销性
                  秒级可撤                      不可撤（回滚要修数据）
          ┌──────────────────────────┬──────────────────────────┐
   爆 大  │ ① 配置：超时/限流/开关     │ ② DB schema：DDL/索引    │
   炸     │ ② 策略规则：风控/计费       │ ③ 缓存 key 结构/序列化   │
   半     │ ③ 模型与 prompt 路由        │ ④ 基础设施：网关/网络     │
   径     │ ④ 灰度比例本身              │ ⑤ 计费公式/口径          │
   （全   ├──────────────────────────┼──────────────────────────┤
   站/    │ ⑤ 代码（蓝绿 + 灰标）       │ ⑥ 依赖版本（重启才生效）  │
   全客   │ ⑥ 配置灰度中的中间态         │ ⑦ 证书/密钥轮换           │
   户）   │                            │                          │
          └──────────────────────────┴──────────────────────────┘
              ▲ 你现在的护栏大多配在这一格（因为"能改回来"）
                    ▲ 真正需要双人 + 预演 + 排期的是右边两格
```

读图三句话：

1. **右上角 = 必须先证明安全再动手**（影子/双跑/预演 + 变更单 + 排期窗口）。它的代价不是钱，是**时间**，所以只能用在「一个月几次」的变更上。
2. **左上角 = 允许高频，但必须能秒回**（配置灰度 + 快照回滚 + 变更进大盘）。事故一就死在「它长得像左上角，实际打出了右上角的伤害」。
3. **左下角（代码）最被过度治理，也最不该过度治理**：它的可逆性最好（镜像回滚 17 分钟，可先切 5%），所以正常代码应该**提高发布频次、缩小单次改动**，而不是加审批。

## 07.5 形态怎么选②：灰度的四种维度，与"选错对象"的三次翻车

### 四种灰度维度

| 维度 | 粒度 | 适合的变更 | **盲区（会漏掉什么）** |
| --- | --- | --- | --- |
| **用户 / 租户**（业务对象） | 1 个客户、1 个商户、1 个门店 | 计费、权限、结算、对外契约 | 内部白名单客户不代表真实长尾；单租户流量小则样本不足 |
| **流量比例**（一致性哈希） | 0.1%~50%，按对象哈希 | 绝大多数无状态读路径 | 比例是流量口径：5% 流量里可能一个核心客户都没有，也可能全是 |
| **地域 / 机房 / AZ** | 单 AZ、单地域、单单元 | 基础设施、连接层、多活切流（→ [10 多活](10-multi-active-and-cell.md)） | 小规模业务里「一个地域」= 100% 用户；跨地域数据不一致会污染结论 |
| **请求特征**（设备/版本/渠道/端） | App 版本、SDK 版本、渠道 | 客户端协议、渲染、埋点 | **最新版本用户往往是最活跃、付费最重的群体**；渠道里常有单一大客户 |

### 三个反例：比例对了，对象错了

| 反例 | 做法 | 为什么错 | 正确做法 |
| --- | --- | --- | --- |
| **① 按 userId 尾号灰度支付链路** | 灰度 5%「用户」 | 一个商户的订单一半走新逻辑、一半走旧逻辑 → 商户日结平不了账，灰度期数据不可用 | 分流键取 **`merchant_id`**，保证「钱的对象」原子；用户维度只用于**读**路径 |
| **② 按地域灰度价格策略** | 上海机房先上 | 上海贡献 62% GMV → 名义 25% 机房，实际 62% 收入；且价格策略跨地域必须一致（否则同一用户切换网络看到两个价） | 价格类变更只能按**租户/合同**灰度，且必须能一屏回滚 |
| **③ 按 App 版本灰度推荐/结算** | 新版本客户端 8% 用户 | 新版本用户 100% 是活跃用户，其中包含**全部 100 个核心客户里 的 94 个**；比例 8%，风险敞口接近全量 | 按 `tenant_id` 一致性哈希；版本维度只用于「新功能可见性」，不用于「算法/资金」变更 |

> **这三条合起来是一条硬规则**：**分流键必须是"风险的最小不可分割单元"**。钱按商户切、权限按租户切、算法按用户切、渲染按版本切。选错键的代价不是「多影响 5%」，而是「**事后无法归因，也无法只回滚一半**」。

### 选键的正确顺序（评审必问）

```
风险的最小单元是什么？（钱/权限/合同 → 租户或商户；体验 → 用户；协议 → 版本）
        │
        ├─ 该单元在系统里全局唯一且不可变吗？ ── 否 ──▶ 用一个"上级稳定 ID"（tenant_id）
        │          是
        ▼
  流量是否足以在 15 分钟内积累 min_samples？ ── 否 ──▶ 改维度（租户白名单 + 长窗口），不要提高比例
        │          是
        ▼
  → 固定 salt 一致性哈希（扩量只改 percent，保证"先灰的还在灰里"）
```

## 07.6 会在哪崩①：分流一致性——最贵的一类事故是"跨侧"

灰度可以接受「一半人用新、一半人用旧」，**绝不能接受「同一个人一半新一半旧」**。后者不是灰度，是数据分叉。

### 一致性的三个层级

| 层级 | 要求 | 违反后的症状 | 强度 |
| --- | --- | --- | --- |
| **请求级** | 一次请求内的 N 次下游调用同侧 | 价格用新算法、库存用旧口径 → 下单即超额 | 必须 100% |
| **会话级** | 一个会话/购物车生命周期同侧 | 加购在 A 组、下单在 B 组 → 优惠券失效、库存扣不动 | 必须 100% |
| **业务对象级** | 一个订单/合同/账单从创建到退款同侧 | 退款按旧规则算 → 账对不平（本篇事故二） | 必须 100%，含异步 |

### 灰度 token 透传链路

```
 客户端（无灰度知识）
   │  ① 入口只判一次：bucket = hash(tenant_id | salt) % 10000
   ▼
 [接入网关] ──② 签发并写死灰标（此后全链路只读不改）──┐
   │   Header: X-Gray-Plan: p12                           │
   │           X-Gray-Bucket: NEW                          │
   │           X-Gray-Token: t_004411/NEW/v3  ← 可验签      │
   │                                                       │
   ├─▶ [BFF / Java 应用]──③ 放进 RPC metadata 与 MDC ──────┤
   │         │                                             │
   │         ├─▶ [价格服务]  读 token → 新算法               │
   │         ├─▶ [库存服务]  读 token → 新扣减口径            │
   │         └─▶ [优惠券]   读 token → 新叠加规则             │
   │                                                       │
   ├─▶ [MQ 生产者]──④ 消息头带 producer_version + gray_token
   │         │
   │         └─▶ [消费者组] 按 token 选处理分支；
   │                        无 token 走"旧侧消费者"（安全默认）
   │
   └─▶ [定时任务 / 对账]──⑤ 按业务对象反查落章
             SELECT bucket FROM gray_stamp WHERE obj_id = ? AND plan = 'p12'
             └─ gray_stamp(obj_id, plan, bucket, created_at) 只写不改
```

**这张图有三个不能省的约束**：

1. **只在入口判一次**。链路中间任何节点重新算哈希 = 换了分桶输入 = 必然分叉。
2. **落章要持久化**（`gray_stamp` 或业务表上的 `gray_plan` 字段）。异步链路和定时任务没有请求上下文，只能靠这张表反查；事后复盘「这笔单走的是哪一侧」也只能靠它。
3. **签 token**。否则前端传一个 `X-Gray-Bucket: NEW` 就能把自己塞进灰度侧（尤其当灰度侧有优惠时，这变成一个可套利的漏洞）。

### 无法透传时的四种降级做法

| 场景 | 降级做法 | 代价 |
| --- | --- | --- |
| 三方回调（支付/物流） | 落章反查：回调里带业务单号 → 查 `gray_stamp` → 决定分支 | 多一次读；必须保证落章先于回调（写入时同事务落章） |
| 老客户端 / 老 SDK | 按 `tenant_id` 哈希兜底（不用 userId，不用随机） | 粒度变粗，扩量要更谨慎 |
| 消息里没 token（历史积压） | 消费端**只走旧侧**并打点计数；不打点直接猜是最坏的选择 | 灰度期积压消息不能用新逻辑处理（正确，不是缺陷） |
| 链路无法改造（如数据库触发器、老 job） | 把该路径**整体排除**在灰度之外（走旧侧直到切换日），并在切换日用双写窗口 | 该路径无法灰度，只能一次性切 → 必须走影子验证 |

### 骨架：Java 灰度分流器（Spring，28 行）

```java
@Component
public class GrayRouter {
    private final FlagSnapshot snapshot;      // 原子快照，无网络调用（见 llm/43）

    /** 一次判定、全链路复用：入口调用，结果写 header + MDC + 消息头 */
    public Bucket route(GrayContext ctx) {
        GrayPlan plan = snapshot.activePlan("p12");
        String key = plan.stickyKeyOf(ctx);            // tenant_id / merchant_id / order_id
        if (key == null) return Bucket.OLD;            // 无键 = 保守走旧侧，禁止就地算哈希
        if (plan.alwaysExclude(ctx, key)) return Bucket.OLD;  // 铂金/支付/合规场景永久排除
        Bucket pinned = plan.pinnedOf(key);            // 落章结果优先：保证业务对象级一致
        if (pinned != null) { ctx.stamp(pinned); return pinned; }
        long h = Hashing.murmur3_128().hashString(key + "|" + plan.salt(), UTF_8).asLong();
        Bucket b = Math.floorMod(h, 10_000L) < plan.percentBasisPoints() ? Bucket.NEW : Bucket.OLD;
        ctx.stamp(b);                                  // 写 header + MDC + gray_stamp（异步）
        return b;
    }

    /** 下游读取：只读上下文，绝不重算 */
    public Bucket current(GrayContext ctx) {
        Bucket b = ctx.fromHeaderOrMdc();              // 缺失即 OLD
        return b == null ? Bucket.OLD : b;
    }
}
```

> 关键在 `current()`：**全链路只有入口有"计算"的资格，其余地方只有"读取"的资格**。把这条写成 ArchUnit 规则（`route(` 只允许在 Gateway 包被调用），比分流算法本身重要得多。

## 07.7 会在哪崩②：灰度与三种状态化组件的冲突

无状态服务灰度很干净：切过去、切回来。但只要路径上**有状态**，灰度就变成「两个版本共享一个世界」，冲突必然发生。这三节必须单独写，因为它们各自的解法和「按比例切流量」完全无关。

### （1）与缓存的冲突：切换瞬间读到对方写的 key

| 介质 | 冲突形态 | 具体例子 | 解法 |
| --- | --- | --- | --- |
| 本地缓存（进程内） | 各实例各自持有旧值，切换后长期不一致 | 实例 A 缓存 `price:sku123=99`，B 侧改成含税 109 | 变更前置**缓存版本号**进 key；或变更时广播失效 + 给实例加「接受本版本」标记 |
| 分布式缓存（Redis） | **同一 key 被两侧写入，互相污染** | A 组写成本价、B 组写含税价，读侧无法分辨 | key 前缀带灰标：`v3:p12:NEW:price:sku123`；灰度期**不共享**热 key |
| CDN / 边缘 | 边缘缓存跨侧复用 | 返回 301 或长 `max-age` 把「临时灰度」变成「永久」（→ [12 短链 · §12.7](12-shortlink-system-design.md)） | 永不缓存可回滚内容；必须缓存时 key 带 plan |

**切换时刻的正确姿势（顺序不能换）**：

```
1. 摘流：把待切实例从 LB 摘掉（不等它自己失败）
2. 等温：等它本地缓存与 Redis 写入活动停止 ≥ 2 × 最长 TTL 的一半
3. 换版本：重启/换标（此时无新写入，旧值自然过期）
4. 回填：按新版本预热一层热 key（打 1% 流量）
5. 接流：分批接回，每批 5%，间隔 > 客户端重试窗口
```

反例：**「改缓存结构时两边同时读写同一个 key」**——这是本篇评分里最常被抓的答法。正确做法永远是 **双 key 并行**（旧 key 写旧格式、新 key 写新格式、读侧按灰度标记选 key），等 100% 之后停写旧 key，再等一个 TTL 删掉。

### （2）与长连接的冲突：切流时的连接重建风暴

长连接（WebSocket/SSE）没有「按请求分流」这回事——**连接一旦建立就绑定了版本**。于是「灰度 5%」实际是「切换时 5% 的连接被踢」，而客户端往往同时重连。

```
10,000 个连接同时重建 →
  TLS 握手 3~5ms × 10,000 = 30~50 秒的网关 CPU 时间
  + 鉴权查库 10,000 QPS 突发（平时 40 QPS）
  + 重连风暴二次打到接入层 → 触发限流 → 更多客户端重试
```

| 做法 | 结果 | 正确做法 |
| --- | --- | --- |
| 一次性踢掉灰度侧的连接 | 重连风暴，接入层 P99 从 20ms 涨到 2s | **分批排水**：每批 ≤ 5%、间隔 > 客户端退避窗口（通常 30s） |
| 服务端直接 RST | 用户看到「网络错误」，会话丢失 | 主动发 `server_draining` 帧 + `reconnect: true` + `Last-Event-ID`（→ `llm/46 · §46.7`） |
| 灰度比例作用在「连接」上 | 用户每重连一次可能换一侧 → 会话状态在两个版本间摇摆 | 灰度标记**绑定在用户/会话**上，连接建立时按对象判定，重连仍同侧 |
| 新版本只接受新连接 | 老连接永远不换 → 灰度永远到不了 100% | 给老连接设**生命周期上限**（如 6 小时强制排水一次） |

**结论**：长连接的灰度单位不是「连接」，是「**用户 + 时间窗**」。要预留「排空期」：100% 之前，新旧两版必须能同时处理同一会话（协议向后兼容），否则会话会在重建时丢失。

### （3）与长事务 / 异步任务的冲突：已投递的消息由新版本消费

这是最隐蔽的一类：变更那一刻，队列里躺着 40 万条「由旧版本产生」的消息，而消费者已经升级。

| 异步形态 | 冲突 | 症状 | 解法 |
| --- | --- | --- | --- |
| MQ 消息 | 消息体字段按旧口径，新消费者按新口径解读 | 金额少算 1 位小数、状态映射不到 | 消息带 `producer_version`；消费端**按消息头选处理分支**，两条分支至少共存一个「最长积压时长」（如 24 小时）→ `eng/24` |
| 定时任务 / 批处理 | 任务被灰度侧实例捞起，但数据是另一侧写的 | 对账批量失败、补偿放大 | 任务按数据侧分片：`WHERE gray_plan = 'OLD'` 与 `NEW` 两组独立任务 |
| CDC / binlog 消费 | schema 已 expand，老记录没有新字段 | 反序列化炸 / 默认值污染 | expand-contract：先加可空字段 → 双写 → 回填 → 才允许读新字段（→ [20 迁移](20-data-migration.md)） |
| 长事务（跨请求） | 事务中途换版本 | 上下文里有旧版计算结果 | **版本钉子**：事务开始时钉 `plan` 与 `release_id`，全程不换（→ `llm/42 · §42.4`「Run 内版本粘性」） |

> 这条铁律请写在发布清单第一行：**「本次变更是否改变了消息/记录的解读方式？若是，则消费者必须双分支共存 ≥ 一个最长积压时长，且必须能在 5 秒内切回旧分支。」** 不满足，就只能走停机窗口或影子验证。

## 07.8 会在哪崩③：自动回滚不能只看错误率

### 三轴判定表

只看错误率的护栏有两种死法：**漏杀**（事故一里超时后重试成功，5xx 几乎没动）和**误杀**（下游抖 30 秒就把一个正确变更回滚掉，团队于是关掉护栏）。

| 轴 | 指标 | 窗口 / 最小样本 | 越线动作 | 为什么必须有 |
| --- | --- | --- | --- | --- |
| **业务** | 下单成功率、支付成功率、转化率、客单价、退单率 | 15m / ≥300 单（`min_samples`） | 降 2pp → freeze；降 5pp → rollback | 系统全绿但业务崩，是变更事故的典型长相 |
| **延迟** | P99、TTFT、队列等待时长 | 10m / ≥1,000 次 | +20% → freeze；+50% → rollback | 事故一的真实信号在这里（超时≠错误） |
| **饱和度** | 队列深度、连接数、下游 429 率、线程池占用 | 5m / 连续 3 点 | 任一 > 80% → freeze；> 95% → rollback | 它是「即将崩」的唯一提前指标 |

```
每 60s 采样（滑动窗口）
      │
      ▼
┌ 样本量 ≥ min_samples ? ──── 否 ──▶ 只 alert，不动手（防误杀 —— llm/42 事故 F）
│        │ 是
│        ▼
│ ┌ 三轴任一越线 ? ─────────── 否 ──▶ 继续观察；到点允许扩量
│ │      │ 是
│ │      ▼
│ │ ┌ 对照组（灰度外）也变差 ? ── 是 ──▶ 不是变更的锅 → 转事故流程；
│ │ │      │ 否                          ▲ 此时回滚只会丢人丢时间
│ │ │      ▼
│ │ │ ┌ 越线幅度分档
│ │ │ │   轻微 ──▶ alert    （通知值班，人工判断，不阻断）
│ │ │ │   中等 ──▶ freeze   （冻结扩量 + 30 分钟观察；可手动放行）
│ │ │ │   严重 ──▶ rollback （L1 改路由/开关，5 秒生效）
│ │ │ │              │
│ │ │ │              ▼
│ │ │ │      回滚后三件事：① remediation_queue 修已产生的坏数据
│ │ │ │                      ② 同 scope 2 小时禁止再发（防"回滚→重发→又炸"）
│ │ │ │                      ③ 开单复盘，护栏阈值本身也要复盘
```

### 回滚本身也是一次变更

这是最容易被跳过的一段。回滚不是「按撤销键」，它是**把线上从 B 状态拉到 A 状态**，而 A 状态可能已经不在最佳状态了。

| 回滚自带的风险 | 机制 | 后果 | 缓解 |
| --- | --- | --- | --- |
| **旧版本也坏了** | 回滚目标 = 上一次未经本次验证的变更；或旧版本已无人维护 | 回滚后仍然失败，且团队陷入「没有可回退点」的恐慌 | 保留 N-2 可回滚点；每月演练一次回滚（不是演练发布） |
| **数据已被写坏** | 回滚只改代码路径，不回改数据 | 回滚后指标恢复，第二天财务发现错账（本篇事故二） | `remediation_queue` 按 `release_id/plan` 捞坏数据重放或补偿（→ `llm/42 · §42.4`） |
| **回滚触发第二次流量抖动** | 缓存/长连接/队列又要切一次 | 故障时长翻倍 | 回滚也走「摘流 → 等温 → 换版本 → 分批接回」 |
| **回滚与扩量打架** | 自动化还在放量，人工在回滚 | 线上状态随机 | 回滚必须能**抢占**：置 `plan=ROLLED_BACK`，扩量控制器立即失效 |
| **回滚也有生效窗口** | 配置推送 P99 5s、客户端缓存 60s | 「我回滚了但还是有人报错」 | 回滚后必须验证**覆盖率**（多少实例/客户端已生效），而不是只看「已提交」 |

> 一句话：**回滚的成本 = 一次变更的成本 + 数据修复的成本**。所以「能秒回」是必要条件，不是充分条件；写路径的变更必须同时准备「数据修复脚本」，否则它其实是不可回滚的。

## 07.9 怎么验证：影子 / 双跑 / 镜像对比

灰度能验证「不炸」，不能验证「对不对」。金额算错 1 分钱、排序差 3 个位置、权限多放 1 个人——这些都**不会让错误率动一下**。所以有一部分变更必须在用户看到之前，用真实流量对比出结论。

| 做法 | 怎么做 | 成本（人日 / 机器 / 钱） | 结论可信度 | 能验证写路径吗 | 必须做的场合 |
| --- | --- | --- | --- | --- | --- |
| **镜像（Mirror）** | 把线上请求复制一份打到新版本，结果丢弃 | 2 人日 / +30% 机器 / 低 | **高**（真实流量、真实比例） | ❌ 必须把写操作替换成 dry-run，否则把世界改了 | 协议/网关/序列化层变更；影子读缓存结构 |
| **双跑/旁路（Dual-compute）** | 同一次请求里新旧两套逻辑都算，只返回一套 | 3~5 人日 / +10% CPU / 中 | **最高**（同输入同上下文，可逐字段 diff） | ⚠️ 只验证计算，不验证副作用 | 计价、费率、税费、配额、风控打分、排序函数 |
| **影子（Shadow）** | 采样一部分请求在新版本上完整跑一遍（只读替身） | 5~8 人日 / 独立影子环境 / 高（LLM 场景可达 $2 万/次，→ `llm/42 · §42.4`） | 中高（采样可能漏长尾切片） | ❌ 显式禁止 | 换模型/prompt、索引重建、schema 迁移后的读路径 |
| **离线回放** | 用历史流量重放（T+1，无实时性） | 1~2 人日 / 低 | 中（无法覆盖「今天才出现的流量形态」） | ✅ 可在影子库上验证写 | 风控规则、策略变更，变更频繁的场景 |

**什么时候必须做影子（不可跳过）**：

1. **改变钱的计算**（计价、折扣、税费、结算）→ 双跑 + 逐笔 diff，差异率必须 < 0.01% 且每笔差异可解释；
2. **改变准入判定**（风控、权限、额度）→ 离线回放 + 误杀率对比，禁止只凭灰度；
3. **改变数据格式**（schema、缓存序列化、消息体）→ 影子读 + 校验和；
4. **换模型 / 换排序 / 换召回**（行为不可 diff）→ 影子 + 一致性指标 + 切片（→ `llm/42`）；
5. **一次性、影响全部租户且不可回滚**（基础设施拓扑、证书）→ 演练 + 单 AZ 镜像，而不是直接上。

> 成本纪律：**双跑 = 一次性的工程成本，影子 = 每次变更的持续成本**。所以对「每月一次」的变更用双跑（一次投入长期收益），对「每周多次」的变更只能靠离线回放 + 灰度护栏——指望每次都影子，最后一定因为太贵而整套被跳过。

## 07.10 换挡信号：特性开关的债务治理

开关是变更治理最锋利的工具，也是最容易腐烂的资产。腐烂的判据很具体：**当你不敢关它的时候，它已经变成了生产代码的一部分。**

| 开关类别 | 用途 | 存活期上限 | 到期后必须发生什么 | 谁負責 |
| --- | --- | --- | --- | --- |
| **发布开关**（Release） | 新逻辑上线期间遮挡未完成部分 | **≤ 14 天**（含灰度与观察） | 固化到目标分支 → 删除另一分支 → 删 flag | 开发（发起人） |
| **实验开关**（Experiment） | A/B 实验分流 | ≤ 1 个实验周期（**≤ 6 周**，含显著性所需样本） | 出结论 → 固化赢家 → 删 flag 与实验配置 | 产品 |
| **权限开关**（Entitlement） | 套餐/合同能力差异（付费才有） | **长期**，但必须绑定「合同条款或套餐定义」 | 每季度复核：是否仍被合同引用；无引用即删 | 商务 + 平台 |
| **降级开关**（Kill switch） | 故障时关掉某能力 | **永久**，但必须有「演练证据」 | 每季度演练一次，演练失败视为 P2 | SRE |

### 债务的量化与清理流程

```
【度量（每月跑）】
  flag_total           单服务 > 40 个 → 免新功能开发一周做清理（"开关清账周"）
  flag_overdue         超过 expires_at 的比例 > 30% → 冻结新增 flag 权限
  branch_coverage      flag 分支的测试覆盖率 < 80% 的分支 = 事实上的第二套生产逻辑
  uncloseable          "不敢关"的 flag 数（每次评估 ≥1 就视为严重）→ 立即排期
```

| 步骤 | 动作 | 判定 | 谁签 |
| --- | --- | --- | --- |
| 1 冻结 | 该 flag 14 天内禁止修改取值（只观察） | 这段期内无回滚需求 | 开发 |
| 2 取证 | 查 `flag_evaluation` 日志：两侧各有多少真实调用 | 有一侧 30 天调用量为 0 → 死代码 | 开发 |
| 3 固化 | 把目标分支的代码**内联**到主路径，删除另一分支 | 单测与集成测试在「无 flag」状态下全绿 | 开发 |
| 4 摘除 | 删 flag 定义、删配置项、删灰标分支、删文档 | 全仓 `grep flag 名` 为 0 | 开发 + 平台 |
| 5 归档 | 审计记录保留（谁、何时、为什么删） | 可回溯 | 平台 |

**两个不可清理的例外**：降级开关（它存在的意义就是长期）、被合同引用的权限开关。除此之外，任何「以防万一先留着」的开关，都必须写一个 `expires_at`——本篇事故二的 738 天，就是从一个「以防万一」开始的。

### 开关求值的四条硬约束（Go 骨架，22 行）

腐烂的开关在代码里长得一样：一个布尔变量、几个 if。要让它可治理，求值函数必须**纯函数化**并显式满足四个约束：读不到就关（安全默认）、kill switch 最高优先、过期即视为默认、分桶键取业务维度。

```go
// Eval 必须是纯函数 + 有界耗时（< 1µs）+ 无网络调用；否则它自己就是故障点
func (e *Evaluator) Eval(f Flag, c Ctx) bool {
	snap := e.snap.Load()                       // ① 原子快照：读本地内存，绝不 RPC
	if snap == nil {
		e.metrics.Miss(f.Name)                  //    配置中心挂了 = 全部关闭，不是全部打开
		return f.SafeDefault
	}
	if snap.Killed(f.Name) {                    // ② kill switch 走独立通道，优先级最高
		return false
	}
	if v, ok := snap.Override(f.Name, c.Tenant); ok {
		return v                                // ③ 租户级钉死值（事故里"临时置 false"必须能查回来）
	}
	if f.ExpiresAt.Before(e.now()) {            // ④ 过期即降级为默认值 + 打点，逼你清理
		e.metrics.OverdueFlag(f.Name)           //    这条打点是"开关清账周"的唯一数据来源
		return f.SafeDefault
	}
	h := xxhash.Sum64String(f.Name + "|" + f.Salt + "|" + f.StickyKey(c))
	return h%10_000 < uint64(f.Percent)*100     // 桶键 = 业务对象，不是 userId+随机
}
```

> `Override` 这一条最容易被嫌"多余"，但它是事故二的直接解药：如果当初那次「临时把某租户置 false」被记录成一条**带到期时间的覆盖率异常**（1 个租户 = 长期停在旧分支），它会在 30 天后自动报警，而不是沉默 738 天。

## 07.11 变更日历与冻结期

冻结期的本质是：**在损失函数最陡的时段，把「变更风险」这个变量钉死。**

| 冻结类型 | 时间窗（示例） | 冻结范围 | 期间允许的紧急变更 | 审批链 |
| --- | --- | --- | --- | --- |
| **大促**（618/双 11） | T-7 ~ T+1（前后共 9 天） | 代码、schema、依赖、基础设施、价格策略 | 只允许「配置回退」与「关开关」（可秒回、可验证） | 值班 + 值班经理双签，事后 24h 内复审 |
| **月末结账** | 每月最后 3 个工作日 + 次月前 2 个 | 计费、结算、对账、报表相关的一切 | 只允许止血（关闭出问题的能力，不上新逻辑） | 财务 + 平台双签 |
| **财报窗口** | 季度结束后 10 个交易日 | 所有影响收入确认的变更 | 同月末结账 | CFO 办公室备案 |
| **重大发布/直播** | 事件前后各 24 小时 | 全站 | 仅 P1 止血 | 值班经理 |
| **周末与节假日**（无值班加强时） | 周五 18:00 ~ 周一 10:00 | 非配置类变更 | 配置回退、开关 | 单人（限已演练过的手段） |

### 冻结期允许的紧急变更：三条门槛

1. **手段必须是「可秒回」的**：配置回退、关开关、切路由。冻结期内**不允许发版**，因为发版本身的回滚要 17 分钟，等于在冻结期内引入两个风险。
2. **必须带观察窗口**：变更后 30 分钟内，须有一个人只看指标不做别的事；没有这个人，就不许改。
3. **必须 24 小时内补审**：冻结期审批是「先做后审」，但补审不通过要追责——否则冻结期会变成「免责期」。

### 反例：冻结期末尾的变更风暴

某团队大促冻结 10 天，解冻首日积压 87 次变更、3 起事故（占当月事故 43%）。**冻结不是「攒着」，因为攒出来的变更带着"必须今天上"的焦虑，反而更粗糙。** 正确做法：

```
解冻首日限速：每小时 ≤ 3 次变更，且只允许「低风险等级」（代码/配置可秒回类）
解冻次日：恢复常态，但当日变更总量不超过日均 1.5 倍
冻结期内：每天允许 ≤ 2 次「低风险 + 可秒回」的变更（保持团队手感，避免堆积）
```

## 07.12 灰度 vs 实验（A/B）：目标不同，纪律就不同

两者共用一套分流基础设施，但**目标相反**，所以几乎所有细节都不同。把两者混用是评审里最常见的概念错误。

| 维度 | 灰度（Canary） | 实验（A/B） |
| --- | --- | --- |
| **目标** | 求安全：尽快证明「它坏了」 | 求结论：可靠地证明「它更好」 |
| **分流单位** | 风险最小单元（租户/商户/地域），**不必随机** | 必须是**随机**且独立的单元（用户/会话），保证组间可比 |
| **比例** | 从 0.1% 起，按风险决定；可停在 5% | 由样本量反推（`MDD = sqrt(1.411/n)`，→ `llm/42 · §42.4`），常需 10%~50% |
| **时长** | 分钟~小时；越短越好 | 周级（覆盖完整行为周期），提前停会得出错误结论 |
| **指标** | **护栏指标**（错误率、延迟、饱和度、成功率） | **决策指标**（转化、留存、ARPU）+ 护栏指标 |
| **停止条件** | 任一护栏越线立即停 | 达到预定样本量；中途"偷看"必须用序贯检验，否则显著性是假的 |
| **失败代价** | 事故（影响真实客户） | 白跑（时间与机会成本） |
| **回落方式** | 回滚（撤掉新版本） | 结束实验、固化赢家或输家 |
| **可以中途改分流比例吗** | 可以（扩量，靠固定 salt 保证"先灰的还在灰里"） | **不可以**（改了组间就不可比，实验作废） |
| **能否用灰度流量做实验结论** | — | ❌ 不行：5% 的样本既不够显著，又因为扩量导致组内成分变化 |

**一句话区分**：**灰度想「快」，实验想「准」。** 所以灰度允许在 5% 上停 15 分钟就下结论（"不炸就行"），实验绝不允许；实验允许把 50% 用户放在新逻辑上跑 4 周（"为了显著"），灰度绝不允许（那是把风险敞口开到最大）。

**唯一一致的纪律**：两者都要求「分流键在变更期间不可变」，且都要求「业务对象不跨侧」。这条不满足，灰度和实验同时失去意义（§07.6）。

## 07.13 回滚预案矩阵：每类变更都必须有一行

发布单里最该有的是这张表。缺一行的变更，视为「不可回滚」——那就必须走冻结期之外的停机窗口。

| 变更类别 | 回滚手段 | 回滚耗时 | 是否丢数据 | 备注 |
| --- | --- | --- | --- | --- |
| 代码 | 切回上一镜像（蓝绿/滚动） | 8~25 分钟 | 否（除非新版本已写坏数据） | 保留 N-2 可回滚点 |
| 配置 | 回滚快照（单调版本，5~6s 生效） | **秒级** | 否 | 必须验证覆盖率，不是「已提交」 |
| 灰度比例/开关 | 改 `percent=0` / `kill_switch` | **1~5 秒** | 否 | kill switch 走独立通道（→ `llm/43`） |
| DB schema（加列/加索引） | 无需回滚（expand 阶段天然兼容） | 0 | 否 | 这是为什么必须 expand-contract |
| DB schema（删列/改类型/删索引） | 逆向 DDL 或从备份恢复 | 15 分钟~数小时 | **是（期间写入丢失）** | 需 DBA 值守 + 备份验证 |
| 模型 / prompt | 改 `release_id` 指回旧版 | 5 秒 | 否（已产生的输出不追回） | 需确认旧快照仍可用（→ `llm/42`） |
| 策略规则 | 回滚规则版本 | 秒级 | 部分（已误杀的请求需人工修） | 必须有「误杀名单补回」脚本 |
| 缓存 key 结构 | 双 key 并行 → 停写新 key → 等 TTL | 分钟级（受 TTL 支配） | 否 | 不能靠「改回代码」解决数据格式 |
| 依赖版本 | 重新部署旧版本 | 10~30 分钟 | 否 | 重启本身是一次变更，需分批 |
| 基础设施 | 反向变更 / 切回旧拓扑 | 分钟级~不可撤 | 视情况（证书吊销不可撤） | 必须分 AZ 灰度，禁止一次性全量 |

**这张表的用法**：发布单里填「本次变更属于哪一行、回滚耗时多少、谁执行、演练过没有」。填不出来 = 不许发。

## 07.14 十分钟答题卡

被问「你们怎么做变更治理/灰度发布」时，按这个顺序讲，不要从「我们有 Jenkins」开始：

```
1  量级    配置变更 312 次/天 vs 代码 34 次/天；变更相关事故占 75%，其中配置 32.6%
2  真问题  最容易炸的是配置和 schema；灰度最难的不是比例，是对象选错
3  分类    八类变更 × 爆炸半径/可逆性/验证/审批；治理强度配在"大半径 + 不可撤"那格
4  维度    用户租户 / 流量比例 / 地域机房 / 请求特征；分流键 = 风险最小不可分割单元
5  一致性  入口判一次 → token 全链路透传 → 写入落章（gray_stamp）→ 异步按消息头选分支
6  状态    缓存双 key 并行；长连接分批排水 + reconnect 帧；异步消息双分支共存 ≥ 最长积压
7  护栏    三轴（业务/延迟/饱和度）+ min_samples + 分级动作（alert→freeze→rollback）
8  回滚    回滚也是变更：N-2 可回滚点 + remediation_queue + 2h 冻结 + 覆盖率验证
9  债务    开关四类 + 存活期上限（发布 14 天/实验 6 周）；不敢关 = 已经烂了
10 冻结    大促 T-7~T+1、月末、财报期只允许"可秒回"的止血手段，24h 补审
```
