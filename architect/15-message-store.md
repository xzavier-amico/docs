## 15.1 引子：两起「数据都对、用户看到的都不对」的事故

**事故一：已读回执跑到「发出」前面（2025-02-18，某 IM）**

发号器用 Redis `INCR` 给每个会话分配 seq。当晚哨兵做了一次主从切换，新主节点从 AOF 恢复，**计数器比真实值落后了 3.7 秒**。

| 时间 | 事件 | 数据 |
| --- | --- | --- |
| 20:41:03 | Redis 主节点故障，哨兵切换，`conv:{id}:seq` 回退 | 落后 3,842 个号 |
| 20:41:12 | 新消息拿到**比历史更小**的 seq，与老消息的 seq 撞上 | 冲突 8,927 次 |
| 20:41:15 | 写入用 `ON DUPLICATE KEY UPDATE` 覆盖同 seq 行 | **8,927 条消息被覆盖 = 永久丢失** |
| 20:44 | 客服收到工单：「已读」气泡出现在「发出」之前 | 首批 63 单 |
| 20:52 | 客户端渲染倒序、空白气泡、红点数字跳变 | 2,140 个会话 |
| 21:06 | 定位：发号回退 + 拉取游标已越过回退区间 | 41,600 条**拉不回来** |
| 02-19 ~ 02-26 | 从客户端本地库反向对账补数据 | 只补回 63% |

根因不是「Redis 不可靠」，是三件事同时成立：**发号器允许回退**、**拉取用「游标之后」的语义把回退区间永久跳过**、**UI 用时间戳而不是 seq 排序**。

**事故二：撤回之后，仍有设备看得到（2025-06-05，同一产品）**

撤回的实现是「主库 `UPDATE msg SET state='revoked', body=NULL` + 给在线端推一条 revoke 指令」。

| 时间 | 事件 | 数据 |
| --- | --- | --- |
| 10:02:00 | 用户撤回一条含身份证照片的消息 | 1 条 |
| 10:02:03 | 热库修改完成，在线端收到指令并删除 | 在线覆盖率 99.2% |
| 10:03:40 | 安全抽检：离线超 7 天的设备重连后**仍能看到** | 命中 37 台 |
| 10:12 | 追查：该消息 10:00 刚被打包进冷存 block，**block 是不可变的** | 受影响 block 2.4 万个 |
| 10:15 ~ 13:20 | 全量重写受影响 block + 强制客户端清本地库缓存 | 3 小时 5 分 |
| 结果 | 2,860 名用户 × 1 条，合规事件（个人信息未按承诺删除） | 罚款 + 通报 |

根因同样不是「忘了改」，而是**同一份消息当时有三个真源**（热库、冷存 block、设备本地库），撤回只改了最便宜的那一个。

> 🩸 两起事故的公共结构：**只要「消息是可编辑的状态」，你就必须为每一个副本回答「改到哪了、什么时候改到、改不到怎么办」。** 而副本数量不是设计的输入，是设计的输出——它是「真源定在哪」的推论。这就是本篇的唯一真问题。

## 15.2 一句话定位与唯一真问题

**定位**：消息存储是「**同一会话内全序、跨会话无序、写多读多、永不原地改写**」的一类专用存储。它长得像 KV（`(conv_id, seq)` 就是 key），但它比 KV 多三条约束：必须保序、必须能差分同步、必须在撤回与加密之间做出选择。

### 唯一真问题

> **消息到底是「只追加的日志」，还是「可编辑的状态」？**
> 日志模型的每一行写下去就不变，撤回是**再加一行**；状态模型的行会被改，撤回是**把那一行改掉**。
> 这一个选择决定了五件事：**seq 是否必须连续**、**撤回能不能跨端一致**、**多端能不能任意拉取**、**服务端有没有能力读明文**、**冷热分层的单位是 block 还是行**。

从这条矛盾推出的全部设计：

| 从「日志模型」推出的约束 | 推出的设计 | 违反后的现场 |
| --- | --- | --- |
| 一行写下去就不变 → 修改必须是新事件 | 撤回/编辑写 `revoke_log` / `edit_log`，读时合并 | 冷存 block 不可变，撤回改不到（§15.1 事故二） |
| seq 是这条日志的位置，不是数据的属性 | 发号与追加**同一分片、同一事务** | 发号回退 → 覆盖丢消息（§15.1 事故一） |
| 差分同步靠「位置」而不是「时间」 | 游标 = `seq`，永不回退，永不跳号 | 用时间戳做游标 → 漏拉 |
| 日志可以不连续（号段浪费、回滚） | 「允许空洞」或「补占位」二选一，必须显式选 | 悄悄假设连续 → 客户端卡死在空洞上 |
| 不可变 → 可以打包成 block 归档 | 冷存单位 = `(conv_id, seq)` 有序块 | 按行存冷数据 → 成本 ×10 |

**对比一下就知道这条矛盾有多特殊**：

| 系统 | 一条记录的地位 | 撤回/修改 | 结论 |
| --- | --- | --- | --- |
| 消息 | 日志行，全序 | 追加事件 | **本篇** |
| 订单 | 状态机，可流转 | 不允许删，只允许流转 | 状态模型（→ [02 领域建模](02-domain-modeling.md)） |
| 短链目标 | 版本化不可变值 | 新版本 | 同构！所以可以抄「版本化」的思路（→ [12 短链 · §12.6](12-shortlink-system-design.md)） |
| 社交动态 | 可编辑内容 | 原地改 + 通知 | 可编辑状态，不需要 seq |
| 审计流水 | 绝对不懂 | 禁止 | 纯日志 |

**所以消息最该抄的作业是短链的「版本化」和搜索的「段 + 合并」，而不是数据库的 UPDATE。**

## 15.3 量级与预算：三个数决定全部形态

不许拍脑袋。IM 的存储形态只由三个数决定，而这三个数都能在白板上推出来。

### 三个数

```
① 日发送条数 = DAU × 人均发送条数
   3.0 亿 × 40 条/天（单聊 26 + 群 14）              = 120 亿条/天

② 日投递次数 = DAU × 人均接收条数（群扇出放大）
   3.0 亿 × 220 条/天                                = 660 亿次/天
   ⚠️ 这个数进的是 [13 扇出] 的预算，不是存储预算；两个数差 5.5 倍，混在一起算必错

③ 单条写入成本 = 正文 + 收件人元数据 + 索引
   60 B + 90 B = 150 B，索引 ×1.6                    = 250 B/条
```

### 从三个数推到分片数

```
日增（逻辑）  120e8 × 250 B                        = 3.0 TB/天
日增（物理）  3 副本 → 9.0 TB/天
5 年总量      3.0 TB × 365 × 5                     = 5.48 PB（逻辑）；物理 16.4 PB
热区（近 90 天）3.0 TB × 90                        = 270 TB
分片数        单分片温区上限 2 TB（自研 KV / 分片 MySQL，见 §03.12）
              5,480 TB ÷ 2,000 TB = 2.74 → 预留 4096 虚拟槽（→ [03 存储形态 · §03.10]）
写峰值        120e8 / 86,400 = 13.9 万 QPS；× K(3，晚 20–22 点) = 42 万 QPS
              单会话单写者、单分片安全写 8,000 条/s → 写维 53 分片
              按热点倾斜 4 倍（大群、红包雨）取 212 分片 → 4096 槽下没有单点
媒体          日均 3 亿个文件 × 300 KB             = 90 TB/天 → 5 年 164 PB（只存引用）
```

### 成本：一个反直觉的结论

| 项 | 量 | 单价（量级） | 月成本 |
| --- | --- | --- | --- |
| 热区消息（SSD 三副本） | 270 TB | 700 元/TB/月 | ≈ 18.9 万元 |
| 冷区消息（对象存储低频） | 5,210 TB | 40 元/TB/月 | ≈ 20.8 万元 |
| **消息存储合计** | 5.48 PB | — | **≈ 40 万元** |
| 媒体文件 | 164 PB | 40 元/TB/月 | **≈ 656 万元** |

> **这张表是本节唯一真正重要的结论**：云端全量留存与端上为主的差额，在总账单里只值 4%。所以「真源放端上还是云上」**不能靠成本论证**——它必须靠**能力**论证（要不要任意设备登录、要不要云端搜索、要不要服务端审核）。用成本去论证一个能力选择，是这类系统最常见的一次跑偏。

## 15.4 两种哲学：微信 vs Telegram（本篇招牌）

这是全文最值得抄走的一节。两家做的是同一个业务，做出来的却是**两套不相容的存储哲学**。下表每一行都是一个「选了 A 就必须接受 A 的账单」的关系。

| 维度 | 微信路线（端上为主） | Telegram 路线（云为真源） | 谁在为什么买单 |
| --- | --- | --- | --- |
| **① 真源在哪** | **手机本地库为主**（端上 SQLite 级别的库是权威副本），服务端保存「同步日志 + 有限漫游 + 短期离线队列」；换机的标准动作是**把本地库整体迁移过去** | **云端为真源**，客户端只是缓存；任意新设备登录即拉历史，MTProto 用 `pts / qts / seq` 逐账户做差分同步（客户端上报 pts，服务端补齐增量） | 端上真源把「历史」变成用户资产，云真源把「历史」变成服务端负债 |
| **② 撤回能力** | 撤回窗口短（分钟级），实现是「向双方端下发删除指令」；**离线设备靠下次上线补指令**，冷归档必须可重写（§15.1 事故二就是这么炸的） | 只要服务端还存着就能删（可「为所有人删除」且无长窗口限制），因为只有一份真源，删一次全部端一致 | 删一份 vs 删 N 份，撤回成本与端数成正比 |
| **③ 多端体验** | 多端**不是天然等价**：手机是主库，PC 端历史上要靠手机中转；多端同时在线要处理「谁是主设备」 | 多端**天然等价**：登录即全量，退出即消失，端之间没有主从；代价是每次冷启动、每次重连都要走一次差分同步 | 等价的多端 = 服务端必须持有全序 + 可差分 |
| **④ 加密边界** | 传输 TLS + 服务端持有密钥的存储加密，**默认不是端到端**；因此服务端能做全文搜索、内容审核、模型检测、垃圾信息识别 | 普通聊天是「客户端–服务端」加密（服务端可解密，能做审核与搜索）；**Secret Chat 才是 E2EE，且绑定单设备、不进云备份、不支持多端** | 这就是核心交易：**多端同步能力与明文可见性是同一枚硬币** |
| **⑤ 存储成本** | 消息表小（因为不承诺云端永久多副本），成本主体是**媒体 + CDN**；长期历史留在用户设备上 | 消息表大（云端永久 + 多 DC 复制），必须靠冷热分层与媒体分离把成本压回来 | 云真源的成本不是消息，是「承诺」 |
| **⑥ 离线容量** | 离线队列短（天级），超期要靠漫游/迁移；「云端能存多久」是一个产品策略参数 | 离线容量 = 云端容量，几乎无限；新设备首次全量靠**分页 + 懒加载 + 只拉最近 N 个会话** | 无限漫游必须配「首屏裁剪」，否则第一部手机会被 20 万条历史撑爆 |

### 抄什么、别抄什么

| 你的产品约束 | 必须选 | 必须接受 | 千万别抄 |
| --- | --- | --- | --- |
| 要「任意设备登录即看到全部历史」 | 云真源 + 差分游标（Telegram 路线） | 服务端可解密（或 E2EE 下放弃多端）+ 云端存储负债 | 端上为主却承诺无限漫游 → 换机就丢历史，客诉爆炸 |
| 要「历史只属于用户、服务端不碰明文」 | 端上为主 + 显式迁移（微信路线） | 换设备体验要专门设计；撤回要能重写归档 | 端上为主却做「云端搜索」→ 服务端没有明文，功能做不出来 |
| 要「合规审核 + 举报处置」 | 服务端可读（非 E2EE） | 加密边界退到 TLS + 存储加密 | 宣称 E2EE 又做云端审核 → 这是虚假宣传，法务风险 |
| 要「秘密聊天」 | E2EE + 单设备绑定 | 放弃多端、放弃云备份、放弃云端搜索 | E2EE + 多端同步 + 云端审核三者同时要 → 不存在 |

> 🩸 **本节的判决**：**「多端任意拉取」和「服务端看不见明文」在架构上互斥**（除非每台设备各自独立加密会话，那样"多端"就退化成了"多个独立账号"）。所以任何一份 IM 需求文档里如果同时出现"端到端加密"和"换手机自动同步全部历史"，它要么在说谎，要么在要求客户端自己保管密钥——而这就等于把"数据丢失"变成了用户责任。

## 15.5 消息模型：四个核心实体

```
                    ┌──────────────────────────────────────────┐
                    │ conversation 会话                        │
                    │  conv_id · type · last_seq · member_count│
                    │  retention · visibility · enc_mode       │
                    └───────┬──────────────────────┬───────────┘
                     1      │                      │ 1
                            │ N                    │ N
              ┌─────────────▼────────┐   ┌─────────▼──────────────────┐
              │ member 成员关系       │   │ message 消息（append-only） │
              │  user_id · role      │   │  seq · client_msg_id       │
              │  join_seq · leave_seq│   │  sender · ts · type · body │
              │  mute · pinned       │   │  reply_to_seq · state      │
              └─────────┬────────────┘   └─────────┬──────────────────┘
                        │ 1                        │ 0..N
                        │ N                ┌───────▼──────────┐
              ┌─────────▼──────────────┐  │ attachment       │
              │ read_cursor 已读游标    │  │  uri · sha256 ·  │
              │ (user_id, device_id)   │  │  size · mime     │
              │  read_seq · updated_at │  └──────────────────┘
              └────────────────────────┘        → 对象存储（→ [25 大文件]）
```

| 实体 | 关键字段 | 不变量（必须由同一个事务/同一个分片守护） |
| --- | --- | --- |
| `conversation` | `conv_id`（时间有序雪花）、`type`（single/group/channel）、`last_seq`、`last_msg_ts`、`member_count`、`visibility`（历史是否对新成员可见）、`retention`（TTL）、`enc_mode` | `last_seq` 只能单调增；`last_seq ≥ 任何已提交消息的 seq` |
| `member` | `conv_id`、`user_id`、`role`、**`join_seq`**、`leave_seq`、`mute`、`pinned` | `join_seq` 是**可见性下界**：新成员看不到入群前的历史（E2EE 群必守，公开群可选放开） |
| `message` | `conv_id`、`seq`、`client_msg_id`（幂等键）、`sender_id`、`sender_device`、`ts`（客户端时间）、`server_ts`、`type`、`body`（≤1 KB 内联）/`body_ref`、`reply_to_seq`、`state` | `(conv_id, seq)` 唯一且单调；`(conv_id, sender_id, client_msg_id)` 唯一（幂等）；**业务列永不 UPDATE** |
| `read_cursor` | `conv_id`、`user_id`、`device_id`、`read_seq`、`source`、`updated_at` | `read_seq ≤ conv.last_seq`；**每设备一行**，会话级读数由聚合算出（§15.8） |

**为什么 `seq` 必须挂在 `message` 上而不是自己单独一套 id**：因为「消息的位置」和「消息的身份」在这个领域是同一个东西。一旦拆成 `msg_id`（全局雪花）+ `seq`（会话内序号）两套，你就必须回答「哪个是真顺序」——而绝大多数系统的答案是"两个都不是，UI 用第三个（时间戳）"，这就是 §15.1 事故一的起点。

## 15.6 会话内序号 seq：谁来发号，怎么保序

### 三条发号路线

| 方案 | 机制 | 优点 | 致命问题 | 判定 |
| --- | --- | --- | --- | --- |
| **服务端单写者**（推荐） | 会话分片是唯一 writer，`UPDATE conv_seq SET next = next + 1` 与 `INSERT msg_log` 同事务 | 无空洞、无重复、天然全序，沉默地正确 | 单会话写吞吐 = 单分片写吞吐；大群要拆 lane | ✅ 默认 |
| **Redis INCR** | 中心化计数器，快 | 简单、延迟低 | **主从切换会回退**（§15.1 事故一）；回退 = 覆盖 = 丢消息；Redis 与 DB 不同事务 | ❌ 除非加号段 + 单调校验 |
| **号段预分配** | 每次从中心取 1,000 个号，本地自增 | 吞吐高、可跨分片 | 进程崩溃 → **号段浪费 → seq 空洞**；空洞要求下游能容忍 | ✅ 与「允许空洞」配套 |
| **混合逻辑时钟 HLC** | `seq = max(本地 HLC, 观察到的 max+1)` | 无需中心协调，多写者可用 | **会重号、会回退**，必须靠 `(device_id)` 破平局，UI 还要二次排序 | ⚠️ 只在端上发号（E2EE 群）时被迫使用 |

### 发号与追加的闭环

```
客户端 ──send(client_msg_id)──► 接入网关（鉴权 · 限流 · 幂等键 = client_msg_id）
                                    │ 路由：conv_id → 会话分片（唯一 writer）
                                    ▼
                    ┌───────────────────────────────────────────┐
                    │ 会话分片（单写者）· 一个本地事务            │
                    │  ① 幂等查：(conv, sender, client_id) → 有则返回原 seq
                    │  ② 发号：seq = nextval(本地号段) 或 UPDATE +1
                    │  ③ 追加：INSERT msg_log(conv_id, seq, ...)  ← 永不 UPDATE
                    │  ④ 摘要：UPDATE conversation SET last_seq = seq
                    │  ⑤ 事件：INSERT outbox(conv_id, seq)         ← 同事务
                    └───────────────────┬───────────────────────┘
                                        ▼ commit
                          投递器（→ [13 扇出]、[14 长连接]）
                          ├─ 在线端：长连接推 (conv_id, seq, payload)
                          └─ 离线端：**不投递**，只让会话摘要可见 → 由端上拉取（§15.9）
```

**五步必须在一个事务/一个分片里**，理由只有一条：如果 `last_seq` 领先于 `msg_log`，客户端会拿着一个「指向不存在的消息」的游标去拉，然后**永远卡在那一条上**；如果 `msg_log` 领先于 `last_seq`，这条消息**永远不会被差分同步发现**（只能全量重扫）。这两种不一致都比"丢一条"更难查。

### 消息写入（Go 骨架）

```go
// Append：发号、追加、摘要、事件在同一个会话分片、同一个本地事务里完成
func (s *Store) Append(ctx context.Context, m *Message) (int64, error) {
	sh := s.router.ShardOf(m.ConvID) // conv_id → 会话分片（唯一 writer，不跨片）
	return sh.WithTx(ctx, func(tx *sql.Tx) error {
		// ① 幂等：同一 (conv, sender, client_msg_id) 重发，返回原 seq，绝不二次入日志
		if seq, ok, err := findByClientID(tx, m.ConvID, m.SenderID, m.ClientMsgID); err != nil || ok {
			m.Seq = seq
			return err
		}
		// ② 发号：本地号段（1000/次）。号段浪费可接受，回退不可接受（§15.14 崩法一）
		seq, err := s.seq.Next(ctx, tx, m.ConvID) // UPDATE conv_seq SET next = next+1 WHERE conv_id=?
		if err != nil {
			return err
		}
		m.Seq = seq
		// ③ 追加：只 INSERT，业务列永不 UPDATE（撤回走 msg_mutation，§15.10）
		if err := insertMsgLog(tx, m); err != nil {
			return err
		}
		// ④ 摘要与事件同事务：否则游标会领先于日志，客户端永久卡在空洞上
		if err := bumpConv(tx, m.ConvID, seq, m.ServerTS); err != nil {
			return err
		}
		return insertOutbox(tx, m.ConvID, seq) // 扇出与推送由投递器异步完成（→ [13 扇出]）
	})
}
```

### seq 与时间戳：两个都要存，但只有一个能排序

| 用途 | 用谁 | 为什么 |
| --- | --- | --- |
| 排序、渲染、游标、差分 | **seq** | 单调、可比、与设备时钟无关 |
| 展示「昨天 14:32」 | `server_ts` | 用户看的是时间，不是序号 |
| 法律留存、审计、跨系统对齐 | `server_ts` + `client_ts` | 需要真实时间；`client_ts` 只作参考（可被用户改） |
| **绝对不能用来做游标** | `ts` | 同毫秒多条会重复；时钟回拨会**永久漏拉**；补发/迁移的消息 ts 会倒挂 |

### 空洞：必须显式选一种语义

```
A 允许空洞（默认，配合号段/回滚）
  客户端只按「本批实际返回的最后一条 seq」推进游标：
     next_cursor = last_returned_seq      ← 不是 from + limit
  渲染按 seq 排序，缺失的 seq 就是"不存在"，不做等待、不做重试。
  代价：客户端不能假设连续；「消息数 = seq 差」这类算法全部失效。

B 禁止空洞（Telegram 式 pts 差分同步）
  服务端必须为每个被跳过的号补一条占位事件（pts 的 gap 必须被填）：
     崩溃浪费的号段 → 补 NOOP 事件
     事务回滚掠过的号 → 从发号表回收，或补 NOOP
  收益：客户端可用「pts 必须连续」做完整性校验，差一个点就全量重拉。
  代价：发号必须与写入同事务（不能用纯号段），且补洞逻辑本身会出 bug。
```

> **判定**：如果你的客户端要在弱网下做「我知道我没收到的确切范围」，选 B；如果你只是做「往上翻页 + 增量拉」，选 A。**A 的成本是客户端不能做连续性假设，B 的成本是服务端必须有一个不会漏的补洞器**——两者都不能"顺便"。

## 15.7 存储形态：按会话分片，还是按用户分片

### 对照与判定

| 维度 | 按会话分片（`hash(conv_id)`） | 按用户分片（`hash(user_id)`，收件箱） |
| --- | --- | --- |
| 写入 | 1 条消息 **1 次写** | 1 条消息 **N 次写**（N = 接收者数） |
| 会话内读取 | ✅ 单分片、`(conv_id, seq)` 顺序扫，零排序 | ❌ 需要把 N 个用户收件箱归并 |
| 「我所有会话的消息」 | ❌ 需另建会话列表 + N 路归并 | ✅ 单分片范围扫 |
| 热点 | ⚠️ **大群 = 单分片热点**（万人群每秒数百条） | ⚠️ 大 V 的收件箱 = 热点（→ [13 扇出](13-fanout-push.md)） |
| 撤回/删除 | ✅ 改一处（追加一条事件） | ❌ 要改 N 份副本，且历史副本可能在冷存 |
| 容量 | ✅ 与「冷热按会话归档」天然对齐 | ❌ 同一会话的消息在 N 个分片里各存一份，容量 ×N |
| 判定 | ✅ **消息日志用它**（唯一不可替代） | ✅ **只用于小群/单聊的收件箱投影与离线提示**，绝不作为真源 |

**判定一句话**：**消息日志必须按 `conv_id` 分片，因为它的读模式是「同一会话按 seq 顺序扫」。** 收件箱是**派生视图**（可重建、可丢弃），不是真源——把它当真源就是 §15.1 事故二的推广版：一份消息 N 个副本，撤回要改 N 次。

### append-only 表设计（骨架，完整 DDL 见 [26 收口 · 附录 A](26-closing-playbook.md)）

```sql
-- 消息日志：分区键 = conv_id，聚簇键 = seq。业务列永不 UPDATE。
CREATE TABLE msg_log (
  conv_id       BIGINT      NOT NULL,
  seq           BIGINT      NOT NULL,
  client_msg_id CHAR(22)    NOT NULL,      -- 幂等键（客户端生成，重发不变）
  sender_id     BIGINT      NOT NULL,
  sender_device CHAR(16)    NOT NULL,
  server_ts     DATETIME(3) NOT NULL,      -- 排序不用它，审计用它
  client_ts     DATETIME(3) NOT NULL,
  msg_type      TINYINT     NOT NULL,
  body          VARBINARY(1024)  NULL,     -- ≤1KB 内联；超出走 body_ref
  body_ref      VARCHAR(255)     NULL,     -- 对象存储 uri
  reply_to_seq  BIGINT      NULL,
  PRIMARY KEY (conv_id, seq),
  UNIQUE KEY uk_idem (conv_id, sender_id, client_msg_id)   -- 幂等：重发返回原 seq
) PARTITION BY HASH(conv_id) PARTITIONS 4096;

-- 修改与撤回：只追加，读时合并
CREATE TABLE msg_mutation (
  conv_id   BIGINT   NOT NULL,
  target_seq BIGINT  NOT NULL,             -- 被撤回/编辑的那条
  mut_seq   BIGINT   NOT NULL,             -- 产生这次修改时占用的 seq（本身是一条系统消息）
  kind      TINYINT  NOT NULL,             -- 1=revoke 2=edit 3=delete_local_only
  operator  BIGINT   NOT NULL,
  payload   VARBINARY(1024) NULL,          -- edit 的新正文（加密态）
  mut_ts    DATETIME(3) NOT NULL,
  PRIMARY KEY (conv_id, target_seq, mut_seq)
);
```

### 冷热分层：日志模型在成本上的最大红利

| 层 | 数据 | 载体 | 组织单位 | 为什么能这么便宜 |
| --- | --- | --- | --- | --- |
| 热 | 近 90 天 | 分片 KV / SSD | 行（按 `seq` 聚簇） | 点查 + 范围扫都在同一分片 |
| 温 | 90 天 ~ 2 年 | 列式 / 大宽表 | 行 | 只读、可压缩列编码 |
| 冷 | 2 年 ~ 永久 | 对象存储 | **block = `(conv_id, seq_start, seq_end)`** | 一次打包几万条，压缩后单条成本降一个量级 |

```
冷存索引（很小，可以常驻内存）：
   arch_index(conv_id, seq_start, seq_end, object_uri, size)
   拉取时：热区 miss → 二分定位 block → 拉一个 block 解压 → 取区间
   一个 block ≈ 2 MB ≈ 8,000 条消息
```

> **这就是「日志 vs 状态」在钱上的差别**：日志 block 一旦写入就不可变，所以可以随便打包、随便压缩、随便多副本；而「可编辑的状态」在冷存里每一行都要能被单独改，于是你只能退回"行存"或者写一个会重写 block 的后台任务（§15.1 事故二的 3 小时）。

## 15.8 多端同步：三端同时在线，已读游标怎么合并

### 游标的形态

```
   设备 A（手机）            设备 B（PC）              设备 C（iPad，7 天未上线）
   read_seq = 118           read_seq = 132            read_seq = 97
        │                        │                          │
        ▼                        ▼                          ▼
   ┌─────────────────────────────────────────────────────────────────┐
   │ read_cursor(conv_id, user_id, device_id, read_seq, updated_at)    │  每设备一行
   │                                                                   │
   │ 活跃设备集 = 近 30 天有连接的设备 = {A, B}                          │
   │ 会话级读数 = max(活跃设备) = 132      ← C 的 97 不参与              │
   └──────────────────────────────┬────────────────────────────────────┘
                                  ▼
             未读 = last_seq(150) − 132 − 自己发的(4) − 已过滤(2) = 12
             （增量计数器兜底：从 132 之后逐条累减，见下表）
```

**四条合并规则，缺一条就出红点事故**：

| 规则 | 内容 | 违反后的现场 |
| --- | --- | --- |
| 1 | 合并用 **`max`**，绝不用「最后一次写入」 | 老设备上线把读数从 132 拉回 97 → 红点暴增、用户以为丢了消息 |
| 2 | 只有**活跃设备集**参与合并 | 丢弃的设备永久抑制未读；用户"永远有一个红点消不掉" |
| 3 | **「标记未读」是独立事件，不能被 max 吸收** | 用户手动标未读，被另一端的 max 立刻抹掉 → 功能失效 |
| 4 | 设备退役必须**显式 revoke**（不是等过期） | 二手手机仍能读到新消息（安全事件，不是体验问题） |

### 未读数：增量还是全量

| 方案 | 机制 | 写放大 | 撤回/删除后 | 多端合并 | 判定 |
| --- | --- | --- | --- | --- | --- |
| **全量算** | `unread = last_seq − read_seq − self − filtered` | 0 | 天然正确 | 天然正确 | ✅ **对账与冷启动**用它 |
| **增量计数** | 每会话一个 counter，新消息 `+1` | 1 次（还需为每个成员更新计数→ N 次） | ❌ **永久漂移**（撤回不递减、删除不递减） | ⚠️ 需按设备分桶再聚合 | ✅ 会话列表**热路径**用它 |
| 混合（推荐） | 增量计数做展示，**每次拉会话列表 / 冷启动时用全量算校准** | 1 | 自愈 | ✅ | ✅ **唯一正确解** |

> **为什么必须给未读数配一条自愈路径**：用户对红点数字极其敏感（"1 和 2 都能吵起来"），而撤回、删除、退群、静音、免打扰、折叠，**每一个都会让计数器漂移**。一个不能自愈的计数器，三个月内必然被客服工单淹没。

## 15.9 离线消息与补拉：窗口、游标、裁剪

### 拉取窗口的三个上限

| 参数 | 建议值 | 为什么必须有上限 | 不设的现场 |
| --- | --- | --- | --- |
| 单次返回条数 | ≤ 500 条 | 手机内存与渲染 | 一次拉 10 万条 → App 卡死、OOM |
| 单次返回字节 | ≤ 2 MB | 弱网 | 4G 下 40 秒白屏 |
| 拉取总时长 | ≤ 3 秒（服务端硬超时） | 不能让一次补拉占满连接（→ [14 长连接](14-websocket-fleet.md)） | 一个换机用户吃掉一个分片的十分之一 |

### 游标语义：三种都会写错的细节

```
① 游标是「已消费到的位置」，不是「下一条的编号」
     next_cursor = 本批最后一条的 seq（返回空则不动）
   错误写法：next_cursor = from + limit ← 有空洞就永久跳过（§15.1 事故一）

② 会话列表也要增量
     sync(conv_list_cursor) → [变化的会话 + 各自 last_seq + 未读数]
   只拉"变化的"，不拉全量会话列表：一个 2,000 会话的用户，全量列表 = 800 KB

③ 首次登录不等于「拉全部历史」
     首屏 = 最近 50 个会话 × 各 200 条 ≈ 1 万条（≈ 1.2 MB）
     更早的历史 = 点进会话时懒加载 / 云端搜索 / 付费漫游
```

### 超大离线量的两级裁剪

| 场景 | 原始量 | 裁剪后 | 用户感受 |
| --- | --- | --- | --- |
| 离线 3 天，20 个活跃会话 | 4,000 条 | 全给 | 无感 |
| 离线 30 天，300 个会话 | 6 万条 | 最近 50 会话 × 200 条 | 首屏秒开，翻历史有轻微 loading |
| 换机 / 重装 | 全量历史 | 同上 + 媒体按需 | 必须给"正在恢复"的进度条，否则用户以为丢了 |
| 万人群静默 30 天 | 单会话 40 万条 | 最新 50 条 + "查看全部" | 必须显式提示裁剪过，不能静默 |

### 拉取补偿（Java 骨架）

```java
/** 增量拉取：游标是 seq 不是时间戳；空洞不跳号；热区不足回落到归档 block */
public PullPage pull(long convId, long cursor, int limit, long visibleFrom) {
    long from = Math.max(cursor + 1, visibleFrom);          // ① join_seq 之前不可见
    List<Message> rows = msgLogMapper.range(convId, from, Math.min(limit, MAX_PER_PAGE));
    if (rows.size() < limit) {                              // ② 热区只留 90 天，缺口回落冷存
        rows = mergeBySeq(rows, archive.read(convId, from, limit - rows.size()));
    }
    List<Message> out = revoker.apply(rows, mutationMapper.after(convId, from)); // ③ 撤回/编辑读时合并
    long next = out.isEmpty() ? cursor : out.get(out.size() - 1).getSeq();       // ④ 只推进到实际返回处
    if (out.size() == limit) {                                               // ⑤ 截断时必须重算未读
        unreadCalibrator.enqueue(convId, next);                              //    否则红点永远差一截
    }
    return new PullPage(out, next, out.size() == limit);
}
```

## 15.10 撤回 / 编辑 / 删除：对日志模型的三种冲击

撤回是这套系统里**唯一一个「必须修改历史」的需求**，也是「日志 vs 状态」这个哲学选择的试金石。

| 实现 | 机制 | 存储成本 | 读路径 | 审计/合规 | 冷存兼容 | 跨端一致 | 判定 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| **① 追加撤回事件** | 写 `msg_mutation(kind=revoke)`，读时合并 | +1 行/次 | ❌ **每次读都要 join**（可按时间窗缓存） | ✅ 完整（谁、何时、撤了什么） | ✅ 完全兼容（block 不可变） | ✅ 游标一动就一致 | ✅ **默认选它** |
| **② 原地修改** | `UPDATE msg_log SET state='revoked', body=NULL` | 0 | ✅ 无合并 | ⚠️ 需另建审计表，否则查不到历史 | ❌ **冷存 block 改不了**（§15.1 事故二） | ❌ N 个副本各改一次 | ❌ 仅小规模/单端可用 |
| **③ 墓碑** | `INSERT` 一条占位行覆盖 body + `revoked_at` | +1 行 | ✅ 无需 join（读同一 key） | ⚠️ 原内容没了 | ⚠️ 需要"最后一条胜"的读语义 | ✅ | ✅ **大群/高频撤回**用它（读路径更短） |
| ④ 只删本地 | 只给端发指令，服务端不动 | 0 | ✅ | ❌ 服务端仍有明文（法律风险） | ✅ | ❌ 新设备一登录就看见 | ❌ 只能做"本地删除"，不能叫"撤回" |

**三条落地纪律**：

1. **`revoke` 本身占用一个 `seq`**。否则客户端的游标无法表达"我在第 100 条之后看到了撤回事件"，差分同步就会漏掉它。
2. **`revoke` 的可见范围必须等于原消息的可见范围**。群聊里撤回一条"只有部分人可见"的消息（入群前历史），如果撤回事件广播给全部成员，就泄露了"这里曾经有条消息"。
3. **编辑（edit）必须保留版本链**。否则「消息被改了」这件事在审计上是不存在的——而这恰恰是最需要留痕的场景（诈骗话术改口、合同条款替换）。

> **对比一下就知道为什么"日志模型"赢**：状态模型把撤回做成一次 UPDATE，写下的是"历史被改过"，代价是**任何不可变的下游（冷存 block、CDC 副本、客户端本地库、导出文件）都会变成一个需要被追着改的副本**。日志模型把撤回做成"反事实的记录"，代价只是读时多一次合并——**一次可预算的 CPU，换掉一条永远追不完的清单**。

## 15.11 端到端加密下的服务端能力边界

加密不是"加个 TLS"，而是**服务端还能不能读懂它保存的东西**。这一条决定了整个产品的功能集合。

| 能力 | 非 E2EE（服务端可读） | E2EE · 普通聊天（Signal 协议 / 双棘轮） | E2EE · 秘密聊天（单设备绑定） |
| --- | --- | --- | --- |
| 传输与按 seq 排序 | ✅ | ✅（序号是明文控制帧） | ✅ |
| 离线队列存储 | ✅ | ✅（只存密文 + seq） | ✅ |
| 撤回指令 | ✅ 服务端直接删 | ✅ 控制帧明文，正文无需解密 | ✅ |
| 已读回执 | ✅ | ✅（可选，元数据） | ✅ |
| **服务端全文搜索** | ✅ | ❌ **做不了** → 只能"端上本地索引"（受设备历史限制） | ❌ |
| **内容审核 / 垃圾信息识别** | ✅ | ❌ 只能看元数据（频率、关系图、举报率）→ [08 风控与反作弊](08-risk-and-antifraud.md) | ❌ |
| **举报处置** | ✅ 服务端直接取证 | ⚠️ 只有"客户端主动上报的明文片段" | ⚠️ 同左 |
| **多端同步** | ✅ 任意端拉全量 | ⚠️ 每设备一条独立会话（每端各自加密），历史不跨端 | ❌ **不支持** |
| **云备份恢复** | ✅ | ⚠️ 只能客户端加密备份（密钥自管） | ❌ |
| 存储成本 | 可压缩、可去重、可搜索索引 | 密文不可压缩（去重还可能泄露内容） | 同左 |

```
服务端在 E2EE 下的真实身份：
   序号发生器 + 不可读中继 + 离线队列 + 元数据（谁、何时、多长、发给谁）
   ↓
   于是「搜索 / 审核 / 多端同步」三样能力必须搬到端上，或直接放弃
   ↓
   这就是为什么「秘密聊天」在产品上总是一个单独的、功能更少的入口
```

> **判据**：如果需求里出现"加密聊天也要能云端搜关键词"，唯一诚实的答案是把索引做成**端上加密索引 + 拉取候选后本地解密过滤**——代价是搜不到超出本地留存范围的历史。任何声称"服务端在不解密的情况下能高效全文检索加密消息"的方案，要么在做可搜索加密（有泄露风险），要么在骗人。

## 15.12 群聊扇出：小群写扩散、大群读扩散、超大群分层

扇出的完整推拉边界在 [13 亿级粉丝互关与推送](13-fanout-push.md) 已定案，本节只补"消息存储侧"的那一半：**扇出方式决定了 `msg_log` 有几份、撤回要改几处**。

```
小群（≤200 人）              大群（200 ~ 1 万）              超大群/频道（>1 万）
写扩散：一条消息 N 写          读扩散：1 写 + M 读              读扩散 + 分层推送
┌────────────┐               ┌────────────┐                  ┌────────────┐
│ msg_log    │               │ msg_log    │                  │ msg_log    │
│ conv=G 1 行│               │ conv=G 1 行│                  │ conv=G 1 行│ ← 唯一
└─────┬──────┘               └─────┬──────┘                  └─────┬──────┘
      │ ×N（收件箱投影）             │ 0（不投影）                    │ 0
      ▼                             ▼                              ▼
 inbox(u1..uN)              成员各自按游标拉              推送只发"有新消息"摘要
 未读可直接读投影            未读 = last_seq − read_seq      活跃 Top 1% 预取热缓存
 写放大 = N，读 = 1          写 = 1，读 = M（活跃成员）       写 = 1，推送 N × 极小载荷
```

| 群规模 | 存储形态 | 扇出方式 | 单位消息的存储成本 | 关键风险 |
| --- | --- | --- | --- | --- |
| 单聊 / ≤200 人 | 会话日志 + 成员收件箱投影 | 写扩散 | N × 250 B（N ≤ 200） | 收件箱与日志不一致（必须可重建） |
| 200 ~ 1 万 | **只存会话日志** | 读扩散 | 250 B | 单个分片热点（大群每秒数百条） |
| > 1 万（频道/直播群） | 会话日志 + 活跃成员热缓存 | 读扩散 + 摘要推送 | 250 B | seq 发号成为瓶颈 → 按 lane 分片（`lane_id, seq`），仅保证 lane 内有序 |

**阈值怎么算，而不是怎么感觉**：

```
写扩散成本 = N 次写（N = 成员数）
读扩散成本 = M 次读（M = 真实活跃读成员数，静音成员不算）
判定：N / 单写成本  vs  M / 单读成本   →  取小者

万人群实测算例：N = 10,000；M = 300（95% 静音 + 99% 不看历史）
  写扩散：10,000 次写 / 8,000 次每秒每分片 ≈ 1.25 个分片被一条消息打满
  读扩散：300 次读，分散在 300 个用户的拉取请求里
  结论：差 33 倍 → 万人群必须读扩散
```

**万人群的三个额外账单**（都是存储侧的，不是推送侧的）：

1. **成员表 = 存储成本的主体之一**：1 万成员 × `member` 行（含 `read_cursor` 每设备一行）≈ 1.4 万行/群。10 万个万人群 = 14 亿行，比消息本身更占地方。
2. **撤回要广播"删掉这条"给 1 万人**：用「读时合并 + 版本号」把成本摊到读路径，绝不在写路径同步广播（→ §15.10 实现 ①）。
3. **`join_seq` 决定历史可见性**：万人群默认"新成员看不到入群前历史"。这不是体验选择，而是**发送者的隐私预期**——而它同时也是一个巨大的存储红利（不必为新成员准备历史）。

## 15.13 L0 → L5：六次换挡与换挡信号

| 阶段 | 形态 | 容量 | **换挡信号（硬阈值）** | 代价 |
| --- | --- | --- | --- | --- |
| L0 | 单机 MySQL 单表 `message(conv_id, seq)` | 1 万条/s | 单表 > 50 GB 或 P99 > 50 ms | — |
| L1 | 按会话 `PARTITION BY HASH` + 冷数据归档 | 5 万条/s | 单实例 IO util > 70%；备份超低峰窗口 | 跨分区查询消失 |
| L2 | **消息日志与收件箱投影分离** + 读写分离 | 20 万条/s | 投影与日志不一致率 > 0.01%；复制延迟 > 1 s | 需要重建工具（没有重建 = 没有投影） |
| L3 | **按 `conv_id` 分片 4096 槽 + 单一 writer** | 100 万条/s | 单分片写 > 8,000 条/s；倾斜度 max/avg > 2 | 跨分片查询全废；发号与写入必须同分片 |
| L4 | 冷热分层（block 打包）+ 大群 lane 化 | 500 万条/s | 热区 > 270 TB；单群 > 500 条/s；归档重写次数 > 10/天 | 冷存读取延迟 100~500 ms |
| L5 | 单元化（按用户地域切单元）+ 多 DC 复制 | 千万级 | 单地域容量 > 60%；跨地域 P99 > 80 ms | 跨单元会话（跨地域群）必须选"归主单元"或"双写" |

**当前目标量级（120 亿条/天）落在 L4。L3 → L4 的临界点值得展开**：到 L3 之后你会发现成本曲线突然变陡——3.0 TB/天的新增里有 80% 的消息**写入后 90 天内只被读过 1.2 次**。这时候正确的动作不是继续加 SSD 分片（线性堆钱），而是把这些消息**打包成不可变 block 下沉**：

- 前提条件：**消息必须是日志模型**（不可变），否则 block 会在撤回时被反复重写（§15.1 事故二的 3 小时）；
- 收益：冷区单 GB 成本降到 1/17，5 年总账单从 40 万/月压到 32 万/月；
- **不要跳级**：没有 `(conv_id, seq)` 有序打包能力就下沉，等于把「顺序读」打散成随机读。

## 15.14 这个形态特有的崩法

不是"高可用"套话，是消息存储自己会炸的地方：

| 失效 | 长什么样 | 定位方法 | 预防 |
| --- | --- | --- | --- |
| **发号器回退** | 消息乱序、序列冲突、部分消息凭空消失 | 比对 `conv_seq.next` 与 `max(msg_log.seq)` 的差值（应为 0） | 发号与写入同事务；Redis 号段必须带"单调校验"（见 §15.6） |
| **游标跳过空洞** | 用户说"有消息没收到"，服务端查得到 | 抽样对比 `read_cursor` 与实际返回的最后一条 seq | `next_cursor = last_returned_seq`，不是 `from + limit` |
| **未读永久漂移** | 红点消不掉 / 明明没消息却有 99+ | 对同一用户全量算 vs 增量计数比对 | 每次拉会话列表用全量算校准；撤回/删除必须递减 |
| **大群热分片** | 单分片 CPU 100%，同分片其它会话一起卡 | 按 `conv_id` 聚合分片写入 QPS，看 top10 会话占比 | 大群 lane 化 / 独立分片 / 消息合并推送 |
| **冷存撤回重写** | 撤回后个别设备仍可见；归档任务 CPU 飙高 | 统计"归档后又被修改"的 block 数 | 撤回走 `msg_mutation`，永不回写 block（§15.10 实现 ①） |
| **投影与日志不一致** | 会话列表有红点但点进去是空的 | 抽样比对 `inbox.last_seq` 与 `msg_log.max(seq)` | 投影必须可重建；重建脚本每季度真跑一次 |
| **深翻页打满 IO** | 用户往上翻到 2 年前，整站变慢 | 慢查询里 `LIMIT 100000,20` 型 SQL | 游标分页 + 冷区 block 预取 + 翻页限流 |
| **设备退役未回收** | 二手手机能读新消息（安全事件） | 审计"30 天无连接但未 revoke"的设备数 | 设备表有显式状态机，不靠 TTL 自然过期 |

## 15.15 砍掉 90% 预算还能不能跑

机器砍到 1/10、冷存关掉、大群 lane 化取消：

| 保留 | 砍掉 | 后果 |
| --- | --- | --- |
| **append-only 日志 + `(conv_id, seq)` 分片 + 单一 writer** | 冷热分层、block 归档 | 存储成本涨 3~4 倍（全放 SSD），但 5.48 PB 的量级仍可跑 |
| **游标式增量拉取 + 未读全量校准** | 收件箱投影、lane 化 | 大群变成单分片热点，晚高峰 P99 从 200 ms → 1.5 s |
| **`msg_mutation` 撤回事件** | 多端已读合并（退化为"最后上线设备胜"） | 红点偶发不准，客诉上升但无数据风险 |
| **媒体外置对象存储 + 生命周期** | CDN 边缘、转码多档 | 图/视频加载慢一倍，成本反而上升（带宽） |

**结论：这个系统的必需品只有三样——`(conv_id, seq)` 单写者日志、游标式增量拉取、追加式撤回。** 其余（冷热分层、投影、lane、多端游标合并）全是量级或体验驱动的优化。每次评审都问一遍"哪三个是必需品"，能砍掉一半的架构虚荣。

## 15.16 十分钟答题卡

被要求现场设计 IM 消息存储时，按这个顺序讲，不要从"我用 HBase"或"我用 Cassandra"开始：

```
1  问三句     消息要云端永久可拉吗（真源在云还是在端）？
              要 E2EE 吗？要任意设备登录即看全历史吗？
              —— 这三问决定一切，且它们互相冲突（§15.4）
2  真问题     消息是「只追加日志」还是「可编辑状态」→ 撤回、多端、加密、成本全是它的推论
3  量级       DAU 3 亿 × 40 条/天 = 120 亿条/天；250 B/条 = 3.0 TB/天
              × 365 × 5 = 5.48 PB；单分片 2 TB → 4096 槽；写峰值 42 万/s
              扇出 660 亿次/天 是推送预算，不是存储预算（差 5.5 倍）
4  模型       四实体：conversation / member(join_seq) / message(seq) / read_cursor(每设备)
5  发号       服务端单写者 + 同分片同事务；号段可浪费（空洞），回退绝不允许
              seq 排序、ts 展示；游标只用 seq，永不用时间戳
6  分片       消息日志按 conv_id（点查/范围 = 查询条件）；收件箱是派生投影，不是真源
7  同步       已读游标每设备一行，聚合取 max 且只算活跃设备；未读 = 增量计数 + 全量校准
8  补拉       窗口 ≤500 条 / 2 MB / 3 s；next_cursor = 实际返回的最后一条 seq
              首次登录 ≠ 全量历史：50 会话 × 200 条
9  撤回       追加 revoke 事件（保审计、兼容冷存）；原地 UPDATE 只在单端小规模可用
10 加密       E2EE 下服务端 = 序号发生器 + 不可读中继；搜索/审核/多端同步必须砍
11 扇出       ≤200 写扩散；200~1 万读扩散；>1 万读扩散 + 摘要推送 + lane 发号
12 换挡       单表 50 GB → 分区 → 投影分离 → 4096 槽 → 冷热分层 → 单元化
13 崩法       发号回退 / 游标跳洞 / 未读漂移 / 大群热分片 / 冷存撤回重写
14 必需       单写者日志、游标式增量拉取、追加式撤回 —— 其余都是量级驱动
```

**三句收尾话术**（评审现场最能体现你想透了）：

- 「这一篇的不可逆决策只有一个：**真源在端还是在云**。它一旦定了，撤回、多端、加密三件事的形态就一起定了。」
- 「**多端任意拉取和服务端不可读明文，在架构上互斥。** 需求里同时要求这两个，我们得先改需求，再谈设计。」
- 「撤回的性能不是问题，**副本数量才是**。所以撤回必须是一次追加，而不是一次修改。」
