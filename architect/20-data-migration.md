## 20.1 引子：三个「搬完了才发现搬错了」的故障

### 事故一：切读那一刻，新库少了 3 天（2025-09，某订单中台）

订单中台 8 库 64 表、4.1 亿订单 + 19 亿明细、物理 1.6 TB，单分片容量水位 71%，立项扩到 16 库。团队按「双写 → 全量 → 增量 → 影子读 → 切读写 → 摘老库」走，前四步全部按计划，第五步出事。

| 时间 | 事件 | 数据 |
| --- | --- | --- |
| 08-30 02:00 | 双写开启（Gate 100%），写老库 + 写新库 | 双写差异率 0.0008% |
| 09-02 02:00 | 全量启动，按主键游标分批，每库限速 12 MB/s | 8 库并行 96 MB/s |
| 09-02 06:55 | 全量完成，CDC 增量开始追平 | 1.6 TB / 96 MB/s ≈ 4.6 h |
| 09-06 19:52 | 运维发现 `cdc_lag` 涨到 1,180 s，执行「跳过积压快速追上」：`--reset-offsets --to-latest`，并把 consumer `group.id` 从 `mig-cdc-v1` 换成 `mig-cdc-v1-fix` | 新 group 无 offset → 直接 latest |
| 09-06 20:00 起 | **09-06 20:00 ~ 09-09 22:08 的增量被整段跳过**，位点表 `mig_watermark` 仍每 10 min 刷新，显示"正常" | 静默缺口 3.1 天 |
| 09-07 ~ 09-08 | 双写差异率仅 0.0009%，指标全绿 | 双写看不到历史缺口 |
| 09-09 21:00 | 影子读 1% 抽样不一致率 0.31%，被解释为「CDC 延迟正常抖动」 | 差异未归因 |
| 09-09 22:08 | 切读 100%（**跳过了"差异必须归因"这道门**） | 新库成为读权威 |
| 09-09 22:40 | 客服工单爆量：「订单列表少了几单」「已发货显示待发货」 | 3 分钟内 260 单 |
| 09-10 00:20 | 按 runbook 顺序继续切写，新库成为唯一写者 | 独有写入开始累积 |
| 09-10 01:10 | 决定回滚 → **发现回滚不成立** | 三个阻断点，见下表 |
| 09-10 01:40 | 决策：不回滚，向前修（从物理备份 + binlog 归档重建差异集） | — |
| 09-10 08:30 | 补写完成，checksum 全量比对通过 | 恢复耗时 6.8 h |
| 09-10 11:20 | 差异行 1,140 行人工处置完毕，读写全量恢复 | 不可用 13.2 h |

**为什么"回滚"这条退路在 01:10 已经不存在**——这是本篇的全部要害：

| 阻断点 | 应有的设计 | 当时的状态 | 后果 |
| --- | --- | --- | --- |
| ① 新库已有"只在新库"的写入 | 切写前保留 ≥24 h「可回滚窗口」，窗口内继续双写 | 00:20 起新库独占写入 50 min，8.6 万单只在新库 | 回滚即丢这 8.6 万单 |
| ② 老库已被反向污染 | 差异修复脚本必须**单向**（只补新库），并在老库侧留版本水位 | 修复脚本按 diff 双向跑，把 4.7 万行老库数据刷成了新库的旧版本 | 老库不再是 09-06 的一致快照，回滚回去是"更旧的错数据" |
| ③ 新语义已写入老库 | 枚举扩展必须走 expand-contract（老库先加值域，旧代码忽略未知值） | 双写期两个新枚举 `REFUNDING_V2` 已落老库 varchar | 旧代码把未知状态置为"待支付"，回滚即制造二次错单 |

**丢失/受影响数据量与恢复耗时（必须算出来，否则复盘会停在"加强监控"）**：

```
缺失区间        09-06 20:00 ~ 09-09 22:08 = 3.1 天
受影响订单      62 万单/天 × 3.1 天           ≈ 192 万单
受影响明细      192 万 × 4.7 行/单            ≈ 903 万行
需补写总行数    192 万 ×（1 + 4.7 + 4.3 次状态更新）≈ 1,912 万行
被反向污染      47,000 行（需人工确认语义）
人工差异        1,140 行
不可用时长      22:08 → 次日 11:20            = 13.2 h（其中 5.1 h 完全不可写）
恢复明细        定位 1.5 h + 临时实例恢复 2.5 h + binlog 重放 1.4 h
                + checksum 定位差异块 0.4 h + 行级补写 1.5 h + 全量复核 1.0 h ≈ 8.3 h
```

三处失败可以压成三句话，也是本篇的三条主线：**位点丢失靠"位点与应用进度同事务"防（§20.7）**；**差异未归因就切读靠"三件套 + 归因门"防（§20.6）**；**回滚失效靠"可回滚窗口 = 反向数据路径"防（§20.10）**。

### 事故二：换库换掉了排序规则（2025-05，某 CRM MySQL→PG）

表从 `utf8mb4_general_ci` 迁到 PG 的默认 collation，`customer_name` 唯一索引在 PG 侧判定 `'Zhang'` 与 `'zhang'` 为不同值、MySQL 侧为相同值。迁移工具报"0 差异"（行数、主键全对），上线后重复客户 3.1 万条，销售提成按重复客户算了两遍。**校验工具只校验数据，不校验语义**——这是"三件套必须有一层业务口径比对"的原因。

### 事故三：迁移任务没有断点，崩三次等于从头三次（2025-11，某日志库归档）

自研迁移任务用 `LIMIT offset, 5000` 分批，第 41 批 OOM 后进程重启，从 offset 0 重跑。三次重启耗尽 6 h 低峰窗口，被迫白天继续跑，把源库 `%util` 打到 98%，线上查询 P99 从 40 ms 涨到 3.2 s，持续 41 分钟。**断点续跑不是"优化"，它是"任务能活过第一次失败"的前提**（§20.11）；**限速不是"慢一点"，它是任务与线上业务共存的条件**（§20.12）。

## 20.2 一句话定位与唯一真问题

**定位**：迁移是「**把一个正在被写入的系统，从一个存储形态换到另一个，过程中业务连续、数据可证、退路可走**」的一次性工程。它是一次外科手术，不是一次数据拷贝。

### 唯一真问题

> **迁移的难点从来不是"搬数据"，而是「双写期间的一致性 + 任何时刻都能回滚 + 业务不停机」这三件事同时成立。**

这三件事构成一个**三角，只能同时放松量级，不能同时满足**：

| 你想要 | 它的真实代价 | 放松哪一项才能得到 |
| --- | --- | --- |
| 双写期间强一致 | 两库要 2PC/XA，性能税 3~5 倍且悬挂事务（`eng/8` 结论） | 放松一致性 → 改成"差异可枚举可修复" |
| 任意时刻可回滚 | 反方向的数据路径必须一直在线（反向 CDC 或持续双写） | 放松回滚 → 定义 `T_no_return` 截止点 |
| 完全不停机 | 同一行不能有两个写者，所有权转移那一瞬必须冻结 | 放松停机 → 接受 2~5 min 冻结窗口 |

所以正确的表述不是"三个都要"，而是：

> **一致性用「可枚举」换，回滚用「窗口」换，不停机用「冻结瞬间」换。**
> 你必须把这三笔交换**写进 runbook 的第一页**，并在开工前告诉业务方每一项的数字化代价。

这条判断与三个常见误解正面冲突：

| 你以为的 | 真相 | 不做会怎样 |
| --- | --- | --- |
| 「双写就是两边都写，数据自然一致」 | 双写不是原子操作，永远有差异；目标不是"一样"，是"差异可枚举" | 事故一：0.0009% 的双写差异掩盖了 3.1 天的历史缺口 |
| 「有开关就能回滚」 | 开关只切**读写方向**，不搬运**已经产生的数据** | 切写 50 min 后回滚 = 丢 50 min；切写 3 天后回滚 = 丢 3 天 |
| 「校验通过就该切」 | 校验通过只证明"数据对"，不证明"业务对" | 事故二：行数全对，语义全错 |

| --- | --- | --- |

## 20.3 迁移的四类场景：同样五个阶段，四种不同死法

**没有"通用迁移方案"这回事。** 同一个五阶段骨架，放到四类场景里，难点、手段、窗口、回滚代价全都不同——评审时第一句该问的是"你属于哪一类"。

| 场景 | 典型触发信号 | 真正难点（不是数据量） | 关键手段 | 停写窗口 | 回滚代价 | 验收口径 |
| --- | --- | --- | --- | --- | --- | --- |
| **同构扩容**（8 库 → 16 库） | 单分片容量水位 > 60%，或写 TPS > 单库安全值 70%（`[06 · §06.5]` L2→L3） | 分片映射变更后**同一实体跨两个库**；跨槽事务消失 | 虚拟槽 4096 + 映射版本号 + 双写 + 按槽搬 + 影子读 + **按槽原子切读** | 0（映射表原子替换） | **秒级**（改回映射版本） | 槽级 checksum 差异 = 0；倾斜度 max/avg < 1.5 |
| **异构换库**（MySQL→PG/TiDB） | 单库 > 5 TB 且 3 年翻倍；需跨片事务或 HTAP（`eng/36 §36.8`） | **语义漂移**：自增、`ON DUPLICATE KEY`、隔离级别、字符集排序、时区、浮点精度、大事务上限 | 类型/语义映射表 + SQL 兼容层 + 双跑比对（同一请求打两库比结果）+ 逐步切读 | 0 ~ 5 min（改 ID 生成器时要停） | 分钟级，但**已写入的新语义不可自动回退** | SQL 回归集 100% 通过 + 影子读差异 0（`eng/36 §36.8` 的 12 项迁移成本清单逐项签收） |
| **拆服务**（数据分离） | 事务边界真的分开了——"这一步之后还能不能用一个事务守护这条不变量"答"不能"（`[06 · §06.6.3]`） | 原来靠**本地事务**保证的不变量，拆完只能靠 Saga + 对账；双写救不了跨库事务 | 先拆 schema（同实例不同库）→ 再拆实例 → 再拆进程；跨库一致性走 Outbox + 三层对账（`eng/14`） | **一次所有权转移的冻结 ≤2 min**（同一行不能有两个写者） | 中（补偿逻辑必须自带逆操作） | 双库对账差异 = 0 且连续 7 天；补偿成功率 > 99.99% |
| **跨云跨地域** | 合规（数据不出境）、单元化（`[10 多活与单元化]`）、云厂商迁移 | 带宽与光速：100 Mbps 专线搬 10 TB = 9.3 天；链路中断、验收工具两侧不一致 | 物理介质/专线 + 增量 CDC 长跑 + 按单元（租户/地域）整体切 + 双向对账 | 分钟级（网关/DNS 路由生效） | **小时级**（回切要再同步一轮增量） | 双向对账 + 端到端只读演练 + 回切演练已跑过 |

三条从这张表里直接读出来的规律：

1. **场景决定你能不能"零停写"**。同构扩容天然可以（映射表是原子的）；拆服务天然不行（所有权转移有实体）。**任何声称"拆服务也能零停写"的方案，都是在某个环节偷偷接受了双写者。**
2. **场景决定回滚的单位**。同构扩容回滚是"改配置"，异构换库回滚是"搬数据"，跨云回滚是"再搬一次"。**回滚代价决定了你敢把灰度放多快**，而不是反过来。
3. **四类场景里最难的不是同构扩容**（数据结构不变，只是搬运），而是**异构换库**：它的失败不在数据里，在语义里（事故二），而语义差异没有任何工具会替你发现。

## 20.4 量级与预算：迁移只有四个数，全部可推

不许说"大概要一晚上"。迁移的排期只由四个数决定，评审时要求对方当场推一遍。

### 数一：全量时长（决定你要不要分批、要不要并行）

```
D          = 源端物理字节数（data + index，取 information_schema 实测，别用裸数据量）
             = 1.6 TB = 1.6e12 B（含索引 ×1.6，推导见 [03 · §03.11]）
N_shard    = 并行库数          = 8
v_shard    = 单库限速          = 12 MB/s（限速的取值见 §20.12）
T_all      = D / (N_shard × v_shard) = 1.6e12 / 96e6 s ≈ 16,667 s ≈ 4.6 h

全速（不限速 60 MB/s/库）时 T_all ≈ 0.93 h——但会把源库 %util 打到 90%+（事故三）
结论：限速是必须的，4.6 h 是"和业务共存"的价格，不是"技术落后"
```

### 数二：追平时间（唯一的除法陷阱）

```
v_produce  = 源端写入产生的 binlog 速率 = 1.5 GB/天 ≈ 17 KB/s
             推导：62 万单/天 ×（1 insert + 4.7 明细 + 4.3 更新）≈ 620 万行变更 × 260 B ≈ 1.5 GB
v_consume  = 迁移侧可应用速率（实测单 consumer ≈ 70 KB/s）
积压 L     = 全量期间产生的增量 = 4.6 h × 17 KB/s ≈ 280 MB
T_catch    = L / (v_consume − v_produce) = 280e6 / ((70−17)×1e3) s ≈ 5,283 s ≈ 88 min

⚠ 若 v_consume < v_produce，T_catch 为负 → 永远追不平，加机器只是延长崩溃时间
   这时唯一的解是"缩短链路"（同机房 / 批量提交 / 去掉逐行反序列化），不是加并发
```

### 数三：对线上库的 IO 干扰（这是迁移真正的风险敞口）

```
迁移读 IOPS = 96 MB/s ÷ 16 KB 页 ≈ 6,000 IOPS
源库实测峰值 IOPS = 24,000，业务峰值已占用 65% → 余量 8,400 IOPS
迁移占余量比例 = 6,000 / 8,400 ≈ 71%   ← 超了。安全线是 ≤40%（余量 3,360 IOPS ≈ 54 MB/s）

于是三选一：① 全局限速 54 MB/s（全量拉长到 8.2 h）
            ② 按业务曲线变速：低峰 96 MB/s、白天 20 MB/s（推荐，见 §20.12）
            ③ 从只读副本迁（代价：副本延迟 + 副本被读业务占用）
```

### 数四：停写窗口（分子是所有不可并行的步骤，分母是你的运维手速）

```
T_freeze = 关双写/置只读 (30 s) + 等 lag 归零 (≤60 s) + 最后一批校验 (≤120 s)
         + 路由生效（配置中心推送 P99 1 s + 客户端 refresh 60 s）= 60 s
         + 冒烟用例 20 条 (60 s) + 开写确认 (30 s)
         ≈ 6 min  → runbook 按 10 min 预算，对外承诺 15 min

若 refresh 间隔能提前一个版本从 60 s 降到 5 s，T_freeze 可压到 ≈ 5 min
——这是唯一值得为"缩窗口"单独发一次版的动作
```

### 成本侧（迁移的钱不是机器钱，是"重复写 + 人力 + 风险"三笔）

| 科目 | 算式 | 量级 |
| --- | --- | --- |
| 双写期写放大 | 目标库 IO +100%，7 天双写 → 目标库规格 ×2 | 月增 ≈ 3.2 万元 |
| 全量迁移机时 | 8 台 4C16G × 8.2 h / 月 | ≈ 400 元（可忽略） |
| 人力 | 迁移 owner 1 人 × 全程 + SRE 3 人 × 关键窗口 6 次 | ≈ 30 人天 |
| **风险敞口** | 一次 P1 = 13.2 h 不可用（事故一）；期望 0.2 次 → 年均 ≈ 2.6 h 不可用预算 | 必须显式记账 |

> 一条划算的判断：**双写多花 3.2 万元/月，换的是"任何时刻可回滚"**。这笔钱在该花的时候最便宜——事故一的直接损失远超 10 年的双写成本。真正该砍的是**双写时长（7 天 → 3 天）**，而不是"要不要双写"。

## 20.5 五阶段迁移法（核心）：每一步都带退路

这是全篇可打印的一页。**五个阶段之外还有第六步"摘老库"——它不是阶段，是收尾**，因为从切写那一刻起你已经不可回头，摘库只是把老库从"回滚素材"降级为"备份"。

```
阶段      0d        3d        6d        9d        12d       15d       22d
          │         │         │         │         │         │         │
①双写     ████████████████████████████████████████████████████████░░░  关双写
②全量     ─────████████
③增量     ──────────────██████████████████████████████████████████···  持续到切写后 24h
④影子读   ────────────────────────████████████████
⑤切读写   ─────────────────────────────────────███░███░███░███░███   按槽/按租户灰度
⑥摘老库   ──────────────────────────────────────────────────────────███

```

### 五阶段表（目标 / 可回滚方式 / 耗时 / 验收）

| 阶段 | 目标（唯一目的） | 关键动作 | 可回滚方式 | 耗时（1.6 TB 量级） | 验收标准（不达标不许进下一阶段） |
| --- | --- | --- | --- | --- | --- |
| **① 双写** | 让新库**从现在起**不再落后；暴露 schema 与语义冲突 | 先写权威（老库）后写影子（新库）；影子失败入待补队列；开关三档 | ✅ 关双写开关，秒级（新库整体作废） | 24~72 h（覆盖一次周批/月批） | 双写差异率 < 0.01%**且差异分布已归因**；影子失败率 < 0.05% |
| **② 全量搬迁** | 把存量按**可校验的最小单元**搬过去 | 主键游标分批（5,000 行/批）、限速、每批落 checksum | ✅ 删目标端数据重来（老库未动，零风险） | 4.6 h（限速）~ 8.2 h（安全限速） | 每批行数 + checksum 双对账通过；批次完成率 100% |
| **③ 增量追平** | 把"全量期间的增量"消化掉，让 lag 归零并稳住 | 位点与应用进度同事务落库；gap 检测；追平判定双条件 | ✅ 停消费、清目标增量、从任一 GTID 重放 | 88 min 追平 + 24 h 稳定观察 | lag < 3 s 连续 30 min，**且** 消费速率 ≥ 源端写入速率 ×1.5 |
| **④ 影子读比对** | 证明"读新库和读老库给出**同样的业务结果**" | 1% 稳定分桶双读、只比对不返回；payload hash + 关键字段全等 | ✅ 关影子开关，业务无感知 | 24~72 h（**必须覆盖一次低频批任务**） | 不一致率 = 0 连续 24 h；**每一条历史差异都有工单号** |
| **⑤ 切读写** | 把权威移交给新库，且按最小爆炸半径放量 | 按槽/按租户灰度切读（5% → 25% → 100%）→ 每档看 3 项指标 → 进冻结窗口切写 | ✅ 切读阶段：改映射版本，秒级；切写后：⚠️ 只剩 §20.10 的三种补救 | 切读 3 天 + 冻结窗口 10 min + 观察 7 天 | 切读各档 P99 / 错误率 / 结果比对全绿；切写后 7 天无 P1 |
| **⑥ 摘老库（收尾）** | 把成本与运维对象收回来 | 老库置只读 30 天 → 逻辑备份 + 快照 90 天 → 摘从库 → 摘主库 | ❌ 不可回滚（此时回滚等于重建） | 30~90 天 | 30 天内无"要回老库读"的请求；备份恢复演练成功 1 次 |

### 三个最容易偷懒、也最致命的地方

1. **阶段① 必须跨过一次"低频批任务"。** 定时结算、T+1 归档、月批大事务这些路径走的是**另一套写代码**，双写开关常常漏在这些路径上没接。事故一的 3 天缺口就藏在"只有 CDC 覆盖、没有双写覆盖"的区间里——**双写指标永远看不见历史缺口**。
2. **阶段④ 的"0 不一致"必须带归因门。** 不一致率 0.31% 时的正确动作是**停**，不是"再观察"；归因的定义是：每一条差异都能说清是"哪一类原因、属于哪个已知集合、是否已修复"。**说不清 = 不许切**（§20.6 的阈值表）。
3. **阶段⑤ 必须"同一个槽/同一个租户原子切"。** 同一实体的两次读取落在两个库上，而新库还没追到该实体的最新写入 → 用户看到"数据回退了"。这不是缓存脏，是数据分裂，且极难定位（`[03 · §03.10]` 第 4 阶段铁律）。

## 20.6 一致性校验三件套：从"看起来对"到"证得出来"

校验不是一道工序，是**三层漏斗**：便宜的粗筛在前，昂贵的精查在后，越往后越贵但越少跑。

```
                  ┌──────────── 源头：双写 + CDC 双通道 ────────────┐
 业务写 ─────────►│  Gate(tenant, pct)                              │
                  │    ├─① 权威库（同步；失败 = 业务失败）           │
                  │    └─② 影子库（幂等 upsert；失败 → 待补队列）     │
                  └───────┬──────────────────────────┬──────────────┘
                          │                          │
                   权威库 binlog              待补队列（Outbox 表）
                          │                          │
                          ▼                          ▼
                    CDC Consumer ──────────► 追平器（按主键幂等 upsert）
                          │                          │
                          └────────► 校验器 ◄────────┘
                                       │
              ┌────────────────────────┼────────────────────────┐
              ▼                        ▼                        ▼
      ① 行数 / checksum          ② 稳定抽样比对            ③ 全量行级 diff
        每批、每槽、5 min 一次     1% 稳定分桶，常驻         切读前跑一次，最贵
              │                        │                        │
              └────────────┬───────────┴────────────────────────┘
                           ▼
                      差异集 DiffSet
                    ├─ 可解释 → 自动重放（幂等）
                    ├─ 不可解释 → 人工队列（带工单号）
                    └─ 差异率 > 阈值 → 冻结切读（熔断）
```

### 三件套的实现与工具选型

| 层 | 查什么 | 成本 / 频率 | SQL / 工具 |
| --- | --- | --- | --- |
| **① 行数 + checksum 级** | "整块丢了没有" | 每批 5 min / 每槽每小时；全库 1.6 TB 约 4~6 min（覆盖索引 + 并行） | 分块聚合 SQL（下）；`pt-table-checksum --chunk-size=2000 --max-lag=5`；TiDB 用 `sync-diff-inspector` |
| **② 抽样比对** | "随机抓到的行对不对" | 常驻 1%、CPU 可忽略 | 稳定分桶 SQL（下）+ 应用层比对；`MySQL Shell util.compare_tables()` |
| **③ 全量行级 diff** | "到底哪几行、哪个字段不一样" | 切读前 1 次；23 亿行 checksum 定位差异块 ≈ 24 min，行级只查差异块 | 跨实例比：分块导出 `sha256sum` 比对（最稳）；同实例跨库：`LEFT JOIN`（下）；异构：DataX + 自研 diff 或 AWS DMS 校验 |

```sql
-- ① 槽级指纹：分块边界用「主键半开区间」，两侧必须用同一组边界
--    三个值一起看：cnt 抓"丢行/多行"，sig 抓"值变了"，max_id 抓"尾巴被截断"
SELECT slot,
       COUNT(*)                                                                    AS cnt,
       BIT_XOR(CRC32(CONCAT_WS('#', id, status, amount, UNIX_TIMESTAMP(updated_at)))) AS sig,
       MAX(id)                                                                     AS max_id
FROM   t_order
WHERE  id >= ? AND id < ?          -- 例如 [1024 段: 340000000, 350000000)
GROUP  BY slot
ORDER  BY slot;
-- 注意：BIT_XOR 对行序无关，但「两行相同内容」会互相抵消 → 必须与 cnt、max_id 同时判
```

```sql
-- ② 稳定抽样：同一 id 永远落同一桶（跑多次结果可比，不抖动）
SELECT id, status, amount, updated_at
FROM   t_order
WHERE  id >= ? AND id < ?
  AND  CRC32(CONCAT(id, 'mig-v3')) % 1000 < 10;   -- 1%；换 salt 即换一批样本
```

```sql
-- ③ 同实例跨库行级 diff：只对"checksum 不一致的块"跑，才能便宜
SELECT o.id,
       (n.id IS NULL)                      AS missing_in_new,
       (o.id IS NULL)                      AS extra_in_new,
       o.status, n.status, o.amount, n.amount, o.updated_at, n.updated_at
FROM   old_db.t_order o
LEFT   JOIN new_db.t_order n ON n.id = o.id
WHERE  o.id >= ? AND o.id < ?
  AND (n.id IS NULL
       OR n.status     <> o.status     OR n.amount <> o.amount
       OR n.updated_at <> o.updated_at)
LIMIT  1000;
-- 跨实例/跨云不要用 JOIN（会走 FEDERATED 或导出全表）：改成分块导出 → 两侧排序 → sha256 逐块比
```

### 差异率阈值定多少才敢切

**先说结论：敢切的判据不是某个百分比，而是"每一条差异都有不属于 bug 的解释，且解释集合已收敛"。** 百分比只用来决定"要不要开始归因"。

| 阶段 | 硬阈值 | 为什么是这个数 | 达不到的动作 |
| --- | --- | --- | --- |
| ① 双写期 | 差异率 < **0.01%**（1e-4） | 双写的正常差异只来自"非幂等副作用 + 部分失败"，量级天然在 1e-5 上下；到 1e-4 说明存在**系统性语义差** | 停止推进，逐条归因；把这个数当成 bug 积压看 |
| ② 全量后 | checksum 差异块 = **0** | 块级差异没有"正常"，只有"漏搬/搬错" | 重放该块，不许"整表重来" |
| ③ 增量追平 | lag < **3 s** 连续 **30 min**，且消费速率 ≥ 生产速率 **×1.5** | 30 min 覆盖一次 GC/批任务周期；×1.5 留出突发余量 | 见 §20.8 的"追不上怎么办" |
| ④ 影子读 | 不一致率 = **0 连续 24 h**（历史差异全部有关单） | 24 h 覆盖日内所有流量形态 | 冻结切读，回到归因 |
| ⑤ 全量行级 diff（切读前） | 差异行 = **0**，或 ≤ **0.0001%** 且**每一行都有工单号与结论** | 差异绝对值为 0 在跨系统迁移里不现实；可接受的只有"已归因的历史遗留" | 不许切；「0.01% 且未归因」是最危险的状态——它既是事故一，也是事故二 |

> ⚠️ **反常识一条**：差异率**从大变小**不可怕（说明修复在生效），**从大变没**才可怕——它通常意味着比对逻辑自己坏了（比如桶算法改了口径、比对只比了主键）。所以每轮比对必须附带一条"**心跳样本**"：往两侧各插 1 行已知不同的测试行，看校验器能不能报出来。**没抓到自己埋的错的校验器，等于没有校验器。**

## 20.7 增量追平：位点管理是这一节的全部

增量阶段 90% 的事故来自位点，10% 来自追不上。

### 位点载体四选一：只有一种能防事故

| 位点载体 | 存哪 | 优点 | 致命问题 |
| --- | --- | --- | --- |
| Kafka consumer offset | broker（消费者组） | 零开发 | **换 `group.id`、换 topic、重置 offset 都会静默丢失进度**（事故一的直接原因） |
| binlog `file + pos` | 中间件/配置文件 | 直观 | 位点与"数据是否已应用"**不在同一事务** → 应用挂了但位点已提交 = 永久缺口 |
| GTID set | 中间件 | 单调、可用 `GTID_SUBTRACT` 做 gap 检测 | binlog 过期后不可回补（要靠归档或备份） |
| **应用进度表（推荐）** | **目标库自己的表** | **位点与已应用数据同事务提交**；重启、换消费者、加并行度全部安全 | 多一次写；必须自己写 gap 检测 |

```sql
-- 推荐形态：把"已应用到哪"和"应用了什么"放在同一个事务里（目标库内）
CREATE TABLE mig_progress (
  task_id     VARCHAR(64) NOT NULL,
  gtid_set    TEXT        NOT NULL,        -- 已应用的 GTID 集合（或 offset 区间）
  applied_seq BIGINT      NOT NULL,        -- 单调递增，用于 gap 检测
  rows_applied BIGINT     NOT NULL,
  updated_at  DATETIME(3) NOT NULL,
  PRIMARY KEY (task_id)
) ENGINE=InnoDB;

-- 应用一批：upsert 业务行 + 更新位点，同一本地事务；断在任何一步都可安全重放
START TRANSACTION;
  /* 按主键幂等 upsert 本批业务行 */
  UPDATE mig_progress
     SET gtid_set = ?, applied_seq = applied_seq + 1, rows_applied = rows_applied + ?
   WHERE task_id = 'order-8to16' AND applied_seq = ?;   -- 乐观锁：seq 不连续即表示并发/重放
COMMIT;   -- affected_rows = 0 说明有人先提交了 → 本批作废重取，绝不覆盖
```

### 三条铁律

1. **位点必须落在"数据的同一侧"**。位点存 broker、数据存目标库 = 两个事务管理器 = 必然有窗口不一致。**唯一安全的形态是位点表在目标库、与业务 upsert 同事务。**
2. **位点必须是"已应用"而不是"已拉取"**。预取 10 万条缓存后提交 offset，崩溃即丢 10 万条。宁可吞吐减半，也要"应用完再提交"。
3. **必须有 gap 检测**，且它是独立任务：`SELECT GTID_SUBTRACT(源端已执行集合, 目标端已应用集合)` 非空 → 立即告警并冻结切读。事故一的 3 天缺口，任何一条 gap 检测都能抓到（可惜当时只监控了 lag 这个"瞬时值"）。

### 追平判定：双条件，缺一不可

```
条件 A（延迟）：lag = 源端最新 gtid 对应的时间戳 − now()  < 3 s，且持续 30 min
条件 B（余量）：v_consume ≥ v_produce × 1.5
为什么必须双条件：lag 可以在"业务低谷"时漂亮地归零，而 v_consume 根本没有余量；
                 一到高峰立刻反弹——单看 lag 归零就切写 = 在低谷里做了一个高峰会打脸的判断
```

### 追不上时怎么办（按代价从小到大，绝不按直觉）

| 手段 | 做法 | 真实效果 | 代价 / 边界 |
| --- | --- | --- | --- |
| **加并发** | consumer 并行度 4 → 16；按主键范围切分（不能按 topic 分区乱切，会破坏同主键顺序） | 吞吐近线性到瓶颈为止 | 并行度上限 = min(源库 IOPS 余量 / 单线程 IOPS, 目标库写连接上限, binlog 顺序边界) |
| **批量提交** | 逐行 apply → 500 行一批；去 index 后重建（仅对目标端影子表可行） | 2~4 倍 | 目标端崩溃时回放大一批；影子表期间唯一索引不可用 → 双写会写入重复 |
| **缩短链路** | 同机房部署、去掉逐行 JSON 反序列化、binlog 直读（去掉 MQ 中转） | 1.5~3 倍 | 需要改架构，1~2 天工作量 |
| **限流写入** | 对源库业务写限速（削峰） | 直接降低 v_produce | **几乎不可能被业务批准**；只在"已经出事"时作为止血手段 |
| **延长 binlog retention** | 从 3 天 → 7 天 | 不是提速，是**买时间** | 存储成本；且它防的是"追不上导致位点过期"这个二次事故 |
| **放弃实时、改为双跑** | 承认追不平，影子库只做"批同步 + 只读报表" | 保住了读，写仍留老库 | 计划目标降级——这是合法决策，前提是**明确写进计划**，不许悄悄降级 |

> **唯一的结构性判断**：如果 `v_consume < v_produce` 是**恒定**的（不是波动），那么你面对的不是"性能问题"，是"目标形态装不下这台写入机"。此时加任何机器都只是延长崩溃时间，正确的动作是**回到 `[03 · §03.6]` 重新选形态**。

## 20.8 双写：它不可能是原子的，那还能怎么办

### 先把"不可能"钉死

两个独立的存储引擎、两个事务管理器、两条网络路径。要原子只有 2PC/XA，而 XA 的实际代价是：提交阶段多两次网络往返（写 P99 +3~8 ms）、协调者故障留下悬挂事务（`eng/8` 的结论），以及**两库任一方不可用时业务直接不可用**——这正是双写要避免的事。

> 所以双写的目标不是"两边一样"，而是：**差异可枚举、可解释、可修复、不影响业务。**

### 顺序：永远先写权威库

| 顺序 | 权威库失败 | 影子库失败 | 读侧表现 | 判定 |
| --- | --- | --- | --- | --- |
| **先权威 → 后影子（✅）** | 业务失败，正常报错 | 入待补队列，业务成功 | 老库有、新库暂无 → 影子读会报差异，**这是"少一份副本"** | ✅ 唯一正确 |
| 先影子 → 后权威（❌） | 影子有、权威无 → **幻影数据** | 业务失败 | 切读后用户在列表里看到"不存在/不该存在"的订单 | ❌ 直接制造脏读 |
| 并行（❌） | 不确定谁成功 | 不确定 | 两端都可能多出或少掉 | ❌ 不可归因 |

**失败处理的固定顺序**：写权威（同步，失败=业务失败，无重试）→ 写影子（同步调用但**语义上是尽力而为**，超时 200 ms，异常不抛）→ 入待补队列（Outbox，与权威写同事务或紧随其后）→ 异步指数退避重试（1 s/5 s/30 s/5 min，5 次）→ 仍失败进 `mig_shadow_failed` 表 + 告警 + 计入差异率 → **绝不回滚业务事务**。

### 四类系统性差异（双写差异率的"底噪"，必须全部显式处理）

| 差异类型 | 具体来源 | 处置 |
| --- | --- | --- |
| **非幂等副作用** | 自增主键、`now()`/`CURRENT_TIMESTAMP`、`UUID()`、`ON UPDATE CURRENT_TIMESTAMP`、触发器 | ID 用应用侧生成（雪花/号段）；时间戳由应用传入同一值；目标端禁用触发器 |
| **语义差异** | 枚举值域、字符集排序（事故二）、时区、浮点精度、`NULL` 与空串、大小写敏感 | 建立"类型/语义映射表"并写测试；枚举**先扩值域再双写** |
| **并发乱序** | 同一行两次更新经两条路径乱序到达 → 影子短暂落后 | 带版本号/`updated_at` 做 last-writer-wins；**追平阶段以源端 binlog 为准强制覆盖** |
| **部分失败** | 写入超时但实际成功 → 重试造成重复 | 幂等 upsert（`ON DUPLICATE KEY UPDATE` / `ON CONFLICT DO UPDATE`）；绝不使用纯 `INSERT` |

### 骨架代码一：Java 双写 + 抽样比对（Spring / JdbcTemplate）

```java
@Service
public class OrderDualWriter {
    private final JdbcTemplate oldDb, newDb;      // 两个 DataSource，绝不共用事务管理器
    private final MigGate gate;                   // 按租户 + 稳定分桶，热更新，故障一键关
    private final ShadowPendingQueue pending;     // 影子失败入 Outbox，不阻塞业务

    /** 事务只包住权威库：绝不把两个库放进同一个 @Transactional */
    @Transactional(transactionManager = "oldTx")
    public void update(Order o) {
        oldDb.update("UPDATE t_order SET status=?, amount=?, updated_at=?, ver=ver+1 WHERE id=?",
                     o.status(), o.amount(), o.updatedAt(), o.id());   // ① 权威：失败=业务失败
        if (!gate.on(o.tenantId(), o.id())) return;
        try {
            int n = newDb.update("""
                INSERT INTO t_order (id, status, amount, updated_at, ver) VALUES (?,?,?,?,?)
                ON DUPLICATE KEY UPDATE status=VALUES(status), amount=VALUES(amount),
                    updated_at=GREATEST(updated_at, VALUES(updated_at)), ver=GREATEST(ver,VALUES(ver))
                """, o.id(), o.status(), o.amount(), o.updatedAt(), o.ver());
            metrics.counter("mig.dual_write.ok").increment();
            if (n == 0) pending.enqueue(o.id(), "upsert-noop");        // 影子行缺失，记差异
        } catch (Exception e) {
            pending.enqueue(o.id(), e.getClass().getSimpleName());     // ② 影子失败：记账，不抛
            metrics.counter("mig.dual_write.failed").increment();
        }
    }

    /** 抽样比对：稳定分桶（同一 id 永远同一档，多次运行可比），1% */
    public void verify(long id) {
        if (Math.floorMod(Long.hashCode(id), 1000) >= 10) return;
        Order a = oldDb.queryForObject(SQL_OLD, ROW, id);              // ③ 差异落表，绝不吞
        Order b = newDb.queryForObject(SQL_NEW, ROW, id);
        if (b == null || !a.sameContentAs(b)) diffSink.write(id, a, b);
    }
}
```

### 骨架代码二：Go 迁移任务（批次边界 + 断点续跑 + 限速）

```go
// 主循环：批次 = 主键半开区间；进度落目标库；失败批次隔离而非中断
func (m *Migrator) Run(ctx context.Context) error {
	for {
		b, err := m.claimNextBatch(ctx) // UPDATE mig_batch SET state='RUNNING',owner=?,heartbeat_at=NOW()
		if err != nil {                  //  WHERE state='PENDING' ORDER BY id LIMIT 1 （乐观锁认领）
			return err
		}
		if b == nil {                    // 无待跑批次
			return nil
		}
		if err := m.runBatch(ctx, b); err != nil {
			m.quarantine(ctx, b, err)         // 隔离：state='QUARANTINED'，不阻塞后续批次
			if m.failRate() > 0.01 {          // 失败率熔断：整体停下等人看
				return ErrCircuitOpen
			}
			continue
		}
	}
}

func (m *Migrator) runBatch(ctx context.Context, b *Batch) error {
	rows := make([]Order, 0, m.batchSize)
	// 半开区间 [start_pk, end_pk) → 边界不重不漏；绝不用 LIMIT offset（事故三）
	if err := m.src.QueryRows(ctx, `SELECT * FROM t_order WHERE id >= ? AND id < ? ORDER BY id`,
		&rows, b.StartPK, b.EndPK); err != nil {
		return err
	}
	if err := m.limiter.Wait(ctx, len(rows)); err != nil { // 令牌桶：速率由 QPS/IO util 双维动态调整
		return err
	}
	if err := m.dst.UpsertAll(ctx, rows); err != nil {     // 按主键 upsert → 整批可重复执行
		return err
	}
	return m.markDone(ctx, b, len(rows), checksum(rows))    // 同事务写 state/rows/sig
}
```

## 20.9 停写窗口最小化：能不能做到零停写

**能，但不是所有场景都能。** 说"我们能零停写"的方案，通常是把停写藏进了某个没被告知的瞬间。

| 场景 | 零停写？ | 为什么 | 若必须停，窗口多长 |
| --- | --- | --- | --- |
| 同构扩容（分片翻倍） | ✅ 可以 | 分片映射是配置，**整表原子替换**（`[03 · §03.10]` 骨架代码） | 0 |
| 异构换库（结构不变） | ✅ 基本可以 | 双跑比对 + 逐表切读；proxy 层可做"表级切换" | 0，**除非改 ID 生成器** |
| 拆服务（数据所有权转移） | ❌ 不行 | 同一行不能有**两个写者**，所有权交接的那一瞬必须冻结 | ≤2 min |
| 全局唯一序 / 自增 ID 重排 | ❌ 不行 | 号段切换点之后的历史 ID 依赖与外部引用要对齐 | 2~10 min |
| 无主键 / 无 `updated_at` / 无 binlog 权限 | ❌ 不行 | **无法做增量**，只能全量 + 冻结 | 全量时长（小时级）——先补主键与 binlog，别硬干 |
| 跨云跨地域 | ⚠️ 看路由 | 应用连接串/DNS 生效时间决定 | 分钟级（受 TTL 与客户端重连影响） |

### 停写窗口内要做完的 7 件事（顺序不可换）

| # | 动作 | 时间预算 | 失败即回退到 |
| --- | --- | --- | --- |
| 1 | 关双写开关（确认全链路包括批任务已生效） | 30 s | 开双写 |
| 2 | 老库置只读（`SET GLOBAL super_read_only=ON`，保留迁移账号白名单） | 20 s | 置回可写 |
| 3 | 等 CDC lag 归零（**容差 0，含 gap 检测为空**） | ≤60 s | 解只读 |
| 4 | 最后一批全量校验（只校"冻结后变化的行"，走变更集不扫全表） | ≤120 s | 解只读 |
| 5 | 路由切到新库（配置中心推送 + 客户端 refresh 生效确认） | 20~60 s | 切回路由版本 |
| 6 | 冒烟用例 20 条（下单/改单/退款/查列表/对账查询各 4 条） | 60 s | 切回路由版本 |
| 7 | 开写 + 打开"切后双写"（老库继续收一份，用于 §20.10 的反向同步） | 30 s | —— |

三条让窗口"缩得下去"的前置条件：

- **把 6 号冒烟用例提前自动化并演练 3 次**。窗口内的手速靠不住，自动化的 20 条能在 60 s 内给出绿/红。
- **把路由 refresh 间隔从 60 s 改到 5 s**（提前一个版本发布）。这是唯一值得为"缩窗口"单独发版的动作。
- **窗口外做完 90% 的准备**：账号、白名单、开关、脚本、回滚包、值守表——窗口内只允许"按按钮"，不允许"改脚本"。

## 20.10 回滚的残酷真相

### 残酷的那句话

> **切到新库运行 N 小时后回滚，必然丢这 N 小时的数据。**
> 因为没有被写入老库的东西，回滚这个动作本身无法凭空生成。

所以"能不能回滚"不取决于你有没有开关，取决于**你在切写之后还留没留一条反方向的数据路径**。这条判断有三种补救，选哪一种决定了你的回滚窗口有多长。

| 补救 | 做法 | 回滚窗口（可无损退回的最长时间） | 代价 | 前提 |
| --- | --- | --- | --- | --- |
| **① 反向同步（推荐）** | 切写后保留"新 → 老"的反向 CDC（或应用层反向双写），老库持续收到增量 | **≈ 反向同步延迟（秒级）~ 24 h** | 老库写入成本 + 反向链路运维；**老库 schema 必须能表达新值域**（否则事故一阻断点③） | 老库未删除、schema 兼容、有反向位点 |
| **② 双写保留** | 切写后继续双写（新库权威、老库影子）N 天 | **N 天**（但老库侧可能有不一致，需校验） | 写放大 2 倍持续 N 天；差异修复方向必须单向（往老库补），否则制造阻断点② | 同上 + 老库写容量 |
| **③ 接受丢失** | 不回老库，用业务日志/消息重放补单 | 0（有损） | 需人工核对；对已产生外部副作用的操作（发货、扣款）不可逆 | 有完整业务日志与可重放的消息 |

**推荐组合**：① 为主（小时级窗口）+ ③ 兜底（明确写出"超过窗口就向前修"）+ 定期演练"从老库读回一条切写后的数据"，验证反向链路真的活着。**没演练过的反向链路等于不存在。**

### 回滚决策树（切读/切写之后出问题时，按图走，不要按直觉走）

```
                   发现问题（切读或切写之后）
                               │
                 ┌─────────────▼──────────────┐
                 │ Q1 新库有没有"只在新库"的写入？│
                 │   （切写后的数据 / 只写新库路径）│
                 └───┬────────────────────┬───┘
                没有 │                    │ 有
                     ▼                    ▼
        ┌────────────────────────┐   ┌──────────────────────────────────┐
```

### 三条铁律（写进 runbook 第一页）

1. **`T_no_return` 必须是一个具体时刻。** 例："09-10 00:20 切写完成 + 24 h 反向同步在线 → 回滚截止 09-11 00:20；此后只剩向前修。" **没有截止点的回滚预案是安慰剂。**
2. **回滚也要演练，且演练时必须真的有数据被写进新库。** 演练里"切过去再切回来"什么都没丢，会让你误判窗口长度。
3. **回滚的决策者是"数据 owner"而不是"值班 SRE"。** 因为回滚 = 主动丢弃数据，这是业务决策；运维只能执行。事故一的 58 分钟里，最浪费时间的就是"等一个能决定丢数据的人"。

## 20.11 断点续跑与限流：任务要能活过第一次失败

### 批次划分：边界必须可重放

| 划分方式 | 判定 | 理由 |
| --- | --- | --- |
| **主键半开区间 `[start_pk, end_pk)`** | ✅ 唯一正确 | 边界确定、可重复、可跳过、可并行；`end_pk` 在一次迁移开始时**一次性算好**（对主键取分位点），全流程不变 |
| `LIMIT offset, N` | ❌ | offset 随写入漂移 → 重跑时漏行/重行（事故三）；深 offset 本身是 O(offset) 成本 |
| `WHERE updated_at > ?` 单调水位 | ⚠️ 仅增量阶段 | 时钟回拨、同毫秒多行会漏；必须叠加主键条件 |
| 按 `id % N` 取模 | ⚠️ 并行时可用 | 只适合"分片并行"，不适合"提交单元"（无法做批次级对账） |

**批次大小**：`min(5,000 行, 8 MB)`。行宽大的表按字节切，否则一批 8 MB 变 800 MB（大字段表），一次 OOM 就是事故三。

### 进度持久化：两张表 + 一个状态机

```sql
CREATE TABLE mig_task (
  task_id    VARCHAR(64) PRIMARY KEY,
  src_dsn    VARCHAR(255) NOT NULL, dst_dsn VARCHAR(255) NOT NULL,
  state      VARCHAR(16) NOT NULL,          -- PREPARING / DUAL / FULL / CATCHUP / SHADOW / CUTOVER / DONE / FROZEN
  created_at DATETIME(3) NOT NULL, updated_at DATETIME(3) NOT NULL
) ENGINE=InnoDB;

CREATE TABLE mig_batch (
  id         BIGINT AUTO_INCREMENT PRIMARY KEY,
  task_id    VARCHAR(64) NOT NULL,
  tbl        VARCHAR(64) NOT NULL,
  start_pk   BIGINT NOT NULL, end_pk BIGINT NOT NULL,   -- 半开区间
  state      VARCHAR(16) NOT NULL,          -- PENDING/RUNNING/DONE/FAILED/QUARANTINED
  rows_cnt   BIGINT NULL, sig CHAR(32) NULL,           -- 落 checksum → 重跑后可对账
  owner      VARCHAR(64) NULL, heartbeat_at DATETIME(3) NULL,
  attempt    INT NOT NULL DEFAULT 0,
  err_msg    VARCHAR(512) NULL,
  UNIQUE KEY uk_rng (task_id, tbl, start_pk),
  KEY idx_state (task_id, state, id)
) ENGINE=InnoDB;
```

状态机：`PENDING → RUNNING → DONE`；`RUNNING` 心跳超时 5 min → 重新认领（`attempt + 1`）；`attempt > 3` → `QUARANTINED`；`QUARANTINED` 累计 > 1% → 整个任务 `FROZEN`。

### 幂等重跑的四条硬规矩

1. **只允许 upsert，不允许 insert**（`ON DUPLICATE KEY UPDATE` / `ON CONFLICT DO UPDATE`）。任何纯 `INSERT` 都在赌"这批只跑一次"。
2. **整批可重复**：同一批次跑 1 次和跑 10 次结果必须一致（`rows_cnt` 与 `sig` 相同）。
3. **重跑前先 dry-run 比差异**：先算本批两侧的 `cnt/sig`，一致就跳过（省掉 70% 的无效重跑）。
4. **失败批次隔离而不是重试到底**：`QUARANTINED` 批次在"所有批次跑完后"集中处理（多数是脏数据：超长字符串、非法编码、主键冲突），**绝不阻塞主流程、也绝不静默跳过**。

### 限流：按 QPS 还是按 IO util

**两个都要，但它们是不同层的闸门**：QPS/字节速率是"事前计划速率"，IO util 与复制延迟是"事中熔断信号"。

| 闸门 | 指标 | 采集方式 | 阈值 | 动作 |
| --- | --- | --- | --- | --- |
| 字节速率（计划） | 迁移读 MB/s | 任务自身计数器 | 低峰 96 MB/s、白天 20 MB/s（按 24 h 曲线） | 令牌桶阻塞 `Wait()` |
| 源库 IO | `%util` | `iostat -x 1` / Prometheus node_exporter | > 70% 持续 60 s | 速率减半；> 85% 暂停 30 s |
| 源库并发 | `Threads_running` | `SHOW GLOBAL STATUS` | > 核数 × 1.5 | 暂停 10 s |
| 复制延迟 | `Seconds_Behind_Master` | 从库 | > 5 s | 暂停 60 s（保护的是读业务） |
| 目标库写 | 写 P99 / 锁等待 | 目标库监控 | P99 > 50 ms | 批次减半 + 降并发 |
| 业务 SLO | 业务接口 P99 | APM | 超 SLO 20% | 整体降速到 1/4，并告警给迁移 owner |

### 24 h 速率曲线（"低峰"不是一个时间点，是一条曲线）

| 时段 | 业务压力 | 迁移速率 | 说明 |
| --- | --- | --- | --- |
| 00:00–06:00 | 谷（~15% 峰值） | 100%（96 MB/s） | 主战场：约 2.6 h 可搬 0.9 TB |
| 06:00–09:00 | 爬升 | 50% | 让业务先起 |
| 09:00–21:00 | 峰（100%） | 20%（20 MB/s） | 只保"不落后"，不追求进度 |
| 21:00–24:00 | 回落 | 60% | 二次冲刺 |

> **一条纪律**：迁移任务的限速**必须由业务指标闭环控制**，而不是配一个固定值。固定值在业务低谷时浪费窗口、在高峰时打挂线上——两个方向都错。事故三的本质就是"没有这条闭环"。

## 20.12 L0 → L5：数据量决定迁移形态，不是"技术栈"

**10 GB 和 100 TB 的迁移不是同一件事加机器。** 下面这张表可以直接用来回答"我们这套系统该用哪种迁移方式"。

| 阶段 | 数据量 | 迁移形态 | 停写窗口 | 关键风险 | 回滚方式 / 代价 |
| --- | --- | --- | --- | --- | --- |
| **L0** | 10 GB | `mysqldump` + 单次导入 | 20~40 min | 停机本身 | 备份还原（分钟级） |
| **L1** | 100 GB | 主从复制（把新库做成从库）→ 提升为主 | 5~15 min | 复制延迟、GTID 断裂 | 提升旧主（分钟级） |
| **L2** | 1 TB | 双写 + 并行全量（DataX/自研）+ CDC 追平 | 5~10 min | 位点、双写差异 | 熔断开关 + 反删目标端（小时级） |
| **L3** | 10 TB | 虚拟槽分片 + 逐槽双写 + 槽级 checksum + 影子读 + 按槽切读 | **0** | 同槽原子性、跨槽查询消失 | 改映射版本（**秒级**） |
| **L4** | 100 TB | 物理备份（XtraBackup 并行流）+ binlog 归档追平 + **多轮迁移**（先冷后热、先大表后小表） | 0~10 min | 追平永远差一点（表多、链路长）；备份恢复窗口是关键路径 | 反向同步（小时级）；**回滚窗口实质只剩几小时** |
| **L5** | >100 TB / 跨域 | 按单元（租户/地域）整体迁移 + 物理介质 + 双向对账 + 多波次常驻（双写常态化） | 分钟级（路由） | 两侧工具不一致、验收口径不一致、跨域光速 | 单元级回切（小时~天级） |

**读懂这张表只需要抓住两条：**

1. **数据量越大，停写窗口越短、回滚代价越高。** L0 可以停 40 min 但回滚便宜；L4 只能停 0 但回滚几乎不可行。**这就是为什么"越大的库越要早迁"**——等到 L4 的量级才动手，等于放弃了回滚权。
2. **L3 是唯一"回滚比迁移便宜"的形态**（改一个映射版本）。所有能在 L3 解决的问题，都不要拖到 L4 用备份+重放去解决。

## 20.13 这个形态特有的崩法

不是"高可用"套话，是迁移这件事自己的失效点。

| 崩法 | 长什么样 | 定位方法 | 预防 |
| --- | --- | --- | --- |
| **位点静默跳变** | 指标全绿，但有整段增量没应用 | 对比"源端已执行 GTID"与"目标端已应用 GTID"（gap 检测） | 位点与应用进度同事务；禁止换 group.id/重置 offset 进生产 |
| **双写掩盖历史缺口** | 双写差异率 0.000x%，切读后大面积数据缺失 | 双写差异率**不能**作为历史一致性的证据；要看全量 diff | 阶段④必须有全量行级 diff，不能只靠双写差异 |
| **校验通过但语义错** | 行数、主键、checksum 全对，业务口径错（事故二） | 业务口径对账（同一报表在两侧跑，比金额/笔数） | 三件套外加"业务口径比对"一层；异构换库必须有 SQL 回归集 |
| **回滚污染** | 老库被修复脚本反向写过，回滚回去是更旧的错数据 | 老库侧保留"最后一次外部写入时间"，回滚前比对 | 修复脚本**单向**；老库侧版本水位；回滚前必须校验而非直接切 |
| **追不上** | lag 单调上升，加了 consumer 只撑 2 h | 对比 `v_consume` 与 `v_produce` 的比值 | 提前压测消费速率；明确"结构性追不上"的判据与降级方案 |
| **切读后读分裂** | 同一用户刷新两次看到不同数据 | 按实体统计"读落到几个库" | 同槽/同租户原子切；路由表整表替换 |
| **路由缓存未刷新** | 部分用户"回退"到旧数据，比例稳定但不是 100% | 比对客户端路由版本分布 | refresh 5 s + 切后校验版本分布（不是校验"我推了"） |
| **binlog 过期** | 想出问题补数据时发现归档已被清理 | 每日检查最早可用 binlog 时间 | retention ≥ 迁移全程 + 30 天；另存对象存储归档 |
| **自增 ID 冲突** | 双写期两侧各自自增，合并/回切时主键撞车 | `SELECT COUNT(*) FROM ... WHERE id IN (…旁侧区间…)` | ID 由应用生成；两侧号段不重叠（`[06 · §06.11]` 的 ID 空间冲突项） |
| **任务无断点** | 崩一次从头再来，窗口耗尽后白天跑（事故三） | 看 `mig_batch` 的 `RUNNING` 心跳与重跑次数 | 半开区间 + 心跳认领 + 幂等 upsert |

## 20.14 砍掉 90% 预算还能不能跑

**结论先说：迁移的预算是"环节预算"，砍环节等于砍退路；能砍的只有"范围"。** 把机器、人力、时间砍到十分之一，合法的操作是下面四种缩范围，各自代价明确：

| 缩范围的做法 | 能砍掉什么 | 保留哪些环节 | 代价（必须签字） |
| --- | --- | --- | --- |
| **只迁热数据**（近 18 个月，冷数据留老库只读） | 全量时长 ÷ 3~4（1.6 TB → 0.45 TB）；机器 ÷ 4 | 双写、增量、影子读、按槽切读全部保留 | 长期"双库共存"：老库不能摘，运维对象不减；跨库查询要写兼容层 |
| **砍场景数**（先做同构扩容，异构换库延后一个季度） | 人力 50% | 本期只维护一套迁移工具链 | 异构换库的技术债继续累积（自增、字符集、时区这些坑晚发现晚付） |
| **降 SLA：接受 30 min 停写窗口** | 影子读 + 按槽灰度两个阶段；增量追平可以不做 | 双写、全量、冻结窗口 | **回滚从秒级变成小时级**——因为 30 min 窗口意味着切写后立刻失去反向余额度 |
| **砍校验层**（只做 checksum + 抽样，不做全量行级 diff） | 校验机时 60%、2 人天 | 双写差异 + 块级 checksum | 差异**归因能力**归零：出问题时你只能说"有差异"，说不出"哪几行、为什么"（事故一的正解就在这里） |

**唯一不许砍的三件事（砍了就变成事故）：**

```
① 位点与应用进度同事务      —— 砍掉 = 事故一（3 天静默缺口）
② 差异归因门（差异不清不许切）—— 砍掉 = 事故一（0.31% 当作"延迟正常"切了）
③ 老库 30 天不动 + 备份可恢复 —— 砍掉 = 回滚与向前修同时失去素材
```

> 一句给老板的话：**"迁移不是可以省钱的工程，是可以拖的工程。拖一年，数据量涨一倍，回滚代价涨一个量级。"** 砍预算的正确姿势是"缩范围 + 缩短双写时长 + 提高自动化"，而不是"少校验一遍"。

## 20.15 十分钟答题卡

被问「怎么把一个 2 TB 的生产库迁到新架构，业务不能停」时，按这个顺序讲，**不要从"我用 DataX"开始**：

```
1  定场景    同构扩容 / 异构换库 / 拆服务 / 跨云？——它决定停写窗口与回滚代价（§20.3）
2  算四个数  全量 T=D/(N×v)；追平 T=L/(v_consume−v_produce)（为负就追不平！）；
             迁移 IOPS 占源库余量 ≤40%；冻结窗口 = 7 步之和 ≈ 6~10 min
3  立三角    一致性用"可枚举"换，回滚用"窗口"换，不停机用"冻结瞬间"换——三笔交换写进第一页
4  五阶段    双写 → 全量 → 增量追平 → 影子读 → 切读写（+ 摘老库作为收尾），每阶段带回滚方式与验收
5  双写      先权威后影子；影子失败入 Outbox 不抛；差异四类（幂等副作用/语义/乱序/部分失败）
6  位点      位点表放目标库、与业务 upsert 同事务；"已应用"而非"已拉取"；独立 gap 检测
7  校验      行数+checksum（BIT_XOR(CRC32)）→ 稳定分桶抽样 → 切读前一次全量行级 diff；
             敢切的判据是"每条差异都有解释"，不是某个百分比
8  回滚      切写 N 小时后回滚丢 N 小时；补救三选一：反向同步 / 双写保留 / 接受丢失；
             写死 T_no_return 时刻；回滚决策者是数据 owner
9  任务      半开区间批次 + 心跳认领 + 幂等 upsert + 失败批次隔离 + 失败率 1% 熔断；
             限速按 24h 曲线闭环调，不配固定值
10 砍预算    砍不掉环节，只能缩范围（热数据/场景数/SLA/校验层）；三件事不许砍：
             位点同事务、差异归因门、老库 30 天不动
```

现场被追问时最值钱的三句：

- 「**双写差异率看不到历史缺口**，所以在切读前必须跑一次全量行级 diff，而且差异必须归因。」
- 「**回滚不是开关，是反向数据路径**；切写之后我们保留 24 h 反向同步，T_no_return 是 9-11 00:20。」
- 「**我们的追平速率是生产速率的 4.1 倍**，这个比值小于 1.5 就不许切写——lag 归零只说明现在是低谷。」
