# 24. 多租户 SaaS 底座与配额计费：隔离级别的不可能三角

> **状态**：`已完成（初稿）` ｜ **所属**：第三部分 · 案例（族 F·平台） ｜ **编号**：24 / 26
> **本篇定位**：族 F 的第一篇，讲**「一个产品卖给一万家公司」时底座怎么装配**。它不重复 `llm/44` 的 Agent 平台治理（那里讲 GPU 池、Prompt 隔离、Run 计量），本篇讲**通用 SaaS 的业务库、路由、租户生命周期与共享资源的公平性**。核心论点只有一个：**隔离级别（行级 / Schema 级 / 库级）与成本、可运维性构成一个不可能三角——选行级最便宜但最容易被大租户拖死，选库级最安全但运营成本爆炸**。底座的全部设计，都是在这个三角里给不同租户找不同落点。
> **读法**：§24.4 的三方案对比大表是全篇骨架，评审时先填它；§24.5 说明为什么**纯一种隔离方式一定错**；§24.7 的"漏一处就全泄露"门禁与 §24.8 的池化隔离清单是最该直接抄走的两节；赶时间读 §24.16。

## 24.1 引子：三起事故，三种隔离级别的代价

### 事故一：一个租户导入 2000 万条数据并跑全表统计，把共享库打挂 40 分钟（2025-11-18）

平台上 12,600 个付费租户共用一个 MySQL 集群的 3 台 8C32G 实例，行级隔离（同库同表 + `tenant_id`）。T-8471 是铂金租户，占平台存储 0.9%，被销售口头承诺"什么都能导"。

| 时间 | 事件 | 数据 |
| --- | --- | --- |
| 10:02 | T-8471 提交客户明细批量导入，一次性 2000 万行 | 该租户日常占平台写入 0.4% |
| 10:03 | 导入走**同步**接口，客户端 32 并发 × 每批 5,000 行 | 4,000 批，压缩在 6 分钟内 |
| 10:05 | 共享库写入 IOPS 从 3,200 涨到 **18,400**（规格上限 10,000） | 单租户把 IO 用成 5.7 倍 |
| 10:06 | 同实例 4,247 个租户的查询 P99 从 90 ms 涨到 **6.4 s** | 读写互相排队 |
| 10:12 | T-8471 的 BI 报表触发 `ANALYZE TABLE` + 全表 `GROUP BY` | `rows_examined` = **2,140 万** |
| 10:14 | 连接池 400 全占满，健康检查连续失败，实例被 LB 摘除 | 4,247 租户 **100% 不可用** |
| 10:18 | 揪出凶手：慢日志里唯一一条 `rows_examined > 1000 万` 的 SQL | 定位耗时 12 分钟 |
| 10:22 | kill 会话；但已写入 1,400 万行的导入事务开始回滚 | 大事务回滚 18 分钟 |
| 10:40 | 回滚完成、连接池恢复，SLO 回到基线 | **不可用 40 分钟** |

**受影响租户 4,247（直接）+ 6,783（同集群共用元数据库的计量与路由查询超时，降级为只读）= 11,030，占付费租户 87.5%；失败请求 312 万次；9 家触发 SLA 赔付条款，赔付 186 万元。** T-8471 自己也丢了 6 分钟的导入进度——它同样很委屈：没人告诉它有上限，也没人告诉它大租户不该住共享库。

根因三条，都不是"运维手滑"：

1. **只有行级隔离，且没有任何租户维度的资源边界**——数据行是隔离的，IO、连接、CPU、锁是共享的，等于"账户隔离、钱包共享"；
2. **批量导入走同步大事务**——4,000 批压成 6 分钟，等价于把一次离线迁移塞进 OLTP 库（正解见 §24.8 的异步通道）；
3. **没有"相对基线异常"检测**——大盘 QPS 只涨了 11%，单租户涨了 57 倍，被"整体正常"掩盖（同 `eng/20`、[09 开放平台 · §09.1](09-open-platform.md) 事故二）。

### 事故二：一条漏了 `tenant_id` 的 SQL，把 8 万家租户的客户名单暴露了 6 天（2025-06-04）

营销模块新加"客户标签筛选"，走的是手写 XML 里的动态 SQL，`<if test="tagId != null">` 分支没有带 `tenant_id`（拦截器只做了"追加条件"的自动补全，`UNION` 子查询逃过了改写）。上线 6 天后由客户侧发现同行数据出现在筛选结果里。

| 时间 | 事件 | 数据 |
| --- | --- | --- |
| 06-04 15:00 | 发布 v3.7.2，新增标签筛选接口 | 1 个 mapper 方法 |
| 06-04 15:00–06-10 | 该接口被 2,140 个租户调用 | 跨租户返回 87 万条记录 |
| 06-10 09:20 | 租户 B 的运营发现列表里有租户 A 的客户手机号 | 首个报告 |
| 06-10 10:40 | 定位：`UNION ALL` 的第二段没有 `tenant_id` 谓词 | 该分支 4 个月无人改动 |
| 06-10 12:00 | 热修 + 全量审计日志回放，确认影响 2,140 个租户 | — |
| 06-11 ~ 07-20 | 逐家通知、数据删除确认函、监管报备 | 罚款 320 万元，2 家中型客户解约 |

**根因只有一条：越权防护挂在一个"试图变聪明"的拦截器上，而不是挂在"默认拒绝"上。** 一条 SQL 的上线路径有 mapper XML、`@Select` 注解、JdbcTemplate、定时任务、运营后台、数据修复脚本六条，只要有一条没被覆盖，全部租户数据一起暴露。

### 事故三：为一个租户恢复 3 天前的数据，全平台回滚了 6 小时（2025-09-21）

租户 T-3302 的运营误删了 1.2 万条商品（真实误操作）。行级隔离下没有"单租户时间点恢复"这个能力，只有"整个实例 PITR"。运维选择：克隆实例到 3 天前 → 过滤出该租户数据 → 回灌。克隆 6.4 TB 用了 5 小时 40 分，期间库锁与 IO 抖动导致全平台 P99 劣化 3 倍。

**三起事故分别对应隔离级别的三个代价：噪声邻居（行级）、越权（行级缺少强制边界）、单租户运维能力缺失（行级根本做不到）。** 而换成库级，前两个问题一起消失，代价立刻转成 §24.3 的账单和 §24.10 的运维工时——这就是本篇的不可能三角。

## 24.2 到底是什么：多租户 = 隔离 + 配额 + 账本 + 删除

**定义**：多租户底座 = 让 N 个互不信任的主体共享同一套部署，同时能对每个主体**证明**四件事：**数据没串（隔离）、拿到的资源是他付钱买的那份（配额）、账能对上（账本）、数据能删干净（删除）**。缺任何一条，它只是"带 `tenant_id` 字段的单体应用"。

| 你以为的多租户 | 为什么不是 | 缺了它会怎样 |
| --- | --- | --- |
| 每张表加 `tenant_id` | 字段是**约定**，隔离是**机制**；约定靠人守，机制靠系统守 | 事故二 |
| 加个租户管理后台 | 后台管的是"租户元数据"，不解决共享资源的分配与追责 | 事故一：没人知道是谁打挂的 |
| 给每个租户一个数据库账号 | 账号只能挡"连库"，挡不住"同库同表里的行" | 一个账号看到全表 |
| 上 Kubernetes 就隔离了 | K8s 隔离的是**进程与 CPU**，不是你的业务库、缓存 key、MQ 分区 | 库和缓存照样互相踩 |
| 做一套权限系统 | 权限回答"人能不能做这个动作"，多租户还要回答"这个动作属于哪个租户的账" | 越权 + 账单串户 |

### 唯一真问题

> **隔离级别（行级 / Schema 级 / 库级）与成本、可运维性三者构成一个不可能三角：**
> **行级最便宜、最容易统一运维，但故障域是全体——一个大租户就能拖死所有人；**
> **库级/实例级最安全，但每租户成本高一个数量级、DDL 与升级从"一次"变成"一万次"。**
> **你只能同时要两样，而且必须为不同的租户要不同的两样。**

```
                    隔离度 ↑（大租户打不死别人）
                          /\
                         /  \   ← 要"隔离 + 可运维"，代价是钱：
                        /    \     每租户独立库/实例，成本 ×283
                       /      \
          【库级/实例级】       【Schema 级】
                     /          \
                    /            \  ← 要"隔离 + 便宜"，代价是运维：
                   /              \    DDL/升级/备份从 1 次变 N 次
                  /                \
        ─────────【行级：共享库表】──────────→ 成本 ↓ / 可运维性 ↑
                    ← 要"便宜 + 可运维"，代价是隔离：
                      一个租户的 SQL 能打死全部 5,000 租户
```

从这条矛盾推出的全部设计：

| 从不可能三角推出的约束 | 推出的设计 |
| --- | --- |
| 纯一种隔离一定错（租户规模是重尾分布，§24.5） | **混合隔离 + 升级通道**：默认行级，大租户逐级升档 |
| 行级下"数据不串"只能靠代码自觉 | **默认拒绝**的强制裁剪 + 数据库 RLS 兜底 + ArchUnit/测试门禁（§24.7） |
| 行级下"资源不抢"必须显式池化 | 连接池/线程池/队列按 tier 分池 + 租户维度限流（§24.8） |
| 升级必然发生，且不能停机 | 迁移流水线按租户原子切换（§24.9，引用 → [20 数据迁移](20-data-migration.md)） |
| 隔离级别决定运维能力上限 | 单租户备份/恢复/删除按档位能力的显式矩阵（§24.10） |
| 路由表是混合隔离的代价 | 租户 → 库/实例映射必须按分布式系统设计（§24.13） |

## 24.3 量级与预算：先把分布和单价算出来

### 平台量级

```
在册租户      100,000（付费 12,000 / 试用 88,000）
日 API 调用   42 亿        均值 4.9 万 QPS   峰值 ×5.3 = 26 万 QPS
业务数据      380 TB       日增 1.1 TB
DB 实例       96 台（8C32G ×72 + 16C64G ×24）  月成本 ¥92 万
缓存/对象/MQ  月成本 ¥31 万   合计基础设施 ≈ ¥123 万/月
```

### 租户规模分布：重尾是全部设计的前提

| 分位 | 家数 | 月调用量 | 存储 | 累计用量占比 |
| --- | --- | --- | --- | --- |
| p50 | 50,000 | 42 万 | 0.6 GB | — |
| p90 | 10,000 | 960 万 | 11 GB | — |
| p99 | 1,000 | 1.6 亿 | 92 GB | — |
| p99.9 | 100 | 12 亿 | 780 GB | — |
| max（单租户） | 1 | 68 亿 | **6.4 TB** | **2.1%** |

**累计视角（这张表决定架构，比上面更值钱）**：

| 群体 | 家数 | 家数占比 | 用量占比 | 数据量占比 | 该给哪档隔离 |
| --- | --- | --- | --- | --- | --- |
| Top 20 | 20 | 0.02% | **41%** | 27% | 独立库 / 专属实例 |
| Top 200 | 200 | 0.2% | 67% | 51% | 独立 Schema 或独立库 |
| Top 2,000 | 2,000 | 2% | 88% | 79% | Schema 级分组池 |
| 长尾 98,000 | 98,000 | 98% | 12% | 21% | **行级共享** |

> **结论先行：少数大客户占 80% 以上用量（Top 2% 占 88%），因此"选一种隔离方式"这个命题本身是错的。** 若全选行级，Top 20 里任何一个都能复现事故一；若全选库级，98,000 个长尾租户每户每年要多付 10 倍的钱去买他们用不到的隔离（见下）。

### 单位成本推导：隔离每升一档，成本升一个量级

以 8C32G + 4 TB 实例 **¥9,600/月** 为基准，成本口径含机器 + 运维人力摊销：

```
单租户年成本 = [实例月费 / 每实例可容纳租户数 × 12] + 年运维人力/租户数
运维人力单价 ¥45 万/人年（含社保与值班摊销）
```

| 档位 | 每实例容纳 | 机器 ¥/租户·年 | 人力配置 | 人力 ¥/租户·年 | 合计 | 相对倍数 |
| --- | --- | --- | --- | --- | --- | --- |
| 行级共享 | 5,000 | 23 | 1 DBA / 20 万租户 | 2.3 | **≈ 26** | **1.0×** |
| Schema 级 | 400 | 288 | 1 DBA / 1.2 万 schema | 37 | **≈ 325** | **12.5×** |
| 库级 | 12 | 9,600 | 1 DBA / 300 库 | 1,500 | **≈ 11,100** | **427×** |
| 实例级 | 1（按峰值预留，利用率 15% vs 共享 60%） | 9,600×4 = 38,400 | 1 DBA / 60 实例 + 专属值班 | 12,000 | **≈ 50,400** | **1,940×** |

**注意"每实例容纳数"不是拍脑袋，是三个硬约束的较小值**：

| 档位 | 硬约束 |
| --- | --- |
| 行级 | 单表行数（> 5 亿行单表管理失效）与索引膨胀；按 5,000 租户 × 均值 8 GB 反推 |
| Schema 级 | MySQL `table_open_cache` + 文件句柄：每 schema 约 600 个 `.ibd`，400 schema = 24 万文件句柄，已接近实例上限；PostgreSQL 可到 2,000，故 PG 更适合 Schema 级 |
| 库级 | 连接池：每库独立最小连接 8–16，12 库即 96–192 连接；备份窗口：12 个库串行备份需 12 小时 > 夜间窗口 |
| 实例级 | 备份与升级窗口必须错开；每个实例一次 DDL 都是独立的变更单（→ [07 变更治理](07-change-governance.md)） |

**所以"给所有租户上独立库"的年成本是 1,940× 的局部数字，按 Top 2% 上升档后整体只增加 1.6 倍**——这就是混合策略的全部经济学。

### 路由表容量

```
路由行 = tenant_id(8) + db_key(16) + level(1) + shard(2) + version(8) + flags(4) ≈ 40 B
10 万租户 × 40 B = 4 MB  →  可全量常驻每个进程（不是"每次查 Redis"）
峰值 26 万 QPS × 全量命中 → 路由查询对 DB 的压力 ≈ 0（见 §24.13）
```

## 24.4 三种隔离方案对比（全篇核心表）

**这张表必须在架构评审桌上摊开。** 任何"我们要不要做多租户改造"的讨论，先填完它再说话。

```
① 行级（共享库表）              ② Schema 级（同实例多 schema）
┌───── 实例 A ─────────────┐    ┌───── 实例 A ─────────────────────────┐
│ db: saas                  │    │ tbl_a.orders  tbl_b.orders  tbl_c...│
│ ┌───────────────────────┐ │    │  (schema a)    (schema b)           │
│ │ orders(tenant_id, ...) │ │    │ 各 400 个 schema / 实例              │
│ │ 5,000 租户混在一张表   │ │    │ 连接池共享、IO/CPU/锁共享            │
│ └───────────────────────┘ │    └──────────────────────────────────────┘
│ 连接池 / IO / 锁 全部共享 │
└──────────────────────────┘    ③ 库级 / ④ 实例级
                                 ┌─ 实例 A ─┐ ┌─ 实例 B ─┐ ┌─ 实例 C ─┐
  故障域 = 5,000 租户            │ db_t1    │ │ db_t2    │ │ db_t3    │
  事故一现场                     │ 独立账号 │ │ 独立池   │ │ 独立备份 │
                                 └──────────┘ └──────────┘ └──────────┘
                                 故障域 = 1（库级实例内仍共享 IO，实例级彻底独立）
```

| 维度 | ① 行级（共享库表） | ② Schema 级（同实例） | ③ 库级（独立 database） | ④ 实例级（独立实例/专属单元） |
| --- | --- | --- | --- | --- |
| **单位成本**（¥/租户·年） | **≈26** | ≈325（12.5×） | ≈11,100（427×） | ≈50,400（1,940×） |
| 有效资源利用率 | 60% | 35%（元数据开销 + 长尾冷 schema） | 25% | 15% |
| **隔离度**（故障域大小） | 5,000 租户同生共死 | 400 租户同生共死 | 12 库共享 IO/CPU，逻辑独立 | **1 租户**，物理独立 |
| **噪声邻居风险** | **极高**：一条全表 SQL = 全员宕机（事故一） | 高：连接数、IOPS、锁仍共享；单 schema 大事务可拖慢全实例 | 中：IO/CPU 共享，但慢 SQL 只影响自己库（无跨库锁） | **≈0** |
| **跨租户查询/聚合** | **容易**（一条 SQL 全平台统计，运维报表天然好写） | 难（需跨 schema `UNION`，且 schema 名动态） | 很难（跨库 join 不可用，需数仓） | 不可能（必须走数据仓库） |
| **备份恢复粒度** | **只有全库**：单租户恢复 = 克隆 + 过滤 + 回灌（事故三，6 小时） | 单 schema `mysqldump` / `pg_dump -n`，粒度可接受 | 单库备份/恢复，10–40 分钟 | 实例快照，分钟级，可单租户 PITR |
| **迁移难度**（升档） | 从行级搬出：按 `tenant_id` 全表扫描导出，量 = 该租户数据量 | 从 schema 搬到库：`pg_dump -n` 直搬，**最容易** | 搬机房/跨云：实例级复制 | 搬机房：按租户迁移（→ [10 多活与单元化](10-multi-active-and-cell.md)） |
| **DDL 变更成本** | **1 次变更，全部租户同时生效**（最便宜，也最危险） | 需遍历 N 个 schema（400 次/实例），或用 `gh-ost` 循环 | N 次（12/实例），必须错峰 + 变更单 | 每租户单独变更 + 兼容性通知（合规租户常要求"我先"） |
| 连接数占用 | 5,000 租户共享 400 连接（单租户并发上限必须硬限） | 每 schema 建议独立账号，连接仍共享实例上限 | 每库独立池 8–16，实例上限易撞 | 独立池，互不影响 |
| **安全边界**（一个 bug 的爆炸半径） | **全平台**：漏一处 `tenant_id` = 全泄露（事故二） | 单实例 400 租户 | 单租户（同实例其他库仍可被 DBA 视角看到） | 单租户 + 可独立 KMS 密钥 / BYOK |
| 可观测与容量规划 | 难：按租户聚合需要 `GROUP BY tenant_id` 打全表 | 中：按 schema 采指标 | 易：按库/实例采指标 | 易，且能单租户水位告警 |
| 适用租户规模 | 长尾 98%（月调用 < 1,000 万，存储 < 20 GB） | 中腰部 2%（月调用 1,000 万–10 亿） | Top 200（> 10 亿/月或存储 > 100 GB） | Top 20 + 受监管/BYOK/私有化 |
| 单租户容量上限 | 受单表 5 亿行、单实例 IOPS 限制，**实际 ≈ 300 GB** | 受单实例总容量限制 ≈ 2 TB | 受单实例 ≈ 8 TB | 无实际上限 |

**这张表最该被追问的三点**：

1. **"隔离度"这一行不是感受，是故障域大小。** 行级下面写的是 5,000，就能立刻算出"单租户故障造成 5,000 租户不可用"的概率；把它当 SLA 的输入，比任何"高可用"套话都有用。
2. **"备份恢复粒度"是最容易被忽略、也最容易引发合同纠纷的一行。** 客户合同里写"RPO ≤ 5 分钟"，在行级下只对"整库"成立，对"我这一个租户的数据"并不成立。**签合同前必须把档位能力写进附件。**
3. **"跨租户查询容易"是行级唯一的真优势**，不要放弃它：平台的运营大盘、计费对账、风控模型全都需要全平台视角。所以行级不能全砍——它是**默认档**，也是**分析视角的天然落点**。

## 24.5 现实结论：必须混合，且必须有升级通道

### 三条决策规则

```
规则 1（默认）：新租户一律进行级共享池。理由：98% 的租户一辈子碰不到行级的上限。
规则 2（升级）：任一信号命中即升档，不等年度评审（信号见 §24.9）。
规则 3（不可逆）：升档只能向上，不允许"降档回共享池"——数据合并回共享表的
              风险（主键冲突、索引膨胀）远高于省下的钱；降档只允许"新开租户"。
```

### 混合拓扑与升级通道

```
                    ┌──────────────── 租户路由表（唯一真相，§24.13）────────────────┐
                    │  tenant_id → { level, db_key, shard, version }                │
                    └───────┬───────────────┬────────────────┬──────────────────────┘
                            │               │                │
        ┌───────────────────▼──┐  ┌─────────▼─────────┐  ┌───▼──────────────────┐
        │ 行级共享池（默认）    │  │ Schema 分组池      │  │ 独立库 / 专属实例      │
        │ 96,000 租户 / 20 实例 │  │ 2,000 租户 / 分 4 组│  │ 200 租户 / 220 实例    │
        │ 一个池 5,000 租户     │  │ 每组 500 schema    │  │ 一户一库（Top 20 独占）│
        └──────────┬───────────┘  └─────────┬──────────┘  └───┬──────────────────┘
                   │                        │                 │
            月度用量 < 1,000 万       1,000 万 – 10 亿      > 10 亿 或 合规要求
                   │                        │                 │
                   └───── 升级①  ───────────┴──── 升级② ───────┘
                     （按 tenant_id 全表导出 → 灌入新 schema/库 → 影子读比对 → 原子切路由）
```

**升级①与升级②的差别只在搬运工具**（`WHERE tenant_id=?` 导出 vs `pg_dump -n`），流程完全一致（§24.9）。**所以底座必须从一开始就把"迁移"当成一等公民**：要有 `tenant_id` 唯一索引、要有单租户数据量统计、要有可编排的迁移流水线——这三样在行级时代就要埋，等大租户找上门再补，就是事故三（6 小时）。

| 混合策略 | 全局成本 | Top 20 体验 | 事故一风险 | 结论 |
| --- | --- | --- | --- | --- |
| 全行级 | 1.0× | 随时被自己/别人拖死 | 高 | ❌ |
| 全 Schema 级 | 3.2× | 中（同实例仍互相影响） | 中 | ❌ 长尾白付钱 |
| 全库级 | 8.7× | 好 | 低 | ❌ 成本不可接受 |
| **混合（98% 行级 + 2% Schema + 0.2% 库级 + 20 户实例级）** | **1.6×** | **好** | **低（故障域 ≤ 5,000，且大租户已隔离）** | ✅ |

## 24.6 租户识别与上下文传递：上下文丢了等于越权

### 三种识别来源，顺序写死

| 来源 | 形态 | 优点 | 风险 | 用于 |
| --- | --- | --- | --- | --- |
| **子域名** | `acme.app.com` | 天然可见、可定制品牌、Cookie 同源 | 通配符证书 + DNS 泛解析必须有；**子域枚举**会暴露客户名单 | 浏览器/前端入口（主） |
| **Token** | JWT 的 `iss`/`tid` 或 API Key → 租户 | 不可伪造、可轮换、可绑定 scope | token 泄露 = 租户被接管；**必须二次校验"路径里的租户 == token 的租户"** | 服务端/API 入口（主） |
| **路径** | `/t/acme/v1/...` | 最直白，易做多环境 | 转发/代理容易丢前缀；日志里带 PII | 内部服务、沙箱、白标 |

**铁律：三者同时出现时必须一致，不一致直接 403 + 审计。** 只在 token 里信租户、或只在子域里信租户，都会给出可绕过路径——`acme.app.com` + 别人租户的 token 是最常见的越权入口（同 [09 开放平台 · §09.14](09-open-platform.md) 的水平越权）。

### 上下文传递链：四个必须句柄化的位置

```
请求 ──> 网关(识别 tenant) ──> 路由表(→ db_key) ──> 应用(ThreadLocal) ──┬──> DB（裁剪 + 强制 tenant_id）
                                          ├──> Redis（key 前缀 t:{id}:）
                                          ├──> MQ（消息 header 带 tenant_id，消费端重绑）
                                          └──> 线程池/异步/定时任务（必须显式快照透传）
```

| 位置 | 丢失后果 | 机制 |
| --- | --- | --- |
| `Async` / `@Async` / 线程池 | 子线程 `get()` 抛异常（好）或取到上次的租户（**灾难**） | 包装 `TaskDecorator` 透传，或 `TenantContext.wrap()` |
| MQ 生产/消费 | 消费端在"无租户"状态下写全表 | 消息 header 携带 `tenant_id`，消费端**强制重绑**，缺失即进死信 |
| 定时任务 | 跑了 96,000 个租户的数据却没带租户 → 全表更新 | 任务模板化：`for (tenant : pageOfTenants) { bind; run; }`，禁止裸跑 |
| Hibernate/MyBatis 二级缓存 | 缓存 key 不含租户 → A 读到 B 的数据 | 缓存 key 一律加 `tenant_id`，且缓存拦截器与裁剪拦截器同源 |
| 日志/链路追踪 | 出事不知道"是谁" | MDC 与 trace tag 注入 `tenant_id`，缺失即告警（这也是 §24.1 事故一定位慢 12 分钟的原因） |

### 骨架代码一：Java 租户上下文 + 强制裁剪拦截器

```java
// ① 上下文：ThreadLocal 是唯一写入口；漏 clear = 线程复用导致跨租户串号
public final class TenantContext {
    private static final ThreadLocal<Scope> H = new ThreadLocal<>();
    public static Scope get() { Scope s = H.get();
        if (s == null) throw new IllegalStateException("TENANT_CONTEXT_MISSING"); // fail-closed
        return s; }
    static void bind(Scope s) { H.set(s); }
    static void clear() { H.remove(); }
    public static <T> Callable<T> wrap(Callable<T> task) {          // 异步/线程池透传
        Scope snap = get();
        return () -> { H.set(snap); try { return task.call(); } finally { H.remove(); } };
    }
}
// ② 入口：子域 > 路径 > Token.iss，顺序写死；解析不出就 401，绝不猜默认租户
@Component
public class TenantFilter extends OncePerRequestFilter {
    protected void doFilterInternal(HttpServletRequest q, HttpServletResponse r, FilterChain c)
            throws ServletException, IOException {
        Long tid = resolver.resolve(q);
        if (tid == null) { r.sendError(401, "AUTH.TENANT_UNRESOLVED"); return; }
        TenantContext.bind(new Scope(tid, tierOf(tid)));
        try { c.doFilter(q, r); } finally { TenantContext.clear(); }
    }
}
// ③ 裁剪：SQL 里没有 tenant_id 就抛异常（拒绝执行），而不是"帮它补条件"
@Intercepts(@Signature(type = Executor.class, method = "query",
        args = {MappedStatement.class, Object.class, RowBounds.class, ResultHandler.class}))
public class TenantLineInterceptor implements Interceptor {
    public Object intercept(Invocation inv) throws Throwable {
        MappedStatement ms = (MappedStatement) inv.getArgs()[0];
        if (TenantTables.isGlobal(ms.getId())) return inv.proceed();   // 白名单，CI 校验
        if (!ms.getBoundSql(inv.getArgs()[1]).getSql().toLowerCase().contains("tenant_id"))
            throw new TenantIsolationBreach(ms.getId());               // ★ 一票否决
        return inv.proceed();
    }
}
```

**为什么是"校验"而不是"自动补 `AND tenant_id = ?`"**：自动补只能处理最简单的一层 `SELECT`；一旦遇到 `UNION`、子查询、`JOIN` 派生表、`UPDATE ... JOIN`，改写就不可靠（事故二正是 `UNION ALL` 的第二段被漏掉）。**"帮它补"给你的是错觉，"拒绝执行"给你的是构建失败。** 把痛感放到开发和 CI 阶段，而不是放到客户的数据里。

## 24.7 越权防护：三种强制裁剪做法的取舍

| 做法 | 作用点 | 覆盖率 | 性能开销 | 可运维性 | 适用 |
| --- | --- | --- | --- | --- | --- |
| **① 应用层拦截器**（MyBatis/JPA/Hibernate Filter） | SQL 执行前校验/改写 | 仅覆盖被框架代理的调用；**原生 SQL、脚本、定时任务、`JdbcTemplate` 会漏** | ≈0（AST 解析可缓存） | 好：与代码同时评审 | ✅ **主力**，必须配合② |
| **② 数据库行级安全 RLS**（PostgreSQL `ROW LEVEL SECURITY` + `SET LOCAL app.tenant_id`） | 存储引擎 | **100%**：任何入口的 SQL 都被过滤，漏写条件返回 0 行 | 5–12%（策略表达式 + 计划缓存失效） | 中：会话变量必须在**每个事务**内设置，连接池复用会导致串号；`SET LOCAL` 缺失 = 0 行（fail-closed，正确方向） | ✅ **兜底**，行级档位建议默认开 |
| **③ 每租户视图**（`v_orders` 内建 `WHERE tenant_id = CURRENT_xxx`） | 数据库对象 | 100%（若强制只授权视图） | 低 | **差**：视图数量 = 表数 × 每租户 → 1 万租户 × 40 表 = 40 万对象，元数据爆炸；DDL 要乘 N | ❌ 行级不可用；✅ **Schema 级天然等价物**（schema 本身即视图边界） |
| ④ 物理隔离（库/实例） | 连接层 | 100% | 0 | 中（迁移与变更成本，见 §24.4） | ✅ 大租户与受监管租户 |

**MySQL 的现实**：无原生 RLS。可行替代是「每租户只授权视图」或「Schema 级隔离」，因此**用 MySQL 做行级多租户时，应用层拦截器从"主力"变成"唯一防线"**——这就是为什么门禁必须做到 §24.7 下半段的强度。选型时把这一条算进成本：PostgreSQL 的 RLS 值这个迁移价。

### "漏一处就全部泄露"的六道防护

| # | 防线 | 具体机制 | 拦住了什么 |
| --- | --- | --- | --- |
| 1 | **单写入口** | `TenantContext.bind()` 包私有、只被 Filter 调用；ArchUnit 规则：除 `TenantFilter` 外任何类不得调用 `bind/clear/wrap` | 业务代码"手动指定租户"绕过 |
| 2 | **静态 SQL 扫描** | CI 用 JSqlParser 遍历全部 mapper XML 与 `@Select`：凡 `FROM/JOIN` 的表不在全局白名单、且 AST 里无 `tenant_id` 谓词 → 构建失败 | 事故二（`UNION` 分支漏条件） |
| 3 | **越权用例矩阵（测试门禁）** | 对 1,700 个 mapper 方法自动生成 2 个用例（"A 上下文查 A 数据 = 命中"、"A 上下文查 B 数据 = 0 行"），共 3,400 例，合并前必须全绿 | 逻辑层"看起来对"的越权 |
| 4 | **RLS / 视图兜底** | 行级档位生产环境必须开启数据库侧策略，**开发与测试环境同样开启**（禁止"为调试关掉"） | 任何应用层漏网路径 |
| 5 | **跨租户白名单显式化** | 平台级查询必须标 `@CrossTenant(reason="billing_rollup")`，且 ArchUnit 强制：该注解只能出现在 `platform.admin` 包，且必须同时有 `@Audited` + `@RequireMfa` | "顺手写个跨租户报表"变成常态 |
| 6 | **生产交叉读探针** | 每小时用两个哨兵租户跑一次 `SELECT`，断言互不可见；非 0 行即 P0（比等客户发现早 6 天） | 配置漂移、灰度版本的漏网 |

```java
// ArchUnit 三条规则（写成测试类，进 CI）
// ① 除 TenantFilter 外禁用 bind/clear
noClasses().that().areNotAssignableTo(TenantFilter.class)
    .should().callMethod(TenantContext.class, "bind", Scope.class).check(classes);
// ② @CrossTenant 只允许在 platform.admin 包，且必须带 @Audited
methods().that().areAnnotatedWith(CrossTenant.class)
    .should().beDeclaredInClassesThat().resideInAPackage("..platform.admin..")
    .andShould().beAnnotatedWith(Audited.class).check(classes);
// ③ 禁止直接持有 JdbcTemplate（绕过拦截器的唯一路径）
noClasses().should().dependOnClassesThat().assignableTo(JdbcTemplate.class).check(classes);
```

> 一句话纪律：**越权防护不能靠"我们测试过了"，只能靠"没通过检查就构建不出来"。** 与 [09 开放平台 · §09.8](09-open-platform.md) 兼容性门禁是同一种纪律：把人的自觉换成机器的拒绝。

## 24.8 噪声邻居治理：关键资源必须池化隔离

**行级档位的隔离度靠两件事买：数据靠裁剪，资源靠池化。** 事故一里 4,247 个租户被拖死，根因不是"混在一张表里"，是"混在一个池子里"。

| 资源 | 必须隔离？ | 做法 | 不隔离的现场 |
| --- | --- | --- | --- |
| **数据库连接池** | ✅ 必须 | 按 tier 分 3 池：自助 45% / 标准 30% / 企业+铂金 25%；**单租户并发上限 = 池容量 × 2%** | 事故一：单租户 32 并发 × 批量 = 打满 400 连接 |
| **线程池 / 执行器** | ✅ 必须 | 按接口族隔离：`read` / `write` / `batch` / `export` 四个池，互不借用；队列有上限且满即拒 | 一个批量任务吃满 Tomcat 200 线程 |
| **导出与报表** | ✅ 必须 | 独立 worker + **异步 job（202）** + 行数预算（单 job ≤ 500 万行）+ 并发 1 | 报表 `COUNT(*)` 打满从库 |
| **定时任务** | ✅ 必须 | 分布式锁 key = `{tenant}:{task}`、错峰窗口、单租户并发 1、限速行/秒 | 凌晨 2 点 96,000 个租户同时跑同一批任务 |
| **Redis** | ⚠️ 按大 Key | 统一 key 前缀 `t:{id}:`，单租户内存上限；Top 0.1% 独立实例 | 一个大租户的 4 GB 集合触发大 key 阻塞 |
| **消息队列** | ⚠️ 按大租户 | topic 共用但**大租户专属 partition**；消费端按租户限速 | 一个租户的 200 万条积压阻塞所有人 |
| **CPU / 磁盘 IO（cgroup）** | ✅ 实例级 | `cpu.weight` + `io.max`（IOPS 上限）+ `memory.max`；**按 tier 设权重而非独占** | 单实例上别的容器把磁盘 IOPS 打满 |
| **搜索引擎** | ⚠️ 分组 | 索引按池分（大租户独立索引），查询走 `tenant_id` filter + 单查询超时 1 s | 一次深分页 query 拖慢整组检索 |
| **对象存储** | ✅ 便宜 | bucket + 前缀配额、独立 KMS key（合规）、单租户流量上限 | 一个租户的同步备份打满出口带宽 |
| **租户路由表** | ❌ 不隔离 | 共享 + 多级缓存 + fail-closed（§24.13） | —（隔离它反而制造新单点） |

三档限流的落点（与 [09 开放平台 · §09.10](09-open-platform.md) 的双桶同源，这里只给多租户底座独有的部分）：

```
租户级：令牌桶 (S, 60S)，S 由 tier 决定      → 挡"这个客户整体太猛"
接口族级：read/write/batch/export 各自独立桶   → 挡"这个客户的导出吃满连接"
单资源级：并发信号量（连接 ≤ 池×2%、导出 ≤ 1、报表 ≤ 1）→ 挡"同一租户自己挤死自己"
```

**"关键资源必须池化隔离"的判定标准只有一条：这个资源被一个租户占满时，其他租户是否会不可用？会 → 必须隔离。** 按这条标准过一遍上表，能砍掉一半"看起来需要隔离"的资源（比如路由表、配置中心），把运维成本留给真需要的。

## 24.9 大租户升级路径：从行级到独立库

### 升级触发信号（命中任一即启动，不等年度评审）

| 信号 | 阈值 | 为什么是这个数 | 去向 |
| --- | --- | --- | --- |
| 单租户存储量 | > 300 GB | 行级单表管理上限（5 亿行 / 索引膨胀） | Schema 级 → 库级 |
| 单租户占单实例资源 | CPU/IOPS > **8%** 连续 7 天 | 5,000 租户池里，8% 意味着"他一个人顶 400 个平均租户"，再涨就是事故一 | 库级 |
| 单租户占平台总用量 | > 1% | 与 [09 开放平台 · §09.4](09-open-platform.md) 的配额分摊同口径：超过 1% 后共享池的公平性无法用技术保证 | 库级/实例级 |
| 相对基线异常 | 用量 > 30 天基线 × 10 | 事故一的正解是"先限流，再升级"，两条一起做 | 先限流 → 升级 |
| 合规要求 | 等保三级、金融监管、BYOK、数据驻留 | 合同义务，与用量无关 | 实例级 |
| 噪声邻居投诉 | 同库其他租户 P99 劣化归因到该租户 ≥ 2 次 | 商业信号，最贵 | 库级 |
| 大事务/锁冲突 | 单租户的大事务回滚 > 3 分钟或锁等待 > 30 s | 行级下这会锁住同表其他租户的行 | 库级 |

### 迁移流程（九步，全程不停机）

```
① 触发 & 立项      信号命中 → 生成迁移工单（记录触发指标快照，作为后续复盘依据）
② 目标选型         Schema / 库级 / 实例级；确定目标实例与 shard，写入路由表"目标"字段（不生效）
③ 建影子库         空 schema + 全量 DDL（由 schema 版本机生成，禁止手工）
④ 双写开           写主库 + 写影子库（同事务内两侧写，失败以主库为准，影子记差异队列）
⑤ 全量搬 + 增量追  按 tenant_id 分批（每批 5 万行）+ binlog/CDC 追增量（→ [20 数据迁移]）
⑥ 影子读比对       1% 流量读影子，逐字段比对，不一致率 > 0 即回退；连续 6 小时 0 差异
⑦ 原子切读         按 tenant_id 一次切换（同一租户的读写必须同一时刻切）
⑧ 切写 + 停双写    确认读稳定 30 分钟 → 写切到新库 → 关闭双写
⑨ 观察 & 摘旧      观察 7 天（P99、错误率、慢查询）→ 旧数据打快照保留 30 天 → 物理清除
```

**七条不可跳过的纪律**（每条都对应一次真实事故，与 [10 多活与单元化 · §10.10](10-multi-active-and-cell.md) 的回切清单同源）：

| 纪律 | 跳过会怎样 |
| --- | --- |
| **读写必须同一时刻切**（按租户原子） | 写已到新库、读还在旧库 → 客户"下单后查不到订单" |
| **双写期间以主库为准 + 差异队列有监控** | 双写失败静默丢弃 → 迁移后少数据，且无从对账 |
| **全量搬运必须走 `tenant_id` 索引**，禁止全表扫描 | 一次 6.4 TB 全表扫描 = 事故三的翻版 |
| **迁移期间该租户不开新的批量导入** | 边迁边灌，增量永远追不上 |
| **切换前必须停该租户的定时任务** | 定时任务还在旧库写 → 切完被覆盖 |
| **旧数据保留 30 天不删** | 发现问题无法回退，只能从备份捞 |
| **迁移是一个可重入的 job，不是一次脚本** | 中途失败重跑会重复写；带幂等键才可重试 |

### 升级对租户的可见影响

| 影响面 | 实际变化 | 租户感知 | 沟通时机 |
| --- | --- | --- | --- |
| 停机 | **0**（不停机迁移） | 无 | — |
| 接口/域名 | 不变（路由表在内部切换） | 无 | 不通知 |
| 延迟 | 跨实例多一次网络跳，P99 **+0.8–1.5 ms** | 基本无感 | 提前 7 天告知 |
| 备份窗口/恢复能力 | **变好**：从"整库 PITR"升为"单租户 15 分钟恢复" | 正向 | 升级后作为卖点告知 |
| 配额口径 | 重算（独立实例的配额更高） | 正向 | 同步报价 |
| 数据量上限 | 从 300 GB 升到 8 TB+ | 正向 | 同步报价 |
| 价格 | 档位变化，通常上涨 | 需商务谈判 | **提前 90 天**（与 [09 开放平台 · §09.9](09-open-platform.md) 的弃用提前期同量级） |
| 变更窗口 | 从"跟随平台统一发布"变为"可约定窗口" | 正向（合规租户的刚需） | 升级时确认 |

> **"升级是产品能力，不是技术债清理。"** 对客户讲这件事的顺序必须是"你获得了什么"（恢复粒度、容量上限、变更窗口、稳定性），而不是"我们数据库撑不住了"。

## 24.10 租户级运维：四个能力决定能不能签大客户

大客户尽调清单里一定会问这四件事。**行级档位做不到的，必须在合同里写清楚，并给出升级路径。**

| 能力 | 行级 | Schema 级 | 库级/实例级 | 通用要求 |
| --- | --- | --- | --- | --- |
| **单租户备份** | 逻辑导出 `WHERE tenant_id=?`（大租户 4 小时）或 binlog 过滤重建 | `pg_dump -n schema` / `mysqldump schema` | 实例快照 / 单库 dump（10–40 min） | 备份必须**加密 + 异地 + 可验证恢复**（每月一次演练恢复） |
| **单租户恢复到时间点** | ⚠️ 需"克隆整库 → 过滤 → 回灌 + 冲突裁决"，2–6 小时（事故三） | 30–90 分钟 | 10–20 分钟 | 合同里的 RPO/RTO 必须**按档位分别写** |
| **单租户数据导出** | 异步 job（202）+ 行数上限 + 加密 + 24h 时效链接 + 审计 | 同 | 同 | 导出是**最高频的越权入口**：链接必须一次性、必须记录下载者 |
| **单租户删除（DSAR）** | 难：跨 42 张表级联 + 派生数据 + 备份 | 中：`DROP SCHEMA` + 派生清理 | 易：`DROP DATABASE` | 必须产出**删除证明**（每表删除行数 + 校验和 + 签名） |

### 删除的级联清单（漏一处就是合规事件）

| 层 | 内容 | 处理 |
| --- | --- | --- |
| 业务表 | 42 张主表 + 外键级联 | 软删 30 天（可撤销）→ 硬删 + `VACUUM` |
| 派生视图 | ES 索引文档、Redis key（`t:{id}:*`）、对象存储前缀、宽表 | 按前缀/字段删除，删除后跑"残留扫描" |
| 数仓 | 分区表里该租户的分区 | 删除 + 重算受影响聚合（注意：重算会改动历史报表，需留说明） |
| 审计日志 | 登录/操作/越权审计 | **不随租户删除**（法定期 6 年），但要脱敏 PII |
| 备份 | 全库备份、binlog | 备份不可变（WORM）→ **无法单条删除**：删除请求打标记，按轮转周期（7/35 天）自然消亡。**必须在隐私条款里写明这一点**，否则审计时无法自证 |
| 计量与账单 | 计费记录 | 按财务法规保留 10 年，脱敏后保留 |

**单租户迁移机房**：按租户为单位迁移（不是按实例），走 §24.9 同一套流程，只是目标跨地域；跨地域时要额外判"数据出境"（→ [10 多活与单元化 · §10.14](10-multi-active-and-cell.md)）。

## 24.11 共享资源的公平调度：为什么"先到先得"不公平

**FIFO 的数学事实**：一个租户贡献 8 万条批量任务、其余 5,000 个租户各贡献 1 条，FIFO 下前者占队头 → 后者平均排队 ≈ 8 万 / 处理速率。若处理速率 3,000/s，其余租户的 P99 排队 ≈ **27 s**，而如果没有那个批量任务只需 3 ms。**这不是"某租户太坏"，是调度器把"谁先到"当成了"谁更重要"。**

| 算法 | 机制 | 优点 | 代价 / 崩法 | 适用 |
| --- | --- | --- | --- | --- |
| **令牌桶/漏桶（租户维度）** | 每租户速率 S + 突发 60S | 实现简单、可解释、与报价直接对应 | 只封顶不分配：池子里有空闲时大租户也用不上（浪费 20–30% 容量） | ✅ 入口限流（必须） |
| **加权轮询 / DRR（Deficit Round Robin）** | 按付费权重分配处理配额，队空即让出 | 空闲容量可被借用，整体利用率高；天然公平 | 需要 per-tenant 队列（96,000 个队列的内存与调度开销）；权重配置错了会变成"隐形降级" | ✅ 异步 job/批量队列 |
| **分级队列 + 优先级** | 交互 > 报表 > 批量；批量可被抢占 | 保护交互类 SLO 最有效 | 批量可能饿死（需老化机制防饿） | ✅ 混跑型任务池 |
| **预留 + 上限 + 借用**（K8s `requests/limits` 思路） | 保底 R、封顶 L、空闲可借、忙时归还 | 同时解决"公平"与"利用率" | 需要回收机制（借出去的容量要主动抢回），实现复杂 | ✅ 计算型资源（worker/渲染） |
| 全局 FIFO | — | 无 | 事故一 / `llm/44` 的事故现场 | ❌ 任何共享池 |

**落地组合（本篇推荐）**：**入口令牌桶（防猛）+ 队列 DRR（防霸）+ 分级优先级（保交互）+ 单租户并发信号量（防自己挤自己）**。四层缺一层都能复现某类事故：只有令牌桶 → 长任务仍能长时间占住 worker；只有 DRR → 单租户可以瞬间打满入口。

## 24.12 计费与配额的落点：计量口径必须与限流口径同源

**计量在网关，配额在网关，账单在计量表——三处必须是同一个 `tenant_id` 语义。** 用两套租户标识（一处用 api_key、一处用 org_id）是账单对不上的第一原因。

| 计费项 | 计量点 | 口径（写进合同） | 常见坑 |
| --- | --- | --- | --- |
| API 调用 | 网关成功响应 | 计 `2xx`；`429`/`5xx` **不计**；重试按幂等键去重后计一次 | 计了失败请求 → 客户投诉"你们自己挂了还收钱" |
| 存储 | 存储采样（日峰值） | `GB·天`，按每日 00:00 采样，取当月峰值作为计费基数 | 按平均值计 → 大租户账单骤降，收入受损 |
| 导出流量 | 导出 job 完成 | `GB`，压缩后体积 | 按未压缩算 → 争议 |
| 席位 | 用户表快照（日） | 活跃席位（近 30 天登录过） | 按注册席位 → 客户不删号 |
| 专属容量 | 实例/单元分配 | 按预留下单，不按用量（预留就得付） | 按用量 → 预留失去意义，无法给 SLA |

**对账三层**（与 `eng/14` 的分层核对同构，这里只给多租户特有的部分）：

```
L1 网关计量 vs 计量表        差异应 = 0（同一事件流，落库失败要能重放）
L2 计量表 vs 账单明细        差异 ≤ 0.05%（聚合与舍入，按日结 + 月结双重核对）
L3 账单 vs 客户侧统计        差异 > 1% 必须能逐条 drill-down 到 request_id
```

配额契约、429 语义、双桶参数、超额的三条商业出路（买配额 / 换通道 / 专属容量）**不在这里重写**，全部引用 → [09 开放平台 · §09.10](09-open-platform.md)。本篇只补一条：**多租户底座的配额必须按"隔离档位"分池计算**——独立库租户的配额约束是"他的实例容量"，共享池租户的约束是"池容量 × 他的人群权重"，两者不能用同一套公式。

## 24.13 租户元数据与路由表：它挂了全站挂

混合隔离的直接代价是**路由**：任何请求都必须先知道"这个租户在哪个库/实例/分片"。这张表是全平台唯一的强依赖。

```
tenant_route(tenant_id PK, level, db_key, shard, region, version, status, updated_at)
  level  : ROW | SCHEMA | DB | INSTANCE
  db_key : 逻辑数据源名（连接串由配置中心解析，路由表不存密码）
  version: 单调递增，用于"缓存失效"与"变更溯源"（同 [10 多活 · §10.7]）
```

**可用性的三条纪律**（与 [10 多活与单元化 · §10.7](10-multi-active-and-cell.md) 逐条同源，改一个字都不行）：

| 纪律 | 多活里的版本 | 多租户里的版本 |
| --- | --- | --- |
| 全量常驻 + 多级缓存 | L1 进程内 LRU 92% / L2 Redis / L3 DB | **全量 4 MB 直接常驻**（10 万租户很小，别只做缓存），L2/L3 只做冷启动与兜底 |
| 查不到时**绝不猜** | 降级到默认单元只读 | **返回 503**，绝不允许"默认库"——写错库 = 把 A 的数据写进 B 的库 |
| 变更必须版本号单调 + 双写过渡 | 迁移完成前只写源单元 | 升级迁移完成前只写源库（§24.9 第 ⑦ 步） |

### 骨架代码二：Go 租户路由

```go
// 租户路由：域名/Token → tenant → 数据源。三级缓存 + fail-closed（查不到不许"选默认库"）
type Router struct {
	l1 *lru.Cache    // 全量 10 万条 × 40 B ≈ 4 MB，常驻进程，命中 99.7%
	l2 *redis.Client // 冷启动与跨实例同步，命中 0.29%，5 ms 超时
	l3 *sql.DB       // 元数据只读副本，命中 0.01%
}

func (r *Router) Resolve(ctx context.Context, host, token string) (Route, error) {
	key, err := r.identify(ctx, host, token) // 精确域名 > 通配子域 > Token.iss，顺序写死
	if err != nil {
		return Route{}, err // 401：绝不退回"默认租户"
	}
	if v, ok := r.l1.Get(key); ok {
		return v.(Route), nil
	}
	rt, err := r.fromRedis(ctx, key)
	if err == nil {
		r.l1.Add(key, rt)
		return rt, nil
	}
	if !errors.Is(err, redis.Nil) { // Redis 挂了 ≠ 租户不存在，必须区分
		r.metrics.Inc("route_l2_error")
	}
	rt, err = r.fromMeta(ctx, key) // 5 ms 超时，绝不重试
	switch {
	case err == nil:
		r.l2.Set(ctx, key, rt, 10*time.Minute)
		r.l1.Add(key, rt)
		return rt, nil
	case errors.Is(err, sql.ErrNoRows):
		return Route{}, ErrTenantNotFound // 404
	default:
		return Route{}, ErrRouteDegraded // 503：宁可不可用，不可写错租户库
	}
}
```

**路由表为什么不能放进业务库**：它一旦和某个租户的数据共库，就变成"最大租户拖死全站路由"的单点（事故一的后半段正是这样：计量与路由查询跟着挂了，6,783 个无关租户被降级）。**路由元数据必须独立小库 + 只读副本 + 全量内存**，且它的可用性目标应高于业务库一个 9（99.99% vs 99.9%）。

## 24.14 L0 → L5：从 10 个租户到 10 万个租户

| 阶段 | 租户数 | 形态 | **换挡信号（硬阈值）** | 代价 |
| --- | --- | --- | --- | --- |
| L0 | ≤10 | 单库单表 + `tenant_id`；甚至"一租户一部署" | 一个新租户开通超过 1 天，或第 11 个租户出现 | 无（这阶段手工最省） |
| L1 | 10–200 | 强制租户拦截器 + 单租户限流 + 租户上下文 | 首次出现"某租户 SQL 打满库"；或客户开始问"数据怎么隔离" | 拦截器与门禁的建设成本（2–3 人月） |
| L2 | 200–2,000 | 连接池/线程池按 tier 分池 + 异步批量通道 + cgroup | 单租户 > 单库 8% 资源；或库容量 > 60% | 池化后利用率从 60% 降到 45% |
| L3 | 2,000–20,000 | **混合起步**：行级为主 + Top 1% 独立 Schema；**路由表上线** | 单月 Schema 迁移 > 5 家（人工撑不住）；或出现"一租户恢复 6 小时"的投诉 | 两套形态并存，测试矩阵 ×2；路由表成为新单点 |
| L4 | 20,000–100,000 | 分片集群（32 逻辑分片）+ Schema 分组池 + Top 0.2% 独立库 + 数仓承接跨租户聚合 | 单分片 > 35% 全局流量；跨分片报表超时；单实例 IOPS 稳态 > 70% | 跨租户查询必须走数仓，运营实时性下降 |
| L5 | >100,000 | 单元化（按租户/地域）+ 专属实例 + 计费配额自动化 + 分单元治理 | 路由表成为瓶颈；单单元容量红线；合规域超 3 个 | 成本 3.5–5×（→ [10 多活与单元化 · §10.4](10-multi-active-and-cell.md)），组织成本独立平台团队 |

**当前落在 L4。重点说 L3→L4 的临界点**：L3 之后你会发现"混合"还不够——单个行级池仍是 5,000 租户一个故障域，而 5,000 租户里必然出现一个 p99.9。这时候正确的动作**不是继续升级大租户**（那是给 0.2% 的人花钱），而是**把共享池本身切小**：拆成 32 个逻辑分片、每片 1,500 租户，把故障域从 5,000 降到 1,500，同时按 `tenant_id` 哈希让租户均匀落片。**这是本篇唯一"用架构而不是钱买隔离度"的手段**，代价是跨分片聚合必须走数仓。

### 这个形态特有的崩法

| 崩法 | 长什么样 | 定位方法 | 预防 |
| --- | --- | --- | --- |
| **上下文丢失** | 少量请求写入 `tenant_id = null` 或串到别人家 | 扫全表 `WHERE tenant_id IS NULL`；对比"无租户请求数"与总请求数 | 单写入口 + `wrap()` 透传 + MDC 缺失告警 |
| **拦截器白名单漂移** | 新上线的表/新加的 mapper 没登记 → 要么被拒（好）要么被放行（坏） | CI 扫描 vs 运行时实际 SQL 表名集合的差集 | 白名单 = 代码里的注解，不是配置文件 |
| **连接池被单租户占满** | 全库 429/timeout，但 CPU 不高 | 按 `tenant_id` 聚合活跃连接数（Top 10 占比） | 池化 + 单租户并发上限 |
| **路由表缓存不一致** | 极少数租户读不到刚写的数据 / 写进错库 | 采样比对 L1/L2/DB 三处 `db_key + version` | 版本号单调 + 全量常驻 + fail-closed |
| **大事务回滚** | 导入失败后库"卡住"十几分钟（事故一） | 看 `trx_rows_modified` 与 `SHOW ENGINE INNODB STATUS` 的回滚进度 | 批大小 ≤ 5,000 + 异步 job + 禁止超 10 万行事务 |
| **Schema 对象爆炸** | `table_open_cache` 打满、DDL 秒级变分钟级 | 监控打开表数 / 文件句柄 / 元数据锁等待 | 每实例 schema 上限硬限（400）+ 超限拒绝开通 |
| **单租户备份撞全局备份** | 夜间备份窗口重叠 → 白天 P99 抖动 | 备份任务按租户/库错峰排程 | 备份调度器按分片错峰 + 快照优先于逻辑导出 |
| **计量与限流口径不一致** | 客户说"我没超"，账单说"超了" | 按 `tenant_id × 小时` 比对网关计量表与限流计数器 | 同源：限流器直接吐计量事件 |
| **删除不干净** | DSAR 后仍能搜到旧数据（ES/数仓/备份） | 每月跑"删除残余扫描"：按前缀与关键词全库搜 | 删除清单化 + 删除证明 + 残留扫描 job |

## 24.15 砍掉 90% 预算还能不能跑

预算砍到 1/10：96 台实例砍到 10 台、路由表保留、Schema/库级隔离全部取消、异步 job 通道退化为同步、数仓停用。

| 保留 | 砍掉 | 后果 |
| --- | --- | --- |
| **强制租户裁剪 + 门禁 + RLS 兜底** | Schema 分组池、独立库、专属实例 | 越权风险不变（这是唯一不能砍的）；大租户回到共享池 |
| **租户路由表（单库 + 内存）** | 分片集群、跨分片路由 | 路由仍可靠，但容量天花板降到 ~2 万租户 |
| **租户级限流 + 连接池分 2 池（交互/批量）** | cgroup、线程池四池、DRR 队列 | 事故一的风险回来一半，靠"人工白名单 + 商务约束"兜 |
| 单租户逻辑导出（慢但可用） | 单租户 PITR、异步导出 job | 大租户恢复从 15 分钟退化为 4 小时 |
| — | 数仓、跨租户实时聚合 | 运营报表退化为 T+1 离线跑批（夜间全表扫，必须限速） |

**结论：这个底座的必需品只有三样——强制租户裁剪（含门禁）、租户路由表、租户级限流与池化。** 隔离档位、专属实例、单租户 PITR 全是"客户结构与单价"驱动的商业决策，不是技术必需品。任何一次评审都问一遍"哪三样砍了会立刻泄露或立刻宕机"，答案就是这三样。

## 24.16 十分钟答题卡

被要求设计一个多租户 SaaS 底座时，按这个顺序讲，不要从"每张表加 tenant_id"开始：

```
1  真问题   隔离度 × 成本 × 可运维性 不可能三角；纯一种隔离一定错
2  分布     重尾：Top 2% 占 88% 用量 → 默认行级 + 大租户升档（混合）
3  档位     行级 26 元/租户年 · Schema 325 · 库级 11,100 · 实例级 50,400（1:12:427:1,940）
4  隔离     行级靠"裁剪 + 池化"买隔离：数据靠强制注入，资源靠分池
5  裁剪     默认拒绝：SQL 无 tenant_id 就抛异常；RLS/视图兜底；ArchUnit + 越权矩阵门禁
6  上下文   子域/Path/Token 三者一致；ThreadLocal 唯一写入口；异步/MQ/定时任务显式透传
7  噪声     连接池(3 池) · 线程池(4 池) · 导出 worker · 定时任务锁带租户前缀 · cgroup
8  公平     入口令牌桶 + 队列 DRR + 分级优先级 + 单租户并发信号量（缺一层就复现一类事故）
9  运维     单租户备份/恢复/导出/删除四件套按档位写成矩阵，进合同附件；删除要出证明
10 路由     全量常驻 + fail-closed 503（绝不默认库）+ 版本号单调；它挂 = 全站挂
11 计费     网关计量 = 限流口径同源；2xx 才计费；L1/L2/L3 三层对账；配额引用 → 09
12 换挡     L2: 单租户 8% 资源 → L3: 混合+路由表 → L4: 32 分片（故障域 5000→1500）→ L5: 单元化
```

一句收口：**多租户底座的成熟度不看它支持多少租户，看它能不能证明"任何一个租户都打不死别人，也看不到别人"。**
