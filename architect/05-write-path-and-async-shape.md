## 05.1 事故引子：一次「无害」的异步化，和它的两张账单

某会员订阅系统原本是同步链路：定时任务扫出到期会员 → 逐条调支付网关扣 199 元 → 调权益服务开通 → 发短信。三个月前为了「降耦合、提吞吐」，改成：任务侧写库并发 `renewal.due` 事件（`key = user_id + period`），扣款、权益、短信、对账四个消费者各自异步执行。压测很漂亮，RT 从 1.2 s 降到 40 ms。

**事故 A：消息被重投，用户被扣两次（2025-11-04）**

| 时间 | 事件 | 数据 |
| --- | --- | --- |
| 13:58 | Kafka 一次 broker 主从切换，relay 侧出现 `TimeoutException` | — |
| 14:00 | relay 按「发送失败」重投，实际 broker 已落盘（发送成功、标记失败） | 重投 26,000 条，占当批 38% |
| 14:02 | 扣款消费者无幂等键、支付网关不校验幂等，同一会员被再次发起扣款 | 重复发起 3,120 笔 |
| 14:19 | 其中 1,180 笔重复扣款成功 | 199 元 × 1,180 = **23.5 万元** |
| 14:40 | 财务日切对账发现「流水数 > 会员数」 | 差 3,120 |
| 11-05 ~ 11-08 | 逐笔冲正 + 客诉处理 + 网关侧补幂等 | 客诉 910 起，处理 4 天 |

根因三件同时缺失：**relay 重投没有幂等键拦（生产端）**、**消费者没有去重表（消费端）**、**外部副作用没有幂等 token（边界）**。三处任一存在，事故都不会发生。

**事故 B：为了「可靠」加了无限重试，把下游打挂（同日 15:10）**

| 时间 | 事件 | 数据 |
| --- | --- | --- |
| 15:10 | 权益服务对第三方开通接口超时（P99 从 300 ms → 8 s） | — |
| 15:11 | 消费者代码是 `while(true) { try{...} catch{ continue; } }`，无退避、无上限 | 单实例 30 次/s |
| 15:14 | 消费者实例数 80 × 30 次/s，打向第三方 | **2,400 → 24,000 QPS（30 倍）** |
| 15:15 | 第三方限流全量拒绝，失败率 100%，重试量继续上升 | — |
| 15:40 | 摘除重试逻辑，改为指数退避 + DLQ，恢复 | 46,000 名会员权益延迟 3 小时 |

两张账单的本质是同一句话被违反两次：**重做是设计内的常态，不是故障**。事故 A 是「重做没被挡住」，事故 B 是「重做没有预算」。

## 05.2 ① 到底是什么：异步买的是「可用性加法」，付的是「重做许可」

**定义**：异步 = 把「A 同步调用 B 并等待返回」换成「A 写一条不可变记录进 broker，B 在之后某个时刻读到它」。A 的成功不再依赖 B 的可用性，代价是 A 不再拥有 B 的结果。

所以它买的从来不是「更快」，而是**可用性从乘积变成加法**：同步扇出 4 个下游、每个 99.9%，链路可用性 99.6%；异步后订单侧可用性 = 订单 API × broker，下游各自承压、各自重试。

| 维度 | 同步调用 | 异步消息 |
| --- | --- | --- |
| 「成功」的定义 | B 返回 200 | 消息落盘（broker ack） |
| 失败暴露时机 | 立刻，调用方可见并有上下文 | 事后，靠监控 / 对账 |
| 可用性 | 各下游连乘 | 加法（下游彼此隔离） |
| 事务边界 | 可以在同一个本地事务里 | **必然被切成两段**，中间没有原子性 |
| 重试由谁做 | 调用方（有上下文，可放弃、可改写参数） | 消费者（无上下文，只能**原样重做**） |
| 一致性 | 强（同事务）或会话内一致 | 最终一致，有一个可见窗口 |
| 幂等要求 | 可选（客户端重试才需要） | **强制，且必须端到端** |
| 排查成本 | 一个 trace | 两个 trace + 位点 + 积压 |

**四个「不叫异步」的反例**（判定只要一句：发送方是否依赖消费方的结果）：

- **假异步**：发完消息 `future.get()` 等回执——RT 变长，还多一次序列化，纯负收益。
- **拿 MQ 当 RPC**：reply topic + correlationId，排队延迟不可控，P99 通常比同步差一个数量级。
- **共享表轮询**：`status=0` 扫表是异步，但把削峰压力全压回主库，扫描成本随历史数据线性增长（→ `eng/28`）。
- **事件驱动、消费者直接改生产者的表**：耦合没消失，只从「接口耦合」退化成「表结构耦合」，更糟——表结构变更不经过契约评审。

## 05.3 ② 唯一真问题与 ③ 量级预算

### 唯一真问题

> **异步的全部内容，就是一份「允许重做」的授权书。**
> 一旦签了它，四件事同时变成你的活：重做要挡住（幂等）、重做可能乱序（顺序）、重做会堆积（背压）、重做看不见（可观测）。**四件事没有一件是免费的，必须逐条报价。**

| 从「允许重做」推出的约束 | 推出的设计 | 不做的后果 |
| --- | --- | --- |
| 重做一定会发生 | 每个副作用必须有幂等键，且端到端透传 | 重复扣款（§05.1 事故 A） |
| 重做可能乱序 | 顺序需求按业务不变量倒推，不按「看起来需要」 | 已取消订单被发货 |
| 重做会堆积 | 积压水位是一个要算的数，不是「看着办」 | 崩溃被推迟 4 分钟，然后一起爆 |
| 重做不可见 | `trace_id` + 幂等命中率 + 最老消息年龄，三个指标缺一不可 | 事后 3 天才发现账差 |
| 重做有单价 | 重复率 × 单价 × 量 = 每天固定成本，要写进预算 | 「优化」掉幂等表省 2 台机器，赔 23 万 |

### 量级与预算：全部推一遍

```
到期会员        5.8 万/天 → 均值 0.67 条/s
峰值系数        ×20（不是流量峰值，是定时任务集中触发的尖峰）→ 13.4 条/s
下游扇出        4 个消费者（扣款 / 权益 / 短信 / 对账）→ 峰值 54 次/s 下游调用
分区数          13.4 ÷ 单分区 50 条/s（外部 IO 型，不是 CPU 型）= 1 个够
                但按「消费者并行度 + 未来 10 倍」留 8 个分区
积压账          尖峰 5.8 万条一次灌入 / 消费速率 200 条/s = 290 秒 ≈ 5 分钟
                这就是本篇的 N：资金类 T > 5 分钟必须扩容或限流生产端
重复率预算      设计内 0.1%（relay 重投 + rebalance）→ 58 条/天
重做的固定成本  58 × 199 元 = 1.15 万元/天（扣款类）
                58 × 0.8 元 = 46 元/天（权益类）  ← 同一个重复率，单价差 250 倍
```

最后一行是本节唯一真正重要的结论：**「重复率」不是质量指标，是成本项；决定它该被压到多少的，是重做一次的单价。** 埋点类重复 1% 无所谓，扣款类重复 0.01% 也要建幂等表。

## 05.4 ④ 形态怎么选（一）：同步 / 异步判定矩阵

四个维度决定形态，但只有两个能画成象限——**「调用方能否等待」×「重做是否安全」**。另两个（是否必须立刻给用户结果、是否有外部副作用）作为一票否决项叠加。

| 象限 | 条件 | 结论（形态） | 幂等要求 | 失败处理 | 典型 |
| --- | --- | --- | --- | --- | --- |
| **Q1 必须等 + 重做不安全** | 用户/上游此刻就要确定结果，且错一次不可逆 | **同步 + 本地事务 + 幂等键**，不许异步 | 必需（防客户端重试） | 快速失败，返回明确错误码 | 扣款、余额扣减、库存预占、下单 |
| **Q2 必须等 + 重做安全** | 结果要立刻给，但错了重算即可 | **同步调用 + 短超时 + 降级兜底**（并行扇出） | 不必需 | 超时返回兜底值，记降级日志 | 风控分、推荐补位、积分展示 |
| **Q3 可等 + 重做安全** | 没人等，错了重做一遍也无害 | **纯异步事件，允许丢（打点计数）** | 可选 | 丢弃 + 计数告警 | 埋点、报表、缓存刷新、搜索索引 |
| **Q4 可等 + 重做不安全** | 没人等，但错一次就是钱/权益 | **异步 + 幂等 + 保序 + DLQ + 对账**（本篇全部内容） | **强制，端到端** | 退避重试 → DLQ → 人工 | 扣款通知、发券、积分、异步开卡 |

```
┌─────────────────────────────────────────────┐
│ ① 调用方能否等待结果？（HTTP 上下文 < 300ms）│
└──────────────┬───────────────┬──────────────┘
          不能 │               │ 能
               ▼               ▼
┌───────────────────┐  ┌───────────────────┐
│ ② 重做安全吗？     │  │ ② 重做安全吗？     │
└──┬─────────────┬──┘  └──┬─────────────┬──┘
否 │             │ 是  否 │             │ 是
   ▼             ▼        ▼             ▼
┌────────┐ ┌────────┐ ┌────────┐ ┌─────────┐
│Q1 同步 │ │Q2 同步 │ │Q4 异步 │ │Q3 纯异步│
│+事务   │ │+降级   │ │+幂等   │ │（可丢） │
│幂等键  │ │短超时  │ │保序DLQ │ │丢弃+计数│
│扣款/库存│ │风控/推荐│ │发券/通知│ │埋点/索引│
└────────┘ └────────┘ └────────┘ └─────────┘

一票否决 1：有不可撤销的外部副作用（打款 / 短信 / 邮件 / 发券）
           → 无论落在哪个象限，必须带幂等 token，且第三方要能校验
一票否决 2：调用方是 HTTP 请求上下文且预算 < 300ms
           → 不允许同步扇出 ≥3 个下游（改写：并行 + 分档超时，或移出请求路径）
```

**顺序很重要**：先问 ①（这是架构约束，通常改不了），再问 ②（这是业务后果，必须业务 owner 签字）。反过来先问「用什么 MQ」的评审，答的都是错的问题。

## 05.5 ④ 形态怎么选（二）：消息形态三选一

同一件事用错消息形态，后面所有设计都会歪。判据只有一句：**这条消息描述的是「已经发生的事实」，还是「希望对方做点什么」？**

| 维度 | 领域事件（事实） | 命令（意图） | 状态复制（数据同步） |
| --- | --- | --- | --- |
| 语义 | 宣告发生过什么，不关心谁来消费 | 指定「你去做这件事」 | 让另一个存储跟上这份数据 |
| 命名 | `order.paid`、`renewal.due`（过去式/名词） | `charge.renewal`、`grant.coupon`（祈使） | `user_row.changed`、binlog event |
| 消费者数量 | **0 到 N 个**（没人消费也合法） | **恰好 1 个执行者** | **1 个复制器** |
| 载荷 | 事实 + 最小投影（ID、关键字段、`schema_version`） | 执行所需**全部参数** + 幂等键 | 行级变更：主键 + after image + 位点 |
| 重试语义 | 每个消费者独立重试，互不牵连 | 执行者重试至成功，或进 DLQ | 可整批重放、可从位点重来 |
| 幂等责任方 | **每个消费者各自负责** | **执行者负责**（命令自带 token） | **复制器负责**（按主键 upsert + 位点） |
| 顺序要求 | 同一聚合内保序 | 同一目标的命令必须串行 | 必须严格按变更顺序 |
| schema 演进 | 只许向后兼容（加字段、不改语义） | 契约即接口，版本化 | 跟随源表结构，需 expand-contract |
| 反模式 | 用事件表达意图（消费者互相猜） | 一个命令多个执行者（重复干活） | 用事件做同步（丢一条就永久不一致） |

三条落地规则：

1. **事件的载荷里不要放「希望对方做什么」**。一旦放了，它就是伪装成事件的命令，会出现「两个消费者都以为自己该执行」的事故。
2. **命令必须有明确的唯一执行者与回执通道**。命令没有回执，等于把「失败」变成了「不知道」，只能靠对账兜底。
3. **状态复制不要用业务事件实现**。业务事件是语义层，会漏字段、会改含义；数据同步应该走 CDC binlog（→ `eng/28`），保证「行的最终态一致」而不是「你猜我改了什么」。

## 05.6 ④ 形态怎么选（三）：要不要顺序（按不变量倒推，不按感觉）

### 判定方法（三步，写进评审模板）

```
第 1 步  写出这条链路要守护的不变量（来自 02 的聚合不变量表，不许凭空想）
第 2 步  问：把同一聚合的两条消息执行顺序互换，哪条不变量会破？破在哪个字段上？
第 3 步  再看它能否被「状态机条件更新 / 版本号」吸收：
           能吸收 → 不必保序，用条件更新兜底（吞吐不受损）
           不能吸收 → 必须保序，且顺序范围 = 那个聚合（不是全局）
```

**「看起来需要顺序」最常见的假阳性**：看到「订单」「账户」就要求有序，但真正的不变量可能只约束「同一订单的两条相邻事件」，与不同订单之间毫无关系——那就不需要全局单分区，只要 key 选对。

### 三个正例、三个反例

| # | 场景 | 不变量 | 乱序后果 | 判定 |
| --- | --- | --- | --- | --- |
| 正 1 | 订单状态机 `CREATED→PAID→SHIPPED/CANCELLED` | 状态只能单向流转 | 已取消订单被改回已支付 → 发货（代价 74 万，→ `eng/25 §25.1`） | **必须保序**（key=`order_id`） |
| 正 2 | 账户余额增减 + 版本号 | 余额 = Σ流水，且 `version` 单调 | 旧版本覆盖新版本 → 余额算错 | **必须保序**，或按 version 拒绝旧消息 |
| 正 3 | 同一会话的 Agent 上下文 | 第 N 步必须看到第 N-1 步结果 | 上下文错位，模型基于旧状态回答；`tool.call` 早于 `approval` = 安全事故 | **必须保序**（key=`session_id`） |
| 反 1 | 跨用户的短信通知 | 无（不同聚合，彼此无关） | 无 | 不需要，key 随便选 |
| 反 2 | 埋点上报（UV 靠 `visitor_hash` 去重） | 无跨事件不变量，最终收敛 | 计数瞬时偏差，秒级自愈 | 不需要，甚至可丢 |
| 反 3 | 搜索索引 / 缓存刷新（全量 upsert） | 目标态 = 最后一次写入 | 短暂脏读 | 不需要保序，但**要求带 `ts/version` 条件写**，否则乱序会留下永久旧值 |

注意反 3 的尾巴：**「不需要保序」不等于「不需要版本号」**。乱序会造成暂时脏读，能自愈的前提是写入带比较条件（`WHERE version < ?`）或「最后写胜 + 时间戳」。少了这一条，反 3 就变成正 3。

### 两种实现与代价

| 实现 | 顺序范围 | 吞吐上限 | 扩容方式 | 代价 | 用在哪 |
| --- | --- | --- | --- | --- | --- |
| **按 key 分区**（推荐） | 单 key 内（分区内） | 分区数 × 单分区能力 | 加实例（≤ 分区数）或加分区（**会改 key→分区映射，破序**） | key 选错 = 白保序；扩分区要挑低峰 | 99% 的业务：订单、支付、库存、会话 |
| **单分区** | 全局 | 单分区 1k~5k msg/s | **不能扩，只能升配** | 一条慢消息阻塞全站 | 账务流水、配置变更等极窄场景 |
| 业务串行化（lane） | 单 key（lane 内） | 受下游与 lane 调度限制 | 加 lane（同 key 不能换 lane） | 实现最复杂，位点要按连续水位提交 | 上游 key 不可控、同 key 跨 Topic |

**记住这一行**：`最大吞吐 = 分区数 × 单分区处理能力`，`最大并发度 = 分区数`。所以「消费者扩到 48 个但分区只有 24 个」是纯浪费——多出的实例分不到分区（→ `eng/25 §25.4`）。

```
   │退避→分层重试 ││丢弃+计数 ││DLQ + 人工    │
   │→ DLQ       │└─────────┘└─────────────┘
   └───────────┘
观测五件：lag(按分区) · 最老消息年龄 · 幂等命中率 · DLQ 水位 · 重复业务副作用数(=0)
```

## 05.7 ⑤ 会在哪崩（一）：幂等的落点

### 幂等键该属于哪个聚合

不属于消息，属于**产生副作用的那一侧的聚合根**。三条规则：

1. **必须是「创建后不变」的业务主键**：`order_no`、`(user_id, period)`、`(run_id, step_seq)`。用 `status`、`updated_at` 当键，第二次算出来就是另一个值（→ `eng/24 §24.6`）。
2. **一个副作用一个键**。同一事件的「扣款」和「发短信」是两个副作用、两个等级（L2 / L1），必须分别去重。若强行共用一个 `event_id`，要么短信被误跳，要么扣款被放行。
3. **键的归属方是执行者，不是生产者**。生产者只能提供 `event_id`（它不知道下游有几个副作用）；`event_id` 只够做 L1 级去重，跨消费者共享同一个 `event_id` 去重表会互相误判。

### 放在哪一层

| 层 | 能挡什么 | 挡不住什么 | 用在哪 |
| --- | --- | --- | --- |
| **网关** | 同一 `request_id` 的客户端重放、双击、重定向重提 | 消费端 broker 重投（没有 `request_id`） | 开放 API、C 端提交按钮 |
| **应用层**（消费幂等表） | 任意来源的重复消费 | 外部副作用（无法与 DB 同事务）；跨库场景的脏标记 | 通用底座，L1/L2 默认落点 |
| **领域层**（状态机 + 唯一索引） | 非法状态迁移、并发写、累加型脏写 | 需要建模出状态机；无流转语义的业务无效 | 有状态的聚合：订单、工单、账户 |

> 一条纪律：**幂等表必须与业务表同库同事务**。分开写会留下 `status=PROCESSING` 的永久脏标记，后续消息全被当重复跳过，业务永远不生效（→ `eng/24 §24.6` 第 2 条）。

### 三种实现与适用边界

| 实现 | 机制 | 适用 | 边界 / 代价 |
| --- | --- | --- | --- |
| **唯一键** | 业务表加 `biz_key` 唯一索引，冲突即重复 | 有天然业务键的写入：流水、券、账单、权益记录 | 只挡「同一库内」；冲突必须回查是哪条索引，别把「手机号冲突」吞成「消息重复」 |
| **状态机** | 条件更新 `WHERE status IN (...)`，影响 0 行 = 重复 | 单向流转的聚合：订单、审批、发货、支付回调 | 累加型（`balance = balance + x`）无效，必须配合唯一键 |
| **token / 一次一密** | 预发放 token，执行后原子作废；透传给第三方 | 外部不可撤销副作用：打款、发券、发短信 | 第三方必须支持幂等键或提供查询接口；token 作废要原子 |

实现细节一律引 `eng/1`–`eng/6`（幂等实现与失效模式），本篇只回答「键属于谁、放在哪层」。

## 05.8 ⑤ 会在哪崩（二）：Outbox 与事务边界

**为什么「写库 + 发消息」必须同事务**：它们是两个独立的写操作，中间没有原子性，于是有两个方向的脏数据：

- 先提交、后发送 → 发送失败 → **事件永久丢失**，下游永远不知道（超卖、账不平）。
- 先发送、后提交 → 提交失败 → **幽灵消息**，下游扣了不存在的库存。

**结论只有一句话：把「发消息」这个不可控的外部动作，变成「写本地表」这个可控的数据库动作。** 原子性来自本地事务，不来自 MQ，也不来自分布式事务框架。

| 实现 | 原子性靠什么 | 消息何时可见 | 投递延迟 | 运维复杂度 | 顺序 | 主要坑 |
| --- | --- | --- | --- | --- | --- | --- |
| **本地消息表 + 轮询** | 业务库本地事务 | relay 投递后 | 200 ms ~ 2 s | 低（一个定时任务） | 按聚合分区 | 长事务锁行、表膨胀、只写不删 |
| **事务消息**（RocketMQ 半消息 + 回查） | MQ 协调半消息 | 本地事务提交后 | 10 ~ 100 ms | 中（MQ + 回查） | 按 MessageQueue | 回查依赖业务主键可查；半消息堆积；换 MQ 要重写 |
| **binlog 订阅**（Debezium CDC） | 本地事务（binlog 即事实） | CDC 读到 INSERT 后 | 10 ~ 100 ms | 高（Connect、位点、schema） | 按 Kafka key | binlog 权限、位点回退重复、表结构变更要兼容 |

选型建议：**先用轮询把链路跑通，再按积压与延迟决定要不要上 CDC**。一上来就 Debezium + Kafka Connect，出问题时你会在「binlog 权限、Connector 位点、schema 兼容」三件事里同时迷路。实现细节、DDL、清理归档全部在 → `eng/10`。

```java
// Java 骨架：写路径（业务 + 事件同事务，绝不在此发 MQ）+ 投递器（至少一次）
@Service
public class RenewalService {
    @Transactional(rollbackFor = Exception.class)
    public void schedule(String userId, String period, long amountFen) {
        RenewalTask task = RenewalTask.of(userId, period, amountFen);
        taskMapper.insert(task);                       // 业务写
        outboxMapper.insert(OutboxEvent.builder()
            .eventId(task.getId())                     // 幂等键在事务内生成
            .aggregateType("renewal")
            .aggregateId(userId + ":" + period)        // 分区键 = 聚合根
            .aggregateVersion(1L)
            .eventType("renewal.due")                  // 领域事件命名：事实，不是命令
            .payload(Map.of("schema_version", 2, "user_id", userId,
                            "period", period, "amount_fen", amountFen))
            .build());                                 // 同一事务，见 eng/10
    }
}

@Scheduled(fixedDelay = 200)
public void relayOnce() {
    // 短事务认领：SKIP LOCKED 让多实例互不阻塞；不要在事务内发 MQ
    for (OutboxEvent e : outboxMapper.claim(100)) {     // NEW/FAILED 且 next_retry_at <= now
        try {
            producer.send("renewal.due", e.getAggregateId(), e.getPayload());
            outboxMapper.markSent(e.getId());
        } catch (Exception ex) {
            outboxMapper.markRetry(e.getId(), ex.getMessage()); // 指数退避，10 次后进人工
        }
    }
}
```

## 05.9 ⑤ 会在哪崩（三）：投递语义的现实

**至少一次是默认，精确一次只在「同一存储内」成立。** 三个必须记住的边界：

- `enable.idempotence=true` 只保证「同一 producer 会话、同一分区」不重复，不管消费者、不管跨库。
- Kafka 事务把「输出记录 + 输入位点」原子提交，实现的是 **Kafka 内部** exactly-once；你的 `UPDATE account` 不在这个事务里。
- 「消息只投一次」不存在——broker 只存一条，消费者处理完、ack 丢失、重投，业务仍然执行了两次。

### 「端到端不重复」的完整条件清单（缺一条就是 0）

```
端到端不重复 = 生产不丢 × 消费不丢 × 副作用去重

①  生产端不丢    acks=all + min.insync.replicas>=2 + 幂等生产者
②  生产的原子性  Outbox / 事务消息：保证「写库成功 ⇔ 事件存在」
③  消费端不丢    enable.auto.commit=false + 先处理再提交位点（manual_immediate）
④  消费端去重    (consumer_group, 幂等键) 唯一索引，且与业务写同库同事务
⑤  外部副作用    幂等键透传给第三方（token / 一次一密），或第三方提供查询接口
⑥  保留期够长    去重表保留 ≥ max(消息保留, 重试窗口, 位点回退窗口) × 2
⑦  兜底对账      每日条数对账 + 金额对账；没有对账，静默丢失永远发现不了
```

```go
// Go 骨架：先处理（幂等）→ 再提交位点；失败退避 → DLQ，绝不无限重试
func (h *Handler) Handle(ctx context.Context, m kafka.Message) error {
	key := string(m.Key) // user_id:period，幂等键来自 key，不解析 body
	err := h.inTx(ctx, func(tx *sql.Tx) error {
		res, err := tx.ExecContext(ctx, `
			INSERT INTO consume_dedup (consumer_group, idem_key, topic, partition_no, offset_no, status)
			VALUES (?, ?, ?, ?, ?, 2) ON DUPLICATE KEY UPDATE id = id`,
			"renewal-charge", key, m.Topic, m.Partition, m.Offset)
		if err != nil {
			return err
		}
		if n, _ := res.RowsAffected(); n == 0 {
			return nil // 已处理过：静默成功，本次不再调支付网关
		}
		// 外部副作用：幂等 token = key，网关侧可校验（一票否决项）
		if err := h.gateway.Charge(ctx, key, amountOf(key)); err != nil {
			return err // 回滚去重行，交给退避重试
		}
		_, err = tx.ExecContext(ctx, `INSERT INTO renewal_ledger(idem_key, amount_fen) VALUES (?, ?)`,
			key, amountOf(key))
		return err
	})
	if err != nil {
		if h.attempts(m) < 5 {
			return err // 不 ack → 指数退避重投
		}
		return h.dlq.Send(ctx, m, err) // 超过上限：进 DLQ + 告警，不原地死磕
	}
	return h.committer.Commit(ctx, m) // 业务提交成功后才提交位点
}
```

注意这段代码里的三处顺序：**去重行与业务写在同一个事务**、**去重插入排在外部调用之前**、**位点提交排在事务提交之后**。外部副作用不可回滚，所以必须「先占位再调用」；占位失败时退化为「重试前先查网关的幂等结果」。

## 05.10 削峰与背压：队列长度不是容量，是延迟

### 三个公式

```
积压增速      g = p - c                 p=生产速率，c=消费速率
追上时间      T = L / (c - p)           仅当 c > p；c ≤ p 时 T = ∞（扩消费者无用）
平均排队延迟  W = L / c                 Little's law 稳态形式：L = λW
扩容后目标    c' ≥ 2p                   留一倍余量，否则下一波尖峰立刻再次堆积
```

**同一队列长度，含义完全不同**：当 `c = 200 条/s`，

| 积压 L | 平均排队延迟 W | 结论 |
| --- | --- | --- |
| 1,000 | 5 s | 正常毛刺，不动 |
| 10,000 | 50 s | 超过多数业务的可见窗口，告警 |
| 100,000 | 500 s ≈ 8 分钟 | 必须扩容，否则 SLA 已破 |
| 2,880 万 | 40 小时 | 已经不是在扩容，是在事故中（→ `eng/25 §25.1` 事故二） |

### 扩容信号：看「追上时间」，不看「lag 绝对值」

| 信号 | 含义 | 动作 |
| --- | --- | --- |
| `g > 0` 且所有分区均匀上涨 | 消费能力不足 | 扩实例（**≤ 分区数**）→ 优化批量 → 最后才扩分区 |
| `T > N 分钟` | 按当前速率追不上 SLA | 立即扩容，或对生产端限流 |
| 只有单个分区 lag 涨 | 毒消息卡住 | 转 DLQ + reset 位点，重启无用 |
| 消费速率整体下降、下游 P99 上升 | 下游慢 | 限流/熔断/降级，扩容只会把下游打得更死 |
| lag 锯齿状 + rebalance 次数飙升 | 重平衡抖动 | 调 `max.poll.interval.ms`、静态成员、避开高峰发布 |

`N` 的取值按业务定，写进告警配置：**资金类 5 分钟、交易类 15 分钟、通知类 60 分钟、分析类不设（改为日终对账）**。

### 什么时候该丢弃（按业务分级）

| 级别 | 判据 | 例子 | 积压时的动作 |
| --- | --- | --- | --- |
| **可丢** | 丢一条不影响账，事后可重算 | 埋点、报表计数、缓存刷新、搜索索引 | 直接丢或降采样，**但必须计数告警**（静默丢是最坏的） |
| **不可丢** | 丢一条造成脏数据但可事后补 | 通知、积分、投影、存档 | 进 DLQ + 补偿任务重放（`idempotentKey` 已在 Topic 登记表里） |
| **必须补偿** | 丢一条就是资金/权益损失 | 扣款、发券、库存、开卡 | **禁止丢弃**；只能限流生产端 + 扩容 + 人工兜底 |

铁律：**队列只能当缓冲，不能当「不丢」的保证**。不丢靠 Outbox（§05.8）+ 幂等（§05.7）+ 对账（§05.9 ⑦）三件套。

## 05.11 哪些业务绝对不能异步

不是「涉及钱都不能异步」——而是**「用户是否立刻需要这个结果」**画出这条线。

| 业务 | 为什么不能异步 | 正确的异步边界（切在哪） |
| --- | --- | --- |
| 支付/扣款结果页 | 用户 3 秒内要确定结果；异步窗口会诱发重复提交 | **扣款同步 + 幂等键**；对账、通知、积分异步 |
| 强一致余额扣减（主账） | 典型「读后写」：扣完立刻要看到新余额 | 主账同步扣；权益、账单、积分异步 |
| 库存扣减（不超卖） | 超卖不可回滚，只能赔 | **预占同步**（条件更新 / Redis Lua）；风控与日志异步 |
| 需要立刻回滚的编排步骤 | 异步后失败只能补偿，不能回滚 | 同步 + 本地事务；跨服务用 Saga 补偿（→ `eng/13`） |
| 下单前的风控拦截 | 拦截必须在写入**之前**发生 | 同步调用，短超时 + 降级放行策略必须业务签字 |
| 单号 / 幂等键发放 | 拿不到单号无法给用户返回 | 同步（号段 / 雪花），失败即失败 |

反过来也有一条：**「扣款成功之后的一切」都必须异步**。同步链路里只要有一个下游能拖慢主路径，它就会在某个深夜把整条交易链路拖死（→ `eng/23 §23.1` 事故一：40 ms 的积分服务拖死 200 个线程）。

## 05.12 ⑥ 换挡信号与 ⑦ 怎么验证

| 阶段 | 形态 | 量级 | **换挡信号（硬阈值）** | 代价 |
| --- | --- | --- | --- | --- |
| A0 | 同步串行扇出 | 下游 ≤2，RT < 100 ms | 下游 ≥3，或任一 P99 > 主链路预算的 40% | — |
| A1 | **并行同步 + 分档超时** | RT = max(下游) | 峰值/均值 > 3，且按峰值扩容成本 > 3 倍均值成本 | 一票否决项要求降级策略 |
| A2 | **Outbox + 单 Topic 按 key 分区** | 万级 msg/s | `T > N` 分钟、单分区 > 80%、最老消息年龄 > 5 min | 最终一致窗口出现 |
| A3 | 消费者拆分 + 重试分层 + DLQ + 幂等表 | 十万级 | 重复率 > 0.5%、DLQ 增长 > 100 条/小时 | 幂等表存储 × 保留期成本 |
| A4 | 扩分区 + 分层存储 + 按业务隔离 Topic/集群 | 百万级 | 单 Topic 分区 > 200、rebalance > 5 min | key 重分布、运维复杂度跳一级 |

**先试 A1，再试 A2**：并行 + 分档超时在「可用性」上与 MQ 等价，只在「削峰」上不等价。只有峰值/均值 > 3 时才必须上 MQ——这条判据能省掉一半不必要的中间件。

验证四件事（可执行，不是「做好监控」）：

1. **崩溃注入**：在「业务提交后、位点提交前」`kill -9` 消费者，断言业务表只有 1 条、`consume_dedup` 只有 1 条 `DONE`、位点最终推进。
2. **重复注入**：同一 `event_id` / 幂等键灌 100 次、200 并发，断言副作用只发生一次（扣款只 1 笔）。
3. **乱序注入**：同 key 倒序投递 `paid` / `cancelled`，断言状态机拒绝非法迁移（影响 0 行），最终态正确。
4. **积压演练**：停消费者 10 分钟，断言告警 2 分钟内触发、扩容后 `T` 在 5 分钟内开始下降；并核对「实例数 ≤ 分区数」。

## 05.13 反模式表

| 反模式 | 长什么样 | 为什么错 | 正确做法 |
| --- | --- | --- | --- |
| **异步里做同步 RPC 长调用** | 消费者内直接调 3 秒的第三方接口 | 消费吞吐被最慢外部依赖封顶；一条慢消息阻塞整个分区，lag 全量上涨 | 消费者只写本地状态 + 入队；外部调用交给独立 worker + 状态机 |
| **消费者无限重试不退避** | `while(true){ try{}catch{continue} }`，无上限无退避 | 重试风暴把下游打挂（§05.1 事故 B：2,400 → 24,000 QPS） | 指数退避 + 次数上限 + DLQ + 熔断（→ `eng/18`） |
| **用 MQ 当数据库** | 从 Topic 反查历史订单；`retention=-1` 当存储用；拿 MQ 做唯一查询入口 | 无索引、无事务、重放成本随量线性增长；retention 一清数据就没了 | 真相源永远在 DB；MQ 只传「变更通知」 |
| **消息体里塞实体快照** | payload 放整个 Order + 用户档案 + 附件 | schema 演进地狱；消费者拿到过期快照；2 MB 撞消息上限 | 只放 ID + 必要投影 + `schema_version`；大对象外置传引用 |
| **没有 DLQ** | 失败原地重试到天荒地老 | 一条毒消息冻住整个分区，lag 涨到全量 | 重试分层 + DLQ + 人工队列 + `dlq_size > 0` 即告警 |
| **假异步** | 发完消息 `future.get()` 等结果 | RT 变长，还多一次序列化 | 要么真异步，要么老实同步调用 |
| **消费端无幂等就上线** | 「消息只会来一次吧」 | 至少一次语义下重复是必然，把重复变成脏数据 | 幂等键缺失即禁止上线（写进 Topic 登记表） |

## 05.14 十分钟答题卡

被问「这里为什么要异步 / 要不要上 MQ」时，按这个顺序答，不要从「我用 Kafka」开始：

```
1  该不该   四问：要立刻给用户结果？重做安全？有外部副作用？调用方能等？
2  真问题   异步 = 允许重做；重做的四项代价（幂等/乱序/积压/可观测）当场报价
3  消息形态  事实→领域事件（0~N 消费者）；意图→命令（1 个执行者）；数据同步→状态复制（CDC）
4  要不要序  按不变量倒推：两条消息顺序互换会破哪条不变量？能被状态机吸收就不必保序
5  幂等落点  键属于"产生副作用的聚合根"；应用层去重表 + 领域层状态机/唯一索引
6  事务边界  写库+发事件必须同事务 → Outbox（本地消息表 / 事务消息 / binlog 订阅）
7  投递语义  至少一次是默认；恰好一次 = 生产不丢 × 消费不丢 × 副作用去重，缺一是 0
8  积压      T = L/(c-p)；c ≤ p 时 T=∞ 扩消费者无用；T > N 分钟就扩，N 按业务分级
9  丢弃      可丢 / 不可丢 / 必须补偿三级；资金类禁止丢弃，只能限流生产端
10 换挡      下游≥3、峰值均值比>3、T>N、DLQ>100/h —— 四条阈值就是换挡开关
```
