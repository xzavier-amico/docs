## 01.1 事故引子：按均值配容量的第 47 分钟

**背景**：某零售 App 的「券会场」接口，日请求 1,900 万次（DAU 620 万 × 人均 3.06 次），日均 QPS 220。大促前架构评审时，负责人写了一句「日均 220 QPS，加 30% 余量，2 台 4C8G 足够」——这句话在评审板上没有任何人反对，因为它**每一步都成立**，只是中间少了三个乘号和一个挂载点。

**时间表（2025-11-11，大促首日）**：

| 时间 | 事件 | 数据 |
| --- | --- | --- |
| 19:40 | 首页挂「限时券」入口，全量 AB 放开 | 覆盖 100% 用户 |
| 19:58 | 网关 QPS 从 60 抬到 780，CPU 2 台各 31% | 看起来健康 |
| 20:00:00 | 开抢瞬间，券列表 QPS 冲到 **3,400** | 峰值系数 15.4 |
| 20:00:24 | 客户端因 3s 超时开始重试，接口错误率 15% | 入口 QPS 涨到 4,300 |
| 20:00:41 | 下游「券库存」DB 读 QPS 到 **9,100**，主库 CPU 96% | 缓存未命中放大 |
| 20:01:07 | 连接池 pending 涨到 214，Tomcat 200 线程全满 | 连接数 100% |
| 20:01:30 | P99 从 180 ms 涨到 **8.4 s**，错误率 61% | 用户看到「太火爆了」 |
| 20:03 | 运维把副本扩到 6 台，**错误率不降反升到 68%** | 每台新实例多 50 个抢连接的进程 |
| 20:12 | 加缓存 + 网关限流 1,200 QPS，P99 回到 400 ms | 限流误伤 43% 真实流量 |
| 20:47 | 全部恢复。限流期间可售时段流失 **47 分钟** | 折 GMV 约 380 万元 |
| 次日 | 客服工单 2,100 单，补偿券 12 万元，值班复核 3 人 × 2 天 | 直接 + 间接成本约 412 万元 |

**一次事故里同时踩了四个坑**，每一个都是"少算了一个乘号"：

| 他们算的 | 真实值 | 漏掉的乘号 | 后果 |
| --- | --- | --- | --- |
| 220 QPS（日均） | 3,400 QPS（峰值） | 峰值系数 K ≈ 15 | 容量差 **15 倍** |
| 3,400 QPS | 4,300 QPS（入口） | 重试放大 R = 1.26 | 自我 DDoS |
| 一个接口一次调用 | 5 个下游 / 请求 | 扇出 F = 5 | 下游承压 ×5 |
| 缓存命中 95% → 回源 5% | 命中滑到 85% → 回源 15% | 未命中放大 M = 1/(1−h) | DB 读 ×3 |
| "2 台够" | 需 16 台 | 单机安全 QPS = 拐点值 ×0.75 | 在拐点 **5.2 倍**处运行 |

**错误推导链 vs 正确推导链**（本篇最重要的一张对照表，评审时逐行对）：

| 步骤 | 错误推导链（事故版） | 正确推导链 | 偏差倍数 |
| --- | --- | --- | --- |
| ① 请求量 | 1,900 万 / 天 | 1,900 万 / 天 | 1.0 |
| ② 均值 QPS | 220 | 220 | 1.0 |
| ③ 峰值 QPS | **没做，直接用 220** | 220 × K(15) = 3,300 | 15.0 |
| ④ 入口 QPS | 3,300 | 3,300 × R(1.26) = 4,158 | 1.26 |
| ⑤ 下游调用 | 未计 | 4,158 × F(5) = 20,790 | 5.0 |
| ⑥ 回源 QPS | 未计 | 4,158 × Σ未命中 ≈ 1,164（稳态）/ 2,495（命中率滑档） | 2.1 |
| ⑦ 机器数 | ceil(286/400)+1 = **2 台** | ceil(4,158/(400×0.75)) + 2 = 14 + 2 = **16 台** | **8.0** |
| ⑧ 月成本 | 2×480+3,600+800 = 5,360 元 | 16×480+3,600+800+1,400 = 13,480 元 | 2.5 |
| ⑨ 结论 | "够用，量大了再加" | "实载 65%，其余靠弹性 + 降级" | — |

> 🩸 **本篇的唯一真问题就在这里**：错误推导链的每一行都**能被一个不懂技术的人听懂**——"日均 220 QPS，加 30% 余量"，逻辑完美。所以约束卡的价值不在"算得准"，而在**强制把每一层放大显式写出来，让漏算变成看得见的空格**。评审时如果一行乘号是空的，那就是事故的入口。

## 01.2 到底是什么：约束卡的七个字段

**定义**：约束卡 = 用**七个数字**描述一个系统的输入边界，使得「加不加缓存」「分不分片」「上不上异步」这三个问题都有唯一答案。它有三个反例：

- **不是需求文档**：「支持大促高峰」不含数字，进不了卡。
- **不是指标看板**：看板是"现在是多少"，卡是"允许多少"。前者事后，后者事前。
- **不是容量结论**：「需要 12 台」是推导的**输出**；如果它出现在输入里，说明有人在拍脑袋并把结论伪装成前提。

| # | 字段 | 怎么问出来（可复制的话术） | 答错的后果 |
| --- | --- | --- | --- |
| 1 | **读写比** | 「这个接口上，一天里读操作和写操作分别是多少次？把埋点原始 count 给我，不要给比例。」——比例是推导物，不是原始输入 | 读写比答成 1:1（实际 18:1），会得出"读写分离没必要"的结论，直接砍掉最便宜的优化；反向答错（实际 2:1 当成 100:1）会做出一个无用的多级缓存，并把一致性问题带进账务链路 |
| 2 | **峰值系数 K** | 「过去 12 个月，**峰值 5 分钟的平均 QPS** 除以**当日日均 QPS**，最大值是多少？峰值持续多久？」——必须带"持续时长"，因为没有它就算不出弹性 vs 常驻 | K 答成 3（实际 15），容量差 5 倍；K 答成 15 但不说"只持续 1 小时"，会导致 12 台机器 23 小时空转，成本被吃掉 60%（→ §01.8） |
| 3 | **增长曲线** | 「年增长是按倍数还是按线性？倍数多少？拐点是什么事件（投放 / 上首页 / 出海）？」——必须区分"自然增长"和"事件驱动跳变" | 用 30% 线性增长去规划一个"上首页即 ×6"的业务，每 4 个月重做一次容量；反过来按 ×10 预留，会买一堆半年用不上的机器 |
| 4 | **延迟预算** | 「端到端 P99 目标是多少毫秒？这个数字来自哪里——竞品、用户访谈、还是上一版监控？」——必须能追到来源 | 预算答成"越快越好"，等于没有预算，每个环节都敢要 200 ms；答成 P50 目标，则整条链路会在 P99 上同时超支，且无法判断先砍谁（→ §01.6） |
| 5 | **一致性要求** | 「如果用户刚领的券，1 秒后刷新看不见，能接受吗？如果看见券但下单时提示没了，能接受吗？」——必须问**两种方向的错**，不能只问一种 | 只问"能不能接受延迟"会漏掉"读己之写"这一档；一致性答得比业务需要更强（要强一致），代价是缓存全废、跨库事务、P99 翻倍；答得更弱，则出现"领了看不到"的客诉 |
| 6 | **成本上限** | 「这套系统每月允许花多少钱？按每百万请求多少元报，还是按月总额报？」——必须拿到**预算责任人的数字**，不是架构师估计 | 没有上限时，"加个 Redis""上个 ES""拆个微服务"全部零阻力通过，成本在 6 个月内变成 3 倍且无人决策；上限答错（按均值报价，实际按峰值付费）会导致预算超支 1.8 倍（→ §01.3 末） |
| 7 | **SLA** | 「允许每月不可用多少分钟？4 个 9（4.3 分钟）还是 3 个 9（43 分钟）？」——必须换算成分钟，且追问"这个数字在合同里吗" | SLA 答成"高可用"，则容灾副本数、多 AZ、预案全都无从取舍；答得比合同更高（内部 5 个 9）会让所有冗余都变成必需品，成本翻倍而合同并不要求 |

> **七个字段的相互关系必须一起解，不能逐个填**：K 大且峰值时长短 → 弹性优先；读写比高且一致性弱 → 缓存优先；一致性强制且读写比低 → 直接单库 + 事务，任何缓存都是负债。**单看任何一个字段都会得出错误形态**，这也是 §01.7 那张读写比表必须和 §01.6 延迟预算表一起读的原因。

约束卡进代码（Java，演示"约束卡进代码"而不是进文档）：

```java
public record ConstraintCard(
        double readWriteRatio, double peakFactor, double growthPerYear,
        int p99BudgetMs, Consistency consistency, long monthlyCostCapCny, Sla sla) {

    public enum Consistency { STRONG, READ_YOUR_WRITES, EVENTUAL }
    public enum Sla { THREE_9, FOUR_9, FIVE_9 }

    /** 缺一个字段就不是约束卡：宁可抛异常，也不要让下游拿到"大概"的数字 */
    public ConstraintCard {
        if (!(peakFactor >= 1.0)) throw new IllegalArgumentException("peakFactor 必须 >= 1，均值不能当峰值用");
        if (!(readWriteRatio > 0)) throw new IllegalArgumentException("读写比缺失：它是形态分叉点");
        if (p99BudgetMs <= 0 || p99BudgetMs > 2000) throw new IllegalArgumentException("P99 预算缺失或超可感知上限");
        if (monthlyCostCapCny <= 0) throw new IllegalArgumentException("没有成本上限的评审等于没评审");
        if (growthPerYear < 0 || growthPerYear > 20) throw new IllegalArgumentException("年增长应为倍数且 <= 20");
        if (consistency == null || sla == null) throw new IllegalArgumentException("一致性等级与 SLA 不能留空");
    }

    /** 推导链进代码：同样七个字段，任何时候都能重算机器数，禁止手抄结论 */
    public int instances(long dailyRequests, double qpsPerInstance, int lossBudget) {
        double avgQps = dailyRequests / 86400.0;
        double peakQps = avgQps * peakFactor;
        double utilTarget = 0.75;                      // 实载率上限，见 §01.10
        return (int) Math.ceil(peakQps / (qpsPerInstance * utilTarget)) + lossBudget;
    }
}
```

`instances()` 里那行 `utilTarget = 0.75` 是关键：**机器数不是 `峰值/单机 QPS`，而是 `峰值/(单机 QPS × 实载率上限)`**。上一节事故的第 ⑦ 步就是漏了这个除法，配出 11 台却在 100% 实载上运行。

## 01.3 从业务指标到技术指标：一条不能断的推导链

下面是本篇的核心图，每个箭头上都标了"这里会漏什么"：

```
 业务指标（业务方能承诺的）                      技术指标（架构方能承诺的）
┌──────────────────────┐
│ DAU 620 万           │
│ 人均请求 3.06 次/天  │
└──────────┬───────────┘
           │  ×(1 + 机器/爬虫流量占比 8%)
           ▼
   日请求量 1,900 万 ──── ① /86400 ────▶  均值 QPS 220
           │                                   │
           │                        × K 峰值系数 15（峰值 5 分钟均值/日均）
           │                        ⚠️ 漏 K → 容量差 15 倍（事故第 ③ 行）
           ▼                                   ▼
                                     峰值 QPS 3,300
                                              │
                                          × R 重试放大 1.26（错误率 15% × 重试 2 次）
                                          ⚠️ 漏 R → 系统自我 DDoS
                                              ▼
                                     入口 QPS 4,158
                              ┌───────────────┼───────────────┐
                       × F 扇出 5      × L=λ×W 并发      × B 带宽
                              ▼               ▼               ▼
                      下游 20,790 QPS   在飞 831 请求    1.2 Gbps
                              │
                     × M = 1/(1−h) 未命中放大（h=0.85 → ×6.7）
                     ⚠️ 漏 M → DB 被打穿，而 App 看起来"只用了一半"
                              ▼
                     回源 QPS 2,495
                              │
                     ÷ (单机安全 QPS 400 × 实载率 0.75) + 容灾 2
                              ▼
                     机器数 16 台 ──▶ 月成本 13,480 元 ──▶ 23.6 元/百万请求
```

**公式表（每条都带假设，假设变了公式就得改）**：

| # | 公式 | 假设（不成立时怎么办） | 本篇算例 |
| --- | --- | --- | --- |
| 1 | `日请求 = DAU × 人均次数 × (1 + 机器流量占比)` | 假定 DAU 是**去重活跃**，不是 PV；若拿到的是 PV 要先除以 1.6~2.5 的人均访问深度 | 620 万 × 3.06 × 1.08 = 2,049 万 → 取 1,900 万（扣掉无效请求） |
| 2 | `均值 QPS = 日请求 / 86,400` | 假定流量在全天均匀；**这个假定 100% 不成立**，所以第 3 步必须有 | 1.9e7 / 86400 = 220 |
| 3 | `峰值 QPS = 均值 QPS × K`，`K = 峰值 5 分钟均值 / 当日日均` | K 必须来自**实测**（监控取 12 个月最大值）；活动型业务 K=10~20，工具型 K=2~4，秒杀型 K=50+ | 220 × 15 = 3,300 |
| 4 | `入口 QPS = 峰值 QPS × (1 + 错误率 × 重试次数)` | 假定重试是同步立即重试；若是退避重试，峰值被摊平但尾部拉长，K 与 R 不能重复计入 | 3,300 × (1+0.15×2) = 4,290 ≈ 4,158（退避后实测 1.26） |
| 5 | `下游调用 QPS = 入口 QPS × 扇出 F` | F 只算**同步**调用；异步消息的消费压力按"消息条数 × 消费者组数"另算（→ `eng/23`） | 4,158 × 5 = 20,790 |
| 6 | `回源 QPS = 入口 QPS × Σ(每个下游的未命中率)` | 命中率必须用**峰值时段**的实测值，不能用户均值；冷启动和大促首日的命中率会掉 10~20 个百分点 | 4,158 × (0.05×4 + 0.15) = 1,164（稳态）/ 2,495（滑档） |
| 7 | `机器数 = ceil(峰值入口 QPS / (单机安全 QPS × 0.75)) + 容灾台数` | 单机安全 QPS 必须是**拐点实测值**，不是压测"挂之前的值"（→ `eng/22`） | ceil(4,158/(400×0.75)) = ceil(13.9) = 14，+2 容灾 = 16 台；实载 4,158/6,400 = 65% |
| 8 | `并发数 L = 入口 QPS × P99 延迟(s)` | Little's law；容量的真实单位是**在飞数**，线程池/连接池都按它配 | 4,158 × 0.2 = 831 |
| 9 | `带宽 = 响应字节 × QPS × 8 / 1e9` Gbps | 只算响应体，但要乘 2 覆盖 TLS 与协议头；压缩率按 0.3 折 | 200 KB × 4,158 × 8 = 6.6 Gbps，×2(TLS) = 13.3 Gbps，压缩后 4.0 Gbps |
| 10 | `月成本 = N×单机月费 + 中间件 + 存储 + 带宽` | 假定常驻；若弹性，按"常驻 + 峰值机时 × 按量单价"重算（→ §01.8） | 16×480 + 3,600 + 800 + 1,400 = 13,480 元 |
| 11 | `每百万请求成本 = 月成本 / (月请求量 / 1e6)` | **分母必须是按峰值容量摊的月请求量**，否则报出来的单价一定偏乐观 | 13,480 / 570 = 23.6 元 |

**算例复算（评审时要求对方当场复述这 11 行）**：

```
日请求    620万 × 3.06 × 1.08 = 2,049 万 → 取 1,900 万（剔除 7% 无效/重放）
均值 QPS  1.9e7 / 86,400                     = 220
峰值 QPS  220 × 15                           = 3,300
入口 QPS  3,300 × 1.26                       = 4,158
在飞并发  4,158 × 0.200s                     = 831
下游调用  4,158 × 5                          = 20,790
回源 DB   4,158 × 0.28                       = 1,164（命中率滑档到 85% 时 2,495）
机器数    ceil(4,158/(400×0.75)) + 2         = ceil(13.9) + 2 = 16 台
带宽      200KB × 4,158 × 8 / 1e9 × 2(TLS)   = 13.3 Gbps → 压缩后 4.0 Gbps
月成本    16×480 + 3,600 + 800 + 1,400       = 13,480 元
单价      13,480 / (1.9e7×30/1e6 = 570)      = 23.6 元/百万请求
```

> **"单位成本"是所有容量讨论的终极口径**。评审时只问一句「这个接口每百万请求多少钱」，答不出的人在裸奔：他不知道自己买了什么，也不知道砍掉哪一层还能活。反向验证：如果算出来是 0.3 元/百万请求，那么这个接口不可能在对外报价里贡献毛利——要么这是内部接口，要么口径错了。

## 01.4 三个最常被漏掉的放大因子

这三个因子的共同特点：**它们都不在架构图上，只存在于乘法里**。图上是一个箭头，算上是 ×3。

### 因子一：重试放大 R

```
R = 1 + 错误率 e × 每次失败的平均重试次数 n
例：e = 15%，n = 2（立即重试）  →  R = 1.30
    若重试是退避（1s/3s/9s），峰值时刻的 R 会降到 1.05~1.15，但尾部长 10 分钟以上
```

**真实量级**：无退避的立即重试下，一次 15% 错误率的抖动，会把 100% 的流量放大成 130%；错误率 30% 时放大成 160%。**更危险的是重试暴风雪**：下游越慢 → 超时越多 → 重试越多 → 下游更慢，这就是事故里"扩到 6 台反而更糟"的机制（也更像"自我 DDoS"而非容量不足）。

**判定口径**：
- 重试必须由**客户端**发起，且带**退避 + 抖动**（`base × 2^attempt + rand(0, base)`）
- 重试次数上限 2，且**只有幂等接口允许重试**（→ `eng/1`）
- 服务端要有**重试预算**：网关限流值 = 峰值 QPS × 1.2，而不是 × 1.5——多留的余量会被重试吃光

### 因子二：扇出放大 F

```
F = 一次入口请求的同步下游调用数（相同下游重复调用要按次数计）
下游总 QPS = 入口 QPS × F
```

**真实量级**：聚合类接口（首页、详情页、列表页）F = 8~30 很常见；本篇算例 F = 5，已被放大到 20,790 QPS。**这里最容易犯的错是"按最外层 QPS 给下游定容量"**——下游的容量必须按 `入口 × F` 算，且每个下游的 F 不同（画像被调 1 次、商品被批量调 1 次但扫 20 行，二者不是一个量级）。

**F 的正确记法**：不要画"1 个请求 → 5 个服务"，要画"**1 个请求 → 5 个服务 → 7 次实际 RPC / 23 行 DB 行扫描**"。RPC 数和行扫描数才是资源。

**串行 vs 并行**：F 个串行调用的 P99 = Σ P99 之和；并行调用 = max(P99)，但**并发数 = F × L**（线程或连接池按这个算）。所以 F 既放大了下游 QPS，也放大了本地的在飞数——两处都要乘。

### 因子三：未命中放大 M

```
M = 1 / (1 − h)      h = 峰值时段的缓存命中率
例：h = 0.95 → M = 20；h = 0.90 → M = 10；h = 0.85 → M = 6.7
回源 QPS = 入口 QPS（或下游调用 QPS） × M
```

**真实量级**：命中率从 99% 掉到 95%，回源涨 **5 倍**；从 95% 掉到 85%，回源涨 **3 倍**（20 → 6.7 的倒数是 3）。这就是为什么"缓存命中率跌 5 个百分点"必须进告警（→ §01.10），也是为什么 §01.8 会证明**缓存收益是阶跃的，不是线性的**。

**三个必算的命中率**：
1. **稳态命中率**（日常）：决定常规容量
2. **冷启动命中率**（发布后 / 大促首分钟）：通常比稳态低 10~20 个百分点，决定预热策略
3. **雪崩命中率**（缓存集群故障 / 大批 key 同时过期）：接近 0，决定**降级与限流**，而不是容量

> 三个因子必须**连乘**，而不是取最大：`实际下游承压 = 均值 QPS × K × R × F`，`回源 = 均值 QPS × K × R × Σ(下游未命中率)`。本例中 `K×R×F = 15×1.26×5 ≈ 95`，把 220 放大到 20,790；若下游命中率同时滑到 85%（M=6.7），回源会到 **13.9 万 QPS**——而评审时每个人脑子里都还是 220。

Go 侧把三个因子做成一个可执行的 CLI 计算器（骨架，可直接进 CI）：

```go
package capacity

import "math"

// Constraints 是约束卡的可计算形态：进代码的是数字，不是形容词
type Constraints struct {
	DAU        float64 // 日活
	ReqPerUser float64 // 人均日请求
	PeakFactor float64 // K=峰值5分钟均值/日均
	RetryRate, RetryTimes float64 // 错误率 e / 每次失败的平均重试次数 n
	Fanout     float64 // 一次入口请求的同步下游调用数 F
	HitRate    float64 // 峰值时段命中率 h（最坏值，不取日均）
	QPSPerInst float64 // 单实例安全 QPS（拐点实测 ×0.75）
	LossBudget int     // 容灾实例数
}

type Plan struct {
	AvgQPS, PeakQPS, EntryQPS, DownstreamQPS, OriginQPS float64
	Inflight, Instances                                 float64
	Warnings                                            []string
}
func (c Constraints) Compute(p99Seconds float64) Plan {
	avg := c.DAU * c.ReqPerUser / 86400
	peak := avg * c.PeakFactor
	entry := peak * (1 + c.RetryRate*c.RetryTimes) // 重试放大 R
	p := Plan{
		AvgQPS: avg, PeakQPS: peak, EntryQPS: entry,
		DownstreamQPS: entry * c.Fanout,                 // 扇出放大 F
		OriginQPS:     entry * c.Fanout / (1 - c.HitRate), // 未命中放大 M
		Inflight:      entry * p99Seconds,
	}
	p.Instances = math.Ceil(p.EntryQPS / c.QPSPerInst) + float64(c.LossBudget)
	if c.PeakFactor < 2 {
		p.Warnings = append(p.Warnings, "K<2：确认是否真的没有峰值，还是取错了时间段")
	}
	if c.HitRate < 0.9 {
		p.Warnings = append(p.Warnings, "命中率<90%：回源放大>10倍，DB 容量按 OriginQPS 校验")
	}
	return p
}
```

`Warnings` 是这篇代码存在的理由：**计算器的价值不是给出答案，而是拦住"K=1""命中率 99.9%"这类没有实测依据的输入**。

## 01.5 存储估算：行宽、索引 1.6、TTL 与五年总量

存储估算的失败率比 QPS 估算更高，因为它**不报错**：少算 3 倍，会在第 14 个月的一个凌晨以"磁盘 100%、所有写入失败"的形式还给你。详细的行宽算法、binlog/备份账、分区与归档实现在 `eng/40` §40.2–§40.4，本节只给**架构决策需要的四个数**。

**四个数，按顺序算，不能跳**：

| # | 数 | 公式 | 影响什么架构决策 |
| --- | --- | --- | --- |
| 1 | 单行实际占用 | `(列宽和 + 18B 行头) / 0.7 页填充率` | 是否要拆大字段、是否要归档 |
| 2 | 索引开销倍数 | `1 + Σ(二级索引行宽) / 数据行宽`，经验 **×1.4 ~ ×2.0**，本篇取 **×1.6** | 加一个索引 ≈ 加 0.1~0.3 倍存储 + 拖慢写入 |
| 3 | 副本倍数 | 主 1 + 从 n | SLA 要求几个 9；跨 AZ/跨城再 × |
| 4 | 5 年总量 | `日增 × 365 × 5 × (1 + 增长) × 副本 + 日志 + 备份` | 单表是否越过 50 GB 换挡线（→ §01.10） |

**算例（券领取记录表 `coupon_user`）**：

```
行宽   coupon_id 8 + user_id 8 + status 1 + 领取时间 DATETIME(3) 7
       + 使用时间 DATETIME(3) 7 + order_id 8 + channel 1 + 备注等 10 = 50B
       + 行头 18B = 68B ÷ 0.7 填充率 = 97B ≈ 100B

索引   PK(coupon_id, user_id) 聚簇，不额外算
       idx_user_time(user_id 8 + 领取时间 7 + PK 16) = 31B/行
       idx_status_time(status 1 + 领取时间 7 + PK 16) = 24B/行
       ⇒ 数据+索引 = 100B × 1.6 ≈ 160B/行（与经验倍数一致）

日增   100 万领券/天 × 160B = 160 MB/天 → 4.8 GB/月
副本   主 1 + 从 1 = ×2 → 9.6 GB/月
5 年   160 MB × 365 × 5 × 2 副本 = 584 GB      （假设日增不变）
       若日增年涨 22%（第 5 年 2.70 倍），累计倍数 = (1.22⁵−1)/(0.22×5) ≈ 1.55
       ⇒ 584 × 1.55 ≈ 904 GB ≈ 0.9 TB
```

**TTL 与归档要分三档写进约束卡**，不是一句"过期删除"：

| 档 | 数据 | 保留期 | 手段 | 决策依据 |
| --- | --- | --- | --- | --- |
| 热 | 近 30 天领券记录 | 30 天 | 主库 | 客服与"我的券"高频点查 |
| 温 | 30~180 天 | 180 天 | 分区表 / 归档表 | 财务对账窗口（→ `eng/14`） |
| 冷 | 180 天~5 年 | 5 年 | 对象存储（Parquet，压缩 0.3） | 合规留痕，只能查不能改 |

**"曝光/点击明细"绝不能进主库**：日 1,900 万 × 80B = 1.5 GB/天，90 天 = 137 GB，且它的访问模式是扫描聚合而非点查——它属于分析面（→ [11 数据闭环](11-data-loop.md)、`eng/40` §40.4 手段三）。**把明细放主库，等于用 OLTP 的机器做 OLAP 的活，两件事都做不好。**

> **存储估算最常见的三个漏项**：① 只算数据不算索引（×1.6 常被漏，列越窄倍数越高）；② 只算主库不算副本与备份（×2~×3.3）；③ 只算现在不算五年（×3~×5）。三个一漏，报出来的预算就是真实需求的 **1/10**。

## 01.6 延迟预算：预算表、超时级联与"先砍谁"

延迟预算是约束卡里唯一**必须自上而下分配**的字段：端到端 P99 是合同/体验决定的硬数，然后往下切成每个环节的配额。切错了，每个环节都"达标"，端到端必然超标。

**券会场列表接口的预算表**（端到端 P99 目标 300 ms）：

| 环节 | P99 配额 | 超时设置 | 串联 / 并行 | 超预算时的可降级性 |
| --- | --- | --- | --- | --- |
| 终端 → 网关（4G） | 60 ms | — | 串联 | 不可控（要算进预算，别当它不存在） |
| 网关：鉴权 + 路由 | 10 ms | 30 ms | 串联 | ❌ 不可降（安全） |
| 服务自身：反序列化 + 组装 | 25 ms | 100 ms | 串联 | ⚠️ 有限（压缩/裁剪字段） |
| Redis 券池（一次 MGET） | 15 ms | 40 ms | 串联 | ⚠️ 有限（本地 LRU 兜底） |
| 券库存校验 | 50 ms | 60 ms | 并行分支 A | ⚠️ 最后才砍（→ 见下） |
| 用户画像 | 60 ms | 80 ms | 并行分支 B | ✅ 可降级（离线画像兜底） |
| 商品信息 | 45 ms | 60 ms | 并行分支 C | ❌ 不可降（缺了页面不成立） |
| 推荐位 | 120 ms | 150 ms | 并行分支 D | ✅ 首选降级（返回空列表） |
| **端到端** | **60+10+25+15+max(50,60,45,120)=230 → 目标 300（留 70 ms 抖动/重试）** | **800 ms 硬超时** | — | — |

**超时预算级联的两条铁律**（违反任何一条都会引发雪崩，而不是超时）：

```
铁律一  父超时 ≥ Σ(子超时) + 自身固定开销
        反例：父 300ms，子各 300ms × 5 → 父先放弃，5 个子还在跑，
              父的线程释放了但下游连接全占着 → 重试 + 下游堆积 → 雪崩

铁律二  子超时 = 父剩余预算 × 0.7（30% 留给退避重试与网络抖动）
        例：父 800ms，已花 60ms → 剩余 740 × 0.7 = 518ms 分给所有子（并行取 max）

第三件必须做的事：超时值 × QPS = 在飞请求上限
        4,158 QPS × 0.8s 硬超时 = 3,326 个在飞请求
        ⇒ 线程池 200（Tomcat 默认）在 0.01 秒内就被打满
        ⇒ 所以超时必须 ≤ 300ms：4,158 × 0.3 = 1,247，才落在可配的池子范围内
```

最后一行是本篇最容易被忽视的算术：**超时值是容量参数，不是健壮性参数**。上面事故里客户端 `3s 超时` 配 4,158 QPS，理论在飞 12,474 —— 任何线程池都会瞬间打满，此时"加机器"只会增加抢连接的进程（这就是 §01.1 表里 20:03 那一行的机制）。

**预算超支时先砍谁（按顺序，不许跳）**：

| 顺序 | 砍谁 | 手段 | 省下 | 代价（必须明说） |
| --- | --- | --- | --- | --- |
| 1 | 推荐位 | 返回空列表 / 缓存兜底内容 | 120 ms | 转化率 −1~2%，可接受 |
| 2 | 用户画像 | 用离线画像（T−1） | 60 ms | 新用户画像不准，客诉低 |
| 3 | 券库存的"实时精确校验" | 本地阈值预扣 + 异步扣减 | 50 ms | **可能超发 0.3%**，必须有幂等 + 对账兜底（→ `eng/1`、`eng/14`） |
| 4 | 服务自身序列化 | 字段裁剪 + gzip | 10~15 ms | 前端要改，跨团队 |
| — | **永不砍** | 鉴权、商品信息、"售罄硬拦截" | — | 砍了不是变慢，是资金损失与安全漏洞 |

> 排序原则只有一条：**先砍"降级后错误在业务上不可见"的部分，最后砍"降级后错误会变成账差"的部分**。第 3 项之所以排在最后且必须配兜底，就是因为它会把延迟问题转换成一致性问题——延迟是体验，账差是法律。

## 01.7 读写比决定形态：一张必须背下来的表

读写比是约束卡里唯一一个**直接指定存储与缓存形态**的字段。原因很简单：读和写的优化手段完全不通用，读写比告诉你把预算花在哪一边。

| 读写比 | 典型系统 | 存储形态 | 缓存形态 | 一致性策略 | 主要失效点 |
| --- | --- | --- | --- | --- | --- |
| **< 10**（写多或读写均衡） | 订单、账务、库存扣减 | 单库 + 本地事务；分库要极谨慎 | **基本不加缓存**（写穿透成本 > 收益）；只做只读副本 | 强一致，事务守护不变量 | 锁竞争、长事务；加缓存反而引入脏读 |
| **10 ~ 100** | 商品、用户、会员 | 单库 + 读写分离 | 旁路缓存（Cache-Aside），TTL 兜底 | 读从库允许秒级延迟；**读己之写要粘主或写后回填** | 复制延迟导致"刚改看不到" |
| **100 ~ 1000** | 券、短链、配置查询 | 按查询条件分片（分片键 = 点查条件） | 多级缓存（本地 LRU + Redis）+ **版本化 key** | 最终一致；失效靠"换指针"而非 purge | 热点 key、缓存穿透、失效传播 |
| **> 1000** | 内容分发、静态投影、榜单 | 只读投影 / KV / 边缘存储（CQRS） | 边缘缓存 + CDN + 主动 purge 能力 | 最终一致 + 短 TTL 兜底；**必须能秒级撤销** | 边缘缓存顽固、回滚失效（→ [12 短链 · §12.7](12-shortlink-system-design.md)） |

**这张表的三个读法**：

1. **读写比升高时，缓存不是"可选优化"，是"存储形态的一部分"**。到了 >1000，主库已经不再是读路径的一部分，它退化成"写与回源的源"——这时候把它当读库用就是架构错位。
2. **读写比降低到 <10 时，缓存从资产变负债**。写多读少时，每次写都要失效缓存，命中率低、一致性复杂，收益接近 0。
3. **读写比决定"哪一边允许贵"**。→ [12 短链系统](12-shortlink-system-design.md) 的读写比是 2000:1，所以它的写路径可以走审批、走强一致、走三次校验——因为写 QPS 只有 58，付得起任何代价。反过来，18:1 的券会场里，给"领券"加 200 ms 的强一致校验是可接受的，但给"券列表"加 5 ms 的额外调用就要重算容量。

**读写比与扇出的交叉陷阱**：一个接口整体读写比 18:1，但其中**写请求的扇出是 3，读请求扇出是 5**。按整体比值定缓存策略会算错两边的预算。**正确做法是按"每类请求"分别算读写比与扇出**，再求和——这也是为什么 §01.3 的公式表里第 5 行要写"扇出只算同步调用、按下游计次"。

## 01.8 成本反推决策：这一层缓存到底该不该加

成本不是"算完容量后乘单价"，它是**一个可以用来做技术决策的工具**。给定每百万请求成本，很多争论会瞬间结束。

```
每百万请求成本  C = 月总成本 / (月请求量 / 1e6)
月总成本        = N × 单机月费 + 中间件月费 + 存储月费 + 带宽月费
月请求量        = 日请求 × 30
```

**核心判据（加任何一层缓存/索引/副本前先跑一遍）**：

```
判据：ΔC_节省 > ΔC_自身 + ΔC_风险

ΔC_节省 = (N_加前 − N_加后) × 单机/中间件月费      ← 用【峰值】算 N，不用月总量
ΔC_自身 = 新增层的月费（实例 + 运维人力折算）
ΔC_风险 = 一致性错误率的期望损失（脏读导致的客诉/赔付/对账人力）
```

**算例：该不该加 Redis（本篇算例的真实决策）**

设：券会场入口峰值 4,158 QPS，其中需要读券池的请求 4,158（每个请求都读），DB 单实例在 P99<20 ms 下的点查安全 QPS = 2,500，DB 规格 8C32G 主从月费 1,800 元/实例，Redis 4G 主从月费 800 元。

| 方案 | 峰值回源 QPS | DB 实例数 | DB 月费 | Redis 月费 | 合计 | 结论 |
| --- | --- | --- | --- | --- | --- | --- |
| A 无缓存 | 4,158 | ceil(4,158/2,500)=2 主 + 2 从 | 7,200 | 0 | **7,200** | 便宜？看下面 |
| B 加 Redis（h=92%） | 4,158 × 0.08 = 333 | ceil(333/2,500)=1 主 + 1 从 | 3,600 | 800 | **4,400** | ✅ 净省 2,800/月 |
| C 加 Redis（h=99.9%） | 4 | 1 主 1 从（不能更少） | 3,600 | 800 | 4,400 | ❌ 多花的功夫 0 收益 |

**三行算完，三个结论**：

1. **B 值得做**：省 2,800 元/月 = 3.36 万/年，代价是引入一致性复杂度（必须配版本化 key 或短 TTL，→ [04 读路径形态](04-read-path-and-cache-shape.md)）。**判据成立的前提是"用峰值算实例数"**——如果按日均 220 QPS 算，两种方案都是 1 主 1 从，加 Redis 就是纯花钱，这也是很多团队"加了缓存没省钱"的真实原因。
2. **C 不值**：命中率从 92% 提到 99.9%，回源从 333 降到 4，但 **DB 实例数不变**，所以收益为 0。**缓存收益是阶跃函数，越过阶跃点之后所有努力都是零**。
3. **跃迁阈值可以算出来**：要让 DB 从 2 主 2 从降到 1 主 1 从，需要 `4,158 × (1−h) ≤ 2,500 × 1`，即 `h ≥ 40%`。**命中率 40% 与 92% 的架构成本完全相同**——所以"命中率 92% 还不够，要做到 99%"这个要求，本质是没有算过跃迁点。

**再算一个"弹性 vs 常驻"**（K=15 但峰值只持续 1 小时）：常驻 16 台 × 480 = 7,680 元/月；常驻 4 台 + 峰值弹性 12 台 × 1 小时/天 × 30 天 × 0.9 元/机时 = 1,920 + 324 = 2,244 元/月，**省 71%**。前提三条必须同时成立，否则不能省：① 冷启动 < 90 秒；② 有预热脚本（缓存预热 + JIT 预热）；③ 有降级兜底（弹性来不及时先限流而不是崩）。

> **每百万请求成本的作用是横向比较，不是竖向炫耀**。本篇算例 23.6 元/百万请求；同一家公司的短链跳转是 0.4 元/百万（读写比 2000:1，靠边缘缓存）；大文件下载是 60~200 元/百万（带宽驱动）。**三个数量级的差异不是"优化水平"，是形态决定的**——所以拿"我们每百万请求只要 0.5 元"去要求一个带宽型接口，是无意义的指标竞赛。

## 01.9 四个反模式：它们都不报错，只在峰值还账

| # | 反模式 | 现场长什么样 | 错在哪（数学） | 正确做法 |
| --- | --- | --- | --- | --- |
| 1 | **用均值代替峰值** | "日均 220 QPS，加 30% 余量，2 台够" | 漏 ×K（本算例 K=15），容量差一个数量级 | 峰值系数必须实测（12 个月最大值），且记录"峰值持续时长" |
| 2 | **只算 QPS，不算连接数与带宽** | QPS 达标、CPU 30%，但 P99 8 秒、`Too many connections` 每秒 1,400 次 | 容量的单位是**在飞数** `L=λ×W` 与**比特**，不是 QPS | 三件一起算：`在飞 = QPS×P99`、`连接 = 实例×池`（全集群 ≤ DB 上限 ×0.7）、`带宽 = 字节×QPS×8×2`（→ `eng/22`） |
| 3 | **忽略写放大** | "一次下单就写一行"，实际主库 + 2 从 + binlog + 4 个二级索引 + ES + 数仓 | 1 次逻辑写 ≈ **9~12 次物理写**；索引越多倍数越高，批量更新更甚 | 写容量按"逻辑写 × 写放大"算；每个二级索引都要问"它服务于哪个查询"（→ `eng/40` §40.7） |
| 4 | **忽略 GC 与连接数上限** | 压测到 800 QPS 很稳，生产 700 就抖；`jstat` 显示 Full GC 1.2 次/分钟；`max_connections=800` 而副本×池=1,200 | 分配速率 = `QPS × 单请求分配字节`；连接总数 = `副本数 × 池大小`，两者都是**乘法**，扩容会让它们一起爆 | 分配速率 > 300 MB/s 必须换 ZGC/G1 调参或减少对象；容量模型进 CI：`副本 × 池 ≤ max_connections × 0.7`（→ `eng/22` §22.4） |

**写放大的具体算法**（很多人只会说"注意写放大"，不会算）：

```
单次逻辑写入的物理写次数 ≈ (1 主 + n 从) × (1 聚簇 + k 二级索引) + binlog + 下游投影
本篇算例：n=1, k=2  ⇒ (1+1)×(1+2) = 6 次 + binlog 1 + ES 投影 1 = 8 次
写 QPS 100 万/天 = 11.6 QPS → 物理写 93 次/秒（无所谓）
若某活动批量改 500 万行：500万 × 8 = 4,000 万次物理写 —— 这才是要命的，必须拆批 ≤5,000/批
```

**第 4 项的两个乘法必须写进容量模型代码里**，因为它们的错误方向是"机器越加越糟"：加副本让连接数线性上升，加实例让 GC 内存总量线性上升，而瓶颈往往就在这两个池子上，不在 CPU。

## 01.10 换挡信号：水位线定在哪里，为什么是这条线

约束卡的最后一行是**换挡线**：不是"量大了再说"，而是"某个具体指标越过某个具体数值时必须换形态"。这张表是评审现场可直接勾选的 checklist。

```
 使用率
 100% ┤                              ╔══ 断崖：拒绝连接 / 写入失败（不可恢复）
  90% ┤                          ╔═══╝
  80% ┤                    ╔═════╝      连接数红线：新连接直接拒绝
  75% ┤              ╔═════╝            实载率红线：P99 开始非线性
  60% ┤        ╔═════╝                  CPU 红线：P99 劣化的起点
   0% └────────┴──────────────────────────────────▶ 时间
        ↑ 每条线的位置都不是拍的：它标在"哪个指标开始让 P99 变坏"的那个点
```

| 指标 | 水位线 | 为什么是这条线（不是 80%/90%） | 越过后的动作 |
| --- | --- | --- | --- |
| **CPU** | **60%** | 60% 之后排队开始显现、P99 出现第一个拐点；80% 时 P99 通常已劣化 2~3 倍，此时"加机器"已经晚了 | 加副本 / 加缓存层 / 砍扇出 |
| **单机实载率**（峰值 QPS / 单机安全 QPS） | **75%** | 留 25% 给抖动与容灾实例退出；>75% 就在拐点上运行 | 加实例，且先算连接数（→ `eng/22`） |
| **DB 连接数** | **max_connections × 80%** | 100% 时新连接被直接拒绝且**不会自愈**；80% 时还有回旋余量 | 收池 / 加代理 / 网关限流 |
| **复制延迟** | **1 s** | >1 s 时"刚写看不见"的时间窗超过用户刷新周期，客诉开始出现 | 读走主库 / 拆热点 / 降批量写 |
| **单表容量** | **50 GB** | B+ 树由 3 层变 4 层，且备份/DDL 窗口开始不可接受 | 分区 / 分片（→ [03 存储与索引的形态决策树](03-storage-and-index-shape.md)） |
| **缓存命中率** | **低于基线 5 个百分点** | 95%→90% 回源翻倍（M: 20→10），是**乘法式恶化**，不是线性 | 查热点 key / 大 key / 批量过期时间 |
| **出口带宽** | **70%** | 70% 后 TCP 重传上升，P99 抖动先于吞吐见顶出现 | 压缩 / 边缘下沉 / 改协议 |
| **峰值时长** | **峰值 < 2 小时/天** | 常驻成本 > 弹性成本 + 冷启动风险时（→ §01.8 算例省 71%） | 弹性伸缩 + 预热 + 降级兜底 |
| **每百万请求成本** | **月增 > 15% 而流量月增 < 15%** | 成本增速超过流量增速，说明有层在低效堆钱 | 回到 §01.8 逐层算跃迁阈值 |

**换挡信号的两个使用纪律**：

1. **一条线只触发一个动作**。若一个水位线对应三个可能的动作，说明形态还没想清楚——例如"CPU 60%" 只对应"加实例或加缓存层"二选一，选哪个由读写比决定（→ §01.7）。
2. **水位线必须与现实一致，不能只写在文档里**。做法：把 §01.2 的 `ConstraintCard` 与 §01.4 的 `Compute()` 接进监控，每天定时用**当天的实测 K、h、F** 重算一次，算出来的实例数低于当前实例数的 70% 就打告警——**这条告警的含义是"你的约束卡过期了"**，它比任何单个指标告警都更早发现问题。

## 01.11 十分钟答题卡

被要求「现场估一下这个系统的容量」时，按这个顺序讲，不要从"我用 Redis"开始，也不要从"我们大概有十万 QPS"开始：

```
1  问七个字段   读写比 / K / 增长 / P99 / 一致性 / 成本上限 / SLA
                —— 缺哪个就当场问，问不到就明说"这一项我按 X 假设，误差 ±2 倍"

2  算日请求     DAU × 人均次数 × (1+机器流量)         → 1,900 万/天
3  算均值       日请求 / 86,400                        → 220 QPS

4  三个乘号     峰值 K × 重试 R × 扇出 F
                → 220 × 15 = 3,300；× 1.26 = 4,158；× 5 = 20,790
                —— 每一个都说出"数据来源"，没有来源就标明是假设

5  算回源       M = 1/(1−h)，h 取峰值时段最坏值
                → 4,158 × 0.28 = 1,164（滑档到 85% 命中率时 2,495）

6  算资源       实例 = 峰值/(单机安全QPS × 0.75) + 容灾
                在飞 L = QPS × P99；连接 = 实例 × 池 ≤ DB 上限 ×0.7
                带宽 = 字节 × QPS × 8 × 2

7  算钱         月成本 → 每百万请求成本 → 与"该不该加这层缓存"的判据
                → 13,480 元/月 ÷ 570 百万 = 23.6 元/百万请求

8  定预算       P99 300 ms 自上而下切；子超时 = 父剩余 × 0.7；
                超时值 × QPS = 在飞上限（这条最先炸）

9  定形态       读写比 18:1 → 单库 + 读写分离 + 旁路缓存（不是分片，也不是边缘）
                —— 形态是推导的输出，不是偏好

10 定换挡线     CPU 60% / 连接 80% / 复制延迟 1s / 单表 50GB / 命中率 −5pt
                —— 每条线对应一个动作，否则这条线不算定完
```

**三句收尾话术**（评审时最能体现你想透了）：

- 「这七个字段里有 2 个我没拿到实测值，我按 X 假设，所以结论的误差是 ±2 倍——这个误差是可接受的，因为它不改变形态选择。」
- 「这里最脆弱的不是 QPS，是**超时值乘 QPS 的在飞数**：800 ms 超时配 4,158 QPS 就是 3,300 个在飞请求，任何线程池都会瞬间打满。」
- 「如果预算砍一半，我只保留三样：**旁路缓存 + 峰值弹性 + 硬限流**；砍掉多级缓存、推荐位、实时画像。」
