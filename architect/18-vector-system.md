## 18.1 引子：三个「指标正常、体验崩了」的故障

### 事故一：500 万向量还在做暴力扫描（2025-04，内容社区「相似推荐」）

团队用 `faiss.IndexFlatIP` 起步——这是最正确的起步方式，recall 恰好等于 1.0，没有任何近似。三个月后内容库涨到 512 万条，相似推荐接口的 P99 从 180 ms 变成 1.18 s。

| 时间 | 事件 | 数据 |
| --- | --- | --- |
| 04-02 10:00 | 向量量到 512 万，详情页「相似内容」模块 P99 = 1.18 s | 5.12e6 × 1536 维 |
| 04-02 14:00 | 第一反应「加机器」：从 4 台扩到 12 台 | QPS 只涨了 2.9 倍，P99 到 420 ms |
| 04-02 18:00 | 内存账单超预算 3.1 倍，但仍未达 SLA（目标 100 ms） | 每台都装全量 30 GB |
| 04-03 09:00 | 确认物理下界：单查必须扫完 30.7 GB，与代码无关 | 见下方推导 |
| 04-03 ~ 04-18 | 改 HNSW（M=32, efSearch=128），recall@10 从 1.00 落到 0.968 | P99 = 4.6 ms |
| 04-18 | 上线，机器从 12 台降到 4 台，内存从 360 GB 降到 26 GB | — |

延迟下界必须自己算一遍，否则复盘的结论会停在「加机器」：

```
单查必须读的字节 = N × d × 4 B = 5.12e6 × 1536 × 4 = 31.5 GB
内存带宽有效值 ≈ 26 GB/s（多核 + SIMD 实测，不是标称峰值）
单查下界 ≈ 31.5 / 26 ≈ 1.21 s     ← 这就是那 1.2 s，不是"没优化"
加机器的本质：每台仍要装 31.5 GB 全量索引，只能线性稀释 QPS，
              内存成本 ×N，而 recall 一点也没变
```

**根因不是"用了暴力检索"——512 万这个量级用 Flat 是对的。根因是没人给它设换挡点**：Flat 的适用上限是「单查延迟 = N×d×4/带宽」,到了 50 万条、P99 就摸到 100 ms 了。这个阈值是可算的，本可以提前一个季度报警。

### 事故二：索引重建把服务停了 4 小时（2025-08）

embedding 模型从 v2 换到 v3（维度 768 → 1024）。团队的计划是「凌晨低峰重建，6 小时窗口够了」。

| 时间 | 事件 | 数据 |
| --- | --- | --- |
| 08-14 00:30 | 停写，启动全量重建：拉权威源 42 min + 重算 embedding 38 min + 建图 | 5,000 万条 |
| 08-14 03:50 | 建图跑到 78%，节点 OOM 重启（新旧索引两份常驻内存） | 需 1.3 TB，只有 800 GB |
| 08-14 04:20 | 第二次尝试，因「先删旧集合释放内存」导致**没有回滚点** | 旧索引已删 |
| 08-14 04:25 | 相似推荐全站降级为「按类目热门」，人工兜底 6 名运营 | 20 万次/小时降级 |
| 08-14 08:40 | 重建完成，灰度切流 | 停服 4 小时 10 分 |
| 08-14 ~ 08-22 | 补做分片滚动重建：一次只重建 1/16 分片，任何分片可回滚 | 窗口降到 22 min/分片 |

```
重建时间 = 拉数据 + 重算 embedding + 建图 + 校验
        = 42 min + 38 min + 4.1 h + 20 min ≈ 5.9 h    （预算窗口 4 h）
双份索引内存 = 2 × 640 GB = 1.28 TB > 集群 800 GB
⇒ 唯一出路：分片级滚动重建（单元 = 分片，不是集群）
```

**一个容量决策（能不能同时放下两份索引）直接决定了「可回滚」是否存在。** 这和 [12 短链 · §12.7](12-shortlink-system-design.md) 里「301 把可回滚废掉」是同一类错误：不是性能问题，是**把单向门当成了双向门**。

### 事故三：加了租户过滤，recall 从 0.92 掉到 0.31（2025-11）

多租户上线，要求「只在当前租户的素材里做语义检索」。实现是 top-100 检索 + 应用层按 `tenant_id` 过滤：

| 时间 | 事件 | 数据 |
| --- | --- | --- |
| 11-06 | 上线 post-filter，最大的 3 个租户体验正常 | 大租户占库容 >10% |
| 11-09 | 客服收到「我有素材但搜不出来」工单 89 张，集中在小租户 | 小租户占库容 0.8% |
| 11-10 | 复现：top-100 × 0.8% = 期望 0.8 条合格结果 | recall@10 = 0.31 |
| 11-11 | 改成 pre-filter（位图），延迟从 8 ms 涨到 210 ms，recall 只回到 0.55 | 图在 0.8% 子集上断裂 |
| 11-12 ~ 11-20 | 改成按租户分区索引，recall 0.95、P99 9 ms | 分区键 = 过滤里必带的字段 |

三起事故分别对应 **形态选错（索引结构）× 变更失控（重建）× 过滤错位（混合检索）**——正好是本篇的三条主线。

## 18.2 一句话定位与唯一真问题

**定位**：向量系统是「给定一个查询向量，返回库里最像它的 k 条」的**近似排序服务**。它是一个把内存换成延迟的排序器，不是数据库。

先钉死三个误解：

| 你以为的 | 真相 | 后果 |
| --- | --- | --- |
| 「向量库是能理解语义的数据库」 | 它只做一件事：按距离排序。不理解语义，"语义"在 embedding 模型里，不在索引里 | 把模型问题当索引问题，调三个月 `efSearch` 白干 |
| 「向量库可以当权威源」 | 向量不可读、不可解释、不可审计，重建成本以小时计 | 一次索引损坏 = 一次数据灾难（原文必须在对象存储/KV，→ [03 存储与索引形态](03-storage-and-index-shape.md) 决策树出口） |
| 「向量检索能替代精确检索」 | 型号、订单号、错误码、人名全称的语义召回率往往 <60% | 必须与倒排/前缀索引分层融合（→ [16 高效匹配](16-matching-multi-recall.md)）；本篇只负责语义那一路 |

### 唯一真问题

> **ANN 检索是一场明码标价的交易：你用 recall 买延迟，用内存买 recall。**
> 架构师的工作不是"选个向量库"，而是**把这张价签写清楚**：这笔生意买了多少 recall（0.968 还是 0.85）、付了多少内存（每百万向量 6.4 GB 还是 448 B）、以及在哪些查询分布上交易所会违约（高选择性过滤、墓碑堆积、模型升级、跨分片 fan-out）。

一句话概括这篇与 `llm/20` 的分工：那篇讲「RAG 应用怎么把召回用对」，本篇讲「**召回这件事本身要付多少钱、在哪违约**」。

从这一条矛盾推出的全部设计：

| 交易项 | 你付出 | 你得到 | 违约条件（本篇哪一节） |
| --- | --- | --- | --- |
| 用图近似代替全扫 | recall（0.968 而不是 1.00） | 延迟 ÷250（1.21 s → 4.6 ms） | 过滤选择性 <1%（§18.7） |
| 用内存装索引 | 6.4 GB / 百万向量 / 副本 | 单查 4 ms | 内存预算不够 → 必须量化（§18.12） |
| 用墓碑代替物理删除 | 内存不释放 + recall 缓降 | 图连通性不被破坏 | 墓碑 >30% 必须重建（§18.8） |
| 用聚类分片换扩展性 | 每次查询 1 片（理想）或 N 片（灾难） | 容量线性扩展 | 分片键与查询过滤不一致（§18.9） |
| 用"少返回"代替"放宽过滤" | 用户看到 3 条而不是 10 条 | 永不越权、永不返回垃圾 | 产品不接受空结果（§18.7） |

## 18.3 量级与预算：全部推导一遍

场景：内容社区的「相似内容推荐 + 语义素材搜索」。不许拍脑袋，四次推导，评审时要求对方复述这条链。

### 请求量

```
相似推荐   1,200 万 DAU × 6 次详情页 = 7,200 万次/天
语义搜索   480 万次/天
多路召回   1 次请求 → 3 路（标题/正文/封面图）→ ×3
日 ANN 查询 ≈ (7,200 + 480) 万 × 3 = 2.30 亿次/天
均值 QPS  ≈ 2.30e8 / 86400 ≈ 2,660
峰值 QPS  ×4（晚 8 点 + 内容热点）≈ 1.06 万
```

### 索引量与内存

```
对象数 N    = 1 亿（1,200 万 DAU 的内容库 + 三年沉淀）
维度 d      = 1536，float32
裸向量      = N × d × 4 = 1e8 × 6,144 B = 614 GB
HNSW 图     = N × 8 × M = 1e8 × 256 B   =  25.6 GB（M=32，推导见 §18.6）
索引总量    ≈ 640 GB（×1.10 的对齐/墓碑/ID 映射 → 704 GB）
元数据      1e8 × 400 B = 40 GB      → KV / MySQL 从库，不进向量节点
原文+摘要   1e8 × 8 KB = 800 GB      → 对象存储
```

### 分片、副本与单节点容量

```
单节点可用索引内存 = 96 GB × 0.8 水位 = 76 GB
每分片承载 40 GB → 分片数 = 16（16 也是重建并行度的下界，见 §18.8）
主 16 + 备 16 = 32 节点 × 96 GB = 3,072 GB
成本 = 3,072 GB × 20 元/GB/月 ≈ 6.14 万元/月
每百万向量 ≈ 614 元/月（含副本与水位；单副本裸算 128 元/月）
对照：同量数据放 SSD（0.6 元/GB/月）= 1,843 元/月，差 33 倍
⇒ 这句话要写在预算表第一行：向量系统 = 内存系统
```

### 延迟预算（单次查询 P99 ≤ 20 ms）

| 环节 | P99 预算 | 说明 |
| --- | --- | --- |
| 查询向量编码（过模型） | 6 ms | 独立服务，热点 query 可缓存，命中则 <0.2 ms |
| 网关 + 路由到分片（1~3 片） | 1 ms | 多数请求 1 片（§18.9 分区键选对） |
| 分片内 HNSW 检索（efSearch=128） | 4.6 ms | 主成本，与 N 基本无关（这是买图索引的全部理由） |
| 过滤候选不足的放大重试（约 8% 请求） | +4 ms | §18.7 解法 C，必须封顶 3 轮 |
| 归并 + 截断 top-100 | 1 ms | 多路召回的 RRF 在此层完成（→ [16 高效匹配](16-matching-multi-recall.md)） |
| **端到端 P99** | **15 ms** | 留 5 ms 给下游 rerank |

> **推导方向纪律**（与 [12 短链 · §12.3](12-shortlink-system-design.md) 同一条）：先定 recall 目标 → 再定 `efSearch` → 得到单查延迟 → 除以延迟预算得到**每节点可承载 QPS** → QPS ÷ 载荷 → 定副本数 → 最后才是分片与内存。反过来（先买 32 台机器再想 recall）是本篇最常见的倒置。

## 18.4 向量化的架构约束：只讲影响架构的四条

模型细节归算法同学，架构师必须钉死的是这四条——它们每一条都会变成「不可逆」或「必须全量重建」。

| # | 约束 | 为什么是架构问题 | 架构上必须做的 |
| --- | --- | --- | --- |
| 1 | **维度 d 是物理量** | 内存 ∝ d，d=1536 → 6 KB/向量；改了 d，索引和下游全部作废 | `dim` 写进 collection 元数据并做写入/查询双侧校验；降维（PCA/Matryoshka）只能作为"换索引版本"来做 |
| 2 | **距离度量与归一化必须钉死** | 一侧归一化一侧没归一化 → 内积排序随机化，表现为「某些 query 全错」 | `metric` 与 `normalize=true` 进契约；编码服务返回前校验 `‖v‖≈1`，不符直接拒（§18.7 代码①） |
| 3 | **模型版本 = 索引版本** | v2/v3 向量在同一空间不可比，混用 → 召回塌方（另见 `llm/20 §20.3`） | 索引带 `model_version`，查询按版本路由；升级 = 新集合 + 双写 + 影子比对 + 灰度切流（→ [07 变更治理](07-change-governance.md)） |
| 4 | **向量不是真相源** | 它只存"像不像"，不存任何可读信息；删除与更新在向量库里都是**软删除** | 原文 → 对象存储；元数据 → KV；向量节点只存 `int64 内部 id → 业务 id` 的映射（§18.10） |

### 变更影响半径表：这张表决定"要不要停服"

| 变更类型 | 影响半径 | 必须做什么 | 可回滚 | 窗口量级（1 亿） |
| --- | --- | --- | --- | --- |
| 新对象入库 | 1 个点 | 增量插入（元数据先落库，索引后到） | ✅ | 秒级 |
| 对象内容修改 | 1 个点 | 墓碑 + 插入（§18.8） | ✅ | 秒级 |
| 换 embedding 模型（同维度） | **全量** | 新集合 + 双写 + 影子 + 分片灰度 | ✅（旧集合保留 7 天） | 4~6 h |
| 换维度（768 → 1024） | 全量 + 下游 | 同上，且必须新集合（不能原地扩维） | ✅ | 4~6 h |
| 换 metric（cos → L2） | 全量 | 同上 | ✅ | 4~6 h |
| 新增/删除过滤字段 | **全部 payload 索引** | 重建标量索引；历史数据无法追溯 | ⚠️ | 1~3 h |
| 改 HNSW 的 M | 全量 | 改了要重建，且要改内存预算 | ⚠️ | 4~6 h |

> 关键结论：**跑一次"模型升级"的总机时大概是 7 小时，成本约 1,700 元（GPU 8 卡 × 7 h × 30 元/卡时）——钱不是问题，窗口才是问题。** 所以重建的设计目标从来不是"更快"，而是"**任何时刻都可以停、都可以退**"。

## 18.5 形态一：索引结构五选一（本篇的字典表）

每一行只回答四句话：什么规模下它是唯一正确选择、recall 大概多少、付多少内存、什么时候必须换掉。recall@10 与延迟的量测口径统一为：**d=1536、单查 top-10、32 核单节点、并发 100 的 P99、真值由 Flat 全扫给出。**

| 索引 | 一句话原理 | recall@10 | 单查 P99 | 内存 / 磁盘 | 构建（1 亿） | 增量 | 删除 | 适用规模 | 崩点 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| **Flat（暴力）** | 全量算距离取前 k | **1.000** | 1.2 s @500 万；@1 亿 ≈ 24 s | 6.4 KB /向量 | 0（无索引） | ✅ 追加即可 | ✅ 真删 | ≤ 50 万 | 延迟 = N/带宽，纯物理墙 |
| **IVF-Flat** | k-means 分 `nlist` 个簇，只扫 `nprobe` 个 | 0.90~0.97 | 5~20 ms | 6.4 KB + 簇心 | 40~90 min | ⚠️ 可追加，但分布漂移后需重训 | ⚠️ 同 HNSW | 100 万~2,000 万 | `nprobe` 小则漏，大则退化为 Flat |
| **IVF-PQ** | 簇内 + 乘积量化（子空间码本）压缩 | 0.70~0.90（rerank 后 0.90+） | 2~8 ms | **32~192 B** /向量 | 3~6 h（要训码本） | ⚠️ 追加点会加剧量化误差 | ⚠️ | 1 亿~100 亿 | 召回损失不可解释；距离用 LUT，精度天花板 |
| **HNSW** | 分层可导航小世界图，逐层贪心下降 | **0.95~0.99** | **1~5 ms** | 6.4 KB /向量（图 +10%） | 4~6 h | ✅ 插入友好（近实时） | ⚠️ 只能墓碑 | 100 万~1 亿 | 图连通性依赖；过滤/删除破坏可达性 |
| **LSH** | 多组随机超平面哈希，同桶即候选 | 0.60~0.85 | 2~10 ms | 中（多表） | 20~40 min | ✅ | ✅ | 任意大（但精度差） | 高维下「同桶」几乎不相关；参数难调 |

**读这张表的正确姿势**：不要横着比"谁快"，要**竖着看"崩点"那一列**——那才是评审时真正会用到的一列。三个补充事实：

1. **同一系统里通常同时存在 2~3 种索引**：Flat 作为离线真值（永不删，见 §18.11）；IVF-PQ 做粗筛（1 亿 → 1 万）；HNSW 在候选里做精排。这不矛盾，因为这三种索引的角色不同（真值 / 压缩 / 低延迟）。
2. **HNSW 与 IVF 的分界线不是数据量，是写入模式**：写入频繁（内容平台、素材库）→ HNSW（插入友好）；写入一次读千万次（离线语料）→ IVF-PQ 更省内存。
3. **量化是横切维度，不是第六种索引**：任何索引都能叠 int8/PQ，代价与档位见 §18.12。

```
                         ┌── N ≤ 50 万 ───────────────► Flat（recall=1.0，别过度设计）
                         │
   语义 top-k 查询 ──────┼── 写入频繁 + N ≤ 1 亿 ─────► HNSW (+int8)
                         │
                         ├── 写一次读亿次 + 预算紧 ───► IVF-PQ (+rerank)
                         │
                         └── N ≥ 10 亿 ───────────────► 磁盘型（DiskANN/SPANN）
                                                         = 图 + SSD + 少量内存
   任一分支出现「过滤选择性 <1%」→ 不是换索引，是改分区（§18.7）
```

## 18.6 形态二：HNSW 的三个旋钮与内存估算

### 分层图长什么样

```
Layer 2  (约 1/400 的点)          ●───────────●
                                  │           │
Layer 1  (约 1/40 的点)     ●─────●─────●─────●─────●
                            │     │     │     │     │
Layer 0  (全部点)   ●───●───●──●──●──●───●─●───●───●──●───●
                    ↑ 入口点固定在最顶层
       查询 = 每层"贪心找更近的邻居"下降一层 → 底层用 efSearch 宽度做 best-first → 取 top-k
       直觉：上层是高速公路（跳得远），下层是街道（找得准）；层级越高点越稀
```

### 三个旋钮：性质完全不同，别混着调

| 旋钮 | 默认 | 调大后 | 内存影响 | 延迟影响 | 什么时候调它 |
| --- | --- | --- | --- | --- | --- |
| **M**（每层最大出边） | 16~32 | 图更稠密、远端可达性更好 | **常驻内存 +8 B × M / 向量** | 轻微上升 | 架构旋钮：d ≥ 1024 或高 recall 目标时定 32；**改了要重建 + 改预算** |
| **efConstruction** | 100~200 | 建图质量更好、长尾点更不容易孤岛 | 只占**建图期临时内存**，不进常驻 | 构建时间近似线性上升 | 发布旋钮：只要重建窗口够，就调到 200；它是"一次性的投资" |
| **efSearch** | 64~128 | recall 上升 | **零** | 近似线性上升 | 运行旋钮：**recall 不达标时第一个调它**，可在线、可按请求、可随时回滚 |

> 纪律一句话：**`efSearch` 是运行旋钮，`efConstruction` 是发布旋钮，`M` 是架构旋钮。** 三者混着调的团队，通常会在半年后发现「为了提 recall 把 efSearch 调到 2000，延迟翻 6 倍，而真正的瓶颈其实是过滤」。

### 内存公式与 1 亿向量的实例

```
单向量内存 ≈ 4 × d      向量本体（float32）
           + 8 × M      图层：底层 2M 条边 + 平均上层 M 条边，每条边 4 B 的 int32 邻居 id
总内存     ≈ N × (4d + 8M) × (1 + α)     α = 对齐/槽位/墓碑位/ID 映射开销，取 0.10~0.15

实例：N = 1 亿, d = 1536, M = 32
  向量   = 1e8 × 4 × 1536 = 614.4 GB
  图     = 1e8 × 8 × 32   =  25.6 GB
  ×1.10 → 总计 ≈ 704 GB  ⇒ 16 分片 × 40 GB + 副本（§18.3）
```

### 敏感性表：内存到底被谁吃掉

| d | M | 每向量 | 1 亿总量 | 结论 |
| --- | --- | --- | --- | --- |
| 768 | 16 | 3,072 + 128 = 3.2 KB | 352 GB | 小模型 + 稀疏图，省一半 |
| **1536** | **32** | **6,144 + 256 = 6.4 KB** | **704 GB** | **本篇基线** |
| 1536 | 64 | 6,144 + 512 = 6.7 KB | 737 GB | M 翻倍只涨 4.7%，但建图时间翻倍 |
| 1536 | 32 + int8 | 1,536 + 256 = 1.8 KB | 198 GB | **最划算的一刀**（recall −1~2 点） |
| 1536 | 32 + PQ96 | 96 + 256 = 352 B | 39 GB | 省 18 倍，代价见 §18.12 |

**两条硬结论**：① **内存是被维度吃掉的，不是被图吃掉的**——所以省内存的顺序是「先量化 → 再降维 → 最后才动 M」；② 把 M 从 32 调到 16 只省 3.8% 内存，却掉 2~3 个 recall 点，这是本篇性价比最差的操作。

### efSearch 的边际收益曲线（必须自己测出来，别信默认值）

| efSearch | recall@10 | 单查 P99 | 单节点 QPS |
| --- | --- | --- | --- |
| 32 | 0.892 | 1.8 ms | 4,200 |
| 64 | 0.941 | 2.9 ms | 2,800 |
| **128** | **0.968** | **4.6 ms** | **1,750** |
| 256 | 0.984 | 8.1 ms | 980 |
| 512 | 0.993 | 15.4 ms | 510 |
| 1024 | 0.998 | 29.6 ms | 270 |

> 从 128 到 512，付出 3.3 倍延迟只买 2.5 个千分点——**这条曲线的拐点在 64~128**。超过拐点还在加 `efSearch`，说明真正的问题不在索引：要么 embedding 本身不行（→ §18.11 归因），要么过滤吃掉了候选（→ §18.7）。

## 18.7 形态三：过滤 + 向量的混合检索（本篇最贵的一节）

业务现实：**90% 的语义查询自带过滤条件**——租户、类目、语言、时间窗、上下架状态、权限范围。纯向量索引完全不理解这些条件，于是只有两个朴素做法，两个都错。

```
① post-filter（先检索，后过滤）：过滤很凶时，top-k 里几乎没剩的
   Query ──► HNSW（全库）──► Top-100 ──► WHERE tenant=42 AND status=online ──► 3 条
   选择性 s = 0.8% 时：期望命中 = 100 × 0.8% = 0.8 条  ⇒ recall@10 ≈ 0.08~0.31
   ⚠️ 而且不报错：用户只看到"搜不到"，监控上一切正常（引子事故三）

② pre-filter（先过滤，后检索）：图在子集上断裂
   Query ──► 位图(tenant=42) 得 8,000 个 id ──► 图上遍历时 99% 的邻居被丢弃
                                              └─► 连通性断裂，走不远 → 退化为"子集上的半暴力"
   延迟从 4 ms 变 210 ms，recall 从 0.96 掉到 0.55（回退次数暴涨）

③ 正确形态：让过滤成为索引结构的一部分
   ┌─ A 分区索引：分区键 = 过滤里最热、基数最高、且查询必带的那个字段
   │     tenant=42 → 只查 partition_42（一个独立的小 HNSW，图完整、候选充足）
   ├─ B 带过滤的专用索引：标量/payload 索引 + 图遍历时"跳过不合规邻居但仍可绕行"
   │     Qdrant filterable HNSW / Milvus bitset / pgvector iterative_scan
   └─ C 多次召回重试：检索 k → 过滤得 n 条 → n < 目标就把 k ×10 再来，最多 3 轮
         代价：尾部延迟方差大，必须封顶 + 有降级（返回 3 条也比返回 500 好）
```

### 先算账：post-filter 的可用边界

```
要拿到 k 条合格结果，过滤选择性 s，则必须先检索 k' = k / s 条
   s = 50%   → k' = 20    延迟 +40%，可接受
   s = 10%   → k' = 100   延迟 ×3（efSearch 要跟着涨），勉强
   s = 1%    → k' = 1,000  延迟 ×10，且图的 top-1,000 本身召回就在掉
   s = 0.1%  → k' = 10,000 比"直接暴力扫子集"又慢又不准
⇒ 结论：post-filter 的有效边界是 s ≥ 10%；s < 1% 时必须分区
```

### 三种解法对比与判定

| 解法 | 适用选择性 | 延迟 | 内存代价 | 实现成本 | 崩点 |
| --- | --- | --- | --- | --- | --- |
| **A 分区索引** | 单分区 ≥ 10 万点 | 与全局相同（4~6 ms） | 每分区固定开销（图头、簇心），分区数 >1,000 时显著 | 中：分区路由 + 分区生命周期管理 | 分区过多导致小分区图质量差；分区键选错 → 跨分区查询 |
| **B 专用过滤索引** | 10%~50% | +10~30% | payload 标量索引 +5~15% | 低（多数库已内置） | 选择性 <1% 时仍退化为 ② 的行为 |
| **C 多次召回重试** | 任意，但 s <1% 时轮次爆炸 | 方差大（P99 可达均值的 4 倍） | 0 | 极低（客户端就能做） | 无上限时会打出雪崩（§18.15） |
| ❌ 暴力 + 过滤 | < 10 万点 | 线性 | 6.4 KB/向量 | 0 | 量一涨就崩（引子事故一） |

**判定表（按选择性与规模两个维度）**：

| 过滤选择性 \ 分区规模 | < 10 万点 | 10 万 ~ 1,000 万 | > 1,000 万 |
| --- | --- | --- | --- |
| > 50% | 暴力 / Flat | HNSW + post-filter | HNSW + post-filter |
| 10%~50% | B | B（payload 索引下推） | B + C（重试兜底） |
| 1%~10% | B | **A 或 A+B** | **A（按租户/类目分区）** |
| < 1% | B + C | **A（必须分区）** | **A + 分区内二级分区** |

### 一条非性能的红线：post-filter 等于越权

过滤放在应用层的另一个后果不是慢，是**越权**：A 租户的向量被读出、算过距离、进了内存，只是最后被丢弃——审计上这已经是一次数据读取（→ `llm/20 §20.2` 第 5 条）。所以对多租户系统，**post-filter 是架构违规，不是性能选项**：过滤必须下推到位图/payload 索引，由检索线程在遍历时判定。

### 骨架代码一：数据面检索服务（Go）

```go
// 单分片内的 top-k 检索：契约校验 + 过滤下推 + 候选不足放大重试（Go 骨架）
func (s *Shard) Search(ctx context.Context, q []float32, f Filter, k int) ([]Hit, error) {
	if len(q) != s.dim || math.Abs(norm(q)-1) > 1e-3 { // ① 维度与归一化是契约，不是建议
		return nil, ErrVectorContract
	}
	bits := s.exec.FilterBits(f) // ② 过滤以位图下推，绝不在返回后过滤
	hits := make([]Hit, 0, k)
	for mul := 1; mul <= 100; mul *= 10 { // ③ 候选不足最多放大 3 轮
		cand, err := s.hnsw.SearchKnnWithBitset(q, s.efBase*mul, bits)
		if err != nil {
			return nil, err
		}
		hits = hits[:0]
		for _, c := range cand {
			if s.exec.IsDeleted(c.ID) { // ④ 墓碑：图里还在，语义上已死
				continue
			}
			hits = append(hits, Hit{ID: s.exec.BizID(c.ID), Score: c.Dist})
		}
		if len(hits) >= k || !f.Selective() { // 选择性 >10% 时放大无意义
			break
		}
	}
	if len(hits) > k {
		hits = hits[:k]
	}
	if len(hits) < k {
		s.metrics.Inc("candidate_short") // ⑤ 少而准：绝不放宽过滤凑数
	}
	return hits, nil
}
```

## 18.8 形态四：增量更新、删除与全量重建

### 为什么删除只能墓碑

HNSW 的边在缩边时不保证邻居回指（双向但可能半断）。**物理删一个点会让部分点失去唯一通路，图不连通 → 召回变成随机下降**，而且不可复现、不报错。所以所有主流实现都只做软删：置 `delete_bit` + 检索时跳过。

代价必须显式买单：① 内存不释放；② `efSearch` 的候选预算里越来越多是死点（有效宽度变窄）；③ recall 缓慢下滑，且**从指标上看像是"模型变差了"**。

### 为什么更新 = 删 + 插

向量变了，这个点在空间里就换了位置，它在旧位置上的所有边都失效。原地改写 = 图里留一个位置错误的点，它的邻居会持续把查询引向错误区域。所以 `update = tombstone + insert`，并且**必须按 `version` 去重**（同一业务 id 在库里出现两次时，取 version 最大者）。

| 操作 | 物理动作 | 可见性延迟 | 内存 | 必须守住的不变量 |
| --- | --- | --- | --- | --- |
| 新增 | 插入图 | 秒级（取决于缓冲/segment） | +6.4 KB | **元数据先落库、索引后到**；查不到就降级查倒排，不能假装存在 |
| 删除 | 置墓碑 | 立即（检索时跳过） | 不变 | 墓碑**必须**同时写元数据（否则权限兜不住） |
| 修改 | 墓碑 + 插入新点 | 秒级 | +6.4 KB，旧点变墓碑 | 同一 `biz_id` 只返回最高 `version` |
| 换模型 | 新集合全量重建 | 分钟~小时（灰度） | ×2（新旧并存，§18.8 判定） | 双写期间两侧版本号必须一致 |

### 什么时候必须全量重建：判定表

| 信号 | 阈值 | 为什么这个值 | 动作 |
| --- | --- | --- | --- |
| **墓碑占比** | > 30% | 有效点只剩七成，召回与延迟同时劣化；再攒下去纯亏内存 | 重建 |
| **近 30 天变更比例**（删+插 / 总量） | > 20% | 图的"距离结构"已经不代表当前数据分布 | 重建 |
| 模型 / 维度 / metric 变更 | 任何变更 | 空间不可比，混用即塌方 | **必须**全量重建 |
| `efSearch` 已到 512 仍达不到 recall 目标 | — | 图质量坏了，不是参数问题 | 重建 |
| **新点召回明显差于老点**（按入库时间分桶，差 >5 点） | — | 后插入的点连不上 clique，长尾退化 | 重建 |
| 与 Flat 真值抽样差 > 3 点（同一 query 集） | — | 图退化，已可量化 | 重建 |
| 每月固定窗口 | 每月一次 | 让重建成为常态，而不是事故 | 分片滚动重建 |

### 索引重建的时序（本篇第三个必看图）

```
T0  预检：新索引内存 = 旧索引 × 1.15（墓碑 + 施工余量）
    ├─ 能同时放下两份 → 原地并行重建（可回滚）
    └─ 放不下        → 只能分片滚动（一次 1/16），否则没有回滚点（引子事故二）
    │
T1  建空集合 index_v3 + 挂双写：写入同时进 v2(旧) 与 v3(新)，查询仍只读 v2
    │
T2  回填历史：按 id 游标扫权威源（KV/对象存储）→ 批量 embedding → 写 v3
    │  可断点续传；每 100 万条校验 COUNT + 抽样 1,000 条比对向量 hash
    │
T3  影子比对：1% 线上 query 双查 v2/v3，看 top-10 重合率（≥85%）+ golden set 的 recall
    │  ⚠️ 重合率低不等于错：新模型本来就会改排序，判据只能是"标注 recall + 业务指标"
    │
T4  分片灰度切读：路由表把 shard 0-1 指向 v3 → 观察 P99 / recall / 空结果率 → 全量
    │  铁律：切读单元 = 分片；绝不允许同一租户一半查 v2 一半查 v3（会看到"结果来回跳"）
    │
T5  切写 → 观察 7 天 → 卸载 v2（保留快照 7 天）
       回滚 = 路由表指回 v2 + 反向双写补齐 T4~T5 期间的差异
```

| 阶段 | 1 亿向量下的耗时 | 并行度 | 失败恢复 | 可回滚 |
| --- | --- | --- | --- | --- |
| T1 双写 | 即时生效 | — | 关开关（v3 整体作废） | ✅ |
| T2 回填 | 3.5~4.5 h（embedding 0.7 h + 写入 3 h） | 16 分片并行 | 断点续传，从游标重来 | ✅ |
| T3 影子 | 24 h 观察 | — | 关影子开关 | ✅ |
| T4 切读 | 3 天（每批 4 分片） | 按分片 | 改路由表 | ✅ |
| T5 切写/卸载 | 7 天观察 | — | ⚠️ 只剩快照（恢复小时级） | ⚠️ |

### 骨架代码二：控制面索引导出与重建编排（Java / Spring）

```java
@Service
public class IndexRebuildService {
    /** 导出：打成可 mmap 的快照。冷启动加载比重建快 30~50 倍，这是唯一能快速扩缩容的手段 */
    public Snapshot export(String indexId, Path dst) throws IOException {
        IndexMeta meta = metaRepo.get(indexId);                 // 含 modelVersion / dim / metric
        try (SnapshotWriter w = SnapshotWriter.mmap(dst, meta.vectorBytes())) {
            store.scanByCursor(indexId, 500_000, batch -> {      // 主键游标分批，禁 LIMIT offset
                for (VectorRow r : batch) {
                    w.writeVector(r.internalId(), r.float32());
                    w.writeGraphNode(r.internalId(), graph.edgesOf(r.internalId()));
                }
            });
        }
        audit.record("index.export", indexId, meta.modelVersion(), dst.toString());
        return Snapshot.of(dst, meta);
    }

    /** 重建编排：先算容量与窗口。放不下两份就只能分片滚动——容量决定可回滚性 */
    public RebuildPlan plan(String indexId, long totalVectors, int dim) {
        long bytes = totalVectors * (4L * dim + 8L * 32) * 11 / 10;  // §18.6 内存公式
        if (bytes * 2 > capacity.freeBytes()) {                     // 新旧并存放不下
            int shards = capacity.requiredShards(bytes);            // → 分片滚动，逐片可回滚
            return RebuildPlan.rolling(shards, Duration.ofMinutes(30));
        }
        return RebuildPlan.parallel(Duration.ofHours(6));            // → 并行重建，整体可回滚
    }
}
```

## 18.9 形态五：多租户与分片

### 先回答那个反直觉的问题：向量能不能按 ID hash 分片，仍然保证全局 top-k？

**不能——因为 top-k 是「全局有序」谓词，而不是「每片各自 top-k 的并集」。** 哈希把 id 均匀打散，与距离完全无关：任意一片的 top-k 都只是全局 top-k 的一个随机子集，所以你**必须 fan-out 全部分片再归并**。这与 [03 存储与索引形态 · §03.7](03-storage-and-index-shape.md) 里「分片键 = 查询条件」是同一条定律的两个投影：

```
按 ID hash 分片 + 全局 top-k 需要的代价
  每片都要处理【全量查询】：全局 1.06 万 QPS ⇒ 每片都扛 1.06 万 QPS
  总计算量 = 16 片 × 全量          （不是 1/16，是 ×16）
  延迟 = max(各片 P99) + 归并      （并行不降低 P99，只降低均值）
  内存 = 不变（数据没复制），但每片都要为"全量 QPS"配 CPU 与副本
  ⇒ 成本 ×16，延迟无改善，recall 无改善 —— 这是最典型的"分片反模式"
```

边界：只有当"分片数 ≤ 3 且单查极便宜（<2 ms）"时，fan-out 才是可接受的工程妥协。超过 3 片必须换分片维度。

**正确的分片维度只有两类**：

| 分片依据 | 条件 | 效果 | 代价 |
| --- | --- | --- | --- |
| **过滤维度**（租户 / 类目 / 语言 / 业务线） | 查询必带该条件（覆盖率 >90%） | 每次查询只打 1~3 片，延迟与单片相同 | 跨维度查询要 fan-out（少而贵，需限流） |
| **向量空间聚类**（IVF 的 coarse centroid 落到片上） | 查询无业务分区键（如"全网相似"） | 每查只扫最近的几个簇 → 但仍需全片搜索 | 分布漂移后要重训；扩缩容要搬簇 |

### 多租户三方案：隔离 vs 内存放大

| 方案 | 隔离级别 | 内存放大 | 长尾租户 | 大租户 | 重建影响面 | 判定 |
| --- | --- | --- | --- | --- | --- | --- |
| **每租户独立集合/索引** | 物理级 | 高：每集合有固定开销（图头、簇心、段元数据），1 万租户 × 40 MB = 400 GB 空转 | 严重：小租户的固定开销吃掉 8 倍于数据的空间 | 好：可单独扩容、单独重建 | 只影响自身 | 只用于 <50 租户或强合规分离 |
| **共享索引 + 过滤下推（payload 分区）** | 逻辑级 | 低（无浪费） | 无 | 混住：大租户的点占据邻居，小租户要靠"跳过 + 绕行" | 影响全体 | ✅ 默认：租户数 >100 且单租户 <10% |
| **混合：Top N 独立 + 长尾共享** | 两级 | 中 | 无 | 好 | 大租户独立重建 | ✅ 成熟形态（Top 10 独立，其余共享） |

**副本的真正用途**：不是扩读（读靠分片就够了），而是**在滚动重建、快照加载、节点替换时不掉容量**。所以副本数应该由「重建期间的最小容量」倒推，而不是由 QPS 倒推——这是向量系统与普通 KV 在容量规划上最大的差异。

## 18.10 存储布局：向量与元数据必须分离

### 五类数据，五个落点

| 数据 | 1 亿下的体量 | 落点 | 访问模式 | 为什么不能混在一起 |
| --- | --- | --- | --- | --- |
| 向量 + 图 | 704 GB | 向量节点内存（常驻/mmap） | 每查必读 | 放磁盘 = 每次查询在数百 GB 里随机摸，延迟 ×100 |
| 内部 id ↔ 业务 id 映射 | 1e8 × 16 B = 1.6 GB | 向量节点内存 | 每查必读 | 存字符串 id 会让每向量多 16~40 B（内存 +25%），用 int64 一次间接寻址换回来 |
| **下推的过滤字段**（租户/类目/状态） | 1e8 × 8 B = 0.8 GB（位图/标量索引） | **向量节点**（与索引同生共死） | 每查必读 | 跨网络下推 = 4 ms → 40 ms；**它必须和索引一个生命周期** |
| 元数据（标题/作者/时间/权限/状态） | 40 GB | KV（Redis/RocksDB）或 MySQL 从库 | 过滤后可回查 | 放向量节点 = 每次重建都要搬业务库 |
| 原文/摘要/图片 | 800 GB | 对象存储 | 只对 top-10 取 | 向量系统永不返回正文 |

> 一条纪律：**「下推的字段」和索引同生共死，「回查的字段」允许迟到。** 混淆这两者，一次重建就会被拖进整个业务库，窗口从 4 小时变成 40 小时（→ [20 海量数据迁移与拆分](20-data-migration.md)）。

### 持久化：存快照，不存插入日志

要持久化的不是"我插过哪些点"的操作日志，而是**当前图的二进制快照**（向量块 + 邻居表 + 层级 + 墓碑位图 + 版本元数据）。理由：恢复的目标是"立刻可服务"，而按日志重放等于重建一遍图。

```
1 亿向量冷启动加载时间（NVMe，顺序读）
  顺序读带宽：单盘 3.2 GB/s，8 盘并行实测取 8 GB/s
  读 704 GB            ≈ 88 s
  反序列化 + 校验（0.6 s/GB） ≈ 422 s
  ⇒ 整集群并行加载 ≈ 8~12 min（单分片 40 GB ≈ 5~8 min 含校验）
  对照：全量重建（拉数据 + embedding + 建图）≈ 4~6 h
  ⇒ 快照加载比重建快 30~50 倍 —— 这就是"能导出快照"是必需品的原因
```

### 预热三条（不做就等着发布期间 P99 尖刺）

1. **分片级预热，不是集群级**：先加载 Top 5% 高频查询涉及的租户/类目分区，再加载尾部。冷分区可以在第一次访问时懒加载（延迟几百 ms，但只影响长尾）。
2. **先加载后摘流**：readiness 探针必须在索引加载完成、且跑过 100 条 golden query 之后才返回 200；滚动发布保持 N+2 实例冗余（因为一台正在加载时不能承载流量）。
3. **锁内存、避缺页**：常驻内存用 `mlock`/大页；否则首次访问 40 GB 的缺页会打出 200 ms 的 P99 尖刺——这种尖刺在压测里看不到（压测时数据已热），只在发布后出现。

## 18.11 评测：怎么知道你到底买了多少 recall

三件事：造真值、算指标、定位归因。第三件才是线上救命的。

### 造标注集（五步，可执行）

1. **分层抽样 query**：从线上日志按频率分头/腰/尾三层抽 2,000 条（500 / 800 / 700）。**长尾必须超采样**——所有崩塌都发生在长尾，按流量抽样等于自己蒙住眼睛。
2. **用 Flat 造候选池**：每条 query 全扫 top-200。这是「索引无关的真值池」，它自己也可能漏（属于 recall 天花板），但比任何 ANN 都可靠。
3. **分级标注**：2 = 完全满足、1 = 部分满足、0 = 不相关；每条 query 至少标出 10 个 2 级，构成该 query 的真值集。
4. **冻结成 golden set**：带版本号，每季度新增 300 条；双人标注一致性 Kappa > 0.7 才算合格。
5. **记下 Flat 基线**：上线前把 golden set 跑成 Flat 的 recall/nDCG，贴在评审文档首页——**没有基线，"recall 0.96" 这个数字毫无意义**。

### 两个指标，各管一半问题

```
recall@k = |ANN top-k ∩ 真值集| / min(|真值集|, k)        ← 捞得回来吗
nDCG@k   = DCG(ANN 排序) / DCG(理想排序)，DCG = Σ (2^rel_i − 1)/log2(i+1)   ← 排得对吗
```

| 场景 | 主指标 | 为什么 |
| --- | --- | --- |
| 召回层（交 100 条给 rerank） | recall@100 ≥ 0.95 | 后面还有 rerank，排序不重要 |
| 直接展示（相似推荐） | nDCG@10 ≥ 0.75 且 recall@10 ≥ 0.90 | 位置就是价值 |
| 多路召回融合 | 每路单独 recall + 融合后 recall | 单路差而融合好是常态（→ [16 高效匹配](16-matching-multi-recall.md)） |
| **带过滤的检索** | **按选择性分桶的 recall**（<1% / 1~10% / >10%） | 全局均值会把 <1% 桶的崩塌平均掉（引子事故三） |

### 线上「看起来不准」的归因表（本篇最值钱的一张表）

| 症状 | 先查什么 | 若是 → | 若不是 → |
| --- | --- | --- | --- |
| 某些 query 完全搜不到 | 编码服务是否返回 0 向量/未归一化/语言不支持 | embedding 链路 | 索引侧 |
| 全局 recall 掉了 3 点 | **用 golden set 跑一遍 Flat，与 ANN 对比** | Flat 也低 → embedding/切分/模型版本问题 | Flat 高 → 索引参数（`efSearch`/`M`/`nprobe`）或图退化 |
| 只有小租户不准 | 按租户选择性分桶算 recall | <1% 桶崩 → 过滤方案错（§18.7） | 分区路由错 |
| 新入库的搜不到 | 双写是否成功 / 可见性缓冲 / 是否只写了元数据 | 写入链路 | 索引段延迟 |
| 已下架的还搜得到 | 墓碑是否落地、检索是否跳过 `delete_bit` | 删除链路（合规事故，最高优先级） | — |
| 结果新旧版本混杂 | `model_version` 是否混用在同一集合 | 编码侧版本路由 | 重建不完整 |
| recall 正常但用户说"不准" | 真值集里"相关"的定义（是否缺了"当前有效"维度） | 重造评测集（→ `llm/20 §20.1`） | rerank/排序层 |

> **唯一不可省的工具**：任何一个 badcase，先用 Flat 在同一批数据上重算一遍。它能一刀把「算法/数据问题」和「索引问题」劈成两半——没有它，所有调参都是盲的。

## 18.12 成本：内存是绝对瓶颈

### 每百万向量每月成本（算式 + 三个代入）

```
每百万向量每月成本
 = 1e6 × (4d + 8M) × (1+α) × 副本数 / 水位 ÷ 1e9   [GB]
   × 内存单价（元/GB/月）

代入 d=1536, M=32, α=0.10, 副本 2, 水位 0.8, 单价 20 元/GB/月：
   裸向量      = 1e6 × 6,400 B = 6.4 GB
   ×1.10       = 7.04 GB
   ×2 副本     = 14.1 GB
   ÷0.8 水位   = 17.6 GB
   ×20 元      = 352 元/月/百万向量
1 亿向量 ⇒ 3.5 万元/月（含副本与水位；单副本裸算 128 元/月/百万）
同样数据放 SSD ⇒ 1,843 元/月，差 33 倍
```

### 量化档位：用正确率换成本的四档

| 档位 | 每向量 | 1 亿总量 | 相对 float32 | recall@10 | 额外代价 |
| --- | --- | --- | --- | --- | --- |
| float32 | 6,400 B | 704 GB | 1.0× | 0.968（基线） | 无 |
| float16 | 3,200 B | 352 GB | 0.5× | −0.1 点 | CPU 转换开销，需硬件支持 |
| **int8（标量量化）** | 1,792 B | **198 GB** | **0.28×** | **−1~2 点** | 每维存 min/max 缩放系数；量化误差随分布漂移 |
| PQ 96×8 | 352 B | 39 GB | 0.05× | −8~12 点（rerank 后 −2~3） | **必须**保留 float32 在 SSD 上做 rerank；码本训练 1~2 h；距离用 LUT |
| PQ 32×8 | 288 B | 32 GB | 0.045× | −20 点以上（不可用） | 别做 |

### 上 PQ 之前必须把 rerank 的账也算了

```
PQ 省下的内存：704 GB → 39 GB，两个月省 ≈ 3.1 万元
rerank 的代价：top-100 需要读回 float32 原始向量
  2,660 QPS × 100 条 × 6 KB = 1.6 GB/s 磁盘带宽
  ⇒ 5 台 NVMe（0.5 GB/s 有效）承载 640 GB 原始向量
  ⇒ 640 GB × 0.6 元/GB/月 ≈ 384 元/月 + 5 节点 IO 成本
净效果：省 3 万元/月，付 400 元/月 ⇒ 账非常划算，但前提是"必须做 rerank"
```

**三条判断**：① **int8 是白捡的一刀**（省 3.5 倍内存只掉 1~2 点）——任何超过 1,000 万向量的系统都应该先做它，再谈其它优化；② PQ 只在「总量 ≥5 亿且可接受 rerank 链路」时成立，**不做 rerank 直接用 PQ 是把 0.968 变成 0.85，不是省钱是降级产品**；③ 成本优化顺序：int8 → 降维（768 维的小模型）→ 冷热分区（尾部租户用 PQ + rerank）→ 最后才是全量 PQ。

## 18.13 L0 → L5：换挡表与崩法表

### 从 10 万到 100 亿向量的六次换挡

| 阶段 | 规模 | 形态 | recall 档 | 内存 | **换挡信号（硬阈值）** | 代价 |
| --- | --- | --- | --- | --- | --- | --- |
| **L0** | 10 万 | 单进程 Flat + 文件快照（faiss/numpy） | 1.000 | 0.7 GB | 单查 P99 > 30 ms 或 N > 50 万 | — |
| **L1** | 100 万 | 单机 HNSW（pgvector/faiss），与业务同库 | 0.97 | 7 GB | 内存 > 单机 60% / 重建 > 30 min / QPS > 300 | 一致性变弱（索引落库有延迟） |
| **L2** | 1,000 万 | 独立向量服务 + 4 分片 × 2 副本 + int8 | 0.96 | 20 GB/分片 | 过滤查询占比 >30% / 单分片重建 >2 h | 多一套服务与运维 |
| **L3** | **1 亿** | **16 分片 × 2 副本 + 分区索引 + 过滤下推 + int8** | **0.95** | **3 TB（含副本）** | 内存成本超预算 / 墓碑 >30% / 重建窗口 >4 h | 跨分区查询需 fan-out |
| **L4** | 10 亿 | PQ/磁盘型（DiskANN、SPANN）+ rerank 层 + 两级分区 | 0.90（rerank 后 0.93） | 内存 300 GB + SSD 2 TB | 单租户 > 分片容量 / fan-out >3 片 / 重建 >12 h | rerank 链路必须常驻，P99 多 3~5 ms |
| **L5** | 100 亿 | 磁盘型 + 冷热分层（热 5% 内存 / 冷 95% SSD）+ 版本化双索引 + 单元化 | 0.90 | 内存 1/10 + 20 TB SSD | 全量重建不可能 → 只能增量建图 + 分区滚动 | 运维复杂度、跨单元查询 |

**当前系统落在 L3。重点说 L2 → L3 的临界点**：L2 之前，"一个向量服务 + 分片"就能解决全部问题；到 L3 你会发现三件事同时发生——① 过滤条件变成主流（业务开始按租户/类目切）；② 重建窗口超出低峰窗口；③ 内存成本超过业务毛利能承受的量级。此时正确的动作**不是加机器**，而是：**int8 量化（省 3.5 倍）+ 按过滤维度分区（让每次查询只打 1 片）+ 分片滚动重建（让窗口变成 22 分钟）**。

**不要跳级**：没有 Flat 真值集就上 PQ = 你永远不知道自己掉了多少 recall；没有分区键就上多租户 = 引子事故三重演。

### 这个形态特有的崩法

| # | 失效 | 长什么样 | 定位方法 | 预防 |
| --- | --- | --- | --- | --- |
| 1 | 暴力扫顶到带宽墙 | 延迟随 N 线性涨，加机器只是线性稀释 | 算 `N×d×4/带宽` 与实测比 | 设 N/延迟换挡阈值（L0→L1） |
| 2 | `efSearch` 军备竞赛 | 为提 recall 从 128 调到 2000，延迟 ×6、QPS ÷6 | 画 efSearch-recall 曲线，找拐点 | 拐点定死；超出即查 embedding 与过滤 |
| 3 | **post-filter 静默崩塌** | 无报错、监控正常，只是小租户"搜不到" | 按选择性分桶算 recall | 过滤下推到位图/payload（§18.7） |
| 4 | pre-filter 图断裂 | P99 从 4 ms 抖动到 200 ms，空白变多 | 过滤后的候选集大小 vs 命中数 | 分区索引 + 重试封顶 |
| 5 | 墓碑堆积 | 内存不降、recall 缓降，像"模型变差" | 墓碑占比指标（>30% 告警） | 每月分片重建 |
| 6 | 重建双份内存 OOM | 建到 78% 节点重启，且旧索引已删 | 预检 `2×bytes > free`（§18.8 代码） | 分片滚动重建 |
| 7 | 模型版本混索引 | 召回质量塌方式下降，且只在部分数据上 | 扫 `model_version` 分布 | 版本进 collection 元数据 + 查询侧路由 |
| 8 | 冷启动抢 IO | 发布期间 P99 尖刺 10 分钟 | 对比加载期间的磁盘 util 与查询 P99 | N+2 冗余 + 先加载后摘流 + `mlock` |
| 9 | 切读不是分片原子 | 同一租户的结果"来回跳" | 比对同一 query 在 v2/v3 的 top-10 | 切读单元 = 分片（§18.8 T4） |
| 10 | 长尾点退化 | 新入库内容召回明显差于老内容 | 按入库时间分桶算 recall | `efConstruction=200` + 定期重建 |

## 18.14 砍掉 90% 预算还能不能跑

内存从 3,072 GB 砍到 300 GB、集群从 32 节点砍到 3 节点、PQ 与 rerank 全部停用、退回 pgvector 单集群：

| 保留 | 砍掉 | 后果 |
| --- | --- | --- |
| **int8 量化** + 单副本 + 16 分片压到 4 分片 | 双副本、PQ、rerank 层、独立向量集群 | P99 从 15 ms → 35 ms；成本降到 1/9 |
| **Flat 真值集 + 按选择性分桶的 recall 看板** | 影子比对、自动评测流水线 | 调参变慢（人工每周跑一次），但不会瞎 |
| **可导出的索引快照**（能 mmap 加载） | 原地并行重建、双索引并存 | 重建只能分片滚动，窗口 22 min → 70 min |
| **分区索引（按租户）** | payload 专用索引、多路召回 | 跨类目查询退化为"分片 fan-out ≤3"，需限流 |
| 元数据 KV + 原文对象存储 | 独立元数据服务 | 过滤字段回查变慢 1~2 ms |

**结论：这个系统的必需品只有三样**——
① **一份 Flat 真值集**（否则你不知道自己买了多少 recall，一切调参是盲的）；
② **可导出、可回滚的索引快照**（没有它，重建就是单程票，引子事故二重演）；
③ **过滤能下推的分区键**（没有它，90% 的查询从第一步就错了，引子事故三重演）。
其余（多副本、PQ、rerank 层、独立集群、影子比对）全是量级或成本驱动的优化。每次评审都问一遍"哪三个是必需品"，能砍掉一半的架构虚荣。

## 18.15 十分钟答题卡

被要求设计「相似推荐 / 语义搜索 / 图片检索」时，按这个顺序讲，**不要从"我用 Milvus"开始**：

```
0  先反问三句   N 大概率是几千万还是一次性 1 亿？写入是一次性灌入还是每天新增？
                查询里带过滤条件的比例多少、过滤选择性多少？
                延迟预算是多少、recall 目标是多少（谁定的、依据是什么）？
1  算量级       内存 = N × (4d + 8M) × 1.1；1 亿 × 1536 维 ≈ 704 GB → 这就是分片数的来源
                QPS = 日查询/86400 × 峰值系数；每节点 QPS 由 efSearch 决定（128 → 1,750）
2  立真问题     ANN 是用 recall 买延迟、用内存买 recall 的交易 —— 说清买了多少、付了多少
3  选索引       ≤50 万 Flat（recall=1）/ 写入频繁 ≤1 亿 HNSW / 一次写入读亿次 IVF-PQ / ≥10 亿磁盘型
                任何索引先叠 int8（省 3.5 倍，只掉 1~2 点）
4  定旋钮       M 是架构旋钮（改了重建+改预算）、efConstruction 是发布旋钮、efSearch 是运行旋钮
                买 recall 的拐点在 efSearch 64~128，超过就查 embedding 与过滤
5  处理过滤      选择性 <1% 必须分区；1~10% 用 payload 下推 + 重试；>50% 才允许 post-filter
                多租户场景：过滤必须下推，post-filter 等于越权
6  定分片       分片键 = 查询必带的过滤维度（租户/类目），绝不是 id hash（hash 分片 → fan-out ×N）
                副本由"重建期间最小容量"倒推，不由 QPS 倒推
7  定更新       删除只能墓碑、更新=删+插；墓碑 >30% 或月变更 >20% 或模型升级 → 重建
                重建前提：能同时放下两份索引，否则只能分片滚动（这决定可回滚性）
8  定布局       向量+图+下推字段在内存；元数据在 KV；原文在对象存储
                持久化存快照（加载 10 min）而不是日志（重放 5 h）；预热分片级 + 先加载后摘流
9  说评测       golden set（分层抽样 + Flat 造池 + 分级标注）→ recall@k / nDCG@k / 按选择性分桶
                badcase 先用 Flat 重算，一刀劈开"算法问题"与"索引问题"
10 报成本       每百万向量每月 = 1e6×(4d+8M)×1.1×副本/水位/1e9 × 单价 ≈ 352 元（含副本）
                砍 90% 预算时只留三样：Flat 真值集、可回滚快照、过滤分区键
```

现场被追问时最值钱的三句：

- 「**1 亿向量 1536 维就是 704 GB 内存，这不是"选个库"的问题，是"你打算付多少钱买 4 毫秒"的问题。**」
- 「**过滤选择性低于 1% 时，任何 post-filter 方案都在骗自己——它不报错，只是让用户搜不到。**」
- 「**重建的核心指标不是"多快"，而是"能不能同时放下两份索引"——放不下，你就没有回滚点。**」
