# 17. 搜索系统深窥：准实时性与写入吞吐的那笔账

> **状态**：`已完成（初稿）` ｜ **所属**：第三部分 · 案例（族 B·检索） ｜ **编号**：17 / 26
> **本篇定位**：族 B（16–18）三套索引里的「倒排那一套」。16 讲「三套索引怎么分层融合」，18 讲「向量怎么用正确率换延迟」，本篇只讲一件事：**倒排索引这个形态，为什么天然是"近实时"的，以及为什么每个想把它调成"实时"的人最后都在修集群**。它同时是全书唯一一处深入存储引擎内部的篇目——不是因为好奇源码，而是 **segment 的不可变性直接决定了索引能不能更新、mapping 能不能改、重建要不要停机、副本数怎么定**。这四条都是架构边界，不是运维细节。

## 17.1 引子：三起「没人报错」的故障

搜索的事故有个共同特点：**误码率零、错误日志零、面板全绿**。搜索挂了不叫挂，叫"结果不对劲"——而"结果不对劲"没有 SLO。

### 事故一：把 refresh_interval 从 30s 改成 1s（2025-10-14）

某电商商品搜索：4.2 亿文档，6 节点（32C128G + 3.2 TB NVMe），12 主分片 × 1 副本，`refresh_interval: 30s`。运营侧反复投诉「新建的商品要等半分钟才搜得到，大促上新来不及」。

开发看到一个"配置项"叫 `refresh_interval`，语义里写着「数据多久可被搜索」，值改成 `1s`，走配置中心推下去——**6 个索引、72 个主分片，同一秒生效，无灰度**。

| 时间 | 事件 | 段数 / 分片 | 待合并数据 | 磁盘写 util | 搜索 P99 |
| --- | --- | --- | --- | --- | --- |
| 10-14 09:00（改前） | 稳态，merge 跟得上 | 12 | ≈ 0 | 22% | 50 ms |
| 10-14 10:02 | 6 个索引 refresh 30s → 1s | 12 | 0 | 24% | 50 ms |
| 10-14 10:30 | 每分片每秒生成 1 个新段，merge 线程跑满 | 210 | 1.3 TB | 71% | 90 ms |
| 10-14 12:00 | merge 队列积压，段消费速度 < 段产生速度 | 480 | 4.1 TB | 96% | 380 ms |
| 10-14 15:40 | 一次查询要遍历 760 个段；搜索线程池开始排队 | 760 | 6.8 TB | 99% | 620 ms |
| 10-14 16:20 | 大促预热流量翻倍（6 万 QPS），12% 请求 503 | 1,050 | 8.2 TB | 100% | **3,100 ms** |
| 10-14 16:35 | 回滚 `refresh_interval: 30s`，段数停止增长 | 1,050 | 8.2 TB | 100% | 3,000 ms |
| 10-14 ~ 10-17 | merge backlog 消化 63 小时，期间 P99 未回到 200 ms 以下 | 1,050 → 41 | 8.2 TB → 0 | 逐日下降 | 缓慢恢复 |
| 10-17 复盘 | 超时/空结果会话 470 万次，GMV 损失约 1,180 万元 | — | — | — | — |

**回滚只停止了恶化，没有恢复现状。** 因为段是不可变的：已经生成的 1,050 个段必须靠 merge 一个个吃掉，而 merge 是纯 IO 活，8.2 TB 的数据重写量在 96% 利用率的盘上只能排队。**这就是"配置项"三个字最贵的一次教训：`refresh_interval` 不是可见性开关，它是段生产速率的分母。**

三件事同时缺失：**没有把可见性延迟写进接口契约**（谁也没定义"多快可搜"算合格）、**refresh 被当成实时性开关**（而不是按索引类型分级的写入预算）、**变更没有灰度对象**（一次推 72 个主分片，见 [07 变更治理](07-change-governance.md)）。

### 事故二：搜得到，点不开（2025-06，某 SaaS 商品库）

应用层双写：业务事务提交后调 ES `bulk`，超时重试 3 次后放弃并只打一条 warn。删除/下架也是双写。跑了 6 周后抽样比对：

| 差异类型 | 条数 | 占比 | 根因 |
| --- | --- | --- | --- |
| ES 有、DB 无（**幽灵文档**） | 47,200 | 0.41% | DB 事务回滚/删除成功，ES 写入已生效且无反向补偿 |
| DB 有、ES 无（**缺失文档**） | 21,500 | 0.19% | bulk 超时被放弃；发布期间一段代码路径漏写 |
| 值不一致（价格/状态） | 8,900 | 0.08% | 两线程并发写同一 `_id`，后到的旧值覆盖了新值 |
| **合计差异** | 77,600 | **0.68%** | 搜索点击后 404 率 4.1%，客诉"搜到点不开" |

0.68% 听起来很小。但搜索的点击只有 2.3% 转化，落在差异文档上的点击**必然**是坏体验——分母不在这里，在"点击"那里，放大 40 倍。

### 事故三：动态 mapping 爆掉整个集群（2025-09）

多租户商品库，租户自定义属性以 JSON 直传，索引模板 `dynamic: true`（默认值）。某租户把 SKU 编码写成了属性名（`{"a1b2c3": "红色"}`），48 小时内字段名从 300 涨到 3.2 万，两周后到 11 万。

| 时刻 | 字段数 | cluster state 更新耗时 | 后果 |
| --- | --- | --- | --- |
| 09-02 | 312 | 40 ms | 正常 |
| 09-16 | 3.2 万 | 1.8 s | master CPU 常驻 60%，写入偶发 429 |
| 09-29 | 11 万 | 8.4 s | master CPU 100%，全集群写入被拒 22 分钟 |
| 09-29 复盘 | — | — | 只能新建索引重建；`dynamic: strict` 上线 |

三次事故分别对应本篇三大节：**可见性与段（§17.3）**、**派生索引的一致性与对账（§17.6–17.7）**、**mapping 与容量（§17.5、§17.12）**。

## 17.2 一句话定位与唯一真问题

**定位**：搜索系统 = 「权威源 → **可重建的派生索引**」+ 一个把「匹配 + 排序」做成服务的查询层。它有三个"不是"：不是主库、不是事务系统、不是实时系统（是**近**实时）。

### 唯一真问题

> **索引的「准实时性」与「写入吞吐」天生矛盾，而段合并（merge）是这个矛盾的代价所在。**
> 因为段不可变：**每一次让新数据"立刻可见"，都必须新开一个段**；段越多，merge 越重；而 merge 的账单最终以**磁盘 IO 和查询延迟**的形式，由读路径和下一次写入偿还。
> 不懂这一点的人会把 `refresh` 调成 1s，然后看着集群炸（§17.1 事故一）——他优化的是一个自己没算过的成本项。

一条更锋利的表述：**可见性延迟 ≈ `refresh_interval`，而段生成速率 = 1 / `refresh_interval`。两个数是倒数关系，所以"可见性"与"段成本"永远不可能同时变好。** 这不是调参问题，是这个形态的定义。

这一个矛盾推出全部设计：

| 从矛盾推出的约束 | 推出的设计 |
| --- | --- |
| 可见性是**写入预算**，不是"实时性开关" | `refresh_interval` 按索引类型分级：写入密集 30s、会话类 1s、批量导入 `-1` |
| 业务真正要的是"我自己刚写的能立刻看到" | **写后读回源权威源**（或按 `_id` 精确查），代价 1 次点查，而不是让全库 1s 可见 |
| 段不可变 → 更新 = 重建倒排，删除 = 标记 | 设计上避开"高频更新同一文档"（计数、库存水位**不要放 ES**） |
| 删除只有在 merge 时才物理释放 | 删除比例 > 30% 的索引要**重建**，而不是持续 update 后等 merge |
| mapping 字段类型不可变 | **索引必须可重建** → 别名 + 重建流水线是基础设施，不是运维脚本（§17.11） |
| 可见性有延迟，必然存在"库里有、ES 没有" | 写路径必须有补偿（CDC/Outbox）+ 对账节奏（§17.7、`eng/14`） |

| 七问 | 落在哪节 | 一句话答案 |
| --- | --- | --- |

## 17.3 内核形态如何决定架构边界

ES 的写入不是"改文件"，是"生产新文件"。四个动作构成了全部因果关系，其余一切都是推论。

| 动作 | 触发条件 | 它做了什么 | 代价（必须显式买单） | 它决定的架构边界 |
| --- | --- | --- | --- | --- |
| **写入缓冲 + translog** | 每次 bulk | 进内存 buffer，同时顺序追加 translog（默认 5s 刷盘） | 暂不可搜；translog 未刷盘时机器挂会丢这几秒 | **RPO 不由 ES 保证**，只由副本数 + translog 刷盘频率决定 |
| **refresh** | 默认 1s / 按索引配置 | 把 buffer 变成一个**新 segment** 并打开供搜索 | 每次 refresh = 1 个段；段数 = 写入时长 ÷ interval | **可见性 SLA 与写入吞吐的上限只能二选一**（按索引分级） |
| **flush** | translog 512 MB 或 30 min | 段落盘 fsync + 写 commit point + 清 translog | 一次周期性大 IO | 持久化边界；恢复时只能从 commit point 重放 |
| **merge** | 后台，段数/删除比例触发 | 把 N 个小段合并成 1 个大段，**物理删除 tombstone** | 写放大 3~10×；与查询争磁盘 IO | **磁盘带宽预算**；也决定"更新型"负载能不能放进来 |
| （force merge） | 手动，仅只读索引 | 合并到 1 段 | 一次性重写全索引 | 历史索引归档形态（→ 可搜索快照） |

**图 1 · segment 生命周期（不可变性如何变成一条成本链）**

```
bulk 写请求
   │
   ▼
┌────────────────────┐    refresh（默认 1s / 写入密集可设 30s）
│  内存 buffer        │ ──────────────────────────────► ┌──────────────────┐
│  + translog        │      每次 refresh = 新建 1 个段    │  segment N       │ ← 可被搜索
└────────┬───────────┘                                 │  不可变 · 只读    │   （可见性在这一刻产生）
         │                                             └────────┬─────────┘
         │ flush：translog 512MB / 30min                          │
         │ （段落盘 fsync + 写 commit point + 清空 translog）      │ merge（后台，段数/删除比例触发）
         ▼                                                       ▼
┌────────────────────┐                                 ┌──────────────────┐
│ 磁盘 segment 持久化 │                                 │  segment M       │  1 个大段
└────────────────────┘                                 │  旧段引用归零后删除 │
                                                       └──────────────────┘
删除 / 更新：旧 doc 只被标 _deleted
   ├─ 更新 = 标记旧 doc 删除 + 写一条新 doc（倒排整套重建）
   ├─ 被标记的 doc 仍占磁盘、仍被查询遍历（只是过滤掉）
   └─ **只有 merge 才真正物理释放**  ← 所以"频繁 update"是双重成本：写放大 + 段碎片
```

### 「写入到可搜」的延迟链

```
t0  客户端组批（0 ~ 200 ms，取决于 bulk 攒批策略）
t1  写线程池排队（队列满则 429；看到 es_rejected_execution 说明在 t1 就卡了）
t2  主分片写入 buffer + translog（1 ~ 5 ms）
t3  同步复制到 1 副本（1 ~ 10 ms；副本 ack 后才算写成功）
t4  等下一次 refresh（0 ~ interval，均值 interval/2）
t5  段打开供搜索（50 ~ 200 ms，与段大小相关）
t6  搜索请求路由到某副本 → 命中（1 ~ 3 ms）
                                            ┌ 默认 1s：可见延迟 P50 ≈ 0.55 s，P99 ≈ 1.3 s
总可见延迟 ≈ t0 + t1 + t4 + t5  ────────────┤ 30s：     P50 ≈ 15 s，  P99 ≈ 31 s
                                            └ 而段生成速率 = 1/interval：1s → 86400 段/天/分片
```

**看到这条链就该明白两件事**：①要"立刻可搜"，唯一零成本的做法是**读回权威源**，而不是压 `refresh`；②写入吞吐的天花板不在 ES 的写线程池，而在**盘能不能消化 merge**。

### 边界：ES 能做什么、不能做什么

| 需求 | ES 能不能 | 该走哪 |
| --- | --- | --- |
| 按 `_id` 点查 | 能，但**不能当主库** | 权威源 / KV（→ [04 读路径形态](04-read-path-and-cache-shape.md)） |
| 全文相关排序 | 能，这是它的存在理由 | ES |
| 多维筛选 + 排序取 top-k | 能（`filter` + `search_after`） | ES |
| 任意深度聚合报表 | 勉强，会打满查询线程池 | ClickHouse（→ [21 埋点管道与数据湖](21-telemetry-pipeline.md)） |
| 业务判定（下架、库存、权限） | **不能** | 权威源 + 查询后二次校验 |
| 同一请求内"写后立刻读" | **不能**（除非 `refresh=wait_for`，代价是每次写多等一个 refresh） | 读权威源 |
| 深分页逐页遍历到底 | **不能**（`from+size` 上限 10,000） | `search_after` / 离线导出 |
| 唯一约束、跨文档事务 | **不能** | 关系型（→ [02 领域建模](02-domain-modeling.md)） |

## 17.4 量级与预算：从文档数算到 merge 带宽

不许拍脑袋。这条推导链评审时要能复述（目标量级：ToC 商品/内容搜索，10 亿级文档，落在 §17.13 的 L4）：

```
文档数          100 亿（5 年累计，日增 5,000 万，其中 40% 是更新）
单文档          _source 均值 800 B（JSON）+ 倒排/doc_values ≈ ×1.1 → 880 B
索引总量        100 亿 × 880 B ≈ 8.8 TB（不含副本）
副本            1 副本 → 17.6 TB 磁盘
查询 QPS        峰值 6 万（页面 82%、联想 12%、运营后台 6%）
写入 TPS        均值 8,000；峰值 3 万（商品变更 + 状态同步，其中 40% 是 update）
写入字节        3 万 × 800 B = 24 MB/s
merge 写放大    稳态 3~5×（更新越多、refresh 越频繁越高）取 4
磁盘写带宽需求  24 MB/s × 4（merge）× 2（副本）= 192 MB/s   ← 这才是真正的 IO 预算
```

**注意最后一行**：业务方看到的是「24 MB/s 写入」，磁盘看到的是「192 MB/s」，两者差 8 倍。事故一的 96% util 就是这 8 倍造成的——**估算写入容量时忘掉 merge 与副本，是这个形态最常见的一次性错误**（与 [01 约束卡与量级估算](01-constraint-card-and-capacity.md) 的三个放大因子同源）。

### 延迟预算（一次搜索请求）

| 环节 | P99 预算 | 说明 |
| --- | --- | --- |
| 接入 + 鉴权 + 参数校验 | 3 ms | 无关 ES |
| Query 解析 → DSL 改写（同义词、类目映射） | 4 ms | 每次多一跳字典，别做同步远程调用 |
| 单分片查询（含遍历 ~300 段） | 20 ms | **段数是这里的乘数**，不是常量 |
| 协调节点 top-k 归并 | 8 ms | 分片越多越大，`size × 分片数` 的内存 |
| 业务重排 / 二次加权 | 5 ms | 从 top-200 里挑，不要重排全量 |
| **端到端 P99（无聚合）** | **120 ms** | 目标 |
| 端到端 P99（带 1 层 terms 聚合） | 300 ms | 聚合单独给预算，且必须限流 |

### 成本

```
热节点   12 节点 ×（32C128G + 3.2 TB NVMe）≈ 12 × 1.15 万 = 13.8 万/月
温节点   3 节点（HDD 大容量，30 天以上数据）       ≈ 1.2 万/月
快照     17.6 TB × 0.12 元/GB/月（对象存储）       ≈ 0.2 万/月
合计     ≈ 15.2 万元/月  →  约 1.5 元/GB/月（这正是 [03] 与 `eng/37 §37.6` 里 ES"热节点 1.5~4 元/GB"的落点）
```

## 17.5 索引与 mapping 设计

### 字段类型：五个判断，选错要重建

| 需求 | 类型 | 代价 | 常见反例 |
| --- | --- | --- | --- |
| 精确匹配 / 过滤 / 排序 / 聚合 | `keyword` | doc_values 占盘，高基数字段最贵 | 用 `text` 做过滤 → 分词后 `"iphone 15"` 匹配不到 `"iPhone15"` 的整值 |
| 全文检索 | `text` + **显式 analyzer** | 无 doc_values，**不能排序不能聚合** | 用 `keyword` 做全文 → 只能全等，形同没做搜索 |
| 既要全文又要精确筛选 | `text` + `.keyword` 子字段（`ignore_above: 256`） | 双份存储（约 +25%） | 不设 `ignore_above` → 长文本进 keyword，doc_values 打爆磁盘 |
| 数值范围 + 排序 | `long` / `double` / `scaled_float` | 数值 doc_values 8 B/值 | 用 `keyword` 存数字 → 字典序 `"10" < "9"`，价格排序全错 |
| 时间 | `date`（`epoch_millis`） | — | 存字符串 → 时区与区间查询不可靠，聚合全废 |
| 不可枚举的多租户属性 | `flattened` | 只能"任意字段包含某值"过滤，**不能算分** | 用 `dynamic: true` 自动建字段 → §17.1 事故三 |

**doc_values 是什么、为什么它在架构里重要**：它是字段值的列式存储（落盘、默认对非 `text` 字段开启），排序与聚合全靠它——所以你**能**对 keyword/numeric 排序聚合，而**不能**对 `text` 做同样的事。硬要做的唯一途径是 `fielddata`（把倒排反转成堆内存），这是 ES 最常见的 OOM 原因之一：一个 `text` 字段的 `terms` 聚合，能在 3 秒内吃掉 20 GB 堆。关掉 doc_values 可省 30% 磁盘，代价是失去排序与聚合能力——**先问业务要不要排序，再决定省不省这笔盘**。

### 一对多：nested vs 宽表 vs join 字段

| 方案 | 语义 | 索引成本 | 查询成本 | 更新成本 | 上限 / 判据 |
| --- | --- | --- | --- | --- | --- |
| **宽表（反范式拍平）** | 一个商品一行，属性拼成 `sku_color: ["红","蓝"]` | 重复存储 × 子项数 | **最低**（一次匹配） | **最低** | 子项 ≤ 几百；**默认首选** |
| **nested** | 每个子对象是独立 Lucene doc | 每个 nested doc 一条倒排，需维护父子块 | nested query 慢 2~5×（要构位图做"同一子对象内"约束） | **改一个子项 = 重写整个父文档** | nested doc / 父文档 ≤ 50；只在"数组内字段必须成组匹配"时用 |
| **join（parent/child）** | 父子同分片，靠 `join` 字段关联 | 中 | join query 慢，且必须 `routing=父 id` | 便宜（子文档独立更新） | 子文档量大且频繁变（评论、库存） |
| **flattened** | 整个 JSON 当一个字段 | 低 | 只能过滤不能算分 | 低 | 属性不可枚举的多租户（事故三的正解） |

**判据一句话**：能用宽表就别 nested——**nested 的代价不在查询，在"更新一个子项要重写整个父文档"**，而这在一个"库存频繁变"的商品上等于把更新成本乘以子项数。真正必须 nested 的场景只有一个：**数组内字段之间存在"同一子对象"约束**（"红色且 XL"不能匹配"红色 S + 蓝色 XL"）。

### 动态 mapping 的四种死法

| 风险 | 可观测症状 | 触发条件 | 防御 |
| --- | --- | --- | --- |
| **mapping 爆炸** | `cluster state` 更新秒级、master CPU 100%、写入被拒 | `dynamic: true` + 用户可控字段名（事故三） | `dynamic: strict` + 显式 mapping + 属性走 `flattened` |
| **类型猜错** | 第一批文档某字段是 `"123"` → `long`；后续 `"12A"` → 整个 bulk 被 400 拒 | 动态类型推断 | 显式 mapping + 采集侧预校验 + 死信队列（§17.6 代码） |
| **模板漂移** | 新索引与老索引 analyzer/字段数不同，同一查询两种结果 | 手建索引 / 无模板 | index template + component template，版本化进 Git（→ [07 变更治理](07-change-governance.md)） |
| **高基数字段进 keyword** | doc_values 磁盘暴涨，聚合变慢 | 把 `trace_id`/URL/时间戳塞 keyword | `ignore_above`、`index: false`、或干脆不进 ES |

**一条纪律**：生产索引**不允许** `dynamic: true`。这条不是洁癖——它是事故三唯一有效的预防，而且成本只是一个 JSON 模板文件。

## 17.6 写入路径三种形态：双写 / CDC / 全量

| 维度 | **应用层双写** | **binlog CDC** | **定时全量** |
| --- | --- | --- | --- |
| 一致性 | **最弱**：任一步失败即分叉，且无反向补偿 | 强：binlog 是"事务提交后的唯一事实"，顺序 = 事务顺序 | 弱但**自愈**：每次都整体重置 |
| 可见延迟 | 秒级（取决于 refresh） | 秒级 ~ 十秒（CDC 链路 + refresh） | 小时 ~ 天 |
| 实现成本 | 低（加一行调用），但**每张表都要加** | 中：Connector + 位点 + schema 演进 + DDL 兼容 | 低（跑任务），但占源库与大集群带宽 |
| 丢数据风险 | **高**：超时放弃、发布期代码路径不一致、删除漏写 | **低**：位点可回退重放 → 只会重复，不会丢 | 0（每次重来），但两次全量之间的变更要靠增量补 |
| 删除 / 下架 | 极易漏（业务代码只写 upsert） | **天然支持**（binlog 有 DELETE） | 需要显式对齐（rebuild 而非 delete_by_query） |
| 幂等要求 | 天然可重复，但仍需 `_id` 稳定 | **必须幂等**（至少一次投递必然重复，`eng/11`） | 天然幂等 |
| 演进成本 | 加表/加字段要改应用代码 | 加表只改 Connector 配置 | 无需改代码 |
| 适合 | ≤ 5 张表、写入 < 100 TPS、业务能接受差异 | **默认推荐**（≥ 10 表 / 有删除 / 要顺序） | 首次灌数 + 日增量对账兜底 |

**结论一句话**：**双写是"把一致性责任分给每一个写业务的开发者"，CDC 是"把一致性责任收回到一条链路"。** 前者在 5 张表时可行，在第 20 张表时必然有人漏写（事故二就是第 9 张表漏了删除），而漏的那张表不会报错——它只会让 0.68% 的搜索结果变成 404。

### 双写为什么会分叉：五个失效窗口

**图 2 · 应用层双写的一致性链路与五个分叉点**

```
应用（业务事务）                MySQL                    Elasticsearch
     │                            │                            │
```

### 骨架代码一 · Java：批量写入的唯一入口（≤ 40 行）

```java
// 纪律：_id 由业务主键派生 → 幂等；refresh 交给索引设置，绝不逐条 refresh=true
@Service
public class ProductIndexWriter {
    private final ElasticsearchClient es;
    private final BulkIngester ingester;   // 攒批：5 MB 或 500 条 或 1s，三者先到者触发

    public void submit(ProductDoc d) {     // 调用方只入本地队列，不参与业务事务，不阻塞
        ingester.add(IndexOperation.of(o -> o.index("products_v2")   // 只认别名/版本化索引
            .id(d.skuId())                                            // ← 幂等键
            .document(d)));
    }

    /** 批量响应必须分类处理：429/503 可重试，4xx（mapping 冲突）不可重试 → 死信 */
    public void onBulkResponse(BulkResponse resp, int attempt) {
        for (BulkResponseItem item : resp.items()) {
            if (item.error() == null) continue;
            int code = item.status();
            if (code == 429 || code == 503) {
                retryQueue.add(item.id(), Backoff.expo(attempt));     // 客户端限流，eng/15
                metrics.inc("es.bulk.retry");
            } else {
                deadLetter.add(item.id(), item.error().reason());     // 写不进去 = 索引设计错了
                metrics.inc("es.bulk.deadletter");                    // 该指标 > 0 立即告警
            }
        }
        if (resp.errors()) metrics.inc("es.bulk.partial_error");       // 部分失败最容易被忽略
    }
}
```

### 骨架代码二 · Java：查询 DSL —— 过滤进 filter，算分只给该算分的（≤ 40 行）

```java
SearchResponse<ProductDoc> search(String q, String tenantId, List<Object> after) {
    Query text = MultiMatchQuery.of(m -> m.query(q)
        .fields("title^3", "brand^2", "desc").type(Type.BestFields))._toQuery();

    Query scope = BoolQuery.of(b -> b
        .must(text)                                                   // 唯一进 query context 的东西
        .filter(TermQuery.of(t -> t.field("tenant_id").value(tenantId))._toQuery(),
                TermQuery.of(t -> t.field("status").value("ON_SALE"))._toQuery())
        .mustNot(ExistsQuery.of(e -> e.field("deleted_at"))._toQuery()) // 墓碑：软删即不可见
    )._toQuery();

    Query scored = FunctionScore.of(f -> f.query(scope)
        .functions(FieldValueFactor.of(v -> v.field("sales_7d").factor(0.4)
                      .modifier(Modifier.Log1p).missing(0))._toFunction(),   // 业务权重
                   GaussDecay.of(g -> g.field("on_shelf_at").origin("now")
                      .scale("30d").decay(0.5)._toFunction())              // 时效衰减
                   .filter(TermQuery.of(t -> t.field("cat_l1").value("NEW"))._toQuery()))
        .scoreMode(Mode.Sum).boostMode(BoostMode.Sum))._toQuery();

    return es.search(s -> s.index("products_search")            // 只认别名，永不写具体版本
        .pit(p -> p.id(pitId).keepAlive(k -> k.time("2m")))     // 快照 → 翻页不漂移
        .size(20)
        .query(scored)
        .sort(o -> o.field(f -> f.field("_score").order(Desc)),
              o -> o.field(f -> f.field("_shard_doc").order(Asc))).  // tie-breaker 必须有
        searchAfter(after), ProductDoc.class);
}
```

## 17.7 一致性对账：怎么发现「库里有、ES 没有」

对账的机制（三层对账、差异分类、分片并行核对 SQL、断点续跑）全部在 `eng/14`，本篇只给三句结论和一个 ES 特有的改造清单：

> **结论 1**：对账的本质是**两个独立记录源的交叉验证**，不是"再查一遍库"——所以两边的取数口径必须独立（一边走权威源直读，一边走 ES 查询），同一个 bug 不能同时污染两边。
> **结论 2**：差异必须**分类处置**（缺失 / 多余 / 值不一致 / 重复），四类的修复动作不同，混在一起就等于"重跑一次全量"。
> **结论 3**：对账的价值不在修，在**趋势**——差异率 0.01% 且平稳是可接受的稳态；从 0.01% 涨到 0.1% 的那一周才是真信号（→ `eng/14 §14.3`）。

### ES 侧必须改造的四个地方

| 与 MySQL 对账的差异 | 改造 |
| --- | --- |
| **没有 join，无法在库内做差集** | 两侧各按 `_id` hash 分 1,024 桶，逐桶比 `count + sum(hash(_id))`；不一致的桶再拉明细 |
| `_count` 与 `_stats.docs.count` 不等 | 用 `_count` 比总数（**只算主分片**）；`docs.count` 含未 merge 的 `_deleted`，不能用作核对基准 |
| 删除在 ES 侧是"文档没了"，无法分辨"从未有过" | 权威源必须有 **墓碑字段** `deleted_at`（软删），否则删除类差异永远无法归因 |
| 更新是整体覆盖，无历史 | 用业务 `update_time` 做水位与比对基准，**别用 `_version`**（两个索引各自计数，无意义） |

### 节奏表（频率由"最坏情况能接受多久不一致"反推）

| 校验 | 频率 | 范围 | 成本 | 能发现 | 发现不了 |
| --- | --- | --- | --- | --- | --- |
| **实时抽样** | 每 5 分钟 | 最近 15 分钟变更的 1,000 条（按主键抽样回查） | 可忽略 | 链路整体断了、字段整体错位 | 零散的个别缺失 |
| **日增量对账** | T+1 | 昨日全量变更（按 `update_time` 分片并行 + 校验和） | ≈ 2 CU·h | 全部缺失/多余/值不一致 | 极低比例（< 0.001%）的静默漂移 |
| **周全量对账** | 每周 | 全量按 `_id` hash 分桶比对 | 8 节点 × 3 h | 历史累积漂移、mapping 变更导致的值截断 | 桶内哈希碰撞抵消（概率极低但存在） |
| **重建演练** | 每季度 | 从权威源重建 `v_next`，与线上抽样比对结果集 | 半天 | **"索引已经不可重建"**（权威源缺字段，最致命） | — |

第四行是很少有人做、但最值钱的一次校验：**你以为 ES 是派生索引，可真到要重建那天才发现权威源里没有某个属性**——那时线上索引就是唯一副本，而它不可修改。

### 修复动作与对账锚点

| 差异类型 | 修复 | 注意 |
| --- | --- | --- |
| 缺失文档 | 按 `_id` 补写（upsert） | 补写用同一份 mapping，否则又造一条差异 |
| 多余文档（幽灵） | 查权威源确认已删 → `delete` | 直接批量删有风险：**先确认权威源，再删 ES** |
| 值不一致 | 以权威源覆盖 | 若覆盖后仍不一致 → mapping 类型截断/分词问题，要改索引 |
| 重复文档 | `_id` 不是业务键导致的，只能重建 | 重建索引时用确定性 `_id` |

**对账锚点必须在建模期埋**（与 `12 短链 · §12.8`、`11 数据闭环 · §11.5` 同一条纪律）：`updated_at`（单调、可索引、可按片并行）、`deleted_at`（墓碑）、以及**重建所需的全部字段都在权威源里**。这三样事后补不回来，只能认损。

## 17.8 查询设计：两个 context、深分页与聚合成本

### query context vs filter context：90% 的条件应该进 filter

| 维度 | **query context**（`must` / `should`） | **filter context**（`filter` / `must_not`） |
| --- | --- | --- |
| 是否算分 | 是（BM25 / 函数打分） | 否 |
| 缓存 | 无 | **有**（bitset 结果缓存，可跨请求复用） |
| 性能 | 慢 3~10×（要遍历 postings 算分） | 快（bitset 直接与运算） |
| 该放什么 | 全文相关、业务加权 | 租户、状态、时间、类目、是否删除 |
| 典型错误 | 把 `status = 'ON_SALE'` 放进 `must` | 把全文匹配放进 `filter`（结果没有相关性，只剩"包含") |

一条可执行的判据：**"这个条件是否会影响文档的排序？"不影响 → 一律 filter。** 一个搜索请求里 `must` 的子句数应该 ≤ 2。事故二之外的另一类事故是：把 12 个筛选条件全塞 `must`，单请求 CPU 涨 6 倍，扩了 4 个节点才发现只需要改一个关键字。

### 深分页：为什么必须 `search_after`

`from + size` 的机制是：**每个分片**都要构造 `from + size` 个候选的优先队列，协调节点再归并。`from=100000, size=20, 5 个分片` → 每片 100,020 个 doc 的堆内存候选 × 5。10 个用户同时翻到第 5,000 页 → 节点 OOM。这就是 `index.max_result_window` 默认 10,000 的来历，它不是随便拍的。

| 方案 | 结果稳定性 | 内存 | 深度上限 | 代价 |
| --- | --- | --- | --- | --- |
| `from + size` | 差：翻页间有新数据会**漂移/重复** | 高（随深度线性） | 10,000 | 越深越慢，禁止用于深翻 |
| `scroll` | 好（快照） | 中 | 无限 | 服务端持有上下文（保底占用堆与段引用），不适合用户交互 |
| **`search_after` + PIT** | 好（PIT 快照） | **低** | 无限 | 必须有**唯一**排序键（末尾加 `_shard_doc` 作 tie-breaker）；PIT 有 TTL |

**一个反直觉的代价**：PIT 会持有段引用，**因此会阻止 merge**。客户端忘了 `close` PIT（或 TTL 设成 1 小时），结果是磁盘不降、merge 不推进、段越来越多——症状和事故一一模一样，但根因完全不同。所以 PIT TTL 一律设短（2 分钟量级），且必须监控 `open_contexts`。

### 聚合的成本：桶数与基数

| 聚合 | 成本量级 | 陷阱 |
| --- | --- | --- |
| 单层 `terms` | O(每分片唯一值) + 协调节点 O(分片数 × size) | `size` 太大 → 协调节点内存按分片数倍增 |
| 多层嵌套 `terms`（类目→品牌→型号） | 桶数 = 各层 `size` 的**乘积** | 3 层 × 100 = 100 万桶 → 堆爆（这就是"深度聚合"） |
| `cardinality` | 每分片 HLL++ 估算，内存 ≈ `precision_threshold × 8 B` | **精度陷阱见下** |
| `date_histogram` 大区间 | 桶数 = 区间 ÷ 间隔 | 5 年按秒聚合 = 1.5 亿桶 |
| `nested` 聚合 | 需遍历 nested doc + 位图 | 比普通聚合慢 3~10× |
| `script` 聚合 | 每 doc 执行脚本 | 禁用或白名单，它是集群级 DoS 入口 |

**`cardinality` 的精度陷阱**（评审里最容易被问倒的一处）：它默认用 HyperLogLog++ **估算**去重数。`precision_threshold` 默认 3,000、最大 40,000：阈值内的基数精确；超过阈值转为估算，相对误差约 1%~3%，而且**多个分片的估算结果合并时误差不会互相抵消**。所以：

- 报"UV 大约 830 万"可以；用来做**对账、计费、KPI 考核**就是事故。
- 需要精确去重 → 用 `composite` 聚合分页枚举后自己算，或把这件事交给 ClickHouse（→ `eng/37 §37.4.5`）。
- 更隐蔽的一种错：`cardinality` 在**低基数长尾**上误差看起来很小，于是团队用它做了"每个租户的 SKU 数"统计，某租户实际 47 个，报表显示 51 个——差 8%，业务侧直接不信整个数据平台了。

铁律：**用户可控的聚合维度必须白名单 + `size` 上限 + 强制超时（`search.default_search_timeout` / `terminate_after`）**。一个开放的自定义聚合后台，等于给每个运营一个把集群打挂的按钮。

## 17.9 相关性调权：BM25 的直觉、三种 boosting、以及怎么证明调对了

### BM25：三句话的直觉，不推公式

$$ \text{score}(q,D) = \sum_{i} \text{IDF}(q_i)\cdot\frac{f(q_i,D)\cdot(k_1+1)}{f(q_i,D)+k_1\left(1-b+b\cdot\frac{|D|}{\text{avgdl}}\right)} $$

只要记住三个直觉，工程师就够用了：

1. **词频会饱和**（$k_1$，默认 1.2）：一个词出现 10 次不比出现 1 次相关 10 倍，边际收益递减——所以堆关键词刷排名是有上限的。
2. **罕见词更值钱**（IDF）：`"iphone"` 在百万文档里几乎不带信息，`"钛金属"` 才有区分度。
3. **长文档要打折**（$b$，默认 0.75）：详情页 5,000 字天然命中更多词，不折扣就会让"长 = 相关"。

**BM25 的边界**：它只衡量"文本相似"，完全不懂业务。销量、库存、毛利、时效、租户等级它一概不知——所以相关性调权这件事，本质上就是**把业务信号注入到一个只懂词频的打分器里**。

### 三种 boosting 手段

| 手段 | 位置 | 实现 | 优点 | 代价 |
| --- | --- | --- | --- | --- |
| **① 查询期字段/词权重** | 查询 DSL | `multi_match` + `fields: ["title^3","brand^2"]`；同义词扩展带 `boost` | 零重建，可随时 A/B | 权重散落在代码里，半年后没人知道为什么是 3 |
| **② 索引期信号字段** | mapping | `rank_feature`（稠密）/ `rank_features`（稀疏）；把销量对数、评分直接落字段 | 打分极快（不用解 postings 再算） | **改字段要重建索引**（这就是 §17.11 存在的理由） |
| **③ 查询期业务注入** | `function_score` | `field_value_factor`（销量/评分）、`gauss`（时间衰减）、`filter`（类目加权）、`script_score` | 灵活，业务指标能直接进排序 | 权重调参依赖评测；`script` 有性能与安全成本 |

**业务权重注入最容易犯的错是量纲**。BM25 分数在 5~40 之间浮动，而 `sales_7d` 可能是 120,000——直接相加的结果就是"BM25 完全消失，排序等于按销量排"。正确做法是**先归一化再加权**，并把这个公式写进文档：

```
final = 1.0 × norm(bm25)                 # min-max 归一化到 [0,1]，按本次结果集
      + 0.4 × log(1 + sales_7d) / log(1 + max_sales_7d)
      + 0.3 × gauss(on_shelf_at, scale=30d, decay=0.5)
      + 0.2 × is_promoted                 # 布尔信号，直接 0/1
```

第四档是**两阶段重排**：ES 只做召回（top-200），排序交给应用层的模型（CTR/CVR 预估），这已经属于 [19 推荐系统的本质](19-recommendation-essence.md) 的漏斗问题——**但边界要清楚**：重排能用的候选数受"召回 top-k 的 k"限制，k 太小则重排无用武之地，k 太大则延迟与带宽爆掉，200 是常见折中。

### 离线评测（NDCG）与线上 A/B

| 要素 | 做法 | 陷阱 |
| --- | --- | --- |
| 标注集 | ≥ 200 个 query × 每个 20 条结果，人工标 `rel ∈ {0,1,2,3}` | 只标头部 query → 长尾改动完全没信号 |
| **NDCG@10** | `DCG = Σ (2^rel − 1) / log₂(i+1)`；`NDCG = DCG / IDCG` | 绝对分数无意义，只比同一 query 集上的相对变化 |
| 分桶看 | 按 query 频次 / 类目 / 意图分桶，不看总分 | 总分 +2% 可能是"头部涨 5%、长尾跌 10%" |
| 护栏指标 | 零结果率、结果集大小、类目熵（多样性）、延迟 | 只盯 NDCG → 优化成"全给爆款"，这是 [11 数据闭环 · §11.9](11-data-loop.md) 的自我强化 |
| 线上 A/B | CTR@10 / CVR / 加购 + **交错实验（interleaving）** | 只看 CTR → 标题党上位；位置偏差必须用交错实验校正（`11 · §11.10`） |

**改一次权重的标准流程（四道闸，一道不过就停）**：离线 NDCG 不降 → 分桶无恶化 → 交错实验胜出（它比 A/B 灵敏 10 倍，样本量小一个量级）→ 5% 流量 A/B 两天，护栏不恶化 → 全量。**跳过前两道直接上线的团队，最后都是靠"感觉搜得不对"回滚的。**

## 17.10 多租户隔离：索引级 / routing 级 / 字段级

| 维度 | **索引级**（一租户一索引） | **routing 级**（共享索引 + `routing=tenant_id`） | **字段级**（共享索引 + `tenant_id` filter） |
| --- | --- | --- | --- |
| 成本 | **高**：每索引至少 1 主分片 × 副本，固定开销（master 元数据 + 每分片数十 MB 堆） | 中 | **最低** |
| 隔离度 | **最强**：可单独限流、单独删除、单独恢复、独立 mapping | 中：同分片内共享 merge 与查询线程 | 弱：一个租户的重聚合能拖慢全体 |
| 查询性能 | 最好（分片最少） | 好（routing 命中单分片，等价点查） | 差（每次都要查所有分片，靠 filter bitset 减损） |
| 扩展上限 | 受**分片数**硬约束：每 GB 堆 ≤ 20 分片 → 1,000 租户 × 2 分片 = 2,000 分片，需要 ≈ 100 GB 堆（4~5 个 32 GB 堆的节点） | 分片数固定、租户数理论无上限，但**大租户变热点分片** | 租户数无上限，受单索引文档数与查询并发约束 |
| 运维 | 索引数 × 备份/ILM/别名对象，必须自动化 | 中 | 低 |
| 单租户迁出 | 容易（整索引迁） | 必须重建 | `delete_by_query` + 重导 |
| 适用 | ≤ 200 租户，或大客户合同要求物理隔离 | 200~5,000 租户，中小租户为主 | > 5,000 租户，或租户数据量差异极大 |

**演进路径是混合，不是三选一**：大租户（Top 1%~5%，通常占 40%+ 数据量）给**独立索引**，长尾租户共享 3~5 个索引并按 `routing` 打散。判据来自分布本身——先按租户聚合文档数与 QPS，画出洛伦兹曲线（方法与 [11 数据闭环 · §11.13 案例 C](11-data-loop.md) 一致），再决定切点。

**两个必踩的坑**：

1. **routing 热点**：`routing=tenant_id` 意味着一个租户的所有文档落在一个分片上。头部租户（占 30% 数据）会把那一个分片打成热点，**routing 隔离把"隔离"和"热点"绑成了同一件事**。解法是大租户升级为独立索引，或对大租户用 `routing = tenant_id + "_" + hash(sku) % 4` 打散（代价：点查要并发 4 次或带上正确后缀）。
2. **字段级隔离其实没有隔离**：`tenant_id` 只是 filter，查询仍然扫全部分片、共享同一查询线程池与 merge 预算。你能做的最多是在应用层做**按租户的并发配额**（→ [24 多租户 SaaS 底座与配额计费](24-multi-tenant-saas.md)、[09 开放平台](09-open-platform.md)），把"吵到别人"的概率降下来——这属于限流问题，不属于隔离问题。

## 17.11 零停机重建：别名、双写、追平、切流、回滚

**为什么"必须能重建"是硬需求**：字段类型不可变（`keyword` 改不成 `text`）、analyzer 改了历史数据不会重算、删除比例高到 merge 追不回空间、集群大版本升级。这四件事每周都在发生，**所以重建不是运维事故的补救措施，是常规操作**——它必须像发版一样有流程。

**图 3 · 零停机重建时序（别名是唯一切流开关）**

```
时间 ─────────────────────────────────────────────────────────────────────────────►
        T0            T1                 T2                    T3          T4     T5
        │             │                  │                     │           │      │
别名  products_search ══════════════════════════(一直指向 v1)══════┌─原子切换─┐
        └──► products_v1  (v1 正常服务读写)                     │   (1 ms)  └──► products_v2
                                │                                │
v2 索引 │ ① 建 v2：显式 mapping   │                                │
        │    别名暂不指向 v2       │                                │
        │    ② 全量 reindex（从权威源，slices=分片数，限速）           │
        │             │           │                                │
        │             └─► ③ 双写开始：应用/CDC 同时写 v1 + v2         │
        │                            │                             │
        │                            └─► ④ 增量追平（watermark=update_time）
        │                                   └─► 抽样 1,000 条逐字段比对
        │                                          差异率 < 0.1% 才允许下一步
流量    100% v1 ══════════════════════════════════════════════════┤ 100% v2
回滚    改回别名指针即可（v1 数据仍在，双写保留 7 天）◄────────────┘（秒级）
```

| 阶段 | 动作 | 可回滚动作 | 验收（不达标不许进下一阶段） | 坑 |
| --- | --- | --- | --- | --- |
| ① 建 v2 | 显式 mapping + 模板；别名**暂不**指向它 | 删索引 | 字段数在上限内、analyzer 与评测集一致 | 用 `dynamic: true` 建 v2 = 事故三重演 |
| ② 全量灌数 | `_reindex`（**从权威源**，不是从 v1）+ `slices=auto` + 限速 | 删 v2 数据重来 | 文档数 / 校验和与权威源一致 | 从 v1 reindex 会把 v1 的 `_deleted` 与旧 mapping 的缺陷一起继承过来 |
| ③ 双写 | 应用双写或 CDC 同时写 v1、v2（`_id` 相同） | 关开关，只写 v1 | v2 的追平 lag < 5 s | 双写期间改 v2 的 mapping = 灾难，必须冻结 |
| ④ 增量追平 + 比对 | 以 `update_time` 水位补差；抽样 1,000 条逐字段比 | 无（修正后重比） | 差异率 < 0.1%，且 P99 延迟不超过 v1 的 1.2 倍 | 用 `_version` 比对无意义（两索引各自计数）→ 用业务字段 |
| ⑤ 切流 | `POST /_aliases`：**同一请求**里 `remove v1 + add v2` | 反向改别名（秒级） | 错误率、延迟、零结果率、CTR 都不恶化 | 只换"读别名"不换"写别名" = 读新写旧；切换后 v1 保留 7 天再删 |

**这一段最该抄走的一句**：切流不是"改代码"，是"改一个指针"，所以回滚成本是 1 秒——**这是 ES 形态最大的运维红利，前提是你从第一天就用别名，并且别名与物理索引名严格分离（代码里出现 `products_v1` 就是架构违规，用 ArchUnit 守住，同 [12 短链 · §12.4](12-shortlink-system-design.md) 的依赖方向纪律）。**

## 17.12 容量规划：分片数、副本、堆与 GC

### 分片数：先算总量，再夹在上下限之间

```
总数据量 D（含索引膨胀，不含副本）       8.8 TB
单分片目标 s ∈ [10, 50] GB
分片数 = clamp( ceil(D / s), 节点数, 堆GB × 20 )
       = clamp( ceil(8800 / 50), 12, 12 × 31 × 20 )
       = ceil(176) → 取 192（= 12 节点 × 16 分片/节点）
副本 1 → 磁盘 17.6 TB
```

**10–50 GB 这条经验是从三件事推出来的，不是抄来的**：

| 约束 | 推导 | 对分片大小的要求 |
| --- | --- | --- |
| **故障恢复时间** | 单节点快照恢复吞吐 ≈ 40~100 MB/s。50 GB ÷ 60 MB/s ≈ 14 分钟/分片；一节点挂掉要分摊恢复 ≈ 2 TB → 40 个分片 × 14 min ≈ 9 小时（超标） | 分片**越大**，单分片恢复越久，越容易破 RTO |
| **merge 峰值临时空间** | 一次 merge 需要额外 `新段大小` 的空闲盘；50 GB 分片的最后一层 merge 需 ≈ 50 GB 空闲 | 分片越大，磁盘低水位要求越高（这就是必须留 15%~25% 的直接原因） |
| **单分片查询是单线程** | 分片越大，一个慢查询能用的核越少（无法跨分片并行化单分片内的遍历） | 分片**过大** → 长尾查询变长 |
| **固定开销下限** | 每分片 ≈ 数十 MB 堆 + 段元数据 + master cluster state 条目 | 分片**过小** → 10 万个 1 GB 分片先把 master 打死 |

**为什么不是"按天分索引"**：搜索是随机访问，按时间分索引等于让每次查询都跨所有索引（除非查询天然带时间窗）。**"按天分"适用于日志（查询必带时间窗），不适用于商品（查询不带时间窗）**——这是 `03 存储与索引的形态决策树` 里分片键四原则在 ES 上的投影。

### 副本数：它是持久性与读吞吐，不是"可用性保险"

| 副本 | 磁盘 | 读吞吐 | 写成本 | 索引速度 | 何时用 |
| --- | --- | --- | --- | --- | --- |
| 0 | 1× | 1× | 1× | 最快 | **只用于批量导入中的临时索引**，线上严禁 |
| **1** | 2× | 2× | 2× | 基准 | **搜索型默认** |
| 2 | 3× | 3× | 3× | −30% | 读 QPS 超出单节点能力，或需要跨 AZ 容灾 |

关键事实：ES 的写是**同步写所有 in-sync 副本后才 ack**，所以副本数影响的是"能扛几个节点同时挂"，而不是"写是否更快"。而**改副本数 = 全量复制分片**，是一次 IO 风暴——变更前按 [07 变更治理](07-change-governance.md) 走低峰窗口。

### 堆内存与 page cache：为什么堆不超过 50%

| 规则 | 数值 | 为什么 |
| --- | --- | --- |
| 堆 ≤ 物理内存 50% | 64 GB 机器 → 31 GB 堆 + 33 GB page cache | ES 读的**全是 segment 文件**，Lucene 靠 OS page cache 加速；堆给多了，page cache 就少了，于是每次查询都读盘 |
| 堆 ≤ 26~31 GB | 31 GB | 超过 32 GB 失去 compressed oops（对象指针变宽），**有效内存反而下降**，且 GC 停顿变长 |
| 堆必须装下"最坏单次查询" | 分片数 × 深分页/聚合瞬时内存 | OOM 几乎从不来自"总量不够"，而来自"一次深分页或一个大聚合" |
| 剩余给 page cache 的现实检查 | 8.8 TB ÷ 12 节点 = 733 GB/节点，page cache 33 GB 只能覆盖 **4.5%** | 所以"热数据必须是索引的一部分"——冷热分层不是省钱技巧，是性能前提（ILM：hot/warm/cold/frozen） |

### JVM 与 GC 纪律

| 项 | 推荐 | 理由 | 反例 |
| --- | --- | --- | --- |
| GC | G1（默认），`MaxGCPauseMillis` 保持默认量级，**不要手调 Eden** | 大堆下 G1 的停顿可预测 | 照搬"电商 Java 应用"的 JVM 参数（`Xmn` 大年轻代）→ 老年代回收变频繁 |
| `-Xms = -Xmx` | 必须相等 | 避免堆伸缩带来的停顿 | 让 JVM 自己长，冷启动后抖动 |
| GC 日志 | 必开，保留 ≥ 7 天 | Full GC 频率是**唯一能提前发现堆泄漏**的信号 | 出事才想起来没开 |
| 线程池 | `write` 队列满 = 429；先看队列长度，**别盲目调大队列** | 调大队列只是把"拒绝"换成"长延迟 + 堆堆积" | 429 一多就 `queue_size: 10000`，然后 OOM |
| 熔断器 | `indices.breaker.request` / `total`（父熔断 95% 堆）必须监控 | 熔断至少返回 429，OOM 会让节点被踢出集群 | 熔断指标从没人看过 |

## 17.13 L0 → L5：从 100 万到 100 亿文档

| 阶段 | 文档量 | 形态 | 能力上限 | **换挡信号（硬阈值）** | 代价 |
| --- | --- | --- | --- | --- | --- |
| **L0** | 100 万（≈ 0.9 GB） | 单节点 ES，0 副本，`refresh: 1s` 也无所谓 | 千级 QPS 点查式搜索 | 单节点磁盘 > 60%；一次发布 = 全站搜索不可用；重建时要停机 | — |
| **L1** | 1,000 万（≈ 9 GB） | 3 节点 + 1 副本 + 6 分片，别名 + 模板 | 5,000 QPS / 亿级 | 单分片 > 50 GB；bulk 429 > 0.1%；查询 P99 > 200 ms | 一致性开始变弱（refresh 延迟） |
| **L2** | 1 亿（≈ 90 GB） | 24~36 分片 × 副本 + **CDC 投影** + 对账 | 3 万 QPS | 单查询触达段数 > 100；深分页/聚合 P99 > 1 s；merge IO > 70% 持续 30 min | 需要专职运维；mapping 变更要重建 |
| **L3** | 10 亿（≈ 900 GB） | **冷热分层（ILM）** + 独立协调节点 + 强制 filter 纪律 + 慢日志 | 5 万 QPS | `cluster state` 更新 > 1 s；分片数 > 节点数 × 20；聚合把查询线程池打满；磁盘水位 > 75% | 冷查询延迟上升（warm/cold 节点）；分层规则本身要维护 |
| **L4** | 100 亿（≈ 9 TB） | 按业务/大租户**分集群** + CCS（跨集群搜索）+ 专用 ingest/coordinating 角色 | 6~10 万 QPS | 单集群节点 > 50；master 元数据/jvm 堆 > 60%；mapping 字段数逼近上限；跨集群查询 P99 > 300 ms | 跨集群聚合不精确；运维对象 × 集群数 |
| **L5** | 1,000 亿+ | 索引分片（时间/租户）+ **可搜索快照**（冷数据在对象存储）+ CCR 多活 | 百万 QPS 级 | 单地域容量/合规；跨地域复制延迟 > 5 s 且不可接受 | 多活的一致性与脑裂；可搜索快照的读延迟 |

**当前主流业务（商品/内容搜索）落在 L3。重点说 L2→L3 的临界点**：

L2 之后你会发现瓶颈已经不是"数据多"，而是**"查询的多样性"**——运营后台的多层聚合、用户的深翻页、租户的临时取数，三类请求抢同一个查询线程池，任何一类失控都会拖垮搜索。这时候正确的动作**不是加节点**（那是线性堆钱），而是：

- **拆角色**：专用 coordinating 节点承接聚合，data 节点只负责取数；
- **分索引**：把一个索引按"是否带时间窗"拆成两个（在线搜索 + 运营归档），让 ILM 把老数据下沉到 warm；
- **把重聚合赶出去**：报表类需求交给 ClickHouse（→ [21]），ES 只保留 top-k。

**不要跳级**：没有别名就上分集群 = 你失去了唯一的秒级切流手段；没有 CDC 就上冷热分层 = 冷数据里躺着的是三个月前就不一致的文档，而你已经没有能力重建。

## 17.14 这个形态特有的崩法

不是"高可用"套话，是倒排索引这个形态自己的失效点：

| 失效 | 长什么样 | 定位方法 | 预防 |
| --- | --- | --- | --- |
| **段爆炸** | 段数/分片 > 500，merge backlog 上涨，查询 P99 抖动 | `_nodes/stats/indices/segments`、`_cat/segments`、merge 队列 | refresh 分级；批量导入 `refresh_interval: -1`；删除比例 > 30% 直接重建 |
| **堆 OOM** | 节点被踢出集群 → 分片重分配 → 集群黄/红 | 堆直方图、breaker 指标、`_nodes/hot_threads` | 禁深分页；聚合 `size` 白名单；`text` 禁 `fielddata` |
| **深度聚合** | 一次运营报表把查询线程池占满，所有用户变慢 | `search.slowlog` > 1 s、`_tasks` 看长任务 | 强制超时 + `terminate_after` + 聚合下推到 ClickHouse |
| **mapping 爆炸** | cluster state 更新秒级，master CPU 100%，写入被拒 | `_cluster/state` 大小、索引字段数 | `dynamic: strict` + 模板 + `flattened`（事故三） |
| **写拒绝（429）** | bulk 大量 429，客户端重试放大成雪崩 | `es_rejected_execution` 按线程池拆 | 客户端限流 + 退避（`eng/15`）；**不要靠加队列解决** |
| **磁盘水位** | 85% 后分片只读，90% 后无法分配 | `_cat/allocation`、ILM 报错 | 预留 15%~25%（merge 需要临时空间！）+ ILM 删除策略 |
| **PIT / scroll 泄漏** | 磁盘不降、merge 不推进、段越来越多 | `_nodes/stats/indices/search` 的 `open_contexts` | PIT TTL 短 + 客户端必须 `close`；滚动任务设上限 |
| **`_update` 风暴** | 计数/库存类高频更新，merge 永远追不上 | 段数 + merge backlog + 写 TPS | **别用 ES 存计数**（见 `03` 与 `eng/37 §37.4.4`）；改成批量 upsert 合并 |
| **幽灵/缺失文档** | 搜到点不开 / 该搜到的搜不到 | 抽样比对（§17.7） | CDC + 日增量对账；建模期埋 `updated_at`、`deleted_at` |

## 17.15 砍掉 90% 预算还能不能跑

从 12 个热节点 + 3 个温节点砍到 **3 个节点**，砍掉冷热分层、CCS、独立协调节点、可搜索快照、实时对账平台：

| 保留 | 砍掉 | 后果 |
| --- | --- | --- |
| 3 节点 + 1 副本 + **别名** + 严格 mapping | 冷热分层、跨集群搜索、独立协调节点、可搜索快照 | 冷数据查询慢（但仍能查）；单集群上限 ≈ 30 亿文档 |
| `refresh: 30s`（写入密集索引）+ **写后读回源权威源** | 1s refresh 的 6 个索引、`refresh=wait_for` | 新建内容最多 30 秒可见；运营"我刚存的"走权威源兜底，体验无感 |
| 一套 **CDC** 链路 + 日增量对账 | 应用双写、实时抽样对账、重建演练平台 | 差异发现从 5 分钟变 24 小时；必须业务方书面接受 |
| `filter` 纪律 + `search_after` + 固定聚合视图 | 用户自定义多维聚合、相关性 A/B 平台、离线 NDCG 自动化 | 运营后台退化为固定报表（走 ClickHouse/直连 SQL）；相关性改动只能靠肉眼 |

**结论：这个形态的必需品只有三样——**

1. **权威源 + 一个能重建的、带别名的索引**（没有它，索引就是不可修改的单副本）；
2. **可见性契约**（`refresh` 分级 + 写后读回源，写进接口文档的"30 秒内可见"）；
3. **查询纪律**（`filter` context + `strict` mapping + 深分页走 `search_after`）。

其余全部（分集群、冷热分层、CCS、实时对账、相关性平台、多活）都是**量级与组织规模驱动**的。每次评审都问一遍"哪三个是必需品"，能砍掉一半的架构虚荣（与 [12 短链 · §12.12](12-shortlink-system-design.md) 同一把尺子）。

## 17.16 十分钟答题卡

被要求现场设计搜索系统时，按这个顺序讲，不要从"我们用 ES"开始：

```
1  真问题   准实时性与写入吞吐互为倒数；段不可变 → 可见性=新开段，代价=merge
2  量级     100 亿文档 × 880 B = 8.8 TB；写入 24 MB/s → merge+副本后磁盘要 192 MB/s
3  边界     ES 永远是派生索引；写成功不算业务成功；写后读走权威源
4  mapping  keyword/text 分清；多字段用 .keyword 子字段；一对多先宽表后 nested；
            dynamic: strict（不然 mapping 爆炸会打死 master）
5  写路径   CDC > 双写 > 全量；_id 由业务主键派生保证幂等；429 退避不加大队列
6  可见性   refresh 分级：写入密集 30s、会话 1s、导入 -1；"30 秒可见"写进契约
7  一致性   对账三层：5 分钟抽样 / T+1 增量 / 每周全量 + 每季度重建演练
8  查询     90% 条件进 filter；深分页 search_after + PIT（PIT 会阻止 merge）；
            cardinality 是估算，禁止用于对账与计费
9  相关性   BM25 三直觉（饱和/IDF/长度归一）；权重先归一化；NDCG 分桶 + 交错实验
10 容量     分片 = clamp(D/50GB, 节点数, 堆GB×20)；堆 ≤ 31GB 且 ≤ 物理 50%（留 page cache）
11 运维     别名是唯一切流开关 → 零停机重建五阶段；回滚 = 改指针，1 秒
12 换挡     单分片 > 50GB → 加分片；段数/分片 > 500 或 merge IO > 70% → 改 refresh/重建
```
