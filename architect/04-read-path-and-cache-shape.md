## 04.1 事故引子：一次改价，让 661 万人看到旧价格

**背景**：商品详情页，峰值读 62,000 QPS，Cache-Aside（先写库、再删缓存），Redis TTL 24 h，读侧连只读副本（复制延迟 P99 200 ms）。这套组合几乎是业界默认配置。

**事故（2025-11-04，大促前 90 秒）**：运营把某爆款价格从 ¥199 改成 ¥129。

| 时间 | 事件 | 数据 |
| --- | --- | --- |
| 09:58:30.412 | 应用执行 `DEL i:P88132`，返回成功 | 缓存已空 |
| 09:58:30.590 | 主库提交成功，binlog 位点 4,882,113 | 真值已是 ¥129 |
| 09:58:30.6 ~ 31.3 | 17 个读请求 miss，回源打到**只读副本**（lag 680 ms） | 17 次读到 ¥199 |
| 09:58:31.284 | 其中一个请求把 ¥199 回填进 Redis，TTL 24 h | **脏值固化，这是唯一的关键瞬间** |
| 10:00:00 | 大促开闸，QPS 8,200 → 62,000，该商品进首页热榜 | 命中率 98.7% |
| 10:00 ~ 12:58 | 每一次命中都在返回 ¥199 | **旧价展示 6,612,400 次** |
| 11:20 | 客服接到首批「页面 199、结算 129」投诉 | 客诉 340 起 |
| 12:58 | 定位：Redis 值 ¥199，TTL 剩 20.9 h；删除后 3 分钟未复现 | 排查 3 小时 18 分 |
| 13:05 | 修正 + 补发 ¥70 差价券 | 直接补偿 18.2 万元 |

失效只发生在**一个瞬间**（09:58:31.284），之后 3 小时全部正常——所有监控指标都是绿的：命中率 98.7%（比平时还高）、Redis 延迟 0.9 ms、DB 负载很低。**缓存工作得完美，返回的却是错的。**

同类事故的另一种触发是**删除本身失败**（2025-10-19）：Redis 主从切换 8 秒，`DEL` 超时，应用只记了一条日志、不重试、不告警，旧值活到 TTL 12 h 自然过期。两次事故的根因是同一个：**把"失效"当成一次可以失败的尽力而为调用。**

### 写完之后，系统里有五处视图是活的

| 视图 | 谁在持有 | 写完之后多久才会变 | 谁能强制它变 |
| --- | --- | --- | --- |
| ① 浏览器 | 约 180 万终端 | `max-age` 到期（60 s）或被用户清 | **没人**，除非改 URL |
| ② CDN / 边缘 | 37 个 PoP | purge 生效，或 TTL 到期 | purge API（有失败率，不可枚举） |
| ③ 进程内 LRU | 240 个 Pod × 10 万条 | 广播 80 ms / 轮询 1 s | 广播 + 硬 TTL 10 s |
| ④ Redis | 1 主 3 从 | `DEL` / 换指针即刻 | `DEL`、版本化指针 |
| ⑤ 只读副本 | 4 个副本 | 复制延迟 L（P99 200 ms，长尾 1.2 s） | **只能等**，或改读主库 |

```
      T+0      主库真值 ¥129 ●──────────────────────────┐
                                                      │ 复制延迟 L = 680 ms
      T+0.68s  只读副本仍是 ¥199 ●──┐                   │
                                    │ 回源读           │
      T+1.2s   ①浏览器  ②边缘  ③本地LRU×240  ④Redis  ⑤副本
                 旧值     旧值      旧值         旧值    旧值
                   │        │         │           │       │
                   └────────┴─────────┴───────────┴───────┘
                        「用户可能看到旧值」的视图：241 处 + 180 万终端

     能让 ④ 立刻变：一次 DEL 或换指针（毫秒级）
     能让 ③ 立刻变：广播（80 ms），丢包则靠轮询（1 s），最坏靠硬 TTL（10 s）
     能让 ② 立刻变：purge（秒～分钟，且不可靠）
     能让 ① 立刻变：不能。所以「可回滚」必须靠 URL 版本，不靠缓存语义
```

**这就是本篇的全部张力**：命中率是一个数字，失效是一组**分布在四个层级、五种机制、还各带失败模式**的动作。前者可以靠加内存买到，后者只能靠形态设计消灭。所以本篇的目标不是把命中率从 95% 推到 99%，而是**把"要失效的视图数"从 245 降到 1**——§04.5 会给出这条路径。

## 04.2 精确定义与唯一真问题

**定义**：读路径形态 = 一个读请求从终端到真源穿过的**所有视图层**，加上**每层失效语义的合成**。它由三件事共同决定，缺一不可：层的数量、每层的缓存内容、每层的失效机制。

**反例（什么不算"读过缓存"）**：

| 说法 | 为什么不算 |
| --- | --- |
| "我们加了 Redis" | 只说了层，没说失效语义。TTL 24 h + 无失效 = 一份只读快照，不是缓存 |
| "我们用了最终一致" | 最终一致必须给出**窗口多长**和**窗口内谁保证什么**（§04.7）。没有数字的"最终一致"是免责声明 |
| "缓存失效了就回源" | 没定义"失效失败"怎么办。事故 2 的全部成因就在这一句 |
| "命中率 99%，所以没问题" | 命中率是成本指标，不是正确性指标。99% × 62,000 QPS = 620 QPS 在读错的路上 |

### 唯一真问题

> **缓存的难点不在命中率，而在「写完之后，系统里还有几处视图是活的」。**
> 因为**写入方只有一处**（主库），而**读取方有 N 处**（浏览器、边缘、进程、Redis、副本）。每一处都持有一份可能过期的副本，每一处的失效机制有不同的延迟和不同的失败模式。设计读路径，本质上是在回答：**我允许哪几处视图活着、各允许活多久、出错时表现在谁身上。**

推出的全部结论：

| 从这条推出的设计 | 具体形态 |
| --- | --- |
| 失效必须"换 key"而不是"删 key"，因为删是不可靠的广播 | 版本化 key（§04.5） |
| 越靠外的层，越只能用"版本化 URL"这种不可失败的机制 | 边缘路径带 `vN`，绝不依赖 purge 成功（§04.4） |
| 越靠内的层，越可以接受广播 + 轮询 + 硬 TTL 的三重兜底 | 本地 LRU 硬 TTL 10 s（§04.8） |
| 窗口必须算出来并写进契约，不能靠"最终一致"糊过去 | 一致性窗口公式（§04.7） |
| 有些数据不该进缓存，因为窗口本身不可接受 | 不该加缓存的六种信号（§04.11） |

## 04.3 缓存形态谱系：六种形态，六种一致性账本

选型失败 90% 的原因不是选了错的技术，而是**选的形态与"写完多久必须生效"这个业务要求不匹配**。

| 形态 | 一致性保证 | 写代价 | 失效方式 | 适用 | 禁用 |
| --- | --- | --- | --- | --- | --- |
| **Cache-Aside**（旁路） | 最终一致，窗口 = 回填竞争 + 复制延迟（§04.7） | 1 次 DB 写 + 1 次 DEL（可能失败） | 删 key（不可靠） | 读多写少、容忍秒级窗口、团队最熟 | 强一致读；删除失败无兜底时 |
| **Read-Through** | 同上，但读路径封装在缓存层 | 无写代价（写走 Cache-Aside） | 删 key | 想统一回源逻辑、多语言栈 | 回源逻辑需要业务分支时（缓存层不该懂业务） |
| **Write-Through** | 缓存与库同事务边界内更新，窗口≈0 | **双写**，写延迟 = max(库, 缓存)，且失败要回滚 | 不失效，直接写新值 | 写少、读多、值小、强一致要求中等 | 写 QPS 高（放大写延迟）；缓存挂=写挂 |
| **Write-Behind**（回写） | 弱：缓存是临时真源，丢数据窗口 = 刷盘间隔 | 写极快，异步刷盘 | 无失效概念 | 计数、会话、可容忍丢失的聚合 | **任何不能丢的数据**（订单、余额、库存） |
| **版本化 key** | 强（内容不可变，指针单 key 原子切换） | 1 次 append + 1 次指针更新（同一事务） | **换指针，无需删内容** | 内容可变但历史需保留、要求秒级撤销 | 值极大（双份存储贵）；纯递增计数器（版本爆炸） |
| **物化视图 / CQRS** | 最终一致，窗口 = 消费滞后（可见且可监控） | 异步，写代价在消费者侧 | 重建投影（幂等） | 多维查询、聚合报表、搜索 | 要求"写完立刻按新维度查到"；投影不可重建时 |

三条选择纪律：

1. **默认 Cache-Aside，但只要出现"必须秒级撤销"，立刻升级到版本化 key**（§04.5 给时间对比）。这两者不是性能差别，是**失效可靠性**差别。
2. **Write-Through 只在写 QPS < 读 QPS / 100 时考虑**。它把写变成双写，把缓存可用性绑进写路径——对下单、支付这类写是灾难。
3. **物化视图不是"缓存"，是"第二份真源"**：它必须有重建脚本、有滞后监控、有"建后读回主库"的兜底。把投影当缓存用（以为删了就好）是最容易出账差的一类事故。

## 04.4 五级链路：逐级的命中率、延迟、容量与失效语义

```
                     ┌────────────────────────────────────────────────┐
 Browser             │ ① 浏览器缓存   max-age=60 / 静态资源名带内容 hash │ 结束 30%
                     └───────────────────┬────────────────────────────┘
                                         │ 70%
                     ┌───────────────────▼────────────────────────────┐
 Edge / CDN          │ ② 边缘缓存  路径 /v{ver}/slug  且 可 purge      │ 结束 40%
                     └───────────────────┬────────────────────────────┘
                                         │ 42%
                     ┌───────────────────▼────────────────────────────┐
 进程内               │ ③ 本地 LRU   广播 + 版本轮询 + 硬 TTL 10 s      │ 命中 65%
                     └───────────────────┬────────────────────────────┘
                                         │ 14.7%
                     ┌───────────────────▼────────────────────────────┐
 Redis               │ ④ i:slug → {ver,status} ・ s:slug:v{ver}        │ 命中 99.0%
                     └───────────────────┬────────────────────────────┘
                                         │ 0.15%  ≈ 93 QPS
                     ┌───────────────────▼────────────────────────────┐
 MySQL               │ ⑤ 主库（强一致）/ 只读副本（滞后 L）             │ 真源
                     └────────────────────────────────────────────────┘

 未命中率 = (1-0.30)(1-0.40)(1-0.65)(1-0.99) = 0.147%   ← 乘法，不是加法
 回源 QPS = 62,000 × 0.147% ≈ 91    ← 这个数决定分片数（→ [03 存储与索引]）
```

| 层 | 命中率目标 | 单次延迟 | 容量 | 失效手段 | 一致性语义 |
| --- | --- | --- | --- | --- | --- |
| ① 浏览器 | 30% | 0 ms | 终端侧，不可控 | **只有改 URL**（`max-age` 到期不可促） | 不可撤销；所以只能放"可版本化"的 URL |
| ② 边缘 | 其中 40% | 3 ms | 按 TTL + LRU，单 PoP 数百 GB | `purge` API（秒～分钟，不可枚举全 PoP） | 最终一致，purge 有静默失败 |
| ③ 本地 LRU | 65% | 0.05 ms | 10 万条 / 实例 ≈ 40 MB | pub/sub 广播 + 1 s 版本轮询 + 硬 TTL 10 s | **秒级**最终一致，三机制叠加 |
| ④ Redis | 99.0% | 1.2 ms（跨 AZ +0.8） | 工作集 2.4 GB | 换指针（无需删内容）；少量场景 `DEL` | 单 key 原子；主从切换可能回退旧值 |
| ⑤ 主库 / 副本 | — | 8 ms | 全量 | — | 主库强；副本有 L，不可作为"读己之写"的依据 |

**三条从这张表直接推出的工程结论**：

1. **每往内一层，延迟降一个数量级，可靠性降一个等级。** 所以热点放在最内层，可撤销性的保证放在最外层——方向恰好相反，这就是为什么"边缘缓存 + 可撤销"必须靠 URL 版本（②不接受 purge 失败）而"本地 LRU + 强正确"必须靠硬 TTL（③不接受广播失败）。
2. **乘法决定了优化顺序**：把最外层命中率从 30% 提到 40%，回源降 14%（0.147% → 0.126%）；把 Redis 从 99% 提到 99.9%，回源降 90%（0.147% → 0.015%）。**但前者省的是带宽和 TLS，后者省的是 DB 机器**——按你要省的东西选，不按百分比选。
3. **缓存不能加在"会失败就没兜底"的位置**：任何一层挂掉，必须能整体降级为"回到上一层或直连真源 + 限流"。§04.13 给验证方法。

## 04.5 版本化 key：把"要失效 245 处视图"降维成"1 个 16 字节指针"

### 核心结构

```
  i:{id}        →  { version: 7, status: "active", flags: 0 }     16 B，唯一会变的东西
  s:{id}:v7     →  内容字节（价格、标题、详情…）                    不可变，可无限缓存
  s:{id}:v6     →  上一版内容                                      还在，只是没人引用
```

读路径两次 GET（指针 + 内容），写路径 = **插新版本 + 切指针**。**旧内容的缓存 key 永远不需要删**——它不再被任何指针引用，自然过期后被 LRU 淘汰。

### 为什么它比 purge / TTL / 双删都正确：紧急下线的时间对比

场景：09:00:00.000 发现某 item 指向违规内容，要求"全量生效，越快越好"。

| 方案 | 生效路径 | P50 | P99 | 最坏 | 失败模式（这是关键） |
| --- | --- | --- | --- | --- | --- |
| **TTL 等待** | 什么都不做 | 30 min | 24 h | **永不** | 每个命中都在刷新 TTL（或有长 TTL 层）→ 旧值永生 |
| **删 key + 逐节点清本地** | 1 次 Redis `DEL` + 240 次进程广播 + M 个边缘 purge | 800 ms | 12 s | 旧值活到 TTL | 任一节点删除失败/不回 ack → 该 Pod 继续返回旧值；删除与回源竞争还会**回填**旧值（§04.1） |
| **双删（延迟双删）** | 删 → 写 → sleep 500 ms → 再删 | 1.1 s | 3 s | 第二次删失败无告警 | 本质是"赌第二次能覆盖第一次的竞争"，窗口内的回填仍可能落在第二次删之后 |
| **版本化 key** | 写 v8 → 更新 `i:{id}` 指向 8 | **12 ms** | 1.05 s | 5 s（本地指针硬 TTL） | 指针写失败（单 key，写失败即可返回错误给控制面重试，**不会静默**）；`s:` 旧值残留但**无人引用**，不构成风险 |

**差距的量级不是 2 倍，是 100~1000 倍，而且失败模式从"静默错误"变成"显式错误"。** 这就是全部论证：删除是**向 N 个持有者发出的、不可确认的广播**，而换指针是**对 1 个权威位置的一次原子写**。分布式系统里，能确认的单点写永远优于不可确认的广播。

**延伸到边缘**：如果边缘缓存按 `/v7/{slug}` 取 key，那么"换指针"同样能让边缘失效——新请求带着新版本号，永远打不中旧 key，**不需要 purge API 成功**。这是本套书反复用的一条手法：**用 key 的不可变性，替代失效机制的可达性。**（同源手法：`→ [12 短链 · §12.6](12-shortlink-system-design.md)`；Agent 侧的 key 版本化见 `→ llm/24 · §24.4.4`）

### 代价：必须显式买单

| 代价 | 量级 | 缓解 |
| --- | --- | --- |
| 多一次 GET | +0.05 ms（本地缓存指针后）～+1.2 ms（每次都读 Redis） | 指针进本地 LRU（16 B × 10 万条 = 1.6 MB） |
| 需要一张版本表 | append-only，写放大 1 条/次 | 按 `(id, version)` 主键；旧版本 TTL 30 天后归档到冷存储 |
| 存储放大 | 内容存两份（当前 + 上一版） | 只保留 N 个版本；大对象（>100 KB）不适用（改用内联小字段也版本化） |
| 指针层成为新的失效面 | 自己的本地 LRU 也要失效 | 指针硬 TTL 5~10 s + 广播；**但失效面从"全部内容"缩到"16 B × 全部 id"** |
| 不适用纯计数器 | 每次 +1 都会产生新版本 | 计数器用 `INCR` 单 key（原子，无需版本） |

> **判定线**：只要数据满足"**读完就可能被合规/运营要求立刻下线**"，版本化 key 就不是优化项而是必需品。反过来，纯计数、纯追加日志（内容永不改）没有版本可言，硬套只会加大复杂度。

## 04.6 三个经典问题：正解、错解与各自的失败模式

### 04.6.1 穿透（查一个根本不存在的东西）

| 做法 | 效果 | 失败模式 | 判定 |
| --- | --- | --- | --- |
| **直接返回 404**（不查 DB） | 回源 = 0 | 只要判断依据（布隆/名单）不同步，就是把"不确定"变成"确定的错误" | ❌ 除非数据永不变 |
| **布隆过滤器** | 挡掉 99.9% 的随机扫描 | 见下方"假阴性的致命性" | ✅ 主手段，必须 fail-open |
| **空值缓存（60 s）** | 挡掉重复枚举 | 攻击者每次换随机 id → 缓存条目被打爆（内存型攻击）；新数据创建后 60 s 内"不存在" | ✅ 必须叠加，但**限频** |
| 布隆 + 空值 + IP 限流 | 组合 | — | ✅ **正确解** |

**布隆假阴性的致命性**（本篇最该背的一条）：布隆的契约是"**只可能假阳性（说存在其实不存在），绝不假阴性（说不存在其实存在）**"。所以当它说"不存在"时，系统会走"确定不存在"的快路径——**直接 404，不回源**。一旦契约被违反，后果不是"慢"，是：

- 用户刚创建的 item 立刻 404，而他手上已经有链接（**无法解释、无法回滚**）；
- 触发原因几乎总是"同步点漏了"：写库成功但写布隆失败、批量导入绕过应用层、布隆分片重建期间读旧位图、多副本位图不同步；
- 更糟的是它**极低频**，监控看不到，客服只能一个个手工查库。

所以三条铁律：**① 写路径必须"写库 → 写布隆 → 才返回成功"，宁可创建慢 5 ms；② 布隆重建用双位图 + 版本号，切换是换指针不是原地清空；③ 布隆不可用/未加载完成时必须 fail-open（回源 DB），绝不 fail-closed。**

### 04.6.2 击穿（一个热点 key 过期的瞬间）

| 做法 | 并发回源数 | 失败模式 | 适用 |
| --- | --- | --- | --- |
| **singleflight**（进程内合并） | 单 Pod 1 个，集群 = Pod 数（240） | ① leader panic / ctx 取消 → **所有等待者一起失败**（必须让等待者降级去读旧值或直接报错）；② 跨 Pod 不合并，240 个回源仍可能压垮小库 | ✅ 默认解，必须配 ctx 超时 + 旧值兜底 |
| **互斥锁**（Redis `SETNX`） | 全集群 1 个 | ① 持有者崩溃 → 锁 TTL 期间全员阻塞（TTL 短则双回源，长则雪崩）；② 锁本身是单 key 热点；③ 多一次 RTT | ⚠️ 只用于"回源成本极高"（如 3 s 的聚合查询） |
| **逻辑过期**（值内带 `expire_at`，不设物理 TTL） | 1 个异步刷新 | ① 刷新线程/任务挂了 → **永久返回旧值且无 miss 信号**（最危险，必须给"刷新失败"单独告警）；② 冷 key 首次仍是击穿 | ✅ 超高热点（如首页、秒杀） |
| 本地 LRU + 上述之一 | 热点在进程内根本不 miss | 本地层的失效延迟变成正确性风险 | ✅ 组合 |

### 04.6.3 雪崩（大批 key 同时不在）

| 做法 | 作用 | 失败模式 |
| --- | --- | --- |
| **TTL 抖动**（`ttl × (0.8 + rand×0.4)`） | 打散过期时刻，把尖峰摊平成斜坡 | 只解决"同时过期"，不解决"缓存全挂" |
| **分层 TTL**（Redis 24 h > 本地 10 s > 空值 60 s） | 内层先失效、外层兜住，回源被削峰 | 必须显式设计，默认常常写成"每层同一个 TTL" |
| **预热**（大促/发布前按 top N 灌入） | 冷启动不打库 | 预热的 key 集合会与实际热点偏离，需带预热命中率监控 |
| **降级兜底**（限流 + 旧值 + 静态页） | 缓存全挂时保住核心接口 | 需要提前准备，事后加不了 `→ eng/19` |

## 04.7 一致性窗口：把"最终一致"算成一个数字

### 公式

```
W = L + R_a + R_c + B + P

  L    主从复制延迟（写主库到副本可见）        ← 通常最大项
  R_a  写库 ack 的往返（含一次 fsync）
  R_c  失效动作的往返（DEL / 指针更新）
  B    应用重试退避总时长（指数退避的累计）
  P    失效广播到 N 个进程的最长时间（或轮询周期）
```

| 环节 | 符号 | 典型值 | 极端值 | 触发极端值的原因 |
| --- | --- | --- | --- | --- |
| 复制延迟 | L | 80 ms（P99 200 ms） | 1.2 s | 大事务、DDL、从库 IO 抖动 |
| 写 ack | R_a | 1.5 ms | 30 ms | 双 1 刷盘、跨 AZ |
| 失效往返 | R_c | 0.8 ms | 5 ms | 主从切换中的重连 |
| 重试退避 | B | 50 ms（1 次） | 400 ms（3 次） | 失效失败后的指数退避 |
| 广播/轮询 | P | 80 ms | 2 s（轮询兜底） | pub/sub 丢包 |
| **合计 W** | | **≈ 210 ms** | **≈ 3.6 s** | |

**这个数字要写进接口契约**，而不是写在架构文档的形容词里：「创建/修改后 3.6 秒内全局可见；P50 210 ms」。

### 窗口内"读己之写"的三种做法

| 做法 | 机制 | 保证 | 代价 | 适用 |
| --- | --- | --- | --- | --- |
| **会话粘滞** | 同一用户 N 秒内路由到同一副本/同一处理节点 | 弱：只保证"自己"看到，且副本本身可能落后 | 路由粘滞降低负载均衡质量；节点挂则失效 | 成本最低，适合非关键展示 |
| **主库读**（变更后开窗） | 写完成后 30 s 内，该主体（user/item）的读强制走主库 | 强：窗口内必读到新值 | 主库 QPS 增量 = 变更主体的读流量；热点主体可能把主库打满 | ✅ **默认推荐**，主体粒度限流 |
| **版本号比较** | 客户端持有 `last_write_version`，读时带上；服务端在视图版本 < 客户端版本时回源主库或拒绝 | 最强：显式可判 | 需要契约支持（响应带版本、请求带版本）；不适合所有 API | 结算、审批、后台编辑（"刚存的东西必须能看到"） |

> 一条经验：**把"变更后开窗"实现成读路径的一个开关（按 subject 维度），比在每一处业务代码里写 `useMaster=true` 可靠得多。** 前者是形态，后者是习惯；习惯一定会漏。

## 04.8 本地缓存的失效广播：三种方案与"永远要有的第三层"

| 方案 | 一致性延迟 | 可靠性 | 代价 | 失败模式 |
| --- | --- | --- | --- | --- |
| **pub/sub 广播** | 80 ms（P99 1 s） | 中 | 一次广播 N 份，消息量大但极小 | **消息丢失 = 该节点永久不一致**（Redis pub/sub 不持久化、无 ack）；重启期间的节点收不到任何历史消息 |
| **版本号轮询** | 周期/2（1 s 周期 → P50 500 ms，P99 1 s） | **高**（拉模式天然自愈） | N × 1/周期 = 240 QPS 的读放大（可忽略） | 延迟有下界；版本号本身也要缓存 |
| **gossip** | 秒～十秒（log N 跳） | 高（节点故障可绕过、无中心） | 实现复杂，带宽 MB 级，调试困难 | 收敛时间不确定；>1000 节点才值得 |

**工程结论：不要三选一，要叠三层。**

```
第 1 层  pub/sub      快，负责 99% 的及时性
第 2 层  版本号轮询    1 s 周期，负责"广播丢了的那些"
第 3 层  条目硬 TTL    10 s 上限，负责"前两层都失效的那些"

铁律：本地缓存的任何条目都必须有硬 TTL 上限，且这个上限 = 你能接受的最坏不一致时长。
      没有硬 TTL 的本地缓存是"一台永不重启的错误复制机"。
```

## 04.9 热点 key：识别、隔离、吸收

**先识别，再动手。** 热点 key 的特征是"单 key QPS 占集群 > 1%"，症状是"某个分片 CPU 是均值的数倍"。

| 识别手段 | 怎么取 | 能回答什么 | 代价 |
| --- | --- | --- | --- |
| **客户端采样** | 每 1000 次请求记 1 次 key，进本地 Count-Min Sketch / Space-Saving，每 10 s 上报 top 50 | 谁最热（够用，误差可控） | 极低；**采样比 1/1000 时，1% 的热 key 仍能被稳定识别** |
| **分片指标倾斜** | 每分片 CPU/QPS 的 `max/avg`，> 1.5 即告警 | 有没有热点（不需要知道是谁） | 仅为观测 |
| **代理层统计** | 自建 Redis 代理按 key 前缀计数 | 精确 top N | 中：需要代理或 `--hotkeys` |
| 慢查询/slowlog | Redis slowlog | 大 key、复杂命令 | 只能看到慢的，看不到热的 |

| 手段 | 原理 | 收益 | 代价 |
| --- | --- | --- | --- |
| **本地 LRU 天然吸收** | 热 key 在每个 Pod 内存里都有一份 | 单 key 的读 QPS 被摊到 240 个进程 → Redis 侧降 99% | 一致性降到"秒级"（§04.8），读多写少才可用 |
| **多副本 key** | `hot:{id}:0..9`，写时写 10 份（或版本化后写 1 份指针 + 10 份内容），读时随机 | 单分片压力 ÷ 10 | 写放大 10×；副本间可能短暂不一致 |
| **请求合并** | singleflight（§04.6.2） | 同一瞬间的 N 个 miss 变 1 个 | 单 Pod 有效，跨 Pod 无效 |
| **独立分片 / VIP 分片** | 把该 key 家族单独放一个分片 | 隔离故障域 | 运维复杂，需要路由表 |
| 逻辑过期 + 异步刷新 | 永不 miss | 峰值完全不回源 | 旧值风险（必须告警刷新失败） |

**注意一个反直觉**：热点 key 的"多副本"在**版本化 key 下是免费的**——因为内容不可变，`s:{id}:v7:0..9` 可以随便复制，指针 `i:{id}` 只有一个。这就是 §04.5 的第二个红利：**不可变内容天然可复制，可变指针天然单点。**

## 04.10 命中率-成本曲线：算到拐点，然后停手

**前提（全部给推导）**：峰值读 62,000 QPS；单库实例安全回源水位 2,000 QPS（点查 P99 ≤ 10 ms）；只读副本 8C32G ≈ **$620/月**；Redis 主从 ×2，16 GB 规格 ≈ **$600/月**（32 GB ≈ $1,200）；单条缓存值 400 B（含 key 与对象开销）。

```
需要实例数 = ceil(62,000 × (1 - h) / 2,000)
内存容量   = 工作集条数 × 400 B          ← 工作集由幂律决定，不是全量
```

| Redis 命中率 h | 工作集条数 | 内存 | Redis $/月 | 回源 QPS | DB 实例 | DB $/月 | 合计 $/月 | 边际收益 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 0%（无缓存） | — | — | 0 | 62,000 | 32 | 19,840 | **19,840** | 基线 |
| 90% | 20 万 | 80 MB | 600 | 6,200 | 4 | 2,480 | **3,080** | 省 16,760 |
| 95% | 60 万 | 240 MB | 600 | 3,100 | 2 | 1,240 | **1,840** | 省 1,240 |
| 98% | 200 万 | 800 MB | 600 | 1,240 | 1 | 620 | **1,220** | 省 620 |
| 99% | 600 万 | 2.4 GB | 600 | 620 | 1 | 620 | **1,220** | **省 0** |
| 99.9% | 5,000 万 | 20 GB | 1,200 | 62 | 1 | 620 | **1,820** | **−600（负收益）** |

**拐点在 98%，而且理由不是"够用了"，是数学：**

1. 98% 时回源 1,240 QPS，已经在单实例水位（2,000）的 62% 以下 → **再多命中率换不来一台机器**，只是把 CPU 利用率从 62% 降到 3%。
2. 98% → 99% 多花 1.6 GB 内存，省 0 台库；99% → 99.9% 还要再花 17.6 GB，**机器成本反而涨 600**，因为命中 99.9% 要求缓存 5,000 万条全量热点集合。
3. 所以 98% 之后正确的动作不是"再加内存"，而是：**给回源加弹性（限流 + 队列，`→ eng/15`–`eng/19`）**，或者**降低单次回源成本（分片 + 覆盖索引，`→ [03 存储与索引]`）**。

**反过来看早期**：无缓存 → 90% 命中率，投入 80 MB 内存省下 28 台库。这是全书投入产出比最高的一次改动，而它只需要"单级 Redis + Cache-Aside"，不需要多级缓存、不需要边缘。**先把 90% 拿到，再谈后面每一项都更贵的百分点。**

**什么时候干脆不划算**：边际回源 QPS 已经低于单实例水位的 30%，且内存单价高于算力单价——此时你在"用贵内存换便宜 CPU"。判据写成一句话：**每提升 1 个百分点命中率，如果省下的 DB 成本 < 增加的缓存成本，就停手。**

## 04.11 什么时候不该加缓存

| 信号 | 判据（可测） | 为什么缓存无效/有害 | 替代方案 |
| --- | --- | --- | --- |
| **写多读少** | 读写比 < 3:1 | 每次写都要失效，缓存刚填就被推翻，命中率天花板 < 50% | 写优化：批量、覆盖索引、减少索引数 |
| **数据量小** | 工作集 < 单实例内存 1/10，P99 < 10 ms | DB 的 buffer pool 已经是进程内缓存，你只是加了一层更远的缓存 | 加 buffer pool / 加索引 |
| **强一致要求** | 业务不能接受任何窗口（余额判定、库存扣减依据、权限） | 任何缓存都把"确定"变成"窗口"；§04.7 的 W 再小也不是 0 | 主库读 + 单写者 + 乐观锁 |
| **访问无热点** | 命中率天花板 < 60%（长尾/随机/个性化） | 缓存只是把一个 8 ms 的查询换成"两次 1.2 ms + 一次 8 ms"，还多一个失败面 | 分区裁剪、索引、只读副本 |
| **缓存本身成为单点** | 单 Redis 实例承载 100% 流量，无降级路径 | 可用性从 99.95% 掉到 99.9% × 99.95%，**加缓存反而降低可用性** | 先做副本 + 熔断降级 + 限流 |
| **尚无观测** | 没有命中率、回源 QPS、失效成功率三个指标 | 你看不到 §04.1 那种"命中率很高但值是错的"状态 | 先埋点，再上缓存 |

> 面试与评审里最快的一条反驳：**"这数据读写比多少？命中率天花板多少？缓存挂了你降级到什么？"** 三个问题答不出来，就还没到加缓存的时候。

## 04.12 反模式表

| 反模式 | 长什么样 | 为什么致命 | 正确做法 |
| --- | --- | --- | --- |
| **缓存当数据库** | 有些数据只存在 Redis（无 TTL、无持久化兜底、DB 里没有） | Redis 重启/淘汰即数据丢失；扩容时 slot 迁移丢 key | Redis 只放可重建的副本；真源永远在 DB |
| **缓存里存大对象** | 存 200 KB 的详情 JSON / 整个列表 | 序列化 + 网络 + 反序列化成本超过回源；单 key 打满带宽；淘汰时抖动 | 只缓存"渲染所需的最小字段"（< 10 KB）；大对象走对象存储 |
| **用 TTL 代替失效** | "反正 5 分钟会过期" | 5 分钟内是**确定的错**，且任何刷新都会把 TTL 续上（§04.7 的"永不"） | TTL 只做兜底；主手段是版本化换指针 |
| **多级缓存不同步** | 本地 TTL 10 min、Redis TTL 1 h、无广播 | 各层各自过期 → 长尾不一致时长 = 最差那层；回滚后各地表现不同 | 分层 TTL 有明确大小关系（内 < 外）+ 广播 + 硬 TTL 上限 |
| **穿透用 try-catch 兜** | `try { cache.get() } catch { return db.query() }` | 把"缓存不可用"静默变成"全量回源"，缓存挂的那一刻就是雪崩 | 显式降级：限流 + 旧值 + 快速失败；告警到"回源 QPS 异常" |
| **先删缓存再写库，删除失败不重试** | 只打日志 | 旧值存活到 TTL（§04.1 事故 2） | 删除幂等 + 重试 + 失败告警 + 最终换指针 |
| **发号/校验类判断依赖缓存** | 用缓存判断"是否已领取""是否存在" | 缓存 miss 时判断反转，产生重复发奖/误 404 | 判断走真源或走不可变位图（布隆，fail-open） |
| **key 里缺维度** | 多租户/多用户共用 key | 跨租户/跨用户泄露（`→ llm/24 · §24.1`） | key 由唯一构造函数生成，强制含租户、用户、版本 |

## 04.13 会在哪崩、什么时候换挡、怎么验证

### 这个形态特有的崩法

| 失效 | 长什么样 | 定位方法 | 预防 |
| --- | --- | --- | --- |
| **回填旧值** | 改了数据，缓存里是旧值，且 TTL 很长 | 抽样比对缓存值与主库；对"写入后 60 s 内该 key 的 miss 次数"打点 | 回源走主库 + 回填前二次校验版本（下方代码）；删除加延迟重试 |
| **布隆假阴性** | 极低概率"新建即 404" | 定时用真实 id 抽样验证布隆；统计"库里有、布隆说没有" | 写库→写布隆→才返回成功；双位图换指针；fail-open |
| **广播丢失** | 少数 Pod 长时间返回旧值，重启即恢复 | 对"本地缓存 age > TTL 上限"的条目计数，> 0 即告警 | 轮询兜底 + 硬 TTL |
| **热点单分片** | 某分片 CPU 100%，整体 P99 抖动 | 分片 `max/avg` > 1.5 | 多副本 key + 本地 LRU + 逻辑过期 |
| **缓存挂全量回源** | 回源 QPS 瞬间 ×240 | 回源 QPS 与缓存错误率同时飙升 | 熔断 + 限流 + 旧值兜底（`→ eng/18`、`eng/19`） |
| **版本表膨胀** | 版本表行数是主表的 30 倍 | 表大小与归档任务水位 | 保留 N 版 + 定期归档 |

### 换挡信号

| 当前形态 | 容量 | **换成下一个的硬阈值** | 代价 |
| --- | --- | --- | --- |
| 无缓存（L0） | 1k QPS | 回源 P99 > 50 ms 或 DB CPU > 70% | 一致性变弱 |
| 单级 Redis（L1） | 1 万 | 回源 > 单实例水位 60% | 多一个失败面 |
| + 读写分离 + singleflight + 空值缓存 + 布隆（L2） | 5 万 | 主库连接数 > 80% 或复制延迟 > 1 s | 必须处理"读己之写" |
| + 进程内 LRU + 失效广播（L3） | 30 万 | 边缘命中 < 30%，或单 AZ 带宽打满 | 秒级不一致，需要广播体系 |
| + 边缘缓存 + 版本化 URL（L4） | 千万 | 单地域容量上限 / 跨境 P99 > 80 ms（`→ [10 多活与单元化]`） | 撤销只能靠 URL 版本，不可 purge 兜底 |

### 怎么验证（"证明它对了"的定义）

1. **失效演练**（必做，每周）：随机选 10 个 key，走一次真实变更，测量"所有层都返回新值"的耗时分布。**判定标准：P99 ≤ W（§04.7 算出的窗口），且失败为 0。** 只测"服务端变了"不算通过。
2. **命中率-延迟曲线**：压测时逐级关闭缓存层（Redis → 本地 → 边缘），画出回源 QPS 与 P99 的对应关系。判定：任一层全挂时，核心接口仍能靠限流 + 旧值撑住 N 分钟不雪崩。
3. **影子比对**：写路径变更后，抽样 1% 请求同时读"缓存视图"和"主库真值"，比对不一致率。判定：不一致率 ≤ 采样窗口内的理论窗口比例（W × 写 QPS），超出即形态有洞。
4. **故障注入**：杀掉一个 Redis 从节点、丢 1% 的 pub/sub 消息、把复制延迟拉到 2 s。判定：本地缓存 age 指标告警，但无静默长尾（≤ 硬 TTL）。

### 骨架代码一：Go · singleflight + 本地 LRU + 回填前二次校验版本

```go
type entry struct{ data []byte; ver int64 }

// Get：本地 LRU → 合并回源 → 指针 + 内容 → 二次校验版本 → 回填
func (h *Handler) Get(ctx context.Context, id string) ([]byte, error) {
	if v, ok := h.local.Get(id); ok {
		return v.data, nil
	}
	v, err, _ := h.grp.Do(id, func() (any, error) { // 同 key 并发只放一个回源
		if v, ok := h.local.Get(id); ok {
			return v, nil // 双检：等锁期间别人已填好
		}
		ptr, err := h.ptr(ctx, id) // i:id → {ver, status}
		if err != nil {
			return nil, err
		}
		raw, err := h.redis.Get(ctx, fmt.Sprintf("s:%s:v%d", id, ptr.Ver)).Bytes()
		if err != nil {
			raw, err = h.db.LoadFromPrimary(ctx, id) // 回源必须走主库（§04.7）
			if err != nil {
				return nil, err
			}
		}
		cur, err := h.ptr(ctx, id) // 二次校验：回源期间指针可能已切换
		if err != nil || cur.Ver != ptr.Ver {
			return nil, ErrVersionMoved // 放弃回填，绝不复活旧值
		}
		h.local.Set(id, entry{raw, cur.Ver}, 10*time.Second) // 硬 TTL 上限
		h.redis.Set(ctx, fmt.Sprintf("s:%s:v%d", id, cur.Ver), raw, 24*time.Hour)
		return entry{raw, cur.Ver}, nil
	})
	if err != nil {
		return nil, err // 调用方降级：读旧值或返回 503，绝不静默回源
	}
	return v.(entry).data, nil
}
```

### 骨架代码二：Java · 版本化 key 的读路径与写路径

```java
// 读：先 i:id 取指针，再 s:id:vN 取内容
public String contentOf(String id) {
    Pointer p = local.get("i:" + id, () ->            // Caffeine，硬 TTL 5s
            json.read(redis.get("i:" + id)));
    if (p == null || p.status() != ACTIVE) throw new GoneException();
    String key = "s:" + id + ":v" + p.ver();          // 内容不可变，可长缓存
    String v = local.get(key, () -> redis.get(key));
    if (v != null) return v;
    Row row = versionMapper.selectByPk(id, p.ver());  // 回源走主库
    redis.setex(key, 86400, row.content());           // 只填内容，不碰指针
    return row.content();
}

// 写：插新版本 + 切指针（同一主库事务），提交后只失效 16B 指针
@Transactional
public void change(String id, String content, String operator) {
    linkMapper.lockById(id);                          // 行锁：同一 id 串行改
    int next = versionMapper.nextVersion(id);
    versionMapper.insert(id, next, content);          // append-only，旧版本仍可回溯
    linkMapper.updatePointer(id, next);               // 唯一会变的东西
    auditMapper.insert(id, next, operator);           // 可追溯、可回滚
    TransactionSynchronizationManager.registerSynchronization(
        afterCommit(() -> local.invalidate("i:" + id))); // 只失效指针，不扫内容
}
```

## 04.14 十分钟答题卡

被要求现场设计"某接口读不动了"时，按这个顺序讲，不要从"我加个 Redis"开始：

```
1  真问题  写完之后还有几处视图是活的？先数层，再谈命中率
2  量级    峰值读 QPS → 读写比 → 命中率天花板（工作集/全量）→ 回源 QPS → 分片数
3  形态    默认 Cache-Aside；出现"必须秒级撤销"就升级版本化 key；物化视图是第二份真源
4  链路    Browser 30% / 边缘 40% / 本地 65% / Redis 99% → 回源 0.15%（乘法，不是加法）
5  失效    换指针 > 删 key > TTL 等待；紧急下线 12ms vs 800ms vs 30min（1000 倍差）
6  三坑    穿透=布隆(fail-open, 写库→写布隆→成功)+空值+限流；击穿=singleflight+ctx+旧值；
           雪崩=TTL 抖动+分层 TTL+预热+降级
7  窗口    W = L + R_a + R_c + B + P ≈ 210ms(典型) / 3.6s(极端)，写进契约
8  读己之写 变更后开窗读主库（默认）/ 会话粘滞（省）/ 版本号比较（最强）
9  广播    pub/sub + 1s 轮询 + 硬 TTL 10s，三层叠加，缺一层就有静默长尾
10 何时不加 写多读少 / 数据量小 / 强一致 / 无热点 / 缓存成单点 / 无观测 —— 六个信号任一成立就停
11 换挡    回源 > 单实例水位 60% → 分层；边缘命中 < 30% → 带宽打满，不是 DB
12 验证    失效演练 P99 ≤ W、逐层关闭压测、影子比对、故障注入
```
