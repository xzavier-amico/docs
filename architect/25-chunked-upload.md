# 25. 大文件分片上传与秒传：断点续传的三件套

> **状态**：`已完成（初稿）` ｜ **所属**：第三部分 · 案例（族 F·平台） ｜ **编号**：25 / 26
> **本篇定位**：族 F「平台」的第二篇。`24` 讲多租户的隔离与计费口径，本篇讲平台里唯一一个**写放大 1000 倍于读**的子系统：文件上传。它是全库最容易被低估的一篇——因为它看起来只是「调个 SDK 传文件」，实际上它同时踩在**幂等、去重、异步事务**三块地基上。上承 [05 写路径形态](05-write-path-and-async-shape.md) 的「允许重做」授权书，下启 `26` 收口的反模式库。
> **唯一真问题**：断点续传不是「支持续传」这个功能，而是**分片幂等 + 内容指纹去重 + 异步转码流水线**三件事的叠加——少任何一件，要么浪费带宽，要么数据损坏，要么上传成功但打不开。
> **读法**：§25.2 先看三件套缺一不可的推导表；§25.6 的「ETag 不等于 MD5」与 §25.8 的「秒传必须做授权」是两处最容易致命的地方；§25.11 的成本表会告诉你为什么「秒传省一半存储」是评审会上最常见的假账。

## 25.1 引子：三起「功能正常」的故障

**事故一：4 GB 文件传了六遍，用户放弃（2025-07-08）**

在线教育平台的教师上传课程录屏，客户端的实现是**单次 PUT、无分片、无断点**。弱网环境（上行 2 Mbps、丢包 3%、Wi-Fi/4G 切换）下，单次 4 GB 需要 `4×1024×8/2 ≈ 16,400 秒 ≈ 4.5 小时`，而链路上任何一次 NAT 超时、网络切换、客户端休眠都会让连接断开且**从头开始**。

| 时间 | 事件 | 数据 |
| --- | --- | --- |
| 07-08 10:04 | 教师第 1 次上传 4 GB 录屏 | 上行 2 Mbps |
| 10:52 | 进度 78%，Wi-Fi 切 4G，TCP 断 | 已传 3.1 GB 作废 |
| 11:30 | 第 2 次，进度 92% 时客户端休眠 | 3.7 GB 作废 |
| 13:10 ~ 17:40 | 第 3~6 次，全部在 80%~95% 区间失败 | 累计上传 **24 GB** |
| 07-09 ~ 07-15 | 同一批弱网教师集中投诉 | 工单 3,800 起，续费率 −6.2% |
| 07-16 | 上线分片 + 断点续传，同场景平均重传量 | 从 100% 降到 **3.8%** |

事故的账不在 CDN 账单上（上行本来就免费），而在**用户的四小时**和**每天被白传一遍的 20 TB 里的 20%**。请注意：**「传输成功了 500 次但从未合并成功过」也是同一类问题**——分片传上去了而 `Complete` 从未被正确调用，在存储侧就变成僵尸分片（见事故三）。

**事故二：秒传把别人的文件发给了用户（2026-02-19，数据泄露级）**

平台为了省 CPU 与工期，指纹算法定为 `MD5(文件大小 + 首 1 MB + 尾 1 MB)`，且「命中即秒传」的实现只做了一件事：**返回已存在对象的下载链接**。

| 时间 | 事件 | 数据 |
| --- | --- | --- |
| 02-19 09:12 | 「秒传加速」上线，指纹采样 MD5，无授权校验 | — |
| 02-20 11:40 | 客服收到 3 起「下载的课件不是我的」 | 用户体感：别人家的合同 |
| 02-21 09:00 | 安全团队按 `object_id` 反查引用 | **1,214 条引用指向他人对象** |
| 02-21 15:00 | 紧急关闭秒传，全站降级为普通上传 | 上传 P95 从 1.2 s 涨到 4 min |
| 02-22 ~ 02-24 | 全量重建指纹（SHA-256）+ 复核 12 万对象，逐条通知受影响用户 | 涉及 87 个租户 |
| 02-25 | 合规通报，罚款与整改成本 | 约 210 万元 |

根因是三件同时缺失：**指纹不抗碰撞**（采样 MD5 连「抗偶然碰撞」都不满足，且对攻击者完全可控：同尺寸模板类文件的首尾字节高度相似）；**「物理对象存在」被当成「你有权引用」**（把去重表做成了越权下载器）；**没有引用计数**（事后还发现删掉 A 的课件导致 B 的课件 404）。

**事故三：没人清理的未完成上传（同月发现）**

对象存储里躺着 **41 万个未完成的 multipart 会话、2,100 万个孤立分片、380 TB 存储**，最老的一个创建于 18 个月前。没有 TTL、没有 `AbortMultipartUpload`，控制台也看不到它们。按 0.08 元/GB/月计算，每年为「上传失败」这件事付费 **36 万元**。

三起事故正好对应本篇的三个核心小节：**分片幂等（§25.6）× 指纹去重（§25.8）× 异步流水线（§25.10）**。

## 25.2 一句话定位与唯一真问题

**定位**：大文件上传是「**一次写入、极少读、但必须能被不确定多个人读到**」的系统。它和短链刚好相反——短链的读写比是 2000:1，上传系统的「写」本身还带着 20 TB/天的物理搬动量，所以**它的问题不在 QPS，而在「一次写入要跨越多少个不可靠环节」**。

### 三件套缺一不可（本篇的全部内容）

| 少了哪一件 | 表面现象 | 真实后果 | 落在哪节 |
| --- | --- | --- | --- |
| 只有分片，没有**幂等** | 续传时「重传同一片」 | 分片被重复计入 / 旧片覆盖新片 → **合并出的文件内容错乱**，且校验不出来的话就静默损坏 | §25.6 |
| 只有分片 + 幂等，没有**指纹去重** | 每个用户都完整传一遍 | 带宽与存储线性放大，4 GB 素材永远要等 20 分钟 | §25.8 |
| 只有指纹去重，没有**转码流水线** | 秒传命中、上传成功 | 源文件格式/码率不可播 → **上传成功但打不开**，用户以为文件坏了 | §25.10 |

反过来，缺「引用计数」会让去重变成删除事故（删 A 的引用把 B 的对象删了）；缺「整体校验」会让分片级检查全部通过但组装结果错误。**所以这三件是主干，另外两件（引用计数、整体校验）是它们的地基。**

### 唯一真问题

> **用户以为他在「上传一个文件」，系统里实际发生的是三件互不相关的事：搬字节（幂等分片）、证明「这就是那份字节」（内容指纹）、让这份字节变得有用（异步转码）。**
> 这三件事的**失败模式完全不同**，却被用户的一个「上传」按钮绑在一次体验里。断点续传的设计，本质是**把这三件事的失败各自封装成可重入的一步**——搬字节可以重传一片，证明可以重算一次，转码可以重跑一遍，而任何一步的重做都不能污染另外两步。

| 从这句话推出的约束 | 推出的设计 |
| --- | --- |
| 搬字节必须能任一片重做 | 分片幂等键 = `(uploadId, partNumber)`，单片 checksum |
| 「同一份字节」必须全局可判 | SHA-256 全量指纹 + 尺寸，且**客户端算、服务端复核** |
| 指纹命中 ≠ 有权使用 | 命中只建**引用**，永不返回他人 `file_id`（§25.8 安全边界） |
| 一份字节可能属于 N 个人 | 物理对象/逻辑引用两层模型 + 引用计数（§25.9） |
| 字节「可播」是异步的、有状态的 | 转码状态机 + 幂等输出 key（§25.10） |
| 合并这个动作不可回滚 | 先分片校验 → 原子合并 → 整体校验 → 失败即删（§25.11） |

## 25.3 量级与预算：全部推一遍

```
日上传量          20 TB = 20,480 GB = 2.048e7 MB
平均文件大小       20 MB              → 1.02 M 个文件/天
秒传命中率         30%（模板、转发、同一素材多租户上传）
物理写入量         20 TB × 0.7 = 14 TB/天

上传会话 QPS       1.02e6 / 86400 ≈ 11.8/s，峰值系数 ×6（晚 8–11 点）≈ 71/s
分片 PUT QPS       平均 4 片/文件（大文件拉高尾部）→ 4.1 M 次/天
                   均值 47/s，峰值 ×6 ≈ 285/s     ← 定签名 URL 服务与限流的数
带宽              20 TB/86400 = 231 MB/s 均值 ≈ 1.9 Gbps，峰值 ×3 ≈ 5.7 Gbps
元数据            4.1 M 行/天 × 120 B ≈ 0.5 GB/天；保留 7 天 ≈ 3.4 GB
                   → MySQL 单表足够，这一步不需要分片（很多人在这里过度设计）
```

**两条只能靠推导得出的结论：**

1. **上传的元数据量级（GB）与内容量级（PB）相差 6 个数量级**。所以元数据用关系库、内容用对象存储，这不是「架构偏好」，是量级决定的必然（→ [03 存储与索引的形态选择](03-storage-and-index-shape.md)）。
2. **分片 PUT 的 285/s 峰值才是真正的 QPS 敌人**，不是上传会话的 71/s。因为每片一次 PUT = 一次签名校验 + 一次审计写 + 一次存储 API 调用。**分片切得过小，等于把这些成本乘以倍数**（§25.5 会给公式）。

## 25.4 协议形态：客户端直传，还是服务端中转

这是上传系统的第一个形态决策，而且**九成团队在事后才想明白**。

| 维度 | 服务端中转（客户端 → 应用 → 对象存储） | **客户端直传（预签名 URL → 对象存储）** |
| --- | --- | --- |
| 带宽成本 | 应用侧要承载 **231 MB/s 均值、峰值 5.7 Gbps** 的持续转发；按公网出网 0.8 元/GB 折算 ≈ **1.6 万元/天** | 入站到对象存储通常不计费；应用侧只承担 KB 级的元数据 |
| 安全性 | 客户端永远拿不到存储凭证；可做同步内容审核 | 需要**预签名 URL 的最小权限化**（限定 bucket/前缀/大小/有效期），否则等于发了一张临时通行证 |
| 可控性 | 每一片都过应用 → 可实时校验、限流、审计、改写 | 分片内容不经应用 → **checksum 必须由客户端头声明 + 服务端事后复核** |
| 可靠性 | 应用进程重启 = 在途分片全丢 | 存储侧接收，应用重启不影响在途分片 |
| 客户端复杂度 | 低 | 中（需并发、重试、算 hash） |
| 适用判据 | 需要**流式改写/强审核/落另一套存储** | **默认选它**：大文件、跨地域、成本敏感 |

**唯一让中转成立的场景**：审核必须在写入前完成（比如央企私有化要求「不落任何未审内容」）。此时做法不是「全部中转」，而是**中转只走首片/摘要**，其余分片直传，审核不通过则删整个对象（代价：一次可能的无效写入，但带宽成本降回 1/20）。

### 直传的协议骨架（预签名两段式）

```
客户端                     上传控制面（Java）                对象存储 / OSS
  │                              │                              │
  │─① InitUpload(size, sha256)──→│                              │
  │                              │─② 秒传查表（physical_object）—→ │ 命中即返回引用，
  │                              │    未命中 ↓                   │ 不传内容（§25.8）
  │                              │─③ CreateMultipartUpload ────→│
  │                              │←── uploadId（含用户/租户前缀）─│
  │←② uploadId + partSize + 签名URL 模板                        │
  │                              │                              │
  │─④ PUT part#0..#N 并发 4~8 ────────────────────────────────→│（不经应用！）
  │←──────────────────────────── ETag + CRC32C ───────────────│
  │─⑤ ReportParts(uploadId, [(no, etag, crc)])─→│              │
  │                              │─⑥ ListParts 交叉校验 ───────→│
  │─⑦ Complete(uploadId)────────→│─⑧ CompleteMultipartUpload ─→│
  │                              │←── 对象 versionId ──────────│
  │                              │─⑨ 整体 SHA-256 复核 ────────→│（流式扫描）
  │                              │─⑩ 本地事务：object+ref+outbox │
  │←── 上传完成（可播放状态=转码中）│                              │
```

### 聚合与不变量（照 `02` 的方法切）

| 聚合 | 不变量 | 守护方式 |
| --- | --- | --- |
| `UploadSession` | 一个 `uploadId` 只能属于一个 `(tenant, user, objectKey)`；`partSize` 在会话内**不可变** | 会话表带 `user_id`，所有 part 操作先校验归属；`partSize` 写入会话行，续传时比对客户端声明 |
| `Part` | 同一 `(uploadId, partNumber)` 至多一条有效记录，且其 `checksum` 与存储侧一致 | 主键 `(upload_id, part_no)` + upsert + 以存储侧 `ListParts` 为准 |
| `PhysicalObject` | `sha256 + size` 全局唯一；引用归零前不可删除 | 唯一索引 + 引用计数条件删除（§25.9） |
| `FileRef` | 一个用户的一条逻辑文件必须指向一个 `AVAILABLE` 的对象 | 状态机 + 秒传命中时的状态过滤 |

**注意 `uploadId` 的归属属于会话而不是用户**：把 `uploadId` 当成全局凭证（能拿到就用）是「分片被合到别人对象上」的唯一入口，而这类事故在日志里看起来完全正常。

## 25.5 分片策略：分片大小是一道成本方程，不是一个数字

### 先说一个反直觉的结论

**「分片越小、重传越省」是错的。** 设单分片失败率 `f`、文件大小 `S`、分片大小 `P`，则

```
分片数        N = ceil(S / P)
失败次数期望  N × f
单次失败损失  半个分片 P/2
期望重传浪费  E = N × f × P/2 = f × S / 2      ← 与 P 完全无关！
```

**每次失败损失半个分片，但失败次数与分片数成正比，两者互相抵消。** 决定 `P` 的是另外三笔账：

```
① 单片传输时间要足够长，让 TCP 慢启动摊薄（否则吞吐利用率 < 50%）
   P / BW_up ≥ 3 × RTT    且     P / BW_up ∈ [30s, 90s]（用户可感知的粒度）
② 请求固定开销随片数线性增长
   C(N) = N × (签名耗时 + 元数据写 + 存储 API 计费) ≈ N × 0.5 MB 当量
③ 存储硬约束（不可谈）
   5 MiB ≤ P ≤ 5 GiB，且 N ≤ 10,000  →  单对象上限 5 TiB
```

**取法**：`P* = clamp(BW_up × 45s, 5 MiB, min(5 GiB, BW_up × 120s, 512 MiB))`，再校验 `N ≤ 10,000`。

| 上行带宽 | `P*`（45 s 规则） | 4 GB 文件片数 | 结论 |
| --- | --- | --- | --- |
| 2 Mbps（弱网/移动） | 11 MB → 取 16 MB | 256 | 片多但单片小，续传粒度细 |
| 10 Mbps | 56 MB → 取 64 MB | 64 | **主力档位** |
| 50 Mbps | 281 MB → 取 256 MB | 16 | 大文件首选 |
| 500 Mbps（机房/专线） | 2.8 GB → **clamp 到 512 MB** | 8 | 再大就撞 10,000 片上限（20 PB 级） |
| 20 TB 单文件（极限） | 5 GiB × 10,000 片 | 上限 50 TiB | 只有直传 + 多做分段并行 |

### 并发与乱序

| 决策 | 取值 | 依据 |
| --- | --- | --- |
| 并发分片数 | 弱网 **4**，宽带上行 **8**，上限 16 | 并发收益在「填满上行」后迅速归零，而失败面线性放大；16 以上只增加客户端 CPU（并行算 CRC32C）与存储侧突发限流风险 |
| 乱序到达 | **允许，且必须允许** | `partNumber` 显式携带，`Complete` 时按号码排序；**绝不能用「到达顺序」当序号**，也不能用「最后成功的一片」推断进度 |
| 乱序下的一致性 | part 表主键 `(upload_id, part_no)` + upsert | 同一片重传就覆盖，天然满足乱序 + 幂等 |
| 会话内 `partSize` | 固定，写入会话行 | 允许变长时，续传会用新 `partSize` 切出与已传片**不对齐**的边界，合出一个「长度对、内容错」的文件——这是最难查的一类静默损坏 |
| 单用户并发限流 | 同一 `user_id` 同时在途会话 ≤ 4，同时在途 PUT ≤ 32 | 防单用户/脚本占满签名服务与存储突发额度（→ [15 限流](15-message-store.md)） |

## 25.6 分片幂等（核心一）：uploadId + partNumber + checksum

这一节是「断点续传」真正的地基。三条规则，缺一条就会出现引子里那种「看起来成功、内容错乱」。

### 幂等三要素

| 要素 | 作用 | 缺了会怎样 |
| --- | --- | --- |
| **`uploadId`** | 划定「一次上传的命名空间」，绑定 `(tenant, user, objectKey, partSize, declaredSha256)` | 分片被跨会话混用；严重时被合到他人对象（越权 + 数据污染） |
| **`partNumber`** | 分片在最终文件中的**位置**，也是幂等的第二主键 | 按到达顺序组装 → 顺序错乱；重传一片被计成两片 → 文件变长 |
| **单片 `checksum`（CRC32C / SHA-256）** | 证明「这一片的字节就是我以为的那一片」 | 传输出错或客户端 bug 时，坏片被合入且整体校验也过（若整体 hash 也来自同一客户端声明） |

**幂等规则清单（可直接写进接口契约）：**

1. 幂等键 = `(uploadId, partNumber)`；同一片重传 = **覆盖**，不是追加（对象存储的 `UploadPart` 语义天然如此）。
2. 覆盖时必须比对 `checksum`：同号不同内容 → 以最后一次为准，但**写审计**（这通常意味着两个客户端共用了一个 `uploadId`，是 bug 信号）。
3. `partNumber` 不可跳跃式信任：`Complete` 前必须 `ListParts` 与实际登记逐一比对，**片数不符直接拒绝**（不能"缺一片也合"）。
4. 客户端重试同一片必须带同一 `Content-MD5` / `x-amz-checksum-crc32c` 头，让**存储端**拒绝坏数据——传输层幂等 + 完整性双保险。
5. 会话状态机守护：`COMPLETED` / `ABORTED` / `EXPIRED` 的会话**拒绝任何 part 写入**（`WHERE status='UPLOADING'` 条件更新，影响 0 行即拒绝）。

### ETag 与 MD5 的关系（最容易踩的一格）

| 对象 | 实际计算方式 | 能校验什么 | **不能**用来做什么 |
| --- | --- | --- | --- |
| 单分片 ETag | `MD5(该片字节)`（未启用 SSE-KMS 时） | 单片完整性 | 不能代表整体文件 |
| 复合对象 ETag | `MD5(concat(各片二进制 MD5)) + "-" + 片数` | 只能证明「合并用了哪几片」 | **≠ 整体 MD5**，绝不能当秒传指纹 |
| 启用 SSE-KMS / SSE-C 后 | ETag **不是**明文 MD5 | 什么都校验不了 | 连分片校验都不能依赖它 |
| 自算 `CRC32C`（每片） | 客户端算，随 PUT 头上送 | 单片传输完整性（存储端可拒绝坏片） | 不能做身份（不抗碰撞） |
| 自算 `SHA-256`（整体） | 客户端算 + 服务端流式复算 | **唯一可做身份与秒传的指纹** | 慢，需并行/硬件加速 |

> 一条纪律：**ETag 只当「传输层凭据」用于对齐 `ListParts`，不当完整性契约、更不当身份。** 幂等与秒传的账，必须由自己算的 `CRC32C`（片级）+ `SHA-256`（对象级）承担。这一条在换存储厂商时能救你一次。

## 25.7 断点续传：把「已传了什么」变成可校验的事实

断点续传的全部难点是：**「客户端记得传过」不算数，「存储侧确实有且内容正确」才算数。**

### 持久化：三份数据，一个权威

| 数据 | 存哪 | 内容 | 丢了会怎样 |
| --- | --- | --- | --- |
| `upload_session` | MySQL | `upload_id PK, tenant_id, user_id, object_key, file_size, part_size, declared_sha256, status, created_at, expire_at` | 会话丢失 = 用户必须从头传 |
| `upload_part` | MySQL | `PK(upload_id, part_no), etag, crc32c, size, updated_at` | 无法快速算缺失片，只能全量 `ListParts` |
| 客户端本地（localStorage） | 客户端 | `upload_id` + 已成功片号 | **只用于加速，绝不作为权威**——客户端可以撒谎、可以被清缓存、可以多设备 |

**权威判定只有一条**：`服务端 part 表` ∩ `存储侧 ListParts` ∩ `checksum 一致`，三者取交集才算「已传」。

### 恢复流程（四步，任何一步失败都退化为「重传该片」而不是「重传整个文件」）

```
1. 客户端带 (declared_sha256, size) 或 upload_id 请求 Resume
   → 控制面校验归属（user_id 匹配）+ 会话未过期；不匹配一律 404（不泄漏存在性）
2. 服务端并行做两件事：
   a) ListParts(uploadId)        ← 存储侧事实
   b) SELECT ... FROM upload_part WHERE upload_id=?  ← 服务端记录
   取交集，且 etag/crc32c/size 三者全部一致，才算 VALID
3. 返回 { validParts[], missingParts[], partSize, 每片短效签名 URL（15 min） }
4. 客户端只传 missingParts；对 validParts 一律不重传
```

**为什么必须带「存储侧校对」这一层**：生命周期规则可能在 7 天后删掉未合并的分片，此时数据库里还留着「传过」的记录。只信数据库 → 续传后 `Complete` 报 `InvalidPart`，用户看到「传了 100% 却失败」，比从头传更伤。

### 未完成上传的生命周期（引子事故三的修复）

| 状态 | 进入条件 | 出口 | 保留期 |
| --- | --- | --- | --- |
| `UPLOADING` | `InitUpload` 成功 | `COMPLETED` / `ABORTED` / `EXPIRED` | — |
| `STALLED` | 30 分钟无新分片 | 回到 `UPLOADING`（续传） | 不独立清理 |
| `COMPLETED` | 合并 + 整体校验通过 | 终态 | 会话行保留 30 天（审计） |
| `EXPIRED` | `created_at + 7d`（可续期 1 次） | **`AbortMultipartUpload` + 删 part 行** | 分片立即释放 |
| `ABORTED` | 用户主动取消 / 校验失败 | 同上 | 同上 |

**清理必须双保险**：应用侧每日 GC 扫 `expire_at`（带审计、可观测水位）+ 存储侧 bucket lifecycle `AbortIncompleteMultipartUpload: 7 days`。只靠应用侧，一次发版事故就让 GC 停摆一年（引子事故三就是这么攒到 380 TB 的）。

## 25.8 秒传与去重（核心二）：指纹、算力与安全边界

### 指纹算法：为什么不能用 MD5，也不能用「采样」

| 算法 | 抗碰撞性 | 大文件吞吐 | 定位 |
| --- | --- | --- | --- |
| MD5 | **已破**（2017 实际碰撞、2020 起 chosen-prefix 碰撞可在普通 CPU 上小时级构造） | ~600 MB/s | ❌ 绝不能做身份 |
| SHA-1 | **已破**（SHAttered） | ~700 MB/s | ❌ |
| **SHA-256** | 抗碰撞（128 位安全强度） | 800 MB/s（有 SHA-NI）/ 200 MB/s（无） | ✅ **默认选择** |
| BLAKE3 | 抗碰撞（256 位） | 3~6 GB/s | ✅ 客户端可控时的更优解 |
| CRC32C | 不抗碰撞 | 10 GB/s | ✅ 片级传输校验，❌ 身份 |
| `size + 首尾 1 MB` 采样 | **不是哈希，是对手可控的选择器** | — | ❌ 引子事故二 |

**采样指纹为什么必然出事**：它不是「碰撞概率低」，而是「碰撞可以被**构造**」。同尺寸的模板类文件（PPT、合同、批量导出的报表）首尾高度相似，真实碰撞率远高于任何概率估算；再加上攻击者可以精确构造首尾字节。**用采样做身份，等于用一个可被任何人伪造的身份证。**

### 全量哈希算在哪：客户端算 vs 服务端算

| 位置 | 能否实现秒传 | 算力成本（对应 20 TB/天） | 可信度 | 结论 |
| --- | --- | --- | --- | --- |
| **客户端算（上传前）** | ✅ **唯一可能**——指纹要在传数据之前就有 | 0（用户设备） | 低（可谎报/可算错） | **秒传必须靠它**，但必须复核 |
| 服务端算（收到全量后） | ❌ 数据都传完了，秒传已无意义 | 231 MB/s 均值 ÷ 800 MB/s ≈ **0.3 核**，峰值 ≈ 1 核（很便宜！） | 高 | ✅ 只做**异步复核/兜底** |
| 分块并行 + Merkle 树 | ✅ 且支持未来的「只传变化块」 | 同客户端，可多核线性加速 | 低 | 留作演进，不在第一版做 |

**结论要写进设计**：客户端声明 `sha256 + size`，服务端**在合并后异步全量复算**。不一致 → 对象置 `QUARANTINED`、拒绝该文件的任何引用、对用户降权并告警。**没有这一步，「客户端声明指纹」就是一个可以污染全局去重表的写入接口**（攻击者可以声称「我这份是 X 的 hash」并上传任意内容，让后续合法用户秒传到被污染的对象）。

### 安全边界：秒传的四条铁律（事故二的正面修复）

1. **命中只能创建「引用」，绝不返回他人的 `file_id`**。返回的永远是本用户命名空间下的新逻辑文件 id。
2. **命中前必须过滤对象状态**：只有 `AVAILABLE` 可被引用；`QUARANTINED`（风控/审核拒）/ `ARCHIVED`（§25.12）/ `DELETING` 一律视为未命中。
3. **跨租户共享要由策略显式开启**。企业租户常要求「物理隔离」，此时去重表按 `tenant_id` 分区（去重率下降，但合规）。
4. **秒传接口不得成为「存在性预言机」**：未命中必须返回**统一措辞的 miss**（不区分「没有」和「无权」），并对 `(user, hash)` 查询限流；下载永远走短效签名 URL，不通过 hash 直接映射。

```java
// Java 骨架：秒传 —— 命中只建引用，绝不跨用户返回 file_id
@Service
public class InstantUploadService {

    @Transactional(rollbackFor = Exception.class)
    public FileRefDto tryInstant(long tenantId, long userId, String sha256, long size, String name) {
        PhysicalObject obj = objectMapper.selectBySha256(sha256, size);   // 物理层唯一索引
        if (obj == null || obj.getState() != State.AVAILABLE            // 状态过滤：不可用视为未命中
                || !scopePolicy.dedupAllowed(tenantId, obj)) {          // 租户策略：物理隔离要求
            return FileRefDto.miss();                                   // 统一 miss，不泄漏存在性
        }
        int hit = objectMapper.incRef(obj.getId());                      // UPDATE ... SET ref_cnt=ref_cnt+1
        if (hit == 0) {                                                  // 并发删除窗口：归零中
            return FileRefDto.miss();
        }
        FileRef ref = fileRefMapper.insert(FileRef.of(tenantId, userId, obj.getId(), name, sha256));
        auditMapper.insert(Audit.instant(userId, obj.getId(), ref.getFileId())); // 谁引用了谁，可追溯
        return FileRefDto.hit(ref.getFileId());                          // 只返回自己的逻辑文件 id
    }
}
```

## 25.9 引用计数、物理删除与孤儿回收

### 三种计数实现

| 实现 | 一致性 | 删除判定成本 | 崩法 |
| --- | --- | --- | --- |
| 纯 `COUNT(*)` 实时算 | 强 | 每次删除要扫引用索引，高并发下有窗口 | 删除风暴时 CPU 打满 |
| **计数列 + 定期对账**（选它） | 最终（对账收敛） | O(1) 条件更新 | 会漂移 → 必须每日对账修正 |
| 引用表 + 事件流聚合 | 最终 | O(1) | 实现最复杂，收益不成比例 |

选**计数列**：删除走 `UPDATE physical_object SET ref_cnt = ref_cnt - 1 WHERE id = ? AND ref_cnt > 0`，影响 0 行即说明已经归零（幂等）。同时每日跑一次全量对账：

```sql
-- 每日对账：找出计数漂移（差异 > 0 就告警，先修数再查因）
SELECT p.id, p.ref_cnt, COUNT(r.file_id) AS real_cnt
FROM physical_object p LEFT JOIN file_ref r ON r.object_id = p.id
WHERE p.state <> 'DELETING'
GROUP BY p.id, p.ref_cnt
HAVING p.ref_cnt <> real_cnt
LIMIT 1000;
```

### 为什么「归零」不能立刻删：三个真实理由

1. **在途引用**：转码任务、审核任务、CDN 回源、客户端并发下载都在读，它们的引用不体现在 `file_ref` 里。
2. **签名 URL 尚在有效期**：15 分钟内还有效，删了就是「刚点开就 404」。
3. **回收站语义**：用户「删除」只把 `file_ref.state` 改成 `TRASH`，**仍计入引用**；只有回收站 30 天过期后才真正 -1。否则一次误删就成了物理事故。

**删除漏斗**：`ref_cnt = 0` → `pending_delete`（延迟 **24 小时**）→ GC 二次确认（仍为 0、无活跃签名 URL、无在途任务）→ 标 `DELETING` → 物理删除（存储侧软删保留 7 天）→ 记审计。整个链条上任何一步失败都可重入，因为**每一步都是幂等的状态迁移**。

### 三类 GC 任务（引子事故三与「对象泄漏」的兜底）

| 任务 | 判据 | 动作 | 频率 |
| --- | --- | --- | --- |
| 孤儿对象回收（有对象无引用） | 合并完成 > 1 h 且 `ref_cnt = 0` 且无任何 `file_ref` | 标 `DELETING` → 7 天后删（等可能的补偿事务） | 每日 |
| 悬空引用（有引用无对象） | `file_ref.object_id` 在对象表/存储侧均不存在 | 置 `ERROR` + 告警 + 从备份恢复或通知用户重传 | 每小时抽样 / 每日全量 |
| 计数漂移修复 | 对账 `ref_cnt <> COUNT(*)` | 直接以 `COUNT(*)` 为准修正 + 查因 | 每日 |
| 僵尸 multipart | `ListMultipartUploads` 与应用会话表差集 | `AbortMultipartUpload` + 删 part 行 | 每日 |

> 一条经验：**孤儿回收一定要在「合并完成后等 1 小时」再动**。因为「存储侧 Complete 成功、应用侧本地事务失败」这个窗口是真实存在的，而补偿事务可能就排在 30 秒后。抢着删等于制造 100% 复现的「上传成功但文件没了」。

## 25.10 合并与整体校验：校验通过之后才算上传成功

合并（`CompleteMultipartUpload`）是整个流程里**唯一不可回滚、且账单最大**的动作：它一旦成功，分片就被消费掉了。

### 一次正确的合并顺序（四步，顺序不能换）

```
① 分片级校验   ListParts ∩ 应用 part 表，逐片比对 checksum 与 size
                ↳ 不通过：会话置 FAILED，客户端只重传缺失/损坏片（分片还在）
② 原子合并     CompleteMultipartUpload(uploadId, parts[])
                ↳ 存储侧原子：要么对象可见，要么完全不可见；同 uploadId 重试幂等
③ 整体校验     流式 SHA-256 扫一遍对象，比对 declaredSha256 + size（ETag 不可信）
                ↳ 不通过：删除对象 + 会话 FAILED（分片已被消费，必须重传整个文件）
④ 本地事务     physical_object + file_ref + outbox(转码事件) 同一事务提交
                ↳ 不通过：对象已存在但无引用 → 交给 §25.9 的孤儿回收（等 1h）
```

**「上传成功」这个响应，必须来自第 ④ 步提交之后**，而不是第 ② 步。否则客户端立刻播放会 404，而这条 404 在日志里会被归因成「CDN 问题」，排查三天。

```go
// Go 骨架：分片合并 + 双层校验（完整 DDL / 重试矩阵见 26 附录 A）
func (s *Merger) Complete(ctx context.Context, uploadID string) (*Object, error) {
	sess, err := s.sess.Get(ctx, uploadID)                        // ① 归属 + 状态守护
	if err != nil || sess.Expired() || sess.Status != StatusUploading {
		return nil, ErrUploadGone
	}
	parts, err := s.storage.ListParts(ctx, sess.ObjectKey, uploadID) // 以存储侧为准
	if err != nil || len(parts) != sess.PartCount {
		return nil, ErrPartMissing
	}
	for _, p := range parts {                                     // ② 分片级校验
		rec := sess.Parts[p.No]
		if rec == nil || rec.CRC32C != p.CRC32C || rec.Size != p.Size {
			return nil, ErrPartCorrupted
		}
	}
	obj, err := s.storage.Complete(ctx, sess.ObjectKey, uploadID, parts) // ③ 原子合并（幂等）
	if err != nil {
		return nil, err
	}
	sum, size, err := s.storage.StreamSHA256(ctx, obj.Key)        // ④ 整体校验
	if err != nil || sum != sess.DeclaredSHA256 || size != sess.FileSize {
		_ = s.storage.Delete(ctx, obj.Key)                        // 回滚：分片已消费，只能重传
		s.sess.MarkFailed(ctx, uploadID, "HASH_MISMATCH")          // 客户端需重新 InitUpload
		return nil, ErrHashMismatch
	}
	return s.persist(ctx, sess, obj, sum)                         // ⑤ object+ref+outbox 同事务
}
```

### 失败点与补偿（这张表决定你半夜要不要起来）

| 失败点 | 现场状态 | 能否回滚 | 补偿动作 |
| --- | --- | --- | --- |
| 分片校验不通过 | 分片完好，会话 `UPLOADING` | ✅ 完全可回滚 | 只重传坏片，进度 0 损失 |
| `Complete` 调用失败 | 分片完好 | ✅ | **同 `uploadId` 重试**（幂等），不要 abort 重建 |
| `Complete` 成功、本地事务失败 | 对象存在、无引用 | ⚠️ 只能事后清 | 客户端收到失败 → 重试会命中 `uploadId` 已消费 → 孤儿回收兜底 |
| 整体校验不通过 | 对象可见、内容错、分片已消费 | ❌ 不可回滚 | 立即删对象 + 会话 FAILED + 全量重传 + 告警（这是高危信号：传输层或客户端算 hash 有 bug） |
| 转码事件发送失败 | 对象与引用正常 | ✅ | Outbox 保证最终投递（→ `eng/10`）；用户看到「处理中」 |

**能用一张表总结的一句话**：**校验放在合并之前能救带宽，校验放在合并之后能救数据；两个都要做，因为它们防的是不同的东西**（前者防「坏片进合并」，后者防「组装错误/漏片/客户端谎报」）。

## 25.11 转码流水线：上传成功 ≠ 可用

引子里事故二的同族问题是：**指纹命中了、文件也在了，但用户点开是黑屏**——因为源文件是 HEVC/MOV/25 Mbps，而浏览器要 H.264/MP4/3 Mbps。**「上传成功」只是把字节搬进来了，「可用」是一条异步流水线的输出。**

### 转码状态机

```
        ┌────────────┐  合并 + 整体校验通过，physical_object 落库
        │  UPLOADED  │
        └─────┬──────┘
              │ outbox → MQ（分区键 = object_id，幂等键 = (object_id, profile, ver)）
              ▼
        ┌────────────┐  重复投递 → 幂等命中 → 直接 ACK（不重复转码）
        │   QUEUED   │  优先级：付费租户 > 小文件 > "首帧档位"先行
        └─────┬──────┘
              │ worker 认领（租约 15 min，过期可被抢占 → 天然防卡死）
              ▼
        ┌─────────────┐ 失败 → 指数退避 3 次 → 回 QUEUED
        │ TRANSCODING │ ────────────────────────────────┐
        └─────┬───────┘ 超时（> 2× 预估耗时）→ 杀 worker ┘
              │ 全部 profile 产出完成
              ▼
        ┌────────────┐  机器审核（抽帧 + ASR + 指纹比对）→ 命中风险 → 人工队列
        │  AUDITING  │
        └─────┬──────┘
        通过  │  拒绝
              ▼        ▼
        ┌──────────┐  ┌────────────┐
        │  READY   │  │  REJECTED  │  对象 → QUARANTINED，秒传不可引用（§25.8 铁律 2）
        └────┬─────┘  └────────────┘
             │ 30 / 90 / 180 天无访问
             ▼
        ┌──────────┐
        │ ARCHIVED │  此时秒传必须视为未命中（§25.12）
        └──────────┘

  旁路：FAILED（重复失败 5 次）→ DLQ + 告警 + 用户可手动重试；不阻塞其他对象
```

| 状态 | 进入条件 | 超时 | 重试 | 关键约束 |
| --- | --- | --- | --- | --- |
| `QUEUED` | outbox 投递成功 | 队列 lag > 15 min 即告警 | — | 排队时长必须按**优先级分档**，不能单一 FIFO |
| `TRANSCODING` | worker 拿到租约 | `2 × 预估时长`（按时长×码率估） | 3 次退避 | 幂等：输出 key = `f(sha256, profile, ver)`，重跑覆盖同一 key |
| `AUDITING` | 全部 profile 完成 | 30 min（人工队列 24 h） | 1 次 | 审核不通过 → 对象隔离，**不是删**（保留证据链） |
| `READY` | 审核通过 | — | — | 只有 `READY` 才能出现在用户的「可播放」视图里 |
| `FAILED` | 重试耗尽 | — | 用户可手动触发一次全链路重试 | 毒任务隔离：`(profile, 编码组合)` 维度熔断 |

**三个设计要点：**

1. **首帧优先**：先只跑最低档（480p/单格式）让「可播放」P95 < 30 秒，其余档位后台补。**用户感知的「可用」是被最低档定义的**，不是被 4K 定义的。
2. **幂等键必须带 `profile_version`**：编码参数升级时，新对象用新版本，历史对象按需回填——而不是「全量重转 500 PB」（→ [07 变更治理](07-change-governance.md)）。
3. **算力不是瓶颈，队列抖动才是**：20 TB/天对应的转码算力只有约 **292 vCPU 均值**（§25.12 推导），但晚 8–11 点的上传尖峰会让队列 lag 从 0 涨到 30 分钟。所以要**弹性队列 + 分档优先级 + 峰值预扩容**，而不是加机器。

### 访问控制：签名 URL、防盗链、私有桶

| 通道 | 泄漏面 | 正确做法 |
| --- | --- | --- |
| 私有桶 + 服务端签名 URL | URL 即凭证，落日志/被转发即扩散 | 有效期 **≤ 15 min**，绑定 `(object_key, user_id, exp)`，**URL 不落访问日志** |
| CDN + 鉴权 key（时间戳 + 密钥） | 密钥泄露即全站可盗 | 密钥轮换 + 路径级鉴权 + 回源校验，适合播放类大流量 |
| STS 临时凭证（客户端直传） | 权限过大 = 整个 bucket 可写 | 最小权限收敛到 `prefix = u/{tenant}/{uploadId}/*` + 15 min + 限定大小 |
| 永久公开 URL / 公开 list | 全站抓取，且**枚举即泄漏** | **禁止**：bucket 全私有，关 list 权限 |
| 秒传查询接口（`POST /exists`） | 变成「他人文件存在性预言机」 | 统一 miss 措辞 + 限流 + 只返回本租户视角 |

三条纪律：**① 对象 key 不可枚举**（用 `u/{sha256前2位}/{uuid}`，而不是 `user_123/课程合同.pdf`）；**② 防盗链三层递进**（Referer 白名单 → 时间戳签名 → 一次性 token），Referer 只是止血带不是锁；**③ 鉴权失败与不存在返回同一个状态码**，否则 403/404 的差异本身就是信息泄漏。

## 25.12 存储分层与成本算例：钱不在存，也不在传，在出网

### 分层规则与取回成本（取回也要钱，而且很贵）

| 层 | 单价（元/GB/月） | 最小存储期 | 取回延迟 | 取回费（元/GB） |
| --- | --- | --- | --- | --- |
| 标准 | 0.120 | 无 | 毫秒 | 0 |
| 低频 | 0.080 | 30 天 | 毫秒 | 0.02 |
| 归档 | 0.033 | 90 天 | 分钟 ~ 1 小时 | 0.06 |
| 深度归档 | 0.011 | 180 天 | 3 ~ 12 小时 | 0.06（加急另计） |

```
盈亏平衡取回次数   k* = (标准价 - 归档价) × 持有月数 / 取回单价
1 TB 对象持有 12 个月：
  k* = (0.120 - 0.011) × 12 / 0.06 = 21.8 次
  → 一年内被取回超过 22 次，深度归档反而更贵（还算上 12 小时延迟）
1 TB 对象持有 36 个月：
  k* = (0.120 - 0.011) × 36 / 0.06 = 65 次
```

**转换规则（三条硬约束）：**

1. **以「对象级最近访问时间」为准，不是文件级**——共享对象被任一引用者访问即刷新（这正是引用计数模型的副产品）。
2. **秒传可能命中的对象禁止归档**：`ref_cnt > 1`（多用户共享）或 90 天内被访问过的对象，一律留在标准/低频。否则用户秒传成功、点开却要等 12 小时——**秒传成功但打不开，比秒传失败更糟**（本篇唯一真问题的反例）。
3. **冷热判定要留「回温通道」**：归档对象若被访问，立即触发取回 + 拉回标准层（成本一次性，延迟可接受）；连续 3 次回温的对象打标「禁止再分层」。

### 日上传 20 TB 的成本算例

```
输入：
  日上传 20 TB，平均文件 20 MB → 1.02 M 个/天
  秒传命中 30% → 物理写入 14 TB/天 → 5,110 TB/年，年均在库 ≈ 2,555 TB
  视频占 30% → 4.2 TB/天；按 12 Mbps 源码率 → 778 小时素材/天
  转码 6 个输出档（3 分辨率 × 2 格式），1.5 vCPU·h / 素材小时 / 档
  播放倍数 25（视频被平均看 25 遍）→ 下行 4.2 TB × 25 = 105 TB/天
```

| 成本项 | 单价 | 用量 | 年成本 |
| --- | --- | --- | --- |
| 入站（上传到对象存储） | 0 | 20 TB/天 | **0** |
| 反例：服务端中转的网络成本 | 0.8 元/GB（出网折算，自建专线同量级） | 20 TB/天 | **598 万元** ← 直传的第一理由 |
| 存储（全标准，未分层） | 0.120 元/GB/月 | 年均 2,555 TB | 368 万元 |
| 存储（分层后，综合 0.084） | 40% 标准 / 35% 低频 / 25% 归档 | 同上 | **259 万元** |
| 转码算力 | 0.1 元/vCPU·h | 778 h × 6 档 × 1.5 = 7,002 vCPU·h/天（≈292 vCPU 均值） | **25.6 万元** |
| CDN 下行 | 0.2 元/GB | 105 TB/天 | **766 万元** |
| API 请求费 | 0.01 元/万次 | 4.1 M 分片 PUT + 读请求 | < 1 万元 |
| **合计** | | | **≈ 1,050 万元/年** |

**读这张表只需要三句话：**

1. **上传本身几乎不要钱**（入站免费），所以「重传 6 次浪费带宽」浪费的是**用户的时间和客户端流量**，不是你的账单——但**如果你选了中转形态，它就是 598 万元/年**。
2. **存储被分层砍掉 30%，转码便宜到可以忽略（2.4%）**，而**下行占了 73%**。所以优化顺序是：先做 CDN 命中率，再谈分层，最后才谈去重。
3. **转码算力真的便宜**（`7,002 vCPU·h/天 × 0.1 元 ≈ 700 元/天`），**别为了省转码去让用户体验不可播的文件**——这是最典型的「省小钱赔体验」。

### 去重率对成本的影响（评审会上最常被算错的一笔账）

| 去重率 | 物理写入 | 存储/年 | 转码/年 | 下行/年 | 合计 | 相对 0% |
| --- | --- | --- | --- | --- | --- | --- |
| 0% | 20 TB/天 | 368 万 | 36.6 万 | 766 万 | 1,172 万 | — |
| **30%（本算例）** | 14 TB/天 | 259 万 | 25.6 万 | 766 万 | **1,051 万** | −10.3% |
| 60% | 8 TB/天 | 147 万 | 14.6 万 | 766 万 | 929 万 | −20.7% |
| 80% | 4 TB/天 | 74 万 | 7.3 万 | 766 万 | 848 万 | −27.6% |

**结论（值得在评审会上念一遍）：去重率从 0 拉到 80%，总成本只降 27.6%，因为最大的那块（下行）跟去重毫无关系。** 所以：

- **秒传的价值不是「省一半存储」**，而是**体验**（4 GB 素材 0.2 秒完成 vs 4.5 小时）和**抑制重复上传的合规/版权风险**。
- 反过来，**去重率是「被上传内容的结构」决定的，不是你能优化出来的**——模板类业务天然 60~80%，UGC 视频天然 10% 以下。**别把它写进成本优化 KPI。**

## 25.13 L0 → L5：六次换挡与换挡信号

| 阶段 | 形态 | 容量 | **换挡信号（硬阈值）** | 代价 |
| --- | --- | --- | --- | --- |
| L0 | 服务端中转 + 单次 PUT + 本地磁盘 | 日 10 GB，单文件 ≤ 100 MB | 单请求超时率 > 1% / 磁盘 > 80% | 单点、不可扩容 |
| L1 | 对象存储 + 预签名直传（单对象 PUT） | 日 100 GB，≤ 5 GB | **重传率 > 10%** / 上传 P95 > 5 min | 无断点，弱网用户体验崩 |
| L2 | 分片 + 断点续传 + part 表 | 日 1 TB | 会话表 > 1,000 万行 / 分片 PUT > 500/s | 状态机复杂度跳一级；僵尸分片出现 |
| L3 | **分片幂等 + SHA-256 秒传 + 引用计数 + 异步转码** | 日 10 TB | 转码 lag > 15 min / 孤儿对象 > 0.1% / 计数漂移 > 0 | 越权风险面（必须做 §25.8 铁律） |
| L4 | 上传控制面独立 + 元数据按 `user_id` 分片 + 弹性转码队列 + CDN 签名 | 日 100 TB | 单表 > 50 GB / 单区域出口 > 40% / 签名 QPS > 5k | 跨片查询全废；分层与对账成本 |
| L5 | 多区域多活 + 边缘接入加速 + 冷热分层 + 按租户物理隔离 | 日 1 PB | 跨区 RTT > 80 ms / 归档取回 SLA 破 / 单租户占比 > 30% | 一致性、副本成本、去重率下降 |

**当前（日 20 TB）落在 L3 与 L4 之间。重点说 L2→L3 这一步，因为它是最容易被跳过、也最致命的一步：**

很多系统「分片 + 断点续传」做完就以为完事了（L2），而 **L3 才是从「能传」到「正确且省钱」的分界**：幂等（不损坏）、秒传（不白传）、引用计数（不乱删）、异步转码（不是传完就打不开）。跳过的代价不是性能，而是**数据事故**（引子事故二）。

**不要跳级的具体例子**：没有引用计数就直接上「跨租户秒传」，等于把去重表做成越权下载器；没有整体校验就上「分片并行 + 大分片」，等于把静默损坏的概率乘上片数。

## 25.14 这个形态特有的崩法

不是「高可用」套话，是上传系统自己的失效点：

| 失效 | 长什么样 | 定位方法 | 预防 |
| --- | --- | --- | --- |
| **分片被生命周期提前删** | 续传显示 92% 但 `Complete` 报 `InvalidPart` | 比对 `upload_part` 行与 `ListParts` 差集 | 恢复时以存储侧为准（§25.7）；会话 TTL ≤ 分片 TTL |
| **`uploadId` 跨用户复用** | 用户 A 的分片被合进 B 的对象（数据污染 + 越权） | 审计 `upload_session.user_id` 与 `physical_object` 的 owner 链 | `uploadId` 绑定 `(tenant,user,objectKey)`，每次 part 操作校验归属 |
| **计数漂移** | 对象永不删除（存储缓慢泄漏），或提前删除（用户文件 404） | 每日 `ref_cnt vs COUNT(*)` 对账 | 对账任务 + 归零后延迟 24h + 二次确认 |
| **秒传热键** | 一个爆款模板被 10 万人同时秒传，单行 `ref_cnt` 锁冲突 | 按 `object_id` 聚合的锁等待与重试率 | 计数分桶（`ref_cnt_0..7`）或异步合并计数 |
| **毒转码任务** | 某个 `(profile, 编码组合)` 必崩，worker 无限重试打满 GPU | 按 `(profile, error_code)` 聚合的失败率 | 5 次即 DLQ + 该维度熔断（→ `eng/18`） |
| **归档对象被秒传命中** | 秒传 0.2 s 成功，点开转圈 12 小时 | 秒传命中后按 `state` 过滤的埋点 | 归档对象视为未命中（§25.12 规则 2） |
| **签名 URL 扩散** | 某下载链接在外部论坛被批量抓取 | CDN 日志中同一 URL 的独立 IP 数 | 15 min 短效 + 绑定 `user_id` + 一次性 token + 限速 |
| **客户端谎报 hash** | 去重表被污染，后续合法用户秒传到错内容 | 异步复核 `SHA-256` 不一致率（应恒为 0） | 100% 异步全量复核 + `QUARANTINED` + 用户降权 |
| **僵尸 multipart** | 存储成本每月缓慢上涨，控制台看不到 | `ListMultipartUploads` 与桶明细的年龄分布 | 应用侧 GC + bucket lifecycle 双保险（事故三） |

## 25.15 砍掉 90% 预算还能不能跑

日 20 TB 的集群砍到 1/10：机器从 200 台到 20 台、转码队列从 730 vCPU 到 70、CDN 换回源站直出。

| 保留 | 砍掉 | 后果 |
| --- | --- | --- |
| **分片幂等**（`uploadId + partNumber + checksum`） | 并行 8 分片 → 4 分片、大文件提速优化 | 上传慢 1.5 倍，**不损坏** |
| **SHA-256 指纹 + 授权校验** | 跨租户共享（只做同租户/同用户去重） | 去重率从 30% 掉到 8%，存储涨 20%，**不越权** |
| **引用计数 + 延迟删除** | 分层归档、冷热回温、每日对账改每周 | 存储成本涨 30%，对象泄漏风险上升但可控 |
| 单档转码（480p/MP4）+ 异步审核 | 6 档多分辨率、GPU 加速、首帧优先 | 移动端体验下降，**文件仍可播放** |
| 预签名直传（保留）+ 源站直出 | CDN、签名 CDN 鉴权、防盗链三层 | 下行成本涨 2~3 倍，**防盗链退化为弱保护**（可接受） |
| 应用侧每日 GC（保留） | 独立上传控制面、元数据分片、多活 | 单库可撑到日 2 TB 元数据量 |

**结论：这个系统的必需品只有三样——分片幂等、SHA-256 指纹 + 授权校验、引用计数。** 其余（多档转码、分层、CDN、控制面拆分）全是量级或成本驱动的优化。每次评审都问一遍「哪三个是必需品、砍掉哪个会出数据事故」，比问「你用不用 Kafka」有用得多。

## 25.16 十分钟答题卡

被要求现场设计「大文件上传/断点续传」时，按这个顺序讲，不要从「我用 OSS SDK」开始：

```
1  量级    日 20TB → 231 MB/s 均值、5.7 Gbps 峰值；会话 71/s，分片 PUT 285/s
2  真问题  断点续传 = 分片幂等 + 指纹去重 + 异步转码，缺一件 = 浪费带宽 / 损坏 / 打不开
3  协议    客户端直传（预签名 URL）；中转只在「写前必须审核」时局部用
4  分片     P* = clamp(BW_up × 45s, 5MiB, min(5GiB, 512MiB))，校验 N ≤ 10,000
5  幂等     键 = (uploadId, partNumber) + 单片 CRC32C；ETag ≠ MD5，绝不当身份
6  续传     以「存储侧 ListParts ∩ 应用 part 表」为准；7 天 TTL + 双保险清理
7  秒传     SHA-256（禁 MD5/采样）+ 客户端算 + 服务端异步复核；命中只建引用
8  安全     命中≠有权：只返回本用户 file_id；状态过滤；统一 miss；防存在性预言机
9  合并     分片校验 → 原子 Complete → 整体 SHA-256 → 本地事务；成功响应在事务后
10 归属     physical_object(sha256 唯一) + file_ref(N:1) + ref_cnt 归零延迟 24h 删
11 流水线   UPLOADED→QUEUED→TRANSCODING→AUDITING→READY；首帧优先；幂等 key 带 profile_version
12 算账     钱在出网（73%），不在存也不在传；去重率 0→80% 只降总成本 28%
13 换挡     重传率>10% → L2；转码 lag>15min / 孤儿>0.1% → L3→L4；单表>50GB → 分片
14 必需     分片幂等、SHA-256+授权、引用计数 —— 其余都是量级驱动
```
