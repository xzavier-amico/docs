## 10.1 引子：两个「演习时全绿、真出事全黑」的事故

### 事故一：双写两地，同一笔订单被扣了两次钱（2025-04-18）

某电商把订单库改成「华东 + 华北双写、双向同步」，目标是 RTO < 5 分钟。同步用的是行级 LWW（Last-Write-Wins，按 `updated_at` 比较），主键是各机房**本地自增**。

| 时间 | 事件 | 数据 |
| --- | --- | --- |
| 04-18 20:00 | 大促预热，网关超时重试率升到 0.7%（平时 0.02%） | 重试 4.1 万次 |
| 20:00–23:59 | 同一 `request_id` 的重试被 LB 打到两地，**两地本地唯一键各自通过**，用户在两地各生成一单（本地自增主键、业务单号相同），各扣 1,099 元 | 双写订单 12,400 笔 |
| 20:14–24:00 | `coupon_usage` 表两边各插一条，券池被核销 3 次 | 券超发 9 张 |
| 次日 09:30 | T+1 对账发现「渠道实收 ≠ 订单应收」 | 差异 3,100 笔 |
| 次日 10:00–04-25 | 逐笔退款 + 客服外呼 + 券池冲正 | 多扣金额 **412 万元**，赔付与商誉 **38 万元**，投诉 2,180 起 |

根因三条同时成立：**双写当多活**（两地都是写入口）、**没有冲突解决策略**（只有 LWW 覆盖，而对"增量"用"覆盖"等于丢一笔）、**主键本地自增**（唯一键在本地生效，在全局不生效）。这三条在 §10.12 的反模式表里都各占一行。

> 🩸 最反直觉的一点：双写跑了 4 个月没出事——它只在**重试率异常 × 两地都被打中**的交叉点出错，而这个交叉点只在故障或大促时出现。

### 事故二：切流成功，回切丢了 3 小时订单（2025-07-09）

同一套系统。华东机房交换机故障，14:02 起大量连接超时。

| 时间 | 事件 | 数据 |
| --- | --- | --- |
| 14:02 | 华东机房网络故障，订单接口超时率 68% | — |
| 14:10 | 值班按 runbook 切流：摘华东、华北接写（**切换本身是完全成功的**） | 切换耗时 8 分钟 |
| 14:10–17:40 | 华北独立承接全部写入，产生订单 41,600 笔（已支付 28,300 笔，916 万元） | 3 小时 30 分 |
| 17:38 | 华东恢复，运维决定回切 | — |
| 17:52 | 配反向复制 `华北 → 华东`，**位点用了故障前的快照，且方向照抄 runbook 写成了 `华东 → 华北`** | 配错 |
| 18:20 | 流量回切华东，华东以 13:00 的旧数据对外服务 | — |
| 19:10 | 监控发现华北 41,600 笔订单"消失"——实为被华东旧数据覆盖 | 丢失 41,600 笔 |
| 19:40 | 停写排查，想从备份恢复：备份是 13:00 的，无故障期间数据 | 备份无效 |
| 次日 09:30 | 取渠道 T+1 对账单逐笔补单，人工 5 天 | 补单 27,900 笔，退款 3,400 笔 |
| — | 合计：丢失订单 41,600 笔 / 金额 **1,340 万元**，无法补单退款 **112 万元**，赔付 **46 万元** | 影响用户 3.2 万人 |

**切换是成功的，回切是灾难。** 不是运气：切换有 runbook、有演练、有指标；回切没有独立 runbook、没有演练（"反过来做一遍"）、没有数据对齐校验。**团队把 100% 的演练预算花在那 8 分钟上，事故却发生在接下来的 90 分钟里。**

## 10.2 到底是什么：四个容易被混淆的词（问①）

先把定义钉死，反例比定义更有用。

| 词 | 精确定义 | 一个反例（它**不是**） |
| --- | --- | --- |
| **容灾 DR** | **冷或温**副本，故障后**人工**提升为生产，允许 RTO 分钟到小时、RPO≠0 | 「有异地备份」≠ 容灾：备份是给"误删"用的，通常不能直接对外服务 |
| **双活（同城）** | 两故障域**同时对外服务**，共享一份同步复制数据，同一时刻只有一侧处理某个 key 的写 | 「两地都部署了一套」≠ 双活：两边都能独立写同一行，那叫**双写** |
| **两地三中心** | 生产城（两机房同步）+ 异地灾备（异步），异地**不带流量或只带只读流量** | 「异地也接 5% 流量」≠ 三中心：异地一旦接受写入，就是 §10.8 的双向同步问题 |
| **单元化 Cell** | 按**用户维度**切成 N 个**自闭环**单元，每个用户的写入永远只落一个单元 | 「按业务模块拆服务」≠ 单元化：单元内是**全栈同构**，单元间只有只读与异步 |

> **一句话区分**：双活是「两机房、一份数据、**同一行只有一个所有者**」；双写是「两机房、两份数据、**谁写都算数**」。前者是架构，后者是事故的现在进行时。

## 10.3 唯一真问题（问②）

> **多活的难点不是"数据同步"，而是故障切换那一刻的脑裂、写冲突与路由漂移——平时都能跑通，出事的永远是切换和回切的那 10 分钟。**

这个论断有一个可验证的推论：若难点是"数据同步"，优化目标是吞吐、平时就能发现问题、验证方式是压测链路、责任人归中间件团队；若难点是"切换那一刻"，优化目标就变成**决策正确性**、**平时永远发现不了**、验证方式是**杀机房 + 杀时钟 + 杀路由表**、责任人是**架构师 + 值班长**。由此推出本篇全部四个设计：

| 从「切换那一刻才出事」推出的约束 | 推出的设计 |
| --- | --- |
| 两侧都自认为该服务 → 必须有**外部裁判** | 租约 / 多数派 / witness（§10.9） |
| 冲突平时是 0、切换窗口是 100% | 冲突解决必须在**建模阶段**定（§10.8） |
| 路由表挂了 = 全站挂 | 多级缓存 + 兜底单元（§10.7） |
| 回切是反向的第一次切换，从未演练 | 独立 runbook + 校验清单（§10.10） |

## 10.4 四档容灾：一张必须在评审桌上摊开的表（问④）

这是本篇的核心。**任何"我们要做多活"的提案，先让它填完这张表。**

```
① 单活（单地域多 AZ）                  ② 同城双活（同城两机房一份数据）
 ┌──────── 地域 A ────────┐            ┌───── 城市 A ─────────────────┐
 │ AZ-1 生产 ─异步→ AZ-2  │            │ 机房1 ═══同步 1ms═══ 机房2   │

                                       └──────────────────────────────┘

③ 两地三中心（生产城双机房 + 异城灾备）
 ┌─ 城市A 生产城 ─┐  ┌─ 城市B 灾备 ─┐
 │ 机房1 ══ 机房2  │→ │ 机房3 只读/冷 │
 │ （同步 RPO=0）  │异步│ RPO 秒–分钟  │
 └────────────────┘30-80└─────────────┘

④ 单元化多活（每单元全栈同构 · 按用户分片 · 写只写本单元）
   U1 上海            U2 北京            U3 深圳
 ┌──────────┐      ┌──────────┐      ┌──────────┐
 │网关 / App │      │网关 / App │      │网关 / App │
 │DB主从     │      │DB主从     │      │DB主从     │

 └────┬─────┘      └────┬─────┘      └────┬─────┘
      └────────→ 全局只读副本 / 数仓 ←──────┘

 RTO  ① 30 min–4 h   ② 1–5 min    ③ 30 min–2 h   ④ 30 s–3 min（按单元切）
 RPO  ① 5–30 min     ② 0 / 秒级   ③ 秒–分钟      ④ 0（单元内闭环）

```

| 档 | RTO | RPO | 成本倍数 | 能扛什么故障 | **不能扛什么故障** | 典型公司规模 |
| --- | --- | --- | --- | --- | --- | --- |
| **单活** | 30 min–4 h | 5–30 min | **1.0x** | 单机宕、单实例 OOM、单 AZ 抖动（切 AZ 内备用） | 机房断电、城域网割接、地域级灾害；**故障期间写入全丢** | < 100 人研发，日订单 < 10 万 |
| **同城双活** | 1–5 min | 0 或秒级 | **1.8–2.2x** | 单机房火灾/断电/水淹、单 AZ 网络隔离、单实例零感知 | **城市级灾害**（洪水、区域电网、骨干网割接）；同城两机房共享的**汇聚点/波分** | 中型，日订单 10–50 万 |
| **两地三中心** | 30 min–2 h（人工决策） | 秒–分钟 | **2.5–3.5x** | 城市级灾害、区域断电、同城双机房同时不可用 | 异地切换窗口内的写入（RPO≠0，**必然丢一段**）；"只备不练"站起来跑不动 | 大型/金融/政务，日订单 50–300 万 |
| **单元化多活** | 30 s–3 min（**按单元切**） | 0（单元内闭环） | **3.5–5x** | 地域级故障 + 容量线性扩展 + 按地域/用户灰度 + 单单元隔离爆炸半径 | **跨单元全局强一致**（不存在）；路由表本身单点；单个超大租户超过单元容量 | 超大型，日订单 > 300 万 / 亿级用户 |

**两处最该被追问**：① **成本倍数怎么算的**——不是 2x，同城双活按"剩余一侧能否扛全量"配容量，再加同步写放大与双份监控才到 1.8–2.2x。② **"不能扛"那列写不出东西说明没想透**，等于宣称零故障，评审直接打回。另外，一家公司可以分档：订单库单元化、商品库同城双活、报表单活，比"全站上单元化"便宜 3 倍。

## 10.5 量级与预算：把跨地域的账算到毫秒和元（问③）

多活最容易变成"信仰决策"，因为它没有可算的数。这一段把数算出来。

### 延迟预算：物理下限不可谈判

| 距离 | 光纤 RTT 下限 | 工程实测 P99 | 含义 |
| --- | --- | --- | --- |
| 同 AZ | 0.1 ms | 0.2–0.5 ms | 可放进同步复制路径 |
| 同城跨 AZ | 0.2 ms | **1 ms** | 同步复制可行（RPO=0 的真正边界） |
| 跨城 1,000–1,500 km | 12–18 ms | **30–45 ms** | 只能异步；同步复制把写 P99 拉到 100 ms+ |
| 跨城 2,000 km+ | 20 ms | **50–80 ms** | 同上，抖动更大 |
| 跨国（中美） | 130 ms | **150–300 ms** | 任何同步方案不可行 |

**推导式（写路径）**：一次下单写涉及 5 次跨城往返（读商品 → 扣库存 → 建订单 → 写支付 → 发事件）。

```
同城双活 5 × 1 ms = 5 ms（无感）｜跨城写 5 × 40 ms = 200 ms + 最慢分片 ≈ 260 ms（转化率降 3–5%）
跨国 5 × 200 ms = 1,000 ms（不可接受，实测阈值：> 150 ms 开始掉转化）
```

**结论：RPO=0 只能在同城尺度买到。宣称"跨城 RPO=0"的方案，要么在骗你，要么每次写塞了 100 ms 以上等待。** 跨城要 RPO=0 的唯一解法是单元化——单元内闭环，跨城根本不发生同步写。

### 带宽账与路由表容量账

```
同步带宽 8 万条/s × 600 B = 48 MB/s = 384 Mbps → 跨城 ≥ 1 Gbps 双线 ≈ 18 万元/月/对
路由表   1.2 亿 × 10 B ≈ 1.2 GB，峰值 60 万 QPS 每次查 → 必须进程内 LRU，回源 < 0.1%
```

**这就是为什么路由表不是"一张配置表"，而是一个必须按分布式系统设计的组件**（§10.7）。

## 10.6 单元化设计：闭环是唯一的硬约束

### 单元的定义

**单元 = 一组同构的全栈实例 + 一份只属于它自己那批用户的数据，能在完全隔离的情况下独立对外服务。**

判断一个切分是不是真单元，只有一条检查项：**把其他所有单元的网络全部切断，本单元的业务能不能 100% 正常？** 任何一个写路径上还调着别的单元，它就不是单元。

```
 用户 ──→ [接入层 GeoDNS/Anycast] ──携带 user_id──→
   ┌──────────────────────────────────────────┐
   │ 路由层 Router（本篇最脆弱的组件）           │
   │ ① 进程内 LRU 92% ② Redis 7.9% ③ DB 0.1%    │
   └───┬──────────────┬──────────────┬──────────┘
       ↓              ↓              ↓
 ┌──────────┐  ┌──────────┐  ┌──────────┐
 │单元 U1 上海│  │单元 U2 北京│  │单元 U3 深圳│
 │网关 / App  │  │  …同构…   │  │  …同构…   │
 │DB / Redis │  │           │  │           │
 │MQ / 发号器 │  │           │  │           │
 └─────┬────┘  └─────┬────┘  └─────┬────┘
       └── 单元内闭环：写只写本单元 ────┘
            ↓ 只读副本 / binlog 异步（单向）
   ┌──────────────────────────────────────────┐
   │ 全局层：数仓 + ES 全局索引 + 只读宽表（只读、可重建、允许落后）│
   └──────────────────────────────────────────┘
```

### 单元内闭环的六条清单

| 依赖 | 闭环要求 | 违反后的现场 |
| --- | --- | --- |
| 数据库 | 主库在本单元，跨单元只有只读副本 | 写跨单元 = 跨城 40 ms × N 次，且故障时不可写 |
| 缓存 | 本单元 Redis，**不共享跨单元缓存** | 共享 Redis 一挂全站挂，且它就是个跨单元写入口 |
| 消息队列 | 本单元 MQ，跨单元走"全局广播"专用 topic | 复用同一 topic 会让消费位点成跨单元耦合 |
| 发号器 | 本单元预领号段（步长 = 单元数） | 跨单元取号 = 发号器成全局单点（§10.13） |
| 定时任务 | 每单元独立调度 + 锁 key 带单元前缀 | 单例调度器 → N 个单元跑同一批任务 → 重复扣款 |
| 配置中心 | 每单元一份，可独立灰度 | 一改全单元生效 = 无法灰度（→ [07 变更治理](07-change-governance.md)） |

### 单元粒度：按用户，不按地域

| 粒度 | 优点 | 致命问题 | 判定 |
| --- | --- | --- | --- |
| **按 user_id 哈希** | 天然均匀、数据内聚、切换单位 = 用户 | 需要全局路由表 | ✅ **默认选它** |
| 按租户 tenant_id | B 端隔离天然、合规友好 | 大租户能打满一个单元 | ✅ 仅 B 端产品 |
| 按地域 | 就近访问天然、合规（数据出境） | 用户迁移 = 数据搬家；地域流量极不均 | ⚠️ 只作 user_id 之上的一层亲和 |
| 按业务线 | 爆炸半径小 | 同一用户跨业务线要跨单元调用 | ❌ 单元内无法闭环 |

**"大客户跨单元"的例外处理**（真实项目必遇）：

1. **白名单 + 专属单元**：把 Top 0.01% 的租户单独放一个专属单元（甚至一个租户一个单元）。代价：容量规划要按"最大租户"而非"平均"。
2. **"把大客户数据拆散"的直觉是错的**：那等于破坏闭环。正确做法是按子维度二次分片（如 tenant_id + 商户号），并保证事务不跨界。
3. **必须提前定义"单元容量红线"**：单单元承载 > 35% 全局流量时告警——那时"单单元故障"就等于"全局故障"，单元化白做了。

## 10.7 单元路由：路由表挂了，全站就挂了

### 路由信息的存放

```
用户 → 单元 的映射，三级必须同时存在：
L1 进程内 LRU（200 万条 ≈ 20 MB，命中 92%）｜订阅变更广播，全量快照 + 增量
L2 Redis 路由表（分片，hash 副本 ×3，命中 7.9%）｜写 DB → 发事件刷新，带 version
L3 user_unit_route(user_hash PK, unit_id, version, updated_at)
   仅在 L1/L2 全失效时回源（< 0.01%），query timeout = 5 ms
```

**设计纪律（三条，缺一条就埋一颗雷）**：

1. **查不到时默认"降级到默认单元只读"**，不是拒绝服务，更不是随便选一个单元写——选错单元写 = 事故一重演。
2. **路由表必须能全量重算**，且重算只补缺、不改已有映射。不能重算的路由表一旦污染只能停机修。
3. **路由变更必须"双写过渡 + 版本号"**：先在目标单元建好数据 → 改映射 → 观察 → 删源数据。直接改映射 = 用户数据凭空消失。

### 路由漂移的三种原因（这是本篇最容易被忽略的一节）

| 漂移原因 | 现场 | 为什么平时发现不了 | 防法 |
| --- | --- | --- | --- |
| **① 缓存不一致**：L1/L2 版本不同（广播丢失、重启未预热） | 同一用户相邻两请求打到两个单元，一个读到旧数据 | 单请求永远是对的，只有"读自己刚写的"才暴露 | 写后读强制回源；变更走"版本号单调递增"，不做删除式失效 |
| **② 哈希环变化**：从 `% 16` 改成 `% 32`，或取模改成一致性哈希 | 一次性 50% 用户漂移，方向不可预测 | 发布时看起来一切正常（新库都建好了） | **映射必须落表，不能算出来**；算法只用于初始化表 |
| **③ 双写窗口未收敛**：灰度迁移期 A、B 都接受该用户写入 | 同一用户两条数据链，收敛时选一条 = 丢一条 | 数据量小，且监控看"总数"不看"每用户条数" | 以"用户"为单位原子冻结：完成前只写源单元，完成后一次切换 |

> **一条铁律**：**"路由漂移"从来不是算法问题，是"路由的真相存在两个地方"的问题。** 让路由只有一个可写真相（DB 表），其余全是缓存，漂移就变成了"缓存没及时失效"这一个可控问题。

## 10.8 数据同步形态与冲突解决

### 三种同步形态：先决定"谁能写"

| 形态 | 拓扑 | 冲突可能性 | 适用 | 代价 |
| --- | --- | --- | --- | --- |
| **单向** | A ⇒ B，B 只读 | **不可能**（B 不接受写） | 读写分离、异地只读、报表库 | 切换后 B 提升为主，**必须重建反向链路**——事故二的现场 |
| **双向** | A ⇔ B 皆可写，需环回抑制 | **必然发生**，只在切换/重试窗口爆发 | 同城双活（同一行只有一个 owner 时）、短窗口灰度迁移 | 写放大 2x；必须冲突解决；同步延迟导致"读到自己旧值" |
| **环状** | A → B → C → A | 必然 + **可能无限环回** | 三地都要本地写 | 拓扑脆弱（断一环全链路退化）；环回抑制靠 GTID/逻辑时钟，出错极难查 |

**结论：优先单向，谨慎双向，尽量不环状。** 三地都要本地写时正确答案是单元化（每单元只写自己那批用户），不是环状复制。

### 冲突解决四策略对比：每种都会在某一类数据上出错

| 策略 | 判定依据 | 会在**哪种数据**上出错 | 出错长什么样 | 适合 |
| --- | --- | --- | --- | --- |
| **LWW（时间戳）** | `updated_at` 大的赢 | **任何增量型数据**：余额、库存、计数 | 两边各 `+100`，覆盖后仍是 `+100`，**丢 100**；时钟偏移 20 ms 就让"后写的输" | 用户资料、地址、昵称（覆盖可接受） |
| **版本向量** | 只检测"是否并发"，不裁决 | **无法自动合并的**：订单状态、金额、审批流 | 告诉你冲突了，但合并函数要人写；`已支付` vs `已取消` 无解。向量还随节点数膨胀 | 集合类（购物车）并集可合并；文档类需人工 |
| **业务仲裁** | 交给业务规则裁决 | **规则本身有歧义**：券归属、积分有效期 | 规则写不全 → 全进人工队列，量大等于停服；写错 → 系统性偏向一侧 | 券、积分、审批等规则明确的领域 |
| **禁止并发写**（单写者/分区所有权） | 每行有唯一 owner，非 owner 的写拒绝或转发 | **故障切换窗口**：owner 不可达时怎么办 | 要么停写（RPO=0 但可用性归零），要么临时改 owner（回到冲突），**无第三条路** | ✅ 单元化默认：把冲突从运行期问题变成路由期问题 |

> **本篇最重要的一句取舍**：**冲突解决的最高级形式，是让冲突不可能发生。** 前面三种策略都是在"事后裁决"，只有"禁止并发写"是在"事前消除"。单元化的全部价值，就是把这条从理想变成默认。

### 骨架代码一：Go 单元路由（多级缓存 + 兜底降级）

```go
// 单元路由：L1 进程内 → L2 Redis → L3 DB；任何一级失败都不许"随便选一个单元"
func (r *Router) Route(ctx context.Context, userID int64) (UnitID, error) {
	h := hashUser(userID)                    // 只哈希不取模：取模在扩缩容时全量漂移
	if u, ver, ok := r.l1.Get(h); ok {       // ① 进程内 LRU，命中 92%
		return u, nil
	}
	u, ver, err := r.l2.Get(ctx, h)          // ② Redis，5ms 超时
	if err == nil {
		r.l1.Put(h, u, ver)                  // 带版本号，供"写后读失效"判断
		return u, nil
	}
	if err != redis.Nil {                    // L2 挂了 ≠ 用户不存在，必须区分
		r.metrics.Inc("route_l2_error")
	}
	u, ver, err = r.l3.Get(ctx, h)           // ③ DB 兜底，5ms 超时
	switch {
	case err == nil:
		r.l2.Put(ctx, h, u, ver)
		r.l1.Put(h, u, ver)
		return u, nil
	case errors.Is(err, sql.ErrNoRows):
		return r.assign(ctx, h)              // 新用户：落表后才返回
	default:
		return DefaultUnit, ErrRouteDegraded // ★ 兜底：默认单元 + 明确错误码
	}
}
// 写路径拿到 ErrRouteDegraded 一律 503——宁可不可用，不可写错单元（事故一根因）
```

### 骨架代码二：Java 冲突解决（单写者裁决 + 增量合并 + 人工兜底）

```java
/** 同步入站写：只接受 owner 单元的写；非 owner 只允许"增量型"字段合并，其余进人工队列 */
@Service
public class InboundWriteResolver {
    public ResolveResult resolve(Row local, Row remote, UnitId remoteUnit) {
        // ① 分区所有权最优先：非 owner 的整行覆盖一律拒绝
        if (!local.getOwnerUnit().equals(remoteUnit)) {
            return ResolveResult.reject("NOT_OWNER", remote, local.getOwnerUnit());
        }
        // ② 版本号不新 → 幂等重放，直接丢弃
        if (local.getVersion() >= remote.getVersion()) return ResolveResult.skip(local);
        // ③ 增量型字段（余额/库存/计数）：delta 合并，绝不用绝对值覆盖
        if (local.isDeltaField(remote.getField())) {
            long merged = local.getValue() + remote.getDelta();   // ★ 加法而非赋值
            return ResolveResult.merge(merged,
                Math.max(local.getVersion(), remote.getVersion()) + 1);
        }
        // ④ 状态机型字段：只允许向前迁移，向后一律判冲突
        if (local.isStateField(remote.getField())) {
            return local.getState().canTransitTo(remote.getState())
                ? ResolveResult.take(remote)
                : ResolveResult.conflict("STATE_REGRESSION", local, remote);
        }
        // ⑤ 普通覆盖型字段（昵称/地址）：LWW 可接受
        return remote.getUpdatedAt().isAfter(local.getUpdatedAt())
            ? ResolveResult.take(remote) : ResolveResult.skip(local);
    }
}
// conflict() 永远进 conflict_log 表 + 告警，不允许静默选一边
```

**两段代码的共同点**：**所有"我不确定"的分支，都返回错误或进人工队列，绝不猜。** 多活系统里最贵的 bug 是"静默选了一边"。

## 10.9 脑裂的三种防御：必须有外部裁判

**脑裂 = 网络分区后，两侧都认为自己是主，都接受写入。** 它不是"运维失误"，是**分布式系统的默认行为**——默认行为就是裂开，防裂必须主动设计。

| 防御 | 机制 | 防御什么 | 额外延迟 | 成本 | 前提条件 | 自己怎么失效 |
| --- | --- | --- | --- | --- | --- | --- |
| **租约 Lease** | 持 TTL 30 s 租约、每 10 s 续租；过期即**停止接受写**，新主须等旧租约过期才上任 | 旧主"不知道自己已经死了"还在服务 | 无（只影响上任速度） | 极低（一行 etcd/Redis key） | 时钟单调性 + **存储层校验单调 fencing token** | GC 停顿 > 20 s 后本地仍认为持有；时钟回拨；存储层不校验 token → 装死 |
| **多数派 Quorum** | 写需 N/2+1 确认，分区后只有多数派侧能服务 | 两侧都写 | +1 次跨副本往返（同城 +1 ms / 跨城 +40 ms） | 3 副本起（存储 1.5x） | 奇数副本且分布在不同故障域 | 3 副本同机房 → 多数派一起断电；单元化下等于**少数派侧单元停写** |
| **外部仲裁 Witness** | 第三个**不存业务数据**的轻量节点，只投票/发租约 | 2 节点对称拓扑的分区脑裂 | +1 次心跳（同城 1 ms / 跨城 40 ms，仅决策路径） | 很低（1–2 核 + 心跳表 ≈ 1/20 个机房） | **witness 与两侧都不共网络路径** | ★ 与 B 同城 → 城域网割接时一起失联，A 拿不到票 → **全站停写**（比脑裂更糟） |

### 没有仲裁中心时会怎样

**对称双活（A、B 两个节点，都能写，都没有第三方裁判）不是高可用架构，是一个分布式脑裂发生器。** 具体过程：

```
20:00:00  城域网割接，A 与 B 之间丢包 100%
20:00:05  A 判 B 故障 → A 独自服务；B 判 A 故障 → B 独自服务（同一秒，两侧同时）
20:00:05  数据开始分叉：同一用户的两个请求被写到两个地方
21:00:00  网络恢复，双向同步：按 LWW 合并 → 丢掉一半写；规则覆盖不到的进人工队列
          → 41,600 笔订单中 12,300 笔金额/状态不一致 → 人工"择边"冲正
```

**三种防御的选型建议**：

| 拓扑 | 用哪种 | 理由 |
| --- | --- | --- |
| 2 机房 + 1 异地 witness（多数公司的现实选择） | **Witness** | 最便宜，且防住"两机房之间分区"这一最常见场景 |
| 3 AZ 同城（云上标配） | **Quorum（3 副本跨 3 AZ）** | 天然奇数，AZ 间 0.2 ms，多数派代价几乎为零 |
| 单元化（单元 = 写边界） | **租约 + fencing token + 所有权表** | 自闭环本身就是"分区即降级"：宁可整单元不可写，也不许跨单元写 |

> **一条硬规矩**：**任何允许两地同时写的架构，评审时必须回答"谁是裁判，它放在哪，它和两边的网络路径是否独立"。** 答不上来就不许上生产。

## 10.10 切换与回切：回切才是最容易丢数据的一步（问⑦的前半）

### 为什么回切更危险

| 维度 | 切换（failover） | 回切（failback） |
| --- | --- | --- |
| 演练次数 | 每季度 | **通常 0**（"反过来做一遍"） |
| 心态 / 人力 | 高压、谨慎、有 runbook、全员在线 | 放松（"收尾而已"），**往往只剩一个人** |
| 数据方向 | 单向：主 → 备 | **反向**：新建链路，从未验证过 |
| 位点/拓扑 | 现成的、配好的 | **手配的、容易配反的**（事故二就是） |
| 写入量 | 切换时通常已停写 | 回切时 B 已稳定跑数小时，**写入量最大** |

**一句话：切换是"断开"，回切是"缝合"，缝错了比断着更糟。**

### 完整切换/回切时序

```
 【切换 failover】                                  【回切 failback】
 t0      t1       t2       t3                 t4        t5        t6       t7
14:02   14:06    14:10    14:20              17:40     17:45     18:10    18:30
  │       │        │        │                  │         │         │        │
  ▼       ▼        ▼        ▼                  ▼         ▼         ▼        ▼
┌─────┐┌──────┐┌───────┐┌────────┐        ┌────────┐┌───────┐┌───────┐┌──────┐
│A 故障││宣布   ││摘 A 流 ││B 单写   │        │★冻结 B ││反向同步││对齐校验││A 接读│
│告警   ││故障   ││A 只读  ││RPO=0    │        │★快照+位││B → A  ││清单 10││观察30│
│       ││决策   ││B 接写  ││持续 N 时│        │★点记录 ││已应用  ││项全过  ││分钟  │
└─────┘└──────┘└───────┘└────────┘        └────────┘└───────┘└───────┘└──────┘
                                                                    │
                                                          ┌─────────┘
                                                          ▼
                                                   ┌──────────────┐
                                                   │A 接写 → 恢复  │
                                                   │双向 → 观察24h │
                                                   │→ 摘 B 写权限  │
                                                   └──────────────┘

⚠ 事故二死在这一段：t4 忘了冻结 → t5 位点用旧快照 + 方向配反
  → t6 被直接跳过（没有校验清单）→ t7 用旧数据对外服务 3 小时不被发现
```

**时序里三个不可跳过的动作，每个都对应一次真实事故**：

| 动作 | 跳过会怎样 |
| --- | --- |
| **t1 宣布故障 = 一个具名的决策** | 没人拍板 → 两个值班各做一半 → 一侧摘流一侧还在写 → 分叉 |
| **t4 冻结 B 写 + 记录快照与位点** | 同步永远追不上正在写的数据，"对齐"变成"追尾" |
| **t6 对齐校验清单全过** | 事故二：旧数据覆盖新数据，且**乐观监控看不出来**（服务是"健康"的） |

### 回切前的数据对齐校验清单（十项，逐项签字）

| # | 校验项 | 通过标准 | 不通过会怎样 |
| --- | --- | --- | --- |
| 1 | **反向复制位点确认** | 记录 B 的 GTID/位点，并验证已在 A 侧实际应用完成（`Retrieved == Executed`） | 位点回退 → 从旧快照复制 → 事故二重演 |
| 2 | **增量条数与金额双比对** | 按小时分桶比订单数/金额/支付成功数，容差 = 0 | 少同步 1 小时 → 丢一段订单 |
| 3 | **主键冲突扫描** | A、B 自增主键区间无交集（有交集 = 全局 ID 方案失效） | 主键冲突 → 覆盖或复制中断（§10.13） |
| 4 | **中间态扫描** | 状态机中间态（如"待支付"超 30 分钟）数量 ≤ 基线 | 回切后被重复推进 → 重复扣款 |
| 5 | **环回抑制验证** | 双向链路环回抑制生效（GTID / 逻辑时钟 / 单元前缀） | 数据无限往返，CPU 与带宽打满 |
| 6 | **时钟偏差确认** | NTP 偏差 < 50 ms（LWW 的安全阈值），超了改手工裁决 | LWW 选错方向 → 静默丢更新 |
| 7 | **派生视图重建完成** | ES / Redis / 布隆 / 宽表从 A 重建完，刷新位点与 DB 对齐 | 用户搜不到刚下的单 → 二次投诉 |
| 8 | **写冻结窗口一致性** | 冻结期间全站写入口只有 B 一个（含定时任务、脚本、后台、MQ 消费） | 漏一个写入口 → 它的写被覆盖 |
| 9 | **先读后写的顺序** | 先回切只读流量 → 观察 30 分钟 → 再回切写流量 | 写已回 A、读还在 B → 读不到自己的写 |
| 10 | **逆向回滚预案就绪** | 必要时能再次切回 B，且 B 的数据未被破坏（冻结期不删） | 回切失败 = 两边都不能用 = 最坏结局 |

> **这份清单的用法**：打印出来，逐项签字，**任一项不通过就不许解冻写流量**。回切不是"恢复原状"，是一次**新的、方向相反的切换**，必须按切换的标准来做。

## 10.11 切换演练：为什么必须真演练（问⑦的后半）

### 演练成本 vs 事故成本：算给老板看

```
一次完整演练（含回切）：24 人日 ≈ 6 万 + 影子单元 1.5 万 + 脏数据修复 1.5 万 ≈ 9 万元
一次事故（事故二实测）：无法补单 112 万 + 赔付 46 万 + 150 人日 37 万 + 商誉 400 万 ≈ 595 万元
比值 1 : 66  →  一次演练的成本 ≈ 一次事故的 1.5%
```

**"演练太贵"只在一种情况下成立：你的系统一年只可能出一次事故。多活系统恰好相反——它的故障率与"你多久没演练"正相关。**

### 红蓝对抗设计（避免"演练变成了 rehearse runbook"）

| 角色 | 目标 | 具体动作 |
| --- | --- | --- |
| **红军（注入方）** | 制造**最难被发现**的故障，且不影响真实用户 | ① 只断 A→B 单向（心跳仍通）② A 的时钟拨快 300 ms ③ 路由表 L2 随机丢 5% 响应 ④ 同步延迟 10 分钟内爬到 30 s（不是瞬间断）⑤ 只给一个非核心写入口留后门 |
| **蓝军（应急方）** | **看不到红军操作**，按 runbook 处置并把 MTTR 压进目标 | 只能看监控和告警；不许问红军；自己判断"切换还是等恢复" |
| **裁判（架构师 + SRE）** | 只记录，不提示 | 记四个数：MTTD、MTTD-决策、MTTR、误操作数 |

**红军最难给的那一类故障，应该是"看起来像正常波动"的故障。** 断网很简单（监控立刻打红），浅故障才是真实事故的样子。

### RTO 实测方法（不要测"脚本跑完"）

```
① 埋合成事务流（1,000 笔/分钟，每笔带唯一 trace_id 与金额）
② 注入故障 T0 → ③ 首次告警 T1(MTTD) → ④ 决策完成 T2(MTTD-决策，常占总时间 40%)
⑤ 流量全转移且成功率回到基线 99.9% 的 T3 → **T3-T0 才是 RTO**，不是"脚本 exit 0"
⑥ 事后用 trace_id 全量核对存在性/金额/是否只一份 → 这才是 RPO 的真实验证
```

### 演练频率

| 演练类型 | 频率 | 范围 | 触发额外演练的信号 |
| --- | --- | --- | --- |
| **切换开关 dry-run**（只跑控制面，不动流量） | 每周 | 全量 | — |
| **单元级切换**（切一个非核心单元） | 每月 | 单单元 | — |
| **全流程切换 + 回切** | **每季度** | 主备两城 | 每季度必含**回切**，且回切单独评分 |
| **红蓝对抗**（浅故障、隐藏故障） | 每半年 | 全链路 | — |
| **拓扑变更后加练** | 变更后 2 周内 | 受影响链路 | 路由表结构改、同步方向改、单元拆分、新增地域 |

> **一条纪律**：**回切必须单独演练、单独评分。** 把"切过去再切回来"当成一次演练，是最典型的自欺——回切永远在"已经累了"的状态下被顺手做完。

## 10.12 就近访问与一致性的取舍

### 什么时候必须就近写，什么时候只配就近读

| 数据 | 就近写？ | 理由 | 正确形态 |
| --- | --- | --- | --- |
| 订单、消息、个人资料 | ✅ **必须**（= 路由到 owner 单元） | 写延迟直接进转化率：跨城 5 次往返 = 200 ms | 按 user_id 归属，**写只落 owner** |
| 用户自读（订单/消息列表） | ✅ 就近读 | 同单元内读，1 ms | 单元内主库 / 从库 |
| 全局库存、券池 | ❌ **只能就近读** | 唯一计数无法两地同时扣减（§10.8） | 读本地缓存 + 版本号；写回单一 owner 单元 |
| 账户余额 | ❌ 只能就近读 | 同上，且是钱 | 余额读本地 + 版本号；扣款走 owner |
| 全局配置、黑白名单 | ✅ 就近读，写走控制面 | 读多写极少 | 每单元一份 + 变更广播（→ [07 变更治理](07-change-governance.md)） |
| 跨单元报表 | ❌ | 聚合必须在全局层 | 数仓 / 全局只读副本（§10.13） |

**延迟收益的量化**：一个页面 6 次数据访问，全跨城 = 6 × 40 ms = 240 ms → P99 ≈ 320 ms；全就近读 = 6 × 1 ms → P99 ≈ 35 ms。**P99 从 320 ms 降到 35 ms，转化率提升 3–5 个百分点。**

> **一句话**：**"就近访问"不是"把数据放近"，而是"把请求路由到数据的所有者"。** 复制只能解决读，写必须回到 owner；"两地各放一份、两边都能写"的方案，都会在切换那一刻变成 §10.8 的冲突问题。

## 10.13 单元化下的三个隐性难题

这三个难题在方案评审时几乎不会有人问，上线三个月后必然爆发。

### 难题一：全局唯一 ID —— 序列号怎么发

事故一的根因之一就是"本地自增"。四种方案：

| 方案 | 结构 | 优点 | 代价 / 崩法 | 判定 |
| --- | --- | --- | --- | --- |
| **号段 + 单元前缀** | `单元号(3b)+序列(29b)+时间(32b)`，每单元预领一段（10 万个） | 无跨单元调用，本地发号 0 延迟 | 重启浪费未用号段；中央发号器是弱单点（预领多段缓解） | ✅ 订单/交易类默认 |
| 雪花 Snowflake | 时间戳 + 机器 ID + 序列 | 有序、单机高性能 | **依赖时钟单调**：NTP 回拨撞号；机器 ID 靠人工分配 → 撞号 | ⚠️ 仅当能保证 clock monotonic |
| UUIDv7 | 时间前缀 + 随机 | 无需协调 | 128 bit，主键索引膨胀（+8 B/行 × 8 亿行 ≈ 6.4 GB） | ⚠️ 日志/事件可以，交易主键不行 |
| 数据库自增 | 中央序列 | 最简单 | 跨城 40 ms/次；中央库挂 → 全站不能建单 | ❌ 单元化下禁止 |

**判断标准只有一条**：它会被用作主键或唯一键吗？会，就必须全局唯一且单调，且发号不能有跨地域同步调用。

### 难题二：全局时间 —— 时钟偏移对手续的影响

```
真实时钟偏移（云上 VM + NTP）：稳态 1–5 ms ｜ GC 长停顿后 20–60 ms（虚拟化"时钟跳跃"）
跨城两台机器：40 ms 网络 + 各自偏移 → 相对偏差可达 80 ms
```

**这 80 ms 就是事故的物理量。** LWW 的裁决依据是 `updated_at`，而两地同时修改同一行，"谁更晚"在这 80 ms 内**在物理上不可判定**。也就是说：

> **LWW 在多活里本质上不成立。** 它不是"偶尔错"，是"在窗口内必然错"。而切换和重试正好把大量写挤进这个窗口。

**三条解法**（按可靠性排序）：

1. **不用物理时钟做正确性判断**：用逻辑时钟（Lamport / HLC）排序，用 **fencing token（单调任期号）** 由存储层校验锁的合法性——比"租约 + 本地时钟"可靠一个量级。
2. **单写者**：同一行的写永远只在一个单元（§10.8）——把时间比较彻底绕开。
3. **把时间语义显式化**：真要"以最后编辑为准"，就接受"80 ms 内以 owner 单元为准"并写进契约，别假装 LWW 是精确的。

**现场**：退款单的 `refunded_at` 在 B 地比 A 地的 `paid_at` 早 30 ms → 对账脚本判定"先退款后支付" → 900 条异常工单全部人工核对。

### 难题三：跨单元查询 —— 聚合报表怎么办

**先说结论：线上禁止跨单元 join。** 三套可行方案：

| 方案 | 形态 | 延迟 | 新鲜度 | 适合 |
| --- | --- | --- | --- | --- |
| **① 全局层汇聚** | 各单元 binlog → 数仓/ClickHouse（Flink 准实时） | 秒–分钟 | 落后 10 s–T+1 | ✅ **所有报表/聚合/大盘的默认方案** |
| **② 查询扇出** | 网关并发查 N 个单元 → 内存合并 | max(单单元) + 合并（3 单元 +8 ms） | 实时 | ✅ 仅"按 ID 精确定位/批量详情"，N ≤ 8 |
| **③ 全局只读副本/宽表** | 按查询维度冗余一份（如按商户的订单宽表） | 1–5 ms | 落后 1–30 s | ✅ 高频跨维度点查（客服查单） |
| ❌ 在线跨单元 join | 直接在 SQL 里 join 两个单元的库 | 不可控 | — | ❌ 一次 join = N 次跨城往返 + 一个单元抖动全查询挂 |

**为什么扇出不能滥用**：扇出 N=16 时总延迟 ≈ max(16 个独立 12 ms P99) ≈ 22 ms，但任一单元慢就整查询超时；**可用性 = 单单元可用性的 N 次方**，单单元 99.99% → 扇出后 99.85%（月不可用从 4 min 劣化到 65 min）。所以"报表走全局层"不是性能妥协，是**可用性妥协**：扇出把"单单元故障"放大成"全查询故障"。

## 10.14 按用户/地域做切换灰度

### 怎么做

```
阶段0 路由表加"目标单元"字段（默认=当前单元），开关打开但不生效
阶段1 0.1% 内部员工账号 → 观察 24 h（错误率 / P99 / 数据一致性探针）
阶段2 按 user_id 哈希 1% → 5% → 20%，每档观察 ≥ 4 h 且必须跨过一个业务高峰
阶段3 50% → 100%（风险已降但回滚成本已升，见下方风险④）
阶段4 反向验证：对该批用户做"读自己刚写"探针，逐 user_id 校验
```

### 五个必须提前想清的风险

| 风险 | 现场 | 防法 |
| --- | --- | --- |
| **① 单位必须是"用户"**，不是请求/设备 | 按请求灰度 → 同一用户两次请求落两个单元 → 读旧数据、写两份 | 路由表 key 必须是 user_id，灰度只作用于路由表 |
| **② 灰度期该用户是"双写"状态** | 迁移未完成，用户在两个单元都有数据 → 收敛时丢一份 | **切换即迁移**：完成前只写源单元，完成后一次原子切换，禁止"边迁边双写" |
| **③ 指标不可比** | 灰度用户路径不同（跨单元跳转）→ P99 天然更差，误判"新单元有问题" | 与"同结构对照组"比，不与全量比 |
| **④ 回滚成本不对称** | 1% 时回滚免费；70% 后回滚 = 又一次全量切换 | 50% 之后升级为"全流程切换演习"标准：runbook + 校验清单 + 红蓝对抗 |
| **⑤ 灰度边界 ≠ 写入归属** | 只切读没切写 → 读新单元写旧单元 → §10.7 漂移第 3 类 | 读写一起切，以"用户"为原子单位 |

### 按地域灰度的额外风险

按地域切（先切流量最小的深圳单元）更快更便宜，但有两个新问题：**① 地域内用户分布极不均**（某地域只占 0.3% 用户，却含若干大客户）；**② 合规耦合**（地域切换 = 数据出境判断）。

> **规则：地域灰度只用于"整个技术栈的第一次上线验证"，用户级灰度才是常态手段**——地域是基础设施单位，用户才是业务影响单位。

## 10.15 这个形态特有的崩法 + 换挡信号（问⑤、问⑥）

### 特有崩法（不是"高可用"套话）

| 崩法 | 长什么样 | 定位方法 | 预防 |
| --- | --- | --- | --- |
| **路由表缓存不一致** | 少数用户间歇性读到旧数据 / 数据"消失" | 按 user_id 采样比对 L1/L2/DB 的 unit_id 与 version | 版本号单调 + 写后读强制回源 |
| **同步延迟悄悄爬升** | 指标全绿，主备却差 20 分钟 | 看 `replication_delay_seconds` 的**趋势**而非阈值 | > 5 s 告警；> 30 s 自动熔断写 |
| **witness 与 B 同城** | 城域网割接时一起失联 → A 拿不到票 → 全站停写 | 定期探测 witness 到两侧的路径独立性 | witness 放第三方城市 + 不同运营商 |
| **回切窗口双写** | 回切后部分订单状态错乱 | 回切后 24 h 做全量条数 + 金额比对 | 十项清单 + 冻结期只留一个写入口 |
| **单元容量不均 / 定时任务重复** | 单单元 > 35% 流量；凌晨 2 点一批重复扣款 | 按单元统计 QPS 占比；查锁 key 有无单元前缀 | 容量红线告警 + 大客户专属单元；锁 key = `{unit}:{task}` |

### 换挡信号（什么指标越过什么阈值就必须换档）

| 从 → 到 | 硬阈值信号 | 代价 |
| --- | --- | --- |
| 单活 → 同城双活 | 单 AZ 故障造成 > 30 min 不可用或损失 > 100 万；或要求 RTO < 30 min | 1.8–2.2x；须先解决同城汇聚点单点 |
| 同城双活 → 两地三中心 | 监管/合同要求"城市级灾害可恢复"；或两机房被迫共用一个汇聚点 | 2.5–3.5x；RPO≠0，须接受"丢一段" |
| 两地三中心 → 单元化 | ① 单地域容量到顶（DB 写 > 3 万 TPS / 存储 > 30 TB）② 跨城写 > 80 ms 已影响转化 ③ 需按地域灰度或数据出境合规 | 3.5–5x；引入路由表、全局 ID、跨单元查询 |
| 单元化 → 分单元治理 | 单单元 > 35% 全局流量；或单元数 > 8 后路由与全局层成瓶颈 | 需单元自治 + 全局层去中心，再 +50% |

> **不要跳档**：没有仲裁中心就上双向同步 = 事故一；没有回切演练就上单元化 = 事故二。**每一档的"不能扛"列就是下一档的立项理由。**

| --- | --- | --- | --- | --- |

| 5 | **回切不做数据对齐** | 回切是反向的第一次切换，从未验证 | 事故二：丢 41,600 笔，1,340 万 | 十项清单逐项签字（§10.10） |

| 9 | **回切顺序反了** | 写回 A、读还在 B → 读不到自己刚写 | "下单后查不到订单" | 先读 → 观察 → 再写（§10.10 #9） |
| 10 | **只备不切 / witness 同城 / 路由取模** | 灾备没跑过业务起不来；witness 一起失联；取模扩缩容全量漂移 | 切换失败 / 全站停写 / 50% 数据"消失" | 季度演练 + witness 独立城市 + 路由落表 |

## 10.17 十分钟答题卡

被问"怎么设计多活"时，按这个顺序讲——**不要从"上 DTS 双向同步"开始**：

```
1  真问题  难点不在数据同步，在切换/回切那 10 分钟的脑裂、写冲突、路由漂移
2  定档    先问：RTO 多久？RPO 能不能丢一段？跨城写延迟能不能忍？→ 才谈四档
3  四档表  单活(1.0x,30m-4h) → 同城双活(2x,1-5m,RPO=0) → 两地三中心(3x,30m-2h,RPO≠0)
           → 单元化(4-5x,30s-3m,RPO=0)；每档必须说清"不能扛什么"
4  冲突    优先"禁止并发写"（唯一 owner），其次业务仲裁，LWW 只给用户资料；增量用 delta
5  脑裂    必须有外部裁判：2机房+witness / 3AZ+quorum / 单元化+租约+fencing token
           答不上"裁判在哪、路径是否独立"就不许上生产
6  路由    映射落表；L1 LRU + L2 Redis + L3 DB；查不到降级只读，不许猜
           漂移三因：缓存不一致 / 哈希环变化 / 双写窗口未收敛
7  单元    闭环判据：切断所有其他单元，业务能否 100% 正常
8  切换    t1 具名决策 → 摘流+只读 → B 单写 → 记录位点
9  回切    ★冻结B写 → 反向同步 → 十项校验清单 → 先读后写 → 观察 24h（独立 runbook）
10 验证    季度全流程含回切 + 红蓝对抗 + RTO 用合成事务实测（不是脚本 exit 0）
11 三个坑  全局ID（号段+单元前缀）/ 全局时间（LWW 不成立）/ 跨单元查询（走全局层，禁止 join）
12 必需    唯一 owner + 外部裁判 + 回切校验清单 —— 其余都是规模驱动
```
