## 14.1 引子：两次「配置改对了、比例也对，但还是全线不通」的事故

### 事故一：网关分批重启，64 万连接同时重连，把鉴权服务打死（2025-07-16）

平台当时 320 万在线，40 台网关（每台 8 万连接）。发布 v2.31 走「K8s 滚动更新，maxUnavailable=20%」，评审时所有人都认为这是最保守的策略——**20% 确实是保守的，但保守的对象搞错了**。

| 时间 | 事件 | 数据 |
| --- | --- | --- |
| 02:00:00 | 第 1 批 8 台网关收到 `SIGTERM`，进程直接退出 | 8 / 40 台 = 20% 容量 |
| 02:00:05 | 8 台各 8 万连接被 `RST`，SDK 立即重连（**无 jitter、退避 0**） | **64 万条连接同时断** |
| 02:00:06 | 新建连接 QPS 从日常 **3,000/s** 冲到 **64,000/s** | **21 倍** |
| 02:00:09 | 鉴权服务 QPS 3,000 → **61,000**（每个新建连接 1 次 token 校验 + 1 次设备表写） | 21 倍 |
| 02:00:12 | 鉴权 P99 从 11 ms → **4.8 s**，DB 连接池 200 全满，排队 3.1 万 | Java 线程池打满 |
| 02:00:20 | 网关 TLS 握手排队，`accept` 队列打满，`somaxconn` 4096 溢出 | SYN 丢弃 38% |
| 02:00:31 | 客户端 3 s 超时重试，新建 QPS 二次冲到 **89,000/s** | 重试放大 1.39× |
| 02:00:40 | 鉴权熔断，网关降级为「先连后鉴权」 | **22% 的连接未鉴权在线** |
| 02:03:00 | 值班回滚：重新拉起第 1 批 → 连接又断一次 → **二次风暴** | 二次峰值 71,000/s |
| 02:19:00 | 手动限流 15,000 conn/s + 客户端带 jitter 的版本强制升级，才收敛 | — |
| 合计 | 消息中断 **19 分钟**；重连失败 **214 万次**；消息延迟超 60 s 的 **380 万条**；次日客诉 4,100 单 | 直接 + 间接约 690 万元 |

**根因不是「重启方式不对」，是四件事同时缺失**：① 进程退出不打招呼（无 draining 帧，客户端只能等 RST）；② 客户端重连无 jitter、无指数退避（真机上 64 万个进程在同一秒发起）；③ 鉴权在连接建立的**同步热路径**上（应该本地验签）；④ 接入层按「请求 QPS」限流，而瓶颈是「**新建连接 QPS（握手 + TLS + 鉴权）**」，两者的成本差 20 倍。

### 事故二：路由表主从切换 47 秒，11.6 万条消息投给了六分钟前就下线的机器（2025-11-04）

路由表用 Redis Cluster（1 主 2 从，**异步复制**）。一次宿主机故障触发 failover，新主比旧主少了 2.8 秒的写入。而「写失败」在网关侧被 `try/catch` 吞掉后只打了一条 warn 日志。

| 时间 | 事件 | 数据 |
| --- | --- | --- |
| 21:04:12 | Redis 主节点宕机，cluster failover 开始 | — |
| 21:04:19 | 新主选出（7 秒），**丢失 2.8 s 写入** | 3.1 万条路由回退到旧 `gw_id` |
| 21:04:20 | 同一时间窗内注册失败的连接被静默吞掉 | 4.4 万条「有连接、无路由」 |
| 21:04:20–21:05:00 | 下行投递按旧 `gw_id` 找到的还是 21:02 已摘流的 gw-19/gw-22 | **9.2 万条消息写进死连接后被丢弃** |
| 21:05:00 | 「有连接、无路由」的 4.4 万用户被判定「离线」，消息转离线库（可补拉） | 2.4 万条延迟 6 分钟 |
| 21:11:00 | 客诉进线 1,700 单：消息「已读回执正常、内容没到」 | — |
| 21:26:00 | 靠客户端重连触发注册 + 全量对账修正路由 | 影响 **7 分钟**，可恢复 11.6 万条，**不可恢复 380 条** |

**三条根因，一条比一条贵**：① 路由表把「写成功」定义为「主节点回了 OK」，没有 `WAIT 1` 或 quorum；② 摘流时**只关连接、没删路由**，且查表不校验 `epoch`（无法识别「这条路由指向的 gw 已经死了」）；③ 注册失败没有本地重放队列，「路由表挂了」直接退化成「用户离线」。

> 🩸 **本篇的唯一真问题在这两次事故里显形了**：第一次事故里，**网关是健康的、鉴权是健康的、LB 是健康的**，全站却整整 19 分钟不能收发消息；第二次事故里，**消息存储一条都没丢**，却有 9.2 万条消息静默死亡。两次都不是「某个组件坏了」，而是**「谁在哪台机器上」这张表的可用性与正确性出了问题**。它就是本篇要设计的东西。

## 14.2 一句话定位与唯一真问题

**定位**：WebSocket 网关集群是 IM 系统的**数据面接入层**——它唯一不可替代的价值是**持有那条 TCP 连接**，因此它是全站唯一「有状态」的横向扩展层（其他层都可以无状态水平扩）。

### 唯一真问题

> **「谁在哪台机器上」这张路由表，本身就是一个分布式系统。**
> 但比这更麻烦的是：**它的真相不在自己手里。** 路由的真相是那条 TCP 连接，只存在于网关 A 的进程内存和一个内核 socket 结构里。路由表是**连接的派生索引**——一个每秒钟都在失效、无法回滚、无法强一致的缓存。
> 所以：**路由表不能追求「永远对」，只能追求「错了也能被纠正，且纠错前不静默丢消息」。**

这一个判断推出了全部设计：

| 从判断推出的约束 | 推出的设计 |
| --- | --- |
| 路由表是派生索引，一定会有旧值 | 每条路由带 **`epoch`（单调递增）**，查表必须校验「不旧于消息的逻辑时钟」 |
| 网关会死、死了没人通知路由表 | **网关租约（gw lease）**，租约过期 → 该网关全部路由批量标记 stale |
| 千万条路由不能各自续约 | 两道 TTL：**连接级 TTL（内存）** vs **网关级租约（Redis）**，写放大从 33 万/s 降到 16/s |
| 路由查不到 ≠ 用户离线 | 三级判定：`路由未命中` → `回源 DB` → 才判「离线入离线库」，**绝不默认丢弃** |
| 路由表的读取量 ≫ 写入量 | **L1 进程内 LRU + Redis + DB**，87% 命中在 L1，Redis 只承担 13% |
| 连接建立成本远高于请求处理成本 | 限流点在**新建连接**维度，鉴权走**本地验签**（JWKS），不进同步热路径 |
| 连接不能被「切」，只能被「请走」 | **优雅摘流：摘流量 → 通知重连 → 等排空 → 关连接**，顺序不能换 |

先和两个「看起来同构」的东西划清界限，这是很容易混的一节：

| 系统 | 映射内容 | 变更频率 | 真相在哪 | 结论 |
| --- | --- | --- | --- | --- |
| **本篇**：`uid → gw_id` | 连接位置 | **极高**（重连即变，3000 次/s） | **在网络上（TCP 连接）** | 只能近似 + 自愈，必须带 epoch |
| [10 多活 · §10.7](10-multi-active-and-cell.md)：`uid → unit_id` | 数据归属 | 极低（迁移才变，几次/天） | **在 DB 表里（可写真相）** | 必须落表、必须可重算 |
| [12 短链](12-shortlink-system-design.md)：`slug → target` | 资源指向 | 低（有审批） | 在 DB 里 | 必须永久、必须墓碑 |

> **一句话记住区别**：10 篇的路由表错了会「写错地方」（要防），本篇的路由表错了会「投错地方」（要**自愈**）。所以本篇的技术核心不是「一致性」，是**「过期检测 + 兜底路径」**。

## 14.3 量级与预算：先算清一条连接到底吃多少

### 业务量级推导

```
DAU                     1 亿
同时在线峰值             1,000 万（DAU 的 10%，晚 21:00 峰值）
人均日发消息             100 条  → 100 亿条/天 → 11.6 万条/s 均值
峰值系数 K=4（晚高峰）    → 上行 46 万条/s
下行放大 1.6（单聊 1 + 群均摊 0.6）
                         → 下行 74 万条/s
路由查表次数 = 下行接收人数 = 74 万次/s（峰值）   ← 这个数决定路由表的读容量
新建连接 = 1000 万 / 平均会话时长 55 分钟 ≈ 3,000 /s（常态）
                         → 重连风暴峰值被限流到 1.5 万/s（见 §14.8）
心跳    = 1000 万 / 30s = 33.3 万帧/s
带宽    = 74万×400B + 66.6万×60B（心跳 ping/ack）+ ack 批 ≈ 340 MB/s ≈ 2.7 Gbps（集群合计）
```

> **注意最后一行**：1000 万连接的集群出口带宽只有 **2.7 Gbps**——比一个中型视频站还小。**所以千万连接从来不是带宽问题，是 fd、内存、GC、以及「重连风暴」问题。** 找错瓶颈是最常见的评审失分点：会上说「加带宽」的，一般没算过这笔账。

### 单机容量账：一条连接 46 KB，从哪来

| 组成 | 每连接字节 | 说明 / 可控性 |
| --- | --- | --- |
| 内核 `struct sock` + skb 头 | 2,048 | 内核态，进程看不到但占物理内存；不可压缩 |
| 内核 RX buffer（`tcp_rmem` 低水位） | 8,192 | 默认 87 KB，**必须调小**；聊天帧 < 1 KB，8 KB 足够 |
| 内核 TX buffer（`tcp_wmem` 低水位） | 4,096 | 同上 |
| TLS 会话 + 记录缓冲（`tls.Conn`） | 6,144 | 握手期瞬时 16 KB，稳态降到 ~6 KB（帧小） |
| goroutine 栈 × 2（读 + 写） | 16,384 | Go 初始栈 8 KB，**帧大会涨栈**；不要在大帧里 `make([]byte,64K)` |
| `bufio.Reader` + 写批缓冲 | 4,096 | 可压到 1 KB（帧小） |
| 连接上下文（uid/dev/epoch/lastSeen/订阅指针/背压队列 4 KB） | 5,120 | 背压队列 256 帧 × 16 B 指针 = 4 KB |
| **合计** | **≈ 46 KB** | 取 46 KB 做容量计算 |

### 100 万 → 1000 万需要多少台

```
单机连接上限 = min(
    内存上限:  (16 GB × 60% − runtime 1.2 GB) / 46 KB × 1.25(碎片放大) ≈ 13 万,
    fd 上限:   nofile 262144 − 上游/日志/文件 2 万 ≈ 24 万,
    故障半径:  单台挂掉影响面 ≤ 8 万用户（4.8 分钟重连窗口内的扇出上限）,
    热点房间:  单台承载 8 万同房间连接时的合并下行 ≈ 160 万帧/s（见 §14.11）
)  → 取 8 万 / 台（内存实载 46%，留出 GC 与突发余量）

台数 = 1000 万 / 8 万 = 125 台
冗余 = × 1.25（滚动发布摘流窗口 20% + 单 AZ 故障 1/3 × 弹性）
     = 157 → 取 160 台（8 vCPU / 16 GB / 8 Gbps 内网，约 800 元/月·台）
网关月成本 ≈ 160 × 800 = 12.8 万元
```

**fd 与队列的三个致命参数**（写死在部署模板里，不写就等事故）：

```bash
# 进程级
nginx/gateway  soft nofile 262144     # 8 万连接 × 3（上游+文件）= 满负荷的 1.6 倍
# 内核级
net.core.somaxconn           = 16384  # 默认 4096，重连风暴时它就是第一道闸门
net.ipv4.tcp_max_syn_backlog = 16384
net.ipv4.tcp_rmem = 4096 8192 65536   # 低水位压到 8 KB，单连接省 79 KB
net.ipv4.tcp_wmem = 4096 4096 65536
net.ipv4.tcp_keepalive_time  = 60     # 只作补充手段，主判据是应用层心跳（§14.7）
net.ipv4.tcp_fin_timeout     = 15
fs.file-max                  = 2097152
```

> ⚠️ **`tcp_rmem` 调到 8 KB 是有代价的**：单连接吞吐上限下降到约 1 Mbps 以内（受 BDP 限制），跨省 RTT 40 ms 时约 250 KB/s。聊天够用，**但这条通道不能拿来传文件**——大文件走对象存储 + HTTP（→ [25 大文件分片上传](25-chunked-upload.md)）。这也是「网关不承载业务数据」的物理原因。

### GC 与内存碎片：千万连接真正的隐形税

单机 8 万连接、堆 5.8 GB 时，Go 的 GC 行为会变成架构约束：

| 项 | 不治理时 | 治理后 |
| --- | --- | --- |
| 分配速率 | 每帧 ×3 次分配（读缓冲、解包、写批）→ 9,000 帧/s × 1.2 KB ≈ **10 MB/s** | `sync.Pool` + 连接级预分配缓冲 → **< 0.5 MB/s** |
| GC 频率（GOGC=100，堆 5.8 GB） | 每 ~5.8 GB / 10 MB/s = 一次/580s，但每次 STW 标记 6 GB → CPU 峰值 30%，P99 抖动 40 ms | `GOMEMLIMIT=5.5GiB` + `GOGC=50` → 周期缩短但单体停顿 < 3 ms |
| 碎片率 | 8 万个连接结构散落成 30 万个小对象，页碎片 **18%–25%** | **连接槽位化**：`[]Conn` 按 1 万条一块预分配，连接分配/回收只改槽位状态 |

**三条硬纪律**（千万连接级别下违反任何一条，都会在 3 天内暴露）：

1. **连接结构不进 map 键值对**：`map[uint64]*Conn` 在 8 万条目下每次扩容要重哈希全部桶，产生 8 万次指针搬运（一次 200 ms 抖动）。用**槽位数组 + 开放寻址的 uid→slot 索引**。
2. **写批缓冲必须池化**：`writev` 的 iovec 数组、序列化后的帧字节，全部 `sync.Pool`。共享一条广播消息时，**用同一个 `[]byte` 切片给 8 万个连接引用**（见 §14.11），绝不为每个连接复制。
3. **禁止在连接 goroutine 里做任何阻塞调用**：查库、写 Redis、调鉴权服务都在注册阶段一次性做完；运行期只做「读帧 → 更新内存 → 入队」。一次 5 ms 的同步调用 × 8 万连接 = 400 秒的排队。

### 六步流程与每步的失败处理

| 步 | 动作 | 成本 | **失败形态** | **失败处理（写死的默认值）** |
| --- | --- | --- | --- | --- |
| ① DNS/GSLB | 返回区域 VIP，TTL 60s | < 1 ms | 某区域 VIP 全灭 / DNS 污染 | 客户端内置**多域名兜底列表**（主域 → 备用域 → IP 直连）；GSLB 健康检查 3 次失败即摘除，**TTL 不得超过 60s**，否则摘流不生效（§14.8 的前置条件） |
| ② LB → 网关 | TCP accept + TLS 握手 | 3–5 ms CPU | `accept` 队列溢出 / TLS 版本不匹配 | `somaxconn` 16384；超限时**延迟接受**（accept 后不立刻握手，进 hold 队列），绝不丢 SYN——丢 SYN 会让客户端看到「连接超时」而不是「服务繁忙」，从而触发最长 30s 的重试等待 |
| ③ 鉴权 | 验 token 签名 + 取授权上下文 | **本地 0.2 ms**（不调服务） | token 过期 / 密钥轮换期 | JWKS 公钥**本地缓存 5 分钟** + 后台刷新 + 旧密钥保留 24 小时（双 key 重叠）；只有「未知 kid」才回源一次。**鉴权服务不可用时降级：允许「只读鉴权」上线（能收不能发）**，而不是拒绝连接 |
| ④ 注册路由 | 写 `uid → {gw_id, epoch, conn_seq}` | Redis 1 次写 | Redis 超时 / 主从切换丢写 / 部分成功 | **本地重放队列**：写失败进内存队列（容量 2000/台），后台以 200 ms 退避重试；连接**继续可用**（可收消息靠 push 直连本机）但下行会被判「可能投错」，同时打 `route_degraded` 指标（事故二的修复点） |
| ⑤ 会话快照 | 拉订阅关系 + `last_seq` 未读差量 | 1 次 RPC + 1 次存储读 | 会话服务超时 | **连接不算失败**：先完成握手并标记 `SESSION_PENDING`，快照异步补；补完前只推「有新消息」的指针（不带内容），客户端点开走 HTTP 补拉 |
| ⑥ 心跳启动 | 服务端设读超时 = 2.5 × 心跳间隔 | 0 | —— | 见 §14.7（假死识别） |

> **这一节的核心纪律：连接的「可用」与「完备」必须分开判定。** 前五步里任何一步的**非鉴权失败**都不应该让握手失败——因为**握手失败的代价是客户端重试 → 放大风暴**（事故一）。正确姿势是「先接上（降级可用）→ 后台补齐 → 补齐失败才断」。这是千万连接级别与十万连接级别**最重要的形态差异**：小规模下「失败即拒绝」是干净的，大规模下「失败即拒绝」是自杀。

## 14.5 路由表设计（核心）：三种选型与容量估算

### 三种形态，先看结论

| 维度 | **A. Redis 集中式注册表** | **B. 一致性哈希粘性环** | **C. Gossip 自研路由扩散** |
| --- | --- | --- | --- |
| 原理 | 连接建立时写 KV，查表得 `gw_id`；网关可任选 | 客户端先取环，`gw = ring(uid)`；**路由不存，算出来** | 每台网关持有「分片 owner 表」，成员变更靠 SWIM/gossip 扩散 |
| 1000 万条的内存 | 裸数据 **240 MB**（24 B/条），带索引+副本 **6 GB** | **0**（只存环：160 台 × 64 B ≈ 10 KB/客户端） | 全量复制 **≈ 51 GB**（320 MB × 160 台）；分片 owner 表 **≈ 2 MB/台** |
| 查询延迟 P99 | L1 命中 0.05 ms / Redis 1.2 ms / DB 兜底 12 ms | **0 ms（本地算）** | 本地查 owner 表 0.02 ms，**跨机转发 +0.8 ms** |
| 变更传播 | 1 次写即生效（无传播） | 无变更（连接即绑定） | gossip 收敛 **200 ms – 3 s**（不可控，故障时最慢） |
| **网关故障时行为** | 路由指向死网关，靠 **epoch + 租约**识别，转离线库 | **该槽位所有用户全部重连**（环上没有替代者），换环需重建连接 | owner 表在 3 s 内收敛，期间投递失败（丢/重） |
| 扩容行为 | 无影响（新网关只是多了个写入者） | **环变动 → 1/N 连接必须迁移**，扩 20% 台数 = 迁移 17% 连接 | 分片转移 30–120 s，期间双写双读 |
| 写放大（续约） | 网关级租约 **16 次/s**（160 台 / 10s） | 0 | 心跳附带 gossip，**每台每秒数条** |
| 实现成本 | 低（Redis + 一层缓存） | **低但要改客户端 SDK**（发版成本最高的一项） | 高（成员协议、反熵、分区迁移、调试工具） |
| **判定** | ✅ **主选** | ⚠️ 只作为**A 完全不可用时的降级拓扑** | ❌ 千万级下不选（见下） |

### 容量估算：1000 万条路由到底占多少

```
每条路由的二进制布局（不用 JSON，不用十进制字符串——省 30% 内存）
  uid        8 B   uint64，不是 "1234567890" 的 10 B 字符
  gw_id      4 B   网关编号（≤ 65535 用 2 B，留余量取 4 B）
  epoch      8 B   单调逻辑时钟（见 §14.6），用于识别旧路由
  conn_seq   4 B   本连接序号，同一用户多设备时区分
  合计       24 B

裸数据        1000 万 × 24 B                    = 240 MB
Redis 单条目开销   dictEntry 24 + key robj/sds 32 + value robj/sds 48 + expires 32 + bucket 摊销 10
                                             ≈ 146 B → 1000 万 × 146 = 1.46 GB
1 主 2 从                                   = 4.4 GB
过载设计 ×1.4（增长 + 碎片 + 用户翻倍预留）   = 6.2 GB
→ 16 主 32 从（每主 4 GB 上限）的 Redis Cluster，内存占用 39%

但真正的约束不是内存，是 QPS：
  查表 74 万/s × (1 − L1 命中 87%) = 9.6 万/s  →  16 主 → 每主 6,000/s（极轻松）
  写表 3,000/s（新建）+ 3,000/s（摘除）      →  每主 375/s
  ⇒ 结论：路由表的瓶颈在「主从切换的丢写」与「冷启动回源」，不在吞吐。多买内存是浪费。
```

> **这张账最重要的推论**：Redis 内存只要 4 GB 级，却要 16 个分片——**分片的目的不是容量，是把「主从切换」的爆炸半径从 1/1 缩到 1/16**，并让 failover 只影响 62.5 万用户的路由。分片数由**故障半径**决定，不由数据量决定，这一点与 `[03 存储形态]` 里「分片数由回源 QPS 决定」的推导方向同源。

### 为什么不要 Gossip 全量复制

一个具体算式就能否掉它：

```
全量复制内存 = 1000 万 × 32 B（含索引） × 160 台 = 51 GB
变更广播带宽 = 3,000 次/s 变更 × 160 台 × 48 B ≈ 23 MB/s（常态）
重连风暴时   = 15,000 次/s × 160 × 48 B ≈ 115 MB/s ← 风暴会自我放大
收敛时间     = O(log N) 轮 × RTT = 200 ms ~ 3 s，且**故障时恰恰最慢**
```

**故障时最慢的机制，不能用来做故障恢复的核心依赖。** 这是选型时的第一性判据：**路由表的故障行为必须与故障本身解耦**——Redis 挂了，网关还能用 L1 + DB 兜底；Gossip 网络抖了，恰恰是它最不可用的时候。

## 14.6 读写路径：注册、摘除、与僵尸路由的三道闸

**图 2 · 路由表查询链路（下行投递的每一次查表）**

```
下行消息 send(toUid)   ← 来自推送服务/扇出服务，携带 msg_epoch = 写入时刻的逻辑时钟
   │
   ├─(1)─▶ L1 进程内 LRU（每台 20 万条，TTL 30s，命中 87%）
   │        ├─ 命中且 entry.epoch ≥ msg_epoch ────────────────▶ 投递到本机连接 ✅
   │        └─ 命中但 epoch < msg_epoch  → 视为未命中（旧值）──┐
   │                                                          │
   ├─(2)─▶ Redis Cluster（只读从节点，允许 stale read）  ◀─────┘
   │        key = r:{uid & 1023}:{uid}
   │        Lua：HGETALL 后校验 epoch ≥ ARGV[1]，不满足直接返回 nil（不返回旧值）
   │        ├─ 返回 {gw_id, epoch, conn_seq} ──▶ 写回 L1 ──▶ 投递 ✅
   │        └─ 返回 nil（路由不存在 or 已过期）──┐
   │                                            │
   └─(3)─▶ route_owner 表（DB，按 uid 分 64 库）◀┘
            ├─ 有记录且 gw_id 仍在线 ──▶ 用 DB 值修正 Redis（写回，epoch+1）──▶ 投递 ✅
            └─ 无记录 / gw 已下线 ──▶ 判定「离线」→ 写离线库（可补拉）──▶ 客户端下次上线补 ✅
                                      ⚠️ 任何情况下都不允许「丢弃」或「随机选一台网关」
```

三层的职责必须分清，混了就出事故：

| 层 | 存的什么 | 命中率目标 | 允许的失效 | 失效后行为 |
| --- | --- | --- | --- | --- |
| L1（进程内） | 热用户路由 | 87% | 允许 stale ≤ 30 s | epoch 过期即视为未命中 |
| Redis（分片） | 全量在线路由 | 12.9% | 允许 stale ≤ 复制延迟 | 不返回过期值（Lua 内校验） |
| DB（兜底） | **路由变更流水 + 在线网关表** | 0.1% | **不允许丢写**（同步双写） | 回源修正 + 打 `route_cold` 指标 |

### 注册（上线）：一次写 + 三道校验

```
1. 网关分配 conn_seq（本机自增），生成 epoch = max(本地时钟, Redis 当前 epoch + 1)
2. HSET r:{slot}:{uid} {gw_id, epoch, conn_seq}  +  PEXPIRE 90s
3. WAIT 1 120ms     ← 关键：至少 1 个从节点确认，耗时中位数 +1.1 ms
4. 写失败 → 进本地重放队列（2000 条/台，200 ms 退避，最多 30 s）→ 打 route_degraded
```

**第 3 步的 `WAIT` 是本篇最重要的单行命令**。它把事故二的「丢 2.8 秒写入」变成「丢 0 条 + 少数连接注册延迟 120 ms」。代价是注册 P99 从 1.3 ms 涨到 2.6 ms——**在 3,000/s 的写量面前这是免费的；在路由丢了之后找回来是 6 分钟 + 380 条不可恢复。**

### 摘除（下线）：先改路由，再关连接

顺序反了就是事故二：**必须先让新消息不再指向这台，再关连接**。

```
优雅下线：  draining 标记 → 等 30 s（让在途消息投递完）→ 删路由条目 → 关连接
粗糙下线：  关连接 → 删路由          ← 这 30 秒内投进来的消息全部写进死连接
```

### 僵尸路由：三种成因，三道闸

「僵尸路由」= 路由表里有条目，但那条连接早就不存在了。它是千万连接系统里**唯一一种必然发生的脏数据**（因为网关可能被 kill -9、机器可能断电、网络可能黑洞）。

| 成因 | 现场 | 自愈机制 |
| --- | --- | --- |
| 网关进程被 `SIGKILL` / 机器断电 | 8 万条路由全部悬空，无任何通知 | **闸 1 · 网关租约**：`gw_lease:{gw_id}` TTL 30 s，网关每 10 s 刷新；租约过期 → 该 `gw_id` 下所有路由批量判 stale（不用遍历 1000 万条，用 gw_id 反向索引 `gw_routes:{gw_id}`） |
| 连接被中间设备掐断（NAT 超时、4G 切换） | 网关不知道，路由还在 | **闸 2 · 连接级 TTL**：条目 `PEXPIRE 90s`，只由**心跳续约**刷新（心跳不涨 = 自动过期）；服务端读超时 75 s 先 close |
| 旧连接重连到新网关后，旧条目残留 | 同一 uid 两条路由 | **闸 3 · epoch 单调**：新注册 `epoch+1`；查表 Lua 校验 `epoch ≥ msg_epoch`，旧条目永远不会被投递到；30 s 后自然过期 |

**千万连接下不能给每条路由单独续约。** 1000 万条 / 90 s TTL = 11.1 万次/s 续约写——这一条就能把 Redis 打穿。正确的两道 TTL：

| TTL 类型 | 存在哪 | 周期 | 写放大 | 作用 |
| --- | --- | --- | --- | --- |
| **连接级 TTL**（逻辑） | 网关进程内存 `lastSeen` | 心跳 30 s 一次，**纯内存** | **0** | 识别假死连接（§14.7） |
| **网关级租约**（物理） | Redis `gw_lease:{gw_id}` | 10 s，**160 台共 16 次/s** | **16/s** | 识别「整台网关消失」 |
| **条目 TTL**（最终兜底） | Redis `PEXPIRE 90s` | 只在注册/重连时设一次 | 3,000/s（本来就是注册量） | 兜住前两者都漏掉的场景 |

> **这条设计的本质**：把「1000 万个对象的过期」压缩成「160 个对象的过期 + 1000 万个内存时间戳」。**任何需要给每个连接写一次外部的设计，在千万级都不成立**——这是本篇最容易被忽略、也最一票否决的算式。

## 14.7 心跳与假死：TCP keepalive 为什么一定不够

### 三类「TCP 认为活着、业务已经死了」的假死

| 类型 | 机制 | TCP 层为什么无感 |
| --- | --- | --- |
| **NAT 表项静默过期** | 运营商 NAT / 家用路由器删掉映射，不通知两端 | 连接进入半开（half-open）：发包不会收到 RST（路由器直接丢弃），要等**内核重传 15 次、约 15 分钟**才报错 |
| **客户端进程被冻结** | iOS 后台挂起、Android 冻结、用户锁屏 | 内核协议栈仍在（能回 ACK），业务线程不跑 → 心跳不发、消息不读 |
| **黑洞链路** | 4G/5G 切 WiFi、地铁隧道、部分运营商「伪在线」 | 数据包单向可通：下行能进（你写成功），上行全丢（ack 永远不来） |

`tcp_keepalive` 的天生缺陷：① 默认 `time=7200s` + `intvl=75s` + `probes=9` → **最坏 2 小时 11 分**才发现；② 即使调到 60 s，探测包也会被同一个 NAT 表项丢弃，**探测不到「应用已死」**；③ 它是内核行为，**无法携带业务语义**（我还订阅着哪些会话、我最后收到的 seq 是多少）。

### 心跳间隔的推导（不是拍脑袋给 30 s）

三条约束，取最小：

```
约束 1 · NAT 存活：心跳间隔 T < 最短 NAT 空闲超时 / 2
        实测最短：企业防火墙 60 s、部分路由器 120 s、运营商 300–1800 s
        → T < 30 s

约束 2 · 假死发现时间：P99 发现 ≤ 90 s（用户能忍的上限，超了就是「消息不通还不重连」）
        发现时间 = T × 连续丢失数(2) + 服务端超时余量
        → T ≤ 37 s

约束 3 · 成本：心跳帧数 = 在线连接 / T
        T = 5 s  → 1000万/5  = 200 万帧/s（网关 CPU 的 40%，不可接受）
        T = 30 s → 1000万/30 = 33.3 万帧/s（约 2,083 帧/s·台，占 6%）
        → T ≥ 20 s

交集：T = 30 s（前台） / 60 s（后台，App 进 background 后切）
服务端超时 = 2.5 × T = 75 s（前台） / 150 s（后台）
```

**为什么是 2.5 倍而不是 2 倍**：移动网络瞬时丢 1–2 个包很常见（电梯、地铁），2 倍会在弱网下误杀（1 秒内断连重连，反而放大风暴）；2.5 倍能容忍连续 1 次丢失 + 1 次抖动，误杀率从 0.9% 降到 0.12%（实测）。**误杀一个真连接的代价 ≫ 多留一个死连接 45 秒的代价**——死连接的资源成本是 46 KB，误杀的成本是一次重连（3–5 ms CPU + 1 次 Redis 写 + 客户端 1 次全量补拉）。

**有系统推送兜底时可以放宽**：iOS/Android 有 APNs/FCM 时，即使长连接断了也能被唤醒，心跳可放宽到 4.5 分钟（智能机省电策略下这是行业常见值）；**桌面/Web 端没有推送通道，必须 30 s**。这条差异要按端类型分别配置，不要全站一个值。

### 假死连接的识别与清理（四道判据，按成本排序）

| # | 判据 | 实现 | 检出时长 | 覆盖的假死类型 |
| --- | --- | --- | --- | --- |
| 1 | **读超时** | `SetReadDeadline(now+75s)`，每帧刷新 | 75 s | 冻结、半开、进程死 |
| 2 | **ack 停滞** | 连续下发 20 帧且 `ack_seq` 60 s 不前进 | 60 s | 黑洞链路（下行可写、上行全丢） |
| 3 | **写超时 / 背压水位** | 发送队列 > 256 帧或单次写阻塞 > 10 s | 10 s | 慢客户端（内存 / 弱网） |
| 4 | **心跳 RTT 抖动** | 最近 5 次心跳 RTT > 3 s | 2.5 min | 弱网（不清理，降级到推送通道） |

清理动作必须走**同一个函数** `closeConn(reason)`：删 L1 → 删路由（带 epoch 校验，防止删掉刚重连的新条目）→ close fd → 上报在线状态 → 释放槽位。**幂等**，因为它会被至少两条路径同时调用。

> ⚠️ 判据 2 与判据 3 的区别最容易搞混：**判据 2 是「你写的它没收到」，判据 3 是「它连收都收不动」。** 前者要立刻关（黑洞），后者要先降级（把大消息换成「有新消息」的指针，让客户端主动拉），只有降级后仍未缓解才关。混用会导致弱网用户被反复踢下线。

## 14.8 优雅摘流（核心）：先摘流量 → 通知重连 → 等排空 → 关连接

「优雅摘流」这个词被用得极烂，但它的**顺序**是刚性的，四步换任何一步都等于事故一：

| 步 | 动作 | 换顺序的后果 |
| --- | --- | --- |
| 1 | **摘流量**（LB/服务发现权重 0） | 先关连接再摘流：客户端重连会**又打回这台**，无限循环 |
| 2 | **通知客户端重连**（发 `server_draining` 帧，带 jitter 窗口） | 直接 close：客户端只看到 RST → 立刻重连（无延迟）→ 同时重连 |
| 3 | **等排空**（连接数曲线下降，85% 走完） | 不等就关：8 万条连接被服务端主动断，日志全是 `write: broken pipe`，无法判断是「排空完成」还是「服务端崩了」 |
| 4 | **关连接**（剩余的分批 close） | —— |

**图 3 · 优雅摘流时序（一台 8 万连接的网关，全程 61 秒）**

```
Controller    LB        gw-17(8万)         客户端(8万)       RouteFabric
    │          │             │                  │                │
 t=0├─权重0───▶│             │                  │                │
    │          │  (新连接不再进来；已建连接不受影响)              │
 t=1├──────────────────────▶│ DRAINING         │                │
    │          │             ├─写 draining=true, epoch+1────────▶│
    │          │             │                  │                │
 t=1│          │             ├── server_draining{retry_after=rand(0..45s)} ──▶│
    │          │             │                  │  ┄ 客户端各自算 jitter ┄
    │          │             │                  ├─ t=3.1s 重连 ──▶ gw-42    │
    │          │             │                  │   （握手+本地验签+注册）   │
    │          │             │                  ├─ t=17.4s 重连 ─▶ gw-08    │
 t=46│         │             │  连接数 8万→1.2万 │                │
 t=50├──────────────────────▶│ 剩余 1.2 万：再发 draining{delay=0}
 t=50│         │             ├── close 分批：每批 2%(1600) / 200ms ──▶│
 t=60│         │             │  连接数 = 0       │                │
 t=61│         │             ├─删除 gw-17 全部路由 / 回收租约 ─────▶│
    │          │             │ SIGTERM→优雅期 90s 内退出（SIGKILL 兜底）  │
```

### 重连风暴的三道防护（缺一道，事故一就重演）

**防护 1 · jitter：把 δ 函数摊成均匀分布**

```
无 jitter：8 万连接 / 1 s  = 80,000 conn/s（瞬间）
有 jitter：8 万连接 / 45 s =  1,778 conn/s（本机摊平）
160 台同时摘 1 台 × 45 s 窗口 → 全局峰值 ≈ 1,778 conn/s（远低于限流阈值 15,000）
```
jitter 必须由**服务端下发的窗口**决定（`retry_after = rand(0, 45s)`），不能由客户端本地随机——因为老版本 SDK 本地随机值可能是 0，你没法改线上 1 亿个客户端，只能改服务端下发的建议值。**能在服务端修的事，永远不要在客户端修。**

**防护 2 · 指数退避 + 慢通道降级**

```
delay_n = min(60s, 1s × 1.6^n) × (1 ± 20% jitter)
n=0: 1.0s   n=1: 1.6s   n=2: 2.6s   n=3: 4.1s   n=4: 6.6s  ... n≥10: 60s（封顶）
连败 5 次 → 切「慢通道」：UI 标「连接中」，同时开 HTTP 短连接轮询补拉未读
          （用户至少能读到消息，不会以为没网）
连败 10 次 → 弹「网络异常」+ 上报埋点（这是识别区域性故障的唯一手段）
```

**防护 3 · 服务端握手限流（按「新建连接/s」，不是按请求 QPS）**

| 限流点 | 维度 | 阈值 | 超限动作 |
| --- | --- | --- | --- |
| LB / 接入层 | 全局新建连接/s | 15,000/s（5 倍常态） | **延迟接受**：accept 后进 hold 队列慢慢握手，不丢 SYN |
| 单网关 | 本机新建连接/s | 300/s | 同上；hold 队列深度上限 = 1,500，满了才返回 `503 + Retry-After: 5` |
| 单 IP / 单设备 | 每 10 s 新建次数 | 3 次 | **hold 3–8 s**（不是拒绝，因为拒绝会让 SDK 立刻重试） |
| 鉴权服务 | 回源 QPS | 常态的 2 倍 | 熔断 → 降级为「只读鉴权」（走本地 JWKS 验签，不查授权表） |

> **为什么必须「延迟接受」而不是「拒绝」**：拒绝连接的客户端行为是**立刻重试**（大多数 SDK 如此），等于 1.4 倍放大；延迟接受的客户端行为是**等待**（TCP 握手慢但会成功），是 0 倍放大。**在风暴中，让请求变慢是治理，让请求失败是纵火。** 这条原则与 `[07 变更治理 · §7.4]` 的「长连接灰度单位是用户+时间窗」同源。

### Go 骨架：网关连接管理（注册 → 心跳超时 → 批写 → 摘流）

```go
// 单连接 = 两个 goroutine + 一个槽位（骨架，非完整实现）
func (g *Gateway) serve(c *Conn) {
	defer g.freeSlot(c)                     // 幂等：fd、L1、路由、槽位一处释放
	go c.readLoop(g)                        // 上行：心跳/ack/发送
	c.writeLoop(g)                          // 下行：批写 + 摘流 + 背压
}

func (c *Conn) readLoop(g *Gateway) {
	defer close(c.gone)                     // 任何退出路径都必须关 gone
	for {
		c.ws.SetReadDeadline(time.Now().Add(g.hbTimeout)) // 75s = 2.5 × 30s
		typ, p, err := c.ws.ReadFrame()
		if err != nil {                     // EOF / RST / 读超时 三合一，都判假死
			g.metrics.Drop(c.uid, reasonOf(err)); return
		}
		switch typ {
		case FrameHeartbeat: c.lastSeen = nowNano()  // 只改内存，绝不写路由表
		case FrameAck:       g.ackWindow.Advance(c, p)
		case FrameSend:      g.upstream.Publish(c, p) // 上行只进 Kafka，不在此做业务
		}
	}
}

func (c *Conn) writeLoop(g *Gateway) {
	t := time.NewTicker(20 * time.Millisecond)   // 攒批：20ms 或 16 帧，谁先到算谁
	defer t.Stop()
	for {
		select {
		case <-c.gone:
			return
		case <-c.drain:                        // 摘流：通知而不是关闭
			c.ws.WriteFrame(FrameDraining, hint(c.uid)) // retry_after=rand(0,45s)
			g.metrics.Inc("drain_notified")     // 之后交给客户端自己走，服务端不 RST
		case f := <-c.out:                      // 有界队列，满了走降级分支
			batch := append([]byte(nil), f...)
			for len(batch) < c.maxBatch && len(c.out) > 0 {
				batch = append(batch, (<-c.out)...) // 零拷贝共享：广播时同一 slice 复用
			}
			if err := c.ws.Write(batch); err != nil { return }
		case <-t.C:
			if c.out2len() > 256 {              // 背压水位：只发「有新消息」指针
				c.degradeToPointer()
			}
		}
	}
}
```

> 这段代码里被注释掉的每一行都是事故：**`lastSeen` 只写内存**（否则 33 万次/s 心跳变成 33 万次/s Redis 写）；**`drain` 分支只发帧不关闭**（否则摘流变踢人）；**批写在池化的 slice 上追加**（否则 8 万连接 × 每秒 0.07 条 × 2 次分配 = GC 抖）。

## 14.9 连接迁移与会话：重连之后，「我在哪些会话里」从哪来

网关故障后客户端连到新节点，新节点**什么都不知道**。要恢复三样东西：订阅关系、未读差量、未 ack 的在途消息。三样东西存的地方完全不同——**这是本节唯一要记的事**。

| 状态 | 规模 | 变更频率 | 存在哪 | 为什么不能存别处 |
| --- | --- | --- | --- | --- |
| **会话订阅**（我参与了哪些会话、置顶/免打扰） | 每用户 20–300 条 | 低（进群/退群） | **DB（`session_member`）+ 客户端本地** | 存网关 = 换机器就丢；300 个会话 × 1000 万用户 = 30 亿行，不可能全塞 Redis |
| **本连接订阅集合**（我这次连接关心哪些 topic，如对方正在输入） | ≤ 200 个 topic | 高 | **网关进程内存**（`[]topicID` 或 Roaring Bitmap） | 只在连接生命周期内有意义，进程退出即作废 |
| **房间成员**（万人群、直播间） | 单群可达 10 万 | 中 | **不在网关**，在扇出服务的成员分片（Redis Set / Bitmap） | 一个 10 万人的群在每个成员网关都存一份 = 160 × 10 万 = 1600 万条冗余 |
| **未读游标** `last_seq` | 每 (用户, 会话) 一条 | 高（每读一条） | **DB + 客户端本地**，服务端只存「已投递最大 seq」 | 存服务端内存 = 换机丢；靠客户端上报才可靠 |
| **在途未 ack 消息** | 每连接 ≤ 100 条 | 高 | 网关内存环形缓冲（60 s）+ 消息存储的真实 seq | 只保留 60 s，重连后靠补拉 |

### 迁移恢复的四步（客户端主导，服务端只提供三个幂等接口）

```
客户端重连成功（携带 last_seq_map: {sessionID → 我收到的最大 seq}）
 → ① GET /session/snapshot        拿会话列表 + 每会话的 server_max_seq（一次 RPC，≤ 50 KB）
 → ② 差量计算：server_max_seq − last_seq_map，按会话排序取前 N（N ≤ 500 条/会话，总量 ≤ 2000 条）
 → ③ 若差量 > 2000 条 → 服务端只回「指针」，客户端走 HTTP 分页补拉（不占长连接带宽）
 → ④ 客户端上报新的 last_seq（批量，5 s 一次）→ 同时清掉服务端「未 ack 缓冲」
```

**关键设计：`last_seq` 由客户端上报，不由服务端猜测。** 服务端只知道「我发出去了多少」，不知道「你收到了多少」——两者之差就是重连时必须补的东西。这也是 `[15 消息存储与分发]` 里 seq 语义的地基：**seq 必须是每会话单调递增的存储侧序列号，不能是「网关发送序号」**，否则换网关后序号从 1 重来，补拉就完全失效。

> ⚠️ **一个必须提前决定的边界**：离线超过 7 天的会话，差量可能是 10 万条。这时候**不能补**（一次重连拉 10 万条会把网关和客户端同时打挂）。正确姿势是「补摘要 + 首屏 50 条 + 提示『以上为历史消息』」，超过 30 天进归档层。这个阈值必须在**建模阶段**写进协议（`/session/snapshot` 的 `history_hint` 字段），事后补就要改 1 亿个客户端。

## 14.10 下行消息的可靠性：ack 放哪里，决定了重连要补多少

长连接最容易被误判为「可靠」——它看起来是条一直连着的管子。**但网关进程会重启、NAT 会超时、客户端会切网**，所以下行必须当作一条会丢、会重、会乱序的链路来设计。

### 三种 ack 位置，三种补拉量

| ack 位置 | 语义 | 丢消息风险 | 重连补拉量 | 适用 |
| --- | --- | --- | --- | --- |
| 无 ack（fire-and-forget） | 网关写出即认为送达 | **高**：内核缓冲区满时静默丢 | 无法补（不知道丢在哪） | ❌ 不可用于消息类 |
| 网关级 ack | 网关写进 socket 缓冲区即记 ack | 中：客户端崩溃后这段全丢 | 客户端 last_seq 差量 | ✅ **默认选择** |
| 端到端 ack | 客户端回执后才删服务端缓冲 | 低 | 只需补极小窗口 | 仅关键消息（支付/红包） |

**关键结论：ack 由网关做，但「我收到了多少」必须由客户端上报 last_seq。** 网关只知道「我发出去了多少」——它无法区分「客户端收到了」和「客户端正在重启」。这两个数之差，就是重连时必须补的东西。这也是 → [15 消息存储与分发](15-message-store.md) 里 seq 语义的地基：**seq 必须是每会话在存储侧单调递增的序列号，不能是「网关发送序号」**，否则换网关后序号从 1 重来，补拉就完全失效。

### 重与乱的处理责任在客户端，但服务端必须给去重锚点

下行重复几乎必然发生（ack 丢失 → 服务端重发）。服务端能做的是：**给每条消息一个 `(conversation_id, seq)` 作为幂等键**，客户端按 seq 去重并丢弃小于已收最大 seq 的包。乱序只可能出现在「多路复用 + 重发」的场景，处理方式同样是按 seq 重排、留一个滑动窗口。

> 记录一条铁律：**下行链路的幂等键必须是存储侧的 `(cid, seq)`，不能是消息体的 hash**——同一个 `(cid, seq)` 被重发两次是同一件事，而消息体相同不代表是同一条消息（比如「好的」在会话里出现 200 次）。

## 14.11 广播与房间：单播路径的优化，在广播场景全部失效

| 形态 | 扇出规模 | 实现 | 关键约束 |
| --- | --- | --- | --- |
| 单播 | 1 | 查路由表 → 写对应连接 | 路由表查询延迟是唯一瓶颈 |
| 小群（≤500） | 500 | 服务端展开成 500 条单播，批量写 | 同一台网关上的成员要**合并成一次 syscall 批写** |
| 大群 / 万人 | 万级 | 读扩散：只推「有新消息」通知，客户端主动拉 | 扇出成本从服务端转移到存储与客户端 |
| 直播间 / 万级广播 | 十万到千万 | 与消息不同：走**分层广播树**或 CDN 级推送 | 不保证送达，允许丢帧，靠「拉最新状态」兜底 |

**广播形态与消息形态必须分开设计**，这是很多人踩过的坑：把直播间弹幕塞进 IM 的可靠通道，结果是每个弹幕都要 ack + 补拉，网关 CPU 全耗在可靠机制上，而弹幕本来就不需要可靠。→ [13 亿级粉丝互关与推送](13-fanout-push.md) 的扇出模型是第三种形态（写扩散到收件箱），三者不要混用一套代码。

## 14.12 L0 → L5：连接数每涨一个量级，坏的东西都不一样

| 阶段 | 形态 | 连接规模 | **换挡信号（硬阈值）** | 代价 |
| --- | --- | --- | --- | --- |
| L0 | 单机 WebSocket，连接存在进程 map 里 | 1 万 | 单机 fd / 内存到 60% | — |
| L1 | 多网关 + Redis 路由表（`uid → gw_id`） | 10 万 | Redis 单实例 QPS > 5 万 | 路由查询成为关键路径 |
| L2 | 路由表分片 + 本地缓存路由 | 100 万 | 路由缓存不一致导致的消息误投 > 0.1% | 一致性变弱 |
| L3 | 网关分组（按 uid hash）+ 组内广播 | 300 万 | 跨组广播风暴 / 单组重启影响面过大 | 运维复杂度 |
| L4 | 自研 gossip 路由 + 连接迁移 + 优雅摘流 | **1000 万** | 路由表内存 > 单机上限 / Redis 网络带宽打满 | 一致性与调试难度陡增 |
| L5 | 多地域 + 就近接入 + 单元化 | 5000 万+ | 跨地域延迟 > 80 ms / 单地域容量上限 | 跨地域状态同步、脑裂 → [10 多活与单元化](10-multi-active-and-cell.md) |

> **L1→L2 的临界点要特别注意**：Redis 路由表在 10 万连接时是「够用的」，但它有个隐蔽的天花板——**网关重启时 10 万条路由要同时删或同时写**，Redis 的 QPS 会被这波尖峰打满，而恰恰这时候是最需要它可用的。所以 L2 不是「量大才做」，是「一旦你有了批量上下线，就必须做」。

## 14.13 这个形态特有的崩法

| 失效 | 长什么样 | 定位方法 | 预防 |
| --- | --- | --- | --- |
| 重连风暴 | 网关一重启，鉴权 QPS 涨 50 倍，鉴权服务先挂 | 看鉴权入口 QPS 与网关重启时间相关性 | **jitter + 指数退避 + 服务端握手限流**（三道缺一不可） |
| 僵尸路由 | 消息投到已死的网关，发送成功但永远收不到 | 对比「路由表条目数」与「实际连接数」 | 心跳续约 + TTL 自动摘除 |
| fd 泄漏 | 连接数缓慢上涨直到 `too many open files` | 定期采样 `/proc/<pid>/fd` 数量 | 连接关闭必须走 defer 级联关闭（Go 骨架见 §14.8） |
| 慢客户端拖累 | 单个客户端不收数据，网关写阻塞 → 整个连接队列堆积 | 网关侧发送队列长度 P99 | 每连接独立发送队列 + 队列满即断开（保护其他连接） |
| 心跳参数照抄 | 移动端频繁重连或假死连接堆积 | 按网络类型分组看重连率 | 心跳间隔按 NAT 超时推导（§14.7），不同端不同参数 |
| 路由表主从切换 | 切换后几十秒内消息大面积误投 | 路由表切换时间与误投率曲线 | 路由表本身走多级缓存 + 降级为「本地已知路由」 |

## 14.14 砍掉 90% 预算

连接网关从 120 台砍到 12 台、路由表从自研 gossip 退回单 Redis、去掉优雅摘流：

| 保留 | 砍掉 | 后果 |
| --- | --- | --- |
| 单 Redis 路由表 + 本地路由缓存 | gossip、连接迁移、多地域 | 路由表成单点，但 100 万连接下 1 主 1 从够用 |
| 心跳 + TTL 摘除 | 优雅摘流、分层广播 | 网关重启会引发重连风暴，**只能靠夜间低峰发布**规避 |
| 批写 + 每连接队列 | 独立发送队列、慢客户端隔离 | 一个慢客户端可能拖慢同批次的其他连接 |

**结论：这个系统的必需品只有三样——`(cid, seq)` 幂等键、客户端上报 `last_seq`、心跳续约的路由表。** 优雅摘流、连接迁移、分层广播都是规模驱动；但**重连退避与 jitter 是无论如何都不能砍的**，它是唯一一个「成本几乎为零、却能挡住最致命事故」的机制。

## 14.15 十分钟答题卡

```
1  量级    1000 万连接 → 单机 100 万上限（fd + 内存账）→ 120 台网关
2  真问题  「谁在哪台机器」的路由表本身是分布式系统，它挂了消息全部送不达
3  领域    连接状态在网关内存（真源），路由表是投影（可重建）
4  容量    per-conn 内存 × 连接数 = 机器数；给具体字节数，别说"很省"
5  路由    L1 Redis → L2 分片+缓存 → L4 gossip；换挡信号是"批量上下线的尖峰"
6  心跳    TCP keepalive 不够；按 NAT 超时推导间隔；心跳续约路由表
7  摘流    先摘流量 → 通知重连 → 等排空 → 关连接；三道防护防重连风暴
8  可靠性  网关 ack + 客户端上报 last_seq；幂等键是 (cid, seq)
9  广播    单播/小群/大群/万级广播是四种形态，不要共用一套可靠机制
10 必需    (cid,seq) 幂等键、last_seq 上报、心跳续约路由表 + 退避 jitter
```
