# 09. 开放平台：契约、版本与配额

> **状态**：`已完成（初稿）` ｜ **所属**：第二部分 · 空白横切 ｜ **编号**：09 / 26
> **本篇定位**：全库唯一讲「**把系统交出去给别人用**」的一篇。内部系统的失败半径是一个团队，开放平台的失败半径是 300 家公司、300 条发布流水线，以及你根本看不见的 300 份对账表。本篇的产物不是网关架构图，而是**一份可以进 CI 的兼容性规则表 + 一套配额契约 + 一条弃用时间轴**。
> **本篇唯一真问题**：平台化的第一道门槛不是技术能力，而是**契约稳定性和「十年不破坏」的纪律**——你自己改一行代码的便利，等于 300 家接入方的一次故障。
> **读法**：§09.8 兼容性规则表是全篇核心，可直接当 code review checklist 用；§09.4 与 §09.10 给配额的推导与实现；§09.15 专治「内部灰度把第三方打出两套行为」；赶时间只看 §09.17。

## 09.1 事故引子：两次「我们自己觉得很小的改动」

### 事故一：`amount` 从整数分改成浮点元，300 家接入方对账全错（2025-04-08）

发布理由是产品经理的一句话：「接入方一直在抱怨每次都要除以 100，直接把元给他们吧。」改动量：一行 DTO 字段类型。

| 时间 | 事件 | 数据 |
| --- | --- | --- |
| 08:50 | 发布 v2.3：`order.amount` 由 `int64`（分）改为 `double`（元） | 1 行字段改动 |
| 08:55 | 内部 3 个消费方已同步改完，集成测试全绿 | 覆盖率 84% |
| 09:02 | 接入方 A 的日对账跑出 GMV 放大 100 倍 | 该客户日均 41 万笔 |
| 09:15 | 客服开始进线，现象各不相同：有的金额 ×100、有的 ×0.01、有的出现 `12.300000000000001` | 7 家 |
| 09:40 | 定性为字段语义变更，且**字段名不携带单位** | 影响面 300 家 |
| 10:20 | 回滚发布（38 分钟）。服务端已回滚，但接入方用它算过的数**已经落库、已经开票** | 回滚修不了别人的库 |
| 04-08 ~ 04-19 | 逐家协助重算与冲正；11 家客户的 ERP 已自动开票 | 217 张发票作废，人工对账 12 人日 |

根因三条，没有一条是「发布手滑」：

1. **字段名不携带单位**：`amount` 没说清是分还是元，读代码的人只能靠猜，猜错的人不会报错；
2. **JSON 是隐式契约**：`int64 amount_cents` 能表达单位与精度，而线上只有 `{"amount":1230}`；改成 `double` 又引入二进制浮点误差，行级求和会差 1 分，**而 1 分钱的差异在对账口径里叫「不平」**；
3. **兼容性没有门禁**：灰度只覆盖内部 3 个服务，而外部谁在用、用什么客户端、解析成什么类型，平台**根本不知道**。

### 事故二：没有租户配额，一个大客户导入 2000 万条，把全平台打挂 40 分钟（2025-11-18）

| 时间 | 事件 | 数据 |
| --- | --- | --- |
| 10:02 | 铂金客户 X 首次使用批量导入，一次性提交 2000 万条商品数据 | 该租户日常占平台调用 1.2% |
| 10:03 | 平台没有批量端点，客户端 200 并发逐条 `POST /v1/items` | 2000 万 ÷ 500 = 4 万个请求，压缩在 30 秒内 |
| 10:04 | 入口 QPS 从 3,200 涨到 **41,000**（12.8 倍） | 全局阈值 50,000，**没触发** |
| 10:05 | 订单库连接池 800 全占满（单次占用 50 ms，理论容量 16,000 QPS） | 需求是容量的 2.6 倍 |
| 10:06 | **全部租户** P99 从 180 ms 涨到 8.4 s，错误率 61% | 300 家一起挂 |
| 10:09 | 值班同学手工停掉 X 的 API key | 定位「是谁」用了 7 分钟 |
| 10:42 | 连接池恢复、队列排空，SLO 恢复 | 影响 40 分钟 |
| 事后 | 47 万次 API 调用失败、9 家触发 SLA 条款 | 赔付 42 万元；客户 X 也很委屈：没人告诉他有上限 |

根因同样三条：**只有全局阈值、没有租户维度配额**（维度选错比不限流更危险，见 `eng/15`）；**批量场景没有专用通道**（逐条 POST 是平台自己的文档教出来的用法）；**没有「相对基线异常」告警**（单租户涨 30 倍，大盘只涨 12.8 倍，被"整体正常"掩盖）。

> 两次事故正好构成本篇骨架：**第一次是契约的失败（语义变更 + 无门禁），第二次是配额的失败（维度错 + 无异步通道）。** 共同点：平台一直把接入方当成"能同步改代码的自己人"。

## 09.2 到底是什么：开放平台不是「内部 API + API Key」

**定义**：开放平台 = 一组**对不特定外部方做出、且有效期以年计**的接口承诺。它必须同时具备四件事：**契约（说清楚）、配额（用得起）、可观测（查得到）、退出（下得来）**。缺任何一条，它都只是"把内网端口映射到公网"。

| 你以为的开放平台 | 为什么不是 | 缺了它会怎样 |
| --- | --- | --- |
| 内部 API 前面加个 API Key | 内部 API 的语义随时可改（你们能同步改），外部不能 | 事故一 |
| 做一个开发者门户和文档站 | 文档是**描述**，契约是**承诺**；文档可以改，承诺不能 | 文档说 A、实现是 B，联调第一天就失信 |
| 多租户 SaaS 后台 | SaaS 共享一个**产品**，开放平台共享一个**契约**；前者可以改 UI 与默认值 | 把 UI 当契约，改一次布局炸一批集成 |
| 有 SDK 就行 | SDK 只是把契约包一层；SDK 版本与 API 版本不脱钩时，升级 SDK 等于逼客户改代码 | 客户锁死在两年前的 SDK |
| 有签名 + HTTPS 就安全了 | 安全回答「谁能调」，开放平台还要回答「谁调了什么、越权怎么发现」 | §09.14 的越权 |

平台形态只有一张图，注意两个方向：**契约注册中心向下约束一切**，**开放网关是唯一出口**。

```
        ┌────────────── 契约注册中心（唯一事实源）──────────────┐
        │ OpenAPI spec · 错误码表 · 枚举字典 · 事件 schema · 弃用登记 │
        └──────┬────────────────┬──────────────────┬───────────┘
               │ 生成            │ 校验             │ 审判
      ┌────────▼──────┐  ┌──────▼──────────┐  ┌────▼─────────────┐
      │ SDK（多语言/多版本）│ │ 契约测试（CDC）  │  │ 兼容性门禁（CI） │
      └───────────────┘  └─────────────────┘  └──────────────────┘
┌──────────────────── 开放网关（Go）─────────────────────────────────┐
│ 认证(scope) → 租户配额(双桶) → 幂等键 → 路由 → 审计 → 计量          │
└───────────┬────────────────────────────────────┬───────────────────┘
            ▼                                    ▼
      业务微服务（Java）                    事件投递器 Webhook
      幂等 / 事务 / 状态机                  签名 · 重试 · 死信 · 自助重放
```

## 09.3 唯一真问题

> **你的每一次「顺手改一下」，对内部是 1 次发布，对外部是 300 次故障，而且不可回退**——因为回滚能修你的服务端，修不了别人已经落库、开票、发给终端用户的数据。

三条推论，本篇后面每一节都是它的展开：

| 推论 | 因此必须 |
| --- | --- |
| 破坏一次的成本 ≫ 兼容一百次的成本（代价极端不对称） | 默认**只做加法**；破坏性变更必须走新字段双写 + 弃用流程 |
| 你不知道谁在用、用哪个字段 | 必须**测量**调用方：SDK 版本分布 + 字段使用率 + 错误码分布，否则门禁无据可依 |
| 外部是「不可控的慢变量」（季度级发版节奏） | 任何内部节奏——灰度、重构、甚至删一个日志字段——都不能以**请求**为单位作用于外部 |

「测量」是所有门禁的输入，却最常被跳过：`300 家在册 × 6 个集成点 ≈ 1,800 个在跑的客户端`，而平台只看得到 `User-Agent` 与 API key，**没有任何字段级使用信息**。所以「删这个字段影响多少家」的默认答案是"不知道"；唯一解法是网关层记一张**字段使用率表**（响应字段名 × 租户，30 天聚合），否则你只能靠"通知过 4 次了"来决定下线。

## 09.4 量级与预算：配额是反推出来的，不是拍的

```
接入方           300 家（在册），Top 20 占调用量 68%
日调用           3.2 亿次（读 82% / 写 16% / 批量与导出 2%）
均值 QPS         3.2e8 / 86400 ≈ 3,700
峰值系数         ×3.4（上午对账高峰 + 月末结算）→ 12,600 QPS
Webhook 事件     3.2e8 × 20% ≈ 6,400 万条/天（峰值 3,000 条/秒）
```

容量反推（与 `eng/15` 的公式同源，这里只给结论式）：

```
订单库可用连接 800，单次占用 50ms   → 800 / 0.05 = 16,000 QPS
× 安全系数 0.75                     → 平台可放行 12,000 QPS
峰值需求 12,600 略大于 12,000        → 峰值期把 write 族配额收紧 20% 兜住
```

配额分摊表。关键不是数字，而是最后一行那条规矩：

| tier | 家数 | 稳态配额 S（QPS） | 突发额度 cap | 日调用上限 | 备注 |
| --- | --- | --- | --- | --- | --- |
| 自助 | 210 | 8 | 480 | 20 万 | 共享池，允许被挤 |
| 标准 | 70 | 40 | 2,400 | 200 万 | 有 SLA，无赔付 |
| 企业 | 18 | 250 | 15,000 | 2,000 万 | 有赔付 |
| 铂金 | 2 | 1,500 | 90,000 | 不设（月度结算 + 预留容量） | 专属 token 分片 |
| 合计 | 300 | **11,980 ≈ 12,000** | — | — | 稳态配额加总**必须等于容量** |

- 210×8 + 70×40 + 18×250 + 2×1,500 = 1,680 + 2,800 + 4,500 + 3,000 = **11,980**。
- **稳态配额加总必须等于平台容量**：远超容量时"配额"就成了彩票——超额时随机谁先死，而每个人都以为自己"没超"。这正是事故二里全局阈值 50,000 的荒谬：它对单个租户毫无约束力。
- 日调用上限是**天花板而非预留**，必然超卖（5.4 亿 > 3.2 亿实际），由 Top 20 的实际用量分布兜住。

SDK 与契约测试的预算，决定了你能承诺多快的兼容响应：`3 语言 × 最近 4 个 major = 12 条 SDK 流水线`，`OpenAPI N/N-1 × 20 家头部客户 Pact = 22 条契约流水线`，单条 6 分钟——必须并行，串行则没人愿意跑，门禁就形同不存在。

## 09.5 契约七件事：一次定死，十年不动

| 契约项 | 必须一次定死 | 定错的代价 | 推荐写法 |
| --- | --- | --- | --- |
| **幂等键** | 写接口支持 `Idempotency-Key` 请求头，客户端生成（UUIDv7），服务端保留 7 天并返回首次响应快照；同 key 不同 body → 422 `PLATFORM.IDEMPOTENCY_CONFLICT` | 幂等键放 body 里"让对方自己记得"，等于没有；重试即重复扣款 | **Header + 服务端快照**，不放 body、不放 query |
| **错误码体系** | 三层结构、业务码不可变、明细可变（§09.6） | 新需求加一个 code，两年后 300 个码、语义重叠 | L1 HTTP / L2 业务码（机器 switch）/ L3 明细（人看） |
| **分页方式** | 游标分页，`cursor` 为不透明字符串（base64 内含边界，客户端不得解析）；`limit` 默认 20、上限 200 | offset 分页在外部数据只增不减的前提下**结果必然漂移**：导出漏行、对账缺条，且不可复现 | 与 [12 短链 · §12.7](12-shortlink-system-design.md) 同一条结论：深分页必须游标 |
| **时间与时区** | 一律 UTC，RFC 3339（`2025-11-18T02:03:04Z`）；毫秒时间戳字段名带 `_ms` | 返回本地时区字符串或 `yyyy-MM-dd HH:mm:ss`（无时区），跨时区客户差 8 小时 | 永不带本地时区；相对时间只给 duration |
| **金额与精度** | `int64` 最小货币单位 + 字段名带单位（`amount_cents`）+ `currency`；或字符串十进制 `{"amount":"12.30"}` | 事故一：改类型 + 不标单位 + 二进制浮点 | **JSON 里绝不出现浮点金额**；精度属于契约 |
| **枚举未知值** | 客户端必须容忍未知枚举（映射为 `UNKNOWN` 并保留原值）；服务端永不复用旧值语义、永不删除枚举值 | 客户端 `switch` 崩在 default，或把新值当旧值处理 | 加值前先确认已发版 SDK 有兜底（顺序见 §09.15 先扩后收） |
| **批量接口上限** | 单请求 ≤ 500 条且 ≤ 1 MB；超限必须走异步 job：`202 + job_id`，结果与错误明细可下载 | 事故二：没有批量端点 → 逐条 POST → 同步 QPS 被打爆 | 批量是**独立接口族 + 独立配额（按行/天）** |

一句话纪律：**七件事里任何一件"以后再说"，两年后都要用一次大版本 + 一次客户迁移来还。**

## 09.6 错误码体系：三层、不可变、可决策

| 层 | 谁看 | 可变性 | 例子 |
| --- | --- | --- | --- |
| L1 HTTP 状态码 | 网络、网关、所有人 | 严格遵循 RFC，**永不自定义** | 400 / 401 / 403 / 404 / 409 / 422 / 429 / 500 / 503 |
| L2 业务错误码 | 接入方的**代码**（唯一允许 `switch` 的东西） | **不可变**：只新增，不改语义，不删除；按段位登记 | `ORDER.AMOUNT_MISMATCH`、`PLATFORM.RATE_LIMITED` |
| L3 明细原因 | 人：日志、工单、调试 | **可变**，随时新增与改文案，客户端**不得**编程依赖 | `detail.field="amount_cents"`、`detail.request_id`、`detail.hint` |

四条原则：

1. **L2 是契约的一部分，L3 不是。** 把「哪个字段错了」「给用户看什么提示」塞进 L3，你就能随意改文案与提示而不违约。
2. **码段位分配**：`10xxx` 通用与鉴权、`20xxx` 订单、`30xxx` 支付、`40xxx` 平台与配额、`50xxx` 导入导出。新业务先领段——撞码比错码更难查。
3. **每个 L2 码必须有四件套**：含义、可重试性、客户端该做什么、什么时候会变（答案：永不）。
4. **`INTERNAL.UNKNOWN` 是失败而不是"未知"**：它必须 0 容忍告警，出现即代表有未分类异常在漏。

客户端按错误码决定行为的**三分类表**（这是本篇给客户端的唯一产物，SDK 里应直接实现）：

| 分类 | 典型码 | 客户端必须做 | 客户端绝不能做 |
| --- | --- | --- | --- |
| **可重试**（自动） | 429 `PLATFORM.RATE_LIMITED`、503、`PROVIDER.TIMEOUT`、网络错误、`CONFLICT.LOCK` | 指数退避 + 全抖动，**尊重 `Retry-After`**；仅对幂等请求重试，且**复用同一个 Idempotency-Key**；上限 5 次 | 立即重试；无限重试；换一个新幂等键重试（= 重复下单） |
| **不可重试**（立即失败） | 400/422 `VALIDATION.*`、401、403、404、`CONFLICT.STATE` | 归因到调用方 bug：按 `detail.field` 修正后由**业务**决定是否重发 | 重试——会把一个 bug 放大成 5 倍流量，且永远不会成功 |
| **需人工** | `ORDER.AMOUNT_MISMATCH`、`ACCOUNT.RECONCILE_DIFF`、500 中「已提交但响应丢失」 | 落人工/工单队列，附 `request_id` + 幂等键，48 小时内平台可查 | 自动补偿——会重复扣款，且破坏对账口径 |

实现上给显式字段 `error.retryable`：让机器不看文档也能判断，文档负责解释"为什么"。

```json
{ "error": {
    "code": "PLATFORM.RATE_LIMITED", "retryable": true,
    "message": "quota exceeded for class=write",
    "detail": { "class": "write", "limit": 250, "remaining": 0, "reset_ms": 1740000000000 },
    "request_id": "req_01J8Z9K3" } }
```

## 09.7 版本策略：四种方案的代价与适用

| 方案 | 怎么做 | 代价 | 适用 | 判断 |
| --- | --- | --- | --- | --- |
| **URL 版本** `/v1/` | 路径带版本，网关按前缀路由 | 一旦出现 `/v2`，两版要并行 12–18 个月，业务代码里长出 `if (v1)`；**接入方没有迁移动力，会永久留在 v1** | 结构性破坏（认证模型、资源层级）不可避免时 | ✅ 作为**逃生舱**，每年至多一次 |
| **Header 版本** `Accept: application/vnd.acme.v2+json` | URL 不变，内容协商 | **不可见**：CDN 缓存键、日志、APM、告警全要额外配置，值班看流量图分不清版本；接入方最容易漏 | 极少 | ❌ 不作主策略 |
| **字段级演进**（protobuf / GraphQL） | protobuf 有字段号 + `optional/reserved`，天然向后兼容；GraphQL 支持 `@deprecated`、只加不改 | GraphQL 允许客户端自定义查询，**配额与延迟预算失控**（一个深查询能打穿 DB，必须做深度/复杂度限制）；protobuf 对外部有工具链门槛 | protobuf：内部与高性能对接方、gRPC 通道；GraphQL：只用于读型聚合面 | ⚠️ 特定通道用 |
| **永不加版本，只做兼容演进** | 只加不改 + tolerant reader + 弃用登记 | 全靠纪律，必须自动化门禁；**破例一次，之后破例会变常态** | 绝大多数对外 JSON API | ✅ **主策略** |

判断表（拿到一个变更就能对号入座）：

| 变更性质 | 策略 |
| --- | --- |
| 加字段 / 加端点 / 加枚举值 / 放宽校验 | 直接发，属兼容（§09.8） |
| 改语义 / 改类型 / 删字段 | **绝不原地改** → 新字段 + 双写 + 旧字段进弃用流程（§09.9） |
| 结构性重设计（认证、资源层级、分页模型） | 开 `/v2`，与 v1 并行 ≥18 个月，v1 走完整 Sunset |
| 只想"清理代码" | 不发版。**内部整洁不能成为外部破坏的理由** |

## 09.8 兼容性规则表（全篇核心）

先定义「兼容」：**在 N-3 个 SDK 版本、Top 20 接入方的既有客户端、以及 30 天内未升级的任意客户端上，行为不变。** 不是"我们自己测过了"，也不是"我通知过了"。**兼容性由被破坏方判定，不由改动方判定**——所以门禁的输入必须是接入方视角的契约测试。

**兼容（可以做）：**

| 改动 | 为什么兼容 | 例子 | 前提 |
| --- | --- | --- | --- |
| 新增可选响应字段 | 未知字段被忽略 | `order` 多返回 `settled_at` | 客户端开启 tolerant reader（SDK 默认） |
| 新增可选请求字段 | 不传 = 旧行为 | `POST /orders` 加 `buyer_note` | 默认值必须等于旧行为 |
| 新增枚举值 | 客户端容忍未知 | `status` 加 `PARTIALLY_REFUNDED` | 已发版 SDK 已有 `UNKNOWN` 兜底，否则**先改 SDK 再改服务端** |
| 新增端点 / 资源 | 无人调用 | `/v1/refunds` | 不影响既有路径 |
| 放宽校验（上限变大） | 旧请求仍合法 | `limit` 200 → 500 | 放宽也要重算容量（见 §09.10） |
| 新增 L2 错误码 | 旧客户端走 default 分支 | 新增 `ORDER.DUPLICATE_SUBMIT` | 客户端不得对未知码崩溃（SDK 需测这一点） |
| 新增响应 header | 被忽略 | `X-RateLimit-Remaining` | — |
| 放宽超时 | 更宽松 | 5s → 10s | 但会放大下游暴露时间，按 `eng/18` 评估 |

**不兼容（禁止原地改）：**

| 改动 | 为什么破坏 | 例子 | 正确做法 |
| --- | --- | --- | --- |
| 改字段类型 | 解析炸或被静默转换 | `int64` → `double`（事故一） | 新字段 `amount_cents` + 旧字段弃用 |
| 改单位 / 语义 | **最难发现**：不报错，数值全错 | 分→元、秒→毫秒、UTC→本地 | 新字段名带单位 + 双写 ≥90 天 |
| 删字段 / 删端点 | 客户端 NPE 或 404 | 删 `order.discount` | 先返回 null ≥90 天，字段使用率归零后再删 |
| 收严校验 | 旧请求突然 400 | `limit` 上限 200→100、手机号 11 位→13 位 | 只许放宽；必须收严则开新端点 |
| 改默认值 | 旧客户端行为**静默**改变 | 默认 `page_size` 20→50（成本 ×2.5）、默认排序变更 | 默认值属于契约，不可变 |
| 字段必填化 | 旧请求缺字段即 400 | `buyer_note` 变必填 | 永不 |
| 改错误码含义 | 客户端分支逻辑错乱 | `ORDER.CONFLICT` 从"可重试"变成"终态" | 新增码，旧码永久保留 |
| 改幂等语义 | 重复扣款 / 重复发货 | `Idempotency-Key` 有效期 7d → 1h | 幂等窗口只许变长 |
| 改分页稳定性 / 默认排序 | 导出漏行、对账缺条 | 游标从 `created_at` 改 `id` | 新参数 `order_by`，旧行为不变 |
| 改字段名 | 等价于删 + 加 | `user_id` → `buyer_id` | 两个字段同时返回，旧字段弃用 |
| 移出枚举值 | 旧值消失 | 删 `status=CANCELLED` | 永不；只新增 |

**灰区（看起来兼容，实际破坏）——这一栏最值钱：**

| 灰区改动 | 为什么会出事 | 处理 |
| --- | --- | --- |
| 加**必填**请求字段 | 旧客户端不传 → 全量 400 | 视同 breaking；只能加可选 + 服务端默认 |
| 加长字符串上限 | 对方 DB 列不够长 → 落库失败或截断 | `maxLength` 是契约，加长也要公告 |
| 提高数值精度（多给小数位） | 对方按 2 位小数解析 | 精度也是契约 |
| 数组可能变空 / 提前返回空集合 | 对方没处理空集合，直接 NPE | 空集合语义必须在文档写死 |
| 改 `Content-Type` 或压缩算法 | 中间代理与老客户端出问题 | 传输层变更要专门回归 |
| 加新的必填 header | 对方网关 400 | 只能加可选头，且服务端忽略未知头 |

门禁代码：把上面三张表变成 CI 里会失败的东西。结构层靠 OpenAPI diff，**语义层 diff 看不出来**，必须靠显式契约清单。

```java
// CI 兼容性门禁（Java 21 骨架）：破坏性变更必须先证明"不破坏"
public final class ContractGate {

  /** 结构层：OpenAPI diff 只允许 additive，REMOVED/CHANGED 一律拦下 */
  static void assertNoStructuralBreak(Path oldSpec, Path newSpec) {
    var diff = new OpenApiCompare().compare(oldSpec, newSpec);
    var breaking = diff.getChangedElements().stream()
        .filter(e -> e.getType() == ChangedType.REMOVED || e.getType() == ChangedType.CHANGED)
        .filter(e -> e.getChangedElementType() != ChangedElementType.SERVER) // 描述/示例不算
        .map(e -> e.getChangedElementType() + " " + e.getElement())
        .toList();
    if (!breaking.isEmpty()) {
      throw new ContractViolation("破坏性变更必须走新字段双写 + 弃用流程: " + breaking);
    }
  }

  /** 语义层：类型/单位/精度/默认值的变更 diff 看不出来，靠显式字段清单 */
  static void assertSemanticsFrozen(Map<String, FieldSpec> before, Map<String, FieldSpec> after) {
    after.forEach((name, now) -> {
      FieldSpec old = before.get(name);
      if (old == null) return;                       // 新增字段永远兼容
      if (!old.wireType().equals(now.wireType())     // int64 -> double = 事故一
          || !old.unit().equals(now.unit())          // 分 -> 元 = 事故一
          || !old.defaultValue().equals(now.defaultValue())) {
        throw new ContractViolation("%s 的类型/单位/默认值变更: %s/%s -> %s/%s"
            .formatted(name, old.wireType(), old.unit(), now.wireType(), now.unit()));
      }
    });
  }
  // 第三层：Top 20 接入方的 Pact 契约测试必须全绿（在流水线里单独跑）
}
```

## 09.9 弃用流程：Sunset 头、双跑期、下线阈值

响应头三件套，缺一个就会有接入方指责你"没通知"：

```
Deprecation: @1740000000                          # RFC 9745：字段/端点被弃用的时刻
Sunset: Wed, 31 Dec 2025 23:59:59 GMT             # RFC 8594：真正停止服务的时刻
Link: <https://docs.example.com/migrate/amount>; rel="deprecation"; type="text/html"
Warning: 299 - "field amount is deprecated, use amount_cents"
```

- 必须由**网关自动注入**，不靠业务代码记得写——业务代码一定会忘；SDK 把 `Warning` 转成编译期告警（Java `@Deprecated`、Go `// Deprecated:`），让它在接入方的 CI 里响。

```
T0          T0+30d             T0+90d                  T0+180d              T0+365d
│             │                  │                       │                     │
公告 & 登记   双跑开始           停新接入                只保留存量流量        下线
│             │                  │                       │                     │
▼             ▼                  ▼                       ▼                     ▼
Deprecation   新 SDK 不再出该字段   沙箱先行下线             调用占比 < 0.1%      Sunset 生效
Sunset=T0+365 旧 SDK 仍返回(双跑)   文档标灰 + 迁移指南      Top20 无人调用       归档进冻结清单
│             │                  │                       │                     │
└─ 通知1/4 ────┴── 通知2/4 ───────┴── 通知3/4 ────────────┴── 通知4/4 ───────────┘
```

下线标准表（**没有量化的弃用 = 永不结束的弃用**）：

| 判据 | 阈值 | 为什么是这个数 |
| --- | --- | --- |
| 调用量占比 | < 0.1%，连续 14 天 | 300 家 × 0.1% < 1 家，大概率是某个漏改的定时任务 |
| 提前期 | 字段 ≥365 天 / 端点 ≥180 天 | 接入方普遍季度级发版，还要走他们自己的审批 |
| 通知次数 | 4 次（30/90/180/330 天），多通道 | 单一邮件通道打开率约 30% |
| 白名单例外 | Top 20 客户显式签字 | 否则「他们不走，你也下不了」，最后变成永久双跑 |
| 沙箱先下线 | 提前 90 天 | 让新接入方一开始就不写旧字段 |
| 回滚窗口 | 下线后 30 天内可一键恢复 | 事故兜底；超过 30 天转"重新上架"流程（不走同一路径） |

**双跑期最重要的不是"两个字段都返回"，而是"两个字段的值在 90 天里逐笔对得上"**——每天抽样比对 `amount` 与 `amount_cents/100`，不一致数 >0 就阻断弃用推进。

## 09.10 配额与限流契约：维度选错比不限流更危险

| 维度 | 用不用 | 理由 |
| --- | --- | --- |
| **租户**（`tenant_id` / api_key） | ✅ **主维度** | 唯一与"付费主体"一一对应的维度 |
| 接口族（read / write / batch / export） | ✅ | 同一租户读与导出的系统压力差两个数量级（`eng/15`） |
| 重端点（报表、全量拉取） | ✅ 单独限 | 一个导出能占 40% 连接 |
| IP | ⚠️ 仅辅助 | 只用于**匿名探测与防刷**；NAT 后一个 IP 后面是几百个合法客户 |
| 全局 | ✅ 兜底 | 但**绝不能是唯一一层**——事故二 |

稳态与突发用**双桶**，让"月末结算"这类尖峰合法存在，而不是逼客户写奇怪的重试：

```
稳态桶：rate = S /s，burst = S          → 保证长期不吃亏，也不许长期超
突发桶：cap = 60 × S，回填 S/60 /s       → 允许一次性尖峰，喝完 60 分钟回满
放行 = 稳态桶有余 或 突发桶取到令牌；两者皆空 → 429
```

代入企业档 S=250：稳态突发 250 次，尖峰桶 15,000 次、每秒回填 4.2 次。

429 的语义必须完整，否则对方只能盲重试：

| 头 / 字段 | 值 | 说明 |
| --- | --- | --- |
| `Retry-After` | 整数秒 | **按令牌回填时间算**，不能固定写 1 |
| `X-RateLimit-Limit` / `Remaining` / `Reset` | 当前族的 S / 剩余 / 重置秒 | 让 SDK 做**主动**退避，而不是撞到 429 才退 |
| `error.code` | `PLATFORM.RATE_LIMITED` | 属"可重试"分类 |
| `detail.class` | read / write / batch / export | 让对方知道该收敛哪个方向 |

超额的**三条出路（商业设计，不是技术）**：

1. **买配额**：升 tier 或买配额包（+50% S，月度结算）；
2. **换通道**：批量与导出迁到异步 job，配额按"行数/天"计，不占同步 QPS——**事故二的正解不是加大配额，而是让批量不要占用同步 QPS**；
3. **专属容量**：铂金客户预留容量或专属部署单元（成本 1.44×–2.60×，账见 `llm/44`）。

```go
// 租户 × 接口族 双桶限流中间件（Go 骨架）
func QuotaMiddleware(q *QuotaStore, next http.Handler) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		t, ok := TenantFromCtx(r.Context())
		if !ok {
			writeErr(w, 401, "AUTH.MISSING_TOKEN", false)
			return
		}
		class := ClassOf(r.URL.Path) // read / write / batch / export
		lim := q.Limit(t.ID, class)  // S 与 cap 由 tier 决定，见 §09.4 配额表
		if !lim.Steady.Allow() && !lim.Burst.Take() {
			w.Header().Set("Retry-After", strconv.Itoa(lim.RetryAfterSec()))
			w.Header().Set("X-RateLimit-Limit", strconv.Itoa(lim.Steady))
			w.Header().Set("X-RateLimit-Remaining", "0")
			writeErr(w, http.StatusTooManyRequests, "PLATFORM.RATE_LIMITED", true)
			q.ObserveReject(t.ID, class) // 用于"相对基线异常"告警
			return
		}
		next.ServeHTTP(w, r)
	})
}

// 批量接口不在这里限流：POST /v1/import/jobs 只校验"每月行数配额"，
// 立刻返回 202 + job_id，真正的行级预算由消费端按 job 分片慢慢花 —— 这就是事故二的修复。
```

## 09.11 Webhook：签名、重试、乱序、可观测

签名口径（把它写进文档首页，因为 80% 的接入问题在这里）：

```
canonical = timestamp + "." + rawBody        // 用原始字节，不要重新序列化 JSON
signature = base64(HMAC-SHA256(secret, canonical))
X-Signature: t=1740000000,v1=<signature>
```

- **防重放**：时间戳窗口 5 分钟 + `event_id` 去重（服务端侧保留 7 天）。签名失败返回 `401` 且**不重试**（提示 Secret 配错，而不是让平台一直重打）。
- **密钥轮换**：支持 `v1` / `v2` 双 secret 并行 7 天，靠 `X-Signature` 里带版本号区分。
- **SSRF 防护**：回调地址必须 https + 公网，禁止内网段与 169.254；地址变更需租户管理员二次确认。

重试退避表（时间也是契约，写进文档，别让客户猜）：

| 第 n 次 | 间隔 | 触发条件 |
| --- | --- | --- |
| 1 | 立即 | 首次投递 |
| 2 | 30s | 非 2xx / 超时 10s / 连接失败 |
| 3 | 2m | 同上 |
| 4 | 10m | 同上 |
| 5 | 30m | 同上 |
| 6 | 2h | 同上 |
| 7 | 6h | 同上 |
| 8 | 24h（累计 ≈33h） | 同上 |
| → 死信 | 停止 | 达 8 次 / 超 72h |
| → 立即停 | 不重试 | 返回 4xx（非 408/429）：对方明确拒收，重试只会更糟 |
| → 熔断降级 | 暂停 30 分钟 | 同一 endpoint 连续 20 次失败 → 告警并改由对方轮询 |

**乱序是必然，不是异常**：重试必然打乱顺序。承诺要精确到可验证：

- 事件带 `event_id`（ULID，时间有序）、`occurred_at`、`resource_version`（单调递增）；
- 平台**不保证**跨事件的全局顺序，只保证同一 `resource_id` 的 `resource_version` 单调；
- 接入方消费规则：`if (ev.resource_version <= lastSeen) drop;` + 按 `event_id` 幂等落库；
- 文档必须给"最终一致"的可验证承诺：**收到 `order.updated` 后 `GET` 一定能读到 ≥ 该 version 的数据**。否则对方会把事件当事实源，把 bug 埋在对方系统里。

```
  事件创建
     │ 签名 + event_id 入库（持久化，先落库再投递）
     ▼
 ┌──────────┐   2xx    ┌────────────┐
 │ pending  │──────────→│ delivered  │
 └────┬─────┘           └────────────┘
      │ 非 2xx / 超时 / 重试到期且未达上限
      ▼
 ┌──────────┐  退避到期(30s→33h)  ┌──────────────┐
 │ retrying │────────────────────→│ 再次投递      │
 └────┬─────┘                     └──────┬───────┘
      │ 达 8 次 / 超 72h / 返回 4xx      │ 2xx
      ▼                                 └──→ delivered
 ┌─────────────┐   接入方修复后自助重放 / 平台补推
 │ dead(死信)  │──────────────────────────→ pending
 └─────────────┘
```

**可观测与自助重放**（缺了它，支持团队会被手工补推淹没）：投递日志（事件 ID / 时间 / 响应码 / 耗时 / 重试次数）客户后台可查 30 天；自助重放 `POST /v1/webhook/events/{event_id}/replay` 限每天 1,000 次（防止被当成重试机制）；死信可导出 CSV；`endpoint` 维度成功率看板 + 「连续失败 >1h」告警。

## 09.12 SDK 与文档即契约

- **OpenAPI 是唯一事实源**：SDK、文档、示例、Mock、沙箱桩、字段清单全部由它生成。手写文档必然漂移。
- **文档里的示例必须被 CI 实际执行**，否则三个月后示例里就有已删除的字段，而客户会照抄。
- **CDC（consumer-driven contract）**：Top 20 接入方把真实调用序列打包成契约测试，平台 CI 必须全绿；中小客户用「N-3 版本 × 3 语言 = 12 条 SDK 回放」代替。
- **SDK 版本 ≠ API 版本**：SDK major 只随语言侧破坏而变（Java 8→21、Go module 路径），与 API 字段演进解耦；SDK minor 跟随 API 的加法。否则「SDK 升级 = 逼客户改代码」，客户永久锁死。
- SDK 内嵌**能力声明** `supportedApiVersions: ["2024-01","2025-01"]`，平台据此判断某字段能否对该租户开启；SDK 上报版本分布（`User-Agent: acme-sdk-java/3.4.1`），这是「能不能删字段」的唯一数据来源。

四个产物的漂移与防漂移：

| 产物 | 从哪来 | 漂移症状 | 防漂移机制 |
| --- | --- | --- | --- |
| OpenAPI spec | 手写/注解生成 | 与实现不一致 | 1% 采样校验真实响应符合 schema |
| SDK | 由 spec 生成 | 与 spec 不一致 | 生成物 `git diff` 必须为零 |
| 文档 | 由 spec 生成 | 示例过期 | 示例进 CI 执行 |
| 错误码表 | 独立注册表 | 文档有、实现无 | 启动时校验码都在注册表内 |

## 09.13 沙箱与联调：接入方的第一印象就是沙箱

| 能力 | 必须做到 | 常见错误 |
| --- | --- | --- |
| 数据隔离 | 独立租户命名空间 + 独立 key 前缀 `sk_test_` + 独立数据集 | 沙箱与生产同库只打标记 → 一次 SQL 事故删生产 |
| 可重复回放 | 固定时钟、固定随机种子、固定外部桩；同一请求重放得到同一 `request_id` 轨迹 | 沙箱每天重置数据 → 联调问题永远复现不了 |
| 自助调试 | 签名生成器、错误码查询器、Webhook 接收器（自动展示请求体与验签结果）、配额实时查看 | 靠群里问「我这个签名对不对」 |
| 假数据生成 | 覆盖**边界**：0 元、超长字符串、未知枚举、时区边界、空集合 | 只造 happy path，上线才发现 |
| 开通时延 | 自助 5 分钟拿到 key + 沙箱 | 人工审批 3 天 → 接入方在选型阶段就放弃了 |

沙箱 SLO 可低于生产（99.5% vs 99.95%），但**不能抖**：联调期遇到沙箱不稳定，「平台不可靠」会被写进对方的选型结论，比任何压测数据都持久。

## 09.14 租户隔离与越权：scope 说"能读"，不等于"能读这一条"

| scope | 能做什么 | 典型持有方 |
| --- | --- | --- |
| `orders:read` | 读本租户订单 | 接入方服务端 |
| `orders:write` | 创建/取消订单 | 接入方服务端 |
| `webhooks:manage` | 配置回调地址与 secret | 接入方运维（**不该发给业务应用**） |
| `billing:read` | 读账单与用量 | 财务系统 |
| `admin:*` | 平台内部 | 只发给人 + 二次认证 + IP 白名单 |

三条铁律：

1. **归属校验不能只靠 scope**：每个对象级操作必须落到 `WHERE id = ? AND owner_tenant_id = ctx.tenant`；越权**一律返回 404 而不是 403**——403 等于告诉探测者"这个 ID 存在"。
2. **ID 不可枚举是"难度"，不是"权限"**：ULID/雪花 + 扰码都要有，但两者不能互相替代。
3. **跨租户访问审计**：任何 `token.tenant != resource.tenant` 的尝试，无论成功失败都双写到审计流（谁、何时、哪个 token、哪个 resource、IP、UA）；同一 token 10 分钟内 5 次归属失败 → 临时封禁 1 小时并通知租户管理员。

| 越权场景 | 长什么样 | 防法 |
| --- | --- | --- |
| 水平越权 | 用 A 的 token 读 B 的 `order_id` | 归属校验 + 404 + 审计 |
| 垂直越权 | 业务应用拿到 `webhooks:manage`，把全部事件导到攻击者域名 | scope 最小化 + 回调地址变更需管理员二次确认 |
| 混淆代理（deputy） | 平台用"自己的高权限"访问下游，把结果返回给低权限调用方 | 每次下游调用用**调用方身份派生**的 token，不用平台万能 token |
| 密钥泄露 | key 被提交到 GitHub | 可识别前缀 + 泄露扫描 + 一键轮换（新旧并行 7 天） |

## 09.15 对外开放后，灰度不能按请求切

这一节最容易被内部经验带偏，也是本篇必须写的一节。

内部灰度的默认做法是**按请求比例**（1% → 50% → 100%）或按 pod 切。对外部，这等于直接违约：

```
同一家接入方的 100 个请求被随机分到 v1 与 v2
  → 两种响应结构 / 两种默认排序 / 两种错误码 / 两种分页实现
  → 有的记录字段有值有的没值、列表顺序来回跳、翻页漏数据、导出少行
结果：用户侧"偶发"故障、不可复现、接入方判为网络问题，排查两周
```

| 变更类型 | 灰度单位 | 做法 | 禁止 |
| --- | --- | --- | --- |
| 内部实现优化（契约不变） | 请求 / pod | 常规 1% → 5% → 50% → 100% | 顺带改响应语义 |
| **新增字段（加法）** | **先全量发值，再按租户开** | 字段先对所有租户返回（或 null），确认客户端容忍后再按租户开关"开始填值" | 按请求比例返回新字段（对方库里一半有值一半无值） |
| 行为变化（排序、默认值、校验） | **租户（sticky）** | 按 `hash(tenant_id)` 分桶，同一租户灰度期固定版本 | 同一租户跨版本 |
| 配额 / 超时变更 | 租户 tier | 自助 → 标准 → 企业 → 铂金，逐档放 | 一次全量收紧（大面积 429） |
| **灰度回滚** | — | **关开关** | 回滚代码（会让已投产字段消失 = 破坏契约） |

**"先扩后收"的正确顺序**（任何加法都按此执行，顺序颠倒就是事故一的技术版本）：

```
1 发 SDK（容忍未知字段/未知枚举）→ 2 全量返回新字段（客户端忽略它）
→ 3 抽样确认 Top 20 客户端已生效 → 4 按租户开关"开始填值"（默认值仍在）
→ 5 观察 30 天 → 6 旧字段进入弃用流程（§09.9）
```

判定依据是 **SDK 版本分布埋点**，不是"我们通知过了"。没有埋点就没有灰度资格——这条和 [07 变更治理](07-change-governance.md) 的"灰度对象错了，比例对了也没用"是同一句话。

## 09.16 换挡信号与反模式

**换挡表**（接入方规模一变，形态必须换）：

| 阶段 | 规模 | 形态 | 换挡信号（硬阈值） | 代价 |
| --- | --- | --- | --- | --- |
| S0 | ≤20 家，日调用 <100 万 | 单版本 + 人工评审 + 无独立网关 | 第二个业务方接入 | — |
| S1 | 20–100 家 | OpenAPI 单一事实源 + CI 兼容门禁 + 租户配额 | 第一次兼容事故 | 发布变慢（门禁 6 分钟） |
| S2 | 100–500 家，>1 亿/天 | 独立开放网关 + 契约注册中心 + 沙箱 + 契约测试矩阵 | 峰值 > 单库容量 70% / 客户要求 SLA | 平台团队必须独立，不能挂在业务团队下 |
| S3 | >500 家或有赔付条款 | 分级 tier + 专属单元 + 计量计费 + 弃用自动化 | 单客户 >10% 流量 或 赔付 > 收入 2% | 组织成本：需要开发者关系岗 |
| ⚠️ | 并行大版本 >2 | 说明兼容性纪律已失效 | — | 停下来修纪律，**不要发 v3** |

**反模式表**（可直接当评审 checklist）：

| # | 反模式 | 长什么样 | 后果 | 正确做法 |
| --- | --- | --- | --- | --- |
| 1 | 把内部接口直接暴露 | "网关转发一下就行"，内部 DTO 就是 API | 内部重构变成外部故障；命名/分页/错误码全不合规 | 对外契约层，DTO 与内部模型解耦 |
| 2 | 错误码随需求新增 | 每个需求加一个 code，语义重叠、含义漂移 | 接入方 `switch` 全乱，文档 300 条 | 码段注册 + 语义不可变 + L3 承载细节 |
| 3 | 无配额 | 只有全局阈值 | 事故二 | 租户 × 接口族双桶 + 异步批量通道 |
| 4 | 无弃用流程 | 靠"通知过了"直接下线 | 两年后还在为删掉的字段赔钱 | Sunset/Deprecation 头 + 四票下线门槛 |
| 5 | 文档与实现不一致 | 手写文档，示例不执行 | 联调第一天失信，之后每条工单都是"文档说…" | OpenAPI 唯一事实源 + 示例 CI 执行 |
| 6 | 按请求灰度 | 内网经验平移 | §09.15 的"偶发故障" | 按租户粘性灰度 |
| 7 | 幂等键放 body | "对方自己带" | 换个幂等键重试 = 重复扣款 | Header + 服务端响应快照 |
| 8 | 回调当可靠消息 | 不重试、直接当事实源 | 丢一条事件 = 少一笔账 | 重试 + 最终一致 GET 承诺 + 自助重放 |
| 9 | 配额不可见 | 只有 429，没有 remaining | 每条工单都是"我为什么被限" | 实时配额查询 + 用量曲线 |
| 10 | 沙箱 = 生产换标记 | 同库不同前缀 | 一次 SQL 事故删生产 | 物理隔离的数据集 |

**对外系统特有的崩法速查**：

| 现象 | 定位方法 | 预防 |
| --- | --- | --- |
| 一批客户同时报"数据不对" | 按 SDK 版本 × 字段名聚合错误率与读数分布 | 字段使用率埋点 + 兼容门禁 |
| 全平台 429/5xx 但大盘 QPS 正常 | 按租户聚合，找"相对基线倍率"最高的单租户 | 租户配额 + 相对基线告警（`eng/20`） |
| 回调失败率上升但平台无告警 | 看 endpoint 维度投递成功率与死信量 | 投递看板 + 死信 + 熔断降级 |
| 客户投诉"偶发不一致" | 查灰度分桶是否为请求级、是否粘租户 | 按租户粘性 + 关闭请求级灰度 |

## 09.17 十分钟答题卡

被问"怎么设计一个开放平台"时，按这个顺序讲，不要从"我上个 Kong"开始：

```
1  真问题   你改一行 = 300 家故障，且回滚修不了别人的库 → 只做加法，破例走流程
2  四件事   契约（说清）· 配额（用得起）· 可观测（查得到）· 退出（下得来）
3  七件事   幂等键(Header) · 错误码三层 · 游标分页 · UTC RFC3339
            · 金额整数分且字段名带单位 · 枚举容忍未知 · 批量≤500 且走异步 job
4  错误码   L1 HTTP / L2 业务码(不可变，机器 switch) / L3 明细(可变，人看)
            + retryable 显式字段 + 可重试/不可重试/需人工 三分类
5  版本     默认永不加版本；破坏性变更 = 新字段 + 双写 90 天 + Sunset 365 天
6  兼容     加字段/加枚举/放宽 = 兼容；改类型/改语义/删字段/收严/改默认 = 破坏
            灰区：加长字段、提精度、加必填头 —— 都当破坏处理
7  配额     租户 × 接口族 双桶(S, 60S)；429 + Retry-After + X-RateLimit-*；
            批量走 202 + job（事故二的正解不是加配额，是不占同步 QPS）
8  回调     签名 = t.body；5 分钟窗口；event_id 幂等；8 次退避到 33h；
            4xx 立停；resource_version 丢旧；自助重放 + 死信
9  灰度     第三方按租户粘性，绝不按请求；回滚 = 关开关，不是回滚代码
10 换挡     S2 = 100 家 / 日 1 亿 → 独立网关 + 契约注册中心；
            并行大版本 >2 = 纪律已失效，先修纪律不发 v3
```

一句收口：**契约稳定性的成本由你付，破坏的代价由客户付。**
