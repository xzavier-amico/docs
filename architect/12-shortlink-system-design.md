## 12.1 引子：三个「没人报错」的故障

**事故一：营销短码被改成赌博站（2025-03-11）**

某快消品牌把 12 万个短码印在了全国 4 万家便利店的瓶身上，有效期三年。攻击者通过「开放注册 + 批量试」拿到一批**已回收但未做墓碑**的短码，把目标改成赌博落地页。

| 时间 | 事件 | 数据 |
| --- | --- | --- |
| 03-11 08:00 | 用户举报扫码进入博彩站 | 17 起 |
| 03-11 09:30 | 排查发现 2,340 个短码指向同一博彩域名 | 占已回收池 3.1% |
| 03-11 11:00 | 下架回收池，但**已印刷的 1.2 万个码仍在物理世界上流通** | 无法回收 |
| 03-11 14:00 | 紧急改回原目标，但部分码已被攻击者转卖 | 631 个码无法确认归属 |
| 03-12 ~ 03-18 | 品牌方承担危机公关与渠道召回，直接损失 340 万元 | — |

根因不是"被黑"，是三件事同时缺失：**回收后 slug 可直接复用**、**目标变更无审批无留痕**、**没有强制下线的熔断开关**。

**事故二：灰度把 3% 的流量永久导向旧页面（2025-06-27）**

跳转服务上线「智能落地页」灰度 3%。因为全部响应用了 `301 Moved Permanently`，被浏览器与 CDN 永久缓存。

| 时间 | 事件 | 数据 |
| --- | --- | --- |
| 06-27 14:00 | 灰度放量 3%，`301` + `Cache-Control: max-age=31536000` | 3% 流量 |
| 06-27 14:20 | 指标正常，继续放量至 50% | — |
| 06-28 09:00 | 发现 3% 用户仍停在旧页面，回滚无效 | 约 11 万终端 |
| 06-28 11:00 | 定位：**301 被永久缓存，回滚只改了服务端** | 缓存无法清除 |
| 06-28 ~ 07-15 | 只能等浏览器缓存自然过期，或换新短码重印 | 影响 2.4 万单 |

一个 HTTP 状态码的选择，把「可回滚」这个前提直接废掉了。**这就是持久性契约的第一个推论。**

**事故三：单表 4.2 亿行后的雪崩（2025-09-02）**

某内部短链服务日增 20 万条，两年半后单表 4.2 亿行、索引 11 个、单表 210 GB。一次运营侧的 `ORDER BY created_at DESC LIMIT 100000,20` 打满 IO，导致跳转查询 P99 从 8 ms 涨到 1.9 s，全站分享链接失效 26 分钟。

三起事故分别对应**领域边界缺失 × 缓存语义错误 × 存储形态停滞**——正好是本篇的三大节。

## 12.2 一句话定位与唯一真问题

**定位**：短链是「**一次写入、十亿次读取、永不失效**」的标识符解析服务。本质是一个分布式 KV，但带着三条普通 KV 没有的约束。

### 唯一真问题

> **短码是承诺，不是数据。**
> 短码一旦印在瓶身、二维码、合同、短信里，它的**存在性**就永久化了；但它的**目标**会变（活动换页）、**状态**会变（合规下线）、**归属**会变（租户退租）。
> 也就是说：**标识符必须永久不可变，而被标识的东西必须可变且可撤销。**

这一个矛盾推出了全部设计：

| 从矛盾推出的约束 | 推出的设计 |
| --- | --- |
| 短码不能复用（复用即"劫持别人已印刷的流量"） | **墓碑机制**，回收的 slug 永不重发 |
| 目标可变，但缓存必须能感知变更 | **版本化缓存 key**，不是 TTL 等待 |
| 必须能立刻撤销（钓鱼、违规） | **302 而非 301** + 短 `max-age` + 边缘可刷新 |
| 变更必须可追溯、可回滚 | 目标变更走**控制面审批 + 版本快照** |
| 跳转路径不能有任何依赖控制面 | **数据面与控制面物理分离** |

对比一下就知道这条矛盾有多特殊：

| 系统 | 标识符 | 目标 | 结论 |
| --- | --- | --- | --- |
| 短链 | 永久 | 可变、可撤销 | **本篇** |
| 对象存储签名 URL | 短时 | 不可变 | 无此矛盾，但有过期语义 |
| DNS | 永久 | 可变、可撤销 | 同构！所以 DNS 的 TTL 博弈可以直接借鉴 |
| 数据库主键 | 永久 | 不可变 | 简单得多 |

**所以短链最该抄的作业不是"分布式 KV"，是 DNS**——DNS 花了四十年解决的就是"名字永久、指向可变、缓存要能感知"这一件事。

## 12.3 量级与预算：全部推导一遍

不许拍脑袋。给出推导链，评审时要求对方复述这条链。

### 请求量

```
日跳转          100 亿次  （1000 万 DAU × 人均 50 次 + 机器流量 40%）
均值 QPS        100e8 / 86400        ≈ 11.6 万
峰值系数        ×5（营销活动、晚 8 点、扫码高峰）  →  58 万 QPS
日新增短链      500 万条（API 批量占 78%）
写 QPS 均值     58（几乎可以忽略）
读写比          约 2000 : 1        ← 这个数字决定了后面所有取舍
```

> **读写比 2000:1 是整篇的支点。** 它意味着：优化写路径的收益上限是 0.05%，而优化读路径每 1% 都值钱；也意味着**写路径可以很贵**（走审批、走同步校验、走强一致），因为它的 QPS 低到可以付任何代价。

### 存储量

```
单条记录         slug 8B + target 120B（均值，留膨胀）+ 元数据 120B = 248B
                含索引开销 ×1.6 ≈ 400B
日增            500 万 × 400B = 2.0 GB（已含索引）
5 年总量        2.0 GB × 365 × 5 ≈ 3.6 TB
点击明细        100 亿/天 × 80 B = 800 GB/天 → 不进主库，见 §12.8
```

### slug 空间：一个必须算对的数字

base62（`0-9a-zA-Z`）的容量与耗尽时间：

| 长度 | 空间 | 日耗 500 万下的耗尽时间 | 结论 |
| --- | --- | --- | --- |
| 5 位 | 9.16 亿 | 183 天 ≈ 0.5 年 | ❌ 短链要活十年以上 |
| **6 位** | **568 亿** | **11,360 天 ≈ 31 年** | ✅ 默认长度 |
| 7 位 | 3.5 万亿 | 704,000 天 ≈ 1,930 年 | 留给付费自选/语义 slug |

**但长度算对了不代表能用随机生成。** 生日悖论：一年累积 18.25 亿个 slug，落在 568 亿空间里，期望碰撞次数

```
n² / (2N) = (1.825e9)² / (2 × 5.68e10) ≈ 2.9 × 10⁷
```

**一年 2900 万次碰撞**——每次都要回表重试，写路径直接被自己的重试打垮。结论：

> **随机生成只在负载因子 < 0.01% 时才可行。短链必须用发号器（号段模式）+ base62 编码，天然无碰撞。**

### 缓存预算

```
热数据        遵循幂律，Top 2% 的 slug 承载约 92% 的请求 → 100 万条
单条缓存值    200 B（target + version + flags）
Redis 总量    100 万 × 200 B ≈ 200 MB  →  3 主 3 从 × 16 GB 极度过剩
目标命中率    Redis 99.0% / 本地 LRU 65% → 组合未命中 ≈ 0.35%
回源 QPS      58 万 × 0.35% ≈ 2,030  ← 这个数决定分片数，而不是总量
```

**注意这里的推导方向：先定命中率，再算回源，再由回源决定分片数。** 反过来（先定 1024 分片再想命中率）是新手最常见的倒置。

### 延迟预算（跳转路径）

| 环节 | P99 预算 | 说明 |
| --- | --- | --- |
| 边缘/CDN 命中 | 3 ms | 目标 40% 请求在此结束 |
| 接入层 TLS + HTTP 解析 | 2 ms | Go 数据面，连接复用 |
| 本地 LRU | 0.05 ms | 65% 命中 |
| Redis 单次 GET | 1.5 ms | 跨 AZ 时 +0.8 ms |
| DB 回源（0.35%） | 12 ms | 允许慢，因为稀少 |
| **端到端 P99 目标** | **20 ms** | 未命中链路才有机会超 10 ms |

## 12.4 领域与边界：不变量比类图重要

### 限界上下文

```
┌──────────────────────────────────────────────────────────────────┐
│  数据面 DataPlane（Go）        「slug → target」单向查询，无状态   │
│  ─ 解析 Resolver   ─ 边缘缓存   ─ 归因打点（写 MQ 即返回）        │
├──────────────────────────────────────────────────────────────────┤
│  控制面 ControlPlane（Java）  「有状态、有审批、有计费」           │
│  ─ 链接生命周期   ─ slug 分配   ─ 目标变更审批   ─ 租户与配额      │
│  ─ 治理（风控/封禁/申诉）        ─ 运营后台                        │
├──────────────────────────────────────────────────────────────────┤
│  分析面 Analytics   ─ 点击流 → 实时聚合 → 数仓 → 报表/计费对账     │
└──────────────────────────────────────────────────────────────────┘
            数据面只依赖一个只读副本 + 缓存，永不调用控制面
```

**这条依赖方向是硬约束**：数据面 → 控制面 的任何同步调用都是架构违规（`ArchUnit` 规则守住）。理由：控制面发布、审批、慢 SQL 的抖动会直接变成 58 万 QPS 的跳转失败。

### 聚合与不变量

| 聚合 | 不变量 | 守护方式 |
| --- | --- | --- |
| `ShortLink` | slug 全局唯一且**永不复用** | 唯一索引 + 墓碑表 |
| `ShortLink` | 每次目标变更必须产生**新版本**，旧版本可回滚 | `link_version` 表，append-only |
| `SlugAllocation` | 一个 slug 在任一时点只能属于一个租户 | 号段 + 租户配额前置校验 |
| `Policy` | 被封禁的 slug 必须在**秒级**对全边缘生效 | 封禁走独立高频刷新通道，不等缓存过期 |

**注意 slug 唯一性属于哪个聚合**：它不属于 `ShortLink`，而属于**全局命名空间**。这是很反直觉的一点——如果当成 `ShortLink` 的属性，你会自然地写「删除后新建同 slug 的链接」，而这个操作在物理世界里等于劫持。**所以墓碑必须是独立的表，且永不清空**（只归档）。

### 状态机

```
        ┌────────┐  创建/审核通过   ┌────────┐
        │ draft  │ ───────────────→ │ active │
        └────────┘                  └────┬───┘
             ↑                           │ 违规/合规/租户主动
             │ 申诉通过                   ↓
        ┌────────┐   申诉    ┌──────────────────┐
        │ banned │ ←──────── │ suspended(临时)  │
        └────┬───┘           └────────┬─────────┘
             │ 永久封禁                │ 到期自动恢复
             ↓                        └──→ active
        ┌────────────┐
        │ terminated │  → slug 进墓碑池，target 置空，仅保留审计
        └────────────┘
```

`expired`（活动到期）与 `terminated`（合规终止）必须区分：前者目标仍可访问但提示活动结束，后者直接 410 且 slug 永不复活。

## 12.5 存储形态：分片键之争

### 表结构演进（DDL 全集见篇 26 附录 A）

| 版本 | 形态 | 触发信号 | 代价 |
| --- | --- | --- | --- |
| v0 | 单表 `short_link(slug PK, target)` | — | 无 |
| v1 | 单表 + 唯一索引 + `link_version` | 需要目标可回滚 | 多一次 join 或读最新版本指针 |
| v2 | **按 slug hash 分 512 片** | 单表 > 50 GB 或回源 QPS > 5k | 跨片查询全部失效 |
| v3 | 热冷分离：冷链接转 KV/对象存储 | 冷数据占 85% 且无访问 | 冷热判定与迁移任务 |

### 分片键：这篇最该看的一段

三个候选，选错就再也回不去：

| 候选键 | 优点 | 致命问题 | 判定 |
| --- | --- | --- | --- |
| **slug hash** | 跳转点查天然单分片，天然均匀 | 租户视角的列表/统计**必须扫全部分片** | ✅ **主库选它** |
| tenant_id | 租户隔离天然、运营查询单分片 | 大租户变热点分片（一家占 30% 流量），且**跳转必须带租户信息** | ❌ 主库不可用 |
| 时间（月表） | 归档容易 | 跳转是随机访问，按月分片等于把热数据打散 | ❌ |

**结论：点查型系统，分片键必须选「查询条件本身」。** 短链 99.99% 的查询是 `WHERE slug = ?`，所以只能是 slug。

但运营侧要按租户查列表、按活动查统计怎么办？**不要试图用主库满足**，走异构投影：

```
主库（slug hash 512 片）── binlog/CDC ──→ 三个投影
                                          ├→ ES：按 tenant/activity/domain 多维检索
                                          ├→ ClickHouse：按租户 × 天聚合
                                          └→ 宽表：运营后台列表（游标分页）
```

这就是 **CQRS 的存储侧形态**：写走主库，所有"非点查"需求走投影，投影可以随意重建。

### 再分片：512 → 1024 的在线迁移

不要等到必须扩才想。预留**虚拟槽**：`slot = hash(slug) % 4096`，`slot → shard` 的映射放配置中心。扩容时只需搬 slot，不用改任何代码路径。

| 阶段 | 动作 | 可回滚 |
| --- | --- | --- |
| 1 | 新老库**双写**（写主库 + 影子库） | ✅ 关双写 |
| 2 | 全量 + 增量迁移，按 slot 分批，每批带校验和 | ✅ 删除目标数据 |
| 3 | **影子读**：1% 流量读新库，比对结果不一致则告警 | ✅ 切回 |
| 4 | 按 slot 灰度切读（同一 slot 必须原子切换，否则读到旧数据） | ✅ 改映射表 |
| 5 | 切写 → 观察 7 天 → 摘除老库 | ⚠️ 需备份 |

## 12.6 读路径形态：版本化 key 是唯一正确解

### 五级缓存链路

```
Browser ──→ CDN/边缘(40%) ──→ 本地LRU(65%) ──→ Redis(99.0%) ──→ DB(0.35%)
   ↑              ↑                ↑                 ↑
max-age=60   可 purge API      进程内,广播失效   版本化 key
```

### 为什么 TTL 不够

目标变更后，TTL 意味着最长 `TTL` 秒的脏数据。对「活动换页」可接受，对「钓鱼站紧急下线」**不可接受**（1 秒都不能）。

### 版本化 key：让失效变成"换 key"

```sql
-- 主库：版本表 append-only，current_version 指向最新
link_version(slug, version, target, created_at, PRIMARY KEY(slug, version))
```

```
缓存 key  =  s:{slug}:v{version}          ← 内容不可变，所以可以无限缓存
索引 key  =  i:{slug}  →  {version, status}  ← 唯一会变的东西，很小
```

读路径：先读 `i:{slug}` 拿 version → 再读 `s:{slug}:v{ver}`。

- 目标变更 = 插入 v2 + 更新 `i:{slug}` → **所有旧缓存自动失效，无需 purge**（老 key 自然过期）
- 变更只需一次小对象写，传播是"指针换向"，几乎不可能不一致
- 代价：多一次 Redis GET。实测本地 LRU 把 `i:` 缓存起来后，额外开销 < 0.05 ms

```go
// 数据面跳转核心（Go，骨架）
func (h *Handler) Redirect(w http.ResponseWriter, r *http.Request) {
	slug := path.Base(r.URL.Path)
	idx, err := h.idxCache.Get(slug)          // i:{slug}，本地 LRU 优先
	if err != nil {
		h.miss(slug)                          // 打点后回源，绝不阻塞
		http.Error(w, "not found", 404)
		return
	}
	if idx.Status != StatusActive {
		h.writeGone(w, idx)                   // banned/terminated 返回 410
		return
	}
	tgt := h.targetCache.Get(slug, idx.Version) // s:{slug}:v{ver}
	w.Header().Set("Location", tgt)
	w.Header().Set("Cache-Control", "public, max-age=60") // 绝不 301
	w.WriteHeader(http.StatusFound)           // 302
}
```

### 三个必须显式设计的失效场景

| 场景 | 朴素做法 | 正确做法 |
| --- | --- | --- |
| 紧急封禁（钓鱼） | 等 TTL 过期 | **旁路广播**：封禁写 Redis 黑名单 `bl:{slug}`，数据面每次多一次本地布隆查询，命中即 410 |
| 热点 slug（爆款二维码） | 单 key 打满单分片 | 按 `slot % N` 复制 N 份 key，请求随机取；本地 LRU 天然吸收 |
| 缓存穿透（扫描器枚举） | 全部回源 | **布隆过滤器**（全量 slug）+ 空值缓存 60s + IP 限流 |

> **布隆过滤器的数据面铁律**：它只能有假阳性，不能有假阴性。所以控制面新增 slug 时必须**同步**写入布隆（Redis bitmap 或进程内分片 bitmap + 版本号），这个同步点必须走「写库成功 → 写布隆 → 才返回成功」，宁可创建变慢，不可漏写。

## 12.7 查询形态：四类需求，四套方案

| 查询 | 特征 | 方案 | 反模式 |
| --- | --- | --- | --- |
| 点查（跳转） | 58 万 QPS，单 key | 五级缓存 + 分片主库 | 用 ES 承载跳转 |
| 列表（运营后台） | 低 QPS，多维筛选，深分页 | ES/宽表 + **游标分页** | `LIMIT 100000,20` |
| 聚合（租户报表） | 按天/活动/地域 | ClickHouse 预聚合 | `COUNT(*) WHERE` 打主库 |
| 分析（转化漏斗） | 百亿级点击明细 | 明细湖 + OLAP | 明细进 MySQL |

**深分页必须用游标**：`WHERE created_at < ? AND slug < ? ORDER BY created_at DESC, slug DESC LIMIT 20`。原因不是性能玄学，而是 offset 分页在数据增长时**结果会漂移**——运营看到的第 3 页和第 4 页可能重叠，这在"排查某个短码去哪了"时是实实在在的运营事故。

**301 还是 302**（本篇最重要的单条决策）：

| 状态码 | 浏览器缓存 | 可撤销 | 适用 |
| --- | --- | --- | --- |
| 301 | 永久，**服务端无法清除** | ❌ | 目标永不变化的镜像/静态资源 |
| **302 / 307** | 按 `Cache-Control` | ✅ | **短链默认** |
| 302 + `max-age=60` | 60 秒 | ✅ | 印刷场景（省 40% 回源） |
| 302 + `max-age=0` | 不缓存 | ✅ 立即 | 合规敏感、需秒级下线 |

对应引子里的事故二：**任何"可能被回滚"的东西，都不许用 301。**

## 12.8 异步与一致性：点击流不是日志，是资产

100 亿次/天的跳转不能同步写任何东西。数据面只做一件事：**向本地 ring buffer 写一条 80 B 的点击事件，异步批量发 MQ**。

```
数据面 ──(批量 500 条/10ms)──→ Kafka(topic: click, key=slug, 64 分区)
                                    │
                    ┌───────────────┼────────────────┐
                    ↓               ↓                ↓
              Flink 实时聚合    ClickHouse 明细   对象存储归档
              (分钟级看板)      (报表/漏斗)       (T+1 对账/审计)
```

| 决策点 | 选择 | 理由 |
| --- | --- | --- |
| 要不要顺序 | **按 slug 分区保序** | 同一短码的点击顺序影响 UV 去重与漏斗 |
| 投递语义 | **至少一次 + 消费端幂等** | 精确一次在跨系统下不存在，见 `eng/11` |
| 丢了怎么办 | **可丢，但不能静默丢** | 计费类事件必须走 Outbox（`eng/10`），分析类可容忍 0.01% 丢失 |
| 幂等键 | `(slug, ts_bucket, visitor_hash)` | 聚合侧按此去重 |

**计费口径必须和点击流分开**：计费事件（按跳转次数向租户收费）走**独立的、带 Outbox 的强可靠链路**，因为它是钱；分析事件可以 Sampling 1%（十亿级足够）。把两者混在一条链路上，是「要么太贵、要么账不准」的根源。

对账锚点：**在建模阶段就要在点击事件里埋 `tenant_id`、`link_version`、`billing_key`**——等出了账差再回头补字段，历史数据补不回来，只能认损。

## 12.9 编排：数据面/控制面两种完全不同的编排

| | 数据面（Go） | 控制面（Java） |
| --- | --- | --- |
| 编排形态 | 无状态中间件管道：TLS → 限流 → 路由 → 解析 → 打点 | Saga/状态机：审批 → 占 slug → 写库 → 写布隆 → 发事件 |
| 失败处理 | 快速失败 + 降级（返回 404/410，绝不排队） | 补偿 + 重试 + 人工介入 |
| 发布 | 边缘灰度，5% → 25% → 100%，**必须可 purge** | 蓝绿 + 数据库 expand-contract |
| 容量 | 按峰值 58 万 QPS 预留 1.5 倍 | 按写 QPS 58 预留 10 倍（便宜） |

**创建短链的 Saga**（`eng/13` 讲实现，这里只给编排边界）：

```
1. 校验配额与目标 URL（同步，快）
2. 分配 slug（号段，本地原子 +1，失败率极低）
3. 写 link + link_version（同一本地事务）
4. 写 Outbox 事件（同事务，见 eng/10）
5. 异步消费者：写布隆、写 ES 投影、通知审核
6. 若审核拒绝 → 补偿：slug 进墓碑，target 置空，状态 terminated
```

**注意第 6 步是"进墓碑"而不是"释放 slug"**——这是 §12.4 不变量的直接体现，也是引子里事故一的修复点。

## 12.10 L0 → L5：六次换挡与换挡信号

这是本篇最可用于评审的一张表。**每一次重构都不是"因为量大"，而是某个具体指标越过了具体阈值。**

| 阶段 | 形态 | 容量 | **换挡信号（硬阈值）** | 代价 |
| --- | --- | --- | --- | --- |
| L0 | 单机 + PG/SQLite 单表 | 1k QPS | 磁盘 IO 打满 / P99 > 50 ms | — |
| L1 | + Redis 旁路缓存 | 1 万 | 缓存未命中回源 > 2k QPS | 一致性变弱 |
| L2 | + 读写分离 + 布隆 + singleflight + 空值缓存 | 5 万 | 主库连接数 > 80% / 复制延迟 > 1 s | 读到旧数据 |
| L3 | **数据面/控制面拆分** + 512 分片 | 30 万 | 单表 > 50 GB / 回源 > 5k QPS | 跨片查询全废 |
| L4 | 边缘 KV + CDN + 本地 LRU + 热点副本 | **58 万** | 边缘命中 < 30% / 单 AZ 带宽打满 | 失效传播变复杂 |
| L5 | 多租户 + 单元化多活 + 冷热分离 | 千万 | 单地域容量上限 / 跨境延迟 > 80 ms | 写冲突、脑裂风险 |

**当前目标量级落在 L4。重点说 L3→L4 的临界点：**

L3 之后你会发现带宽和 TLS 握手成本已经超过数据库成本——因为 58 万 QPS 里 40% 的请求指向不到 2% 的 slug。这时候正确的动作**不是继续加 Redis 分片**（那是线性堆钱），而是把命中下沉到边缘：

- 边缘 302（Cloudflare Workers / 自建边缘 KV），`max-age=60`
- 前提条件：**必须有边缘 purge 能力**，否则 §12.6 的紧急封禁退化成 TTL 等待（引子事故二的重演）
- 收益：回源降 40%，P99 从 20 ms 降到 8 ms

**不要跳级**：没有墓碑就上边缘缓存 = 边缘缓存把一个可撤销系统变成不可撤销系统。

## 12.11 这个形态特有的崩法

不是"高可用"套话，是短链这个形态自己的失效点：

| 失效 | 长什么样 | 定位方法 | 预防 |
| --- | --- | --- | --- |
| 号段耗尽 | 创建接口全量 500，跳转正常 | 看发号器剩余号段水位 | 水位 < 20% 告警 |
| 布隆假阴性 | 极低概率新建链接 404 | 对比"库里有、布隆认为无"抽样 | 布隆分片重建 + 版本号校验 |
| 热点单分片打满 | 某分片 CPU 100%，整体 P99 抖动 | 按 slug 聚合 Redis/DB 指标 | 副本 key + 本地 LRU |
| 边缘缓存顽固 | 改了目标但部分地区仍旧 | 多地域探查脚本 | 302 + purge API + 版本化 key |
| 投影落后 | 运营搜索不到刚建的链接 | 对比 binlog 位点与 ES 刷新时间 | 建后读返回主库 + 提示"索引中" |
| 墓碑误清 | 老短码指向新租户（最严重） | 定期扫描墓碑表与主表 slug 交集 | 墓碑表只归档不清空；唯一索引覆盖 |

## 12.12 砍掉 90% 预算还能不能跑

机器从 310 台砍到 31 台、Redis 从 6 节点砍到 1 节点、Kafka 停用：

| 保留 | 砍掉 | 后果 |
| --- | --- | --- |
| 单级 Redis + 布隆 + 302 短 `max-age` | 边缘 KV、CDN、Flink、ES、ClickHouse | 带宽成本上升 3 倍，运营后台退化为按 slug 精确查 |
| 版本化 key + 墓碑 | 多级本地缓存、热点副本 | P99 从 8 ms → 35 ms，仍可用 |
| 分片主库（可分少些） | 冷热分离、双写迁移 | 存储成本高，但十亿级还扛得住 |

**结论：这个系统的必需品只有三样——版本化 key、墓碑、302。** 其余全是量级或成本驱动的优化。每次评审都问一遍"哪三个是必需品"，能砍掉一半的架构虚荣。

## 12.13 十分钟答题卡

被要求现场设计短链时，按这个顺序讲，不要从"我用 Redis"开始：

```
1  量级    日 100 亿跳转 → 58 万 QPS 峰值；读写比 2000:1
2  真问题  短码永久、目标可变可撤销 → 这是全部设计的源头
3  领域    数据面/控制面物理分离；slug 唯一性属于全局命名空间；墓碑
4  存储    slug hash 512 分片（点查型系统分片键=查询条件）
5  读      五级缓存 + 版本化 key（失效=换指针，不是 purge）
6  写      Saga：占 slug → 写库+版本+Outbox → 异步投影
7  协议    302（绝不 301）+ 短 max-age + 边缘 purge 能力
8  异步    点击流至少一次+幂等；计费独立链路 + 建模期埋对账锚点
9  换挡    L3 单表 50GB / 回源 5k；L4 边缘命中 <30%
10 必需    版本化 key、墓碑、302 —— 其余都是量级驱动
```
