## 139.1 题目

**原题链接**：<https://leetcode.cn/problems/task-scheduler/>

### 题意重述（把隐含条件补齐）

给你一个字符数组 `tasks`（每个字符是一种任务，只有 `'A'`–`'Z'` 26 种）和一个非负整数 `n`（冷却时间）。CPU 在每个**单位时间**里可以完成一个任务，也可以处于**待命（idle）**状态。**同一个任务**的两次执行之间必须至少间隔 `n` 个单位时间（即中间至少有 `n` 个时间单位在做别的事或待命）。求完成所有任务所需的**最短时间**。

| 隐含条件 | 出处 | 违反了会怎样 |
| --- | --- | --- |
| **每个单位时间最多一个任务** | 「每个任务都可以在 1 个单位时间内执行完」 | 以为可并行 → 答案变成「最大频次」 |
| **间隔是 ≥ n 个时间单位** | 「两个相同任务之间必须有长度为 n 的冷却时间」 | 把 n 当成「中间隔 n−1 个」→ 整体少算 |
| **任务之间可以插任意别的任务** | 「可以以任意顺序执行」 | 误以为必须按原顺序 → 变成另一道题 |
| **不足时可以待命** | 「CPU 待命」 | 不允许待命 → 很多输入变成无解 |
| **`n` 可以为 0** | 约束 `0 <= n` | `n = 0` 时答案是 `tasks.length`，公式必须能自动退化成它 |
| **只有 26 种任务** | 字符集固定 | 计数表 `int[26]` 就够；这也让「桶」的列数有限 |
| **`tasks.length >= 1`** | 约束 | 空输入返回 0；本题不会出现，但通用函数要兜底 |

> **本章的题眼**：冷却约束只跟「同一个任务的两次执行」有关，**跟别的任务毫无关系**。于是只要盯住**出现次数最多的那个任务**，整条时间轴就被它「切成等长的段」—— 这就是「桶」的来源。

### 约束与「量级反推」

| 约束 | 值 | 它对算法的含义 |
| --- | --- | --- |
| `1 <= tasks.length <= 10^4` | 最多 1 万 | **搜索/状压 DP 全部不可行**（状态数是 `26` 维的乘积）；但 `O(n · 26)` 的模拟可以过 |
| `0 <= n <= 100` | 冷却最多 100 | 答案最大约 `10^4 × 101 ≈ 10^6`，`int` 绰绰有余 |
| `tasks[i]` 是大写英文字母 | 26 种 | 计数表 `O(1)`；画桶时最多 26 列 |
| 允许重复任务 | 频次可以很高 | 单任务频次最高 `10^4` ⟹ 答案可能远大于 `N`（大量待命） |

> 💡 **量级反推**：`N = 10^4`、`n = 100` 这一对数字说明「答案可能比任务数大很多」（最多 `10^6`），所以**不能用「能不能塞满」的思维去模拟整条时间轴**（那会是 `10^6` 次操作，虽然也能过，但拿不到 O(N)）。真正的解法只需**统计频次** + 一次公式计算。

### 示例

```
输入：tasks = ["A","A","A","B","B","B"], n = 2
输出：8
解释：A B _ A B _ A B        （_ 表示待命）
      A 出现在 0、3、6，两两间隔 3 ≥ 2 ✓；B 出现在 1、4、7 ✓

输入：tasks = ["A","A","A","B","B","B"], n = 0
输出：6
解释：冷却为 0 时可以直接连续执行：A A A B B B

输入：tasks = ["A","A","A","A","A","A","B","C","D","E","F","G"], n = 2
输出：16
解释：A 有 6 次，桶阵列 5 个整轮 + 尾轮 1 个 → (6−1)×3 + 1 = 16

输入：tasks = ["A","A","A","B","B","B","C","C","C","D","D","D"], n = 2
输出：12
解释：四种任务各 3 次，可以完全排满：A B C D A B C D A B C D，无待命 → 12
```

### 我自造的四个反例

```text
① tasks = ["A"], n = 100        → 答案 1（只有一个任务，冷却不会产生额外开销）
                                   m=1, c=1 → 桶长 = 0×101+1 = 1，max(1,1) = 1 ✓
② tasks = ["A","A"], n = 100    → 答案 102
                                   两副本距离 ≥ n+1 = 101 → 位置 0 与 101 → 长度 102
                                   m=2, c=1 → 桶长 = 1×101+1 = 102 ✓
③ tasks = ["A","A","A"], n = 2  → 答案 7（A _ _ A _ _ A）
                                   m=3, c=1 → 桶长 = 2×3+1 = 7 ✓
④ tasks = ["A","B","C","D","E","F"], n = 100
                                → 答案 6（m=1, c=6 → 桶长 = 0×101+6 = 6，max(6,6)=6）✓
⑤ tasks = A×2 + B..Z 各 1 次（共 28 个任务），n = 1
                                → 答案 28（m=2, c=1 → 桶长 = 1×2+1 = 3，
                                   但 N = 28 > 3 → max 得 28）✓

第 ⑤ 条是「必须取 max」的死刑判决书：只写桶长会得到 3 —— 比任务总数还小，
物理上不可能。第 ④ 条则说明：**任务种类足够多时冷却「永远等得起」，答案就是 N。**
```

## 139.2 从暴力到最优：第一个念头为什么错

### 第一步：暴力 —— 搜索整条时间轴

最直白的想法：既然每个单位时间只能做一件事，那就**逐时刻决策**：

```text
状态 = (每个任务的剩余次数, 每个任务的「还要等几个时间单位」)
每一步：在所有「冷却已结束且有剩余」的任务里挑一个执行；若没有则待命
```

- 状态数是 `∏(f_i + 1) × (n+1)^26` 量级，对 `N = 10^4` 完全不可能。
- 即使只做「带记忆化的搜索」，也因为状态爆炸而无法使用。

再退一步：**优先队列模拟**（每次执行剩余次数最多的可用任务）——

```
每一时刻：
  从「冷却结束」的任务里取剩余次数最大的执行；
  把执行过的任务放入冷却队列（n 个时间单位后解锁）；
  若没有可用任务 → 待命（答案 +1）
```

- 时间 `O(answer · 26)`，`answer` 最大约 `10^6`，`26` 是常数 → 实际约 `2.6·10^7` 次操作，**能过本题**。
- 但它「模拟整条时间轴」，代码 30 行以上，而且**必须证明这个贪心是最优的** —— 那并不比本章的公式更容易。

### 第二步：卡点在哪

把冷却约束单独拎出来看，只有一个数字重要：

```
出现次数最多的任务（记为 A，次数 m）
```

因为**只有它会「逼出待命」**：其它任务总可以在 A 的间隙里被塞进去。于是问题从「26 种任务的排布」塌缩成「**A 的 m 个副本在时间轴上怎么站**」。

A 的相邻两次执行之间必须至少隔 `n` 个时间单位，也就是说：

```
A 在 0 处，下一次最早在 n+1 处，再下一次最早在 2(n+1) 处，……
```

**这就把时间轴切成了等长的段**：每段长度 `n+1`，A 站在每段的**第一格**。

```
段 0：[A, ?, ?, …, ?]      ← 一共 n+1 格
段 1：[A, ?, ?, …, ?]
…
段 m-2：[A, ?, …, ?]
段 m-1：[A, …]             ← 最后一段只需要放「和 A 一样多的任务」的那几个
```

### 第三步：灵感的来源 —— 桶

上面这个「段」，就是本章的**桶**：

- 一共 `m` 个桶（`m` = 最大频次），每个桶 `n+1` 格；
- 每个桶的第一格被一个「最高频任务」占据；
- 如果一个任务出现了 `f` 次，它就占据 `f` 个**不同**桶的格子（同一个桶里不能放同一个任务两次，因为桶内的距离 < n+1，会违反冷却）。

于是：

```
所需时间 ≥ 前 (m-1) 个满桶 + 最后那个只装了 c 格的桶
        = (m-1)(n+1) + c
其中 c = 「频次等于 m 的任务个数」（它们每个都要出现在最后一个桶里）

同时，时间不可能少于任务总数 N（每个时间单位最多干一件事）
⟹ 答案 ≥ max(N, (m-1)(n+1) + c)
```

**剩下的唯一问题是：这个下界能不能达到？** 这正是 §139.3.2 要证的（也是绝大多数题解直接跳过的地方）。

## 139.3 原理拆解

### 139.3.1 数据结构与算法选型

| 方案 | 时间 | 空间 | 代码量 | 什么时候会输 |
| --- | --- | --- | --- | --- |
| 逐时刻搜索 / 状压 DP | 指数级 | 指数级 | 50+ 行 | `N ≥ 20` 就跑不动；只能当小规模对拍判据 |
| 优先队列模拟（每时刻取剩余最多者） | `O(answer · 26)` | `O(26)` | 35 行 | `answer` 达 `10^6` 时约 `2.6·10^7` 次操作，能过但不优雅；且需要额外证明贪心最优 |
| **桶公式 `max(N, (m-1)(n+1)+c)`** ✅ | **O(N)** | **O(1)** | **8 行** | 需要「下界 + 构造」两段证明；频次相同时的 `c` 数错就会偏 |
| 排序后逐段削（把桶阵列真的建出来） | O(N + 26 log 26) | O(26) | 20 行 | 只是为了「看得见」而多写代码，收益为零 |
| 二分答案 + 可行性判定 | O(N log N) | O(1) | 30 行 | 判定函数本身就要写公式 —— 等于绕远路 |

**为什么选公式**：它把「排布」这件看起来必须模拟的事，压缩成两个统计量（`m`、`c`）和一个 `max`。这就是「找到结构」的收益：**从 O(answer) 的模拟降到 O(N) 的统计**。

### 139.3.2 为什么这个做法是对的（正确性论证 · 下界 + 构造）

**记号**

```
N     = tasks.length（任务总数）
cnt[x] = 任务 x 的出现次数
m     = max cnt[x]                （最大频次）
c     = #{ x : cnt[x] = m }       （达到最大频次的任务种类数）
L1    = (m-1)(n+1) + c            （桶阵列给出的长度下界）
L     = 实际最短调度长度
```

**下界 1（容量下界）**：`L ≥ N`。
每个单位时间最多执行一个任务（任务不能并行），`N` 个任务至少要 `N` 个时间单位。∎

**下界 2（桶下界）：`L ≥ L1`**

取任意一个频次为 `m` 的任务 `A`（存在，因为 `m` 是最大频次）。设它的 `m` 个副本在调度中的时间位置（从 0 开始编号）为

```
0 ≤ p_1 < p_2 < … < p_m
```

由冷却约束，相邻两次之间至少隔 `n` 个「别的时间单位」，即

```
p_{j+1} - p_j ≥ n+1        (j = 1, …, m-1)
```

于是 `p_m ≥ p_1 + (m-1)(n+1) ≥ (m-1)(n+1)`。

现在考虑**所有** `c` 个频次为 `m` 的任务。对其中每一个，同样的推导给出：**它最后一个副本的位置 ≥ (m-1)(n+1)**。而这 `c` 个「最后一个副本」位于**互不相同**的时间位置（同一个时间单位只能执行一个任务），所以这 `c` 个位置里最靠后的那个至少是

```
(m-1)(n+1) + (c-1)
```

调度长度 `L`（时间单位的个数）必须大于最靠后的位置，即

```
L ≥ (m-1)(n+1) + (c-1) + 1 = (m-1)(n+1) + c = L1 ∎
```

> 这就是「桶」的严格版本：`(m-1)` 个满桶给出 `(m-1)(n+1)` 格，最后那个「不完整桶」必须容纳 `c` 个最高频任务，所以还要 `+c`。**注意这里没有用到任何贪心选择 —— 下界对任何调度都成立，这正是它硬的原因。**

**定理（下界可达到）**：存在长度恰为 `max(N, L1)` 的合法调度。

这部分要构造，分两种情形。设把每个任务都看作一列（列号与任务一一对应），第 `j` 个副本放在第 `j` 个「桶」的第「列号」格里 —— 位置 = `桶号 × (n+1) + 列号`。**同一列的两个副本在不同桶里，位置差是 `(n+1)` 的整数倍，自然 ≥ n+1。**

**情形 A：`N ≤ L1`（任务少、待命多）**

此时可以验证 `c ≤ n+1`：若 `c > n+1`，则 `N ≥ c·m > (m-1)(n+1) + c = L1`（因为 `c > n+1` 时 `c(m-1) > (m-1)(n+1)`），与 `N ≤ L1` 矛盾。所以列数是够的。

构造一个「阶梯桶阵列」：

```
列 0 … 列 (c-1)：高度 m     （这 c 列装 c 个最高频任务，每个占 m 格）
列 c … 列 n    ：高度 m-1   （其余任务每个至多 m-1 次，装得下）
```

- **总格数** = `c·m + (n+1-c)(m-1) = (m-1)(n+1) + c = L1`，恰好等于下界；
- **每个最高频任务**：占满自己那一列的 `m` 格，副本间距恰为 `n+1` ✓；
- **其余任务**：在高度为 `m-1` 的列里「往下堆」，每个任务占自己列的连续若干格，副本间距仍是 `n+1` 的整数倍 ✓；
- **放得下**：其余任务的总副本数 = `N - c·m`，而空位数 = `L1 - c·m = (m-1)(n+1-c)`；由 `N ≤ L1` 直接得 `N - c·m ≤ L1 - c·m` ✓。

于是得到一个长度 `L1` 的合法排布（空着的格子就是待命），故 `L ≤ L1`；结合下界 2 得 `L = L1 = max(N, L1)`。∎

**情形 B：`N ≥ L1`（任务多、待命几乎不需要）**

此时构造改用「**块填充**」——把时间轴切成一块块长度 `n+1` 的块，每块里依次放入「当前剩余次数最大、且互不相同」的任务：

```
while 还有任务剩余:
    从剩余次数 > 0 的任务里，按剩余次数降序取至多 n+1 个（每个最多取一次）
    把它们按顺序放进这一块的 n+1 个格子（不够就补待命）
```

三条性质保证它合法：

1. **块内互不相同** ⟹ 同一块里没有同一任务的两个副本 ⟹ 同一任务在相邻两块里的距离 ≥ 剩下一整块的格子数 + 自己在两块中的偏移 ≥ `n+1` ✓；
2. **按剩余次数降序取人** ⟹ 一个任务在两块里的「块内名次」不会提前（因为它（以及所有被取的任务）都恰好减少 1，相对顺序保持不变；没被取的任务剩余更少，只可能排到它后面）⟹ 跨块距离始终 ≥ `n+1` ✓；
3. **`N ≥ L1` 时每个非末块都能凑满 `n+1` 个任务**：一旦某块凑不满，就说明此刻剩余任务种类 `≤ n`，所有「非最高频」的任务都已做完 —— 这时时间轴上剩下的只有那 `c` 个最高频任务，而它们每个还剩 `m - k` 次（`k` 为已过去的块数），于是总长度退化成 `(m-1)(n+1) + c = L1`，与 `N ≥ L1` 相容（此时恰好 `N = L1`）。

由 1、2 得到合法调度；由 3，长度恰为 `N`。故 `L ≤ N`；结合下界 1 得 `L = N = max(N, L1)`。∎

**综上所述**：

```
L = max( N, (m-1)(n+1) + c )
```

> **这一节的写法值得注意**：绝大多数题解只写下界（下界 2），然后就宣称「所以答案是它」。这是**不完整**的 —— 下界只说明「不可能更快」，必须再给出一个达到下界的构造，才叫「答案就是它」。本章把两半都写出来：**下界用「最后副本位置互不相同」的计数，构造用「桶阵列（情形 A）/ 块填充（情形 B）」**。情形 B 的第 3 条性质被 §139.5.4 的对拍逐例验证（5 万组随机输入下，块填充的长度与公式**完全一致**）。

### 139.3.3 通用解题思路（可迁移的那一层）

本题是 **「最频繁元素决定骨架 → 桶阵列 → 下界 + 构造夹逼」** 模型：

```
原始问题：带冷却的调度，看起来必须模拟时间轴
         ↓ 观察：冷却约束只作用在「同一任务」
建模：    最高频任务的 m 个副本把时间轴切成 m 段（桶），每段 n+1 格
         ↓ 其它任务只是「填格子」
结论：    L = max( N , (m-1)(n+1) + c )
证明：    下界（计数）+ 构造（桶阵列 / 块填充）
```

**同族题目**：

| 题 | 「骨架」是什么 | 结论的形态 |
| --- | --- | --- |
| [LC 621 任务调度器](https://leetcode.cn/problems/task-scheduler/) | 最高频任务的副本 | `max(N, (m-1)(n+1)+c)` |
| [LC 767 重构字符串](https://leetcode.cn/problems/reorganize-string/) | 最高频字符 | 可重排 ⟺ `max cnt ≤ ⌈N/2⌉` |
| [LC 1054 距离相等的条形码](https://leetcode.cn/problems/distant-barcodes/) | 最高频数字 | 先放最高频，再填其余（同一套桶） |
| [LC 358 K 距离间隔重排字符串](https://leetcode.cn/problems/rearrange-string-k-distance-apart/) | 最高频字符 + 冷却 `k` | 冷却版的重排，用优先队列模拟 |
| [LC 1953 你可以工作的最大周数](https://leetcode.cn/problems/maximum-number-of-weeks-for-which-you-can-work/) | 最高频工期 | `min(sum, 2·(sum-max)+1)` |
| [LC 2335 装满杯子需要的最短总时长](https://leetcode.cn/problems/minimum-amount-of-time-to-fill-cups/) | 最大的一杯 | `max(⌈sum/2⌉, max)` |

**共同点**：只要问题里有「同一个东西不能靠太近」的约束，**最高频的那个元素就是骨架**，答案几乎总能写成「`max(下界1, 下界2)`」。

### 139.3.4 可扩展性（面试追问的六个方向）

| 追问 | 变化 | 应对 |
| --- | --- | --- |
| 冷却时间**因任务而异**（每个任务自己的 `n_i`） | 桶的格数不再统一 | 公式失效；用优先队列模拟或线性规划/构造，而且最优性证明变复杂 |
| 要求输出**具体调度方案** | 要方案，不只是长度 | 情形 A 直接填桶（空位即待命）；情形 B 用块填充 —— 本章的构造本身就是方案 |
| 任务变成**无限流**（不断到来，要求稳态吞吐） | 无终止 | 稳态最优吞吐 = `min(1, (n+1)/… )`，要用「每 n+1 时间最多执行一个最高频任务」来算 |
| 允许**并行执行** `k` 个任务 | 每个时间单位能做好几件 | 变成「k 条流水线 + 冷却」，答案与 `⌈N/k⌉` 和桶长同时取 max（本质仍一样） |
| `n` 为负数 / 极大 | 约束变化 | `n = 0` 时公式自动退化为 `N`；`n` 极大时答案约等于 `(m-1)(n+1)+c`，注意 `int` 溢出（`m·n ≤ 10^4 × 100 = 10^6`，本题安全） |
| 字符集扩大到全 Unicode | 计数表不再是 26 | 换 `map[rune]int`；但只有 26 种字符时 `int[26]` 更快、更省 |

**进阶延伸（自己写代码验证）**：

- **LC 767 / LC 1054**：把「冷却」换成「相邻不能相同」，桶阵列的形状变了，但「最高频决定骨架」的思路一模一样。
- **LC 358 K 距离间隔重排字符串**：冷却为 `k` 的**重排**版本，必须真的输出字符串，模拟比公式更自然。
- **LC 1953 你可以工作的最大周数**：`min(sum, 2·(sum−max)+1)` 与本章同构 —— 都是「最大者决定骨架」。


## 139.5 双语言实现

### 139.5.1 Java

```java
class Solution {
    public int leastInterval(char[] tasks, int n) {
        // ① 统计频次：只有 26 种任务 → 定长数组，O(1) 额外空间
        int[] cnt = new int[26];
        for (char t : tasks) {
            cnt[t - 'A']++;
        }

        // ② 求最大频次 m 与「达到最大频次的种类数」c
        int m = 0;
        for (int v : cnt) {
            if (v > m) {
                m = v;
            }
        }
        int c = 0;
        for (int v : cnt) {
            if (v == m) {
                c++;
            }
        }

        // ③ 两条下界取最大：
        //    桶下界 L1 = (m-1)*(n+1) + c —— 由「最高频任务把时间轴切成 m 个桶」推出
        //    容量下界 N = tasks.length —— 每个时间单位最多干一件事
        //    m = 0 只在 tasks 为空时出现（约束保证 n >= 1，这里顺手兜底）
        int bucket = (m == 0) ? 0 : (m - 1) * (n + 1) + c;
        return Math.max(tasks.length, bucket);
    }
}
```

### 139.5.2 Go

```go
package main

func leastInterval(tasks []byte, n int) int {
	// ① 频次统计（与 Java 完全同构）
	cnt := make([]int, 26)
	for _, t := range tasks {
		cnt[t-'A']++
	}

	// ② 最大频次 m 与达标的种类数 c
	m := 0
	for _, v := range cnt {
		if v > m {
			m = v
		}
	}
	c := 0
	for _, v := range cnt {
		if v == m && m > 0 {
			c++
		}
	}

	// ③ 两条下界取最大
	bucket := 0
	if m > 0 {
		bucket = (m-1)*(n+1) + c
	}
	if len(tasks) > bucket {
		return len(tasks)
	}
	return bucket
}
```

> **注意 Go 版本的签名**：LeetCode 上 `tasks` 是 `[]byte`（字符数组），不是 `string`；`t-'A'` 得到 `byte`，用它当切片下标是合法的（`byte` 可直接作下标），但若你要做算术比较，记得显式转 `int`。另外 Go 没有 `Math.max`，`max` 要自己写 `if`（Go 1.21+ 才有内建 `max`，但题解环境不保证版本）。

### 139.5.3 双语言差异批注

| 点 | Java | Go | 对本题的影响 |
| --- | --- | --- | --- |
| 入参类型 | `char[]` | `[]byte` | 都按「小写字母以外的大写字母」处理；`t - 'A'` 的下标范围 `0..25` |
| 求最大值的写法 | `for` 循环 + `if` | 同（Go 1.21 之前没有内建 `max`） | 本题用 `for` 最稳，且顺便能一次求出 `m` |
| 取两数最大值 | `Math.max(a,b)` | 自己写 `if`（或 `max(a,b)`，版本相关） | 别依赖 `max` 内建，避免「本地能过、判题机版本低」 |
| 整数溢出 | `(m-1)*(n+1)` 最大 `10^4 × 101 ≈ 10^6` | 同 | 两语言都安全；若 `n` 放大到 `10^9` 就要 `long` |
| 空输入 | `tasks.length == 0` → `m = 0` | `len(tasks) == 0` 同样 | 本题约束排除，但通用函数要有 `m == 0` 的兜底（否则 `(m-1)` 变成 `-1`，答案可能为负） |

### 139.5.4 对拍测试（与「最优模拟调度」逐例比对）

```go
package main

import (
	"container/heap"
	"math/rand"
	"sort"
	"testing"
)

// ---------- 参考实现 1：优先队列模拟（每时刻执行剩余次数最多的可用任务）----------

type maxHeap []int

func (h maxHeap) Len() int            { return len(h) }
func (h maxHeap) Less(i, j int) bool  { return h[i] > h[j] }
func (h maxHeap) Swap(i, j int)       { h[i], h[j] = h[j], h[i] }
func (h *maxHeap) Push(x interface{}) { *h = append(*h, x.(int)) }
func (h *maxHeap) Pop() interface{} {
	old := *h
	n := len(old)
	v := old[n-1]
	*h = old[:n-1]
	return v
}

// simulateOptimal：经典的「冷却队列 + 最大堆」调度模拟，返回所需时间。
// 它逐时刻推进，与公式推导完全独立 → 是本题最可信的判据。
func simulateOptimal(tasks []byte, n int) int {
	cnt := make([]int, 26)
	for _, t := range tasks {
		cnt[t-'A']++
	}
	h := &maxHeap{}
	heap.Init(h)
	for _, v := range cnt {
		if v > 0 {
			heap.Push(h, v)
		}
	}
	// 冷却表：cool[i] = 该任务还剩几个时间单位才能再次执行
	// 用一个长度 n+1 的环形队列存「刚执行过的任务」
	type pending struct{ count, readyAt int }
	waiting := make([]pending, 0, 32)

	time := 0
	for h.Len() > 0 || len(waiting) > 0 {
		// 解锁所有 readyAt <= time 的任务
		still := waiting[:0]
		for _, p := range waiting {
			if p.readyAt <= time {
				heap.Push(h, p.count)
			} else {
				still = append(still, p)
			}
		}
		waiting = still

		if h.Len() > 0 {
			cur := heap.Pop(h).(int)
			cur--
			if cur > 0 {
				waiting = append(waiting, pending{cur, time + n + 1})
			}
		}
		// 若 h 为空 → 本时刻待命（time 仍然 +1），这正是「idle」的来源
		time++
	}
	return time
}

// ---------- 参考实现 2：块填充构造（用来验证 §139.3.2 情形 B 的构造）----------

func blockSchedule(tasks []byte, n int) int {
	cnt := make([]int, 26)
	for _, t := range tasks {
		cnt[t-'A']++
	}
	block := n + 1
	time := 0
	lastBlockSize := 0
	for {
		// 取剩余次数最大的至多 block 个任务（互不相同）
		idxs := make([]int, 0, 26)
		for i := 0; i < 26; i++ {
			if cnt[i] > 0 {
				idxs = append(idxs, i)
			}
		}
		if len(idxs) == 0 {
			break
		}
		sort.Slice(idxs, func(a, b int) bool { return cnt[idxs[a]] > cnt[idxs[b]] })
		take := idxs
		if len(take) > block {
			take = take[:block]
		}
		for _, i := range take {
			cnt[i]--
		}
		if lastBlockSize > 0 {
			time += block // 上一块不是最后一块 → 补齐 n+1 个时间单位
		}
		lastBlockSize = len(take)
	}
	if lastBlockSize > 0 {
		time += lastBlockSize
	}
	return time
}

// ---------- 校验调度合法性 ----------

func legalSchedule(seq []int, n int) bool { // seq 里 -1 表示待命
	last := map[int]int{}
	for i, v := range seq {
		if v < 0 {
			continue
		}
		if p, ok := last[v]; ok && i-p < n+1 {
			return false
		}
		last[v] = i
	}
	return true
}
```

## 139.6 复杂度与常见坑

### 139.6.1 复杂度推导

- **时间 O(N)**：统计频次扫一遍 `N`；再扫两遍 26 个格子（常数）。没有排序、没有模拟。
  - 对照 `simulateOptimal`：`O(answer · 26)`，`answer` 可达 `10^6`，约 `2.6·10^7` 次操作 —— 能过，但和 `O(N)` 差三个数量级。
- **空间 O(1)**：`int[26]` 与 `N` 无关，三个标量 `m / c / bucket`。
- **注意**：答案本身可能比 `N` 大很多（最多约 `N × (n+1)`），但**计算答案不需要走那么多步** —— 这正是公式的收益。

### 139.6.2 七个真实踩过的坑

1. **贪心没有证明 = 猜** —— 本题最典型：公式只有一行，很多人「背下来了」。但被问「为什么不是 `(m-1)(n+2)+c`」「为什么 `c` 要加在最后」时说不清。更糟的是被问「这个下界能不能达到」—— 下界只证明「不可能更快」，**必须再给构造**才能说「答案就是它」。§139.3.2 的两半缺一不可。
2. **`c` 数错** —— `c` 是「频次恰等于 `m` 的种类数」，不是「所有频次的种类数」，也不是「最大频次」。`AAABBB`、`n = 2` 时 `m = 3, c = 2`，答案 `2×3+2 = 8`；若误取 `c = 1` 会得到 7。
3. **忘记取 `max(N, ...)`** —— `tasks = A×2 + 26 个单次任务`、`n = 1` 时桶长只有 3，答案必须是 28。只写桶长会让答案**小于任务数**，这连物理意义都不成立。
4. **`n = 0` 的特殊处理** —— 冷却为 0 时答案就是 `N`。公式 `(m-1)×1 + c` 可能小于 `N`（例如 `A×3, B×3` 给 4），靠 `max` 兜住。**所以 `max` 不是保险，是必需。**
5. **`m == 0` 时 `(m-1)` 变成 `-1`** —— 空输入会让桶长为负。约束保证 `N ≥ 1`，但写库函数时要显式判 `m == 0`。
6. **把「间隔 ≥ n」理解成「间隔 ≥ n−1」** —— 题目说「两个相同任务之间必须有长度为 n 的冷却时间」，中间要有 `n` 个时间单位，所以距离是 `n+1`。差 1 会让所有答案偏小。
7. **用 `int` 存桶长却在 `n` 放大后溢出** —— 本题 `(m-1)(n+1) ≤ 10^4 × 101 ≈ 10^6`，安全；但如果 `n ≤ 10^9`，`(m-1)*(n+1)` 会溢出成负数，`Math.max` 又会把错误结果「洗白」成 `N`，看不出 bug。换 `long`。

### 139.6.3 面试官最爱追问的三个问题

**Q1：为什么答案是 `max(N, (m-1)(n+1)+c)`？**

> 「两条下界 + 一个构造。下界一：每个时间单位最多执行一个任务，所以 ≥ N。下界二：取任意一个频次为 `m` 的任务 `A`，它 `m` 个副本相邻至少隔 `n+1`，所以最后一个副本位置 ≥ `(m-1)(n+1)`；而所有 `c` 个频次为 `m` 的任务的「最后一个副本」占据 `c` 个互不相同的位置，最靠后的至少是 `(m-1)(n+1)+(c-1)`，长度再 +1 得 `(m-1)(n+1)+c`。构造方面：`N ≤ L1` 时用阶梯桶阵列（`c` 列高度 `m`、其余列高度 `m-1`，总格数恰为 `L1`）；`N ≥ L1` 时用「块填充」，每块 `n+1` 格放当前剩余最多的不同任务，此时不会出现空转，长度就是 N。两条下界都被达到，所以答案是 `max`。」

**Q2：如果冷却时间对每个任务不同呢？**

> 「公式失效，因为「桶的宽度」不再统一，最高频任务仍然决定骨架，但每个间隙的容量取决于具体任务。此时稳妥做法是优先队列模拟：`O(answer × 种类数)`，其中 `answer` 是最终长度。要证明它最优，需要论证「每一步取剩余最多的可用任务」不会让后续更差 —— 这比本章的下界论证麻烦得多，也说明**统一的冷却时间是一个很强的结构假设**。」

**Q3：如果要求输出具体调度方案，怎么办？**

> 「本章的构造本身就是方案：`N ≤ L1` 时把阶梯桶阵列填出来（空格即待命）；`N ≥ L1` 时用块填充，每块取剩余次数最多的不同任务。两者都是 `O(N · 26)` 或 `O(N log 26)`，而且直接可证明合法（同一列/同一任务在相邻块之间的距离 ≥ n+1）。」

## 附：本章小结（可背走的三句话）

```text
① 最高频任务的 m 个副本把时间轴切成 m 个「桶」，每桶 n+1 格 → 下界 (m-1)(n+1)+c
② 另有容量下界 N；两条下界都能被达到（阶梯桶阵列 / 块填充）→ 答案 = max(N, L1)
③ 只有下界没有构造 = 证明只写了一半；c 是「频次等于 m 的种类数」，不是别的
```
