## 032.1 题目

**原题链接**：<https://leetcode.cn/problems/top-k-frequent-elements/>

### 题意重述（把隐含条件补齐）

给你一个整数数组 `nums` 和一个整数 `k`，返回其中出现**频率前 `k` 高**的元素。可以按**任意顺序**返回答案。

题干最后还有一句关键提示：「**你算法的复杂度必须优于 `O(n log n)`**」。

| 隐含条件 | 出处 | 违反了会怎样 |
| --- | --- | --- |
| **返回元素本身，不是频次** | 「返回出现频率前 k 高的元素」 | 返回 `[[1,3],[2,2]]` 这种带频次的结构 → 类型不匹配 |
| **顺序不限** | 「可以按任意顺序返回答案」 | 不必为排序结果做额外处理，省掉 `O(k log k)` |
| **答案集合唯一** | 数据保证 | 不会出现「两个元素频次相同、抢第 k 名」的裁决问题——**这是能直接比较集合的前提**（见 §032.6.2 坑 7） |
| **`k` 合法** | `1 <= k <= 不同元素的个数` | 不必判越界 |
| **必须优于 `O(n log n)`** | 题干末句 | 「哈希计数 + `sort` 全排」是 `O(n log n)`，**判题能过但违背题意** |
| **元素值可能为负** | `-10⁴ <= nums[i] <= 10⁴` | 不能用值当下标（除非先加偏移），只能用哈希或偏移计数数组 |

### 约束与「量级反推」

| 约束 | 值 | 它对算法的含义 |
| --- | --- | --- |
| `1 <= nums.length <= 10⁵` | n 最多 10 万 | `O(n log n)` 的全排实测 6~40 ms（含哈希计数），能过但不是答案 |
| `k ∈ [1, 不同元素个数]` | k 可达 `n` | `O(n log k)` 在 `k = n` 时退化成 `O(n log n)`，要留意 |
| `-10⁴ <= nums[i] <= 10⁴` | 值域只有 2·10⁴ | 可以用「值 + 偏移」当计数数组下标，省掉哈希；**但频次排序仍要处理** |
| **频次 ∈ [1, n]** | 频次天然有界 | **这是本题的题眼**：频次是小整数 → 可以当桶下标 → `O(n)` |
| `k` 与「不同元素个数」同阶可能 | 无额外限制 | 桶排序在这里不会退化，堆会（见 §032.3.1 实测） |

> 💡 **量级 → 算法**：看到「频次」「计数」「排名」，先问一句「**这个量是 `[0, n]` 的小整数吗**」。
> 是 → 桶 / 计数排序可以做到 `O(n)`；不是（值是浮点、字符串、`10⁹` 级大数）→ 只能堆或快速选择。
> **比较排序的 `Ω(n log n)` 下界只约束「比较」，不约束「用值当下标」。**

### 示例

```text
输入：nums = [1,1,1,2,2,3], k = 2
输出：[1,2]
解释：1 出现 3 次，2 出现 2 次，3 出现 1 次 → 前 2 高是 1 和 2

输入：nums = [1], k = 1
输出：[1]

输入：nums = [4,4,4,5,5,6], k = 1
输出：[4]        ← 只取频次最高的一个，不能把并列的 5 也带上
```

### 我自造的五个反例

```text
① [4,4,4,5,5,6], k=1             → 打「桶里同频次的元素全拿走」：会返回 2 个，超出 k
② [1,2], k=2                     → 打「k 等于不同元素个数」：两个频次都是 1
③ [7,7,7,7,7], k=1               → 打「maxCnt = n」：桶数组要开 n+1 个，空间与时间的边界在这
④ [1,1,2,2,3,3], k=2             → 打「频次并列」：三个都是 2 次，题目保证不会出现这种输入，
                                    但对拍的判据必须按「频次阈值」而不是「集合相等」
⑤ [10000,-10000,0], k=3          → 打「用值当数组下标」：负下标直接越界
```

②③④ 都在说明同一件事：**频次是这道题里唯一「有序」的量**，元素值本身完全无序。

## 032.2 从暴力到最优：第一个念头为什么错

### 第一步：暴力（哈希计数 + 按频次全排序）

```text
freq = {}                       // O(n)
for v in nums: freq[v]++
pairs = freq 的所有 (值, 频次)
sort pairs by 频次 降序          // O(m log m)，m = 不同元素个数 ≤ n
取前 k 个的值
```

- 时间 `O(n + m log m)`，最坏 `O(n log n)`；空间 `O(m)`。
- 本机实测（Go 1.19.8，`n = 2·10⁵`，值域 `10⁴`）：**41.4 ms**（含哈希计数；其中计数约 6 ms，排序约 35 ms）。
- **它违背题干的「必须优于 `O(n log n)`」**，但在 LeetCode 上能过——所以它是最容易被当成答案交上去的错误答案。

### 第二步：卡点在哪 —— 为什么要排序？

我们把问题拆成两半：

| 子问题 | 代价 | 有没有更快的办法 |
| --- | --- | --- |
| 统计每个元素的频次 | `O(n)`，哈希一遍 | 没有更快（每个元素至少要看一次） |
| **从 `m` 个频次里挑出前 `k` 大** | 排序要 `O(m log m)` | **有**：频次是 `[1, n]` 的整数，可以当**数组下标**，不需要比较 |

**卡点就在第二半**：`m log m` 的排序把频次当成「任意可比较的值」，但频次其实有个更强的性质——**它有界且密集**（`1 ≤ freq ≤ n`）。有界的整数不需要比较，只需要「放到它该在的位置上」。

### 第三步：灵感 —— 用频次当桶的下标

```text
freq: {1:3, 2:2, 3:1}
                    ↓ 把「频次」当下标
buckets[3] = [1]     ← 出现 3 次的元素
buckets[2] = [2]     ← 出现 2 次的元素
buckets[1] = [3]     ← 出现 1 次的元素
                    ↓ 从大到小扫，凑够 k 个就停
3 → [1]，已取 1 个
2 → [2]，已取 2 个 = k → 停
答案 {1, 2}
```

关键点有三个：

1. **桶的个数由「最大频次」决定，与元素值域无关**。这是它比「值域计数排序」更强的地方：哪怕元素是 `10⁹` 级的随机大数，只要频次不超过 `n`，桶数组就只要 `n+1` 个。
2. **从高到低扫桶，天然得到「频次降序」**。不需要任何比较。
3. **同一个桶里的元素顺序无意义**（题目允许任意顺序），所以桶内不需要排序。

### 第四步：另一条腿 —— 小顶堆（`O(n log k)`）

把 031 的 TopK 模型直接套过来：维护一个**按频次比较**的、大小为 `k` 的小顶堆，堆顶是「当前 k 个里频次最小的」。

- 时间 `O(n + m log k)`，空间 `O(m + k)`。
- 它符合「优于 `O(n log n)`」的要求（因为 `log k ≤ log m`），而且**不依赖「频次有界」这个性质**，所以换到「按任意实数打分排序」的场景仍然成立。

**两者的取舍正是本章的核心**，见下一节。

## 032.3 原理拆解

### 032.3.1 数据结构与算法选型

| 方案 | 时间 | 空间 | 代码量 | 什么时候会输 |
| --- | --- | --- | --- | --- |
| 哈希计数 + 按频次全排序 | O(n + m log m) | O(m) | 10 行 | 违背题意（不优于 `O(n log n)`）；`m` 大时最慢 |
| **小顶堆（按频次）** ✅ | O(n + m log k) | O(m) + O(k) | 15 行 + 堆实现 | `k` 接近 `m` 时退化成 `O(m log m)`；常数大（Java 装箱） |
| **频次桶（计数排序）** ✅ | **O(n + maxCnt)** | O(m) + O(maxCnt) | 18 行 | 频次上界不可知或极大时；`maxCnt` 很大而 `m` 很小时浪费 |
| 快速选择（按频次） | 平均 O(n + m) | O(m) | 25 行 | 需要输出「前 k 个」时仍要再扫一遍；`k` 个结果无序 |
| 值域计数数组（值当下标） | O(n + V) | O(V) | 12 行 | 值域大（`10⁹`）或值为负（要偏移）；**只省掉哈希，不解决排序** |

**实测对比**

**Go 1.19.8 / n = 2·10⁵ / 值域 10⁴ / 单位 ms / 7 次取最快**

| k | 小顶堆 | 频次桶 | 堆 / 桶 | 结论 |
| --- | --- | --- | --- | --- |
| 1 | **3.943** | 6.024 | 0.65× | 堆快 |
| 10 | **3.943** | 6.024 | 0.65× | 堆快 |
| 100 | **6.375** | 7.881 | 0.81× | 堆更快一点 |
| 5,000 | 8.142 | **7.060** | 1.15× | 桶反超（`log k ≈ 12`，堆开始吃亏） |

**Java 17 / n = 2·10⁵ / 值域 10⁴ / 单位 ms / 5 次取最快**

| k | 小顶堆 | 频次桶 | 堆 / 桶 |
| --- | --- | --- | --- |
| 1 | 5.392 | 5.754 | 0.94× |
| 10 | **4.630** | 5.228 | 0.89× |
| 100 | **4.683** | 4.967 | 0.94× |
| 5,000 | 5.556 | **4.922** | 1.13× |

**从这两张表要读出三件事**：

1. **`k` 小时堆更快**。这不是因为堆的复杂度更好，而是因为「哈希计数」这一半已经把两边都拖到 4~6 ms 了。堆在 `k` 小时每次 `O(log k)` 几乎为零，而桶排序要先分配 `maxCnt+1` 个桶、再 `append` 进桶——**分配桶的固定开销大于 `log k` 的节省**。
2. **`k` 大时桶反超**。堆每次替换要 `log k ≈ 12` 次比较，`m = 10⁴` 个不同元素就是 12 万次比较；桶始终是两趟线性。
3. **两边的绝对差距很小（0.65× ~ 1.15×），说明瓶颈不在这一步，而在哈希计数**。所以面试里正确的表述是「两者都是 `O(n)` 量级（堆是 `O(n log k)`），主导成本是哈希，选择依据是可扩展性而不是这几个百分点」。

**频次桶的两个边界（这一段是本题最容易翻车的地方）**

| 边界 | 现象 | 实测 / 结论 |
| --- | --- | --- |
| **`maxCnt = n`**（全部元素相同） | 桶数组要 `n+1` 个槽位 | Go 实测 `n = 2·10⁵` 时 **16.7 ms**（大量空切片分配），反而比小顶堆慢一半 |
| **`maxCnt = 1`**（全部不同，值域极大） | 桶数组只有 2 个槽位 | Go 实测值域 `2³⁰`、20 万个不同值：**22.4 ms**，瓶颈全在哈希；桶本身几乎免费 |
| 桶数组长度写成 `n+1` 而不是 `maxCnt+1` | 不致命，但白分配内存 | 全相同时 `n+1` 与 `maxCnt+1` 相等；全不同时前者浪费 `n` 个槽 |
| 同一频次有多个元素 | 桶里是切片，可能一次取超 | `res` 可能在最后一步长度 `> k`，**必须 `res[:k]` 截断** |

### 032.3.2 为什么这个做法是对的（正确性论证）

**（1）频次桶的正确性**

- 引理 1：每个元素的频次 `c` 满足 `1 ≤ c ≤ maxCnt`，因此 `buckets[c]` 一定存在，不会漏掉任何元素。
- 引理 2：从 `c = maxCnt` 递减到 `1` 遍历时，访问到的频次序列**严格递减**，所以「先被加入 `res` 的元素频次 ≥ 后被加入的」。
- 定理：`res` 的前 `k` 个元素恰好是频次最高的 `k` 个。因为按频次降序排列后，前 `k` 个的频次阈值是 `θ`（第 k 大的频次）；遍历时所有频次 `> θ` 的元素一定在频次 `≥ θ` 的桶之前被取完，而桶内元素频次相同、任取即可。所以取到 `k` 个时，已经取得的元素频次都 `≥ θ`，未取得的都 `≤ θ`。∎

> 注意这个证明**不要求答案唯一**：即使第 k 名有并列，任何一组取法都满足「频次 ≥ θ」，都合法。题目额外保证唯一，只是为了让我们能直接比集合。

**（2）小顶堆的正确性**

不变量：**处理完前 `i` 个不同元素后，堆中恰好是其中频次最大的 `min(i, k)` 个。** 与 031 的证明完全同构：

- 堆未满 → 直接入堆；
- 堆满且新元素频次 `> 堆顶频次` → 踢掉堆顶（当前 k 个里最弱的）换新的；
- 堆满且 `≤` 堆顶 → 它挤不进前 k，跳过。∎

**（3）为什么「桶排序」能突破 `Ω(n log n)` 下界**

这是很多人答不上来的一问。答案：**那个下界只对「基于比较」的排序成立**。决策树论证的前提是「算法只能通过 `a < b` 获得信息」，`n!` 种排列需要 `log₂(n!) = Θ(n log n)` 次比较才能区分。而桶排序**根本不做比较**：它用「频次 `c` 作为下标」直接定位，读者可以理解为「一次性读取了 `log n` 位信息」，绕开了决策树模型。代价是：**必须存在一个有界的小整数键**（这里是频次），并且需要 `O(maxCnt)` 的额外空间。

### 032.3.3 通用解题思路（可迁移的那一层）

本题是 **「用值域换时间」** 这个模型的母题：

```
原始问题：从 m 个 (元素, 计数) 里挑出计数最大的 k 个
          ↓ 问一句：计数是不是 [0, C] 的小整数？
是 → 桶：buckets[计数] = 元素列表，从高往低扫 → O(n + C)
否 → 堆：大小 k 的小顶堆 → O(n log k)
          ↓ 还可以结合：如果计数范围大但离散程度低（只有几十种取值）→ 坐标压缩后开桶
```

同一模型下的题：

| 题 | 被当桶下标的量 | 上界 |
| --- | --- | --- |
| [LC 347 前 K 个高频元素](https://leetcode.cn/problems/top-k-frequent-elements/) | 元素频次 | `n` |
| [LC 451 根据字符出现频率排序](https://leetcode.cn/problems/sort-characters-by-frequency/) | 字符频次 | 字符串长度 |
| [LC 1636 按照频率将数组升序排序](https://leetcode.cn/problems/sort-array-by-increasing-frequency/) | 元素频次 | `n` |
| [LC 912 排序数组](https://leetcode.cn/problems/sort-an-array/) | 元素值 | 值域宽度（见 `028`） |
| [LC 274 H 指数](https://leetcode.cn/problems/h-index/) | 论文引用数 | `n`（超过 n 的一律按 n 算） |
| [LC 1122 数组的相对排序](https://leetcode.cn/problems/relative-sort-array/) | 元素值 | `arr1` 的值域（1001） |
| [LC 692 前 K 个高频单词](https://leetcode.cn/problems/top-k-frequent-words/) | 频次（但并列要比字典序） | `n`，桶内还要排序 |

**共同点**：**看到「计数」「频次」「排名」，先检查这个量是否落在 `[0, O(n)]`；是的话，`O(n)` 的解就在眼前。**

### 032.3.4 可扩展性（面试追问的六个方向）

| 追问 | 变化 | 应对 |
| --- | --- | --- |
| 要求按频次**降序**返回，并列时按值升序 | 桶内不再无序 | 桶天然给出频次降序，只需对**每个桶内部**排序（总代价 `O(m log m)` 但只在桶内） |
| 元素是**字符串** | 哈希 key 变字符串 | 结构完全不变：`map[string]int` 计数 + `buckets[c] = []string` |
| 数据**流式**到达，随时查询 TopK | 无法两趟 | 小顶堆（`O(log k)` 每次插入）；或「堆 + 懒删除」维护频次变化 |
| `k` 接近不同元素个数 | 桶仍然 `O(n)`，堆退化 | **选桶**；堆此时是 `O(m log m)`，等于全排序 |
| 频次上界不可知（如按浮点分数聚合） | 桶失效 | 堆 / 快速选择；或先求 `maxCnt` 再开桶（多一趟 `O(m)` 扫描，可行） |
| 内存极紧（要求 `O(k)` 空间） | 桶是 `O(maxCnt + m)` | **堆是唯一选择**：`O(k)` 额外空间，配合流式读取 |

## 032.4 图解推演

### 032.4.1 从频次表到桶的映射

`nums = [1,1,1,2,2,3,4,4,4,4]`，`k = 2`：

```text
第 1 步：哈希计数
   ┌─────┬─────┬─────┬─────┐
   │  1  │  2  │  3  │  4  │   ← 元素
   ├─────┼─────┼─────┼─────┤
   │  3  │  2  │  1  │  4  │   ← 频次
   └─────┴─────┴─────┴─────┘
   maxCnt = 4

第 2 步：频次当桶下标（桶数组长 maxCnt+1 = 5）
   buckets[0] = []            ← 恒为空（频次至少 1）
   buckets[1] = [3]
   buckets[2] = [2]
   buckets[3] = [1]
   buckets[4] = [4]
                  ↑
   注意：桶的「下标」是频次，「内容」是元素 —— 与常见的「下标是元素、内容是频次」正好反过来

第 3 步：从高往低扫，凑够 k 个
   c=4 → [4]   res=[4]      len=1 < 2  继续
   c=3 → [1]   res=[4,1]    len=2 = k  → 停
   c=2/1 不再访问

答案 {4, 1}（顺序任意）
```

### 032.4.2 小顶堆的替换过程（同一个例子）

`k = 2`，按 `freq` 的遍历顺序 `1(3), 2(2), 3(1), 4(4)`：

```text
      操作                     堆（按频次的小顶堆）        堆顶频次
 ────────────────────────────────────────────────────────────────
  1(3) 入堆              [1:3]                          3
  2(2) 入堆              [2:2, 1:3]                     2
  3(1)：1 > 2 ? 否       [2:2, 1:3]                     2   ← 跳过
  4(4)：4 > 2 ? 是       [1:3, 4:4]   弹出 2:2，4 入堆     3

  结束：堆内有 1(3) 与 4(4)，堆顶 = 频次最小的那个 = 3
```

堆的内部形态（`container/heap` 的数组表示，`Push` 追加后上浮）：

```text
入堆 2:2（此前堆只有 1:3）
      [1:3]                    [1:3, 2:2]
                                父 3 比子 2 大 → 2 上浮
      [2:2, 1:3]              堆顶 = 2 ✓

替换：pop 2:2（把末尾 2:2 换到根，下沉）→ push 4:4（追加到末尾，上浮）
      [1:3]  →  [1:3, 4:4]
                 父 3 比子 4 小 → 不上浮，堆顶仍是 3 ✓
```

### 032.4.3 两条路线的对比 + 选型判据

```text
                  ┌────── nums（n 个元素）──────┐
                  │                             │
        ┌─────────▼──────────┐      ┌───────────▼─────────────┐
        │ 路线 A：小顶堆       │      │ 路线 B：频次桶           │
        │ O(n + m log k)      │      │ O(n + maxCnt)            │
        │ 空间 O(m + k)       │      │ 空间 O(m + maxCnt)       │
        │ 不依赖「频次有界」   │      │ **依赖 maxCnt ≤ n**      │
        └─────────┬──────────┘      └───────────┬─────────────┘
                  │                             │
      k 小 / 流式 / 内存紧 → 选 A        k 大 / 要求频次降序 → 选 B
      Go 实测 k=1: 3.94 ms             Go 实测 k=5000: 7.06 ms
      但 maxCnt=n（全相同）时 B 要 16.7 ms ← 边界
```

## 032.5 双语言实现

### 032.5.1 Java

```java
import java.util.*;

class Solution {

    // ===== 解法一：哈希计数 + 大小为 k 的小顶堆，O(n + m log k) =====
    public int[] topKFrequent(int[] nums, int k) {
        Map<Integer, Integer> freq = new HashMap<>();
        for (int v : nums) freq.merge(v, 1, Integer::sum);   // merge 比 getOrDefault 少一次查表

        // 堆按「频次」比较：堆顶是当前 k 个里频次最小的，用来决定要不要淘汰
        PriorityQueue<int[]> pq = new PriorityQueue<>(k, (a, b) -> a[1] - b[1]);
        for (Map.Entry<Integer, Integer> e : freq.entrySet()) {
            if (pq.size() < k) {
                pq.offer(new int[]{e.getKey(), e.getValue()});
            } else if (e.getValue() > pq.peek()[1]) {          // 严格大于才替换
                pq.poll();
                pq.offer(new int[]{e.getKey(), e.getValue()});
            }
        }

        int[] res = new int[k];
        for (int i = k - 1; i >= 0; i--) res[i] = pq.poll()[0];  // 倒着填：堆弹出是频次升序
        return res;
    }

    // ===== 解法二：哈希计数 + 频次桶（计数排序），O(n + maxCnt) =====
    public int[] topKFrequentBucket(int[] nums, int k) {
        Map<Integer, Integer> freq = new HashMap<>();
        int maxCnt = 0;
        for (int v : nums) {
            int c = freq.merge(v, 1, Integer::sum);
            maxCnt = Math.max(maxCnt, c);       // 桶数组只要 maxCnt+1，不需要 n+1
        }

        // buckets[c] = 出现 c 次的全部元素；用 null 占位，避免 new 出 maxCnt+1 个空 ArrayList
        List<List<Integer>> buckets = new ArrayList<>(Collections.nCopies(maxCnt + 1, (List<Integer>) null));
        for (Map.Entry<Integer, Integer> e : freq.entrySet()) {
            int c = e.getValue();
            if (buckets.get(c) == null) buckets.set(c, new ArrayList<>());
            buckets.get(c).add(e.getKey());
        }

        int[] res = new int[k];
        int idx = 0;
        for (int c = maxCnt; c >= 1 && idx < k; c--) {   // 从高到低，天然频次降序
            List<Integer> b = buckets.get(c);
            if (b == null) continue;
            for (int v : b) {
                if (idx == k) break;      // 同一桶里元素可能多于剩余名额，必须及时停
                res[idx++] = v;
            }
        }
        return res;
    }
}
```

### 032.5.2 Go

```go
package main

import (
	"container/heap"
	"fmt"
	"math/rand"
	"sort"
)

// ===== 解法一：哈希计数 + 大小为 k 的小顶堆，O(n + m log k) =====
type freqPair struct{ val, cnt int }

// Go 的 container/heap 要求实现 5 个方法：Len / Less / Swap / Push / Pop。
// Java 的 PriorityQueue 只要一个 Comparator —— 这是 Go 堆代码更长的根本原因
type freqHeap []freqPair

func (h freqHeap) Len() int            { return len(h) }
func (h freqHeap) Less(i, j int) bool  { return h[i].cnt < h[j].cnt } // 按频次的小顶堆
func (h freqHeap) Swap(i, j int)       { h[i], h[j] = h[j], h[i] }
func (h *freqHeap) Push(x interface{}) { *h = append(*h, x.(freqPair)) }
func (h *freqHeap) Pop() interface{} {
	old := *h
	n := len(old)
	v := old[n-1] // 取末尾：container/heap 会先把堆顶换到末尾再调 Pop
	*h = old[:n-1]
	return v
}

func topKFrequent(nums []int, k int) []int {
	freq := make(map[int]int, len(nums))
	for _, v := range nums {
		freq[v]++
	}

	h := &freqHeap{}
	for v, c := range freq {
		if h.Len() < k {
			heap.Push(h, freqPair{v, c})
		} else if c > (*h)[0].cnt {
			// 比堆顶（当前 k 个里频次最小的）更强：替换堆顶再修复，
			// 比 Pop + Push 少一次 O(log k) 的下沉
			(*h)[0] = freqPair{v, c}
			heap.Fix(h, 0)
		}
	}

	res := make([]int, h.Len())
	for i := len(res) - 1; i >= 0; i-- {
		res[i] = heap.Pop(h).(freqPair).val // 倒着填，使结果大致按频次升序
	}
	return res
}

// ===== 解法二：哈希计数 + 频次桶（计数排序），O(n + maxCnt) =====
func topKFrequentBucket(nums []int, k int) []int {
	freq := make(map[int]int, len(nums))
	maxCnt := 0
	for _, v := range nums {
		freq[v]++
		if freq[v] > maxCnt {
			maxCnt = freq[v] // 桶数组只要 maxCnt+1：全不同时是 2，全相同时是 n+1
		}
	}

	buckets := make([][]int, maxCnt+1)
	for v, c := range freq {
		buckets[c] = append(buckets[c], v)
	}

	res := make([]int, 0, k)
	for c := maxCnt; c >= 1 && len(res) < k; c-- {
		res = append(res, buckets[c]...)
	}
	return res[:k] // 必须截断：最后一个桶可能有多个元素，append 会超出 k
}

func main() {
	r := rand.New(rand.NewSource(41))
	// 对拍判据：不能比「集合相等」，因为频次并列时答案不唯一（题目保证唯一，
	// 但随机数据经常造出并列）。正确判据是「每个返回元素的频次 ≥ 第 k 大的频次阈值」。
	for iter := 0; iter < 20000; iter++ {
		n := r.Intn(30) + 1
		nums := make([]int, n)
		for i := range nums {
			nums[i] = r.Intn(6) // 值域小 → 频次密集、并列多
		}
		freq := map[int]int{}
		for _, v := range nums {
			freq[v]++
		}
		if len(freq) == 0 {
			continue
		}
		k := r.Intn(len(freq)) + 1
		cnts := make([]int, 0, len(freq))
		for _, c := range freq {
			cnts = append(cnts, c)
		}
		sort.Sort(sort.Reverse(sort.IntSlice(cnts)))
		threshold := cnts[k-1] // 第 k 大的频次

		for _, got := range [][]int{topKFrequent(nums, k), topKFrequentBucket(nums, k)} {
			if len(got) != k {
				panic(fmt.Sprintf("长度错 got=%v k=%d", got, k))
			}
			seen := map[int]bool{}
			for _, v := range got {
				if seen[v] {
					panic(fmt.Sprintf("重复元素 %v", got))
				}
				seen[v] = true
				if freq[v] < threshold {
					panic(fmt.Sprintf("频次不足: %v, threshold=%d, nums=%v", got, threshold, nums))
				}
			}
		}
	}
	fmt.Println("topKFrequent / topKFrequentBucket: 20000 组随机对拍通过")

	// 边界：全相同 → maxCnt = n，桶数组要 n+1 个槽
	same := make([]int, 200000)
	for i := range same {
		same[i] = 42
	}
	fmt.Println("全相同 n=2e5, k=1 →", topKFrequentBucket(same, 1))
	// 边界：全不同 → maxCnt = 1，桶数组只有 2 个槽（值域多大都无所谓）
	distinct := make([]int, 2000)
	for i := range distinct {
		distinct[i] = i * 7919
	}
	fmt.Println("全不同 n=2000, k=3 →", topKFrequentBucket(distinct, 3))
}
```

### 032.5.3 双语言差异批注

| 点 | Java | Go | 对本题的影响 |
| --- | --- | --- | --- |
| 计数写法 | `map.merge(v, 1, Integer::sum)` | `freq[v]++`（map 零值即 0，可直接 `++`） | Go 更短；Java 用 `merge` 比 `getOrDefault` 少一次查表 |
| 堆的比较器 | `(a, b) -> a[1] - b[1]`（一个 lambda） | `Less` 方法里写 `h[i].cnt < h[j].cnt` | **`Less` 里写成 `>` 就变成大顶堆**，结果是「频次最低的 k 个」 |
| 替换堆顶 | `poll()` + `offer()`，两次 `O(log k)` | `(*h)[0] = ...; heap.Fix(h, 0)`，一次 | Go 更快；Java 想省这一次只能自己写数组堆 |
| 桶容器的类型 | `List<List<Integer>>` + `Collections.nCopies` 占位 | `[][]int`，`nil` 天然占位 | Java 的泛型数组不能直接 `new List<Integer>[]`（会警告），用 `List<List<Integer>>` 最干净 |
| 桶内追加 | `buckets.get(c).add(v)` | `buckets[c] = append(buckets[c], v)` | Go 的 `append` 让「桶」天然是可变长切片；Java 需要先判 `null` 再 `set` 一个新的 `ArrayList` |
| 截断到 k | 循环内 `if (idx == k) break;` | `return res[:k]` 一行 | Go 的切片截断更直接，但**要保证 `len(res) ≥ k`**（本题保证 `k ≤ 不同元素数`，所以安全） |
| 结果排序 | 堆弹出后倒着填 | 同 | 题目允许任意顺序，这一步只是为了「结果看起来像频次升序」，可以省 |

## 032.6 复杂度与常见坑

### 032.6.1 复杂度推导

- **哈希计数**：`O(n)` 均摊。最坏 `O(n²)`（哈希碰撞攻击），本题值是小整数，哈希均匀，实际是 `O(n)`。
- **小顶堆**：`O(m log k)`，`m` 是不同元素个数。每个元素最多一次入堆或替换，每次 `O(log k)`。`k = m` 时退化成 `O(m log m)`。
- **频次桶**：`O(n + maxCnt + m)`。注意这里 **`maxCnt` 而不是 `n`**：桶数组的长度是 `maxCnt+1`，遍历桶也是 `maxCnt` 次。
  - `maxCnt ≤ n` 恒成立（最极端是全部元素相同 → `maxCnt = n`）。
  - 所以桶排序严格是 `O(n)` 的，但**常数与 `maxCnt` 成正比**：`maxCnt = n` 时要分配 `n+1` 个切片头（Go 里每个 24 字节，2·10⁵ 个约 4.8 MB），实测 16.7 ms。
- **空间**：
  - 堆：`O(m + k)`；
  - 桶：`O(m + maxCnt)` —— **这是桶相对堆的唯一劣势**，也是「内存紧就选堆」的依据。

### 032.6.2 八个真实踩过的坑

1. **桶取完不截断**。`buckets[c]` 里有 3 个元素但只差 1 个名额时，`res` 长度变成 `k+2`，判题直接错。修法：循环里 `if idx == k break;`，或最后 `res[:k]`。
2. **桶数组开 `n+1`**。全不同时 `maxCnt = 1`，却分配了 `n+1` 个槽。正确做法是先求 `maxCnt`（多一趟 `O(m)` 扫描，这个代价很小）。
3. **`maxCnt = 0` 时开 `buckets[0]`**。本题 `n ≥ 1` 所以不会触发；但如果写成工具函数，空输入时要提前返回 `[]`。
4. **堆的比较器写反**。Java 写 `(a, b) -> b[1] - a[1]`（大顶堆）会返回频次**最低**的 k 个；Go 的 `Less` 写 `>` 也一样。**判据：堆顶必须是最容易被淘汰的那个**（频次最小的）。
5. **`getOrDefault(v, 0) + 1` 写成 `get(v) + 1`**。`HashMap.get` 对不存在的键返回 `null`，`null + 1` 抛 `NullPointerException`。用 `merge` 或 `getOrDefault`。
6. **拿「集合相等」做对拍断言**。频次并列时（`[1,1,2,2], k=1`）答案不唯一，堆和桶可能给出不同集合，但都合法。**断言必须写成「频次 ≥ 第 k 大频次」**（§032.5.2 的 `main` 就是这么写的）。这是 001 章那条教训的复现：**判据必须与「解是否唯一」对齐。**
7. **以为题目保证的「唯一」是多余的**。它唯一的作用就是让「返回集合」这件事有确定答案。如果面试官去掉这个保证，你就要在代码里说明「并列时可任取」，并让对拍判据变成阈值式。
8. **用值当数组下标**。`nums[i]` 可能是 `-10⁴`，直接 `count[nums[i]]++` 越界。要偏移 `+10⁴`（值域 2·10⁴ 时可以这么做，省掉哈希）。

### 032.6.3 面试官最爱追问的三个问题

**Q1：桶排序为什么能突破 `O(n log n)`？比较排序的下界不是被推翻了吗？**
> 「没有推翻。`Ω(n log n)` 是**基于比较**的排序下界：算法只能通过 `a < b` 获取信息，`n!` 种排列需要 `Θ(n log n)` 次比较才能区分。桶排序不做比较，它用「频次 `c`」直接算出位置，等于一次读取了 `log n` 位信息，跳出了决策树模型。代价有三条：① 必须存在**有界的小整数键**（这里是频次 ∈ `[1, n]`）；② 需要 `O(maxCnt)` 的额外空间；③ 对任意实数 / 字符串键不成立。」

**Q2：桶排序和堆，你会在生产代码里选哪个？**
> 「看三个约束：① **`k` 相对 `m` 的大小**——`k` 小时堆更省空间也更快（实测 `k=1` 堆快 35%），`k` 接近 `m` 时桶更稳（堆退化到 `O(m log m)`）；② **内存**——堆是 `O(k)` 额外空间，桶是 `O(maxCnt)`，`maxCnt` 可能等于 `n`（全相同时实测多花 10 ms 分配桶）；③ **是否要求频次降序输出**——桶天然有序，堆还要额外排。**在我实测的数据上两者只差 0.65×~1.15×，真正的瓶颈是哈希计数，所以我会按「内存」和「是否需要有序」来选，而不是按这几个百分点。**」

**Q3：如果数据是一条永不停歇的日志流，要随时回答「当前 TopK 高频 IP」呢？**
> 「流式场景下桶排序不可用（需要两趟），只能用堆，而且要做**懒删除**：维护 `map[ip]int` 计数 + 一个按频次的小顶堆，每次某 IP 计数 +1 时不立刻调整堆（否则每次都要 `O(log k)`），而是把 `(ip, 新频次)` 推入堆，查询时不断弹出「堆顶频次 ≠ map 里当前频次」的过期项。摊还下来每次插入 `O(log n)`，查询 `O(k log n)` 最坏但通常很快。工程上还会加『分段 + 定期合并』来限制堆的大小。」
