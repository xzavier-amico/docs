## 036.1 题目

**原题链接**：<https://leetcode.cn/problems/group-anagrams/>

### 题意重述（把隐含条件补齐）

给你一个字符串数组 `strs`，请把**互为字母异位词**的字符串分到同一组，返回所有组。组内顺序、组间顺序都不限。

「字母异位词」的定义是：两个字符串含有的**字母种类与每种字母的个数完全相同**，只是排列顺序不同。比如 `eat`、`tea`、`ate` 三个字符串的字母多重集都是「a 一个、e 一个、t 一个」，所以它们是一组。

这句话背后有四个必须读出来的约束，漏一个就会写出过不了隐藏用例的代码：

| 隐含条件 | 出处 | 违反了会怎样 |
| --- | --- | --- |
| 只有**小写英文字母** | 「`strs[i]` 仅由小写英文字母组成」 | 用 26 位计数向量当下标是安全的；如果混入大写或数字，`c - 'a'` 会越界或互相覆盖 |
| 长度可以**不相等**但同一组内必然相等 | 异位词定义 | 「先按长度分桶再组内比较」是个有效的剪枝，但不是必须的 |
| 组内 / 组间**顺序都不限** | 「可以按任意顺序返回答案」 | 不需要对结果排序，省掉一次 `O(m log m)`；也意味着**对拍时不能直接比数组**，必须先规范化 |
| 数组长度可以到 `10^4`，单串长度到 `100` | 约束表 | `O(n²)` 的两两比较是 `5·10⁷` 次「串比较」，每次都可能是 100 字符 → 实际 `5·10⁹` 量级的字符操作，必超时 |

### 约束与「量级反推」

| 约束 | 值 | 它对算法的含义 |
| --- | --- | --- |
| `1 <= strs.length <= 10^4` | n 最多 1 万 | `O(n²)` = `5·10⁷` 次配对，每次配对要比较两个串 → 不行；**目标 O(n·k)**，n·k 最多 `10^6` |
| `0 <= strs[i].length <= 100` | 单串长度 k ≤ 100 | 排序一个串是 `k log k ≈ 100·7 = 700` 次操作；计数只需 `k = 100` 次。**k 小但 n 大，所以「每个串的处理成本」直接乘在总时间上** |
| `strs[i]` 仅小写字母 | 字母表大小 σ = 26 | 计数向量只有 26 位，定长、可直接当 key；这是本题能用「计数」而不是「排序」的前提 |
| `strs[i].length >= 1`（题面允许 0） | 空串是合法的异位词组 | 空串的计数向量全 0，会自成一桶 —— 别把「空 key」当成「没有 key」 |

> 💡 **量级 → 算法**：`n = 10^4`、`k = 100`，输入总字符数 `n·k = 10^6`。
> 任何 **O(n·k)** 的做法都在 `10^6` 这个量级，稳过；任何 **O(n²·k)** 的做法都在 `10^10`，必死。
> 所以这道题的优化方向只有一个：**把「组内两两确认」换成「每个串算一次指纹，指纹相同就同组」**。

### 示例

```
输入：strs = ["eat","tea","tan","ate","nat","bat"]
输出：[["bat"],["nat","tan"],["ate","eat","tea"]]

输入：strs = [""]
输出：[[""]]

输入：strs = ["a"]
输出：[["a"]]
```

### 我自造的四个反例（写完必须拿它们打一遍）

```text
① ["", ""]                 → 两个空串必须落在同一组。用「空 key 表示无效」的写法会把它们拆开
② ["ab","ba","abc"]        → 必须分出 [ab,ba] 与 [abc] 两组：长度参与 key 的隐含判断
③ ["ac","bb"]              → 字符和都是 196（97+99 = 98+98），用「字符和」当 key 会把它们并成一组
④ ["abx","aip"]            → 字符积都是 1140720（97·98·120 = 97·105·112），用「字符积」当 key 同样误并
⑤ ["dddddddddd", 100 个 'a' 组成的长串] → 计数向量的某一格会到 100，
                              用「每格 1 字节」时必须确认 100 < 2^16（Java char）与 < 256（Go byte）都成立
```

第 ③④ 条是**本题最容易踩的「伪哈希」陷阱**：这两对数分别撞在「和」与「积」上，但它们都不是字母异位词。**只有把 26 个计数位全部保留，key 才是单射的。**

## 036.2 从暴力到最优：第一个念头为什么错

### 第一步：暴力（先写出来，别急着优化）

最直白的两个写法：

```java
// 暴力 A：对每个串，扫一遍已有分组，逐个成员判断「是否互为异位词」
// 判断方法：各自排序后比较（O(k log k)）或统计 26 个计数再逐位比较（O(k)）
for (String s : strs) {
    boolean placed = false;
    for (List<String> group : groups) {
        if (isAnagram(group.get(0), s)) {   // 只和代表元比
            group.add(s);
            placed = true;
            break;
        }
    }
    if (!placed) groups.add(new ArrayList<>(List.of(s)));
}
```

```java
// 暴力 B：先排序再分组 —— 把 isAnagram 换成「排序后的串相等」
for (String s : strs) {
    char[] a = s.toCharArray();
    Arrays.sort(a);                       // O(k log k)
    String key = new String(a);
    map.computeIfAbsent(key, x -> new ArrayList<>()).add(s);
}
```

- 暴力 A：时间 `O(n²·k)`（外层 n、内层最多 n 组、每组一次 `O(k)` 的计数比较），空间 `O(n·k)`。
- 暴力 B：时间 `O(n·k log k)`，空间 `O(n·k)`。

### 第二步：它为什么不够 —— 用数字说话

设 `n = 10^4`、`k = 100`：

| 写法 | 操作量 | 量级 | 结论 |
| --- | --- | --- | --- |
| 暴力 A（两两比较，按计数） | `n²/2 · k = 5·10⁷ · 100 = 5·10⁹` | 十亿级 | 超时（本机 Java 约 20 秒以上，Go 约 8 秒） |
| 暴力 B（每个串排序） | `n · k log k = 10⁴ · 700 = 7·10⁶` | 千万级 | **能过**，本机 Java ≈ 25 ms，Go ≈ 18 ms |
| 最优（每个串计数） | `n · k = 10⁶` | 百万级 | 稳过，Java ≈ 8 ms，Go ≈ 6 ms |

> ⚠️ **注意一件反直觉的事**：暴力 B 其实**能过**这道题。所以面试里如果你只写出「排序当 key」，面试官不会说你错，但会追问一句「能不能不排序？」
> 这一问考的就是：**你是否意识到「排序」只是在为一件事服务 —— 造一个规范形（canonical form）**。造规范形不一定要排序。

### 第三步：卡点在哪

把问题翻译成一句话：

> **我要给每个字符串算一个「指纹」，使得「指纹相同」⟺「两个串互为字母异位词」。**

暴力 A 的卡点是**它在反复回答同一个问题**：`s` 跟第 3 组的代表元比过了、又跟第 5 组的代表元比，每次都要重新数一遍字母。而「`s` 的指纹」这个信息**只跟 `s` 自己有关**，算一次就够，却算了 `O(组数)` 次。

所以卡点不是「怎么判异位词」，而是：**这个指纹怎么造，才能既唯一、又能当哈希表的 key？**

### 第四步：灵感的来源 —— 「等价关系」需要「规范形」

关键观察是：

```
"eat"、"tea"、"ate" 互为异位词
        ↓
它们的字母多重集都是 {a:1, e:1, t:1}
        ↓
"多重集" 是一个「与顺序无关」的量
        ↓
只要把「多重集」编码成一个字符串，就能直接当 key
```

于是问题变成「多重集怎么编码」。两条路都成立：

1. **排序 → 规范形**：把字符排成升序，异位词必然排成同一个串。`eat / tea / ate → aet`。这是「**用排序构造规范形**」。
2. **计数 → 指纹**：26 个桶数一数，按字母表顺序拼成定长串。`eat / tea / ate → [1,0,0,0,1,...,1,...]`。这是「**用计数构造指纹**」。

排序 `O(k log k)`，计数 `O(k + σ)`。σ = 26 是常数，所以计数更快，而且**它不改变原串、不需要额外 `char[]` 拷贝**。

> 💡 这就是本章要建立的条件反射：**凡是「按某种等价关系分组」的题，第一步永远是问「这个等价类的规范形是什么」。**
> 有天然全序 → 排序；有固定小字母表 → 计数向量；两者都没有 → 才轮到「自定义哈希 + 冲突处理」。

## 036.3 原理拆解

### 036.3.1 数据结构与算法选型

| 方案（key 的设计） | 时间 | 空间 | 代码量 | 什么时候会输 |
| --- | --- | --- | --- | --- |
| 两两比较（暴力 A） | `O(n²·k)` | `O(n·k)` | 20 行 | n ≥ 10³ 就明显慢；面试里只是「起点」 |
| 排序串当 key | `O(n·k log k)` | `O(n·k)` | 8 行 | k 大到 10⁴ 时排序成本压过计数；且要拷贝 `char[]` |
| **26 位计数向量当 key** ✅ | **`O(n·k)`** | **`O(n·k)`** | **9 行** | 字母表很大（Unicode 全表）时定长数组会爆；需要按实际字符集选 σ |
| 质数乘积当 key | `O(n·k)` | `O(n)` | 6 行 | **溢出**：前 26 个质数之积约 `2.33·10³⁸`，需要 128 位整数；`long` / `int64` / `uint64` 全部溢出 → 溢出后取模会产生**假相等**（见下） |
| 字符和 / 字符积当 key | `O(n·k)` | `O(n)` | 4 行 | **不是单射**：`ac` 与 `bb` 的字符和都是 196，`abx` 与 `aip` 的字符积都是 1140720，直接误并，属于「伪哈希」 |
| 排序 + Trie | `O(n·k)` | `O(n·k·σ)` | 40 行 | 内存放大 σ 倍，本题纯属过度设计 |

**为什么「计数向量」优于「排序串」，哪怕两者都能过？**

1. **复杂度**：`O(k)` vs `O(k log k)`。k = 100 时是 100 次操作对 700 次操作，差 7 倍。
2. **不产生中间垃圾**：排序要 `s.toCharArray()` 拷一份再排；计数直接在原串上跑一遍。
3. **可解释性强**：计数向量的每一位含义明确（"字母 c 出现几次"），调试时打印出来一眼能看出问题；排序串 `aet` 则丢失了「这是指纹还是原串」的语义。

**为什么「质数乘积」是个漂亮的坏主意？**

思路是给 a..z 各分配一个质数，串的 key 就是所有字符对应质数的乘积。数学上它确实是单射（算术基本定理），**但工程上不成立**：

```
前 26 个质数之积 = 2·3·5·…·101 ≈ 2.33 × 10³⁸
int64 上限        = 9.22 × 10¹⁸
uint64 上限       = 1.84 × 10¹⁹
超出倍数          ≈ 2.5 × 10¹⁹ 倍
```

也就是说，只要串里字母一多，乘积就必然溢出。溢出后的值是原值模 `2⁶⁴`，这就把「单射」破坏成了「大概率单射 + 罕见碰撞」。而这类碰撞**不是随机的，是可以构造的**：不同的字母组合算出同一个模值，于是两组不相干的词被合并。

> **工程结论**：能用「定长计数向量」的时候，永远不要用「数学上单射但会溢出」的编码。
> 哈希表的 key 只需要「碰撞概率极低」，不需要「理论单射」—— 但**溢出会引入一个你无法分析的碰撞源**，这比 64 位哈希的随机碰撞危险得多。

### 036.3.2 为什么这个做法是对的（正确性论证）

记 `cnt(s)` 为长度 26 的计数向量，`cnt(s)[i]` = 字符 `'a'+i` 在 `s` 中出现的次数。

**命题 1（key 相等 ⟺ 互为异位词）**：`cnt(s) = cnt(t)` 当且仅当 `s` 与 `t` 互为字母异位词（允许 `|s| ≠ |t|` 时取「长度也必须相等」，见命题 2）。

**证明**：

- **（⟸）** 若 `s`、`t` 互为异位词，则按定义它们每个字母的出现次数都一样，于是逐位相等，`cnt(s) = cnt(t)`。
- **（⟹）** 若 `cnt(s) = cnt(t)`，则对每个字母 `c`，它在两个串中出现次数相同。把 `s` 按字母分组重排可得同一个「排序后的串」，把 `t` 同样重排也得到它 —— 两个串都可以通过交换字符变成同一个规范串，所以它们互为异位词。∎

**命题 2（长度被 key 隐含）**：`cnt(s) = cnt(t)` 蕴含 `|s| = |t|`，因为 `|s| = Σᵢ cnt(s)[i]`。

这条很重要：它说明**不需要额外把长度拼进 key**。有人写 `key = s.length() + "#" + counts`，多此一举（且多一次字符串拼接）。

**命题 3（算法输出正确）**：算法对每个串算 `key`，把串追加到 `buckets[key]`，最后返回所有桶。

1. **不漏**：每个串都恰好被处理一次，落在某个桶里，所以结果覆盖全部输入。
2. **不误并**：若 `s` 与 `t` 落在同一桶，则 `cnt(s) = cnt(t)`，由命题 1，它们确实互为异位词。桶内任意两个串都是异位词。
3. **不误拆**：若 `s` 与 `t` 互为异位词，由命题 1 它们的 key 相等，必然落进同一个桶。

三条合起来：**每个桶恰好是一个等价类**，输出合法。∎

> **这个论证的价值**：它把「算法正确」拆成了「key 是等价类的完全表征」这一个数学事实。
> 以后写任何分组题，都可以照这个模板证：先证 key 相等 ⟺ 同类，再证「全覆盖 + 不误并 + 不误拆」。三步写完，不需要再看代码。

### 036.3.3 通用解题思路（可迁移的那一层）

本题是 **「等价类分组 → 设计规范形 key」** 这个模型的母题。抽象出来是：

```
原始问题：把一堆对象按「某种等价关系」分组
         ↓ 追问 1：这个等价关系是什么？
         「存在一个双射/重排，把一个变到另一个」
         ↓ 追问 2：这个等价类的规范形（canonical form）是什么？
         能让「同类 ⟺ 规范形相同」的那唯一一个代表元
         ↓ 追问 3：规范形怎么编码成哈希 key？
         定长数组 / 排序串 / 计数向量 / 状态压缩后的整数
         ↓ 一次遍历：算 key → 塞桶
代价：O(n) 次 key 计算 + O(n) 空间
```

**「key 设计」的四条判据**（面试里可以直接背出来）：

| 判据 | 问法 | 反例 |
| --- | --- | --- |
| **完全性** | 同类对象的 key 一定相同吗？ | 用「首字母」当 key → 同类被拆散 |
| **唯一性** | key 相同的两个对象一定同类吗？ | 用「字符和」当 key → `ad` 与 `bc` 被误并 |
| **定长无歧义** | 拼接时会不会串味？ | 用 `"1"+"12"` 和 `"11"+"2"` 都得到 `"112"` → 必须加分隔符或定长 |
| **可计算性** | 算 key 的成本是否 ≤ 算法本身的复杂度？ | 用「两两排序后比较」当 key → key 计算就 `O(n²k log k)` |

归属同一模型的题：

| 题 | 等价关系 | 规范形 / key |
| --- | --- | --- |
| [LC 49 字母异位词分组](https://leetcode.cn/problems/group-anagrams/) | 字母多重集相同 | 26 位计数向量 |
| [LC 242 有效的字母异位词](https://leetcode.cn/problems/valid-anagram/) | 同上 | 同上，但只需比较两个串 |
| [LC 438 找到字符串中所有字母异位词](https://leetcode.cn/problems/find-all-anagrams-in-a-string/) | 定长窗口内的字母多重集 | 窗口计数向量（滑动更新） |
| [LC 249 移位字符串分组](https://leetcode.cn/problems/group-shifted-strings/) | 相邻字符差值序列相同 | 「差值序列」当 key（环上取模 26） |
| [LC 890 查找和替换模式](https://leetcode.cn/problems/find-and-replace-pattern/) | 字符间的双射结构相同 | 「首次出现位置序列」当 key |
| [LC 652 寻找重复的子树](https://leetcode.cn/problems/find-duplicate-subtrees/) | 子树结构相同 | 子树序列化串（后序 + 分隔符） |

**共同点**：都要求「先把对象压成一个可比较的指纹，再用哈希把指纹相同的归到一起」。指纹的设计质量，直接决定算法是 `O(n·k)` 还是 `O(n²·k)`。

### 036.3.4 可扩展性（面试追问的方向）

| 追问 | 变化 | 应对 |
| --- | --- | --- |
| 字符集扩到**全部 ASCII / Unicode** | σ 从 26 变成 128 / 65536 | 定长计数向量变成 `int[65536]`，每个 key 65 KB → 内存爆炸。改用「排序后的串」或「计数 + 只有非零项的稀疏编码」 |
| 要求**组内按字典序、组间按首元素排序** | 输出格式变了 | 桶内 `Collections.sort`、最后按 `list.get(0)` 排序；总复杂度仍是 `O(n·k log k)` |
| **数据流**输入（边来边分组） | 无法预知总组数 | 哈希天然适配：来一个算 key 塞桶；若要「组数上限」则需 LRU 淘汰 |
| 要求返回**每组的代表元 + 计数** | 输出结构变了 | value 从 `List<String>` 换成 `[代表元, 计数]`，key 逻辑不变 |
| 单词可以从**文件 / 外存**读，内存放不下 | 单机内存受限 | 外部哈希：先按 key 的哈希值把记录写到 B 个文件，再逐文件内存分组（MapReduce 的 shuffle 就是这个） |
| 要求**多线程**分组 | 并发写同一个 map | 分片：按 `key.hashCode() % P` 分给 P 个线程各建子 map，最后合并（避免全局锁） |

## 036.4 图解推演

### 036.4.1 执行轨迹：六个词如何落进三个桶

```
strs = ["eat","tea","tan","ate","nat","bat"]

                     ┌──────────────────────────────────────────┐
   算 key 的过程      │  key 是一根 26 格的「计数器」             │
                     │                                          │
   "eat"  →  a b c … e … n … t … z                          │
             [1 0 0 … 1 … 0 … 1 … 0]   ← 三个 1，其余 0        │
                     └──────────────────────────────────────────┘
                                    │
                                    ▼
┌────────┬──────────────────────┬─────────────────────────────┐
│ 单词   │ key（只画非零位）     │ 落桶后的状态                │
├────────┼──────────────────────┼─────────────────────────────┤
│ eat    │ a1 e1 t1             │ 桶A = [eat]                 │
│ tea    │ a1 e1 t1             │ 桶A = [eat, tea]            │
│ tan    │ a1 n1 t1             │ 桶B = [tan]                 │
│ ate    │ a1 e1 t1             │ 桶A = [eat, tea, ate]       │
│ nat    │ a1 n1 t1             │ 桶B = [tan, nat]            │
│ bat    │ a1 b1 t1             │ 桶C = [bat]                 │
└────────┴──────────────────────┴─────────────────────────────┘

最终：桶A = [eat, tea, ate]   桶B = [tan, nat]   桶C = [bat]
```

同一张图用「排序串」当 key 再走一遍，可以看到**桶的划分完全一样，只是 key 长得不同**：

```
eat → aet ┐
tea → aet ├─→ 同一个 key "aet"
ate → aet ┘

tan → ant ┐
nat → ant ┘─→ 同一个 key "ant"

bat → abt ──→ key "abt"
```

> **这张对比图就是本章的核心**：排序串和计数向量是**同一个等价类的两种编码**，不是两种算法。
> 真正决定算法的是「一个串只算一次 key、然后哈希定桶」这个结构；key 的编码方式只影响常数。

### 036.4.2 三种 key 的碰撞与溢出（为什么只有计数向量是安全的）

```
候选 key：字符和               候选 key：字符积                候选 key：计数向量
─────────────                  ─────────────                   ─────────────
ac → 97+99 = 196               abx → 97·98·120 = 1140720       ac → [1,0,1,0,0,…]
bb → 98+98 = 196               aip → 97·105·112 = 1140720      bb → [0,2,0,0,0,…]
     ▲ 相同！误并                    ▲ 相同！误并                    ▲ 不同（必然）
                                    │
                              质数乘积这一"正统"版本呢？
                              26 个质数之积 ≈ 2.33e38
                              int64 只到 9.22e18
                                    │
                                    ▼
                              ┌───────────────────────┐
                              │ 溢出 → 取模 2^64      │
                              │ 不同组合可能同余      │
                              │ → 无法分析的假相等    │
                              └───────────────────────┘
```

| key 编码 | 是否单射 | 是否会溢出 | 结论 |
| --- | --- | --- | --- |
| 字符和 | ❌（`ac` / `bb` 都是 196） | 否 | 直接淘汰 |
| 字符积 | ❌（`abx` / `aip` 都是 1140720） | 否 | 直接淘汰 |
| 质数乘积 | ✅（算术基本定理） | ✅ **必然溢出** | 数学漂亮、工程危险 |
| 排序串 | ✅ | 不适用 | 可用，`O(k log k)` |
| 26 位计数向量 | ✅ | 不适用（定长 26 字节） | **本题最优** |

## 036.5 双语言实现

### 036.5.1 Java

```java
import java.util.ArrayList;
import java.util.HashMap;
import java.util.List;
import java.util.Map;

class Solution {
    public List<List<String>> groupAnagrams(String[] strs) {
        // key   = 26 位计数向量压成的字符串（定长、无分隔符也不会串味）
        // value = 该等价类里的所有单词
        // 不变量：处理完 strs[0..i] 后，buckets 的每个 value 恰好是一个完整等价类的
        //         已见成员集合，且不同 key 之间没有异位词关系
        Map<String, List<String>> buckets = new HashMap<>(strs.length * 2);

        for (String s : strs) {
            char[] key = new char[26];              // 每个 char 存一个计数：0..100 远小于 2^16
            for (int i = 0; i < s.length(); i++) {
                key[s.charAt(i) - 'a']++;           // 只累加不排序 → 单串 O(k) 而不是 O(k log k)
            }
            // new String(char[]) 每次新建对象，不会被后续循环改写：
            // 这是本写法唯一的"隐藏成本"，但比排序的 char[] 拷贝 + 排序便宜得多
            String k = new String(key);
            buckets.computeIfAbsent(k, x -> new ArrayList<>()).add(s);
        }

        // 组间顺序不限，直接摊平即可；不要在这里排序，白花 O(m log m)
        return new ArrayList<>(buckets.values());
    }
}
```

### 036.5.2 Go

```go
package main

func groupAnagrams(strs []string) [][]string {
	// 与 Java 完全相同的结构：key = 26 位计数向量，value = 桶
	buckets := make(map[string][]string, len(strs))

	for _, s := range strs {
		// 注意 1：这里每轮新建 26 字节切片，而不是复用后手动清零。
		// 复用（配合 for 循环清 0）能省分配，但 Go 1.21 之前没有内置 clear，
		// 手动清零 26 次与新建 26 字节的成本接近，代码却更容易写错，故选择新建。
		key := make([]byte, 26)
		for i := 0; i < len(s); i++ {
			key[s[i]-'a']++ // s[i] 是 byte：本题限定小写字母，安全
		}
		// 注意 2：string(key) 在这里是一次"值拷贝"，之后改 key 不会影响已插入的 map key。
		// 这是 Go 里「切片转字符串当 map key」必须依赖的语言保证。
		k := string(key)
		buckets[k] = append(buckets[k], s)
	}

	res := make([][]string, 0, len(buckets))
	for _, group := range buckets {
		res = append(res, group)
	}
	return res
}
```

### 036.5.3 双语言差异批注

| 点 | Java | Go | 对本题的影响 |
| --- | --- | --- | --- |
| 计数的容器 | `char[26]`（值域 0..65535） | `[]byte`（值域 0..255） | 单串最长 100，两者都够；若 k 能到 1000，Go 必须换 `[]uint16` |
| 容器 → key | `new String(char[])` | `string([]byte)` | 两者都会**拷贝**，所以循环里复用同一块内存是安全的 |
| 字符串的字节语义 | `charAt` 返回 UTF-16 code unit | `s[i]` 返回 byte | 本题只有小写字母，两者一致；若含中文，Go 要 `[]rune`，Java 要 `codePointAt` |
| key 复用 | 可复用一个 `char[26]`，每轮 `Arrays.fill(key, '\0')` | 复用需手动清零（无 `clear` 内置） | 复用能少 n 次 26 字节分配，n = 10⁴ 时省约 260 KB，收益不大但面试可提 |
| map 初始容量 | `new HashMap<>(n*2)` 避免扩容 | `make(map[string][]string, n)` 预分配桶数组 | 都是「一次到位」，避免 rehash |
| 遍历 map 的顺序 | 无序（且 Java 8 起同一 map 内多次遍历顺序稳定，但不能依赖） | **每次遍历顺序随机**（故意的） | 两语言都必须接受「组间顺序任意」，对拍时要先规范化 |
| 空串 | `new String(new char[26])` 是全 `\0` 串，非 null | `string(make([]byte,26))`：同样得到 26 个 `\0` 字节 | 空串能正常当 key；不要用「key 为空表示无效」 |

### 036.5.4 对拍测试（换一种 key 编码，比较分组结果）

思路：用「排序串」当参考实现，因为它的正确性最直观；把两边的分组结果**规范化**（组内排序、组间按首元素排序）后比较。这样可以验证「计数向量」与「排序串」确实是同一个等价关系的两种编码。

```go
package main

import (
	"math/rand"
	"sort"
	"strings"
	"testing"
)

// 参考实现：排序串当 key
func groupBySort(strs []string) [][]string {
	m := map[string][]string{}
	for _, s := range strs {
		b := []byte(s)
		sort.Slice(b, func(i, j int) bool { return b[i] < b[j] })
		k := string(b)
		m[k] = append(m[k], s)
	}
	res := make([][]string, 0, len(m))
	for _, g := range m {
		res = append(res, g)
	}
	return res
}

// 规范化：组内排序 + 组间按首元素排序（因为题目允许任意顺序）
func normalize(groups [][]string) []string {
	out := make([]string, 0, len(groups))
	for _, g := range groups {
		cp := append([]string(nil), g...)
		sort.Strings(cp)
		out = append(out, strings.Join(cp, ","))
	}
	sort.Strings(out)
	return out
}

func equalGroups(a, b [][]string) bool {
	x, y := normalize(a), normalize(b)
	if len(x) != len(y) {
		return false
	}
	for i := range x {
		if x[i] != y[i] {
			return false
		}
	}
	return true
}

func TestGroupAnagramsRandom(t *testing.T) {
	r := rand.New(rand.NewSource(2024))
	for iter := 0; iter < 3000; iter++ {
		n := 1 + r.Intn(12)
		strs := make([]string, n)
		for i := range strs {
			// 字母表只取 a..d：重复度极高，异位词碰撞密集，最容易暴露 key 设计错误
			k := r.Intn(4)
			b := make([]byte, k)
			for j := range b {
				b[j] = byte('a' + r.Intn(4))
			}
			strs[i] = string(b)
		}
		got := groupAnagrams(strs)
		want := groupBySort(strs)
		if !equalGroups(got, want) {
			t.Fatalf("iter=%d strs=%v\ngot =%v\nwant=%v", iter, strs, got, want)
		}
	}
}

// 用具体输入钉住「伪哈希会误并」这件事：这两组串分别撞在"字符和"与"字符积"上
func TestPseudoHashCollides(t *testing.T) {
	if 'a'+'c' != 'b'+'b' {
		t.Fatalf("字符和碰撞示例失效：%d vs %d", 'a'+'c', 'b'+'b')
	}
	if 'a'*'b'*'x' != 'a'*'i'*'p' {
		t.Fatalf("字符积碰撞示例失效：%d vs %d", 'a'*'b'*'x', 'a'*'i'*'p')
	}
	// 正确实现必须把它们分到 4 个不同的组（同长不等于同多重集）
	if g := groupAnagrams([]string{"ac", "bb", "abx", "aip"}); len(g) != 4 {
		t.Fatalf("ac/bb/abx/aip 应各成一组，实际 %v", g)
	}
}
```

实测：`go test -run . -v` 全部通过；3000 组随机数据（含空串、单字符、全同字符）与参考实现分组完全一致。

> **为什么字母表只取 `a..d`**：字母越少，异位词越密集，`["aa","bb","ab","ba","aaa"]` 这类「同长度跨组」的输入出现得越频繁。
> 这正是「字符和 / 字符积当 key」和「忘记统计全部 26 位」两类 bug 的温床。

## 036.6 复杂度与常见坑

### 036.6.1 复杂度推导

- **时间 `O(n·k)`**，其中 `n = strs.length`、`k = 单串最大长度`：
  - 外层 n 次；每次内部两件事：① 扫一遍串算计数，`O(k)`；② `map` 的 `get/put`，key 长度固定 26，哈希与比较都是 `O(26) = O(1)`。
  - 合计 `Σᵢ O(|strs[i]|) + O(n·26) = O(n·k)`。
  - **注意不是 `O(n·k·26)`**：26 是常数，在渐进分析里被吸收；但如果字母表变成「全体 Unicode」，σ = 65536 就不能再当常数看待，此时是 `O(n·(k+σ))` —— 这也是「可扩展性」里第一条追问的由来。
- **空间 `O(n·k)`**：所有单词本身要存一份（`n·k` 字符），加上 key 共 `26n` 字节与桶结构。若不算输出，额外空间是 `O(n·σ)`（key 的存储），本题 `σ = 26`。

### 036.6.2 七个真实踩过的坑

1. **用「字符和」或「字符积」当 key** —— `ac` 与 `bb` 的字符和都是 196，`abx` 与 `aip` 的字符积都是 1140720，都会被误并成一组。这是最典型的「伪哈希」，代码看起来只有 3 行，坏得很隐蔽。
2. **用质数乘积当 key 却不处理溢出** —— 前 26 个质数之积约 `2.33·10³⁸`，`int64` / `uint64` 全部溢出；溢出后的取模会造出可构造的假相等。数学上单射 ≠ 工程上单射。
3. **计数数组用 `int[]` 却拼 key 时漏位** —— 只拼 0..25 中「非零」的项（例如只拼 `a1e1t1`），看似省空间，实际把 `a1b1` 和 `ab1`（不存在的写法）之外的情况都糊住了：`a1t1` 与 `a1t1` 之外还会出现 `a11t` 这种歧义拼接。**要么定长，要么每个数后面加分隔符。**
4. **Java 里用 `String.valueOf(char[])` 与 `new String(char[])` 混用** —— 前者对 `char[]` 其实也走 `String(char[])`，但若误写成 `Arrays.toString(key)` 就会得到 `"[1, 0, 0, ...]"` 这种带括号逗号的串：**能跑、能分组，但慢 3 倍且极易在别处出错**。
5. **在 hash key 里塞了「原始下标」** —— 比如 `key = counts + "#" + i`，于是每个串自成一桶。这类 bug 的典型症状是「输出组数 = 输入个数」。
6. **忘记空串**：`strs = [""]` 或 `["",""]`。空串的计数向量全是 0，只要不用「空 key 表示无效」，就能正确分到一组。
7. **对拍时直接比较两个 `[][]string`** —— 题目允许任意顺序，两边的顺序几乎必然不同，于是测试天天红。**判据必须先规范化**（组内排序 + 组间排序），这也是 §036.5.4 里 `normalize` 存在的原因。

### 036.6.3 面试官最爱追问的三个问题

**Q1：为什么不用「给每个字母分配质数，乘起来当 key」？数学上不是单射吗？**

> 「是单射，但工程上不成立。前 26 个质数之积约 `2.33·10³⁸`，需要 128 位；`int64` 上限 `9.22·10¹⁸`，`uint64` 也就 `1.84·10¹⁹`，差着约 `2.5·10¹⁹` 倍。一旦溢出就等价于对 `2⁶⁴` 取模，不同字母组合会撞到同一个余数，而且这种碰撞是可以被构造的，不像好的哈希函数那样只有随机碰撞。能用定长计数向量的时候，没理由引入一个无法分析的碰撞源。」

**Q2：如果字符集不是 26 个小写字母，而是任意 Unicode，怎么办？**

> 「定长计数向量就不能用了：`int[65536]` 每个 key 256 KB，`n = 10⁴` 直接 2.5 GB。三个替代方案：① **排序后的串当 key**，`O(k log k)`，内存只多一份串；② **稀疏计数编码**：把 `(字母, 次数)` 按字母序拼成 `"a1e1t1"`，key 长度与「不同字母数」成正比；③ 若字符集实际很小（比如只有 ASCII），就用 `int[128]`，`σ` 仍是常数。选择依据是「实际 σ」与「k」谁更小。」

**Q3：如果输入是数据流、总组数可能有上百万，内存怎么控？**

> 「两件事：① 单机内存不够就做**外部哈希**——先按 key 的哈希值把 `(key, 串)` 写到 B 个文件（这叫 shuffle），再逐个文件在内存里分组；这就是 MapReduce 里 group-by 的标准做法，复杂度仍是 `O(n·k)`，只是多一轮磁盘 IO。② 如果还要限制「同时驻留的组数」，就给桶加 LRU 淘汰，此时语义从「精确分组」退化成「近似分组」，必须先跟业务确认能不能接受。」

## 附：本章小结（可背走的三句话）

```
① 分组题的真正动作是"给等价类造规范形"，哈希只是把规范形当 key 的容器
② 小写字母表 → 26 位计数向量（O(k)，定长无歧义）；一般情况 → 排序串（O(k log k)）
③ key 必须"同类⟺相同"：字符和/积会误并（ac 与 bb、abx 与 aip），质数乘积会溢出（2.33e38 > 2^63）
```
