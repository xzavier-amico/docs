## 013.1 题目

**原题链接**：<https://leetcode.cn/problems/range-sum-query-immutable/>

### 题意重述（把隐含条件补齐）

实现一个类 `NumArray`：

- `NumArray(int[] nums)`：用数组 `nums` 初始化对象；
- `int sumRange(int left, int right)`：返回 `nums[left] + nums[left+1] + … + nums[right]`（**含两端**）。

它和前面几章最大的不同是：**这是一道「设计题」**，你要交付的不是「算一次」的函数，而是「能被反复调用很多次」的对象。这个差别决定了整套思路，见下表：

| 隐含条件 | 出处 | 违反了会怎样 |
| --- | --- | --- |
| **会调用 `sumRange` 很多次** | 「多次调用」是设计题的默认语义 | 每次调用都从头累加 → 总复杂度 O(n·q)，`q` 大时超时 |
| **数组不可变** | 题名里的 `Immutable` | 你想「边改边查」→ 题目明确不会改，不需要为动态做准备 |
| **闭区间 `[left, right]`** | 示例与签名 | 你按半开区间 `[left, right)` 处理 → 每个答案都少算 `nums[right]` |
| **`left <= right`，且都合法** | 约束 | 不需要处理 `left > right`；但自己写通用代码时应返回 0 |
| **可能有负数** | `-10⁴ <= nums[i]` | 不能用「前缀和单调」做任何假设（那是 019 才有的前提） |
| **要返回 `int`** | 签名 | 本题量级安全（见下表），但把 n 放大到 10⁵ 且元素 10⁴ 时就要 `long` |

### 约束与「量级反推」

| 约束 | 值 | 它对算法的含义 |
| --- | --- | --- |
| `1 <= nums.length <= 10⁴` | n 最多 1 万 | 单次暴力求和 O(n) = 10⁴ 次加法；若无预处理、查询 10⁴ 次，总 O(n·q) = **10⁸** 次，临界 |
| `-10⁴ <= nums[i] <= 10⁴` | 单元素绝对值 | 整段和最大 `10⁴ × 10⁴ = 10⁸`，`int32` 安全（上限 2.147·10⁹） |
| `-10⁴ <= left <= right <= nums.length - 1` | 区间合法 | **不需要**判空、判越界、判 `left > right` |
| `最多调用 10⁴ 次 sumRange` | q ≤ 10⁴ | **这是本题的题眼**：预处理 O(n) = 10⁴，查询 q·O(1) = 10⁴，总计 2·10⁴ ≪ 暴力的 10⁸ |

> 💡 量级 → 算法：设计题要算的是**总代价**，不是单次代价。
> `构造 + q 次查询` 的总代价：暴力 = `O(n·q)`；前缀和 = `O(n + q)`。
> 当 `q ≈ n` 时，前者是平方级、后者是线性级 —— 这就是「预处理」这个思想的价值所在。

### 示例

```
输入：
  ["NumArray", "sumRange", "sumRange", "sumRange"]
  [[[-2, 0, 3, -5, 2, -1]], [0, 2], [2, 5], [0, 5]]

输出：
  [null, 1, -1, -3]

解释：
  NumArray([-2,0,3,-5,2,-1])
  sumRange(0, 2) = -2 + 0 + 3 = 1
  sumRange(2, 5) = 3 + (-5) + 2 + (-1) = -1
  sumRange(0, 5) = -2 + 0 + 3 - 5 + 2 - 1 = -3
```

### 我自造的四个反例（写完必须打一遍）

```text
① sumRange(0, 0)        → 暴露"用 pre[i] 表示 nums[0..i] 之和"时的 l = 0 特判
② sumRange(0, n-1)      → 整段查询，暴露 pre 数组长度少开一位导致的越界
③ sumRange(i, i)        → 每次只查一个元素，是"含两端"语义的最小检验
④ 全负数数组            → 暴露"用 0 当哨兵就当作没命中"之类的写法；前缀和可以是负数
```

第 ① 条是这道题唯一真正的难点：**`pre` 的下标和 `nums` 的下标错位一格**。错位本身不是问题，忘记错位才是。

## 013.2 从暴力到最优：第一个念头为什么错

### 第一步：暴力（先写出来）

```java
class NumArray {
    private int[] a;
    public NumArray(int[] nums) { a = nums; }
    public int sumRange(int left, int right) {
        int s = 0;
        for (int i = left; i <= right; i++) s += a[i];
        return s;
    }
}
```

- 构造 **O(1)**，单次查询 **O(right − left + 1)**，最坏 **O(n)**。
- `q` 次查询总代价 **O(n·q)**：`n = q = 10⁴` 时是 **10⁸ 次加法** —— 恰好卡在超时边缘。

### 第二步：它为什么不够

问题不在「求和」，在**每次查询都在重算同一批前缀**：

```
q 次查询，每次都从 left 加到 right：

  查询 1: [0, 5000]      加 5001 次
  查询 2: [1, 5000]      加 5000 次  ← 和查询 1 重叠了 5000 次加法
  查询 3: [2, 5000]      加 4999 次  ← 又重叠了 4999 次
  ...
```

**重叠的部分被反复计算。** 而「`nums[0..k]` 的和」这个量只依赖于 `k`，与查询无关——它完全可以只算一次。

换个说法：暴力把「区间和」看成了一个**需要现场加工**的东西；而区间和其实可以**分解成两个预先算好的量之差**：

```
sum(nums[left..right]) = sum(nums[0..right]) − sum(nums[0..left-1])
                         └── 只依赖 right ──┘   └── 只依赖 left ──┘
```

一旦这么写，每次查询就只剩**一次减法**。

### 第三步：卡点与灵感

卡点只有一个：**`left = 0` 时 `left-1 = -1` 会越界**。

这里有个非常经典的处理：**把「前缀和」的下标整体右移一格，在头部放一个 0**。

```
定义：pre[0] = 0
      pre[i] = nums[0] + nums[1] + … + nums[i-1]     （i = 1..n）

于是：sum(nums[left..right]) = pre[right+1] − pre[left]
```

`left = 0` 时是 `pre[right+1] - pre[0] = pre[right+1] - 0`，**天然正确，不需要任何特判**。

> 这个「头部放 0」的操作不是小聪明，它是**哨兵（sentinel）思想**：用一个人造的、语义上合法的元素，把边界情况吸收进通用公式。`011` 里的 `cnt{0: 1}` 是同一个东西 —— 那里是「空前缀」，这里是「空前缀的和 = 0」。**同一个哨兵，两个名字。**

### 第四步：这就是「前缀和」从技巧变成数据结构的一刻

`011` 里前缀和是「一遍扫描时的中间量」；到了 `013`，它被**物化成对象的一个字段**：

```
                     ┌──────────────────────────────┐
   构造时算一次      │  NumArray { int[] pre }       │
   O(n)              │  pre[0..n]，长度 n+1         │
                     └──────────────┬───────────────┘
                                    │ q 次查询，每次 O(1)
                                    ↓
                     sumRange(l, r) = pre[r+1] - pre[l]
```

这就是「空间换时间」最干净的样子：用 `n+1` 个 `int`，把 `q` 次 O(n) 换成 `q` 次 O(1)。

## 013.3 原理拆解

### 013.3.1 数据结构与算法选型

| 方案 | 构造 | 单次查询 | q 次总代价 | 代码量 | 什么时候会输 |
| --- | --- | --- | --- | --- | --- |
| 每次现场累加 | O(1) | O(n) | O(n·q) | 6 行 | q 大时超时；`n = q = 10⁴` 已到 10⁸ |
| 存二维前缀（所有 `[i,j]` 的和） | O(n²) | O(1) | O(n² + q) | 15 行 | 空间 O(n²) = 10⁸ 个 int（400 MB），**内存直接爆** |
| **一维前缀和** ✅ | **O(n)** | **O(1)** | **O(n + q)** | **5 行** | 数组**可变**时失效（那要 307 的树状数组 / 线段树） |
| 分块（sqrt 分块） | O(n) | O(√n) | O(n + q√n) | 30 行 | 本题不需要；但**数组可变**时它是「代码短 + 够快」的折中 |
| 树状数组 / 线段树 | O(n) | O(log n) | O(n + q log n) | 30~60 行 | 静态数组用它属于过度设计（但面试官可能追问） |

**为什么「存二维前缀」是最糟的中间态**：它把查询降到 O(1)，却付出了 O(n²) 的空间和 O(n²) 的构造时间。**为了省一次减法，付出了 n 倍的代价。**

### 013.3.2 为什么这个做法是对的（正确性论证）

**命题**：对任意 `0 <= left <= right <= n-1`，`pre[right+1] - pre[left] = Σ_{i=left}^{right} nums[i]`。

**证明**（直接展开）：

```
pre[right+1] = nums[0] + nums[1] + … + nums[left-1] + nums[left] + … + nums[right]
             └─────────────── 这一段是 pre[left] ───────────────┘└─ 目标区间 ─┘

两式相减：
pre[right+1] - pre[left]
  = ( nums[0] + … + nums[left-1] + nums[left] + … + nums[right] )
  - ( nums[0] + … + nums[left-1] )
  = nums[left] + … + nums[right]                              ∎
```

这个证明有一个**必须成立的前提**：`pre[left]` 里的项**必须完整地出现在** `pre[right+1]` 里。因为两者都是同一个数组的前缀，这个前提自动成立（`left <= right+1`）。**如果某天你处理的是「二维前缀」或「环形数组」，这个前提就会破**，那正是 304 和「环形子数组」类题目的难点。

**同时说明「含两端」为什么对应 `right+1`**：`pre` 的第 `k` 项覆盖 `nums[0..k-1]`，所以要让 `nums[right]` 被包含，必须取到 `pre[right+1]`。**差一位就是少一个元素**，这也是本题唯一的下标陷阱。

### 013.3.3 通用解题思路（可迁移的那一层）

本题是 **「静态区间查询 → 前缀和」** 模型的母题。它的可迁移形式：

```
问题：q 次询问「区间 [l, r] 的聚合值」
     ↓ 判断聚合运算是否"可撤销"（有逆运算）
可撤销（加法、异或）→ 前缀量 + 一次减法，O(1) 查询
     ↓ 判断数组是否可变
不可变 → 预处理一次，查询 O(1)      ← 本题（303）
可变   → 树状数组（单点改 + 区间查）或线段树（区间改 + 区间查）
     ↓ 判断是否"只有区间加、最后才问"
差分 → 见 014
```

**本批（011–019）里三种「前缀类」结构的对照**，这是本书第 2 部分最重要的一张表：

| 结构 | 预处理 | 单次操作 | 适合的访问模式 | 章节 |
| --- | --- | --- | --- | --- |
| 前缀和数组 | O(n) | 查询 O(1) | **读多写零**（不可变） | 013 |
| 前缀和 + 哈希 | O(1) 摊销 | 查询 O(1) | 一遍流式扫描，边扫边问 | 011 |
| 差分数组 | O(n) 空间 | 区间修改 O(1) | **写多读少**，最后一次性还原 | 014 |

三者是同一个「前缀」概念的三种用法：**前缀和是「查询端」，差分是「更新端」，而哈希版前缀和是「流式端」。**

### 013.3.4 可扩展性（面试追问的六个方向）

| 追问 | 变化 | 应对 |
| --- | --- | --- |
| **数组可变**（单点修改 + 区间查询） | 前缀和失效（改一个点要更新 O(n) 个前缀） | **树状数组**（Fenwick，单点改 / 区间查都是 O(log n)）或线段树 → LC 307 |
| **二维矩阵**的区间和 | 需要容斥 | 二维前缀和：`pre[i][j] = pre[i-1][j] + pre[i][j-1] - pre[i-1][j-1] + a[i-1][j-1]`；查询四个角加减 → LC 304 |
| **区间加 + 区间和** | 两边都要 | 差分 + 树状数组，或线段树（带 lazy 标记） |
| 只做**区间加**，最后才问每个位置 | 差分的主场 | 见 `014` |
| 内存受限（`pre` 都开不下） | n 极大 | 分块：只存每块的和，查询时整块 O(1) + 边界 O(块大小)；空间 O(n/B) |
| q 极大且查询有规律 | 常数优化 | 把 `pre` 换成 `long[]` 反而更慢（缓存行装得少）；保持 `int[]` 的**缓存友好**更重要 |
| 要求返回区间和的**下标**而不只是值 | 语义变化 | 前缀和无法直接回答「哪一段」，需要额外结构（如「和为 k 的最长子数组」LC 325 用哈希存首次下标） |

## 013.4 图解推演

### 013.4.1 `pre` 与 `nums` 的错位对齐（本题唯一的下标陷阱）

```
nums 下标    0     1     2     3     4     5
nums       ┌─────┬─────┬─────┬─────┬─────┬─────┐
           │ -2  │  0  │  3  │ -5  │  2  │ -1  │
           └─────┴─────┴─────┴─────┴─────┴─────┘

pre  下标    0     1     2     3     4     5     6
pre        ┌─────┬─────┬─────┬─────┬─────┬─────┬─────┐
           │  0  │ -2  │ -2  │  1  │ -4  │ -2  │ -3  │
           └─────┴─────┴─────┴─────┴─────┴─────┴─────┘
             ↑     ↑
             │     └── pre[1] = nums[0]
             └──────── pre[0] = 0（哨兵：空前缀的和）

             pre[k] 覆盖的是 nums[0 .. k-1]，共 k 个元素
             所以 pre 长度 = n + 1，最后一项是 pre[n] = 全数组和
```

### 013.4.2 一次查询的取数位置

```
要求 sumRange(2, 5)，即 nums[2..5] = 3 + (-5) + 2 + (-1) = -1

           pre[left]              pre[right+1]
              │                       │
              ↓                       ↓
     ┌─────┬─────┬─────┬─────┬─────┬─────┬─────┐
pre  │  0  │ -2  │ -2  │  1  │ -4  │ -2  │ -3  │
     └─────┴─────┴─────┴─────┴─────┴─────┴─────┴─────┘
        0     1     2     3     4     5     6
                    └─────────────────────┘
                       被减掉的部分        相减的结果

     pre[6] - pre[2] = (-3) - (-2) = -1      ✅

         ↑ left = 2 → 取 pre[2]
                        ↑ right = 5 → 取 pre[6] = pre[right+1]
```

### 013.4.3 边界用例 `left = 0`

```
sumRange(0, 2) = pre[3] - pre[0] = 1 - 0 = 1     ✅ 无需特判

   如果 pre 的定义改成"pre[i] = nums[0..i] 之和"（含自身），长度只有 n：
   sumRange(0, 2) = pre[2] - ?   ← left = 0 时没有"前一项"可减 → 必须写 if (left == 0)

   ┌───────────────────── 两种定义的分岔 ─────────────────────┐
   │ pre[i] = nums[0..i-1]（长度 n+1）  → 公式统一，无特判  ✅ │
   │ pre[i] = nums[0..i]  （长度 n）    → l=0 特判，易漏     ❌ │
   └──────────────────────────────────────────────────────────┘
```

### 013.4.4 查询代价对比（q 次查询的总加法/减法次数）

| 查询次数 q | 暴力总代价（加法次数，上界） | 前缀和总代价（构造 + 查询） | 倍数关系 |
| --- | --- | --- | --- |
| 10 | 10 × 10⁴ = 10⁵ | 10⁴ + 10 = 10⁴ | 约 10 倍 |
| 10³ | 10⁷ | 10⁴ + 10³ ≈ 1.1·10⁴ | 约 900 倍 |
| 10⁴（本题上限） | **10⁸** | **≈ 2·10⁴** | **约 5000 倍** |

> 这张表说明的是**渐进关系**（O(n·q) vs O(n+q)），不是实测耗时；倍数按「最坏区间长度」估算，是数量的比较而非性能测量。

## 013.5 双语言实现

### 013.5.1 Java

```java
class NumArray {
    // pre 长度是 n+1：pre[0] = 0 是哨兵，pre[k] = nums[0..k-1] 的和
    // 用 final 强调"构造后不再变"——这题的前提就是不可变
    private final int[] pre;

    public NumArray(int[] nums) {
        pre = new int[nums.length + 1];
        for (int i = 0; i < nums.length; i++) {
            // 前缀和的标准递推：pre[i+1] = pre[i] + nums[i]
            // 注意这里写的是 pre[i+1] 和 nums[i]，错位一格是刻意的
            pre[i + 1] = pre[i] + nums[i];
        }
    }

    public int sumRange(int left, int right) {
        // 含两端 [left, right] → 减 pre[left]、取 pre[right+1]
        // left = 0 时 pre[0] = 0，公式天然成立，不需要 if
        return pre[right + 1] - pre[left];
    }
}
```

### 013.5.2 Go

```go
package main

type NumArray struct {
	// pre 长度 n+1，pre[0] = 0 是哨兵
	pre []int
}

func Constructor(nums []int) NumArray {
	pre := make([]int, len(nums)+1)
	for i, x := range nums {
		pre[i+1] = pre[i] + x // 错位一格：pre 比 nums 多一个前导 0
	}
	return NumArray{pre: pre}
}

// SumRange 用指针接收者：LeetCode 的 Go 模板就是 *NumArray，
// 而且指针接收者避免每次调用都复制整个 struct（虽然这里只有一个 slice 头）
func (this *NumArray) SumRange(left int, right int) int {
	return this.pre[right+1] - this.pre[left]
}
```

### 013.5.3 双语言差异批注

| 点 | Java | Go | 对本题的影响 |
| --- | --- | --- | --- |
| 「类」的写法 | `class NumArray` + 构造函数 | `type NumArray struct` + `Constructor` 函数 | Go 没有构造函数语法，靠**约定名** `Constructor` 让 LeetCode 识别 |
| 字段可见性 | `private final int[] pre` | 首字母小写 `pre`（包内可见） | Go 没有 `final`，「不可变」只能靠约定与注释表达 |
| 方法接收者 | 隐式 `this` | 显式 `(this *NumArray)` | 值接收者会复制 struct；`pre` 是 slice 头（24 字节），复制不致命但没必要 |
| 数组默认值 | `new int[n]` 全 0 | `make([]int, n)` 全 0 | 本题恰好**依赖** 0：`pre[0] = 0` 不用显式赋值。但别把「零值可用」当成习惯，`012` 的 `ans[0]` 就必须显式设 1 |
| 越界检查 | `ArrayIndexOutOfBoundsException`（运行时） | panic（运行时） | 两者都不会在编译期帮你发现「`pre` 少开一位」，必须靠 `right = n-1` 的用例压测 |
| 整数宽度 | `int` 恒 32 位 | `int` 在 64 位平台 64 位 | `10⁸` 的区间和在两语言都安全；若 n 与元素同时放大，Java 必须换 `long` |

```go
	"testing"
)

func TestNumArrayRandom(t *testing.T) {
	// 固定用例：包含 l = 0、l == r、整段查询、全负数
	na := Constructor([]int{-2, 0, 3, -5, 2, -1})
	fixed := []struct{ l, r, want int }{
		{0, 2, 1}, {2, 5, -1}, {0, 5, -3}, {1, 1, 0}, {0, 0, -2}, {5, 5, -1},
	}
	for _, f := range fixed {
		if got := na.SumRange(f.l, f.r); got != f.want {
			t.Fatalf("SumRange(%d,%d)=%d want %d", f.l, f.r, got, f.want)
		}
	}

	r := rand.New(rand.NewSource(13))
	for iter := 0; iter < 5000; iter++ {
		n := 1 + r.Intn(20)
		a := make([]int, n)
		for i := range a {
			a[i] = r.Intn(201) - 100 // 值域 [-100,100]，正负都有
		}
		na := Constructor(a)
		for q := 0; q < 10; q++ {
			l := r.Intn(n)
			rr := l + r.Intn(n-l) // 保证 l <= rr 且都在界内
			want := 0
			for k := l; k <= rr; k++ {
				want += a[k]
			}
			if got := na.SumRange(l, rr); got != want {
				t.Fatalf("a=%v l=%d r=%d got=%d want=%d", a, l, rr, got, want)
			}
		}
	}
}
```

> **为什么必须包含 `{0, 0}` 和 `{0, n-1}`**：前者测「`left = 0` 时不需要特判」，后者测「`right = n-1` 时 `pre` 有没有多开一位」。这两个位置正好是 `pre` 长度和定义最容易写错的两端。

## 013.6 复杂度与常见坑

### 013.6.1 复杂度推导

- **构造 O(n)**：恰好 `n` 次加法 + `n+1` 次写入（含 `pre[0] = 0`）。
- **单次查询 O(1)**：一次减法、两次数组随机访问。
- **q 次查询总代价 O(n + q)**：预处理只做一次，查询之间互不影响、无状态。
- **空间 O(n)**：`n+1` 个 `int`。这是**唯一的**额外空间，且是刻意付出的 —— 它就是「用空间换查询时间」的那笔钱。

### 013.6.2 七个真实踩过的坑

1. **`pre` 少开一位** —— `new int[n]` 而不是 `new int[n+1]`，`right = n-1` 时 `pre[n]` 越界。这是本题最高频的错误。
2. **定义与公式不匹配** —— 一边用 `pre[i] = nums[0..i]`（含自身），一边写 `pre[right+1] - pre[left]`，等于每个答案多算 `nums[right]`。选一种定义，然后让公式严格服从它。
3. **`left = 0` 特判写错** —— 用「含自身」定义时忘了 `if (left == 0) return pre[right];`，`sumRange(0, k)` 全部报错。
4. **把闭区间当半开区间** —— 返回 `pre[right] - pre[left]`，少算最后一个元素。示例里 `sumRange(2,5)` 会得到 0 而不是 −1。
5. **溢出** —— 本题 `10⁸` 安全；但如果元素上限提到 `10⁵` 且 n 到 `10⁵`，区间和到 `10¹⁰`，Java 的 `int` 静默溢出。**前缀和题永远先算一遍「最大值 × 项数」**。
6. **以为「不可变」意味着可以随便缓存** —— 题目保证不改，但你的类不应该在 `sumRange` 里修改任何字段；一旦加了缓存，多线程调用会出问题（LeetCode 单线程测不出来）。
7. **Go 用值接收者 + 返回 `NumArray` 值** —— 本身能跑，但 `Constructor` 返回值和 LeetCode 模板（`*NumArray`）不一致会编译失败；照抄模板最稳。

### 013.6.3 面试官最爱追问的三个问题

**Q1：如果数组可以被修改呢？**
> 「前缀和立刻失效：改一个 `nums[i]` 会波及 `pre[i+1..n]` 共 O(n) 项，退化成 O(n) 更新。这时要用**树状数组**（Fenwick）：单点改 O(log n)、前缀和查询 O(log n)，代码 20 行左右；或者**线段树**，能支持区间改 + 区间查，代价是代码 60 行。选择依据是操作类型：只单点改 → 树状数组；有区间改 → 线段树（带 lazy）。这就是 LC 307。」

**Q2：二维矩阵怎么做？**
> 「二维前缀和 + 容斥。`pre[i][j]` 表示左上角 `(0,0)` 到 `(i-1,j-1)` 的矩形和，递推是 `pre[i][j] = pre[i-1][j] + pre[i][j-1] - pre[i-1][j-1] + a[i-1][j-1]`；查询矩形 `(r1,c1)-(r2,c2)` 是四个角的两加两减。构造 O(mn)、查询 O(1)。减掉的那一项 `pre[i-1][j-1]` 就是容斥里被加了两次的部分 —— 和 `013` 一维时『减掉左边那段』是同一个思想。」

**Q3：`q` 次查询里如果有一半是「把某个区间整体加 v」呢？**
> 「那就是混合操作：单点/区间改 + 区间查。两条路：① 用两个树状数组维护差分（区间加 + 区间和，O(log n)）；② 直接上带 lazy 的线段树。而如果所有修改都发生在查询之前（离线），用**差分数组**一次 O(n+m) 就能还原全部答案 —— 这正是下一章 014 的场景。」
