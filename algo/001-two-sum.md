## 001.1 题目

**原题链接**：<https://leetcode.cn/problems/two-sum/>

### 题意重述（把隐含条件补齐）

给你一个整数数组 `nums` 和一个整数 `target`，请你在数组中找出**两个不同的元素**，使它们的和等于 `target`，返回这两个元素的**下标**（顺序不限）。

看起来一句话就完了，但它藏了四个必须读出来的约束：

| 隐含条件 | 出处 | 违反了会怎样 |
| --- | --- | --- |
| **同一个元素不能用两次** | 「两个不同的元素」 | `[3,3], target=6` 你返回 `[0,0]` → 错 |
| **保证恰好有且只有一个答案** | 「你可以假设每种输入只会对应一个答案」 | 所以可以「找到就立刻 return」，不需要收集所有解 |
| **返回下标，不是返回值** | 「返回这两个数的下标」 | 返回 `[2,7]` 而不是 `[0,1]` → 错 |
| **下标顺序不限** | 「你可以按任意顺序返回答案」 | 不必排序结果，省掉一次无谓操作 |

### 约束与「量级反推」

| 约束 | 值 | 它对算法的含义 |
| --- | --- | --- |
| `2 <= nums.length <= 10^4` | n 最多 1 万 | **O(n²) = n²/2 ≈ 5·10⁷ 次配对**，本机实测 Java ≈ 12 ms、Go ≈ 23 ms（2 核容器），「能过但不优」；**O(n)** 才是这题想考的 |
| `-10^9 <= nums[i] <= 10^9` | 有负数 | 不能假设「只处理正数」，也不能用值当下标 |
| `-10^9 <= target <= 10^9` | 差值可能越界 | `target - nums[i]` 最小到 `-2·10⁹`，超出 int32 正区间但**未跌破 int32 下界**（`-2.147·10⁹`），Java `int` 仍安全；但如果约束放大到 `10^9+` 就必须换 `long` |
| 只有**一个**答案 | n 最多 1e4 但答案唯一 | 允许「提前结束」，这是 O(n) 能成立的前提之一 |

> 💡 **量级 → 算法** 是本书第一章就要建立的条件反射：
> `n ≤ 20` → 状压/暴力枚举；`n ≤ 2·10³` → O(n²)；`n ≤ 2·10⁵` → O(n log n)；`n ≤ 10⁷` → O(n)；`n ≤ 10¹⁸` → O(log n) 或数学公式。
> **看到 `10^4`，先想「O(n) 或 O(n log n) 才行，O(n²) 需要解释」。**

### 示例

```
输入：nums = [2, 7, 11, 15], target = 9
输出：[0, 1]
解释：nums[0] + nums[1] = 2 + 7 = 9

输入：nums = [3, 2, 4], target = 6
输出：[1, 2]         ← 注意：不是 [0, 1]（3+3 用了两次同一个元素）

输入：nums = [3, 3], target = 6
输出：[0, 1]         ← 唯一一个"必须允许重复值"的样例
```

### 我自造的三个反例（写完解法必须拿它们打一遍）

```text
① [3,3], 6            → 暴露「先存后查」会让同一个元素匹配自己
② [0,4,3,0], 0        → 暴露「用 0 当哨兵」的错误（真实下标就是 0）
③ [-1,-2,-3,-4,-5], -8 → 暴露「只处理正数」或「map 里存 0 表示不存在」的写法
```

第 ② 条是最经典的坑：很多人写 `if j := seen[need]; j != 0 { ... }`，而正确答案恰好是 `[0, 3]` —— 下标 0 被当成了「没找到」。

## 001.2 从暴力到最优：第一个念头为什么错

### 第一步：暴力（先写出来，别急着优化）

```java
// 暴力：枚举所有 (i, j), i < j
for (int i = 0; i < n; i++)
    for (int j = i + 1; j < n; j++)
        if (nums[i] + nums[j] == target) return new int[]{i, j};
```

- 时间 **O(n²)**，空间 **O(1)**。
- 在 `n = 10^4` 时是 **`n(n-1)/2 ≈ 5·10⁷` 次**比较与加法。本机实测（2 核容器 / JDK 17 / Go 1.19）：**Java ≈ 12 ms，Go ≈ 23 ms** —— **能过**。
- 但把它想成一条斜线：`n` 翻 10 倍，时间翻 100 倍。`n = 10^5` 就是 **≈ 1.2 s**，直接 TLE；`n = 10^6` 是 2 分钟。**面试给的是 `10^4`，考的是你知不知道它是 `10^5` 的失败解。**

那为什么还要优化？两个理由，都必须在面试里说出来：

1. **约束会变**。同一道题改成「`n ≤ 10^5`」或者「查询 `q` 次」，O(n²) 立刻死。
2. **暴力在做重复劳动**。当外层固定 `i` 时，你要找的是「数组里有没有 `target - nums[i]`」——这是一个**查找**，不是一次枚举。查找有 O(1) 的做法。

### 第二步：卡点在哪

把问题翻译成一句话：

> **对每个 `x = nums[i]`，问「`target - x` 在不在这堆数里、下标是多少」。**

暴力把「在不在这堆数里」也当成了 O(n) 的线性扫描。**卡点不是「两两配对」，而是「查找被做成了线性」。**

一旦识别出「查找」，解法就只剩一个方向：**换一个查找结构**。而数组上能 O(1) 查找的结构，就是哈希表。

### 第三步：灵感的来源 —— 「边遍历边登记」

这里有个很容易被忽略的细节：为什么能**一遍**遍历就够？

因为答案是一对数 `(i, j)`，假设 `i < j`。当我们遍历到 `j` 时，`i` 必然**已经被遍历过了**。所以只要在遍历过程中，把「见过的数 → 下标」存下来，到 `j` 时一定能查到 `i`。

```
不变量：进入第 i 轮循环前，seen 中恰好是 nums[0..i-1] 的全部元素
```

这个不变量是 O(n) 正确性的全部依据 —— 后面 §001.3.2 会用它做严格论证。

### 另一条路：排序 + 双指针（顺便说清它为什么在这题里「输了」）

如果先把数组排序，就能用「对撞双指针」在 O(n) 里找到那对数（见 `002-two-sum-ii-input-array-is-sorted.md`）：

```
l = 0, r = n-1
while l < r:
    s = a[l] + a[r]
    if s == target: 找到
    elif s < target: l++      # 和太小，只能加大的 → 左指针右移
    else: r--                 # 和太大，只能减小 → 右指针左移
```

总复杂度 O(n log n)（排序主导），空间 O(1) 或 O(n)（取决于是否复制数组）。

**它在这题里输在哪？** 题目要的是**原下标**，排序会把下标打乱。你要么额外保存 `(值, 原下标)` 对（空间 O(n)，且排序后还要回填），要么排序完再线性找原下标（遇到重复值会歧义）。代码复杂度反而比哈希高。

> ⚠️ 这正是「算法没有优劣，只有**匹配约束**」的最好例子：**同一道题、同一组输入，要下标就哈希，不要下标就双指针。** 167、15、18 都是「不要下标 / 可以排序」的版本，所以它们用双指针。

## 001.3 原理拆解

### 001.3.1 数据结构与算法选型

| 方案 | 时间 | 空间 | 代码量 | 什么时候会输 |
| --- | --- | --- | --- | --- |
| 暴力枚举 | O(n²) | O(1) | 5 行 | n ≥ 10⁵；需要多次查询 |
| 排序 + 双指针 | O(n log n) | O(1)~O(n) | 15 行 | **需要原下标**（本题）；重复值定位歧义 |
| 哈希（两遍） | O(n) | O(n) | 10 行 | 需要先建完整表；本题多一次遍历但无收益 |
| **哈希（一遍）** ✅ | **O(n)** | **O(n)** | **8 行** | 值域极大且内存受限（要外部排序） |

**为什么「一遍哈希」优于「两遍哈希」**：

- 两遍：先 `for x in nums: map[x] = i`，再 `for x in nums: if (target-x) in map`。要额外处理「`target - x == x` 且表中只有自己」的情况，必须判 `map[target-x] != i`。
- 一遍：**天然不会匹配到自己**，因为查表发生在「把自己放进表」之前。少一个分支，少一处 bug。

### 001.3.2 为什么这个做法是对的（正确性论证）

**命题**：若存在唯一解 `(i, j)`（`i ≠ j`），算法返回 `(i, j)`。

**证明**（用 §001.2 的不变量）：

设 `i < j`（否则交换，答案无序）。考虑循环执行到 `k = j` 的那一轮。

1. 由不变量，此时 `seen` 中包含 `nums[0..j-1]` 全部元素，因此 `nums[i]` 已在 `seen` 中，且 `seen[nums[i]] = i`。
2. 这一轮计算 `need = target - nums[j] = nums[i]`。
3. `seen.get(need)` 命中，返回 `(i, j)`。∎

**再证「不会返回错误答案」**：若返回 `(j', i)`，说明 `seen[nums[i]] = j'`，即 `nums[j'] = nums[i]` 且 `j' < i`，于是 `nums[j'] + nums[i] = 2·nums[i]`，必须等于 `target` —— 它确实是一组**合法解**。题目保证解唯一，所以它就是那个解。∎

> **这个论证的价值**：它同时说明了「为什么要先查后存」和「为什么重复值 `[3,3]` 能正确返回 `[0,1]`」—— 两个最容易写错的点，被一个不变量同时管住了。

### 001.3.3 通用解题思路（可迁移的那一层）

本题是 **「查找型问题 → 空间换时间」** 这个模型的母题：

```
原始问题：在序列里找满足 f(a, b) = C 的一对 (a, b)
         ↓ 固定一端
降维成：  对每个 a，找 b 使 b = g(a, C)
         ↓ 识别为查找
优化：    用哈希把「线性查找」变成「O(1) 查找」
         ↓ 一遍遍历同时完成「查询」与「登记」
代价：    O(n) 额外空间
```

属于同一模型的题：

| 题 | 被查找的东西 | 哈希 key 设计 |
| --- | --- | --- |
| [LC 1 两数之和](https://leetcode.cn/problems/two-sum/) | `target - x` | 数值 → 下标 |
| [LC 454 四数相加 II](https://leetcode.cn/problems/4sum-ii/) | 两两和的相反数 | 两数组和的计数 |
| [LC 560 和为 K 的子数组](https://leetcode.cn/problems/subarray-sum-equals-k/) | 前缀和之差 | 前缀和 → 出现次数 |
| [LC 128 最长连续序列](https://leetcode.cn/problems/longest-consecutive-sequence/) | `x+1` 是否存在 | 值 → 是否存在 |
| [LC 349 两个数组的交集](https://leetcode.cn/problems/intersection-of-two-arrays/) | 是否出现过 | 值 → 布尔 |

**共同点**：都是「把『找』这件事从 O(n) 降到 O(1)」，代价都是 O(n) 空间。

### 001.3.4 可扩展性（面试追问的六个方向）

| 追问 | 变化 | 应对 |
| --- | --- | --- |
| 数组**已经有序** | 不需要哈希 | 对撞双指针，O(1) 空间 → 见 `002` |
| 要找出**所有**数对 | 不能提前 return | 哈希存「值 → 下标列表」，或排序双指针收集所有；注意**去重** |
| 元素**不能重复使用** | 已有约束 | `i < j` 或「先查后存」 |
| 允许**同一个元素用两次** | 语义变了 | 查的时候包含自己：先把全部放入表再查 |
| **数据流**输入（边来边问） | 只有一个方向 | 哈希天然适配：来一个查一个存一个 |
| **内存受限**（放不下 10⁹ 个不同值） | 哈希爆内存 | 外部排序 + 双指针；或分桶后分治（值域二分） |

**进阶延伸（自己写代码验证）**：

- **LC 170 两数之和 III - 数据结构设计**（会员题）：`add` 与 `find` 交替调用 —— 体会「哈希 vs 有序数组」在动态场景下的取舍。
- **LC 653 两数之和 IV - 输入 BST**：把「数组」换成「树」，遍历顺序变成中序（得到有序序列），于是可以退化成 167。
- **三数 / 四数之和**（15 / 18）：`n` 数之和的统一降维法 —— 固定一个数，剩下的递归成 `(n-1)` 数之和。

## 001.4 图解推演

### 001.4.1 一遍哈希的执行轨迹

```
nums = [2, 7, 11, 15]   target = 9
seen = { }

┌─────┬─────┬─────┬─────┐
│  2  │  7  │ 11  │ 15  │   ← 值
├─────┼─────┼─────┼─────┤
│ [0] │ [1] │ [2] │ [3] │   ← 下标
└─────┴─────┴─────┴─────┘
  ↑
  i

第 0 轮  i=0  x=2   need=9-2=7    seen 无 7   → 登记 seen{2:0}
第 1 轮  i=1  x=7   need=9-7=2    seen 有 2 ✅ → 返回 [seen[2], 1] = [0, 1]
```

用一张「状态表」看清楚每一轮 `seen` 的形态：

| 轮次 i | nums[i] | need = target - x | seen 命中？ | 命中返回 | 本轮后 seen |
| --- | --- | --- | --- | --- | --- |
| 0 | 2 | 7 | 否 | — | `{2: 0}` |
| 1 | 7 | 2 | **是**（下标 0） | `[0, 1]` | 不再执行 |

### 001.4.2 为什么「先查后存」是必须的（反例轨迹）

```
nums = [3, 3]   target = 6

❌ 先存后查：
第 0 轮  x=3  先 seen{3:0}  再查 need=3 → 命中自己 → 返回 [0, 0]   ✗ 非法

✅ 先查后存：
第 0 轮  x=3  查 need=3 → seen 空 → 未命中 → 登记 seen{3:0}
第 1 轮  x=3  查 need=3 → 命中下标 0 → 返回 [0, 1]                ✓
```

```
┌──────────────── 关键差异 ────────────────┐
│ 先存后查：查表时"自己"已经在表里 → 自己配自己 │
│ 先查后存：查表时"自己"还没进表 → 只能配到别人 │
└──────────────────────────────────────────┘
```

### 001.4.3 两条路线的对比图

```
                     ┌──────────── 输入 nums, target ────────────┐
                     │                                          │
          ┌──────────▼──────────┐                    ┌──────────▼──────────┐
          │  路线 A：哈希        │                    │  路线 B：排序+双指针  │
          │  O(n) 时间 / O(n) 空间│                    │  O(n log n) / O(1)  │
          └──────────┬──────────┘                    └──────────┬──────────┘
                     │                                          │
        一遍遍历：查 need → 存 x                      排序(丢下标) → 对撞
                     │                                          │
          ✅ 直接得到原下标                             ❌ 下标丢失，需额外记录
                     │                                          │
              【本题选择 A】                          【167 / 15 / 18 选择 B】
```

> **记住这张图**：它解释了 `001`（要下标）和 `002`（有序、不要下标）为什么是两种解法，而不是「两种写法」。

## 001.5 双语言实现

### 001.5.1 Java

```java
import java.util.HashMap;
import java.util.Map;

class Solution {
    public int[] twoSum(int[] nums, int target) {
        // key = 已经见过的数值，value = 它在 nums 中的下标
        // 不变量：进入第 i 轮前，seen 中恰好是 nums[0 .. i-1] 的全部元素
        Map<Integer, Integer> seen = new HashMap<>(nums.length * 2);

        for (int i = 0; i < nums.length; i++) {
            int need = target - nums[i];

            // 用包装类型接收：null 才表示"没找到"，不能用 0 当哨兵（下标 0 是合法值）
            Integer j = seen.get(need);
            if (j != null) {
                return new int[]{j, i};   // 先查后存：保证不会匹配到 nums[i] 自己
            }

            seen.put(nums[i], i);         // 直接覆盖：重复值留下"最近"的下标，答案唯一所以不影响结果
        }

        return new int[0];                // 题目保证有解，这行只为满足编译器的返回要求
    }
}
```

### 001.5.2 Go

```go
package main

func twoSum(nums []int, target int) []int {
	// key = 已经见过的数值，value = 它在 nums 中的下标
	// 不变量：进入第 i 轮前，seen 中恰好是 nums[0 .. i-1] 的全部元素
	seen := make(map[int]int, len(nums))

	for i, x := range nums {
		need := target - x

		// 必须用「逗号 ok」语法：map 的零值是 0，而下标 0 是合法答案
		if j, ok := seen[need]; ok {
			return []int{j, i}            // 先查后存
		}

		seen[x] = i
	}

	return nil                            // 题目保证有解；返回 nil 而不是空切片，语义更诚实
}
```

### 001.5.3 双语言差异批注

| 点 | Java | Go | 对本题的影响 |
| --- | --- | --- | --- |
| 「不存在」的表示 | `get()` 返回 `null` | `v, ok := m[k]` 的 `ok` | Go **没有 null**，不能靠值判断；Java 若用 `-1` 当哨兵则要小心下标 0 |
| 装箱开销 | `Map<Integer,Integer>` 每个 entry 两个 `Integer` 对象 | `map[int]int` 无装箱 | 1e4 规模无感；1e7 规模 Go 明显更快 |
| 返回空 | `new int[0]` | `nil`（`[]int(nil)`） | LeetCode 两者都接受；`nil` 的 `len` 也是 0，安全 |
| 循环写法 | 下标 `for (int i = 0; ...)` | `for i, x := range nums` | Go 的 `range` 直接给值，避免重复 `nums[i]` |
| 整数宽度 | `int` 恒 32 位 | `int` 在 64 位平台是 64 位 | 本题都安全；但 `target - x` 若接近 2³¹ 边界，Java 需换 `long` |

### 001.5.4 对拍测试（写完必须跑，这是本书的验收习惯）

```go
package main

import (
	"math/rand"
	"testing"
)

// 暴力参考实现：返回「解的数量」+「第一个解」
// 注意：必须返回数量——本题虽保证唯一解，但随机造的数据经常有多个解，
// 这时「和暴力返回的第一组下标完全相等」是错误断言（见下方注释）
func brute(nums []int, target int) (int, []int) {
	cnt := 0
	var first []int
	for i := 0; i < len(nums); i++ {
		for j := i + 1; j < len(nums); j++ {
			if nums[i]+nums[j] == target {
				cnt++
				if first == nil {
					first = []int{i, j}
				}
			}
		}
	}
	return cnt, first
}

// 判定一组下标是否是合法解（不关心它是不是暴力返回的那一组）
func isValid(nums []int, target int, p []int) bool {
	if len(p) != 2 {
		return false
	}
	i, j := p[0], p[1]
	if i == j || i < 0 || j < 0 || i >= len(nums) || j >= len(nums) {
		return false
	}
	return nums[i]+nums[j] == target
}

func samePair(a, b []int) bool {
	if len(a) != 2 || len(b) != 2 {
		return false
	}
	return (a[0] == b[0] && a[1] == b[1]) || (a[0] == b[1] && a[1] == b[0])
}

func TestTwoSumRandom(t *testing.T) {
	r := rand.New(rand.NewSource(42)) // 固定种子，失败可复现
	for iter := 0; iter < 20000; iter++ {
		n := 2 + r.Intn(30)
		nums := make([]int, n)
		for i := range nums {
			nums[i] = r.Intn(41) - 20 // 值域 [-20, 20]，故意制造大量重复值
		}
		// 随机挑两个不同下标造一个"保证有解"的输入
		i := r.Intn(n)
		j := r.Intn(n - 1)
		if j >= i {
			j++
		}
		target := nums[i] + nums[j]

		got := twoSum(nums, target)
		cnt, want := brute(nums, target)

		if cnt == 1 {
			// 题目保证唯一解 → 必须与暴力结果完全一致（顺序不限）
			if !samePair(got, want) {
				t.Fatalf("iter=%d nums=%v target=%d got=%v want=%v", iter, nums, target, got, want)
			}
		} else if !isValid(nums, target, got) {
			// 随机数据出现多解 → 只要求返回的是「某一组合法解」
			t.Fatalf("iter=%d nums=%v target=%d got=%v 不是合法解", iter, nums, target, got)
		}
	}
}
```

> ⚠️ **这段测试本身踩过一次坑，值得记下来**：最初我写的是「`got` 必须等于暴力返回的第一组下标」，结果 2 万次随机里第 2 次就挂了 —— 因为随机数据经常有**多组解**，暴力返回 `[0,10]`，哈希返回 `[3,7]`，两者都对。
> **教训**：随机对拍的判据必须与题目的「解是否唯一」对齐 —— **唯一解比精确相等，多解只验合法性**。这也是为什么 `brute` 要返回解的**数量**。

> **为什么值域要设成 `[-20, 20]`**：重复值密集，才能把「先存后查」「下标 0 当哨兵」这类 bug 逼出来。**随机测试的价值不在覆盖正常情况，而在频繁制造边界。**

## 001.6 复杂度与常见坑

### 001.6.1 复杂度推导（写结论不算本事，要能推）

- **时间 O(n)**：循环恰好执行 `n` 次；每次循环内 `HashMap.get` 与 `put` 是**均摊 O(1)**。
  - 为什么是「均摊」：哈希冲突时退化成链表/红黑树（Java 8+ 桶内超过 8 个转红黑树），单次可能 O(log n)；均摊到每次插入是 O(1)。
  - **什么时候会退化成 O(n²)**：所有 key 落在同一个桶（哈希函数被攻击 / 自定义 `hashCode` 写成常量）。生产代码里这是**哈希碰撞攻击**，不是理论问题。
- **空间 O(n)**：最坏存 `n` 个键值对。注意 Java 的 `HashMap` 有**负载因子 0.75**，`n` 个元素实际容量约 `n/0.75`，所以 `new HashMap<>(n*2)` 能避免扩容重哈希（本题这么写了）。

### 001.6.2 七个真实踩过的坑

1. **「先存后查」导致 `[3,3] → [0,0]`** —— 最高频错误。修法：把 `seen.put` 放到 `if` 之后。
2. **`Integer` 用 `==` 比较** —— `seen.get(need) == i` 在值超过 `[-128,127]` 时会因缓存失效而**恒为 false**。必须用 `.equals()` 或先拆箱成 `int`。
3. **用 `-1` 或 `0` 当「不存在」** —— `[0,4,3,0], target=0` 的正确答案是 `[0,3]`，下标 0 被误判为「没找到」。Go 里必须用 `ok`。
4. **`target - x` 溢出** —— 本题约束安全；但如果 `nums[i]` 到 `-2³¹`，Java 的 `int need = target - x` 会溢出成正数，导致误命中。生产代码用 `long`。
5. **返回 `List<Integer>` 而不是 `int[]`** —— LeetCode 判题签名固定是 `int[]`，返回类型错会直接编译失败。
6. **认为「数组有序就该用双指针」** —— 有序但**要原下标**时，双指针要先花 O(n) 记录原始位置，反而更绕。
7. **`HashMap` 初始容量不设** —— 1e4 元素会触发 3~4 次扩容（每次 rehash 全部元素）。虽然不影响复杂度量级，但面试里能说出来是加分项。

### 001.6.3 面试官最爱追问的三个问题

**Q1：为什么不能先排序再用双指针？**
> 「因为题目要求返回**原下标**。排序后下标关系被打乱，要额外存 `(值, 原下标)`，空间也变成 O(n)，代码还更容易在重复值上出错。如果题目改成『返回两个数本身』或『输入本来就有序』（LC 167），双指针才是更优解，因为它空间 O(1)。」

**Q2：哈希表的 O(1) 是真的 O(1) 吗？**
> 「是**均摊** O(1)。最坏 O(n)：所有 key 哈希到同一个桶。Java 8 之后桶内节点超过 8 个会转红黑树，单桶退化为 O(log n)。真正要防的是**哈希碰撞攻击**——攻击者构造大量同桶 key 让服务从 O(n) 变 O(n²)，这是很多语言运行时都打过补丁的漏洞类型。」

**Q3：如果内存放不下所有数，怎么办？**
> 「两条路：① **外部排序**——把数据分块排序落盘，再做 k 路归并，最后双指针扫描，时间 O(n log n)、空间 O(块大小)；② **值域分桶**——按值域把数分到 B 个文件，两数之和的配对必落在同一桶或相邻桶（需要处理跨桶），逐桶处理，空间 O(n/B)。本质都是『用外存换内存』。」
