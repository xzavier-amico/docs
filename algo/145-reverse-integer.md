## 145.1 题目

**原题链接**：<https://leetcode.cn/problems/reverse-integer/>

### 题意重述（把隐含条件补齐）

给你一个 **32 位有符号整数** `x`，把它的十进制数字**反过来**并返回。如果反转后的结果**超出 32 位有符号整数的范围** `[−2³¹, 2³¹ − 1]`，则返回 `0`。

题面还有一句极关键的附加约束（新版本才有）：**「假设环境不允许存储 64 位整数（有符号或无符号）」**。这句话把「用 `long` 一把梭」这条路直接堵住了，逼你去理解 `int` 的边界。

五个必须读出来的条件：

| 隐含条件 | 出处 | 违反了会怎样 |
| --- | --- | --- |
| `x` 是 32 位有符号整数 | 「`-2³¹ <= x <= 2³¹ - 1`」 | `x = −2³¹` 时 `Math.abs(x)` 还是负数（补码没有对称的正数），任何「先取绝对值」的写法都会错 |
| **符号要保留** | 示例 `−123 → −321` | 把符号丢掉、只反转数字部分再补符号也可以，但顺序别弄反 |
| 末尾的 `0` 反转后要**消失** | `120 → 21` | 若你拼字符串后不转成整数，会得到 `"021"`，与答案形式不符 |
| 溢出就返回 **`0`**，不是抛异常、不是夹到边界 | 「如果反转后整数超过 32 位有符号数的范围，就返回 0」 | 返回 `INT_MAX` / `INT_MIN`（夹逼）是 atoi 的规矩，**不是这题的** |
| **不允许用 64 位存储** | 「假设环境不允许存储 64 位整数」 | 用 `long` 累加能过题，但答不到这题真正想问的东西 |

### 约束与「量级反推」

| 约束 | 值 | 它对算法的含义 |
| --- | --- | --- |
| `x ∈ [−2³¹, 2³¹−1]` | 最多 **10 位**十进制数字 | 循环最多 10 轮，所以 `O(log₁₀|x|)` 就是 `O(1)` 级别；真正的难点在**边界**而不是时间 |
| 结果必须落在 `[−2147483648, 2147483647]` | 正数上限末位是 **7**，负数下限末位是 **8** | 预判条件里那两个神秘的 `7` 和 `8` 就是从这里来的 |
| 环境不许 64 位 | 题面明写 | 必须用「先比较再乘」的办法，把 `rev` 控制在安全区间内 |
| 只有 10 位数才可能溢出 | `|x| ≤ 2³¹−1` 意味着首位 ≤ 2 | 这解释了一个常见疑问：为什么有人不写预判也能过大部分用例 |

> 💡 **量级 → 算法** 之外再加一条**边界 → 算法**：
> **凡是「结果可能超出目标类型」的题，先问一句：溢出是可逆的吗？**
> 加法溢出可以事后减回来判；**乘法溢出会把低位信息丢掉（乘 10 之后最低位恒为 0），事后无法还原**——所以必须预判。

### 示例

```text
输入：x = 123          输出：321
输入：x = -123         输出：-321
输入：x = 120          输出：21        ← 末尾的 0 反转后在前面，作为整数自然消失
输入：x = 0            输出：0
输入：x = 1534236469  输出：0         ← 反转后 9646324351 超出上限
```

### 我自造的六个反例（写完解法必须拿它们打一遍）

```text
① x = 2147483647       → 反转 7463847412 溢出 → 0
② x = -2147483648      → 反转 -8463847412 溢出 → 0
                         暴露：先 Math.abs 的写法（abs(INT_MIN) 还是 INT_MIN）
③ x = 1463847412       → 反转 2147483641，恰好 ≤ INT_MAX → 返回 2147483641
                         暴露：预判里把 `>` 写成 `>=`（会误判成 0）
④ x = -1463847412      → 反转 -2147483641，恰好 ≥ INT_MIN → 返回 -2147483641
                         暴露：只写了正方向预判、忘了负方向
⑤ x = 1000000003       → 反转 3000000001 溢出 → 0
                         而失败实现常返回 -1294967295（回绕后的负数，符号都反了）
⑥ x = 0                → 0
                         暴露：把 0 当「哨兵」或 do-while 写法（会多算一轮）
```

第 ③④ 是这题最锋利的一对：**边界值本身是合法答案**，所以预判条件必须精确到「等于的时候还要看末位」。

## 145.2 从暴力到最优：第一个念头为什么错

### 第一步：暴力（先写出来，别急着优化）

最直白的思路是「字符串反转」，或者「取模累加」。两者都要面对溢出。

```java
// 方案 A：转字符串反转（看起来最省事）
String s = String.valueOf(x);
String r = new StringBuilder(s).reverse().toString();
// 问题马上来了：怎么把 r 变回 int？
// Integer.parseInt("9646324351") 会抛 NumberFormatException，
// 而你又不能用 Long.parseLong —— 题面禁止 64 位存储。
```

```java
// 方案 B：取模累加（正确方向，但边界写错了）
int rev = 0;
while (x != 0) {
    int d = x % 10;
    rev = rev * 10 + d;   // ← 溢出就发生在这里，而且悄悄发生
    x /= 10;
}
if (rev < Integer.MIN_VALUE || rev > Integer.MAX_VALUE) return 0;   // 永远为 false！
return rev;
```

- 方案 A：时间 `O(位数)`，空间 `O(位数)`；而且**没有合法的类型**能装下中间结果（题目明确禁止 64 位）。
- 方案 B：时间 `O(位数) ≤ 10 轮`，空间 `O(1)`。看起来无懈可击——**但它做的事后检查永远不会成立**：`rev` 的类型就是 `int`，`int` 不可能大于 `Integer.MAX_VALUE`，那个 `if` 是**恒假**的死代码。

### 第二步：卡点在哪 —— 为什么「先算再判」根本不可能

这是本章的核心。`int` 的溢出在 Java / Go 里是**静默回绕**（补码模 `2³²`），不会抛异常。于是：

```
正确的数学结果：  9646324351
32 位里存下的值： 1056389759     （9646324351 − 2³² = 5351357055；再 − 2³² 得 1056389759）
```

`1056389759` 是一个**完全合法的正数**，比 `INT_MAX` 小得多。所以任何「算完再看 `rev > INT_MAX`」的检查都必然通过——**溢出这件事在结果里彻底消失了**。

用一张表把 `x = 1534236469` 的每一轮摊开看：

| 轮次 | `d = x % 10` | 此时 `rev`（数学真值） | 是否已超出 `INT_MAX` |
| --- | --- | --- | --- |
| 1 | 9 | 9 | 否 |
| 2 | 6 | 96 | 否 |
| 3 | 4 | 964 | 否 |
| 4 | 6 | 9646 | 否 |
| 5 | 3 | 96463 | 否 |
| 6 | 2 | 964632 | 否 |
| 7 | 4 | 9646324 | 否 |
| 8 | 3 | 96463243 | 否 |
| 9 | 5 | 964632435 | 否 |
| 10 | 1 | **9646324351** | **是**（存进去变成 `1056389759`） |

结论：**溢出必须在这一步「之前」被判出来**，也就是在第 10 轮开始前，看到 `rev = 964632435 > 214748364 = INT_MAX / 10`，立刻返回 0。

### 第三步：「算完再除回去」行不行？（很多人以为可以，其实不行）

有人会说：`rev = rev * 10 + d` 之后，用 `(rev - d) / 10 != 旧rev` 就能检测溢出。**这对加法成立，对乘 10 不成立**：

- 乘以 10 之后，结果的**最低位恒为 0**，也就是说「乘 10 这个映射不是单射」——32 位里 `2³²/10` 个值挤到了同一批结果上，原始信息已经丢了。
- 具体地说，`10` 与 `2³²` 不互质（`10 = 2 × 5`），所以「乘 10」在模 `2³²` 下**不可逆**。你无法从回绕后的值反推「是否越界」。

> **这就是本章那句必背的话**：
> **溢出预判必须发生在「不可逆运算」之前；加法可逆（可以事后减回去），乘法不可逆（必须事前比）。**

### 第四步：灵感 —— 把「乘 10 加数字」拆成「比较 + 乘 + 加」

既然不能算完再判，那就**在算之前**用一个等价的比较来判。设本轮的 `d = x % 10`，要执行 `rev' = rev * 10 + d`。这个值会溢出，当且仅当：

```
rev > INT_MAX / 10                      → rev * 10 已经超过 INT_MAX，必然溢出
rev == INT_MAX / 10  且  d > 7          → 此时 rev * 10 == 2147483640，再加 d
                                          d ≤ 7 得到 ≤ 2147483647；d ≥ 8 就溢出
```

`INT_MAX / 10 = 214748364`，`INT_MAX` 的末位是 `7`——**那两个数字 `214748364` 和 `7`，就是 `2147483647` 被「切开」的样子**。

负方向对称：`INT_MIN = −2147483648`，`INT_MIN / 10 = −214748364`（Java / Go 的整数除法向零截断），末位是 `−8`：

```
rev < INT_MIN / 10                      → 必然下溢
rev == INT_MIN / 10  且  d < -8         → 溢出
```

### 为什么「`d > 7` 这个条件其实永远不会触发」

`|x| ≤ 2³¹ − 1 = 2147483647`，所以 `x` 最多 10 位，且首位只能是 `1` 或 `2`。反转之后，那个首位变成**末位**，所以最后一次迭代里 `d ∈ {1, 2}`，绝不会大于 7。

**那还要不要写？要。** 原因有两条，面试里说出来很有分量：

1. 这个「恒不成立」依赖于**具体约束**；如果把题目改成「反转 64 位整数」，`d > 7` 就会出现。
2. 写全了之后，条件与 `INT_MAX` 的定义**一一对应**，读代码的人不需要再做一遍推理。

## 145.3 原理拆解

### 145.3.1 数据结构与算法选型

| 方案 | 时间 | 空间 | 符合「不用 64 位」 | 什么时候会输 |
| --- | --- | --- | --- | --- |
| 转字符串 + `Integer.parseInt` | O(位数) | O(位数) | ✗（解析溢出会抛异常） | 溢出输入直接抛 `NumberFormatException`；题面禁止 64 位解析 |
| `long` 累加 + 最后比范围 | O(位数) | O(1) | ✗（题面禁止） | 面试官会追问「不许用 64 位怎么做」 |
| 算完再判 `rev > INT_MAX` | O(位数) | O(1) | ✓ | **恒假条件**，溢出后返回错值（方案 B 的死法） |
| 算完再「除回去」反查 | O(位数) | O(1) | ✓ | 乘 10 不可逆，反查不可靠 |
| **累加前预判** ✅ | **O(位数)** | **O(1)** | **✓** | 需要想清楚边界（±7/±8） |
| 只反转一半（用于回文数，LC 9） | O(位数/2) | O(1) | ✓ | 本题要返回整个反转值，只能全反转 |

### 145.3.2 为什么这个做法是对的（正确性论证）

**命题 1（累加正确性）**：设 `x` 的十进制数字（先不看符号）为 `d₀d₁…d_{m−1}`（`d₀` 最高位）。执行 `k` 轮后，`rev` 恰为整数 `d_{k−1}d_{k−2}…d₀`，剩余待处理部分恰为 `d_k…d_{m−1}`（带原符号）。

**证明**（对 `k` 归纳）：

- `k = 0`：`rev = 0`（空前缀），剩余是整个数 ✓。
- 设第 `k` 轮前成立。该轮 `d = x % 10 = d_{k−1}`（当前剩余的最低位），`rev' = rev · 10 + d_{k−1}`，即把旧反转值左移一位再接上 `d_{k−1}` —— 正好是 `d_{k−1}d_{k−2}…d₀`；`x /= 10` 让剩余变成 `d_k…d_{m−1}` ✓。
- 终止（`x == 0`）：`rev` 是完整的数字反转 ✓。∎

> 注意 `x % 10` 在**负数**上得到负余数（Java、Go 的 `%` 都向零截断），所以 `d` 自带符号，`rev` 全程带着符号增长，符号问题自动解决，**不需要额外处理**。

**命题 2（预判条件精确等价）**：设 `q = INT_MAX / 10 = 214748364`（整数除法向下取整），则

```
rev · 10 + d 能放进 int（不溢出）  ⟺  rev < q  或  (rev == q 且 d ≤ 7)
```

**证明**：因为 `INT_MAX = 10q + 7`。

- 若 `rev ≤ q − 1`：`rev·10 + d ≤ 10(q−1) + 9 = 10q − 1 < 10q + 7 = INT_MAX` ✓（用到了 `d ≤ 9`）。
- 若 `rev = q`：`rev·10 + d = 10q + d`，它 `≤ INT_MAX = 10q + 7` 当且仅当 `d ≤ 7` ✓。
- 若 `rev ≥ q + 1`：`rev·10 + d ≥ 10q + 10 > INT_MAX`，必然溢出 ✓。∎

**负方向**：`INT_MIN = −(10q + 8)`。把上面三段推导照着做一遍、只把不等号方向翻过来：`rev ≥ −q+1` 时 `rev·10+d ≥ −10q+10−9 > −10q−8`；`rev = −q` 时需 `d ≥ −8`；`rev ≤ −q−1` 时 `rev·10+d ≤ −10q−1 < INT_MIN`。合起来即「不溢出 ⟺ `rev > −q` 或（`rev == −q` 且 `d ≥ −8`）」。∎

> 这两个证明没有任何技巧，就是**把 `INT_MAX` / `INT_MIN` 写成 `10q + 余数` 的形式再比大小**。面试时能把这个推导写出来，比背结论强得多。

### 145.3.3 通用解题思路（可迁移的那一层）

**模型：不可逆运算前的边界预判**

```
要对 acc 做一次「可能溢出」的运算 f
        ↓ 问：f 可逆吗？（加法可逆；乘法、位运算一般不可逆）
可逆  → 可以在运算后检查：acc' - b != acc  ⇒ 溢出（加法）
不可逆 → 必须在运算前比较：用一个等价的「安全区间」条件挡在前面（乘法）
        ↓ 常见的安全区间写法
a * b 溢出 ⟺ a > MAX / b            （b > 0）
a * b + c 溢出 ⟺ a > (MAX - c) / b
```

这套思路出现在所有「整数边界」题里：

| 题 / 场景 | 预判什么 | 关键点 |
| --- | --- | --- |
| [LC 7 整数反转](https://leetcode.cn/problems/reverse-integer/) | `rev*10 + d` 溢出 | `MAX/10` 与末位 `7` |
| [LC 8 字符串转换整数](https://leetcode.cn/problems/string-to-integer-atoi/) | `acc*10 + d` 溢出 | 但这题要**夹逼**到 `INT_MAX` / `INT_MIN`，不是返回 0 |
| [LC 9 回文数](https://leetcode.cn/problems/palindrome-number/) | 反转**一半**即可 | 只反转到 `rev >= x` 就停，天然不会溢出 |
| [LC 29 两数相除](https://leetcode.cn/problems/divide-two-integers/) | `−INT_MIN` 溢出 | 先转成负数运算，避免取绝对值 |
| [LC 50 Pow(x, n)](https://leetcode.cn/problems/powx-n/) | `−n` 溢出 | 见 [`144-powx-n.md`](144-powx-n.md)：转 `long` 或 `int64` |
| [LC 2 两数相加](https://leetcode.cn/problems/add-two-numbers/) | 进位 | 链表加法天然不会溢出（边加边建节点），是可逆场景 |

### 145.3.4 可扩展性（面试追问的六个方向）

| 追问 | 变化 | 应对 |
| --- | --- | --- |
| 允许用 64 位 | 约束放宽 | `long rev` 累加，最后 `if (rev > INT_MAX \|\| rev < INT_MIN) return 0;` ——简单，但**要在面试里同时给出不用 64 位的版本** |
| 溢出时要求**夹逼到边界**（像 atoi） | 返回值语义变了 | 一旦预判到溢出，直接返回 `INT_MAX` / `INT_MIN`；不能返回 0 |
| 改成 **64 位整数**反转 | 边界变成 `9.22·10¹⁸` | 同样的预判结构，`q = Long.MAX_VALUE / 10 = 922337203685477580`，末位 `7`；负方向末位 `−8` |
| 输入是**任意精度的字符串** | 不存在溢出 | 直接字符串反转即可，但要自己处理符号与前导零 |
| 要反转**二进制位**而不是十进制位 | 语义变化 | 那就是 LC 190：`res = (res << 1) \| (n & 1)`，循环 32 次，用无符号类型（Go 的 `uint32`） |
| 要求**不改内存、流式**处理 | 不能存数字 | 边读边输出字符，把符号与末尾 0 单独处理；这时候「反转」变成一次「从尾到头」的遍历 |

## 145.4 图解推演

### 145.4.1 正常情况：`x = 123` 的三轮

```
初始        rev = 0        x = 123
────────────────────────────────────────────────────
第 1 轮  d = 123 % 10 = 3      rev = 0*10 + 3 = 3      x = 12
         └─ 把 3 接到 rev 的「个位」
第 2 轮  d = 12 % 10  = 2      rev = 3*10 + 2 = 32     x = 1
         └─ 旧的 3 左移一位变成「十位」，2 补进个位
第 3 轮  d = 1 % 10   = 1      rev = 32*10 + 1 = 321   x = 0
────────────────────────────────────────────────────
x == 0 → 返回 321
```

```
    rev 的增长形状（每轮「左移一格 + 补末位」）

       0  ──►  3  ──►  3 2  ──►  3 2 1
               ▲        ▲          ▲
               │        │          └── 补上 d=1
               │        └───────────── 补上 d=2，旧的 3 左移
               └────────────────────── 补上 d=3
```

### 145.4.2 预判的几何位置

```
             INT_MAX = 2147483647
                       └───┬───┘└┬┘
                       q = 214748364  末位 7

  rev 的值域（本轮开始前）
  ├──────────────┼──────────────┼──────────────►
  0            ...          q=214748364     更大
  │◄── 安全 ────►│◄─ 还要看 d ─►│◄── 必然溢出 ──►│
                  rev < q        rev == q       rev > q
                                 且 d ≤ 7 → 安全
                                 d ≥ 8   → 溢出
```

负方向把上面这张图整体镜像，并把末位的 `7` 换成 `8`（因为 `INT_MIN = −2147483648`，末位比正方向的 `7` 大 1）。

### 145.4.3 溢出实例的逐步对照（`x = 1534236469`）

| 轮次 | `rev`（数学值） | `rev > q`? | `rev == q && d > 7`? | 处理 |
| --- | --- | --- | --- | --- |
| … | … | 否 | 否 | 正常累加 |
| 9 | 964632435 | 否（`964632435 < 214748364` 不成立 → 是 **大于**） | — | **第 9 轮后已危险** |

把关键的一次说清楚：

```
第 10 轮开始前：rev = 964632435，d = 1
                 q = 214748364
                 rev > q  → 964632435 > 214748364  成立
                 ⇒ 立刻返回 0     ✓（正确）

若没有预判：rev = 964632435 * 10 + 1 = 9646324351
             32 位回绕 → 1056389759（一个看起来完全正常的正数）
             事后检查 rev > INT_MAX ？  1056389759 < 2147483647 → 不成立
             ⇒ 返回 1056389759     ✗（答案要求 0）
```

> **这张对照表就是本章的全部价值**：同一组输入，预判版返回 `0`，事后判版返回 `1056389759`——而且后者**不会报错、不会崩溃、看起来毫无问题**。

## 145.5 双语言实现

### 145.5.1 Java

```java
class Solution {
    public int reverse(int x) {
        int rev = 0;

        while (x != 0) {
            int d = x % 10;   // 负数时 d 也是负数（Java 的 % 向零截断），符号自动跟着 rev 走

            // 预判：马上要执行 rev * 10 + d，先在「乘之前」挡住溢出的两种情况。
            // 214748364 = Integer.MAX_VALUE / 10，而 Integer.MAX_VALUE 的末位是 7。
            if (rev > Integer.MAX_VALUE / 10
                    || (rev == Integer.MAX_VALUE / 10 && d > 7)) {
                return 0;     // 题目要求：溢出就返回 0，不是夹到边界
            }
            // 负方向对称：Integer.MIN_VALUE = -2147483648，末位是 -8
            if (rev < Integer.MIN_VALUE / 10
                    || (rev == Integer.MIN_VALUE / 10 && d < -8)) {
                return 0;
            }

            rev = rev * 10 + d;   // 到这里才能安全地乘
            x /= 10;
        }

        return rev;
    }
}
```

> **为什么不用 `Math.abs(x)`**：`x = Integer.MIN_VALUE` 时 `Math.abs` 返回的还是 `Integer.MIN_VALUE`（补码没有对称的正数），之后 `x % 10` 一路负数、`x /= 10` 的方向也会让人算错。**让 `d` 带着符号走，是最省心的写法。**

### 145.5.2 Go

```go
package main

// 用常量表达 32 位边界：Go 的 int 在 64 位平台是 64 位，
// 直接写 2147483647 / -2147483648 会让读者误以为是「平台相关」的判断。
const (
	maxInt32 = 1<<31 - 1 // 2147483647
	minInt32 = -1 << 31  // -2147483648
)

func reverse(x int) int {
	rev := 0

	for x != 0 {
		d := x % 10 // 与 Java 一致：负数取模得负数

		// 关键差异：Go 的 int 是 64 位，rev*10+d 在这里「不会真的溢出」，
		// 但题目要的是「32 位有符号溢出就返回 0」——所以必须显式与 32 位常量比较，
		// 不能指望类型自己溢出来提醒你。
		if rev > maxInt32/10 || (rev == maxInt32/10 && d > 7) {
			return 0
		}
		if rev < minInt32/10 || (rev == minInt32/10 && d < -8) {
			return 0
		}

		rev = rev*10 + d
		x /= 10
	}

	return rev
}
```

### 145.5.3 双语言差异批注

| 点 | Java | Go | 对本题的影响 |
| --- | --- | --- | --- |
| `int` 宽度 | 恒 **32 位**，`rev*10+d` **真的会溢出** | 64 位平台 **64 位**，`rev*10+d` **不会溢出** | Java 的危险是「悄悄回绕」；Go 的危险是「不溢出所以检测不到」——**两边都必须写显式比较，但理由完全相反** |
| 边界常量 | `Integer.MAX_VALUE` / `Integer.MIN_VALUE` | 没有内建 `int32` 边界常量，习惯上自定义 `const maxInt32 = 1<<31 - 1` | Go 里直接把 `2147483647` 写进代码容易被人误认为可配置，用 `1<<31 - 1` 更能表达「这就是 32 位上限」 |
| 取模符号 | `−123 % 10 = −3` | `−123 % 10 = −3` | 一致，负数方向的分析在两种语言里可以共用 |
| 整数除法 | 向零截断：`-2147483648 / 10 = -214748364` | 向零截断，结果相同 | `minInt32/10` 的取整方向与预判推导严格对齐 |
| 溢出行为 | 静默回绕（补码模 `2³²`） | 与 Java 相同（有符号整数回绕，Go 规范明文规定） | 两种语言都不会抛异常，**所以「靠异常发现溢出」这条路不存在** |

### 145.5.4 对拍测试（写完必须跑）

```go
package main

import (
	"math/rand"
	"strconv"
	"strings"
	"testing"
)

// 参考实现：字符串反转 + int64 解析后判范围。
// 它与被测实现的思路完全无关（一个走十进制字符串，一个走取模累加），
// 所以两者的 bug 不会同向。
func bruteReverse(x int) int {
	s := strconv.Itoa(x)
	neg := strings.HasPrefix(s, "-")
	if neg {
		s = s[1:]
	}
	b := []byte(s)
	for i, j := 0, len(b)-1; i < j; i, j = i+1, j-1 {
		b[i], b[j] = b[j], b[i]
	}
	var v int64
	for _, c := range b {
		v = v*10 + int64(c-'0') // 字符串解析天然吃掉前导 0（"021" → 21）
	}
	if neg {
		v = -v
	}
	if v > 2147483647 || v < -2147483648 {
		return 0
	}
	return int(v)
}

func TestReverseRandom(t *testing.T) {
	r := rand.New(rand.NewSource(20260218))
	for iter := 0; iter < 20000; iter++ {
		var x int
		switch iter % 4 {
		case 0:
			x = r.Intn(2000000001) - 1000000000 // 常规范围
		case 1:
			x = int(int32(r.Uint32())) // 全 int32 值域，覆盖极值附近
		case 2:
			x = r.Intn(1000) // 短数字，覆盖末尾 0 的情形
		default:
			// 制造「反转后刚好在边界附近」的数：把 2147483641 之类反向拼出来
			x = 0
			for _, v := range []int{1, 4, 6, 3, 8, 4, 7, 4, 1, 9} {
				x = x*10 + v
			}
			if r.Intn(2) == 0 {
				x = -x
			}
			if x > 2147483647 || x < -2147483648 {
				x = 1463847412 // 收回合法值域（反向拼出的数可能越界）
			}
		}
		want := bruteReverse(x)
		if got := reverse(x); got != want {
			t.Fatalf("iter=%d reverse(%d) got=%d want=%d", iter, x, got, want)
		}
	}
}

func TestReverseEdge(t *testing.T) {
	cases := []struct {
		x    int
		want int
	}{
		{123, 321},
		{-123, -321},
		{120, 21},               // 末尾 0 消失
		{0, 0},
		{1, 1},
		{-1, -1},
		{2147483647, 0},         // 反转 7463847412 溢出
		{-2147483648, 0},        // 反转 -8463847412 溢出；先 abs 的写法会在这里崩
		{1463847412, 2147483641},  // 恰好合法：专治把 `>` 写成 `>=`
		{-1463847412, -2147483641}, // 负方向恰好合法：专治漏写负方向预判
		{1534236469, 0},         // 反转 9646324351，回绕后是 1056389759
		{1000000003, 0},         // 反转 3000000001 溢出
		{1000000000, 1},          // 10 位数末尾 0：1000000000 → 1
	}
	for _, c := range cases {
		if got := reverse(c.x); got != c.want {
			t.Fatalf("reverse(%d) got=%d want=%d", c.x, got, c.want)
		}
	}
}
```

> **对拍里最关键的两条**：`{1534236469, 0}`（回绕后是 `1056389759`，暴露「先算后判」）与 `{1463847412, 2147483641}`（合法边界，暴露 `>=` / `>` 的差别）。**只跑随机不足以覆盖这两处**——随机生成 `1534236469` 的概率几乎为 0，所以边界用例必须手写。

## 145.6 复杂度与常见坑

### 145.6.1 复杂度推导（写结论不算本事，要能推）

- **时间 O(log₁₀|x|)**：每轮 `x /= 10`，所以轮数 = `x` 的十进制位数。`|x| ≤ 2³¹ − 1 < 10¹⁰`，所以**最多 10 轮**——事实上是 `O(1)`（常数上界 10）。每轮只做「取模、比较、乘加、整除」各一次。
- **空间 O(1)**：只有 `rev`、`d` 两个标量，不用字符串、不用数组、不用 64 位。
- **对比字符串方案**：字符串需要 `O(位数)` 的额外空间（`StringBuilder` 的 `char[]`），而且解析回整数时**没有合法类型**可用（题面禁止 64 位），所以它不只是慢，而是**在这个约束下不可行**。
- **溢出检测的代价**：每次迭代多做两次比较（正、负各一次），是常数开销；不改变复杂度，但**把「正确性」从概率问题变成了确定问题**。

### 145.6.2 七个真实踩过的坑

1. **算完再判 `rev > Integer.MAX_VALUE`** —— 条件恒假（`int` 装不下更大的值），溢出的输入会返回回绕后的乱值（如 `1056389759`）。必须在累加**之前**判。
2. **用「除回去」反查溢出** —— `rev * 10` 在模 `2³²` 下不可逆（结果最低位恒为 0，信息已丢），反查不可靠。**预判是唯一正确的做法。**
3. **只写正方向预判** —— `144` 章的坑是 `−n` 溢出，本章的坑是「只想着正数”。`x = −2147483648` / `−1463847412` 会给出错值。负方向必须单独写一条。
4. **`>` 写成 `>=`** —— `rev == 214748364` 且 `d = 1` 时，`rev*10 + d = 2147483641` **是合法答案**。写成 `>=` 会把它误判成溢出返回 0。这一条是「边界值本身合法」的典型。
5. **Go 里吃 64 位 `int` 的便宜** —— `rev*10 + d` 在 amd64 上不会溢出，于是「不写检测也能过」，但返回的是超出 `int32` 的值，答案错。必须显式与 32 位常量比较。
6. **`Math.abs(x)` 处理 `INT_MIN`** —— `Math.abs(Integer.MIN_VALUE) == Integer.MIN_VALUE`（仍是负数），后续取模得到负数字、除法方向混乱，结果完全错。
7. **把溢出返回值写成「夹逼到边界」** —— atoi（LC 8）要求夹到 `INT_MAX` / `INT_MIN`，本题要求返回 **`0`**。两题混淆是高频失分点。

### 145.6.3 面试官最爱追问的三个问题

**Q1：为什么不能先算完再判溢出？**

> 「因为 `int` 的溢出是**模 2³² 的静默回绕**，越界的值会被折回一个看起来完全正常的小数字。比如 `1534236469` 反转的最后一步 `964632435 * 10 + 1 = 9646324351`，存进 `int` 变成 `1056389759`——它小于 `INT_MAX`，任何『事后检查范围』都通过，程序会老老实实返回一个错答案。加法的溢出还能用『减回去』检测，但乘 10 在模 2³² 下不可逆（结果最低位恒为 0，信息已丢），所以必须在乘之前用一个等价的比较把危险局面挡掉。」

**Q2：那两个常数 `214748364` 和 `7` 是怎么来的？**

> 「`INT_MAX = 2147483647` 写成 `10 × 214748364 + 7`，商就是 `214748364`，余数就是末位 `7`。于是 `rev * 10 + d` 不溢出等价于：`rev < 214748364`，或者 `rev == 214748364` 且 `d ≤ 7`。负方向把 `INT_MIN = −2147483648` 写成 `−(10 × 214748364 + 8)`，条件变成 `rev > −214748364`，或者 `rev == −214748364` 且 `d ≥ −8`。」

**Q3：如果允许你用 `long`，代码会怎么变？**

> 「会短很多：`long rev = 0; while (x != 0) { rev = rev * 10 + x % 10; x /= 10; }`，最后 `return (rev < Integer.MIN_VALUE || rev > Integer.MAX_VALUE) ? 0 : (int) rev;`。逻辑上完全正确，因为 `long` 装得下任何 10 位反转结果。但题面明确『假设环境不允许存储 64 位整数』，所以这个版本只是用来对照理解边界，正式答案还得是预判版。顺便说，如果约束放大到 64 位整数反转，预判结构完全一样，只是商变成 `922337203685477580`、末位还是 `7` 和 `-8`。」
