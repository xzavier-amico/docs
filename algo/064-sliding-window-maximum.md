## 064.1 题目

**原题链接**：<https://leetcode.cn/problems/sliding-window-maximum/>

### 题意重述（把隐含条件补齐）

给定数组 `nums` 和整数 `k`，有一个大小为 `k` 的窗口从数组最左端向右滑动，**每次只滑动一格**。返回**每一个窗口内的最大值**组成的数组。

一句话说完，但它藏着六个必须读出来的约束：

| 隐含条件 | 出处 | 违反了会怎样 |
| --- | --- | --- |
| **窗口大小固定为 `k`** | 「大小为 k 的滑动窗口」 | 若按变长窗口来做，会漏掉或重复统计窗口 |
| **每次只滑动一位** | 「每次窗口向右移动一位」 | 相邻窗口有 `k-1` 个元素重叠 —— 这是「不能重复扫描」的根本原因 |
| **输出 `n - k + 1` 个值** | 窗口数 = `n - k + 1` | 结果数组开成 `n - k` 会漏掉最后一个窗口（返回长度不足，判题直接错） |
| **`1 <= k <= n`** | 约束 | `k = 1` 时答案是原数组；`k = n` 时答案只有一个元素 = 全局最大。两者都要能跑 |
| **元素可以是负数、可以等于 `Integer.MIN_VALUE`** | `-10⁴ <= nums[i] <= 10⁴`（原型题更宽） | 用 `0` 或 `-1` 当「队首为空」的哨兵会误判；Go 里必须靠 `head < tail` 判空 |
| **返回最大值本身，不是下标** | 「返回滑动窗口中的最大值」 | 内部**必须**存下标（要判断过期），输出时才转成值 |

### 约束与「量级反推」

| 约束 | 值 | 它对算法的含义 |
| --- | --- | --- |
| `1 <= n <= 10⁵` | n 最大十万 | **O(nk) 必死**：`k = n/2` 时是 `5·10⁹` 次比较。本机实测 `n = 2·10⁴, k = 10⁴` 的暴力已需 **69 ms**，按 `nk` 外推到 `n = 10⁵, k = 5·10⁴` 约 **1.7 s**；单调队列只要 **1.3 ms** |
| `1 <= k <= n` | 窗口长度可变 | 算法必须对 `k = 1` 和 `k = n` 都成立，不能写「假设 k < n」的代码 |
| `-10⁴ <= nums[i] <= 10⁴` | 可为负、可相等 | 大量相等值时，队列里「留谁」会影响队列长度，但不影响正确性（§064.3.2 会证明） |
| 返回 `int[]` | 定长 `n-k+1` | `O(n)` 空间，无法避免（要存输出） |
| 只需**最大值** | 不是中位数、不是第 k 大 | 极值有「支配关系」，这是能用单调队列的根本前提（§064.3.4 会说明中位数为什么不行） |

> 💡 **量级 → 算法**：`n = 10⁵` 且「求解对象是滑动窗口的极值」→ 这是单调队列的**教科书场景**。
> 同时要注意：`k` 最大也能到 `10⁵`，所以「每个窗口扫一遍」和「每个窗口建一次堆」都要仔细掂量 —— 前者 `O(nk)` 必死，后者 `O(n log k)` 能过但常数大 3 倍以上。

### 示例

```
输入：nums = [1, 3, -1, -3, 5, 3, 6, 7], k = 3
输出：[3, 3, 5, 5, 6, 7]

窗口位置                     窗口内元素            最大值
[1  3  -1] -3  5  3  6  7    1, 3, -1             3
 1 [3  -1  -3] 5  3  6  7    3, -1, -3            3
 1  3 [-1  -3  5] 3  6  7    -1, -3, 5            5
 1  3  -1 [-3  5  3] 6  7    -3, 5, 3             5
 1  3  -1  -3 [5  3  6] 7    5, 3, 6              6
 1  3  -1  -3  5 [3  6  7]   3, 6, 7              7

输入：nums = [1], k = 1
输出：[1]

输入：nums = [1, -1], k = 1
输出：[1, -1]
```

### 我自造的六个反例（写完解法必须拿它们打一遍）

```text
① nums = [1,2,3,4], k = 1        → [1,2,3,4]    k=1：每个元素自己就是一个窗口
   暴露「结果数组长度写成 n-k」

② nums = [9,8,7,6], k = 4        → [9]          k=n：只有一个窗口，答案 = 全局最大
   暴露「窗口没满就输出」或「长度算错」

③ nums = [7,7,7], k = 2          → [7,7]        全相同值
   暴露「用 < 还是 <= 淘汰队尾」引起的队列长度差异（结果必须一样）

④ nums = [9,8,7,6,5], k = 3      → [9,8,7]      严格递减：每轮队首都要过期
   暴露「忘记判队首过期」，会一直输出 9

⑤ nums = [1,2,3,4,5], k = 3      → [3,4,5]      严格递增：每轮入队都清空队列
   暴露「尾部淘汰时的 head/tail 边界」——队列被清空后还要能正常入队

⑥ nums = [-2147483648, 2147483647], k = 1  → 原样输出
   暴露「用 0 / -1 / MIN_VALUE 当空队列哨兵」的写法
```

第 ④ 与第 ⑤ 条是**一对镜像**，必须都跑：

- **递减序列**考「队首过期」——最大值一直在队首，`k` 步之后必须把它踢掉；
- **递增序列**考「队尾淘汰」——每一轮都要把队里所有元素清空，`head == tail` 之后仍要能正确入队。

只测其中一种，就总会漏掉另一条分支。

## 064.2 从暴力到最优：第一个念头为什么错

### 第一步：暴力（先写出来，别急着优化）

```java
// 暴力：每个窗口单独扫一遍取 max
int[] res = new int[n - k + 1];
for (int i = 0; i + k <= n; i++) {
    int mx = nums[i];
    for (int j = i + 1; j < i + k; j++) mx = Math.max(mx, nums[j]);
    res[i] = mx;
}
```

- 时间 **O(nk)**，空间 **O(1)**（不计输出）。
- 具体数字（本机实测）：

| n | k | 暴力 O(nk) | 单调队列 O(n) | 倍数 |
| --- | --- | --- | --- | --- |
| 5·10³ | 2.5·10³ | 5.27 ms | 75 µs | 70× |
| 2·10⁴ | 10⁴ | 69.3 ms | 266 µs | 261× |
| 10⁵ | 5·10⁴ | ≈ 1.7 s（外推） | **1.27 ms** | ≈ 1340× |

- 卡点不是「怎么取 max」，而是**重复**：相邻两个窗口有 `k-1` 个元素是同一批，暴力把它们重新扫了一遍。

### 第二步：第一个「聪明」念头，以及它为什么错

求和滑窗的经验告诉我们可以「进一个、出一个」，于是有人想：

```
维护当前窗口的 max；
新元素进来：max = Math.max(max, 新元素)
老元素出去：如果出去的正好是 max，就…… 重新扫一遍？
```

**问题就在「如果」这里**：最大值被移走后，你无法 O(1) 知道「第二大的还在不在窗口里」。求和之所以能这么干，是因为加法有**逆运算**（减法）；而 `max` 没有逆运算 —— 你不知道「去掉这个元素之后最大值是谁」。

于是逼出两条路：

- **用一个能「记住顺序」的容器**（平衡树 / 堆），`O(n log k)`；
- **用一个能「记住候选」的队列**，`O(n)`。

### 第三步：灵感的来源 —— 支配关系

盯着两个下标 `i < j` 看：

```
若 nums[i] <= nums[j]（i 比 j 旧，且不比 j 大）：
    · 只要 j 还在窗口里，i 就永远不可能成为最大值（因为 j 比它大）
    · 而 j 还会比 i 活得久（j 更靠右，更晚滑出窗口）
    ⇒ i 在 j 出现的那一刻就"死了"：既没机会，也没未来
```

这就是**支配关系**（domination）：**又旧又小**的元素被「又新又大」的元素彻底支配。

于是算法只要维护「**还没被支配的候选**」：

```
每当新元素 j 进来：
    把队尾所有 <= nums[j] 的元素全部踢掉（它们被 j 支配了）
    把 j 放进队尾
每当窗口右移：
    把队首所有已经滑出窗口的元素踢掉（它们过期了）
队首 = 当前窗口最大值
```

**为什么用「双端队列」，而不是栈？** 因为这里有两种**方向相反**的淘汰：

```
   队首 ←──────────────────────────────  队尾
   │  过期淘汰（下标太小，滑出窗口）      │  支配淘汰（值太小，被新元素支配）
   │  head++                        tail-- │
   └──────────────────────────────────────┘
             队首就是最大值
```

栈只能在一端操作，而「过期」必须发生在**旧的那一端**、「支配淘汰」必须发生在**新的那一端** —— 所以必须两端都能动：这就是**双端队列**（deque）。

### 第四步：与 061/062 的关系 —— 同一句话，换个容器

| | 061 / 062（单调栈） | 064（单调队列） |
| --- | --- | --- |
| 淘汰规则 | 新元素**比栈顶大/小** → 弹栈顶 | 新元素**不比队尾小** → 弹队尾 |
| 另一个规则 | 无（栈里的元素永不过期） | **队首过期**（滑出窗口就扔） |
| 谁被结算 | 被弹出的元素（答案定稿） | **队首**（它是当前窗口的答案） |
| 存什么 | 下标 | 下标（必须，否则判不了过期） |
| 为什么能 O(n) | 每个下标只入栈一次、出栈一次 | 每个下标只入队一次、出队一次 |

一句话：**「单调栈」是「只从一端淘汰」的单调结构；「单调队列」多了一条『过期』规则，因此要两端都能淘汰。**

## 064.3 原理拆解

### 064.3.1 数据结构与算法选型

| 方案 | 时间 | 空间 | 代码量 | 什么时候会输 |
| --- | --- | --- | --- | --- |
| A 每个窗口扫一遍 | O(nk) | O(1) | 8 行 | `k` 大就死：`n = 10⁵, k = 5·10⁴` ≈ 1.7 s |
| B 平衡树 / 多重集（值 → 计数） | O(n log k) | O(k) | 20 行 | 常数大、每步都是一次树操作；Java 里要 `TreeMap` 手工维护计数 |
| C 大顶堆 + 懒删除 | O(n log n) | O(n) | 20 行 | 堆里会残留过期元素（空间 O(n)），且 `log n` 比 `log k` 更贵；Go 要自己实现 `heap.Interface` |
| D 稀疏表（ST 表）离线 RMQ | O(n log n) 预处理 + O(1) 查询 | O(n log n) | 30 行 | 空间是 `n log n`，`10⁵` 时约 `1.7·10⁶` 个 int；且只适合**静态数组** |
| E **分块两次扫描**（按 k 分块，算前缀 max 与后缀 max） | **O(n)** | O(n) | 20 行 | 需要预先知道 `k`；优点是**不用 deque**，缺点是「窗口右移时端点跨块」的边界要算清 |
| **F 单调队列（双端队列）** ✅ | **O(n)** | **O(k)** | 15 行 | 需要正确实现「两端淘汰」；空间最省（队列长度 ≤ k） |

**为什么选 F**：

- 与 B/C 相比：`O(n)` 对 `O(n log k)`，在 `n = 10⁵` 时是数量级差异（实测 1.27 ms vs 数十毫秒级别），且**空间只要 O(k)** —— 队列里最多装 k 个下标。
- 与 E 相比：E 也是 O(n)，但它的正确性依赖「按 k 对齐分块」这个不那么直观的技巧；F 的思路更直接（只留可能成为最大值的候选），而且**能直接推广到变长窗口**（见 §064.3.4），E 不行。
- 与 D 相比：D 是「离线 RMQ」的思路，预处理 `O(n log n)` 换 `O(1)` 查询，只有当**查询次数远多于一次遍历**时才划算。

### 064.3.2 为什么这个做法是对的（正确性论证）

记窗口右端为 `i`（左端 `i-k+1`），队列内有效区间是 `dq[head..tail)`。

**不变量（每轮输出前成立）**：

- **I1（下标递增）**：`dq` 中的下标严格递增。
- **I2（值严格递减）**：`nums[dq[head]] > nums[dq[head+1]] > … > nums[dq[tail-1]]`。
- **I3（窗口内）**：`dq` 中所有下标都在 `[i-k+1, i]` 内。
- **I4（支配完备）**：窗口内任意下标 `j`，若 `j ∉ dq`，则存在 `t ∈ dq`，使 `t > j` 且 `nums[t] >= nums[j]`（`t` 支配 `j`）。

**证明 I1 / I2**：入队时新下标 `i` 一定大于队列中所有下标（下标递增）；同时把 `<= nums[i]` 的队尾全部弹掉，剩下的队尾都 `> nums[i]`。故两条都保持。∎

**证明 I3**：每轮先弹掉队首所有 `<= i-k` 的下标，它们已滑出窗口；由于 I1，新入队的是当前 `i`，也在窗口内。∎

**证明 I4（关键）**：考虑 `j` 不在队列里的原因，只有两种：

1. **`j` 被支配淘汰**：`j` 被某个 `m > j` 且 `nums[m] >= nums[j]` 的元素从队尾弹出。此时对 `m` 递归：若 `m` 还在队里，取 `t = m`；若 `m` 也被淘汰，继续往上找。下标严格增大、值不减，链必然终止（有限），落在某个仍在队列中的 `t` 上，满足 `t > j`、`nums[t] >= nums[j]`。
2. **`j` 已过期**：它不在窗口内，I4 的前提（`j` 在窗口内）不成立。

∎

**命题（队首即最大值）**：设 `x = dq[head]`，则 `nums[x] = max{ nums[j] : i-k+1 <= j <= i }`。

**证明**：由 I3，`x` 在窗口内，所以 `nums[x] <= max`。反过来，任取窗口内的 `j`：若 `j ∈ dq`，由 I2 与 I1，`x` 是最靠前（也是最大）的那个，`nums[x] >= nums[j]`；若 `j ∉ dq`，由 I4 存在 `t ∈ dq` 使 `nums[t] >= nums[j]`，再由 I2 得 `nums[x] >= nums[t] >= nums[j]`。两种情况都有 `nums[x] >= nums[j]`，故 `nums[x] >= max`。两向夹逼取等。∎

**关于「`<=` 还是 `<`」（相等元素留谁）**：队尾淘汰用 `<=` 意味着**相等的旧元素也被新元素淘汰**。这不影响正确性（`nums` 相等，谁当代表都一样），但有两个后果：

| 写法 | 队列内值的形状 | 队列长度 | 影响 |
| --- | --- | --- | --- |
| `while (nums[尾部] <= nums[i])`（本章） | **严格**递减 | 更短（相等只留最新的） | 新元素的「寿命」更长，过期压力小；不需要额外的相等处理 |
| `while (nums[尾部] < nums[i])` | 非严格递减（允许相等） | 更长 | 也能算对（相等的旧值会在过期时被踢掉），但队里堆着相等元素，常数更大 |

> **记住判据**：求**极值**时，两种写法等价；但一旦题目要求「相等元素也要被正确统计次数」（比如计数类变体），就必须先定好「谁代表这一批相等元素」，否则会重复计数 —— 这与 062 §062.3.2 里「等高归谁」是同一个问题的两面。

### 064.3.3 通用解题思路（可迁移的那一层）

本批（060–064）的统一判定语言，在 064 这里补上最后一块：

| 章 | 结构里存什么 | 单调性 | 淘汰规则 1（支配） | 淘汰规则 2（过期） | 谁是答案 |
| --- | --- | --- | --- | --- | --- |
| 060 | 每层的最小值 | 辅助栈单调不增 | 无 | `pop` | 栈顶 |
| 061 | 下标 | 温度单调不增 | 遇到更大者弹栈 | 无 | 被弹出者的答案 |
| 062 | 下标 | 高度单调非递减 | 遇到更矮者弹栈 | 无 | 被弹出者的面积 |
| 063 | 下标（复用 062） | 同 062 | 同 062 | 无 | 每行取 max |
| **064** | **下标** | **值严格递减** | **新元素 `>=` 队尾 → 弹队尾** | **队首滑出 → `head++`** | **队首** |

```
┌──────────── 单调结构的「三问定生死」 ─────────────┐
│ 问 1：谁被支配？（新元素出现时，旧元素里谁"没未来"）│
│       061/062：比新元素矮/高的 → 弹出                │
│       064：比新元素小的 → 从队尾弹出                 │
│ 问 2：谁过期？（时间维度上谁"活到头"了）             │
│       栈类题：没有过期，只有被支配                   │
│       队列类题：队首滑出窗口 → 必须从队首丢弃         │
│ 问 3：谁被结算/谁是答案？                            │
│       弹出时结算（061/062） 或 直接读队首（064）      │
└──────────────────────────────────────────────────────┘
```

**「有支配关系」是单调结构能成立的前提**，而支配关系来自「偏序 + 单调时间」：

```
元素 j 能不能彻底取代元素 i ？
   需要两个条件同时成立：
   ① nums[j] 不劣于 nums[i]   ← 值上的偏序（更大/更小）
   ② j 比 i 活得更久          ← 时间上的单调（下标更大）
   两个都成立 ⇒ i 永远出不了头 ⇒ 可以安全删除
```

### 064.3.4 可扩展性（面试追问的七个方向）

| 追问 | 变化 | 应对 |
| --- | --- | --- |
| 求窗口**最小值** | 极值方向反过来 | 队尾淘汰改成 `>=`、队列内值**严格递增**；骨架一行不变 |
| 同时要窗口的最大值和最小值 | 两个单调队列 | LC 1438：`maxQ` 递减 + `minQ` 递增，用它们维护「极差 ≤ limit」的最长窗口 |
| 窗口**长度不固定**（如在和 ≥ target 的前提下求最短窗口） | 窗口由条件驱动 | 单调队列照样能用：窗口收缩时从队首丢过期元素（LC 862、1696 都是这个套路） |
| 求窗口**中位数** | 不是极值 | **单调队列失效**：中位数没有「又新又大就支配旧的小」这种关系。改用两个堆 / 有序容器 `O(n log k)`（LC 480） |
| 求窗口**第 k 大** | 序而不是极值 | 同上，需要平衡树或分块计数；单调队列只能给出排名第 1 的那个 |
| 查询量远大于一次遍历（静态数组、任意区间 RMQ） | 要 `O(1)` 单次查询 | 稀疏表（ST 表）预处理 `O(n log n)`；单调队列只适用于「窗口单调右移」的在线场景 |
| 数据流 + 任意时刻的滑动窗口 | 无法预知 `n` | 单调队列天然适配（只依赖最近 k 个元素），空间恒为 `O(k)` |

### 064.4.3 为什么「又旧又小」的必须淘汰（支配关系的三段图）

```
情形一：i 比 j 旧（i < j）且 nums[i] < nums[j]
        ┌──────────────────────────────┐
        │ 窗口: … [ i=1(值3) , … , j=4(值5) ] │
        │ 只要 5 还在，3 永远不是最大          │
        │ 而 5 更靠右，会比 3 更晚滑出窗口      │
        │ ⇒ 3 在 4 号入队的瞬间就"死了"         │
        └──────────────────────────────┘

情形二：i 比 j 旧，但 nums[i] > nums[j]
        ┌──────────────────────────────┐
        │ 窗口: … [ i=1(值5) , … , j=4(值3) ] │
        │ 3 比 5 小，但当 5 滑出窗口后，3 可能就是最大 │
        │ ⇒ 3 必须留下（它是"未来的候选"）      │
        └──────────────────────────────┘

情形三：i 比 j 旧，nums[i] == nums[j]（相等）
        ┌──────────────────────────────┐
        │ 留着旧的那个 → 它会更早过期，队列更长  │
        │ 踢掉旧的那个 → 队列更短，答案不变      │
        │ ⇒ 用 <= 淘汰旧的，是新元素的最优选择    │
        └──────────────────────────────┘

    结论：队列里活下来的元素，天然满足「越靠队首越旧、且值越大」
          ⇒  下标递增 + 值递减，两条不变量同时成立
```

## 064.5 双语言实现

### 064.5.1 Java

```java
class Solution {
    public int[] maxSlidingWindow(int[] nums, int k) {
        int n = nums.length;
        if (n == 0 || k <= 0 || k > n) {
            return new int[0]; // 题目保证 1 <= k <= n，这里只是防御
        }
        int[] dq = new int[n];  // 双端队列：存下标，对应值从队首到队尾严格递减
        int head = 0, tail = 0; // 有效区间 [head, tail)
        int[] res = new int[n - k + 1]; // 窗口数 = n - k + 1，不是 n - k
        int idx = 0;

        for (int i = 0; i < n; i++) {
            // ① 队首过期：下标 <= i-k 说明它已经滑出窗口 [i-k+1, i]
            //    用 if 而不是 while 就够：下标严格递增，每轮最多过期一个
            if (head < tail && dq[head] <= i - k) {
                head++;
            }
            // ② 队尾淘汰：nums[dq[tail-1]] <= nums[i] 的都被 i 支配
            //    （更旧、且不更大 → 永远出不了头，也不会更晚过期）
            while (head < tail && nums[dq[tail - 1]] <= nums[i]) {
                tail--;
            }
            // ③ 入队
            dq[tail++] = i;
            // ④ 窗口凑满 k 个才开始产出答案
            if (i >= k - 1) {
                res[idx++] = nums[dq[head]];
            }
        }
        return res;
    }
}
```

### 064.5.2 Go

```go
package main

// maxSlidingWindow 单调队列：队列存下标，对应值从队首到队尾严格递减。
// head/tail 是游标，用定长切片当双端队列，出队/入队都是 O(1) 且不搬数据。
func maxSlidingWindow(nums []int, k int) []int {
	n := len(nums)
	if n == 0 || k <= 0 || k > n {
		return nil // 题目保证 1 <= k <= n，这里只是防御
	}
	dq := make([]int, n) // 存下标（每个下标最多入队一次，长度 n 足够）
	head, tail := 0, 0   // 队列区间 [head, tail)
	res := make([]int, 0, n-k+1)

	for i := 0; i < n; i++ {
		// ① 队首过期：下标 <= i-k 已经滑出窗口
		if head < tail && dq[head] <= i-k {
			head++
		}
		// ② 队尾维护递减：新元素不比队尾小，队尾就永远等不到出头的日子
		for head < tail && nums[dq[tail-1]] <= nums[i] {
			tail--
		}
		// ③ 入队。tail 可能刚回退过，但回退掉的都是已作废的位置，直接覆盖是安全的
		dq[tail] = i
		tail++
		// ④ 窗口满 k 个才产出答案
		if i >= k-1 {
			res = append(res, nums[dq[head]])
		}
	}
	return res
}
```

### 064.5.3 双语言差异批注

| 点 | Java | Go | 对本题的影响 |
| --- | --- | --- | --- |
| 双端队列的载体 | `new int[n]` + `head/tail`，或 `ArrayDeque<Integer>` | `make([]int, n)` + `head/tail` 游标 | Go **没有内建 deque**，用切片 + 双游标是最地道的写法；`container/list` 是双向链表，每个元素一次堆分配，慢一个数量级 |
| `ArrayDeque` 的坑 | `push/pop` 是**队首**操作，`offerLast/pollLast` 是队尾 | 无对应问题 | Java 里混用 `push`（队首）与 `pollLast`（队尾）会把队列搞成栈语义，答案全错 |
| 结果数组 | `new int[n-k+1]` + 游标 `idx` | `make([]int, 0, n-k+1)` + `append` | Go 预分配 `cap` 可以完全避免扩容；用 `append` 而不预先 `make` 定长，是为了让「空输入返回 nil」更自然 |
| 空队列判定 | `head < tail` | `head < tail` | 两语言一致；**都不能用「值为 0」判空**（值可能就是 0） |
| 索引回退覆盖 | `dq[tail++] = i` | `dq[tail] = i; tail++` | Go 没有后置自增，必须写成两行；顺序写反会造成覆盖错误 |
| 整数溢出 | 不涉及（只比较和取值） | 同 | 本题没有 `long` 需求，这一点与 062（`h × w` 接近 int 上界）不同 |

func brute(nums []int, k int) []int {
	n := len(nums)
	if n == 0 || k <= 0 || k > n {
		return nil
	}
	res := make([]int, 0, n-k+1)
	for i := 0; i+k <= n; i++ {

			if nums[j] > m {
				m = nums[j]
			}
		}

	}

## 064.6 复杂度与常见坑

### 064.6.1 复杂度推导（摊还分析，必须能自己推）

- **时间 O(n)**：
  - 外层循环 `n` 次。
  - 「队首过期」每轮最多执行一次（`if`，不是 `while`）→ 总计 `<= n` 次。之所以最多一次，是因为下标严格递增，每轮窗口只右移一格，最多一个新下标滑出。
  - 「队尾淘汰」每次执行都弹掉一个下标，而每个下标**只入队一次**，所以总弹出次数 `<= n` → 总计 `O(n)`。
  - 因此总时间 `O(n)`，**摊还**分析的核心仍是那句：**用入队次数给出队次数封顶**。
- **空间 O(k)**（不算输出）：
  - 队列里最多装 `k` 个下标 —— 因为队列内所有下标都在窗口 `[i-k+1, i]` 内（不变量 I3），窗口只有 `k` 个位置。
  - 本章代码开的是 `new int[n]`，**这是为了省掉环形缓冲区的取模运算**，实际使用长度不超过 `k`。想严格做到 `O(k)` 空间，就开 `new int[k]` 并用 `(head+1) % k` 之类的环形索引。
- **对比**：暴力 `O(nk)`；堆 `O(n log n)`；平衡树 `O(n log k)`；ST 表 `O(n log n)` 预处理 + `O(1)` 查询。单调队列是**唯一同时做到 `O(n)` 时间与 `O(k)` 空间**的方案。

### 064.6.2 九个真实踩过的坑

1. **结果数组长度写成 `n - k`** —— 漏掉最后一个窗口。正确是 `n - k + 1`（6 个窗口的例子会只输出 5 个）。
2. **窗口没满就输出** —— 少写 `if (i >= k - 1)`，前 `k-1` 轮就会往结果里塞值，整个数组错位。
3. **忘记判队首过期** —— 递减序列（`[9,8,7,6,5], k=3`）会一直输出 9，因为队首早就滑出窗口了却还在被读。
4. **过期判断写成 `<` 而不是 `<=`** —— `dq[head] <= i - k` 才是「已滑出」。写成 `<` 会让刚刚滑出的那个下标多留一轮，输出过期值。这是本章最隐蔽的 off-by-one。
5. **存值不存下标** —— 没有下标就无法判断「它出没出窗口」，题目一需要过期判断就废。**单调队列/栈里永远存下标。**
6. **用 `0` 或 `-1` 当「队列为空」的哨兵** —— 元素本身可能就是 0 或 -1（题面值域包含负数）。必须用 `head < tail` 判空。
7. **`tail` 回退后不敢覆盖** —— 担心 `dq[tail] = i` 会覆盖有效数据。其实回退掉的都是「已作废」的槽位，覆盖是安全的；**但入队顺序必须是「先回退、后写入、再 `tail++`」**。
8. **Java 里 `ArrayDeque` 的 `push/pop` 是队首操作** —— 与 `offerLast/pollLast`（队尾）混用会变成栈语义。要么全程用 `offerLast/pollFirst/pollLast`，要么自己用数组 + 游标。
9. **Go 里用 `container/list`** —— 每个元素一次堆分配 + 接口装箱，`10⁵` 规模下比数组游标慢一个数量级。标准库里「没有 deque 类型」不等于「必须用链表」。

### 064.6.3 面试官最爱追问的三个问题

**Q1：为什么这是 O(n)？队尾那个 `while` 看起来可能弹很多次。**

> 「是摊还 O(n)。每个下标只会入队一次，所以出队次数总和不超过 n；队尾 `while` 的每一次迭代都恰好弹掉一个下标，因此所有 `while` 加起来不超过 n 次。队首过期那条更简单 —— 我用的是 `if` 而不是 `while`，因为窗口每轮只右移一格，最多一个新下标滑出，所以它本身最多 n 次。两者相加就是 O(n)。这和 061/062 的论证是同一句话：**用『入队次数』给『出队次数』封顶。**」

**Q2：为什么不能像「滑动窗口求和」那样，进一个、减一个？**

> 「因为 `max` 没有逆运算。求和能这么做，是因为加法有减法这个逆运算：滑出一个元素就从和里减掉它。但最大值被移走之后，你无法 O(1) 知道第二大的还在不在窗口里 —— 你必须重新扫一遍，或者用一个能记住顺序的结构。这也是为什么所有『滑窗极值』题都要引入额外结构（单调队列 / 堆 / 平衡树），而『滑窗求和』只要一个变量。」

**Q3：如果窗口大小不固定，或者要求窗口中位数，你的解法还够吗？**

> 「分两种情况。**变长窗口**（比如求『极差 ≤ limit 的最长子数组』，LC 1438）单调队列照样能用：窗口由条件驱动、只会单调右移，队首过期规则换成『下标 < 左端点』即可；如果同时要 max 和 min，就开两个队列（一个递减、一个递增），这正是 LC 1438 的标准解法。
> **中位数就完全不行了**：单调队列的威力来自支配关系 —— 『又新又大』的元素可以彻底淘汰『又旧又小』的元素。中位数没有这种偏序，任意元素都可能是中位数，所以只能退到 `O(n log k)` 的两堆 / 有序容器（LC 480）。**这是判断『能不能用单调结构』的通用判据：先问存不存在支配关系。**」

## 附：本章小结（可背走的三句话）

```
① 单调队列的本质是"支配关系"：又旧又小的元素被又新又大的元素彻底取代，可以立刻删除
② 两端各管一件事：队首丢弃过期（head++），队尾丢弃被支配（tail--），队首就是窗口最大值
③ 复杂度靠摊还封顶：每个下标入队一次 → 出队总次数 ≤ n；空间 O(k)，队列里只装窗口内的候选
```
