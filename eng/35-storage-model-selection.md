# 35. 数据模型决定存储：八类存储的本质

> **状态**：`已完成（初稿）` ｜ **所属**：第六部分 · 存储选型：状态该放哪 ｜ **编号**：35 / 52
> **本章定位**：存储选型 90% 的错误不是「选了个差产品」，而是「用 A 类的数据模型去承载 B 类的访问模式」。这一章给你一套**先问访问模式、再问产品**的顺序，一张能贴进设计文档的映射表，以及九类存储各自的「后悔案例」。

## 35.1 引子：三次选错存储的账单

**事故一：把心跳写进 MySQL（2024-06，某 IoT 平台）**

设备心跳 12 亿行/月，直接写进 MySQL 单表。16 个月后单表 4.7 TB，二级索引 2.3 TB，buffer pool 命中率从 99.6% 掉到 91%。某天运营跑了一句「统计上月活跃设备数」，`COUNT(*)` 把 buffer pool 冲干净，主库 IO util 打满 100%，订单服务连带超时 **38 分钟**，当天 GMV 损失约 **210 万元**。

**事故二：用文档库做四层权限递归（2024-11，某 SaaS）**

权限模型是「用户 → 角色 → 资源 → 组织」，放在 MongoDB 里用 `$lookup` 做递归。单次鉴权 **1.9 秒**，QPS 800 时 Mongo 的 CPU 打满，全站登录失败 **22 分钟**，影响 6.4 万用户，续费谈判丢了两单。

**事故三：把 Elasticsearch 当主库（2025-02，某内容平台）**

编辑改完标题，前台 1 秒内看不到；更糟的是发布流程以 ES 写入成功为准，refresh 还没发生就返回了「发布成功」。一周内相关客诉 **1,100 起**，最后加了一层 MySQL 才收场。

> 🩸 三次都不是产品烂，是**模型与访问模式错配**。选型的第一性问题不是「哪个数据库强」，而是「我的数据长什么样、我要怎么查它」。

## 35.2 到底是什么：存储选的是四件事，不是一张 Logo

**定义**：一个存储系统的本质由四件事决定——

1. **数据模型**：数据怎么组织（行 / 文档 / 键值 / 点边 / 时间序列 / 倒排 / 向量 / 对象）。
2. **访问路径**：允许你怎么查，靠什么索引，能不能 join、能不能多跳。
3. **一致性模型**：写完什么时候、被谁看到；能不能跨行/跨文档原子。
4. **扩展单元**：加机器时按什么切（无 / 主从 / 分片键 / 一致性哈希 / 副本）。

产品只是这四件事的一种打包。先钉死四个常见误解：

| 你以为的 | 为什么错 | 不做会怎样 |
| --- | --- | --- |
| 「NoSQL 比 MySQL 快」 | 快的是「按 key 取整块」或「顺序写 LSM」，代价是查询能力与事务 | 拿 Mongo 做多维报表，最后全表扫，P99 从 50ms 变 8s |
| 「一个 PG 能通吃」 | PG 能存 JSON，不等于它是文档库；能装向量插件，不等于它是向量库 | JSON 列上做全文检索，CPU 打满还查不准 |
| 「先选产品，再设计表」 | 产品决定了你**只能**怎么建模 | 选了 ES 才发现业务要跨文档事务 |
| 「有关系就该上图」 | 图的价值在**多跳遍历**，不在「表之间有外键」 | 花 68 万/年跑 90% 都是 1 跳的点查 |

### 八种访问模式清单（选型时逐条打勾）

| # | 访问模式 | 判定问句 | 首选 | 备选 | 明确不要用 |
| --- | --- | --- | --- | --- | --- |
| 1 | **点查** | 「按唯一 ID 取一条，QPS 多少？」 | KV、关系 | 文档 | 搜索（相关性用不上，白付倒排成本） |
| 2 | **范围** | 「按时间/ID 区间取一批，要不要排序？」 | 关系（B+ 树）、时序 | 宽列 | KV（除非用 ZSet 之类有序结构） |
| 3 | **聚合** | 「group by 几个维度、扫多少行、要多快？」 | 列存 | 关系（小数据/预聚合表） | KV、文档（只能应用层硬算） |
| 4 | **全文** | 「要分词、相关性排序、高亮吗？」 | 搜索 | PG GIN（千万级以内） | MySQL `LIKE '%x%'` |
| 5 | **多跳** | 「几跳？每跳扇出多少？要不要路径？」 | 图（≥3 跳） | 递归 CTE（≤3 跳）、应用层 BFS | 关系库硬递归到 5 跳 |
| 6 | **时序** | 「写多读少？按时间窗口降采样？TTL？」 | 时序库、列存 | 宽列 | 关系库单表无限长 |
| 7 | **大对象** | 「单对象多大？要不要 CDN/直传？读多还是写多？」 | 对象存储 | 文件系统 | 数据库 BLOB（备份会被撑爆） |
| 8 | **向量** | 「top-k 语义召回？过滤条件多吗？删除频繁吗？」 | 向量库 | pgvector（千万级以内） | 关系库全表算余弦 |

> 💡 **顺序不能反**：先写「访问模式清单」，再写「候选产品」。反过来做，你会在 PoC 阶段才发现「这个产品不支持我最重要的那条查询」，而这时架构图已经画完了。

## 35.3 结构图：六步选型流程

```
业务问题
  │
  ├─ ① 访问模式：怎么查？点/范围/聚合/全文/多跳/时序/大对象/向量
  │      └─ 把每条查询的 QPS、P99、返回行数写出来（不许写"若干"）
  ├─ ② 数据形状：一行多宽？嵌套多深？大文本/数组/二进制？
  ├─ ③ 一致性：写完必须立刻读到？能忍几秒？要不要跨实体原子？
  ├─ ④ 规模与增长：3 年多少 TB？峰值写 QPS？单分区上限？
  ├─ ⑤ 运维能力：团队现在养几个组件？能接受再加一个有状态集群吗？
  └─ ⑥ 退出成本：数据怎么迁走？有没有厂商锁死？
        │
        ▼
   候选 2~3 个 ──► PoC（真实数据分布 + 真实查询 mix + 故障注入）
        │
        ▼
   打分（功能/性能/成本/运维/退出）──► 决策记录（ADR）──► 落地
```

**这张图的杀伤力在 ① 和 ⑥**：① 逼你把「查询」写具体，⑥ 逼你想「三年后怎么跑」。中间四步都是可以算的，只有这两步最容易被跳过。

## 35.4 九类存储：一张总表 + 三个最贵的误用

> 业界常说「八类」，实际数下来是九类。把搜索算作「索引型存储」、向量算作「检索型存储」，就是八类；但它们的失效模式完全不同，工程上必须分开看。

| 类别 | 数据模型 | 强项 | 弱项 | 真实误用（后果） |
| --- | --- | --- | --- | --- |
| **关系** MySQL/PG | 行 + 强类型列 + B+ 树 | 事务、约束、join、多维查询、生态 | 水平扩展难、宽表/大文本差、DDL 有代价 | 12 亿行心跳写单表，4.7TB，一次 COUNT 打挂主库 **38 分钟** |
| **文档** MongoDB | BSON 文档 + 集合 | 嵌套结构、schema 灵活、单文档原子 | 跨文档事务贵、join 弱、大集合吃内存 | 四层权限用 `$lookup`，鉴权 **1.9s**，登录失败 **22 分钟** |
| **宽列** Cassandra/HBase | partition key + clustering + 列族 | 写吞吐、线性扩展、海量稀疏 | 查询必须按分区设计、无 join、聚合弱 | 按 `user_id` 分区却按时间查，扫 200 节点，P99 **12s** |
| **KV** Redis/etcd | key → value（+ TTL） | O(1)、亚毫秒、简单 | 无查询语言、内存贵、持久化弱 | Redis 当订单唯一存储，主从切换丢 **40 分钟 / 2.3 万单** |
| **图** Neo4j/Nebula | 点 + 边 + 属性 | 多跳、路径、免索引邻接 | 全量聚合弱、写入放大、运维重 | 90% 是 1 跳点查，仍买了 **68 万/年** 集群 |
| **时序** InfluxDB/Timescale | 时间戳 + tag + field | 高写入、时间窗口、降采样、TTL | 乱序写、高基数 tag、更新删除难 | 设备 ID 做 tag，基数 **1,200 万**，内存 OOM 每小时一次 |
| **搜索** ES/OpenSearch | 倒排 + doc_values | 全文、相关性、聚合、模糊 | 近实时（默认 1s）、更新贵、深分页 | ES 当主库，refresh 前读不到，客诉 **1,100 起** |
| **向量** Milvus/Qdrant | 向量 + ANN 索引 | 语义召回、多模态 | 近似、吃内存、删除/更新难 | 删文档不删向量，Agent 报已下架产品价格，赔付 **14 万** |
| **对象** S3/OSS/MinIO | 对象 + bucket + 元数据 | 海量、便宜、11 个 9 持久性 | 无查询、无事务、延迟高、list 慢 | 2 亿个 PDF 靠 `list` 找文件，一次导出跑 **6 小时** |

### 35.4.1 关系库：默认选项，但不是万能选项

关系库的护城河是**约束 + 事务 + 优化器**。只要你的写集合能用「一个连接 + 一个事务」覆盖，且查询维度不超过 4 个，它通常是最省心的选择。它真正不擅长的只有三件事：单表无限增长、超高写入（单机写 TPS 上限几千到一万）、以及「一行几百 KB 的大文本/二进制」。

```sql
-- 关系建模的关键：热字段拆列，冷字段/快照进 JSON，且 JSON 只读
CREATE TABLE `order` (
  id           BIGINT UNSIGNED NOT NULL COMMENT '雪花 ID',
  order_no     CHAR(26)        NOT NULL COMMENT '业务单号，对外可见',
  user_id      BIGINT UNSIGNED NOT NULL,
  status       TINYINT         NOT NULL DEFAULT 10 COMMENT '10待支付 20已支付 30已发货 40完成 50关闭',
  total_amount DECIMAL(18,2)   NOT NULL,
  currency     CHAR(3)         NOT NULL DEFAULT 'CNY',
  receiver     JSON            NOT NULL COMMENT '收货信息快照，下单后只读',
  created_at   DATETIME(3)     NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
  updated_at   DATETIME(3)     NOT NULL DEFAULT CURRENT_TIMESTAMP(3) ON UPDATE CURRENT_TIMESTAMP(3),
  PRIMARY KEY (id),
  UNIQUE KEY uk_order_no (order_no),
  KEY idx_user_created (user_id, created_at),
  KEY idx_status_created (status, created_at)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci;
```

> ⚠️ JSON 列不是「文档库替代品」：它不能建普通二级索引（只能建生成列或函数索引），更新是整列重写，大 JSON 会把行溢出页撑大。

### 35.4.2 文档库：以「聚合」为单位读写

文档库的正确用法是：**一次查询取回一个完整聚合**（一篇文章 + 它的段落 + 标签），且这个聚合不会被多个写者并发修改。错误用法是把它当关系库：拆成 8 个集合再 `$lookup` 拼回来。

```javascript
// 正确：文章 + 段落是一个聚合，永远一起读；作者是引用，单独变
db.article.insertOne({
  _id: ObjectId(),
  slug: "storage-35",
  title: "数据模型决定存储",
  tags: ["storage", "modeling"],
  author: { id: 1001, name: "老张" },          // 冗余少量字段，避免每次 join
  blocks: [                                     // 内嵌：总大小 < 16MB 上限
    { type: "p",    text: "存储选型选的是四件事……" },
    { type: "code", lang: "sql", text: "CREATE TABLE ..." }
  ],
  stats: { views: 12034, likes: 87 },
  publishedAt: ISODate("2026-03-01T08:00:00Z"),
  schemaVersion: 3
});
db.article.createIndex({ slug: 1 }, { unique: true });
db.article.createIndex({ tags: 1, publishedAt: -1 });
db.article.createIndex({ title: "text", "blocks.text": "text" });
```

### 35.4.3 宽列、KV、图、时序、搜索、向量、对象：一句话判据

- **宽列**：你能提前列出所有查询，且每个查询都能落到「一个分区 + 一个 clustering 范围」。
- **KV**：你只需要「按 key 取整块」，且能接受它**不是数据库**（见第 37 章）。
- **图**：核心查询是 3 跳以上的路径/递归，且关系本身就是答案。
- **时序**：写入是 append-only，查询永远带时间窗口，老数据要 TTL。
- **搜索**：你要的是「相关性排序」，不是「精确匹配」；它永远是派生索引，不是权威源。
- **向量**：你要的是「语义相似 top-k」，且能接受近似召回与删除延迟。
- **对象**：单对象 ≥ 1MB、只按 key 存取、要 CDN/直传/生命周期。

## 35.5 双修对照：同一套选型方法，多三类数据

| 维度 | 传统系统 | Agent 系统 | 同 or 异 |
| --- | --- | --- | --- |
| **机制本体** | 按访问模式选模型 | 多三类：向量、事件流、大对象（artifact） | **方法论完全相同**，候选集扩大 |
| **唯一键** | `order_id` / `user_id` | `run_id` / `step_id` / `chunk_id` / `content_hash` | 结构相同，键的含义变 |
| **失败模式** | 慢查询、热点、容量满 | 加：写放大、向量与原文不一致、embedding 版本漂移 | 多两类，见第 39 章 |
| **恢复方式** | 备份 + binlog 回放 | 原文是权威源，向量/摘要/缓存**可重建** | 原则相同：派生数据不必备份 |
| **验证方法** | EXPLAIN + 压测 + 行数核对 | 加：召回率、引用命中率、向量条数对账 | 指标扩展 |
| **成本结构** | 存储 + IOPS | 加：向量内存、事件写入、token | 结构不同 |

**完全相同、可以直接复用的部分**：

1. **访问模式清单**——把「点查/范围/聚合/全文/多跳/时序/大对象/向量」换成 Agent 的查询，照样成立。
2. **容量算法**——行数 × 行宽 × 副本 × 索引放大 × 增长（第 40 章），只是「行」变成了 event/chunk。
3. **权威源原则**——谁是真身、谁是派生，必须先写死。
4. **派生数据可重建**——这条对 ES 索引、物化视图、向量索引一视同仁。

**Agent 侧真正的差异只有一个：写放大**。一次 Run 产生的数据：

```
1 条 run 记录（2KB）
+ 平均 42 条 step event（每条 1.5KB）        = 63KB
+ 1 份 prompt（8KB）+ 1 份 completion（2KB）  = 10KB
+ 3 个工具结果（合计 30KB）                   = 30KB
+ 12 个 chunk 的 embedding（每个 6KB）        = 72KB
────────────────────────────────────────────
约 177KB / run；100 万 run/月 ≈ 177GB/月 ≈ 2.1TB/年（单副本）
```

传统订单一次写约 2KB，**差 88 倍**。这就是为什么 Agent 团队不能照抄「订单表」的建模习惯：事件表必须按时间分区、prompt 大字段要外置到对象存储、embedding 要能整批重建。

> 💡 **一个反直觉结论**：Agent 系统里最贵的往往不是向量库，而是**事件表**。向量是「一份内容一个向量」，事件是「一次交互几十条」，增长速度快一个量级。

## 35.6 会在哪炸：失效模式清单

| 现象 | 根因 | 怎么查 | 怎么修 | 怎么防复发 |
| --- | --- | --- | --- | --- |
| 单表越大越慢，加索引也没用 | 热数据超出 buffer pool，随机 IO | `innodb_buffer_pool_read_requests` vs `reads`；命中率 < 99% | 归档冷数据 / 分区 / 换列存 | 容量水位 + 增长预测进季度评审 |
| 查询 P99 突然 10 倍 | 执行计划走错索引 / 隐式转换 | `EXPLAIN ANALYZE`、`performance_schema` 行扫描数 | 改 SQL / 加联合索引 / 强制索引 | 慢查询门禁：rows_examined/rows_sent > 100 报警 |
| 文档库 CPU 打满 | `$lookup` 递归 + 无索引 | `explain("executionStats")` 看 `totalDocsExamined` | 改内嵌 / 预计算 / 换图或关系库 | 评审时禁止跨集合递归 |
| 搜索内容「改了看不到」 | refresh 间隔 + 以 ES 为写成功标准 | 对比 MySQL 与 ES 的 `updated_at` | 写库为准，ES 异步刷新 | 权威源写进 ADR |
| 时序库 OOM | tag 基数爆炸（设备 ID/用户 ID 做 tag） | `show tag cardinality` / 内存曲线 | 高基数字段改 field 或拆表 | 建模规范：tag 只放低基数枚举 |
| 向量召回「答非所问」 | embedding 模型换版未重建 / 删除未同步 | 抽样比对原文与向量条数 | 全量重建 + 墓碑删除 | 模型版本写进索引名 |

## 35.7 怎么验证：PoC 只做三件事

**第一，用真实数据分布**。不要拿 1 万行测 1 亿行：B+ 树从 2 层变 3 层，buffer pool 命中率会断崖。至少灌入生产 3 个月的数据量，且保持相同的字段长度分布（用 `SELECT AVG(LENGTH(...))` 先算）。

**第二，用真实查询 mix**。把生产慢查询日志 Top 50 按 QPS 加权，做成压测脚本；读写比、点查/范围比必须一致。只压「按主键查」的 PoC 等于没压。

**第三，注入真实故障**。kill 主库、拔网线、磁盘写满、副本延迟 30 秒，看它降级成什么样。

```sql
-- 1) 谁在扫全表：按扫描行数排序
SELECT object_schema, object_name, index_name,
       count_star, sum_rows_examined, sum_timer_wait/1e12 AS total_sec
FROM performance_schema.table_io_waits_summary_by_index_usage
WHERE object_schema = 'order_db'
ORDER BY sum_rows_examined DESC
LIMIT 20;

-- 2) 表实际占用：数据 + 索引 + 碎片，别只看行数
SELECT table_name,
       ROUND(data_length /1024/1024/1024, 2) AS data_gb,
       ROUND(index_length/1024/1024/1024, 2) AS index_gb,
       ROUND(data_free   /1024/1024/1024, 2) AS free_gb,
       table_rows
FROM information_schema.tables
WHERE table_schema = 'order_db'
ORDER BY data_length + index_length DESC;
```

**观测四个指标**：每种访问模式的 P99、`rows_examined / rows_returned`（>100 就是索引设计有问题）、缓存命中率、存储放大比（实际占用 / 裸数据）。

## 35.8 用什么工具：默认 + 例外

| 需求 | 首选 | 备选 | 不要用 |
| --- | --- | --- | --- |
| 交易/账务/配置 | MySQL 8.0 / PostgreSQL | — | 任何最终一致的存储 |
| 内容/目录/商品详情 | MySQL + JSON 列 | MongoDB | 纯文档库存账务 |
| 海量写入 + 按分区查 | Cassandra / HBase | TiDB | 单机 MySQL |
| 缓存/会话/计数 | Redis | Memcached | Redis 当唯一存储 |
| 权限/血缘/多跳 | Neo4j / NebulaGraph | 递归 CTE（≤3 跳） | 5 跳以上硬递归 |
| 指标/日志/大屏 | ClickHouse / 时序库 | ES（日志检索） | MySQL 做 OLAP |
| 全文/站内搜索 | Elasticsearch / OpenSearch | PG GIN | `LIKE '%x%'` |
| 语义检索 | Milvus / Qdrant / pgvector | ES kNN | 关系库全表算余弦 |
| 图片/PDF/模型权重 | S3 / OSS / MinIO | — | 数据库 BLOB |

**自研边界**：只有「访问模式确实特殊 + 现成产品都验证过不行」才自研存储。自研一个 KV 容易，自研它的**备份、扩缩容、故障恢复、监控**要三年。

## 35.9 一页速记

| 关键词 | 必须记住的结论 |
| --- | --- |
| 选型顺序 | 访问模式 → 数据形状 → 一致性 → 规模 → 运维 → 退出成本，最后才是产品 |
| 四件事 | 数据模型 / 访问路径 / 一致性模型 / 扩展单元，产品只是打包 |
| 关系库 | 默认选项；死于单表无限增长、超高写入、大字段 |
| 文档库 | 以聚合为单位读写；跨集合递归是自杀 |
| 宽列 | 先定查询，再定分区键；查询之外的能力一律没有 |
| KV | 不是数据库；持久化 ≠ 不丢数据 |
| 图 | 3 跳以上、路径是答案才上图；1~2 跳用邻接表 |
| 时序 | tag 只放低基数；高基数 tag 等于 OOM |
| 搜索 | 近实时派生索引，永远不是权威源 |
| 向量 | 近似召回 + 吃内存 + 删除难；必须能整批重建 |
| 对象 | 只按 key 存取；list 不是查询 |
| 双修 | Agent 多向量/事件/大对象；最贵的是事件表，不是向量库 |

## 35.10 自检题

1. **业务说「我们要存用户行为，将来可能按任意维度分析」，你怎么回？**
   > 答案要点：① 「任意维度」不是访问模式，逼他给出 Top 5 查询和 QPS；② 行为数据 append-only，先落对象存储/列存，按已知维度建 2~3 张宽表；③ 不要为「将来可能」选一个现在运维不了的产品；④ 预留原始明细，将来可以重建任何索引。

2. **为什么「有关系」不等于「要上图」？给一个量化判据。**
   > 答案要点：图的价值在遍历时「代价与全图规模无关」。如果 95% 的查询是 1~2 跳、每跳扇出 < 20，邻接表 + 批量 `IN` 查询的延迟与图库差距在 10ms 内，而图库要多养一个有状态集群。判据：3 跳以上查询占比 > 30%，或需要路径/最短路径/环路检测，才考虑上图。

3. **PoC 时用 10 万行数据跑得很欢，上线 3 个月就崩，最可能漏了什么？**
   > 答案要点：① 数据分布（字段长度、基数、热点 key）；② 索引从内存装得下变成装不下（buffer pool 命中率断崖）；③ 真实查询 mix（只压了点查）；④ 写放大与副本延迟；⑤ 故障注入（主从切换、磁盘满）。
