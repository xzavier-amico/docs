## 51.1 为什么需要手册：故障时的三类时间浪费

一次 P1 故障的平均耗时分布（某平台 2025 年 47 次 P1 统计）：

| 阶段 | 占比 | 典型浪费 |
| --- | --- | --- |
| **发现** | 12% | 告警太吵没人看；或指标没覆盖 |
| **定位** | **58%** | 不知道从哪查；查错方向；等日志 |
| **止血** | 20% | 不敢重启；不会回滚；找不到开关 |
| **恢复验证** | 10% | 不知道「好了没有」的判据 |

**定位占了近 6 成**，而定位慢的原因通常不是技术难，是**没有固定的排查路径**——每个人凭直觉查，查到哪算哪。

手册的价值就是把「直觉」变成「路径」：**同一类症状，永远按同一个顺序查**。这样即使换人值班，也能在 5 分钟内排除掉 80% 的可能。

## 51.2 排障总纲：先分层，再分叉

### 第一原则：先确定「影响面」，再确定「根因」

```text
                 ┌─────────────────────────────┐
                 │ 1. 影响面：谁在用？多严重？    │
                 │    全站 / 单接口 / 单租户 / 单地域 │
                 └──────────────┬──────────────┘
                                ▼
        ┌───────────────┬───────────────┬───────────────┐
        ▼               ▼               ▼               ▼
   全站不可用        单接口异常       单租户异常       偶发/长尾
        │               │               │               │
   查基础设施        查该接口链路      查数据/配置      查慢查询/GC/
   (DNS/LB/DB/     (依赖/代码/       (租户配置/      锁/网络抖动
    中间件)          发布)            配额/数据)
```

**先止血，再定位**——除非定位只需要 30 秒。止血手段的优先级（§51.6）：

```text
回滚 > 开关降级 > 限流/摘流 > 扩容 > 重启 > 改数据
（前三个通常 1~3 分钟；重启会丢现场，放后面）
```

### 第二原则：任何「慢」都先看四个数

```text
QPS（流量变了吗？）→ RT（哪个分位变慢了？）→ 错误率（是超时还是报错？）→ 饱和度（CPU/内存/连接/线程池）
```

这四个数能把问题空间切成 16 种组合，每一种对应的根因集合都很小。**没有这四个数就开始猜，是排障最大的浪费。**

### 第三原则：区分「自身慢」与「依赖慢」

```text
在入口打点：总耗时 800ms
  ├── 自身逻辑 50ms
  └── 依赖调用 750ms
        ├── DB 600ms  ← 这里
        └── Redis 150ms
```

**没有分段计时的系统，排障只能靠猜。** 这也是为什么第 20 章强调「指标要能拆到依赖」。

## 51.4 六张卡片展开（最危险的六个）

表格只能给方向，下面六个必须给完整路径。

### 卡片 16 · 账不平（最贵的故障）

```text
Step 1  确认范围：哪段时间、哪些业务键、差多少
        SELECT business_key, COUNT(*) c, SUM(amount) s
        FROM ledger_entries
        WHERE created_at BETWEEN ? AND ?
        GROUP BY business_key HAVING COUNT(*) > 1;      -- 重复分录

Step 2  确认方向：长款（多记）还是短款（少记）
        -- 与权威侧（支付渠道/上游）对账文件比对

Step 3  止血：立刻停止该业务的自动写入（开关），避免差异扩大
        ⚠️ 不要先改数据——先保留现场（导出差异明细）

Step 4  修复：冲正而非删除（第 3 章）
        INSERT INTO ledger_entries (..., amount, direction, ref_entry_id, reason)
        VALUES (..., 原金额, 'REVERSE', 原分录ID, 'dup_20260915');

Step 5  验证：重跑对账，差异数 = 0；抽 10 笔人工核对
```

> 🩸 **铁律**：账务问题**永远不要 UPDATE/DELETE 原分录**。冲正留下完整审计链，删除会让你在监管问询时无法解释。

### 卡片 21 · 消息堆积

```text
Step 1  看 lag 是「稳定」还是「持续增长」
        稳定 → 消费能力刚好不足，扩消费者即可
        增长 → 有卡点，先找卡在哪

Step 2  看单分区 lag：所有分区都涨 = 整体能力不足；单分区涨 = 该分区有热点/毒消息

Step 3  看消费线程栈：是否卡在某个下游调用（DB/HTTP）
        jstack <pid> | grep -A 20 "consumer"

Step 4  看是否有重复重试的同一条消息（日志里同一个 offset/key 反复出现）
        → 毒消息：先转发到 DLQ，让消费继续

Step 5  止血顺序：扩消费者（分区数够）→ 提高批量 → 跳过毒消息 → 降级下游
```

### 卡片 11 · CPU 打满

```bash
# 1. 找进程
top -o cpu | head
# 2. 找线程（Java）
top -H -p <pid>
printf '%x\n' <tid>            # 转 16 进制
jstack <pid> | grep -A 30 "nid=0x<hex>"
# 3. 找热点（Go）
go tool pprof http://localhost:6060/debug/pprof/profile?seconds=30
# 4. 找系统调用（可能是 IO 伪装成 CPU）
pidstat -p <pid> 1 5
```

| 根因 | 特征 | 处理 |
| --- | --- | --- |
| 死循环/正则回溯 | 单线程 100%，栈固定在同一方法 | 摘流 + 热修 |
| 序列化/加密 | CPU 与 QPS 成正比 | 换算法/加缓存 |
| GC | 多线程同时忙，日志有 Full GC | 调堆/查泄漏 |
| 限流器自身 | 限流 QPS 与 CPU 同步上涨 | 见第 17 章 |

### 卡片 6 · 5xx 飙升

```text
Step 1  是否刚发布？（看发布时间与错误开始时间，误差 < 5 分钟 → 高度怀疑）
        → 直接回滚，不要先分析

Step 2  错误是否集中在单实例/单可用区？
        → 摘除，保留现场

Step 3  看错误码与异常栈 Top1
        连接超时 → 下游/池子
        NPE/参数错 → 代码/配置
        磁盘/权限 → 环境

Step 4  看依赖健康度（DB/Redis/MQ/三方）

Step 5  回滚后仍异常 → 不是代码问题，查配置/数据/依赖
```

### 卡片 17 · 卡单

```sql
-- 找出所有超过 SLA 未迁移的单据
SELECT id, status, updated_at, TIMESTAMPDIFF(MINUTE, updated_at, NOW()) AS stuck_min
FROM orders
WHERE status IN ('REFUNDING','SHIPPING','AUDITING')
  AND updated_at < NOW() - INTERVAL 30 MINUTE
ORDER BY updated_at
LIMIT 100;
```

处理顺序：**先看是否有补偿任务/巡检** → 有则手动触发 → 无则按状态机补推一次（幂等）→ 仍失败则进人工队列。

### 卡片 29 · Agent 成本飙升

```text
Step 1  按维度拆：租户 / 模型 / Run / step
        → 是单租户刷量，还是全体上涨？

Step 2  看 token 结构：输入 vs 输出 vs 缓存命中
        输入暴涨 → 上下文累积/检索 k 变大
        输出暴涨 → 模型啰嗦/循环

Step 3  看重试率：失败重试会 3 倍放大成本

Step 4  止血：租户限额 → 模型路由降级 → 关非核心功能 → 全局预算熔断
```

## 51.5 双修对照：同一张表，两套症状

| 维度 | 传统系统 | Agent 系统 | 相同 / 差异根因 |
| --- | --- | --- | --- |
| **「慢」的定义** | P99 延迟 | P99 延迟 + **首 token 时间（TTFT）** + 整轮完成时间 | Agent 多两个阶段 |
| **「错」的定义** | 5xx / 业务失败 | 5xx + **答错（幻觉）** + 拒答不当 | Agent 的错不一定报错 |
| **资源** | CPU/内存/连接 | 以上 + **token 速率（TPM）** + **并发 Run 配额** | 稀缺资源多一层 |
| **成本** | 机器折旧（近似固定） | **每次调用精确计费**，故障可能同时烧钱 | 成本是故障的一等公民 |
| **定位入口** | trace_id | trace_id + **run_id** + step 序列 | 结构相同，多一层 |
| **最常见根因** | 发布/依赖/容量 | 以上 + **prompt 变更** + **模型版本漂移** | Agent 多两个变更源 |
| **止血手段** | 回滚/降级/限流 | 以上 + **切模型** + **关工具** + **强制模板回复** | 手段集扩展 |

**完全相同的部分**：§51.4 的排查方法论（分层 → 影响面 → 分段计时 → 止血优先）、命令清单、告警分级、复盘模板。**这些一条都不用改。**

## 51.6 止血手段优先级表

| 手段 | 生效时间 | 风险 | 适用 | 不适用 |
| --- | --- | --- | --- | --- |
| **回滚** | 1~5 min | 低（回到已知状态） | 发布后出现的任何异常 | 数据/配置问题 |
| **开关降级** | < 1 min | 中（功能缺失） | 非核心功能拖垮核心 | 核心链路本身故障 |
| **限流/摘流** | < 1 min | 中（部分用户失败） | 流量突增、单实例故障 | 全站依赖故障 |
| **扩容** | 3~15 min | 低 | 容量不足 | 代码/数据问题 |
| **切依赖/切模型** | 1~5 min | 中（行为变化） | 单依赖/单供应商故障 | 无备用 |
| **重启** | 1~3 min | **高（丢现场）** | 内存泄漏、僵死 | 需要保留现场时 |
| **改数据** | 5~30 min | **最高（不可逆）** | 数据错误且已止血 | 未确认根因前 |

> ⚠️ **重启前先抓现场**：`jstack`、`jmap`、`pprof`、关键日志。重启会丢掉 90% 的定位线索，而故障很可能复现。

## 51.7 从排障到复盘：把这次的时间变成下次的 5 分钟

每次 P1 之后，只问三个问题：

1. **这次定位花了多久？卡在哪一步？** → 补指标/补命令/补手册
2. **这次止血靠什么？有没有更快的？** → 补开关/补预案
3. **同样的事会不会再发生？** → 改进项 + owner + 截止日期（第 42 章）

**判断复盘有没有价值，只看一个数：改进项闭环率。** 写了 20 条改进项、3 个月后完成 3 条，等于没复盘。

| 时间分布 | 定位占故障总时长 ~58%；手册就是把定位变成路径 |
| 第一原则 | 先定影响面（全站/单接口/单租户/偶发），再定根因 |
| 第二原则 | 任何「慢」先看四个数：QPS / RT 分位 / 错误率 / 饱和度 |
| 第三原则 | 必须有分段计时，否则「自身慢」和「依赖慢」分不清 |
| 止血顺序 | 回滚 > 开关 > 限流 > 扩容 > 重启 > 改数据 |
| 最贵故障 | 账不平：先停写、保现场、冲正不删除、重跑对账 |
| 重启铁律 | 重启前抓 jstack/heap/pprof，否则丢现场 |
| Agent 特有 | 幻觉、工具循环、上下文爆窗、成本飙升、流式卡住 |
| 双修 | 方法论与命令 100% 复用；Agent 多了「答错也是故障」 |
| 复盘 | 只看改进项闭环率，不看报告写得多漂亮 |

## 51.9 自检题

1. **凌晨 2 点告警：某接口 P99 从 200ms 涨到 2s，QPS 没变。你的前三个动作是什么？**
   > 要点：① 按实例拆 P99，看是否集中在少数实例（是 → 摘除并查该实例 GC/IO）；② 看分段计时，确定是自身还是依赖（DB/Redis/三方）；③ 看连接池等待与线程池队列。不要一上来重启——QPS 没变说明不是容量问题，重启会丢现场且很可能复现。

2. **消息堆积，消费者 CPU 只有 10%，lag 持续增长。最可能是什么？为什么扩容没用？**
   > 要点：CPU 低说明消费者不是在算，而是在**等**——等下游（DB/HTTP）或卡在单条毒消息。扩容消费者对「单分区卡住」无效（分区数固定，消费者数不能超过分区数）。正确路径：看单分区 lag 分布 → 看消费线程栈 → 找重复重试的 key → 毒消息转 DLQ。

3. **Agent 平台成本一夜翻 3 倍，但 QPS 只涨了 20%。列出三种排查方向。**
   > 要点：① 按租户/模型拆，看是否单租户刷量或模型路由错（用了贵模型）；② 看 token 结构：输入暴涨（上下文累积/检索 k 变大）还是输出暴涨（循环/啰嗦）；③ 看重试率与失败率（失败重试会成倍放大成本）；④ 看是否有死循环 Run（step 数异常）。止血：租户限额 + 预算熔断 + 路由降级。
