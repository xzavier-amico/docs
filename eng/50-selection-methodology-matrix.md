## 50.1 引子：一次选型，六个月迁移

2024 年，某团队为「削峰」选了 RabbitMQ。理由很充分：社区成熟、文档多、Spring 集成好。

一年后他们要做「消息回溯 + 按 key 顺序 + 亿级堆积」，发现 RabbitMQ 的模型不匹配：

| 需求 | RabbitMQ | 实际后果 |
| --- | --- | --- |
| 消息回溯（重放 3 天前） | 不支持（消费即删） | 只能靠业务表补 |
| 按 key 顺序 | 需单队列单消费者，吞吐上不去 | 大客户订单乱序 |
| 亿级堆积 | 堆积会打爆内存/磁盘 | 大促期间磁盘告警 |
| 多租户隔离 | vhost 粒度太粗 | 一个租户拖垮全部 |

迁移到 Kafka 花了 **6 个月**（双写、切流、回滚预案、消费者重写），期间两次 P2。

复盘时他们承认：**当初选型只对比了「功能有没有」，没对比「模型匹不匹配」和「退出成本」。**

> 💡 **选型的第一性原理**：**你不是在选一个产品，你是在选一套「未来三年的约束」。** 功能可以补，模型不能改。

## 50.2 六步法：把「我觉得」变成「算出来」

```text
① 需求排序        ② 候选清单        ③ 加权打分        ④ PoC 验证
必须/重要/可选      3~5 个            维度 × 权重        真实场景跑通
   │                 │                 │                 │
   ▼                 ▼                 ▼                 ▼
⑤ 总成本核算      ⑥ 退出成本
3 年 TCO          迁移难度/锁定风险
```

### 第一步：需求排序（必须 / 重要 / 可选）

**只写「必须」的硬约束**，其余都是加分项。硬约束通常不超过 5 条：

```text
示例（消息中间件）：
必须：① 支持按 key 顺序 ② 支持 3 天回溯 ③ 堆积 1 亿不崩 ④ 多租户隔离
重要：⑤ 事务消息 ⑥ 生态与团队熟悉度
可选：⑦ 延迟消息 ⑧ 多语言客户端
```

> ⚠️ **硬约束超过 5 条，说明你还没想清楚。** 把它们按「不做会死」排序，砍掉「有了更好」的。

### 第二步：候选清单（3~5 个，不要超过）

候选太多会陷入「比较瘫痪」。经验值：**2 个主流 + 1 个备选 + 1 个「不选」**（自研或现有方案）。

### 第三步：加权打分（给公式，不要拍脑袋）

```text
总分 = Σ (维度得分 × 权重)
维度得分 1~5 分；权重之和 = 100%
```

**通用维度与建议权重**：

| 维度 | 权重 | 打分要点 |
| --- | --- | --- |
| 功能匹配（硬约束） | 30% | 硬约束不满足 → 直接淘汰，不进入打分 |
| 性能与容量 | 15% | 按你的目标 QPS/数据量：按峰值 1.3 倍配置，按 3 倍做扩容/压测上限 |
| 运维成本 | 15% | 需要几个专职？故障恢复难吗？ |
| 团队熟悉度 | 15% | 有没有人能 3am 排障？ |
| 生态与社区 | 10% | 活跃度、文档、招聘难度 |
| 成本（3 年 TCO） | 10% | 机器 + 人力 + 托管费 |
| 退出成本 | 5% | 迁移难度、数据锁定 |

> 💡 **硬约束用「淘汰制」，不用「扣分制」**：不满足硬约束的直接出局，避免「功能差一点但其他分高」的伪最优。

### 第四步：PoC（不是 demo）

**PoC 必须跑真实场景的三个最狠的点**：

| PoC 项 | 怎么做 | 通过标准 |
| --- | --- | --- |
| 目标负载 | 按生产 1.5 倍 QPS 压 30 分钟 | P99 达标、无错误 |
| 故障注入 | kill 一个节点 / 断网 / 磁盘满 | 自动恢复或明确降级 |
| 数据规模 | 灌入生产同量级数据（或 1/10 外推） | 查询/写入不退化 |
| 运维操作 | 扩容、升级、备份恢复 | 有文档、可重复 |
| 成本实测 | 跑一天，按账单外推 | 在预算内 |

> 🩸 **只做 demo 的 PoC 等于没做**：demo 跑通只证明「能启动」，不证明「能扛住」。

### 第五步：3 年 TCO（总算账）

```text
TCO = 机器/托管费 + 人力（运维 + 开发） + 迁移成本 + 故障成本（预期损失）
```

**人力常被低估**：一个需要专职运维的组件，3 年 ≈ 0.5 人 × 36 个月 × 3 万 = **54 万**，往往超过机器成本。

### 第六步：退出成本（最容易被忽略）

| 退出维度 | 问题 | 高分（易退出） | 低分（被锁死） |
| --- | --- | --- | --- |
| 数据 | 能否导出为标准格式？ | 开放格式 | 私有格式 |
| 协议 | 是否兼容标准协议？ | Kafka 协议 / SQL | 私有 SDK |
| 代码 | 业务代码是否依赖厂商 API？ | 抽象层隔离 | 到处 `vendor.xxx()` |
| 人才 | 市场上好不好招？ | 主流技术 | 冷门 |

> 💡 **降低退出成本的最实用手段**：**在业务与中间件之间加一层薄抽象**（如 `MessageBus` 接口），哪怕只封装 5 个方法。迁移时只改适配器，不改业务。

## 50.3 五张选型矩阵

### 矩阵一：消息中间件

| 维度（权重） | Kafka | RocketMQ | Pulsar | RabbitMQ | NATS JetStream |
| --- | --- | --- | --- | --- | --- |
| 吞吐（20%） | 5 | 4 | 5 | 2 | 3 |
| 顺序（15%） | 4（分区内） | 5（分区内） | 4 | 2 | 3 |
| 回溯（15%） | 5 | 4 | 5 | 1 | 4 |
| 延迟消息（10%） | 1（需自研） | 5 | 3 | 4 | 2 |
| 事务消息（10%） | 3（仅内部） | 5 | 3 | 1 | 1 |
| 运维成本（15%） | 4 | 4 | 2 | 3 | 3 |
| 生态（15%） | 5 | 3 | 3 | 5 | 2 |

> **读法**：不是选总分最高的，是**先看硬约束**（顺序/回溯/事务），再在剩下的里选运维成本低的。

### 矩阵二：存储

| 场景 | 首选 | 备选 | 别用 |
| --- | --- | --- | --- |
| 事务型业务数据 | MySQL / PostgreSQL | TiDB / OceanBase | MongoDB / Redis |
| 海量写 + 宽表 | Cassandra / HBase | ClickHouse（分析） | MySQL 单表 |
| 缓存 / 会话 | Redis | Memcached | DB 当缓存 |
| 全文检索 | Elasticsearch | OpenSearch | LIKE '%x%' |
| 聚合分析 | ClickHouse / Doris | StarRocks | MySQL 大表 group by |
| 多跳关系 | Neo4j / NebulaGraph | PostgreSQL 递归 CTE | 应用层循环查 |
| 向量检索 | pgvector（<千万） | Milvus / Qdrant | ES 的向量（量大时） |
| 大对象 | S3 / OSS / MinIO | — | DB blob |

### 矩阵三：编排

| 维度（权重） | Temporal | Argo | Airflow | BPMN 引擎 | 自研状态机 |
| --- | --- | --- | --- | --- | --- |
| 长事务（25%） | 5 | 3 | 2 | 4 | 4 |
| 学习成本（20%） | 2 | 4 | 4 | 3 | 5 |
| 运维成本（15%） | 3 | 4 | 3 | 3 | 5 |
| 可观测（15%） | 5 | 4 | 4 | 4 | 2 |
| 业务可视化（15%） | 3 | 3 | 3 | 5 | 2 |
| 与代码耦合（10%） | 5（代码即流程） | 2 | 2 | 2 | 5 |

### 矩阵四：限流熔断

| 维度 | Sentinel | Resilience4j | Envoy/网关 | 自研 |
| --- | --- | --- | --- | --- |
| 功能完整 | 5 | 4 | 4 | 2 |
| 接入成本 | 3（Java 友好） | 5 | 4 | 2 |
| 多语言 | 2 | 1（Java） | 5 | 4 |
| 集群流控 | 5 | 1 | 4 | 3 |
| 可观测 | 5 | 3 | 4 | 2 |
| 运维成本 | 3（需 dashboard） | 5 | 3 | 4 |

### 矩阵五：分布式事务

| 方案 | 一致性 | 性能 | 侵入性 | 适用 |
| --- | --- | --- | --- | --- |
| 2PC/XA | 强 | 低 | 低 | 同库/短事务 |
| TCC | 强（业务） | 中 | **高** | 资金、库存 |
| Saga | 最终 | 高 | 中 | 长流程 |
| 可靠消息 | 最终 | 高 | 中 | 异步解耦 |
| Outbox | 最终 | 高 | 低 | **默认首选** |
| 最大努力通知 | 弱 | 高 | 低 | 对外通知 |

> **默认结论**：**能用 Outbox 就用 Outbox；不能（跨第三方）才用最大努力通知；资金类才上 TCC；长流程才上 Saga。**

## 50.4 选型最贵的三件事

| # | 成本 | 表现 | 量级 | 怎么降 |
| --- | --- | --- | --- | --- |
| 1 | **迁移成本** | 换组件要双写、切流、回滚，业务停摆 | 3~12 个月 | 加抽象层；数据用开放格式 |
| 2 | **人才成本** | 冷门技术招不到人、没人能排障 | 常年 0.5~1 人 | 选主流；至少 2 人熟悉 |
| 3 | **锁死风险** | 业务代码到处是厂商 API | 换供应商 = 重写 | 依赖倒置；SDK 只出现在适配器层 |

**一条经验**：**任何「只有一个人会」的技术，都是定时炸弹。** 选型时问一句「他离职了怎么办」。

## 50.6 双修对照：选型的通用与特有

| 维度 | 传统系统 | Agent 系统 | 相同 / 差异 |
| --- | --- | --- | --- |
| 六步法 | 完全适用 | 完全适用 | **100% 相同** |
| 硬约束 | QPS/延迟/一致性 | 以上 + **TPM/上下文长度/模型能力** | 多一维 |
| PoC | 压测 + 故障注入 | 以上 + **评测集（质量）** | Agent 多「质量」维度 |
| TCO | 机器 + 人力 | 以上 + **按 token 计费**（随量线性） | 成本结构不同 |
| 退出成本 | 数据/协议 | 以上 + **模型供应商锁定**（prompt 与模型强相关） | Agent 多一层 |
| 最贵三件事 | 迁移/人才/锁死 | 同上 + **效果回退**（换模型可能变差） | 同构 + 新风险 |

**Agent 特有的两条选型判据**：

1. **模型可替换性**：prompt 是否绑定了某家模型的特殊格式？能否用统一抽象（如 OpenAI 兼容协议）隔离？
2. **效果可回归**：换模型/换版本后，有没有评测集能证明「没变差」？（第 49 章 §49.8）

## 50.9 打分表模板与算分脚本

打分最容易变成「拍脑袋填数字」。把它落成 JSON + 脚本，谁填的、权重多少、算出来多少，都可追溯。

```yaml
# selection/mq-2026.yaml —— 一次示例选型打分（消息中间件）
title: 消息中间件选型
date: 2026-09-20
weights:
  throughput: 0.20
  ordering: 0.15
  replay: 0.15
  delay: 0.10
  transaction: 0.10
  ops_cost: 0.15
  ecosystem: 0.15
hard_constraints:
  - key: ordering
    min: 4          # 必须支持按 key 顺序
  - key: replay
    min: 4          # 必须支持 3 天回溯
candidates:
  - name: Kafka
    scores: { throughput: 5, ordering: 4, replay: 5, delay: 1, transaction: 3, ops_cost: 4, ecosystem: 5 }
    notes: 延迟消息需自研；事务仅 Kafka 内部
  - name: RocketMQ
    scores: { throughput: 4, ordering: 5, replay: 4, delay: 5, transaction: 5, ops_cost: 4, ecosystem: 3 }
    notes: 延迟/事务都原生；生态弱于 Kafka
  - name: Pulsar
    scores: { throughput: 5, ordering: 4, replay: 5, delay: 3, transaction: 3, ops_cost: 2, ecosystem: 3 }
    notes: 架构先进但运维复杂（BookKeeper）
```

```python
# selection/score.py —— 硬约束淘汰 + 加权算分
import json, sys
from pathlib import Path

def load(p):
    txt = Path(p).read_text(encoding="utf-8")
    if p.endswith(".json"):
        return json.loads(txt)
    import yaml
    return yaml.safe_load(txt)

def evaluate(cfg):
    rows = []
    for c in cfg["candidates"]:
        s = c["scores"]
        # 1) 硬约束：不满足直接淘汰，不参与加权（避免「功能差但总分高」的伪最优）
        failed = [h["key"] for h in cfg["hard_constraints"] if s.get(h["key"], 0) < h["min"]]
        if failed:
            rows.append((c["name"], None, "淘汰：" + ",".join(failed)))
            continue
        # 2) 加权总分
        total = sum(s[k] * w for k, w in cfg["weights"].items())
        rows.append((c["name"], round(total, 2), ""))
    return sorted(rows, key=lambda r: (r[1] is None, -(r[1] or 0)))

if __name__ == "__main__":
    for name, score, note in evaluate(load(sys.argv[1])):
        print(f"{name:<12} {('—' if score is None else f'{score:.2f}'):>6}  {note}")
```

```text
$ python selection/score.py selection/mq-2026.yaml
Kafka         4.10
RocketMQ      4.20
Pulsar        3.70
```

**注意这个结果**：RocketMQ 4.20 与 Kafka 4.10 只差 0.10，**在打分误差范围内**。这时不要机械选第一名，而是回到「退出成本」与「团队熟悉度」做定性判断——**打分的作用是排除明显不合适的，不是替你做最后决定**。本例最终选 Kafka（§50.12），依据是团队已有经验与生态，而不是它的加权分最高。

> 💡 **一个反直觉的结论**：**如果两个候选分数差 < 0.2，说明它们在你的场景下等价**。此时应该选「团队更熟、退出更容易」的那个，而不是纠结小数点。

## 50.10 案例复盘：RabbitMQ → Kafka 的六个月迁移

第 50.1 节那个「选错 MQ」的团队，真实迁移计划如下（已脱敏）。

### 迁移的三个阶段

```text
阶段一（第 1~2 月）：双写 + 影子消费
  - 生产端同时写 RabbitMQ 与 Kafka
  - 新增 Kafka 消费者，只做「影子处理」（写影子表，不产生副作用）
  - 每天比对：RabbitMQ 处理结果 vs Kafka 影子结果

阶段二（第 3~4 月）：按 Topic 灰度切流
  - 按业务域切：先非核心（通知/日志），再核心（订单/支付）
  - 每个 Topic 切流后观察 48 小时，错误率与延迟达标才继续
  - RabbitMQ 保留只读回退能力

阶段三（第 5~6 月）：下线与清理
  - 全量切完，观察 2 周
  - 下线生产者、消费者、运维监控
  - 归档 RabbitMQ 数据（合规要求）
```

### 真实成本（六个月）

| 项 | 成本 | 说明 |
| --- | --- | --- |
| 人力 | 2 人 × 6 月 = 12 人月 | 生产/消费改造 + 运维 |
| 机器 | Kafka 集群（3 broker + 3 zk/kraft）× 6 月 | 约 12 万元 |
| 双跑期间资源 | RabbitMQ 与 Kafka 并行 | 约 6 万元 |
| 故障成本 | 2 次 P2（切流期间消费延迟） | 约 3 万元 |
| **合计** | **约 60~80 万元 + 12 人月** | |

### 如果重来一次，成本可以降到多少

```text
① 一开始就在业务与 MQ 之间加抽象层（MessageBus 接口）
   → 迁移只改适配器，不改 200 处业务代码（省 6~8 人月）
② 选型时把「回溯/顺序/堆积」列为硬约束
   → 根本不会选 RabbitMQ（省全部迁移成本）
③ 用 PoC 压 1 亿条堆积
   → 第 2 周就发现不匹配（省 5 个月）
```

> 🩸 **选型的最大成本不是「买贵了」，是「选错了再换」**。12 人月足够把核心业务重写一遍。

## 50.11 退出成本怎么设计：一层薄抽象（可复用代码）

降低退出成本最有效的手段，是在业务与中间件之间加一层**只包含必要方法**的接口。不要追求「大而全的抽象层」——那本身就是一种锁定。

```go
// internal/port/messagebus.go —— 只抽象「业务真正用到的 4 个方法」
package port

import "context"

type Message struct {
	Key     string            // 分区/顺序键
	Topic   string
	Payload []byte
	Headers map[string]string
}

// MessageBus 是唯一允许业务依赖的消息接口。
// 实现方（kafka/rocketmq/内存）放在 internal/adapter/ 下。
type MessageBus interface {
	Publish(ctx context.Context, msgs ...Message) error
	Subscribe(ctx context.Context, topic, group string, fn func(context.Context, Message) error) error
	Close(ctx context.Context) error
}
```

```go
// internal/adapter/kafka/bus.go —— 唯一出现 kafka-go 的地方
package kafka

import (
	"context"
	"github.com/segmentio/kafka-go"
	"yourorg/app/internal/port"
)

type Bus struct {
	w *kafka.Writer
	r map[string]*kafka.Reader
}

func (b *Bus) Publish(ctx context.Context, msgs ...port.Message) error {
	km := make([]kafka.Message, 0, len(msgs))
	for _, m := range msgs {
		km = append(km, kafka.Message{Topic: m.Topic, Key: []byte(m.Key), Value: m.Payload})
	}
	return b.w.WriteMessages(ctx, km...)
}

func (b *Bus) Subscribe(ctx context.Context, topic, group string, fn func(context.Context, port.Message) error) error {
	r := kafka.NewReader(kafka.ReaderConfig{Brokers: []string{"kafka:9092"}, Topic: topic, GroupID: group})
	b.r[topic] = r
	go func() {
		for {
			m, err := r.FetchMessage(ctx)
			if err != nil { return }
			// ★ 幂等与位点：先处理成功再提交（第 24 章）
			if err := fn(ctx, port.Message{Key: string(m.Key), Topic: m.Topic, Payload: m.Value}); err != nil {
				continue // 交给上层重试/DLQ
			}
			_ = r.CommitMessages(ctx, m)
		}
	}()
	return nil
}

func (b *Bus) Close(ctx context.Context) error {
	for _, r := range b.r { _ = r.Close() }
	return b.w.Close()
}
```

**用 CI 守住这层抽象**：

```bash
# 业务代码里出现具体中间件包 = 破坏退出能力
if rg -n 'segmentio/kafka-go|apache/rocketmq|rabbitmq/amqp091' --type go internal/ \
     | grep -v 'internal/adapter/'; then
  echo "❌ 业务层直接依赖了具体 MQ，请通过 port.MessageBus"
  exit 1
fi
```

**抽象层的边界（别做过头）**：

| 该抽象 | 不该抽象 |
| --- | --- |
| 发布/订阅/确认/关闭 | 分区分配策略、ISR、消费组 rebalance 细节 |
| 消息的 key/headers | 各家特有的延迟消息语法 |
| 错误分类（可重试/致命） | 具体的错误码 |

> 💡 **抽象的目的是「能换」，不是「统一所有差异」**。把差异全部抹平，会得到一个「什么特性都用不了」的最低公分母。

## 50.12 ADR：把「不选什么」也记下来

选型文档通常只写「我们选了 X」，但**真正防复发的是「我们为什么不选 Y」**。半年后新人问「为什么不用 Pulsar」，你能翻到答案。

```markdown
# ADR-014：消息中间件选型

- 状态：已接受（2026-09-20）
- 决策者：架构组 + 后端 TL + SRE
- 关联：负载评估（`docs/capacity/mq-2026.md`）、打分表（`selection/mq-2026.yaml`）

## 背景
订单/支付/通知三条链路需要异步解耦，日峰值 50 万消息，要求：
按 key 顺序、支持 3 天回溯、堆积 1 亿不崩、多租户隔离。

## 决策
选择 **Kafka**（3 broker + KRaft），延迟消息用「时间轮 + 定时表」自研。

## 备选与不选的理由
| 候选 | 得分 | 不选的理由 |
| --- | --- | --- |
| RocketMQ | 4.20 | 延迟/事务原生更好，但团队无运维经验，且生态/招聘弱 |
| Pulsar | 3.70 | 存算分离架构先进，但 BookKeeper 运维复杂度超出团队能力（运维成本项 2 分） |
| RabbitMQ | 淘汰 | 不支持回溯（硬约束不满足）——去年已因此迁移一次，成本 12 人月 |

## 后果（正面/负面）
- 正面：吞吐/回溯满足；生态好、招人容易；团队已有 2 人熟悉
- 负面：延迟消息需自研（约 3 人周）；事务消息仅限 Kafka 内部，跨库仍需 Outbox

## 什么情况下会重新考虑
- 单日消息 > 50 亿 或 需要跨地域强一致
- 团队引入 Pulsar 专职运维（≥1 人）
```

**ADR 的三条纪律**：

| 纪律 | 说明 |
| --- | --- |
| **必须写「不选的理由」** | 否则半年后会有人重新提同一个方案，再讨论一遍 |
| **必须写「什么情况下重新考虑」** | 让决策可被推翻，而不是变成教条 |
| **必须链接证据** | 打分表、PoC 报告、压测数据——没有证据的决策无法复盘 |

> 💡 **ADR 是团队记忆**。模型也会读它——当你让 AI 帮你选型时，一份好的 ADR 能让它直接给出符合团队约束的建议，而不是重新推荐一遍 RabbitMQ。

## 50.13 一页速记

| 关键词 | 必须记住的结论 |
| --- | --- |
| 第一性原理 | 选型不是选产品，是选**未来三年的约束**；功能可补，模型不能改 |
| 六步 | 需求排序 → 候选 → 打分 → PoC → TCO → 退出成本 |
| 硬约束 | ≤5 条；用**淘汰制**不用扣分制 |
| PoC | 必须压目标负载 + 故障注入 + 真实数据量，demo 不算 |
| TCO | 机器 + 人力 + 迁移 + 故障预期；人力常被低估 |
| 最贵三件事 | 迁移成本 / 人才成本 / 锁死风险 |
| 降锁死 | 业务与中间件之间加薄抽象层（5 个方法就够） |
| 默认结论 | 事务首选 Outbox；消息看顺序/回溯；存储先问访问模式 |
| 双修 | 六步法 100% 通用；Agent 多「模型可替换性 + 效果可回归」 |
| 一句话 | **选型的目标不是「最优」，是「最不容易后悔」。** |

## 50.14 自检题

1. **为什么硬约束要用「淘汰制」而不是「加权扣分」？**
   > 要点：加权会把「硬约束不满足」用其他高分补回来，选出「功能差一点但总分高」的伪最优。硬约束是「不做会死」的条件（如顺序、回溯、多租户），不满足就应直接出局。加权只用于「都满足硬约束之后」的优选。

2. **一个组件性能最好、功能最全，但团队没人会运维。你选不选？为什么？**
   > 要点：不选（或只在有明确运维方案时选）。3am 排障能力比峰值性能更决定可用性；运维成本按 3 年算通常超过机器成本。若非要选，必须配「至少 2 人培训 + 托管服务 + 回滚预案」，否则一次故障就抵消所有性能收益。

3. **怎么把「退出成本」从口号变成可执行的设计？**
   > 要点：① 业务只依赖自定义接口（`MessageBus`/`ObjectStore`/`LLMClient`），厂商 SDK 只出现在适配器层；② 数据用开放格式（Parquet/JSON/标准 SQL）；③ 关键路径有「双写 + 切流」预案；④ 定期演练导出/迁移；⑤ 代码 review 时禁止业务层直接 import 厂商包（用 ArchUnit/lint 强制）。
