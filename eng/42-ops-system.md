# 42. 运维体系：值班、Runbook 与事故指挥

> **状态**：`已完成（初稿）` ｜ **所属**：第七部分 · 运维与运营 ｜ **编号**：42 / 52
> **本章定位**：事故的总耗时里，定位占 ~58%、止血占 ~20%，而**组织混乱造成的浪费**（找不到人、两个人同时操作、没人对外沟通）往往被算进「定位」里，实际上是**流程缺失**。本章给一套能落地的最小运维体系：值班、分级、Runbook、指挥、复盘、演练。
> **读法**：§42.4 的 Runbook 模板与角色卡可直接复制；§42.5 的「改进项闭环率」是判断复盘有没有用的唯一标准。

## 42.1 事故现场：40 分钟，三个人同时重启，没人对外说话

2025 年 6 月，某平台一次 P1（核心下单接口 5xx 达 37%）的真实时间线：

| 时间 | 发生了什么 |
| --- | --- |
| 20:04 | 告警群连发 14 条告警（下单错误率、DB 连接数、超时、GC…） |
| 20:06 | 值班 A 在群里问「谁在看？」——**无人应答**（A 是新来的，不熟悉下单服务） |
| 20:11 | 后端 B 被电话叫醒，开始看日志 |
| 20:15 | 运维 C 也进来了，**直接重启了应用**（未通知任何人） |
| 20:16 | 重启后错误率短暂下降，B 认为是「内存问题」，继续观察 |
| 20:22 | 错误率再次上升，B 也重启了一台 |
| 20:25 | **两台实例同时重启 → 剩余实例被打满 → 全站不可用** |
| 20:31 | 客服在群里问「怎么回复客户」，**无人回应** |
| 20:38 | 技术总监进群，指定 B 为指挥，才停止无序操作 |
| 20:44 | 定位到是 DB 连接池配置被一次发布改小（50 → 10） |
| 20:46 | 回滚配置，恢复 |
| 21:10 | 错误率归零，但**对外无任何公告**，客服自行编了说法 |

**总影响 42 分钟**，其中：

| 浪费类型 | 时长 | 原因 |
| --- | --- | --- |
| 无人应答 | 5 min | 值班不认识服务、无升级链 |
| 无指挥、重复操作 | 20 min | 没有 IC（事故指挥）角色 |
| 二次故障（同时重启） | 6 min | 无变更锁、无「一次只动一个变量」纪律 |
| 对外沉默 | 全程 | 没有沟通角色 |
| 定位 | 8 min | 实际上不看告警也能猜到是发布——**但没人看发布记录** |

> 🩸 **这次事故的技术根因只有一行配置，但组织根因有五条。** 复盘时如果只写「配置改小了」，下次还会以另一种形式发生。

## 42.2 精确定义：运维体系是六个可交付物

```text
① 值班表（谁在什么时候负责什么服务）
② 分级标准（什么算 P0/P1，谁有权定级）
③ Runbook（每类故障的固定处置路径）
④ 事故指挥（谁决策、谁沟通、谁操作、谁记录）
⑤ 复盘（时间线 + 根因 + 改进项 + owner + 日期）
⑥ 演练（把 Runbook 跑一遍，而不是等真事故）
```

**六件里缺任何一件，另外五件的效果都会打折**：

| 缺 | 后果 |
| --- | --- |
| 值班表 | 告警没人认领，靠「谁看见谁上」 |
| 分级 | 所有故障都喊 P0，狼来了 |
| Runbook | 每次现场现学，处置时间翻倍 |
| 指挥 | 多人并行操作，二次故障 |
| 复盘 | 同样的问题重复发生 |
| 演练 | Runbook 是纸上谈兵，真用时发现命令都跑不通 |

### 一个必须先统一的定义：什么叫「处理完」

| 阶段 | 判据 |
| --- | --- |
| **已止血** | 核心指标回到 SLO 内，用户可正常使用（≠ 根因已修复） |
| **已恢复** | 所有受影响功能恢复，积压/脏数据清理完 |
| **已闭环** | 根因修复上线 + 改进项完成 + 监控补上（防止复发） |

> 💡 **90% 的团队只做到「已止血」就宣布结束**，于是同一个故障每月来一次。

## 42.3 结构图：一次事故的完整流转

```text
  告警/用户反馈
        │
        ▼
  ┌──────────────┐   5 分钟内
  │ 值班认领      │──────────────┐
  └──────┬───────┘              │ 无人认领 → 自动升级到 backup → TL
         ▼
  ┌──────────────┐
  │ 定级 P0-P3    │   P0/P1 → 立即拉事故群 + 指定 IC
  └──────┬───────┘
         ▼
  ┌──────────────────────────────────────────┐
  │ 事故群（单一信息源）                       │
  │  IC（指挥）  ── 决策、分配、叫停            │
  │  Ops（操作） ── 只做 IC 批准的操作          │
  │  Comms（沟通）── 对内/对外同步              │
  │  Scribe（记录）── 时间线，每 5 分钟一条      │
  └──────┬───────────────────────────────────┘
         ▼
   Runbook：现象 → 判定 → 止血 → 验证 → 升级
         │
         ▼
   已止血 → 恢复 → 根因 → 复盘 → 改进项 → 演练验证
```

**三条纪律**（比工具重要）：

1. **单一信息源**：所有信息进事故群/事故文档，不在私聊里决策。
2. **一次只改一个变量**：同时重启 + 改配置 + 限流，永远不知道是哪个生效。
3. **变更锁**：P0/P1 期间，除 IC 批准，禁止任何与止血无关的发布/变更。

## 42.4 怎么实现：四张表 + 四个模板

### 表一：值班表（跟服务，不跟人）

```sql
CREATE TABLE oncall_service (
    service_id    VARCHAR(64) PRIMARY KEY,     -- order-api, payment-worker
    display_name  VARCHAR(128) NOT NULL,
    tier          TINYINT NOT NULL,            -- 1=核心 2=重要 3=一般
    runbook_url   VARCHAR(512),
    owner_team    VARCHAR(64) NOT NULL
);

CREATE TABLE oncall_rotation (
    id           BIGINT AUTO_INCREMENT PRIMARY KEY,
    service_id   VARCHAR(64) NOT NULL,
    role         ENUM('PRIMARY','BACKUP','MANAGER') NOT NULL,
    engineer     VARCHAR(64) NOT NULL,
    starts_at    DATETIME NOT NULL,
    ends_at      DATETIME NOT NULL,
    handover_note TEXT,                         -- 交接：近期变更/已知风险
    KEY idx_service_time (service_id, starts_at, ends_at),
    KEY idx_engineer (engineer, starts_at)
);

CREATE TABLE oncall_escalation (
    id          BIGINT AUTO_INCREMENT PRIMARY KEY,
    service_id  VARCHAR(64) NOT NULL,
    level       TINYINT NOT NULL,               -- 1=primary 2=backup 3=TL 4=总监
    ack_timeout_sec INT NOT NULL,               -- 该级认领超时（秒）
    target      VARCHAR(64) NOT NULL            -- 个人/组/电话
);
```

**排班四条规则**：

| 规则 | 说明 |
| --- | --- |
| 跟服务不跟人 | 「订单服务值班」而不是「张三值班」——人走服务还在 |
| 必须有 backup | 主值班 5 分钟未认领自动升级 |
| 交接必写 notes | 近期变更、已知风险、未闭环的告警 |
| 新人不能独自值班 | 前 3 个月必须有导师 backup |

### 表二：事故记录

```sql
CREATE TABLE incident (
    id            BIGINT AUTO_INCREMENT PRIMARY KEY,
    title         VARCHAR(256) NOT NULL,
    severity      ENUM('P0','P1','P2','P3') NOT NULL,
    status        ENUM('OPEN','MITIGATED','RECOVERED','CLOSED') NOT NULL,
    started_at    DATETIME(3) NOT NULL,
    mitigated_at  DATETIME(3),
    recovered_at  DATETIME(3),
    closed_at     DATETIME(3),
    ic            VARCHAR(64),                  -- 事故指挥
    comms         VARCHAR(64),
    scribe        VARCHAR(64),
    impact_users  INT,
    impact_orders INT,
    impact_amount BIGINT,                       -- 分
    root_cause    TEXT,
    timeline      JSON,                          -- [{ts, actor, action}]
    detection     ENUM('ALERT','CUSTOMER','INTERNAL','MONITOR') NOT NULL,
    KEY idx_time (started_at),
    KEY idx_sev (severity, started_at)
);
```

> 💡 **`detection` 字段是金矿**：如果 60% 的 P1 是 `CUSTOMER` 发现的，说明你的监控有系统性缺口——这比任何「加个指标」的讨论都有说服力。

### 表三：改进项（复盘的意义在这里）

```sql
CREATE TABLE action_item (
    id          BIGINT AUTO_INCREMENT PRIMARY KEY,
    incident_id BIGINT NOT NULL,
    category    ENUM('PREVENT','DETECT','MITIGATE','PROCESS') NOT NULL,
    description TEXT NOT NULL,
    owner       VARCHAR(64) NOT NULL,
    due_date    DATE NOT NULL,
    status      ENUM('TODO','DOING','DONE','CANCELLED') NOT NULL DEFAULT 'TODO',
    done_at     DATETIME,
    verify_note TEXT,                            -- 怎么证明它有效
    KEY idx_owner (owner, status),
    KEY idx_due (status, due_date)
);
```

**四类改进项缺一不可**：

| 类别 | 回答的问题 | 例子 |
| --- | --- | --- |
| PREVENT | 怎么让它不再发生 | 加配置变更审批 + 上限校验 |
| DETECT | 下次怎么更早发现 | 加连接池使用率告警（1 分钟） |
| MITIGATE | 下次怎么更快止血 | 一键回滚配置 + 开关 |
| PROCESS | 流程哪里有问题 | 值班表补 backup、指定 IC 制度 |

### 模板一：Runbook（完整示例）

```markdown
# Runbook：下单接口错误率上升

## 0. 适用
- 告警：`order_create_error_rate > 5% for 3m`
- 服务：order-api（tier 1）
- 最近更新：2026-10-12（演练验证）

## 1. 现象确认（1 分钟）
1. 打开看板：Order / Error Rate、QPS、P99、DB 连接数
2. 确认影响面：
   - 全站 or 单渠道？ → 看 `channel` 维度
   - 单实例 or 全部？ → 看 `instance` 维度
   - 何时开始？ → 对齐最近一次发布/配置变更时间

## 2. 快速判定（2 分钟）
| 观察 | 最可能原因 | 跳到 |
| --- | --- | --- |
| 刚发布 5 分钟内 | 代码/配置问题 | §3.1 回滚 |
| DB 连接数打满 + 慢查询 | 连接池/慢 SQL | §3.2 |
| 依赖（支付/库存）超时 | 下游故障 | §3.3 降级 |
| 单实例异常，其他正常 | 实例故障 | §3.4 摘流 |
| 流量突增 3 倍+ | 容量/攻击 | §3.5 限流 |

## 3. 止血动作
### 3.1 回滚（首选，1~3 分钟）
kubectl -n prod rollout undo deploy/order-api
# 或平台：发布 → 历史 → 回滚到上一版本
验证：错误率 5 分钟内回落

### 3.2 连接池/慢 SQL
-- 看正在跑的慢查询（> 2s）
SELECT id, user, time, LEFT(info,120) FROM information_schema.processlist
WHERE command='Query' AND time > 2 ORDER BY time DESC LIMIT 10;
-- 确认后可 kill（需 IC 批准）
KILL <id>;
若连接池配置被改小：改回 50 并滚动重启（一次一台）

### 3.3 下游降级
打开开关：/admin/switch?key=order.skip_stock_check&value=true
影响：可能超卖 → 必须 30 分钟内恢复并人工核对
对外：客服话术见 §5

### 3.4 摘流
kubectl -n prod label pod <pod> unhealthy=true   # 从 LB 摘除
保留现场：jstack / pprof 先抓再重启

### 3.5 限流
调整：/admin/ratelimit?key=order_create&qps=2000
注意：先确认下游能扛，否则限流无效

## 4. 验证
- 错误率 < 1% 持续 10 分钟
- P99 < 500ms
- 积压（若用 MQ）< 1000
- 抽样 20 笔下单成功

## 5. 升级
- 15 分钟未止血 → 升级到 TL
- 涉及资金/数据 → 立即叫 DBA + 财务
- 影响 > 1 万用户 → 启动对外沟通

## 6. 事后
- 建 incident 记录，指定 IC/Comms/Scribe
- 24 小时内出初步时间线，72 小时内复盘
- 改进项进 action_item，owner + 日期
```

### 模板二：事故指挥角色卡

| 角色 | 职责 | 不该做什么 |
| --- | --- | --- |
| **IC（指挥）** | 定级、分配任务、决定止血方案、叫停危险操作、控制节奏（每 5 分钟同步） | 不要自己埋头查日志 |
| **Ops（操作）** | 执行 IC 批准的命令，回报结果 | 不要擅自操作/并行操作 |
| **Comms（沟通）** | 对内同步（每 10 分钟）、对外公告、客服话术 | 不要承诺未确认的恢复时间 |
| **Scribe（记录）** | 时间线（谁在何时做了什么）、关键数据快照 | 不要参与技术判断 |

> 💡 **小团队可以一人多角**，但**必须显式声明**「我现在是 IC，兼 Comms」。**没声明的多角 = 没人负责。**

### 模板三：复盘（时间线 + 5 Why 的边界）

```markdown
# 复盘：2026-06-11 下单接口 P1

## 摘要
- 影响：37% 请求失败，持续 42 分钟，影响约 1.2 万单
- 定级：P1（核心功能不可用，未全站）
- 发现方式：ALERT（20:04）→ 认领延迟 7 分钟
- 根因：连接池上限由 50 改为 10（配置发布未走审批）
- 直接损失：约 8.6 万元

## 时间线（精确到分钟）
20:04 告警触发（14 条）
20:06 值班 A 询问，无人应答
20:11 B 介入
20:15 C 未经沟通重启实例 1
20:22 B 重启实例 2 → 全站不可用
20:38 总监指定 B 为 IC
20:44 定位配置变更
20:46 回滚
21:10 指标归零

## 根因（分层）
- 技术：配置无边界校验（可改到 10）
- 流程：配置变更未走审批、无灰度
- 组织：值班无 backup、无 IC 制度、无对外沟通

## 做得好的
- 20:44 定位快（因为有人想到看发布记录）

## 做得不好的
- 认领延迟 7 分钟；双重启；全程无公告

## 改进项（必须四类齐全）
| 类别 | 内容 | owner | 截止 |
| --- | --- | --- | --- |
| PREVENT | 连接池配置加下限校验（≥20），CI 拦截 | 平台组 | 06-18 |
| DETECT | 连接池使用率 > 80% 告警（1 分钟） | SRE | 06-15 |
| MITIGATE | 一键回滚配置（平台按钮） | 平台组 | 06-25 |
| PROCESS | 值班表加 backup + 5 分钟自动升级 | TL | 06-14 |
| PROCESS | 强制 IC 制度 + 角色卡 | TL | 06-14 |
```

> 🩸 **「5 Why」要慎用**：它容易导向「员工不小心」这种无效结论。**更好的框架是「三层根因」：技术、流程、组织。** 三层都写了，改进项才可能真正防复发。

### 模板四：演练（桌面推演 + 混沌）

| 类型 | 频率 | 做法 | 产出 |
| --- | --- | --- | --- |
| **桌面推演** | 每月 | 给一个故障场景，值班口述处置步骤 | 发现 Runbook 缺口 |
| **单点故障注入** | 每季度 | kill 一台实例/断 Redis/断 MQ | 验证自动恢复 |
| **全链路演练** | 每半年 | 模拟机房故障/依赖全挂 | 验证降级与 RTO |
| **备份恢复演练** | 每季度 | 真恢复到空机器并计时 | 实测 RTO/RPO |

**演练的三条纪律**：

1. **必须在生产或生产同构环境**（测试环境的故障演练没有意义）。
2. **必须计时**（不计时的演练等于走过场）。
3. **必须更新 Runbook**（演练中卡住的每一步，都是 Runbook 的漏洞）。

## 42.5 双修对照：Agent 平台多出的三类故障源

| 维度 | 传统系统 | Agent 系统 | 相同 / 差异根因 |
| --- | --- | --- | --- |
| **故障定义** | 5xx、超时、不可用 | 以上 + **答错、拒答不当、越权、幻觉** | 质量也是故障 |
| **发现方式** | 告警 | 以上 + **用户投诉、评测回退、成本异常** | 多两个信号源 |
| **止血手段** | 回滚/降级/限流 | 以上 + **切模型、关工具、强制模板回复、清语义缓存** | 手段集扩展 |
| **根因常见处** | 发布、依赖、容量 | 以上 + **prompt 变更、模型版本漂移、知识库更新** | 多两个变更源 |
| **Runbook 关键项** | 看板、回滚命令 | 以上 + **模型/供应商切换开关、成本熔断** | 新增章节 |
| **复盘改进项** | 代码/配置/容量 | 以上 + **评测集补充、prompt 版本化、灰度策略** | 新增类别 |

### Agent 平台的三份必备 Runbook（要点）

```markdown
# Runbook A：模型供应商故障（错误率/延迟飙升）
1. 确认：供应商状态页 + 我方错误码分布（429/5xx/timeout）
2. 切换：/admin/model-route?primary=backup-provider（预设好的备用）
3. 降级：非核心功能切小模型；关闭联网/工具调用
4. 验证：TTFT、成功率、成本
5. 恢复后：把流量切回，观察 30 分钟

# Runbook B：效果回退（评测分数下降/投诉上升）
1. 确认：对比最近 24h 的评测结果与 prompt/模型版本变更记录
2. 回滚：prompt 版本回退 / 模型版本回退（二者独立开关）
3. 隔离：对受影响租户启用保守策略（强制引用 + 拒答阈值提高）
4. 验证：用固定评测集跑一遍（第 49 章）
5. 复盘：为什么评测没拦住（门禁阈值/覆盖不足）

# Runbook C：成本异常（日成本 > 预算 150%）
1. 拆维度：租户 / 模型 / Run / step
2. 止血：租户限额 → 模型路由降级 → 关闭非核心功能 → 全局预算熔断
3. 定位：重试风暴？上下文膨胀？死循环 Run？贵模型误路由？
4. 恢复：逐步放开，观察单位成本
```

## 42.6 会在哪炸：八个坑

| # | 坑 | 现象 | 根因 | 怎么修 |
| --- | --- | --- | --- | --- |
| 1 | 值班「跟人」 | 人一走服务没人管 | 排班按人 | 按服务排 + 交接 notes |
| 2 | 无 backup | 主值班失联，告警无人认领 | 没设升级链 | 5 分钟自动升级 |
| 3 | Runbook 过期 | 命令跑不通、路径改了 | 没人维护 | 演练后更新 + 季度评审 |
| 4 | 多人并行操作 | 二次故障 | 无 IC | 强制 IC + 一次一个变量 |
| 5 | 事故群变聊天群 | 信息淹没，决策丢失 | 无 Scribe | 每 5 分钟一条时间线 |
| 6 | 复盘只写技术根因 | 同类事故复发 | 缺流程/组织层 | 三层根因 + 四类改进项 |
| 7 | 改进项无 owner | 三个月后还是 TODO | 没有跟踪 | 周会看板 + 闭环率 |
| 8 | 演练走形式 | 真事故时 Runbook 无用 | 不计时/不同构 | 生产同构 + 计时 + 更新 |

## 42.7 怎么验证：四个可度量的指标

| 指标 | 定义 | 目标 |
| --- | --- | --- |
| **MTTD**（平均发现时长） | 故障开始 → 被发现 | P1 < 5 min |
| **MTTA**（平均认领时长） | 告警 → 有人认领 | < 5 min |
| **MTTM**（平均止血时长） | 认领 → 已止血 | P1 < 30 min |
| **改进项闭环率** | 90 天内 DONE / 总数 | ≥ 70% |
| **告警可执行率** | 有明确处置动作的告警 / 总告警 | ≥ 80% |
| **演练覆盖** | 已演练的 tier1 服务 / 总数 | 100%/半年 |

```sql
-- 每月的 MTTD/MTTA/MTTM 与发现方式分布
SELECT DATE_FORMAT(started_at,'%Y-%m') AS mon,
       severity,
       COUNT(*) AS cnt,
       ROUND(AVG(TIMESTAMPDIFF(MINUTE, started_at, mitigated_at)),1) AS mttm_min,
       SUM(detection='CUSTOMER')/COUNT(*) AS customer_detected_ratio
FROM incident
WHERE started_at >= DATE_SUB(NOW(), INTERVAL 6 MONTH)
GROUP BY mon, severity ORDER BY mon DESC, severity;
```

> 💡 **`customer_detected_ratio` 是最扎心的指标**：如果它 > 30%，说明你的监控在替客户「发现问题」。

## 42.9 实战：一次混沌演练的完整记录

演练的价值在于**暴露 Runbook 与自动化里的窟窿**，而不是「证明系统很稳」。下面是一次真实的季度演练记录（已脱敏）。

```markdown
# 演练记录：订单服务单实例故障 + Redis 主从切换
- 日期：2026-09-18 14:00~15:10
- 环境：生产（影子流量 5%，真实流量不受影响）
- 参与：值班 A（primary）、B（backup）、SRE C、IC（临时指定）
- 假设：验证「实例故障自动摘流 + 缓存降级」是否有效

## 时间线
14:00  注入：kill order-api 的 pod-3（占 1/3 流量）
14:00  告警触发（PodNotReady），自动摘流 12s 后生效
14:01  A 认领，确认错误率 0.4%（未超阈值）
14:03  发现 pod-3 未自动重建（HPA 配置 minReplicas=3，但 PDB 阻止驱逐）
14:05  **Runbook 缺口**：Runbook 只写了「kubectl delete pod」，未写 PDB 卡住怎么办
14:08  C 手动 `kubectl scale --replicas=4`，恢复
14:12  注入：Redis 主节点 kill，触发哨兵切换
14:12  切换耗时 8s，期间 2,140 次请求报错（应用未做本地缓存兜底）
14:15  **发现**：应用的重试没有退避，切换期间 QPS 放大 1.8 倍
14:20  A 打开降级开关（读本地缓存），错误率回落
14:35  演练结束，恢复流量
14:40  复盘：3 个 Runbook 缺口、2 个配置问题

## 结论与改进项
| # | 问题 | 改进 | owner | 截止 |
| --- | --- | --- | --- | --- |
| 1 | Runbook 未覆盖 PDB 阻止驱逐 | 补章节 + 演练验证 | A | 09-25 |
| 2 | 应用无本地缓存兜底 | 加 Caffeine 一级缓存（TTL 5s） | 订单组 | 10-15 |
| 3 | 重试无退避 | 加指数退避 + 抖动 | 订单组 | 10-10 |
| 4 | 演练未计时 | 下次用秒表记录每个阶段 | SRE C | 下次演练 |

## 演练本身的问题
- 14:03~14:08 的 5 分钟，A 在翻 Runbook 而不是「按图操作」→ Runbook 太长（18 页），需要拆成「5 分钟速查卡」。
- IC 是临时指定的，前 3 分钟不清楚自己该做什么 → 角色卡需要打印贴在值班位。
```

> 💡 **演练最大的产出不是「通过了」，而是「发现了 5 个具体缺口」**。一次演练发现 0 个问题的团队，通常是演练设计得太温和。

## 42.10 值班交接模板（每天 10 分钟，避免信息断层）

```markdown
# 值班交接单 2026-09-18 → 09-19
- 交班：A    接班：B

## 1. 当前系统状态
- 全部 tier1 服务正常；order-api 昨日 1 次 P2（已闭环）
- 进行中的变更：无；计划变更：09-19 10:00 库存服务发布（已审批）

## 2. 未闭环告警（必须逐条说明）
| 告警 | 开始时间 | 现状 | 是否已建工单 |
| --- | --- | --- | --- |
| OrderP99High | 09-18 21:00 | 已回落，疑似定时任务 | 是（OPS-8821） |
| DLQ 积压 32 条 | 09-18 23:10 | 已人工处理 20 条，剩 12 | 是（OPS-8822） |

## 3. 已知风险（今天可能爆的）
- 大客户 A 今日批量导入（预计 8 万行）→ 关注同步队列水位
- 证书 09-20 到期，已排期更换（负责人 C）

## 4. 待跟进事项
- 昨日 P2 的改进项：连接池告警，SRE 本周完成

## 5. 联系方式
- 备份值班：B；TL：D；DBA：E
```

**交接的三条纪律**：

1. **口头 + 书面双确认**：书面单发群里，口头过一遍「未闭环告警」。
2. **未闭环告警必须带工单号**：否则接班的人不知道上下文。
3. **风险要主动说**：今天有什么大动作、什么证书要过期、哪个客户在搞大促。

## 42.11 一页速记

| 关键词 | 必须记住的结论 |
| --- | --- |
| 六件套 | 值班表/分级/Runbook/指挥/复盘/演练，缺一件其余打折 |
| 值班 | **跟服务不跟人**；必须有 backup + 5 分钟自动升级 |
| 三级状态 | 已止血 ≠ 已恢复 ≠ 已闭环 |
| 三条纪律 | 单一信息源、一次只改一个变量、变更锁 |
| 四个角色 | IC / Ops / Comms / Scribe；小团队可兼但必须显式声明 |
| Runbook | 现象 → 判定 → 止血 → 验证 → 升级；必须演练验证 |
| 复盘 | **三层根因**（技术/流程/组织）+ **四类改进项**（防/测/止/流程） |
| 闭环率 | 90 天 ≥70% 才算有效复盘 |
| 指标 | MTTD/MTTA/MTTM/闭环率/告警可执行率/客户发现占比 |
| 双修 | Agent 多三类故障源：供应商、效果回退、成本 |

## 42.12 自检题

1. **为什么值班要「跟服务不跟人」？给出一个「跟人」会失效的场景。**
   > 要点：「跟人」在人员离职、调岗、休假、交接不清时会断档；且个人不掌握全部服务的上下文。场景：核心服务负责人离职两周，告警仍发给他，无人认领；或他休假，backup 不知道在哪。正解：服务维度定义值班 + 明确 backup + 交接 notes + 自动升级。

2. **事故中「同时重启两台实例导致全站不可用」，除了技术原因，暴露了什么流程问题？**
   > 要点：① 无 IC，无人统一决策与叫停；② 违反「一次只改一个变量」；③ 无变更锁（P1 期间禁止无关/危险变更）；④ 操作前未评估剩余容量。改进项应落在 PROCESS 类（IC 制度、变更锁、操作审批），而不只是「加个重启限制」。

3. **复盘写了 20 条改进项，三个月后完成 3 条。问题出在哪？怎么改？**
   > 要点：缺 owner、截止日期、优先级与跟踪机制；改进项过多导致没有聚焦。改法：每起事故**最多 5 条**、每条必须有 owner + 日期 + 验证方式；进周会看板；度量「90 天闭环率」；未完成的必须在下次复盘说明原因。**改进项闭环率是唯一有效的复盘质量指标。**
