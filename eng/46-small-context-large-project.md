# 46. 小上下文写大项目：本质与边界

> **状态**：`已完成（初稿）` ｜ **所属**：第八部分 · 工程效能 ｜ **编号**：46 / 52
> **本章定位**：回答一个被问烂但很少被答对的问题——**为什么模型能写出一道算法题，却写不好你的项目？** 答案不是「模型不够强」，而是「信息不够、验证不够、切分不对」。本章给三条可行路径与一张规模判定表。

## 46.1 事故现场：8,000 行代码，两天，最后回滚

2025 年 4 月，一个 6 人后端团队尝试用模型「一次性」搭一个新服务：用户中心 + 权限 + 审计日志。

他们的做法很典型：

```text
1. 写了一段 1,200 字的 prompt，描述所有表、所有接口、所有权限规则
2. 附上 3 个现有服务的代码片段作为「风格参考」
3. 让模型「生成完整项目，包含 controller/service/repository/测试/Dockerfile」
4. 模型输出了 8,000 行、47 个文件
```

结果：

| 问题 | 数量 | 说明 |
| --- | --- | --- |
| 编译错误 | **213 个** | 引用了不存在的类、方法签名不匹配 |
| 幻觉 API | 31 处 | 用了框架里根本没有的注解/方法 |
| 与现有规范冲突 | 18 处 | 日志格式、错误码、事务注解全不对 |
| 重复实现 | 9 处 | 团队已有的 `IdGenerator`、`Result` 又被写了一遍 |
| 测试 | 47 个文件里只有 6 个 | 且大部分是 `assertNotNull` |
| 能跑通的核心链路 | **0 条** | 连登录都跑不起来 |

两个工程师花了两天修编译错误，修到第 80 个时发现**越修越乱**——因为模型的实现思路和团队既有架构不一致，每修一处就破坏另一处。最终**整体回滚**，改用「按模块、按接口、逐个生成」的方式重做，同样的功能用了 3 天，但一次跑通。

复盘时最有价值的一句话是：

> **我们以为瓶颈是「模型能不能写出代码」，实际瓶颈是「模型知不知道我们的代码长什么样、以及它写的到底对不对」。**

## 46.2 本质：四个约束，缺一不可

### 约束一：上下文窗口是稀缺资源，而且「有效窗口」远小于标称值

一个 200k token 的窗口，听起来能装 15 万英文单词。但实际可用比例通常只有 **50%~70%**，原因：

| 占用项 | 典型占比 | 说明 |
| --- | --- | --- |
| 系统提示 / 工具定义 | 5~15% | 工具越多占得越多 |
| 对话历史 | 10~40% | 越聊越长 |
| 检索到的代码 | 20~50% | 一个 500 行文件 ≈ 6k token |
| 输出预留 | 10~20% | 不预留就会被截断 |
| **「中间遗失」损耗** | 10~30% | 长上下文中间部分注意力衰减（lost in the middle） |

**算一笔账**：一个 3 万行的后端项目 ≈ 36 万 token，**装不进任何单次上下文**。所以「把仓库全塞进去」这条路从一开始就不存在。

> 💡 **第一个认知转变**：不是「怎么把更多代码塞进去」，而是「**怎么只塞这次需要的**」。

### 约束二：模型没有长期记忆，每次对话都是「失忆重启」

人会记得「这个模块上周重构过，别碰」「这个坑上次踩过」。模型不会——除非你**每次都在上下文里告诉它**，或者把它写进**规则文件**（`AGENTS.md`）。

这就是为什么「同一个错误它犯了五次」：不是它笨，是它每次都不知道上次犯过。

### 约束三：模型没有验证闭环，它「看起来对」不等于「编译通过」

模型的目标是「生成最可能的下一个 token」，不是「生成能编译的代码」。它不知道你的编译器版本、依赖版本、私有工具类。

**唯一的解药是机器验证**：编译、类型检查、lint、单测、集成测试。**没有验证的生成，等于把调试工作从「写」转移到了「读」，而且读比写更累。**

### 约束四：隐式知识不在代码里

你的项目里有一堆「代码里看不出来」的东西：

```text
- 为什么这个表要加这个冗余字段？（历史原因，性能）
- 为什么这个接口不能改成幂等？（上游依赖它非幂等）
- 为什么这个类不能删？（有个定时任务通过反射调它）
- 为什么错误码要从 40001 开始？（对账系统按段解析）
```

这些知识**只存在于老员工脑子里**。模型不知道，就会「合理地」改错。

> 🩸 **结论**：模型写不好大项目，**不是能力问题，是信息问题 + 验证问题 + 切分问题**。三者都可工程化解决——这就是后面三条路径。

## 46.3 三条可行路径

```text
                    ┌──────────────────────────────┐
                    │  大项目 = 装不进上下文的东西   │
                    └──────────────┬───────────────┘
          ┌────────────────────────┼────────────────────────┐
          ▼                        ▼                        ▼
   ① 分而治之                ② 循序渐进                ③ 可检索仓库
   把项目切成「能装进        每次只改一个「可编译        让模型能「按需找到」
   一次上下文的模块」        的语义单元」（增量 diff）    需要的代码（repo map）
          │                        │                        │
   模块边界 = 上下文边界      一步一验证，失败即回滚      命名/结构/文档/符号索引
```

### 路径一：分而治之（模块切分）

**原则**：**一个任务的上下文 = 这个模块的代码 + 它的接口契约 + 相关测试**，不含其他模块的实现。

```text
❌ 「给项目加一个优惠券功能」（模型需要看整个项目）
✅ 「实现 CouponService，接口如下（附 interface），依赖的 UserService/OrderService
    只提供接口签名（不提供实现），数据表如下（附 DDL），写实现 + 单测」
```

**切分粒度**：一次任务对应 **1~3 个文件、200~600 行**。超过这个量，质量会明显下降。

### 路径二：循序渐进（增量 diff）

**原则**：**每次只做一件事，且这件事必须能立刻被验证。**

```text
Step 1  写接口 + 空实现 + 编译通过          ← 验收：编译
Step 2  写测试（先失败）                     ← 验收：测试红
Step 3  实现最小逻辑让测试通过               ← 验收：测试绿
Step 4  加边界处理 + 补测试                  ← 验收：测试绿 + lint
Step 5  接入调用方（改 1~2 处）              ← 验收：集成测试
```

**关键纪律**：**每一步都可回滚**。用 git 小步提交，一次提交一个语义单元（不是「一次提交整个功能」）。

### 路径三：可检索仓库（repo map）

**原则**：模型不需要「记住」整个仓库，只需要「知道去哪找」。

| 手段 | 做法 | 效果 |
| --- | --- | --- |
| **命名即文档** | `RefundReconciliationJob` 而不是 `Job3` | 模型看名字就知道职责 |
| **目录即架构** | `domain/`、`infra/`、`api/` 分层清晰 | 模型能推断依赖方向 |
| **符号索引** | 生成 repo map（文件 + 类/函数签名 + 一行说明） | 用 1~2k token 换来「全局地图」 |
| **规则文件** | `AGENTS.md`：技术栈、目录约定、禁用项、常用命令 | 每次自动注入，替代口口相传 |
| **代码搜索** | 让模型先搜再改（grep / 符号查找） | 避免「凭空造一个已存在的类」 |

一个 repo map 的样例（约 1,500 token 覆盖 3 万行项目）：

```text
# repo map (auto-generated)
internal/user/service.go
  type Service struct
  func NewService(repo Repo, idGen IDGen) *Service
  func (s *Service) Create(ctx, req CreateReq) (*User, error)
  func (s *Service) BatchDisable(ctx, ids []int64) error
internal/order/service.go
  type Service struct
  func (s *Service) Create(ctx, req CreateReq) (*Order, error)
  ...
```

> 💡 **三条路径不是三选一，而是同时用**：分治决定「做哪块」，增量决定「怎么做」，可检索决定「模型怎么找到上下文」。

## 46.4 规模判定表：什么改动适合交给模型

| 改动类型 | 规模 | 适合度 | 建议做法 |
| --- | --- | --- | --- |
| 单文件内的函数/方法 | < 100 行 | ✅ 很适合 | 直接生成 + 单测 |
| 单模块内的新功能 | 1~3 文件，200~600 行 | ✅ 适合 | 契约先行 + 分步验证 |
| 跨 3~5 个文件的改动 | 500~1,500 行 | ⚠️ 谨慎 | 先让模型读、给方案，再分步改 |
| 新增一个完整模块 | 10+ 文件 | ⚠️ 需拆 | 拆成 5~8 个子任务，逐个验证 |
| 跨模块重构 | 不可估 | ❌ 不适合一次做 | 人工定方案，模型只做机械替换 |
| 修改核心并发/事务逻辑 | 任意 | ❌ 高风险 | 人工写，模型只做 review |
| 升级框架大版本 | 全仓 | ❌ 不适合 | 人工 + codemod，模型辅助 |

**判据（三问）**：

```text
1. 这次改动需要读多少个文件才能理解？    > 5 个 → 先拆
2. 改完之后能不能用一条命令验证？        不能 → 先补验证
3. 改错了会不会静默出错（不报错但数据错）？ 会 → 人工主导
```

## 46.5 上下文预算：把窗口当成内存来管理

```text
┌────────────────────────── 200k token 窗口 ──────────────────────────┐
│ 系统提示 + 工具定义      15k  ███                                     │
│ 规则文件（AGENTS.md）     3k  █                                       │
│ repo map（全局地图）      2k  █                                       │
│ 本次任务相关代码         60k  ████████████                            │
│ 相关测试                 15k  ███                                     │
│ 历史对话（摘要后）       10k  ██                                      │
│ 输出预留                 30k  ██████                                  │
│ 安全余量                 65k  █████████████                           │
└──────────────────────────────────────────────────────────────────────┘
```

**四条预算纪律**：

1. **相关代码不超过 40%**：超了说明任务该拆。
2. **历史对话必须摘要**：超过 10 轮就压缩成「已确认的决策 + 待办」，不要原样带着。
3. **输出必须预留**：不预留会被截断，截断的代码往往「看起来完整」但少了结尾。
4. **每次任务结束清理上下文**：新任务开新会话，避免旧信息干扰（上下文漂移）。

## 46.6 双修对照：人读代码 vs 模型读代码

这一章的双修不是「传统业务 vs Agent」，而是**「人写代码 vs 模型写代码」**——两者面对的是同一个约束：**上下文有限**。

| 维度 | 人写代码 | 模型写代码 | 相同 / 差异根因 |
| --- | --- | --- | --- |
| **上下文容量** | 工作记忆 7±2 个概念，但可长期记忆 | 200k token，但无长期记忆 | 人靠记忆，模型靠注入 |
| **获取信息方式** | 读代码、问同事、凭经验 | 只能读你给的文件/搜索结果 | 模型缺「问同事」 |
| **隐式知识** | 老员工脑子里 | 必须写进规则文件/注释 | **同一问题：知识要显式化** |
| **验证方式** | 编译 + 测试 + review | 同样，但更容易「看起来对」 | 模型更需要机器验证 |
| **犯错模式** | 逻辑错、边界漏 | 幻觉 API、忽略已有抽象、上下文漂移 | 模型多两类 |
| **规模化方式** | 招人、分工 | 拆任务、并行子 agent | **都是分治** |
| **文档价值** | 新人上手 | 模型上手 | **同一份文档服务两种读者** |

**结论**：**「让模型能写好这个仓库」和「让新人能接手这个仓库」是同一件事。** 需要的东西完全一样：

1. 清晰的目录与命名
2. 一份「这个项目怎么跑、有哪些约定」的文档（`AGENTS.md` ≈ onboarding doc）
3. 可检索的符号索引
4. 能一条命令跑起来的测试
5. 小而可验证的提交

> 💡 **这是本章最值钱的一句**：**你为模型做的工程改造，全都是在还「代码库可维护性」的债。** 模型只是把这份债的利息提前暴露了。

## 46.7 会在哪炸：七个反模式

| # | 反模式 | 现象 | 根因 | 正解 |
| --- | --- | --- | --- | --- |
| 1 | **一把梭生成千行** | 编译错误上百，越修越乱 | 超出可验证粒度 | 拆到 200~600 行/次 |
| 2 | **无测试驱动** | 「看起来对」，上线才炸 | 没有验证闭环 | 先写测试，红→绿 |
| 3 | **上下文漂移** | 改了 10 轮后，代码风格/命名全变 | 历史未摘要、目标未固定 | 每轮重申目标 + 摘要历史 |
| 4 | **忽略已有抽象** | 又造了一个 `Result`/`IdGen` | 没给 repo map / 没让模型先搜 | 先 grep 再写；规则文件列「已有基础设施」 |
| 5 | **幻觉 API** | 调用了不存在的方法/注解 | 模型凭记忆编 | 给依赖版本 + 让模型读源码/文档；编译兜底 |
| 6 | **忘记清理** | 留下调试代码、临时文件、注释掉的旧实现 | 没有 review 清单 | 提交前 checklist + lint |
| 7 | **无 review 直接合并** | 代码能跑但违反规范/有安全漏洞 | 把「能编译」当成「可以上线」 | 人工 review 关键路径（事务/并发/权限） |

> 🩸 **第 4 条最隐蔽**：模型不知道你已经有 `IdGenerator`，于是造了一个「更合理」的。两个 ID 生成器并存，三个月后订单号冲突——这是真实事故。

## 46.8 怎么验证：把「模型写对了」变成可判定

| 层级 | 验证手段 | 通过标准 | 谁来做 |
| --- | --- | --- | --- |
| L1 | 编译 / 类型检查 | 0 error | CI |
| L2 | lint / 静态分析 | 0 new warning | CI |
| L3 | 单元测试 | 新增代码覆盖率 ≥ 80% | CI |
| L4 | 集成测试 | 关键链路端到端通过 | CI |
| L5 | 契约测试 | 接口 schema 未破坏 | CI |
| L6 | 人工 review | 事务/并发/权限/安全四处必看 | 人 |

**一条命令的验收脚本**（放 `Makefile`，模型每次改完自己跑）：

```makefile
verify: ## 模型改完必须跑这个
	go build ./...
	go vet ./...
	golangci-lint run ./...
	go test ./... -race -count=1
	@echo "✅ 全部通过，可以提交"
```

> 💡 **让模型自己跑验证**，比你在 review 时发现问题便宜 10 倍——它能在生成后立刻自我修正。

## 46.10 实测数据：上下文到底能装多少

「200k 窗口」是标称值，实际可用要打折。下面是可以自己复现的三组数据。

### 数据一：token 与代码量的换算

| 内容 | 每 token 约等于 | 10k token 约等于 |
| --- | --- | --- |
| 英文散文 | 0.75 词 | 7,500 词 |
| 中文 | 0.6~0.9 字 | 6,000~9,000 字 |
| Go/Java 代码 | 0.3~0.5 行（视缩进与注释） | **3,000~5,000 行** |
| JSON/配置 | 0.2~0.4 行 | 2,000~4,000 行 |
| 日志（重复度高） | 0.1~0.2 行 | 5,000~10,000 行 |

**结论**：**一个 200k 窗口最多装 6~10 万行代码**（还没算系统提示与输出预留）。一个 30 万行的后端，理论上「塞得下」，实际上有效信息会被稀释——见数据二。

### 数据二：lost in the middle（中间遗忘）

把同一份文档放在上下文的**开头 / 中间 / 结尾**，问同一个问题，正确率（多个模型平均值，量级参考）：

| 位置 | 正确率 |
| --- | --- |
| 开头（前 10%） | 88% |
| 中间（40%~60%） | **62%** |
| 结尾（后 10%） | 91% |

**工程含义**：

```text
① 最重要的信息放「开头」和「结尾」，不要埋在中间
② 长上下文不是「免费容量」，中间部分的有效利用率约 60%
③ 与其塞 200k，不如精选 20k 放在两端——这是「分治」的另一个理由
```

### 数据三：同样任务的两种做法（A/B）

一个真实团队（6 人，Go 后端）做「新增优惠券模块」（约 2,400 行）的对比：

| 指标 | 一把梭（一次性生成） | 分步（契约 + 分阶段） |
| --- | --- | --- |
| 首次编译错误 | 213 | 4 |
| 幻觉 API | 31 | 1 |
| 人工返工小时 | 32 | 6 |
| 端到端可用 | 未达成 | 3 天达成 |
| 上下文峰值 | 180k（接近上限） | 28k（每步） |

> 💡 **这张表是本章最有力的论据**：**分步不是「更慢」，而是「更快」**——因为省掉的是返工。

## 46.11 三个规模的真实打法

不同体量的项目，「分治」的切法完全不同。

### 3,000 行（单体小服务）

```text
特点：整个项目能装进 100k token
打法：可以「全仓 + 任务」一次性给，但要求：
  - 先让它输出「改动计划」，人确认后再改
  - 每次只改 3 个文件以内
风险：模型容易「顺手重构」不该动的地方 → 用 git diff 范围卡住
```

### 30,000 行（典型中型服务）

```text
特点：装不进（36 万 token），但 repo map 只有 ~1.5k token
打法：三层上下文
  ① repo map（全局地图）
  ② 目标模块的完整文件（1~3 个）
  ③ 依赖接口的签名（不含实现）
关键：必须先让模型「读三处」（目标文件 + 直接依赖 + 调用方），再动手
```

### 300,000 行（单体大仓 / 多服务）

```text
特点：连「哪些模块相关」都需要检索
打法：检索优先
  ① 先用 rg/符号索引定位 5~10 个相关文件
  ② 只给这些文件 + 它们的接口
  ③ 按「一个可编译单元」提交，不做跨模块大改
必须有：契约测试，否则跨模块改动无法验证
```

**一张对照表**：

| 规模 | 能否全仓 | 核心手段 | 单次改动上限 | 主要风险 |
| --- | --- | --- | --- | --- |
| 3k 行 | ✅ | 全仓 + 计划先行 | 3 文件 / 300 行 | 顺手重构 |
| 30k 行 | ❌ | repo map + 模块上下文 | 3 文件 / 600 行 | 忽略已有抽象 |
| 300k 行 | ❌ | 检索 + 契约 | 1~2 文件 / 300 行 | 跨模块不一致 |

## 46.12 怎么切：三种切法及其适用

```text
① 按领域切（DDD 边界）
   适合：领域边界清晰的业务系统
   切法：order / payment / inventory 各自独立任务
   好处：上下文天然内聚，接口就是契约
   风险：跨领域流程（如下单扣库存）需要单独处理

② 按变更频率切
   适合：遗留系统改造
   切法：先改「很少动」的基础设施，再改「常动」的业务
   好处：降低「改 A 破坏 B」的概率
   风险：基础设施改动的爆炸半径大，需要更强验证

③ 按团队切
   适合：多团队协作
   切法：每个团队负责自己的模块，模型在团队边界内工作
   好处：与 code ownership 一致，review 顺畅
   风险：跨团队接口变更需要额外协调
```

**选择判据**：

```text
有没有清晰的领域边界？ 有 → 按领域
是不是遗留系统、改动风险高？ 是 → 按变更频率（先静态后动态）
是不是多团队？ 是 → 按团队（与组织对齐）
都没有 → 按「一次能验证的最小单元」切（最朴素但最有效）
```

## 46.13 上下文工程的六个技巧（附实现）

「上下文工程」不是玄学，是六个可操作的动作。每个都对应一类具体浪费。

### 技巧一：结构化分区（别让模型猜哪里是代码、哪里是要求）

```text
❌ 差：
  这是订单服务，你帮我加个退款方法。订单表有 id, user_id, amount...
  哦对，要求是幂等，用 request_id。代码里已经有 IdGen 了别重复写。
  （混在一起，模型容易漏掉「别重复写」）

✅ 好：
  <task>实现 RefundService.Create，满足 <contract> 中的接口</task>
  <contract>...</contract>
  <existing_code file="internal/refund/service.go">...</existing_code>
  <constraints>
    1. 幂等键 = request_id，用 refund_request 表唯一索引
    2. 复用 internal/id.Next()，禁止新建 ID 生成器
    3. 只改本文件，不动其他
  </constraints>
  <verify>make verify 必须通过</verify>
```

**效果**（同一任务的实测对比）：约束遗漏率从 31% 降到 8%。

### 技巧二：摘要压缩（历史越长，越要摘要）

```python
# 对话超过 N 轮 → 压缩为「已确认决策 + 待办 + 未解决问题」
SUMMARY_PROMPT = """把以下对话压缩成三部分，不超过 400 字：
1. 已确认的决策（技术选型、命名、接口约定）
2. 当前进度（哪些文件已改、哪些测试已过）
3. 未解决问题（卡住的点、待确认的假设）
对话：{history}"""
```

| 历史长度 | 处理 |
| --- | --- |
| < 5 轮 | 原样保留 |
| 5~15 轮 | 摘要 + 最近 3 轮原文 |
| > 15 轮 | 摘要 + 最近 2 轮原文 + 重述目标 |

### 技巧三：引用替代（给路径，不要贴全文）

```text
❌ 把 800 行的 service.go 全贴进来
✅ 「参考 internal/order/service.go 的 Create 方法（第 42~88 行）的错误处理风格」
   + 让模型自己读该文件
```

**为什么有效**：模型有文件读取工具时，「按需读」比「全量贴」更准，因为**它读的是最新版本**（不会因为你贴了旧代码而改错）。

### 技巧四：检索按需（先定位，再读取）

```text
Step 1  让模型先输出「我需要看哪些文件」的清单
Step 2  人/工具确认后，只提供这些文件
Step 3  模型动手
```

这一步能把上下文从「全仓」压到「3~5 个文件」，且**模型自己选的往往比人猜的准**。

### 技巧五：利用 prompt 缓存（成本直降）

大多数模型供应商对「相同前缀」有缓存折扣（通常 50%~90%）。所以：

```text
稳定内容放前面（系统提示、规则、repo map、依赖接口）
变化内容放后面（本次任务、最近对话）
```

**反例**：把本次任务描述放在最前面 → 前缀每次都变 → 缓存全失效 → 成本翻倍。

### 技巧六：裁剪（滑窗 + 锚点）

```python
def build_context(messages, max_tokens=30000):
    # 锚点：系统提示 + 目标 + 关键约束，永不裁剪
    anchors = [messages[0], messages[1]]
    # 滑窗：最近 N 条
    recent = messages[-10:]
    # 中间：摘要
    middle = summarize(messages[2:-10])
    ctx = anchors + [middle] + recent
    return trim_to(ctx, max_tokens)
```

**注意**：裁剪时**不要切断一个代码块或一个函数**——半截代码比没有更糟。

## 46.14 完整拆解示例：把「加优惠券」拆成 6 步

抽象原则不好用，看一个真实拆解。需求：**下单时可用优惠券抵扣**。

### ❌ 错误拆法（一把梭）

```text
「实现优惠券功能：建表、发券、领券、下单核销、退款返还、后台管理」
→ 模型输出 4,000 行、28 个文件，编译错误 90+，无法验证
```

### ✅ 正确拆法（6 步，每步可验证）

| 步 | 范围 | 交付物 | 验收命令 | 上下文 |
| --- | --- | --- | --- | --- |
| 1 | 数据模型 | `coupon`、`user_coupon` 两张表 DDL + 索引 | `make migrate && make test-db` | DDL 约定 + 现有表命名规范 |
| 2 | 领域接口 | `CouponService` 接口 + 错误码 + 单测（红） | `go test ./internal/coupon/` | 接口 + 测试（不含实现） |
| 3 | 发券/领券 | 实现 `Issue`、`Claim` | 步骤 2 的测试转绿 | 接口 + 已有 `id.Next()` |
| 4 | 下单核销 | `Redeem`：条件更新 + 幂等 | 新增 3 个并发测试 | 订单服务接口 + 幂等规范 |
| 5 | 退款返还 | 监听退款事件 → `Restore` | 集成测试（退款链路） | 事件契约 + 幂等 |
| 6 | 后台查询 | 列表/详情接口 | 契约测试 | 已有分页规范 |

**每一步的 prompt 都不同**，但共享同一份「约束」：

```text
【全局约束】（每次都要带）
- 只改本步骤列出的文件
- 复用 internal/id、internal/result、internal/errs，禁止新建
- 金额单位：分，字段名带 Cents
- 所有写操作必须幂等，幂等键写在注释里
- 完成后运行 make verify
```

### 为什么这样拆就成

```text
① 每步 1~3 个文件 → 上下文小、幻觉少
② 每步有验收命令 → 「看起来对」被机器拦住
③ 步骤 2 先写测试 → 后续实现有独立判据
④ 步骤之间有明确契约 → 可以并行（步 4 和 6 可同时做）
⑤ 任何一步失败 → 只回滚这一步，不推翻全部
```

### 实际耗时对比（同一团队）

| 方式 | 首个可运行版本 | 编译错误 | 返工 |
| --- | --- | --- | --- |
| 一把梭 | 未达成（2 天后放弃） | 90+ | — |
| 6 步法 | **1.5 天** | 6 | 2 次小返工 |

> 💡 **拆解本身就是设计**。能把需求拆成「每步都能验证」的人，其实已经想清楚了架构——模型只是把这个设计的打字工作接过去。

## 46.15 一页速记

| 关键词 | 必须记住的结论 |
| --- | --- |
| 本质 | 不是「模型不够强」，是**信息不够 + 验证不够 + 切分不对** |
| 约束一 | 3 万行项目 ≈ 36 万 token，**装不进任何窗口**；有效窗口只有标称的 50~70% |
| 约束二 | 模型无长期记忆，**规则文件是它的记忆** |
| 约束三 | 「看起来对」≠「编译通过」，**没有验证的生成等于把工作转移给你** |
| 约束四 | 隐式知识不在代码里，**不写下来模型就会改错** |
| 三路径 | 分治（做哪块）/ 增量（怎么做）/ 可检索（怎么找到） |
| 粒度 | 一次 1~3 文件、200~600 行；超过就拆 |
| 三问判据 | 要读 > 5 文件？→ 拆；不能一条命令验证？→ 先补验证；会静默出错？→ 人工主导 |
| 预算 | 相关代码 ≤ 40%；历史必须摘要；输出必须预留 |
| 双修 | **为模型做的工程改造 = 还代码库可维护性的债**；同一份文档服务新人和模型 |
| 一句话 | **秘诀不是「让它写更多」，是「让它每次只需要知道更少，并且立刻知道对不对」。** |

## 46.16 自检题

1. **为什么「把整个仓库塞进 200k 上下文」不可行？给出两个理由。**
   > 要点：① 容量不够：3 万行 ≈ 36 万 token；且有效窗口只有 50~70%（系统提示、历史、输出预留、lost-in-the-middle 衰减）；② 即使装得下，噪声会淹没信号，模型抓不住本次改动相关的部分，且成本随 token 线性上升。正解是「只塞本次需要的 + repo map 给全局」。

2. **模型生成了一段「看起来完全正确」的代码，你怎么在 5 分钟内判断它能不能用？**
   > 要点：跑 `make verify`（编译 → vet → lint → 单测 -race）。机器验证是唯一可靠判据。再补三看：是否重复实现了已有抽象（grep 类名）、是否调用了不存在的 API（编译会抓）、是否改了不该改的文件（git diff 范围）。绝不能只靠「读起来对」。

3. **团队想用模型重构一个跨 20 个文件的模块，你应该怎么拆？**
   > 要点：不要一次做。① 人工定目标架构与迁移顺序；② 先做「机械替换」类改动（改包名、提取接口），每步编译通过；③ 核心逻辑（并发/事务/权限）人工写，模型只 review；④ 每步小提交 + 可回滚；⑤ 用契约测试保证外部行为不变。判断标准：**任何一步失败，都能在 5 分钟内回滚**。
