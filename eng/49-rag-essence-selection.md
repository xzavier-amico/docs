## 49.1 事故现场：知识库上线三个月，客服不用了

2025 年 6 月，某 SaaS 公司给客服团队上了 RAG 知识库：把 1.2 万篇帮助文档切片、embedding 进向量库，top-5 召回后拼进 prompt。

上线时 demo 效果惊艳——问「怎么导出数据」，答得比老客服还准。

三个月后，产品经理做了一次使用统计：

| 指标 | 数值 |
| --- | --- |
| 日均提问 | 从 1,400 降到 **210** |
| 客服主动使用率 | **8%**（其余仍靠人肉搜文档） |
| 「答非所问」投诉 | 每周 30+ |
| 平均会话轮次 | 1.3（问一次就放弃） |

拉出 200 条 badcase 人工标注，问题分布是：

```text
召回错误（检索到的段落根本不含答案）        112 条  56%
召回正确但答案被截断/拼接错乱               38 条  19%
召回了旧版本文档（同一问题有 3 个版本）      27 条  14%
答案正确但用户不信（没有出处链接）            15 条   8%
其他                                          8 条   4%
```

**没有一条是「模型不够聪明」。全是检索层的问题。**

而团队最初的方案里，「检索」只占了两行代码：

```python
docs = vector_store.similarity_search(question, k=5)
prompt = f"根据以下资料回答：\n{docs}\n\n问题：{question}"
```

这正是本章要纠正的认知：**RAG 是一个检索系统，不是一个 prompt 技巧。** 90% 的 RAG 质量问题出在「检索」而不是「生成」，而绝大多数团队把 90% 的精力花在了「生成」上。

## 49.2 精确定义：RAG 到底在弥补什么

### 一句话定义

> **RAG（Retrieval-Augmented Generation）= 在生成之前，用一次「检索」把模型参数里没有、或已经过时的知识，以原文片段的形式注入上下文。**

拆开看，它只做了三件事：

```text
Retrieve（检索）→ Augment（拼进上下文）→ Generate（生成）
     ↑                  ↑                    ↑
  90% 的问题在这    10% 的问题在这       10% 的问题在这
```

### 它弥补的是参数化知识的三个缺陷

| 缺陷 | 表现 | RAG 怎么补 | 不能补的替代方案 |
| --- | --- | --- | --- |
| **时效性** | 模型训练截止后的事它不知道 | 检索最新文档 | 微调（也会过期）、长上下文（塞不下全部） |
| **私有性** | 你的内部制度、客户数据它没见过 | 检索私有库 | 微调（成本高、更新慢、有泄露风险） |
| **可溯源性** | 它说了但你不知道依据是什么 | 返回原文 + 出处 | 微调做不到（知识被压进参数，无法定位） |

**这三条是 RAG 存在的全部理由。** 如果你的场景一条都不占，就不该用 RAG（§49.4）。

### 四个反例：这些都不是 RAG

```text
反例 1：只搭了向量库，没有「检索→注入」链路
  → 那是一个「向量数据库」，不是 RAG。

反例 2：把整本手册（20 万字）全塞进 prompt
  → 那是「长上下文」，不是 RAG。它可能更好（如果模型支持且成本可接受），
     也可能更差（中间信息丢失、成本爆炸）。两者是替代关系，不是同义词。

反例 3：用 RAG 查「我的订单到哪了」
  → 那是「结构化查询」，该用 SQL/API。向量检索查精确字段是灾难。

反例 4：把 RAG 当成「让模型说对话」的万能药
  → 模型不会因为多给几段文档就变聪明；它只会「照着文档说」。
     文档里没有的，它要么说不知道，要么编。
```

> 💡 **判据**：**「这个问题的答案，是否存在于某份可被检索的文本里？」**
> 是 → RAG 可能有用。否（需要计算、需要实时状态、需要推理）→ 别用 RAG。

## 49.3 技术树：RAG 不是一个技术，是八个决策点

```text
                              ┌─────────────────┐
                              │   你的 RAG 系统   │
                              └────────┬────────┘
        ┌──────────┬──────────┬────────┼────────┬──────────┬──────────┐
        ▼          ▼          ▼        ▼        ▼          ▼          ▼
   ① 切分      ② 索引      ③ 查询改写 ④ 检索   ⑤ 融合     ⑥ 重排    ⑦ 生成   ⑧ 评测
   Chunking   Embedding   Rewrite   Retrieve   Fusion    Rerank    Generate  Eval
      │          │          │        │         │          │          │        │
   固定长度    稠密向量    同义扩展  向量检索    RRF       Cross-   拼上下文  Recall@k
   语义切分    稀疏BM25    多查询    关键词     加权       Encoder  引用标注  MRR/nDCG
   父子文档    混合索引    HyDE     图检索     去重       LLM 打分  拒答策略  Groundedness
   按标题      多向量     分解子问题  SQL/API    ─        ─        压缩     人工抽检
```

**八个决策点里，只有 ②④ 是「买什么产品」，其余都是「怎么设计」。** 这就是为什么换个更贵的向量库通常救不了 RAG——问题往往在 ①③⑤⑥⑧。

### 每个决策点的一句话结论

| # | 决策点 | 一句话结论 | 默认选择 |
| --- | --- | --- | --- |
| ① | 切分 | **切分决定召回上限**；切错了，后面再强也召不回 | 按标题/语义切，400~800 token，带 10~20% overlap |
| ② | 索引 | 稠密向量擅长语义，BM25 擅长精确词；**两者都要** | 混合索引（向量 + 全文） |
| ③ | 查询改写 | 用户的问法和文档的写法往往不一样 | 先做同义扩展 + 多查询，再考虑 HyDE |
| ④ | 检索 | top-k 不是越大越好；k 大了噪声压过信号 | 召回 20~50，重排后取 3~5 |
| ⑤ | 融合 | 多路召回需要合并排序 | RRF（Reciprocal Rank Fusion） |
| ⑥ | 重排 | **重排是性价比最高的一步**：几十毫秒换 10~20 个点准确率 | Cross-Encoder 或 LLM rerank |
| ⑦ | 生成 | 上下文不是越多越好；**要给模型「拒答」的出口** | 3~5 段 + 出处 + 明确「不知道就说不知道」 |
| ⑧ | 评测 | 没有评测集的 RAG 是玄学 | 100~300 条标注问答，跑 recall@k 与 groundedness |

## 49.4 什么时候根本不该用 RAG

这一节比「怎么用 RAG」更值钱。**下面五条，命中任何一条，先考虑替代方案。**

| # | 场景特征 | 为什么 RAG 不合适 | 该用什么 |
| --- | --- | --- | --- |
| 1 | **数据量很小**（< 50 页 / < 5 万 token） | 全部塞进 prompt 就行，检索只会引入噪声 | 长上下文 / 直接拼 prompt |
| 2 | **需要精确聚合**（「本月销售额多少」「有多少个未处理工单」） | 向量检索是「相似」，不是「求和/计数」 | SQL / 数仓 / API |
| 3 | **强事务/实时状态**（订单状态、库存、账户余额） | 文档是快照，检索到的是过期状态 | 直接查库（工具调用） |
| 4 | **答案需要多步推理而非查找**（「比较 A 和 B 哪个更适合我们」） | 检索只能给素材，推理要靠模型或人 | 检索 + 明确的分析框架，或 Agent 多步 |
| 5 | **数据实时变化且要求秒级一致**（价格、库存） | 索引更新有延迟，且无法保证一致 | 实时 API + 缓存 |

### 替代方案对照表

| 你的真实需求 | 更便宜/更准的做法 | 成本对比（相对 RAG） |
| --- | --- | --- |
| 让模型知道公司制度 | 长上下文（如果 < 100k token） | 每次调用更贵，但省掉整套检索设施 |
| 让模型会按格式回答 | 微调 / few-shot | 一次性成本，无检索延迟 |
| 查业务数据 | Function Calling / MCP 工具 | 更准、更实时 |
| 找相似案例 | 向量检索（这就是 RAG 的核心） | 相同 |
| 找精确编号/条款 | BM25 / 全文索引 | 更便宜、更准 |

> ⚠️ **最常见的过度工程**：一个只有 30 页产品手册的客服机器人，上了向量库 + 重排 + 查询改写，延迟 800ms、成本翻 5 倍，效果还不如把 30 页全塞进去。
> **先问「数据有多大」，再问「要不要 RAG」。**

## 49.5 怎么实现：五段流水线与关键代码

### 全景

```text
离线（索引侧）                                在线（查询侧）
┌──────────────────────────┐                ┌──────────────────────────┐
│ 文档 → 解析 → 切分 → 向量化 │                │ 问题 → 改写 → 多路召回    │
│        ↓        ↓         │                │        ↓                 │
│     元数据    向量库+全文库 │ ── 同一份索引 ──▶ │ 融合(RRF) → 重排 → top-k │
└──────────────────────────┘                │        ↓                 │
                                            │ 拼上下文 + 出处 → 生成    │
                                            └──────────────────────────┘
```

### 第一段：切分（决定召回上限）

```go
// 语义切分：按标题层级切，超长再按句子窗口切，保留父子关系
type Chunk struct {
    ID       string
    DocID    string
    ParentID string // 父块：用于「小块召回、大块生成」
    Title    string // 标题路径，如 "退款政策 > 跨境订单 > 时效"
    Text     string
    Tokens   int
}

func SplitByHeading(doc Document, maxTokens int) []Chunk {
    var out []Chunk
    for _, sec := range doc.Sections { // 解析阶段已按 H1/H2/H3 拆好
        path := strings.Join(sec.HeadingPath, " > ")
        for _, w := range window(sec.Paragraphs, maxTokens, maxTokens/5) { // 20% overlap
            out = append(out, Chunk{
                ID: hash(doc.ID, path, w[0]), DocID: doc.ID,
                ParentID: sec.ID, Title: path,
                Text:     path + "\n" + strings.Join(w, "\n"), // 标题拼进正文，提升召回
                Tokens:   countTokens(w),
            })
        }
    }
    return out
}
```

**三条经验值**（不是定律，要按你的语料调）：

| 参数 | 默认 | 调整信号 |
| --- | --- | --- |
| chunk size | 400~800 token | 召回片段常被截断 → 调大；噪声多 → 调小 |
| overlap | 10~20% | 答案跨段丢失 → 调大 |
| 是否拼标题 | 是 | 文档标题含关键限定词（版本/地区）时必须拼 |

### 第二段：混合检索 + RRF 融合（完整可跑 SQL）

以 PostgreSQL + pgvector 为例（`tsvector` 做全文，`vector` 做语义）：

```sql
-- 表结构
CREATE EXTENSION IF NOT EXISTS vector;
CREATE TABLE chunks (
    id          BIGSERIAL PRIMARY KEY,
    doc_id      TEXT NOT NULL,
    title_path  TEXT NOT NULL,
    content     TEXT NOT NULL,
    embedding   vector(1024) NOT NULL,           -- 维度按你的 embedding 模型
    tsv         tsvector GENERATED ALWAYS AS (to_tsvector('simple', content)) STORED,
    updated_at  TIMESTAMPTZ DEFAULT now()
);
CREATE INDEX ON chunks USING hnsw (embedding vector_cosine_ops);
CREATE INDEX ON chunks USING gin (tsv);
CREATE INDEX ON chunks (doc_id);

-- 混合检索 + RRF 融合（k=60 是常用经验值）
WITH vec AS (
    SELECT id, ROW_NUMBER() OVER (ORDER BY embedding <=> $1) AS rank
    FROM chunks
    ORDER BY embedding <=> $1
    LIMIT 50
),
kw AS (
    SELECT id, ROW_NUMBER() OVER (ORDER BY ts_rank_cd(tsv, plainto_tsquery('simple', $2)) DESC) AS rank
    FROM chunks
    WHERE tsv @@ plainto_tsquery('simple', $2)
    LIMIT 50
)
SELECT c.id, c.title_path, c.content,
       COALESCE(1.0/(60 + v.rank), 0) + COALESCE(1.0/(60 + k.rank), 0) AS score
FROM chunks c
LEFT JOIN vec v ON v.id = c.id
LEFT JOIN kw  k ON k.id = c.id
WHERE v.id IS NOT NULL OR k.id IS NOT NULL
ORDER BY score DESC
LIMIT 20;   -- 召回 20，交给重排
```

> 💡 **RRF 的好处**：不需要把「余弦相似度」和「BM25 分数」归一化到同一量纲——只用了**排名**。这就是它成为默认融合算法的原因。

### 第三段：重排（性价比最高）

```java
// Cross-Encoder 重排：把 (query, passage) 一起送进模型打分，比向量相似度准得多
public List<Chunk> rerank(String query, List<Chunk> candidates, int topK) {
    List<Pair<Chunk, Double>> scored = new ArrayList<>();
    for (Chunk c : candidates) {                       // 20~50 条
        double s = reranker.score(query, c.getContent()); // 本地模型或 API
        scored.add(Pair.of(c, s));
    }
    return scored.stream()
        .sorted(Comparator.comparingDouble(Pair::getRight).reversed())
        .limit(topK)
        .map(Pair::getLeft)
        .toList();
}
```

**代价与收益**（实测区间，按你的语料会有差异）：

| 方案 | 延迟 | 准确率提升 | 成本 |
| --- | --- | --- | --- |
| 不重排 | 0 | 基线 | 0 |
| 小模型 Cross-Encoder（本地） | +20~50ms | +8~15 点 | GPU/CPU 资源 |
| LLM rerank（API） | +300~800ms | +10~20 点 | 每 query 一次调用 |
| 向量相似度当重排 | +1ms | +0~3 点 | 0（基本没用） |

### 第四段：生成（给模型「拒答」的出口）

```text
你是客服助手。只根据【资料】回答，不要使用资料外的知识。
如果资料不足以回答，直接说「我在知识库里没找到相关内容」，不要猜测。
回答末尾用 [1][2] 标注引用的资料编号。

【资料】
[1] {title_path_1}
{content_1}
[2] {title_path_2}
{content_2}
...

【问题】{question}
```

> 🩸 **不加「拒答」指令的 RAG 一定会编**：模型看到 5 段不相关的资料，也会硬凑一个答案——因为它的训练目标是「有用」，不是「诚实」。

## 49.6 双修对照：传统搜索 vs RAG

这一章是「双修」最典型的例子：**检索的技术栈几乎完全相同，变的是「消费者」。**

| 维度 | 传统搜索（人消费） | RAG（模型消费） | 相同 / 差异根因 |
| --- | --- | --- | --- |
| **检索目标** | 给用户 10 条结果，让他自己点 | 给模型 3~5 段，**必须包含答案** | 人对噪声容忍度高，模型会被噪声带偏 |
| **核心指标** | 点击率、首条点击率 | **Recall@k**（答案在不在里面）、Groundedness | 人看排名，模型看「有没有」 |
| **查询形态** | 关键词，短 | 自然语言问句，长 | 需要查询改写 |
| **结果展示** | 标题 + 摘要 + 链接 | 原文片段 + 出处 | 相同：都要可溯源 |
| **排序信号** | 点击反馈、时效、权威性 | 语义相关性为主 | RAG 缺反馈闭环 |
| **失败代价** | 用户换个词再搜 | 模型直接编造 | RAG 的失败更隐蔽 |
| **更新频率** | 可天级 | 常要求分钟级 | 索引更新成为瓶颈 |
| **评测方法** | A/B + 人工 | 标注集 + LLM-as-judge + 人工抽检 | 方法不同，都要有 |

**结论**：**RAG = 传统检索系统 + 一个新的、更挑剔的消费者。** 所以：

1. 传统搜索的积累（分词、同义词、BM25、rerank、评测）**全部可复用**，不要从零发明。
2. 但所有参数要重调：`k` 从 10 变成 3~5，排序目标从「用户会点」变成「包含答案」，必须加「拒答」。
3. Agent 侧多一层：检索本身可能是**工具调用**（模型决定什么时候检索、检索什么），见 `../llm/20-rag-engineering.md`。

| Agent 特有 | 说明 | 对策 |
| --- | --- | --- |
| **检索时机由模型决定** | 模型可能不检索就答，或反复检索 | 强制检索的场景 + 检索次数上限 |
| **查询由模型生成** | 可能生成很差的查询 | 多查询 + 查询改写 + 失败后重写 |
| **上下文预算竞争** | 检索结果挤占对话历史 | 按 token 预算分配（第 46 章） |
| **记忆 vs 知识库** | 两者都是检索，但生命周期不同 | 分开存储、分开索引、分开评测 |

## 49.7 会在哪炸：十个失效模式

| # | 失效模式 | 现象 | 根因 | 怎么查 | 怎么修 |
| --- | --- | --- | --- | --- | --- |
| 1 | **切分切断答案** | 召回片段只有半句话 | 固定长度切分，切断表格/步骤 | 看 badcase 的 chunk 边界 | 语义切分 + overlap + 父子块 |
| 2 | **旧版本文档混入** | 答的是去年的政策 | 索引没删旧文档 / 无版本过滤 | 查 chunk 的 `updated_at` 与版本字段 | 版本元数据 + 检索时过滤 |
| 3 | **精确词召不回** | 搜「ERR-4021」找不到 | 纯向量检索对编号不敏感 | 对比 BM25 与向量结果 | 混合检索 + RRF |
| 4 | **k 太大引入噪声** | 答案对，但模型被无关段落带偏 | top-k=20 直接拼进 prompt | 对比 k=3/5/10 的答案质量 | 召回大、重排后取小 |
| 5 | **表格/图片丢失** | 文档里的表格变成乱码 | 解析器不支持 | 看解析后的文本 | 专用解析器 + 表格转 Markdown |
| 6 | **多跳问题答不了** | 「A 和 B 的政策差异」只答了一半 | 单次检索只覆盖一个实体 | 看召回是否只含一侧 | 查询分解 + 多轮检索 |
| 7 | **权限穿透** | 用户看到了别的租户的文档 | 检索没带租户过滤 | 构造越权查询测试 | 检索层强制 `tenant_id` 过滤 |
| 8 | **索引延迟** | 刚更新的文档搜不到 | 批量索引周期长 | 对比文档更新时间与索引时间 | 增量索引 + 更新后主动刷新 |
| 9 | **幻觉引用** | 标了 [1] 但 [1] 里没这句话 | 模型编造引用 | 校验引用片段是否包含关键实体 | 引用校验 + 只允许抽原文 |
| 10 | **评测集污染** | 离线 92 分，线上 60 分 | 评测问题与训练/索引重叠 | 检查评测集来源 | 时间切分 + 独立标注 |

> 🩸 **第 7 条是事故级**：RAG 的权限过滤必须做在**检索层**（SQL/向量库的 where 条件），不能做在「生成后过滤」——那时模型已经看到了。

## 49.8 怎么验证：没有评测集的 RAG 是玄学

### 离线评测（上线前必须有的三张表）

| 指标 | 定义 | 目标（参考） | 怎么算 |
| --- | --- | --- | --- |
| **Recall@k** | 标注答案所在 chunk 是否出现在 top-k | ≥ 90%（k=5） | 标注集逐条命中统计 |
| **MRR** | 第一个正确结果的排名倒数均值 | ≥ 0.7 | `mean(1/rank)` |
| **Groundedness** | 答案中的断言能否在召回片段中找到依据 | ≥ 95% | LLM-as-judge + 人工抽检 |
| **Answer Accuracy** | 答案与标准答案一致 | 按业务定 | 人工/LLM 评判 |
| **Refusal Correctness** | 该拒答时是否拒答 | ≥ 90% | 构造 50 条「库里没有」的问题 |

### 评测集怎么建（100~300 条就够起步）

```text
1. 从真实日志里采样问题（不是自己编）—— 至少 60%
2. 每条标注：标准答案 + 依据的文档 ID + 该文档的 chunk
3. 故意加入 10~20%「库里没有答案」的问题，测拒答
4. 按时间切分：评测集里的文档不能与索引完全重叠（防污染）
5. 每次改切分/模型/重排，都跑同一套，记录版本
```

### 线上指标（离线好不代表线上好）

| 指标 | 含义 | 异常信号 |
| --- | --- | --- |
| 检索命中率（有点击/有引用） | 召回是否为空 | 突降 → 索引挂了/过滤条件错 |
| 平均召回条数 | top-k 实际返回 | 变少 → 索引缺失 |
| 拒答率 | 模型说「不知道」的比例 | 突增 → 召回质量下降 |
| 用户追问率 | 同一问题 30s 内再问 | 升高 → 答非所问 |
| 引用点击率 | 用户点开出处 | 降低 → 不信任 |
| P99 延迟 | 检索 + 重排 + 生成 | 突增 → 重排/向量库慢 |

### 一个可执行的对比实验

```bash
# 固定评测集，逐项开启，看每一步的边际收益
run_eval --config baseline.yaml          # 纯向量 top5
run_eval --config +hybrid.yaml           # 向量 + BM25 + RRF
run_eval --config +rerank.yaml           # 加 Cross-Encoder
run_eval --config +rewrite.yaml          # 加查询改写
# 输出：recall@5 / MRR / groundedness / p99 / 单次成本
```

> 💡 **经验**：**混合检索 + 重排**通常带来最大的两个跳跃（合计 +15~25 点 Recall@5）；查询改写收益不稳定，可能 +5 也可能 -3，必须用评测集验证，不能凭感觉加。

## 49.9 用什么工具：分层选型

| 层 | 开源/自建 | 托管服务 | 选型建议 |
| --- | --- | --- | --- |
| **向量库** | pgvector、Milvus、Qdrant、Weaviate | Pinecone、Zilliz Cloud | 已有 PG 且量 < 千万级 → **pgvector 起步**；亿级/高并发 → Milvus/Qdrant |
| **全文检索** | Elasticsearch / OpenSearch | 阿里云 ES | 已有 ES 就直接用，别为 RAG 再引一套 |
| **Embedding** | BGE-M3、E5、Jina | OpenAI/Cohere/各家云 | 中文优先 BGE-M3；必须用**同一模型**建库与查询 |
| **重排** | bge-reranker、Cohere Rerank | 各家 API | 先上本地小模型，不够再上 API |
| **解析** | Unstructured、Marker、MinerU | 云文档解析 | 表格/扫描件多 → 专用解析器 |
| **编排** | LangChain / LlamaIndex | — | 原型可用，生产建议自己写 300 行（见 §49.7 的坑） |
| **评测** | Ragas、TruLens、自研 | — | 自研脚本 + 标注集最可靠 |

**成本算式**（每次查询）：

```text
单次成本 = embedding(问题) + 向量检索 + 重排 + 生成
        ≈ $0.00002 + $0.0001 + $0.0005 + (输入 token × 单价 + 输出 token × 单价)
        ≈ $0.0006 + 0.0035 ≈ $0.004 / 次   （以 5 段 × 500 token、输出 300 token 估算）

10 万次/天 → $400/天 ≈ $12k/月
其中生成占 ~85%，检索+重排只占 ~15%
```

> ⚠️ 所以「优化 RAG 成本」的主战场是**减少上下文 token**（更好的重排、更小的 k），不是换更便宜的向量库。

## 49.10 一页速记

| 关键词 | 必须记住的结论 |
| --- | --- |
| 本质 | 用检索弥补参数化知识的**时效性、私有性、可溯源性**三个缺陷 |
| 不是 | 不是向量库、不是长上下文、不是万能药、不是「让模型变聪明」 |
| 质量分布 | **90% 的问题在检索层**，不在生成层 |
| 技术树 | 八个决策点：切分/索引/改写/检索/融合/重排/生成/评测 |
| 默认栈 | 语义切分 + 混合检索（向量+BM25）+ RRF + Cross-Encoder 重排 + 3~5 段 + 拒答指令 |
| 不该用 | 数据 < 50 页、需要聚合、强事务实时状态、多步推理、秒级一致 → 换方案 |
| 切分 | **切分决定召回上限**；400~800 token，10~20% overlap，标题拼进正文 |
| 重排 | **性价比最高的一步**：几十毫秒换 10~20 点准确率 |
| 权限 | 过滤必须做在**检索层**，不能生成后过滤 |
| 评测 | 100~300 条真实问题 + 10~20% 无答案题；看 Recall@5 / MRR / Groundedness |
| 双修 | 检索技术栈几乎全复用，**消费者从人变成模型**：k 变小、要拒答、要溯源 |

## 49.11 自检题

1. **老板说「我们上个向量库就能解决知识问答」，你怎么反驳？**
   > 要点：向量库只是八个决策点里的一个（索引）。RAG 的质量主要取决于切分、混合检索、重排、拒答与评测。先问三个问题：数据量多大（< 50 页直接塞 prompt）、问题是否需要聚合/实时状态（是则用 SQL/API）、有没有评测集（没有就无法证明有效）。给出「先做 100 条评测集 + 基线，再逐项加技术」的路径。

2. **为什么「召回 20 条、重排取 5 条」比「直接召回 5 条」效果好？代价是什么？**
   > 要点：召回阶段用便宜但粗糙的方法（向量/BM25）扩大候选集，保证答案在集合里（Recall 高）；重排用贵的模型（Cross-Encoder）精排，保证进入 prompt 的是最相关的（Precision 高）。代价是重排的延迟（+20~800ms）与算力；k 太大也会引入噪声，所以重排后仍要截断到 3~5 条。

3. **一个 RAG 系统离线 Recall@5 = 93%，线上用户却大量追问。列出三种可能原因。**
   > 要点：① 线上查询分布与评测集不同（评测集自编、线上是口语/错别字/多语言）；② 索引延迟/版本错（线上检索到旧文档）；③ 权限过滤过严导致召回为空；④ 生成层问题（上下文正确但答案被截断/模型没按资料说）；⑤ 评测集的「正确答案」标准与用户期望不一致。排查顺序：先看线上召回是否为空，再看 chunk 是否含答案，最后看生成。
