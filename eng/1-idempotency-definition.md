# 1. 幂等的精确定义与边界：你到底「确保」了什么

## 1.1 事故现场：340 万是怎么没的

2026 年 3 月，某零售平台做拉新活动：新用户首单立减 50 元，券由「下单服务」在创建订单时发放。

活动第一天中午，运营发现券的发放量是新增订单量的 **1.8 倍**。追查下来是一条再普通不过的链路：

```
用户点击「提交订单」
  → 网关超时（3s），客户端自动重试
  → 第二次请求到达时，第一次的订单还在写库（未提交）
  → 下单服务先「查有没有未支付订单」→ 没查到
  → 两次都走了「创建订单 + 发券」
```

结果：**重复订单 6.2 万笔、重复发券 12.4 万张、直接损失 340 万**，还额外花了 11 个人天做人工核销与客服解释。

事故复盘会上，后端负责人说了一句话，是本章存在的理由：

> 「我们做了幂等啊，下单前查了一下有没有重复订单。」

**「先查一下」不是幂等。** 它是「降低重复概率」，而幂等要求的是「重复发生时不产生额外后果」。这两者的差距，就是 340 万。

## 1.2 精确定义：N 次执行 ≡ 1 次执行

### 数学定义（了解即可）

对函数 `f`，若对定义域内任意 `x` 都有：

```
f(f(x)) = f(x)
```

则称 `f` 是幂等的。注意它**只约束「结果」**，不约束「执行了几次」。

### 业务定义（真正要用的）

对一次业务操作 `Op(x)`，若满足：

| 维度 | 要求 |
| --- | --- |
| **结果等价** | 执行 1 次与执行 N 次，返回给调用方的**业务结果**相同（可以是同一条记录、也可以是一个明确的「已处理」） |
| **副作用等价** | 执行 1 次与执行 N 次，对外部世界造成的**净变化**相同（钱只扣一次、券只发一张、邮件只发一封） |
| **状态等价** | 执行 N 次后，系统状态与执行 1 次后一致（不会出现「状态被推进两次」） |

三条里**任何一条不满足，就不是幂等**。而绝大多数「假幂等」都挂在第二条上：接口返回了「已存在」，但券已经发出去了。

### 五个反例：这些都不是幂等

```go
// 反例 1：查询是「天然幂等」？——对系统状态是，但对「副作用」不是
func GetOrder(id string) (*Order, error) { ... }        // 没有副作用 → 天然幂等

// 反例 2：带自增的写入
db.Exec("UPDATE account SET balance = balance - 100 WHERE id = ?", id)
// 执行两次扣 200 → 不幂等

// 反例 3：先查后插（本章事故的写法）
if !exists(orderNo) { insert(order) }                    // 查询与插入之间有窗口 → 假幂等

// 反例 4：状态机推进
db.Exec("UPDATE orders SET status='PAID' WHERE id=?", id) // 第二次也是 PAID，看起来幂等……
// 但如果同时还有「PAID → 发券」「PAID → 通知仓库」的副作用，就会重复触发 → 假幂等

// 反例 5：发消息/发邮件/调三方
mq.Send("order.created", order)                          // 发两次就是两条消息 → 不幂等
```

> 💡 **一句话判据**：**「再执行一次，会不会有东西多出来？」**
> 会（多一条记录、多一笔钱、多一张券、多一条消息、多一次外部调用）→ 不幂等。
> 不会 → 幂等。注意：**「多一条日志」也算多**，只是通常可接受——所以幂等永远是有范围的（§1.4）。

## 1.3 三组必须分清的易混概念

| 概念 | 定义 | 解决什么 | 不能解决什么 | 典型实现 |
| --- | --- | --- | --- | --- |
| **幂等 Idempotency** | 重复执行不产生额外后果 | 重试安全 | 不保证不丢、不保证顺序、不保证只执行一次 | 唯一键、去重表、状态机 |
| **去重 Deduplication** | 识别并丢弃重复请求 | 重复流量 | 不保证状态正确（可能把「不同请求」误判为重复） | 请求指纹、布隆过滤器、幂等表 |
| **恰好一次 Exactly-once** | 端到端只生效一次 | 语义最强 | **分布式下无法单独由某一层保证** | 不丢（生产端确认）+ 幂等（消费端） |

再用一张图说清它们的关系：

```
「至少一次」投递 ──┬──▶ 重复到达 ──▶ 去重（识别）──▶ 幂等（吸收）──▶ 业务只生效一次
                  │
「至多一次」投递 ──┴──▶ 可能丢失 ──▶ 需要「不丢」机制（确认/重试/对账）
```

**结论**：所谓「恰好一次」，在工程上从来不是某一层的能力，而是 **「不丢」+「幂等」的组合结果**。任何声称「我们 MQ 支持 exactly-once 所以业务不用管」的说法，都是把责任推给了下游（第 11 章会拆穿它）。

## 1.4 边界：幂等保证了什么，没保证什么

这是最容易被跳过、也最容易在事故后被追问的一节。

| 幂等**保证**了 | 幂等**没有保证** |
| --- | --- |
| 重复请求不会造成**额外副作用** | 请求**不会丢**（丢了幂等也救不了） |
| 重试是安全的（可以放心重试） | 请求**不会乱序**（先到的可能后执行） |
| 结果可预期（第二次返回「已处理」而非报错） | 数据**一定正确**（幂等只防重复，不防算错） |
| 故障恢复后可以安全重放 | **不会越权**（同样的请求换个用户照样能执行） |
| — | **不会超时**（幂等不解决慢） |

所以完整的正确性公式是：

```
端到端正确 = 不丢（确认/重试/对账）
           + 不重（幂等）
           + 不错（校验/对账）
           + 不乱（顺序/版本）
```

**幂等只负责第二项。** 这就是为什么第 14 章要单独讲对账——因为幂等永远发现不了「算错了」和「丢了一条」。

### 幂等的范围：不是所有副作用都值得幂等

| 副作用 | 要不要幂等 | 理由 |
| --- | --- | --- |
| 扣款、退款、发券、扣库存 | **必须** | 直接资金/资产损失 |
| 创建订单、创建工单 | **必须** | 重复数据难清理，影响对账 |
| 发邮件/短信/推送 | **应该** | 用户体验 + 投诉成本；可用「幂等键 + 去重窗口」 |
| 写日志、打点 | **不需要** | 多一条可接受，强行幂等反而增加成本 |
| 查询、读接口 | **不需要** | 无副作用（但要注意缓存与计数的副作用） |
| 调三方「查询类」接口 | **不需要** | 但要限流与超时（第 15 章） |

> ⚠️ **反模式**：给所有接口无脑加幂等表。结果是写放大、TTL 管理、清理任务、存储成本全上来了，而真正危险的三个接口反而没覆盖。**幂等要按副作用分级做**（第 4 章订单场景会给分级表）。

## 1.5 幂等的成本：它从来不是免费的

| 成本项 | 具体表现 | 量级参考 |
| --- | --- | --- |
| **一次额外写** | 幂等表/去重表插入 | 每次请求 +1 次写入；QPS 5k → 多 5k TPS 写入 |
| **一次额外读** | 先查幂等表 | +1 次 RT（Redis 0.2ms / MySQL 1ms） |
| **存储** | 幂等键留存 | 5k QPS × 86400 × 7 天 × 100B ≈ **300 GB** |
| **TTL 管理** | 过期清理、分区删除 | 需要定时任务与监控 |
| **复杂度** | 键的设计、异常分支、测试 | 每个写接口 +2~3 人天 |
| **一致性** | 幂等表与业务表的事务边界 | 跨库时需 Outbox（第 10 章） |

**所以幂等的第一原则是：先分级，再做。** 不是所有写接口都值得付这笔钱。

## 1.6 双修对照：传统系统 vs Agent 系统

| 维度 | 传统系统 | Agent 系统 | 相同 / 差异根因 |
| --- | --- | --- | --- |
| **幂等身份** | `request_id` / 订单号 / 支付流水号 | `run_id` + `step_id` + `tool_call_id` | 结构相同；Agent 多一层「步骤」粒度 |
| **重复来源** | 用户重复点击、网关重试、MQ 重投 | 以上全部 + **模型重试** + **工具重放** + **HITL 恢复重跑** | Agent 的重复源更多 |
| **结果是否可复现** | 同输入必同输出 | **同输入可能不同输出**（采样/版本漂移） | 差异根因一：非确定性 |
| **幂等键能否用内容 hash** | 可以（参数稳定） | **不行**：prompt 里的时间戳、检索结果顺序、模型版本都会变 | 差异根因二：输入不稳定 |
| **副作用规模** | 一笔钱、一条记录 | 一次工具调用可能删文件/发邮件/下单 | 相同机制，**后果更重** |
| **验证方式** | 并发压测 + 对账 | 并发压测 + **重放同一条 trace** + 对账（token/调用次数） | 方法同构，Agent 多了重放 |

**结论**：
1. **幂等的表结构、去重逻辑、状态机前置校验可以 100% 复用**——这部分没有「Agent 版」。
2. 真正需要重新设计的是**幂等键的组成**：必须包含「模型版本 + 提示词版本 + 工具版本」，否则一次版本升级会让所有历史幂等键失效（或者更糟：把不同结果误判为重复）。
3. Agent 侧多了一个传统没有的问题：**「同参不同果」时，重放到底是「重复」还是「新的一次尝试」？** 工程上的答案是：**以「业务意图」为幂等粒度**（用户的一次请求 = 一个 `run_id`），而不是以「模型调用」为粒度。

```go
// Agent 侧幂等键的正确组成（示意）
func idempotencyKey(req RunRequest, step Step, tool ToolCall) string {
    h := sha256.New()
    io.WriteString(h, req.TenantID)
    io.WriteString(h, req.RunID)        // 业务意图粒度
    io.WriteString(h, step.ID)          // 步骤粒度
    io.WriteString(h, tool.Name)
    io.WriteString(h, canonicalJSON(tool.Args)) // 规范化参数
    io.WriteString(h, req.ModelVersion) // 版本进键：升级后不复用旧结果
    io.WriteString(h, req.PromptVersion)
    return hex.EncodeToString(h.Sum(nil))
}
```

> 详细实现见第 2 章；订单/金融场景见第 3、4 章；Agent 工具幂等见 `../llm/22-tool-system-mcp.md`。

## 1.7 判定问答 20 条（评审会直接念）

给每个写接口过一遍，**任何一条答「否」就要在设计文档里写清为什么可以接受**。

| # | 问题 | 期望 |
| --- | --- | --- |
| 1 | 这个接口会不会修改资金/资产/权益？ | 会 → 必须幂等 |
| 2 | 重复执行会不会多出记录？ | 会 → 必须有唯一约束或去重 |
| 3 | 幂等键是什么？由谁生成？ | 明确到字段 |
| 4 | 幂等键在客户端还是服务端生成？ | 客户端生成（可重试）；服务端生成不可靠 |
| 5 | 幂等键的 TTL 多长？覆盖最长重试窗口吗？ | ≥ 重试窗口 × 2 |
| 6 | 「先查后写」的窗口有多大？ | 有窗口 → 必须靠唯一约束兜底 |
| 7 | 并发 200 同参请求会发生什么？ | 只有 1 条生效 |
| 8 | 唯一索引冲突时返回什么？ | 返回成功（幂等语义），不是 500 |
| 9 | 幂等表与业务表在同一事务吗？ | 跨库 → 需要 Outbox/对账 |
| 10 | 第二次请求的响应与第一次一致吗？ | 一致，或明确返回「已处理」 |
| 11 | 幂等失败（如去重表写失败）会怎样？ | 有降级策略，不能静默放过 |
| 12 | 幂等命中会打点吗？ | 有指标：`idempotent_hit_total` |
| 13 | 幂等键里有没有可变字段（时间戳/随机数）？ | 不能有 |
| 14 | 版本升级后旧幂等键怎么办？ | 版本进键或显式失效 |
| 15 | 重试时 `request_id` 会变吗？ | 不能变（这是最常见的坑） |
| 16 | 网关重试与服务重试会叠加吗？ | 只允许一层重试带新 ID |
| 17 | 幂等与顺序冲突时怎么处理？ | 幂等优先，顺序用版本号 |
| 18 | 幂等表怎么清理？会影响正在重试的请求吗？ | 分区删除 + TTL 双保险 |
| 19 | 出问题怎么证明「只生效了一次」？ | 有审计日志/事件可查 |
| 20 | 有没有测试用例覆盖并发重复？ | 有 200 并发同参的集成测试 |

## 1.8 幂等键怎么设计：一棵决策树

幂等做不对，一半以上是「键选错了」。键不是随便一个 UUID，它要满足三条：

```text
① 唯一性：同一个业务意图，每次重试都得到同一个键
② 稳定性：键里的任何字段都不能随时间/环境变化（不能用 now()、随机数、会话 ID）
③ 可定位：能从键反查到「这是谁的哪次操作」（便于排障与对账）
```

### 决策树

```text
这次操作的「业务意图」能不能用业务单号唯一标识？
├── 能（订单号、退款单号、外部流水号）
│     键 = 业务单号          ← 首选：天然幂等，跨服务/跨天都稳定
│     ⚠️ 但要确认：一个单号是否允许多次操作？（部分退款 → 需要子单号）
└── 不能
      ├── 客户端能生成并保存一个 ID 吗？（App/H5 本地生成）
      │     ├── 能 → 键 = 客户端生成的 requestID（UUID/ULID）
      │     │        ⚠️ 必须在「用户点击」时生成一次，重试复用同一个
      │     └── 不能（如第三方回调）
      │           └── 键 = 外部系统的唯一号（支付流水号/消息 msgId）
      └── 都没有 → 键 = hash(全部业务参数 + 操作类型)
                   ⚠️ 最不可靠：参数顺序/精度/时区变化都会让键漂移
```

### 四种键的对比

| 键类型 | 稳定性 | 可读性 | 适用 | 风险 |
| --- | --- | --- | --- | --- |
| **业务单号** | 极高 | 高 | 订单/退款/审批 | 一单多操作时会误判（需子单号） |
| **客户端 requestID** | 高 | 中 | 用户主动提交 | 客户端未复用会失效（最常见坑） |
| **外部唯一号** | 高 | 中 | 支付回调/三方通知 | 外部可能重复或不提供 |
| **参数 hash** | 低 | 低 | 兜底 | 参数微变即漂移；升级后全线失效 |

```go
// 推荐：优先业务号，退化到 requestID，最后才是 hash
func IdempotencyKey(req CreateOrderReq) string {
    if req.OrderNo != "" {
        return "order:" + req.OrderNo
    }
    if req.RequestID != "" {
        return "req:" + req.RequestID
    }
    // 兜底：规范化后再 hash（排序参数、金额用分、时间用 UTC）
    return "hash:" + sha256hex(canonicalJSON(req))
}
```

> 🩸 **「参数 hash」为什么排最后**：`{"amount": 10.0}` 与 `{"amount": 10}`、`{"ts":"2026-09-15T10:00:00+08:00"}` 与 `{"ts":"2026-09-15T02:00:00Z"}` 会得到不同 hash，**同一个业务意图变成两个键**，幂等直接失效。用它之前必须先做规范化（canonical JSON）。

### 复合键：一个业务动作涉及多个实体时

```text
退款：key = refund_no（一次退款一个号）
部分退款：key = refund_no + item_id（同一退款单多次退不同商品）
库存扣减：key = order_no + sku_id（一单多 SKU）
幂等表：key = biz_type + biz_key（不同类型可能撞号）
```

**判据**：**「如果这两次调用被合并成一次，业务上会有损失吗？」**
会（少退一件商品、少扣一个 SKU）→ 键要更细；不会 → 用粗粒度键。

## 1.9 幂等的成本模型：什么时候不值得做

第 1.5 节给了成本项，这里给可算的公式，让你能回答「这个接口加幂等值不值」。

### 公式

```text
年化幂等成本 C = 存储成本 + 写入成本 + 复杂度成本

存储成本 = QPS × 86400 × 365 × 键大小 × 留存天数 / 86400 ... （按 TTL 折算）
         ≈ QPS × 留存秒数 × 键大小 × 副本数 × 单价

写入成本 = QPS × 1 次额外写 × 单次写成本
复杂度成本 ≈ 2~3 人天/接口（设计 + 测试 + 运维）
```

### 三个规模的算例

| 场景 | QPS | 键大小 | TTL | 存储量 | 月存储成本（$0.1/GB） | 评价 |
| --- | --- | --- | --- | --- | --- | --- |
| 内部后台 | 5 | 80B | 7 天 | 2.4 MB | ≈ 0 | 随便加 |
| 中等业务 | 500 | 80B | 7 天 | 242 MB | ≈ $0.02 | 无感 |
| 高频接口 | 50,000 | 80B | 30 天 | **10.4 GB** | ≈ $1 | 仍便宜 |
| 高频 + 大 payload | 50,000 | 2KB | 30 天 | **259 GB** | ≈ $26 | 要压缩/只存 hash |

> 💡 **结论**：**纯键的存储成本几乎可以忽略**（哪怕 5 万 QPS）。真正贵的是「复杂度」和「幂等表与业务表不同事务」带来的一致性风险。所以决策不该是「省存储」，而是「这个接口值不值得多 2 人天」。

### 什么时候不值得做

| 条件 | 例子 | 理由 |
| --- | --- | --- |
| 无副作用 | 查询、计算 | 重复执行无损失 |
| 副作用可叠加但无害 | 打点、日志 | 多一条可接受 |
| 重复概率极低且损失小 | 内部工具触发一次报表 | 成本 > 收益 |
| 有天然幂等 | `UPDATE ... SET status='X' WHERE id=?`（无条件推进） | 本身已幂等 |

> ⚠️ 但注意最后一条的陷阱：「无条件推进」在**有副作用时**并不幂等（第 1.2 节的五个反例之一）。**判断依据永远是「有没有东西多出来」，不是「SQL 长什么样」。**

## 1.10 事故二：一次「重试」把券发了三遍

第一个案例（§1.1）是「先查后写」；第二个案例是「重试换了键」——两者占了幂等事故的 70%。

某平台的「新人首单礼」：下单成功后发一张 50 元券。

```text
客户端点「提交订单」
  → 网关超时（5s），客户端 SDK 自动重试
  → 第二次请求带了新的 traceId，但 requestID 也重新生成了（SDK bug）
  → 服务端：两次 requestID 不同 → 幂等表认为是两次请求
  → 发了两张券
  → 用户发现后连点 5 次「再试一次」→ 共 6 张券
```

| 时间 | 事件 |
| --- | --- |
| 10:00:00 | 用户点击（requestID=R1） |
| 10:00:05 | 网关超时，SDK 重试（**requestID=R2**，bug） |
| 10:00:06 | 服务端处理 R1 成功，发券 |
| 10:00:07 | 服务端处理 R2，键不同 → 又发一张 |
| 10:00:20 | 用户看到「失败」，连点 5 次 → 又发 4 张 |
| 当日 | 受影响用户 1,842 人，多发券 3,106 张，损失 15.5 万 |

**三个缺陷**：

1. **SDK 每次重试重新生成 requestID**（应在「用户点击」时生成一次）。
2. **服务端没有「同一用户 + 同一商品 + 时间窗」的业务级兜底**（只有请求级幂等）。
3. **发券是同步调用且在事务内**，失败重试会重复执行。

**修复**：

```java
// 1) requestID 在用户点击时生成，重试复用（客户端）
String requestId = UUID.randomUUID().toString();   // 只生成一次，存入本次提交流程
retry(() -> api.createOrder(req.withRequestId(requestId)));

// 2) 服务端业务级兜底：同一用户同一活动只发一次（唯一索引）
// UNIQUE KEY uk_user_activity (user_id, activity_id)

// 3) 发券改为「状态机 + 事件驱动」，且用券的唯一业务键
INSERT INTO coupon(user_id, activity_id, coupon_no)
VALUES (?, ?, ?) ON DUPLICATE KEY UPDATE coupon_no = coupon_no;  -- 幂等
```

> 💡 **两级幂等**：**请求级**（防同一请求重试）+ **业务级**（防不同请求达到同一业务效果）。只做请求级，遇到「用户连点」就失效。

## 1.11 测试矩阵：幂等要怎么测才算测过

| 维度 | 取值 | 目的 |
| --- | --- | --- |
| 并发数 | 1 / 10 / 200 | 验证唯一约束与条件更新 |
| 键 | 同一个 / 不同 | 验证「同键只生效一次、不同键都生效」 |
| 时间间隔 | 0ms / 100ms / TTL 边界 | 验证窗口与 TTL |
| 失败注入 | 无 / DB 超时 / 唯一冲突 / 锁超时 | 验证异常路径 |
| 顺序 | 顺序 / 乱序 | 验证乱序不破坏结果 |

```go
// 关键断言只有三条
// ① 同键 N 次 → 副作用 1 次
// ② 不同键 → 副作用 N 次
// ③ TTL 过期后同键 → 副作用 2 次（这是可接受的，但要明确）
```

> 🩸 **第 ③ 条最容易被忽略**：TTL 过期后的重复是「设计允许」的，但你必须确认「最长重试窗口 < TTL」，否则就是漏洞（见第 5 章）。

## 1.12 一页速记

| 关键词 | 必须记住的结论 |
| --- | --- |
| 定义 | N 次执行 ≡ 1 次执行，且要求「结果/副作用/状态」三者都等价 |
| 假幂等 | 「先查一下」不是幂等；查询与写入之间的窗口就是事故入口 |
| 三概念 | 幂等 ≠ 去重 ≠ 恰好一次；恰好一次 = 不丢 + 幂等 |
| 边界 | 幂等只管「不重」，不管「不丢、不乱、不错、不越权」 |
| 成本 | 一次额外写 + 存储 + TTL + 复杂度；**先按副作用分级** |
| 分级 | 资金/资产 → 必须；消息通知 → 应该；日志/查询 → 不需要 |
| 双修 | 表结构与去重逻辑完全复用；**Agent 的幂等键必须含模型/提示词/工具版本** |
| 粒度 | 以「业务意图」（`run_id`）为幂等粒度，不以「模型调用」为粒度 |
| 验证 | 200 并发同参 + 幂等命中率指标 + 审计可证 |
| 一句话 | **幂等不是「防重复请求」，是「重复请求来临时，后果只发生一次」。** |

## 1.13 自检题

1. **为什么「下单前查一下有没有重复订单」不能算幂等？请说出两种会让它失效的场景。**
   > 要点：① 查询与写入之间存在时间窗口，并发下两个请求都查不到；② 唯一性依赖的字段（如「未支付订单」）会随状态变化，重试时条件已不成立；③ 多实例下查询走从库有延迟。正解：唯一约束 + 幂等表 + 状态机条件更新三件套。

2. **一个接口「返回了已存在」，但用户收到了两封邮件，它幂等吗？**
   > 要点：不幂等。结果等价（返回一致）但**副作用不等价**。需要把「发邮件」也纳入幂等范围（发件幂等键 + 去重窗口），或者把发件改为「由状态迁移事件驱动」，确保只触发一次。

3. **Agent 系统里，`request_id` 为什么常常不够用？**
   > 要点：一次 Run 内会有多次模型调用与工具调用，粒度不同；模型重试/工具重放需要更细的 `step_id`/`tool_call_id`；且同参不同果要求幂等键含模型与提示词版本，否则版本升级后键失效或误判。
