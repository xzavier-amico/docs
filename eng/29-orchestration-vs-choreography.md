## 29.1 事故现场：退款在三个服务之间跳了 47 分钟

2025 年 9 月，某电商平台的退款链路被拆成三个服务，采用「纯事件驱动」：

```
退款服务   收到退款申请 → 发 refund.requested
订单服务   订阅 refund.requested → 改订单状态 → 发 order.refunded
库存服务   订阅 order.refunded  → 回补库存   → 发 stock.restored
账务服务   订阅 order.refunded  → 记退款分录 → 发 ledger.recorded
通知服务   订阅 ledger.recorded → 发短信
```

看起来优雅：每个服务只关心自己的事件，加一个「优惠券回补」只要再订阅一次，不用改任何现有代码。

**问题出在那天下午的一批异常单。**

14:02，一笔 2,380 元的退款卡住了。客服后台显示「退款中」，用户打了三次电话。排查发现：

1. `order.refunded` 事件被**重复投递了 3 次**（Kafka 消费者 rebalance 导致位点回退）。
2. 库存服务幂等做得好，只回补了一次。
3. 账务服务没做幂等，**记了 3 笔退款分录**，多退 4,760 元。
4. 更糟的是：通知服务收到 3 条 `ledger.recorded`，给用户发了 3 条「退款到账」短信，但其中 2 条对应的钱根本不存在。

而**没有人知道这笔退款「现在走到哪一步了」**——因为流程不存在于任何地方，它是 5 个服务各自状态的一个「涌现结果」。运维要看进度，只能：

```bash
# 真实排查过程：在 5 个服务的日志里按 order_id 捞
grep "2380" refund-service.log | tail
grep "order_88213" order-service.log | tail
grep "order_88213" stock-service.log | tail
grep "order_88213" ledger-service.log | tail   # ← 这里才发现 3 条分录
```

**47 分钟后**才定位到根因，期间用户投诉 6 次，最终人工冲正 2 笔、补偿 200 元无门槛券。

复盘时的结论不是「不该用事件驱动」，而是：

> **我们把「流程的所有权」也一起拆散了，却没有人负责把它拼回来。**

这就是本章要解决的问题。

## 29.2 精确定义：编排 = 谁拥有「下一步」的决定权

### 一句话定义

> **编排（Orchestration）是一组「关于谁在什么时候做什么」的决策权分配。**
> 它不关心你用什么技术（状态机、BPMN、Temporal、还是 if-else），只关心一件事：**当 A 做完之后，是谁决定接下来做 B？**

按这个定义，只有三种形态：

| 形态 | 「下一步」由谁决定 | 典型实现 | 流程知识在哪 |
| --- | --- | --- | --- |
| **中心编排 Orchestration** | 一个**编排者**（ orchestrator / workflow engine / 状态机驱动器） | Temporal、Cadence、Argo、BPMN 引擎、自研状态机表 | **集中在一处**，可读、可画、可改 |
| **事件协同 Choreography** | **每个参与者自己**（订阅什么就做什么） | Kafka 事件、SNS/SQS、EventBridge | **分散在各服务**，是涌现的 |
| **无主广播（反模式）** | 没有人 | 到处 `publish` 但没人对终态负责 | **不存在**，出事只能靠 grep |

第三种最危险，因为它**长得和第二种一模一样**。区别只有一个判据：

> **能不能回答「这个流程现在到哪一步了、下一步该谁做、如果他不做谁来兜底」？**
> 能 → 是编排或合格的协同；不能 → 是无主广播。

### 三个反例：这些都不是「编排」

```text
反例 1：有流程图，但代码不按图跑
  → 那是「文档」，不是编排。图会腐烂，代码才是真相。

反例 2：有一张 status 字段，但没有驱动器
  → 那是「状态存储」，不是编排。谁把 status 从 A 推到 B？靠人点？靠定时任务扫？
     如果没有明确的推进者，卡单就是必然。

反例 3：每个服务都发事件，但没人订阅终态
  → 那是「日志广播」，不是协同。协同要求每个事件都有明确的责任消费者。
```

### 编排 vs 协同：不是「新旧」之争

很多团队把事件驱动当成「更高级」的架构，这是一个昂贵的误解。两者的真实差异是**决策权的集中度**，而集中度带来的是**可观测性与耦合度的交换**：

| 维度 | 中心编排 | 事件协同 |
| --- | --- | --- |
| **流程可见性** | 高：一个定义就是完整流程 | 低：流程是各服务订阅关系的并集 |
| **变更影响面** | 小：改编排者一处 | 大：改协议要动多个服务 |
| **参与者耦合** | 编排者知道所有参与者（强） | 参与者只知事件（弱） |
| **新增参与者** | 要改编排定义 | 只需订阅（但可能漏订阅） |
| **失败定位** | 看编排实例的历史 | 跨服务 grep |
| **长流程/长事务** | 天然适合（有持久化状态） | 需要额外的事件溯源与补偿 |
| **吞吐上限** | 受编排者吞吐限制 | 天然水平扩展 |
| **组织边界** | 适合**一个团队**拥有全流程 | 适合**跨团队/跨公司**的松耦合 |

> 💡 **一句话选型**：
> **「流程的终态由谁负责？」** 如果答案是「一个团队/一个系统」，用中心编排；如果答案是「多个组织各自负责自己的部分，靠契约衔接」，用事件协同。
> **最糟的是「终态没人负责」——那两种都不是，那是事故。**

## 29.3 结构图：两种范式的数据流

### 中心编排

```text
                    ┌──────────────────────────────┐
                    │  Orchestrator（唯一真相）      │
                    │  ┌────────────────────────┐  │
   请求 ──────────▶ │  │ Workflow Instance      │  │
                    │  │  state: REFUNDING      │  │
                    │  │  step:  3/5            │  │
                    │  │  history: [...]        │  │
                    │  └────────────────────────┘  │
                    └───┬────────┬────────┬────────┘
                        │命令     │命令     │命令
                        ▼        ▼        ▼
                    ┌──────┐ ┌──────┐ ┌──────┐
                    │订单  │ │库存  │ │账务  │
                    └──────┘ └──────┘ └──────┘
                        │        │        │
                        └────────┴────────┘
                         结果回传给编排者（不是事件广播）
```

**关键特征**：参与者**不知道流程**，只执行命令并返回结果。流程的「下一步」由编排者算出来。

### 事件协同

```text
   ┌──────┐  refund.requested   ┌──────┐  order.refunded   ┌──────┐
   │退款  │ ──────────────────▶ │订单  │ ────────────────▶ │库存  │
   └──────┘                     └──────┘                   └──────┘
                                   │
                                   │ order.refunded
                                   ▼
                                ┌──────┐  ledger.recorded  ┌──────┐
                                │账务  │ ────────────────▶ │通知  │
                                └──────┘                   └──────┘

   每个箭头 = 一次「我知道接下来该干什么」的局部决策
   没有任何一个节点持有完整流程
```

**关键特征**：每个参与者**知道自己的上游和下游**，但不知道全局。流程的正确性依赖「每个订阅者都记得订阅、都做了幂等、都不丢事件」。

### 混合方案（生产上最常见）

```text
   ┌─────────────────────────────────────────────┐
   │  编排者只负责「关键路径 + 终态」              │
   │  REFUNDING → LEDGER_DONE → NOTIFIED → CLOSED │
   └───────┬─────────────────────┬───────────────┘
           │ 命令                 │ 订阅（旁路）
           ▼                     ▼
      ┌─────────┐          ┌──────────────┐
      │ 账务     │          │ 通知/风控/报表 │
      │（强一致）│          │（最终一致旁路）│
      └─────────┘          └──────────────┘

   主链路有主，旁路事件化。
```

> ⚠️ **混合方案的红线**：**只能有一个「终态负责人」**。旁路订阅者可以失败、可以重放，但不能影响主流程的终态判定。否则你只是把无主广播包装得更复杂了。

## 29.4 六条选择判据（设计评审直接念）

| # | 判据 | 倾向中心编排 | 倾向事件协同 |
| --- | --- | --- | --- |
| 1 | **流程长度**（步数） | ≥ 4 步、有分支/循环 | ≤ 3 步、线性 |
| 2 | **参与者数量与归属** | 1~5 个，同一团队 | 多团队/跨公司，各自演进 |
| 3 | **终态责任** | 必须有人对「最终成功/失败」负责 | 各方只对自己的部分负责 |
| 4 | **可见性要求** | 业务要看进度、客服要查「到哪了」 | 内部管道，无人关心中间态 |
| 5 | **变更频率** | 流程经常变（促销规则、审批链） | 协议稳定，参与者常增删 |
| 6 | **失败处理** | 需要补偿、重试、人工介入、卡单巡检 | 失败可由上游重发或人工兜底 |

**再加两条工程判据（很多人忽略）**：

| # | 判据 | 说明 |
| --- | --- | --- |
| 7 | **单实例吞吐** | 中心编排的每次状态转移要落库，典型 1~5ms；10 万 QPS 的短流程会被编排者卡住 → 这种用协同或「批量编排」 |
| 8 | **团队的排障能力** | 事件协同的故障定位成本是编排的 3~10 倍（要跨服务 grep）。没有成熟 trace 体系的团队，别碰纯协同 |

### 一张决策表

```text
流程是否跨团队/跨公司？
├── 是 → 事件协同（契约优先），但必须指定「终态负责人」与「对账方」
└── 否 → 流程步数 ≥ 4 或有分支/补偿？
         ├── 是 → 中心编排（状态机/引擎）
         └── 否 → 同步调用 or 简单事件，别上引擎
```

## 29.5 如何确立一个架构编排：四步法

这是本章最该被复制到设计文档里的部分。**顺序不能换**——先选引擎的人，最后一定会把业务塞进引擎的模型里。

### 第一步：列「账本」——谁的状态需要被推进

不要先画流程图。先列出**所有会被这个流程改变的实体**，以及它们的**状态集合**：

| 实体 | 状态集合 | 终态 | 谁负责推进 |
| --- | --- | --- | --- |
| 退款单 | `INIT → AUDITING → REFUNDING → SUCCESS / FAILED` | SUCCESS/FAILED | 退款服务 |
| 订单 | `PAID → REFUNDING → REFUNDED` | REFUNDED | 订单服务 |
| 库存 | `DEDUCTED → RESTORED` | RESTORED | 库存服务 |
| 账务分录 | `PENDING → POSTED / REVERSED` | POSTED/REVERSED | 账务服务 |

> 🩸 **这一步的产出是「状态清单」，不是「流程图」。** 流程图是状态的投影；先有状态，图才有意义。跳过这一步直接画图，一定会画出「图上有、库里没有」的状态。

### 第二步：定「下一步」的所有权——每个转移只能有一个主人

给每个状态转移标注**决策者**：

| 转移 | 触发条件 | 决策者 | 执行者 |
| --- | --- | --- | --- |
| `INIT → AUDITING` | 用户提交 | 退款服务（同步校验） | 退款服务 |
| `AUDITING → REFUNDING` | 风控通过 | **编排者**（收到风控结果后） | 编排者 |
| `REFUNDING → SUCCESS` | 账务返回成功 | **编排者** | 编排者 |
| `PAID → REFUNDING` | 收到 `refund.approved` | 订单服务（自己） | 订单服务 |
| `DEDUCTED → RESTORED` | 收到 `order.refunded` | 库存服务（自己） | 库存服务 |

**规则**：
- 一个转移**只能有一个决策者**。两个服务都能改同一个状态 = 迟早互相覆盖。
- 「决策者」和「执行者」可以不同（编排者决策、参与者执行）。
- 如果某个转移找不到决策者 → 它就是**卡单的源头**，现在就要补上。

### 第三步：定边界与契约——命令 vs 事件

| 类型 | 语义 | 谁消费 | 失败怎么办 |
| --- | --- | --- | --- |
| **命令 Command** | 「请你做 X」（点对点，期望有结果） | 一个明确的执行者 | 编排者重试/补偿/告警 |
| **事件 Event** | 「我已经做了 X」（广播，不期望回复） | 零到多个订阅者 | 订阅者自己重试；不影响主流程 |

**最常见的错误**：把命令写成事件。

```text
❌ refund.requested 广播出去，等三个服务都处理完 → 谁来判断「都完成了」？没人。
✅ 编排者依次调用：reserveRefund → restoreStock → postLedger，每步有返回值。
   旁路再发 refund.completed 给通知/报表。
```

**契约必须写清的六件事**（少一件就会在联调时吵架）：

1. 消息的唯一键（`refund_id`）与幂等键
2. 时序要求（是否要求顺序、是否允许乱序）
3. 超时与重试语义（重试几次、退避策略、是否幂等）
4. 失败语义（失败后是回滚、补偿还是挂起等人）
5. schema 版本与兼容规则（只加字段不删不改类型）
6. 谁负责对账（见第 14 章）

### 第四步：选引擎——先问「要不要引擎」，再问「用哪个」

| 形态 | 适用 | 成本 | 典型实现 |
| --- | --- | --- | --- |
| **代码内编排**（无引擎） | 流程 ≤ 3 步、同步、失败可整体重试 | 最低 | 一个 `@Transactional` 方法 + 补偿代码 |
| **状态机表 + 驱动器** | 流程 4~10 步、需要卡单巡检、需要人工干预 | 中 | 自研：`state` + `WHERE status IN (...)` + 定时扫描 |
| **持久化执行引擎** | 长流程（分钟~天）、需要重放、需要定时器、需要版本化 | 高 | Temporal / Cadence |
| **可视化 BPMN** | 业务人员要改流程、审批类 | 高 | Flowable / Camunda / Activiti |
| **批处理 DAG** | 数据管道、离线任务 | 中 | Argo Workflows / Airflow |

> ⚠️ **不要用引擎解决「代码写得烂」**。引擎只解决三件事：**持久化状态、可靠重试、可视化**。如果你的流程只有 3 步且都在一个事务里，引入 Temporal 只会让你多一个要运维的集群（详见第 32 章的五维打分）。

### 四步法的产出物（可直接进设计文档）

```text
1. 实体状态清单（表）
2. 状态转移责任表（每个转移一个决策者）
3. 命令/事件契约清单（六要素）
4. 引擎选型结论 + 理由（含「为什么不用引擎」）
```

## 29.6 双修对照：传统业务 vs Agent 执行

| 维度 | 传统系统 | Agent 系统 | 相同 / 差异根因 |
| --- | --- | --- | --- |
| **编排对象** | 固定的服务调用序列 | **模型动态决定下一步**（工具选择、是否继续） | 差异根因：非确定性 |
| **「下一步」的决定权** | 编排者（代码写死） | 编排者定**边界**，模型定**路径**（受限自主） | 决策权部分让渡 |
| **流程可见性** | 状态机/流程图 | 需要额外记录「模型为什么选这一步」（推理轨迹） | Agent 多一层可解释性要求 |
| **失败语义** | 调用失败 → 重试/补偿 | 工具失败 → 模型可能自己换路；也可能死循环 | Agent 多「循环」这类失败 |
| **幂等粒度** | 请求/订单 | `run_id` + `step_id` + `tool_call_id` | 结构相同，粒度更细 |
| **长流程** | 分钟级已算长事务 | 一次 Run 可达小时级（等人审批、等外部回调） | 差异根因：长事务+随时中断 |
| **可视化** | 流程图即真相 | 图只能画「允许的路径」，实际路径要看 trace | Agent 的图是**约束**，不是**轨迹** |

**哪些部分完全相同**：

1. **状态机的落库套路**（当前状态 + 条件更新 + 版本号）——第 30 章，两侧一字不改。
2. **卡单巡检与重跑**——第 33 章，Agent 的「卡住的 Run」和「卡住的订单」是同一张巡检表。
3. **命令/事件契约六要素**——Agent 的工具契约就是命令契约，只是参数是 JSON Schema。
4. **「终态负责人」原则**——Agent 也必须有人对「这个 Run 最终算成功还是失败」负责，不能全靠模型说「我完成了」。

**Agent 特有的三条**：

| 特有 | 说明 | 对策 |
| --- | --- | --- |
| **路径爆炸** | 10 个工具、每步任选 → 组合数巨大，无法穷举测试 | 用「允许的状态机」约束：只允许特定状态下的特定工具集 |
| **模型自认为完成** | 模型说「已完成」但实际没调工具/调失败 | 终态必须由**代码校验**（检查产物/工具返回值），不信模型的话 |
| **循环** | A→B→A→B 无限调用 | 步数上限 + 重复调用检测 + 成本熔断（第 18 章） |

```go
// Agent 编排的骨架：编排者定边界，模型定路径，代码定终态
type RunState string

const (
    StatePlanning  RunState = "PLANNING"
    StateActing    RunState = "ACTING"
    StateWaiting   RunState = "WAITING_HUMAN" // 等人审批：长事务的典型中断点
    StateVerifying RunState = "VERIFYING"     // 代码校验，不信模型自述
    StateDone      RunState = "DONE"
    StateFailed    RunState = "FAILED"
)

func (r *Run) Step(ctx context.Context) (RunState, error) {
    switch r.State {
    case StatePlanning:
        plan, err := r.model.Plan(ctx, r.Goal, r.AllowedTools()) // 工具集由状态决定
        if err != nil { return StateFailed, err }
        r.Plan = plan
        return StateActing, nil

    case StateActing:
        if r.Steps >= r.MaxSteps { return StateFailed, ErrStepLimit } // 防循环
        if r.CostUSD >= r.Budget  { return StateFailed, ErrBudget  } // 成本熔断
        call := r.Plan.Next()
        if call.RequiresApproval() { return StateWaiting, nil }        // 中断点
        res, err := r.tools.Invoke(ctx, call)                          // 幂等：见第 2 章
        r.Record(call, res, err)
        return StateVerifying, nil

    case StateVerifying:
        if ok := r.verify(); !ok { return StatePlanning, nil }         // 失败回规划，但有上限
        return StateDone, nil
    }
    return r.State, nil
}
```

> 💡 **一句话**：**传统编排是「代码决定路径」，Agent 编排是「代码决定边界，模型决定路径，代码校验终态」。** 三者缺一，要么僵化，要么失控。

## 29.7 会在哪炸：失效模式清单

| # | 失效模式 | 现象 | 根因 | 怎么查 | 怎么修 | 怎么防复发 |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | **无主流程** | 出事后没人能说清「到哪一步」 | 纯广播、无终态负责人 | 问「谁负责这个流程的终态」，答不上来 | 指定编排者或终态负责人 | 设计评审强制填「终态负责人」 |
| 2 | **双主推进** | 状态被两个服务来回改，最终值随机 | 同一转移有两个决策者 | 查状态变更日志，看 actor 是否交替 | 收敛到一个决策者，另一个改为发命令 | 状态转移责任表 |
| 3 | **事件丢失导致永久卡住** | 订单停在 `REFUNDING` 三天 | 订阅者漏订阅/消费失败无重试 | 对账：应有终态的单据 vs 实际 | 补发事件 + 修消费者 | 卡单巡检（第 33 章）+ 对账（第 14 章） |
| 4 | **重复事件导致重复副作用** | 多退钱、多发短信 | 消费不幂等 | 按业务键 group by 看重复 | 幂等表 + 状态机前置校验 | 第 24 章 |
| 5 | **编排者成为单点** | 所有流程卡住，编排器 CPU 100% | 编排器同步调用所有参与者、无队列 | 看编排器 RT 与线程池 | 改为异步 + 队列 + 水平扩展 | 容量规划（第 22 章） |
| 6 | **版本升级导致旧实例无法重放** | 发布后历史工作流报错 | 工作流代码不兼容（Temporal 的确定性要求） | 看 history replay 报错 | 用版本化 API / patching | 工作流代码只做编排，业务逻辑放 activity |
| 7 | **流程图与代码不一致** | 图上 5 步，实际 7 步 | 图是手画的，没人维护 | 对比状态转移日志与图 | 从代码生成图 | 图由状态机定义生成 |
| 8 | **超时语义缺失** | 某步永远不返回，流程挂死 | 没有 per-step 超时 | 看最老实例的年龄 | 加超时 + 超时后的补偿 | 每个 activity 必填超时 |

> 🩸 **最贵的是第 1 和第 3 条**：前者让你在事故中浪费几十分钟定位，后者让钱静静地错下去。两者的解药都不是「换个更好的引擎」，而是**指定终态负责人 + 对账**。

## 29.8 怎么验证：编排不是画出来的，是跑出来的

| 验证项 | 方法 | 通过标准 |
| --- | --- | --- |
| **流程完整性** | 用状态转移表生成测试用例：每个状态 × 每个事件 | 无「未定义转移」；非法转移被拒绝 |
| **并发安全** | 同一单据 200 并发推进 | 只有 1 次成功，其余返回「状态已变更」 |
| **中断恢复** | 在每步之后 kill 进程 / 断网 | 重启后能从断点继续，不重复副作用 |
| **重复投递** | 同一事件投递 3 次 | 副作用只发生 1 次 |
| **超时与补偿** | 注入某步 30s 超时 | 触发补偿，终态为 FAILED 且可人工重试 |
| **卡单发现** | 人为把单据停在中间态 | 巡检在 SLA 内发现并告警 |
| **可视化一致性** | 对比编排定义与实际转移日志 | 实际路径 ⊆ 定义路径 |

给一个可直接跑的**状态机并发测试**（Go）：

```go
func TestConcurrentTransition(t *testing.T) {
    db := setupTestDB(t)
    orderID := createOrder(t, db, "PAID")

    var wg sync.WaitGroup
    var success int32
    for i := 0; i < 200; i++ {
        wg.Add(1)
        go func() {
            defer wg.Done()
            // 条件更新：只有当前状态是 PAID 才能推进
            res, err := db.Exec(`UPDATE orders SET status='REFUNDING', version=version+1
                                 WHERE id=? AND status='PAID' AND version=?`, orderID, 0)
            if err != nil { t.Error(err); return }
            if n, _ := res.RowsAffected(); n == 1 { atomic.AddInt32(&success, 1) }
        }()
    }
    wg.Wait()
    if success != 1 {
        t.Fatalf("expected exactly 1 success, got %d", success) // 这条断言就是幂等的证明
    }
}
```

**观测三件套**（编排必须有的指标）：

| 指标 | 含义 | 告警阈值（示例） |
| --- | --- | --- |
| `workflow_instances_in_flight` | 在途实例数 | 突增 3 倍 / 持续 1h 不降 |
| `workflow_step_duration_p99` | 单步耗时 | > 该步 SLO 的 2 倍 |
| `workflow_stuck_total` | 超过 SLA 未迁移的实例数 | > 0 即告警（按流程分级） |

## 29.9 用什么工具：一张表看完

| 需求 | 首选 | 备选 | 不要用 |
| --- | --- | --- | --- |
| 3 步以内、同步、可整体重试 | 代码 + 本地事务 | — | 任何引擎 |
| 4~10 步、要卡单巡检/人工干预 | 自研状态机表 | Temporal | BPMN（太重） |
| 分钟~天级、要定时器/重放/版本化 | **Temporal / Cadence** | 自研 + 队列 | 纯 MQ（无状态） |
| 业务人员要改流程、审批流 | Flowable / Camunda | 低代码平台 | 硬编码 |
| 离线数据管道/DAG | Argo Workflows / Airflow | DolphinScheduler | Temporal（不是它的场景） |
| Agent 多步执行 | 自研 Run 状态机 + Temporal（长任务） | LangGraph（原型） | 纯 prompt 里写流程 |

> 💡 **Temporal 的边界**（第 32 章细讲）：它保证**编排代码的持久化执行**，不保证你的 activity 幂等、不保证外部系统可补偿、不保证业务正确。**它只是把「状态机 + 重试 + 定时器」做成了基础设施。**

## 29.10 一页速记

| 关键词 | 必须记住的结论 |
| --- | --- |
| 定义 | 编排 = **谁拥有「下一步」的决定权**，不是「用了什么引擎」 |
| 三形态 | 中心编排（集中）/ 事件协同（分散）/ 无主广播（没人负责 = 事故） |
| 判据 | 流程终态由**一个团队**负责 → 编排；**多组织契约衔接** → 协同 |
| 反例 | 有图没代码、有状态没驱动器、有事件没终态负责人 —— 都不是编排 |
| 四步法 | 列状态账本 → 定转移所有权 → 定命令/事件契约 → 选引擎 |
| 铁律 | **一个转移只能有一个决策者；一个流程只能有一个终态负责人** |
| 命令 vs 事件 | 命令点对点、要结果；事件广播、不期待回复。**别把命令写成事件** |
| 引擎边界 | 引擎只解决持久化/重试/可视化，不解决业务幂等与正确性 |
| 双修 | 传统：代码定路径；Agent：**代码定边界、模型定路径、代码校验终态** |
| 验证 | 200 并发同单推进只有 1 次成功；中断可恢复；重复投递副作用只 1 次 |

## 29.11 自检题

1. **一个退款流程用 Kafka 事件串了 5 个服务，每个服务都做了幂等和重试。它算「编排」吗？**
   > 要点：算「事件协同」，不算「中心编排」。判断标准不是技术，而是**能否回答「现在到哪一步、下一步谁做、终态谁负责」**。如果没人能回答终态，那就是无主广播——即使每个服务都幂等，也会出现「某一步永远没人做」的卡单。

2. **为什么「一个转移只能有一个决策者」？两个服务都能改 `order.status` 会怎样？**
   > 要点：并发下会互相覆盖，最终状态取决于时序（lost update）；排障时无法确定是谁改的；补偿时不知道该找谁。解法：指定唯一决策者，另一方改为发命令；DB 层用 `WHERE status IN (...)` + 版本号兜底。

3. **Agent 系统里，为什么不能把「下一步做什么」完全交给模型？又为什么不能完全写死？**
   > 要点：完全交给模型 → 路径爆炸、循环、越权调用、成本失控、终态不可信；完全写死 → 失去 Agent 的价值（无法应对开放场景）。正解是**受限自主**：状态机约束「在什么状态下允许哪些工具」，模型在允许集内选路径，终态由代码校验（产物/返回值/断言），并设步数上限与成本熔断。
