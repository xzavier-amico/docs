## 52.1 引子：清单的价值不在「全」，在「每次都用」

1995 年，波音 299 型轰炸机试飞，试飞员因一个「太简单所以忘了」的操作（升降舵锁未解锁）坠机。此后波音制定了飞行检查清单——**不是因为飞行员不会飞，而是因为人在压力下会漏**。

上线评审同理。你不需要 300 项清单，你需要**30 项每次都被真正执行的**。

> 💡 **一条清单只有满足三个条件才有用**：① 每项都能用「是/否」回答；② 答「否」有明确的阻断或豁免流程；③ 有人对勾选负责。

## 52.2 上线前 30 项检查（Go / No-Go）

### A 组 · 正确性（1-10）

| # | 检查项 | 通过标准 | 阻断级别 |
| --- | --- | --- | --- |
| 1 | 所有写接口是否声明了幂等键？ | 幂等键字段 + 生成方 + TTL 都写明 | **P0 阻断** |
| 2 | 幂等键是否含可变字段？ | 无时间戳/随机数/会话 ID | **P0 阻断** |
| 3 | 是否有「先查后写」且无唯一约束兜底？ | 有唯一索引或条件更新 | **P0 阻断** |
| 4 | 支付/退款/扣库存是否有并发测试？ | 200 并发同参，仅 1 次生效 | **P0 阻断** |
| 5 | 事务边界内是否有外部调用（HTTP/MQ）？ | 无（移到事务外 + Outbox） | **P0 阻断** |
| 6 | 跨服务一致性是否有补偿/对账？ | 有补偿逻辑 + 对账任务 | P1 阻断 |
| 7 | 消息消费是否幂等？ | 去重表/状态机/唯一索引 | **P0 阻断** |
| 8 | 位点提交与业务提交顺序是否正确？ | 先处理后提交（或幂等兜底） | P1 阻断 |

| --- | --- | --- | --- |
| 21 | 四个黄金信号是否齐全？ | 延迟/流量/错误/饱和度 | P1 阻断 |

## 52.3 分主题清单（可单独打印）

### 幂等 10 条

```text
□ 1. 每个写接口都有幂等键，且写进了 API 文档
□ 2. 幂等键由客户端生成（或业务单号），可跨重试复用
□ 3. 幂等键不含时间戳/随机数/会话 ID
□ 4. 有唯一索引或条件更新兜底「先查后写」的窗口
□ 5. 唯一冲突返回成功（幂等语义），不是 500
□ 6. 幂等表与业务表同事务，或跨库时有 Outbox/对账
□ 7. TTL ≥ 最长重试窗口 × 2
□ 8. 重试不换 request_id；网关与服务只有一层重试
□ 9. 有幂等命中率指标与告警
□ 10. 有 200 并发同参的集成测试
```

### 事务 10 条

```text
□ 1. @Transactional 不在同类自调用/private 方法上
□ 2. 异常不被吞；受检异常显式 rollbackFor
□ 3. 事务内无 HTTP/MQ/文件 IO
□ 4. 传播行为显式声明（REQUIRED/REQUIRES_NEW 有理由）
□ 5. 大事务已拆分（批量 ≤ 500 行/批）
□ 6. 跨服务一致性有明确方案（Outbox/Saga/对账）
□ 7. 补偿操作可重复、可逆、可审计
□ 8. Saga 有空回滚/悬挂防护
□ 9. 有对账任务，且差异有处理流程
□ 10. 死锁有重试策略与监控
```

### 韧性 10 条

```text
□ 1. 限流保护的是「最贵且最先耗尽的资源」
□ 2. 限流器自身有降级开关
□ 3. 熔断有错误率与慢调用两类阈值
□ 4. 熔断半开探测有并发保护
□ 5. 降级有阶梯（缓存→简化→静态→明确失败）
□ 6. 降级不静默（有对外表达）
□ 7. 每个依赖都有超时
□ 8. 重试有退避、上限、抖动
□ 9. 压测覆盖 1.5 倍目标负载
□ 10. 容量有余量 ≥ 30%
```

### 存储 8 条

```text
□ 1. 选型先看访问模式，不先看产品
□ 2. 单表容量/索引大小有监控与拆分预案
□ 3. 分片键选择有热点分析
□ 4. 跨分片查询有方案（冗余表/ES/聚合层）
□ 5. 缓存与库的一致性等级写明
□ 6. 多存储双写有 Outbox/CDC/对账
□ 7. 备份恢复演练过（记录 RTO/RPO）
□ 8. 冷热分层与保留期合规
```

### 运维运营 8 条

```text
□ 1. 故障分级 P0-P3 有判定标准
□ 2. 运维/运营转派规则明确
□ 3. 每个核心服务有 Runbook
□ 4. 复盘改进项有 owner 与截止日期
□ 5. 工单有分类/SLA/升级
□ 6. 自助诊断覆盖 Top 5 问题
□ 7. 对外状态页可用
□ 8. 一次故障两份报告（内部/客户）
```

## 52.4 30 个反模式速查

| # | 反模式 | 一句话后果 | 正解 |
| --- | --- | --- | --- |
| 1 | 「先查一下」当幂等 | 并发窗口导致重复 | 唯一索引 + 条件更新 |
| 2 | 幂等键带时间戳 | 每次重试都是新请求 | 键只含业务标识 |
| 3 | 唯一冲突 catch 后返回 500 | 调用方重试，雪崩 | 返回成功/已处理 |
| 4 | 幂等表与业务表不同事务 | 一边成功一边失败 | 同库同事务 / Outbox |

| 7 | 空 catch | 错误静默 | 至少记日志 + 上报 |

| 9 | Saga 无补偿上限 | 无限重试打爆下游 | 上限 + 人工队列 |
| 10 | 无对账 | 静默错误永远发现不了 | 日终对账 |
| 11 | 限流只做在网关 | 内网调用绕过 | 多层限流 |
| 12 | 限流每请求查 Redis | 限流器打满 CPU | 本地令牌桶 + 异步续期 |
| 13 | 限流阈值拍脑袋 | 要么误伤要么没保护 | 容量模型反推 |
| 14 | 熔断阈值只看错误率 | 慢调用拖死系统 | 加慢调用熔断 |
| 15 | 降级悄悄发生 | 用户以为功能正常 | 对外表达 + 指标 |
| 16 | 重试无退避 | 重试风暴 | 指数退避 + 抖动 |
| 17 | 超时层层放大 | 线程池耗尽 | 超时预算递减 |
| 18 | 无限流 | 一个租户拖垮全部 | 多租户配额 |
| 19 | 无消息幂等 | 重复消费脏数据 | 去重表 |
| 20 | 先提交位点再处理 | 丢消息 | 先处理后提交 |
| 21 | 无 DLQ | 毒消息卡死消费 | DLQ + 重试队列 |

| 25 | 状态与标志位混用 | 状态爆炸 | 单一状态机 |
| 26 | 缓存与库双写无策略 | 脏数据 | 先库后删缓存 / CDC |
| 27 | Redis 当唯一存储 | 丢数据 | 只做缓存，落库 |
| 28 | 分库分表过早 | 运维成本 > 收益 | 先优化索引/归档 |
| 29 | 运维运营混做 | 两边都做不好 | 分工 + 转派规则 |

## 52.6 检查单怎么才不变成形式：证据与豁免

**清单最常见的死法**：上线前 10 分钟，开发把 30 项全部勾「是」，没人看证据。三个月后所有人都知道这是走形式。

解法是给每一项挂**证据**与**豁免**两件东西。

### 每一项都必须能指向一个「证据」

| 检查项 | 可接受的证据 | 不可接受的「证据」 |
| --- | --- | --- |
| 幂等键已声明 | API 文档链接 + 代码位置（`file:line`） | 「做了」 |
| 200 并发测试通过 | CI 报告链接（含时间戳） | 「测过了」 |
| 事务内无外部调用 | 静态扫描报告（`rg` 输出） | 「我记得没有」 |
| 回滚演练过 | 演练记录（含耗时） | 「能回滚」 |
| 敏感数据脱敏 | 抽样 10 条的截图/日志 | 「都脱敏了」 |

```text
评审时的标准问法只有一句：
「这一项的证据在哪？给我链接或命令输出。」
拿不出来 = 未通过 = 不许上线（P0）或必须走豁免（P1）。
```

### 豁免机制（否则清单会被绕过）

```sql
CREATE TABLE launch_waiver (
    id           BIGINT AUTO_INCREMENT PRIMARY KEY,
    release_id   VARCHAR(64) NOT NULL,
    item_no      INT NOT NULL,                 -- 对应 30 项编号
    reason       TEXT NOT NULL,                -- 为什么这次可以不做
    risk         TEXT NOT NULL,                -- 不做的最坏后果
    mitigation   TEXT NOT NULL,                -- 临时兜底措施
    approver     VARCHAR(64) NOT NULL,         -- 必须是 P1 项的 owner 或更高
    expires_at   DATETIME NOT NULL,            -- ★ 豁免必须过期
    created_at   DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    UNIQUE KEY uk_release_item (release_id, item_no)
);
```

**三条规则**：

1. **P0 项不可豁免**（资金/安全/回滚类）。
2. **豁免必须有到期时间**，到期未修复自动升级为 P1 事故风险，进周会。
3. **同一项连续 3 次豁免** ⇒ 强制排期修复，否则等于「永久豁免」。

```sql
-- 每周检查：哪些豁免快到期/已过期
SELECT w.item_no, w.release_id, w.approver, w.expires_at,
       DATEDIFF(w.expires_at, NOW()) AS days_left
FROM launch_waiver w
WHERE w.expires_at < NOW() + INTERVAL 7 DAY
ORDER BY w.expires_at;
```

## 52.7 三个真实的 Go / No-Go 现场

清单的价值在「敢说不」。三个真实决策（已脱敏）：

### 现场一：拒绝上线（P0 项缺失）

```text
背景：大促前 3 天，新促销引擎要上线。
检查结果：第 4 项「支付回调并发测试」未做（开发说「逻辑很简单」）。
决策：No-Go。
理由：促销期支付回调量是平日 8 倍，回调重复是历史高发事故（去年因此赔 23 万）。
后续：延期 2 天补测试，发现一个真实的重复回调 bug（同一 requestID 两次回调会重复发券）。
结果：如期上线，大促零事故。
```

### 现场二：带条件上线（P1 项豁免）

```text
背景：一个内部报表功能，要求当天上线给管理层看。
检查结果：第 15 项「降级是否悄悄发生」未做（无对外表达）。
决策：Go，但带 3 个条件：
  ① 仅对内部账号开放（白名单），不对客户开放；
  ② 加开关，异常时一键关闭；
  ③ 豁免 7 天到期，到期前补对外提示。
结果：上线当天确实降级过一次（数据源超时），因白名单 + 开关，无外部影响。
```

### 现场三：强行上线，两周后回滚

```text
背景：某团队认为「清单太重」，绕过评审直接上线了新的同步链路。
结果：第 6 项「跨服务一致性补偿」缺失 →
     上线第 9 天出现「库存扣了订单没建」，差异 1,100 单，人工修 3 天。
复盘结论：这 30 项里，被绕过的恰好是最贵的那一项。
后续：把「清单通过」做成发布流水线的硬门禁（不通过无法点发布）。
```

> 💡 **三个现场的共同点**：**清单从来不是「限制速度」，而是「把事故成本提前定价」。** 现场一的 2 天延期换来零事故；现场三的「省 1 天」换来 3 天修数据 + 客户信任损失。

## 52.8 把 30 个反模式变成可执行的检查

反模式写在纸上没用，要能被 grep/CI 抓到。下面是可直接落地的检查片段（Go/Java 混合项目）。

```bash
#!/usr/bin/env bash
# scripts/antipattern-check.sh —— 把 30 条反模式里可自动化的部分做成门禁
set -uo pipefail
fail=0
hit() { echo "❌ $1"; shift; "$@" || true; fail=1; }

# 1.「先查后写」且无唯一约束的迹象：count/select 后紧跟 insert（启发式）
if rg -n -U 'countBy\w+\([^)]*\)\s*(==|>)\s*0[\s\S]{0,200}?insert' --type java . ; then
  hit "疑似『先查后写』：请确认有唯一索引兜底（反模式 1）" true
fi

# 2. 空 catch（反模式 7）
if rg -n -U 'catch\s*\([^)]*\)\s*\{\s*\}' --type java . ; then
  hit "空的 catch 会吞错（反模式 7）" true
fi

# 3. @Transactional 方法内出现 HTTP/MQ 调用（反模式 5）
if rg -n -U '@Transactional[\s\S]{0,600}?(RestTemplate|WebClient|feign|kafkaTemplate\.send)' --type java . ; then
  hit "事务内出现外部调用（反模式 5）" true
fi

# 4. 无限重试 / 无退避（反模式 16）
if rg -n 'while\s*\(\s*true\s*\)[\s\S]{0,300}?(retry|Retry)' --type go . ; then
  hit "疑似无上限重试（反模式 16）" true
fi

# 5. 无超时的 HTTP 客户端（反模式 17）
if rg -n '&http\.Client\{\s*\}' --type go . ; then
  hit "http.Client 未设 Timeout（反模式 17）" true
fi

# 6. context.Background() 出现在请求链路深处（反模式 17 变体）
if rg -n 'context\.Background\(\)' --type go internal/ | rg -v '_test.go' ; then
  echo "⚠️ 检查这些 context.Background() 是否丢了超时/取消（建议从入口传入）"
fi

# 7. 裸 Amount 字段（反模式：金额单位不统一）
if rg -n '\bAmount\s+(int64|float64|BigDecimal)' --type go --type java . ; then
  hit "金额字段必须带单位（反模式：单位不统一）" true
fi

# 8. 消息消费未声明幂等（启发式：消费者函数里没有去重表/状态判断）
if rg -n 'func .*Handle.*Event' --type go internal/ | rg -v 'idempot|dedup|exists|status' ; then
  echo "⚠️ 确认这些事件处理器有幂等落点（反模式 19）"
fi

exit $fail
```

**能被自动化的反模式只有 8~10 条**，其余（如「无终态负责人」「复盘无闭环」）属于流程，要靠评审与数据度量。承认这一点，比假装「全都自动化了」更专业。

| 反模式类型 | 检查方式 | 覆盖率 |
| --- | --- | --- |
| 代码模式 | 静态扫描（上例） | ~10 条 |
| 配置缺失 | 检查配置文件/环境变量 | ~5 条 |
| 数据状态 | 定期 SQL 巡检（卡单/账不平） | ~5 条 |
| 流程缺失 | 评审表 + 度量（闭环率/告警可执行率） | ~10 条 |

## 52.9 防止清单形式化：三条机制

```text
① 抽查：每季度随机抽 5 次上线，核对勾选与证据是否一致。
       不一致 → 全团队通报 + 当次发布负责人复盘。
② 反向激励：漏检导致 P1 的，复盘时必须回答「30 项里哪一项没做/做假了」。
③ 清单瘦身：每半年删掉「从未拦下过问题」的项，保留真正有效的。
       （30 项不是圣旨；如果某项 2 年没拦下任何问题，它可能只是安慰剂）
```

> 🩸 **清单最大的敌人不是「不写」，而是「写了但没人信」**。一旦团队形成「反正都会勾是」的共识，这张纸就变成了事故后的证据，而不是事故前的防线。

## 52.10 回到三条定律（全书的收口）

```text
定律一 · 状态机定律
任何「多步 + 可能失败 + 需要恢复 + 需要补偿」的流程，最终都是三件套：
    状态机（谁是真相） + 幂等（重放安全） + 补偿（不可回滚时的退路）
没有第四种解法。框架只是把这三件事做成了基础设施。

定律二 · 稀缺资源定律
限流熔断保护的永远是「最贵且最先耗尽」的那个资源：
    传统：线程 → 连接池 → DB 连接 → 下游 QPS
    Agent：token 速率 → 模型并发 → 单 Run 预算 → 供应商配额
算法可复用，「限什么、限多少」必须重算。

定律三 · 不可回滚定律
凡是外部副作用（扣款/发信/下单/删文件/调三方）都不可回滚，只能补偿。
Agent 把它放大了一万倍：每次工具调用都是副作用，
而且「要不要调用」还是模型自己决定的。
```

**如果你只记住一句话**：

> **分布式系统的正确性，不来自「不出错」，而来自「出错后能被发现、被纠正、且不会被重复放大」。**
> 幂等防放大，对账发现错，补偿纠正错，状态机让这一切有据可查。

## 52.12 上线评审会的 30 分钟开法

清单如果只是「自己勾」，一定会走形式。**用 30 分钟的会把它变成集体决策**。

```text
00:00~02:00  发布负责人介绍：改了什么、影响哪些服务、回滚方式
02:00~15:00  逐项过 30 项（只看 P0 + 本次变更相关的 P1）
             - 每项问一句：「证据在哪？」
             - 没有证据 = 未通过
15:00~22:00  过豁免项（每项必须有 reason/risk/mitigation/approver/expires）
22:00~26:00  过监控与预案：
             - 这次发布新增了哪些指标？告警阈值对吗？
             - 出问题第一个看哪个看板？Runbook 在哪？
26:00~29:00  表决：Go / 带条件 Go / No-Go（记录反对意见）
29:00~30:00  明确：谁发、几点发、谁盯、出问题谁决策（IC）
```

**三个关键角色（必须到场）**：

| 角色 | 职责 | 缺席后果 |
| --- | --- | --- |
| 发布负责人（研发） | 讲清变更与回滚 | 没人能回答「改了什么」 |
| SRE/运维 | 确认监控与容量 | 出问题没有看板与预案 |
| 业务/运营 | 确认影响面与对外话术 | 客户先知道，你后知道 |

**评审会的三条纪律**：

1. **不许「会后补证据」**：P0 项当场拿不出，就是 No-Go。
2. **不许「这次特殊」**：连续三次「特殊」，说明清单该改，而不是该破例。
3. **记录反对意见**：如果事后出事，反对意见是最有价值的复盘材料；如果没事，它是下次判断的依据。

```markdown
# 发布评审记录（模板）
- 发布：order-api v2.14.0    时间：2026-09-20 14:00
- 变更：新增优惠券核销；连接池 50→100
- 结论：**带条件 Go**
- 条件：① 先灰度 10% 观察 30 分钟；② 若 P99 > 500ms 自动回滚；③ 运营准备话术
- 反对意见：A 认为连接池调整应独立发布（记录在案）
- 盯盘：B（14:00~15:00）；IC：C
```

## 52.13 双修对照：清单在两类系统上的差异

| 维度 | 传统系统 | Agent 系统 | 相同 / 差异根因 |
| --- | --- | --- | --- |
| **幂等** | `request_id` + 唯一索引 | `run_id/step_id/tool_call_id` + **模型结果缓存** | 结构相同，粒度更细 |
| **事务** | 本地事务/Outbox | 以上 + **工具副作用必须补偿** | Agent 多「不可回滚」 |
| **限流** | QPS/连接数 | **TPM/并发 Run/单 Run 预算** | 度量单位不同 |
| **监控** | 四黄金信号 | 以上 + **token/成本/TTFT/工具成功率** | 指标扩展 |
| **回滚** | 代码/配置回滚 | 以上 + **prompt 版本回滚、模型切换、知识库回退** | 多三个开关 |
| **上线门禁** | 编译/测试/压测 | 以上 + **评测集门禁（质量不降）** | 新增一类门禁 |
| **数据安全** | 权限/脱敏 | 以上 + **跨租户记忆隔离、输出审计** | 更敏感 |
| **事故定义** | 不可用 | 以上 + **答错/越权** | 质量即事故 |
| **完全相同的部分** | — | — | §52.2 的 30 项里，**约 22 项一字不改**；P0 判据、评审会、豁免机制全部复用 |

**Agent 多出的 8 项检查**（建议加到你们的 30 项里）：

```text
□ 31. 每个 Run 有唯一 run_id，且可反查到 trace
□ 32. 工具调用幂等键含 run_id + step_id + 工具版本
□ 33. 单 Run 有步数上限与成本预算（防循环与烧钱）
□ 34. 上下文超限时有裁剪策略（不静默截断）
□ 35. 输出有审计与撤回预案（说错话怎么收回）
□ 36. prompt/模型/知识库 都有版本号与回滚开关
□ 37. 发布前跑评测集，质量指标不下降（门禁）
□ 38. 跨租户数据隔离验证（记忆/检索/日志都不串）
```

> 💡 **不是把清单变长，而是把「Agent 特有的风险」补上**。传统那 30 项仍然有效——它们检查的是「系统是否可靠」，而新增的 8 项检查「智能是否可靠」。

## 52.14 一页速记

| 关键词 | 必须记住的结论 |
| --- | --- |
| 清单 | 30 项，P0 不通过不许上线；每项「是/否」+ 负责人 |
| P0 十项 | 幂等键/无唯一兜底/并发测试/事务内外部调用/消息幂等/金额单位/超时/重试放大/回滚演练/敏感数据 |
| 分主题 | 幂等 10、事务 10、韧性 10、存储 8、运维运营 8 |
| 反模式 | 30 条，每条「后果 + 正解」，可直接做 review  checklist |
| 三个月 | 止血 → 一致性与韧性 → 运营与效能 |
| 验收 | 看「事故数/发现时长/闭环率/自助率」，不看「做了没有」 |
| 三定律 | 状态机 / 稀缺资源 / 不可回滚 |
| 收口 | 正确性 = 幂等（防放大）+ 对账（发现）+ 补偿（纠正）+ 状态机（可查） |

## 52.15 自检题

1. **上线评审时，开发说「这个接口不需要幂等，因为前端按钮已经置灰了」。你怎么回应？**
   > 要点：前端置灰只能防「用户重复点击」，防不了网关重试、服务重试、MQ 重投、超时重发、脚本刷接口。判据是「这个接口有没有资金/资产/权益副作用」，有就必须幂等。且置灰本身不可靠（多标签页、断网重试、直接调 API）。

2. **为什么「改进项闭环率」比「复盘报告质量」更能说明团队水平？**
   > 要点：报告写得好只说明表达能力强；闭环率说明「是否真的改变了系统」。同样故障反复发生，通常不是「没分析出来」，而是「改进项没人做」。度量闭环率会把责任落到 owner 与截止日期上。

3. **用三定律分析「Agent 调用工具下单」这个场景，各出一条设计约束。**
   > 要点：① 状态机定律 → Run 必须有状态机（含 `WAITING_EXTERNAL`），下单结果要落库，不能只存在对话历史里；② 稀缺资源定律 → 限流要限「模型并发 + 工具调用 QPS + 单 Run 预算」，不是只限 HTTP QPS；③ 不可回滚定律 → 下单是外部副作用，失败只能补偿（取消订单/退款），所以必须幂等（`run_id`+`step_id`）且有补偿预案。
