## 52.1 引子：清单的价值不在「全」，在「每次都用」

1995 年，波音 299 型轰炸机试飞，试飞员因一个「太简单所以忘了」的操作（升降舵锁未解锁）坠机。此后波音制定了飞行检查清单——**不是因为飞行员不会飞，而是因为人在压力下会漏**。

上线评审同理。你不需要 300 项清单，你需要**30 项每次都被真正执行的**。

> 💡 **一条清单只有满足三个条件才有用**：① 每项都能用「是/否」回答；② 答「否」有明确的阻断或豁免流程；③ 有人对勾选负责。

## 52.2 上线前 30 项检查（Go / No-Go）

### A 组 · 正确性（1-10）

| # | 检查项 | 通过标准 | 阻断级别 |
| --- | --- | --- | --- |
| 1 | 所有写接口是否声明了幂等键？ | 幂等键字段 + 生成方 + TTL 都写明 | **P0 阻断** |
| 2 | 幂等键是否含可变字段？ | 无时间戳/随机数/会话 ID | **P0 阻断** |
| 3 | 是否有「先查后写」且无唯一约束兜底？ | 有唯一索引或条件更新 | **P0 阻断** |
| 4 | 支付/退款/扣库存是否有并发测试？ | 200 并发同参，仅 1 次生效 | **P0 阻断** |
| 5 | 事务边界内是否有外部调用（HTTP/MQ）？ | 无（移到事务外 + Outbox） | **P0 阻断** |
| 6 | 跨服务一致性是否有补偿/对账？ | 有补偿逻辑 + 对账任务 | P1 阻断 |
| 7 | 消息消费是否幂等？ | 去重表/状态机/唯一索引 | **P0 阻断** |
| 8 | 位点提交与业务提交顺序是否正确？ | 先处理后提交（或幂等兜底） | P1 阻断 |
| 9 | 是否有对账任务覆盖新链路？ | 差异表 + 日终对账 | P1 阻断 |
| 10 | 金额单位是否统一为「分」？ | 字段名带 `Cents`，无浮点 | **P0 阻断** |

### B 组 · 韧性（11-20）

| # | 检查项 | 通过标准 | 阻断级别 |
| --- | --- | --- | --- |
| 11 | 是否有限流？限的是哪个资源？ | 明确「保护下游/DB/模型配额」 | P1 阻断 |
| 12 | 限流器自身故障时会怎样？ | 有降级开关（放行/固定阈值）+ 告警 | P1 阻断 |
| 13 | 是否有关键依赖的熔断？ | 错误率/慢调用两类阈值 | P1 阻断 |
| 14 | 熔断/降级是否有兜底返回？ | 缓存/默认值/明确失败 | P1 阻断 |
| 15 | 降级是否会「悄悄发生」？ | 有对外表达 + 指标 | P2 |
| 16 | 是否压测过目标负载的 1.5 倍？ | P99 达标、错误率 < 0.1% | P1 阻断 |
| 17 | 容量是否按「目标 QPS + P99」算过？ | 有算式与余量（≥ 30%） | P1 阻断 |
| 18 | 是否有超时？每层都设了吗？ | 连接/读/写/整体 都有 | **P0 阻断** |
| 19 | 重试是否会导致放大？ | 有退避 + 上限 + 只一层重试 | **P0 阻断** |
| 20 | 单实例故障是否影响全局？ | 多副本 + 健康检查 + 摘流 | P1 阻断 |

### C 组 · 可观测与运维（21-30）

| # | 检查项 | 通过标准 | 阻断级别 |
| --- | --- | --- | --- |
| 21 | 四个黄金信号是否齐全？ | 延迟/流量/错误/饱和度 | P1 阻断 |
| 22 | 是否能区分「自身慢」与「依赖慢」？ | 分段计时/依赖 span | P1 阻断 |
| 23 | 是否有业务指标（不只是系统指标）？ | 订单量/成功率/差异数 | P1 阻断 |
| 24 | 告警是否可执行？ | 每条告警有「怎么做」 | P2 |
| 25 | 是否有 Runbook？ | 现象/判定/止血/升级 | P1 阻断 |
| 26 | 回滚是否演练过？ | 5 分钟内可回滚 | **P0 阻断** |
| 27 | 是否有降级/限流开关，且验证过？ | 开关可热生效 | P1 阻断 |
| 28 | 日志是否含 trace_id + 业务键？ | 可按单号串起来 | P1 阻断 |
| 29 | 敏感数据是否脱敏？ | 手机/身份证/卡号 | **P0 阻断** |

## 52.3 分主题清单（可单独打印）

### 幂等 10 条

```text
□ 1. 每个写接口都有幂等键，且写进了 API 文档
□ 2. 幂等键由客户端生成（或业务单号），可跨重试复用
□ 3. 幂等键不含时间戳/随机数/会话 ID
□ 4. 有唯一索引或条件更新兜底「先查后写」的窗口
□ 5. 唯一冲突返回成功（幂等语义），不是 500
□ 6. 幂等表与业务表同事务，或跨库时有 Outbox/对账
□ 7. TTL ≥ 最长重试窗口 × 2
□ 8. 重试不换 request_id；网关与服务只有一层重试
□ 9. 有幂等命中率指标与告警
□ 10. 有 200 并发同参的集成测试
```

### 事务 10 条

```text
□ 1. @Transactional 不在同类自调用/private 方法上
□ 2. 异常不被吞；受检异常显式 rollbackFor
□ 3. 事务内无 HTTP/MQ/文件 IO
□ 4. 传播行为显式声明（REQUIRED/REQUIRES_NEW 有理由）
□ 5. 大事务已拆分（批量 ≤ 500 行/批）
□ 6. 跨服务一致性有明确方案（Outbox/Saga/对账）
□ 7. 补偿操作可重复、可逆、可审计
□ 8. Saga 有空回滚/悬挂防护
□ 9. 有对账任务，且差异有处理流程
□ 10. 死锁有重试策略与监控
```

### 韧性 10 条

```text
□ 1. 限流保护的是「最贵且最先耗尽的资源」
□ 2. 限流器自身有降级开关
□ 3. 熔断有错误率与慢调用两类阈值
□ 4. 熔断半开探测有并发保护
□ 5. 降级有阶梯（缓存→简化→静态→明确失败）
□ 6. 降级不静默（有对外表达）
□ 7. 每个依赖都有超时
□ 8. 重试有退避、上限、抖动
□ 9. 压测覆盖 1.5 倍目标负载
□ 10. 容量有余量 ≥ 30%
```

### 存储 8 条

```text
□ 1. 选型先看访问模式，不先看产品
□ 2. 单表容量/索引大小有监控与拆分预案
□ 3. 分片键选择有热点分析
□ 4. 跨分片查询有方案（冗余表/ES/聚合层）
□ 5. 缓存与库的一致性等级写明
□ 6. 多存储双写有 Outbox/CDC/对账
□ 7. 备份恢复演练过（记录 RTO/RPO）
□ 8. 冷热分层与保留期合规
```

### 运维运营 8 条

```text
□ 1. 故障分级 P0-P3 有判定标准
□ 2. 运维/运营转派规则明确
□ 3. 每个核心服务有 Runbook
□ 4. 复盘改进项有 owner 与截止日期
□ 5. 工单有分类/SLA/升级
□ 6. 自助诊断覆盖 Top 5 问题
□ 7. 对外状态页可用
□ 8. 一次故障两份报告（内部/客户）
```

## 52.4 30 个反模式速查

| # | 反模式 | 一句话后果 | 正解 |
| --- | --- | --- | --- |
| 1 | 「先查一下」当幂等 | 并发窗口导致重复 | 唯一索引 + 条件更新 |
| 2 | 幂等键带时间戳 | 每次重试都是新请求 | 键只含业务标识 |
| 3 | 唯一冲突 catch 后返回 500 | 调用方重试，雪崩 | 返回成功/已处理 |
| 4 | 幂等表与业务表不同事务 | 一边成功一边失败 | 同库同事务 / Outbox |
| 5 | 事务里调 HTTP | 长事务 + 连接占用 | 移到事务外 |
| 6 | `@Transactional` 自调用 | 事务不生效 | 拆类 / AopContext |
| 7 | 空 catch | 错误静默 | 至少记日志 + 上报 |
| 8 | 分布式事务包一切 | 性能崩塌 | 最终一致 + 对账 |
| 9 | Saga 无补偿上限 | 无限重试打爆下游 | 上限 + 人工队列 |
| 10 | 无对账 | 静默错误永远发现不了 | 日终对账 |
| 11 | 限流只做在网关 | 内网调用绕过 | 多层限流 |
| 12 | 限流每请求查 Redis | 限流器打满 CPU | 本地令牌桶 + 异步续期 |
| 13 | 限流阈值拍脑袋 | 要么误伤要么没保护 | 容量模型反推 |
| 14 | 熔断阈值只看错误率 | 慢调用拖死系统 | 加慢调用熔断 |
| 15 | 降级悄悄发生 | 用户以为功能正常 | 对外表达 + 指标 |
| 16 | 重试无退避 | 重试风暴 | 指数退避 + 抖动 |
| 17 | 超时层层放大 | 线程池耗尽 | 超时预算递减 |
| 18 | 无限流 | 一个租户拖垮全部 | 多租户配额 |
| 19 | 无消息幂等 | 重复消费脏数据 | 去重表 |
| 20 | 先提交位点再处理 | 丢消息 | 先处理后提交 |
| 21 | 无 DLQ | 毒消息卡死消费 | DLQ + 重试队列 |
| 22 | 消息体过大 | 被 broker 拒绝 | 存对象存储 + 传引用 |
| 23 | 序列化不兼容 | 升级后消费失败 | 只加字段 + 版本号 |
| 24 | 无终态负责人 | 卡单没人管 | 指定 owner + 巡检 |
| 25 | 状态与标志位混用 | 状态爆炸 | 单一状态机 |
| 26 | 缓存与库双写无策略 | 脏数据 | 先库后删缓存 / CDC |
| 27 | Redis 当唯一存储 | 丢数据 | 只做缓存，落库 |
| 28 | 分库分表过早 | 运维成本 > 收益 | 先优化索引/归档 |
| 29 | 运维运营混做 | 两边都做不好 | 分工 + 转派规则 |
| 30 | 复盘无闭环 | 同样故障反复发生 | 改进项 owner + 度量 |

## 52.5 团队落地：三个月路线

```text
第 1 月 · 止血与基线
  ├─ 上线 30 项检查（§52.2）跑一遍，P0 项清零
  ├─ 核心链路补：幂等 + 超时 + 回滚演练

  ├─ 跨服务链路补 Outbox/对账

  ├─ 工单系统 + 客户健康分 + 自助诊断 Top5
```

## 52.6 回到三条定律（全书的收口）

```text
定律一 · 状态机定律
任何「多步 + 可能失败 + 需要恢复 + 需要补偿」的流程，最终都是三件套：
    状态机（谁是真相） + 幂等（重放安全） + 补偿（不可回滚时的退路）
没有第四种解法。框架只是把这三件事做成了基础设施。

定律二 · 稀缺资源定律
限流熔断保护的永远是「最贵且最先耗尽」的那个资源：
    传统：线程 → 连接池 → DB 连接 → 下游 QPS
    Agent：token 速率 → 模型并发 → 单 Run 预算 → 供应商配额
算法可复用，「限什么、限多少」必须重算。

定律三 · 不可回滚定律
凡是外部副作用（扣款/发信/下单/删文件/调三方）都不可回滚，只能补偿。
Agent 把它放大了一万倍：每次工具调用都是副作用，
而且「要不要调用」还是模型自己决定的。
```

**如果你只记住一句话**：

> **分布式系统的正确性，不来自「不出错」，而来自「出错后能被发现、被纠正、且不会被重复放大」。**
> 幂等防放大，对账发现错，补偿纠正错，状态机让这一切有据可查。

## 52.7 一页速记

| 关键词 | 必须记住的结论 |

| P0 十项 | 幂等键/无唯一兜底/并发测试/事务内外部调用/消息幂等/金额单位/超时/重试放大/回滚演练/敏感数据 |
| 分主题 | 幂等 10、事务 10、韧性 10、存储 8、运维运营 8 |

| 三个月 | 止血 → 一致性与韧性 → 运营与效能 |
| 验收 | 看「事故数/发现时长/闭环率/自助率」，不看「做了没有」 |
| 三定律 | 状态机 / 稀缺资源 / 不可回滚 |
| 收口 | 正确性 = 幂等（防放大）+ 对账（发现）+ 补偿（纠正）+ 状态机（可查） |

## 52.8 自检题

1. **上线评审时，开发说「这个接口不需要幂等，因为前端按钮已经置灰了」。你怎么回应？**
   > 要点：前端置灰只能防「用户重复点击」，防不了网关重试、服务重试、MQ 重投、超时重发、脚本刷接口。判据是「这个接口有没有资金/资产/权益副作用」，有就必须幂等。且置灰本身不可靠（多标签页、断网重试、直接调 API）。

2. **为什么「改进项闭环率」比「复盘报告质量」更能说明团队水平？**
   > 要点：报告写得好只说明表达能力强；闭环率说明「是否真的改变了系统」。同样故障反复发生，通常不是「没分析出来」，而是「改进项没人做」。度量闭环率会把责任落到 owner 与截止日期上。

3. **用三定律分析「Agent 调用工具下单」这个场景，各出一条设计约束。**
   > 要点：① 状态机定律 → Run 必须有状态机（含 `WAITING_EXTERNAL`），下单结果要落库，不能只存在对话历史里；② 稀缺资源定律 → 限流要限「模型并发 + 工具调用 QPS + 单 Run 预算」，不是只限 HTTP QPS；③ 不可回滚定律 → 下单是外部副作用，失败只能补偿（取消订单/退款），所以必须幂等（`run_id`+`step_id`）且有补偿预案。
