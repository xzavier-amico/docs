## 28.1 引子：一个 2Gi 的 pod，堆只有 800MB，却被 OOMKilled

一个 RAG 服务，`kubectl top` 显示 RSS 常驻 1.9Gi，而 `/debug/pprof/heap` 里 `inuse_space` 只有 780MB。K8s 的 limit 是 2Gi，于是它每天被 OOMKilled 一两次。你的第一反应（Java 直觉）：「堆才 780MB，怎么可能 OOM？是不是泄漏？」

Go 的账本比 JVM 多几栏，而且**GC 的目标从来不是「把 RSS 压到最小」，而是「用尽量少的 CPU 换尽量小的延迟」**：

- 780MB 是 `inuse_space`（活对象），但 GC 还允许堆涨到 **`GOGC` 目标**：默认 `GOGC=100`，即活对象 × 2 = 1.56GB 才开始回收，再加上正在标记期间新分配的对象，峰值冲上 1.9GB 完全正常。
- 回收后归还操作系统的内存由 **scavenger** 慢慢做（默认在后台以极低速率还给 OS），所以 RSS 的下降总是滞后于堆的下降。
- Go 运行时自身还有 `mheap` 元数据、`mcache`/`mcentral` 的 span 缓存、goroutine 栈（第 17 章）、以及 `sync.Pool` 的 victim 缓存（第 22 章）——那些不在 `inuse_space` 里。

修法不是调大 limit，而是两条：`GOMEMLIMIT=1700MiB`（让 pacer 知道真实的墙在哪），以及把超大的请求缓冲改成有界 + 池化（第 30 章）。改完 RSS 稳定在 1.5Gi，OOMKilled 消失。

> 🎯 本章的立场：**Go 的 GC 是「为服务端低延迟 + 低复杂度」量身定做的一台机器，它故意放弃了三代 JVM 收集器引以为傲的三件武器——分代、压缩、可移动对象。** 这不是落后，是权衡。你只有理解它放弃了什么，才知道什么时候该绕开它。

## 28.2 直觉模型：一个「不停工的大扫除队」

先给一张能记住的脑图。Go 的 GC 是**并发标记清扫（concurrent mark-sweep）**，不分代、不压缩、对象一旦分配**永不移动**。

```
时间轴（一次完整的 GC 周期）：

  ┌── STW ──┐                        ┌── STW ──┐
  │ sweep   │◀──── 并发标记 (mark) ───│  mark   │     并发清扫 (sweep)
  │ term.   │     与用户代码同时跑      │  term.  │     与用户代码同时跑
  └─────────┘                        └─────────┘
     几十 µs          占掉 25% CPU         几十~几百 µs        后台 & 按需

  阶段名（源码宏）：_GCoff → _GCsweepTerm → _GCMark → _GCMarkTerm → _GCSweep
  对应函数：        sweepone   stopTheWorld  gcBgMarkWorker  stopTheWorld  gcSweep
```

**两次 STW（stop-the-world）**就是图里那两个尖峰，也是最容易被误解的地方：Go 的 STW **不负责标记也不负责清扫**，它只做「开会前的点名」——把所有的 P 挂起、把根集合（各个 goroutine 的栈、全局变量、寄存器）确定下来。所以它极短，典型是几十微秒量级；真实世界的尾延迟大头在**标记期间的 CPU 争抢**和 **mark assist**（28.3.2），不在 STW。

### 三色标记：一句话版本

把堆里所有对象都涂成白色（「可能是垃圾」），从根出发把遇到的涂灰（「活着，孩子还没检查」），检查完一个灰对象的所有指针就把自己涂黑（「我和我的孩子都确认活着」）。标记结束时还白着的，就是垃圾。

```
标记开始前（全部白，✓ 表示在根集合里）          标记过程中
                                              
 栈/全局(根)                                   栈/全局(根)
   │                                             │
   ▼                                             ▼
 ┌───┐    ┌───┐    ┌───┐                     ┌───┐    ┌───┐    ┌───┐
 │ A │───▶│ B │───▶│ C │                     │ A │───▶│ B │───▶│ C │
 └───┘    └───┘    └───┘                     └───┘    └───┘    └───┘
  gray     white    white                     black    gray     white
                                          （A 的指针已扫完）(B 待扫描) (还没被发现)

标记结束：C 被 B 扫描后变灰→黑；所有仍白的对象 = 垃圾，等待 sweep 回收。
```

### 为什么需要写屏障：一个必须防住的时序

标记是**并发**的，用户代码还在跑，随时可能改指针。看这个致命时序：

```
   ① A(黑) ──▶ C(白)                ② 删掉 A→C，把 C 挂到 B(黑) 上
                                    A(黑)   B(黑) ──▶ C(白)
   如果 A 已经被扫描过（黑的），GC 不会再去看 A，
   那么 C 只被黑对象引用，永远不会被标灰 → 被当成垃圾回收掉 ❌
```

**这就是三色不变式要防的东西**。两种经典补法：**Dijkstra 插入屏障**（写指针时把新值涂灰，"不许黑指白"）和 **Yuasa 删除屏障**（写指针时把旧值涂灰，"放过被断开的那个"）。Go 1.8 起用的是**混合写屏障（hybrid write barrier）**——两个都做：

```go
// Go 1.8 hybrid write barrier（提案原文伪代码，实现在 runtime/mbarrier.go + asm_amd64.s）
writePointer(slot, ptr):
	shade(*slot)   // Yuasa：被覆盖的旧值，涂灰
	shade(ptr)     // Dijkstra：写入的新值，涂灰
	*slot = ptr
```

它换来一个巨大的好处：**标记结束时不需要再 STW 重扫所有 goroutine 栈**。老的 Dijkstra 屏障必须「屏障期间被写过栈的 goroutine 全部重扫一遍」，那是一笔几毫秒到几十毫秒的 STW 账单；混合屏障把这张账单砍掉了，同时把「对栈的写入」也统一纳入了保护。代价是**每个堆指针写都多一条指令**——这也是为什么 Go 程序员要关心「减少指针密集的写入」（第 30 章的分配优化其实是同一个账本）。

## 28.3 底层实现

### 28.3.1 标记位的存放：`mspan` + `mbitmap`

Go 的标记位不在对象头（**Go 没有对象头**，这是和 JVM 最本质的差异之一）。每个 span（一组同 size class 的对象）自带两张位图：`mspan.gcmarkBits` 和 `mspan.allocBits`（`runtime/mheap.go` 的 `type mspan struct`），位图操作在 `runtime/mbitmap.go`（`isMarked`、`setMarked`、`markBits` 等）。因为位图按 span 组织、按 8 个对象一组压缩存放，扫描时是**连续内存顺序访问**——这正是 1.25 Green Tea GC 要利用的局部性。

### 28.3.2 mark assist：谁分配谁还债

标记期间 GC 只有 25% 的 CPU 额度（`gcController` 的 `consMark` 就是那个比例）。如果业务代码疯狂分配，标记追不上，堆会失控。于是 Go 引入了**分配即还债**：

```go
// runtime/mgc.go，删减后的骨架（关键行保留）
func gcAssistAlloc(gp *g) {
	// 在 g0 上、持锁、preemptoff 时不能帮忙（会破坏运行时自身的不变量）
	if getg() == gp.m.g0 { return }
	if mp := getg().m; mp.locks > 0 || mp.preemptoff != "" { return }
	// gcAssistBytes < 0 表示这个 goroutine 已经"欠债"了
	if gcBlackenEnabled == 0 || gp.gcAssistBytes >= 0 { return }

	for {
		// 按「扫描一个字节需要多少分配字节」的汇率折算工作量
		scanWork, _ := gcAssistAlloc1(gp, gcController.assistWorkPerByte)
		if scanWork == 0 { break } // 债务人已清
	}
	// 多扫的部分记账，用来抵消其他 goroutine 的债务
	gcFlushBgCredit(scanWork)
}
```

画面感：**你在标记期间分配到多少字节，就得亲手扫掉对应数量的对象**。所以一个分配猛的 goroutine 会有相当一部分 CPU 花在 `gcAssistAlloc` 里——**这在 pprof 里长得像「业务代码变慢」，其实是 GC 在收费**（第 29 章会教你怎么在火焰图里认出来）。

### 28.3.3 GC pacer：它到底想在什么时候开始回收

`runtime/mgcpacer.go` 里的 `gcControllerState` 是「GC 的自动驾驶」，它的核心输出是 `heapGoal`（下一次 GC 的目标堆大小）和 `trigger`（触发点）。你可以用一个公式概括：

```
无内存限制：  next_gc ≈ live_heap × (1 + GOGC/100)        // GOGC=100 → 涨到活对象的 2 倍就回收
有内存限制：  heap_goal = min(下一个 GOGC 目标, 由 GOMEMLIMIT 推出的上限)
             且 GC 越接近内存上限，就越"提前、越频繁、越省内存"
```

`GOGC` 影响三件事：**回收频率、GC CPU 占比、峰值 RSS**。`GOGC=off` 就是关掉自动 GC（只有 `debug.SetGCPercent(-1)` 或 `GOMEMLIMIT` 顶着才不会爆）。

### 28.3.4 `GOMEMLIMIT`（1.19）：软限制，不是硬墙

`GOMEMLIMIT` 是**软**限制：Go 会尽最大努力让总内存（堆 + runtime 管理的内存）不超过它，但**不保证**。官方明确说过：它替代不了 `GOGC`，唯一安全的用法是「容器 limit 的 80%~90%」。

```go
package main

import (
	"fmt"
	"runtime/debug"
)

func main() {
	// 容器 limit = 2GiB，留 ~15% 给栈、runtime 元数据、cgo、页缓存波动
	const limit = 1700 << 20 // ≈1.7GiB
	debug.SetMemoryLimit(limit)

	// GOGC 可以放宽到 200~400：反正有内存上限兜底，减少 GC 次数
	debug.SetGCPercent(200)

	stats := debug.GCStats{}
	debug.ReadGCStats(&stats)
	fmt.Printf("GC 次数=%d 最近暂停=%v\n", stats.NumGC, stats.Pause[0])
}
```

⚠️ **死亡螺旋保护**：当 GC 已经吃掉约一半 CPU（`runtime/mgcpacer.go` 里的 `gcCPULimiter` 负责监测），pacer 会**停止收紧**——宁可短暂超一点内存，也不让程序 100% 卡在 GC 里。所以 `GOMEMLIMIT` 设成一个根本达不到的值，等价于没设。

### 28.3.5 栈扫描与安全点：STW 到底在等什么

标记开始时必须拿到**根集合**：全局变量（`runtime/data` 段 + `moduledata`）、每个 goroutine 的栈、以及当前在寄存器里的指针。扫栈要求 goroutine **停在安全点**：

- 主动安全点：函数序言里的 `stackguard` 检查、`morestack`。
- 被动安全点：1.14 起基于信号的异步抢占（`runtime/preempt.go` 的 `suspendG`、`asyncPreempt`，SIGURG），详见第 19 章。
- 真正的扫描在 `runtime/mgcmark.go` 的 `scanstack()`：逐帧解析 `runtime._func` 的 stack map，判断每个栈槽是指针还是标量。

因为混合写屏障免掉了「标记结束时重扫栈」，第二次 STW（`_GCMarkTerm`）只需要检查各 P 的标记任务是否完成、把白对象转成可回收、重置状态。这就是为什么 Go 的 STW 分位能做到**几十到几百微秒**——它和堆大小几乎无关。

### 28.3.6 scavenger：RSS 为什么总跟不上 GC

`sweep` 只是把 span 标成可复用（内存还在 Go 的 `mheap` 里），**还给操作系统是 scavenger 的活**（`runtime/mgcscavenge.go`，`bgscavenge` goroutine）。它以「不引起下一次 GC 提前」为前提慢慢 `madvise`。所以「GC 之后 RSS 没降」是**设计如此**，不是泄漏。想强制归还：`debug.FreeOSMemory()`——但它会触发一次完整的 GC + 全量 scavenge，**线上千万别在请求路径上调**。分配器与 scavenger 的细节见第 15 章。

### 28.3.7 Green Tea GC（1.25）

Go 1.25 引入实验性 GC：`GOEXPERIMENT=greenteagc`。核心思路一句话——**别一个对象一个对象地扫，把同一个 span 里的对象攒成批，一次扫完**。收益来自两点：① 连续内存的顺序访问（减少 cache miss 与 TLB 压力），② 批量分配扫描工作给 P，减少调度与原子操作开销。官方口径是许多工作负载上 GC CPU 降低 10%~40%，对小对象密集的服务最明显。它对用户代码透明（没有 API 变化），但**注意实验开关会影响构建**——线上别盲开，用真实流量压一遍。（实现随版本演进，以你本地 `$GOROOT/src/runtime` 为准。）

## 28.4 Java 对照：Go 为什么不做分代、不做压缩

| 维度 | G1 | ZGC | Go（并发标记清扫） |
| --- | --- | --- | --- |
| 分代 | 是（Young/Old） | 是 | **否** |
| 压缩/移动对象 | 是（region 内拷贝） | 是（并发重定位） | **否，永不移动** |
| 写/读屏障成本 | SATB 写屏障 | **染色指针 + 读屏障**（每次读都检查） | 混合写屏障（每次堆指针写） |
| 暂停目标 | 可设 `MaxGCPauseMillis` | < 1ms | 无参数，实测几十~几百 µs |
| 吞吐开销 | 10%~20% | 更高（读屏障） | GC CPU 目标 25%，峰值可超 |
| 调参旋钮 | 一堆 | 一堆 | **只有 `GOGC` + `GOMEMLIMIT` 两个** |
| 碎片 | 压缩后无碎片 | 压缩后无碎片 | **有碎片，但 span size class 已缓解** |

**Go 主动放弃三件武器的理由，逐条都要能讲：**

1. **不分代 → 因为「短命对象根本不该上堆」**。分代假说（多数对象朝生夕死）在 Java 里成立，所以把新生代做小、频繁回收最划算。Go 的答案是**把这道题提前到编译期**：逃逸分析（第 14 章）把大量短命对象直接放栈上，函数返回就没了，压根不进 GC 的视野；再剩下来的堆对象，寿命分布已经没那么「朝生夕死」。分代还要维护「跨代引用」的记录（card table），那是额外的写屏障与额外内存。
2. **不压缩 → 因为「对象不可移动」是 Go 生态的隐性契约**。`unsafe.Pointer`（第 16 章）、cgo 传给 C 的指针、`runtime.KeepAlive` 的使用、以及大量「地址作为 key」的代码，都建立在「对象在堆里待着就不动」这一前提上。允许移动就必须引入读屏障（ZGC 那种染色指针），每次读指针都多一条指令——对一个把「简单可预测」当圭臬的运行时来说，这笔税太贵。
3. **不分代 + 不压缩的直接代价**：内存有碎片、RSS 归还滞后、堆增长只能靠 `GOGC` 与 scavenger 慢慢磨。这就是 28.1 那台服务 OOMKilled 的根因；而它**不需要**像 JVM 那样去调 region 大小和 GC 线程数。

> 💡 一句话对比：「G1/ZGC 是在**堆内**用移动和分代把垃圾处理得又快又整齐；Go 是在**堆外**（编译期逃逸分析 + 栈）先把垃圾挡在门外。」

## 28.5 框架与工程落地

- **K8s 三件套对齐**：`resources.limits.memory` → `GOMEMLIMIT = limit × 0.85` → `GOGC=200`（有余量时放宽，减少 GC 次数）。1.25 起 `GOMAXPROCS` 也会感知 cgroup CPU limit，不用再手写 `automaxprocs`。完整清单见第 52 章。
- **观测**：短期 `GODEBUG=gctrace=1`；长期用 `runtime/metrics` 拉 `/gc/heap/goal:bytes`、`/gc/pauses:seconds`（直方图）、`/memory/classes/heap/objects:bytes`，再接 Prometheus（第 35 章）。
- **Agent 场景的三个具体动作**：
  1. **流式响应用 `bufio.Reader` 逐块读，绝不 `string +=` 拼全文**（第 13 章）——SSE 的 token 流是典型的「小对象雪崩」。
  2. **批量 embedding / 大文档解析要有界**：一次 `io.ReadAll` 200MB 的 PDF，等于给 GC 塞一个巨型对象。用 `io.LimitReader` + 分块。
  3. **`sync.Pool` 缓存请求级 buffer**（第 30 章），但记住它会被 GC 清空——**不能拿 Pool 当缓存用**。
- **`gctrace` 长什么样、怎么读**：

```bash
GODEBUG=gctrace=1 ./gateway
# gc 12 @3.421s 3%: 0.018+2.1+0.004 ms clock, 0.14+0.72/1.9/0.34+0.032 ms cpu, 812->815->402 MB, 900 MB goal, 0->8 P
```

| 位置 | 含义 | 什么时候该紧张 |
| --- | --- | --- |
| `gc 12 @3.421s 3%` | 第 12 次 GC、程序启动 3.421s、**GC 累计占用 CPU 3%** | 持续 > 25% 说明 GC 过载 |
| `0.018+2.1+0.004 ms clock` | STW(sweep term) + 并发标记 + STW(mark term) | 两个 STW 应远小于 1ms |
| `0.14+0.72/1.9/0.34+0.032 ms cpu` | assist / 后台标记(并发/空闲) / mark term 的 CPU 时间 | assist 高 = 分配太猛 |
| `812->815->402 MB` | GC 开始时 → 标记结束后 → 清扫结束后 的堆大小 | 「开始时」远超 goal 说明分配过快 |
| `900 MB goal` | 本次目标是 900MB | 比预期低/高，去查 `GOGC`/`GOMEMLIMIT` |
| `0->8 P` | 参与标记的 P 数量（从 0 变成 8） | 远小于 GOMAXPROCS 说明 CPU 不够分给 GC |

## 28.6 踩坑清单（CR 可直接抄）

| 现象 | 原因 | 正确写法 | 详见 |
| --- | --- | --- | --- |
| pod 被 OOMKilled，但 heap profile 只有 limit 的一半 | `GOGC=100` 允许堆翻倍；RSS 还包含栈、runtime 元数据、未归还 span | 设 `GOMEMLIMIT = limit × 0.85`，并核对 `inuse_space` 与 RSS 的差 | 28.1 / 28.3.4 |
| GC 之后 RSS 不降，以为泄漏 | scavenger 是后台慢速归还，属设计行为 | 看 `heap profile` 的 `inuse_space` 是否稳定；不要用 `debug.FreeOSMemory()` 救火 | 28.3.6 |
| 尾延迟出现周期性 5~20ms 尖峰 | 不是 STW，而是并发标记挤占 CPU / mark assist | 提高 CPU limit 或降 `GOGC`；在 pprof 里搜 `gcAssistAlloc`、`gcBgMarkWorker` | 28.3.2 |
| 为了「省内存」把 `GOGC` 设成 20 | GC 频率暴涨，CPU 全花在 GC 上，吞吐崩 | 有内存墙就用 `GOMEMLIMIT`，`GOGC` 反而可以放宽 | 28.3.3 |
| 把 `GOMEMLIMIT` 设成恰好等于 limit | 软限制 + 栈/元数据/页缓存超支 → OOMKilled | 留 10%~20% 余量 | 28.3.4 |
| 在请求路径上调 `debug.FreeOSMemory()` | 触发完整 GC + 全量 scavenge，秒级抖动 | 只在诊断脚本里用 | 28.3.6 |
| 用 `sync.Pool` 缓存跨请求的业务数据 | Pool 会被 GC 清空（victim cache 只保一轮） | Pool 只放「可重建的临时缓冲」，业务缓存用 LRU | 第 22 章 |
| 大对象（> 32KB）频繁分配 | 走 large object 路径，直接进 mheap，GC 与 scavenger 都更贵 | 池化/分块/流式处理 | 第 15 章、第 30 章 |

## 28.7 一页速记

| 关键词 | 一句话结论 |
| --- | --- |
| 算法 | 并发三色标记 + 清扫；不分代、不压缩、对象永不移动 |
| 写屏障 | 1.8 起混合屏障（Dijkstra 插入 + Yuasa 删除），代价是每次堆指针写 |
| 省下的账 | 标记结束**不需要** STW 重扫所有栈 |
| 两次 STW | sweep termination + mark termination，只做「点名取根」，几十~几百 µs |
| mark assist | 分配多少就扫多少，pacer 用汇率 `assistWorkPerByte` 折算 |
| pacer | `next_gc ≈ live × (1+GOGC/100)`；有 `GOMEMLIMIT` 时取更紧的那个 |
| `GOGC` | 调回收频率/CPU 占比/峰值 RSS；`off` 等于关自动 GC |
| `GOMEMLIMIT` | 1.19，**软**限制，只该设为容器 limit 的 80%~90% |
| scavenger | 后台把空闲 span 还给 OS；RSS 滞后是正常的 |
| Green Tea | 1.25 实验（`GOEXPERIMENT=greenteagc`），按 span 批量扫描提升局部性 |
| 观测量 | `GODEBUG=gctrace=1`、`runtime/metrics` 的 `/gc/pauses:seconds` |
| Java 对照 | G1/ZGC 靠「分代 + 移动」，Go 靠「编译期逃逸分析把垃圾挡在堆外」 |

## 28.8 自检题

1. **为什么 Go 的 STW 时间几乎与堆大小无关？G1 的 `MaxGCPauseMillis` 为什么做不到这点？**
   > 要点：Go 的 STW 只做「挂起所有 P + 固化根集合 + 校验标记进度」，真正的标记清扫全在用户代码并发跑；堆越大只是「并发标记跑更久」，不增加 STW。G1 的暂停里包含 copy/evacuation 与 remember set 更新，堆越大要移动/扫描的对象越多，暂停随堆增长。

2. **混合写屏障为什么能砍掉「mark termination 重扫所有栈」这一步？它付出了什么代价？**
   > 要点：它对「新值」和「被覆盖的旧值」都涂灰（Dijkstra + Yuasa 双保险），因此任何在标记期间被改写的指针关系都被显式记录，不再需要「屏障期间写过栈的 goroutine 重扫」。代价是每次堆指针写多一条指令 + `wbBuf` 缓冲与 flush 开销；且屏障期间对栈的写入也要付出同样成本。

3. **一个服务 `heap inuse` 稳定在 600MB，容器 limit 1Gi，却偶发 OOMKilled。三个最可能的解释是什么？**
   > 要点：① `GOGC=100` 允许堆涨到 ~1.2GB，超了 limit（修：`GOMEMLIMIT≈850MiB`）；② `inuse` 只算活对象，未归还的 span + 栈 + runtime 元数据让 RSS 更高（修：看 `/memory/classes/*` 全类目）；③ 突发大请求造成瞬时大分配（如 `io.ReadAll` 一个大 body），GC 来不及反应（修：`io.LimitReader` / 有界缓冲 / 提前预估 `MaxBytesReader`）。
