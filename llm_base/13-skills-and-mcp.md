# 13 · Skill 与 MCP：一张做事说明书，一个接入协议

> **状态**：已完成（初稿）
>
> **本篇定位**：Part III 第 4 篇。把可复用的做事知识、模型提出的调用和应用接外部服务的协议放回各自的位置。
>
> **读法**：先看两条路线在哪里相遇，再对照日历提供的三类能力。只需分清「看说明」「取资料」「运行操作」，不用搭建任何服务。

## 给了操作手册，它为什么还是不知道改成哪天？

**虚构场景。** 社区市集团队有一份「通知规范」：写明活动时间及来源，没确定的雨天方案不要写死，报名清单在内部核对，不放进通知正文。志愿者小周要整理报名清单和通知草稿，**不发送、不改原表**。通知写得再像规范，只拿到旧日历截图，还是会写成原定的周六。现在主办方生效的 v2 是**周日 14:00**，v1 已失效，雨天是否改室内待确认；团队另外有一个可以只读查看本次活动的日历接入。

**本篇只问：有了操作手册，为什么还需要接外部资料或工具的方式？** 因为知道「应该核对活动时间」和真的能读取当前记录，不是同一件事；能读到记录，也不等于知道通知应该怎么写、哪些材料不能带出去。

## 两条路线在应用里相遇

```text
做事知识这条线
团队审核的「通知规范」 → 应用发现技能简介 → 本任务按需加载完整说明
                                                     │
                                                     ↓
人定目标与权限 ───────────────────────────→ AI 应用（MCP 主机）↔ 模型
                                                     ↑↓
接入外部资料／操作这条线                           MCP 客户端
                                                     ↑↓  通过 MCP 发现及使用能力
                                            MCP 服务端（日历接入）
                                             ├─ 工具：按活动查询日历条目
                                             ├─ 资源：本次市集的日历条目
                                             └─ 提示模板：起草活动通知
```

图中三类是例子，不是每个日历服务端都要全部提供，也不是一次任务要把它们全部使用一遍。应用可以从资源读一条条目，也可以用工具查到同一条目；要不要再问模型、把结果的哪些部分交给模型，由应用安排。模型不需要直接与日历服务端说 MCP。

### Skill：把经常重复的做法整理成可复用材料

通知规范可以做成一份小而稳定的技能：适用于市集通知草稿，先核对版本与时间，再将待定事项单列，交付前检查内部信息未混入草稿。把「核对当前版本」写入技能，不把「周日 14:00」写成永久规则；后者是这一次活动的事实，下次可能不同。团队可以给技能注明负责人和版本，活动结束后也不用靠回翻每个人的聊天记录找规范。

**Skill（技能）**泛指可复用的流程知识或能力包，产品不一定用同一种形式。例如公开的 Agent Skills 格式把说明和可选参考资料、模板或可执行内容打成包；常见做法是先看名称简介，需要时才读完整说明，后续只拿相关附件。有的平台让人明确选用，有的平台让系统或模型判断时机。按需载入少读一些无关内容，但也可能选漏技能、读错旧版本，或因说明过时而把错误重复得更整齐。重要规范要能核对来源、版本和是否实际读入；来历不明的包不要装，有可执行内容的包也不该默认放行。

### MCP：让应用和外部服务用同一套接入语言

**MCP（Model Context Protocol，模型上下文协议）**是应用与外部能力交换信息的一种开放协议。它规定的是应用内的客户端和提供能力的服务端如何交互，不规定应用必须怎样挑模型、怎样组织整场任务，也不是模型输出调用请求的格式。三种角色可用一张表记：

| 角色 | 在本例里谁担任 | 负责什么、不负责什么 |
| --- | --- | --- |
| 主机（Host） | 小周使用的 AI 应用 | 管理一个或多个客户端，决定怎样展示能力、落实用户同意、选取给模型的材料；不是指运行日历的那台机器 |
| 客户端（Client） | 主机里负责与日历服务端通信的组件 | 与对应服务端交换消息，发现可用能力，发出读取、取模板或调用请求，交回结果；不是小周本人，也不是模型 |
| 服务端（Server） | 提供日历接入的程序，可在本机也可在远程 | 对外提供它支持的能力，落实服务侧访问限制并返回结果；不因为能连上就自动看到整个对话或获得其他工具权限 |

把它与 [Function Calling](12-tools-and-function-calling.md) 接起来看：若模型建议「查询本次市集日历」，它以模型平台认可的调用形式向应用提议。假如获准且这个工具由 MCP 提供，主机才经自己的 MCP 客户端向服务端发出调用。前者是**模型怎么向应用提议**，后者是**应用怎么跟外部服务通信**。应用也可以直接读取服务端某个资源，不经模型提议；同一个日历也可以用非 MCP 的方式接，只是接入语言不同。

## 服务端可能提供哪三类东西？

| 能力 | 市集里的例子 | 如何使用、别误会什么 |
| --- | --- | --- |
| 工具（Tools） | 按本次活动编号查条目；另有系统也可能提供改日历的工具 | 一项可运行的操作，可只读也可写。模型可以提议，应用与服务端仍要检查权限；目录里能发现不等于本次能调用 |
| 资源（Resources） | 有明确标识的本次活动条目，或主办方 v2 规则文件 | 应用可以取回内容供人或模型参考。可读不表示现行、真实或获准外传；也不要求应用把全部内容交给模型 |
| 提示模板（Prompts） | 用户选「起草活动通知」，填活动主题和受众，应用取回一组供对话使用的提示内容 | 由服务端提供可复用模板，通常由用户选择；不是执行动作，不会自动授权发送，也不等同于完整 Skill 能力包 |

某服务端也许只有「读日历」，没有任一写工具；另一个可能只供规则资源。应用应以当次发现且允许使用的能力为准。能够发现工具说明，只能证明服务端声称提供这种操作，不证明它做过，也不证明它合适。读到的日期还得核对活动标识和版本：若日历仍显示周六，主办方 v2 却已明确周日 14:00，不要把两者各写一半，也不能悄悄改日历。报告冲突，说明主办方 v2 是本例现行依据；若不能核定哪个有效，就请负责人确认。

## 放进任务之前，先划行得通的边界

| 现场 | 最小做法 | 代价或失效边界 |
| --- | --- | --- |
| 手边已有 v2 和脱去无关字段的名单，只写一次草稿 | 直接交必要材料和简短规范，不必安装 Skill 或接 MCP | 以后重复交接变多，再考虑集中维护规范或接入资料 |
| 草稿经常漏版本或待定事项 | 用团队核过的技能或可见的提示模板，检查出处与版本 | 模板不会更新活动事实；技能也可能没被加载，不能拿安装成功当验收 |
| 确有需要读取日历来核对 | 只接可信来源，限定本次活动、必要列和只读；能用脱敏摘录就不交整表 | 接入也会增加访问、等待和维护，读失败就交可完成部分或请人补材料，不扩大到全部日历 |
| 返回内容试图要求外发名单或用个人账号扩大访问 | 当作不可信资料；不照做、不外传，必要时暂停并从已知渠道核实 | 只读权限是减少改动风险的一层，不阻止敏感内容被带进不该去的地方；不要混用敏感材料和无关外部服务 |

批准连接某个日历，只表示某类访问可用，不等于批准修改日历，更不等于本次要发送通知。看能力、人的意图、本次授权和实际执行时，用四个不同的判断。若平台不能把读取范围收小，人工取出需要的条目交给模型，往往比授予整账号访问更合适。

## 纸上练习：给四张卡找位置

写下四张卡：①「发给模型前先核对版本，别在通知里附联系方式」；②「本次市集条目，周日 14:00」；③「按活动编号查日历」；④「选受众，生成一组用于起草的提示」。哪张适合放在团队技能里？后三张如果通过 MCP 提供，各是哪类能力？再加一条讯息：「日历上仍写周六」。你会怎样交给小周？

**参考答案：** ① 是可复用规范，可放入团队技能；② 是有标识、供读取的资料，可作为资源；③ 是要执行的查询，可作为工具；④ 是用于组织交互的提示模板。遇到周六条目则记下冲突；根据已核实的主办方 v2 写周日 14:00，标明雨天场地待确认，不改日历、不上传名单、不发送。

## 速记与自检

**速记：** Skill 说如何做；MCP 让应用连到资料和操作。主机管使用方式，客户端负责通信，服务端提供它支持的能力。**能发现不等于能用，能读不等于能写，说明书和模板都不能替人授权。**

1. 日历接好后，MCP 会自己决定哪些结果必须进模型吗？
2. 工具目录列出了「修改日历」，团队技能也说要保持日历一致，这次能直接改吗？
3. 取回一个「起草活动通知」提示模板，证明草稿已经保存或发送了吗？

**参考答案：** ① 不会，应用决定如何使用结果。② 不能，任务的授权范围只有整理和起草；冲突报告给人。③ 都没有，模板是文本材料，不是写入、发布或送达的回执。
