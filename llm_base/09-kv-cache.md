# 09 · KV Cache：为什么模型不用把前文从头再算一遍

> **状态**：已完成（初稿）
>
> **本篇定位**：以常见的自回归 Transformer 为例，看清缓存保留了哪些中间结果、为什么长对话和多人同时使用会占地方。
>
> **读法**：先跟图看一次「读入、续写、再续写」，再用四张纸条判断哪些东西可以复用；分不清缓存和记忆时，直接看第三节的表。

## 1. 草稿写到一半，模型又读了一遍整份报名表吗？

还是这个**虚构市集**：原定周六的旧通知 v1 已失效，现行 v2 改为**周日 14:00**，雨天是否改室内待确认。运营同事只要整理好的报名清单和通知草稿，**不发送**。草稿刚写出「本周末市集调整为……」时，后面接什么显然要参考 v2。可如果每续写一点，都要把清单和通知从头算一遍，新添一句话岂不是要反复返工？反过来，第二次用同一份规则，草稿很快露出开头，也不能说明它背下了规则，更不能说明它知道哪份才是最新版。

本篇只问：**KV Cache 让模型省掉了什么计算，又用什么空间来换？** 下面以常见的自回归 Transformer（仅解码器）为例：每一步根据已经给定或生成的内容预测下一个 Token。不同架构或推理引擎不一定用同一种缓存。

```text
本轮材料：任务边界、现行 v2、必要的报名信息
    │
    ▼
读入（Prefill）处理输入 ──→ 得到候选，选出首个输出 Token
    │                                             │
    └─ 留下已处理位置的 K、V                       ▼
        ┌─────────────────┐   取用         续写（Decode）：处理刚选出的 Token
        │ 工作区：各层的 KV │ ────────────→ 结合现有 K、V，预测下一 Token
        └─────────────────┘ ←───────────── 把刚处理位置的 K、V 留下
                           下一步用更新后的工作区继续
```

图里的工作区保留的是**模型各注意力层里，已处理 Token 对应的 Key 和 Value**。它们是模型算出的数字表示，不是原文、草稿、事实清单或长期记忆。可以把 **Key（键）**想成线索卡上用于匹配的特征，**Value（值）**想成匹配后能用上的信息；新位置形成一个 **Query（查询）**，用它与各个可见位置的 Key 比较，再把相应 Value 按相关程度合起来。类比只帮助理解分工：它不是翻文件时按标题精确命中一张卡，也不是人能读懂的「周日」或「雨天待确认」笔记。不同层保留各自的 K、V，不是给每条事实贴一张便签。

为什么能用旧结果？在这种模型的因果注意力里，前面的位置看不见后面还没出现的 Token。只要前文不变，往末尾加东西就不必把旧位置的 K、V 重做一遍。假如刚选出了通知开头的第一个 Token，下个续写步骤会处理**这个**位置，取用已经留好的历史 K、V，并把新算出的 K、V 放进去，再选下一个 Token。没有这份缓存，常见做法要重新处理整段已知序列来准备下一步。**省下的是旧位置的重复计算，不是新位置与前文之间的注意力计算。** 旧资料仍要被用到，新 Token 仍要算，界面也不会因此让一份长稿瞬间完成。

## 2. 空间换时间：桌上放得越多，越容易挤

权重像多位同事共享的一套固定工具，KV 像每份正在处理的稿子摊开的工作材料。同一个服务通常能让多条请求共用一份加载好的模型权重，但每条请求都要带自己已经处理到的位置。对常见的全注意力模型来说，输入越长、已处理的输出越多，每条序列要留的 KV 往往越多；同时进行的独立序列越多，总占用通常也越大。假如几位同事用的是相同的公开规则，并不意味着他们带着的不同报名数据也能共用。滑动窗口等注意力实现可能只保留一段历史；前缀共享、缓存表示和分配策略也会改变实际占用，不能看字数就报出需要多少显存。

| 发生了什么 | 会影响哪里 | 边界或取舍 |
| --- | --- | --- |
| 输入更长，或续写出更多内容 | 要留的中间结果往往更多；每一步可能还要读取更多历史 KV | 有缓存不等于越写越快。先去掉无关旧材料，不删 v2、雨天待确认和不发送等关键约束 |
| 更多请求同时进行 | 容量紧张时，服务可能减少同时运行的请求、让新请求排队，或按实现暂停、搬走、淘汰部分状态 | 吞吐不保证一直增加；这不是多个人「共用一段聊天」 |
| 把缓存移到主内存，或用更紧凑的表示 | 可少占显存，给更长的任务或更多在跑的请求留空间 | 移动要花时间；降低数字精度可能影响质量，也不保证提速。两者都不是免费扩大模型的上下文窗口 |
| 请求结束或缓存被逐出 | 工作区可回收，有的服务会暂留合格前缀供后续复用 | 缓存丢了通常是要重算，不意味着聊天记录或资料被删除；实际保存范围看产品政策 |

这也补完了[上一篇的时间线](08-cpu-gpu-inference.md)：请求内 KV Cache 主要省的是**续写时**反复算历史的工作；跨请求前缀复用主要省的是**读入时**重算同一个开头。后者有机会让首个 Token 更早到，但如果最久的那段是服务排队、传附件或生成一篇长稿，命中前缀也不等于用户明显感觉更快。多人使用时，省下的计算也可能间接缓解拥堵，但那不是前缀缓存直接跳过了谁的排队。

## 3. 都叫「缓存」或「记得」，到底重用的是什么？

| 机制 | 留着什么？ | 市集里怎么用？ | 不该指望什么？ |
| --- | --- | --- | --- |
| 请求内 KV Cache | 本轮已处理位置的注意力 Key、Value | 写草稿的下一步沿用前文的计算 | 不会替你查到新版通知，也不保存一篇成稿 |
| 跨请求前缀复用 | 先前算好的、仍可用的开头 KV | 两次请求若从相同的任务边界和现行 v2 开始，在满足条件时可少算那段开头 | 不复制旧答案；换了前缀里的日期，相关后缀不能因为看起来相似就直接沿用 |
| 结果缓存 | 之前交付过的结果或回答 | 对可复用的同一任务，应用有条件地取回旧稿，而不重新生成 | 若没区分 v1/v2 或资料更新，可能拿出仍写「周六」的过时稿 |
| 跨会话记忆 | 应用保存的偏好或任务记录 | 下次可以取回「通知先给人审」这一偏好，再由应用纳入本轮材料 | 有记录不代表每次都取回，也不代表旧记录有权覆盖 v2 或获得发送权限 |

跨请求前缀复用说的是**从开头起的 Token 序列吻合**，且模型等运行条件兼容、缓存仍在且获准复用。看起来大意相同的两份输入，换了顺序、改了版本或被应用插入不同内容，实际送入模型的开头就可能不一样。有的引擎按块匹配，并不保证每个相同 Token 都可复用。改动点**之前**共同的开头仍可能命中；改动之后，即使有一段原文一样，也已经不是同一个上下文里的中间结果。不要为了追求命中而把已经失效的 v1 当作现行材料放回去。

**不是明文，也不是匿名。** KV 来自实际输入，和原始报名资料一样需要有相称的存储与访问边界。不要为提升命中率而放宽跨用户共享；涉及名单时，依组织规则核对是否能传到云端、服务是否会暂留、能否隔离不同用户、日志和结果如何保存。缓存命中有时能带来输入计费折扣，但各服务规则不同；不能把「算得少了」直接写成「账单一定少」。

## 4. 手工练习：哪几张纸条还可以留？

找四张纸，依次写下「只交清单和草稿、不发送」「现行 v2：周日 14:00」「雨天是否改室内待确认」「报名材料 A」。它们代表输入的四个**区段**，不是四个 Token。另拿几张便签，画成小方格当「算出的 K、V」，每处理一张输入纸条，就在旁边摆一张方格。把「通知草稿」写在另一张纸上，不混进方格堆。

1. **在同一次请求里续写。** 把一个新生成片段放在末尾，轮到处理它时，保留之前的方格，为新位置添一张。下一步仍要用前面的方格，但不用重画。真实模型以 Token 和层处理；这只是空间与重算的示意。
2. **用同一份规则再处理一份报名材料。** 把 A 换成 B，前三张纸不变。若前缀条件满足，有机会从共同开头接着做，第四张和新草稿仍须重新处理。把完整的旧草稿直接递过去，则是结果复用，不是前缀复用。
3. **找出为什么旧稿不能拿来交差。** 从抽屉拿出上次按旧 v1 做的稿子，第二张写「周六」。与当前四张纸对照，第一张仍可能是共同开头；从第二张不同起，即使后面某张字面相同，也不能拿旧方格当成当前结果，更不能把旧稿当现行通知。验收时请人逐项确认：周日 14:00、雨天待确认、清单符合来源、没有发送。

这套纸条看不出真实命中率，也不能测速度。它能让你分清「不用重画方格」「直接递旧稿」「翻抽屉找记录」是不同的三个动作。

## 一页速记与自检

- **用空间换计算**：Prefill 为输入准备 KV；Decode 用已有 KV 并继续添，不用把旧位置重算一遍。
- **别混淆四件事**：同一请求用旧中间结果；跨请求重用相同开头；应用拿旧答案；应用查旧记录。
- **性能不等于正确或便宜**：长上下文与多请求会占空间，命中只省相应的计算。仍要验版本、权限和账单。

1. **KV Cache 里有一张写着「雨天待确认」的事实卡吗？** 没有。里面是模型内部的 Key、Value 数字表示，已处理的资料仍通过注意力影响续写，不能把缓存当事实表读。
2. **两次请求开头相同，前缀命中后，长通知可以不用逐步生成吗？** 不可以。前缀命中主要跳过部分读入计算，续写仍要做；只有适用的结果缓存才直接交付旧结果。
3. **清空 KV Cache，是否等于删除云端存过的名单和跨会话记忆？** 不等于。聊天记录、附件、日志、结果和记忆有各自的保存边界，要分别核对。
