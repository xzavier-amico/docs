## 0.1 全书的尺子：先找负责的人，再看哪份信息出了问题

```text
用户：定目标、给材料、划权限、定验收
  ↓
应用 / Agent：组装上下文 ──→ LLM：给出回答或提出下一步行动
  ↑                             ├─ 回答 → 应用交付草稿 → 人验收
  │                             └─ 行动建议 → 运行时检查权限
  │                                              ├─ 未授权 → 停下或请人审批
  └──── 把结果或错误放回上下文，判断下一步 ←────────└─ 已授权 → 执行工具
```

这张图画的是一种工具型 Agent。没有执行循环时，对话应用也能只调一次模型；接了工具，也不意味着每次都要调用它。贯穿示例用一个不依赖技术背景的任务：**「按最新规则整理周末市集的报名清单和通知草稿，先别发。」** 第 01 篇看用户、应用与模型的分工；以后逐步加入资料检索、改期指示、并行核对和发送审批；第 26 篇再从头走完整条链路。

每篇用同一套问题收口：**谁在做、看到了什么、代价是什么、怎么确认它做对了？** 比如「还记得我的偏好」要问谁保存、这次有没有取回来；「又快又便宜」要分清是首字更快、总时长更短、账单更低，还是漏做了验收。

## 0.2 全书结构与逐篇大纲

### Part I · 先认清模型：一句话怎样变成一次回答（01–07）

| # | 篇目 | 唯一真问题 · 预定图例或练习 |
| --- | --- | --- |
| 01 | LLM 是什么：分清模型、应用与 Agent | **屏幕上的一条回答，到底是谁做出来的？** 用「同一个问题，普通聊天给清单、联网应用给出处、Agent 起草通知」拆开大语言模型、聊天产品、搜索与 Agent。图上区分预先学到的权重、本轮给的材料，以及外部工具能查到的信息。 |
| 02 | Token 与分词：为什么一个字不一定是一个 Token | **模型计数的单位是什么？** 对比字节、字符、词、子词与特殊 Token；先画字符级、词级、子词级、字节级切分，再用小词表讲 BPE 的合并思路，简比 WordPiece、Unigram；说明 SentencePiece 是工具体系而非并列算法。用中英混排、空格、Emoji 对照两个有标注的 tokenizer，解释输入、输出与账单为什么不能按字数直接换算。 |
| 03 | Transformer 图解：Token 进来以后发生了什么 | **同一个词在不同句子里，模型怎么用上周围线索？** 用「苹果」画出 Token ID → 输入向量与位置信息 → 多层 Attention 和前馈处理 → 上下文表示。用连线粗细示意注意力，解释生成时为何不能看见尚未生成的内容；点明注意力示意不是模型的思考记录。 |
| 04 | 模型家族：Encoder、Decoder 与 Embedding 分别做什么 | **我想生成、翻译、分类或找相似资料，应该选什么？** 做两轴图：架构轴是 Encoder-only、Decoder-only、Encoder–Decoder；任务轴是生成、分类、向量表示等。对照「输入向量」与「Embedding 模型交付的检索向量」；用语义地图说明相似度不是事实正确性。给任务选型表，区分参数量、上下文长度、文字/图片/音频的输入输出能力和样例上的实际表现。 |
| 05 | 一次推理走到底：从读完输入到流式输出 | **为什么通常先等一会儿，然后答案一点一点冒出来？** 以常见 Decoder-only 自回归模型为例，画「组装输入 → 分词 → Prefill 处理输入并得到首步候选 → 选 Token → 后续 Decode → 停止」；用候选条形图手走几步，区分候选分布、采样和界面流式展示，也区分工程里的「推理（使用模型）」与产品说的「推理模式」。 |
| 06 | 模型是怎么练出来的：预训练、后训练与微调 | **什么会改变模型的长期行为，什么只影响当下这次？** 画「预训练 → 后训练（如 SFT、偏好优化）→ 部署使用」；解释全量微调与 LoRA 更新的范围，以及学习率、训练步数/轮数、批大小、数据质量与覆盖面可能影响什么。对照调提示词、接 RAG、做微调的成本与适用症状：新政策不必靠重新训练多背一遍。 |
| 07 | 推理设置：哪些旋钮改变输出，哪些不会 | **想让回答更稳、更有变化或更短，该动哪个设置？** 用同一组候选演示 Temperature、Top-p、Top-k；用反例区分最大输出长度、停止条件、结构化输出、重复惩罚和部分产品提供的推理预算。说明参数名与可用性因产品而异，固定 seed 也不等于跨环境复现；低温、结构正确和事实正确是三件事。 |

### Part II · 解释性能：为什么会卡，缓存的又是什么（08–09）

| # | 篇目 | 唯一真问题 · 预定图例或练习 |
| --- | --- | --- |
| 08 | CPU 与 GPU 推理：快在什么地方，慢在哪里 | **为什么跑的是同一种模型，换机器却不一定每项都更快？** 用分工图解释 CPU/GPU、运算并行、内存/显存容量与带宽，比较本地、云端、混合方案的设备、数据边界、维护与计费。用时间线分开排队、首 Token 等待、生成速度与多人吞吐；讲清量化主要压缩数字表示，可能换来更低占用，也可能损失质量，速度还取决于硬件和实现。 |
| 09 | KV Cache：为什么模型不用把前文从头再算一遍 | **省掉了什么计算，又付出了什么空间？** 用「第一轮把前文算好的中间结果留下，后续接着用」的图，注明缓存的是注意力的 Key/Value，不是文本、答案或长期记忆；解释上下文变长、并行请求增多如何带来额外占用。并排比较请求内 KV Cache、前缀复用（已有计算）、结果缓存（已有答案）和跨会话记忆（已有记录）。 |

### Part III · 从聊天到办事：Agent 怎样行动，谁能叫停（10–14）

| # | 篇目 | 唯一真问题 · 预定图例或练习 |
| --- | --- | --- |
| 10 | Agent 是什么：聊天、固定工作流与行动循环 | **什么时候「会回答」变成了「能根据结果决定下一步」？** 用同一任务做三张泳道图：单轮回答、预设工作流、Agent 循环。讲目标、状态、行动、观察、停止；遇到信息不够、预算耗尽或工具失败时，归还控制权而不是无限尝试。 |
| 11 | 从 Prompt Engineering 到 Harness 再到 AgentOS | **每加一层，到底接管了什么责任？** 用同一任务四个版本演化：先写清指令；再管理何时送哪些材料（Context Engineering）；再由 Harness 把工具、状态、校验、重试和停止装进可控的执行外壳；最后由 AgentOS 式的平台为多个 Agent 提供共享调度、权限、预算、记录与恢复。给一张能力阶梯和「何时不升级」表：这是理解分工的视角，不是统一术语标准或必经的历史阶段。 |
| 12 | Tools 与 Function Calling：建议调用不等于已经执行 | **AI 说「已登记」时，怎么知道真的做了？** 用登记草稿的泳道图区分工具能力、模型给出的结构化调用请求、运行时的验证与执行、外部返回的结果。对照只读查询和有副作用的写入，用确认回执解释「模型声称」与「动作成功」的差别。 |
| 13 | Skill 与 MCP：一张做事说明书，一个接入协议 | **有了操作手册，为什么还需要接工具的方式？** 用「通知规范」和「日历接入」并排说明：Skill 是可复用的流程知识或能力包，平台具体形态不同；MCP 是应用连接外部工具、资源或提示模板的一种开放协议，不是模型调用格式，也不等同于某个工具。画出 Skill 按需加载与 MCP 能力发现/使用的不同位置。 |
| 14 | Steering 与人机协同：任务跑到一半怎么改方向 | **做到一半改日期，哪些步骤可以继承、重做或取消？** 区分出发前指令、运行中追加约束或反馈、暂停/审批/取消，说明实现因平台而异、已发动作不能靠一句话撤销。用权限边界图讲最小权限、敏感材料、来自网页或工具结果的不可信指令，以及发送、付款、发布前的人审。 |

### Part IV · 会管理资料和资源：有记忆，不等于什么都要带（15–20）

| # | 篇目 | 唯一真问题 · 预定图例或练习 |
| --- | --- | --- |
| 15 | 上下文管理：这一轮模型到底看见了什么 | **明明在聊天记录里，为什么这轮还是没用上？** 用「一张有限的工作台」画指令、消息、附件、工具说明、检索结果与输出预留；区分模型窗口、应用截断与使用效果，提醒不同产品对输入和输出限制的计算方式不同。做一张「必带／按需带／不带」的上下文预算表。 |
| 16 | 上下文压缩：少带什么，绝不能丢什么 | **怎样省掉旧对话，又不丢掉承诺和否决记录？** 对照截断、滑动窗口、结构化摘要、引用原始材料、按需找回。用一场日期和预算反复改动的对话验证压缩前后有没有保留决定、依据、边界、未决项；区分压缩内容与复用前缀计算。 |
| 17 | Agent 的记忆：写进去、找回来、改得掉 | **为什么换个会话它可能还记得，也可能记错？** 区分本轮上下文、会话历史、跨会话偏好、可恢复的任务状态和模型权重。画「筛选 → 保存 → 按需取回 → 修正或删除」，讲冲突、时效、授权，以及保存了不代表每轮都能看见。 |
| 18 | RAG：先找出证据，再根据它作答 | **接了知识库，为什么还可能拿旧规则说事？** 一图分开索引准备和查询阶段，走过分段、关键词/向量检索、重排、带出处生成；用新旧市集通知对照检索错误、使用错误与证据不足。讲清 RAG 不改权重、不是有来源就必然正确、也不等于记忆：两者能复用检索手段，但管理目标不同。 |
| 19 | Agent 并行：拆开跑，还是一条线做到底 | **哪些工作能同时做，哪些必须等上游定稿？** 用依赖图拆「核对场地、预算、名单 → 汇总 → 审批」，对比串行、同一 Agent 并行调用独立工具、多 Agent 分工。分支只带必要材料，用统一交付格式合并，并解释冲突、重复劳动、失败取消和预算上限。并行可能缩短等待，但不保证省钱。 |
| 20 | Token 与成本账：省了字，不一定省了钱 | **同一个任务为什么越自动越贵？** 用标为假设的账本对照单次、长循环与并行分支，算清重复输入、工具输出、摘要、失败重试和缓存命中。给优化顺序：先去掉无用轮次与重复材料，再做按需检索、压缩与工具结果裁剪，然后考虑前缀复用、模型分工和预算上限。分别记总 Token、计费金额、等待时间与最终通过率，不保证所有供应商计价相同。 |

### Part V · 真的交付：从模糊提示词到可验收的产物（21–26）

| # | 篇目 | 唯一真问题 · 预定图例或交付物 |
| --- | --- | --- |
| 21 | 提示词怎么写：目标、材料、边界、格式、验收 | **怎样让模型知道什么叫「做好了」？** 用差提示词 → 好提示词 → 仍需人工核实的三列对照，覆盖摘要、事实问答、文件整理和创意发散；区分必须满足、可采用默认和需要先澄清的事，演示给示例怎样固定格式，而不是给事实背书。交付可复制的自然语言任务卡。 |
| ◆22 | AI 短剧：从一句创意到分集大纲与镜头卡 | **「要反转、有电影感」怎么变成能拍、能验收的要求？** 从目标观众、平台/时长、题材与制作限制，走到人物动机、故事节拍、每集钩子和镜头说明。用同一虚构样例给三轮提示词、分集大纲、人物/场景一致性卡、镜头前后对照；区分给 LLM 的编剧指令和给生成工具的画面指令。 |
| ◆23 | Spec Coding 与 Vibe Coding：从快速探索到可验收变更 | **一句「加个导出」要补哪些问题，AI 才不会凭猜测改功能？** 用报名表导出举例，走 **Requirements → Design → Tasks → Testing**：确认人群、权限、筛选范围与非目标，比较设计和边界，拆有依赖的任务，按正常、异常和回归场景验收。验收条件在 Requirements 就写，Testing 阶段执行验证、回报证据并修订。对比 Vibe Coding 用于低风险、可丢弃的探索和用 Spec 收敛重要变更；只展示提示词、规格、任务卡和测试清单，不展示代码。 |
| ◆24 | 小说共创：先澄清读者体验，再开正文 | **作者也没想清楚时，哪几个问题最值得先问？** 用一次澄清对话定核心冲突、叙事视角、风格边界与结局开放度，分清作者已定、允许模型提案、尚未决定；从故事设定簿到章纲再到试写和修订，交付提示词、样章验收表与连续性检查表，对照「先写十章」为什么容易返工。 |
| 25 | 验证与评测：别用一句「我觉得更好」做决定 | **换了提示词、资料、设置或模型，怎么知道真的有改善？** 一次只改一项，用同一组典型、边界、失败样例作前后对照；模型输出有波动时，不凭一次结果下结论。用一页评分表区分机器可查、人工审阅、必须审批；核对出处能不能支持事实、任务有没有实际完成、用了多少时间和预算。越权等硬失败单列，不能靠平均分抵消。 |
| 26 | 收口：一次 Agent 请求的完整旅程与排障表 | **遇到答错、忘事、跑慢、超预算、擅自执行，该先改哪一层？** 走完市集任务的澄清、上下文组装、推理、检索与工具、并行核对、中途改期、审批、交付和复盘，用一张泳道图与账本解释每一步。附症状到处理方法的速查表与术语地图；任务简单时也指出哪些环节可删。 |

## 0.5 写作与验收公约

**机制篇**：一个反直觉现场 → 本篇唯一真问题 → 一张标清谁做什么的图 → 一个正反例或手工练习 → 「能做什么／代价是什么／何时失效」边界表 → 一页速记与 2–3 道自检题。

**场景篇**：从一份真实感的模糊任务开始，保留**初稿 → 澄清 → 修订 → 交付 → 验收**的对照；给可复制的自然语言模板，也展示至少一个不合格产物为什么不能交付。场景可虚构但要明确标记，不编实测、不许用「一致性极高」之类的结论替代证据。

- **图先于术语。** 正文优先用当前站点无需新增依赖就能阅读的文本流程图、泳道图、时间线和对照表；不拿伪代码或 JSON 冒充图解。类比要写明在哪一步失效。
- **数字带条件。** Token 实测标模型或 tokenizer；示意分词和模拟账单标为示意；性能数字标设备、模型、上下文和并发，不能用单条数据宣称「GPU 永远快几倍」。
- **产品行为不是模型定律。** 模型窗口、记忆开关、计费方式、参数、Skill 加载和 Steering 实现因平台而异；讲共通机制，产品例子注明适用范围，不做按钮教程或品牌排名。
- **不重写旧系列。** GPU 硬件看 [计算机系统基座 · CPU vs GPU](../base/18-cpu-vs-gpu.md)，推理引擎实现看 [组件剖析 · vLLM](../comp/49-inference-engine-vllm.md)，生产级调度、平台治理与计费看 [AgentOS 工程架构](../llm/0-summary.md)。本专题只讲读者看得见、能判断、能用的那一层，不展开训练公式、协议字段、引擎源码或集群部署。

| 部分 | 读完应能交出的纸面产物 |
| --- | --- |
| I | 一张「提示词到输出」路径图；能针对一个问题判断是调生成设置、补材料，还是该考虑训练 |
| II | 一张性能诊断卡：慢在排队、读入还是生成，缓存能帮哪一段 |
| III | 一张 Agent 分工与权限图：谁提议、谁执行、何时暂停和找人 |
| IV | 一份上下文与成本账本：带哪些资料、并行哪些步骤、怎样证明没省掉质量 |
| V | 选一个场景，写出能直接使用的提示词、交付物要求和验收清单 |

## 0.6 阅读路线

- **普通用户速读**：[01](01-what-is-llm.md) → [02](02-tokenization.md) → [10](10-agent-loop.md) → [14](14-steering-and-approval.md) → [15](15-context-window.md) → [17](17-agent-memory.md)–[18](18-rag.md) → [21](21-writing-prompts.md) → [25](25-evaluating-results.md)。先知道 AI 能看什么、能做什么、凭什么信它。
- **模型与性能**：[01](01-what-is-llm.md)–[09](09-kv-cache.md) → [15](15-context-window.md) → [20](20-token-and-cost.md)。先看懂模型怎么输出，再定位时间与成本。
- **创作者**：[02](02-tokenization.md) → [15](15-context-window.md)–[16](16-context-compression.md) → [21](21-writing-prompts.md) → [22](22-ai-short-drama.md) 或 [24](24-novel-cowriting.md) → [25](25-evaluating-results.md)。先写好任务卡，再选短剧或小说实例。
- **用 AI 写软件**：[10](10-agent-loop.md)–[14](14-steering-and-approval.md) → [15](15-context-window.md)–[16](16-context-compression.md) → [19](19-agent-parallelism.md)–[21](21-writing-prompts.md) → [23](23-spec-and-vibe-coding.md) → [25](25-evaluating-results.md)–[26](26-end-to-end.md)。先划执行边界，再把模糊需求拆成有证据的验收。

**案例编排**：市集任务贯穿机制篇，短剧／软件／小说各有完整案例。贯穿案例统一口径：原定周六，旧版 v1 已失效；现行 v2 改为周日 14:00，雨天是否改室内仍待确认。本轮只整理报名清单和通知草稿，不获准发送。

**术语边界**：`参数量`是模型里学得的数值规模，`训练参数`在训练时控制更新过程，`推理设置`在使用模型时影响生成。这三种说法常被统称为「参数」，遇到时先问它改变的是哪一步。
