## 30.1 引子：一句「加个导出」，两天后变成一次道歉

**以下案例为虚构，人数、行数与日期为示意，用于展示一次软件变更的完整走法，不是实测。**

10 月 8 日晚上，读书会活动的筹备群里，运营小陈发了一句话：

> 报名表加个导出吧，我下周五要交给场地。

群里四个人，读出了四个版本。

小陈想的是：把第三组那 28 个人导出来，发给组长，让他按名单核对签到。

技术同事阿哲想的是：列表页右上角加一个按钮，点了就把报名表全部导出来。

管数据的老周想的是：又多了一个能把手机号带出去的口子，谁批的？

AI 想的是：这段话最像哪一种「导出」？答案很直接——一个按钮，一张完整的表，所有列。因为这是它见过的、最顺的续写。

第二天下午，阿哲用 AI 做了一个能点的版本，按钮就叫「导出」。小陈试了一次：120 行，七列，姓名、手机号、报名时间、小组、饮食备注、紧急联系人、是否已签到，全在。她愣了一下，随即觉得这样也好——**导出全部更简单，也更全，组长自己挑自己要的。**

10 月 10 日，她把这份文件发给了四个组长。当天下午，一个组长把文件转进了自己小组的群。老周看到那张带手机号的表，问了一句：

> 这个导出，谁能点？

没有人答得上来。因为这个问题从来没有被写下来过。

这件事里没有一个人是恶意的，也没有一处是「模型算错了」。四个人的理解都对，只是他们对「导出」这个词填了四个不同的宾语：**导出谁、导出哪些列、导出给谁看。** 这三格没填，剩下的全是猜。

但真正值得记住的，是另一句更反直觉的话：

> **在软件变更里，AI 最危险的地方不是不会做，而是做得又快又全。**

「全」在别的地方是优点，在这里不是。多导出一组人，多带一列手机号，多发一个群，都是在扩大范围；而范围、权限、数据去向，恰好都不在代码里，在需求里。代码只是把需求里的空白，用一种最顺手的方式填满。

## 30.2 唯一真问题：不写代码的人，凭什么说「它改对了」

**一个不写代码的人，怎么判断 AI 有没有把这次变更改对？**

短答案：**不看它改了哪些代码，看四段承诺能不能对上，看每一步有没有可观察的证据。**

这句话要拆成三个判断。

**第一，你看不懂实现，但你看得懂承诺。** 你不需要知道文件是怎么生成的，你只需要知道：筛选第三组时，文件里应该是 28 行；组长点「全部」时，仍然只能拿到本组；文件里不应该有手机号。这三句话都是业务语言，第三个人可以自己数、自己看、自己对照。**验收的对象是行为，不是实现。**

**第二，空白不是中性的。** AI 的默认动作是把空格填满，而且填得最顺手。你不说「只导当前筛选」，它就会按「导出一张完整的表」来补；你不说「不要联系方式」，它就会按「报名表有什么就带什么」来补。这不是它想多做，是「更全」在大量表格任务里就是更顺的下一段（P1 续写）。**你不写的那一格，会由最省力的那一种解释来填。**

**第三，证据不在对话里。** 它说「改好了」，是一句文本；文件里到底几行、有没有手机号、审计里有没有记录，要去原始系统看（P5 提议与执行；回执见第 16 篇）。一个人不写代码，完全不妨碍他做这件事：他只要坚持看**前后对照、样例数据、谁验证的**。

把这三句合起来：

> **规格不是保证；但没有规格，你连「改错了」都定义不了。**

第 26 篇已经讲过四段怎么分、验收条件为什么写在需求段。这一篇不重复方法，只走现场。

### 四个定位问题，在软件变更里各管一格

| 四问 | 在这次变更里问什么 | 答不上来会怎样 |
| --- | --- | --- |
| **这句话是谁说的？** | 「导出全部更全」是小陈的业务判断，还是 AI 在上一轮自己补的？ | 把模型的猜测写成需求，后面所有人按猜测验收 |
| **它这一轮看见了什么？** | 它看到的列表页、字段、角色，是最新的吗？它知道组长只能看本组吗？ | 按一份过时的页面写验收，做出来必然对不上 |
| **这是提议、事实，还是已执行？** | 「导出做好了」是它说的，还是你真的点过、数过、看过审计？ | 把「它说改好了」当成「改好了」 |
| **我拿什么独立验证？** | 行数对照、角色对照、审计条目，还是只有它自己的复述？ | 验收退化成「我看着还行」 |

第三问在软件变更里格外容易踩。群里有人说「导出功能早就有了」，这句话是提议还是事实？去看一眼那个按钮，比在群里争半小时有用。**规格的第一页不该是功能列表，该是「现在是什么样」。**

「全部」之所以危险，不是因为它是一个坏选项，而是因为它同时满足了三个看起来都对的直觉：更简单、更全、更省事。三个直觉都在回答「怎么做最方便」，没有回答「谁需要、谁可见、到哪去」。而 AI 最擅长的，正是沿着「最方便」往下续写。**它不是故意越权，它只是把「全」当成了「好」。**

## 30.3 四段全流程图：从一句口语到一份证据

先把整条链摆出来。它不是一条单向瀑布，中间有两条回头箭头：一条从测试设计回到需求，一条从执行回到实现或规格。

```text
一句口语
「报名表加个导出」
        │
        ▼
┌──────────────────────────────────────────────┐
│ Requirements  需求                            │
│ 范围 / 非目标 / 权限与字段可见性 / 验收条件    │
│ 出口：带编号的需求 + 每条一个验收 + 权限段      │
└───────────────────┬──────────────────────────┘
                    ▼
┌──────────────────────────────────────────────┐
│ Design  设计                                  │
│ 主路径 / 被否掉的备选 / 边界值 / 风险与挡法     │
│ 出口：方案 + 否掉的理由 + 风险清单              │
└───────────────────┬──────────────────────────┘
                    ▼
┌──────────────────────────────────────────────┐
│ Tasks  任务                                   │
│ 做什么 / 依赖 / 完成标志 / 谁来验                │
│ 出口：一张每行都能单独验的任务表                │
└───────────────────┬──────────────────────────┘
                    ▼
┌──────────────────────────────────────────────┐
│ Testing  测试                                 │
│ 正常 / 异常 / 回归 / 证据                      │
│ 出口：用例清单 + 证据包                        │
└───────────────────┬──────────────────────────┘
                    ▼
              验收签字
        「抽一条需求，能顺着链找到证据」
                    │
        ┌───────────┴───────────┐
        ▼                       ▼
  测试设计发现需求空洞      执行发现不对
  回改需求，不补测试凑      实现错 → 改实现
                            规格没写清 → 回改需求
                            规格写错 → 改规格并留理由
```

图里有两条隐含的顺序。第一条：**权限与字段范围，要在「把东西做出来」之前定。** 不是先易后难，而是先做出来再补权限，会把一次真实的越权留在环境里；而测试环境里的名单，往往就是真名单。第二条：**测试设计要在执行之前。** 写用例时发现的需求空洞，改一句需求就行；上线后被组长发现，就是一次投诉。

### 谁在做什么

| 位置 | 负责 | 不负责 | 出事时最常听到的话 |
| --- | --- | --- | --- |
| **小陈（提需求 / 验收）** | 说清两个场景、四列够不够、谁能看；按证据判收不收 | 设计实现、判断技术可行性 | 「我当时不是这个意思」 |
| **阿哲（执行）** | 用 AI 起草与实现；按任务做；留下可观察的结果 | 替业务定范围；替老周定权限 | 「我是按需求做的」 |
| **老周（数据与权限）** | 定角色上限、字段可见性、审计要留什么 | 写页面文案；替小陈验收行数 | 「需求里没写」 |
| **AI** | 起草四段、补异常场景、生成实现提议 | 确认范围；确认权限；签字 | 「已经改好了」 |
| **原始系统** | 取数、生成文件、写审计、给回执 | 判断谁「应该」看到 | 「系统返回成功」 |
| **组长（使用方）** | 用自己的账号导本组、核对签到、反馈好不好用 | 批准权限；替别人验收 | 「我这边能看到就行」 |

三处分不清就会出事。**提需求和拍板不是一回事**：小陈可以提「我要导第三组」，但「组长能不能看手机号」要老周按数据边界拍板；AI 可以起草需求，但不能确认需求。**起草和执行不是一回事**：AI 可以写出一份很像样的需求段，也能生成一版能跑的页面，但「这一版算不算做到了」不是它说了算。**执行和验收不是一回事**：阿哲可以说「按需求做了」，老周可以说「权限配了」，最后仍要有人拿着文件、角色对照和审计条目说「收」。

## 30.4 Requirements：范围、非目标、权限与验收，一次写死

### 先看写错的那一版

这是 10 月 9 日聊天里凑出来的需求。它只有五句话，每一句都很像人话，所以它通过得很快。

```text
需求（v0，10 月 9 日，聊天里凑出来的）

1. 报名表加个导出按钮。
2. 点了能把报名表导出来，发给组长和场地。
3. 导出全部更简单也更全，组长自己挑自己要的。
4. 联系方式也带上，方便组长联系组员。
5. 下周五之前能用。
```

五句话，四个空格：

| v0 的句子 | 它没说什么 | AI 最顺手的填法 | 后果 |
| --- | --- | --- | --- |
| 加个导出按钮 | 导出谁：当前筛选，还是全部 | 全部 120 条 | 组长拿到别组的名单 |
| 发给组长和场地 | 谁能看：文件去哪、留多久 | 直接发群、发共享盘 | 文件离开系统后收不回 |
| 全部更全 | 范围：这次做到哪里停 | 全部行、全部列 | 范围一次膨胀到底 |
| 联系方式也带上 | 字段级可见性：哪些列能进文件 | 七列全带 | 手机号、饮食备注、紧急联系人一起出去 |
| 下周五之前能用 | 验收：怎样算能用 | 能点开、有文件 | 20 行也叫能用，120 行也叫能用 |

这张表里没有一条是「技术错误」。五句话都成立，只是它们都在说「要什么」，没有一句在说「不要什么、谁能看、怎么算做到」。**需求段的空白不会留在那里；它会由实现的人、AI、或者下一个接手的人，按最省力的方式填掉。**

### 错法一：把「导出当前筛选」做成「导出全部」

这是这次变更里最先发生的错，也是最容易重犯的错。它的起点甚至不是恶意，而是一句听起来很合理的话：

> 导出全部更简单也更全，组长自己挑自己要的。

这句话有三个问题。

**第一，它把「全」当成了「好」。** 对一张 120 行的报名表来说，「全」意味着四个组的人都在里面。组长要的是自己组那 28 行，不是另外 92 行。多出来的部分不是赠品，是别人的数据。

**第二，它把筛选的责任推给了使用的人。** 「组长自己挑」听起来很自由，实际上是把「谁该看什么」从系统搬到了人的自觉上。组长可能挑错，可能懒得挑，可能直接把整张表转出去。**权限一旦变成「请你自觉筛选」，它就不再是权限。**

**第三，它会让「当前筛选」这个真正的需求消失。** 小陈最早说的是「把第三组那 28 个人导出来」；到了 v0 里，这句话变成了「导出全部」。两个版本差的不是 92 行，是**一个功能到底为谁服务**。

正确的写法不是「不要导出全部」，而是把范围写死：**导出范围只跟当前筛选一致；筛选为「全部」时才导出全部；组长的筛选上限就是本组，选「全部」也等同选本组。** 这句话要写在需求段，不是设计段。写在需求段，它是一条范围；写在设计段，它就变成了一条实现选择，下次有人想改，只需要改设计，不需要改需求。**位置决定了它有多难被推翻。**

### 错法二：把联系方式一并导出，没有确认「谁能看」

第二个错更安静，因为它披着一件「方便」的外衣：

> 联系方式也带上，方便组长联系组员。

这句话在业务上完全说得通。组长要通知组员集合时间，要问谁还没签到，手机号确实方便。但它漏了一个问题：**文件离开系统之后，谁还能看？**

页面上的手机号，至少还受页面权限管；文件一旦下载，就可以被转发、被截图、被放进群里、被存进个人网盘。到那一步，系统里的权限配置再严，也管不到一个已经发出去的文件。**导出的本质，是把数据从「有权限的页面」搬到「没有权限的地方」。**

所以「联系方式能不能进文件」不是一道口味题，是一道数据边界题。它至少要回答三件事：哪些列能进文件？哪些角色能看到哪些列？文件去哪、留多久？这三个问题，就是「字段级可见性」和「导出留痕」的入口。它们不是设置项，是需求。

### 改对后的需求段

下面是 10 月 12 日重写的版本。它比 v0 长很多，但没有一句是技术实现；每一句都能被一个不写代码的人读懂、检查、或者拒绝。

```text
需求段（Requirements）· 报名表导出 · v2 · 10 月 12 日

一、为谁做
  提出人：活动运营 小陈（管理员账号）。
  场景一：活动前，把本组名单发给组长，组长按名单核对签到。
  场景二：活动结束后，把名单交给场地与餐饮，用于备餐与保险。
  这两件事决定了：导出必须跟着筛选走，不能只有「全部」；
  文件里不能有联系方式。

二、范围
  在「报名列表」页增加一个导出入口，导出当前筛选条件下的记录。
  导出列固定四列：姓名、小组、报名时间、是否已签到。
  入口上显示本次将导出的行数，例如「导出当前筛选（28 条）」。
  每次成功导出，在审计里留一条记录。

三、非目标（这次明确不做）
  1. 不做「导出全部」的第二个按钮，也不做「先导全部再自己筛」的旁路；
     导出范围只跟当前筛选一致，筛选为「全部」时才导出全部。
  2. 不做定时导出、自动发邮件、共享链接、跨活动合并；
     文件只下载到操作者本机，不进群、不落公共盘、不进共享链接。
  3. 不改报名表单、列表排序、翻页与搜索，也不新增任何导出列；
     手机号、饮食备注、紧急联系人本期不进文件。

四、权限与数据范围
  角色只有三类：管理员 3 人、组长 4 人、普通成员。
  谁能导：
    管理员可以导出全部小组，也可以先筛选再导出。
    组长只能导出自己组；即使把筛选选成「全部」，上限仍是本组。
    普通成员看不到导出入口，也不能通过其它入口导出。
  导什么（字段级可见性）：
    姓名、小组、报名时间、是否已签到：三种角色在文件里都只看得到这四列。
    手机号：只在管理员页面上可见，任何角色的文件里都不出现。
    饮食备注：只在管理员页面与餐饮对接人处可见，文件里不出现。
    紧急联系人：只在管理员页面可见，文件里不出现。
  谁能看、文件去哪：
    文件只下载到操作者本机；下载入口 30 分钟内有效，过期需重新导出。
    不允许转发到群、共享盘、邮件列表；需要给别人时，
    由对方用自己的权限再导一次。
  留什么痕：
    谁（账号）、什么时间、用了什么筛选、导出了多少行、
    包含哪几列、下载入口何时过期。
  权限的时间：只在本期任务内有效；不做「临时开一下、以后再说」。

五、验收条件（做到没做到，看这十条）
  1. 管理员筛选「第三组」后导出，文件里 28 行，每行的小组都是第三组。
  2. 管理员不设筛选直接导出，文件里 120 行，不是当前页的 20 行。
  3. 文件里只有姓名、小组、报名时间、是否已签到四列；
     没有手机号、饮食备注、紧急联系人。
  4. 组长把筛选选成「全部」再导出，文件里仍只有自己组的行，
     且不出现别组任何一行。
  5. 普通成员账号看不到导出入口；即使知道入口位置，也无法完成导出。
  6. 筛选结果为空时，页面提示「当前筛选没有记录」，不生成空文件。
  7. 单次超过 2,000 行时，提示「请收窄筛选」，不生成文件，也不分片下载。
  8. 每次成功导出后，审计里出现一条记录，
     账号、时间、筛选、行数、列与文件一致。
  9. 生成后等 31 分钟再点下载，提示已过期；重新导出后可以下载。
  10. 原有的翻页、搜索、单条查看、报名表单提交、列表排序，行为不变。
```

这份需求段把三样东西从「默认值」变成了「承诺」：**范围**（当前筛选，不是全部）、**非目标**（三条）、**权限与数据范围**（谁能导、导什么、谁能看、留什么痕）。

### 字段级可见性：把「谁能看」写到列上

「权限」如果只写到「组长能导出」，它还是粗的。组长能导出，导出哪些列？手机号能不能带？饮食备注算不算敏感？这些要写到列上。

| 字段 | 管理员页面 | 组长页面 | 普通成员页面 | 导出文件 |
| --- | --- | --- | --- | --- |
| 姓名 | 可见 | 本组可见 | 仅自己 | 可见 |
| 小组 | 可见 | 本组可见 | 仅自己 | 可见 |
| 报名时间 | 可见 | 本组可见 | 仅自己 | 可见 |
| 是否已签到 | 可见 | 本组可见 | 仅自己 | 可见 |
| 手机号 | 可见 | 中间四位隐藏 | 不可见 | 不出现 |
| 饮食备注 | 可见 | 不可见 | 不可见 | 不出现 |
| 紧急联系人 | 可见 | 不可见 | 不可见 | 不出现 |

这张表不是按「谁职位高」排的，是按「谁需要用它做什么」排的。组长需要知道本组谁来了、谁没来，四列够了；他不需要手机号，因为通知可以在群里发，签到可以当面核。管理员需要手机号，是为了处理报名异常，不是为了把它转发出去。饮食备注和紧急联系人只服务于备餐与应急，不属于「发名单」这个场景。

把它写成表，还有一个额外的好处：**任何一列的变化，都能被看见。** 下次有人想「顺手把手机号加上」，他改的不是一句模糊的「导出报名表」，而是这张表里的一格；这一格会牵动需求段、验收条件、测试用例和审计字段。**让改动变麻烦，本身就是一道防线。**

### 导出留痕：不是「有日志」，是能对上文件

「留痕」很容易被做成一句空话：系统里有一条「导出成功」的日志，看上去就有了。但这条日志回答不了最关键的问题：是谁导的？什么时间？用了什么筛选？导出了多少行？包含哪几列？下载入口什么时候过期？

所以需求段里写的不是「记一条日志」，而是：**每次成功导出后，审计里出现一条记录，账号、时间、筛选、行数、列与文件一致。** 这里有两个关键词。**「一致」**：审计里的行数要和文件里的行数一样，不能一个 120、一个 28。**「成功」**：没有留痕就不算成功；页面不能先给下载入口，再慢慢补记录。**留痕不是事后补的说明，它是导出这件事的一部分。**

### 非目标：为什么它比目标更重要

需求段里最容易被人跳过的是非目标。大家觉得目标是干货，非目标是客套。恰恰相反：**目标是开口的，非目标是闭口的；开口的会被一直加，闭口的才能用来拒绝。**

| | 目标 | 非目标 |
| --- | --- | --- |
| 它说什么 | 这次要做什么 | 这次明确不做什么 |
| 它的形状 | 开口，可以一直往上加 | 闭口，写到哪就是哪 |
| 它挡什么 | 挡「不做」 | 挡「顺手多做」 |
| 没有它会怎样 | 不知道往哪走 | 范围膨胀，而且每一步都看起来很合理 |

这次写进需求段的三条非目标，各自挡的是一种很具体的「顺手」：

**第一条：不做「导出全部」的第二个按钮，也不做「先导全部再自己筛」的旁路。** 它挡的是「更全」的诱惑。为什么这条必须写？因为「导出全部」是仅次于「导出当前筛选」的第二顺位自然想法。你不写，它就会以「方便组长自己挑」的形状出现。写清楚之后，任何人再提，你不需要说「这次先不做」，你可以说「需求里已经写了不做，理由是它会扩大数据范围」。

**第二条：不做定时导出、自动发邮件、共享链接、跨活动合并。** 它挡的是「自动化」的诱惑。导出做完之后，下一个最顺的想法一定是「能不能每周自动发给组长」。自动发是另一个动作，涉及对外发送、收件人名单和撤回；它不该被塞进这次变更里。**非目标把「下一步」挡在门外，不是否定下一步，是让下一步单独被评估。**

**第三条：不改报名表单、列表排序、翻页与搜索，也不新增任何导出列。** 它挡的是「反正字段都在表里」的诱惑。报名表已经有七列，导出时「顺手带上」几乎不需要成本；但这一顺手，就把一次名单交付变成了数据泄露的入口。把「不新增列」和「不改表单」写在一起，是为了让实现的人知道：**这次变更的边界在导出，不在报名表本身。**

三条非目标的共同点：**它们都不是「没人会提」的荒唐要求，而是「一定会有人提」的合理要求。** 写非目标的技巧，就是写你预计会有人提的那些；写「不做火星殖民」只是凑数，挡不住任何一次真实的顺手。

### 权限写进需求，不等于权限会发生

> 需求段写「不导出手机号」，是一句承诺；真正让手机号出不去的，是取数时的列白名单和运行时的权限。

需求段能做的，是把「不该做」写成一个可检查的条件；它不能替运行时拦动作。如果取数时仍然把七列都取出来，只是在页面上隐藏了三列，那么文件里还是可能带上；如果组长账号本身有权限看全部，那么页面隐藏也只是遮眼。**需求写边界，设计落实边界，运行时执行边界，测试证明边界。四件事缺一不可**（见第 17 篇）。

### Requirements 的出口：三样东西

1. **一份带编号的需求**，每条一句话，业务语言，不含实现词。
2. **每条需求至少一条验收条件**，形状是「在什么条件下、做什么、看到什么」。
3. **一段权限与数据范围**，回答导出谁、导什么、谁能看、留什么痕；外加一段非目标。

缺了第三样，设计就会按最省事的方式补；缺了第二样，测试就会替需求做决定；缺了第一样，后面所有讨论都会回到「我当时不是这个意思」。

## 30.5 Design：主路径、被否掉的备选，以及哪里会坏

需求段说「要什么」，设计段说「打算怎么走、走到哪里停、哪里会坏」。它不写实现细节，写的是能被业务的人读懂的约束和取舍。

```text
设计段（Design）· 报名表导出 · v2 · 10 月 13 日

一、主路径（一句话说清怎么走）
  列表页把「当前筛选」原样交给取数；
  取数先按角色上限收窄，再按同一套筛选条件取记录；
  生成文件时只取四列白名单；
  生成完给一个 30 分钟内有效的下载入口；
  成功与留痕成对出现，没有留痕就不给下载入口。

二、为什么是这条路（三条备选被否掉）
  备选甲：在浏览器里把当前页的表格拼成文件。
    否掉：只能导当前页的 20 条；而且手机号已经进了浏览器，
    权限收不回来。
  备选乙：新做一个「导出中心」页面。
    否掉：本期只有两个场景；多一个页面就多一套权限要维护。
  备选丙：生成后直接发到组长邮箱。
    否掉：这是对外发送，属于需要人确认的动作；
    本期只做本机下载，发送由人自己做。

三、边界（做到哪里停）
  单次上限 2,000 行；超过提示收窄，不分片。
  同一账号同时只允许一个导出在进行；重复点击返回「正在生成」。
  文件生成后 30 分钟内可下载；过期删除，不保留副本。
  0 条不生成文件，只给提示。

四、风险与挡法
  风险 1：「当前筛选」被理解成「当前页」。
    挡法：入口上直接显示行数；验收 2 专门用 120 与 20 对照。
  风险 2：组长看到别组。
    挡法：组别上限放在取数这一步，不靠页面隐藏；
    组长选「全部」等同选本组。
  风险 3：联系方式被顺手加进列里。
    挡法：列白名单写在需求段；新增列必须改需求段并重新验收。
  风险 4：文件落在服务器或共享目录被别人取走。
    挡法：不落共享目录；下载入口短时有效；不提供转发链接。
  风险 5：导出拖慢列表。
    挡法：导出与列表查询分开限流；导出排队时不影响翻页。
  风险 6：导出成功但没留痕。
    挡法：留痕与成功成对出现；没有留痕不算成功，页面不给下载入口。

五、这次不在设计里留开关
  手机号导出、跨活动合并、多工作表、定时发送——都不在本期。
  不留「以后再打开」的配置项；它会变成一条没人负责的旁路。
```

### 设计段写约束，不写实现

设计段最容易犯的错，是写成一份实现说明：用了哪个组件、加了哪个字段、调了哪个接口。这类内容有两个问题：一是把方案锁死，二是让测试变成「测实现」而不是「测行为」。业务的人看不懂，也没法判断对错。

| 要写 | 写成什么 | 不要写成 |
| --- | --- | --- |
| 主路径 | 「筛选条件原样交给取数，取数按同一套条件取记录」 | 「调用某个查询、传三个参数」 |
| 被否掉的备选 | 「在浏览器里拼文件被否：只能导当前页，手机号已进浏览器」 | 只写选了什么，不写为什么没选别的 |
| 边界值 | 「单次上限 2,000 行；超过提示收窄，不分片」 | 「性能要优化」 |
| 风险与挡法 | 「组长可能看到别组 → 组别上限放在取数这一步」 | 「注意权限问题」 |

第四行最该学：**「注意权限问题」不是挡法，是情绪。** 挡法要落在结构上：过滤、白名单、限额、过期、留痕。每一条都能被验证，也都能被检查是不是真的做了。

### 被否掉的备选：给自己留的后悔药

三个月后，如果有人问「为什么不做成导出中心」，你翻回这一段，能立刻说出当时的理由：本期只有两个场景，多一个页面就多一套权限要维护。没有这一段，讨论会从头再来一遍，而且大概率会得出一个不同的结论，因为没人记得当时的约束。

| 备选 | 看起来的好处 | 否掉的理由 | 留下了什么 |
| --- | --- | --- | --- |
| 在浏览器里拼当前页 | 快，不用改取数 | 只能导 20 条；手机号已经进了浏览器，权限收不回 | 一条「当前筛选 ≠ 当前页」的验收 |
| 新做导出中心 | 集中、以后好扩展 | 本期只有两个场景；多一个页面多一套权限 | 一条「本期不扩页面」的非目标 |
| 生成后直接发邮箱 | 省一步，组长直接收到 | 对外发送要人确认；发出去收不回 | 一条「只本机下载」的权限边界 |

**「被否掉」不是「没想到」，是「想过，并且有理由不做」。** 这两者在返工时差别很大：前者会让你怀疑自己漏了，后者能让你稳住范围。

### 设计段的出口：四样东西

1. **一条主路径**，用业务语言说清数据从哪来、经过谁、到哪去。
2. **至少一个被否掉的备选**，以及否掉的理由。
3. **边界值**：数量上限、时间上限、并发上限，各自超了怎么办。
4. **风险清单**：每条风险配一个挡法，挡法要落在结构上，不能落在「注意」上。

缺了边界值，测试会在执行时临场决定「超过 2,000 行是报错还是截断」；缺了风险清单，测试会第一次听说「组长可能看到别组」，然后把它当成一个意外。

## 30.6 Tasks：依赖、完成标志，以及权限为什么排在生成之前

任务段最常见的切法，是按工种切：页面一条、取数一条、测试一条。这种切法看起来整齐，实际有一个致命问题：**每条都做完了，但没有一条能单独证明做对了。**

正确的切法只有一条标准：**这一条做完，能不能有人单独验它？**

```text
任务段（Tasks）· 报名表导出 · v2 · 10 月 14 日
每一行都要能单独验；验不了的行，说明它还不是一个任务。

任务 1  定四列白名单与三类角色的可见字段
  依赖：小陈确认四列够用（10 月 12 日已确认）
  完成标志：管理员、组长、普通成员三个账号各看一次，
            文件里都只有四列；手机号、饮食备注、紧急联系人
            不在任何文件里。
  谁来验：老周

任务 2  把组别上限放进取数
  依赖：任务 1
  完成标志：组长账号把筛选选成「全部」再导出，文件里仍只有本组；
            换一个组长账号重复一次，结果同样只有本组。
  谁来验：老周

任务 3  接上「当前筛选」，并把行数显示在入口上
  依赖：任务 1
  完成标志：列表显示 28 条时，入口写「28 条」；
            切到「全部」时写「120 条」；入口数字与列表总数一致。
  谁来验：小陈

任务 4  生成文件与短时下载入口
  依赖：任务 2、任务 3
  完成标志：文件能打开；四列正确；中文不乱码；
            28 条与 120 条两种输入都与页面一致。
  谁来验：小陈 + 一名组长

任务 5  审计留痕
  依赖：任务 4
  完成标志：导出一次，审计里出现一条；
            账号、时间、筛选、行数、列都与文件一致；
            没有留痕时页面不给下载入口。
  谁来验：老周

任务 6  空结果、超限与重复点击
  依赖：任务 4
  完成标志：0 条、2,001 条、连点两次三种情况下，
            提示正确且不产生多余文件。
  谁来验：小陈

任务 7  回归原有功能
  依赖：任务 4
  完成标志：翻页、搜索、单条查看、报名提交、列表排序逐项打勾；
            普通成员仍能正常报名，普通成员仍看不到导出入口。
  谁来验：小陈
```

### 坏任务与好任务，差在「能不能单独验」

| 坏任务 | 为什么验不了 | 改成 |
| --- | --- | --- |
| 「页面改一下」 | 改成什么样算改完？ | 「入口显示行数，数字与列表总数一致」 |
| 「取数加个过滤」 | 过滤到什么程度？ | 「组长选全部仍只导本组」 |
| 「测试一下」 | 谁、测什么、拿什么证据？ | 「老周用三个账号各导一次，填角色对照表」 |
| 「把权限配上」 | 配到哪一列、哪个角色？ | 「三种角色在文件里都只有四列，联系方式不出现」 |
| 「优化一下导出」 | 优化到什么算好？ | 「2,001 行时提示收窄，不生成文件」 |

每一行的右边，都有一个共同点：**它是一个可观察的结果，不是一个动作。** 「改一下」是动作，「28 行」是结果；「配权限」是动作，「组长选全部仍只有本组」是结果。

### 依赖：为什么任务 2 必须排在任务 4 之前

> **涉及权限与数据范围的条目，排在「把东西做出来」之前。**

理由不是「先易后难」，也不是「先做重要的」。理由是：**先做出来再补权限，会把一次真实的越权留在环境里。** 如果先做「点一下生成文件」，再补「组长只能导本组」，那么中间那段时间里，任何一个组长点一下，都能拿到全部 120 条含手机号的名单。这段窗口可能只有两天，也可能只有两小时；但测试环境里的名单，往往就是真名单。**权限不是最后一道检查，它是开工顺序的一部分。**

任务 1 在任务 2 之前，也是同一个道理：先定「文件里有哪些列」，再定「谁能拿到这些列」。如果列还没定，权限就只能配一个模糊的「能导出」，最后还是会在文件里露出不该露的东西。任务 5 在任务 4 之后，是因为审计要有一次真实的导出来记录；但审计的设计不能等到任务 5 才开始。**顺序是执行顺序，不是思考顺序。**

### 完成标志：第三个人能看见，才算完成

一条完成标志要成立，至少要满足三件事：**可观察**（不是「我觉得好了」，是「文件里 28 行」）、**可重复**（换一个组长账号、换一天、换一个筛选，结论一致）、**有验收人**（一个具体的人或角色，不是「测试」这个抽象词）。

第三件最容易被敷衍。任务表上写「谁来验：测试」，等于没写，因为没有人知道「测试」是谁、他手里拿什么、他判完记在哪。这次三条任务分别给了小陈、老周、组长：小陈验业务行数与列，老周验权限与留痕，组长验真实使用。**三个人的视角不一样，合起来才是一张完整的证据。**

### 任务段的出口：三样东西

1. **每条任务都有完成标志**，且这个标志能被第三个人观察到。
2. **依赖写清了「为什么是它前面」**，不只是「在它前面」。
3. **每条任务都指派了一个具体的验收人**，不是「测试」这个抽象角色。

## 30.7 Testing：正常、异常、回归，以及四种证据

### 先写用例，再动手

测试段不是「做完之后点一遍」，它是一份在动手之前就写好的清单。写用例的过程，就是第二次检查需求的过程：你会被迫回答很多需求段没写清的问题。

```text
测试段（Testing）· 报名表导出 · v2
10 月 14 日写，10 月 15 日执行。
每条前面标它对应哪条验收条件。

正常
  用 1：管理员筛选第三组导出 → 28 行，全为第三组（验收 1）
  用 2：管理员不筛选导出 → 120 行，不是 20 行（验收 2）
  用 3：组长导出本组 → 只有本组（验收 4）
  用 4：组长把筛选选成「全部」再导出 → 仍只有本组（验收 4）

异常
  用 5：筛选一个没有记录的小组 → 提示，不生成文件（验收 6）
  用 6：造 2,001 条数据 → 提示收窄，不生成文件（验收 7）
  用 7：连点两次导出 → 第二次提示「正在生成」，
        不产生两个文件（设计边界）
  用 8：生成后等 31 分钟再点下载 → 提示过期，可重新导出（验收 9）
  用 9：小组名里有引号、斜杠、空格 → 文件名正常，
        文件能打开（异常输入）
  用 10：普通成员账号直接打开导出入口 → 不能完成导出（验收 5）

回归
  用 11：翻页、搜索、单条查看、报名提交、列表排序
         逐项打勾（验收 10）
  用 12：普通成员报名后，自己那条记录仍能看到；
         管理员列表仍能看到新记录（验收 10）
```

三类里最容易被省的是**回归**，因为它不产生「新功能可用」的成就感。但回归恰恰是变更类工作里最值钱的一类：**你改的是一个已经在运转的系统，最大的风险不是新功能不好用，是老功能被顺手弄坏了。**

### 测试设计在前，先暴露了一个需求空洞

这次写用例时，真的撞上了一个需求空洞。它发生在用 4：**组长把筛选选成「全部」，应该看到什么？**

需求 v1 只写了「组长只能导出自己组」，没有写「筛选选全部时怎么表现」。实现的人可以选三种做法：报错、自动收窄到本组、显示全部但导不出。三种都说得通，但它们是三种不同的产品行为。

```text
测试设计时发现的需求空洞：

  用例：组长把筛选选成「全部」，点导出。
  期望：只得到本组。
  但需求只写了「组长只能导自己组」，
  没写「筛选选全部时怎么表现」。

  处置：回改需求段，补一句
        「组长的筛选上限就是本组；选全部等同选本组」；
        再补验收 4；
        不补一条「允许两种情况」的测试。
```

这就是「测试设计在前」的实际作用：**它在系统还不存在的时候，就逼你把需求里的空洞找出来。** 这个空洞在写用例时被发现，改一句需求就行；在上线后被组长发现，就是一次投诉。另外两个空洞也顺带被补上了：超过 2,000 行是报错还是截断（回改设计，定「提示收窄，不生成文件」）；「文件能打开」算不算验收条件（不可判定，改写成「四列正确、中文不乱码、行数与页面一致」）。

### 结果不对，回改规格，不补测试

| 情况 | 这次长什么样 | 正确处置 | 错误处置 |
| --- | --- | --- | --- |
| **实现错了** | 规格写 28 行，组长选全部却导出了 120 行 | 改实现，重跑同一条用例 | 改验收条件，把 120 说成「也合理」 |
| **规格没写清** | 组长选全部时行为未定义，实现选了一种 | 回改需求段，写清，再补用例 | 在测试里加一条「允许两种情况」，把问题盖住 |
| **规格写错了** | 规格要求 28 行，但业务其实要 31 行 | 回改需求段，说明为什么改，同步给所有相关人 | 直接改测试，让它过 |

三种情况有一个共同的错误处置：**补一条测试，让不符合规格的结果变得合法。** 它不删需求，它让需求变得不重要。跑一次，加一条例外；再跑一次，再加一条。三个月后，测试全绿，但没有人知道系统到底该做什么。

> **测试是规格的证据，不是规格的橡皮擦。**

### 执行现场：两次不对，两次都改实现

10 月 15 日上午，第一次跑用例 4，失败了：组长把筛选选成「全部」，导出了 120 行。规格写的是「组长只能导自己组」，所以这是**实现错**：组别上限只加在了页面上，取数时没有按角色收窄。处置：改实现，重跑同一条用例，不改验收条件。

第二次跑，用例 4 过了，但审计对不上：文件 28 行，审计里写 120 行。需求段写的是「行数与文件一致」，所以这仍然是**实现错**：审计记的是筛选前的总数，不是最终生成的行数。处置：改实现，让审计与文件同源，重跑。

中间还有一次过度修正：阿哲第一次改的时候，把组长的导出入口整个去掉了，理由是「组长最容易越权」。结果用例 3 失败——组长本来就应该能导本组。这不是需求错，需求写的是「组长只能导出自己组」，不是「组长不能导出」。处置：恢复组长入口，保留取数时的本组上限，重跑用例 3 和 4。**需求段写边界，是为了让实现知道停在哪，不是让它把整条路封死。**

三次都没有改测试，也没有改需求。**如果规格是对的，就不要因为实现难而改规格；改实现。**

### 证据：四种形态，谁验证的

| 断言 | 证据形态 | 谁验 | 日期 |
| --- | --- | --- | --- |
| **行数对** | 页面显示 28 条，文件 28 行；截图带日期 | 小陈 | 10 月 15 日 |
| **列对** | 文件表头与首尾行：只有四列，无手机号、饮食备注、紧急联系人 | 小陈 + 老周 | 10 月 15 日 |
| **权限对** | 管理员、组长、普通成员三个账号各导一次，列与行范围的对照表 | 老周 | 10 月 15 日 |
| **动作发生过** | 审计里一条记录：账号、时间、筛选、行数、列、过期时间 | 老周 | 10 月 15 日 |
| **没弄坏别的** | 回归清单六项逐项打勾，写清谁打的、什么时候 | 小陈 | 10 月 15 日 |
| **变更前后** | v0 与 v1 的对照表：范围、列、去向、留痕、验收 | 小陈 | 10 月 16 日 |

四种证据里，第三种最容易被省略，也最容易被伪造。系统里写着「导出成功」不等于审计里有记录；审计里有记录，也不等于那次导出真的是这个人做的。**证据要指向原始系统，不指向模型或页面的措辞。**

### 一个不写代码的人，具体看什么

小陈看不懂实现，但她可以看三样东西，而且这三样比代码更接近验收。

**第一，前后对照表。** 同一个输入，改前和改后各跑一次。改前：筛选第三组，导出 120 行、七列。改后：筛选第三组，导出 28 行、四列。两个数字摆在一起，不需要懂代码也能判断。

**第二，样例数据。** 不用等真实名单，造一小份就够：

```text
样例数据（虚构，用于验收）

  第三组：3 条（含 1 条饮食备注、1 条紧急联系人）
  第一组：2 条
  操作：管理员筛选第三组 → 导出

  期望：文件 3 行，全部第三组，四列，无联系方式
  实际：____ 行
  出现别组：是 / 否
  出现联系方式：是 / 否
  文件能否打开：是 / 否
```

**第三，谁验证的。** 行数与列由小陈验，权限与留痕由老周验，真实使用由一名组长验。三个人各自签字，而不是一个人「总体看了一下」。**AI 可以帮你准备样例、整理对照表，但它不能当验收人；它说「我检查过」，只是另一段文本。**

### 抽查一条需求：验收 4 的链

抽验收 4：「组长把筛选选成『全部』再导出，文件里仍只有自己组的行。」

| 环节 | 对应的内容 | 如果缺了会怎样 |
| --- | --- | --- |
| **需求** | 权限段「组长只能导出自己组；选全部上限仍是本组」+ 验收 4 | 组长选全部时行为未定义 |
| **设计** | 风险 2「组长看到别组 → 组别上限放在取数这一步」 | 只在页面上隐藏，取数仍取全部 |
| **任务** | 任务 2「把组别上限放进取数」，完成标志就是这句话 | 做了页面隐藏，没人验取数 |
| **测试** | 用 3、用 4：组长导本组；组长选全部仍只导本组 | 只测管理员，权限没覆盖 |
| **证据** | 角色对照表：三个账号各导一次，行范围写清 | 只有一句「权限配好了」 |

这条链是完整的。完整的意思是：**每一环都能指出上一环的哪一句话，也能指出下一环的哪一个动作。** 如果抽一条需求，发现设计里没有对应、任务里没有对应、测试里没有对应、证据里也没有，那这条需求要么是多余的，要么是这次变更里最薄的一块。

## 30.8 返工现场：从「导出全部」到「导出当前筛选」

### 事故当天

10 月 10 日，小陈把 120 行、七列的文件发给了四个组长。她当时的想法很朴素：**「全部更全，组长自己挑。」** 这句话她后来在返工会上又说了一遍，老周听完，只问了一句：

> 如果组长把这份表转给组员，组员能看到别人的手机号吗？

小陈没说话。她没想过文件离开系统之后的事。当天下午，一个组长把文件转进了小组群。老周看到那张带手机号的表，问了「这个谁能点」。没有人答得上来。幸运的是，文件没有流出公司；但这是一次完整的越权路径，只是最后一步没有发生。**未发生不等于安全，它只说明这次运气好。**

### 把「谁的错」换成「哪一段空了」

返工会上，三个人没有争「是谁的错」。他们做了一张表，把现象翻译成段：

| 看到的现象 | 真正的原因 | 该补在哪一段 |
| --- | --- | --- |
| 导出 120 行 | 「当前筛选」没写死；「全部」成了默认 | 需求段：范围 |
| 文件里有手机号 | 字段级可见性没写；「方便联系」压过了「谁能看」 | 需求段：权限 |
| 组长能点导出 | 角色上限没写；入口也没按角色区分 | 需求段 + 设计段 |
| 文件发进了群 | 文件去向没写；没有留痕 | 需求段 + 设计段 |
| 没人能回答「谁能点」 | 没有验收条件 | 需求段：验收 |

这张表最重要的作用是：**它把一次「AI 做错了」的叙事，改成了一次「需求空了」的叙事。** 如果停在第一句，下一步一定是「换个更聪明的模型」或者「加一句提示词」；而这两个动作都改不了范围、列和权限。

### 返工会议的三个决定

```text
返工会议（10 月 12 日，虚构）的三个决定

决定 1：把「当前筛选」写进范围；
        把「导出全部」降级成筛选的一个值，不是默认。

决定 2：文件只保留四列；联系方式留在页面，不进文件；
        谁能看写到字段级。

决定 3：权限先于生成；每次导出留痕；
        没有留痕不算成功。
```

三个决定没有一个是「加功能」。恰恰相反，它们都在**减**：减掉默认的全部，减掉三列联系方式，减掉直接发群和共享盘。**返工不是把东西做得更多，是把范围收回来，再把证据补上。**

| 删掉 | 补上 |
| --- | --- |
| 「全部 120 条」的默认范围 | 当前筛选；组长上限本组 |
| 手机号、饮食备注、紧急联系人三列 | 字段级可见性表 |
| 直接发群、发共享盘 | 只本机下载，30 分钟内有效 |
| 「能导出」这一句验收 | 十条可判定的验收条件 |
| 没有记录 | 审计条目 + 角色对照表 |

改完之后的版本，看起来比 v0「能力更小」——它不能导全部，不能带手机号，不能直接发。但它才是对的，因为 v0 的「能力」里有三样本来就不该属于它。**一个功能的价值，不是它多能做多少，是它在该停的地方停住。**

### 两次修偏

**第一次修过头：组长不能导出了。** 10 月 14 日，阿哲按新需求改第一版。他读到「组长最容易越权」，于是把组长的导出入口整个去掉，只留管理员。10 月 15 日跑用例 3，失败：组长应该能导本组，但页面上没有入口。这不是需求错，需求写的是「组长只能导出自己组」，不是「组长不能导出」。处置：恢复组长入口，保留取数时的本组上限，重跑用例 3 和 4。**如果验收条件只写「组长不能看别组」，这次过度修正甚至可能通过；正是「组长能导本组」这半句，把它拦了下来。**

**第二次修偏：审计只记了行数。** 同一天下午，老周看审计，发现第一条记录只有「导出了 28 行」，没有筛选条件。他问：「如果组长先选全部、再选本组，我怎么知道他那次导的是什么？」需求段写的是「谁、什么时间、用了什么筛选、导出了多少行、包含哪几列、下载入口何时过期」。审计只做了其中两项，所以这是实现漏了需求，不是需求没写。处置：补上筛选、列和过期时间，重跑用例 1 和 4，确认审计与文件对得上。老周补了一句：「留痕不是给系统看的，是给事后的人看的。」

### 变更前后对照

```text
变更前后对照（10 月 16 日，虚构）

项目            变更前 v0                      变更后 v1
────────        ──────────────────────         ──────────────────────
按钮            导出                           导出当前筛选（28 条）
默认范围        全部 120 条                    当前筛选；组长上限本组
列              7 列，含手机号、饮食备注、      4 列，不含联系方式
                紧急联系人
文件去向        发群、共享盘                    仅本机下载，30 分钟有效
留痕            无                             账号/时间/筛选/行数/列/过期时间
验收            能打开                         10 条，逐条有证据
```

### 如果重来一次，最早能在哪一步拦住

答案是需求段，而且是最短的那一句：**非目标。** 如果在 10 月 9 日写下「不做导出全部」，小陈就不会把 120 行发给组长；如果写下「联系方式不进文件」，那份文件里就不会有手机号；如果写下「组长只能导本组」，入口就不会对四个组长一视同仁；如果写下「每次导出留痕」，老周当天就能查出是谁导的。

四句话都不长，但它们分别挡住了范围、字段、角色和追责。**非目标之所以比目标更重要，是因为目标告诉你往哪走，非目标告诉你哪里不能走；而事故几乎都发生在「不能走」的那一侧。**

## 30.9 边界三列账：四段规格能做什么、代价是什么、何时失效

| 能做什么 | 代价是什么 | 何时失效 |
| --- | --- | --- |
| 把一句口语变成可判定的承诺，让第三个人能独立验收 | 写验收要花时间，而且常常写到一半发现需求没想清 | 验收写成形容词（「好用」「流畅」）或实现细节（「用某个组件」） |
| 在动手前定下权限与字段范围，把越权挡在设计阶段 | 要有人拍板「谁能看」；拍板的人常常不在会议里 | 需求写了权限，运行时没配；或者上线后被人临时放开 |
| 让变更可追溯：每条需求能追到设计、任务、测试、证据 | 维护这条链要成本；小改动上四段，成本可能超过收益 | 链只在交付时对一次，之后没人更新；需求改了，下游没跟着改 |
| 让测试先于实现，提前暴露需求的空洞 | 前期会变慢，而且慢在「还没看到东西」的时候，最难被接受 | 团队把写用例当成流程动作，先做完再补用例，顺序反了 |
| 让不写代码的人也能验收，不必看懂实现 | 要有人愿意看证据；只看演示、只看截图，就会退化成观感 | 证据是模型自述、截图没有日期、角色对照缺失 |

这张表最该看的是最后一列。**四段规格的失效，几乎都不是因为它写得不够长，而是因为它被用在了不该用的阶段，或者被当成了文档而不是承诺。**

### 这个类比在这里失效

四段规格常被比作**装修的设计图、报价单、工序表和验收单**：先把要什么画出来，再报价，再排工序，最后按单验收。

这个类比在「先定后做」这一半成立，但它在三个地方不成立。**第一，装修的现场是同一个物理空间，你可以走进去看；软件变更的现场有一部分是数据与权限，图纸上看不见。** 你能看见一面墙有没有砌歪，但你看不见「组长账号能不能取到别组的数据」；后者要去原始系统里用角色对照才能看见。**第二，装修做错了可以拆了重来；软件的一次导出，文件已经离开系统。** 拆一面墙是钱和时间的问题；把 120 条手机号发进群，是收不回来的问题。**第三，装修的「好看」可以由业主一人拍板；软件变更的「谁能看」不能由提需求的人一人拍板。** 小陈可以决定名单发给哪个组长，但不能决定组长能不能看手机号；后者是数据边界，要老周拍。

### 它管不了什么，什么时候不该上四段

四段规格管得住「说清楚」，管不住运行时权限（需求写「不导出手机号」，不等于系统真的挡住了；挡住的是取数列白名单和账号权限）、代码质量、业务决定和组织责任。它能留下证据，不能替代签字（见第 17 篇、第 28 篇）。

也不是所有变更都值得写四段。判断标准不是「重要不重要」，是四条更具体的：

| 判据 | 这次变更 | 结论 |
| --- | --- | --- |
| **不可逆** | 文件发出去就收不回 | 命中 |
| **影响面** | 120 人的手机号、四个组长、场地与餐饮 | 命中 |
| **承诺对象** | 组长要按名单核对签到，场地要按人数备餐 | 命中 |
| **复用与追责** | 每次活动都用，出事要查「当初定的是什么」 | 命中 |

四条全中，所以这次必须上四段。反过来，如果只是你自己看的一次性统计，做完就扔、不碰别人的数据、没有第二个人按它做事，那么做一个能点的原型就够了。**判据看的是「这次变更」，不是「这个项目」；同一个报名系统里，改按钮颜色可以乱试，加导出必须写规格。**

## 30.10 术语考古：三个在变更里被用坏的词

### 变更（change）

| 栏 | 内容 |
| --- | --- |
| **最早出处** | 软件工程与配置管理领域的长期用语，**没有单一发明人**；它指对已交付系统的一次有意的修改，通常伴随范围、影响分析与回退安排。 |
| **原义** | 一次会改变系统行为的修改；重点在**改变了什么、影响了谁、能不能退**，不在「改了几行」。 |
| **现在被怎么用** | 常被缩成「改代码」「提个需求」，有时任何一次编辑都叫变更。于是「变更管理」被理解成填一张表，而不是判断影响面。 |
| **本文怎么用** | 一次会改变别人行为的承诺；必须带范围、权限、验收与证据。没有这四样，它只是「改了一下」，不是一次可验收的变更。 |

### 回归（regression）

| 栏 | 内容 |
| --- | --- |
| **最早出处** | 软件测试领域的长期实践，**没有统一规范**；具体最早由谁在何时提出，本文不指认。 |
| **原义** | 检查这次变更有没有弄坏**原来能用的行为**；重点在「原来」和「还能不能用」，不在「再测一遍所有东西」。 |
| **现在被怎么用** | 常被当成「全面回归」「再测一轮」，甚至把「回归」当成一个 bug 的名字。于是回归变成一项没有边界的体力活。 |
| **本文怎么用** | 一份列明「原来能用、现在还必须能用」的清单；每条有谁验、什么时候验。它挡的是「修好一个，弄坏三个」。 |

### 留痕 / 审计（audit trail）

| 栏 | 内容 |
| --- | --- |
| **最早出处** | 会计与信息安全领域的长期做法，**不是软件专有词**；它指按时间顺序留下「谁、什么时候、做了什么、结果如何」的记录。 |
| **原义** | 供事后核对的责任记录；重点在**能回答谁做了什么**，不在「有没有一条日志」。 |
| **现在被怎么用** | 常被等同于「日志」：系统里有记录，就叫有留痕。可一条「导出成功」的日志，回答不了「谁、导了哪些行、带了哪些列」。 |
| **本文怎么用** | 一条能回答账号、时间、筛选、行数、列、过期时间的记录，且与导出文件对得上；没有它，「已导出」只是一句页面提示。 |

三个词共同的毛病，是**把「一次动作」当成「一段文本」**：变更不是一句「改好了」，回归不是一句「再测一遍」，留痕不是一句「系统有日志」。它们都要落到可观察的结果上，才算数。

## 30.11 自检：一页速记与三道题

### 一页速记

| 你遇到的情况 | 一句话带走 |
| --- | --- |
| 一句「加个导出」 | 先问导出谁、导什么、谁能看、怎么算做到 |
| 想加「导出全部」 | 它不是更全，是把别人的数据也装进文件 |
| 想把联系方式带上 | 先问文件离开系统之后，谁还能看 |
| 想「顺手加一列」 | 先看需求里的非目标；加列要改需求，不是改页面 |
| 测试跑出 120 行，规格写 28 行 | 先分实现错、规格没写清、规格写错 |
| 结果不对 | 回改规格或改实现，不改测试 |
| 想证明改对了 | 前后对照 + 样例数据 + 谁验证的 |
| 验收 | 抽一条需求，顺着链找设计、任务、测试、证据 |
| 有人说「AI 已经检查过了」 | 让它给证据位置，你回原始系统核 |

**五句话带走**

1. 软件变更里，AI 最危险的不是不会做，是做得又快又全。
2. 非目标不是限制想象力，是把「顺手多做」挡在门外。
3. 权限要写到字段级，留痕要能对上文件；写在需求里，也要在运行时收住。
4. 测试设计在前；结果不对，回改规格，不补测试凑。
5. 不写代码的人验收，看的是承诺链和证据，不是实现。

### 三道自检

**第一题**：小陈说「导出全部更简单也更全，组长自己挑」。你用哪三句话反驳？

**第二题**：测试跑出 120 行，规格写的是 28 行，业务说「其实全部也行」。你改哪里？

**第三题**：抽查验收 4「组长选全部仍只导本组」，你能顺着链找到什么？如果有一环找不到，说明什么？

**第一题**：第一句问范围——「全」是筛选的一个值，不是默认；这次要的是当前筛选，组长不需要另外 92 行。第二句问权限——文件离开系统后，手机号会被谁看到；组长要联系组员，不等于他要拿到全组的手机号。第三句问非目标——需求里已经写了「不做导出全部」「联系方式不进文件」，这不是临时的拒绝，是开工前就定好的范围。三句话合起来，把「更全」从优点还原成了**范围与权限问题**。

**第二题**：先分三种情况。如果规格是 28 行、实现出了 120 行，那是实现错，改实现，重跑同一条用例。如果规格没写清「全部」时该怎样，回改需求段，补一句，再补验收和用例。如果业务真的改主意了，要的是全部，那就正式改需求段，写清为什么改、影响哪些列和角色，再让设计、任务、测试跟着改。**唯一不能做的是直接改测试让它过**——那会让「28 行」从一条承诺变成一句建议。业务说「其实也行」时，要追问的是：那原来那条还要不要？如果要，就是实现问题；如果不要，就正式改规格并留理由。

**第三题**：能找到五环。需求段：权限里写「组长只能导出自己组；选全部上限仍是本组」，验收 4 就是这句话。设计段：风险 2「组长看到别组 → 组别上限放在取数这一步」。任务段：任务 2「把组别上限放进取数」，完成标志就是「组长选全部仍只导本组」。测试段：用 3 和用 4，分别测组长导本组、组长选全部仍只导本组。证据：三个账号各导一次的角色对照表，写清列与行范围。**如果有一环找不到，那一环就是这次变更最薄的地方**：可能是需求多余，可能是设计漏了，可能是任务没切出来，也可能是测试没覆盖或证据没留。
