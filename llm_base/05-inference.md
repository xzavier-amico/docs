# 05 · 一次推理走到底：从读完输入到流式输出

> **状态**：已完成（初稿）· 深写样章，待审阅
>
> **本篇定位**：跟一条回答过五道关：材料组装、读入、选第一块、续写、显示。读完应该能解释：为什么读输入能并行，为什么第一块和第二块的依赖不同，为什么屏幕上的一个字不一定对应一个生成步骤。
>
> **读法**：§05.2 的分词是真实测量，§05.3–05.4 是可以手推的机制示意，§05.5 的时间账是带假设的算例。三类证据不混用。本篇以常见的仅解码器 Transformer 为例，不要求代码或公式推导。

## 05.1 引子：同一句通知，为什么会有三种「改错」？

资料上写着「由周六改为周日 14:00」，屏幕却显示「周六」。很容易把三种情况都怪到模型头上：

| 现场 | 真正不同的地方 | 该看什么证据 |
| --- | --- | --- |
| 聊天窗口挂了新附件，发给模型的却是旧摘录 | 错误发生在应用准备材料时，模型根本没见到新日期 | 最终输入里的摘录和来源，不只看附件名称 |
| 正确摘录已经送到，模型还是生成了「周六」 | 输入里有证据，不等于模型一定按证据选块 | 对照实际输入和输出；仅靠文字不能反推出内部概率 |
| 模型刚写到「周」，页面停住，刷新后才出现「周日」 | 也许模型已经继续生成，只是显示或传输滞后 | 服务收到首块的时间、页面显示的时间、最终结束状态 |

**本篇只回答一个问题：从我点发送，到屏幕上出现一个「日」，每一步究竟依赖什么？** 这里的任务只是写一句改期通知，不需要工具执行。若应用还要查资料、跑工具或审批，那些是本次模型调用外面的工作，见[第 10 篇](10-agent-loop.md)。

## 05.2 先验明正身：模型接到的不是你肉眼看见的字

想象应用给出任务和依据，模型开始写「市集改为……」。先不猜模型会喜欢哪些词，只测一件可复核的事：**用 `tiktoken` 0.12.0、`o200k_base` 对下面的孤立原文编码**。方括号是一块，`␠` 是普通空格。编码没有加入角色标记，也不是线上某次生成日志。

| 原文 | 实际切分 | Token ID |
| --- | --- | --- |
| `市集改为` | `[市] [集] [改] [为]` | 6190 · 12389 · 15346 · 6209 |
| `周日 14:00` | `[周] [日] [␠] [14] [:] [00]` | 17442 · 2292 · 220 · 1265 · 25 · 504 |
| `市集改为周日 14:00。` | `[市] [集] [改] [为] [周] [日] [␠] [14] [:] [00] [。]` | 6190 · 12389 · 15346 · 6209 · 17442 · 2292 · 220 · 1265 · 25 · 504 · 788 |
| `💡` | `[F0 9F 92] [A1]`（两段十六进制字节） | 31446 · 94 |

「周日」不是这一编码里的单块；「14」却是一块。更反直觉的是，灯泡的第一块只含前三个字节，**积齐两块才能还原这个字符**。于是，一次模型选块可以暂时不显示一个完整字符；反过来，界面一次显示「周日 14:00」，也不代表只生成了一块。不同分词器会切得不同，孤立文本重新编码出来的切分也不保证等于某次实际生成的 ID 序列。此处实测只回答「这个分词器怎样编码这几段原文」。分词训练及空格差异见[第 02 篇](02-tokenization.md)。

模型实际收到的输入是应用组装后的序列：用户请求、采用的资料、可能还有产品指令与消息边界。**屏幕里的聊天记录是档案，模型这次收到的序列才是工作材料。** 下面故意抓住这条序列，不把界面、模型和服务统称为「AI 在读」。

## 05.3 为什么第一步看起来是「一起读」，第二步却要等？

用四个示意位置看一个常见的因果注意力层。下图省略了一切不影响依赖关系的细节，每列是一个已给出的输入位置；`●` 表示那一行的位置在本层可看见该列。空格不是「模型不想看」，而是这里不允许它使用未来位置。

```text
                                  已给出的输入位置
                              ①任务  ②旧日期  ③改期  ④新日期
① 在处理「任务」                ●       —      —      —
② 在处理「旧日期」              ●       ●      —      —
③ 在处理「改期」                ●       ●      ●      —
④ 在处理「新日期」              ●       ●      ●      ●
                                                   ↓
                                  末位置表示 → 第一个输出位置的候选分数
```

这里「先后」有两层：**同一层中，所有已知输入位置的计算可以一起安排**，各位置只能用允许看到的上一层表示；**层与层之间仍有依赖**，后一层要等前一层产生结果。如果有并行工位，可以让四个工位同时按自己的可见范围做，但没有谁可以偷看一块尚未选出的输出。这叫 **Prefill（读入或预填充）**。正常未命中的情况下，输入越长往往要处理更多东西；能并行不意味着不花时间。

最后一个输入位置经过模型各层形成内部表示，再映射成词表里每个候选块的分数（常称 **logits**）。生成策略可调整或过滤候选，然后选择第一个输出块。**首块分数通常已经在 Prefill 的这次计算里得到**，不是 Prefill 完成后还必须再拿一个不存在的「第一个输出块」跑一次 Decode 才选得出来。

| 到这一步 | 已算出来什么 | 还没有什么 |
| --- | --- | --- |
| 组装与分词结束 | 输入 Token 序列 | 首个候选的分数、答案正文 |
| Prefill 结束 | 首步候选分数；启用 KV Cache 时留有前文中间结果 | 无法仅凭这些分数断言哪句是真实事实 |
| 选出第一个输出 | 下一步可用的一块前文 | 它还需在下一次模型前向处理中产生自己的 KV，若生成继续 |
| 选到结束标记或触及上限 | 模型停止继续生成 | 不证明交付已完整，更不代表任何外部动作已做 |

## 05.4 真正走两条分叉：为什么不是先写完再挑着显示？

以下的候选分布是**教学设定，不是模型实测**，数值不用于判断事实，块名只借用 §05.2 中的例子。从输入末尾「市集改为」开始，假设第一下都选到「周」。下一下可能走两条路：

```text
已有序列：… 市集改为 + [周]
                        ↓ 新一轮得到候选（省略其他候选）
                [日] 70%                [六] 25%       其他 5%
                   │                       │
     路 A：… 市集改为周日      路 B：… 市集改为周六
                   ↓                       ↓
     重新算 A 的下一步候选     重新算 B 的下一步候选
     可能继续写新时间          可能接出一整段旧安排
```

如果每次直接取最高，这一轮走 A；如果按这组分布抽取，B 也可能被选到。**重要的是：选过的块会进入下一步输入。** 不能把路径 A 计算出的下一步分数原封不动拿去给路径 B。早期一个错误不必然决定结局，但会改变后续条件；由此就能解释「一个事实错了，后面却越写越顺」为什么并不奇怪。需要否定旧日期时，第一步也可能写出「周六」再接「不是本次日期」；**单块高分既不是对整句的承诺，更不是置信度或出处**。

这也正好看清 [KV Cache](09-kv-cache.md) 的作用。没有缓存，简单实现可把更长的整段前文重新处理；有缓存，就复用**已经处理过的旧位置**在各注意力层里的 Key／Value，把刚选中的块处理一遍，得到下一步分数，再留它自己的中间结果。它不是直接把旧答案抄出来，**新位置仍要使用所能看见的旧位置做注意力计算**。两个分叉可以共享条件一致的共同前缀，却不能把不同后缀的中间结果混用。

一般的逐步解码中，同一条序列的后续输出有先后依赖；一轮内部可以并行算，服务也可以批量推进多条序列。投机解码等加速方法可以先提议多块再验证，**它是改变执行方式，不是让真正未来的输出无条件被提前知道**。工程里的「推理」指使用已训练模型；产品说的「推理模式」有时增加内部生成或使用不同流程，不一定等于界面上这些可见步骤。

## 05.5 算一笔时间账：两种「慢」怎么用一个反例分开？

下面全是**假设数字**。从点发送开始算，两次都交付同样长、同样合格的结果，模型交出首个输出后还有 40 个 Token。为了便于逐项相加，假设各阶段顺序执行、不重叠，且首个输出到手即可显示；真实系统可能重叠或缓冲。

| 从点击开始的阶段 | A：输入材料更长 | B：输出阶段更慢 |
| --- | ---: | ---: |
| 准备、网络和排队 | 0.4 s | 0.4 s |
| 读入到首个输出可取 | 1.6 s | 0.2 s |
| 首个输出后再生成 40 Token | 1.0 s（40 Token/s） | 3.0 s（约 13.3 Token/s） |
| 用户见首块 | **2.0 s** | **0.6 s** |
| 用户见完稿 | **3.0 s** | **3.6 s** |

现在用同一张表验三句常见判断：

1. **「B 首字更快，所以 B 交稿更快」**不成立：B 早 1.4 秒开口，却晚 0.6 秒完稿。首 Token、生成速度、任务总时长是三把尺子。
2. **「只要缩短输出，就能解决 A 开口慢」**不成立：把后续 40 Token 减到 20，按设定 A 的首块还是 2.0 秒，完稿变成 2.5 秒。若实际服务的预算或内部生成也跟着变动，需另测，不能套这个独立变量的结论。
3. **「输出改成流式，GPU 就算得更快」**也不能推出：在算例 A 中，改成等全文再显示，首段可从 2.0 秒变成 3.0 秒，模型计算并没有变。现实中协议缓冲、网络和渲染还能改变肉眼看到的首段时间。

如果你只能用聊天界面，做一个**能排除一种解释**的对照，比说「这个模型快」有用：固定模型和交付格式，一组用全附件，另一组用人工核准、保留同样必要信息的摘录；记录多次「首段出现」与「完整输出」时间，并检查输出长度和事实。只有首段明显变动时，先查附件处理、排队或读入，不宣称已经测到了 GPU 的 Prefill。若平台给服务端指标，再核对各自从哪里起算后对比。[第 08 篇](08-cpu-gpu-inference.md)还会区分个人速度与多人吞吐。

## 05.6 收口：只改一件事，先猜哪一步会变

| 操作 | 优先检查的阶段 | 这个操作解决不了什么 |
| --- | --- | --- |
| 删除三页失效旧公告，保留现行条款 | 材料组装、输入长度、读入；如命中前缀也会影响结果 | 不保证模型会正确引用，仍应与原文对照 |
| 只要一行通知，不要解释四段背景 | 后续生成量和完稿时间 | 不会让没传入的附件自动出现 |
| 应用不要攒完整句才显示 | 首段可见时间和更新节奏 | 不直接减少模型选块次数 |
| 同一天、同一模型，却持续写错日期 | 先核对最后送入的事实，再逐句验证用法 | 单凭降低温度，不能把旧事实变成新事实 |
| 输到半行停了 | 查长度上限、中断、取消或应用纪录 | 有结束标记也可能漏项；别把停止当成验收 |

**自检（含简答）**

1. **在图上，为什么 ① 不知道 ④，却能和 ④「一起算」？** 因为所有输入已经存在。同一层的各位置从前一层取自己允许看到的部分，不需要等 ④ 先产生本层结果；层间依赖仍在。
2. **刚选中「周」，缓存里一定已经写入了「周」的 Key 和 Value 吗？** 在图示的常见循环里，选中只是得到这个 ID；下一步处理它才会计算对应中间结果。若这时已停止，不必为了续写再处理它。
3. **记录显示首个输出 0.6 秒，页面 1.2 秒后才冒字，该把差值全算成 GPU 慢吗？** 不能。先核对测量起点；若相同，优先看传输、文本还原、应用缓冲与渲染。
4. **只看到「周日」这个答案，能说模型内部认为周日为真的概率是 70% 吗？** 不能。70% 只是教学候选；真实的 Token 选择分布也不是事实真值概率。

**一句话带走：** 读入之所以能一起做，是因为输入已知；续写之所以要接着来，是因为后文依赖刚选的块；屏幕何时露字，则是另一条时间线。排障先说是哪条时间线出了问题。
