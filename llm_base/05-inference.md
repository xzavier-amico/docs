# 05 · 一次推理走到底：从读完输入到流式输出

> **状态**：已完成（初稿）
>
> **本篇定位**：追踪常见文本生成模型的一次推理，分清读输入、选下一块文字和把文字显示出来。
>
> **读法**：先沿流程找「第一笔输出」在哪发生，再按候选条形图走三步；遇到卡顿时，可以查最后的边界表。

## 为什么先是一片空白，随后文字陆续出现？

市集的现行通知只有两段，你交给应用请它顺手整理报名清单和通知草稿。界面安静了一会儿，接着显示「市集改为」，又冒出「周日 14:00」。片刻后，它才补上雨天那句。你只看到了一条答案，背后却至少可以分成两段时间：**等可见输出出现**，以及**从开始输出到全部结束**。两段慢起来，原因未必一样。

虚构市集原定周六；现行 v2 为**周日 14:00**，雨天是否改室内待确认，旧 v1 已失效。任务仅整理报名清单及通知草稿，不发送。假设这一轮应用选中了 v2 的相关段落、核对所需报名字段和用户指令，送给一个常见的 Decoder-only 自回归模型（也就是往已知文字后面接下一块的模型）。

**本篇的真问题：为什么通常先等一会儿，然后答案一点一点冒出来？**

```text
应用：        组装本轮输入（必要时先读附件、找材料）
                           ↓
分词器：      文字 → 输入 Token 序列
                           ↓
模型 Prefill：处理已给出的输入，得到首步候选的分数
                           ↓
生成策略：    选第一个 Token ───→ 应用可把转成的文字陆续展示
                           ↓                     ↑
模型 Decode：用新增 Token 和已有上下文，得到下一步候选
                           ↓                     │
生成策略：    再选一个 Token ──────────────────┘
                           ↓
            达到结束标记、长度上限或其他停止条件 → 结束
```

这张图描的是一次典型调用。某些服务能分块处理输入、复用前缀计算或加速生成；产品还可能把多次调用和工具操作拼成一次对话。图不是对所有系统实现的计时承诺。

## 哪些步骤在读材料，哪些步骤在写答案？

**Prefill（预填充）**处理已经给出的输入。附件若需要取文字，常在这之前由应用处理；模型面对的是实际送进来的序列，不会因为对话框上显示了文件名就自动读完一整份表。常见系统可以在 Prefill 阶段并行处理很多已知的输入位置，最后得到首个输出位置的候选分数，也可把后续注意力会用到的中间结果留起来。并行读已给材料，不表示能看见未来生成的答案。

**Decode（逐步解码）**在读完已有输入后，接着处理新增的输出 Token、得到下一步候选。第一步的分数通常已经由 Prefill 给出；后续每一次选择都会成为下一步的前文。错选了「室内」，后面也许会顺着写出入口须知，听起来越完整，却越偏离原文。反过来，模型也可能写完一句后主动更正；已经展示过的文字仍不能自动当作通过校验的最终内容。

| 容易叫混的两件事 | 各表示什么 | 怎么从界面判断 |
| --- | --- | --- |
| 工程里的「推理」与产品的「推理模式」 | 前者是部署后使用模型算输出；后者常指某项让系统投入更多计算或采用特定模型／流程的功能 | 普通聊天也在做工程意义的推理；开关差异以产品说明为准 |
| 候选分布与采样 | 分布描述下一步各候选的相对机会；采样按分布抽取是选法之一，也可选当前最高的一项 | 自然的回答不意味着总选最高；不公开分布时，不能倒推每个候选的数值 |
| 选 Token 与流式展示 | 一个是生成过程，另一个是应用分批接收或展示结果的方式 | 界面可以合并多块文字一起显示，也可能一次性显示，不能逐闪数 Token |
| 结束生成与交付完成 | 达到停止条件时模型不再续写；交付还包括人工核对、补完或标待确认 | 末尾看起来像结束不等于表完整，更不等于已发送 |

## 手工练习：让候选真的影响下一步

在纸上写「现行通知：市集改为」，把三张卡盖在手边，每轮翻一张。下面的条长是**人为示意**，只画少量候选，不是模型实测；为了好练，每块用可读的词或短语代表一个教学 Token，和真实分词无关。

```text
已有：现行通知：市集改为
  周日    ██████     周六   ██      待定    █
  ↓ 假设选了「周日」
已有：现行通知：市集改为周日
  14:00   █████      下午   ███     。      █
  ↓ 假设选了「14:00」
已有：现行通知：市集改为周日 14:00
  。      █████      ，     ███     结束    █
```

1. 第一遍每轮圈最长的条，写到前文后。第三轮选「。」后并没有必然停止：后续还应有雨天状态等内容。若这时到了输出上限，就是写到一半，不是验收完毕。
2. 第二遍在第一轮故意圈「周六」。**不要**拿图上的第二行替它续写：那张卡假定前文是「周日」，前文变了，下一步候选需要重新由模型给出。手工练习只需写下「发生了前缀变化」，不用猜模型会怎么算。
3. 最后回看 v2：正确的时间不是因为条最长，而是有原文支持。补出「雨天是否改室内待确认」；给整理清单留位置，并在交付说明标「草稿，未发送」。

你也可以指定一个人写纸条，另一个人晚一拍再朗读：他有时一口气读两张，不代表写的人那一刻同时选了两张。这就是把生成和流式展示分开的好处。不过在真实服务里也有额外的生成加速机制，纸条类比不应用来推断后端运行细节。

## 把「慢」说具体，再动手

| 你看到的症状 | 可能慢在哪 | 可以做什么／有什么代价 |
| --- | --- | --- |
| 等了很久才看到第一个字 | 排队、附件读取、查询、处理长输入，或产品把第一批输出合并显示 | 比较短输入与原材料下的多次表现；只删重复材料，别删 v2 或雨天未决状态 |
| 首字出来快，写完特别慢 | 后续生成长、服务速度较慢，或中途做了额外工作 | 先让交付更明确、要求简洁；不能靠极短上限省掉名单末尾 |
| 表格写到半行就停 | 可能撞上输出上限、被取消或连接中断 | 查产品能否区分结束原因，核对完整行数，再选择重做或分段续写 |
| 输出很快但用了旧规则 | 问题很可能不在速度，而在送入的材料或核对 | 确认应用实际看到了 v2，再把原句与时间、雨天安排逐项验收 |

看用户体验，可分别记录「提出请求到看见首段」和「提出请求到最终结果」；如果系统还报告首 Token 时间和生成速度，先看定义再比较，不把它们直接和肉眼观察混为一谈。好用的速度指标也要带上通过率：一份秒出的错草稿，可能比一份慢两秒的正确稿多花好几轮人工返工。

例如，想知道附件读取是否值得优化，可以用同一模型、同一交付格式分别试两种材料：完整的市集交接包，以及经人工核准、包含同样关键事实和报名字段的简版。分别记首段和最终用时，抽查日期、雨天状态、清单行数和未发送状态，不把某一次恰逢服务繁忙的结果当结论。简版若总是更早出首段，但同样长的草稿生成用时接近，就有线索优先检查读入之前或读入阶段；它还不足以证明具体是哪一步最慢。若简版漏了必要字段，即使更快也不是好方案。

**速记：** 应用组装材料，分词器切片；Prefill 读已知输入、给首步候选；Decode 接着生成后续；流式只是怎样显示。停止不等于写全，写全不等于核实，核实草稿也不等于发送。

### 自检（含简答）

1. **为什么模型能并行处理输入，却不能直接看尚未生成的尾句？** 输入已知，各位置可按规则处理；未来输出还不在序列里，后续必须依赖已确定的前文。
2. **界面一次冒出「周日 14:00」，能据此说它是一个 Token 吗？** 不能。显示可以合并多个 Token；分词单位要用指定分词器来数。
3. **模型停在正确时间之后，但没写雨天和名单，能通过吗？** 不能。检查是否中断或触及长度上限，并补完整任务；正确一句不等于整个交付合格。
