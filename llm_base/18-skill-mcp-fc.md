# 18. 知识包、接入协议、调用格式：Skill、MCP 与 Function Calling

> **本篇定位**：把「能力」这个词拆成三段——知道怎么做、够得着谁、说得清要什么——并说明这三段各自装在哪一层、断了怎么查。

**Skill、MCP、Function Calling 解决的是三个不同的问题——「怎么做」「怎么接」「怎么说」。它们可以叠在一起，但不能互相替代。**

---

## 18.1 引子：三句话，三个宾语

虚构一次评审会。桌上摆着一个需求：把 10 月 25 日场地 B 的档期查回来。三个人分别汇报自己那一摊：

**产品先说**：「我们给助手装了一套差旅技能，报销流程、场地询价的标准步骤，它都懂。」

**工程接着说**：「我们接了 MCP，外部系统现在都能连。」

**供应商最后说**：「我们支持 Function Calling，什么工具都能调。」

主持人问了一句：「那它现在能不能把 B 场地的档期查回来？」

三个人都停了一下。因为三句话各答了一个问题，没有一句在回答「这一次能不能查出结果」。

这三句话都不假。但它们量的不是同一段东西：

- 第一句量的是**它读没读过一套流程**。读过了，它知道「先问档期、再问容纳人数、最后问报价」这个顺序。
- 第二句量的是**管道通没通**。通了，应用有能力去够到外面的系统。
- 第三句量的是**它会不会把请求说成一个能被程序接住的形状**。会了，应用才不用去猜它的自然语言。

注意这三个动词：**装、接、支持**。它们都是及物动词，听起来都在「增加能力」，可宾语完全不同——装的是**文档**，接的是**连接**，支持的是**格式**。日常语言把这三件事抹平了，于是「我们装了技能」听起来就像「我们有了这个能力」。

这就是本篇要拆的东西。听到这三个词，不要问「强不强」，先问一句：**它接的是哪一段？**

## 18.2 唯一真问题：为什么「装了技能」和「接了工具」不是一回事？

因为它们改变的是三份不同的东西，而「能不能办成」还取决于第四件、第五件它们都不管的事。

**反直觉命题**：三个都装上，系统的能力**不会自动变强**。它们只是把「知道怎么做」「够得着谁」「说得清要什么」这三段接上了；真正决定办不办得成的，是第四段「运行时放不放行」与第五段「回执对不对得上」，而这两段跟这三个词没有关系。

这个命题由 **P5（提议 / 执行）** 推出：模型只出主意，动手的是外面那圈系统。三个词分别落在这圈系统的不同位置——Skill 落在「放上桌的材料」，MCP 落在「系统能触达的边界」，Function Calling 落在「模型输出与系统输入之间的接口」。**没有一个是「模型变强了」。**

它的失效条件也要说清：当任务根本不需要外部动作（纯写作、纯分析、纯改写），这三样都不改变质量上限。这时装它们买到的是流程一致性，代价却是上下文、维护与攻击面。**在该省的地方装，是负收益。**

把「能力」这个词拆开，它至少是三种不同的能力：

| 说法 | 具体指什么 | 缺了它会长什么样 |
| --- | --- | --- |
| **读到的能力** | 这一轮里多了一段流程知识，模型知道标准做法 | 它可能用一套自创的、漏步骤的做法 |
| **够得着的能力** | 应用能连到某个外部系统，能发现它提供什么 | 流程再清楚，也没有东西可问 |
| **说得出的能力** | 模型能把「我要调谁、参数是什么」说成可解析的形状 | 应用只能靠猜自然语言，或者由人手工转达 |

三种都具备，才轮到「办成」。而「办成」还要过两关：**运行时放不放行**，以及**回执对不对得上**。前者是权限，后者是证据，都不在这三个词里。

### 三个追问，把三个词分开

遇到任何一个这类说法，用三个追问定位，比背定义有效：

| 追问 | Skill（技能） | MCP（协议） | Function Calling（调用格式） |
| --- | --- | --- | --- |
| 它改变了这一轮的哪份输入？ | 多了一段**前文**（步骤、检查项、示例） | 多了一组**可发现的远端能力**（也可能只是可读材料） | 多了一种**输出形状**的约束 |
| 它扩大了谁的边界？ | 谁的边界都没扩，只改了「它读到什么」 | 扩大了**应用的触达范围** | 扩大了**模型的表达方式** |
| 它坏了，换模型有用吗？ | 多半没用：问题在文档写法和加载 | 没用：问题在连接、发现、权限 | 有时有用：问题可能在守格式的能力 |

三个追问走完，混乱通常会消失一半。因为大多数争论不是「谁更强」，而是三个人各自盯着不同的那一段。

### 用四问再压一遍

按第 01 篇[那把尺子](01-ruler.md)：

1. **这句话是谁说的？** 「装了技能」通常是产品经理说的，「接了 MCP」是工程说的，「支持调用格式」是供应商说的。**没有一句是模型在承诺**——模型根本不知道你这周装了什么。
2. **它这一轮看见了什么？** 技能正文进没进这一轮？工具说明进没进这一轮？这两样都是**文本**，都可能没被放上桌。
3. **这是提议、事实，还是已经执行？** 三者叠加之后，模型给出的仍然只是**提议**；执行发生在外面。
4. **我拿什么独立验证？** 只能看回执，或者去原始系统查。看它自己说「已查询」，等于没查。

第 2 问和第 4 问，是这一篇里最常被跳过的两问。

## 18.3 一张图：三件事各自管一段

先把三段并排放。它们回答的是三个不同的问题，所以不能互相顶替：

```text
                同一个目标：把 10 月 25 日场地 B 的档期查回来
                                  │
        ┌─────────────────────────┼─────────────────────────┐
        │                         │                         │
   ①「怎么做」                ②「怎么接」                ③「怎么说」
      Skill                     MCP                Function Calling
   流程知识 / 能力包         应用 ↔ 服务端的协议          模型的调用意图
        │                         │                         │
   改变：这一轮多了一段前文   改变：应用够得着的边界    改变：意图的形状
   不改变：权限、连接、执行   不改变：模型会不会用      不改变：执行与回执
        │                         │                         │
        └──────────────► 三段都只是「前半程」 ◄──────────────┘
                                  │
                    ④ 运行时：这一次放不放行
                    ⑤ 执行：到底做没做成
                    ⑥ 回执：对不对得上原始系统
```

这张图最该记住的是下半部分：**三个词全都在「前半程」。** 它们决定「能不能开始办」，不决定「办成了没有」。

### 谁在做什么

| 角色 | 它决定什么 | 它决定不了什么 |
| --- | --- | --- |
| **人** | 目标、边界、哪些动作要签字、验收标准 | 具体措辞、服务端返回什么 |
| **应用** | 这一轮放什么上桌、允许列表里有哪些名字、把哪个回执放回去 | 模型会不会照做、服务端内部是否正确 |
| **模型** | 读到这些之后怎么续写、给出什么调用意图 | 有没有权限、动作执行没执行 |
| **服务端 / 工具** | 这个动作实际做了什么、返回什么 | 这个动作该不该做、结果该怎么解释 |

四者里，**只有「模型」这一行能靠换模型改善。** 其余三行换了模型都不动。这也是为什么「装了什么」和「办没办成」经常对不上——它们根本不在同一行。

### 三个词各自换了什么，没换什么

```text
      「怎么做」          「怎么接」          「怎么说」
        Skill               MCP                FC
          │                  │                  │
          ▼                  ▼                  ▼
     换了文档，          换了管道，         换了说法，
     流程会变；          能到的地方会变；   能被解析的概率会变；
     能做的事不变。      会做的事不变。     做过的事不变。
```

三列最后一句是重点。「能做的事不变」「会做的事不变」「做过的事不变」——这三句听起来像废话，但每一句都对应一类事故：以为换了文档就有了能力、以为通了管道就会用、以为说得出就做得到。

## 18.4 Skill：它解决「这件事的标准做法是什么」

### 它是什么

Skill（技能）是一份**可复用的流程知识或能力包**。常见形态是一份说明文档，加上若干辅助材料：检查清单、示例、模板、参考资料，有的还会带脚本。

它要回答的问题很具体：**这件事，我们公司/这个团队的标准做法是什么？** 先做什么、后做什么、哪一步必须核对、什么情况下要停下来问人。

举个和团建有关的例子。一份「场地询价」技能可能写着：

1. 先确认日期与人数口径（记录条数不等于人数，42 条要去重成 39 人）。
2. 再问档期，不要先问价格——档期不确定，价格没有意义。
3. 问容纳人数时，要问「同时容纳」还是「分批」，这两个数不一样。
4. 报价必须问清含不含午餐、场地、保险。
5. 对方口头确认不算确认，要有书面回复或合同。
6. 任何「先交定金锁档期」的动作，停下来问人。

这六条里没有一句是「模型变强了」。它们全是**前文**：读到了，它就按这个顺序想；读不到，它就按训练里更常见的顺序想——通常是先问价格，因为网上讲比价的内容更多。

### 按需加载：两级，不是一次性灌进去

技能通常不是整本塞进每一轮。它是两级加载：

```text
 技能目录（名称 + 一句话）        ← 一直在，但很短
        │  应用判断：这次要不要
        ▼
 技能正文（步骤、检查项、示例）    ← 按需加载，占工作台
        │  可能再引用
        ▼
 辅助材料（模板、参考、脚本）      ← 只有被引用时才进来
```

这个结构解释了三种「装了却没用上」：

- **目录里没有它**，或者名称与这次任务对不上，应用根本不会去取。
- **取了正文，但太长**，关键的第 5 条被挤到中间，模型没被推到注意力集中的位置（[第 05 篇](05-context-workbench.md)、[第 11 篇](11-compression.md)讲过的位置效应与压缩损失）。
- **正文读了，但它假设的能力不存在**。比如写着「致电场地确认」，而模型没有打电话的能力。

第三种最隐蔽，也最危险。因为**文档写得越细，越像「它应该能做到」**。一份好文档会把步骤写到「谁来做」这一层，而很多技能文档只写到「做什么」，读者（包括模型）就会默认「它自己会做」。

### 关键边界：加载进来也只是前文

这是本篇最容易被跳过的一句：**技能被加载，等于多了一段前文，不等于多了一分权限。**

技能里写「可以直接在系统里改名单」，不会让模型获得改名单的权限。技能里写「确认后即可发送」，也不会让发送这个动作变得可逆。权限在运行时，不在文档里（见第 17 篇）。

还有一层更细的：**技能包里带的脚本，和技能本身不是一回事。** 技能正文是文本，属于「读到的能力」；脚本被执行时，属于「执行」，要单独授权、单独留回执。把「这个技能带了一个脚本」当成「这个技能自带执行权」，是同类错误里最常见的一种。

### 一个类比，以及它在哪里失效

把 Skill 想成厨房里的**菜谱**：它告诉你先放什么、火候多大、什么时候起锅。同一个厨师，有菜谱和没菜谱，做出来的东西不一样。

但这个类比在**「谁来翻页」**这一步失效。菜谱不会自己翻到那一页；同理，技能不会自己跳进这一轮。**「按需加载」是应用做的一个选择动作**——它要先知道有这本菜谱、判断这次用得上、再决定把哪几页放上桌。所以「我们写了技能」和「这次用上了技能」之间，隔着一整套检索与预算分配。把它当成「写好了就自动生效」，等于假设书架会自己翻页。

第二个失效点在**结果**。菜谱不保证菜好吃，因为还取决于食材（材料）和厨师（模型）。技能也不保证任务办成，它只保证「如果照做，流程是对的」。流程对、材料错，结果照样错。

## 18.5 MCP：它解决「怎么把外部能力接进来」

### 它是什么

MCP 是一种**开放协议**，用来让应用连接外部的工具、资源与提示模板。它采用客户端 / 服务端结构：**应用侧发起连接**，服务端提供能力。2024 年公开发布，后续版本持续修订；具体版本号、条款与能力清单，以官方规范为准，本篇不引用具体条款。

它要回答的问题是：**一个应用，怎么用一套统一的约定，去接很多个外部系统？**

没有这类协议时，每接一个系统就要写一套专门的对接：接日历一套、接工单一套、接文档库又一套。系统有 M 个、应用有 N 个，接线数量会迅速变得难以维护。协议把这件事变成「每个系统实现一次服务端，每个应用实现一次客户端」。

但要说清楚：**这是工程收益，不是能力收益。** 接线变整齐了，不代表模型变聪明了，也不代表权限变宽松了。

### 它提供的不只是「工具」

这一点经常被忽略。MCP 服务端通常能提供三类东西，而它们落在完全不同的层：

| 服务端提供 | 到了这一轮是什么 | 落在哪一层 |
| --- | --- | --- |
| **可执行动作** | 一段工具说明 + 一个可被请求的名字 | 执行（要过运行时） |
| **可读资源** | 一份材料 | 材料（只是前文） |
| **提示模板** | 一段预设的前文 | 前文（只是前文） |

所以「接了 MCP」不等于「多了工具」。它可能只是多了几份能读的材料，或者几个能套用的模板。**只有第一类涉及执行**，也才需要问权限。

### 「接上了」不是一步，是七道关口

这是拆掉「接了 MCP，模型就会用」这个误解的关键。从「连上」到「办成」，中间隔着七道可以各自失败的关口：

```text
 连接建立 ──▶ 能力发现 ──▶ 说明上桌 ──▶ 模型选择 ──▶ 运行时放行 ──▶ 执行 ──▶ 回执
    │            │            │            │            │          │        │
 身份通过     知道有什么    进了这一轮    给对意图    权限/参数    真做了   能核对
```

- **连接建立**：应用能不能连上这个服务端，身份认不认。
- **能力发现**：服务端说自己有哪些动作、哪些资源。注意，这是**服务端的自述**。
- **说明上桌**：应用决定把哪些说明放进这一轮。没放进去，模型就不知道有这个工具——它不会「感知」到远端存在什么。
- **模型选择**：说明够不够清楚、有没有重名、模型有没有选错。这一段属于模型与格式，见第 14 篇。
- **运行时放行**：这一次、这个用户、这组参数，允不允许。
- **执行**：服务端真的做了没有；可能成功、失败、部分成功或超时。
- **回执**：返回的是它的说法，不是世界的事实，要能对上原始系统（见第 16 篇）。

七道关口里，只有第四道跟「模型强不强」有关。前三道是应用与连接的事，后三道是运行时、执行与证据的事。**大多数「接了却不好用」的现场，坏的都不是第四道。**

### 关键边界：协议本身不授予权限

这句话要拆成三层，因为「授权」在三个地方都出现，含义完全不同：

| 哪一层 | 它在确认什么 | 它**不**确认什么 |
| --- | --- | --- |
| 连接鉴权 | 这个客户端是不是它自称的那个 | 这个用户能不能做这个动作 |
| 工具声明 | 这个动作需要什么范围 | 这一次是否满足这个范围 |
| 运行时校验 | 这一次、这个人、这组参数是否放行 | 这个动作该不该由人来签字 |

三层串起来才叫「有权做」。只过第一层就当已经授权，是越权最常见的那条路：**连接成功被当成了动作许可。** 详见第 17 篇。

还有一条更细的：模型给出的工具名，是**模型说的**。应用必须拿这个名字去允许列表里查，确认它指向一个真实存在、且这次允许的服务端。否则模型可以「发明」一个听起来合理的名字，而一套没有校验的接线会认真地去找它。名字是提议，允许列表才是事实。

### 一个类比，以及它在哪里失效

把 MCP 想成**插座标准**：形状统一了，任何符合标准的电器都能插。这个类比在「接线变整齐」这一层很准。

它有三处失效：

1. **插上不等于通电。** 协议规定形状与握手，不提供电力。电力是权限，在运行时。
2. **通电不等于电器知道有电。** 服务端在那儿，不代表模型知道它在那儿；工具说明得被放上桌。
3. **形状对不等于电压对。** 协议统一了「怎么问」，没有统一「每个服务端怎么答、错了怎么报、哪些参数算越界」。这些语义差异，各家实现仍然不同。

所以「符合协议」能保证的是**能对接**，保证不了**能办成**，更保证不了**办得对**。

## 18.6 Function Calling：它解决「模型怎么表达这个意图」

### 它是什么

Function Calling（调用格式）是模型的一种输出约定：模型不说「麻烦帮我查一下档期」这种自然语言，而是给出一段结构化的意图——**我想调用哪个工具，参数是什么。**

它要回答的问题是：**模型怎么把「我想做什么」说成一个程序能稳定接住的形状？**

注意它的位置：这是**输出侧**的约定，属于[第 14 篇](14-structured-output.md)讲过的格式约束，只是压力更大。普通的格式约束错了，最多是解析失败；调用意图错了，可能触发一次真实动作。

它之所以必要，是因为自然语言太难稳定解析。同一句「查一下 B 场地」，可以有一百种说法，程序猜不准；换成固定字段的意图，应用才敢往下走。

### 三个失败层次，修法完全不同

| 层次 | 长什么样 | 该改哪里 |
| --- | --- | --- |
| **形状错** | 输出解析不了，字段缺、类型不对 | 输出约定、校验、重试策略 |
| **选错** | 该查档期，它去查了天气；两个工具名字很像，选混了 | 工具说明的命名与描述、候选数量 |
| **参数错** | 日期写成 10 月 18 日（那是作废的 v1）；人数写成 42（那是记录条数） | 材料与口径，不是格式 |

第三层最值得警惕，因为它**穿着格式正确的外衣**。一段意图可以完全合法、字段齐全、解析通过，然后带着一个作废的日期出门。第 14 篇那句话在这里同样成立：格式对了，不等于内容对了。

### 关键边界：意图不等于执行

这是三个词里最容易被高估的一个。模型给出调用意图，只证明了一件事：**它能按约定表达。** 它没有证明：

- 这个工具真的存在（名字可能是编的）；
- 这次调用被允许（权限在运行时）；
- 参数在业务上成立（10 月 18 日不是有效日期）；
- 动作真的执行了（执行在服务端）；
- 执行结果是它说的那样（回执要核对）。

还有一层常被忽略：**意图可以被拒绝，而模型不会自动知道。** 运行时因为权限、参数越界、预算耗尽或重复提交而拒绝，这个「拒绝」必须作为一条观察结果重新放回桌上，模型才可能改。否则它会继续按「我已经查过了」往下写——这是第 15 篇那个循环里最容易断的一环。

所以「支持 Function Calling」这句话，准确的含义是：**这个模型能按约定输出调用意图。** 它不保证工具有实现，不保证执行有保护，也不保证结果可信。

## 18.7 叠加：一条完整链路长什么样

三段接起来，才是能办事的样子。把前面所有角色放进同一张图：

```text
 人          应用                          模型              服务端 / 工具
 │            │                             │                    │
 │ 目标       │                             │                    │
 │ 边界 ─────▶│                             │                    │
 │            │ ① 组装这一轮：              │                    │
 │            │    系统指令 + 技能正文       │                    │
 │            │    + 工具说明 + 材料 ───────▶│                    │
 │            │                             │ ② 续写：给出        │
 │            │◀──── 调用意图（谁、什么参数）│    结构化意图       │
 │            │ ③ 查允许列表：这个名字       │                    │
 │            │    在不在、指向哪个服务端 ───┼───────────────────▶│
 │            │ ④ 运行时校验：身份/权限/      │                    │
 │            │    参数/预算/是否重复         │                    │
 │            │ ⑤ 放行 ─────────────────────┼───────────────────▶│ 执行
 │            │◀────────────────────────────┼── ⑥ 回执 / 错误 / 超时
 │            │ ⑦ 把结果作为观察放回桌上 ───▶│                    │
 │            │                             │ 决定下一步或停下    │
```

七步，每一步都能单独断。断在哪一步，决定了你该找谁，也决定了换模型有没有用：

| 步 | 断了长什么样 | 归哪一层 | 换模型有用吗 |
| --- | --- | --- | --- |
| ① 组装 | 技能没进这一轮；工具说明被预算挤掉 | 应用 | 没用 |
| ② 续写 | 意图形状不合法；选错工具 | 模型 + 格式约定 | 有时有用 |
| ③ 查名字 | 名字不在允许列表；指向了不该连的服务端 | 应用 | 没用 |
| ④ 校验 | 权限不足、参数越界、超预算、重复提交 | 运行时 | 没用 |
| ⑤ 执行 | 服务端报错、超时、部分成功 | 服务端 / 网络 | 没用 |
| ⑥ 回执 | 回执丢了；回执说的是「已受理」不是「已完成」 | 应用 / 服务端 | 没用 |
| ⑦ 放回 | 结果没被放回桌上；模型不知道被拒绝 | 应用 | 没用 |

七行里只有一行跟模型有关。这不是说模型不重要，而是说：**三段叠起来之后，失败面反而变大了，而新增的失败面几乎都不在模型层。**

### 叠加之后，多出来的是「接口」，不是「保证」

三段接齐，你会得到一条完整的通路：技能告诉它流程，模型给出意图，应用经协议找到服务端，运行时校验，执行，回执回来。

但这条通路**没有一处自带保证**：

- 技能可能过期（三个月改一次的规则，写进技能就会腐化，见[第 07 篇](07-weights-vs-carried.md)）。
- 协议可能对不上（语义差异、错误码差异）。
- 意图可能被误读（参数名相近、单位不同）。
- 回执可能不可信（服务端说受理了，不代表做完了）。

**保证来自闸门，不来自接线。** 闸门是权限、校验、幂等、回执核对、人审——它们分别在第 16、17 篇。接线只负责「让这条路能走」。

## 18.8 混淆对照表：四个等式，逐个拆

这一节把最常见的四个等式摆出来。它们的共同形状是：**用「存在」冒充「生效」。**

| 说法 | 它其实证明了什么 | 它没证明什么 | 当场怎么验 |
| --- | --- | --- | --- |
| 「我们装了技能」 | 这份流程文档存在，且可被加载 | 这次加载了没有；模型照做了没有；有没有权限 | 问一个只有该技能才有的细节，看它答不答得出；再问「这一步谁来做」 |
| 「我们接了 MCP」 | 应用与某个服务端建立了连接，能发现能力 | 工具说明进没进这一轮；模型会不会选；这次允不允许 | 让它说「你现在能用哪些工具」，对照允许列表；再看一次真实调用的回执 |
| 「我们支持 Function Calling」 | 模型能按约定输出调用意图 | 工具有没有实现；执行有没有保护；参数对不对 | 让它对一个**不存在**的工具提要求，看它是编一个名字，还是说做不到 |
| 「工具都有了，它自然会用」 | 工具在允许列表里 | 说明够不够清楚；名字会不会混；模型选了没有 | 把两个名字相近的工具放一起，看它选哪个、理由是什么 |

### 为什么这四个等式特别顽固

有三个原因，都不是技术原因：

1. **界面把它们放在同一个地方。** 很多产品把技能、连接、工具放在同一个「能力」面板里，视觉上就是一排开关。用户自然以为它们是一类东西。
2. **销售话术共用三个动词。** 装、接、支持——都能接「能力」这个词，于是听起来等价。
3. **「能力」这个词本身不指层。** 说「它有这个能力」，可以指它知道怎么做，也可以指它够得着，还可以指它说得出。三种意思共用一个词，讨论就永远对不齐。

所以拆解的办法不是争论定义，而是**把宾语补出来**：「装了」什么？「接了」哪里？「支持」哪种输出？宾语一补，四个等式自动散架。

### 还有两个不常被提的混淆

- **「技能」和「提示词」不是一回事，但边界很软。** 一段写得很长的提示词，和一份技能文档，在模型看来都是前文。区别在组织方式：技能有目录、有按需加载、有辅助材料、可复用；提示词通常跟着某次任务走。**但两者的作用机制相同**——都只改「读到什么」。所以「我们把提示词整理成技能了」这句话，不带来任何权限或执行上的变化。
- **「连接器」「插件」「工具」可能指同一个东西。** 不同产品用不同名字指同一层能力，也可能是同一个名字指不同层。**不要按名字推断，要看这次请求里到底有什么。**

## 18.9 边界：能做什么、代价是什么、何时失效

| 对象 | 能做什么 | 代价是什么 | 何时失效 |
| --- | --- | --- | --- |
| **Skill** | 把标准做法固定下来；减少步骤遗漏；让不同人得到同一套流程 | 占工作台；写得越细越容易过期；维护要人；可能诱导「它应该能做到」的错觉 | 没被加载；描述与任务不匹配；正文太长被挤掉；文档假设了不存在的能力；文档里的规则已作废 |
| **MCP** | 用统一约定接多个外部系统；让能力可发现、可替换 | 多一层要维护的服务端；多一处鉴权面；语义与错误处理各家不同 | 连接不上；能力没被发现；说明没上桌；名字不在允许列表；服务端语义与预期不符 |
| **Function Calling** | 把意图说成可解析的形状；让应用能可靠接住 | 格式压力会诱发「为填满而编参数」；工具一多就容易选错 | 模型不守约定；工具说明含糊或重名；参数口径错；把意图当成执行 |
| **三者叠加** | 一条从「知道怎么做」到「拿到回执」的完整通路 | 失败面变大；排查要分段；成本与攻击面都增加 | 任一环断；或者七步都通、但没人核对回执 |
| **三者都不做** | 成本最低，边界最清楚；纯文本任务足够 | 复杂流程靠人转达，易漏步骤 | 任务需要外部实时数据，或需要真实动作 |

### 三条边界，比表格更重要

**第一，这些词都没有统一的行业标准。** 「技能」在不同产品里边界不同，有的只指文档，有的含脚本与资源；「工具」有时指协议层的动作，有时指一个封装好的外部服务；同一个「调用格式」，各家的字段约定、错误表达、并行规则都不一样。**任何「业界标准就是这样」的说法，都要先问是哪一家的哪一版。**

**第二，不要按名字推断能力。** 名字只说明它想解决哪一类问题，不说明它这次解决了。一个叫「智能日程」的技能，可能只是一份写得很好的提示词；一个叫「全自动接入」的连接，可能只读不写。

**第三，看「这次请求里到底有什么」。** 这是唯一可靠的判据，也是[第 09 篇](09-whats-in-the-request.md)那张清单的用法：

```text
 看三样东西：
   ① 这一轮的输入清单里，有没有技能正文、有没有工具说明？
   ② 允许列表里，有没有那个名字？它指向哪个服务端？
   ③ 回执里，写的是「已受理」还是「已完成」？能不能对上原始系统？
```

三样都看到了，你才知道「能力」是真的到了这一轮，还是只到了宣传页上。

### 成本这一栏为什么不能省

三段都要付钱，而且付的不是同一种钱：

- 技能正文进上下文，付的是 **Token 与注意力**——它挤占的正是材料的位置。
- 连接与发现，付的是 **维护与鉴权**——多一个服务端，就多一处要盯着的东西。
- 调用意图，付的是 **格式压力与选错概率**——工具越多，选错的组合越多。

所以「全都装上」很少是最优解。一个只写周报的任务，装十个工具只会让它在十个错误选项里挑。**装什么，取决于这次任务真的需要哪一段。**

## 18.10 反例与正例：同一个「查档期」，两种做法

同一个需求：确认 10 月 25 日场地 B 有没有档期。两种做法都能做，但它们的失败点完全不同。

```text
 甲（写清步骤）  目标 ─▶ 技能里的流程 ─▶ 模型照步骤写 ─▶ 人拿结果去核
 乙（接档期）    目标 ─▶ 模型给意图 ─▶ 应用查服务端 ─▶ 执行 ─▶ 回执 ─▶ 人核回执
```

### 反例：把「装了技能」当成「能办事」

虚构一个现场。团队给助手装了一份「场地询价」技能，里面写着「确认档期后，记录对接人姓名与时间」。上线第一周，助手输出了一段很漂亮的回复：

> 「已致电场地 B，对接人确认 10 月 25 日有档期，可容纳 40 人。」

这段话每一句都符合技能文档的格式。问题是：**它没有打电话的能力。** 它是照着文档的句式，把「应该发生的事」写成了「已经发生的事」。

这是一次典型的**文档承诺被当成系统承诺**。技能只提供前文，前文写得越像流程，越容易被续写成「流程已完成」的语气——第 02 篇讲过，模型最擅长的就是让文本看起来合理。

### 正例：把三段分开验收

改对的做法不是把技能写得更严，而是**分段验收**：

| 段 | 验收什么 | 怎么验 |
| --- | --- | --- |
| 技能 | 步骤对不对、有没有假设不存在的能力 | 逐条问「这一步谁来做」，把模型做不到的步骤标成「必须人做」 |
| 连接 | 服务端能不能被找到、返回什么 | 单独调一次只读查询，看返回的是数据还是一段话 |
| 意图 | 形状对不对、参数口径对不对 | 用一个已知答案的日期试，看它填的是 10 月 25 日还是 10 月 18 日 |
| 运行时 | 这次允不允许 | 故意让它做一次越权动作，看是拒绝还是照做 |
| 回执 | 对不对得上原始系统 | 去档期系统里看，而不是问它 |

改完之后，那段回复会变成两种可能：要么是「查询结果：10 月 25 日可预订，来源：档期系统，时间戳……」，要么是「我没有查询档期的能力，需要你确认」。**两种都比一段漂亮的假回执好。**

### 这里最该记住的一句

**三者叠加不产生可靠性。** 它只是把路修通了。可靠性来自路上的闸门：允许列表、参数校验、权限、幂等、回执核对、人审。修路和设闸是两件事，不能因为路修好了，就假设闸也装好了。

## 18.11 你可以自己做的检验

十分钟，不用写任何东西，只需要一个能对话的助手和一张纸。

**任务**：让它确认「10 月 25 日场地 B 有没有档期」。

**做法甲（技能式）**：在提示里写清步骤——先确认日期与人数口径，再问档期，再问容纳人数，最后问报价；并注明「你没有打电话的能力，凡是你没查到的，写未确认」。

**做法乙（接入式）**：如果你的产品支持接外部能力，接一个只读的档期查询，然后同样问这一句。

两种都做，或者只做甲，然后填这张表：

| 观察项 | 甲（写清步骤） | 乙（接了查询） |
| --- | --- | --- |
| 它给出的答案是数据，还是叙述 |  |  |
| 它有没有声称做了自己做不到的事 |  |  |
| 失败时它停在哪一步 |  |  |
| 你能不能独立核对这个答案 |  |  |

**判据**：

- 甲的能力上限，是「它会不会照步骤做」；乙的能力上限，是「连接通不通、说明对不对、权限给没给」。**两者的失败点不重叠。** 如果甲失败了你去换模型，可能有用；如果乙失败了你去换模型，基本没用。
- 如果乙在没有真正接通的情况下也给出了一个像模像样的档期，那说明它在编——而你以为它查了。这是最该被抓到的一种「假成功」。
- 如果甲老老实实写了「我没有查询能力，以下是需要你确认的清单」，那它比一个假装查到的乙更可信。

**这个检验能推翻什么**：如果你原本相信「装了技能/接了工具，它就自动会办这件事」，那么甲、乙里总有一边会让你看到断点。看到断点，结论就得改。

## 18.12 术语考古：三个被混着用的词

术语考古不是考据癖。它解决一个很实际的问题：**两个人说同一个词，指的可能不是同一层。** 一个人说「我们有技能」，可能指一份文档；另一个人听成「它能执行这套流程」。会开两小时，其实在争两件事。

| 词 | 最早出处 | 原义 | 现在被怎么用 | 本文怎么用 |
| --- | --- | --- | --- | --- |
| **Skill（技能）** | 产品与社区用语，没有单一出处，也没有统一规范；近两年多款产品用它指「可复用的流程知识 + 辅助材料」 | 强调「一套可复用的做法」，介于文档与能力包之间 | 有时指一份提示词模板，有时指带脚本的完整能力包，有时只是产品面板上的一个开关 | 指**可复用的流程知识或能力包**，按需加载；它只改变这一轮的前文，不带来权限与执行 |
| **MCP** | 2024 年公开发布的开放协议，采用客户端 / 服务端结构；具体版本与条款以官方规范为准 | 让应用用统一约定连接外部的工具、资源与提示模板 | 常被当成「工具市场」或「万能接口」，也有人用它指任何外部接入 | 指**接入协议**，解决「怎么接」；协议只统一形状与握手，**不授予权限**，也不保证语义一致 |
| **Function Calling（调用格式）** | 由模型 / 平台厂商在产品中引入的机制名称，各家叫法不同（工具调用、tool use 等），没有统一规范文本 | 模型输出结构化的「调用谁、参数是什么」的意图 | 常被理解成「模型能操作工具」，甚至被当成「已经执行」 | 指**调用意图的表达格式**；它属于输出约定，**意图不等于执行**，也不保证参数在业务上成立 |

### 三个词之外，还有一层命名混乱

同一个东西可能有三个名字，同一个名字也可能指三个东西：

- 「插件」「连接器」「工具」「扩展」——可能都指接入层，也可能其中一个只是提示词包。
- 「技能」「模板」「工作流」——可能都指前文，但工作流里可能含固定编排，那部分属于应用逻辑，不是模型。
- 「支持调用」「支持工具」「支持联网」——三种说法都可能只表示「能输出意图」，不表示「能执行」。

所以遇到新名字，别问「它是什么」，问「它落在哪一层」：改的是前文、连接，还是输出形状？三问下去，名字就不重要了。

## 18.13 一页速记

| 你听到的话 | 它其实在说 | 你该追问 |
| --- | --- | --- |
| 「装了技能」 | 有一份流程文档可被加载 | 这次加载了吗？它假设的能力存在吗？ |
| 「接了 MCP」 | 应用能连到某个服务端 | 工具说明上桌了吗？名字在允许列表里吗？ |
| 「支持调用格式」 | 模型能按约定输出意图 | 工具有实现吗？执行有保护吗？参数谁校验？ |
| 「它说它查过了」 | 它生成了一段像回执的话 | 回执在哪？对不对得上原始系统？ |
| 「三个都上了，应该没问题」 | 路修通了 | 闸门装了吗？谁签字？ |

**五句话带走**

1. Skill 管「怎么做」，MCP 管「怎么接」，Function Calling 管「怎么说」；三段可以叠，不能互替。
2. 技能加载进来只是前文，不给权限；协议接进来只是通路，不授权；意图说出来只是提议，不等于执行。
3. 「接了」不是一步，是七道：连接、发现、上桌、选择、放行、执行、回执。大多数失败不在「选择」那一道。
4. 七步链路里只有一步跟模型有关；所以「换模型」修不了大多数「接了却不好用」。
5. 叠加不产生可靠性；可靠性来自闸门与回执，不来自接线。

**三道自检**

1. 同事说：「我们把这个流程写成技能了，以后它就能自动办这套事。」这句话缺了哪一段？你会怎么验？
2. 一个产品同时宣传「支持 MCP」和「支持 Function Calling」，但你说「查一下明天天气」，它答「好的，已为你查询：晴，26 度」。你应该先怀疑什么？
3. 三个人争论「到底要不要上 MCP」。甲说能提效，乙说会增加风险，丙说先写技能就够。他们的分歧其实是哪三个问题？

1. 缺的是「连接」与「执行」两段。写成技能只说明流程被固定成了前文，不说明它能触达任何外部系统，也不说明有人给了它执行权。验法：挑技能里最像「动作」的一条（例如「致电确认」），问它「这一步谁来做」；再让它真做一次只读查询，看返回的是数据还是一段叙述。**如果它把「应该发生」写成「已经发生」，那缺的不是文档，是执行与回执。**

2. 先怀疑「假成功」，而不是先怀疑格式。它给出的是一个完整的天气结论，但没有说明来源、时间、地点——这更像一段续写，而不是一次查询的返回。验法：问它「你用的是哪个工具、返回的原始结果是什么、查询的是哪个城市」；再问一个它不可能知道的细节（例如「那明天下午三点呢」）。**如果它每次都答得很顺、从不承认查不到，那「支持」两个字只落在格式层。**

3. 三个问题分别是：**「怎么做」**（丙说的，技能够不够）、**「怎么接」**（甲说的，通路值不值得接）、**「接进来之后谁放行、出了事谁核」**（乙说的，风险与回执）。三个人其实没有对立，他们在说三段。正确的开法不是投票，而是先问「这次任务缺的是哪一段」——缺流程就写技能，缺实时数据才接协议，缺证据就补回执。**先定位，再决定要不要上。**
