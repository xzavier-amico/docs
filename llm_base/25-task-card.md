## 25.1 引子：同一句需求，两种交付结果

**虚构场景**，沿用团建那套材料。10 月 8 日晚上，两个人都对 AI 说了同一句话：

> 帮我写个团建通知。

第二天早上，两份东西摆在桌上。

```text
同一条需求：帮我写个团建通知

A 的交付                              B 的交付
──────────────                       ──────────────
一段 300 字通知                       一段 180 字草稿
日期 10 月 25 日  ✓                   日期 10 月 25 日  ✓
人数 42  ✗                            人数 39  ✓（注明 42 是记录条数）
雨天「改室内多功能厅」  ✗              雨天「待确认」  ✓
「已同步至群公告」  ✗                  「本稿未群发」  ✓
读起来像成品                          读起来像半成品
一周后三处要返工                      发出前核出三处
```

两份都叫「写完了」。A 的那份甚至更像成品：段落完整、语气热络、结尾还有一句让人放心的「已同步至群公告」。B 的那份短、干、还带着一张表和三条「没定」的事，交出去的时候像个没做完的作业。

但一周后，A 的那份被转发进群，有人问「到底多少人来」，有人按「室内多功能厅」去问场地，才发现根本没有这个确认；B 的那份在发出前被核了三处：42 只是记录条数、室内只是待确认、群公告并没有同步。三处都在卡上被拦下。

差别不在模型，也不在谁更会写提示词。**A 给的是一个句子，B 给的是一张卡。**

这里有一个反直觉的判断，也是本篇的起点：

> **看起来更完整的交付，往往更不可验收。** 因为它把「没定的」写成了「定了的」，把「没做的」写成了「做了的」；而完整度恰好掩盖了这两件事。

完整度是文本的属性，可验收性是结构的属性。一段文字可以又长又顺又自信，却没有任何一处能被人拿原文、回执或对照去核。反过来，一份短、干、留着空格的草稿，可能每一句都能指到出处。

所以这一篇要区分两个东西：

- **任务卡**：人在开工前写给自己和验收人的一张纸。它记录这次要什么、凭什么、不许什么、交什么、怎么算过。
- **提示词**：这一轮真正送进请求的那段文字。它只是任务卡的一部分，而且通常不是最重要的那部分。

任务卡里关于验收的那一段，多数时候**不进请求**。它留在人手里，用来判交付。这一点很关键：如果把验收条件也写成「请你确保自己符合以下标准」，那又变成了让模型自评；而模型的自评，只是另一段续写（[02](02-continue-writing.md)）。

B 做的事并不神秘：他把「一句话」拆成了五个决定，并且把最后一个决定留给了自己。

## 25.2 唯一真问题：凭什么说「做好了」

**怎样写，才能让「做好了」是可检查的？**

这句话要拆成四问，缺一问，「做好了」就退回成一句观感：

| # | 问 | 答不上来会怎样 |
| --- | --- | --- |
| 1 | **谁有资格说好了？** 你、同事、客户，还是有签字权的人？ | 谁都能说「还行」，谁都不负责 |
| 2 | **哪一条算过？** 必须项是哪几条，加分项是哪几条？ | 用整体印象代替逐条判断 |
| 3 | **拿什么证明？** 原文、回执、对照，还是它自己的复述？ | 把「它说它检查过」当成检查 |
| 4 | **不过怎么办？** 退回、重做、换方案，还是直接否决？ | 明知有问题，仍被「总体不错」推着走 |

四问里最容易被跳过的是第 3 问。因为前两问可以在纸上完成，第 3 问要求你手里真的有一份能对照的东西。没有它，验收就变成「读一遍，觉得行」。

### 写不出验收条件，不是文字问题

很多人以为「写不清」是表达能力的毛病，于是去学更花的提示词句式。真正的原因通常更靠前：**你还没决定要什么。**

| 说法 | 它描述的到底是什么 | 能不能验收 | 缺的那一句 |
| --- | --- | --- | --- |
| 「写得专业一点」 | 一种观感 | 不能 | 哪些具体特征算专业：长度、称呼、是否分点、有没有感叹号 |
| 「不要出错」 | 一个愿望 | 不能 | 哪种错：日期、人数、口径、权限，还是错别字 |
| 「让人看了想参加」 | 一个效果 | 不能 | 读完要记住哪三件事；哪一句负责让人想去 |
| 「按 v2 写，日期只出现 10 月 25 日」 | 一个条件 | 能 | 已经够了 |

前三条不是「说得不够狠」，是**没有对象**。你没法检查「专业」，只能检查「全文没有出现『亲』『哈』『哟』，称呼统一用『各位同事』，每段不超过三行」。后者不一定等于专业，但它是可观察的；而可观察，是验收的入口。

### 可检查的三个条件

一条验收条件要成立，至少要满足三件事：

1. **可观察**：不是「我觉得」，是「纸上/屏幕上/原始系统里能看到」。
2. **可重复**：换一个没参与的人，按同一条判，结论一致；不一致，说明这条还没写清。
3. **有证据**：能指到一句原文、一张回执、一次对照，而不是「它自己说」。

三条里，第 2 条最容易被忽略。一个人判得很稳，不代表这条条件写得清；可能只是他心里有一套没写出来的标准。**验收条件的读者不是写卡的人，是那个要接手的人。**

### 从三个原语推出来

为什么「感觉不错」不能当验收？不是因为它不高级，是因为这台机器的三件事决定了它：

- **P1 续写**：它每一步都在选「接下来最像什么」。一段完整的、自信的、把空格填满的文字，本来就比一段留着「待确认」的文字更像「完成」。所以它会天然倾向于把未定写成已定。
- **P2 工作台**：它只能看见这一轮放上桌的东西。你没把验收条件放上桌，它就没有目标可对；你放了，它也只是多了一段材料，不保证照做。
- **P3 抽样**：同一个工作台能抽出不同的下一步。这一轮碰巧对了，不代表下一轮还对；所以验收要能重复，不能靠一次印象。

三条合起来，结论很朴素：**验收必须在模型外面，必须写下来，必须能被重复执行。** 这也是为什么本篇讲的不是「怎么让它更听话」，而是「怎么让你自己知道它有没有做到」。

### 四个定位问题在任务卡里的形态

| 四问 | 在任务卡里问什么 | 答错会长什么样 |
| --- | --- | --- |
| 这句话是谁说的？ | 这条验收条件是客户定的、材料里写的，还是模型自己总结的？ | 把模型建议的「合格标准」当成甲方标准 |
| 它这一轮看见了什么？ | 卡里列的材料，这一轮真的送进去了吗？ | 卡上写了 v2，请求里进的是 v1 |
| 这是提议、事实，还是已执行？ | 交付物是草稿、可发布稿，还是已经发出去的东西？ | 把「已同步」当成交付完成 |
| 我拿什么独立验证？ | 验收拿的是原文、回执、对照，还是它的复述？ | 它说「已逐条核对」，你就签了字 |

第三问在这一篇格外重要。任务卡的「交付」段如果不写「这次只做到草稿」，模型很容易把「写好通知」续写成「通知已发出」；这不是它想骗你，是「已发出」在大量通知文本里就是那个更顺的结尾（[16](16-receipt.md)）。

## 25.3 一张图：五段卡住的是五个决定

五段不是五个标题，是五个必须有人做的决定。把它们排成一条链，能看出每一段各自挡住什么。

```text
   ① 目标 ──▶ ② 材料 ──▶ ③ 边界 ──▶ ④ 交付 ──▶ ⑤ 验收
   为什么做     凭什么做     不许做什么    做成什么样    怎么算过
       │           │            │            │           │
       └───────────┴────────────┴────────────┴───────────┘
                五段合起来只回答一句话：
        「谁，拿什么，在什么限制下，交什么，由谁凭什么判过」
```

这五段对应的不是文档目录，而是五处**默认值**。你空一段，就有一个决定被别的角色代做：

| 空的段 | 谁替你做决定 | 常见结果 |
| --- | --- | --- |
| 目标 | 模型按「最顺的续写方向」补 | 写成一篇面面俱到的活动宣传，而不是一条能发群的通知 |
| 材料 | 应用按「这次放了什么」补，模型按「常见值」补 | 42 人、10 月 18 日、B 场地「可选」 |
| 边界 | 运行时按「权限内最顺的动作」补 | 只读任务被做成写入；该保密的名单被附在通知后 |
| 交付 | 模型按「最省事的形式」补 | 给一大段散文，不给可核对的结构 |
| 验收 | 你用「读起来行不行」补 | 三处未定项被流畅的文本盖过去 |

这张表最值得记住的是最后一行。**验收空着，不是「没人验收」，是「用观感验收」。** 而观感恰好是 P1 最擅长的产物：它生成的东西，读起来总是像那么回事。

再看一眼参与者。任务卡不是只给模型看的，它至少有三个读者：

```text
   谁          拿什么                做什么                      对什么负责
   ──          ──────                ────                        ──────────
   写卡的人     目标 / 材料 / 边界     把决定写下来                五段有没有空格
   应用         这张卡的一部分         拼这一轮的清单              送进去的是哪几段
   模型         清单里的文字           续写出草稿                  措辞与结构，不负责真假
   工具/运行时  权限与回执            执行或不执行                动作与回执
   验收的人     验收条件 + 原文/回执   逐条打勾                    过或不过，签不签字
```

图里有两处责任不能混。

**第一处：写卡的人和验收的人。** 可以是同一个人，但如果这个人同时又是「最想让它通过」的人，验收就会往宽松的方向漂。至少要有一次，由没参与写卡的人按条件判（这条和 [22](22-evaluation.md) 的盲评是同一个道理，只是规模小得多）。

**第二处：模型和工具。** 模型只能交出文字，不能交出「已执行」。卡里写「完成后告诉我」，得到的是一句「已完成」；卡里写「把回执贴出来」，得到的仍可能是一段像回执的文字。**真正的回执在原始系统里，不在卡里，也不在模型的回答里。**

## 25.4 逐段讲（一）：目标——不是「写个通知」，是「谁读完做什么」

### 写什么

目标段只写三件事：

1. **给谁看**：同事、领导、客户、外部供应商，还是只给你自己。
2. **读完/用完之后能做到什么**：知道哪三件事、能做什么决定、不再来问什么。
3. **这次做到哪一步**：草稿、可发布稿、可执行的动作，还是只要一个方案对比。

第三件事最容易被省，也最值钱。因为 P5 决定了模型只出主意、不动手；但它的文字很容易越过这条线。你写「写个通知」，它可能写「通知已发出」；你写「这次只到草稿」，它至少少了一个顺理成章的结尾。

### 坏写法与好写法

| 类型 | 原话 | 它的问题 / 为什么可用 |
| --- | --- | --- |
| 坏 | 「帮我写个团建通知，语气好一点，专业一点。」 | 没写读者、没写读完要知道什么、没写做到哪一步；「专业」不可观察 |
| 坏 | 「先分析名单，再比价，最后写通知。」 | 这是流程，不是目标；流程可以商量，目标不能 |
| 好 | 「读者是 39 位同事。读完要知道三件事：10 月 25 日周六当天往返、8:00 公司门口集合、需要自带什么。读完不再来问日期和人数。这次只到草稿，不发布。」 | 读者可指名，成功状态可观察，边界（草稿）写进了目标 |

### 判据

写完目标段，做三个删减测试：

- 把「专业」「高级」「有感染力」全删掉，还剩不剩一句能指导写作的话？不剩，说明目标还停在观感。
- 读者能不能换成一个具体的人或一群具体的人？不能，说明你还不知道在为谁写。
- 成功状态能不能写成「读完不再问什么」？不能，说明你还没想清这次交付要解决哪个问题。

最后一句话可以当口诀：**目标不是「我要它写成什么样」，是「谁读完以后，什么变了」。**

## 25.5 逐段讲（二）：材料——版本、范围、不可用

### 写什么

材料段要回答四个问题，每个问题都比「文件在哪」更要紧：

1. **用哪些**：这次允许进入任务的材料的白名单。
2. **哪一版算数**：版本、日期、状态（现行 / 已作废 / 仅参考）。
3. **冲突时以谁为准**：一句能被第三人复核的仲裁话，不是「以最新为准」。
4. **缺了怎么办**：材料里没有答案时，是停下、标注，还是允许它推断。

### 坏写法与好写法

| 类型 | 原话 | 它把什么留给了默认 |
| --- | --- | --- |
| 坏 | 「资料都发你了，你自己看。」 | 哪一版算数、哪份只能参考、缺了怎么办，全留给了模型和应用的默认顺序 |
| 坏 | 「参考一下群里的消息。」 | 群消息没有版本、没有状态、没有适用范围；说过的话和定过的事混在一起 |
| 坏 | 「就是你知道的那个文件。」 | 模型没有「上次那个文件」；它只有这一轮送上桌的东西（[09](09-whats-in-the-request.md)） |
| 好 | 「只用通知 v2（10 月 25 日）；v1（10 月 18 日）已作废，不得引用；名单按人去重后 39 人，导出 42 条中 3 条重复；B 场地合同未签、档期未确认，只能作比较；雨天室内备选未确认，原样保留待确认。」 | 版本、口径、状态、未定项都写成了可读的句子 |

### 材料段的七个格子

把团建这套材料摊开，每一份在卡里都该有四个字段：名称、版本/日期、状态、卡里怎么写。

| 材料 | 版本 / 日期 | 状态 | 卡里必须写的那一句 |
| --- | --- | --- | --- |
| 通知 v2 | 10 月 25 日方案 | 现行 | 「日期、集合时间只以 v2 为准」 |
| 通知 v1 | 10 月 18 日方案 | 已作废 | 「v1 已作废，不得引用，不得出现在交付物里」 |
| 名单导出 | 42 条记录 | 原始数据 | 「按人去重后 39 人；42 是记录条数，不是人数」 |
| 场地 A 报价 | 人均 260 元 | 现行 | 「含午餐、场地、保险；39×260=10,140」 |
| 场地 B 报价 | 人均 310 元 | 仅比较 | 「合同未签、档期未确认；合计 15,690，超预算 90 元」 |
| 饮食备注 | 2 人素食、1 人花生过敏 | 现行，待场地确认 | 「过敏一条必须写『与场地确认』，不得写『已安排』」 |
| 预算 | 总额 15,600 元 | 硬约束 | 「按 39 人、人均 400 计；追加 90 元未决」 |

这张表有一个隐含的顺序：**先写状态，再写内容。** 因为一份材料的危险程度，主要不取决于它写了什么，而取决于它现在还算不算数。作废的 v1 内容完全正确，只是不再适用于这次任务；把它放进卡里而不标状态，等于给冲突开门。

### 判据

- 每份材料能不能回答「它现在是现行还是作废」？不能，说明材料段还没写完。
- 两份材料冲突时，卡里有没有一句可复核的仲裁话？没有，说明你把仲裁留给了模型的显著性。
- 材料里没有答案时，有没有出口？没有出口，它最省力的做法就是编一个（[02](02-continue-writing.md)）。

最后一条边界：**材料段是白名单，不是仓库清单。** 把所有资料都倒进去，不会让它更聪明，只会让旧版、宣传文案、无关附件一起上桌。卡的材料段应该像门禁名单，不像搬家清单。

## 25.6 逐段讲（三）：边界——不做什么，比做什么更省事

### 写什么

边界段要写五种东西，顺序从硬到软：

1. **非目标**：这次明确不做什么（不写领导讲话、不做奖品方案、不做预算申请）。
2. **权限**：可读、可写、可发、可付，分别是哪一档。
3. **不可逆动作**：哪些动作一旦发生就收不回（群发、付款、删除、发布）。
4. **事实边界**：不许新增材料里没有的事实；找不到就说找不到。
5. **决策边界**：哪些事不替人定（是否追加 90 元、B 要不要选、雨天怎么办）。

### 坏写法与好写法

| 类型 | 原话 | 它的问题 / 为什么可用 |
| --- | --- | --- |
| 坏 | 「注意安全，别出错，别乱来。」 | 没有一条能对应到具体动作；「乱来」不是一个可指认的违规 |
| 坏 | 「你是一个有十年经验的团建策划专家，做事很稳。」 | 这是身份，不是边界；身份改变语气，不改变它能不能发群、能不能付款 |
| 坏 | 「不该做的别做。」 | 把判断权又退回给模型；它不知道你说的「不该」是哪一条 |
| 好 | 「只起草；不发群、不付定金、不改名单；不新增材料外的事实；不替人决定是否追加 90 元；B 只能写成待确认；雨天只能写待确认。」 | 每一条都对应一个能指认的动作或一句话 |

第二行值得多说一句。这是最常见的一种「万能模板腔」：开头先给模型一个身份——你是一个专业的某某、资深某某、顶尖某某。它读起来很正式，实际提供的是一层**语气**，不是一层**约束**。一个「十年经验的团建策划专家」在文本里完全可能写出「已同步至群公告」，因为专家也会假定行政已经发了。身份不能替代权限，也不能替代回执。

### 最常漏的是「不替谁做决定」

多数人写边界，只写「不许做什么动作」，漏了「不许替谁做什么决定」。而后者才是未定项被填掉的主要入口：

- 是否追加 90 元把 B 方案做下来——这是有预算权的人的决定，不是模型的。
- B 场地要不要选——合同未签、档期未确认，模型只能比较，不能拍板。
- 雨天怎么办——材料写的是「待确认」，模型不能把它写成「已安排」。

一旦这三类决定被写进边界，验收就多了一条非常具体的检查：**交付物里有没有出现一个本不该由它做的决定。**

### 写了「不许发」，不等于发不出去

这是本篇必须提前说清的一件事，也是全书反复回到的那条线：

> **任务卡里写「禁止群发」，是一句提醒，不是一道闸门。**

提醒能降低概率，改不了权限。真正拦住发送的，是运行时的权限校验、审批点和回执（[16](16-receipt.md)、[17](17-injection-and-permission.md)）。所以边界段要写，但不能把安全感全押在它身上；卡里最好再加一句「这些是提醒，真正的闸门在发送权限与审批」，让读卡的人知道该去哪里核。

### 判据

每写一条边界，问一句：**如果它违反了这一条，我能指出它做了哪个具体动作、或写了哪句具体的话吗？** 指不出来，这条就是情绪，不是边界。

## 25.7 逐段讲（四）：交付——形状、位置、长度、给谁

### 写什么

交付段决定「做成什么样」，要写六件事：

1. **形态**：一段文字、一张表、一份清单，还是几样一起。
2. **长度**：上限或区间，不写「尽量」。
3. **必须包含的字段**：日期、人数、集合时间、饮食提醒。
4. **交付位置**：给你、给某个同事、进某个文档，还是进群。
5. **附带物**：事实对照表、未定项清单、改动说明。
6. **版本与命名**：这是草稿还是终稿，文件名带不带日期。

### 坏写法与好写法

| 类型 | 原话 | 它的问题 / 为什么可用 |
| --- | --- | --- |
| 坏 | 「给我一份通知。」 | 没写长度、字段、位置；它会给最省事的那一种 |
| 坏 | 「越详细越好。」 | 没有上限，它就用字数掩盖不确定；越详细越像认真 |
| 坏 | 「看着办，你懂的。」 | 把交付形状整个退回给默认值 |
| 好 | 「一段群通知草稿，180 字以内，含日期、人数、集合时间地点、饮食提醒；另附一张事实对照表（每条事实一行：结论 / 原句 / 出自哪份）和一张未定项清单（最多 3 条）。交给我，不进群。文件名带 10 月 8 日。」 | 形态、长度、字段、附带物、位置、版本都能被检查 |

### 交付位置是权限问题

「发给我」和「发到群里」看起来只是两个位置，实际是两档权限。前者只产生一份文件，后者产生一次对外动作。交付段如果不写位置，默认值往往是「就地完成」——在聊天产品里，这就可能被理解成「可以直接发」。

所以位置要写死，并且和边界段对齐：边界说「不可群发」，交付说「交给我，不进群」。两段说的是同一件事，但一个管动作，一个管去向；两处都写，读卡的人才不会在最后一步顺手点发送。

### 附带物是验收的抓手

只交一段正文，验收只能靠读。带上三样东西，验收就有了落点：

- **事实对照表**：每条结论对应哪句原文、出自哪份材料。它让「这句话哪来的」变成一个可以逐行核的问题。
- **未定项清单**：还缺什么、找谁确认。它让「没定」有一个合法的输出位置，而不是被填满。
- **改动说明**：这一版改了什么、为什么改。它让第二个人接手时不用重新猜。

最后一样在多轮任务里尤其重要。没有改动说明，第二轮的人（或下一轮的模型）会把这一版当成唯一版本，前面为什么改、改掉了什么，全都消失。

### 判据

把交付物交给一个没参与的人，他能不能不问你就转交？如果能，说明形态、位置、附带物都够了；如果他还要问「这是给谁的」「还差什么」「能不能发」，说明交付段还缺格子。

## 25.8 逐段讲（五）：验收——每一条都要能被第三个人执行

### 写什么

验收段是整张卡的核心，要写五类内容：

1. **必须项**：一条不过就是不过的硬条件。
2. **加分项**：可以做得好、但不参与否决的条件。
3. **不得出现**：错误日期、错误人数、越权措辞、隐私字段。
4. **硬失败**：越权、泄密、编造事实、不可逆动作未审批，任一出现即整份否决。
5. **谁判、拿什么判**：人、原文、回执，还是工具检查。

### 坏写法与好写法

| 类型 | 原话 | 它的问题 / 为什么可用 |
| --- | --- | --- |
| 坏 | 「写得专业、有感染力，让人想参加。」 | 三条都不可观察；三个人会给出三个结论 |
| 坏 | 「不要有错别字，不要有错误。」 | 「错误」没有对象；错别字能查，事实错、口径错、权限错查不了 |
| 坏 | 「符合公司风格。」 | 没有样本、没有特征；「公司风格」在每个人心里不一样 |
| 好 | 「日期只出现 10 月 25 日；人数为 39；不出现 42（除非在『记录条数』的说明里）；雨天写『待确认』；不出现『已发送/已同步』；全文 ≤180 字；不含手机号。」 | 每条都能打勾，且能指到一处具体的字 |

### 否定条件比肯定条件更有用

肯定条件（「要包含日期」）容易被一段流畅的文本来满足；否定条件（「不出现 10 月 18 日」「不出现 42」「不出现已确认」）更难被绕过，因为它是**排除法**。

团建这张卡里，最该写成否定条件的有四条：

- 不出现 10 月 18 日（旧版日期）。
- 不出现 42（除非明确写成「42 条记录」）。
- 不出现「已发送」「已同步」「已通知」（未执行的动作）。
- 不出现「已确认」「已安排」「已预订」（未定的状态）。

这四条对应的正是三类最常见的失败：版本错、口径错、状态错。它们都不靠语气判断，只靠搜字符串就能发现——这也让一部分验收可以先交给机器做（[14](14-structured-output.md)）。

### 必须项与加分项要分开

一份卡里所有的条件都写成「必须」，会导致两个后果：要么交付永远不过，要么判的人开始偷偷放水。比较稳的做法是分层：

- **必须项**：事实、口径、边界、权限。一条不过，整份不过。
- **加分项**：语气更自然、结构更清楚、长度更贴近场景。可以「需修改」，不能否决。

分层不是降低标准，是让标准**可执行**。一条永远达不到的必须项，最后一定会被当成建议。

### 硬失败单列

有四类问题不该进平均分，也不该被「总体不错」抵消：越权、泄密、编造事实、不可逆动作未审批。它们在 [22](22-evaluation.md) 里已经拆过，这里只落到任务卡上：

> 验收段要有一行写「硬失败」，并且写明「任一出现，整份不通过，不看其它项」。

没有这一行，验收就会退化成打分：九条过、一条越权，平均下来还是「不错」。而越权不是分数，是闸门。

### 判据

找一个人，把卡给他，不解释，让他独立判一份交付。你们两个结论不一致的地方，就是验收段没写清的那一条。**改那一条，不要投票。** 投票只会决定谁的声音大，不会让条件变得更可执行。

## 25.9 三类约束：硬约束、可用默认、必须澄清

[09](09-whats-in-the-request.md) 把约束账分成硬约束、可用默认、未定项三类。任务卡要在这本账上再往前走一步：把三类变成三种**动作**。

| 类别 | 一句话判据 | 团建里的例子 | 谁有权定 | 写进卡里怎么写 | 猜错的代价 |
| --- | --- | --- | --- | --- | --- |
| **硬约束** | 改了之后，这就不是同一个任务了 | 日期 10 月 25 日；39 人；总额 15,600 元；2 人素食、1 人花生过敏 | 有预算权或活动决策权的人 | 陈述句 + 来源，例如「日期只以 v2 为准」 | 事故或整体返工 |
| **可用默认** | 它自己定了，最坏结果是重写一遍 | 通知语气、段落顺序、称呼方式、金额写法、标题层级 | 任何人 | 可以只写「按常规」，不必逐条确认 | 重写一段 |
| **必须澄清** | 材料里没人有权定，且答案会改变交付或触及红线 | 是否追加 90 元；B 要不要选；雨天怎么办；3 条重复记录保留哪一条 | 对应的责任人 | 列在卡头「开工前必须回答」，未答不填 | 对外承诺、花钱、不可逆 |

三类之外还有一类，容易混进来：**权限**。权限不是「任务的参数」，是「谁能做哪个动作」；它记在权限账里（[16](16-receipt.md)），在任务卡里落到「边界」段，不在这张三行的约束表里。把权限写成约束，会让人以为「卡上说了不许发」就等于发不出去。

### 硬约束：不许改

硬约束的判据只有一句：**改了它，任务就变成另一个任务。** 10 月 25 日改成 10 月 18 日，不是「日期写法不同」，是另一场活动；39 人改成 42 人，不是「口径差异」，是另一个预算。权限比硬约束更硬：它根本不在这张表里，也不该由任务参数来谈；卡上写「可以发」不会产生发送权，卡上写「不许发」也拦不住一次点击。

硬约束在卡里要写成陈述句，并且带来源。不要写「注意日期」，要写「日期只以 v2 为准，v1 已作废」；不要写「控制预算」，要写「总额 15,600 元，按 39 人、人均 400 计」。**带来源的陈述句能被复核，形容词不能。**

### 可用默认：不必问

可用默认都发生在表达层：语气、顺序、称呼、单位写法、标题层级。它们影响读起来舒不舒服，不影响结论对不对。

这一类最常见的错误不是「定错了」，是**过度请示**：把每一处语气都拿回来问，一次五分钟的活变成三轮往返。卡里写一句「语气、段落顺序按常规处理，不必回来确认」，就能把这类往返省掉。

判断它是不是可用默认，问一句：**它自己定了，最坏结果是什么？** 如果只是「重写一遍」，那就是默认；如果要重新算账、重新确认场地、重新报批，那就不是。

### 必须澄清：不许猜

这是三类里最容易被忽略的一类，因为它既不像硬约束那样有明确的值，也不像可用默认那样可以放手。它的特征是：

- 材料里没有答案；
- 材料里也没有一个有资格定这件事的人；
- 而这个答案会改变交付物的形状、结论，或者触及红线。

团建里至少有三处：是否追加 90 元、B 要不要选、雨天怎么办。这三处如果被「合理推断」填掉，文本会更完整，但承诺是假的。**模型的默认动作是把空格填满，不是把空格留着。** 所以卡里必须给「没定」一个合法的位置，并且明确「未答不填」。

### 未定项和必须澄清不是一回事

这两个词容易混，区别在状态与动作：

- **未定项**是一个状态：这件事还没定，原样保留「待确认」。
- **必须澄清**是一个动作：这件事不能靠猜，开工前要有人去问、去答。

一个未定项如果只是附注，原样保留就够了；如果它会挡住交付（比如「B 到底选不选」），就要升级成必须澄清。反过来，必须澄清的问题答完之后，也可能变成硬约束（「定了，就选 A」）或者可用默认（「怎么称呼都行」）。

```text
   硬约束   ──▶ 抄进卡，标来源        ──▶ 不许改
   可用默认 ──▶ 放手，最多写「按常规」 ──▶ 不必问
   必须澄清 ──▶ 开工前问，未答不填     ──▶ 不许猜
   未定项   ──▶ 原样保留「待确认」     ──▶ 不许写成已定
```

### 三类混用会产生的三种失败

- **把未定项当默认值填掉**：输出里出现「雨天改在室内多功能厅」「B 场地已确定」。读起来最完整，也最危险。
- **把可用默认当硬约束**：输出里塞满「如需调整请告知」，每改一个字都来问一遍。没有错，只是把本可以自己定的事退回了你。
- **把硬约束当默认**：日期变成 10 月 18 日、人数变成 42、预算按记录条数重算。每一个都算得通，只是不是你这次要的那个任务。

三种失败的共同点：**它们都不像错误，像另一种合理的写法。** 这就是为什么验收条件必须写死，而不能靠「它应该知道」。

## 25.10 什么时候该让 AI 先问

「让它先问」听起来像一种礼貌，其实是一个成本判断。问一次要花你的时间，猜错要花返工的时间；只有当猜错的代价明显更高时，先问才划算。

### 五条判据

| # | 判据 | 团建里的例子 | 该怎么做 |
| --- | --- | --- | --- |
| 1 | 答案会改变交付物的形状或结论 | 选 A 还是 B；写群通知还是写内部说明 | 停下问，别先写 |
| 2 | 触及红线，且卡里没有可引用的依据 | 能不能群发；名单能不能附出去；肖像能不能用 | 停下问；没有答复就不做 |
| 3 | 两份材料互相冲突，且没有仲裁 | v1 与 v2 日期不同；两个人报的人数不同 | 停下问，或按卡里的仲裁句处理 |
| 4 | 猜错要整体返工，且返工成本高于问一次 | 预算是否按 39 人重算；B 是否进入候选 | 先问，再开工 |
| 5 | 用户自己也没定，而任务要求把它写成已定 | 追加 90 元；雨天备选 | 保留未定，或升级为必须澄清 |

五条里有三条（1、2、4）都指向同一个词：**代价**。不确定本身不是理由；不确定且代价高，才是。

### 一条判断流

```text
   这个空，填错会怎样？
        │
        ├─ 只是措辞不同，重写一遍就行
        │        └─▶ 可用默认：自己定，交付时说明一句
        │
        ├─ 交付形状或结论会变，但可逆、便宜
        │        └─▶ 先按最保守的默认做，在交付里标注「此处按 X 处理」
        │
        └─ 会产生对外承诺 / 花钱 / 不可逆 / 事实错
                 │
                 ├─ 材料里有具名的人定过 ──▶ 引用那句，不必再问
                 └─ 没有 ──▶ 必须澄清：停下来问，不给默认
```

这张图有一个容易看漏的分支：**「材料里有具名的人定过」不必再问。** 很多「先问」的冲动，其实是因为没读材料；卡里已经把决定写下来了，再去问一遍，只会把责任推回去。先查卡，再决定问不问。

### 问的时候怎么问

一次不超过三条，按影响排序。每条给四样东西：

1. 一句背景：为什么这件事会挡住任务。
2. 两个选项：不要开放式地问「你想怎么办」。
3. 一个建议：你打算默认怎么处理。
4. 不答的后果：会停在哪一步，或者会按哪个保守方案做。

硬约束不给默认，必须等答复；可用默认给默认，允许对方沉默。这样「先问」不会变成「每件事都等回复」。

### 什么时候不该问

- **表达层的事**：语气、顺序、称呼。问了也只是把决定退回给用户。
- **材料里已有答案**：先查卡，再问人。
- **可逆且便宜的事**：先做，交付时标注，允许对方改。为一件改一句话就能修的事停半小时，是另一种浪费。

过度请示和擅自决定是一对镜像：一个把成本推给用户，一个把风险推给用户。任务卡的作用，是提前把这两种成本标出来。

### 「AI 先问」在工程上是什么

这里要泼一盆冷水：**模型不会自己知道哪个空重要。** 它没有「这件事要不要问」的独立判断，它只是接着前文续写；你写「不确定就问」，它可能问一些无关紧要的，也可能在真正关键的地方直接填掉。

所以「先问」不能只靠一句提示词。它需要两样东西：

- 卡里有一张**必须澄清清单**，逐条列出「未答就不能开工」的问题；
- 应用或人在开工前做一次检查，清单没清空就不进入生成。

这仍然是 P5 的分工：模型负责提问题、给选项；停不停、谁答、答完记在哪，是外面那圈系统的事。**把「先问」写进卡，不等于它会先问；把「未答不填」做成流程，才算。**

## 25.11 示例的两种作用：固定格式有效，为事实背书危险

示例是任务卡里最有效的部分，也是最危险的部分。有效，是因为它一次固定了格式、粒度、语气；危险，是因为它会连同里面的**值**一起被复制。

### 两种作用，两条规则

| 示例的类型 | 它固定了什么 | 为什么有效 / 为什么危险 | 团建里的样子 |
| --- | --- | --- | --- |
| **格式示例** | 字段、顺序、句长、语气、粒度 | 有效：格式是一种约定，不依赖这次的事实；给一个结构，输出会明显更稳 | 「第一行日期，第二行集合，第三行提醒，最后联系人；每行不超过 30 字」 |
| **事实示例** | 具体日期、人数、金额、状态 | 危险：它会连同值一起被当成「已经核过的事实」，哪怕那份示例是上一次的 | 「照这份写：10 月 25 日，共 42 人，雨天改室内多功能厅，已同步群公告」 |

第二行里的三个值，恰好是这次任务里最不能沿用的三个：42 是记录条数（去重后 39），室内是未确认，已同步是没发生。示例越完整、越像成品，这三个值就越容易被当成「格式的一部分」抄进去。

### 三个泄漏口

示例的危险不只在于「数字写错」，它有三个泄漏口：

1. **值泄漏**：示例里的 42、10 月 18 日、15,690，被当成这次的值。模型没有「这是上一次的」这个变量，它只有「这段文字和当前任务很像」。
2. **状态泄漏**：示例写「雨天改室内」，模型学到的是「雨天要给出一个安排」，于是把「待确认」写成「已安排」。这比抄错数字更隐蔽，因为输出里没有任何一个字符是错的，错的是**确定性**。
3. **长度泄漏**：给一个 500 字的范文，它就会写 500 字，即使你要求 180 字。示例是最具体的长度信号，比「180 字以内」更具体。

### 四条用法

- **示例只给形状，值从材料来。** 示例里可以出现「日期」「人数」这些字段名，但不要出现具体的 10 月 25 日、39 人；真值放在材料段。
- **必须带值时，标注「示例值，不得沿用」。** 并且在材料段把真值单独列一遍，让两处能对上。
- **优先用结构示例，不用成品示例。** 只留字段和句式，比给一份填满的成品安全得多。
- **示例和交付要求必须一致。** 如果示例是 500 字、交付要求是 180 字，示例会赢；因为具体压过抽象。

### 判据

把示例里的数字全涂掉，它还能不能固定格式？能，说明它是格式示例；不能，说明它在为事实背书。**为事实背书的示例，不该出现在任务卡里，只该出现在材料里，并且带版本和状态。**

## 25.12 场景差异：四类任务，收紧不同的段

同一张五段卡，在不同任务里不是同一个重心。事实问答怕编，摘要怕丢，行动怕越权，创意怕早收敛；所以每类任务该收紧的段不一样。

| 场景 | 最常崩在哪 | 该收紧 | 可以放宽 | 验收锚点 |
| --- | --- | --- | --- | --- |
| **事实问答** | 编来源、把未定写成已定 | 材料（版本、范围）+ 验收（每句有出处） | 交付格式、语气、长度 | 每条结论能回原文；找不到就说找不到 |
| **摘要提取** | 剪掉否决与未决、抬高结论强度 | 边界（必须保留哪五类）+ 验收（逐条对照） | 句式、段落顺序、字数（在区间内） | 决定、否决、依据、未决、边界五类都在 |
| **行动任务** | 越权执行、把「已办」当回执 | 边界（权限）+ 验收（回执、原始系统） | 措辞、格式、解释长度 | 只做权限内的事；原始系统里能查到 |
| **创意发散** | 太早收敛、全是安全答案 | 目标（受众、禁区、评价维度）+ 边界（不许碰的红线） | 材料（允许联想）、格式、长度 | 数量够、方向覆盖、每条有一个具体细节 |

### 事实问答：验收写在「出处」上

事实类任务的验收，不要写「答案正确」，要写「每条结论能指到一句原文」。因为「正确」由谁判、拿什么判，都没说；「指到原文」是第三个人能执行的。

再加一条否定条件：「材料里没有的，不许补；找不到就说找不到。」这一句同时解决两个问题：降低编造，也给「不知道」一个合法的输出位置（[02](02-continue-writing.md)）。

### 摘要提取：验收写在「没丢什么」上

摘要的失败很少是「写得太长」，多数是「把不该省的省了」。所以验收要盯住五类必须保留的东西：决定、否决、依据、未决、边界。团建里就是：日期定了 10 月 25 日（决定）、v1 作废（否决）、按 39 人算（依据）、雨天待确认（未决）、不可群发（边界）。

这五类里，「否决」和「未决」最容易被剪，因为它们是短句、否定句，读起来不像结论。验收条件要专门为它们写一行：「必须保留 v1 已作废、雨天待确认、不可群发这三句。」（压缩机制见 [11](11-compression.md)。）

### 行动任务：验收写在「原始系统」上

行动类任务的交付，不是一段文字，是一次状态变化。所以验收不能停在「它说办好了」，要落到原始系统：群里有没有这条消息、后台有没有这条记录、回执号是多少。

任务卡在这里能做的，是把动作切成两半：**提议**和**执行**。卡里写「只出草稿和调用建议，不执行」，验收写「原始系统无变化，或变化与回执一致」。至于它会不会真的执行，取决于运行时的权限，不取决于卡里的措辞（[16](16-receipt.md)、[17](17-injection-and-permission.md)）。

### 创意发散：验收写在「范围和禁区」上

创意任务最容易把验收写成「有创意」「有电影感」「有后劲」，这三句都不可检查。可行的替代是三条：

- **数量**：给 10 条，不是「多给几条」。
- **覆盖**：必须覆盖三个指定方向（比如三种人物动机、三种反转位置）。
- **禁区**：不许碰的题材、语气、套路，明确列出来。

再加一条「每条必须有一个具体细节」（一个动作、一个画面、一句台词），用来挡住「正确的废话」。这样验收的不是「好不好」，而是「够不够多、覆盖不覆盖、能不能用」；好不好仍然要人来判，但人判的时候手里有东西可指（创作的两件事见第 27 篇）。

### 四类任务的共同底线

放宽的永远只是表达层：格式、语气、长度、顺序。**事实、权限、隐私、版权、不可逆，在任何场景里都不放宽。** 创意任务可以允许它编一个不存在的情节，但不能允许它把「已发送」写成事实；行动任务可以放宽措辞，但不能放宽权限。这条底线不随场景变。

## 25.13 提示词的三个不能

任务卡能写很多事，但有三件事，无论提示词写得多好都做不到。分不清这三件事，就会出现一种最常见的错误：把该由系统做的事，写成一句话，然后以为它已经发生了。

| 不能 | 为什么 | 它最多能做到 | 该由谁做 |
| --- | --- | --- | --- |
| **不能给权限** | 权限是运行时对动作的许可，不是文本里的声明 | 提高它「不主动去做」的概率 | 运行时权限、审批点、只读账号（[16](16-receipt.md)、[17](17-injection-and-permission.md)） |
| **不能给回执** | 回执是原始系统对一次执行的记录；模型只能生成一段像回执的句子 | 让它描述「应该有什么回执、长什么样」 | 工具与原始系统（[16](16-receipt.md)） |
| **不能替代证据** | 证据是原文、回执、对照；模型的自述也是生成 | 让它给出引用位置，供你回原文核 | 人 + 原文 / 回执 / 对照（[09](09-whats-in-the-request.md)、[22](22-evaluation.md)） |

### 不能给权限

团建任务里，卡上写着「不可群发」。这句话能让模型少说几次「已发到群里」，但它不能让群发按钮消失。如果运行时给了发送权，一段文本拦不住一次点击；反过来，如果运行时没有发送权，卡上不写也发不出去。

所以「不可群发」在卡里是**告知**，在运行时才是**限制**。两处都要有：卡里写，是为了让读卡的人知道边界；运行时收权，是为了让越界真的发生不了。只写卡不收回权限，得到的是一种很舒服的错觉。

### 不能给回执

模型可以写「已同步至群公告」，可以写一个看起来很像的回执号，甚至可以写「系统返回成功」。这些都是文字，不是回执。回执要能在原始系统里查到：群里有没有那条消息、后台有没有这条记录、付款方有没有到账。

因此验收段不能写「请回复已发送」，只能写「交给我，不进群」，然后由人去原始系统看。**问它「发了吗」，得到的仍然是文本；去群里看，得到的才是状态。** 这一条在 [16](16-receipt.md) 里拆得更细，这里只留一句：回执不在对话里。

### 不能替代证据

「我核对过，人数是 39。」这句话不是核对，是续写。真正的核对是你自己按人去重，或者让它给出「哪 3 条重复、按什么字段判重」，你再回名单看。

证据至少要满足一条：能指到原文的某一句、能指到原始系统的某条记录、能指到一次可重复的对照。三者都没有，只剩下它的复述，那就还没有证据。**模型可以帮你找证据的位置，不能替你成为证据。**

### 那提示词能做什么

把这三件事划出去之后，提示词剩下的用途反而更清楚了：

- 固定格式：字段、顺序、长度、语气。
- 写清目标：给谁看、读完能做什么、这次做到哪一步。
- 列材料：用哪些、哪版作废、缺了怎么办。
- 给验收：把可打勾的条件放上桌，让它有机会照着做。
- 要求引用：让每条结论带原句或位置，方便你回原文核。
- 要求标未定：让「待确认」有一个合法的输出位置。

一句话：**提示词能把任务说清，不能把后果兜住。** 任务卡也是同理；它比提示词多出来的，不是权力，是给人看的那一半。

## 25.14 边界三列账：任务卡能做什么、代价是什么、何时失效

| 能做什么 | 代价是什么 | 何时失效 |
| --- | --- | --- |
| 把「做好了」写成可逐条核的条件，让验收从观感变成动作 | 写卡要花时间；条件写多了，交付会变慢 | 验收条件本身不可观察（审美、气质、后劲）时，只能退回人来判 |
| 把材料版本与状态摆上桌，减少旧版、口径、未定项的混入 | 要维护版本；卡和材料不一致时，卡会变成新的错误源 | 材料在任务中途变了，而卡没更新时 |
| 把权限与非目标说清，减少「顺手做了不该做的事」 | 边界写太死，会压掉合理的探索 | 卡里写「禁止」但运行时没闸门时，它只提供安慰 |
| 把未定项保住，给「没定」一个合法位置 | 需要有人真的去确认，否则未定项会永远挂着 | 任务要求必须给出确定答案，而未定项又无法确认时 |
| 让第三人接手：换人、换模型、换时间，都能按同一张卡判 | 卡会过期；过期卡比没有卡更危险 | 日期、预算、权限、材料版本变化后，旧卡不能再用 |

这张表里最贵的一行是第三行。任务卡能写清权限，但**写不清不等于挡得住**；它是一张告知书，不是一道闸门。真正的闸门在运行时：谁能发、谁能付、谁要批（[16](16-receipt.md)、[17](17-injection-and-permission.md)）。把这两件事混在一起，就会得到一种很危险的安全感：卡上写了「不可群发」，于是没人再去检查发送权限。

### 这个类比在这里失效

任务卡常被比作**点菜单**：把「想吃什么」写成后厨能执行的单子，菜名、份量、忌口，一项一项列清楚。

这个类比在前半段成立：它确实把模糊的愿望变成了可执行的条目。但它在三个地方不成立。

**第一，后厨的手艺是稳定的，模型不是。** 同一张单子，两次出的菜可能不一样（P3）；你今天按这张卡验收通过，明天同一张卡可能交出一份不同的东西。所以任务卡不能像菜单那样「点过一次就放心」，它要配合重复与对照（[22](22-evaluation.md)）。

**第二，菜可以退，有些交付不能退。** 口味不对，端回去重做；群发出去的通知、付出去的定金、发出去的名单，退不回来。菜单的默认假设是「错了可以换」，任务卡的某些格子必须假设「错了没有下一次」。

**第三，菜单不需要向厨师解释「为什么点这道菜」，任务卡需要写目标。** 因为模型会用目标去补你没写清的格：你说「写个通知」，它按「通知一般长什么样」补；你说「让 39 位同事读完知道三件事」，它至少有一个可对的方向。**目标不是礼貌，是给续写一个约束。**

还有一层更细的失效：**任务卡不是合同。** 合同有对手方、有违约责任、有签字；模型不承担后果，也不记得上一轮。它这一轮读到的只是卡的一部分，下一轮可能连这部分都不在原位。所以卡要每轮重读，执行要靠外面的闸门，不能靠「上次说好了」。

最后一句：**卡会过期。** 材料换了、日期改了、权限变了，旧卡就不再是同一张卡。过期卡比没有卡更危险，因为它看起来像已经想清了。卡头写日期和版本，不是为了好看，是为了让下一个人知道「这张卡什么时候作废」。

## 25.15 一张可复制的任务卡模板

下面这张是填好的版本，可以直接改成你的任务。它用的是团建这套既定材料，数字不要改；换成你自己的任务时，五段的结构保留，值全部换掉。

```text
【任务卡】团建通知草稿（v1，10 月 8 日）

一、目标
  给谁看：39 位同事（不是领导，不是外部）。
  读完要能做到：知道 10 月 25 日（周六）当天往返、集合时间与地点、需要自带什么；
  不再来问日期和人数。
  这次只到「草稿」为止，不发布。

二、材料（只用这些，按状态标）
  1. 通知 v2：10 月 25 日方案，正文写明 v1 作废。→ 现行，唯一日期依据。
  2. 通知 v1：10 月 18 日方案。→ 已作废，不得引用，不得出现在交付物里。
  3. 名单导出：42 条记录，其中 3 条是同一人的重复提交。→ 去重后 39 人。
  4. 场地 A 报价：人均 260 元，含午餐、场地、保险。→ 现行。
  5. 场地 B 报价：人均 310 元；合同未签、档期未确认。→ 只作比较，不得写成已选。
  6. 饮食备注：2 人素食，1 人花生过敏。→ 过敏须写「与场地确认」。
  7. 预算：总额 15,600 元（按 39 人、人均 400 计）。
  材料里没有的，不要补；找不到依据的，写「材料未提供」。

三、边界
  可做：起草、核对名单人数、算 A 与 B 两版费用。
  不可做：群发、付定金、改名单、替人决定是否追加 90 元。
  不写：材料外的天气、流程、奖品、领导讲话。
  不把「待确认」写成「已确认」；不把 B 写成「已选」。
  （这些是提醒；真正的闸门在发送权限与审批，不在这张卡里。）

四、交付
  1. 群通知草稿一段，180 字以内，含日期、人数、集合时间地点、饮食提醒。
  2. 事实对照表：每条事实一行，写「结论 / 材料原句 / 出自哪份」。
  3. 未定项清单：最多 3 条，每条写「缺什么、找谁确认」。
  4. 结尾一句：说明本稿为草稿、未群发。
  交给我，不进群。

五、验收（第三人可逐条打勾）
  □ 日期只出现 10 月 25 日；不出现 10 月 18 日。
  □ 人数为 39；不出现 42（除非在「记录条数」的说明里）。
  □ 集合时间与地点能在 v2 原句中找到。
  □ 2 人素食、1 人花生过敏均在文中；过敏写「与场地确认」。
  □ 雨天写「待确认」；不出现「已确认 / 已安排 / 已预订」。
  □ 如提 B：写 15,690、超预算 90 元、合同未签；不得写成已选。
  □ 全文不超过 180 字；不含手机号、身份证号、家庭住址。
  □ 不出现「已发送 / 已同步 / 已通知」。
  □ 事实对照表每一行都能回原文找到；找不到的标「材料未提供」。
  以上任一「必须项」不过，即不通过；不看语气。
```

```text
  附带物：
  交到哪、给谁：

五、验收
  必须项（逐条可打勾）：
  不得出现：
  硬失败（一条即否决）：
  谁来判、拿什么判：
```

### 怎么用这张卡

- **先填第五段，再填第一段。** 先写清「怎么算过」，目标往往会自动变具体；反过来先写目标，容易写成一段漂亮但没法验收的话。
- **第二段只放这次真正要用的材料。** 白名单，不是仓库；旧版要么不写，要么写「已作废」。
- **第三段和第四段要对齐。** 边界说「不可群发」，交付就说「交给我，不进群」；两处指向同一件事，读卡的人才不会在最后一步顺手发出去。

## 25.16 你可以自己做的检验：让第三个人按卡验收

这个检验十分钟能做完，不需要代码，只需要一条你最近发过的模糊需求，和一个没参与的人。

### 动作

1. **找一条模糊需求**。比如「帮我整理一下会议记录」「写个活动通知」「把这堆反馈归纳一下」。
2. **只写验收段**。写五条必须项，其中一条是硬失败；每条都要能打勾，不能出现「专业」「清楚」「有感染力」。
3. **让它按原需求跑一次**，不要在提示词里加入这五条；你要测的是「原来的需求」会交出什么。
4. **你和同事各自按五条独立判**，不讨论，先写结论。

### 记录表

| 检验 | 固定什么 | 只改什么 | 观察什么 | 什么结果会推翻文中结论 |
| --- | --- | --- | --- | --- |
| 第三人验收 | 需求、材料、模型与模式 | 是否把验收条件写出来并交给第三人 | 两人结论是否一致；不一致在哪一条 | 不写验收、第三人也能稳定判对（说明这个任务本来就不需要卡） |
| 只写验收段 | 原需求 | 验收条件的粒度 | 哪几条能打勾、哪几条只能写「感觉」 | 五条里超过两条不可打勾，说明不是卡的问题，是需求还没想清 |
| 硬失败单列 | 同一份交付 | 是否把越权/编造单列 | 平均分是否掩盖了一次硬失败 | 单列之后结论完全不变（说明这次没出现硬失败，不能证明单列没用） |

### 三种结果怎么读

- **两个人判得一样，且都过**：这张卡在这次任务上可用。但不能推广到下一次；材料一变，验收条件要重核。
- **两个人判得不一样**：不是谁对谁错，是那一条没写清。把分歧点改写成更具体的一句，再判一次；不要投票。
- **两个人都判不过，但你说不出哪条不过**：说明验收段写的是愿望，不是条件。回到「可观察」那一条，把「专业」翻译成具体特征。

### 这个检验能推翻什么

它至少能推翻一种常见的自信：**「我心里知道什么是好」不等于「我能把它写成别人能执行的条件」。** 如果你和同事判得不一样，你心里的那套标准就没有被写出来；它在你这儿成立，在别人那儿不成立，而交付最后往往要经过别人。

反过来，如果你们判得一样，也不能证明卡写得好；只能证明这次没有暴露分歧。要证明它稳，得换一份材料、换一个模型、再判一次（这就是 [22](22-evaluation.md) 说的「一次不算证据」，只是缩小到一张卡上）。

## 25.17 术语考古：提示词、任务卡、验收条件

这三个词经常被当成同义词用：「把提示词写清楚一点」「做张任务卡」「验收条件就是提示词里那几句」。它们其实分属三个位置：请求里的文字、人手里的纸、判断交付的标准。

### 提示词

| 栏 | 内容 |
| --- | --- |
| 最早出处 | 英文 prompt 在戏剧、心理学等领域早有「提示、促使」之义；作为人机交互里的常用词，是随聊天式接口形成的**社区与产品惯例**，没有单一发明人，也没有统一规范定义。本文按**社区用语**处理。 |
| 原义 | 交给模型的一段输入，用来诱导或约束它的下一步输出。 |
| 现在被怎么用 | 被当成「模型的操作说明书」「性格设定」「安全策略」，甚至被当成「写完就万事大吉」的那张符。也常把系统指令、附件、历史、检索片段统统叫成「提示词」。 |
| 本文怎么用 | 只指**这一轮请求里由人写的那段文字**，是六类输入之一（[09](09-whats-in-the-request.md)）。它能提高某类输出的概率，改不了材料里有什么、权限归谁、动作做没做。**提示词是条件，不是保证。** |

### 任务卡

| 栏 | 内容 |
| --- | --- |
| 最早出处 | 借自工业、项目管理与看板里的「工单」「作业卡」「任务卡」传统：一张卡承载一个工作单元的输入、约束与完成标准。AI 语境下没有统一规范，本文按**社区与行业惯用语**处理，不指认某一年、某一产品为起点。 |
| 原义 | 一张随任务流转的卡，写清要做什么、用什么、做到什么程度算完，供执行者与验收者共同使用。 |
| 现在被怎么用 | 有时被当成「一段更长的提示词」，有时被当成「角色扮演的开场白」，还有人把它等同于某个产品里的模板按钮。 |
| 本文怎么用 | 人在开工前写的五段式产物：目标、材料、边界、交付、验收。它可以有一部分被抄进提示词，但**验收段通常不进请求**，留在人手里。它不是权限，也不是回执。 |

### 验收条件

| 栏 | 内容 |
| --- | --- |
| 最早出处 | 借自工程、采购与合同管理里的「验收标准」传统：交付前先约定什么算合格。具体起源本文不指认，按**行业与社区用语**处理。 |
| 原义 | 事先约定的、可判断的条件；满足则接收，不满足则退回或整改。 |
| 现在被怎么用 | 常被缩成「我觉得行」「客户说不错」「没有明显问题」；也有人把它写成一段鼓励性的要求，例如「请确保高质量」。 |
| 本文怎么用 | 可观察、可重复、有证据的逐条条件；必须项与加分项分开，硬失败单列。**它必须由第三方能执行，不能由被验收的一方自评。** |

三个词共同的毛病，和 [09](09-whats-in-the-request.md) 那三个词一样：**把条件说成了保证。** 提示词是条件，任务卡是条件，验收条件是条件；保证要靠原文、回执、对照，以及一道不在这张纸上的闸门。

## 25.18 一页速记

| 你遇到的情况 | 先改哪一段 |
| --- | --- |
| 它写得很顺，但把没定的写成了已定 | 边界 + 验收：给「待确认」一个合法位置，并列出禁止出现的词 |
| 它用了作废的旧版 | 材料：写状态与仲裁句，旧版标「已作废」 |
| 它算错了人数、金额 | 材料：写口径与算式来源；验收：写「42 是记录条数，人数为 39」 |
| 它说要发群、要付款 | 边界 + 运行时：卡里写不可做，真正拦住靠权限与审批 |
| 交付物很长，但没法用 | 交付：写形态、长度、字段、位置；验收：写「不超过多少字」 |
| 两个人验收结论不一样 | 验收：把那条改写成可观察的动作，不投票 |
| 不知道要不要让它先问 | 看猜错的代价：可逆便宜就标注默认，不可逆就停下问 |

**五句话带走**

1. 「做好了」不是一种观感，是一组能被第三个人逐条执行的条件。
2. 五段卡对应五个决定；空一段，就有一个决定被模型或默认值代做。
3. 硬约束不许改，可用默认不必问，必须澄清不许猜；未定项原样保留。
4. 示例能固定格式，不能为事实背书；值必须来自本次材料。
5. 提示词不能给权限、不能给回执、不能替代证据；这三件事分别在运行时、原始系统和原文里。

**三道自检**

1. 你把「写得专业一点」写进了验收条件。这算可验收吗？如果不算，至少要把它翻译成哪三样东西？
2. 任务卡里写了「禁止群发」，是不是就不会发出去了？为什么？
3. 你给了一个上次的成品当示例，格式很稳。里面的日期和人数能不能直接沿用？为什么？

1. 不算。「专业」是一种观感，三个人会给出三个结论。至少要翻译成三样可观察的东西：例如长度与分段（不超过 180 字、每段不超过三行）、称呼与语气（统一用「各位同事」、不用「亲/哈/哟」）、结构与字段（日期、人数、集合时间、饮食提醒齐全）。翻译完还不等于「专业」，但它变成了第三个人能打勾的条件；剩下的审美判断留给人，不混进必须项。

2. 不是。卡里写「禁止群发」是一句提醒，能降低概率，改不了权限。真正拦住发送的是运行时的权限校验、审批点和回执；如果发送权限开着，卡上写十遍也挡不住。正确做法是两件事一起做：卡里写清「只出草稿、不进群」，运行时把发送权收走或加一道审批；验收时去原始系统看有没有这条消息，而不是看它有没有说「已发送」。

3. 不能。示例能固定格式，不能为事实背书；它里面的日期、人数、金额、状态都属于「值」，不是「形状」。上次的成品可能写着 42 人、10 月 18 日、雨天改室内，这些值一旦被沿用，就会把作废的、未定的、没发生的事一起带进这次交付。正确做法是把示例里的值涂掉，只留字段和句式；真值从本次材料来，并在材料段标清版本与状态。判据是：把数字全涂掉，示例还能不能固定格式？能，才是格式示例。
