# 23 · Spec Coding 与 Vibe Coding：从快速探索到可验收变更

> **状态**：已完成（初稿）
>
> **本篇定位**：Part V · 场景实作。用「给报名表加个导出」说明什么时候可以边试边改，什么时候要把权限和验收写在前面。
>
> **读法**：跟着四份纸面交付物走一遍：需求、设计、任务、测试；最后拿一张虚构报名表手算一次。

「在报名页加个导出按钮，交给 AI 做吧。」演示时，按钮果然能下文件。但列表只筛了「候补」，文件却包含所有报名，还带上了手机号。按钮不是没做出来，是一开始没人定义它该交出什么、谁有权拿到。

**本篇的问题是：一句「加个导出」要补哪些条件，软件变更才不会靠猜？** 下面是一份独立的虚构案例：为报名管理后台设计**未来**的导出功能，本篇只交纸面材料，不实现、不上线，也不读写真实名单。贯穿全书的**当前市集任务**仍按 v2（周日 14:00，雨天是否改室内待确认；周六的 v1 作废），只整理报名清单和通知草稿，不发送。两件事的授权不可互借。

```text
想试试怎么用 → 可丢弃样稿 → 人确认要不要做成正式功能
                                ↓
Requirements 需求［先定怎么验］ → Design 设计［比方案］ → Tasks 任务［排依赖］
       ↑                                                       ↓
规则有歧义：回需求；未按规则完成：退回相应任务 ← Testing 测试［做验证、留证据］
```

## 1. 初稿 → 澄清：可以探索，不可把探索当承诺

**初稿（未通过的设计提案）：** 「导出当前报名表，可在 Excel 打开，方便分享。」没有说「当前」是屏幕这一页还是筛选出的全部页、哪些字段该藏，也没说报名员能看表是否就能导出。把这句交给模型探索按钮位置没问题；拿去指导对真实数据的变更就不行。

| 做法 | 更适合的情形 | 什么时候要换挡 |
| --- | --- | --- |
| Vibe Coding：用自然语言边提出、边看结果、边调方向 | 用虚构数据画能丢弃的样稿：按钮放哪里、下载前要不要先说明范围 | 接触真实个人资料、共享系统或权限时，先停；样稿不直接搬到正式环境 |
| Spec Coding：以明确规格指导变更并逐项验收 | 权限、筛选和兼容行为不能凭感觉；多人交接要看同一份规则 | 规格有空白时问负责人；能用一页说清就不必堆大文档 |

两个词不是统一的行业标准，也不是非选一个：先用样稿找方向，再用规格锁定要交付的行为。有时两张截图就能澄清「当前」：一张筛选后第一页，一张第二页。

| 澄清对话 | 负责人确认 |
| --- | --- |
| 「能看报名表的人都可以下载？」 | 不行。只给具备该活动导出权限的主办人员；普通查看者不能导出，其他活动的授权不通用。 |
| 「当前报名表」是当前页还是筛选后的整批？ | 本活动中，点下载时**已应用**筛选匹配的全部记录，包括未显示的后续页；未点「应用」的选择不算。以编号从小到大排列。 |
| 「方便分享」要给联系方式吗？没数据怎么办？ | 只给报名编号、摊位名、摊位类别、状态；不含手机号、邮箱、内部备注，缺类别就空着。没有匹配项给提示，不下空文件。 |
| 「要不要群发通知或同步报名表？」 | 不要；不要跨活动合并、批量修改、定时导出或改变原列表。下载后仅供内部整理，不能把功能可用当作分享授权。 |

**复制提示词：**

> 把「给报名表加个导出」写成一页规格。暂不改任何软件，也不用真实报名资料。先问清谁能导出、按哪个活动和筛选范围、允许哪些字段、空结果和失败怎样提示。把已确定、待确认和不做分开。先交需求与可观察的验收条件，再交方案、带依赖的任务和如何验证；未运行的验证明确写「未执行」。

## 2. 修订① · Requirements：需求里先定验收

**目标：** 主办方在内部核对报名时，把活动报名页中符合筛选的记录下载成一份能用常见表格软件打开的 CSV（纯文本表格文件）。用户是有该活动导出权限的主办人员，列表可看权限不能替代导出权限。以下是负责人已确认的本次最小范围，任一项不满足都不算完成。

| 编号 | 可观察的验收条件（此处定义） |
| --- | --- |
| R1 权限 | 本活动有权限才可下载。无权限、只有别的活动权限或权限已被收回的人，不能从出口取得文件或行数据；只把按钮藏起来不算通过。 |
| R2 范围与顺序 | 按点击时当前活动与已应用筛选，导出所有匹配页、每条恰好一次，按编号升序；不含其他活动，不采纳尚未应用的筛选。 |
| R3 字段与可读性 | 列为报名编号、摊位名、摊位类别、状态，按此顺序。手机号、邮箱和内部备注一律不出现在文件中；缺类别留空，中文和名称里的逗号等应能正确打开在同一格。 |
| R4 空与失败 | 没有匹配项时提示「没有符合条件的报名」，不下载文件；导出失败提示可重试，不给错误文件，不报「成功」。 |
| R5 回归 | 导出不改报名、筛选、分页或已有的查看权限；不发送、不共享，不新增批改、定时任务或跨活动导出。 |

若导出量、大表处理时间、下载文件保留期限要进入正式交付，先另问负责人确认并增补验收；这份规格不凭空承诺速度或保留策略。这里也**不**设「只能导出屏幕上看得到的列」这样的模糊捷径，而是用明确允许的列来守界。

## 3. 修订② · Design：选一个不容易漏守范围的方案

| 方案 | 好处 | 代价 / 决定 |
| --- | --- | --- |
| 直接从当前屏幕复制表格 | 快，适合用假数据摆样稿 | 容易漏后续页；如果页面展示个人资料，可能误带。不选作正式导出 |
| 按本活动和已应用筛选，重新取符合条件的记录，只生成允许的四列 | 范围明确；在生成或提供文件的位置实际检查权限、限制活动与字段 | 要做分页边界和权限测试；选为正式设计，暂不引入后台队列或邮件 |

草拟界面：按钮旁注明「导出筛选结果（全部页）」，条件显示以实际已应用状态为准。点击时取得当前筛选；后台按权限允许的活动生成文件。普通人员可以继续按原权限浏览列表；无权导出时既不提供文件，也不返回导出行数据。下载产生内部副本并不是外发许可；文件创建后，也不能靠收回应用权限自动收回某人已经拿到的本地副本。

## 4. 交付 · Tasks：交接时写「依赖谁、交什么」

| 任务卡（拟议，未实施） | 依赖 | 做完应留下的证据 |
| --- | --- | --- |
| T1 · 定批准角色和虚构样表 | 需求 R1–R3 经负责人确认 | 角色对照、活动范围、列定义、样本和预期结果 |
| T2 · 按活动和已应用筛选导出并限制字段、校验权限 | T1 | 可演示的导出行为与文件样本，能对照 R1–R3 |
| T3 · 做按钮范围说明、空结果与失败提示 | T1 可先拟文案；T2 完成后联查 | 正常、空、失败三种状态对应的界面证据 |
| T4 · 用假数据走正常、异常、回归检查 | T2、T3 | 实际观察、证据位置、结果、未验证项；出问题退回相应任务复验 |

## 5. 验收 · Testing：列测试不是跑测试

纸面样本设每页两条。活动甲有 A01 纸舟（正式，书摊）、A02 风铃（候补，类别缺失）、A03 「纸,墨」（候补，手作；名字里有半角逗号），以及 A04 晴窗（候补，插画）；活动乙有 B01 山灯（候补，手作）。筛选甲的「候补」会跨两页。样表另有联系方式和内部备注，但不使用真人数据。

| 场景 | 对照什么和预期结果 | 实际记录 |
| --- | --- | --- |
| 正常：甲的授权者在候补第 1 页下载，未应用的新选择为「正式」（R2、R3） | 文件只有 A02、A03、A04，依序出现；A02 类别格空，「纸,墨」完整留在同一格，只见四个允许列；保留脱敏文件作证 | 未执行；无文件证据 |
| 异常：普通查看者、仅乙授权者、收回甲权限者请求下载（R1） | 三种身份都拿不到甲的导出数据。由测试者记录各次实际结果，不拿「没有按钮」替代拒绝证据 | 未执行；无权限验证记录 |
| 异常：零匹配；模拟导出失败（R4） | 分别看到空结果或失败提示；都无下载，失败也不报成功 | 未执行；无观察记录 |
| 回归：导出前后对照甲的列表，复查查看者原有权限（R5） | 报名、筛选与页码不变，原可查看者仍可查看；无发送、共享或批量修改 | 未执行；无回归证据 |

**失败反例（纸面演示，不是实测记录）：** 如果样本文件只有 A02、A03 并额外出现联系电话列，即使按钮能用，也违反 R2、R3。把可追溯的预期与所见交给 T2，修好后既复查跨页和字段，也复查权限与回归；如果测试者无法模拟失败，就写「失败路径未验证」，不能把它算进通过。这里最终交付的是**规格、设计、任务卡与测试计划**，不是一个已经完工的软件。

**手工练习：** 在纸上列出五条样本记录。盖住第二页，把已应用筛选写在左边、尚未应用的选择写在右边。请朋友只看需求写预期文件，再比对三行四列。然后把「本活动权限」换成「仅乙权限」，问他预期应变为什么；发现歧义就先改需求，不用演示结果倒推规则。

**速记：** 探索做可丢弃样稿；需求先定验收；设计管范围权限；任务排依赖；测试要证据、不是打勾。

### 自检

1. **为什么「按钮用起来顺」不是验收？** 简答：它没证明字段、跨页范围、拒绝无权限或原功能不受影响。
2. **有报名查看权限，就能按本规格下载吗？** 简答：不能；要有这个活动的导出权限，并在实际提供文件的位置核查。
3. **测试表写了预期结果，却没有实际观察，可以报通过吗？** 简答：不可以；只能报告规格和测试计划已交，实际验证尚未执行。
