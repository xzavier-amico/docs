# 16 · 上下文压缩：少带什么，绝不能丢什么

> **状态**：已完成（初稿）
>
> **本篇定位**：Part IV 第 2 篇。学会收短一段长对话，同时保留决定、依据、权限和未决项。
>
> **读法**：先看压缩前后的市集记录；遇到需要交接的长任务，就用后半篇的纸笔核对法。

## 最后一句是「好的」，删到只剩它行吗？

虚构的市集筹备群先讨论日期，再改预算，最后连续冒出许多「收到」。几轮以后，助手看到一份简短摘要：「市集改期，雨天可进室内，预算约 600 元，通知准备就绪。」它比聊天记录短得多，却把雨天设想写成确定安排，也没记住一条关键边界：**只整理报名清单及通知草稿，不发送。** 如果下一轮靠这份摘要交接，短就是短了，事却做错了。

市集原定周六，旧 v1 已失效，现行 v2 为**周日 14:00**，下雨是否改室内仍待确认。本篇另设一条仅供主办方内部核对的虚构预算线：600 元是旧上限，后来讨论过 800 元但没批准，现行上限是 700 元；这不是实际支出，也不授权购买，不写进对外通知。把日期和金额放在同一串对话里，是为了看看压缩时会不会把「曾讨论」「最后批准」「还没确认」都压成一种说法。

**本篇的真问题：怎样省掉旧对话，却不丢掉承诺、否决记录和重新核查的路？**

## 1. 压缩是换一份工作记录，不是给原文盖章

```text
原始材料（按授权留存的 v1、v2、预算确认、任务指示）
                 ↓ 应用或整理者挑选、压缩
交接摘要（现行事实、失效决定、权限、未决、原文位置）
                 ↓ 下一轮先用摘要处理当前任务
遇到矛盾、变更或关键事实？──→ 到有权限的原文逐条核查
                 ↑                          ↓
                 └── 更新摘要，标明取代哪条，复核受影响草稿
```

这张图把摘要与原文分开。摘要是给下一轮用的工作记录，不是额外的权威来源。它可以由人整理，也可以请模型起草、人来核对。为了做到**可找回**，链接或索引要能指到资料的版本与具体位置；为了做到**可纠正**，改口时要能找到被取代的条目，并知道哪些下游草稿曾据此生成。光有一段「以最新为准」的总结，既不能告诉你最新是哪份，也不能帮你找到受影响的段落。

## 2. 五种做法并不等价

| 做法 | 它实际少带什么 | 适合何处；会在哪失手 |
| --- | --- | --- |
| 截断 | 按长度或位置直接砍掉一部分 | 快，适合可丢的尾部或重复内容；不识别承诺，可能连「不发送」一起砍掉 |
| 滑动窗口 | 只带最近若干轮，随对话向前移动 | 适合只接续最近讨论；老决定没被重申时，最近的寒暄会挤走有效批准 |
| 结构化摘要 | 保留按状态分类的条目，省略往返原句 | 方便交接；生成摘要的人或模型可能弄错版本、否定词和例外，关键条目要核查 |
| 引用原始材料 | 在交接里用版本与段落定位代替搬全文 | 保留核查路线；仅有链接不等于本轮读过，失效或无权访问的链接不能当证据 |
| 按需找回 | 需要核证时才把相关原段加入新一轮 | 适合争议或稀有例外；找不到、权限不足或版本不明时，应报告缺口，而不是猜 |

这些做法可以组合：近几轮保留原话，稳定决定做摘要，重要原句附可用的定位。处理敏感信息时，还要先检查是否允许保留；可找回指的是**被允许保留的资料**能重新核查，不是所有资料都该复制进摘要或永久存着。若规则要求不留存某段原文，应注明该段无法回查；确需证据时请有权限的人重新提供，而不是偷偷另存一份。

## 3. 市集的交接卡：把不同地位的句子分开

假设看过这几条原始记录：「v1：定周六」；「预算上限先按 600 元」；「改为周日 14:00，见 v2；雨天是否换室内待确认」；「800 元能不能批？」；「不批 800，现行上限 700」；「只整理报名清单及通知草稿，别发」；最后是许多「收到」。可核对的压缩不是把这些句子取平均，而是分类后留下必要状态。

| 交接栏目 | 该留下的短条目 | 回查哪里、影响什么 |
| --- | --- | --- |
| 生效事实 | 周日 14:00，以 v2 为准 | v2 的时间条款；影响通知时间以及任何按日期整理的记录 |
| 失效或否决 | v1 周六失效；600 元旧上限已替代；800 元提案未批准 | v1 与 v2 的改期记录、内部预算确认；避免把旧数字或提案当现行规则 |
| 内部决定 | 上限 700 元；不是实际支出，不授权购买，也不对外写 | 内部预算批准那条记录；只给有权限处理预算的人核查 |
| 未决 | 雨天是否改室内待负责人确认 | v2 的雨天条款；草稿写待确认，不填肯定的地点 |
| 交付边界 | 只整理报名清单及通知草稿，不发送 | 用户本轮任务指示；任何成品版式都不意味着获准发送 |

实际工作中，「预算批准那条」最好换成可定位的文档名和段落，且标明谁确认、何时有效。联系人等个人资料不应进通用交接卡；授权工作区已有的必要名单，可以按权限单独取用。交接卡也不宜一压再压：如果第二版只根据第一版摘要重写，就可能把第一版漏掉的条件永久传下去。有变更时最好回到相应原文，把旧条目标失效，写清现在用哪条，再比对受影响的草稿。若雨天仍未确认，压缩后的新版本也继续写待确认，不能靠删掉这行来消除不确定性。

如果多人轮流接手，同一个条目同时冒出两个版本，不要把其中一份直接覆盖成「最新」。例如有人在交接卡上写「700 元上限」，另一人把报销范围缩写成「700 元场地费」。先回预算批准原文：它确认的是总上限，还是指定用途？没有写用途就不要补。核定以后标清哪些草稿用过错误摘要，以及仍有哪些人需要重查。对影响较大的误读，留下一句更正说明比仅替换数值更有用：接手人知道哪里错、为什么改，才不会复制旧副本再改坏。相反，如果改的只是卡片标题的措辞，就不用重新整理名单。这是在保住纠错能力的同时，不让每次更正都变成通篇返工。

## 4. 手工练习：盖住原话，交接还能过关吗？

用纸抄下上一节的原始记录，另写一张不超过六行的交接卡。让另一人只拿交接卡填写通知时间、雨天说明、预算状态和允许动作，然后打开原始记录逐项核对。除了「答案是否一样」，还要检查：原文是否真支持这个答案，凭交接卡能否找到这段原文，以及有没有把内部信息带进对外草稿。

**参考结果**：收卡的人应答出「周日 14:00」「雨天是否改室内待确认」「700 元上限仅供内部核对，800 未获批」「只整理清单和草稿，不发」。再故意把摘要改错一处，例如写「室内已确认」。修正时先回 v2，改回「待确认」，找到草稿里受到影响的句子，核查是否还有副本使用错条目。若你只能改掉交接卡、找不到已生成的通知草稿，流程只做到了更正记录，未做到纠正产物。

这是验收摘要而非比字数。几句寒暄、重复确认和过时的样式尝试通常可以丢；做过什么、为什么不做某项、接下来谁确认，往往才是下一轮要用的。短摘要适合接续工作，不适合充当发生过什么的唯一档案。

## 5. 别把少读内容同少算一遍混在一起

**压缩内容**是下一轮少带文本，信息可能丢失；**前缀复用**是应用或服务在满足条件时复用相同输入开头的计算，这些内容逻辑上仍在模型的输入里。前者要验关键事实和权限制约有没有保住；后者要看是否命中以及产品的计费和算力实现，命中也不会纠正旧日期。重写输入开头以放入摘要，还可能让原来可复用的开头变了。两者都不是跨会话的个人记忆。

**速记**：过程可缩，决定不混；未决要留，权限不省；重要信息能回原文，原文变了能修到草稿。问清是谁整理、下一轮看到哪份、压缩省了什么、错了能否改回来。

**自检（含简答）**

1. 摘要写「讨论室内方案」，草稿写「改在室内」可以吗？**不可以。** 讨论不是批准，回查 v2 后应写待确认。
2. 需要保留 v1 全文在每轮输入吗？**不需要。** 明记 v1 失效；有授权且需要对照时再定位旧原文。
3. 前缀缓存命中，说明摘要保住了纪律吗？**不说明。** 缓存处理的是计算复用，摘要内容必须单独验收。
