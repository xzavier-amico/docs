# 08 · CPU 与 GPU 推理：快在什么地方，慢在哪里

> **状态**：已完成（初稿）
>
> **本篇定位**：看懂一次推理的等待发生在哪里，再判断换设备、整理输入，还是换服务更有用。
>
> **读法**：先看时间线，圈出你遇到的「慢」；如果正在选本地还是云端，直接看第四节，再做纸面练习。

## 1. 同一份通知草稿，哪一次更快？

在这个**虚构场景**里，社区市集原定周六，旧通知 v1 已失效；现行 v2 改为**周日 14:00**，雨天是否改室内仍待确认。运营同事让 AI **只整理报名清单、起草通知，不发送**。她在笔记本上打开本地工具，又用不含个人信息的同一份示例材料试了云端服务：本地较早开始出字，但一点一点往外蹦；云端先空白了一阵，出字后却很快写完。另一个同事说：「云端用的不是更快的 GPU 吗，怎么还要多等？」这里只是情景设定，并非性能实测。两套工具若未确认用的是同一模型版本，也不能把体验差异全归给硬件。

本篇的问题是：**即使跑的是同一种模型，换机器为什么也不一定每一项都更快？** 先把「快」拆开。一份草稿更早露出开头、从开头到结尾写得更快、多人一起交活儿时整队处理得更多，是三件事。

```text
提交 → 应用准备材料并发出请求 → 服务排队
                                 ↓
                           模型读入（Prefill）
                                 ↓
                           产生首个 Token ───→ 界面开始显示文字
                                 ↓
                           逐步续写（Decode） → 界面不断更新
                                 ↓
                           生成结束 ─────────→ 界面显示完整稿
```

图是简化的顺序，不是每段等长。有的应用还会读取附件、查资料、首次加载模型；网络和界面也可能攒几段再显示。Token 是模型处理文字的基本单位，不一定等于一个字。**首 Token 等待（TTFT）**在这里用端到端口径：从发起请求到收到首个输出 Token；它不等于 Prefill 耗时。用户能直接看见的是首段文字，既可能晚于服务产出首个 Token，也可能一次显示好几个 Token。读入与续写才是图中的模型计算阶段；排队是服务调度的一段，不是模型在「读得慢」。

| 说「慢」时在说什么 | 它回答哪个问题？ | 看见什么还不能下结论？ |
| --- | --- | --- |
| 排队等待 | 请求到了服务，却还没轮到开始做模型计算，等了多久？ | 光看首段文字来得晚，不能区分排队、附件处理、传输或读入 |
| 首 Token 等待 | 提交后多久收到首个输出 Token？ | 开头来得快，不代表后面也快；界面首段只是近似观察 |
| 单次生成速度 | 开始输出后，这条回答续写得多快，例如每秒产生多少输出 Token？ | 界面一口气刷新一段，不代表模型一口气算出一段；长稿即使写得快也可能更晚完成 |
| 端到端总时长 | 从提交到整份草稿可用，等了多久？ | 同样用时，一份写了几句、一份写满两页，不能据此比较生成速度 |
| 服务吞吐 | 同样长的一段时间里，整个服务完成多少请求，或产出多少输出 Token？ | 总产量升了，不代表任何一位用户的首段或整稿更早到 |

比如服务把多位用户可同时处理的工作凑在一起做，叫**批处理**。这样可能让设备少闲着，同一段时间交更多稿；但有些请求可能更晚轮到，正在生成的请求也可能分到较少资源。到了繁忙时段，同一个服务完全可能出现「总吞吐更高，我的首段反而更迟」。反过来，一个人独享机器时感觉很快，也不代表它能同时照顾一群人。

## 2. CPU 和 GPU 分工不同，读入和续写也不同

把推理想成运营组整理报名表。**CPU** 像擅长处理不同事项的几位干事：能并行做事，也擅长随时切换任务、判断下一步。**GPU** 像一排能同时按同样规则处理许多格子的工位，特别适合把大量相似运算一起做。这个类比只用来理解分工：GPU 不会替人判断雨天方案，CPU 也不是只能一个人一格一格算。常见带 GPU 的运行方式里，CPU 往往负责接请求、分词、调度等，GPU 承担大块模型计算；也有只用 CPU 或把模型计算分摊到两边的方式。

```text
常见分工（以装有独立 GPU 的机器为例）
CPU ＋ 主内存：接请求、分词、安排工作 ──→ GPU ＋ 显存：并行做大块模型计算
                接收并交回结果       ←──                   产出结果
```

以常见逐 Token 生成的模型为例，**读入（Prefill）**处理本轮输入，比如任务指令、现行 v2 和必要的报名材料，算出第一个输出 Token 的候选。输入里的许多位置可以在同一层中一起处理，GPU 往往能发挥并行优势。**续写（Decode）**则要基于已经选出的 Token 来预测下一个：对同一条回答，先选出上一个 Token，才能接着算下一步。每一步里面仍有大量并行运算，也可以同时推进不同人的回答，但常见方式并不是给同一篇通知多派几组工位，就让它们各写一段再拼起来。

小模型、材料短、一次只跑一份时，本地 CPU 有机会够用，尤其当比较对象还要经过网络和排队；若已有合适的 GPU，模型放得下、工作也足够大，常能加速不少计算。大模型通常要读更多权重（模型学到的数字），并不能只看「有 GPU」就保证运行。即使同一台机器，读一大份材料和慢慢写长稿也可能卡在不同地方。

## 3. 桌面够不够大，取料够不够快

**容量**像工作台能同时摊开多少东西；**带宽**像每秒能把多少材料送到工位。前者问「装不装得下」，后者问「搬得够不够快」。CPU 通常使用主内存，独立 GPU 通常使用自己的显存，有些设备则共享内存。除了模型权重，还要给临时工作空间以及生成时留下的中间结果（下一篇的 KV Cache）留位置。**能把模型装进去，不等于能把一次长输入和多份并行请求也一起装进去。**

| 可能碰到的墙 | 表现与可考虑的办法 | 边界 |
| --- | --- | --- |
| 容量不够 | 大模型一加载就失败，或单份能跑、长材料和多人同跑就吃紧；可先试更小的模型，删掉无关输入，减少同时进行的任务 | 多买容量不直接等于出字变快；分一部分到主内存可能装得下，却增加搬运等待 |
| 数据搬不够快 | 在许多低并发的续写场景，反复读取权重和中间结果比做运算更容易拖住节奏；可考虑更适合的硬件或表示方式 | 峰值算力再高也不能替代带宽；并非所有模型、设备和并发条件都卡在这里 |
| 算不够快 | 大量相似运算有时能让 GPU 的工位都忙起来，读入阶段尤其常见 | 短小任务未必能发挥优势；实际还看模型、软件实现、设备之间的搬运和当时的负载 |

听到「**量化**」时，可以想成用更少的刻度记数字：常见做法是降低权重的数字精度，减少模型占用和要搬运的数据；也有专门对 KV Cache 的量化，两者不是一回事。它可能使模型能在原来的机器上放下，或在硬件和软件支持时变快；也可能因转换开销或实现不合适没变快，并可能损失输出质量。别只看草稿是不是通顺：用同一份报名样例核对有没有漏行或合并错人，有没有把「雨天待确认」改写成「已决定移到室内」。不要把容量收益直接报成速度收益。

## 4. 本地、云端还是混合？先划材料和账单的边界

假如报名表包含姓名、电话等个人信息，而通知草稿其实只需要现行时间和待确认事项，就没有必要把原表一起交给云端。先问哪部分获准离开自己的设备或组织，再问质量和时间，最后算总成本。

| 方式 | 市集任务怎么分 | 隐私与成本边界 |
| --- | --- | --- |
| 本地 | 在受控设备上清理名单、写草稿；小模型能否胜任要用样例验收 | 真正在本地处理才不必把原表交给云服务，仍要查应用遥测、同步备份、插件和设备访问权限。不一定有按次费用，但有设备、电费、维护与等待成本 |
| 云端 | 在组织允许时，提交获准外传的最少材料；云端可提供本地放不下的模型或更高的服务容量 | 上传前核对留存、日志、训练使用和访问约定；计费可能按用量或订阅，别忽略反复提交、重试和网络等待 |
| 混合 | 在本地整理原始名单；只把获准外传的 v2 规则和必要的去标识信息交给云端起草，回到本地做最后核对 | 删了姓名也未必去识别成功，少见的组合信息仍可能识别个人；多了两边交接、复核、两个环境的成本，不保证更快更便宜 |

这三种做法都**不授予发送权限**。假如云端只能拿到公开活动信息，就只请它写不含个人资料的通用草稿；假如小模型总把报名行对错，即使它很快，也应改用经批准的方案或让人核对。比较的是一份**合格草稿**的总耗费，而不是一次看起来很快的回答。

## 5. 手工练习：做一张性能诊断卡

不用运行模型。把纸分成四格，写下「提交到看见首段」「首段到整稿」「同一时段共完成多少合格稿」「还缺什么证据」。对照以下三个场景，把已知的现象归到格子里，再写要先查什么。不要从现象直接写「GPU 不行」。

1. **只换材料长度**：同一服务，同样要求短草稿，一份给必要清单和 v2，另一份又附上无关的旧群聊，首段似乎更晚。
2. **只换输出要求**：第一段出现得差不多，但一份要附逐条解释，等整稿明显更久。
3. **只换使用时段**：大家同时核对时，同样长的一段时间里完成的稿子更多，但有的人首段来得晚。

**参考填法**：第一种先查附件准备和读入，做对照时只去掉无关历史，不丢必要名单、规则版本或权限约束。第二种先看输出长度，别急着判定每个 Token 都变慢，把两份输出约到同等长度再比较。第三种把「全组完成更多」与「个人首段变迟」分开记；想判定是不是排队，还得有服务端的分段记录。

若要把练习变成实际比较，先用虚构或获准的样例，尽量固定模型版本、材料、输出要求和界面，记录并发与首次加载条件，不拿一次偶然结果下结论；对不上这些条件，就标作两套产品的体验比较，不声称测出了 GPU 的单独作用。

## 一页速记与自检

- **先问慢在哪**：排队不是 Prefill，首段早不代表整稿早，多人吞吐高不代表单人快。
- **再问卡什么**：容量管装下多少，带宽管搬运多快，算力管能做多少运算；量化不是测速结果。
- **最后问能不能交**：按 v2 核实时间，保留雨天待确认，只交清单和草稿。隐私、质量和总成本不随出字速度自动改善。

1. **首段来得晚，能否直接说 GPU 读入慢？** 不能。可能是网络、附件、排队、首次加载、读入或界面缓冲；要看分段记录。
2. **机器加了显存，模型终于装得下，为什么续写不一定加快？** 容量解决放置，续写还可能受带宽、计算和调度约束。
3. **通知不需要报名者电话，云模型又写得快，该把整张表上传吗？** 不该。隔离名单、只送获准且必要的资料；用同一验收要求比较合格草稿。
