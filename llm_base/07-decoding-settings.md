# 07 · 推理设置：哪些旋钮改变输出，哪些不会

> **状态**：已完成（初稿）
>
> **本篇定位**：区分怎样选下一块文字、何时停笔、交付长什么样，以及哪些问题根本不能靠调整生成设置解决。
>
> **读法**：先用同一组纸片试三个旋钮，再用末尾的症状表选做法；不必找齐工具界面里的每个选项。

## 一份低温、规整、但是错误的草稿

你想让给摊主的通知别太花哨，便把生成的随机性调低。应用返回一份完整表格，语气也稳定，每次却都把周六写成活动时间。它的确「更稳」了，只是很稳定地用了旧资料。也可能是表格时间完全正确，最后一栏却因长度上限没有输出。这些症状来自不同的地方。

虚构市集原定周六；现行 v2 为**周日 14:00**，雨天是否改室内待确认，旧 v1 已失效。任务只整理报名清单和通知草稿，不发送。时间、雨天状态和不发送是硬条件；开头写「各位摊主好」还是「摊主朋友们好」，才有商量的余地。

**本篇的真问题：想让回答更稳、更有变化或更短，该动哪个设置？** 先看旋钮插在哪一步。

```text
应用交给模型：指令 + 有效材料 ──→ 模型给下一步候选打分
                                         ↓
                           调整候选分布或取舍：温度、Top-p、Top-k 等
                                         ↓
                             选择下一块，接回已生成的前文
                                         ↓
                           达到停止条件？ ── 是 → 停笔并验收
                                  └── 否 → 继续给下一步候选打分

结构约束可在部分产品的生成过程中参与限制候选；也有产品在输出后检查。
```

图只是常见生成环节的示意，并非某产品的选项顺序。平常说的「调参数」还可能指训练或模型权重；这里谈的是**使用时的生成设置**，不会把新公告写进权重，也不会增减应用权限。

## 用一组候选弄懂 Temperature、Top-p 和 Top-k

假设草稿已经写了「欢迎来到周末市集」，接着要写一句副标题。把四张教学卡按基准机会从高到低排好。以下数字和条形是**人为示意**，不是实测；真实模型按 Token 选择，并不是把每个副标题都当成一个 Token。我们用短语只是为了便于一眼看出区别。

```text
逛摊指南    50%   ██████████
入场提醒    25%   █████
周末好去处  15%   ███
摊主小贴士  10%   ██
```

| 旋钮 | 在同一组候选上会怎样 | 哪些事它没有做 |
| --- | --- | --- |
| **Temperature（温度）** | 降低温度会让高分项更占优势，第一条更常被选中；升高会让分布趋平，低分项更有机会。单独调正温度通常不改分数高低的排序 | 不负责判断「逛摊指南」更符合事实，也不直接规定只剩几个候选 |
| **Top-p** | 从高到低留下累计机会达到门槛的最小一组（含跨过门槛的那项）。此处单独用 `p = 0.80` 时，前两条合计 75% 不够，要加第三条，才有 90% | 不是每项都要超过 80%，也不是只取前 80% 的候选个数 |
| **Top-k** | 直接留下分数靠前的固定数量。此处单独用 `k = 2`，只保留「逛摊指南」与「入场提醒」 | 不管这两项合起来占 75% 还是别的比例；候选少不表示事实更正确 |

筛过候选后，若采用采样，通常在剩下的候选里重新分配机会再抽，保留下来不表示一定选中。比较三个旋钮时，每次从同一基准重来；如果先降低温度，Top-p 可能用更少的候选就能达到门槛。多个设置一起使用的处理顺序、允许范围和默认值因产品而异。有的界面用「更有创意」组合多个预设，有的连 Top-k 都不提供。不要把例子的数字当推荐配方。

## 结束、格式和预算是另一组问题

| 设置或手段 | 适合处理什么 | 反例：它不会保证什么 |
| --- | --- | --- |
| **最大输出长度** | 给生成量设上限；不同产品的限制单位和包含范围不尽相同 | 太小会截在名单中间；把上限放大也不会迫使它填满，更不是准确的字数要求 |
| **停止条件** | 在输出到结束标记、指定片段（若支持）或满足其他条件时停下来 | 把一个正文常用词当停止片段，可能提前停在雨天说明之前；结束不等于任务做完 |
| **结构化输出** | 需要固定字段、类别或格式供读者和后续流程使用；不同产品可在生成时强约束，或在事后核验 | 「日期」栏填了周六，格式仍可能完全正确；字段齐全不能证明事实齐全 |
| **重复惩罚** | 一些产品通过降低已出现片段被选中的机会，减少无意义的反复 | 调得太强，可能使表里本该反复出现的品类或时间被奇怪地改写；也不能可靠去除重复报名 |
| **推理预算** | 部分产品可限制或引导模型在较难的问题上投入多少推理工作；有的以档位而非数值提供 | 增加预算可能多花时间或费用，不保证答案更长、更准，也补不出还没确认的雨天安排 |

有些产品允许固定 **seed（随机种子）**，大体是让采用随机选择时可以从同一状态出发。要做可比的重复试验，还要尽量固定输入、模型版本、设置和服务环境。应用取回了不同资料、服务更新、后端执行存在差异，都可能改变输出；同 seed 不等于跨环境复现。低温通常减少变化，但并不自动等于逐字一致。

## 手工练习：把「稳」分别写成三项验收

先拿四张副标题卡做两次筛选。第一遍按 Top-k 留前两张，第二遍把四张放回，按 Top-p 的 80% 门槛留前三张。再假定产品不用采样、总挑基准最高的一张，比较三个结果：**限制候选**和**选中谁**并不是同一件事。

然后做一张两栏任务卡。左栏写「不允许变」：现行 v2 的周日 14:00、雨天是否改室内待确认、旧 v1 无效、不发送。右栏写「允许变」：称呼、语气、副标题。给下面三张交付贴上不通过的理由：

1. **日期周六、字段齐全、措辞每次相同。** 格式和稳定性可以通过，事实失败。先看是不是实际送了 v2，不应再把温度往下调当修复。
2. **日期正确、措辞自然，却漏了待核行。** 检查是否长度上限过小、任意停笔或指令漏列交付项；回对照报名原表，不能以语气好作替代。
3. **公告事实都对、文件标成「草稿」，应用却已实际发送。** 是权限与执行边界失败，不是文本风格问题。清楚区分启用工具与生成草稿，不给无关的发送权限。

真正试用时，每次只改变一个因素，用同一材料重复几次。可以把两种风格的草稿交给同事盲看，但先验日期、雨天状态、名单完整性和未发送，再比较是否更好读。否则可能把一次抽到的好文案误当成某个设置的稳定效果。

## 边界与速记

| 想改善什么 | 先动哪里 | 注意代价或验证方法 |
| --- | --- | --- |
| 输出更一致 | 固定依据和交付要求；有相应设置可测试较低温度 | 多跑几次看是否相对一致；错误也可能一起稳定下来 |
| 有更多文案备选 | 仅对标题、称呼等允许变化处做多案比较 | 创意方案变多，筛选成本也会上升；硬事实仍逐条锁定、核验 |
| 阅读更短、更好扫 | 写清交付优先级和格式，必要时再设长度上限 | 检查截断及缺行，别牺牲风险提示和待核信息 |
| 日期或雨天状态更准确 | 找现行来源，核对应用实际使用的材料和草稿 | 低温、结构正确和事实正确是三件事；没有证据的地方留待确认 |

**速记：** 温度改变候选机会，Top-p 按累计机会画线，Top-k 按名次画线；长度和停止条件管停笔，结构管形状，事实靠证据，权限靠应用。先认清哪件事不合格，再找对应旋钮。

### 自检（含简答）

1. **用上面的基准机会，`p = 0.80` 为什么不只保留前两项？** 这两项合计 75%，还未达到门槛，要把第三项一起纳入。
2. **日期栏固定存在、温度也很低，能不能跳过事实核验？** 不能。可能每次都在正确的栏里填错时间；要看有效的 v2 原文。
3. **想要短通知，可以把最大输出长度设得很小吗？** 硬上限能控制最多生成多少，但可能截断通知或名单；先指定简洁要求，再检查完整性。
