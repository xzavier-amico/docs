## 03.1 引子：四十个汉字，两次都只差一个

（虚构对话，示意；用来提问，不是任何产品的实测记录。）

今天 10 月 8 日，秋季团建的 B 方案还差最后一道判断。B 场地人均 310 元，39 人参加，包车 3,600 元，预算总额 15,600 元。我把这三个数发给一款聊天产品，问：

> B 方案超预算了吗？只回答超没超。

它答：**「人均 310，39 人合计大约一万五出头，加包车 3,600，和 15,600 差不多，应该没超。」**

这句话每一段都几乎对：310×39 确实是一万二千出头，加 3,600 确实是一万五出头，和 15,600 确实「差不多」。唯一错的是最后两个字——**「没超」**。实际是 15,690，超了 90 元。

同一天，我又写了一段正好四十个汉字的活动通知，标点不计：

> 名单四十二条，去重后三十九人；预算一万五千六百，场地按三十九人乘二百六十算，包车三千六百。

我问它：「三」在这段话里出现了几次？它答：**四次。**

我自己数：第 10、25、37 个字，**三次**。我又问「十」出现了几次，它答三次；实际是第 4、11、26、33 个字，**四次**。

两次都只差一个。这比错得离谱更麻烦：**错得离谱你会立刻去核，只差一个你会点头。**

更刺眼的是，它刚刚还替我写了一份结构完整的核对清单，分点、编号、连「先核版本再核金额」的顺序都对。一个能写出核对流程的东西，为什么在流程里最简单的两步上失手？

## 03.2 唯一真问题：它到底有没有「数」这个动作

本篇只回答一个问题：

> **为什么它能写代码，却数不对一段话里有几个「的」？**

常见的三种解释都不成立：

- 「它不够聪明」——它能写出可运行的代码，也能把一份通知改得比原稿清楚，这不是「不够聪明」能解释的。
- 「训练数据里没有这类题」——如果只是见得少，多给同类例子就该稳定变好；但同一道题换个说法，答案就会变，说明缺的不是例子。
- 「它太粗心」——粗心是一种可以回头的状态：看漏了可以重数，写错了可以改。它没有「回头」这个动作。

把这三句拿掉之后，剩下的解释只有一条，而且是从 P1 直接推出来的：

> **P1 说，它每一次只决定「下一个片段最可能是什么」。计数要求「逐个走过每一个位置，并累加」；算术要求「逐位对齐，并进位」。这两件事都需要一个能保存中间状态、能回头、能循环的过程，而 P1 只有一条单向的续写链。**

所以更准确的说法不是「它数错了」，而是：

> **它没有「数」这个动作。它是在生成一个「看起来像计数结果」的片段。**

这句话就是本篇的反直觉命题。它由 P1 推出，不依赖任何厂商的说法。它也有明确的失效条件：**当任务可以被改写成「整块匹配」而不是「逐个遍历」时，这个结论就不适用**——判断某句话里有没有出现某个词、把一段话分类、把一句话改写得更客气，这些不需要数，它可能做得很好。一旦要求给出「几次」「第几个」「差多少」，就回到了「遍历 + 累加」或「对齐 + 进位」，结论重新成立。

顺带把定位问题问完：

- **第 2 问：它这一轮看见了什么？** 它看见的不是这段文字，而是这段文字被切碎后的一串编号。这一点是下面几节要展开的全部内容，也是本篇的地基。
- **第 4 问：我拿什么独立验证？** 计数用「自己数一遍」或「用会数的工具」，算术用「自己列竖式」或「用会算的工具」。它自己的第二次回答不算验证——那只是又生成了一遍。

**本篇的判定线只有一句：凡是答案要求「逐个数」或「逐位进位」，就不要向它要结果，只要它的草稿；结果从工具或人这里来。**

## 03.3 一张图：文本先变成编号，它才看得见

先把一条最普通的链路画出来。这里没有工具调用，只有一次问答，但「谁在做什么」已经分了四层：

```text
人：写下「B 方案 39 人，人均 310，加包车 3,600」
        │
        │ 一段连续的文本
        ▼
应用：拼系统指令、历史、材料、问题；决定这一次送什么
        │
        │ 仍然是文本（可能还夹着附件抽取出来的文字）
        ▼
分词器：按词表把文本切成 Token，再逐个换成编号
        │
        │ 编号序列：4821  9137  1203  8452 …
        ▼
模型：只看见编号；每次选出下一个编号（P1 续写）
        │
        │ 编号序列
        ▼
分词器：把编号解回文本
        │
        ▼
应用：显示；或者把「要用计算器」的提议交给运行时（P5）
        │
        ▼
人：自己按 39×310+3,600 核一遍，再决定签不签字
```

这张图里最容易被跳过的是中间那一格。**分词器不是「把文字读进去」的通道，它是一次替换**：把一段人可以读的字符串，换成另一串只对模型有意义的编号。替换发生在模型之前，而且是单向的——模型内部再没有任何一步会「重新看一遍原文」。

### 四个角色，各自拿得到什么

| 角色 | 它拿到的是什么 | 它拿不到什么 | 出了问题先查谁 |
| --- | --- | --- | --- |
| **人** | 目标、原文、验收权、签字权 | 模型内部的取舍过程 | 目标说清了吗？验收标准是什么？（25、28） |
| **应用** | 本轮的材料清单、顺序、长度预算 | 模型会不会照着做 | 该送的送进去了吗？顺序对吗？（05、09） |
| **分词器** | 原始文本、一份固定的词表 | 语义、上下文、这段文字想干什么 | 是哪个分词器？版本对吗？（本篇） |
| **模型** | 编号序列 | 字符、笔画、列、数位、位置索引 | 这是不是它能力之外的任务？（02、04） |
| **工具 / 运行时** | 明确的入参、可执行的规则 | 模型为什么这么想 | 入参对吗？回执拿到了吗？（16、17） |

分词器通常跟着模型一起发布，由应用在送模型之前调用。它既不是「应用的可配置项」，也不是「模型的器官」：**换模型常常等于换分词器，而换分词器会改变同一段话的 Token 数**。这一点在 03.7 会直接变成钱的问题。

### 一张示意词表：编号不是数量

下面这张表是为了讲清楚「替换」而编的，**编号全部是示意，不对应任何真实分词器**：

| 词表里的片段（示意） | 编号（示意） | 这个表项实际覆盖什么 |
| --- | --- | --- |
| 团建 | 4821 | 两个汉字 |
| 预算 | 9137 | 两个汉字 |
| 39 | 1203 | 两个数字字符 |
| 310 | 8452 | 三个数字字符 |
| ▁包车 | 6620 | 一个前导空格 + 两个汉字 |
| ， | 29 | 一个全角逗号 |
| ☔ | 118 | 一个天气符号的基础码位 |

这张表要读出三件事：

1. **编号是任意的。** 4821 不比 1203 大，也不比它重要；编号之间没有大小、顺序或算术关系。模型拿到的是一串索引，不是一串数量。
2. **一个表项覆盖多少字符，是不固定的。** 可能是一个字、两个字的常见组合、半个字的字节片段、一整个词、一个标点，或者「空格 + 词」。
3. **编号会先被换成向量，再进模型。** 从这一步起，字符的形状、笔画、先后位置都不再以「字符」的形式存在。模型对「团建」有语义，但它没有一步叫「把 4821 拆回两个字，再数一数」。

表里那个「▁」只是「词首空格」的可见占位符；有些分词器这样标记，有些用别的办法，还有些根本不把空格单独看待。**示意不等于通用。**

## 03.4 机制：切分与合并，一次讲透

### 分词器做的四步

不管哪一家，分词器大体都走这四步。顺序不能换，换一步结果就不同：

| 步 | 做什么 | 一个常被忽略的后果 |
| --- | --- | --- |
| ① 规范化 | 统一全角半角、统一 Unicode 组合形式、处理大小写、压缩连续空白（不同分词器做的项目不同） | **字符数在进入模型前就可能已经变了**；有些规范化还是不可逆的 |
| ② 预切分 | 先按空格、标点、数字、字母把文本粗切成小段 | 切法本身带语言偏好：英文靠空格，中文没有空格可用 |
| ③ 合并 | 按训练时学到的顺序，把相邻片段合成更大的片段 | 合并表是固定的，**编码时不会重新统计这段文本的频率** |
| ④ 查表 | 每个片段查词表，换成一个编号；查不到就退到更小的片段或字节 | 词表大小固定；加新词要连模型的输入层一起改 |

第 ③ 步最容易被误解。很多人以为分词器每次都在「分析这段话里什么组合最常见」。不是。**合并规则是训练分词器时一次学定的，之后每次编码只是照着这张已经排好序的合并清单往下套。** 同一段文字，今天切和明年切，只要分词器没换，切法就一样；换了分词器，切法立刻不同。

### 四种粒度：一个单位到底有多大

「粒度」问的是：**词表里的一个表项，最小可以小到什么、最大可以大到什么。** 四种常见选择：

| 粒度 | 一个单位是什么 | 词表规模（量级，示意） | 强在哪 | 弱在哪 |
| --- | --- | --- | --- | --- |
| **字符级** | 一个字符 | 几千到几万 | 任何字都能表示，不会有「没见过这个字」 | 序列长；一个汉字一个单位，词义要靠上下文自己拼 |
| **词级** | 一个词 | 十万到上百万 | 单位本身有语义，序列最短 | 词表爆炸；没收录的词只能退回「未知」，形态变化要每种都收 |
| **子词级** | 反复出现的片段 | 几万到几十万 | 折中：常见词整块，生僻词拆开 | 切法不唯一；边界对人不透明 |
| **字节级** | 一个字节（0–255） | 从 256 起步，合并后仍不大 | 任何文字、任何符号都能表示，不会出现「未知」 | 序列最长；一个常用汉字通常占 3 个字节，可能被切成「半个字」 |

四种粒度不是四个品牌，也不是四代技术，而是四种设计取舍。真实分词器常常是混合的：**以字节为起点，再在上面做子词合并**。这就是「字节级 BPE」这个词的来历，也是它最容易被说错的地方。

### 算法和粒度是两个轴，不要并成一张表

| 名字 | 它是粒度还是算法 | 一句话机制 | 常见误解 |
| --- | --- | --- | --- |
| **BPE** | 算法 | 从最小单位开始，反复把「最常相邻出现的一对」合并成一个新符号 | 以为 BPE 是一种固定的词表大小 |
| **字节级 BPE** | **两件事叠在一起**：字节粒度 + BPE 合并 | 起点是 256 个字节值，再按频率合并；因此任何字符串都能表示 | 以为它是与 BPE 并列的第三种算法 |
| **WordPiece** | 算法 | 从字符开始，按「合并后对语料概率的提升」挑合并对；词内续接常用双井号前缀标记 | 以为它只能用于英文 |
| **Unigram** | 算法 | 从一个大候选表开始，反复删掉「删了最不伤语料概率」的片段；编码时选整体概率最高的切法 | 以为子词只有 BPE 一条路 |
| **SentencePiece** | **工具体系，不是并列算法** | 直接在原始文本上训练与切分，空格也当作符号处理；它支持 BPE 与 Unigram 两种模型 | 把它当成第三种算法，或当成某个模型专用的文件格式 |

这张表只要求记住一句：**「字节级」回答「起点有多小」，「BPE」回答「怎么往上合并」。** 两个词同时出现，不是在说两种东西，而是在各回答一个问题。SentencePiece 则是把规范化、训练、切分打包在一起的一套实现，它内部可以跑 BPE，也可以跑 Unigram。

### 手工演示：三轮合并，字是怎么被「吃掉」的

下面是一个**示意语料**，只有四个词，频次是编的。约定两条：按词边界切开后统计，不跨词合并；次数相同时取先出现的对（真实实现的 tie-break 各有各的规则，这里只为了让演示能往下走）。

| 片段（示意） | 出现次数 | 初始切法 |
| --- | --- | --- |
| 团建 | 3 | 团 + 建 |
| 建组 | 2 | 建 + 组 |
| 团队 | 2 | 团 + 队 |
| 预算 | 1 | 预 + 算 |

第 0 轮，统计所有相邻对：

| 相邻对 | 次数 |
| --- | --- |
| 团 + 建 | 3 |
| 建 + 组 | 2 |
| 团 + 队 | 2 |
| 预 + 算 | 1 |

然后一轮一轮合并：

| 轮次 | 合并哪一对 | 次数 | 新符号 | 合并后还剩哪些对 |
| --- | --- | --- | --- | --- |
| 1 | 团 + 建 | 3 | 【团建】 | 建+组 2、团+队 2、预+算 1 |
| 2 | 建 + 组 | 2 | 【建组】 | 团+队 2、预+算 1 |
| 3 | 团 + 队 | 2 | 【团队】 | 预+算 1 |

三轮之后，语料变成了三个整块：【团建】×3、【建组】×2、【团队】×2，外加还没合并的「预」「算」两个单字。如果继续合并，「预+算」也会变成一个块。

现在来看最关键的一步。**「建」这个字在原始语料里出现了 5 次（团建 3 次、建组 2 次）。但编码这段文本时，它一次都不会单独出现**——每次都被【团建】或【建组】这条更长的规则先接走。注意措辞：词表里那个基础表项通常还在（多数实现保留全部基础符号），**不在的是它在序列里的位置**。同理，「团」也不会单独出现。

这个区分很重要，因为它决定了修法。若说「词表里没有这个字」，对策会变成「把字加回词表」——那是错的。真正的事实是：**它从未被要求以「字」的身份出场。**

如果这时问模型「『建』出现了几次」，它手里只有这一串编号：

```text
原始文本：  团 建 团 建 团 建 建 组 建 组 团 队 团 队
                ↓ 分词器按学到的合并顺序套用
模型看见：  【团建】【团建】【团建】【建组】【建组】【团队】【团队】
                ↓ 换成编号
编号序列：  4821  4821  4821  5306  5306  7710  7710
```

它要回答「5」，必须先知道 4821 的内部是「团 + 建」、5306 的内部是「建 + 组」，再各乘一次频次，再相加。**这些都不是「看一眼」能得到的，而是一串需要展开、需要遍历、需要累加的动作。** 它可能因为见过太多「团建」而答对，也可能因为把 4821 当成一个整体而漏掉。对错取决于它见过多少类似的模式，不取决于它数没数。

还有一个反直觉的细节：**合并之后，「字」不是变模糊了，而是根本不在序列里了。** 你以为它在看「团建预算」四个字，它看到的是两个块。块的内部结构只存在于词表那一行字符串里，而模型前向计算时并不会去查那一行。

### 同一段文字，会被切碎成什么样

下面全部是**示意**，用「｜」表示 Token 边界。真实切法取决于具体分词器，同一行在不同产品上可能完全不同；这里要学的是「为什么会这样切」，不是记切法。

| 输入（示意） | 一种可能的切法 | 为什么会这样 | 对任务的后果 |
| --- | --- | --- | --- |
| 团建预算 | 团建 ｜ 预算 | 两个高频双字组合，各自成块 | 2 个 Token 覆盖 4 个字；数字数必须回查词表 |
| 我们团建 | 我们 ｜ 团建 | 同上，「我们」也是高频块 | 词边界与 Token 边界不必一致 |
| OpenAI | Open ｜ AI | 品牌名反复出现，前半段也是常见片段 | 字母数不等于 Token 数 |
| 10月25日（周六） | 10 ｜ 月 ｜ 25 ｜ 日 ｜ （ ｜ 周六 ｜ ） | 数字与单位各自成块，星期是另一个块 | 日期没有被表示成「日期」，只是几个块挨着 |
| 15,690 | 15 ｜ , ｜ 690 | 千分位与三位分组在语料里常见 | 位与位被切开，「进位」没有通道 |
| 39×310 | 39 ｜ × ｜ 310 | 运算符常单独成块 | 它看见的是「两个数、一个符号」，不是一个待执行的乘法 |
| 3.14 | 3 ｜ . ｜ 14 | 小数点常单独成块 | 小数点的位置靠模式记，不靠数位对齐 |
| 空格 | ▁ ｜ 下一个词 | 前导空格常被并进后一个块 | 「有几个空格」这种问题从单位上就答不了 |
| 「先别发」 | 「 ｜ 先别 ｜ 发 ｜ 」 | 标点常单独成块，也可能与相邻字合并 | 引号不是「边界标记」，只是普通字符 |
| 下雨了☔️ | 下雨 ｜ 了 ｜ ☔ ｜ （不可见的变体选择符） | 天气符号的基础码位与变体选择符合并或分开 | 一个「表情」可能是 2–4 个 Token |
| 👨‍👩‍👧‍👦 | 多个字节片段 | 家庭符号由多个码位与连接符组成 | 一个视觉符号可能十几个 Token |

这张表可以横向读，也可以纵向读。横向读，你会看到**同一句话里，不同成分的「碎片率」差别很大**：汉字词可能两个合一块，数字和 Emoji 却碎得厉害。纵向读，你会看到**所有行都指向同一件事**：Token 边界是按「语料里常见的片段」定的，不是按「人觉得什么是一个单位」定的。

空格值得单独说一句。英文里空格是词边界，所以很多分词器把「空格 + 词」当成一个整体；中文没有空格，词边界只能靠合并表里的统计结果。**两种语言的「同一个意思」，在 Token 数上并不对等**——这不是翻译质量问题，是切分方式不同。到了 21 篇算账时，这会变成两件不同的成本。

### 切分带来的三个副作用

1. **字符级的事，它天然做不了。** 数笔画、数偏旁、判断两个字是不是同一个字的不同写法，都要求先有「字符」这个单位。
2. **跨块的关系，它只能猜。** 15,690 被切成 15 和 690 之后，「十位是多少」这个问题要先跨过块边界；块与块之间没有「同属一个数」的标记。
3. **它对自己用了多少 Token 也不可靠。** 它看不见分词器的计数过程，只能根据「这段话大概多长」给一个估计。这一点在 03.9 会变成一个可测的项目。

## 03.5 错误清单：同一副骨架，八种长相

下面这些任务，表面差别很大，底层要求是同两件事之一：**遍历后累加**，或者**对齐后进位**。

| 任务 | 它实际在做的事 | 典型错法 | 最小可行做法 |
| --- | --- | --- | --- |
| 数一段话里有几个某字 | 根据长度与重复感，生成一个「像次数」的数 | 差一两个；整十整百；把词块内部的字漏掉 | 自己数，或用查找替换的计数 |
| 数一串字母有几个 | 把字母当成词块的一部分来感知 | 多数或漏数；大小写规范化后再错一次 | 用编辑器的查找计数，或表格的计数函数 |
| 数一张表有几列 | 读表头文本，估计「大概几列」 | 合并单元格、空列、隐藏列全算错 | 看表格软件的列标或状态栏 |
| 比较两个长数字的大小 | 看位数、看开头几位，生成一个「谁大」的判断 | 位数相同就看不准中间位；9,999 与 10,000 混淆 | 补零对齐，从最高位逐位比 |
| 算两个日期差几天 | 背常见间隔，套一个接近的数 | 跨月、闰年、含不含首尾，各错一次 | 日历工具；或明确「含头不含尾」后手算 |
| 做单位换算 | 套一个记得的比例 | 带偏移的换算（如温度）把加法当乘法；非十进制单位乱套 | 写出换算公式，逐步代入并保留中间量 |
| 数条目、段落、行 | 数换行与编号的「样子」 | 空行、跳号、自动编号被当成内容 | 结构化导出后计数 |
| 报这段文本的 Token 数 | 估计长度，再乘一个印象中的比例 | 不同分词器差很多；把字数当 Token 数 | 用对应分词器的计数工具，或看账单 |

八行里，前七行是「数」，最后一行是「数自己」。最后一行最容易被放过，因为它听起来像技术细节，实际上它直接决定了预算和报价——详见 03.7。

### 为什么这些错都「只差一点」

因为它的输出不是从一次遍历里得到的，而是从一个「合理范围」里抽出来的。**合理范围的中心由模式决定，误差由抽样决定。** 所以你会看到：

- 40 个字里数出 4 次（实际 3 次），不是数出 40 次；
- 15,690 说成「一万五出头」，不是「五万」；
- 9,999 和 10,000 比大小，它可能两个都说「差不多」；
- 日期差 17 天，它可能答 16 天或 18 天。

**「只差一点」不是它努力过的证据，恰恰是它在附近抽样的证据。** 一个真的逐个数过的东西，错也会错在「漏了哪一段」，而不是稳定地偏向某个整数。

### 反过来的那一半：哪些「像计数」的事它反而能做

为了不把结论说过头，必须补上这一栏：

| 任务 | 为什么可能做对 | 但仍要注意 |
| --- | --- | --- |
| 判断某词在不在（是 / 否） | 这是一次整块匹配，不需要遍历累加 | 长文里仍可能漏；要它指出原句 |
| 找出第一个出现的匹配 | 只需要定位一次，不需要数总数 | 位置可能记错；要用原文核 |
| 估算「大概几百字」 | 量级判断可以靠模式 | 不能用于预算、合同、字数上限 |
| 按给定格式生成编号列表 | 格式是高频模式 | 编号可能跳号或重复；必须逐行核 |
| 复述你给出的数字 | 抄写比计算容易 | 抄也可能改一位；参与后续计算前必须核 |

这张表是本文的边界，也是下一节要展开的「能做什么 / 代价 / 何时失效」。

## 03.6 为什么它能写代码，却算错 39×310

这是全篇最值得停一下的地方，因为「会写代码」经常被当成「会计算」的证据。

### 写代码时，算的不是它

它写代码时，输出的是**一段要被别人执行的文本**。乘法、循环、求和，真正的执行发生在代码跑起来之后——由运行时、由 CPU、由数据库完成。它只需要让这段文本「看起来对、语法对、调用对」。

```text
写代码：  模型 ──▶ 输出一段表达式 ──▶ 运行时真的执行 ──▶ 结果
                        ↑
                   它只需要把式子写对

算算术：  模型 ──▶ 输出一个结果 ──▶ 没有人接手 ──▶ 对错全在这一次续写里
                        ↑
                   它必须自己「算出」这个数
```

这就是「能写代码却算错」的第一层答案：**写代码时它把计算外包给了运行时；算 39×310 时没有运行时接手。**

顺带解释一个常见现象：它在代码的注释里、文档的示例里给出的那个结果，经常比代码本身更容易错。因为代码里的乘法由机器执行，注释里的数字却要它自己填。

### 39×310 到底要求它做什么

把这道题拆开，正确路径是三步，每一步都带状态：

```text
39 × 310
  = 39 × 300 + 39 × 10
  = 11,700 + 390
  = 12,090
再加包车 3,600
  = 15,690
与预算 15,600 比较
  = 超 90
```

这条路径要求：

1. **保存中间量。** 11,700 和 390 必须先存住，才能相加。
2. **对齐数位。** 个位对个位、十位对十位，否则加出来是另一个数。
3. **处理进位。** 12,090 的千位、百位怎么来，取决于低位的进位。
4. **保留比较的方向。** 15,690 比 15,600 大，所以是「超」，不是「没超」。

模型手里没有 1、2、3 里的任何一个机制。它没有寄存器保存 11,700，没有「对齐」这个操作，也没有一个叫「进位」的状态位。它每选一个片段，条件只是「前面已经写了什么」。**进位如果要发生，它必须先把进位写成文本，再从文本里读回来；而「读回来」本身又是一次模式匹配。** 这不是一个可靠的计算回路，而是一串越来越长的猜测。

还有一个单向性：**生成不能回头。** 如果它先把百位写成了 1，后面就会顺着这个 1 继续编，而不是停下来把百位改掉。它可以在写完之后「再检查一遍」，但那是重新生成一段新文本，不是回到上一步修改状态。两段文本还可能互相矛盾，而它没有机制判断哪一段对。这就是 01 篇说的「它道歉并改正，不代表它定位到了原因」。

### 代码和算术，差在「冗余」和「可验证」

代码有两个算术没有的东西：

- **强语法冗余。** 括号、缩进、关键字、常见函数名，把下一个片段约束得很紧。写错一个词，上下文常常能把它拉回「像代码」的形状。算术没有这种冗余：12,090 和 12,190 在形式上同样合法，只有数值分对错，而形式帮不上忙。
- **外部可执行。** 代码可以跑，跑不通会报错；算术的答案没有编译器。它写完 15,690 或 15,600，没有任何一步会告诉它「这个数不对」。

所以「能写代码」证明的是**它对结构的模式掌握得好**，不是**它有一个计算器**。这两件事在它身上可以同时成立，而且经常同时成立。

### 分步提示为什么有时管用，又为什么不够

把「算 39×310+3,600」拆成「先只算 39×310」「再只加 3,600」「再只做一次减法」，往往会改善结果。原因不神秘：**中间结果被写成了可见的文本，等于给它一张外部草稿纸。** 每一步只做一件事，单步的搜索空间变小了，模式更容易命中。

但这只是「降低错误率」，不是「获得计算能力」：

- 它写下的中间结果本身仍可能是错的，而下一步会顺着错的往下算；
- 步骤一多，它可能在某个中间步编一个「看起来合理」的数；
- 同一道题换个说法、换一次抽样，结果可能又变（见 04）。

**分步是让它把草稿写出来给你看，不是让它真的会算。** 正确的用法是：让它写步骤，你来核每一步；或者让它把步骤写成可执行的表格公式，由工具算出结果，再由你对回执。后者属于 P5 的分工，详见 16–17。

## 03.7 边界：能做什么、代价是什么、什么时候失效

### 三列账

| 它能做的（在计数与算术上） | 代价是什么 | 什么时候失效 |
| --- | --- | --- |
| 估算长度与量级（「大概几百字」「大约一万五」） | 听起来像精确值；误差可能几十个百分点 | 进入预算、合同、字数上限、报价时 |
| 判断某词在不在、找第一个匹配 | 长文会漏；位置可能记错 | 需要给出次数、位置、全部匹配时 |
| 复述你给出的数字 | 抄写也会改一位 | 这个数字要参与后续计算时 |
| 给出换算公式与计算步骤 | 公式对，代入可能错 | 单位带偏移（温度）、非十进制、复合单位时 |
| 分步写出中间结果 | 更慢、更贵；中间值仍可能编 | 每一步都需要外部核对；不能替代工具 |
| 把计算写成可执行的表格公式 | 公式的引用范围可能错 | 需要回执与人工复核（16、17） |

这张表最重要的不是第一列，是第三列。**「它能做」与「它做得对」之间，隔着一个「谁来核」的问题。** 只要答案要进入钱、合同、人数、日期、剂量，第三列就会亮起来。

### 同一段话，为什么两个产品报的 Token 数不同

这不是谁在撒谎，是四层差异叠在一起：

| 差异层 | 具体差在哪 | 结果 |
| --- | --- | --- |
| 词表 | 同一个「团建」在 A 是一个表项，在 B 是两个字两个表项 | 同一段话的 Token 数不同 |
| 合并规则 | BPE、WordPiece、Unigram 的合并准则不同；合并顺序也不同 | 切点不同，块的大小不同 |
| 规范化 | 有的统一全角半角、有的统一大小写、有的压缩空白 | 进入模型前的字符数就不同 |
| 特殊标记 | 聊天模板会加角色标记、起止标记；系统提示算不算输入，各产品口径不同 | 账单上的「输入 Token」不是「你看到的字数」 |

再往外还有一层：**同一份附件，不同产品抽取成文本的方式不同**（见 13）。扫描件 OCR 出来的字数和原文就不一样，Token 数自然也不同。

所以「按字数估价钱」不可靠，误差至少来自四段：

```text
你看到的字数
   │ ① 字数 → Token：取决于分词器，中文一字可能不到 1 个 Token，也可能超过 1 个
   ▼
Token 数
   │ ② Token → 计费单位：输入与输出分别计价，缓存命中与否也不同
   ▼
计费量
   │ ③ 可见文本 → 实际送入：系统提示、历史、附件、工具说明都要算
   ▼
这一次的账单
   │ ④ 一次 → 一个任务：重试、并行、工具往返会放大
   ▼
任务的真实成本
```

四段里，第 ②③ 段还能从账单上部分看到，第 ① 段取决于分词器、第 ④ 段取决于你怎么用，都只能你自己控制。**所以预算表里不要写「按字数 × 单价」，要写「按分词器计数 × 计价规则 × 预估轮次」。** 具体怎么算，21 篇展开。

还有一种常见说法要拆掉：「中文比英文贵」。这句话不准确。贵不贵取决于**分词器对这种文字的切法**，以及内容里数字、代码、标点、Emoji 的比例。同一段中文，全是常用词和全是长数字，Token 数可以差出很多；同一段英文，普通散文和代码也一样。**语言只是其中一个变量，不是结论。**

### 这个类比在这里失效

讲 Token 最顺的类比是**乐高积木**：世界被拆成一块一块，模型拿起一块，拼到已经拼好的部分上。

这个类比在三个地方成立：块是离散的；块有固定形状；拼装是单向的。但它在一个关键步骤上失效：

> **乐高块可以拿起来翻面、看花纹、拆开重拼；Token 拆开之后，编号就没了。**

人拿起一块印着「建」的积木，能看到那个字，能把它单独放回去数。模型拿到 4821，看到的是一个索引；它没有「翻面」这个动作，也没有「把这一块拆成两半」这个动作。词表里那一行「团建」的字符串，不会在模型前向计算时被展开。

第二个失效点更细：**「半个汉字」这种积木，在人手里不存在。** 字节级分词器真的会把一个汉字切成跨 Token 的字节片段。你可以把它想成「一块积木上印着半个字」，但人不会这样造积木，所以这个类比帮不到你理解「为什么它连字都看不见」——只能帮到「为什么它看见的是块」。

把类比用到这里就该停：**它能解释「离散」，解释不了「不可展开」。**

### 什么时候这篇的结论不再适用

三种情况要单独标出来：

1. **任务被改写成整块匹配。** 判断包含、分类、改写、摘要，不需要遍历累加，Token 边界的影响小得多。
2. **计算被交给工具，并且有回执。** 这时结果不是模型算的，本文说的「它不会算」不适用于那个结果；但你要去核回执，而不是核它的措辞（见 16）。
3. **产品明确用外部校验兜住了结果。** 例如表格公式、代码执行、计算器返回，错误率会变。但「有校验」和「校验通过」是两件事，仍然要人看一眼。

## 03.8 反例与正例：同一笔账，两种问法

### 反例：一句话把四件事塞进去

> 「B 方案人均 310，39 人，包车 3,600，预算 15,600，超没超？顺便把每人实际摊多少也算一下。」

这一句里有：一次乘法、一次加法、一次比较、一次除法。四步都要求中间状态，而它只会给一个最终结论。你拿到「没超」两个字，既不知道它乘对了没有，也不知道它比对了没有。**结论越短，越不可核。**

更糟的是加压版：「请仔细算，这很重要，算错要负责。」这句话不改变机制，只改变措辞。它可能让答案更「像认真算过」，也可能让它在错的时候更自信。**压力不是校验。**

### 正例：把一件事拆成一张卡

同一笔账，改写成四步，每步只做一件事，且每步都可核：

| 步 | 只让它做这一件事 | 产出 | 你怎么核 |
| --- | --- | --- | --- |
| ① 抄 | 从原文里抄出三个数：人数、人均、包车 | 39、310、3,600 | 对着原文逐字看 |
| ② 算 | 用表格公式算 39×310 | 12,090 | 看单元格里的公式与结果 |
| ③ 加 | 把上一步结果加 3,600 | 15,690 | 看单元格，不看出自哪段话 |
| ④ 比 | 用 15,690 减 15,600，写出差额与方向 | 差 90，超 | 自己再减一次 |

这张卡的关键不是「拆得细」，是**每一步的产出都能离开模型独立存在**：原文、单元格、差额。到了第 ④ 步，结论已经不需要它来说了——你自己减一次就知道。

### 两条链的差别

```text
错的链：一句话问总算 ──▶ 它给一个像样的数 ──▶ 「差不多」 ──▶ 签字
对的链：抄原文 ──▶ 工具算 ──▶ 人对表 ──▶ 留算式与截图 ──▶ 签字
```

两条链的差别不在提示词长度，在**中间产物有没有落在模型之外**。错的链里，所有中间量都在它脑子里（如果它有的话）；对的链里，中间量在表格里、在原文里、在你的纸上。**能被别人复核的中间量，才叫证据。**

### 三个可以立刻改的问法

| 不要这样问 | 改成这样问 | 为什么 |
| --- | --- | --- |
| 「这段有多少字？」 | 「把这段按句号拆成几段，逐段列出字数；最后一行写总计。」 | 拆句把「遍历全文」变成「逐段处理」，总计仍要你核 |
| 「这两个数哪个大？」 | 「把两个数补到相同位数，逐位列出比较结果。」 | 补位把「看感觉」变成「对齐」 |
| 「帮我算一下总价」 | 「先写出公式和三个入参，再用表格算；结果单独一格。」 | 公式与入参可核，结果有出处 |

注意最后一行：**不是让它「更努力地算」，而是让「算」发生在别处。** 这是本篇和「提示词工程」的分界线。

## 03.9 你可以自己做的检验

十分钟，不用写代码，一款聊天产品、一张纸就够。三项都做完，你对自己手上这个产品的判断会比读十篇文章准。

### 准备

用上面那段四十个汉字（标点不计）：

> 名单四十二条，去重后三十九人；预算一万五千六百，场地按三十九人乘二百六十算，包车三千六百。

先自己数一遍，把答案写在纸上，别让它的回答影响你。正确值是：「三」3 次（第 10、25、37 字），「十」4 次（第 4、11、26、33 字）。

### 第一步：数两个字

新开一个会话，把这段话原样贴进去，问：

> 「三」在这段话里出现了几次？只给数字。

记下答案。再问「十」。再记下。

**判据**：两次都对，不等于它「会数」——换一段更长、更少见的段落再试一次。两次里错一个，和本文的判断一致：它在给一个附近的数。**如果它每次都精确对，并且换段落也对，本文的结论就要收窄**：不是「绝对不能」，而是「没有保证，且你无法从输出判断它这次是数出来的还是猜中的」。这个收窄很重要，它把「能力判断」换成了「可验证性判断」。

### 第二步：一次问两道算术

同一个会话，问：

> 39×260 等于多少？39×310 再加 3,600 等于多少？只给两个结果。

正确值：10,140；15,690。

记下它给的两个数。然后做一件比「对答案」更有用的事：**把同一个问题换三种说法各问一次**（例如「39 乘 310 加 3600」「310 的 39 倍再加 3600」「先算 39×310，再加 3600」），看三次答案是否一致。

**判据**：三次一致且正确，说明这类题在它的高频模式里；三次不一致，说明它在抽样，而不是在算。**不一致比错更值得记**——它证明没有一条稳定的计算路径。

### 第三步：分步重试，比较

把第二题拆成三问，每问只做一件事：

1. 「只算 39×310，把中间步骤写出来。」
2. 「把上一步的结果加 3,600，只做加法。」
3. 「用 15,690 减 15,600，只写差额和方向。」

记下每一步。再和第二步的一次性答案比较。

**判据**：分步后变对，说明「外部草稿纸」有用，但不要因此相信它「会算」——第 2 步可能顺着第 1 步的错值继续算。分步后仍错，说明连单步都不稳，这类任务必须交给工具。两种结果都支持本文的结论，只是支持的方式不同。

### 记录表

| 项目 | 一次问的结果 | 分步问的结果 | 我自己核出的值 | 这说明什么 |
| --- | --- | --- | --- | --- |
| 「三」出现次数 |  | — | 3 | 计数是否有稳定路径 |
| 「十」出现次数 |  | — | 4 | 换字后是否仍只差一个 |
| 39×260 |  | — | 10,140 | 两位数乘法是否可靠 |
| 39×310+3,600 |  |  | 15,690 | 分步是否改善 |
| 与 15,600 的差额 |  |  | 90，超 | 比较这一步是否被漏掉 |

最后一行最容易被忽略。**很多错误不在乘法，在比较**：数算对了，结论说反了。这也是引子里那个「应该没超」的真正错处——它的 12,090 和 15,690 可能都对，错的是最后一步的方向。

## 03.10 术语考古：三个被用坏的词

### Token

| 栏 | 内容 |
| --- | --- |
| 最早出处 | 计算与语言学里早已使用，指「被当作一个整体处理的单位」，没有单一发明人；本文不标年份与具体文献，避免把二手转述当出处。 |
| 原义 | 一个不可再分的记号；在词法分析里指扫描出来的最小单位。 |
| 现在被怎么用 | 计价单位、容量单位，有时被直接当成「字」或「词」的同义词；「一个 Token 等于一个字」是最常见的误读。 |
| 本文怎么用 | 词表里的一行：一段字节串加一个编号。它可能是一个字、半个字、一个词、一个词加前导空格、一个标点，或一段数字。 |

### 词表（vocabulary）

| 栏 | 内容 |
| --- | --- |
| 最早出处 | 语言学里的「词汇表」；工程上指分词器持有的符号集合。本文不标具体文献。 |
| 原义 | 一个系统所承认的符号清单。 |
| 现在被怎么用 | 常与「模型知道的词」「训练语料」混为一谈，也常被当成「越大越强」的同义词。 |
| 本文怎么用 | 分词器的「片段 ↔ 编号」映射表，大小与内容在训练分词器时固定。它不等于模型权重，也不等于知识；要加词，得连模型的输入层一起改。 |

### BPE

| 栏 | 内容 |
| --- | --- |
| 最早出处 | 数据压缩领域的「字节对编码」，后来被引入子词分词。本文不在此标年份与具体文献，避免把转述当出处。 |
| 原义 | 反复把最常相邻出现的一对符号合并成一个新符号，用更短的序列表示数据。 |
| 现在被怎么用 | 常被当成「子词分词」的同义词，甚至泛指任何分词器；「字节级 BPE」也常被说成另一种算法。 |
| 本文怎么用 | 一种具体的合并算法，可以架在字符上，也可以架在字节上。「字节级」说的是起点粒度，「BPE」说的是合并规则，两件事。 |

三个词填完，有一件事会变得清楚：**争论「它到底认不认识字」，往往不是观点之争，是词义之争。** 一方说的「字」是屏幕上的字符，另一方说的「字」是词表里的表项。把单位说清楚，一半的争论会自动消失。

## 03.11 一页速记

| 现象 | 机制 | 你该怎么做 |
| --- | --- | --- |
| 数汉字、数字母总是差一点 | 它看到的是 Token，不是字符；字符可能藏在块内部 | 自己数，或用会数的工具 |
| 长数字比大小、算差额出错 | 数字被切成几段，段间没有对齐与进位 | 补位对齐，逐位比较 |
| 日期差、单位换算不稳 | 需要规则与偏移，不是模式 | 用日历 / 换算工具，保留中间量 |
| 能写代码却算错乘法 | 代码由运行时执行，算术要它自己产出结果 | 让它写公式，让工具算 |
| 分步之后好一些 | 中间结果变成了可见的草稿 | 分步用来「看过程」，不用来「信结果」 |
| 两个产品报的 Token 数不同 | 词表、合并、规范化、特殊标记都不同 | 固定分词器计数，按实际用量做预算 |

**五句话带走**

1. 它不是在数，是在生成一个「像计数结果」的片段。
2. 字被合并进 Token 之后，在序列里就不再作为可数的对象存在。
3. 乘法要进位，进位要状态；它没有保存状态的地方。
4. 写代码时算的是运行时；算 39×310 时没有运行时。
5. 分步能让它写出草稿，不能让结论变成证据。

**最后一句**：这一篇不要求你记住 BPE 的合并顺序，只要求你在下一次看到「一共 4 次」「大约 1.2 万」「应该没超」时，先问一句：**这个数是它数出来的，还是它写出来的？** 如果是写出来的，就把它当草稿；结果从会数、会算的地方来。

**三道自检**

1. 它说：「这段话 480 字，大约 600 Token。」这句话里哪些数可信？
2. 它算出 B 方案 15,690，却说「没超 15,600」。错在哪一步？
3. 同一段话，A 产品报 520 Token，B 产品报 610 Token。谁错了？

<details>
<summary>查看参考答案</summary>

1. 两个数都不可信，但不可信的原因不同。480 这个字数它没有逐字数过，是估的；600 这个 Token 数取决于分词器，而且「字数乘一个固定比例」这种换算没有普遍依据。可信的做法是：字数自己数或用工具数；Token 数用对应分词器的计数，或直接看账单上的实际用量。如果这句话出现在报价里，两个数都要重算。
2. 不在乘法，在比较。39×310 = 12,090，加 3,600 = 15,690，比 15,600 多 90。它把「接近」当成了「没超」。正确的问法不是「超没超」，而是「用 15,690 减 15,600，写出差额和方向」——把结论拆成一个可核的减法。
3. 不一定有人错。分词器不同，词表、合并规则、规范化、特殊标记都不同，同一段话的 Token 数本来就可以不同。要比，就固定产品与版本，或者用同一个分词器的计数；做预算，以账单上的实际用量为准。**「谁错了」这个问题本身问错了单位。**

</details>
