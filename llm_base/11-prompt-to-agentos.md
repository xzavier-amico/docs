# 11 · 从 Prompt Engineering 到 Harness 再到 AgentOS

> **状态**：已完成（初稿）
>
> **本篇定位**：Part III 第 2 篇。沿着同一个市集任务，看清指令、资料、单任务执行与共享平台各负什么责任。
>
> **读法**：先看能力阶梯，再从四个版本里挑一个你用过的方式对照。最后用「何时不升级」表给下一次任务选做法。

## 同一句话写得更用力，怎么还是出了两种错？

**虚构场景。** 社区市集原定周六，主办方现行规则 v2 改为**周日 14:00**，旧 v1 失效，雨天是否改室内待确认。志愿者小周要的只有报名清单和通知草稿，**不发送、不改原表**。她把任务交给不同的应用，发现两种错误：一个写成周六，因为它手里只有 v1；另一个能认对日期，却出现「准备群发」的动作请求。给两边都加一句「请务必小心」没什么用：前者缺的是可信的材料；后者缺的是能阻止越界的执行控制。

**本篇只问：每加一层，到底接管了什么责任？** 下图是同个任务的四种做法，不是产品成熟度评级。可以只用其中一层，也可以在同一应用里同时做几层的事。词义常常重叠，尤其「Harness」和「AgentOS」不是大家都按同一方式划分的产品类别，更不是所有项目必经的历史阶段。

## 能力阶梯：这次把哪件事交给系统？

```text
         较多运行责任由系统承担 ↑

④ AgentOS 式平台  多个任务共享队列、权限规则、预算、记录与恢复机制
                  ── 多个运行怎样互不踩脚？
③ 执行外壳        一次运行里的派工具、记状态、校验、有限重试与停止
                  ── 这次具体怎么跑，哪里拦住？
② 上下文管理      本轮放哪份资料、哪项决定，何时再取补充材料
                  ── 模型现在看到什么？
① 提示词          目标、表达要求、行动边界与验收口径
                  ── 人到底要什么？

         人始终决定目标与授权，并验收交付结果
```

### 版本一：写清要什么——Prompt Engineering（提示词工程）

开始只有「把市集的事弄一下」。改为：「按照主办方当前有效的规则，交一份内部报名清单和一份通知草稿。清单标出待核记录；草稿注明时间依据，未定场地标待确认。不改原表，不发送。」这次改的是**任务表达**：要几份东西、什么叫写完、哪些事不要做。材料齐全时，把 v2 和报名摘录附上就能办。只给 v1 时，写得再清楚也不能凭空变出 v2；在具备发送能力的产品里，一句「不发送」也不能替代实际权限限制。人不仅要写出意图，还要确认产品怎样落实这条边界。

### 版本二：每轮给对材料——Context Engineering（上下文工程）

以前小周每次把整个群聊、两版通知和整张表一起贴进窗口。现在她先让应用带上主办方 v2、报名表必要列、以及「只交草稿、不发送」；v1 如要留作改期对照，只带「原周六、已失效」并明确区隔。不用把联系电话带进草稿环节；读到新证据时，下一轮仍须带上当前约束和关键未决项。这改的是**材料怎么选、什么时候给、如何标出来源和版本**，没改模型学到的东西，也没改变权限。应用如果误取同名 v1，更多上下文只会让误用旧规则更难被发现。

### 版本三：把执行变成可检查的过程——Harness（执行外壳）

小周不想每隔几分钟看一次人工复制进度。于是由应用的单任务执行外壳维持当前状态：只派获准的只读查询；发起前检查请求是否对着本次活动和允许读取的列；收到结果就记下来源、是否为 v2 和哪些行还需核对。工具短暂无响应时，只在约定范围内重试；访问被拒、预算触顶或出现需决策的冲突，就保留进度并交回给小周。交付前能检查草稿有没有标明依据和待确认项，但是否真的引用对了、语气是否合适，仍要按验收规则判断，不靠一个「通过」标签。

Harness 指围绕模型安排执行的那层，不是另一个更聪明的模型。同一外壳也能包住固定工作流。它可以不向这个任务提供发送工具，并由运行时拒绝任何发送请求；「提示词要求模型别发」和「运行时没有权限发」是两道不同的线。至于重试和恢复，也只能在清楚知道前一步状态时用：连动作是否已发生都不清楚就再派一次，有副作用的工具可能做两次。本例没有这种写入需求，不必为它接入写权限。

### 版本四：让多个运行共用规矩——AgentOS 式平台

一次市集不一定需要这层。想象同一个主办团队在为几个会场分别起草通知，同时跑各自的报名整理任务。平台可以把任务排队，限制同时访问同一报名服务的数量，分配每次运行和全团队的用量上限，让每个任务只看到自己授权的活动资料。有人接班时，可从记录核对哪些步骤已完成、适用的版本是什么、哪里仍等人确认，再决定是否恢复，避免不加核对地从头重跑。**共享调度不等于共享全部数据；恢复任务也不意味着恢复一切旧授权。**

这里的 AgentOS 是一种平台组织方式：多个 Agent 或工作流共用若干运行服务。现实里这些能力可能分散在几个产品中，也可能和 Harness 绑成一体；名字里带 OS 不代表它是操作系统，也不保证上述能力都齐。单个应用能定时跑，不代表需要一套跨任务调度平台；反过来，一个平台也不能替主办方判断雨天去哪儿。

## 先找责任，再谈加层

| 看到的问题 | 先核对谁的责任 | 修好之后应看到什么 |
| --- | --- | --- |
| 助手只写一段通知，漏了清单 | 看人给的产物要求、示例和验收项是否明确 | 同时返回清单与草稿，分别标明待核问题 |
| 草稿又写成周六 | 看本轮是否实际拿到可信 v2，旧 v1 是否清楚标为失效 | 草稿写周日 14:00，并能指出依据，雨天仍待确认 |
| 查不到材料却一直重试，或试图发送 | 看执行外壳的工具范围、权限检查、状态记录和停止条件 | 没有发送路径；受阻能报告，重试有上限 |
| 不同会场的运行挤满服务，或恢复后读错会场名单 | 看共享队列、任务隔离、会场权限与恢复记录 | 资源在约定范围内分配，各次运行只见必要数据，恢复时核对当前版本与权限 |

别把「能做什么」「人想让它做什么」「它获准做什么」「实际做了什么」合在一张勾选表里。比如平台明明具备群发能力，用户意图仍只是草稿，本次无发送授权，执行记录也应显示未发。反过来，模型在聊天里写「未发」不能证明运行时一定拦住过发送；要看本次实际可用的工具和正式记录。

## 何时不升级：复杂度也要有回报

| 现场 | 足够的办法 | 升级的代价或边界 |
| --- | --- | --- |
| 一次性的草稿，v2 和必要名单字段都在手边 | 写清提示词，把附件核对好，人工审阅 | 新接外部服务只会多出权限、等待与排查工作 |
| 经常被旧文件误导，但资料能人工选好 | 固定版本来源和附资料规则，用几份旧新版混放的样例回测 | 加执行外壳不能自动把错误来源变成可信来源 |
| 每次都按相同步骤读资料和审稿 | 用简单固定流程；有需要再补有上限的执行检查 | 更自主的循环多耗时，要验证是否真能处理预先想不到的分支 |
| 只有一人偶尔跑一次，失败了自己能接手 | 保留简单的任务记录与权限限制 | 共享平台带来维护、权限管理和日志保留负担；多任务冲突反复出现时才有明显收益 |

判定升级有没有用，可以始终拿三张相同的样例卡比：材料齐全、旧版误混、只读工具读不到。比前后哪版更常同时交出合格清单和草稿，是否在边界停住，需要人补几次，是否花更多时间。不要把一次写得更漂亮，当成执行安全或稳定性已经提高。

## 纸上练习：最小改动能在哪一层解决？

在纸上画「指令、材料、一次运行、多个运行」四格。把下面三张情况卡贴到合适位置，并为每张写一个可验证的结果：① 草稿日期正确，但忘了交报名清单；② 对话明写只交草稿，可同一个运行会一遍遍发起失败的读表请求；③ 两个会场明明各自过了权限检查，开在一起却耗尽同一个团队的用量。

**参考贴法：** ① 先查指令与验收标准，补「分别交两份」，验证两份都在；如果早已写清，再查单次运行的交付检查。② 单次运行的执行外壳，验证到重试上限就停，并能说清未读到什么。③ 共享平台或已有的团队级配额，验证某个任务用到自己的上限，另一个仍有预算。日期写成周六且本轮只有 v1，则补到材料格，不是去改这三张卡的答案。

## 速记与自检

**速记：** 提示词写目标和边界，上下文给对证据，执行外壳管好一次运行，平台协调多个运行。**先看责任缺在哪，再决定是否增加复杂度。**

1. 模型本轮只见到失效 v1，提高提示词强调力度能保证写对日期吗？
2. 「不许发送」和「当前运行没有发送权限」是同一件事吗？
3. 就一次市集、资料齐、只要一份清单和一份草稿，需要 AgentOS 式平台吗？

**参考答案：** ① 不能，补可信 v2 才能确认周日 14:00。② 不同：前者表达本次边界，后者让运行时无法执行；还要核对实际执行记录。③ 不需要，单轮回答配合人工验收就可能足够。
