## 15.1 引子：同一件团建事，三种做法

**虚构场景**。10 月 8 日下午，秋季团建筹备到一半。三个人，同一份材料，同一个下午，都想拿到一份能发的通知草稿。**先别发**。

**做法一（小陈）**：她在对话框里写「帮我写一份秋季团建通知，公司 39 人，10 月 25 日」。四十秒后拿到一段很体面的文字，改了两个词，复制进文档。整个过程只有一次来回：她问，它答，她拿走。

**做法二（老周）**：他把这件事做成了一个固定流程。第一步跑名单去重——系统导出 42 条记录，其中 3 条是同一人的重复提交，去重后 39 人；第二步按 A 场地算 39×260=10,140，加包车 2×1,800=3,600，合计 13,740；第三步套通知模板；第四步自己核日期和雨天方案。每一步走向下一步是写死的。中间任何一步出错，流程不会自己发现，是他发现的。

**做法三（小林）**：她没有写步骤，她给了四样东西——目标（一份可发的通知草稿，今天不发）、材料（通知 v2、A 与 B 两份报价、名单导出、包车询价）、权限（可起草、可查名单；不可群发、不可付定金、不可改名单）、停止条件（人数口径不确定就问、档期不确定就标出来、群发前停）。然后让系统自己决定先看哪一份、看到之后下一步做什么。

系统的走法大致是这样：先读通知，发现 v1 已作废、现行日期是 10 月 25 日，但雨天方案写着「待确认」；再去读名单，报出「42 条记录」，然后停下来问：按记录算，还是按人去重？小林回答「按人去重」。它继续，算出 A 方案 13,740、B 方案 15,690，超预算 90 元，于是把 B 标成「不可作为方案」；起草时把雨天安排留在待确认清单里，没有替她写成「已安排室内」；最后停在群发之前，把草稿交回来。

三个人的产出可能差不多。但有三件事完全不同：

| | 下一步由谁决定 | 意外由谁接住 | 事后能查到什么 |
| --- | --- | --- | --- |
| 做法一 | 人（读完再问一次） | 人 | 一段对话 |
| 做法二 | 流程（写死的顺序） | 人 | 每一步的中间文件 |
| 做法三 | 模型（看到结果之后决定） | 混合：系统按条件停，人接 | 每一步的动作、返回、判断理由 |

这篇要说的就是这张表的后两列：**产出一样，不代表结构一样；结构不一样，出意外时的表现完全不同。**

但先要拆掉一个更常见的误会。小陈用的那款产品也能查天气、能读文件、能发邮件——界面上有三个工具的图标。于是她以为自己也在用 Agent。其实她用到的仍然是「一次回答 + 几个工具」：先查什么、后查什么、查到之后要不要改主意，全都发生在她脑子里。工具在系统里，循环不在。

## 15.2 唯一真问题：能调用工具，和「会根据结果改下一步」，差在哪

短答案：差在一个「回」字。

工具调用是一条单向边：模型说「请查一下档期」，运行时去做，把结果贴回来。这条边本身不构成循环。构成循环的是：**结果回来之后，下一步的选择因此改变。**

所以判定只需要一句可以当场做的测试：

> **把某一步的工具返回换成一个失败的结果、或者一个空的结果，下一步会变吗？**

如果不变，路线是写死的，那是工作流，不是 Agent。这个测试比起「它有几个工具」「它有没有名字」「它会不会自己规划」都可靠，因为它检验的是结构，不是界面。

十次工具调用，如果每一次调什么、按什么顺序，都在任务开始前就定好了，那只是把一条工作流拆成了十段，段与段之间由代码衔接，不由模型判断。反过来，**一次工具调用也可能构成循环的最小版本**：查档期失败 → 模型决定改查邮件里的确认函 → 拿到确认函 → 决定继续还是停。这里的「变」不是因为模型更强，是因为它看见了上一个动作的结果。

于是得到这一篇的中心判断：

> **Agent 多出来的不是「更强的模型」，而是一个「看结果再决定下一步」的循环。没有这个循环，调用十次工具也只是工作流。**

这句话从哪来？从 P5 来，再往下推一步。P5 说：模型只出主意，动手的是外面那圈系统。既然动手在外面，那么**「结果」也先落在外面**；要让模型用上结果，系统必须把结果当作新的一段材料放回下一轮（这是 P2 的机制，见 [05](05-context-workbench.md)）。所以「会办」= P5 的执行 + P2 的回读 + 一个「还要不要再来一轮」的判断。三者缺一，闭环不成立。

这条判断有它不成立的条件，后面 15.7、15.8 会写明：当任务只有一步，或者所有分支都能在事前穷举时，循环带来的只有不确定性和成本。**在这个范围里，Agent 不是升级，是负优化。**

四个定位问题在这一篇各有具体形态：

| # | 问 | 在本篇里问什么 |
| --- | --- | --- |
| 1 | 这句话是谁说的？ | 「已完成」是模型说的，还是运行时返回的？ |
| 2 | 它这一轮看见了什么？ | 上一步的结果真的被放回前文了吗，还是只在界面上闪了一下？ |
| 3 | 这是提议、事实，还是已经执行？ | 它提议下一步，还是已经做了下一步？ |
| 4 | 我拿什么独立验证？ | 每一步的记录，还是最后那段自我总结？ |

第 1 问和第 2 问在这一篇最要紧，因为循环把这两问从「一次」变成了「每一轮一次」。**单轮回答里可以靠运气躲过的问题，在循环里会被重复十遍。**

## 15.3 三张泳道：三种形态，不是三个时代

先把三种形态并排画出来。注意每一栏里「决定下一步」的那个方块在哪。

```text
形态 A · 单轮回答
  人 ──问题+材料──▶ 模型 ──一段文字──▶ 人
                                      │
                                      └─ 下一步由人决定：再问、改、用

形态 B · 固定工作流（步骤预先写死）
  人 ──▶[取名单]──▶[去重]──▶[算预算]──▶[套模板]──▶[校对]──▶ 人
         └────────── 每一步去哪，写在流程里 ──────────┘
                     模型可以在某一格，但格子不由它改

形态 C · 由模型参与决策的循环
  人 ──目标 / 材料 / 权限 / 停止条件──▶ [ 模型：读状态 → 选下一步 ]
                                                 │            ▲
                                                 │ 提议        │ 观察
                                                 ▼            │
                                        [ 运行时：验权限 → 执行 → 返回 ]
                                                 │
                                                 ├── 还能往下走 ──▶ 回到「模型」
                                                 │
                                                 └── 触发停止 ──▶ 人（验收与签字）

  五条停止：达成 / 预算耗尽 / 连续失败 / 需授权 / 信息不足
```

三张图放在一起，最容易被读成一条进化线：先会答，再会按流程办，最后会自己办。**这个读法是错的。**

三者不是三代，是三种取舍。差别不在能力高低，在**不确定性被放在了哪里**：

| 形态 | 不确定性放在哪 | 什么时候它最优 | 它的硬伤 |
| --- | --- | --- | --- |
| 单轮回答 | 人的下一次提问 | 任务一次能说完；答案本身就够用 | 需要中间结果时，人得手动搬运 |
| 固定工作流 | 写流程的人对分支的预判 | 步骤可枚举、格式固定、要审计 | 事前没想到的分支，一步都走不了 |
| 决策循环 | 运行时，每一步现算 | 分支不可穷举、下一步取决于上一步查到什么 | 不确定、难观测、贵 |

这张表解释了为什么三者会长期共存：**它们各自最优的条件不重叠。** 一个团队同时有这三样东西，不是技术栈混乱，是任务本来就分三类。

Agent 可以嵌在工作流里当某一步。整条团建流程仍然可以是固定的：收集名单 → 比价并给建议 → 审批 → 发布。其中「比价并给建议」这一格交给循环，因为「B 超了 90 元，该换方案还是申请追加」这件事取决于算出来的数和人的偏好，事前写不完。这样，循环的不确定性被关在一个格子里，前后仍是可审计的步骤。**这是工程上最常见也最稳的形态**：不是二选一，是划一块地给它。

反过来也成立：循环里可以把一个固定流程当作一个「动作」。例如「生成周报」这个动作内部是死步骤，循环只负责决定「今天要不要生成、生成完发给谁」。**形态可以嵌套，嵌套的位置决定了风险落在哪一格。** 把循环放在最外层，风险最大；放在一格，风险可控；放在最内层，通常和单轮回答差不多。

还有一层经常被忽略：**工作流不是「不智能」的同义词。** 在可枚举的任务上，工作流比循环更专业，理由和「红绿灯不用 AI 判断」一样——不是做不到，是不该为一件能穷举的事承担不确定性。反过来，把一件分支不可穷举的事硬写成工作流，结果是一堆「其他情况：跳过」，而真实世界的意外恰好都落在「其他情况」里。

### 这个类比在这里失效

「雇一个能干的实习生」是解释 Agent 最顺手的类比：给目标、给权限、给预算，他自己想办法，遇到不懂的来问你。它在两处具体失效。

**第一处：实习生有「上一次」。** 他昨天知道了 B 场地没签约，今天不用你再说一遍。Agent 没有这个「上一次」——除非有人把这条事实写进这一轮的前文里（P2）。所以「它昨天已经知道」这句话，在它今天没被重新告知时是不成立的。这带来一个非常实际的要求：**状态必须被写下来并放回桌上，否则等于没发生。** 跨任务保存「B 场地没签」属于记忆层的活（见 [12](12-memory.md)），本篇只管本次任务的状态。

**第二处：实习生会在没授权时自己拒绝。** 他知道「群发」这件事得问老板，因为他懂规矩。Agent 的拒绝不取决于它懂不懂规矩，取决于运行时那一层有没有拦（见第 17 篇）。你写十句「发送前务必确认」，改不了它有没有权限；能改这件事的是一张权限清单和一个拦得住人的闸门。

两处失效指向同一个结论：**类比让你理解「给目标而不是给步骤」，但不能让你推出「它会自己管理状态和权限」。这两样都得在外面建。**

## 15.4 机制：循环的六个要素

一个能转的循环，必须同时有六样东西。少一样，它转不起来，或者转起来之后停不下来。

```text
                 目标（人给，可验收）
                        │
                        ▼
   ┌──────────────▶ 计划：这一步做什么、为什么
   │                    │
   │                    ▼
   │                动作（模型提议）──▶ 运行时执行（验权限）
   │                                        │
   │                                        ▼
   └──── 状态 ◀────────── 观察：结果 / 报错 / 缺料
          │
          └── 五条停止之一 ──▶ 人：验收、签字
```

六个要素逐个说清：谁提供、谁维护、缺了会怎样、怎么判定它在不在。

| 要素 | 谁提供 / 谁维护 | 一句话作用 | 缺了会怎样 | 判定它在不在 |
| --- | --- | --- | --- | --- |
| **目标** | 人给 | 给循环一个可验收的终点 | 它会自己发明一个终点，通常是「输出一段完整的话」 | 目标能不能逐条打勾 |
| **计划** | 模型，每一步现算 | 说明这一步做什么、依据哪条状态 | 变成随机试探：这一步做这个，下一步做那个 | 每一步能不能说出「为什么现在做这个」 |
| **状态** | 应用保存，人确认 | 已确认的事实、已做过的动作、还没解决的问题 | 每轮从零开始：重复查、重复错、前后矛盾 | 第 5 轮的前文里有没有第 1 轮的结论 |
| **动作** | 模型提议，运行时执行 | 把主意变成一次可执行的操作 | 只剩说话，什么也没办 | 有没有「执行 / 拒绝」的返回，而不只是文字 |
| **观察** | 运行时与工具 | 把外部世界的结果送回决策 | 它在猜自己做了什么，然后基于猜继续 | 下一轮的选择是否引用了上一步的返回 |
| **停止** | 人定条件，运行时执行 | 决定什么时候交回控制权 | 转到预算烧完，或者转到自己认为完成 | 能不能说出这次是按哪一条停的 |

### 15.4.1 目标：必须能被逐条打勾

「把团建搞定」不是目标，是一个愿望。愿望没有边界，所以循环无法判断自己是否接近了它，只能一直做下去，直到做出一个看起来像完成品的东西。

可验收的目标长这样：**一份可发的群通知草稿 + 一张两方案对照表；今天不发。** 这句话里有交付物、有数量、有一个明确的禁止项。三者都能打勾。

目标的质量直接决定循环的长度。目标模糊时，循环不是「更努力」，而是「更久地朝一个不确定的方向走」——这两件事在账单上一样，在结果上完全不同。

### 15.4.2 计划：不是施工图，是这一步的理由

这里的「计划」不是一份事先写完的完整方案。如果一份计划能事先写完，那它其实是工作流，不该用循环。

循环里的计划是**局部的**：这一步打算做什么、依据哪条状态、预期拿到什么。它每一步都会重写。所以判断一个系统有没有「计划」，不能看它有没有输出一份计划书，要看它每一步能不能说出「为什么现在做这个」。

一个具体的对照。第 3 轮，系统选择「读 A 报价并计算」，理由是「人数口径已确认为 39，可以开始比价」。这句话是计划。如果它给不出这句话，只说「正在处理中」，那它在试探，不在计划。

### 15.4.3 状态：循环里最容易缺的一样

状态是「已经确认的事实 + 已经做过的动作 + 还没解决的问题」。它有三个特征，每一个都容易做错。

**第一，它必须是显式的。** 存在模型「脑子里」的状态等于不存在；下一轮的前文里没有它，它就是丢了。这也是为什么循环系统一定要把状态写出来，而不是指望它「记得」。

**第二，它是任务级的，不是长期偏好。** 这一轮确认了「39 人」，任务结束这条就该并进账本，不该变成「这家公司永远 39 人」。把任务状态当长期记忆存，是隐私与正确性的双重风险（见 [12](12-memory.md)）。

**第三，它必须能被检查。** 一份好的状态读起来像一张小表：哪些已确认、依据是什么、哪些还没定、卡在谁那里。人接手时，看这张表就知道该从哪继续。**这也是循环唯一能被人接住的前提**——状态不清楚，人接过来也只能重跑。

要说明一句：状态不是第七本账。六本账是长期对照物（材料、版本、约束、权限、证据、预算），状态是这一次任务的临时工作副本。任务结束时，该并进账的并进去，其余丢掉。把两者混在一起，账本会被一堆一次性细节撑爆。

### 15.4.4 动作：分只读与有副作用

动作有两种，代价差一个数量级。

**只读动作**：查名单、读报价、看档期、检索文档。做错了可以再做一次，最坏的结果是多花一次钱。

**有副作用的动作**：发消息、付款、改名单、删文件、发布。做错了不能靠「再做一次正确版」抵消——错误的那一次已经发生（见第 16 篇）。

循环里必须把这两类分开，因为它们的停止条件不同：只读动作可以自动重试，有副作用的动作不该自动重试。一个系统如果对两类动作用同一套重试策略，它迟早会在「超时但可能已执行」的那一格上出事故（见第 16 篇）。

### 15.4.5 观察：不是它说成功，是运行时说结果

这是六个要素里最容易被糊弄过去的一个。因为「观察」在界面上经常表现为一句「已完成」。

真正的观察至少有三类，而且必须来自运行时，不来自模型的自述：

| 观察的类型 | 长什么样 | 它支持什么判断 |
| --- | --- | --- |
| **成功的结果** | 返回了要查的那条记录、那张报价 | 可以继续下一步 |
| **失败的原因** | 文件不存在、没有权限、日期格式不对 | 该换动作、该修参数，还是该停 |
| **不确定的状态** | 超时、连接中断、只返回了一部分 | 不能当成失败，也不能当成成功；要单独处理 |

第三类最危险。超时不等于没发生：动作可能已经执行，只是回执丢了。这时如果循环把它当成失败并重试，就会做两次（见第 16 篇）。所以「观察」这一格必须能表达「不知道」，而不是只有成功与失败两个值。一个只能表达两种状态的系统，遇到第三种状态时一定会说谎。

### 15.4.6 停止：单独用一节讲

六个要素里，前五个决定「它能不能动」，第六个决定「它会不会停」。而实际事故里，绝大多数不是「动不了」，是「停不下来」。所以下一节专门讲停止。

## 15.5 停止条件：五种停法，一张表

一个循环正常工作的证据，不是它跑了很多轮，而是它在该停的地方停了。五种停止条件，每一种都要有一句可判定的判据，而且这句判据必须写在循环外面。

| 停止条件 | 一句话判据 | 正确收尾 | 错误收尾长什么样 | 谁定这条 |
| --- | --- | --- | --- | --- |
| **达成** | 验收清单逐条对上，且每条有证据（原文、回执、对照），不是它说完成了 | 交交付物 + 证据 + 未定项 | 它写「已完成」，你手里只有一段话 | 人，在任务开始前 |
| **预算耗尽** | 轮次、时间、金额任一触到事先写下的数字上限 | 交出当前进度 + 还差什么 + 已花多少 | 悄悄降级：少查一步、少核一遍，装作跑完了 | 人，写进任务卡 |
| **连续失败** | 同一动作以同类错误失败到事先定的次数，或连续两轮没有新增信息 | 报错 + 已试过什么 + 建议换什么 | 无限重试，或者换个说法再试一次同样的动作 | 人定次数，运行时报数 |
| **需要授权** | 下一步落在权限清单里写「不可」的那一格 | 停在这一步之前，把「准备做什么」交回人 | 先做了再说，或者用一段措辞假装征求过同意 | 人，写进权限清单 |
| **信息不足** | 缺的那条事实无法由现有工具取得，继续只能靠猜 | 列出缺什么、查过什么、拿到后怎么做 | 猜一个合理值填进去，然后继续 | 人定「哪些不许猜」 |

五条里只有第一条是「向前走」，其余四条都是「停下来」。所以判断一个循环写得好不好，主要看它停得对不对，而不是看它跑得多远。

### 15.5.1 为什么停止条件必须写在循环外面

如果把「该不该停」交给循环自己判断，等于让被考核的人自己出考卷。而且这个判断本身也是一次生成：它会倾向于输出「还差一点，再试一次」或者「已经完成」，因为这两种说法在语料里都比「我需要你确认一件事」更像一个称职的助手。

所以停止条件必须是外部的、可数的、运行时可执行的：

- 「最多 8 轮」是可执行的；「注意控制成本」不是。
- 「群发前必须停」是可执行的；「发送前谨慎一点」不是。
- 「同一动作失败 3 次就停」是可执行的；「失败几次就别试了」不是。

这三组对照里，左边都能被运行时直接实现，右边都只能被模型「理解」。而模型的理解是概率性的（P1），运行时的判断是确定的。**在停止这件事上，必须用确定的东西。**

### 15.5.2 连续失败与「换个方法再试」的边界

这条最容易含混。区分只需要一个问题：**动作变了吗？**

- 动作没变，参数没变，只是又试了一次 → 这是重试。重试只在「上一次失败是暂时的」时有意义（网络抖动、服务排队）。
- 动作变了，或者参数变了，依据是上一次的错误 → 这是换方法，属于循环的正常工作。
- 动作没变，但把错误信息原样喂回去再试 → 大多数时候是无效重试，因为错误的原因没有被消除。

所以「连续失败」这条停止条件的准确写法是：**同一动作、同类错误、连续 N 次，且中间没有引入新信息。** 三个条件缺一个，都可能把一次正常的方法切换误判成死循环，或者把一次死循环当成「它还在努力」。

### 15.5.3 五条同时成立时，取最保守的那条

真实任务里，停止条件经常同时触发。第 9 轮，轮次上限是 10，雨天方案还没拿到，草稿已经写完——这是「预算即将耗尽」+「信息不足」+「部分达成」三条同时成立。

规则很简单：**取最保守的那条。** 也就是「信息不足」，因为另外两条还能靠再跑一轮解决，信息不足不能。跑第 10 轮去猜一个室内备选，是把一个「缺一条事实」的问题，变成一个「基于假事实的交付」的问题。

## 15.6 为什么「信息不足时交回控制权」比「继续猜」更专业

这一节是整篇最想说服人的地方，因为它违反直觉：停下来看起来像没干活，猜一个值看起来像在推进。

### 15.6.1 猜错会污染状态，而且会一路污染下去

单轮回答里，一个错数只是一句话；循环里，一个错数会变成一个被后续每一步引用的状态。这个差别不是程度上的，是结构上的。

用团建走一遍。第 2 轮，系统读到名单导出，报出「42 条记录」。此时人数口径不在材料里。它有两个选择。

**选择一：继续猜（按 42 算）。** 于是：预算变成 42×400=16,800；A 方案变成 42×260=10,920，加包车 3,600 是 14,520，看起来「没超预算」；B 方案变成 42×310=13,020，加 3,600 是 16,620，超 1,020。每一个乘法都对，每一个结论都错。更糟的是，16,800 会写进草稿，草稿会被复制，复制件会被贴进群。

**选择二：停下来问。** 成本是一次打断，一句话：「42 是记录条数，按人去重是 39，用哪个？」拿到答案后，后面每一步都建立在 39 上。

两者当下差多少？一次打断。出错后差多少？不是「改一个数」，是「把后面所有基于它的结论全部推翻」——预算、人均、餐位、保险、车座，全都得重算，而且你得先发现它错了。

这里有一个必须点明的细节：**42 这个数不是编的。** 它真实存在于导出表里，模型没有幻觉，它只是把「条」当成了「人」（见 [01](01-ruler.md) 第 02 节那张表）。这一类错误在单轮里叫「口径错」，在循环里叫「污染源」。同一个错，换一个结构，严重程度完全不同。

### 15.6.2 交回控制权不是摆烂，是一个要设计的动作

「我无法完成，请提供更多信息。」这不是交回控制权，这是把问题原样退回。它没有让人更容易决策，只是把难题挪了个位置。

合格的交回带三样东西：

1. **缺什么**，具体到一条事实。「缺人数口径」不够具体；「导出表 42 条记录里有 3 条重复，需要确认是按记录还是按人去重」才够。
2. **为什么现有工具拿不到**，也就是查过什么、返回了什么。「名单表里没有工号字段，无法自动去重」——这句话让人知道不是它偷懒。
3. **拿到之后打算怎么做**，最好给两三个选项和各自后果。「按 39 人算：A 方案 13,740，余 1,860；按 42 人算：A 方案 14,520，余 1,080。我建议按 39，因为 3 条是同一人的重复提交。」

第三样最值钱，因为它把「一次打断」变成了「一次选择」。人只需要说「按 39」，不需要重新把上下文读一遍。

### 15.6.3 三种「交回」，对应三种停止条件

同样叫「停下来问」，实际有三种，混在一起会让系统在该硬的时候软、该软的时候硬：

| 类型 | 缺的是什么 | 对应的停止条件 | 人会怎么答 |
| --- | --- | --- | --- |
| **澄清式** | 一条事实或一个口径 | 信息不足 | 给一个值、给一条规则 |
| **授权式** | 一个许可 | 需要授权 | 批准、拒绝、换人做 |
| **确认式** | 对高风险动作的最后一次确认 | 需要授权（动作不可逆时） | 确认、取消 |

澄清式可以批量问（一次列三条），因为它不涉及风险；授权式必须一次一个，而且必须停在动作之前，不能停在动作之后。把授权式做成澄清式（「我可以发吗？」然后自己回答「应该可以」）是这一篇最常见的失败形态。

### 15.6.4 这个判断什么时候不成立

「宁可停，不要猜」也有代价。停得太频繁，任务永远做不完——一个每轮都要问的系统，和一个每轮都要人盯着的工作流没有区别，只是更贵；有些事实也不值得停，「称呼写哪个」「日期要不要带星期」这类不影响结论的细节，猜错的成本低于打断的成本；还有些场景根本没有人可问，半夜跑的批处理任务停下来就等于失败，这时正确的做法不是猜，而是按预设默认值走，并把「用了默认值」标在交付物上。

所以准确的表述不是「信息不足就停」，而是：**缺的那条事实会改变结论、且无法在事后被发现和纠正时，必须停。** 其余的，用默认值 + 标注。这条界线要写进任务卡，不能靠模型现场判断。

## 15.7 代价：三列账

循环不是免费的。它同时抬高三条曲线，而且这三条会互相加强。这一节把账摊开，每一行都要能回答「这笔代价在什么条件下不值」。

| 代价 | 机制上为什么 | 具体长什么样 | 什么条件下这笔代价不值 |
| --- | --- | --- | --- |
| **不确定性上升** | 每一步都是一次抽样（P3），路径由每一步的选择累积而成 | 同一任务两次跑，先查 A 还是先查 B 不同；轮数不同；措辞不同 | 任务要求可复现、要过审计、要两次结果一致时 |
| **可观测性下降** | 单轮只有一段输出；循环有 N 步，每步都有动作、参数、返回、判断 | 你只看到最后一段总结，中间三次失败被它抹平了 | 没人看日志、或者日志本身没人维护时，记了也等于没记 |
| **成本上升** | 多轮 = 多次输入；每轮通常要把之前的材料重送一遍（P2） | 第 5 轮的输入不是「第 5 步的材料」，是「前四步 + 第 5 步」 | 任务很简单、轮数很少、材料很短时，这点成本可以忽略 |

### 15.7.1 不确定性：不是「它不稳定」，是「它每一步都在选」

单轮回答的差异主要来自措辞；循环的差异来自**路径**。两件事的量级不一样：措辞不同，你读一遍就过去了；路径不同，你可能拿到一个结论相同但依据完全不同的交付物，而其中一条路径可能踩过三次失败又爬出来，另一条一次成功。

这带来一个验收上的硬规矩：**循环任务不能靠「跑一次成功」验收。** 一次成功只说明这条路径通，不说明系统稳定（见 [04](04-sampling-and-reruns.md)）。至少要跑三次，看三件事：结论是否一致、路径是否一致、失败是否出现在同一处。

如果三次结论一致但路径不同，通常可以接受——那是它在适应不同的中间结果。如果三次结论不同，问题不在措辞，在状态或口径。

### 15.7.2 可观测性：至少要记五样

「可观测性下降」不是抽象的抱怨，它有一个非常具体的后果：**出事后你无法定位到哪一步。** 而循环的失败几乎都是「某一步埋了一个错，后面几步把它放大」。

最小记录集是五样，每一步一行：

| 记什么 | 为什么非记不可 |
| --- | --- |
| 这一步想做什么 | 事后才能判断「这个动作本身合不合理」 |
| 依据哪条状态 | 才能查出「它当时以为的事实是什么」 |
| 调了什么、参数是什么 | 才能复现；参数错和逻辑错是两种修法 |
| 返回了什么 | 才能分清「没查到」和「查到了但没用」 |
| 为什么继续 / 为什么停 | 才能判断停止条件是被执行了，还是被绕过了 |

这五样不需要多漂亮，一张表就够。但它有一个反身代价：**记日志本身也花钱、也占地方**。所以不要记全部原文，记「动作 + 参数摘要 + 返回摘要 + 判断理由」。原文留在原始系统里，需要时回查。

一个很实用的判据：**如果你只能看到最后那段总结，你就没有循环，你只有一个更贵的单轮回答。** 因为最后那段总结恰恰是最会骗人的部分——它会把中间所有失败抹平，写成一个顺利的过程。

### 15.7.3 成本：轮次线性，累计输入接近平方

单轮的账好算：一次输入，一次输出。循环的账不好算，因为每一轮都要把前面的东西重新带上。

粗略的形状是这样的（**示意，不是任何产品的计价公式**）：如果每轮都把全部历史重送，那么第 n 轮的输入大致是前 n−1 轮之和，跑到第 n 轮时，累计输入的量级接近 n²/2。轮次翻倍，累计输入大约翻四倍。这不是精确等式，因为实际系统会做压缩、会复用前缀、会只带摘要；但形状是对的：**轮次的成本不是线性的。**

再叠上两笔：失败重试（每一次重试都是一次完整调用）和工具返回（一份长文档原样返回，可能比问题本身长十倍）。这两笔在单轮里不存在，在循环里是常态（完整账单与优化顺序见第 21 篇）。

所以「让它自己多试几次」这句话，在账单上的意思是「多买几份输入」。这不必然是错的——如果多试几次能把成功率从「要人返工」提到「一次过」，那这笔钱花得值。但要说清买的是什么，不能把它当成免费的智能。

### 15.7.4 三条曲线会互相加强

这是三列账里最需要警惕的一层，也是它不能拆开看的原因：

```text
（示意）循环里的一个正反馈

  不确定性上升 ──▶ 你不敢只跑一次 ──▶ 多跑几次
        ▲                                  │
        │                                  ▼
  更不敢信 ◀── 可观测性更差 ◀── 想省成本，少记日志
        ▲                                  │
        │                                  ▼
        └──────────── 成本上升 ◀───────────┘
```

这个环的每一段都「合理」：多跑几次是为了稳，少记日志是为了省，不敢信是因为确实看不出差别。合起来就是一个越跑越贵、越跑越不敢用的系统。

**切断它的地方只有一个：把验收和停止条件写在循环外面。** 验收写好了，跑三次就够，不需要跑十次；停止条件写好了，轮次有上限，成本可预算；记录只有五样，不记原文，可观测性的成本被压到很低。三件事都在循环外面，所以它们不受循环内部那个正反馈的影响。

## 15.8 边界：什么时候 Agent 是负优化

先说结论：**在简单任务上，Agent 是负优化。** 不是「效果差一点」，是「更慢、更贵、更不稳定，而且没有任何一项变好」。

### 15.8.1 四个判据：四条都成立，就该用工作流

| 判据 | 问什么 | 成立的例子 |
| --- | --- | --- |
| 步骤能事前穷举 | 一屏能不能把步骤写完 | 每周固定格式的销售周报汇总 |
| 每步输入输出格式固定 | 换一份材料，步骤变不变 | 从 100 份简历里抽五个固定字段 |
| 失败模式已知可枚举 | 可能出的错能不能列成一张表 | 合同条款与标准条款逐条比对 |
| 验收可完全自动化 | 能不能用程序判定对错 | 发票金额与明细是否对得上 |

四条都成立时，工作流在三个维度上全面胜出：更快（没有多余的判断）、更便宜（没有多轮输入）、更可审计（每一步的输入输出都是确定的）。这时上 Agent，唯一的收益是「看起来更先进」。

四条里只要有一条不成立，循环才有价值。最典型的是第一条：分支不可穷举。团建这件事就是——「B 超了 90 元怎么办」取决于算出来的数、预算的弹性、以及人对「团建感」的偏好，事前写不完。

### 15.8.2 中间形态：只让循环做「分类与路由」

如果整件事大部分可枚举、少部分不可枚举，最省的做法不是全上循环，而是**让循环只负责一件事：把任务分到几条固定工作流之一**。来件进来，先由循环判断「这是什么请求、缺哪些材料、该走哪条流程」，然后交给报销、请假、采购三条固定流程之一，或者退回人。

这样，不确定性只在分类那一步，之后全是可审计的步骤。分类错了，影响面也只有一条流程，不会污染整条链。

### 15.8.3 三个「该退回工作流」的信号

这三个信号都能在运行中观察到，不需要重新设计：

1. **最近十次跑，路径有九次一样。** 那条路径就该被写死。继续用循环，只是在为「万一不一样」付十次的钱。
2. **同一类失败反复出现，而且每次都要人接。** 这不是「模型还不够强」，是缺一道校验或一个固定步骤。换更大的模型不会让这一类失败消失，只会让它以更流畅的方式发生。
3. **成本主要花在「重新确认已经知道的事」。** 说明状态没写好——每一轮都在重查同一份名单。修状态比换模型便宜得多。

### 15.8.4 三列账：能做什么 / 代价 / 何时失效

| 动作 | 能做什么 | 代价是什么 | 何时失效 |
| --- | --- | --- | --- |
| 用循环处理不可穷举的分支 | 遇到事前没想到的情况还能继续 | 不确定性、可观测性、成本三条同时上升 | 分支其实可枚举时，纯亏 |
| 把循环嵌进工作流的某一格 | 把不确定性关在一个格子里，前后可审计 | 格子之间的接口要设计；格子的输出格式要固定 | 格子输出格式不稳时，前后衔接会断 |
| 用循环做分类与路由 | 只在一处承担不确定性，成本可控 | 分类错会把任务送进错误流程 | 类别边界模糊、且错了没人发现时 |
| 自动重试只读动作 | 吸收网络抖动、服务排队 | 多花调用；日志变长 | 失败原因是参数错或权限错时，重试无用 |
| 自动重试有副作用的动作 | 几乎从不值得 | 可能做两次；超时那一格无法区分 | 任何不可逆动作上，都不该自动重试 |
| 让循环自己判断该不该停 | 看起来省了一个外部条件 | 判断本身是抽样，会偏向「再试一次」或「已完成」 | 涉及钱、权限、不可逆时，绝不能用 |

## 15.9 反例与正例：同一句「帮我搞定」

### 15.9.1 反例：一句话总目标

> 你帮我把团建搞定，能用的都用上。

这句话里有目标（搞定）、有授权（能用的都用上）、有期望（完整），但没有任何一条可判定的东西。于是循环自己补全了缺的部分——用最像「一个称职助手」的方式。

```text
（示意）一条典型的失控链

一句话总目标
  ──▶ 它自行判断「搞定 = 把通知发出去」，先去起草
  ──▶ 运行时拦下群发（权限在这一层才生效，不在它的理解里）
  ──▶ 它改去算预算，用了 42 条记录
  ──▶ 得出 16,800，写进草稿正文
  ──▶ 为了「完成」，把雨天方案写成「已安排室内备选」
  ──▶ 输出一段完整、流畅、处处有错的交付
```

四处错，每一处单独看都「合理」：发通知是合理的目标理解；42 真的在表里；16,800 是正确乘法；写「已安排室内」是为了让通知完整。**这正是循环最危险的地方——它会把每一个小错都接着往下用，直到最后看起来像一个完整的东西。**

注意第三行的细节：拦下群发的不是模型，是运行时。这说明权限这一层是对的，但它只挡住了「发出去」，没挡住「写一份准备发的东西」。而一份处处有错的草稿，只要有人点一下发送，后果和自动发送一样。

### 15.9.2 正例：任务卡五段 + 五条停止条件

同一个人、同一份材料，换一种给法：

| 段 | 内容 |
| --- | --- |
| **目标** | 一份可发的群通知草稿 + 一张 A/B 两方案对照表；今天不发 |
| **材料** | 通知 v2（v1 已作废）、A 报价、B 报价、名单导出（42 条）、包车询价 |
| **边界** | 可起草、可查名单；不可群发、不可付定金、不可改名单。不猜人数口径、不猜 B 档期、不猜雨天方案 |
| **交付** | 通知草稿；对照表（含合计与是否超预算）；待确认清单（每条注明「问谁」） |
| **验收** | 日期回 v2 原文；人数分列 42 与 39；A 合计 13,740；B 15,690 且标「超 90」；雨天与 B 档期只出现在待确认清单，不出现在正文里被写成已定 |

有了这五段，循环的行为变了：

```text
（示意）同一条链，加上边界之后

目标 + 验收 + 权限 + 停止条件
  ──▶ 读 v2：10 月 25 日；v1 作废；雨天「待确认」
  ──▶ 读名单：42 条记录 ──▶ 信息不足 ──▶ 停，问口径
  ──▶ 人答「按人去重」──▶ 39
  ──▶ A：10,140 + 3,600 = 13,740（余 1,860）
  ──▶ B：12,090 + 3,600 = 15,690（超 90，标「不可作为方案」）
  ──▶ 起草；未定项留空，进待确认清单
  ──▶ 需授权：群发 ──▶ 停，交回人
```

对照两边，差别不在模型，在**每一条停止条件都有对应的那一句话**：「不猜人数口径」对应第 2 轮停；「不可群发」对应最后停；「雨天只进待确认清单」对应起草时不补全。

| 五个停止条件 | 反例停在哪 | 正例停在哪 |
| --- | --- | --- |
| 达成 | 没停：它认为写完就是完成 | 停：验收五条逐条对上才交 |
| 预算耗尽 | 没设，跑到它自己认为完成 | 设了轮次上限；本例 5 轮内完成 |
| 连续失败 | 没设，失败后换说法再试 | 设了；本例未触发 |
| 需要授权 | 撞上了才被拦（拦在群发） | 停在群发之前，把草稿交回 |
| 信息不足 | 用 42 猜过去，还猜了雨天 | 停在人数口径，雨天进待确认清单 |

这张表最值得看的是第一行：反例其实也「完成」了，只是它的完成标准和你的不是同一个。**没有验收清单时，「完成」由它定义。**

## 15.10 你可以自己做的检验

十分钟，不需要写程序。目的是把「它有没有循环」和「它的停止条件是什么」这两件事分开看。

### 15.10.1 主检验：「若失败则——」填空（10 分钟）

**准备**：选一个你常用的、声称能自动完成多步任务的产品；准备一个**必然会在中间失败**的任务（给一个不存在的文件名、一个查不到的日期、一个没有权限的账号）。

**做法**：

1. 先把任务写成一句：「先做甲，再做乙，**若某一步失败则**……」，把这个空留着。
2. 把前半句交给它跑。
3. 只观察一件事：它替这个空填了什么。

| 它的反应 | 说明它有没有循环 | 说明它的停止条件是什么 | 风险 |
| --- | --- | --- | --- |
| 原样重试同一动作 | 有观察，但没有「连续失败」这一条 | 只有预算 | 烧钱；可能重复副作用 |
| 换一个动作再试 | 有观察，有换方法的判断 | 缺「连续失败」边界 | 可能越换越远，偏离目标 |
| 跳过失败那步继续 | 有循环，但目标里没有「这条必须成立」 | 只有达成 | 交付物看起来完整，缺一块 |
| 停下来问你，且问得具体 | 有观察，有「信息不足 / 需授权」 | 至少两条 | 打断频率是唯一成本 |
| 报告「已完成」 | **没有观察**，只有动作 | 无 | 最危险：错被写进交付物 |

**判据**：如果它在失败后仍然报告成功，说明它没有把结果送回过决策——那是工作流，且是一条没有错误处理的工作流。如果它无限重试，说明它有观察但没有停止条件。**这两种都不是 Agent，第一种比第二种更危险，因为它看起来更像。**

**这条检验能推翻本文结论的情形**：如果某个产品在失败后既不停下问、也不重试，而是把失败如实写进交付物并标「未完成，原因是……」，那它其实做对了——这说明「停下来」不等于「必须问人」，把失败如实交出去也是一种合格停止。本文的结论应该被收窄为：**合格的停止是「控制权交回 + 缺什么说清楚」，不是「必须弹出对话框」。**

### 15.10.2 记录表

| 检验 | 固定什么 | 只改什么 | 观察什么 | 什么结果会推翻文中结论 |
| --- | --- | --- | --- | --- |
| 失败填空 | 任务、材料、产品 | 失败发生在哪一步 | 重试 / 换法 / 跳过 / 停问 / 报成功 | 失败被如实标注且交付可用 |
| 三次重跑 | 任务卡、材料、产品 | 只重跑 | 结论、路径、失败位置 | 三次路径与结论都完全一致且成本不变 |

表里第二行（三次重跑）是 15.7.1 那条硬规矩的操作版。它不需要十分钟，但需要你愿意接受一个不太舒服的结果：**同一份任务卡，跑三次，路径很可能不一样。** 这不是它坏了，这是循环的结构决定的（P3）。你要判断的是「结论是否一致」，不是「过程是否一致」。

## 15.11 术语考古：Agent / 工作流 / 循环

这三个词在会议里几乎总是混着用。甲说「我们上了 Agent」，可能指接了两个工具；乙说「这就是个工作流」，可能指界面上有连线的编排；丙说「它没循环起来」，可能指它失败后不会重试。三个人争一小时，其实在争三件事。

每个词给四栏。**没有可靠出处的标「社区用语」，不编年份，不指认文献。**

### Agent

| 栏 | 内容 |
| --- | --- |
| 最早出处 | 一般用语，源自「行动者」；在 AI 领域长期指「能感知环境并采取行动的系统」。**跨领域借用的社区与学界混用词，没有单一发明人，也没有统一规范定义。** |
| 原义 | 强调**行动**与**环境反馈**，不强调「会聊天」，也不强调「有几个工具」。 |
| 现在被怎么用 | 常被用来指「带工具调用的聊天产品」，甚至只是「预设了提示词、有名字的助手」；也有产品把「自动跑几步」叫 Agent，把「可视化编排」叫另一个名字。同一个词在两家产品里可能指两件不同的事，甚至同一家产品的两个版本里含义也不同。 |
| 本文怎么用 | 只有出现「**看结果 → 决定下一步**」的循环，才叫 Agent。工具数量、名字、界面、是否自称「自主」，都不参与判定。判据是 15.2 那一句替换测试：把某一步的返回换成失败，看下一步变不变。 |

### 工作流

| 栏 | 内容 |
| --- | --- |
| 最早出处 | 来自办公与工业流程里的 workflow，指一组按既定顺序流转的步骤。**工程与产品里的通行说法，没有统一规范定义。** |
| 原义 | 步骤与流转条件**事先定义**；谁在什么条件下把活交给谁，是写下来的。 |
| 现在被怎么用 | 有时指「可视化编排」这个产品功能；有时被当成「不智能」的同义词；营销里也把带模型的固定流程叫 Agent，于是「工作流」和「Agent」的边界在产品话术里被抹掉了。 |
| 本文怎么用 | 指「下一步去哪由预先写下的规则决定」的形态。**它不带贬义**；在可枚举的任务上，它比循环更专业。工作流里可以有模型，模型也可以只占其中一格。 |

### 循环

| 栏 | 内容 |
| --- | --- |
| 最早出处 | 控制论里的「反馈回路」：输出被送回输入，系统据此调整。**这是跨领域借用的概念，不是 AI 专有，也没有单一发明人。** |
| 原义 | 有回读、有比较、有调整。没有回读的重复不叫循环，叫重放。 |
| 现在被怎么用 | 被当成「多跑几轮」「多调几次模型」；把失败重试也叫循环；把「多 Agent 互相说话」叫循环，即使谁也没有因为对方的话改变下一步。 |
| 本文怎么用 | 必须满足一条：**观察进入下一轮的决策**。重试同一个动作不算循环（没有新信息），换动作才算。轮数多不等于循环，工具多也不等于循环。 |

三个词共同的毛病是同一个：**把「有没有那个动作」当成了「有没有那个结构」。** 有工具 ≠ 有循环；有循环 ≠ 有停止条件；有停止条件 ≠ 停对了地方。三者要分开验。

## 15.12 一页速记

| 你看到的现象 | 机制上最可能发生了什么 | 先做什么 |
| --- | --- | --- |
| 它调了五个工具，还是答错 | 路线是写死的，结果没有回到决策 | 做 15.2 的替换测试：换个失败返回，看下一步变不变 |
| 同一任务两次路径不同 | 正常：每一步都在抽样（P3） | 比结论，不比路径；跑三次看结论是否一致 |
| 它一直重试同一个动作 | 有观察，但没有「连续失败」这条停止条件 | 查它有没有轮次上限；查有没有把错误原因喂回去 |
| 它说「已完成」，交付物缺一块 | 目标里没有「这条必须成立」，观察被跳过了 | 回原始系统核；补验收清单，不是补提示词 |
| 它猜了一个数继续跑 | 缺「信息不足就停」；或者没人可问又没标默认值 | 查这条事实会不会改变结论；会，就必须停 |
| 账单比单轮高好几倍 | 多轮输入 + 重试 + 长工具返回 | 先看轮次，再看每轮带了多少历史（第 21 篇） |
| 出事后查不出哪一步错 | 只留了最后那段总结 | 补五样记录：想做什么、依据什么、调什么、返回什么、为什么停 |

**五句话带走**

1. Agent 多出来的不是更强的模型，是一个「看结果再决定下一步」的循环；没有它，十次工具调用也只是工作流。
2. 单轮、工作流、循环不是三代，是三种取舍；差别在不确定性被放在哪里；Agent 可以嵌在工作流里当一格。
3. 循环六要素：目标、计划、状态、动作、观察、停止；最容易缺的是状态与停止。
4. 五种停止：达成、预算耗尽、连续失败、需要授权、信息不足；只有第一种是向前走，其余四种都是交回控制权。
5. 信息不足时猜一个值，会把状态污染成一条错误的前提链；停下来的成本是一次打断，猜错的成本是一次返工加一次信任损失。

**三道自检**

1. 同事说：「这个产品能查天气、能读文件、能发邮件，所以它是 Agent。」这句话错在哪？你会用哪个动作验证？
2. 一个循环跑到第 9 轮，轮次上限是 10。通知草稿已经写完，但雨天室内备选还没确认。它应该用第 10 轮去猜一个备选吗？
3. 同事说：「上次它自己跑完了，挺聪明的，以后这类活都交给它。」这句话缺了什么？

<details>
<summary>查看参考答案</summary>

1. 错在把「有工具」当成了「有循环」。工具数量、种类、界面图标都不参与判定；判定只有一个动作：把某一步的工具返回换成失败或空结果，看下一步是否改变。不变，就是一条工作流被拆成了几段。第 2 问在这里也要跟着问：上一轮的结果，真的被放回这一轮的前文里了吗？如果只在界面上闪了一下、没有进入下一轮的输入，那连「观察」都不成立。

2. 不应该。雨天备选属于「信息不足」，不是「多试一次就能拿到」——它不在任何可查的系统里，只能问人。第 10 轮的唯一合法用途，是把「缺什么、问谁、拿到之后怎么写」写进待确认清单。而且这里同时触发了「预算即将耗尽」与「信息不足」两条，按 15.5.3 的规则取最保守的那条。猜一个「已安排室内备选」写进通知，就是 15.6.1 那条污染链的起点：这个假事实会进草稿、进群、进当天的执行。

3. 缺三样。第一，那一次的路径是什么——循环任务不能靠「跑一次成功」验收，至少要三次，看结论是否一致（P3，见 [04](04-sampling-and-reruns.md)）。第二，它的停止条件在哪——失败时它会重试、跳过，还是报告成功？这一条决定它出错时你是被通知，还是被骗。第三，成本是多少——多轮输入不是线性增长，加上重试和长工具返回，单任务成本可能是单轮的好几倍。「挺聪明的」是一句印象，不是一条可复用的判据。

</details>
