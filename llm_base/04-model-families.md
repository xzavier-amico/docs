# 04 · 模型家族：Encoder、Decoder 与 Embedding 分别做什么

> **状态**：已完成（初稿）
>
> **本篇定位**：区分模型内部的架构、外部交付的能力，给生成、翻译、分类和查找相似资料选合适的工具。
>
> **读法**：先用两轴图找任务的位置，再看语义地图和多模态边界；想选型，可以直接做文末的纸面试用计划。

## 你要的是一段通知、一列标签，还是两条原文？

虚构市集的交接包里有摊位报名表、旧海报、现行公告和几张摊位照片。原定周六，现行 v2 改为**周日 14:00**，雨天是否改室内待确认，旧 v1 已失效。任务只整理报名清单和通知草稿，不发送。面对同一堆材料，你可能要写新通知、给报名分组，或者从一串公告里找出有关改期的段落。这三种请求拿到手的结果不同，不见得用同一种工具最省事。

**本篇的真问题：我想生成、翻译、分类或找相似资料，应该选什么？** 可以分两条轴问：内部**怎么处理信息**，外部**交付什么**。下面的格子是常见例子，不是能力许可表；空格也不表示该架构做不到。

```text
                          任务轴 →  生成或转换          分类与标注          向量表示供检索
架构轴 ↓
Encoder-only                        —                   常见用法            常见用法
Decoder-only                        常见用法            可用指令生成标签     有专门训练的做法
Encoder–Decoder                     常见于翻译、摘要    也能生成标签         —
```

| 架构 | 先理解成怎样的分工 | 常见交付与注意点 |
| --- | --- | --- |
| **Encoder-only（仅编码器）** | 读完一段给定输入，在常见设计里各位置都能利用前后线索 | 接上任务部件，可为报名备注打标签，或把材料变成向量；通常不承担逐步写长篇草稿 |
| **Decoder-only（仅解码器）** | 把已知输入和已写出的内容接在一起，逐步生成后续 | 常见于聊天、起草和开放式生成，也能按指令输出固定标签；「能输出」不等于稳定符合标签集 |
| **Encoder–Decoder（编码器—解码器）** | 一边把给定原文读成内部表示，另一边参照这些表示和已写内容逐步输出 | 常见于翻译、摘要等从一段到另一段的任务；翻译并非这个架构独有 |

「Decoder-only」不是说它不会读，而是说它不用分开的编码器来读入这段文字。反过来，「Embedding 模型」也不是与 Encoder、Decoder 并列的第三种结构：它更常指为特定向量表示任务训练并交付向量的模型。看产品或模型说明时先问**输出到底是什么**，不必从名字猜完所有能力。

## 两种都叫 Embedding 的东西，不是同一张卡

| 名称在这里指什么 | 谁一般会使用它 | 该怎么检验 |
| --- | --- | --- |
| 模型内部的**输入向量** | 模型把一个 Token 的编号对应到数字表示，作为后续处理的输入 | 它不是现成的文档索引，不能抽一块就当成整份公告的检索向量 |
| Embedding 模型**交付的向量** | 搜索、推荐、去重候选等应用拿它比较短句、段落或其他对象 | 用相互兼容的向量模型或编码方式来比较；拿实际查询验证召回和排序，而非凭坐标猜真相 |

可以把检索向量想成语义地图上的坐标。下面是**手画示意**，没有实测坐标和距离；相邻只表示话题很像，位置本身不说明哪一份是现行规则。

```text
  改期话题：  ● 查询「市集改到哪天」
              ● v2：本场周日 14:00（有效）    ● v1：本场周六（失效）
                                                ● 上一届改期说明（别场）

  报名话题：  ● 食品摊报名须填品类             ● 报名表疑似重复项
```

最危险的不是找到完全无关的文章，而是旧 v1 语义很像、读起来也像正经通知。查到相似材料之后，还要核活动身份、发布者、生效状态和相关段落；有条件可结合活动编号、版本字段或关键词找资料。碰到 v2 只写「雨天是否改室内待确认」，即使上一届真有室内备用场地，也不能拿去替本场决定。检索可以帮你找到原文，不能为原文没说的事作证。

## 多模态：能接收图片，不等于能制作视频

有些模型或应用除文字外还支持图片、音频等**模态**。例如，视觉处理部件可把照片转成模型能用的内部表示；也有应用先从图片提字、先把音频转写，再把文字交给语言模型。两种界面都可能显示「已上传」，但模型收到的材料不一定相同。只收到转写时，别让模型去判断录音里转写遗漏的语气、停顿或背景声。

| 市集的实际需求 | 针对性检查 | 常见失效方式 |
| --- | --- | --- |
| 读旧海报和 v2 截图里的时间 | 能否接收图片、识别小字，并把版本和具体原文对应上 | 模糊小字、裁掉的版本号或旧图转发都可能造成误判；最好核对主办方原文 |
| 整理语音交接里的待办 | 是直接处理音频，还是只拿到转写；关键处能否回听 | 录音把「还没定」听成「定了」，就会把未决事项写错 |
| 为通知写新海报文案 | 看它能否按批准文字和限制起草 | 能写文案不等于能交付图片；看图和生图是两种能力 |
| 需要成片或海报图片 | 单独验收是否支持对应输出，再检查画面和关键字 | 产品可能调用另一个生成模型；能生图不等于能正确排出时间，也不代表获得发布权 |

## 选型别只看模型大小

**参数量**说的是模型有多少学习得来的内部数值，像在描述模型本身的规模；**上下文长度**说的是一次能处理多少序列内容，像在描述工作台能放下多少材料。桌子大不代表每张纸都会看对，模型参数多也不保证工作台更大。两者都不是**实际任务能力**：准确分清 v1 和 v2、识别一张低清图、把多份报名表整理对，得用你的样本验证。模型训练、所用工具、应用如何组装输入，都会影响结果。产品实际接收的材料也可能比模型标称支持的少。

### 手工练习：给候选产品做一张试用卡

拿虚构材料做一次纸面测试计划，不用开通多个产品。先分别写下要得到的三样东西，再为每样写一条能判通过的条件：

1. **名单标签：** 给「水果摊」和「数码体验摊」分组，信息不足的单列待核；没有足够证据不合并同名行。表不大时，先比较人工筛选、规则和模型，不为分类专门上一个大的聊天模型。
2. **公告依据：** 给候选工具 v1、v2 和上一届公告，看能否找到而且区分三份材料。只找到很相似的 v1 或把上一届政策当本场结论，都不过关。
3. **通知草稿：** 用同一份现行 v2 和同样的指令比较候选；核「周日 14:00」「雨天待确认」「未发送」，再看语气与校订时间。有截图的用例另外测读图，不拿纯文本的成绩替代。

| 试用后看到什么 | 下一步怎么选 | 代价或边界 |
| --- | --- | --- |
| 小模型用可靠材料就能持续达标 | 保留更便宜或更快的方案，不为榜单换模型 | 样本需有冲突版本、缺字段等容易出错的情况，不能只试最简单一条 |
| 主要错在找错资料 | 先修检索范围、权威来源和版本；给生成模型固定证据重测 | 换更大的模型也不能凭空看见没找到的 v2 |
| 接收图片但常认错截图小字 | 加原文核对、用清晰材料，再找更合适的视觉工具 | 增加核验时间；不把私人报名截图传给不允许接收的服务 |
| 排序正确，仍经常写错事实 | 把版本、事实和未决项设成验收关，再考虑更合适的生成模型 | 不能用更自然的语气抵消错时、错地或越权 |

**速记：** 架构回答「怎样处理」，任务回答「交付什么」。相似度负责找候选，不负责有效性；看图、听音频和生成媒体各自验收。选型看任务通过率、延迟、成本和资料边界，再看规格表。

### 自检（含简答）

1. **需要从成堆通知里找到相似段落，为什么不先让聊天模型写答案？** 先找并核对候选能拿到依据；聊天生成可以接在证据之后，不能替代证据。
2. **甲模型参数更多，乙产品允许送进更长的文本，谁更适合市集交接？** 仅凭这些无法判断；用同一批含新旧版本、歧义记录的样本验证任务质量与代价。
3. **能读旧海报，是否表示能做新版海报或发布通知？** 都不表示。读图、生成图片和执行发布是不同能力与权限。
