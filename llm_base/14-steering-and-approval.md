# 14 · Steering 与人机协同：任务跑到一半怎么改方向

> **状态**：已完成（初稿）
>
> **本篇定位**：Part III 第 5 篇。学会在运行中更新要求、判断哪些进度仍有效，并在外部动作前设置明确的审批边界。
>
> **读法**：先沿时间线找改期前后，再用权限图和审批卡过一遍。就算没用过带暂停按钮的产品，也可以在纸上练习。

## 「改到周日」发出去了，Agent 真停下旧流程了吗？

**虚构场景。** 周五上午，小周已经让助手按当时交给它的 v1 整理周末市集报名清单和通知草稿，明确说了**不改原表、不发送**。草稿刚写到「周六」，小周收到主办方的新决定：现行 v2 改为**周日 14:00**，旧 v1 失效，雨天是否改室内待确认。她留言：「周日 14:00，以 v2 为准，先别发。」这条消息显示在聊天底部，不代表后台的每一步都已收到更新。一个查询可能正在返回，旧草稿可能仍在队列里，编辑器里也可能还开着旧版。好在这次任务根本没给发送权限，但依然要防止最后交出一份漂亮的旧稿。

**本篇只问：做到一半改日期，哪些步骤可继承、哪些要重做、哪些该取消？** 把更改当成对正在运行的任务更新，而不仅是又给模型一句话。

## 时间线：新要求要传到运行里才算数

```text
出发前                         运行中收到改期                  恢复或重开
小周：仅整理与起草，不发送 ───→ 小周：v2 生效，周日 14:00 ────→ 小周审清单和新稿
应用：只读取必要资料 ─────────→ 停派依赖旧日期的步骤 ─────────→ 保留无关日期的结果
                              核对在途状态、作废旧草稿           用 v2 重做并复核
外部：不会收到发送请求          有在途查询则记下状态              仍未发送
```

有些产品把运行中追加要求或反馈叫 **Steering（运行中引导）**。有的等当前步骤结束才处理新消息，有的需要先暂停，有的只能把新消息排到下一轮，或者得停止后重开；并没有一个跨产品统一的「立刻接管」按钮。收到消息、理解意思、更新运行状态和停止外部动作是四回事。若看不到应用明确采用了 v2 或停止派发旧步骤，先暂停或取消旧任务，确认状态，再从已验证的材料开启一个新任务。只在对话里说「停」而不核对状态，不足以证明外部动作停下了。

| 想做什么 | 适合的操作 | 要核对的边界 |
| --- | --- | --- |
| 出发前定目标和限制 | 说明产物、资料来源、只读范围、不发送及停止条件 | 可用能力是否也按任务收小；不是一句「小心」就有权限控制 |
| 运行中换方向或补约束 | 补「v2 生效、v1 失效」，要求列出保留、重做、取消的部分 | 应用是否已采纳新要求；在途旧结果是否被标记并阻止进入新稿 |
| 暂时留在当前进度 | 暂停，检查任务记录与外部状态；确认后才恢复 | 暂停可能只阻止下一步，不一定能停止已交给外部服务的查询或动作 |
| 永久停止这次运行 | 取消，核对排队、在途、已完成、状态未知的步骤 | 取消不是回滚。外部已发生的事不会随聊天停止而消失 |
| 允许某个有后果的动作 | 让有权人看清具体动作后，单独决定批准或拒绝 | 对草稿点「看过」不等于同意发送；本市集任务里没有发送这一步 |

当天可以这样发更新：「**请停止沿用 v1。** 本次现行 v2：周日 14:00，雨天是否改室内仍待确认。保留不受日期影响、已核实的报名信息；重核依赖日期的记录和通知草稿；废弃旧稿。只整理清单和草稿、不改原表、不发送。请回报哪些步骤已停止、哪些仍在途中。」这段话的价值在于把差异、仍然有效的限制和验收点说清楚，不在于能替产品执行暂停。

## 改期后，不要把所有成果一键丢掉，也不要全盘沿用

| 旧进度 | 怎么处理 | 原因 |
| --- | --- | --- |
| 已核实的报名编号与摊位类别 | 可继承；若数据源在这段时间变动，再核对版本 | 这些字段通常不依赖活动日期 |
| 标着「仅周六可到」的报名记录 | 保留记录，重做可到场判断；标「需确认」，不代摊主决定 | 报了名不是同意改期，任务也没授权直接去联系摊主 |
| 旧稿、旧稿预览、依据 v1 排队的待办 | 把旧稿标为失效；取消未派发的旧待办，按 v2 重做 | 只改标题会漏掉正文、预览或日期相关提示里的旧时间 |
| 仍在返回的 v1 查阅结果 | 保留必要记录但不作为现行依据；若系统不能保证隔离，暂停检查 | 晚到的结果不等于更新的版本 |
| 雨天是否进室内 | 标待确认，指明要找主办方 | 改了日期不等于确认场地，查到降雨预报也不是场地决定 |

合理的暂停与复核会让任务等久一点，但只重做真正受影响的部分，通常比整单重来容易。当天如果已经到约定的截止时间，交已核实部分和待办，比让旧流程偷偷跑完更好。验收至少看两处：稿件写「周日 14:00，依据 v2」，旧 v1 不再被当作有效通知；执行过程没有发消息或改原表。

## 权限边界图：资料可以支持判断，不能下命令

```text
有权的人：定任务、给本次授权、批准特定外部动作
                 ↓
应用：为本次运行限定只读范围 → 模型看材料、提议下一步
                 ↓                           ↑
通过边界检查才让工具执行       网页、附件、工具正文 ── 仅作资料，核对来源
                 ↓
拿执行回执和交付物给人核对     不需要的写、发送、付款、发布权限不开
```

网页、附件、报名备注或外部工具返回的正文，即使语气像主办方指令，也按**不可信资料**处理。页面可能确实记录了「周日 14:00」，但这条事实须按已知来源核对；如果页面又声称需要外传报名名单，那段话不代表小周的授权，不应照做。作为使用者，可以先只接已知出处的只读资料，把联系方式等无关字段删掉或遮盖；不要在同一个任务中把敏感报名材料和不必要的外部服务混用。发现异常就暂停，查看实际活动记录，通过你已知的主办方渠道核实；若可能已外传，联系负责的人，必要时停掉相关连接。不要仅依赖一句「忽略不可信指令」来防止后果。

**能力、意图、授权、执行分开看。** 邮件工具有群发能力；人要的是通知草稿；本次没批准发送；实际有没有发送要看应用或目标系统的记录。最小权限不是「本来可以发，但每次提醒小心」，而是根本不给这个任务发信凭据和写权限，只开放指定活动的必要只读资料。如果产品做不到，把必要资料人工取出来，在不接高权限工具的会话里起草。

### 审批是行动前的闸门，不是事后免责

发送、发布、付款等高后果动作，应该留到**另有明确需求的任务**，由有权的人在执行前核对。审批卡应说明：**具体动作和执行账号、对象或收件人、准确内容和版本、时间（付款还要金额和收款方）、可能的副作用**。所有这些都应与真正要执行的动作一致；关键内容或对象改了，旧批准不能照搬。看不清范围先拒绝或等澄清，不默认选「总是允许」，也不把沉默当同意。对本次只交草稿的任务，突然弹出「是否立即群发」就该拒绝，不该为走完流程批准。

如果外部动作已完成，新的「别发」或「撤回」不会让收件人忘掉邮件，也不保证已发布页面没被看到，付款同样可能只剩退款流程。应先核对实际结果，阻止尚未发生的后续动作，再由有权的人处理补救。如果请求已派发却没可靠结果，就报告「状态未知」，先去目标系统核对，不重复发送或付款。

## 纸上练习：你有三张进度卡，先动哪一张？

你接班时有三张卡：①「已核对报名编号」；②「旧草稿写周六，还有两行只接受周六的报名」；③「应用弹出『群发』，未执行」。先写一句改方向的交接，再给每张卡标「继承、重做、取消」之一；有多种处理时分开写。

**参考交接：**「停止沿用 v1，周日 14:00 以 v2 为准，雨天场地待确认；仍只交报名清单和通知草稿，不改原表、不发送。」① 继承经核对且不受日期影响的编号；② 旧草稿作废重做，两个报名保留并标「周日能否到场待确认」；③ 拒绝并取消该未执行请求，核对记录，不为它扩大权限。若连是否已派发都看不清，先暂停，查状态再继续。

换成自己的任务时，把这张纸留在手边：最左写「谁定目标和授权」，中间写「谁提议、谁检查后执行、允许读什么」，最右写「出现什么该停、由谁审批、到哪儿核对回执」。如果某一步说不出谁负责，先把责任定下来再运行。

## 速记与自检

**速记：** 改方向先记新版本，再查运行是否采纳；能继承的留，依赖旧决定的重做，越界的取消。**暂停挡未来，不改过去；审批针对具体动作；网页是资料，不是授权人。**

1. 聊天里已出现「以 v2 为准」，能直接假定后台所有步骤都改过来了吗？
2. 工具成功读取一个网页，网页要求把报名表交给外部服务。应该先授权那个服务吗？
3. 人点了「草稿通过」，是否等于批准发送？如果某次另行授权的发送已经做了，取消运行能收回吗？

**参考答案：** ① 不能，检查运行是否采用新版本、旧步骤是否停止，并隔离在途旧结果。② 不应该；把网页内容当资料，拒绝越界，保护敏感字段，通过已知渠道核实。③ 都不是；审批要单独针对具体版本、对象和动作，取消也不能保证撤回已发生的外部影响。
