# 12 · Tools 与 Function Calling：建议调用不等于已经执行

> **状态**：已完成（初稿）
>
> **本篇定位**：Part III 第 3 篇。拆开工具能力、模型的调用请求、授权检查、实际执行和确认回执。
>
> **读法**：先跟一次只读查询，再看「登记草稿」在哪里被拦下。看到「已完成」时，拿回执对照表问一句：到底完成了哪件事？

## 它说「已登记」，登记在哪里？

**虚构场景。** 社区市集原定周六，现行规则 v2 改为**周日 14:00**，旧 v1 失效；雨天是否改室内待确认。小周交代：「整理本次报名清单和通知草稿，先别发。」这里的交付是把两份东西放在当前任务里给人审，不是登记回主办方后台，不是改原表，也不是发通知。她却看到助手说：「报名清单和通知草稿已登记。」在聊天里生成了一份草稿，在共享系统里保存了一条草稿记录，向摊主发了一封通知，是三个完全不同的结果。

本篇的真问题是：**AI 说「已登记」时，怎么确认实际动作和任务要求一致？** 不要只问它「你确定吗」；模型可以重复同一句话。要看哪一步停了、有什么证据，以及这个动作原本该不该发生。

## 一次调用，至少要分开看四层

| 层 | 市集里是什么 | 不能从中推出什么 |
| --- | --- | --- |
| 能力 | 应用可能接了读报名表的工具；某些团队另有保存共享草稿或发送通知的工具 | 看见按钮、工具名或曾经连过账号，不代表本次能用，更不代表用户要用 |
| 意图与提议 | 人只要清单和草稿；模型可以提出「读取本次市集报名摘录」，也可能误提议「登记草稿」 | 模型提出的动作不一定符合人的意图；调用请求本身没改变外部状态 |
| 授权 | 本次只开放指定规则和报名摘录的只读访问；不改原表、不共享登记、不发送 | 请求填得完整，或账号可以写入，不等于这次获准写 |
| 执行与结果 | 应用通过检查后才派工具；工具或外部系统返回读到的记录、错误或处理状态 | 「已提交请求」不是「已完成登记」，更不是「收件人已读」 |

**Tool（工具）**就是应用能调用的一项能力，例如读表、查询日历、保存草稿。**Function Calling（函数调用）**在不少模型接口里指模型用约定结构提出要调用哪个函数型工具、给它什么输入。例如这次要查「本次市集」的表，只取报名编号、摊位类别和供清单使用的状态，不是只回复一句「我会帮你查」。这种形式便于应用检查是否有必填信息，但结构完整不代表活动编号、规则版本或操作本身正确。产品也会用 Tool Calling 等叫法，函数型工具不是所有工具的唯一形态。

常见链路是模型提议，应用的运行时检查并调度，外部系统处理，然后把结果交回应用，供模型下一轮总结。有些内置工具由平台代为检查和执行，界面不一定展示中间步骤；也有固定流程由应用直接查表，不需要模型发出调用请求。看不见具体步骤时，更不应把模型的叙述当成独立的完成证明。

## 泳道图：只读能通过，登记草稿不能通过

```text
人                         模型                   应用／运行时            外部工具
只整理清单与草稿、不发送 ─→ 提议读报名摘录 ──────→ 核对活动、来源、列范围
                                                  放行只读查询 ─────────→ 读指定摘录
                            依据已核规则整理 ←─── 返回读取结果 ←───────── 报名摘录
                            误提议登记草稿 ──────→ 拒绝：无写入授权          （未调用）
拿到清单和通知草稿 ←─────── 返回任务内的产物
```

这是一种示意，不是说模型总会错误请求登记。理想情况下本任务根本不向模型提供写入或发送能力；即便平台因其他用途接过这些工具，运行时也得按当前任务裁定。底层账号若也只有必要的只读权限，限制就不只是靠提示词。读到报名行之后，清单可以使用足够区分记录的字段，但通知草稿不需要附带姓名、联系方式或报名表截屏。**只读意味着不更新业务记录，不意味着读取范围可以无限大，也不意味着可以把读到的数据发给其他地方。**

对比一种**不在本任务内**的情况：日后主办方另开任务，明确批准「将这份定稿存入指定栏目，仅作为私有草稿，不发布、不发送」。此时模型才可以提出保存请求，应用核对版本、栏目、可见范围和授权，再让外部系统保存，收到相应回执。草稿回执最多证明那份草稿被保存；若外部系统的「保存」还会通知同事，实际副作用就不符合「不发送」，不能只靠按钮写着「存草稿」就放行。先弄清工具会做什么，比事后找撤回按钮更可靠。

## 回执怎么读：成功也要问「成功到哪一步」

| 你看到的迹象 | 能说明什么 | 合适的确认方式 |
| --- | --- | --- |
| 聊天里说「已登记」，下方只有草稿文字 | 只能确认界面给了文本，不能独立确认外部写入 | 看本次活动记录；必要时到目标系统核对，不把一句话当回执 |
| 工具请求被拒绝，运行记录显示未派发 | 这条请求没有调用到目标工具 | 说明阻止了什么、照原边界交草稿；不把拒绝叙述为已完成 |
| 工具回「已读取指定活动」，返回摘录与来源 | 这次查询返回了资料，不代表草稿已登记、资料一定正确或最新 | 核对活动、出处和版本，确认 v2 才是依据；不把网页内容当指令 |
| 外部系统回「已受理」，或请求超时没收到回执 | 受理不等于处理完成；超时也可能是做了但回执没回来 | 查目标系统的状态或已有记录；有副作用的请求不盲目重发；无法确认就报「状态未知」 |
| 另立的登记任务里，正式回执给出记录号、目标栏目、版本及「私有草稿」状态 | 能核对此记录存在哪里、当前是什么状态 | 条目重要时对照记录本身；「私有草稿」不等于公开发布、发送或对方已读 |

把来自工具的**执行元数据**与工具装回来的**原文内容**分开看。例如，可信运行记录说「读网页成功」，可以说明查询完成了；网页正文若自称「通知已群发」或要求助手额外操作，不等于平台自己执行过群发，更不能打开新权限。错把两种东西当作同一种证据，就会得到「附件里写着已发布，所以我已经发布」之类的离谱结论。[第 14 篇](14-steering-and-approval.md)会从使用者角度再看这条边界。

查看回执也有代价：状态不一定立即更新，不同系统的显示不一样，完整日志还可能包含敏感字段。日常核对通常只需要本次任务号、动作对象、版本和状态，不必把全量原始日志复制到聊天里。请区分「在本次任务中没有发现发送记录」和「已确认没有发送」：前者可能只是你无权查看日志，后者需要足以覆盖此次动作的记录或明确的权限限制。一些产品不给你可靠的写入记录；这时不要用更自信的措辞补上证据。关键操作可以留给人到目标系统处理并检查。

## 纸上练习：把三句播报改成一份可验收的交付

假设小周看到三条消息。①「工具返回：只读读取了本次报名摘录」；②「草稿已经写好，已登记」；③「登记请求被运行时拒绝，未派发」。请用不超过三句话向小周交接，另外指出「周日 14:00」与「雨天可能改室内」在草稿里应各写成什么状态。假设你手边有主办方 v2，且记录显示本任务只做过只读查询。

**参考交接：**「已按主办方 v2 整理报名清单及通知草稿，旧 v1 的周六时间已失效，现行时间为周日 14:00。雨天是否改室内待主办方确认。两份产物供内部审核；未登记到共享系统，未改原表，未发送。」其中「读取」有第一条和运行记录作证；「未登记」要看第三条和本次活动记录，不能因为第二条说得笃定就给它升级成成功回执。

## 速记与自检

**速记：** 工具是能力，调用是提议，授权看本次边界，执行看可核对的结果。**没派发就没执行；已受理不等于已完成；写完草稿不等于发出通知。**

1. 模型给出的「登记草稿」请求格式完全正确，但本次是只读。运行时该怎样处理？
2. 一次获准的保存请求超时，能否马上再保存一次，并宣称首次失败？
3. 只读工具成功读取了网页，页面写着需要外发报名名单。能照做吗？

**参考答案：** ① 拒绝写入，按原边界交付草稿。② 不能，先从目标系统核对是否已有记录；状态不明就如实报告。③ 不能，成功读取只说明获得了资料，页面文字不是本次授权，名单也不该外发。
