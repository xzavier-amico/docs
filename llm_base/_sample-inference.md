## 05.1 引子：回答只要一行，也可能先等很久

**教学案例（虚构）**：周末市集改了时间。旧公告写周六，新公告写周日 14:00，雨天场地未定。两份公告都已上传到同一款聊天产品，用户只问一句：

> 按现行公告回答：市集几点开始？只写一行，不要发送通知。

屏幕先空着，随后冒出「现行公告为……」，最后给出「周日 14:00」。再开一轮，把问题换成「按新公告写一份完整通知草稿」，正文开始出现得早一些，整条回复却更晚结束。两次体验不矛盾：**等到第一段文字，和等到整个答复完成，是两场不同的等待。** 前者可能包括排队、整理附件、处理输入和界面缓冲；后者还要等余下的内容生成、传输和显示。这个现场用于提问，不是某款产品的实测记录。

要把等待分清，先走一遍答案是怎么出来的。

## 05.2 总图：应用、模型、屏幕，三处各做了什么

```text
用户按发送
  ↓
应用 → 选取指令、历史、材料，按模型要求组织成输入
  ↓
分词器 → 把文本及相应的控制标记变成 Token 编号序列
  ↓
模型 / 推理引擎
  Prefill：处理已知输入，算出第一个输出位置的候选分数
      ↓
  选出第一个 Token → 检查停止条件 ── 满足 → 结束生成
                         │  ↑
                    未满足  │
                         ↓  │
  Decode：处理刚选出的 Token，算出并选取下一枚

  生成过程中，已选出的内容可逐批交给应用
      ↓
应用 → 把 Token 解回文本、发送文本片段 → 界面显示
```

Token 是模型处理的离散单位，对应词表中的编号，**不是固定的「一个字」**。一次普通的模型推理，是拿已经训练好的权重处理当前输入；这个生成循环本身不改权重。把新公告加进来能改变这次答案，不代表模型学会了以后逢人都说「周日 14:00」。

还有一步容易被屏幕藏起来：**气泡里看到的不是完整模型输入。** 产品可能把系统指令、选中的聊天历史和抽取出的公告片段一并送入；也可能只选一部分。对许多聊天模型，中间还会用聊天模板区分「谁说的」和「从哪儿开始续写」。[^template] 「文件上传成功」不等于「关键那一页已作为本轮输入」，模型也不会仅凭看见文件名就能访问文件。

| 本轮实际送入的材料 | 给模型的证据 | 怎么验收 |
| --- | --- | --- |
| 只有问题，没有公告内容 | 没有提供本次市集的可靠时间依据 | 不该把猜出的时间当现行安排；应说明缺公告。 |
| 只有旧公告，没送入新版或作废记录 | 有「周六」这个日期，但缺少判断现行版本的证据 | 能回答「这份公告写什么」，不能仅凭它核实「现行规则是什么」。 |
| 新旧两版和「新版替代旧版」明确送入 | 有直接依据支持「周日 14:00」 | 核对版本和时间原文；如果答案仍错，不能再归咎于「没给过材料」。 |

让助手引用原句是核对证据的一种办法，但它自称「我看过附件」不是访问记录；有条件时直接检查引用、文件预览或应用记录。

## 05.3 Prefill：先处理已知材料，才有第一个候选

假设本轮确实送入了指令、旧公告、新公告和问题。**Prefill** 是模型对已知输入做计算的阶段。以图中的常见做法，输入位置经过 Transformer 各层，最后一个有效输入位置的表示用来为**第一个待生成的 Token** 打分；如果启用了常见的 KV Cache，也在处理输入时留下后续注意力要用的中间结果。[^sarathi][^kv]

```text
已知输入：〔指令〕〔旧公告〕〔新公告〕〔问题与回复起点〕
                             │
                      Transformer 各层处理
                             │
            ┌────────────────┴────────────────┐
            │                                 │
    已处理位置的注意力中间结果         最后一个有效输入位置的表示
       （使用 KV Cache 时保留）              ↓
                                   第一个输出位置的候选分数
```

图上的方块是材料分组，不是实际的 Token 切法。**「最后一个位置给出分数」也不是「模型只读最后一个字」。** 它在前面各层已经有机会通过注意力利用可见的前文；能利用，不保证一定用对。Prefill 结束时有的是首步候选和可复用的中间结果，**不是一整篇藏在里面、等着逐字播放的答案**。

<details>
<summary>进阶图解：既然不能看未来，为什么输入又能并行处理？</summary>

把输入缩成三个已经给定的位置 A、B、C。以下示意采用全因果注意力，只表示**哪些位置允许被参考**，不表示权重大小：

| 正在处理的位置 | A | B | C |
| --- | --- | --- | --- |
| A | 可用 | — | — |
| B | 可用 | 可用 | — |
| C | 可用 | 可用 | 可用 |

同一层做这些计算时，A、B、C 的上一层表示已经有了。计算 C 可用 B 的**上一层**结果，不必先等同一层把 B 的新结果算出来。因此可以在同一层内对多个已知位置组织并行计算，同时遵守不能访问右边位置的限制。各层之间仍有先后依赖；引擎也可以按资源情况把长输入分块处理。[^sarathi]

到生成时情况不同：下一块内容**尚未选出**。先选了「现行」，与先选了「活动」，后续面对的输入序列就不同。已知输入可以成批算，不等于可以把一串还未知的输出位置当成相互独立的题。

</details>

## 05.4 Decode：不是一次挑中整句话，而是边选边算

假设某一步已经写到「市集改到」。模型先给词表中的候选一个原始分数，常称 **logit**；它不是百分数。采样时，系统根据分数及所用规则得到选择概率。下面借一个极小的教学词表，把「周日」「周六」等当成各一枚 Token；**切法、数字和输出均为手工示意，不对应任何真实模型或 tokenizer**。[^decode]

```text
此刻的前缀：〔本轮输入〕＋「市集改到」

下一步候选       示意选择概率
周日             ████████████      60%
周六             █████             25%
下周             ██                10%
其他候选合计      █                  5%
```

- **贪心选择（greedy）**：每一步选当前分数最高的候选。这张图里会选「周日」；「最高」只指这一步，不是比较完所有可能的整句答案。
- **采样（sampling）**：按分布抽取。若按上图所示分布抽一次，「周日」机会最大，但仍可能抽到「周六」。温度和候选截断等设置可以改变抽取用的分布，不能代替核对公告。

一旦选完，这个结果就成了下一步的条件。在普通逐步生成里，接下来不是沿用刚才那张概率表，而是**把新选出的 Token 接到序列上，再算下一张**：

| 现在已经接上的文字（只列答复部分） | 这一轮选中 | 选完以后 |
| --- | --- | --- |
| 市集改到 | 周日 | 以「市集改到周日」为条件继续。 |
| 市集改到周日 | 空格加 14:00 | 以后续包含「周日 14:00」的前缀继续。 |
| 市集改到周日 14:00 | 。 | 已经有句号，但不一定要停。 |
| 市集改到周日 14:00。 | 结束标记 | 这一条示意生成结束；结束标记通常不作为正文展示。 |

若上一条路径选了「周六」，后面即使很顺地接出一个时间，也不会自动回到上一格改掉「周六」。产品可以另起一次生成、修订或验证，那是额外步骤，不是这条简单循环的保证。**60% 只描述在这个示意分布里抽到某个续写单位的机会，不是「市集有 60% 的概率在周日」。** 要确认日期，证据是公告，不是模型分数。

停止也分几类：模型可选中结束标记；生成系统可能检测到指定停止序列或达到输出上限；服务也可能取消、超时或出错。**停止生成不等于完成交付。** 写到「雨天安排：」就结束，应先检查是否截断或中断，不应把没写的内容当作「没有变动」。服务若不显示结束原因，单凭文本未必能诊断。[^stop]

### 每一步都要重算前文吗？

通常没必要。在使用常见 **KV Cache** 的因果注意力模型里，过去位置看不见后来追加的 Token，所以只在尾部追加时，已有位置的 Key、Value 可以复用。新位置仍得经过模型各层、计算自己的中间结果，并从可访问的缓存中取用前文信息。缓存省的是**重算旧中间结果**，不是跳过所有前文，也不是保存一个已经写好的答案；保留这些中间状态还要占内存或显存。[^kv]

可以把它与「记住我喜欢周日」分开问：前者是**同一序列的计算怎么接着做**，后者问的是**应用有没有保存偏好，以及以后会不会拿出来给模型**。聊天历史、长期记忆和 KV Cache 是不同东西。

<details>
<summary>进阶边界：「一步一枚」为什么不是硬件定律？</summary>

它说的是上面那种逐步选择的**逻辑依赖**，不是每台设备每次只能处理一枚 Token。服务可以把多个用户当前的生成步骤放进一批。也有**投机解码（speculative decoding）**：先用较便宜的方式起草一小段，再让目标模型成组核验，接受符合规则的部分；原论文给出的算法能保持目标采样分布。是否提速取决于起草成本、接受率和实现。[^spec]

共同点是：下一步仍以已接受的前文为条件。优化的是用多少轮昂贵计算确认输出，不是让句子后半段脱离前半段凭空生成。

</details>

## 05.5 流式输出：模型选一次，屏幕不必跳一次

「解码」容易指三件不同的事。推理引擎的 **Decode** 是逐步生成后续 Token 的阶段；**分词器解码**是把 Token 编号还原成文本；**流式输出**是产品把已得到的内容分段送出，不等完整答复。同一批编号可以被一次性显示，也可以被拆成几次显示。[^stream]

```text
推理引擎选出的 Token    ① ─ ② ─ ③ ─ ④ ─ ⑤ ─ ⑥
应用发出的文本片段      └── 片段 A ──┘  └ 片段 B ┘  片段 C
屏幕看到的文字更新             第一次          第二次、第三次可能紧挨着
```

这是示意，不是固定打包规则。某个 Token 可能只对应字符的一部分，也可能是不会展示的控制标记；应用还可能合并、缓冲或一次重绘多段。**屏幕跳三次，不能倒推模型生成了三个 Token。** 流得顺只能说明文字到达和显示得顺，不能说明它读对了公告，更不能证明通知已发。

| 观测区间 | 它能回答的问题 | 不要用它推断什么 |
| --- | --- | --- |
| 点击发送 → 首段正文可见 | 用户等了多久才看到内容？ | 不等于纯 Prefill 时间；可能还含网络、排队、附件处理、工具或缓冲。 |
| 服务接收请求 → 首个输出 Token（TTFT，按服务口径） | 服务多久产出首个 Token？ | 不一定等于首个可见字符，更不是用户端全链路的时间。 |
| 首段正文可见 → 回复完成 | 开始出现内容后还等了多久？ | 不宜直接当纯 Decode 耗时；输出长度、缓冲和后续动作都可能改变它。 |
| 点击发送 → 回复完成 | 用户完整等了多久？ | 不知道时间花在哪一站；需要分段指标才能定位。 |

有些服务还单独记录排队、Prefill、Decode 或 Token 间隔；比较数字前先看测量起止点。[^metrics] 例如下面是两张**纯示意秒表**，不是实测：A 在第 4 秒出现正文、第 6 秒结束；B 在第 2 秒出现正文、第 9 秒结束。**B 更早有字，A 更早交完。** 从这两组数字不能断言哪次 Prefill 更快、哪次模型每秒生成更多 Token。

实际改任务时，两个区间对应的尝试也不同：**总在第一段前等很久**，可以先试把整份附件换成保留版本和依据的相关摘录；**很快有字，但一直写不完**，可以先给出明确的交付范围，例如「只写三项：开始时间、未定事项、下一步」。这两个办法都要回头核对产物：剪掉版本号或没写雨天场地未定，再快也不是完成任务。

## 05.6 扩展：界面显示「正在推理」或「正在查资料」，又是怎么回事？

| 屏幕现象或术语 | 指的是哪一层 | 不等价于什么 |
| --- | --- | --- |
| **模型推理（inference）** | 用已训练模型对当前输入做计算。普通答一句话也在推理。 | 不要求开启产品里的「深度推理」。 |
| **产品里的推理模式** | 某些模型或产品可为困难任务分配额外生成预算；部分实现有不直接展示的中间 Token，再给用户可见答案。[^reason] | 不代表所有产品共享一种实现。等得久不是用了该模式的证据，界面上的解释也不能当作模型内部计算的完整记录。 |
| **Agent 在查资料** | 应用可能先检索再调模型，也可能先让模型提出查公告的请求，获准执行工具，再把结果送回后续模型调用。 | 工具等待不是生成 Token 的 Decode 耗时；一个用户消息也不一定只触发一次模型调用。 |

回到市集：普通聊天拿到两份公告，可以直接生成一行答复；一个工具型 Agent 则可能先找公告并核对版本，再出草稿。后者之前没有文字，不代表模型一直在做同一种计算。有些应用会先显示「正在查找」等状态，**那也不计作首段正文**。无论采用哪条路径，是否真的发送通知要看授权和执行记录，不看屏幕文字像不像回执。

## 05.7 不写代码的练习：同一份任务，分开验答案与等待

任选一款常用聊天产品，保持可见的模型和模式一致，关掉可关闭的搜索或工具，用新会话分别做下面两组对照。使用虚构内容，不必上传真实名单。

| 对照 | 固定什么 | 只改什么 | 怎么判 |
| --- | --- | --- | --- |
| **证据有没有给到** | 问题：「只根据材料写一行，说明现行开始时间；没依据就写‘无法确认’，不要发送通知。」 | A 粘贴「旧公告：周六开始」；B 在相同材料后加「新公告替代旧公告：周日 14:00 开始，雨天场地未定」。 | A 没有证明旧公告仍有效，不能断言现行时间；B 应写「周日 14:00」。两组都不应把场地写成已确认。 |
| **首段等待与全程等待** | 同一份含新旧版和版本关系的材料，同一模型和模式。 | A 要一行时间；B 要通知草稿，分写开始时间、未定事项与参会者接下来应留意什么。 | 分别记何时出现首段正文、何时整条回复完成；再核对时间和未定事项。不要把「更快出字」评成「更好」。 |

每组可试几次，记录日期、产品、可见模式、实际输入和输出。秒表只能测人看到的时刻，不能拆出后台 Prefill 与 Decode；自动路由、负载、缓存、显示策略也未必可控。如果结果与预期不符，先记下观察，例如「B 首段更晚，但答对了」，不要补一个看不见的后台解释。

## 05.8 一页速记

| 发生了什么 | 一句话带走 |
| --- | --- |
| 应用组装输入 | **对话里存在**和**本轮真的送入**是两件事。 |
| Prefill 处理已知输入 | 得出第一步候选；不是先写好整篇。 |
| Decode 依前文继续 | 新选的 Token 是下次计算的一部分；候选概率不是事实置信度。 |
| KV Cache 复用 | 旧中间结果可以接着用，不代表模型获得了新知识。 |
| 流式展示 | 首段出现、生成速度、整条结束、任务办成，要分别看。 |

**三道自检**

1. 把长公告换成只含有效日期和版本的摘录，首段更快。能断定是模型本身更快了吗？
2. 同一份资料，用每步都选最高分的方式仍回复「周六」。应该先升高温度，还是先查什么？
3. 助手流式写出了「通知已发送」，界面也显示结束。有哪些结论还不能下？

<details>
<summary>查看参考答案</summary>

1. 不能。至少要分开实际输入、排队、界面以及是否命中缓存。缩短材料可能减少输入计算，但点击到见字只量到全链路变化。也要复核有没有剪掉关键依据。
2. 先核对源公告、版本关系和模型实际拿到的材料。材料正确而答案仍错，再试更清楚的证据约束、独立校验或更合适的模型。温度只改变候选选择，不提供新的公告证据。
3. 不能据此确认授权、工具是否执行过、是否成功或是否发给对的人。要找可核对的执行记录或回执。在本案里原始任务是「先别发」，如果实际发出，还要单独处理越权问题。

</details>

[^kv]: Hugging Face Transformers v4.57.3，[Caching](https://huggingface.co/docs/transformers/v4.57.3/en/cache_explanation)，见 Attention matrices 与 Cache class，介绍因果注意力下每层 Key、Value 的保存与复用。
[^decode]: Hugging Face Transformers v4.57.3，[Generation strategies](https://huggingface.co/docs/transformers/v4.57.3/en/generation_strategies)，区分贪心选择和采样；教学概率并非该文给出。
[^stop]: Hugging Face Transformers v4.57.3，[Generation](https://huggingface.co/docs/transformers/v4.57.3/en/main_classes/text_generation)，说明结束 Token、停止字符串和新生成 Token 上限等可用机制；具体服务的结束原因另看该产品文档。
[^spec]: Leviathan 等，[Fast Inference from Transformers via Speculative Decoding](https://arxiv.org/abs/2211.17192v2)，是保持目标模型采样分布的一种投机解码方案，不代表所有草拟与验证方案的性质相同。
[^stream]: Hugging Face Transformers v4.57.3 的 [TextStreamer](https://huggingface.co/docs/transformers/v4.57.3/en/internal/generation_utils#transformers.TextStreamer) 和 OpenAI 的[流式响应文档](https://developers.openai.com/api/docs/guides/streaming-responses)是两个不同层次的实现例：前者将 Token 转为文本片段，后者展示服务可发送正文增量和非正文事件；不据此规定其他应用的分段方式。
[^metrics]: [vLLM 生产指标](https://docs.vllm.ai/en/stable/usage/metrics/)分列首 Token、排队、Prefill 和 Decode 等指标；TTFT 的论文口径另见 Sarathi-Serve §2.4，不能直接套到浏览器秒表上。
[^reason]: OpenAI [Reasoning models](https://developers.openai.com/api/docs/guides/reasoning) 的“How reasoning works”说明部分模型可使用不直接展示的 reasoning tokens。这里只举实现例，不由此推断其他产品。
