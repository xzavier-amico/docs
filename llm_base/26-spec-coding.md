## 26.1 引子：一句「加个导出」

**虚构场景。** 周一早上，活动运营小陈在群里发了一句：

> 报名表加个导出吧，我周五要交给场地。

这句话有十几个字，群里三个人各自读出了一个版本。

小陈想的是：把第三组那 28 个人导出来，发给组长，让他核对签到。

技术同事想的是：列表页右上角加一个按钮，点了就把报名表全部导出来。

管数据的人想的是：又多了一个能把手机号带出去的口子，谁批的？

两周后，按钮上线了，名字就叫「导出」。小陈先筛了第三组，再点，导出的还是全部 120 条；文件里有姓名、手机号、饮食备注、紧急联系人。他把文件发给了四个组长。当天下午，管数据的人在设计评审上看到这个按钮，问了一句：「这个谁能点？」

没有人答得上来。因为这个问题从来没被写下来过。

这件事里没有一个人是恶意的，也没有一处是「模型算错了」。三个人的理解都对，只是**他们对「导出」这个词填了三个不同的宾语**：导出谁、导出哪些列、导出给谁看。这三格没填，剩下的全是猜。

但先别急着下结论说「应该先写清楚再做」。同一个团队上周用两个小时做了一个能点的原型：点一下，名单从表格里滑出来，还能按小组变色。那个原型没有一页规格，却让小陈第一次说清了自己要的是什么——「我不要花哨的，我要能按组发给组长」。

所以真正的问题不是「该不该乱试」，是**什么时候停止乱试**。

## 26.2 唯一真问题

**一句「加个导出」，要澄清哪些，才不会改错？**

短答案：不是把所有细节都问一遍。问四个位置就够了——**要什么（范围）、不要什么（非目标）、谁能用（权限与数据范围）、怎么算做到（验收条件）。**

这四个位置有一个共同点：它们都不是「实现细节」，而是**别人要按它做事的东西**。小陈要按「第三组 28 人」去核对签到；组长要按「只有本组」去转发；管数据的人要按「不含手机号」去签字。任何一格空着，就会有一个人按自己的理解把它填上。

先把这个判断放在这里：

> **Vibe 和 Spec 不是水平高低，是用途不同：一个用来发现要什么，一个用来保证改对了。**

这句话反直觉的地方在于：它把「写规格」从一种能力，降成了一种**时机选择**。很多人以为写不出规格是因为不够专业；其实更常见的情况是——**你还没到能写规格的时候**。这时候硬写，写出来的不是规格，是一份把错误答案写得很正式的文档。

### 两种失败，方向相反

| 做法 | 什么时候是对的 | 什么时候是错的 | 错的时候长什么样 |
| --- | --- | --- | --- |
| **直接开做**（Vibe） | 还不知道要什么，需要先看到东西 | 已经有别人要按结果做事 | 做完了才发现方向错；「导出当前筛选」被做成「导出全部」 |
| **先写全规格** | 已经知道要什么，要保证做到 | 还在探索 | 把错的答案写得很正式；返工时要改的不是实现，是当初那三页纸 |

两种错法看起来相反，其实同源：**都是在信息状态不对的时候，用了另一种状态的方法。** 前者是把探索当成交付，后者是把交付当成探索。

### 这条判断从哪推出来

不是从「最佳实践」推出来的，是从三个原语推出来的。

**P2（工作台）** 说：模型只看见这一轮被放到桌上的东西。所以规格的第一个作用不是「存档」，是**决定桌上放什么**。你没写进规格的约束，它这一轮就是看不见；你写进去了，它至少有机会看见。注意是「有机会」——见下一段。

**P5（提议 / 执行）** 说：模型只出主意，动手的是外面那圈系统。所以规格能约束的是**提议**，约束不了**执行**。规格写「只能导出本组」，不等于系统真的挡住了别组；挡住别组的是取数那一步的过滤条件，以及一个没有别组权限的账号。

**P3（抽样）** 说：同一张工作台能抽出不同的下一步。所以 Vibe 里那次「跑通了」，只证明这条路径存在过，不证明它稳定。原型跑通三次，第四次换个说法就散架，这不是原型坏了，是它本来就只有一次的说服力。

三个原语合起来，得到本篇的第二句判断：

> **规格不是保证，它只是把「要什么」变成可检查的承诺；保证要靠测试、权限和证据。**

这句话很重要，因为它是本书反复反驳「写严一点就好了」的另一种形态。文档写得再死，也改不了权限，给不出回执。**把规格当成保证，和把提示词当成边界，是同一类误会。**

### 四问在这里怎么用

[第 01 篇](01-ruler.md)的四问，在写规格时各管一格：

| 四问 | 在规格里问什么 | 答不上来会怎样 |
| --- | --- | --- |
| **这句话是谁说的？** | 这条需求是谁提的？运营、法务、客户，还是模型在上一轮自己补的？ | 把模型的猜测写成需求，后面所有人按猜测做事 |
| **它这一轮看见了什么？** | 写规格时看到的表结构、旧页面行为、字段含义，是最新的吗？ | 按一份已经改过的表写验收，做出来必然对不上 |
| **这是提议、事实，还是已执行？** | 「这个功能已经有了」是有人说的，还是你真去看过？ | 重复做一个已经存在的东西，或者漏掉一个已经坏掉的东西 |
| **我拿什么独立验证？** | 每条验收条件，第三个人能不能不问你就判真假？ | 验收退化成「我看着还行」 |

第三问在软件需求里格外容易踩。群里有人说「导出功能早就有了」，这句话是提议还是事实？去看一眼那个按钮，比在群里争半小时有用。**规格的第一页不该是功能列表，该是「现在是什么样」。**

## 26.3 一张图：分界线在「能不能说出一条验收条件」

先给图。横轴不是难度，是**你对「要什么」的确定程度**。

```text
    还不知道要什么                                    已经知道要什么
    ┌──────────────────────────┐    ┌──────────────────────────┐
    │ Vibe：先看到东西          │    │ Spec：先把承诺写死        │
    │ 目的：发现自己要什么      │    │ 目的：保证改对了          │
    │ 产物：灵感、可丢弃原型    │───▶│ 产物：四段规格 + 证据包   │
    │ 代价：返工、白做、方向错  │    │ 代价：前期慢、要有人拍板  │
    └──────────────────────────┘    └──────────────────────────┘
              ▲                                  ▲
              └──────────── 分界线 ──────────────┘
              能说出一条「第三个人不问你也判得了真假」的验收条件
```

这条分界线是可以操作的，不是比喻。它的判据只有一句：**把这句话交给一个没参与的人，他能不能在不动手的情况下说出「做到没做到」。**

- 「导出要好用」——不能。他得问你「什么叫好用」。
- 「筛选第三组后导出，文件里 28 行，且不含手机号列」——能。他可以自己数。

所以从 Vibe 转到 Spec 的信号，不是「想清楚了」，也不是「开会通过了」，而是**你说出了第一条可判定的验收条件**。在那之前写规格，是在给一个还没成形的东西画施工图。

### 谁在做什么

规格这件事最容易出的一种错，是把它当成「一个人写文档」。实际上它至少涉及四个位置，压在一个人身上就会互相污染：

```text
   人（提需求 / 拍板）
   说清要什么、不要什么、谁能用
        │
        ▼
   模型：起草四段（需求 / 设计 / 任务 / 测试）
        │  只能提议，不能判定「做到了」
        ▼
   应用：决定这次装上哪些材料与任务
        │
        ▼
   工具 / 原始系统：执行、留下结果与记录
        │
        ▼
   证据：行数对照 / 角色对照 / 审计条目
        │
        ▼
   人（验收 / 签字）：按证据判，决定收不收
        │
        └──▶ 不过：退回上一段，改的是规格或实现，不是证据
```

| 位置 | 负责 | 不负责 | 出事时最常听到的话 |
| --- | --- | --- | --- |
| **提需求的人** | 说清场景、范围、非目标；确认验收条件 | 设计实现、判断技术可行性 | 「我当时不是这个意思」 |
| **写规格的人（可以是模型）** | 把口语整理成四段；指出互相矛盾的地方 | 替业务拍板；替验收签字 | 「需求里没写」 |
| **执行的人 / 工具** | 按任务做、留下结果与记录 | 判断「这样算不算做到」 | 「我是按规格做的」 |
| **验收的人** | 按验收条件逐条判、看证据 | 凭印象放行；替提需求的人改范围 | 「看着差不多」 |

四句话指向四个不同的缺口。听到「需求里没写」，先去翻需求段；听到「我是按规格做的」，先去看测试段有没有覆盖这一条；听到「我当时不是这个意思」，说明验收条件没让提需求的人确认过。

这里有一个必须说清的分工：**模型可以起草规格，但不能确认规格。** 它可以把一段口语整理成四段，可以指出「第三条和第五条冲突」，可以补出你没想到的异常场景——这些都是它的强项。但它不能替你决定「这个范围够不够」，因为它不承担范围错了的后果。**起草和拍板，是两件事。**

## 26.4 Vibe Coding：允许乱试，但有三个前提

先把词说清。本篇说的 Vibe Coding，指的是一种做法，不是一种工具：

> 用自然语言把意图抛给模型，边看结果边改，不先写规格，以「先看到东西」为目的。

它最常见的两种误读，方向相反。一种说它是「不写代码也能做产品」的捷径；另一种说它是不专业的代名词。两种都把它当成了一个**水平**，而它其实是一个**阶段**。

### 三个前提，缺一个就不该 Vibe

不是所有事都适合乱试。判断标准只有三条，都是关于「错了会怎样」的：

| 判据 | 问法 | 合格的样子 | 不合格的样子 |
| --- | --- | --- | --- |
| **可丢弃** | 这个东西做废了，我会心疼吗？ | 一个下午的产物，扔了不心疼 | 已经接了真实数据、已经有人在用 |
| **影响面小** | 它会不会碰到别人的数据、钱、对外可见的东西？ | 只在你自己的机器上、只读、假数据 | 连着生产库、能发消息、能改名单 |
| **有回退** | 做错了能不能一次退回？ | 新开一个副本，原样不动 | 直接改主线，改坏了只能重来 |

三条里最容易被跳过的是第二条。很多人觉得「我只是试试，不会真发出去」，但试的时候用的是真名单、真账号、真群——**试的边界，是由账号权限决定的，不是由你的意图决定的**（见[第 17 篇](17-injection-and-permission.md)）。你想的是「试试」，系统看到的是「它有发送权限」。

### 它的产物是灵感，不是交付物

这句话要落到操作上，否则就是一句口号。落到操作上，是四条禁令：

1. **不进主线。** 原型放在副本、沙箱、单独的页面里；不要在原页面上改，改完再想怎么撤。
2. **不接真实数据。** 用假名单、脱敏表、只读账号。真名单进过一次对话框，就已经进过日志了。
3. **不给外部人用。** 原型给同事看可以，给客户、给组长、给场地不行——他们不会知道这是原型，他们会按交付物要求它。
4. **不留「以后再说」的权限。** 为了试通而临时开的发送、写入、导出，试完就关。**临时权限是最容易变成长期权限的东西。**

为什么这四条值得单独列？因为 Vibe 的失败很少是「做不出来」，多数是「做出来了，然后顺手用上了」。**原型的危险不在它粗糙，在它太好用。**

### 「跑通了」不是证据

这是 P3 的直接推论。你在原型上点了一次，名单滑出来了，很顺。这一次成功告诉你什么？

它告诉你：**这条路径存在。** 它没告诉你：换一台机器还行不行、换一个浏览器还行不行、数据多十倍还行不行、换个人操作还行不行、明天再跑还行不行。

所以原型阶段最该记下来的，不是「成了」，是**「在什么条件下成的」**。一句话就够：「在我自己的账号、同一个浏览器、120 条数据、不筛选的情况下，点了三次，三次都出来了。」这句话比「能用」有用得多，因为它写清了边界，而边界正是 Spec 要接着处理的东西。

### Vibe 该怎么收尾

乱试不是烂尾。一次有效的 Vibe 结束时，应该能交出三句话：

```text
Vibe 收尾的三句话（写完就可以交给 Spec）

1. 我要的那个感觉是什么
   例：不是花哨的动效，是「能按组发给组长，组长一眼看到自己人」。

2. 哪些地方不对，或者我不要
   例：不要手机号；不要一次导全部；不要在手机上操作。

3. 我大概能说清的一条验收条件
   例：筛选第三组再导出，文件里应该是 28 行，而且只有第三组。
```

第三句是分界线的门票。写得出，就可以进 Spec；写不出，说明还在第一阶段，继续试，别急着写文档。

这三句话还有一个副作用：它们会暴露「你其实没想清」。很多人试了两小时，第三句还是写不出来——这不是失败，这是这两小时买到的最有价值的信息。**你现在知道问题不在实现，在需求。**

## 26.5 Spec 四段：每一段的输入和出口

Spec 不是一篇长文档，是四段有先后、各有出口的东西。四段的名字不重要，重要的是**每一段结束时，你手上多了一样可以交给下一个人的东西**。

| 段 | 回答什么 | 输入 | 出口（交给下一段的东西） | 缺了会怎样 |
| --- | --- | --- | --- | --- |
| **Requirements 需求** | 为谁做、做什么、不做什么、谁能用、怎么算做到 | 一句口语需求 + 现状（现在是什么样）+ 约束 | 一份带编号的需求，每条都有验收条件；含非目标与权限范围 | 范围永远开放，做完才发现做多了或做偏了 |
| **Design 设计** | 打算怎么做、做到哪里停、哪里会坏 | 需求段 + 现有系统的事实（不是猜测） | 一份方案说明：主路径、被否掉的备选、边界值、风险与挡法 | 方案锁死或反复改；风险在测试时才第一次出现 |
| **Tasks 任务** | 先做什么后做什么、每步怎么单独验 | 设计段 | 一张任务表：依赖、完成标志、谁来验 | 每步都「做完了」，但没有一步能单独证明 |
| **Testing 测试** | 怎么证明做到了、拿什么当证据 | 需求段的验收条件 + 设计段的边界与风险 | 一份用例清单 + 一份证据包 | 验收退化成「我看着还行」；出了问题找不到是哪条没做到 |

四段之间不是瀑布，是**来回**。设计时会发现某条需求写不清，于是回改需求；写测试时会发现某个边界没定义，于是回改设计。但有一条顺序不能反：**验收条件必须在需求段就写出来**，不能等到测试段再补。

### Requirements：验收条件为什么必须在这里写

先说结论：

> **验收条件不是「做完之后怎么测」，是「做之前怎么定义做完」。它写在需求段，不是测试段。**

理由有三条，一条比一条硬。

**第一，它是唯一能让「范围」闭合的东西。** 需求段要写范围，可范围是一个开口的词——「加个导出」可以小到四列，也可以大到跨活动合并。什么时候算写完？只有验收条件能回答。写不出验收条件，说明范围还是开放的，你只是把它写得更长了。

**第二，它会反过来暴露需求的空洞。** 试着给「导出要好用」写验收条件，你会立刻卡住：好用对谁？在什么情况下？卡住的地方，就是需求没想清的地方。这个卡顿发生在写文档时，代价是一杯咖啡；发生在验收时，代价是两周返工。

**第三，没有它，测试段会替需求做决定。** 测试的人看到一条模糊的需求，只能自己补一个解释，然后按自己的解释写用例。**最后交付的其实是他理解的需求，不是你要的。** 这是软件里最常见、也最难追的一种偏差。

一条验收条件长什么样？它有一个固定的形状：

```text
一条验收条件的形状：

  在【什么条件】下，做【什么动作】，能看到【什么可观察的结果】。

  反例（不可判定）：「导出功能正常，体验流畅。」
    —— 谁判？正常是几条？流畅是几秒？

  正例（可判定）：「筛选第三组后点导出，文件里 28 行，每行的小组都是第三组，
                    且没有手机号列。」
    —— 第三个人可以自己数，不需要问你。
```

注意正例里没有一个技术词。「28 行」「第三组」「没有手机号列」都是业务语言。**验收条件应该用业务语言写，因为判它的人是业务的人。**

### 权限与数据范围，也要写进需求段

这一条在软件变更里最容易被漏，因为它不像功能，它像「设置」。但它是红线，不是设置。

三个问题，必须在需求段回答，不能留到设计或上线：

| 问题 | 问法 | 答不上来的后果 |
| --- | --- | --- |
| **导出谁** | 哪些角色能触发这个动作？管理员、组长、普通成员，还是所有人？ | 上线后所有人都能点，包括不该看的人 |
| **导什么** | 文件里到底有哪几列？手机号、备注、紧急联系人算不算？ | 「顺手带上了」，一次导出就是一次泄露 |
| **谁能看** | 文件去哪？下载到本机、落共享盘、发群、还是进邮件？留多久？ | 文件离开系统之后就再也追不回来 |

这三问对应[第 17 篇](17-injection-and-permission.md)的三件事：**能力、数据范围、时间**。那里讲的是「系统给不给这个能力」，这里讲的是「需求有没有要求系统不给」。两者缺一不可——需求不写，实现就会按最省事的方式做；实现做了，需求没写，验收时也没人查。

有个很实用的写法：把「不做」写进需求段，而不是写进设计段。

> 本期不导出手机号、饮食备注、紧急联系人。

这句话放在需求段，它是一条**范围**；放在设计段，它就变成了一条**实现选择**，下次有人想加，只需要改设计，不需要改需求。**位置决定了它有多难被推翻。**

### 非目标：一句话省掉一半返工

非目标是需求段里最短、也最值钱的一段。它回答的不是「还要做什么」，是「这次明确不做什么」。

- 不做「导出全部」的第二个按钮。
- 不做定时导出、不做自动发邮件。
- 不改报名表单，不改列表的排序与翻页。
- 不做跨活动合并导出。

非目标的作用不是限制想象力，是**把「顺便」挡在门外**。软件变更里绝大多数范围膨胀，都不是有人正式提了新需求，而是有人在实现时觉得「反正都做到这了，顺手加一个吧」。非目标就是那句提前说好的「不顺手」。

写非目标有一个技巧：**写你预计会有人提的那些。** 「不做导出全部」之所以要写，正是因为它是第二顺位的自然想法。写那些没人会提的非目标（比如「不做火星殖民」），只是凑数。

### Requirements 的出口

一段合格的需求段，出口是三样东西：

1. **一份带编号的需求清单**，每条一句话，业务语言，不含实现词。
2. **每条需求至少一条验收条件**，形状是「在什么条件下、做什么、看到什么」。
3. **一段权限与数据范围**，回答导出谁、导什么、谁能看；外加一段非目标。

三样齐了，才能进设计。缺验收条件就进设计，等于把「要什么」交给实现的人替你决定。

## 26.6 Design 与 Tasks：把方案和顺序也变成可检查的

### Design：写约束，不写实现

设计段要回答三个问题：**打算怎么走、走到哪里停、哪里会坏。**

它最容易犯的错，是写成了实现说明——「用某个组件的某个方法」「加一个某某字段」。这类内容有两个问题：一是它把方案锁死了，二是它让测试变成了「测实现」而不是「测行为」。业务的人看不懂，也没法判断对错。

设计段该写的是**约束和取舍**：

| 要写 | 写成什么 | 不要写成 |
| --- | --- | --- |
| 主路径 | 「筛选条件原样交给后台，后台按同一套条件取数」 | 「调用某某查询接口，传三个参数」 |
| 被否掉的备选 | 「前端拼文件被否：只能导当前页，且手机号已经进了浏览器」 | 只写选了什么，不写为什么没选别的 |
| 边界值 | 「单次上限 2,000 行；超过提示收窄筛选，不分片」 | 「性能要优化」 |
| 风险与挡法 | 「组长可能看到别组 → 组别过滤放在取数这一步」 | 「注意权限问题」 |

「被否掉的备选」这一栏值得单说。它不是给别人看的礼貌，是给自己留的**后悔药**：三个月后有人问「为什么不做成导出中心」，你翻回这一段，能立刻说出当时的理由。没有这一段，讨论会从头再来一遍。

### Design 的出口

一份合格的设计段，出口是四样：

1. **一条主路径**，用业务语言说清数据从哪来、经过谁、到哪去。
2. **至少一个被否掉的备选**，以及否掉的理由。
3. **边界值**：数量上限、时间上限、并发上限，各自超了怎么办。
4. **风险清单**：每条风险配一个挡法，挡法要落在结构上（过滤、白名单、限额），不能落在「注意」上。

### Tasks：按「可独立验证」切，不按工种切

任务段最常见的切法，是按工种切：前端一条、后端一条、测试一条。这种切法看起来整齐，实际有一个致命问题：**每条都做完了，但没有一条能单独证明做对了。**

正确的切法只有一条标准：**这一条做完，能不能有人单独验它？**

- 「把组别过滤放进取数这一步」——能验：拿组长账号导一次，看是不是只有本组。
- 「前端页面改一下」——不能验：改成什么样算改完？

所以任务表的每一行，至少要有四格：

| 格 | 写什么 | 反例 |
| --- | --- | --- |
| **做什么** | 一个可观察的结果，不是一个动作 | 「改一下导出逻辑」 |
| **依赖** | 它必须在哪一条之后；为什么 | 「无」——但实际要等权限定完 |
| **完成标志** | 别人怎么知道这条完成了 | 「功能正常」 |
| **谁来验** | 一个具体的人或角色，不是「测试」 | 「测试同学」 |

### 顺序：权限先于生成

任务排序有一条不能调的原则：**涉及权限与数据范围的条目，排在「把东西做出来」之前。**

理由不是「先易后难」，也不是「先做重要的」。理由是：**先做出来再补权限，会把一次真实的越权留在环境里。**

具体到导出这件事：如果先做「点一下生成文件」，再补「组长只能导本组」，那么中间那段时间里，任何一个组长点一下，都能拿到全部 120 条含手机号的名单。这段窗口可能只有两天，也可能只有两小时——但**测试环境里的名单，往往就是真名单**。

所以顺序是：先定谁能导、导什么（需求段已经写了），再把过滤放进取数（任务 2），最后才做生成与下载（任务 4）。这三步的顺序，就是一次风险的收口顺序。

### Tasks 的出口

一张合格的任务表，出口是三样：

1. **每条任务都有完成标志**，且这个标志能被第三个人观察到。
2. **依赖写清了「为什么是它前面」**，不只是「在它前面」。
3. **每条任务都指派了一个具体的验收人**，不是「测试」这个抽象角色。

任务表还有一个隐性出口：**它能被用来判断「做完了没有」。** 如果一张任务表上所有条目都打了勾，但没人能说出「现在可以给组长用了」，那这张表只记录了动作，没有记录结果。

## 26.7 Testing：先设计，后执行

### 三类用例，缺一类就测不出东西

测试不是「把功能点一遍」。它至少要有三类，各自回答不同的问题：

| 类型 | 回答什么 | 报名表导出的例子 | 缺了会怎样 |
| --- | --- | --- | --- |
| **正常** | 按预期用，能不能用 | 筛选第三组导出，28 行 | 基本功能都没通，后面不用谈 |
| **异常** | 不按预期用，会不会出事 | 0 条、超上限、连点两次、链接过期、组名带特殊符号 | 上线第一天就遇到没想到的输入 |
| **回归** | 原来能用的，现在还能不能用 | 翻页、搜索、单条查看、报名提交 | 修好一个，弄坏三个，而且没人发现 |

三类里最容易被省的是**回归**，因为它不产生「新功能可用」的成就感。但回归恰恰是变更类工作里最值钱的一类：**你改的是一个已经在运转的系统，最大的风险不是新功能不好用，是老功能被顺手弄坏了。**

### 测试设计在前，执行在后

这句话不是流程洁癖，它有一个很实际的作用：**写用例的过程，就是第二次检查需求的过程。**

当你为「组长只能导本组」写用例时，你会立刻遇到一个问题：组长把筛选选成「全部」，应该看到什么？是报错，是自动收窄到本组，还是显示全部但导不出？需求段没写。这个空洞在写用例时被发现，改一句需求就行；在上线后被用户发现，就是一次投诉。

所以顺序是：**先写用例清单，再动手做，最后才执行。** 写用例时不需要系统存在，只需要需求段和设计段存在。

```text
测试设计在前，能提前暴露的三类空洞：

  需求空洞 ──▶ 例：组长选「全部」时该怎样？需求段没写
                  → 回改需求段，补一句，不补测试

  设计空洞 ──▶ 例：超过 2,000 行是报错还是截断？设计段没定
                  → 回改设计段，定一个值，不靠测试时临场决定

  验收空洞 ──▶ 例：「文件能打开」算不算验收条件？
                  → 它不可判定（什么算能打开？），改写或删掉
```

### 结果不对，回改规格，不是补测试

这是本篇最想让人记住的一条操作纪律。

跑出来不对，有三种可能，处置完全不同：

| 情况 | 长什么样 | 正确处置 | 错误处置 |
| --- | --- | --- | --- |
| **实现错了** | 规格写的是 28 行，跑出来 120 行 | 改实现，重跑同一条用例 | 改验收条件，把 120 说成「也合理」 |
| **规格没写清** | 组长选「全部」时行为未定义，实现选了一种 | **回改需求段**，写清，再补用例 | 在测试里加一条「允许两种情况」，把问题盖住 |
| **规格写错了** | 规格要求 28 行，但业务其实要 31 行 | 回改需求段，说明为什么改，同步给所有相关人 | 直接改测试，让它过 |

三种情况有一个共同的错误处置：**补一条测试，让不符合规格的结果变得合法。** 这是测试里最隐蔽的腐化方式——它不删需求，它让需求变得不重要。跑一次，加一条例外；再跑一次，再加一条。三个月后，测试全绿，但没有人知道系统到底该做什么。

所以纪律可以写成一句话：

> **测试是规格的证据，不是规格的橡皮擦。**

如果一条验收条件反复不通过，正确的问题不是「怎么让它通过」，是「这条验收条件还是不是我们要的」。**如果是，改实现；如果不是，改规格并留下理由。两者都不是「改测试」。**

### 证据：四种形态，都不接受「我看过了」

测试跑完，要留下能给别人看的东西。口头的「我测过了」在复盘时一文不值，因为它无法区分「真的测了」「测了但漏了」「没测但以为测了」。

四种证据，对应四类断言：

| 断言 | 证据形态 | 为什么是它 |
| --- | --- | --- |
| 「行数对」 | 页面显示的数字与文件行数的对照（截图 + 日期） | 两个数摆在一起，第三个人能自己核 |
| 「权限对」 | 三个角色各导出一次的列与行范围对照表 | 权限是「谁能看到什么」，只能用角色对照证明 |
| 「动作发生过」 | 审计里的一条记录，含执行人、时间、筛选、行数 | 自述不算，记录才算（见[第 16 篇](16-receipt.md)） |
| 「没弄坏别的」 | 回归清单逐项打勾，写清谁打的、什么时候 | 「应该没事」不是证据，勾选是 |

四种证据里，第三种最容易被省略，也最容易被伪造。系统里写着「导出成功」不等于审计里有记录；审计里有记录，也不等于那次导出真的是这个人做的。**证据要指向原始系统，不指向模型或页面的措辞。**

### Testing 的出口

一份合格的测试段，出口是两样：

1. **一份用例清单**，每条前面标着它对应哪条验收条件；正常、异常、回归三类都有。
2. **一份证据包**，四类证据各至少一份，带日期和出具人。

再加一条隐性出口：**每条需求都能追到一条测试，每条测试都能追到一份证据。** 追不上的那一条，要么是需求多余，要么是测试漏了，要么是证据没留——三种都得处理。

## 26.8 四件产物示例：「报名表加个导出」

**以下案例为虚构，数字为示意，用于展示四段的写法，不是实测。** 完整软件案例的走法见第 30 篇。

背景：一个读书会活动，报名表里有 120 条记录，分四个小组（31、30、28、31）。三个管理员，四个组长。字段有姓名、手机号、报名时间、小组、饮食备注、紧急联系人、是否已签到。列表每页 20 条，可以按小组筛选。

小陈要的是「周五交给场地」，组长要的是「活动前拿到本组名单」。这两句话，就是需求段的起点。

### 第一件：需求段

```text
需求段（Requirements）· 报名表导出 · v1 · 10 月 12 日

一、这件事为谁做
  提出人：活动运营 小陈（管理员账号）。
  两个使用场景：
  （1）活动结束后，把名单交给场地和餐饮；
  （2）活动前，把本组名单发给组长。
  第二个场景决定了：导出不能只有「全部」一种。

二、范围（这次做什么）
  在「报名列表」页加一个导出入口，导出当前筛选条件下的记录。
  导出的列固定为四列：姓名、小组、报名时间、是否已签到。
  每次成功导出，在审计里留一条记录。

三、非目标（这次明确不做）
  不做「导出全部」的第二个按钮；
  不做定时导出、不做自动发邮件；
  不改报名表单，不改列表的排序与翻页；
  本期不导出手机号、饮食备注、紧急联系人。

四、权限与数据范围
  谁能导：管理员（3 人）可导出全部小组；组长（4 人）只能导出自己组。
  导什么：只导出上面四列，手机号与备注不进文件。
  谁能看：文件只下载到操作者本机，不落公共盘、不发群、不进共享链接；
          下载入口 30 分钟内有效，过期需重新导出。
  留什么痕：谁、什么时间、用了什么筛选、导出了多少行。

五、验收条件（做到没做到，看这七条）
  1. 筛选「第三组」后导出，文件里 28 行，每行的小组都是第三组。
  2. 不设任何筛选直接导出，文件里 120 行，不是当前页的 20 行。
  3. 文件里没有手机号、饮食备注、紧急联系人三列。
  4. 组长账号把筛选选成「全部」再导出，文件里仍只有自己组的行。
  5. 筛选结果为空时，页面提示「当前筛选没有记录」，不生成空文件。
  6. 每次成功导出后，审计里出现一条对应记录，行数与文件一致。
  7. 原有的翻页、搜索、单条查看、报名表单提交，行为不变。
```

这段里最值得看的是第五节的第 2 条和第 4 条。第 2 条挡的是「导出当前页」——那是最省事的实现，也是最容易发生的事。第 4 条挡的是「筛选被绕过」——组长把筛选选成全部，是权限最容易被突破的入口。

### 第二件：设计段

```text
设计段（Design）· 报名表导出 · v1

一、方案（一句话说清怎么走）
  列表页把「当前筛选」原样交给后台；后台按同一套筛选条件取数、按列白名单生成文件；
  生成完给一个短时有效的下载入口。前端不取全量数据再自己筛。

二、为什么是这条路（两条备选被否掉）
  备选甲：前端把当前页的数据拼成文件。
    否掉：只能导当前页；而且手机号已经进了浏览器，权限收不回来。
  备选乙：新做一个「导出中心」页面。
    否掉：本期只有一个场景；多一个页面就多一套权限要维护。

三、边界（做到哪里停）
  单次上限 2,000 行。超过时提示「请收窄筛选」，不做分片下载。
  同一账号同时只允许一个导出在进行；重复点击返回「正在生成」。
  文件生成后 30 分钟内可下载，过期删除，不保留副本。

四、风险与挡法
  风险 1：「当前筛选」被理解成「当前页」。
    挡法：入口上直接写行数——「导出当前筛选（28 条）」。
  风险 2：组长看到别组。
    挡法：组别过滤放在取数这一步，不靠页面隐藏；组长账号的筛选上限就是本组。
  风险 3：手机号被顺手加进列里。
    挡法：列白名单写在需求段；新增列必须改需求段并重新验收。
  风险 4：文件落在服务器上被别人取走。
    挡法：不落共享目录；下载入口一次有效、短时有效。
  风险 5：导出拖慢列表。
    挡法：导出与列表查询分开限流，导出排队时不影响翻页。

五、这次不在设计里留开关
  手机号导出、跨活动合并、Excel 多工作表——都不在本期。
  不留「以后再打开」的配置项，因为它会变成一条没人负责的旁路。
```

第四节的五条风险，每一条都配了一个**结构性的挡法**。注意它们都不是「注意一下」：写行数、过滤放进取数、列白名单写进需求、不落共享目录、分开限流——每一条都能被验证，也都能被检查是不是真的做了。

### 第三件：任务段

```text
任务段（Tasks）· 报名表导出 · v1
每行都要能单独验；验不了的行，说明它还不是一个任务。

任务 1  定列白名单与两个角色的可见列
  依赖：小陈确认四列够用（已确认，10 月 12 日）
  完成标志：管理员、组长、普通成员三个账号各看一次，列完全一致
  谁来验：小陈

任务 2  把组别过滤放进取数这一步
  依赖：任务 1
  完成标志：组长账号把筛选选成「全部」，导出的仍只有本组
  谁来验：管数据的人（不看页面，只看导出结果）

任务 3  接上「当前筛选」，并把行数显示在入口上
  依赖：任务 1
  完成标志：切换筛选后，入口上的数字与列表总数一致
  谁来验：小陈

任务 4  生成文件与短时下载入口
  依赖：任务 2、任务 3
  完成标志：文件能打开；行数、列、中文都对
  谁来验：小陈 + 一个组长，各一次

任务 5  审计记录
  依赖：任务 4
  完成标志：导出一次，审计里出现一条，行数与文件一致
  谁来验：管数据的人

任务 6  空结果与超限提示
  依赖：任务 4
  完成标志：0 条与 2,001 条两种输入下，提示正确且不生成文件
  谁来验：小陈

任务 7  回归原有功能
  依赖：任务 4
  完成标志：翻页、搜索、单条查看、报名提交逐项打勾
  谁来验：小陈

顺序上有一条不能调：任务 2 在任务 4 之前。
理由不是「先易后难」，是「先做出来再补权限」会把一次真实的越权
留在环境里；而测试环境里的名单，往往就是真名单。
```

### 第四件：测试段

```text
测试段（Testing）· 报名表导出 · v1
先写这一页，再动手。每条前面标它对应哪条验收条件。

正常
  用 1：管理员筛选第三组导出 → 28 行，全为第三组（验收 1）
  用 2：管理员不筛选导出 → 120 行（验收 2）
  用 3：组长导出 → 只有本组；把筛选改成「全部」再导一次，结果不变（验收 4）

异常
  用 4：筛选一个没有记录的小组 → 提示，不生成文件（验收 5）
  用 5：造 2,001 条数据 → 提示收窄，不生成文件（设计边界）
  用 6：连点两次导出 → 第二次提示「正在生成」，不产生两个文件
  用 7：生成后等 31 分钟再点下载 → 提示过期，可重新导出
  用 8：小组名里有引号、斜杠、空格 → 文件名正常，文件能打开

回归
  用 9：翻页、搜索、单条查看、报名表单提交、列表排序（验收 7）
  用 10：普通成员账号看不到导出入口（权限段）

证据（每条都要留，不接受「我看过了」）
  行数对照：页面显示的数字 vs 文件行数，截图并写日期
  角色对照：三个账号各导出一次，列与行范围的对照表
  审计条目：一条导出对应一条记录，行数一致
  回归清单：十项逐项打勾，谁打的、什么时候打的
```

### 四段之间怎么对上

四件产物写完，最后要做一次对齐：随便抽一条需求，能不能顺着链找到设计、任务和证据。

| 需求 | 设计里对应 | 任务 | 测试 | 证据 |
| --- | --- | --- | --- | --- |
| 验收 1（筛第三组 28 行） | 方案「当前筛选原样交给后台」 | 任务 3、4 | 用 1 | 行数对照 |
| 验收 2（不筛选 120 行） | 风险 1「当前筛选 ≠ 当前页」 | 任务 3、4 | 用 2 | 行数对照 |
| 验收 3（不含手机号列） | 风险 3「列白名单」 | 任务 1 | 用 1、2、3 | 文件列对照 |
| 验收 4（组长只得本组） | 风险 2「过滤放在取数」 | 任务 2 | 用 3 | 角色对照 |
| 验收 5（空结果） | 边界「0 条不给文件」 | 任务 6 | 用 4 | 提示截图 |
| 验收 6（审计记录） | 方案「每次导出留痕」 | 任务 5 | 用 1 | 审计条目 |
| 验收 7（不弄坏原有） | 非目标「不改列表」 | 任务 7 | 用 9 | 回归清单 |

这张表就是「可追溯」的具体样子。它不要求你写得多漂亮，只要求**每一行都填得出来**。填不出来的那一行，就是这次变更里最薄的一块：要么需求多余，要么设计漏了，要么测试没覆盖。

## 26.9 判断：这类变更该不该上 Spec

不是所有事都值得写四段。判断的标准不是「重要不重要」，是四条更具体的：

| 判据 | 问法 | 命中就上 Spec | 典型反例（可以 Vibe） |
| --- | --- | --- | --- |
| **不可逆** | 做错了，能不能一次退回？ | 会发出、会付款、会删除、会改权限、会让别人看到 | 自己机器上的一个脚本，删了重来 |
| **影响面** | 会不会碰到别人的数据、钱、对外可见的东西？ | 别人的名单、客户能看到的内容、共用的流程 | 一个人的看板配色、内部草稿的排版 |
| **承诺对象** | 有没有一个不在场的人，要按这个结果做事？ | 组长按名单核对签到；场地按人数备餐 | 只有你自己看的一次性分析 |
| **复用与追责** | 会不会被第二个人用、第二次改？出事要不要查「当初定的是什么」？ | 会进流程、会被交接、会有人问「谁定的」 | 一次性的探索、做完就扔的对比 |

四条里只要命中一条，就值得上 Spec。全都不中，可以 Vibe——但产物要明确标成「原型，不进主线」。

这套判据有三个用法上的补充。

**第一，判据看的是「这次变更」，不是「这个项目」。** 同一个报名系统里，改一个按钮颜色可以 Vibe，加一个导出必须 Spec。用项目大小来判断，会让你在最该写规格的地方省掉规格。

**第二，命中「承诺对象」是最强的信号。** 因为它的意思很直接：**有一个人会根据你的结果去行动。** 组长按你给的名单去核对签到，场地按你给的人数去备餐——他们不会去验证你的数据，他们信任它。这种信任一旦被辜负，代价不在你这边。

**第三，小改动可以用「一页纸规格」。** 不必四段齐全，但四样不能少：

```text
一页纸规格（适合小改动，四行写完）

  范围：这次做什么，一句话。
  非目标：这次不做什么，一句话。
  验收：做到没做到，两到三条，每条都可判定。
  权限：谁能用、能碰哪些数据、结果去哪，一句话。
```

四行写不满一页，但它能挡住绝大多数「做偏了」。反过来，如果这四行你都写不出来，那说明这件事不适合现在做——不是不适合 Spec，是不适合开始。

## 26.10 边界三列账：Spec 能做什么、代价是什么、何时失效

| 能做什么 | 代价是什么 | 何时失效 |
| --- | --- | --- |
| 把「做好了」变成可判定的条件，让第三个人能独立验收 | 写验收条件要花时间，而且常常写到一半发现需求没想清 | 验收条件写成了形容词（「流畅」「友好」），或者写成了实现细节（「用某个组件」） |
| 在动手前定下权限与数据范围，把越权挡在设计阶段 | 要有人拍板「谁能用」；拍板的人常常不在会议室 | 需求段写了权限，实现时被当成「设置」漏掉；或者上线后被人临时放开 |
| 让改动可追溯：每条需求能追到设计、任务、测试、证据 | 维护这条链要成本；小改动上四段，成本可能超过收益 | 链只在交付时对一次，之后没人更新；或者需求改了，下游没跟着改 |
| 让测试先于实现，提前暴露需求的空洞 | 前期会变慢，而且慢在「还没看到东西」的时候，最难被接受 | 团队把写用例当成流程动作，先做完再补用例，顺序反了 |
| 减少「做完了才发现方向错」这一类返工 | 它减少不了「做的时候写错了」这一类返工；那要靠测试和评审 | 需求本身是探索性的——这时候 Spec 会把错的答案写得很正式 |

这张表最该看的是最后一列。**Spec 的失效，几乎都不是因为它写得不够长，而是因为它被用在了不该用的阶段，或者被当成了文档而不是承诺。**

### Spec 不是文档负担，但很容易变成文档负担

先说清「负担」是什么。负担不是「写了字」，是**写了没人读、读了也不改变任何决定**。

四段规格如果只是交付时附在邮件后面，它就是负担：写它花了两天，读它花了零分钟，它没有改变任何一个决定。反过来，如果它在写的过程中改变了三个决定——范围从「导出全部」收窄到「导出当前筛选」、权限从「上线再说」提前到「先定谁能导」、测试从「做完再测」提前到「先写用例」——那它这两天就是整个变更里最值钱的两天。

所以判断一份规格值不值，不看它多长，看它**改变了几个决定**。一个很实用的自检：写完四段，问自己「有没有哪一条，是我写着写着才发现的？」如果一条都没有，要么这件事你早就想清了（那四段只是记录），要么你只是把已知的东西抄了一遍（那它确实是负担）。

### 写不出验收条件，说明需求本身没想清

这句话常被当成批评，其实它是一个**诊断**。写不出验收条件，通常是三种情况之一，处置完全不同：

| 情况 | 表现 | 该怎么办 |
| --- | --- | --- |
| **它不是需求，是愿望** | 「我希望名单用起来方便一点」 | 追问场景：谁、在什么时候、要拿它做什么。问出场景，才有验收 |
| **它是探索，不是交付** | 「我也不知道导出来该长什么样，先看看」 | 回 Vibe。做一个能点的原型，看完再回来写 |
| **它是几个需求混在一起** | 「导出要好用、要快、要能发给组长、还要能统计」 | 拆开。一条一条写验收，写不出的那条单独处理 |

三种情况有一个共同点：**它们都不是「文档能力不足」，是「信息不足」。** 硬写只会把信息不足包装成文档完整，让后面的人以为已经想清了。**这比不写更危险**，因为它把不确定性藏起来了。

### 这个类比在这里失效

规格常被比作**合同**：双方把承诺写下来，签字，之后按它执行。

这个类比抓住了「先写死再执行」这一半，但它在一步上不成立：**合同的约束力来自违约成本，规格的约束力不来自文字本身。**

签了合同，对方不履约要赔钱；写了规格，实现不照做不会有任何自动后果。规格不会自己执行，它需要三样东西替它兜底：

1. **测试**——把「有没有做到」变成可观察的结果；
2. **权限**——把「不该做的」变成做不到（见[第 17 篇](17-injection-and-permission.md)）；
3. **验收与签字**——让一个人对着证据说「收」或「不收」。

没有这三样，规格只是一份写得很认真的意愿书。这也回到 26.2 的那句话：**规格是承诺，不是保证。**

还有一个更细的失效点：**合同可以冻结，需求不能。** 合同签完，标的物不会自己变形；而软件需求会在实现过程中反过来改变——你做出第一版导出，小陈才第一次说清「我其实要按组发」。所以规格不该假装自己能一次冻结，它要留一个明确的「改规格」入口：谁改、为什么改、改了之后下游哪几段要跟着改。**能改，但改要有记录**，这才是规格和「边做边改」的区别。

## 26.11 你可以自己做的检验

十分钟，不需要写代码，也不需要打开任何 AI 工具。拿一张纸。

### 检验一：把一条口语需求写成四行

挑一件你最近想做的小事——不是报名表，是你自己的事。比如「把每周的会议记录整理成一个能发给同事的摘要」。

写下四行：

| 行 | 你写什么 | 判据 |
| --- | --- | --- |
| 范围 | 这次做什么，一句话 | 这句话里有没有一个可以数出来的边界 |
| 非目标 | 这次不做什么，一句话 | 这一条是不是「预计会有人提」的那种 |
| 验收 | 两到三条，每条可判定 | 第三个人不问你能不能判 |
| 权限 | 谁能用、碰哪些数据、结果去哪 | 三个问题各有一句回答 |

### 检验二：把验收条件交给一个没参与的人

找一个人（同事、朋友都行），只给他验收那两三条，不给他背景。请他回答一个问题：**「如果我说做完了，你能自己判断真假吗？」**

**判据**：如果他追问超过两次（「什么叫整理好」「摘要多长」「发给谁」），说明你的验收条件还不可判定。追问的每一句，都是需求段缺的那一格。

### 检验三：删掉一条非目标，看范围会不会膨胀

把你写的非目标删掉一条——挑那条最像「顺便也能做」的。然后问自己：如果实现的时候有人提这一条，我有没有依据拒绝？

**判据**：如果你发现自己只能说「这次先不做」，而说不出「为什么不做的理由已经写在需求里」，那这条非目标本来就没写清。**非目标的用处不是禁止，是让拒绝有依据。**

### 这个检验可能推翻本篇

有一种结果会让本篇的结论对你失效：你按四条判据过了一遍，一条都不中——可丢弃、影响面小、没有承诺对象、不会被第二个人用——而你还是写了四段规格，写完发现它没有改变任何一个决定。

这时候正确的结论不是「规格很重要，只是这次没体现」，而是：**这类变更确实不该上 Spec。** 本篇给的是判据，不是义务。**在不需要承诺的地方写承诺，和在没有边界的地方谈边界，是同一种浪费。**

## 26.12 术语考古：三个被用坏的词

### Vibe Coding

| 栏 | 内容 |
| --- | --- |
| **最早出处** | **社区用语**，出处以正文核对为准。它随「用自然语言让模型直接产出可运行结果」这种做法一起流行，没有一个类似规范的统一定义，也没有公认的提出者。本文不指认年份，也不把它归到某一家厂商名下。 |
| **原义** | 强调**姿态**：不先写规格，凭感觉和即时反馈往前推，边看边改。词里的「vibe」指的是这种「跟着感觉走」的工作方式，不是指某一类工具。 |
| **现在被怎么用** | 两个方向都被用坏了。一边把它说成「不写代码也能做产品」的捷径，暗示可以跳过需求与验收；另一边把它当成贬义，等同于「不专业」「玩具」。 |
| **本文怎么用** | 一种**有明确适用条件的探索方式**：低风险、可丢弃、有回退，目的是「先看到东西，从而发现自己要什么」。它的产物是灵感与可丢弃原型，**不是交付物**；它有一个明确的退出条件——你能说出一条第三个人可以判定的验收条件。 |

### 规格（spec / specification）

| 栏 | 内容 |
| --- | --- |
| **最早出处** | 工程与采购领域的长期用语（「规格书」「技术条件」），后来被软件工程借用，指对系统行为的约定。**没有单一发明人**，也不是某一种方法论的专有名词。 |
| **原义** | 一份说清「要什么、不要什么、按什么标准算做到」的约定；重点是**约定**，不是**描述**。 |
| **现在被怎么用** | 常被当成两种东西：一种是「详细设计文档」，写满了实现细节；另一种是「给 AI 的长提示词」，越长越像规格。两种都把它当成了文本，而不是一段有出口的约定。 |
| **本文怎么用** | 四段结构：需求、设计、任务、测试。每一段有输入和出口；需求段必须含验收条件、非目标、权限与数据范围。**规格是承诺，不是保证**——它要配测试、权限和验收才有约束力。 |

### 验收条件（acceptance criteria）

| 栏 | 内容 |
| --- | --- |
| **最早出处** | 软件工程与采购验收的长期实践，社区里常与「完成的定义」一起出现；**没有统一规范**，不同团队写法差别很大。本文按**社区用语**处理，不指认具体文献。 |
| **原义** | 事先写好的、可判定的「做到没做到」的条目；它服务于验收，不服务于描述。 |
| **现在被怎么用** | 常被写成形容词：「功能正常」「体验良好」「性能达标」。也有人把它直接等同于测试用例，于是「测了什么」变成了「要求什么」。 |
| **本文怎么用** | 一条能被第三个人在不问你的情况下判定真假的陈述，形状是「在什么条件下、做什么、看到什么可观察的结果」。它**不等于**测试用例，但每条都必须能长出一个测试；写不出它，说明需求还没想清。 |

三个词共同的毛病，是**把「一段文字」当成了「一种约束」**。Vibe 被当成一种能力标签，规格被当成一份文档，验收条件被当成一句形容词——三者都丢掉了同一个东西：**它们只有在被人使用、并且能改变决定的时候才成立。** 一份没人读的规格，和一句没人判的验收条件，与没写是一样的；区别只在于后者看起来更认真。

## 26.13 一页速记

| 你遇到的情况 | 一句话带走 |
| --- | --- |
| 还不知道要什么，想先看看 | Vibe；但三条前提：可丢弃、影响面小、有回退 |
| 原型跑通了，想直接上线 | 「跑通了」只证明路径存在，不证明稳定（P3） |
| 不知道什么时候该停止乱试 | 你能说出一条第三个人可判定的验收条件时 |
| 一句「加个导出」要澄清什么 | 范围、非目标、权限与数据范围、验收条件 |
| 验收条件写到哪一段 | 需求段。写完再进设计，不能留到测试段补 |
| 权限和数据范围写在哪 | 需求段。写「不做」比写「注意」有用 |
| 任务怎么切 | 按「能不能单独验」切，不按工种切 |
| 测试什么时候写 | 动手之前。写用例是第二次检查需求 |
| 跑出来不对怎么办 | 先分是实现错、规格没写清、还是规格写错；不许改测试 |
| 这份规格值不值 | 看它改变了几个决定，不看它有多长 |
| 写不出验收条件 | 三种可能：是愿望、是探索、是几个需求混在一起 |
| 该不该上 Spec | 四条判据：不可逆、影响面、承诺对象、复用与追责 |

**五句话带走**

1. Vibe 和 Spec 不是水平高低，是用途不同：一个发现要什么，一个保证改对了。
2. Vibe 的三条前提是可丢弃、影响面小、有回退；它的产物是灵感，不是交付物。
3. 验收条件写在需求段；写不出它，说明需求本身没想清，不是文档能力不足。
4. 测试是规格的证据，不是规格的橡皮擦；结果不对，回改规格或改实现，不改测试。
5. 规格是承诺，不是保证；保证要靠测试、权限和验收签字。

**三道自检**

1. 同事说：「这个功能很简单，不用写规格，直接做吧。」你用什么来判断他这句话对不对？
2. 你为一个导出功能写了七条验收条件。跑测试时发现第 4 条怎么都过不了，但业务说「其实这样也行」。你该怎么办？
3. 团队用 Vibe 方式做了一个原型，演示很成功，老板说「下周就上线给客户用」。按本篇的判据，你要先补哪几样东西？

1. 不看「简单不简单」，看四条判据：这件事可不可逆、会不会碰到别人的数据或对外可见的东西、有没有一个不在场的人要按结果做事、会不会被第二个人用或需要追责。四条全不中，可以直接做（并标成原型）；命中任何一条，尤其是「有承诺对象」，就该至少写一页纸规格：范围、非目标、两三条验收、权限。**「简单」描述的是实现，不是后果**——一个按钮很简单，但它能把 120 条手机号导出去。

2. 先分清是哪一种不通过。如果实现和规格不一致（规格要 28 行，跑出来 120 行），改实现。如果规格没写清（比如组长选「全部」时该怎样），回改需求段，补一句，再补用例。如果规格写错了（业务其实要另一种行为），回改需求段，写清为什么改，通知所有相关人，并让下游的设计、任务、测试跟着改。**唯一不能做的是直接改测试让它过**——那会让「第 4 条」从一条承诺变成一句建议。业务说「其实这样也行」时，要追问的是：那原来那条还要不要？如果要，就是实现问题；如果不要，就正式改规格并留理由。

3. 至少补四样。第一，把它从「原型环境」挪到「有人要按它做事」的场景里，重新过一遍四条判据——给客户用，命中「影响面」和「承诺对象」。第二，补需求段：范围、非目标、验收条件，特别是权限与数据范围（客户能看到谁的数据、文件去哪）。第三，补测试，尤其是异常与回归，并留下证据；演示成功只能证明正常路径存在。第四，确认权限是在结构上收住的，不是靠一句提示词——原型阶段为了试通临时开的发送、导出、写入，要先关掉再谈上线。**演示成功不是上线依据，它只是一次 Vibe 的收尾。**
