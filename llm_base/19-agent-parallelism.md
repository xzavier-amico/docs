# 19 · Agent 并行：拆开跑，还是一条线做到底

> **状态**：已完成（初稿）
>
> **本篇定位**：Part IV 第 5 篇。用依赖关系决定要不要并行，约定怎么合并、重试和停手。
>
> **读法**：先把自己当成市集的协调人看依赖图，再用卡片练习一次分工和收尾。

## 三个助手同时开工，为什么反而多做了一遍？

在虚构的周末市集案例里，你让 Agent **只整理报名清单及通知草稿，不发送**。市集原定周六，旧 v1 已失效，现行 v2 改为**周日 14:00**，下雨是否改室内仍待确认。为了快，你把相同的全部材料发给三个助手。一个核对场地，一个查预算，一个整名单。回来一看：三个都重新读了旧通知，有人写周六，有人擅自填了室内，有人还把只有名单整理者能看的个人资料抄进交接。事情是同时做了，但结果不能直接拼一起。

**本篇的真问题：哪些工作能同时做，哪些必须等上游定稿？** 关键不在于找多少助手，而在于画清楚**依赖**：某一步必须先拿到什么，才能正确往下做。分支如果抢跑，快的是草稿出现的速度，不一定是可交付的速度。

## 1. 把「可以先核对」和「可以先定案」分开

```text
用户：确认目标、资料权限和现行 v2；只做清单和通知草稿，不发送
                              ↓ 应用／协调者发出各自任务卡
           ┌──────────────────┼──────────────────┐
           ↓                  ↓                  ↓
     场地组：核对 v2      预算组：查已批准项    名单组：核对获准的报名字段
     雨天室内待确认       不下单、不公开        不假定室内容量
           ↓                  ↓                  ↓
           └─────────────→ 汇总并核验 ←──────────┘
                        对版本、出处和未决项
                              ↓
                  人审阅报名清单与通知草稿
                              ↓
                   交草稿；本任务到此为止
```

图里的「人审阅」是验收草稿，不是审批发送。在同一次任务里就算草稿通过，也没有发送授权。场地、预算、名单之所以能先并行，是因为拆的是**查事实**。场地组不用等名单组才看 v2，预算组不用等场地方谈出室内结果才核对已有批准记录，名单组可以先根据已知规则整理经授权的必要字段。但如果你还想按室内容量安排摊位，就必须等场地和容量确认；如果预算决定取决于是否启用室内，也不能先把条件方案当批准。那些依赖未满足时，最多列待确认项，不给确定安排。

画图时可以逐步问：「这一步若拿不到另一组的结果，能否独立完成它承诺的交付？」能做一部分，就写清做到哪部分。例如「先标重复项」不等于「可以决定谁入选」。所有分支共用 v2，是为了对齐入口，不是为了复制一整摞相同材料。并行读不同资料可以互不打扰；并行写同一份清单则容易相互覆盖，较稳的做法是各交一份有版本的结果，由一个指定的汇总人合并到草稿。

## 2. 三种跑法，先选最简单够用的一种

| 跑法 | 谁在做，什么时候适合 | 代价或容易失效的地方 |
| --- | --- | --- |
| 串行，一条线做到底 | 同一人或 Agent 依次核对；材料少、每步依赖上步，或需要一路审阅 | 独立的等待也会排在一起；流程简单却不一定慢，少了拆分沟通和合并 |
| 一个 Agent 并行查独立资料 | 同一个协调者，让应用同时查 v2 和获准的名单数据，各有返回 | 适合主要在等独立查询；应用必须支持并发、按权限处理结果，不是多个 Agent 自治 |
| 多 Agent 分支协作 | 各分支在独立任务卡上处理材料，协调者汇总、找人核验 | 任务可分、每块工作量足够大时更合适；会多出分派、重复上下文和合并检查，可能多花钱 |

并行缩短的是重叠的等待，汇总仍要等**最慢的必要分支**。如果所有分支共用一个拥挤的服务，有的请求可能排队，时间未必比串行好。收到较快分支的结果不代表整个任务完成；收齐了也不等于事实一致。对小任务，把已经确认的一份 v2 和少量报名字段交给一个人按顺序核对，可能比组队更划算。

## 3. 分给每支一张小卡，收回来一份同格式结果

共同卡头写清楚：同一场市集、现行 v2、旧 v1 已失效、只交内部清单与通知草稿、不发送。具体分支只带必要资料：场地组看 v2 的场地和雨天条款；预算组只在获准时看内部批准记录，与对外草稿隔离；名单组看经授权的必要报名字段。不能为了「让每位都理解全局」，把联系方式和全部聊天同步给每个分支。

| 统一交付栏 | 怎么填 | 场地组的示例 |
| --- | --- | --- |
| 负责事项与材料版本 | 写清只核对哪件事，用到哪份有效材料 | 时间、场地和雨天；现行 v2，v1 已失效 |
| 结论与出处 | 每项结论附能核对的位置；不带无关私人内容 | 周日 14:00，见 v2 时间条款 |
| 未决、错误或缺口 | 不把未确认叫已完成；不把查不到写成不存在 | 雨天是否改室内待确认，见 v2 雨天条款 |
| 影响到哪份交付 | 标注该改清单哪里、草稿哪里，是否阻塞下一步 | 草稿写待确认；不分配室内摊位 |

汇总要找冲突，不能只拼文本。预算组若顺手引用旧通知写「周六」，查它是不是超出了负责范围，再回到自己能核查的 v2；不能靠两个分支都说周六就认定旧版胜出。汇总人如果没权看某段内部原文，应请有权的核对者提供获准交接的结论，不扩权拿全文。发现两个分支事实上核对了同一项，下一轮应去掉重复分派，除非是有意安排的独立复核，并明确它的目的与代价。

## 4. 先定失败处理规则，别让分支各自乱补

提前约定三件事：哪些错误必须拦下，哪些暂缺可以带着交付，最多允许花几次重试来补缺。例如，一个市集草稿可明确标雨天待确认，但不能把旧日期、未授权发送或泄露报名资料当成可接受小误差。试错的次数、耗时和花费也要单列上限，不能为填一个可标待确认的字段无限搜索。

| 情况 | 可预先约定的处理 | 结果如何交代 |
| --- | --- | --- |
| 可短暂恢复的查询失败 | 举例：同一分支最多再试一次；超上限或等得太久就停 | 标清失败的查询、已完成项和还缺什么，不重复其他分支 |
| 可带着走的未决项 | 雨天室内未确认，保留待确认，不再空转查找 | 草稿可交审阅；依赖室内容量的工作暂停 |
| 必须正确的事实或权限 | 现行日期无可核查来源，或名单权限不符，停止受影响步骤，请负责人核查 | 未完成项不冒充成品；未经授权不读取、不扩散、不发送 |
| 分支过期或任务取消 | 通知停止待执行工作，作废迟回的旧版结果；若平台无法立即停，隔离其返回 | 不能保证取消能追回已发生的动作；本例从开始就没有发送权限 |

协调者应收拢预算，不能每个分支都自行认为还有整笔额度。上游改版时，标记受影响的分支结果过期，取消能取消的工作，只重跑受影响的部分；其他已经核对好的事实不必全部重做。无法核验的必要结论要交还给人，不让更多助手轮流猜同一个缺口。

## 5. 手工练习：把分支写在卡片上，故意让一张迟到

准备「确认 v2」「核对场地」「核对预算」「整理报名」「汇总」「人审草稿」六张卡。把只能后做的卡压在它依赖的卡下面，能同时做的排成一排。再插入两张意外卡：「预算查询失败一次」和「迟回的场地结果还写周六」。先约定哪些一票否决、哪些可以待确认、失败最多重试几次，再模拟收卡。

**参考做法**：核对 v2 与本轮范围在前，三条独立核对并排，汇总与人审在后。预算查询若允许重试则按限次再试，仍失败标缺口；如果缺口不影响日期与报名整理，可先交已核查部分。迟回的周六结果不能拼入，查看其版本后改回现行周日 14:00；雨天仍待确认。若有人提议在核对场地时顺手排室内摊位，把这张卡移到室内确认之后。最后只交清单和草稿，不发送。

**速记**：先画依赖，再并行；少给资料，同格式回报；冲突找权威出处，必要失败才阻塞，超预算能停。并行省不省等待和钱，要分别看。

**自检（含简答）**

1. 场地没确认，能不能开始名单去重？**可以。** 若已有获准字段、且去重不依赖室内容量，可先做；不能据此定室内摊位。
2. 多个分支都写周六，少数分支写周日，怎么汇总？**查有效版本，不投票。** v2 生效，周日 14:00；旧 v1 失效。
3. 草稿人审通过，分支可以顺手发送吗？**不可以。** 验收不是发送授权。
