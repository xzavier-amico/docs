## 23.1 引子：「能本地跑」到底解决了什么

虚构现场，10 月 8 日傍晚，团建的通知还没发。负责人把一桌材料贴进一个在线对话框：通知 v1、通知 v2、A 与 B 两份报价、系统导出的 42 条名单、上次会议记录。他想让模型先出三行结论，再起草一份群通知。

IT 同事路过，看了一眼屏幕，问：「名单也贴进去了？」

他说：「就这一次，用完我就把对话删了。」

IT 说：「你删的是你这边。对面的日志、备份、风控记录，你删不掉。」

第二天的会上，三个人给了三个方案。

采购说：「买闭源 API。最省事，效果也最好。」

运维说：「上开源，自己部署。数据不出门，还不用付授权费。」

老板问：「能不能既不出门，又不要人管，还便宜？」

三句话各自都对了一半，也都漏了一半。采购把「通用能力最强」当成了「在你的任务上最好」；运维把「开源」当成了「免费」和「有人维护」；老板把四个约束当成了四个可以同时拉满的指标。

这一幕的核心判断可以先摆出来：

> **「能本地跑」只回答了四个问题里的一个——数据能不能不出门。它没有回答：跑出来的东西够不够用、总账划不划算、半夜坏了谁修。**

这句话从 P4 与 P2 直接推出来。P4 说，能力是烧进权重的：你能选的是「租别人的权重」还是「自己拿一份权重来跑」。后者不只拿到了权重，还把权重的保管、更新、精度、硬件一起接了过来。P2 说，模型只看得见这一轮被放到桌上的东西：数据边界不是一句「支持私有部署」，而是「这一轮放上桌的材料，经过谁的机器、留在谁的日志里」。桌子摆在哪，数据就去了哪。

所以三种形态的差别，说到底只有三件事：**权重在哪、桌子在哪、坏了谁修。** 这三件事的组合，决定了能力上限、成本结构、数据去向和运维负担，而不是反过来。

### 三句听起来都对的话

把会上那三句话拆开，每一句都能用四问过一遍。

| 说法 | 谁说的 | 它没说的是 | 该拿什么验证 |
| --- | --- | --- | --- |
| 「闭源 API 效果最好」 | 采购，基于榜单与演示 | 在**你的**任务上，硬失败有多少；版本会不会变 | 你自己的评测集，加同一批材料的重跑（→ [22](22-evaluation.md)） |
| 「开源不要钱」 | 运维，基于授权模式 | 机器、电、机房、人力、闲置、备件，哪一项是零 | 一张包含固定成本与工时的总账（→ [21](21-three-ledgers.md)） |
| 「私有部署数据不出门」 | 厂商，基于产品能力 | 日志、备份、监控、遥测、更新包，走不走外网 | 断网测试、日志核对、合同条款，不是演示 |

三句话的共同形状是：**把一个条件句说成了结论句。** 「开源可以不要授权费」是条件句；「开源不要钱」是结论句。「支持私有部署」是能力声明；「数据不出门」是事实断言。「在榜单上强」是条件句；「在你的任务上够用」是结论句。

本篇要做的，就是把这三个条件句补回它们缺的那半句。

## 23.2 唯一真问题：哪几个约束是不能谈的

选型的第一句话通常问错。不是「哪个模型最强」，而是：

> **在这四个约束里，哪几个是硬约束，哪几个可以谈？**

「最强」是一个没有主语、没有任务、没有口径的词。通用榜单上的最强，不等于你的任务上的硬失败最少；你的任务上的最强，也不等于总账最低。更准确的问题有两段：**先定下不能谈的约束，再在剩下的空间里找总代价最低的方案。** 跳过第一段，后面所有比较都是在拿一个可谈判的量，去换一个不可谈判的量。

四个约束，各自要用不同的证据来量。下面这张表里，最后一栏最重要：**每一种误认，都是把一个产品声明当成了事实。**

| 轴 | 该怎么量 | 证据长什么样 | 最常见的误认 |
| --- | --- | --- | --- |
| **能力** | 在你的任务分布上，硬失败率与稳定通过率 | 一组固定题、固定判据、重复跑；硬失败单列 | 榜单分数、演示效果、参数量、「它很聪明」 |
| **成本** | 单任务总账＋固定成本＋人力＋闲置＋退出成本 | 账单明细、报价单、工时记录、迁移工作量 | 单价、授权费、「按量很便宜」 |
| **数据边界** | 材料经过谁、留多久、谁能看、是否用于训练、能否删除 | 合同条款、日志、断网测试、删除回执 | 「支持私有部署」「我们不训练」「可以关掉」 |
| **维护** | 谁部署、谁升级、谁监控、谁回滚、谁值班、容量谁扩 | 值班表、变更记录、故障演练、备件清单 | 「开源社区很活跃」「托管方会管」 |

本篇不做三件事：**不排名、不预测下一版会怎样、不给任何单价。** 这三件事都会把选型从「约束下找可行解」变成「追一个不断移动的第一名」。

### 硬约束与软约束，不是同一种东西

四个轴里，能力和数据边界经常是**硬约束**：不满足就不能上线。成本和维护通常是**软约束**：可以换算，可以多花一点，可以少要一点。

这个区分比任何权重都重要。因为打分表会把硬约束稀释成一个小数：数据边界打 3 分、成本打 5 分，一加权，一个越界的方案就可能「总分最高」。**红线一旦被放进加权平均，它就已经被当成账了。**

所以选型的第一步不是打分，是分类：

- **硬约束**：违反一次就不能上线。数据不能出某个边界、监管要求可审计、错误不可逆——这些不参与交换。
- **软约束**：可以谈。预算、上线时间、人力投入、体验——这些可以用三本账互相兑换。
- **伪约束**：听起来像硬约束，其实是习惯或恐惧。「我们一直用这家」「换模型太麻烦」「老板说本地更安全」——这些要追问一句：**是谁说的，依据是什么，违反一次会怎样。**

分类做完，问题就从「四个指标怎么加权」变成了「先排除谁，再在剩下的里选谁」。这是一个小得多、也诚实得多的问题。

### 能力不是通用智力，是「在你的题上不犯硬失败」

这一点值得单独说，因为它是选型里最常见的一次偷换。

虚构的团建材料里，系统导出 42 条记录，其中 3 条是同一人的重复提交，去重后 39 人。一个模型可以在通用测试里表现很好，却仍然把 42 当人数；也可以在通用测试里一般，却因为你的提示里写清了「先去重」而稳定给出 39。

前者说明：**通用能力不等于你的任务能力。** 后者说明：**你的任务能力也不完全由模型决定**——材料、提示、检索、校验都在参与（→ [05](05-context-workbench.md)、[11](11-compression.md)）。

所以「能力」这一轴的正确问法是：

> **在我的评测集上，它的硬失败是哪几类、各出现几次、重跑之后还在不在？**

不是「它排第几」。排名是别人的题，硬失败是你的题。

### 用四问过一遍选型

第 1 问，**这句话是谁说的？** 厂商说「支持私有部署」，是产品能力声明；销售说「数据绝对安全」，是承诺；合同写「不用于训练」，是条款；日志显示「请求经过某区域」，才是事实。四层要分开。

第 2 问，**它这一轮看见了什么？** 在选型里，这个问题变成了：**我的材料，在谁的机器上被读入？** 不是「文件传上去了吗」，而是「传上去之后，经过了哪些环节，留在了哪里」。

第 3 问，**这是提议、事实，还是已经执行？** 「可以私有化」是提议；「已经部署完成、断网还能跑、日志留在本地」才是已执行。演示环境里的私有化，和你的机房里的私有化，是两件事。

第 4 问，**我拿什么独立验证？** 三样：你自己的评测集、试用期的日志、合同里的数据条款。缺一样，你验证的都只是对方的措辞。

## 23.3 四轴不是四个分数：先过三道闸，再算一笔账

四个约束不是平权的。正确的顺序是：**能力是门槛，数据边界是红线，成本与维护才是账。** 顺序一反，结论就会反。

```text
（示意）选型的三道闸；顺序不能反

  候选方案
     │
     ▼
  闸 1  能力：在我的评测集上，硬失败能不能接受？
     │        不能 ──▶ 换任务范围 / 换流程 / 换候选
     │                  （换形态救不了能力门槛）
     │ 能
     ▼
  闸 2  数据：材料能不能离开我控制的边界？
     │        不能 ──▶ 只剩「私有 / 专属托管」两条路
     │                  （先证明脱敏后仍可用，再谈出界）
     │ 能
     ▼
  闸 3  账：单任务总账 + 固定成本 + 人力 + 退出成本
     │        谁最低 ──▶ 再问维护：半夜坏了谁起来？
     ▼
  可行解（可能不止一个，按场景选）
```

三道闸的顺序，对应三个不同性质的判断。

**第一道，能力，是门槛。** 它问的不是「谁最强」，是「硬失败能不能接受」。过不了，就不要在形态上找出路：一个本地跑不动、或者跑出来老把 42 当人数的方案，换成云托管也不会突然变对。先改任务范围、改材料、改流程，或者换候选。

**第二道，数据，是红线。** 它问的不是「谁更安全」，是「材料能不能离开我控制的边界」。如果是硬约束，能选的形态立刻少一半；如果不是，就不要用「安全」当理由去选一个更贵、更难维护的方案。**「我感觉不安全」和「合同规定不能出」是两种约束，前者可以用脱敏、专属托管、审计权来解决，后者不能。**

**第三道，账，才是可以算的。** 它问的是总账，不是单价：单任务多少钱、固定成本多少、人力多少、闲置多少、将来迁走要多少。算完再问维护：谁值班、谁升级、谁回滚。维护这一轴最容易被漏掉，因为它不在报价单上。

### 四个里通常只能同时满足三个

过了三道闸之后，剩下的方案通常不会四个轴都满分。这时「三选二」是一个有用的粗略框架：**你放弃哪一轴，就换来另外三个。**

| 你放弃的轴 | 你换到的三个 | 典型形态 | 这个交换什么时候成立 |
| --- | --- | --- | --- |
| **成本** | 能力＋数据边界＋低维护 | 专属托管、私有云、专属实例 | 事故代价高，预算可谈；数据不能出，又不想自己值班 |
| **数据边界** | 能力＋成本＋低维护 | 闭源 API | 数据可出，合规允许；任务难，上线要快 |
| **低维护** | 能力＋成本＋数据边界 | 本地 / 私有部署 | 有运维、有合规要求；调用量大到固定成本能摊薄 |
| **能力** | 成本＋数据边界＋低维护 | 小模型、云托管小模型、规则＋模型 | 任务标准化，错误可人工兜底；不需要前沿能力 |

这张表不是定理，也不能反过来当广告用。它有两个重要例外。

**例外一：能力和规模都要求不高时，四个可以同时满足。** 一个每月只跑几次、任务简单、错误有人看一眼就能改的场景，用低价档的 API 就可能同时做到「够用、便宜、数据不出事、几乎不用维护」。这时「三选二」不咬人，因为能力门槛本来就很低。

**例外二：把「能力」推到前沿时，三选二才开始收费。** 你想要最新的能力、又要数据不出门、又要没人管、又要便宜——这四件事同时成立的难度，不是线性增加的，是互相拉扯的。**前沿能力是最贵的那一轴，它会把另外三轴的余量吃掉。**

所以「三选二」的正确用法不是拿来当结论，是拿来当**追问清单**：我放弃的那一轴，我是真的想清楚了，还是只是没看见它的账？

### 这一节最容易犯的错

| 错法 | 错在哪 | 改法 |
| --- | --- | --- |
| 先算钱，再守边界 | 把红线当成可以打折的账 | 先过数据闸，再算钱；边界不参与比价 |
| 先比模型，再看任务 | 拿别人的题当自己的题 | 先建自己的评测集，再谈能力 |
| 把「维护」当成「技术支持」 | 技术支持是对方接电话，维护是你半夜起来 | 问值班表、升级窗口、回滚演练 |
| 把「开源」当成一种形态 | 开源是权重许可，不是部署方式 | 分开问：权重在哪、机器在哪、谁维护 |

最后一行值得展开：**开源不是一种部署形态。** 同一个开放权重，可以跑在别人的云上（云托管开源），也可以跑在你的机房里（本地/私有）。两者的数据去向、成本结构、维护负担完全不同。把「开源」和「本地」当成同义词，是这一章后面所有误判的起点。

## 23.4 三种形态：权重在哪、桌子在哪、坏了谁修

先把三种形态摆开。这里说的是**形态**，不是品牌；同一家厂商可能同时提供几种形态，同一个开放权重也可以出现在三种形态里。

| 维度 | 闭源 API | 云托管开源 | 本地 / 私有部署 |
| --- | --- | --- | --- |
| **权重在哪** | 厂商的机器上，你看不到也拿不到 | 托管方的机器上，权重是开放的，但机器不是你的 | 你的机器上，权重由你保管 |
| **桌子在哪** | 厂商的入口与机器 | 托管方的入口与机器 | 你的入口与机器 |
| **能力上限由什么决定** | 厂商愿意卖给你的最新版 | 你能拿到的最好的开放权重＋托管方的工程 | 你能买到的机器能跑的权重与精度 |
| **成本结构** | 按量为主，固定成本低；量大可谈 | 按量或包实例；有固定容量成本，闲置也计费 | 资本支出＋人力＋电＋备件＋闲置；边际调用便宜 |
| **数据去向** | 到厂商；留存、训练、跨境看条款与开关 | 到托管方；权重开放不等于数据开放 | 在你的边界内；但日志、备份、遥测、更新包仍可能外流 |
| **运维负担** | 最低：调用、配额、错误处理 | 中低：选型、配额、版本、数据边界 | 最高：部署、升级、回滚、监控、容量、安全、值班 |
| **可改性** | 只能通过提示、检索、工具、微调接口（若开放） | 可换权重、可微调（若托管方支持） | 权重、推理栈、量化、微调都可改 |
| **升级节奏** | 对方定；旧版可能下线 | 你选版本；托管方可能停止支持旧版 | 你定；不升就自己承担过期与漏洞 |
| **典型失效** | 版本突变、限流、停服、数据条款不清 | 配额、区域、托管层加价、权重版本落后 | 容量不够、故障无人修、精度掉、更新断档 |
| **最适合** | 数据可出、要快上线、任务难 | 数据可出、量大、要可控成本与可换权重 | 数据不可出、有运维、调用量大或要深度改 |

这张表要横着读，不要竖着读。竖着读会变成「哪种形态最好」；横着读才会看见：**每一种形态都是在某一轴上让一步，换另外三轴的空间。**

### 同一份材料，三种走法

下面这张图只画数据经过谁，不画网络细节。它是**示意**，不是任何产品的架构图。

```text
（示意）同一份材料，三种形态下经过谁

闭源 API
  你（人）──材料──▶ 厂商入口（应用）──▶ 厂商机器（模型）
                       │
                       └──▶ 厂商日志 / 备份 / 风控（工具，你看不见）

云托管开源
  你（人）──材料──▶ 托管方入口（应用）──▶ 托管方机器（模型，跑开放权重）
                       │
                       └──▶ 托管方日志 / 备份 / 监控（机器不是你的）

本地 / 私有
  你（人）──材料──▶ 你的入口（应用）──▶ 你的机器（模型，跑你选的权重）
                       │
                       └──▶ 你的日志 / 备份 / 监控（也是你的活）
```

这张图要读出三件事。

**第一，三种形态里，模型都只在最后一跳出现。** 它读入、它续写，然后结束。它不知道材料从哪来，也不知道日志会被谁看。**「模型会不会泄露」这个问题，问错了对象；该问的是「这一圈系统里，谁能看见、谁能留存、谁能导出」。**

**第二，云托管开源和闭源 API 在数据路径上更像，不像本地。** 两者都是「材料进别人的机器」，差别在权重是否开放、版本是否可选、合同是否可谈。**「开源」不会自动把数据留在你家里。**

**第三，本地部署把「数据不出门」换成了「什么事都归你」。** 日志、备份、监控、更新包、故障、容量，全部从「对方的事」变成「你的事」。这不是一句「自己部署更安全」能概括的。

### 两组最容易被忽略的冲突

四轴之间最常发生的交换，其实只有两组。

**第一组：本地省下的是数据外流，接过来的是维护与能力上限。** 材料不用出门，代价是机器、电、机房、值班、升级、故障全归你；而且你能跑的能力上限，受你能买到的机器与可获得的权重限制。**它不是「免费的安全」，是「用运维换边界」。**

**第二组：开源省下的是许可限制与不可改，接过来的是质量兜底。** 权重可获取、可改、可换地方跑，代价是「谁来判断它够不够好、谁来调、坏了谁修」全部落到你这边。**它不是「免费的能力」，是「用工程能力换可改性」。**

这两组冲突，恰好对应会上那两句话没说完的部分。采购只看见了 API 的能力与省事，没看见数据与锁定；运维只看见了本地的边界与开源的可改，没看见维护与质量兜底。

### 五个必须拆开的等号

选型讨论里，有五个等号最容易被顺手划上。每一个都不成立。

**第一个：开源 ＝ 免费。** 授权费可能为零，但机器、电、机房、人力、备件、闲置不是零。一个开放权重跑在你机房里，单次调用的边际成本可能很低，可如果机器大部分时间在闲置，摊到每次任务上的固定成本可能高得离谱（→ [08](08-speed-and-cost.md) 的「闲置」）。**免费的是许可，不是运行。**

**第二个：开源 ＝ 能改。** 权重能下载，不等于训练数据、训练代码、许可条款都齐；能微调，不等于你有数据、有算力、有评测能力把它调好。**「可改」是一项工程能力，不是一个文件属性。**

**第三个：私有部署 ＝ 安全。** 私有部署只改「机器归谁」，不改「权限设计对不对」「日志谁能看」「更新包从哪来」「密钥怎么管」。一个没有权限分级的私有部署，和一个没有权限分级的云服务，一样会越权（→ [17](17-injection-and-permission.md)）。**「私有」是部署位置，不是安全证明。**

**第四个：云托管开源 ＝ 数据不出门。** 机器是托管方的，日志、备份、监控也在托管方。权重开放，只说明「你可以换一个地方跑」，不说明「这一跑的数据归你」。**要问的是合同、区域、日志与删除，不是许可证。**

**第五个：闭源 ＝ 不能私有。** 有些厂商提供专属部署、专属实例、私有云版本。但那是商务形态，不是默认能力；而且模型版本、更新节奏、计费口径仍可能由厂商控制。**「可以私有」和「已经私有」之间，隔着一次真正的部署与验证。**

这五个等号有一个共同的修法：**把形容词换成一个可核对的动词。** 不说「安全」，说「谁能读、留多久、怎么删」；不说「免费」，说「授权费多少、机器多少、人多少」；不说「能改」，说「谁改、用什么数据、改完谁评」。

### 一个常被忽略的中间态

三种形态之外，还有一个中间态：**专属托管**。机器在对方的机房里，但网络、账号、日志、密钥做了隔离，合同里写了数据处理与审计条款。

它值得单独提，因为很多「数据不能出」的场景，真正的约束不是「物理上不能离开我的机房」，而是「不能和别的租户混、不能被用于训练、不能跨境、要能审计」。这些条件，专属托管可能满足；而「私有部署」未必是唯一解。

反过来，专属托管也不是万能：它仍然是别人的机器、别人的升级节奏、别人的计费口径。**它买到的是「边界更清楚」，不是「什么都归你」。**

选型时，先把约束写成一句可核对的话：

> **数据不能离开**什么**边界**？是不能离开公司网络，不能离开某个国家/区域，不能离开某个租户，还是不能进入训练集？

这句话写不清，后面所有方案比较都是在猜。

## 23.5 量化：用精度换空间与速度，掉多少要看任务

量化不是「把模型压小一点」，是**用更少的位表示同一个数**。它是一次有损的近似，不是无损压缩。这个定义决定了它的全部取舍。

它换来三样东西：权重更小，能塞进更小的机器；每一步要搬的字节更少，出字可能更快（如果墙在带宽）；省出来的空间可以给更长的上下文或更多并发。它付出的代价也是三样：数值精度下降；不同任务对精度损失的敏感度不同；数值变了，旧提示词、旧结果、旧评测都可能漂移。

```text
（示意）量化的交换，不是单向加速

   更少的位 ──▶ 权重更小 ──▶ 塞进更小的机器
        │            └──▶ 每步搬得更少 ──▶ 出字可能更快
        └──▶ 数值近似 ──▶ 某些任务变差 ──▶ 旧提示词 / 旧结果漂移
```

机制细节见 [08](08-speed-and-cost.md)，这里只讲选型时的判断。

### 为什么「掉多少」不能看宣传

因为宣传给你的通常是一个平均印象，而选型需要的是**你的任务上的硬失败**。两者之间隔着三道坎。

**第一道，平均值会掩盖硬失败。** 一个量化版可以在大多数题上几乎不变，却把某一类金额、日期、编号算错。平均分看起来只掉了一点，但那一类错误一旦发生，就是不能交付。硬失败必须单列，不参与平均（→ [22](22-evaluation.md)）。

**第二道，退化不是均匀的。** 不同层、不同任务、不同输入长度对精度损失的敏感度不一样。一个总体百分比不能告诉你「哪一类先坏」。你可能在摘要上几乎看不出差别，在逐字引用上却开始错字；也可能在短问短答上正常，在长材料跨页对照时开始丢中间段。

**第三道，抽样会制造假差异。** 同一版跑两次，输出本来就可能不同（→ [04](04-sampling-and-reruns.md)）。量化版和原版各跑一次，看到「这版好一点」，很可能只是抽签。要判断量化是否伤了质量，至少要重跑，并且看**稳定出现的失败类型**，不是看一次谁更顺眼。

所以正确的问法不是「量化掉几个点」，是：

> **在我的评测集上，量化版的硬失败有没有变多？变多的是哪几类？重跑之后还在不在？**

### 哪类任务更敏感：一张方向表

下面这张表给的是**方向**，不是保证。你的任务可能反着来，所以它只能用来决定「先重点看哪几类题」，不能用来代替验收。

| 任务类型 | 对量化的敏感度 | 为什么 | 验收时先看什么 |
| --- | --- | --- | --- |
| 金额、日期、编号、逐位换算 | 高 | 一个数字错就是硬失败，且模型本来就不擅长逐位运算 | 逐字段回原文核对；硬失败单列 |
| 逐字引用、合同条款、代码标识符 | 高 | 一个字符错就可能改变含义 | 原文对照；不许「意思差不多」 |
| 严格格式、字段齐全、schema | 中高 | 格式压力下更容易「为了填满而编」 | 格式校验＋语义校验分开（→ [14](14-structured-output.md)） |
| 长文摘要、风格改写、起草 | 中低 | 局部措辞变化通常可接受 | 五类关键信息是否还在（→ [11](11-compression.md)） |
| 分类、抽取、路由 | 中 | 边界样例最敏感，平均准确率会骗人 | 分层样例；看混淆在哪两类之间 |
| 多轮工具调用、Agent | 高 | 早期小错会被后续步骤放大 | 端到端任务成功率＋回执核对（→ [15](15-agent-loop.md)） |
| 开放闲聊、头脑风暴 | 低 | 多样性反而有益，少量措辞变化不影响用途 | 人工抽检，不必逐字 |

这张表最容易被误读成「高敏感的任务不能用量化」。不是。它说的是：**高敏感任务要用更严的验收，而不是用更响的宣传。** 一个量化版如果在你的高敏感任务上硬失败没有增加，它就是可用的；一个原版如果在你的任务上本来就不稳，量化只会让它更不稳。

### 量化版的成本账，不能只算「便宜」

量化可能让一个原本跑不动的方案变得跑得动：更大的上下文、更多的并发、更小的机器。这些是真实的收益，但它们要进总账，不能只当成「免费加速」。

反过来，量化也可能带来三笔隐藏成本：

1. **重调提示词的成本。** 数值变了，旧提示词里那些「刚好能 work」的措辞可能失效（→ 23.6）。这部分是人的时间。
2. **重跑评测的成本。** 旧结果不能直接拿来比，必须用同一组题重跑，还要看硬失败。
3. **质量下降带来的返工。** 如果量化版在少数题上开始错，而你没有发现，返工的成本会远高于省下的机器钱。

所以量化适不适合，取决于三个条件同时成立：**你的墙确实在显存或带宽；量化版在你的评测集上硬失败没有增加；省下的钱大于重调与重跑的成本。** 缺一条，它就不是优化，是一次赌。

### 量化不是蒸馏，也不是剪枝

三个词经常被混着说，但它们的失败模式不同。

| 做法 | 改了什么 | 还是不是同一个模型 | 典型代价 |
| --- | --- | --- | --- |
| **量化** | 用更少的位表示同一组权重 | 结构不变，数值近似 | 精度损失；旧提示词与旧结果漂移 |
| **蒸馏** | 用一个大模型教一个小模型 | 换了模型，参数与结构都可能变 | 能力上限下降；学生可能学到教师的坏习惯 |
| **剪枝** | 去掉一部分权重或结构 | 结构变了 | 稀疏实现不一定提速；能力可能局部塌陷 |

选型时混淆这三者，会导致一个很常见的错误：**以为「量化版变小了，所以能力一定下降很多」**，或者反过来，**以为「换了个小模型，只要量化一下就能接近大模型」**。前者可能过度保守，后者一定过度乐观。

## 23.6 换模型会让提示词失效：评测集才是资产

这一节是全篇最该背走的部分。先给结论：

> **你调好的不是「提示词」，是「这个模型在这个任务上的补丁集合」。换一个模型，补丁可能全部失效，甚至变成新的干扰。评测集才是资产，提示词不是。**

为什么？因为一段能用的提示词里，混着至少七种东西，它们的「保质期」完全不同。

| 提示词里的成分 | 它实际在做什么 | 换模型后 | 能不能带走 |
| --- | --- | --- | --- |
| **任务目标与验收** | 说清要什么、什么算合格 | 通常稳定 | 能，而且应该带走 |
| **材料组织与来源** | 决定这一轮桌上放什么 | 大体稳定，但抽取/顺序可能要重验 | 能，但要重验 |
| **措辞偏好** | 利用旧模型对某些词的反应 | 可能完全变 | 难，要重调 |
| **格式模板** | 利用旧模型的格式偏置 | 可能被忽略或过度执行 | 难，要重测 |
| **示例** | 让旧模型照抄格式与风格 | 新模型可能连内容一起抄，或完全不理 | 难，要重选 |
| **负向指令** | 压制旧模型的某个坏习惯 | 新模型可能没这个习惯，负向指令反而把它引出来 | 难，要重写 |
| **针对旧模型失败的补丁** | 「它老把 42 当人数，所以加一句先去重」 | 大概率失效；新模型可能不犯这个错，也可能犯别的错 | 不该带走，该变成考题 |

最后一行是关键。**每一条「补丁」都应该变成一条评测用例，而不是一句咒语。** 这样换模型时，你带的不是一堆不知道为什么在那的话，而是一张能重考的题。

### 提示词为什么会贬值

提示词不是一次性写完就稳定的资产。它会因为五种变化而贬值：

1. **模型版本更新。** 措辞偏好、格式偏置、拒绝阈值、工具调用习惯都可能变。你昨天调好的「分三点」，今天可能被理解成「只许三点，不许解释」。
2. **供应商下线旧版。** 旧版一停，提示词直接作废，连对照都做不了。这是「断供」的一种，见第 24 篇。
3. **量化或托管实现变化。** 同一个权重，换一个精度档、换一个推理栈、换一个托管方，数值与行为都可能漂移。
4. **材料与业务变化。** 示例里的旧日期、旧口径、旧模板，会随着业务更新而过期。
5. **团队记忆流失。** 半年后没人记得某句话是为了修哪个 bug，于是谁也不敢删，提示词越堆越长，越堆越脆。

```text
（示意）换模型时，什么贬值、什么保值

提示词        ████████░░░░░░░░░░   随版本、下线、量化而贬值
格式约定      ██████░░░░░░░░░░░░   与模型/模板绑定
示例          █████░░░░░░░░░░░░░   会随业务过期
任务卡        ████████████████░░   目标、材料、边界、验收，跨模型可用
评测集        ██████████████████   每加一条失败案例，反而更值钱
```

这张图是**示意**，只表示方向，不表示任何精确比例。它要说的是：**提示词是一项会折旧的资产，评测集是一项会增值的资产。** 你把时间花在哪一边，决定了换模型那天你是从容还是崩溃。

### 为什么评测集能保值

因为评测集记录的不是「某个模型喜欢什么」，而是「你的任务什么样、什么算合格、什么绝对不能错」。这三件事不随供应商换。

具体说，评测集有五个作用，提示词一个都替代不了：

**第一，它把「能力」从「运气」里分出来。** 同一道题跑多次，看稳定通过率，而不是一次惊艳（→ [04](04-sampling-and-reruns.md)、[22](22-evaluation.md)）。提示词调得再顺，也不能证明它不是抽中的。

**第二，它记录你的真实分布。** 典型题、边界题、失败题，三类都要有。通用榜单不会包含「42 条记录去重成 39 人」「B 场地档期未确认」「v1 已作废」这些你的任务里真正会翻车的地方。

**第三，它能在换供应商时做同题对照。** 没有它，你只能听演示、看榜单、凭感觉；有它，你可以让两个候选跑同一组题，看硬失败与总账。

**第四，它能交接。** 新人、外包、审计看的应该是题和判据，不是一段只有原作者能解释的咒语。

**第五，它会增值。** 每出现一个新失败，加一条；每换一次模型，重跑一遍，题库就更贴近真实。提示词只会越堆越脆，评测集会越用越准。

### 一个类比，以及它在哪里失效

提示词像**给一把锁配的钥匙**：齿形对上了，门就开。评测集像**这扇门必须通过的验收清单**：不管换哪把锁，清单上的项目都要过。

这个类比在一步上失效：**钥匙是确定的，提示词不是。** 同一把钥匙开同一把锁，结果固定；同一段提示词跑同一个模型，输出仍然在抽样（→ [04](04-sampling-and-reruns.md)）。所以评测集不能像验收清单那样「过一遍就签字」，它必须允许重跑、记录波动、把硬失败单列。

失效带来的实际后果有两个：

1. **不能拿一次通过当「钥匙配好了」。** 要重跑，要看稳定通过率。
2. **不能拿「考过的题」当「全部题」。** 评测集只覆盖你见过的分布；没见过的题仍可能翻车。所以线上还要有抽样、监控与硬失败告警。

### 锁定的真实成本：四层，不止接口

换供应商的成本，通常不在「改一个地址」上。它在四层里，一层比一层难搬。

| 锁定层 | 长什么样 | 换走的代价 | 降低办法 |
| --- | --- | --- | --- |
| **接口** | 鉴权、错误码、限流、流式协议、SDK 习惯 | 改调用层、重测异常路径 | 用薄适配层；不把厂商特有字段写进业务 |
| **计费** | 计价单位、最低消费、出网/存储/支持费 | 以为省了单价，结果贵在周边 | 用总账比较；把预算模型做成可替换的 |
| **数据格式** | 聊天模板、工具调用格式、微调产物、索引格式、日志格式 | 重做数据管道；旧微调可能导不出来 | 原始数据存成供应商无关的格式；微调前先问能否导出 |
| **能力** | 调好的提示词、示例、缓存前缀、工作流 | 重调、重测、重训；旧结果不可比 | 用任务卡＋评测集；把补丁变成考题 |

这四层里，最容易被低估的是第四层。接口可以包一层，计费可以重算，数据格式可以转换；**但「调好的东西带不走」是没办法用工程手段完全解决的。** 你只能通过「把调优沉淀成评测集与任务卡」来降低损失，不能指望换模型后一切照旧。

还有一个不在表里、但很真实的锁定：**合同与流程。** 数据能不能导出、删除有没有证明、版本变更提不提前通知、停服给不给过渡期、有没有审计权——这些条款不写，技术上的「可迁移」就只是理论上的。

### 一张「带得走 / 带不走」的清单

| 带得走 | 难带走 |
| --- | --- |
| 任务卡（目标、材料、边界、交付、验收） | 调好的提示词与示例 |
| 评测集、判据、硬失败清单 | 厂商特有的工具调用格式 |
| 你的材料、索引、数据字典 | 缓存前缀与命中结构 |
| 数据结构与校验规则 | 托管方的微调产物（若不能导出） |
| 权限设计与回执流程 | 配额、价格、支持响应 |
| 失败分类与复盘记录 | 某个具体模型版本的行为 |
| 线上日志（若可导出） | 「它在我这表现很好」这句无法复现的印象 |

这张表可以直接拿去做选型评审的一页。**左边越长，你越不怕换；右边越长，你越被锁。** 而把右边转成左边的动作，几乎总是同一个：**把一次调优，变成一条可重跑的题。**

## 23.7 决策表：给定约束组合，选哪一档

下面这张表不是排名，是**条件句**。每一行都写清楚：在什么约束组合下推荐哪一档，以及**什么情况下这个推荐不成立**。最后一行尤其重要：不写「不推荐」的条件，推荐就会变成广告。

先过三道闸，再看表：

```text
（示意）从约束到候选，不是从模型到约束

  数据能不能出边界？
    ├─ 不能 ──▶ 能力够不够？
    │            ├─ 够 ──▶ 有运维？ ── 有 ──▶ 本地 / 私有
    │            │                  └─ 无 ──▶ 专属托管（合同＋隔离）
    │            └─ 不够 ─▶ 先改任务 / 脱敏 / 缩范围；不要硬上
    └─ 能 ────▶ 能力要求高？
                 ├─ 是 ──▶ 量小 / 要快上线 ──▶ 闭源 API
                 │          量大 / 要可控 ──▶ 云托管开源，或与 API 谈量
                 └─ 否 ──▶ 量小 ──▶ 低价档 API / 小模型
                            量大 ──▶ 云托管开源 / 本地（若固定成本能摊薄）
```

| # | 约束组合 | 推荐档 | 为什么 | 不推荐的条件（什么时候这条会错） |
| --- | --- | --- | --- | --- |
| 1 | 数据不可出＋能力要求高＋有运维＋预算可谈 | 本地 / 私有部署 | 边界最硬，能力靠你能买到的最好开放权重＋微调 | 评测集显示本地权重的硬失败不可接受；或没有真正常驻的运维；或调用量小到固定成本摊不薄 |
| 2 | 数据不可出＋能力要求高＋无运维＋预算可谈 | 专属托管 / 私有云 | 用合同与隔离换边界，用钱换掉值班 | 合同不能保证不训练、不跨境、可审计；或「不可出」其实是「不想混租户」，脱敏后可用 API |
| 3 | 数据可出＋能力要求高＋要快上线＋量小 | 闭源 API | 能力上限最高，固定成本最低，上线最快 | 单任务总账随量爆炸；供应商停服/改版风险不可接受；数据其实没有脱敏 |
| 4 | 数据可出＋能力要求中＋量大＋要可控成本 | 云托管开源 | 权重可换、成本可谈、比自建少运维 | 托管方的开放权重版本明显落后；你需要深度微调而托管方不支持；配额/区域成为新瓶颈 |
| 5 | 数据可出＋能力要求低＋量小＋无运维 | 低价档 API / 小模型 | 够用、便宜、几乎不用管 | 任务会随规模变复杂；错误代价高到不能靠人工兜底；低价档的限流影响体验 |
| 6 | 需要改权重/领域适配＋数据敏感＋有 ML 工程 | 本地/私有＋开放权重＋微调 | 权重、数据、评测都在自己手里 | 你其实只需要检索或提示词（→ [07](07-weights-vs-carried.md)）；数据量不足以微调；没有评测能力，调完不知道好坏 |
| 7 | 强监管/可审计＋数据敏感 | 私有部署＋日志/删除/版本控制 | 审计权、日志、删除证明都能自己掌握 | 你承担不了运维；或专属托管＋审计条款已能满足监管；或「审计」只是内部流程，不是法定要求 |
| 8 | 只是「想省钱」，其他约束都不紧 | 先不换形态，先做 [21](21-three-ledgers.md) 的四步 | 账单的大头通常在轮次、材料、重试，不在形态 | 账单结构已经干净，单价确实是主项；或现有形态有硬伤（停服、限流、数据条款） |

这张表有一个总顺序：**先看数据能不能出，再看能力够不够，再看有没有人维护，最后才比钱。** 顺序反了，就会用「便宜」去解释一个越界或不可维护的方案。

### 听到这些话，先追问什么

| 你听到的 | 它其实没回答 | 先追问 |
| --- | --- | --- |
| 「我们支持私有部署」 | 谁的机器、谁管日志、更新包从哪来、断网能不能跑 | 断网测试＋日志核对＋合同条款 |
| 「我们开源」 | 许可、商用、再分发、谁维护、微调产物能否导出 | 许可证原文＋值班表＋导出条款 |
| 「我们最便宜」 | 单价还是总账、闲置、退出成本、支持费 | 按 [21](21-three-ledgers.md) 列一次总账 |
| 「我们效果最好」 | 在谁的题上、硬失败多少、重跑稳不稳 | 用你的评测集跑同一组题（→ [22](22-evaluation.md)） |
| 「可以微调」 | 数据够不够、谁评、调完能不能带走 | 微调后的评测方案＋导出条款 |
| 「数据绝对安全」 | 谁能读、留多久、是否训练、能否删除 | 合同＋日志＋删除回执 |

这张表的作用不是让你不信任对方，是让你**把「能力声明」翻译成「可验收的动作」**。翻译不出来的，就先别签字。

### 一个反直觉的推荐：先别选

有些场景下，最好的选型结论是**暂时不选**。

- 你的任务还没有稳定的评测集，换什么都是在猜；
- 你的账单还没归因，换形态只会把浪费藏得更深；
- 你的数据边界还没写清，选本地可能是过度防御，选 API 可能是越界；
- 你的量太小，任何固定成本都摊不薄，先用按量档跑一段时间更诚实。

**「先别选」不是拖延，是把一个无法验证的决定，推迟到它能被验证的时候。** 这比签一个听起来很先进的方案，然后花半年擦屁股要便宜。

## 23.8 边界：能做什么、代价是什么、何时失效

这张三列账是本篇能拿去做决定的部分。每一行都是一个动作，不是一个名词。

| 动作 | 能做什么 | 代价是什么 | 何时失效 |
| --- | --- | --- | --- |
| **选闭源 API** | 最快拿到较强能力；固定成本低；不用管机器 | 数据出边界；版本与价格由对方定；长上下文/工具返回会放大总账 | 数据不可出；供应商停服/改版；量大到单价成为主项 |
| **选云托管开源** | 权重可换、成本可谈、运维比自建轻 | 机器仍是别人的；日志/备份/配额/区域受制于人；开放权重版本可能落后 | 数据不可出；托管方不支持你需要的微调；区域/合规不满足 |
| **选本地/私有部署** | 数据边界最硬；权重与推理栈可改；边际调用便宜 | 机器、电、机房、人力、备件、闲置；升级与故障全归你 | 没有运维；调用量小到固定成本摊不薄；能力门槛过不了 |
| **用专属托管换边界** | 不共享租户、可审计、可写数据处理条款；比自建少值班 | 仍是别人的机器与升级节奏；合同谈判成本高；价格通常高于公有档 | 「不可出」其实是物理隔离要求；合同拿不到审计权；预算撑不住 |
| **量化换显存/速度** | 跑得动更大的上下文/更多并发；出字可能更快 | 精度损失；旧提示词/旧结果漂移；要重跑评测 | 墙不在显存/带宽；任务对精度极敏感；没有评测能力 |
| **微调换领域适配** | 把领域格式、口径、风格固化进权重 | 数据、算力、评测、维护；会过期；可能过拟合 | 规则三个月一变；数据量不足；问题其实在检索或材料（→ [07](07-weights-vs-carried.md)） |
| **多供应商/薄适配层** | 降低接口锁定；可做同题对照；停服时有退路 | 多一套抽象与测试；两边的差异要抹平；成本不一定更低 | 差异在深层行为（工具调用、格式、拒绝策略）；适配层薄到挡不住 |
| **自建评测集** | 把能力变成可复核的数；换模型时有底；能交接 | 出题、标注、重跑都要人；题会过期；可能过拟合自己的题 | 题不代表线上分布；没有硬失败单列；只跑一次就下结论 |
| **继续用现方案（不换）** | 省掉迁移与重测；保留现有调优 | 可能错过更便宜的档；旧版本的停服/漏洞/能力落后 | 现有方案有硬伤（数据条款、停服、限流）；账单结构已明显浪费 |

这张表有一个总顺序：**先确认硬约束，再选形态，再谈量化/微调/适配层，最后才比价。** 每一行做完，都要用同一组材料复核「硬失败有没有增加、数据去向有没有变」。

### 这个类比在这里失效

「快、好、省，三选二」是选型讨论里最顺手的类比。它在这一步失效：**数据边界不是第三本账，是红线。**

三本账可以互相兑换，是因为它们都是「代价」：多花时间换质量，多花钱换速度。但数据边界一旦是硬约束，它和另外两者之间的「兑换率」不是很大的数，是**不能换**。你不能说「多给一点钱，就可以让名单多外流一次」；也不能说「模型更强，所以数据出界可以接受」。**把红线放进三角里等权交换，这个三角就已经错了。**

第二个失效点：这个三角里没有「维护」这一边。而维护恰恰是本地方案最容易被低估的成本——它不在报价单上，也不在演示里，只在半年后的某个半夜出现。

失效带来的两个实际后果：

1. **不要用「综合评分」选型。** 评分表会把红线稀释成小数，把维护折成一句「技术支持」。
2. **不要把「便宜」当成「可行」。** 一个越界或没人维护的方案，单价再低也不是可行解；它只是把成本推迟到了事故那天。

## 23.9 检验：三个真实任务，两个方案，十分钟

这个检验不需要代码，也不需要采购流程。你只需要三个你真实做过的任务、两个候选方案，以及一张记录表。

**准备**：

- 三个任务，覆盖三种形状：一个**标准任务**（你经常做、答案比较确定）、一个**边界任务**（材料里有旧版/未定项/口径陷阱）、一个**长材料任务**（需要跨段对照）。
- 两个方案。最好一个是你现在用的，另一个是你正在考虑的；如果两个都是 API，也可以，但结论只能回答「这两档谁更合适」，不能回答「本地行不行」。
- 同一批输入、同一套判据、同一段时间。**不要一个方案用整理过的干净材料，另一个用原始材料**——那是换题，不是换方案（→ [22](22-evaluation.md)）。

**记录表**（空格填你自己的观察；本文不给任何示例数值）：

| 任务 | 方案 | 硬失败（有/无，哪类） | 稳定通过（几次/几次） | 单次成本（估） | 首字时间 | 数据去向（谁经手/留哪） | 维护动作 | 结论 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 标准 | A |  |  |  |  |  |  |  |
| 标准 | B |  |  |  |  |  |  |  |
| 边界 | A |  |  |  |  |  |  |  |
| 边界 | B |  |  |  |  |  |  |  |
| 长材料 | A |  |  |  |  |  |  |  |
| 长材料 | B |  |  |  |  |  |  |  |

**怎么读结果**：

| 你看到的 | 说明什么 | 下一步 |
| --- | --- | --- |
| 本地/开源方案三个任务全过，硬失败为零 | 能力门槛不是墙；可以认真算总账 | 再算固定成本、人力、闲置；别急着庆祝 |
| 本地/开源在边界任务上有硬失败，API 没有 | 能力门槛没过；不是「再调调提示词」能救 | 缩任务范围、改流程，或回到 API/专属托管 |
| API 全过，数据可出，成本可接受 | API 是可行解 | 再问锁定：版本、停服、数据条款 |
| API 全过，但数据不可出 | 不能选 API；这不是价格问题 | 转专属托管/私有；或证明脱敏后可用 |
| 两个方案都过，成本接近 | 看维护与退出成本 | 谁值班、谁升级、迁走要多久 |
| 两个方案都不过 | 问题可能在任务设计，不在形态 | 改材料、改验收、拆任务；别换模型 |
| 一次差异很小 | 可能只是抽样 | 重跑；一次不算证据（→ [04](04-sampling-and-reruns.md)） |
| 便宜但返工多 | 省在了前面，赔在了后面 | 把返工与人工时间算进总账 |

**这个检验能推翻本文的三种情形**：

1. **你的「数据不可出」其实不是硬约束。** 如果脱敏、摘要、只传字段之后，任务仍然能过，那么「只能本地」这个结论就是错的；你真正需要的是一条脱敏与最小化上桌的流程（→ [11](11-compression.md)）。
2. **你的本地/开源方案在三个任务上都没有硬失败。** 那么「能力上限不够」这个假设在你的任务上不成立；此时该认真算的是维护与固定成本，不是继续找更强的模型。
3. **你的量小到固定成本永远摊不薄。** 那么「本地更便宜」是错的；本地的便宜是边际便宜，不是总量便宜。

**判据**：做完之后，你应该能说出三句话——**哪一轴是硬约束、哪一轴是当前瓶颈、换形态能解决哪一件、不能解决哪一件。** 说不出来，说明你还在用「哪个更强」代替「哪个可行」。

## 23.10 术语考古：三个被当成「形态」的词

这三个词的共同点是：**听起来像在描述一种东西，实际混着许可、部署、数值三种不同的事。** 不拆开，选型就会把「开源」当「本地」，把「私有」当「安全」，把「量化」当「免费压缩」。

| 词 | 最早出处 | 原义 | 现在被怎么用 | 本文怎么用 |
| --- | --- | --- | --- | --- |
| **开源模型** | 「开源」借自软件领域的开放源代码实践；模型领域更准确的说法是「开放权重」。**没有单一出处，各家的模型许可条款不同；社区用语。** | 软件语境：源代码可获取、可修改、可再分发。模型语境：权重可下载。 | 常被当成「免费」「可商用」「可自部署」「有人维护」的同义词；这四件事都不自动成立。 | 只指「权重可获取」。是否可商用、可改、可再分发、有谁维护，要逐条看许可与事实。**不把「开源」当「免费」。** |
| **私有部署** | 企业软件与云计算语境，与「公有云」相对；**社区用语，没有统一规范定义。** | 把系统部署在自己控制的环境里（机房、专有云、隔离网络）。 | 常被当成「数据不出门」「安全」「合规」的同义词；也被用来指「专属实例」。 | 只指「运行环境归你控制」。数据是否真的不出门，要看日志、备份、遥测、更新通道、密钥；安全与合规要另外证明。 |
| **量化** | 源自数值计算与信号处理：把连续取值映射到有限档位；模型部署借用。**不是模型领域的原创概念。** | 一种有损的数值近似：用更少的位表示同一个数。 | 常与「压缩」「蒸馏」「剪枝」混用；被当成「免费加速」或「一定变笨」。 | 同一个模型用更少位表示；有损；换空间与带宽；质量要在自己的评测集上验。**不等于蒸馏，也不等于剪枝。** |

三个词放在一起，误读路径是同一条：**把「一个条件」当成「一个结论」。** 开源是「权重可获取」这个条件，不是「免费且有人管」这个结论；私有部署是「机器归你」这个条件，不是「数据绝对安全」这个结论；量化是「用更少位表示」这个条件，不是「免费提速」这个结论。

还有一条纪律值得单独写：**任何关于形态的说法，都要能回答「谁的机器、谁的日志、谁的值班表」。** 答不上来，它就还停在形容词阶段。

## 23.11 一页速记

| 你遇到的情况 | 先问什么 | 该动哪里 |
| --- | --- | --- |
| 「能本地跑，所以选本地」 | 本地解决了哪一轴？另外三轴呢？ | 先过能力闸，再算维护账 |
| 「开源不要钱」 | 机器、电、人、闲置，哪一项是零？ | 列总账，不列授权费 |
| 「支持私有部署」 | 谁的机器、谁管日志、更新包从哪来？ | 断网测试＋合同＋日志核对 |
| 「云端也能私有」 | 是专属实例，还是共享池？ | 问隔离、审计权、数据处理条款 |
| 「量化版更小更快」 | 我的任务上硬失败有没有变多？ | 同一评测集重跑，硬失败单列 |
| 「换个模型，改几句提示词就行」 | 提示词里有多少是针对旧模型的补丁？ | 用评测集重跑，补丁变考题 |
| 「这家最便宜」 | 单价还是总账？迁走要多少？ | 算固定成本、人力、退出成本 |
| 「榜单第一」 | 在我的题上硬失败多少？ | 跑自己的三个任务 |
| 「先别选，等有定论」 | 现在的方案能不能过闸？ | 能过就先交付；不能过就改任务范围 |

**五句话带走**

1. 选型不是选最强，是在能力、成本、数据边界、维护四个约束里找可行解；四个里通常只能同时满足三个。
2. 顺序不能反：能力是门槛，数据边界是红线，成本与维护才是账。
3. 三种形态的差别，本质是权重在哪、桌子在哪、坏了谁修；开源不是一种形态，私有不是安全证明。
4. 量化是精度换空间与带宽，掉多少看任务；换模型会让提示词失效，**评测集才是资产，提示词不是**。
5. 锁定的真实成本在接口、计费、数据格式和「调好的东西带不走」；能带走的只有任务卡、评测集与判据。

**最后一句**：这一篇不要求你记住任何厂商的名字，也不要求你判断哪种形态「更先进」。它要求你在听到「我们能本地跑」「我们开源」「我们最便宜」的时候，先做一个动作——**把这句话翻译成「谁的机器、谁的日志、谁的值班表、在我的题上硬失败多少」。** 翻译得出来，你才是在选型；翻译不出来，你只是在选一个听起来更安心的说法。

**三道自检**

1. 同事说：「我们选开源的，因为不要钱，而且数据不出门。」这句话至少混了哪三件事？
2. 「本地部署的模型在通用榜单上分数不低，所以能力够用。」这句话缺了什么？
3. 「我们把提示词调得很顺，换模型后照着改几个词就行。」错在哪？

<details>
<summary>查看参考答案</summary>

1. 至少混了三件。第一，**开源≠免费**：授权费可能为零，但机器、电、机房、人力、备件、闲置都不是零；本地的便宜是边际便宜，不是总量便宜。第二，**开源≠数据不出门**：开放的是权重，不是数据路径；如果跑在别人的云上，日志、备份、监控仍在对方；就算跑在自己机房，遥测、更新包、备份也可能外流。第三，**开源≠有人维护**：社区活跃不等于你的值班表，升级、回滚、容量、安全补丁都要有人接。还要补一句：开源也不自动等于可商用、可再分发，许可要逐条看。

2. 缺的是「你的任务」这一层。通用榜单不是你的分布，它不包含「42 条记录去重成 39 人」「B 场地档期未确认」「v1 已作废」这些真正会翻车的地方；它也不告诉你硬失败率、重跑稳定性、量化后的表现、长材料跨页对照的表现。正确做法是用自己的评测集跑三类题（标准、边界、长材料），硬失败单列，重跑看稳定通过率；榜单只能用来筛候选，不能用来签字。

3. 错在把提示词当成了一段「通用说明」。一段能用的提示词里混着任务目标、材料组织、措辞偏好、格式模板、示例、负向指令，以及针对旧模型特定失败的补丁；换模型后，任务目标和材料组织大体能留，其余大部分会失效，有些还会反噬（例如旧模型没有的坏习惯，被负向指令引出来）。正确做法不是「改几个词」，而是用评测集重跑，把每一条补丁升级成一条考题；这也是为什么**评测集才是资产，提示词不是**。

</details>
