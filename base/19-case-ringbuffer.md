## 19.1 引子：一个「无锁队列」上线后 P99 反而变差

**假设场景**：网关将任务队列替换成 SPSC 环后，微基准吞吐上升，但服务尾延迟变差。下表列出三种可能解释，不是经核实的线上事故。

复盘发现三件事，按发现顺序：

| # | 现象 | 当时的解释 | 真正的原因 |
| --- | --- | --- | --- |
| 1 | 无锁版单线程压测快 4 倍，双线程只快 1.3 倍 | 「无锁不适合多核」 | 两个游标落在**同一条 cache line** 上，每次发布都在两核之间来回搬这一行 |
| 2 | 加了一个 `char pad[64]` 字段后快了一倍 | 「玄学」 | 缓存行的物理尺寸是 64 B，padding 把两个写者分到了不同的行 |
| 3 | 在 ARM 机器上偶发读到「半条消息」 | 「x86 上明明没问题」 | x86 是 TSO，release store 编译成普通 `mov`；ARM 需要 `stlr`，不写屏障就会真的重排 |

三件事指向同一个物理事实，而它不在代码里：

> **多核之间没有「共享变量」，只有「同一条 cache line 的多份副本」，以及一套让它们看起来一致的协议。**

本篇就把这句话拆成可执行的实验。

## 19.2 ① 它是什么：一个数组 + 两个单调递增的游标

RingBuffer（环形缓冲）不是「队列库」，而是**用取模把无限增长的序号映射到有限数组**的一个技巧：

```
   写入位置 head ↓                    ↓ tail 读取位置
   ┌────┬────┬────┬────┬────┬────┬────┬────┐
   │ 8  │ 9  │ 10 │ 11 │    │    │    │    │   容量 8
   └────┴────┴────┴────┴────┴────┴────┴────┘
     ↑ 已写未读（4 个）        ↑ 空闲（4 个）
   head = 12, tail = 8         真实下标 = 序号 & (容量-1)
```

三个设计决定，每一个都有物理理由：

| 决定 | 理由 |
| --- | --- |
| 容量取 2 的幂 | 取模退化成 `& (CAP-1)`，一条 `and` 指令；否则是除法（20–40 cycle） |
| `head`/`tail` 用 `uint64` 单调递增，不取模 | 用 `head - tail` 直接得到「已有多少」，天然区分「满」与「空」；回绕要 2⁶⁴ 次，等于不会发生 |
| 两个游标分开存放 | 见 §19.3——它们会被不同的核写 |

它的承诺只有一条：**单生产者单消费者（SPSC）时，不需要任何锁**。注意这个前提，后面 §19.7 会说它一旦破了会发生什么。

## 19.3 ② 物理形态：8 字节的变量，64 字节的所有权

`base/13` 已经给出：缓存行 64 B，MESI 以**行**为单位转移所有权。把这两个游标放进结构体，它们的物理位置就决定了通信成本。

### 布局一：游标相邻（默认写法）

```c
typedef struct {
    uint64_t head;        /* 偏移 0  */
    uint64_t tail;        /* 偏移 8  ← 和 head 同一条 cache line */
    uint64_t buf[CAP];
} near_t;

/* 实测：sizeof = 131088，head→tail 偏移 = 8 B */
```

```
   cache line 0（64 B）
   ┌────────┬────────┬───────────────────────────────────────────┐
   │ head   │ tail   │ 其它字段 / buf 的前 48 字节                │
   └────────┴────────┴───────────────────────────────────────────┘
     ↑ 生产者写        ↑ 消费者写
     同一条行 → 每次发布都要把整行从另一个核手里抢过来
```

### 布局二：游标各占一行

```c
typedef struct {
    uint64_t head; char p0[56];   /* 头独占 64 B */
    uint64_t tail; char p1[56];   /* 尾独占 64 B */
    uint64_t buf[CAP];
} pad_t;

/* 实测：sizeof = 131200，head→tail 偏移 = 64 B */
```

```
   line 0                          line 1
   ┌────────┬──────────────┐       ┌────────┬──────────────┐
   │ head   │ padding 56 B │       │ tail   │ padding 56 B │
   └────────┴──────────────┘       └────────┴──────────────┘
     只被生产者写                      只被消费者写
```

**代价是明码标价的**：为了把两个 8 字节变量分开，多花了 112 字节（`sizeof` 从 131088 涨到 131200，+0.09%）。**用 112 字节换掉一条 cache line 的跨核乒乓。**

### 为什么是 56 而不是 64

`head` 本身占 8 B，所以补 56 B 就凑满 64 B。写成 `char pad[64]` 也能工作（多浪费 8 B，且下一个字段会被推到第三行），但「补齐到行边界」这个意图不如 `64 - sizeof(head)` 清楚。工程上更稳的写法是用 `alignas(64)` 或 `__attribute__((aligned(64)))`，让编译器替你算。

## 19.4 ③ 走一遍：一次 publish 到底发生了什么

以 SPSC 的入队为例：

```
生产者                                          消费者
  │                                               │
  ├─ 1. 读 tail（自己的缓存里有副本，或从总线拿）      │
   ├─ 2. 已用 = head - tail；空闲 = CAP - 已用      │
  ├─ 3. 若满，自旋等待 ←───────────────────────────┤ 4. 读数据、更新 tail
  ├─ 4. 写 buf[head & mask]                        │
  ├─ 5. head++ 并「发布」（release store）          │
  │        └─────────── cache line 转移 ──────────→│
  │                                               ├─ 6. 看到新 head
  │                                               ├─ 7. 读 buf、更新 tail
  └───────────────── cache line 转移 ─────────────┘
```

每一跳的成本：

| 步骤 | 物理动作 | 量级 |
| --- | --- | --- |
| 读 `tail` | L1 命中，或行在别的核 → 一次 cache-to-cache 传输 | ~1 ns / ~20–60 ns |
| 写 `buf[i]` | 只碰自己独占的行，无通信 | ~1 ns |
| 发布 `head` | 若与 `tail` 同行 → 抢整行；若分行 → 只是本核 dirty | 20–100 ns / 0 |
| 消费者观察到 `head` | 轮询读（可能命中也可能 miss） | 1–60 ns |

**结论**：入队的计算量是几次加法，真正的成本全在第 3 步和第 6 步的**行转移**上。所以「优化 RingBuffer」= 「减少行转移次数」，而不是「减少指令数」。

## 19.5 ④ 改一行：三组实验，六个数字

本机：2 vCPU（AMD EPYC 7K62，KVM），gcc 12.2，`-O2 -pthread`。固定消息数 2000 万条，单生产者单消费者，容量 16384。跑一次 `timeout 90` 内完成。

### 实验 A：有锁 vs 无锁

```c
/* 有锁版本：一把互斥量保护整个环，满/空时自旋 */
for (uint64_t i = 0; i < N; i++) {
    for (;;) {
        pthread_mutex_lock(&mu);
        if (lt - lh < CAP) { L[lt & (CAP-1)] = i; lt++; pthread_mutex_unlock(&mu); break; }
        pthread_mutex_unlock(&mu);           /* 满了，让出再抢 */
    }
}
```

```
lock        15.807 s  ->   1.27 Mmsg/s  (consumed 20000000)
spsc near    3.677 s  ->   5.44 Mmsg/s  (consumed 20000000)
spsc pad     2.094 s  ->   9.55 Mmsg/s  (consumed 20000000)
```

### 实验 B：游标相邻 vs 各占一行（只改布局，不改逻辑）

```
spsc near    5.44 Mmsg/s     head→tail 偏移 = 8 B
spsc pad     9.55 Mmsg/s     head→tail 偏移 = 64 B
提升: pad/near = 1.76x
```

**同一份逻辑，只把两个游标挪开 56 字节，快 76%。** 这不是「代码写得好」，是「少搬了一条 cache line」。

### 实验 C：发布点没有额外 `mfence`，原子语义仍在

这是本篇最反直觉的一条。写下 `__atomic_store_n(&h, v, __ATOMIC_RELEASE)`，在 x86-64 上编译出来是：

```asm
publish:
        mov     QWORD PTR h[rip], rdi      ← 就一条普通的 mov，没有 mfence
        ret
```

而 `__ATOMIC_SEQ_CST` 才是：

```asm
publish_sc:
        xchg    rdi, QWORD PTR h[rip]      ← 隐式 lock，约 20–40 cycle
        ret
```

三条推论：

1. 这次编译的 release store 没有额外的硬件围栏指令；该存储本身仍会占用资源，还可能参与一致性通信。
2. C 的 release/acquire 约束编译器，并在配对观察时建立线程间同步。换成普通变量或只有 `volatile` 的变量，可能形成数据竞争，不能用 x86 TSO 替代码证明正确。
3. AArch64 的常见实现会选择 release/acquire 指令，例如 `stlr`/`ldar`；具体输出看编译目标与原子宽度。本节没有在 ARM 上运行。

**这是本篇最值得带走的一条**：**在 x86 上验证过的并发代码，不能证明它在弱内存序机器上正确。** 判据是看汇编，不是看测试是否通过。

### 实验 D：批量发布——把「每消息一次通信」降到「每 K 条一次」

前面三组实验都在**逐条**同步：每入队一条，就要发布一次 `head`。这意味着每条消息都要付一次跨核行转移。既然成本在通信次数，那就直接减少次数——**一次写入 K 条，只发布一次 `head`**。

```c
/* 生产者：批量写，一次发布 */
while (h < N) {
    uint64_t k = (N - h < K) ? (N - h) : K;
    while (h - __atomic_load_n(&R.tail, __ATOMIC_ACQUIRE) + k > CAP) ;  /* 等空间 */
    for (uint64_t j = 0; j < k; j++) R.buf[(h + j) & (CAP-1)] = h + j;
    h += k;
    __atomic_store_n(&R.head, h, __ATOMIC_RELEASE);   /* 只发布一次 */
}
/* 消费者：读到哪，就把 tail 写回到哪（这一步漏了会死锁，见下文） */
while (t < N) {
    uint64_t h = __atomic_load_n(&R.head, __ATOMIC_ACQUIRE);
    while (t < h) { (void)R.buf[t & (CAP-1)]; t++; }
    __atomic_store_n(&R.tail, t, __ATOMIC_RELEASE);
}
```

容量 65536、每档推进 500 万个游标位置。下列是多轮运行中收集到的各档最高观测，**不是同一轮输出**：

```
CAP=65536  N=5000000
K=1       1.830 s ->   2.73 Mmsg/s
K=8       0.464 s ->  10.77 Mmsg/s
K=64      0.364 s ->  13.74 Mmsg/s
K=512     0.104 s ->  47.97 Mmsg/s
```

| K（每次发布的消息数） | 最好成绩（Mmsg/s） | 相对 K=1 |
| --- | --- | --- |
| 1 | 2.73 | 1.00× |
| 8 | 10.77 | 3.94× |
| 64 | 13.74 | 5.03× |
| 512 | 47.97 | 17.6× |

**必须诚实说明噪声**：这台机器是 2 vCPU 共享 KVM，同一档 K=512 三次跑出 6.16 / 12.84 / 47.97 Mmsg/s，**相差近 8 倍**。所以：

- 各轮并没有一致的单调排序，不能宣称批量越大越快；
- 示例用 `(void)` 丢弃负载，编译器可省去消费者读取，因此这些数更接近**游标推进速度**，不能解释成经过端到端验证的有效吞吐；
- 想拿到干净数字，需要独占核 + `taskset` 绑核 + 关闭其他负载，本机做不到。

### 进度发布故障：消费者遗漏 `tail` 更新

第一版实验 D 写完后 `timeout` 直接超时。原因不是机器慢，是代码错：

```c
/* 错误版本：消费者只读，从不写回 tail */
static void* cons(void*_) {
    uint64_t t = 0;
    while (t < N) {
        uint64_t h = __atomic_load_n(&R.head, __ATOMIC_ACQUIRE);
        while (t < h) { (void)R.buf[t & (CAP-1)]; t++; }
        /* ← 少了这一行：__atomic_store_n(&R.tail, t, __ATOMIC_RELEASE); */
    }
    return NULL;
}
```

后果：生产者看到 `tail` 永远是 0，写满一圈（65536 条）后就在 `while (h - tail + k > CAP);` 上永久自旋。**这是 RingBuffer 最经典的 bug**，而且它的症状极具误导性：

| 症状 | 容易得出的错误结论 | 真实原因 |
| --- | --- | --- |
| 程序卡死、CPU 100% | 「自旋锁/内存序有问题」 | 消费者忘了发布自己的进度 |
| `timeout` 后无输出 | 「机器太慢」 | 生产者在等一个永远不会变的数 |
| 单条 K=1 能跑，批量 K=64 卡住 | 「批量逻辑有 bug」 | 两者都会卡，只是 K=1 卡得更早（更早写满一圈） |

**这一条比任何理论都值得记**：无锁结构的调试成本不在「想不出原理」，而在「一个漏写的 store 会伪装成性能问题」。判据是**看两个游标的单调性**——如果 `tail` 长时间不变而 `head` 在涨，就是消费者没发布。

### 四个数字放在一起

| 版本 | 吞吐（Mmsg/s） | 相对基线 | 改动量 |
| --- | --- | --- | --- |
| 有锁 + 相邻游标 | 1.27 | 1.00× | 基线 |
| 无锁 + 相邻游标 | 5.44 | 4.30× | 去掉锁，加 release/acquire |
| 无锁 + 游标分行 | 9.55 | 7.52× | 加 112 字节 padding |
| 无锁 + 分行 + 批量 K=512 | 47.97 | 37.8× | 每 512 条发布一次 |

**注意**：绝对吞吐很低（百万到千万级），因为这是**单条/小批量入队**、只有 2 个核、且每轮都在跨核同步。它测的是**每次跨核通信的单价**，不是工程上限。真要做到更高，还要叠加无锁内存池、NUMA 亲和、避免 false sharing 的批量消费等——那些是 `base/13`、`base/25` 的事。

> 本机比例也不能外推；批量与逐条实验还用了不同的容量和迭代次数，表里跨实验的相对值不适合解释单变量的收益。生产验收应先检查所有消息内容，再分开测布局和批量，每组报告全部样本或分布。

## 19.6 容量怎么定：从「延迟预算」倒推，而不是拍一个数

环容量是最常被随手定的参数，但它有明确算法。**容量 = 生产速率 × 允许的最大积压时间**，再加上一点余量。

```
容量 ≥ 生产速率 R（条/秒） × 消费者最长停顿 T（秒）
```

三个真实场景的推算：

| 场景 | 生产速率 | 消费者最长停顿 | 最小容量 | 取 2 的幂 | 内存（8 B/条） |
| --- | --- | --- | --- | --- | --- |
| 音频采集 | 48 kHz | 10 ms（一次 GC） | 480 | 512 | 4 KB |
| 网关日志 | 200 万/秒 | 50 ms | 100,000 | 131072 | 1 MB |
| 行情快照 | 50 万/秒 | 500 ms（磁盘抖动） | 250,000 | 262144 | 2 MB |

**两个反直觉的推论**：

1. **容量不是越大越好**。容量翻倍，数组就多占一份内存，且更难驻留 L2/L3——`base/07` 说过，工作集跨过一层缓存，延迟就上一个台阶。131072 × 8 B = 1 MB，已经超出多数机器的 L2（512 KB–1 MB），意味着每次访问都可能打到 L3。**这就是为什么「环里放指针」比「环里放大结构体」重要**：元素从 4 KB 降到 8 B，工作集缩小 512 倍。
2. **停顿时间才是决定项**，不是平均速率。消费者偶发 500 ms 停顿时，容量必须按 500 ms 算，而不是按平均延迟算。如果 500 ms 的停顿无法避免，**就该考虑丢弃策略**（覆盖最旧 / 拒绝新数据）而不是无限加大环。

这也解释了为什么 `io_uring` 的 SQ/CQ 环默认只有几百到几千项（`base/31`）：它优化的是「批处理吞吐」，不是「吸收长停顿」。

## 19.7 怎么验证它真的对：三种手段，成本递增

无锁代码的正确性不能靠「跑起来没崩」。三种验证手段，从便宜到昂贵：

| 手段 | 能抓到什么 | 抓不到什么 | 成本 |
| --- | --- | --- | --- |
| **不变量断言**（debug 版） | `tail ≤ head ≤ tail + CAP`、序号严格递增、无重复 | 只在断言执行的那一瞬间成立 | 极低，加 `#ifdef DEBUG` |
| **数据校验**（每条带序号/校验和） | 读到旧数据、半条数据、乱序 | 概率性，可能漏 | 低，生产环境可保留抽样 |
| **ThreadSanitizer / 形式化** | 数据竞争、缺失的 happens-before | 「缺屏障但无竞争」的弱内存序问题 | 中高，TSan 会慢 5–15× |

**不变量断言的具体写法**（这是最划算的一条）：

```c
#ifdef DEBUG
static void check_inv(const pad_t *r) {
    uint64_t h = __atomic_load_n(&r->head, __ATOMIC_ACQUIRE);
    uint64_t t = __atomic_load_n(&r->tail, __ATOMIC_ACQUIRE);
    assert(t <= h);              /* 消费不能超过生产 */
    assert(h - t <= CAP);        /* 不能写满一圈 */
}
#endif
```

上述双读只适合静止时检查：并发中先读 `head` 再读 `tail` 可能看到不同时刻的状态。满环时 `head - tail == CAP` 是合法状态，断言不会抓住进度停滞。要检测后者，用有限时长的测试逐条核对序号与内容；若超时，报告当时的两个游标和操作计数。无符号游标跨回绕时用模减法，不能直接把普通的 `t <= h` 当成恒真条件。

TSan 检查语言层的数据竞争，和是否出现 `mfence` 不是一回事；它也不能替所有弱内存序性质作证明。正确性先从 happens-before 论证，再通过工具、跨平台测试与代码审查辅助验证。

## 19.8 ⑤ 它证伪了谁

| 流行说法 | 实测结论 | 为什么 |
| --- | --- | --- |
| 「无锁一定比有锁快」 | 只快 4.3×，且**在多生产者场景会退化** | 无锁的优势是「没有睡眠/唤醒」，不是「没有通信」；CAS 竞争激烈时重试成本可能高过互斥量 |
| 「padding 是玄学 / 微优化」 | 112 字节换来 1.76× | 它对齐的是 64 B 这个物理常数，不是「感觉」 |
| 「`volatile` 能保证顺序」 | 不能 | `volatile` 只阻止编译器优化掉访问，不阻止 CPU 重排，也不产生屏障 |
| 「我在 x86 上测过，没问题」 | 不能证明正确 | release store 在 x86 上就是 `mov`；测试通过 ≠ 有屏障 |
| 「RingBuffer 就是环形数组」 | 环是数据结构，**行对齐才是性能** | 同一个算法，两种布局差 1.76× |
| 「卡死是内存序问题」 | 本机实测的卡死是**消费者忘了发布 `tail`** | 一个漏写的 store 会伪装成性能问题；判据看两个游标的单调性 |

---

## 19.9 边界：什么时候不该用它

RingBuffer 的承诺很窄，破了就会以「偶发丢数据/卡死」的形式收账：

| 场景 | 会发生什么 | 该用什么 |
| --- | --- | --- |
| 多生产者 | 两个生产者同时写 `head`，必须 CAS 循环；竞争激烈时退化 | 每生产者一个环（sharded），或 MPSC 队列 |
| 消费者慢于生产者 | 环满，生产者自旋烧 CPU 或阻塞 | 有界队列 + 背压（`base/31`）或落盘 |
| 元素很大（KB 级） | 拷贝成本超过同步成本 | 环里放指针/索引，数据另存 |
| 跨进程 | 需要共享内存 + 跨进程的屏障语义 | `mmap(MAP_SHARED)` + 进程共享 futex（`base/30`） |
| 需要「恰好一次」语义 | 环只保证搬运，不保证不重复 | 幂等键 + 去重（`→ [eng/2](../eng/2-idempotency-implementations.md)`） |

一句话判据：**只有当「一个写者、一个读者、元素小、允许丢弃或背压」四条同时成立时，SPSC 环才是正确选择。**

## 19.11 五问收口

| 五问 | 本篇的答案 |
| --- | --- |
| **① 它是什么** | 一个数组 + 两个单调游标；用取模把无限序号映射到有限空间，SPSC 时免锁 |
| **② 物理形态** | 数组连续（预取友好）；`head`/`tail` 各 8 B；**是否同处一条 64 B cache line 决定了跨核通信成本**；`sizeof` 131088 vs 131200 |
| **③ 走一遍** | 读对端游标 → 判满/空 → 写数据 → 发布游标 → 对端观察到 → 更新自己的游标；成本全在两次行转移 |
| **④ 改一行** | §19.5 记录了单次分行对照与多轮批量对照；未验证负载，只适合探索。编译输出显示 `seq_cst` 的 `xchg` 与 release 的 `mov` 不同 |
| **⑤ 它证伪了谁** | 「无锁一定快」「padding 是玄学」「volatile 保证顺序」「x86 测过就没问题」——四条全部被实测或汇编推翻 |

## 19.12 一页速记

```
【一句话】RingBuffer 的性能不在「环」，在「64 字节」。

【探索性观测（本机 2 vCPU，不作有效吞吐承诺）】
  有锁 + 相邻游标        1.27 Mmsg/s   （基线）
  无锁 + 相邻游标        5.44 Mmsg/s   （4.30×，去掉锁与睡眠/唤醒）
  无锁 + 游标分行        9.55 Mmsg/s   （1.76×，112 B padding 换一条 cache line）
  批量 K=512              6.16 / 12.84 / 47.97 Mmsg/s（部分样本）

【一条布局规则】
  head 与 tail 相差 8 B  → 同一条行 → 每次发布都跨核搬 64 B
  head 与 tail 相差 64 B → 各自独占 → 发布只是本核 dirty

【一条 x86 事实】
  __ATOMIC_RELEASE  →  mov          （没有单独围栏指令，不等于零成本）
  __ATOMIC_SEQ_CST  →  xchg         （隐式 lock，20–40 cycle）
  ⇒ x86 上「忘写屏障也能跑对」不代表代码正确；ARM 上会真的重排

【一条必踩的坑】
  消费者读完不写回 tail → 生产者写满一圈后永久自旋
  症状伪装成「性能问题」，判据是：tail 不动而 head 在涨

【四条适用前提】
  单写者 + 单读者 + 元素小 + 允许背压/丢弃 —— 缺一条就换结构

【判据】
  优化 RingBuffer = 减少 cache line 转移次数，不是减少指令数。
```

## 19.13 自检 3 题

**Q1.** 你把 `head` 和 `tail` 都声明成 `uint64_t` 并紧挨着放，测试显示功能完全正确，但吞吐上不去。请解释原因，并给出两种修法（一种改布局、一种改访问方式）。

<details><summary>答案</summary>

原因：两个游标落在同一条 64 B cache line 上。生产者写 `head`、消费者写 `tail`，每次写都要把整行从对方的缓存里抢过来（MESI 的 invalidate/transfer），于是「无锁」变成了「每条消息一次跨核行转移」。功能正确是因为没有数据竞争（写的是不同变量），但性能被伪共享吃掉。

修法一（改布局）：`alignas(64)` 或手写 padding，让 `head`、`tail` 各占一行。改完 `sizeof` 只增 112 B，实测本机 5.44 → 9.55 Mmsg/s。

修法二（改访问方式）：**批量**。生产者一次写入 K 条再发布一次 `head`，消费者一次读 K 条再更新一次 `tail`。跨核通信次数从「每消息一次」降到「每 K 条一次」，收益随 K 线性增长（受容量与延迟约束）。批量还能顺带减少自旋轮询的次数。

两种可以叠加，工程上通常都做。
</details>

**Q2.** 同事说「我们这个无锁队列在 x86 上压测了两周，没有任何问题，可以直接上 ARM 服务器」。请指出这句话的风险，并给出一个能在提交前抓住问题的检查手段。

<details><summary>答案</summary>

风险：x86 上某次正确执行不证明 C 程序没有数据竞争，编译成 `mov` 不代表 release/acquire 可删除。在弱序架构上，正确的原语还可能生成不同机器指令。审查时分两条同步边：发布 `head` 前写完槽位；发布 `tail` 前读完槽位，生产者才能复用。

检查手段：**看汇编，不看测试**。用 `gcc -S -masm=intel` 或 `objdump -d` 检查发布点是否生成了 `stlr`（ARM）或至少确认 C 代码里用的是 `__atomic_*` 而非普通赋值。更工程化的做法：在 CI 里加一次 ARM64 交叉编译 + QEMU 跑并发测试（`qemu-aarch64 -cpu max`），并开 ThreadSanitizer。TSan 能抓到一部分缺失同步，但它对「缺屏障但没数据竞争」的情况不一定报——所以最终仍以「原语是否用对」为准。

一句话：**检查语言层同步，而不是数汇编里有几条围栏指令。**
</details>

**Q3.** 你的环容量是 1024，元素是 4 KB 的结构体，消费者偶尔会慢 200 ms。请判断这个设计有什么问题，并给出两种改法。

<details><summary>答案</summary>

两个问题：

1. **内存与拷贝**：1024 × 4 KB = 4 MB 的环，每次入队要拷贝 4 KB（约 200–400 ns），同步成本（20–100 ns）反而成了小头；环还常驻 4 MB，对 L2/L3 不友好。
2. **背压形态错了**：消费者慢 200 ms 时，1024 条的缓冲最多撑 1024 × 生产速率；一旦满，生产者要么自旋烧 CPU，要么阻塞。**用「加大环」掩盖消费慢，只会把延迟从入口推到出口**。

改法一：**环里只放索引/指针，数据放池**。元素变成 8 B，环变小、拷贝变没；生命周期用引用计数或「回收环」管理。

改法二：**显式背压 + 有界**。生产者满了就阻塞或用 `select` 语义等待，并把这个「满」暴露成指标；同时把消费者做批量处理（一次取 K 条），把 200 ms 的慢摊到批次上。如果业务允许，改成「落盘 + 异步消费」（`base/29`），用磁盘吸收抖动。

判据：**环是「削峰」工具，不是「扩容」工具**。它吸收的是毫秒级抖动，不是 200 ms 的消费停滞。
</details>
