## 42.1 引子：100 Mbps 的跨境专线，单流只跑到 8 Mbps

2025 年 11 月，一家跨境电商把订单同步从「同城双活」扩到「上海—法兰克福」专线，链路是运营商承诺的 100 Mbps。上线第一天，同步积压：单条 TCP 连接实测只有 **8 Mbps**，把并发从 1 加到 4 才到 31 Mbps，加到 16 条才勉强摸到 92 Mbps。运维的第一反应是「专线没跑满」「运营商限速」「是不是走了公网」，于是换线路、换时段、抓包数重传——重传率 0.02%，链路干净得很。

真正的数字账在两端 `ping` 和一条 `ss` 里：

| 观测量 | 数值 | 说明 |
| --- | --- | --- |
| 承诺带宽 | 100 Mbps | 运营商 SLA，链路本身不限制单流 |
| 往返时延 RTT | 120 ms | 上海—法兰克福，光纤单程约 60 ms（约 1.2 万公里 ÷ 2×10⁸ m/s） |
| 管道容量 BDP | **1.5 MB** | `100 Mbps × 0.12 s ÷ 8 = 1.5 MB`，见 §42.7 |
| 单流实测 | 8 Mbps | 反推在途字节 = `8 Mbps × 0.12 s ÷ 8 = 120 KB` |
| 应用设置的 `SO_RCVBUF` | 64 KB | 一段 2019 年从旧机房带过来的代码，注释写着「省内存」 |
| 内核实际生效的接收缓冲 | 128 KB | Linux 把 `SO_RCVBUF` 翻倍存放簿记（`sk_rcvbuf`），再减去开销 |
| 16 条并发合计 | 92 Mbps | 每条仍然只有 5.7–6 Mbps，但 16 个 120 KB ≈ 1.9 MB，够了 |

`8 Mbps × 0.12 s ÷ 8 = 120 KB`，与「64 KB 被内核翻倍成 128 KB」几乎精确对上：**链路一秒能跑 100 Mb，但这条连接任何时刻最多只允许 1.5 MB 中的 120 KB 待在途中**，剩下 1.38 MB 的管道是空的。把 `SO_RCVBUF` 那行删掉、让内核按 `tcp_rmem` 自动调，单流立刻到 88–94 Mbps。

这个现象有个名字叫**长肥管道**（Long Fat Network，LFN）：带宽 × 时延很大，而窗口很小。它不是「带宽不够」，是「管子太细」——每秒能过多少水，取决于管子里同时存了多少水，以及水跑一趟要多久：

```
吞吐 ≤ 窗口 / RTT
```

本篇要拆的，就是分子上的「窗口」为什么会有**两个**，以及这两个数字如何互相拉扯出延迟与吞吐的全部取舍。

## 42.2 可靠性三件套：字节编号、累积确认、两种重传

IP 层只承诺「尽力送到某个地址」，不保到达、不保顺序、不保不重复（`base/40`）。TCP 要在这样一条信道上做出「可靠、有序、字节流」的抽象，只需三样东西，缺一不可。

**① 序号：给字节编号，不是给包编号。** TCP 的 `seq` 是 32 位，含义是「本报文段第一个数据字节在整条字节流里的偏移」。一次 `write(fd, buf, 100000)` 会被切成许多段，每段 1460 字节（MSS），序号依次是 `S`、`S+1460`、`S+2920`……**这个设计让重传可以只补一段，而不是重发整个 `write`**，也让接收端能把乱序到达的段按字节重新拼回去。32 位会在 4 GiB 处回绕，所以比较序号必须用模 2³² 的偏序（`base/03` 那套环上算术），并靠时间戳选项（PAWS）排除「上一圈的古董包」。

**② ACK：累积确认。** `ack = N` 的含义只有一句：**N 之前的每一个字节我都收到了**。它不表示「我收到了第 N 段」，也不表示「N 之后没收到」。累积语义的好处是抗丢 ACK——中间某个 ACK 丢了，后面更大的 ACK 会把它一并覆盖；坏处是**一个洞会把后面所有 ACK 都钉在洞的左沿**，这正是 §42.4 SACK 要补的窟窿。

**③ 重传：两种触发，成本差三个数量级。**

- **超时重传（RTO）**：发出去的数据在一个「按 RTT 估出来的时间」内没被 ACK，就重发。它是兜底机制，代价是**必须等**，而且一等往往是几百毫秒到几秒（§42.3）。
- **快速重传**：接收方每收到一个「洞后面的段」，就再发一次 `ack = 洞的左沿`。发送方连续收到 **3 个重复 ACK**（dupACK），就判定「这一段大概率丢了」，不等超时立刻重发。代价是**可能误判**——如果只是网络乱序，这一段其实在路上，重传就是白跑一趟（伪重传）。

一个中间段丢失的完整时序（窗口足够大，洞后面还有数据可发）：

```text
发送方                                              接收方
seq 1..1460      ───────────────────────────────►   ACK 1461
seq 1461..2920   ───────────────────────────────►   ACK 2921
seq 2921..4380   ──────────── X （在链路上被丢弃）
seq 4381..5840   ───────────────────────────────►   ACK 2921   dupACK #1（收到 4381，但 2921 缺）
seq 5841..7300   ───────────────────────────────►   ACK 2921   dupACK #2
seq 7301..8760   ───────────────────────────────►   ACK 2921   dupACK #3 → 触发快速重传
seq 2921..4380   ───────────────────────────────►   ACK 8761   （洞补上，累积 ACK 一次跳到 8761）

时间轴：3 个 dupACK 大约在 1 个 RTT 内到齐，所以恢复耗时 ≈ 1 RTT + 重传段传输时间
        若洞后面没有数据（尾部丢包），一个 dupACK 都产生不了 → 只能等 RTO
```

这张图里有两件事值得记住：

1. **dupACK 不是「否认」，是「我还在等 2921」**。它的信息量全部在「序号没前进」这个事实里，所以 3 个是启发式阈值——乱序严重的路径（多路径、链路聚合）会把阈值调高（Linux 有 `tcp_reordering`，默认 3），否则天天伪重传。
2. **尾部丢包最贵**。没有后续数据就没有 dupACK，只能等 RTO；这也是为什么「小请求 + 大响应」的短连接对丢包格外敏感。

三件套解决了「送到」，但没有解决「送多快」。**序号与 ACK 是账本，窗口才是油门**；而窗口有两个来源，一个来自接收方的内存，一个来自发送方对网络的估计。

## 42.3 RTO 是怎么算出来的：为什么不能用固定超时

超时重传的前提是「等多久算超时」。这个值不能拍脑袋：设小了，正常的长 RTT 路径会被判成丢包，疯狂伪重传；设大了，真丢包时要干等很久，吞吐塌陷。而路径 RTT 的跨度是 **0.05 ms（同机回环）到 600 ms（地球同步卫星）**，相差四个数量级，没有任何一个固定值能覆盖。

所以 TCP 维护两个指数加权移动平均（EWMA）：

```
第一次采样：SRTT = R,  RTTVAR = R/2
之后每次采样 R：
    RTTVAR ← (1 - 1/4) · RTTVAR + (1/4) · |SRTT - R|      （β = 1/4）
    SRTT   ← (1 - 1/8) · SRTT   + (1/8) · R               （α = 1/8）
    RTO    = SRTT + max(G, 4 · RTTVAR)                    （G = 时钟粒度）
```

三个系数各有理由，不是凑出来的：

- **α = 1/8 让 SRTT 慢**。它相当于「最近 8 次采样的加权平均」，单次抖动只挪动 12.5%，避免一个突发样本把超时时间带偏。
- **β = 1/4 让 RTTVAR 快**。方差估计必须比均值更敏感——路径刚开始抖动时，要先抬高 RTO，否则下一次就误判。1/4 正好是 1/8 的两倍，工程上取「方差跟得上、均值稳得住」。
- **4 × RTTVAR 的下界**是保守估计。若 RTT 近似正态，4 倍标准差覆盖 99.99% 的样本；即使分布很偏，这个倍数也保证 RTO 不会贴着均值走。RFC 6298 还规定 **RTO 最小 1 秒（实现可更小）**，Linux 取 **200 ms**（`TCP_RTO_MIN`），上限 **120 s**，初始值 **1 s**。

把一组真实形状的采样代进去（含一次 400 ms 的突发），跑出来的数：

```c
#include <stdio.h>
#include <math.h>

int main(void) {
    double samples[] = {100.0, 110.0, 90.0, 400.0, 95.0};
    double srtt = samples[0], rttvar = samples[0] / 2.0;
    printf("RTT采样   SRTT      RTTVAR    RTO=SRTT+4*RTTVAR\n");
    printf("%7.1f   %7.2f   %7.2f   %8.2f ms\n", samples[0], srtt, rttvar, srtt + 4 * rttvar);
    for (int i = 1; i < 5; i++) {
        double r = samples[i], err = fabs(srtt - r);
        rttvar = 0.75 * rttvar + 0.25 * err;   /* beta = 1/4 */
        srtt   = 0.875 * srtt  + 0.125 * r;    /* alpha = 1/8 */
        double rto = srtt + 4 * rttvar;
        if (rto < 200) rto = 200;              /* Linux TCP_RTO_MIN */
        printf("%7.1f   %7.2f   %7.2f   %8.2f ms\n", r, srtt, rttvar, rto);
    }
    return 0;
}
```

```text
RTT采样   SRTT      RTTVAR    RTO=SRTT+4*RTTVAR
  100.0    100.00     50.00     300.00 ms
  110.0    101.25     40.00     261.25 ms
   90.0     99.84     32.81     231.09 ms
  400.0    137.36     99.65     535.96 ms
   95.0    132.07     85.33     473.38 ms
```

三个现象全部可推：

- 前三次路径很稳（90–110 ms），RTTVAR 一路从 50 降到 32.8，RTO 从 300 收到 231 ms——**路径越稳，超时越紧**。
- 一次 400 ms 的突发把 RTTVAR 抬到 99.65，RTO 冲到 536 ms；即便下一次采样回落到 95 ms，RTO 仍停在 473 ms——**方差涨得快、落得慢，这是故意的**，否则抖动路径会反复误判。
- 若某次真的超时，下一次等待按**指数退避**翻倍：`200 → 400 → 800 → 1600 → … → 120000 ms` 封顶。退避的意义不是「更保险」，而是**拥塞时别往已经堵死的路上继续加压**。

固定超时的荒谬可以直接算出来：阈值取 200 ms，上海—法兰克福（RTT 120 ms）在拥塞时抖动到 250 ms，**每一次抖动都触发一次伪重传**；阈值改成 3 s，同城机房（RTT 0.5 ms）丢一个包要等 3 s 才补，相当于把 1 RTT 的恢复拖成 6000 倍。更糟的是伪重传本身会加重拥塞：多打一份数据进队列，队列更长，RTT 更大——**这正是没有拥塞控制的早期网络「拥塞崩溃」的雏形**。

还有两个必须知道的细节：

- **Karn 算法**：重传段的 ACK 到底确认第一份还是第二份？无法区分，所以**重传段不参与 RTT 采样**；代价是丢包期间 RTO 不更新，时间戳选项（TS）让采样重新可用。
- **RTO 抖动不是随机噪声，是信号**。`rto` 忽大忽小通常意味着路径在排队（§42.8）或接收端零窗口（§42.5）。

## 42.4 SACK 与重复 ACK：一个洞好补，多个洞要一张地图

累积 ACK 只描述「洞的左沿」，不描述「洞后面收到了什么」。当一窗数据里丢了**多个段**时，这个信息缺口会直接变成时间：

假设发送方发了 10 段（编号 1–10，每段记为 1 MSS），第 **3** 段和第 **7** 段丢了，其余都到了接收端。

| 机制 | 接收端看到 | 接收端能告诉发送方 | 发送方要多久补完两个洞 |
| --- | --- | --- | --- |
| 只有累积 ACK | 3 缺、4–6 在缓冲、7 缺、8–10 在缓冲 | 只能反复说 `ACK 3` | 先靠 3 个 dupACK 补 3；补完后 ACK 跳到 7；此时若已没有新数据产生 dupACK，只能等 **RTO** 补 7 |
| 有 SACK | 同上，但每个 dupACK 附带区间 | `ACK 3` + `SACK [4,7)` + `SACK [8,11)` | 第一个 dupACK 就能同时看出 3 和 7 缺，**同一 RTT 内重传两段** |

SACK 是 TCP 选项（kind = 5），载荷是一串 **(left edge, right edge)** 的 32 位序号对，表示「这些区间我收到了」。TCP 选项总长最多 40 字节，减去 2 字节 kind/len 和 2 字节标志，**最多放 4 个块**；所以 Linux 默认每个 ACK 报 4 个不连续区间。接收端只需维护乱序队列（out-of-order queue），把收到的段按序号挂进去，再定期把「还缺哪些」压成 SACK 块。

**为什么 3 个 dupACK 之后还需要 SACK？** 因为「重传了 3」并不等于「知道 7 也丢了」。在纯累积 ACK 下，发送方补完 3、收到 `ACK 7` 时，只能推断「3 到 7 之间到了」，无法区分「7 丢了」和「7 在路上」。若有后续数据持续产生 dupACK，还能再触发一次快速重传；若这已经是这一窗的末尾，就退化成 RTO。**SACK 把「等下一轮信号」变成「一次看全地图」**，多洞恢复从「每洞一个 RTT / 一次 RTO」压到「一个 RTT 补完」。

**DSACK（Duplicate SACK）** 是 SACK 的一个特殊用法：第一个块可以报告「**小于累积 ACK 的区间**」，意思是「这段我收到了重复的」。它不用于补洞，而用于**诊断**：

- 发送方看到 DSACK → 自己刚才的快速重传是伪重传（乱序而非丢包），可以据此估计路径乱序度，并放宽 dupACK 阈值；
- 接收方主动报告重复 → 发送方不必等 RTO 才发现「其实没丢」；
- 这也是 Eifel、F-RTO 这类「伪超时检测」的输入之一——**误判的代价不只是浪费带宽，还会让 cwnd 白降一次**（§42.6）。

SACK 不是免费的：接收端要为乱序段保留内存（攻击者可制造大量空洞撑爆 `ofo` 队列，内核有上限与淘汰策略），发送端要维护重传队列与区间映射。它是一个**用状态换时间**的交易——在 BDP 大、丢包成串的链路上稳赚，在短连接、低时延的内网里收益有限。

## 42.5 流量控制：rwnd 是接收方的「还剩多少内存」

第一道天花板来自接收方。TCP 头部的**窗口字段只有 16 位**，最大 65535 字节；接收方在每个 ACK 里告诉对方「我还能接多少」（`rwnd = 接收缓冲剩余空间`）。发送方必须保证：

```
在途未确认字节 ≤ rwnd
```

16 位在 1981 年够用（那时候 BDP 只有几 KB），今天连一条 100 ms、10 Mbps 的路径都撑不住（需要 125 KB）。所以有了**窗口缩放选项**（Window Scale，kind = 3）：在三次握手的 SYN / SYN-ACK 里各带一个 0–14 的移位数，之后所有窗口字段都左移这么多位。

```
实际上限 = 65535 × 2^shift          shift ∈ [0, 14]
最大     = 65535 × 2^14 = 1,073,725,440 B ≈ 1 GiB
```

本机一条真实连接的 `ss -ti` 片段（完整输出见 §42.9）：

```text
cubic wscale:10,10 ... cwnd:11 ssthresh:9 ... snd_wnd:33030144 ... rwnd_limited:188ms(2.4%)
```

- `wscale:10,10`：双方各用 10 位缩放，窗口上限 `65535 × 1024 = 64 MiB`；
- `snd_wnd:33030144`：对端当前 advertises 约 31.5 MiB，这是**发送方看到的接收窗口**，不是缓冲区总量；
- `rwnd_limited:188ms(2.4%)`：在采样窗口里，有 2.4% 的时间发送被**接收窗口**卡住，而不是被拥塞窗口卡住。这个字段是区分「流量控制瓶颈」和「拥塞控制瓶颈」最直接的一把刀。

### 零窗口与探测：不发包的死锁

当应用不读数据时，接收缓冲会满，`rwnd` 降到 0。发送方收到零窗口通告后必须停下来。问题来了：**「窗口打开了」这个消息本身也是一个 ACK，它也可能丢**。如果双方都安静地等，就会永久死锁——接收方以为发送方知道窗口开了，发送方以为窗口还是 0。

解决办法是**零窗口探测（zero window probe）**：发送方启动 persist 定时器，定期发一个字节（或一个不带数据的探测段），强制接收方回一个带当前窗口的 ACK。Linux 从 0.5 s 起指数退避，上限 120 s。**这条机制是「可靠性」与「流控」的交界处**：ACK 不保达，所以任何「等对方主动通知」的设计都必须配一个探测。

顺带一个相关坑：**糊涂窗口综合征（SWS）**——接收方只空出 40 字节就通告 40 字节，发送方发一个 40 字节载荷 + 40 字节头，效率 50%。修正：接收方不到「半个缓冲或一个 MSS」不更新窗口，发送方用 Nagle 攒小包；Nagle 与延迟 ACK 相撞则产生 40 ms 尖刺（§42.11）。

### 第二道天花板：cwnd 在发送方，线路上看不见

与 rwnd 不同，**拥塞窗口 cwnd 没有任何头部字段**。它是发送方自己维护的一个数字，代表「我认为网络现在能承受多少在途字节」。它不在包里，也不告诉任何人；接收方只能从「数据来得快不快」间接感受到它。

于是发送方真正遵守的规则是：

```
在途未确认字节 ≤ min(rwnd, cwnd)
```

```
应用 write()
   │
   ▼
发送缓冲区 ──► [ 在途 ≤ min(rwnd, cwnd) ] ──► 网络 ──► 接收缓冲区 ──► 应用 read()
                    ▲                ▲                      │
                    │                │                      │
              cwnd（拥塞控制）   rwnd（流量控制）◄───────────┘
              发送方估计网络       接收方剩余内存（随 ACK 通告）
```

| 上限 | 谁决定 | 通过什么传递 | 满了会怎样 | 调它的旋钮 |
| --- | --- | --- | --- | --- |
| `rwnd` | 接收方应用读得多快 + 接收缓冲大小 | ACK 的 16 位窗口字段（可缩放） | 发送方停等，接收方 `Recv-Q` 涨 | `SO_RCVBUF`、`net.ipv4.tcp_rmem`、应用读取速度 |
| `cwnd` | 发送方对路径拥塞的估计 | **不上线路**，纯本地状态 | 发送方自我限速，`ss` 里 `cwnd` 变小 | 拥塞算法、`tcp_congestion_control`、路径丢包/时延 |

**这两个数字的博弈就是本篇的「唯一真问题」**：rwnd 是「你有没有地方放」，cwnd 是「路受不受得了」；吞吐取二者较小值除以 RTT，延迟则由「缓冲区里堆了多少」决定。调大缓冲能抬高 rwnd，但抬不动 cwnd；换拥塞算法能改 cwnd 的爬升曲线，却改不了对端只有 64 KB 内存的事实。

## 42.6 拥塞控制：慢启动、拥塞避免、快速恢复，以及 CUBIC 与 BBR 的分道扬镳

流量控制假设「网络无限，只有接收方会满」；1986 年的第一次**拥塞崩溃**打碎了这个假设：链路利用率从 90% 掉到 1%，因为所有发送方都在重传。拥塞控制要回答：**在不知道网络容量时，怎么找到一个既不浪费、又不打爆队列的速率。**

### 三个基本动作

1. **慢启动（slow start）**：连接刚开始，`cwnd` 从 10 MSS 起（RFC 6928 把初始窗口从 2 提到 10），每收到一个 ACK 就 `cwnd += 1 MSS`。由于一个 RTT 内所有段都会被确认，效果是**每个 RTT 翻一倍**。它叫「慢」是相对「一上来就发满」而言，实际是指数增长。
2. **拥塞避免（congestion avoidance）**：当 `cwnd ≥ ssthresh`，改成每个 RTT 只加 1 MSS（实现上是每个 ACK 加 `MSS²/cwnd`）。从指数转为线性，开始小心试探。
3. **快速恢复（fast recovery）**：收到 3 个 dupACK 时，先把 `ssthresh` 砍到在途量的一半，重传丢失段，然后**不回到慢启动**，而是从减半后的窗口继续线性增长。理由是：dupACK 证明「路还通，只是丢了一个包」，没必要从 10 MSS 重来。

这套组合的名字叫 **AIMD**（Additive Increase, Multiplicative Decrease）：加是每次 +1，减是直接乘 0.5。它有一个漂亮的性质——**多条流最终会收敛到公平份额**，因为窗口大的流被砍得更狠。

### CUBIC：把「加」换成一条三次曲线

Reno 的线性增长在高 BDP 链路上太慢：RTT 200 ms、窗口要涨到 1.25 MB，每 RTT 加 1 MSS 需要 `(1.25e6/1460) ≈ 856` 个 RTT ≈ 171 秒才能回到丢包前的窗口。CUBIC 把增长曲线换成以**丢包前窗口 `W_max`** 为锚点的三次函数：

```
W(t) = C · (t - K)³ + W_max
C    = 0.4（单位 MSS/s³，Linux 采用值）
β    = 0.7（乘性减因子，即丢包后保留 70%）
K    = ∛( W_max · (1 - β) / C )      ← 回到 W_max 所需时间
```

`K` 的物理意义是「凹下去多深、要多久爬回来」。代入 `W_max = 1000 MSS`：

```text
CUBIC Wmax=1000 MSS -> K=9.09 s；t=K 时回到 Wmax 的 70%
  t=  0.0s  W=   700.0 MSS     ← 刚丢包，乘 0.7
  t=  9.1s  W=  1000.0 MSS     ← 回到丢包前水平
  t= 14.1s  W=  1050.0 MSS     ← 越过 W_max 后转为凸增长，开始 aggressively 试探
  t= 29.1s  W=  4200.0 MSS     ← 曲线越陡，抢带宽越凶
```

两个要点：曲线在 `W_max` 附近**平缓**（不急着再撞墙），远离 `W_max` 后**陡峭**（快速抢回份额）；而且 `t` 是**墙钟时间**，不是 RTT 数——这让 CUBIC 对长 RTT 流更友好（Reno 的增长按 RTT 计，长 RTT 流天然吃亏），代价是短 RTT 流可能被压制。

### BBR：不把丢包当信号，而是给管道建模

BBR 的问法是另一个：**如果我知道这条路径的带宽和最小 RTT，我直接按 BDP 发不就行了？**

```
BtlBw  = 最近一段时间观测到的最大交付速率（delivery rate 的窗口最大值）
RTprop = 最近一段时间观测到的最小 RTT
cwnd   = BtlBw × RTprop × gain
pacing_rate = BtlBw × pacing_gain
```

- 四个状态：`Startup`（指数探带宽，gain ≈ 2.885）、`Drain`（排空启动期队列）、`ProbeBW`（±25% 周期试探）、`ProbeRTT`（每 10 s 压窗 200 ms，重测最小 RTT）。
- **丢包在 BBR 里不是拥塞信号**，只是一个统计量；真正驱动它的是「交付速率还涨不涨」和「RTT 有没有离开最小值」。
- 代价：BBR 与丢包驱动的流共存时会**抢占**（它不因丢包退让），v1 还存在 RTT 不公平与浅缓冲下排队的问题；这些是 `base/51` 要量的。

### 为什么 1% 丢包能让 CUBIC 塌 10 倍，BBR 却几乎不掉

这是两种「对丢包的解释」的直接后果。用 Mathis 公式估算丢包驱动的稳态吞吐：

```
吞吐 ≈ (MSS / RTT) × (1.22 / √p)
```

`p` 是丢包率。把 `MSS = 1460 B`、`RTT = 100 ms` 代进去：

| 丢包率 p | 估算吞吐（MSS 1460，RTT 100 ms） | 相当于 |
| --- | --- | --- |
| 0.01% | 14.25 Mbps | 轻微损伤 |
| 0.1% | 4.51 Mbps | 已掉一个量级 |
| **1%** | **1.42 Mbps** | 一条 100 Mbps 的流只剩 1.4% |
| 5% | 0.64 Mbps | 基本不可用 |

`√p` 是罪魁：丢包率涨 10 倍，吞吐只降到 `1/√10 ≈ 0.32`，但基数本身已经被 `1.22/√p` 压得很低。**1% 随机丢包对 CUBIC 不是「损失 1% 的包」，而是「每个丢包事件都把窗口乘 0.7，稳态窗口被钉在很小的值」**。而 BBR 根本不看 `p`：只要交付速率还能测到、最小 RTT 没变，它就按 `BtlBw × RTprop` 发，丢一个包只是那一段要重传，不改变它对管道容量的估计。

本机实测（§42.9 有完整命令）把这条差异量了出来：同一条回环链路、同样 20 ms 单程延迟、同样 1% 丢包，**CUBIC 187 Mbps，BBR 2.04 Gbps，差 10.9 倍**。用同一套参数代 Mathis：`MSS = 65483`（回环 GSO 造成的大段）、`RTT = 40 ms`、`p = 1%` → **159.8 Mbps**，与实测 187 Mbps 同量级（差 17%）。模型没算错，只是绝对数字随 MSS 与 RTT 缩放——**能推导的是比例关系，不是某个固定 Mbps**。

| 维度 | Reno / CUBIC（丢包驱动） | BBR（模型驱动） |
| --- | --- | --- |
| 拥塞信号 | 丢包（+ 超时） | 交付速率、RTT 相对最小值 |
| 增 | 每 RTT +1 MSS（CUBIC 为三次曲线） | 按测量带宽直接给速率，周期性 ±25% 试探 |
| 减 | 丢包时 ×0.5（Reno）/ ×0.7（CUBIC） | 不因丢包减，只在排队时降 pacing |
| 1% 随机丢包 | 稳态窗口被压到 `1.22/√p` 量级，吞吐塌一个数量级 | 基本不掉，只多一次重传 |
| 与同类共存 | AIMD 收敛，较公平 | 可能抢占丢包驱动流；v1 有 RTT 不公平 |
| 缓冲很深时 | 靠丢包才知道满了 → 先排满队列 | ProbeRTT 周期性排空，但仍可能压高时延 |
| 适用 | 丢包即拥塞的传统网络 | 有随机丢包（无线、长肥管道）、缓冲较浅的路径 |

一句话收束这一节：**CUBIC 把丢包读成「路满了」，BBR 把丢包读成「这一份运气不好」**。读法不同，同一个 1% 就既是判决书，也是噪声。

## 42.7 BDP 与吞吐上限：所有账都归到一个除法

现在把前面所有机制压成一个不等式。设窗口为 `W` 字节、往返时延为 `RTT` 秒，则一条连接最多每 RTT 送出一窗数据：

```
吞吐 ≤ W / RTT          （B/s）
     = W × 8 / RTT      （bit/s）
```

这里的 `W = min(rwnd, cwnd)`。而「管道里能同时装多少」叫**带宽延迟积**（Bandwidth-Delay Product，BDP）：

```
BDP = 链路带宽 × RTT
```

BDP 的单位是字节，含义是「为了让链路不停顿，必须有多少字节同时在途」。**窗口小于 BDP，链路就一定有空洞；窗口大于 BDP，多出来的部分只会变成队列（延迟）。**

三个必须能自己算的数：

```
100 Mbps × 100 ms ÷ 8 = 1.25 MB          ← 打满这条链路的窗口
64 KB ÷ 100 ms        = 655,360 B/s = 5.24 Mbps   ← 64 KB 窗口的上限
100 Mbps ÷ (64 KB / 100 ms) = 19.1        ← 差 19 倍
```

第一个式子回答了「为什么跨境专线单流慢」；第二个回答了「为什么老代码的 64 KB 缓冲在今天等于限速 5 Mbps」；第三个说明这不是调优 10%，是差一个数量级。

一张随手可查的表（`W × 8 / RTT`，单位 Mbps）：

| 窗口 \ RTT | 1 ms | 10 ms | 50 ms | 100 ms | 200 ms |
| --- | --- | --- | --- | --- | --- |
| 64 KB | 524.3 | 52.4 | 10.5 | 5.2 | 2.6 |
| 1 MB | 8388.6 | 838.9 | 167.8 | 83.9 | 41.9 |
| 16 MB | 134217.7 | 13421.8 | 2684.4 | 1342.2 | 671.1 |

同城机房（RTT 0.5 ms）里 64 KB 窗口能跑 1 Gbps，所以「窗口不是问题」的经验在那边完全成立；一旦跨洲（RTT 100–200 ms），同一个 64 KB 立刻变成 2.6–5.2 Mbps 的硬顶。**「我们内网很快」和「客户说慢」不矛盾，它们只是 RTT 差了 200 倍。**

### 慢启动要多久才能填满管道

窗口不是一开始就有的。初始 `cwnd = 10 MSS = 14,600 B`，每 RTT 翻倍，填满 BDP 需要：

```text
n = log2(BDP / 14,600)
1.25 MB → 6.4 RTT → 0.64 s @100ms      1.5 MB → 6.7 RTT → 0.80 s @120ms
12.5 MB → 9.7 RTT → 0.97 s @100ms      12.5 MB → 9.7 RTT → 0.10 s @10ms
```

这解释了一类常见误判：**一个 200 ms 就结束的 HTTP 请求，永远没有离开慢启动**，平均窗口只有 BDP 的零头，吞吐当然只有链路的几个百分点。把 `initcwnd` 调到 10 以上（CDN 常用 10–20）能省一两个 RTT，但收益有上限且加剧突发——这是 RFC 6928 的取舍。

### 长肥管道（LFN）：16 位窗口字段的死因

LFN 的判据不是「带宽大」或「时延大」，而是 **BDP 大于 16 位窗口能表达的上限**：`BDP > 65535 B`。

| 链路 | 带宽 | RTT | BDP | 16 位窗口（64 KB）能打满吗 |
| --- | --- | --- | --- | --- |
| 同城机房 | 10 Gbps | 0.5 ms | 625 KB | 不能（差 10 倍），但 RTT 小，实际影响小 |
| 跨洲专线 | 100 Mbps | 120 ms | 1.5 MB | 不能（只能跑 4%） |
| 跨大西洋 | 1 Gbps | 80 ms | 10 MB | 不能（只能跑 0.5%） |
| 地球同步卫星 | 50 Mbps | 600 ms | 3.75 MB | 不能（只能跑 1.4%） |

窗口缩放把上限抬到 1 GiB，才让这些链路在协议层成为可能；但「协议允许」不等于「系统配好了」——§42.11 会讲中间盒把缩放选项清零这个高频故障。

最后必须提醒：`W/RTT` 是**上限**，不是保证。真实吞吐还受发送缓冲、应用读写速度、CPU 拷贝、网卡队列限制；`ss -ti` 的 `app_limited`、`sndbuf_limited`、`rwnd_limited`、`cwnd_limited` 就是「这一刻卡在哪一项」。**先看限流项，再谈调参**——本机回环基线只有 6.02 Gbps，卡的是协议栈拷贝与系统调用（`base/32`、`base/37`），不是窗口。

## 42.8 队头阻塞与缓冲膨胀：为什么「加缓冲」会让延迟变差

### 队头阻塞：TCP 的有序承诺是有代价的

TCP 承诺「交给应用的是一个有序字节流」，实现方式是把乱序到达的段先放进接收队列，等洞补上再一起交付。于是**一个丢失的段会挡住它后面所有已经到达的数据**——应用调用 `read()` 只能拿到洞之前的部分，哪怕后面 1 MB 早就在内存里。

```
接收缓冲区（按序号排列）：
  [1 .. 1460] 已交付给应用
  [1461 .. 2920] 丢失（洞）
  [2921 .. 4380] 已收到，但应用读不到   ┐
  [4381 .. 5840] 已收到，但应用读不到   ├ 队头阻塞：全被 1461 挡住
  [5841 .. 7300] 已收到，但应用读不到   ┘
```

`ss` 的 `Recv-Q` 就是「已收到但应用还没读走」的字节数；在有洞时，它还包含无法交付的乱序段。这个阻塞是**连接级**的，所以：

- HTTP/1.1 用多条连接并行绕过它（连接数 × 窗口）；
- HTTP/2 的多路复用把「连接级 HOL」变成「流级 HOL」的收益打了折扣——同一个 TCP 连接里，一个流丢包仍然挡住所有流（`base/46`）；
- QUIC 把可靠性下沉到每条流，才真正做到「一条流丢包不挡别的流」（`base/43`）。

### 缓冲膨胀：队列是吞吐的必要条件，也是延迟的直接来源

链路上的路由器/交换机必须有缓冲，否则突发流量会直接丢包。但缓冲一旦长期被填满，就变成**排队延迟**。由 Little 定律：

```
排队延迟 = 队列中的字节数 / 链路速率
```

| 链路速率 | 队列积压 | 排队延迟 |
| --- | --- | --- |
| 10 Mbps | 1 MB | **839 ms** |
| 100 Mbps | 1 MB | 84 ms |
| 1 Gbps | 1 MB | 8.4 ms |
| 100 Mbps | 8 MB | 671 ms |

这就是 **bufferbloat**：厂商为了让「测速好看、丢包少」把缓冲做大，结果吞吐没变、延迟从 10 ms 涨到 800 ms。更糟的是它和拥塞控制互相喂：队列越长 → RTT 越大 → 丢包驱动的流把窗口算得更保守/更暴躁 → 恢复更慢 → 队列更满。

**缓冲该多大？** 经典答案是「一个 BDP」——刚好填满管道而不排长队；核心链路上大量流统计复用，可小到 `BDP/√N`（N 为流数）。工程上更常用「小缓冲 + AQM」：

- **RED**：按平均队列长度**提前**概率性丢包，让发送方在队列满之前减速。参数难调，容易要么不动作要么过度丢包。
- **CoDel**（Controlled Delay）：不看队列长度，看**每个包在队列里待了多久**（sojourn time）。目标 5 ms、观察窗口 100 ms：只要连续 100 ms 都超过 5 ms，就开始丢包/标记，直到降下来。它对抗 bufferbloat 的关键是**与速率无关**——不管链路多快，延迟目标都是 5 ms。
- **fq_codel**：每条流一个队列 + CoDel，顺带解决「一条大流挤死小流」。本机 `eth0` 的 qdisc 就是 `fq`（`net.core.default_qdisc = fq`），现代发行版常见 `fq_codel`。
- **BBR 的 ProbeRTT**：每 10 秒把在途量压到 4 个包、持续 200 ms，强制排空自己造成的队列，重新测 `RTprop`。这是「端侧主动对抗 bufferbloat」的另一条路。

一句话：**缓冲买的是「突发不丢」，赊的是「延迟」。赊账额度大约一个 BDP，超过就是在用交互延迟补贴吞吐数字。**

## 42.9 实测：在回环上把上面每个数字量一遍

环境：Debian 12 / Linux 6.12，2 vCPU KVM，`iperf 3.12`，`iproute2` 的 `tc`，默认拥塞算法 `bbr`，`tcp_rmem = 4096 87380 33554432`，`tcp_wmem = 4096 65536 33554432`。所有输出都是本机原样粘贴；`tc` 只改 `lo`，跑完立刻删除。

### ① 基线：回环能跑多快

```bash
iperf3 -s -1 -p 5201 &
iperf3 -c 127.0.0.1 -p 5201 -t 3 -i 1
```

```text
[ ID] Interval           Transfer     Bitrate         Retr
[  5]   0.00-3.01   sec  2.11 GBytes  6.02 Gbits/sec    0             sender
[  5]   0.00-3.06   sec  2.11 GBytes  5.91 Gbits/sec                  receiver
```

回环没有物理链路，RTT 约 0.05 ms，窗口能涨到 65 MB，所以 6 Gbps 不是「带宽上限」，而是**协议栈每字节约 1.3 ns 的处理成本**（`2.11 GB / 3 s`）。它顺便证明了一件事：`W/RTT` 只是上界，真实上限经常是 CPU（`base/32`）。

### ② BDP：同一 RTT 下，窗口从 64 KB 到 2 MB

给 `lo` 加 50 ms 单向延迟（往返 100 ms），然后只改客户端接收窗口：

```bash
tc qdisc add dev lo root netem delay 50ms
iperf3 -s -1 -p 5212 &
iperf3 -c 127.0.0.1 -p 5212 -t 5 -i 1 -R -w 64K     # -R：服务端发、客户端收
iperf3 -s -1 -p 5213 &
iperf3 -c 127.0.0.1 -p 5213 -t 5 -i 1 -R -w 2M
tc qdisc del dev lo root
```

```text
=== 64K 窗口 ===
[  5]   0.00-5.10   sec  4.98 MBytes  8.20 Mbits/sec    0             sender
[  5]   0.00-5.00   sec  4.81 MBytes  8.07 Mbits/sec                  receiver

=== 2M 窗口 ===
[  5]   0.00-5.10   sec   139 MBytes   228 Mbits/sec    0             sender
[  5]   0.00-5.00   sec   136 MBytes   228 Mbits/sec                  receiver
```

验证：`SO_RCVBUF=64K` 被内核翻倍成 128 KB，`128 KB / 0.1 s = 10.5 Mbps`，实测 8.07 Mbps（约 77%，差额来自 ACK 开销与窗口未满）；`2 MB / 0.1 s = 168 Mbps`，实测 228 Mbps（内核翻倍成 4 MB，`4MB/0.1s = 336 Mbps` 的上限下达到 68%）。**同一个 RTT、同一条链路，窗口差 32 倍，吞吐差 28 倍**——这就是 `吞吐 ≤ 窗口/RTT` 的现场。

### ③ 系统缓冲：默认 32 MB 上限 vs 钉死 128 KB

这一组不改应用，只改内核自动调优的上限（改完立即恢复）：

```bash
# 默认：rmem 上限 33554432
iperf3 -s -1 -p 5231 &
iperf3 -c 127.0.0.1 -p 5231 -t 6 -i 1 -R

sysctl -w net.ipv4.tcp_rmem="4096 65536 131072" \
           net.ipv4.tcp_wmem="4096 65536 131072"
iperf3 -s -1 -p 5232 &
iperf3 -c 127.0.0.1 -p 5232 -t 6 -i 1 -R
# 恢复原值
sysctl -w net.ipv4.tcp_rmem="4096 87380 33554432" \
           net.ipv4.tcp_wmem="4096 65536 33554432"
```

```text
[  5]   0.00-6.10   sec  1.06 GBytes  1.49 Gbits/sec    0             sender
[  5]   0.00-6.00   sec  1.04 GBytes  1.49 Gbits/sec                  receiver

[  5]   0.00-6.10   sec  5.49 MBytes  7.55 Mbits/sec    0             sender
```

1.49 Gbps 与 7.50 Mbps 相差 **199 倍**。注意这里 `tc` 仍然只有 50 ms 延迟（RTT 100 ms），128 KB 的理论上限正是 `128KB/0.1s = 10.5 Mbps`，实测 7.5 Mbps——**自动调优不是魔法，它只能在 `tcp_rmem` 的第三个数以内生长**。把上限写小，等于给全机所有连接加了一道 10 Mbps 的隐形闸门。

### ④ 1% 丢包：CUBIC vs BBR

```bash
tc qdisc del dev lo root; tc qdisc add dev lo root netem delay 20ms loss 1%
iperf3 -s -1 -p 5221 & iperf3 -c 127.0.0.1 -p 5221 -t 10 -i 2 -O 3 -C cubic
iperf3 -s -1 -p 5222 & iperf3 -c 127.0.0.1 -p 5222 -t 10 -i 2 -O 3 -C bbr
tc qdisc del dev lo root
```

```text
--- cubic ---
[  5]   0.00-10.00  sec   223 MBytes   188 Mbits/sec   35             sender
[  5]   0.00-10.05  sec   224 MBytes   187 Mbits/sec                  receiver

--- bbr ---
[  5]   0.00-10.00  sec  2.38 GBytes  2.04 Gbits/sec  396             sender
[  5]   0.00-10.05  sec  2.40 GBytes  2.05 Gbits/sec                  receiver
```

**187 Mbps vs 2040 Mbps，10.9 倍**。CUBIC 重传 35 次、BBR 重传 396 次——BBR 并没有「避免丢包」，它只是**不因丢包改变发送速率**，所以多打的那一份数据换来了高得多的交付量。这与 §42.6 的 Mathis 估算（同一参数下 159.8 Mbps）同量级，差值来自 GSO 大段与 netem 同时丢 ACK。

### ⑤ 用 `ss -ti` 读窗口、RTT、重传

抓一段带 1% 丢包的 CUBIC 连接（`ss` 输出已折行）：

```text

  cubic wscale:10,10 rto:244 rtt:41.356/2.238 mss:65483 pmtu:65535
```

逐项对账（这是本篇最该学会的一张「体检表」）：

| 字段 | 读法 | 本例的含义 |
| --- | --- | --- |
| `wscale:10,10` | 双方窗口缩放因子 | 窗口上限 64 MB；若是 `wscale:0,0` 而你对端支持缩放，中间盒可能剥了选项 |
| `rto:244` | 当前超时阈值（ms） | 约为 `SRTT + 4×RTTVAR`，接近 200 ms 下限 |
| `mss:65483` | 本连接的最大段 | 回环 GSO 把多段合成大段；真实以太网是 1460 |
| `cwnd:11` | 拥塞窗口，**单位是段** | `11 × 65483 ≈ 720 KB`；`720KB/0.041s ≈ 140 Mbps`，与 `send` 对上 |
| `bytes_retrans` / `retrans:0/45` | 累计重传字节 / 当前在途重传数、总重传次数 | 2.9 MB / 280 MB ≈ 1.05%，与 netem 的 1% 对得上 |
| `rwnd_limited:188ms(2.4%)` | 被接收窗口卡住的时间占比 | 本例很小，说明瓶颈是 cwnd；若它很大，去查对端 `SO_RCVBUF` |
| `minrtt:40` | 观测到的最小 RTT | BBR 的 `RTprop` 就取这个量级；CUBIC 用它做参照 |

**实验可信度的三条声明**：回环 MSS 被 GSO 放大到 65 KB，绝对吞吐与丢包粒度都与 1500 B 的真实广域网不同，比例关系仍成立；`netem loss 1%` 丢的是「包」而非「字节」，且会同时丢 ACK；BDP 实验用 `netem delay` 伪造的是时延而非带宽，验证的是「窗口/RTT」这一半。

## 42.10 三列账：TCP 承诺了什么、收了多少、从哪开始失效

| 维度 | 承诺了什么 | 为此付了什么 | 从哪里开始失效 |
| --- | --- | --- | --- |
| 可靠 | 不丢、不重、按序交付字节流 | 序号 + ACK + 重传队列；每个连接的内核状态与内存 | 高丢包时重传放大；尾部丢包只能等 RTO；RTO 抖动导致伪重传 |
| 有序 | 应用拿到连续字节流 | 接收端乱序队列；**队头阻塞**：一个洞挡住后面全部数据 | 多流复用时一条流拖垮全部（→ `base/46`）；QUIC 才把粒度降到流 |
| 流量控制 | 不把接收方内存打爆 | 16 位窗口 + 缩放选项；零窗口探测；SWS 规避 | 缓冲写小 → 吞吐被 `rwnd/RTT` 钉死；中间盒清缩放 → 回到 64 KB |
| 拥塞控制 | 不把网络打爆，且尽量用满 | cwnd 爬升要时间（慢启动）；丢包要减窗；算法间可能不公平 | 1% 随机丢包让 CUBIC 塌 10 倍；BBR 会抢占；bufferbloat 把延迟换成吞吐 |
| 公平 | 多条流大致均分瓶颈 | AIMD 的收敛是以「大家都丢包」为代价 | 不同 RTT / 不同算法混跑时不公平；短流永远在慢启动 |
| 通用 | 任何链路、任何应用都能用 | 所有决策都在端点，网络设备只能丢包或排队 | 无线随机丢包被误读为拥塞；卫星/跨洲的 BDP 超出默认窗口 |

一句话：**TCP 用「端点上的两本账（序号账、窗口账）」换来了「网络可以什么都不做」**；代价是所有智能都压在两端，所有无知都变成丢包与排队。

### 三缺表（协议篇必填）

| 缺什么 | TCP 的现状 | 后果 | 补在哪 |
| --- | --- | --- | --- |
| 认证 | **没有**。序列号只要落在窗口内就被接受，源 IP 可伪造 | 盲注入、RST 攻击、中间人可插入/重置连接 | TLS（`base/47`）、mTLS；总表见 `base/48` |
| 完整性 | 只有 16 位校验和，且只覆盖 TCP 段（不含伪首部之外的语义），可被重算 | 中间盒/攻击者可改写载荷并修正校验和 | TLS record 的 AEAD（`base/47`） |
| 机密性 | **没有**，明文传输 | 旁路可读、可改、可做流量分析 | TLS（`base/47`）、QUIC 的 1-RTT 加密（`base/43`） |

## 42.11 踩坑清单：现象 → 根因 → 定位 → 修 → 防复发

| 现象 | 根因（指回本篇） | 定位命令 | 怎么修 | 怎么防复发 |
| --- | --- | --- | --- | --- |
| 吞吐上不去，但链路监控显示带宽空闲 | 单流被 `min(rwnd,cwnd)/RTT` 卡住（§42.7） | `ss -ti` 看 `rwnd_limited` / `cwnd_limited` / `sndbuf_limited`；`ping` 量 RTT；算 `BDP` | 抬高 `SO_RCVBUF`/`tcp_rmem`；开窗口缩放；必要时多流并行 | 容量评审时把「单流 BDP」算进验收项；禁止硬编码 socket 缓冲 |
| 吞吐上不去，`retrans` 很高 | 真丢包（链路/队列）或伪重传（乱序/超时过紧）（§42.3、§42.4） | `ss -ti` 的 `retrans`、`bytes_retrans`；`nstat -az \| grep -i retrans`；`tcpdump` 看是否重复 seq | 真丢包查链路与 qdisc；伪重传调 `tcp_reordering`、启用 DSACK/F-RTO | 区分「丢包率」与「重传率」，后者含伪重传；基线化 |
| 延迟尖刺，规律性 ~40 ms | Nagle 攒包 + 对端延迟 ACK（§42.5 的 SWS） | `strace -T` 看 `write` 阻塞；`tcpdump` 看小包与 ACK 间隔 | 交互型连接设 `TCP_NODELAY`；批量型保留 Nagle | 按连接类型选 Nagle，不要全局拍板 |
| 跨洲吞吐恰好卡在 5 Mbps 附近 | 窗口缩放被中间盒清零，退化成 64 KB（§42.5） | 两端同时 `tcpdump -i any -v 'tcp[tcpflags] & tcp-syn != 0'` 对比 SYN 选项；`ss -ti` 看 `wscale:0,0` | 换掉剥选项的防火墙/NAT；或让中间盒放行 TCP 选项 | 上线前做「SYN 选项透传」测试；监控 `wscale` 是否为 0 |
| 同一链路 CUBIC 与 BBR 表现差 10 倍 | 对丢包的解释不同（§42.6） | 分别用 `-C cubic` / `-C bbr` 跑；对比 `delivery_rate` 与 `minrtt` | 按路径性质选算法：随机丢包多选 BBR，纯拥塞丢包两者皆可 | 算法变更走 A/B；不要在全机一刀切 |
| 短连接平均吞吐只有链路的几个百分点 | 永远在慢启动（§42.7） | `ss -ti` 看 `cwnd` 是否远小于 BDP；`busy` 时间占比 | 提高 `initcwnd`；连接复用；把大响应合并 | 用「每请求字节数 × RTT」估算，而不是只看带宽 |

三条总结：**看到「吞吐低」，先算 BDP 再看 `ss -ti` 的限流项；看到「延迟高」，先找队列；看到「重传高」，先分清真丢包与伪重传。**

## 42.12 一页速记

```text
【一句话】TCP 被两个上限卡死：min(rwnd, cwnd) / RTT = 吞吐上限。
          rwnd 是接收方的内存，cwnd 是发送方对网络的估计；线路上只有前者有字段。

【可靠三件套】
  序号：字节编号（不是包编号），32 位，模 2^32 比较
  ACK ：累积确认，ack=N 表示 N 之前全到；一个洞钉住后面所有 ACK
  重传：RTO 超时（兜底，≥200ms） + 3 个 dupACK 快速重传（≈1 RTT）

【RTO】
  RTTVAR ← 3/4·RTTVAR + 1/4·|SRTT-R|      SRTT ← 7/8·SRTT + 1/8·R
  RTO = SRTT + 4·RTTVAR，下限 200ms，上限 120s；超时后指数退避
  固定超时不可行：路径 RTT 跨 0.05ms–600ms，四个数量级

【SACK】
  选项 kind=5，最多 4 个 (left,right) 块；一个 RTT 补多个洞
  DSACK：报告重复段 → 识别伪重传与乱序度

【窗口】
  rwnd：16 位 × 2^shift（shift ≤ 14）→ 最大约 1 GiB；零窗口要探测
  cwnd：慢启动每 RTT 翻倍；拥塞避免每 RTT +1 MSS；丢包乘 0.5/0.7

【三个算式（必须会手算）】
  BDP = 带宽 × RTT          100 Mbps × 100 ms ÷ 8 = 1.25 MB
  吞吐 ≤ 窗口 / RTT          64 KB ÷ 100 ms = 5.24 Mbps
  填满管道 RTT 数 = log2(BDP / 10 MSS)   1.25 MB → 6.4 个 RTT

【两个算法】
  CUBIC：W(t)=0.4(t-K)^3+W_max，β=0.7；丢包=拥塞；1% 丢包 → 吞吐 ~1.22/√p
  BBR  ：cwnd = BtlBw × RTprop；丢包=噪声；1% 丢包基本不掉（实测 10.9×）

【三个数字】
  Linux 最小 RTO 200 ms；初始 cwnd 10 MSS；CoDel 目标排队 5 ms
```

## 42.13 自检 3 题

**Q1.** 一条连接 RTT 100 ms，接收方通告窗口 64 KB，发送方 cwnd 已经涨到 1 MB，路径无丢包。实际吞吐大约多少？如果把接收方的 `SO_RCVBUF` 改成 1 MB，还能不能线性涨到 80 Mbps？请写出每一步的算式。

<details><summary>答案</summary>

吞吐上限取两个窗口的较小值：

```
W = min(rwnd, cwnd) = min(64 KB, 1 MB) = 64 KB = 65,536 B
吞吐 ≤ 65,536 B / 0.1 s = 655,360 B/s = 5.24 Mbps
```

所以实际大约 **5.2 Mbps**，`cwnd` 再大也没用——**瓶颈是接收窗口，不是拥塞窗口**。`ss -ti` 上应看到 `rwnd_limited` 占比接近 100%，`cwnd_limited` 为 0。

改成 1 MB 后（注意内核会把 `SO_RCVBUF` 翻倍，实际约 2 MB，窗口上限受缩放因子约束）：

```
1 MB / 0.1 s = 10 MB/s = 80 Mbps
```

**能到 80 Mbps，但不是「线性」**——先撞上 `min(rwnd,cwnd)` 的新上限，还要看 `cwnd` 是否爬过 1 MB（慢启动需 `log2(1MB/14600) ≈ 6.2` 个 RTT）、发送缓冲是否够、应用能否持续写满。若 `cwnd` 仍停在 200 KB，吞吐就是 `200KB/0.1s = 16 Mbps`，`ss` 会显示 `cwnd_limited`。**换窗口只是换掉一道天花板，下一道还在。**

</details>

**Q2.** 一窗 10 段里丢了第 3 和第 7 段，其余都到。只有累积 ACK 时，发送方最快多久能补完？有 SACK 时呢？为什么 3 个 dupACK 在第二种情况下不够用？

<details><summary>答案</summary>

**只有累积 ACK**：第 3 段丢失，接收方对 4–6 各回一个 `ACK 3`，发送方收到 3 个 dupACK，快速重传 3。补上后接收方的累积 ACK 跳到 7（因为 4–6 已在缓冲）。此时第 7 段仍是洞，但**这一窗的数据已经发完**，没有新的段去产生 dupACK，只能等 **RTO**（≥200 ms）。所以最快是「1 RTT 补 3 + 至少一个 RTO 补 7」。

**有 SACK**：第一个 dupACK 就携带 `SACK [4,7)` 和 `SACK [8,11)`，发送方一眼看出缺的是 3 和 7，**在同一个 RTT 内把两段都重传**。恢复时间从「1 RTT + RTO」压到「约 1 RTT」。

**为什么 3 个 dupACK 不够**：dupACK 只证明「洞的左沿缺」，不证明「后面还有没有别的洞」。第二个洞要等第一个补完、ACK 前进后才暴露；若那时没有新数据，就没有 dupACK 可用。SACK 把「接收端的地图」直接交给发送端，才让多洞恢复从串行变并行。

</details>

**Q3.** 同一条 100 Mbps、RTT 40 ms 的链路，注入 1% 随机丢包。用 Mathis 公式估算 CUBIC 的稳态吞吐，并解释为什么 BBR 在同一条件下几乎不掉。

<details><summary>答案</summary>

Mathis：

```
吞吐 ≈ (MSS / RTT) × (1.22 / √p)
     = (1460 / 0.040) × (1.22 / 0.1)
     = 36,500 × 12.2 = 445,300 B/s ≈ 3.56 Mbps
```

只有链路的 **3.6%**。这就是「1% 丢包塌一个数量级」的来源：`√0.01 = 0.1`，分母把结果压到十分之一，再乘 1.22 才是稳态窗口的段数。

BBR 不掉，是因为它**不把丢包当拥塞信号**：它测的是 `BtlBw`（交付速率）与 `RTprop`（最小 RTT），丢一个包只让那一段重传，不改变 `cwnd = BtlBw × RTprop`。只要路径的带宽和最小 RTT 没变，发送速率就不变。本机实测 1% 丢包下 CUBIC 187 Mbps、BBR 2.04 Gbps，比值 10.9，与此一致。

</details>
