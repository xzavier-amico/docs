# 11. 指令集、寄存器与调用约定：x86 vs ARM

## 11.1 引子：三个「没有任何报错」的错误

先看三个真实结果。它们分别发生在「链接成功但语义错」、「调用点」、「栈耗尽」三个位置，看起来毫无关系。

**第一段：一个字段顺序，答案错了 6 倍。** 两个 `.c` 文件，各自 `#include` 一个头文件，两个头文件只差一个字段的先后：

```c
/* abi_v1.h —— 库这一侧 */        /* abi_v2.h —— 主程序这一侧 */
struct cfg {                       struct cfg {
    int timeout;                       int retries;
    int retries;                       int timeout;
};                                 };
long compute(struct cfg c);        long compute(struct cfg c);
```

```c
/* abi_lib.c：库这一侧，按 v1 布局读 */
long compute(struct cfg c) { return c.timeout * 1000L + c.retries; }

/* abi_main.c：主程序这一侧，按 v2 布局写 */
int main(void) {
    struct cfg c = { .timeout = 30, .retries = 5 };
    printf("%ld\n", compute(c));      /* 期望 30005 */
}
```

`gcc -O2` 分别编译、链接，零警告，运行：

```
5030
```

不是 30005，也不是崩溃，是 5030——因为 `5030 = 5×1000 + 30`：库把偏移 0 的 `5` 读成了 `timeout`，把偏移 4 的 `30` 读成了 `retries`。**两个编译单元对同一块 8 字节内存的字段划分不一致，而链接器对此一无所知**，因为布局从来不出现在符号表里。这是 §11.6 的第一个现场。

**第二段：多两个参数，每次调用贵 21%。** 同一个求和函数，一份 4 参数、一份 8 参数，各跑 5000 万次调用（取 7 轮最小值）：

```
f4 min: 1.913 ns/call          ← 4 个参数，全在寄存器
f8 min: 2.309 ns/call          ← 8 个参数，第 7、8 个走栈
delta:  0.396 ns/call  ratio: 1.21x
```

这台机器实测主频 2.65 GHz（1 周期依赖链 5 亿次 0.188 s，与 `/proc/cpuinfo` 的 2595 MHz 对上），所以 0.396 ns ≈ **1.05 个周期**。多出来的正是两条 `push`、两条 `pop`、两次栈上取参的内存访问（§11.7 有反汇编原文）。**参数个数的代价不是线性的，是在第 7 个参数处突然出现的**——因为寄存器槽位用完了。

**第三段：8 MiB 的栈，只能递归 130,989 层。** 默认 `ulimit -s` 是 8192 KB，递归函数每帧 64 B，理论深度 `8,388,608 ÷ 64 = 131,072`，实测：

```
pad=32    depth=130989 frame=64.0B total=7.99MiB
```

预测 131,072、实测 130,989，差 83 帧（0.06%）。把每帧撑到 160 B，深度掉到 52,406；撑到 2080 B，只剩 4,028。**递归深度上限不是语言属性，是 `栈大小 ÷ 帧大小` 这个除法**。

三个现象，三份合同，同一个名字：

| 现象 | 被破坏的合同 | 合同写在哪 |
| --- | --- | --- |
| 字段顺序一换，结果错 | 结构体布局（字段偏移、对齐、填充） | 头文件 + 编译器，链接器看不见 |
| 第 7 个参数开始变贵 | 参数传递约定（哪些寄存器、剩下的往哪放） | ABI 文档（System V AMD64 / AAPCS64） |
| 递归 13 万层就死 | 栈帧布局（帧里有什么、多大、谁负责回收） | 编译器 + ABI + 内核给的栈上限 |

本篇要交付的，就是让这三件事从「玄学」变成「查表 + 一次除法」。而它们的共同源头是：**指令集是硬件与编译器之间唯一一份双方都必须实现、且发布后不能改的接口规格**。

> 主线归属：本篇量到的是**主线③（每层抽象的单价 = 跨界次数 × 单次成本）**在指令层的第一次落地——寄存器就是「跨界」最便宜的那一侧，栈是第二便宜，内存是第三；同时它也是**主线①（没有魔法，只有位与约定）**的第二个落点（第一个在 `base/03` 的位模式）。

## 11.2 指令集不是「指令的集合」，是一份接口规格

### 规格里到底写了哪五件事

「x86 有 ADD、MOV、JMP」这种描述，等价于说「TCP 有 SYN、ACK、FIN」——它列了名词，没给语义。一份真正的指令集规格（Intel SDM、Arm ARM）必须写清五件事，缺一件编译器就无法生成正确代码：

| # | 规格项 | 具体内容 | 不写清会怎样 |
| --- | --- | --- | --- |
| ① | **可见寄存器** | 有哪些名字、多宽、哪些位可写、复位值 | 编译器不知道把中间值放哪，只能全落内存 |
| ② | **指令编码与寻址** | 每条指令的字节序列、操作数从哪来（寄存器/立即数/内存） | 汇编器与 CPU 译码器对不上，二进制无法执行 |
| ③ | **内存模型** | 哪些访问允许非对齐；多核下读写能否重排；原子性粒度 | 编译器会把「你以为有顺序」的代码重排掉（`base/13`） |
| ④ | **异常与特权语义** | 除零/缺页/断点/非法指令分别是什么、压什么栈帧、跳到哪 | 内核无法从故障中恢复，也无法实现系统调用 |
| ⑤ | **边界约定** | 函数调用怎么传参、系统调用怎么传号、谁保存哪些寄存器 | 两个独立编译的目标文件无法链接成可运行程序 |

工程上看，①③⑤ 是每天都会撞上的三条；②④ 只在写汇编、写 JIT、写内核时露面。本篇的重心是 ① 与 ⑤，③ 留给 `base/13`，④ 在 `base/21` 与 `base/15` 展开。

### CISC 与 RISC：差别只剩在「前端」

教科书上的对比是「x86 指令复杂、ARM 指令简单」。这句话在 1995 年成立，今天只剩一个可测量的事实：**x86 的指令是变长的（1–15 字节），ARM64 的指令是定长 4 字节的**。其余差异都被下面这个动作抹平了：

```
x86 机器码（变长字节流）
   ↓ 取指：必须先算出这条指令有多长，才知道下一条从哪开始
   ↓ 译码：一条 add [mem], reg 被拆成 load + add + store 三个 μop
μop 流（定长、类 RISC、三操作数）  ← 这才是执行引擎真正看到的东西
   ↓ 重命名 → 发射 → 执行 → 提交
```

自 P6（Pentium Pro，1995）起，x86 的执行引擎吃的就是 μop，不是「复杂指令」。所以「CISC 一条指令干很多事」这句话的真实代价不在执行，在**前端**：

- **取指边界要现算**：一条指令可能 1 B 也可能 15 B，译码器必须先判长度。ARM64 每条 4 B，16 B 的取指块正好 4 条，边界直接由地址低位算出。
- **译码带宽有限**：x86 每个周期能译出的指令条数被变长格式卡住；ARM64 的定长格式让译码器可以并行切片。
- **于是有了 μop cache**：现代 x86 把译完的 μop 缓存起来（Intel 的 DSB、AMD 的 op cache），热代码直接从缓存发 μop，绕开变长译码。**这一步等于承认了「复杂指令集」只在冷代码路径上存在。**

| 维度 | x86-64 | ARM64（AArch64） | 这条差异落在哪 |
| --- | --- | --- | --- |
| 指令长度 | 1–15 B，典型 3–4 B | 固定 4 B | 前端取指/译码 |
| 通用寄存器 | 16 个（rax…r15） | 31 个（x0…x30）+ SP + XZR | 编码字段位宽 |
| 编码里的寄存器字段 | ModRM 3 bit + REX 扩展 1 bit = 4 bit = 16 | 5 bit = 32 | 为什么 x86 停在 16 |
| 条件执行 | 独立 RFLAGS + `jcc`/`cmov`/`setcc` | NZCV + `csel`/`cset`/`cinc`（可无分支选择） | 分支预测压力 |
| 访存 | 只有 `mov` 类能碰内存（load/store 架构） | 同样 load/store，但寻址模式更多（基址+偏移+前后变址） | 指令条数 |
| 内存序 | TSO：store-store 不重排 | 弱序：读写默认可重排，需 `dmb`/`ldar`/`stlr` | 编译器能否删屏障（`base/13`） |
| 非对齐访问 | 普通访问允许（有性能代价） | 普通访问允许；独占/原子访问要求对齐 | 结构体打包 |
| 谁负责「一条复杂操作」 | 硬件译码器拆 | 编译器用多条定长指令拼 | 编译器工作量 |

最后一行值得单独说：**ARM64 把复杂度从硬件搬到了编译器**。所以「同一个 C 函数在两个平台上生成的汇编行数不同」是必然的——但那是编译器在替硬件还债，不是硬件更强或更弱。本篇不做跨平台实测：本机没有 ARM 工具链，编造数字比不写更糟，ARM 部分只讲差异落在哪一层。

### 合同的单向性：编译器只能相信规格里写了的东西

C 的有符号溢出是未定义行为（`base/03`），这不是语言设计者的懒，而是因为**指令集只承诺了「加法器按 mod 2ⁿ 算」，没承诺「溢出时给你一个可判定的标志位且编译器必须保留你的检查」**。同理，`volatile` 在 x86 上看起来「够用」，是因为 x86 的 TSO 恰好不许 store-store 重排；同一份代码在 ARM64 上必须补 `atomic_thread_fence(release)`。**你写的每一条「跨平台一定成立」的假设，都必须能在规格里找到出处；找不到的，都是运气。**

## 11.3 寄存器：16 个与 31 个，差的不只是数字

### x86-64 的 16 个通用寄存器

先把名字、别名、约定用途和保存责任摆在一张表里（保存责任是 §11.4 的内容，这里先给结论，因为查表时它们总是一起用）：

| 寄存器 | 低 32 位 | 约定用途 | 谁负责保存 |
| --- | --- | --- | --- |
| `rax` | `eax` | 返回值；变参函数的 `al` = 用到的向量寄存器个数；系统调用号 | caller |
| `rbx` | `ebx` | 通用；历史上是基址寄存器 | **callee** |
| `rcx` | `ecx` | 第 4 个整型参数；移位/循环计数 | caller |
| `rdx` | `edx` | 第 3 个整型参数；128 位返回的高半；除法的高半 | caller |
| `rsi` | `esi` | 第 2 个整型参数；字符串操作的源 | caller |
| `rdi` | `edi` | 第 1 个整型参数；字符串操作的目的 | caller |
| `rbp` | `ebp` | 帧指针（`-fomit-frame-pointer` 下可当通用寄存器） | **callee** |
| `rsp` | `esp` | 栈指针；不能当通用寄存器用（`push`/`pop`/`call` 隐式改它） | **callee**（恢复原值） |
| `r8`–`r9` | `r8d`–`r9d` | 第 5、6 个整型参数 | caller |
| `r10`–`r11` | `r10d`–`r11d` | 临时；`syscall` 用 `r10` 顶替 `rcx`，`r11` 存返回后的 RFLAGS | caller |
| `r12`–`r15` | `r12d`–`r15d` | 通用 | **callee** |
| `rip` | `eip` | 指令指针（不能直接写，只能 `jmp`/`call`/`ret` 改） | — |
| `rflags` | `eflags` | 条件码 ZF/SF/OF/CF/DF 等 | caller（`pushfq` 可保存） |

三条容易被忽略的事实：

1. **32 位写入自动清零高 32 位。** `mov eax, 1` 会把 `rax` 高半清零；这不是「保留」也不是「未定义」，是规格强制的零扩展——所以 `xor eax,eax` 比 `mov rax,0` 少一个字节且打破依赖链，成了清零的惯用法。
2. **`rsp` 不是第 17 个通用寄存器。** 它是 `call`/`ret`/`push`/`pop` 的隐式操作数，任何时刻都必须指向一个「栈顶」；把它当累加器用，下一条 `call` 就把返回地址写到别处。
3. **`rbp` 可以不要。** `-O2` 默认省略帧指针，把 `rbp` 让给通用值；代价是栈回溯要靠 `.eh_frame` 的 DWARF 描述符（`base/12` 会用到 `readelf --debug-dump=frames`）。

### ARM64：31 个通用寄存器 + 一个零寄存器

| 寄存器 | 用途 | 谁负责保存 |
| --- | --- | --- |
| `x0`–`x7` | 整型/指针参数；`x0` 兼返回值（128 位时 `x0:x1`） | caller |
| `x8` | 间接结果位置：返回大结构体时，调用者把目标地址放这里 | caller |
| `x9`–`x15` | 临时寄存器 | caller |
| `x16`–`x17` | `IP0`/`IP1`，链接器插桩（PLT 跳板）专用 | caller |
| `x18` | 平台寄存器，某些系统保留给 OS/运行时 | 平台相关 |
| `x19`–`x28` | 通用 | **callee** |
| `x29` | 帧指针（FP） | **callee** |
| `x30` | 链接寄存器（LR）：`bl` 把返回地址写这里 | **callee** |
| `sp` | 栈指针，单独编址，不能当通用寄存器 | **callee** |
| `xzr`/`wzr` | 零寄存器：读恒为 0，写直接丢弃 | — |

其中 `x30`（LR）是结构性的差异：**x86 的 `call` 把返回地址压栈，ARM64 的 `bl` 把它写进寄存器**。后果是——一个不再调用别人的叶子函数，在 ARM64 上**完全不需要栈帧**：没有 `push`、没有 `pop`、没有 `sub rsp`，直接算完 `ret`。这就是为什么同一段简单函数在 ARM64 上的序言常常是空的，而在 x86-64 上至少有一对 `push rbp`/`pop rbp`（或者干脆没有，靠 red zone）。非叶子函数才需要 `stp x29, x30, [sp, #-16]!` 把 FP 和 LR 一起存到栈上。

### 为什么 16 这个数字是硬的

「为什么 x86-64 只有 16 个通用寄存器，ARM64 有 31 个」——答案不在工艺，在**编码字段**：

- x86 的 ModRM 字节把「寄存器」「r/m」「寻址模式」挤在 8 位里，其中 `reg` 字段只有 **3 位 = 8 个**；AMD64 加了一个 REX 前缀，用其中的 `R`/`X`/`B` 各 1 位把 3 位扩到 **4 位 = 16 个**。想再翻倍到 32，需要再加 1 位——而前缀空间（`0x40`–`0x4F` 已被 REX 占满，`0x66`/`0xF2`/`0xF3` 已被占用）没有位置，只能定义一套新前缀，那等于让所有旧译码器作废。
- ARM64 的指令固定 32 位，`Rd`/`Rn`/`Rm` 各占 **5 位 = 32 个**，从第一天就够用。31 个可用 + `xzr` 占掉编码 31 号，是「留一个位置当零」的便宜设计——读零寄存器不需要指令，省掉 `mov r0, #0`。

再看「寄存器为什么是最贵的资源」，三个可推导的量：

| 成本项 | 估算 | 说明 |
| --- | --- | --- |
| 存储阵列 | 16 × 64 bit = 1,024 bit = **128 B / 读端口**；31+1 = 2,048 bit = 256 B / 端口 | 寄存器堆是 SRAM，面积 ≈ 位宽 × 条目 × 端口数 |
| 端口数 | 典型 4 读 + 2 写 → 上述值 ×6 ≈ **0.75–1.5 KiB** | 每周期要同时喂多条指令的操作数 |
| 访问延迟 | 直接进关键路径，且随条目数增加的多路选择器级数上升 | 这是「为什么不做 256 个寄存器」的物理原因 |
| 编码代价 | x86 每多 1 位要新前缀；ARM64 每多 1 位要从 32 位指令里抢 | 指令格式一旦发布不可改 |

> 上表是**量级估算**（按 SRAM 位单元 + 多路选择器模型推），不是某颗芯片的实测面积；结论只有一条：寄存器堆的成本随「条目 × 端口」线性涨，而多路选择的延迟随条目数对数涨，所以寄存器数量存在一个性价比拐点，16 与 31 都在拐点附近。

### 重命名：16 个名字，不等于 16 个物理寄存器

现代 x86 用寄存器重命名（register renaming）把 16 个**架构寄存器**映射到一张更大的**物理寄存器堆**上，从而消除 `WAW`/`WAR` 假依赖，让乱序窗口里同时飞着几十条指令（`base/10`）。这带来一个常见误解：「既然物理寄存器上百个，寄存器压力就不存在了」。

不成立。重命名解决的是**流水线内部的假依赖**，不解决**编译器可见的名字不够用**：

- 编译器要在两个函数调用之间保住 20 个活值，可用的 callee-saved 只有 6 个（`rbx, rbp, r12–r15`，其中 `rbp` 在省略帧指针时可用），剩下的必须 `mov` 到栈上再 `mov` 回来。重命名帮不了它——栈槽是真实的存储。
- 每个 spill 是 1 次 store + 1 次 load，L1 命中约 4–5 周期（`base/07`）。

**所以「寄存器数量」的真正含义是：编译器能免费同时活着的值的个数。** 超出的部分全部变成内存流量。这是 §11.4 所有约定的出发点。

## 11.4 调用约定：把「寄存器不够用」写成一份可执行的规矩

### System V AMD64（Linux/macOS 的函数 ABI）

| 类别 | 规则 |
| --- | --- |
| 整型/指针参数 | `rdi`, `rsi`, `rdx`, `rcx`, `r8`, `r9` —— **6 个**，从左到右 |
| 浮点/向量参数 | `xmm0`–`xmm7` —— **8 个**，独立计数，不与整型抢位 |
| 整型返回值 | `rax`；128 位结果用 `rdx:rax`；大结构体用 `rdi` 传隐藏指针 |
| 浮点返回值 | `xmm0`；占两个 eightbyte 的向量用 `xmm0:xmm1` |
| 超出寄存器的参数 | 从右往左压栈，第 7 个整型参数在 `[rsp+8]`（`call` 之后） |
| 栈对齐 | `call` 执行**前** `rsp ≡ 0 (mod 16)`；`call` 压入 8 字节返回地址后，被调用者看到 `rsp ≡ 8 (mod 16)` |
| red zone | `rsp` 以下 **128 B** 可被叶子函数直接使用，不必先 `sub rsp`（信号处理会破坏它） |
| 变参函数 | `al` 必须填入「用到几个向量寄存器」，被调用者据此决定是否保存 `xmm0–7` |
| 方向标志 | 进入函数时 `DF = 0`（`rep movs` 才敢往前扫） |

`al` 这一条是 ABI 里最反直觉的：**变参函数的调用者要在 `al` 里报数**。实测 `take(4, 1.5f, 2.5f, 3.0, 4.0)` 的调用点：

```asm
	movsd	xmm3, QWORD PTR .LC1[rip]     ; 4 个 double 依次进 xmm0–xmm3
	movsd	xmm2, QWORD PTR .LC2[rip]
	mov	edi, 4                        ; 第 1 个固定参数
	movsd	xmm1, QWORD PTR .LC3[rip]
	movsd	xmm0, QWORD PTR .LC4[rip]
	mov	eax, 4                        ; ★ al = 4：用了 4 个向量寄存器
	call	take
```

被调用者那边对应的第一件事就是检查它：

```asm
take:
	sub	rsp, 48                        ; 6 个整型寄存器的保存区 = 48 B
	test	al, al                         ; al == 0 就一个 xmm 都不用存
	je	.L8
	movaps	XMMWORD PTR -88[rsp], xmm0
	...
	movaps	XMMWORD PTR 24[rsp], xmm7      ; 8 个 xmm = 128 B
.L8:
	lea	rax, 56[rsp]                   ; overflow_arg_area（栈上参数）
	lea	r8, -136[rsp]                  ; reg_save_area（寄存器保存区）
```

两个数字：**寄存器保存区 = 6×8 + 8×16 = 176 B**，每次变参调用都要准备（本机上 GCC 只实体化了实际用到的那部分；另一份同时读 `int` 与 `double` 的变参函数，帧是 96 B，但 ABI 允许被调用者按需全部落盘）。这就是 `printf` 比同功能的固定参数函数贵的机制来源，与「格式化解析慢」是两笔独立的账。

### AAPCS64（ARM64 的函数 ABI）

| 类别 | 规则 |
| --- | --- |
| 整型/指针参数 | `x0`–`x7` —— **8 个** |
| 浮点/向量参数 | `v0`–`v7` —— 8 个，独立计数 |
| 返回值 | `x0`（128 位 `x0:x1`）；浮点 `v0`（更大用 `v0`–`v3`） |
| 间接结果 | `x8` = 调用者给的缓冲区地址（返回大结构体时） |
| 超出寄存器的参数 | 从右往左写到栈上，8 字节对齐递增 |
| 栈对齐 | 任何时刻 `sp ≡ 0 (mod 16)`（硬件强制，异常返回也依赖它） |
| 返回地址 | `x30`（LR）；非叶子函数必须自己把 `x30` 存到栈上 |
| red zone | **没有**（信号处理与异步异常随时可能用到 `sp` 以下） |

### caller-saved 与 callee-saved：谁该为「值还活着」付钱

| 类别 | SysV x86-64 | AAPCS64 |
| --- | --- | --- |
| **被调用者必须原样恢复** | `rbx`, `rbp`, `r12`–`r15`, `rsp` | `x19`–`x28`, `x29`, `x30`, `sp`；`v8`–`v15` 的低 64 位 |
| **调用者自己负责**（被调用者可随意破坏） | `rax`, `rcx`, `rdx`, `rsi`, `rdi`, `r8`–`r11`, `xmm0`–`xmm15`, `rflags` | `x0`–`x18`, `v0`–`v7`, `v16`–`v31`, NZCV |
| 保存方式 | `push`/`pop` 或 `mov` 到栈槽 | `stp`/`ldp` 成对操作（一条指令存两个，省一半指令数） |
| 谁的决定更省 | 调用点知道哪些值「调用后还要用」，所以让**调用者**保存大部分寄存器最省 | 同左 |

这条规则的推论很硬：**callee-saved 寄存器是跨调用的「长期存储」，数量固定（x86 有 6 个，ARM64 有 10 个）**。一个函数里同时活着的值超过这个数，就必然产生 spill。这也解释了为什么 ARM64 的 31 个寄存器不只是「多 15 个」：callee-saved 从 6 个涨到 10 个，跨调用能白拿的活值接近翻倍。

### 实测：int 与 double 不抢同一个槽

```c
double mix8(int a, double b, int c, double d,
            int e, double f, int g, double h) { return a+b+c+d+e+f+g+h; }
```

`gcc -O2 -S` 的结果（节选）：

```asm
mix8:
	pxor	xmm4, xmm4
	cvtsi2sd	xmm4, edi          ; a 从 edi 来
	addsd	xmm4, xmm0              ; b 从 xmm0 来
	pxor	xmm0, xmm0
	cvtsi2sd	xmm0, esi          ; c 从 esi 来
	addsd	xmm4, xmm0
	pxor	xmm0, xmm0
	cvtsi2sd	xmm0, edx          ; e 从 edx 来
	addsd	xmm4, xmm1              ; d 从 xmm1 来
	...
	addsd	xmm0, xmm3              ; h 从 xmm3 来
	ret
```

八个参数，**零次栈访问**。整型走 `edi/esi/edx/ecx`，浮点走 `xmm0–xmm3`，两套寄存器文件各自从 0 开始编号。这是「参数槽位」最容易被误解的一点：`double f(int, double, ...)` 里第 2 个参数不会占掉整型的第 2 个槽。

### `syscall` 是第三套约定

同一条 `syscall` 指令，用的既不是 C 的调用约定，也不是 Windows 的：

| 用途 | 函数调用（SysV） | `syscall` 指令 |
| --- | --- | --- |
| 调用号 | —（直接 `call` 地址） | `rax` |
| 参数 1–6 | `rdi, rsi, rdx, rcx, r8, r9` | `rdi, rsi, rdx` **`r10`**, `r8, r9` |
| 返回值 | `rax` | `rax`（负值 = `-errno`，不是 `-1` + `errno`） |
| 被破坏 | `rax, rcx, rdx, rsi, rdi, r8–r11` | `rcx`（存返回地址）、`r11`（存 RFLAGS） |

**第 4 个参数从 `rcx` 换成了 `r10`**，因为 `syscall` 指令本身要用 `rcx` 存「返回后跳回哪」。`base/21` 讲一次系统调用的全过程时会把这张表当第一块砖；这里只需记住：**ABI 不是「一份」，是「一层一份」，跨界就换合同**。

## 11.5 栈帧：帧里到底有什么，以及递归为什么会在那个数字上死

### 标准序言与尾声

`-O0 -fno-omit-frame-pointer` 编译 `work(long,long)`（`char buf[64]` 局部数组），`objdump -d` 原文：

```asm
0000000000001139 <work>:
    1139:	push   rbp                    ; ① 保存调用者的帧指针
    113a:	mov    rbp,rsp                ; ② 本帧基准 = 当前栈顶
    113d:	mov    QWORD PTR [rbp-0x48],rdi   ; ③ 参数溢出到栈（-O0 不优化）
    1141:	mov    QWORD PTR [rbp-0x50],rsi
    1145:	mov    rax,QWORD PTR [rbp-0x48]
    1149:	mov    BYTE PTR [rbp-0x40],al      ; buf[0]
    1150:	mov    BYTE PTR [rbp-0x1],al       ; buf[63]
    ...
    1165:	pop    rbp                    ; ④ 恢复帧指针
    1166:	ret                           ; ⑤ 弹出返回地址并跳转
```

`-O0` 下没有 `sub rsp, N`，因为 GCC 把「局部数组」放在了 red zone 里（`rbp-0x50` 距离 `rsp` 不到 128 B）。一旦有函数调用或有 canary，就会看到完整形态：

```asm
work:
	push   rbp                 ; 8 B
	mov    rbp,rsp
	sub    rsp,0x60            ; 96 B：局部变量 + canary + 对齐填充
	mov    rax,QWORD PTR fs:0x28   ; canary 从 TLS 读
	mov    QWORD PTR [rbp-0x8],rax ; 放在局部变量与 rbp 之间
	...
	mov    rdx,QWORD PTR [rbp-0x8]
	sub    rdx,QWORD PTR fs:0x28   ; 与 TLS 里的原值比
	je     .ok
	call   __stack_chk_fail@plt
.ok:
	leave                      ; = mov rsp,rbp; pop rbp
	ret
```

> 本机 GCC 12.2 的默认配置里 `-fstack-protector*` 全是 disabled（`gcc -Q --help=common` 的输出为证），所以上面这段是显式加 `-fstack-protector-all` 才出现的。发行版自带的 GCC 通常在 configure 时打开 `-fstack-protector-strong`，插入条件是「函数里有数组，或取过局部变量地址」。

### 帧的解剖图

```
高地址
        ┌──────────────────────────────┐
        │ 调用者的栈帧 …                │
        ├──────────────────────────────┤
        │ 第 8 个参数 h                 │  [rbp+24]  ← 只有超过 6 个整型参数才有
        │ 第 7 个参数 g                 │  [rbp+16]
        ├──────────────────────────────┤
        │ 返回地址（call 压入的 8 B）    │  [rbp+8]
        ├──────────────────────────────┤
        │ 保存的调用者 rbp（push rbp）   │  [rbp]     ← rbp 指向这里
        ├──────────────────────────────┤
        │ 局部变量 / 数组 buf[64]        │  [rbp-0x50] …
        │ …                             │
        ├──────────────────────────────┤
        │ canary（8 B，fs:0x28 的副本）  │  [rbp-0x8]
        └──────────────────────────────┘  ← rsp（16 B 对齐）
低地址        （rsp 以下 128 B 是 red zone，叶子函数可白用）
```

一帧的字节数 = `返回地址 8 + 保存的 rbp 8 + 局部变量 + canary 8 + 对齐填充`，并向 16 取整。以上图为例：`8 + 8 + 96 = 112 = 16 × 7`（96 就是 `sub rsp,0x60` 那段，里面装着 buf、canary 与填充，正好不浪费）。**这个数字决定了递归上限**，没有别的因素。

### 递归深度上限：一个除法，加三个修正项

```
depth_max ≈ (栈上限 - 启动已用量) / 每帧字节数
```

实测方法：递归函数里放一个长度可变的局部数组（VLA），每层记下 `&pad[0]`，用第一层与最后一层的地址差除以层数得到**真实帧距**（含返回地址与保存的寄存器），再用 `SIGSEGV` + `sigaltstack` 在栈耗尽的那一刻把深度打出来。8 MiB 栈、2.65 GHz、GCC 12.2 的实测：

| 每层局部数组 | 实测帧距 | 公式预测深度 | 实测深度 | 实际占用 |
| --- | --- | --- | --- | --- |
| 32 B | 64.0 B | 131,072 | **130,989** | 7.99 MiB |
| 128 B | 160.0 B | 52,428 | **52,406** | 8.00 MiB |
| 512 B | 544.0 B | 15,420 | **15,407** | 7.99 MiB |
| 2048 B | 2,079.5 B | 4,033 | **4,028** | 7.99 MiB |
| 128 B，`ulimit -s 1024` | 160.0 B | 6,553 | **6,497** | 0.99 MiB |

三列的关系是干净的：`实测帧距 × 实测深度 ≈ 栈上限`，误差 ≤ 1%。实测比预测低 5–83 帧，来源有三个，都可推：

1. **启动已用量**：`argv`/`environ`/`auxv` 在 `main` 之前就压在栈顶，量级 1–10 KiB。
2. **最后一帧必须死在写 guard page 之前**：探测只写了 `pad[0]` 和 `pad[n-1]`，实际越界点在两者之间。
3. **16 字节对齐把每帧向上取整**：`2048 + 32 = 2080`，实测平均 2,079.5 B 是采样点取整造成的零点几字节偏差。

**所以「递归多少层会爆栈」是一个可以事前算出来的数**：拿 `ulimit -s` 除以你函数在 `-O2` 下的帧大小。工程上更稳的做法是留 10% 余量，因为内核还会在栈顶放环境变量、`LD_PRELOAD`、`MALLOC_*` 这些可变长度的东西。

### 「换成尾递归就好了」——只在编译器真的把它变成跳转时成立

同一个尾递归函数 `tail(n, acc) { if (n==0) return acc; return tail(n-1, acc+1); }`，`gcc -O2` 生成的汇编：

```asm
tail:
	mov	rax, rsi
	test	rdi, rdi
	je	.L5
.L2:
	add	rax, rdi          ; 累加
	sub	rdi, 1
	jne	.L2               ; ★ 直接跳回，没有 call、没有新帧
.L5:
	ret
```

`call` 消失，函数变成循环，10,000,000 层照样返回（实测 `./tailO2 10000000` 输出 `10000000`，退出码 0）。同一个源文件用 `-O0` 编译：

```
-- O0 10M:
Segmentation fault (exit=139)
-- O0 depth via handler:
depth=262016
```

262,016 帧 × 32 B = 8,384,512 B ≈ 8 MiB，与 `8,388,608 / 32 = 262,144` 只差 128 帧。**同一份代码、同一台机器，一个活一个死，差别只是优化级别。**

三条结论：

- **C 标准不保证尾调用优化。** `-O0`、`-fno-optimize-sibling-calls`、或者「尾调用之后还有清理工作」（如 C++ 析构）都会让帧留下来。把正确性押在「编译器一定会 TCO」上，是在赌一个没有写进标准的实现细节。
- **尾递归只对「直接自递归」有效。** 互递归（A 调 B、B 调 A）、或递归调用不是最后一个动作（`return n + f(n-1)`）都不行。
- **语言可以换掉这个约束。** Go 不做 TCO，而是让 goroutine 的栈**按需增长**：初始 2 KiB，每次不够就分配一块更大的、把旧栈整段拷过去，64 位平台上限 1 GiB。代价从「爆栈」变成「拷贝 + 逃逸分析约束」（`base/27` 讲分配器时会再遇到这条）。

## 11.6 ABI 兼容：为什么改一个字段顺序就 break 二进制

### 现场一：结构体布局是约定，符号表里没有它

回到 §11.1 的 `5030`。两个目标文件都只导出一个符号 `compute`，参数是一个「8 字节、按值传递」的结构体——**符号表里只有名字和大小，没有字段偏移**。System V AMD64 对 8 字节结构体的分类是 `INTEGER`，两个 `int` 字段被打包进一个 8 字节的「eightbyte」，用 `rdi` 传。库在 `rdi` 的低 4 字节读 `timeout`，主程序在低 4 字节写 `retries`。**双方都完全正确地执行了自己那份合同，只是合同不是同一份。**

字段顺序不是唯一能改坏 ABI 的东西。下面四个改动，每一个都不会触发任何编译错误：

| 改动 | 后果 | 为什么链接器发现不了 |
| --- | --- | --- |
| 交换两个同类型字段的顺序 | 语义错位（本例：5030 而非 30005） | 大小没变、符号没变 |
| 在中间插一个字段 | 后续字段偏移整体平移 | 同上 |
| 改字段类型（`int`→`long`） | 大小变、偏移变，传参分类可能跟着变 | 只有「结构体总大小」进了调试信息 |
| 改对齐（`__attribute__((aligned(32)))`） | 传参分类变 `MEMORY`，函数序言还要 `and rsp,-32` 重对齐 | 调用约定变了，但符号名不变 |

本机实测的布局与填充（`offsetof` + `sizeof`）：

```
a: size=8  off(i)=4      struct a { char c; int i; }     ← 3 B 填充
b: size=8  off(c)=4      struct b { int i; char c; }     ← 尾部 3 B 填充
c: size=16 off(l)=8      struct c { char c; long l; }    ← 7 B 填充
d: size=12               struct d { int a, b, c; }       ← 无填充，但传参要拆成 2 个 eightbyte
```

`struct d` 那行值得注意：12 字节，不是 8 的倍数，按值传递时占 **2 个 eightbyte**（第二个只用了 4 字节），走 `rdi`+`rsi` 两个寄存器。**填充字节从不被保证是 0**，所以拿 `memcmp` 比较两个结构体是错的（`base/06` 的 padding 一节）。

让它在编译期就爆，只有三条路：

1. **不透明指针**：头文件只暴露 `struct cfg *`，布局留在库里。C 的 API 里这是唯一真正稳定的做法（`FILE *`、`pthread_mutex_t` 的 `_opaque` 变体都是这个套路）。
2. **把布局指纹写进符号名**：`compute_v2_cfg8` 这类命名，或 C++ 的 inline namespace（`namespace v2 { ... }` → 符号变成 `_ZN2v27computeE3cfg`，见下）。
3. **静态断言**：在头文件里写 `_Static_assert(sizeof(struct cfg) == 8 && offsetof(struct cfg, timeout) == 0, "ABI changed")`，让**用错头文件的那一侧**编译失败。

### 现场二：C++ 的名字改编让「跨编译器」变成不可能

C 的符号名就是函数名，所以 `compute` 在 C 里永远是 `compute`。C++ 要把重载、命名空间、模板参数都编进符号名，于是有了 name mangling。实测 `nm` 输出：

```
0000000000000000 T _Z7compute3cfg          ← compute(cfg)
0000000000000010 T _Z7compute3cfgi         ← compute(cfg, int)
0000000000000020 T _ZN2v27computeE3cfg     ← v2::compute(cfg)
```

解码规则是固定的：`_Z` + 名字长度 + 名字 + 参数类型编码。**只要有一侧的类型写法不同，符号名就不同，链接器会报 undefined reference**——在这一层，C++ 比 C 安全，因为错误在链接期就暴露了。

但 mangling 只保证「名字对得上」，不保证「布局对得上」。真正的坑在标准库：`std::string` 在 libstdc++ 的新旧 ABI 之间有 `_GLIBCXX_USE_CXX11_ABI` 两套布局（`std::__cxx11::basic_string` vs 旧版），`std::vector` 的实现细节、异常表格式、虚表布局都由实现决定。**C++ 没有跨编译器的稳定 ABI**，同一份源码用 GCC 与 Clang、或不同版本的 libstdc++ 编译出的 `.so` 不能互换。这就是为什么大厂的基础库要么全 C 接口，要么把整个工具链钉死。

### 现场三：Go 为什么敢用自己的调用约定

Go 从 1.17 起在 amd64 上把「栈传参」换成了「寄存器传参」（register-based ABI）。同一个 8 参数求和函数，`go build -gcflags=-S` 的输出：

```
main.sum8 STEXT nosplit size=24 args=0x40 locals=0x0
	TEXT	main.sum8(SB), NOSPLIT|ABIInternal, $0-64
	LEAQ	(BX)(AX*1), DX
	ADDQ	DX, CX
	ADDQ	DI, CX
	ADDQ	SI, CX
	ADDQ	R8, CX
	ADDQ	R9, CX
	LEAQ	(R10)(CX*1), AX
	RET
```

八个参数全部落在 **`AX, BX, CX, DI, SI, R8, R9, R10`** 八个寄存器里，`$0-64` 表示「0 字节局部变量、64 字节参数」，**整个函数没有一次栈访问**。对照 §11.7 的 C 版本 `sum8`：6 个寄存器 + 两次 `[rsp+8]`/`[rsp+16]` 的栈读取。同一个函数，Go 的版本少两次内存访问。

Go 敢改的理由是一条经济学，不是技术优越：

| 前提 | C/C++ | Go |
| --- | --- | --- |
| 谁一起编译 | 各库独立编译，运行期才拼起来 | 默认整程序一起编译（`go build` 一个包图） |
| 标准库形态 | 独立的 `.so`，ABI 必须稳定 | 随工具链一起编译进二进制（静态链接） |
| 改了 ABI 谁受影响 | 所有已发布的二进制 | 只有源码，重新编译一次即可 |
| 跨 ABI 的边界 | 到处都有 | 只剩 `cgo`、汇编、`//go:linkname` |

代价是边界处必须做转换：Go 的汇编与 `cgo` 走的是另一套「栈传参」的 `ABI0`，编译器在调用点生成 wrapper 做寄存器↔栈的搬运。所以「Go 调用 C 的回调」不是一次跳转，而是一条 `ABIInternal → ABI0 → C` 的链，还要切换 goroutine 栈（`runtime.cgocallback`）。**这就是跨语言回调崩溃的第一大来源：两侧对「参数在哪、栈是谁的」理解不一致**（§11.9 展开）。

## 11.7 实测手册：五条命令量完本篇所有结论

**① 第 7、8 个参数怎么走栈**

```bash

```

```
sum8:
	add	rdi, rsi
	add	rdi, rdx
	add	rdi, rcx
	add	rdi, r8
	lea	rax, [rdi+r9]           ; 前 6 个：rdi rsi rdx rcx r8 r9
	add	rax, QWORD PTR 8[rsp]   ; 第 7 个：调用者的栈
	add	rax, QWORD PTR 16[rsp]  ; 第 8 个
	ret
```

调用点（`push` 顺序是**从右往左**，所以第 7 个落在最低地址）：

```asm

	push	0x7                     ; g   ← 最后压，位置最低
	mov	r9d, 0x6
	mov	r8d, 0x5

	mov	esi, 0x2
	mov	rdi, r10
	call	f8
	pop	rdx                     ; 调用者负责把 16 B 弹掉
	pop	rcx
```

**② `call`/`ret`/`push`/`pop` 在机器码里的样子**


## 11.8 三列账：这份合同承诺了什么、收了多少、从哪开始失效

| 维度 | 承诺了什么 | 为此付了什么 | 从哪里开始失效 |
| --- | --- | --- | --- |
| **寄存器可见集** | 编译器有 16 / 31 个名字可以免费存放中间值 | 寄存器堆面积 ∝ 条目×端口；编码位宽锁死数量 | 同时活着的值超过 callee-saved 数量 → spill 到栈 |
| **指令编码** | 一份字节流在任何同架构 CPU 上行为一致（向前兼容） | 变长编码让前端译码成为瓶颈，需 μop cache 兜底 | 用上新扩展（AVX-512）就在旧 CPU 上 `SIGILL` |
| **调用约定** | 独立编译的两个目标文件可以直接链接、互调 | 参数超 6 个就落栈；每次调用至少一次 `call`+`ret` | 跨 ABI 边界（Win64 / ARM64 / Go ABI0 / 32 位）全部重来 |
| **栈帧布局** | 递归、局部变量、返回地址各就各位，`ret` 一定回到对的地方 | 非叶子函数每帧至少 16 B（返回地址 + 旧 rbp）；栈是有限资源（默认 8 MiB） | 深度 × 帧大小 > 栈上限 → 栈溢出（无救，只能提前算） |
| **结构体布局** | 同一次编译内，字段偏移与对齐完全可预测 | 填充字节；布局写不进符号表 | 两侧头文件不一致 → 静默错位（本例 5030） |
| **名字改编** | 重载与命名空间在链接期可区分 | 符号名与编译器实现绑定，无跨编译器稳定 ABI | 换编译器/换标准库版本 → 链接失败或运行期错乱 |
| **系统调用约定** | 用户态用一条指令进入内核并拿回结果 | 寄存器用途与函数调用不同（`rcx`→`r10`），需专用封装 | 自己写内联 `syscall` 时忘掉 `r11` 被破坏 → 标志位错乱 |

一句话收束：**ABI 买到的是「独立编译、按名链接」，付出的是「一旦发布就冻结」**。所有「升级编译器后二进制不兼容」「换个语言调回调就崩」「改个字段就出错」的事故，都是这笔冻结账的利息。

## 11.9 踩坑清单：现象 → 根因 → 定位 → 修

| 现象 | 根因（指回本篇） | 定位命令 | 怎么修 | 怎么防复发 |
| --- | --- | --- | --- | --- |
| `printf("%f", 1)` 打出 `0.000000` 或乱码 | 变参不提升 `int`→`double`，且 `%f` 从 `xmm` 取（§11.4） | `gcc -Wformat=2`；`objdump` 看调用点 `al` 的值 | 用 `1.0` 而不是 `1`；或 `printf("%d", 1)` | 编译加 `-Wformat=2 -Werror=format` |
| 自己的变参函数读 `double` 得到垃圾 | 调用者没在 `al` 报数，被调用者以为没有 `xmm` 要存 | 看被调用者序言里 `test al,al` 那条分支 | 保证原型可见（不要隐式声明）；变参一律用 `<stdarg.h>` | 变参函数必须有原型且在头文件里 |
| `float` 传到声明为 `double` 的接口，值变成 0 或极小 | 无原型/跨语言时不做提升：`float` 在 `xmm0` 低 32 位，`double` 读低 64 位（§11.4、`base/05`） | `-Wdouble-promotion`；打印 `sizeof` 与位模式；`objdump` 看调用点是否 `cvtss2sd` | 显式转换；接口统一用 `double` 或统一用 `float` | 接口签名里禁止裸 `float` 与 `double` 混用，跨语言边界写死宽度 |
| C 回调在 Go/C++/C# 里崩在第一句 | 两侧 ABI 不同（参数寄存器、栈归属、`al` 约定） | `gdb` 看崩溃时 `rdi/rsi/xmm0` 是否为空；`bt` 看是否跨了 wrapper | 用 `extern "C"` + 明确的 C 结构体；跨语言边界只传不透明指针与 POD | 边界层单独一层，禁止跨语言传 C++ 对象/异常 |
| 结构体按值传大对象，调用点多出一段栈拷贝 | >16 B 或含非整数成员 → 传参分类为 `MEMORY`（§11.6） | `objdump` 看调用点是否 `sub rsp` + `movdqa` 连续拷贝 | 改成 `const T *`；或拆成 ≤16 B 的小结构体 | 公开 API 一律指针传结构体 |
| 升级 GCC 后 `.so` 链接不上，报 `undefined reference` | C++ mangling 或 `_GLIBCXX_USE_CXX11_ABI` 不一致（§11.6） | `nm -C` / `c++filt` 对比两侧符号；`readelf -p .comment` 看编译器版本 | 统一工具链；C 接口导出；或钉死 `-D_GLIBCXX_USE_CXX11_ABI` | 发布物记录「编译器版本 + 标准库 ABI 开关」 |
| 递归深度一到 13 万就 SIGSEGV | 帧大小 × 深度 > 8 MiB（§11.5） | `ulimit -s`；`gdb` 看 `bt` 深度与 `rsp` 差值 | 改迭代 / 显式栈 / 增大 `ulimit -s` / 减小帧 | 上线前按「最坏深度 × 帧大小」算一遍，留 10% 余量 |
| 开了 `-fstack-protector-all` 后热路径变慢 | 每次调用多 2 次 `fs:` 段访问 + 1 次 `cmp` + 1 条条件跳转（§11.5 的反汇编） | `perf stat` 对比开关前后；`objdump` 数 `fs:0x28` 出现次数 | 只在处理外部输入的模块开 `-all`，其余用默认 `-strong` | 按模块分级开启，不要全局 `-all` |

第一条值得展开一句，因为它每天都在发生：`printf` 的 `%f` 期望一个 **`double`**（不是 `float`），而 C 的默认实参提升会把 `float` 转成 `double`，所以 `printf("%f", 1.5f)` 是对的；错的是 `printf("%f", 1)`——`int` 不会被提升成 `double`，它会留在整型寄存器里，而 `%f` 去 `xmm0` 里读，读到的可能是上一次运算的残留。**变参是唯一一处「类型系统完全失明」的接口**，这也是为什么现代 C++ 用 `std::format` 的编译期检查替代它。

## 11.10 一页速记

```
【一句话】指令集是硬件与编译器的合同；寄存器是合同里最稀缺的资源；ABI 是资源不够用时的分配规则。

【寄存器】
  x86-64：16 个通用（rax rbx rcx rdx rsi rdi rbp rsp + r8–r15），3 bit + REX 1 bit = 16
  ARM64 ：31 个（x0–x30）+ SP + XZR，5 bit 字段 = 32
  贵在哪：寄存器堆面积 ∝ 条目 × 端口；多路选择延迟 ∝ log(条目)
  重命名只消假依赖，不增加编译器可见的名字

【调用约定】
  SysV  ：整型 rdi rsi rdx rcx r8 r9（6）；浮点 xmm0–7（8）；返回 rax/xmm0；栈 16 B 对齐；red zone 128 B
  AAPCS64：整型 x0–x7（8）；浮点 v0–v7；返回 x0/v0；无 red zone；LR = x30
  callee-saved：x86 = rbx rbp r12–r15；ARM64 = x19–x28 x29 x30
  syscall：号在 rax，第 4 个参数用 r10（不是 rcx），rcx/r11 被破坏

【栈帧】
  帧 = 返回地址 8 + 旧 rbp 8 + 局部变量 + canary 8 → 向 16 取整
  深度上限 = 栈上限 ÷ 帧字节数（8 MiB ÷ 64 B = 131,072，实测 130,989）
  尾递归只在「编译成 jmp」时救你：-O2 活，-O0 在 262,016 层死

【ABI 三条铁律】
  ① 结构体布局不进符号表 → 改字段顺序 = 静默错位（30005 → 5030）
  ② C++ mangling 只在链接期查名字，不查布局 → 跨编译器无稳定 ABI
  ③ Go 用 ABIInternal（8 寄存器传参），靠「整程序重编译」换自由，cgo 处退回 ABI0
```

## 11.11 自检 3 题

**Q1.** 一个函数有 6 个 `long` 和 8 个 `double` 参数（共 14 个）。在 System V AMD64 上，哪几个参数会走栈？如果把其中 4 个 `long` 改成 `int`，会变吗？

<details><summary>答案</summary>

**一个都不走栈。** 整型与浮点使用**两套独立的寄存器文件与独立的计数器**：6 个 `long` 依次进 `rdi, rsi, rdx, rcx, r8, r9`（正好用完 6 个整型槽），8 个 `double` 依次进 `xmm0`–`xmm7`（正好用完 8 个向量槽）。两边的「第几个」互不影响，所以第 7 个整型参数才落栈、第 9 个浮点参数才落栈。

把 4 个 `long` 改成 `int` 也**不会变**：`int` 仍属 INTEGER 类，仍占一个整型槽（用 `edi` 而不是 `rdi` 传，高 32 位未定义，被调用者按 32 位读）。真正的变化只发生在「超过 6 个整型」或「超过 8 个浮点」时。

推论：判断会不会走栈，要**分别数** INTEGER 类与 SSE 类的个数，而不是数参数总数。这也是 §11.7 里 8 个 `long` 会走栈、而 §11.4 里 4 个 `int` + 4 个 `double` 一个都不走栈的原因。

</details>

**Q2.** 8 MiB 栈、每帧 160 B，公式给出 52,428 层，实测 52,406 层。差的 22 帧去哪了？如果要让这个递归函数支持 4 倍深度，有哪四种改法，各自的代价是什么？

<details><summary>答案</summary>

差的 22 帧（22 × 160 = 3,520 B）不是「算错了」，而是公式漏了三项：① `main` 之前已经被 `argv`/`environ`/`auxv` 占掉的栈（量级 1–10 KiB）；② 最后一帧必须在写 guard page **之前**失败，探测写的两个字节之间还有空隙；③ 16 字节对齐把帧向上取整。所以公式是**上限**，实测永远略低（本例低 0.04%）。

四种改法：

1. **加大栈**：`ulimit -s 32768`（或 `setrlimit`/线程属性），深度线性 ×4。代价：每个线程的虚拟地址占用 ×4，且要改部署配置。线程栈在 `pthread_attr_setstacksize` 里设，默认常是 8 MiB。
2. **减小帧**：把 160 B 的局部数组改成「按需从堆分配」或复用调用者的缓冲区。代价：多一次 `malloc`/指针间接，缓存局部性变差。
3. **改迭代 + 显式栈**：自己维护一个 `malloc` 出来的数组当栈。代价：代码复杂度上升，但**深度只受堆限制**，且栈溢出变成可检查的返回值。
4. **尾递归化**：只有当递归调用是函数的最后一个动作、且编译器愿意 TCO 时才有效（`-O2` 实测 10⁷ 层通过，`-O0` 在 262,016 层崩）。代价：不能依赖标准保证，且只适用于直接自递归。

工程上正确的顺序是：先算「最坏深度 × 帧大小」看是否真会超，再选 1 或 3。**不要在没算过的情况下靠「加大 ulimit」蒙混**——那只是把崩溃点往后推，没有消除它。

</details>

**Q3.** 你发布了一个 C 库，头文件里有 `struct cfg { int timeout; int retries; };` 和 `long compute(struct cfg);`。三年后你想把 `retries` 改成 `long`。为什么不能直接改？如果必须改，给出一个既能让老二进制继续工作、又能让新代码用上新字段的方案。

<details><summary>答案</summary>

不能直接改，因为**布局是编译期约定，链接期不可见**：老调用方按「8 字节、两个 `int`、走 `rdi` 一个 eightbyte」编译，新库按「16 字节、`int` + 填充 + `long`、走 `rdi`+`rsi` 两个 eightbyte」读。链接器只检查符号名 `compute`，两边对得上，于是链接成功、运行错位——最坏的一种失败：不报错、不崩溃、答案错（§11.1 的 5030 就是这个形状）。

而且改 `retries` 的类型还会改变**传参分类**：8 字节时是 `INTEGER`（寄存器传），16 字节且含 `long` 时仍是两个 `INTEGER` eightbyte（还能走寄存器），但只要结构体超过 16 字节或有非整数成员，就整体变成 `MEMORY`（栈传），调用点的栈布局跟着变。**这是一次 ABI 断裂，不是一次源码修改。**

可行方案（同时满足新老两侧）：

1. **保留旧符号，新增版本化符号**：`compute`（旧布局）继续导出，内部转调 `compute_v2`；新头文件声明 `compute_v2(struct cfg_v2)`。老二进制按老符号链接，新代码按新符号链接。这是 glibc 的 `symbol versioning`（`.symver`）与 libstdc++ 的 `_GLIBCXX_USE_CXX11_ABI` 用的同一招。
2. **字段访问器 + 不透明结构体**：`struct cfg;` 只前向声明，提供 `cfg_set_timeout()`/`cfg_set_retries64()` 与 `cfg_create()`/`cfg_destroy()`。布局彻底藏进库，改多少次都不影响 ABI。代价：多一次函数调用，不能栈上分配。
3. **在头文件里钉死检查**：`_Static_assert(sizeof(struct cfg) == 8, ...)` + 版本宏（`CFG_ABI_VERSION`），让用错头文件的一侧**编译失败**，把静默错位变成编译错误。这只是防线，不是方案。

正确答案是 1 或 2，并且**在发布的第一天就选**——ABI 一旦发出去，就没有「悄悄改回来」这条路。

</details>
