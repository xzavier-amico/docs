## 03.1 引子：一次「补码背得很熟」的评审与一次线上事故

2025-09 中旬，某内容平台的排序服务上线「负反馈加权」。逻辑只有一行：拿模型原始分 `raw`，取负得到惩罚量，负则降权。

```c
int boost = -raw;              /* 原始分取负 = 惩罚量 */
if (boost < 0) return DROP;    /* 负分直接丢弃 */
```

上线 5 天后巡检发现：某品类 **43.6% 的候选从未进过曝光池**。

| 时间 | 事件 | 观测 |
| --- | --- | --- |
| 09-03 | 上线「负反馈加权」，`raw` 来自上游离线写入的 `INT` 列 | — |
| 09-08 | 曝光分布巡检：该品类 43.6% 候选 0 曝光 | 初判「模型分偏低」 |
| 09-10 | 抽样打印未曝光候选的 `raw` | 全部是 `-2147483648`（上游用它当「未设置」哨兵） |
| 09-11 | 本地复现：`printf("%d", -(-2147483648))` 输出 `-2147483648` | 取负没变号 → `boost < 0` 成立 → 全量 `DROP` |
| 09-11 | 统计影响面：41.2 万条候选、8 天、约 6,900 万次预期曝光被吞 | 线上事故定级 P2 |

同一周，同一份代码的评审记录里有两句话（我原样抄下来）：

> **评审 A**：「补码我知道，取反加一。所以 `INT_MIN` 取负就是 `INT_MAX` 吧？这里为什么还要判 `== INT_MIN`？」
> **评审 B**：「`(int)-1 < (unsigned)1` 应该是 `true` 才对啊，-1 当然小于 1。」

两条都错，而且错在同一处：**把补码当成一条口诀（取反加一），而不是当成「模 2ⁿ 环里的一个等价类」**。口诀只告诉你「怎么造出 -x 的位模式」，不告诉你「造出来的东西在环上还有没有对应物」、也不告诉你「两个不同类型的值比较前谁先被重新解释」。

| 说法 | 真实结果 | 原因（一句话） |
| --- | --- | --- |
| `-INT_MIN == INT_MAX` | 假，`-INT_MIN == INT_MIN` | `0x80000000` 在 32 位环上的补数就是它自己（`2³²-2³¹ = 2³¹`，超出上限，落回原位） |
| `(int)-1 < (unsigned)1` | 假 | 比较前 `int` 被转成 `unsigned`，`0xFFFFFFFF` = 4294967295，不小于 1 |
| 「最高位是符号位」 | 不成立 | 最高位只是**权值为 `-2ⁿ⁻¹`** 的一位；「符号」是解释出来的，不是标记出来的 |
| 「溢出是电路出错」 | 不成立 | 电路每次都算对了（它算的是 mod 2ⁿ）；越界的是**解释**，不是运算 |

本篇要交付的，就是把上面四条从「记」变成「推」：先建环（§03.2），再用加法器把减法白送掉（§03.3），然后解释为什么不用原码/反码（§03.4），接着拆掉「符号位」这个说法（§03.5），最后把三大坑——溢出、无符号比较、类型提升——全部落回同一张环图上（§03.6–03.7）。

## 03.2 模运算与环：时间能对上，是因为表盘只有 12 格

### 时钟模型：不需要「减法」这个动作

现在是 3 点。你要知道「5 小时前是几点」，两个办法：

- 数学上：`3 - 5 = -2`，然后映射成表盘上的 10。
- 机械上：**把时针倒着拨 5 格**，落在 10。或者更省事——**正着拨 7 格**，也落在 10。

后者才是硬件干的事：`-2 ≡ 10 (mod 12)`，所以「减 5」等价于「加 7」。表盘没有负数，也没有减法指针，只有「往前走」这一个动作和 12 这个模。**n 位加法器就是一张有 2ⁿ 格的表盘**：

```
                      0x00 = 0       ← (-1) + 1 正好落回这里
                 ┌───────┴───────┐
    0xFF ≡ -1    │               │    0x01 = 1
   (255 = 256-1) │   8 位环      │
                 │  256 个位模式  │
    0xFE ≡ -2    │  -x ≡ 256 - x │    0x02 = 2
   (254 = 256-2) │               │
                 └───────┬───────┘
                      0x80 ≡ -128
                    (128 = 256-128)
```

环上每一格是一个**位模式**；它「等于几」取决于你选哪套解释（§03.5 会讲有四种以上）。同一个 8 位环，把位模式当无符号读，它是一条从 0 到 255 的单调数轴；按补码读，它在 `0x80` 处**断成两段**：

```
数学值:   -1     0     1     2   ...   127  ┊  -128  -127  ...  -1
位模式:  0xFF  0x00  0x01  0x02  ...  0x7F  ┊  0x80  0x81  ... 0xFF
          └──── 无符号读数 0..127 ────────┘  └──── 无符号读数 128..255 ──┘
                  （补码段 A：0 和正数）            （补码段 B：负数）
```

**这张图就是「符号位」的全部真相**：`0x7F` 加 1 变成 `0x80`，无符号读数从 127 涨到 128，补码读数却从 127 掉到 -128——因为 `0x80` 的最高位从 0 跳到 1，而最高位的权值是负的。所谓「符号位翻转」，只是这条断层的视觉别名。

### 三条必须能背下来推的公式

设位宽为 n，模 `M = 2ⁿ`：

| 事实 | 8 位 | 32 位 | 64 位 |
| --- | --- | --- | --- |
| 模 `M = 2ⁿ` | 256 | 4,294,967,296 | 18,446,744,073,709,551,616 |
| 状态数（位模式个数） | 256 | 4,294,967,296 | 1.845×10¹⁹ |
| `-1` 的位模式 | `0xFF` = 255 | `0xFFFFFFFF` = 4,294,967,295 | `0xFFFF…FF` |
| `-x ≡ M - x` | `256 - x` | `2³² - x` | `2⁶⁴ - x` |
| 补码可表示范围 | -128 … 127 | -2,147,483,648 … 2,147,483,647 | -9.22×10¹⁸ … 9.22×10¹⁸ |
| 有多少个「负数」 | 128 个 | 2,147,483,648 个 | 9.22×10¹⁸ 个 |
| 有多少个「非负数」 | 128 个（含 0） | 2,147,483,648 个（含 0） | 9.22×10¹⁸ 个（含 0） |

三行推导，全部只用「模」这一个概念：

1. **`-x ≡ M - x`**：因为 `x + (M - x) = M ≡ 0 (mod M)`。这就是全部。`-1 ≡ 256 - 1 = 255 = 0xFF`。
2. **负数比非负数多一个**：`2ⁿ` 个位模式要覆盖 `0` 和正负两边，`0` 占了中间一格，剩下的奇数个只能一边多一个。补码选择「负数多一个」，代价是最小负数**取不到相反数**（§03.6 的坑表第一行）。
3. **`-0` 不存在**：`0x00` 的补数 = `~0x00 + 1` = `0xFF + 1` = `0x1_00`，截 8 位 = `0x00`。环上 `0` 的对面只有它自己。**这一条是补码相对原码/反码最大的便宜**（§03.4）。

> 顺带说清一件事：`Z/2ⁿZ` 是**环**不是**域**——2 在 mod 2ⁿ 下没有逆元（`2k ≡ 1 (mod 2ⁿ)` 无解），所以「除以 2」在环上不成立，除法的行为必须由语言额外规定（向零取整、余数带被除数符号）。这属于 `base/04`，本篇只留一句：**能在环上白送的是加减，除法的所有坑都源自「2 不是可逆元」。**

## 03.3 用加法器白送减法：`a - b = a + (~b) + 1` 的完整推演

### 第一步：先造出 `-b`

取 `b = 30 = 0b0001_1110`。按 §03.2 第 1 条，`-30 ≡ 256 - 30 = 226 = 0b1110_0010`。机器怎么造 226？**按位取反再加一**：

```
   b    = 0001 1110        (30)
  ~b    = 1110 0001        (225 = 255 - 30)
  ~b+1  = 1110 0010        (226 = 256 - 30)   ← 这就是 -30 的位模式
```

注意 `~b = 255 - b` 这一步为什么成立：8 位全 1 是 255，逐位取反等价于「用 255 去减」。于是 `~b + 1 = (255 - b) + 1 = 256 - b`——**取反加一的代数内容就是「对 2ⁿ 取补」**，口诀与公式在这里对上了。

### 第二步：把减法变成加法，看竖式

```
   a    = 0011 0101        (53)
  -b    = 1110 0010        (226)
  ─────────────────────
  和    = 1 0001 0111      (279，第 9 位 = 256)
  取低 8 位 = 0001 0111    (23 = 53 - 30 ✓)
           ↑ 第 9 位那个 1 被硬件直接丢掉，它就是 2⁸ = 模
```

也可以用「先加 `~b`、再喂一个最低位进位」的形式看，这就是电路真正做的事：

```
   a    = 0011 0101        (53)
  ~b    = 1110 0001        (225)
  cin   =          1        (SUB 指令把加法器的最低位进位钉成 1)
  ─────────────────────
  和    = 1 0001 0111      (279 → 低 8 位 23)
```

**结论只有一句：那个被丢掉的第 9 位，正是我们想丢的 `2⁸`。** 硬件「算错」的那部分（多出来一个 256）和「mod 256」正好抵消，所以结果精确。减法没有发生，发生的是「加上一个补数，然后扔掉模」。

### 第三步：这就是补码存在的唯一目的

补码不是为了「让负数好看」，是为了**让同一套加法器通吃加减法**。它的物理契约是：

- **一条控制线**：`SUB` 时把 B 操作数逐位取反（n 个 XOR 门），并把最低位进位 `cin` 钉成 1；`ADD` 时 B 直通、`cin = 0`。
- **一个加法器**：所有算术都走它。`sub`、`neg`、`cmp`、`inc`、`dec` 都是同一条加法链的不同入口。

```
        A ──────────────┐
                        ├──► [ 加法器 ] ──► S (+ 进位 out)
        B ──► XOR(n) ────┘        ▲
                ▲                 │
             SUB 控制线 ──────────┘（SUB=1 时 B 取反、cin=1）
```

**成本账（量级结论，来自教学模型）**：32 位行波进位加法器 = 32 个全加器，每个全加器 ≈ 5 个二输入门（2 XOR + 2 AND + 1 OR），合计 ≈ 160 门。让它兼做减法，只要再加 **32 个 XOR + 1 条进位控制** ≈ 33 门，约等于加法器本身的 **20%**。反过来，如果单独做减法器，就要一个**大小比较器**（判断 `|a| ≥ |b|`）加一套**条件求补**，那是另一个功能块、另一条关键路径，而且是「减法才用得上」的闲置面积。**补码把 100% 的硬件复用率换成了 20% 的加法器增量。**

### 第四步：为什么只有一个 0

| 编码（8 位） | `+0` 的位模式 | `-0` 的位模式 | 零的个数 |
| --- | --- | --- | --- |
| 原码（符号-数值） | `0000 0000` | `1000 0000` | 2 |
| 反码 | `0000 0000` | `1111 1111` | 2 |
| **补码** | `0000 0000` | 不存在（`~0+1` 溢出成 `0000 0000`） | **1** |

一个零值听起来只是「省了一格」，实际后果是一条**最常用的推论变得无条件成立**：`a + b == 0` ⟺ `a == -b`。在反码里，`a + (-a) = 0xFF…FF = -0`，与 `+0` 位模式不同，于是任何「用求和判相等、用求和判抵消」的代码都必须多一次归一化；在补码里 `a + (-a)` 精确等于 `0x00…00`，硬件零成本。**这一个 bit 的便宜，被全世界的比较、哈希、序列化、查表一起赚走了。**

### 第五步：跑出来验证（真实输出）

把「只有加法器」写成代码，跑遍 8 位全空间 65,536 组 `(a, b)`：

```c
#include <stdio.h>
int main(void) {
    int bad = 0;
    for (int a = 0; a < 256; a++) {
        for (int b = 0; b < 256; b++) {
            unsigned char diff = (unsigned char)(a - b);              /* 真减法（模 256） */
            unsigned char addc = (unsigned char)(a + (~b & 0xFF) + 1); /* 只有加法器 */
            if (diff != addc) bad++;
        }
    }
    printf("8 位全空间 65536 组 (a,b)：不相等组数 = %d\n", bad);
    return 0;
}
```

```
8 位全空间 65536 组 (a,b)：不相等组数 = 0
```

**65,536 组零例外**——`a + (~b) + 1` 与 `a - b` 在 mod 256 上恒等。这不是巧合，是 §03.2 第 1 条的代数恒等式在全部输入上的展开。

再加一条时间证据：同一个 `volatile` 累加器跑 2×10⁸ 次，分别做 `+`、`-`、`^`：

| 运算 | 总耗时 | 每次迭代 | 说明 |
| --- | --- | --- | --- |
| `acc = acc + k` | 0.496 s | 2.48 ns | — |
| `acc = acc - k` | 0.494 s | 2.47 ns | 与加法**在测量噪声内相同** |
| `acc = acc ^ k` | 0.496 s | 2.48 ns | 逻辑运算同一量级 |

推导一下这 2.48 ns 是什么：@3.3 GHz 一个周期 = 0.30 ns，2.48 ns ≈ 8.2 周期——这是 `volatile` 那条 **load→ALU→store 的访存往返**，不是 ALU 本身。ALU 的加法是 1 周期，被访存完全遮住。**所以「减法比加法慢」在任何一台现代 CPU 上都测不出来——它们根本不是两条指令，是同一个电路的两个入口。**

## 03.4 为什么不是原码、反码：三条被历史淘汰的代价

历史上有三套主流编码，用同一批位模式（8 位）摆在一起对比：

| 位模式 | 无符号读数 | 原码（符号-数值） | 反码（ones' complement） | 补码（two's complement） |
| --- | --- | --- | --- | --- |
| `0x00` | 0 | +0 | +0 | 0 |
| `0x01` | 1 | +1 | +1 | 1 |
| `0x7F` | 127 | +127 | +127 | 127 |
| `0x80` | 128 | **-0** | -127 | **-128** |
| `0x81` | 129 | -1 | -126 | -127 |
| `0xFE` | 254 | -126 | -1 | -2 |
| `0xFF` | 255 | -127 | **-0** | -1 |

三列差异对应三条代价，每一条都是硬件的钱：

**① 两个零 → 比较与相等判断都要多一道。** 原码里 `+0 = 0x00`、`-0 = 0x80`；反码里 `+0 = 0x00`、`-0 = 0xFF`。于是「`x == 0`」不能只比一次，要写成「低 7 位全 0」的掩码比较（多一个 AND 加一次比较），而 `a + b == 0` 不再等价于 `a == -b`。补码只有一格零，这条推论无条件成立。

**② 减法必须额外判断符号 → 关键路径上多一级比较器。** 原码做 `a - b`，要对齐的是「绝对值相减 + 符号由谁大决定」：需要一个 n 位大小比较器（`log₂n` 级：32 位约 5 级门），再按比较结果条件求补。也就是说原码的减法器**不是加法器**，是一条「比较 → 选择 → 相减 → 定符号」的组合逻辑。补码的减法器**就是加法器**（§03.3）。

**③ 反码的端回绕进位要二次加。** 反码加法里，最高位的进位不能丢，要**加回到最低位**（end-around carry）：`x + ~x = 0xFF = -0`，想让它是 `+0` 就得再补一次。硬件上有两种做法，都贵：串行做两趟加法（关键路径 ×2，最坏 2n 级门），或者预判「是否全 1」提前补偿（多一条检测链）。**补码的进位直接丢掉就对了——而「丢掉」是零成本的，因为加法器本来就只有 n 位输出。**

| 判据 | 原码 | 反码 | 补码 |
| --- | --- | --- | --- |
| 零的个数 | 2 | 2 | **1** |
| 可表示范围（8 位） | -127 … 127 | -127 … 127 | **-128 … 127** |
| 加减法共用加法器 | 否（需比较器 + 条件求补） | 是（但需端回绕进位） | **是（进位直接丢）** |
| 减法关键路径 | 加法级 + 比较级 | 加法级 ×2（最坏） | **1 个加法级** |
| `-x` 怎么造 | 只翻最高位 | 逐位取反 | 逐位取反再加 1 |
| 是否被现代通用 CPU 采用 | 否（历史上部分机型用） | 否 | **是（x86/ARM/RISC-V 全部）** |

补码唯一让步的地方，是**范围不对称**：8 位能表示 `-128` 但表示不了 `+128`，32 位能表示 `-2147483648` 但表示不了 `+2147483648`。这个「多出来的一个负数」就是 §03.1 那场事故的全部弹药——**它没有相反数**。

## 03.5 「符号位」不是符号位：它只是权值为 `-2ⁿ⁻¹` 的那一位

教科书常说「最高位是符号位」，这句话在描述**现象**，不在描述**机制**，用它推推论会立刻翻车。真正的定义是一个求和式（n 位补码，`bₙ₋₁` 为最高位）：

```
x = -bₙ₋₁ · 2ⁿ⁻¹  +  Σ (i = 0 … n-2) bᵢ · 2ⁱ
```

也就是：**除最高位以外的位都是正的权，最高位的权是负的。** 代入 `0x80 = 1000_0000`：`-1×2⁷ + 0 = -128`。如果按「符号位 + 数值位」理解，会得到「-0」——一个根本不存在的值。再看 `0xFF = 1111_1111`：`-128 + 64 + 32 + 16 + 8 + 4 + 2 + 1 = -1`。「符号位」这个说法完全没有出现在这个计算里，它是结果的**副产品**：只有当最高位为 1 且其余位不足以把总值抬回非负时，结果才是负的。

| 说法 | 能否推导 | 反例 |
| --- | --- | --- |
| 「最高位是符号位」 | 不能 | `0x80` 按此读得「-0」，而 `-0` 不存在 |
| 「最高位权值是 `-2ⁿ⁻¹`」 | 能，可算任意位模式 | 无 |
| 「符号位为 1 ⟺ 负数」 | **能**（在上面那条定义下等价） | 无（这是推论，不是定义） |
| 「取负就是翻符号位」 | 不能 | `-0x80` 翻最高位得 `0x00`，但 `-(-128)` 应是 128（不可表示），实际仍为 `-128` |

### 同一串位模式的四种解释

取 `0xFFFFFFFF`（4 个字节全是 1）。**位模式一个都没变，含义有四种以上**：

| 解释框架 | 值 | 依据 |
| --- | --- | --- |
| 32 位有符号（补码） | `-1` | `-1·2³¹ + Σ 2ⁱ = -1` |
| 32 位无符号 | `4294967295` | `Σ 2ⁱ = 2³²-1` |
| IEEE 754 binary32 | **NaN**（符号 1、指数全 1、尾数非 0） | 指数域 `0xFF` = 255 = 最大值，尾数 `0x7FFFFF ≠ 0` → NaN |
| 4 个字节 | `FF FF FF FF` | 与整数解释无关，只是 4 个 8 位值 |
| UTF-8 字节流 | 非法序列 | `0xFF` 不是合法首字节（合法首字节最高位模式受限） |
| 32 位地址 | `4 GiB - 1` | 与「-1」无关，地址就是无符号偏移 |

这张表要记住的不是六个答案，而是**一句话：`0xFFFFFFFF` 没有「真正的值」，只有「在某套约定下的值」**——这正是全书主线①「没有魔法，只有位与约定」在位层的第一个落点。凡是出现「这个数怎么会变成那个数」的疑问，先问：**谁在哪一层重新解释了它？**

### 类型转换 = 换解释，不是换位

C 的整数转换规则里，`int` → `unsigned` 是**位模式原样保留、解释换一套**（不是取绝对值，也不是加个负号）。汇编里能直接看到这两种转换的物理差别：

```asm
# long widen(int x) { return x; }            ← 有符号扩宽：补符号位
   1f: mov    -0x4(%rbp),%eax
   22: cltq                                    ← sign-extend：用最高位填满高 32 位
   24: pop    %rbp

# unsigned long widen_u(int x) { return (unsigned)x; }  ← 先按无符号解释再扩宽
   2d: mov    -0x4(%rbp),%eax
   30: mov    %eax,%eax                        ← 零扩展：高 32 位直接清零
```

两条指令的差别就是「高 32 位填 1 还是填 0」。`x = -1` 时，前者得到 `0xFFFFFFFFFFFFFFFF`（-1），后者得到 `0x00000000FFFFFFFF`（4294967295）。**「类型提升」这个词听着像算术，它其实是「往高位补什么」这一个选择**（`base/04` 会把这张选择表铺满）。

## 03.6 溢出：电路从不出错，出错的是解释

### 定义：溢出不是「算错了」，是「算对了但不代表」

n 位加法器**永远**算的是 `(a + b) mod 2ⁿ`，它一次都没算错。所谓「溢出」，是**真实数学结果落到了可表示区间之外**——这是解释层的事实。所以判断溢出不能看结果位模式，只能额外比较「符号位进位」和「次高位进位」。

### 检测：`cin_MSB XOR cout_MSB`（硬件里就是 OF 标志）

设 `a, b` 为 n 位，`S = (a + b) mod 2ⁿ`。记 `cout` 为**出了最高位**的进位、`cin` 为**进到最高位**的进位，则：

```
有符号溢出  ⟺  cout ⊕ cin = 1        （x86 的 OF 标志）
无符号溢出  ⟺  cout = 1               （x86 的 CF 标志）
```

道理：最高位是唯一的「负权」位。当进到它的进位与出它的进位不一致时，负权的贡献被翻转了两次，「符号」就翻了——正 + 正得负、负 + 负得正。四种组合的实测对照（8 位）：

| 操作（位模式） | 数学结果 | 结果位模式 | CF（无符号溢出） | OF（有符号溢出） | 谁觉得出事了 |
| --- | --- | --- | --- | --- | --- |
| `0xC8 + 0x64`（200 + 100） | 300 | `0x2C`（-56） | 1 | 0 | 只有无符号 |
| `0x64 + 0x64`（100 + 100） | 200 | `0xC8`（-56） | 0 | 1 | 只有有符号 |
| `0xC8 + 0x37`（200 + 55） | 255 | `0xFF`（-1） | 0 | 0 | 都没事 |
| `0x80 + 0xFF`（-128 + -1） | -129 | `0x7F`（127） | 1 | 1 | 两个都出事 |

第三行值得单独看：`200 + 55 = 255`，位模式 `0xFF`。作为无符号它是 255（刚好没溢出），作为有符号它是 -1（`-56 + 55 = -1`，也没溢出）。**同一串位、零个错误、两种解释、两个「没事」**——因为溢出是解释的属性，不是位的属性。

跑遍全空间的实测（真实输出）：

```
int8 全空间 65536 组：XOR 检测与真实溢出不一致 = 0，真实溢出组数 = 16384
```

两个数字都要记住：**XOR 检测零例外**（它是定理，不是经验），以及**16,384 / 65,536 = 25%**——在 `[-128,127]` 上均匀随机取两个数相加，**四分之一**会溢出。它不是边角料。

### 三种语言，三种态度

| 语言 | 有符号溢出 | 无符号溢出 | 溢出检测手段 |
| --- | --- | --- | --- |
| **C / C++** | **未定义行为（UB）**：编译器可假设「不会发生」 | 定义良好：按 mod 2ⁿ 回绕 | `__builtin_add_overflow`、`-fsanitize=signed-integer-overflow`、`-ftrapv` |
| **Java** | 定义良好：静默回绕（JLS 15.18.2） | 无无符号类型（有 `Integer.compareUnsigned` 等） | `Math.addExact` / `multiplyExact`（抛异常）、`Math.toIntExact` |
| **Go** | 定义良好：**静默回绕**（规范明确「有符号整数运算可以溢出，结果确定存在」） | 同样回绕 | 手写检查或 `math/bits`；`go vet` 不查算术溢出 |

C 这一行的严重性要展开一句：**因为有符号溢出是 UB，编译器可以把「溢出检测代码」优化掉。** 经典的例子是 `if (x + 1 < x) { /* 溢出 */ }`——编译器推导「有符号加法不会溢出」，于是 `x + 1 < x` 恒假，整段删除。这就是为什么正确的检测必须**换到无符号域或使用内建函数**，而**不能**靠「算完了再看结果对不对」。

```c
int r = 12345;
int of = __builtin_add_overflow(2147483647, 1, &r);      /* 有符号：OF=1，r 未必写回 */
unsigned ur = 0;
int of2 = __builtin_add_overflow(4294967295u, 1u, &ur);  /* 无符号：OF=1，ur = 0 */
```

```
__builtin_add_overflow(INT_MAX,1) -> ovf=1, r=12345 (0x00003039)   ← 溢出时不保证写回
__builtin_add_overflow(UINT_MAX,1) -> ovf=1, r=0
```

注意第一行：`r` 仍是初始值 `12345`，因为溢出时它**不会**替你写一个「看起来对」的结果。这正是内建函数的设计意图——**先问「会不会溢出」，再去取值**，而不是「先取一个被模掉的值，再猜它对不对」。

### 为什么 `(int)-1 < (unsigned)1` 是假

回到 §03.1 那条评审意见。C 的「通常算术转换」规定：`int` 与 `unsigned` 同时出现时，`int` **先被转成 `unsigned`**，然后做**无符号比较**。于是：

```
(int)-1            = 0xFFFFFFFF  → 转 unsigned → 4294967295
(unsigned)1        = 0x00000001  →             1
4294967295 < 1     = 假
```

汇编里看得一清二楚：`cmp` 之后用 `setb`（**below**，无符号语义），不是 `setl`（less，有符号语义）：

```asm
# int cmp(int a, unsigned b) { return a < b; }
   d: mov    -0x4(%rbp),%eax        ← int a
  10: cmp    -0x8(%rbp),%eax        ← 与 unsigned b 比较
  13: setb   %al                    ← b = below：CF=1 才置 1（无符号比较）
  16: movzbl %al,%eax
```

**`-1` 的位模式是 `0xFFFFFFFF`，在无符号解释下它是「最大的那个数」——所以它不小于 1，它大于一切。** 这条规则的伤害面比它看起来大得多：任何 `int` 与 `size_t`（长度、`sizeof`、`vector::size()`）的比较，负值都会跳变成 10¹⁹ 量级。

## 03.7 常见坑表：现象 → 位模式原因 → 正确写法

| 现象 | 位模式原因 | 正确写法 |
| --- | --- | --- |
| `-INT_MIN == INT_MIN`（取负没变号） | `0x80000000` 的补数是它自己：`2³² - 2³¹ = 2³¹`，超出上限，绕回原位 | 先判 `x == INT_MIN` 走特殊分支；或全程用 `int64_t` 承载 |
| `abs(INT_MIN) < 0`（绝对值仍是负） | 同上；`abs` 的定义要求结果非负，而结果取不到 | `llabs((long long)x)`（范围够）／显式判 `INT_MIN` |
| `if (x < 0)` 对 `size_t` 永远为假 | 无符号没有负数，编译器直接删掉该分支（`-Wtype-limits` 会警告） | 先判 `(ptrdiff_t)x < 0`，再转 `size_t` |
| `for (size_t i = n-1; i >= 0; i--)` 死循环 | `i >= 0` 对无符号恒真；`0` 再减一绕到 `2⁶⁴-1` | `for (size_t i = n; i-- > 0;)`，或改用有符号下标 |
| 有符号长度做边界检查被绕过 | `len + 16` 先溢出成负数，`<= 64` 反而成立 | 先扩宽（`int64_t`/`size_t`）再比较；或先比较后相加 |
| `a - b` 明明该为负，却打印成 4,294,967,295 | 无符号减法在环上绕一圈，`-1` 的位模式就是最大无符号数 | 用 `int64_t` 存差值，或两边都先转有符号 |
| `x % 8` 对负 `x` 得负数 | C 的除法向零取整，余数带被除数符号（`-7 % 8 = -7`，不是 1） | `(unsigned)x & 7`（环上与 mod 8 等价），或先加 8 再取 |
| 打印 `uint64` 用 `%d` 得到负数 | 位模式相同、`printf` 按 32 位有符号解释低半部分 | 用 `%llu` / `PRIu64`，并显式转换 |

第五行值得单独讲机制（**只讲机制，不讲利用**）：这一类「边界检查被算术溢出绕过」是真实存在的一整类漏洞。它的形状固定——**检查用有符号算术、使用用无符号长度**，于是「检查时算出来的值」和「真正被当成长度的位模式」不是同一个。真实输出：

```
len = 2147483639
check_bad(len)  = 1  (len+16 绕成 -2147483641)     ← 检查通过
check_good(len) = 0                                 ← 先把 len 当长度比，拒绝
```

`check_bad` 的 `len + 16 <= 64` 在 `len = INT_MAX - 8` 时溢出成负数，条件成立；随后这个 `len`（或 `len + 16`）被当作 `size_t` 使用，位模式就是 `0xFFFFFFFF…`。**根因不是「忘了检查」，是「检查的算术域」和「使用的算术域」不一致。** 正确写法只有一条：**先把长度扩到能容纳最坏中间结果的位宽，再比较，再使用**。

## 03.8 实验：把上面每句话跑出来

### 实验①：`INT_MIN` 的取负、`INT_MAX + 1`、混类型比较、无符号回绕

```c
#include <stdio.h>
#include <limits.h>
int main(void) {
    int i_min = INT_MIN, i_max = INT_MAX;
    unsigned u_max = UINT_MAX, one = 1u;
    printf("INT_MIN      = %11d   0x%08X\n", i_min, (unsigned)i_min);
    printf("INT_MAX      = %11d   0x%08X\n", i_max, (unsigned)i_max);
    printf("-INT_MIN     = %11d   0x%08X\n", -i_min, (unsigned)(-i_min));
    printf("INT_MAX + 1  = %11d   0x%08X\n", i_max + 1, (unsigned)(i_max + 1));
    printf("(int)-1 < (unsigned)1  ->  %s\n", ((int)-1 < (unsigned)1) ? "true" : "false");
    printf("(unsigned)(int)-1 == 0xFFFFFFFF -> %s\n", ((unsigned)(int)-1 == 0xFFFFFFFFu) ? "true" : "false");
    printf("UINT_MAX + 1 = %11u   0x%08X\n", u_max + one, u_max + one);
    return 0;
}
```

`gcc -O0 -fwrapv` 编译（`-fwrapv` 把有符号回绕钉成「位模式标准行为」，方便观察；生产代码不要依赖它）：

```
INT_MIN      = -2147483648   0x80000000
INT_MAX      =  2147483647   0x7FFFFFFF
-INT_MIN     = -2147483648   0x80000000   ← 取负后位模式没变
INT_MAX + 1  = -2147483648   0x80000000   ← 涨到顶绕回底
(int)-1 < (unsigned)1  ->  false
(unsigned)(int)-1 == 0xFFFFFFFF -> true
UINT_MAX + 1 =           0   0x00000000   ← 模 2³² 归零
```

四行就是四个推论：`-INT_MIN` 不变号（最小负数无相反数）、`INT_MAX + 1` 落到 `INT_MIN`（环上相邻）、混类型比较按无符号（`0xFFFFFFFF` 最大）、无符号加满归零（`2³² ≡ 0`）。

### 实验②：`abs(INT_MIN)` 与「用更宽的宽度救回来」

```c
printf("abs(INT_MIN)       = %d  (0x%08X)\n", abs(INT_MIN), (unsigned)abs(INT_MIN));
printf("llabs((long long)) = %lld\n", llabs((long long)INT_MIN));
```

```
abs(INT_MIN)       = -2147483648  (0x80000000)     ← 绝对值仍是负的
llabs((long long)) = 2147483648                     ← 换到 64 位就取出来了
```

**32 位里取不出来的绝对值，64 位里取得出来**——这就是「溢出是位宽问题」最便宜的实证。

### 实验③：`sub` / `neg` 与 `add` 是同一套电路（`objdump -d`）

```c
int sub_a(int a, int b) { return a - b; }
int sub_b(int a, int b) { return a + (~b) + 1; }
int neg_b(int a)        { return ~a + 1; }
int neg_a(int a)        { return -a; }
```

`gcc -O1 -c` 后反汇编，两组函数生成**逐字节相同**的机器码：

```
0000000000000000 <sub_a>:
   0:	mov    %edi,%eax
   2:	sub    %esi,%eax
   4:	ret
0000000000000005 <sub_b>:        ← 编译器认出了 a+(~b)+1 ≡ a-b
   5:	mov    %edi,%eax
   7:	sub    %esi,%eax
   9:	ret

000000000000000a <neg_b>:
   a:	mov    %edi,%eax
   c:	neg    %eax              ← ~a+1 与 -a 同一条指令
   e:	ret
000000000000000f <neg_a>:
   f:	mov    %edi,%eax
  11:	neg    %eax
  13:	ret
```

`sub_b` 与 `sub_a` 一模一样，这是编译器层面的恒等式证明；而 `sub`/`neg` 在微架构里都**落到同一条加法链**上（`sub` = B 取反 + `cin=1`，`neg` = `0 - a`）。x86 还留着 `ADC`/`SBB`（带进位加/借）两个指令，正是这条进位链暴露在外面的证据。另外 `a + (-1)` 在 `-O1` 下被编成 `lea -0x1(%rdi),%eax`——编译器连加法器都不肯用，直接走地址生成单元（AGU），**因为加减本就是同一种地址算术**。

### 实验④：Go 的静默回绕，以及 Go 抓得住的一种情况

```go
package main

import "fmt"

func main() {
	var i8 int8 = 127
	var u8 uint8 = 255
	var i32 int32 = 2147483647
	var mn int8 = -128
	fmt.Printf("int8(127)   + 1 = %4d   位模式 0x%02X\n", i8+1, uint8(i8+1))
	fmt.Printf("uint8(255)  + 1 = %4d   位模式 0x%02X\n", u8+1, uint8(u8+1))
	fmt.Printf("int32(MAX)  + 1 = %11d   位模式 0x%08X\n", i32+1, uint32(i32+1))
	fmt.Printf("-int8(-128)     = %4d   位模式 0x%02X\n", -mn, uint8(-mn))
}
```

```
int8(127)   + 1 = -128   位模式 0x80
uint8(255)  + 1 =    0   位模式 0x00
int32(MAX)  + 1 = -2147483648   位模式 0x80000000
-int8(-128)     = -128   位模式 0x80
```

Go **有符号也回绕**（规范保证，无 UB），所以线上不会出现「C 编译器把检查删了」那种惊喜；但代价是**运行时不会替你报错**。有意思的是：把 `-int8(-128)` 写成**常量表达式**时，Go 在编译期就拒绝：`constant 128 overflows int8`。**同一件事，常量路径报错、变量路径静默**——所以 Go 的安全网在常量折叠上，不在运行时。

## 03.9 三列账：补码承诺了什么、收了多少、从哪开始失效

| 维度 | 承诺了什么 | 为此付了什么 | 从哪里开始失效 |
| --- | --- | --- | --- |
| 加减法共用电路 | 一套加法器通吃 `+`/`-`/`neg`/`cmp`/`inc` | 加法器 +20% 门（32 个 XOR + 1 条进位线）；最高位权值为负 | 一旦需要「绝对值和符号」，就得重新判断（`abs(INT_MIN)`） |
| 唯一的零 | `a + b == 0` ⟺ `a == -b`，无条件成立 | 范围不对称：负数比正数多一个 | 最小负数无相反数：`-INT_MIN`、`abs(INT_MIN)`、`|x|` 全失效 |
| 溢出的可见性 | 无符号溢出 = 丢掉最高进位，永远可判定（CF） | 有符号溢出需要额外看 XOR（OF），C 里甚至是 UB | 任何「先算后查」的检测写法，可能被编译器整体删除 |
| 解释与位模式解耦 | 同一串位可有多种含义（int/uint/float/字节/地址） | 每次跨解释都要显式约定（打印格式、序列化、ABI） | `%d` 打 `uint64`、把 `int` 直接当长度用、把位模式当数学值 |
| 类型提升 | 让不同类型能参与同一运算 | 比较前偷偷换解释（`int`→`unsigned`） | `x < 0` 与 `size_t` 混用；`-1` 变成最大无符号数 |
| 跨语言一致 | 位模式语义在 C/Java/Go 上其实是同一台机器 | 语义责任不同：C 是 UB、Java/Go 是回绕 | 把 C 的回绕行为当保证；或把 Java/Go 的回绕当「不可能发生」 |

一句话收束：**补码买到的是「一套加法器 + 一个零」，付出的是「范围不对称 + 解释与位模式必须始终分清」。** 三大坑（溢出、无符号比较、类型提升）不是三个 bug，是后一笔代价的三个出口。

## 03.10 踩坑清单：现象 → 根因 → 怎么定位 → 怎么修 → 怎么防复发

| 现象 | 根因（指回本篇） | 定位命令 | 怎么修 | 怎么防复发 |
| --- | --- | --- | --- | --- |
| 取负后值不变，降权逻辑翻车 | 最小负数在环上是自己的补数（§03.2 第 2 条） | 在可疑处打印 `x` 与 `-x` 的 `%d` 和 `0x%08X` | 显式判 `x == INT_MIN`；或换 `int64_t` | 用哨兵值时禁止用「极值」；CI 里加 `INT_MIN`/`INT_MAX` 边界用例 |
| 某分支永远不进（或永远进） | 无符号比较把负数变最大值（§03.6 末节） | `gcc -Wall -Wextra` 看 `-Wsign-compare`；`objdump` 看 `setb`/`setl` | 统一符号性；先把 `int` 判负再转 `size_t` | 编译选项加 `-Wsign-compare -Wtype-limits -Werror` |
| 倒序循环卡死，CPU 100% | `i >= 0` 对无符号恒真，`0-1` 绕到 `2⁶⁴-1`（§03.2） | `gdb` 看 `i` 的值为 `18446744073709551612` | 改 `for (size_t i = n; i-- > 0;)` | Code review 清单里禁「无符号倒序」写法 |
| 溢出检测代码「没生效」 | 有符号溢出是 UB，编译器删掉了检查（§03.6） | `gcc -fsanitize=signed-integer-overflow` 或 `-ftrapv` | 用 `__builtin_*_overflow`／无符号域比较 | CI 加 UBSan 全量跑；禁写 `x + 1 < x` 这类检查 |
| 长度检查被绕过（安全类） | 检查用有符号、使用用无符号（§03.7 第五行） | 静态扫描「算术在 `int`、`memcpy` 收 `size_t`」的调用点 | 先扩宽再比较再使用，一次都不混 | 引入 `size_t` 参数的中间层；Fuzz 输入极值长度 |
| 打印值对不上（4294967295 或负数） | 位模式相同、解释不同（§03.5） | `printf("%zu/%llu/%d")` 逐个对照 | 用 `PRIu64` 等带宽度宏，且显式转换 | 编译加 `-Wformat=2` |
| 跨语言/跨进程传值变成负数 | 序列化时按不同宽度或符号写出（§03.5） | 对比两端的 hexdump | 协议层固定「宽度 + 符号」，一律 zigzag 或 varint | 接口文档规定字段宽度与符号性；测试用极值样本 |

三行总结这一张表：**看到「值突然变得极大」，先怀疑无符号解释；看到「值突然变成负数」，先怀疑位宽与符号扩展；看到「检查写了却不生效」，先怀疑 UB 被优化掉。**

## 03.11 一页速记

```
【一句话】补码不是口诀，是环：位模式 ∈ Z/2ⁿZ，负数只是一个等价类的别名。

【三条公式】
  ① -x ≡ 2ⁿ - x              （环上取补；取反加一只是它的机械实现）
  ② 补码读数 = -bₙ₋₁·2ⁿ⁻¹ + Σ bᵢ·2ⁱ   （最高位权值为负，不是「符号标记」）
  ③ 有符号溢出 ⟺ cin_MSB ⊕ cout_MSB    （x86 的 OF；无符号溢出就是 CF）

【三个数字】
  8 位：256 格，-128…127；32 位：2³²=4,294,967,296 格，-2,147,483,648…2,147,483,647
  int8 均匀随机两数相加，25% 会溢出（实测 16384/65536）

【为什么要补码】
  加法器 +20% 的门（32 个 XOR + 1 条进位线）→ 减法免费、零只有一个、比较就是减法
  代价：范围不对称，最小负数没有相反数

【四个坑的同一条根】
  溢出       = 解释越界，电路没错           → 用 __builtin_*_overflow
  无符号比较 = 比较前被换了解释             → 统一符号性
  类型提升   = 换解释而不是换值             → 扩宽后比较
  1 个 0xFFFFFFFF = int -1 / uint 4294967295 / float NaN / 四个 0xFF 字节
```

## 03.12 自检 3 题

**Q1.** 用 8 位环推出 `-(-128)` 的结果，并解释「取反加一」这条口诀在这里为什么没错、但结论必须自己算。顺便说明：为什么「最小负数取负」在 32 位里也是同一个答案？

<details><summary>答案</summary>

`-128` 的位模式是 `0x80`。取反：`~0x80 = 0x7F`（127），加一：`0x7F + 1 = 0x80`（128 → 8 位装不下，绕回 `0x80`）。所以 `-(-128)` 的结果位模式仍是 `0x80`，还是 `-128`。

口诀完全没错——它机械地执行了「取补」这个动作，`2⁸ - 128 = 128 ≡ 0x80`。错的是**把结果当成数学值**：`+128` 在 8 位补码里不可表示，环上「`0x80` 的对面」这个位置不存在，落回自己。

32 位同理：`0x80000000` 取补 = `~0x80000000 + 1 = 0x7FFFFFFF + 1 = 0x80000000`。区别只是模变成了 `2³²`：`2³² - 2³¹ = 2³¹`，而 `+2³¹` 超出上限 `2³¹-1`，绕回 `-2³¹`。**这是「负数比正数多一个」这条代价的唯一出口。**
</details>

**Q2.** `(int)-1 < (unsigned)1` 为什么是假？请写出两边在比较那一刻的位模式，并说出 x86 上它对应哪条 `set` 指令、为什么不是另一条。

<details><summary>答案</summary>

C 的通常算术转换规定：`int` 与 `unsigned`（同宽）同时运算时，`int` 先转成 `unsigned`，然后按无符号比较。

- 左：`(int)-1` = `0xFFFFFFFF` → 转 `unsigned` 后仍是 `0xFFFFFFFF` = 4294967295
- 右：`(unsigned)1` = `0x00000001` = 1
- `4294967295 < 1` → **假**

汇编上是 `cmp` + `setb`（**below**，看 CF，无符号语义）。如果用 `setl`（**less**，看 SF⊕OF，有符号语义），结果会是真——但类型已经统一到无符号了，编译器必须用 `setb`。这条规则的推广形式就是：**任何 `int` 与 `size_t` 的比较，负值都会变成 10¹⁹ 量级的最大无符号数**，于是 `if (x < 0)` 对 `size_t` 恒假，编译器甚至直接删掉该分支。
</details>

**Q3.** 一段代码用 `if (a + b < a)` 检测「加法溢出」并返回错误，在 `-O2` 下这段错误处理从来没触发过。解释原因，并给出两种正确的改法。

<details><summary>答案</summary>

因为 `a`、`b` 是有符号 `int`，有符号溢出在 C 里是**未定义行为**。编译器有权假设「溢出不会发生」，于是「无溢出」时 `a + b ≥ a`（在 `b ≥ 0` 的前提下）恒成立，`a + b < a` 恒假，整段代码被当作死代码删除——**这不是编译器 bug，是 UB 的合法后果**。

正确改法（任选其一，两种都要做到「先判后用」）：

1. **换到无符号域**：`if ((unsigned)a + (unsigned)b < (unsigned)a) return -1;` —— 无符号加法按 mod 2ⁿ 定义良好，溢出可判定（CF）。
2. **用内建函数**：`int s; if (__builtin_add_overflow(a, b, &s)) return -1;` —— 编译器会生成 OF 判断（`jo`/`seto`），且**只在真正不溢出时才把结果写给你**。

同时建议 `-fsanitize=signed-integer-overflow` 或 `-ftrapv` 在 CI 里全量跑一遍，把「本来就已经 UB 但恰好没爆」的代码先清掉。
</details>
