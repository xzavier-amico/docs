## 53.1 引子：首屏 1.2 秒，五个团队各认领 50 毫秒

先把场景摆出来。这是把多次真实排查拼在一起的一个复合案例，数字按量级归一，但每一段的查法都能在你自己机器上复现；§53.7 给的是本机实测，不是转述。

某后台系统的首屏（从用户敲回车到看见第一屏内容）稳定在 **1.2 s**。周五下午拉了五个团队，每人交一份「我们这段的耗时」：

| 团队 | 自报耗时 | 他们量的到底是什么 |
| --- | --- | --- |
| 前端 | 60 ms | `performance` 里 `scripting` 那一段，JS 执行时间 |
| 网关 | 40 ms | 网关进程内从收到请求到转发出去的时间 |
| 应用 | 120 ms | 业务 handler 第一行到最后一行的计时 |
| DBA | 50 ms | 慢查询日志里那条 SQL 的 `Query_time` |
| 运维 | 30 ms | 监控上「网络延迟」面板的均值 |

加起来 **300 ms**。可浏览器 `Navigation Timing` 里的 `duration` 是 **1200 ms**。

会议室里出现了三种解释：前端说「后端慢」，后端说「DB 慢」，DBA 说「SQL 只要 50 ms，是你们连接池的问题」，运维说「网络很正常，你看均值才 30 ms」。**没有一个人在撒谎，也没有一个人的数字是错的**——他们量的是各自进程内的「服务时间」，而 1200 ms 里还有 900 ms 根本不在任何进程的执行时间里。

那 900 ms 长什么样？后来用一条请求的边界时间戳把它切开：

| 段落 | 耗时 | 它属于谁 | 为什么不在任何人的计时器里 |
| --- | --- | --- | --- |
| 浏览器 DNS + TCP + TLS 冷启动 | 110 ms | 客户端网络栈 | 不在页面 JS 计时里，也不在服务端日志里 |
| 连接池排队等一个空闲连接 | 350 ms | 应用与 DB 之间的池 | handler 还没开始执行，计时器没启动 |
| DB 行锁等待（被批处理任务占着） | 240 ms | 数据库内部队列 | 不在 `Query_time` 之外单独暴露，应用只看到「这条 SQL 慢」 |
| 一次丢包触发的重传 | 200 ms | 内核 TCP | 应用只看到「超时」，内核只看到一个计数器 |
| 首屏 HTML 到达后的解析、布局、绘制 | 110 ms | 浏览器渲染 | 服务端早已返回 200，日志里是「快」的 |

合计 1100 ms，再加上五个团队那 300 ms 里被重复计算的 200 ms（例如网关的 40 ms 又出现在应用的 120 ms 里），正好 1200 ms。**关键不是这些数字，而是这五段里有四段是「排队」，一段是「渲染」；没有一段是「算得慢」。**

这就是本篇要立的唯一真问题：

> **把五部分焊成一条链：你的每一毫秒都能在这条链上找到归属；找不到归属的那部分，才是真正的未知。**

它有两个直接推论，后面每一节都在展开：

1. **「慢」不是形容词，是一个可以被分摊到链路上的和**。`1200 ms = Σ 服务时间 + Σ 排队时间 + Σ 重试时间 + Σ 渲染时间`。谁报的数只覆盖了第一项，谁的归因就必然缺口。
2. **缺口的形状永远是「边界」**：进程与内核的边界（系统调用）、机器与机器的边界（RTT）、队列与消费者的边界（唤醒）、请求与响应的边界（连接复用）。**每一段边界都有一个计数器**；找不到计数器，说明你还没找到边界。

## 53.2 全景链路图：一次回车，穿过五部分

下面这张图是全篇的支点。横向是「客户端 → 网络 → 服务端」，纵向是「用户态 → 内核态 → 硬件」。每一段旁边标了三样东西：**发生了什么、时间花在哪、归属哪一篇**。

```
┌──────────────── 客户端：用户态 ────────────────┐
│ 回车/触摸 → 键盘控制器 ──USB 中断──► 内核 input 子系统 ──evdev──► 浏览器 UI
│            (base/14 总线·中断)      (base/21 两态)          (base/23/24/25)
│ 浏览器网络进程：② DNS(base/44) → ③ TCP 1 RTT(41) → ④ TLS 1.3 1 RTT(47)
│                ⑤ HTTP 请求(46) → write()/sendmsg() ⑥ 跨界(base/21)
└──────────────────────────┬───────────────────────┘
                           ▼
┌──────────────── 客户端：内核态 ────────────────┐
│ syscall → socket 发送队列(sk_wmem, 31/32) → TCP 分段(42) → IP(40)
│ → qdisc 排队(40) → 网卡驱动填 DMA 环 → 网卡读走 → 硬中断「发送完成」(14)
└──────────────────────────┬───────────────────────┘
                           │ ⑦ 比特上线（传播 5 ns/米）
                           ▼
┌──────────────── 网络 ─────────────────────────┐
│ 交换机 L2 查 MAC(39) → 路由器 L3 查路由/NAT(40) → 城域 → 骨干 → 对端
│ 每跳都有：队列(qdisc/backlog) + 串行化(包长/带宽) + 传播
│ 丢包、乱序、ECN、MTU 分片都在这一段发生(39/42)
└──────────────────────────┬───────────────────────┘
                           │ ⑧ 到达服务端网卡
                           ▼
┌──────────────── 服务端：内核态 ────────────────┐
│ 网卡 DMA 写 RX ring(14) → 硬中断 → NAPI 轮询/软中断(32)
│ → 链路层(39) → IP(40) → TCP 查序列号/ACK/重组(41/42)
│ → socket 接收队列(sk_rmem, 32) → epoll 就绪链表(31) → 唤醒进程(25)
└──────────────────────────┬───────────────────────┘
                           │ ⑨ accept()/read()
                           ▼
┌──────────────── 服务端：用户态 ────────────────┐
│ 应用：调度排队(25) → 取锁/等锁(30) → 缓存/内存(26/27)
│ → DB/磁盘(28/29) → 序列化(06) → 业务逻辑(10–13)
│ 连接池、线程池、协程池：每个「池」都是一个队列，都能吞几百毫秒
│                                    ⑩ write()/sendmsg()
└──────────────────────────┬───────────────────────┘
                           ▼
              反向再走 ⑦–④：响应回到客户端 ⑪ 解析/布局/绘制/合成/上屏(46)
              渲染属于浏览器内核，不属于网络，也不属于服务端
```

这张图有三个读法，缺一个就会把它当成海报：

**读法一：纵轴是「特权级」，每一次上下穿越都要付一次固定单价。** ① 的键盘中断、⑥ 的 `write`、⑨ 的 `read`、⑩ 的 `write`，全是跨界。一次空 syscall 是 0.1–1 μs 量级（`base/21`），一次上下文切换是 1–5 μs 量级（`base/24/25`）。单看很便宜，但一次请求如果有 200 次 syscall、20 次唤醒，就是几百微秒到几毫秒——**这部分钱不写在任何业务代码里，却真实存在于链上**。

**读法二：横轴是「距离」，距离只买 RTT，不买别的。** 回环 RTT 20–50 μs，同机房 0.2–0.5 ms，跨城 20–40 ms（§53.3 给推导）。**跨城不会让 `memcpy` 变慢，只会让「等一个来回」变慢**。所以跨城服务里出现的 900 ms，几乎一定是「串行往返次数 × RTT」或「排队」，而不是「CPU 变慢了」。

**读法三：每一个「池」「队列」「缓冲区」都是时间可以藏身的地方。** 图里出现了至少八个：qdisc、网卡 ring、socket 发送队列、socket 接收队列、epoll 就绪链表、runqueue、连接池、DB 锁等待队列。**1.2 s 的故事之所以讲不圆，就是因为大家只盯着「正在运行的代码」，而时间大多待在「没有运行的队列」里**（主线②：快慢只有一种解释——排队）。

把这张图和 `0-summary` 的 §0.4 对照着看，会发现五部分其实是按这张图的纵轴切的：

| 图中的段 | 它回答的问题 | 归属 |
| --- | --- | --- |
| 按键 → 扫描码 → 中断 | 一次外部事件怎么变成内核里的一个字节 | `base/14` |
| 进程、线程、调度、唤醒 | 谁在跑、谁在等、等多久 | `base/23`–`base/25` |
| syscall 与两态 | 跨界一次付多少钱 | `base/21` |

## 53.3 每一跳的时间账：三档距离，一张量级表

在填表之前，先把「时间从哪来」拆成三项，否则数字只能背不能推：

```
一段链路的时间 = 传播（距离 / 光速） + 串行化（字节数 / 带宽） + 排队（队列长度 / 服务速率）
```

- **传播**是物理硬账：光纤里约 `2×10⁸ m/s`，即 **5 ns/米**。1000 km 单程 5 ms，往返 10 ms。
- **串行化**是带宽账：1 KB 在 10 Gbps 上要 `8192 bit / 10¹⁰ bit/s = 0.8 μs`；在 1 Gbps 上要 8 μs。
- **排队**是唯一会「非线性爆炸」的一项：队列利用率到 80% 时，等待时间已经翻几倍；到 95% 时，一点点流量波动就能让 p99 变成 p50 的十几倍。

三档距离的差别，几乎全部落在第一项和第三项上，第二项在任何档位都可以忽略（除非你在传大文件）。

| 段 | 本机（回环） | 同机房（同交换机） | 跨城（约 1000 km） | 出生证明（量级结论） |
| --- | --- | --- | --- | --- |
| 一次空 syscall | 0.1–1 μs | 同左 | 同左 | 入口 + 出口约 100–300 ns，带参数拷贝到 μs；与距离无关 |
| 一次上下文切换 | 1–5 μs | 同左 | 同左 | 直接切换 1–3 μs；缓存/TLB 污染后 5–10 μs |
| 协议栈处理一遍（TCP 收或发） | 5–20 μs | 同左 | 同左 | 分段、校验、查表、拷贝；与距离无关 |
| 网卡中断 + NAPI 一轮 | 5–50 μs | 同左 | 同左 | 中断上半部 <1 μs，主要成本在软中断与轮询 |
| 回环 RTT | 20–50 μs（空载） | — | — | 两次协议栈 + 两次调度；§53.7 在负载 8.6 的容器里实测 0.1–9.7 ms |
| 同机房 RTT | — | 0.2–0.5 ms | — | 传播仅 0.1–0.3 μs，其余是交换机存储转发、排队、中断合并 |
| 跨城 RTT | — | — | 20–40 ms | `2 × 1000 km / 2×10⁸ m/s = 10 ms` 传播；设备与排队再加一倍量级 |
| TCP 三次握手 | 1 RTT | 0.2–0.5 ms | 20–40 ms | 协议承诺；SYN + SYN-ACK + ACK，最后一个 ACK 可捎带数据 |
| TLS 1.3 握手 | 1 RTT | +0.2–0.5 ms | +20–40 ms | 协议承诺；会话恢复可 0-RTT，代价是重放窗口 |
| DNS 冷查询 | 0–1 ms（本机缓存） | 1–20 ms | 20–100 ms | 递归解析通常 2–3 个 RTT；TTL 内命中为 0 |
| 磁盘随机读 | SSD 0.1 ms / HDD 10 ms | 网络存储再加 1 RTT | 同左 | SSD 读延迟 ~100 μs；HDD 寻道 8–10 ms + 旋转 4.2 ms（7200 rpm） |
| 缺页 | minor 1–10 μs / major 0.1–10 ms | 同左 | 同左 | minor 只补页表；major 要读盘或触发回收 |
| GC 停顿 | 0.1–10 ms | 同左 | 同左 | 取决于堆大小与收集器；与网络无关 |
| 一次丢包重传 | ≥200 ms | ≥200 ms | ≥200 ms | Linux `RTO_min` 默认 200 ms（`/proc/net/snmp` 的 `RtoMin` 实测为 200） |

> **除了标注「实测」的两行，表内数字都是量级结论，不是承诺值。** 「同机房 0.2–0.5 ms」是「传播可忽略 + 交换机排队 + 中断合并」叠出来的经验量级，换机房、换网卡可以是 0.1 ms 或 2 ms。真正的承诺只有三行：TCP 握手 1 RTT、TLS 1.3 握手 1 RTT、`RTO_min` 200 ms。

### 三个必须会做的换算

**换算一：RTT 是按「串行往返次数」放大的。** 跨城 30 ms，一次请求如果在关键路径上串了 30 个往返（DNS → TCP → TLS → 请求 → 多次 DB 往返 → 多次缓存往返 → 响应分块），就是 `30 × 30 = 900 ms`。**这就是 53.1 那 900 ms 最容易被低估的来源**：不是某一跳慢，而是「跳数 × 单跳」。

**换算二：丢包是按「RTO」计价的，不是按「丢一个包」计价的。** 一个包丢了，发送方要等到重传定时器超时；Linux 的 `RTO_min` 是 200 ms。所以「丢 1% 的包」在短连接上可能表现为「每 100 个请求里有 1 个凭空多 200 ms」，在长连接上则表现为队头阻塞（`base/42`）。**`200 ms × 4.5 次 ≈ 900 ms`——四个半丢包就能吃掉整条预算。**

**换算三：一个 900 ms 的队列，胜过一千个 0.9 ms 的优化。** 如果 900 ms 里有 350 ms 在等连接池、240 ms 在等行锁，那么把 handler 从 120 ms 优化到 20 ms，首屏只会从 1.2 s 变成 1.1 s。**优化要先找「最大的那一格」，而最大的那一格通常是排队，不是计算。**

反过来也成立：如果一条跨城请求只有 3 次往返，网络只占 90 ms，那么剩下的 1110 ms 一定在别处——**别再把「跨城」当成万能借口**。

## 53.4 900 ms 去哪了：按「排队」逐层排查

53.1 的 900 ms 最后被分到四个队列上。这一节把它做成一张可执行的台账：**每一层都给出「它长什么样」「怎么证明是它」「怎么排除它」**。

| 层 / 队列 | 它吞时间的形态 | 如何证明是它（观测点） | 怎么排除它 |
| --- | --- | --- | --- |
| CPU runqueue | 线程可运行但拿不到核；`loadavg` 高、`r` 列高 | `vmstat 1` 看 `r`/`b`；`pidstat -w` 看 `cswch/s`；cgroup 看 `cpu.stat` 的 `nr_throttled`/`throttled_usec` | 若 `%idle` 高、`r` 接近核数，则不是它 |
| cgroup CPU 配额 | 配额用完被 throttle，整组停跑到下个周期 | `cpu.stat` 的 `nr_throttled` 持续增长；`cpu.max` 与 `cpu.pressure` | 若 `nr_throttled` 不涨，排除 |
| 锁等待 / futex | 线程睡眠，CPU 不高但延迟高（convoy） | `perf lock`；`offcputime`（eBPF）；Go 的 mutex profile；`strace -c -e futex` | 若等待时间为 0，排除 |
| 连接池 / 线程池 | handler 还没开始，请求在池队列里 | 在「收到请求」与「handler 第一行」各打一个时间戳，差值就是池等待；池的 `pending`/`wait_time` 指标 | 若差值 <1 ms，排除 |
| accept 队列 | 三次握手完成了，但应用没 `accept` | `nstat -az TcpExtListenOverflows`、`ListenDrops`；`ss -lnt` 的 `Send-Q`（backlog 上限） | 若 overflow 为 0，排除 |
| DB 慢查询 / 行锁 | SQL 执行久，或在等锁、等 IO、等刷盘 | 慢查询日志；`performance_schema` 的 wait event；`pg_stat_activity` 的 `wait_event`；`SHOW ENGINE INNODB STATUS` | 若 `Query_time` 与 handler 内 SQL 耗时都对得上，才坐实 |
| GC / 内存回收 | 世界停住；日志出现整段空白 | `-Xlog:gc*`、`GODEBUG=gctrace=1`；`/proc/vmstat` 的 `allocstall`；`perf stat -e page-faults` | 若停顿总量 <10 ms，排除 |
| 缺页 / 直接回收 | 分配路径里等回收，`sy` 高、延迟尖刺 | `/proc/<pid>/stat` 的 `majflt`；`sar -B` 的 `pgscank/pgsteal`；`/proc/pressure/memory` | 若无 major fault、无 stall，排除 |
| 网络重传 / 乱序 | 应用超时，服务端 handler 却很快 | `ss -ti` 的 `retrans`；`nstat -az TcpRetransSegs`；`tcpdump` 看重复 ACK | 若 retrans 为 0，排除 |
| 磁盘 / 远端存储 | `read`/`fsync` 卡住，`iowait` 高 | `iostat -x 1` 的 `await`、`%util`；`blktrace`；`/proc/pressure/io` | 若 `await` 正常，排除 |
| 软中断 / 网卡队列 | `%soft` 高、单核打满、丢包 | `/proc/softirqs` 差值；`mpstat -P ALL 1` 的 `%soft`；`ethtool -S` 的 `drop` | 若 `%soft` 低、drop 为 0，排除 |

这张表的使用方式不是「从上往下挨个查」，而是**先定位那 900 ms 落在哪个「段」，再只查那一段的队列**。定位段的方法见 §53.5；这里先给三个最容易被漏掉的细节。

### 细节一：`loadavg` 是排队长度，不是 CPU 使用率

`/proc/loadavg` 的三个数分别是 1、5、15 分钟的**可运行 + 不可中断睡眠**任务数均值。它高不一定 CPU 忙：如果一堆线程卡在 D 状态（等磁盘、等 NFS），`loadavg` 照样高，而 CPU 可能闲着。反过来，一个 100% 跑满的单线程，在 8 核机器上 `loadavg` 只有 1。

判据要一起看：`vmstat 1` 的 `r`（可运行队列）与 `b`（不可中断睡眠）、`us/sy/id/wa` 四个百分比、以及 cgroup 的 `cpu.stat`。**只看一个数就下结论，等于把「排队」和「干活」混为一谈。**

### 细节二：连接池的等待，任何进程内计时器都看不见

这是 53.1 里 350 ms 的来源，也是最常见的归因黑洞。请求已经到了应用进程（socket 可读），但业务代码在 `pool.Get()` 上阻塞——此时：

- 网关的「转发耗时」已经结束（它只看到自己写完了）；
- 应用的 handler 计时器还没启动（它从拿到连接之后才开始）；
- DB 的慢查询日志里什么都没有（SQL 还没发出去）；
- 监控上的「应用 RT」如果是在 handler 内部埋点，也看不到。

**唯一能抓住它的是「边界时间戳」**：在 `accept`/`read` 返回时打一个点，在 handler 第一行打一个点，两点之差就是池等待。这个差值不需要任何昂贵工具，只需要你承认「请求到达」和「业务开始」不是同一时刻。

### 细节三：`RTO_min = 200 ms` 是一条硬底线

`/proc/net/snmp` 里的 `RtoMin` 在本机实测是 `200`（单位 ms）。这意味着：**只要发生一次需要重传的丢包，这条连接上后续数据的等待就不会小于 200 ms**（快速重传/恢复除外，但那需要足够的重复 ACK）。所以看到「偶发 200 ms 尖刺」，第一反应应该是重传，而不是 GC——GC 的尖刺通常更短、更规律，而且能在 GC 日志里找到对应时刻。

一个 200 ms 的尖刺乘上 4.5 次，就是 900 ms；而 4.5 次重传在 1% 丢包的链路上并不罕见（`base/51` 量过 1% 丢包对 CUBIC 的杀伤）。

### 把 53.1 的 900 ms 归位

| 那 900 ms | 落在哪个队列 | 一句话证据 |
| --- | --- | --- |
| 350 ms | 连接池 | `accept` 时间戳与 handler 首行时间戳差 350 ms，池 `pending` 长期 >0 |
| 240 ms | DB 行锁 | `wait_event=innodb_row_lock`，`innodb_row_lock_time` 与缺口对得上 |
| 200 ms | TCP 重传 | `ss -ti` 的 `retrans` 增长，时间点与尖刺重合 |
| 110 ms | 浏览器渲染 | 服务端 200 已返回，`Navigation Timing` 的 `domContentLoaded` 之前还有 110 ms |

四段相加正好 900 ms。**没有一段是「算得慢」；四段全是「等」**——等池、等锁、等重传、等渲染。这就是主线②在收口篇的最终形态：**性能问题的答案，几乎永远是「谁在等，等什么，等多久」**。

## 53.5 分层的价值：同一条 1.2 s，五个人各查一层而不互相甩锅

分层最被低估的价值不是「解耦」，而是**归因**：它让五个团队可以同时工作而不打架，因为每一层都有独立的承诺、独立的计数器、独立的失败模式。吵架的根源从来不是「谁的责任」，而是**没有共享的时间戳**——每个人手里都有一把自己的尺子。

### 先决定方向：自下而上，还是自上而下

| 症状 | 建议方向 | 理由 | 第一刀切在哪 |
| --- | --- | --- | --- |
| 全站同时慢、多个服务一起抖 | **自下而上** | 共同依赖只可能在底层（宿主、网络、存储、DNS） | `loadavg`、`%soft`、`retrans`、`iostat` |
| 只有某个接口慢，其他正常 | **自上而下** | 差异只可能在这条业务路径上 | 该接口的 trace，按 span 排序 |
| 只有某地区/某运营商慢 | **自下而上到网络层** | 共性是路径，不是代码 | 分地区 RTT、丢包、DNS 解析结果 |
| 只有首屏慢、API 单独测很快 | **从客户端开始** | 缺口在连接建立或渲染 | `curl -w`、`Navigation Timing` |
| 周期性抖动（整点、每 5 分钟） | **先看队列长度的时间序列** | 周期 = 某个定时任务在抢同一个队列 | 批处理、GC、日志轮转、备份 |
| 新版本上线后开始 | **自上而下，但先排除资源** | 先证明「不是容量」，再查「改了什么」 | 版本 diff + 资源四件套 |

### 边界打点：唯一能让五个团队不吵架的技术

不要在每个团队内部计时，**在每个「交接面」计时**，并且用同一个时钟（同一台机器用 `CLOCK_MONOTONIC`，跨机器用 trace id + 各自单调时钟，靠 `base/55` 的时钟纪律对齐）。一次请求至少打六个点：

| 边界 | 谁打 | 它能切出什么 |
| --- | --- | --- |
| ① 客户端发起 | 浏览器/客户端 | 起点 |
| ② 连接建立完成（TCP/TLS 后） | 客户端 | ①–② = DNS + 握手 |
| ③ 请求写完 | 客户端 | ②–③ = 发送 + 本地排队 |
| ④ 服务端收到（`accept`/`read` 返回） | 服务端 | ③–④ = 网络 + accept 队列 |
| ⑤ 服务端 handler 首行 | 服务端 | ④–⑤ = 池等待 + 调度 |
| ⑥ 服务端响应写完 | 服务端 | ⑤–⑥ = 业务 + DB + 序列化 |
| ⑦ 客户端收到首字节 | 客户端 | ⑥–⑦ = 回程 + 服务端发送队列 |
| ⑧ 首屏可见 | 客户端 | ⑦–⑧ = 解析 + 布局 + 绘制 |

有了这八个点，53.1 的争论会在五分钟内结束：350 ms 落在 ④–⑤，240 ms 落在 ⑤–⑥ 里的 DB span，200 ms 落在 ③–④ 的重传，110 ms 落在 ⑦–⑧。**每一段都有主，且每一段的主人都无法把锅推给邻居**——因为边界时间戳是共享的。

### 按层归因的顺序（一张可执行的顺序表）

1. **先算总账**：`总耗时 − Σ 已知段`，得到「无人认领」的缺口。缺口为负，说明有重复计算；缺口为正，说明有段没打点。
2. **再看影响面**：全站 / 单接口 / 单地区 / 单用户，四种影响面对应四个起点（上表）。
3. **只查缺口所在的那一段**：不要顺手把整条链都查一遍；查得越宽，越容易找到一个「确实有问题但与本次无关」的现象，然后误把它当根因。
4. **对每一段问一句「这是服务时间还是排队时间」**：服务时间找 CPU/IO/算法，排队时间找队列长度与服务速率。
5. **最后做一次「反证」**：把怀疑的那一层换掉/绕开（换连接池、换机器、关掉批处理、注入 0 丢包），看缺口是否消失。**不能反证的归因，只是相关性。**

这套顺序有一个副作用：优化会变得很无聊——你不再需要猜哪里可以优化，只需要看哪一格的绝对值最大。

## 53.6 跨层耦合：为什么「数据库慢」会表现为「CPU 高」

分层让人能分工，但也会制造一种错觉：**每一层都可以被独立观测**。真实系统里，层与层之间会「串味」——一层的故障在另一层留下完全不同的指纹。把这类现象叫「跨层伪装」。识别不了伪装，就会把工具用在对的层、却读错结论。

### 伪装一：DB 慢 → CPU 高（自旋、重试、放大）

机制有三条，常常同时发生：

1. **锁内做慢操作**：业务代码在互斥锁里调用 DB/缓存（哪怕只是一次「快速查询」）。锁一被持有 200 ms，其他线程并不会立刻睡——`futex` 的 adaptive spinning 会先自旋一小段时间，Go runtime 也会自旋等 P。**自旋不产生任何有用工作，只产生 `us`/`sy` 和热量。**
2. **重试风暴**：DB 超时后，上层重试 3 次、客户端再重试 3 次，放大 9 倍；每次重试都重新走连接池、重新查缓存、重新分配对象。**QPS 看起来没涨，CPU 却涨了**，因为「完成的工作」没变，「尝试的工作」变了。
3. **结果集分配与 GC**：慢查询往往伴随大结果集；序列化、拷贝、临时对象把 GC 压力顶上去，GC 又反过来拖慢所有线程。**CPU 高的最后一环可能是 GC，但根因是 DB。**

**一眼识别**：`CPU 高 + QPS 不涨 + p99 变差`。这是「工作放大」的签名，不是「流量增长」的签名。进一步看 `pidstat -u` 的 `us` 与 `sy`：`sy` 高、`perf top` 里出现 `futex`/`spin_lock`，基本可以坐实自旋；`perf lock contention` 能直接列出争用的锁与等待时间。反过来，如果 `us` 高、`perf top` 里是业务函数，那才是真的在算。

### 伪装二：网络丢包 → 应用超时（RTO、队头阻塞、池耗尽）

应用侧看到的是 `context deadline exceeded`，服务端侧的 handler 却只有 5 ms——两边都没说谎：**请求要么没到，要么响应没回来，而这两段时间都不在 handler 里**。

机制链条：丢一个包 → 发送方等 `RTO_min`（200 ms）→ 若在长连接上，后续数据被队头阻塞（TCP 是有序流）→ 客户端连接池里的连接被占住 → 其他请求排队 → 应用层超时 → 重试 → 更多连接被占住。**一次丢包可以放大成几十个超时**，而服务端的 CPU、handler 时间、QPS 可能全都正常。

**一眼识别**：`服务端请求数 < 客户端尝试数`，且服务端 handler 时间正常。先看客户端 `curl -w` 的 `time_connect`/`time_starttransfer` 与 `time_total` 的差，再看 `ss -ti` 的 `retrans`、`nstat -az TcpRetransSegs`，最后 `tcpdump` 抓重复 ACK。

### 伪装三：内存回收 → 「下游变慢」（分配路径里的直接回收）

当空闲页不够时，分配内存的线程可能进入**直接回收**（direct reclaim），在自己的执行路径里帮内核扫页、回写、等 IO。于是：

- 每一次 `malloc`/缺页都可能多花几百微秒到几毫秒；
- 表现为「所有下游都变慢」——DB、缓存、序列化、日志，因为它们都要分配内存；
- 但每个下游自己的监控都正常，因为慢在**调用方的分配路径**上。

**一眼识别**：`/proc/pressure/memory` 的 `some/full` 增长、`/proc/vmstat` 的 `allocstall` 增长、`/proc/<pid>/stat` 的 `majflt` 增长；`perf stat -e page-faults` 与延迟尖刺对齐。若这些都为 0，别把锅甩给内存。

### 六个常见伪装，一张表看完

| 你看到的表象 | 真正出问题的层 | 机制一句话 | 一眼识别的证据 |
| --- | --- | --- | --- |
| CPU 90%，QPS 不涨 | 锁 / 重试 / GC | 自旋与重试只烧 CPU 不完成请求 | `sy` 高、`futex`/`spin_lock` 在 `perf top` 顶部 |
| 应用大面积超时 | 网络丢包 | RTO ≥200 ms + 队头阻塞 + 池耗尽 | `ss -ti` retrans 增长，服务端 handler 正常 |
| 所有下游都「变慢」 | 本机内存回收 | 分配路径里直接回收 | `allocstall`、`majflt`、memory pressure 同时涨 |
| 服务端 RT 很低，用户 RT 很高 | 连接建立 / TLS / 渲染 | 时间花在请求到达前或响应到达后 | `curl -w` 的 `time_appconnect`/`time_starttransfer` |
| 偶发整 200 ms 尖刺 | TCP 重传 | `RTO_min` 恰好 200 ms | 尖刺宽度集中在 200/400/800 ms |
| 吞吐上不去、CPU 不高 | 队列 / 窗口 / 连接数 | 并发度被某个上限卡住 | `ss -s`、连接池 `pending`、TCP 窗口 |

**跨层伪装的第一原则：不要问「哪一层坏了」，要问「哪一层的计数器与这个现象对得上」。** 计数器对不上，再像的因果也是故事。

## 53.7 一次完整的时间线：在本机把 1 次请求拆成四段

前面都是「应该怎样」。这一节全部是本机实测：一台 2 vCPU 的容器，Linux 6.12.113，测试期间 `/proc/loadavg` 为 **8.62**（宿主是共享的，这个负载很关键，后面会解释），服务端与客户端都在这台机器上，走回环。

### 服务端：一个会打点的 HTTP server

```python
import http.server, socketserver, time, sys
T0 = time.perf_counter()
def us(t): return (t - T0) * 1e6

class H(http.server.BaseHTTPRequestHandler):
    protocol_version = "HTTP/1.1"
    def setup(self):
        self.t_accept = time.perf_counter()   # accept 返回
        super().setup()
    def do_GET(self):
        self.t_req = time.perf_counter()      # 请求行+头读完
        if self.path.startswith("/slow"):
            time.sleep(0.020)                 # 模拟 20 ms 业务处理
        body = b"ok\n"
        hdr = b"HTTP/1.1 200 OK\r\nContent-Length: %d\r\n\r\n" % len(body)
        self.wfile.write(hdr + body)          # 头部与 body 一次写出
        self.t_out = time.perf_counter()
        print("accept=%.0f req=%.0f out=%.0f handler_us=%.0f path=%s" % (
            us(self.t_accept), us(self.t_req), us(self.t_out),
            (self.t_out - self.t_req) * 1e6, self.path), flush=True)
    def log_message(self, *a):
        pass

class S(socketserver.ThreadingTCPServer):
    allow_reuse_address = True
    daemon_threads = True

S(("127.0.0.1", int(sys.argv[1])), H).serve_forever()
```

三个打点分别对应：**accept 返回**（连接已建立、请求可能还没到）、**请求头读完**（业务可以开始了）、**响应写完**（进入内核发送队列）。注意最后一个点不是「客户端收到」——从 `write` 到客户端 `read` 之间还有内核发送队列、网卡、回环、接收队列、唤醒。

### 客户端：`curl -w` 打四个点

```bash
python3 srv53c.py 18057 &
for i in $(seq 1 12); do
  curl -s -o /dev/null -w \
    "fast connect=%{time_connect} start=%{time_starttransfer} total=%{time_total}\n" \
    http://127.0.0.1:18057/fast
done
for i in $(seq 1 6); do
  curl -s -o /dev/null -w \
    "slow connect=%{time_connect} start=%{time_starttransfer} total=%{time_total}\n" \
    http://127.0.0.1:18057/slow
done
```

`time_connect` 是 TCP 握手完成（回环上没有 DNS，所以基本等于建连成本）；`time_starttransfer` 是收到响应首字节；`time_total` 是读完响应。三个差值分别对应「建连」「等首字节」「读响应」。

先看中位数（心算即可）：`/fast` 的 `connect` 中位数约 **0.13 ms**，`total` 约 **2.4 ms**；服务端 handler 中位数约 **38 μs**。`/slow` 的 handler 中位数约 **21.8 ms**，`total` 约 **23.6 ms**。

**第一个结论：服务端处理只占客户端总耗时的 1.6%（38 μs / 2.4 ms）。** 如果你只看应用日志（`handler_us=38`），会得出「接口很快」；如果只看用户（`2.4 ms`），会得出「没那么快」。两个都对，差在链路上。

**第二个结论：本机不等于零延迟，负载会把「微秒」变成「毫秒」。** 同样是 `connect`，最好 93 μs，最差 7.5 ms，差 80 倍。原因不在 TCP——握手的内核路径没有变——而在**进程被唤醒后要排 runqueue**。`/proc/loadavg` 的 `8.62` 意味着 2 个核上平均有 8.6 个任务在等；`accept` 线程和 curl 都可能等上几毫秒。**这也解释了为什么「压测环境很快、线上很慢」：不是代码变了，是队列变长了。**

### 把一次 `/slow` 请求拆成四段

取 `slow run=3`：客户端 `total = 22.131 ms`，`connect = 0.116 ms`；服务端日志的 `accept=987385`、`req=987558`、`out=1008796`（微秒），即 accept 到请求读完 **0.173 ms**，业务处理 **21.238 ms**。于是：

| 段 | 耗时 | 怎么得到 | 归属 |
| --- | --- | --- | --- |
| 建连（TCP 握手） | 0.116 ms | `curl time_connect` | `base/41` + `base/25`（唤醒） |
| accept → 请求读完 | 0.173 ms | 服务端 `req − accept` | `base/32` + `base/31` |
| 服务端处理 | 21.238 ms | 服务端 `out − req` | 应用（本例故意 `sleep 20 ms`） |
| 回程 + 客户端读 | 0.604 ms | `total − 上三段` | `base/32` + `base/25` |
| **合计** | **22.131 ms** | 与 `curl total` 逐位对上 | — |

四段加起来与客户端总数**精确到微秒地对上**。这就是「每一毫秒都有归属」的最小可行证明：不需要分布式追踪，只需要在**边界**打点，并且用同一个时钟。

### 配合 `/proc`：把「排队」量出来

```bash
$ cat /proc/loadavg
8.62 10.43 7.26 9/474 3348931      # 2 vCPU，r≈9：唤醒要排队

$ grep '^Tcp:' /proc/net/snmp | tail -1
Tcp: 1 200 120000 -1 1011007 273978 30302 39529 537 71175696 72811138 1628380 ...
#        ↑ RtoMin=200 ms                         ↑ RetransSegs=1,628,380

$ awk '/^voluntary_ctxt_switches/{print $2}' /proc/$SRV/status
76
# 100 次请求后再读一次：406 → 100 次请求共 330 次自愿切换 ≈ 3.3 次/请求
```

三个数字各有各的读法：

- `RtoMin = 200` 是**承诺值**：它解释了为什么丢包尖刺总是 200 ms 的整数倍。
- `RetransSegs = 1,628,380 / OutSegs = 72,811,138 ≈ 2.24%`，看起来很高——但这是**宿主 netns 的全局计数**（容器没有隔离 `/proc/net`），它统计的不只是本容器、也不只是回环。**这就是「计数器口径」的陷阱：数字是真的，归因是错的。**
- `3.3 次上下文切换/请求` 是**实测**：一次 accept 唤醒、一次 handler 线程唤醒、一次返回/调度。单次 1–5 μs，3 次就是 3–15 μs；在 38 μs 的 handler 面前不可忽略，在 20 ms 的业务面前可以忽略。

### 连接复用：把「建连」从账上划掉

同一个 `curl` 进程连打 6 次（复用一条连接），再与 6 个新进程对比：

| 方式 | `connect` | `total` 范围 | 中位数 |
| --- | --- | --- | --- |
| 一个进程连打 6 次（复用） | 仅第一次 3.1 ms，之后 0 | 0.153–2.072 ms | 0.98 ms |
| 每次新进程（新连接） | 0.10–9.73 ms | 0.695–13.227 ms | 5.56 ms |

复用把中位数从 **5.56 ms 压到 0.98 ms**，但**没有压到零**——剩下的 0.15–2 ms 仍然是调度、协议栈、线程唤醒。**这就是连接池的真实收益边界：它省掉握手与慢启动，不省掉排队。** 如果池子本身满了，你只是把「TCP 握手」换成了「等一个空闲连接」，后者可能更贵（53.1 的 350 ms 就是它）。

### 这一节证明了什么

1. **时间可以被完整分摊**：四段相加与总数逐位对上；分摊不掉的部分，一定是你少打了一个点。
2. **「本机」不是基准，空载才是**：同一段代码在负载 8.6 的机器上，建连从 0.09 ms 抖到 9.7 ms；**抖动来自 runqueue，不来自 TCP**。
3. **计数器有口径**：`/proc/net/snmp` 的 2.24% 重传是宿主全局，不是本次请求；用它归因会闹笑话。**先问「这个计数器统计的是谁」。**

## 53.8 三列账 + 一页速记

### 三列账：每一层承诺了什么、收了什么、从哪崩

| 层 | 承诺了什么 | 为此付了什么 | 从哪里开始失效 | 它在 1.2 s 里的位置 |
| --- | --- | --- | --- | --- |
| 位与表示（`base/02`–`base/09`） | 同一批字节按约定解释出确定的值 | 每次跨界都要显式约定宽度、符号、端序、编码 | 约定不一致：乱码、错位、精度丢失 | 通常不在热路径；一旦在，表现为「数据不对」而非「慢」 |
| CPU 与缓存（`base/10`–`base/18`） | 指令按序退休，缓存假装内存很快 | 分支预测、乱序窗口、cache line 一致性 | 预测失败、伪共享、带宽打满 | handler 内的计算；通常 μs–ms |
| 内核与内存（`base/21`–`base/27`） | 每个进程有独立地址空间，`malloc` 像无限内存 | 每次跨界 0.1–1 μs；每次缺页 1 μs–10 ms | 缺页、直接回收、OOM、syscall 过多 | 分配、拷贝、唤醒；μs–几十 ms |
| 文件与磁盘（`base/28`–`base/29`） | `write` 成功、`fsync` 后数据在盘上 | 页缓存、日志、磁盘写缓存三层 | `fsync` 卡住、随机写放大、崩溃丢数据 | DB 提交、日志落盘；0.1–10 ms |
| socket 与协议栈（`base/31`–`base/37`） | 一次 `read` 拿到一段有序字节流 | 收发队列、软中断、拷贝次数 | 队列满、软中断打满、零拷贝用错 | 每次收发；10 μs–几 ms |
| 网络与协议（`base/38`–`base/51`） | 尽力送到、可靠流、加密与身份 | RTT、握手、重传、队头阻塞 | 丢包、拥塞、DNS、证书 | 建连 + 往返；0.2 ms–几百 ms |
| 应用与队列（本篇 + `base/54`） | 请求被处理、依赖被调用 | 连接池、线程池、锁、重试 | 池满、锁 convoy、重试放大 | 350 ms 的池等待、240 ms 的行锁 |
| 客户端渲染 | 字节变成可见像素 | 解析、布局、绘制、合成 | 大 JS、强制同步布局、字体 | 首屏最后 110 ms |

一句话收束：**这条链上每一层都在卖「确定性」，收的都是「时间」；1.2 s 就是所有层收据的和。** 找不到收据的那一段，不是没有成本，是没有人开票。

### 一页速记

```
【一句话】
  1.2 s = Σ服务时间 + Σ排队时间 + Σ重试时间 + Σ渲染时间
  找不到归属的毫秒，才是真正的未知。

【一条链（八段）】
  键盘/事件 → 浏览器网络 → syscall → 本机协议栈 → 网线/交换/路由
  → 服务端协议栈 → accept/read → 应用/DB → write → 回程 → 解析渲染

【三个换算】
  跨城 30 ms × 30 次串行往返 = 900 ms
  丢包 1 次 ≥ RTO_min 200 ms；4.5 次 ≈ 900 ms
  一个 900 ms 的队列 > 一千个 0.9 ms 的优化

【四个必打点】
  accept 返回 / handler 首行 / 响应写完 / 客户端首字节
  差值分别对应：网络+队列 / 池+调度 / 业务+DB / 回程

【五个队列】
  runqueue、连接池、DB 行锁、socket 收发队列、GC/回收
  每一个都能吞几百毫秒，且都不在任何人的 handler 计时里

【六个口径陷阱】
  loadavg ≠ CPU 使用率；retrans 是宿主全局；
  strace -T 含观测开销；time_total 含渲染前的一切；
  Query_time 不含池等待；服务端 RT 不含建连与回程
```

## 53.9 自检 3 题

**Q1.** 一个跨城接口总耗时 1.2 s。服务端 handler 80 ms，其中 DB 查询 60 ms；跨城 RTT 30 ms；服务端日志显示「200 OK」只用了 80 ms。请给出至少三种能吞掉 900 ms 的机制，并各说一个观测点。

<details><summary>答案</summary>

先做减法：`1200 − 80 = 1120 ms` 不在 handler 里；其中网络若只走 3 个往返是 90 ms，仍有约 1030 ms 需要解释。三种典型机制：

1. **串行往返太多**：DNS + TCP + TLS + 多次 DB/缓存往返，如果有 30 次串行 RTT，就是 `30 × 30 = 900 ms`。观测点：客户端/服务端的 span 数，或 `curl -w` 的 `time_namelookup`、`time_connect`、`time_appconnect`、`time_starttransfer` 四段差。
2. **连接池或线程池排队**：请求已到进程，但 handler 还没开始。观测点：在 `accept` 返回与 handler 首行各打一个时间戳，差值就是池等待；再看池的 `pending`。
3. **丢包重传**：`RTO_min = 200 ms`，4–5 次重传就是 800–1000 ms。观测点：`ss -ti` 的 `retrans`、`nstat -az TcpRetransSegs`，以及尖刺宽度是否集中在 200/400/800 ms。
4. **DB 行锁/IO 等待**：`Query_time` 60 ms 只代表这一次执行，等连接或等锁的时间不在 SQL 里。观测点：`performance_schema` 的 wait event、`innodb_row_lock_time`。

判据：**先看 1120 ms 落在哪个边界区间，再只查那一段**；不要同时把所有层都查一遍。
</details>

**Q2.** 监控显示 CPU 使用率 90%，但 QPS 与上周持平，p99 从 50 ms 涨到 200 ms。怎么判断是「真的在算」还是「自旋/重试」？给出三条互相独立的证据。

<details><summary>答案</summary>

「CPU 高 + 完成的工作没涨」是工作放大的签名。三条独立证据：

1. **`us` 与 `sy` 的拆分**：`pidstat -u 1` 或 `mpstat`。`sy` 显著升高、`us` 不升，说明时间花在内核路径（自旋锁、futex、系统调用），不是在业务计算。
2. **`perf top` / `perf lock`**：如果顶部是 `futex`、`__pv_queued_spin_lock_slowpath`、`mutex_lock`，就是锁争用；如果顶部是业务函数且 IPC 正常，才是在算。`perf stat -e cycles,instructions` 的 IPC 骤降也支持「在等/在转」而不是「在算」。
3. **重试与 QPS 的口径**：对比「客户端尝试数」「服务端收到数」「成功完成数」。如果尝试数涨、完成数不涨，重试在放大；再看连接池 `pending`、DB 超时计数、GC 日志。

结论：**CPU 高只说明「有人在烧核」，不说明「有人在完成任务」；把「完成的工作」和「烧掉的核」放在同一张图上，伪装立刻现形。**
</details>

**Q3.** 客户端测到一次请求 200 ms，服务端 handler 5 ms，服务端访问日志也是 5 ms，两端都没有报错。时间可能花在哪？给出一个能一次定位的实验。

<details><summary>答案</summary>

时间只能在三段里：**请求到达服务端之前、服务端 handler 之外、响应离开服务端之后**。常见嫌疑：

- **建连**：DNS 冷解析、TCP 握手、TLS 握手；跨城 30 ms 时，TCP+TLS 1.3 就是 60 ms 起。
- **重传**：一次丢包的 `RTO_min` 恰好 200 ms，和观测值精确吻合——这是最值得先排除的。
- **排队**：accept 队列满、连接池等待、服务端线程池排队；这些都不在 handler 计时里。
- **回程**：响应写完到客户端读完，可能卡在发送队列、Nagle/延迟 ACK、或客户端读取慢。

一次定位实验：用 `curl -w` 打四段，并与服务端时间戳对齐：

```bash
curl -s -o /dev/null -w \
 'dns=%{time_namelookup} tcp=%{time_connect} tls=%{time_appconnect} first=%{time_starttransfer} total=%{time_total}\n' \
 https://example.com/api
```

如果 `time_appconnect` 已经很大 → 握手/网络；如果 `time_starttransfer − time_appconnect` 大而服务端 handler 小 → 服务端排队或重传；如果 `total − time_starttransfer` 大 → 回程/读响应。再配合 `ss -ti` 看 `retrans`、`tcpdump` 看是否有 200 ms 后的重传，就能把 200 ms 钉死在某一段。
</details>
