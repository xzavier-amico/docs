## 16.1 引子：`sm__throughput` 95%，端到端只快 1.9 倍

先摆一个几乎每个「把离线任务搬上 GPU」的团队都会撞上的账。业务是给 2000 万条候选打分，每条 40 个 float 特征，CPU 版 16 核跑 4.2 s。迁到一张 A100 上，`ncu` 报 `sm__throughput.avg.pct_of_peak_sustained_elapsed = 95%`——按这个数字，卡是「跑满」的。可端到端只从 4.2 s 变成 2.2 s。

把 2.2 s 拆开，账立刻清楚：**GPU 的时间从来不是「你写的那个 kernel」，而是「把数据搬进去 + kernel + 把结果搬出来 + 那些没被改写的 CPU 段」**。

| 段 | CPU 版 | GPU 版 | 说明 |
| --- | --- | --- | --- |
| 从存储读原始记录 + 反序列化 | 1.00 s | 1.00 s | 留在 CPU，没动 |
| 特征拼装 / 归一化 | 0.50 s | 0.50 s | 留在 CPU，没动 |
| 打分内核 | 2.40 s | **0.06 s** | 这一段快了 40 倍，也确实 95% 吞吐 |
| 排序 + 截断 top-k | 0.30 s | 0.30 s | 留在 CPU，没动 |
| H2D + D2H 传输 | 0 | **0.26 s** | 3.2 GB 输入 + 0.08 GB 输出，~25 GB/s 有效带宽 |
| kernel 启动、流同步、页锁定拷贝开销 | 0 | 0.05 s | 见 §16.10 的启动开销一行 |
| **合计** | **4.20 s** | **2.17 s** | 端到端 1.9× |

上表的每一格都能按本篇公式复算：3.2 GB ÷ 25 GB/s ≈ 128 ms 单向，往返 256 ms。**`sm__throughput` 95% 描述的是「那 60 ms 里 SM 的发射槽有多满」，它一个字都没说「这 60 ms 占端到端多少」。** 这是本篇要建立的第一条直觉：GPU 的指标全是**局部**指标，必须乘上「这段占全局的比例」才有意义（Amdahl 的那把尺子在这里照样生效）。

第二笔账更狠，也是本篇真正的主线。同一个团队试过「直接把 CPU 版逻辑搬过去」：原代码对每条候选做一棵深度 5 的规则树，叶子按类别走不同分支。搬到 GPU 后，**同一个 kernel 慢了 50 倍**。原因不是「GPU 不适合规则」，而是那棵树在 warp 里被串行化了：

```
一个 warp 的 32 条 lane 处理 32 条候选
每条候选在各层走不同分支
→ 这一层有 3 个分支，就要执行 3 遍（每遍只有 1/3 的 lane 有效）
→ 深度 5，平均每层 3 个分支：3⁵ = 243 遍
→ 有效 lane 占比 ~1/243，再乘上每遍的掩码开销 → 实测 ~50 倍
```

50 倍不是玄学，是 `3⁵` 除以常数因子。**这正是唯一真问题的形状：GPU 是「一个取指单元带 32 条执行通道」的机器，所以它只能跑「同一段代码处理不同数据」；一旦 32 条 lane 要走不同代码，硬件没有第二条取指通路，只能排队。**

所以本篇不回答「GPU 快不快」，只回答四个「为什么」：

1. 为什么它的核看起来「又小又笨」——面积去哪了（§16.2、§16.7）；
2. 为什么 32 条 lane 必须同进同退，代价怎么算（§16.3）；
3. 为什么它不怕延迟、却怕占用率低（§16.4）和放不下（§16.5）；
4. 为什么「寄存器溢出」比「少几个核」严重一个数量级（§16.6）。

## 16.2 从 CPU 核到 SM：把「猜」的面积换成「算」的面积

### 两种核，两种面积分配

一颗现代 CPU 核（比如 Zen 4 / Golden Cove 级别）为了把**一条**指令流跑快，面积大致这么分：取指与译码、分支预测器（含 BTB、方向预测表、返回栈）、寄存器重命名与乱序调度（ROB 几百项）、访存乱序队列、L1d/L1i、L2 slice，最后剩给整数/浮点执行单元的只有一小块。GPU 的一个 SM 反过来：**几乎没有「猜」的硬件，绝大部分面积是寄存器堆 + 执行通道 + 共享存储**。

| 面积去向 | CPU 单核（量级/示意） | GPU 单个 SM（量级/示意） | 差别的原因 |
| --- | --- | --- | --- |
| 取指 + 译码 | 5–10% | 2–4% | GPU 一次取指喂 32 条 lane，摊薄 32× |
| 分支预测（BTB/方向/返回栈） | 5–10% | **0** | 数据并行的分支是「数据相关」，不是「历史相关」，预测器学不到 |
| 乱序调度（ROB/重命名/发射队列） | 15–25% | **0** | 用「同时挂 64 个 warp」代替「同时飞 500 条指令」 |
| 寄存器堆 | 5–8% | 25–30% | 每线程私有寄存器是 SIMT 的唯一状态 |
| L1 / shared memory | 25–35% | 15–20% | 只服务「有复用」的块内数据，容量小、带宽极高 |
| ALU / FPU / 张量单元 | 10–15% | **40–50%** | 省下来的全在这 |
| 控制/其它 | 余量 | 余量 | — |

> 这张表是**量级示意**，不是任何一颗芯片的 floorplan 测量值；它只用来解释「为什么 GPU 单核那么弱而整卡那么强」。

用 A100 做个上限估算：GA100 die 约 826 mm²，108 个 SM。826 ÷ 108 ≈ **7.6 mm²/SM**——这是「假设全部面积都是 SM」的上限，实际每个 SM 只占更小一块。**「GPU 核笨」不是设计缺陷，是面积预算的主动选择。**

### 一个 SM 里到底有什么

```
                        ┌──────────── 一个 SM（A100 级，量级示意）────────────┐
                        │                                                     │
   warp scheduler 0 ────┤  ┌──────────────────────────────────────────────┐   │
   warp scheduler 1 ────┤  │  寄存器堆 65536 × 32 bit = 256 KB            │   │
   warp scheduler 2 ────┤  │  （全 SM 共享，按 warp 静态切给每个线程）      │   │
   warp scheduler 3 ────┤  └──────────────────────────────────────────────┘   │
                        │            │  每个 scheduler 每 cycle 发射 1 条 warp 指令
                        │  ┌─────────┴─────────┬───────────┬───────────┐      │
                        │  │ 16 FP32 lane 组   │ 16 FP32   │ 16 FP32   │ 16   │      │
                        │  │ (CUDA core)       │           │           │      │      │
                        │  ├───────────────────┴───────────┴───────────┤      │
                        │  │ 4 × SFU（sin/exp/rcp）  4 × Tensor Core    │      │
                        │  ├─────────────────────────────────────────────┤      │
                        │  │ shared memory / L1：192 KB 物理上合一       │      │
                        │  │ （可切成 164 KB shared + 28 KB L1）         │      │
                        │  └─────────────────────────────────────────────┘      │
                        └─────────────────────────────────────────────────────┘
```

三个数字必须记住，它们是后面所有账的分母：

| 量 | A100（GA100） | H100（GH100） | 含义 |
| --- | --- | --- | --- |
| 每 SM 的 FP32 lane 数 | 64 | 128 | 决定峰值 FLOPs |
| 每 SM 的 warp scheduler | 4 | 4 | 决定每 cycle 最多发射 4 条 warp 指令 |
| 每 SM 常驻 warp 上限 | 64 | 64 | 决定「用多少条指令流去填延迟」 |
| 每 SM 常驻线程上限 | 2048 | 2048 | 64 warp × 32 lane |
| 每 SM 寄存器 | 65536 × 32 bit | 65536 × 32 bit | 256 KB，占用率的真正闸门 |
| 全卡 SM 数 | 108 | 132 | — |
| FP32 峰值 | 19.5 TFLOPS | 66.9 TFLOPS | §16.8 有完整算式 |

注意「4 个 scheduler」这件事：**一个 SM 同时在飞的不是 1 条指令流，而是 4 条**（每个 scheduler 一条），每条又有 32 条 lane。所以一个 SM 的并行度是 4 × 32 = 128 条数据通道，而不是 32。这也解释了为什么 SM 里要放 64 个 warp：**4 个 scheduler × 16 个候选 warp**，每个 scheduler 在自己的 16 个里挑一个能发射的。

## 16.3 SIMT 与 warp：32 条 lane，一份取指

### SIMT 的物理定义

SIMT（Single Instruction, Multiple Threads）不是「SIMD 的软件版」这种含糊说法，它有一个精确的硬件含义：

- **一个 warp = 32 条 lane，共享一个程序计数器（PC）和一份取指/译码结果**；
- **每条 lane 有自己的寄存器堆切片**（所以 32 条 lane 可以有 32 个不同的 `x`）；
- 调度器（warp scheduler）**以 warp 为单位**分配执行槽：这一 cycle 选中哪个 warp，就把它的**同一条指令**广播给 32 条 lane。

对比 SIMD（如 AVX-512）：SIMD 是「一条指令操作 16 个 float 的向量寄存器」，编译器必须先把数据塞进向量；SIMT 是「32 个线程各跑各的，硬件保证它们的 PC 相同」。前者对程序员是显式的，后者是隐式的——**你在 CUDA 里写的是「每个线程都执行 `y[i] = a[i] * b[i]`」，硬件看到的是「一个 warp 执行一条 `FMUL`，32 条 lane 各取自己的地址」**。

```
程序员视角（32 个线程）             硬件视角（1 个 warp）
t0: y[0] = a[0]*b[0]  ┐
t1: y[1] = a[1]*b[1]  │  编译 + warp 化   ┌──────────────────────────────┐
...                   ├──────────────────►│ LDG  r1, [a + lane*4]        │
t31: y[31]=a[31]*b[31]┘                   │ LDG  r2, [b + lane*4]        │
                                          │ FMUL r3, r1, r2              │
                                          │ STG  [y + lane*4], r3        │
                                          └──────────────────────────────┘
                                             一条指令，32 条 lane 同时执行
```

### 分支发散：if-else 为什么是 2 倍

现在把 `x > 0` 塞进去。warp 只有**一个** PC，而 32 条 lane 的条件各不相同。硬件不会为另一半 lane 再开一条取指通路，它做的是：**把两条路径都执行一遍，每次用「活跃掩码」屏蔽掉不该动的 lane**。

```
if (x > 0) y = A(x); else y = B(x);
warp 里 lane 0–15 的 x > 0，lane 16–31 的 x <= 0

 指令流（同一个取指单元发出）              活跃掩码（1 = 该 lane 真的在算）
 ─────────────────────────────────────────────────────────────────────────
  LDG   r1, [x]                            1111 1111 1111 1111 1111 1111 1111 1111
  FSETP p, r1 > 0                          1111 1111 1111 1111 1111 1111 1111 1111
  @!p BRA  L_else                          1111 1111 1111 1111 0000 0000 0000 0000
  ┌ A 路径（lane 0–15 有效）                1111 1111 1111 1111 0000 0000 0000 0000
  │ FMUL r2, r1, c1                         1111 1111 1111 1111 0000 0000 0000 0000
  │ FADD r3, r2, c2                         1111 1111 1111 1111 0000 0000 0000 0000
  │ BRA  L_end      （跳转仍要发射）         1111 1111 1111 1111 0000 0000 0000 0000
 L_else:                                    0000 0000 0000 0000 1111 1111 1111 1111
  │ FMUL r2, r1, c3                         0000 0000 0000 0000 1111 1111 1111 1111
  │ FSUB r3, r2, c4                         0000 0000 0000 0000 1111 1111 1111 1111
 L_end:                                     1111 1111 1111 1111 1111 1111 1111 1111
  │ STG  [y], r3   （重汇聚后一起写回）       1111 1111 1111 1111 1111 1111 1111 1111
```

代价是清楚的：**A、B 两段都执行了，每段只有一半 lane 在干活**。最坏 2 倍（两条路径等长），最好 1 倍（所有 lane 走同一边，这叫「warp 一致 / warp-uniform」，编译器会专门优化这种分支）。

如果分支不是 2 路而是 `switch` 的 32 路（每条 lane 一个 case），就是 **32 倍**：硬件串行 32 遍，每遍 1/32 的 lane 有效。§16.1 那棵规则树是同一个形状的叠加。

### 循环次数不同：同一个除法

```
for (int i = 0; i < n[lane]; i++) acc += a[i];

lane 0–15：n = 5        lane 16–31：n = 20
→ warp 必须跑到 max(5, 20) = 20 次
→ 有用 lane-迭代 = 16×5 + 16×20 = 400
→ 实际执行 lane-迭代 = 32×20 = 640
→ 有效占比 = 400/640 = 62.5%
```

**注意 62.5% 不是「慢了 1.6 倍」而是「这部分算力打了 6.25 折」**——它不和别的损耗相加，它乘在 kernel 时间上。判断一个 kernel 的发散程度，`ncu` 里看这两个指标的比值即可：

| 指标 | 含义 | 健康值（量级） |
| --- | --- | --- |
| `smsp__thread_inst_executed_per_inst_executed` | 每条 warp 指令平均激活多少 lane | 接近 32 才好；20 以下说明有明显发散 |
| `smsp__sass_average_branch_targets_threads_uniform.pct` | 分支目标在 warp 内一致的比例 | 越高越好；低于 80% 要去看分支 |
| `sm__warps_active.avg.pct_of_peak_sustained_active` | 占用率（§16.4） | 不是越高越好，见 §16.4 |
| `smsp__inst_executed.avg.per_cycle_active` | 每个 scheduler 每 cycle 发射几条 | 上限 1.0，0.3 以下多半在等内存 |

### 重汇聚：硬件怎么知道「该合回来了」

warp 内部维护一个**活跃掩码 + 一个（或一栈）重汇聚点**。`if` 时把「另一条路的入口地址」压栈，执行完当前路径后弹栈跳到那里；两条路都执行完，掩码恢复全 1（重汇聚）。Volta 之后每个 warp 有独立 PC 和收敛管理，但**这不改变「一个 warp 一次只能发射一条指令」**——它只让重汇聚更省，发散本身照样要串行。

**一句话记住 §16.3：warp 是「指令流的车道组」，不是「32 个独立核」。凡是让 32 条 lane 走不同代码的东西，硬件都只能按「不同代码的条数」收费。**

## 16.4 延迟隐藏：GPU 不靠 cache，靠换 warp

### 先把延迟量级摆出来

HBM 的一次访问（发请求 → 数据回来）在 A100 上是 **400–800 cycle** 量级。按 1.41 GHz 算：

```
500 ns × 1.41 GHz ≈ 705 cycle
```

对比 CPU：L1 命中 4 cycle、L2 约 14、L3 约 40–70、DRAM 约 200–300 cycle。GPU 的 HBM 延迟**绝对值和 CPU 的 DRAM 差不多**（都是 DRAM 器件，`base/08`），但 GPU 的核**没有** CPU 那套「乱序 + 预测 + 大 cache」去挡它。它只有一招：**这个 warp 停了，就换下一个 warp**。

### Little 定律：需要多少在飞请求

排队论里最有用的一条公式，在这里是唯一的算法：

```
并发（in-flight）= 延迟 × 吞吐
```

三种写法，对应三个不同的问法：

| 问法 | 公式 | A100 的数 |
| --- | --- | --- |
| 要多少**字节**在飞才能喂满带宽 | `BW × latency` | 1555 GB/s × 500 ns ≈ **778 KB** |
| 折成多少个 128 B 请求 | `÷ 128 B` | ≈ **6074 个** |
| 每个 SM 要挂几个 | `÷ 108 SM` | ≈ **56 个** |
| 每个 warp 要挂几个（满占用 64 warp） | `÷ 64` | ≈ **0.88 个** |

最后一行最反直觉，也最有用：**满载时，每个 warp 只要平均有 1 个 128 B 的请求在飞，就足够把 HBM 带宽吃满。** 因为一个 warp 的一次 `LDG` 是 32 条 lane × 4 B = 128 B，一次就是一整条 cache line。

于是「占用率」和「每 warp 的并行度（MLP）」是**可互换的两种货币**：

| 每 SM 常驻 warp | 占用率 | 每 warp 需在飞 128 B 请求 | 怎么做到 |
| --- | --- | --- | --- |
| 64 | 100% | 0.88 | 一条 `float` 的合并访存就够 |
| 32 | 50% | 1.76 | 循环展开 2 次，或两个独立数组同时读 |
| 16 | 25% | 3.52 | 展开 4 次，或每线程改读 `float4` |
| 8 | 12.5% | 7.03 | 基本要靠 `float4` + 深展开 |

「每线程改读 `float4`」这一行值得单独算：一次 `LDG.128` 是 32 lane × 16 B = **512 B/请求**，请求数直接除以 4。所以在 16 warp（25% 占用率）下，用 `float4` 也能达到 0.88 个请求/warp——**这就是「向量化访存能救低占用率」的完整推导**，不是经验口诀。

### 指令侧：为什么 16 个 warp 填不满 800 cycle

换个角度，只看发射槽。每个 scheduler 有 16 个 warp，如果每个 warp 发一条指令就要等 800 cycle 才能发下一条（纯依赖链），那么：

```
每 cycle 发射概率 = 16 / 800 = 0.02 条/cycle
→ 单 scheduler IPC 0.02，4 个 scheduler 合计 0.08
→ 这就是「占用率不低但 kernel 很慢」的标准形状
```

不同管道的延迟决定了「需要多少 warp 才够」：

| 依赖的管道 | 典型延迟（cycle） | 1 IPC 需要的 warp 数 | 现实 |
| --- | --- | --- | --- |
| FP32 ALU（FMA） | 4 | 4 | 16 warp 绰绰有余 |
| shared memory | ~20–30 | 20–30 | 勉强，看 bank 冲突 |
| L2 命中 | ~200 | 200 | 不够，必须靠 ILP |
| HBM | 400–800 | 400–800 | **永远不够**，只能靠 MLP + 减少访存 |

所以一个成熟的 GPU kernel 的写法是**两头都做**：既把占用率维持在能接受的水平（通常 25%–50% 就够，不必追 100%），又在每个 warp 里塞进 4–8 个独立的访存/计算（展开、双缓冲、软件流水）。这就是 §16.7 说的「用软件代替硬件调度」。

```
时间线（一个 scheduler 里 4 个 warp 互相填坑）
cycle   0        200       400       600       800       1000
w0     [LDG]────stall(≈700 cycle)──────────────────────[FMA][STG]
w1        [LDG]────stall──────────────────────────────[FMA][STG]
w2           [LDG]────stall──────────────────────────[FMA][STG]
w3              [LDG]────stall────────────────────────[FMA][STG]
        └── 单看每个 warp 都在等；合起来，每 200 cycle 就有一条指令可发 ──┘
```

**但要诚实**：上图填的是**发射槽**，不是**带宽**。带宽够不够仍要回到 §16.4 第一张表的「在飞字节数」——两个账分开算，这是 GPU 性能分析里最常见的混淆。

## 16.5 层级：thread → warp → block → grid

### 四层，四种「共享什么」

| 层级 | 是什么 | 谁分配 | 上限（A100） | 共享什么 |
| --- | --- | --- | --- | --- |
| thread | 一条 lane，一个私有寄存器上下文 | 由 block 尺寸决定 | — | 与同 warp 的 31 条 lane 共享 PC |
| warp | 32 条 lane，**调度与发射的单位** | 硬件按 `threadIdx.x / 32` 切 | 64 / SM | 一条指令流 |
| block | 一组 warp，**调度的原子单位** | 程序员指定（≤1024 线程） | 32 个 block / SM | shared memory、`__syncthreads()`、block 内可见的 L1 |
| grid | 一次 kernel launch 的全部 block | 程序员指定 | 2³¹−1 个 block（x 维） | 只有全局内存与 L2 |

三条物理事实，全部由「block 是原子单位」推出来：

1. **一个 block 只能待在一个 SM 上**，不许跨 SM。所以 block 内的 `__syncthreads()` 才是廉价的（只是 SM 内的一条栅栏），block 间的同步则必须落回全局内存 + 原子操作（或者干脆起两个 kernel）。
2. **block 的资源一次占满**：寄存器、shared memory、warp 槽，在 block 放进去的那一刻就按「最大可能用量」划走。所以「我的 kernel 只用了一半 shared memory」不会自动让别的 block 挤进来——只要声明了，就按声明算。
3. **block 之间没有任何顺序保证**，也不该假设。同一份代码在 108 SM 和 132 SM 上执行顺序不同，这是可移植性的一部分，不是 bug。

### block 的尺寸：两头都是坑

以 256 线程/block 为例，一个 SM 要放 8 个 block（8 × 256 = 2048）才算满载。但两个上限会先卡住：

```
太小：block = 32 线程（1 warp）
  → 硬件上限 32 block/SM
  → 32 × 32 = 1024 线程 = 50% 占用率，永远上不去
  → 而且每个 block 都要独立算 shared memory / 同步开销

太大：block = 1024 线程（32 warp）× 64 寄存器/线程
  → 1024 × 64 = 65536 寄存器 = 一个 SM 的全部
  → 只能放 1 个 block，占用率 50%（32/64 warp）
  → 且只要有一个 warp 在等 barrier，整个 block 的另外 31 个 warp 也在等
```

寄存器是占用率的真正闸门，因为它是**按线程乘出来**的：

| 每线程寄存器 | 一个 SM 能放多少线程 | 占用率 | 典型来源 |
| --- | --- | --- | --- |
| 32 | 2048 | 100% | 极简 kernel（copy/scale） |
| 40 | 1638 → 实际 1536 | 75% | 简单逐元素 |
| 64 | 1024 | 50% | 常规 GEMM 的起点 |
| 96 | 682 → 实际 640 | 31% | 卷积/归约 |
| 128 | 512 | 25% | 重载 kernel，必须靠 ILP |
| 255（上限） | 257 → 实际 256 | 12.5% | 已接近 spill 边缘 |

（右列「实际」按 32 线程/warp 向下取整；真实值以 `ncu` 的 `launch__occupancy_limit_registers` 为准。）

### 波量化：1000 个 block 在 108 个 SM 上

这是「利用率上不去」最容易被忽略的一种：**不是 block 内的问题，是 grid 除不尽的余数**。

```
A100：108 SM，每 SM 可同时放 8 个 256 线程的 block → 864 个 block 槽位
grid = 1000 个 block
第 1 波：864 个 block 跑满
第 2 波：只剩 136 个 block → 736 个槽位空着（占用率 15.7%）
总时间 ≈ 2 × 单波时间
有效利用率 = 1000 / (864 × 2) = 57.9%
```

**修法不是「优化 kernel」，是改 grid 的形状**：把 1000 个 block 切成 864 或 1728 个（把工作切成更细的块，让余数摊薄），或者用 persistent kernel（起 864 个 block，每个 block 循环领取任务）。前者是「让除法整除」，后者是「把调度权从硬件拿回软件」。

### shared memory 与 `__syncthreads()`

shared memory 是 block 内的显式暂存区：A100 每 SM 192 KB（L1 与 shared 物理合一，最多切 164 KB 给 shared），H100 最多 228 KB。它存在的唯一理由是**复用**：一个 tile 被 block 内多个线程反复读时，从 HBM 读一次进 shared，比每个线程各读一次便宜一个数量级。

```
        HBM（1555 GB/s，~700 cycle）
              │  一次 tile 加载
              ▼
        ┌───────────────┐
        │ shared memory │  192 KB/SM，~20-30 cycle，180 GB/s/SM
        │  tile 16×16   │  ← block 内所有 warp 共享
        └───────┬───────┘
                │  __syncthreads() 之后才能读
        ┌───────┴───────┐
        │  寄存器 / FMA  │
        └───────────────┘
```

`__syncthreads()` 的语义只有一句：**block 内所有线程都到达这里，才允许继续**。由此推出两条硬规则：

1. **它只同步 block 内**。想让两个 block 同步，唯一正确的做法是「结束这个 kernel，再起一个」（或用 cooperative groups 的 grid sync，代价是整卡栅栏）。
2. **它不能出现在「部分线程会跳过」的分支里**。若某个 warp 因为 `if (threadIdx.x < 16)` 永远到不了 barrier，其余 warp 会一直等——不是报错，是挂死（或触发未定义行为）。这是最常见的挂死原因。

## 16.6 显存层级：从 255 个寄存器到几十 GB 的 HBM

### 五层，一张金字塔

```
                    容量                        延迟            带宽
                 ┌────────┐
  每线程寄存器    │ 255 个 │  256 KB/SM      1 cycle        ~20 TB/s（全卡，量级）
                 ├────────┤
  shared / L1    │ 192 KB │  每 SM          20–30 cycle    180 GB/s/SM ≈ 19.5 TB/s
                 ├────────┤
  L2              │ 40 MB  │  全卡共享        ~200 cycle     4–8 TB/s（量级）
                 ├────────┤
  HBM             │ 40/80GB│  全卡           400–800 cycle  1555–2039 GB/s
                 ├────────┤
  PCIe / NVLink   │ 主机   │  —              ~10 μs 量级    25 GB/s / 600 GB/s
                 └────────┘
```

| 层级 | 谁能看见 | 分配方式 | 命中/未命中的后果 |
| --- | --- | --- | --- |
| 寄存器 | 单个线程 | 编译器静态分配 | 不够 → **spill 到 local memory**（本节重点） |
| shared memory | block 内所有线程 | 静态声明或动态申请，block 生命周期 | 不够 → block 放不进 SM，占用率掉 |
| L1 | SM 内（与 shared 争同一块物理） | 硬件自动 | 命中省 ~600 cycle，但容量太小，命中率靠局部性 |
| L2 | 全卡 | 硬件自动 | 命中省一个数量级，是「跨 block 复用」的唯一希望 |
| HBM | 全卡 | 显存分配器（`cudaMalloc`/PyTorch caching allocator） | 不够 → OOM，或被迫换出（极慢） |

### 寄存器溢出：为什么它比「少几个核」严重一个数量级

寄存器是唯一「零延迟」的存储。编译器会尽量把变量放在寄存器里，但每个线程最多 255 个（硬件编码限制），而且**整个 SM 只有 65536 个**——两个线程抢一个寄存器时，编译器必须做选择。

放不下的变量去哪？**local memory**。名字叫 local，物理上它在**全局显存**里（每线程一段私有、按 32 线程交错的区域），访问它要走 L1/L2/HBM。于是一次「寄存器读」从 1 cycle 变成：

```
spill 一次 = STL/LDL（store/load local）
  L1 命中：~30 cycle
  L1 未命中、L2 命中：~200 cycle
  L2 未命中：~700 cycle
→ 是寄存器访问的 30–700 倍
```

如果 spill 发生在内层循环里（最典型：一个 4×4 的局部数组，索引是运行期变量），每次迭代都多几次 local 往返，kernel 直接慢一个数量级。**这就是「我明明只改了一个数组的大小，性能掉了 10 倍」的标准根因。**

两个必须知道的事实：

1. **`float a[4]` 且下标是常量 → 寄存器**；`float a[4]` 且下标是 `a[i]`（`i` 运行期才知道）→ **local memory**，因为它必须可寻址。这是「数组」在 GPU 上最反直觉的一点：数组不等于连续内存，它等于「能不能被静态展开」。
2. **`--maxrregcount` / `__launch_bounds__` 压寄存器，是在「spill」和「占用率」之间做交换**。压到 32 个能上 100% 占用率，但如果因此 spill 到循环里，100% 占用率也救不回来。判断依据只有一个：`ncu` 的 `launch__registers_per_thread` 与 `memory_l2_theoretical_sectors_global` 里 local 的部分。

### 由带宽推出的两个数

shared memory 的带宽是可以从规格推出来的：每个 SM 每个 cycle 能读写 128 B（32 bank × 4 B），1.41 GHz 下就是：

```
128 B × 1.41×10⁹ /s = 180 GB/s 每 SM
180 GB/s × 108 SM   = 19.5 TB/s 全卡
```

也就是说 **shared memory 的聚合带宽大约是 HBM 的 12.5 倍**（19.5 ÷ 1.555）。这正是「分块」的全部经济学：把一次 HBM 读换成 12 次 shared 读，只要 tile 被复用超过 1 次就赚（`base/20` 会把这条账算到 GEMM 的每一级）。

## 16.7 为什么 GPU 的核「笨」：省下来的面积去哪了

把前面几张表合成一张对照。左边是 CPU 核为「一条指令流」花的钱，右边是 GPU 用同样的钱买到了什么：

| CPU 核有 | GPU 没有 | 省下的面积换成了 | 代价（什么时候崩） |
| --- | --- | --- | --- |
| 分支预测（BTB + 方向表 + 返回栈） | 无预测、无推测执行 | 更多 FP32 lane | 分支密集的代码（§16.1 的规则树） |
| 乱序执行（ROB 几百项 + 重命名） | 严格按序，warp 内指令顺序发射 | 更多 warp（64 个） | 长依赖链：只能靠软件展开/重排 |
| 大 L1/L2 + 预取器 | 小 L1、无预取（靠合并访存） | 更高 HBM 带宽 + 更多寄存器 | 不规则访存（指针追逐、稀疏索引） |
| 每核独立取指/译码 | **1 份取指喂 32 条 lane** | 32× 的取指面积摊薄 | 发散（同一份指令喂不了两条路） |
| 深流水 + 高主频 | 浅流水 + 低主频（1.4 GHz 级） | 上千个 lane | 单线程延迟（一次访存 800 cycle 没人挡） |

三条推论，每条都能直接指导工程：

**① 取指摊销是 SIMT 的全部秘密。** 一个 CPU 核为了让「一条指令流」不停顿，要花面积在预测和乱序上；GPU 反过来——它把「取指/译码」这件事**除以 32**（一次取指服务 32 条 lane），于是同样的面积能放 32 倍的执行通道。这笔交易的前提是「32 条 lane 跑同一段代码」；一旦前提破了（发散），摊销立刻变成串行，而且是 32 倍地串行。**所以 GPU 的性能不是「并行度」问题，是「一致性」问题。**

**② 用「多 warp」代替「多指令」。** CPU 用乱序窗口在**一条**指令流里找并行（ILP），GPU 用 64 个 warp 在**多条**指令流之间找并行（TLP）。前者对程序员透明，后者要求程序员自己制造并行：展开循环、拆分独立累加器、双缓冲——这些「GPU 编程技巧」没有一条是玄学，全是「把 TLP 灌进硬件给的槽位」。

**③ 没有大 cache，是因为数据并行里没有复用。** cache 的经济学是「同一份数据被读多次」；而 GPU 的典型负载是「每个数据被读一次、算一次、写一次」（逐元素）或「一块数据被一个 tile 用几十次」（GEMM，这时用 shared memory 显式管）。所以它把钱花在**带宽**和**显式暂存**上，而不是**自动缓存**上。**「显存大、带宽高、cache 小」是同一个选择的三面。**

## 16.8 实测与估算：本机没有 GPU，所以只给公式和路径

### 先把话说清楚

**本机的运行环境里没有 NVIDIA GPU，`nvidia-smi` 不存在。** 所以本节不贴任何 GPU 命令的输出——贴了就是编的。下面所有数字分三类，每类都标清楚：

| 类别 | 来源 | 可信度 |
| --- | --- | --- |
| 规格值（SM 数、lane 数、带宽、容量） | 厂商公开规格 | 承诺值，可核对 |
| 推导值（TFLOPS、roofline 拐点、在飞字节） | 本篇公式 + 规格值 | 量级结论，可复算 |
| 实测值（你的卡跑出来多少） | **必须你自己跑** | 只有你的机器说了算 |

### 可复现路径 1：先把自己的卡读出来（不需要编译）

```python
import torch
p = torch.cuda.get_device_properties(0)
print("name        ", p.name)
print("SM count    ", p.multi_processor_count)
print("clock (GHz) ", p.clock_rate / 1e6)          # kHz -> GHz，注意这是 max clock
print("mem (GB)    ", p.total_memory / 2**30)
print("L2 (MB)     ", p.L2_cache_size / 2**20)
print("shared/block", p.shared_memory_per_block / 1024, "KB")
print("regs/block  ", p.regs_per_multiprocessor)

# 用规格值算峰值：SM × lane × 2(FMA) × clock
peak = p.multi_processor_count * 128 * 2 * (p.clock_rate * 1e3)
print("FP32 peak   ", peak / 1e12, "TFLOPS（假设每 SM 128 lane）")
```

三行要注意：`clock_rate` 是 **kHz**，要乘 `1e3` 才是 Hz；`multi_processor_count` 才是 SM 数（不要用 `torch.cuda.device_count()`，那是卡数）；**不同架构每 SM 的 lane 数不同**（A100 是 64，H100 是 128），脚本里写死 128 只对 Hopper/Ada 成立，A100 上要把 `128` 改成 `64`——这正是「数字要有出生证明」的意思。

### 可复现路径 2：A100 的 19.5 TFLOPS 完整算式

```
FP32 峰值 = SM 数 × 每 SM 的 FP32 lane 数 × 每 lane 每 cycle 的 FLOP × 时钟
         = 108 × 64 × 2 × 1.41×10⁹
         = 108 × 64 × 2.82×10⁹
         = 1.949×10¹³ FLOP/s
         ≈ 19.5 TFLOPS
```

那个 `2` 是 FMA（fused multiply-add）：一条 `a*b+c` 算 2 次浮点运算。这是**承诺值**（boost 时钟下的理论峰值），任何真实 kernel 都到不了——能到 70%–85% 已经是很好的 GEMM。同法算 H100：`132 × 128 × 2 × 1.98×10⁹ ≈ 66.9 TFLOPS`。

顺手得到两个能直接用的推论：

```
每 SM 的算力 = 19.5 TFLOPS / 108 = 180.5 GFLOPS
roofline 拐点 = 19.5×10¹² / 1.555×10¹² = 12.53 FLOP/byte
```

**第二行是判据**：一个 kernel 的算术强度（FLOP/byte）低于 12.5，它一定卡在带宽上，优化 ALU 毫无意义；高于 12.5 才轮到算力（`base/17` 会把这条线画成图）。

### 可复现路径 3：本机就能跑的纯算术（下面是真实输出）

这段不需要 GPU，它把本篇所有推导数算一遍。**它证明的是「公式自洽」，不是「你的卡有多快」**：

```python
SM, CORE, CLK, BW, LAT = 108, 64, 1.41e9, 1555e9, 500e-9
peak = SM * CORE * 2 * CLK
print("A100 FP32 =", f"{peak:.4g}", "FLOP/s")
print("每 SM     =", f"{peak/SM/1e9:.1f}", "GFLOP/s")
print("拐点      =", f"{peak/BW:.2f}", "FLOP/byte")
inf = BW * LAT
print("在飞字节  =", f"{inf:.0f}", "B; 128B 请求 =", f"{inf/128:.0f}",
      "; 每 SM =", f"{inf/128/SM:.1f}")
for w in (64, 32, 16, 8):
    print(f"  {w:>2} warp/SM -> 每 warp 需在飞 {inf/128/SM/w:.2f} 个请求")
print("float4(512B) @16 warp ->", f"{inf/512/SM/16:.2f}")
print("1000 block / 864 槽 ->", -(-1000//864), "波, 效率",
      f"{1000/(864*2)*100:.1f}%")
```

```
A100 FP32 = 1.949e+13 FLOP/s
每 SM     = 180.5 GFLOP/s
拐点      = 12.53 FLOP/byte
在飞字节  = 777500 B; 128B 请求 = 6074 ; 每 SM = 56.2
  64 warp/SM -> 每 warp 需在飞 0.88 个请求
  32 warp/SM -> 每 warp 需在飞 1.76 个请求
  16 warp/SM -> 每 warp 需在飞 3.52 个请求
   8 warp/SM -> 每 warp 需在飞 7.03 个请求
float4(512B) @16 warp -> 0.88
1000 block / 864 槽 -> 2 波, 效率 57.9%
```

### 可复现路径 4：在真卡上量「到底卡在哪」

工具是 Nsight Compute（`ncu`），一次典型调用：

```bash
ncu --set full --kernel-name regex:my_kernel \
    --launch-count 1 --export profile ./my_kernel \
    python bench.py
```

只看四个指标就能定性，不用读完整报告：

| 你问的问题 | 指标 | 判据（量级） |
| --- | --- | --- |
| 是不是带宽瓶颈 | `gpu__compute_memory_throughput.avg.pct_of_peak_sustained_elapsed` | >80% → 卡带宽，别再调 ALU |
| 是不是算力瓶颈 | `sm__throughput.avg.pct_of_peak_sustained_elapsed` | >80% 且上一条低 → 卡算力 |
| 占用率被谁限住 | `launch__occupancy_limit_registers` / `_shared_mem` / `_blocks` / `_warps` | 看哪个是 `Yes`，那就是根因 |
| 发散有多严重 | `smsp__thread_inst_executed_per_inst_executed` | 接近 32 才好；<20 去查分支 |
| 有没有 spill | `launch__registers_per_thread` + `memory_l2_...local` | 寄存器接近 255 且有 local 流量 → spill |

**顺序很重要**：先看「卡带宽还是卡算力」（这是物理天花板），再看「占用率被谁限住」（这是你唯一能改的旋钮），最后才看发散。反过来做，就会陷入「把占用率从 40% 调到 42%」的无效优化。

## 16.9 三列账：承诺、代价、崩点

| 维度 | 承诺了什么 | 为此付了什么 | 从哪里开始失效 |
| --- | --- | --- | --- |
| 取指摊销 | 一次取指喂 32 条 lane，面积效率 32× | 32 条 lane 必须同进同退 | 分支发散：2 路 → 2×，32 路 → 32×；循环次数不均 → 按最大值计费 |
| 吞吐优先 | 上千 lane 同时算，峰值 19.5 TFLOPS（A100 FP32） | 单线程延迟极差（一次 HBM 800 cycle 无人遮挡） | 数据依赖链、串行归约、小规模问题（填不满 108 个 SM） |
| 用 warp 换延迟 | 不需要大 cache、不需要乱序，靠 64 warp 轮转 | 必须维持足够占用率或足够的每 warp 并行度 | 寄存器/共享内存吃满 → 占用率掉 → 延迟藏不住 |
| 显式存储层级 | shared memory 19.5 TB/s（HBM 的 12.5 倍） | 要手工分块、手工同步，且容量极小（164 KB/SM） | bank conflict、tile 切错、`__syncthreads` 漏写/多写 |
| 大量弱核 | 108 个 SM 便宜地堆出来 | block 是原子单位，粒度粗 | grid 除不尽（波量化）、block 太大放不进、太小占不满 |
| 高带宽 HBM | 1.5–2 TB/s，是 CPU 的 20–30 倍 | 数据必须先搬上卡；容量只有几十 GB | PCIe 往返 25 GB/s、OOM、kv-cache 挤爆（`comp/49`） |
| 编程模型 | 一套 `thread/block/grid` 抽象，可移植 | 要自己管层级、同步、边界 | 把 GPU 当「更快的 CPU」写：分支密集 + 指针追逐 + 频繁小 kernel |

一句话收束：**GPU 买到的是「每 FLOP 的面积和每字节的带宽」，付出的是「一致性、延迟、显式管理」三笔钱。** §16.1 的 50 倍、§16.4 的 0.88 个请求、§16.6 的 spill，都是这三笔钱的不同账单。

## 16.10 踩坑清单：现象 → 根因 → 定位 → 修 → 防

| 现象 | 根因（指回本篇） | 定位 | 怎么修 | 怎么防复发 |
| --- | --- | --- | --- | --- |
| kernel 只跑出峰值的 5%，`ncu` 说占用率 12% | 寄存器吃满（§16.6 的表），每线程接近 255 | `launch__registers_per_thread`、`launch__occupancy_limit_registers` | 减局部数组、拆分 kernel、必要时 `__launch_bounds__` 压寄存器（但要先确认不 spill） | 把「每线程寄存器 ≤64」写进 kernel 设计约束；CI 里跑一次 `ncu` 基线 |
| 明明 100% 占用率，还是慢 | 每 warp 的 MLP 不足，靠 warp 数硬撑（§16.4） | `l1tex__throughput`、`gpu__compute_memory_throughput`、看是否 <80% 却仍慢 | 展开循环、`float4` 访存、一个 warp 挂多个独立请求 | 用「在飞字节 = BW × 延迟」先算需求，再决定占用率目标 |
| 加了个 `if`，性能掉一半 | 分支发散，两条路都执行（§16.3） | `smsp__thread_inst_executed_per_inst_executed` 从 32 掉到 16 | 改写成 `select`/谓词、按分支分组数据、把分支提到 kernel 外 | 数据并行代码里禁「按元素走不同路径」；用 warp-uniform 判断 |
| 程序挂死，不报错 | `__syncthreads()` 在部分线程跳过的分支里（§16.5） | `cuda-gdb` 看卡在 barrier 的 warp；`compute-sanitizer --tool synccheck` | 把 barrier 移出分支，或改成「所有线程都到达」的写法 | 代码评审硬规则：`__syncthreads` 不许在 `if (threadIdx...)` 内 |
| shared memory 版本比全局还慢 | bank conflict：stride 是 32 的倍数（§16.6） | `l1tex__data_bank_conflicts_pipe_lsu_mem_shared` | 数组补一列（`[16][17]` 而不是 `[16][16]`） | tile 宽度避开 32 的倍数；用 `ncu` 基线卡住冲突数 |
| 小 kernel 一大堆，GPU 利用率很低 | 启动开销 5–10 μs/次，且每次都要同步（§16.8） | `ncu` 看 kernel 时长；`nsys` 看时间轴上的空隙 | 合并 kernel、批处理、CUDA Graph 捕获 | 规定「单个 kernel <50 μs 就要问为什么」 |
| 端到端不到 2 倍，kernel 快 40 倍 | Amdahl：只有一段被加速（§16.1） | `nsys` 时间轴，把每段标上占比 | 把前后处理也搬上卡，或减少 H2D/D2H | 迁移前先画「段-占比」表，算理论天花板 |

**三行总结这张表**：看到「占用率低」，先查寄存器与 shared memory 的静态占用，再查 grid 是否除不尽；看到「占用率不低却慢」，先查每 warp 的并行度和带宽；看到「结果对但慢一个数量级」，先怀疑 spill 和 bank conflict——这两个都不会报错，只会静静地把 1 cycle 变成 700 cycle。

## 16.11 一页速记

```
【一句话】GPU 是用控制逻辑换并行度的机器：1 份取指带 32 条 lane，
         所以它只能跑「同一段代码处理不同数据」。

【四个数字（A100）】
  108 SM × 64 FP32 lane × 1.41 GHz × 2(FMA) = 19.5 TFLOPS
  每 SM：4 scheduler / 64 warp / 2048 thread / 65536 寄存器 / 192 KB L1+shared
  roofline 拐点 = 19.5e12 / 1.555e12 = 12.5 FLOP/byte
  在飞字节 = 1555 GB/s × 500 ns ≈ 778 KB ≈ 每 SM 56 个 128B 请求

【三条推论】
  ① 发散 = 按「不同代码的条数」收费：2 路 2×，32 路 32×
  ② 延迟不靠 cache 靠换 warp：64 warp 满载时每 warp 只需 0.88 个在飞请求；
     16 warp 时需 3.5 个 → 要么展开，要么读 float4（512B/请求）
  ③ 寄存器 255/线程是硬顶：放不下 → local memory（物理在显存）→ 慢 30–700 倍

【三个层级】
  thread → warp(32) → block(≤1024, 原子单位, 共享 shared + __syncthreads) → grid
  占用率闸门：寄存器 > shared memory > block 数 > warp 槽
  波量化：1000 block / 864 槽 = 2 波，利用率 57.9%

【三笔代价】
  一致性（发散）· 延迟（依赖链）· 显式管理（分块/同步/搬运）
```

## 16.12 自检 3 题

**Q1.** 一个 warp 里，`if (x > 0) y = a*x + b; else y = c*x + d;`，32 条 lane 中恰好 16 条走 A、16 条走 B。这个 warp 执行这条语句，理论上要花几条指令的时间？如果 32 条 lane 各走一个不同的 `switch` 分支，又是几倍？请用「活跃掩码」解释，并说明为什么「最坏 2 倍」不是笔误。

<details><summary>答案</summary>

A、B 两条路径都要执行，每条路径的指令都只对 16 条 lane 有效，所以耗时是「两条路径指令数之和」。若两条等长（各 `k` 条），总耗时 ≈ `2k`，即**单条路径的 2 倍**——这就是「最坏 2 倍」。

32 路 `switch` 则是 32 条路径依次执行，每遍只有 1 条 lane 有效，总耗时 ≈ `32k`，即 **32 倍**。硬件不变，变的是「不同代码的条数」。

「最坏 2 倍」不是笔误，因为 `if-else` 只有两条路径：硬件把两条都跑一遍（掩码先 `0x0000FFFF` 后 `0xFFFF0000`），然后重汇聚回 `0xFFFFFFFF`。它不能只跑一条——因为另一半 lane 需要另一条。**发散的代价 = 该 warp 内不同路径的条数，而不是「分支指令的条数」。**

另外：如果 `x > 0` 在 32 条 lane 上结论一致（warp-uniform），硬件只跑一条路，代价是 1 倍——所以「按分支分组数据」是真实存在的优化。
</details>

**Q2.** 某 kernel 占用率只有 25%（每 SM 16 个 warp），但它的带宽利用率却接近 100%。这矛盾吗？请用 Little 定律算一遍，并说出两种「在低占用率下仍然吃满带宽」的写法。如果这个 kernel 的算术强度只有 4 FLOP/byte，它的上限是什么？

<details><summary>答案</summary>

不矛盾。Little 定律：`在飞字节 = 带宽 × 延迟 = 1555 GB/s × 500 ns ≈ 778 KB`，折成每 SM 约 56 个 128 B 请求。16 个 warp 分摊，每个 warp 需要 `56/16 ≈ 3.5` 个在飞请求。

只要每个 warp 同时挂 3–4 个独立的 128 B 请求，就能在 25% 占用率下吃满带宽。两种写法：

1. **循环展开 + 多个独立累加器**：一次发 4 个 `LDG`，它们的地址互不依赖，硬件可以同时在飞；
2. **向量化访存**：每线程读 `float4`，一个 warp 一次请求就是 32×16 B = 512 B，请求数直接除以 4，于是 16 warp 下每 warp 只需 `56×128/512/16 ≈ 0.88` 个请求。

算术强度 4 FLOP/byte 远低于 A100 的拐点 12.5 FLOP/byte，所以它**必然卡在带宽上**：上限 = `1555 GB/s × 4 FLOP/byte ≈ 6.2 TFLOPS`，只有峰值 19.5 TFLOPS 的 32%。此时优化 ALU、提高占用率都没用，唯一有意义的方向是**减少字节数**（改变数据布局、复用、压缩、把中间结果留在 shared/寄存器）。
</details>

**Q3.** 一个 kernel 在 A100 上跑，grid 是 1000 个 block，每 block 256 线程、每线程 64 个寄存器、每 block 用 40 KB shared memory。请算出它每个 SM 能放几个 block、占用率多少、总共几波、理论利用率多少；并说出三个「不改算法只改形状」就能提速的方向。

<details><summary>答案</summary>

逐个上限算，取最小值：

- **寄存器**：65536 / (256 × 64) = **4 个 block**（恰好用满 65536 个寄存器）；
- **shared memory**：164 KB 可用 / 40 KB = **4 个 block**；
- **线程/warp**：2048 / 256 = 8 个 block（warp 槽 64/8 = 8）；
- **硬件 block 上限**：32 个。

所以每 SM 只能放 **4 个 block**（寄存器与 shared 同时卡在 4），即 1024 线程 = 32 warp = **50% 占用率**。

槽位 = 108 SM × 4 = 432 个 block；1000 / 432 = 2.31 → **3 波**；利用率 = 1000 / (432 × 3) = **77.2%**（最后一波只有 136 个 block，占 31.5% 的槽位）。

三个「只改形状」的方向（注意：这个例子里**两个闸门同时卡在 4**，只松一个没用，这是最容易白干的地方）：

1. **改 grid 形状**：把 1000 个 block 合成 432 或 864 个（每个 block 多领几份活），或用 persistent kernel 起 432 个 block 循环领取任务 → 第三波消失，时间从 3 波降到 2.31 波，**1.30×**；
2. **同时松两个闸门**：寄存器压到 ≤42（65536/(256×42) = 6）**且** shared 降到 ≤27 KB（164/27 = 6）→ 6 个 block = 1536 线程 = 75%；只降一个仍然是 4 个 block，占用率纹丝不动；
3. **不动占用率，抬每 warp 的 MLP**：32 warp 时 Little 定律只要求 `56/32 = 1.76` 个在飞请求。若当前每个 warp 只有 1 个，带宽只能到 `1/1.76 ≈ 57%`；展开一次或改读 `float4` 就能补齐——**这条路常常比追占用率更便宜**。

反过来，把 block 改小到 128 线程是**负优化**：寄存器允许 8 个 block，但 40 KB shared 只允许 4 个，于是 4 × 128 = 512 线程 = 25%，比原来还低。**先算清谁在卡，再动手。**
</details>
