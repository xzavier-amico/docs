## 01.1 引子：三个「背得出，推不出」的现场

三个场景，三个人，同一种断层。

**现场一（会话，2024-11，某支付公司茶水间）。** 同事问：「网关 `TIME_WAIT` 堆了 6 万个，`tcp_tw_reuse` 打开是不是就好了？」你答得很顺：「`TIME_WAIT` 是主动关闭方的义务，不能乱关。」他追问一句「**为什么是 60 秒，不是 6 秒？**」——你卡住了。因为你记住的是「义务」这个词，而 60 秒这个数字来自另一条东西：**任何 TCP 段的存活时间不能超过 MSL（2 分钟量级），主动关闭方必须保证「自己最后一个 ACK 丢了、对方重发的 FIN 还能被正确应答」的时间窗 = 2 × MSL**。这条约束一写出来，`tcp_tw_reuse` 在干什么也顺带清楚了：它不是「关掉 TIME_WAIT」，它是**赌网络上没有迟到包**。

**现场二（评审，2025-03，一次缓存方案评审）。** 设计文档写着：「热点 key 上本地缓存，Redis 兜底，5 万 QPS 没问题。」有人问「5 万 QPS 的瓶颈落在哪一层？」回答是「加机器」。评审最后通过了——通过的原因不是方案对，而是**没人能把它证伪**。真实的账是：5 万 QPS ÷ 2 核 = 每核 25,000 次/秒 = **每次 40 µs 预算**，而一次 Redis 往返（同机房 RTT 50–100 µs，见 §01.3）单这一项就超预算 1.25–2.5 倍。这一条不需要压测，**算一遍就塌**。

**现场三（排障，2025-07 凌晨，P99 从 40 ms 涨到 200 ms）。** CPU 30%、内存正常、磁盘不忙、下游 RT 没变。群里同时冒出三种意见：「加核」「换 JSON 库」「上更细的 P99 监控」。没有一种意见在回答那个唯一有意义的问题：**这 160 ms 落在哪一层？** 而这个问题可以被回答——一旦你手上有 §01.3 那张表，知道「一次 syscall 107 ns」「一次 minor 缺页 ≈ 1 µs」「一次同机房 RTT 50–100 µs」「一次 SATA 随机读 100 µs」「一次 HDD 寻道 10 ms」，你会先算**次数**：160 ms ÷ 100 µs = 1,600 次 RTT；160 ms ÷ 1 µs = 16 万次缺页；160 ms ÷ 10 ms = 16 次寻道。次数一出来，嫌疑面立刻从「全部」缩到「能凑出这个次数的那个循环」。

三个现场的共同形状：**结论还在，出生证明丢了。** 结论能被复述，所以面试能过；出生证明丢了，所以场景一微调（60 秒改 5 秒、2 核改 32 核、同机房改跨城），同一句话就从「知识」退化成「口头禅」。

## 01.2 唯一真问题：一把尺子，量 56 次

**判「懂没懂」只有一个标准：能不能说出这条结论由哪条物理约束推出来。**

这个标准里没有「读过源码」「做过项目」「能画架构图」——因为那些都可能绕过它。它也不要求你记住结论：结论是推导的产物，**产物可以随时重算，出生证明不能**。

这把尺子有四个刻度，任何一条结论都要能在四格上填满：

| 刻度 | 问法 | 不合格的回答 | 合格的回答（以「`write()` 成功 ≠ 落盘」为例） |
| --- | --- | --- | --- |
| ① 约束 | 它由哪条物理事实逼出来？ | 「文件系统就是这么设计的」 | 磁盘最小的可原子写单位是扇区（512 B / 4 KB），内核不可能每次 `write` 都同步等盘（100 µs–10 ms 量级） |
| ② 量级 | 这条约束给出的数是多少？ | 「很慢」 | `write` = 一次 syscall（154 ns 实测）+ 两次内存拷贝；`fsync` = 一次器件级 flush（100 µs–10 ms）→ **差 3–5 个数量级** |
| ③ 承诺 | 它换来了什么？ | 「性能好」 | 「写入延迟与磁盘无关」——应用看到的 `write` 是内存速度 |
| ④ 崩点 | 它在什么条件下失效？ | 无（这是最常见的症状） | 掉电 / panic 时页缓存里未回写的脏页全丢；跨机器读同一文件看不见最新内容 |

**填不出④的结论，等于没懂。** 因为工程上所有事故都住在④里：④没写出来的方案，看起来永远是对的。

再补一条操作层判据，它把「懂」变成可当场执行的动作：**能用一条命令把它量出来吗？** 这就是本套 11 篇「实例剖析」存在的全部理由（§01.7）。`objdump` / `perf` / `strace` / `tcpdump` 各自的覆盖范围，就是这本书四层结构的另一面。

于是全书 = 同一把尺子量 56 次：每次只换「被量的那条约束」。**这也是为什么本套不要你背任何定义**——定义是 ① 的缩写，②③④ 才是内容。

### 指针追逐：把每一级缓存量出来

缓存延迟不是「查表得到」的，是**测**出来的：在数组里建一条随机置换的环，然后跟着指针走。环多大，数据就只能住在那一级缓存里。

```c
#include <stdio.h>
#include <stdlib.h>
#include <time.h>
static double now(void){struct timespec t;clock_gettime(CLOCK_MONOTONIC,&t);return t.tv_sec+t.tv_nsec*1e-9;}
int main(int argc,char**argv){
  long steps=2000000;
  for(int k=1;k<argc;k++){
    long bytes=atol(argv[k]), n=bytes/sizeof(long);
    long *a=malloc(bytes), *p=malloc(n*sizeof(long));
    for(long i=0;i<n;i++)p[i]=i;
    for(long i=n-1;i>0;i--){long j=rand()%(i+1),t=p[i];p[i]=p[j];p[j]=t;}
    for(long i=0;i<n;i++)a[p[i]]=p[(i+1)%n];    /* a[] 里存的是链上"下一个下标" */
    long idx=0;
    for(long i=0;i<100000;i++)idx=a[idx];        /* 预热，把整条环拉进缓存 */
    double t0=now(); for(long i=0;i<steps;i++)idx=a[idx]; double t1=now();
    printf("%8ld KB  %7.2f ns/access  (sink=%ld)\n",bytes/1024,(t1-t0)/steps*1e9,idx);
    free(a); free(p);
  }
}
```

```
$ gcc -O2 -o chase chase.c && ./chase 32768 262144 4194304 67108864
      32 KB     1.71 ns/access  (sink=3996)
     256 KB     4.12 ns/access  (sink=28857)
    4096 KB    13.84 ns/access  (sink=20389)
   65536 KB   120.95 ns/access  (sink=6702058)
```

四级台阶正好对上 `lscpu -C` 的四级缓存：32 KB 全在 L1d（64 KB）→ **1.71 ns**；256 KB 撞进 L2（512 KB）→ **4.12 ns**；4 MB 还在 L3（16 MB）里 → **13.84 ns**；64 MB 溢出到 DRAM → **120.95 ns**。**L1 到 DRAM 跨了 70 倍**——这一个数字就是「数据结构决定性能」的完整物理依据，也是 `base/07` 全篇要展开的那条约束。

### 系统调用的价

```c
#define _GNU_SOURCE
#include <stdio.h>
#include <time.h>
#include <unistd.h>
#include <sys/syscall.h>
#include <fcntl.h>
static double now(void){struct timespec t;clock_gettime(CLOCK_MONOTONIC,&t);return t.tv_sec+t.tv_nsec*1e-9;}
int main(void){
  long n=5000000; volatile long sink=0; double t0,t1;
  t0=now(); for(long i=0;i<n;i++) sink+=syscall(SYS_getpid); t1=now();
  printf("getpid         %7.2f ns/call  (%.0f cycles)\n",(t1-t0)/n*1e9,(t1-t0)/n*2.6e9);
  int fd=open("/dev/null",O_WRONLY);
  t0=now(); for(long i=0;i<1000000;i++) sink+=write(fd,"x",1); t1=now();
  printf("write(1 byte)  %7.2f ns/call\n",(t1-t0)/1000000*1e9);
}
```

```
getpid           106.59 ns/call  (277 cycles)
write(1 byte)    154.33 ns/call
```

`write` 比 `getpid` 贵 48 ns，多出来的是「把 1 字节从用户地址空间拷进页缓存」与 fd 表查表。**这 154 ns 是全书最贵的一个常数**：凡讲「批处理 / 零拷贝 / `io_uring`」的篇目（`base/21`、`base/31`、`base/32`、`base/37`）都在跟它算账。

### 这张表里哪些是「量级」，假设是什么

**必须先承认六条假设**，否则表就变成了另一种八股：

1. **频率按 2.6 GHz 折算 cycle**。`cpu MHz` 是瞬时值，睿频/降频让同一段代码的 cycle 数不变、纳秒数变 ±30%。要对比两台机器，**先比 cycle，再比纳秒**。
2. **缓存数字来自这台 KVM 虚拟机**。L3 标 16 MB（`ALL-SIZE 32M` 是两路合计），所以 4 MB 的环还能命中；你自己的机器可能是 8 MB 或 96 MB，台阶位置会移动，但**台阶的存在与 10 倍以上的落差不会变**——那才是量级结论。
3. **DRAM 的 121 ns 偏高**。KPTI 双页表 + 虚拟化退出让它比裸金属的 70–90 ns 更贵。量级结论只到「百纳秒级」，**不要引用到小数点**。
4. **NVMe / SATA / HDD / RTT 四行是「承诺值」或「量级」，不是本机实测**。本机 `dd` 打出 1.3 GB/s 是顺序带宽 + 内存级后备存储，与随机 IOPS 无关。器件数字来自「拿 datasheet 的量级参数做算例」，用的时候必须在你自己的机器上重新量。
5. **网络两行假设无拥塞、无丢包**。一旦有 1% 丢包，跨城 RTT 就从 25 ms 变成「25 ms × 重传次数」——这正是 `base/51` 要用 `tc netem` 证明的事。
6. **所有 µs 以上的数字都是「空队列下的服务时间」**。系统真正观测到的延迟 = 服务时间 + **排队**时间，而排队那一半归主线②，不属于这张表。

**三类结论必须分清**（总纲 §0.7 第 2 条）：

- **实测**（L1 / L2 / L3 / DRAM / syscall / 切换 / AES）：本机跑出来的，可引用到两位有效数字，但必须带机器型号。
- **量级**（寄存器、NVMe、SATA、HDD、RTT、缺页）：由物理参数算出来的数量级，**只在「差几倍 / 差几个数量级」的意义上成立**。
- **承诺**（器件 datasheet 的 IOPS 与延迟）：厂商在最优条件下测的，**只能当上界**。

## 01.4 三个示范：把纳秒推到工程结论

用表的方法是固定动作：**拿一条约束 + 一个次数，乘出结论**。三个示范，正好对应后面三大部分。

**示范一（主线③）：为什么「一次 `write` 写 1 字节」是灾难。** 实测 `write(1 B) = 154 ns`。写 1 KB 分 1,024 次 = **158 µs**；一次 `write(1 KB)` = 154 ns + 1 KB 内存拷贝（按 10 GB/s ≈ 0.1 µs）≈ **250 ns**。**差 630 倍，业务逻辑一模一样。** 所以结论不是「用缓冲更好」，而是「跨界单价 × 次数」——`base/21` 解释内核为什么收这个价，`base/31`、`base/36` 用 `strace -c` 把次数摊在屏幕上。

**示范二（主线②）：为什么两个计数器要用 padding 隔开。** 两个 `long` 落在同一条 64 B cache line 上，两个核各写各的：每次写都把对方的 line 从「独占」打回「失效」，对方下次写就得多付一次**跨核一致性往返**，量级取 L3 那一级 = **13.8 ns**（本机实测）。10⁹ 次自增 = **13.8 s 的纯浪费**。这是 `base/19` 用 `perf c2c` 要量的东西，也是 `base/13` 讲 MESI 时唯一需要记住的数字。

**示范三（主线②④）：为什么 1 Gbps 链路配 30 ms RTT 只有 3.75 MB 在途。** 带宽时延积 BDP = 125 MB/s × 0.03 s = **3.75 MB**。要让这条链路跑满，发送方必需有 3.75 MB「已发出、未确认」的数据；窗口小于它，吞吐上限就被 `窗口 ÷ RTT` 卡死，**跟带宽无关**。1% 丢包下 CUBIC 把丢包读成拥塞、主动砍半窗口，于是吞吐塌到 1/10；BBR 读成链路噪声，靠带宽与 RTT 估计维持窗口——**这不是「算法好坏」，是两个算法对同一条约束的不同解释**（`base/42` 的机制、`base/51` 的证据）。

三个示范都只用表里一个数 + 一个次数。**这就是这把尺子的全部用法：不给结论，给乘法。**

## 01.5 三层账本：后面 55 篇都在往这三张表里填格子

本书不按「知识点」组织，按**层**组织。每一层只做一件事：**用一个抽象，遮住下面那层的物理混乱**。遮住 = 承诺；遮挡的成本 = 代价；遮不住的地方 = 崩点。

| 层 | 它承诺什么 | 它为此付什么 | 它从哪里开始失效 |
| --- | --- | --- | --- |
| **位层**（Part I，02–09） | 一个数就是一个值；加减乘除与十进制直觉一致 | 固定位宽上的模运算：溢出环绕、精度由尾数位数预先限定、`0.1` 无法精确表示；跨字节含义全靠约定 | 值超出可表示范围（溢出 / 精度丢失 / 大数吃小数）；两端约定不一致（大小端、编码、对齐） |
| **内核层**（Part II–III，10–37） | 每个进程独占一台机器：独占 CPU、独占内存、文件是字节流 | 每次「假装独占」都要拦一次 CPU（syscall 107 ns）、填一次页表（缺页 1 µs）、等一次调度（切换 2 µs）、拷一次数据 | 次数太多（syscall / 缺页 / 切换的**次数**乘单价超预算）；资源真的用光（OOM、fd 泄漏）；崩溃时承诺兑不了现（`write` ≠ 落盘） |
| **协议层**（Part IV–V，38–56） | 对端能证明身份、数据在途中可被检测篡改、内容可被保密 | 每层头部 20–60 B + 每层状态机 + 每次握手往返 1–3 RTT + 加密的单字节成本 | 某一项承诺由谁提供、覆盖哪一段没说清；`RTT × 次数` 超预算；中间盒、代理终止或旁路让「端到端」不成立 |

这张表有个关键性质值得单独说：**三层的代价单位不一样，而且不能互换。** 位层花的是**精度**，内核层花的是**次数**，协议层花的是**往返**。所以「加机器」治不好「精度丢了」，也治不好「握手多一跳」——**每一次错误的优化，都是拿错层的钱去买另一层的账。**

后面 55 篇的分布，就是把这三张表填满：

| 层 | 填格子的篇 | 你会拿到的一条硬结论（举例） |
| --- | --- | --- |
| 位层 | `base/02`–`base/05`（表示）、`base/06`（约定）、`base/07`–`base/08`（存储与器件）、◆`base/09` | `-x ≡ 2ⁿ - x`；`0.1 + 0.2 ≠ 0.3` 不是 bug；cache line = 64 B；SSD 随机写慢在擦除块 |
| CPU 子层 | `base/10`–`base/15`、`base/16`–`base/18`、◆`base/19`、◆`base/20` | 流水线上同时飞几十条；多核并不共享内存；功耗 ∝ f·V²，提频最贵、堆核最便宜 |
| 内核层 | `base/21`–`base/33`、◆`base/34`–◆`base/37` | 进程 = 地址空间 + 内核簿记；`malloc(100)` 通常不向内核要内存；收包要过六道门 |
| 协议层 | `base/38`–`base/48`、◆`base/49`–◆`base/52` | 每层头部 = 它替下层补的窟窿；TIME_WAIT 是义务不是参数；SNI/证书/应用身份各管一段 |

## 01.6 四条贯穿全书的主线

这四条不是「主题」，是**判据**：任何一条优化经验或安全实践，如果不能用下面四条之一解释，大概率已经过时。每条后面跟一个用 §01.3 数字算出来的最小例子。

| 主线 | 一句话 | 用它一眼解释掉的东西 | 最小例子（带数字） |
| --- | --- | --- | --- |
| **① 没有魔法，只有位与约定** | 从晶体管到 TLS，全是「同一批字节 + 一套约定」；约定在哪一层，责任就在哪一层 | 补码 / 大小端 / 对齐 padding / 编码 / 序列化 / TCP 头部 / 证书链 | 同一个 4 字节值 `0x00000001`，小端机器内存里是 `01 00 00 00`；`struct {char c; long x;}` 从 9 B 被 padding 到 16 B——**多出的 7 B 是约定费** |
| **② 快慢只有一种解释——排队** | 性能问题永远是「某一层队列满了」或「跨界次数太多」；CPU 只是队列的处理者 | 中断风暴 / 软中断 backlog / 网卡队列 / socket 缓冲 / 锁等待 / runqueue / `load average` | 5 万 QPS ÷ 2 核 = 每请求 40 µs 预算；一次 Redis 往返 50–100 µs → **单这一项就超预算 1.25–2.5 倍**，与 CPU 快慢无关 |
| **③ 每层抽象的单价 = 跨界次数 × 单次成本** | syscall / 缺页 / 切换 / RTT 的价都是固定量级；架构设计就是在买这些单 | `read` 1 B / `mmap` / 零拷贝 / `epoll` 批量 / 用户态协议栈 / batch 化 | 107 ns × 10⁶ 次 = **107 ms** 的纯 syscall 开销；`io_uring` 把它压到 10³ 次 = **107 µs** |
| **④ 安全要按层核对** | 分别问认证、完整性、机密性由谁提供、覆盖哪一段，以及该层不保证什么；可用性和业务授权另算 | 基础 ARP/DNS 不提供密码学身份 → 投毒与劫持；TCP 无认证 → 注入与 RST；IP 可伪造源 → 反射放大；HTTP 明文 → 中间盒；TLS 补通道，证书校验绑定对端；DNSSEC 只验签名数据，DoH 只保护到解析器的一跳 | 一次 TLS 1.3 握手 1 RTT = 25 ms（京↔沪）；若每请求都重握手，10 万 QPS 需要 10 万 × 25 ms 的并发在途量 = **2,500 个连接只为握手存在** |

**主线②与③是同一枚硬币**：②说「慢在等」，③说「等一次多少钱」。②负责定位到层，③负责把层的价算出来。**只会 ② 的人，定位到层也没法判断该不该改。**

## 01.9 用这本书的方法：三条纪律

**① 先机制篇，再实例篇。** 每个部分的实例篇都挂在该部分末尾（◆ 在 09、19、20、34–37、49–52），这不是排版习惯，是依赖关系：◆`base/19` 要你先知道 cache line 与 MESI（`base/13`），◆`base/36` 要你先知道 syscall 的价（`base/21`）与 epoll 省了什么（`base/31`）。**反过来读，你会把实例当演示视频看**——看到数字跳动，但说不出它证明了哪条约束。正确的顺序永远是：机制篇给出推论 → 自己动手跑一遍 → 实例篇把它量成红字。

**② 每篇都要自己跑一遍实验，跑不出来就换机器，不许抄。** 本篇已经给了你一个模板，请把 §01.3 那段 `lscpu -C` 的输出抄到你自己的笔记第一页，然后固定四个自测：

```bash
lscpu | grep -E "Model name|CPU\(s\)"   # 频率与核数 → cycle ↔ ns 的汇率
lscpu -C | grep L1d                     # cache line 与 L1d 大小 → 判断你的数据结构住哪层
getconf PAGESIZE                        # 页大小 → 缺页与 RSS 的粒度
# 再把 §01.3 的两个 C 程序在你的机器上跑一遍，记下 syscall 与四级缓存延迟
```

四个数记下来之后，**每读一篇就把该篇的实验重跑一次，输出贴进自己的笔记**。「跑不出来就换案例」是总纲 §0.7 第 6 条：本套不允许编输出。写了 20 篇笔记之后你会发现，你的笔记比这本书更值钱——因为它带你的机器型号。

**③ 锚点式查阅，不做线性读者。** 全书的编号**一旦发布不再改**，跨集引用一律写成 `→ go/19`、`→ comp/49` 这种锚点，从不写「上文」「前面讲过」。这条纪律的直接好处是：**你可以只读第 36 篇，而不觉得自己缺了什么**——它需要的前提，会在开头以 `base/21`、`base/31` 的形式明确标出。所以正确的用法是：**带着一个现象来，顺着锚点走出去**，而不是从 01 读到 56。

## 01.11 自检题

**Q1.** 同事说：「网关 `TIME_WAIT` 堆了 6 万，把 `tcp_tw_reuse` 打开就行。」请用四格尺子给出完整回答，必须包含至少两个可推导的数字，并说明你在什么条件下会同意他。

<details><summary>答案</summary>

① **约束**：主动关闭方必须保留连接状态一段时间，保证「自己最后一个 ACK 丢了、对端重发的 FIN 还能被正确应答、且网络里迟到的旧段不会污染新连接」。这个时间窗 = **2 × MSL**，MSL 取 60 s → **TIME_WAIT = 120 s**（Linux 固定 `TCP_TIMEWAIT_LEN`）。

② **量级**：6 万个 TIME_WAIT 占的是**源端口与内存**，不是「带宽」。一台客户端每个 `(src_ip, src_port, dst_ip, dst_port)` 四元组只能用一次，可用临时端口默认 28232–60999 ≈ 3.2 万个；若 6 万个 TIME_WAIT 全部落在同一条「本机 → 单个目的 IP:端口」上，**可用四元组被吃穿，新连接报 `Cannot assign requested address`**。反推需要的速率：3.2 万端口 ÷ 120 s = **每秒最多 267 条短连接**到同一目标。所以真正该问的是「我这台机器是不是每秒新建几百条短连接到一个固定后端」。

③ **承诺**：`tcp_tw_reuse` 换来的是「可以把处于 TIME_WAIT 的四元组，在**时间戳单调递增**的前提下复用于新的**主动**连接」。注意它只对**主动发起方**生效，对服务端被动关闭毫无用处。

④ **崩点**：它把「等 2×MSL」换成「赌 PAWS 时间戳能挡住迟到包」。跨 NAT、对端禁用/回绕时间戳、中间设备改写时间戳时，这个赌注就输——症状是极偶发的「连接建立后立刻收到莫名其妙的 RST / 数据错乱」，且**不可复现**。

**我会同意的条件**：① 我是主动发起方（客户端/代理出口）；② 对端支持并启用 TCP 时间戳（`net.ipv4.tcp_timestamps=1`，默认开）；③ 真正的修法是**连接池 / 长连接 / 多目的地址打散四元组**，`tw_reuse` 只是止血。若这三条不满足，正确动作是改架构，不是改 sysctl。
</details>

**Q2.** P99 从 40 ms 涨到 200 ms，`top` 显示 CPU 30%。用 §01.3 的表给出三种归因，每种必须写出「需要多少次才凑得出这 160 ms」，再说明你会用哪条命令排除它。

<details><summary>答案</summary>

先做除法，把延迟翻译成**次数**——这是把「玄学」变成「嫌疑名单」的唯一一步：

| 归因 | 单价（§01.3） | 需要的次数 | 排除手段 |
| --- | --- | --- | --- |
| 多出的 syscall | 107–154 ns | 160 ms ÷ 150 ns ≈ **10⁶ 次** | `strace -c -T -p <pid>`：看总调用次数与单次耗时分布 |
| minor 缺页 | ~1 µs | **1.6×10⁵ 次** | `/proc/<pid>/stat` 的 `minflt` 增量；`perf stat -e page-faults` |
| major 缺页（SSD） | ~100 µs | **1,600 次** | `perf stat -e major-faults`；`smaps` 看是否有文件页反复换入 |
| 同机房 RTT | 50–100 µs | **1,600–3,200 次** | `tcpdump -i any` 抓一轮请求的全部 RTT；看是否有串行下游调用 |
| 上下文切换 | 2 µs | **8×10⁴ 次** | `pidstat -w`；`perf sched latency` |
| 锁等待 | 无固定单价 | — | `perf lock` / `bpftrace` 的 futex 计数 |

三种最可能的归因（按「CPU 只有 30%」这个线索排序）：**多出来的串行 RTT**（CPU 闲着等网络，最符合 30% 使用率）、**major 缺页**（进程在等盘，CPU 也闲着）、**锁等待**（等别人放锁，CPU 同样闲着）。而「多 10⁶ 次 syscall」这一项会把 CPU 打满，与 30% 矛盾——**这条线索本身就排除了它**。

关键结论：**CPU 使用率低而延迟高，说明瓶颈不在 CPU 这一层**，「加核」是对着错误的层花钱。160 ms 里能被 `tcpdump` 直接量出来的 RTT 部分，就是这条链上第一个该被证伪的假设。
</details>

**Q3.** 本机实测：AES-128-GCM 在 16 B 块下只有 29 MB/s，在 16 KB 块下有 3.44 GB/s，差 117 倍。「加密不影响性能」这句话在什么条件下成立、在什么条件下彻底错？

<details><summary>答案</summary>

用主线③拆：**总开销 = 固定单价（每次调用的进入/退出、IV 与状态装载、尾部 tag 计算）× 次数 + 数据量 ÷ 硬件吞吐**。

- 16 B/次：每次只搬 16 B 却付一次完整的函数/指令序列开销 → **29 MB/s** 说明瓶颈全在「次数」，加密本身的 0.76 cycle/B 根本没被用到。
- 16 KB/次：调用开销摊到 16,384 B 上 → **3.44 GB/s**，逼近 AES-NI 的 0.76 cycle/B（2.6 GHz ÷ 0.756 = 3.44 GB/s）。此时瓶颈才回到硬件吞吐。

**成立的条件**：批量。TLS record 上限 16 KB、`sendfile`/`splice` 大块搬运、整文件加密——单次数据量 ≥ 4 KB 时，加密只值 0.76 cycle/B，相对于网卡带宽与 RTT 可以忽略。

**彻底错的条件**：**每次调用只处理几十字节**。代理逐条消息加密、按小包（几十 B 的 IoT 遥测）加密、每次请求都重新握手/重新装载密钥——此时吞吐由「次数 × 固定开销」决定，与 AES-NI 多强无关。这也是 ◆`base/49` 里「record 层复用」的核心动机：把已经加密的 TLS record 直接 `splice` 出去，等于把「每条消息一次加解密」变成「每条连接一次」，省掉的正是这个次数。
</details>
