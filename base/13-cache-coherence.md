## 13.1 引子：两个线程各写各的变量，总吞吐掉到单线程的 1/4

2026-01，一个广告计费聚合服务做扩容。它按分片统计，每个 worker 线程只管自己那片，指标结构长这样：

```c
struct shard_stat {          /* 每个 worker 一份，互不干扰 */
    long req_count;          /* 本片处理的请求数 */
    long err_count;          /* 本片的错误数 */
    long bytes;              /* 本片流量 */
};
static struct shard_stat st[2];   /* 两个 worker 各用 st[id] */
```

代码里没有锁，没有共享写，甚至连读都没有交叉——按直觉，两线程应该接近两倍。上线后压测数据却是反的：

| 时间 | 观测 | 当时的判断 |
| --- | --- | --- |
| 扩到 2 线程，压测 5 分钟 | QPS 只有单线程的 **26%** | 先怀疑锁：但代码里没有锁 |
| 看 CPU | 两个核都只有 ~30% 忙，`%sys` 很低 | 再怀疑内存带宽：但每秒只写 2×10⁷ 次 |
| 把 `st[2]` 改成两个独立全局变量 | 仍然 26% | 开始怀疑分配器、false alarm |
| `pahole`/`offsetof` 打印布局 | `sizeof(struct shard_stat)=24`，两个实例的头尾正好落在同一行 | — |
| 给结构体加 `aligned(64)`（每实例独占一行） | QPS 回到单线程的 **1.92 倍** | 结案 |

真相一句话：**两个 worker 写的确实是两个不同的变量，但这两个变量住在同一条 64 B 的 cache line 里。** 而 cache line 是硬件维持一致性的最小单位——协议不知道"你只改了 8 个字节"，它只知道"这一行被改过"。于是两个核轮流抢同一行的所有权，`req_count` 的每一次 `++` 都要把整行从对方核里夺过来。

这个现象叫 **false sharing（伪共享）**："共享"是真的（硬件层面整行共享），"伪"是因为源码层面两个变量毫无关系。

先给这台机器的档案，本篇所有数字都长在它上面（与 `base/07` 同一台）：

| 项 | 实测/报告值 | 来源 |
| --- | --- | --- |
| CPU | AMD EPYC 7K62，QEMU/KVM，**2 vCPU** | `lscpu` |
| 有效主频 | 3.22 GHz（周期数由此换算） | 自写基准 |
| L1d | 64 KiB/核，**2 路**，64 B 行，**512 组** | `sysfs .../index0/` |
| L2 | 512 KiB/核，16 路，512 组 | `sysfs .../index2/` |
| L3 | 16 MiB，16 路，16384 组（两核共享） | `sysfs .../index3/` |
| 缺什么 | **没有 `perf`、没有 `numactl`** | `which perf numactl` |

把上面那个事故压缩成一段可跑的基准（30 余行），在本机跑：

```c
/* fs_bench.c:  gcc -O2 -pthread fs_bench.c -o fs_bench && ./fs_bench */
#define _GNU_SOURCE
#include <pthread.h>
#include <stdio.h>
#include <sched.h>
#include <time.h>
#define N 50000000L
static volatile long same[2];                                  /* 8 B 相邻 → 同一行 */
static volatile long sole[2][8] __attribute__((aligned(64)));  /* 每格 64 B → 各占一行 */
static double now(void){struct timespec t;clock_gettime(CLOCK_MONOTONIC,&t);
                        return t.tv_sec+t.tv_nsec/1e9;}
struct job { volatile long *p; long n; int cpu; };
static void *work(void *a){
    struct job *j=a; cpu_set_t s; CPU_ZERO(&s); CPU_SET(j->cpu,&s);
    sched_setaffinity(0,sizeof s,&s);
    for(long i=0;i<j->n;i++) (*j->p)++;
    return 0;
}
static double two(volatile long *a, volatile long *b){
    pthread_t t[2]; struct job j0={a,N,0}, j1={b,N,1};
    double t0=now();
    pthread_create(&t[0],0,work,&j0); pthread_create(&t[1],0,work,&j1);
    pthread_join(t[0],0); pthread_join(t[1],0);
    return now()-t0;
}
int main(void){
    double s=two(&same[0],&same[1]);        /* 同一行 */
    double d=two(&sole[0][0],&sole[1][0]);  /* 各占一行 */
    printf("same line %.3f s  %.2f ns/op\n", s, s/N*1e9);
    printf("diff line %.3f s  %.2f ns/op\n", d, d/N*1e9);
    printf("penalty   %.2fx\n", s/d);
    return 0;
}
```

```
same line 0.200 s  4.01 ns/op
diff line 0.065 s  1.30 ns/op
penalty   3.09x
```

**3.09 倍**，而且这 4.01 ns 里没有一行多余指令——两个版本的机器码逐字节相同，只有地址不同。本机连跑三次分别是 3.09×、2.62×、2.56×（虚拟机、邻居有负载、L3 两核共享，都会削平这个数；裸机同实验常在 5–10×）。前面事故里的 4×，是典型的"跨 socket 抢行"：行要从另一个 CPU 的 L3 里搬过来。

本篇要交付的就是这一件事：**多核并不共享内存，只有一堆各自缓存 + 一套协议在假装共享。** 所有可见性、重排、伪共享的问题都从这句话出生。

## 13.2 缓存的结构：一条地址怎么被切成三段

### 先看几何：为什么必须"组相联"

一个核的 L1d 只有 64 KiB。若做成"一条数据随便放哪"，找起来要全表比较，太慢；若做成"每个地址只有一个固定位置"（直接映射），两条常用的地址撞到同一个格就互相踢。真实的设计是折中——**组相联（set-associative）**：把 64 KiB 切成若干**组（set）**，每组里有 k 个**路（way）**；地址先决定它属于哪个组，再在这个组里的 k 个位置中任选一个放。

本机的数字全部可查、可算：

| 级别 | 容量 | 路数 k | 行大小 | 组数 = 容量/(k×64) | index 位数 | tag 位数（48 位地址） |
| --- | --- | --- | --- | --- | --- | --- |
| L1d | 64 KiB | 2 | 64 B | 65536/(2×64) = **512** | log₂512 = **9** | 48−9−6 = **33** |
| L2 | 512 KiB | 16 | 64 B | 524288/(16×64) = 512 | 9 | 33 |
| L3 | 16 MiB | 16 | 64 B | 16777216/(16×64) = **16384** | 14 | 28 |

一条 48 位地址被切成三段（L1 是物理索引：低 12 位与虚拟地址相同，index 最高 3 位要过页表，所以"同页不同帧"的地址仍可能撞组——这就是 page coloring）：

```
  48 位地址
  ┌──────────────────┬──────────┬─────────┐
  │  tag (33 bit)    │index (9) │offset(6)│
  └──────────────────┴──────────┴─────────┘
     47 …… 15          14 …… 6    5 …… 0
        │                 │          │
        │                 │          └─ 行内偏移：0..63（6 bit）
        │                 └──────────── 选组：512 组里的哪一个（9 bit）
        └────────────────────────────── 与组内 2 个 tag 并行比较（33 bit）
```

拿一个真实形态的栈地址 `0x7ffd_1234_5678` 手算一遍：

```
offset = 0x5678 & 0x3F           = 0x38 = 56          （落在行内第 56 字节）
index  = (0x5678 >> 6) & 0x1FF   = 345 = 0x159         （第 345 组）
tag    = 0x7ffd12345678 >> 15    = 0xfffa2468          （33 bit，此地址最高位为 0）
```

三条推论直接从这个切分里掉出来：

1. **相邻的 64 字节共用一个 index**——所以"连续访问"只花一次 tag 比较，剩下的全是行内偏移，这是 `base/07` 里"连续就快"的硬件原因。
2. **地址每加 4096（一页），index 加 64**（`0x159 + 64 = 409`）。所以 8 个相隔 4 KiB 的地址刚好把 512 组轮一遍又回到原点：**相隔 32 KiB 的地址必落在同一组**。
3. 2 路意味着"同一组里放 3 个就必有 1 个被踢"。三个相隔 32 KiB 的数组（比如 `a[i]`、`b[i]`、`c[i]` 同时参与一个循环）就是最小可复现的冲突例：每次访问都要从 L2 重新取。这条推导就是"数组长度取 2 的幂、并行数组一多就变慢"那类老经验背后的算法（注意它依赖本机这份 2 路基线；换一台 8 路 L1 的机器，撞组的 stride 会变成 4 KiB）。

### 替换策略：LRU 装不下，所以用 PLRU

一组 k 路满了要踢谁？理想是 LRU（踢最久未用的）。但**精确 LRU 要记全序**：k 路有 k! 种顺序，需要 log₂(k!) 位。2 路只要 1 位（记"上次用的是哪路"），16 路要 log₂(16!) ≈ 44 位/组——16384 组就是 9 万字节的状态，比数据本身的结构开销还难忍，而且每次访问都要更新一棵比较树。

所以硬件用 **PLRU（伪 LRU）**：一棵 k 叶的二叉树，每个内部结点 1 位，指向"较不最近使用的那半边"。k 路只需 k−1 位（16 路 15 位），每次访问翻 log₂k 个 bit。代价是偶尔踢错——它保证的是"不会踢刚用过的那条"，不是"一定踢最旧的"。这解释了为什么冲突 miss 的代价有时比理论值更随机：**缓存的替换决策本身是近似的**。

### 写回 vs 写直达：为什么 L1 必须是 write-back

| 策略 | 一次写做什么 | 省了什么 | 代价 |
| --- | --- | --- | --- |
| write-through | 同时写 L1 和下一级（或内存） | 实现简单，内存永远最新 | 每次写都产生下级流量；写密集时代价极高 |
| **write-back** | 只写 L1，把这行标脏（dirty），被替换时才写回 | 同一行被写 100 次只付 1 次下级流量 | 内存可能是旧的；**一致性协议必须额外处理"脏行在别人手里"** |
| write-allocate | 写 miss 时先把整行读进来再改 | 后续对同行的读写都命中 | 只写一次就丢的场景白读 64 B |
| no-write-allocate | 写 miss 直接写穿到下级 | 不污染缓存 | 每次写都走总线 |

L1/L2 都是 write-back + write-allocate。**这张表里 write-back 那一行的"代价"一栏，就是 §13.4 全部复杂度的来源**：因为脏数据可能只存在于某个核的私有缓存里，所以"别人要读这一行"时，必须有人负责把它交出来；因为写只改了一部分字节，所以"作废别人手里的副本"必须精确到整行。

## 13.3 cache line 是所有权单位：64 B 一次搬完

### 为什么是 64 B，而不是 8 B

CPU 和内存之间不是"要 8 个字节给 8 个字节"。DRAM 的一次突发传输（burst）按行缓冲连续吐出多个字，DDR4/DDR5 一个 burst 是 64 B；L2/L3 与 L1 之间的总线宽度也是按这个粒度设计。于是整个存储层次共用同一个搬运单位：**cache line = 64 B = 8 个 `long` = 16 个 `int`**。

这不是"顺手定的"，是三条约束的交点：① 要有足够的空间让**空间局部性**生效（一次搬太少，预取无用）；② 行的元数据（tag + 状态位 + LRU 位）要摊薄（行越小，元数据占比越高）；③ 一致性协议的每次消息要摊薄（行越小，同样的数据要发更多次 invalidate）。

**于是最重要的一句话出现了：你只写 1 个字节，硬件买的是整行 64 字节的所有权。** 你为"改一个计数器"付的钱，和"改 8 个计数器"一模一样；反过来，两个毫不相干的变量只要同行，就会被绑成一次交易。

### 结构体：字段顺序决定你买几次行

跑一个真实布局（`gcc -O2`，x86-64）：

```c
struct bad  { char kind; long hits; char flag; long bytes; int id; };
struct good { long hits; long bytes; int id; char kind; char flag; };
struct split{ long hits, bytes; int id; char kind, flag; char pad[64-8-8-4-1-1]; }
             __attribute__((aligned(64)));
```

```
bad  : sizeof=40  kind@0 hits@8 flag@16 bytes@24 id@32
good : sizeof=24  hits@0 bytes@8 id@16 kind@20 flag@21
split: sizeof=64  (每结构体独占一条 64 B 行)
```

`bad` 的 40 字节里有 3 处对齐洞（7 + 7 + 4 = 18 字节是纯浪费），而 `hits` 与 `flag` 相隔 16 B——**它们一定在同一行**。`good` 只花 24 字节，`hits` 与 `bytes` 相邻，一条 64 B 行装得下 2.67 个对象。

| 版本 | sizeof | 4M 个对象占的行数 | 每行装几个对象 | 相邻两个实例会同行？ |
| --- | --- | --- | --- | --- |
| `bad` | 40 B | 4M×40/64 = 2.5M 行 | 1.6 | 会（`st[i].id` 与 `st[i+1].kind` 只差 8 B） |
| `good` | 24 B | 4M×24/64 = 1.5M 行 | 2.67 | 会（这是它的优点：装得多） |
| `split` | 64 B | 4M 行 | 1 | 不会（每实例独占一行） |

`bad → good` 一项就把要搬的行数从 250 万降到 150 万（**−40%**），且没有改任何算法——这是 `base/07` 那条"连续就快"在**结构体内部**的版本。

### 按访问频率重排：三档修法，代价递增

1. **只重排字段**（零成本）：按"一起被访问的放一起"排，大的在前消掉 padding。`bad → good` 就是这一档。
2. **热冷拆分**（改代码结构）：把每轮循环都要碰的字段留在主结构里，把统计/调试/审计字段挪到旁路数组（SoA）。一次遍历从"每对象 1 行"变成"每 2.67 对象 1 行"。
3. **独占行**（改内存布局）：当这个结构体会被**多个核并发写**时，字段重排反而有害——两个核写同一结构的两个字段，照样是伪共享（§13.5）。这时必须 `aligned(64)` 把它撑到整行（`split`），用 42 字节的浪费买"零共享"。

三档的顺序不能颠倒：**先减总量，再谈隔离**。给 4M 个 24 B 的对象每个都加 64 B 对齐，等于把内存从 96 MB 撑到 256 MB，L3 直接被冲爆——那是拿带宽换来的假优化。

## 13.4 MESI 四态：一致性协议到底在维持什么

### 它要维持的那条假象

每个核都有自己的 L1/L2，同一地址的 64 B 可能在 2 个核里各有一份。协议要维持的假象只有两条：

- **单一写者**：任一时刻，一条行最多只有一个核在写（否则两次写会打架，谁赢没有定义）。
- **最终可见**：一个核写完之后，别的核**迟早**能看到（"迟早"是多久，协议不管——这是 §13.6 的伏笔）。

注意它**没有**承诺"立刻可见"，也**没有**承诺"顺序"。这两条不承诺，就是后面所有重排与屏障问题的总开关。

### 四个状态

| 状态 | 含义 | 内存里的副本 | 本核可写？ | 别的核持有？ |
| --- | --- | --- | --- | --- |
| **M**（Modified） | 本核独占，且已改过 | **过期**（旧值） | 是 | 否 |
| **E**（Exclusive） | 本核独占，未改 | 有效 | 是（静默升 M） | 否 |
| **S**（Shared） | 可能多核共有，未改 | 有效 | 否（要先作废别人） | 可能 |
| **I**（Invalid） | 本核这份无效 | — | 否（要先取） | 可能 |

### 状态转换表：一次操作要发什么消息

| 当前态 | 本地读 | 本地写 | 收到远程读（BusRd） | 收到远程写（BusRdX） |
| --- | --- | --- | --- | --- |
| **M** | 命中（M） | 命中（M） | 交出数据并降 **S**（或写回内存） | 交出数据并降 **I** |
| **E** | 命中（E） | **静默升 M**（无总线事务） | 降 **S** | 降 **I** |
| **S** | 命中（S） | 发 invalidate，等全部确认 → **M** | 不变（S） | 降 **I** |
| **I** | 发 BusRd，回来进 **S**（无人持有则 **E**） | 发 BusRdX → **M** | — | — |

三个细节值得停一下：

- **E 态是白送的**：独占且干净时，写不需要任何总线消息——这是"单线程程序几乎不付一致性成本"的原因，也是为什么"跑一个线程时一切正常"。
- **S → M 要等**：必须收到所有共享者的 invalidate 确认（ACK）才能拿到独占权。这段等待就是 §13.5 里那 3 ns 的来源。
- **M 态的行被替换时要写回**：脏行不能默默丢掉。AMD 用 **MOESI** 加了第五态 **O（Owner）**：由 O 态直接向前来要数据的核转发，而不必先写回内存——省一次 DRAM 写。Intel 用 MESIF 解决类似问题。对我们来说，两者都只是"谁来交付这份数据"的记账方式，不变的是"**一条行任一时刻只有一个写者**"。

### 一条时序：两核都读，然后一核写

```
 核0 L1            核1 L1                L3 / 内存
   │                 │                      │
   ├── BusRd ────────┼─────────────────────►│  ① 核0 读 X
   │◄────────────────┼──────── 64 B ────────┤     无人持有 → 核0 得 E
   │  E              │                      │
   │                 ├── BusRd ────────────►│  ② 核1 读 X
   │◄──── 转发 ──────┤                      │     核0 的 E 被探听 → 降 S
   │  S              │  S                   │     核1 得 S（干净的共享）
   │                 │                      │
   ├── BusRdX ───────┼─────────────────────►│  ③ 核0 写 X
   │                 │◄── invalidate ───────┤     核0 要独占
   │                 │  I                   │     核1 作废并回 ACK
   │  M              │                      │     核0 得 M（内存副本已过期）
   │                 │                      │
   │                 ├── BusRd ────────────►│  ④ 核1 再读 X
   │◄──── 转发 ──────┤                      │     核0 的 M 必须交出数据
   │  S              │  S                   │     并写回/转发，双方降 S
```

第 ③ 步就是伪共享的全部成本：**核 0 为了让核 1 手里那份作废，必须发一条 invalidate 并等 ACK。** 核 1 改自己那 8 字节时，也要对核 0 做同样的事。两个核都没碰对方的变量，却在同一条行上打乒乓球。

所以本节的结论可以写成一句可算的账：

```
伪共享成本 ≈ (每次所有权转移的往返延迟) × (每单位时间转移次数)
```

而"总线上传的是整行"——**协议看不见你只改了 8 字节**。这就是为什么 §13.1 那个 24 B 的结构体一放进数组就出事：一条行里坐着 2.67 个实例，谁都不是独占的；而把每个实例撑到 64 B 之后，一条行只属于一个写者。

## 13.5 伪共享：两个线程写同一行的不同变量

### 实验：把 §13.1 的复现做成可对照的两列

代码已在 §13.1 给出（`same[2]` vs `sole[2][8]`，对齐 64 B），这里只补完整的三组数字。`taskset` 绑核、每线程 5000 万次、三次取最小：

| 配置 | 耗时 | 每线程每次 | 总吞吐 | 相对 |
| --- | --- | --- | --- | --- |
| 1 线程 / 独占一行 | 0.063 s | 1.27 ns（4.1 周期） | 0.79 G/s | 1.00×（基准） |
| 2 线程 / **各占一行** | 0.065 s | 1.30 ns（4.2 周期） | 1.54 G/s | **1.96×**（线性扩展） |
| 2 线程 / **同一行** | 0.200 s | 4.01 ns（12.9 周期） | 0.50 G/s | **0.63×**（比单线程还低） |

三行读数要一起看：

- **各占一行时 1.96×**——证明这确实是两个真核在并行，不是时间切片。
- **同一行时每线程 4.01 ns**，比独占行的 1.30 ns 多出 2.7 ns（≈ 8.8 周期）。这 2.7 ns 不是计算，是**等对方交出所有权**。
- **同一行时总吞吐 0.50 G/s，低于单线程的 0.79 G/s**——两个线程加在一起还不如一个。这就是"扩容后 QPS 掉到 1/4"那种事故的最小形态。

同一台机器上把自增换成 `atomic_fetch_add(seq_cst)`，现象的另一种写法：

| 配置（总操作数 5000 万） | 耗时 | 每次 | 总吞吐 | 相对单线程 |
| --- | --- | --- | --- | --- |
| 1 线程 | 0.545 s | 10.89 ns（35 周期） | 91.8 Mops/s | 1.00× |
| 2 线程 / 各占一行 | 0.274 s | 5.49 ns | 182.2 Mops/s | **1.98×** |
| 2 线程 / 同一行 | 0.439 s | 8.78 ns | 113.9 Mops/s | **1.24×** |

原子版的扩展比从 1.98× 掉到 1.24×：`lock xadd` 必须在独占状态下执行，同一行时两个核的独占请求直接串行化。**注意它没有"变得极慢"**——因为 `lock` 前缀本身已经把每条指令变成了一次"取独占 + 屏障"，伪共享只是让这次取独占变成排队，边际成本没有普通自增大。这也说明一个反直觉的事实：**原子操作会掩盖伪共享的倍数，但不掩盖它的绝对成本**。

### 为什么裸机上常常是 5–10×

本机只测到 2.6–3.1×，不是实验做错了。三个原因叠加：

1. **L3 是两核共享的**（同一 CCX），行的所有权在 L3 层就能转手，比跨 socket 少一个数量级的总线往返。
2. **硬件预取器会提前取所有权**：连续的写同一行，属于最容易识别的流，预取可以在你需要之前把行拿过来，把延迟摊到多次迭代上。
3. 虚拟机、邻居负载、频率波动，都会削平差距。

换成 4 个核跨两个 socket，倍数立刻上去；而换成 CAS 循环，**倍数反而会变小**（因为每次操作本来就要付一次取独占的钱，伪共享只是让它排队），绝对成本却更高——这正是上面那张原子表的第二层读法。**判据不是"几倍"，而是"每个写者是否独占一条行"**——这一点与机器无关。

### 修法：padding 加在哪

```c
/* 错：两个热计数器相邻 */
struct stat { long req; long err; };

/* 对：两个热字段各占一行（sizeof 会变成 128） */
struct stat { _Alignas(64) long req; _Alignas(64) long err; };

/* 对：数组场景，按行对齐分配 */
struct slot { long v; char pad[56]; } __attribute__((aligned(64)));
static struct slot slots[8];       /* slots[i] 与 slots[j] 永不同行 */
```

三条纪律：

- **padding 加在"会被不同线程写的变量之间"**，不是加在结构体末尾就完事。`struct stat` 里 `req` 和 `err` 由同一线程写，不需要隔离；真正要隔的是 `stat[0]` 与 `stat[1]`。
- **对齐要加在"元素类型"上，不是加在数组声明上**。`struct { long v; } __attribute__((aligned(64)))` 的 `sizeof` 会是 64（本机实测），数组里每个元素自然各占一行；但 `_Alignas(64) long cnt[8];` 只把**数组起点**对齐，`cnt[0]` 与 `cnt[1]` 仍差 8 字节——隔离必须落到每个可独立寻址的对象上。
- **别给只读共享加 padding**：只读的行在所有核里都是 S 态，没有任何转移，padding 纯粹浪费缓存。

Java 的 `@Contended`（需 `-XX:-RestrictContended`）和 Go 里手写 `[64]byte` 填充是同一件事的两种语法。Go 的 `sync.Pool`、`runtime.P` 里的 `pad` 字段就是给"每个 P 一个计数器"准备的——**这是标准库自己在用的技术，不是偏方**。

## 13.6 存储缓冲与重排：写还没出门，别人已经看见了

### 为什么每个核都有一个 store buffer

一条 `store` 指令要拿到独占权才能改缓存，而拿到独占权可能要等几百个周期（行在别的核手里）。如果 CPU 在这里停下等，流水线就废了。所以每个核都有一个 **store buffer**：写先落进这个 FIFO，指令立刻退休，后台慢慢把行买过来、把值写进去。

```
  执行单元 ──store──► [ store buffer (FIFO, 每核一个) ] ──► L1d
                              │
                              └─ 本地 load 可以先从这里转发（store-to-load forwarding）

  L1d ◄──invalidate── [ invalidate queue (FIFO) ] ◄── 总线上的作废消息
                              │
                              └─ 收到不等于处理完：本核的读还可能命中旧副本
```

两个 FIFO 各自解决一个性能问题，也各自打开一个口子：

- **store buffer 的洞**：本核的 store 还没进缓存，别人当然看不到——于是"我写了"和"别人看见我写了"之间有一段窗口。
- **invalidate queue 的洞**：别人发来的作废消息排队等着处理，在处理完之前本核的读**仍然命中旧值**——于是"别人写了"和"我看见别人写了"之间也有一段窗口。

### 四种重排，以及每种架构允许哪几种

把"两个操作"按读写组合排一下，只有四类。这张表是全篇最该背下来的一张：

| 重排类型 | 含义（程序序 → 实际序） | x86-64（TSO） | ARM64 | 后果 |
| --- | --- | --- | --- | --- |
| LoadLoad | 读₁ 后 读₂ → 读₂ 先 | 禁止 | 允许 | 读到"半个初始化"的对象 |
| LoadStore | 读₁ 后 写₂ → 写₂ 先 | 禁止 | 允许 | 检查与使用之间被插队 |
| StoreStore | 写₁ 后 写₂ → 写₂ 先 | **禁止** | 允许 | **数据先到、标志后到** |
| StoreLoad | 写₁ 后 读₂ → 读₂ 先 | **允许** | 允许 | 看到"对方还没写"的旧值 |

x86 的模型叫 **TSO（Total Store Order）**，它只放宽了一样东西：**StoreLoad**。也就是说，x86 上"写一个变量、紧接着读另一个变量"时，读可以在写对别人可见之前完成；但"写数据、再写标志"这两个 store，硬件保证按程序序被别人看见。

### 那个著名的时序：在 x86 上其实不会发生

教科书里那张图是这样的（弱内存模型，ARM/POWER/Alpha）：

```
 核0：x = 1;  flag = 1;          核1：while (flag == 0) ;  print(x);

 时间 ──────────────────────────────────────────────────────►
 核0  x=1 进 store buffer  ─────────────┐
 核0  flag=1 先落地（StoreStore 被重排）─┼──► 核1 看到 flag==1
 核1  读 x ──────────────────────────────┘    读到 0（x 的写还在 buffer 里）
 核0  x=1 落地
```

**在 x86-TSO 上，这个交错抓不到**——因为 StoreStore 是禁止重排的，`x=1` 一定比 `flag=1` 先可见。想复现它，需要 ARM64/POWER 的硬件，或者"编译器重排"这个另一层：

```c
x = 1;              /* 普通全局变量，非 atomic、非 volatile */
flag = 1;
```

这段代码在**任何**架构上都可能被编译器调换顺序（C11 的数据竞争是 UB，编译器没有义务保序），也可能被读者一侧的编译器把 `print(x)` 提前到 `while` 之前。所以正确的结论不是"x86 不用管"，而是：

- **硬件层**：x86 只会 StoreLoad 重排；ARM/POWER 四种都可能。
- **编译器层**：任何架构都可能重排，只有 `atomic`/`volatile`/屏障能约束它。
- 你在 x86 上遇到的"flag 有了、数据没有"，**根因几乎总是编译器，不是 CPU**。

### 真实测到的：store 不等，屏障才等

把"等"这件事量出来。同一段 store 循环，只改中间那道屏障（`taskset -c 0`，5000 万次，两次取小）：

```
纯 store（无屏障）      : 0.136 s   2.71 ns/次   (≈ 9 周期)
store + seq_cst fence  : 1.048 s  20.97 ns/次   (≈ 68 周期)
store + mfence         : 4.596 s  91.91 ns/次   (≈ 296 周期)
seq_cst atomic store   : 0.904 s  18.07 ns/次   (≈ 58 周期，xchg)
```

2.71 ns 的纯 store 意味着：`store` 指令退休时，值**还在 store buffer 里**，CPU 没有等它可见，只付了队列挤满后的反压。加上一道 `seq_cst` 屏障立刻变成 20.97 ns——多出来的 18 ns 就是"等 store buffer 排空 + 等失效确认"的价。而 `mfence` 竟然是 91.91 ns（≈ 300 周期），比"锁一下栈顶"贵 4 倍多；这个差距在 §13.7 会解释，也是编译器宁可用 `lock or` 也不生成 `mfence` 的原因（虚拟机对 `mfence` 的放大让它更夸张，裸机上通常是几十周期的量级）。

## 13.7 内存屏障与原子：谁在什么时候踩刹车

### x86-TSO 的四条规则（只记这四条）

| # | 规则 | 直白说法 |
| --- | --- | --- |
| 1 | Loads are not reordered with other loads | 两次读，按程序序 |
| 2 | Writes are not reordered with older reads | 读后写不能翻（LoadStore 禁止） |
| 3 | Writes are not reordered with other writes | 写后写不能翻（StoreStore 禁止） |
| 4 | **Reads may be reordered with older writes to different locations** | **写后读可以翻**（StoreLoad 允许） |

第 4 条是唯一的口子，也是 `x = 1; flag = 1;` 在 x86 上安全、而 `x = 1; if (y == 0)` 不安全的原因。

### 屏障指令与 `lock` 前缀，和它们的真实编译结果

| 指令 | 拦住什么 | 典型场景 | 本机实测代价 |
| --- | --- | --- | --- |
| `sfence` | StoreStore | 非临时存储（`movnt`）之后、DMA 之前 | 未单测：它只排空 store buffer，不排空 load 侧 |
| `lfence` | LoadLoad（+ 让后续指令不再往前取） | 极少用于内存序；多用于把 `rdtsc` 与前面的读隔开 | 未单测：不排空 store buffer |
| `mfence` | 全部（主要是 StoreLoad） | 需要完全屏障时 | **91.9 ns**（本机，含虚拟化放大） |
| `lock` 前缀 | 全部 + 原子性 | `lock add/xadd/cmpxchg` | 10.9 ns（无争用），≈ 35 周期 |

有意思的是：**编译器并不生成 `mfence`**。同一段 `__atomic_thread_fence(__ATOMIC_SEQ_CST)`，`objdump -d` 出来是：

```asm
0000000000000000 <plain_inc>:          # long plain_inc(volatile long *p)
   0:	mov    (%rdi),%rax             # 读
   3:	add    $0x1,%rax
   7:	mov    %rax,(%rdi)             # 写回：三步，中间可被打断
   a:	ret

0000000000000010 <atomic_inc>:         # atomic_fetch_add(p,1)
  10:	mov    $0x1,%eax
  15:	lock xadd %rax,(%rdi)          # 一条指令完成"取独占 + 加 + 放回"
  1a:	add    $0x1,%rax
  1e:	ret

0000000000000020 <fence_demo>:         # *x=1; __atomic_thread_fence(seq_cst); *flag=1
  20:	movl   $0x1,(%rdi)
  26:	lock orq $0x0,(%rsp)           # ← 屏障：锁一下栈顶，比 mfence 便宜 4 倍多
  2c:	movl   $0x1,(%rsi)
  32:	ret
```

`lock orq $0x0,(%rsp)` 是个经典技巧：它"锁"的是栈顶一个没人用（但一定存在、一定可写）的位置，效果却是一道完整的 StoreLoad 屏障——因为 `lock` 前缀本身就意味着"排空 store buffer + 串行化"。第 26 行和第 2c 行之间的顺序被强制住了，而代价只有 21 ns 而不是 92 ns。

### `lock` 前缀：总线锁还是缓存锁

`lock` 有两种实现，硬件自动选：

- **缓存锁（cache lock）**：行在本地缓存里时，直接把这一行锁住（置一个 lock 位），其他核的访问被挡在门外。**今天 99.9% 的情况走这条**，代价是一次独占权获取 ≈ 35 周期。
- **总线锁（bus lock）**：行跨越缓存边界、或涉及不可缓存区域（MMIO）时，拉低总线锁信号，整条内存总线停摆。这才是"锁总线"的字面意思，代价是几十到几百周期，**现代 CPU 会尽量避免**。

原子读-改-写（CAS）就是在这上面搭出来的：

```c
/* 一个不会退化成"两步"的 CAS 循环（C11） */
static inline int cas_inc(_Atomic int *p, int expect) {
    while (!atomic_compare_exchange_weak_explicit(
               p, &expect, expect + 1,
               memory_order_acq_rel, memory_order_acquire)) {
        /* 失败时 expect 已被硬件写回当前值，直接重试 */
    }
    return expect + 1;
}
```

`atomic_compare_exchange_weak` 编译成 `lock cmpxchg`：一条指令里完成"读—比较—条件写"，并且带着完整的屏障语义。失败重试的循环，就是"没抢到独占权就再来一次"——**在高争用下它会退化成 §13.5 里那张原子表的最后一行**（同一行 8.78 ns/op）。

### 语言内存模型：只给结论

- **Go**：`sync/atomic` 的原子操作、`channel` 收发、`Mutex` 的加解锁，都会建立 happens-before；`go` 语句的启动、`WaitGroup` 的 `Done`/`Wait` 同理。**没有 happens-before 的并发读写就是数据竞争，行为未定义**。硬件那一半就是本节的 TSO 与 `lock` 前缀；语言那一半见 [go/23](../go/23-memory-model.md)。
- **Java**：`volatile` 写 = StoreStore + StoreLoad 屏障，`volatile` 读 = LoadLoad + LoadStore 屏障；在 x86 上写屏障落地成 `lock addl $0,(%rsp)` 或 `xchg`，读屏障通常是空的（因为 x86 的 LoadLoad 本来就禁止）。这就是为什么"volatile 在 x86 上几乎不要钱"，也是为什么"volatile 不等于线程安全"：它保证可见性与顺序，**不保证复合操作的原子性**。`count++` 依然是读-改-写三步。
- **C/C++**：`memory_order_relaxed` 只保证原子性、不建立顺序；`acquire/release` 配对建立单向顺序；`seq_cst` 是全局单一总序。默认用 `seq_cst`，热点路径再用 `relaxed`，中间那档留给真正需要的人。

## 13.8 实测汇总：这台机器上量到的四组数

全部由本机（2 vCPU KVM）跑出，无 `perf`、无 `numactl`，命令即代码：

```bash
gcc -O2 -pthread fs_bench.c -o fs_bench && ./fs_bench    # 伪共享
gcc -O2 -pthread atom.c     -o atom     && ./atom        # 原子扩展性
gcc -O2          fence.c    -o fence    && taskset -c 0 ./fence   # 屏障
gcc -O2 -c dis.c && objdump -d dis.o                     # 看 lock 前缀
```

| # | 量的是什么 | 结果 | 一句话结论 |
| --- | --- | --- | --- |
| ① | 伪共享（同线 vs 异线，2 线程各 5×10⁷ 次） | 4.01 ns vs 1.30 ns，**3.09×** | 一条行两个写者 = 所有权来回搬 |
| ② | 原子自增扩展性（总 5×10⁷ 次） | 1T 91.8 / 2T 异线 182.2 / 2T 同线 113.9 Mops/s | 异线 **1.98×**，同线掉到 **1.24×** |
| ③ | 同一行 vs 不同行的 RMW 代价 | 8.78 ns vs 5.49 ns（每 op） | 争用把行级串行化变成排队 |
| ④ | 屏障的价 | store 2.71 / +fence 20.97 / +mfence 91.91 ns | `mfence` 是最后手段，`lock or` 便宜 4 倍多 |

怎么读这张表：**②的 1.98× 是"没有伪共享"的基线，①的 3.09× 是"伪共享"的代价，③把两者放在同一条时间轴上，④告诉你为恢复顺序要付多少钱。** 四组数乘起来，就是一次并发写路径的全部硬件开销。

## 13.9 三列账：缓存承诺了什么、收了多少、从哪开始失效

| 维度 | 承诺了什么 | 为此付了什么 | 从哪里开始失效 |
| --- | --- | --- | --- |
| 近似共享内存 | 每个核看到同一份地址空间，读写"像"在操作同一块内存 | 一致性协议 + 行级所有权转移；一次 miss 搬 64 B | 一旦有多个写者，同一行变成排队点（§13.4、§13.5） |
| 局部性红利 | 连续访问只付一次 tag 与一次搬运 | 缓存容量、2 路/16 路的组冲突、替换策略的近似 | 工作集超过 L3，或 stride 撞同一组（§13.2） |
| 单一写者 | 任一时刻一条行只有一个写者，写不会互相覆盖 | 写前必须 invalidate 并等 ACK；S→M 有等待 | 伪共享把"等待"放大到每次写（§13.5） |
| 最终可见 | 写完的数据"迟早"能被别人看到 | store buffer 掩盖延迟；可见性有窗口 | 依赖"写完立刻可见"的代码全部错（§13.6） |
| 顺序 | 单核内程序序保持（x86 除 StoreLoad 外） | 屏障指令；`lock` 前缀；原子指令 35 周期起 | 无屏障的跨核标志位、双重检查锁（§13.7） |
| 原子性 | `lock` 系列指令提供读-改-写的原子性 | 独占权 + 屏障，10.9 ns 起；争用时排队 | 复合操作（`count++`）在语言层依然不是原子的 |

一句话收束：**缓存买到的是"看起来共享"，付出的是"行级所有权 + 可见性窗口 + 顺序要自己补"。** 伪共享、屏障开销、NUMA 抖动，都是这张账的三个出口，不是三个独立 bug。

## 13.10 踩坑清单：现象 → 根因 → 定位 → 修 → 防复发

| 现象 | 根因（指回本篇） | 定位 | 怎么修 | 防复发 |
| --- | --- | --- | --- | --- |
| 加线程后总吞吐不升反降，CPU 却不忙 | 两个热变量同行，写者互相抢所有权（§13.5） | 打印 `offsetof`；把结构体按 64 B 对齐后重测 | 每写者独占一行（`alignas(64)` + 补足 64 B） | 并发写的数据结构评审时必看"哪些字段会被不同线程写" |
| 加了 padding 无效 | 只对齐了起点，`sizeof` 还是 8/24（§13.5） | `sizeof` + `offsetof` + 打印相邻元素地址差 | 显式补一个 `char pad[...]` 把 `sizeof` 撑到 64，或 `__attribute__((aligned(64)))` + 手算尺寸 | 加一个 `static_assert(sizeof(T) == 64)` |
| 标志位有了、数据是旧的 | StoreStore 被重排（ARM/POWER）或编译器重排（§13.6） | 反汇编看两个 store 的相对顺序；查是否有 `atomic` | 用 `release` 写标志、`acquire` 读标志；或 `atomic_thread_fence` | 禁止"裸标志位 + 裸数据"的发布模式 |
| `volatile` 加了还是不线程安全 | `volatile` 只保可见与顺序，不保复合操作原子性（§13.7） | 反汇编看 `count++` 是不是 `mov/add/mov` | 换 `atomic_fetch_add` / `Interlocked` / `sync/atomic` | Code review 里把 `volatile` 当"可见性"而不是"互斥"用 |
| 压测机快、线上慢 | 线下单 socket，线上跨 NUMA/socket（§13.9） | `lscpu -e`、`/sys/devices/system/node/`、绑核 | 绑核 + 每 NUMA 节点一份数据 | 容量规划按 socket 数分片，不按线程数分片 |
| 双重检查锁偶发拿到半初始化对象 | 构造函数的写与"发布指针"的写被重排（§13.6、§13.7） | 看发布路径有没有 release/acquire | 指针用 `atomic` + `release`，或改用函数内静态初始化 | 单例模板统一封装，不允许手写 DCL |

### 没有 `perf c2c` 时怎么定位伪共享

`perf c2c` 的价值在于它的 **HITM 列**：一条 cache line 被本核命中、但该行处于别的核的 Modified 态（"命中被改行"），HITM 高的地址就是伪共享的热点；`perf c2c report` 还会给出参与冲突的 PID/CPU 与行内偏移。本机没有 `perf`，替代路径是三条：

1. **二分法**：把可疑结构体按 64 B 对齐，A/B 两次跑同一压测；差 2× 以上就是它。
2. **看地址**：`offsetof` + `printf("%p")` 打印每个线程写的那几个变量，算 `addr & ~63UL`，相同即同一行。
3. **看反汇编**：热路径里出现 `lock` 前缀说明有原子操作；出现 `mov/add/mov` 三步说明是普通读改写——后者在多写者场景下一定丢更新，且一定争行。

`pahole -C 结构体名 二进制` 能直接打印字段偏移与 padding 洞，是查"一条行装几个对象"最快的工具。

## 13.11 一页速记

```
【一句话】多核不共享内存：一堆私有缓存 + 一套协议在假装共享。
          协议的最小单位是 64 B 行，不是你的 8 字节变量。

【地址怎么切】L1d 64 KiB / 2 路 / 64 B 行 = 512 组
  offset 6 bit │ index 9 bit │ tag 33 bit（48 位地址）
  地址每 +4096 → index +64；相隔 32 KiB 的三块数据必撞同一组

【四态】M 独占脏 / E 独占净 / S 共享净 / I 无效
  本地写：E 静默升 M（免费）；S 要发 invalidate 等 ACK（收费）；M 直接写
  远程写：任何持有者 → I

【三个数】独占行自增 1.30 ns；同行两写者 4.01 ns（3.1×）
          lock xadd 10.9 ns（35 周期）；mfence 91.9 ns，lock or 21.0 ns

【四种重排】x86-TSO 只允许 StoreLoad；ARM/POWER 四种都允许
  x=1; flag=1   → x86 硬件安全，编译器可能翻
  x=1; r=y      → x86 硬件就可能翻（要 mfence / lock / atomic）

【修法优先级】先减总量（字段重排/热冷分离）→ 再隔离（每写者一行）
             → 最后才上原子（原子掩盖倍数，不掩盖成本）
```

## 13.12 自检 3 题

**Q1.** 本机 L1d 是 64 KiB、2 路、64 B 行。请算出组数与 index 位数；再解释：为什么三个相隔 32 KiB 的数组会互相踢，而相隔 4 KiB 的不会？

<details><summary>答案</summary>

组数 = 65536 / (2 × 64) = **512 组**；index = log₂512 = **9 位**；offset 6 位；48 位地址剩 **33 位 tag**。

地址每增加 4096，`index = (addr >> 6) & 0x1FF` 增加 `4096/64 = 64`。所以相隔 4 KiB 的两个地址落在**不同组**（index 差 64），互不干扰；而相隔 32 KiB（= 8 × 4 KiB）时 index 增加 `8 × 64 = 512 ≡ 0`，**回到同一组**。2 路只能放 2 条，第 3 个同组地址必然踢掉一个，于是三个数组一起遍历时每次访问都 miss。

推广：只要 stride 是"组数 × 行大小"的整数倍（512 × 64 = 32 KiB），就会自撞。这就是"矩阵边长取 2 的幂、并行数组一多就慢"的物理原因。
</details>

**Q2.** 一个结构体里有 `long a` 和 `long b` 两个计数器，被两个线程分别写——注意是**同一个实例**。你给结构体加了 `__attribute__((aligned(64)))`，`sizeof` 从 16 变成 64，性能一点没变。为什么？给出两种正确的修法。

<details><summary>答案</summary>

因为对齐改变的是**这个对象占多大、从哪开始**，不是**它内部两个字段的相对位置**。`struct { long a, b; } __attribute__((aligned(64)))` 里 `a@0`、`b@8`，仍在同一条 64 B 行里；`sizeof=64` 只影响相邻的下一个实例从哪里开始。两个线程写的还是同一行，伪共享原封不动。

修法：
1. **拆对象**：两个计数器不再是同一实例的字段，而是两个各自按 64 B 对齐的对象——`static _Alignas(64) long cnt_a, cnt_b;`；或每个线程一个 `struct slot { long v; char pad[56]; } aligned(64)`，放在 `aligned_alloc(64, 64)` 的独立块里。
2. **拆到不同实例**：如果计数器本来就属于"每个 worker 一份"的结构，就让每个 worker 用**不同实例**（`st[0]` / `st[1]`），并把该结构体尺寸撑到 64 的倍数——同实例内相邻字段永远救不了。

判别方法只有一个：打印两个变量地址的 `addr & ~63UL`，不同才算真隔离。
</details>

**Q3.** 下面这段"发布配置"的代码在 x86 上跑了两年没事，换到 ARM 服务器后偶发读到半初始化对象。请指出两处问题，并给出最小修法。

```c
static Config *g_cfg;
void publish(void) { g_cfg = load_config(); g_ready = 1; }   /* g_ready 是 volatile int */
Config *get(void)  { if (g_ready) return g_cfg; return NULL; }
```

<details><summary>答案</summary>

两处问题：

1. **StoreStore 重排**：`g_cfg = ...` 与 `g_ready = 1` 是两个普通写。x86-TSO 禁止 StoreStore 重排，所以两年没事；ARM64 允许，读者可能先看到 `g_ready == 1`、再读到旧的 `g_cfg`（NULL 或半初始化对象）。`volatile` 只约束"不许优化掉这次访问"，**不建立跨核的顺序**。
2. **LoadLoad/LoadStore 重排**：读者侧 `if (g_ready) return g_cfg;` 也可能先读 `g_cfg` 再读 `g_ready`。

最小修法（C11）：写者用 release 发布指针，读者用 acquire 取指针，`g_ready` 根本不需要：

```c
static _Atomic(Config *) g_cfg;
void publish(void) { atomic_store_explicit(&g_cfg, load_config(), memory_order_release); }
Config *get(void)  { return atomic_load_explicit(&g_cfg, memory_order_acquire); }
```

release 保证"初始化对象的全部写"先于"发布指针的写"可见；acquire 保证"读到指针之后的所有读"不会被提前。Go 里对应 `atomic.Pointer[T].Store/Load`，Java 里对应 `volatile` 字段（在 x86 上写侧生成 `lock or`，读侧为空）。
</details>
