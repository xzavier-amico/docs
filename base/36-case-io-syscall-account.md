## 36.1 引子：四条消息，为什么有两种正确的调用账？

假设一个连接上有四条 32 字节消息，服务端只把内容原样回传。第一种客户端发一条、等一条；第二种客户端一次发送四条，再收四条。业务处理的净字节数都是 128 B，但两种发送策略给服务端留下的合并空间不同。不要先问换哪种 API，先问：**服务端必须什么时候把结果交出去？** 如果协议要求客户端等到上一条的结果才知道下一条是什么，第二种策略根本不可用。反过来，如果四条本来就独立，每条单独穿过系统调用边界就值得检验。

| 口径 | 是什么 | 不是什么 |
| --- | --- | --- |
| 业务消息 | 由应用分帧规则定义 | TCP 段、一次 `recv` 的结果 |
| 就绪通知 | 现在尝试操作可能有进展 | 已替应用读完一条消息 |
| 完成通知 | 已提交操作得到的结果，例如读到多少字节 | 完整业务请求已处理 |
| 系统调用 | 一次通过 syscall 接口进入内核 | 一次线程上下文切换；不睡眠也能进出内核 |

## 36.2 ① 它是什么：同一条连接的三种等法

| 模型 | 等在哪里 | 有数据后谁发起实际读写 | 账从哪开始算 |
| --- | --- | --- | --- |
| 阻塞 I/O | 工作线程在 `recv` 等待 | 这个线程的 `recv`、`send` | 实际调用次数，另记调度与线程资源 |
| `epoll` | 一个或多个线程等待就绪集合 | 事件循环对就绪 fd 做 `recv`、`send` | `epoll_wait` 和读写分别计；注册/修改另计 |
| `io_uring` | 应用等待完成，或继续干别的活 | 应用先提交读写，内核或辅助线程处理，结果进 CQ | SQE/CQE 数与 `io_uring_enter` 数分别计 |

阻塞 I/O 的好处是有一条清楚的调用栈：一条连接每阶段在哪等，代码看得见。它不会因为“阻塞”两字就比 epoll 多做系统调用。epoll 节省的是对大量闲置描述符逐个检查的工作，并让少量线程照看很多连接；同一个活跃 fd 可能反而多一次等待就绪的调用。`io_uring` 的结构性收益是一次提交多个独立操作、一次消费多个完成，不是把读写本身省掉。

## 36.3 ② 物理形态：就绪与完成的分界

```text
epoll : socket 可读 → 就绪表 → epoll_wait 返回 fd → recv → 应用处理 → send
uring : 写 SQE → 通知内核（可批）→ 请求执行 → CQE 带结果 → 应用处理 → 提交 send
```

就绪不能替代错误处理。非阻塞 `recv` 有可能返回 `EAGAIN`，例如这份数据已经被另一个消费者读走；读 0 表示有序关闭接收方向，不能当成“暂时没数据”。`send` 返回正数也可能只发出前一段。ET 对普通流式 socket 的惯用读法是读到 `EAGAIN`，或者在应用维护一份待继续处理的就绪列表；如果为了公平性设了每轮预算，就不能读一半后完全依赖下一次边沿通知。LT 较容易写对，但反复唤醒后不清理积压，仍会消耗 CPU。**两种触发方式不规定哪一种调用次数较少**：ET 的最后一次探测本身可能就是一次返回 `EAGAIN` 的调用。

`io_uring` 的 `user_data` 适合标识连接和操作，在 CQE 中检查 `res`：负数是错误，非负数仍可能是短读短写。缓冲区不能在操作完成前随意复用；提交 `cancel` 也不是“这一刻所有操作已经停止引用”。设置批量时，还要考虑 SQ 是否有空位、CQ 怎么及时消费以及如何应对连接关闭。否则虽然 `enter` 次数降低了，排队、内存占用或尾延迟可能变坏。

## 36.4 ③ 走一遍：只用一对本地 socket

这是可控的调用计数实验，不建监听端口，不改内核参数，不跑高并发。用 `socketpair` 隔开两端，用 `MSG_WAITALL` 固定实验的读取长度。每轮只发送 32 或 128 B，且每次读之前数据已写入，不用忙等。**这不是生产版事件循环**：阻塞接收与固定长度只是在这里方便控制变量。

```python
import select, socket

for batch in (1, 4):
    client, server = socket.socketpair()
    with client, server, select.epoll() as ep:
        client.settimeout(.5)
        # server.recv 使用 MSG_WAITALL；数据先写入，且入站只有一个读者。
        ep.register(server, select.EPOLLIN)
        count = {'wait': 0, 'recv': 0, 'send': 0}
        for _ in range(0, 4, batch):
            payload = b'x' * (32 * batch)
            client.sendall(payload)
            assert ep.poll(.2) == [(server.fileno(), select.EPOLLIN)]
            count['wait'] += 1
            chunk = server.recv(len(payload), socket.MSG_WAITALL)
            count['recv'] += 1
            server.sendall(chunk)
            count['send'] += 1
            assert client.recv(len(payload), socket.MSG_WAITALL) == payload
        print(batch, count)
```

收尾时实跑了上述核心路径（给客户端加超时不改变成功路径的逻辑计数）：

```text
1 {'wait': 4, 'recv': 4, 'send': 4}
4 {'wait': 1, 'recv': 1, 'send': 1}
```

计数的是服务端 API 调用，不是内核 trace；不含客户端、注册、关闭，也不把包装函数 `sendall` 当作任何环境下都只调用一次 `send` 的证明。实验未测跨机吞吐、`io_uring`、ET 或线程池的性能。若需要实际系统调用次数，用跟踪器在相同连接模型下计数，并把跟踪开销和独立计时分开。若要精确比较批量成本，额外统计每批消息的数量、每项操作的返回值、短读写次数，以及进程 CPU 时间。

## 36.5 ④ 改一行：先比较消息策略，再比较 API

| 四条消息，各 32 B | 逐条请求应答 | 批量请求应答 |
| --- | ---: | ---: |
| 业务净载荷（单向） | 128 B | 128 B |
| 服务端等待/读/写逻辑调用 | 4 / 4 / 4 | 1 / 1 / 1 |
| 服务端上述计数合计 | 12 | 3 |
| 业务确认可以提前到第几条 | 第一条 | 批次交付；第一条可能等后三条 |

为什么不拿这个结果宣称 `io_uring` 比 epoll 快四倍？因为两边都是 epoll，而且变的是**何时发送与确认**。假设有 32 条独立连接均可读，环可以一次提交 32 个接收请求；处理完再提交 32 个发送请求。模型上，若每阶段只需一次 `enter`、队列容量够、无需单独的等待调用，则有 2 次提交入口、64 个操作；真实环境可能需要额外等待、重新提交短操作或补偿 SQ/CQ 背压。这些都要记账。如果每条请求必须读完才能知道发什么，不能预先把同连接的所有读写作为彼此独立的请求处理。

### 算法怎样影响尾延迟

流量均匀，设到达率为 4,000 条/秒，凑齐 4 条才发。批内第一条等待后三条，假设等间隔则额外等 `3 / 4000 = 0.75 ms`；若流量忽然停了，最坏等待不是这个数，而是业务设定的刷新时限（没设就可能一直等）。因此常用策略是满批或计时阈值先到即发。计量时要同时看批次分布和端到端 P99；只报满载时的调用数看不到稀疏流量那一端。

## 36.6 ⑤ 它证伪了谁：少一次入口不等于少一次操作

例如在一个**估算**里，8 万请求/秒，每请求省 3 次入口，假设每次仅入口开销为 150 ns，则省下 `80,000 × 3 × 150 ns = 36 ms/s`，约一个核的 3.6%。这不包括内核实际处理、数据复制、唤醒和争抢。很可能值得做，但不能据此承诺 4 倍 QPS。如果原来 20% 的端到端 CPU 工作可被优化为原来的 1/4，其他不变，新成本比例为 `0.8 + 0.2/4 = 0.85`，CPU 受限吞吐才可能接近 `1/0.85 ≈ 1.18×`。如果瓶颈是下游速率，吞吐甚至不动，只是 CPU 降了。

| 看到的现象 | 先证实什么 | 再考虑什么 |
| --- | --- | --- |
| `epoll_wait` 次数很多 | 每次返回多少 fd、是否空转、读写返回什么 | 去掉零超时忙等，确认是否需要批量 |
| `EAGAIN` 很多 | 是 ET 的正常收尾，还是写入侧一直打不出去 | 只在有待发数据时订阅可写；做每连接队列上限 |
| CQ 越积越多 | 应用取完成不及时，还是瞬时提交太多 | 限制在飞操作；检查短读写和取消路径 |
| 从 epoll 换环后 QPS 不变 | CPU、带宽、队列哪个先饱和 | 用相同负载、消息语义、连接数和资源配额再比 |

## 36.7 三列账与一页速记

| 承诺 | 代价 | 失效边界 |
| --- | --- | --- |
| 就绪接口可用一个等待观察多个 fd | 仍要读写并处理错误 | 将就绪等同完成、ET 漏读 |
| 完成接口可以摊薄提交/等待成本 | 管理在飞操作、缓冲区和完成队列 | 短操作没有重发、完成队列积压、批量拉高尾延迟 |
| 合批减少调用总数 | 要为第一条设置最大等批时间 | 请求有因果依赖，不可合批 |

**速记**：业务消息数、逻辑 I/O 数、入口次数、调度切换数分别统计。测性能前先保证四种数的分母是同一批已正确处理的消息。

## 36.8 自检 3 题

1. LT 有 100 个 fd 就绪，`epoll_wait(maxevents=32)` 能一次返回全部吗？
2. 收到 128 B，能否断言里面恰好有四条业务消息？
3. 32 个 SQE 被一次提交，实测为什么仍有多次 `enter`？

<details><summary>答案</summary>

1. 不能，一次最多返回 32 项；应用不能把 `maxevents` 当成全量计数。
2. 只有在已知这是对齐的固定长度 32 B 协议、没有其他控制字段时才可以；一般靠分帧规则。
3. 提交和等待不一定合并，环有容量和在飞限制，短操作可能要补交，唤醒轮询线程也可能要进内核。要到运行现场逐项分类。

</details>
