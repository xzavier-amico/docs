# 45. DNS 安全剖析：一个三缺协议怎么被攻击、又怎么被补

> **状态**：`已完成（初稿）` ｜ **所属**：第四部分 · 网络：从一根网线到一张证书 ｜ **编号**：45 / 56
> **本篇定位**：Part IV 的第八篇，也是 44 的安全对偶。44 讲 DNS 的报文、递归与 TTL，本篇只回答一件事：**这个协议天生缺认证、缺完整性、缺机密，三缺各自长出了什么攻击，每一种补法又把坑挪到了哪里**。全篇只有一条推论链——`查询是一个无状态 UDP 小包` → `客户端只能靠一堆可猜的字段认领响应` → `所以攻击的成本等于猜中概率` → `随机化只是把概率做小，DNSSEC 才补上完整性，DoH 只补机密` → `而每一层补法都自带新的失效面`。48 篇会把这张三缺表推广到所有协议，本篇只把 DNS 这一列拆到底。

## 45.1 引子：证书是合法的，锁是绿的，人还是被钓了

先看一份脱敏的事故时间线。数字取自工单，域名与 IP 已替换；它不是某一家公司的独家故事，而是一整类事件的共同形状。

| 时间 | 事件 | 当时监控看到什么 |
| --- | --- | --- |
| T-14d | 域名托管在第三方 DNS 面板，账号未开 MFA，登录无告警 | 一切正常 |
| T-6d | 凭据从一台失陷的运维笔记本泄露，攻击者登录面板，只读观察了一周 | 面板无异常登录规则 |
| T-0 08:57 | A 记录由 `198.51.100.10` 改为 `203.0.113.7`，TTL 300 | 权威侧无变更审计，递归侧只是「按 TTL 生效」 |
| 09:03 | 攻击者用 DNS-01 向一家公共 CA 申请证书——**因为 zone 已经在他手里**，挑战自然通过 | CA 认为「域名控制权已验证」 |
| 09:05 | 员工访问 `bank.example.com`：解析到 `203.0.113.7`，TLS 握手成功，证书 SAN 正是 `bank.example.com`，链到公共根 | 浏览器：锁是绿的；EDR：无告警 |
| 09:06–09:40 | 钓鱼页把凭据与 OTP 实时中继到真站，用户完成登录 | 真站看到的是「合法会话」 |
| 09:41 | 财务发现一笔转账收款方变更 | 人工 |
| 10:20 | 安全团队在 CT（Certificate Transparency）日志里发现一张 6 分钟前签发、issuer 不是本单位惯用 CA 的证书 | **唯一留下痕迹的地方** |
| 10:35 | 改回记录、吊销证书；OCSP/CRL 生效还有延迟 | 伤害已发生 |

这张表最刺眼的一行是 09:05。绝大多数人的直觉是「有 HTTPS 就安全」，而这一步里 TLS 的三件事全部成立：机密性（密钥协商成功）、完整性（MAC/AEAD 校验通过）、对端身份（证书链校验通过、名字匹配）。**TLS 没有说谎，它只是回答了它被设计来回答的那个问题：你连上的这台机器，是不是持有 `bank.example.com` 私钥的那台。** 而「`bank.example.com` 应该指向哪台机器」这个问题，TLS 从来没管过——它是 DNS 回答的。

所以本篇要拆的不是「怎么防钓鱼」。要拆的是：DNS 在这条信任链上到底承诺了什么、缺了什么，以及为什么**它缺的东西恰好是 PKI 的根**。把这件事说清楚，后面所有攻击都只是同一句话的不同句式：`客户端无法证明这个回答来自它声称的来源`。

## 45.2 三缺总表：一张表把全篇的攻击与补法串起来

DNS 的设计目标是「小、快、无状态、能撑住全球查询量」，不是「安全」。它缺的三样东西不是并列的三个 bug，而是三层不同性质的缺口：

- **无认证**：协议里没有任何字段能证明「这个响应来自该 zone 的权威服务器」。客户端只能靠一串**可猜的巧合**（源地址、源端口、事务 ID、问题名）来认领响应。攻击者不需要破解任何密码，只需要猜中。
- **无完整性**：RRset 上没有签名。任何能碰到报文的人——路上的中间盒、Wi-Fi 热点、被投毒的递归——都能改一个字节而不被发现。
- **无机密**：53 端口是明文 UDP/TCP。路径上任何人都能读到你查了什么、得到什么答案。

三者的关系是：**认证缺失让「伪造」成为可能，完整性缺失让伪造的结果能被长期缓存，机密性缺失让攻击者从「猜」升级为「读」。** 下面这张四列表是全篇索引，每一行都对应后面一节：

| 缺什么 | 由此长出的攻击 | 补什么 | 补法的代价（新坑） |
| --- | --- | --- | --- |
| 认证 | 伪造响应、缓存投毒、Kaminsky（§45.3–§45.4） | 源端口 + 事务 ID + 0x20 随机化、DNS Cookie | 只把猜测成本做高，不证明来源；NAT 与中间盒会把熵吃回去 |
| 认证 | 反射放大 DDoS（§45.6） | BCP38 入口过滤、RRL、最小响应、拒绝 ANY | 要 ISP 配合；RRL 误伤正常重试；ANY 被工具依赖 |
| 完整性 | 中间人改写、投毒、上游被篡改后无法察觉（§45.7） | DNSSEC：RRSIG + DS 链 + 信任锚 | 运维成本高；断链即全站不可用；响应变大 2–7 倍 |
| 机密性 | 路径监听、按域名审查、DNS 隧道外带（§45.8） | DoT / DoH / DoQ | 默认不认证「答案的来源」；企业失去可见性；解析权外移给第三方 |
| 语义 | rebinding、子域接管、通配符与 NXDOMAIN 缓存、`search` 劫持（§45.9） | TTL 下限、私有地址过滤、CNAME 归属审计 | 与 CDN/动态 DNS 冲突；误杀合法内网解析 |
| 本地 | `hosts`/`resolv.conf` 被改、LLMNR/NBNS 广播投毒、恶意 DHCP（§45.10） | 文件完整性、DHCP snooping、关闭广播解析 | 部署成本；旧设备兼容性 |

再补一句话，它是全篇的判据：**后面每一种补法，都只是在「猜中的概率」「被改的可能性」「被读的可能性」三者里挑一个往下压，没有一个把「来源可信」这件事真正补全。** DNSSEC 最接近，但它只签「这个 RRset 是 zone 主人签的」，不签「你现在连的这台递归有没有骗你」。

## 45.3 无认证 → 伪造响应：客户端凭什么认领一个 UDP 包

### 一次查询的物理形态

`dig example.com A` 在线上是这样一个东西（本机实测，报文体 40 字节，加 IP/UDP 头 28 字节，共 68 字节上线路）：

```
IP 头 20B │ UDP 头 8B │ DNS 头 12B │ QNAME "example.com" 13B │ QTYPE 2B │ QCLASS 2B │ OPT 11B
                                    12 + 13 + 4 + 11 = 40B
```

关键在 DNS 头里的 16 位事务 ID，和 IPv4 头里的源地址——**两者都不是秘密，也都不是证明**。客户端发出查询后，内核里只有一个「等一个 UDP 包」的接收队列；当包到达，递归解析器（或 stub）要决定「这个包是不是我在等的那一个」。它手上只有这些字段：

| 匹配键 | 谁选的 | 攻击者能否伪造 | 说明 |
| --- | --- | --- | --- |
| 客户端本地端口 | 客户端内核（临时端口） | 不能直接伪造，**只能猜** | 现代解析器每查询换一个 |
| 事务 ID（16 bit） | 客户端随机数 | 不能直接伪造，**只能猜** | 老实现用计数器，更糟 |
| 服务端地址:端口 | 配置/根提示 | **可以完全伪造**（UDP 无握手） | 所以这一项不提供熵 |
| QNAME / QTYPE / QCLASS | 查询本身 | 攻击者知道（他触发的查询） | 用来过滤「答非所问」 |
| 附加字段（0x20 大小写等） | 客户端编码 | 不知道则猜 | 见 §45.5 |

**注意第三行**：来源地址是一项匹配条件，不是密码学身份。事务 ID 的字段宽度和临时端口字段宽度也不是实际随机熵；有效值受实现、可用端口和中间设备影响。

### 防御核对：用离线测试向量检查应答匹配

以下是防御测试的**预期断言**，不是抓包结果。测试输入是解析后的记录，不发送数据报，不复现攻击。

| 离线输入 | 预期判定 |
| --- | --- |
| 事务 ID 与问题一致，但对端地址或端口不同 | 不匹配未决查询 |
| 对端一致，但问题类型或类不同 | 不匹配未决查询 |
| 报文匹配，但收录范围或 DNSSEC 验证不通过 | 不应作为已验证答案接受或缓存 |
| 匹配与验证均通过 | 按解析器配置与缓存规则继续处理 |

这些检查各有作用。匹配降低误收概率，但不提供密码学意义上的数据来源证明；IP 源地址验证还受路径与网络策略约束，不能说在任何环境都可任意伪造。

要分别验收查询匹配和数据可信度：即使应答匹配未决查询，正常解析器还要限制收录范围，验证可验证的数据，并维护缓存的有效期限。

## 45.4 缓存投毒与 Kaminsky：2008 年那笔账是怎么算的

### 投毒投的不是「一个人」，是「一台递归的缓存」

§45.3 的伪造要每次都抢在真答案前面，收益只有一次查询。**缓存**改变了收益结构：递归解析器会把答案连同 TTL 存下来，TTL 内所有客户端都复用。于是攻击者的目标从「骗一个用户」变成「骗一台递归」，一次成功的收益是这台递归背后的所有人 × TTL 时长。

缓存的安全风险在于共享：错误数据可能影响后来查询的其他客户端，错误的委派信息还可能让影响范围从单条记录扩大到整个区。检查答案区、权威区与附加区的收录边界，并将异常委派与正常变更记录核对。

### 2008 年公开问题带来的防御变化

历史问题表明，可预测的响应关联字段及宽松的委派收录策略会共同放大缓存风险。修复不是单独调 TTL：更新递归解析器，按 RFC 5452 严格匹配未决查询，启用不可预测的关联字段，限制可进入缓存的记录范围，并在适用的委派链上做 DNSSEC 验证。

| 防御层 | 核对证据 | 不应误读 |
| --- | --- | --- |
| 解析器 | 安全更新、查询匹配与委派范围设置 | 事务 ID 是匹配字段，不是身份凭证 |
| 出口 | 不可预测的临时端口，检查 NAT 是否压缩可用空间 | 协议字段位数不是实际熵 |
| 认证 | 签名验证与受信解析路径 | 传输加密不等于权威数据已签名 |

### 为什么「每查询一端口」是分水岭

如果解析器开一个 socket 服务所有查询，端口就固定了，32 位又退回 16 位。RFC 5452 把要求写成四条：ID 不可预测、源端口不可预测、校验响应的问题名与类型、校验响应来自被查询的地址；RFC 6056 专门讲端口选择算法。**这四条是同一件事的四个面：在没有认证的协议里，客户端能做只有「让自己难猜，并且只接受答得上的那个」。**

## 45.5 补法一：随机化——把 32 位做成 32 位有多难

随机化有三个层次，本机实测都拿得到证据。

**第一层：源端口。** 连开 16 个 UDP socket，让内核挑临时端口，得到：

```
28910 26236 60978 13238 17165 54571 54648 51313 28438 27078 38384 53843 25698 33909 52203 26143
range 13238..60978   distinct 16/16
```

不是递增，不是固定，16 个全不同——这是 Linux 的端口选择在起作用。但「看起来随机」不等于「密码学随机」：端口空间只有 16 位，且内核是在一个可用区间里做哈希/偏移，攻击者能压缩候选集（比如排除掉本机已用的端口、排除掉 NAT 保留段）。

**第二层：事务 ID。** 连查 10 次，`dig` 打印的 ID：

```
30755 25180 32756 48616 2539 11505 40668 50112 24093 7698
```

10 个值横跨 2539–50112，没有单调性。老实现用 `rand()` 或递增计数器，那样 16 位里的有效熵可能只有个位数。

**第三层：0x20 编码。** DNS 名字大小写不敏感，但响应必须原样回显问题里的字节。于是客户端可以把 `example.com` 发成 `ExAmPlE.CoM`，只有真正看到了这个查询的服务器才能把大小写原样抄回来。本机实测：

```
;; QUESTION SECTION:
;ExAmPlE.CoM.			IN	A
;; ANSWER SECTION:
ExAmPlE.CoM.		266	IN	A	172.66.147.243
```

问题区和答案区的名字都保留了原始大小写——这就是 0x20 能工作的物理前提。它给每个字母加 1 bit，13 个字母就是 13 bit；代价是双方都要多做一次大小写比较，而且**任何把名字规范化为小写的中间设备都会让它失效**。

### 随机化买到了什么、没买到什么

| 层次 | 增加的熵 | 挡住的攻击 | 现实中的折扣 |
| --- | --- | --- | --- |
| 临时端口选择 | 取决于出口实际分配 | 降低固定端口带来的可预测性 | NAT 映射不一定均分端口；根据受管网络的配置和观察核对 |
| 密码学随机 ID | 16 bit（若原来是计数器则更多） | 可预测 ID | 中间盒「ID 归一化」把它改回递增；老设备 PRNG 早期熵不足 |
| 0x20 | 每字母 1 bit | 看不见查询的离线猜测 | 权威/负载均衡把名字小写化即失效；DNSSEC 的规范化形式本来就是小写，签过名的数据上它不增加任何安全性 |
| DNS Cookie（RFC 7873、RFC 9018） | 有独立的协议规定，不与字段宽度直接相加 | 缓解部分路径外伪造与滥用 | 需要端点支持；不是数据签名或保密机制 |

一句话：**随机化是把「猜中概率」从 2⁻¹⁶ 压到 2⁻³²，属于「提高犯罪成本」，不属于「建立信任」。** 只要攻击者能**看到**你的查询，随机化立刻归零——他不用猜，照抄 ID 和端口就行。这既说明它补不了认证，也说明为什么机密性（§45.8）是另一条独立的缺口。

## 45.6 无认证 → 反射放大：60 字节换 4 KB

反射放大要求网络未阻止源地址伪造，且能向不受信客户端返回较大的无连接响应。容量评估要区分递归和权威：开放递归与响应较大的权威服务都可能带来风险，但策略和限制不同。

响应大小和请求大小都要按同一层计量，不能给不同查询套用同一个请求长度。EDNS 的接收上限也不是实际响应长度；大应答可以截断并改用 TCP。下面是历史稿保留的 `dig` 截断输出节选，只用于解释 `TC`，不作为放大倍率的测量：

```
;; flags: qr tc rd ra; QUERY: 1, ANSWER: 0, AUTHORITY: 0, ADDITIONAL: 1
;; MSG SIZE  rcvd: 38
```

`TC=1` 表示结果被截断；这一份只有 38 B 且没有答案记录，不是完整应答的大小。

### 补法：把「开放」和「大」两件事各自关掉

| 措施 | 作用点 | 代价 |
| --- | --- | --- |
| 关闭开放递归（只服务授权客户端） | 递归侧 | 运维上要维护 ACL；漫游用户要 VPN |
| BCP 38 / RFC 2827 入口过滤 | ISP 侧 | 需要运营商在边缘做 uRPF；多宿主与旧 CPE 会误伤 |
| RRL（Response Rate Limiting） | 权威侧 | 按 zone + /24 限速，超限回 TC 或丢弃；**误伤** DNSSEC 重试与 NAT 后的大量用户 |
| 最小响应 / 拒绝 ANY（RFC 8482） | 权威侧 | 老工具依赖 ANY；本机实测 1.1.1.1 对 ANY 直接回 `status: NOTIMP`、42 字节 |
| 限制 EDNS 缓冲到 1232 | 权威侧 | 大响应改走 TCP，延迟上升；2020 年 DNS Flag Day 的默认值 |
| DNS Cookie | 双方 | 需要服务端支持；只挡伪造，不挡真实的大查询 |

排查时先找生效的 ACL、是否拒绝非授权递归、响应策略以及源网的地址校验，再用本系统日志和指标估算风险；不要把 EDNS 上限写成固定倍率。

## 45.7 无完整性 → DNSSEC：只签名，不加密

### 它到底签了什么

DNSSEC 不给 DNS 加密，也不隐藏查询。它只做一件事：**让每个 RRset 带上一段由 zone 私钥签出的 RRSIG，并让「这把公钥属于这个 zone」这件事可以沿着一棵树追到根。** 本机对 `isc.org` 的实测：

```
isc.org.  300  IN  A      199.232.90.0
isc.org.  300  IN  RRSIG  A 13 2 300 20261130060025 20261116055922 27566 isc.org. SFZrZq...
;; flags: qr rd ra ad;
```

`RRSIG` 后面那串字段每一位都有含义：类型 `A`、算法 `13`（ECDSA P-256）、标签数 `2`、原始 TTL `300`、签名过期 `20261130060025`、生效 `20261116055922`、密钥 tag `27566`、签名者 `isc.org.`，最后是签名本身。**`ad` 位是递归替你做完了验证后打的勾**——它不是权威签的，是你信的那台递归的判断。

链的形状是这样的（`DS` 在父区、`DNSKEY` 在子区，这是 DNSSEC 唯一需要的两种新记录）：

```
根 KSK（配置在解析器里的信任锚，不靠 DNS 获取）
  └─ 签 根 DNSKEY 集合（含 ZSK）
       └─ 根区放 com. 的 DS ──►  com. 的 DNSKEY（自签 + 被 DS 摘要校验）
            └─ com. 区放 cloudflare.com. 的 DS ──► cloudflare.com. 的 DNSKEY
                 └─ cloudflare.com. 用 ZSK 签 A / AAAA / MX ...
```

本机把这条链上的三段都抓了出来：根区是 1 把 ZSK（flags 256）+ 2 把 KSK（flags 257）、算法 8（RSA/SHA-256）；`com.` 的 DS 在根区，key tag `19718`、算法 13、摘要 2；`cloudflare.com.` 的 DS 在 `com.` 区，tag `2371`，child 侧的 DNSKEY 则是 256（ZSK）与 257（KSK）各一把。

`DS` 后面的 `13 2` 是「算法 13、摘要类型 2（SHA-256）」，摘要正好 32 字节 = 64 个十六进制字符。**KSK 签 DNSKEY（离线、少见），ZSK 签业务数据（在线、常换）**：这个分工让日常签名密钥可以待在联网机器上，而信任锚留在离线环境。根区同时发布 2 把 KSK 也是刻意的——轮换时新旧并存，避免全球解析器在同一秒失去锚点。

### 否定回答也要签：NSEC / NSEC3 与 zone walking

「这个域名不存在」同样需要一个可验证的证明，否则攻击者只要伪造 NXDOMAIN 就能让一个存在的名字消失。DNSSEC 的办法是**把 zone 里所有名字按序排好，返回「夹住这个查询名的那一对相邻名字」**。本机对 `nosuchname-abc123.cloudflare.com` 的实测：

```
nosuchname-abc123.cloudflare.com. 300 IN NSEC \000.nosuchname-abc123.cloudflare.com. RRSIG NSEC TYPE128
```

`NSEC` 直接给出「下一个存在的名字」，于是**任何人都能顺着它把整个 zone 枚举出来**——这就是 zone walking。名字本身是商业信息（内网主机名、未公开 API、员工邮箱域），所以有了 NSEC3：只返回名字的哈希。本机对 `nic.cz` 的实测：

```
37i294g7lfkknon49e4gbd7aec6m0s9p.nic.cz. 1800 IN NSEC3 1 0 0 - 38RFRSDU96G843QJ0STQTMFMGEBLDIIC TXT RRSIG
```

`1 0 0 -` 是「哈希算法 1（SHA-1）、flags 0、迭代 0 次、空 salt」。**迭代 0 次意味着枚举者只需对每个候选名字做一次哈希**——NSEC3 把「直接读」换成了「离线字典」，字典便宜时它只是延缓。真实部署里还有 opt-out 与 Cloudflare 式的「black lies」（对任何不存在名字都回一个覆盖 `\000` 的 NSEC），后者用统一回答换掉了可枚举性。

### 为什么全球部署率还是低

我在本机对 35 个常见域名做了一次抽样（`dig +dnssec` 看 `ad` 位，再用 `dig DS` 交叉验证），结果是 **10 个有 DS 且拿到 `ad`，25 个没有**，28.6%：

```
SIGNED   cloudflare.com  comcast.com  gov.uk  ietf.org  isc.org
         nic.cz  nlnetlabs.nl  paypal.com  verisign.com  whitehouse.gov
unsigned google.com  youtube.com  facebook.com  amazon.com  github.com  ...
```

两组完全重合，说明抽样里没有「签了但验不过」的噪音——28.6% 是一个干净的观测值。原因不是技术不成熟，而是**收益与成本不对等**：

- **运维成本**：密钥要轮换、备份、演练；KSK 滚动出错是全球事故；多 CDN、多签（multi-signer）要几方协调。
- **断链即全站不可用**：DNSSEC 的失败模式是「全有或全无」。本机对 `dnssec-failed.org` 的对照：

```
$ dig dnssec-failed.org A     -> status: SERVFAIL, ANSWER: 0, 103 B
$ dig +cd dnssec-failed.org A -> status: NOERROR,  A 96.99.227.255, 119 B
```

一条 RRSIG 过期、一个时钟偏差、一次 DS 上传漏了，用户看到的不是「安全性下降」，而是「网站打不开」——对业务方这是不可接受的失败模式。
- **动态 DNS 与 CDN 复杂**：短 TTL、按请求签发、边缘在线签名，把「签名」从一次配置变成一条流水线。
- **只保护名字，不保护你**：DNSSEC 签的是「zone 主人说是这个值」，zone 主人自己被钓鱼（§45.1）时，签名会忠实地为假记录背书。

### DNSSEC 自己留下的坑

| 新坑 | 机制 | 本机证据 |
| --- | --- | --- |
| 响应变大 → 更容易被放大 | RRSIG/NSEC 把答案撑大 | `isc.org` 100 → 203 字节；`nic.cz` 51 → 153；NXDOMAIN 105 → **754**（7.2×） |
| 分片与 TCP 回退 | 超过 EDNS 缓冲就置 TC，改走 TCP；TCP/53 被封就整域失败 | `+bufsize=512` 时 TXT 响应 `tc=1`、38 字节 |
| NSEC 可枚举 | 否定证明直接给出下一个名字 | `NSEC \000.nosuchname...` 实测 |
| 时钟敏感 | RRSIG 有生效/过期时间 | 设备时间错 → 全部 SERVFAIL（时钟机制见 `base/55`） |
| 放大杠杆变大 | 签名域是更好的反射器 | 上面 7.2× 的 NXDOMAIN |

一句收束：**DNSSEC 补的是完整性，代价是把「解析失败」从「拿到一个可疑答案」升级成「什么都拿不到」，并且顺手把反射放大的杠杆做大了。**

## 45.8 DoT、DoH、DoQ：认证解析器不等于验证签名数据

### 三种封装，同一件事

| 方案 | 端口/传输 | 外观 | 它隐藏了什么 | 它没隐藏什么 |
| --- | --- | --- | --- | --- |
| DoT（RFC 7858） | 853/TCP + TLS | 专用端口，一眼可识别 | 查询名、答案、EDNS 选项 | 你在用 DoT、目标解析器是谁 |
| DoH（RFC 8484） | 443/TCP + HTTPS | 与普通网页流量混在一起 | 同上 | 目标域名（SNI 可见，除非 ECH）；流量时序 |
| DoQ（RFC 9250） | 853/UDP + QUIC | 专用端口，UDP 上加密 | 同上，且无 TCP 队头阻塞 | 端口与流量形态 |

本机实测暴露了两件事：`dig` 的 `SERVER` 字段直接写出了「我在用谁、走什么协议」——`1.1.1.1#53(1.1.1.1) (UDP)`；而 853 在公共解析器上是开着的（`nc -zv 1.1.1.1 853` 与 `8.8.8.8 853` 都返回 succeeded，完整输出见 §45.11 ④）。合起来说明：**这台机器当前走的是明文 53，而加密通道就在旁边开着。** 换成 DoT/DoH 只是改配置，但「改了以后是否更安全」是另一个问题。

### 加密补的是路径，不是来源

TLS 在 DoH 里认证的是**解析器**（`cloudflare-dns.com` 的证书），不是**答案的来源**。这中间隔着一整条链：

```
你 ──TLS──► 公共解析器 ──明文/加密──► 权威服务器
      ↑ 这里被认证            ↑ 这里才是答案的出生地，没有被端到端认证
```

于是有三种「加密但不安全」的形态：

1. **解析器说谎或被投毒**。TLS 让路径上的人看不见，也让**你**看不见——你无法像抓包那样发现答案不对。
2. **解析权外移**。用公共 DoH 等于把「你查了什么」交给第三方；ECS 还会把你的网段一起带过去。
3. **内部名字失效**。split-horizon 的 `intranet.corp` 在公共解析器上不存在，浏览器自动升级后直接「域名不存在」。

### 企业侧的后果：DNS 日志是最好用的检测面，DoH 把它关了

DNS 查询日志是安全运营的主战场，因为它**便宜、全量、跨应用**：C2 回连、DGA、隧道外带、钓鱼首跳都在这留一条记录。DoH 一上，网络侧只剩「一条到 1.1.1.1:443 的长连接」。这不是理论问题——Chrome、Firefox、Windows、iOS 都在推自动升级，员工装个浏览器就绕过了。

补偿措施按代价从低到高：把 DHCP/DHCPv6 的解析器指向内网 DoH（有日志）；用 `use-application-dns.net` 这类 canary 域名阻止自动 DoH；出口封 853 与已知 DoH IP；对无法封的做 SNI/指纹识别；最后才是 TLS 解密。**这些全是「把可见性抢回来」，没有一条恢复「端到端可信」。**

### DNS 隧道：把协议当信道

DNS 字段可能被用作非预期的数据通道。排查时调查客户端、查询角色与业务目的；TXT、长标签或解析失败各自都可能有正常成因，不能单独作为阻断依据。

检测侧只看形态，不看内容（本节只讲识别）：

| 信号 | 正常流量 | 隧道流量 |
| --- | --- | --- |
| 唯一子域数量 | 按业务角色建立基线 | 与自身历史显著偏离时提高调查优先级 |
| 标签长度分布 | 受服务发现、CDN 和业务命名影响 | 长标签增多不等同于有害流量 |
| 字符分布 | 合法查询也可能带随机化或校验标识 | 与进程、频率、时间分布交叉核对 |
| NXDOMAIN 比例 | 会受搜索域、缓存和配置变化影响 | 结合失败目标与变更记录查原因 |
| QTYPE 分布 | A/AAAA 占绝大多数 | TXT/NULL/CNAME 异常偏高 |
| 请求/响应大小比 | 接近对称 | 明显不对称（上行小、下行大） |

这些信号在**加密之后仍然成立**——DoH 藏住了名字，但藏不住「这条连接在持续发小包、收大包、目标固定」。所以 DoH 隧道的检测点从「DNS 内容」移到了「流形态 + 端点」，这属于 `base/48` 与 ◆`base/50` 的范畴。

## 45.9 语义层攻击：协议没错，用法错了

前面几节都在「报文层」。还有一类攻击完全不碰报文，只利用**解析结果的语义**——它们不需要伪造、不需要投毒、不需要加密，甚至在 DNSSEC 全量部署的世界里依然成立。

### DNS rebinding：服务端不能把可变的名称解析当授权

同源策略使用 `scheme + host + port`，不是 IP；解析结果则可以随时间变化。风险来自把“请求来自某个名字”或“地址是本地的”当成授权。TTL 为零不保证浏览器立即重查，多地址记录也不保证客户端按响应顺序连接。防御回归测试可直接向地址分类函数提供私网、环回和链路本地地址的离线数据，并检查重定向或重连是否重新做策略验证；不需要运行重新绑定服务或访问任何内网资源。

防御不能只在 DNS 一侧：浏览器要有 DNS pinning（独立于 TTL 的短时固定，量级一分钟）与 Private Network Access 预检；内网服务要校验 `Host`/`Origin` 并强制认证头（跨源页面没有预检就加不了自定义头）；解析器可以拒绝把公网名字解析到私有地址段。**「把服务绑在 127.0.0.1」不是防御**——rebinding 打的就是回环。

### 子域接管：悬空的 CNAME

`www.example.com CNAME example.saas-vendor.com`，SaaS 租约到期被释放，CNAME 还在。攻击者在同一家 SaaS 注册 `example`，就继承了 `www.example.com` 的全部流量，还能用 HTTP-01 拿到它的合法证书（挑战确实落在了他控制的主机上）。本机抓一个健康链作为形状参照：

```
www.github.com. 3600 IN CNAME github.com.
```

检测很机械：把全部 CNAME 的目标逐个查一遍，目标 NXDOMAIN 或指向厂商「未认领」页面就是悬空。这是资产清单问题，不是协议问题。

### 通配符、NXDOMAIN 缓存与 `search` 域

- **NXDOMAIN 截断（RFC 8020）**：父名不存在则其下全部不存在。这条优化让一个 NXDOMAIN 压掉整棵子树，但也意味着**一个错误的 NXDOMAIN 会黑掉一整个新上线的子域**，直到负缓存 TTL（SOA 的 MINIMUM）过期——本机看到的 SOA TTL 是 300 秒，故障窗口就是 5 分钟。
- **通配符 + DNSSEC**：`*.example.com` 的肯定回答要签「通配符展开」，否定回答要证明「连通配符都不匹配」，两种证明形状不同，配错就是「有的名字能查、有的不能」。
- **`search` 劫持**：`search corp.example.com` + `ndots:5` 会把 `printer` 先拼成 `printer.corp.example.com`；若这个域不属于你（写错、过期、被收购），单标签查询就泄漏到公共根，谁注册谁回答。本机没有 `search` 行（§45.11 ③），这正说明「配置干净」本身就是一种防御。

## 45.10 本地层：在报文之前，还有四个更低的入口

一台机器上的「DNS」不只有 53 端口。按 glibc 的查找顺序（本机 `/etc/nsswitch.conf` 实测 `hosts: files dns`），`files` 在 `dns` 之前——**`/etc/hosts` 永远赢**。这就是第一个入口。

| 入口 | 本机实测 | 攻击形态 | 防御 |
| --- | --- | --- | --- |
| `/etc/hosts` | 有 `127.0.1.1 LegendVPS-...` 与 `127.0.0.1 localhost` | 恶意软件写一行，永久覆盖某个域名 | 文件完整性监控、异常条目告警 |
| `/etc/resolv.conf` | 注释说 `127.0.0.53` 是 stub，实际 `nameserver 1.1.1.1` | 改成攻击者的解析器；或删掉 `search` 让内网名泄漏 | 由 NetworkManager/resolved 托管、`chattr +i`（代价是 DHCP 失效） |
| LLMNR / NBNS（5355 / 137） | 本机 `ss` 无 5353/5355 监听 | 广播「我是 `\\fileserver`」，收 NTLM 哈希 | 组策略关闭 LLMNR、禁用 NBT-NS |
| mDNS（5353） | 同上，无监听 | 冒充 `printer.local`、`nas.local` | 只在需要的链路开启、按 VLAN 隔离 |

这张表里最值得警惕的是**注释与实际不一致**：文件开头写着「由 resolvconf 生成、127.0.0.53 是 systemd-resolved stub」，但真正生效的 `nameserver` 是 `1.1.1.1`。**libc 只看最后生效的那一行，不看注释，也不看 `resolvectl` 以为的配置**——排障时先 `cat`，再信工具。

广播解析（LLMNR/NBNS/mDNS）的本质是「谁先回答谁赢」，和 §45.3 的伪造响应同一个形状，只是战场从公网换到了同一个广播域。**它是内网投毒最便宜的入口：不需要认证，也不需要猜 ID，广播域里所有人都能听见问题。** DHCP 下发的 DNS 也一样——恶意 DHCP 只要把 option 6 指向自己，后面所有解析都归它。

## 45.11 实测：五组在本机跑出来的输出

以下全部在本环境执行（Debian 12、dig 9.18.49、Python 3.11），递归为 `1.1.1.1`。

### ① DNSSEC：签名与 `ad` 位

```
$ dig +dnssec cloudflare.com A
;; flags: qr rd ra ad; QUERY: 1, ANSWER: 3, AUTHORITY: 0, ADDITIONAL: 1
cloudflare.com. 211 IN A     104.16.132.229
cloudflare.com. 211 IN RRSIG A 13 2 300 20261120141350 20261118121350 34505 cloudflare.com. pYB3Dc...
;; MSG SIZE  rcvd: 185

$ dig +dnssec isc.org A
isc.org. 300 IN RRSIG A 13 2 300 20261130060025 20261116055922 27566 isc.org. SFZrZq...
;; MSG SIZE  rcvd: 203
```

`ad` 位是递归替你做完了验证的结论，不是权威的签名。把同一个查询发给一台不校验的解析器，`ad` 就不会出现；而对 `dnssec-failed.org` 这样的断链域，校验中的递归直接回 SERVFAIL（§45.7 有 `+cd` 对照）。

### ② 应答匹配：离线防御断言

见 §45.3 的预期判定表。不要用这张表代替真实解析器的回归结果。

### ③ 本机的解析配置

```
$ cat /etc/resolv.conf
# Dynamic resolv.conf(5) file for glibc resolver(3) generated by resolvconf(8)
# 127.0.0.53 is the systemd-resolved stub resolver.
nameserver 1.1.1.1

$ cat /etc/nsswitch.conf | grep ^hosts
hosts:          files dns

$ cat /etc/hosts | grep -v '^#'
127.0.1.1 LegendVPS-20260712140708acd8 LegendVPS-20260712140708acd8
127.0.0.1 localhost
```

三行合起来回答「这台机器怎么解析」：先查 hosts（有一条 cloud-init 写的主机名），再问 `1.1.1.1`，没有 `search` 域，没有 `options ndots`。

### ④ 本机是否走 DoH

```
$ dig example.com A | grep SERVER
;; SERVER: 1.1.1.1#53(1.1.1.1) (UDP)
$ command -v resolvectl || echo "resolvectl: not installed"
resolvectl: not installed
$ nc -zv -w3 1.1.1.1 853
Connection to 1.1.1.1 853 port [tcp/domain-s] succeeded!
```

判读：`#53 (UDP)` 只说明这次 `dig` 使用明文 UDP；不代表浏览器或其他应用使用同一解析路径。`resolvectl` 不存在不能排除其他 DoH 代理；TCP 853 可连也不证明已成功完成 TLS 或正在使用 DoT。要确认某个应用的解析方式，核对应用配置、所选解析器与授权日志，不能仅看端口。

### ⑤ 地址随时间变化：防御检查

见 §45.9。把正常 DNS 变化视为输入条件，验证应用层授权与地址策略是否独立生效。

## 45.12 防御清单：四栏，按「谁出钱」分

| 权威侧（zone 主人 / DNS 托管商） | 递归侧（解析器运维） | 客户端侧（终端 / 浏览器） | 企业出口（网络与安全团队） |
| --- | --- | --- | --- |
| 关掉开放递归之外的 ANY，按 RFC 8482 回最小响应（代价：老诊断工具失效） | 每查询随机源端口 + 密码学随机 ID（代价：几乎为零，必须做） | 启用 DNSSEC 校验（代价：断链站点直接不可用） | 只允许出网 53 到内网解析器，其余丢弃（代价：漫游/访客要例外） |
| 上 RRL，按 zone + /24 限速（代价：误伤 NAT 后的大客户与重试） | 校验响应的问题名/类型/来源地址（代价：几行代码） | 开 DoT/DoH 到**受信任**解析器（代价：内网名可能失效） | 封 853 与已知 DoH IP；用 canary 域名关浏览器自动升级（代价：名单要维护） |
| 开 DNSSEC，做 KSK 轮换演练（代价：断链即全站不可用） | 限制 EDNS 缓冲到 1232，必要时 TCP 回退（代价：大响应延迟上升） | 开 DNS pinning / PNA（代价：少数应用被误伤） | 保留内网 DoH 并全量记日志（代价：容量与隐私合规） |
| 给 TTL 设下限（≥30 s），别用 0（代价：动态 DNS 生效变慢） | 开 serve-stale 与负缓存，防上游抖动（代价：可能返回旧数据） | 不用 `search` 域，或只用自己拥有的域（代价：短名输入不便） | 出口做 DNS 隧道检测：唯一子域数、标签长度、NXDOMAIN 比例（代价：误报调参） |
| 审计全部 CNAME 目标，清理悬空记录（代价：需要资产清单） | 拒绝把公网名字解析到私网地址段（代价：少数 split-horizon 场景要白名单） | 服务端校验 `Host`/`Origin`，别把内网服务暴露给任意浏览器源（代价：改造老应用） | DHCP snooping + RA guard + 关 LLMNR/NBNS（代价：旧设备兼容） |

优先级只有一条判据：**先做「便宜且不可绕过」的**——递归侧的端口/ID 随机化与响应校验、权威侧的关开放递归与拒绝 ANY、出口的 53 收敛。DNSSEC 与 DoH 都是有真实代价的工程，不是勾选项。

## 45.13 三列账：每种补法承诺了什么、收了多少钱、从哪失效

| 补法 | 承诺了什么 | 为此付了什么 | 从哪里开始失效 |
| --- | --- | --- | --- |
| 端口/ID/0x20 随机化 | 把伪造命中率从 2⁻¹⁶ 压到 2⁻³² 或更低 | 每查询一次端口分配；双方多做一次比较 | NAT 复用把端口熵压到个位数；中间盒重写 ID；on-path 攻击者直接照抄 |
| DNS Cookie | 证明「这条路径来回通」，挡住源地址伪造 | 服务端状态与密钥；客户端要重试一次 | 只保护路径，不保护数据；服务端不支持就退回裸 UDP |
| DNSSEC | 答案的完整性与「属于哪个 zone」可验证 | 密钥运维、断链即不可用、响应变大 2–7 倍 | zone 主人自己被攻破时签名照样为假数据背书；stub 不验就白签；时钟错就全挂 |
| DoT/DoH/DoQ | 路径上读不到、改不了 | 解析权交给第三方；企业失去 DNS 可见性；内网名失效 | 解析器说谎时你更看不见；SNI/流形态仍然泄漏；隧道可以把合规协议用成信道 |
| RRL + BCP38 + 最小响应 | 抬高反射放大的成本，砍掉 60 倍杠杆 | ISP 协作、误伤重试、老工具失效 | 未部署 BCP38 的网络仍然是弹药库；攻击者可换协议/端口 |
| TTL 下限 + 私网地址过滤 | 压缩 rebinding 的时间窗与可达目标 | 动态 DNS 生效变慢；split-horizon 要白名单 | 浏览器缓存策略、PNA 实现不一致；非 HTTP 协议不受 SOP 约束 |

**本篇的三缺表（纪律要求的那一行）**：DNS 缺**认证**（任何 UDP 包都能自称答案）、缺**完整性**（RRset 无签名）、缺**机密性**（53 端口明文）；随机化只压认证的攻击成本，DNSSEC 只补完整性，DoT/DoH 只补机密性——**三样都补上也不等于端到端可信，因为信任锚、解析器与 zone 主人仍是三个可被攻破的点**。这张表的通用版本（ARP、TCP、IP、HTTP 怎么缺、怎么补）在 `base/48`。

## 45.14 踩坑清单：现象 → 根因 → 定位 → 修

| 现象 | 根因（指回本篇） | 定位 | 修 |
| --- | --- | --- | --- |
| 只有部分用户被导到陌生站点，证书却是合法的 | 权威/注册商侧被改，DNS 层先失守（§45.1） | 多地点 `dig +trace` 对比；查 CT 日志有无异常签发；查 DNS 面板登录审计 | 改回记录、吊销证书、开 MFA；给关键域上 DNSSEC + CAA + 注册锁 |
| 内部域名突然解析不了，公网正常 | 浏览器自动 DoH 绕过内网解析器（§45.8） | `dig` 与浏览器分别查同一名字；看 `SERVER` 字段与 443 长连接 | 下发内网 DoH、canary 域名、出口封公共 DoH；或改 split-horizon 策略 |
| 某站点全公司打不开，`+cd` 就正常 | DNSSEC 断链：RRSIG 过期/DS 不匹配/时钟错（§45.7） | `dig +dnssec` 看 `ad` 与 `SERVFAIL`；逐级 `dig DS`；核对系统时间 | 修签名/DS/时钟；临时 `+cd` 只用于定位，不能当修复 |
| 权威服务器 QPS 暴涨，TTL 却是 0 | TTL 0 让每次访问都回源；再叠加递归重试（§45.9） | 看权威日志的 QPS 与 TTL 分布；对照客户端数 | 权威侧设 TTL 下限（30–300 s）；递归侧开缓存与 serve-stale |
| 解析结果在两个 IP 间跳，内网服务被陌生源访问 | rebinding：TTL 0 + 多 A（§45.9） | 看该名字的 TTL 与 A 记录数；看服务端 `Host`/`Origin` 日志 | 解析器拒绝私网答案；服务端校验 Host/Origin + 认证头；浏览器开 PNA |
| 单标签主机名解析到公网 | `search` 域不属于自己 / ndots 配置（§45.9） | `cat /etc/resolv.conf`；`dig printer` 看是否带后缀 | 去掉不属于自己的 `search`；应用一律用 FQDN |
| 同一台机器 `dig` 正常、应用却走别的解析器 | `nsswitch` 的 `files` 先于 `dns`，或应用自带解析库（§45.10） | `cat /etc/nsswitch.conf`、`/etc/hosts`；`strace -e connect` 看目标 | 统一解析入口；把 hosts 纳入配置管理 |

这七行的共同形状是：**「DNS 出问题」几乎从不是 DNS 服务器坏了，而是「某一层替 DNS 做了决定」**——浏览器替它选了 DoH、hosts 替它答了、search 域替它补了后缀、TTL 0 替它取消了缓存。

## 45.15 一页速记

```
【一句话】DNS 缺认证、缺完整性、缺机密；所有攻击都是这三缺的某种补法没补上。

【三缺 → 攻击 → 补法 → 新坑】
  认证  → 伪造响应 / 缓存投毒 / Kaminsky  → 端口+ID+0x20 随机化 → 只抬成本，NAT 吃熵
  认证  → 反射放大（伪造源 IP）           → BCP38 / RRL / 最小响应 → 误伤 + 要 ISP 配合
  完整  → 中间人改写 / 上游被篡改          → DNSSEC（RRSIG+DS+信任锚）→ 断链即全挂，响应 2–7×
  机密  → 监听 / 审查 / 隧道外带            → DoT / DoH / DoQ → 不认证来源，企业失去可见性
  语义  → rebinding / 子域接管 / search    → TTL 下限 / 私网过滤 / 审计 → 与 CDN 冲突

【四条核对】
  字段位数不等于出口实际随机性。
  EDNS 通告的接收上限不等于实际响应大小。
  检查 DNSSEC 时要确认在哪里验证、哪个信任锚和哪条委派链。
  加密解析与应用授权各管一段，不能相互替代。

【三句判据】
  1. 随机化不是认证，是把「几秒」变成「几个月」。
  2. DNSSEC 签的是 zone 主人的话，不是「你连的递归没骗你」。
  3. DoH 加密的是路径，解析权交给了谁才是真问题。
```

## 45.16 自检 3 题

**Q1.** 一台递归解析器声称已随机化事务 ID 和源端口。安全评审还应核对哪些边界？

<details><summary>答案</summary>

核对 DNS 实现版本、对端与问题匹配、缓存收录范围、实际 NAT 映射策略以及 DNSSEC 验证点。随机化不是身份验证；少量样本不重复也不证明不可预测。

</details>

**Q2.** 有人提议「上了 DNSSEC 就不需要端口随机化了，反正签名能验伪」。这句话哪对、哪错？请从「攻击者能做什么」和「验证发生在哪里」两个角度回答。

<details><summary>答案</summary>

**对的一半**：如果验证真的发生，伪造的 RRset 过不了 RRSIG 校验，投毒确实失效——签名覆盖了数据本身，这比猜 ID 强得多。

**错的一半**有两个：

1. **验证不一定发生**。验证点在递归或 stub，`ad` 位只是递归的判断；客户端若信任一台不验证的递归，签名就是没人看的附件。本机 `dnssec-failed.org` 的 `+cd` 对照就是证据：关掉校验，同一个名字立刻正常返回。
2. **DNSSEC 不保护「谁在回答你」**。它签的是「zone 主人说是这个值」，防不了被控的递归重放旧数据、也防不了 zone 主人自己作恶（§45.1）。而随机化保护的正是「查询—响应」这条路径。在本机抽样里 71.4% 的域没有 DS，在验证链断掉或 `+cd` 被打开时，端口随机化仍是唯一防线。

所以正确说法是：**DNSSEC 让投毒「即使命中也无效」，随机化让投毒「难以命中」；两者不是替代，是乘法。**

</details>

**Q3.** 一家公司为了「防窃听」把全员 DNS 切到公共 DoH，两周后安全团队发现三件事：内网 Wiki 打不开、DNS 隧道告警归零、某员工的机器在向一个陌生域名持续发查询却查不到内容。分别解释原因，并给出各自的第一处置。

<details><summary>答案</summary>

1. **内网 Wiki 打不开**：split-horizon 的 `wiki.corp.example` 在公网不存在，公共解析器回 NXDOMAIN，浏览器还可能把它缓存下来。处置：把 DHCP/DHCPv6 的解析器指回内网 DoH（仍加密，但有日志），或用 canary 域名阻止自动升级。
2. **DNS 隧道告警归零**：检测原本依赖查询日志（唯一子域数、标签长度、NXDOMAIN 比例、TXT 占比），DoH 把这些封进 443，网络侧只剩一条长连接。处置：恢复内网解析并全量记日志，同时在出口补流形态检测。
3. **陌生域名持续查询但看不到内容**：查询仍在发生、名字被加密，这是 DoH 隧道或 C2 的典型外观。处置：先从 EDR 的 DNS 事件与 `ss -tnp` 的对端定位进程，再看对端是不是已知 DoH 解析器。**不要**指望在网络上解开 TLS 来「看清域名」，成本高且滞后。

三件事的共同结论：**加密把「可见性」从一个免费副产品变成了要单独设计的系统**；DoH 本身没错，错在「切过去」和「补上检测」没有同时做。

</details>
