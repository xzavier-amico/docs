## 18.1 引子：三个真实的决策错误，三种不同的死法

这三个案例都来自「知道 GPU 核多，于是把核多当成万能」这同一个念头。它们的失败方式完全不同，但根因落在同一条判据的三个不同的门上。

### 错误①：把 OLTP 数据库放进 GPU

某行情系统把「按主键查最新报价」的存储层换成 GPU 显存驻留的哈希/跳表实现，理由是「一张表全放显存，查得快」。上线后单次点查延迟从 8 μs 涨到 90 μs，P99 从 30 μs 涨到 1.4 ms。

**根因**：单次点查是一次**串行依赖链**——算 hash、取桶、比 key、可能再跳一层。链上的每一步都要等上一步的地址，这不叫「一万份独立数据」，这叫「一份数据走十步」。GPU 的 16384 条 lane 在这条链上一条都用不上，用上的只有 1 条；而每一次「发起查询」都要付一次 kernel launch（5–20 μs），比查询本身贵一个数量级。

### 错误②：把分支密集的规则引擎放进 GPU

某风控系统把「200 条规则、按特征逐条判定」的逻辑写成 GPU kernel，期望靠并行度把 QPS 拉起来。实测同一批请求，GPU 版比 CPU 单线程版**慢 30 倍**。

**根因**：一个 warp 的 32 条 lane 共享同一个程序计数器。当 32 个样本各自命中不同规则、路径长度从 1 步到 120 步不等时，硬件只能把不同路径**依次**执行，每条 lane 在自己不走的那些路径上空转。§18.2 会推出这个上限：32 条 lane 走出 32 条不同路径时，利用率就是 **1/32 = 3.1%**——「慢 30 倍」不是玄学，是这条上限的直接读数。

### 错误③：把图像卷积留在 CPU

某团队的离线推理服务只有 CPU 机器，跑一个 3×3 卷积的检测网络，单帧 480 ms，被要求「优化到实时」。他们尝试了多线程、手写 AVX2 内积、换分配器，最好做到 190 ms。

**根因**：这一层卷积每帧约 `1920×1080 × 3×3×128 × 2 ≈ 4.8 GFLOP`，而 2 核 AVX2 的峰值只有 `16 flop/cycle × 2.6 GHz × 2 ≈ 83 GFLOPS`——纯算力上限就是 58 ms，再乘上实际效率，190 ms 已经是好成绩。同一份计算在 RTX 4090 上是 `4.8 GFLOP / 82.6 TFLOPS ≈ 58 μs` 的算力上限。**差 1000 倍不是代码问题，是「每瓦能同时开工多少条独立乘加」的物理问题。**

三个案例的判决在这张表里：

| 案例 | 它缺的是哪一条 | 具体数字 | 结论 |
| --- | --- | --- | --- |
| ① OLTP 点查 | 门① 并行度 | 并行度 = 1，单次链路 10 步 × 80 ns ≈ 1 μs，却要付 5–20 μs 启动 | 留在 CPU，且要减少依赖链 |
| ② 规则引擎 | 门③ 控制流同构 | 32 lane 走出 20–32 条不同路径 → 利用率 3%–5% | 留在 CPU，用分支预测换并行 |
| ③ 图像卷积 | 门② 算力密度 | AI ≈ 8–30 flop/B，远高于 CPU 平衡点 4.2 | 去 GPU，且必须做 tiling |

注意①和③的区别：同样是「一次操作」，①的每一步都依赖上一步，③的每个像素互不相干。这就是全篇唯一的判据。

## 18.2 判据的推导：一条判据，三个不等式

### 判据本体

> **同一段代码，是否作用于成千上万份互相独立的数据？**

「同一段代码」对应 GPU 的物理形态：一个取指单元、一套控制逻辑、32/64 条并排的通道（`base/16`）。「互相独立」对应没有 lane 间通信、没有分支分叉。「成千上万份」对应并行度足够摊薄固定开销。三个条件不是三条经验，是三个可以算的不等式。

### 不等式①：总工作量必须压过启动开销

设单份数据的处理时间是 `t`，份数是 `N`，目标并行度是 `p`，每次「把活派下去」的固定开销是 `L`。串行时间 `T₁ = N·t`，并行时间：

```
T_p = L + N·t/p
```

加速比 `S = T₁/T_p = N·t / (L + N·t/p)`。要 `S > 1`（也就是「上 GPU 不吃亏」），只需 `N·t > L·p/(p-1) ≈ L`；要拿到**一半**的峰值加速（`S = p/2`），需要 `N·t = p·L`。**后一个门槛看着吓人（`p·L` 到几十毫秒），因为模型假设 `p` 条 lane 一次性就位；真实 GPU 是 block 逐步填满 SM、启动与计算重叠，所以工程上只用下面那个交点解法。**

具体到 GPU：`L = 5–20 μs`（kernel launch + 驱动 + 队列），`p = 1.6×10⁴` 条 lane。取 `L = 5 μs`、`t` 由 CPU 侧的单价决定，直接解「GPU 时间 = CPU 时间」这个交点更实用。以 `y[i] = a·x[i] + y[i]` 为例（每元素搬 8 字节，CPU 双核带宽按实测 20 GB/s 计）：

```
CPU:  T = 8N / 20×10⁹                      = 0.4 ns × N
GPU:  T = 8N / 1008×10⁹ + 5×10⁻⁶           = 0.008 ns × N + 5 μs
交点: N* = 5×10⁻⁶ / (0.4 - 0.008)×10⁻⁹     ≈ 1.28×10⁴
```

`L = 20 μs` 时 `N*` 变成 `5.1×10⁴`。这就是「**10³–10⁴ 份**」这个数字的出生证明：它不是一个经验阈值，它是「启动开销 ÷ 单份处理时间」再乘上两台机器的带宽比。**N 小于这个数，GPU 一定更慢，而且不是慢一点——是慢在固定开销上，加多少核都救不回来。**

### 不等式②：每字节的计算量必须高过机器平衡点

定义算术强度 `AI = 浮点运算次数 / 搬运字节数`（flop/B）。一台机器的**平衡点**是它的峰值算力除以峰值带宽：

| 机器 | 峰值算力（FP32） | 带宽 | 平衡点 | 出处 |
| --- | --- | --- | --- | --- |
| 本机 2 核 AVX2 | 83 GFLOPS（推算） | 20 GB/s（实测） | **4.2 flop/B** | 本文 §18.9 |
| A100 80GB | 19.5 TFLOPS | 2039 GB/s | **9.6 flop/B** | 公开规格 |
| H100 SXM5 | 66.9 TFLOPS | 3350 GB/s | **20 flop/B** | 公开规格 |
| RTX 4090 | 82.6 TFLOPS | 1008 GB/s | **82 flop/B** | 公开规格 |

于是一个 kernel 的实测时间服从 roofline（`base/17`）：

```
T = max( FLOP / 峰值算力 , Byte / 带宽 )   ⟺   T = Byte / min(带宽, 峰值算力/AI)
```

`AI < 平衡点` 时，两条曲线中带宽那条在上，机器是**带宽受限**的——此时 GPU 的 TFLOPS 全是装饰，加核等于加更多排队等内存的人。`AI > 平衡点` 时才是算力受限，堆核才有意义。

**注意这张表最反直觉的一格：RTX 4090 的平衡点是 82，比 A100 的 9.6 高 8 倍多。** 因为它把算力堆到了 82.6 TFLOPS 却没把带宽同步堆上去。这意味着**同一份 kernel 在 A100 上是算力受限、搬到 4090 上可能变成带宽受限**——「换个更快的卡」不一定更快，要先看 AI 落在哪一侧。

### 不等式③：一个 warp 的 32 条 lane 必须走同一条路

SIMT 的物理事实：32 条 lane 共用一个 PC。如果这 32 条 lane 在某个分支处分叉成 `k` 组、各组路径长度是 `l₁…l_k`，硬件必须把 `k` 条路径**依次**执行，总步数是 `Σlᵢ`，而真正有用的步数是 `Σ(nᵢ·lᵢ)`（`nᵢ` 是第 i 组的 lane 数）。利用率：

```
U = Σ(nᵢ·lᵢ) / (32 · Σlᵢ)   ≤   1/32   （最坏：32 条 lane 走 32 条不同路径）
```

极限情况就是 3.1%——**32 倍**。§18.1 的「慢 30 倍」正是这条公式的读数。补一句常被忽略的推论：`k = 2`、两组各 16 条 lane 时 `U = 50%`，只损失一半；**发散之所以致命，不是因为「有分支」，而是因为「路径数接近 lane 数」**。这解释了为什么「if 里有分支」的 shader 依然跑得飞快，而「每个元素查一张不同的表」立刻崩。

### 三维判据图

三条不等式就是三道门，顺序执行，任何一道过不去，后面的计算都不必做：

```
  判据：同一段代码，是否作用于成千上万份互不依赖的数据？
   │
   ├─ 门① 并行度    N·t > L ？  ── 否 ──► 留 CPU（慢在 5–20 μs 启动费上，加核无效）
   ├─ 门② 算术强度  AI > 平衡点 ？  ── 否 ──► 带宽墙（先 tiling / 融合 / 量化；换卡没用）
   ├─ 门③ 同构性    一个 warp 的 32 lane 走同一条路 ？  ── 否 ──► 发散（利用率 ≤ 1/路径数）
   │
   └─ 三道全过 ──► 去 GPU
                   加速比上限 = min( p , AI ÷ 平衡点 , 32 ÷ 路径数 )
```

同一张判据还可以画成一张「落点图」——纵轴是算术强度，横轴是独立份数，三条横线是三种机器的平衡点，落在某条线以下的负载，在那台机器上加多少条 lane 都是白加：

```
      AI (flop/B，对数轴)
       ^
 10^3  |                            * 分块 GEMM + 张量核
       |                 * prefill（1000 token）
 10^2  | ====================================  RTX 4090 平衡点 82
       |                            * decode（B=164）
  10   |      * 3x3 卷积（AI≈12）        * attention（长上下文）
       | ====================================  A100 平衡点 9.6
   4   | ...................................  CPU 2 核平衡点 4.2
   1   | * decode（B=1）
       | * B+ 树点查（AI≈0.01）
 0.01  |
       +----------+----------+----------+----------+----> N（独立份数）
       10^3       10^4       10^6       10^9
                      ^
                门① 的交点带 1.3x10^4
```

最后那个 `min` 值得单独看：**加速比的天花板由三道门里最窄的那道决定**，不是由「多少核」决定。买一张核数翻倍的卡，只抬高第一个上限；后两个不变，加速比一分不涨。这是「换卡不提速」的完整解释。

## 18.3 结构性对比：一张表看完两种机器的取舍

所有数字给量级，不给「大概」。CPU 列以本机 2 vCPU（EPYC 7K62，AVX2）+ 通用服务器核为参照；GPU 列以 RTX 4090 / A100 这一档为参照。

| 维度 | CPU | GPU | 这个差异是从哪条物理约束推出来的 |
| --- | --- | --- | --- |
| 执行单元数 | 2–96 个核，每核 4–6 宽乱序 | 128 SM × 128 lane ≈ 1.6×10⁴ 条 FP32 通道 | 控制逻辑（取指/重命名/乱序窗口）只做一份 vs 做 128 份 |
| 单通道性能 | 每 cycle 4–6 条指令，IPC 2–4 | 每 lane 每 cycle 至多 1 条指令，顺序执行 | 单线程性能靠 ILP 挖，ILP 靠昂贵的乱序窗口 |
| 频率 | 2.0–5.5 GHz | 1.0–2.5 GHz | `P ∝ f·V²`，散热封顶时提频最贵（`base/17`） |
| 私有缓存 | L1 32–48 KB/核 + L2 1–2 MB/核 | L1/shared 128–256 KB/SM，**无跨 SM 一致性** | 一致性协议的成本随核数平方级上升，GPU 选择不付 |
| 末级缓存 | L3 32–256 MB 全核共享 + 目录协议 | L2 40–72 MB，切片式，软件不感知 | 同上；GPU 用「不保证一致」换容量与带宽 |
| 内存容量 | 数十 GB – 数 TB（可插满） | 24 / 40 / 80 GB，焊死 | 显存要贴着脸放在 PCB 上换带宽，插槽换不来 3 TB/s |
| 内存带宽 | 20–100 GB/s（双路可到 400+） | 1008 GB/s – 3.35 TB/s | HBM 用 1024-bit 以上的宽接口堆出来的 |
| 单次访存延迟 | L3 约 40 cycle，DRAM 80–100 ns | DRAM 400–600 cycle，**靠 TLP 掩盖而非缩短** | 延迟由器件与距离决定，两边都改不了，只能改「谁来等」 |
| 线程切换成本 | 1–5 μs（内核栈 + 保存现场） | 0（warp 切换 = 换一个就绪表项） | 上下文保存在寄存器堆里，硬件每 cycle 都在做 |
| 并行度的来源 | 多核 + SMT（2–4×） | 每核 48–64 个 warp 的 TLP × 32 lane | 前者要软件显式分线程，后者由硬件自动填满 |
| 典型失败模式 | 分支预测错（15–20 cycle 清空）、缓存不命中、锁竞争 | warp 发散、bank conflict、显存不足、launch 开销 | 各自的「贵」落在不同的地方 |
| 编程模型 | 线程 + 隐式一致的共享内存 | 数千线程 + 显式层次 + 无跨 lane 通信 | 一致性不免费，所以 GPU 把它从合同里划掉 |

表里最该记住的是「线程切换成本 0」那行。它不是「GPU 更先进」，而是**它把上下文保存这件工作摊到了每一层硬件上**：每条 lane 的寄存器是物理独占的，切换 warp 只是改一个「下一个发射谁」的指针。CPU 做不到这一点，因为它的乱序窗口要跟踪每条在飞指令的依赖——那是单线程性能的来源，也是切换昂贵的来源。**两种机器在同一个预算（面积、功耗）下做了互斥的选择。**

## 18.4 为什么图形适合 GPU：同构、独立、海量，三件同时成立

### 一次 draw call 到底是什么

你在游戏里看到的一帧，在 GPU 眼里是这样一条流水线：

```
+----------------------------------+   整帧只有一次，成本可忽略
| CPU: 提交 draw call（每帧一次）  |
+----------------------------------+
   |
   v
+----------------------------------+   本帧 10^5–10^7 个顶点，每个独立
| 顶点着色器：每个顶点跑同一段代码 |
+----------------------------------+
   |
   v
+----------------------------------+   把几何切成一堆互不相干的方格
| 图元装配 + 光栅化（固定硬件）    |
+----------------------------------+
   |
   v
+----------------------------------+   1920x1080 = 2.07x10^6 个片元/帧
| 像素着色器：每个片元跑同一段代码 |
+----------------------------------+
   |
   v
+----------------------------------+   所有片元的最终合并，帧末一次
| 深度测试 / 混合（固定功能）      |
+----------------------------------+
```

关键在光栅化这一步：它把几何图形**切成一堆互不相干的方格**，每个方格带着自己的 `(u, v)`、自己的法线、自己的材质坐标。这不是「程序里有循环」，这是**问题本身就被物理过程切成了独立份**。

三个条件在这里同时成立，而且是免费的：

- **同构**：所有像素跑的是**同一个 shader 程序**，连分支都是同一份（`if (alpha < 0.5) discard;` 在绝大多数像素上走同一边）。
- **独立**：一个像素的输出不依赖任何其它像素的输入。深度测试要读别人的结果？那是固定功能硬件在帧末做的，不是 lane 之间在通信。
- **海量**：2.07×10⁶ 个片元/帧 × 60 帧 = 1.24×10⁸ 次着色/秒，比任何启动开销大六个数量级。

### 一个像素着色器的形状

```glsl
// 逐片元调用；每个片元拿到的 v_uv / v_normal / v_world 都不同，
// 但程序计数器是同一条 —— 这正是 SIMT 要的形状
vec4 shade(vec2 v_uv, vec3 v_normal, vec3 v_world) {
    vec3  n   = normalize(v_normal);
    vec3  l   = normalize(u_lightPos - v_world);
    float ndl = max(dot(n, l), 0.0);          // 无条件分支：max 而不是 if
    vec3  albedo = texture(u_albedo, v_uv).rgb;
    vec3  color  = albedo * ndl * u_lightColor;
    float fog    = clamp(length(u_eye - v_world) / u_fogFar, 0.0, 1.0);
    return vec4(mix(color, u_fogColor, fog), 1.0);
}
```

这段代码里没有一处「等别人」：`texture()` 的采样坐标 `v_uv` 是该片元自己的，采样结果也只喂给自己。GPU 因此可以让 64 个 warp 同时在飞——某个 warp 卡在 400 cycle 的纹理读取上时，发射器换下一个 warp 继续干活。

顺着这条线能算出一个必须知道的上限：**只靠 TLP 是掩不住延迟的**。400 cycle 的显存延迟，每 warp 每 cycle 能发 1 条指令，一个 SM 最多驻留 64 个 warp，那么理论发射率 = `64/400 = 16%`。也就是说，**纯「读一个值、算一下、再读下一个」的 shader 最多只能跑到 16% 的发射率**。真实图形代码之所以能跑满，是因为每个像素上有一大段不依赖内存的算术（光照、混合、雾化），让 16% 的发射率也够用。这条推论在 §18.7 会以另一种面貌出现：**decode 阶段每步只搬权重、几乎不算，就是那个 16% 的极端版**。

### 反过来说：图形为什么不放 CPU

2.07×10⁶ 个片元、每个 ~300 条指令，一帧就是 `6.2×10⁸` 条指令。CPU 的单核乱序窗口（ROB 约 200–500 条）在这里毫无用处——**没有依赖链可以挖 ILP，只有海量的独立工作**。用 CPU 做这件事，等于用几十台单线程极强的机器去打一场需要一万条流水线的仗。这就是 §18.1 错误③的形状，只不过那里是卷积，这里是着色，同一个根因。

## 18.5 为什么矩阵乘法适合 GPU：AI 可以被分块推上去

### 先算朴素 GEMM 有多蠢

`C = A·B`，三个 `n×n` 矩阵。浮点运算数是 `2n³`（每个输出元素 n 次乘加）。如果完全不做复用、每个乘加都从内存取两个操作数：

```
flops = 2n³
bytes = 2n³ × 4 B          （两次 load，每次 4 字节）
AI    = 2n³ / 8n³ = 0.25 flop/B
```

**0.25**。对照 §18.2 的表：CPU 平衡点 4.2，4090 平衡点 82。也就是说朴素 GEMM 在**任何**机器上都是带宽受限，而且是差 17 倍 / 328 倍的那种。这就是为什么「矩阵乘法天生适合 GPU」这句话单独说是错的——**朴素 GEMM 在 GPU 上一样慢，慢到 1008 GB/s × 0.25 = 252 GFLOPS，只有峰值的 0.3%**。

### 分块把 AI 从 0.25 推到 >10

把 `C` 切成 `T×T` 的块，每次把一个 `A` 的块行和一个 `B` 的块列读进缓存/共享内存，块内做全部乘加：

```c
/* T×T 分块：一次装载喂 T 次乘加，AI 从 0.25 抬到 T/4 */
for (int ii = 0; ii < n; ii += T)
  for (int jj = 0; jj < n; jj += T)
    for (int kk = 0; kk < n; kk += T) {
        /* 装载 A[ii..ii+T)[kk..kk+T] 与 B[kk..kk+T)[jj..jj+T] 到 L1/shared */
        for (int i = ii; i < ii + T; i++)
          for (int k = kk; k < kk + T; k++) {
              float a = A[i][k];                    /* 装载 1 次 */
              for (int j = jj; j < jj + T; j++)     /* 复用 T 次 */
                  C[i][j] += a * B[k][j];
          }
    }
```

算一下这个块的账：`T³` 次乘加 = `2T³` flops，装载 `2T²` 个元素 = `8T²` 字节：

```
AI = 2T³ / 8T² = T/4
```

| 分块 T | AI (flop/B) | CPU 2 核（平衡点 4.2） | RTX 4090（平衡点 82） |
| --- | --- | --- | --- |
| 不分块 | 0.25 | 带宽受限：20 GB/s × 0.25 = **5 GFLOPS** | 带宽受限：1008 × 0.25 = **252 GFLOPS** |
| 32 | 8 | 算力受限：**83 GFLOPS**（16× 提升） | 仍带宽受限：8064 GFLOPS |
| 64 | 16 | 算力受限：83 GFLOPS（封顶） | 仍带宽受限：16128 GFLOPS |
| 128 | 32 | 封顶 | 仍带宽受限：32256 GFLOPS |
| 256 | 64 | 封顶 | 仍带宽受限：64512 GFLOPS |

这张表的结论很实用：**同一个 64×64 分块，在 CPU 上已经越过了平衡点（16 > 4.2），在 4090 上还差 5 倍（16 < 82）。** 所以「把 CPU 上跑得不错的 GEMM 原样搬到 GPU」会得到一个带宽受限的 kernel——GPU 版的真实做法是 `128×128` 的共享内存块**再叠一层 8×8 寄存器块**，让一次装载喂 64 次 FMA，等效 AI 再乘 4。这就是 `base/20` 那条阶梯的第三、第四级：每一级都在做同一件事——**减少数据在层与层之间搬一次的次数**。

补一句边界：上面所有「GFLOPS」都是 FP32 CUDA core 的账。张量核（Tensor Core）不改变搬运量，只把每 cycle 的乘加数乘上 8–16 倍（fp16/bf16 的 MMA 一次算 4×4×4 或更大），于是**平衡点本身被抬到了 300 以上**——这解释了为什么大模型必须用 fp16/bf16：不是为了省显存，是为了把平衡点抬到「矩阵乘法真的算力受限」的位置。这条线 `base/20` 会量化，`base/17` 会从 `f·V²` 那一侧解释为什么张量核是「用面积换 flops」而不是「用频率换 flops」。

## 18.6 为什么数据库/事务不适合：四条全部违反

把一次「按主键查一行」摊开，它把三条不等式全部违反，还额外欠着一笔 PCIe 的账。

### ① 分支密集：B+ 树的每一层都不一样

一次 3 层 B+ 树查找是这样的：根节点二分（4–8 次比较、每次结果决定下一次读哪）→ 中间节点二分 → 叶节点线性扫描 + 比较。**每一层的比较次数、分支走向、内存地址都不一样**。放进一个 warp，32 条 lane 会在第一层就分叉成 8–16 条不同路径，利用率直接掉到 §18.2 的 `1/k`。

### ② 数据依赖：每一步都要等上一步的地址

`key → 节点 → 子节点指针 → 叶 → 行`，这条链上每一次访存都要等上一次的**值**。本机实测（16 MB 随机环，完全打乱顺序的指针追逐）：**135–227 ns/次**；在一张 2²⁴ 个键（64 MB）的有序表上做 24 层二分查找（等价于一棵 24 层索引树）：**2.73–2.95 μs/次**。这两个数字就是「一条串行依赖链」的实测单价——它不是带宽问题，是**延迟 × 链长**，而 GPU 对这个乘积毫无办法：一个 warp 里 32 条 lane 各自走 32 条不同的链，正好落进最坏情况。

### ③ 延迟敏感：一次查询的预算不够一次 kernel launch

| 操作 | 单价 | 出生证明 |
| --- | --- | --- |
| 一次 AVX2 FMA（8 lane） | **0.38 ns** | 1 cycle @ 2.6 GHz |
| 一次 L3 命中 | 约 15 ns | 40 cycle @ 2.6 GHz |
| 一次 DRAM 访存（TLB 命中） | 80–100 ns | 器件物理，`base/07`/`base/08` |
| 一次 24 层索引查找（64 MB 表） | **2.7 μs** | 本机实测，§18.9 |
| 一次 GPU kernel launch | **5–20 μs** | 公开量级，驱动 + 队列 + 网格下发 |
| 一次页缓存未命中的点查（本地 NVMe） | 100 μs – 1 ms | `base/08` |

倒数第二行是判决：**一次查询的全部时间预算是微秒级，而「把活派给 GPU」这个动作本身就要 5–20 μs。** 你还没开始查，预算已经花完了。而 2.7 μs 的查找时间里，CPU 能塞下 `2.7 μs / 0.38 ns ≈ 7,100` 条 AVX2 FMA（5.7 万个浮点操作）——**这就是 SIMD 与「跳着访存」的差价：一个是流水线上一格，一个是等一趟内存**。

### ④ 随机访存：索引跳转把预取器彻底废掉

CPU 的一半性能来自「猜你要读哪」：顺序访问时硬件预取器能把有效带宽翻倍，分支预测器能把 15–20 cycle 的清空概率压到 1% 以下。索引查找同时废掉这两样——下一次读哪完全取决于上一次读到了什么，预取器和预测器都只能瞎猜。这也是为什么 §18.9 里那条依赖链是 135–227 ns/次：折成带宽只有 `4 B / 185 ns ≈ 0.02 GB/s`，比顺序流水的 22.5 GB/s 差三个数量级——**不是内存变慢了，是「提前准备」这件免费的好处没了**。

把这四条与判据对照，结论就一行：

| 判据门 | OLTP 点查 | 判定 |
| --- | --- | --- |
| ① 并行度 | 并发连接 10²–10³，但每次查询是 1 条链 | 分母是链不是连接，门①不过 |
| ② 算术强度 | 每字节 0.01 flop 量级（取一行就为了比一个值） | 门②差 400 倍 |
| ③ 同构性 | 每层分支走向不同 | 门③不过 |
| 额外一条 | 要跨 PCIe 才能碰数据（`base/14`） | 单次 4 KB 拷贝的固定延迟 2–5 μs |

那 GPU 数据库为什么还有研究价值？因为它把「点查」换成了「全表扫描 + 聚合」——`SELECT sum(x) WHERE ...` 这类查询有 10⁸ 行独立数据、每行同样的判断、AI 也够。**同一台机器，换个查询形状就从「完全不适合」变成「非常适合」，这恰好证明判据是可用的，而不是「数据库不适合 GPU」这种含糊结论。**

## 18.7 为什么 LLM 推理「半适合」：prefill 是矩阵，decode 是自回归

这是全篇最有价值的一次代入：它解释了当前所有推理引擎的核心设计。

### 两段完全不同的负载

一次生成请求分成两段：

```
prompt: "把下面这段话翻译成英文：……"（1000 token）
   │
   ├── prefill：1000 个 token 一起过模型
   │     每个 token 独立、走同一段代码 → 本质是 GEMM
   │     矩阵形状：(1000 × d) × (d × d)
   │
   └── decode：一次只出 1 个 token，循环 500 次
         第 t 个 token 依赖第 t-1 个 token → 本质是 GEMV
         矩阵形状：(1 × d) × (d × d)     ← 注意左边是 1
```

### 用 AI 算一遍：decode 的 AI 只有 1，离平衡点差 82 倍

设模型参数量 `P`（每个参数 2 字节 fp16），批大小为 `B`（一次并行处理几个请求）。一次 forward 的浮点运算约 `2·B·P`（每个参数做一次乘加），要搬运的字节约 `2·P`（**全部权重必须过一遍**，因为每个权重都要参与这 B 个 token 的计算）：

```
AI = 2·B·P / (2·P) = B   flop/B（按 fp16 每参数 2 字节）
```

**AI 只跟批大小有关，跟模型多大完全无关。** 记下来：

| 阶段 | 批大小 B | AI (flop/B) | 4090 平衡点 82 | 判决 |
| --- | --- | --- | --- | --- |
| decode | 1 | 1 | 差 82 倍 | **带宽受限**：1008 GB/s × 1 = 1 TFLOPS，只有峰值的 1.2% |
| decode | 32 | 32 | 差 2.6 倍 | 仍带宽受限：32 TFLOPS |
| decode | 164 | 164 | 刚好越过 | 开始算力受限 |
| prefill | 1000 | 1000 | 高 12 倍 | **算力受限**，82.6 TFLOPS 全用上 |

以 A100（平衡点 9.6）为例，decode 只需 `B ≥ 10` 就能越过平衡点——**这就是为什么同样的模型在 A100 上 batch≈10 就越过平衡点，在 4090 上却要 batch=164：不是 4090 更差，是它的平衡点被算力堆高了 8 倍。**

### 于是 batching 和 KV cache 不是「优化技巧」，是物理必需

- **batching**：把 `B` 从 1 抬到 164，AI 就抬 164 倍。这不是「提高吞吐的常规手段」，这是**唯一能让 decode 从「等内存」变成「算数学」的手段**。
- **KV cache**：decode 第 t 步要重算前面所有 token 的 K/V 吗？不重算，就得把 `2·L·d·t` 个数存下来（L 层、d 维、t 个历史 token），每步重读一遍。**它把「重复计算」换成了「重复搬运」，而 decode 本来就是带宽受限**——所以 KV cache 的容量与带宽才是长上下文的真正瓶颈，而不是算力。
- **连续批处理（continuous batching）**：既然 B 越大越好，就要让不同请求的 token 尽量塞满同一个 batch，于是有了「谁的 KV 还在、谁的已经结束」的调度问题。

这三件事的完整工程形态（PagedAttention、显存分页、抢占与重算）在 [`comp/49`](../comp/49-inference-engine-vllm.md) 里，本篇只交付一句可推导的结论：**decode 的瓶颈是「每生成 1 个 token 要把全部权重读一遍」，所以它的上限是 `带宽 / 模型字节数`，而不是 `算力 / 模型 flops`。** 一个 7B fp16 模型（14 GB）在 1008 GB/s 上的理论上限是 `1008/14 ≈ 72 token/s`；要更快，只能减字节（量化）或加带宽，加减算力没有用。

## 18.8 混合架构：CPU 做控制，GPU 做数据

判据从来不是「选一个」，而是「把负载切开，各段送到它该去的地方」。一个推理服务的链路：

```
  ①  请求（HTTP / gRPC）                                                      ← 入口
      |
      v
  ②  [CPU] 解析 JSON / 鉴权 / 路由 / 组 batch            ~50–200 μs           ← 门①③ 不过：分支 + 串行
      |
      v
  ③  H2D：输入张量过 PCIe（4 KB）                        ~2–5 μs              ← 延迟主导，不是带宽主导
      |
      v
  ④  [GPU] prefill：B×L 个 token 的 GEMM                 AI ≈ 批内 token 数   ← 算力受限
      |
      v
  ⑤  [GPU] decode × k：k 步自回归（不回 CPU）            AI ≈ batch           ← 带宽受限
      |
      v
  ⑥  D2H：logits / token id（KB 级）                     ~2–5 μs              ← 同上
      |
      v
  ⑦  [CPU] detokenize / 拼 JSON / 写回                   ~10–50 μs            ← 只能 CPU

  ②+⑦ = 60–250 μs，③+⑥ = 4–10 μs —— CPU 段比 GPU 的两端边界开销贵一个数量级
```

三段延迟的量级对比值得盯一下：**CPU 段（50–200 μs + 10–50 μs）比 GPU 段（几十 μs 到几十 ms）里的固定部分还大**。所以「GPU 利用率不高」的常见根因不在 kernel 里，而在两端：JSON 解析、TLS 握手、Python GIL、日志同步写盘。这也解释了为什么推理服务的第一优化往往是「批处理 + 前置队列」而不是「换更快的卡」。

链路里还有两个容易算错的点：

- **PCIe 拷贝的固定延迟是 2–5 μs，不是 0.16 μs。** 4 KB / 25 GB/s = 0.16 μs 是纯带宽账，实际还有 DMA 建立、驱动提交、同步开销。**小张量过 PCIe 永远是延迟主导。**
- **不要让 GPU 的输出回到 CPU 再回 GPU。** 一个 `argmax` 之后 CPU 做了 50 μs 的后处理，再把结果送回 GPU 做下一步——这 50 μs 里 GPU 在空转，而它本来可以跑下一个 batch。正确形状是「一次 H2D、一次 kernel 链、一次 D2H」。

## 18.9 实测与估算：本机只有 2 个核，没有 GPU

**先说清楚实验边界：这台机器没有 GPU。** 下面第一部分是真实跑出来的 CPU 数据（`nproc = 2`，AMD EPYC 7K62 的 2 个 vCPU，AVX2+FMA，Debian 12 / gcc 12.2；`BogoMIPS 5190` → 推算实际频率约 2.6 GHz，后文所有 cycle 换算都按这个数）；第二部分是把公开规格代进 §18.2 的公式算出来的估算值。**两者不混在一张表里，估算值不会伪装成实测。**

### 实测①：宽度 8 倍的 SIMD，只快了 3.65 倍

同一段点积，一份写标量、一份写 AVX2（控制流不改，只是每条指令吃 8 个数），数组 32 MB（远超末级缓存）：

```c
/* 标量：每个 cycle 处理 1 个数 */
for (int i = 0; i < n; i += 4) {
    s0 += a[i] * b[i];     s1 += a[i+1] * b[i+1];
    s2 += a[i+2] * b[i+2]; s3 += a[i+3] * b[i+3];
}
/* AVX2：一条指令 8 个数，程序结构完全一样 */
__m256 x0 = _mm256_setzero_ps(), x1 = _mm256_setzero_ps();
for (int i = 0; i < n; i += 16) {
    x0 = _mm256_fmadd_ps(_mm256_loadu_ps(a+i),   _mm256_loadu_ps(b+i),   x0);
    x1 = _mm256_fmadd_ps(_mm256_loadu_ps(a+i+8), _mm256_loadu_ps(b+i+8), x1);
}
```

两次运行的输出（取 7 轮最小值）：

```
[32MB 大数组] dot 标量 10.886 ms  1.54 GFLOPS  6.2 GB/s
[32MB 大数组] dot AVX2  2.986 ms  5.62 GFLOPS  22.5 GB/s
[32MB 大数组] 宽度 8x，实测加速 3.65x
（第二次运行：12.026 ms / 2.942 ms / 加速 4.09x）
```

**宽度 8 倍，实测 3.65–4.09 倍。** 剩下的 2 倍去哪了？看第三列：AVX2 版的有效带宽是 22.5 GB/s，已经贴在这台机器双流读的上限上。这个 kernel 的 `AI = 2 flop / 8 B = 0.25`，远低于 CPU 平衡点 4.2——**它是带宽受限的，所以「指令变宽」只能把「等带宽」的比例放大到极限，不能把时间缩到 1/8。** 这就是 §18.2 不等式②在 CPU 上的一次预演；换成 GPU，同样的 0.25 会让比例更难看。

### 实测②：2 线程的扩展性曲线，左边是启动开销，右边是带宽墙

固定工作量 `n`，一份串行跑、一份切成两半交给两个线程（每次调用都新建线程——这正是「启动开销」的来源，与 GPU 的 kernel launch 同构）。内核是对每 8 个元素做 17 次 FMA（就地读写，每元素搬 8 字节）：

```
pthread 新建+回收 k=1: 10.85 us   k=2: 25.80 us   k=4: 52.29 us
```

| n（元素） | 1 线程 | 2 线程 | 2 线程/1 线程 | 提速 |
| --- | --- | --- | --- | --- |
| 1,000 | 1.46 μs | 59.1 μs | 40.5× | **0.02×** |
| 4,000 | 6.03 μs | 72.6 μs | 12.0× | **0.08×** |
| 16,000 | 24.9 μs | 122.4 μs | 4.92× | **0.20×** |
| 64,000 | 92.5 μs | 234.0 μs | 2.53× | **0.40×** |
| 256,000 | 360 μs | 636 μs | 1.77× | **0.57×** |
| 1,000,000 | 1.46 ms | 1.37 ms | 0.93× | 1.07× |
| 8,000,000 | 12.7 ms | 10.5 ms | 0.83× | **1.21×** |

这条曲线的三段落差，每一段都能对上一条不等式：

- **左边（n ≤ 4×10³）：慢 10–40 倍。** 一次 `pthread_create + join` 实测 10.9–25.8 μs，而 n=1000 时工作只有 1.46 μs。这不是「并行没写好」，是判据①：`T = L + N·t/p`，`L` 比 `N·t` 大一个数量级，分母全被 `L` 占了。**GPU 的 kernel launch 是 5–20 μs，同一个量级、同一个死法**，只是 GPU 一次能派 1.6 万条 lane，交点被推到 `10⁴` 而不是 `10⁶`。
- **右边（n ≥ 10⁶）：只到 1.21 倍。** 这个内核的元素搬运量是 8 B（读 4 + 写 4），`AI ≈ 4.25 flop / 8 B ≈ 0.53`，低于平衡点 4.2——**第二个核来了也只是多一个人一起等内存**。要看清「核数就是上限」这件事，得把内核换成纯寄存器版（工作集为 0，AI = ∞）：同一台机器上 2 线程跑 4 轮，最好一轮 **1.99×**，最差 **1.11×**。差距不是代码，是这台 2 vCPU 的共享虚拟机在被邻居抢 CPU。
- **所以「扩展性」这个词必须带两个下标**：`L`（启动开销）和 `AI`（算术强度）。**GPU 不是「扩展性更好的 CPU」，它是把 `p` 从 2 改成 1.6×10⁴、把 `L` 从 25 μs 压到 10 μs，而 `AI` 这一项一点没帮你改。** 这就是为什么「核多」的解释力只有三分之一。

「1.11–1.99× 的抖动」本身就是结论：**在这台机器上只引用量级，不引用小数位。** 下面所有估算都按这个纪律写。

### 估算③：同一个循环，假设搬到 GPU 上要多久

以下全部是**公式推算**（GPU 规格取自公开参数，CPU 侧取本机实测带宽 20 GB/s）：

| 负载 | 每元素搬运 | 每元素 flops | CPU 时间 | GPU（4090）时间 | 交点 N* |
| --- | --- | --- | --- | --- | --- |
| SAXPY `y=a·x+y` | 8 B | 2 | `0.4 ns × N` | `0.008 ns × N + 5 μs` | **1.28×10⁴** |
| 逐元素 ReLU+缩放 | 8 B | 2 | `0.4 ns × N` | `0.008 ns × N + 5 μs` | 1.28×10⁴ |
| 逐元素 sigmoid（查表） | 8 B | ~10 | `0.4 ns × N`（带宽受限） | `0.008 ns × N + 5 μs` | 1.28×10⁴ |
| 小卷积（100 flop/元素） | 8 B | 100 | `1.2 ns × N`（算力受限） | `7.9 ps × N + 5 μs`（仍带宽受限） | **4.2×10³** |
| GEMM 64×64 分块 | — | — | 83 GFLOPS 封顶 | `AI = 16` → 16.1 TFLOPS | 由矩阵规模决定 |

读法：**`N < N*` 时 GPU 更慢，且慢在 5 μs 的固定开销上，加核无效；`N > N*` 后 GPU 的领先幅度迅速饱和到两台机器的带宽比或算力比。** 第 4 行要单独看一眼：它每元素 100 flop，`AI = 12.5`，**在 4090 上仍是带宽受限**（12.5 < 82）——所以它的 GPU 单价是 `8 B / 1008 GB/s = 7.9 ps`，不是 `100 / 82.6 TFLOPS = 1.21 ps`。而它的交点反而更低（4.2×10³ 对 1.28×10⁴），原因在**分母的 CPU 那一侧**：算力密集负载让 CPU 每元素花 1.2 ns（比带宽型的 0.4 ns 贵 3 倍），`L/(t_cpu - t_gpu)` 的分母更大，交点就被压低了。**记住交点公式 `N* = L/(t_cpu - t_gpu)`：它同时由两台机器的单价决定，只盯 GPU 那一侧会算错方向。**

同理可以算出「为什么 1 GB 数据不要来回搬」：`1 GB / 25 GB/s（PCIe 4.0 x16 有效带宽）≈ 40 ms`，而 1 GB 数据在 4090 上做 `AI = 100` 的计算只要 `100 GFLOP / 82.6 TFLOPS ≈ 1.2 ms`。**拷贝比计算贵 33 倍。** 这就是「把数据留在显存里」这条工程纪律的全部依据，也是 `base/14` 那条「CPU 最贵的资源不是算力是搬数据的次数」在 GPU 侧的镜像。

## 18.10 三列账：GPU 承诺了什么、收了多少、从哪开始失效

| 维度 | 承诺了什么 | 为此付了什么 | 从哪里开始失效 |
| --- | --- | --- | --- |
| 并行度 | 1.6×10⁴ 条 lane，峰值算力是 CPU 的 10²–10³ 倍 | 只对「互相独立」的数据有效；控制逻辑只有一份 | `N·t < L`（约 10³–10⁴ 份）时，加速比为负 |
| 算力密度 | FP32 82.6 TFLOPS / FP16 张量核 10³ TFLOPS 量级 | 平衡点被抬到 82 flop/B，比 A100 高 8 倍 | `AI < 82` 时实测只有带宽乘以 AI，TFLOPS 是装饰 |
| 延迟掩盖 | warp 切换零成本，硬件自动填满流水线 | 必须驻留几十个 warp 才掩得住 400 cycle | 依赖链（索引查找、自回归 decode）让 32 条 lane 各走各的链 |
| 显存带宽 | 1–3.35 TB/s，是 DDR 的 10–30 倍 | 容量焊死（24–80 GB），且不能跨卡共享 | 模型 + KV cache 超过显存 → 换页或降 batch，带宽优势立刻归零 |
| 编程模型 | 一套代码跑一万条 lane，不用管调度 | 没有跨 lane 通信、没有隐式一致的缓存、没有异常与递归 | 需要 lane 间交换数据时，只能走 shared memory + 显式同步 |
| 成本口径 | 每 flop 的电费比 CPU 低一个数量级 | 空转时照样吃 300–700 W；启动开销按次计费 | 小 batch、小 kernel、断断续续的请求流 → 每有效 flop 的成本反超 CPU |

一句话收束：**GPU 买到的是「同一段代码同时作用于一万份数据」的能力，付出的是「问题必须能被切成一万份、每份走同一条路、且工作量大到摊薄 10 μs 启动开销」。** 三列账里最容易被忽略的是最后一行的「空转功耗」——它意味着 GPU 的账要按**利用率**算而不是按峰值算：一台跑 5% 利用率的 GPU，单位有效算力的成本会输给 CPU。

## 18.11 踩坑清单：现象 → 根因 → 定位 → 修

| 现象 | 根因（指回本篇） | 怎么定位 | 怎么修 | 怎么防复发 |
| --- | --- | --- | --- | --- |
| 小 batch 上 GPU 比 CPU 还慢 | `N·t < L`，被 5–20 μs 启动开销吃光（§18.2 门①） | 同一输入跑 `batch=1` 与 `batch=64`，算每 token 的耗时；对比 kernel 时间与端到端时间 | 攒 batch；或对小请求直接走 CPU 路径 | 容量规划时把「最小 batch」写进 SLO，而不是只写峰值 QPS |
| 每个小算子都慢 5 μs，链路一共 200 个算子 | kernel launch 是**按次**计费的 | Nsight/timeline 里数 kernel 数量；`nvidia-smi` 看利用率长期 < 20% | 算子融合（fusion）、CUDA Graph、把循环搬进 kernel 内 | 设计阶段就按「每毫秒允许几次 launch」预算 |
| 单卡算得飞快，端到端却没变快 | PCIe 拷贝 40 ms/GB，比计算贵 33 倍（§18.9 估算③） | 对比 kernel 时间与 `H2D/D2H` 时间；看是否每步都在搬 | 数据常驻显存；用 pinned memory + 异步拷贝 + 双缓冲 | 把「每请求的 PCIe 字节数」当一级指标 |
| 显存不足，框架自动降级后变慢 10 倍 | 显存焊死，超了就换页/重算/降 batch（§18.10 第 4 行） | 看 `nvidia-smi` 显存曲线与 batch 是否被动态调小；看是否有大量 `cudaMalloc` 失败重试 | 量化权重、PagedAttention 式的 KV 分页、限制上下文长度 | 上线前用「最大上下文 × 最大并发」算一遍显存账 |
| 搬到大卡上反而更慢 | 平衡点被算力堆高了：A100 是 9.6，4090 是 82（§18.2 表） | 算 kernel 的 AI，与两张卡的平衡点比 | 提高 AI（分块、融合、提高复用），而不是换卡 | 选型表里除了 TFLOPS 与显存，必须写「平衡点」 |
| 分支多的 kernel 利用率只有个位数 | 32 lane 走出 32 条路径，利用率 1/32（§18.2 门③） | 用 warp 效率指标（achieved occupancy + branch efficiency）看发散 | 把分支改成「无分支选择」（`select`/查表/predication）；或把不同路径拆成不同 kernel | code review 里禁「warp 内按数据走不同长循环」 |
| 同样的 kernel，batch 从 1 加到 8 只快了 2 倍 | decode 的 AI = B，仍远低于平衡点（§18.7） | 算 `AI = B`，对比平衡点 | 继续加 batch；或量化把每参数字节从 2 降到 1（AI 翻倍） | 把「decode 是带宽受限」写进容量模型，别按 TFLOPS 估吞吐 |

第 2、3 行是同一件事：**GPU 本身很快，但你没让它连续工作**。它的性能不是「每秒多少 flop」，是「每秒有多少 cycle 在发射指令」；launch 间隙、PCIe 等待、CPU 解析，都是发射率为 0 的 cycle。

## 18.12 一页速记

```
【唯一判据】
  同一段代码，是否作用于成千上万份互相独立的数据？
  —— 三个词各对应一道门：同一段（同构）、独立（无依赖）、成千上万（够摊薄启动）。

【三个不等式】
  ① 并行度：N·t > L（L = kernel launch 5–20 μs）→ 否则加速比为负
             SAXPY 的交点 N* ≈ 1.3×10⁴（@5 μs 启动、20 GB/s CPU）
  ② 算力密度：AI = flop/Byte > 平衡点 = 峰值算力/带宽
             CPU 4.2 ｜ A100 9.6 ｜ H100 20 ｜ 4090 82
  ③ 同构性：一个 warp 的 32 lane 必须同路
             利用率 ≤ 1/路径数；最坏 1/32 = 3.1% → 慢 32 倍

【四个场景的代入】
  图形   2×10⁶ 像素/帧 × 同一 shader × 互不依赖      → 三样全中，天生 GPU
  GEMM   朴素 AI=0.25；T×T 分块 AI=T/4（T=64 → 16） → 分块后才算力受限
  OLTP   并行度=1、AI≈0.01、每层分支不同、还要过 PCIe → 三道门全不过
  推理   prefill AI≈批内 token 数（10²–10³ → 算力受限）
         decode  AI=B，B=1 时只有平衡点的 1/82     → batching 与 KV cache 的物理原因

【三个数字】
  pthread 新建+回收 10.9–25.8 μs ≈ kernel launch 5–20 μs
  SIMD 宽度 8 倍，实测只快 3.65–4.09 倍（AI=0.25，撞带宽）
  1 GB 过 PCIe 4.0 ≈ 40 ms，同一 GB 在 4090 上算 AI=100 只要 1.2 ms → 拷贝贵 33 倍

【一句话】
  换卡只抬高 min(p, AI/平衡点, 32/路径数) 里的第一项；
  后两项不变，钱就白花。
```

## 18.13 自检 3 题

**Q1.** 一个服务要把「用户上传的 4 KB JSON 做 schema 校验」搬到 GPU，理由是「校验规则有 300 条，可以并行」。请用本判据的三道门逐条判决，并给出一个能立刻算出来的数字来说明它为什么必败。

<details><summary>答案</summary>

**门① 并行度：不过。** 这里的「并行单位」是 300 条规则，但每条规则要读**同一份** JSON——它们不是 300 份独立数据，而是 300 个阅读者读一页纸。真正能并行的份数是 1（一个请求）。而且校验是短链：一次请求的全部工作约 1–5 μs（4 KB 内存 + 几百次比较）。

**门② 算术强度：不过。** 4 KB 数据上做几百次整数比较，`AI ≈ 0.1 flop/B` 量级，远低于任何机器的平衡点。

**门③ 同构性：不过。** 300 条规则里绝大多数在第一个字节就短路返回（schema 不匹配），路径长度从 1 步到几十步不等；放进一个 warp 就是 32 条 lane 走 32 条不同长度的路。

**能立刻算的数字**：一次 kernel launch 5–20 μs，而单个请求的全部工作只有 1–5 μs。也就是说**「把活派下去」这个动作比「活本身」贵 4–10 倍**，无论 GPU 有多少核。正确做法是把「每请求一次」变成「每批 10⁴ 个请求一次」——那时并行单位才真的变成 10⁴ 份独立 JSON，门① 才过。**判据的第一道门问的不是「能不能并行」，而是「并行的是不是独立的那些份」。**
</details>

**Q2.** 有人把 7B 模型的 decode 从 batch=1 提到 batch=32，吞吐只涨了 6 倍而不是 32 倍；再加到 batch=128，涨幅进一步变小。用 AI 与 roofline 解释这个饱和，并说出「加 batch」在什么条件下才继续有效。

<details><summary>答案</summary>

decode 的算术强度 `AI = B`（fp16：`flops = 2BP`、`bytes = 2P`）。带宽受限时，吞吐上限 = `带宽 × AI / (2P)`，与 B 成正比——所以从理论上看，batch 从 1 到 32 应该接近 32 倍。

实际只涨 6 倍，说明在 batch=1 到 32 的区间里，还有别的天花板先到了：① **延迟**——batch=32 时每步要等 32 个请求的 KV 都就绪，尾延迟拉长，有效并发没有真的到 32；② **KV cache 带宽与容量**——batch 越大，每步除了读权重还要读 32 份 KV，`bytes` 不再是 `2P` 而是 `2P + 32×KV`，AI 被 KV 拉低；③ **显存带宽没有跑满**（kernel 效率、wave quantization）。

到 batch=128 时饱和，最可能的原因是**已经越过平衡点**（A100 只需 B≈10，4090 需要 B≈164），此时从带宽受限转为算力受限，继续加 batch 的收益从「线性」变成「不能再涨」。所以「加 batch 是否继续有效」的判据是：**当前的 `AI = B_eff`（B 减去 KV 的额外流量）是否还低于平衡点**。低于就继续加，高于就只能提高算力（张量核/量化/更好的 kernel）或加带宽（更多卡、更大显存带宽）。

顺带一个结论：**同样的 batch，在 A100 上早就不涨了，在 4090 上还在涨**——因为平衡点差 8 倍。这解释了为什么「最佳 batch」不是一个模型属性，而是「模型 × 卡」的属性。
</details>

**Q3.** 下面四段代码，哪一段「搬到 GPU 会更快」？请只用三道门判断，不要凭直觉。

```c
A. for (i = 0; i < n; i++) out[i] = sqrt(in[i]);            // n = 1e8
B. for (i = 0; i < n; i++) p = next[p];                     // 链表遍历，n = 1e6
C. for (i = 0; i < n; i++) if (flag[i]) out[i] = f(in[i]);  // n = 1e8，flag 随机
D. for (i = 0; i < n; i++) out[i] = a[i] * b[i] + c[i];     // n = 1e3
```

<details><summary>答案</summary>

**A：会更快。** 三样全中：n = 10⁸ 份独立数据（门①过）；`sqrt` 是 1 条指令量级、8 B/元素的搬运，`AI ≈ 0.25` **不过门②**——所以它是带宽受限的，GPU 的加速比上限是 `1008/20 ≈ 50 倍`（带宽比），不是 1000 倍。**「会更快」和「快到什么程度」是两个问题**，门② 决定后者。而且 sqrt 在 GPU 上有硬件近似指令（`rsqrt` 迭代），实际还能再好一点。

**B：不会更快。** 门① 直接不过：`p = next[p]` 是一条**长度 10⁶ 的串行依赖链**，并行度 = 1。每次跳转都是一次随机访存（本机实测 135–227 ns/次）。GPU 的 1.6 万条 lane 一条也用不上；而且每次遍历要 launch 一次，5–20 μs 的启动开销对 1e6 次 × 200 ns = 0.2 s 的串行时间来说还不算致命，但**并行度这一项就判决了**：GPU 版和 CPU 版的时间会完全一样（都是那条链），却多了 PCIe 和启动开销。

**C：多半不会更快，或者只快一点。** 门① 过（10⁸ 份），门② 不过（2 flop / 8 B），**门③ 是刀口**：`flag` 随机意味着一个 warp 的 32 条 lane 里约有一半分叉。好在只有两条路径，利用率约 50%（`k=2`，§18.2），损失可接受；真正的问题是 `if` 让向量化失效 + 存储是条件性的。结论是「能跑，收益被门② 和门③ 各切一刀」，要在 GPU 上做好得改成无分支写（先算再按 mask 混写），这属于工程改写而不是「搬过去」。

**D：不会更快。** 门① 硬不过：n = 10³，而 GPU 的交点 N* ≈ 1.3×10⁴（SAXPY 同构）。工作量 1000 × 0.4 ns = 0.4 μs，启动开销 5–20 μs——**慢 12–50 倍**，且加核无效。这一段必须留 CPU，而且 CPU 上它已经快到不值得优化（0.4 μs）。

四段的判决合起来就是一句话：**A 过三道门但被带宽限速，B 死在门①，C 半死门③，D 死在门①的数字上。** 判据不是「数据量大就去 GPU」，是「独立份数 × 每份工作量 / 启动开销」这个比值。
</details>
