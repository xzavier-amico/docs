## 29.1 引子：一次掉电后「数据库说已提交、审计日志却是 0 字节」

2025-10 中旬，一台跑着订单服务的小机柜做 UPS 切换演练，切换失败，整柜掉电约 1.4 秒。来电后 ext4 正常挂载、日志 replay 了一个事务，服务 90 秒内恢复。真正的麻烦在第二天早上：财务对账时发现，**审计日志里 40 分钟的记录全没了，而订单表一条不少**。

复盘表（我按工单原样整理）：

| 时间 | 事件 | 观测 |
| --- | --- | --- |
| 02:11:07 | UPS 切换失败，整柜掉电 | 无任何 `sync` 在飞 |
| 02:11:09 | 来电，内核挂载 ext4，replay 1 个事务 | `dmesg` 只有一行 recovery |
| 02:12 | 服务拉起，订单数、金额与对账前置库完全一致 | MySQL 侧无丢失 |
| 02:40 | 审计文件按天分片，37 个文件 `stat` 大小为 0 | 文件名在、目录项在、内容没了 |
| 03:10 | 阅读审计写入代码：`fopen(path,"a")` + `fprintf` + `fclose`，**全程没有 `fsync`** | 与 MySQL 的 `innodb_flush_log_at_trx_commit=1` 形成对照 |
| 03:20 | 复核：这 40 分钟里，审计文件所在的页缓存从未被回写（当天写入量 3.2 MB，远低于任何阈值） | `Dirty` 一直没被推到需要回写的量级 |

两套代码在同一个进程里，跑在同一块盘上，对「提交」这个词给了两个完全不同的承诺：

- MySQL 的「提交成功」= redo log 已经 `fsync` 到设备并收到确认；
- 审计模块的「写完」= `fprintf` 把字节拷进了 stdio 缓冲，`fclose` 又把它们拷进了页缓存。**两次拷贝，零次设备接触。**

这就是本篇要拆的东西。先排掉一个常见误诊，它会把排查引向错误方向。

### 先证伪：「kill -9 之后文件会变空」

工单里有人坚持「是运维 `kill -9` 重启导致的」。这台机器上可以直接验：

```c
int fd = open("/tmp/opencode/k9.bin", O_CREAT|O_TRUNC|O_WRONLY, 0644);
for (int i = 0; i < 256; i++) write(fd, buf, 4096);   /* 1 MB，刻意不 fsync */
pause();                                              /* 等外部 kill -9 */
```

```
写满 1MB，未 fsync，pid=3322187，等待被 kill -9
-rw-r--r-- 1 root root 1048576 Nov 19 08:10 /tmp/opencode/k9.bin
 41 41 41 41 41 41 41 41          ← 0x41 = 'A'，一个字节都没少
Dirty:              2584 kB       ← 进程死了，脏页还挂在页缓存上
```

**`kill -9` 不丢数据。** 页缓存属于内核，不属于进程；进程的地址空间被拆掉，那 1 MB 的脏页仍然挂在该 inode 的 xarray 上，等着回写线程或者下一个 `fsync` 来收。真正会丢的只有三种情况：内核自己也死了（panic）、电没了、或者虚拟化层/云盘把「已经确认的写」弄丢了。第一类靠日志恢复，第二类只能靠 `fsync`，第三类连 `fsync` 都救不了（§29.7 会看到实测证据）。

### 三层谎，一句话一层

| 层 | 你听到的承诺 | 实际含义 | 谁在说谎 |
| --- | --- | --- | --- |
| ① 页缓存 | `write()` 返回 1 MB | 这 1 MB 已经在你和内核共享的那块内存里了，**一块盘都没碰** | 不怪它，POSIX 只承诺 read-after-write 一致性 |
| ② 日志 | 日志事务「提交了」 | 元数据已经顺序写进 journal 并落了 commit 块；**你的数据块可能还在页缓存里**（`data=ordered` 才补上顺序） | 「提交」这个词被借去指了两件事 |
| ③ 设备缓存 | `fsync()` 返回了 | 设备回了「FLUSH 完成」；盘上 DRAM、阵列控制器、宿主页缓存、云盘的三副本，任何一层都还没到介质 | 这一层连内核都验不了 |

再补一条容易漏的：**目录项也有自己的一次持久化**。`fsync(file_fd)` 保证的是「这个 inode 的数据和元数据」，不保证「这个名字在目录里」。新建文件后要 `fsync(dir_fd)`，否则掉电后文件内容在、名字没了——这个坑在 §29.11 还会出现。

## 29.2 写路径的六层缓冲：每一层都在替上一层「先答应」

一次 `write(1 MB)` 要经过六段持有者，关键在于：**每一段都可以先收下、后兑现，而收下的那一刻就是你看到的「成功」**。

```
 ①用户态缓冲        ②页缓存            ③块层队列        ④设备缓存        ⑤介质
┌───────────┐  write() ┌─────────────┐ submit_bio ┌────────────┐ FLUSH ┌──────────┐
│ stdio /   │ ───────► │ page cache  │ ─────────► │ 盘上 DRAM  │ ────► │ platter  │
│ Java 缓冲 │          │ dirty page  │            │ 16MB–4GB   │       │ NAND page│
│ Go bufio  │          │ (xarray)    │            │ 靠电容保命  │       │          │
└───────────┘          └─────────────┘            └────────────┘       └──────────┘
      │                      │                          │                   │
  fflush() 止步于此     write() 返回于此           FLUSH 返回于此      真正的「在盘上」
                        （脏页只存在于内存）        （设备说它刷完了）

      另一边：元数据不走这条路，它先拐进 ③' 日志（jbd2），再 checkpoint 回原位
              ┌──────────────────────────┐
              │ journal (环形,64–128MB)  │ ── commit ──► 设备 ──► 原位
              └──────────────────────────┘
```

六层各自的「什么时候算安全」：

| # | 层 | 谁持有 | 掉电后还在吗 | 让这一层变安全的动作 | 这台机器上的量级 |
| --- | --- | --- | --- | --- | --- |
| ① | 用户态缓冲 | 进程堆 | 否 | `fflush` / `fclose` / `write` 系统调用 | 一次 memcpy，1 MB ≈ 38 µs |
| ② | 页缓存 | 内核 xarray | 否 | `fsync` / `fdatasync` / `sync` / 回写线程 | 1 MB 拷贝 ≈ 137 µs |
| ③ | 块层队列 | 内核 request queue | 否 | 无需动作（它本来就是内存） | 队列 256 条，`scheduler=[none]` |
| ③' | 日志（仅元数据） | jbd2 + 页缓存 | 否 | 事务提交（commit 块落盘） | 单事务均值 9 块，提交 1.06 ms |
| ④ | 设备写缓存 | 盘上 DRAM | **看固件与电容** | `FLUSH`（ext4 的 `barrier=1`） | 本机 `write_cache=write back` |
| ⑤ | 介质 | 磁片 / NAND | 是 | 没有上一层了 | HDD 随机 4K ≈ 122 IOPS |

两个必须记住的推论：

1. **每一层的「安全动作」都是一次等待。** `fsync` 贵，不是因为它做了多少计算，而是因为它要把 ①→④ 全部串行地等一遍，最后再加一次设备往返。这就是主线③「每层抽象的单价 = 跨界次数 × 单次成本」在存储栈上的样子。
2. **层数越多，承诺越容易缩水。** 本地一块裸盘是五层；容器里跑在 virtio 上、宿主再跑在云盘上，实际是七到八层，而 `fsync` 只买得到「最近那一层说 OK」。

日志只装元数据（inode、目录项、extent 树），因为 ext4 默认 `data=ordered`：把数据也写两遍会让写放大直接翻倍，而绝大多数场景只需要「结构别坏」。

## 29.3 `write()` 到底做了什么：一次拷贝，一次标脏，然后返回

把 `write(2)` 在内核里的路径按顺序拆开（ext4 + buffered IO）：

```
sys_write
 └─ vfs_write
     └─ file->f_op->write_iter  =  ext4_file_write_iter
         └─ generic_perform_write          ← buffered 路径
             ├─ ext4_da_write_begin        ← 在 page cache 里找页；没有就分配
             │    （页已存在但只写一部分 → 可能要先把 4KB 读上来）
             ├─ copy_from_user             ← 真正的成本：1 MB ≈ 137 µs
             ├─ ext4_da_write_end          ← SetPageDirty + mark_inode_dirty
             └─ balance_dirty_pages        ← 脏页超限时，这里会 sleep（§29.4）
     return 已拷贝字节数                    ← 到此为止，设备一次都没被打扰
```

返回值是「已经拷进页缓存的字节数」。POSIX 对 `write` 的承诺只有一条：**同一台机器上，后续 `read` 能读到刚写的内容**。它没有、也不可能承诺「已经在介质上」——因为那会把每次 `write` 都变成一次设备往返，`cp` 一个 10 GB 文件会慢两个数量级。

### 成本拆解（本机实测，p50，N=50）

| 动作 | 耗时 | 折合带宽 | 成本归谁 |
| --- | --- | --- | --- |
| 单次 `write(4 KB)`，页已在缓存 | **0.6 µs** | — | 系统调用 + 4 KB 拷贝 |
| 重写已在缓存的 1 MB | **137 µs** | 7.6 GB/s | `copy_from_user` |
| 首次 `write(1 MB)`（要分配 256 个页） | **401 µs** | 2.6 GB/s | 拷贝 + 页分配 + 块预留 |
| 用户态 `memcpy(1 MB)` 参照 | 38.5 µs | 27 GB/s | 纯带宽上限 |
| `fsync(1 MB)`（新文件，紧随其后） | **10.08 ms**（p90 17.8 ms） | 99 MB/s | 一次设备往返 + FLUSH |

这张表就是全篇最重要的一组对比。**同一份数据，`write` 花了 137 µs，`fsync` 花了 10 ms——73 倍。** 而 4 KB 那个 0.6 µs 更极端：它快到不像 IO，因为它确实不是 IO，它是「往一块共享内存里 memcpy 4 KB，顺便记一笔账」。

`fsync` 那 10 ms 是什么？拆开是：把 256 个脏页组织成 bio → 提交给 virtio 队列 → 宿主处理 → 设备写 → 发 FLUSH → 等设备把 DRAM 缓存刷进介质 → 完成中断回来 → 唤醒你。其中**只有最后一步（FLUSH 往返）是不可压缩的**，其余都能被批量和异步吃掉——这也解释了为什么组提交（§29.8）是数据库的第一性优化，而不是什么高级技巧。

### 一个容易被忽略的细节：部分页写要先读

`write` 路径里那行注释不是摆设。如果你往一个已存在文件的中间写 100 字节，而那个 4 KB 页不在页缓存里，内核必须先把这个块读上来（read-modify-write），否则页里另外 3996 字节会被写成 0。实测里「首次写」比「重写」慢 3 倍，一部分来自页分配，另一部分就来自这种隐含的读。

这也解释了 `O_DIRECT` 的 `EINVAL`（偏移/长度/缓冲区没对齐）与「写 100 字节却慢了 1 ms」（设备侧做了一次读-改-写）。

```c
/* 量 write 与 fsync 的价差：同一块缓冲区，同一块盘 */
double t0 = now_us();
write(fd, buf, 1 << 20);            /* ① 只进页缓存 */
double t1 = now_us();
fsync(fd);                          /* ② 等它真的到设备 */
double t2 = now_us();
printf("write %8.1f us   fsync %8.1f us\n", t1 - t0, t2 - t1);
```

## 29.4 回写机制：脏页攒到什么时候、谁来搬、为什么你会突然卡住

`write` 把页标脏之后就不管了。真正把它送到设备的是**回写（writeback）**，由两组东西驱动：一组是阈值（比例），一组是时间（老化）。

### 三个阈值 + 两个时间

本机 `/proc/sys/vm` 的真实值（就是默认值）：

```console
$ sysctl vm.dirty_ratio vm.dirty_background_ratio \
         vm.dirty_expire_centisecs vm.dirty_writeback_centisecs
vm.dirty_ratio = 20
vm.dirty_background_ratio = 10
vm.dirty_expire_centisecs = 3000
vm.dirty_writeback_centisecs = 500
```

按 `MemTotal = 2,021,692 kB`（1.93 GiB）换算：

| 参数 | 值 | 折算成字节 | 作用 |
| --- | --- | --- | --- |
| `dirty_background_ratio` | 10% | **197 MiB** | 超过它 → 唤醒 flusher 后台异步回写，**写者不阻塞** |
| `dirty_ratio` | 20% | **395 MiB** | 超过它 → 写者自己在 `balance_dirty_pages` 里**睡着等**，这就是「卡住」 |
| `dirty_expire_centisecs` | 3000（30 s） | — | 脏页超过 30 s 必须排队回写 |
| `dirty_writeback_centisecs` | 500（5 s） | — | flusher 每 5 s 醒一次，检查有没有超龄页 |

「30 s（老化）+ 5 s（周期唤醒）」只提示空闲且正常回写时，老脏页大约何时有机会进入回写，**不是落盘时限或最大丢失窗口**。写回仍可能因调度、设备拥塞或故障延后，应用层缓冲中尚未交给内核的字节也不在这些计时器的范围内。不能仅凭总写入量和掉电时间解释 29.1 的 40 分钟缺口；需要核对应用刷缓冲、文件同步及存储链路证据。

### 谁来搬：per-bdi 的 flush 线程

`pdflush` 是 2.6.32 之前的历史名词。现在每个块设备（更准确说是每个 bdi）有自己的回写线程：

```console
$ ps -eo pid,comm | grep -E 'flush|jbd2'
    238 jbd2/vda1-8
2620367 kworker/u8:2-flush-254:0
3311849 kworker/u8:3-flush-254:0
```

`flush-254:0` 里的 254 是设备号（vda），`jbd2/vda1-8` 是 ext4 的日志线程。分设备的意义很直接：**一块慢盘的回写不应该拖住另一块快盘**。

### 「写很快，然后突然卡住」的完整机制

稳态吞吐由两个上限中较小的那个决定：

```
缓存侧速度 = copy_from_user 带宽           ≈ 7.6 GB/s（实测 1 MB/137 µs）
设备侧速度 = 回写带宽                       ≈ 350 MB/s（200 MB / 540 ms 反推）
净积累速度 = 缓存侧 − 设备侧                ≈ 7.2 GB/s

脏页从 0 涨到 197 MiB（background 阈值）：197 MiB ÷ 7.2 GB/s ≈ 29 ms
```

也就是说，**在满速写入下，29 毫秒就会撞到 background 阈值**。从这一刻起，flusher 开始追，但设备侧只有 350 MB/s；脏页继续涨，再涨 198 MiB 就撞 `dirty_ratio`，写者开始睡。表现就是：前几十毫秒「飞快」，接着吞吐塌到设备速度，延迟从几十微秒跳到几十毫秒，而且**周期性**——因为回写一追上来，写者又被放行。

这也是主线②「快慢只有一种解释——排队」在存储栈上的原话：抖动、P99 尖刺、写入一段时间后 RT 翻倍，第一嫌疑不是 GC 也不是锁，而是**队列深度被阈值量化了**。

### 真实输出：一边写 200 MB，一边读 `Dirty`

```
已写MB 本次耗时ms   Dirty_MB   累计ms
     1       0.52        1.8          1
     2       0.50        2.8          1
   ...
    50       0.47       50.9        110
    60       5.90       52.1        141     ← 第一次明显停顿
    70      15.08       54.1        183     ← 15 ms 写 1 MB = 66 MB/s
    80       0.57       56.1        200
   ...
   170       9.20       58.2        460
   190      11.80       54.1        509
   200       0.51       56.1        540
```

三个读法：

1. **`Dirty` 稳定在 50–60 MB，没有涨到 197 MB。** 因为这台机器的「设备」是 virtio 虚拟盘，请求被宿主立刻收下（宿主也有页缓存），回写速度远高于 350 MB/s，脏页攒不起来。这本身就是第三层谎的现场证据：**你以为在等盘，其实在等宿主的页缓存。**
2. **平峰 0.5 ms/MB = 2 GB/s，尖峰 15 ms/MB = 66 MB/s，差 30 倍。** 平峰是内存速度，尖峰才是「真的碰了设备」。
3. **尖峰是周期性的，且每次只有 1 MB 受影响。** 这是「写者被节流」而不是「设备挂了」的典型形状——如果是设备故障，整段都会慢。

为了把「撞上限就卡」压到可观测的幅度，又把阈值临时压到 `dirty_background_bytes=8 MiB`、`dirty_bytes=16 MiB` 重跑（跑完立即改回）：

```
     4       0.49        7.3          2
     5      22.11        1.0         24     ← 撞 16 MiB 上限，单块 22 ms
     8      12.69        4.0         38
   ...
    50      14.52        6.0        186
   150      16.55        5.9        422
```

`Dirty` 被硬钉在 4–8 MB，每次撞线就罚 12–22 ms。**同一个 `write(1 MB)`，代价从 0.5 ms 变成 22 ms，44 倍，唯一变量是两个 sysctl。** 这就是「参数即架构」最便宜的一次演示。

## 29.5 崩溃一致性：数据与元数据的顺序，决定你看到 0 字节还是乱码

先把三个词分开，它们经常被混成一个：

- **一致性（consistency）**：崩溃后文件系统还能挂载、结构自洽、不指向已释放的块。这是日志买到的。
- **持久性（durability）**：崩溃前你确认过的数据还在。这是 `fsync` 买到的。
- **原子性（atomicity）**：一次操作要么全生效要么全不生效。这是「日志事务 + `rename`」买到的，而且只在有限范围内。

**日志只保证第一个。** 第二个必须由应用自己调 `fsync`，第三个要看具体操作（`rename` 在同文件系统内原子，跨文件系统直接 `EXDEV` 失败）。

### 一个 0 字节文件的完整推演

`open(O_CREAT) + write + close`，四个掉电位置，四种结果：

| 掉电发生在 | 文件存在？ | 长度 | 内容 | 机制 |
| --- | --- | --- | --- | --- |
| 创建事务未提交 | 否 | — | — | 目录项和 inode 只在 journal 里，回滚 |
| 创建事务已提交，数据未回写 | **是** | **0** | 空 | inode 里 size 还是 0；delalloc 还没分配块，**连「指向数据的元数据」都不存在** |
| 数据已写、extent 事务已提交 | 是 | 正确 | 正确 | ordered 保证数据先于映射元数据落盘 |
| 全部完成（checkpoint 也做了） | 是 | 正确 | 正确 | 无需 replay |

第二行是全部问题的核心，也是最反直觉的一行：**`data=ordered` 并没有承诺「write 过就有内容」。** 它承诺的是「**如果有**一条元数据事务把这些块映射给这个文件，那么数据块必须先落盘」。而延迟分配（delalloc）让这条事务要等到回写时才生成——回写没发生，事务就不存在，崩溃后你看到的是创建时那份 `size=0` 的 inode。

这就是为什么「文件系统一致」和「你的文件完整」是两件事，也是为什么 `auto_da_alloc` 这个挂载选项存在：本机 `/proc/fs/ext4/vda1/options` 里确实有它。它做的是一个**启发式**——遇到 `O_TRUNC` 或 `rename` 覆盖已存在文件时，先把数据写下去再提交元数据，专门用来消灭历史上高频出现的「邮件 spool 变 0 字节」。注意「启发式」三个字：它不是保证，不能替代 `fsync`。

### 三种 `data=` 模式

| 模式 | 数据怎么走 | 崩溃后可能看到 | 写放大 | 典型用途 |
| --- | --- | --- | --- | --- |
| `data=writeback` | 数据直接写原位，元数据走日志，**两者无顺序约束** | 长度对、内容是**旧数据或别人剩下的块**（可能泄露前一个文件的字节） | 最低 | 追求吞吐、且自己能保证顺序的场景（少） |
| `data=ordered`（**默认**） | 先写入相关数据块，再提交关联的元数据事务 | 元数据有序，不保证普通数据写入的原子性；覆盖多个已有块时，文件长度可以不变，但仍可能新旧块混杂 | 中 | 几乎所有通用场景 |
| `data=journal` | 数据和元数据都写进日志 | 恢复以日志事务为单位；一次应用写入不等于一个日志事务 | 最高（数据块通常写两次） | 确实需要数据日志的场景 |

`data=writeback` 的风险发生在崩溃恢复后：映射可能已提交，新数据却未写入，读到的是存储介质上的旧内容，而不是重启前的页缓存。`ordered` 约束关联数据与元数据提交的顺序，不会把没有同步的普通多块覆盖变成原子替换。见 [ext4 日志模式](https://www.kernel.org/doc/html/latest/filesystems/ext4/journal.html)。

### 目录项：`fsync(file)` 不等于 `fsync(name)`

新建文件 `creat("a.tmp")` → 写 → `fsync(fd)` → `rename("a.tmp","a")` → 掉电。你可能得到：`a` 不存在，`a.tmp` 存在且内容完整。因为 `fsync(fd)` 保证的是 inode 与数据，**目录项是另一个 inode（目录）的元数据**。

正确顺序只有一条：**先 `fsync(file_fd)`，再 `fsync(dir_fd)`**。少后一步，文件名可能回退到上一个已提交的状态；在「写完临时文件再原子替换」的模式里，这表现为「新版本内容在盘上，但名字还指着旧文件」——数据没丢，语义丢了。

## 29.6 ext4 日志（jbd2）：descriptor / data / commit 与 barrier 的全部意义

ext4 的日志不是「把操作记下来」，而是「**先把要改的块的新内容写到一个环形区域，写一个 commit 标记，再慢慢搬回原位**」。三个角色：

```
journal 环形区（常见 64–128 MB，本机 /dev/vda1 上）
┌──────────────┬─────────────────────────┬──────────────┐
│ descriptor   │  metadata blocks        │ commit       │
│ 每个 tag:    │  （要改的块的「新」内容） │ 序列号 +     │
│  fsblk 4B    │                         │ checksum     │
│  flags  4B   │                         │ 12–16 B      │
│  csum   4B   │                         │              │
└──────────────┴─────────────────────────┴──────────────┘
   ①写日志（顺序）        ②提交（一次 FLUSH）      ③checkpoint（写回原位）
```

三个阶段缺一不可：

1. **journal write**：把 descriptor + 新块内容顺序写进日志区。顺序写，所以快（HDD 上顺序 ≈ 250 MB/s，随机 4K 只有 122 IOPS，差两个数量级）。
2. **commit**：写 commit 块，并且**在它之前发一次 FLUSH**。commit 块落盘 = 这个事务生效。恢复时只 replay 有 commit 的事务。
3. **checkpoint**：把日志里的块写回文件系统原位，然后这段日志空间可以复用。checkpoint 是异步的，所以「已提交」远早于「已回原位」。

### `barrier=1` 到底在防什么

设备有写缓存（本机 `cat /sys/block/vda/queue/write_cache` → `write back`），意味着**设备可以自由重排它收到的写**。如果内核先发 descriptor、再发 commit，而设备把 commit 提到前面写了，掉电后恢复程序会看到「commit 说事务有效，但 descriptor 那块区域是上一轮的垃圾」——replay 直接把垃圾写进文件系统结构。

`barrier=1` 就是在 descriptor 和 commit 之间插一条 `REQ_PREFLUSH`：**设备必须把之前的所有写刷到介质，才允许写 commit**。所以：

| 配置 | 换到了什么 | 放弃了什么 | 掉电后果 |
| --- | --- | --- | --- |
| `barrier=1`（默认） | 日志顺序被设备尊重 | 每个事务多一次 FLUSH 往返 | 最坏丢最近未提交的事务 |
| `barrier=0` / `nobarrier` | 少一次往返，事务提交变快 | **顺序保证完全交给设备缓存** | 可能 replay 出损坏的日志 → 文件系统结构损坏，需 fsck |
| 盘无写缓存（`write_cache=write through`） | barrier 退化为空操作 | 无 | 与 `barrier=1` 等价 |

「关 barrier 换 IOPS」是云上最常见的自杀式调参：它省下的是每次提交几百微秒，赌的是「我的盘不会在错误的时刻掉电」。而虚拟化让这件事更糟——你在 guest 里关掉 barrier，宿主可能还在聚合写，掉电窗口反而变大。

### `journal_async_commit`

标准流程里，commit 块必须等 descriptor 全部落盘后才能写，中间那次 FLUSH 是硬成本。`journal_async_commit` 的做法是：**在 commit 块里存上 descriptor 的 checksum**，于是 commit 可以和 descriptor 并发写——恢复时若 checksum 对不上，就判定这个事务无效。省掉一次等待，代价是把「顺序」换成了「校验」。

### 字节账：一次 `rename` 到底写了多少

`rename("a","b")`（同目录、覆盖已存在的 `b`）在逻辑上只改了约 200 字节：两条目录项、两个 inode 的 ctime/mtime。实际写下去的：

| 块 | 数量 | 字节 | 内容 |
| --- | --- | --- | --- |
| descriptor | 1 | 4,096 | 4 个 tag（每个 12 B）+ 块头 |
| 目录块 | 2 | 8,192 | 删除 `a` 的项、写入 `b` 的项 |
| inode 块 | 2 | 8,192 | 目录 inode 的 mtime、`b` 的 ctime |
| commit | 1 | 4,096 | 序列号 + checksum |
| **日志小计** | **6** | **24,576** | 顺序写 |
| checkpoint（稍后原位写） | 4 | 16,384 | 同一批元数据块 |
| **合计** | **10** | **40,960** | ≈ 200 B 逻辑 → **200×** |

而这条链的实际延迟，本机量到的是 `rename + fsync(dir)` **p50 0.130 ms、p90 0.355 ms**。为什么不是 10 ms 级？因为 `commit=5`（本机挂载参数里确实有）意味着日志每 5 秒至少提交一次，你的事务大概率**搭上了别人（或定时器）已经发起的那班车**——这正是组提交在文件系统层的版本。

日志的统计也能直接读到：

```console
$ cat /proc/fs/jbd2/vda1-8/info
238227 transactions (139373 requested), each up to 2730 blocks
average:
  0ms waiting for transaction
  1063us average transaction commit time
  9 blocks per transaction
  11 logged blocks per transaction
```

`1063 µs` 的平均提交时间，和 §29.9 测到的 `fsync` 10 ms 差一个量级——因为一次 `fsync` 可能等不止一个事务，还要等数据块回写和设备 FLUSH。**「提交快」和「你的 fsync 快」不是一回事。**

## 29.7 fsync / fdatasync / sync_file_range / syncfs：各自买到了什么

这一族系统调用的区别，全在「同步哪些东西」和「等不等设备」两个维度上：

| 调用 | 同步数据 | 同步元数据 | 等设备 FLUSH | 代价（本机 p50） | 典型误用 |
| --- | --- | --- | --- | --- | --- |
| `write()` | 否 | 否 | 否 | 0.6 µs / 4 KB | 当成「已保存」 |
| `fsync(fd)` | 是 | 是（含 mtime/ctime） | 是 | 10.08 ms / 1 MB | 每行调用一次 |
| `fdatasync(fd)` | 是 | 只同步「读回数据所需」的部分 | 是 | 7.22 ms / 1 MB | 以为它等于不持久 |
| `sync_file_range()` | 只**发起**回写 | 否 | **否** | 数十 µs（不等待） | 以为它等于 fsync |
| `syncfs(fd)` | 整个文件系统 | 整个文件系统 | 是 | 不可控（可能 GB 级） | 在请求路径上调用 |
| `sync()` | 全系统 | 全系统 | 是 | 不可控 | 定时任务里跑 |
| `O_DSYNC` | 每次 write 内含 | 部分 | 是 | 537 µs / 4 KB（dd 折合） | 小写入场景 |
| `O_DIRECT` | 绕页缓存 | 否 | **否** | 0.223 ms / 1 MB | 以为绕缓存就持久 |

几条必须说清的：

**`fdatasync` 省掉的是哪一次写。** 文件的 mtime/ctime 在每次 `write` 后都会变脏；`fsync` 要把这个 inode 更新也提交，`fdatasync` 则只保证「size + 块映射」正确。所以只有在**覆盖写、长度不变**时它才真的省；如果是追加导致 size 变化，size 本身就在必须同步的元数据里，两者几乎一样贵。实测 10.08 ms vs 7.22 ms，差的那 30% 就是这次 inode 提交，而且噪声很大（min 分别是 0.62 ms 和 0.56 ms）。

**`sync_file_range` 不是弱化版 `fsync`，它是另一个东西。** 它只把「这段区间」的脏页丢给块层，**不等待完成、不刷设备缓存、不管元数据**。它的正当用途是「在大 `fsync` 之前先把数据铺出去，让最后的等待变短」；单独用它做持久化，等于什么都没做。

**`O_DIRECT` 绕的是页缓存，不是设备缓存。** 它只保证数据不经过内核页缓存，写请求进了设备写缓存就返回，掉电照样丢；之后仍然需要 `fsync`。

本机实测：

```
O_DIRECT write(1MB)     p50 0.223 ms
O_DIRECT 后 fsync       p50 0.191 ms      ← 比 buffered 的 fsync 快 50 倍
```

`0.191 ms` 不可能是「把 1 MB 刷进介质」的时间（那至少是毫秒级，HDD 还要加寻道）。它是**宿主说「收到了」**的时间。这就是第三层谎最直白的证据：在虚拟化环境里，`fsync` 的延迟测的是最近那一层缓存的 RTT，不是介质。

### `write + fsync` 的组合才是「持久化」

```c
/* 正确的持久化写入：数据 → 文件 → 目录，三步都要 */
int fd = open("/data/audit/2025-10-14.log", O_CREAT|O_WRONLY|O_APPEND, 0644);
write(fd, rec, len);
if (fsync(fd) != 0) abort();          /* ① 数据 + inode */
close(fd);
int dfd = open("/data/audit", O_RDONLY|O_DIRECTORY);
if (fsync(dfd) != 0) abort();          /* ② 目录项（新建文件时才需要） */
close(dfd);
```

## 29.8 数据库为什么需要 WAL + fsync：把随机写换成顺序写，再把 N 次 fsync 合成 1 次

**第一个动机：随机改变数据页太贵。** 一条 UPDATE 落在 B+ 树的一个 16 KB 页上，这个页在文件里的位置是随机的。直接改它，就是一次随机 4 KB–16 KB 写。按 `base/08` 的账：HDD 随机 4K 只有 122 IOPS，顺序写有 250 MB/s，差两个数量级以上；SSD 上随机写还要触发擦除块的 GC。而 WAL 把「随机改页」变成「顺序追加一条记录」——**同样一份字节，只是换了个落点，代价差一到两个数量级**。

**第二个动机：一次 fsync 可以服务很多事务。** 实测单次 `fsync` p50 是 10.08 ms，也就是单线程每秒最多约 **99 次提交**。如果每笔事务都独立 `fsync`，这个数据库的写入上限就是 99 TPS，跟 CPU、跟 SQL 复杂度都没关系——**天花板由盘的一次往返钉死**（这也是 `base/08` 里 8.2 ms commit 的同一个现象）。

组提交（group commit）把这件事拆开：

| 批大小 N | 每批一次 fsync | 提交吞吐 | 单事务的 fsync 等待 |
| --- | --- | --- | --- |
| 1 | 10.08 ms | 99 /s | 10.1 ms |
| 8 | 10.08 ms | 793 /s | 10.1 ms |
| 64 | 10.08 ms | **6,349 /s** | 10.1 ms |
| 256 | 10.08 ms | 25,397 /s | 10.1 ms |

读法：**吞吐随批大小线性涨，单事务延迟几乎不变**——因为大家等的是同一次设备往返。这就是为什么「把 `fsync` 去掉」不是优化而是毁约：真正该做的是「让更多事务共享同一次 `fsync`」。

批大小不能无限大，卡在两个地方：① 日志写入的字节数仍然线性增长，撞到日志带宽上限后 `fsync` 本身会变慢；② 延迟 = 等待窗口 + fsync，窗口开太大，P99 就上去了。所以真实系统里它是一个可调参数（`innodb_flush_log_at_trx_commit`、PostgreSQL 的 `commit_delay`），而不是「越大越好」。

**WAL 的两条铁律**（机制细节在 [comp/03](../comp/03-wal-bufferpool-crash-recovery.md)）：

1. **日志先行**：日志记录必须先于对应的数据页落盘。否则崩溃后你有一个「改过的页」和一条「没记录的变更」，redo 无从重放。
2. **提交即持久**：只有 commit 记录 `fsync` 返回，事务才算提交。返回之前崩溃 → 事务不存在；返回之后崩溃 → 必须能重放出来。

redo/undo 的分工、checkpoint 与 LSN、2PC 与 binlog 的顺序，全部在 [comp/08](../comp/08-redo-undo-binlog-2pc.md) 里，本篇不重复。这里只留一句可迁移的判据：**看到「提交慢」，先问「一次提交等了几次设备往返」，再问「能不能让更多提交共享同一次往返」。**

## 29.9 实测：把这台机器上的三层谎量出来

### E0 · 先探测 `/tmp` 是什么文件系统

```console
$ df -T /tmp
Filesystem     Type 1K-blocks    Used Available Use% Mounted on
/dev/vda1      ext4  20605384 8654076  11077712  44% /

$ grep ' / ' /proc/mounts
/dev/vda1 / ext4 rw,relatime,errors=remount-ro 0 0

$ cat /sys/block/vda/queue/write_cache
write back
```

`/tmp` **不是**独立挂载点，它就在根文件系统上：真 ext4、真 virtio 块设备、设备自报有写缓存。所以 `fsync` 会真的走到设备队列，不是 tmpfs 的空操作。

但要说清边界：这是 **KVM 上的 virtio 虚拟盘**（2 vCPU、1.93 GiB 内存、内核 6.12.113），设备背后是宿主的页缓存与宿主的物理盘。**「掉电后数据在不在介质上」这件事，容器里无法验证**——我没有权限拔电，也无法观测宿主是否真的把 FLUSH 落到了盘片。下面所有数字都是「到虚拟设备为止」的语义。

### E1 · write 的成本拆解

```
① 首次 write(1MB)（含分配 256 页）     p50     401.4 us   min     363.1 us
② 重写已在缓存的 1MB（纯拷贝+syscall） p50     137.4 us   min     135.2 us
③ 重写后的 fsync(1MB)                  p50     538.1 us   min     361.2 us
④ 单次 write(4KB)（页已在缓存）        p50       0.6 us   min       0.6 us
⑤ memcpy(1MB) 用户态参照               p50      38.5 us   min      30.0 us
```

`③` 只有 0.54 ms，因为 ① 已经把块分配好、后面又没有新元数据要提交。**`fsync` 的价不是一个常数**，取决于「有多少东西要提交、设备要不要真的转一圈」。

### E2 · 1 MB：write 与 fsync 的价差（N=40）

```
write(1MB) 一次 write 系统调用   min 0.408  p50 0.494  p90 0.589  mean 0.555  ms
fsync(1MB) 紧随其后             min 0.616  p50 10.077 p90 17.776 mean 9.026  ms
fdatasync(1MB) 新文件同长度      min 0.562  p50 7.221  p90 17.616 mean 7.352  ms
```

`p50` 与 `min` 差 16 倍，说明设备延迟被邻居严重影响；同一台机器上 `fsync` 的 p50 在不同轮次间能从 0.5 ms 摆到 10 ms（E1 的 `③` 与这里就是两个样本）。**所以这张表只看量级与分布形状，不要当基准值。** 但「write 是亚毫秒、fsync 是毫秒」在任何一块真盘上都成立。

### E3 · 1000 次 4 KB vs 1 次 4 MB（同样是 4 MB）

```
1000×4KB write（共 4MB）   min 2.110  p50 2.304  p90 12.862  mean 5.199  ms
   └ 其后 fsync            min 1.479  p50 13.094 p90 33.480  mean 15.315 ms
1×4MB write（同样 4MB）    min 1.752  p50 1.922  p90  8.623  mean 4.303  ms
   └ 其后 fsync            min 1.255  p50  8.044 p90 25.767  mean 11.442 ms
```

两个结论，一正一反：

- **write 阶段差别不大**（2.3 ms vs 1.9 ms，约 20%）。1000 次 syscall 的 0.6 µs 摊到 4 MB 上总共才 0.6 ms，其余都是内存拷贝。**「小写慢」在页缓存这一层几乎不成立**——4 KB 太小，拷贝和 syscall 都便宜。
- **fsync 阶段差 63%**（13.1 ms vs 8.0 ms）。因为 1000 次写产生的是 1000 个脏页、可能跨多个 extent，回写时要组织更多的 bio；而一次 4 MB 写天然连续。**持久化的代价与「写的碎片度」正相关，与「系统调用次数」关系不大。**

### E4 · `dd`：四种写法的差距（4 MB，三轮）

| 写法 | 第 1 轮 | 第 2 轮 | 第 3 轮 | 说明 |
| --- | --- | --- | --- | --- |
| `dd` 只写（bs=4k count=1024） | 28 ms | 15 ms | 20 ms | 之后单独 `sync` 花 35 / 30 / 12 ms |
| `dd conv=fsync` | 33 ms | 41 ms | 40 ms | 写完等一次 fsync |
| `dd oflag=dsync` | 560 ms | 534 ms | 593 ms | **每块**都同步 |
| `dd oflag=direct` | 180 ms | 267 ms | 164 ms | 绕页缓存，未 fsync |

`dsync` 是 `conv=fsync` 的 **13–16 倍**：1024 块 × 约 537 µs/块 ≈ 0.55 s，折合 **1,860 次同步写/秒**。这个数字可以直接用来算「每次 `write` 都 `fsync`」的 QPS 上限——29.11 第一条坑就是它。

### E5 · `Dirty` 的现场（见 §29.4 的两段输出）

两段输出的对照本身就是结论：**卡顿来自阈值，不来自数据量**——默认阈值下停在 50–60 MB，压到 8/16 MB 后钉在 4–8 MB 并出现 12–22 ms 尖峰。

### E6 · 一次 `rename` 的延迟与 jbd2 的账

```
rename+fsync(dir)  p50 0.130 ms  p90 0.355 ms  min 0.117 ms
```

配合 §29.6 的字节账：**一次逻辑上改 200 字节的改名写下去约 40 KB（200× 放大），耗时 0.13 ms（搭了 commit=5 的便车）。**

### 诚实边界

| 想验证的 | 能不能 | 原因 |
| --- | --- | --- |
| `write` 与 `fsync` 的价差 | ✅ 能 | 都是本机 syscall，与介质无关 |
| `Dirty` 阈值导致节流 | ✅ 能 | 改 sysctl 可复现，已恢复原值 |
| 0 字节文件 | ❌ 不能 | 需要真掉电或 `dm-flakey`；容器内没有块设备控制权 |
| `barrier` 关掉会坏日志 | ❌ 不能 | 同上，且不能拿共享机器做破坏性实验 |
| `fsync` 返回后数据真在介质 | ❌ 不能 | 虚拟盘 + 宿主缓存，观测不到介质 |

## 29.10 三列账：承诺、代价、崩点

| 机制 | 承诺了什么 | 为此付了什么 | 从哪里开始失效 |
| --- | --- | --- | --- |
| `write()` | 数据进入页缓存，后续 `read` 可见；返回字节数 | 一次 `copy_from_user`（1 MB ≈ 137 µs）+ 页分配 | 进程退出/崩溃不影响；**掉电、panic 全丢** |
| 页缓存回写 | 脏页最终会落盘（老化 30 s + 唤醒 5 s） | 内存被脏页占住；撞阈值时写者被节流 | 阈值抖动 → P99 尖刺；容器内存上限会提前触发回收 |
| `fsync()` | 文件数据 + 元数据到达设备，且设备确认 FLUSH | 10 ms 级往返（本机 p50 10.08 ms） | 每行一次 → QPS 被钉在 ~100；设备缓存/宿主/云盘仍可能吞掉 |
| `fdatasync()` | 同上，但只保证「读回数据」所需的元数据 | 略便宜（7.22 ms vs 10.08 ms） | 追加导致 size 变化时，便宜基本消失 |
| `data=ordered` | 相关数据先于关联元数据提交 | 元数据提交可能等待相关数据回写 | 不保证多块写入全成或全败；delalloc 下未同步的文件也可能仍是 0 字节 |
| `barrier=1` | 日志 descriptor 先于 commit 落盘，replay 不会读到垃圾 | 每事务一次额外 FLUSH | 关掉它 → 掉电可能损坏文件系统结构 |
| `rename()` | 同文件系统内原子替换目录项 | 一次日志事务（≈40 KB，200× 放大） | 跨文件系统直接 `EXDEV`；不 `fsync(dir)` 名字会回退 |
| `O_DIRECT` | 绕开页缓存，数据直接进出设备 | 对齐要求；失去 readahead 与合并 | **不保证持久**，仍要 `fsync`；小写会退化成读-改-写 |

一句话收束：**这套机制买到的是「顺序」和「可恢复」，不是「不丢」。** 不丢要应用自己拿 `fsync` 去换，而 `fsync` 的兑现能力止步于最近一层愿意回话的缓存。

## 29.11 踩坑清单：现象 → 根因 → 定位 → 修 → 防复发

| 现象 | 根因（指回本篇） | 怎么定位 | 怎么修 | 怎么防复发 |
| --- | --- | --- | --- | --- |
| 写入 QPS 只有几百，CPU 却很闲 | 每条记录一次 `fsync`，被设备往返钉死（§29.8） | `strace -c -T -e trace=fsync,fdatasync` 看调用次数与单次耗时；`iostat -x 1` 看 `w/s` 是否等于 QPS | 组提交：攒批、单线程刷、或让框架批量提交 | 代码评审禁「循环体内 fsync」；压测必须报 `fsync/s` |
| 掉电后文件在、内容 0 字节 | delalloc + 未 `fsync`，inode size 还停在 0（§29.5） | 对比 `stat` 的 size 与写入日志；确认写路径有无 `fsync` | 写关键文件后 `fsync(fd)`；新建文件再加 `fsync(dir)` | 把「写文件」封装成带 fsync 的函数，禁止裸 `fprintf` 落关键数据 |
| `O_TRUNC` 重写配置后掉电，文件变 0 字节 | 截断把长度归零，新数据还在页缓存（§29.5） | 复现 `truncate` + `write` + 掉电；确认 `auto_da_alloc` 是否生效 | 写临时文件 + `fsync` + `rename` 替换，不要原地 `O_TRUNC` | 配置写入统一走「临时文件 + 原子替换」模板 |
| 写完立刻改名，掉电后名字回退 | `fsync(file)` 不含目录项，`rename` 的目录事务未提交（§29.5） | 崩溃后 `ls` 看到临时文件名还在 | 顺序改成 `fsync(file)` → `rename` → `fsync(dir)` | 原子替换写成固定模板，不给调用方选择 |
| `fsync` 很快（几十 µs），以为盘很快 | 测到的是宿主/设备缓存的 RTT（§29.7） | 与 `iostat` 的 `await`、`fio --direct=1` 对照；看 `write_cache` | 接受它只是「到缓存」；需要真持久就换本地盘或加副本 | 容量规划用 `fio` 稳态值，不用容器里的 `fsync` 延迟 |
| 大文件拷贝后立即重启，目标文件截断 | 拷贝工具（`cp`/`tar`）读完就返回，没 `fsync`；页缓存随重启丢失 | 比较源与目标的 size/`sha256`；`strace -e trace=fsync` 看拷贝进程有没有调用 | 拷贝后 `sync` 或对目标 `fsync`；备份流程显式落盘 | 备份脚本末尾固定 `sync`，并校验 checksum |
| 关掉 barrier 后 IOPS 涨了，几个月后 fs 损坏 | 设备缓存重排，commit 先于 descriptor 落盘（§29.6） | `dmesg` 里的 ext4 错误、`fsck` 报告、`/proc/fs/ext4/*/options` 确认 `barrier` | 恢复 `barrier=1`；有电池/电容保护的阵列可评估关闭 | 把挂载参数纳入配置审计，禁止为跑分关 barrier |
| `rename` 跨挂载点报 `EXDEV`，改用「拷贝+删除」 | `rename` 的原子性只在同一文件系统内（§29.5） | `stat -f` 看两端是否同一 `Device` | 用「临时文件 + `fsync` + `rename`」在同一目录内完成；跨 fs 用两阶段 + 校验 | 目录规划时把「需要原子替换」的文件放同一挂载点 |

## 29.12 一页速记

```
【一句话】write 只是 memcpy 进页缓存；从「提交成功」到「在盘上」隔着页缓存、日志、
         设备缓存三层，每一层都可以先答应后兑现。

【六层】 用户缓冲 → 页缓存 → 块层队列 → 日志(jbd2) → 设备缓存 → 介质
         fflush     write返回    submit_bio   commit      FLUSH       真的在

【四个数字】
  write(4KB)            0.6 µs        ← 一次 syscall + 4KB 拷贝
  write(1MB) 首次       401 µs        ← 含 256 个页分配
  fsync(1MB)           10.08 ms p50   ← 一次设备往返 + FLUSH
  O_DSYNC(4KB)          537 µs        ← 每次写都同步 → 1,860/s 上限

【三个阈值】dirty_background 10%（197MiB）→ 后台回写
           dirty 20%（395MiB）→ 写者自己睡
           dirty_expire 30s + 唤醒 5s → 不 fsync 的最坏落盘上界

【崩溃一致性】
  data=ordered（默认）：相关数据先于关联元数据提交，不保证多块覆盖的原子性
  但仍可能 0 字节：delalloc 还没生成那条元数据事务
  目录项是另一个 inode → 新建文件要 fsync(dir)

【日志】descriptor + 新块 + commit；barrier=1 保证 commit 不会抢跑
        一次 rename ≈ 24KB 日志 + 16KB checkpoint ≈ 200× 放大

【fsync 家族】fsync=数据+元数据+FLUSH；fdatasync 省一次 inode；
             sync_file_range 只铺路；O_DIRECT 绕缓存但不持久
```

## 29.13 自检 3 题

**Q1.** 同一台机器上，`write(1 MB)` 的 p50 是 0.137 ms，`fsync` 是 10.08 ms。请解释这 73 倍差在哪，并说明为什么 `fsync` 返回后数据**仍然可能**丢。

<details><summary>答案</summary>

`write` 只做三件事：在页缓存里找到/分配 256 个页、`copy_from_user` 拷 1 MB、把页标脏并记账。137 µs 对应约 7.6 GB/s，就是内存拷贝带宽加上系统调用开销，**没有任何设备参与**。

`fsync` 要做完：把 256 个脏页组织成 bio → 提交到块层队列 → 设备执行写 → 发 `REQ_PREFLUSH` → 设备把自身 DRAM 缓存刷进介质 → 完成中断 → 唤醒进程。其中只有「设备写 + FLUSH」这一段是不可压缩的，10 ms 就是它的量级（HDD 上还在 `base/08` 的 8–13 ms 区间内）。

`fsync` 返回后仍可能丢，是因为「设备说刷完了」只是最近一层的话：盘上 DRAM 可能靠电容撑着、RAID 控制器有缓存、虚拟化层把写聚合在宿主页缓存里、云盘的三副本可能异步落盘。**`fsync` 买到的是「到设备为止」的承诺，不是「到介质为止」的事实**——这也是为什么本机 `O_DIRECT + fsync` 只要 0.191 ms，那个数不可能是物理写。
</details>

**Q2.** `open(O_CREAT|O_WRONLY)` + `write` + `close`，没有 `fsync`，掉电后得到一个 0 字节文件。请用 `data=ordered` 与 delalloc 解释，并说明 `fsync(file)` 之后为什么还要 `fsync(dir)`。

<details><summary>答案</summary>

`data=ordered` 的承诺是：**如果**某条元数据事务把数据块映射给这个文件，那么数据块必须先落盘。它没有承诺「write 过就生成那条事务」。ext4 默认延迟分配：`write` 时只在页缓存里放数据、在 inode 上标脏，块映射与 size 更新要等回写时才生成事务。如果掉电发生在回写之前，日志里只有「创建了这个 inode」的那条事务（它可能被 5 秒的 `commit=5` 定时器提交了），replay 出来就是一个 `size=0` 的 inode——文件存在、名字在、内容为空。

补上 `fsync(file)` 之后，数据与 size 都会落盘，但**目录项属于目录 inode 的元数据**，是另一次提交。新建文件、删除文件、`rename` 都需要再 `fsync(dir_fd)`；否则掉电后可能出现「内容在盘上，但目录里没有这个名字」，或者 `rename` 回退到旧名字。正确顺序：`write` → `fsync(file)` → `rename` → `fsync(dir)`。
</details>

**Q3.** 单次 `fsync` 是 10 ms，业务要求 5,000 TPS 的持久化提交。不改硬件，怎么做到？算一下批大小，并说明批大小为什么不能无限增大。

<details><summary>答案</summary>

单次提交的天花板是 `1 / 0.010 s = 99 次/秒`。要让 5,000 笔/秒都持久，必须让多笔共享同一次设备往返，即组提交：

```
所需批大小 N = 5000 ÷ 99 ≈ 51        （取 64 更稳）
吞吐 = N / fsync_latency = 64 / 0.010 = 6,400 /s
单笔延迟 ≈ 等待窗口 + 10 ms
```

批大小不能无限增大，卡在两处：① 日志字节数仍线性增长，批太大时一次 `fsync` 要写的字节变多，`fsync` 本身从 10 ms 涨上去，吞吐不再线性；② 延迟 = 攒批窗口 + `fsync`，窗口开大，P99 直接上去（64 笔时每笔平均多等半个窗口）。所以真实系统把它做成可调参数，并按「延迟预算 ÷ fsync 延迟」反推批大小，而不是拍一个大数。

顺带一句：这也是为什么「把 `fsync` 关掉换吞吐」是错的——它把「最多丢最近一次未提交事务」换成了「掉电丢 30 秒」，而正确解法本来就在手边。
</details>
