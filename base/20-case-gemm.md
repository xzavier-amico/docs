## 20.1 引子：同一个 O(n³)，为什么能差 100 倍

先把结论放在桌上：同一台机器、同一个 `C = A × B`、同样的 268,435,456 次浮点运算（2n³，n=512），从 **0.352 秒**降到 **0.00346 秒**，**101.7×**。没有换算法，没有换语言，没有用 GPU，甚至连乘法和加法的个数都没变。

变的是数据在**寄存器 → L1 → L2 → L3 → DRAM → 另一个核**之间被搬动的次数和形态。每一级优化都只回答一个问题：**这一层的数据，能不能在它还热的时候多用几次？**

| 级别 | 做法 | 这一级少搬了什么 | 瓶颈被推到哪里 |
| --- | --- | --- | --- |
| 0 | naive `i-j-k` | 没有；B 按列跨行读，点积只有一个累加器 | L1/L2 行访问 + 串行依赖 |
| 1 | 换成 `i-k-j` | 内层 `j` 连续，B 按行流，C 的 512 个元素互相独立 | 标量 ALU |
| 2 | 分块（cache + 寄存器） | B 面板从 L3 搬进 L2，C 的 4×4 子块从 L1 搬进寄存器 | 标量/SSE 算力 |
| 3 | `-O3 -march=native` + 手写 4×8 AVX2 | 一条指令搬 8 个 float，B 面板 128 KiB 常驻 L2 | 算力 / load 端口 |
| 4 | 2 线程 pthread，按行切 | 两份行块并行，两个核各自算自己的 C | 2 核算力（理论上限 2×） |
| 5 | GPU / 张量核 | 同一套分块在 shared memory / HBM 上重做一遍 | 带宽 / 启动开销（只讲推论） |

测量方法必须先交代，否则下面的数字没有出生证明：

| 项 | 值 |
| --- | --- |
| CPU | AMD EPYC 7K62，2 vCPU（2 个独立核，1 线程/核），2.6 GHz，AVX2 + FMA |
| Cache | L1d 64 KiB / L2 512 KiB / L3 16 MiB（每核） |
| 内存 | 1.9 GiB，可用约 0.5 GiB |
| 编译器 | gcc 12.2.0；基线 `-O2`，第 3 级起 `-O3 -march=native` |
| 计时 | 单线程用 `CLOCK_PROCESS_CPUTIME_ID`（CPU 时间，排除被宿主机挤掉的墙钟）；pthread 用 `CLOCK_MONOTONIC` |
| 稳定性 | `chrt -f 10` + `taskset -c 0,1`，每项取 5 次最小值 |
| 矩阵 | `float`，n=512，每个 1 MiB，三个共 3 MiB |

为什么要在 `chrt` 里跑？因为这台机器的 `load average` 常年在 5–10。不做实时调度、不绑核，两个线程会被邻居挤成 1.1×，你测到的是邻居的负载，不是自己的代码。下面的阶梯数字来自同一份程序、同一轮测量；块大小扫描与编译选项对照是另外两组同构测量，都在文中标了出处。**没有一个是抄来的**。

## 20.2 ① 它是什么：C = A×B 的三重循环

GEMM（General Matrix Multiply）就一句话：给定两个 n×n 的矩阵 A、B，算 C = A×B。每个 C 元素是 A 的一行与 B 的一列的点积：

```
C[i][j] = Σ(k=0..n-1) A[i][k] * B[k][j]
```

三重循环，n³ 次乘加，2n³ 次浮点运算。n=512 时是 **1.342 亿次乘加 / 2.684 亿次浮点运算**。如果机器每纳秒能做 1 次乘加，就是 0.134 秒；如果只能做 0.1 次，就是 1.34 秒。**复杂度只告诉你“算多少次”，不告诉你“每次算之前数据在哪”。**

最直白的写法：

```c
/* 台阶 0：naive i-j-k */
for (int i = 0; i < n; i++)
  for (int j = 0; j < n; j++) {
    float s = 0;
    for (int k = 0; k < n; k++)
      s += A[i*n + k] * B[k*n + j];   /* B：每步跳 n 个 float */
    C[i*n + j] = s;
  }
```

这段代码的内层是**一个点积**：`s` 是唯一的累加器，`s += ...` 形成一条串行依赖链。每次乘加要读两个源操作数：

- `A[i*n + k]`：沿 k 连续，硬件预取器能一路流过去；
- `B[k*n + j]`：k 每加 1，地址跳 `n×4 = 2048` 字节，是**跨行**的列访问；
- `C` 不在内层，它只在最后写一次。

所以“每次乘加要碰 2 次内存”不是夸张：一次 A 的 load，一次 B 的 load；C 被压在寄存器 `s` 里。问题在于第二次 load 的形态——它不是“再读一个数”，而是“跳到 2 KiB 之外再读一个数”。

## 20.3 ② 物理形态：三个矩阵、一条 cache line、一个 AI

### 20.3.1 行优先布局与那条 64 字节的线

C 语言的多维数组是行优先：`A[i][k]` 在地址 `A + (i*n + k)*4`，同一行的元素连续，跨一行跳 `n*4` 字节。n=512 时，一行是 **2 KiB**。

```
A（行优先）                    B（行优先）                    C（行优先）
i 行: A[i][0..n-1]             k 行: B[k][0..n-1]             i 行: C[i][0..n-1]
      连续 2 KiB                     连续 2 KiB                     连续 2 KiB

naive 内层:  A[i][k] 连续  →  B[k][j] 每步 +2 KiB（列）
ikj   内层:  B[k][j] 连续  →  C[i][j] 连续
```

一条 cache line 是 **64 字节 = 16 个 float**。这决定了三件事：

1. 读 A 的一行，16 个 float 共用一条 line，**空间局部性满分**；
2. 读 B 的一列，`B[k][j]` 和 `B[k+1][j]` 相差 2048 字节，**每次都是不同的 line**；一条 line 里的另外 15 个 float 要等到 `j+1..j+15` 才被用到，前提是这条 line 还能在 L1 里活到那时候；
3. 写 C 的一行，16 个 float 共用一条 line，**写合并（write-combining）友好**。

所以 naive 的慢不是“B 没被缓存”，而是“B 被切成 512 条互不相邻的线，每条线在一次列扫描里只用 1 个 float；预取器看到的不是一条流，而是 512 条跳跃的地址”。这也是为什么只把 `j` 和 `k` 换一下，后面会快 4 倍——同一份 B，从“列扫”变成“行流”。

### 20.3.2 三个矩阵装得下吗

n=512 时，每个矩阵 `512² × 4 B = 1 MiB`，三个共 **3 MiB**。这正好落在“L2 装不下、L3 装得下”的区间：

| n | 单矩阵 | 三个矩阵 | AI = n/6（FLOP/B） | 住在哪 |
| --- | --- | --- | --- | --- |
| 64 | 16 KiB | 48 KiB | 10.7 | L1/L2 |
| 256 | 256 KiB | 768 KiB | 42.7 | L2 边缘 |
| 512 | 1 MiB | 3 MiB | 85.3 | L3 |
| 1024 | 4 MiB | 12 MiB | 170.7 | L3 |
| 2048 | 16 MiB | 48 MiB | 341.3 | 超出 L3，落 DRAM |

这张表解释了两件事：**n 越大，GEMM 越算力密集**（AI 线性涨）；**n=512 时，B 单独 1 MiB，装不进 512 KiB 的 L2，但三个矩阵都装得进 16 MiB 的 L3**。于是“分块”在这一档的第一个作用不是省 DRAM，而是把 B 的工作集从 L3 搬到 L2。

### 20.3.3 算术强度 AI 的完整推导

算术强度（Arithmetic Intensity）定义为单位字节搬运所对应的浮点运算数：

```
AI = FLOPs / Bytes
```

对 n×n 的 GEMM：

- 浮点运算：每个 C 元素做 n 次乘加，n² 个元素，共 `2n³` FLOP；
- **compulsory 搬运**：A、B 各读一遍，C 写一遍，共 `3n²` 个 float = `3n² × 4` 字节；

所以

```
AI = 2n³ / (3n² × 4) = n / 6   （FLOP/B）
```

代入 n=512：`512 / 6 = 85.33 FLOP/B`。这个数字的含义是：**每从内存搬 1 字节，平均要做 85 次浮点运算**。如果机器的算力是 82 GFLOPS、内存带宽是 27 GB/s，那么带宽能支撑的算力上限是 `85.33 × 27 ≈ 2304 GFLOPS`，远高于 82——**GEMM 在理论上应该是算力密集的，不是带宽密集的**。

但这是 **compulsory AI**：它假设每个矩阵只从 DRAM 读一次。实际实现会把同一份 B 读 n 次、n/64 次、或者 8 次。把实际搬运量代进去，得到 **实现 AI（AI_eff）**：

```
AI_eff = 2n³ / 实际搬运字节
```

- naive / ikj：B 被每个 i 重新读一遍，实际约 `4n³ + 3×4n²` 字节，AI_eff ≈ **0.5**；
- cache 分块（BS=64，i 循环在块内）：B 只读 n/64 = 8 遍，A/C 也各被重读 n/64 遍，总搬运约 32 MiB，AI_eff ≈ **8**；
- AVX 的 BS 只切 k、不切 i，B 仍按每 4 行（ii）重读一遍，AI_eff 还是 ≈ **2**；它靠的是 k 循环变短后的 TLB/预取局部性，不是总流量下降；
- 理想 BLAS：A/B 各读一遍、C 写一遍，AI_eff ≈ **85**。

**整条阶梯干的同一件事，就是把 AI_eff 从 0.5 拉回 85。** 每拉一次，就少搬一批数据；少搬的那批数据，要么变成更快的 cache 命中，要么变成更多的算力时间。至于时间到底降不降，要看被少搬的那批数据是不是当前的瓶颈——这正是 §20.6 的 roofline 要回答的。

## 20.4 ③④ 走一遍：五级台阶与真实的改前/改后

### 20.4.1 开场实验：memcpy 的带宽天花板

在谈 GEMM 之前，先量一条最朴素的线：`memcpy`。它只做一件事——把 S 字节从 a 搬到 b。如果连这条线都上不去，谈“算力”没有意义。

```c
/* 1 MiB – 256 MiB，取 5 次最小值；GB/s 按“读 + 写”计 */
size_t sizes[] = {1<<20, 4<<20, 16<<20, 32<<20, 64<<20, 128<<20, 256<<20};
for (int q = 0; q < 7; q++) {
  size_t S = sizes[q];
  char *a = mmap(NULL, S, PROT_READ|PROT_WRITE, MAP_PRIVATE|MAP_ANONYMOUS, -1, 0);
  char *b = mmap(NULL, S, PROT_READ|PROT_WRITE, MAP_PRIVATE|MAP_ANONYMOUS, -1, 0);
  memset(a, 0x5a, S);
  double best = 1e9;
  for (int r = 0; r < 5; r++) {
    struct timespec t0, t1;
    clock_gettime(CLOCK_MONOTONIC, &t0);
    memcpy(b, a, S);
    clock_gettime(CLOCK_MONOTONIC, &t1);
    double dt = (t1.tv_sec - t0.tv_sec) + (t1.tv_nsec - t0.tv_nsec) * 1e-9;
    if (dt < best) best = dt;
  }
  printf("%4zu MB  %8.3f ms  %6.2f GB/s\n", S>>20, best*1e3, 2.0*S/best/1e9);
  munmap(a, S); munmap(b, S);
}
```

本机实测（`chrt -f 10 taskset -c 0`，取 5 次最小值）：

| 大小 | 时间 | 带宽（读+写） | 相对 1 MiB | 主要住在哪 |
| --- | --- | --- | --- | --- |
| 1 MiB | 0.038 ms | 55.5 GB/s | 1.00× | L2/L3 |
| 4 MiB | 0.153 ms | 54.8 GB/s | 0.99× | L3 |
| 16 MiB | 0.974 ms | 34.4 GB/s | 0.62× | L3 边缘 |
| 32 MiB | 2.219 ms | 30.2 GB/s | 0.54× | L3/DRAM |
| 64 MiB | 4.542 ms | 29.6 GB/s | 0.53× | DRAM |
| 128 MiB | 9.604 ms | 28.0 GB/s | 0.50× | DRAM |
| 256 MiB | 19.492 ms | 27.5 GB/s | 0.50× | DRAM |

三行结论：

1. **1 MiB 的 55 GB/s 是 cache 给的，256 MiB 的 27.5 GB/s 是 DRAM 给的**；容量涨了 256 倍，带宽反而掉了一半。
2. 拐点在 **16 MiB** 附近——正好是这颗核的 L3 容量。超过 L3 之后，曲线基本压平在 27–30 GB/s，这就是“内存带宽的天花板”。
3. 本机可用内存只有约 0.5 GiB，256 MiB 的双缓冲已经接近上限；再往上会触发 OOM，所以实验止步于 256 MiB。**这不是算法限制，是这台机器的物理限制。**

这条 27 GB/s 的线，后面会反复出现：GEMM 的每一次“少搬一次”，都是在和这条线（以及 L2/L3 更高的线）做交易。

### 20.4.2 台阶 0：naive i-j-k，0.352 秒

§20.2 的代码，`-O2`，n=512：

| 指标 | 值 |
| --- | --- |
| 耗时 | **0.352 s** |
| GFLOPS | **0.76** |
| 相对 naive | 1.00× |
| B 的实际流量 | 约 512 MiB（每个 i 读一遍 1 MiB） |
| 这 0.352 秒里的 B 带宽 | 512 MiB / 0.352 s ≈ **1.5 GB/s** |

注意最后一行：**1.5 GB/s 只有 DRAM 天花板的 5.5%**。所以 naive 慢**不是**因为带宽不够，而是因为：

- 内层点积只有一个累加器 `s`，`s += a*b` 是 4-cycle 的串行依赖，CPU 的乱序引擎想并行也找不到第二条独立的链；
- B 的列访问每步跳 2 KiB，512 条 line 轮流被碰，预取器无法把它识别成流；
- A 的行访问虽然是连续的，但一条 line 的 16 个 float 只用 1 个就被下一行打断。

这就是第一课：**“慢”至少有三种——搬不动（带宽）、算不动（算力）、等不到（延迟/依赖）。** 不看清楚就加缓存、换语言、上 GPU，都是在给错误的瓶颈买药。

### 20.4.3 台阶 1：i-k-j，只换三个循环的顺序

把 `j` 和 `k` 对调，内层从“点积”变成“axpy”（一个标量乘一行向量再加到 C 的一行）：

```c
/* 台阶 1：i-k-j，内层 j 连续 */
memset(C, 0, (size_t)n * n * sizeof(float));
for (int i = 0; i < n; i++)
  for (int k = 0; k < n; k++) {
    float a = A[i*n + k];
    for (int j = 0; j < n; j++)
      C[i*n + j] += a * B[k*n + j];   /* B、C 都是行连续 */
  }
```

| 指标 | 改前（naive） | 改后（ikj） | 变化 |
| --- | --- | --- | --- |
| 耗时 | 0.352 s | **0.0876 s** | **4.0×** |
| GFLOPS | 0.76 | **3.06** | 4.0× |
| 内层依赖 | 单个 `s`，串行 | 512 个独立的 `C[j]` | 乱序可并行 |
| B 的访问 | 列，每步 +2 KiB | 行，连续 2 KiB | 预取器可流 |
| B 的实际流量 | 约 512 MiB | 约 512 MiB（没变） | **流量没变，形态变了** |

这张表最重要的一行是最后一行：**B 的流量一点没少，还是 512 MiB；少的是“每次访问的代价”。** 同一份数据，从“512 条跳跃的线”变成“一条 2 KiB 的流”，预取器就能提前把下一段拉进 L1；同时内层 512 个 C 元素互相独立，CPU 可以同时发射多条 FMA。

0.0876 秒对应的 B 带宽是 `512 MiB / 0.0876 ≈ 6.1 GB/s`，仍然只有 DRAM 的 22%。所以这一级之后，瓶颈已经从“等内存”变成了“标量 ALU”：单核标量 FMA 峰值约 10.4 GFLOPS（2 FMA/cycle × 2 flop × 2.6 GHz），实测 3.06，是峰值的 29%。**下一步该做的是减少 ALU 旁边的内存动作，而不是继续省 DRAM 流量。**

### 20.4.4 台阶 2：分块，两级——cache 级与寄存器级

“分块”经常被当成一个词，其实是两个层级的同一件事：

1. **cache 级分块**：把 i、j、k 各切一块，让 A 块、B 块、C 块同时驻留 L1/L2；
2. **寄存器级分块**：把 C 的一个 4×4 子块放进 16 个寄存器，在 k 循环里只累加、不读回 C。

先看纯 cache 级。块大小 BS=64：

```c
/* 台阶 2a：三层 cache 分块，BS=64 */
for (int ii = 0; ii < n; ii += BS)
 for (int kk = 0; kk < n; kk += BS)
  for (int jj = 0; jj < n; jj += BS)
   for (int i = ii; i < ii+BS && i < n; i++)
    for (int k = kk; k < kk+BS && k < n; k++) {
      float a = A[i*n + k];
      for (int j = jj; j < jj+BS && j < n; j++)
        C[i*n + j] += a * B[k*n + j];
    }
```

| 指标 | 改前（ikj） | 改后（cache 分块 BS=64） | 变化 |
| --- | --- | --- | --- |
| 耗时 | 0.0876 s | **0.0532 s** | **1.65×** |
| GFLOPS | 3.06 | **5.05** | 1.65× |
| B 从 L3 读的次数 | n = 512 次 | n/64 = **8 次** | 64× 少搬 |
| 三个块的大小 | A/B/C 各 1 MiB | 各 64×64×4 = 16 KiB | 刚好进 L1 |

为什么这次有效？因为 B 的 64×64 面板只有 16 KiB，A 的 64×64 块 16 KiB，C 的 64×64 块 16 KiB，三个加起来 48 KiB，**刚好塞进 64 KiB 的 L1**。内层 j 循环的 64 个 float 全部命中 L1，B 从“每个 i 从 L3 拉一遍”变成“每 64 个 i 从 L3 拉一遍”。

块大小不是越大越好：BS=128 时三个块各 64 KiB，加起来 192 KiB，超过 L1，访问重新掉回 L2；BS=16 时内层太短，循环开销占比上升。**BS=32/64 是这一档的甜点，64 略好。**

但纯 cache 分块只解决了 B 的搬运，没有解决 C 的读改写：内层每个 `C[i*n+j] +=` 仍然是一次 load + 一次 store。下一步把 C 的 4×4 子块搬进寄存器：

```c
/* 台阶 2b：4×4 寄存器分块，k 再按 BS 切 */
for (int ii = 0; ii < n; ii += 4)
 for (int jj = 0; jj < n; jj += 4)
  for (int kk = 0; kk < n; kk += BS) {
    float c[4][4] = {{0}};
    int km = (kk + BS < n) ? kk + BS : n;
    for (int k = kk; k < km; k++) {
      float b[4] = {B[k*n+jj], B[k*n+jj+1], B[k*n+jj+2], B[k*n+jj+3]};
      for (int r = 0; r < 4; r++) {
        float a = A[(ii+r)*n + k];
        for (int s = 0; s < 4; s++) c[r][s] += a * b[s];
      }
    }
    for (int r = 0; r < 4; r++)
      for (int s = 0; s < 4; s++)
        C[(ii+r)*n + jj+s] += c[r][s];
  }
```

| 指标 | 改前（cache 分块） | 改后（4×4 寄存器） | 变化 |
| --- | --- | --- | --- |
| 耗时 | 0.0532 s | **0.0303 s** | **1.76×** |
| GFLOPS | 5.05 | **8.85** | 1.76× |
| 每 16 次 FMA 的 C 访问 | 16 次 load + 16 次 store | **0 次**（全在寄存器） | 省掉 32 次 |
| 每次 FMA 的 L1 访存 | ≈3.0 次（1/64 A + 1 B + 2 C） | **0.5 次**（1/4 A + 1/4 B） | **6× 少碰 L1** |

这一级的账最干净：**16 个 FMA 只需要 4 个 A load + 4 个 B load，C 在 k 循环里一次都不读回。** 内层 `s` 循环的 trip count 固定为 4，GCC 在 `-O2` 下就把它自动向量化成 SSE（4 个 float 一条指令），所以 8.85 GFLOPS 已经接近“标量 + SSE”这一档的天花板。两级分块合起来，从 ikj 的 0.0876 秒降到 0.0303 秒，**2.9×**。

### 20.4.5 台阶 3：向量化，一条指令搬 8 个 float

4×4 的 SSE 只有 4 个 float 宽。AVX2 有 8 个 float 宽，还带 FMA（乘加一条指令）。把 4×4 扩成 **4 行 × 8 列**：

```c
/* 台阶 3：4×8 AVX2 微内核，BS=64 */
for (int ii = 0; ii < n; ii += 4)
 for (int kk = 0; kk < n; kk += BS)
  for (int jj = 0; jj < n; jj += 8) {
    __m256 c0 = _mm256_setzero_ps(), c1 = c0, c2 = c0, c3 = c0;
    int km = (kk + BS < n) ? kk + BS : n;
    for (int k = kk; k < km; k++) {
      __m256 b = _mm256_loadu_ps(B + k*n + jj);
      c0 = _mm256_fmadd_ps(_mm256_set1_ps(A[(ii+0)*n + k]), b, c0);
      c1 = _mm256_fmadd_ps(_mm256_set1_ps(A[(ii+1)*n + k]), b, c1);
      c2 = _mm256_fmadd_ps(_mm256_set1_ps(A[(ii+2)*n + k]), b, c2);
      c3 = _mm256_fmadd_ps(_mm256_set1_ps(A[(ii+3)*n + k]), b, c3);
    }
    _mm256_storeu_ps(C + (ii+0)*n + jj, c0);
    _mm256_storeu_ps(C + (ii+1)*n + jj, c1);
    _mm256_storeu_ps(C + (ii+2)*n + jj, c2);
    _mm256_storeu_ps(C + (ii+3)*n + jj, c3);
  }
```

（这里假设 n 是 4 和 8 的倍数；通用版要在 `ii+4`、`jj+8` 越界时补边界。）

| 指标 | 改前（4×4 SSE） | 改后（4×8 AVX2） | 变化 |
| --- | --- | --- | --- |
| 耗时 | 0.0303 s | **0.00663 s** | **4.6×** |
| GFLOPS | 8.85 | **40.5** | 4.6× |
| 每次 k 迭代的 FMA | 16 次（SSE 4 宽） | **32 次**（AVX 8 宽 × 4 行） | 2× 宽度 |
| C 的驻留 | 16 个 SSE 寄存器 | 4 个 ymm 累加器 | 寄存器压力更低 |

这一级把“每一条指令搬多少数据”从 4 个 float 提到 8 个 float，同时用 FMA 把乘和加合成一条。40.5 GFLOPS 是单核 FMA 峰值 82 GFLOPS 的 **49%**——还剩一半，卡在 load 端口、循环开销和 L2 到 L1 的 B 面板搬运上。

如果只改编译选项、不改代码，编译器能做到多少？把台阶 1 的 `i-k-j` 用 `-O3 -march=native` 重新编译：

| 版本 | 耗时 | GFLOPS | 说明 |
| --- | --- | --- | --- |
| `i-k-j`，`-O2` | 0.0876 s | 3.06 | 标量 |
| `i-k-j`，`-O3 -march=native` | **0.01125 s** | **23.9** | 编译器自动向量化，7.8× |
| 手写 4×8 AVX2，`-O3 -march=native` | **0.00663 s** | **40.5** | 再快 1.70× |

编译器确实会向量化，而且白送了 7.8×。用 `objdump` 能直接看到证据：

```bash
$ gcc -O2 -pthread -o gemm gemm.c
$ gcc -O3 -march=native -pthread -o gemm_native gemm.c
$ objdump -d gemm        | grep -cE 'vfmadd[0-9]+ps'   # 5
$ objdump -d gemm_native | grep -cE 'vfmadd[0-9]+ps'   # 35
```

`-O2` 的 5 条 packed FMA 全部来自手写 AVX kernel；`-O3 -march=native` 的 35 条里，多出来的 30 条来自编译器自动向量化的循环（主要是 `i-k-j` 的内层）。**但编译器不会替你选块大小**：同一个手写 kernel，只改 BS：

| BS | 耗时 | GFLOPS | B 面板大小 | 相对 BS=512 |
| --- | --- | --- | --- | --- |
| 512（不分块） | 0.00984 s | 27.3 | 1 MiB | 1.00× |
| 256 | 0.00848 s | 31.7 | 512 KiB | 1.16× |
| 128 | 0.00784 s | 34.2 | 256 KiB | 1.25× |
| 64 | **0.00637 s** | **42.2** | **128 KiB** | **1.55×** |
| 32 | 0.00649 s | 41.4 | 64 KiB | 1.52× |

（这张扫描表用单独的分块测试程序；BS=64 的 42.2 与阶梯表的 40.5 差 4%，属测量批次差异。）

BS=512 时，k 循环要跨 512 行、256 个页，B 的每次 jj 切片都在 2 KiB 步长上跳，预取器和 TLB 都更容易失手；BS=64 时，k 循环只有 64 行，一个 64 行的 B 面板是 128 KiB，落在 L2，64 条步长为 2 KiB 的流能被预取窗口覆盖。**同一份算术、同一台机器，只改一个块大小，1.55×。** 注意：这里的 BS 只切 k、不切 i，B 的总流量并没有从 128 MiB 降下来；降的是**每一次读的局部性代价**。这就是分块在向量化之后才兑付的证据：标量阶段它被 ALU 掩盖，向量化把 ALU 抬高之后，B 的搬运质量才浮出水面。

### 20.4.6 台阶 4：2 线程，按行切

C 的每一行只依赖 A 的对应行和整个 B，行与行之间没有写冲突。最自然的切法是**按行切**：线程 0 算 `[0, n/2)`，线程 1 算 `[n/2, n)`。

```c
typedef struct { int n, lo, hi, BS; const float *A, *B; float *C; } arg_t;

static void *worker(void *p) {
  arg_t *a = p;
  gemm_avx_range(a->A, a->B, a->C, a->n, a->lo, a->hi, a->BS);
  return NULL;
}

int chunk = (n + 1) / 2;
arg_t args[2] = {
  {n, 0,     chunk, BS, A, B, C},
  {n, chunk, n,     BS, A, B, C},
};
pthread_t th[2];
for (int t = 0; t < 2; t++) pthread_create(&th[t], NULL, worker, &args[t]);
for (int t = 0; t < 2; t++) pthread_join(th[t], NULL);
```

（`gemm_avx_range` 就是台阶 3 的 4×8 kernel，只是把 `ii` 的起点/终点换成 `lo/hi`。）

| 指标 | 改前（1 线程） | 改后（2 线程） | 变化 |
| --- | --- | --- | --- |
| 耗时 | 0.00663 s | **0.00346 s** | **1.92×** |
| GFLOPS | 40.5 | **77.6** | 1.92× |
| 理论 2 核峰值 | 164 GFLOPS | 164 GFLOPS | 实测达 47% |
| 数据竞争 | 无（行不相交） | 无（行不相交） | 不需要锁 |

为什么能接近 2×？因为两个线程写的是**不同的 C 行**，B 是只读的、被两个核共享（L3 里一份），A 也是只读的。只要行边界按 64 字节对齐（n=512 时 chunk=256 行，边界偏移 512 KiB，天然对齐），就不会出现伪共享。**如果按列切**，两个线程会在 C 的同一行上写相邻的列，边界那条 cache line 被两个核反复抢，性能会掉一个档次——这就是 `base/13` 里的 false sharing。

实测 1.92× 而不是 2.00×，差的 4% 是 pthread 创建/汇合、以及两个核争 L2/L3 的钱。这个数字还有一个前提：**必须在 `chrt` 里测**。在同一台机器上不加实时调度，两个线程会被宿主机的邻居挤成 1.1×；那不是你的代码不并行，是你没拿到第二个核。

### 20.4.7 台阶 5：GPU 与张量核，只讲推论

GPU 不改变这条推论的任何一个字，它只是把“层”换了一套名字：

| CPU 这一套 | GPU 那一套 | 同样的角色 |
| --- | --- | --- |
| 寄存器 | 寄存器 / 每线程私有 | 最快，容量最小 |
| L1 / L2 | shared memory / L1 | 软件显式管理的块 |
| L3 | L2 | 全片共享 |
| DRAM | HBM | 容量最大，带宽被全片分 |

CPU 上的 4×8 微内核，在 GPU 上会变成一个 warp 的 tile；CPU 上的 BS=64 面板，在 GPU 上会变成 shared memory 里的一个 64×64 块；CPU 上的 `i-k-j`，在 GPU 上会变成“每个线程算一个 C 元素、沿 k 读 A 的一列和 B 的一行”。**张量核（Tensor Core）则是把“寄存器分块”做成硬件：一条 MMA 指令一次算 16×16×16 或 8×8×4 的乘加，相当于把 4×4 的寄存器 tile 放大到 16×16，并且把 k 的 16 步压进一条指令。** 它之所以快，不是因为“GPU 主频高”，而是因为它在同样的时钟里搬更少的数据、做更多的乘加。

但“GPU 一定快”是假的，尤其是小矩阵。做一个量级估算（**以下是推论，不是本机实测**）：

- 512×512 的三个 float 矩阵共 3 MiB。走 PCIe 以 10 GB/s 量级算，单程约 **0.3 ms**；
- kernel 启动开销约 **5–10 μs**；
- GPU 上 2.68 亿 FLOP，即使按 100 TFLOPS 量级算，也只有 **2.7 μs**；
- 合计约 **0.31 ms**，对比本机 CPU 的 3.46 ms，约 **11×**，不是 1000×。

如果矩阵缩到 64×64，三个矩阵只有 48 KiB，传输约 5 μs，启动 5 μs，GPU 计算不到 1 μs；而 CPU 用 BLAS 可能只要十几 μs——**GPU 反而可能更慢**。所以 §18 的判据在这里落地：GPU 的收益来自“同一段代码作用于成千上万份独立数据”，当数据量小到启动和传输占主导时，这条收益就被吃光了。

### 20.4.8 阶梯总表与改前/改后

把五级放在同一张表里（n=512，单线程用 CPU 时间，2 线程用墙钟 + `chrt`）：

| 级别 | 关键改动 | 耗时 | GFLOPS | 相对 naive | 相对上一级 | 瓶颈 |
| --- | --- | --- | --- | --- | --- | --- |
| 0 | naive `i-j-k` | 0.352 s | 0.76 | 1.00× | — | 列访问 + 点积依赖 |
| 1 | `i-k-j` | 0.0876 s | 3.06 | 4.02× | 4.02× | 标量 ALU |
| 2 | cache 分块 + 4×4 寄存器 | 0.0303 s | 8.85 | 11.6× | 2.89× | 标量/SSE 算力 |
| 3 | `-O3 -march=native` + 4×8 AVX2 | 0.00663 s | 40.5 | 53.1× | 4.57× | 算力 / load 端口 |
| 4 | 2 线程按行切 | 0.00346 s | 77.6 | **101.7×** | **1.92×** | 2 核算力 |

“改前/改后”两列，单独再列一次，方便直接贴进实验报告：

| 改法 | 改前 | 改后 |
| --- | --- | --- |
| 循环顺序 `i-j-k` → `i-k-j` | 0.352 s / 0.76 GFLOPS | 0.0876 s / 3.06 GFLOPS |
| 加 cache 分块（BS=64） | 0.0876 s / 3.06 | 0.0532 s / 5.05 |
| 加 4×4 寄存器分块 | 0.0532 s / 5.05 | 0.0303 s / 8.85 |
| 换 `-O3 -march=native` + 4×8 AVX2 | 0.0303 s / 8.85 | 0.00663 s / 40.5 |
| 2 线程按行切 | 0.00663 s / 40.5 | 0.00346 s / 77.6 |
| 只加 `-O3 -march=native`，不改代码（对照） | 0.0876 s / 3.06 | 0.01125 s / 23.9 |
| 纯 cache 分块、不做寄存器分块（对照） | 0.0876 s / 3.06 | 0.0532 s / 5.05 |

最后两行是“对照组”，它们说明了两件事：**编译器的确能白送 7.8×；但纯 cache 分块只值 1.65×，真正把 C 从 L1 搬进寄存器的那一步，才让分块的总收益到 2.89×。**

## 20.5 ⑤ 它证伪了谁

### ① “优化就是换更快的算法”

整篇的 FLOP 数一次没变：`2n³ = 268,435,456`。乘法和加法的个数一模一样，连浮点结果的量级都没变。102× 全部来自**数据在哪、被搬了几次、能不能并行**。如果“优化 = 换算法”，那这 102× 就无法解释；如果“优化 = 减少数据搬运 + 提高并行度”，每一级都能对上号。

这也是为什么面试里“快排 O(n log n) 比冒泡 O(n²) 快”只回答了复杂度，没回答“为什么同样的 O(n log n)，有的实现快 5 倍”——后者是 cache、分支预测、SIMD 的账，不是复杂度的账。

### ② “内存/显存越大越好”

同一个 `memcpy`，1 MiB 跑 55.5 GB/s，256 MiB 跑 27.5 GB/s。**容量涨了 256 倍，带宽反而掉了一半。** 大内存解决的是“装不装得下”，不解决“喂不喂得饱”。GEMM 的 n=512 只用了 3 MiB，连 L3 都没出去；它的瓶颈从头到尾不是容量，而是“同一份 B 被搬了几遍”。

工程上的翻译：看到“内存不够”就加内存，看到“内存带宽不够”要改的是**访问形态**（分块、连续化、复用寄存器），不是买更大的条子。这两件事经常被混为一谈。

### ③ “GPU 一定快”

见 §20.4.7 的量级账：512×512 的 3 MiB 数据，传输 + 启动约 0.3 ms，GPU 计算只有几 μs；对比 CPU 的 3.46 ms，约 11×，不是 1000×。矩阵再小，传输和启动会吃掉全部收益。GPU 快的前提是**数据量足够大、并行度足够高、传输占比足够低**；离开这三条，“GPU 一定快”就是一句没有前提的口号。

### ④ “`-O3` 会自动搞定”

`-O3 -march=native` 确实把 `i-k-j` 从 3.06 拉到 23.9 GFLOPS，白送 7.8×；但它搞不定三件事：

1. **块大小**：同一个 AVX kernel，BS=512 是 27.3 GFLOPS，BS=64 是 42.2 GFLOPS，1.55× 的差距来自一个编译器不会搜索的参数；
2. **打包（packing）**：BLAS 会把 A/B 重排成连续的 panel，让微内核的 load 对齐、TLB 友好；编译器不会替你重排整个矩阵；
3. **线程与调度**：2 线程的 1.92× 不是编译选项给的，是程序设计给的。

所以正确的说法是：**`-O3` 把地板抬高了，但天花板仍要人推。** 先用 `-O3 -march=native` 拿到白送的向量化，再决定要不要手写微内核、要不要分块、要不要多线程——顺序反了，就会在错误的地方花时间。

### ⑤ 加一条：“多线程一定线性”

本机 2 线程是 1.92×，接近线性；但这是在同一台机器、同一轮 `chrt` 测量、行边界对齐的前提下。换到共享宿主机、不加绑核、或者按列切，1.92× 会掉到 1.1× 甚至更低。**线程的收益不是“核数”，是“你能不能同时拿到两个核、并且不让它们抢同一条 cache line”。**

## 20.6 roofline：你在哪条线上

经典 roofline 只有两条线：一条水平的算力天花板，一条斜的带宽线（`GFLOPS = AI × 带宽`）。本机的四条基准是：

- 单核算力：**82 GFLOPS**（FMA 微基准实测 82.3）；
- 双核算力：**164 GFLOPS**；
- DRAM 带宽：**27 GB/s**（memcpy 256 MiB 实测）；
- L3 带宽：**约 55 GB/s**（memcpy 1 MiB 实测）。

对 GEMM，算法 AI = n/6 = 85 FLOP/B。把 85 代进 DRAM 线：`85 × 27 = 2295 GFLOPS`，远高于 82。所以**在 DRAM 这一级，GEMM 应该稳稳落在算力线上**。这张图的拐点在 `82/27 ≈ 3.0 FLOP/B`，85 在拐点右边很远。

但实测的七个点不是一条线能解释的。先看“离算力天花板还有多远”：

| 实现 | 实测 GFLOPS | 占 1 核 82 的比例 | 占 2 核 164 的比例 | 卡在哪 |
| --- | --- | --- | --- | --- |
| naive | 0.76 | 0.9% | 0.5% | 列访问延迟 + 串行依赖 |
| ikj | 3.06 | 3.7% | 1.9% | 标量 ALU（峰值 10.4） |
| cache 分块 BS=64 | 5.05 | 6.2% | 3.1% | 标量/SSE 算力 |
| 4×4 寄存器 | 8.85 | 10.8% | 5.4% | SSE 算力 + L1 访存 |
| AVX BS=512 | 27.3 | 33.3% | 16.6% | L2↔L3 局部性 |
| AVX BS=64 | 40.5 | **49.4%** | 24.7% | 算力 / load 端口 |
| 2 线程 AVX | 77.6 | — | **47.3%** | 2 核算力 |

再看“带宽线有没有可能成为瓶颈”。把每个实现的 AI_eff 和两条带宽线放在一起：

| 实现 | AI_eff | L3 线给的上限 | DRAM 线给的上限 | 实测 | 结论 |
| --- | --- | --- | --- | --- | --- |
| naive | ≈0.5 | 27.5 | 13.5 | 0.76 | 连带宽线都没摸到 → 延迟/依赖 |
| ikj | ≈0.5 | 27.5 | 13.5 | 3.06 | 带宽线在 27.5，但标量 ALU 只有 10.4 → 算力先到 |
| cache 分块 BS=64 | ≈8 | 440 | 216 | 5.05 | 带宽线在天上 → 纯算力 |
| 4×4 寄存器 | ≈1 | 55 | 27 | 8.85 | DRAM/L3 线很低，但它绑定的是 L1/寄存器 → 算力 |
| AVX BS=512 | ≈2 | 110 | 54 | 27.3 | L3 线 110 高于算力线 82，DRAM 线 54 低于 82；实测 27.3 两边都没到 → L2↔L3 局部性 |
| AVX BS=64 | ≈2 | 110 | 54 | 40.5 | 仍低于算力线 → 算力（49%） |
| 2 线程 AVX | ≈2 | 110（共享） | 54 | 77.6 | 算力线 164，实测 47% |

这张表说明了一个反直觉的事实：**AI_eff 低的实现不一定慢，AI_eff 高的实现也不一定快**。4×4 寄存器的 AI_eff 只有约 1（它按 4×4 的 tile 重读 A/B），却比 AI_eff≈8 的 cache 分块更快——因为它把 C 留在了寄存器，绑定的是 L1/寄存器的账，而不是 DRAM 的账。**roofline 必须按“当前绑定层”来画；拿 DRAM 线去解释寄存器分块，就像拿高速公路的限速去解释停车场的倒车。**

示意图（位置关系真实，比例不严谨）：

```
GFLOPS
 164 |--------------------------------  2 核算力上限
  82 |--------------------------------  1 核算力上限
     |                          ● MT2 77.6
     |                    ● AVX64 40.5
     |              ● AVX512 27.3
     |      ● t44 8.85   ● cache 5.05
     |  ● ikj 3.06
     |● naive 0.76
     +--+--------+--------+--------+---→ AI_eff (FLOP/B)
       0.5       2        8       85
```

- **naive 和 ikj 在图的左下角**：AI_eff≈0.5，带宽线给的上限只有 27.5（L3）/13.5（DRAM），实测 0.76/3.06，连这条线都没摸到——它们卡在延迟和串行依赖上；
- **cache 分块和 4×4 寄存器在中间**：cache 分块的 AI_eff 被 i 分块推到 8，带宽线已经高到不相关，卡在标量/SSE；4×4 寄存器把 C 搬进寄存器，绑定层从 L1 挪到了寄存器，roofline 的坐标已经不是 DRAM 了；
- **AVX 和 MT2 在右边**：AI_eff≈2（因为 AVX 的 BS 只切 k、不切 i，B 的总流量没降），但带宽线 110 已经高于算力线 82，所以它们贴着算力线跑，40.5/77.6 分别是 82/164 的 49%/47%。

结论只有一句：**实测永远落在“算力、当前 cache 层的带宽、DRAM 带宽、延迟”这四个上限的最低那一条上。** 每一级优化做的事，要么是把 AI_eff 往右推（少搬），要么是把算力上限往上抬（SIMD/多核/张量核），要么是把绑定层从慢的那一级挪到快的那一级（寄存器分块）。如果推错了方向——比如在 ikj 已经算力受限时继续省 DRAM 流量——时间不会变，甚至会更慢（纯 cache 分块在有些编译形态下就不如 ikj）。

最后给一个边界：n=512 的三个矩阵只有 3 MiB，全程待在 L3 里，所以 **DRAM 27 GB/s 这条线从头到尾没被碰到**。等到 n≥2048（三个矩阵 48 MiB > L3），DRAM 线才会变成主角；那时分块的第一目的才是“省 DRAM 流量”，而不是本篇的“把 B 从 L3 挪进 L2”。同一套分块，在不同 n 下服务的是不同的层——这就是为什么不能背“分块一定快”，只能问“现在哪一层最慢”。

## 20.7 工程意义：为什么 BLAS 比你手写快

本机手写的最好成绩是 2 线程 77.6 GFLOPS，而 2 核 FMA 峰值是 164 GFLOPS，**效率 47%**。OpenBLAS / MKL / BLIS 这类库在同一台机器上通常能把峰值吃得更满（公开资料的经验值约 80% 上下，不是本机实测），也就是 130 GFLOPS 量级，差不多是手写版的 **1.7×**。这 1.7× 从哪来？不是魔法，是五件手写版没做的事：

| 库做的事 | 手写版缺了什么 | 值多少 |
| --- | --- | --- |
| **打包（packing）**：把 A/B 重排成连续的 panel | 我们的 kernel 直接读原矩阵，行间有 2 KiB 的跳变，TLB 和预取都不友好 | 10–30% |
| **多级分块**：L1/L2/L3 各自一块，块大小按 CPUID 探测 | 我们只手调了 BS=64，且没按 L2/L3 容量自适应 | 10–20% |
| **微内核**：每个 ISA 一份手写汇编，寄存器排到极限 | 我们的 4×8 还有 load 端口和循环开销，峰值 49% | 20–40% |
| **多线程 + 调度**：按 NUMA/缓存亲和分块 | 我们只做了最简单的按行二分 | 接近线性，但大矩阵才明显 |
| **CPU 派发**：AVX-512/AVX2/NEON 各走各的 | 我们只写了 AVX2，换台机器就退化 | 决定“能不能跑” |

所以“为什么 numpy/torch 的 `matmul` 比自己写循环快 100×”有两个原因，别混在一起：

1. **它调的是 BLAS**，不是 Python 循环。`np.matmul` 对 float32/float64 会进 OpenBLAS/MKL 的 GEMM，走的就是上面五件套；
2. **Python 三层循环的解释器开销**。134M 次内层迭代，每次哪怕只有 50 ns 的解释器成本，也是 **6.7 秒**；即使按本机手写的 3.5 ms 算，也差 **1900×**（真正的 BLAS 只会更快）。这个 1900× 里，大部分是“解释器 vs 机器码”，不是“算法 vs 算法”。

什么时候该自己写？

- **学习/验伪**：像本篇这样，为了看清每一层的账；
- **特殊布局/融合**：GEMM + bias + ReLU + 转置，或者权重是稀疏/量化的，BLAS 的接口不够用；
- **固定小尺寸**：比如 4×4、8×8 的批量小矩阵，BLAS 的调用/调度开销可能比计算还大；
- **没有 BLAS 的嵌入式环境**。

其余情况——尤其是“我写个三重循环试试”——**先调库，再谈手写**。库已经把你在这篇文章里看到的每一级都做完了，而且做得更细。

## 20.9 一页速记

```
【一句话】
GEMM 的 100× 不是算出来的，是搬出来的；每一级只做一件事——
让同一份数据在被用掉之前，少搬一次。

【六个数字 · n=512 · 本机 2 核】
  naive i-j-k        0.352 s    0.76 GFLOPS
  i-k-j              0.0876 s   3.06 GFLOPS    4.0×
  分块（cache+4×4）  0.0303 s   8.85 GFLOPS    2.9×
  AVX2 4×8           0.00663 s  40.5 GFLOPS    4.6×
  2 线程             0.00346 s  77.6 GFLOPS    1.92×
  合计               101.7×     单核峰值 82 / 双核 164

【三个天花板】
  算力：1 核 82 GFLOPS，2 核 164 GFLOPS
  L3：约 55 GB/s（1 MiB memcpy）
  DRAM：约 27 GB/s（256 MiB memcpy）
  实测 = min(算力, AI_eff × 带宽, 延迟)

【两个 AI】
  算法 AI = n/6 = 85 FLOP/B        → 理论上算力密集
  实现 AI_eff = 2n³ / 实际搬运     → ikj 0.5，cache 分块 8，AVX 约 2
  优化的方向：把 AI_eff 往 85 推，或者把算力上限往上抬

【三个判据】
  1. 先看瓶颈：搬不动、算不动、还是等不到？
  2. 分块有两级：cache 级让 B 少搬，寄存器级让 C 不搬
  3. 编译器能向量化，但选不了块大小、不会打包、不会开线程

【一条边界】
  GPU 只在“数据够大、并行够多、传输占比够低”时赢；
  512×512 的 3 MiB，传输 + 启动约 0.3 ms，收益只有 10× 量级。
```

## 20.10 自检 3 题

**Q1.** n=1024 时，算法 AI 是多少？三个矩阵共多大、住在哪一级 cache？如果你把 §20.4.5 的 AVX kernel 直接拿过去、仍然用 BS=512（不分块），预测它会比 BS=64 快还是慢，为什么？

<details><summary>答案</summary>

AI = n/6 = 1024/6 ≈ **170.7 FLOP/B**。每个矩阵 `1024² × 4 B = 4 MiB`，三个共 **12 MiB**，仍然装得进 16 MiB 的 L3，但远远超过 512 KiB 的 L2。

BS=512（不分块）会**更慢**。B 面板 = 512 行 × 1024 列 × 4 B = **2 MiB**，装不进 512 KiB 的 L2；k 循环一次跨 512 行、256 个页，预取器和 TLB 都容易失手。BS=64 时 k 循环只有 64 行，面板 `64 × 1024 × 4 = 256 KiB`，刚好进 L2，TLB 也只压 32 个页，局部性好得多。

注意一个容易说错的点：在 `ii` 最外层的循环顺序下，B 的**总 L3 流量**两边都是 `(n/4) × 4 MiB = 256 × 4 MiB = 1 GiB`，BS=64 降的是**每次读的局部性代价**，不是总流量。要把总流量也降 16 倍，得把 `kk` 放到 `ii` 外面，让一个 B 面板被所有 ii 复用——那是 BLAS 的 packing / loop order 做的事，也是“分块”和“重排”容易混淆的地方。

</details>

**Q2.** 2 线程按行切能到 1.92×。如果改成按列切（线程 0 算 C 的左半列，线程 1 算右半列），预计会发生什么？如果 n 不是 16 的倍数，行切又要注意什么？

<details><summary>答案</summary>

按列切会让两个线程写 C 的**同一行**的相邻列。C 是行优先，同一行的相邻列共享同一条 64 B cache line；线程 0 写左半、线程 1 写右半，边界那条 line 会被两个核反复失效、反复同步，这就是 **false sharing**。轻则掉 2–5×，重则比单线程还慢。按行切时，两个线程写的是不同的行，行与行之间至少隔 2 KiB（n=512），不会共享 line，所以没有这个问题。

行切也要注意边界：如果 `chunk` 不是 16 个 float 的倍数（64 B / 4 B = 16），两个线程的边界会落在同一条 line 里，仍然会伪共享。正确做法是把 `chunk` 向上取整到 16 的倍数，或者让第二个线程从 `chunk` 行开始、第一个线程到 `chunk` 行结束，并保证 `chunk % 16 == 0`。n=512 时 chunk=256，天然是 16 的倍数，所以本机没有这个问题。

</details>

**Q3.** 你说 GPU 在 512×512 上大约快 11×，不是 1000×。那什么情况下 GPU 会明显赢？请用“计算量 / 传输量”的比值给出一个判据，并说明为什么大模型的 GEMM 属于赢的那一边。

<details><summary>答案</summary>

判据是 **每搬 1 字节能做多少 FLOP**，也就是 AI_eff，和 GPU 的 roofline 拐点比较。GPU 的算力上限很高（张量核把 FP16 峰值抬到 CPU 的 1–2 个数量级），但 HBM 的带宽也有上限；roofline 的拐点是 `F / BW`，GEMM 要压在算力线上，必须让 `AI = n/6 > F/BW`，也就是：

```
n > 6 × (F / BW)
```

用公开规格的量级代入（**不是本机实测**）：FP16 张量核峰值 `F ≈ 1000 TFLOPS`，HBM 带宽 `BW ≈ 3 TB/s`，`F/BW ≈ 333 FLOP/B`，于是 `n > 6 × 333 ≈ 2000`。512 的 AI 只有 85，远低于拐点，所以在 GPU 上它是**带宽/传输受限**，不是算力受限——这解释了为什么它只快 10× 量级，而不是 1000×。大模型的 GEMM 是 **大 n × 大 batch**：n 是几千（hidden size），AI 过千，batch 又把权重复用放大，传输只占一次，计算占绝对主导——这时 GPU 的算力线才真正兑现，张量核的 1–2 个数量级优势才变成墙钟时间。

如果只看单次传输，还可以用 `传输时间 / 计算时间 ≈ 6F/(n × BW_link)` 做粗判；但那个式子里的 `BW_link` 是 PCIe 的 10 GB/s 量级，不是 HBM 的 3 TB/s，两者不要混用。**算力线看 HBM，启动/传输看 PCIe**——这是 GPU 版本的两层账。

</details>
