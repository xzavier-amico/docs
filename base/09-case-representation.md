## 09.1 引子：四起事故，同一条裂缝

四个教学场景的共同点不是「不会用浮点」或「不懂 UTF-8」，而是排查时没有先把数值与其表示区分开：

> **在看到「值不对」的那一刻，没有人打印位模式。所有人都在改代码。**

而「值」是最表层的东西。同一个 8 字节，可以是 `0x3FB999999999999A`（`0.1`）、可以是 `4,611,686,018,427,387,904`（把它当整数读）、可以是两个 `int32`、可以是 `"你好"` 的前半截。**只要打印出位模式，四起事故都能在 5 分钟内定位；不打印，它们都会伪装成「偶发的、环境相关的、很难复现的 bug」。**

| # | 事故 | 表面症状 | 真实层 | 一句话根因 |
| --- | --- | --- | --- | --- |
| ① | 对账差 0.07 元 | 「某几笔金额算错了」 | 浮点 ulp（`float`）+ 量级 | `float` 尾数不足 24 位量级，累加误差随笔数增长 |
| ② | 统计值偏 8.79% | 「监控数字和大盘对不上」 | 浮点 ulp（更严重） | `float` 只有 24 位尾数，百万级累加后 ulp 大于单次增量 |
| ③ | 用户昵称变乱码 | 「前端渲染问题 / 字体问题」 | 编码边界 | 按**字节**截断 UTF-8，切开了多字节序列 |
| ④ | 跨机 RPC 解析错位 | 「对端服务有 bug」 | 对齐 + 字节序 + 位域 | 把内存布局当线路格式，padding 与端序双双违约 |

四起事故都能用同一句话归类：**「你看到的值」和「机器里的位」不是一回事，而中间那层解释权，被某一方擅自改掉了。**

## 09.2 事故①：金额用浮点累加，日终对账差 0.07 元

### 现象

某结算系统日终对账，`sum(明细金额)` 与「按订单号重新汇总」差 **0.07 元**。数据库里金额列是 `DECIMAL(18,2)`，问题只出在**中间计算**：一个服务为了「快速汇总十万行」，把金额读成 `float`（当时为了省内存，数组用 `float[]` 存了 50 万条流水）。

复盘时间线：

| 时刻 | 事件 |
| --- | --- |
| 21:40 | 对账任务报警，差额 0.07 元，笔数 1 笔 |
| 22:15 | 怀疑某笔订单重复入账，查了 90 分钟 |
| 23:50 | 把明细导出到 CSV，用 Python 一列求和，**结果正确** |
| 次日 01:20 | 换 Java 服务的浮点路径重算，误差复现 |
| 次日 02:40 | 发现用的是 `float[]` 而非 `double[]`；改成 `double` 后差额消失 |
| 次日 03:30 | 但仍不能解释「为什么以前没事」：查历史，此前最大单日只有 3 万笔 |
| 损失 | 对账阻塞 6 小时，财务未结账；按流程补一笔 0.07 元人工调整 |

### 位级推导（这是本篇的支点，也是本文被实验修正过的地方）

先给结论，因为它与「直觉」相反：

> **`double` 累加 5 万笔两位小数金额，误差只有 4.5×10⁻¹⁰ 元——完全解释不了 0.07 元。真正差 7 分钱的是 `float`。**

`double` 的 53 位尾数在 5 万元量级（`2^15.6`）上，ulp 只有 `2^(15-52) ≈ 7.1×10⁻¹²`；每笔最多 2.00 元，累加 5 万笔的舍入误差上界约 `n × ulp/2 ≈ 1.8×10⁻⁷`，远低于 1 分钱。

而 `float` 只有 **24 位**尾数。在 5 万元量级上 ulp = `2^(15-23) = 2⁻⁸ = 0.00390625`——**每加一笔，误差就有可能达到 0.2 分**；5 万笔随机游走，偏差 `≈ √n × ulp` 量级 = `224 × 0.0039 ≈ 0.087 元`。**这个 0.087 与本次的 0.07 是同一个量级，不是巧合。**

关键推导（三个量级必须分开记）：

| 类型 | 尾数位 | 5 万元量级的 ulp | 5 万笔误差量级 | 能否解释 0.07 元 |
| --- | --- | --- | --- | --- |
| `float` | 24 | `2⁻⁸ = 0.0039` | `√n × ulp ≈ 0.087` | ✅ 能 |
| `double` | 53 | `2⁻³⁷ ≈ 7.3×10⁻¹²` | `√n × ulp ≈ 1.6×10⁻¹⁰` | ❌ 不能 |

**那 `double` 什么时候真的会坏？** 不是「笔数多」，而是「**累加值远大于单次增量**」：

- 累计金额到 `10¹⁴` 元时，ulp = `2^(46-52) = 0.015625`。`0.01` 大于半个 ulp，因此按最近舍入会前进一个 ulp，实际加了 `0.015625`，不是丢掉，也不是精确加一分；
- 临界点可以精确算：`ulp > 0.02`（因为 0.01 在 ulp 一半以上才会进位）对应的值约 **1.407×10¹⁴ 元**。过了这条线，1 分钱就加不进去了。

### 复现实验（真实输出，本机 2 核 AMD EPYC 7K62 @2.6 GHz）

**实验 A：`float` vs `double` vs 整数分，5 万笔两位小数金额（种子固定，可复现）**

```c
#include <stdio.h>
#include <stdlib.h>
#include <stdint.h>
#include <math.h>
int main(void){
  int n = 50000, seed = 26;
  srand(seed);
  int64_t cents = 0; float ff = 0; double dd = 0;
  for (int i = 0; i < n; i++) {
    int c = 1 + rand() % 200;            /* 0.01 ~ 2.00 元 */
    cents += c;
    ff += (float)c / 100.0f;
    dd += (double)c / 100.0;
  }
  double truth = (double)cents / 100.0;
  printf("n=%d  truth=%.2f\n", n, truth);
  printf("float  = %.6f  diff=%+.6f\n", (double)ff, (double)ff - truth);
  printf("double = %.10f diff=%+.3e\n", dd, dd - truth);
  printf("float ulp@%.0f = %g\n", truth,
         (double)(nextafterf((float)truth, 1e9f) - (float)truth));
  return 0;
}
```

**`diff=-0.072344`** 是这组特定输入的测量结果，按分显示约为 `−0.07` 元，不是对某个生产事故的证据。

**实验 B：`double` 真正失效的地方——大数吃小数**

```c
#include <stdio.h>
#include <math.h>
int main(void){
  for (double base = 1e12; base <= 1e15; base *= 10) {
    double v = base, b = base;
    for (int k = 0; k < 1000; k++) v += 0.01;      /* 1000 笔 1 分钱 */
    printf("base=%.0e ulp=%-12.8g +1000x0.01 -> %+.6f (应 +10.00)\n",
           base, nextafter(base, 2 * base) - base, v - b);
  }
  /* 精确求临界点：ulp > 0.02 时，1 分钱开始被舍掉 */
  double lo = 1, hi = 1e17;
  for (int i = 0; i < 200; i++) {
    double m = (lo + hi) / 2;
    if (nextafter(m, 2 * m) - m > 0.02) hi = m; else lo = m;
  }
  printf("1 分钱开始加不进去的临界值 ≈ %.6e\n", hi);
  return 0;
}
```

```
$ gcc -O2 -o th th.c -lm && ./th

base=1e+13 ulp=0.001953125    +1000x0.01 -> +9.765625  (应 +10.00)
base=1e+14 ulp=0.015625       +1000x0.01 -> +15.625000 (应 +10.00)
base=1e+15 ulp=0.125          +1000x0.01 -> +0.000000  (应 +10.00)  [全部丢失]
```

这张表才是 `double` 的真实杀伤力：**累计到 10¹⁵ 时，加 1000 笔 1 分钱，结果是「一分没加」**。如果对账系统先算「历史累计余额」（10¹⁵ 级）再把当日流水加上去，那么**整天的流水会被完全吞掉**——而监控上只看到「余额没变」，这比 0.07 元的偏差难查得多。

### 为什么事故里「以前没事」

这是最容易误判的一点：**浮点误差是「量级 × 笔数」的函数，不是「代码有没有 bug」的函数。**

| 时期 | 单日笔数 | 累计金额量级 | `float` 的 ulp | 误差量级 | 是否报警 |
| --- | --- | --- | --- | --- | --- |
| 3 个月前 | 3 万 | 3×10⁴ | `2⁻⁸ = 0.0039` | `√3e4 × 0.0039 ≈ 0.067` | 偶发 0.0x，肉眼当噪声 |
| 上线日 | 5 万 | 5×10⁴ | `0.0039` | `≈ 0.087` | **差 0.07，触发对账** |
| 大促预估 | 20 万 | 2×10⁵ | `0.0156` | `≈ 0.22` | 会持续报警 |

同一段代码、同一台机器、同一批种子——**只是笔数涨了 66%**，误差就跨过了「1 分钱 × 7」的对账阈值。

**排查判据**（可直接写进 SOP）：`累加值 / ulp > 增量 × 1000` 才算安全。一旦 `ulp ≥ 增量`，这个累加器就是坏的。

### 修复（改一行，两列数字）

| 改法 | 改前（5 万笔，seed=26） | 改后 |
| --- | --- | --- |
| `float` → `int64` 分 | 偏 `-0.072344` 元 | **偏 0**，且可逐笔审计 |
| `float` → `double` | 偏 `-0.072344` 元 | 偏 `-4.511e-10` 元（5 万笔安全） |
| `double` → `int64` 分（10¹⁵ 级累计） | 加 1000 笔 1 分钱：**增量 0** | **精确 +10.00** |
| 并行分片归约：固定分片键与树形求和 | 同一数据两次跑结果不同 | 结果**可复现**，误差上界可给出 |

**注意第 2 行与第 3 行的区别**：换成 `double` 只是把失效阈值从 5 万元推到 1.4×10¹⁴ 元，**并没有消除失效**。所以真正的答案是第 1/3 行：金额是**整数计数**（多少分），不是近似量。

### 实验 C：顺序不确定——比误差更可怕的「不可复现」

比「偏 0.07」更麻烦的是「**同一份数据跑两次，结果不一样**」。把 5 万笔按奇偶分片求和再相加，与顺序求和相比：

```c
#include <stdio.h>
#include <stdlib.h>
#include <stdint.h>
int main(void){
  int n = 50000; srand(26);
  int64_t cents = 0; double seq = 0, a = 0, b = 0;
  for (int i = 0; i < n; i++) {
    int c = 1 + rand() % 200; cents += c;
    double v = (double)c / 100.0;
    seq += v;
    if (i & 1) a += v; else b += v;      /* 奇偶分片 */
  }
  double truth = (double)cents / 100.0;
  printf("truth   = %.10f\n", truth);
  printf("seq     = %.10f  diff %+.3e\n", seq, seq - truth);
  printf("shard2  = %.10f  diff %+.3e\n", a + b, (a + b) - truth);
  return 0;
}
```

```
$ gcc -O2 -o seq seq.c && ./seq
truth   = 50357.1700000000
seq     = 50357.1699999995  diff -4.511e-10
shard2  = 50357.1700000001  diff +8.731e-11
```

三行输出说明了两件事：

1. 两个结果**都不等于真值**，但都远小于 1 分钱——`double` 在这个量级是安全的；
2. **两条路径的结果不相等**（`-4.511e-10` vs `+8.731e-11`）。把并行度从 2 改成 4、改成 16，结果又会变一次。

对账系统如果用「重算一次看是否相等」做校验，这个校验会**误报**——而误报的根因不是「算错了」，是「**求和顺序变了**」。

这才是并行归约必须固定顺序（或改用整数）的真正理由：**不是为了更准，是为了可复现。**

### 归类

> 属于 **表示层约束 ①**：`binary64` 能精确表示的数，其分母必须是 2 的幂。0.01 不是。
> 但本条约束的**失效点由量级决定**：`float` 在 5 万元量级就失效（ulp 0.0039），`double` 要到 1.4×10¹⁴ 元才失效（ulp 0.02）。**「我用的是 double 所以没事」是一句需要配上量级才成立的话。**

## 09.3 事故②：`float` 累加 1000 万次，统计值偏 8.79%

### 现象

一个实时风控服务用 `float` 累加请求耗时（毫秒），算平均值。上线三个月后，监控大盘和离线对账的「平均耗时」差 **8.79%**。大家都以为是采样口径不同，直到有人把同一批数据离线重算。

### 位级推导

`float` 只有 **24 位尾数**（含隐含前导 1），十进制有效位 `24×log10(2) ≈ 7.22` 位。当累加值达到 10⁶ 量级时，它的 ulp = `2^(20-23) = 2^-3`? 不对——精确算：

`1e6 ≈ 2^19.93`，落在 `[2^19, 2^20)` 区间，该区间 ulp = `2^(19-23) = 2^-4 = 0.0625`。

在这个区间，按最近舍入时，小于**半个** ulp 的正增量会被吞掉（恰好一半时看舍入规则）；而 `0.1f` 大于一个 ulp，通常前进 `2 × 0.0625 = 0.125`。小数 `0.1f` 自身的表示误差与这一步的舍入误差还要分别计算。

### 复现实验（真实输出）

```c
#include <stdio.h>
#include <math.h>
int main(void){
  volatile float  fs = 0;
  for (int i = 0; i < 10000000; i++) fs += 0.1f;
  volatile double ds = 0;
  for (int i = 0; i < 10000000; i++) ds += 0.1;
  printf("float  0.1 x 1e7 = %.9g  rel err = %+.3g%%\n",
         (double)fs, ((double)fs - 1e6) / 1e6 * 100);
  printf("double 0.1 x 1e7 = %.17g  rel err = %+.3g%%\n",
         (double)ds, ((double)ds - 1e6) / 1e6 * 100);
  printf("float  ulp@1e6 = %g ; ulp@1e7 = %g\n",
         (double)(nextafterf(1e6f, 2e6f) - 1e6f),
         (double)(nextafterf(1e7f, 2e7f) - 1e7f));
  printf("float  0.1f exact = %.20f\n", (double)0.1f);
  return 0;
}
```

```
$ gcc -O2 -o b09_f b09_f.c -lm && ./b09_f
float  0.1 x 1e7 = 1087937  rel err = +8.79%
double 0.1 x 1e7 = 999999.99983897537  rel err = -1.61e-08%
float  ulp@1e6 = 0.0625 ; ulp@1e7 = 1
float  0.1f exact = 0.10000000149011611938
```

**8.79% 是这一轮的误差，不是通用系数。** 在 `[2¹⁹, 2²⁰)` 区间增量常被舍入为 `0.125`；在 `[2²⁰, 2²¹)` 区间，`0.1f` 也会舍入到 `0.125` 的一个步长。最终结果约 108.8 万，仍在增长，并没有停住。若继续加到 `2²¹`，下一档 ulp 为 `0.25`，其一半 `0.125` 才超过这次的增量，按最近舍入时会停滞。不同区间的步长不同，不能用终点 ulp 重算整条路径。

### 定位命令

```bash
# 关键是「让 ulp 现形」
python3 -c "
import numpy as np
print(np.spacing(np.float32(1e6)))   # 0.0625
print(np.spacing(np.float32(1e7)))   # 1.0
print(np.float32(0.1))               # 0.1 (打印看不出来)

```

**判据**：如果累加次数 `n × 单次增量` 的量级让 `累加值 / ulp` 不再明显增长（每加一次，相对增长小于 1 ulp），就该换类型。粗略阈值：`float` 累加不要超过 `2^24 × 最小增量`；`double` 同理，阈值是 `2^53 × 增量`。

### 修复（改一行，两列数字）

| 改法 | 改前（1e7 次累加 0.1） | 改后 |
| --- | --- | --- |
| `float` → `double` | 偏 `+8.79%` | 偏 `-1.61e-08%` |
| `float` → 「整数毫秒累加 + 最后除」 | 偏 `+8.79%` | **偏差 0**（整数精确） |
| `float` + Kahan 补偿 | 偏 `+8.79%` | **本例 0**（实测见下），但代价是 6× 运算量 |
| 采用 Welford / 在线均值算法（避免大数累加） | 偏 `+8.79%` | 均值稳定，但方差仍有舍入 |

**Kahan 到底救不救？分两种情况，别只记一句结论。**

对「**从 0 开始、增量跨度不大**」的累加，Kahan 在 `float` 上表现惊人：

```c
/* 场景一：从 0 起加 1e7 笔 0.1f */
volatile float s = 0;  for (int i = 0; i < 10000000; i++) s += 0.1f;
volatile float ks = 0, kc = 0, y, t;
for (int i = 0; i < 10000000; i++) { y = 0.1f - kc; t = ks + y; kc = (t - ks) - y; ks = t; }
```

```
float  plain = 1087937.000000  (err +87937.0000)
float  Kahan = 1000000.000000  (err +0.0000)
```

**普通累加偏 8.79%，Kahan 一点不差。** 原因：补偿项 `c` 把每次丢掉的低位存起来，下一次从增量里「补回来」；只要**增量本身还能被表示**（`0.1f` 的 ulp 在 10⁰ 量级是 `2⁻²⁷`，远小于 1），这项补偿就有效。

但对「**基数巨大、增量相对 ln 极小**」的累加，Kahan 也会失效，甚至**引入更大偏差**：

```c
/* 场景二：从 1e10 起加 1e6 笔 0.01f —— 每笔都远小于 1e10 处的 ulp */
volatile float s = 1e10f; for (int i = 0; i < 1000000; i++) s += 0.01f;
volatile float ks = 1e10f, kc = 0, y, t;
for (int i = 0; i < 1000000; i++) { y = 0.01f - kc; t = ks + y; kc = (t - ks) - y; ks = t; }
```

```
base 1e10 + 1e6*0.01  plain = 10000000000.00   (一笔没加)
                      kahan = 10000010240.00   (比应加值多 240)
                      want  = 10000010000.00
```

普通累加**一分没加**（`1e10` 处 ulp = 1024）。Kahan 结果比十进制真值高 240，却比普通累加更接近真值：`1e10 + 10240` 是离真值最近的 binary32 值。补偿可以把小增量积攒起来，但不能给最终结果增加表示位数。

> **结论**：补偿求和可以减少逐次舍入误差，不能保证精确；要求账务精确时，应明确整数最小单位、范围和舍入规则，或使用合适的十进制表示。

### 归类

> 属于 **表示层约束 ②**：`float` 的精度由 24 位尾数**预先决定**，与「数据有多大」无关。累加值跨过 `2^23 × 增量` 之后，精度就死了。

## 09.4 事故③：用户昵称变乱码——按字节切断了 UTF-8

### 现象

某 IM 系统限制昵称「最多 16 字节」，前端输入框按**字符**限制（看起来是 16 个汉字），后端按**字节**截断。用户输入一个带 emoji 的昵称后，昵称显示成 `张三👨�` 这种带问号的乱码。客服收到 200+ 投诉，技术侧第一反应是「前端字体渲染问题」。

同时另一处：HTTP 响应分块（8 KB）时按字节切 JSON body，导致下游 JSON 解析偶发失败。

### 位级推导

UTF-8 是**变长编码**，一个「字符」（码点）占 1–4 字节；**多字节序列的后续字节必须以 `10xxxxxx` 开头**。这是 UTF-8 最重要的性质：**自同步（self-synchronizing）**——从任意字节位置开始扫描，最多跳过 3 个字节就能找到下一个合法起始字节。这既是它比 GBK 健壮的原因，也是「按字节切就会坏」的原因：

```
U+4F60 你  →  e4 bd a0        3 字节
U+597D 好  →  e5 a5 bd        3 字节
U+1F468 👨 →  f0 9f 91 a8     4 字节（F0-F4 开头）
U+200D  ZWJ →  e2 80 8d       3 字节（把 👨 和 👩 粘成一个字素）
```

如果取前 8 字节（`chunk[0:8] = e4bda0 e5a5bd e4b8`），末尾是「世」的前两字节 `e4 b8`，还差最后一个续字节 `96`。单独按替换模式解码这片不完整序列会得到 `U+FFFD`；严格模式会报错。

### 复现实验（真实输出）

```bash
$ printf '你好世界👨‍👩‍👧‍👦abc' > u.txt
$ xxd u.txt
00000000: e4bd a0e5 a5bd e4b8 96e7 958c f09f 91a8  ................
00000010: e280 8df0 9f91 a9e2 808d f09f 91a7 e280  ................
00000020: 8df0 9f91 a661 6263                      .....abc
```

```python
s = "你好世界👨‍👩‍👧‍👦abc"
b = s.encode()
print("bytes:", len(b), "codepoints:", len(s))   # 40 14

for i in range(0, len(b), 8):                      # 模拟 8 字节切片
    chunk = b[i:i+8]
    print(f"chunk[{i}:{i+8}] = {chunk.hex()} -> {chunk.decode('utf-8', errors='replace')!r}")
```

```
bytes: 40 codepoints: 14
chunk[0:8]  = e4bda0e5a5bde4b8      -> '你好�'
chunk[8:16] = 96e7958cf09f91a8      -> '�界👨'
chunk[16:24]= e2808df09f91a9e2      -> '\u200d👩�'
chunk[24:32]= 808df09f91a7e280      -> '��👧�'
chunk[32:40]= 8df09f91a6616263      -> '�👦abc'
```

按 8 字节切 5 片并逐片解码，**5 片都出现替换字符**。如果先重组字节再解码，结果是完整的。即使按码点切，`s[:8]` 也只能得到 `你好世界👨‍👩‍`：家庭 emoji 一共 7 个码点，包含 4 个人物码点和 3 个 ZWJ（U+200D），在 Unicode 字素分段中为一个簇。

```
family bytes: 25  codepoints: 7  graphemes: 1
codepoints: ['0x1f468', '0x200d', '0x1f469', '0x200d', '0x1f467', '0x200d', '0x1f466']
```

**25 字节 / 7 码点 / 1 个字素簇**——这是三个完全不同的「长度」，选错哪个，都会出现「看起来没问题但用户觉得坏了」的问题。

### 定位命令

```bash
# 1. 看字节
xxd nick.txt | head -3
# 2. 用 Python 标出每个字符的字节区间
python3 -c "
s=open('nick.txt',encoding='utf-8').read()
for ch in s: print(repr(ch), ch.encode().hex(), len(ch.encode()))
"
# 3. 检查是否含替换字符（乱码的铁证）
grep -c $'\xEF\xBF\xBD' nick.txt
```

### 修复（改一行，两列数字）

| 改法 | 改前 | 改后 |
| --- | --- | --- |
| 按**码点**（rune）边界截断 | 5 个 8 字节片段独立解码，均含替换字符 | 从有效输入按码点切不会制造非法 UTF-8，但可能切开字素簇 |
| 按**字素簇**边界截断 | 同上 | 需要用 ICU / `unicode-segmentation` 库，成本约 1–5 μs/词 |
| 长度限制单位改为「码点数」而非字节数 | 16 字节 → 最多 5 个汉字（或 4 个 emoji） | 16 码点 → 稳定可预期，DB 列长度按字符而非字节 |
| 数据库列：`utf8`(3B) → `utf8mb4`(4B) | emoji 写入**直接报错或截断** | 正常存储 |

实验对比的是**独立解码每个字节分块**与**先重组再解码**。HTTP 传输分块本身允许任意字节边界，出错的是把每块当成完整文本。实际产品若要求不截断用户可见的字符，还需按字素簇确定边界，并另设必要的字节上限。

### 归类

> 属于 **表示层约束 ③**：UTF-8 的多字节序列有内部结构，**任何「按长度切」的操作都必须落在序列边界上**。而这层的上游还有一层：码点 ≠ 字素簇，视觉上的「一个字符」可能是 7 个码点。

## 09.5 事故④：跨机 RPC 解析错位——对齐、字节序、位域三重叠加

### 现象

同一个 RPC 框架，x86 测试环境一切正常，上到 ARM 生产机后**每 3–5 分钟**出现一次「序号错乱」：客户端发的 `seq=0x11223344`，服务端记录成 `0x44332211`；随后「重复请求」被判定为新请求，触发 2 倍流量。排查了 3 天，先后怀疑网卡、内核、负载均衡，最后发现是**服务端一个版本把 `struct` 直接 `write()` 到 socket**。

### 位级推导

三件事叠加：

1. **padding**：`struct { uint8_t ver; uint32_t seq; uint16_t code; }` 在 x86-64 上，`seq` 必须 4 字节对齐，于是 `ver` 后面填了 3 字节 padding，结构体 `sizeof` = 12 而不是 7；
2. **字节序**：x86 小端，网络序是大端。`seq = 0x11223344` 在小端内存里是 `44 33 22 11`，对端按大端读成 `0x44332211`；
3. **位域**：`unsigned flag:3` 的布局**由实现定义**，跨编译器（GCC/Clang/MSVC）可能不同，跨字节边界叠加端序必然错。

### 复现实验（真实输出）

```c
#include <stdio.h>
#include <stdint.h>
#include <string.h>

#pragma pack(push,1)
typedef struct { uint8_t ver; uint32_t seq; uint16_t code; uint8_t flag; } wire_t;
#pragma pack(pop)
typedef struct { uint8_t ver; uint32_t seq; uint16_t code; uint8_t flag; } nat_t;

int main(void){
  printf("packed sizeof=%zu  natural sizeof=%zu  diff=%zu\n",
         sizeof(wire_t), sizeof(nat_t), sizeof(nat_t) - sizeof(wire_t));

  wire_t m = { 1, 0x11223344, 0x0102, 0xFF };
  unsigned char *p = (unsigned char *)&m;
  printf("wire bytes: ");
  for (size_t i = 0; i < sizeof m; i++) printf("%02x ", p[i]);
  printf("\n");

  uint32_t be = __builtin_bswap32(m.seq);
  printf("seq native=0x%08x  network(be)=0x%08x  be bytes:", m.seq, be);
  unsigned char *q = (unsigned char *)&be;
  for (int i = 0; i < 4; i++) printf(" %02x", q[i]);
  printf("\n");
  return 0;
}
```

```
$ gcc -O2 -o b09_s b09_s.c && ./b09_s
packed sizeof=8  natural sizeof=12  diff=4
wire bytes: 01 44 33 22 11 02 01 ff
seq native=0x11223344  network(be)=0x44332211  be bytes: 11 22 33 44
```

**三行输出解释了三天的排查**：

- `sizeof` 差 **4 字节**（padding），对端如果你的解析结构体没有 `packed`，`ver` 后面会直接读 `seq` 的 4 个字节——读到的是 `44 33 22 11` 的低位位置偏移，整条字段全错位；
- `seq` 在网络上的正确字节序是 `11 22 33 44`（大端，人类可读顺序），而小端机器内存里是 `44 33 22 11`。**不做 `htonl`，对端读到的就是字节反转**；
- 注意 `wire bytes` 里的 `02 01`——在小端机器上，`code = 0x0102` 的**低位字节 0x02 在前**。对端按大端读到的是 `0x0201 = 513`，不是 `258`。

**为什么 x86 测试环境没发现？** 因为两端都是 x86，都是小端，都不做字节序转换，于是「大家都错」等于「大家都对」——这就是端序 bug 的典型特征：**它只在跨端序时才现形，而在你的 CI 里，所有机器可能都是同一个端序。**

### 定位命令

```bash
# 1. 看机器的字节序
lscpu | grep -i "byte order"            # Little Endian
# 2. 看网络字节序的正确值（十六进制 dump 对比）
tcpdump -i any -X -s0 port 9000 | head -20
# 3. 结构体偏移与尺寸
gcc -o off off.c && ./off                # 用 offsetof() 打印每个字段偏移
```

### 修复（改一行，两列数字）

| 改法 | 改前 | 改后 |
| --- | --- | --- |
| 结构体裸传 → **显式序列化**（每个字段定长度、定字节序） | 跨端序：`seq` 反转、`code` 由 `258` 变 `513`；每次上线 3–5 分钟一次错乱 | **每个字段可预期**：字节数固定，端序统一为大端（或明确声明 little-endian） |
| 网络传输加入长度前缀 | 无，靠 TCP 边界，粘包即错 | 每条消息自带总长度，天然分帧 |
| `packed` 保留但**只用于内部 mmap**，不用于线路 | — | 内部可省 4 字节，跨机必须换格式 |
| 版本演进：新增字段放末尾 + 保留字段号 | 加 `flag` 字段后老客户端解析全错 | protobuf 的 `field number` 机制直接解决 |

**算例**：本例每条多 4 B。若恒定 1,000 条/秒，不做压缩或合并，24 小时多 `4 × 1000 × 86400 = 345,600,000 B`，约 345.6 MB（十进制）。这不是对 1 KB 消息的测量，也不表示所有结构体都有同样的填充比例。

### 归类

> 属于 **表示层约束 ④**：内存布局不是线路格式。**padding（编译器自由）、字节序（硬件约定）、位域（实现定义）** 三者任何一个跨机器都会违约，而它们恰好都是「编译器/硬件说了算，你说了不算」的部分。

## 09.6 表示层防御清单（可直接贴进 Code Review 模板）

| # | 规则 | 为什么 | 违反后的症状 |
| --- | --- | --- | --- |
| 1 | 金额、计数、ID 一律用整数最小单位 | `binary64` 只能精确表示分母为 2 的幂的数；且失效阈值由量级决定（`float` 5 万元、`double` 1.4×10¹⁴ 元） | 对账误差随机漂移、无法复现 |
| 2 | 累加器位数 ≥ `log2(最大累加值 / 最小增量)` + 精度位 | ulp 随量级增长，超过增量就加不动 | 统计值系统性偏大/偏小（本次 8.79%） |
| 3 | 浮点只参与「相对误差可接受」的计算，不参与精确判等 | `0.1+0.2 ≠ 0.3` 是数学事实 | `if (a == b)` 偶发不成立 |
| 4 | 任何「按长度切」的操作必须落在编码边界 | UTF-8 多字节序列有内部结构 | 乱码（`U+FFFD`）、JSON 解析失败 |
| 5 | 区分 **字节数 / 码点数 / 字素簇数** 三个长度 | emoji 家庭 = 25 字节 / 7 码点 / 1 字素 | 用户觉得「明明没超长却被截断」 |
| 6 | 跨机传输必须显式序列化，禁 `memcpy(struct)` | padding、端序、位域都是平台相关 | 跨端序/跨编译器/跨版本必现错位 |
| 7 | 网络协议多字节字段统一用大端（网络序），边界处只转换一次 | 避免「有的字段转了、有的没转」 | 一半字段正确、一半反转 |
| 8 | 协议演进：新字段加在末尾，或使用带字段号的编码 | 旧客户端按固定偏移解析 | 加字段就破坏兼容 |
| 9 | 对 `float`/`double` 的二进制序列化，显式声明 IEEE 754 与端序 | `NaN` 有多个位模式、端序不同 | 跨语言对比失败、hash 不一致 |
| 10 | 在 CI 里跑「另一台端序/架构」的测试（QEMU/交叉编译） | 端序 bug 只在跨端序时现形 | 生产才发现，回滚困难 |

| 五问 | 本篇的答案 |
| --- | --- |
| **① 它是什么** | 一场「值不对但代码看起来对」的事故家族：浮点精度、编码边界、内存布局。它们共同属于「表示层」——**同一个位模式，在不同解释下是不同的值** |
| **② 物理形态** | `binary64` = 1+11+52 位（ulp 随指数增长）；UTF-8 = 1–4 字节变长（首字节前缀 + 续字节 `10xxxxxx`）；`struct` = 字段 + padding（偏移由对齐规则决定）；大端/小端 = 高低位字节的存放顺序 |
| **③ 走一遍** | 一次事故的完整链路：业务读字段 → 类型转换 → 运算舍入 → 序列化/编码 → 传输 → 对端解码 → **任一步的解释约定不一致，整条链就错**。每步成本：浮点加法 ~1 cycle，UTF-8 解码 ~1–5 cycle/字节，`htonl` 几乎是免费的（1 条指令） |
| **④ 改一行** | 见 §09.6 清单的 10 条规则，每条都对应一个「改前/改后」数字（§09.2–§09.5 各有一张表） |
| **⑤ 它证伪了谁** | ①「`double` 精度足够，金额用它没问题」——精度不是位数问题，是**分母能否是 2 的幂**；②「`float` 省内存，统计用它够了」——累加会吃光精度；③「UTF-8 是变长编码，按字节切也一样」——切开就是非法序列；④「结构体直接发过去最快」——快的是你的机器，慢的是排查三天 |

### 同一件事在各层叫什么

| 你嘴里的词 | 在位层叫什么 | 在协议层叫什么 | 在工程里通常叫 |
| --- | --- | --- | --- |
| 「精度丢失」 | ulp 随指数增长，尾数被截断 | 无（表示层问题） | 浮点误差 |
| 「乱码」 | UTF-8 序列被劈开，出现 `U+FFFD` | 无（应用层编码） | mojibake |
| 「字段错位」 | padding / 端序 / 位域不一致 | 线路格式 ≠ 内存格式 | 序列化 bug |
| 「时间对不上」 | 时钟源与单位不同 | NTP/TTL/时区 | 时钟漂移（→ `base/55`） |

## 09.8 一页速记

```
【一句话】值不对时，第一反应打印位模式，不要改代码。

【五个数字】
  float  ulp@1e6 = 0.0625 ；ulp@1e7 = 1.0        → 累加会「加不动」
  float  5 万笔两位小数金额 = 偏 0.072 元        （ulp 0.0039，√n 随机游走）
  double ulp@1e15 = 0.125 ；1 分钱失效临界 ≈ 1.4e14 元
  0.1 x 1e7  float = 1087937 (+8.79%) ；double = 999999.9998 (-1.6e-8%)
  emoji 家庭 = 25 字节 / 7 码点 / 1 字素簇

【Kahan 的适用边界】
  增量能被表示、只是单次加法丢低位 → 救（实测 8.79% → 0）
  最终值仍须落在原浮点格式的表示网格，补偿不能增加最终结果的位数

【三个切分边界】
  字节边界  ≠ 码点边界  ≠ 字素簇边界     （30 / 14 / 1 的区别）
  UTF-8 续字节一律 10xxxxxx → 自同步，从任意位置最多跳 3 字节就能对齐

【一个铁律】
  结构体裸传 = padding（编译器自由）+ 端序（硬件约定）+ 位域（实现定义）
  三者任一跨机器 → 每天几次的「偶发错乱」，且 CI 发现不了

【四起事故的同一句话】
  你看到的值 ←（某一层解释约定）← 机器里的位；
  约定被谁改掉，值就在谁那里坏。
```

## 09.9 自检 3 题

**Q1.** 一个服务用 `float` 累加「每秒请求数」运行 24 小时，单机峰值约 3 万 QPS。运行到第 12 小时，累计值约 13 亿。请判断这个累加器是否已经失效，并给出临界点的推算。

<details><summary>答案</summary>

先算临界点：`float` 的尾数 24 位。累加值跨过 `2^23 = 8,388,608` 后，ulp 变成 1；跨过 `2^24 = 16,777,216` 后，ulp 变成 2。

累计 13 亿（1.3×10⁹）落在 `[2^30, 2^31)`，网格间距为 128。如果每个请求做一次 `+1`，按最近偶数舍入会在 `2²⁴` 处停滞；按恒定 3 万次/秒估算约 559 秒。若**每秒汇总一次**，每次加约 30,000，则不会因间距 128 而停滞，但到这一区间时不再精确保留每个整数；30,000 可被舍入为 `234 × 128 = 29,952`。题目只给峰值，不能据此预测停滞时刻，必须先问清单次更新的增量和到达率。

正确做法：计数用足够宽的整数，按预期最大值核对溢出边界；平均值单独计算。判断增量是否会被舍掉，比较增量与当前值到邻点间距的一半，并注明舍入规则。
</details>

**Q2.** 一个 HTTP API 返回 JSON，其中 `nickname` 字段限长 32 字节。产品要求「支持 emoji」。请说明这个限制会引发哪两类问题，各给一个具体例子，并给出正确的限制方式。

<details><summary>答案</summary>

两类问题：

1. **截断破坏编码**：四字节 emoji 如果在字节限额处被切开，替换模式解码器可能产出 `U+FFFD`。本篇的小实验中，40 B 样本按 8 B 切开的五段分别解码，五段都有替换字符。
2. **码点 ≠ 字素簇**：👨‍👩‍👧‍👦 是 7 个码点 25 字节，占 1 个「视觉字符」。如果按「32 字节」限制，一个家庭 emoji 就吃掉 25 字节；如果按「32 码点」，它只占 7 个。产品说的「支持 emoji」到底指哪种，必须明确。

正确方式：**限制单位选「字素簇（grapheme cluster）」**，用 ICU / `unicode-segmentation` 做边界切分；数据库列用 `utf8mb4`（4 字节上限）；同时在 API 文档里写清「长度 = 字素簇数」。如果性能敏感，退一步用「码点数」并明确告知用户（emoji 家庭算 7 个字符），绝不用字节数。
</details>

**Q3.** 某团队把「结构体直接发到 socket」改成了 protobuf，但发现**小消息**（< 64 字节）的 CPU 占用反而上升了 15%。这可能吗？请从「序列化成本」与「网络收益」两个方向给出解释，并说明什么时候该保留结构体裸传。

<details><summary>答案</summary>

完全可能，而且是常见现象：

- **序列化成本**：protobuf 需要遍历字段、写 tag（field number + wire type）、变长整数编码（varint）；结构体裸传是一次 `memcpy`（甚至零拷贝 `sendfile`）。对于 8–64 字节的小消息，编码开销可能比 `memcpy` 高 2–5 倍。
- **网络收益**：protobuf 省下的字节数在**小消息**上不明显（padding 浪费 vs tag 开销可能抵消）；而大消息（KB 级）省下的带宽才是主要收益。更关键的是「跨版本兼容」——这是可靠性收益，不是 CPU 收益。
- **CPU 上升的另一个原因**：protobuf 的对象分配（`Builder`/`Message`）与 GC 压力，在 Go/Java 里尤其明显。

**什么时候可以保留裸传**：① 同进程内（`mmap` 共享内存、本机 IPC）；② 两端**完全同构**（同架构、同端序、同编译器、同版本）且**永不演进**；③ 极端性能路径（如高频交易内部的 `memcpy` 环形缓冲）。**只要跨机器、跨版本、跨语言任一成立，就必须显式序列化**——这不是性能问题，是正确性问题。

正确的折中：小消息用「定长紧凑布局 + 显式端序转换」（比 protobuf 快，比裸传安全），大消息用 protobuf；或者用 `flatbuffers`/`capnproto`（零拷贝 + 显式 schema），代价是构建复杂。
</details>
