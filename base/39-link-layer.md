# 39. 链路层：MAC、ARP、交换机、VLAN 与 MTU/分片

> **状态**：`已完成（初稿）` ｜ **所属**：第四部分 · 网络：从一根网线到一张证书 ｜ **编号**：39 / 56
> **本篇定位**：IP 要把包送到终点，但在这一跳，设备只需要把帧交给下一跳。理解这两个目的地址为什么能同时出现，就能把邻居解析、交换、路由和 MTU 分开排查。
> **读法**：先手算 §39.2 的帧长度，再看 §39.4 的同网段与跨网段对照，最后用 §39.7 从“大包不通”反推证据。

## 39.1 引子：能 ping 通，不代表文件能传完

设一条 IPv4 路径两端的接口 MTU 都是 1500，中间有一跳只能承载 1400 B 的 IP 包。一个携带 56 B 数据的 ICMP Echo 只需 `20 + 8 + 56 = 84 B`；它成功了，只能证明这类小包能在当时往返。TCP 的握手包通常也很小；发起上传后首次出现大数据段，才可能碰到路径上限。如果发送方要求不分片，沿途又无法把有效的 MTU 反馈送回，连接就可能表现为「握手完成，正文卡住」。这是**机制推演**，不是对某台线上机器的诊断。对照项包括代理大小限制、接收端没有持续读、应用事务卡住；这些也能造成上传卡顿。

## 39.2 以太网帧：从 64 B 算到 1518 B

```text
物理发出:  前导码 7 B | SFD 1 B |            帧             | 帧间间隔
基本帧:    目的 MAC 6 | 源 MAC 6 | 类型/长度 2 | 负载及填充 | FCS 4
单 VLAN:   目的 MAC 6 | 源 MAC 6 | 802.1Q 标签 4 | 内层类型 2 | … | FCS 4
```

| 量 | 怎么算 | 不应混在一起的量 |
| --- | --- | --- |
| 无标签帧最小长度 | `14 + 46 + 4 = 64 B` | 不含前导码和帧间间隔；46 B 含可能的填充 |
| 无标签帧常见最大长度 | `14 + 1500 + 4 = 1518 B` | 1500 B 是这里的负载上限，不是整个帧的长度 |
| 单标签帧对应上限 | `18 + 1500 + 4 = 1522 B` | 设备支持该帧长时，打标签不必把 IP MTU 降到 1496 |
| 连续最小无标签帧的线速预算 | `(64 + 8 + 12) × 8 = 672 bit` 帧时 | 12 B 是等效空闲时间，不属于帧；这里未额外计入物理编码开销 |

早期共享介质半双工以太网中，最小帧长与碰撞检测所需时间有关；现代全双工交换端口没有同样的共享碰撞域，但沿用帧格式。FCS 是用于检测传输差错的 CRC，不提供防篡改证明。普通抓包也常看不到 FCS：网卡和驱动可能在交给抓包点之前就去掉了它。抓包长度比算式少 4 B，不意味着线上的帧没有 FCS。

## 39.3 交换机：用收到的帧学习，不凭 IP 路由

学习型交换机从入端口帧的**源 MAC**建立或刷新转发表项，再查**目的 MAC**决定怎么发。实现与配置有差异，但基本转发口径如下：

| 到达的目的地址 | 本 VLAN 中的典型动作 | 诊断关注点 |
| --- | --- | --- |
| 已知单播 | 转发到查到的端口；若目标就是入端口，一般不从原端口送回 | MAC 是否在正确的 VLAN 和端口上 |
| 未知单播 | 在允许的同 VLAN 转发端口泛洪，不包括入端口 | 表项老化、地址迁移、学习受限 |
| 广播 | 同 VLAN 内泛洪，有控制策略时受其约束 | 广播域是否太大，是否有环路或风暴抑制 |
| 多播 | 取决于协议、监听表和配置，不宜一概按广播理解 | 组播侦听和端口成员是否正确 |

广播和未知单播进入桥接环路后，没有 IP 路由器那样每跳递减的 TTL；二层环路可能反复转发帧，MAC 表也可能在端口之间摇摆。STP/RSTP 的作用是使活动路径无环，并在拓扑变化后重新收敛。链路聚合则在满足两端配置条件时把物理链路当作一个逻辑口；不能把任意两根线直接接成环来“加带宽”。多层交换机可同时做路由和二层交换，但这两项决策仍属于不同层。

## 39.4 ARP：为什么同一个 IP 包换了目的 MAC？

发送主机先查路由，决定出接口与下一跳；在需要 ARP 的 IPv4 以太网上，再把**下一跳 IPv4 地址**映射为 MAC。邻居表维护的是 IP 到 MAC 的映射；交换机的转发表维护的是 VLAN 内 MAC 到端口的映射。两者都叫“表”，但查的键、填表的人和故障范围都不同。

```text
同网段（示例）：
  A 192.0.2.10 → B 192.0.2.20
  路由判定 B 在链路上 → 查 B 的 MAC → IP dst=B，帧 dst=B 的 MAC

跨网段（示例）：
  A 192.0.2.10 → C 198.51.100.20，经 G 192.0.2.1
  查 G 的 MAC → IP dst=C，帧 dst=G 的 MAC → G 在下一跳重新封装
```

常见的 ARP 查询是广播，应答通常是单播；具体收到的广播、宣告或探测要结合 [RFC 826](https://www.rfc-editor.org/rfc/rfc826) 和实现处理。邻居表 `STALE` 不是“不通”：旧映射可能还可用于发送，并在使用过程中重新验证；`INCOMPLETE` 或 `FAILED` 则提示解析还没完成或已失败，需要检查 VLAN、链路和对端。IPv6 使用 ICMPv6 邻居发现，不沿用 ARP；不能以“ARP 表为空”判断 IPv6 不通。对应的 IPv6 邻居状态仍可由 `ip -6 neigh` 观察。

## 39.5 VLAN：隔开的是广播域，不是租户身份

一个 802.1Q 标签通常占 4 B：外侧 TPID 2 B，接着是 2 B TCI，内含 3 位优先级 PCP、1 位 DEI 和 12 位 VID。VID 0 表示仅带优先级的标签语义，4095 保留，不能把 12 位全当可分配 VLAN。接入口通常给无标签入站帧归入指定 VLAN；干道允许一组 VLAN 同行，如何处理无标签帧取决于两端配置。如果两端对 native VLAN 或允许列表理解不同，二层转发可能失败或把流量放到不该去的域。跨 VLAN 通常需要三层转发；能否访问由路由和策略决定，不是 VLAN 编号决定。

| 对象 | 做什么 | 不保证什么 |
| --- | --- | --- |
| Linux bridge | 连接二层端口；可做 VLAN 过滤 | 不自动建立租户鉴权或三层路由 |
| veth pair | 一端发的帧从另一端收到，常跨命名空间连接 | 不自动建立 bridge 或 NAT |
| TUN / TAP | 用户态分别读写三层包 / 二层帧 | 不自动把流量安全地转到远端 |
| 环回接口 | 内核内通信，不经过物理以太网 | 其 MTU 不能代表生产路径 |

## 39.6 MTU、MSS 与分片：先把三个量的单位对齐

MTU 在这里是接口能承载的 IP 包长度上限；路径 MTU 是这条方向上的最小值。它可能随隧道、路由切换、对端方向而变化。TCP MSS 是数据段载荷的限制之一，不包括基本 IP/TCP 头；在 1500 B MTU、无 IP/TCP 选项的 IPv4 示例中是 `1500 − 20 − 20 = 1460 B`；IPv6 基本首部 40 B，则是 `1500 − 40 − 20 = 1440 B`。如果 TCP 数据段带选项，发送端还应为实际头部留空间。传统 PPPoE 常见的 1492 B 来自 `1500 − 8`；能否使用更大的 MTU 取决于链路和协商，不能只看“PPPoE”三个字。

| 情况 | 太大的包会去哪 | 诊断提示 |
| --- | --- | --- |
| IPv4，允许分片 | 发送端或路由器可能分片；终点重组 | 每片有自己的 IP 头；任何一片缺失都可能令原报文无法交付 |
| IPv4，设置 DF | 中间节点不能分片，按协议回 ICMP 需要分片 | 检查反馈是否可达，以及发送端是否调整 |
| IPv6 | 路由器不分片，回 ICMPv6 Packet Too Big；需分片时由源端处理 | 不要将 IPv4 的 DF 逻辑套到 IPv6 |
| TCP 使用 MSS | 只限制 TCP 数据段的一部分条件 | 没有为 UDP 或新的隧道自动解决路径 MTU |

**分片手算**：设 IPv4 包头 20 B、载荷 2000 B，中间 MTU 1500 B，允许分片且无 IP 选项。非最后一片的数据长度必须是 8 B 的整数倍。第一片载荷 `floor((1500−20)/8)×8=1480 B`，总长 1500，MF=1；第二片载荷 520 B，偏移字段 `1480/8=185`，总长 540，MF=0。偏移不按到达顺序编号，也不含 IP 头；第一片先到并不是重组前提。抓包如果在卸载前看到超过 MTU 的长度，也不能直接判定线路真的传了那个大帧，要区分在 TSO/GSO 之前还是在接收聚合之后观测。

## 39.7 只读排查：按大小和方向收窄问题

收尾时只读取本机接口信息，不改路由、qdisc 或防火墙，也不制造链路故障：

```console
$ cat /sys/class/net/lo/mtu
65536
```

这是**这台机器的环回接口配置**。它不能验证任何物理链路 MTU，也不能验证 39.1 的黑洞场景。下列命令是供读者在其有权限管理的环境中使用的诊断入口，未把输出写成实测：

```bash
ip -br link
ip -d link show
ip route get 192.0.2.20           # 文档示例地址：实际排查替换为己方目标
ip -4 neigh show
ip -6 neigh show
```

| 症状 | 优先找的证据 | 不能从它推出什么 |
| --- | --- | --- |
| 连小包都不通 | 预期出接口、下一跳是否可达、邻居状态、VLAN 成员关系 | 不能仅凭一次 `ping` 失败断定链路断开 |
| 小包通，大包在复现阈值卡住 | 各跳 MTU、隧道开销、反馈、同方向抓包与重传 | 不能凭入口接口 MTU 推出整条路径 MTU |
| 同一 VLAN 部分设备失联 | 交换端口、标签口径、邻居和 FDB 是否指向同一设备 | VLAN ID 一致不代表 VLAN 在每段干道都被允许 |
| 跨 VLAN 失败 | 先证实本地网关邻居，再查转发与策略 | 不意味着应把两个 VLAN 合并 |

## 39.8 安全边界与三列账

| 认证 | 完整性 | 机密性 |
| --- | --- | --- |
| 基础 Ethernet 与 ARP 不提供端点的密码学身份；MAC 不等于用户或设备凭证 | FCS 提供差错检测，不提供密码学完整性 | VLAN 分隔广播域，不加密；视需求选用链路保护或更高层加密 |

防御上，DHCP Snooping/DAI 等能力依赖交换网络正确维护绑定与信任端口，静态地址也要有明确的绑定来源；不能把这些特性当作端到端身份验证。考虑接入身份时区分 802.1X 的接入控制与 MACsec 的链路保护：后者只保护部署过且协商成功的相邻链路，不替代跨网段应用的 TLS 或授权。更完整的分层对照见 [48](48-defense-and-app-auth.md)。

| 承诺 | 代价 | 失效边界 |
| --- | --- | --- |
| 在一个广播域送帧 | 学习、老化、泛洪 | 环路、表项摆动、错误的 VLAN 或端口状态 |
| 用下一跳 IP 找本地帧地址 | 邻居缓存和重试 | 映射过期、接入绑定失效、链路不可达 |
| 按链路载荷限制传输 | 额外头部与路径反馈 | 隧道开销未计、反馈被丢、两方向不对称 |

## 39.9 一页速记与自检

**速记**：先查 IP 路由选哪跳，再查邻居映射；MAC 的转发范围由 VLAN 限定。每过一跳，帧头可以变，端到端 IP 目的地址在普通转发中不变。MTU 算 IP 整包，MSS 算 TCP 数据。大包卡顿是一条线索，不是根因。

1. 主机给异网段的服务发包，第一跳 ARP 查谁？
2. 路径上的一个方向多封装 40 B，外层 MTU 1500，内层最多有多大？
3. 抓包工具没有 FCS 字段，能断定发送端没生成 FCS 吗？

<details><summary>答案</summary>

1. 查路由选中的下一跳；典型情况是本地网关而不是异网段的服务。
2. 若 40 B 是外层整套新增开销，则是 1460 B；先确认这 40 B 的起止边界和该方向实际路径 MTU。
3. 不能。观察点可能看不到硬件处理过的 FCS，也可能根本不在物理接口。

</details>
