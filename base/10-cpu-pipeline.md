## 10.1 引子：同一个循环，改一行，快 4 倍；同一份 `if`，换个数据顺序，快 9 倍

本文所有数字都长在这台机器上；换一台机器绝对值会变，比例关系不会：

| 项 | 实测值 | 来源 |
| --- | --- | --- |
| CPU | AMD EPYC 7K62（QEMU/KVM 虚拟机，2 vCPU，1 socket） | `lscpu` |
| 标称主频 | 2595.122 MHz | `/proc/cpuinfo` |
| **有效主频** | **3.22 GHz**（CPU1，一条依赖 `add` 0.310 ns 反推）；**1.64 GHz**（CPU0，同一份代码 0.609 ns） | 自写校准循环 |
| L1d / L1i | 64 KiB / 64 KiB，2 路，64 B 行 | `/sys/.../cache/index0`、`index1` |
| L2 / L3 | 512 KiB / 16 MiB，16 路 | `index2`、`index3` |
| 内存 | 1.9 GiB，1 个 NUMA 节点 | `free -h` |
| 编译器 | gcc 12.2.0（Debian 12.2.0-14+deb12u1） | `gcc --version` |
| 缺什么 | **没有 `perf`、`strace`、`numactl`**；所有计时用 `clock_gettime(CLOCK_MONOTONIC)` + `taskset` | `which` |

现在写两个循环。它们都没有 IO、没有锁、没有 `malloc`，连数据都完全相同：一个 256 KiB 的 `float` 数组，反复累加 1677 万次，全部落在 L2 里。

**版本 A（一条串行依赖链）**：

```c
float s = 0;
for (long i = 0; i < n; i++) s += a[i];
```

**版本 B（拆成 4 条互不相干的链）**：

```c
float s0 = 0, s1 = 0, s2 = 0, s3 = 0;
for (long i = 0; i + 3 < n; i += 4) {
    s0 += a[i]; s1 += a[i+1]; s2 += a[i+2]; s3 += a[i+3];
}
return (s0 + s1) + (s2 + s3);
```

同样是 1677 万次 `addss`、同样一份数据，`-O2 -fno-tree-vectorize`（关掉自动向量化，确保比较的是标量循环）编译，绑到 CPU1 跑，取 5 次最小值：

| 版本 | 总时间 | 每次加法 | 每周期加法数 | 相对 A |
| --- | --- | --- | --- | --- |
| A：单累加器 | 15.449 ms | 0.921 ns | 0.34 条/周期 | 1.00× |
| B：4 路累加器 | 3.894 ms | 0.232 ns | 1.33 条/周期 | **3.97×** |
| B′：8 路累加器 | 2.568 ms | 0.153 ns | 2.03 条/周期 | **6.02×** |

第二组实验更刺眼。同一份 `if (a[i] >= 128) s += a[i];`，同一台机器、同一个编译选项，只把 1 MiB 的输入数组排一次序：

| 输入顺序 | 每次判断 | 每周期判断 | 说明 |
| --- | --- | --- | --- |
| 随机 0…255 | 4.331 ns | 14.0 周期 | 分支结果不可预测 |
| 升序排好 | 0.458 ns | 1.48 周期 | 前一半全不取、后一半全取，预测器百发百中 |
| 无分支写法（`cmov`） | 0.660 ns | 2.13 周期 | 两边都算，但不跳 |

**9.46 倍**，只因为数据换了顺序。这不是 cache：1 MiB 数组远小于 16 MiB 的 L3，访问严格顺序，预取器全部命中。**变的是「同一条指令什么时候能拿到操作数」，即流水线里同时在飞的指令之间的依赖。**

这就是本篇的唯一真问题：**CPU 不是「一条条执行指令」，而是一条流水线上同时飞着几十条；分支预测失败、数据依赖、乱序窗口解释了几乎所有「莫名其妙变慢」。** 你写的程序顺序是**提交顺序**（retire order），不是**执行顺序**，也不是**完成顺序**。不理解这一点，你只能记住「循环展开快」「少用分支快」「拆累加器快」这些互相矛盾的经验；理解了，每条经验都能从 §10.2 的 0.385 ns 推出来。

## 10.2 一个节拍有多长：0.385 ns，光只走 8 cm

### 先把「主频」翻译成时间

2.6 GHz 即每秒 2.6×10⁹ 拍，一拍是：

```
T = 1 / (2.6×10⁹) s = 3.846×10⁻¹⁰ s = 0.385 ns
```

本机实测有效主频 3.22 GHz，对应 `T = 0.311 ns`；下面为了对齐厂商标称值，先用 0.385 ns 算，最后再换回实测值。

### 光在一个节拍里走多远

真空光速 `c = 3.0×10⁸ m/s`：

```
d_vacuum = c × T = 3.0×10⁸ × 3.846×10⁻¹⁰ = 0.1154 m = 11.5 cm
```

芯片里的信号不在真空里走，介质是 SiO₂ 与低 k 介质，相对介电常数 ε_r ≈ 2.0–2.2，折射率 n = √ε_r ≈ 1.4–1.5，速度是 `c/n ≈ 0.67c–0.71c`：

```
d_silicon = 0.1154 m × 0.67…0.71 = 7.7…8.2 cm
```

所以「一个节拍光走 8 cm」不是比喻，是这一代主频下的硬边界。**而一颗服务器 CPU 的 die 对角线只有 2–3 cm。** 一条信号从芯片一头走到另一头再回来，就要吃掉半个到一个完整节拍；全局总线、时钟树、L3 crossbar 这些「长线」无法靠加晶体管变快，只能加流水线寄存器切成两段——而每切一段就多一个触发器（建立时间、保持时间、时钟偏斜、功耗）。

**「流水线级数不能无限加」的第一条原因就在这里：晶体管缩小让门变快，但线没有同比变快。** 把一级逻辑切成两级，逻辑延迟减半，可线上的延迟、触发器的开销、时钟树的偏斜一分不少。到某个深度，加一级省下的门延迟已经小于新加的触发器开销，频率不再上升，只剩面积、功耗和更贵的分支惩罚。

### 算一笔「加深流水线」的账

用一个极简模型：一整块组合逻辑总延迟 `T_logic = 1.0 ns`，每加一级流水线要插一个触发器，触发器 + 时钟偏斜的总开销 `t_ff = 0.03 ns`（30 ps，这是 7 nm 上下比较乐观的数）。分成 `d` 级后：

```
周期 = T_logic / d + t_ff
频率 = 1 / (T_logic / d + t_ff)
```

| 级数 d | 每级逻辑 | 每级总延迟 | 频率 | 分支误预测至少丢 | 丢的时间 |
| --- | --- | --- | --- | --- | --- |
| 1（无流水线） | 1.000 ns | 1.030 ns | 0.97 GHz | 1 周期 | 1.03 ns |
| 5 | 0.200 ns | 0.230 ns | **4.35 GHz** | 5 周期 | 1.15 ns |
| 10 | 0.100 ns | 0.130 ns | 7.69 GHz | 10 周期 | 1.30 ns |
| 20 | 0.050 ns | 0.080 ns | 12.5 GHz | 20 周期 | 1.60 ns |
| 40 | 0.025 ns | 0.055 ns | 18.2 GHz | 40 周期 | 2.20 ns |
| ∞ | →0 | 0.030 ns | 33.3 GHz（渐近线） | ∞ | ∞ |

这张表要读出三件事：

1. **收益递减**：1→5 级拿到 4.5 倍频率，5→10 级只多 77%，10→20 级只多 63%，再往上全是零头。真实 CPU 还要受电压下限（约 0.7–0.8 V）与功耗密度约束：动态功耗 `P ∝ C·V²·f`，频率翻倍、功耗也接近翻倍，散热撑不住。这就是 2006 年以后主频停在 3–5 GHz 的原因（`base/17` 会把这条账推到 GPU 的「低频 × 海量核」）。
2. **误预测的绝对时间在涨**：5 级时一次预测失败丢 1.15 ns，40 级时丢 2.20 ns。深流水线把「猜错」的罚金做大了，于是分支预测必须越来越准，否则频率的收益被罚金吃掉。
3. **渐近线是 33 GHz，不是无限**：那 30 ps 的触发器开销就是硬底。真实芯片还有时钟树、供电网络、温度，最终落在 3–5 GHz。

这也解释了 **Pentium 4 的 31 级流水线跑到 3.8 GHz，却常打不过十几级的 Core 2**：分支密度一高，多出来的频率被误预测罚金吃掉。

## 10.3 五级流水线：五条指令怎么在同一张时间表上错开

### 五个阶段各自在干什么

| 阶段 | 全称 | 这一拍做的事 | 典型资源 | 失败/停顿来源 |
| --- | --- | --- | --- | --- |
| **IF** | Instruction Fetch | 用 PC 读 I-cache，取出 16–32 B 的指令字节 | I-cache、BTB、预取器 | I-cache miss、分支目标未知 |
| **ID** | Instruction Decode | 译码成微操作（µop），读架构寄存器，检查依赖 | 译码器（Zen 2 为 4 宽） | 译码宽度不够、指令过长 |
| **EX** | Execute | ALU 运算、地址生成、分支条件判断 | 4 个整数 ALU、2 个 FP 端口 | 数据没到（RAW）、除法/乘法多周期 |
| **MEM** | Memory | load 读 D-cache，store 写 store buffer | 2 load + 1 store / 周期 | L1 miss、store 转发失败 |
| **WB** | Write Back | 把结果写回架构寄存器 | 寄存器堆写口 | 写口冲突（多发射时） |

### 时空图：5 条指令、9 个节拍

纵轴是指令，横轴是节拍。每一行往右错开一格，就是「流水线」的全部含义：

```
节拍 →        1     2     3     4     5     6     7     8     9
I1: add       IF    ID    EX    MEM   WB
I2: sub             IF    ID    EX    MEM   WB
I3: and                   IF    ID    EX    MEM   WB
I4: or                          IF    ID    EX    MEM   WB
I5: xor                               IF    ID    EX    MEM   WB
                    └──── 填满 4 拍 ────┘                 └─ 排空 4 拍 ─┘
```

- **第 1–4 拍**：流水线在「填」，只有 1、2、3、4 条指令分别进入不同阶段，没有任何一条完成。这 4 拍是纯开销。
- **第 5 拍起**：每一拍都有一条指令完成（WB），直到最后一条。稳态下 **CPI = 1**（每周期完成一条）。
- **第 6–9 拍**：流水线在「排空」，IF 已经没活干，但前面还有指令在走。

### 把「填满/排空」写成公式

`d` 级流水线跑 `n` 条指令（不考虑冒险）：

```
总周期 = n + (d - 1)
CPI    = 1 + (d - 1) / n
加速比 = n·d / (n + d - 1)        （相对于一条一条串行做，每条 d 拍）
```

代入 `d = 5`：

| 指令数 n | 总周期 | CPI | 相对串行的加速比 |
| --- | --- | --- | --- |
| 1 | 5 | 5.00 | 1.00× |
| 5 | 9 | 1.80 | 2.78× |
| 20 | 24 | 1.20 | 4.17× |
| 100 | 104 | 1.04 | 4.81× |
| 10,000 | 10,004 | 1.0004 | 4.998× |

三行结论：

1. **五级流水线的理论上限是 5 倍，不是 5 个阶段各快 5 倍**。`n→∞` 时加速比才趋近 `d`，而且要求每一级延迟完全相同。
2. **短循环被填满/排空税伤得最重**：一个只跑 10 次的循环，`(10+4)/10 = 1.4` CPI，**29% 的周期花在填和排空上**。这就是循环展开（unroll）的第一条收益——不是因为少了几个 `cmp/jne`，而是把固定 4 拍的填/排空摊到更多指令上。
3. **真实流水线到不了 CPI=1**：级间延迟不均衡（最慢的一级决定周期）、冒险、cache miss、分支误预测都会插 bubble。厂商给的「IPC」是这些因素乘完的结果，不是流水线级数。

本机有一组现成的反例：§10.8 的「排序后分支」循环，每个元素 1.48 周期，循环体是 load + cmp + 条件 add + 循环控制约 4 条 µop，折合 **IPC ≈ 2.7**。**CPI 已经小于 1 了**——因为真实 CPU 不是五级标量流水线，而是 §10.5 的四到六宽超标量。五级流水线是理解「为什么能重叠」的最小模型，不是现代机器的实际结构。

## 10.4 三类冒险：流水线为什么会空转

流水线只有在「每一拍每一级都有活干」时才值钱。三类事件会让某一级空出一拍，这一拍叫 **bubble（气泡）**，也叫 **stall（停顿）**。三类冒险的名字不重要，重要的是**每一类分别由谁买单**：结构冒险靠加硬件，数据冒险靠转发 + 调度，控制冒险靠预测。

### 10.4.1 结构冒险：两条指令抢同一个部件

```c
/* 每次迭代：读 c[i]、a[i]、b[i]，写 c[i] —— 3 个 load + 1 个 store */
for (long i = 0; i < n; i++)
    c[i] += a[i] + b[i];
```

本机（Zen 2）每个周期能做 **2 个 load + 1 个 store**。上面这个循环每迭代要 3 个 load，load 端口不够，于是**平均每迭代至少 1.5 个周期**——哪怕所有数据都在 L1、哪怕 ALU 闲着。这就是结构冒险：**不是数据没准备好，是部件数量不够。** 编译器插不了 stall（端口是硬件），只能改代码形状：合并循环、把 `c[i]` 的读改写拆开、减少每迭代访存。

| 资源 | 每周期数量 | 被谁抢 |
| --- | --- | --- |
| load 端口 | 2 | 数组读、指针追逐、结构体字段 |
| store 端口 | 1 | 数组写、栈写 |
| 整数 ALU | 4 | 算术、地址生成、比较 |
| FP 加法端口 | 2 | 浮点累加、点积 |
| 除法单元 | 1（且多周期） | `idiv`、`fdiv` 会独占 |

结构冒险的工程翻译只有一句：**先数「每迭代要几次访存」，再谈算法**。`base/07` 的「连续比算法更决定速度」是存储侧的同一句话。

### 10.4.2 数据冒险：RAW 是真依赖，WAW/WAR 只是名字冲突

三种依赖的名字按「读/写」的先后排列：

| 类型 | 含义 | 例子 | 在乱序机器上 |
| --- | --- | --- | --- |
| **RAW**（Read After Write） | 后一条要读前一条刚写的值 | `x = a + b; y = x * 3;` | **真依赖**，无法消除，只能转发或等 |
| **WAW**（Write After Write） | 两条指令写同一个寄存器 | `x = a + b; x = c + d;` | 寄存器重命名后消失（写不同物理寄存器） |
| **WAR**（Write After Read） | 后一条写前一条要读的寄存器 | `y = x + 1; x = c + d;` | 寄存器重命名后消失（读旧物理寄存器） |

**RAW 的转发（forwarding/bypassing）**：`add` 在 EX 结束就算出结果，不必等它 WB 写回寄存器堆；结果从 EX/MEM 流水线寄存器直接送回下一条指令的 EX 入口：

```
节拍:          1     2     3     4     5
add r1,r2,r3   IF    ID    EX    MEM   WB
sub r4,r1,r5         IF    ID    EX    MEM   WB
                            ↑     │
                            └─────┘  转发路径：EX 的输出直接进下一条的 EX
                                      sub 的 EX 与 add 的 MEM 同拍，不用等 WB
```

转发能把「等 2 拍」压成「0 拍」，但**load 的结果要到 MEM 结束才出来**，而它的消费者下一条就要在 EX 用，转发也来不及：

```
ldr r1,[x]     IF    ID    EX    MEM   WB
add r2,r1,#1         IF    ID    EX*   EX    WB
                                  ↑
                            这里必须空一拍（load-use penalty = 1 拍）
```

这一拍是**所有流水线教科书里唯一必须记住的固定成本**。在顺序执行的五级机器上，编译器会把一条无关指令塞进这个空位（指令调度）；在乱序机器上，硬件从窗口里找一条就绪的指令填进去（§10.5）。`-O0` 的代码不调度，所以你能在反汇编里直接看到 load 之后紧跟使用它的 `add`：

```asm
# long f(long *p, long i) { long x = p[i]; return x * 3 + 1; }   gcc -O0
  1f:	mov    (%rax),%rax        ← load x
  22:	mov    %rax,-0x8(%rbp)    ← 先存回栈（-O0 的痕迹）
  26:	mov    -0x8(%rbp),%rdx    ← 再 load 回来：store-to-load 转发要 4–5 拍
  2d:	add    %rax,%rax
  30:	add    %rdx,%rax
```

`-O2` 会把 `x` 留在寄存器里，那两行栈往返直接消失——这是「同一个算法，`-O0` 比 `-O2` 慢 10 倍」的一半原因，另一半是自动向量化（§10.10 会量出来）。

**WAW/WAR 为什么在乱序机器上不算事**：架构上只有 16 个通用寄存器，硬件把它们映射到 180 个物理寄存器（Zen 2 的整数 PRF），每次写 `rax` 都分配一个新的，旧值留给还在读它的指令。名字冲突被重命名器拆掉了，**只剩 RAW 是真依赖**。

### 10.4.3 控制冒险：分支没算出来，下一条取哪里

```c
/* 分支条件依赖刚 load 进来的值：地址算得再快，也要等数据到 */
for (long i = 0; i < n; i++)
    if (a[i] >= 128) s += a[i];
```

`if` 在 EX 才算出「跳不跳」，但 IF 每拍都要取指令。EX 出结果之前，IF 已经往前取了好几条——**取哪里的指令？** 只有两个选择：停（等 EX 算完，五级流水线空 2–3 拍，深的空十几拍），或猜（按预测器继续取，猜错再作废重取）。现代 CPU 一律选猜：**「分支」在硬件上不是一条指令，是一次下注**。编译器能做的是用 PGO / `__builtin_expect` 摆好冷热路径，或改成 `cmov`；猜的动作在硬件。

### 三类冒险的总表

| 冒险 | 触发条件 | 谁来解决 | 解决不了的代价 | 你能改的代码 |
| --- | --- | --- | --- | --- |
| 结构 | 同一拍抢同一部件 | 加端口、加 ALU、分离 cache | 端口不够时 CPI 被硬顶住 | 减少每迭代访存次数、合并循环、改数据布局 |
| 数据 RAW | 后一条读前一条的结果 | 转发；load-use 插 1 拍 | 依赖链长度 × 单条延迟 | 拆累加器、改变结合顺序、提前算 |
| 数据 WAW/WAR | 复用同一个架构寄存器 | 寄存器重命名 | 顺序机器上要等；乱序机器上≈0 | 无需改，编译器/硬件已处理 |
| 控制 | 分支结果晚于取指 | 分支预测 + 推测执行 | 误预测 15–22 拍 | 排序数据、无分支写法、减少不可预测分支 |

**一句话**：结构冒险是「部件不够」，数据冒险是「值没到」，控制冒险是「地址没定」。三类都表现为「流水线空了一拍」，但修法完全不同——看到慢，先分清是哪一类，否则会把「端口不够」误判成「分支太多」，然后越优化越慢。

## 10.5 超标量与乱序：一拍取 4–6 条，窗口里同时飞 200 多条

### 从「一条流水线」到「四条并排的流水线」

五级标量流水线每拍最多完成 1 条指令。要更快，最直接的办法是**把取指、译码、执行都加宽**：每拍取 4–6 条，译码 4 条，派发 6 条 µop，后端有 4 个整数 ALU、2 个 FP 端口、2 个 load 端口。这就是**超标量（superscalar）**。

本机（Zen 2 微架构，EPYC 7K62）的公开参数与实测对照：

| 项 | 公开参数（Zen 2） | 本机实测 | 说明 |
| --- | --- | --- | --- |
| 取指/译码宽度 | 4 条/周期 | — | 指令长度解码是 x86 的瓶颈 |
| 派发宽度 | 6 µop/周期 | — | 到调度器为止 |
| 重排序缓冲 ROB | **224 条** | — | 「窗口」的物理大小 |
| 整数物理寄存器 | 180 个 | — | 重命名用 |
| FP 物理寄存器 | 160 个 | — | 重命名用 |
| 整数 ALU | 4 个 | 8 条独立 `add` 跑到 **3.11 条/周期** | 见 §10.8 |
| FP 加法端口 | 2 个 | 8 路累加跑到 **2.03 条/周期** | 见 §10.7 |
| load / store | 2 / 1 每周期 | — | 结构冒险的上限 |

「8 条独立 `add` 跑到 3.11 条/周期」值得停一下：一个每拍取 4 条、派发 6 条、有 4 个 ALU 的机器，为什么不是 4.0？因为循环体里还有 `sub` 和 `jne`，要和 8 条 `add` 一起抢派发宽度；每迭代 10 条 µop、2.57 拍，折合 **3.9 条 µop/周期**，卡在「派发 6 条、取指 4 条」之间。**3.1 条加法/周期不是「CPU 有 3 个核」，是这一拍真的同时完成了 3 条独立指令。**

### 乱序：顺序取指，乱序执行，顺序提交

```
   程序顺序（你写的）                     硬件里的实际流动
   ─────────────────                     ──────────────────────────────
   I1  load  [r1]  ← L3 miss（300 拍）
   I2  add   r2,r3,r4   ┐
   I3  add   r5,r6,r7   ├─ 与 I1 无依赖，可以先生效
   I4  mul   r8,r9,r10  ┘
   I5  add   r11,r1,r2  ← 依赖 I1，必须等
                                             ↓
   取指/译码（顺序） → 重命名 → 派发到保留站（乱序）
                                             ↓
                        执行单元按「操作数就绪」挑指令，不按程序顺序
                                             ↓
                    ROB 按程序顺序提交（retire），保证异常/中断的语义
```

三个「顺序」必须分开记：

1. **取指与译码是顺序的**：PC 只能沿着预测路径往前走。
2. **执行是乱序的**：只要操作数齐了，I4 可以先于 I3 算完；I2/I3/I4 谁先发到 ALU 由保留站（reservation station）和调度器决定。
3. **提交是顺序的**：ROB 从头到尾按程序顺序退休，前一条没完成，后面的结果不能写进架构寄存器。**你在 `gdb` 里看到的寄存器值永远对应程序顺序**，所以乱序不会让程序算错；它只让「哪条先跑」变得不可观测、不可依赖。

### 窗口：224 条 ROB 能掩盖多少延迟

ROB 是那个「同时飞着几十条」的物理容器。它不是队列长度指标，是**能容忍的延迟 × 需要的并行度**的乘积：

```
可掩盖的延迟 ≈ 窗口内独立指令数 × 每周期完成数
```

反过来：一条 L3 miss 约 40 周期、DRAM 约 300 周期（`base/07` 实测 12 ns / 93 ns）。如果每条指令平均 4 个 µop，224 条 ROB 只装得下约 56 条指令。**一次 DRAM miss 就会把 56 条填满**：后面的指令可以继续执行，直到 ROB 没有空位；一旦填满，前端停止取指，整台机器开始等那一个 cache line。

这解释了一个常见现象：**同样的代码，工作集在 L2 与在 DRAM 上的差距不只是 3.9 ns 对 93 ns（`base/07`），而是「L2 命中时窗口装得下，DRAM miss 时窗口塞满、乱序彻底失效」**。乱序只能掩盖「有独立工作可做」的延迟；没有独立工作，窗口再大也只是排队。

### 为什么「两条无关代码谁先跑」不确定

考虑两条真的无关的指令：I2 改 `r2`，I4 改 `r8`。它们都就绪时，谁先发到 ALU 取决于：

- 保留站里的年龄/优先级策略；
- 哪一条的端口先空出来；
- 哪一条的源操作数在同一个周期到达；
- 甚至取决于两条指令在 32 B 取指块里的对齐。

**这是规格允许的。** 两条工程含义：

1. **不能拿「先跑哪条」当性能保证**。微基准里把 `A` 放在 `B` 前面测出 A 快，换一次编译、换一个对齐，顺序可能反过来。要比较两个算法，必须把两者放进**同一个进程、同一份数据、交替多轮**，取最小值或中位数，而不是各跑一次。
2. **不能拿「顺序」当正确性依赖**（除非有屏障/原子操作）。乱序 + store buffer 会让两个线程看到不同的写顺序；这是 `base/13` 的 MESI 与内存屏障要解决的问题，不是本篇的流水线能管的。

### 一个隐蔽的结构冒险：4K aliasing

乱序机器允许 load 在更老的 store 之前**推测执行**，但硬件要先猜「这两个地址是不是同一个」；猜错就作废重放，代价 10–15 拍。x86 的地址比较只看低 12 位，于是两个相隔 4096 字节、实际不相干的数组可能被误判为别名（4K aliasing）。修法不是改算法，是给数组之间加 padding 或改变分配顺序，让它们不落在同一个 4 KiB 偏移上。

## 10.6 分支预测：一次猜错 15–22 拍，猜对是零

### 静态预测：只看指令本身

最早的做法是**静态**的：后向分支（循环回跳）预测 taken，前向分支（`if` 跳过一段）预测 not taken；或者编译时用 `__builtin_expect` / PGO 给一个提示位。它不需要历史，成本是一个 bit：循环上很准，数据相关的 `if` 上接近抛硬币。

### 动态预测：用过去猜未来

**两级自适应（two-level adaptive）** 是第一个真正有效的动态方案：用一个全局历史寄存器 `H` 记录最近 `h` 个分支的 taken/not-taken，用 `(PC, H)` 索引一张计数器表。它不是「记这个分支上次跳不跳」，而是「记这个分支**在这种历史模式下**跳不跳」——于是 `if (a[i] && b[i])` 这种短序列也能被学到。

2-bit 饱和计数器是最小的动态预测器，四个状态：

| 状态 | 含义 | 本次实际 taken | 本次实际 not-taken |
| --- | --- | --- | --- |
| `00` | 强 not-taken | → `01` | → `00` |
| `01` | 弱 not-taken | → `10` | → `00` |
| `10` | 弱 taken | → `11` | → `01` |
| `11` | 强 taken | → `11` | → `10` |

它比 1-bit 多一个状态：单次异常不翻转预测（长期 taken 的循环退出一次，`11→10`，下次仍猜 taken）；模式真变时要多错一次。

**TAGE** 把「多级历史」做到极致：维护几种不同长度的历史（4/8/16/32/64 位），每种配一张带 tag 的表，预测时选**命中的最长历史**；长历史能抓住「每 100 次出现一次」的规律，但在随机数据上会过拟合，所以要用 tag 和置信度淘汰。AMD Zen 系列用**感知机（perceptron）** 一类方案：历史位当特征，权重求和、在线更新。名字不同，本质相同：**用「这个分支在类似上下文里怎么走」猜下一次。**

### 猜错的代价：从 20 拍推回纳秒

猜错时，IF 已取、ID 已译码、甚至 EX 已执行的错误路径指令全部作废，从正确目标重填：

```
前端重填 ≈ 分支解析延迟 + 取指队列清空 + I-cache 重新访问 ≈ 流水线深度 + 排队
```

厂商典型值 **15–20 拍**；按 2.6 GHz 算：

```
20 拍 × 0.385 ns/拍 = 7.7 ns
```

**一次猜错，等于 7.7 ns 的纯空转。** 对比一下：一次 L1 命中约 1.5 ns，一次 L3 命中约 12 ns（`base/07`）。所以一次误预测比一次 L1 命中贵 5 倍，和一次 L2 命中同量级。

本机用「阈值扫描」把这个数推出来：数据是 0…255 的随机字节，`if (a[i] < th)` 的 taken 概率 `p = th/256`；`p` 越大，误预测越多。固定 32768 个元素（32 KiB，全在 L1）反复跑 2.6 亿次判断，取 11 轮最小值：

| 阈值 th | P(taken) | 分支版周期/元素 | `cmov` 版周期/元素 |
| --- | --- | --- | --- |
| 32 | 0.125 | 5.54 | 2.10 |
| 64 | 0.250 | 9.32 | 2.13 |
| 128 | 0.500 | 14.76 | 2.07 |
| 256 | 1.000 | 2.00 | 2.12 |

从 `p=0.25` 到 `p=0.5`，每元素多出 `14.76 - 9.32 = 5.44` 拍；taken 概率多了 0.25，所以**每次误预测约 `5.44 / 0.25 = 21.8` 拍**。本机有效主频 3.22 GHz，折合 `21.8 × 0.311 = 6.8 ns`；与厂商的 15–20 拍同量级。

### 每 100 条错一次，IPC 掉多少

设一台 4 宽机器，理想 CPI = 0.25（IPC = 4）。每 `k` 条指令有一次误预测，罚 20 拍：

```
周期 = k / 4 + 20
IPC  = k / (k/4 + 20) = 4k / (k + 80)
```

| 误预测频率 | 每 100 条错几次 | 周期/100 条 | IPC | 相对理想 |
| --- | --- | --- | --- | --- |
| 1 / 1000 | 0.1 | 25 + 2 = 27 | 3.70 | 93% |
| 1 / 100 | 1 | 25 + 20 = 45 | **2.22** | 56% |
| 1 / 50 | 2 | 25 + 40 = 65 | 1.54 | 38% |
| 1 / 20 | 5 | 25 + 100 = 125 | 0.80 | 20% |
| 1 / 10 | 10 | 25 + 200 = 225 | **0.44** | 11% |

**每 100 条错一次，4 宽机器只剩 2.22 IPC；每 20 条错一次，IPC 掉到 0.8，比五级标量还慢。** 这就是分支密集的解析器、状态机、压缩算法常常打不过「表驱动 + 无分支」的原因：不是分支指令本身贵，是它把整条流水线的并行度打掉了。

### 无分支写法：`cmov` 什么时候赢、什么时候输

C 里的三元表达式

```c
s += (a[i] >= 128) ? a[i] : 0;
```

在 x86 上可能编成 `cmov`（条件传送），而不是 `jcc`：

```asm
# gcc 12 -O2 生成（本机实测，节选）
    movzbl (%rax),%ecx
    cmp    $0x7f,%rcx
    lea    (%rdx,%rcx,1),%rsi
    cmovg  %rsi,%rdx        ← 条件成立就把 rsi 送进 rdx，不跳转
```

`cmov` 的语义是「两条路都算，按条件选一个结果」。它没有分支，所以**没有误预测**；代价是**两条路都要执行**，而且结果要等两边都算完（依赖链变长）。

本机实测（1 MiB 数组，`-O2 -fno-tree-vectorize`，CPU1）：

| 写法 | 随机数据 | 升序数据 | 结论 |
| --- | --- | --- | --- |
| `if (a[i] >= 128) s += a[i];` | 4.331 ns/元素 | 0.458 ns/元素 | 可预测时最快 |
| `s += (a[i] >= 128) ? a[i] : 0;`（`cmov`） | 0.660 ns/元素 | 0.660 ns/元素 | 不可预测时快 6.6 倍，可预测时慢 1.44 倍 |

**分界线可以算出来。** 设分支基线的每元素成本为 `B ≈ 1.48` 拍，`cmov` 为 `C ≈ 2.13` 拍，误预测率为 `m`，罚金 `P ≈ 21` 拍：

```
分支：B + m·P
cmov：C
cmov 更快的条件：m > (C - B) / P = (2.13 - 1.48) / 21 ≈ 0.031
```

**误预测率超过约 3%，`cmov` 就开始赢。** 但有三个边界：①`cmov` 两边都算，若「不取的那边」可能越界解引用，编译器不能生成 `cmov`，只能保留分支；②它拉长依赖链，结果要等两个操作数都就绪，串行循环里可能比「预测很准的分支」更慢；③掩码、`max/min`、SIMD blend 都是「用算术换跳转」，选哪个取决于端口和依赖，不取决于名字。

## 10.7 依赖链 vs 吞吐：`sum += a[i]` 为什么只能跑到 1/3 的速度

### 三行周期账

本机实测（16.8M 次 `float` 加法，全部 L2 命中，`-O2 -fno-tree-vectorize`）：

| 版本 | 总时间 | ns/加法 | 周期/加法（3.22 GHz） | 加法/周期 | 相对单链 |
| --- | --- | --- | --- | --- | --- |
| 单累加器 | 15.449 ms | 0.921 | **2.97** | 0.34 | 1.00× |
| 4 路累加器 | 3.894 ms | 0.232 | **0.75** | 1.33 | 3.97× |
| 8 路累加器 | 2.568 ms | 0.153 | **0.49** | 2.03 | 6.02× |

三个数字对应三条物理约束，一条都不能少：

1. **单链被「延迟」卡住**：Zen 2 的 `addss` 延迟是 3 拍。`s += a[i]` 里下一次加法要等上一次的 `s`，所以每 3 拍才能完成一次，吞吐 0.33 条/周期。实测 2.97 拍/次 ≈ 3 拍，完全吻合。
2. **4 路刚好填满延迟**：4 条互不相干的链，每条仍然 3 拍一次，但 4 条错开，平均每 3 拍完成 4 次 → 1.33 条/周期。实测 0.75 拍/次 = 1.33 条/周期，**4 倍不是「算了 4 次并行」，是「把 3 拍的等待用另外 3 条链填满了」**。
3. **8 路撞到「端口」天花板**：FP 加法端口只有 2 个，最多 2 条/周期，理论极限是单链的 `2 / 0.33 = 6` 倍。实测 6.02 倍，正好到顶。再加到 16 路不会更快——**瓶颈已经从延迟换成了吞吐**。

### 汇编里看到的就是「寄存器独立性」

```asm
# 单累加器：一条 addss 依赖上一条的 xmm0
.L1:  addss  (%rax),%xmm0
      add    $0x4,%rax
      cmp    %rax,%rdx
      jne    .L1

# 4 路：四条 addss 分别写 xmm0/xmm3/xmm1/xmm2，互不依赖
.L2:  addss  (%rax),%xmm0
      addss  0x4(%rax),%xmm3
      add    $0x10,%rax
      addss  -0x8(%rax),%xmm1
      addss  -0x4(%rax),%xmm2
      cmp    %rax,%rdx
      jne    .L2
```

两段循环的指令条数、访存次数、数据全一样，**唯一差别是后一条 `addss` 要不要等前一条的 `xmm0`**。拆累加器的全部功劳就在这里，与 cache、分支、向量化无关。

### 整数版：链更长，倍数一样

把「乘法 + 加法」做成依赖链（`x = x*1664525 + 1013904223`，`imul` 3 拍 + `add` 1 拍 = 4 拍），单链 vs 4 链：

| 版本 | 总时间（5000 万次运算） | ns/运算 | 周期/运算 | 运算/周期 |
| --- | --- | --- | --- | --- |
| 1 条链 | 61.696 ms | 1.234 | **3.98** | 0.25 |
| 4 条链 | 15.391 ms | 0.308 | **0.99** | 1.01 |
| 比值 | — | — | — | **4.01×** |

4 条链把 4 拍的延迟完全填满，达到 1 条/周期；但**再增加到 8 条也不会变成 2 条/周期**，因为 `imul` 只有 1 个乘法端口（本机实测 8 条链仍是约 1 条/周期）。这是「延迟」与「吞吐」的第二次分界：**先被延迟卡，再被端口卡，最后被取指/译码宽度卡。**

### 工程含义：拆的是链，不是循环

- **点积、求和、校验和、直方图**：4 路或 8 路累加器是标准做法，收益 4–6 倍，代码只多三行。
- **浮点结果会变**：`(s0+s1)+(s2+s3)` 与 `((s0+s1)+s2)+s3` 不是同一个数（`base/05`）。要可复现就用固定顺序的两两求和（pairwise/Kahan），别用「编译器高兴怎么结合就怎么结合」的 `-ffast-math`。
- **整数加法可以被编译器自由重排**，所以整数版可能在你没写 4 路时就被自动向量化；浮点版不会，除非显式开 `-ffast-math`。**「编译器会不会替我拆」取决于类型和编译选项，不取决于循环长相。**

## 10.8 实测三件事：分支、累加器、依赖链

### 环境与口径

- 机器：AMD EPYC 7K62，KVM，2 vCPU；`/proc/cpuinfo` 标称 2595 MHz。
- **绑核**：`taskset -c 1`。CPU0 的依赖 `add` 是 0.609 ns/次（1.64 GHz），CPU1 是 0.310 ns/次（3.22 GHz），同一份代码在 CPU0 上慢 1.96 倍；不指定 CPU，数会随调度漂移一倍。
- 计时：`clock_gettime(CLOCK_MONOTONIC)`，每项跑 5–11 轮取最小值；调用自身约 **35.2 ns/次**，所以每个区间都做到毫秒级。
- 编译：`gcc -O2 -fno-tree-vectorize`，让「单链 vs 4 链」比较的是标量依赖，而不是「有没有被自动向量化」。
- 没有 `perf` 和硬件计数器；下面的「周期」是用 0.310 ns/拍从墙钟换算的**量级值**，不是 PMU 读数。
- 宿主负载会让单次绝对值上浮（复跑漂移 2–3 倍），所以只信同轮比值与多轮最小值。

### ① 分支可预测 vs 不可预测

```c
#define N (1u << 20)
static unsigned char buf[N];

__attribute__((noinline, optimize("no-if-conversion,no-if-conversion2")))
static long scan(const unsigned char *a, long n) {
    long s = 0;
    for (long i = 0; i < n; i++)
        if (a[i] >= 128) s += a[i];     /* 强制生成 jcc，而不是 cmov */
    return s;
}

/* 主程序：先随机填 0..255，测一次；qsort 升序，再测一次 */
```

为什么必须加 `optimize("no-if-conversion")`：gcc 12 在 `-O2` 下会把上面这个 `if` **自动变成 `cmov`**。不关掉它，你测到的是「两次都是 `cmov`」，随机和排序当然一样快——这正是很多人「复现失败」的原因。下面是本机实测：

```
branch.random   4.542 ms   4.331 ns/elem     ← 1 MiB，随机 0..255
branch.sorted   0.480 ms   0.458 ns/elem     ← 同一份数据 qsort 之后
ratio           9.46x
cmov.random     0.692 ms   0.660 ns/elem     ← 同样数据，无分支写法
cmov.sorted     0.692 ms   0.660 ns/elem     ← 排序对 cmov 没有影响
```

**同一份 `if`、同一份数据、同一个二进制，只换数据顺序，差 9.46 倍。** 这就是「分支预测失败」最干净的证据：没有任何算法差异可以解释它。

### ② 单累加器 vs 4 路累加器

```c
#define FN 65536                       /* 256 KiB，L2 内 */
static float fa[FN];

__attribute__((noinline)) static float sum1(const float *a, long n) {
    float s = 0;
    for (long i = 0; i < n; i++) s += a[i];
    return s;
}
__attribute__((noinline)) static float sum4(const float *a, long n) {
    float s0 = 0, s1 = 0, s2 = 0, s3 = 0;
    for (long i = 0; i + 3 < n; i += 4) {
        s0 += a[i]; s1 += a[i+1]; s2 += a[i+2]; s3 += a[i+3];
    }
    return (s0 + s1) + (s2 + s3);
}
/* 每轮把整个数组扫 256 遍，共 16.8M 次加法；取 5 轮最小值 */
```

```
sum1   15.449 ms   0.921 ns/add   2.97 cyc/add   0.34 add/cyc
sum4    3.894 ms   0.232 ns/add   0.75 cyc/add   1.33 add/cyc
sum8    2.568 ms   0.153 ns/add   0.49 cyc/add   2.03 add/cyc
ratio sum1/sum4 = 3.97x    sum1/sum8 = 6.02x
```

### ③ 有依赖链 vs 独立链

```c
__attribute__((noinline)) static uint64_t chain1(uint64_t n) {
    uint64_t x = 1;
    for (uint64_t i = 0; i < n; i++) x = x * 1664525u + 1013904223u;
    return x;
}
__attribute__((noinline)) static uint64_t chain4(uint64_t n) {
    uint64_t a = 1, b = 7, c = 13, d = 29;
    for (uint64_t i = 0; i < n; i += 4) {
        a = a * 1664525u + 1013904223u;
        b = b * 1664525u + 1013904223u;
        c = c * 1664525u + 1013904223u;
        d = d * 1664525u + 1013904223u;
    }
    return a ^ b ^ c ^ d;
}
/* n = 5000 万，即 5000 万次「乘加」；取 7 轮最小值 */
```

```
chain1   61.696 ms   1.234 ns/op   3.98 cyc/op   0.25 op/cyc
chain4   15.391 ms   0.308 ns/op   0.99 cyc/op   1.01 op/cyc
ratio chain1/chain4 = 4.01x
```

### 三件事的同一张表

| 实验 | 变的那一行 | 时间（每元素/每次） | 倍数 | 卡在哪 |
| --- | --- | --- | --- | --- |
| 分支 | 数据从随机改升序 | 4.331 → 0.458 ns | **9.46×** | 控制冒险：误预测 21.8 拍/次 |
| 分支 | 改成 `cmov` | 4.331 → 0.660 ns | 6.56× | 用「两边都算」换掉跳转 |
| 累加 | 1 个 → 4 个累加器 | 0.921 → 0.232 ns | **3.97×** | RAW 依赖链：3 拍延迟 |
| 累加 | 4 个 → 8 个累加器 | 0.232 → 0.153 ns | 1.52× | FP 端口：2 条/周期封顶 |
| 依赖链 | 1 条 → 4 条 | 1.234 → 0.308 ns | **4.01×** | `imul` 4 拍延迟被 4 条链填满 |

**五个倍数，五个物理原因。** 同样「快 4 倍」，分支、依赖链、端口的修法完全不同，换个负载就失效。

## 10.9 三列账：流水线承诺了什么、收了多少、从哪开始失效

| 维度 | 承诺了什么 | 为此付了什么 | 从哪里开始失效 |
| --- | --- | --- | --- |
| **吞吐** | 稳态 CPI 可以 < 1；4–6 宽机器 IPC 到 3–4 | 面积：4 个 ALU、2 个 load 口、224 条 ROB、180 个物理寄存器；功耗随宽度与频率上升 | 端口不够（3 load/迭代）、依赖链太长（每 3 拍一次）、取指宽度不够 |
| **频率** | 切段让关键路径变短，主频从 MHz 到 GHz | 触发器 + 时钟树 + 偏斜；深流水线让误预测罚金从 5 拍涨到 40 拍；`P ∝ f·V²` 撞散热墙 | 线延迟不随晶体管缩小；电压下限；超过 ~5 GHz 后收益为零 |
| **乱序** | 用窗口掩盖 L1/L2 延迟，让无关指令先跑 | 224 条 ROB、重命名表、保留站、内存消歧的复杂度与面积 | cache miss 填满 ROB；没有独立指令可调度；4K aliasing 重放 |
| **分支预测** | 猜对时零成本，让 IF 不断流 | 预测器存储、功耗；猜错要 flush 15–22 拍 | 数据随机、模式突变、间接跳转（虚函数、`switch`）；每次 6–8 ns |
| **无分支写法** | 消掉控制冒险，随机数据下快 6.6 倍 | 两边都算；依赖链变长；可能引入非法访存，编译器不敢用 `cmov` | 可预测分支（排序数据）反而慢 1.44 倍；重的一侧很贵时更亏 |
| **多发射** | 同一拍完成多条独立指令 | 译码/派发宽度、寄存器堆端口、指令对齐敏感 | 指令间有依赖；代码对齐变化；分支密集 |
| **可移植性** | 同一份二进制在 x86/ARM 上都能跑 | 性能对微架构、对齐、数据分布、绑核极其敏感 | 换 CPU、换编译器、换数据顺序，倍数全变；微基准不可跨机比较 |

一句话收束：**流水线买到的是「一段时间里让多条指令重叠」，付出的是「顺序不再可依赖 + 对数据分布和代码布局极度敏感」。** 「莫名其妙变慢」不是玄学，是上面某一行代价到期了。

## 10.10 踩坑清单：现象 → 根因 → 定位 → 修 → 防复发

| 现象 | 根因（指回本篇） | 定位命令 | 怎么修 | 怎么防复发 |
| --- | --- | --- | --- | --- |
| 微基准显示 0.0000 ms，快得离谱 | `-O2` 发现结果没人用，把整个循环删了 | `objdump -d` 看函数体是不是只剩 `xor %eax,%eax; ret` | 用 `volatile` sink 或内联汇编 `"r"(s)` 把结果钉住 | 基准函数返回值必须被 `printf`/`volatile` 消费；先看反汇编再信时间 |
| 标量循环「快得不像话」 | `-O2` 默认开了 `-ftree-vectorize`，一次算 4/8 个 | `objdump` 看有没有 `addps`/`vpaddd`/`ymm` | 加 `-fno-tree-vectorize`（若要测标量） | 基准的编译选项写进注释；标量与向量分开测 |
| 加了 `volatile` 反而慢 3.7 倍 | `volatile` 禁止寄存器分配，每次累加都变成 load+add+store | `objdump` 看循环里有没有 `mov` 往返 | 只在「防止删除」处用一次性 `volatile` sink，不要修饰热变量 | 基准变量用 `asm volatile("" :: "r"(x))`，不要用 `volatile` 变量 |
| 同一份代码在两台机器/两个核上差 2 倍 | 本机 CPU0 1.64 GHz、CPU1 3.22 GHz；频率/邻居噪声不同 | `taskset -c N` 各跑一遍；读 `/proc/cpuinfo` | 固定核，取多轮最小值，报告核号与频率 | 基准脚本里写死 `taskset`，并打印有效频率 |
| 纳秒计时器测 100 ns 的区间，误差 30% | `clock_gettime` 自身 35.2 ns/次 | 跑一个空计时循环，量出每次调用开销 | 把区间做到 ≥100 µs，或一次测 N 次再除 | 先量计时器开销；小于 100 倍开销的区间不测 |
| 排序后基准快了，但线上没变快 | 线上数据分布不是「先全 0 后全 1」 | 打印分支 taken 比例；按分位数分组测 | 用真实分布做输入，别用 `qsort` 后的数组 | 基准输入必须来自生产采样；报告 p50/p99 而不是均值 |
| 代码加了一行 `if` 就慢 3 倍 | 误预测率超过约 3%，分支罚金吃掉多发射 | 对比 `cmov` 版与分支版；看数据分布 | 改无分支写法/掩码/查表；或先把数据排序/分桶 | 热路径里禁止「数据相关且不可预测」的分支 |

### 三个必须亲手看的现场

**① `-O2` 把循环整个删掉。** 下面这个函数在 `-O2` 下编译出来的机器码只有两条指令：

```c
__attribute__((noinline)) long dead(int *p, long n) {
    long s = 0;
    for (long i = 0; i < n; i++) s += p[i];
    return 0;                    /* s 没用上 → 整个循环是死代码 */
}
```

```
dead 0.0000 ms
0000000000001270 <dead>:
    1270:	xor    %eax,%eax
    1272:	ret
```

`s` 没返回，编译器判定循环无副作用，直接删掉。**基准的第一行检查应是反汇编，不是计时。**

**② 自动向量化把「标量」变成了「向量」。** 同一份 `s += a[i]`（`int` 数组，1M 元素），`-O0` 下 1.633 ns/元素（每步走栈、未调度），`-O2` 下 0.155 ns/元素（gcc 生成 `paddd`/`vmovdqu`，一次处理 4–8 个），加 `volatile` 后 0.570 ns/元素（慢 3.7 倍，但你测的对象已经从「吞吐」变成「store-to-load 转发」）。**同一个循环，三种编译方式在测三件不同的事。**

**③ 计时区间太短。** `clock_gettime` 35.2 ns/次：测 100 ns 的循环，开销占 35%。正确做法是循环 N 次测总时间再除 N，让总时间 ≥100 µs，并报告 N。

## 10.11 一页速记

```
【一句话】CPU 不是一条条执行指令，是一条流水线上同时飞着几十条；
         你写的顺序是提交顺序，不是执行顺序。

【三个数】
  2.6 GHz → 一拍 0.385 ns；光在真空走 11.5 cm，在硅里走 7.7–8.2 cm
  3.22 GHz（本机 CPU1）→ 一拍 0.311 ns；CPU0 只有 1.64 GHz
  一次分支误预测：15–22 拍 ≈ 6–8 ns（本机斜率 21.8 拍）

【三条公式】
  五级流水线：CPI = 1 + (d-1)/n；加速比 = n·d/(n+d-1)；n→∞ 才到 d
  误预测后的 IPC（4 宽，每 k 条错一次，罚 20 拍）：IPC = 4k/(k+80)
  延迟 vs 吞吐：单链吞吐 = 1/延迟；N 条链吞吐 = min(N/延迟, 端口数)

【三列账】
  承诺：CPI<1、IPC 3–4、乱序掩盖 L1/L2
  代价：面积/功耗、误预测 6–8 ns、对数据分布与代码对齐敏感
  崩点：依赖链、分支密集、cache miss 塞满 ROB、端口不够

【四个改法，对应四种根因】
  分支不可预测（误预测 >3%） → 无分支/cmov/掩码/排序分桶
  串行依赖（每 3–4 拍一次） → 拆 4 路累加器（注意浮点顺序）
  端口不够（3 load/迭代）    → 合并循环、改布局、减少每迭代访存
  ROB 塞满（DRAM miss）      → 分块、预取、把工作集压进 L2/L3

【一句防身】
  看到「快 N 倍」，先问：是延迟、吞吐、端口、分支，还是 cache？
  四个答案的修法互不通用。
```

## 10.12 自检 3 题

**Q1.** 一台 4 宽、ROB 224 条的机器，理想 CPI = 0.25。某循环每 100 条指令有 1 次分支误预测，罚 20 拍。求实际 IPC；如果把循环里的分支改成 `cmov`，代价是每条指令多 1 拍（100 条多 100 拍），哪个更快？

<details><summary>答案</summary>

先算分支版：100 条指令的理想周期是 `100 / 4 = 25` 拍，加一次误预测 20 拍，共 45 拍，`IPC = 100 / 45 = 2.22`。

`cmov` 版：没有误预测，但每条多 1 拍，共 `25 + 100 = 125` 拍，`IPC = 100 / 125 = 0.80`。

**分支版更快（2.22 > 0.80）。** 这与 §10.6 的「`cmov` 更快」不矛盾：那里的 `cmov` 只多一条 `lea` 和一次选择，约 0.65 拍/元素；这里假设「每条多 1 拍」，代价远大于误预测。**结论取决于「无分支的额外成本」与「误预测率 × 罚金」的比值**：本例 `C-B = 1`、`P = 20`，要 `m > 5%` 才划算，而题设是 1%。

</details>

**Q2.** 单累加器 `sum1` 实测 2.97 拍/次，4 路 0.75 拍/次，8 路 0.49 拍/次。解释三个数字各自的瓶颈；为什么 8 路不是 4 路的 2 倍，而 4 路几乎是单链的 4 倍？

<details><summary>答案</summary>

- 单链：`addss` 延迟 3 拍，下一次加法必须等上一次的 `xmm0`，所以 1 次/3 拍 = 0.33 次/拍，即 3 拍/次。实测 2.97 拍，吻合。
- 4 路：4 条独立链，每条仍 3 拍一次，但错开执行，平均 4 次/3 拍 = 1.33 次/拍，即 0.75 拍/次。**4 倍来自「用 4 条链填满 3 拍延迟」，不是「4 个加法器」**（FP 加法端口只有 2 个，4 路时还没撞到端口）。
- 8 路：理论上 8/3 = 2.67 次/拍，但 FP 加法端口只有 2 个，最多 2 次/拍，即 0.5 拍/次（实测 0.49）。**瓶颈从「延迟」切换成「吞吐」**，所以 8 路相对 4 路只快 0.75/0.49 = 1.53 倍，而不是 2 倍。

再往上加链不会更快；要更快只能减少加法次数（算法）、用 SIMD（一条指令算 4/8 个）、或换到有更多 FP 端口的机器。

</details>

**Q3.** 同一份 `if (a[i] >= 128) s += a[i];`，随机数据 4.331 ns/元素，排序后 0.458 ns/元素。有人把数据排序后上线，发现线上 P99 反而变差。解释这两个观测为什么不矛盾，并给出一个不排序也能稳定的改法。

<details><summary>答案</summary>

排序后快，是因为分支结果变成了「前一半全不取、后一半全取」，预测器只需要学一次相位变化，误预测率接近 0；随机数据每次判断都是新信息，误预测率接近 50%，每次罚 21 拍，所以慢 9.46 倍。**这是「数据分布」的功劳，不是「排序」这个动作的功劳。**

线上 P99 变差：线上分布随用户/时间变化，不是「先全 0 后全 1」；排序只改了基准那一段，真实分支仍随机。如果为排序引入 `qsort` 或额外缓冲，O(n log n) 与内存访问还会直接打爆尾延迟——均值没变，P99 变差。

不排序的稳定改法（按代价从低到高）：

1. **无分支写法**：`s += (a[i] >= 128) ? a[i] : 0;`，让编译器生成 `cmov`；随机数据下 0.660 ns，且不随顺序变化。
2. **掩码/算术**：`long m = -(a[i] >= 128); s += a[i] & m;`，完全不依赖分支预测。
3. **分桶或查表**：先按阈值把数据分两堆再各自无分支处理，或用一次 L1 表查找换掉分支；两者都要多一次内存读写，只适合批处理，不适合低延迟路径。

判断标准仍是 §10.6 的分界线：先量真实数据的误预测率，超过约 3% 再考虑无分支；否则保留分支。

</details>
