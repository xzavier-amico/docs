## 05.1 引子：一起「差 7 分钱」的对账事故，和一次甩锅

### 事故：日终对账差 0.07 元，第一嫌疑人被冤枉了

2025-09-11，某支付公司的清结算系统日终对账：

```
对账文件（渠道侧）    合计  84,327,15?.??   ← 渠道给的原始金额是对得上的
本地台账（我方汇总）  合计  84,327,15?.??
差额                 0.07 元（7 分）
差异笔数             1 笔（一笔 7.00 元的三方分摊）
```

值班同学的第一反应是「浮点精度问题吧」，于是把金额字段从 `DOUBLE` 改成 `DECIMAL(18,2)`。改完，第二天照样差 0.07 元。第三天换了个新人，翻了那一笔业务：7.00 元由三个商户等分，代码写的是

```python
per = round(total / 3, 2)   # 7.00 / 3 = 2.3333333333333335 -> 2.33
```

`2.33 × 3 = 6.99`，**每一笔分摊掉 1 分**，当天有 7 笔这种三方分摊，于是差 7 分。根因是**「先除后四舍五入，余数没人兜」**，跟浮点表示误差一点关系都没有。

这个复盘里最值得记住的不是「要兜余数」，而是那个量级对比：**在 `double` 上做 100 万笔 0.01 元的累加，误差量级是 10⁻⁷ 元**（下面 §05.1 的实验贴了真实输出）；而**「round 到分的时点不一致」每笔就能扔掉 0.5 分**。差 0.07 元的案子，可能是 round 时点问题，基本不可能是 `double` 的表示误差——**因为 1 个 `double` ulp 在 10⁸ 元上的绝对值只有 1.5×10⁻⁸ 元**。分不清这两件事的人，会把系统的金额精度从 15 位改成 18 位，然后继续差 7 分。

真实数据（`gcc -O2`，x86-64，Debian 12 / gcc 12.2，下同）：

```c
/* 口径 A: 一口气累加 100 万笔 0.01 元 */
double a = 0.0;
for (int i = 0; i < 1000000; i++) a += 0.01;
/* 口径 B: 每 100 笔做一次小计, 再把 1 万个小计相加 */
double b = 0.0;
for (int j = 0; j < 10000; j++) {
    double sub = 0.0;
    for (int i = 0; i < 100; i++) sub += 0.01;
    b += sub;
}
```

```
A 一笔一笔累加   = 10000.000000171856
B 按百笔小计累加 = 10000.000000000002
A - B            = 1.7185448086820543e-07  元 = 0.0000171854 分
A 与 10000 的差  = 1.7185629985760897e-07  元
```

**同一批流水、两种合法的汇总口径，差 1.7×10⁻⁷ 元。** 这个数字离「差 1 分」（10⁻² 元）还差 5 个数量级。所以：`double` 累加确实不是精确的（后面 §05.8 会把它推到 0.00016 元），但**对账差几分的锅，绝大多数时候不在浮点表示上，在「round 到哪一位、什么时候 round」上**。这是本篇的第一个纪律：**先把故障分到正确的层，再谈浮点**。

### 真正的浮点事故长什么样

```c
float dau = 123456789.0f;   /* 日活 1.23456789 亿 */
printf("float(123456789)=%.1f\n", (double)dau);
```

```
float(123456789)=123456792.0
float(123456789) bits=0x4CEB79A3   double bits=0x419D6F3454000000
```

**1.23456789 亿被存成 1.23456792 亿，凭空多出 3。** 日报里的日活曲线会在没有任何异常流量的情况下自己往上跳几个人。这才是浮点事故的典型形态：**不是算错，是「你以为存进去了，其实存进去的是另一个数」**。

### 那道开胃题：为什么有的能精确，有的不能

```
0.1 + 0.2 = 0.30000000000000004   (≠ 0.3)
0.5 + 0.25 = 0.75                (精确)
12.375                            (精确)
```

同一个 `double`、同一台 CPU，为什么一半精确一半不精确？这不是「精度不够所以有误差」，而是**「有一类数根本不在可表示集合里」**——一个非此即彼的集合归属问题。答案在 §05.2，一句话：**binary64 能表示的数是「分母为 2 的幂」的有理数**；0.5、0.25、0.375 是，0.1、0.2、0.05 不是。

## 05.2 一个数在二进制里到底能不能写下来：数论的判据

### 先说十进制里的同一件事，你会发现你早就懂

```
1/3 = 0.3333333333...  十进制写不完 → 只能用「约等于」表示
1/4 = 0.25             十进制写完了
1/5 = 0.2              十进制写完了
```

十进制写不完 1/3，因为 3 不是 10 的因子。**二进制写不完 1/10，因为 5 不是 2 的因子。** 这就是全部的谜底：

> **一个有理数 `p/q`（既约）能在 b 进制下被有限位写完，当且仅当 q 的所有质因子都整除 b。**

十进制 b=10=2×5，所以分母只能是 2ᵃ5ᵇ 的组合；二进制 b=2，**分母只能含因子 2**。

### 把这个判据套到 binary64 上

binary64 的一个数在数学上恒等于

```
值 = (-1)^S × 1.M₂ × 2^(E-1023)        (规格化数)
   = (-1)^S × M × 2^(E-1023-52)        (M 是 52 位整数, 前面补上隐含的 1 就是 53 位)
```

所以它**永远**是 `整数 / 2^k` 的形式——**分母必然是 2 的幂**。这就是判据的直接推论。

实测（`python3` + `fractions`，判「分母是不是 2 的幂」）：

```
    0.5  分数=         1/2  分母2的幂?  True  float=0.5      实际存储=1/2
   0.25  分数=         1/4  分母2的幂?  True  float=0.25     实际存储=1/4
  0.125  分数=         1/8  分母2的幂?  True  float=0.125    实际存储=1/8
 0.0625  分数=        1/16  分母2的幂?  True  float=0.0625   实际存储=1/16
    0.1  分数=        1/10  分母2的幂? False  float=0.1      实际存储=3602879701896397/36028797018963968
    0.2  分数=         1/5  分母2的幂? False  float=0.2      实际存储=3602879701896397/18014398509481984
    0.3  分数=        3/10  分母2的幂? False  float=0.3      实际存储=5404319552844595/18014398509481984
12.375  分数=        99/8  分母2的幂?  True  float=12.375   实际存储=99/8
```

看最后两列：`0.1` 实际存的值是 `3602879701896397 / 36028797018963968`，分母 `36028797018963968 = 2^55`。**它是一个分母为 2 的幂的数，但它不等于 1/10**——它是离 1/10 最近的那个「分母为 2 的幂」的数。误差

```
3602879701896397/2^55 - 1/10 = -5551115123125783 / (10 × 2^55) ≈ -1.54×10^-18
```

这个 10⁻¹⁸ 量级的「舍入」，就是 `0.1` 这个字面量在 `double` 里的全部真相。**注意：舍入只发生一次，之后这个位模式就固定了。** 所以「`0.1` 存不准」不是每次运算都抖动，而是**你输入的字面量本身已经被换成了另一个数**。

### 换算成位：手算 0.1 的尾数

`0.1 × 2 = 0.2 → 0`；`0.4 → 0`；`0.8 → 0`；`1.6 → 1`，剩 `0.6`；`1.2 → 1`，剩 `0.2`——**回到 0.2 了，循环开始**。于是

```
0.1 = 0.0001100110011001100110011001100110011... ₂   (1100 无限循环)
    = 1.1001100110011001100110011001100110011001100110011001|10011...₂ × 2^-4
```

竖线右边是第 53 位有效数字之后的部分，**要被舍入（round-to-nearest-even）掉**。53 位有效数字是二进制的 `1.1001...1001`（`1001` 重复 12 次 = 48 位，再加 `1001` 的前 4 位凑到 52 位尾数），这就是 §05.6 里 `0x3FB999999999999A` 那个 `A` 的来历：**最后一位不是 `9` 而是 `A`，因为在第 53 位上发生了进位**。

> 一句话：`0.1` 在二进制里是无限循环小数，`double` 只留下了它的前 53 位有效数字——**和你在纸上把 1/3 写成 0.3333 是同一件事，只是进制不同**。

## 05.3 字段拆解：S/E/M 三块积木与它们的三种状态

### binary64 与 binary32 的位图

```
binary64 (double, 8 字节, IEEE 754-1985 起, C 的 double)
 bit 63        62              52 51                                0
┌──────────────┬─────────────────┬───────────────────────────────────┐
│   S  (1 bit) │  E  (11 bit)    │            M   (52 bit)           │
│   符号        │  指数(移码 1023) │       尾数(隐含前导 1, 省掉)       │
└──────────────┴─────────────────┴───────────────────────────────────┘
  负=1/正=0      E=0: 次正规/零    1.M 里那个 "1." 是白赚的 1 位精度
                 E=2047: Inf/NaN

binary32 (float, 4 字节, C 的 float)
 bit 31   30                    23 22                            0
┌─────────┬──────────────────────┬───────────────────────────────┐
│S(1 bit) │     E  (8 bit)       │          M   (23 bit)         │
│ 符号     │  指数(移码 127)       │      尾数(隐含前导 1)          │
└─────────┴──────────────────────┴───────────────────────────────┘
```

**三个字段各管一件事，互不干扰——这是这个设计最狠的地方：**

| 字段 | 位数(binary64) | 管什么 | 改它会发生什么 |
| --- | --- | --- | --- |
| **S 符号** | 1 | 正负 | 只翻正负号，`0x8000000000000000` 就是 `-0.0` |
| **E 指数** | 11 | **量级/范围** | 决定这个数能有多大/多小；11 位给 2¹¹=2048 档，覆盖 10⁻³⁰⁸ 到 10³⁰⁸ |
| **M 尾数** | 52 | **精度/分辨率** | 决定「两个相邻的数隔多远」；多 1 位就精度翻倍，少 1 位就精度减半 |

**这就是全篇的唯一真问题的物理形态**：精度不是「算出来的」，是**上电时就焊在 M 字段的位宽里的**。你把 52 位改成 23 位（double→float），精度立刻从 15.95 位十进制掉到 7.22 位，**与你的算法好坏、CPU 多快完全无关**。

### 为什么指数用「移码 bias」而不是补码：一条能自己推出来的设计

`base/03` 讲过补码。这里为什么不用补码存指数？因为要让**「位模式的无符号整数值」与「浮点数值」的大小顺序一致**（对正数）：`E` 字段小的数一定小。用移码 `E = e + bias`，指数的 -1022..+1023 被映射到 1..2046 这个全正区间，**于是 CPU 可以直接用整数比较器比浮点数**，硬件白赚一条指令。

| 格式 | 总位宽 | S | E | M | bias | 隐含前导 1 | 有效二进制位 | 最小规格化数 | 最大有限值 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| binary16 (fp16) | 16 | 1 | 5 | 10 | 15 | 有 | 11 | 2⁻¹⁴ ≈ 6.10×10⁻⁵ | 65504 |
| bfloat16 (bf16) | 16 | 1 | 8 | 7 | 127 | 有 | 8 | 2⁻¹²⁶ ≈ 1.18×10⁻³⁸ | ≈3.39×10³⁸ |
| binary32 (float) | 32 | 1 | 8 | 23 | 127 | 有 | 24 | 2⁻¹²⁶ ≈ 1.18×10⁻³⁸ | ≈3.40×10³⁸ |
| tf32 (NVIDIA) | 19 | 1 | 8 | 10 | 127 | 有 | 11 | 同 fp32 | 同 fp32 |
| binary64 (double) | 64 | 1 | 11 | 52 | 1023 | 有 | 53 | 2⁻¹⁰²² ≈ 2.23×10⁻³⁰⁸ | ≈1.80×10³⁰⁸ |

**看 bf16 与 fp16 的那两行**：同为 16 位，bf16 把 3 位尾数换成了 3 位指数——于是 bf16 的**范围与 fp32 一模一样**（指数 8 位、bias 127），代价是精度只剩 8 位有效位。这个「尾数换范围」的取舍是 AI 芯片选 bf16 而不是 fp16 的全部原因，§05.10 展开。

### 指数区间表：E 的四种状态决定了四种数

以 binary64 为例（binary32 把 1023→127、1074→149 即可）：

| E 字段（11 位） | 实际指数 e | 尾数 M 的解释 | 类别 | 值域 / 例 |
| --- | --- | --- | --- | --- |
| `0` | `1-1023 = -1022` | `0.M`（**无**隐含 1） | **次正规数** | ±[2⁻¹⁰⁷⁴, 2⁻¹⁰²²)，间距固定 2⁻¹⁰⁷⁴ |
| `0` | — | `M == 0` | **±0** | `+0.0` / `-0.0`（`0x8000000000000000`） |
| `1 … 2046` | `E-1023`（-1022…+1023） | `1.M`（有隐含 1） | **规格化数** | ±[2⁻¹⁰²², 2¹⁰²⁴) |
| `2047` | — | `M == 0` | **Inf** | `+∞`=`0x7FF0…0` / `-∞` |
| `2047` | — | `M ≠ 0` | **NaN** | `0x7FF8000000000000`（quiet NaN） |

**三个必须记住的推论，全部能从这张表推出来：**

1. **次正规数存在，是为了「精度下探」而不是「范围下探」。** 最小的规格化数是 2⁻¹⁰²²，但 E=0 时隐含的 1 变成了 0、指数固定为 -1022，于是尾数每减 1，值就减 2⁻¹⁰⁷⁴——**这是硬件在范围用完之后用「牺牲有效位」换来的斜率**。真实值：`DBL_TRUE_MIN = 4.9406564584124654e-324 = 2^-1074`，**次正规区的 ulp 是一个常数 2⁻¹⁰⁷⁴**。
2. **`±0` 有两个。** 因为 S 是独立的 1 位，`0x0000000000000000` 和 `0x8000000000000000` 都是零，它们相等但**不**可互换（`1/±0` 见 §05.9）。
3. **`NaN` 不是一个值，是一个「指数满了且尾数非零」的编码空间**。2047 这一档里除 `M==0` 之外的 2⁵²-1 个位模式全是 NaN，这就是为什么 NaN 可以带 payload（`0x7FF8000000000001` 也是 NaN）——**也是为什么 NaN 不能参与相等比较**：它根本没有「一个值」可言。

## 05.4 手工把一个数写成 IEEE 754：`-12.375` 全流程

这一段是全篇的核心实验。**不许跳，因为后面所有关于精度的直觉都建立在「你能亲手拼出位模式」上。**

### 第一步：十进制 → 二进制（整数部分与小数部分分开算）

```
整数部分 12  = 8 + 4        = 1100₂
小数部分 0.375 = 3/8        = 0.011₂    ← 3/8 = 1/4 + 1/8 = 2^-2 + 2^-3
                            （0.375×2=0.75→取0；0.75×2=1.5→取1余0.5；0.5×2=1.0→取1余0，停）

12.375 = 1100.011₂
```

注意 `0.375 = 3/8`，分母是 2 的幂 → 按 §05.2 的判据它**必然能精确表示**。这不是巧合。

### 第二步：规格化成 `1.xxx × 2^e`

```
1100.011₂ = 1.100011₂ × 2³        ← 小数点左移 3 位
             └─┬─┘
          尾数 6 位, 前面那个 1 不用存（隐含）
所以 e = 3,  M = 100011 后面补 46 个 0 = 0x8C00000000000
```

### 第三步：指数转移码

```
E = e + bias = 3 + 1023 = 1026 = 0b10000000010 = 0x402
```

### 第四步：三块拼起来

```
S  E(11 位)     M(52 位)
1  10000000010  1000110000...0000
↓
分组: 1100 0000 0010 1000 1100 0000 ... 0000
       C    0    2    8    C    0   ...  0
    = 0xC028C00000000000
```

### 第五步：用 C 现场验伪（`union` + `%a`）

```c
#include <stdio.h>
#include <stdint.h>
#include <string.h>

int main(void) {
    double x = -12.375;
    uint64_t sgn  = 1ULL << 63;                        /* 负数 */
    uint64_t expf = (uint64_t)(3 + 1023) << 52;        /* e=3, bias 1023 */
    uint64_t man  = (uint64_t)0b100011ULL << (52 - 6); /* 1.100011 去掉隐含 1 */
    uint64_t built = sgn | expf | man;

    uint64_t real; memcpy(&real, &x, 8);               /* union 的等价写法 */
    printf("sig=0x%016lX exp=0x%016lX man=0x%013lX\n",
           (unsigned long)sgn, (unsigned long)expf, (unsigned long)man);
    printf("手工拼出   : 0x%016lX\n", (unsigned long)built);
    printf("内存真实值 : 0x%016lX  -> %s\n",
           (unsigned long)real, built == real ? "一致" : "不一致");
    printf("printf: %%.17g -> %.17g   %%a -> %a\n", x, x);
    return 0;
}
```

真实输出（`gcc -O2 -o e2 e2.c && ./e2`）：

```
sig=0x8000000000000000 exp=0x4020000000000000 man=0x8C00000000000
手工拼出   : 0xC028C00000000000
内存真实值 : 0xC028C00000000000  -> 一致
printf: %.17g -> -12.375   %a -> -0x1.8cp+3
```

**三件事同时被验证了：**

1. 我手推的 `0xC028C00000000000` 与内存里的字节**逐位一致**——说明 S/E/M 的分配我记对了。
2. `%a`（C99 的十六进制浮点格式）打印 `-0x1.8cp+3`：`1.8c` 是 `1.10001100₂` 的十六进制写法，`p+3` 就是 `×2³`。**`%a` 是浮点的 `%x`——它是唯一能把「值」直接翻译成「位」的 `printf` 格式，调浮点 bug 时第一件事就是加 `%a`。**
3. `%.17g` 打印 `-12.375` 精确还原。为什么是 17？见 §05.5 与 §05.6：`17` 是「能把 binary64 往返（round-trip）回来」的最少十进制有效位数（`DBL_DECIMAL_DIG == 17`）。

> **`%a` 的读法**：`-0x1.8cp+3` 展开成二进制 `1.1000 1100₂ × 2³ = 1100.011₂ = 12.375`。十六进制一位 = 四位二进制，所以 `%a` 的尾数部分天然按 4 位对齐，肉眼就能对回位图。

## 05.5 ulp 与精度：`24×log10(2)=7.22` 是怎么来的

### 推导：有效十进制位数 = 有效二进制位数 × log10(2)

`log10(2) ≈ 0.30103`。这个常数就是「1 个二进制位能装多少十进制信息」。

```
float : 24 位有效二进制位 → 24 × 0.30103 = 7.2247  → 7.22 位十进制
double: 53 位有效二进制位 → 53 × 0.30103 = 15.9546 → 15.95 位十进制
```

实测这三行常量（`float.h`）都跟推导一致：

```
DBL_EPSILON=2.2204460492503131e-16  FLT_EPSILON=1.1920929e-07
DBL_DECIMAL_DIG=17 FLT_DECIMAL_DIG=9  DBL_DIG=15 FLT_DIG=6
24*log10(2)=7.22472   53*log10(2)=15.95459  log10(2^24)=7.22472
```

**注意 `DBL_DIG=15` 与 `15.95` 的差别**：15 是「保证能往返的**最少**位数」的下界（保守），17 是「区分所有相邻 `double`」的**最少**位数（`DBL_DECIMAL_DIG`）。`printf("%.17g")` 打出来的就是「能唯一还原这个数」的最短十进制串——这就是 §05.6「打印出来是 0.3」的全部机关。

### ulp：相邻两个浮点数之间的距离

**ulp（unit in the last place）不是一个常数，它随指数线性增长。** 因为尾数固定 52 位，指数每加 1，同样的尾数分辨率就要乘 2：

```
ulp(x) = 2^(floor(log2|x|) - 52)        (规格化区)
```

实测表（`nextafter(x, INFINITY) - x`，真实输出）：

```
x          2^e          double 间距(ulp)     float ulp    float 相对精度
1e+00      2^0          2.2204460493e-16     1.192093e-07 1.192e-07
1e+03      2^10         2.2737367544e-13     1.220703e-04 1.192e-07
1e+06      2^19         1.1641532183e-10     6.250000e-02 6.250e-08
1e+09      2^29         1.1920928955e-07     6.400000e+01 6.400e-08
1e+12      2^39         1.2207031250e-04     6.553600e+04 6.554e-08
1e+15      2^49         1.2500000000e-01     6.710886e+07 6.711e-08
1e+16      2^53         2.0000000000e+00     1.073742e+09 1.074e-07
```

**读这张表的正确方法（这是全篇最有用的一张表）：**

| 数值区间 | `double` 的 ulp | 含义：这个量级上「最小可分辨差」 | float 的 ulp |
| --- | --- | --- | --- |
| 1 ~ 2 | 2.22×10⁻¹⁶ | 15–16 位有效数字 | 1.19×10⁻⁷ |
| 10⁶（百万） | 1.16×10⁻¹⁰ | 10 位小数；分（10⁻²）绰绰有余 | 0.0625 |
| 10⁹（十亿） | 1.19×10⁻⁷ | ns 级；金额到分仍够 | 64 |
| 10¹²（万亿） | 1.22×10⁻⁴ | 到「分」已经紧张（ulp > 0.5 分的一半） | 65536 |
| 10¹⁵ | 0.125 | **分（0.01）已经分辨不出** | 6.7×10⁷ |
| 10¹⁶ | 2.0 | 整数只能到偶数 | 1.07×10⁹ |

**关键推论：`float` 的相对精度恒为 1.19×10⁻⁷（= 2⁻²³），与量级无关；但它的绝对 ulp 随量级飞涨。** 所以「`float` 够不够用」的正确问法是：**在我要用到的最大量级上，ulp 小于我要分辨的最小单位吗？**

### 为什么 `float` 存日活/订单号会丢

```
2^24 = 16777216       ← float 能精确表示全部整数的上界
16777216.0f + 1.0f == 16777216.0f   实际输出: yes
```

`float` 的尾数是 23 位 + 隐含 1 = 24 位有效位，**一旦整数超过 2²⁴ = 16,777,216，就有一半的整数消失在集合里**（ulp 变成 2，之后变成 4、8…）。实测：

```
float(123456789)=123456792.0  int=123456792.0  丢 -3
float(123456789) bits=0x4CEB79A3   double bits=0x419D6F3454000000
```

`123456789 → 123456792`，往**上**偏 3（因为 1.23 亿处 ulp = 8，最近的可表示数是 ...792）。注意这是**确定性**偏差：**同一批数据每次跑结果一样，所以它不会触发任何「随机」告警，只会悄无声息地把数字改掉 3**。

`double` 的同一条线是 2⁵³ = 9,007,199,254,740,992：

```
2^53 = 9007199254740992  2^53+1 在 double 里 = 9007199254740992
```

所以：

| 用途 | 需要精确到 | 选型 | 依据（从 ulp 推） |
| --- | --- | --- | --- |
| 日活/订单数（≤ 10⁹） | 1 个 | `int32`/`int64`，**绝不用 float** | float 在 10⁹ 处 ulp=64 |
| 订单号（19 位雪花 ID） | 1 个 | `int64`/字符串，**绝不用 float；double 也不行** | double 在 10¹⁸ > 2⁵³ 处 ulp=128 |
| 金额（到分，总额 ≤ 10¹⁰ 元） | 0.01 | `int64` 存「分」 | double 在 10¹⁰ 处 ulp ≈ 1.9×10⁻⁶，够；但取整时点仍是坑（§05.7） |
| 科学计算（相对误差 10⁻¹⁵） | 相对 | `double` | 53×log10(2)=15.95 |
| 神经网络前向（相对误差 10⁻² ~ 10⁻³） | 相对 | `bf16`/`fp16` | 8 或 11 位有效位（§05.10） |

## 05.6 `0.1` 的真实位模式与 `0.1+0.2` 的真实结果

先把真实输出贴全，**一个数都不许猜**（`gcc -O2`，`memcpy` 取位模式；`python3` 用 `struct` 交叉验证）：

```c
#include <stdio.h>
#include <stdint.h>
#include <string.h>

static void dump(const char *tag, double x) {
    uint64_t b; memcpy(&b, &x, sizeof b);
    printf("%-10s = %-24.17g %-20a  0x%016lX\n", tag, x, x, (unsigned long)b);
}

int main(void) {
    dump("0.1", 0.1);
    dump("0.2", 0.2);
    dump("0.1+0.2", 0.1 + 0.2);
    dump("0.3", 0.3);
    dump("0.5+0.25", 0.5 + 0.25);
    printf("0.1+0.2 == 0.3 -> %s\n", (0.1 + 0.2) == 0.3 ? "true" : "false");
    printf("diff           -> %.20g\n", (0.1 + 0.2) - 0.3);
    return 0;
}
```

```
0.1        = 0.10000000000000001      0x1.999999999999ap-4  0x3FB999999999999A
0.2        = 0.20000000000000001      0x1.999999999999ap-3  0x3FC999999999999A
0.1+0.2    = 0.30000000000000004      0x1.3333333333334p-2  0x3FD3333333333334
0.3        = 0.29999999999999999      0x1.3333333333333p-2  0x3FD3333333333333
0.5+0.25   = 0.75                     0x1.8p-1              0x3FE8000000000000
0.1+0.2 == 0.3 -> false
diff           -> 5.5511151231257827021e-17
```

`python3` 交叉验证（`float.hex()` 与 `struct.pack`）：

```
0.1                  hex=0x1.999999999999ap-4     bits=0x3FB999999999999A
0.2                  hex=0x1.999999999999ap-3     bits=0x3FC999999999999A
0.30000000000000004  hex=0x1.3333333333334p-2     bits=0x3FD3333333333334
0.3                  hex=0x1.3333333333333p-2     bits=0x3FD3333333333333
```

### 三条能一眼看出的规律

**① `0.1` 与 `0.2` 的尾数位模式完全相同（`0x999999999999A`），只有指数字段差 1。**

```
0.1 = 0x3FB999999999999A   E = 0x3FB = 1019 → e = 1019-1023 = -4
0.2 = 0x3FC999999999999A   E = 0x3FC = 1020 → e = 1020-1023 = -3
```

因为 `0.2 = 0.1 × 2`，**乘 2 只是指数加 1，尾数一位不动**——这就是二进制的「移位」在浮点里的样子。所以 0.1 与 0.2 的舍入误差方向是一致的（都是「离它最近的分母为 2 的幂的数」，且略大），这就解释了为什么 `0.1+0.2` 一定**偏大**。

**② `0.1+0.2` 与 `0.3` 只差 1 个 ulp。**

```
0.1+0.2 = 0x3FD3333333333334
0.3     = 0x3FD3333333333333
                         └─ 差 1
diff    = 5.5511151231257827021e-17  =  2^-54.02 ≈ 2^-54
这个量级处的 ulp = 2^(floor(log2 0.3) - 52) = 2^(-2-52) = 2^-54 = 5.5511151231257827e-17  ✓
```

**差恰好等于 1 个 ulp，不多不少。** `0.1+0.2` 的结果在真实数学里是 0.300000000000000000000000000000...4 左右（因为两个输入都已经偏大），而机器只能停在离它最近的那一格，正好落在 0.3 的上一格——**于是差 1 ulp。**

> 顺便纠正一个常见的抄错：有人会说 `0.1+0.2` 的位模式是 `0x3FF0000000000001`。那是 `1.0000000000000002`（`1 + 2⁻⁵²`），**不是 `0.1+0.2`**。真实值就是上面那个 `0x3FD3333333333334`。凡是能贴真实输出的地方，都不要用记忆。

**③ `0.5+0.25` 精确，因为两个加数的分母都是 2 的幂，和也是。**

```
0.5  = 1/2    → 0x3FE0000000000000
0.25 = 1/4    → 0x3FD0000000000000
和   0.75     → 0x3FE8000000000000   (1.1₂ × 2^-1, 尾数只有 1 位非零 → 零舍入误差)
```

**这就是「有的能精确有的不能」的完整答案：能不能精确，由「分母是否为 2 的幂」在**进机器之前**就已决定，与运算过程无关。**

### 为什么「打印出来是 0.3」

因为 `printf` 只打你要求的位数，而**舍入到 16 位以内时，1 ulp 的差就被隐藏了**：

```
%.1f  -> 0.3
%.15g -> 0.3
%.16g -> 0.3
%.17g -> 0.30000000000000004
%.20g -> 0.30000000000000004441
```

**16 位有效数字的输出是全世界的默认值**（Python 2、老 PHP、Java `Double.toString` 的简化版、SQL 的 `DECIMAL` 显示、Excel），所以你在控制台看到的永远是 `0.3`。**「打印出来是 0.3」不是误差消失了，是显示精度把它截掉了。** 这就是为什么调试浮点必须上 `%.17g` 或 `%a`：用 16 位以下的有效位数去 debug 浮点，等于蒙着眼睛调。

一个能救命的经验：**`%.17g` 往返（打印→再解析）一定还原原值；`%.16g` 有极小的可能不还原；`%.15g` 有约 10⁻³ 概率不还原。** 所以序列化浮点、存 JSON、写 CSV 时用 17 位有效数字，不是强迫症。

## 05.7 比较与判等：`==` 什么时候能用、什么时候是定时炸弹

### `==` 的三条判决线

| 场景 | 能不能用 `==` | 理由（从 §05.2 的集合归属推） |
| --- | --- | --- |
| 两个数来自**同一条计算路径**（同一表达式、同一顺序、同一精度），且都在精确可表示范围内 | **能** | 位模式逐位相同，结果必然相等；例如 `x == x` 判 NaN |
| 计数/比较目标（`while (x != 0.0)`） | **能** | 只要 0 是可精确表示的值（它是），判断「是否到达 0」精确 |
| 「两个数在数学上应该相等」的比较（`0.1+0.2 == 0.3`） | **不能** | 两条路径的舍入不同，结果可能差 1 ulp；`Diff` 已实测 false |
| 累加结果与理论值比较 | **不能** | 误差随项数累积（§05.8） |

### 需要比较「近似相等」时的三条路，按推荐度排序

**路 1（最推荐）：根本不要用浮点存，用整数存最小单位。**

```c
/* 金额: 一律用 int64 存"分"，不出现任何 double */
int64_t amount_cents = 123456;            /* 1234.56 元 */
int64_t total_cents  = 0;
total_cents += amount_cents;              /* 精确, 无 ulp */
printf("%lld.%02lld\n", (long long)(total_cents/100), (long long)(total_cents%100));
```

账单、配额、库存、计数器、ID——**凡是「必须精确」的量，就应该用整数存最小单位。** 上限：`int64` 存分可以表示 9.22×10¹⁶ 分 = 9.22×10¹⁴ 元 = 922 万亿；存微（10⁻⁶）能到 9.22×10¹² 元。远够。**这条纪律能消灭掉 90% 的「金额对不上」问题，且与 §05.1 的事故根因（round 时点）配合起来才完整。**

**路 2：相对 eps 比较（量级很大的科学计算）。**

```c
#include <math.h>
static int nearly_eq(double a, double b) {
    double diff = fabs(a - b);
    if (a == b) return 1;                        /* 顺手处理 ±0 与 Inf */
    double scale = fmax(fabs(a), fabs(b));
    return diff <= 8.0 * DBL_EPSILON * scale;    /* 约 8 ulp 容差 */
}
```

要点：**容差必须乘上 `scale`（相对），不能用一个固定的 `1e-9`（绝对）**。因为 ulp 随量级变（§05.5 表），在 10⁹ 处 8 个 ulp 就是 9.5×10⁻⁷，而在 1 处是 1.8×10⁻¹⁵——**固定绝对容差在大量级上过严、在小量级上过松，两头都错。**

| 容差写法 | 在 1.0 附近 | 在 10⁹ 附近 | 判决 |
| --- | --- | --- | --- |
| `fabs(a-b) < 1e-9` | 过于宽松（450 万 ulp） | 过严（差 1 ulp 就判不等） | ❌ 两头错 |
| `fabs(a-b) < 8*DBL_EPSILON*fmax(|a|,|b|)` | 8 ulp | 8 ulp | ✅ 尺度自适应 |
| 绝对容差 `1e-12` **仅限**量级已知且固定（如都在 [0,1]） | 合理 | 不适用 | ⚠️ 需注释前提 |

**路 3：ULP 距离比较（最严格，用于验证库函数）。**

```
ulp_diff = |整数位模式(a) - 整数位模式(b)|      （同号时可直接减，因为移码让位模式单调）
```

这条是 `sin/cos/exp` 这类数学库验收时的标准做法——「误差 ≤ 1 ulp」比「相对误差 ≤ 1e-16」更精确。**副作用**：它跨越 ±0 和次正规区时要特殊处理，工程里一般不用，知道有这条路即可。

### `round(x*100)` 的边界：必须亲眼看的表

「金额用元存 `double`，显示/入账时 `round(x*100)`」是极常见的写法，也是极常见的 bug。实测：

```
1.005      *100 = 100.49999999999999       round=100   printf(%.2f)=1.00
2.675      *100 = 267.5                    round=268   printf(%.2f)=2.67
0.615      *100 = 61.5                     round=62    printf(%.2f)=0.61
1.115      *100 = 111.5                    round=112   printf(%.2f)=1.11
4.015      *100 = 401.49999999999994       round=401   printf(%.2f)=4.01
```

**两个方向相反的坑，同一条语句里同时出现：**

- `1.005`：数学上应入账 101 分，但 `1.005` 在 `double` 里是 `1.00499999999999989...`，乘 100 得 `100.49999999999999`，`round` 得 **100**——**比正确值少 1 分**。
- `2.675`：数学上应入账 268 分（2.675 → 2.68），机器算出来是 `267.5`，`round` 恰好得 268——**看起来对了，但过程是「半个 ulp 的运气」，换个编译器/优化等级/`-ffast-math` 就可能变 267**。
- `printf("%.2f", 1.005)` 打 `1.00` 而不是 `1.01`——**`printf` 的舍入遵守当前 FP 舍入模式（默认就近偶数）**，而 `1.005` 的真实二进制值是「小于 1.005」的，所以它就近到 `1.00`。

**正确写法（有三条，任选其一）：**

| 写法 | 适用 | 关键点 |
| --- | --- | --- |
| 输入即整数：`int64_t cents` 从 JSON/DB 读出来就是分 | 新系统 | 根本不让「元」进入内存 |
| `round(x * 100.0)` 前先加一个**明确的容差**：`floor(x*100 + 0.5 + 1e-9)` | 存量系统过渡 | 1e-9 要小于最小金额（0.01）对应的 ulp 的 10 倍，且必须写成常量并注释 |
| 用十进制库（`decimal.Decimal` / `DECIMAL(18,2)` / `libdecnumber`） | 必须严格符合「四舍五入到分」的会计规则 | 十进制运算无需二进制舍入；代价是慢 10–100 倍 |

> **`round(x*100)` 的边界是一条可以被算出来的线**：只有当 `x*100` 的结果落在 `k + 0.5` 的 ±(ulp/2) 窗口内时才有歧义；ulp 在 100 附近是 1.42×10⁻¹⁴（`2^(6-52)`），所以**「恰好等于 .5 分」的金额有极小但非零的概率被算错**，而 `1.005`、`4.015` 这类恰好落在窗口里的「人类友好数字」是重灾区。测试用例必须包含 `.005`、`.015`、`.025`、`.045`、`.065` 这一族。

## 05.8 累加：大数吃小数、Kahan 与「1e16 + 1.0 == 1e16」

### 最小例子：一个加数被整个吃掉

```
1e16             = 10000000000000000        0x1.1c37937e08p+53  0x4341C37937E08000
1e16+1.0         = 10000000000000000        0x1.1c37937e08p+53  0x4341C37937E08000
1e16+1.0 == 1e16        -> true
1e16+2.0 == 1e16        -> false
1e16+3.0 - 1e16         -> 4.0
```

**一眼能算出来的三个结论：**

1. `1e16 ≈ 2^53.15`，落在 ulp = 2 的区间（§05.5 表最后一行）。所以 `1e16 + 1.0` 的结果要舍入到最近的偶数倍 2 上——`1.0 < ulp/2 = 1.0`？**恰好等于半个 ulp**，按「就近偶数（round-half-to-even）」舍回 `1e16` 本身。**加数完整地被扔掉了，`+1` 一点痕迹都没有。**
2. `+2.0` 正好是 1 个 ulp，能表示，所以 `!= 1e16`。
3. `1e16 + 3.0` 的结果舍到 `1e16 + 4.0`（3 离 4 近还是离 2 近？|3-2|=1、|3-4|=1，平局→就近偶数→4），所以减回去是 **4.0**。**加法不再可逆，`(a+b)-b ≠ a`。**

**这不是 bug。** 这是「53 位有效数字」这条物理约束在 `1e16` 上的直接读数：**这个量级上，机器只有「每隔 2 一个刻度」的分辨力，1 根本不在刻度上。**

### 累加误差的量级：可以推导，也可以实测

朴素循环累加 n 项 `x_i`，最坏误差满足

```
|误差| ≤ (n-1) × u × Σ|x_i|        ,  u = 2^-53 ≈ 1.11×10⁻¹⁶
```

这是**上界**；实测通常是「随机游走」量级 ≈ `√n × u × Σ|x|`。用它反推 §05.1 那个对账问题：`n = 10⁶`、`Σ|x| = 10⁴ 元`、`u = 1.11×10⁻¹⁶` → 上界 `1.1×10⁻⁶ 元`，实测 `1.7×10⁻⁷ 元`（同一数量级，符合）。**要差到 1 分（10⁻² 元），需要 `n·u·Σ|x| ≥ 10⁻²`，即 `n × Σ|x| ≥ 9×10¹³`——比如 10⁶ 笔且总额 10⁸ 元，或 10⁸ 笔且总额 10⁶ 元。** 这个不等式是你在评审里反驳「浮点导致差几分」的定量武器。

### 实测：1e7 与 1e8 次累加 0.1 的四种写法

```c
long n = atol(argv[1]);
float  fs = 0.0f; for (long i = 0; i < n; i++) fs += 0.1f;
double ds = 0.0;  for (long i = 0; i < n; i++) ds += 0.1;
float  fk = 0.0f, fc = 0.0f;                       /* Kahan: 单独存"欠账" */
for (long i = 0; i < n; i++) { float y = 0.1f - fc, t = fk + y; fc = (t - fk) - y; fk = t; }
double dk = 0.0,  dc = 0.0;
for (long i = 0; i < n; i++) { double y = 0.1 - dc, t = dk + y; dc = (t - dk) - y; dk = t; }
double exact = n * 0.1;
```

真实输出（`./c 10000000` 与 `./c 100000000`）：

```
n = 10000000,  期望 10000000 * 0.1 = 1000000
float  朴素累加   = 1087937.0000000000   误差 +8.793700e+04
float  Kahan      = 1000000.0000000000   误差 +0.000000e+00
double 朴素累加   = 999999.99983897537   误差 -1.610246e-04
double Kahan      = 1000000             误差 +0.000000e+00
float 朴素 - double 朴素 = +87937.0001610246

n = 100000000,  期望 100000000 * 0.1 = 10000000
float  朴素累加   = 2097152.0000000000   误差 -7.902848e+06
float  Kahan      = 10000000.0000000000  误差 +0.000000e+00
double 朴素累加   = 9999999.9811294507   误差 -1.887055e-02
double Kahan      = 10000000            误差 +0.000000e+00
float 朴素 - double 朴素 = -7902847.9811294507
```

**这张表里有四个必须读出来的东西：**

| 观察 | 数字 | 解释（从 ulp 推） |
| --- | --- | --- |
| `float` 朴素累加 1e7 次，误差 **+8.79 万（相对 8.8%）** | +87937 | 累加值涨到 10⁶ 时 ulp = 0.0625，每次加 `0.1f` 都要舍到 0.0625 的倍数上，**系统性偏大 ~0.0088/次**，×10⁷ = 8.8×10⁴。误差不是随机的，是**偏差（bias）** |
| `float` 朴素累加 1e8 次，结果**冻结在 2097152 = 2²¹** | 2097152 | 累加值到 2²¹ 时 ulp = 0.25，`0.1f < 0.125 = ulp/2` 的一半？不：`0.1 < 0.125`，**每次加都舍回自己，和就再也涨不上去了**。程序没崩、没报错、结果是个漂亮的整数 |
| `double` 朴素 1e7 次误差 **-1.61×10⁻⁴**（0.016 分） | -1.61e-4 | 相对误差 1.6×10⁻¹⁰ ≈ √n × u = 3162 × 1.11×10⁻¹⁶ × … 同量级，符合随机游走 |
| `Kahan` 两种精度都 **误差 0** | 0 | 补偿项把每次的舍入残差留起来下次补上，误差上界从 O(n·u) 降到 O(u)（与 n 无关） |

**「`float` 累加到 2²¹ 就冻结」这一条值得单独讲**：它不是误差变大，是**运算本身失效**——`s + 0.1f == s` 恒成立。这种 bug 在生产里的形态是「计数器涨到某个值后不再变化，但 CPU/内存/日志一切正常」。**任何用 float 做单调累加的地方（指标聚合、字数统计、耗时总计）都有这条天花板。**

### 三种修法，代价与适用面不同

| 方法 | 代码量 | 误差上界 | 并行友好 | 何时用 |
| --- | --- | --- | --- | --- |
| **换 `double`** | 改一个类型 | 从 O(n·u₃₂) → O(n·u₆₄)，**精度提升 2²⁹ ≈ 5×10⁸ 倍** | ✅ | 默认答案；`float` 只是为了省内存时才用 |
| **Kahan 补偿求和** | 每项多 4 次加减 | **O(u)，与 n 无关** | ❌ 强串行依赖 | 单线程、必须用 `float` 存结果、n ≥ 10⁶ |
| **成对/分块求和（pairwise）** | 递归或按 1024 一块 | O(u·log n) | ✅✅ 天然并行 | 归约、map-reduce、GPU 内核 |
| **`long double` / `__float128` / `math.fsum`** | 换类型或调库 | 接近精确 | ✅ | 一次性的高精度校验（对照用） |

**成对求和为什么有效，一句话**：误差正比于「每个加数相对于中间和的大小」，而分块求和让「大数只在最后几步一起加」，中间的累加都在同一量级内部完成——**误差从 O(n·u) 掉到 O(u·log n)**。1e8 项时 `log₂(1e8) ≈ 27`，即误差改善约 3.7×10⁶ 倍。实测对照（`python3`）：

```
sum([1e16, 1.0, -1e16]) = 0.0    math.fsum = 1.0
sum([0.1]*10)           = 0.9999999999999999    math.fsum([0.1]*10) = 1.0
```

`sum([1e16, 1.0, -1e16])` 得到 **0.0** —— 因为左折叠先算 `1e16+1 = 1e16`（吃掉），再 `-1e16` 得 0，**那个 1.0 彻底消失**。而 `math.fsum`（Shewchuk 精确求和，等价于「先把所有项按指数对齐再相加」）得 **1.0**。**同一个列表、同一台机器、差 1.0。** 这就是「累加顺序不是实现细节，是结果的一部分」。

### 为什么 GPU / 并行归约必须用 Kahan 或 double

并行归约（GPU 的 warp shuffle、CUDA 的 block reduce、Spark 的 `reduce`、Java 的 `parallelStream().sum()`）把「一条加法链」变成「一棵加法树」，**每一步的分组方式取决于线程数、block 大小、调度顺序——也就是不确定**。两个直接后果：

1. **同一个程序跑两次结果可能不同**（线程数变了、负载均衡变了）。这在 §05.1 的对账语境里是致命的：**两份报表对不上，但两份都没错。**
2. **树形归约的误差比串行还大**，因为大数早早就被加到了一起。这就是为什么 `numpy.sum`（成对求和）与 `numpy.float32` 的大数组相加要小心，也是为什么 pytorch 的 `loss.item()` 在多次 `backward` 间会有 10⁻⁷ 量级的抖动。

**工程判据（可以直接进评审）：**

- 归约**必须可复现**（对账、审计、模型训练 loss 曲线）→ 用 `double` 累加，或用 Kahan，或**固定归约顺序**（分块 + 固定块大小，如每 1024 一项单独求和最后再相加）。
- 归约**只求数量级**（监控、图表）→ `float` 无所谓，但要在文档里写明「不确定」。
- **绝不要**在「求和结果要跟另一个系统逐位对上」的地方用 `float` 并行归约。

## 05.9 特殊值：NaN、±0、Inf，以及「`x - x` 不一定是 0」

### `NaN != NaN`：一条会传染的规则

```
NAN == NAN              -> false
NAN != NAN              -> true
```

**这不是 bug，是 IEEE 754 的规定**：NaN 表示「不是一个数」（0/0、∞-∞、`sqrt(-1)`），两个「不是数」没有理由相等。**代价是：`==` 不再是等价关系**（不自反），于是所有依赖「全序/等价关系」的算法都可能在 NaN 上崩掉：

| 场景 | 后果 | 实测证据 |
| --- | --- | --- |
| **排序** | 比较函数不构成全序，`qsort`/`sort` 的结果未定义（可能破坏数组、可能死循环） | `qsort([3,NaN,1,-2,NaN,5])` → `-2 3 nan 1 nan 5`（**没有排好**） |
| **`map`/`dict` 的 key** | `NaN != NaN`，但 `dict` 用「id 相同或 `==`」判等 → **只有同一个 NaN 对象能查到** | `d.get(原NaN) → 1`，`d.get(float('nan')) → None` |
| **聚合**（`avg`/`max`/`min`） | `max` 一旦遇到 NaN，多数实现返回 NaN 或返回错误的值；`sum` 直接把整个和污染成 NaN | `INFINITY - INFINITY` → `-nan`，之后怎么加都是 nan |
| **`GROUP BY` / `JOIN`** | SQL 里 `NaN` 与 `NULL` 是两套语义，笛卡尔积会悄悄丢行 | 依赖数据库实现，需逐库验证 |
| **缓存/去重** | 用浮点做去重 key → NaN 项永远不命中，重复插入 | 同 `dict` |

**三个防御动作：**

1. **排序/比较前清洗**：`if (!isnan(x))` 或者把 NaN 映射成一个哨兵值（如 `-Infinity` 排最前）。
2. **不要用浮点做 key**：要 key 就转成整数（乘以 10⁶ 取整）或字符串（`%a` 格式）。
3. **判断 NaN 只能用 `x != x` 或 `isnan(x)`**，永远不要写 `x == NAN`（恒 false，编译器还会给 warning）。

### `-0.0 == 0.0`，但 `1/-0.0 = -Inf`

```
-0.0             = -0                       -0x0p+0       0x8000000000000000
-0.0 == 0.0             -> true
1/-0.0                  -> -inf
1.0/0.0          = inf                      inf           0x7FF0000000000000
```

**两个零相等，但除法结果符号相反。** 因为 `-0.0` 不是「负得很小的数」，它就是「符号位为 1 的零」——§05.3 的 S 字段是独立的一位，零也有正负。这在**符号敏感**的场合会咬人：

- `atan2(-0.0, -1.0)` = `-π`，`atan2(0.0, -1.0)` = `+π`（角度差 2π）
- `log(-0.0)` = `-Inf`，`log(0.0)` = `-Inf`（相同，但 `1/x` 会分裂）
- `copysign(1.0, -0.0)` = `-1.0`，用它做符号传播时 `-0.0` 会把符号传染出去
- `printf("%g", -0.0)` 打 `-0`，很多序列化库会因此产生 `-0` 字面量，被下游当作非法输入

### Inf 的传播：一污染全污染，**而且不可逆**

```
INFINITY - INFINITY     -> -nan  isnan=1
(1e308*10) - (1e308*10) -> -nan
```

`1e308 × 10` 溢出成 `+Inf`（binary64 的最大值是 1.798×10³⁰⁸），两个 Inf 相减得 NaN。**注意：溢出到 Inf 是「饱和」，但从 Inf 回来是没有路的——`Inf - Inf` 不会给你 0，它给你 NaN。** 于是链式公式里只要中间一步溢出，后面全部变 NaN，而**中间那一步的值再也恢复不了**（信息已丢失）。

| 表达式 | 结果 | 说明 |
| --- | --- | --- |
| `1.0/0.0` | `+Inf` | 除零不 trappable（默认） |
| `-1.0/0.0` | `-Inf` | 符号来自 S 字段 |
| `0.0/0.0` | `NaN` | 无意义 |
| `Inf + 1` | `Inf` | 饱和 |
| `Inf × 0` | `NaN` | 无意义 |
| `Inf - Inf` | `NaN` | **不可逆的信息损失** |

### `x - x` 不一定是 0

```
0.1+0.2 - (0.1+0.2)  -> 0        (x==x -> true)
```

在这个例子里 `x - x` 确实是 0（IEEE 754 规定同一有限值相减得 `+0`）。**但下面两种情况 `x - x ≠ 0`：**

1. **`x` 是 Inf**：`Inf - Inf = NaN`（见上）。
2. **编译器把 `x` 算了两次且两次结果不同**（`-ffast-math`、x87 80 位中间结果被 spill、`volatile` 缺失导致的重复求值）——这时 `x - x` 是两个不同位模式相减，得到非零。
3. **`x` 是 NaN**：`NaN - NaN = NaN`。

第 2 条的历史版本就是下面这个坑。

### `FLT_EVAL_METHOD` 与 x87 80 位：一个已经死掉但还在报错的坑

```
FLT_EVAL_METHOD=0
```

我当前这台机器（x86-64 + SSE2 默认）打印 `0`——表示「所有运算都按类型的实际精度求值」，`float` 就是 binary32，`double` 就是 binary64。**但在 32 位 x86 上把 `float` 交给 x87 FPU 算时，`FLT_EVAL_METHOD` 是 `2`：所有中间结果都按 80 位扩展精度（binary80，64 位尾数）算，只在最后存回内存时截断。**

这个「比你以为的更准」的实现，制造了三个经典坑：

| 现象 | 机制 | 现在还需要管吗 |
| --- | --- | --- |
| `double x = 0.1; if (x == 0.1) ...` 在 32 位机上偶尔 false | 一边走 80 位寄存器、一边走 64 位内存 | 只在 32 位 x86 + 未指定 `-mfpmath=sse` 时；x86-64 默认 SSE，`FLT_EVAL_METHOD=0` |
| 同一段循环，`-O0` 与 `-O2` 结果差 1 ulp | 优化器少 spill，中间一直留在 80 位寄存器 | 同上，以及 `-ffast-math` 会主动重排 |
| 浮点结果在 ARM 与 x86 上不同 | ARM64 无 80 位扩展，`float` 严格按 binary32 | 跨平台时**必须**用 `double` 或整数，别依赖 `float` 的中间精度 |

**当代工程结论**：x86-64 上 `FLT_EVAL_METHOD == 0`，这个坑基本只剩「交叉编译到 32 位 ARM/x86」与「`-ffast-math`」两个入口。**但纪律不变：不要依赖「中间结果比类型精度更高」；跨平台对账的数字类型选 `double` 或整数。**

## 05.10 低精度浮点预告：fp16 / bf16 / tf32 为什么给 AI 用

§05.3 那张格式表已经给出了答案的骨架，这里只把「为什么」补齐。**一切低精度的取舍都是同一句话：把尾数位换成指数位，或者把尾数位直接砍掉，用精度换吞吐/带宽。**

| 格式 | S/E/M | 有效位 | 十进制精度 | 动态范围 | 位模式实测（`0.1`） |
| --- | --- | --- | --- | --- | --- |
| fp16 | 1/5/10 | 11 | ≈3.31 位（11×0.301） | ±6.1×10⁻⁵ … 65504 | `0x2E66` → 回读 `0.0999755859375`（误差 2.4×10⁻⁵） |
| bf16 | 1/8/7 | 8 | ≈2.41 位 | ±1.18×10⁻³⁸ … 3.39×10³⁸ | `0x3DCD` → 回读 `0.10009765625`（误差 9.8×10⁻⁵） |
| tf32 | 1/8/10 | 11 | ≈3.31 位 | 同 fp32 | 截断 fp32 的尾数到 10 位 |
| fp32 | 1/8/23 | 24 | ≈7.22 位 | ±1.18×10⁻³⁸ … 3.40×10³⁸ | `0x3DCCCCCD` |

真实输出（`python3`，`struct.pack('<e')` 走 fp16，bf16 用「加 0x8000 后截高 16 位」的 round-to-nearest-even 近似）：

```
fp16(0.1) bits=0x2E66 回读=0.0999755859375
bf16(0.1) bits=0x3DCD 回读=0.10009765625
```

**三个关键推论：**

1. **bf16 与 fp16 的差别不是「精度谁高」，是「范围够不够」。** 训练里 `loss`、梯度、激活值的动态范围可能跨 10³⁰，fp16 的指数只有 5 位（上限 65504）**会直接溢出成 Inf**，必须配 loss scaling 才能用；bf16 的指数 8 位给了和 fp32 一样的范围，**不用 loss scaling 就能跑**——代价是尾数只有 7 位（精度 ≈ 2.4 位十进制，比 fp16 差 3 倍）。**AI 业界选 bf16 做训练、fp16 做推理，根因就在这张表的「动态范围」一列。**
2. **低精度的收益与「带宽/面积」成正比，与「数学正确性」无关。** 一个 fp16 数占 2 字节，一个 fp32 占 4 字节 → 同样的显存带宽能搬双倍数据；矩阵乘单元的面积与位宽平方相关 → 16 位乘加器比 32 位省约 4 倍硅面积。**所以低精度的钱，买的是「每秒能喂多少个 MAC」，不是「算得多准」。**
3. **混合精度（fp16/bf16 算、fp32 累加）是必须的。** 因为 §05.8 的结论在 GPU 上更狠：一个 4096 项的点积如果全程 bf16 累加，8 位有效位的误差按 O(n·u) 会吃掉全部结果。**所以每个张量核的 MAC 单元都是「低精度输入 × 高精度累加器」**——这是 §05.8 的表与 §05.3 的位宽表在硬件里的合体。

→ 结构侧（SIMT、warp、SM、显存层级）：`base/16`；→ roofline 与「为什么 GPU 主频低」：`base/17`；→ GEMM 优化阶梯与张量核里的混合精度：`base/20`。

## 05.11 三列账与踩坑清单

### 三列账：IEEE 754 承诺了什么、收了你多少钱、从哪开始崩

| 账 | 内容 |
| --- | --- |
| **承诺了什么** | ① **统一**：同一段 C 代码在任何遵守 IEEE 754 的机器上得到逐位相同的结果（这是可复现计算的地基）；② **相对精度恒定**：`double` 相对误差恒为 2⁻⁵³ ≈ 1.11×10⁻¹⁶，与数值大小无关；③ **范围极大**：一个 8 字节的 `double` 覆盖 10⁻³⁰⁸ … 10³⁰⁸，跨 616 个数量级，用整数做不到；④ **特殊值有定义**：±0/±Inf/NaN 的运算规则是确定的，不会「未定义行为」；⑤ **舍入可控**：四种舍入模式（就近偶数/向上/向下/向零）由硬件与 `fesetround` 指定 |
| **为此付了什么** | ① **精度被位宽焊死**：52 位尾数 → 15.95 位十进制，与算法无关；② **间距不固定**：ulp 随指数线性增长（§05.5 表），10¹⁶ 处整数只能到偶数；③ **加法不可结合**：`(a+b)+c ≠ a+(b+c)`，累加顺序变成结果的一部分；④ **相等不再是等价关系**：`NaN != NaN`，全序被破坏，排序/去重/聚合全要有 NaN 分支；⑤ **表示与字面量不等**：`0.1` 进内存就被换成另一个数，误差发生在**输入那一刻**；⑥ **速度**：x86 上 `float`/`double` 的加乘是 3–5 cycle 延迟（SSE），比整数慢，除法 10–20 cycle；⑦ **跨平台不保证**：`-ffast-math`、x87 80 位、`FLT_EVAL_METHOD`、非规格化数的 flush-to-zero 都能破坏「逐位相同」 |
| **从哪里开始崩** | ① **比较相等**：`0.1+0.2 == 0.3` 是 false（§05.6）；② **单调累加**：`float` 到 2²¹ 后 `s += x` 失效（§05.8，实测冻结在 2097152）；③ **大数吃小数**：`1e16 + 1.0 == 1e16`（§05.8）；④ **round 到分的边界**：`1.005` 入账成 1.00（§05.7）；⑤ **以 ID/计数为载体**：`float(123456789) = 123456792`（§05.5）；⑥ **并行归约不可复现**：线程数变了结果就变（§05.8）；⑦ **NaN 进入排序/分组/缓存 key**：排序结果被破坏、缓存永不命中（§05.9） |

### 踩坑清单（现象 → 根因 → 怎么定位 → 怎么修 → 怎么防）

| 现象 | 根因（指回本篇哪一节） | 怎么定位 | 怎么修 | 怎么防复发 |
| --- | --- | --- | --- | --- |
| 对账差几分钱，改精度没用 | round 时点不一致 / 分摊余数没人兜（§05.1、§05.7） | 把一天流水按「先 round 再累加」与「先累加再 round」两种口径各跑一遍，看差额是否恰好是「笔数 × 0~0.5 分」 | 统一口径（先累加后 round）+ 余数进最大项；金额改整数分 | 对账测试用例必须含 `.005/.015/.025` 族与被 3、7 整除的分摊 |
| 控制台看 `0.3`，代码里 `==0.3` 是 false | `printf` 只打 16 位有效数字（§05.6） | 加 `%.17g` 或 `%a` 打印 | 用 eps 比较或整数化 | Code review 禁令：浮点比较必须走 `nearly_eq` 或整数；调试打印一律 `%.17g` |
| 计数器涨到某个值后不再变化 | `float` 累加冻结（§05.8，实测 2²¹） | 打印累加值看是否是 2 的幂；`s + x == s` 断言 | 换 `double`/`int64`/Kahan | 指标类字段的类型审计：任何计数器禁止 `float` |
| 日活/订单数每天多几个人或少几个人 | `float` 整数精度上界 2²⁴（§05.5） | `printf("%.1f", x)` 与原整数对比 | 换 `int64` | 表结构评审：`FLOAT/DOUBLE` 存「个/次/元」一律打回 |
| 同一批数据两份报表对不上，两边都没错 | 累加顺序/并行归约不确定（§05.8） | 固定线程数重跑；对比单线程串行结果 | `double` + Kahan 或固定分块顺序 | 归约代码必须写明「顺序」或「可复现」 |
| 排序后顺序很奇怪 / 数组被破坏 | NaN 破坏全序（§05.9） | 检查输入是否有 NaN（`x != x`） | 排序前清洗 NaN 或用 `total_order` 比较 | 数据入口做 NaN/Inf 校验，脏数据不进内存 |
| 缓存命中率异常低 / 去重不生效 | 浮点做 key，NaN 永不命中（§05.9） | 打印 key 的 `%a` | 换成定点整数或字符串 | 架构约束：任何缓存 key 禁止浮点 |
| 金额存 `DECIMAL(18,2)` 还是差 | 业务层用的是 `double` 中转（§05.7） | 在 DAO 层前后各打一次 `%.17g` | 全链路整数分或全链路 decimal | 传输协议里金额字段必须是字符串或整数 |
| GPU/多线程下 loss 每次抖动 10⁻⁷ | float 并行归约（§05.8） | 单卡单线程 vs 多卡对比 | `double` 累加或 Kahan | 训练脚本记录「可复现性开关」 |

## 05.12 一页速记

```
一个 float = 1 位符号 + E 位指数(移码) + M 位尾数(隐含前导 1)
           = (-1)^S × 1.M × 2^(E-bias)
精度由 M 的位宽焊死：float 24 位有效 → 7.22 位十进制；double 53 位 → 15.95 位
  （推导：有效二进制位 × log10(2) = 有效位 × 0.30103）

能不能精确表示，是"分母是不是 2 的幂"的集合归属问题，与算法无关：
  1/2 1/4 1/8 0.375 12.375  → 精确
  1/10 1/5 3/10 0.1 0.2 0.3 → 只能是"离它最近的那个数"

ulp 随量级线性增长：ulp(x) = 2^(floor(log2|x|) - 52)
  1 附近 2.2e-16 ｜ 1e9 附近 1.2e-7 ｜ 1e15 附近 0.125 ｜ 1e16 附近 2.0

三条铁律：
  ① 必须精确的量（钱、ID、计数、配额）→ 整数存最小单位，绝不放浮点
  ② 必须比较的量 → eps 相对比较（容差乘量级），或整数化
  ③ 必须求和的量 → double 起步；float 求和大数据用 Kahan/成对求和；并行归约必须固定顺序

特殊值：
  NaN != NaN（排序/去重/聚合/缓存全部要有分支）；-0.0 == 0.0 但 1/-0.0 = -Inf
  Inf 饱和但不可逆：Inf - Inf = NaN（信息永久丢失）

调浮点 bug 的两个 printf：
  printf("%.17g", x)  ← 能唯一还原位模式的最短十进制
  printf("%a",    x)  ← 直接看 S/E/M 的十六进制（1.8cp+3 = 1100.011b = 12.375）
```

## 05.13 自检 3 题

**Q1.** `double(1e16) + 1.0 == 1e16` 为什么为真？`1e16 + 3.0 - 1e16` 为什么等于 4 而不是 3？

<details><summary>答案</summary>

`1e16 ≈ 2^53.15`，落在 `floor(log2 x) = 53` 的区间，因此 `ulp = 2^(53-52) = 2`。也就是说这个量级上**机器只有「2、4、6、8…」这些刻度，奇数根本不在刻度上**。

- `1e16 + 1.0`：1.0 恰好是半个 ulp，按「就近偶数（round-half-to-even）」舍回 `1e16` 本身，于是 `== 1e16` 为真，**整个加数被丢弃**。
- `1e16 + 3.0`：3 落在两个刻度 2 与 4 的正中（`|3-2| = |3-4| = 1`），平局时「就近偶数」把尾数末位清成 0，于是舍到 `1e16 + 4.0`；再减 `1e16` 得 **4.0**。

推论：在这个量级上**加法不再可逆**（`(a+b)-b ≠ a`），而且误差不是随机的、是确定的——所以它不会触发任何告警。修法：这类量必须用 `int64`（2⁶³ 覆盖 9.2×10¹⁸）或 `long double`/`__int128`。

</details>

**Q2.** 为什么 `0.5 + 0.25` 精确，而 `0.1 + 0.2` 不精确？请给出判据、`0.1+0.2` 的真实位模式，以及它和 `0.3` 差多少。

<details><summary>答案</summary>

**判据**：IEEE 754 的数恒等于 `M × 2^e`（M 为整数），所以可表示集合就是「分母为 2 的幂的有理数」。`0.5 = 1/2`、`0.25 = 1/4` 的分母都是 2 的幂 → 精确；`0.1 = 1/10`、`0.2 = 1/5` 的分母含因子 5，二进制下是无限循环小数 → **只能存最接近的那个数**。

`0.5 + 0.25 = 1.1₂ × 2⁻¹ = 0.75 = 0x3FE8000000000000`，尾数只有 1 位非零，零舍入误差。

**真实位模式（实测，不是猜）**：

```
0.1      = 0x3FB999999999999A
0.2      = 0x3FC999999999999A
0.1+0.2  = 0x3FD3333333333334
0.3      = 0x3FD3333333333333
diff     = 5.5511151231257827021e-17 = 2^-54 = 该量级的 1 个 ulp
```

注意 `0.1` 与 `0.2` 的尾数位模式完全相同（`0x999999999999A`），只差指数字段 1 —— 因为 `0.2 = 0.1 × 2` 在浮点里就是指数加 1。两个输入都略大于真值，所以和也偏大，正好落在 `0.3` 的上一格。

常见抄错：`0x3FF0000000000001` 是 `1.0000000000000002`，**不是** `0.1+0.2`。

</details>

**Q3.** 一段用 `float` 累加 1e8 次 `0.1f` 的代码，跑完打印出 `2097152.000000`——程序没崩、没有 NaN、没有 Inf，为什么结果是这样？你会怎么定位和修复？

<details><summary>答案</summary>

**根因**：累加到 `s = 2²¹ = 2097152` 时，该量级的 `ulp = 2^(21-23) = 0.25`，半个 ulp 是 0.125；而待加的 `0.1f < 0.125`，**每次加法的结果按「就近偶数」舍回 `s` 自己**，于是 `s + 0.1f == s` 恒成立，和永久冻结在 2²¹。这不是「误差变大」，是**运算本身失效**。

为什么恰好是 2²¹：它是这一族里第一个「ulp/2 > 0.1」的幂次刻度（`2²⁰` 处 ulp = 0.125、半 ulp = 0.0625 < 0.1，还能涨；到 `2²¹` 处半 ulp = 0.125 > 0.1，涨不动了）。

**定位手法**：① 在循环里加一条断言 `assert(s + 0.1f != s)`，它会在 2²¹ 处第一次失败；② `printf("%.17g", s)` 看一眼是否是个 2 的幂；③ 换个 n（1e6 也能看到 `float` 已经偏出 8.8 万，见 §05.8 实测表）——**1e6 时是误差、1e8 时是冻结，同一根因的两个阶段**。

**修复**：换 `double`（误差降到 -1.9×10⁻²，仍是误差但已可容忍）；要求「与理论值逐位一致」就上 Kahan 补偿（实测误差 0）或用 `math.fsum` 等精确求和；如果只是为了计数，直接用 `int64`。**永远不要用 `float` 做单调累加**——它的天花板是 `2²¹` 这个具体的数。

</details>
