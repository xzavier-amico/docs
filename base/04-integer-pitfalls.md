## 04.1 引子：三行「绝对正确」的代码

下面三行都能通过编译、都能过 code review、在测试环境都返回正确答案。它们错在同一个地方：**把人脑里的「数学整数」当成了机器上的「定宽位模式」**。

```c
int32_t price_cents = 1999;        /* 19.99 元 */
int32_t qty         = 1500000;     /* 150 万件 */
int32_t total       = price_cents * qty;   /* 期望 2,998,500,000 分 = 29,985,000.00 元 */
```

期望值 2,998,500,000 分，而 `int32_t` 能表示的上界是 2,147,483,647。真实结果是把 2,998,500,000 放进 mod 2³² 环：

```
2,998,500,000 − 4,294,967,296 = −1,296,467,296
```

于是 `total` = **−12,964,672.96 元**。负数金额，还是负得毫无规律的数。注意它**不是**「差一点」：−1,296,467,296 与 2,998,500,000 之间差了 4,294,967,296，正好一个 2³²，这就是「模」的全部含义。

第二行，`(a+b)/2` 求两个数的中间值——写二分查找的人天天写：

```
a = b = 2,000,000,000
a + b = 4,000,000,000 − 4,294,967,296 = −294,967,296
(int32_t)(a+b)/2 = −147,483,648      真实答案应为 2,000,000,000
```

差值 2,147,483,648，又是 2³¹。修法两条：`a + (b - a) / 2`（前提 `b ≥ a`），或 `(int64_t)a + b` 之后再除。**两数都合法、运算也合法，结果非法**——这是整数陷阱区别于其它 bug 的地方：没有哪一行的输入是非法的，非法性在「两个合法值的中点」这个位置上。

第三行更隐蔽，它连「值」都还没算，坏在**位模式**上：

```c
int   x = 1 << 31;                    /* C：若 int 是 32 位，这是 UB（移位进符号位） */
unsigned y = 1u << 31;                /* 2147483648，合法 */
long long z = 1LL << 31;              /* 2147483648，合法 */
```

x86-64 上这三行实测给出 `x = -2147483648`、`y = 2147483648`、`z = 2147483648`（见 §04.9 实验）。`x << 31` 被标准判为未定义行为，是因为 C 的 `int` 是**有符号**的、溢出是 UB；硬件不会因此报错，它老老实实把位搬到第 31 位，于是同一个 32 位模式 `0x80000000` 被解释成了 −2147483648。**不是编译器错了，是你用错了「环的模」。**

三行代码，三种错法，同一条真问题：

> **每次整数运算都是在固定位宽上做模运算。「值」与「位模式」必须分开看；C / Java / Go 的全部差异，都是「谁在何时把位宽扩宽或截断」。**

## 04.2 位宽清单：C 只承诺下界，Go 与 Java 各自拍板

C 标准从不规定 `int` 是几位，它只规定**最小宽度**和**相对顺序**：`sizeof(char) ≤ sizeof(short) ≤ sizeof(int) ≤ sizeof(long) ≤ sizeof(long long)`，且 `char` 恰好 1 字节、`short` ≥ 16 位、`int` ≥ 16 位、`long` ≥ 32 位、`long long` ≥ 64 位。于是同一个 `long` 在三种 ABI 里是三个不同的数：

| 类型 | C 标准最小宽度 | LP64（Linux / macOS，x86-64 与 AArch64） | LLP64（Windows x86-64） | ILP32（32 位 Linux / Windows） |
| --- | --- | --- | --- | --- |
| `char` | ≥ 8 | 8 | 8 | 8 |
| `short` | ≥ 16 | 16 | 16 | 16 |
| `int` | ≥ 16 | **32** | **32** | **32** |
| `long` | ≥ 32 | **64** | **32** | **32** |
| `long long` | ≥ 64 | 64 | 64 | 64 |
| 指针 / `size_t` | 不规定 | **64** | **64** | **32** |
| `time_t`（glibc 2.39） | 不规定 | **64** | 64 | **32**（2038 的根） |

名字里的字母就是宽度顺序：**L**ong / **P**ointer / **I**nt。LP64 = long 与指针都是 64；LLP64 = long long 与指针 64、long 仍是 32；ILP32 = int / long / 指针全是 32。

这张表的工程后果只有一句：**凡是跨平台的 C 代码，`long` 一律不可用于「我要 64 位」**。要 64 位就写 `int64_t`，要「能装下指针」就写 `intptr_t`，要「能装下一个对象大小」就写 `size_t`。这四类「带用途的名字」比宽度名字更重要，因为它们的宽度是编译器替你选的：

| 类型 | 语义（不是宽度！） | 有无符号 | 典型踩坑 |
| --- | --- | --- | --- |
| `size_t` | 任何对象的大小、数组下标、`sizeof` 的结果 | **无符号** | 相减得负数 → 变成 1.8e19；与有符号数比较 → 有符号那侧被转无符号 |
| `ssize_t` | 「可能失败的字节数」，`read`/`write` 的返回值 | 有符号 | 只在这里有符号，混用 `size_t` 就来回转 |
| `ptrdiff_t` | 两个指针之差 | **有符号** | 与 `size_t` 混算时符号被吞 |
| `intptr_t` / `uintptr_t` | 装得下一个指针的整数 | 有 / 无 | 只该用于「把指针当数」的场合（哈希、对齐、标记位） |
| `off_t` | 文件偏移 | 有符号 | 32 位下默认 32 位 → 2 GiB 上限；要 `_FILE_OFFSET_BITS=64` + `fseeko` |
| `intmax_t` / `uintmax_t` | 最宽整数，`printf` 用 `%jd` | 有 / 无 | 打印 `size_t` 必须 `%zu`，写 `%d` 是 UB |
| `time_t` | 日历时间（秒） | 有符号 | 32 位下 2038-01-19 03:14:07 UTC 撞墙 |

本机实测（Debian 12 / gcc 12 / x86-64，LP64）：

```
sizeof(int)=4 sizeof(long)=8 sizeof(size_t)=8 sizeof(off_t)=8
sizeof(ssize_t)=8 sizeof(intptr_t)=8 sizeof(intmax_t)=8
SIZE_MAX=18446744073709551615  PTRDIFF_MAX=9223372036854775807
(size_t)-1 = 18446744073709551615
```

最后一行值得盯三秒：`(size_t)-1` 是 `SIZE_MAX`，不是 −1。这就是「把 −1 送进无符号」的全部后果——**它在环上换了个名字，值变成了 2⁶⁴−1**。

Go 的取舍与 C 相反：**宽度写进名字，只有 `int` / `uint` / `uintptr` 随平台**。

| Go 类型 | 宽度 | 说明 |
| --- | --- | --- |
| `int8/16/32/64`、`uint8/16/32/64` | 固定 | 与 C 的 `intN_t` 一一对应 |
| `byte` / `rune` | 8 / 32 | `byte = uint8`，`rune = int32`（不是 `uint32`） |
| `int` / `uint` | **32 或 64，看平台** | 只用于「下标、长度、循环变量」这类不需要精确宽度的地方 |
| `uintptr` | 等于指针宽度 | 唯一的「指针当整数」出口，`unsafe` 才用 |
| 溢出行为 | **静默回绕** | 运行期 wrap；**常量表达式在编译期报错** |

实测同一份 `strconv.IntSize` 在两种架构下的取值：

```
$ go run is.go                    # GOARCH=amd64
int bits = 64
$ GOARCH=386 go run is.go
int bits = 32
```

Java 是第三条路：**全部定宽，没有平台差异，没有 unsigned**。

| Java 类型 | 宽度 | 备注 |
| --- | --- | --- |
| `byte` / `short` / `int` / `long` | 8 / 16 / 32 / 64 | 全部有符号，规范锁死 |
| `char` | 16 | **唯一的无符号整数类型**，且是字符语义 |
| 溢出 | **静默回绕**（规范明确定义为 mod 2ⁿ） | 与 C 的 UB 不同：Java 保证结果 |
| 需要报错时 | `Math.addExact` / `multiplyExact` / `toIntExact` | 显式换成抛 `ArithmeticException` |

Java 的“宽度锁死”带来一个直接好处：**同一段代码在任何 JVM 上得到同一个位模式**，这是「一次编写到处运行」在数值层唯一的真实含义。C 做不到（宽度不定），Go 做不到（`int` 不定），Java 做到了，代价是丢掉 unsigned 与 8 位以下的零扩展语义。

## 04.3 整型提升与 usual arithmetic conversions

C 里两个操作数做二元运算前，编译器会按一张固定规则表把它们的类型改掉——改的是**类型**，不是值（值只是随之被扩宽或截断）。这条规则叫 usual arithmetic conversions，它是 §04.1 里 `-1 < sizeof(x)` 恒假的唯一起因。

```
                       a op b   (op 是 + - * / % & | ^ << >> < == …)
                          │
   ① 整型提升 (integer promotion)：只作用于 rank < int 的类型
      char / signed char / unsigned char / short / unsigned short / _Bool / 位域
        ├─ int 能表示它的全部值 ──────> 转 int
        └─ 否则（如 16 位机的 unsigned short）──> 转 unsigned int
                          │
   ② 两边类型相同？ ── 是 ──> 结束，就用这个类型算
                          │ 否
   ③ 有一边是浮点？ ── 是 ──> long double > double > float，向高者转
                          │ 否（两边都是整型，进入 ④）
   ④ 整型 rank 比较：long long > long > int > short > char（同 rank 里有/无符号并列）
        ├─(a) rank 相同，一有符号一无符号 ──> 两边都转成「无符号那个」
        ├─(b) 无符号那边 rank 更高 ────────> 有符号那边转成无符号那边的类型
        ├─(c) 有符号那边 rank 更高，且它能表示无符号那边的全部值
        │                                   ──> 无符号那边转成有符号那边的类型
        └─(d) 否则（有符号方 rank 更高但表示不全，例如 long vs unsigned int）
                                            ──> 两边都转成「有符号方类型的无符号版本」
```

三个必须当场验证的推论：

```c
printf("%d\n", (uint32_t)-1 > 0);        /* 1  —— 必然成立，无符号恒 ≥ 0 */
printf("%d\n", -1 < sizeof(int));        /* 0  —— 恒假！见下面推导 */
printf("%d\n", -1 < (int)sizeof(int));   /* 1  —— 强转之后才正常 */
```

`-1 < sizeof(int)` 为什么恒假：`sizeof` 的类型是 `size_t`，在 LP64 上它是 `unsigned long`（rank 高于 `int`），命中流程图的 **(b)**：`int` 的 −1 被转成 `unsigned long`，位模式从 `0xFFFFFFFFFFFFFFFF`… 一路零扩展成 `18446744073709551615`。于是比较实际变成了 `18446744073709551615 < 8`，答案只能是 0。**不是比较算错了，是 −1 在被比较之前已经改名叫 1.8×10¹⁹。**

同一个机制下，`size_t` 的减法同样致命：

```c
const char *p = "hello";
size_t n = strlen(p) - 6;      /* 5 - 6，在 size_t 里 = 18446744073709551615 */
if (n < sizeof(buf)) { /* 竟然成立 —— 缓冲区溢出 */ }
```

实测 `strlen(p) - 6 = 18446744073709551615`。这是「整数下溢变成巨大正数」这一类漏洞的共同模板，机制全部在流程图第 (a)/(b) 条里。

整型提升本身也会「帮你」把结果改掉，方向正好相反：

```c
unsigned char x = 250, y = 250;
printf("%d\n", x * y);            /* 62500 —— 两边都提升成 int 再乘，没溢出 */
unsigned char z = x * y;          /* 36    —— 回写 8 位时截断：62500 mod 256 */
uint16_t a = 65535;
printf("%d\n", a * 2);            /* 131070 —— 提升到 int，所以没有 16 位回绕 */
```

实测三行分别是 `62500`、`36`、`131070`。**提升让中间结果更宽（这是保护），赋回窄类型时截断（这是伤害）**——两步的位模式完全不同，而 C 允许你在同一行里不写一个强转就完成它们。

Go 的选择是**直接禁止混合**：没有任何隐式数值转换，不同数值类型之间必须显式写 `T(v)`。这不是「更严格」，而是一个设计判断——既然隐式转换规则复杂到没人记得住（上面那张流程图就是证据），那就把「谁来扩宽」这件事从编译器手里收回到程序员手里，代价是所有混合算的地方都要写一堆强转。Java 则保留隐式提升但**只有一张小表**：

| 参与运算的类型 | 提升结果 | 说明 |
| --- | --- | --- |
| `byte`、`short`、`char`（任意组合） | `int` | 与 C 的整型提升同义，但没有「int 装不下」的分支 |
| 有 `long` | `long` | |
| 有 `float`（无 `double`） | `float` | |
| 有 `double` | `double` | |
| 一侧是 `String` 且 op 是 `+` | `String` 拼接 | 这是唯一非数值的 `+`，也是最常见的类型意外 |

Java 表里没有 unsigned，所以整张表只有「向更宽的有符号靠」一个方向，**不可能出现「−1 变成 1.8×10¹⁹」的那一类**。它换来的坑是另一类：`byte b = -1; b >>> 4` 先被提升为 `int`，于是高位补进来 28 个 1，结果是 `268435455` 而不是你以为的 `15`。**没有 unsigned 不等于没有符号扩展。**

## 04.4 截断与扩宽：符号扩展 vs 零扩展

扩宽（8 → 32）有两种做法，选哪一种**取决于源类型的符号性，与目标类型无关**：

```
源 8 位              符号扩展 (int8_t → int32_t)         零扩展 (uint8_t → uint32_t)
0xFF = 1111 1111  →  1111 1111 1111 ... 1111 1111     →  0000 0000 0000 ... 1111 1111
                     0xFFFFFFFF  (= −1)                   0x000000FF  (= 255)
0x80 = 1000 0000  →  1111 1111 1111 ... 1000 0000     →  0000 0000 0000 ... 1000 0000
                     0xFFFFFF80  (= −128)                 0x00000080  (= 128)
```

指令层面看得最清楚，`gcc -O1` 生成的三个函数，每个只剩一条指令：

```
0000000000000000 <sign_extend>:          # int32_t f(int8_t v)
   0:   movsbl %dil,%eax                 # mov  sign  byte → long
   4:   ret
0000000000000005 <zero_extend>:          # uint32_t f(uint8_t v)
   5:   movzbl %dil,%eax                 # mov  zero  byte → long
   9:   ret
000000000000000a <widen32>:              # int64_t f(int32_t v)
   a:   movslq %edi,%rax                 # mov  sign  long → quad
   d:   ret
```

`movsbl` 与 `movzbl` 只差一个字母，语义差 2³¹ 级别的值。这不是「编译器的小聪明」：**扩展方式由源类型的有符号性决定，是类型系统在指令层的投影**。所以「我把 `int8_t` 换成 `uint8_t` 只是语义更清楚」这句话是错的，它换的是机器码。

把 8 位拓宽到 32 位、再拓宽到 64 位的全部符号组合：

| 8 位位模式 | 解释为 `int8_t` | `int32_t`（符号扩展） | `int64_t` | 解释为 `uint8_t` | `uint32_t`（零扩展） | `int64_t` |
| --- | --- | --- | --- | --- | --- | --- |
| `0xFF` | −1 | −1 / `0xFFFFFFFF` | −1 / `0xFFFF…FF` | 255 | 255 / `0x000000FF` | 255 |
| `0x80` | −128 | −128 / `0xFFFFFF80` | −128 | 128 | 128 / `0x00000080` | 128 |
| `0x7F` | 127 | 127 / `0x0000007F` | 127 | 127 | 127 | 127 |
| `0x00` | 0 | 0 | 0 | 0 | 0 | 0 |

实测的关键两行（C）：

```
(int8_t)0xFF  → int32  0xffffffff  = -1     |  (uint8_t)0xFF → uint32 0x000000ff = 255
(int8_t)0x80  → int32  -128                 |  (uint16_t)0x8000 → uint32 = 32768
```

32 → 64 的坑更贵，因为它是「32 位系统上正确、迁到 64 位就错」的原型：

```
uint32_t u = 0xFFFFFFFF;          int32_t s = -1;
(int64_t)u = 4294967295   （零扩展）     (int64_t)s = -1   （符号扩展）
(int64_t)(int32_t)u = -1  （先截后扩，解读方式变了）
```

Go 与 Java 里同样的表：Go 的 `int32(u)` 与 `int64(u)` 都是显式截断/扩宽，`uint64(-1)` 是**编译错误**（`cannot convert -1 (untyped int constant) to type uint64`），只有 `uint64(uint32(-1))` 这种「经由一个无符号类型」的写法才合法；Java 的 `(byte)0xFF = -1`、`(int)(char)(byte)-1 = 65535`——**两次强转，先经 16 位无符号 char 成了 65535，再一次宽化**，实测如此。

截断（32 → 8）则是无条件丢掉高位，与符号无关，但结果同样要按目标类型的符号性重新解释：`(uint8_t)62500 = 36`（62500 = 244×256 + 36），`(int8_t)200 = -56`（200 − 256）。

## 04.5 移位：右移有两种，移位量有边界

左移只有一种（低位补 0），右移有两种，C 里**由实现决定用哪一种**，Java 把两种都给了你，Go 只给一种（算术）。

| 表达式 | C（GCC/Clang，x86-64 实测） | Go | Java |
| --- | --- | --- | --- |
| `0xFFFFFFFFu >> 1` | `0x7FFFFFFF`（逻辑右移） | 同为无符号类型 → `0x7FFFFFFF` | 无 unsigned，对应 `>>>` → `0x7FFFFFFF` |
| `(int)0xFFFFFFFF >> 1` | `0xFFFFFFFF`（算术右移，实现定义） | `-1 >> 1 = -1` | `-1 >> 1 = -1` |
| `-1 >>> 1` | 无此运算符 | 无此运算符 | `2147483647` |
| 移位量 ≥ 位宽 | **UB** | **定义为 0**（`uint64(1)<<64 = 0`） | **掩码 `& 0x1F` / `& 0x3F`**（`1<<32 = 1`） |
| 有符号左移溢出 | UB（C++20 起定义为回绕） | 定义为回绕 | 定义为回绕 |

实测（C，`1u << 32` 与 `1u << 33`）：

```
u=0xffffffff  u>>1 =0x7fffffff  u>>4 =0x0fffffff
s=0xffffffff  s>>1 =0xffffffff  s>>4 =0xffffffff
1u << 32 (UB, x86 实测) = 0x00000001   1u << 33 = 0x00000002
x*2=2000  x<<1=2000  一致
y*2 wrap=-2147483648  y<<1 wrap=-2147483648  一致
-16>>1=-8  -16>>2=-4  等价于 /2 /4 向下取整
```

三件事在这里同时发生：

**① 同一个 `0xFFFFFFFF >> 1` 有两个答案。** 差别只在「右移时高位补 0 还是补符号位」。CPU 的 `shr` 补 0、`sar` 补符号位，编译器按操作数的**类型**选一条（无符号 → `shr`，有符号 → `sar`）。所以「`>>` 是除以 2 的幂」这句话只在无符号或非负数上成立。

**② 移位量 ≥ 位宽是 UB，但硬件只在低 5/6 位上看你的移位量。** x86 的 `shl`/`shr` 用操作数宽度决定取模：32 位操作数取 `count & 31`，64 位取 `count & 63`。于是 `1u << 32` 在 x86 上等于 `1u << 0 = 1`——**一次 UB 换来了一个「看起来正常」的结果**，这才是它最危险的地方：你测出来是 1，换到 ARM64（`lsl` 直接把结果清零）或换成常量折叠的编译器（GCC 会把 `1u << 32` 警告成 `-Wshift-count-overflow` 并给出 0 或任意值）就全变了。Go 与 Java 不给你这个不确定性：Go 定义「移 n 次 1 位」→ 移 64 次就是 0；Java 干脆掩码。

**③ `x << 1` 与 `x * 2` 在溢出时给同一个位模式，但一个 UB、一个定义。** 实测 `y = 0x40000000` 时两者都是 `-2147483648`（因为补码的左移就是模 2ⁿ 乘 2，硬件同一套加法器）。但 `x << 1` 在 C 里若溢出是 UB，编译器可以假设「不发生溢出」进而做出任意优化；`x * 2` 同样是 UB。**所以两个都不是安全写法**，只是恰好在 x86-64 + gcc -O1 上答案一致。

最容易被忽略的一条不等价：**`x / 2` 与 `x >> 1` 对负数是两个结果**。

```
-7 / 2 = -3   （C99 起：商向零截断）
-7 >> 1 = -4  （算术右移 = 向下取整 = floor）
```

实测 C、Go、Java 三个语言都是 `-7/2 = -3`、`-7>>1 = -4`。所以「用右移优化除法」这一步，只在被除数非负时等价；对负数，差 1。Python 反而是 `-7//2 = -4`、`-7%2 = 1`——**Python 的 `//` 是 floor 除法，与 C 家族相反**，跨语言移植时这是高频错。

## 04.6 除法与取模：唯一能触发硬件异常的整数运算

整数世界里有一处**真的会让 CPU 报异常**的地方：`INT_MIN / -1`。

x86 的 `idiv` 做的是「被除数 ÷ 除数 = 商 + 余数」，商必须装进与被除数同宽的目标寄存器。`INT_MIN / -1 = 2³¹` 的数学结果超出 `int32_t` 上界 1，于是**商溢出**，CPU 触发 `#DE`（Divide Error），Linux 内核把它翻译成 `SIGFPE` 投给进程：

```
即将执行 INT_MIN /-SIGFPE(8): x86 idiv 商溢出 -> CPU 触发 #DE
exit=136            # 128 + 8(SIGFPE)
```

汇编层面就两条指令，没有任何检查，异常由硬件抛出：

```
1202:   cltd                 # 把 eax 的符号位扩到 edx:eax（64 位被除数）
1203:   idiv   %ecx          # 32位除法；商放不进 eax → #DE
```

注意 `SIGFPE` 的字面意思是 floating-point exception，但它与浮点毫无关系——这个名字是历史遗留。**整数除法的失败方式不是「返回错误值」，而是「给进程发一个信号」**，所以它能在任何没有装信号处理器的服务里直接把进程干掉（退出码 136）。

三种语言在这里分道扬镳：

| 表达式 | C（x86-64，gcc） | Go | Java |
| --- | --- | --- | --- |
| `INT_MIN / -1` | **UB**；x86 的 `idiv` → `SIGFPE`，进程死 | **定义回绕**：`MinInt64/-1 = MinInt64` | **定义回绕**：`-2147483648`，不抛异常 |
| `INT_MIN % -1` | 同样 UB（x86 上也走同一条 `idiv`） | `0` | `0` |
| 需要报错时 | 自己判断 | 自己判断 | `Math.floorDiv`/`Math.floorMod` 也回绕；`Math.toIntExact` 只查转换 |

Go 的实测输出是 `MinInt64=-9223372036854775808  MinInt64/-1=-9223372036854775808  MinInt64%-1=0`——**它返回了数学上不可能的结果，并且不 panic**。Java 同样是 `-2147483648`。这一条可以当作「定义良好的回绕」与「UB」的判据：Go/Java 让程序继续跑（结果错），C 让程序死（至少你知道出事了）。

余数的符号规则是第二个高频错点：**C99 起（以及 Go、Java），商向零截断，余数与被除数同号**。

| 表达式 | C / Go / Java | Python（floor 除法） |
| --- | --- | --- |
| `-7 / 2` | `-3` | `-4` |
| `-7 % 2` | `-1`（**负**） | `1`（正） |
| `7 / -2` | `-3` | `-4` |
| `7 % -2` | `1` | `-1` |
| 恒等式 | `(a/b)*b + a%b == a` | `(a//b)*b + a%b == a` |

实测 C：`neg=-3 rem=-1`；Go：`-7/2=-3  -7%2=-1  7%-2=1`；Java：`-7/2 = -3  -7%2 = -1  7%-2 = 1`。**三个语言一致，Python 不一致。** 所以「哈希取桶」这种用 `%` 的地方，负数键在 C 家族里会得到负下标，必须写成 `((a % b) + b) % b`。

最后一条判据是本篇最实用的：**`a % b` 什么时候能换成 `a & (b-1)`？**

| 条件 | `a % b` | `a & (b-1)` | 是否等价 |
| --- | --- | --- | --- |
| `b` 是 2 的幂，`a` **无符号** | 同 | 同 | **等价**，且 `&` 是 1 cycle vs `idiv` 20+ cycle |
| `b` 是 2 的幂，`a` 有符号且 `a ≥ 0` | 同 | 同 | 等价 |
| `b` 是 2 的幂，`a` 有符号且 `a < 0` | `-7 % 4 = -3` | `-7 & 3 = 1` | **不等价** |
| `b` 不是 2 的幂 | 只有 `%` | 不成立 | 不等价 |

实测 `-7 & 3 = 1` 而 `-7 % 4 = -3`。原因在位模式：`-7` 是 `…1111 1001`，与 `3 = …0000 0011` 相与得 `1`——`&` 拿到的是「模 4 的最小非负剩余」，而 `%` 拿到的是「向零截断后的余数」，两者差一个 `b`。所以 `n & (n-1)` 判 2 的幂、`i & (cap-1)` 取环形下标，这两个写法**必须保证操作数无符号或非负**，否则高位那串 1 会漏进掩码里。编译器很清楚这件事：对无符号 `%` 常量 2 的幂，它会自动生成 `and`；对有符号则要额外插几条修正指令——所以「有符号取模更慢」不是因为 CPU 偏心，是因为它要额外算那个符号修正。

## 04.7 位运算的工程用法：掩码、位图、popcount 与对齐

位运算在工程里只干四件事：**切出位段、并行处理位、数位、把数凑成对齐的倍数**。每一件都对应一个物理事实。

### 掩码：从地址里切出页内偏移

一张 4 KiB 页表，页内偏移就是地址的低 12 位，因为 `4096 = 2¹²`：

```
addr = 0x00007f3a2b6c1a37
       高位 ─────────────┘└── 低 12 位 = 0xa37 = 2615  ← 4 KiB 页内偏移
页号  = addr >> 12  = 0x7f3a2b6c1
```

实测三种页大小下的切法：

```
addr         = 0x00007f3a2b6c1a37
页内偏移 4K  = 0xa37  (2615)        # addr & 0xFFF
页内偏移 64K = 0x1a37               # addr & 0xFFFF
2MB 页内偏移 = 0xc1a37              # addr & 0x1FFFFF
虚拟页号     = 0x7f3a2b6c1          # addr >> 12
```

一个 `and`、一个 `shr`，各 1 cycle。这就是「页大小必须是 2 的幂」的工程理由——如果是 3 KiB 页，每一次地址翻译都要做除法，而除法是 20+ cycle。机制细节 → `base/26`。

### 位图与布隆过滤器：把 8 个布尔压成 1 字节

位图的全部内容就是一次除法换一次移位加一次与：

```c
uint64_t bits[N];                       /* N 个 64 位字 = 64N 个槽 */
static inline void set_bit(uint64_t *b, size_t i)   { b[i >> 6] |= (1ULL << (i & 63)); }
static inline int  get_bit(const uint64_t *b, size_t i){ return (b[i >> 6] >> (i & 63)) & 1; }
```

账很简单：100 万个用户 ID 的存在性，`bool` 数组＝1,000,000 B ≈ 1 MB；位图＝1,000,000 / 8 = 125,000 B ≈ 122 KiB，**8×**，而且这 122 KiB 在 L2 里放得下（典型 L2 = 512 KiB–1 MiB），`bool` 数组的 1 MB 放不下——**省的不只是内存，是一次 L2 命中（≈14 cycle）与一次 L3/DRAM（≈200 cycle）的差**。布隆过滤器把这一层再往前推：位图存「有」，布隆用 k 个哈希置 k 位，用可控的假阳性率换更小的空间，`m/n = 10`、`k = 7` 时假阳性约 0.8%。

### popcount：数一数有几个 1

```
popcount(0xdeadbeefcafebabe)=46
ctz(1<<20)=20  clz32(1<<20)=11
```

`__builtin_popcountll` 编成 `popcnt` 指令是 1 cycle（延迟 3 cycle，Skylake 级），没有 POPCNT 时编译器展开成 SWAR 五步（经典 `x - ((x>>1)&0x55…)`）。这两个函数的用途不是「算法题」：`ctz` 用来「找第一个空闲槽位」（分发器、jemalloc 的位图分箱），`clz` 用来「算 2 的幂上取整」和「浮点指数提取」。它们是「位图结构」和「位运算 CPU 指令」之间的桥。

### 对齐：`(n + 7) & ~7` 的回绕

把 `n` 上取整到 8 的倍数，一句 `(n + 7) & ~7`，跑出来的规律是：

```
(8+7)&~7=8   (9+7)&~7=16   (100+7)&~7=104
```

但如果 `n` 已经接近 `SIZE_MAX`，`n + 7` 会**回绕**：

```
n=SIZE_MAX-3=0xfffffffffffffffc  ->  (n+7)&~7 = 0x0   (比 n 还小)
SIZE_MAX=18446744073709551615
```

`(n+7)` 在无符号加法里溢出成 `3`，`3 & ~7 = 0`。于是「按 n 算出来的对齐长度」变成了 0——上游若拿它去 `malloc` 再 `memcpy(dst, src, n)`，这就是一类真实的堆溢出模板（**整数溢出 → 分配过小 → 拷贝过大**）。这里只讲机制与判据，不展开利用手法（→ `base/33`）。

判据只有一条：**任何「先加常数再比较/分配」的表达式，都要先问「加法的和会不会越过类型上界」**。写法上把校验挪到加法之前：

```c
static int align_up(size_t n, size_t *out) {
    if (n > SIZE_MAX - 7) return -1;      /* 加法前先挡住回绕 */
    *out = (n + 7) & ~(size_t)7;
    return 0;
}
```

同一条纪律在乘法上更贵：`hdr + count * 4`。32 位累加器里 `0x40000000 * 4` 会截成 `0`，于是「要 4 GiB」的被算成「要 32 字节」——实测见 §04.9 的 `money.c` 输出。

## 04.8 三类真实事故：现象 → 位模式根因 → 定位 → 修

下面三类事故的共同点：**每一行的输入都是合法值，坏的是「位宽不够」与「符号解释错了」这两件看不见的事**。

| # | 现象 | 位模式根因（可推导） | 怎么定位 | 怎么修 |
| --- | --- | --- | --- | --- |
| 1 | 金额列出现负数，对账差了整整一个 2³²，退款金额荒唐 | `int32_t` 累加，每笔 1000.00 元（100,000 分），上界 2,147,483,647 分 = 21,474,836.47 元 → **第 21,475 笔**就回绕：实测 −2,147,467,296 分 | 用 `int64_t` 复算同一批数据比对；`-fsanitize=signed-integer-overflow`；对账时按 `sum % 2**32` 反查 | 金额一律 `int64_t` 存**最小货币单位**（分/微元）；DB 用 `DECIMAL(18,2)` 或 `BIGINT`；禁止 `int` 存任何金额 |
| 2 | 时间跳到 1970 或 1901，定时任务全部错过触发窗口 | 秒级时间戳乘 1000 存进 `int32_t`：上界 2,147,483,647 ms = **1970-01-25 20:31:23 UTC** 就撞墙；秒本身的上界是 2,147,483,647 s = **2038-01-19 03:14:07 UTC** | 直接算：`int32_max / 1000 / 86400 = 24.855` 天；`date -u -d @2147483647` | 时间戳全程 `int64`（ms / µs / ns 一律）；`time_t` 在 ILP32 上显式用 `int64_t`；跨版本时区/单位在 API 边界就定死 |
| 3 | 偶发堆溢出 / 崩溃，只在「很大的请求」上复现 | `size_t n = strlen(s) - 6` 得 1.8×10¹⁹，或 `hdr + len*4` 在 32 位截断成 32 字节，分配过小 | 打开 `-fsanitize=address,undefined`；`valgrind`；在分配点打印「请求长度 vs 实际分配」 | 分配前先做「上界检查」（`n > SIZE_MAX - 7` 这类）；长度用 `size_t` 但**比较时两侧同类型**；`strlen` 结果不许减法 |

三条账里的数字都是算出来的，不是估的：

```
int32 上限        2,147,483,647
  ÷100（分）    = 21,474,836.47 元        ← 事故 1 的金额天花板
  ÷1000（ms）   = 2,147,483.647 秒 = 24.855 天  → 1970-01-25 20:31:23 UTC
  ÷1（秒）      = 2,147,483,647 秒       → 2038-01-19 03:14:07 UTC
uint32 上限       4,294,967,295 秒       → 2106-02-07 06:28:15 UTC（「2106 问题」）
int32 存纳秒      2,147,483,647 ns       = 2.147 秒        ← 连一次 RPC 都不够
int32 存微秒      2,147,483,647 µs       = 35 分 47 秒
int64 上限        9.22×10¹⁸ 秒           ≈ 2.92×10¹¹ 年
```

这张表说明一件事：**「用 int 存时间戳」在不同单位下的寿命差 9 个数量级**（秒：68 年；毫秒：24.9 天；微秒：35.8 分钟；纳秒：2.15 秒）。所以「时间戳用 int 也没出事」这句话永远缺一个单位。

## 04.10 三列账：承诺 / 代价 / 崩点

| 承诺了什么 | 为此付了什么 | 从哪里开始失效 |
| --- | --- | --- |
| **「整数是精确的」**——不同于浮点，整数运算无舍入误差，`a+b-b == a` 在无溢出时恒成立 | 固定位宽：n 位只能表示 2ⁿ 个值，代价是范围上下界都是硬墙，且墙外没有「近似」只有「回绕」 | 一旦结果超出 `[MIN, MAX]`：无符号回绕（定义）、有符号溢出（C 里 UB / Go、Java 回绕）。**这一刻「精确」变成「精确地错」** |
| **「类型只是给编译器看的」**——值相同就一样 | 类型决定三条机器码：扩展方式（`movsbl`/`movzbl`）、移位方式（`sar`/`shr`）、除法方式（`idiv` 有无符号）。代价是多一次强转就多一条指令 | 在任何「隐式转换」处：整型提升、usual arithmetic conversions、`size_t` 与 `int` 混算、`int32` 与 `int64` 混算。**位模式没变，解释变了** |
| **「位运算最快」**——`&`/`|`/`^`/`<<` 都 1 cycle，比 `%`/`/` 的 20+ cycle 便宜一个量级 | 只在**无符号或非负**语义下等价：`a & (b-1) == a % b` 成立要 `b` 是 2 的幂且 `a ≥ 0`。代价是你必须自己保证这两条，编译器不会替你验 | `a < 0` 时 `&` 给「最小非负剩余」、`%` 给「向零余数」，差一个 `b`。掩码类代码（哈希取桶、环形缓冲、页内偏移）在负数下标上全线偏移 |
| **「`idiv` 会告诉你除错了」**——硬件有 `#DE` 异常，比返回错误值诚实 | 代价是这个「告诉」的方式是**杀进程**（SIGFPE），而且 C 里它是 UB，编译器可以假设它不发生 | `INT_MIN / -1` 与 `% 0` 两个入口。前者在 Go/Java 被定义成回绕（**不报错，结果错**），在 C + x86 上是 `exit 136` |

四行账可以压成一句：**整数运算的每一个「承诺」都附一个「模」，而模的边界不在你的代码里，在类型的宽度里。**

## 04.12 一页速记

```
固定位宽 + 模运算 —— 本篇的唯一真问题
  n 位类型只能装 2ⁿ 个值；「值」与「位模式」必须分开看
  C/Java/Go 的全部差异 = 谁在何时把位宽扩宽或截断

位宽（LP64 / LLP64 / ILP32）
  C  只规定最小宽度与顺序：short≥16  int≥16  long≥32  long long≥64
     要精确宽度就写 intN_t；size_t 无符号、ptrdiff_t 有符号、off_t 可 32 位
  Go  intN 全定宽；int/uint 随平台（amd64→64、386→32）；常量溢出=编译错误
  Java byte/short/int/long 全定宽、全有符号（char 是唯一无符号）；溢出回绕有定义

隐式转换（C 的两步）
  ① 整型提升：rank < int 的（char/short/位域）→ int
  ② usual arithmetic conversions：向 rank 高者；同 rank 一有一无符号 → 转无符号
     ⇒ -1 < sizeof(x) 恒假（-1 → 2⁶⁴-1）；strlen(s)-6 = 1.8e19

扩宽 vs 截断
  int8_t→int32_t  movsbl 符号扩展 0xFF→0xFFFFFFFF
  uint8_t→uint32_t movzbl 零扩展  0xFF→0x000000FF
  32→64：uint32 值 0xFFFFFFFF 零扩展成 4294967295，不是 -1

移位
  右移两种：shr（补 0）/ sar（补符号），由操作数类型决定
  -1>>1=-1，0xFFFFFFFFu>>1=0x7FFFFFFF，-1>>>1=2147483647(Java)
  移位量 ≥ 位宽：C 是 UB；x86 硬件取 &31/&63（1u<<32=1）；Go 得 0；Java 掩码
  x>>1 ≠ x/2 当 x<0（-7>>1=-4，-7/2=-3）

除法取模
  INT_MIN/-1：C UB（x86 idiv → SIGFPE，exit 136）；Go/Java 回绕不报错
  余数符号跟被除数：-7%2=-1, 7%-2=1（C99/Go/Java 一致，Python 相反）
  a & (b-1) == a % b  iff  b 是 2 的幂 且 a 无符号或 a≥0

边界数字（记这 6 个）
  INT32_MAX 2,147,483,647 = 21.47 亿分 = 2147.48 万元
  秒  → 2038-01-19 03:14:07 UTC
  毫秒 → 1970-01-25 20:31:23 UTC（24.86 天）
  微秒 → 35 分 47 秒       纳秒 → 2.147 秒
  UINT32_MAX 秒 → 2106-02-07 06:28:15 UTC

自查三问（写在 code review 模板里）
  1 这个加法/乘法的最大可能值有没有超过类型上界？
  2 这次比较的两侧，是不是同符号、同宽度？
  3 这个分配的 size 是怎么算出来的，算的时候会不会回绕？
```

## 04.13 自检题

**Q1.** 某服务的金额字段是 `int32_t`（单位：分），单笔 1000.00 元，日增 300 万笔。为什么它在第 21,475 笔就出错，而不是「差不多 2,147 万笔」？请给出回绕前后的两个数字，并说明为什么「用 `uint32_t` 存分」也不能解决问题。

<details><summary>答案</summary>

每笔 1000.00 元 = 100,000 分。`int32_t` 上界 2,147,483,647 分，`2,147,483,647 / 100,000 = 21,474.83`，所以**第 21,474 笔合法、第 21,475 笔回绕**。回绕后的值 = `21,475 × 100,000 − 2³²` = `2,147,500,000 − 4,294,967,296` = **−2,147,467,296 分**（本机实测正是这个数）。注意「2,147 万笔」是把 2,147,483,647 当「笔数」读的误读——它是个**分数**，除以每笔的分值才是笔数，量级差 100 倍。

`uint32_t` 只把墙从 2147 万元挪到 4294 万元（`4,294,967,295 / 100 = 42,949,672.95` 元），仍然是 **4 千万元级的硬墙**，而且**回绕后还不显负数**——它会静默地回到 0 继续累加，比 `int32_t` 更难发现。正确做法只有一条：金额用 `int64_t`（上界 9.22×10¹⁶ 分 ≈ 9.2×10¹⁴ 元）或 `DECIMAL`，且累加器与单笔、与汇总、与 DB 列**全部同一宽度**。混宽（单笔 `int32`、汇总 `int64`）时，回绕发生在单笔那一层，汇总再宽也救不回来。
</details>

**Q2.** 下面两个判断为什么都得到和直觉相反的答案？分别写出转换后的实际比较式。

```c
if (-1 < sizeof(int))   { /* 进入这里？ */ }
int8_t m = -1; unsigned int u = 1;
if (m < u)              { /* 进入这里？ */ }
```

<details><summary>答案</summary>

两处都是 usual arithmetic conversions 的结果，转换发生在**比较之前**。

① `sizeof` 的类型是 `size_t` = `unsigned long`（LP64 下 64 位），rank 高于 `int`，命中规则 **(b)**：`int` 的 −1 被转成 `unsigned long`，位模式符号扩展后是 `0xFFFFFFFFFFFFFFFF` = 18,446,744,073,709,551,615。实际比较式是 `18446744073709551615 < 8` → **假**，不进入。实测 `-1 < sizeof(int)` 打印 0，`-1 < (int)sizeof(int)` 打印 1。

② `int8_t` 先做**整型提升**变成 `int`（因为 `int` 能装下 `int8_t` 的全部值），得到 `int` 的 −1；再与 `unsigned int` 做转换，rank 相同、一有一无符号，命中规则 **(a)**：`int` 转 `unsigned int`，`−1` 变 `0xFFFFFFFF` = 4,294,967,295。实际比较式是 `4294967295 < 1` → **假**，不进入。实测打印 0。

修法不是「加个判断」而是**让两侧同类型**：`-1 < (int)sizeof(int)`；或把有符号那侧显式转成足够宽的有符号类型 `(long long)m < (long long)u`（`LLP64` 下 `long long` 一定装得下 `unsigned int`，命中规则 (c)）。Go 里这两个都不存在——同一表达式会直接编译失败；Java 里也不存在——没有 unsigned 可混。

关键判据：**看到「无符号量」与「可能为负的有符号量」出现在同一个比较/算术表达式里，先假设结果是错的，再去查。** `-Wsign-compare` 就是为这一条存在。
</details>

**Q3.** `INT_MIN / -1` 在 C 里导致进程退出码 136，在 Go/Java 里返回 `INT_MIN` 本身。这两条路各自的「危险」在哪？给出定位该问题所需的两条命令。

<details><summary>答案</summary>

**C 这条路：危险在「不可预测」。** 标准说这是 UB，x86 的 `idiv` 在商溢出时触发 `#DE`，内核投 `SIGFPE`，进程死（退出码 136 = 128 + 8）。但既然它是 UB，编译器有权假设「不发生」，把 `x / -1` 直接优化成 `-x`——那样结果就是 `INT_MIN` 的回绕值，进程**不死**。也就是说同一个源码在不同优化等级下可能是「死」也可能是「静默错」，这是最坏的一种不确定性。危险在**无法靠测试覆盖**，只能靠 UBSan。

**Go/Java 这条路：危险在「沉默」。** 规范明确定义为回绕，`MinInt/ -1 = MinInt`、`MinInt % -1 = 0`。程序不崩、日志无异常，但算出来的是一个数学上不可能的数（本该是 `|MinInt|`，即 2⁶³）。它会在下游变成「负数除以负数得负数」这种逻辑错误，比崩溃难查一个数量级。

**两条命令：**
① `./prog; echo $?` → 得 136，且 `dmesg | tail` 里出现 `traps: prog[pid] trap divide error`；再用 `objdump -d ./prog | grep -A2 idiv` 确认故障指令（本机实测 `cltd` + `idiv %ecx`）。
② `gcc -O1 -fsanitize=undefined -o p p.c && ./p` → 直接报「runtime error: division of ... cannot be represented in type 'int'」并给出**行列号**；把 `-fsanitize-recover` 打开可一次报完所有点。

顺带一条：`% 0` 走同一条 `idiv`，也是 `SIGFPE`——所以「除数为外部输入」时必须判 `0` 与 `INT_MIN/-1` 两个条件，只判 `0` 挡不住这一个。
</details>
