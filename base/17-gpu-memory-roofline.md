## 17.1 引子：一个「每个词都对、结论全错」的问题

先把原始问题抄在这里：

> 「为什么 RTX 4090 主频 2.5 GHz、显存 24 GB，而服务器 CPU 也 2–3 GHz 却只有几百 GB 内存、几十 MB 缓存？」

这句话里的每个数字都能在规格表上查到，但它拼出来的结论是错的。四个前提逐个拆：

| # | 问题里的隐含前提 | 规格表上的事实 | 错在哪 |
| --- | --- | --- | --- |
| ① | 服务器的内存「只有几百 GB」，比显存小 | 双路服务器 24 条 DIMM 槽，单条 128 GB → **3 TB**；4090 是 24 GB | 绝对容量上 CPU 赢 100 倍。所谓「显存大」从来不指容量 |
| ② | 显存和内存是同一种东西，只是大小不同 | 4090 用 GDDR6X（384-bit 总线），H100 用 HBM3（5120-bit，3D 堆叠），服务器用 DDR5（12 通道 × 64-bit） | 介质、总线宽度、封装方式全不同，带宽差 2–7 倍 |
| ③ | 主频低 ⟹ 算得慢 | 4090 峰值 FP32 82.6 TFLOPS；64 核 × 3 GHz 的服务器 CPU 峰值 FP32 ≈ 0.38 TFLOPS（每核每周期 2 FLOP） | 差 200 倍。频率只解释其中 1 倍 |
| ④ | 显存大是「为了装更多东西」 | 7B 模型做 Adam FP32 全参训练需要 112 GB（见 §17.7），24 GB 连一份都装不下 | 显存的第一作用是**喂饱核**，不是仓库 |

四个前提一倒，真正该问的问题浮出来了，而且只有三问：

1. **为什么 GPU 的频率停在 1–2.5 GHz？**（服务器 CPU 的睿频反而能到 4 GHz 以上）
2. **为什么它要用 5120-bit 这种在 PCB 上根本走不通的总线？**
3. **给定这两个数，一段具体的代码到底卡在算力上还是带宽上？**

这三问的答案是同一条物理链，也是本篇的全部内容。先给结论，再给推导：

```
功耗 ∝ f·V²，而提频必须同时提压，于是提频的单价 ∝ f³
        ↓ 所以「再快 1 GHz」是最贵的一条路
散热有硬上限（风冷单 socket ≈ 250 W，整机架 ≈ 10 kW）
        ↓ 所以功率预算固定时，唯一可扩展的方向是「加核，不加频」
于是 GPU = 10⁴ 个慢核 + 一片极宽的显存
        ↓ 核越多，每个 FLOP 能分到的字节越少
于是「算得快」的真相是「等得少」：靠上万条并行指令把延迟藏起来
        ↓ 藏不住的那部分，就是 roofline 上的带宽墙
```

## 17.2 功耗与频率：为什么「再超 1 GHz」是所有方案里最贵的

### 一个算式，四个量

CMOS 电路的动态功耗只有一条公式：

```
P_dyn = α · C · V² · f
```

| 量 | 含义 | 量级（GPU/CPU） | 怎么反推 |
| --- | --- | --- | --- |
| `α` | 活动因子：每个周期真正翻转的电容占比 | 0.1–0.3 | 由电路结构与负载估计，不单独可测 |
| `C` | 被翻转的等效电容（全芯片求和） | 见下 | `αC = P / (V²f)` |
| `V` | 核心供电电压 | 0.7–1.3 V | 由工艺节点与目标频率共同决定 |
| `f` | 时钟频率 | 1–5 GHz | 由关键路径延迟决定 |

用两个真实机器的 TDP 反推 `αC`（量级结论，假设 V 与 f 取标称值）：

```
H100 SXM：700 W ≈ αC × (1.0 V)² × 1.8 GHz  →  αC ≈ 389 nF
服务器 CPU：250 W ≈ αC × (1.2 V)² × 3.5 GHz →  αC ≈ 50 nF
```

`αC` 差 7.8 倍，对应的是 die 面积与晶体管数的差距。这个反推的价值不在精度，而在于让你知道**公式里没有自由变量**：想让 `f` 涨，只有两条路——要么降 `C`（换工艺，几年一代），要么涨 `V`（立刻见效，但代价是平方）。

### 关键：`f` 和 `V` 不是两个独立旋钮

门延迟近似正比于 `CV/(V - V_th)`。想让关键路径再短一点、时钟再快一点，**必须把 V 抬上去**，否则晶体管根本来不及翻转。工程上的经验关系是 `V ∝ f^0.5` 到 `f^1`，取保守的线性近似 `V ∝ f`，就得到那个著名的结论：

```
若只提压 10%、频率不变：P ∝ 1.1² = 1.21      →  +21%
若提频 10%、必须同步提压 10%：P ∝ 1.1³ = 1.331 →  +33%
```

> 市面上流传的「提频 10% 功耗涨 21%」，算的是 `1.1²`——那只算上了电压项，默认频率没动，自相矛盾。真正提频时两项一起涨，是 `1.1³ ≈ +33%`。两个数都记住，估算时才不会差一倍。

把幅度拉大，墙就更清楚。一个核从 `2.5 GHz @ 0.85 V` 超到 `5.0 GHz @ 1.30 V`：

```
P 比值 = (1.30 / 0.85)² × (5.0 / 2.5)
       = 2.34 × 2
       = 4.68 倍
```

**同样一个核，频率翻倍，功耗涨 4.7 倍。** 这就是为什么 CPU 的单核睿频在 4–5 GHz 附近就上不去了：再往上，每 100 MHz 都要用整机的散热余量去换。

### 散热：一条谁也不能商量的上限

| 散热形态 | 能持续带走的热 | 对应什么 |
| --- | --- | --- |
| 被动/薄型笔记本 | 15–45 W | 低压 U 系列，基频 1.0–1.8 GHz |
| 桌面塔式风冷 | ≈ 250 W（单 socket） | 桌面 CPU 的持续功耗墙 |
| 1U/2U 机架风冷 | ≈ 10 kW / 机架 | 8 卡服务器：8 × 700 W + 2 × 350 W CPU + 风扇/电源 ≈ 7 kW |
| 液冷机架 | 30–100 kW / 机架 | H100/B200 集群的默认形态 |

H100 SXM 单卡 TDP 700 W，B200 到 1000–1200 W 量级。**这不是厂商不想做快，是 700 W 已经需要把整机架改成液冷。** 在这条约束下比较三种提速手段：

| 手段 | 功耗代价 | 性能代价 | 可扩展性 |
| --- | --- | --- | --- |
| 提频（`f ↑`） | ∝ `f³`，翻倍即 4.7× | 无 | 最差，撞散热墙 |
| 提 IPC（微架构） | 同频下面积/功耗小幅上升 | 每代 +10–20%，需要重做前端 | 慢，几年一代 |
| 堆核（`N ↑`） | ∝ `N`（线性），且可降压降频换平方收益 | 需要并行度，串行段不变 | **最好，唯一可扩展** |

最后一行是关键：**堆核是线性付费，提频是三次方付费。** 同样的功率预算，堆 2 倍核只花 2 倍电，而提 2 倍频要花 4.7 倍电。所以任何一台追求峰值吞吐的机器，最后都会走到「低频 × 海量核」这条路上——GPU 只是把这条路走到了极致。

顺带解释一个常见困惑：为什么 GPU 反而能效更高？用 TDP 除以峰值算「每 FLOP 花多少焦耳」（量级结论，峰值未打折）：

| 机器 | 峰值 | TDP | 每 FLOP 能耗 |
| --- | --- | --- | --- |
| 64 核 CPU（FP32 向量） | 0.38 TFLOPS | 250 W | **651 pJ** |
| RTX 4090（FP32） | 82.6 TFLOPS | 450 W | 5.4 pJ |
| A100（FP32） | 19.5 TFLOPS | 400 W | 20.5 pJ |
| A100（FP16 张量核） | 312 TFLOPS | 400 W | 1.3 pJ |
| H100（FP16 张量核） | 989 TFLOPS | 700 W | **0.71 pJ** |

从 CPU 到 H100 张量核，单 FLOP 能耗差 **900 倍**。这不是「GPU 更省电」，是「GPU 把每个 FLOP 摊到了上万个核和更窄的位上」——同样一度电，买到的并行乘加多三个数量级。

## 17.3 为什么 GPU 可以低频：吞吐 = 核数 × 频率，延迟不能

### 把吞吐拆成两个乘数

一个芯片的峰值吞吐近似是：

```
峰值 FLOP/s = SM 数 × 每 SM 的 FP32 通道数 × 2（FMA 算两次运算）× 频率
```

代入三台机器（厂商规格）：

| 机器 | SM/核数 | 每 SM 通道 | 频率 | 算式 | 峰值 FP32 |
| --- | --- | --- | --- | --- | --- |
| A100 80GB | 108 SM | 64 | 1.41 GHz | 108×64×2×1.41e9 | 19.5 TFLOPS |
| H100 SXM | 132 SM | 128 | 1.98 GHz | 132×128×2×1.98e9 | 66.9 TFLOPS |
| RTX 4090 | 128 SM | 128 | 2.52 GHz | 128×128×2×2.52e9 | 82.6 TFLOPS |
| 服务器 CPU | 64 核 | 8（AVX2 双发射） | 3.0 GHz | 64×16×2×3.0e9 | 6.1 TFLOPS |

看清这张表只需要一句话：**频率那一列全都落在 1.4–3.0 GHz 的同一个窄带里，差的是前面两个乘数。** GPU 用 128 个通道/SM 换掉了 CPU 的 8 个通道/核，再用 132 个 SM 换掉了 64 个核——乘出来是 11 倍，而不是靠频率。

### 为什么 CPU 不能靠堆核解决单线程延迟

因为延迟和吞吐是两个方向。一段程序的耗时可以写成：

```
T(N) = T_串行 + T_并行 / N
加速比 S(N) = 1 / ((1 - p) + p / N)     ← Amdahl
```

`p` 是可并行比例。这张表说明为什么「堆核」在 CPU 侧会撞墙（`N` 取 64）：

| 串行段 `1-p` | N=8 | N=64 | N=1024 | 上限 |
| --- | --- | --- | --- | --- |
| 50% | 1.78× | 1.97× | 1.998× | 2× |
| 10% | 4.7× | 8.8× | 9.9× | 10× |
| 5% | 6.0× | 14.5× | 19.3× | 20× |
| 1% | 7.5× | 39.0× | 91.2× | 100× |

一个事务型服务里，`1-p = 5%` 是极常见的（一次加锁、一次写日志、一次跨核传指针）。这时堆到 64 核只有 14.5 倍，堆到 1024 核也只有 20 倍——**多出来的 960 个核全在等那 5%**。CPU 卖的是「一条线程在 3 GHz 上尽快走完串行段」，所以它必须提频、必须做深乱序窗口、必须堆大缓存；这些全是为了缩短 `T_串行`。

GPU 反过来：它根本不承诺单线程快，它承诺「给我一万份互相独立的数据，我用一万条通道同时算」。于是串行段的绝对值可以很丑（一个线程比 CPU 慢 5–10 倍），但 `T_并行 / N` 被压到极小。

### 「算得快」的真相是「等得少」

GPU 的一个 SM 里有 4 个 warp scheduler，每个周期从几十个常驻 warp 里挑一个「操作数已就绪」的发出去。DRAM 延迟是 400–600 个周期，而一颗 A100 的 SM 可以同时挂 64 个 warp、每个 warp 32 条通道：

```
一次 DRAM 访问的等待 ≈ 500 cycle
一个 SM 可并行的 warp 数 = 64
→ 有效可隐藏的等待 ≈ 64 个独立访存同时在飞
```

所以 GPU 的主频低不是缺陷，是**它把「等待」摊给了并行度**。这也是为什么 GPU 上「增加占用率（occupancy）」几乎总是第一优化手段：占用率不够，延迟没东西可藏，慢核就会真的慢下去。

> 这就是本篇标题里那句话的物理含义：**它算得快，常常是因为它等得少。** 单看一条指令的延迟，GPU 比 CPU 差一个数量级；看单位时间完成的乘加数，它赢一个数量级。中间那 100 倍，全在「同时有多少条指令在飞」上。

## 17.4 显存为什么「大」：HBM 是 3D 堆叠 + 超宽总线

### 先把带宽算出来：一条公式打通所有机器

```
带宽 = 位宽(bit) × 每 pin 数据率(Gbps) ÷ 8
```

如果规格给的是时钟而不是 DDR 数据率，则数据率 = 时钟 × 2。把四台机器代进去，误差都在 1% 以内（厂商规格）：

| 机器 | 介质 | 位宽 | 时钟 / 数据率 | 算式 | 标称带宽 |
| --- | --- | --- | --- | --- | --- |
| RTX 4090 | GDDR6X | 384 bit | 21 Gbps/pin（PAM4） | 384×21÷8 | 1008 GB/s |
| A100 40GB | HBM2e | 5120 bit | 1.20 GHz ×2 | 5120×1.2e9×2÷8 | 1.54 TB/s |
| H100 SXM | HBM3 | 5120 bit | 2.60 GHz ×2 | 5120×2.6e9×2÷8 | 3.33 TB/s |
| H200 | HBM3e | 6144 bit | 3.13 GHz ×2 | 6144×3.13e9×2÷8 | 4.80 TB/s |
| 服务器 CPU | DDR5-4800 | 768 bit（12 通道） | 2.40 GHz ×2 | 768×2.4e9×2÷8 | 461 GB/s |

注意两件事：

**第一，位宽差 6.7 倍，数据率只差 2 倍，带宽就差 13 倍。** 从 DDR5 的 768 bit 到 HBM3 的 5120 bit，靠的不是「频率更高」，而是「线更多」——而线多到 5120 根时，PCB 已经布不下了。

**第二，5120 bit 只能走硅中介层。** 一根 PCB 走线要穿过封装、过孔、连接器，5000 多根并行走线在几厘米尺度上无法保证时序对齐（skew）和信号完整性，功耗也会被 I/O 吃掉。HBM 的解法是把 DRAM die 一层层叠起来（8–12 层），用硅通孔（TSV）垂直打通，再把整摞放在 GPU die 旁边的硅中介层（interposer）上——**距离从厘米降到毫米，宽度才能从 64 bit 涨到 1024 bit/摞**：

```
        ┌──────────────── 硅中介层 (interposer) ────────────────┐
        │                                                      │
        │   ┌──────────┐   ┌────┐ ┌────┐ ┌────┐ ┌────┐ ┌────┐ │
        │   │  GPU die │   │HBM │ │HBM │ │HBM │ │HBM │ │HBM │ │
        │   │ 132 SM   │   │ 0  │ │ 1  │ │ 2  │ │ 3  │ │ 4  │ │
        │   │          │◄─►│1024│ │1024│ │1024│ │1024│ │1024│ │ ← bit/摞
        │   └──────────┘   │bit │ │bit │ │bit │ │bit │ │bit │ │
        │                  └────┘ └────┘ └────┘ └────┘ └────┘ │
        │                  每摞 8–12 层 DRAM die 垂直堆叠        │
        └──────────────────────────────────────────────────────┘
        总位宽 = 5 × 1024 = 5120 bit；容量 = 5 × 16 GB = 80 GB
```

**容量就是这么来的：一摞 HBM 的高度决定容量，摞数决定位宽。** H100 的 80 GB = 5 摞 × 16 GB；位宽 5120 bit = 5 摞 × 1024 bit。想加容量就加层数（HBM3 12-Hi 单摞 24 GB），想加带宽就加摞数（H200 加到 6 摞 → 6144 bit）。两者共用同一个物理动作，所以「显存大」和「带宽高」在 HBM 上是同一件事的两面。

### 「显存大」的真正含义：每个字节配的搬运能力

把每台机器的带宽除以容量，得到一个很少有人看的数：

| 机器 | 带宽 | 容量 | 每 GB 容量配到的带宽 |
| --- | --- | --- | --- |
| RTX 4090 | 1008 GB/s | 24 GB | **42 GB/s per GB** |
| H100 | 3.33 TB/s | 80 GB | 42 GB/s per GB |
| 服务器（768 GB DDR5） | 461 GB/s | 768 GB | **0.6 GB/s per GB** |

GPU 每装 1 GB 数据，配的搬运能力是服务器的 **70 倍**。这才是「显存大」的真相：**不是仓库大，是传送带宽得离谱。** 因为核太多，每个核分到的字节太少，所以必须用最贵的封装去换位宽。

### 每 FLOP 能分到多少字节

把带宽除以峰值算力：

| 机器 | 峰值 | 带宽 | 每 FLOP 可用字节 | 每字节可做 FLOP |
| --- | --- | --- | --- | --- |
| 64 核 CPU（FP32） | 0.38 TFLOPS | 461 GB/s | **1.2 B** | 0.83 |
| H100（FP32 向量） | 66.9 TFLOPS | 3.33 TB/s | **0.05 B** | 50 |
| H100（FP16 张量核） | 989 TFLOPS | 3.33 TB/s | 0.0034 B | 295 |

CPU 每做一次浮点运算，可以从内存拿到 1.2 个字节；H100 做一次 FP32 只能拿到 0.05 个字节。**所以 GPU 天生就是「算力过剩、数据饥渴」的机器**——它必须让数据在片上反复复用（寄存器、共享内存、分块），否则再宽的 HBM 也喂不饱。这一条直接推出 ◆20 的全部优化阶梯：分块、复用、提高 arithmetic intensity，全是在补这 0.05 B 的缺口。

## 17.5 roofline：两条天花板，一个拐点

### 模型

把上面两张表合成一张图。横轴是**算术强度**（arithmetic intensity，AI，单位 FLOP/Byte），纵轴是实际性能（FLOP/s）：

```
 性能
  ▲
  │            ┌──────────────────────  算力天花板：π（峰值 FLOP/s）
  │           ╱
  │          ╱   ← 这一段斜率为 β（带宽），性能 = AI × β
  │         ╱
  │        ╱
  │       ╱
  │      ╱
  └─────┴──────────────► 算术强度 AI (FLOP/Byte)
       拐点 I* = π / β
```

一条公式：

```
可达性能 P(AI) = min( π , β · AI )
拐点（ridge point） I* = π / β
```

- `AI < I*`：**带宽瓶颈**。性能 = `β · AI`，斜率就是带宽。加算力没用，加带宽才有用。
- `AI > I*`：**算力瓶颈**。性能 = `π`，AI 再高也上不去。加带宽没用。

### 算例：A100 40GB

```
π = 19.5 TFLOPS（FP32 向量）
β = 1.55 TB/s
I* = 19.5e12 / 1.55e12 = 12.6 FLOP/Byte
```

也就是说：**A100 上任何一段 FP32 代码，只要每搬 1 字节做不到 12.6 次浮点运算，它就跑不满算力。** 换个精度，拐点会剧烈移动：

| 机器 / 精度 | π | β | 拐点 I* | 含义 |
| --- | --- | --- | --- | --- |
| 64 核 CPU（FP32） | 0.38 TFLOPS | 461 GB/s | **0.83** | 几乎一切代码都是算力瓶颈 |
| A100（FP32） | 19.5 TFLOPS | 1.55 TB/s | **12.6** | 多数逐元素算子卡带宽 |
| A100（FP16 张量核） | 312 TFLOPS | 1.55 TB/s | **201** | 连 GEMM 都可能卡带宽 |
| A100（INT8 张量核） | 624 TOPS | 1.55 TB/s | **403** | 只有大矩阵才喂得饱 |
| H100（FP32） | 66.9 TFLOPS | 3.35 TB/s | 20.0 | 比 A100 更「渴」 |
| H100（FP16 张量核） | 989 TFLOPS | 3.35 TB/s | 295 | — |
| RTX 4090（FP32） | 82.6 TFLOPS | 1.008 TB/s | 82 | 消费卡的带宽配比更差 |

这张表最反直觉的一行是最后：**4090 的 FP32 拐点比 A100 还高**（82 vs 12.6）。因为它把 82.6 TFLOPS 挂在一条只有 1 TB/s 的 GDDR6X 上，算力/带宽比是 82，而 A100 是 12.6。所以消费卡跑大模型时更容易掉进带宽坑，这也是「4090 推理单条吞吐高、batch 一大就顶住」的原因之一。

### 用 GEMM 验证：矩阵多大才算「够稠」

方阵 `n×n` 的矩阵乘，FP32 下的算术强度可以直接推：

```
FLOP = 2n³
Byte = 4 × (n² + n² + n²) = 12n²
AI   = 2n³ / 12n² = n / 6
```

| n | 32 | 64 | 76 | 128 | 256 | 1024 | 4096 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| AI（FLOP/B） | 5.3 | 10.7 | 12.7 | 21.3 | 42.7 | 171 | 683 |
| A100 FP32 上看谁 | 带宽 | 带宽 | **拐点** | 算力 | 算力 | 算力 | 算力 |

**A100 上 FP32 方阵 GEMM 的分水岭是 `n ≈ 76`。** 小于 76 的矩阵乘，无论你把 kernel 写得多好，都卡在带宽上；大于 128 之后才逐步吃到算力。这个数字解释了两件事：小 batch 的推理为什么慢（AI 太低），以及 GEMM 优化的第一步为什么永远是分块（把 AI 从 `n/6` 抬到能超过拐点的高度）。

把这段算成代码（20 行，可直接改参数）：

```python
def ridge(peak_tflops, bw_tbs):
    return peak_tflops / bw_tbs          # FLOP/Byte

def attainable(peak, bw, ai):
    return min(peak, bw * ai)            # FLOP/s（单位统一为 TFLOPS / TB/s）

machines = {
    "A100-fp32": (19.5, 1.55),
    "A100-fp16t": (312.0, 1.55),
    "H100-fp32": (66.9, 3.35),
    "4090-fp32": (82.6, 1.008),
}
for name, (peak, bw) in machines.items():
    i = ridge(peak, bw)
    print(f"{name:11s} 拐点 {i:6.1f} FLOP/B  |  n=128 方阵 AI=21.3 -> {attainable(peak,bw,21.3):6.1f} TFLOPS")
```

```
A100-fp32   拐点   12.6 FLOP/B  |  n=128 方阵 AI=21.3 ->   19.5 TFLOPS
A100-fp16t  拐点  201.3 FLOP/B  |  n=128 方阵 AI=21.3 ->   33.0 TFLOPS
H100-fp32   拐点   20.0 FLOP/B  |  n=128 方阵 AI=21.3 ->   66.9 TFLOPS
4090-fp32   拐点   81.9 FLOP/B  |  n=128 方阵 AI=21.3 ->   21.5 TFLOPS
```

第二行最值得盯：**A100 的 FP16 张量核有 312 TFLOPS，但一个 128×128 的方阵只能跑出 33 TFLOPS——只用到 10.6%。** 这不是 kernel 写得差，是 roofline 说它最多就只能到这个数。想吃到那 279 TFLOPS，要么把矩阵放大（AI 上去），要么把数据在片上复用（把有效 AI 抬上去）。

## 17.6 浮点位宽与吞吐：16× 是从哪来的

### 一张表看清七种格式

| 格式 | 总位 | 指数位 | 尾数位 | 最大可表示 | 最小正规数 | 十进制有效位 | A100 吞吐 | 相对 FP32 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| FP64 | 64 | 11 | 52 | 1.8×10³⁰⁸ | 2.2×10⁻³⁰⁸ | 15–17 | 9.7 TFLOPS | 0.5× |
| FP32 | 32 | 8 | 23 | 3.4×10³⁸ | 1.2×10⁻³⁸ | 7.2 | 19.5 TFLOPS | 1× |
| TF32 | 19（存 32） | 8 | 10 | 3.4×10³⁸ | 1.2×10⁻³⁸ | 3.3 | 156 TFLOPS | 8× |
| FP16 | 16 | 5 | 10 | 65,504 | 6.1×10⁻⁵ | 3.3 | 312 TFLOPS | 16× |
| BF16 | 16 | 8 | 7 | 3.4×10³⁸ | 1.2×10⁻³⁸ | 2.4 | 312 TFLOPS | 16× |
| FP8 (E4M3) | 8 | 4 | 3 | 448 | 1.6×10⁻² | 1.2 | H100: 1979 TFLOPS | — |
| INT8 | 8 | — | 7（补码） | 127 | — | 2.4 | 624 TOPS | 32× |

三列值得单独读：

**① 指数位决定「范围」，尾数位决定「精度」，两者抢同一批 bit。** FP16 有 10 位尾数（精度 3.3 位十进制，够用），但只有 5 位指数，范围被压到 `±65504`——这正是 LLM 训练里 `inf` 与 `nan` 的主要来源。BF16 反过来：8 位指数（范围和 FP32 一模一样），只剩 7 位尾数（精度 2.4 位十进制）。

**② 为什么 LLM 爱 BF16：范围比精度重要。** 训练时梯度、激活、loss 会跨很多个数量级，一次 `exp` 或一次累加就能把值推出 `65504`。FP16 的补救办法是 loss scaling（把 loss 乘一个常数把梯度抬进可表示区间，反传前再除回来），这是一整套额外的工程复杂度。BF16 直接把指数位借够，范围与 FP32 相同，代价只是尾数少 3 位——而随机梯度的噪声本来就比这 3 位大，所以「精度掉一点」在统计上几乎看不见。这就是「用范围换精度」在深度学习里成立的唯一理由。

**③ TF32 是「FP32 的存储、FP16 的乘法器」。** 它把 FP32 的 23 位尾数截到 10 位，指数仍是 8 位，累加仍在 FP32 里做。所以 `torch.backends.cuda.matmul.allow_tf32 = True` 通常只需要一行、几乎不掉点，而吞吐能到 FP32 的 8 倍。

### 16× 的分解

`312 / 19.5 = 16`。这个 16 倍不是「精度低就自动快」，它由两个独立的机制相乘：

| 机制 | 贡献（量级） | 原理 |
| --- | --- | --- |
| 更低精度 + 打包运算 | 2–4× | 同样一条 32-bit 数据通路可以塞两个 16-bit 数，乘法器面积 ∝ 位宽²，16 位乘法器约 1/4 面积 |
| 张量核（Tensor Core） | 4–8× | 把 `4×4×4`（或更大）的乘累加阵列做成一条指令，操作数从寄存器复用，不再每步取指/译码 |

两者相乘到 16×。**关键结论不是这个倍数，而是「吞吐倍率是厂商按精度分档给的」**——同一块硅，跑 FP32 是 19.5，跑 FP16 张量是 312。所以 roofline 的 `π` 不是一个常数，它是一个随精度变化的族。选精度就是选 `π`，也就选了拐点 `I* = π/β` 往右移多少。

> 代价也要说清：位宽每砍一半，拐点就往右翻一倍。FP16 张量核的拐点是 201 FLOP/B，是 FP32 的 16 倍——**你换来了 16 倍算力，也换来了 16 倍「喂不饱」的风险**。低精度的收益从来不是免费的，它是把瓶颈从算力搬到了带宽。

## 17.7 显存带宽 vs 容量 vs 延迟：三件事，别混

| 维度 | 物理含义 | 典型量级 | 什么时候它是瓶颈 | 怎么加 |
| --- | --- | --- | --- | --- |
| **延迟** | 一次访存的往返时间 | 片上 1–30 ns，DRAM 80–500 ns | 依赖链、小 batch、pointer chasing | 提高并行度/占用率，预取 |
| **带宽** | 单位时间能搬多少字节 | 服务器 0.46 TB/s，H100 3.35 TB/s | AI 低于拐点、decode、逐元素算子 | 更宽的总线、更高的数据率 |
| **容量** | 同时能装多少字节 | 24 GB – 141 GB | 权重 + 激活 + KV cache 装不下 | 更多摞、更低位宽、分片 |

三者的关系不是「越大越好」，而是**互相换算**：容量不够时，你要么降精度（FP16→INT8，容量减半）、要么分片到多卡（吃 PCIe/NVLink 带宽）、要么把 KV 换出去（吃主机内存带宽，延迟涨一个数量级）。**每一次「省容量」的操作，最后都变成一次「花带宽」或「花延迟」。**

### KV cache：一个把三者同时踩满的例子

以 7B 模型为例（32 层、hidden 4096、BF16 存储），每 token 的 KV cache：

```
每 token 字节 = 2（K 和 V）× 层数 × hidden × 2 B
             = 2 × 32 × 4096 × 2
             = 524,288 B
             = 512 KiB / token
```

| 并发 × 上下文 | KV 占用 | 80 GB 卡上还剩多少给权重（权重 14 GB） |
| --- | --- | --- |
| 8 × 2048 token | 8 GiB | 58 GiB |
| 32 × 2048 token | 32 GiB | 34 GiB |
| 32 × 8192 token | 128 GiB | **装不下，必须分片或换出** |

再看 decode 阶段的算术强度。每生成 1 个 token，要读一遍全部权重（7e9 × 2 B = 14 GB），做 2 × 7e9 = 1.4e10 FLOP：

```
AI = 1.4e10 FLOP / 1.4e10 B = 1 FLOP/Byte
```

**1 FLOP/Byte，而 A100 FP16 张量核的拐点是 201。** 差 200 倍——decode 是纯粹的带宽瓶颈，算力利用率的理论上限就是 `1/201 = 0.5%`。这也直接给出单卡 decode 的 token/s 上限：

```
A100：1.55 TB/s ÷ 14 GB = 111 token/s
H100：3.35 TB/s ÷ 14 GB = 239 token/s
4090：1.008 TB/s ÷ 14 GB = 72 token/s（24 GB 刚好装下 14 GB 权重）
```

### 为什么 batch 能提高吞吐：把 AI 乘上去

batch = B 时，权重仍然只读一遍，但一次算出 B 个 token：

```
AI ≈ 2 × 7e9 × B / 14e9 = B FLOP/Byte
```

- `B = 1` → AI = 1，带宽瓶颈，吞吐 111 token/s，单 token 要 9 ms。
- `B = 32` → AI = 32，仍是带宽瓶颈（32 < 201），但**同样的 9 ms 出 32 个 token**，吞吐 3555 token/s，32 倍。
- `B ≈ 200` → AI ≈ 200，撞上算力线；再大的 batch 只会让每步变慢，不再提升吞吐。

这就是「batch 调大能提吞吐」的完整物理原因：**它不是让计算变快，是让同一批权重被更多 token 摊薄。** 而它失效的地方也在这里：一旦 AI 越过拐点，或者 KV cache 把显存占满导致抢占，吞吐就会掉头向下（抢占与重算的账见 [comp/49](../comp/49-inference-engine-vllm.md) §49.3–49.6，本篇不重复）。

顺带把「为什么 prefill 快、decode 慢」也解释了：prefill 一次处理几千个 token，AI 高、算力瓶颈；decode 一次一个 token，AI = 1、带宽瓶颈。同一张卡，两个阶段的瓶颈完全不同——这是推理引擎要做 continuous batching 的根本原因。

## 17.8 实测/估算：本机没有 GPU，只有方法和一台 CPU

**必须先说清楚：本机是 2 vCPU 的 KVM 虚拟机（`lscpu` 显示 AMD EPYC 7K62 的两个核、32 MiB L3、1 GiB 内存），没有 NVIDIA 设备，`nvidia-smi` 不存在。** 所以下面所有 GPU 数字都是**厂商规格/量级**，标了假设；能跑的是最后那个 CPU 对照实验。

### 在自己卡上测 roofline 的方法

思路：造一批**算术强度可控**的 kernel，测每个 kernel 的实际 FLOPS，画在横轴为 AI 的图上，看它贴着哪条线。

```python
import torch, time
dev = "cuda"
def bench(fn, iters=50):
    for _ in range(5): fn()                    # 预热
    torch.cuda.synchronize(); t0 = time.time()
    for _ in range(iters): fn()
    torch.cuda.synchronize()
    return iters / (time.time() - t0)

# 低 AI：逐元素乘加（每元素读 8B 写 4B，做 2 FLOP -> AI ≈ 0.17）
x = torch.randn(1 << 24, device=dev); y = torch.randn_like(x)
t = bench(lambda: torch.addcmul(y, x, x, value=1.0))
print("elementwise", (1 << 24) * 2 / t / 1e12, "TFLOPS")

# 高 AI：方阵 GEMM，AI = n/6，n 从 64 扫到 8192
for n in (64, 256, 1024, 4096, 8192):
    a = torch.randn(n, n, device=dev); b = torch.randn(n, n, device=dev)
    t = bench(lambda: a @ b, iters=20)
    print(f"n={n:5d} AI={n/6:7.1f} {2*n**3/t/1e12:8.2f} TFLOPS")
```

两条注意：`torch.backends.cuda.matmul.allow_tf32` 决定 `π` 取 19.5 还是 156；`n=64` 那一行会被 kernel launch 开销污染（一次 launch 约 3–10 μs，而 64³ 的计算只有 0.5 μs 量级），所以拐点要从中等 n 读。

再用 `ncu` 直接读两条天花板的利用率，比画图更快：

```bash
# 看一个 kernel 到底卡在哪条线上：两个百分比，谁接近 100% 谁是瓶颈
ncu --metrics \
  sm__throughput.avg.pct_of_peak_sustained_elapsed,\
  dram__throughput.avg.pct_of_peak_sustained_elapsed,\
  l1tex__throughput.avg.pct_of_peak_sustained_elapsed \
  python gemm.py
```

- `dram__throughput` 接近 100%、`sm__throughput` 只有 20–40% → 带宽瓶颈，去提 AI（分块、融合、加 batch）。
- 反过来 → 算力瓶颈，去换精度（FP32→TF32→BF16）或换更快的指令。
- 两个都低 → **延迟瓶颈**：占用率不够，或者依赖链太长。

### 本机 CPU 对照：同一台机器上的两条线

用同一台机器测两个数：`memcpy` 的字节吞吐，和 FMA 的浮点吞吐。

```c
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <time.h>
static double now(void){struct timespec t;clock_gettime(CLOCK_MONOTONIC,&t);return t.tv_sec+1e-9*t.tv_nsec;}
int main(void){
    size_t N = 32u<<20;                      /* 32 MiB，大于本机 L3 的一半 */
    char *a = malloc(N), *b = malloc(N);
    memset(a,1,N); memset(b,2,N);
    double t0 = now();
    for (int i=0;i<40;i++){ memcpy(b,a,N); __asm__ volatile(""::"r"(b):"memory"); }
    double dt = now()-t0;
    printf("[memcpy] 32 MiB x40 = %.3f s -> 读+写 %.2f GB/s\n", dt, 2.0*N*40/dt/1e9);

    double acc[8]; for(int j=0;j<8;j++) acc[j]=1.0+j*1e-3;
    long it = 100000000; t0 = now();
    for (long i=0;i<it;i++)
        #pragma GCC ivdep
        for (int j=0;j<8;j++) acc[j] = acc[j]*1.0000001 + 1e-9;
    dt = now()-t0;
    printf("[FMA] 8 条独立链 x1e8 = %.3f s -> %.2f GFLOP/s\n", dt, it*8*2/dt/1e9);
    return 0;
}
```

`gcc -O3 -march=native` 的真实输出（本机）：

```
[memcpy] 32 MiB x40 = 0.100 s -> 读+写 26.74 GB/s
[FMA] 8 条独立链 x1e8 = 0.160 s -> 10.00 GFLOP/s
```

于是这台机器的拐点：

```
I* = 10.0 GFLOP/s ÷ 26.74 GB/s = 0.37 FLOP/Byte
```

作为对照，A100 的 FP32 拐点是 12.6——**差 34 倍**。含义很直接：在这台 CPU 上，几乎任何代码（哪怕 `n=8` 的小矩阵乘，AI ≈ 1.3）都是**算力瓶颈**；同一段代码搬到 A100 上，`n=8` 的 AI 只有 1.3，远低于 12.6，立刻变成**带宽瓶颈**。这就是「移植到 GPU 有时快 100 倍、有时只快 3 倍」的定量解释：**你换的不只是执行单元，还换了瓶颈的位置。**

再补一个延迟的实测（同一台机器，随机指针追逐）：1 MiB 工作集（落在 L2）11.9 ns/次，8 MiB（落 L3）27.7 ns/次，64 MiB（落 DRAM）115.8 ns/次，256 MiB 167.4 ns/次。**同一台机器上，延迟差了 14 倍，带宽却没有变**——这是 §17.7 那张「三者不是一回事」的表最直白的证据。

> 这些绝对数字只对本机（2 vCPU 的 VM）成立，别拿去做承诺值。你在裸金属上跑，FMA 通常会高 2–10 倍（AVX2/AVX-512 全宽），但拐点仍落在 1–5 FLOP/B 这个区间，比 A100 低一个数量级——**结论不变，数字会变。**

## 17.9 三列账：GPU 这条路承诺了什么、收了多少、从哪开始崩

| # | 承诺 | 代价 | 崩点 |
| --- | --- | --- | --- |
| ① | **高吞吐**：把 10³–10⁴ 条独立数据压进同一条指令流，峰值比 CPU 高 1–2 个数量级 | 控制逻辑被砍到极限：没有深乱序、没有大 cache、分支发散就串行化；必须凑够并行度 | 数据不独立（分支密集、指针追逐、图遍历）→ 占用率上不去，慢核真的慢 |
| ② | **高带宽**：5120–6144 bit 的 HBM，3–5 TB/s，靠 3D 堆叠和硅中介层实现 | 封装成本高、容量受限于摞数、必须和 GPU 焊死在同一块板（不可插拔、不可扩容） | 容量不够时只能降精度或分片，每次分片都吃互联带宽，延迟涨一个数量级 |
| ③ | **低精度高吞吐**：同样硅面积换 8–32 倍 FLOP | 动态范围与精度按位宽指数级缩水：FP16 上限 65504、FP8 只有 448 | 梯度溢出成 `inf`/`nan`（FP16）、量化掉点（INT8/FP8）、需要 loss scaling 或校准集 |
| ④ | **roofline 可预测**：给 `π` 和 `β` 就能算出上限，优化有方向 | 只对「规则、稠密、可复用」的负载成立；稀疏、动态形状、控制流都不在模型里 | 真实 kernel 只能到峰值的 30–60%（MFU），roofline 给的是上限，不是承诺 |
| ⑤ | **低频也够快**：靠并行度隐藏 400–600 cycle 的访存延迟 | 隐藏的前提是「有足够多独立的活在飞」；占用率一掉，延迟立刻现形 | 小 batch、短序列、单请求低延迟场景：延迟藏不住，GPU 反而不如 CPU |

一句话收束：**GPU 买到的是「单位时间做多少个乘加」，付出的是「每个乘加能拿到的字节、精度和灵活性」。** 三样代价里任何一样被踩穿，roofline 就会从算力线掉到带宽线，或者干脆掉到延迟线。

## 17.10 踩坑清单：现象 → 根因 → 怎么定位 → 怎么修

| 现象 | 根因（指回本篇） | 定位 | 怎么修 | 怎么防 |
| --- | --- | --- | --- | --- |
| 显存 OOM，但 GPU 利用率只有 15% | 容量与算力无关：权重 + KV 占满，计算单元在等数据（§17.4、§17.7） | `nvidia-smi` 看显存；`ncu` 看 `dram__throughput` | 降精度（BF16→INT8）、减 `max_num_seqs`、开 KV 分页/换出 | 上线前按 `2×L×H×2B×并发×上下文` 算一遍容量表 |
| batch 调大反而变慢 | 要么 AI 越过拐点进入算力瓶颈，要么 KV 爆了触发抢占/重算（§17.7） | 扫 batch ∈ {1,2,4,…,256}，画吞吐-延迟曲线找拐点 | 取拐点前 70% 的 batch；把 `max_model_len` 与并发一起算 | 容量与吞吐分开做压测，不用「并发数」当唯一旋钮 |
| FP16 训练突然 `inf` / `nan` | FP16 上限只有 65504，梯度/激活越界（§17.6 ①） | 在 loss 与每层输出上打 `max()`，看谁先到 6e4 | 用 BF16（同范围换精度），或加 loss scaling + 溢出跳过 | 训练脚本默认 BF16；用 FP16 必须配 dynamic loss scale |
| 把 TFLOPS 当端到端性能 | TFLOPS 是 `π`，实际性能是 `min(π, β·AI)`（§17.5） | 算这段代码的 AI，和拐点比 | 提 AI（分块/融合/加 batch），或换精度抬高 `π` | 容量规划一律用「实测 MFU × 峰值」，不用峰值 |
| 小矩阵/小 batch 上 GPU 比 CPU 还慢 | AI 低于拐点 + kernel launch 开销（§17.5、§17.8） | 对比 `n=32/64` 的实测 FLOPS 与 CPU | 合并 kernel、加大 batch、把数据留在片上 | 小于拐点的负载先在 CPU 上算一遍基线 |
| 多卡扩展不到线性 | 卡间互联带宽远低于 HBM（PCIe 64 GB/s 级 vs HBM 3.35 TB/s） | `nvidia-smi topo -m` 看是否走 NVLink；`ncu` 看跨卡流量 | 用张量并行只在 NVLink 域内；跨机用流水线并行 | 分片策略按互联带宽算，不按卡数算 |
| 4090 推理「开始吞吐高，后来掉下去」 | 24 GB 装不下 KV + 权重，被迫换出；或 GDDR6X 拐点 82 高于预期（§17.5） | 看显存水位与 `dram__throughput` | 限上下文、量化权重、降到能装下的 batch | 容量规划用「权重 + KV + 激活峰值」三块和，不只看权重 |

最后一行值得展开一句：**4090 的 FP32 拐点是 82 FLOP/B，比 A100 的 12.6 高 6.5 倍。** 同一段代码在 A100 上算力瓶颈，在 4090 上可能已经掉到带宽瓶颈——所以「换一张更便宜的卡」从来不是等比缩小，它改变的是瓶颈的位置。

## 17.11 一页速记

```
【一句话】功耗 ∝ f·V² 且散热封顶 → 提频最贵（∝f³）、堆核最便宜（∝N）
          → GPU = 低频 × 海量核 × 超宽总线 → 「算得快」其实是「等得少」

【三条公式】
  ① P_dyn = α·C·V²·f        V 必须跟着 f 涨 → 提频 10% 约 +33%（1.1³）
  ② 带宽 = 位宽(bit) × 数据率(Gbps) ÷ 8 （给时钟时数据率 = 时钟 × 2）
  ③ P(AI) = min(π, β·AI)，拐点 I* = π/β

【五个数（厂商规格/量级）】
  A100 40G: π=19.5 TFLOPS(FP32)  β=1.55 TB/s  I*=12.6 FLOP/B
  A100 FP16 张量核: π=312        同一 β        I*=201
  H100:     π=66.9 / 989(FP16t)  β=3.35 TB/s  I*=20 / 295
  4090:     π=82.6(FP32)         β=1.008 TB/s I*=82
  服务器:   π≈0.38(64C FP32)     β=0.461 TB/s I*=0.83
  → CPU 几乎总是算力瓶颈，GPU 几乎总是带宽瓶颈

【显存「大」的真相】
  不是容量大（服务器 768 GB > 4090 的 24 GB），是每 GB 配 42 GB/s（服务器 0.6）
  HBM：3D 堆叠给容量，摞数 × 1024 bit 给位宽，硅中介层让 5120 根线走得通

【浮点】
  FP16: 5 位指数 → 上限 65504，会溢出，要 loss scaling
  BF16: 8 位指数（同 FP32 范围）+ 7 位尾数 → LLM 默认
  TF32: FP32 的存储、10 位尾数 → 一行开关换 8×
  16× = 低精度打包(2–4×) × 张量核(4–8×)；拐点也跟着往右搬 16 倍

【一句话判瓶颈】
  AI < I* → 加带宽/加 batch/分块复用；AI > I* → 换精度/换更快指令；
  两个利用率都低 → 占用率不够，延迟没东西可藏
```

## 17.12 自检 3 题

**Q1.** 某卡 FP32 峰值 20 TFLOPS、带宽 1.6 TB/s。一个逐元素算子每个元素读 8 B、写 4 B、做 2 FLOP。它在这张卡上的性能上限是多少？如果把权重从 FP32 换成 BF16（算力不变、字节减半），上限变成多少？为什么？

<details><summary>答案</summary>

先算 AI：每元素搬运 `8 + 4 = 12 B`，做 `2 FLOP`，所以 `AI = 2/12 = 0.167 FLOP/B`。

拐点 `I* = 20e12 / 1.6e12 = 12.5 FLOP/B`。`0.167 ≪ 12.5`，所以是**带宽瓶颈**：

```
P = β · AI = 1.6e12 × 0.167 = 2.67e11 = 267 GFLOPS
```

只有峰值的 **1.3%**——这就是「逐元素算子永远跑不满」的定量答案。

换成 BF16 后，每元素 `4 + 2 = 6 B`，`AI = 2/6 = 0.333`，`P = 1.6e12 × 0.333 = 533 GFLOPS`。**字节减半，性能翻倍，但仍然是峰值的 2.7%。** 结论：低精度对带宽瓶颈的算子只有线性收益（字节减半 → 吞吐翻倍），拿不到张量核那 16 倍；那 16 倍只属于 AI 已经超过拐点的稠密矩阵乘。

</details>

**Q2.** 为什么 H100 的 FP16 张量核峰值是 FP32 的约 15 倍，但同一块卡上跑 7B 模型的 decode 时，两者的 token/s 几乎一样？

<details><summary>答案</summary>

因为 decode 的瓶颈不是 `π`，是 `β`。decode 每生成 1 个 token 要把 14 GB 权重完整读一遍（7B × 2 B），做 `2 × 7e9 = 1.4e10 FLOP`：

```
AI = 1.4e10 / 1.4e10 = 1 FLOP/B
```

而 FP16 张量核的拐点是 295 FLOP/B（H100）。`AI = 1 ≪ 295`，所以 `P = β × AI`，**与 `π` 无关**。token/s 的上限是 `3.35 TB/s ÷ 14 GB = 239 token/s`，FP16 和 FP32 都受同一条带宽线约束。

这也解释了为什么 decode 阶段换精度没用、加 batch 有用：换精度只抬 `π`（本来就没用上），加 batch 抬的是 `AI`。只有当 batch 大到 `AI > 295`（约 300），张量核的算力才开始参与。

</details>

**Q3.** 同事说：「把 GPU 频率从 1.8 GHz 超到 2.2 GHz，性能能涨 22%，因为 2.2/1.8 = 1.22。」这句话在什么前提下成立？在真实芯片上为什么通常做不到？

<details><summary>答案</summary>

前提是**电压不变、散热有余量、且瓶颈在算力而不在带宽**。三个前提缺一不可。

真实芯片上：

1. **电压必须跟着涨**。门延迟 ∝ `CV/(V-V_th)`，1.8→2.2 GHz（+22%）通常要把 V 从 ~1.0 V 抬到 ~1.15 V。功耗 `P ∝ V²f`：`(1.15/1.0)² × 1.22 = 1.61`，**+61% 功耗换 +22% 性能**。
2. **散热没有余量**。H100 的 700 W 已经是液冷机架的设计点，+61% 直接越过封装与供电上限，芯片会降频保护，实际收益可能为负。
3. **瓶颈可能不在算力**。如果这段代码的 `AI` 低于拐点，性能 = `β·AI`，超频只让 `π` 变大，`β` 一点没变，实测性能涨 0。

所以「按频率线性外推性能」只在「算力瓶颈 + 电压不动 + 散热无限」的假想世界里成立。真实的 GPU 选择停在 1.4–2.5 GHz，正是因为这三点全都反向——**频率是三次方付费的奢侈品，核数是线性付费的日用品。**

</details>
