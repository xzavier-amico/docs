## 08.1 引子：三起「器件约束」伪装成代码事故

三种器件各有**一条**无法绕过的硬约束。事故的共同形态是：这条约束在监控上看不见，只表现为「慢了」，于是所有人都去改代码。

### 事故一：每次 commit 卡 8 ms（2025-04，某支付对账服务）

对账引擎每处理一笔订单就 `write` WAL 再 `fsync`，P99 提交耗时 **8.2 ms**，而 CPU 使用率只有 3%，GC 日志干净，慢 SQL 一条没有。运维第一反应是「代码里 `fsync` 写太多了，去掉」——去掉就等于取消持久性，这是拿正确性换延迟。

`iostat -x 1` 拿到的是另一幅图：

| 时间 | `w/s` | `await` | `aqu-sz` | `%util` | 盘 | 业务 P99 commit |
| --- | --- | --- | --- | --- | --- | --- |
| 10:00 | 148 | 13.1 ms | 2.0 | 99% | HDD RAID1 云盘 | 8.2 ms |
| 10:30 组提交上线 | 1,900（批量 16） | 11.8 ms | 1.1 | 61% | 同上 | 0.9 ms（分摊/笔） |
| 次日 换 NVMe | 42,000 | 0.19 ms | 8.2 | 87% | NVMe 云盘 | 0.15 ms |

把 13.1 ms 拆开：平均寻道 4.5 ms + 旋转半圈 4.17 ms + 4 KB 传输 0.02 ms ≈ 8.7 ms，再加上控制器与排队 → 13 ms。**8.2 ms 的 commit 不是「代码慢」，是磁盘转了半圈。** 修法只有两条：让一次机械动作摊到 16 笔提交上（组提交，`base/29` 的 WAL 机制），或者换掉机械介质。

### 事故二：换成 SSD 后随机写更慢，三个月寿命掉 40%（2025-06，某订单库迁移）

把 1.2 亿行的订单库从 HDD 云盘迁到 2 TB **QLC** 云 SSD（宣传顺序读 3 GB/s、写 1.5 GB/s）。上线第一周压测正常，第二周 4 KB 随机写从 6,000 IOPS 掉到 1,800，第三个月 `fio` 只剩 800 IOPS——比老 HDD 还难看。

`smartctl -A /dev/nvme0` 三个月后的两个数：`Percentage Used = 40%`、`Data Units Written = 65,900,000`（单位 512 KB）。业务侧统计逻辑写量 375 GB/天。把这两组数对上：

```
主机写量   = 65,900,000 × 512 KB      = 33.8 TB（90 天）
器件写量   = 40% × 1,100 TB（TBW）    = 440 TB
写放大 WA  = 440 / 33.8               = 13.0×
```

**没有一行代码写错，是这颗器件的擦除块被踩了。** 4 KB 随机写 + 盘内有效数据 92% + 从未 TRIM 过批量删除的历史数据 → 每次垃圾回收都要搬走块里 92% 的页。修法与账见 §08.4。

### 事故三：把 HDD 的随机 4K 当 SSD 用（2025-09，某日志检索服务）

32 个线程各做 4 KB 随机读，按「SSD 上 200 IOPS/线程」估了 6,400 IOPS，实测 **180 IOPS**，且 P99 从 12 ms 涨到 420 ms。用 Little 定律当场算清：`180 IOPS × 0.42 s = 76` 个未完成请求——队列里堵着 76 个请求，而磁头只有一个。加线程在这块盘上**唯一的效果是把队列拉长**（§08.7）。

## 08.2 DRAM：一个电容记住一位，于是刷新成了强制税

### 物理形态：1T1C + 一个灵敏放大器

每一位 = 一个 NMOS 管 + 一个电容（DDR4 世代约 25 fF）。写 1 = 给电容充电，写 0 = 放电。读的时候把电荷倒进一条很长的位线，位线的寄生电容约是单元电容的 10 倍——电荷共享后电压摆幅只有 **几十 mV**，所以每一列必须配一个**灵敏放大器**把它放大到全摆幅。灵敏放大器同时是唯一的「刷新器」：它把放大后的值原样写回单元。

```
       一条位线（Bit Line）                  灵敏放大器
  ┌───────────────────────────────────────┐   ┌────────┐
  │  ┌───┐  ┌───┐  ┌───┐  ┌───┐           │   │  ┌──┐  │
字│  │T  │  │T  │  │T  │  │T  │  ...      │──▶│  │SA│  │──▶ 数据输出
线│  │   │  │   │  │   │  │   │           │   │  └──┘  │
  │  └─┬─┘  └─┬─┘  └─┬─┘  └─┬─┘           │   └────────┘
  │   ─┴─     ─┴─     ─┴─     ─┴─  25 fF   │        ▲
  │   ⏚       ⏚       ⏚       ⏚  会漏电   │        └─ 放大后写回 = 刷新
  └───────────────────────────────────────┘
```

### 为什么必须刷新：算一次带宽税

电荷在 10–100 ms 量级漏光（亚阈值漏电 + 结漏电）。JEDEC 的折中：**64 ms 内把整个阵列的每一行都读一遍写回**。

| 量 | 数值 | 出生证明 |
| --- | --- | --- |
| 刷新窗口 | 64 ms | JEDEC 器件规范 |
| 每窗口刷新命令数 | 8,192（以 8,192 行/bank 的器件为例） | 行数 = 命令数 |
| 命令间隔 tREFI | 64 ms / 8,192 = **7.81 µs** | 上两行相除 |
| 每条命令占用时间 tRFC | ≈ 350 ns | DDR4 8 Gb tRFC1 |
| 每窗口被占用时间 | 8,192 × 350 ns = **2.87 ms** | 相乘 |
| **带宽税** | 2.87 / 64 = **4.5%** | 相除 |

4.5% 是**与负载无关的常数**：哪怕你的程序一个字节都不读，DRAM 每秒也照样交出这部分时间。两个现实修正：① 更大容量的 die 行数翻倍（16,384 行 → tREFI 3.9 µs），all-bank 刷新的税升到 8–9%；② 高温要加倍刷新（tREFI 减半 → 税翻倍），所以机房温度直接变成了内存带宽成本。

### 行缓冲：顺序快、随机慢的第一层原因

阵列是「行 × 列」矩阵。一次 `ACT` 把一整行搬进**行缓冲**（每颗 x8 芯片 1 KB，一个 64-bit rank = 8 颗 = **8 KB**），后续 `CAS` 只动这个缓冲。

- **行命中（row hit）**：直接 `CAS`。DDR4-3200 CL22 = 22 cycle × 0.625 ns = **13.75 ns**。
- **行未命中（row miss）**：先 `PRE` 关行、再 `ACT` 开新行，额外 `tRP + tRCD` ≈ 13.75 + 13.75 = **27.5 ns**。
- 于是：顺序读 8 KB = 一次 `ACT` + 128 次 `CAS`（每次 64 B），摊到 64 B 上是 13.75/128 ≈ 0.1 ns 的开关销；随机读每次都撞新行，每 64 B 要付 ≈ 41 ns 的开关销 → 有效带宽掉一个数量级以上。

**"DRAM 随机访问 ~80 ns" 这个数字就是从这三行推出来的**（13.75 命中 + 27.5 未命中 + 控制器/纠错排队）。这也是 `base/07` 里「按行遍历数组比按列快 5–10 倍」的另一半原因：缓存只是一半，另一半是 DRAM 行命中。

### DDR 双沿与 burst 8：带宽公式的出生证明

DDR 的「双」指时钟上下沿各传一次：1600 MHz 时钟 → **3200 MT/s**。每一条读命令固定传 BL8 = 8 个传输。64 位通道 = 8 B。

```
单通道带宽 = 位宽 × 传输率 = 8 B × 3200 MT/s = 25.6 GB/s
双通道     = 25.6 × 2                     = 51.2 GB/s   ← DDR4-3200 双通道
DDR5-4800 双通道 = 8 B × 4800 MT/s × 2    = 76.8 GB/s
每次 burst 搬 8 × 8 B = 64 B               = 一条 cache line（不是巧合，是对齐设计）
```

51.2 GB/s 是**承诺值**；`STREAM` 实测通常 60–75%，即 32–38 GB/s（量级结论，取决于内存控制器与 NUMA 拓扑）。再乘上 4.5% 的刷新税，你可用的稳态带宽还要再低一点。

## 08.3 SSD：写单位是页，擦除单位是块 —— 全部麻烦的源头

### 物理形态：浮栅里的电子数 = 电压等级 = 数据

NAND 每个 cell 是浮栅晶体管：注入电子会抬高阈值电压 `Vth`。读 = 用参考电压去比 `Vth` 落在哪个区间。**区间越多，每 cell 装的 bit 越多，但写得更慢、更容易读错、能承受的擦写次数更少。**

| 等级 | bit/cell | 电压区间 | 参考电压数 | P/E 寿命 | 典型场景 |
| --- | --- | --- | --- | --- | --- |
| SLC | 1 | 2 | 1 | 50k–100k | 企业写密集、SLC 缓存区 |
| MLC | 2 | 4 | 3 | 3k–10k | 上一代企业盘 |
| TLC | 3 | 8 | 7 | 1k–3k | 2020 后主流 |
| QLC | 4 | 16 | 15 | 100–1k | 读多写少、冷数据、消费级大容量 |

### 两条铁律（这就是全部麻烦）

1. **编程（写）单位 = 页，4–16 KB**。页在被擦除之前只能写一次，且只能往「1 → 0」的方向写。
2. **擦除单位 = 块，4–16 MB**，一块含 256–1024 个页。擦一下，整块的所有页一起归零。

于是「原地更新 4 KB」在这颗器件上**不存在**：你不能改已写页里的一个字节，只能把新数据写到另一个空闲页、把旧页标记作废、再改一张映射表。**不懂擦除块，就永远不懂随机写为什么慢两个数量级。**

```
 块 (4 MB = 256 页 × 16 KB)                    空闲块池
┌────┬────┬────┬────┬────┬────┬────┬────┐    ┌────┬────┐
│ P0 │ P1 │ P2 │ P3 │ P4 │ P5 │ P6 │P255│    │    │    │
│ 有效│作废│ 有效│作废│ 有效│作废│ 有效│ ...│    │    │    │
└────┴────┴────┴────┴────┴────┴────┴────┘    └────┴────┘
   GC 要回收这个块：读 128 个有效页 → 写到新块 → 改映射 → 才能 ERASE
   u = 有效页占比 = 128/256 = 0.5  →  WA = 1/(1-u) = 2.0×
```

### FTL：那张必须靠电容才能活下来的表

| 映射粒度 | 表大小（4 TB 盘） | 优点 | 致命缺点 | 用在哪 |
| --- | --- | --- | --- | --- |
| 页级 | 4 TB / 16 KB × 4 B ≈ **1 GB** | 任意页可写、写放大低 | 表太大，必须放 DRAM | 绝大多数消费/企业盘 |
| 块级 | 4 TB / 4 MB × 4 B ≈ **4 MB** | 表可以塞进 SRAM 甚至片上 | 块内只能顺序写，小写放大爆炸 | 早期 U 盘、部分嵌入式 |
| 混合 | 数据块级 + 日志块吸收小写 | 折中 | 复杂度高 | 部分企业盘 |

页级映射意味着**盘上有一张 1 GB 的表需要随机访问**——这就是企业盘为什么配 1–4 GB DRAM，以及为什么必须配**掉电保护电容**（PLP，钽电容或超级电容）：断电瞬间要把 DRAM 里的映射表与写缓存刷回 NAND 的空闲区，否则整盘数据变成孤儿。消费级盘没有这个电容，靠「掉电时直接丢弃缓存 + 上电扫描重建」，代价是掉电后可能丢最后几十 MB 且映射重建慢。

### 垃圾回收、TRIM、OP、磨损均衡

- **GC（垃圾回收）**：空闲块不够时，挑一个有效页最少的块，把有效页搬到别处，再擦除。搬动的量就是**写放大**。
- **TRIM / discard**：文件系统删文件只改元数据，SSD 不知道那些页已经作废，GC 会把垃圾当宝贝搬一遍。TRIM 显式通知器件。批量化用 `fstrim -av`（周期性）优于挂载 `discard`（每次删除都发一条命令，抖动大）。
- **OP（预留空间）**：出厂隐藏一部分容量（消费级 ~7%，企业级 28% 起），让稳态下 `u` 更低。**OP 不是浪费，是买写放大的钱。**
- **磨损均衡**：动态（新写入挑擦除次数少的块）+ 静态（定期把冷块里的数据搬走，避免冷数据"钉住"健康块）。静态均衡本身是一次额外搬迁，也是写放大。
- **掉速**：盘写满后没有空闲块，GC 只能"边写边回收"，第一次出现了「写一条就要搬一条」的正反馈；这就是 §08.9 里 TLC/QLC"缓外掉速"的根。

## 08.4 写放大账：一个可以自己复算的算例

### 三项分解（先给公式，再给数）

| 项 | 公式 | 4 KB 随机写算例 | 说明 |
| --- | --- | --- | --- |
| GC 放大 | `1/(1−u)`，`u` = 被回收块内有效页占比 | `u=0.70 → 3.33×` | 盘越满，`u` 越高，放大越快 |
| 部分页放大 | `页大小 / 写大小`（仅当不能合并追加时） | `16 KB / 4 KB = 4.0×` | 只能靠攒满一页或 SLC 缓存规避 |
| 元数据/映射日志 | 实测 1.05–1.3 | `1.1×` | 每次写都要记映射日志 |
| **合成** | 前两项相乘再乘第三项 | **3.33×（能合并）～14.7×（不能合并）** | 事故二的 13× 落在高档 |

### 主算例（题目要求的这一条，逐步可复算）

**假设清单**（每一条都会影响结果，所以必须写出来）：盘 2 TB QLC；页 16 KB；块 4 MB（= 256 页）；TBW 1,100 TB（≈0.3 DWPD × 5 年）；负载 = 4 KB 随机写 **375 GB/天**；稳态下盘内有效数据 92%；GC 时被回收块里 **70% 的页仍有效**。

```
第 1 步  写放大      WA   = 1/(1 − 0.70)          = 3.33×
第 2 步  器件写量    375 GB × 3.33                = 1.25 TB/天
第 3 步  寿命        1,100 TB ÷ 1.25 TB/天        = 880 天 ≈ 2.4 年
第 4 步  DWPD 对照   主机侧 375/2000 = 0.19       器件侧 1.25/2000 = 0.63
```

第 4 步是最容易被忽略的一行：**厂家标的是 0.3 DWPD（器件侧），你按主机侧算出来「只用了额度的 63%」，实际器件侧已经超 2 倍。**

### 敏感性：`u` 是唯一的开关

| 盘内有效占比 `u` | 写放大 `1/(1−u)` | 器件写量（375 GB/天） | 寿命（TBW 1,100 TB） | 90 天消耗 TBW |
| --- | --- | --- | --- | --- |
| 50%（半满 + OP 充足） | 2.0× | 0.75 TB/天 | 1,467 天 | 6.1% |
| 70%（算例给定） | 3.33× | 1.25 TB/天 | 880 天 | 10.2% |
| 90%（快写满） | 10.0× | 3.75 TB/天 | 293 天 | 30.7% |
| 92% + 不能合并（事故二） | 13.0× | 4.88 TB/天 | 226 天 | 39.9% |

最后一行与 `smartctl` 读到的 `Percentage Used = 40%` 对上了。**同一块盘、同一份业务，`u` 从 0.70 挪到 0.92，寿命从 2.4 年掉到 7.4 个月。**

可执行版本（三行核心）：

```python
def wa(u):                      # u = GC 时块内有效页占比
    return 1 / (1 - u)

def life_days(tbw_tb, host_gb_day, amplification):
    return tbw_tb * 1000 / (host_gb_day * amplification)

print(round(wa(0.70), 2))                        # 3.33
print(round(life_days(1100, 375, wa(0.70))))     # 880   天
print(round(life_days(1100, 375, 13.0)))         # 226   天
print(round(0.40 * 1100 / (65_900_000 * 512e3/1e12), 1))   # 13.0  从 smartctl 反推
```

**修正后的收益**：`fstrim` + 18% OP + 把 4 KB 随机改成 16 KB 对齐批量 + 关掉应用层冗余双写 → `WA` 13 → 3.3，寿命 226 天 → 880 天；同时器件侧写量降到 1/4，随机写 IOPS 从 800 回到 3 万级。**这是器件约束直接翻译出来的运维动作，不是"调优经验"。**

## 08.5 为什么「随机 4K 写」慢两个数量级：把链条走一遍

一次逻辑 4 KB 随机写（覆盖一个已存在的页），在满盘 QLC 上要走完这七步：

```
① 查映射        FTL 查 LPN→PPN 表（命中 DRAM ~1 µs；未命中读 NAND 映射页 ~60 µs）
② 读旧页        页里还有别的有效数据 → 读整页 16 KB（tR ≈ 50–70 µs）
③ 改内存        在 SRAM 里改 4 KB（~0.1 µs，可以忽略，但它是"必须读"的原因）
④ 编程新页      写一页 16 KB（tPROG ≈ 500–800 µs，多平面并行后摊薄到 100–200 µs）
⑤ 记映射        追加映射日志（小块写，必须原子）
⑥ 触发 GC       空闲块不足 → 搬 u × 256 页（u=0.92 → 235 页 = 3.8 MB 额外读 + 额外写）
⑦ 擦除          tBERS ≈ 2–5 ms（可并行，但会占满那些 die 的带宽）
```

**用户买了 4 KB，器件付了 16 KB 读 + 16 KB 写 + 3.8 MB GC 搬运 + 一次块擦除。** 顺序写只走 ①④⑤：数据连续追加，页被攒满，GC 的 `u` 接近 0（整块都是同一个文件的旧版本，全部作废），写放大趋近 1。**"随机"这个词本身不慢，"随机导致擦除块反复被半填 + 反复搬运"才慢。**

| 器件 | 顺序写带宽 | 4K 随机写 QD1 | 4K 随机写队列满 | 4K 随机写有效带宽 | 单请求延迟 |
| --- | --- | --- | --- | --- | --- |
| HDD 7200 rpm（RAID 无缓存） | 150–250 MB/s | 90 IOPS | 150–200 IOPS | 0.36–0.8 MB/s | 8–13 ms |
| SATA TLC SSD | 500–550 MB/s | 10k IOPS | 60–90k IOPS | 240–360 MB/s | ~100 µs |
| NVMe TLC SSD（缓内） | 1.5–3.5 GB/s | 12–15k IOPS | 200–500k IOPS | 0.8–2 GB/s | 70–100 µs |
| NVMe QLC（92% 满，WA 13） | 1.5 GB/s 缓内 / 0.3 GB/s 缓外 | 5k IOPS | 25–40k IOPS | 100–160 MB/s ÷ 13 | 200–400 µs |

读这张表的方式：HDD 的顺序/随机比是 `200 MB/s ÷ 0.36 MB/s ≈ 555×`，**这就是那两个数量级的原始形态**；SSD 的带宽比只有 5–20×，但它的**寿命账**是 3–15×，两者相乘才是运维感受到的「慢」。所有数字都是量级结论（厂商公开规格区间 + 上述公式），不是某一台机器的实测；本机实测见 §08.10。

## 08.6 HDD：一次定位 < 5 ms，于是 IOPS 被机械动作封顶

### 几何：一个磁臂管所有盘面

盘片 1–9 张同轴旋转 → 每面若干条磁道 → 每条磁道切成扇区。**所有盘面共用一根臂**，同一时刻只有一个磁头在读写——这就是"机械盘没有内部并行度"的物理原因（NCQ 只能重排，不能并行）。

- **扇区**：`512e` = 逻辑 512 B / 物理 4 KB（固件做转换）；`4Kn` = 逻辑与物理都 4 KB。512e 上小于 4 KB 且不对齐的写，固件要做**读-改-写整个物理扇区**，放大 8×，且掉电有撕裂风险。
- **容量账**：7200 rpm 下 200 MB/s ÷ 120 转/秒 = **每转传输 1.67 MB**；20 TB / 9 盘片 ≈ 每面 2.2 TB。这两个数共同决定了磁道密度。

| 时间项 | 数值 | 出生证明 |
| --- | --- | --- |
| 平均寻道 | 4.0–5.0 ms（近线盘）/ 8.5 ms（桌面盘） | 机械臂移动 + 稳定时间 |
| 旋转延迟（平均） | **4.17 ms** | 7200 rpm = 120 r/s → 8.33 ms/圈 → 平均半圈 |
| 传输 4 KB | 0.02 ms | 4 KB ÷ 200 MB/s |
| 控制器 + 排队 | 0.05–0.2 ms | 队列非空时 |
| **合计** | **8.2–12.9 ms** | |

```
随机 4K IOPS = 1 / (寻道 + 旋转 + 传输) = 1 / 0.0082 s = 122
                                         1 / 0.0129 s =  78
顺序带宽    = 200 MB/s（只付"传输"那一行）
随机有效带宽 = 122 × 4 KB = 0.49 MB/s      → 比值 ≈ 408×
```

**注意最后一个数字的形状**：`120 r/s` 是这块盘的物理上限——它每秒只有 120 次机会把磁头停在正确位置。所以「HDD 随机 IOPS ≈ 100–200」里那个 200 的上界，来自「一半机会正好落在外圈（转速不变但每圈字节更多）+ 磁盘缓存 + 队列重排」的好运气，**不是来自更强的电机**。

## 08.7 队列深度与并发：Little 定律是唯一的账本

三个量，一条恒等式：

```
未完成请求数 L = 吞吐 λ × 单请求延迟 W
=> IOPS = QD / 延迟          （QD = 同时在飞的请求数）
```

| 器件 | 单请求延迟 W | 队列结构 | QD=1 的 IOPS | 队列打满的 IOPS | 打满时的延迟 |
| --- | --- | --- | --- | --- | --- |
| HDD 7200 rpm | 8.2–12.9 ms | 1 队列 × 32 条目（NCQ） | 90 | 150–200 | 60–170 ms（全在排队） |
| SATA SSD | ~100 µs | 1 队列 × 32 条目（AHCI） | 10k | 60–90k | ~400 µs |
| NVMe SSD | ~80 µs | **64K 队列 × 每队列 64K 条目** | 12.5k | 200k–1M | 300–600 µs |
| 网络块存储（云盘） | 0.5–2 ms | 依厂商规格，通常按 IOPS 配额限流 | 500–2k | = 你的配额 | 配额打满后线性上涨 |

两条推论，都是可以直接用来判故障的：

1. **加并发买到的是并行度，不是速度。** 器件内部并行度用尽之后（HDD 是 1，SSD 是 NAND die 数 × 平面数，NVMe 是主控通道数），再加 QD 只增加 `W`，不增加 `λ`。事故三里 32 线程把延迟从 12 ms 顶到 420 ms，吞吐几乎没动，正是 QD 越过器件并行度后的标准形态。
2. **NVMe 的 64K 队列不是"你需要 6.4 万并发"，而是"不再有一个队列一把锁"。** SATA/AHCI 只有 1 个队列 32 条目，所有核抢同一把锁、同一个中断；NVMe 让每个核一对队列，无锁、无跨核中断——**这是接口层面的排队结构差异，不是带宽差异**（主线②、主线③）。

## 08.8 器件约束如何翻译成系统设计

这一节是全篇的出口：**每一个"约定俗成"的设计，都能在这里找到它的器件出处。**

| 器件约束 | 它翻译出来的设计 | 为什么非这样不可 |
| --- | --- | --- |
| 擦除单位 4 MB、页只能写一次 | 日志结构文件系统（F2FS/NILFS）、LSM-tree、WAL | 把随机更新改成顺序追加，让"作废"发生在整块粒度 |
| 同上 | COW（btrfs/ZFS 写时复制） | 与器件"只能写到新位置"的方向一致，省掉一次搬迁 |
| 扇区原子性只有 4 KB，页有 16 KB | InnoDB doublewrite、文件系统日志校验和 | 16 KB 页可能被撕裂，必须有一次"可重放的整页副本" |
| 断电丢 DRAM 缓存 | `fsync` / `fdatasync` + 对盘的 FLUSH CACHE | `write()` 返回只代表进了页缓存（`base/29`） |
| 页缓存回写时机不可控 | `O_DIRECT` | 数据库自己管缓存与顺序，且要求 4 KB 对齐落盘 |
| 器件延迟 µs–ms 级、需要并发填充 | `io_uring` / AIO / 线程池 | 单线程只能拿到 `1/W` 的吞吐 |
| 单磁臂无内部并行 | `mq-deadline` / `bfq`、预读、请求合并 | 把随机重排成近顺序，是机械盘唯一能"优化"的东西 |
| NAND 需知道哪些页作废 | TRIM/discard + OP | 降低 GC 搬运量 = 直接降低写放大 |

几个必须展开的点：

- **4 KB 页大小的由来（历史 + 缺页成本 + TLB 覆盖）**：i386（1985）选 4 KB，因为当时 1 MB 内存 ÷ 4 KB = 256 个页帧，两级页表各 1,024 项 × 4 B = 正好 4 KB = 1 页，页表开销 0.4%。而缺页要付一次 4–8 ms 的机械 IO，页从 4 KB 加到 8 KB 只多传 0.02 ms——**在机械时代"页大一点"几乎白送**，但页表会变大、内部碎片会变多。今天 TLB 1536 项 × 4 KB = 6 MB 覆盖，2 MB 巨页 → 3 GB 覆盖，这才是 THP 存在的理由（账在 `base/26`、`base/07`）。
- **页缓存与 `fsync` 的必要性**：这台机器的默认值是 `dirty_ratio=20`、`dirty_background_ratio=10`（见 §08.10 实测），意味着最多 20% 的内存可以装脏页，30 秒后才被回写。`write()` 只是把数据拷进页缓存，**"提交成功"到"数据在盘上"之间隔着页缓存、文件系统日志、盘上写缓存三层谎**——完整拆解在 `base/29`。
- **WAL / LFS / LSM 是同一招**：都靠"只追加、不改原地"把随机小写变成顺序大写，代价是把"更新"变成"留下旧版本 + 后续清理"（LSM 的 compaction 与 SSD 的 GC 是**同构**的，都在搬有效数据）。见 `base/28`、[comp/02](../comp/02-storage-engine-three-shapes.md)、[comp/03](../comp/03-wal-bufferpool-crash-recovery.md)。
- **16 KB 页 + doublewrite**：器件保证的原子单位是 4 KB 物理扇区，InnoDB 的 16 KB 页在掉电瞬间可能只落了一半。doublewrite 先把页顺序写到一块连续区域再写数据文件，代价是 2× 写——**用 100% 的写放大换"崩溃后一定可恢复"**（账在 [comp/05](../comp/05-innodb-page-and-row.md)）。
- **`O_DIRECT` 为什么存在**：① 避免双重缓存（DB 有 buffer pool，页缓存里再存一份是纯浪费）；② 避免内核回写时机不可控（想要"一次 `pwrite` 就真的落到器件"）；③ 让 WAL 的顺序追加真的顺序（绕开 readahead 与合并）。代价：缓冲区必须 `posix_memalign(4096)` 对齐、偏移必须 512 B/4 KB 对齐、不能跨页。

## 08.9 三列账 + 踩坑清单

### 三列账

| 器件 | 承诺了什么 | 为此付了什么 | 从哪里开始失效 |
| --- | --- | --- | --- |
| DRAM | 任意地址 ~14 ns 的行命中；可无限次改写、无磨损 | 每 64 ms 全阵列刷一遍（4.5–9% 带宽）+ 持续供电 + 纠错码 | 断电即失；行冲突/刷新抖动让 P99 尖刺；容量与功耗墙 |
| SSD (NAND) | 随机访问与顺序一样"寻址"；无机械、µs 级延迟、抗震动 | 先擦后写 → FTL 映射 + GC 搬运 + 写放大；P/E 有限；OP 与 DRAM+电容 | `u` 高 → WA 爆炸（3.3× → 13×）；写满后掉速；寿命按 TBW 走完 |
| HDD | 每 GB 最便宜；顺序 150–250 MB/s | 每次访问付 4.5 ms 寻道 + 4.17 ms 旋转；单磁臂无并行 | 随机负载（IOPS 封顶 100–200）；队列一深延迟线性上涨；512e 的不对齐写放大 8× |

### 踩坑清单（现象 → 根因 → 定位 → 修）

| 现象 | 根因（指回物理事实） | 怎么定位 | 怎么修 |
| --- | --- | --- | --- |
| commit 稳定在 8–13 ms，CPU 却闲置 | 每次 `fsync` 等一次完整机械动作 | `iostat -x 1` 看 `await` 是否 ≈ 寻道+旋转 | 组提交、批量 `fsync`、换闪存 |
| 换 SSD 后随机写反而更慢 | 盘满 + `u` 高 → GC 写放大；或落到 QLC 缓外 | `smartctl` 的 `Percentage Used` / `Data Units Written` 反推 WA | `fstrim`、加 OP、4K 随机改 16 KB 对齐批量 |
| 寿命 3 个月掉 30–40% | WA 远超预期（主机侧算起来只用了一半额度） | 同上，把 TBW × Percentage 除以主机写量 | 降 WA 比换盘便宜：TRIM + OP + 减少小随机写 |
| `%util` 100% 但 IOPS 极低 | 单队列器件（HDD）队列已满，`%util` 就是饱和信号 | 与 `aqu-sz`、`await` 一起看：`aqu-sz ≈ (r/s+w/s) × await/1000` | 加并发无效，改批量或换介质 |
| `%util` 100% 但延迟很低 | SSD/NVMe 支持并发，`%util` 只表示"至少一条在飞"，不是饱和 | 看 `aqu-sz` 与 `await` 是否同时上涨 | 不要拿 `%util` 给闪存判死刑 |
| 大文件拷贝前 50 GB 快、后面骤降 | TLC/QLC 的 SLC 缓存写完，进入原生写速 | `fio --rw=write --size=200G --runtime=600` 看 `bw` 随时间两段 | 规划写带宽按"缓外速度"算；企业盘看稳态规格 |
| 512e 盘上小写特别慢 | 4 KB 物理扇区的读-改-写放大 8× | `lsblk -t` 看 `PHY-SEC=4096 / LOG-SEC=512` | 分区与文件系统按 4 KB 对齐；`mkfs` 对齐到 1 MB |
| 虚拟机里"机械盘"却跑出 1.2 GB/s | `rotational=1` 是虚拟化遗留，调度器/预读按机械盘策略走 | `cat /sys/block/vda/queue/rotational` | 按实测设 `rotational=0`、调 `nr_requests` 与调度器 |

### 三条命令的读法（现象落到数字上）

`iostat -x 1` 只看四列：`r/s`+`w/s` 是完成的 IOPS；`await` 是**排队 + 服务**的平均毫秒数（HDD 上 ≈ 8–13 ms 说明每个请求都在等机械动作，SSD 上 > 1 ms 说明队列堆积）；`aqu-sz` 是平均队列深度，用来与 Little 定律互验；`%util` 是"设备有请求在飞的时间占比"，**对单队列 HDD 是饱和度信号，对并发器件不是**。

`fio` 只看四列：`iops`（吞吐）、`clat`（完成延迟，不含排队，反映器件）、`lat`（含排队，反映用户感受）、`bw`；再配三个开关才能测到真话——`--direct=1`（绕页缓存）、`--ramp_time`（跳过预热与 SLC 缓存）、`--runtime=600 --time_based`（看稳态，缓外掉速只在长跑里出现）。

`smartctl -A` 只看四个字段：`Percentage Used`（寿命消耗估算）、`Data Units Written`（×512 KB = 主机写量）、`Available Spare`（备用块余量）、`Media and Data Integrity Errors`（不可纠正错误，> 0 就换盘）。

## 08.10 实验：在这台机器上量四个数

**环境**：KVM 小机，2 vCPU（AMD EPYC 7K62）、2 GB 内存、单块 virtio 盘 `/dev/vda`，Debian 12 / 内核 6.12。**这台机器没装 `fio` 与 `smartctl`，也无法访问真实 HDD 与 QLC 盘**，所以下面只贴真跑得到的输出；HDD 与 QLC 的部分给出可推导的估算，并明确标注是估算。

### E1 · `lsblk -t`：器件自报的几何（真实输出）

```console
$ lsblk -t
NAME   ALIGNMENT MIN-IO OPT-IO PHY-SEC LOG-SEC ROTA SCHED RQ-SIZE  RA WSAME
sr0            0   2048      0    2048    2048    1 none      256 128    0B
vda            0    512      0     512     512    1 none      256 128    0B
└─vda1         0    512      0     512     512    1 none      256 128    0B
```

读法：`PHY-SEC=512 / LOG-SEC=512` → 这块虚拟盘不是 4Kn 也不是 512e，小写不会被放大；`ROTA=1` → 自报机械盘（虚拟化遗留，见下）；`RA=128` = 预读 128 KB = 16 个 8 KB 块；`RQ-SIZE=256` = 队列 256 条目。

### E2 · 队列参数（真实输出）

```console
$ for f in rotational nr_requests scheduler logical_block_size physical_block_size \
           max_sectors_kb write_cache; do
    printf '%-20s %s\n' "$f" "$(cat /sys/block/vda/queue/$f)"; done
rotational           1
nr_requests          256
scheduler            [none]
logical_block_size   512
physical_block_size  512
max_sectors_kb       1280
write_cache          write back
```

`scheduler=[none]` 说明这是 blk-mq 单队列直通（虚拟盘由宿主调度，内核不该再重排）；`write_cache=write back` 说明**盘上有写缓存**——这就是 `fsync` 必须额外发 FLUSH 的原因（`base/29`）。

### E3 · `df -T` 与内核回写阈值（真实输出）

```console
$ df -T
Filesystem     Type     1K-blocks    Used Available Use% Mounted on
/dev/vda1      ext4      20605384 8398740  11333048  43% /
$ cat /proc/sys/vm/dirty_ratio /proc/sys/vm/dirty_background_ratio
20
10
```

43% 的占用率意味着 `u ≈ 0.43`，对 SSD 属于舒服区间（WA ≈ 1.75×）——**容量水位本身就是寿命参数**。

### E4 · `dd`：顺序 vs 每次同步（真实输出）

```console
$ dd if=/dev/zero of=/tmp/dd1.bin bs=1M count=256 conv=fsync
268435456 bytes (268 MB, 256 MiB) copied, 0.226 s, 1.2 GB/s     # 顺序 + 末尾一次 fsync
$ dd if=/dev/zero of=/tmp/dd2.bin bs=1M count=256 oflag=direct
268435456 bytes (268 MB, 256 MiB) copied, 0.1568 s, 1.7 GB/s    # 绕页缓存顺序写
$ dd if=/dev/zero of=/tmp/dd3.bin bs=4k count=2000 oflag=direct
8192000 bytes (8.2 MB, 7.8 MiB) copied, 0.1452 s, 56.4 MB/s    # 4K 但不等落盘
$ dd if=/dev/zero of=/tmp/dd4.bin bs=4k count=2000 oflag=dsync
8192000 bytes (8.2 MB, 7.8 MiB) copied, 0.6199 s, 13.2 MB/s    # 4K 且每次等落盘
```

第四行是关键：**每次同步的 4 KB 写只能做 13.2 MB/s ÷ 4 KB = 3,200 次/秒**，即 0.31 ms/次。顺序写的 1.2–1.7 GB/s 与它相差 **90–130 倍**——不是因为"随机"，而是因为每次都要等器件确认。

### E5 · 4 KB 顺序写 vs 随机写（自写微基准，附代码与真实输出）

```c
#define _GNU_SOURCE
#include <stdio.h>
#include <stdlib.h>
#include <fcntl.h>
#include <string.h>
#include <time.h>
static double now(void){struct timespec t;clock_gettime(CLOCK_MONOTONIC,&t);
    return t.tv_sec + t.tv_nsec/1e9;}
static unsigned long long s=88172645463325252ULL;
static unsigned long long xr(void){s^=s<<13;s^=s>>7;s^=s<<17;return s;}
int main(int argc,char**argv){
    int rand_=atoi(argv[1]); long long n=atol(argv[2]), span=atol(argv[3]);
    void*buf; posix_memalign(&buf,4096,4096); memset(buf,0x5a,4096);
    int fd=open(argv[4],O_RDWR|O_CREAT|O_DIRECT,0644); ftruncate(fd,span*4096);
    double t0=now();
    for(long long i=0;i<n;i++){
        long long off=(rand_? (long long)(xr()%span) : i)*4096;
        if(pwrite(fd,buf,4096,off)!=4096){perror("pwrite");return 1;}
        fsync(fd);                       /* 模拟"每次 commit 都落盘" */
    }
    double t1=now();
    printf("mode=%s n=%lld  4K+fsync: %.3fs  => %.0f op/s, %.3f ms/op\n",
           rand_?"rand":"seq", n, t1-t0, n/(t1-t0), (t1-t0)*1000/n);
    close(fd); free(buf); return 0;
}
```

```console
$ gcc -O2 -o devtest2 devtest2.c
$ ./devtest2 0 600 4096 /tmp/t.bin     # 顺序
mode=seq  n=600  4K+fsync: 0.127s  => 4732 op/s, 0.211 ms/op
$ ./devtest2 1 600 4096 /tmp/t.bin     # 64 MB 范围内随机
mode=rand n=600  4K+fsync: 0.116s  => 5185 op/s, 0.193 ms/op
```

**诚实的结论**：在这台机器上，4 KB 随机与 4 KB 顺序**没有差别**（0.193 vs 0.211 ms/次）。原因是它的后端是闪存 + 宿主页缓存，随机 4 KB 落在不同 die/不同 SSD page 上，器件内部有足够并行度吸收掉"不连续"；而每请求 `fsync` 的 0.2 ms 把两者都压成了"同步代价"这一个数。

**这恰好证明本篇的论点**：慢的从来不是"随机"这个词，而是那件具体器件里被踩到的物理机制——HDD 的机械臂（§08.6）、NAND 的擦除块（§08.3）。同一份代码在 HDD 上会变成 `1/(4.5+4.17) ms ≈ 115 op/s`，即 **0.193 ms → 8.7 ms，差 45 倍**；在 92% 满的 QLC 上会因为 WA 13 而掉到几十 op/s。

### E6 · 跑不了的三个数（估算，标明推导）

| 量 | 估算值 | 推导 | 性质 |
| --- | --- | --- | --- |
| HDD 随机 4K IOPS | 78–122 | `1/(4.5 ms + 4.17 ms + 0.02 ms)` | 量级结论（§08.6 表格） |
| 单线程同步 commit 上限（HDD） | 115 次/秒 | 同上，每次 commit 一次定位 | 推算 + 本机 SSD 实测 4,732 次/秒 同构验证 |

三条都不是实测，因为这台机器上没有机械盘、没有 QLC 盘、也没有 `fio`；给出推导路径是为了让你在**自己的**机器上用同一组命令复现。

## 08.11 一页速记

```
一条主线：器件的"最小操作单位"决定了系统的所有设计。
  DRAM  最小改写单位 = 1 bit（无磨损）→ 但必须 64 ms 刷一遍 → 4.5% 带宽税
  NAND  写单位 = 页 4–16 KB，擦单位 = 块 4–16 MB → 不能原地更新 → FTL + GC → 写放大 1/(1-u)
  HDD   定位单位 = 4 KB 扇区，但一次定位 = 4.5 ms 寻道 + 4.17 ms 旋转 → IOPS 封顶 1/(寻道+旋转)

五个必背数字（都能现场推）：
  DDR4-3200 双通道  = 8 B × 3200 MT/s × 2 = 51.2 GB/s
  刷新带宽税        = 8192 × 350 ns / 64 ms = 4.5%
  QLC 写放大        = 1/(1-0.92) ≈ 12.5×，加部分页 ≈ 13×
  HDD 随机 IOPS     = 1/(0.0045+0.00417) ≈ 115
  Little 定律       = IOPS = 队列深度 / 延迟（加并发只买并行度，不买单请求延迟）

三条推论（评审时直接说）：
  ① 顺序写快不是玄学：NAND 的 u→0、HDD 只付传输、DRAM 行命中。
  ② 日志结构（WAL/LFS/LSM/COW）不是潮流，是擦除块的翻译。
  ③ 寿命要按器件侧算：TBW ÷ (主机写量 × WA)，不要按"每天多少 GB"算。
```

### 自检 3 题

**Q1.** 一块 3,200 MT/s 的 DDR4 双通道内存，标称 51.2 GB/s，为什么实测 `STREAM` 只有 32–38 GB/s？请给出至少两条与**器件**有关的解释，并估算刷新这一项的贡献。

<details><summary>答案</summary>

① **刷新税**：每 64 ms 要刷完 8192 行，`8192 × tRFC(350 ns) = 2.87 ms`，占 **4.5%**（更大 die 的 all-bank 刷新 8–9%），这部分时间与负载无关。

② **行未命中**：真实访问不是纯顺序。每次跨行要付 `tRP + tRCD ≈ 27.5 ns`；`STREAM` 的多路流并发遍历，在 bank 数与行缓冲数之间来回冲突，行命中率达不到 100%。基准报告值通常当行命中率 85–95% 时，有效带宽就落到峰值的 65–75%。

③ **其他**：双通道只有 2 个 64-bit 子通道，`CAS` 命令的周转与 bank group 冲突（tFAW/tRRD）会额外占时间；ECC 开启还要多传 12.5% 位（72 bit/64 bit）。所以 51.2 GB/s 是**承诺值**，32–38 GB/s 是**可交付值**。

</details>

**Q2.** 一块 2 TB QLC 盘，页 16 KB、块 4 MB、TBW 1,100 TB。业务每天做 375 GB 的 4 KB 随机写，盘内有效数据 92%。请算出写放大、器件写量、寿命，并解释为什么 `smartctl` 显示 3 个月用掉 40%。

<details><summary>答案</summary>

- GC 写放大：`1/(1−0.92) = 12.5×`；4 KB 写进 16 KB 页若不能合并，再加 `16/4 = 4×` 的部分页放大；元数据约 1.1×。事故二的实测合成值是 **13×**（说明该负载基本能靠 SLC 缓存合并，部分页项≈1，只多付了 12.5 × 1.05 左右）。
- 器件写量：`375 GB × 13 = 4.88 TB/天`。
- 寿命：`1,100 TB ÷ 4.88 TB/天 ≈ 226 天 ≈ 7.4 个月`。
- 90 天消耗：`4.88 × 90 = 439 TB` = **39.9% of TBW**，与 `Percentage Used = 40%` 一致。
- 反推公式（现场可用）：`WA = (Percentage_Used × TBW) / (Data_Units_Written × 512 KB)`。
- 关键认知：主机侧 DWPD 只有 `375/2000 = 0.19`，看起来"只用了 0.3 DWPD 额度的 63%"，但器件侧 `4.88/2000 = 2.44 DWPD`，**超标 8 倍**。寿命只能按器件侧算。

</details>

**Q3.** 一块 7200 rpm 的 HDD，一次 4 KB 随机读为什么是 8–13 ms 而不是"100 MB/s 除以 4 KB"？如果把这批 4 KB 请求改成 32 个线程并发，为什么 IOPS 只从 90 涨到 150–200，而延迟涨到 60–170 ms？

<details><summary>答案</summary>

① **传输时间不是瓶颈**：`4 KB ÷ 200 MB/s = 0.02 ms`，真正的时间花在**定位**——平均寻道 4.5 ms + 旋转半圈 4.17 ms ≈ 8.7 ms，控制器与排队再加 0.05–0.2 ms。所以随机 4K 的有效带宽只有 `115 × 4 KB ≈ 0.47 MB/s`，与 200 MB/s 差约 400 倍。

② **并发买不到机械动作**：所有盘面共用一根臂，同一时刻只有一个磁头在工作，器件内部并行度 = 1。加并发只是把请求排进 32 条目的 NCQ 队列，队列调度能做的是**重排**（把物理位置相邻的请求合并、把本来就要经过的磁道顺便读掉），于是 IOPS 从 90 涨到 150–200（这是重排的收益，不是并行），但每个请求的完成时间变成了"等待 + 服务"，按 Little 定律 `L = λW`：`180 IOPS × 0.42 s ≈ 76` 个请求同时在飞——延迟涨 30–50 倍，吞吐几乎没动。

③ 正确修法：把随机变顺序（批量、按主键区间扫）、把热数据放页缓存/闪存、或者换介质；**不要加线程**。

</details>
