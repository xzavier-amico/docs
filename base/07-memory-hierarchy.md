## 07.1 引子：同样的 400 万条记录，同样的 64 MB，差 100 倍

先给出这台机器的档案，后面所有数字都长在它上面：

| 项 | 实测值 | 来源命令 |
| --- | --- | --- |
| CPU | AMD EPYC 7K62（QEMU/KVM 虚拟机，2 vCPU，1 socket） | `lscpu` |
| 有效主频 | **3.22 GHz**（1 周期依赖加法 0.310 ns 反推，见 §07.2 注） | 自写基准 |
| TSC 频率 | 2.60 GHz（`__rdtsc` 与 `clock_gettime` 对拍） | 自写基准 |
| 内存 | 1.9 GiB，**1 个 NUMA 节点** | `free -h`、`/sys/devices/system/node/online` |
| L1d | 64 KiB / 核，2 路，**64 B 行** | `index0/{level,size,coherency_line_size}` |
| L2 | 512 KiB / 核，16 路 | `index2/…` |
| L3 | 16 MiB（本机 2 个实例共享），16 路 | `index3/…`、`lscpu` |
| 内核 | 6.12.113，THP 为 `[always]` | `uname -r`、`transparent_hugepage/enabled` |
| 缺什么 | **没有 `perf`，没有 `numactl`**（下面会给出替代方案） | `which perf numactl` |

现在两段代码。它们做的是**完全相同**的事：遍历 400 万条 16 字节记录，把其中的 `v` 加起来。数据量都是 64 MB，元素个数都是 4M，连结构体大小都一样。

```c
#include <stdio.h>
#include <stdlib.h>
#include <time.h>
#include <x86intrin.h>
typedef struct Node { long v; struct Node *next; } Node;   /* 16 B */
typedef struct Rec  { long v; long pad; } Rec;             /* 16 B，只为对齐大小 */
static volatile long sink;
#define N (4L<<20)                        /* 4M × 16B = 64 MB */
int main(void){
    Rec  *arr  = aligned_alloc(64, (size_t)N*sizeof(Rec));
    Node *pool = malloc((size_t)N*sizeof(Node));
    int  *perm = malloc((size_t)N*4);
    for (long i=0;i<N;i++){ arr[i].v=i; pool[i].v=i; perm[i]=(int)i; }
    srand(42);
    for (long i=N-1;i>0;i--){                 /* 洗牌：把节点打散到整个 64 MB */
        long j=rand()%(i+1); int t=perm[i]; perm[i]=perm[j]; perm[j]=t; }
    for (long i=0;i<N-1;i++) pool[perm[i]].next=&pool[perm[i+1]];
    pool[perm[N-1]].next=NULL;
    long s=0; struct timespec t0,t1;
    clock_gettime(CLOCK_MONOTONIC,&t0);
    for (long i=0;i<N;i++) s+=arr[i].v;                       /* A：连续 */
    clock_gettime(CLOCK_MONOTONIC,&t1);
    printf("A 数组    %8.2f ms\n",(t1.tv_sec-t0.tv_sec)*1e3+(t1.tv_nsec-t0.tv_nsec)/1e6);
    clock_gettime(CLOCK_MONOTONIC,&t0);
    for (Node*p=&pool[perm[0]];p;p=p->next) s+=p->v;          /* B：指针追逐 */
    clock_gettime(CLOCK_MONOTONIC,&t1);
    printf("B 链表    %8.2f ms\n",(t1.tv_sec-t0.tv_sec)*1e3+(t1.tv_nsec-t0.tv_nsec)/1e6);
    sink=s; return 0;
}
```

`gcc -O2` 之后 `taskset -c 0` 绑定到固定核，连跑三次：

```
A 结构体数组 64MB 顺序          4.15 ms    2.57 cyc/条    16.2 GB/s
B 链表     64MB 随机指针      413.64 ms  255.93 cyc/条    0.16 GB/s
同样 64 MB、同样 4M 条 16 B 记录，只换访问顺序：B/A = 99.6x

A 结构体数组 64MB 顺序          4.08 ms    2.52 cyc/条    16.5 GB/s
B 链表     64MB 随机指针      408.78 ms  252.92 cyc/条    0.16 GB/s
同样 64 MB、同样 4M 条 16 B 记录，只换访问顺序：B/A = 100.3x
```

**100 倍。** 没有编译器差异（同一个 `-O2`），没有算法差异（都是线性求和），没有数据差异（和都相同）。唯一的差别是**下一条记录在不在上一条记录旁边**。

再补一刀：把「数组」换成一个很朴素的 4096×4096 二维整型矩阵（也是 64 MB），只交换两层循环的次序：

```
行优先  i 外 j 内     4.8 ms   0.28 ns/元素   14.1 GB/s
列优先  j 外 i 内   336.1 ms  20.03 ns/元素    0.20 GB/s
比值 70.6x   （三次运行 70–82x）
```

同样是 1600 万次加法，一次 4.8 ms，一次 336 ms。**代码的「好看程度」在这里一点用都没有；决定速度的是数据落在第几层、以及相邻两次访问在物理地址上隔多远。** 这就是本篇的全部命题，剩下十三节只是把它拆成可推导的账。

## 07.2 层次金字塔：容量、延迟、带宽，每一格都能算出来

### 为什么必然分层

存储单元的单价随「快」指数上升：一个 SRAM 位要 6 个晶体管，一个 DRAM 位只要 1 个晶体管加 1 个电容，一个 NAND 位只要不到 1 个（多层堆叠、共享字线），而磁盘的一位是一小片磁畴。于是**每 bit 价格差 10³–10⁶ 倍，容量也就差 10³–10⁶ 倍**。CPU 想要「大且快」，硬件只能给「小的快、大的慢」，中间用「猜你下次要什么」把它们粘起来。金字塔不是设计品味，是价格表的直接投影。

```
        容量小、快、贵                              容量大、慢、便宜
   ┌──────┐  ~128 B/线程   0.3 ns   每 bit 最贵（16 个寄存器 × 8 B）
   │ 寄存器│
   ├──────┤  64 KiB/核     1.5 ns
   │  L1  │  ← 64 B 一次搬完
   ├──────┤  512 KiB/核    3–4 ns
   │  L2  │
   ├──────┤  16 MiB/CCX    12 ns
   │  L3  │  ← 多核共享，一致性协议在这里（→ base/13）
   ├──────┤  1.9 GiB      93 ns   ← 本文所有「慢」的基准
   │ DRAM │
   ├──────┤  TB 级       28 µs（4 KB 随机）
   │ NVMe │
   ├──────┤  TB 级       10 ms（寻道）
   │ HDD  │
   └──────┘  全球          0.8 ms – 200 ms（RTT）
```

### 三列表：本机实测（每格给推导式）

| 层 | 容量（本机） | 延迟（实测） | 带宽（实测） | 推导式 / 出处 |
| --- | --- | --- | --- | --- |
| 寄存器 | 16 GPR × 8 B = 128 B/线程 | 1 周期 ≈ 0.31 ns | 受发射宽度限：4 条/周期 | 重命名后读延迟为 0，记账时按 1 周期算 |
| L1d | 64 KiB/核 | **1.52 ns ≈ 4.9 周期** | **91 GB/s ≈ 28 B/周期** | 指针追逐（工作集 ≤ 32 KB）测得；带宽 = 2 个 16 B load/周期 × 3.2 GHz = 102 GB/s 上界 |
| L2 | 512 KiB/核 | **3.9 ns ≈ 12.5 周期** | **65–100 GB/s** | 工作集 256 KB 的追逐测得；带宽受 L1↔L2 通路 32 B/周期约束 |
| L3 | 16 MiB | **12 ns ≈ 38 周期** | **52–70 GB/s** | 工作集 8 MB 测得；L3 是 victim/共享，带宽随核数分摊 |
| DRAM | 1.9 GiB | **93 ns ≈ 300 周期** | **18.4 GB/s（12–19 波动）** | 工作集 64 MB 的随机追逐测得；带宽由 §07.8 的 Little 定律核对 |
| NVMe（本机是 virtio-blk） | 20 GB 盘 | **27.9 µs**（4 KB 随机） | 219 MB/s 顺序、36 kIOPS 随机 | `O_DIRECT` + `pread(4096)` 实测，含 VM 出口开销 |
| 网络（同城） | 全球 | **0.83 ms** RTT | — | `ping 1.1.1.1` 实测（往返） |
| 网络（本机回环） | — | **8.2 µs** RTT | — | 1 字节 echo，`socketpair` 全路径 |
| HDD | 无此设备 | **约 10 ms**（推导） | 约 200 MB/s | 7200 rpm：旋转 8.3 ms + 平均寻道 4–10 ms |

三个必须自己动手算一遍的推导：

**① 周期换算。** 主频不能信 `lscpu`（虚拟机报 2.0 GHz，`cpu MHz` 报 2595，都不对）。用一条已知 1 周期的依赖链（`a = a + 1` 且加编译屏障防止向量化/展开）计时：

```
1-cycle 依赖 add: 0.3104 ns -> 有效主频 3.22 GHz
```

于是「周期 → 纳秒」只有一个系数：`ns = 周期 ÷ 3.2`。L1 的 4.9 周期、DRAM 的 300 周期都是这么来的。**任何「某某操作要 N 个周期」的说法，不给主频就是没给数字。**

**② 带宽的位宽算式。** 一条 DDR4-3200 通道的理论峰值 = `8 B（64 位位宽）× 3.2 GT/s × 2（DDR 双沿）= 51.2 GB/s`；EPYC 7K62 是 8 通道，整机 409.6 GB/s。但本机只有 2 个 vCPU，实测 18.4 GB/s——**差 22 倍不是内存不行，是「只有 2 个核在发请求」**，这个缺口由 §07.8 的 Little 定律解释。

**③ 容量的位宽算式。** L1 的 64 KiB = `64 B/行 × 64 组 × 2 路 × 8 行？` 不必背；只需知道 `64 KiB ÷ 64 B = 1024 行`，而 `2 路 × 512 组 = 1024`，所以它是 512 组 2 路组相联。**容量 / 行大小 = 行数**，这条换算在算「多少行能被同时装下」时天天用（→ `base/13`）。

> **量级结论（不是承诺值）**：从 L1 到 DRAM，延迟涨 **60 倍**（1.5 → 93 ns），容量涨 **3 万倍**（64 KiB → 1.9 GiB）。这两条比例决定了后面所有优化：**让命中率提高 1% 的价值，远大于让循环体少一条指令。**

## 07.3 纳秒换算表：如果 L1 命中是 1 秒

纳秒对人类没有直觉。把 **L1 命中 = 1 秒** 当作基准，按同一比例放大（比例 = 1 ÷ 1.5 ns ≈ 6.7×10⁸）：

| 事件 | 真实延迟 | 放大后 | 换成人类尺度 |
| --- | --- | --- | --- |
| 寄存器访问 | 0.31 ns | 0.2 s | 眨一下眼 |
| **L1 命中** | 1.5 ns | **1 s** | **基准：说一句话** |
| L2 命中 | 3.9 ns | 2.6 s | 系个鞋带 |
| L3 命中 | 12 ns | 8 s | 泡一杯茶 |
| **DRAM 命中** | 93 ns | **62 s** | **等一分钟，什么也干不了** |
| NVMe 4 KB 随机读 | 27.9 µs | 5.2 小时 | 一个工作日的一半 |
| `write`+`fsync` 一次 | 50.7 µs | 9.4 小时 | 一天 |
| 跨机房 RTT（约 30 ms） | 30 ms | 232 天 | 大半年 |
| HDD 寻道 | 10 ms | 77 天 | 两个半月 |
| 跨洲 RTT（约 150 ms） | 150 ms | 3.2 年 | 读一次本科 |

这张表要建立的直觉只有一句：**如果 L1 是「说一句话」，那 DRAM 就是「等一分钟」，SSD 就是「等半天」，机械盘就是「等下个季度」。** 一个每 8 个元素就要等一分钟的循环，和一个每 8 个元素只需说一句话的循环，差 100 倍——这正是 §07.1 量到的 99.6×。

再换一个方向看同一张表：**CPU 在等 DRAM 的那 300 个周期里，能算 1200 条指令**（3.2 GHz × 4 发射 × 93 ns）。也就是说，一次 cache miss 的「机会成本」是一千多条本来可以做完的指令。这就是为什么「少一次 miss」比「少一条指令」值钱三个数量级。

> 注意表里 NVMe 那一行：**27.9 µs 是本机virtio-blk 的实测，含虚拟化出口**。真实裸机 NVMe 的 4 KB 随机读在 20 µs 上下同一量级；而 §07.10 的 `fsync` 50.7 µs 是「写+刷」的整条链路，两者不要混用（→ `base/08`、`base/29`）。

## 07.4 cache line：64 字节是这一层的「原子单位」

### 一次 miss 搬多少

CPU 与内存之间**没有「读 4 个字节」这个动作**。缓存的最小装载单位是**行（line）**，本机 `coherency_line_size = 64`。你只要读一个 `int`，硬件就把包含它的**整 64 字节**搬进 L1；行再细分为 4 个 16 B 的 **sector**，AMD 可以只取需要的 sector，但 L1↔L2 的记账、一致性协议的记账、预取器的记账，全部以行为单位。

这直接给出两个结论：

1. **读 1 字节和读 64 字节一样贵。** 带宽按行计费，不按你用了多少计费。
2. **一行里塞进来的东西越多，这次 miss 越值。** 顺序访问能把 64 B 全部用上；随机访问每次只用 4 B，剩下的 60 B 是纯浪费。

实测这个「浪费率」（256 MB 顺序扫，每行只取前 u 个字节）：

| 每行有用字节 | 触及带宽 | 有用带宽 | 放大倍数 |
| --- | --- | --- | --- |
| 1 | 17.6 GB/s | 0.27 GB/s | **64×** |
| 4 | 14.7 GB/s | 0.92 GB/s | 16× |
| 8 | 12.8 GB/s | 1.60 GB/s | 8× |
| 16 | 10.0 GB/s | 2.50 GB/s | 4× |
| 32 | 5.3 GB/s | 2.65 GB/s | 2× |
| 64 | 2.3 GB/s | 2.27 GB/s | 1× |

最后一行「触及带宽」掉到 2.3 GB/s 不是变慢了，而是**这段循环每次迭代要加 64 个数**，加法成了瓶颈——所以这张表只读前五行：**每行只用 1 字节，等于把 18 GB/s 的 DRAM 用成 0.27 GB/s。** 这就是「结构体数组 vs 数组结构体」之争的全部物理内容（→ `go/14`）。

### TLB 与页表：行之上还有一层「地址翻译」

行只管 64 B，页管 4 KiB（本机默认），而**每次访存都要先把虚拟地址翻译成物理地址**。翻译结果缓存在 TLB 里：L1 dTLB 约 64 项、L2 TLB 约 2048 项（Zen 2 量级）。算一下覆盖面：

- 4 KiB 页 × 2048 项 = **8 MiB** —— 也就是说，工作集一旦超过 8 MiB，TLB 就开始漏。
- 2 MiB 大页 × 2048 项 = **4 GiB** —— 这就是大页存在的唯一理由。

漏了之后要**走四级页表**（x86-64：PGD → PUD → PMD → PTE），每一级都是一次内存读；最坏情况 4 次 DRAM 访问，约 `4 × 93 ns ≈ 372 ns`，而这次访问本身才 93 ns。**一次 TLB miss 能把一次访存放大 4 倍**（细节与缺页处理 → `base/26`）。

实测（256 MB 区域，按页打乱顺序，每页只碰 1 字节，65,536 次访问）：

```
4KB      页数=65536 AnonHuge=     0 kB    12.24 ns/页
THP      页数=65536 AnonHuge=262144 kB     8.88 ns/页
4KB      页数=65536 AnonHuge=     0 kB    12.77 ns/页
THP      页数=65536 AnonHuge=262144 kB     9.07 ns/页
```

`madvise(MADV_HUGEPAGE)` 后 `AnonHugePages` 从 0 变成 262144 kB（整块 2 MB 大页），每页成本从 **12.5 ns 降到 8.9 ns**，省 29%。推算一下这个 3.5 ns 对不对：

```
65536 页 / 2048 项 TLB = 32 次里有 1 次要走页表
一次 walk 的额外成本 ≈ 3 次 DRAM 读（PGD/PUD/PMD 命中率不同，取 100 ns 量级）
1/32 × 100 ns ≈ 3.1 ns        ← 与实测 3.5 ns 同量级
```

**这个算式只用来判断「是不是 TLB 在拖」，不用来预测精确值**——walk 之间可以并发，所以实测往往小于上式。

### 代码：让大页真正生效

```c
#define _GNU_SOURCE
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <sys/mman.h>
#define SZ (256u<<20)
int main(void){
    char *b = mmap(NULL, SZ, PROT_READ|PROT_WRITE,
                   MAP_PRIVATE|MAP_ANONYMOUS, -1, 0);
    madvise(b, SZ, MADV_HUGEPAGE);      /* 或 MADV_NOHUGEPAGE 做对照 */
    memset(b, 1, SZ);                   /* 必须先写一遍，THP 才在缺页时合并 */
    /* 之后按 4096 的随机顺序访问，量「每页一次」的成本 */
    /* 验证是否真的用了大页：读 /proc/self/smaps 的 AnonHugePages */
    return b[0];
}
```

三个坑要记住：`madvise` 只是**建议**（本机 `THP=always` 才生效）；必须在**首次写**之前调用，页已经映射成 4 KB 就晚了；**先 `memset` 再测**，否则你量的是缺页而不是 TLB。

## 07.5 空间局部性实测：连续、步长、与链表的三种死法

### ① 二维数组：同一份数据，两种次序

```c
#define M 4096                       /* 4096×4096×4B = 64 MB */
int *m = malloc((size_t)M*M*4);
for (int i=0;i<M;i++) for (int j=0;j<M;j++) s += m[(size_t)i*M+j];   /* 行优先 */
for (int j=0;j<M;j++) for (int i=0;i<M;i++) s += m[(size_t)i*M+j];   /* 列优先 */
```

```
行优先  i 外 j 内     4.8 ms   0.28 ns/元素   14.1 GB/s
列优先  j 外 i 内   336.1 ms  20.03 ns/元素    0.20 GB/s
```

为什么是 70 倍而不是 64 倍？列优先时，内层每走一步跨 **16 KiB**（一整行 4096 × 4 B），远超 64 B 行，也超过 L1 的 1024 行容量。于是**每一步都是一次新 miss**，而且这 4096 个「当前列位置」要同时活着——4096 × 64 B = 256 KiB，正好压在本机 512 KiB 的 L2 边界上。所以它既 miss L1，也几乎 miss L2，只能吃 L3/DRAM 的 12–93 ns。

> **这条实验的教学价值**：慢不在「列优先」这个写法，而在于**内层循环的步长 × 内层次数 > 缓存容量**。判断方法是算「工作集」：`步长 × 同时活跃的元素数`。本机 4096 × 64 B = 256 KiB ≈ L2 的一半，所以它落在 L2/L3 之间——这就是 20 ns 这个数字的来源，而不是乱猜。

### ② 链表 vs 数组：把「数据量」和「顺序」分开

§07.1 已经给出 99.6×。但那个实验有个漏洞：数组是 32 MB（8 B/元素），链表是 64 MB（16 B/节点），数据量不同。补一个严格对照——**两者都是 64 MB、都是 4M 条 16 B 记录**：

```
A 结构体数组 64MB 顺序          4.09 ms    2.53 cyc/条    16.4 GB/s
B 链表     64MB 随机指针      407.92 ms  252.39 cyc/条    0.16 GB/s
同样 64 MB、同样 4M 条 16 B 记录，只换访问顺序：B/A = 99.7x
```

链表慢在两处，可分开计账：

| 损失 | 物理原因 | 实测证据 |
| --- | --- | --- |
| 指针追逐串行化 | 下个地址要等这次 load 回来，MLP = 1（无并发） | 每节点 **252 周期 ≈ 79 ns**，接近单次 DRAM 延迟 93 ns |
| 行内浪费 | 16 B 节点只用了 1/4 行 | 每节点 1.0 次 L1 miss（见 §07.12 的 PMU 数据） |
| 预取失效 | 地址不可预测，硬件预取器只能瞎猜 | 随机链表的预取「猜中率」≈ 0 |

**第一行是最致命的**：数组的 8 次独立 load 可以同时在飞（MLP ≈ 8–12），链表的下一次 load 必须等上一次**完成**（MLP = 1）。同样的 93 ns，数组摊到 8 个元素上是 12 ns/元素，链表就是 93 ns/元素——**8 倍差距纯由「能不能并发」产生**，与带宽无关。

### ③ stride 扫描：步长跨过一条行就开始付钱

64 MB 区域，固定总访问次数 200 万，逐步放大步长：

| 步长 | 每次 ns | 折算周期 | 处在哪一层 / 发生了什么 |
| --- | --- | --- | --- |
| 4 B | 1.36 | 3.5 | L1；一行 16 个 int，全用上 |
| 8 B | 1.38 | 3.6 | L1；一行 8 个 long |
| 16 B | 1.45 | 3.8 | L1；一行 4 个 |
| 32 B | 2.16 | 5.6 | L1 边界：一行只用一半 |
| 64 B | 3.46 | 9.0 | **正好一行一次**：每行只用 1 个元素 |
| 128 B | 3.70 | 9.6 | 一行 64 B，每步跨 2 行 |
| 256 B | 4.67 | 12.1 | 4 行取 1 行 → 触及 4 倍数据 |
| 1 KiB | 4.53 | 11.8 | 16 行取 1 行 |
| 2 KiB | 6.84 | 17.8 | 32 行取 1 行 |
| 4 KiB | 7.69 | 20.0 | **跨页**：每次一个新页 → TLB 开始参与 |
| 8 KiB | 7.87 | 20.5 | L1 装不下 8192 个活跃行 |
| 16 KiB | 7.38 | 19.2 | 触及数据 512 MB，L2 已溢出 |
| 32 KiB | 18.97 | 49.3 | 触及数据 2 GB，L3 也装不下 |
| 64 KiB | 51.15 | 133.0 | 触及 4 GB，DRAM + TLB |
| 2 MiB | 59.30 | 154.2 | 每次都是新大页 |
| 8 MiB | **1.35** | **3.5** | **陷阱：64 MB ÷ 8 MB = 8 个地址，反复命中同一行** |

> 上表是**一次完整运行**的原始输出（`taskset -c 0 ./e3`）。本机是共享虚拟机，16 B/32 B 两行在两次运行间会互换（1.45 ↔ 2.50），因为这两个步长正好压在「一行 4 个元素 / 一行 2 个元素」的边界上；**结论看台阶位置，不看单点小数**。

最后一行必须单独讲：**大步长不等于慢**，因为总数据量固定时，步长越大**访问次数越少、足迹越大**；当步长接近整个缓冲区，活跃地址只剩 8 个，全部待在 L1 里，于是又快回来了。任何 stride 基准，如果不控制「N 次独立访问」，都会量出这条假谷底。

**三条实测合起来只说明一句：价格的台阶不在「算法复杂度」上，而在「步长跨过 64 B、跨过 4 KiB、跨过 16 MiB」这三个边界上。**

## 07.6 时间局部性：工作集跨过 LLC 就突然变慢

空间局部性问「相邻两次访问隔多远」，时间局部性问「同一批数据要重复用多久」。把「工作集大小」当自变量，重复扫描到总字节数固定（256 MB），量吞吐：

| 工作集 | 重复次数 | 吞吐 GB/s | 在哪一层 |
| --- | --- | --- | --- |
| 1 KB | 100000 | 96.2 | L1 |
| 4 KB | 65536 | 101.3 | L1 |
| 32 KB | 8192 | 93.5 | L1 上限 |
| 256 KB | 1024 | 101.5 | L2 |
| 1 MB | 256 | 31.5 | L2 溢出（本机 L2 512 KB） |
| 2 MB | 128 | 58.1 | L3 |
| 8 MB | 32 | 32.0 | L3 上限 |
| **16 MB** | 16 | **11.1** | **L3 = 16 MiB，正好跨线** |
| 32 MB | 8 | 8.6 | DRAM |
| 256 MB | 1 | 8.3 | DRAM（含缺页/TLB） |

三个台阶清清楚楚：**L1/L2 内 93–101 GB/s，跨过 L2 掉到 31–58，跨过 L3（16 MiB）掉到 8.3–11.1**。最陡的一段是 8 MB → 16 MB：32.0 → 11.1，**2.9 倍**；整条曲线从 101 到 8.3，**12 倍**。

> 本机是共享虚拟机，吞吐列抖动可达 ±30%（同一份代码不同次运行会在 8.6–18.4 之间跳）。**结论只用来看台阶位置，不要引用绝对值**。台阶位置是物理的（L2 512 KiB、L3 16 MiB 都由 `sysfs` 直接给出），所以它可复现。

**这条曲线的工程含义**：优化一个「每次请求都扫一遍大表」的服务时，把表从 20 MB 压到 12 MB（比如换更紧凑的编码、砍掉冗余字段），吞吐可能直接翻倍——**不是因为代码变好，而是因为工作集从 DRAM 挪回了 L3**。反过来，把一个 8 MB 的表扩到 20 MB 做「功能增强」，可能是整套系统最贵的一次「加个小功能」（→ `base/20` 的 tiling、`comp/` 各组件缓存）。

### 为什么是「台阶」而不是「斜坡」

因为容量是硬边界：装得下就每次命中，装不下就每一次都 miss，中间没有「半命中」。真实的曲线会被三件事抹圆——预取器提前把下一行拿来、LRU 近似算法（CLOCK）的抖动、以及「重复扫描」本身对预取极其友好。所以你会看到 1 MB 处反而比 2 MB 慢（31.5 vs 58.1）这种反直觉点：那是 L2 刚好装不下、L3 又太远，预取器跟不上的「过渡带」。**看到非单调，先怀疑预取与测量方法，再怀疑硬件。**

## 07.7 预取器：硬件猜顺序，软件只能帮一点

CPU 里有专门的预取单元，规则朴素到可以背：**看到连续 2–3 个行被访问，就假设你会继续往下走，提前把后面几行拉进来**。它对顺序扫描近乎免费（§07.6 的 96–101 GB/s 里有一半是它的功劳），对随机访问几乎无效。

`__builtin_prefetch(addr, rw, locality)` 是软件给的那一点点帮助。实测（192 MB 区域，1600 万次随机行访问，提前 D 次迭代预取）：

| 预取距离 | ns/访问 | 相对基线 |
| --- | --- | --- |
| 无 | 26.48 | 1.00× |
| +4 | 25.96 | **1.02×**（无效） |
| +8 | 22.28 | 1.19× |
| +16 | 20.04 | 1.32× |
| +32 | 19.77 | **1.34×** |
| +64 | 19.84 | 1.33× |
| +128 | 20.32 | 1.30× |

三个必须记住的数字关系：

1. **太近无效。** 预取指令发出后，数据要 93 ns 才到；+4 个迭代在编译器展开后只隔几十个周期，等于没提前。经验值：**预取距离 ≈ 延迟 ÷ 每次迭代周期数**，本机 93 ns ÷ 3.5 周期/次 ≈ 85 次，所以 +32～+64 是平台区。
2. **收益有上限，且只有 1.3×。** 因为随机访问的瓶颈是**地址依赖**（MLP=1），预取只是把「等」提前了，不能让多个 miss 真正并行。真正的并发要靠**软件流水/多路独立链**，不是靠 prefetch。
3. **太远有害。** +128 开始回落：预取的数据在到达前被别的流量挤出 L1/L2，白耗带宽。更糟的是 `prefetch` 对一个**未映射地址**不会出错（它被设计成安全），但会白白触发一次页表 walk。

```c
for (long i = 0; i < n; i++) {
    if (i + 32 < n) __builtin_prefetch(&a[idx[i + 32]], 0, 1);  /* rw=0 读, locality=1 到 L2 */
    s += a[idx[i]];
}
```

**什么时候不要用**：① 顺序访问（硬件已经做了，加了是噪声）；② 链表/树（下个地址要等这次 load，预取不出来）；③ 数据量小于 L3（本来就命中，预取纯耗指令）。**能用布局解决的，不要用预取解决**——把链表换成数组，收益是 100×；把预取调到最优，收益是 1.34×。

## 07.8 内存墙：每纳秒能算几条指令，DRAM 每纳秒给几个字节

### 两个数字，一个比值

- **算力**：3.2 GHz × 4 发射 = **12.8 G 指令/s = 12.8 条/ns**（这是上界；本机实测数组扫描的 IPC 是 1.75，即 5.6 条/ns）。
- **喂数**：DRAM 实测 **18.4 GB/s = 18.4 字节/ns**。

比值：`18.4 ÷ 12.8 = 1.44 字节/指令`（按理论上界算）。如果每条指令平均要吃 8 字节新数据（一个 `long`），缺口是 **5.5 倍**；按实测 IPC 算，缺口 **14 倍**。

这就是**内存墙**：算力按 4 发射/周期增长，DRAM 带宽几十年只从 3.2 GB/s 涨到几十 GB/s。墙不是一个比喻，是上面那个除法。

### Little 定律：为什么本机只有 18.4 GB/s 而不是 409 GB/s

带宽 = 并发请求数 × 每请求字节 ÷ 延迟：

```
B = MLP × 64 B / 93 ns
18.4 GB/s = MLP × 64 / 93e-9   →   MLP ≈ 27 条 cache line 同时在飞
```

反过来说：**要跑满 18.4 GB/s，必须有 27 条行同时在途**（27 × 64 B = 1.7 KiB 的「在途窗口」）。整机 8 通道 409 GB/s 则需要 `409e9 × 93e-9 / 64 ≈ 594` 条在途——那需要几十个核一起发请求。**2 个 vCPU 撑死也就 20 GB/s 上下**，这不是配置问题，是并发数不足。

这条定律直接决定了四种优化的合法性：

| 优化 | 它在改哪个变量 | 为什么有效 |
| --- | --- | --- |
| **分块（tiling）** | 延迟（把 DRAM 访问换成 L2 访问：93 → 4 ns） | 同一块数据在 L2 里被用几十次，每次省 89 ns（→ `base/20`） |
| **批处理** | MLP（一次发 N 个独立请求） | 把 MLP 从 1 提到 27，带宽从 0.7 提到 18.4 GB/s（→ `base/29`） |
| **少指针追逐** | MLP（把依赖链打断） | 链表 MLP=1，数组可到 8–12（§07.5） |
| **数据紧凑化** | 每请求字节的「有效率」 | 64 B 行里有用字节从 4 提到 32，有效带宽 ×8（§07.4） |

**四件事是同一个式子的四个变量。** 判断一个「性能优化方案」值不值得做，只需问：它改的是延迟、并发、还是每行的有效率？一个都不改的，基本是安慰剂。

## 07.9 NUMA：本地内存和远端内存差多少

本机只有 1 个 NUMA 节点，所以只能给出「结构」和「推导」，同时**明说 `numactl` 没装**（`numactl: command not found`）：

```
$ cat /sys/devices/system/node/online
0
$ cat /sys/devices/system/node/node0/distance
10
$ cat /sys/devices/system/node/node0/cpulist
0-1
$ cat /sys/devices/system/node/node0/numastat
numa_hit          668760723
numa_miss                   0
numa_foreign                0
local_node        668759774
other_node                  0
$ cat /proc/sys/kernel/numa_balancing
0
```

**`distance` 这张表怎么读**：Linux 用「10 = 本地」作基准，跨一个 hop 记 20，再远 30/40。`numa_hit / numa_miss` 是「分配时命中所属节点的次数 / 未命中的次数」，`local_node / other_node` 是「访问落在本地/远端的次数」。**`other_node` 一旦不为 0，就说明有跨节点流量**，这是排查「同配置两台机器性能差 30%」的第一条命令。

多节点机器上的量级（推导，非本机实测）：跨节点访问要经过 Infinity Fabric / UPI，延迟约为本地的 **1.4–2.2 倍**（本地 93 ns → 远端 140–200 ns），带宽约为本地的 **1/2**（链路是共享的）。代入 §07.8 的 Little 定律：MLP 不变时带宽直接减半，**一次「把线程放在 A 节点、内存分在 B 节点」的部署事故，可以让延迟敏感型服务整体掉 40%**。

### 三个工具的分工，别混用

| 工具 | 管什么 | 典型用法 | 不做什么 |
| --- | --- | --- | --- |
| `taskset -c` | **只绑 CPU**，不管内存在哪 | `taskset -c 0 ./svc` | 不改变内存分配节点 |
| `numactl --cpunodebind=N --membind=N` | 同时绑 CPU 与**内存分配**节点 | `numactl -N 0 -m 0 ./svc` | 不影响已 mmap 的共享段 |
| cgroup `cpuset.cpus` / `cpuset.mems` | 容器/进程组的**可用**集合 | 写 `cpuset.mems=0` | 不保证首次触碰时的策略（首次触碰决定） |

**关键机制**：内存落在哪个节点，由**第一次写它的那个线程当时在哪个节点**决定（first-touch）。所以「先创建线程、后 `malloc`」和「先 `malloc`、后起线程」在这件事上完全不同；`numa_balancing=1` 时内核会周期性扫描并迁移，代价是 CPU 与页表抖动——**低延迟服务通常关掉它**（像本机这样 `=0`）。调度与亲和性的完整内容 → `base/25`。

## 07.10 写路径：为什么「写」通常比「读」贵

### 写分配与 RFO

读 miss 的代价是「搬一行进来」。写 miss 的代价通常是**「先把这一行读进来，改几个字节，再写回去」**——这叫**写分配（write-allocate）**，那次多余的读叫 **RFO（Read For Ownership）**：因为一致性协议要求「要写之前必须独占这一行」。

于是写一行的真实流量有三种情况：

| 写法 | 流量 | 相对成本 | 说明 |
| --- | --- | --- | --- |
| 读一行 | 64 B（读） | 1× | 基准 |
| 改几个字节（部分写） | 64 B 读 + 64 B 写 = 128 B | **2×** | RFO：先读进来才能改 |
| 整行写（streaming store / `memcpy` 已对齐） | 64 B（写） | 1× | 硬件可省掉 RFO（写合并） |

本机实测（256 MB，每行写 8 字节 vs 整行流式写 vs 只读）：

```
普通 store（带 RFO）     19.9 ms   13.5 GB/s
非临时 store（无 RFO）   14.4 ms   18.7 GB/s
只读（每 line 1 字节）   14.7 ms   18.3 GB/s
```

**写 = 读的 1.35–1.4 倍**（19.9 ms vs 14.7 ms），而流式写几乎和读一样快。这个比例在不同机器上会在 1.0–3.0 之间浮动，**由「能不能整行写」决定**，不由 CPU 型号决定。

### 写回、写直达与 store buffer

- **写回（write-back）**：改了只在 L1 标 dirty，等这行被替换时才写回下一层。省流量，但**崩溃时数据在缓存里**——这是 `base/29` 那三层谎的第一层。
- **写直达（write-through）**：每次写都往下送。简单、可预测，但流量翻倍；x86 的 L1 是写回，某些 GPU/嵌入式核是写直达。
- **store buffer**：store 指令不等内存，先塞进 store buffer 就退休。这带来**「你写的顺序 ≠ 别人看到的顺序」**，即内存重排的物理来源（→ `base/13` 的屏障）。

工程含义只有三条：**① 能整行写就别零敲碎打**（批量、对齐、`memcpy` 大块）；**② 同一行被多个线程写 = 灾难**（伪共享，§07.12）；**③ 「写完就算落盘」是错觉**，`fsync` 一次本机 50.7 µs，比 `write` 的 0.5 µs 贵 100 倍，那 100 倍买的是「真的在介质上」（→ `base/08`）。

## 07.11 三列账：这一层承诺了什么、收了多少、从哪失效

| 维度 | 承诺了什么 | 为此付了什么 | 从哪里开始失效 |
| --- | --- | --- | --- |
| 分层存储 | 用 1.9 GiB 的价钱，给你「接近 64 KiB 的速度」 | 命中率必须 ≥ 某条线，否则每 miss 一次赔 60 倍延迟 | 工作集 > L3（16 MiB）时，命中率断崖（§07.6） |
| 64 B 行 | 一次搬运摊薄到 16 个 int / 8 个 long | 用不满一行就是纯浪费（1 字节/行 → 有效带宽 ÷64） | 随机访问、结构体膨胀、AoS 布局（§07.4、§07.5） |
| TLB | 让你以为有 1.9 GiB 连续地址空间 | 2048 项 × 4 KiB = 只覆盖 8 MiB | 工作集 > 8 MiB 且访问分散时，每次多走 3–4 级页表（§07.4） |
| 预取 | 顺序访问近乎免费地提前取数 | 判错就白耗带宽；对随机地址无效 | 指针追逐、哈希探测、稀疏图（§07.7） |
| 多级缓存一致性 | 多核看起来共享内存 | 每次跨核共享一行都要仲裁（→ `base/13`） | 伪共享：两个变量同行，吞吐掉 2–7 倍（§07.12） |
| NUMA | 给更多核更多带宽 | 远端延迟 1.4–2.2×、带宽 1/2 | 线程与首次触碰不在同一节点（§07.9） |
| 写路径 | 写和读一样简单 | RFO 让部分写变 2× 流量 | 非对齐、跨行、多线程同行写（§07.10） |

一句话收束：**这一层买到的是「用便宜介质伪装成快介质」，付出的是「必须连续、必须局部、必须可预测」三条纪律。** 违反任何一条，不会报错，只会慢——而慢的倍数在 2× 到 100× 之间。

## 07.12 踩坑清单：`perf stat` 的 cache-miss 到底怎么读

### 先说本机的特殊情况

`perf` 没装（`which perf` 为空），但**内核的 PMU 接口是开的**（`/proc/sys/kernel/perf_event_paranoid = 3` 却不影响用户态计数，`perf_event_open` 成功返回 fd）。所以下面这段 30 行的程序就是「没有 perf 时的 perf」：

```c
#define _GNU_SOURCE
#include <string.h>
#include <unistd.h>
#include <sys/ioctl.h>
#include <sys/syscall.h>
#include <linux/perf_event.h>
static int openc(unsigned type, unsigned long cfg){
    struct perf_event_attr a; memset(&a,0,sizeof a);
    a.type=type; a.size=sizeof a; a.config=cfg;
    a.disabled=1; a.exclude_kernel=1; a.exclude_hv=1;
    return (int)syscall(__NR_perf_event_open,&a,0,-1,-1,0);
}
/* 用法：openc(PERF_TYPE_HARDWARE, PERF_COUNT_HW_CACHE_MISSES)
 *       openc(PERF_TYPE_HW_CACHE,
 *             PERF_COUNT_HW_CACHE_L1D | (OP_READ<<8) | (RESULT_MISS<<16))
 * 之后 ioctl(fd, PERF_EVENT_IOC_RESET/ENABLE, 0) 包住被测代码，
 * 再 read(fd, &v, 8) 取计数。 */
```

用它包住 §07.1 的两段循环（4M 条、各 64 MB）：

```
--- array 4M x 8B = 32MB 顺序 ---
cycles               9568639
instructions        16777402
L1d loads            4196252
L1d load miss        524576
branch miss               44

--- list 4M nodes = 64MB 随机指针 ---
cycles            1375099004
instructions        33555347
L1d loads            12638731
L1d load miss         4757693
branch miss               1050
```

**怎么读这六个数**（这才是踩坑清单的核心）：

1. **`cycles ÷ instructions`** = IPC。数组 16.8M/9.57M = **1.75**；链表 33.6M/1375M = **0.024**。后者说明 CPU 99% 的时间在等，不在算。
2. **`L1d load miss ÷ L1d loads`** = 本地 miss 率。数组 524,576/4,196,252 = **12.5%**，而 `4M ÷ 8 = 524,288` —— **每个 64 B 行正好一次**，一个不差，说明顺序扫描的 miss 率下限就是 `1/每行元素数`。
3. **`miss ÷ 迭代次数`** = 每次迭代摊到几次 miss。链表 **1.13 次/节点**（>1 是因为还有取 `next` 的那次）；数组 **0.125 次/元素**。两者差 **9 倍**，而周期数差 **100 倍**——缺口正是 §07.5 说的「miss 之间不能并发」。
4. **只看 `cache-misses` 一个数毫无意义。** 它必须配 `instructions`（算 IPC）或 `cycles`（算 CPI）才有解释力；孤立地说「miss 很多」不是诊断。

### 七个高频坑

| 现象 | 根因（指回本篇） | 定位 | 怎么修 | 怎么防复发 |
| --- | --- | --- | --- | --- |
| 同一逻辑改个写法慢 10× | 数据从连续变分散（§07.5） | 量 `ns/元素`，算工作集 | 换 SoA、把指针换成索引/偏移 | 代码评审看「热路径有没有指针追逐」 |
| 二维数组某个方向特别慢 | 内层步长 × 内层次数 > 缓存（§07.5） | 算 `步长 × 活跃元素数` 对比 L2/L3 | 交换循环次序，或分块 64×64 | 矩阵类代码强制「最内层连续」 |
| 服务加了个功能后整体掉一半 | 工作集从 L3 溢出到 DRAM（§07.6） | 量 1KB→1GB 吞吐曲线找台阶 | 压缩字段、拆分热/冷数据 | 上线前跑一次工作集曲线 |
| miss 很高但算法明明 O(n) | 每行只用 4 B（§07.4） | `L1 miss ÷ 迭代` 是否 ≈ 1 | 结构体拆开（AoS→SoA）、紧凑编码 | 热结构体 `sizeof` 进 CI 断言 |
| 多线程后更慢 | 伪共享：两个计数器同一行（§07.10、`base/13`） | `perf c2c` 看 HITM；或本机用两线程自增对比 | 按 64 B 对齐 + padding | 共享结构体每个写者独占一行 |
| 大页开了却没效果 | `madvise` 在首次写之后才调（§07.4） | 读 `smaps` 的 `AnonHugePages` 是否为 0 | 分配后立刻 `madvise`，再 `memset` | 用 `smaps` 验证，不信「已开启」 |
| 容器里性能比物理机差 40% | NUMA / cpuset 的 mems 与 cpus 不匹配（§07.9） | `numastat` 的 `other_node` 是否非 0 | `cpuset.mems` 与 `cpuset.cpus` 同节点 | 部署模板里成对设置 |

### 伪共享：本机的实测与「为什么它难测」

两个线程各跑 2000 万次自增，计数器放在同一行 vs 各占一行：

```
同一 cache line 两个计数器:    25.8 ms    0.65 ns/自增
各占一条 cache line     :    12.8 ms    0.32 ns/自增
```

**2.0 倍**。但在本机（2 vCPU 共享宿主、会被调度走）连跑五次会得到 0.65/2.32/0.65/0.86/0.67 这样的抖动——**伪共享的绝对值不可靠，比值的方向可靠**（同一行永远更慢）。真正的定位工具是 `perf c2c`（看 HITM：一行被两个核同时持有且其中一个要写），本机没有该命令，只能靠「按行对齐前后对比」。机制与屏障 → `base/13`，工程形态 → ◆`base/19`。

## 07.13 一页速记

```
【一句话】快慢 = 数据在第几层 + 相邻访问隔多远。代码好不好看，排第三。

【本机这张表】（3.2 GHz，1.5 ns = L1）
  寄存器 0.3ns | L1 1.5ns(4.9cyc) | L2 3.9ns | L3 12ns | DRAM 93ns(300cyc)
  SSD 4K 随机 28µs | 回环 RTT 8.2µs | 同城 RTT 0.83ms | HDD 10ms
  带宽：L1 91 | L2 80-100 | L3 55-70 | DRAM 18.4 GB/s

【记忆锚】L1 = 1 秒 → DRAM = 1 分钟 → SSD = 5 小时 → HDD = 77 天

【三个边界】64 B（行）、4 KiB（页）、16 MiB（LLC）
  跨过 64 B：一行只用一个元素，有效带宽 ÷(64/用到的字节)
  跨过 4 KiB：TLB 漏，每次多走 3-4 级页表
  跨过 16 MiB：命中率断崖，延迟从 12 ns 变 93 ns

【内存墙】18.4 B/ns ÷ 12.8 指令/ns = 1.44 B/指令；吃 8 B 就差 5.5 倍
  Little：B = MLP × 64 B ÷ 延迟；要 18.4 GB/s 就要 27 条行在飞

【四条改法】（同一个式子的四个变量）
  分块 → 降延迟 | 批处理 → 提 MLP | 少指针 → 提 MLP | 紧凑化 → 提每行有效率

【两个反直觉】
  大步长基准的谷底是假的（活跃地址变少，反而全命中 L1）
  链表慢不只是 miss，是 miss 之间不能并发（MLP=1 vs 8-12）
```

## 07.14 自检 3 题

**Q1.** 一台机器的 L1 是 1.5 ns、DRAM 是 93 ns。一段代码每次迭代读 1 个 `long`（8 B），共 1 亿次，全部 miss 到 DRAM，且**迭代之间无依赖**。理论上它最快多久跑完？如果改成有依赖的指针追逐呢？两个答案差多少倍，差在哪个物理量上？

<details><summary>答案</summary>

**无依赖**：1 亿次独立 load 可以同时在飞。以 §07.8 的 Little 定律，本机实测能维持 MLP ≈ 27 条行在飞，带宽 18.4 GB/s。总数据量 = 1e8 × 8 B = 800 MB → `800 MB ÷ 18.4 GB/s ≈ 43 ms`。

**有依赖**：每次 load 要等上一次回来（MLP = 1），`1e8 × 93 ns ≈ 9.3 s`。

**差 216 倍**。这个差距**全部来自 MLP**（并发在途的请求数），与「命中率」「带宽」都无关——两条路径的 miss 数一模一样，都是 1 亿次。所以「miss 了多少次」不是性能指标，**「miss 之间能不能重叠」才是**。这也是为什么链表 → 数组的收益远大于任何指令级优化。

</details>

**Q2.** 有人把一个大数组的遍历从 `for (i…) sum += a[i]` 改成 `for (i…) sum += a[i*64]`（步长 64 个元素 = 512 B），发现**变快了**。请给出两种完全不同的解释，并说明怎么用实验区分它们。

<details><summary>答案</summary>

**解释 A（假象）**：访问次数没变、但**足迹**变了。如果数组只有 1 MB，步长 512 B 时活跃地址只剩 2048 个，仍然全在 L1/L2 内，而**每次迭代的加法次数相同**，所以它不是变快，而是**你量错了对象**——变快的是「每个字节的触及成本」，总量没变。

**解释 B（真实）**：原来的 `a[i]` 是 4 B/元素，SIMD 化后每行要用 64 B；改成 `a[i*64]` 后每行只用 4 B，**触及带宽 ÷16**，如果瓶颈在带宽（工作集远大于 L3），确实会变快 16 倍以内。

**怎么区分**：把**总触及数据量**算出来对比（`访问次数 × 行大小` 的近似），而不是只看墙钟。再补一组「固定总访问次数、只变步长」的扫描（像 §07.5 那样控制 N），如果曲线在步长接近缓冲区大小时**回升**，就是解释 A 的假谷底；如果随步长单调下降到平台，才是解释 B。**判据是「足迹」和「次数」必须有一个被固定住。**

</details>

**Q3.** 一台 2 路服务器，服务 A 用 `taskset -c 0` 绑在节点 0 的一个核上，内存却由启动时在节点 0 的初始化线程分配；服务 B 由容器启动，`cpuset.cpus=0` 但 `cpuset.mems=1`。两者代码一样。为什么 B 的 P99 会明显更差？给出两条命令确认，并说明为什么「加大内存」和「换更快的盘」都救不了。

<details><summary>答案</summary>

**根因**：B 的 CPU 在节点 0、内存在节点 1，**每次 miss 都要跨节点**。跨节点延迟是本地的 1.4–2.2 倍（93 ns → 140–200 ns），带宽约 1/2。代入 Little 定律，同样的 MLP 下带宽减半，**P99 直接翻倍**。

**两条确认命令**：① `numastat -p <pid>`（或 `/sys/devices/system/node/node*/numastat`），看 `other_node` 是否显著非 0；② `cat /proc/<pid>/numa_maps`，看各段的 `N0=` / `N1=` 页数分布。

**为什么加大内存/换盘无效**：这是**延迟**问题，不是容量或 IOPS 问题。内存加再多，跨节点的物理链路长度不变；换盘只影响 miss 之后的下一层（28 µs 级），而这里的瓶颈是 40–100 ns 级的额外交互——**改善了一个不在关键路径上的量**。正确的修法是让 `cpuset.mems` 与 `cpuset.cpus` 落在同一节点（本机这种单节点机器上则天然不存在此问题）。

</details>
